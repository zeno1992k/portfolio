## Server Rendering

서버 렌더링(Server-Side Rendering, SSR)은 서버에서 React 컴포넌트를 실행해 HTML을 만들고, 그 HTML을 응답으로 보내는 방식입니다. 브라우저는 JavaScript가 실행되기 전에 이미 완성된 화면을 받습니다.

클라이언트 렌더링(CSR)과 첫 응답을 비교하면 차이가 분명합니다.

```html
<!-- CSR: 빈 껍데기 + 스크립트 -->
<div id="root"></div>
<script src="/main.js"></script>

<!-- SSR: 렌더된 결과 + 스크립트 -->
<div id="root"><h1>상품 목록</h1><ul>...</ul></div>
<script src="/main.js"></script>
```

SSR의 전체 흐름은 다음과 같습니다.

1. 브라우저가 페이지를 요청한다.
2. 서버가 `react-dom/server`의 API로 컴포넌트를 HTML로 바꾼다.
3. 브라우저가 HTML을 받아 바로 화면에 그린다.
4. JavaScript 번들이 로드되고, React가 기존 HTML에 이벤트를 연결한다(Hydration).

- 서버에서 도는 코드는 브라우저가 아니라 Node.js 같은 서버 런타임에서 실행됩니다. 그래서 `window`, `document`가 없습니다.
- SSR은 React만의 기능이 아니라 렌더링 전략입니다. React는 렌더링 API(`react-dom/server`)를 제공하고, 라우팅과 데이터 로딩, 빌드는 Next.js 같은 프레임워크가 맡습니다(자세히는 24편).
- 서버에서 HTML을 만든 뒤에도 클라이언트는 같은 컴포넌트를 다시 실행해야 합니다. 그 이유가 Hydration입니다(아래 "Client Hydration").

## renderToString

`renderToString`은 React 노드를 HTML 문자열 하나로 돌려주는 서버 API입니다. `react-dom/server`에서 가져옵니다.

```jsx
import { renderToString } from 'react-dom/server'

app.get('/', (req, res) => {
  const html = renderToString(<App />)
  res.send(`<!doctype html>
<div id="root">${html}</div>
<script src="/client.js"></script>`)
})
```

- 시그니처는 `renderToString(reactNode, options?)`입니다. 옵션은 `identifierPrefix` 하나로, `useId`가 만드는 ID의 접두사입니다. 한 페이지에 루트가 여러 개일 때 충돌을 막으며, `hydrateRoot`에 넘기는 값과 같아야 합니다.
- 결과는 문자열입니다. 서버는 이 문자열을 응답에 넣어 보냅니다.
- 스트리밍과 데이터 대기를 지원하지 않습니다. 호출하면 곧바로 문자열을 반환하므로 필요한 데이터는 렌더 전에 가져와 props로 넘겨야 합니다.
- Suspense 지원이 제한적입니다. 컴포넌트가 중단되면 내용을 기다리지 않고 `fallback`을 HTML로 내보내며, 실제 내용은 클라이언트 코드가 로드된 뒤에 나타납니다.
- 이 문자열을 `hydrateRoot`로 이어받을 수 있습니다. 문자열에 감싸는 `div`의 안쪽에 공백이나 줄바꿈을 넣으면 Hydration 불일치가 생깁니다.
- 브라우저에서도 동작하지만 권장하지 않습니다. 번들만 커집니다. 브라우저 화면은 `createRoot`로 DOM에 렌더링합니다.

react.dev는 `renderToString`을 deprecated가 아니라 레거시로 분류합니다. 스트리밍이 필요한 환경에는 아래 API를 권합니다(자세히는 02편).

| 용도 | 실행 환경 | 대안 API |
|------|-----------|----------|
| 스트리밍 렌더 | Node.js | `renderToPipeableStream` |
| 스트리밍 렌더 | Deno·엣지(Web Streams) | `renderToReadableStream` |
| 정적 프리렌더 | Node.js | `prerenderToNodeStream` |
| 정적 프리렌더 | Deno·엣지(Web Streams) | `prerender` |

**흔한 실수:** `renderToString` 안에서 데이터를 기다릴 수 있다고 가정하는 것입니다. 비동기 데이터는 반환 시점까지 도착하지 않으므로 서버 HTML에 빠집니다.

## renderToStaticMarkup

`renderToStaticMarkup`은 React 노드를 상호작용이 없는 HTML 문자열로 돌려줍니다. 시그니처는 `renderToStaticMarkup(reactNode, options?)`이고 옵션은 `identifierPrefix`입니다.

```jsx
import { renderToStaticMarkup } from 'react-dom/server'

const html = renderToStaticMarkup(<Receipt order={order} />)
// 이메일 본문이나 정적 문서에 그대로 넣는다
```

- 결과 HTML은 Hydration할 수 없습니다. 클라이언트에서 `hydrateRoot`로 이어받을 의도가 있다면 쓰지 않습니다.
- 용도는 React를 정적 HTML 생성기로 쓰는 경우입니다. 이메일 본문, 완전히 정적인 페이지, 서버 응답에 담을 HTML이 해당합니다.
- Suspense 처리는 `renderToString`과 같습니다. 중단된 컴포넌트는 `fallback`을 HTML로 내보냅니다.
- 브라우저에서 쓰는 것은 권장하지 않습니다.

두 API는 한 줄로 구분합니다.

| 항목 | `renderToString` | `renderToStaticMarkup` |
|------|------------------|------------------------|
| 결과 | HTML 문자열 | HTML 문자열 |
| 뒤이은 Hydration | 가능 | 불가능 |
| 쓰는 곳 | 상호작용이 있는 앱의 초기 HTML | 이메일·정적 문서 |
| 클라이언트 JS 필요 | 필요 | 필요 없음 |

시험이나 면접에서는 "Hydration이 가능한가"로 두 API를 구분해 묻습니다. 상호작용이 있는 앱에는 `renderToString`(또는 스트리밍 API)과 `hydrateRoot`를 짝지어 씁니다.

## 초기 로딩

SSR의 가장 큰 효과는 첫 화면이 JavaScript 실행을 기다리지 않는다는 점입니다.

| 단계 | CSR | SSR |
|------|-----|-----|
| 1 | 빈 HTML 수신 | 렌더된 HTML 수신 |
| 2 | JS 번들 다운로드·실행 | 화면에 바로 표시(FCP) |
| 3 | 컴포넌트 실행, 데이터 요청 | JS 번들 다운로드·실행 |
| 4 | 화면 표시(FCP) | Hydration 완료, 상호작용 가능 |

- CSR은 JS가 실행되고 데이터가 도착해야 화면이 생깁니다. 그동안 사용자는 빈 화면이나 로딩 표시를 봅니다.
- SSR은 HTML이 도착한 순간 내용이 보이지만, Hydration이 끝나기 전에는 버튼이 눌리지 않습니다. 보이는 시점과 동작하는 시점이 갈립니다.
- 서버 데이터는 서버 안에서 가져오므로 브라우저가 API를 한 번 더 왕복하는 요청이 줄어듭니다.

### TTFB·FCP·TTI

초기 로딩은 세 지표로 비교합니다. 기준값은 web.dev 문서에 따릅니다.

| 지표 | 측정 대상 | 기준 |
|------|-----------|------|
| TTFB(Time to First Byte) | 탐색 시작부터 응답 첫 바이트가 도착할 때까지 | 0.8초 이하가 좋음, 1.8초 초과가 나쁨 |
| FCP(First Contentful Paint) | 탐색 시작부터 첫 콘텐츠(텍스트·이미지·SVG)가 그려질 때까지 | 1.8초 이하가 좋음, 3.0초 초과가 나쁨 |
| TTI(Time to Interactive) | 로드 후 입력에 안정적으로 반응할 수 있게 될 때까지 | 평균 모바일 기기에서 5초 미만을 권장 |

- 기준은 방문의 75번째 백분위수에 적용합니다.
- TTFB에는 리다이렉트, DNS, 연결, TLS, 서버 처리 시간이 모두 들어갑니다.
- TTI는 실험실(lab) 지표입니다. 이상치 요청과 긴 작업에 지나치게 민감해서 Lighthouse 10에서 제거되었습니다. web.dev는 대안으로 LCP, TBT, INP를 권합니다. SSR 설명에서 "TTI가 늦어진다"는 말은 Hydration 때문에 보이는 시점 이후에도 입력이 막힌다는 개념으로 이해합니다.

렌더링 방식별 경향은 다음과 같습니다.

| 방식 | TTFB | FCP | TTI |
|------|------|-----|-----|
| CSR | 빠름(최소한의 HTML) | 느림(JS에 의존) | 느림 |
| SSR | 느림(요청마다 생성) | 빠름 | 가변(JS 실행에 좌우) |

SSR은 서버가 HTML을 만드는 시간만큼 TTFB가 늘어나고, 그 대가로 FCP를 앞당깁니다. 스트리밍은 이 TTFB 부담을 줄입니다(자세히는 02편).

## SEO

SSR은 크롤러가 JavaScript를 실행하지 않고도 내용을 읽게 해 줍니다. 검색 엔진과 링크 미리보기 봇은 응답 HTML을 먼저 읽기 때문입니다.

- Google은 페이지를 크롤링한 뒤 렌더링 대기열에서 JavaScript를 실행하고 그 결과로 색인합니다. 렌더링이 지연될 수 있습니다.
- Google 문서는 서버 사이드 렌더링이나 프리렌더링이 "여전히 좋은 방법"이라고 설명합니다. 사용자와 크롤러 모두에게 더 빠르고, 모든 봇이 JavaScript를 실행하는 것은 아니기 때문입니다.
- 따라서 SSR이 SEO의 필수 조건은 아닙니다. Googlebot은 CSR 페이지도 렌더링합니다. 다만 다른 크롤러, 소셜 미리보기(제목·설명·이미지)처럼 JS를 실행하지 않는 소비자에게는 SSR 결과가 의미 있습니다.
- 페이지마다 고유한 `title`과 `meta description`이 있어야 합니다. 이런 태그를 서버 HTML에 담는 것이 권장 방식입니다. React 19는 컴포넌트에서 렌더한 `title`, `meta`, `link`를 `head`로 올려 주며, 이 기능은 스트리밍 SSR과 Server Components에서도 동작합니다.
- 로그인 뒤에서만 보이는 화면(관리자, 대시보드)은 검색에 노출되지 않으므로 SEO를 이유로 SSR을 택할 필요가 없습니다.

**흔한 실수:** 비동기 데이터가 서버 렌더링 결과에 빠진 채 배포하는 것입니다. SSR을 켰어도 데이터가 클라이언트에서만 로드되면 크롤러가 받는 HTML은 비어 있습니다. 로드 전 HTML에서 확인합니다.

## Client Hydration

Hydration은 서버가 만든 HTML에 React가 이벤트 핸들러와 상태를 연결해 상호작용 가능하게 만드는 과정입니다. 클라이언트 진입점에서 `hydrateRoot`를 호출합니다.

```jsx
import { hydrateRoot } from 'react-dom/client'

hydrateRoot(document.getElementById('root'), <App />)
```

- 클라이언트는 서버와 같은 컴포넌트를 다시 렌더링하면서 기존 DOM과 맞춰 봅니다. DOM을 새로 만들지 않고 재사용합니다.
- 서버 렌더링된 HTML에 `createRoot`를 쓰면 안 됩니다. 기존 HTML을 버리고 DOM을 처음부터 다시 만듭니다. `hydrateRoot`는 기존 DOM 노드를 재사용하므로 포커스, 스크롤 위치, 사용자가 입력한 값이 유지됩니다.
- 서버와 클라이언트의 출력이 같아야 합니다. 다르면 불일치 경고가 나옵니다.
- 서버에서 `renderToString`에 준 컴포넌트와 클라이언트에서 `hydrateRoot`에 준 컴포넌트, 그리고 `identifierPrefix`가 같아야 합니다.
- 클라이언트 번들에는 서버에서 이미 한 번 실행한 컴포넌트의 코드가 그대로 포함됩니다. 이 중복은 SSR 단점의 근거입니다. 서버에서만 실행되는 컴포넌트로 번들을 줄이는 방법은 04편에서 다룹니다.

`hydrateRoot`의 옵션, 불일치의 원인, 해결은 03편에서 자세히 다룹니다.

## 장점

SSR의 장점은 초기 화면 속도, 크롤러 노출, 서버 자원 활용으로 정리합니다.

| 장점 | 이유 |
|------|------|
| 빠른 FCP | HTML이 도착하면 JS 실행 없이 내용이 그려진다 |
| 크롤러·미리보기 대응 | 응답 HTML에 내용과 메타 정보가 있다 |
| 저사양 기기 부담 감소 | 첫 화면 렌더링 작업을 서버가 처리한다 |
| 서버에서 데이터 접근 | 비밀 키와 내부 API를 브라우저에 노출하지 않고 데이터를 가져온다 |
| 개인화 | 요청 정보(쿠키·헤더)를 보고 사용자별 HTML을 만들 수 있다 |

web.dev는 SSR이 큰 JS 번들을 보내지 않고도 첫 화면을 보여 주고, 메인 스레드의 막힘을 줄이며, 개인화를 지원한다고 정리합니다.

## 단점

SSR은 서버 비용, 느려지는 TTFB, 복잡한 코드, Hydration 비용을 치릅니다.

| 단점 | 이유 |
|------|------|
| 서버 비용 | 요청마다 렌더링하므로 서버 연산이 필요하다. 정적 호스팅만으로는 안 된다 |
| 느린 TTFB | 서버가 HTML을 다 만들어야 응답이 시작된다. 정적 파일이나 CDN 캐시보다 느리다 |
| 보이지만 안 눌리는 구간 | HTML이 보여도 JS가 로드되고 Hydration이 끝나야 상호작용한다 |
| 중복 코드와 데이터 | 서버와 클라이언트가 같은 코드를 실행하고, 데이터도 서버 HTML과 직렬화한 상태로 이중 전송된다 |
| 환경 제약 | 서버에 `window`가 없어서 브라우저 API를 쓰는 코드가 깨진다(아래) |
| 일치 규칙 | 서버와 클라이언트가 같은 결과를 내야 해서 시간·난수 코드가 까다롭다(03편) |

web.dev는 보이지만 입력에 반응하지 않는 구간을 "uncanny valley"라 부르고, SSR이 UI 설명과 직렬화된 데이터, 구현 코드를 서버와 클라이언트에 이중으로 담아 "하나의 앱을 두 값에" 보내는 구조가 된다고 지적합니다. 스트리밍과 선택적 Hydration이 이 문제를 줄이는 방법입니다(자세히는 02편).

## Browser-only API

서버에는 브라우저 전역 객체가 없습니다. `window`, `document`, `localStorage`, `navigator`, `matchMedia`를 렌더링 중에 읽으면 서버에서 ReferenceError가 납니다.

```jsx
function Theme() {
  const dark = window.matchMedia('(prefers-color-scheme: dark)')
  // 서버: ReferenceError: window is not defined
  return <p>{dark.matches ? '다크' : '라이트'}</p>
}
```

원인은 렌더링 중 코드가 서버에서도 실행되기 때문입니다. 초기값 계산(`useState(() => localStorage.getItem(...))`)도 렌더링 중 코드라서 같은 문제가 있습니다.

해결책은 상황에 따라 다릅니다.

| 방법 | 설명 | 주의 |
|------|------|------|
| Effect 안에서 읽기 | Effect는 클라이언트에서만 실행된다 | 첫 렌더는 서버와 같은 기본값이어야 한다 |
| `useSyncExternalStore` | 서버용 스냅샷을 따로 지정한다 | 03편 |
| Suspense와 에러로 서버 건너뛰기 | 서버에서 던지고 `fallback`을 HTML로 내보낸 뒤 클라이언트가 렌더 | 02편 |
| `browser()` | `use(browser())`로 서버에서만 중단시킨다. 19.3부터 정식(Stable) | 클라이언트 컴포넌트에서, Suspense 안에서만 쓴다 |

```jsx
useEffect(() => {
  const saved = localStorage.getItem('theme')
  if (saved) setTheme(saved)
}, [])
// 서버 HTML과 첫 클라이언트 렌더는 기본값, 이후 갱신
```

- `typeof window !== 'undefined'`로 렌더링 분기를 나누면 서버 출력과 클라이언트 첫 렌더가 달라져 불일치가 생깁니다. react.dev는 이를 불일치의 흔한 원인으로 꼽습니다.
- 브라우저 전용 라이브러리(차트, 에디터, 지도)는 서버에서 import만 해도 터질 수 있습니다. 서버 렌더링에서 제외하거나 Effect 안에서 불러옵니다.
- `useEffect`는 서버에서 실행되지 않으므로 서버 쪽 DOM 접근을 숨기는 가장 단순한 방법입니다. 대신 서버 HTML에는 그 값이 반영되지 않습니다.

상세한 불일치 처리는 03편에서 다룹니다.

## CSR·SSR·SSG·ISR 비교

렌더링 시점을 기준으로 네 방식을 비교합니다.

| 항목 | CSR | SSR | SSG | ISR |
|------|-----|-----|-----|-----|
| HTML 생성 시점 | 브라우저에서 실행 시 | 요청마다 서버에서 | 빌드 때 한 번 | 빌드 때 + 주기적·요청 시 재생성 |
| TTFB | 빠름 | 느림 | 빠름(CDN) | 빠름(캐시된 페이지) |
| FCP | 느림 | 빠름 | 빠름 | 빠름 |
| 최신 데이터 | 항상 최신(클라이언트 요청) | 요청 시점 최신 | 빌드 시점 데이터 | 갱신 주기만큼 오래될 수 있음 |
| 서버 필요 | 정적 호스팅 | 서버 필수 | 정적 호스팅 | 재생성할 서버·플랫폼 |
| 개인화 | 클라이언트에서 처리 | 쉬움 | 어려움 | 어려움 |
| 적합한 곳 | 로그인 뒤 앱, 대시보드 | 개인화된 공개 페이지 | 블로그, 문서, 마케팅 | 자주 바뀌지만 요청마다 새로 만들 필요는 없는 상품·글 목록 |

- SSG(Static Site Generation)는 빌드 때 모든 URL의 HTML을 미리 만들어 둡니다. 정적 호스팅과 CDN에 올릴 수 있고, 개인화나 동적 URL 생성에는 맞지 않습니다. React의 `prerender` API가 이 용도입니다(자세히는 02편).
- ISR(Incremental Static Regeneration)은 React가 아니라 Next.js의 기능입니다. 정적 페이지를 캐시로 서빙하다가 `revalidate` 시간이 지난 뒤 첫 요청에 낡은 페이지를 그대로 돌려주고, 백그라운드에서 새 페이지를 만들어 교체합니다. 전체를 다시 빌드하지 않고 정적 콘텐츠를 갱신하는 방식입니다. Next.js 문서는 정적 내보내기(Static Export)에서는 ISR을 지원하지 않는다고 밝힙니다.
- 한 앱 안에서 페이지마다 방식을 섞는 것이 일반적입니다. 마케팅 페이지는 SSG, 상품 목록은 ISR, 마이페이지는 CSR 또는 SSR을 택하는 식입니다. 프레임워크별 선택은 24편에서 다룹니다.
- 렌더링 방식 선택 기준은 데이터 변경 빈도, 개인화 여부, SEO 필요, 서버 운영 부담입니다.

## 핵심 정리

- SSR은 서버에서 컴포넌트를 HTML로 렌더링해 보내고, 브라우저는 JS 실행 전에 완성된 화면을 받습니다.
- `renderToString`은 Hydration할 수 있는 HTML 문자열을, `renderToStaticMarkup`은 Hydration할 수 없는 정적 HTML 문자열을 만듭니다. 둘 다 스트리밍과 데이터 대기를 지원하지 않는 레거시 API입니다.
- SSR은 FCP를 앞당기고 크롤러 대응에 유리하지만, TTFB가 늘고 서버 비용이 들며, 보이는 시점과 동작하는 시점 사이에 간격이 생깁니다.
- 서버 HTML에는 `hydrateRoot`로 이어받습니다. `createRoot`는 기존 HTML을 버립니다.
- 서버에는 `window`와 `document`가 없어서 렌더링 중 브라우저 API를 읽으면 오류가 나며, Effect나 `useSyncExternalStore`, `browser()`로 피합니다.
- CSR·SSR·SSG·ISR은 HTML을 만드는 시점이 달라서 TTFB, 최신성, 서버 부담이 다릅니다.

이 편은 앞선 편들의 부품을 한 앱의 구조로 배치하는 방법을 다룹니다. 기능 단위 폴더의 세부 규칙은 14편, 데이터 화면의 쿼리 설계는 17편에서 다뤘습니다. 코드는 Vite 기반 SPA에 React Router 데이터 모드와 TanStack Query를 쓴다고 가정합니다. 프레임워크가 라우팅·서버 렌더링·배포를 맡는 구조는 24편에서 비교합니다.

## App Shell

App Shell은 라우트가 바뀌어도 유지되는 앱의 뼈대입니다. 진입점에서 Provider를 쌓고, 라우터를 렌더하며, 헤더·내비게이션 같은 공통 레이아웃을 담습니다. 화면별 내용은 이 안의 자리에 끼워집니다.

```tsx
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <ThemeProvider>
        <RouterProvider router={router} />
      </ThemeProvider>
    </QueryClientProvider>
  </StrictMode>,
)
```

- Provider는 안쪽이 바깥쪽에 의존하는 순서로 쌓습니다. 라우터 안의 화면이 쿼리 캐시와 테마를 쓰므로 둘이 라우터 바깥에 있습니다.
- 전역 Provider는 앱 전체가 필요로 하는 것만 둡니다. 한 기능만 쓰는 Context는 그 기능의 최상위에 둡니다(자세히는 중급 01편).
- 진입점 파일은 조립만 합니다. 데이터 호출, 권한 판단, 화면 로직을 넣지 않습니다.
- 셸의 로딩은 첫 화면 성능과 직결됩니다. 셸이 의존하는 데이터(현재 사용자 등)가 늦으면 모든 화면이 늦게 열립니다. 셸에는 즉시 그릴 수 있는 뼈대만 두고 나머지는 경계로 감쌉니다.

**흔한 실수:** 모든 Provider를 한 컴포넌트에 몰아 넣고 그 안에서 값을 계산하는 것입니다. 값이 바뀌면 Provider 하위 전체가 다시 렌더됩니다(자세히는 중급 01편).

## Page / Layout / Feature / UI

코드를 역할별 네 층으로 나눕니다. 각 층은 자기 아래 층만 import합니다.

| 층 | 역할 | 알고 있는 것 |
|----|------|--------------|
| Page | 라우트 하나에 대응하는 화면 조립 | 라우트 파라미터, Feature 조합 |
| Layout | 여러 Page가 공유하는 틀(헤더, 사이드바) | 내비게이션 구조, `Outlet` 위치 |
| Feature | 기능 하나의 UI·Hook·API·타입 | 도메인 규칙, 서버 통신 |
| UI | 도메인을 모르는 재사용 컴포넌트 | 오직 props |

```
src/
  app/        진입점, Provider, 라우터 정의
  pages/      Page와 Layout
  features/   todos/ auth/ billing/ ...
  shared/     ui/ api/ lib/ config.ts
```

- 의존 방향은 `app → pages → features → shared`입니다. `features` 안의 한 기능이 다른 기능의 내부 파일을 직접 import하지 않고, 공개한 진입점으로만 접근합니다(자세히는 14편).
- Page는 얇게 유지합니다. 데이터 호출과 조작은 Feature에 두고 Page는 조립과 레이아웃만 합니다. Page에 로직이 쌓이면 재사용과 테스트가 어려워집니다.
- UI 층은 `Button`, `Dialog`, `Table`처럼 도메인 단어가 없는 것만 담습니다. `TodoCard`는 도메인을 알므로 Feature에 속합니다.
- 두 기능이 모두 쓰는 코드는 `shared`로 내리고, 한 기능만 쓰면 그 기능 안에 둡니다. 위로 올려 해결하지 않습니다.

**흔한 실수:** 처음부터 모든 컴포넌트를 `shared/components`에 두는 것입니다. 도메인 로직이 섞인 컴포넌트가 공용 폴더에 쌓이면 어느 기능의 변경이 어디에 영향을 주는지 알 수 없게 됩니다.

## Routing

라우트 구조가 곧 레이아웃 계층입니다. React Router 데이터 모드는 라우트 객체의 배열로 구조를 선언하고, 부모 라우트가 `Outlet`으로 자식을 그립니다. `path`가 없는 라우트는 URL에 영향을 주지 않는 Layout 라우트입니다.

```tsx
// 인증이 필요한 화면을 모은 Layout 라우트
const authedRoutes = {
  loader: requireAuth,
  Component: AuthedLayout,
  children: [
    { index: true, Component: DashboardPage },
    { path: 'todos', lazy: () => import('./pages/todos') },
  ],
}
```

```tsx
const router = createBrowserRouter([
  {
    Component: AppShell,
    ErrorBoundary: RootError,
    children: [
      { path: 'login', Component: LoginPage },
      authedRoutes,
    ],
  },
])
```

- 인증이 필요한 화면을 하나의 Layout 라우트 아래에 모으면, 인증 검사를 그 라우트 한 곳에 둘 수 있습니다. 화면마다 검사를 복사하지 않습니다.
- `loader`는 라우트가 렌더되기 전에 실행됩니다. 로더에서 `throw redirect('/login')`으로 이동시킬 수 있습니다.
- `lazy`는 라우트의 코드를 해당 라우트에 처음 진입할 때 불러옵니다. 라우트 단위 분할이 가장 효과 큰 분할 지점입니다(자세히는 중급 12편).
- 라우트의 `ErrorBoundary`는 자신과 자식 라우트에서 난 에러를 잡고, 가장 가까운 경계가 처리합니다. 루트에는 반드시 경계를 둡니다.
- URL에 둘 상태(검색어, 페이지, 선택한 id)와 라우트 파라미터 설계는 중급 29편을 따릅니다.

**흔한 실수:** 라우트 정의 파일이 모든 Page를 정적 import하는 것입니다. 첫 로딩에 모든 화면의 코드가 들어옵니다.

## Authentication

인증은 요청한 사용자가 누구인지 확인하는 일입니다. 확인은 서버가 합니다. 클라이언트의 역할은 다음 세 가지입니다.

- 로그인 요청을 보내고 서버가 준 인증 수단(쿠키나 토큰)을 보관한다.
- 매 요청에 인증 수단이 실려 가게 한다.
- 현재 사용자 정보를 앱에서 읽을 수 있게 한다.

현재 사용자는 서버가 원본을 가진 데이터라서 서버 상태입니다. `['me']` 같은 쿼리로 가져오고, 로그아웃하면 쿼리 캐시를 비웁니다. 사용자 정보를 `useState`나 전역 스토어에 복사하면 서버 쪽 변경과 어긋납니다.

- 로그인 후 원래 가려던 주소로 보내려면 로그인 페이지로 이동할 때 원래 경로를 검색 파라미터로 넘깁니다. 이 값은 검증 없이 `redirect`에 쓰지 않습니다. 외부 주소로 보내는 오픈 리디렉트가 됩니다(자세히는 23편).
- 앱이 처음 열릴 때는 "로그인 여부를 아직 모르는 상태"가 있습니다. 로그인 여부 조회가 끝나기 전에 로그인 페이지로 보내면 안 됩니다.
- 인증 상태 확인을 라우트 로더나 Layout에 두면 화면마다 반복하지 않습니다(앞 절의 `requireAuth`).

```ts
async function requireAuth() {
  const user = await fetchMe() // 401이면 null
  if (!user) throw redirect('/login')
  return user
}
```

### 인증 흐름

인증 수단은 크게 두 가지입니다.

| 구분 | 세션 쿠키 | JWT(Bearer 토큰) |
|------|-----------|-------------------|
| 서버가 상태를 | 보관한다(세션 저장소) | 보관하지 않아도 된다 |
| 클라이언트가 보관 | 브라우저가 쿠키로 자동 전송 | 코드가 헤더 `Authorization`에 실어 보냄 |
| JS에서 접근 | `HttpOnly`면 불가 | 저장 위치에 따라 가능 |
| 무효화 | 서버에서 세션 삭제 | 만료까지 유효(별도 장치 필요) |

세션 쿠키 방식의 흐름은 다음과 같습니다.

1. 로그인 요청에 서버가 세션 ID를 쿠키로 응답한다(`Set-Cookie`).
2. 브라우저가 이후 요청에 쿠키를 자동으로 붙인다.
3. 서버가 세션 ID로 사용자를 확인한다.

- 인증용 쿠키에는 `HttpOnly`(JS의 접근 차단), `Secure`(HTTPS에서만 전송), `SameSite`(교차 사이트 요청 제한)를 설정합니다.
- 프런트엔드와 API의 출처가 다르면 `fetch`에 `credentials: 'include'`를 줘야 쿠키가 전송됩니다.
- 쿠키는 브라우저가 자동으로 보내므로 CSRF에 대비해야 합니다(자세히는 23편).

JWT는 `header.payload.signature` 세 부분을 마침표로 이은 토큰입니다. 기본은 서명만 하고 암호화하지 않으므로 payload는 누구나 읽을 수 있습니다. 비밀 값을 넣지 않습니다. `exp` 클레임이 만료 시각입니다.

액세스 토큰은 수명을 짧게 하고, 만료되면 리프레시 토큰으로 새 액세스 토큰을 받는 방식으로 재발급합니다. 리프레시 토큰은 인증 서버에만 보내는 용도입니다(RFC 6749).

```ts
let refreshing: Promise<void> | null = null

async function refreshOnce() {
  refreshing ??= doRefresh().finally(() => {
    refreshing = null
  })
  return refreshing
}
// 401 응답 → refreshOnce() → 원래 요청을 한 번만 재시도
// 재발급 실패 → 로그아웃 후 /login
```

- 동시에 여러 요청이 401을 받아도 재발급은 한 번만 하도록 진행 중인 Promise를 공유합니다. 아니면 요청마다 재발급을 시도해 토큰이 서로 무효화될 수 있습니다.
- 원래 요청의 재시도는 한 번만 합니다. 재시도해도 401이면 로그아웃입니다. 쿼리의 자동 재시도(`retry`)에 401을 맡기면 안 됩니다(17편).
- 토큰을 어디에 저장할지(HttpOnly 쿠키, 메모리, localStorage)는 XSS와 CSRF 위험이 서로 다르므로 23편에서 비교합니다.

**흔한 실수:** JWT를 디코딩해서 얻은 역할이나 만료 시각으로 접근을 허용하는 것입니다. 클라이언트 쪽 판단은 화면 제어용이고, 허용 여부는 서버가 매 요청마다 검증합니다.

## Authorization

인가는 인증된 사용자가 그 일을 할 수 있는지 정하는 일입니다. 요청의 응답 코드로 구분합니다.

| 상태 | 뜻 | 화면의 처리 |
|------|----|-------------|
| 401 | 인증이 없거나 유효하지 않음 | 재인증(토큰 재발급 또는 로그인 이동) |
| 403 | 인증은 됐지만 권한이 없음 | 권한 없음 안내. 재시도하지 않음 |

- 권한 검사는 서버가 강제합니다. 클라이언트의 검사는 버튼을 숨기거나 화면을 막는 UX 장치이고 보안 경계가 아닙니다. 누구나 개발자 도구로 요청을 직접 보낼 수 있습니다.
- 권한 정보는 서버가 내려 준 값(`['me']` 응답의 역할이나 권한 목록)을 씁니다. 클라이언트에 역할 이름과 권한을 하드코딩해 두면 서버 정책과 어긋납니다.
- 권한 판단 코드는 한곳에 모읍니다. 컴포넌트마다 `user.role === 'admin'`을 쓰지 않습니다.

### 권한별 라우트·UI

라우트는 Layout 라우트의 로더에서 막고, UI 요소는 권한 확인 Hook이나 컴포넌트로 가립니다.

```tsx
function useCan(permission: string) {
  const { data: me } = useMe()
  return me?.permissions.includes(permission) ?? false
}

function Can({ permission, children }: CanProps) {
  return useCan(permission) ? children : null
}
// <Can permission="todo:delete"><DeleteButton /></Can>
```

- 라우트 단위 제한은 해당 Layout 라우트 로더에서 권한이 없으면 403 페이지로 보냅니다. 메뉴에서만 숨기고 주소로 들어오는 경로를 막지 않으면 접근이 가능합니다.
- 권한 없는 버튼은 숨길지 비활성화할지 선택합니다. 있다는 사실 자체를 알려도 되면 비활성화하고 이유를 안내하고, 그렇지 않으면 숨깁니다.
- 서버가 403을 돌려주는 경우를 항상 처리합니다. 권한이 화면이 열린 뒤에 바뀔 수 있고, 클라이언트의 권한 정보가 낡아 있을 수 있습니다.

**흔한 실수:** 권한 없는 사용자에게 메뉴만 숨기고 라우트와 API 호출은 막지 않는 것입니다. 화면에서 안 보일 뿐 주소를 직접 입력하면 열립니다.

## API Layer

API 층은 서버와의 통신을 한곳에 모은 계층입니다. 컴포넌트는 `fetch`를 직접 호출하지 않고 이 층의 함수를 거칩니다. 기반 클라이언트 하나와, 기능별 엔드포인트 함수로 나눕니다.

```ts
export class HttpError extends Error {
  constructor(public status: number, message: string) {
    super(message)
  }
}
```

```ts
export async function api<T>(
  path: string,
  init?: RequestInit,
) {
  const res = await fetch(config.apiUrl + path, {
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
    ...init,
  })
  if (!res.ok) {
    throw new HttpError(res.status, res.statusText)
  }
  return (await res.json()) as T
}
```

- `fetch`는 404나 500에도 reject하지 않습니다. `res.ok`를 확인해 직접 에러를 던져야 호출한 쪽이 에러로 받습니다.
- 에러를 `HttpError` 같은 하나의 형태로 통일하면 상태 코드로 분기하는 코드(재시도 여부, 401 처리)를 한곳에서 씁니다.
- 기본 URL, 공통 헤더, 인증 처리(401 시 재발급)는 이 클라이언트가 담당합니다. 기능 코드는 알지 못합니다.
- 기능별 함수는 도메인 이름으로 만듭니다. 반환 타입은 도메인 타입입니다.

```ts
export const getTodos = (f: Filters) =>
  api<Page<Todo>>(`/todos?${toSearch(f)}`)

export const patchTodo = (id: string, body: Body) =>
  api<Todo>(`/todos/${id}`, {
    method: 'PATCH',
    body: JSON.stringify(body),
  })
```

- 응답은 타입 단언만으로는 런타임에 검증되지 않습니다. 서버를 완전히 믿을 수 없는 경계라면 스키마로 검증합니다(자세히는 중급 31편).
- API 층에는 React가 없습니다. Hook이나 컴포넌트를 import하지 않으므로 단위 테스트가 쉽고 다른 환경에서도 재사용됩니다.

**흔한 실수:** 컴포넌트마다 `fetch`와 `res.json()`을 직접 쓰는 것입니다. 기본 URL이 바뀌거나 인증 방식이 바뀌면 모든 호출을 고쳐야 합니다.

## State Layer

상태 층에서는 값마다 어디에 둘지 먼저 정합니다. 위치는 값의 성격이 정합니다.

| 값의 성격 | 위치 |
|-----------|------|
| 서버가 원본인 데이터 | 서버 상태 계층(쿼리 캐시) |
| 공유하고 복원할 화면 조건(검색어, 페이지, 탭) | URL |
| 한 컴포넌트 안에서만 쓰는 값 | `useState` |
| 형제가 공유하는 값 | 가장 가까운 공통 부모로 끌어올림 |
| 많은 곳이 읽는 클라이언트 값(테마, 사이드바) | Context 또는 외부 스토어(Zustand) |
| 폼의 입력과 검증 | 폼 라이브러리(React Hook Form) |

- 위에서 아래로 내려가며 처음 해당하는 곳에 둡니다. 전역 스토어는 마지막 수단입니다.
- 어떤 값에서 계산할 수 있는 값은 State로 두지 않고 렌더 중에 계산합니다.
- 서버 데이터를 전역 스토어에 복사하는 것이 가장 흔한 설계 오류입니다. 원본이 둘이 되어 동기화 코드가 필요해집니다.
- 스토어를 쓴다면 기능별로 나눕니다. 하나의 거대한 스토어는 Feature 경계를 무너뜨립니다(자세히는 중급 22편, 24편).

**흔한 실수:** 인증 정보, 필터, 서버 응답, UI 열림 상태를 한 스토어에 모으는 것입니다. 성격이 다른 값이 같은 갱신 경로와 구독 비용을 공유합니다.

## Server State Layer

서버 상태 계층은 쿼리 클라이언트를 중심으로, 기능마다 쿼리 정의를 한곳에 둡니다. 키, 요청 함수, 캐시 정책을 `queryOptions`로 묶습니다.

```ts
export const todoQueries = {
  list: (f: Filters) =>
    queryOptions({
      queryKey: ['todos', 'list', f],
      queryFn: () => getTodos(f),
      staleTime: 30_000,
    }),
}
// useQuery(todoQueries.list(filters))
```

- `queryOptions`는 키와 요청 함수를 한 객체로 묶어, `useQuery`와 `queryClient`의 메서드가 같은 정의를 쓰게 합니다. 타입도 함께 추론됩니다.
- 쿼리 정의는 해당 Feature 폴더 안에 둡니다. Hook은 `useQuery(todoQueries.list(f))`를 감쌉니다.
- 앱 전체 기본값은 `QueryClient`에서 한 번 정합니다. 에러 알림처럼 전역 처리는 `QueryCache`의 `onError`에 둡니다. 쿼리당 한 번만 호출되고 컴포넌트 수와 무관합니다.

```ts
const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      if (query.state.data !== undefined) {
        toast.error('갱신 실패')
      }
    },
  }),
})
```

- 위 예는 이미 보여 주는 데이터가 있는데 백그라운드 갱신이 실패한 경우에만 알립니다. 처음부터 실패한 경우는 화면의 에러 UI가 담당합니다.
- 변경 뒤의 무효화 규칙도 이 계층에 모읍니다(자세히는 17편).

**흔한 실수:** 컴포넌트마다 `queryKey`를 문자열 배열로 직접 쓰는 것입니다. 철자 하나가 다르면 무효화가 빗나갑니다.

## Error Boundary

Error Boundary는 렌더 중에 던져진 에러를 잡아 대체 UI를 보여 주는 컴포넌트입니다. 클래스 컴포넌트로만 만들 수 있어서, 함수 컴포넌트에서는 `react-error-boundary` 같은 라이브러리를 씁니다(레거시 구현은 25편).

잡는 것과 못 잡는 것을 구분해야 합니다.

| 잡는다 | 잡지 못한다 |
|--------|-------------|
| 자식 컴포넌트의 렌더 중 에러 | 이벤트 핸들러 안의 에러 |
| `startTransition` 안에서 던진 에러 | 비동기 콜백(`setTimeout` 등)의 에러 |
| | 서버 렌더링 중의 에러 |
| | 경계 자신의 에러 |

배치는 세 단계로 나눕니다.

- 앱 루트(라우터의 최상위 `ErrorBoundary`): 예상하지 못한 에러의 마지막 방어선입니다. 전체 화면 에러 페이지를 보여 줍니다.
- 라우트: 한 화면의 실패가 셸과 다른 화면에 영향을 주지 않게 합니다. 라우트 객체의 `ErrorBoundary`로 둡니다. 가장 가까운 경계가 처리하고 처리하지 못하면 부모로 올라갑니다.
- 위젯: 대시보드의 한 카드가 실패해도 나머지는 살립니다.

```tsx
<ErrorBoundary
  fallbackRender={({ error, resetErrorBoundary }) => (
    <SectionError
      error={error}
      onRetry={resetErrorBoundary}
    />
  )}
  onError={(error) => reportError(error)}
>
  <Stats />
</ErrorBoundary>
```

- `onError`에서 모니터링 서비스로 보고합니다(자세히는 26편).
- 이벤트 핸들러와 비동기 에러는 직접 `try/catch`로 처리하거나, 상태에 담아 렌더 중에 던지는 방식으로 경계에 넘깁니다.
- `resetKeys`에 라우트 파라미터 같은 값을 넣으면 값이 바뀔 때 경계가 초기화됩니다. 한 화면에서 에러가 난 뒤 다른 항목으로 이동해도 에러 화면이 남는 일을 막습니다.
- 쿼리 에러를 경계로 올릴지 컴포넌트에서 처리할지는 에러의 성격으로 정합니다. 복구 불가능하거나 화면 전체를 못 그리는 에러는 경계로, 재시도 가능한 갱신 실패는 컴포넌트에서 처리합니다.

**흔한 실수:** 앱 전체에 경계 하나만 두는 것입니다. 작은 위젯 하나의 실패로 앱 전체가 에러 화면이 됩니다.

## Suspense Boundary

Suspense 경계는 하위 트리가 준비되기 전까지 `fallback`을 보여 주는 로딩 경계입니다. 다음 경우에만 작동합니다.

- `lazy`로 불러오는 컴포넌트 코드
- `use`로 읽는 Promise와 Suspense를 지원하는 데이터 소스
- 스트리밍 서버 렌더링

**Effect나 이벤트 핸들러 안에서 하는 데이터 패칭은 감지하지 못합니다.** 쿼리에서는 `useSuspenseQuery`를 쓰면 경계가 로딩을 처리합니다(자세히는 중급 11편, 28편).

```tsx
<Suspense fallback={<PageSkeleton />}>
  <Outlet />
</Suspense>
```

- 라우트 단위 분할(`lazy`)의 로딩은 Layout의 `Outlet` 둘레에 경계를 둡니다. 셸은 유지하고 본문만 fallback으로 바뀝니다.
- 경계를 중첩하면 느린 부분만 따로 로딩합니다. 빠른 부분은 먼저 보입니다. 경계가 너무 잘게 나뉘면 화면이 조각조각 튀어 나오므로, 함께 보여야 하는 것은 한 경계로 묶습니다.
- 같은 영역에서는 Error Boundary가 바깥, Suspense가 안쪽입니다. 에러면 에러 UI, 로딩 중이면 fallback이 보입니다.
- 이미 화면에 보이는 내용이 fallback으로 교체되는 것을 막으려면 이동을 `startTransition`으로 감쌉니다. 긴급하지 않은 갱신에서만 효과가 있습니다.
- `key`를 바꾸면 경계가 초기화되어 항목이 바뀔 때 fallback이 다시 보입니다.
- fallback은 스켈레톤으로 최종 모양을 닮게 만듭니다(자세히는 17편).

**흔한 실수:** Effect 안에서 데이터를 가져오는 컴포넌트를 Suspense로 감싸고 로딩이 표시되지 않는다고 하는 것입니다. 경계는 데이터 패칭을 알지 못합니다.

## Design System

디자인 시스템은 앱들이 함께 쓰는 시각·상호작용의 규칙과 컴포넌트 묶음입니다. 아키텍처 관점에서는 `shared/ui` 층의 원천입니다.

- 구성은 토큰(색, 간격, 글꼴), 프리미티브(Button, Dialog 같은 기본 컴포넌트), 조합 컴포넌트, 문서로 이뤄집니다. 상세는 22편에서 다룹니다.
- UI 층은 Feature를 import하지 않습니다. 의존이 거꾸로 되면 디자인 시스템을 다른 앱에서 쓸 수 없습니다.
- 접근성(키보드, 포커스, ARIA)을 프리미티브가 책임지면 사용하는 쪽에서 반복하지 않습니다(자세히는 13편).
- 앱이 하나면 `shared/ui` 폴더로 충분합니다. 앱이 둘 이상이 되고 팀이 나뉘면 패키지로 분리합니다.
- 스타일 값은 하드코딩하지 않고 토큰(CSS 변수)으로 참조합니다. 테마 전환과 일괄 변경이 가능해집니다.

**흔한 실수:** 디자인 시스템 컴포넌트에 도메인 용어나 서버 호출을 넣는 것입니다. 재사용이 막히고 변경 범위가 커집니다.

## Testing

계층마다 가장 싼 테스트로 검증합니다. 아래 계층일수록 빠르고 위로 갈수록 실제와 가깝습니다.

| 대상 | 테스트 | 도구 |
|------|--------|------|
| 순수 함수, API 층의 변환 | 단위 | Vitest |
| UI 컴포넌트, Hook | 컴포넌트 | Testing Library |
| Feature 한 개의 흐름 | 통합(네트워크는 모킹) | Testing Library, MSW |
| 로그인, 결제 같은 핵심 흐름 | E2E | Playwright |
| 접근성 | 쿼리, axe | Testing Library, axe |

- 아키텍처의 경계가 테스트의 경계입니다. API 층이 React와 분리되어 있으면 네트워크만 모킹해 Feature를 검증할 수 있습니다.
- 앱 Provider(쿼리 클라이언트, 라우터)를 감싼 `render` 헬퍼를 한 곳에 둡니다. 테스트마다 새 `QueryClient`를 만들어 캐시가 테스트 사이에 새지 않게 합니다(자세히는 중급 35편).
- 구현이 아니라 사용자가 보는 결과를 검증합니다. 역할과 레이블로 요소를 찾습니다(자세히는 20편).
- E2E는 핵심 흐름만 남깁니다. 모든 경우를 E2E로 만들면 느리고 불안정해집니다(자세히는 21편).

**흔한 실수:** 모든 테스트에서 같은 `QueryClient`를 재사용하는 것입니다. 앞 테스트의 캐시가 다음 테스트의 결과를 바꿉니다.

## Performance

성능은 측정으로 시작합니다. 핵심 지표와 좋음 기준(75번째 백분위)은 다음과 같습니다.

| 지표 | 측정 대상 | 좋음 기준 |
|------|-----------|-----------|
| LCP | 가장 큰 콘텐츠가 그려지는 시점 | 2.5초 이하 |
| INP | 입력에서 다음 화면 갱신까지의 반응 | 200밀리초 이하 |
| CLS | 레이아웃이 밀리는 정도 | 0.1 이하 |

아키텍처가 정하는 성능은 대부분 구조에서 나옵니다.

- 라우트 단위 코드 분할: 첫 로딩에 필요한 코드만 받습니다(`lazy`).
- 서버 요청: 쿼리 캐시와 중복 요청 제거, `staleTime` 조정, 필요한 데이터만 요청합니다. 부모가 데이터를 가져온 뒤 자식이 요청하는 워터폴을 만들지 않습니다.
- 렌더링 비용: 먼저 구조(State 위치, 경계)를 바로잡고, 그다음 측정으로 병목을 찾습니다. 메모이제이션은 마지막이며, 컴파일러가 자동으로 적용합니다(자세히는 07편).
- 긴 목록은 가상화하고, 입력과 무거운 렌더는 `useTransition`·`useDeferredValue`로 나눕니다(자세히는 중급 09편, 21편).
- CLS는 이미지·스켈레톤에 크기를 지정해 줄입니다.
- 번들 크기 분석과 Web Vitals 수집은 26편에서 다룹니다.

**흔한 실수:** 측정 없이 `useMemo`와 `React.memo`를 덧붙이는 것입니다. 병목이 렌더가 아니라 네트워크나 번들 크기라면 효과가 없고 코드만 복잡해집니다.

## 환경 설정 계층

환경 설정은 API 주소, 기능 플래그, 모니터링 키처럼 환경(개발·스테이징·운영)마다 달라지는 값을 코드 밖에서 주입하는 계층입니다. Vite는 `import.meta.env`로 이 값을 제공합니다.

| 값 | 내용 |
|----|------|
| `import.meta.env.MODE` | 실행 모드(`development`, `production`, 또는 `--mode`로 지정) |
| `DEV`, `PROD` | 개발·운영 여부 불리언 |
| `VITE_` 접두사 변수 | 클라이언트 코드에 노출되는 사용자 정의 값 |

- 클라이언트 번들에 노출되는 것은 `VITE_` 접두사 변수뿐입니다. 이 값은 빌드 결과물에 문자열로 들어가므로 비밀 값(API 비밀 키)을 두지 않습니다.
- `.env`, `.env.local`, `.env.[mode]`, `.env.[mode].local` 순으로 읽고 모드별 파일이 일반 파일을 덮어씁니다. `.local` 파일은 Git에 올리지 않습니다. `vite build --mode staging`으로 모드를 지정합니다.
- 모드와 `NODE_ENV`는 별개의 개념입니다.
- `import.meta.env`를 코드 곳곳에서 읽지 않고 설정 모듈 하나에서 읽어 검증하고 내보냅니다.

```ts
// shared/config.ts
const apiUrl = import.meta.env.VITE_API_URL
if (!apiUrl) throw new Error('VITE_API_URL is not set')

export const config = {
  apiUrl,
  isProd: import.meta.env.PROD,
}
```

- 값이 빠지면 앱이 시작될 때 바로 실패합니다. 요청이 나가는 시점에야 `undefined`를 발견하는 것보다 낫습니다.
- `vite-env.d.ts`에 `ImportMetaEnv`를 확장하면 변수 이름이 자동 완성되고 오타를 잡습니다.
- 빌드 시점에 값이 고정되므로 환경마다 다시 빌드해야 합니다. 같은 빌드를 여러 환경에 배포하려면 값을 런타임에 가져오는 별도 설정 파일을 두는 방식을 씁니다(자세히는 26편).

**흔한 실수:** 비밀 키를 `VITE_` 변수에 넣는 것입니다. 번들에 문자열로 들어가 누구나 볼 수 있습니다(자세히는 23편).

## 핵심 정리

- 앱은 `app → pages → features → shared` 방향으로만 의존하는 계층으로 나누고, Page는 조립만 하며 도메인을 모르는 코드만 UI 층에 둡니다.
- 라우트 구조가 레이아웃 계층이고, 인증 검사와 코드 분할은 Layout 라우트 단위로 한 곳에 둡니다.
- 인증은 세션 쿠키나 토큰으로 서버가 확인하고, 401은 재인증, 403은 권한 없음으로 구분하며, 클라이언트의 권한 검사는 UX 장치이고 허용은 서버가 강제합니다.
- 서버 통신은 API 층 한 곳, 서버 데이터는 쿼리 캐시, 화면 조건은 URL로 두고 서버 데이터를 전역 스토어에 복사하지 않습니다.
- Error Boundary는 앱·라우트·위젯 단계로 두고, Suspense 경계는 그 안쪽에서 로딩 단위를 정하며 Effect 안의 패칭은 감지하지 못합니다.
- 테스트는 계층마다 가장 싼 방법을 쓰고, 성능은 측정 뒤 구조부터 고치며, 환경 값은 `VITE_` 접두사 변수에 비밀을 두지 않고 설정 모듈 한 곳에서 읽습니다.

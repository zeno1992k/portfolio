## 작은 API Surface

API 표면(API surface)은 컴포넌트가 바깥에 약속하는 모든 것, 곧 props, 콜백, 슬롯, 내보내는 하위 컴포넌트입니다. 표면이 작을수록 사용법이 단순하고 바꿀 때 깨지는 곳이 적습니다.

- 표면에 올린 항목은 호출하는 쪽이 의존하게 되므로, 뺄 때는 모든 사용처를 고쳐야 하는 변경이 됩니다. 추가는 쉽고 제거는 어렵습니다.
- 지금 쓰는 사용처가 요구하는 것만 열어 둡니다. "혹시 필요할지 모르는" prop은 두지 않습니다.
- 스타일 값을 prop 하나씩 받지 않습니다(`paddingTop`, `borderColor` 같은 prop 나열). 정해진 선택지(Variant)나 `className`으로 받습니다.
- 내부 구현이 바뀌면 같이 바뀔 prop(내부 state의 이름, 내부 요소의 ref)은 노출하지 않습니다.
- react.dev는 props 전체를 넘기는 스프레드 문법을 "절제해서 쓰라"고 하며, 자주 쓰게 되면 컴포넌트를 쪼개고 자식을 JSX로 넘기라는 신호라고 설명합니다.

```tsx
// ❌ 표면이 넓다: 호출자가 내부 구조를 알아야 함
<Modal title="삭제" titleSize={18} showClose closeIcon={x}
  footerAlign="right" okText="확인" cancelText="취소" />

// ✅ 표면이 작다: 조각은 children으로 조립
<Modal title="삭제" onClose={close}>
  <p>정말 삭제할까요?</p>
</Modal>
```

## 명확한 Props

props는 이름과 타입만 보고 쓸 수 있어야 합니다.

- **이벤트 콜백**: react.dev의 관례대로 `on` 뒤에 대문자로 시작합니다(`onSelect`, `onClose`). 내장 요소와 달리 사용자 컴포넌트의 이벤트 prop은 이름을 자유롭게 지을 수 있으므로 도메인 의미를 담습니다. 컴포넌트 안에서 이를 처리하는 함수는 `handle`로 시작합니다.
- **필수와 선택**: 없으면 동작하지 않는 값은 필수로, 합리적인 기본값이 있는 값은 선택으로 둡니다.
- **기본값**: 구조 분해의 기본값은 prop이 없거나 `undefined`일 때만 적용됩니다. `null`과 `0`을 넘기면 기본값이 쓰이지 않습니다.
- **타입**: 문자열 두 개 중 하나를 고르는 prop은 `string`이 아니라 리터럴 유니언으로 씁니다. `children`은 보통 `React.ReactNode`로 받고, JSX 요소만 받으려면 `React.ReactElement`로 좁힙니다(TypeScript 기준, react.dev 설명).
- **함께 의미가 있는 prop**: 서로 의존하는 prop은 판별 유니언(discriminated union)으로 묶습니다. 공통 리터럴 속성이 어느 쪽인지 정해서 허용되지 않는 조합을 타입에서 막습니다.

```tsx
type Props =
  | { kind: 'link'; href: string }
  | { kind: 'button'; onClick: () => void }

function Action(props: Props) {
  if (props.kind === 'link') {
    return <a href={props.href}>이동</a>
  }
  return <button onClick={props.onClick}>실행</button>
}
// <Action kind="link" /> → 타입 에러(href 누락)
```

- props는 읽기 전용 스냅샷이므로 컴포넌트 안에서 바꾸지 않습니다. 바꿔야 하면 부모에게 다른 props를 달라고 요청하는 콜백을 받습니다.
- 이름은 긍정형으로 씁니다. `disabled`는 되지만 `notEnabled`나 `disableNotAllowed` 같은 부정형 이름은 조건을 읽기 어렵게 만듭니다.

## Boolean Prop 남용 방지

boolean prop은 쓰기 쉬워서 늘어나기 쉽고, n개가 모이면 조합이 2의 n제곱이 됩니다. 서로 배타적인 boolean이 문제입니다.

```tsx
// ❌ primary와 danger를 동시에 켤 수 있음. 어느 쪽이 이기는지 불명확
<Button primary danger large />

// ✅ 한 번에 하나만 고르는 값은 유니언 하나로
<Button variant="danger" size="lg" />
```

- 같은 축의 선택지(스타일, 크기, 상태)가 boolean 둘 이상으로 흩어졌으면 유니언 prop 하나로 합칩니다.
- 새 선택지가 생기면 boolean은 prop을 추가해야 하지만, 유니언은 값을 하나 더하면 됩니다.
- 호출부의 `<Button large />`처럼 값이 없는 boolean은 읽기 쉽지만, `<List sortable={false} />`처럼 끄는 쪽은 의미를 한 번 더 해석해야 하므로 기본값이 `false`가 되도록 이름을 정합니다.
- boolean이 어울리는 경우는 서로 독립된 켜고 끔입니다. `disabled`, `loading`, `required`가 그렇습니다. 이들은 HTML 속성과 의미가 같아서 그대로 따릅니다.
- boolean이 `true`가 되면 다른 prop이 필요해진다면(예: `editable`이 켜지면 `onSave`가 필요) 판별 유니언으로 바꿉니다.

## Variant Props

Variant prop은 시각적·의미적 대안을 정해진 목록에서 고르게 하는 prop입니다. 이름은 관례적으로 `variant`, `size`, `tone`을 씁니다.

```tsx
type Variant = 'primary' | 'secondary' | 'danger'
const styles: Record<Variant, string> = {
  primary: 'btn-primary',
  secondary: 'btn-secondary',
  danger: 'btn-danger',
}
function Button({ variant = 'primary', ...rest }: {
  variant?: Variant
} & React.ComponentPropsWithoutRef<'button'>) {
  return <button className={styles[variant]} {...rest} />
}
```

- 변형을 객체로 매핑하면 분기문이 사라지고, `Record<Variant, string>` 타입이 새 변형을 추가할 때 매핑 누락을 잡아 줍니다.
- 기본값은 구조 분해에서 지정해서 호출부가 가장 흔한 경우를 생략하게 합니다.
- variant는 겉모습과 의미의 대안입니다. 동작이 근본적으로 다르면(링크와 버튼처럼 렌더링 요소가 달라지는 경우) 위의 판별 유니언이나 별도 컴포넌트가 맞습니다.
- 변형이 계속 늘고 서로 다른 props를 요구하기 시작하면 하나의 컴포넌트가 두 역할을 하고 있다는 신호입니다. 쪼갭니다.
- 서로 직교하는 축(크기와 톤)은 prop을 따로 둡니다. 합쳐서 `primaryLarge` 같은 값을 만들면 조합마다 항목이 필요해집니다.

## Controlled API

Controlled(제어) 컴포넌트는 중요한 값이 props로 결정되고, 부모가 상태를 소유하는 컴포넌트입니다. react.dev는 이를 두고 부모가 동작을 완전히 지정할 수 있어 유연성이 가장 높지만 부모가 props로 모두 설정해 줘야 한다고 설명합니다.

관례적인 모양은 값과 변경 콜백의 쌍입니다. `<input>`의 `value`와 `onChange`, Radix의 `value`와 `onValueChange`, `open`과 `onOpenChange`가 그렇습니다.

```tsx
function Toggle({ pressed, onPressedChange }: {
  pressed: boolean
  onPressedChange: (next: boolean) => void
}) {
  return (
    <button onClick={() => onPressedChange(!pressed)}>
      {pressed ? 'ON' : 'OFF'}
    </button>
  )
}
```

- 컴포넌트는 값을 직접 바꾸지 않고 "다음 값은 이것이다"라고 콜백으로 알립니다. 부모가 받아들이지 않으면 화면은 바뀌지 않습니다.
- 콜백 이름은 `onChange`보다 값의 의미가 드러나게(`onPressedChange`, `onOpenChange`) 짓습니다. 인자는 이벤트 객체가 아니라 다음 값입니다.
- 장점은 부모가 값을 검증·거절하고, 다른 컴포넌트와 상태를 동기화하고, 값을 코드로 바꿀 수 있다는 점입니다. 단점은 쓰는 쪽마다 `useState`와 연결 코드가 필요하다는 점입니다.
- `value`를 주면 반드시 변경 핸들러도 줘야 합니다. 핸들러가 없는 `<input value={...} />`는 react.dev가 잘못된 예로 드는 코드이며, 입력이 값에 고정됩니다.

## Uncontrolled API

Uncontrolled(비제어) 컴포넌트는 값을 내부 상태로 관리하고, 부모는 초기값만 줍니다. react.dev는 로컬 상태를 가진 컴포넌트를 uncontrolled라 부르며, 쓰기는 쉽지만 다른 컴포넌트와 조율하기는 어렵다고 설명합니다.

관례적인 모양은 `defaultValue`(`defaultOpen`, `defaultPressed`)입니다. 초기값일 뿐이라 이후 값이 바뀌어도 반영되지 않습니다.

```tsx
<input defaultValue="초기 텍스트" />  // 내부가 소유
<input value={text} onChange={...} /> // 부모가 소유
```

좋은 라이브러리 컴포넌트는 둘을 모두 지원합니다. `value`가 있으면 Controlled, 없으면 Uncontrolled로 동작합니다. Radix가 쓰는 `useControllableState`의 원리는 다음과 같습니다.

```tsx
function useControllable<T>(
  value: T | undefined,
  defaultValue: T,
  onChange?: (v: T) => void,
) {
  const [inner, setInner] = useState(defaultValue)
  const isControlled = value !== undefined
  const current = isControlled ? value : inner
  const set = (next: T) => {
    if (!isControlled) setInner(next)
    if (next !== current) onChange?.(next)
  }
  return [current, set] as const
}
```

- 제어 여부는 `value !== undefined`로 판단합니다. Radix의 구현도 `prop !== undefined`를 쓰고, Controlled일 때는 내부 상태를 바꾸지 않고 `onChange`만 호출합니다.
- Controlled일 때도 변경이 일어나면 콜백을 호출하고, Uncontrolled일 때는 내부 상태를 바꾼 뒤 콜백도 호출해서 부모가 변화를 관찰할 수 있게 합니다.
- 중간에 모드를 바꾸면 안 됩니다. `<input>`에 `value={undefined}`로 시작했다가 문자열을 넘기면 React가 경고하고, Radix 구현도 개발 모드에서 "controlled와 uncontrolled를 오가면 안 된다"고 경고합니다. API에서 오는 값이 `null`이나 `undefined`일 수 있으면 `value ?? ''`처럼 항상 같은 모드가 되게 만듭니다.
- Uncontrolled 컴포넌트를 처음 상태로 되돌리려면 `key`를 바꿉니다. 같은 위치에서 `key`가 다르면 React가 다른 컴포넌트로 보고 상태를 새로 만듭니다.
- 선택 기준: 값을 부모가 알아야 하거나 조율해야 하면 Controlled, 폼이 제출될 때만 읽으면 되거나 단순한 위젯이면 Uncontrolled입니다. 가능하면 둘 다 열어 두는 것이 재사용 컴포넌트의 기본입니다.

## Compound Component

Compound Component는 서로 짝이 되는 여러 컴포넌트가 Context로 상태를 공유하며 하나의 위젯을 이루는 API입니다. 하나의 거대한 컴포넌트에 prop을 계속 추가하는 대신, 조각을 따로 내보내 사용자가 조립합니다.

```tsx
<Tabs defaultValue="a">
  <Tabs.List>
    <Tabs.Trigger value="a">개요</Tabs.Trigger>
    <Tabs.Trigger value="b">설정</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="a">...</Tabs.Content>
  <Tabs.Content value="b">...</Tabs.Content>
</Tabs>
```

- Radix의 Tabs는 `Root`, `List`, `Trigger`, `Content`, Accordion은 `Root`, `Item`, `Header`, `Trigger`, `Content`로 이루어집니다.
- 장점은 조각의 순서·배치·스타일을 사용자가 정하고, 내부 상태와 접근성 연결은 컴포넌트가 책임지는 것입니다. `titleSize`, `footerAlign` 같은 prop 없이 JSX 구조로 해결합니다.
- 상태 공유는 `children`을 순회해 props를 주입(`Children.map` + `cloneElement`)하는 대신 Context로 합니다. react.dev는 `Children`과 `cloneElement`를 "드물게 쓰며 코드가 깨지기 쉽다"고 경고하고 대안으로 여러 컴포넌트를 내보내는 방식과 Context를 권합니다.
- 구현과 접근성은 12편에서, 다른 합성 패턴과의 비교는 11편에서 다룹니다.

## children Composition

`children`은 컴포넌트가 열어 두는 구멍입니다. react.dev는 JSX 태그 안에 넣은 내용이 `children` prop으로 전달된다고 설명하고, legacy 문서는 이를 포함(containment)이라고 부릅니다.

```tsx
function Card({ children }: { children: React.ReactNode }) {
  return <div className="card">{children}</div>
}

<Card><Avatar /></Card>
```

- 구멍이 여러 개면 `children` 대신 이름 있는 prop으로 받습니다(`left`, `right`, `header`, `footer`). legacy 합성 문서의 `SplitPane` 예가 이 방식입니다.
- 일반화한 컴포넌트를 구체화하려면 상속이 아니라 합성을 씁니다. 구체 컴포넌트가 일반 컴포넌트를 렌더링하면서 props로 설정합니다. React 팀은 컴포넌트 상속 계층이 필요한 사례를 찾지 못했다고 밝힙니다.
- prop drilling 해결에도 쓰입니다. react.dev는 Context를 쓰기 전에, 컴포넌트를 추출하고 `<Layout><Posts posts={posts} /></Layout>`처럼 JSX를 `children`으로 넘겨 중간 단계를 줄이라고 안내합니다.
- `children`을 읽고 가공(`Children.map`, `cloneElement`)하는 방식은 피합니다. `Children`은 컴포넌트가 렌더링한 결과를 볼 수 없어서(`<MoreRows />`가 만든 행은 세지 못함) 컴포넌트를 추출하는 순간 깨집니다. 가공이 필요하면 하위 컴포넌트를 내보내거나 데이터 배열 prop, Render Props를 씁니다.

## Render Props

Render prop은 컴포넌트가 무엇을 렌더링할지 알기 위해 호출하는 함수 prop입니다. 컴포넌트는 데이터를 인자로 넘기고, 모양은 호출자가 결정합니다.

```tsx
type Render<T> = (item: T, on: boolean) => React.ReactNode

function List<T>({ items, renderItem }: {
  items: T[]
  renderItem: Render<T>
}) {
  const [selected] = useState(0)
  return items.map((v, i) => renderItem(v, i === selected))
}
```

- 이름이 `render`일 필요는 없습니다. legacy 문서는 `children`을 함수로 쓰는 형태도 같은 패턴이라고 설명합니다(Function as Child, 자세히는 11편).
- react.dev가 `cloneElement`의 대안으로 제시한 방식입니다. 값이 어디서 오는지 추적하기 쉬워집니다.
- 쓸 곳은 컴포넌트가 가진 내부 값(선택 상태, 측정 결과, 마우스 좌표)이 있어야 호출자가 렌더링할 수 있는 경우입니다.
- 인라인 함수는 렌더링마다 새로 만들어져서 `React.PureComponent`나 `memo`의 얕은 비교 이점을 없앱니다(legacy 문서의 주의점).
- 로직만 공유하려면 지금은 커스텀 Hook이 더 단순합니다. react.dev도 `cloneElement` 대안으로 로직 추출 Hook을 제시합니다. 렌더링 위치까지 건네야 할 때 Render Props가 남습니다.

## Headless Component

Headless 컴포넌트는 상태, 키보드 동작, ARIA 속성 같은 동작 로직만 제공하고 마크업과 스타일은 사용자가 정하는 컴포넌트입니다. Radix Primitives는 "스타일 없이 제공되어 외형을 완전히 통제할 수 있다"는 점과, aria·role 속성, 포커스 관리, 키보드 내비게이션 같은 접근성 세부를 대신 처리한다는 점을 핵심으로 소개합니다.

- 제공 방식은 Compound Component(Radix), 커스텀 Hook, Render Props 중 하나이거나 이들의 조합입니다.
- API 설계의 관점에서는 "어디까지가 컴포넌트의 책임인가"를 정하는 선택입니다. 동작은 안쪽, 모양은 바깥에 둡니다.
- 구체적인 구조와 라이브러리 비교는 13편에서 다룹니다.

## Escape Hatch

Escape Hatch는 컴포넌트가 예상하지 못한 요구를 호출자가 API 밖으로 풀어낼 수 있게 열어 둔 통로입니다. 표면을 작게 유지하면서 막다른 길을 없애려는 장치입니다.

| 통로 | 허용하는 것 |
|------|-------------|
| 나머지 props 스프레드 | 루트 요소의 HTML 속성(`aria-*`, `data-*`, 이벤트) |
| `className`, `style` | 스타일 덧붙이기 |
| `ref` | 루트 DOM 노드 접근 |
| `asChild`, `as` | 렌더링할 요소 교체 |
| Render Props | 내부 일부의 렌더링 대체 |
| `data-state` 같은 속성 | 상태 기반 스타일링 훅(Radix의 `data-state`) |

```tsx
type InputProps = React.ComponentPropsWithoutRef<'input'>

function Input({ className, ...rest }: InputProps) {
  const merged = `input ${className ?? ''}`
  return <input className={merged} {...rest} />
}
```

- `ref`는 React 19부터 함수 컴포넌트가 prop으로 직접 받습니다. react.dev는 새 컴포넌트에 `forwardRef`가 필요 없고 앞으로 `forwardRef`를 deprecate한다고 밝힙니다. 기존 코드와 라이브러리에는 `forwardRef`가 남아 있습니다.
- 병합이 대체보다 안전합니다. 호출자의 `className`과 `onClick`이 컴포넌트 내부 값을 덮어쓰지 않고 합쳐져야 합니다. 스프레드를 내부 props보다 뒤에 두면 호출자가 내부 핸들러를 덮어써서 내부 동작이 사라집니다.
- 통로마다 표면이 넓어집니다. 루트 요소 하나에만 열고, 필요가 확인된 곳에만 추가합니다.
- 접근성 속성(`role`, `aria-*`)을 호출자가 덮어쓸 수 있는 통로는 내부 동작과 어긋날 수 있다는 점을 문서화합니다.

## asChild와 Slot 패턴

asChild는 컴포넌트가 기본 DOM 요소를 만들지 않고, 자식 요소를 복제해서 필요한 props와 동작을 입혀 주는 prop입니다. Radix가 널리 쓰는 방식이고 내부에는 `Slot`이라는 유틸이 있습니다. Radix 합성 문서는 `asChild`일 때 "기본 DOM 요소를 렌더링하지 않고 자식을 복제해 필요한 props와 동작을 넘긴다"고 설명합니다.

```tsx
<Dialog.Trigger asChild>
  <MyButton>Open</MyButton>
</Dialog.Trigger>
// <button> 래퍼 없이 MyButton이 트리거 동작을 받음
```

직접 만들 때의 형태는 Radix 문서의 예와 같습니다.

```tsx
import { Slot } from 'radix-ui'

function Button({ asChild, ...props }: ButtonProps) {
  const Comp = asChild ? Slot.Root : 'button'
  return <Comp {...props} />
}
```

`Slot`의 소스(`slot.tsx`)가 하는 일은 다음과 같습니다.

| 대상 | 병합 규칙 |
|------|-----------|
| 이벤트 핸들러 | 둘 다 있으면 자식 핸들러를 먼저, 이어서 슬롯 핸들러를 호출 |
| `style` | 객체를 합치되 자식 값이 우선 |
| `className` | 공백으로 이어 붙임 |
| `ref` | 자식 ref와 슬롯 ref를 합성 |
| 마지막 | 병합한 props로 `cloneElement`를 호출해 단일 자식에 적용 |

- 자식 컴포넌트는 두 가지를 지켜야 합니다. 받은 props를 DOM 요소에 모두 펼쳐 주고(`{...props}`), ref를 DOM 노드까지 전달해야 합니다. 지키지 않으면 클릭·포커스·측정 같은 동작이 사라집니다. Radix 문서는 이 때문에 `forwardRef` 예제를 보여 주며, React 19에서는 `ref`를 prop으로 받는 것으로 같은 요건을 채웁니다.
- 슬롯은 자식 요소 하나에 적용됩니다. 요소가 아닌 자식(여러 개나 문자열)을 주면 소스는 에러를 던집니다. 여러 자식 중 어느 것을 대상으로 할지 정해야 할 때 `Slot.Slottable`을 씁니다.
- 용도는 "스타일은 내 컴포넌트(또는 `<a>`, 라우터 Link)로 두고, 동작은 컴포넌트가 부여"하는 경우입니다. 래퍼 요소가 늘어나 DOM이 달라지는 문제를 피합니다.

## 다형성(as prop)

다형성(polymorphic) 컴포넌트는 prop 하나로 렌더링할 루트 요소를 바꿉니다. 이름은 라이브러리마다 다릅니다. MUI는 `component`라는 prop으로 루트 요소를 바꾸며 `<List component="menu">`처럼 씁니다.

```tsx
type BoxProps<C extends React.ElementType> = { as?: C } &
  Omit<React.ComponentPropsWithoutRef<C>, 'as'>

function Box<C extends React.ElementType = 'div'>(
  { as, ...rest }: BoxProps<C>,
) {
  const Comp: React.ElementType = as ?? 'div'
  return <Comp {...rest} />
}
// <Box as="a" href="/home" />  href 타입이 허용됨
```

- 값은 `'a'` 같은 태그 문자열이거나 컴포넌트입니다. 컴포넌트를 넘길 때는 asChild와 같은 요건이 붙습니다. MUI 문서도 props를 모두 전달하고 ref를 전달하라고 요구합니다.
- 타입이 핵심 난점입니다. `as`에 따라 허용 props가 달라져야 해서 제네릭 `C extends React.ElementType`를 씁니다. MUI 문서도 TypeScript에서는 제네릭 형태가 필요하다고 안내합니다. 타입이 복잡해지고 에러 메시지가 읽기 어려워지는 비용이 있습니다.
- 접근성이 자동으로 따라오지 않습니다. `as="div"`로 버튼 역할을 만들면 키보드 동작과 `role`을 직접 채워야 합니다.

| 항목 | `as` | `asChild` |
|------|------|-----------|
| 지정 방법 | prop 값(태그 또는 컴포넌트) | 자식 요소 자체 |
| 자식 구조 | 컴포넌트가 요소를 만듦 | 호출자의 요소를 그대로 사용 |
| props 병합 | 컴포넌트가 직접 전달 | `Slot`이 핸들러·style·className·ref 병합 |
| 타입 | 제네릭 필요 | 자식 컴포넌트 책임 |
| 대표 사례 | MUI의 `component` | Radix |

**흔한 실수:** 둘을 한 컴포넌트에 모두 열어 두는 것입니다. 표면이 넓어지는 만큼 호출자가 어느 쪽을 써야 하는지 혼란스러워지므로 하나를 고릅니다.

## 핵심 정리

- API 표면은 필요한 것만 열고, 이벤트 콜백은 `on`으로 시작하며, 함께 의미가 있는 props는 판별 유니언으로 묶어 불가능한 조합을 타입에서 막습니다.
- 서로 배타적인 boolean 여러 개는 `variant`나 `size` 같은 유니언 하나로 합치고, boolean은 독립된 켜고 끔(`disabled`, `loading`)에만 씁니다.
- Controlled는 `value`와 `onChange`로 부모가 상태를 소유하고, Uncontrolled는 `defaultValue`로 내부가 소유합니다. 재사용 컴포넌트는 `value !== undefined`로 둘을 모두 지원하고 중간에 모드를 바꾸지 않습니다.
- 합성은 `children`, 이름 있는 슬롯 prop, Compound Component(Context 공유), Render Props로 하며, `Children.map`과 `cloneElement`로 children을 가공하는 방식은 피합니다.
- Escape Hatch는 루트 요소의 나머지 props 스프레드, `className`, `ref`(React 19부터 prop), `as`, `asChild`로 열되, 덮어쓰지 말고 병합합니다.
- `asChild`는 `Slot`이 단일 자식에 핸들러·style·className·ref를 병합해 복제하는 방식이고, `as`는 루트 요소를 prop으로 바꾸는 다형성 방식입니다. 둘 다 자식이 props와 ref를 DOM까지 전달해야 합니다.

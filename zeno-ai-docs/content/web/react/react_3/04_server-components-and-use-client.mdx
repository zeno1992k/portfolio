## Server Component

Server Component는 번들링 전에, 클라이언트 앱이나 SSR 서버와 분리된 환경에서 미리 렌더링되는 컴포넌트 종류입니다(React 19 기준). 결과만 클라이언트에 전달되고 컴포넌트 코드는 브라우저로 가지 않습니다.

```jsx
// 지시어 없음 = Server Component (RSC 앱의 기본)
async function Notes() {
  const notes = await db.notes.getAll()
  return notes.map((n) => <p key={n.id}>{n.text}</p>)
}
```

- 실행 시점은 두 가지입니다. 빌드할 때 CI 서버에서 한 번(정적 콘텐츠), 또는 요청마다 웹 서버에서(동적 콘텐츠)입니다. 서버 없이도 빌드 시점에 쓸 수 있습니다.
- Server Component에는 지시어가 없습니다. RSC를 지원하는 환경에서는 `use client`가 없는 모듈이 기본입니다. `use server`는 Server Component용이 아니라 Server Function용입니다(자세히는 05편).
- 사용할 수 있는 것은 `async`/`await`, 데이터베이스와 파일 시스템 접근, 서버에만 두는 비밀 값입니다.
- 사용할 수 없는 것은 `useState`·`useEffect` 같은 Hook, 브라우저 API, `onClick` 같은 이벤트 핸들러입니다.
- RSC는 번들러와 프레임워크의 지원이 필요합니다. react.dev는 19.x 마이너 버전 사이에 RSC를 구현하는 번들러·프레임워크용 API가 깨질 수 있다고 경고하며, 프레임워크는 React 버전을 고정하거나 Canary를 쓰라고 안내합니다.

## Client Component

Client Component는 `use client` 지시어가 붙은 모듈(과 그 모듈이 가져오는 코드)에서 정의되는 컴포넌트입니다. 상태, Effect, 이벤트 핸들러, 브라우저 API가 필요한 부분에 씁니다.

```jsx
'use client'
import { useState } from 'react'

export default function Counter() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
```

- 중급까지 배운 일반적인 React 컴포넌트가 Client Component입니다. 이름과 달리 서버에서 한 번도 실행되지 않는다는 뜻이 아닙니다. 초기 HTML을 만들 때 서버에서도 렌더링됩니다(SSR). Hydration과 이후 상호작용은 클라이언트에서 일어납니다.
- 정리하면 Server Component는 서버에서만 실행되는 컴포넌트이고, Client Component는 클라이언트에서 실행되며 SSR을 위해 서버에서도 한 번 렌더링될 수 있는 컴포넌트입니다.

| 구분 | Server Component | Client Component |
|------|------------------|------------------|
| 표시 | 없음(기본값) | 파일 맨 위 `use client` |
| 실행 위치 | 서버(빌드 시점 또는 요청 시점) | 클라이언트(초기 HTML을 위해 서버에서도 렌더링) |
| `async` 컴포넌트 | 가능 | 불가능(`use`로 Promise를 읽음) |
| Hook(`useState` 등) | 불가능 | 가능 |
| 이벤트 핸들러 | 불가능 | 가능 |
| 브라우저 API | 불가능 | 가능 |
| 서버 자원(DB·파일·비밀 값) | 가능 | 불가능 |
| 번들에 포함 | 안 됨 | 됨 |
| Hydration | 하지 않음 | 함(03편) |

## Server에서 실행

Server Component는 데이터가 있는 곳에서 직접 실행되므로 데이터 접근을 위해 API를 따로 만들지 않아도 됩니다.

```jsx
import db from './database'

async function Note({ id }) {
  const note = await db.notes.get(id)
  return (
    <div>
      <Author id={note.authorId} />
      <p>{note.text}</p>
    </div>
  )
}
```

- 클라이언트에서 Effect로 가져오면 `Note`가 데이터를 받은 뒤에야 `Author`가 요청을 시작하는 워터폴이 생깁니다. 서버에서는 데이터베이스와 가까워서 이 문제가 줄어듭니다. react.dev는 Server Component의 장점으로 워터폴 없음, 직접 DB 접근, 데이터 가져오기 코드와 UI의 한 곳 배치를 꼽습니다.
- 비밀 값과 토큰을 클라이언트에 노출하지 않고 쓸 수 있습니다.
- 브라우저는 렌더링된 결과만 받습니다.
- 컴포넌트 사이의 데이터 흐름과 병렬화는 06편에서 다룹니다.

## Client Bundle 감소

Server Component가 쓰는 라이브러리는 클라이언트 번들에 들어가지 않습니다. 정적 콘텐츠를 렌더링하느라 쓰는 무거운 라이브러리가 브라우저로 가지 않습니다.

```jsx
import marked from 'marked'              // 번들에 안 들어감
import sanitizeHtml from 'sanitize-html' // 번들에 안 들어감

async function Page({ page }) {
  const content = await file.readFile(`${page}.md`)
  return <div>{sanitizeHtml(marked(content))}</div>
}
```

- react.dev의 예에서 `marked`는 gzip 11.2K, `sanitize-html`은 gzip 63.3K입니다. 클라이언트 컴포넌트였다면 약 75K가 번들에 들어가고, 내용은 두 번째 요청이 끝난 뒤에야 보입니다. Server Component에서는 브라우저가 렌더링된 HTML만 받습니다.
- 첫 로드에서 내용이 보이므로 FCP에도 유리합니다.
- 번들에서 빠지는 것은 서버 전용 컴포넌트와 그 의존성뿐입니다. `use client` 아래의 코드는 모두 번들에 들어갑니다(아래 "Client Bundle").

## 비동기 Server Component

Server Component는 `async` 함수로 만들고 렌더링 중에 `await`할 수 있습니다.

```jsx
async function Page({ id }) {
  const note = await db.notes.get(id)
  return <div>{note.text}</div>
}
```

- `await`한 컴포넌트는 데이터가 준비될 때까지 중단되고, 그 아래 트리도 함께 기다립니다. 독립적인 영역은 `Suspense`로 감싸 스트리밍합니다(02편).
- Client Component는 렌더링 중에 `await`할 수 없습니다. 대신 `use`로 Promise를 읽습니다(중급 15편).
- 서버에서 만든 Promise를 `await`하지 않고 Client Component에 넘기면, 클라이언트가 `use`로 읽는 동안 우선순위가 낮은 내용을 스트리밍할 수 있습니다.

```jsx
// Server Component
const commentsPromise = db.comments.get(note.id) // await 안 함
return (
  <Suspense fallback={<p>Loading...</p>}>
    <Comments commentsPromise={commentsPromise} />
  </Suspense>
)
```

- Promise가 해결된 값은 직렬화 가능해야 합니다(아래 "Serializable Props").
- 서로 독립적인 `await`를 줄줄이 쓰면 앞의 것이 끝나야 다음이 시작되는 워터폴이 됩니다. 병렬화 방법은 06편에서 다룹니다.

## Server/Client 경계

경계(boundary)는 서버에서 실행되는 모듈 그래프와 클라이언트에서 실행되는 모듈 그래프가 만나는 지점입니다. 그 안으로는 직렬화 가능한 값만 넘길 수 있습니다.

```text
App.js (Server)
├── Copyright.js (Server)
└── Generator.js ('use client')   ← 경계
    ├── FancyText.js  (여기서는 Client)
    └── quotes.js     (Client)
```

- 경계는 렌더 트리가 아니라 모듈 의존 트리에서 정해집니다. 모듈이 `use client` 모듈에서 가져와 쓰이면 클라이언트 쪽에서 평가됩니다.
- 같은 컴포넌트 정의가 양쪽에서 쓰일 수 있습니다. `use client`가 없는 `FancyText`를 Server Component가 쓰면 서버에서, Client Component 안에서 쓰면 클라이언트에서 실행됩니다.
- 서버에서 클라이언트로 넘어가는 모든 데이터는 props로 가며 직렬화 규칙을 따라야 합니다.
- 반대로 클라이언트에서 서버로 가는 호출은 Server Function입니다(05편).

## use client

`use client`는 파일과 그 파일이 가져오는 모든 의존성을 클라이언트 코드로 표시하는 지시어입니다. 모듈 의존 트리에 서버/클라이언트 경계를 만듭니다.

```jsx
'use client'

import { useState } from 'react'
import { formatDate } from './formatters'
```

규칙은 다음과 같습니다.

- 파일 맨 위, 모든 import와 코드보다 앞에 씁니다. 주석은 앞에 올 수 있습니다.
- 작은따옴표나 큰따옴표만 쓰며 백틱은 안 됩니다.
- `use client` 모듈을 다른 클라이언트 모듈이 가져오면 지시어는 아무 영향이 없습니다. 이미 클라이언트 경계 안이기 때문입니다.
- `use client`가 있는 컴포넌트는 반드시 Client Component입니다. 반대로 지시어가 없어도 클라이언트 모듈의 의존성이면 클라이언트에서 평가됩니다.
- 서버 모듈이 `use client` 모듈에서 가져오는 값은 React 컴포넌트이거나 직렬화 가능한 props여야 합니다. 아니면 오류가 납니다.
- 지시어를 모든 클라이언트 컴포넌트에 쓸 필요는 없습니다. 경계의 진입점 파일에 쓰면 그 아래는 같은 경계에 속합니다.

`use client`를 써야 하는 경우는 다음과 같습니다.

| 쓴다 | 쓰지 않는다 |
|------|-------------|
| 이벤트 핸들러(`onClick` 등) | 정적이고 상호작용이 없는 UI |
| `useState`, `useEffect` 등 Hook | 파일·DB·비밀 값 같은 서버 자원 사용 |
| 브라우저 API(`localStorage`, canvas) | 상태·이벤트 없이 UI만 렌더링 |
| 클라이언트 API에 의존하는 서드파티 라이브러리 | |

서드파티 컴포넌트가 `use client` 없이 Hook을 쓰면 Server Component에서 바로 쓸 수 없습니다. 이럴 때 `use client`가 붙은 래퍼 파일에서 다시 내보내 쓰는 방식이 일반적입니다.

## Client Boundary

Client Boundary는 `use client`가 붙은 모듈이 이루는 클라이언트 영역의 경계입니다. 경계 안의 모든 모듈은 클라이언트에서 실행됩니다.

- 경계 안의 코드는 컴포넌트뿐 아니라 모든 코드가 클라이언트로 전송되어 실행됩니다.
- 경계 안에서 가져온 컴포넌트는 지시어가 없어도 Client Component입니다.
- 서버 컴포넌트를 경계 안에서 `import`하면 서버 컴포넌트가 아니라 클라이언트 모듈이 됩니다. 서버 렌더링을 유지하려면 props나 `children`으로 받아야 합니다(아래 "Client에 Server Component 전달").
- 경계를 어디에 두느냐가 번들 크기와 서버 렌더링 범위를 정합니다(아래 "Boundary 최소화").

## Interactive Component

상호작용이 있는 컴포넌트는 Client Component입니다. 이벤트 핸들러와 상태를 가진 가장 작은 단위를 `use client`로 분리합니다.

```jsx
// 서버: 데이터와 정적 UI
async function Post({ id }) {
  const post = await getPost(id)
  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton likes={post.likes} />
    </article>
  )
}
```

- `LikeButton`처럼 클릭에 반응하는 부분만 Client Component로 만들고, 제목·본문처럼 정적인 부분은 서버에 남깁니다.
- 폼 입력, 토글, 모달 열림 상태, 드롭다운, 탭 전환이 해당합니다.
- Server Component에 `onClick`을 직접 쓰면 오류가 납니다. 이벤트 핸들러는 직렬화할 수 없기 때문입니다.
- Server Function을 폼 `action`에 쓰면 Client Component 없이도 서버 호출을 연결할 수 있습니다(05편).

## Hook 사용 영역

Hook은 Client Component에서만 씁니다. 상태·생명주기·Context 읽기 Hook은 렌더 결과를 클라이언트에서 갱신하는 기능이기 때문입니다.

| Hook과 API | Server Component | Client Component |
|------------|------------------|------------------|
| `useState`, `useReducer` | 불가능 | 가능 |
| `useEffect`, `useLayoutEffect` | 불가능 | 가능 |
| `useContext`, `use(context)` | 불가능 | 가능 |
| `use(promise)` | `await`가 권장 | 가능 |
| `async`/`await` 렌더링 | 가능 | 불가능 |

- Server Component에서 Context를 읽을 수 없고(`use(context)`는 지원되지 않음), `createContext`로 만들 수도 없습니다. Context 생성은 `use client` 모듈에서 합니다.
- 19.3부터는 Server Component가 클라이언트 모듈의 Context를 직접 렌더링해 값을 줄 수 있습니다. 이전에는 `use client` 래퍼 Provider 컴포넌트가 필요했습니다.

```jsx
// user-context.js: 'use client' 모듈에서 Context를 만든다
// server-component.js (19.3부터)
return (
  <UserContext value={currentUser}>
    {children}
  </UserContext>
)
```

- 커스텀 Hook이 내부에서 상태·Effect를 쓰면 그 Hook을 호출하는 컴포넌트는 Client Component입니다.
- Hook만 쓰는 로직을 Server Component에서 쓰려면 서버에서 계산 가능한 일반 함수로 바꿉니다.

## Browser API

`window`, `document`, `localStorage`, canvas 같은 브라우저 API는 클라이언트에서만 있으므로 Client Component에서 씁니다.

```jsx
'use client'
import { useRef, useLayoutEffect } from 'react'

export default function Circle() {
  const ref = useRef(null)
  useLayoutEffect(() => {
    ref.current.getContext('2d').arc(100, 75, 50, 0, 7)
  })
  return <canvas ref={ref} />
}
```

- Server Component에서 브라우저 API를 호출하면 서버에 존재하지 않아 오류가 납니다.
- Client Component도 SSR 때 서버에서 한 번 렌더링됩니다. 따라서 렌더링 중에 읽는 브라우저 API는 여전히 서버에서 깨집니다. Effect로 옮기거나 `useSyncExternalStore`, `use(browser())`를 씁니다(01편, 03편).
- 브라우저 API가 필요한 부분만 작은 Client Component로 빼면 나머지는 서버에 남습니다.

## Serializable Props

서버에서 클라이언트로 넘기는 props는 React가 직렬화할 수 있는 값이어야 합니다. 직렬화는 값을 네트워크로 전송할 수 있는 형태로 바꾸는 것입니다.

| 가능 | 불가능 |
|------|--------|
| 원시 값(string, number, bigint, boolean, undefined, null) | 일반 함수(클라이언트 모듈에서 내보낸 함수와 Server Function 제외) |
| `Symbol.for()`로 등록한 전역 심벌 | `Symbol('x')` 같은 전역이 아닌 심벌 |
| 문자열, 배열, Map, Set, TypedArray, ArrayBuffer | 클래스, 클래스 인스턴스(`Date` 같은 내장 타입 제외) |
| `Date` | 프로토타입이 null인 객체 |
| 객체 리터럴로 만든 일반 객체(값이 직렬화 가능) | |
| Server Function(`use server`) | |
| JSX 요소(Client·Server Component) | |
| Promise | |

```jsx
// Server Component
<Chart
  data={rows}               // ✅ 배열과 일반 객체
  updatedAt={new Date()}    // ✅ Date
  onSelect={(r) => log(r)}  // ❌ 일반 함수
  formatter={new Intl.NumberFormat()} // ❌ 클래스 인스턴스
/>
```

- 일반 함수를 넘기고 싶다면 이벤트 핸들러를 클라이언트 쪽에서 정의하거나, 서버 쪽 로직이면 Server Function으로 만듭니다(05편).
- 직렬화할 수 없는 값을 넘기면 오류가 납니다. 서버에서 필요한 필드만 뽑아 일반 객체로 넘기는 습관이 안전합니다.
- 서버가 보낸 props는 클라이언트에 전송되므로 비밀 값이 들어 있으면 노출됩니다. DB 객체를 통째로 넘기지 않습니다.
- Promise를 넘기면 그 해결 값도 직렬화 가능해야 합니다.

## Server → Client Composition

서버 컴포넌트가 클라이언트 컴포넌트를 렌더링하며 props로 데이터를 전달하는 것이 가장 기본적인 조합입니다. 서버가 데이터를 가져오고, 상호작용은 클라이언트가 맡습니다.

```jsx
// app/[id]/page.js (Server)
import LikeButton from './like-button'

export default async function Page({ id }) {
  const post = await getPost(id)
  return <LikeButton likes={post.likes} />
}
```

```jsx
// like-button.js (Client)
'use client'
export default function LikeButton({ likes }) {
  // 상태와 클릭 핸들러
}
```

- 서버는 `post`를 가져와 필요한 값만 props로 내립니다. 클라이언트는 초기값을 받아 상태로 이어갑니다.
- 렌더링 중에 값을 받고 싶으면 Promise를 props로 넘겨 `use`로 읽게 합니다.
- 서버 → 클라이언트 방향만 가능합니다. 클라이언트가 서버 컴포넌트를 `import`해서 쓰면 그 컴포넌트는 클라이언트로 넘어갑니다.

## Client에 Server Component 전달

Client Component는 Server Component를 직접 import할 수 없지만, `children`이나 props로 받아 렌더링할 수 있습니다. 서버에서 이미 렌더링된 결과가 슬롯에 들어갑니다.

```jsx
// Server Component
<Modal>
  <Cart />  {/* 서버에서 렌더링 */}
</Modal>
```

```jsx
// Modal.js (Client)
'use client'
export default function Modal({ children }) {
  const [open, setOpen] = useState(false)
  return open ? <div>{children}</div> : null
}
```

- `Cart`는 서버에서 실행됩니다. `Modal`이 렌더링되기 전에 이미 결과가 만들어져 있어서 `children`으로 전달될 뿐입니다.
- `Modal`은 열림 상태만 관리하고 `Cart`의 내용을 모릅니다. `Cart`의 데이터 접근과 코드는 서버에 남습니다.
- 이 방식은 `Modal`의 모듈 의존성에 `Cart`가 포함되지 않기 때문에 가능합니다. 렌더링 위치(JSX 트리)는 `Modal` 안이지만 모듈 의존 트리에서는 서버 쪽입니다.
- `children`만이 아니라 이름 있는 props도 같은 방식으로 슬롯이 됩니다. 컴포지션 패턴은 11편에서 다룹니다.
- Context Provider를 클라이언트 컴포넌트로 만들어 `children`을 받게 하는 방식도 같은 원리입니다. Provider를 트리 위쪽에서 `children`만 감싸야 서버 컴포넌트가 정적으로 남습니다.

**흔한 실수:** Client Component 파일 안에서 Server Component를 `import`해 직접 렌더링하는 것입니다. 그 컴포넌트는 클라이언트 모듈로 바뀌어 서버 전용 코드(DB 접근)가 깨집니다. 부모 서버 컴포넌트에서 조립하고 `children`으로 전달합니다.

## Client Bundle

클라이언트 번들에는 `use client` 모듈과 그 모듈이 가져오는 모든 코드가 들어갑니다. 컴포넌트가 아닌 유틸 함수나 큰 라이브러리도 포함됩니다.

```jsx
'use client'
import _ from 'lodash'           // 번들에 포함
import { format } from './dates' // 번들에 포함
```

- 번들에 들어가지 않는 것은 서버 모듈과 `children`·props로 넘겨 받은 서버 컴포넌트입니다.
- 한 파일에 `use client`를 붙이면 그 파일이 가져오는 하위 컴포넌트와 라이브러리가 모두 클라이언트 번들로 향합니다. 큰 레이아웃 전체에 붙이면 번들이 크게 불어납니다.
- 번들 크기는 번들 분석 도구로 확인합니다(자세히는 26편).
- 클라이언트 모듈이 서버 전용 모듈을 가져오면 서버 전용 코드와 그 의존성이 번들에 끌려갑니다(아래 "server-only와 client-only").

## Boundary 최소화

`use client`는 가능한 한 트리 아래쪽, 상호작용이 필요한 가장 작은 컴포넌트에 붙입니다. 경계를 좁히면 클라이언트 번들이 줄고 서버에서 렌더링되는 범위가 넓어집니다.

```jsx
// ❌ 레이아웃 전체를 Client로 만든다
'use client'
export default function Layout({ children }) { /* Logo, Search, Nav */ }

// ✅ 검색창만 Client로 분리한다
import Search from './search'   // 'use client'
import Logo from './logo'       // Server
export default function Layout({ children }) {
  return <nav><Logo /><Search /></nav>
}
```

- 정적 UI(로고, 링크)는 서버에 남기고, 상호작용이 필요한 검색창만 Client Component로 분리합니다.
- 상태가 필요한 부분을 컴포넌트로 빼서 상태와 UI를 가까이 둡니다. 페이지 전체를 Client로 바꾸는 것보다 작게 쪼갭니다.
- Context Provider는 필요한 가장 깊은 곳에 두고 `children`만 감쌉니다. Next.js 문서는 `html` 전체가 아니라 `children`만 감싸라고 안내합니다. 서버 컴포넌트의 정적 부분을 최적화하는 데 유리하기 때문입니다.
- 라이브러리를 만드는 쪽에서는 클라이언트 전용 기능에 의존하는 진입점에 `use client`를 달아 두면 사용자가 래퍼 없이 Server Component에서 가져다 쓸 수 있습니다.
- 경계가 많아져도 괜찮습니다. 목표는 클라이언트로 가는 코드의 양을 줄이는 것이지 경계의 개수를 줄이는 것이 아닙니다.

## RSC payload

RSC payload는 서버가 렌더링한 Server Component 트리를 직렬화한 데이터입니다. React가 클라이언트에서 DOM을 갱신하고 트리를 맞추는 데 씁니다. Next.js 문서가 설명하는 구성은 다음과 같습니다.

| 포함 | 내용 |
|------|------|
| Server Component의 렌더링 결과 | 이미 실행된 결과 |
| Client Component 자리 표시자 | 렌더링할 위치와 JS 파일 참조 |
| 서버에서 클라이언트로 넘긴 props | 직렬화된 값 |

- 컴포넌트 코드가 아니라 렌더링 결과가 전달됩니다. 그래서 Server Component의 코드는 번들에 들어가지 않습니다.
- 스트리밍됩니다. Suspense 경계가 해결되는 대로 payload 조각이 도착합니다(02편).
- 첫 로드에서는 HTML이 빠른 미리보기를 보여 주고, payload가 클라이언트·서버 트리를 맞추며, JS가 Client Component를 Hydration합니다.
- 이후 이동에서는 payload를 받아 화면을 갱신합니다. Client Component는 서버 HTML 없이 클라이언트에서 렌더링됩니다.
- RSC payload라는 이름과 구성 설명은 Next.js 문서 기준입니다. 전송 형식은 프레임워크가 다루므로 "직렬화된 서버 렌더 결과"로 이해하면 충분합니다.

## server-only와 client-only

`server-only`와 `client-only`는 모듈이 잘못된 환경에서 쓰이면 빌드 시점에 오류를 내는 표식 패키지입니다. 서버 전용 코드가 클라이언트로 흘러드는 사고(환경 오염)를 막습니다.

```js
import 'server-only'

export async function getData() {
  const res = await fetch(url, {
    headers: { authorization: process.env.API_KEY },
  })
  return res.json()
}
```

- 서버 전용 코드가 있는 파일에 `import 'server-only'`를 넣으면, 그 모듈을 Client Component에서 가져올 때 빌드 오류가 납니다.
- `client-only`는 짝이 되는 패키지로, `window`를 쓰는 코드처럼 클라이언트 전용 로직의 모듈에 씁니다.
- Next.js에서는 접두사 `NEXT_PUBLIC_`이 붙은 환경 변수만 클라이언트 번들에 들어가고, 나머지는 빈 문자열로 바뀝니다. 그래도 코드가 실수로 실행될 수 있어서 `server-only`로 한 번 더 막습니다.
- Next.js에서 이 패키지 설치는 선택입니다. 프레임워크가 두 import를 내부에서 처리해 더 명확한 오류 메시지를 줍니다. 린트가 불필요한 의존성을 지적하면 설치합니다.
- 환경 변수와 비밀 값의 노출 경로는 23편에서 다룹니다.

## RSC와 SSR의 차이

RSC와 SSR은 서로 다른 개념이고 함께 쓰입니다. 면접에서 자주 묻습니다.

- SSR은 컴포넌트(Client Component 포함)를 서버에서 HTML로 렌더링하는 방식입니다. 모든 컴포넌트의 JS가 클라이언트로 오고 Hydration됩니다.
- RSC는 서버에서만 실행되는 컴포넌트 종류입니다. 결과만 직렬화해 보내며 코드는 번들에 없고 Hydration하지 않습니다.

| 항목 | SSR | RSC |
|------|-----|-----|
| 정의 | 서버에서 HTML을 만드는 렌더링 전략 | 서버에서만 실행되는 컴포넌트 종류 |
| 결과물 | HTML(상호작용을 위해 JS 필요) | 직렬화된 렌더 결과(RSC payload) |
| 컴포넌트 JS | 클라이언트 번들에 포함 | Server Component는 번들에 포함되지 않음 |
| Hydration | 전체 트리 | Client Component만 |
| 데이터 접근 | 렌더링 전에 가져와 props로 | 컴포넌트 안에서 직접 `await` |
| 실행 시점 | 요청마다 | 요청마다 또는 빌드 시점 |
| 목적 | 첫 화면 속도, SEO | 번들 감소, 서버 자원 직접 접근 |

- RSC는 SSR 없이도 쓸 수 있습니다. react.dev는 Server Component가 클라이언트 앱이나 SSR 서버와 분리된 환경에서 렌더링된다고 설명하고, 서버 없이 빌드 시점에 실행하는 경우도 안내합니다.
- 반대로 SSR은 RSC 없이도 합니다. 중급까지 다룬 일반 컴포넌트를 `renderToString`으로 렌더링하는 것이 해당합니다.
- 함께 쓰면 첫 로드에서 Client Component와 RSC payload로 HTML을 만들어 미리 보여 주고(SSR), payload로 트리를 맞춘 뒤 Client Component만 Hydration합니다.
- 면접 답변 한 줄: "SSR은 어디서 HTML을 만드느냐의 문제이고, RSC는 어떤 컴포넌트의 코드를 브라우저에 보내느냐의 문제입니다."
- Client Component도 SSR에서는 서버에서 한 번 렌더링됩니다. "Client Component는 서버에서 실행되지 않는다"는 흔한 오해입니다.

## 핵심 정리

- Server Component는 지시어 없는 기본값이며 서버(빌드 또는 요청 시점)에서만 실행됩니다. `async`/`await`와 서버 자원 접근이 가능하고 Hook, 이벤트, 브라우저 API는 쓸 수 없으며 코드가 번들에 들어가지 않습니다.
- `use client`는 파일 맨 위에 쓰며, 그 파일과 가져오는 모든 코드를 클라이언트 번들에 넣는 경계를 모듈 의존 트리에 만듭니다.
- 서버에서 클라이언트로 가는 props는 직렬화 가능해야 하며 일반 함수, 클래스 인스턴스, 전역이 아닌 심벌은 안 됩니다.
- Client Component는 Server Component를 import할 수 없고, `children`이나 props로 받아 서버에서 렌더링된 결과를 슬롯에 넣습니다.
- 경계는 상호작용이 필요한 가장 작은 컴포넌트에 둡니다. 서버 전용 모듈은 `server-only`로 클라이언트 import를 빌드 단계에서 막습니다.
- SSR은 HTML을 어디서 만드느냐, RSC는 어떤 컴포넌트 코드를 브라우저로 보내느냐의 문제이며 서로 독립적이고 함께 쓸 수 있습니다.

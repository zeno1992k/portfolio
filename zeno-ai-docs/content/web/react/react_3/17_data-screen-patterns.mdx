이 편의 코드는 TanStack Query v5(2026-10 기준 5.104.x)를 쓴다고 가정합니다. 사용법의 기초는 중급 27편·28편, 검색 조건을 URL에 두는 방법은 중급 29편에서 다뤘습니다.

## Server State

서버 상태는 서버가 원본을 가지고 있고, 클라이언트는 비동기로 가져온 사본만 가진 데이터입니다. 사본은 가져온 순간부터 낡을 수 있어서, 가져오기·캐시·중복 요청 제거·갱신을 따로 관리해야 합니다(자세히는 중급 26편).

데이터 화면의 설계는 세 가지 결정으로 시작합니다.

- 서버 데이터는 `useState`에 복사하지 않고 쿼리 캐시에서 읽는다.
- 화면에서 정하는 값(검색어, 페이지, 선택한 항목)은 URL이나 로컬 State에 두고 쿼리 키로만 연결한다.
- 쿼리 키는 한곳에서 만든다.

```ts
const todoKeys = {
  all: ['todos'] as const,
  list: (f: Filters) =>
    [...todoKeys.all, 'list', f] as const,
  detail: (id: string) =>
    [...todoKeys.all, 'detail', id] as const,
}
```

키가 `['todos']`로 시작하므로 `invalidateQueries({ queryKey: todoKeys.all })` 한 번으로 목록과 상세를 모두 무효화할 수 있습니다. 기본값은 다음과 같습니다.

| 항목 | 기본값 |
|------|--------|
| `staleTime` | 0 (가져오자마자 stale) |
| `gcTime` | 5분 (사용하는 곳이 없어진 뒤 캐시 삭제까지) |
| 자동 재요청 시점 | 새 인스턴스 마운트, 창 포커스, 네트워크 재연결 |
| `retry` | 3회 (서버에서는 0회) |

화면은 쿼리 하나당 네 상태 중 하나입니다. 분기는 이 순서로 씁니다.

```tsx
if (isPending) return <ListSkeleton />
if (isError) return <ErrorPanel onRetry={refetch} />
if (data.items.length === 0) return <EmptyState />
return <TodoList items={data.items} />
```

- `isPending`은 캐시된 데이터가 없고 아직 한 번도 끝나지 않은 상태입니다.
- 이 순서가 바뀌면 로딩 중에 "결과 없음"이 보이거나, 에러가 빈 목록으로 보입니다.
- Server Components 환경에서는 서버에서 데이터를 읽고 클라이언트 캐시를 쓰지 않을 수 있습니다(자세히는 06편).

**흔한 실수:** 응답을 `useEffect`로 `useState`에 옮겨 담는 것입니다. 같은 데이터가 두 곳에 있게 되어 mutation 뒤에 하나만 갱신되는 불일치가 생깁니다.

## List / Detail

목록과 상세는 서로 다른 쿼리입니다. 키가 다르므로 캐시도 따로 쌓입니다. 선택한 항목의 id는 State가 아니라 URL 경로 파라미터에 두어 새로고침과 공유에 견디게 합니다.

```tsx
function useTodo(id: string, filters: Filters) {
  const qc = useQueryClient()
  return useQuery({
    queryKey: todoKeys.detail(id),
    queryFn: () => fetchTodo(id),
    placeholderData: () =>
      qc.getQueryData(todoKeys.list(filters))?.items
        .find((t) => t.id === id),
  })
}
```

- 목록에서 이미 받은 요약 데이터를 `placeholderData`로 먼저 보여 주면 상세 화면이 즉시 열립니다. 상세 응답이 오면 교체됩니다.
- `placeholderData`는 캐시에 저장되지 않습니다. 완전한 데이터를 캐시에 넣고 싶을 때만 `initialData`를 쓰고, 이때는 원본 쿼리의 `dataUpdatedAt`을 `initialDataUpdatedAt`으로 넘겨야 신선도를 따로 판단합니다.
- 목록에서 상세로 이동한 뒤 돌아왔을 때 목록이 즉시 보이는 것은 목록 캐시가 `gcTime` 동안 남아 있기 때문입니다.
- 상세 데이터를 바꾸면 목록의 같은 항목도 낡습니다. 어느 쿼리를 함께 갱신할지는 다음 절의 규칙을 따릅니다.

**흔한 실수:** 상세 쿼리의 키에 id를 넣지 않는 것입니다. 항목을 바꿔도 같은 캐시 항목을 읽어 이전 항목이 보입니다.

## CRUD

CRUD 네 동작은 쿼리와 mutation으로 나뉩니다. 읽기는 `useQuery`, 나머지 셋은 `useMutation`이고, 성공 뒤에 캐시를 어떻게 맞추느냐가 다릅니다.

| 동작 | HTTP | 성공 뒤 캐시 처리 |
|------|------|-------------------|
| Create | POST | 목록 키 무효화(새 항목의 위치는 서버가 정함) |
| Read | GET | 쿼리가 담당 |
| Update | PUT, PATCH | 응답으로 상세를 `setQueryData`, 목록 무효화 |
| Delete | DELETE | 상세는 `removeQueries`, 목록 무효화 |

```tsx
const qc = useQueryClient()
const update = useMutation({
  mutationFn: patchTodo,
  onSuccess: (saved) => {
    qc.setQueryData(todoKeys.detail(saved.id), saved)
    qc.invalidateQueries({
      queryKey: [...todoKeys.all, 'list'],
    })
  },
})
```

- `setQueryData`는 캐시를 즉시 동기로 바꿉니다. 서버가 최종 상태를 응답으로 돌려주면 추가 요청 없이 상세가 맞춰집니다.
- 캐시 객체는 직접 수정하지 않고 새 객체로 교체합니다. `old.title = 'x'` 같은 변경은 구독자에게 알려지지 않습니다.
- `removeQueries`는 캐시 항목 자체를 지웁니다. 삭제된 항목의 상세 쿼리를 `invalidateQueries`로 처리하면 존재하지 않는 항목을 다시 요청해 404가 납니다.
- mutation은 기본 재시도가 0회입니다. 같은 POST가 두 번 가면 항목이 두 개 생길 수 있어서 자동 재시도를 켜지 않습니다.
- 버튼 중복 클릭은 `isPending`으로 막습니다. 제출 UI는 16편을 참고합니다.

**흔한 실수:** 목록 키에 필터가 들어 있는데 `['todos', 'list']` 정확히 일치로 무효화하는 것입니다. 쿼리 키 매칭은 기본이 접두사 일치이므로 `exact`를 주지 않는 한 필터가 붙은 목록도 함께 무효화됩니다. 반대로 `exact: true`를 습관적으로 붙이면 필터 목록이 갱신되지 않습니다.

## Search + Filter + Sort

검색어·필터·정렬은 URL의 검색 파라미터에 두고, 같은 값을 쿼리 키에 넣습니다. 조건이 바뀌면 키가 바뀌어 새 요청이 나가고, 이미 본 조건은 캐시에서 즉시 나옵니다.

```tsx
const [params] = useSearchParams()
const filters = {
  q: params.get('q') ?? '',
  status: params.get('status') ?? 'all',
  sort: params.get('sort') ?? 'created',
}
const { data } = useQuery({
  queryKey: todoKeys.list(filters),
  queryFn: ({ signal }) => fetchTodos(filters, signal),
  placeholderData: keepPreviousData,
})
```

- 응답을 기다리는 동안 이전 결과를 남기려면 `placeholderData: keepPreviousData`를 씁니다. 목록이 매번 스켈레톤으로 깜빡이지 않습니다.
- `queryFn`이 받는 `signal`을 `fetch`에 넘기면, 키가 바뀌어 이전 요청이 필요 없어질 때 요청이 취소됩니다.
- 응답 순서가 뒤바뀌어도 키마다 캐시가 분리되어 있어 느린 이전 응답이 새 결과를 덮어쓰지 않습니다.
- 검색어를 입력할 때마다 요청하지 않도록 입력 State와 URL에 반영하는 값을 분리합니다. 입력 중인 값은 로컬 State로 두고, 지연(debounce)이나 `useDeferredValue`를 거친 값을 키에 씁니다(자세히는 중급 10편).
- 누가 전체 데이터를 가졌는지가 처리 위치를 정합니다. 서버가 전체를 가지고 있으면 서버가 필터·정렬하고, 클라이언트가 이미 전체를 받았다면 렌더 중에 계산합니다. 파생 값을 State나 Effect로 저장하지 않습니다.
- 필터나 정렬이 바뀌면 페이지를 1로 되돌립니다. 아니면 존재하지 않는 페이지를 요청합니다.

**흔한 실수:** 필터를 쿼리 키에 넣지 않는 것입니다. 키가 같아서 조건을 바꿔도 이전 조건의 캐시가 보이고, 새로 가져온 결과가 같은 항목을 덮어씁니다.

## Pagination

페이지네이션은 한 번에 일부만 가져오는 방식입니다. 서버 방식이 두 가지입니다.

| 구분 | 오프셋 방식 | 커서 방식 |
|------|-------------|-----------|
| 요청 | 페이지 번호와 크기 | 마지막으로 받은 항목의 커서 |
| 임의 페이지 이동 | 가능 | 불가능 |
| 데이터가 중간에 바뀔 때 | 항목이 중복되거나 빠질 수 있음 | 안정적 |
| 어울리는 UI | 번호 이동 | 더 보기, 무한 스크롤 |

번호 이동 UI는 페이지 번호를 쿼리 키에 넣고 `keepPreviousData`로 전환 중에도 이전 페이지를 유지합니다.

```tsx
const { data, isPlaceholderData } = useQuery({
  queryKey: todoKeys.list({ ...filters, page }),
  queryFn: () => fetchTodos({ ...filters, page }),
  placeholderData: keepPreviousData,
})
const canNext = !isPlaceholderData && data?.hasMore
```

- `isPlaceholderData`가 `true`면 지금 보이는 목록은 이전 페이지입니다. 이 동안 "다음" 버튼을 비활성화해야 페이지를 건너뛰는 일이 없습니다.
- 페이지 번호는 URL 검색 파라미터에 둡니다. 뒤로 가기와 공유가 동작합니다.
- 더 보기·무한 스크롤은 `useInfiniteQuery`를 씁니다. 페이지가 계속 누적되므로 항목이 많아지면 가상화를 함께 씁니다(자세히는 중급 21편, 28편).
- 응답에 전체 개수나 `hasMore` 같은 표지가 있어야 마지막 페이지를 판단합니다. 항목 수가 페이지 크기보다 적은지로 추측하면 마지막 페이지의 크기가 딱 맞을 때 빈 페이지를 한 번 더 요청합니다.

**흔한 실수:** 마지막 항목을 지운 뒤 그 페이지가 비어 버리는 경우를 처리하지 않는 것입니다. 이전 페이지로 되돌리거나 빈 상태가 아니라 페이지 이동을 안내해야 합니다.

## Optimistic Mutation

낙관적 변경은 서버 응답을 기다리지 않고 성공할 것으로 가정해 화면을 먼저 바꾸는 방식입니다. 실패하면 되돌립니다. 두 가지 구현이 있습니다.

| 방식 | 동작 | 어울리는 경우 |
|------|------|----------------|
| 변수 사용 | mutation의 `variables`로 대기 중인 항목을 목록 끝에 임시 표시 | 화면의 한 곳만 바뀔 때 |
| 캐시 수정 | `onMutate`에서 캐시를 직접 수정하고 실패 시 복구 | 여러 곳이 같은 데이터를 볼 때 |

캐시 수정 방식은 네 단계입니다. 진행 중인 요청을 취소하고, 이전 값을 저장하고, 캐시를 바꾸고, 실패하면 저장한 값으로 되돌립니다.

```tsx
const qc = useQueryClient()
const toggle = useMutation({
  mutationFn: toggleTodo,
  onMutate: async (id: string) => {
    await qc.cancelQueries({ queryKey: todoKeys.all })
    const prev = qc.getQueryData(todoKeys.detail(id))
    qc.setQueryData(todoKeys.detail(id), (old) =>
      old ? { ...old, done: !old.done } : old)
    return { prev }
  },
  onError: (_e, id, ctx) =>
    qc.setQueryData(todoKeys.detail(id), ctx?.prev),
  onSettled: () =>
    qc.invalidateQueries({ queryKey: todoKeys.all }),
})
```

- `cancelQueries`를 빼면 이미 나간 refetch가 응답으로 낙관적 값을 덮어쓸 수 있습니다.
- `onMutate`의 반환값이 `onError`의 세 번째 인수로 전달됩니다. 되돌릴 값은 여기에 담습니다.
- `onSettled`에서 무효화하면 성공이든 실패든 서버의 실제 값과 맞춰집니다.
- 서버가 만들어 줘야 하는 값(새 id, 생성 시각)이 필요한 Create에는 캐시 수정이 맞지 않습니다. 변수 방식으로 임시 항목을 표시합니다.
- 실패가 잦거나 되돌릴 때 사용자가 혼란스러운 작업(결제, 삭제 확정)에는 낙관적 변경을 쓰지 않습니다.
- 한 컴포넌트 안에서만 쓰는 낙관적 값이라면 React의 `useOptimistic`이 더 간단합니다. 쿼리 캐시와 별개의 값이며, Action이 끝나면 서버 값으로 돌아갑니다(자세히는 중급 08편).

**흔한 실수:** `onError`에서 되돌린 뒤 `onSettled`의 무효화를 빼는 것입니다. 복구한 값이 서버의 최신 값과 다를 수 있습니다.

## Loading Skeleton

스켈레톤은 데이터가 올 자리의 모양을 회색 블록으로 먼저 그려 두는 로딩 표시입니다. 처음 로딩(`isPending`)에만 씁니다. 이미 데이터가 있는 상태의 갱신(`isFetching`)에는 쓰지 않고 데이터를 그대로 둡니다.

```tsx
function ListSkeleton({ rows = 5 }: { rows?: number }) {
  return (
    <ul aria-busy="true" aria-label="목록 불러오는 중">
      {Array.from({ length: rows }, (_, i) => (
        <li key={i} className="skeleton-row" />
      ))}
    </ul>
  )
}
```

- 실제 행과 같은 높이·너비로 그려야 데이터가 도착할 때 레이아웃이 밀리지 않습니다(CLS).
- 같은 구조를 한 번만 정의합니다. 실제 행 컴포넌트와 스켈레톤을 한 파일에 두면 한쪽만 바뀌는 일을 막습니다.
- 요청이 매우 빠르면 스켈레톤이 깜빡이기만 합니다. 일정 시간이 지난 뒤에 표시하는 방식으로 줄입니다.
- 스켈레톤 블록은 장식입니다. 컨테이너에 `aria-busy`를 두고, 블록마다 스크린 리더가 읽지 않게 합니다.
- `useSuspenseQuery`를 쓰면 `isPending` 분기 대신 Suspense의 fallback에 스켈레톤을 둡니다(자세히는 중급 11편).
- 스피너와 달리 스켈레톤은 최종 모양을 예고하므로 목록·카드·표처럼 구조가 정해진 화면에 어울립니다. 버튼 안의 처리 중 표시는 스피너가 맞습니다.

**흔한 실수:** 키가 바뀔 때마다 스켈레톤으로 돌아가는 것입니다. 검색·페이지 전환은 `keepPreviousData`로 이전 결과를 유지하고 흐리게 처리하는 쪽이 덜 흔들립니다.

## Error Retry

데이터 화면의 에러는 두 가지 상황으로 나뉩니다. 데이터가 아직 없는 상태에서 실패한 경우는 화면 전체를 에러 패널로 바꾸고 재시도 버튼을 둡니다. 이미 받은 데이터가 있는 상태에서 갱신이 실패한 경우는 기존 데이터를 유지하고 알림만 띄웁니다. `data`는 마지막으로 성공한 값이기 때문에 두 번째 경우에도 남아 있습니다.

```tsx
const { data, isError, error, refetch } = useQuery(options)
if (isError && !data) {
  return <ErrorPanel error={error} onRetry={refetch} />
}
// data가 있으면 목록을 그리고, isError이면 배너를 추가한다
```

자동 재시도 규칙은 다음과 같습니다.

- 쿼리는 실패하면 기본 3회까지 지수 백오프로 재시도합니다. 대기 시간은 1초에서 시작해 두 배씩 늘며 30초가 상한입니다. 서버 렌더링에서는 기본 0회입니다.
- 모든 재시도가 끝나야 `isError`가 됩니다. 재시도 중에는 상태가 바뀌지 않습니다.
- 재시도해도 소용없는 에러(400번대 응답)는 함수로 걸러 냅니다.

```ts
retry: (count, error) =>
  !(error instanceof HttpError && error.status < 500) &&
  count < 3,
```

- `HttpError`는 직접 정의한 클래스입니다. `fetch`는 404나 500에도 reject하지 않으므로 `queryFn`에서 `response.ok`를 확인해 에러를 던져야 쿼리가 에러로 인식합니다.
- 재시도 버튼은 `refetch`를 호출합니다. 재시도 중에는 버튼을 비활성화하고 `isFetching`으로 상태를 표시합니다.
- mutation은 기본 재시도가 없습니다. 실패하면 입력 값을 보존한 채 오류를 보여 주고 사용자가 다시 제출하게 합니다.
- 렌더 중에 던져진 에러는 Error Boundary가 잡습니다. 에러 처리를 경계로 올릴지 컴포넌트에서 처리할지는 18편에서 다룹니다.

**흔한 실수:** 인증 만료(401)를 3회 재시도하는 것입니다. 같은 요청이 계속 실패하며 대기 시간만 쌓입니다. 401은 재시도 대신 로그인 흐름으로 보냅니다(자세히는 18편).

## Empty State

빈 상태는 요청이 성공했는데 보여 줄 항목이 없는 상태입니다. 로딩이나 에러가 아닙니다. 원인이 둘이라서 안내와 행동이 다릅니다.

| 원인 | 안내 | 행동 |
|------|------|------|
| 처음부터 데이터가 없음 | 무엇을 만들 수 있는지 | 생성 버튼 |
| 조건에 맞는 결과가 없음 | 조건을 바꿔 보라는 안내 | 필터 초기화 |

```tsx
const hasFilter =
  filters.q !== '' || filters.status !== 'all'
if (data.items.length === 0) {
  return hasFilter
    ? <NoResults onReset={clearFilters} />
    : <FirstUse onCreate={openCreate} />
}
```

- 빈 상태 분기는 `isPending`과 `isError` 분기 뒤에 둡니다. `!data`나 `data?.items.length`를 조건으로 쓰면 로딩과 에러가 빈 상태로 보입니다.
- `keepPreviousData`로 이전 결과를 보여 주는 중에는 빈 상태를 결정하지 않습니다. 새 응답이 도착한 뒤(`isPlaceholderData`가 `false`)에만 판단합니다.
- 삭제로 마지막 항목이 사라지면 같은 컴포넌트가 곧바로 빈 상태로 전환됩니다. 포커스가 사라진 요소에 있지 않도록 안내 영역으로 옮깁니다.
- 안내 문구는 텍스트로 제공합니다. 일러스트만 두면 스크린 리더 사용자는 상태를 알 수 없습니다.

**흔한 실수:** 모든 빈 목록에 같은 문구를 쓰는 것입니다. 필터 때문에 빈 목록인데 "첫 항목을 만들어 보세요"가 나오면 사용자가 필터를 의심하지 못합니다.

## Refresh

새로고침은 현재 화면의 데이터를 서버에서 다시 가져오는 동작입니다. 시작하는 주체가 셋입니다.

| 방식 | 설정 | 비고 |
|------|------|------|
| 사용자 요청 | 버튼에서 `refetch()` 호출 | 모바일은 당겨서 새로고침 |
| 시간 기준 | `refetchInterval` (기본 false) | 폴링. 실시간성이 필요한 화면만 |
| 환경 변화 | `refetchOnWindowFocus`, `refetchOnReconnect` (기본 켜짐) | stale일 때만 실행 |

```tsx
const { refetch, isFetching } = useQuery(options)
<button onClick={() => refetch()} disabled={isFetching}>
  {isFetching ? '갱신 중' : '새로고침'}
</button>
```

- `refetch`는 stale 여부와 상관없이 항상 요청합니다. 반면 포커스·재연결·마운트에 의한 재요청은 stale일 때만 일어납니다.
- 새로고침 중에도 기존 데이터를 지우지 않습니다. 진행 표시는 `isFetching`이나 `isRefetching`을 씁니다. `isRefetching`은 `isFetching`이면서 `isPending`이 아닌 경우입니다.
- 화면 전체 스피너가 필요하면 쿼리별 값 대신 `useIsFetching`으로 진행 중인 쿼리 수를 셉니다.
- 폴링 간격은 서버 부하와 갱신 필요성의 균형으로 정합니다. 실시간 반영이 목적이면 폴링 대신 WebSocket·SSE 같은 서버 푸시가 맞는지 먼저 따집니다.

**흔한 실수:** 새로고침 중에 `isPending`으로 스켈레톤을 보여 주는 것입니다. `isPending`은 처음 로딩에만 `true`이므로 새로고침 표시에는 `isFetching`을 써야 합니다.

## Revalidation

재검증은 캐시에 있는 데이터가 아직 유효한지 확인하고 낡았으면 다시 가져오는 규칙입니다. 캐시를 먼저 보여 주고 뒤에서 확인하는 stale-while-revalidate 방식으로 동작합니다. 사용자는 기다리지 않고, 데이터는 곧 최신이 됩니다.

재검증이 일어나는 경로는 세 가지입니다.

- 시간: `staleTime`이 지나면 데이터가 stale이 되고, 다음 마운트·포커스·재연결 때 재요청합니다.
- 변경: mutation 뒤에 `invalidateQueries`로 관련 키를 stale로 표시합니다.
- 수동: `refetchQueries`로 stale 여부와 관계없이 다시 가져옵니다.

| 메서드 | 하는 일 |
|--------|---------|
| `invalidateQueries` | stale로 표시하고 활성 쿼리를 재요청 |
| `refetchQueries` | stale 여부와 관계없이 재요청 |
| `removeQueries` | 캐시에서 삭제 |
| `resetQueries` | 초기 상태로 되돌리고 활성 쿼리를 재요청 |

```ts
// 접두사 일치(기본)
qc.invalidateQueries({ queryKey: todoKeys.all })
// 정확히 일치
qc.invalidateQueries({ queryKey: ['todos'], exact: true })
// 조건 함수
qc.invalidateQueries({
  predicate: (q) => q.queryKey[0] === 'todos',
})
```

- 무효화는 `staleTime` 설정을 무시하고 stale로 만듭니다. 화면에 쓰이지 않는 쿼리는 stale로만 표시하고, 다음에 쓰일 때 재요청합니다.
- `refetchType`으로 재요청 대상을 바꿀 수 있습니다. 기본은 `'active'`이고 `'inactive'`, `'all'`, `'none'`이 있습니다.
- `staleTime`은 데이터 성격에 맞춥니다. 거의 바뀌지 않는 코드 목록은 길게, 재고처럼 자주 바뀌는 값은 짧게 둡니다. 기본 0은 안전하지만 마운트마다 요청이 나갑니다.
- 갱신의 책임은 변경한 쪽이 집니다. mutation을 만든 곳에서 영향받는 키를 무효화하는 규칙을 정해 두면 화면이 늘어도 누락이 없습니다.
- 프레임워크의 서버 캐시 재검증(Next.js의 데이터 캐시 등)은 쿼리 캐시와 별개입니다(자세히는 Next.js 과목).

**흔한 실수:** `invalidateQueries`를 `refetchQueries`처럼 쓰는 것입니다. 무효화는 화면에서 쓰이지 않는 쿼리는 즉시 요청하지 않습니다. 그 쿼리가 곧 필요하다면 mutation 직후에 반드시 가져와야 하는지 따져 봅니다.

## 핵심 정리

- 서버 데이터는 쿼리 캐시에서 읽고 `useState`에 복사하지 않으며, 쿼리 키는 키 팩토리 한곳에서 만들고 화면 조건을 모두 키에 넣습니다.
- 화면 분기는 로딩, 에러, 빈 상태, 데이터 순서로 쓰고, 스켈레톤은 처음 로딩에만, 갱신 표시는 `isFetching`으로 합니다.
- Update는 응답으로 `setQueryData`, Create·Delete는 목록 무효화와 `removeQueries`로 캐시를 맞춥니다.
- 검색·필터·정렬·페이지는 URL에 두고 키에 넣으며, 전환 중 이전 결과는 `keepPreviousData`로 유지하고 `isPlaceholderData` 동안 다음 이동을 막습니다.
- 낙관적 변경은 취소, 저장, 수정, 복구, 무효화 순서이며, 서버가 값을 만드는 Create에는 변수 방식을 씁니다.
- 쿼리 재시도는 기본 3회 지수 백오프이고 mutation은 0회이며, 재검증은 stale 표시와 재요청으로 나뉩니다.

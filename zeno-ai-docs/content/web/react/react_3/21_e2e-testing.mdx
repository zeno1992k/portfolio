## Playwright 계열

E2E(End-to-End) 테스트는 실제 브라우저에서 앱을 띄우고 사용자가 하는 순서대로 조작해 결과를 확인하는 테스트입니다. 단위·컴포넌트 테스트가 한 조각을 검증한다면 E2E는 라우터, 서버, 네트워크, 브라우저 엔진까지 이어진 전체 경로를 검증합니다(자세히는 중급 34편).

Playwright는 E2E 도구이고, 공식 테스트 러너인 Playwright Test(`@playwright/test`)를 함께 제공합니다. 이 문서가 확인한 최신 릴리스 노트는 1.63입니다.

| 구성 | 역할 |
|------|------|
| Playwright Test | 테스트 러너. 병렬 실행, 재시도, 리포터, `expect` 포함 |
| 브라우저 | Chromium, Firefox, WebKit을 Playwright가 제공하는 빌드로 실행 |
| codegen | 브라우저에서 조작한 내용을 코드와 로케이터로 만들어 주는 도구 |
| UI Mode·VS Code 확장 | 로컬에서 테스트를 보며 실행·디버깅 |
| Trace Viewer | 실행 기록(단계별 DOM 스냅샷, 네트워크, 로그)을 되돌려 보는 도구 |

설치와 실행은 아래 명령입니다. 설치 마법사가 `playwright.config.ts`와 예제 테스트를 만들고, 테스트 폴더는 기본적으로 `tests/`입니다.

```bash
npm init playwright@latest   # 설치와 초기 파일 생성
npx playwright test          # 전체 실행
npx playwright show-report   # HTML 리포트 열기
```

가장 짧은 테스트는 다음과 같습니다. `page`는 테스트마다 새로 만들어지는 탭입니다.

```ts
import { test, expect } from '@playwright/test'

test('홈 제목이 보인다', async ({ page }) => {
  await page.goto('/')
  await expect(page.getByRole('heading', { name: '홈' }))
    .toBeVisible()
})
```

같은 계열의 대안으로 Cypress가 자주 비교됩니다. 둘 다 자동 대기와 네트워크 가로채기를 제공하지만 실행 구조가 다릅니다.

| 항목 | Playwright | Cypress |
|------|------------|---------|
| 실행 위치 | 테스트가 Node 프로세스에서 브라우저를 원격 제어 | 테스트가 앱과 같은 브라우저 실행 루프 안에서 실행 |
| 지원 브라우저 | Chromium, Firefox, WebKit | Chrome 계열(Edge 포함), Firefox |
| 다른 출처 이동 | 별도 API 없이 일반 이동 | `cy.origin()` 사용 |
| 인증 캐시 | `storageState` | `cy.session()` |

시험이나 면접에서 묻는 방식은 "단위·통합·E2E를 어디에 얼마나 쓰는가"입니다. E2E는 느리고 깨지기 쉬워서 사용자에게 치명적인 소수의 경로에만 쓰고, 나머지는 더 작은 테스트로 검증합니다.

## 로케이터와 자동 대기

E2E가 안정적인지는 요소를 찾는 방식과 기다리는 방식이 결정합니다.

로케이터는 요소를 찾는 방법이고, 호출할 때마다 현재 DOM에서 다시 찾습니다. 공식 문서는 사용자와 보조 기술이 페이지를 인식하는 방식에 가장 가까운 역할(role) 로케이터를 우선하라고 권합니다.

| 로케이터 | 대상 |
|----------|------|
| `getByRole` | 역할과 접근성 이름 |
| `getByLabel` | label에 연결된 폼 컨트롤 |
| `getByPlaceholder` | placeholder 텍스트 |
| `getByText` | 텍스트 내용 |
| `getByAltText`, `getByTitle` | alt, title 속성 |
| `getByTestId` | `data-testid` 속성(속성 이름은 `testIdAttribute`로 변경) |

- CSS·XPath 선택자는 DOM 구조가 바뀌면 깨지므로 권장하지 않습니다.
- 한 요소에 하는 동작은 엄격(strict)합니다. 로케이터가 둘 이상에 일치하면 에러가 나므로 `filter({ hasText })`나 `and()`·`or()`로 좁힙니다.
- 접근성 이름 기반 로케이터를 쓰면 접근성 개선이 곧 테스트 안정성이 됩니다(자세히는 20편).

동작(`click`, `fill` 등)은 실행 전에 요소가 준비될 때까지 자동으로 기다립니다. 확인 항목은 다음과 같습니다.

| 확인 | 의미 |
|------|------|
| Visible | 크기가 있고 `visibility:hidden`이 아님 |
| Stable | 두 애니메이션 프레임 이상 같은 위치 |
| Receives Events | 클릭 지점에서 다른 요소에 가려지지 않음 |
| Enabled | 비활성(disabled)이 아님 |
| Editable | 활성이고 읽기 전용이 아님 |

`click`은 다섯 가지를 모두, `fill`은 Visible·Enabled·Editable을 확인합니다. 시간 안에 통과하지 못하면 `TimeoutError`로 실패합니다. 기본 제한은 테스트 30초, 단언 5초이며 동작과 이동에는 기본 제한이 없습니다.

단언은 웹 우선(web-first) 단언을 씁니다. `await expect(locator).toBeVisible()`처럼 조건이 참이 될 때까지 재시도하는 단언입니다.

```ts
// ✅ 재시도한다
await expect(page.getByText('저장됨')).toBeVisible()
// ❌ 한 번만 확인한다
expect(await page.getByText('저장됨').isVisible()).toBe(true)
```

## 페이지 이동

`page.goto(url)`은 `load` 이벤트까지 기다립니다. 설정의 `baseURL`을 두면 `page.goto('/login')`처럼 상대 경로를 쓸 수 있습니다.

```ts
// playwright.config.ts
export default defineConfig({
  use: { baseURL: 'http://localhost:3000' },
  webServer: {
    command: 'npm run start',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
})
```

`webServer`는 테스트 전에 앱 서버를 띄우고 `url`이 응답할 때까지 기다립니다. 기본 대기 제한은 60초입니다. `reuseExistingServer`를 `!process.env.CI`로 두면 로컬에서는 떠 있는 서버를 재사용하고 CI에서는 새로 띄웁니다.

링크 클릭이나 `router.push`로 일어나는 클라이언트 이동은 이동을 일으킨 동작 뒤에 URL이나 화면 변화를 단언으로 확인합니다.

```ts
await page.getByRole('link', { name: '상품' }).click()
await expect(page).toHaveURL(/\/products$/)
await expect(
  page.getByRole('heading', { name: '상품 목록' }),
).toBeVisible()
```

- `page.waitForURL()`은 클릭 이후 특정 URL이 될 때까지 기다립니다. 단언 `toHaveURL`로 충분하면 단언을 씁니다.
- 새 탭이나 팝업은 `page.waitForEvent('popup')`로 받습니다.
- 뒤로 가기는 `page.goBack()`입니다. Back/Forward Cache는 Playwright에서 기본 꺼져 있고 복원 동작은 테스트 대상이 아닙니다.

**흔한 실수:** SSR 앱에서 버튼이 화면에 보이지만 Hydration이 끝나지 않아 이벤트 핸들러가 아직 없는 경우입니다. Playwright는 빠른 사용자처럼 즉시 클릭하므로 클릭이 무시될 수 있습니다. 공식 문서는 네트워크를 느리게 제한해서 이런 상태를 재현해 보라고 안내합니다(자세히는 03편).

## Form 제출

폼 조작은 사용자가 하는 동작과 같은 이름의 메서드로 합니다.

| 동작 | 코드 |
|------|------|
| 텍스트 입력 | `getByLabel('이메일').fill('a@b.com')` |
| 체크박스 | `getByLabel('약관 동의').check()` |
| 셀렉트 | `getByLabel('색상').selectOption('blue')` |
| 파일 업로드 | `getByLabel('첨부').setInputFiles('a.pdf')` |
| 키 입력 | `press('Enter')`, `pressSequentially('abc')` |

`fill`은 입력창을 비우고 값을 한 번에 넣습니다. 키 입력마다 반응하는 UI(자동완성 등)는 `pressSequentially`로 한 글자씩 칩니다.

제출한 뒤에는 화면에 나타나는 결과를 단언합니다. 성공은 알림이나 이동으로, 실패는 필드 오류 메시지로 확인합니다.

```ts
test('가입 성공', async ({ page }) => {
  await page.goto('/signup')
  await page.getByLabel('이메일').fill('new@example.com')
  await page.getByLabel('비밀번호').fill('pw-1234-abcd')
  await page.getByRole('button', { name: '가입' }).click()
  await expect(page).toHaveURL('/welcome')
})

test('이메일 형식 오류', async ({ page }) => {
  await page.goto('/signup')
  await page.getByLabel('이메일').fill('wrong')
  await page.getByRole('button', { name: '가입' }).click()
  await expect(page.getByRole('alert')).toContainText('이메일')
})
```

- 검증 오류는 서버 응답으로 만들 수도 있습니다. 이럴 때는 아래 "Network Mock"으로 응답을 정해 둡니다(자세히는 16편).
- `getByLabel`이 실패하면 label과 입력창이 연결돼 있지 않다는 신호입니다. 접근성 결함을 발견한 것이므로 로케이터가 아니라 앱을 고칩니다.
- 제출 중 버튼 비활성, 중복 제출 방지는 `toBeDisabled()`로 확인합니다.

## 인증 Flow

로그인 자체를 검증하는 테스트는 실제 화면에서 로그인 폼을 조작해 로그인 상태에 도달하는지 확인합니다.

```ts
test('로그인하면 대시보드로 이동', async ({ page }) => {
  await page.goto('/login')
  await page.getByLabel('이메일').fill(process.env.E2E_USER!)
  await page.getByLabel('비밀번호').fill(process.env.E2E_PASS!)
  await page.getByRole('button', { name: '로그인' }).click()
  await expect(page).toHaveURL('/dashboard')
})
```

- 계정 정보는 코드에 쓰지 않고 환경 변수나 CI 시크릿으로 넣습니다. 운영 계정이 아니라 테스트 전용 계정과 스테이징 환경을 씁니다.
- 로그아웃, 잘못된 비밀번호, 로그인 필요 페이지에 비로그인 상태로 접근했을 때의 리다이렉트도 각각 별도 테스트로 둡니다.
- 로그인이 필요 없는 테스트마다 이 폼을 반복하면 느리고 불안정해집니다. 그 경우는 다음 절의 인증 상태 재사용을 씁니다.
- 외부 로그인(소셜 로그인)은 제3자 서비스를 직접 테스트하지 않는 것이 원칙입니다. 로그인 이후 상태를 만들어 쓰거나 인증 응답을 Mock합니다(자세히는 18편).

## 테스트 격리와 인증 상태 재사용

Playwright Test는 테스트마다 새 BrowserContext를 만듭니다. 쿠키, localStorage, sessionStorage가 테스트끼리 공유되지 않으므로 한 테스트의 실패나 잔여 상태가 다음 테스트에 번지지 않습니다. 정리(cleanup)에 의존하지 않고 새로 시작하는 방식입니다.

- 테스트는 순서와 상관없이 단독으로 실행되고, 병렬 실행과 재시도에 안전해야 합니다.
- 서버나 DB에 남는 상태는 컨텍스트로 격리되지 않습니다. 테스트마다 고유한 데이터(예: 고유한 이메일)를 만들거나 API로 준비·정리합니다.
- 기본 병렬 규칙은 파일끼리는 병렬, 한 파일 안의 테스트는 순차입니다. `fullyParallel: true`면 모든 테스트가 병렬입니다. 실패하면 워커 프로세스가 폐기되고 새로 시작됩니다.
- 다중 사용자 시나리오는 한 테스트에서 컨텍스트를 둘 만듭니다: `browser.newContext()`를 사용자별로 호출합니다.

로그인 상태를 매 테스트마다 만드는 대신, 한 번 로그인해서 브라우저 상태를 파일로 저장하고 재사용합니다. 공식 문서의 기본 방식은 setup 프로젝트입니다.

```ts
// tests/auth.setup.ts
import { test as setup } from '@playwright/test'
const authFile = 'playwright/.auth/user.json'

setup('로그인', async ({ page }) => {
  await page.goto('/login')
  // ... 로그인 폼 조작 ...
  await page.waitForURL('/dashboard')
  await page.context().storageState({ path: authFile })
})
```

```ts
// playwright.config.ts (projects)
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    use: { storageState: 'playwright/.auth/user.json' },
    dependencies: ['setup'],
  },
]
```

- `dependencies`에 지정한 프로젝트가 먼저 실행되고, 통과해야 의존하는 프로젝트가 실행됩니다.
- 저장 파일에는 쿠키와 헤더가 들어 있어 계정을 사칭할 수 있습니다. `playwright/.auth` 폴더를 `.gitignore`에 추가합니다.
- 역할이 여러 개면 `admin.json`, `user.json`을 각각 만들고 파일 단위로 `test.use({ storageState: 'playwright/.auth/admin.json' })`를 씁니다.
- 로그인하지 않은 상태가 필요한 테스트는 `test.use({ storageState: { cookies: [], origins: [] } })`로 초기화합니다.
- API로 로그인할 수 있으면 `request.storageState({ path })`로 폼 조작 없이 상태를 만듭니다.
- 이 방식은 테스트가 서버 상태를 바꾸지 않을 때 적합합니다. 테스트가 계정의 서버 데이터를 바꾼다면 워커마다 다른 계정을 쓰도록 워커 범위 fixture에서 `storageState`를 덮어씁니다.
- sessionStorage는 저장되지 않습니다. 로그인 상태를 sessionStorage에 두는 앱은 별도 처리가 필요합니다.

## Network Mock

`page.route()`는 요청을 가로채 직접 응답하거나, 통과시키거나, 막습니다. 이동 전에 설정해야 첫 요청부터 적용됩니다.

```ts
await page.route('**/api/products', (route) =>
  route.fulfill({ json: [{ id: 1, name: '키보드' }] }),
)
await page.goto('/products')
await expect(page.getByText('키보드')).toBeVisible()
```

| 메서드 | 동작 |
|--------|------|
| `route.fulfill()` | 서버에 가지 않고 정한 응답 반환 |
| `route.continue()` | 요청을 그대로 서버로 보냄 |
| `route.abort()` | 요청을 실패시킴(오프라인, 연결 오류 재현) |
| `route.fetch()` | 실제 응답을 받아 고친 뒤 `fulfill`에 넘김 |

- 서버 오류 화면이나 빈 목록처럼 실제 서버로 만들기 어려운 상태는 `status: 500`이나 빈 배열 응답으로 재현합니다.
- 실제 응답을 일부만 바꾸려면 `route.fetch()`로 받은 JSON을 고쳐 `route.fulfill({ response, json })`으로 돌려줍니다.
- 네트워크 기록(HAR 파일)을 `routeFromHAR()`로 녹화하고 `update: false`로 재생하는 방식도 있습니다.
- 공식 문서의 원칙은 제3자 서비스나 직접 통제하지 않는 API를 테스트하지 않는 것입니다. 그런 호출은 Mock으로 고정합니다.
- 브라우저에서 일어나는 요청만 가로챕니다. 서버 컴포넌트나 서버 함수가 서버 안에서 보내는 요청은 `page.route`로 볼 수 없으므로 테스트 서버의 대상 API를 Mock 서버로 바꿔야 합니다(자세히는 06편).
- 어디까지 Mock할지가 E2E의 성격을 정합니다. 전부 Mock하면 빠르지만 실제 연동을 검증하지 못하고, 전부 실제로 두면 느리고 불안정합니다. Critical Flow는 실제 백엔드(스테이징), 오류·예외 경로는 Mock이 일반적인 배분입니다.

## 실제 Browser

E2E는 JSDOM이 아니라 실제 브라우저 엔진에서 실행되는 점이 컴포넌트 테스트와 다릅니다. 레이아웃, CSS, 포커스, 스크롤, 브라우저 API는 JSDOM으로 검증할 수 없습니다(자세히는 중급 35편).

- Playwright는 Chromium, Firefox, WebKit을 설치해 사용합니다. WebKit은 Safari의 엔진 계열이지만 브랜드가 붙은 Safari 자체는 아닙니다.
- Chrome이나 Edge를 직접 쓰려면 프로젝트에 `channel: 'chrome'`, `channel: 'msedge'`를 지정합니다.
- 기본 실행은 헤드리스입니다. 로컬에서 눈으로 보려면 `--headed`나 UI Mode를 씁니다.
- CI에서는 브라우저와 시스템 라이브러리를 `npx playwright install --with-deps`로 설치합니다.
- 공식 문서는 CI에서 세 엔진 모두를 프로젝트로 두라고 권합니다. 엔진마다 발생하는 차이(특히 WebKit)를 잡기 위해서입니다.

```ts
projects: [
  { name: 'chromium', use: devices['Desktop Chrome'] },
  { name: 'firefox', use: devices['Desktop Firefox'] },
  { name: 'webkit', use: devices['Desktop Safari'] },
]
```

한 프로젝트만 실행하려면 `npx playwright test --project=firefox`입니다. 모든 테스트를 모든 엔진에서 돌리면 시간이 세 배가 되므로 엔진별 차이를 확인할 가치가 있는 소수의 테스트만 모든 엔진에서 돌리는 구성도 가능합니다.

## Responsive Test

반응형 검증은 프로젝트마다 기기 설정(`devices`)을 지정해서 합니다. 기기 설정은 뷰포트, 사용자 에이전트, 터치 여부, 배율을 묶어 둔 값입니다.

```ts
projects: [
  { name: 'desktop', use: devices['Desktop Chrome'] },
  { name: 'mobile', use: devices['Pixel 5'] },
  { name: 'iphone', use: devices['iPhone 12'] },
]
```

개별 테스트에서는 설정을 덮어쓰거나 크기만 바꿉니다.

```ts
test.use({ viewport: { width: 375, height: 812 } })

test('모바일에서 메뉴 버튼이 보인다', async ({ page }) => {
  await page.goto('/')
  await expect(page.getByRole('button', { name: '메뉴' }))
    .toBeVisible()
})
```

- 실행 중 크기를 바꾸려면 `page.setViewportSize()`를 씁니다. 크기를 줄여 가며 레이아웃 전환 지점을 확인할 수 있습니다.
- 에뮬레이션 옵션으로 `isMobile`, `hasTouch`, `locale`, `timezoneId`, `colorScheme`('light' 또는 'dark'), `geolocation`, `permissions`, `offline`이 있습니다.
- 반응형 테스트에서 확인할 것은 같은 기능이 두 레이아웃에서 모두 되는지입니다. 모바일에서는 메뉴가 햄버거로 바뀌므로 로케이터가 같은 요소를 찾지 못할 수 있습니다. 이때 접근성 이름이 같으면 `getByRole`이 그대로 통합니다.
- 뷰포트와 UA 에뮬레이션은 실제 기기가 아닙니다. 터치 제스처의 미세한 차이나 기기 고유 버그는 에뮬레이션으로 잡히지 않습니다.

## Visual Regression

시각 회귀 테스트는 화면을 캡처해 이전에 승인한 기준 이미지(baseline)와 픽셀 단위로 비교합니다. DOM이 같아도 CSS가 깨져 달라진 모습을 잡는 용도입니다.

```ts
test('결제 화면 모습', async ({ page }) => {
  await page.goto('/checkout')
  await expect(page).toHaveScreenshot('checkout.png')
})
```

- 처음 실행하면 기준 이미지가 없으므로 이미지를 만들고 실패 처리됩니다. 기준 이미지는 커밋합니다. 다음 실행부터 비교합니다.
- 의도한 UI 변경은 `npx playwright test --update-snapshots`로 기준 이미지를 갱신하고, 갱신된 이미지를 코드 리뷰에서 눈으로 확인합니다.
- 파일 이름에 브라우저와 플랫폼이 붙습니다(예: `checkout-chromium-darwin.png`). 같은 테스트도 운영체제마다 기준 이미지가 따로 필요합니다.

| 옵션 | 의미 |
|------|------|
| `maxDiffPixels`, `maxDiffPixelRatio` | 허용할 다른 픽셀의 수·비율 |
| `threshold` | 픽셀 하나의 색 차이 허용치(기본 0.2) |
| `mask` | 지정한 요소를 색칠해 비교에서 제외(현재 시간 표시, 광고, 아바타 등) |
| `fullPage`, `clip` | 전체 페이지, 일부 영역만 캡처 |
| `stylePath` | 캡처 때만 적용할 CSS(동적 요소 숨기기) |
| `animations` | 기본 `disabled`. CSS 애니메이션과 전환을 멈춤 |

- 공식 문서는 렌더링이 OS, 버전, 설정, 하드웨어, 헤드리스 여부에 따라 달라진다고 경고합니다. 기준 이미지를 만든 환경과 같은 환경(보통 CI와 같은 컨테이너)에서 비교해야 합니다.
- 로컬 개발 컴퓨터에서 만든 기준 이미지를 CI에서 비교하면 폰트와 안티앨리어싱 차이로 계속 실패합니다. 기준 이미지는 CI 환경에서 만들어 두는 편이 안정적입니다.
- 날짜, 랜덤 값, 로딩 스피너처럼 매번 달라지는 영역은 `mask`나 Mock으로 고정합니다.
- 전체 페이지 캡처는 변경 한 곳으로 많은 테스트가 한꺼번에 실패합니다. 핵심 영역이나 컴포넌트 단위로 범위를 좁힙니다. 컴포넌트 단위 시각 회귀는 Storybook으로도 합니다(자세히는 22편).

## Critical Flow

Critical Flow는 깨지면 서비스의 가치나 매출이 바로 사라지는 핵심 사용자 경로입니다. E2E의 대상으로 우선 고르는 것은 이 경로입니다.

| 서비스 | Critical Flow 예 |
|--------|------------------|
| 쇼핑몰 | 검색 → 상품 상세 → 장바구니 → 결제 |
| SaaS | 가입 → 로그인 → 핵심 기능 한 번 사용 |
| 콘텐츠 | 로그인 → 글 작성 → 게시 → 목록 확인 |

선택 기준은 다음과 같습니다.

- 실패했을 때 비용(매출, 신뢰)이 큰 경로
- 여러 계층(UI, API, DB, 외부 연동)을 가로지르는 경로
- 컴포넌트·통합 테스트로 확인하기 어려운 브라우저 수준 동작(리다이렉트, 쿠키, 새 탭)

작성 원칙은 다음과 같습니다.

- 한 테스트는 한 사용자 목표를 처음부터 끝까지 검증합니다. 여러 목표를 이어 붙이지 않습니다.
- 사용자가 볼 수 있는 결과(텍스트, 이동, 알림)를 단언하고, 내부 구현(상태 값, CSS 클래스)은 단언하지 않습니다.
- 사전 조건은 UI가 아니라 API나 인증 상태로 준비합니다. `request` fixture로 서버에 데이터를 만들고 UI는 검증 대상 구간에만 씁니다.
- 한 테스트 안에서 `expect.soft()`를 쓰면 실패해도 중단하지 않고 끝까지 확인한 뒤 모든 실패를 보고합니다.
- 개수는 적게 유지합니다. 전체 기능을 E2E로 덮으려 하면 실행 시간과 유지 비용이 감당되지 않습니다.

## CI와 Page Object

### CI

CI에서는 푸시와 풀 리퀘스트마다 테스트를 돌립니다. 공식 문서의 GitHub Actions 예시는 다음 흐름입니다.

```yaml
name: Playwright Tests
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }
jobs:
  test:
    timeout-minutes: 60
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with: { node-version: lts/* }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test
```

마지막 단계로 리포트를 아티팩트로 올립니다.

```yaml
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: playwright-report/
```

- 리포트 폴더를 아티팩트로 올리면 실패한 실행을 내려받아 `npx playwright show-report`로 볼 수 있습니다.
- 공식 문서는 비용 때문에 Linux 러너를 권하고, 필요한 브라우저만 설치하라고 안내합니다.
- 트레이스는 `trace: 'on-first-retry'`가 권장 설정입니다. 실패한 테스트가 첫 재시도에서만 기록해 통과한 테스트의 부담을 피합니다. 설정 파일 예시는 CI에서 `retries: 2`를 둡니다.
- 워커 수는 CI에서 제한하고 로컬은 기본값을 쓰라고 안내합니다. 여러 머신으로 나눌 때는 `--shard=1/3` 같은 샤딩을 씁니다.
- 환경 변수와 시크릿(테스트 계정, API 키)은 CI의 시크릿 저장소에서 주입합니다. 운영 배포 파이프라인과의 연결은 26편에서 다룹니다.

### Page Object

Page Object Model은 한 페이지(또는 화면 일부)의 로케이터와 동작을 클래스 하나에 모아 두는 패턴입니다. 선택자가 한 곳에 있어서 UI가 바뀔 때 고칠 곳이 하나입니다.

```ts
export class LoginPage {
  constructor(private readonly page: Page) {}

  async goto() {
    await this.page.goto('/login')
  }
  async login(email: string, password: string) {
    await this.page.getByLabel('이메일').fill(email)
    await this.page.getByLabel('비밀번호').fill(password)
    await this.page
      .getByRole('button', { name: '로그인' })
      .click()
  }
}
```

```ts
test('로그인', async ({ page }) => {
  const login = new LoginPage(page)
  await login.goto()
  await login.login('a@b.com', 'pw')
  await expect(page).toHaveURL('/dashboard')
})
```

- 단언은 테스트 본문에 둡니다. Page Object는 찾기와 동작만 담당하게 하면 테스트가 무엇을 기대하는지 본문에서 읽힙니다.
- 로케이터는 생성자에 속성으로 두거나 메서드 안에서 만듭니다. 로케이터는 호출 때마다 다시 찾으므로 속성으로 저장해도 오래된 요소를 잡지 않습니다.
- 테스트가 몇 개 안 되는 작은 프로젝트에서는 Page Object가 과한 추상화일 수 있습니다. 같은 화면 조작이 여러 파일에 반복될 때 도입합니다.
- Playwright의 fixture로 Page Object를 만들어 주입하면 각 테스트에서 `new`를 쓰지 않아도 됩니다(공식 인증 문서가 `AdminPage`, `UserPage` fixture를 예로 듭니다).

## flaky 테스트 원인

flaky 테스트는 코드가 바뀌지 않았는데 통과와 실패를 오가는 테스트입니다. Playwright는 재시도에서 통과한 테스트를 `flaky`로 분류하고, 첫 시도부터 통과하면 `passed`, 모든 시도에서 실패하면 `failed`로 구분합니다. 재시도(`retries`)는 증상을 숨길 뿐 원인을 고치지 않으므로 flaky 목록을 따로 추적해서 고쳐야 합니다.

| 원인 | 증상 | 대응 |
|------|------|------|
| 고정 대기(`waitForTimeout`) | 느린 환경에서 실패 | 단언·로케이터의 자동 대기로 교체 |
| 재시도하지 않는 단언 | 값이 아직 안 바뀐 순간에 확인 | 웹 우선 단언(`await expect(locator)`) |
| Hydration 전 조작 | 클릭이 무시됨 | 상호작용 가능 상태를 나타내는 요소를 단언한 뒤 조작 |
| 테스트 간 상태 공유 | 순서에 따라 결과가 바뀜 | 테스트별 고유 데이터, 컨텍스트 격리, 직렬 모드 지양 |
| 불안정한 선택자 | DOM 변경 시 실패 | role·label 기반 로케이터 |
| 외부 서비스 의존 | 외부 장애·지연 시 실패 | `page.route`로 Mock |
| 시간·랜덤 의존 | 날짜에 따라 달라짐 | 시간 고정, 값 Mock, 스냅샷 `mask` |
| 애니메이션·가려짐 | 클릭 지점에서 다른 요소가 받음 | 자동 대기(Stable, Receives Events) 통과를 기다림, 애니메이션 비활성 |
| 리소스 경합 | 병렬 실행에서만 실패 | 워커 수 조정, 같은 리소스는 test lock |
| 환경 차이 | 로컬은 통과, CI는 실패 | 같은 브라우저 버전·컨테이너, 시각 비교 기준 이미지 일치 |

- `await`를 빼먹은 비동기 호출도 흔한 원인입니다. `@typescript-eslint/no-floating-promises` 규칙으로 잡습니다.
- 동기 단언(`expect(await locator.isVisible()).toBe(true)`)은 재시도하지 않아 flaky의 원인이 됩니다. 공식 문서는 이런 수동 단언을 피하라고 안내합니다.
- 원인 분석은 트레이스로 합니다. 단계마다의 DOM 스냅샷, 네트워크, 콘솔 로그를 되돌려 보면 어느 동작에서 무엇이 준비되지 않았는지 보입니다.
- 의심되는 테스트는 `--repeat-each=20`처럼 반복 실행하면 재현 확률이 올라갑니다.
- 직렬 모드(`test.describe.serial`)는 테스트끼리 의존할 때 쓰는 마지막 수단입니다. 공식 문서는 격리된 테스트가 더 낫다고 말합니다.
- 어쩔 수 없는 환경 문제는 `testInfo.retry`로 재시도 때만 캐시를 비우는 식으로 대응합니다.

## 핵심 정리

- E2E는 실제 브라우저에서 사용자 경로 전체를 검증하므로 느리고 비쌉니다. 깨지면 치명적인 Critical Flow에 집중하고 나머지는 더 작은 테스트로 검증합니다.
- Playwright는 role·label 로케이터와 자동 대기, 재시도하는 웹 우선 단언으로 안정성을 얻습니다. 고정 대기와 수동 단언은 flaky의 주된 원인입니다.
- 테스트마다 새 BrowserContext가 만들어져 쿠키와 스토리지가 격리됩니다. 로그인은 setup 프로젝트에서 한 번 하고 `storageState` 파일로 재사용하며, 이 파일은 커밋하지 않습니다.
- `page.route`로 요청을 Mock해 외부 서비스와 오류 상황을 고정합니다. 브라우저 요청만 가로챌 수 있고, 서버 안의 요청은 대상이 아닙니다.
- 시각 회귀는 기준 이미지와 비교하며, 같은 환경에서 만든 이미지로만 비교하고 동적 영역은 `mask`로 제외합니다.
- CI에서는 `--with-deps`로 설치하고 리포트를 아티팩트로 남기며, 트레이스는 `on-first-retry`로 기록합니다. 반복되는 조작은 Page Object로 모읍니다.

## children

`children`은 JSX 태그 사이에 넣은 내용을 컴포넌트가 받는 prop이며, 합성의 가장 기본 형태입니다. 컨테이너는 안에 무엇이 들어올지 모르는 채로 틀만 제공합니다.

```tsx
type Node = React.ReactNode

function Panel({ children }: { children: Node }) {
  return <section className="panel">{children}</section>
}

<Panel><UserProfile id={id} /></Panel>
```

- 컨테이너가 내용을 알 필요가 없으면 `children`을 씁니다. 감싸는 틀(카드, 패널, 모달 본문)이 대표적입니다.
- 중간 컴포넌트가 데이터를 전달만 하고 있다면, 안쪽 컴포넌트를 부모에서 직접 만들어 `children`으로 넘기는 편이 prop drilling을 줄입니다. react.dev가 Context보다 먼저 시도하라고 권하는 방법입니다(`<Layout posts={posts} />` 대신 `<Layout><Posts posts={posts} /></Layout>`).
- 타입은 보통 `React.ReactNode`입니다. 요소 하나만 받아야 하면 `React.ReactElement`로 좁힙니다.
- `children`을 읽어 가공(`Children.map`, `cloneElement`)하는 방식은 깨지기 쉬워 피합니다(자세히는 10편).

## Slot Pattern

Slot 패턴은 `children` 하나로 부족할 때 이름 있는 prop으로 여러 자리에 내용을 넣는 방식입니다. legacy 합성 문서는 `SplitPane`이 `left`와 `right` prop으로 두 영역을 받는 예를 보여 줍니다.

```tsx
function PageFrame({ header, sidebar, children }: {
  header: React.ReactNode
  sidebar?: React.ReactNode
  children: React.ReactNode
}) {
  return (
    <div className="frame">
      <header>{header}</header>
      {sidebar && <aside>{sidebar}</aside>}
      <main>{children}</main>
    </div>
  )
}
```

- 슬롯 prop의 타입은 `React.ReactNode`입니다. 선택 슬롯은 `?`로 두고 비었을 때 영역을 그리지 않습니다.
- 슬롯에 넣는 요소는 호출하는 쪽이 만들기 때문에, 데이터와 이벤트 처리도 호출자가 가집니다. 컨테이너는 위치만 정합니다.
- 슬롯이 많아지고 서로 의존하기 시작하면 Compound Component로 바꾸는 편이 낫습니다.
- Radix의 `Slot`·`asChild`는 이름만 같을 뿐 다른 기능입니다. 요소 자체를 교체하고 props를 병합합니다(자세히는 10편).

## Compound Component

Compound Component는 `Tabs`, `Tabs.List`, `Tabs.Trigger`처럼 짝이 되는 컴포넌트들이 Context로 상태를 암묵적으로 공유하는 패턴입니다. 호출자는 조각의 배치와 순서를 JSX로 정합니다.

- 고를 때: 부품 사이에 관계가 있는 위젯(탭, 아코디언, 메뉴, 선택 목록)입니다.
- 얻는 것: prop을 늘리지 않고 구조를 바꿀 수 있고, 접근성 속성 연결 같은 내부 약속은 컴포넌트가 책임집니다.
- 비용: Context와 부품 규약(어떤 부품이 어디 들어가야 하는지)이 생깁니다.
- 구현은 12편에서 다룹니다.

## Provider + Consumer

Provider + Consumer는 Context로 트리 아래 어디서든 값을 읽게 하는 패턴입니다. 만들고(`createContext`), 제공하고(Provider), 읽는(Consumer) 세 단계입니다.

```tsx
type Theme = 'light' | 'dark'
const ThemeContext = createContext<Theme>('light')

function App() {
  return (
    <ThemeContext value="dark">
      <Page />
    </ThemeContext>
  )
}
const theme = useContext(ThemeContext) // 'dark'
```

- React 19부터는 `<Context.Provider>` 대신 `<Context>`를 Provider로 직접 렌더링합니다. 기존 `Context.Provider`는 앞으로 deprecate될 예정입니다(React 19 발표 글). `Context.Consumer`는 옛 방식이며, react.dev는 새 코드에서 `useContext`를 쓰라고 안내합니다.
- 값은 위쪽으로 가장 가까운 Provider에서 가져옵니다. Provider가 없으면 `createContext`의 기본값이 쓰이고, 기본값은 정적이라 변하지 않는 최후 대비책입니다.
- 값이 바뀌면(`Object.is` 비교) 그 Context를 읽는 컴포넌트가 모두 다시 렌더링됩니다. 중간의 `memo`로 막을 수 없습니다.
- 객체나 함수를 값으로 넘길 때는 `useMemo`와 `useCallback`으로 감싸 매 렌더링마다 새 값이 만들어지지 않게 합니다.
- 같은 컴포넌트가 반환하는 Provider는 그 컴포넌트의 `useContext`에 영향을 주지 않습니다. Provider는 읽는 쪽보다 위에 있어야 합니다.
- `use(Context)`는 `useContext`와 같은 값을 읽되, 조건문이나 반복문 안에서도 호출할 수 있습니다.

읽는 쪽에는 커스텀 Hook을 만들어 Provider 밖에서의 사용을 막는 것이 관례입니다.

```tsx
const CartContext = createContext<Cart | null>(null)

function useCart() {
  const cart = useContext(CartContext)
  if (cart === null) {
    throw new Error('useCart는 CartProvider 안에서만 씁니다')
  }
  return cart
}
```

- 쓸 곳은 테마, 현재 사용자, 라우팅처럼 많은 컴포넌트가 읽는 값과 Compound Component의 내부 상태 공유입니다.
- Context는 prop drilling의 해법이지만 첫 선택지가 아닙니다. react.dev는 props로 시작하고, 컴포넌트를 추출해 `children`으로 넘긴 다음에 Context를 고려하라고 권합니다.

## Render Props

Render Props는 컴포넌트가 무엇을 그릴지 정하는 함수를 prop으로 받고, 내부 데이터를 인자로 넘기는 패턴입니다(정의는 10편).

```tsx
<Mouse render={(pos) => <Cat x={pos.x} y={pos.y} />} />
```

- 고를 때: 컴포넌트 내부에서만 아는 값(마우스 좌표, 선택 상태, 측정 크기)이 있고, 호출자가 그 값으로 렌더링 방식을 정해야 할 때입니다.
- 장점은 값의 출처가 인자로 드러나 데이터 흐름을 추적하기 쉽다는 점입니다. react.dev가 `cloneElement`의 대안으로 제시하는 이유입니다.
- 이름이 다른 함수 prop(`renderItem`, `renderHeader`)을 여러 개 둘 수 있습니다.
- 인라인 함수는 매 렌더링마다 새로 만들어져 `memo`나 `PureComponent`의 얕은 비교를 무력화합니다(legacy 문서의 주의점).
- 로직만 나누고 싶다면 요즘은 커스텀 Hook이 더 단순합니다. 호출자가 렌더링할 위치까지 넘겨받아야 할 때 Render Props가 남습니다.

## Function as Child

Function as Child는 Render Props를 `children` 자리에 쓰는 형태입니다. legacy 문서는 `render`라는 이름이 필요 없고 `children`도 같은 패턴이라고 설명합니다.

```tsx
type Props = {
  children: (open: boolean) => React.ReactNode
}

function Disclosure({ children }: Props) {
  const [open, setOpen] = useState(false)
  const toggle = () => setOpen(!open)
  return <div onClick={toggle}>{children(open)}</div>
}

<Disclosure>
  {(open) => <span>{open ? '접기' : '펼치기'}</span>}
</Disclosure>
```

- 장점은 JSX 중첩 모양이 자연스럽다는 점이고, 단점은 함수 하나만 받을 수 있다는 점입니다. 렌더링할 자리가 여럿이면 이름 있는 Render Props가 맞습니다.
- `children` 타입이 노드가 아니라 함수가 되므로 일반 `children`과 섞어 쓸 수 없고, 타입 선언에서 그 사실이 드러납니다.
- 렌더링마다 함수가 새로 만들어지는 비용은 Render Props와 같습니다.

## Headless UI

Headless UI는 상태, 키보드 처리, 접근성 속성 같은 동작만 제공하고 마크업과 스타일은 사용하는 쪽이 정하는 방식입니다. Radix Primitives는 스타일 없이 제공하면서 aria·role 속성, 포커스 관리, 키보드 내비게이션을 대신 처리한다고 소개합니다.

- 구현 형태는 Compound Component(Radix), 커스텀 Hook, Render Props 중 하나이거나 조합입니다.
- 고를 때: 디자인 시스템처럼 같은 동작에 여러 모양이 필요하거나, 접근성을 직접 구현하고 싶지 않을 때입니다.
- 비용: 모양을 모두 직접 만들어야 하므로 스타일 일관성은 사용자 책임입니다.
- 라이브러리 비교와 구조는 13편에서 다룹니다.

## Wrapper Component

Wrapper 컴포넌트는 기존 컴포넌트를 감싸서 기본값을 고정하거나 props를 변환하거나 동작을 덧붙이고, 나머지는 그대로 전달하는 컴포넌트입니다.

```tsx
type ButtonProps =
  React.ComponentPropsWithoutRef<typeof Button>

function DangerButton(props: ButtonProps) {
  return <Button variant="danger" {...props} />
}

function SubmitButton({ pending, ...rest }: ButtonProps & {
  pending: boolean
}) {
  return <Button disabled={pending} {...rest} />
}
```

- 쓰는 곳은 앱 안에서 반복되는 설정을 이름 붙일 때(`DangerButton`), 외부 라이브러리 컴포넌트를 앱의 규약에 맞춰 감쌀 때, 데이터 변환을 한곳에 모을 때입니다.
- 나머지 props를 `...rest`로 넘겨야 원래 컴포넌트의 API가 막히지 않습니다. 고정하고 싶은 값은 스프레드 앞에 두면 호출자가 덮어쓸 수 있고, 뒤에 두면 덮어쓸 수 없습니다.
- `ref`를 쓰는 컴포넌트를 감쌀 때는 `ref`도 전달해야 합니다. React 19부터는 함수 컴포넌트가 `ref`를 prop으로 받으므로 `...rest`에 포함됩니다.
- 렌더링 안에서 Wrapper를 새로 만들면 안 됩니다. 렌더링마다 다른 컴포넌트 타입이 되어 매번 다시 마운트되고 상태를 잃습니다(legacy HOC 문서가 경고하는 같은 문제).
- 단순히 한 단계 감싸고 props 이름만 바꾸는 Wrapper가 쌓이면 추적이 어려워집니다. 의미 있는 이름이 붙을 때만 만듭니다.

## Layout Component

Layout 컴포넌트는 자식들의 배치(간격, 정렬, 영역 나누기)만 맡고 내용은 알지 못하는 컴포넌트입니다. `children`이나 슬롯 prop으로 내용을 받습니다.

```tsx
function Stack({ gap = 8, children }: {
  gap?: number
  children: React.ReactNode
}) {
  return (
    <div style={{ display: 'grid', gap }}>
      {children}
    </div>
  )
}
```

- 종류는 한 방향으로 쌓는 `Stack`, 격자 `Grid`, 페이지 틀(`header`·`sidebar`·`main` 슬롯)입니다.
- 레이아웃은 데이터 조회나 비즈니스 로직을 가지지 않습니다. 가지면 재사용할 수 없고, 하위 컴포넌트와 의존이 생깁니다.
- 레이아웃의 반응형·간격 규칙을 한곳에 모으면 페이지 컴포넌트에서 스타일 반복이 줄어듭니다.

## Composition 우선

React는 컴포넌트 재사용에서 상속보다 합성을 택합니다. legacy 합성 문서는 컴포넌트 상속 계층을 만들어야 할 사례를 찾지 못했다고 밝히고, props와 합성이 겉모습과 동작을 명시적이고 안전하게 바꾸는 데 필요한 모든 유연성을 준다고 설명합니다. 구체적인 컴포넌트는 일반적인 컴포넌트를 렌더링하면서 props로 설정합니다(특수화).

```tsx
// ❌ 상속
class DangerButton extends Button {}

// ✅ 합성: 일반 컴포넌트를 props로 설정
const DangerButton = (p: ButtonProps) =>
  <Button variant="danger" {...p} />
```

- 합성은 의존이 props와 children이라는 명시적 통로로만 흐르므로 변경 영향이 눈에 보입니다.
- 순서는 props로 시작하고, `children`과 슬롯으로 조립하고, 필요할 때 Context나 Compound Component를 고릅니다.

### HOC와 비교

HOC(고차 컴포넌트)는 컴포넌트를 받아 새 컴포넌트를 반환하는 함수입니다. legacy 문서는 이를 React의 합성적 성격에서 나온 패턴이라고 설명하고, `React.memo`처럼 컴포넌트를 받아 컴포넌트를 반환하는 형태도 이 모양입니다.

```tsx
function withUser<P>(Wrapped: React.ComponentType<P>) {
  return function WithUser(props: P) {
    const user = useUser()
    return <Wrapped {...props} user={user} />
  }
}
```

legacy 문서가 정리한 주의점은 세 가지입니다.

| 주의점 | 내용 |
|--------|------|
| 렌더링 안에서 적용 금지 | 매 렌더링마다 새 컴포넌트가 만들어져 다시 마운트되고 상태를 잃음 |
| 정적 메서드 | 새 컴포넌트에는 원본의 정적 메서드가 없어 복사해야 함 |
| ref | `ref`는 감싼 컴포넌트가 아니라 바깥 컨테이너를 가리킴. 전달하려면 `forwardRef`가 필요 |

- props를 가로채 주입하므로 어떤 props가 어디서 왔는지 컴포넌트 선언만 보고는 알 수 없고, 여러 HOC를 겹치면 이름 충돌과 순서 문제가 생깁니다.
- 로직 재사용은 이제 커스텀 Hook이 대체합니다. react.dev에 따르면 커스텀 Hook은 상태를 담은 로직을 공유하지만 상태 자체를 공유하지는 않고, 호출마다 독립입니다. 컴포넌트 트리에 층이 늘지 않습니다.
- HOC는 클래스 컴포넌트 시절의 코드와, HOC 형태의 API를 제공하는 라이브러리에서 지금도 만납니다(자세히는 25편).

## 패턴 선택 기준표

| 상황 | 패턴 | 이유 | 비용 |
|------|------|------|------|
| 감싸는 틀 하나 | `children` | 가장 단순함 | 가공 불가 |
| 영역이 둘에서 넷인 틀 | Slot(이름 있는 prop) | 위치를 이름으로 지정 | 슬롯이 많아지면 prop 폭증 |
| 부품이 서로 의존하는 위젯 | Compound Component | 구조를 JSX로 조립, 상태는 암묵 공유 | Context와 부품 규약 |
| 멀리 있는 컴포넌트가 같은 값을 읽음 | Provider + Consumer | prop drilling 제거 | 값 변경 시 모든 Consumer 재렌더링 |
| 내부 데이터로 호출자가 렌더링 | Render Props | 데이터 출처가 인자로 드러남 | 인라인 함수, 중첩 |
| 렌더링 자리가 하나이고 값만 받음 | Function as Child | 간결한 JSX | 함수 하나만 가능 |
| 동작은 같고 모양이 여럿 | Headless UI | 접근성·키보드는 내부 책임 | 모양은 직접 구현 |
| 앱 안 설정 반복, 라이브러리 어댑터 | Wrapper | 이름 붙은 재사용 | 단순 위임이 쌓이면 추적 어려움 |
| 배치와 간격만 | Layout | 로직 없이 재사용 | 내용 지식 없음 |
| 로직만 재사용 | 커스텀 Hook | 트리에 층 추가 없음 | 렌더링 위치 결정은 못 함 |
| 요소 자체를 호출자가 교체 | `asChild`, `as` | 래퍼 요소 없이 동작 부여 | 자식이 props와 ref를 전달해야 함 |

- 선택 순서: props → `children`/Slot → Hook → Compound Component → Context → Render Props. 위쪽이 더 단순하고 추적이 쉽습니다.
- 한 컴포넌트가 여러 패턴을 함께 쓰는 것이 흔합니다. Radix 같은 Headless 라이브러리는 Compound Component, Context, Slot(`asChild`), Controlled·Uncontrolled를 모두 조합합니다.

## 핵심 정리

- 합성은 `children`, 슬롯 prop, Compound Component, Context, Render Props 같은 명시적 통로로 컴포넌트를 조립하는 방식이며, React는 상속이 아니라 합성을 권장합니다.
- `children`은 내용을 모르는 틀에, Slot 패턴은 영역이 여럿인 틀에 쓰고, `children`을 가공하는 방식(`Children.map`, `cloneElement`)은 피합니다.
- Provider + Consumer는 가장 가까운 Provider의 값을 읽고 값이 바뀌면 모든 Consumer가 다시 렌더링되므로, props와 `children`으로 해결할 수 없을 때 씁니다.
- Render Props와 Function as Child는 내부 데이터를 인자로 넘겨 호출자가 렌더링하게 하며, 인라인 함수가 메모이제이션을 무력화할 수 있습니다.
- Wrapper는 기본값 고정과 props 변환에, Layout은 배치에 쓰고, 둘 다 나머지 props를 전달하고 렌더링 안에서 새로 만들지 않습니다.
- HOC는 props 출처가 감춰지고 ref·정적 메서드 문제가 있어서, 로직 재사용은 커스텀 Hook이 대체합니다.

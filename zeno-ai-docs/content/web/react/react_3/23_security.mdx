## XSS

XSS(Cross-Site Scripting)는 공격자가 만든 스크립트가 내 사이트의 출처(origin)에서 실행되게 만드는 공격입니다. 스크립트가 내 사이트 안에서 돌기 때문에 같은 출처 정책을 우회합니다.

| 유형 | 경로 |
|------|------|
| 저장형 | 댓글·프로필처럼 저장된 입력이 다른 사용자에게 렌더링됨 |
| 반사형 | URL 파라미터가 응답에 그대로 반영됨 |
| DOM 기반 | 브라우저의 JavaScript가 입력을 위험한 API(`innerHTML` 등)에 넣음 |

스크립트가 실행되면 공격자는 페이지 내용과 로컬 스토리지를 읽고, 사용자의 인증 정보로 HTTP 요청을 보내고, 사용자를 사칭할 수 있습니다. 그래서 인증 토큰을 어디에 두든 XSS가 뚫리면 피해가 큽니다.

React는 기본 방어를 제공합니다. JSX에 넣은 값은 렌더링 전에 이스케이프되어 텍스트로 처리됩니다.

```jsx
const input = '<img src=x onerror=alert(1)>'
return <p>{input}</p>
// 화면에 문자열 그대로 표시. 스크립트는 실행되지 않음
```

기본 방어가 뚫리는 곳은 이스케이프를 우회하는 지점입니다.

- `dangerouslySetInnerHTML`로 HTML 문자열을 직접 넣는 곳
- `href`, `src` 같은 URL 속성에 신뢰할 수 없는 값을 넣는 곳(`javascript:` 등)
- `ref.current.innerHTML`, `document.write`, `eval` 등 DOM·실행 API를 직접 쓰는 곳
- 서버에서 직접 만든 HTML(템플릿, 마크다운 변환 결과)을 그대로 응답하는 곳
- 취약한 의존성이나 서드파티 스크립트

방어는 한 겹이 아니라 여러 겹입니다. OWASP의 원칙도 단일 기법으로 XSS가 해결되지 않는다는 것입니다. 이 문서의 순서는 입력을 다루는 단계(이스케이프, sanitization)에서 시작해 실행을 제한하는 단계(CSP)로 이어집니다.

**흔한 실수:** 입력 검증만으로 XSS를 막으려는 것입니다. 입력에서 `<script>`를 지우는 방식은 우회가 쉽습니다. 출력할 위치(HTML 본문, 속성, URL, 스크립트)에 맞게 인코딩하는 것이 기본이고, 이스케이프는 렌더링 시점에 합니다.

## dangerouslySetInnerHTML

`dangerouslySetInnerHTML`은 DOM의 `innerHTML`에 해당하는 React의 prop으로, `__html` 키를 가진 객체를 받아 HTML 문자열을 그대로 넣습니다. 이름이 위험을 경고합니다.

```jsx
const markup = { __html: '<p>some raw html</p>' }
return <div dangerouslySetInnerHTML={markup} />
```

공식 문서의 경고는 신뢰할 수 없는 출처의 마크업이면 XSS 취약점을 만들기 쉽다는 것입니다. 아래는 공식 문서가 보안 결함으로 드는 예입니다.

```jsx
// 🔴 신뢰할 수 없는 입력을 그대로 넣음
const post = { content: '<img src="" onerror="alert(1)">' }
function Preview() {
  const markup = { __html: post.content }
  return <div dangerouslySetInnerHTML={markup} />
}
// 이미지 로드 실패로 onerror가 실행된다
```

- 같은 요소에 `children`과 `dangerouslySetInnerHTML`을 함께 쓸 수 없습니다.
- 공식 문서의 권고: `{__html}` 객체는 HTML을 만드는 지점 가까이에서 만들어 "이것은 원본 HTML"임을 드러내고, 인라인 객체(`dangerouslySetInnerHTML={{ __html: x }}`)는 피합니다.
- 사이트가 Trusted Types를 강제한다면 `__html`에 보안 정책이 만든 `TrustedHTML` 값을 넘깁니다.
- 안전한 경우는 출처를 완전히 신뢰하거나(자기 서버가 만든 정적 콘텐츠), sanitization을 거친 결과뿐입니다.
- 마크다운이나 리치 텍스트를 보여 주려면 React 컴포넌트로 렌더링하는 마크다운 라이브러리를 쓰면 HTML 문자열이 아니라 React 요소가 만들어져 이스케이프가 유지됩니다.

대부분의 화면에서 `dangerouslySetInnerHTML`이 필요한 경우는 사용자가 작성한 서식 있는 글(리치 텍스트), CMS 본문, 이메일 본문 정도입니다. 그 경우도 sanitization이 필수입니다.

## Sanitization

Sanitization은 HTML 문자열에서 실행 가능한 부분(스크립트, 이벤트 핸들러 속성, 위험한 URL)을 제거해 안전한 부분만 남기는 처리입니다. 직접 정규식으로 만들지 않고, 검증된 라이브러리인 DOMPurify를 씁니다. OWASP도 사용자가 HTML을 작성하는 경우 DOMPurify 같은 라이브러리를 권합니다.

```jsx
import DOMPurify from 'dompurify'

function Rich({ html }) {
  const clean = DOMPurify.sanitize(html)
  return <div dangerouslySetInnerHTML={{ __html: clean }} />
}
```

- 허용 범위는 옵션으로 좁힙니다: `ALLOWED_TAGS: ['b', 'i', 'a']`, `USE_PROFILES: { html: true }`. 필요한 만큼만 허용하는 것이 안전합니다.
- 태그·속성 추가는 `ADD_TAGS`, `ADD_ATTR`로 합니다. 늘릴수록 공격 면이 넓어집니다.
- DOMPurify는 DOM이 필요한 브라우저 라이브러리입니다. Node(서버 렌더링)에서는 jsdom 같은 DOM 구현이 필요하고, 공식 문서는 jsdom을 최신으로 유지하라고 안내합니다.
- sanitization한 뒤 문자열을 다시 가공하면 방어가 무효가 될 수 있습니다. 결과를 바로 사용합니다.
- sanitizer도 취약점이 발견되므로 의존성 점검 대상입니다(아래 "의존성 취약점 점검").
- 서버에 저장할 때 sanitization하는 방식과 렌더링 때 하는 방식 중, 렌더링 직전에 하는 쪽이 정책 변경과 신규 우회 기법에 대응하기 쉽습니다. 서버에서 한 번 더 하는 이중 방어도 흔합니다.

**흔한 실수:**

- 클라이언트에서만 sanitization하고 서버가 받은 HTML을 다른 경로(이메일, PDF, 관리자 화면)에 그대로 쓰는 것입니다. 출력하는 곳마다 방어합니다.
- sanitization 결과가 안전하다고 믿고 `href`에 쓰는 URL 검증을 생략하는 것입니다.

## URL 스킴 주입

`href`, `src`, `action` 같은 URL 속성에 `javascript:` 스킴의 값이 들어가면, 클릭하는 순간 그 코드가 실행됩니다. 이스케이프는 이 경우를 막지 못합니다. 값 자체가 올바른 문자열이기 때문입니다.

```jsx
const site = 'javascript:alert(document.cookie)'
return <a href={site}>홈페이지</a>
// 클릭하면 코드가 실행될 수 있는 URL
```

- MDN은 `javascript:` URL을 `href` 등에 주입하는 것을 XSS 공격 경로의 하나로 설명합니다.
- React는 이 문제를 알려 왔습니다. React 19 업그레이드 가이드의 breaking change 목록에 `src`와 `href`의 `javascript:` URL이 에러로 처리된다는 항목이 있습니다. 다만 이것에 의존하지 않습니다. 모든 속성과 모든 스킴을 막아 주지는 않기 때문에 앱이 직접 검증해야 합니다.
- CSP를 설정하면 `javascript:` URL도 기본으로 막힙니다(아래 "CSP").
- `javascript:` 자체를 코드에서 쓰는 것(`href="javascript:void(0)"`)도 피합니다. 동작이 목적이면 `button`과 이벤트 핸들러를 씁니다.

사용자가 입력한 URL을 링크로 쓸 때는 차단 목록(`javascript:`를 걸러 냄)이 아니라 허용 목록으로 검증합니다. `URL` 생성자로 파싱한 뒤 스킴이 허용 목록에 있는지 확인합니다.

```js
function safeHref(value) {
  try {
    const url = new URL(value, window.location.origin)
    const ok = ['https:', 'http:', 'mailto:']
    return ok.includes(url.protocol) ? url.href : '#'
  } catch {
    return '#'
  }
}
```

- 대문자(`JavaScript:`)나 앞쪽 공백·제어 문자로 단순한 문자열 비교를 우회할 수 있으므로, 문자열 비교보다 파서가 돌려준 `protocol`을 비교합니다.
- 리다이렉트 URL 파라미터(`?next=...`)도 같은 이유로 같은 출처의 경로만 허용합니다. 그렇지 않으면 열린 리다이렉트가 됩니다.

## CSRF

CSRF(Cross-Site Request Forgery)는 다른 사이트가 사용자의 브라우저를 시켜 내 서비스로 요청을 보내게 하는 공격입니다. 요청에 사용자의 쿠키가 자동으로 붙기 때문에 서버는 정상 요청과 구별하지 못합니다. 세션을 쿠키로 유지하는 방식에서 생기는 문제입니다.

- 공격은 숨겨진 폼 자동 제출이나 이미지 태그로 시작합니다. 요청의 응답을 읽는 것이 아니라 상태를 바꾸는 요청을 일으키는 것이 목적입니다.
- GET은 어디서든 보낼 수 있는 단순 요청이므로 상태를 바꾸는 데 쓰지 않습니다.

방어 수단은 다음과 같습니다.

| 방어 | 내용 |
|------|------|
| `SameSite` 쿠키 | `Strict`는 교차 사이트 요청에 쿠키를 보내지 않음, `Lax`는 안전한 메서드의 최상위 이동에만 보냄, `None`은 항상 보냄(`Secure` 필요) |
| CSRF 토큰 | 서버가 예측 불가능한 토큰을 페이지에 심고, 상태 변경 요청에 포함시켜 검증 |
| 단순 요청 회피 | `fetch`에 커스텀 헤더나 JSON 콘텐츠 타입을 쓰면 교차 출처에서는 사전 요청(preflight)이 필요해 CORS 없이는 막힘 |
| Fetch Metadata | `Sec-Fetch-Site` 헤더가 같은 출처·같은 사이트인 요청만 허용 |
| Origin 검증 | `Origin` 헤더를 서버의 호스트와 비교 |

- 브라우저는 `SameSite`를 지정하지 않은 쿠키를 `Lax`로 처리합니다. 그래도 명시적으로 쓰는 것이 안전합니다.
- `SameSite`는 사이트(site) 단위여서 서브도메인 간 요청은 같은 사이트로 취급됩니다. 이것만으로 완전한 방어가 아니라 다른 방어와 겹쳐 씁니다.
- `Authorization: Bearer` 헤더로 토큰을 직접 붙이는 방식은 브라우저가 자동으로 붙이지 않으므로 CSRF에 강합니다. 대신 토큰을 JavaScript가 다뤄야 해서 XSS에 노출됩니다(다음 절).
- Next.js의 Server Action은 POST로만 호출되고, `Origin` 헤더와 `Host` 헤더를 비교해 다르면 요청을 중단합니다. 프록시 뒤에 있는 경우 `serverActions.allowedOrigins`로 허용 출처를 지정합니다.

**흔한 실수:** SPA가 쿠키 인증을 쓰면서 "JSON API라서 안전하다"고 생각하는 것입니다. 서버가 다른 콘텐츠 타입도 JSON으로 받아 주거나 CORS를 느슨하게 열어 두면 단순 요청 회피가 깨집니다. `SameSite`와 Origin 검증을 같이 둡니다.

## 인증 Token과 저장 위치

인증은 로그인 후 서버가 발급한 자격 증명을 이후 요청에 실어 보내는 방식입니다. 대표 형태는 서버가 상태를 저장하는 세션 ID와 서버가 상태를 저장하지 않는 JWT(JSON Web Token)입니다. 인증 흐름의 전체 구조는 18편에서 다룹니다. 여기서는 클라이언트에서 토큰을 어디에 두는지가 쟁점입니다.

| 저장 위치 | 읽을 수 있는 쪽 | XSS | CSRF |
|-----------|------------------|-----|------|
| `HttpOnly` 쿠키 | 서버만(JavaScript는 못 읽음) | 토큰 탈취는 막음 | 자동 전송되므로 방어 필요 |
| 메모리(JS 변수) | 실행 중인 스크립트 | 페이지가 열려 있는 동안 접근 가능 | 자동 전송 안 됨 |
| `localStorage`, `sessionStorage` | 같은 출처의 모든 스크립트 | 한 번의 XSS로 전부 탈취 | 자동 전송 안 됨 |

- OWASP는 세션 식별자를 localStorage에 두지 말라고 권합니다. JavaScript가 항상 접근할 수 있고, 한 번의 XSS로 저장된 값이 모두 유출되기 때문입니다. `httpOnly` 쿠키가 이 위험을 줄입니다.
- `HttpOnly`는 `document.cookie`로 읽는 것을 막습니다. XSS 자체를 막는 것도, 공격 스크립트가 그 쿠키가 붙는 요청을 보내는 것도 막지 못합니다. 토큰이 유출되는 것을 막는 방어일 뿐입니다.
- 쿠키를 쓰면 `HttpOnly`, `Secure`(HTTPS에서만 전송), `SameSite`를 함께 지정합니다. `__Host-` 접두사는 `Secure`, `Path=/`, `Domain` 없음을 강제해 하위 도메인이 덮어쓰는 것을 막습니다.

```http
Set-Cookie: __Host-sid=abc123; Secure; HttpOnly;
  Path=/; SameSite=Lax
```

실무에서 흔한 조합은 다음과 같습니다.

- 서버 렌더링이 있는 앱: 세션 쿠키(`HttpOnly`, `Secure`, `SameSite`)와 CSRF 방어.
- SPA와 별도 API 서버: 수명이 짧은 액세스 토큰은 메모리에 두고, 재발급용 리프레시 토큰은 `HttpOnly` 쿠키에 둡니다. 새로고침으로 메모리가 비면 쿠키로 재발급합니다.
- 액세스 토큰의 수명을 짧게(분 단위) 하고, 리프레시 토큰은 교체(rotation)해서 탈취된 토큰의 쓸모를 줄입니다.
- 서버가 상태를 저장하지 않는 JWT는 발급 후 서버가 무효화하기 어렵습니다. 로그아웃과 강제 만료가 필요하면 짧은 수명과 서버 쪽 차단 목록 또는 세션 방식을 씁니다.
- 토큰을 URL 쿼리에 담지 않습니다. 브라우저 기록, 서버 로그, Referer 헤더로 새어 나갑니다.

**흔한 실수:** `localStorage`에 JWT를 두고 "HTTPS라서 안전하다"고 믿는 것입니다. HTTPS는 전송 구간을 보호할 뿐 페이지 안에서 실행되는 스크립트는 막지 못합니다.

## 민감 정보 노출 금지

브라우저에 전달되는 모든 것은 사용자가 볼 수 있습니다. JavaScript 번들, 소스맵, 네트워크 응답, HTML, RSC payload(자세히는 04편)가 모두 포함됩니다. 난독화와 압축은 보안이 아닙니다. 클라이언트가 알면 안 되는 값은 클라이언트로 보내지 않는 것이 유일한 방어입니다.

| 보내면 안 되는 것 | 이유 |
|-------------------|------|
| API 시크릿 키, DB 접속 정보, 서명 키 | 번들·네트워크에서 그대로 읽힘 |
| 다른 사용자의 개인 정보 | 화면에 안 보여도 응답에 있으면 노출 |
| 내부 필드(비밀번호 해시, 내부 ID, 권한 플래그) | DB 레코드를 통째로 반환하면 따라 나감 |
| 에러의 스택 트레이스·쿼리 | 내부 구조 노출 |

- 응답에는 화면이 필요한 필드만 담습니다. DB 레코드를 그대로 반환하지 않고 필요한 필드만 고른 전송 객체(DTO)를 만듭니다.
- 클라이언트 코드에 있는 검사(`if (user.isAdmin)`)는 화면 편의일 뿐 보안이 아닙니다. 실제 방어는 서버가 합니다.
- `console.log`로 토큰과 개인 정보를 남기지 않습니다. 운영 로그와 에러 모니터링(26편)으로 전송되는 데이터도 같은 기준으로 걸러 냅니다.
- 프로덕션에서 소스맵을 공개 배포하면 원본 소스가 노출됩니다. 에러 모니터링 서비스에만 업로드하는 구성이 흔합니다(자세히는 26편).
- 서버 컴포넌트에서 가져온 객체를 클라이언트 컴포넌트에 props로 넘기면 그 객체 전체가 직렬화되어 브라우저로 갑니다. 서버에서 필요한 값만 골라 넘깁니다.
- React의 `experimental_taintObjectReference`와 `experimental_taintUniqueValue`는 지정한 객체나 값이 클라이언트 컴포넌트로 전달되면 에러를 냅니다. 실험 기능이고 `{...user}`처럼 복제하면 우회되므로 공식 문서도 보조 방어선으로만 쓰라고 합니다.

## 환경 변수

환경 변수는 코드 밖에서 설정을 주입하는 방법이고, 비밀값을 코드에 하드코딩하지 않는 기본 수단입니다. 하지만 클라이언트용 환경 변수는 비밀이 아닙니다. 번들러가 빌드할 때 값을 코드에 문자열로 박아 넣기 때문입니다.

| 도구 | 클라이언트에 노출되는 조건 | 서버에서만 보이는 것 |
|------|---------------------------|----------------------|
| Vite | `VITE_` 접두사가 붙은 변수가 `import.meta.env`로 번들에 포함 | 접두사 없는 변수 |
| Next.js | `NEXT_PUBLIC_` 접두사가 붙은 변수가 `process.env` 참조를 값으로 치환 | 접두사 없는 변수(기본값) |

- Vite 공식 문서는 `VITE_*` 변수에 API 키 같은 민감한 정보를 넣지 말라고 경고하고, 비밀값은 백엔드나 서버리스·엣지 함수에서 처리하라고 안내합니다.
- Next.js는 접두사 없는 변수를 브라우저에 노출하지 않습니다. `NEXT_PUBLIC_` 변수는 `next build` 시점에 값이 고정됩니다. 같은 빌드를 여러 환경에 배포하면 모두 빌드 때의 값을 갖습니다.
- `.env` 파일은 저장소에 올리지 않습니다. Vite는 `.env.local`과 `.env.[mode].local`을 Git에서 제외하는 것을 권하고(`*.local`을 `.gitignore`에), Next.js의 기본 템플릿은 `.env` 파일들을 `.gitignore`에 넣습니다.
- 접두사 때문에 노출된 값은 바꿀 수 있는 키(공개용 분석 ID, 지도 API 키 등)여야 하고, 노출돼도 되도록 제공자 쪽에서 도메인·사용량 제한을 겁니다.
- 한 번 노출된 비밀값은 삭제가 아니라 폐기(재발급)해야 합니다. Git 기록, 빌드 캐시, CDN에 이미 복사됐을 수 있습니다.
- 환경 분리와 배포 파이프라인의 비밀 관리는 26편에서 다룹니다.

**흔한 실수:** 비밀 키를 `VITE_API_SECRET`이나 `NEXT_PUBLIC_SECRET`으로 이름 붙이는 것입니다. 이름에 접두사를 붙이는 순간 번들에 포함됩니다.

## 클라이언트 번들에 비밀값이 들어가는 경로

비밀값이 번들에 들어가는 경로는 환경 변수 접두사만이 아닙니다. 코드 리뷰에서 확인할 경로는 다음과 같습니다.

| 경로 | 설명 | 대응 |
|------|------|------|
| 공개 접두사 환경 변수 | `VITE_`·`NEXT_PUBLIC_` 변수 | 비밀값에 접두사를 쓰지 않음 |
| 하드코딩 | 소스에 키를 직접 씀 | 환경 변수로 분리, 비밀 스캔 도구 |
| 서버 모듈 import | `'use client'` 파일이나 그 의존성이 DB·시크릿 모듈을 import | `server-only`로 빌드 에러화(자세히는 04편) |
| props 전달 | 서버 컴포넌트가 객체 전체를 클라이언트 컴포넌트에 넘김 | 필요한 필드만 넘김, 타입을 좁게 정의 |
| Server Function 반환값·클로저 | 반환값은 직렬화되어 클라이언트로 감, 컴포넌트 안에서 정의한 함수의 클로저 값도 클라이언트를 거쳐 전달 | 필요한 값만 반환, 비밀을 클로저에 담지 않음 |
| 소스맵 | 원본 소스를 복원 가능 | 공개 배포 금지 |
| 설정 파일 | `define` 치환이나 설정 객체를 통째로 주입 | 클라이언트용 설정을 따로 분리 |

- `server-only` 패키지는 클라이언트 환경에서 import되면 빌드 에러를 내서 서버 전용 모듈이 클라이언트 번들에 섞이는 것을 막습니다(Next.js는 내부에서 처리). `client-only`는 반대 방향입니다.
- Next.js 공식 가이드는 새 프로젝트에 데이터 접근 계층(DAL)을 권합니다. 서버에서만 실행되고, 권한 검사를 하고, 안전한 최소 DTO를 반환하게 만들며 `process.env` 접근도 이 계층에서만 합니다.
- Server Function이 클로저로 값을 잡는 경우 Next.js는 그 값을 암호화해서 전달하지만, 공식 문서는 암호화에만 의존하지 말라고 말합니다.
- 배포한 번들에 비밀값이 있는지는 빌드 결과물에서 문자열을 검색하는 것으로 확인할 수 있습니다. 비밀 스캔 도구를 CI에 두는 것도 방법입니다.

## Server Function 보안

Server Function(`'use server'`)은 클라이언트에서 호출할 수 있는 서버 함수이고, 실체는 공개된 네트워크 엔드포인트입니다. 컴포넌트가 호출하는 방식으로만 쓰일 것이라고 가정하면 안 됩니다. 정의는 05편에서 다룹니다. 여기서는 공격 관점을 정리합니다.

- 호출은 일반 POST 요청으로 도달합니다. Next.js 문서도 내보낸 Server Action은 UI가 아니라 직접 POST 요청으로 닿을 수 있다고 설명합니다. 어디에서도 import되지 않은 함수도 같은 취급을 해야 합니다.
- 인자는 신뢰할 수 없는 입력입니다. 폼 데이터, URL 파라미터, 헤더, `searchParams`를 모두 검증합니다. 스키마 검증(Zod 등)을 함수 안에서 합니다(자세히는 05편).
- 페이지에서 한 인증 검사는 그 안의 Server Function으로 이어지지 않습니다. 함수 안에서 매번 다시 확인합니다.
- 반환값은 직렬화되어 클라이언트로 갑니다. DB 레코드를 그대로 반환하지 않고 UI가 필요한 값만 반환합니다.
- 비용이 큰 작업(메일 발송, 쓰기)에는 요청 횟수 제한(rate limiting)을 둡니다.
- 렌더링 중에 쿠키 삭제나 캐시 무효화 같은 변경을 하지 않고, 변경은 Server Function으로 처리합니다.
- CSRF는 POST 전용 호출, `SameSite` 기본값, Next.js의 `Origin`과 `Host` 비교로 막습니다(앞의 "CSRF").

2025년 12월에 공개된 React Server Components 취약점은 이 엔드포인트가 실제로 공격받은 사례입니다. React 공식 블로그 발표 기준입니다(자세히는 05편).

| CVE | 유형 | 심각도(CVSS) |
|-----|------|--------------|
| CVE-2025-55182 | 인증 없는 원격 코드 실행 | Critical(10.0) |
| CVE-2025-55184, CVE-2025-67779, CVE-2026-23864 | 서비스 거부 | High(7.5) |
| CVE-2025-55183 | 소스 코드 노출(하드코딩된 비밀값 포함) | Medium(5.3) |

- 영향받는 패키지는 `react-server-dom-webpack`, `react-server-dom-parcel`, `react-server-dom-turbopack`이고, 서버가 있고 RSC를 지원하는 프레임워크(Next.js, React Router, Waku 등)를 쓰는 앱이 대상입니다. 서버를 쓰지 않는 앱은 영향받지 않습니다.
- RCE는 19.0.1, 19.1.2, 19.2.1에서 고쳐졌고, DoS와 소스 노출은 19.0.4, 19.1.5, 19.2.4에서 고쳐졌습니다. 19.0.3, 19.1.4, 19.2.3은 불완전한 수정이므로 다시 올려야 합니다.
- 교훈은 세 가지입니다. 프레임워크와 RSC 의존성을 패치 버전으로 유지하고, 소스에 비밀값을 하드코딩하지 않고, 인증·검증을 함수 안에서 합니다.

## 권한 검증

인증(Authentication)은 누구인지 확인하는 일이고, 인가(Authorization)는 이 사용자가 이 자원에 이 작업을 해도 되는지 확인하는 일입니다. 인증만 하고 인가를 빠뜨리면 로그인한 사용자가 다른 사용자의 데이터에 접근하는 IDOR(Insecure Direct Object Reference) 취약점이 됩니다.

```ts
'use server'
export async function deletePost(postId: string) {
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')

  const post = await db.post.findUnique({
    where: { id: postId },
  })
  if (post.authorId !== session.user.id) {
    throw new Error('Forbidden')
  }
  await db.post.delete({ where: { id: postId } })
}
```

- 권한은 서버에서, 요청마다, 자원 단위로 검사합니다. 클라이언트의 `isAdmin` 상태나 URL 파라미터(`?isAdmin=true`)를 믿지 않습니다.
- 숨긴 버튼이나 막아 둔 라우트(클라이언트 라우터의 가드)는 사용자 경험일 뿐 보안이 아닙니다. 같은 기능의 API가 인가를 검사해야 합니다(자세히는 18편).
- 인증 검사를 함수마다 복사하지 않고 한 계층(데이터 접근 계층, 미들웨어, 래퍼 함수)에 모아 누락을 줄입니다. 인가 검사가 없는 코드 경로가 없는지 감사할 수 있는 구조가 안전합니다.
- Next.js 가이드의 감사 항목: DAL이 분리돼 있는지, `'use client'` 파일의 props가 비공개 데이터를 요구하는지, `'use server'` 파일에서 인자를 검증하고 다시 인가하며 소유권을 확인하는지, 동적 경로 파라미터를 검증하는지.
- 실패 응답은 내부 정보를 드러내지 않게 일반적인 메시지로 줍니다. 존재하지 않음과 권한 없음을 구분하지 않아야 하는 경우도 있습니다.
- 세션 만료와 토큰 재발급 실패 시 서버가 401을 주고, 클라이언트는 로그인으로 보내는 흐름을 일관되게 둡니다.

## CSP

CSP(Content Security Policy)는 브라우저에게 어떤 출처의 스크립트와 리소스를 허용할지 알려 주는 응답 헤더입니다. XSS가 뚫려도 주입된 스크립트의 실행을 막아 피해를 줄이는 마지막 방어선입니다. OWASP는 CSP를 단독 방어가 아니라 심층 방어(defense in depth)로 두라고 합니다.

```http
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-RANDOM';
  object-src 'none'; base-uri 'none'
```

- `default-src`는 지정되지 않은 리소스의 기본 정책이고, `script-src`는 스크립트 출처입니다.
- `default-src`나 `script-src`를 지정하면 기본적으로 인라인 `<script>`, 인라인 이벤트 핸들러(`onerror` 등), `javascript:` URL, `eval()` 계열이 차단됩니다.
- 인라인 스크립트가 꼭 필요하면 nonce(요청마다 새로 만드는 예측 불가능한 값)나 해시로 허용합니다. nonce는 동적 콘텐츠, 해시는 정적 콘텐츠에 맞습니다. `'strict-dynamic'`은 nonce·해시로 신뢰된 스크립트가 불러오는 스크립트를 허용합니다.
- `object-src 'none'`, `base-uri` 제한, `frame-ancestors`(클릭재킹 방어)를 함께 둡니다.
- 처음부터 강제하지 말고 `Content-Security-Policy-Report-Only` 헤더로 위반만 보고받으며 정책을 다듬은 뒤 적용합니다.
- 헤더는 서버나 호스팅이 보냅니다. Vite 기반 SPA는 정적 호스팅의 헤더 설정(S3·CloudFront, Netlify, Vercel)에서 지정합니다(자세히는 26편).
- Next.js는 nonce를 `proxy`에서 요청마다 만들고, 렌더링 중에 프레임워크 스크립트에 자동 적용합니다. nonce를 쓰려면 모든 페이지가 동적 렌더링이어야 해서 정적 최적화와 ISR을 쓸 수 없고, CDN 캐시와 PPR도 어려워집니다. 대안으로 실험 기능인 SRI(해시 기반)가 있습니다.
- 개발 모드에서는 React가 디버깅 정보를 위해 `eval`을 쓰므로 `'unsafe-eval'`이 필요하고 프로덕션에서는 필요 없습니다.
- 서드파티 스크립트(분석, 광고)는 CSP에 출처를 추가해야 하고, 허용 범위가 넓을수록 방어가 약해집니다.

**흔한 실수:** 인라인 스크립트가 막힌다고 `'unsafe-inline'`을 추가하는 것입니다. 그러면 주입된 인라인 스크립트도 실행돼 CSP의 XSS 방어가 사실상 사라집니다.

## 의존성 취약점 점검

React 앱의 코드 대부분은 npm 의존성입니다. 의존성의 취약점이 곧 내 앱의 취약점이 됩니다. 앞에서 본 2025년 12월 사건도 의존성(React, 프레임워크) 취약점이었습니다.

- `npm audit`은 의존성 트리를 보안 권고 데이터베이스와 대조해 알려진 취약점을 보고합니다. `npm audit fix`는 호환 가능한 업데이트를 적용하고, 자동으로 고쳐지지 않는 항목은 수동 검토가 필요합니다.
- CI에서 `npm audit --audit-level=high`처럼 기준 심각도를 정하면 해당 심각도 이상일 때 실패 종료 코드를 반환해 빌드를 막을 수 있습니다. `--omit=dev`로 개발 의존성을 제외할 수 있습니다.
- `npm audit signatures`는 레지스트리 서명과 출처 증명(provenance)을 검증합니다.
- 잠금 파일(`package-lock.json`)을 커밋하고 CI에서 `npm ci`로 같은 버전을 설치합니다. 예기치 않은 버전 변동이 줄어듭니다.
- 의존성 업데이트 자동화(Dependabot, Renovate)로 패치 버전을 빨리 반영합니다. 보안 권고가 나오면 프레임워크와 React의 패치 버전부터 확인합니다.
- 권고가 모두 내 코드에 해당하는 것은 아닙니다. 취약한 코드 경로를 실제로 쓰는지 확인해 우선순위를 정합니다. 개발 도구에만 있는 취약점은 위험이 낮습니다.
- 의존성이 늘수록 공급망 공격(악성 패키지, 탈취된 계정으로 올라온 새 버전) 위험이 커집니다. 의존성 수를 줄이고, 설치 스크립트를 실행하는 패키지를 주의하고, 이름이 비슷한 패키지(오타 선점)를 확인합니다.
- 서드파티 스크립트(CDN으로 불러오는 것)에는 Subresource Integrity(`integrity` 속성)와 CSP로 변조를 막습니다.

## 핵심 정리

- React는 JSX 값을 이스케이프하므로 기본은 안전하고, `dangerouslySetInnerHTML`, `href` 같은 URL 속성, DOM 직접 조작이 이스케이프를 우회하는 지점입니다. HTML을 넣어야 하면 DOMPurify로 sanitization합니다.
- 사용자 입력 URL은 허용 스킴 목록(`https:`, `http:`, `mailto:`)으로 `URL` 파서를 거쳐 검증하고, CSP는 인라인 스크립트와 `javascript:` URL을 막는 심층 방어입니다.
- 쿠키 인증에는 CSRF 방어(`SameSite`, 토큰, Origin 검증)가 필요하고, 토큰은 `localStorage`가 아니라 `HttpOnly`·`Secure` 쿠키나 짧은 수명의 메모리에 둡니다.
- 클라이언트에 전달된 것은 모두 공개입니다. `VITE_`·`NEXT_PUBLIC_` 변수, 하드코딩, props 전달, 서버 모듈 import가 번들에 비밀값이 들어가는 경로이고 `server-only`와 DTO로 막습니다.
- Server Function은 공개 엔드포인트이므로 함수 안에서 인자 검증, 인증, 소유권 인가를 매번 합니다. 2025년 12월 RSC 취약점은 19.0.4, 19.1.5, 19.2.4 이상으로 올려야 합니다.
- `npm audit`을 CI에 두고 잠금 파일과 자동 업데이트로 패치를 빨리 반영합니다.

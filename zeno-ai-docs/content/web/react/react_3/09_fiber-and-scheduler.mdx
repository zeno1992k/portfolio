## Stack Reconciler의 한계

Stack Reconciler는 React 15 이하가 쓰던 재조정(reconciliation) 구현입니다. 최상위 요소에서 시작해 자식을 재귀 호출로 끝까지 방문하며 트리를 만듭니다.

- 재귀는 JavaScript 호출 스택에 의존하므로, 시작한 작업은 끝날 때까지 메인 스레드를 점유합니다.
- 레거시 구현 노트는 이 한계를 "동기적이고, 작업을 중단하거나 조각으로 나눌 수 없다"고 적었습니다.
- 큰 트리를 렌더링하는 동안 클릭·입력·애니메이션 처리가 밀려 프레임이 떨어집니다.

Fiber는 이 문제를 풀려는 재구현이고 React 16부터 기본 재조정기입니다. 레거시 코드베이스 개요가 밝힌 목표는 다음과 같습니다.

| 목표 | 뜻 |
|------|----|
| 작업을 조각으로 분할 | 중단 가능한 단위로 쪼갬 |
| 우선순위 부여, 재사용 | 급한 작업을 먼저, 끝낸 작업은 재활용 |
| 부모와 자식 사이를 오가며 양보 | 호출 스택 없이 위치를 기억 |
| `render()`에서 여러 요소 반환 | 배열·Fragment 지원 |
| 에러 경계 개선 | 렌더 중 에러 처리 |

핵심은 호출 스택을 자료구조(Fiber 트리)로 바꿔서, 작업의 위치를 직접 들고 있게 만든 것입니다.

## Fiber 노드

Fiber는 컴포넌트 하나에 대응하는 작업 단위 객체입니다. acdlite의 비공식 설계 문서는 Fiber를 "가상 스택 프레임"이라고 설명합니다. React 요소가 "무엇을 그릴지"를 적은 일회용 설명이라면, Fiber는 렌더링 사이에 유지되며 상태와 작업 정보를 담는 객체입니다. Virtual DOM이라는 용어는 보통 React 요소를 가리키고, Fiber는 컴포넌트 트리 정보를 더 담는 내부 객체라고 legacy FAQ가 구분합니다.

트리 구조는 세 포인터로 만듭니다. 자식은 첫째 자식 하나만 `child`로 가리키고, 나머지는 형제를 `sibling`으로 잇습니다. `return`은 작업을 마치고 돌아갈 부모입니다.

```text
App
├─ Header
└─ List
   ├─ Item A
   └─ Item B

App.child     → Header
Header.sibling → List
List.child    → Item A
Item A.sibling → Item B
Item B.return → List
```

소스(`ReactInternalTypes.js`)의 `Fiber` 타입에서 주요 필드는 다음과 같습니다.

| 필드 | 역할 |
|------|------|
| `tag` | Fiber 종류(함수 컴포넌트, 호스트 요소 등) |
| `key`, `type` | 재조정에서 정체성을 유지하는 기준 |
| `stateNode` | 호스트 DOM 노드나 클래스 인스턴스 같은 로컬 상태 |
| `return`, `child`, `sibling`, `index` | 단일 연결 리스트 트리 |
| `pendingProps`, `memoizedProps` | 이번 입력 props, 이전 출력에 쓴 props |
| `memoizedState`, `updateQueue` | 출력에 쓴 상태, 상태 업데이트 큐 |
| `flags`, `subtreeFlags` | 이 노드와 하위 트리에서 commit이 해야 할 일 |
| `lanes`, `childLanes` | 이 노드와 하위 트리에 남은 업데이트의 우선순위 |
| `alternate` | 짝이 되는 반대편 Fiber(다음 절) |

- 함수 컴포넌트의 `memoizedState`에는 Hook 연결 리스트의 첫 항목이 들어갑니다(아래 "Hook이 Fiber에 저장되는 방식").
- 순회 순서는 깊이 우선입니다. 아래로는 `child`를 따라 내려가고, 더 내려갈 곳이 없으면 `sibling`으로 옮기며, 형제가 없으면 `return`으로 올라갑니다.
- 문서마다 필드 목록이 다릅니다. acdlite 문서에는 `pendingWorkPriority`가 나오지만 현재 소스는 `lanes`를 씁니다. 그 문서는 작성 시점의 스냅샷이므로 필드 이름은 소스를 기준으로 봅니다.

## current와 workInProgress 트리

React는 화면에 반영된 트리(current)와 렌더링 중인 트리(workInProgress)를 따로 두는 이중 버퍼링(double buffering)을 씁니다. 각 Fiber의 `alternate`가 짝 Fiber를 가리키고, 어느 쪽이 current인지는 루트의 `current` 포인터가 정합니다.

```text
root.current ─→ Fiber(current)  ⇄ alternate ⇄  Fiber(wip)
render 중: wip 쪽에서 작업, current는 화면 그대로
commit 후: root.current = finishedWork (wip가 새 current)
```

- 소스의 `createWorkInProgress`는 짝 Fiber가 없을 때만 새로 만들고, 있으면 재사용합니다. 주석은 "트리 버전은 최대 둘뿐이라는 점을 이용해 반대편 노드를 풀링한다"고 설명하며, 업데이트되지 않는 부분에는 객체를 할당하지 않도록 지연 생성합니다.
- 재사용할 때는 `flags`, `subtreeFlags`, `deletions`를 초기화하고 `pendingProps`만 새로 넣습니다.
- 렌더링이 끝나도 DOM은 건드리지 않았으므로 render 중간에 버려도 화면에는 영향이 없습니다. 이 구조가 "버리고 다시 시작"을 값싸게 만듭니다.
- 이중 버퍼는 화면 일관성을 위한 장치이기도 합니다. React 18 발표 글은 "렌더가 중단돼도 UI는 일관되게 보인다. 트리 전체를 평가한 뒤 끝에서 DOM 변경을 한다"고 보장합니다.

## 작업 루프와 시간 분할

작업 루프(work loop)는 workInProgress 포인터가 가리키는 Fiber를 하나씩 처리하는 반복문입니다. 한 Fiber를 처리하는 `performUnitOfWork`는 두 단계로 나뉩니다.

- `beginWork`: 현재 Fiber를 렌더링(함수 컴포넌트 호출, 자식 재조정)하고 다음 작업 대상인 자식을 반환합니다.
- `completeWork`: 자식이 없을 때 호출됩니다. `completeUnitOfWork`가 형제로 옮기고, 형제가 없으면 `return`으로 올라가며 반복해서 완료 처리합니다. 루트까지 올라오면 렌더 종료입니다.

```js
// ReactFiberWorkLoop.js (요약)
function workLoopSync() {
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress)
  }
}
function workLoopConcurrentByScheduler() {
  while (workInProgress !== null && !shouldYield()) {
    performUnitOfWork(workInProgress)
  }
}
```

동기 루프는 양보 없이 끝까지 돌고, 동시성 루프는 매 Fiber 뒤에 양보 여부를 확인합니다. `main` 브랜치에는 시간 기준으로 양보하는 `workLoopConcurrent`도 함께 있는데, 둘 다 "Fiber 하나를 끝낸 뒤 확인한다"는 점이 같습니다.

- 양보 지점은 Fiber 사이입니다. 컴포넌트 함수 하나가 실행되는 도중에는 끊을 수 없으므로 한 컴포넌트의 계산이 길면 그만큼 메인 스레드가 막힙니다.
- 양보는 Scheduler가 정합니다. `scheduler` 패키지는 메인 스레드를 오래 점유하지 않도록 주기적으로 양보하며, `main`의 `frameYieldMs`는 5ms입니다.
- Scheduler는 작업을 최소 힙(min heap) 큐에 두고 만료 시각 순으로 꺼냅니다. 우선순위별 제한 시간은 Immediate 즉시, UserBlocking 250ms, Normal 5000ms, Low 10000ms, Idle 무제한입니다.
- 실행 신호는 `MessageChannel`로 보냅니다. 주석은 `setTimeout`의 4ms 클램핑을 피하려는 선택이라고 밝히고, Node.js와 jsdom에서는 `setImmediate`를 우선합니다.
- 렌더가 끝나지 않으면 작업 콜백이 연속 콜백(continuation)을 돌려주고, Scheduler는 남은 시간과 상관없이 즉시 메인 스레드에 양보한 뒤 이어서 실행합니다.
- 어느 쪽 루프로 렌더하는지는 Lane이 정합니다(다음 절).

**흔한 오해:** 시간 분할이 렌더링을 병렬화하는 것은 아닙니다. 작업은 여전히 메인 스레드 하나에서 순서대로 실행되고, 조각 사이에 브라우저가 다른 일을 처리할 틈을 줄 뿐입니다.

## Lane 우선순위

Lane은 업데이트의 우선순위를 나타내는 비트 하나입니다. 소스는 31비트 정수를 쓰고, 여러 Lane을 비트 OR로 묶은 집합(Lanes)을 한 번에 다룹니다. 낮은 비트일수록 우선순위가 높고, 가장 높은 Lane은 `lanes & -lanes`로 뽑습니다.

| Lane (높음 → 낮음) | 오는 곳 |
|--------------------|---------|
| `SyncLane` | 클릭, 키 입력 같은 이산 이벤트 |
| `InputContinuousLane` | `mousemove`, `scroll` 같은 연속 이벤트 |
| `DefaultLane` | 이벤트 밖에서 일어난 업데이트(타이머, 네트워크 등) |
| `TransitionLanes` | `startTransition`, `useTransition` 안의 업데이트 |
| `RetryLanes` | Suspense 경계의 재시도 |
| `IdleLane`, `OffscreenLane` | 가장 낮은 작업 |

- `setState`가 호출되면 `requestUpdateLane`이 Lane을 정합니다. 트랜지션 안이면 트랜지션 Lane, 아니면 현재 이벤트의 우선순위를 Lane으로 바꿔 씁니다. `ReactDOMEventListener`는 `click`, `input`, `keydown`을 이산 이벤트로, `mousemove`와 `scroll`을 연속 이벤트로 분류합니다.
- 업데이트는 Hook의 업데이트 큐에 자기 `lane`을 단 채 쌓이고, Fiber의 `lanes`와 조상 쪽 `childLanes`에 표시됩니다. 렌더링이 하위 트리에 남은 일이 없는 가지를 건너뛰는 근거가 이 표시입니다.
- 렌더링은 Lane 집합을 골라서 실행합니다. 큐의 업데이트 중 이번 Lane에 포함되지 않은 것은 건너뛰고 큐에 남기며, 나중에 순서를 유지한 채 다시 적용합니다.
- 렌더 중인 Lane보다 더 급한 업데이트가 들어오면 현재 진행 중이던 트리를 버리고 급한 쪽을 먼저 렌더링합니다.

시간 분할 여부도 Lane으로 결정됩니다. `main`의 `performWorkOnRoot`는 다음 조건에서 시간 분할을 쓰지 않습니다.

| 조건 | 렌더 방식 |
|------|-----------|
| `SyncLane`, `InputContinuousLane`, `DefaultLane`을 포함 | 동기 렌더(`renderRootSync`) |
| 오래 밀려 만료된 Lane을 포함 | 동기 렌더 |
| 트랜지션, Retry, Idle Lane만 있음 | 시간 분할 렌더(`renderRootConcurrent`) |

- 즉 `createRoot`를 쓰는 React 18·19 앱이라도 일반 `setState`는 시간 분할되지 않고, 트랜지션 같은 비긴급 업데이트만 쪼개집니다.
- Lane마다 만료 시각이 계산됩니다. 비긴급 업데이트가 계속 밀려 굶는(starvation) 것을 막으려고, 오래 기다린 Lane은 동기 렌더로 처리해 끝냅니다.
- 같은 이벤트에서 이산 업데이트와 트랜지션이 함께 있으면, 이산 업데이트가 먼저 렌더·commit되고 트랜지션은 이어서 처리됩니다.

## render 단계가 중단 가능한 이유

render 단계는 컴포넌트를 호출해 다음 트리를 계산하는 구간입니다. 중단과 폐기가 안전한 이유는 네 가지입니다.

1. **호스트 트리를 건드리지 않습니다.** DOM 변경은 commit 단계에서만 일어납니다. react.dev는 렌더링을 "컴포넌트를 호출해 무엇을 화면에 보일지 알아내는 일"로, DOM을 바꾸는 일은 commit이라고 구분합니다.
2. **작업 결과가 별도 트리(workInProgress)에 쌓입니다.** current 트리는 화면 그대로입니다.
3. **진행 위치가 포인터 하나입니다.** 호출 스택이 아니라 `workInProgress`가 현재 Fiber를 가리키므로 양보했다가 이어 받을 수 있습니다.
4. **렌더링이 순수하다고 가정합니다.** react.dev는 "렌더링 도중 데이터가 바뀌면 오래된 렌더를 끝내느라 낭비하지 않고 다시 시작할 수 있다. 순수성이 언제든 계산을 멈춰도 안전하게 만든다"고 설명합니다.

`renderRootConcurrent`는 시작할 때 루트나 Lane이 이전 진행과 다르면 기존 스택을 버리고 `prepareFreshStack`으로 새로 시작하고, 같으면 이전 위치에서 이어 갑니다. 렌더가 양보하면 `RootInProgress`를 반환하고, 끝까지 가면 완료 상태를 반환합니다.

결과로 지켜야 할 규칙이 생깁니다.

- 컴포넌트 본문은 여러 번 실행될 수 있고, 실행했는데 commit되지 않고 버려질 수 있습니다. 본문에서 외부 값을 바꾸거나 요청을 보내면 안 됩니다.
- 개발 모드 Strict Mode가 컴포넌트를 두 번 호출하는 이유가 이것입니다. 순수하지 않은 코드를 드러냅니다. 프로덕션에는 영향이 없습니다.
- commit 단계는 반대로 중단하지 않고 한 번에 끝냅니다. DOM이 반쯤 바뀐 화면을 사용자에게 보이지 않기 위해서입니다.

## commit 단계의 세부 단계

commit은 render가 끝난 트리를 호스트 환경(DOM)에 반영하는 단계입니다. 소스 주석은 commit을 하위 단계로 나눠 "각 단계마다 이펙트 목록을 따로 한 번씩 훑는다. 모든 mutation 이펙트가 모든 layout 이펙트보다 앞선다"고 설명합니다. 순서는 다음과 같습니다.

| 순서 | 단계 | 하는 일 |
|------|------|---------|
| 1 | before mutation | DOM을 바꾸기 직전 상태를 읽음(클래스의 `getSnapshotBeforeUpdate`) |
| 2 | mutation | DOM 삽입·갱신·삭제, 갱신·삭제되는 `useLayoutEffect`의 cleanup 실행 |
| – | `root.current = finishedWork` | workInProgress 트리가 current가 됨 |
| 3 | layout | `useLayoutEffect` 설정 함수, 클래스의 `componentDidMount`·`componentDidUpdate`, ref 연결 |
| 4 | passive | `useEffect`의 cleanup 전부, 그다음 설정 함수 전부 |

- `root.current` 교체는 mutation 이후, layout 이전입니다. 소스 주석 그대로, 언마운트 중에는 이전 트리가 아직 current이고 `componentDidMount`·`componentDidUpdate`에서는 완성된 트리가 current입니다.
- layout 단계는 DOM이 바뀐 뒤 레이아웃을 읽는 용도입니다. 여기서 동기로 상태를 바꾸면 브라우저가 그리기 전에 다시 렌더링됩니다. react.dev는 `useLayoutEffect`가 "브라우저가 화면을 다시 그리기 전에" 실행되고 그 안의 상태 업데이트도 그리기를 막는다고 설명합니다.
- passive 단계는 commit 직후 곧바로 실행하지 않고 예약합니다. react.dev는 클릭 같은 상호작용이 원인이 아니면 React가 보통 브라우저가 화면을 먼저 그리게 둔 뒤 `useEffect`를 실행하고, 상호작용이 원인이면 그리기 전에 실행할 수 있다고 합니다.
- passive 단계에서는 모든 컴포넌트의 cleanup(`commitPassiveUnmountEffects`)이 먼저 끝난 뒤 설정 함수(`commitPassiveMountEffects`)가 실행됩니다. 컴포넌트마다 cleanup 후 설정을 반복하지 않습니다.
- 다음 렌더링이 시작되기 전에 밀려 있던 passive 이펙트를 먼저 실행합니다(`flushPendingEffects`).

**흔한 실수:** `useEffect`가 DOM 변경 직후 동기로 실행된다고 가정하는 것입니다. 화면 깜빡임을 막아야 하는 측정·배치 코드는 `useLayoutEffect`가 맞고, 그 외는 `useEffect`로 충분합니다.

## Hook이 Fiber에 저장되는 방식

함수 컴포넌트의 모든 Hook 상태는 그 컴포넌트 Fiber의 `memoizedState`에 연결 리스트로 저장됩니다. Hook 객체는 `memoizedState`, `baseState`, `baseQueue`, `queue`, `next` 다섯 필드를 가집니다.

```text
fiber.memoizedState
  → hook1 (useState)  .next →
    hook2 (useRef)    .next →
      hook3 (useMemo) .next → null
```

- 최초 렌더에서는 `mountWorkInProgressHook`이 Hook 객체를 만들어 리스트 끝에 붙입니다. 이후 렌더에서는 `updateWorkInProgressHook`이 짝 Fiber(`alternate`)의 리스트를 같은 순서로 따라가며 복제합니다.
- React는 이름이 아니라 호출 순서로 "몇 번째 Hook인지"를 알아냅니다. 그래서 조건문이나 반복문 안에서 Hook을 호출하면 순서가 어긋납니다. 소스는 순서가 바뀌면 "React has detected a change in the order of Hooks"를, 개수가 다르면 "Rendered more hooks than during the previous render"나 "Rendered fewer hooks than expected" 에러를 던집니다.
- Hook마다 `memoizedState`에 담기는 값이 다릅니다.

| Hook | `memoizedState`에 담기는 것 |
|------|-----------------------------|
| `useState` | 현재 상태 값(업데이트 큐는 `queue`) |
| `useRef` | `{ current: 초기값 }` 객체 |
| `useMemo` | 값과 의존성 배열의 쌍 |

- 렌더링 중에 `ReactSharedInternals.H`가 가리키는 디스패처를 최초 렌더용과 갱신용으로 바꿔 끼웁니다. 같은 `useState` 호출이 단계에 따라 mount나 update 구현으로 연결되는 방식입니다. 렌더가 끝나면 Hook이 아무것도 못 하는 `ContextOnlyDispatcher`로 되돌려 둡니다.
- `useState`의 setter는 `dispatchSetState`에 Fiber와 큐를 미리 묶어 둔 함수입니다. 그래서 setter 참조는 렌더가 바뀌어도 변하지 않습니다.
- setter가 호출되면 업데이트 객체(`lane`, `action`, `hasEagerState`, `eagerState`)를 만들어 큐에 넣고 `scheduleUpdateOnFiber`로 렌더링을 예약합니다. Fiber에 남은 업데이트가 없을 때는 새 상태를 미리 계산해 보고, `Object.is`로 이전 값과 같으면 렌더링을 예약하지 않습니다(eager bailout).

## 동시성 렌더링과 tearing

동시성 렌더링(concurrent rendering)은 렌더링을 중단할 수 있어서 React가 여러 버전의 UI를 동시에 준비할 수 있는 방식입니다. React 18 발표 글은 이것을 기능이 아니라 `startTransition`, Suspense 같은 기능을 가능하게 하는 구현 세부라고 설명합니다.

tearing은 한 번의 렌더링 결과에서 같은 외부 데이터의 서로 다른 시점 값이 화면의 여러 곳에 섞이는 현상입니다. 렌더가 양보하는 사이에 외부 스토어가 바뀌면 생깁니다.

```js
// ❌ 렌더 도중 외부 가변 값을 직접 읽음
function Price() {
  return <span>{store.price}</span>
}
// 앞쪽 컴포넌트는 100, 양보 뒤의 컴포넌트는 120을 보여 줄 수 있음
```

- React 상태(`useState`, `useReducer`)는 업데이트가 Lane과 함께 큐에 쌓이고 렌더마다 같은 스냅샷에서 계산되므로 tearing이 생기지 않습니다. 문제가 되는 것은 React 밖의 가변 스토어입니다.
- 해법은 `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)`입니다. React 18 발표 글은 외부 스토어가 동시 읽기를 지원하도록 스토어 업데이트를 동기로 강제하는 Hook이고 주로 라이브러리가 쓰는 것이라고 설명합니다.
- react.dev에 따르면 트랜지션 업데이트 동안 스토어가 바뀌면, React가 DOM에 반영하기 직전에 `getSnapshot`을 한 번 더 호출해 값이 다르면 렌더링을 처음부터 다시 하되 이번에는 블로킹 업데이트로 처리합니다. 화면의 모든 컴포넌트가 스토어의 같은 버전을 보게 하려는 것입니다.
- 이 때문에 외부 스토어의 변경은 트랜지션으로 표시할 수 없고, 변경이 Suspense 폴백을 띄울 수 있습니다.
- `getSnapshot`은 불변 스냅샷을 반환해야 합니다. 값이 바뀌지 않았으면 캐시한 이전 객체를 그대로 돌려줍니다. 호출할 때마다 새 객체를 만들면 `Object.is` 비교가 매번 달라서 무한 렌더링이 됩니다.
- 상태 관리 라이브러리를 직접 쓰는 앱 코드에서는 라이브러리가 이 Hook으로 구독을 처리하므로 대부분 신경 쓸 필요가 없습니다.

## 배칭 구현

배칭(batching)은 여러 상태 업데이트를 묶어서 한 번만 다시 렌더링하는 동작입니다. react.dev는 React가 이벤트 핸들러의 코드를 모두 실행한 뒤에 상태 업데이트를 처리하므로 "반쯤 끝난" 렌더가 생기지 않는다고 설명합니다.

```js
function handleClick() {
  setCount((c) => c + 1)
  setFlag((f) => !f)
  // 두 호출은 한 번의 렌더링으로 처리됨
}
```

- React 17까지는 React 이벤트 핸들러 안에서만 묶었습니다. React 18은 `setTimeout`, Promise, 네이티브 이벤트 핸들러 등 모든 곳의 업데이트를 자동으로 묶습니다(자동 배칭).
- 구현 원리는 "업데이트는 큐에 넣기만 하고, 렌더링은 나중에 한 번 예약한다"입니다. `setState`는 업데이트를 큐에 쌓고 `ensureRootIsScheduled(root)`를 호출합니다. 이 함수는 루트를 스케줄 목록에 한 번만 올리고, 마이크로태스크를 예약했는지 나타내는 플래그로 마이크로태스크도 한 번만 예약합니다.
- 현재 코드가 끝나 마이크로태스크가 돌 때 `processRootScheduleInMicrotask`가 루트마다 처리할 Lane을 고릅니다. 이 시점에는 같은 틱의 `setState`가 모두 큐에 들어 있어서 한꺼번에 렌더됩니다.
- 동기 Lane의 작업은 이 마이크로태스크 끝에서 바로 실행되고, 그보다 낮은 Lane은 우선순위에 맞는 Scheduler 태스크로 예약됩니다. 이산·연속 이벤트 Lane은 UserBlocking, 기본 Lane은 Normal, 유휴 Lane은 Idle 우선순위로 매핑됩니다(소스 주석: 동기 작업이 마이크로태스크를 쓰게 되어 Immediate는 더 쓰지 않음).
- 서로 다른 Lane의 업데이트는 같은 렌더링에 묶이지 않을 수 있습니다. 트랜지션 업데이트와 긴급 업데이트는 따로 처리됩니다.
- 별개의 의도된 이벤트(클릭 두 번)는 묶지 않습니다. react.dev는 첫 클릭이 폼을 비활성화하면 두 번째 클릭이 다시 제출하지 않도록 하기 위해서라고 설명합니다.
- 묶지 않고 즉시 반영해야 하면 `flushSync`를 씁니다. 업데이트를 동기로 flush해 DOM을 바로 갱신하지만, react.dev는 성능을 해칠 수 있으니 최후의 수단으로 쓰라고 경고합니다.
- 업데이터 함수(`setCount(c => c + 1)`)는 큐에 쌓였다가 다음 렌더에서 순서대로 적용되어 앞 결과가 다음 입력이 됩니다.

| 질문 | 답의 핵심 |
|------|-----------|
| Fiber가 무엇인가 | 컴포넌트마다 하나씩 있는 작업 단위 객체이자 "가상 스택 프레임". `child`·`sibling`·`return`으로 연결된 트리이며 상태, 우선순위, 할 일을 담음 |
| Fiber를 만든 이유 | Stack Reconciler가 재귀 호출 스택에 묶여 중단·분할이 불가능해서. 작업을 쪼개고 우선순위를 주기 위해 |
| Fiber와 Virtual DOM의 관계 | Virtual DOM은 보통 React 요소를 가리키는 개념. Fiber는 이를 점진적으로 렌더링하는 재조정 엔진이 쓰는 내부 객체 |
| render와 commit의 차이 | render는 컴포넌트를 호출해 변경을 계산(중단 가능, DOM 불변). commit은 DOM에 반영(중단 없음, 이펙트 실행) |

| 컴포넌트가 두 번 호출되는 이유 | 개발 모드 Strict Mode가 순수성 위반을 찾으려고 일부러 두 번 호출. 중단·재시작 때문에 프로덕션에서도 본문이 반복 실행될 수 있음 |
| Hook 호출 순서가 중요한 이유 | Hook 상태가 Fiber의 연결 리스트에 순서대로 저장되고 이름이 아닌 순서로 대응되기 때문 |
| 시간 분할이란 | 렌더링을 Fiber 단위로 쪼개 Scheduler가 정한 주기마다 메인 스레드에 양보하는 것. 병렬 실행이 아님 |
| Lane이란 | 업데이트 우선순위를 나타내는 비트. 클릭은 동기, 트랜지션은 전용 Lane이며 전환만 시간 분할됨 |
| `useEffect`와 `useLayoutEffect`의 시점 | 둘 다 commit 이후. layout 이펙트는 브라우저 페인트 전에 동기로, passive 이펙트는 보통 페인트 뒤에 실행 |
| 자동 배칭의 원리 | 업데이트를 큐에 넣고 마이크로태스크로 렌더링을 한 번만 예약해서 같은 틱의 업데이트가 한꺼번에 처리됨 |
| tearing이란, 해법 | 한 렌더에 외부 스토어의 서로 다른 시점 값이 섞이는 것. `useSyncExternalStore`로 동기 읽기를 강제 |

## 핵심 정리

- Stack Reconciler는 재귀 호출 스택에 묶여 중단할 수 없었고, Fiber는 호출 스택을 `child`·`sibling`·`return`으로 연결한 Fiber 트리로 바꿔 작업을 쪼개고 이어 갈 수 있게 했습니다.
- 화면에 반영된 current 트리와 렌더링 중인 workInProgress 트리가 `alternate`로 짝을 이루고, commit 때 `root.current`만 바꿉니다.
- 작업 루프는 Fiber 하나씩 `beginWork`와 `completeWork`를 실행하며, 동시성 루프는 Scheduler가 양보를 요청하면 Fiber 사이에서 멈춥니다. 시간 분할은 병렬이 아니라 양보입니다.
- Lane은 업데이트 우선순위 비트이며, 이산·연속·기본 Lane은 동기 렌더, 트랜지션·Retry·Idle Lane은 시간 분할 렌더로 처리됩니다.
- render는 DOM을 건드리지 않아 중단·폐기가 안전하고 본문이 여러 번 실행될 수 있으며, commit은 before mutation, mutation, layout, passive 순으로 한 번에 끝냅니다.
- Hook은 Fiber의 `memoizedState` 연결 리스트에 호출 순서대로 저장되고, 배칭은 업데이트를 큐에 쌓은 뒤 마이크로태스크에서 렌더링을 한 번 예약해서 이루어집니다. 외부 스토어의 tearing은 `useSyncExternalStore`가 막습니다.

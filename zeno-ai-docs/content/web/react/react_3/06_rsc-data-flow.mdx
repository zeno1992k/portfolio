## Server Fetch

서버 컴포넌트는 렌더링 중에 데이터 소스에 직접 접근합니다. 컴포넌트를 `async` 함수로 만들고 `await`로 값을 기다립니다. 별도의 API 라우트나 클라이언트 쪽 로딩 상태 코드가 필요 없습니다.

```js
// 서버 컴포넌트
async function Page({ id }) {
  const note = await db.notes.get(id)
  return <div>{note.title}</div>
}
```

- 데이터베이스, 파일 시스템, 내부 API를 컴포넌트 안에서 바로 읽을 수 있습니다. 이 코드와 쓰는 라이브러리는 클라이언트 번들에 들어가지 않습니다(자세히는 04편).
- `await`가 끝나기 전까지 컴포넌트는 중단(suspend)되고, 결과가 준비되면 렌더링이 이어집니다.
- 읽기는 이렇게 서버 컴포넌트에서 하고, 쓰기는 Server Function이 맡는 것이 기본 분업입니다(자세히는 05편).
- `async` 컴포넌트는 서버 컴포넌트에서만 가능합니다. 클라이언트 컴포넌트는 `async` 함수가 될 수 없습니다.

**흔한 실수:** 서버 컴포넌트 안에서 자기 서버의 API 라우트를 `fetch`로 다시 호출하는 것입니다. 데이터 소스를 직접 읽으면 되므로 불필요한 왕복입니다.

## Promise 생성

서버 컴포넌트에서 데이터 요청을 시작하고 `await`하지 않으면 Promise를 그대로 들고 있을 수 있습니다. `await`는 값이 필요한 자리에서만 합니다.

```js
async function Page({ id }) {
  const note = await db.notes.get(id)        // 먼저 필요함
  const commentsPromise = db.comments.get(id) // 기다리지 않음
  // ...
}
```

- `await`를 쓰면 그 줄에서 렌더링이 멈춥니다. 쓰지 않으면 요청은 이미 출발했지만 컴포넌트는 계속 진행합니다.
- 이 Promise를 아래쪽 컴포넌트에 props로 넘겨 그쪽에서 값을 읽게 할 수 있습니다.
- 먼저 필요한 데이터는 `await`로, 나중에 보여도 되는 데이터는 Promise로 두는 것이 스트리밍 설계의 시작점입니다.

## Client에 Promise 전달

서버 컴포넌트가 만든 Promise를 클라이언트 컴포넌트에 props로 넘길 수 있습니다. 서버에서 시작한 요청의 결과가 클라이언트로 스트리밍됩니다.

```js
// 서버 컴포넌트
async function Page({ id }) {
  const note = await db.notes.get(id)
  const commentsPromise = db.comments.get(note.id)
  return (
    <div>
      {note.title}
      <Suspense fallback={<p>댓글 로딩 중</p>}>
        <Comments commentsPromise={commentsPromise} />
      </Suspense>
    </div>
  )
}
```

- 클라이언트 컴포넌트는 값이 아니라 Promise를 받습니다. 값이 준비되지 않았어도 서버 컴포넌트는 `note`까지 렌더링해 먼저 보낼 수 있습니다.
- Promise가 이행되었을 때의 값은 직렬화 가능해야 합니다(자세히는 04편).
- 클라이언트 컴포넌트가 렌더링 중에 직접 Promise를 만들면 안 됩니다. 렌더링마다 새 Promise가 생겨 Suspense 폴백이 반복해서 나타납니다(자세히는 중급 15편). 서버에서 만든 Promise를 전달하는 방식은 이 문제를 피합니다.

## use로 읽기

`use`는 렌더링 중에 Promise나 Context를 읽는 React API입니다. Promise를 넘기면 이행된 값을 반환하고, 아직 대기 중이면 컴포넌트를 중단시킵니다(자세히는 중급 15편).

```js
'use client'
import { use } from 'react'

export function Comments({ commentsPromise }) {
  const comments = use(commentsPromise)
  return comments.map((c) => <p key={c.id}>{c.text}</p>)
}
```

- 중단되는 동안 가장 가까운 `Suspense` 경계의 폴백이 보입니다.
- Promise가 거부되면 가장 가까운 Error Boundary가 처리합니다. `use`를 `try`/`catch`로 감쌀 수 없습니다.
- `use`는 조건문과 반복문 안에서도 호출할 수 있습니다. 다른 Hook과 다른 점입니다.

서버 컴포넌트와 클라이언트 컴포넌트에서 값을 읽는 방법을 비교하면 다음과 같습니다.

| 위치 | 값을 읽는 방법 | 비고 |
|------|----------------|------|
| 서버 컴포넌트 | `await` | `async` 컴포넌트 |
| 클라이언트 컴포넌트 | `use(promise)` | Promise는 서버에서 만들어 props로 받음 |

**흔한 실수:** 서버 컴포넌트에서 `use`를 쓰려는 것입니다. 서버 컴포넌트에서는 `async`와 `await`가 맞는 방식입니다.

## Streaming

스트리밍은 준비된 부분부터 클라이언트로 보내고, 나머지는 준비되는 대로 이어서 보내는 방식입니다. 서버 렌더링의 스트리밍은 02편에서 다뤘고, RSC에서도 같은 원리로 동작합니다.

- 페이지 전체를 모든 데이터가 도착할 때까지 붙잡아 두지 않습니다. `await`한 데이터까지 렌더링된 부분이 먼저 가고, Promise로 넘긴 부분은 폴백으로 대신합니다.
- Promise가 이행되면 해당 영역의 결과가 같은 응답 스트림에 이어서 도착해 폴백을 교체합니다.
- 서버 컴포넌트를 `await`하는 방식과 Promise를 넘기는 방식은 선택지입니다.

| 방식 | 화면에 먼저 나오는 것 | 적합한 경우 |
|------|------------------------|-------------|
| `await` 후 렌더링 | 데이터가 모두 준비된 뒤 한 번에 | 화면의 핵심 데이터 |
| Promise를 넘기고 `Suspense` | 폴백, 이후 데이터 도착 시 교체 | 부가 정보, 느린 데이터 |

## Suspense Boundary

`Suspense` 경계는 스트리밍의 단위입니다. 경계마다 폴백이 있고, 안쪽 내용이 준비되면 그 경계만 교체됩니다.

```js
<Suspense fallback={<BigSpinner />}>
  <Biography />
  <Suspense fallback={<AlbumsGlimmer />}>
    <Albums />
  </Suspense>
</Suspense>
```

- 경계가 중첩되면 바깥부터 차례로 채워집니다. `Biography`가 먼저 보이고 `Albums`는 나중에 도착해 자기 폴백만 교체합니다.
- 서버 스트리밍 중에는 서버에서 보낸 HTML이 도착할 때 경계가 열립니다.
- 경계를 어디에 두느냐가 사용자가 보는 로딩 순서를 정합니다. 너무 크면 느린 데이터 하나가 전체를 막고, 너무 잘게 나누면 화면이 깜박이며 채워집니다(자세히는 중급 11편).
- Suspense가 감지하는 데이터 소스는 `use`로 읽는 Promise, `lazy`, Suspense를 지원하는 프레임워크의 데이터 읽기 등입니다. Effect나 이벤트 핸들러 안에서 가져오는 데이터는 감지하지 못합니다.
- 이미 화면에 나온 내용을 폴백으로 다시 가리지 않으려면 갱신을 Transition으로 감쌉니다(자세히는 중급 09편).

## Server/Client State 분리

서버 컴포넌트는 상태를 가질 수 없습니다. `useState`, 이벤트 핸들러, 브라우저 API는 클라이언트 컴포넌트에서만 씁니다. 그래서 데이터를 다음과 같이 나눕니다.

| 종류 | 위치 | 예 |
|------|------|-----|
| 서버 데이터 | 서버 컴포넌트가 읽어 렌더링 | 글 목록, 상품 정보 |
| 상호작용 상태 | 클라이언트 컴포넌트의 `useState` | 입력 중인 값, 열림/닫힘 |
| 서버로 보내는 변경 | Server Function | 저장, 삭제 |

- 서버 컴포넌트에는 상태가 없어서 렌더링 결과만 클라이언트로 전달됩니다. 서버 값이 바뀐 화면은 서버가 다시 렌더링한 결과를 받아 반영합니다.
- 서버에서 읽은 값을 클라이언트 컴포넌트의 초기값으로 props로 넘깁니다. 이후의 변경은 클라이언트 상태가 맡습니다.

```js
// 서버 컴포넌트
async function CounterBox() {
  const initial = await readCount()
  return <Counter initialValue={initial} />
}
```

- 서버 데이터를 클라이언트 상태에 복사하면 두 값이 어긋날 수 있습니다. 읽기 전용으로 보여 주는 값은 복사하지 않고 서버 컴포넌트가 렌더링하게 둡니다.
- 클라이언트 경계는 작게 유지합니다. 상호작용이 필요한 가장 작은 컴포넌트만 클라이언트로 만들고, 나머지는 서버에 남깁니다(자세히는 04편).
- 클라이언트 쪽에서 서버 데이터를 계속 새로고침하는 요구가 크면 서버 상태 라이브러리(자세히는 중급 26편)를 쓰는 편이 맞는 경우도 있습니다.

## Framework 통합

RSC는 번들러, 서버, 라우터가 함께 동작해야 하므로 프레임워크가 연동을 제공합니다. 앞의 코드가 실제로 동작하게 하는 부분이 여기에 해당합니다.

- 프레임워크가 서버 컴포넌트 렌더링, 클라이언트 번들 분리, 스트리밍 응답, 서버 함수 엔드포인트를 처리합니다.
- 데이터 로딩 방식(라우트 단위 로더, 컴포넌트 단위 패칭), 캐싱, 재검증 정책은 프레임워크마다 다릅니다.
- React 19에서 서버 컴포넌트는 안정이지만, 번들러·프레임워크가 쓰는 하부 API는 semver를 따르지 않습니다. 이 때문에 RSC를 직접 구현하지 않고 프레임워크를 쓰는 것이 일반적입니다.
- 어떤 프레임워크가 RSC를 지원하고 어떻게 다른지는 24편에서 비교합니다.

## cache

`cache`는 서버 컴포넌트에서 함수의 결과를 인자를 기준으로 메모이제이션하는 React API입니다. 같은 요청 안에서 같은 인자로 호출하면 한 번만 실행됩니다.

```js
import { cache } from 'react'

export const getUser = cache(async (id) => {
  return await db.users.get(id)
})
// 여러 컴포넌트에서 getUser(1)을 호출해도 DB 조회는 한 번
```

- 서버 컴포넌트 전용입니다. 클라이언트 컴포넌트에서는 쓸 수 없습니다.
- 캐시 수명은 서버 요청 하나입니다. React가 요청마다 모든 메모이즈된 함수의 캐시를 무효화하므로 요청 사이에서 공유되지 않습니다.
- 인자는 `Object.is`로 비교합니다. 숫자·문자열 같은 원시 값은 잘 맞고, 객체는 같은 참조여야 캐시에 적중합니다.
- 함수가 예외를 던지면 그 에러도 캐시되어 같은 인자로 다시 호출할 때 다시 던져집니다.
- `cache(fn)`을 호출할 때마다 새 캐시가 생깁니다. 컴포넌트마다 `cache(fn)`을 따로 호출하면 공유되지 않으므로 한 곳에서 만들어 export하고 가져다 씁니다.
- 컴포넌트 밖에서 호출하면 캐시를 쓰지 못합니다.

활용은 두 가지입니다. 하나는 같은 데이터가 필요한 여러 컴포넌트가 데이터를 prop으로 끌어 내리지 않고 각자 호출해 중복 요청 없이 같은 스냅샷을 받는 것이고, 다른 하나는 아래 preload 패턴입니다.

## cacheSignal

`cacheSignal`은 `cache()`의 수명이 끝났는지 알려 주는 API입니다. React 19.2에서 추가됐고 서버 컴포넌트 전용입니다.

```js
import { cache, cacheSignal } from 'react'
const dedupedFetch = cache(fetch)

async function Component() {
  await dedupedFetch(url, { signal: cacheSignal() })
}
```

- 렌더링 중에 호출하면 `AbortSignal`을, 렌더링 밖에서 호출하면 `null`을 반환합니다. 클라이언트 컴포넌트에서는 항상 `null`입니다.
- 신호는 렌더링이 성공적으로 끝났을 때, 렌더링이 중단됐을 때, 렌더링이 실패했을 때 중단(abort) 상태가 됩니다.
- 결과가 더는 쓰이지 않게 된 진행 중인 요청을 취소하는 데 씁니다. 에러 로깅에서는 신호가 중단된 뒤의 에러가 단순한 취소인지 확인해 실제 오류만 기록할 수 있습니다.

```js
catch (x) {
  if (!cacheSignal()?.aborted) logError(x) // 취소는 기록하지 않음
}
```

## 요청 워터폴과 preload 패턴

요청 워터폴은 서로 의존하지 않는 요청이 앞 요청이 끝난 뒤에야 순서대로 시작되는 상태입니다. 서버 컴포넌트는 `await`가 렌더링을 멈추기 때문에 쉽게 생깁니다.

```js
// ❌ 워터폴: 둘이 서로 의존하지 않는데 순서대로 실행
async function Page({ id }) {
  const user = await getUser(id)
  const posts = await getPosts(id)
  // ...
}
```

원인은 두 가지입니다.

- 같은 컴포넌트에서 독립된 `await`를 연달아 쓴 경우.
- 부모 컴포넌트가 `await`를 마친 뒤에야 자식이 렌더링되어, 자식의 데이터 요청이 그제야 시작되는 경우. 컴포넌트 트리 깊이만큼 순차 요청이 쌓입니다.

해결 방법은 요청을 먼저 시작하는 것입니다.

```js
// ✅ 동시에 시작한 뒤 함께 기다림
async function Page({ id }) {
  const [user, posts] = await Promise.all([
    getUser(id),
    getPosts(id),
  ])
}
```

- 값이 바로 필요하지 않으면 Promise로 두고 `Suspense` 아래에서 `use`로 읽습니다(앞의 "Client에 Promise 전달").
- 부모·자식 사이의 워터폴은 preload 패턴으로 풀 수 있습니다. 부모가 `cache`로 감싼 함수를 `await` 없이 호출해 요청을 먼저 출발시키고, 자식이 같은 함수를 `await`로 읽습니다.

```js
const getUser = cache(async (id) => db.user.query(id))

async function Page({ id }) {
  getUser(id)             // 요청 시작, 기다리지 않음
  return <Profile id={id} />
}

async function Profile({ id }) {
  const user = await getUser(id) // 이미 진행 중인 요청을 받음
}
```

- 두 호출이 같은 캐시된 함수를 같은 인자로 부르므로 요청은 한 번만 나가고, 자식은 이미 진행 중인 결과를 받습니다.
- 서로 의존하는 요청(앞 결과가 뒤 요청의 입력)은 순차가 맞습니다. 워터폴을 없애는 것이 아니라 불필요한 순차를 없애는 것이 목표입니다.
- 느린 요청을 `Suspense`로 분리하면 순차이더라도 나머지 화면이 막히지 않습니다.

**흔한 실수:** `Promise.all`로 묶은 요청 중 가장 느린 것이 전체를 결정하는 것을 잊는 것입니다. 한 요청이 유독 느리면 묶지 말고 `Suspense`로 분리해 나머지를 먼저 보여 줍니다.

## 핵심 정리

- 서버 컴포넌트는 `async`/`await`로 데이터 소스를 직접 읽고, 클라이언트 컴포넌트는 서버가 만든 Promise를 `use`로 읽습니다.
- `await` 없이 만든 Promise를 `Suspense` 아래의 클라이언트 컴포넌트에 넘기면 나머지 화면이 먼저 스트리밍됩니다. 이행 값은 직렬화 가능해야 합니다.
- Suspense 경계가 스트리밍과 로딩 순서의 단위입니다. 서버 데이터는 서버 컴포넌트가, 상호작용 상태는 클라이언트 컴포넌트가, 변경은 Server Function이 맡습니다.
- `cache`는 서버 컴포넌트에서 요청 하나 동안 같은 인자의 결과를 재사용하고, `cacheSignal`(19.2)은 그 수명이 끝났음을 알립니다.
- 독립된 요청은 `Promise.all`이나 Promise 전달로 동시에 시작하고, 부모·자식 워터폴은 `cache`와 preload로 푸는 것이 기본입니다.

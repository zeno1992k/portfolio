## Hydration

Hydration은 서버가 만든 HTML에 React가 이벤트 핸들러와 상태를 연결해, 정적인 HTML을 동작하는 앱으로 바꾸는 과정입니다(SSR의 흐름은 01편).

1. 서버가 컴포넌트를 렌더링해 HTML을 보낸다. 브라우저가 이 HTML을 그린다.
2. 브라우저가 JS 번들을 받아 실행한다.
3. React가 같은 컴포넌트를 클라이언트에서 렌더링하고, 결과를 기존 DOM과 맞춰 본다.
4. 일치하면 새 DOM을 만들지 않고 기존 DOM 노드를 재사용하면서 이벤트 핸들러를 붙인다.

- Hydration 중에는 Effect가 아직 실행되지 않은 첫 렌더 결과만 서버 HTML과 비교합니다. 비교 대상은 렌더 결과이고, 그 뒤 Effect로 바뀌는 값은 비교하지 않습니다.
- Hydration 전에 보이는 HTML은 클릭해도 반응하지 않습니다. 이 시간이 길수록 사용자가 체감하는 지연이 커집니다(자세히는 01편의 "보이지만 안 눌리는 구간").
- 스트리밍 SSR에서는 Suspense 경계마다 따로 Hydration합니다(선택적 Hydration, 02편).

## hydrateRoot

`hydrateRoot`는 서버 렌더링된 DOM 노드에 React 트리를 연결하는 클라이언트 API입니다. `react-dom/client`에서 가져옵니다.

```jsx
import { hydrateRoot } from 'react-dom/client'

hydrateRoot(document.getElementById('root'), <App />)
// 문서 전체를 렌더링한 경우
hydrateRoot(document, <App />)
```

시그니처는 `hydrateRoot(domNode, reactNode, options?)`입니다.

| 인자 | 설명 |
|------|------|
| `domNode` | 서버에서 루트로 렌더링한 DOM 요소 |
| `reactNode` | 서버가 렌더링에 쓴 것과 같은 React 노드(보통 `<App />`) |
| `options.onRecoverableError` | React가 오류에서 자동 복구했을 때 호출 |
| `options.onCaughtError` | Error Boundary가 포착한 오류 |
| `options.onUncaughtError` | Error Boundary가 잡지 못한 오류 |
| `options.identifierPrefix` | `useId` ID의 접두사. 서버와 같아야 한다 |
| `options.formState` | 서버 제출에서 온 폼 상태(`useActionState`의 permalink 사용 시) |

- 반환값은 `render(reactNode)`와 `unmount()`를 가진 객체입니다.
- `hydrateRoot`는 보통 앱에서 한 번만 호출합니다.
- 서버 HTML이 없는 앱에는 쓰지 않습니다. 그때는 `createRoot`입니다. 반대로 서버 HTML에 `createRoot`를 쓰면 기존 HTML을 버리고 다시 만듭니다.
- Hydration이 끝나기 전에 `root.render()`를 호출하면 서버 HTML이 지워지고 클라이언트 렌더링으로 바뀝니다. 초기 화면을 바꾸는 것은 컴포넌트 내부 상태로 합니다.
- 오류 콜백은 `hydrateRoot`의 옵션으로 넘깁니다. `root.render()`의 두 번째 인수로 넘기면 "You passed a second argument to root.render" 오류가 납니다.

```jsx
hydrateRoot(container, <App />, {
  onRecoverableError(error, errorInfo) {
    reportError({ type: 'Recoverable', error, errorInfo })
  },
})
```

## Mismatch

불일치(Mismatch)는 서버가 만든 HTML과 클라이언트의 첫 렌더 결과가 다른 상태입니다. React는 두 결과가 같아야 한다고 전제하며, 다르면 버그로 취급합니다.

- 개발 모드에서는 불일치에 경고를 냅니다.
- 속성 차이는 고쳐지지 않을 수 있습니다. react.dev는 속성 불일치가 패치된다는 보장이 없다고 밝힙니다.
- React는 일부 불일치에서 자동으로 복구합니다. 하지만 react.dev는 "다른 버그처럼 고쳐야 한다"고 설명합니다. 최선의 경우 속도가 느려지고, 최악의 경우 이벤트 핸들러가 엉뚱한 요소에 붙을 수 있습니다.
- 자동 복구가 일어나면 `onRecoverableError`가 호출되므로 운영에서 로깅합니다.

react.dev가 꼽는 흔한 원인은 네 가지입니다.

| 원인 | 예 |
|------|----|
| 루트 안쪽의 불필요한 공백 | `<div id="root"> ${html} </div>` |
| 렌더링에서의 `typeof window` 분기 | 서버는 `false`, 클라이언트는 `true` |
| 렌더링 중 브라우저 전용 API | `window.matchMedia` |
| 서버와 클라이언트가 렌더링한 데이터 차이 | 시각, 난수, 사용자별 값 |

- HTML 구조가 잘못된 경우(예: `p` 안에 `div`)도 불일치로 이어질 수 있습니다. 브라우저의 HTML 파서가 서버 HTML의 구조를 바꿔 읽기 때문입니다.
- 브라우저 확장이나 서드파티 스크립트가 `head`·`body`에 요소를 끼워 넣는 경우, React 19는 예상 밖 요소를 건너뛰고 불일치로 취급하지 않습니다(아래 "React 19의 Mismatch 메시지").

## 서버/클라이언트 출력 일치

핵심 규칙은 렌더링을 순수하게 유지하는 것입니다. 같은 props, 같은 state, 같은 데이터이면 서버와 클라이언트가 같은 JSX를 반환해야 합니다.

| 지켜야 할 것 | 방법 |
|--------------|------|
| 같은 데이터 | 서버가 쓴 데이터를 클라이언트에도 전달해 같은 값으로 렌더링한다 |
| 렌더링에서 시각·난수 금지 | 값은 서버에서 정해 props로 내리거나 Effect에서 만든다 |
| 브라우저 API는 Effect에서 | 렌더링 중에는 서버에서도 안전한 값만 읽는다 |
| ID는 `useId` | 서버와 클라이언트에서 같은 ID를 만든다 |
| 같은 컴포넌트 트리 | 서버와 클라이언트가 같은 루트 컴포넌트·옵션을 사용한다 |

- `useId`는 호출한 컴포넌트의 부모 경로로 ID를 만듭니다. 그래서 Hydration 순서가 서버 렌더링 순서와 달라도 같은 ID가 나옵니다. 전역 카운터(`nextId++`)는 순서가 달라지면 어긋납니다(중급 05편).
- 한 페이지에 React 루트가 여러 개이면 `identifierPrefix`를 서버(`renderToPipeableStream`)와 클라이언트(`hydrateRoot`)에서 같게 줍니다.
- 리스트의 `key`에 `useId`를 쓰지 않습니다. key는 데이터에서 만듭니다.
- 조건부 렌더링 분기가 서버와 클라이언트에서 다르게 평가되지 않도록, 분기 조건을 props나 state로 전달합니다.

## Date와 Random 문제

`new Date()`와 `Math.random()`은 호출할 때마다 값이 달라서 서버와 클라이언트의 렌더링 결과가 달라집니다.

```jsx
function Clock() {
  return <p>{new Date().toLocaleTimeString()}</p>
  // ❌ 서버 10:00:01, 클라이언트 10:00:03
}

function Banner() {
  return <p>{Math.random() > 0.5 ? 'A' : 'B'}</p>
  // ❌ 서버와 클라이언트가 다른 값을 고른다
}
```

- 서버와 클라이언트의 시계, 시간대, 로케일이 다를 수 있어서 같은 코드도 다른 문자열을 만듭니다. 서버가 실행되는 지역의 시간대가 사용자와 다르기 때문입니다.
- 렌더링 중 난수를 쓰면 안 됩니다. ID는 `useId`를 쓰고, 무작위 선택은 서버에서 한 번 정해서 props로 전달합니다.

해결책은 세 가지입니다.

```jsx
// ✅ 1. 서버가 정한 값을 props로 전달
function Clock({ serverTime }) {
  return <p>{serverTime}</p>
}

// ✅ 2. 마운트 뒤 Effect에서 갱신
function Clock() {
  const [time, setTime] = useState(null)
  useEffect(() => setTime(new Date().toLocaleTimeString()), [])
  return <p>{time ?? '...'}</p>
}
```

3. 불가피하면 해당 요소에 `suppressHydrationWarning`을 붙입니다(아래).

시각 표시는 같은 입력이면 같은 문자열을 만드는 포맷(시간대를 명시한 `Intl.DateTimeFormat` 옵션 등)으로 서버와 클라이언트 양쪽에서 계산하면 불일치를 피할 수 있습니다.

## Browser API 문제

렌더링 중에 읽는 브라우저 API는 서버에 없거나 다른 값을 내서 문제가 됩니다. 두 가지 증상이 있습니다.

| 증상 | 예 |
|------|----|
| 서버에서 오류 | `window`, `localStorage`를 렌더링 중에 읽으면 ReferenceError(01편) |
| 서버와 클라이언트가 다른 값 | `typeof window`, `matchMedia`, `navigator.onLine`으로 분기하면 첫 렌더가 달라짐 |

```jsx
function Layout() {
  const mobile = window.matchMedia('(max-width: 600px)').matches
  // ❌ 서버: ReferenceError
  return mobile ? <MobileNav /> : <DesktopNav />
}
```

- `typeof window !== 'undefined'`로 가드하면 오류는 사라지지만 서버(`false`)와 클라이언트(`true`)가 다른 JSX를 내서 불일치가 됩니다. react.dev가 흔한 원인으로 직접 꼽습니다.
- 초기 `useState`에 `localStorage` 값을 읽는 것도 같은 문제입니다.
- 읽기는 Effect로 옮기거나 `useSyncExternalStore`로 서버 값을 따로 지정합니다(아래).
- 레이아웃이 화면 폭에 달라지는 경우는 JS 분기보다 CSS 미디어 쿼리로 처리하면 서버 HTML과 어긋나지 않습니다.

## suppressHydrationWarning

`suppressHydrationWarning={true}`는 한 요소에서 서버와 클라이언트의 내용·속성 불일치 경고를 끄는 속성입니다.

```jsx
<h1 suppressHydrationWarning={true}>
  Current Date: {new Date().toLocaleDateString()}
</h1>
```

- 시각, 난수처럼 일치를 보장하기 어려운 드문 경우를 위한 도피 수단(escape hatch)입니다. 남용하지 않습니다.
- 한 단계만 적용됩니다. 그 요소 자체의 속성과 직접 담긴 텍스트에만 효과가 있고, 자식 요소에는 적용되지 않습니다.
- 경고만 끕니다. 불일치를 고치지 않으며, React는 어긋난 텍스트를 맞추려고 시도하지 않습니다. 그래서 서버 값이 화면에 남을 수 있습니다.
- 속성 불일치가 패치된다는 보장도 없습니다.
- 적용 대상은 값이 어긋나도 괜찮은 최소 범위(타임스탬프를 담은 요소 하나)로 제한합니다.

**흔한 실수:** 불일치 경고가 보일 때 상위 컴포넌트나 `html` 태그에 붙여서 조용히 만드는 것입니다. 한 단계만 적용되므로 막히지도 않고, 진짜 버그를 숨깁니다. `suppressHydrationWarning`은 원인을 알고 있는 요소에만 씁니다.

## Client-only Content

서버와 클라이언트가 의도적으로 다른 내용을 보여야 한다면 두 번 렌더링합니다. 첫 렌더는 서버와 같은 내용으로 하고, Hydration 뒤 Effect에서 클라이언트 전용 내용으로 바꿉니다.

```jsx
function ClientOnly({ children, fallback = null }) {
  const [isClient, setIsClient] = useState(false)
  useEffect(() => {
    setIsClient(true)
  }, [])
  return isClient ? children : fallback
}
```

- 서버와 첫 클라이언트 렌더는 `isClient`가 `false`라서 `fallback`이 나옵니다. Effect는 서버에서 실행되지 않으므로 서버 HTML과 일치합니다.
- 단점은 두 번 렌더링하는 비용입니다. Hydration이 느려지고, 느린 연결에서는 Hydration 뒤에 UI가 바뀌어 사용자에게 어색하게 보일 수 있습니다(react.dev).
- `fallback`의 크기를 실제 내용과 비슷하게 맞추면 화면이 튀지 않습니다.

서버에서만 건너뛰는 방법도 있습니다.

| 방법 | 서버 HTML | 비고 |
|------|-----------|------|
| `isClient` 상태와 Effect | `fallback` | 가장 단순. 두 번 렌더링 |
| Suspense 안에서 서버 전용 오류 던지기 | 가장 가까운 Suspense의 `fallback` | 클라이언트가 같은 컴포넌트를 다시 렌더링 |
| `use(browser())` | 가장 가까운 Suspense의 `fallback` | 19.3부터 정식. 클라이언트 컴포넌트에서만 |

```jsx
'use client'
import { Suspense, use } from 'react'
import { browser } from 'react-dom'

function Draft() {
  use(browser('localStorage 필요'))
  const saved = localStorage.getItem('draft') ?? ''
  return <textarea defaultValue={saved} />
}

// <Suspense fallback={<p>...</p>}><Draft /></Suspense>
```

- `use(browser())`는 서버 렌더링에서 컴포넌트를 중단시키고 `fallback`을 HTML로 내보냅니다. 클라이언트(Hydration 포함)에서는 중단 없이 `undefined`를 반환하고 컴포넌트가 그대로 렌더링됩니다.
- Suspense 경계 안에서만 써야 하고, `browser()` 단독 호출은 효과가 없으며 `use()`에 넘겨야 합니다.
- `reason` 인자는 서버의 `onBrowserBailout` 콜백으로 전달되는 오류의 `cause`가 됩니다. 어떤 컴포넌트가 서버 렌더링을 포기했는지 추적하는 데 씁니다.
- `typeof window` 검사와 달리 스트리밍·SSR 비활성 프레임워크와도 맞고, props 조건에 따라 서버 렌더링 여부를 정할 수 있습니다. 조건에 따라 `browser()` 호출 자체를 건너뛸 수 있습니다.
- `browser()`는 19.3 이전 버전에는 없으므로 그 버전에서는 Effect나 Suspense 방식을 씁니다.

## useSyncExternalStore로 클라이언트 전용 값 다루기

`useSyncExternalStore`는 브라우저의 외부 값(`navigator.onLine`, `matchMedia`, `localStorage` 등)을 구독하면서, Hydration에는 서버와 같은 값을 쓰게 하는 Hook입니다(자세히는 중급 05편).

```jsx
function subscribe(callback) {
  window.addEventListener('online', callback)
  window.addEventListener('offline', callback)
  return () => {
    window.removeEventListener('online', callback)
    window.removeEventListener('offline', callback)
  }
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine, // 클라이언트 값
    () => true,             // 서버 렌더링과 Hydration 값
  )
}
```

- 세 번째 인수 `getServerSnapshot`은 서버 렌더링과 Hydration 중에만 호출됩니다. 서버가 반환한 값과 클라이언트 첫 렌더에서 반환하는 값이 똑같아야 합니다.
- 서버 렌더링되는 컴포넌트에서 `getServerSnapshot`을 생략하면 서버에서 오류가 납니다.
- Hydration 동안은 서버 값으로 렌더링해 일치를 지키고, 이후 클라이언트의 실제 값으로 갱신됩니다.
- Effect와 상태로 직접 구현하는 것보다 구독 해제와 갱신 누락을 신경 쓰지 않아도 됩니다.
- `getSnapshot`은 값이 바뀌지 않았으면 같은 참조를 반환해야 합니다. 매번 새 객체를 만들면 무한 재렌더링이 발생합니다.

```jsx
function getSnapshot() {
  return { todos: store.todos } // ❌ 매번 새 객체
}
function getSnapshot() {
  return store.todos // ✅ 같은 참조
}
```

## React 19의 Mismatch 메시지

React 19는 Hydration 불일치를 중복된 경고 여러 개가 아니라 하나의 오류 메시지와 차이(diff)로 보여 줍니다. 어느 컴포넌트의 어느 부분이 달랐는지 바로 알 수 있습니다.

```text
// 이전 버전: 비슷한 경고가 여러 번 반복
Warning: Text content did not match.
  Server: "Server" Client: "Client"
Warning: An error occurred during hydration...

// React 19: 하나로 합쳐진 메시지와 diff
Hydration failed because the server rendered HTML
didn't match the client.
  <App>
    <span>
+    Client
-    Server
```

- `+` 줄은 클라이언트가 렌더링한 내용, `-` 줄은 서버 HTML의 내용입니다. 컴포넌트 계층 안에서 위치가 드러납니다.
- 서드파티 스크립트와 브라우저 확장이 `head`와 `body`에 끼워 넣은 요소는 건너뜁니다. 확장 때문에 생기던 오탐이 줄었습니다.
- 서드파티 스타일시트도 보존됩니다. 무관한 불일치로 React가 다시 렌더링해야 할 때도 마찬가지입니다.
- React 19.3에는 Hydration 중 StrictMode에서 Effect를 두 번 호출하는 변경이 들어갔습니다. 클라이언트 동작과 맞추기 위한 것입니다(19.3 발표 글).

## 디버깅

불일치를 디버깅하는 순서는 이렇습니다.

1. 개발 모드의 오류 메시지에서 diff로 컴포넌트와 어긋난 내용을 확인한다(React 19).
2. 서버가 보낸 원본 HTML(페이지 소스 보기)과 Hydration 뒤 DOM(개발자 도구)을 비교한다.
3. 원인을 분류한다. 시각·난수, 브라우저 API, 데이터 차이, 공백, HTML 구조 중 무엇인지 본다.
4. 브라우저 확장을 끈 시크릿 창에서 재현해 확장 때문인지 가른다.
5. 아래 표에 따라 고친다.

| 원인 | 해결 |
|------|------|
| 시각·난수 | props로 전달, Effect로 이동, 불가피하면 `suppressHydrationWarning` |
| 브라우저 API | Effect, `useSyncExternalStore`, `use(browser())` |
| 서버·클라이언트 데이터 차이 | 서버 데이터를 클라이언트에 그대로 전달 |
| 루트 안 공백 | 서버 HTML 문자열에서 공백·줄바꿈 제거 |
| HTML 구조 오류 | 유효한 중첩으로 수정 |
| ID | `useId` 사용, 루트가 여러 개면 `identifierPrefix` 맞추기 |

- 운영에서는 `onRecoverableError`로 자동 복구된 오류를 수집합니다. 개발에서 안 보이던 불일치(사용자 시간대, 로그인 상태)를 찾을 수 있습니다.
- 불일치를 `suppressHydrationWarning`으로 덮어 두고 지나가면 같은 오류가 다른 곳에서 다시 나타납니다. 가린 요소가 정말 시각·난수인지 다시 확인합니다.
- 해결 뒤에는 서버 응답과 클라이언트 첫 렌더가 같은지 확인하고, 사용자 상태(로그인 여부, 시간대, 로케일, 저장된 설정)를 바꿔 가며 다시 시험합니다.

## 핵심 정리

- Hydration은 서버가 만든 HTML에 이벤트 핸들러와 상태를 연결하는 과정이며, `hydrateRoot(domNode, reactNode, options)`로 시작합니다. 서버 HTML에 `createRoot`를 쓰면 기존 HTML을 버립니다.
- 서버 HTML과 클라이언트 첫 렌더 결과가 달라지면 불일치이며 버그로 취급합니다. 흔한 원인은 공백, `typeof window` 분기, 브라우저 API, 데이터 차이입니다.
- `Date`와 `Math.random`은 렌더링 중에 쓰지 않고 props로 전달하거나 Effect에서 처리합니다. ID는 `useId`를 씁니다.
- `suppressHydrationWarning`은 한 단계만 적용되는 경고 끄기이며, 시각 같은 불가피한 요소에만 씁니다.
- 클라이언트 전용 콘텐츠는 `isClient` 상태와 Effect, Suspense를 이용한 서버 건너뛰기, 19.3의 `use(browser())`로 처리하고, 외부 값은 `useSyncExternalStore`의 `getServerSnapshot`으로 서버 값을 따로 줍니다.
- React 19는 불일치를 하나의 메시지와 diff로 보여 주고, 확장 프로그램이 끼워 넣은 요소를 건너뜁니다. 운영에서는 `onRecoverableError`로 수집합니다.

## Vite 빌드와 청크 전략

`vite build`는 `index.html`을 진입점으로 JavaScript·CSS·이미지를 번들해 `dist` 폴더에 출력합니다. 결과물은 정적 파일뿐이라 어떤 정적 호스팅에도 올릴 수 있습니다. 배포 전에는 `vite preview`로 빌드 결과를 로컬에서 확인합니다(기본 포트 4173).

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `build.target` | `baseline-widely-available` | 변환 대상 브라우저(Chrome 111, Edge 111, Firefox 114, Safari 16.4 이상) |
| `build.outDir` | `dist` | 출력 폴더 |
| `build.sourcemap` | `false` | 소스맵 생성 여부 |
| `build.minify` | `oxc` | 클라이언트 번들 압축기 |
| `build.chunkSizeWarningLimit` | `500` (kB) | 청크가 이 크기를 넘으면 경고 |
| `build.assetsInlineLimit` | `4096` (4 KiB) | 이보다 작은 에셋은 base64로 인라인 |
| `base` | `/` | 에셋 URL의 기준 경로. 하위 경로에 배포하면 바꿔야 함 |

**청크**는 번들러가 만든 출력 JavaScript 파일 하나입니다. 청크 전략의 목표는 첫 화면에 필요한 코드만 먼저 내려받고, 나머지는 필요할 때 받으며, 바뀌지 않는 코드는 캐시에 남기는 것입니다.

- **동적 `import()`**가 자동으로 청크 경계가 됩니다. 라우트 단위로 `lazy`와 함께 쓰는 것이 기본 전략입니다(자세히는 중급 12편).
- Vite는 비동기 청크에서 쓰인 CSS를 별도 파일로 추출해 청크와 함께 로드하고, 진입 청크와 그 직접 의존성에 `modulepreload` 링크를 HTML에 넣습니다. 공통 의존성이 있는 비동기 청크는 순차 요청이 아니라 병렬로 가져오도록 동적 import를 고쳐 씁니다. 설정 없이 적용됩니다.
- **수동 분할**은 변하지 않는 라이브러리(`react`, `react-dom`)를 앱 코드와 분리해 앱 배포 때마다 캐시가 깨지지 않게 할 때 씁니다.

```js
// vite.config.js (Vite 8, Rolldown)
build: {
  rolldownOptions: {
    output: {
      codeSplitting: {
        groups: [
          { test: /node_modules[\\/]react/, name: 'react' },
        ],
      },
    },
  },
},
```

Vite 7 이하는 Rollup 기반이라 `build.rollupOptions.output.manualChunks`로 같은 일을 합니다. 수동 분할을 켜면 Rolldown이 런타임 코드를 담은 `runtime.js` 청크를 따로 만듭니다.

- 청크가 너무 많으면 요청 수가 늘고, 너무 크면 첫 로드가 느려집니다. 경고(500 kB)를 숨기기 전에 무엇이 큰지부터 봅니다(다음 절).
- 동적 import가 실패하면(배포 직후 옛 청크가 사라진 경우 등) Vite는 `vite:preloadError` 이벤트를 발생시킵니다. 이 이벤트로 새로고침을 안내하거나 자동 새로고침을 겁니다.

```js
window.addEventListener('vite:preloadError', () => {
  window.location.reload() // 새 배포의 index.html로 갱신
})
```

**흔한 실수:** 모든 `node_modules`를 하나의 `vendor` 청크로 묶는 것입니다. 라이브러리 하나만 올려도 청크 전체의 해시가 바뀌어 캐시가 무효화되고, 특정 라우트에서만 쓰는 무거운 라이브러리까지 첫 로드에 포함됩니다.

## 번들 분석

번들 분석은 최종 번들에서 어떤 모듈이 용량을 차지하는지 시각화해 줄일 대상을 찾는 일입니다. `vite build`가 출력하는 파일 크기 표는 청크 단위 합계만 알려 주므로 모듈 단위 분석 도구를 씁니다. 대표적으로 `rollup-plugin-visualizer`가 있고 Vite 플러그인으로 등록합니다.

```js
import { visualizer } from 'rollup-plugin-visualizer'

export default defineConfig({
  plugins: [
    visualizer({ filename: 'stats.html', gzipSize: true }),
  ],
})
```

- 빌드하면 `stats.html`이 생기고, 기본 템플릿은 트리맵입니다(`sunburst`, `network` 등도 선택 가능). 프로젝트 파일과 의존성이 구분되어 보입니다.
- `gzipSize`, `brotliSize`를 켜면 전송 크기를 함께 봅니다. 사용자가 받는 것은 압축된 크기입니다.
- 볼 것은 세 가지입니다. 한 번에 큰 의존성(날짜·차트·에디터 라이브러리), 같은 라이브러리가 두 버전으로 들어간 중복, 첫 화면에 필요 없는데 진입 청크에 들어간 모듈입니다.
- 줄이는 순서: 불필요한 의존성 제거, 큰 라이브러리를 라우트·상호작용 시점의 동적 import로 이동, 가벼운 대체재 검토, 필요한 부분만 import(트리 셰이킹이 되는 이름 있는 import).
- 분석 도구의 호환성은 번들러에 따라 달라지므로 Vite 8에서 쓸 때 플러그인 문서의 지원 상태를 확인합니다.

**흔한 실수:** 분석 없이 `chunkSizeWarningLimit` 값만 올려 경고를 없애는 것입니다. 경고는 원인이 아니라 증상입니다.

## 환경 분리

환경 분리는 같은 코드를 dev(개발)·staging(검증)·prod(운영)에 맞는 설정으로 빌드하는 일입니다. 달라지는 것은 API 주소, 분석·모니터링 키, 기능 플래그 기본값입니다. Vite는 `.env` 파일을 모드(mode)별로 읽습니다.

| 파일 | 로드 시점 | 커밋 |
|------|-----------|------|
| `.env` | 항상 | 한다 |
| `.env.local` | 항상 | 하지 않는다(git 무시) |
| `.env.staging` | 모드가 `staging`일 때 | 한다 |
| `.env.staging.local` | 모드가 `staging`일 때 | 하지 않는다 |

뒤의 파일이 앞을 덮어쓰고, 셸에 이미 있는 환경 변수가 가장 우선합니다.

```bash
vite build                  # .env.production 로드
vite build --mode staging   # .env.staging 로드
```

```ts
const api = import.meta.env.VITE_API_URL
import.meta.env.MODE // 'staging'
import.meta.env.PROD // true (NODE_ENV는 production)
```

- `mode`와 `NODE_ENV`는 다른 개념입니다. `--mode staging`은 읽을 `.env` 파일만 바꾸고, 빌드는 여전히 운영 최적화로 합니다.
- `VITE_` 접두사가 붙은 변수만 클라이언트 코드에 노출됩니다. 값은 빌드 시점에 코드에 문자열로 박힙니다. 그래서 같은 빌드 산출물을 환경만 바꿔 재사용할 수 없고 환경마다 다시 빌드해야 합니다.
- **`VITE_` 변수에 비밀값을 넣지 않습니다.** 번들을 열면 누구나 읽을 수 있습니다. API 키 같은 비밀은 서버에 두고 서버를 거쳐 호출합니다(자세히는 23편).
- 변수 이름이 늘면 `vite-env.d.ts`에서 `ImportMetaEnv`를 확장해 타입을 지정합니다.
- 호스팅 서비스의 대시보드에서 환경별 변수를 관리합니다. 예를 들어 Vercel은 Local·Preview·Production 세 환경이 기본이고, 환경마다 고유한 변수를 가지며, Pro와 Enterprise 플랜은 `staging` 같은 사용자 정의 환경을 만들 수 있습니다.

**흔한 실수:** 운영 데이터베이스나 결제 키를 스테이징 환경 변수에 복사해 두는 것입니다. 스테이징은 별도의 자원과 자격 증명을 씁니다.

## 정적 호스팅과 SPA fallback

SPA는 `index.html` 하나와 정적 에셋이므로 객체 저장소와 CDN에 올립니다. 대표 구성은 Vercel·Netlify 같은 호스팅 플랫폼(저장소를 연결하면 Vite를 감지해 빌드·배포)과, AWS의 S3에 파일을 두고 CloudFront로 배포하는 구성입니다.

**SPA fallback**이 필요한 이유는 라우팅이 브라우저 안에서만 일어나기 때문입니다. `/orders/3`을 주소창에 직접 입력하거나 새로고침하면 요청이 서버로 가는데 그 이름의 파일이 없어 404가 납니다. 파일이 없는 경로에 `index.html`을 내려 주고 클라이언트 라우터가 주소를 해석하게 하는 것이 fallback입니다.

| 호스팅 | 설정 |
|--------|------|
| Netlify | `_redirects`에 `/*  /index.html  200` 한 줄 |
| Vercel | `vercel.json`의 `rewrites`에 `source`와 `destination` 지정 |
| CloudFront + S3 | 사용자 지정 오류 응답: 오류 코드(404, 필요하면 403)에 대해 응답 페이지 경로 `/index.html`, 응답 코드 200 |
| Firebase 등 | 모든 경로(`**`)를 `/index.html`로 rewrite |

```json
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

- 상태 코드 `200`이 중요합니다. 리다이렉트가 아니라 rewrite라서 주소창의 URL이 유지되고 라우터가 그 URL을 읽습니다.
- Netlify는 기본으로 실제로 존재하는 정적 파일을 가리지 않습니다. Vercel도 rewrite보다 파일 시스템을 먼저 확인합니다. 그래서 `/assets/app-a1b2.js`는 정상적으로 파일이 내려가고 없는 경로만 `index.html`로 갑니다.
- 모든 없는 경로가 200이므로 진짜 404 페이지는 앱의 라우터에서 `*` 경로로 그려야 합니다. 서버 상태 코드가 200이라서 검색 엔진에는 소프트 404로 보일 수 있으므로 SEO가 중요한 페이지는 CSR이 아니라 SSR·SSG를 고려합니다(자세히는 01편).
- 하위 경로에 배포하는 경우(`https://사용자.github.io/저장소/`) `base`를 `'/저장소/'`로 설정하고 라우터의 basename도 맞춥니다.
- CloudFront의 오류 응답 fallback은 에셋 요청의 오류도 `index.html`로 바꿀 수 있으므로, 없는 청크 요청이 HTML로 오는 경우를 `vite:preloadError`로 처리합니다.

**흔한 실수:** 로컬 개발 서버에서는 되던 새로고침이 배포 후 404가 되는 것입니다. 배포 설정에 fallback이 빠진 경우입니다.

## 해시 파일명과 캐시 무효화

Vite는 `dist/assets/` 아래 에셋 파일명에 내용 기반 해시를 붙입니다(`index-Cx3a9fQ2.js`). 내용이 바뀌면 이름이 바뀌고, 이름이 같으면 내용이 같다는 보장이 생깁니다. 이 보장 덕분에 해시가 붙은 파일은 오래 캐시하고, 이름이 고정된 `index.html`만 항상 새로 확인합니다.

| 파일 | 헤더 | 이유 |
|------|------|------|
| 해시가 붙은 JS·CSS·이미지 | `Cache-Control: public, max-age=31536000, immutable` | 내용이 바뀌면 URL이 바뀌므로 1년 캐시해도 안전 |
| `index.html` | `Cache-Control: no-cache` | 저장은 하되 사용 전에 항상 서버에 변경 여부를 확인(변경 없으면 304) |

- `no-cache`는 캐시하지 말라는 뜻이 아니라 매번 재검증하라는 뜻입니다. 저장 자체를 막는 것은 `no-store`입니다.
- 새 배포가 사용자에게 반영되는 경로는 `index.html`이 새 해시의 에셋을 가리키는 것입니다. 그래서 `index.html`이 오래 캐시되면 배포해도 변화가 보이지 않습니다.
- `immutable`은 새로고침해도 재검증하지 않게 합니다.

S3에 올릴 때 파일 종류별로 헤더를 다르게 주는 예입니다.

```bash
aws s3 sync dist s3://$BUCKET --exclude index.html \
  --cache-control "public,max-age=31536000,immutable"
aws s3 cp dist/index.html s3://$BUCKET/index.html \
  --cache-control "no-cache"
```

- 순서가 있습니다. 새 에셋을 먼저 올리고 `index.html`을 마지막에 올립니다. 반대로 하면 `index.html`이 아직 없는 파일을 가리키는 순간이 생깁니다.
- 이전 배포의 해시 파일을 곧바로 지우지 않습니다. 옛 `index.html`을 가진 탭이 `lazy` 청크를 요청할 때 404가 나기 때문입니다. 일정 기간 남겨 두고, 그래도 실패하면 `vite:preloadError`로 새로고침합니다.
- CDN(CloudFront)에 `index.html`이 캐시되어 있으면 배포 뒤 해당 경로만 무효화(invalidation)합니다. 에셋은 이름이 새로우니 무효화할 필요가 없습니다.

```bash
aws cloudfront create-invalidation \
  --distribution-id $DIST_ID --paths "/index.html"
```

**흔한 실수:** 모든 파일에 같은 긴 `max-age`를 주는 것입니다. `index.html`까지 오래 캐시되어 배포가 반영되지 않습니다. 반대로 모든 파일을 `no-cache`로 두면 해시의 이점을 버립니다.

## CI/CD

CI(지속적 통합)는 변경이 올라올 때마다 린트·타입 검사·테스트·빌드를 자동으로 돌려 깨진 변경을 병합 전에 걸러 내는 것이고, CD(지속적 배포)는 통과한 빌드를 환경에 자동으로 올리는 것입니다. GitHub Actions는 저장소의 `.github/workflows/*.yml` 워크플로 파일로 정의합니다.

| 키 | 역할 |
|----|------|
| `on` | 실행 조건(`push`, `pull_request`, 스케줄) |
| `jobs` | 작업 목록. 기본적으로 병렬 실행 |
| `runs-on` | 실행 환경(`ubuntu-latest`) |
| `steps` | 순서대로 실행하는 단계. `uses`는 액션, `run`은 셸 명령 |
| `needs` | 다른 작업이 끝난 뒤 실행 |
| `permissions` | `GITHUB_TOKEN`의 권한 범위 |
| `concurrency` | 같은 그룹의 중복 실행 제어 |
| `secrets` | 암호화 저장된 비밀값 참조 |

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

```yaml
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: npm ci
      - run: npm run lint && npm test
      - run: npm run build
```

- `npm ci`는 락 파일 그대로 설치해 재현 가능한 빌드를 만듭니다.
- 작업 순서는 빠르게 실패하는 것부터 둡니다. 린트·타입 검사·단위 테스트가 먼저, 비싼 E2E는 뒤입니다(자세히는 21편).
- `permissions`는 최소로 시작해 필요한 것만 올립니다. `concurrency`의 `cancel-in-progress`는 같은 브랜치에 새 커밋이 올라오면 이전 실행을 취소합니다.
- 배포 작업은 `needs: verify`로 CI 통과 뒤에만, `main`일 때만 실행되게 하고 `environment: production`으로 승인 규칙과 비밀값을 묶습니다.
- 배포 자격 증명은 저장소 secrets나 단기 토큰으로 주입하고 코드·로그에 남기지 않습니다. 외부 PR이 비밀값에 접근하지 못하게 `pull_request_target` 같은 트리거에서는 PR 코드를 체크아웃하지 않습니다. `actions/checkout` v7은 이 경우를 기본으로 거부합니다.
- 배포 단계의 내용은 호스팅에 따라 다릅니다. Vercel·Netlify는 저장소 연결만으로 빌드·배포가 되므로 Actions는 검증 용도로 두는 경우가 많고, S3와 CloudFront는 위의 `aws s3` 명령을 작업으로 만듭니다.
- 빌드가 느리면 의존성 캐시와 `turbo` 같은 작업 캐시로 줄입니다(아래 "모노레포").

**흔한 실수:** 로컬에서만 통과하고 CI에서 실패하는 경우의 원인은 Node 버전 차이, 락 파일 불일치, `.env.local`에만 있는 변수입니다. CI에서 쓰는 Node 버전을 `.nvmrc`나 `engines`로 고정합니다.

## 미리보기 배포

미리보기 배포(preview deployment)는 PR마다 운영과 분리된 임시 URL에 빌드를 올려, 병합 전에 결과를 직접 확인하고 공유하는 배포입니다. 코드 리뷰가 diff만이 아니라 동작 확인까지 가능해집니다.

- Vercel은 운영 브랜치가 아닌 브랜치에 푸시하거나 PR을 만들면 미리보기 배포를 자동으로 만듭니다. URL은 두 종류로, 브랜치의 최신 상태를 가리키는 브랜치 URL과 특정 커밋을 가리키는 커밋 URL입니다. 링크는 PR 코멘트에 표시됩니다.
- 미리보기는 별도 환경 변수 집합(Preview)을 씁니다. 운영 데이터가 아닌 스테이징 API와 테스트 자격 증명을 가리키게 합니다.
- 미리보기 URL을 E2E 테스트의 대상 주소로 삼으면 병합 전 실제 배포 환경에서 핵심 흐름을 검증할 수 있습니다(자세히는 21편).
- 로그인 연동(OAuth)은 허용된 리다이렉트 주소에 미리보기 URL이 없으면 실패합니다. 와일드카드나 테스트 전용 계정을 쓰는 방식을 정해 둡니다.
- 미리보기는 공개 주소라서 접근 제한(배포 보호, 비밀번호)을 설정하고, 검색 엔진에 색인되지 않게 합니다. 미리보기에 실제 고객 데이터를 연결하지 않습니다.
- 스테이징 환경은 미리보기와 별개로 오래 유지되는 검증용 환경입니다. 이름 있는 브랜치(`staging`)에 고정 도메인을 붙이거나 플랫폼의 사용자 정의 환경을 씁니다.

## 에러 모니터링과 소스맵

에러 모니터링은 사용자 브라우저에서 발생한 에러를 서버에서 수집해 알림과 통계로 보는 것입니다. 개발자 콘솔은 사용자 기기의 에러를 보여 주지 않으므로 운영에는 필수입니다. Sentry가 대표적이고 `@sentry/react` SDK를 씁니다.

```js
// instrument.js — 가장 먼저 import
import * as Sentry from '@sentry/react'

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  release: import.meta.env.VITE_APP_VERSION,
})
```

React 19에서는 렌더 에러가 다시 던져지지 않고 루트 옵션으로 보고됩니다. Sentry는 이 세 옵션용 핸들러를 제공합니다.

```jsx
createRoot(container, {
  onUncaughtError: Sentry.reactErrorHandler(),
  onCaughtError: Sentry.reactErrorHandler(),
  onRecoverableError: Sentry.reactErrorHandler(),
})
```

- `onUncaughtError`는 에러 바운더리가 잡지 못한 에러, `onCaughtError`는 에러 바운더리가 잡은 에러, `onRecoverableError`는 React가 스스로 복구한 에러(예: Hydration 불일치)에 대응합니다(자세히는 25편, 중급 13편).
- 에러 바운더리 안에서 `componentDidCatch`에서 직접 보고하는 방식도 있으나, 루트 옵션에 연결하면 한곳에서 모두 받습니다.
- `environment`로 dev·staging·prod를 구분하고, `release`로 어느 배포에서 생긴 에러인지 구분합니다. 에러가 어느 배포부터 늘었는지 추적하는 데 필요합니다.
- 이벤트 핸들러·비동기 코드의 에러는 에러 바운더리가 잡지 못하므로 SDK의 전역 핸들러가 수집하거나 직접 `captureException`을 호출합니다.
- 수집하는 데이터에 개인정보(이메일, 토큰, 입력값)가 섞이지 않게 필터링 규칙을 정합니다(자세히는 23편).

**소스맵**은 압축된 번들의 위치를 원본 소스 위치로 되돌리는 매핑 파일입니다. 소스맵이 없으면 스택 트레이스가 `index-Cx3a9fQ2.js:1:48213`처럼 읽을 수 없습니다.

- Sentry는 빌드 중에 소스맵을 Sentry로 업로드하는 방식을 씁니다. 방법은 설치 마법사(`npx @sentry/wizard@latest -i sourcemaps`), 번들러 플러그인(Vite용 포함), `sentry-cli` 세 가지입니다.
- 번들과 소스맵은 빌드 때 심어지는 Debug ID로 연결됩니다. 소스맵을 공개 URL로 서빙하지 않아도 되는 방식입니다.
- 소스맵을 공개 경로에 두면 원본 소스가 노출됩니다. 업로드한 뒤에는 배포 산출물에 `.map` 파일이 남지 않게 합니다.
- 소스맵은 에러가 발생하기 전에 업로드되어 있어야 합니다. 배포 파이프라인에서 업로드 단계를 배포 단계보다 앞에 둡니다.
- 소스맵 생성은 `build.sourcemap` 옵션으로 켭니다(기본값은 `false`).

**흔한 실수:** 소스맵 없이 에러 모니터링을 켜서 알림은 오는데 원인 위치를 모르는 것, 그리고 소스맵을 그대로 호스팅에 올려 두는 것입니다.

## Web Vitals 수집

Web Vitals는 사용자 경험을 수치로 나타낸 지표이고, Core Web Vitals는 그중 세 가지입니다. 합격 기준은 페이지 방문의 75번째 백분위수에서 세 지표가 모두 기준을 만족하는 것입니다.

| 지표 | 측정 대상 | 좋음 기준 |
|------|-----------|-----------|
| LCP | 가장 큰 콘텐츠가 그려지는 시간(로딩) | 2.5초 이내 |
| INP | 상호작용 뒤 다음 화면 갱신까지의 지연(반응성) | 200밀리초 이하 |
| CLS | 레이아웃이 예상 밖으로 움직인 정도(시각 안정성) | 0.1 이하 |

- 측정에는 두 종류가 있습니다. **랩** 측정(Lighthouse, DevTools)은 통제된 환경의 재현 가능한 수치이고, **필드** 측정은 실제 사용자의 기기·네트워크에서 모은 수치입니다. INP는 실제 상호작용이 필요해 랩에서 측정할 수 없습니다.
- 운영에서는 `web-vitals` 라이브러리로 필드 데이터를 수집합니다. 지표마다 `onLCP`, `onINP`, `onCLS`(그리고 `onFCP`, `onTTFB`) 함수가 있고 콜백에 측정값이 전달됩니다.

```js
import { onCLS, onINP, onLCP } from 'web-vitals'

function report(metric) {
  // name, value, rating, delta, id, navigationType
  navigator.sendBeacon('/vitals', JSON.stringify(metric))
}
onLCP(report)
onINP(report)
onCLS(report)
```

- `rating`은 `good`, `needs-improvement`, `poor` 중 하나입니다. `id`는 같은 페이지 방문의 값을 묶는 식별자입니다.
- 페이지가 닫힐 때 전송이 끊기지 않도록 `navigator.sendBeacon`을 씁니다.
- `web-vitals/attribution` 빌드를 쓰면 `attribution` 필드로 느린 원인(어떤 요소가 LCP인지, 어떤 상호작용이 INP를 악화했는지)을 알 수 있어 원인 분석에 씁니다..
- 평균이 아니라 분포(75번째 백분위수)를 봅니다. 라우트·기기·네트워크별로 나눠 집계하면 어디가 느린지 드러납니다. SPA는 화면 전환이 소프트 내비게이션이라 이를 반영하는 `navigationType` 값을 함께 기록합니다.
- 측정과 개선 기법은 중급 20편에서 다뤘습니다.

## 기능 플래그

기능 플래그(feature flag)는 코드를 배포하는 것과 기능을 켜는 것을 분리하는 장치입니다. 런타임에 값이 정해지는 조건문이어서, 재배포 없이 기능을 켜고 끄고, 일부 사용자에게만 열 수 있습니다.

```jsx
function Checkout() {
  const newFlow = useFlag('new-checkout', false)
  return newFlow ? <NewCheckout /> : <OldCheckout />
}
```

- 쓰임새: 카나리 릴리스(소수 사용자에게 먼저), A/B 테스트, 문제 시 즉시 끄는 킬 스위치, 미완성 기능을 코드에 병합하되 숨기기(트렁크 기반 개발), 권한·요금제별 기능 제한.
- 플래그 값은 평가 컨텍스트(사용자 id, 환경, 국가 등)에 따라 달라집니다. 같은 플래그가 사용자마다 다르게 평가됩니다.
- OpenFeature는 벤더에 종속되지 않는 오픈 사양입니다. 코드는 평가 API(`client.getBooleanValue('new-checkout', false)`)만 알고, 실제 값을 가져오는 공급자(provider)를 교체할 수 있습니다. 공급자는 자체 구현, LaunchDarkly 같은 서비스, 오픈소스 도구가 될 수 있습니다.
- 두 번째 인자의 **기본값**이 중요합니다. 플래그 서버에 접근하지 못했을 때 쓰는 값이므로 안전한 쪽(기능 꺼짐)으로 둡니다.
- 플래그는 부채입니다. 출시가 끝나면 플래그와 낡은 분기를 코드에서 제거하고, 만든 사람·목적·제거 예정일을 기록합니다. 오래된 플래그가 쌓이면 조합 수만큼 테스트해야 합니다.
- 클라이언트 쪽 플래그 값은 사용자가 볼 수 있습니다. 숨겨진 기능의 코드가 번들에 있고 값이 네트워크로 전달되므로 권한 판단을 플래그에만 맡기지 않고 서버에서도 검증합니다(자세히는 23편).
- 플래그를 켜고 끌 때의 지표(에러율, Web Vitals, 전환율)를 함께 보고 문제가 있으면 즉시 끕니다. 위의 모니터링 이벤트에 플래그 값을 태그로 달아 둡니다.

## 모노레포

모노레포는 여러 패키지(앱, 디자인 시스템, 공용 설정)를 하나의 저장소에서 관리하는 구성입니다. 앱과 컴포넌트 라이브러리를 함께 수정하고 한 PR로 검토할 수 있고, 공용 코드를 버전 불일치 없이 공유합니다(디자인 시스템 패키지는 22편).

pnpm 워크스페이스는 저장소 루트의 `pnpm-workspace.yaml`로 패키지 위치를 지정합니다.

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

```json
{ "dependencies": { "@acme/ui": "workspace:*" } }
```

- `workspace:` 프로토콜은 레지스트리가 아니라 저장소 안의 패키지로만 해석합니다. 게시할 때는 일반 버전 범위로 바뀝니다.
- 특정 패키지만 대상으로 명령을 실행할 때는 `pnpm --filter 이름 build`처럼 `--filter`를 씁니다.
- 락 파일은 루트에 하나(`pnpm-lock.yaml`)가 기본입니다.
- 패키지 버전 관리와 게시는 pnpm 문서가 changesets 같은 외부 도구를 권합니다.

Turborepo는 모노레포의 작업(build, test, lint)을 의존 순서대로 병렬 실행하고 결과를 캐시하는 도구입니다. 루트의 `turbo.json`에 작업을 정의합니다.

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": { "dependsOn": ["build"] }
  }
}
```

- `dependsOn`의 `^build`는 이 패키지가 의존하는 패키지의 `build`를 먼저 실행하라는 뜻입니다. 접두사 없는 `build`는 같은 패키지의 작업입니다.
- `outputs`는 캐시할 산출물입니다. 입력(소스 파일)이 같으면 작업을 실행하지 않고 캐시된 결과를 복원합니다. 원격 캐시를 쓰면 CI와 팀원 사이에서도 공유됩니다.
- 작업은 기존 `package.json`의 스크립트 이름과 대응합니다. 기존 프로젝트에 점진적으로 도입할 수 있습니다.
- `--filter`로 바뀐 패키지와 그에 의존하는 패키지만 CI에서 실행해 시간을 줄입니다.

**흔한 실수:** 패키지 간 순환 의존, 그리고 `outputs`를 빠뜨려 캐시가 복원되지 않는 것입니다. 작은 프로젝트에 모노레포를 도입하면 설정 비용이 이득보다 클 수 있으므로 공유할 패키지가 둘 이상일 때 고려합니다.

## 국제화

국제화(i18n)는 앱을 여러 언어·지역에 맞게 바꿀 수 있는 구조로 만드는 일입니다. 문자열을 코드에서 분리하고, 숫자·날짜·통화를 지역 규칙으로 표시하는 것이 핵심입니다. 번역하는 작업은 현지화(l10n)입니다.

문자열은 번역 키로 분리하고 번역 파일에서 불러옵니다. React에서 널리 쓰는 `react-i18next`는 `useTranslation` Hook과 `Trans` 컴포넌트를 제공합니다.

```jsx
const { t } = useTranslation()
return <p>{t('inbox.unread', { count })}</p>
// ko.json: "inbox.unread": "안 읽은 메시지 {{count}}개"
```

- 복수형 규칙은 언어마다 다릅니다. 영어는 단수·복수 둘이고 한국어는 구분이 없고 다른 언어는 여럿입니다. 번역 라이브러리의 복수형 기능으로 처리하고 `if (count === 1)`을 직접 쓰지 않습니다.
- 문장을 조각내어 이어 붙이지 않습니다. 어순이 언어마다 달라서 변수를 포함한 하나의 번역 문자열로 둡니다. 문장 안에 태그가 있으면 `Trans` 컴포넌트를 씁니다.
- 번역 파일은 언어·네임스페이스(화면 단위)별로 나누고 해당 언어와 화면이 필요할 때 동적 import로 불러와 번들 크기를 줄입니다. 언어 선택은 사용자 설정, 브라우저 언어(`navigator.language`), 기본 언어 순으로 정합니다.
- 숫자·날짜·통화·상대 시간은 번역 파일이 아니라 브라우저 내장 `Intl`(`NumberFormat`, `DateTimeFormat`, `PluralRules`, `RelativeTimeFormat`, `ListFormat` 등)로 포맷합니다.

```js
new Intl.NumberFormat('de-DE').format(26254.39) // 26.254,39
new Intl.NumberFormat('en-US').format(26254.39) // 26,254.39
```

- 문서의 `lang` 속성을 현재 언어로 갱신하면 스크린 리더와 번역 도구가 올바르게 동작합니다. 아랍어·히브리어처럼 오른쪽에서 왼쪽으로 쓰는 언어는 `dir` 속성과 방향에 중립인 CSS(논리 속성)가 필요합니다.
- 번역문은 원문보다 길어질 수 있습니다. 고정 너비 버튼과 잘림을 피해 레이아웃을 설계합니다.
- 서버 시간은 UTC로 저장하고 표시할 때 사용자 시간대로 바꿉니다. 시간대와 로케일이 서버·클라이언트에서 다르면 Hydration 불일치가 생깁니다(자세히는 03편).
- 번역 키 누락은 CI에서 검사합니다. `i18next-cli` 같은 도구가 키 추출·린트·동기화를 돕습니다.

**흔한 실수:** 한국어 문장 길이에 맞춘 UI, 복수형·성별에 하드코딩된 영어 문법, 날짜를 `toLocaleDateString()` 인자 없이 호출해 실행 환경마다 결과가 달라지는 것입니다.

## AI 코딩 도구와 코드 리뷰

AI 코딩 도구(코드 자동 완성, 대화형 코드 생성, 에이전트)는 초안을 빠르게 만들지만 결과의 책임은 커밋하는 사람에게 있습니다. AI가 쓴 코드도 사람이 쓴 코드와 같은 기준으로 테스트·리뷰·CI를 통과해야 합니다.

- AI는 오래된 API를 섞어 제안할 수 있습니다. 예를 들어 `ReactDOM.render`, 함수 컴포넌트의 `defaultProps`, 불필요한 `useEffect` 같은 패턴입니다. 제안이 현재 버전의 공식 문서와 맞는지 확인합니다(자세히는 25편, 기초 22편).
- 작은 단위로 요청하고 작은 diff로 받습니다. 한 번에 수십 개 파일을 바꾸면 리뷰가 형식적이 됩니다.
- 신뢰의 근거는 AI의 설명이 아니라 테스트와 타입 검사, 린트, 실제 동작 확인입니다. 테스트를 AI가 함께 쓴다면 테스트가 올바른 동작을 검증하는지(기대값이 구현을 베낀 것은 아닌지) 사람이 읽습니다.
- 비밀값(API 키, 토큰, 고객 데이터)을 프롬프트에 붙여 넣지 않습니다. 조직의 데이터 반출 정책과 사용하는 도구의 데이터 처리 방침을 확인합니다.
- 새 의존성 제안은 이름이 실제로 존재하는지, 유지되는 패키지인지, 라이선스와 보안 이력은 어떤지 확인합니다. 존재하지 않는 패키지 이름이 제안되기도 합니다.

AI 코드 리뷰 도구는 PR의 diff를 읽고 버그, 보안 문제, 스타일 문제를 지적합니다. 예를 들어 GitHub Copilot 코드 리뷰는 PR에서 리뷰어로 요청하거나 PR 생성·푸시 때 자동으로 실행하도록 설정할 수 있습니다.

- 공식 문서가 밝히듯 모든 문제를 찾는다고 보장되지 않고 실수도 하므로 지적 사항을 검증하고 사람의 리뷰로 보완합니다. 의존성 파일(`package.json` 등)과 로그, SVG 같은 일부 파일은 리뷰 대상에서 제외됩니다.
- 사람 리뷰어는 AI가 약한 부분에 집중합니다. 요구사항에 맞는지, 상태를 어디에 두었는지, 경계 설계, 접근성, 보안 가정입니다.
- React 리뷰 체크 항목: Effect가 필요한가(기초 22편), 의존성 배열이 정확한가, `key`가 안정적인가, 서버 상태를 `useState`에 복사하지 않았는가, 에러·로딩·빈 상태가 처리됐는가, 접근성(라벨, 키보드)이 지켜졌는가.
- 팀의 규칙을 문서로 정합니다(코딩 규약, 금지 패턴, 테스트 기준). 사람과 도구가 같은 문서를 기준으로 삼아야 결과가 일관됩니다.

**흔한 실수:** 동작하는 것처럼 보인다는 이유로 이해하지 못한 코드를 병합하는 것입니다. 설명할 수 없는 코드는 장애 때 고칠 수 없습니다.

## 핵심 정리

- `vite build`는 정적 파일을 `dist`에 만들고, 청크는 동적 import와 수동 분할(Vite 8은 `codeSplitting.groups`)로 나누며, 크기 경고는 번들 분석으로 원인을 찾아 줄입니다.
- 환경은 `.env.[mode]`와 `--mode`로 나누고, `VITE_` 변수는 번들에 노출되므로 비밀값을 넣지 않습니다.
- SPA 호스팅은 없는 경로를 `index.html`로 200 rewrite해야 하고, 해시 파일은 `immutable` 장기 캐시, `index.html`은 `no-cache`로 두며 배포는 에셋 먼저 `index.html` 나중입니다.
- CI는 린트·테스트·빌드를 PR마다 돌리고, 미리보기 배포는 PR마다 임시 환경을 만들어 병합 전 검증을 가능하게 합니다.
- 운영은 에러 모니터링(`createRoot`의 에러 옵션과 비공개 소스맵)과 Web Vitals 필드 수집(LCP 2.5초, INP 200밀리초, CLS 0.1, 75번째 백분위수)으로 관찰하고, 기능 플래그로 위험을 줄여 출시합니다.
- 모노레포는 pnpm 워크스페이스와 Turborepo 캐시로, 국제화는 번역 키·`Intl`·로케일별 지연 로딩으로, AI 도구의 결과는 테스트와 사람의 리뷰로 검증합니다.

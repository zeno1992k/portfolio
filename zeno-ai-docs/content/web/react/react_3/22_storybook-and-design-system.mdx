## 디자인 시스템 구성

디자인 시스템은 여러 제품이 같은 UI를 일관되게 만들 수 있도록 디자인 결정과 그것을 구현한 코드, 사용 설명을 한 묶음으로 관리하는 체계입니다. 구성은 아래쪽 층일수록 바뀌는 일이 적고, 위쪽 층이 아래쪽 층에 의존합니다.

| 층 | 내용 | 예 |
|----|------|----|
| 토큰 | 색, 간격, 글꼴, 그림자 같은 디자인 결정을 이름 붙인 값 | `color.brand`, `space.4` |
| 프리미티브 | 스타일이 없거나 최소인 동작·접근성 기반 요소 | Dialog, Popover, Slot |
| 컴포넌트 | 토큰과 프리미티브로 만든 완성 UI | Button, Input, Modal |
| 문서 | 사용법, 가이드라인, 살아 있는 예제 | Storybook 페이지 |

- 프리미티브는 13편의 Headless Component가 해당합니다. 키보드·포커스·ARIA 책임을 프리미티브가 지고, 컴포넌트는 스타일과 조합만 담당합니다.
- 토큰을 거치지 않고 컴포넌트에 색을 직접 쓰면 테마 변경과 일관성이 깨집니다.
- 컴포넌트 API 설계 원칙(작은 Props, Variant, Escape Hatch)은 10편을 따릅니다.
- 문서가 코드와 따로 있으면 낡습니다. 코드와 같은 저장소에서 컴포넌트가 바뀔 때 함께 바뀌는 문서가 필요하고, 그 역할을 Storybook이 합니다.
- 직접 만들지 않고 기존 라이브러리를 가져다 쓰는 방법은 UI Libraries 과목에서 다룹니다.

## Storybook과 CSF

Storybook은 컴포넌트와 페이지를 앱 밖에서 격리해 개발하고 확인하는 도구입니다. 문서 기준 최신 버전은 10.6입니다. 앱 전체를 띄우지 않고도 로딩, 에러, 빈 상태처럼 만들기 어려운 상태를 바로 볼 수 있습니다. 문서는 세 기둥을 스토리(Stories), 문서화(Documentation), 테스트(Testing)로 설명합니다.

설치 명령은 `npm create storybook@latest`입니다. React와 Vite 조합은 `@storybook/react-vite` 프레임워크 패키지를 쓰며 React 16.8 이상, Vite 5 이상이 필요합니다.

스토리는 컴포넌트의 한 상태를 코드로 적은 것이고, 스토리를 적는 형식이 CSF(Component Story Format)입니다. 문서 기준 현재 표준은 CSF 3입니다(CSF Next는 프리뷰). 파일 하나에 컴포넌트 하나를 두는 구조입니다.

```tsx
// Button.stories.tsx
import type { Meta, StoryObj } from '@storybook/react-vite'
import { Button } from './Button'

const meta = {
  component: Button,
  args: { children: '저장' },
} satisfies Meta<typeof Button>
export default meta
type Story = StoryObj<typeof meta>

export const Primary: Story = {
  args: { variant: 'primary' },
}
export const Disabled: Story = { args: { disabled: true } }
```

- 기본 내보내기(default export)는 메타데이터입니다. 필드는 `component`(필수), `title`, `tags`, `args`, `argTypes`, `decorators`, `parameters`, `render`, `play`입니다.
- 이름 있는 내보내기(named export) 하나가 스토리 하나입니다. 식별자는 화면에서 시작 대문자 형태로 바뀝니다(`myStory`는 "My Story").
- `title`을 생략하면 파일 경로로 사이드바 위치가 정해집니다.
- 타입은 `Meta`(기본 내보내기)와 `StoryObj`(스토리)입니다. `satisfies Meta<typeof Button>`를 쓰면 `args`가 컴포넌트 Props로 타입 검사됩니다.
- 스토리 파일이 아닌 보조 내보내기(목 데이터 등)는 `includeStories`·`excludeStories`로 걸러 냅니다.
- 스토리는 렌더 함수 없이 `args`만으로 충분합니다. 직접 그려야 하면 `render` 필드를 씁니다.

**흔한 실수:** 스토리 하나에 여러 상태를 몰아 넣는 것입니다. 상태 하나당 스토리 하나로 나누어야 문서, 시각 회귀, 인터랙션 테스트가 각각 그 상태를 가리킬 수 있습니다.

## args와 controls

args는 컴포넌트에 넘길 인자(Props)를 하나의 객체로 모은 것입니다. 컴포넌트 코드를 바꾸지 않고 값을 바꿔 가며 상태를 만들 수 있게 합니다. 정의 위치는 세 단계이고 구체적일수록 우선합니다.

| 수준 | 위치 | 적용 범위 |
|------|------|-----------|
| 스토리 | 스토리의 `args` | 그 스토리 |
| 컴포넌트 | 기본 내보내기의 `args` | 그 파일의 모든 스토리 |
| 프로젝트 | `.storybook/preview.ts`의 `args` | 모든 스토리 |

```tsx
export const Secondary: Story = {
  args: { ...Primary.args, variant: 'secondary' },
}
```

- 다른 스토리의 args를 스프레드로 재사용합니다.
- 이벤트 핸들러 Props는 `storybook/test`의 `fn()`을 args로 넘기면 호출이 기록되고, 인터랙션 테스트에서 호출 여부를 단언할 수 있습니다(아래 "play function").

```tsx
import { fn } from 'storybook/test'

const meta = {
  component: Button,
  args: { onClick: fn() },
} satisfies Meta<typeof Button>
```

Controls 애드온은 args를 화면에서 직접 바꾸는 입력 UI를 만듭니다. 메타에 `component`를 지정하면 `react-docgen` 같은 도구로 TypeScript 타입에서 컨트롤을 추론합니다. 추론을 바꾸려면 `argTypes`로 덮어씁니다.

```tsx
argTypes: {
  variant: {
    options: ['primary', 'secondary'],
    control: { type: 'radio' },
  },
  onClick: { control: false },
},
```

- `parameters.controls.matchers`가 이름 규칙으로 컨트롤을 정합니다. 기본값은 `background`나 `color`로 끝나는 이름에 컬러 피커, `Date`로 끝나는 이름에 날짜 선택기입니다.
- 컨트롤을 끄려면 `control: false`나 `table: { disable: true }`, 일부만 보이려면 `include`·`exclude`를 씁니다.
- 다른 값에 따라 컨트롤을 보이려면 `if`를 씁니다.
- 파라미터(`parameters`)는 스토리 수준, 컴포넌트 수준, 전역 수준에 두며 구체적인 쪽이 우선하고, 병합되므로 키가 덮어써질 뿐 사라지지 않습니다. 대표적으로 `layout`(`centered`, `padded`, `fullscreen`), `backgrounds`, `viewport`가 있습니다.

## decorator

decorator는 스토리를 다른 렌더링 기능으로 감싸는 함수입니다. 여백 같은 마크업을 더하거나 Context Provider, 라우터, 테마를 제공할 때 씁니다. 컴포넌트가 앱 안에서는 Provider 아래에 있으므로, Storybook에서도 같은 조건을 만들어 줘야 합니다.

```tsx
const meta = {
  component: Button,
  decorators: [
    (Story) => (
      <div style={{ padding: '1rem' }}>
        <Story />
      </div>
    ),
  ],
} satisfies Meta<typeof Button>
```

- 시그니처는 `(Story, context)`입니다. `context`에는 `args`, `argTypes`, `globals`, `parameters`, `viewMode` 등이 있습니다.
- 적용 수준은 스토리, 컴포넌트, 전역(`.storybook/preview.tsx`의 `decorators`)입니다.
- 순서는 전역이 가장 바깥, 그다음 컴포넌트, 가장 안쪽이 스토리 decorator입니다.
- 앱 전역에 필요한 Provider(테마, 라우터, i18n, Query 클라이언트)는 전역 decorator에 한 번 둡니다.
- 테마 전환은 `@storybook/addon-themes`의 `withThemeByClassName`, `withThemeByDataAttribute`, `withThemeFromJSXProvider`를 씁니다. 사용 방식(클래스, 데이터 속성, Provider)에 맞는 것을 골라 전역에 등록합니다.
- 네트워크가 필요한 컴포넌트는 `msw-storybook-addon`으로 요청 응답을 스토리마다 정합니다. 핸들러는 스토리의 `beforeEach`에서 `msw.use(...)`로 등록합니다.

**흔한 실수:** 스토리마다 같은 Provider를 반복해서 감싸는 것입니다. 모든 스토리가 필요로 하는 것은 전역 decorator로 올리고, 스토리 수준은 그 스토리만 다른 조건에만 씁니다.

## play function과 인터랙션 테스트

play function은 스토리가 렌더링된 뒤 자동으로 실행되는 함수입니다. 사용자의 조작을 흉내 내고 결과를 단언해서 수동 확인 없이 상호작용을 검증합니다.

```tsx
import { expect, fn } from 'storybook/test'

export const Submits: Story = {
  args: { onSubmit: fn() },
  play: async ({ canvas, userEvent, args }) => {
    await userEvent.type(canvas.getByLabelText('이름'), 'Kim')
    await userEvent.click(canvas.getByRole('button'))
    await expect(args.onSubmit).toHaveBeenCalledWith('Kim')
  },
}
```

- `canvas`는 스토리 루트 안으로 범위가 좁혀진 Testing Library 쿼리입니다. `getBy`, `queryBy`, `findBy` 계열을 씁니다. 모달처럼 canvas 밖에 그려지는 요소는 `storybook/test`의 `screen`으로 찾습니다.
- `userEvent`는 입력과 클릭을 시뮬레이션하고, 단언은 `storybook/test`의 `expect`입니다. 모든 호출은 `await`합니다.
- `step()`으로 조작 묶음에 이름을 붙이고, `beforeEach()`로 사전 설정을 합니다.
- Interactions 패널에서 각 단계를 되돌려 보고 멈추며 디버깅합니다.
- 다른 스토리의 play를 불러서 시나리오를 이을 수 있습니다: `await FirstStory.play(context)`.
- 쿼리 원칙은 중급 35편의 Testing Library와 같습니다. 역할과 label 기반으로 찾습니다(자세히는 20편).

play function이 있는 스토리는 곧 테스트입니다. 실행 방법은 두 가지입니다.

- Storybook UI의 사이드바 테스트 위젯.
- `@storybook/addon-vitest`(설치: `npx storybook add @storybook/addon-vitest`). 스토리를 Vitest 테스트로 바꿔 실제 브라우저(기본은 Vitest 브라우저 모드와 Playwright Chromium)에서 실행합니다. 렌더링만 확인하는 스모크 테스트와 play function 실행이 모두 포함되고, Vitest 3.0 이상이 필요합니다. CI에서도 같은 방식으로 실행합니다.

컴포넌트 단위의 인터랙션은 스토리로, 페이지를 가로지르는 사용자 경로는 E2E로 나눠 두는 것이 일반적인 역할 분담입니다(자세히는 21편).

## 시각 회귀 테스트

Storybook의 시각 테스트는 모든 스토리를 스냅샷으로 찍어 승인된 기준 이미지와 픽셀 단위로 비교합니다. 공식 문서가 안내하는 방법은 Chromatic(Storybook 팀의 클라우드 서비스)과 `@chromatic-com/storybook` 애드온입니다.

| 단계 | 내용 |
|------|------|
| 기준 생성 | 첫 실행에서 모든 스토리의 스냅샷이 기준(baseline)이 됨 |
| 비교 | 이후 실행마다 새 스냅샷과 기준을 비교 |
| 검토 | 바뀐 스토리를 표시. 의도한 변경은 승인, 아니면 거부 |
| PR 연동 | CI에서 풀 리퀘스트에 UI 테스트 결과가 붙어 의도치 않은 변경을 막음 |

- 스토리 하나가 테스트 하나이므로 테스트 코드를 따로 작성하지 않습니다.
- 크로스 브라우저 비교를 지원합니다.
- DOM 마크업이 아니라 렌더된 픽셀을 비교하므로 CSS 회귀를 잡습니다.
- 스토리가 상태마다 나뉘어 있어야 어느 상태가 깨졌는지 바로 보입니다.
- 페이지 단위 Playwright 스냅샷과 비교하면 이쪽은 컴포넌트 단위라서 변경의 원인 범위가 좁습니다(자세히는 21편).
- 시간, 랜덤 값, 애니메이션이 스냅샷에 들어가면 매번 차이가 납니다. 스토리에서 값을 고정합니다.

## 접근성 애드온

`@storybook/addon-a11y`는 Deque의 axe-core로 스토리의 접근성 위반을 자동 검사합니다(설치: `npx storybook add @storybook/addon-a11y`). 접근성 패널에 위반 항목과 수정 제안이 표시되고, 툴바에서 시각 장애를 시뮬레이션할 수도 있습니다.

`parameters.a11y`로 설정합니다.

| 키 | 역할 |
|----|------|
| `context` | 검사할 DOM 범위(기본 `body`) |
| `config` | axe 규칙 개별 설정 |
| `options` | 검사 규칙 집합(WCAG 2.0 AA, AAA 등) |
| `test` | Vitest 애드온과 함께 쓸 때의 동작 |

```tsx
parameters: {
  a11y: { test: 'error' },
},
```

- `test: 'error'`는 위반을 테스트 실패로 처리해 CI에서 막습니다.
- `test: 'todo'`는 위반을 UI에 경고로만 표시합니다. 고칠 목록을 추적할 때 씁니다.
- `test: 'off'`는 검사를 끕니다. 잘못된 사용 예를 일부러 보일 때만 씁니다.
- Vitest 애드온과 함께 쓰면 사이드바 테스트 위젯에서 접근성 검사를 같이 돌립니다.
- 자동 검사로는 WCAG 문제의 일부(공식 문서는 최대 57%)만 잡힙니다. 키보드 조작, 포커스 순서, 스크린 리더 안내는 수동으로 확인해야 합니다(자세히는 20편).

## 문서 자동 생성

Autodocs는 스토리에서 컴포넌트 문서 페이지를 자동으로 만듭니다. `tags`에 `autodocs`를 추가하면 켜집니다.

```tsx
const meta = {
  component: Button,
  tags: ['autodocs'],
} satisfies Meta<typeof Button>
```

- 컴포넌트마다 메타의 `tags`에 쓰거나, 전역은 `.storybook/preview.ts`의 `tags`에 씁니다. 끄려면 `'!autodocs'`입니다.
- 생성되는 페이지는 제목과 설명, 컨트롤이 붙은 대표 스토리, 모든 `args`와 `argTypes`의 Props 표, 나머지 스토리 목록입니다.
- 설명은 컴포넌트와 Props의 JSDoc 주석에서 가져옵니다. 주석을 쓰는 것이 곧 문서 작성입니다.
- `docs` 파라미터로 이름(`defaultName`)과 목차(`toc: true`)를 정합니다. Doc Blocks(`Title`, `Controls`, `Stories` 등)로 템플릿을 직접 구성할 수 있고, MDX 문서와 함께 쓸 수 있습니다.
- 정리하면 코드(타입, JSDoc, args)가 단일 출처이고 문서는 거기서 생성됩니다. 문서와 구현이 어긋나지 않습니다.

게시는 `npm run build-storybook`으로 정적 사이트(`storybook-static` 폴더)를 만들어 올립니다. Chromatic은 호스팅과 버전 관리를 제공하고, GitHub Pages, Netlify, S3 같은 정적 호스팅에도 올릴 수 있습니다.

## 디자인 토큰과 CSS 변수

디자인 토큰은 디자인 결정을 이름 붙인 값으로 분리한 것입니다. 코드는 `#2563eb` 대신 `color.brand`를 참조하고, 값 변경과 테마 전환이 토큰 한 곳에서 일어납니다.

| 구분 | 내용 | 예 |
|------|------|----|
| 원시(primitive) 토큰 | 값 자체 | `blue-600: #2563eb` |
| 의미(semantic) 토큰 | 용도를 이름으로 가리킴 | `color-action: blue-600` |
| 컴포넌트 토큰 | 한 컴포넌트에 한정 | `button-bg: color-action` |

컴포넌트는 의미 토큰이나 컴포넌트 토큰을 참조하고 원시 토큰을 직접 참조하지 않습니다. 다크 모드는 의미 토큰이 가리키는 원시 토큰을 바꿔서 구현합니다.

웹에서 토큰을 런타임에 적용하는 표준 수단이 CSS 변수(custom property)입니다. `--`로 선언하고 `var()`로 읽습니다.

```css
:root {
  --color-action: #2563eb;
  --space-4: 1rem;
}
[data-theme='dark'] {
  --color-action: #60a5fa;
}
.btn {
  background: var(--color-action, blue);
  padding: var(--space-4);
}
```

- CSS 변수는 항상 상속되므로 `:root`에 선언하면 전역이고, 하위 요소에서 다시 선언하면 그 서브트리에서만 값이 바뀝니다. 테마 전환이 클래스나 속성 하나로 되는 이유입니다.
- `var(--name, fallback)`의 두 번째 인자는 변수가 없을 때의 대체값입니다.
- SCSS 같은 전처리기 변수는 빌드할 때 값으로 치환되지만 CSS 변수는 런타임에 계산됩니다. JavaScript의 `style.setProperty('--x', v)`로 바꿀 수도 있습니다.
- `@property`로 변수의 타입(`syntax`), 상속 여부, 초기값을 선언하면 잘못된 값이 들어와도 초기값으로 되돌립니다.
- 토큰의 원본은 JSON 같은 도구 중립 형식으로 두고, 빌드 단계에서 CSS 변수와 Figma 변수 등으로 변환하는 구조가 흔합니다. Design Tokens Community Group은 `$type`과 `$value`를 쓰는 JSON 형식을 표준화하고 있고, 2025년 10월 28일에 첫 안정판 2025.10을 냈습니다.
- Storybook에서 테마를 확인하려면 앞의 `withThemeByDataAttribute`로 `data-theme`를 전환하는 전역 decorator를 둡니다.

**흔한 실수:** 의미 없이 원시 토큰을 컴포넌트에 직접 쓰는 것입니다. 다크 모드나 브랜드 테마를 추가할 때 컴포넌트를 모두 고쳐야 합니다.

## 패키지 배포와 버전 관리

디자인 시스템을 여러 앱이 쓰려면 npm 패키지로 배포합니다. 패키지 구성의 핵심은 세 가지입니다.

- React는 `peerDependencies`로 선언합니다. 소비하는 앱이 React를 제공하고, 라이브러리가 자기 사본을 번들하면 React가 두 개 생겨 Hook이 깨질 수 있습니다. 범위는 `^18 || ^19`처럼 넓게 둡니다.
- 번들에서도 React 같은 의존성은 externalize합니다. Vite의 라이브러리 모드(`build.lib`)는 `entry`, `name`, `fileName`과 `formats`를 받고, 외부화 대상은 빌드 옵션의 `external`에 적습니다. Vite는 타입 선언 파일(`.d.ts`)을 만들지 않으므로 별도 도구가 필요합니다.
- `exports` 필드로 공개 진입점을 정합니다. 여기에 없는 내부 경로는 소비자가 불러올 수 없으므로 공개 API가 캡슐화됩니다. `files` 필드는 게시에 포함할 파일을 정하고, `publishConfig`는 접근 수준과 레지스트리를 정합니다.

버전은 semver(MAJOR.MINOR.PATCH)를 따릅니다.

| 올리는 자리 | 조건 | 디자인 시스템의 예 |
|-------------|------|--------------------|
| MAJOR | 호환되지 않는 API 변경 | Props 이름 변경·삭제, 토큰 이름 변경 |
| MINOR | 호환되는 기능 추가 | 새 컴포넌트, 새 variant |
| PATCH | 호환되는 버그 수정 | 스타일 결함, 접근성 버그 수정 |

- `0.y.z`는 개발 초기로 아무것도 안정적이지 않다고 간주합니다. 사전 릴리스는 `1.0.0-alpha.1`, `1.0.0-beta` 형식이며 정식 버전보다 낮은 우선순위입니다.
- 소비자의 `^1.2.0`은 1.x 안의 호환 변경을 자동으로 받습니다. 그래서 MAJOR 없이 깨지는 변경을 내면 안 됩니다.
- 시각 결과가 바뀌는 변경도 소비자에게는 사실상 변경입니다. 시각 회귀 테스트가 그 변경을 의도한 것인지 검토하게 합니다.

changeset은 이 버전 판단을 코드 변경 시점에 기록하는 도구입니다. 기여자가 변경을 만들 때 bump 종류(major·minor·patch)와 변경 요약을 파일로 남기고, 릴리스 때 그 파일들이 모여 버전과 변경 로그(CHANGELOG)가 된다는 흐름입니다.

```bash
npx @changesets/cli init      # 최초 설정
npx @changesets/cli           # changeset 추가(대화형)
npx @changesets/cli version   # 버전과 CHANGELOG 갱신
npx @changesets/cli publish   # npm에 게시
```

- 모노레포에서는 의존하는 패키지의 버전도 함께 올려 줍니다. 모든 변경에 changeset이 필요한 것은 아닙니다(문서만 바꾼 경우 등).
- CI에서 풀 리퀘스트에 changeset이 있는지 확인하고, 릴리스 브랜치에서 `version`과 `publish`를 실행하게 구성합니다. 파이프라인과 모노레포는 26편에서 다룹니다.

## Figma 연동

디자인과 코드를 잇는 방식은 세 가지입니다.

| 방식 | 방향 | 설명 |
|------|------|------|
| Designs 애드온 | 디자인 → Storybook | Storybook 패널 안에 Figma 프레임을 임베드 |
| Storybook Connect | 코드 → Figma | Figma 플러그인으로 스토리를 Figma 컴포넌트에 연결 |
| Code Connect | 코드 → Figma Dev Mode | Figma 컴포넌트에 실제 코드 스니펫을 매핑 |

Designs 애드온(`@storybook/addon-designs`)은 스토리의 `design` 파라미터에 Figma URL을 적습니다.

```tsx
export const Primary: Story = {
  parameters: {
    design: {
      type: 'figma',
      url: 'https://www.figma.com/file/Sample-File',
    },
  },
}
```

- Storybook Connect는 Chromatic에 게시된 Storybook이 필요하고, 코드가 푸시되면 연결된 링크가 갱신됩니다.
- Code Connect(`@figma/code-connect`)는 `figma.connect()`를 쓰는 `.figma.tsx` 파일로 Figma 컴포넌트와 React 컴포넌트를 매핑하고, Dev Mode에서 속성 매핑에 따른 코드가 표시됩니다. 이 파일은 실행되지 않고 코드 스니펫이 문자열로 취급되므로 조건 로직은 쓴 그대로 표시됩니다. 공식 React 안내는 프레임워크별 파서가 더 이상 업데이트되지 않고 템플릿 파일 방식이 유지된다고 적고 있으므로, 도입할 때 최신 문서를 확인합니다.
- 연동이 해결하는 것은 디자이너와 개발자가 같은 이름(컴포넌트, variant, 토큰)을 쓰게 하는 일입니다. 이름이 맞지 않으면 연동은 의미가 없습니다.

## 핵심 정리

- 디자인 시스템은 토큰, 프리미티브, 컴포넌트, 문서 층으로 나뉘고 위 층은 아래 층에 의존합니다. 컴포넌트는 의미 토큰을 참조합니다.
- CSF의 기본 내보내기는 메타데이터, 이름 있는 내보내기는 스토리입니다. 상태 하나당 스토리 하나로 쓰고 args로 값을, argTypes로 컨트롤을 정합니다.
- decorator는 스토리를 Provider와 테마로 감싸고(전역, 컴포넌트, 스토리 순으로 바깥에서 안쪽), play function은 렌더링 후 조작을 흉내 내 인터랙션 테스트가 됩니다.
- 시각 회귀(Chromatic)는 스토리를 기준 이미지와 픽셀 비교하고, 접근성 애드온(axe-core)은 자동으로 잡는 범위가 일부라서 수동 확인이 남습니다.
- Autodocs는 타입과 JSDoc에서 문서를 만듭니다. 토큰은 CSS 변수로 적용해 서브트리 단위 테마를 구현합니다.
- 배포는 React를 peerDependencies로 두고 exports로 공개 API를 정하며, semver와 changeset으로 변경 영향을 기록합니다. Figma는 Designs 애드온, Storybook Connect, Code Connect로 연결합니다.

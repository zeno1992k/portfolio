## Compiler 설치

컴파일러는 `babel-plugin-react-compiler` 패키지를 개발 의존성으로 설치해 씁니다. 개념과 버전 정보는 07편에서 다뤘습니다.

```bash
npm install -D babel-plugin-react-compiler@latest
```

- npm 기준 `latest` 태그는 1.0.0입니다(2025-10-07 게시).
- 공식 1.0 발표 글은 `--save-exact`(줄여서 `-E`)로 설치해 정확한 버전(예: `1.0.0`)에 고정하라고 권합니다. 버전이 바뀌면 메모이제이션의 세분화가 달라질 수 있기 때문입니다.

```bash
npm i -D -E babel-plugin-react-compiler@latest
```

- React 19는 컴파일러 런타임이 내장되어 있어 추가 설치가 없습니다.
- React 17과 18은 `react-compiler-runtime`을 `dependencies`(devDependencies가 아님)에 설치하고 `target` 옵션을 지정해야 합니다.

```js
// React 18 프로젝트의 컴파일러 옵션
{ target: '18' } // 값은 문자열, 패치 버전은 쓰지 않음
```

| 옵션 | 값 | 기본값 |
|------|-----|--------|
| `target` | `'17'`, `'18'`, `'19'` | `'19'` |

## Babel Plugin

컴파일러의 본체는 Babel 플러그인입니다. 다른 빌드 도구의 연동도 결국 이 플러그인을 호출합니다.

```js
// babel.config.js
module.exports = {
  plugins: [
    'babel-plugin-react-compiler', // 가장 먼저 실행해야 함
    // 다른 플러그인
  ],
}
```

- 컴파일러는 플러그인 목록의 맨 앞에 두어야 합니다. 다른 플러그인이 먼저 코드를 바꾸면 컴파일러가 원래 코드를 분석하지 못합니다.
- 옵션을 넣으려면 `['babel-plugin-react-compiler', { 옵션 }]` 형태의 배열로 씁니다.
- 디렉터리 단위 적용은 `overrides`로 할 수 있습니다(07편의 점진적 도입).

```js
overrides: [{
  test: './src/modern/**/*.{js,jsx,ts,tsx}',
  plugins: ['babel-plugin-react-compiler'],
}]
```

## Vite 연동

Vite는 `@vitejs/plugin-react`의 버전에 따라 연결 방식이 다릅니다. 공식 문서가 안내하는 방식은 세 가지입니다.

```js
// @vitejs/plugin-react 6.0.0 이상
import react, { reactCompilerPreset }
  from '@vitejs/plugin-react'
import babel from '@rolldown/plugin-babel'

export default defineConfig({
  plugins: [
    react(),
    babel({ presets: [reactCompilerPreset()] }),
  ],
})
```

```js
// 이전 버전의 @vitejs/plugin-react
export default defineConfig({
  plugins: [
    react({
      babel: { plugins: ['babel-plugin-react-compiler'] },
    }),
  ],
})
```

- 새 프로젝트는 `npm create vite@latest`의 템플릿에서 컴파일러 포함 선택지를 제공합니다.
- React Router 프레임워크는 `vite-plugin-babel`에 `babel-plugin-react-compiler`를 설정합니다.
- 사용 중인 `@vitejs/plugin-react`의 버전을 먼저 확인하고 위 방식 중 맞는 것을 고릅니다.

## Next.js 연동

Next.js는 `next.config`의 `reactCompiler` 옵션으로 켭니다. 패키지는 별도로 설치해야 합니다.

```js
// next.config.js
const nextConfig = {
  reactCompiler: true,
}
module.exports = nextConfig
```

- Next.js 공식 문서는 `babel-plugin-react-compiler`를 설치한 뒤 이 옵션을 추가하라고 안내합니다.
- Next.js는 SWC 기반 최적화를 써서 JSX나 Hook이 있는 파일 같은 관련 파일에만 컴파일러를 적용합니다. Babel 플러그인만 쓰는 것보다 빌드가 빠릅니다. 이 지원은 Next.js 15.3.1 이상이 권장됩니다.
- 옵트인 모드로 쓰려면 `reactCompiler`에 객체를 넘깁니다.

```js
const nextConfig = {
  reactCompiler: { compilationMode: 'annotation' },
}
```

- 설정 위치와 옵션 이름은 Next.js 쪽 문서가 기준입니다. 버전에 따라 달라질 수 있어 사용하는 Next.js의 문서를 확인합니다(자세히는 24편, Next.js 과목).

## Compilation Mode

`compilationMode`는 어떤 함수를 컴파일할지 고르는 방식입니다.

| 값 | 컴파일 대상 | 용도 |
|----|-------------|------|
| `'infer'` (기본값) | 컴포넌트(파스칼 케이스 이름)와 Hook(`use` 접두사)처럼 JSX를 만들거나 Hook을 호출하는 함수, `"use memo"`가 붙은 함수 | 대부분의 코드베이스 |
| `'annotation'` | `"use memo"`가 붙은 함수만 | 점진적 도입 |
| `'syntax'` | Flow의 `component`, `hook` 문법으로 쓴 함수만 | Flow 코드베이스 |
| `'all'` | 모든 최상위 함수 | 권장하지 않음. React와 무관한 유틸 함수까지 컴파일됨 |

```js
{ compilationMode: 'annotation' }
```

- `infer`에서 `calculateTotal(items)` 같은 일반 유틸 함수는 컴파일되지 않습니다.
- 어떤 모드에서도 `"use no memo"`가 붙은 함수는 항상 건너뜁니다.

## use memo

`"use memo"`는 함수를 컴파일 대상으로 지정하는 지시어입니다. 함수 본문 맨 앞의 문자열 리터럴 문장으로 씁니다.

```js
function TodoList({ todos }) {
  "use memo"
  const sorted = todos.slice().sort()
  return <List items={sorted} />
}
```

- `annotation` 모드에서 컴파일할 함수를 고를 때 씁니다.
- `infer` 모드에서는 컴파일러의 판단을 넘어 강제로 컴파일하게 할 때 씁니다.
- 파일 맨 위(import보다 앞)에 쓰면 모듈 전체에 적용되고, 함수 안의 지시어가 모듈 지시어보다 우선합니다.
- 지시어는 첫 번째 문장이어야 합니다.

## use no memo

`"use no memo"`는 함수를 컴파일에서 제외하는 지시어입니다.

```js
function Legacy() {
  "use no memo" // TODO: 라이브러리 v2 업그레이드 후 제거
  return <ThirdPartyWidget />
}
```

- 문제가 의심되는 컴포넌트를 임시로 제외해 컴파일러가 원인인지 확인하는 디버깅에 씁니다. 컴파일을 끄고 문제가 사라지면 Rules of React 위반입니다.
- 모듈 수준 `"use memo"` 안에서도 특정 함수만 `"use no memo"`로 제외할 수 있습니다.
- 영구 설정이 아니라 임시 우회입니다. 이유를 주석(TODO)으로 남기고 근본 원인을 고친 뒤 제거합니다.

**흔한 실수:** `"use no memo"`를 붙인 채 잊는 것입니다. 해당 컴포넌트는 계속 최적화에서 빠지고, 고친 뒤에는 개발자 도구에서 ✨ 배지가 보이는지 확인해야 합니다.

## Diagnostics

컴파일러는 최적화할 수 없는 컴포넌트를 만나면 빌드를 멈추는 대신 건너뜁니다. 건너뛴 이유와 컴파일 상황을 알려 주는 진단 수단이 있습니다.

| 수단 | 역할 |
|------|------|
| `panicThreshold` | 컴파일 문제 시 빌드를 실패시킬지 정함 |
| `logger` | 컴파일 이벤트를 받아 기록함 |
| ESLint 규칙 | 코드 작성 중에 위반을 미리 알림 |

`panicThreshold`의 값은 다음과 같습니다.

| 값 | 동작 |
|----|------|
| `'none'` (기본값) | 컴파일할 수 없는 컴포넌트는 건너뛰고 빌드를 계속함 |
| `'critical_errors'` | 심각한 컴파일러 오류에서만 빌드 실패 |
| `'all_errors'` | 모든 컴파일러 진단에서 빌드 실패 |

- 프로덕션 빌드는 `'none'`을 권장합니다. 컴파일 문제 때문에 빌드가 깨지지 않고, 최적화되지 않은 컴포넌트도 정상 동작합니다.
- 높은 임계값은 개발 중 디버깅에 유용합니다.

`logger`의 `logEvent`는 컴파일 이벤트마다 호출됩니다.

```js
{
  logger: {
    logEvent(filename, event) {
      if (event.kind === 'CompileError') {
        console.error(filename, event.detail.reason)
      }
    },
  },
}
```

- 이벤트 종류는 `CompileSuccess`(컴파일 성공), `CompileError`(오류로 건너뜀), `CompileDiagnostic`(치명적이지 않은 진단), `CompileSkip`(그 외 이유로 건너뜀), `PipelineError`(예상치 못한 오류), `Timing`(성능 측정)입니다.
- `CompileError`의 `event.detail`에는 `reason`, `description`, `loc`(위치), `suggestions`(수정 제안)가 들어 있습니다.

## ESLint

`eslint-plugin-react-hooks`는 Rules of React를 린트로 검사합니다. 컴파일러 1.0 이후로 컴파일러 기반 규칙이 이 플러그인에 들어 있어서 컴파일러를 설치하지 않아도 린트 규칙만 쓸 수 있습니다.

```bash
npm install -D eslint-plugin-react-hooks@latest
```

```js
// eslint.config.js (Flat Config)
import reactHooks from 'eslint-plugin-react-hooks'
export default [reactHooks.configs.flat.recommended]
```

- 구버전 설정 파일(`eslintrc`)에서는 `"extends": ["plugin:react-hooks/recommended"]`로 씁니다.
- 컴파일러 규칙은 `recommended`와 `recommended-latest` 프리셋에 포함됩니다.
- 컴파일러는 위반이 있는 컴포넌트를 건너뛰고 나머지는 계속 컴파일하므로 린트 위반을 즉시 고치지 않아도 앱이 깨지지 않습니다. 대신 그 컴포넌트는 최적화되지 않습니다.

## 컴파일러 규칙

`eslint-plugin-react-hooks`가 제공하는 규칙 가운데 컴파일러와 관련된 주요 규칙은 다음과 같습니다.

| 규칙 | 검사 내용 |
|------|-----------|
| `rules-of-hooks` | Hook을 최상위에서 React 함수에서만 호출하는지 |
| `exhaustive-deps` | Hook의 의존성 배열이 빠짐없는지 |
| `set-state-in-render` | 렌더링 중에 상태를 설정하지 않는지 |
| `set-state-in-effect` | Effect 안에서 상태를 동기적으로 설정하지 않는지 |
| `refs` | 렌더링 중에 ref를 읽거나 쓰지 않는지 |
| `immutability` | props, state 같은 불변 값을 변경하지 않는지 |
| `purity` | 알려진 비순수 함수를 렌더링 중에 호출하지 않는지 |
| `globals` | 렌더링 중에 전역 값을 대입하거나 변경하지 않는지 |
| `static-components` | 컴포넌트를 렌더링마다 새로 만들지 않는지 |
| `error-boundaries` | 자식의 오류를 try와 catch 대신 Error Boundary로 처리하는지 |
| `incompatible-library` | 메모이제이션과 호환되지 않는 라이브러리를 쓰는지 |
| `preserve-manual-memoization` | 기존 수동 메모이제이션을 컴파일러가 보존할 수 있는지 |
| `use-memo` | `useMemo`가 값을 반환하는지 |
| `unsupported-syntax` | 컴파일러가 지원하지 않는 문법을 쓰는지 |

- 위 목록은 공식 레퍼런스가 `recommended` 프리셋에 포함된 규칙으로 정리한 것 중 일부입니다. 이 밖에 컴파일러 옵션을 검사하는 `config`, `gating` 규칙과 `component-hook-factories` 규칙도 있습니다.
- 규칙이 많아 보여도 대부분 07편의 Rules of React를 코드 패턴별로 쪼갠 것입니다.

## 기존 Memoization

컴파일러를 도입해도 기존 코드의 `useMemo`, `useCallback`, `React.memo`를 반드시 지울 필요는 없습니다.

- 공식 문서는 기존 메모이제이션을 그대로 두거나, 지우기 전에 충분히 테스트하라고 안내합니다. 지우면 컴파일 결과가 달라질 수 있습니다.
- `preserve-manual-memoization` 규칙은 수동 메모이제이션을 컴파일러가 그대로 보존할 수 있는지 검사합니다.
- Effect의 의존성을 안정시키려는 수동 메모이제이션은 탈출구로 계속 쓸 수 있습니다.
- 새 코드는 기본적으로 메모이제이션 없이 쓰고, 필요한 곳에만 추가합니다(자세히는 07편).
- 컴파일러 도입 뒤 흔히 깨지는 패턴은 참조 동일성에 의존하는 Effect, 의존성 배열에서 불안정한 값, 참조 비교로 캐싱하는 조건 로직입니다. 이런 코드는 메모이제이션 결과가 달라질 때 Effect가 과하게 실행되거나 무한 루프가 될 수 있어서 도입 전에 린트와 테스트로 점검합니다.

## 컴파일 결과 확인

컴파일이 실제로 적용됐는지 확인하는 방법은 세 가지입니다.

| 방법 | 확인하는 것 |
|------|-------------|
| React DevTools 배지 | 개발 모드에서 컴포넌트 이름 옆에 `Memo ✨` 배지가 보이면 컴파일됨 |
| 빌드 결과 코드 | 컴파일된 코드에 `react/compiler-runtime`의 캐시 코드가 들어감 |
| Playground | playground.react.dev에서 코드를 붙여 넣어 최적화 결과를 시각적으로 확인 |

```js
// 컴파일 결과의 일부
import { c as _c } from "react/compiler-runtime"
export default function MyApp() {
  const $ = _c(1) // 메모이제이션 슬롯 1개
  let t0
  if ($[0] === Symbol.for("react.memo_cache_sentinel")) {
    t0 = <div>Hello World</div>
    $[0] = t0
  } else {
    t0 = $[0]
  }
  return t0
}
```

- 배지가 없으면 컴파일러가 그 컴포넌트를 건너뛴 것입니다. `logger`의 `CompileError` 이벤트와 ESLint 규칙으로 이유를 확인합니다.
- 문제가 컴파일러 때문인지 가리려면 `"use no memo"`를 붙여 비교합니다. 문제가 사라지면 코드가 Rules of React를 어긴 것입니다.
- 컴파일러 자체의 빌드 오류라면 공식 저장소에 오류 메시지, 문제의 코드, React와 컴파일러 버전을 포함해 보고합니다.

## 핵심 정리

- 컴파일러는 `babel-plugin-react-compiler`로 설치하고(React 17·18은 `react-compiler-runtime`과 `target` 추가), 정확한 버전으로 고정합니다. Babel에서는 플러그인 목록의 맨 앞에 둡니다.
- Vite는 `@vitejs/plugin-react` 버전에 따라 `reactCompilerPreset` 또는 `babel.plugins`로, Next.js는 `reactCompiler` 옵션으로 연결합니다.
- `compilationMode`는 기본 `infer`, 점진적 도입은 `annotation`과 `"use memo"`이며, `"use no memo"`는 모든 모드에서 제외하는 임시 우회입니다.
- 진단은 `panicThreshold`(프로덕션 권장 `none`), `logger`, `eslint-plugin-react-hooks`의 컴파일러 규칙으로 하고, 위반 컴포넌트는 건너뛰어집니다.
- 기존 메모이제이션은 두는 것이 안전하고, 적용 여부는 DevTools의 ✨ 배지, 빌드 결과, Playground로 확인합니다.

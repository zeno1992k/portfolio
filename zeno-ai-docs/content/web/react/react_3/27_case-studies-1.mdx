## 사례를 읽는 틀

모든 사례는 같은 네 질문으로 읽습니다.

1. **상태 모델**: 이 화면이 기억해야 하는 값은 무엇이고, 어느 종류인가.
2. **컴포넌트 트리**: 그 값을 누가 소유하고 누가 읽는가.
3. **데이터 흐름**: 사용자 입력이 어디를 거쳐 화면 변화가 되는가.
4. **경계**: 로딩·에러·빈 상태, 서버·클라이언트, 영향 범위를 어디서 끊는가.

상태 모델은 값마다 먼저 종류를 가려냅니다. 이 분류가 위치를 정합니다(자세히는 기초 12편, 중급 22편).

| 종류 | 예 | 둘 곳 |
|------|----|-------|
| 파생 값 | 필터된 목록, 남은 개수, 합계 | 상태로 두지 않고 렌더 중 계산 |
| 서버 상태 | 목록, 상세, 댓글 | 쿼리 캐시(원본은 서버) |
| URL 상태 | 검색어, 필터, 페이지, 선택 id | 주소 |
| 로컬 UI 상태 | 입력 중인 값, 열림·닫힘 | 가장 가까운 소유 컴포넌트 |
| 전역 클라이언트 상태 | 장바구니, 로그인 사용자, 테마 | Context·Reducer 또는 외부 스토어 |

사례별로 어떤 종류가 주가 되는지 미리 보면 다음과 같습니다.

| 사례 | 주된 상태 | 핵심 판단 |
|------|-----------|-----------|
| Todo | 전역 클라이언트 + 파생 | 무엇을 상태로 두지 않을까 |
| 검색/필터 | URL + 서버 | 입력과 요청을 어떻게 분리할까 |
| Form + Action | 로컬 + 액션 결과 | 검증 책임과 오류 전달 |
| 낙관적 댓글 | 서버 + 낙관적 | 실패 시 되돌림 |
| 대시보드 | 서버 여럿 + URL | 위젯 단위 경계 |
| 포털 시스템 | 오버레이 큐 | 트리와 DOM 위치의 분리 |
| Context + Reducer | 전역 클라이언트 | Context를 나누는 기준 |

## Todo State Model

**요구:** 할 일을 추가·완료 토글·삭제하고, 전체·진행 중·완료로 걸러 보며, 남은 개수를 보여 준다.

**상태 모델:** 상태는 둘뿐입니다.

```js
// state
todos  // [{ id, text, done }]
filter // 'all' | 'active' | 'done'
```

- `visibleTodos`와 `remaining`은 `todos`와 `filter`에서 계산되므로 상태가 아닙니다. 상태로 두면 `todos`를 바꿀 때 함께 갱신하는 것을 잊어 값이 어긋납니다(자세히는 기초 12편).

```js
const visible = todos.filter((t) =>
  filter === 'all' ? true : (filter === 'done') === t.done)
const remaining = todos.filter((t) => !t.done).length
```

- 항목 하나를 편집 중인지(`editing`)는 한 번에 하나만 편집할 수 있다는 규칙이 없으면 `TodoItem`의 로컬 상태입니다. 목록 전체에서 하나만 허용하면 `editingId`로 끌어올립니다.
- 배열로 충분한지는 규모로 정합니다. 수백 개를 id로 자주 찾고 갱신하면 `{ byId, ids }` 형태로 정규화를 고려합니다.

**변경 규칙은 Reducer에 모읍니다.** 갱신 경로가 여럿(추가·토글·삭제·완료 항목 비우기)이고 컴포넌트 여럿이 쓰기 때문입니다(자세히는 중급 02편).

```js
function todosReducer(todos, action) {
  switch (action.type) {
    case 'added': {
      const { id, text } = action
      return [...todos, { id, text, done: false }]
    }
    case 'toggled':
      return todos.map((t) =>
        t.id === action.id ? { ...t, done: !t.done } : t)
    case 'deleted':
      return todos.filter((t) => t.id !== action.id)
    default:
      throw Error('Unknown action')
  }
}
```

- 새 `id`는 Reducer 안이 아니라 이벤트 핸들러에서 만들어 액션에 실어 보냅니다(`crypto.randomUUID()`). Reducer는 순수해야 하는데 난수·시간을 읽으면 같은 입력에 다른 결과가 나옵니다.
- 액션 이름은 `setTodos`가 아니라 일어난 일(`added`, `toggled`)입니다.

**컴포넌트 트리:**

```text
TodoApp                 (todos, filter 소유 / Provider)
├─ AddTodo              (입력 값은 로컬 상태)
├─ TodoList
│  └─ TodoItem          (key = id, editing은 로컬)
└─ Footer
   ├─ RemainingCount    (파생 값 읽기)
   └─ FilterTabs        (filter 읽기와 변경)
```

**데이터 흐름:** 입력 → `dispatch({ type: 'toggled', id })` → Reducer가 새 배열 반환 → `TodoApp` 재렌더 → 파생 값 재계산. `TodoItem`이 깊지 않으면 props로 `onToggle`을 내려 충분하고, 중간 단계가 늘면 Context로 `dispatch`를 내립니다(사례 "Context + Reducer 앱").

**경계와 확장:** 새로고침 후에도 남기려면 `localStorage`에서 초기값을 읽는 지연 초기화(`useReducer`의 세 번째 인자)를 씁니다. 서버에 저장하는 순간 `todos`는 서버 상태가 되어 쿼리 캐시로 옮기고, Reducer에는 `filter`처럼 화면 상태만 남습니다.

**흔한 실수:** `key`를 배열 인덱스로 쓰는 것(삭제·정렬 때 항목의 로컬 상태가 엉킴), `todos`를 직접 변경하는 것, `remaining`을 상태로 중복 저장하는 것입니다.

## 검색/필터 앱

**요구:** 상품 목록을 검색어, 카테고리, 정렬, 페이지로 좁히고, 새로고침·링크 공유에도 같은 결과가 나온다.

**상태 모델:**

| 값 | 종류 | 이유 |
|----|------|------|
| `q`, `category`, `sort`, `page` | URL 상태 | 공유·새로고침·뒤로 가기에 견딤 |
| 입력창에 타이핑 중인 글자 | 로컬 상태 | 타이핑마다 URL을 바꾸지 않음 |
| 검색 결과 | 서버 상태 | 원본은 서버, 쿼리 키가 조건에 대응 |
| 결과 개수, 총 페이지 | 파생 | 응답에서 계산 |

- URL이 원본이고 컴포넌트 상태는 복사본을 두지 않습니다. URL 값을 `useState`에 복사하면 원본이 둘이 되어 뒤로 가기 때 어긋납니다(자세히는 중급 29편).

```tsx
const [params, setParams] = useSearchParams()
const filters = {
  q: params.get('q') ?? '',
  category: params.get('category') ?? 'all',
  page: Number(params.get('page') ?? 1),
}
const { data, isPlaceholderData } = useQuery({
  queryKey: ['products', filters],
  queryFn: () => fetchProducts(filters),
  placeholderData: keepPreviousData,
})
```

- 조건이 쿼리 키에 들어 있으므로 조건이 바뀌면 새 키로 요청하고, 같은 조건이면 캐시를 씁니다. 이전 요청의 응답이 늦게 도착해도 키가 다르면 화면에 섞이지 않습니다.
- `keepPreviousData`는 새 결과가 올 때까지 이전 결과를 보여 줘서 로딩 깜박임을 막고, `isPlaceholderData`로 갱신 중임을 표시합니다.

**컴포넌트 트리:**

```text
SearchPage              (URL 읽기, 쿼리 실행)
├─ SearchBar            (입력 로컬 상태 → 확정 시 URL)
├─ CategoryFilter       (filters.category 읽기, URL 변경)
├─ ResultList
│  └─ ResultItem
└─ Pagination           (page 읽기, 총 페이지는 응답에서)
```

**데이터 흐름:** 입력 → (지연 또는 제출) → `setParams` → URL 변경 → `filters` 재계산 → 쿼리 키 변경 → 요청 또는 캐시 → 결과 렌더. 조건이 바뀌면 `page`를 1로 되돌립니다. 되돌리지 않으면 3페이지에서 카테고리를 바꿨을 때 존재하지 않는 페이지를 요청합니다.

**클라이언트 필터와 서버 필터:** 전체 데이터가 작으면(수백 건 이하) 한 번 받아 렌더 중에 걸러 내고, 크면 조건을 서버에 보냅니다. 클라이언트 필터에서 목록이 커 입력이 버벅이면 입력 값은 즉시 반영하고 목록 계산에는 `useDeferredValue`로 지연된 값을 씁니다(자세히는 중급 10편). 서버 요청은 타이핑마다 보내지 않도록 디바운스하거나 제출 시점에만 보냅니다.

**경계:** 상태를 네 가지로 가르고 분기 순서를 지킵니다. 로딩(처음), 에러(재시도 버튼), 빈 결과("조건에 맞는 상품 없음", 필터 해제 버튼), 정상입니다. 빈 결과와 아직 검색하지 않은 상태는 문구가 달라야 합니다(자세히는 17편).

**흔한 실수:** 응답을 `useEffect`로 `useState`에 복사하는 것, 조건이 바뀌어도 `page`를 유지하는 것, 쿼리 키에서 조건 하나를 빠뜨려 다른 조건의 캐시를 보여 주는 것입니다.

## Form + Action

**요구:** 프로필 수정 폼. 입력을 검증하고, 저장 중에는 버튼을 막고, 서버 오류를 필드 옆에 보여 주며, 성공하면 폼을 비운다.

**상태 모델:**

- 입력 값은 상태로 들고 있지 않습니다. `form`의 `action`에 함수를 주면 제출 시 `FormData`를 받습니다. 값이 필요한 순간은 제출뿐이라 비제어 입력으로 충분합니다(자세히는 중급 06편).
- 상태로 두는 것은 **액션의 결과**입니다. `useActionState`가 액션의 반환값을 상태로 보관하고 진행 여부(`isPending`)를 알려 줍니다(자세히는 중급 07편).

```jsx
function ProfileForm() {
  const [state, action, pending] =
    useActionState(save, init)
  return (
    <form action={action}>
      <input
        name="email"
        defaultValue={state.values.email}
      />
      <p>{state.errors.email}</p>
      <button disabled={pending}>Save</button>
    </form>
  )
}
```

```js
async function save(prev, formData) {
  const values = Object.fromEntries(formData)
  const errors = validate(values) // 필드별 메시지 객체
  if (Object.keys(errors).length) return { errors, values }
  await api.updateProfile(values) // 실패는 throw
  return { errors: {}, values: {} }
}
```

- 액션은 `(이전 상태, FormData)`를 받아 새 상태를 반환합니다. 액션들은 순서대로 실행됩니다.
- 검증 실패는 **throw가 아니라 반환**합니다. 예외는 에러 바운더리로 가는 예기치 못한 실패용이고, 사용자가 고칠 수 있는 입력 오류는 상태입니다.
- 액션이 끝나면 비제어 필드가 초기화됩니다. 그래서 오류 응답에 `values`를 함께 돌려 주고 `defaultValue`로 되돌립니다.

**컴포넌트 트리:**

```text
ProfileForm             (form action, useActionState)
├─ Field × n            (label + input + 오류 문구)
├─ SubmitButton         (useFormStatus로 pending 읽기)
└─ FormMessage          (성공·일반 오류)
```

- `useFormStatus`는 `form` 안쪽의 **자식** 컴포넌트에서만 해당 폼의 상태를 읽습니다. 버튼 컴포넌트를 분리하는 이유입니다. 폼을 렌더하는 같은 컴포넌트에서 호출하면 읽히지 않습니다.

**데이터 흐름:** 제출 → React가 액션을 Transition 안에서 실행 → `isPending` 참 → 검증 → API 호출 → 반환값이 `state`가 됨 → 재렌더로 오류 표시 또는 필드 초기화.

**검증 위치:** 클라이언트 검증은 사용자 편의이고, 신뢰할 수 있는 검증은 서버입니다. 액션이 Server Function이면 같은 검증 함수를 서버에서 실행하며, 인자는 직렬화 가능해야 합니다(자세히는 05편). JavaScript가 로드되기 전에도 제출되는 점진적 향상은 Server Function을 `action`에 직접 줄 때 얻는 이점입니다.

**흔한 실수:** 모든 입력을 제어 컴포넌트로 만들어 폼마다 `useState`를 쌓는 것, 검증 오류를 `throw`하는 것, 오류 응답에 입력 값을 담지 않아 사용자가 쓴 내용이 지워지는 것입니다. 입력이 많고 즉시 검증이 필요한 폼은 React Hook Form 같은 도구가 더 맞습니다(자세히는 16편).

## Optimistic Comment

**요구:** 댓글을 등록하면 서버 응답을 기다리지 않고 목록에 먼저 나타나고, 실패하면 사라지며 오류를 알린다.

**상태 모델:** 낙관적 값은 새 원본이 아니라 **서버 상태 위에 잠시 덮는 층**입니다.

| 값 | 종류 | 수명 |
|----|------|------|
| 확정된 댓글 목록 | 서버 상태 | 서버가 원본 |
| 낙관적 댓글 목록 | 파생(서버 목록 + 대기 중 항목) | 액션이 끝날 때까지 |
| 등록 오류 | 로컬 상태 | 다음 시도까지 |

```jsx
function Comments({ comments, addComment }) {
  const [shown, addOptimistic] = useOptimistic(
    comments,
    (list, text) => [
      ...list,
      { id: 'tmp', text, pending: true },
    ],
  )
  async function action(formData) {
    const text = formData.get('text')
    addOptimistic(text) // 즉시 표시
    await addComment(text) // 저장과 목록 갱신까지 await
  }
  return <form action={action}>{/* shown 렌더 */}</form>
}
```

- `useOptimistic(value, reducer)`는 대기 중인 액션이 없으면 `value`를 그대로 돌려 주고, 액션이 진행 중이면 reducer로 계산한 낙관적 상태를 돌려 줍니다.
- 낙관적 상태는 **Action 안에서만** 갱신할 수 있습니다. `form`의 `action` 함수나 `startTransition` 안입니다. 렌더 중이나 일반 이벤트 핸들러에서 호출하면 안 됩니다.
- 액션이 끝나면 낙관적 상태는 자동으로 실제 `value`로 돌아갑니다. 액션이 에러를 던져도 마찬가지라서 되돌리는 코드를 따로 쓰지 않습니다. 에러 메시지를 보여 주려면 `try`/`catch`로 오류 상태를 따로 저장합니다.
- `pending: true`로 표시해 두면 대기 중인 댓글을 흐리게 그릴 수 있습니다.

**컴포넌트 트리:**

```text
CommentSection          (서버 데이터 소유, 액션 정의)
├─ CommentList
│  └─ CommentItem       (pending이면 흐리게)
└─ CommentForm          (form action, 오류 표시)
```

**데이터 흐름:** 제출 → `addOptimistic`으로 즉시 목록에 추가 → 서버 저장 → **서버 목록 재조회까지 액션 안에서 기다림** → 액션 종료 시 낙관적 층 제거, 확정 목록이 보임. 재조회를 액션 밖에서 하면 낙관적 항목이 사라지고 새 목록이 도착하기 전까지 항목이 잠깐 비는 깜박임이 생깁니다.

**TanStack Query로 할 때:** 선택지가 둘입니다.

| 방식 | 방법 | 맞는 경우 |
|------|------|-----------|
| UI 방식 | `useMutation`의 `variables`로 대기 중인 항목을 렌더 | 낙관적 결과를 보여 줄 곳이 한 군데 |
| 캐시 방식 | `onMutate`에서 이전 캐시를 저장하고 `setQueryData`로 갱신, `onError`에서 되돌림 | 여러 화면이 같은 데이터를 봄 |

캐시 방식은 `onMutate` 처음에 진행 중인 재조회를 취소(`cancelQueries`)하고, 끝나면(`onSettled`) 무효화해 서버 값으로 맞춥니다(자세히는 17편).

**경계:** 서버가 거절할 수 있는 작업(검증이 엄격한 입력, 권한)은 낙관적으로 보여 주면 거짓 성공을 보여 줍니다. 성공 확률이 높고 되돌려도 해가 작은 작업(좋아요, 댓글, 체크)에 씁니다. 결제처럼 되돌릴 수 없는 작업에는 쓰지 않습니다.

**흔한 실수:** 낙관적 임시 `id`를 서버 `id`와 같은 `key`로 쓰지 못해 항목이 교체되며 다시 마운트되는 것(클라이언트가 만든 id를 서버에 보내 그대로 쓰면 피합니다), 실패했는데 사용자에게 알리지 않아 항목이 조용히 사라지는 것입니다.

## Dashboard

**요구:** 매출 요약 카드, 기간별 차트, 최근 주문 표를 한 화면에 보여 주고, 기간을 바꾸면 모두 갱신되며, 일정 간격으로 새로 고친다. 위젯 하나가 실패해도 나머지는 보여야 한다.

**상태 모델:**

- **기간**은 URL 상태입니다. 모든 위젯이 읽는 단 하나의 입력입니다.
- **위젯 데이터**는 위젯마다 독립된 서버 상태(쿼리)입니다. 하나의 거대한 쿼리로 합치지 않습니다. 합치면 가장 느린 위젯이 전체를 막고, 하나의 실패가 전체 실패가 됩니다.
- 합계·증감률 같은 값은 응답에서 계산하는 파생 값입니다.
- 자동 갱신은 상태가 아니라 쿼리 옵션(`refetchInterval`)입니다.

**컴포넌트 트리와 경계:**

```text
DashboardPage           (기간 URL 읽기)
├─ DateRangePicker      (기간 변경)
└─ WidgetGrid
   ├─ [에러 경계 > Suspense] KpiCards
   ├─ [에러 경계 > Suspense] RevenueChart   (lazy)
   └─ [에러 경계 > Suspense] RecentOrders
```

```jsx
<ErrorBoundary fallback={<WidgetError />}>
  <Suspense fallback={<CardSkeleton />}>
    <RevenueChart range={range} />
  </Suspense>
</ErrorBoundary>
```

```tsx
function RevenueChart({ range }) {
  const { data } = useSuspenseQuery(revenueOptions(range))
  return <Chart points={data.points} />
}
```

- 위젯마다 경계를 둡니다. 에러 경계는 그 위젯의 실패를 가두고 재시도 버튼을 제공하고, Suspense는 그 위젯만 스켈레톤으로 대체합니다(자세히는 중급 11편, 13편).
- 쿼리 설정(`queryKey`, `queryFn`)은 `queryOptions`로 한곳에 정의해 위젯과 사전 로딩에서 함께 씁니다.

**데이터 흐름:** 같은 레벨의 위젯들이 각자 요청하므로 요청이 **병렬**로 나갑니다. 부모가 데이터를 받은 뒤에야 자식이 요청하는 구조(워터폴)는 피합니다. 라우트 진입 시 쿼리를 미리 시작(prefetch)하면 렌더 전에 요청이 출발합니다(자세히는 06편).

**기간 변경:** 기간이 바뀌면 모든 위젯의 쿼리 키가 바뀝니다. 그대로 두면 이미 보이던 위젯이 스켈레톤으로 돌아갑니다. 기간 변경을 Transition으로 처리하면 React가 이미 보이는 내용을 fallback으로 되돌리지 않고 새 데이터가 준비될 때까지 기존 화면을 유지합니다(자세히는 중급 09편). 기존 데이터를 유지하는 `keepPreviousData`도 같은 목적입니다.

**성능:** 차트 라이브러리는 무거우므로 `lazy`로 분리해 대시보드 첫 렌더에서 뺍니다(자세히는 26편 "번들 분석", 중급 12편). 자동 갱신은 탭이 보일 때만 의미가 있으므로 간격을 길게 잡고 서버 부하를 고려합니다.

**흔한 실수:** 전체 화면에 Suspense 하나만 둬서 가장 느린 위젯이 모두를 가리는 것, 로딩 플래그를 전역 하나로 관리하는 것, 합계를 상태에 저장해 위젯 간 값이 어긋나는 것입니다.

## Portal System

**요구:** 앱 어디서든 모달, 토스트, 툴팁을 띄운다. 부모의 `overflow: hidden`과 `z-index`에 갇히지 않고, 키보드와 스크린 리더로 쓸 수 있어야 한다.

**포털의 성질:** `createPortal(children, domNode)`는 자식을 부모의 DOM이 아니라 지정한 DOM 노드에 그립니다. DOM 위치만 바뀌고 **React 트리에서는 여전히 렌더한 컴포넌트의 자식**입니다. 그래서 부모의 Context가 그대로 전달되고, 이벤트도 DOM 트리가 아니라 React 트리를 따라 위로 올라갑니다(자세히는 중급 14편).

**상태 모델:** 오버레이 종류마다 상태 소유자가 다릅니다.

| 오버레이 | 상태 | 소유 |
|----------|------|------|
| 모달 | `open` 여부 | 트리거와 가까운 컴포넌트(로컬), 또는 라우트 |
| 툴팁 | 열림 여부, 위치 | 툴팁 컴포넌트 안(로컬) |
| 토스트 | `toasts` 배열 | 앱 전역(Provider나 스토어) |
| `confirm` 같은 명령형 호출 | 대기 중인 요청 | 전역 오버레이 관리자 |

토스트는 어디서든 `toast('저장됨')`처럼 호출하므로 전역 상태가 됩니다. Reducer로 `added`, `dismissed` 액션을 관리하고, 자동 닫힘 타이머는 Effect에서 만들어 정리 함수로 지웁니다.

```jsx
function ToastViewport({ toasts }) {
  return createPortal(
    <div role="status">
      {toasts.map((t) => <Toast key={t.id} {...t} />)}
    </div>,
    document.body,
  )
}
```

**컴포넌트 트리:**

```text
App
├─ ToastProvider        (toasts, add, dismiss)
│  ├─ Routes ... 어디서든 useToast()
│  └─ ToastViewport     → document.body로 포털
└─ Modal (필요한 곳)     → document.body로 포털
```

**데이터 흐름:** 이벤트 핸들러에서 `toast()` 호출 → `dispatch({ type: 'added' })` → `toasts` 갱신 → `ToastViewport`가 새 항목 렌더 → 타이머 만료 시 `dismissed`.

**접근성과 경계:**

- 모달은 열릴 때 포커스를 안으로 옮기고, 열려 있는 동안 포커스가 밖으로 나가지 않게 가두며(포커스 트랩), `Esc`로 닫고, 닫으면 트리거로 포커스를 돌려줍니다. WAI-ARIA의 모달 다이얼로그 패턴을 따릅니다(자세히는 15편, 중급 32편).
- 토스트 영역은 `role="status"` 같은 라이브 영역으로 두어 스크린 리더가 읽게 합니다. 사라지는 시간은 읽을 만큼 충분해야 합니다.
- 포털의 대상 DOM 노드는 이미 존재해야 합니다. 서버 렌더링에는 `document`가 없으므로 포털을 마운트 이후에만 그립니다(자세히는 03편).
- 모달이 여러 개 쌓이면 가장 위의 것만 `Esc`에 반응하도록 스택으로 관리하고, 스크롤 잠금은 한 곳에서만 합니다.

**흔한 실수:** 모달 안의 클릭이 React 트리를 따라 올라가 부모 컴포넌트의 `onClick`을 실행하는 것(DOM에서는 `body` 아래라 무관해 보여도 발생), 포털 없이 `z-index` 숫자만 키우는 것, 토스트에 라이브 영역을 두지 않아 스크린 리더 사용자가 알림을 못 받는 것입니다.

## Context + Reducer 앱

**요구:** 쇼핑몰의 장바구니. 여러 화면(헤더 배지, 상품 목록, 장바구니, 결제)이 같은 장바구니를 읽고 바꾼다. 로그인 사용자와 테마도 전역으로 쓴다.

**상태 모델:**

| 값 | 변경 빈도 | 소유 |
|----|-----------|------|
| 장바구니 항목 | 자주 | `CartProvider`의 Reducer |
| 로그인 사용자 | 드묾 | `AuthProvider` |
| 테마 | 드묾 | `ThemeProvider` |
| 총액, 항목 수 | 파생 | 읽는 쪽에서 계산 |
| 상품 목록 | 서버 상태 | 쿼리 캐시(Context에 넣지 않음) |

**Context를 나누는 기준:**

- **도메인별로** 나눕니다. 장바구니·인증·테마가 한 Context에 섞이면 테마만 바꿔도 장바구니 소비자가 모두 다시 렌더링됩니다.
- **상태와 dispatch를 따로** 둡니다. `dispatch`는 값이 바뀌지 않으므로 쓰기만 하는 컴포넌트(담기 버튼)는 상태가 바뀌어도 재렌더되지 않습니다.

```jsx
const CartContext = createContext(null)
const CartDispatchContext = createContext(null)

export function CartProvider({ children }) {
  const [cart, dispatch] = useReducer(cartReducer, [])
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        {children}
      </CartDispatchContext>
    </CartContext>
  )
}
```

- 읽는 쪽은 Context를 직접 쓰지 않고 `useCart()`, `useCartDispatch()` 커스텀 Hook을 씁니다. Provider 밖에서 호출하면 에러를 던지게 해서 연결 실수를 바로 알립니다.
- Reducer가 **규칙의 집**입니다. 수량의 최소·최대, 중복 담기 시 수량 합산 같은 규칙을 컴포넌트가 아니라 Reducer에 둡니다. 액션은 `item_added`, `quantity_changed`처럼 일어난 일로 이름 짓습니다(자세히는 중급 01편, 02편).

**컴포넌트 트리:**

```text
App
└─ ThemeProvider
   └─ AuthProvider
      └─ CartProvider
         └─ Layout
            ├─ Header → CartBadge   (useCart: 항목 수)
            └─ Routes
               ├─ ProductList → AddButton (useCartDispatch)
               ├─ CartPage            (useCart + dispatch)
               └─ Checkout
```

**데이터 흐름:** `AddButton`의 클릭 → `dispatch({ type: 'item_added', item })` → Reducer → 새 `cart` → `CartContext` 값 변경 → `useCart`를 쓰는 `CartBadge`, `CartPage`만 재렌더(`AddButton`은 `dispatch` Context만 읽어 제외). 로그인한 사용자는 장바구니를 서버에 저장하므로 그때부터 장바구니는 서버 상태가 되고, Context는 화면 상태만 맡습니다.

**한계와 다음 단계:** Context는 값이 바뀌면 그 Context를 읽는 모든 컴포넌트를 다시 렌더링하고, 일부 필드만 구독하는 기능이 없습니다. 갱신이 잦고 소비자가 많거나 필드 단위 구독이 필요하면 외부 스토어(Zustand 등)로 옮깁니다(자세히는 중급 22편, 24편).

**흔한 실수:** 모든 전역 값을 하나의 `AppContext`에 넣는 것, `value`에 렌더마다 새 객체를 만들어 넘기는 것, 총액을 Reducer 상태에 함께 저장해 항목과 어긋나게 하는 것, 서버 데이터를 Context로 감싸 직접 캐시를 만드는 것입니다.

## 핵심 정리

- 설계는 값마다 종류(파생, 서버, URL, 로컬, 전역 클라이언트)를 먼저 가르고 종류에 맞는 위치에 둔다. 계산할 수 있는 값은 상태로 두지 않는다.
- URL이 원본인 값은 상태로 복사하지 않고, 서버 데이터는 쿼리 캐시에서 읽으며, 조건은 쿼리 키로 연결한다.
- 폼은 `FormData`와 `useActionState`의 결과 상태로 다루고, 사용자가 고칠 수 있는 오류는 던지지 않고 반환한다.
- `useOptimistic`은 Action 안에서만 쓰고, 액션이 끝나면 자동으로 되돌아가므로 서버 갱신까지 액션 안에서 기다린다.
- 경계는 위젯·섹션 단위로 끊는다. Suspense와 에러 경계를 나눠 두면 한 곳의 로딩과 실패가 전체로 번지지 않는다.
- 포털은 DOM 위치만 옮기고 React 트리는 그대로이므로 Context와 이벤트 버블링은 트리를 따른다. Context는 도메인별, 상태와 dispatch 별로 나눈다.

## React Library vs Framework

React는 UI를 만드는 라이브러리입니다. 컴포넌트, 상태, 렌더링 모델은 제공하지만 URL 라우팅, 데이터 가져오기 구조, 코드 분할, 서버 렌더링, 빌드와 배포는 정하지 않습니다. 프레임워크는 이 빈자리를 하나의 구조로 채웁니다.

| 영역 | React만 쓸 때 | 프레임워크를 쓸 때 |
|------|---------------|--------------------|
| 라우팅 | 라이브러리를 골라 직접 구성 | 규칙이 내장됨 |
| 데이터 로딩 | `useEffect`나 별도 라이브러리로 직접 구성 | 로더·서버 컴포넌트 등 통합된 방식 |
| 렌더링 | 기본은 클라이언트 렌더링(CSR) | SSR, 정적 생성, 스트리밍을 선택 |
| 코드 분할 | 번들러와 `lazy`로 직접 | 라우트 단위로 자동 |
| 서버 코드 | 별도 백엔드 | 같은 프로젝트에서 서버 코드 작성 |
| 배포 | 정적 파일 | 서버 런타임을 고려 |

- React 공식 문서는 새 앱이나 사이트를 만들 때 프레임워크로 시작하기를 권합니다. 라우팅, 데이터 가져오기, 코드 분할, 서버 렌더링 같은 문제를 직접 풀지 않아도 되고, 미래의 React 기능이 프레임워크를 통해 들어오기 때문입니다.
- 공식 문서가 풀 스택 프레임워크로 소개하는 것은 Next.js(App Router)와 React Router이고, 신생 프레임워크로 TanStack Start와 RedwoodSDK를 소개합니다. Expo는 네이티브 앱용입니다.
- 프레임워크 없이 시작하려면 Vite, Parcel, Rsbuild 같은 빌드 도구에 라우팅(React Router, TanStack Router)과 데이터 가져오기(TanStack Query, SWR) 라이브러리를 직접 골라 조합합니다. 공식 문서는 SSR, 정적 생성, RSC가 필요 없다고 확신할 때 적합하다고 설명합니다.
- 서버 렌더링(01편), Hydration(03편), Server Components(04편), Server Functions(05편)은 React 기능이지만, 번들러와 서버 런타임과의 통합이 필요합니다. 프레임워크가 이 통합을 담당합니다.

선택의 질문은 "프레임워크가 필요한가"가 아니라 "어떤 서버 기능이 필요한가"입니다. 이 문서의 나머지는 세 프레임워크를 같은 항목으로 비교합니다.

## Next.js

Next.js는 풀 스택 React 프레임워크입니다. 이 문서는 문서 버전 16.3.8을 기준으로 합니다. 라우팅·캐싱·배포의 세부는 Next.js 과목에서 다루고, 여기서는 비교에 필요한 특징만 정리합니다.

- App Router가 기본입니다. `app` 폴더의 파일 구조가 라우트가 되고, 컴포넌트는 기본적으로 Server Component입니다.
- 서버 렌더링, 정적 생성, 스트리밍, 캐싱, 이미지·폰트 최적화, 메타데이터, Route Handler(서버 API), Proxy(요청 가로채기)를 프레임워크가 제공합니다.
- 데이터 변경은 Server Function(Server Action)으로 합니다.
- 프레임워크 고유의 규칙(캐싱 동작, 파일 규약)을 따로 학습해야 합니다.
- 서버 코드와 클라이언트 코드의 경계가 가장 깊게 통합돼 있어서 비밀값 노출과 권한 검증을 주의해야 합니다(자세히는 23편).

## React Router 프레임워크 모드

React Router는 가장 널리 쓰이는 React 라우팅 라이브러리이고, 공식 문서 기준 현재 버전은 8.4입니다. 세 가지 모드로 쓸 수 있고 모드가 올라갈수록 기능이 늘어납니다.

| 모드 | 제공 | 번들러·서버 |
|------|------|-------------|
| 선언형(Declarative) | URL과 컴포넌트 연결, `Link`, `useNavigate` | 직접 구성 |
| 데이터(Data) | 위에 더해 `loader`, `action`, `useFetcher`, 진행 상태 | 직접 구성 |
| 프레임워크(Framework) | 위에 더해 Vite 플러그인, 타입 안전 route module, 코드 분할, SSR·SPA·사전 렌더링 | Vite 플러그인이 구성 |

프레임워크 모드가 이 문서의 비교 대상입니다. 공식 문서는 새 프로젝트나 Next.js와 비교하는 경우, SSR·SPA·정적 생성 사이에서 유연성이 필요한 경우에 프레임워크 모드를 권합니다.

- 기본 서버 렌더링이 켜져 있고 `react-router.config.ts`로 바꿉니다(아래 "서버 렌더링").
- 라우트 파일(route module)이 `loader`, `action`, 컴포넌트를 함께 내보내는 구조입니다.
- 기존 선언형·데이터 모드 앱에서 단계적으로 올릴 수 있는 것이 장점입니다.
- RSC는 실험 기능입니다(아래 "Server Components").

## TanStack Start 계열

TanStack Start는 TanStack Router 위에 만든 풀 스택 React 프레임워크입니다. 빌드 도구는 Vite 또는 Rsbuild입니다. 공식 문서는 Release Candidate 단계로 기능이 완성됐고 API가 안정적이라고 보지만 버그가 없다고 보장하지는 않는다고 설명합니다. 도입 전에 현재 상태를 문서에서 다시 확인합니다.

- 계열의 중심은 TanStack Router입니다. 경로와 파라미터, 검색 파라미터(search params)까지 전부 타입이 추론됩니다. 검색 파라미터를 파싱·직렬화되는 상태로 다루는 것이 특징입니다.
- TanStack Router 단독으로도 쓸 수 있고(SPA), Start를 얹으면 서버 렌더링, 스트리밍, 서버 함수가 추가됩니다.
- 데이터 로딩은 라우트 로더와 내장 캐시 계층이 있고, TanStack Query나 SWR과 함께 쓸 수 있습니다.
- 실행 모델이 다릅니다. 모든 코드가 기본적으로 서버와 클라이언트 양쪽에서 실행되는 동형(isomorphic)입니다. 서버에서만 실행하려면 `createServerFn`을 명시합니다. Next.js와 반대로 서버 전용이 기본이 아닙니다.
- 배포는 Nitro 같은 서버 어댑터를 거쳐 Cloudflare Workers, Netlify, Railway, Vercel, Node.js, Bun으로 갑니다.
- RSC는 실험 기능입니다.

**흔한 실수:** 로더가 서버에서만 실행된다고 가정하는 것입니다. TanStack Start의 로더는 최초 요청은 서버에서, 이후 이동은 클라이언트에서 실행되므로 비밀값을 로더 안에서 직접 쓰면 안 됩니다. 문서도 모듈 최상단에서 `process.env`를 읽으면 비밀값이 클라이언트 번들로 새어 나갈 수 있다고 경고합니다.

## Routing

라우팅은 URL을 화면(컴포넌트)에 연결하는 구조입니다. 세 프레임워크 모두 중첩 라우트, 동적 파라미터, 레이아웃을 지원하고 라우트 단위로 코드를 분할합니다. 차이는 라우트를 정의하는 방식입니다.

| 항목 | Next.js | React Router 프레임워크 모드 | TanStack Start |
|------|---------|------------------------------|----------------|
| 정의 방식 | `app` 폴더의 폴더·파일 구조 | `routes.ts` 설정 파일 | 파일 기반(코드 기반도 가능). 설정은 Vite 플러그인이나 CLI가 생성 |
| 페이지 | `page.tsx` | 라우트 모듈의 기본 내보내기 | 라우트 파일에서 `createFileRoute`로 정의 |
| 레이아웃 | `layout.tsx` | 중첩 라우트의 부모 | 중첩 라우트와 상속되는 route context |
| 동적 세그먼트 | `[slug]` 폴더 | `:pid` 같은 경로 파라미터 | 경로 파라미터가 타입으로 추론됨 |
| 타입 안전 | 경로 파라미터 타입 헬퍼(`PageProps`) 생성 | `href`와 `loaderData` 타입 자동 생성 | 경로와 검색 파라미터까지 추론 |

```tsx
// Next.js: app/blog/[slug]/page.tsx
export default async function Page({ params }) {
  const { slug } = await params
  return <h1>{slug}</h1>
}
```

```ts
// React Router: app/routes.ts
import { index, route } from '@react-router/dev/routes'

export default [
  index('./home.tsx'),
  route('products/:pid', './product.tsx'),
]
```

- Next.js의 `params`는 Promise이므로 `await`해서 씁니다.
- Next.js의 레이아웃은 이동할 때 상태를 유지하고 다시 렌더링되지 않습니다.
- TanStack Router의 특징은 검색 파라미터를 타입이 있는 상태로 다루는 것입니다. 필터·정렬·페이지 번호를 URL에 두는 화면에 유리합니다.
- 클라이언트 라우팅 기본기는 중급 과목의 라우팅을 따릅니다.

## Data Loading

데이터를 언제, 어디서 가져오는지가 프레임워크의 핵심 차이입니다. 목표는 렌더링 전에 필요한 데이터를 병렬로 시작해 요청 워터폴을 줄이는 것입니다(자세히는 06편).

| 프레임워크 | 서버에서 가져오는 방법 | 클라이언트에서 가져오는 방법 |
|------------|------------------------|------------------------------|
| Next.js | 서버 컴포넌트를 `async`로 만들고 `fetch`나 DB를 직접 호출 | `use`로 서버에서 넘긴 Promise를 읽거나 SWR·React Query |
| React Router | 라우트의 `loader` | `clientLoader` |
| TanStack Start | 라우트 `loader`(서버 함수 호출) | 같은 로더가 이동 때 클라이언트에서 실행, TanStack Query |

```ts
// React Router: 서버에서 실행되고 클라이언트 번들에서 제거됨
export async function loader({ params }: Route.LoaderArgs) {
  return fakeDb.getProduct(params.pid)
}

export default function Product(p: Route.ComponentProps) {
  return <h1>{p.loaderData.name}</h1>
}
```

- React Router의 `loader`는 최초 로드와 클라이언트 이동 모두에서 서버 실행입니다. 클라이언트 번들에서 제거되므로 서버 전용 API를 쓸 수 있습니다.
- `loader`와 `clientLoader`를 함께 쓰면 최초 로드는 서버, 이후 이동은 클라이언트에서 데이터를 가져옵니다. `clientLoader.hydrate = true`로 Hydration 때 클라이언트 로더를 강제로 실행합니다.
- React Router는 Promise, Map, Set, Date를 자동으로 직렬화하고, Promise를 반환해 Suspense와 `Await`로 스트리밍할 수 있습니다.
- Next.js에서 `fetch`는 기본적으로 캐시되지 않고 렌더링을 막으므로 `Suspense`로 감싸 스트리밍하거나 캐시 지시자로 캐시합니다. 같은 렌더링 트리의 동일한 `fetch` 요청은 자동으로 중복 제거되고, DB 호출은 `React.cache`로 감쌉니다.
- 순서가 있는 요청은 워터폴이 됩니다. 서로 독립된 요청은 먼저 시작한 뒤 `Promise.all`로 기다리거나, 미리 불러오기(preload)로 시작을 앞당깁니다.
- 서버 상태 라이브러리(TanStack Query)는 프레임워크의 로더와 경쟁하지 않고 클라이언트의 캐시, 재검증, 낙관적 갱신을 맡는 조합이 흔합니다(자세히는 17편).

## Server Rendering

세 프레임워크 모두 서버 렌더링(SSR), 스트리밍, Hydration을 제공합니다(자세히는 01편, 02편, 03편). 차이는 렌더링 방식을 고르는 방법입니다.

| 항목 | Next.js | React Router 프레임워크 모드 | TanStack Start |
|------|---------|------------------------------|----------------|
| 기본 | 서버 렌더링, 정적 생성, 스트리밍을 라우트별로 | SSR이 기본(`ssr: true`) | 전체 문서 SSR과 스트리밍 |
| 선택 방법 | 라우트가 사용하는 API(쿠키, `searchParams` 등)로 동적 렌더링 여부 결정 | `react-router.config.ts`의 `ssr`와 `prerender` | 서버 렌더링 중심 |
| SPA | 정적 내보내기·SPA 가이드 | `ssr: false` | 확인한 문서에서는 다루지 않음 |
| 정적 사전 렌더링 | 정적 생성 | `prerender()`에 URL 목록 반환 | 확인한 문서에서는 다루지 않음 |

```ts
// React Router: react-router.config.ts
export default {
  ssr: true,
  async prerender() {
    return ['/', '/about']
  },
} satisfies Config
```

- React Router는 SSR, SPA(`ssr: false`), 정적 사전 렌더링을 설정으로 고르고 조합할 수 있습니다. SSR을 켠 채 일부 경로만 빌드 때 렌더링하는 것도 가능합니다. 사전 렌더링은 빌드 때 로더를 실행합니다.
- Next.js의 `searchParams`나 쿠키 같은 요청 시점 API를 쓰면 그 페이지는 동적 렌더링이 됩니다.
- 봇과 크롤러에게는 Next.js가 스트리밍하지 않고 완전히 렌더링된 페이지를 보냅니다.
- 서버 렌더링이 필요한 이유는 SEO와 첫 화면 속도이고, 대가는 서버 운영과 Hydration 오류 가능성입니다.

## Server Components

Server Components(자세히는 04편)는 서버에서만 실행되는 컴포넌트입니다. 프레임워크별 지원 상태가 가장 크게 갈리는 부분입니다.

| 프레임워크 | RSC 지원 |
|------------|----------|
| Next.js | App Router의 기본. 컴포넌트가 기본적으로 Server Component이고 `'use client'`로 경계를 정함 |
| React Router | 실험적(unstable). 문서가 마이너·패치 릴리스에서도 깨지는 변경이 있을 수 있다고 경고 |
| TanStack Start | 실험적 기능 |

- Next.js는 서버 컴포넌트에서 DB와 비밀값에 직접 접근하고, 클라이언트 컴포넌트는 브라우저와 같은 보안 가정으로 취급해야 합니다(자세히는 23편).
- React Router의 일반 프레임워크 모드는 RSC 없이 `loader`와 `clientLoader`로 서버·클라이언트 데이터를 나눕니다. RSC 프레임워크 모드는 별도 템플릿으로 시험할 수 있지만 프로덕션에는 충분한 검증 없이 권하지 않는다고 문서가 말합니다.
- RSC가 필수가 아니면 로더 기반 프레임워크로도 SSR과 스트리밍을 모두 얻습니다. RSC의 이점은 클라이언트 번들 감소와 서버 데이터를 컴포넌트에 바로 연결하는 구조입니다.
- RSC는 번들러와 프레임워크 통합이 필요해서, RSC를 쓰려면 프레임워크를 써야 한다는 결론으로 이어집니다.

## Server Functions

Server Functions(자세히는 05편)는 클라이언트에서 호출하는 서버 함수입니다. 세 프레임워크는 방식이 다릅니다.

| 프레임워크 | 방식 |
|------------|------|
| Next.js | `'use server'`로 만드는 Server Function(Server Action). 폼 `action`과 `useActionState`에 연결 |
| React Router | 라우트의 `action`과 `Form`·`useFetcher`가 기본. RSC 모드에서는 `'use server'` 함수도 지원(실험적) |
| TanStack Start | `createServerFn()`. `method`를 `GET`(기본)이나 `POST`로 지정하고 `handler`에 서버 로직 작성 |

```ts
// TanStack Start
export const getData = createServerFn().handler(
  async () => ({ message: 'Hello from server!' }),
)
```

- TanStack Start의 서버 함수는 빌드 때 클라이언트 번들에서 구현이 RPC 호출 스텁으로 바뀝니다. 서버 코드는 브라우저에 가지 않고, 클라이언트 호출은 자동으로 `fetch` 요청이 됩니다. 로더와 컴포넌트에서 모두 호출할 수 있습니다.
- 어떤 방식이든 공개 엔드포인트입니다. React Router 문서도 Server Function은 공개 엔드포인트이므로 접근 제어를 직접 해야 한다고 경고합니다. 인자 검증, 인증, 인가는 함수 안에서 합니다(자세히는 23편).
- 폼 중심의 변경은 React Router의 `action` 모델이 단순하고, 컴포넌트에 가까운 서버 호출은 Next.js의 Server Function과 TanStack의 `createServerFn`이 가깝습니다.
- 서버 함수의 반환값과 인자는 직렬화되는 값이어야 합니다.

## Build와 Deployment

프레임워크마다 빌드 결과물과 배포 대상이 다릅니다. 서버 렌더링을 쓰면 정적 호스팅만으로는 안 되고 서버 런타임이 필요합니다.

| 항목 | Next.js | React Router 프레임워크 모드 | TanStack Start |
|------|---------|------------------------------|----------------|
| 빌드 도구 | Next.js 자체 빌드 | Vite | Vite 또는 Rsbuild |
| 빌드 산출물 | 서버와 정적 자산 | `build/client`, `build/server` | Nitro 등 어댑터별 |
| Node 서버 | `next start`, 모든 기능 지원 | 기본 템플릿 또는 커스텀 서버(Express) | Nitro 빌드 결과를 Node로 실행 |
| 컨테이너 | Docker, 모든 기능 지원 | 공식 템플릿(Docker) | Node.js·Docker |
| 정적 호스팅 | 정적 내보내기(기능 제한) | SPA 모드나 사전 렌더링 결과 | 확인한 문서에서는 다루지 않음 |
| 플랫폼 | Vercel, Bun 검증된 어댑터, Cloudflare·Netlify·AWS Amplify 등은 자체 통합 | Vercel, Cloudflare, Netlify 등 | Cloudflare Workers, Netlify, Railway, Vercel, Bun |

- Next.js는 배포 형태에 따라 지원하는 기능이 다릅니다. Node 서버와 Docker는 전체 기능을, 정적 내보내기는 서버가 필요한 기능을 지원하지 않습니다. 어댑터 API로 각 플랫폼이 빌드를 맞춥니다.
- React Router는 서버 렌더링이 있는 풀 스택 호스팅과, SPA를 정적으로 올리는 정적 호스팅 두 가지로 나뉩니다.
- 서버 렌더링 프레임워크를 서버리스·엣지에 올릴 때는 실행 환경의 제약(런타임 API, 실행 시간)을 확인합니다.
- CI/CD, 해시 파일명과 캐시, 환경 분리, 정적 호스팅 구성은 26편에서 다룹니다.
- 2025년 12월의 RSC 취약점은 RSC를 지원하는 프레임워크(공식 발표가 나열한 Next.js, React Router, Waku, Vite RSC 플러그인 등)에 영향을 줬습니다. 프레임워크를 쓰면 프레임워크의 패치를 추적하는 운영 비용이 따릅니다(자세히는 23편).

## 프레임워크 선택 기준표

세 프레임워크와 프레임워크 없는 Vite SPA를 같은 기준으로 비교합니다. 정답은 요구사항에 달려 있습니다.

| 기준 | Next.js | React Router 프레임워크 모드 | TanStack Start | Vite SPA |
|------|---------|------------------------------|----------------|----------|
| SEO·첫 화면 | 서버 렌더링 가능 | SSR 가능 | SSR 가능 | CSR 위주 |
| RSC | 기본 지원 | 실험적 | 실험적 | 지원 안 함 |
| 서버 로직 통합 | Server Function, Route Handler | `loader`, `action` | `createServerFn` | 별도 백엔드 |
| 라우팅 타입 | 경로 파라미터 타입 헬퍼 생성 | `href`, `loaderData` 타입 생성 | 경로와 검색 파라미터 추론 | 라우터에 따라 다름 |
| 단계적 도입 | 해당 구조 없음 | 선언형, 데이터, 프레임워크 모드 순으로 확장 | 해당 구조 없음 | 해당 없음 |
| 배포 | 서버 필요(정적 내보내기는 기능 제한) | SSR은 서버, SPA는 정적 | 서버 어댑터 | 정적 호스팅 |
| 공식 문서 상태 | 문서 버전 16.3.8 | 문서 버전 8.4 | Release Candidate | 해당 없음 |

판단 순서는 다음과 같습니다.

1. 검색 노출이나 첫 화면 속도가 요구사항인가. 그렇다면 서버 렌더링 프레임워크입니다.
2. 서버 컴포넌트로 클라이언트 번들을 줄이고 싶은가. 그렇다면 현재로서는 Next.js가 기본 지원합니다.
3. 팀이 이미 React Router를 쓰는가. 그렇다면 프레임워크 모드로 단계적으로 올릴 수 있습니다.
4. 타입 안전 라우팅과 URL 상태가 핵심인가. TanStack 계열을 검토합니다.
5. 채용이 목적인가. React 프론트엔드 채용 공고에 Next.js 경험이 요건으로 자주 나오므로 학습 목적이라면 Next.js를 먼저 익히는 편이 유리합니다.

**흔한 실수:** 기능 목록만 보고 고르는 것입니다. 팀의 숙련도, 호스팅 제약, 장기 유지 보수와 패치 추적 능력이 실제 비용을 결정합니다.

## Vite 기반 SPA를 유지하는 경우

프레임워크가 항상 정답은 아닙니다. 공식 문서도 프레임워크 없이 시작하는 것이 맞는 경우를 인정합니다. 다음 조건이면 Vite 기반 SPA가 합리적입니다.

- 로그인 뒤에서만 쓰는 내부 도구나 관리자 화면이라 SEO가 필요 없습니다.
- 백엔드 API가 이미 별도로 있고, 프론트엔드는 정적 파일을 올리는 배포로 충분합니다.
- 정적 호스팅(S3와 CloudFront 등)만 가능하거나 서버 운영 비용을 피해야 합니다.
- 팀에 SSR·RSC 운영 경험이 없고 일정이 짧아 학습 비용을 줄여야 합니다.
- 이미 운영 중인 SPA가 안정적이고 프레임워크 마이그레이션의 이득이 비용보다 작습니다.

SPA를 유지하더라도 선택지는 있습니다.

- 라우팅은 React Router나 TanStack Router, 서버 상태는 TanStack Query를 직접 고릅니다.
- 같은 코드를 프레임워크로 옮길 수 있게, 라우트 단위로 코드를 분할하고 데이터 가져오기를 라우트 경계에 모아 둡니다.
- 프레임워크 중에도 SPA 출력이 가능합니다. React Router 프레임워크 모드의 `ssr: false`, Next.js의 정적 내보내기(SPA 가이드)입니다. 처음에는 SPA로 시작하고 나중에 서버 기능을 켜는 경로입니다.
- 서버 기능이 필요해지는 신호는 SEO 요구, 첫 화면의 로딩 지연, 클라이언트 번들의 비대화, 서버에서 처리해야 하는 비밀값이나 데이터 접근입니다.

SPA는 서버 런타임이 없으므로 2025년 12월의 RSC 취약점 같은 서버 측 공격 면이 없다는 점도 선택 요인입니다. 단, 서버 API가 있다면 그 쪽 보안은 별도로 필요합니다(자세히는 23편).

## 핵심 정리

- React는 UI 라이브러리이고, 라우팅·데이터 로딩·서버 렌더링·빌드·배포는 프레임워크가 채웁니다. React 공식 문서는 새 앱에 프레임워크로 시작하기를 권합니다.
- Next.js는 RSC를 기본으로 제공하는 풀 스택 프레임워크이고, React Router 프레임워크 모드는 `loader`·`action` 기반이며 RSC는 실험적입니다. TanStack Start는 타입 안전 라우팅과 `createServerFn`이 중심이고 문서 기준 RC 단계입니다.
- 라우팅은 폴더 구조(Next.js), `routes.ts`(React Router), 타입 추론 파일 라우트(TanStack)로 정의하고, 데이터 로딩은 async 서버 컴포넌트, `loader`/`clientLoader`, 동형 로더로 갈립니다.
- 렌더링 방식은 Next.js가 라우트가 쓰는 API로, React Router가 `ssr`·`prerender` 설정으로 고릅니다. 서버 함수는 모두 공개 엔드포인트라서 함수 안에서 인증·인가·검증을 합니다.
- 서버 렌더링 프레임워크는 서버 런타임이 필요하고 패치 추적 비용이 따릅니다. SEO·RSC·서버 통합이 필요 없으면 Vite SPA가 합리적이며, 프레임워크의 SPA 모드로 시작해 나중에 서버 기능을 켤 수도 있습니다.

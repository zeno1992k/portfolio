## Login

Login은 이메일(또는 아이디)과 비밀번호를 받아 서버에 보내고 결과를 보여 주는 폼입니다. 입력이 두 개뿐이라 Form Action과 `useActionState`만으로 충분합니다.

```tsx
const [state, action, pending] = useActionState(login, null)

<form action={action}>
  <input name="email" autoComplete="username" />
  <input name="password" type="password"
    autoComplete="current-password" />
  <button disabled={pending}>로그인</button>
  {state?.error && <p role="alert">{state.error}</p>}
</form>
```

- `autoComplete`에 `username`과 `current-password`를 지정하면 브라우저와 비밀번호 관리자가 입력을 채울 수 있습니다. MDN은 이것이 WCAG 2.2의 입력 목적 식별 기준(1.3.5)을 충족하는 방법이라고도 설명합니다.
- 비밀번호 입력은 `type="password"`를 씁니다. 로그인 필드에 `autoComplete="off"`를 써도 비밀번호 관리자는 동작할 수 있다고 MDN이 설명하므로 의미가 없습니다.
- 실패 메시지는 "이메일 또는 비밀번호가 올바르지 않습니다"처럼 어느 쪽이 틀렸는지 알려 주지 않는 문구가 일반적입니다. 계정 존재 여부를 노출하지 않으려는 선택입니다.
- 오류는 `role="alert"` 영역에 두어 스크린 리더가 바로 알리게 합니다.
- 공식 문서는 Action이 성공하면 비제어 필드가 초기화된다고 설명합니다. 실패 시 입력값을 남기려면 서버가 돌려준 상태에 값을 담아 `defaultValue`로 다시 채웁니다.
- 토큰을 어디에 저장하는지, 세션 쿠키와 JWT의 차이는 보안 편의 주제입니다(자세히는 23편).

**흔한 실수:** 로그인 중에 버튼을 막지 않아 같은 요청이 두 번 나가는 것입니다(아래 Pending Button).

## Signup

Signup은 새 계정을 만드는 폼으로, Login보다 검증이 많습니다. 이메일 형식, 비밀번호 규칙, 비밀번호 확인, 약관 동의, 이메일 중복 확인이 들어갑니다.

- 비밀번호 필드에는 `autoComplete="new-password"`를 지정해 관리자가 새 비밀번호를 제안하게 합니다. 이름 필드에는 `given-name`, `family-name`, 이메일에는 `email`을 씁니다.
- 필드 하나로 끝나지 않는 규칙(비밀번호와 확인 일치)은 스키마 단계에서 검증합니다. Zod는 교차 필드 검증용으로 `refine`과 `superRefine`을 제공합니다.

```ts
const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  confirm: z.string(),
}).refine((v) => v.password === v.confirm, {
  message: '비밀번호가 일치하지 않습니다',
  path: ['confirm'],
})
```

- 이메일 중복은 서버만 알 수 있습니다. 클라이언트 검증을 통과해도 제출 결과로 필드 오류를 돌려받을 수 있어야 합니다(아래 Server Error).
- 가입 직후 흐름(이메일 인증, 자동 로그인)은 폼이 아니라 인증 설계의 영역입니다(자세히는 18편).
- 비밀번호 규칙은 입력 칸 근처에 미리 보여 줍니다. 제출 후에야 알려 주면 반복하게 됩니다.

## Profile

Profile은 서버에 저장된 값을 보여 주고 수정하는 폼입니다. 신규 입력과 달리 서버의 현재 값이 초기값입니다.

- 초기값은 `defaultValue`(비제어) 또는 폼 라이브러리의 `defaultValues`로 넣습니다. 데이터가 도착한 뒤에 초기값을 넣어야 하므로 로딩이 끝난 뒤에 폼을 렌더링합니다.
- 서버에서 다시 가져온 값으로 폼을 갱신해야 하면 폼의 `key`를 바꿔 새로 시작합니다(자세히는 기초 13편).
- 수정한 필드만 보내는 방식도 있습니다. React Hook Form은 어느 필드가 변경됐는지 `dirtyFields`로 알려 줍니다.
- 프로필 사진은 파일 업로드 패턴을 따릅니다(자세히는 15편). 이메일처럼 민감한 값의 변경은 재인증이나 확인 메일을 거치게 합니다.
- 저장 후에는 성공을 알리고, 화면의 값이 서버 값과 같도록 쿼리를 무효화하거나 응답으로 갱신합니다(자세히는 중급 28편).

## Settings

Settings는 여러 설정을 모아 둔 화면입니다. 저장 방식이 두 가지라서 먼저 정해야 합니다.

| 방식 | 적합한 항목 | 특징 |
|------|-------------|------|
| 즉시 저장 | 켜고 끄는 스위치, 단일 선택 | 바꾸는 즉시 요청. 저장 버튼이 없음. 낙관적 업데이트가 어울림 |
| 묶음 저장 | 여러 필드가 서로 얽힌 설정 | 저장 버튼을 눌러 한 번에 요청. 저장 안 한 변경 경고가 필요 |

- 한 화면에서 섞어 쓰지 않는 것이 좋습니다. 사용자가 저장해야 하는지 알 수 없게 됩니다.
- 설정은 섹션별로 독립된 폼으로 나눕니다. 한 섹션의 오류나 저장이 다른 섹션에 영향을 주지 않습니다.
- 즉시 저장 스위치는 실패하면 원래 값으로 되돌리고 알립니다. `useOptimistic`은 Action이 실패하면 낙관적 상태를 마지막 실제 값으로 되돌립니다(아래 Optimistic Submit).
- 스위치와 라디오는 라벨과 연결합니다. 현재 값이 화면과 보조 기술에 모두 드러나야 합니다.
- 위험한 설정(계정 삭제)은 분리하고 AlertDialog로 확인을 받습니다(자세히는 15편).

## Dynamic Field

Dynamic Field는 다른 입력 값에 따라 나타나거나 사라지는 필드입니다. "배송 방법: 택배/방문 수령"에 따라 주소 입력을 보이고 감추는 식입니다.

```tsx
const [method, setMethod] = useState('delivery')

{method === 'delivery' && (
  <input name="address" required />
)}
```

- 렌더링하지 않은 입력은 `FormData`에 들어가지 않습니다. 감춘 필드의 값을 제출에 포함할지는 의도적으로 정해야 합니다.
- 감춘 필드에 `required`가 남아 있으면 제출이 막힙니다. 조건부 렌더링으로 제거하거나 스키마를 조건별로 나눕니다.
- 조건에 따라 검증 규칙이 달라지면 스키마가 판별 유니온처럼 값에 따라 다른 규칙을 갖게 합니다.
- 감췄다가 다시 보일 때 이전 입력을 유지할지 지울지를 정합니다. 비제어 입력은 언마운트되면 값이 사라집니다. 상태로 들고 있으면 유지됩니다(자세히는 기초 13편).
- 나타나는 필드로 포커스를 옮겨야 하는지, 변화를 스크린 리더에 알려야 하는지도 점검합니다.

## Array Field

Array Field는 같은 모양의 입력 묶음을 사용자가 추가·삭제하는 필드입니다. 연락처 여러 개, 주문 항목 여러 개가 예입니다.

React Hook Form의 `useFieldArray`는 이를 위한 Hook이며 `fields`와 조작 메서드를 돌려줍니다.

```tsx
const { fields, append, remove } = useFieldArray({
  control, name: 'phones',
})

{fields.map((f, i) => (
  <div key={f.id}>
    <input {...register(`phones.${i}.value`)} />
    <button type="button" onClick={() => remove(i)}>
      삭제
    </button>
  </div>
))}
<button type="button" onClick={() => append({ value: '' })}>
  추가
</button>
```

공식 문서가 정한 규칙은 다음과 같습니다.

- `key`는 인덱스가 아니라 `field.id`를 씁니다. 인덱스를 쓰면 삭제와 정렬에서 입력이 어긋납니다(자세히는 기초 07편).
- 배열 원소는 객체여야 합니다. `{ phones: [{ value: 'a' }] }`는 되고 `{ phones: ['a'] }`는 안 됩니다.
- `append`와 `prepend`에는 빈 객체가 아니라 완전한 기본값을 넘깁니다.
- 한 핸들러에서 변경 메서드를 연달아 호출하지 않습니다.
- `shouldUnregister: true`는 `useFieldArray`와 함께 쓰지 않습니다.
- 메서드는 `append`, `prepend`, `insert`, `remove`, `swap`, `move`, `update`, `replace`입니다.

`type="button"`을 빠뜨리면 추가·삭제 버튼이 폼을 제출시킵니다. 최소·최대 개수는 `rules`나 스키마로 제한하고, 삭제 후 포커스가 사라지지 않게 이전 항목이나 추가 버튼으로 옮깁니다.

## Multi-step Form

Multi-step Form은 긴 입력을 여러 단계로 나눠 한 단계씩 받는 폼입니다. 설계의 핵심은 상태를 어디에 두느냐입니다.

- 모든 단계의 값을 한 곳(부모의 폼 상태 하나 또는 스토어)에 모읍니다. 단계 컴포넌트가 각자 상태를 가지면 이전 단계로 돌아갈 때 값이 사라집니다.
- 단계별 스키마로 현재 단계의 필드만 검증하고, 통과해야 다음으로 넘어갑니다. 마지막 제출 직전에 전체 스키마로 다시 검증합니다.
- 현재 단계는 단순한 숫자나 이름 하나로 둡니다. 단계 이동 규칙이 복잡하면 상태 머신으로 모델링합니다(자세히는 13편).
- 단계를 URL에 담으면 새로고침과 뒤로 가기가 자연스럽습니다. 단, 입력값은 URL이 아니라 상태에 둡니다(자세히는 중급 29편).
- 진행 표시에는 `aria-current="step"`을 현재 단계에 둡니다. MDN이 정의한 값이며, 하나의 요소에만 표시합니다.
- 이전 단계로 돌아가도 입력이 유지되어야 하고, 어느 단계에 오류가 있는지 요약에서 알 수 있어야 합니다.
- 최종 제출은 한 번의 요청으로 보내는 방식과 단계마다 임시 저장하는 방식이 있습니다. 중간 이탈이 잦은 폼은 임시 저장이 낫습니다.

## Validation

Validation은 입력이 규칙에 맞는지 확인하는 일이며, 한 곳에서 끝나지 않고 세 층으로 나뉩니다.

| 층 | 수단 | 역할 |
|----|------|------|
| 브라우저 | `required`, `type`, `pattern`, `min`, `max` | 즉각적이고 단순한 규칙 |
| 클라이언트 스키마 | Zod와 폼 라이브러리의 resolver | 필드 간 규칙, 상세한 메시지, 타입 추론 |
| 서버 | 서버 코드의 재검증 | 신뢰할 수 있는 유일한 검증(자세히는 05편, 23편) |

- 클라이언트 검증은 사용자 경험을 위한 것이고 보안이 아닙니다. 서버는 항상 다시 검증합니다.
- Zod는 `parse`가 실패 시 예외를 던지고 `safeParse`가 결과 객체를 돌려줍니다. 사용자 입력은 예외 없이 처리할 수 있는 `safeParse`가 흔합니다. Zod는 TypeScript 5.5 이상과 `strict` 모드를 요구합니다.
- 검증 시점은 제출 시, 포커스를 잃을 때, 입력할 때 중에서 정합니다. 입력 중에 바로 오류를 보이면 사용자가 아직 입력 중인데 오류가 뜹니다. 처음에는 포커스를 잃을 때나 제출 시에 검증하고, 오류가 난 뒤에는 입력할 때마다 다시 확인하는 조합이 흔합니다(자세히는 중급 31편).
- 오류 메시지는 접근성 연결이 필요합니다. 입력에 `aria-invalid`를 두고 `aria-describedby`로 메시지 요소를 가리킵니다. 요소 ID는 `useId`로 만듭니다(자세히는 중급 05편).

```tsx
const id = useId()
<input aria-invalid={!!error} aria-describedby={id} />
{error && <p id={id}>{error}</p>}
```

- 제출 시 오류가 있으면 첫 오류 필드로 포커스를 옮깁니다. React Hook Form의 `setError`에는 `shouldFocus` 옵션이 있습니다.
- 메시지는 무엇이 틀렸고 어떻게 고치는지 알려 줍니다. "잘못된 입력" 대신 "8자 이상 입력하세요"입니다.

## Server Error

Server Error는 클라이언트 검증을 통과했지만 서버가 거절한 결과입니다. 두 가지로 나눕니다.

| 종류 | 예 | 처리 |
|------|----|------|
| 필드 오류 | 이미 가입된 이메일 | 해당 필드 옆에 표시 |
| 폼 전체 오류 | 네트워크 실패, 서버 오류, 권한 없음 | 폼 상단 등에 표시 |

- `useActionState`에서는 Action이 오류를 예외로 던지지 않고 오류 상태를 반환하게 합니다. 공식 문서는 예외 대신 오류 상태를 반환해야 대기 중인 Action이 건너뛰어지지 않는다고 안내합니다. 예외는 가장 가까운 Error Boundary로 전파됩니다(자세히는 중급 13편).
- 예상할 수 있는 오류(검증 실패, 중복)는 반환하고, 예상하지 못한 오류(버그)만 던져 Error Boundary가 맡게 합니다.
- React Hook Form은 `setError`로 서버의 필드 오류를 폼에 넣습니다. 필드마다 한 번씩 호출하며, 서버 응답을 반복하며 설정합니다. `root` 키로 폼 전체 오류도 설정할 수 있고(v7.43.0부터), `root.serverError` 형태의 오류는 제출 후 유지되지 않습니다.

```ts
const res = await save(values)
if (res.fieldErrors) {
  for (const [name, message] of Object.entries(
    res.fieldErrors,
  )) {
    setError(name, { type: 'server', message })
  }
} else if (res.error) {
  setError('root.serverError', { message: res.error })
}
```

- 서버가 필드 이름과 메시지를 구조화해서 돌려주는 계약을 정합니다. 문자열 하나만 주면 필드에 연결할 수 없습니다.
- 인증 만료(401)는 오류 메시지가 아니라 로그인 이동으로 처리하는 경우가 많습니다.
- 재시도할 수 있는 오류는 입력을 그대로 둔 채 다시 제출할 수 있게 합니다.

## Optimistic Submit

Optimistic Submit은 서버 응답을 기다리지 않고 성공했다고 가정해 화면을 먼저 바꾸는 방식입니다. `useOptimistic`이 이를 위한 Hook이며 Action 안에서 호출해야 합니다(자세히는 중급 08편).

```tsx
const [optimistic, addOptimistic] = useOptimistic(
  comments,
  (list, text: string) => [
    ...list, { text, sending: true },
  ],
)

async function submit(formData: FormData) {
  addOptimistic(formData.get('text') as string)
  await postComment(formData)
}
```

공식 문서가 설명하는 동작은 다음과 같습니다.

- Action이 끝나면 낙관적 상태는 부모가 가진 실제 값으로 자동으로 돌아갑니다. 성공하면 서버 값이 이미 반영되어 있어 두 값이 한 번의 렌더링에서 맞춰집니다.
- Action이 실패하면 낙관적 상태는 마지막으로 받은 실제 값으로 되돌아갑니다. 화면에는 변경 전 상태가 보입니다.
- Action이나 `startTransition` 밖에서 호출하면 경고가 나고 바로 되돌아갑니다.

- 전송 중인 항목은 `sending` 표시로 구분해 흐리게 보여 줍니다. 실패했을 때 되돌아가는 것만으로는 사용자가 이유를 모르므로 오류 메시지와 재시도 수단을 함께 제공합니다.
- 낙관적 제출에 어울리는 것은 실패 확률이 낮고 되돌려도 피해가 작은 동작(댓글, 좋아요)입니다. 결제나 삭제처럼 결과가 중요한 동작은 서버 확인을 기다립니다.
- 서버 상태 도구를 쓰면 캐시를 직접 바꾸고 롤백하는 낙관적 업데이트도 가능합니다(자세히는 중급 28편).

## Pending Button

Pending Button은 제출 중임을 알리고 중복 제출을 막는 버튼입니다. 상태를 얻는 방법이 두 가지입니다.

| 방법 | 위치 | 비고 |
|------|------|------|
| `useActionState`의 세 번째 값 `isPending` | 폼을 가진 컴포넌트 | Action을 직접 연결한 경우 |
| `useFormStatus`의 `pending` | 폼 안쪽의 자식 컴포넌트 | 폼을 렌더링하는 같은 컴포넌트에서는 동작하지 않음 |

```tsx
function SubmitButton() {
  const { pending } = useFormStatus()
  return (
    <button disabled={pending}>
      {pending ? '저장 중...' : '저장'}
    </button>
  )
}
```

- `useFormStatus`는 반드시 `form` 안에 렌더링된 자식 컴포넌트에서 호출해야 하며, 같은 컴포넌트가 `form`을 렌더링하면 `pending`이 항상 `false`입니다. 그래서 버튼을 별도 컴포넌트로 뺍니다. 이 Hook은 `pending` 외에 `data`, `method`, `action`도 돌려줍니다.
- 제출 중에는 버튼의 라벨과 폭이 크게 바뀌어 레이아웃이 흔들리지 않게 합니다.
- `disabled` 버튼은 포커스를 잃습니다. React Aria의 Button은 `isPending` 상태에서 포커스를 유지하고 보조 기술에 대기 상태를 알리는 방식을 제공합니다(공식 문서). 직접 만든다면 `aria-disabled`와 클릭 무시를 조합하는 방법이 있습니다.
- 버튼만 막아도 Enter 키 제출이 남는 경우가 있으므로, Action이 진행 중일 때 새 제출을 무시하는 처리가 안전합니다. `useActionState`는 여러 호출을 순서대로 처리합니다.
- 오래 걸리는 작업은 단순한 문구 변경으로 끝내지 않고 진행 상황을 보여 줍니다.

## Unsaved Changes

Unsaved Changes는 저장하지 않은 변경이 있을 때 이탈하려는 사용자에게 확인을 받는 패턴입니다. 막아야 할 이탈이 두 종류입니다.

| 이탈 | 방법 |
|------|------|
| 앱 안의 이동(링크, 뒤로 가기) | 라우터의 이탈 차단 |
| 탭 닫기, 새로고침, 외부 주소 이동 | `beforeunload` 이벤트 |

먼저 "변경이 있는가"를 알아야 합니다. React Hook Form의 `formState.isDirty`는 사용자가 입력을 바꾸면 `true`가 되며, `useForm`에 `defaultValues`를 넘겨야 제대로 동작합니다. `formState`는 Proxy라서 렌더링 중에 읽어야 구독됩니다.

```tsx
const { formState } = useForm({ defaultValues })
const { isDirty } = formState

useEffect(() => {
  if (!isDirty) return
  const h = (e: BeforeUnloadEvent) => e.preventDefault()
  window.addEventListener('beforeunload', h)
  return () => window.removeEventListener('beforeunload', h)
}, [isDirty])
```

MDN이 설명하는 `beforeunload`의 제약은 다음과 같습니다.

- `preventDefault()`로 확인 창을 띄웁니다. 현대 브라우저는 사용자 지정 메시지를 보여 주지 않고 브라우저가 정한 문구만 보여 줍니다.
- 사용자가 페이지와 한 번이라도 상호작용해야 창이 뜹니다.
- 항상 등록해 두지 않고 변경이 있을 때만 추가하고 없으면 제거합니다. 위 코드가 이 방식입니다. 리스너가 있으면 Firefox는 페이지를 bfcache에 넣지 못합니다.
- 모바일에서는 앱 전환이나 브라우저 종료 때 발생하지 않을 수 있습니다. 자동 저장에는 `visibilitychange`가 더 믿을 만합니다.

앱 안의 이동은 React Router의 `useBlocker`로 막습니다. 인자로 불리언 또는 함수를 받고, `blocker.state`는 `unblocked`, `blocked`, `proceeding` 중 하나입니다. 차단되면 `blocker.proceed()`로 계속하거나 `blocker.reset()`으로 남습니다. 프레임워크 모드와 데이터 모드에서 쓸 수 있고 선언적 모드에서는 쓸 수 없으며, 새로고침이나 다른 출처로의 이동은 처리하지 못합니다.

```tsx
const blocker = useBlocker(isDirty)
// blocker.state === 'blocked' 이면 확인 Dialog를 연다
// 확인: blocker.proceed(), 취소: blocker.reset()
```

- 저장에 성공하면 폼을 초기화(`reset`)해 `isDirty`를 `false`로 되돌린 뒤 이동합니다. 순서가 틀리면 저장 직후 이동에서 경고가 뜹니다.
- 확인창은 "저장", "저장하지 않고 나가기", "취소"처럼 선택지가 분명해야 합니다.

## 핵심 정리

- Login·Signup은 `autoComplete`를 정확히 지정해 비밀번호 관리자와 맞추고, 비밀번호 확인 같은 교차 규칙은 Zod 스키마로, 중복 같은 규칙은 서버 오류로 처리합니다.
- Profile은 서버 값을 초기값으로 삼고, Settings는 즉시 저장과 묶음 저장 중 하나를 화면 단위로 정합니다.
- Dynamic Field는 렌더링하지 않은 입력이 `FormData`에서 빠진다는 점을, Array Field는 `field.id`를 key로 쓰는 규칙을 지킵니다.
- Multi-step Form은 모든 단계의 값을 한 곳에 모으고 단계별로 검증합니다.
- 검증은 브라우저·클라이언트 스키마·서버 세 층이고 서버가 최종이며, 서버 오류는 필드 오류와 폼 전체 오류로 나눠 반환합니다.
- `useOptimistic`은 Action 안에서 쓰고 실패하면 실제 값으로 돌아가며, `useFormStatus`는 `form` 안쪽 자식에서만 동작합니다.
- 저장 안 한 변경은 `isDirty`로 감지하고, 앱 안 이동은 라우터 차단으로, 탭 닫기는 변경이 있을 때만 등록한 `beforeunload`로 막습니다.

## Server Function

Server Function은 서버에서 실행되는 비동기 함수를 클라이언트 컴포넌트가 호출할 수 있게 한 기능입니다. 클라이언트에는 함수 본문이 아니라 서버 함수를 가리키는 참조만 전달됩니다. 호출하면 React가 서버로 요청을 보내고, 서버에서 실행된 결과가 돌아옵니다.

- 2024년 9월부터 공식 문서의 용어는 Server Functions입니다. 이전에는 Server Actions라고 불렀습니다.
- `action` prop이나 `startTransition` 같은 Action 안에서 쓰이는 Server Function을 Server Action이라고 부릅니다.
- React 19에서 Server Functions는 안정(stable)이고 마이너 버전 사이에 깨지지 않습니다. 번들러·프레임워크가 쓰는 하부 API는 semver를 따르지 않으므로 직접 구현하는 쪽은 React 버전을 고정하거나 Canary를 써야 합니다.
- 실제로는 Next.js, React Router 등 RSC를 지원하는 프레임워크가 번들러 연동을 해 줍니다(자세히는 24편).

```js
// 클라이언트가 받는 것은 이런 참조 객체다
{ $$typeof: Symbol.for('react.server.reference'),
  $$id: 'createNoteAction' }
```

Server Function은 데이터를 읽는 용도가 아니라 변경하는 용도로 설계되었습니다. 호출은 보통 한 번에 하나씩 처리되고 반환값은 캐시되지 않습니다. 읽기는 서버 컴포넌트의 데이터 패칭이 맡습니다(자세히는 06편).

## use server

`'use server'`는 함수를 Server Function으로 표시하는 지시어입니다. 두 위치에 쓸 수 있습니다.

```js
// 1. 함수 본문 맨 앞: 서버 컴포넌트 안에서만
async function EmptyNote() {
  async function createNote() {
    'use server'
    await db.notes.create()
  }
  return <Button onClick={createNote} />
}
```

```js
// 2. 파일 맨 위: 이 파일의 export 전부가 Server Function
'use server'

export async function createNote() {
  await db.notes.create()
}
```

- 지시어는 함수 본문이나 모듈의 맨 위, 다른 코드보다 앞에 와야 합니다. 주석만 앞에 올 수 있습니다.
- 따옴표는 작은따옴표나 큰따옴표만 됩니다. 백틱은 안 됩니다.
- `async` 함수에만 쓸 수 있습니다.
- 클라이언트 코드에서 import하려면 파일 맨 위 형태(모듈 수준)로 써야 합니다. 서버 컴포넌트 안에 정의한 함수는 서버 컴포넌트가 props로 내려 줄 수 있습니다.

**흔한 실수:** `'use server'`를 서버 컴포넌트를 표시하는 지시어로 착각하는 것입니다. 서버 컴포넌트는 지시어가 없는 기본값이고, `'use client'`가 클라이언트 경계를 표시합니다(자세히는 04편). `'use server'`는 서버에서 호출될 함수에만 씁니다.

## Client에서 호출

클라이언트 컴포넌트는 Server Function을 일반 함수처럼 import해서 호출합니다. 호출은 네트워크 요청이므로 항상 비동기이고 결과는 Promise로 받습니다.

```js
'use client'
import { updateName } from './actions'
import { useTransition } from 'react'

function UpdateName({ name }) {
  const [isPending, startTransition] = useTransition()
  const save = () => {
    startTransition(async () => {
      const { error } = await updateName(name)
      // error가 있으면 화면에 표시한다
    })
  }
  return <button onClick={save} disabled={isPending} />
}
```

- 폼 밖에서 호출할 때는 Transition 안에서 호출하는 것이 규칙입니다. 그래야 `isPending`을 얻고 UI가 막히지 않습니다(자세히는 중급 09편).
- 서버 컴포넌트에서 props로 받은 Server Function도 같은 방식으로 호출합니다.
- 호출마다 서버 왕복이 생깁니다. 실패하거나 느릴 수 있으므로 pending과 에러를 UI에서 처리해야 합니다.

## Form Action

`form`의 `action`에 함수를 넘기면 제출 시 그 함수가 `FormData`를 받아 실행됩니다. Server Function을 넘기면 서버에서 실행됩니다.

```js
// 서버 컴포넌트
async function addToCart(formData) {
  'use server'
  const id = formData.get('productId')
  await updateCart(id)
}

<form action={addToCart}>
  <input type="hidden" name="productId" value={id} />
  <button type="submit">담기</button>
</form>
```

- `action`에 함수를 넘기면 `method`와 관계없이 HTTP 메서드는 POST입니다.
- 함수는 Transition 안에서 실행되고, 성공하면 비제어 필드가 자동으로 리셋됩니다. `e.preventDefault()`는 필요 없습니다.
- 서버 컴포넌트에서 만든 폼은 JavaScript가 로드되기 전에도 제출됩니다(점진적 향상, progressive enhancement). 이 동작이 클라이언트 이벤트 핸들러 방식과 다른 점입니다.
- 인자를 추가로 넘기려면 `bind`를 씁니다.

```js
async function addToCart(productId, formData) {
  'use server'
  await updateCart(productId)
}
const bound = addToCart.bind(null, productId)
// <form action={bound}>
```

`useActionState`는 Action의 반환값을 상태로 받고 pending을 알려 줍니다(자세히는 중급 07편). Server Function과 함께 쓸 때 요점만 정리합니다.

```js
'use client'
import { useActionState } from 'react'
import { updateName } from './actions'

function Form() {
  const [state, run, isPending] = useActionState(
    updateName, { error: null }, '/name/update',
  )
  return <form action={run}>{/* state.error 표시 */}</form>
}
```

- 서버 쪽 `updateName`은 `(이전 상태, formData)`를 받는 형태여야 합니다.
- 세 번째 인자 permalink는 JavaScript가 로드되기 전에 제출됐을 때 브라우저가 이동할 URL입니다. 상호작용이 가능해지면 효과가 없고, 목적지 페이지에 같은 폼 컴포넌트가 있어야 합니다.
- 초기 상태와 `action`에 넘기는 값은 직렬화 가능해야 합니다.
- 하이드레이션 전에 입력해 제출한 내용도 `useActionState`가 재생해 줍니다.
- 19.3 발표 글에는 React가 Server Action 뒤에 폼을 자동 리셋할 때 `onReset`이 실행된다는 변경이 포함돼 있습니다.

## Mutation

Mutation은 서버의 데이터를 바꾸는 작업이고 Server Function의 주된 용도입니다. 생성·수정·삭제를 Server Function에서 처리하고, 끝난 뒤 화면을 새 데이터로 갱신하는 것까지가 한 흐름입니다.

```js
'use server'
import { revalidatePath } from 'next/cache'

export async function deleteNote(id) {
  await db.notes.delete(id)
  revalidatePath('/notes') // Next.js API
}
```

- 캐시 갱신과 리다이렉트 API(`revalidatePath`, `redirect` 등)는 React가 아니라 프레임워크가 제공합니다. 위 예시는 Next.js 기준입니다.
- 한 Action이 끝나기 전에 같은 `useActionState`로 여러 번 호출하면 호출 순서대로 대기열에 쌓여 하나씩 실행됩니다.
- Server Function은 호출 한 번이 서버 왕복 한 번입니다. 여러 번 호출해도 병렬로 처리된다고 가정하면 안 됩니다.
- 낙관적 업데이트를 합치려면 `useOptimistic`을 씁니다(자세히는 16편, 17편).

## Serializable Arguments

클라이언트에서 서버로 넘기는 인자는 직렬화(serialize)되어 네트워크로 전송됩니다. 직렬화할 수 있는 값만 인자가 될 수 있습니다.

| 분류 | 허용되는 값 |
|------|-------------|
| 원시 값 | string, number, bigint, boolean, undefined, null |
| 심벌 | `Symbol.for`로 전역 등록한 것만 |
| 이터러블 | String, Array, Map, Set, TypedArray, ArrayBuffer(안의 값도 직렬화 가능해야 함) |
| 기타 | Date, FormData, 객체 리터럴로 만든 일반 객체, Promise |
| 함수 | Server Function만 |

허용되지 않는 값은 다음과 같습니다.

- React 요소(JSX)
- Server Function이 아닌 일반 함수와 컴포넌트 함수
- 클래스와 클래스 인스턴스(위 내장 타입 제외)
- 프로토타입이 null인 객체
- 전역 등록하지 않은 심벌(`Symbol('x')`)
- 이벤트 객체

```js
await save({ id: 1, at: new Date() }) // ✅
await save({ id: 1, onDone: () => {} }) // ❌ 일반 함수
await save(new Note()) // ❌ 클래스 인스턴스
```

- 인자는 항상 클라이언트가 만든 값이며 신뢰할 수 없습니다. 타입 표기가 `number`여도 실제로 무엇이 올지는 요청을 보낸 쪽이 정합니다(아래 "보안", "입력 검증").
- 폼에서는 `FormData`가 가장 흔한 인자이고, 값은 문자열이거나 파일입니다. 숫자 필드도 문자열로 옵니다.

## Serializable Return

Server Function의 반환값도 직렬화되어 클라이언트로 돌아옵니다. 규칙은 서버 컴포넌트가 클라이언트 컴포넌트에 넘기는 props의 직렬화 규칙과 같습니다(자세히는 04편). 위 표의 값에 더해 JSX 요소도 반환할 수 있다는 점이 인자와 다릅니다.

```js
'use server'
export async function getStatus(id) {
  const note = await db.notes.find(id)
  return { ok: true, title: note.title } // ✅ 일반 객체
  // return note // ❌ 클래스 인스턴스이면 실패
}
```

- ORM이 돌려주는 모델 인스턴스, 클래스로 만든 값 객체는 일반 객체로 바꿔서 반환합니다.
- 필요한 필드만 골라 반환합니다. 객체를 통째로 반환하면 클라이언트에 보여서는 안 되는 필드(해시된 비밀번호, 내부 ID)가 함께 전송됩니다.
- 성공·실패를 값으로 표현해 반환하는 패턴이 흔합니다. 예상 가능한 실패는 반환하고, 예상하지 못한 실패는 던집니다(아래 "Server Error").

## 보안

Server Function은 서버에 공개된 HTTP 진입점입니다. 컴포넌트에 연결하지 않았어도, 존재를 아는 누구나 요청을 직접 만들어 보낼 수 있다고 전제해야 합니다.

| 원칙 | 의미 |
|------|------|
| 인자는 신뢰하지 않는다 | 클라이언트가 보낸 값이므로 검증하고 이스케이프한다 |
| 변경 전에 권한을 확인한다 | 로그인한 사용자가 이 작업을 할 권한이 있는지 매번 서버에서 확인한다 |
| 민감 정보를 새지 않게 한다 | 반환값·props로 비밀값이 클라이언트에 가지 않게 한다 |

- 버튼을 숨겼다고 해서 함수가 보호되는 것은 아닙니다. UI에서의 숨김은 편의이고, 보호는 서버 함수 안에서 합니다.
- 파일 맨 위에 `'use server'`를 쓰면 그 파일의 export가 전부 호출 가능한 엔드포인트가 됩니다. 내부용 헬퍼를 같은 파일에서 export하면 의도치 않게 공개됩니다. 일반 헬퍼는 `'use server'`가 없는 별도 파일에 둡니다.
- 비밀값이 클라이언트로 넘어가는 것을 막기 위해 React에는 실험적 taint API(`experimental_taintUniqueValue`, `experimental_taintObjectReference`)가 있습니다. 실험 기능이므로 의존하지 말고 반환값을 직접 걸러내는 것이 기본입니다.
- 비밀값 관리와 번들 유출 경로는 23편에서 이어집니다.

## 인증/인가

인증(authentication)은 요청한 사용자가 누구인지 확인하는 것이고, 인가(authorization)는 그 사용자가 이 작업을 해도 되는지 확인하는 것입니다. Server Function 안에서 둘 다 매번 수행합니다.

```js
'use server'
export async function deleteNote(id) {
  const user = await getSessionUser() // 인증: 누구인가
  if (!user) throw new Error('로그인이 필요합니다')

  const note = await db.notes.find(id)
  if (note?.ownerId !== user.id) {   // 인가: 이 글의 주인인가
    throw new Error('권한이 없습니다')
  }
  await db.notes.delete(id)
}
```

- 사용자 ID를 인자로 받지 않습니다. 인자로 받으면 클라이언트가 다른 사용자의 ID를 보낼 수 있습니다. 세션이나 쿠키처럼 서버가 아는 값에서 꺼냅니다.
- 리소스 ID는 인자로 받더라도 소유자·권한을 서버에서 다시 조회해 확인합니다. 이를 빠뜨리면 다른 사람의 데이터를 바꾸는 취약점(IDOR, 안전하지 않은 직접 객체 참조)이 됩니다.
- 페이지 접근 제어는 변경 요청을 막아 주지 않습니다. 페이지가 로그인 사용자에게만 열려 있어도 Server Function은 별도로 검증해야 합니다.
- 세션 쿠키와 토큰 흐름은 18편, 보안 관점은 23편에서 다룹니다.

**흔한 실수:** 인증은 확인하고 인가를 빠뜨리는 것입니다. 로그인 여부만 보면 로그인한 모든 사용자가 모든 데이터를 바꿀 수 있습니다.

## Server Error

Server Function 안에서 예외가 나면 호출한 쪽에서 실패로 나타납니다. 오류 처리는 예상 가능한 것과 아닌 것으로 나눠 설계합니다.

| 구분 | 예 | 처리 |
|------|----|------|
| 예상 가능한 실패 | 입력 검증 실패, 중복된 이메일 | 오류 정보를 값으로 반환해 상태로 표시 |
| 예상하지 못한 실패 | DB 장애, 코드 버그 | 던져서 Error Boundary가 처리 |

```js
'use server'
export async function signup(prev, formData) {
  const email = formData.get('email')
  if (await db.users.exists(email)) {
    return { error: '이미 가입된 이메일입니다' } // 반환
  }
  await db.users.create(email) // 실패하면 던져짐
  return { error: null }
}
```

- `useActionState`에서 Action이 던지면 대기 중인 Action이 모두 취소되고 가장 가까운 Error Boundary가 처리합니다(자세히는 중급 07편).
- 오류 메시지에 SQL, 파일 경로, 내부 식별자를 넣어 반환하면 클라이언트에 그대로 전달됩니다. 사용자에게 보여 줄 메시지만 반환하고 상세 내용은 서버 로그에 남깁니다.
- 19.3 발표 글의 변경 목록에는 `Error.cause`와 `AggregateError.errors`를 클라이언트로 전달하는 항목이 있습니다. 던지는 오류에 원인을 붙일 때 그 내용이 어디까지 전달되는지 프레임워크 설정과 함께 확인해야 합니다.
- 네트워크 자체가 끊기는 경우는 서버 코드가 실행되지 않으므로 서버 쪽 처리로는 잡을 수 없습니다. 클라이언트에서 호출을 감싸 처리합니다.

## 입력 검증(Zod)

모든 인자는 서버에서 검증합니다. 클라이언트 쪽 검증은 사용성을 위한 것이고, 서버 검증을 대체하지 못합니다. 스키마 라이브러리인 Zod를 쓰면 검증과 타입 추론을 한 번에 할 수 있습니다.

```js
'use server'
import { z } from 'zod'

const Schema = z.object({
  title: z.string().min(1).max(100),
  age: z.coerce.number().int().min(0),
})

export async function create(prev, formData) {
  const data = Object.fromEntries(formData)
  const parsed = Schema.safeParse(data)
  if (!parsed.success) return { error: '입력값을 확인하세요' }
  await db.items.create(parsed.data) // 검증된 값만 사용
  return { error: null }
}
```

- `parse`는 실패하면 `ZodError`를 던지고, `safeParse`는 `success`와 `data` 또는 `error`를 가진 결과 객체를 반환합니다. 예상 가능한 실패이므로 Server Function에서는 `safeParse`가 맞습니다.
- 실패한 이유는 `error.issues`에 경로(`path`)와 메시지로 들어 있습니다. 필드별 메시지를 반환해 폼에 표시합니다.
- `FormData`의 값은 문자열이므로 숫자 필드는 변환이 필요합니다. 위 예시의 `z.coerce.number()`가 문자열을 숫자로 바꾸면서 검증합니다.
- 검증을 통과한 `parsed.data`만 DB에 넘깁니다. 원본 `formData`를 다시 쓰면 검증이 무의미해집니다.
- 스키마는 파일 맨 위에 `'use server'`를 쓴 파일에서 export하지 않습니다. export하면 그것도 Server Function으로 취급됩니다. 상수·스키마는 별도 파일이나 export하지 않는 선언으로 둡니다.
- 클라이언트 폼 검증에 같은 스키마를 재사용할 수 있습니다(자세히는 중급 31편, 16편).

## 2025년 12월 RSC 보안 권고

2025년 12월 React 팀은 서버 컴포넌트의 Server Function 엔드포인트에 대한 심각한 취약점을 공개했습니다. React 공식 블로그의 발표 기준 내용입니다.

| CVE | 유형 | 심각도(CVSS) | 공개 |
|-----|------|--------------|------|
| CVE-2025-55182 | 인증 없는 원격 코드 실행(RCE) | Critical(10.0) | 2025-12-03 |
| CVE-2025-55184 | 서비스 거부(DoS) | High(7.5) | 2025-12-11 |
| CVE-2025-67779 | 서비스 거부(DoS) | High(7.5) | 2025-12-11 |
| CVE-2025-55183 | 소스 코드 노출 | Medium(5.3) | 2025-12-11 |
| CVE-2026-23864 | 서비스 거부(DoS) | High(7.5) | 2026-01-26 |

- CVE-2025-55182는 조작된 HTTP 요청을 Server Function 엔드포인트로 보내면 React가 역직렬화하는 과정에서 서버에서 코드가 실행되는 취약점입니다. 2025년 11월 29일에 Meta 버그 바운티로 접수됐습니다.
- 서비스 거부 취약점은 조작된 요청으로 무한 루프, 서버 정지, 메모리 부족, CPU 과다 사용이 일어납니다.
- 소스 코드 노출은 Server Function이 인자를 문자열로 바꿀 때(명시적이든 암묵적이든) Server Function의 소스 코드가 응답에 새는 문제입니다. 소스에 하드코딩한 비밀값만 노출되고 `process.env.SECRET` 같은 런타임 비밀값은 영향이 없습니다.

영향받는 패키지는 `react-server-dom-webpack`, `react-server-dom-parcel`, `react-server-dom-turbopack` 세 개입니다.

| 취약점 | 영향 버전 | 고친 버전 |
|--------|-----------|-----------|
| CVE-2025-55182 (RCE) | 19.0, 19.1.0, 19.1.1, 19.2.0 | 19.0.1, 19.1.2, 19.2.1 |
| DoS 3건, 소스 노출 1건 | 19.0.0–19.0.3, 19.1.0–19.1.3, 19.2.0–19.2.3 | 19.0.4, 19.1.5, 19.2.4 |

- 19.0.3, 19.1.4, 19.2.3은 불완전한 수정입니다. CVE-2025-55184의 최초 수정이 불완전해 이 버전에도 취약점이 남으므로 19.0.4, 19.1.5, 19.2.4 이상으로 올려야 합니다.
- 영향받는 앱은 서버가 있고 RSC를 지원하는 프레임워크·번들러를 쓰는 앱입니다. 공식 글이 나열한 대상은 Next.js, React Router, Waku, Parcel, Vite RSC 플러그인, Redwood SDK입니다.
- 서버를 쓰지 않는 앱, RSC를 지원하는 프레임워크·번들러를 쓰지 않는 앱(예: Vite 기반 클라이언트 SPA)은 영향받지 않는다고 공식 글에 적혀 있습니다.
- 대응은 프레임워크·번들러를 패치된 버전으로 올리는 것입니다. 각 프레임워크의 패치 버전은 공식 글이 안내하는 프레임워크별 공지를 확인합니다.

이 사건에서 얻는 설계 교훈은 다음과 같습니다.

- Server Function은 곧 공개 엔드포인트이므로, 컴포넌트에서 쓰지 않는 함수라도 노출됩니다. 인증·인가·검증은 어떤 경우에도 함수 안에서 합니다.
- 소스에 비밀값을 하드코딩하지 않고 환경 변수로 분리합니다(자세히는 23편).
- RSC 의존성(프레임워크, `react-server-dom-*`)을 최신 패치 버전으로 유지합니다.

## 핵심 정리

- Server Function은 서버에서 실행되는 async 함수이고, 클라이언트는 참조만 받아 네트워크로 호출합니다. 파일 맨 위 또는 함수 본문 맨 앞의 `'use server'`로 만듭니다.
- 폼 `action`에 넘기면 `FormData`를 받는 POST가 되고, 서버 컴포넌트에서 만든 폼은 JavaScript 로드 전에도 제출됩니다. 폼 밖 호출은 Transition 안에서 합니다.
- 인자와 반환값은 직렬화 가능한 값만 가능하고, 클래스 인스턴스·일반 함수·JSX(인자)는 안 됩니다. 인자는 항상 신뢰할 수 없는 입력입니다.
- Server Function은 공개 엔드포인트이므로 함수마다 인증, 인가, 입력 검증(Zod의 `safeParse`)을 서버에서 수행합니다.
- 예상 가능한 실패는 값으로 반환하고, 예상하지 못한 실패는 던져 Error Boundary가 처리합니다.
- 2025년 12월 권고는 `react-server-dom-*` 19.0–19.2의 RCE·DoS·소스 노출 취약점이며, 19.0.4, 19.1.5, 19.2.4 이상으로 올려야 합니다.

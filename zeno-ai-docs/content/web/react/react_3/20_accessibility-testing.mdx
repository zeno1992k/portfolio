접근성 자체(시맨틱 HTML, ARIA, 키보드, 포커스 관리)는 중급 32편에서, 컴포넌트 테스트와 쿼리 우선순위는 중급 34편·35편에서 다뤘습니다. 이 편은 둘을 합쳐 접근성을 테스트로 검증하는 방법을 다룹니다. 예제는 Vitest, Testing Library, user-event, jest-dom을 쓴다고 가정합니다. jest-dom은 Vitest에서 `@testing-library/jest-dom/vitest`를 setup 파일에서 import해 등록합니다.

```tsx
const user = userEvent.setup() // render 전에 호출
render(<Page />)
await user.click(screen.getByRole('button', { name: '저장' }))
```

- user-event의 모든 상호작용은 비동기이므로 `await`가 필요합니다.
- `fireEvent`는 DOM 이벤트 하나만 발생시키지만 user-event는 포커스 이동, 키보드·입력 이벤트 등 전체 상호작용을 흉내 내고, 숨겨진 요소 클릭이나 비활성 필드 입력은 막습니다. 접근성 테스트는 user-event를 씁니다.

## Role Query

`getByRole`은 접근성 트리에 노출된 요소를 역할(role)로 찾는 쿼리입니다. Testing Library가 권장하는 쿼리 우선순위의 첫 번째입니다. 우선순위는 `getByRole`, `getByLabelText`, `getByPlaceholderText`, `getByText`, `getByDisplayValue`(모두에게 접근 가능한 쿼리), `getByAltText`, `getByTitle`, 마지막으로 `getByTestId`입니다.

```tsx
screen.getByRole('button', { name: '저장' })
screen.getByRole('heading', { level: 2, name: '설정' })
screen.getByRole('checkbox', { name: '알림', checked: true })
screen.getByRole('tab', { name: '개요', selected: true })
```

- `name` 옵션은 접근 가능한 이름으로 거릅니다. 같은 역할의 요소가 여럿일 때 구분합니다. 문자열 외에 정규식도 쓸 수 있습니다.
- `selected`, `checked`, `pressed`, `expanded` 옵션은 `aria-selected`, `aria-checked`, `aria-pressed`, `aria-expanded` 상태로 거릅니다. `level`은 제목 수준입니다.
- `button` 요소는 button 역할을 암묵적으로 갖습니다. 역할은 문자 그대로 일치하며 ARIA의 상속 관계는 적용되지 않습니다.
- `hidden` 옵션의 기본값은 접근성 트리 제외 규칙을 따릅니다. `display: none`이나 `aria-hidden`으로 가려진 요소는 찾지 못하고, `hidden: true`를 주면 포함합니다.
- `getBy`는 없으면 에러, `queryBy`는 `null`, `findBy`는 나타날 때까지 기다립니다(기본 1초). 요소가 없음을 확인할 때는 `queryBy`를 씁니다.

접근성 관점에서 `getByRole`이 실패하는 것 자체가 신호입니다.

```tsx
<div onClick={save}>저장</div>   // ❌ 역할 없음 → getByRole 실패
<button onClick={save}>저장</button> // ✅ button 역할
```

- `div`와 `span`은 역할이 없습니다. 클릭 가능한 `div`는 `getByRole('button')`으로 찾을 수 없고, 같은 이유로 스크린 리더와 키보드 사용자에게도 버튼이 아닙니다.
- 테스트를 `getByTestId`나 클래스 이름으로 쓰면 이 문제를 놓칩니다. 역할로 찾을 수 있는지가 곧 접근성 검증입니다.

**흔한 실수:** `getByRole`이 실패하자 `getByText`나 `getByTestId`로 바꾸는 것입니다. 쿼리를 바꾸기 전에 요소의 역할과 이름이 올바른지를 먼저 고칩니다.

## Accessible Name

접근 가능한 이름(accessible name)은 보조기술이 요소를 부를 때 쓰는 이름입니다. `getByRole`의 `name` 옵션과 jest-dom의 `toHaveAccessibleName`이 이 값을 검사합니다.

이름은 다음 순서로 정해집니다.

1. `aria-labelledby`가 가리키는 요소의 텍스트
2. `aria-label`
3. 호스트 언어의 레이블(`label` 요소, 이미지의 `alt` 등)
4. 내용에서 얻는 이름(역할이 허용하는 경우, 예: 버튼의 텍스트)
5. `title` 속성(다른 것이 없을 때만 쓰는 최후의 수단)

```tsx
<button aria-label="닫기">
  <XIcon aria-hidden="true" />
</button>
```

```tsx
const close = screen.getByRole('button', { name: '닫기' })
expect(close).toHaveAccessibleName('닫기')
```

- 아이콘만 있는 버튼은 내용에서 이름을 얻을 수 없으므로 `aria-label`이 필요합니다. 아이콘은 `aria-hidden`으로 숨겨 이름에 섞이지 않게 합니다.
- 이름은 화면에 보이는 텍스트를 포함해야 합니다(WCAG 2.5.3, A 수준). 음성 제어 사용자가 보이는 글자를 말해 요소를 조작합니다.
- 같은 화면에 이름이 같은 버튼이 여러 개("삭제" 반복)면 `getByRole`이 여러 요소를 찾아 에러가 납니다. 이는 사용자에게도 문제이므로 "할 일 1 삭제"처럼 이름에 맥락을 넣어 고칩니다.
- 이름의 `name` 쿼리는 부분 문자열이 아니라 전체 일치가 기본입니다. 일부만 확인하려면 정규식을 씁니다.
- 설명은 이름과 다릅니다. `aria-describedby`가 가리키는 텍스트는 접근 가능한 설명이며 `toHaveAccessibleDescription`으로 검사합니다.

**흔한 실수:** `aria-label`을 보이는 텍스트와 다르게 쓰는 것입니다. 화면에는 "검색", 이름은 "찾기"이면 음성 제어 사용자가 보이는 글자를 말해도 동작하지 않습니다.

## Keyboard Test

키보드 테스트는 마우스 없이 모든 기능을 쓸 수 있는지를 검증합니다. `user.keyboard()`와 `user.tab()`을 씁니다.

```tsx
await user.tab()                  // 다음 포커스 가능 요소
await user.tab({ shift: true })   // 이전 요소
await user.keyboard('{Enter}')    // 활성화
await user.keyboard('{ArrowDown}')
await user.keyboard('{Shift>}A{/Shift}') // Shift+A
```

- 키 이름은 중괄호로 씁니다(`{Enter}`, `{Escape}`, `{ArrowDown}`). `>`는 키를 누른 채 유지하고 `/`는 뗍니다.
- 탭 순서가 시각 순서와 같은지 확인합니다. 포커스 가능한 요소를 순서대로 따라가며 검증합니다.

```tsx
render(<LoginForm />)
await user.tab()
expect(screen.getByLabelText('이메일')).toHaveFocus()
await user.tab()
expect(screen.getByLabelText('비밀번호')).toHaveFocus()
await user.tab()
expect(
  screen.getByRole('button', { name: '로그인' }),
).toHaveFocus()
```

- 네이티브 `button`은 Enter와 Space를 모두 처리합니다. `div role="button"`은 직접 구현해야 하며, 키보드 테스트가 이 누락을 잡습니다.
- 탭이나 메뉴처럼 하나의 위젯 안에서 방향키로 이동하는 복합 위젯은 위젯 전체가 탭 정지점 하나이고 안쪽은 방향키로 이동합니다(roving tabindex). 테스트도 Tab으로 들어가 방향키로 움직이는 흐름으로 씁니다.
- 키보드 함정(keyboard trap)이 없는지 확인합니다. 포커스가 들어간 뒤 키보드로 빠져나올 수 있어야 합니다. 모달만 의도된 예외이며 Escape로 닫을 수 있어야 합니다.
- jsdom은 브라우저의 포커스 표시 스타일(`:focus-visible`)을 판단하지 못합니다. 포커스 링이 보이는지는 시각 검증이나 E2E로 확인합니다(자세히는 21편).

**흔한 실수:** `fireEvent.keyDown(el, { key: 'Enter' })`만으로 키보드 지원을 검증하는 것입니다. 이 호출은 이벤트 하나만 발생시키므로 요소가 포커스를 받을 수 있는지, Tab으로 도달할 수 있는지를 확인하지 못합니다.

## Focus Test

포커스 테스트는 상호작용 뒤에 포커스가 올바른 곳에 있는지를 검증합니다. `toHaveFocus` 매처나 `document.activeElement`를 씁니다.

```tsx
await user.click(screen.getByRole('button', { name: '편집' }))
expect(
  screen.getByRole('textbox', { name: '제목' }),
).toHaveFocus()
```

검증할 대표 상황은 다음과 같습니다.

| 상황 | 기대하는 포커스 |
|------|-----------------|
| Dialog를 열 때 | Dialog 안의 요소 |
| Dialog를 닫을 때 | 열었던 트리거 |
| 인라인 편집 시작 | 입력 필드 |
| 항목을 삭제할 때 | 다음 항목이나 목록 제목(사라진 요소에 남기지 않음) |
| 제출 실패 | 첫 오류 필드 또는 오류 요약 |
| 라우트 이동 | 새 화면의 제목이나 본문 시작 |

- 포커스를 받으려면 요소가 포커스 가능해야 합니다. 제목처럼 기본으로 포커스를 받지 않는 요소에 프로그래밍으로 포커스를 주려면 `tabIndex={-1}`을 줍니다.
- 요소가 DOM에서 사라지면 포커스는 `body`로 돌아갑니다. 삭제 테스트는 `document.body`에 포커스가 남지 않는지 확인합니다.
- `autoFocus`는 마운트 직후에 포커스를 줍니다. 화면이 바뀔 때마다 쓰지 않고 포커스를 옮길 이유가 있는 곳에만 씁니다.
- 포커스를 옮기는 코드는 Effect나 ref 콜백에서 합니다. 테스트에서는 `await`로 상호작용이 끝난 뒤 확인합니다(자세히는 중급 03편).

**흔한 실수:** 포커스 이동이 일어나는 상호작용 테스트에서 포커스를 단언하지 않는 것입니다. 화면은 맞게 바뀌지만 포커스는 이전 위치에 남아 키보드 사용자가 새 내용에 도달하지 못합니다.

## Form Label

폼 필드는 모두 레이블이 연결되어 있어야 합니다. `getByLabelText`는 레이블로 필드를 찾기 때문에 레이블이 없으면 실패합니다.

```tsx
<label htmlFor={id}>이메일</label>
<input id={id} type="email" />
```

```tsx
const email = screen.getByLabelText('이메일')
expect(email).toBeRequired()
```

- 연결 방법은 세 가지입니다. `label`의 `htmlFor`와 `input`의 `id` 일치, `label` 안에 `input`을 넣는 방식, `aria-labelledby`입니다. React에서 `id`는 `useId`로 만들어 중복과 서버 불일치를 피합니다(자세히는 중급 05편).
- `placeholder`는 레이블이 아닙니다. 입력을 시작하면 사라지고 이름으로 쓰이는 신뢰도도 낮습니다. `getByPlaceholderText`로만 찾아지는 필드는 레이블이 없는 것입니다.
- 오류 메시지는 `aria-describedby`로 필드와 연결하고, 상태는 `aria-invalid`로 표시합니다. 테스트에서 둘을 함께 확인합니다.

```tsx
await user.type(email, 'x')
await user.tab()
expect(email).toBeInvalid()
expect(email).toHaveAccessibleDescription('올바른 이메일이 아닙니다')
```

- `toBeInvalid`는 요소가 유효하지 않은지, `toBeRequired`는 필수인지 검사합니다.
- 그룹(라디오, 체크박스 묶음)은 `fieldset`과 `legend`로 묶어 그룹 이름을 줍니다. `getByRole('group', { name: '배송 방법' })`으로 검증합니다.
- 제출 오류가 생겼을 때 사용자에게 알려지는지는 `getByRole('alert')`로 확인합니다. 폼 설계는 16편을 참고합니다.

**흔한 실수:** 입력 필드를 `getByRole('textbox')`로만 찾고 이름을 확인하지 않는 것입니다. 필드가 여러 개면 구분이 안 되고, 레이블이 빠져 있어도 테스트가 통과합니다. 항상 `name`을 함께 씁니다.

## Dialog Test

모달 Dialog는 접근성 요건이 많아 테스트할 가치가 큽니다. WAI-ARIA 패턴의 요건을 테스트 항목으로 옮깁니다.

| 요건 | 검증 |
|------|------|
| `role="dialog"`와 이름 | `getByRole('dialog', { name })` |
| 열릴 때 포커스가 안쪽으로 이동 | 활성 요소가 Dialog 안에 있음 |
| Tab과 Shift+Tab이 안에서 순환 | 마지막에서 Tab이면 첫 요소 |
| Escape로 닫힘 | 닫힌 뒤 Dialog가 사라짐 |
| 닫으면 열었던 요소로 포커스 복귀 | 트리거가 `toHaveFocus` |
| 배경과의 상호작용 차단 | 배경 요소를 `queryByRole`로 못 찾음 |

```tsx
const trigger = screen.getByRole('button', { name: '삭제' })
await user.click(trigger)
const dialog = screen.getByRole('dialog', { name: '삭제 확인' })
expect(dialog).toContainElement(
  document.activeElement as HTMLElement,
)
await user.keyboard('{Escape}')
expect(screen.queryByRole('dialog')).toBeNull()
expect(trigger).toHaveFocus()
```

- 모달 Dialog에는 `aria-modal="true"`와 이름(`aria-labelledby`로 제목을 가리키거나 `aria-label`)이 필요합니다. 배경의 상호작용을 막고 시각적으로도 가릴 때 `aria-modal`을 씁니다.
- 네이티브 `dialog` 요소를 `showModal()`로 열면 브라우저가 포커스 이동, 배경 비활성화(`inert`), Escape 닫기, 포커스 복귀를 처리합니다. 직접 만든 Dialog는 이를 직접 구현하므로 테스트가 더 중요합니다.
- jsdom은 브라우저 동작을 완전히 구현하지 않습니다. 네이티브 `dialog`의 포커스와 `inert` 동작은 실제 브라우저(E2E)에서 확인합니다(자세히는 21편).
- Portal로 렌더되는 Dialog는 `screen`으로 찾습니다. `document.body` 아래에 붙으므로 `render`가 돌려주는 `container` 안에서는 찾을 수 없습니다(자세히는 중급 14편).
- 포커스를 가두는 방식은 Headless 라이브러리가 구현합니다. 그 라이브러리를 쓰더라도 우리 앱에서의 조합(트리거 연결, 닫을 때 포커스 복귀)은 테스트합니다(자세히는 13편, 15편).

**흔한 실수:** Dialog가 열렸는지만 확인하고 포커스는 확인하지 않는 것입니다. 시각적으로는 열려 있지만 포커스가 뒤쪽 화면에 남아 키보드 사용자가 Dialog에 도달하지 못합니다.

## Menu Test

메뉴 버튼은 버튼이 메뉴를 여는 패턴입니다. 일반 내비게이션 링크 목록이 아니라 운영체제 메뉴처럼 동작하는 위젯에 씁니다. 역할과 상태, 키보드 동작을 테스트합니다.

역할과 상태는 다음과 같습니다.

- 버튼에 `aria-haspopup`("menu" 또는 "true")과 `aria-expanded`(열림 true, 닫힘 false)가 있다.
- 메뉴 컨테이너는 `role="menu"`, 항목은 `menuitem`(또는 `menuitemcheckbox`, `menuitemradio`)이다.

키보드 동작은 다음과 같습니다.

| 위치 | 키 | 동작 |
|------|----|------|
| 버튼 | Enter, Space | 메뉴를 열고 첫 항목에 포커스 |
| 버튼 | Down Arrow(선택) | 열고 첫 항목에 포커스 |
| 버튼 | Up Arrow(선택) | 열고 마지막 항목에 포커스 |
| 메뉴 | Down, Up Arrow | 다음, 이전 항목으로 이동 |
| 메뉴 | Home, End | 첫, 마지막 항목 |
| 메뉴 | Enter | 항목 실행 후 메뉴 닫기 |
| 메뉴 | Escape | 닫고 버튼으로 포커스 복귀 |
| 메뉴 | Tab | 메뉴를 벗어남 |
| 메뉴 | 문자 키(선택) | 그 글자로 시작하는 다음 항목 |

```tsx
const button = screen.getByRole('button', { name: '더보기' })
expect(button).toHaveAttribute('aria-expanded', 'false')
await user.click(button)
const items = screen.getAllByRole('menuitem')
expect(items[0]).toHaveFocus()
await user.keyboard('{ArrowDown}')
expect(items[1]).toHaveFocus()
await user.keyboard('{Escape}')
expect(button).toHaveFocus()
```

- 선택으로 표시된 키 동작은 구현이 정한 것을 따라 테스트합니다. 어느 쪽이든 문서화된 동작을 고정합니다.
- 방향키로 끝에서 계속 누를 때 순환할지는 구현에 따라 다릅니다. 순환하지 않으면 Home과 End를 제공해야 합니다.
- 사이트 내비게이션에는 `menu` 역할을 쓰지 않고 `nav`와 링크 목록을 씁니다. 역할이 잘못되면 보조기술이 다르게 동작합니다.

**흔한 실수:** 드롭다운을 `ul`과 `li`로 만들고 `role="menu"`를 빠뜨린 채 방향키만 구현하는 것입니다. 마우스와 키보드 테스트는 통과하지만 `getAllByRole('menuitem')`이 실패하며, 스크린 리더는 메뉴로 인식하지 못합니다.

## axe

axe는 접근성 규칙 엔진(axe-core)입니다. DOM을 검사해 위반(violations), 통과(passes), 수동 확인이 필요한 항목(incomplete)으로 나눠 돌려줍니다. 자체 문서는 평균 57퍼센트의 WCAG 문제를 자동으로 찾는다고 하고, 오탐은 없는 것을 목표로 합니다.

```ts
import axe from 'axe-core'

it('접근성 위반이 없다', async () => {
  const { container } = render(<ProfileForm />)
  const results = await axe.run(container)
  expect(results.violations).toEqual([])
})
```

- Jest 환경에서는 `jest-axe`가 `axe(container)`와 `toHaveNoViolations` 매처를 제공합니다. 어느 쪽이든 결과의 `violations`가 비어 있는지를 검사하는 것입니다.
- 규칙은 WCAG 수준·버전별 태그(`wcag2a`, `wcag2aa` 등)와 모범 사례로 나뉩니다. 검사할 태그를 `runOnly`로 제한할 수 있습니다.
- 위반이 나오면 `results.violations`의 각 항목에 규칙 ID, 영향 요소, 설명이 담깁니다. 단언 실패 메시지가 읽기 어려우면 요약해서 출력합니다.
- 색 대비(`color-contrast`) 규칙은 jsdom에서 동작하지 않습니다. 대비는 실제 브라우저에서 검사합니다.
- E2E에서는 `@axe-core/playwright`의 `AxeBuilder`로 실제 페이지를 검사합니다. `withTags()`로 기준을 정하고, `exclude()`로 영역을 빼고, `disableRules()`로 규칙을 끌 수 있습니다(자세히는 21편).
- 컴포넌트 단위에서는 페이지 수준 규칙(제목 구조, 랜드마크 중복 등)이 의미 없는 위반을 만들 수 있습니다. 규칙을 조정해 컴포넌트에 맞는 것만 봅니다.
- axe가 통과해도 접근성이 보장되는 것은 아닙니다. 레이블 문구가 적절한지, 키보드 흐름이 자연스러운지, 읽는 순서가 맞는지는 자동 검사가 판단하지 못합니다. 수동 점검이 필요합니다.

**흔한 실수:** axe 통과를 접근성 완료로 여기는 것입니다. 자동 검사는 "속성이 있는가"를 보고 "사용할 수 있는가"는 보지 못합니다. 이름이 있지만 의미 없는 "버튼"이어도 통과할 수 있습니다.

## Screen Reader

스크린 리더 점검은 사람이 보조기술로 화면을 직접 쓰는 수동 테스트입니다. 스크린 리더는 접근성 트리를 읽으므로, 테스트 코드가 확인한 역할·이름·상태가 실제로 어떻게 읽히는지를 확인합니다.

| 스크린 리더 | 환경 | 비고 |
|-------------|------|------|
| NVDA | Windows | 무료, 오픈 소스 |
| JAWS | Windows | 유료 |
| VoiceOver | macOS, iOS | 운영체제 내장 |
| TalkBack | Android | 운영체제 내장 |

점검할 내용은 다음과 같습니다.

- 각 요소가 역할, 이름, 상태를 함께 읽는가("저장, 버튼", "알림, 체크 박스, 선택됨").
- 제목과 랜드마크로 이동했을 때 구조가 이해되는가.
- 폼에서 레이블, 필수 여부, 오류 메시지가 읽히는가.
- 화면이 바뀌었을 때(토스트, 오류, 로딩 완료) 알림이 읽히는가. 동적 알림은 `role="status"`나 `role="alert"` 같은 live region으로 전달합니다.
- Dialog와 메뉴를 열고 닫을 때 포커스 이동과 읽기 위치가 자연스러운가.

```tsx
await user.click(screen.getByRole('button', { name: '저장' }))
const status = await screen.findByRole('status')
expect(status).toHaveTextContent('저장됨')
```

- 자동 테스트는 live region의 존재와 내용까지만 확인합니다. 실제로 읽히는지는 스크린 리더로 확인합니다.
- 브라우저 개발자 도구의 접근성 인스펙터(예: Firefox Accessibility Inspector)로 접근성 트리를 보면 스크린 리더가 받는 정보를 미리 확인할 수 있습니다.
- 점검은 핵심 흐름(로그인, 결제, 주요 폼)에 집중하고, 릴리스 전이나 큰 변경 때 수행합니다. 지원 대상 환경(예: 모바일 VoiceOver와 TalkBack)은 사용자 분포에 맞춰 정합니다.
- 최종적으로는 장애가 있는 사용자 참여 테스트가 필요합니다. 도구는 그것을 대체하지 못합니다.

**흔한 실수:** 스크린 리더를 켜지 않고 코드만 검토하는 것입니다. `aria-live` 영역이 있어도 렌더 시점이 맞지 않으면 아무것도 읽히지 않을 수 있습니다.

## Regression

접근성 회귀는 한 번 고친 접근성 문제가 코드 변경으로 다시 생기는 것입니다. 한 번 점검하고 끝내지 않고 테스트를 CI에 넣어 지킵니다.

| 계층 | 수단 | 막는 것 |
|------|------|---------|
| 작성 시점 | `eslint-plugin-jsx-a11y` | 레이블 없는 입력, 잘못된 역할 등 정적 오류 |
| 컴포넌트 테스트 | `getByRole`, 키보드·포커스 테스트 | 역할·이름·키보드 동작 변경 |
| 컴포넌트 자동 검사 | axe | 속성 누락, 잘못된 ARIA |
| E2E | Playwright와 axe | 실제 브라우저의 대비, 페이지 구조 |
| 수동 | 스크린 리더 점검 | 자동으로 못 보는 사용 경험 |

- 테스트가 곧 계약입니다. 이름이 있는 `getByRole('button', { name: '저장' })`으로 쓴 테스트는 버튼이 `div`로 바뀌거나 이름이 사라지면 실패합니다.
- 컴포넌트마다 axe 검사를 하나씩 두거나, 공용 `render` 헬퍼에서 자동으로 실행하는 방법이 있습니다. 새 컴포넌트가 검사 없이 들어오지 않게 합니다.
- 기존 위반이 많은 앱에서는 현재 위반 목록을 기준선(baseline)으로 저장하고 새 위반만 실패로 처리해 점차 줄입니다. Playwright 문서는 알려진 위반을 지문(fingerprint)으로 만들어 비교하는 방식을 안내합니다. 위반을 끄거나 요소를 제외하는 것은 그 규칙 검사를 통째로 건너뛰므로 기한과 이유를 기록합니다.
- 디자인 시스템 컴포넌트에는 Storybook의 접근성 애드온과 인터랙션 테스트를 함께 씁니다(자세히는 22편).
- 접근성 버그를 고칠 때는 먼저 실패하는 테스트를 만든 뒤 고칩니다. 재발 방지 효과가 큽니다.

**흔한 실수:** 위반이 많다는 이유로 axe 규칙을 대량으로 꺼 두는 것입니다. 꺼진 규칙은 영원히 검사되지 않아 회귀를 막지 못합니다. 기준선 방식으로 새 위반부터 막습니다.

## 핵심 정리

- `getByRole`이 접근성 트리를 검증하는 기본 쿼리이며, 역할로 찾을 수 없는 요소(클릭 가능한 `div`)는 접근성 결함의 신호입니다.
- 접근 가능한 이름은 `aria-labelledby`, `aria-label`, 호스트 레이블, 내용, `title` 순으로 정해지며 `name` 옵션과 `toHaveAccessibleName`으로 검사합니다.
- 키보드와 포커스 테스트는 `user.tab()`, `user.keyboard()`, `toHaveFocus`로 탭 순서, 키 동작, 상호작용 뒤 포커스 위치를 고정합니다.
- 폼은 `getByLabelText`로 레이블 연결을, `toBeInvalid`와 `toHaveAccessibleDescription`으로 오류 연결을 검증합니다.
- Dialog는 포커스 이동·순환·Escape·복귀, Menu는 역할·상태·방향키·Escape 복귀를 WAI-ARIA 패턴 기준으로 테스트합니다.
- axe는 위반을 자동으로 찾지만 일부만 찾고 jsdom에서는 색 대비가 동작하지 않으므로, 스크린 리더 수동 점검과 CI의 다층 검사로 회귀를 막습니다.

React는 새 코드에 함수 컴포넌트를 권장하지만 클래스 컴포넌트를 제거하지 않았습니다. React 19.3 발표 글에도 클래스 컴포넌트 관련 변경은 없습니다. 기존 코드베이스, 오래된 라이브러리, 에러 바운더리에서 계속 만나게 됩니다. 이 편의 코드는 React 19.3 기준입니다. Hook의 기초는 기초 09편·20편입니다.

## 클래스 컴포넌트

클래스 컴포넌트는 `Component`를 상속하고 `render()` 메서드가 JSX를 반환하는 컴포넌트입니다. `render()`만 필수이고, props는 `this.props`로 읽습니다.

```jsx
import { Component } from 'react'

class Greeting extends Component {
  render() {
    return <h1>Hello, {this.props.name}!</h1>
  }
}
// <Greeting name="Kim" /> → Hello, Kim!
```

- `render()`는 순수해야 합니다. props와 state가 같으면 같은 JSX를 반환하고, 렌더링 중에 값을 바꾸거나 요청을 보내지 않습니다.
- 클래스 컴포넌트 안에서는 Hook(`useState` 등)을 쓸 수 없습니다. 상태와 생명주기는 아래의 인스턴스 속성과 메서드로 다룹니다.
- 인스턴스는 React가 만듭니다. 직접 `new Greeting()`을 호출하지 않습니다.
- 클래스 컴포넌트가 필요한 경우는 하나입니다. 에러 바운더리는 클래스로만 만들 수 있습니다(아래 "클래스 에러 바운더리").

## this

클래스 컴포넌트의 `this`는 컴포넌트 인스턴스이고, `this.props`·`this.state`·`this.setState`가 모두 여기에 붙어 있습니다. 문제는 메서드를 이벤트 핸들러로 넘길 때입니다. 메서드가 인스턴스에서 떨어져 호출되면 `this`가 `undefined`가 됩니다(클래스 본문은 엄격 모드입니다).

```jsx
class Counter extends Component {
  state = { count: 0 }
  handleClick() {
    this.setState({ count: 1 }) // ❌ this가 undefined
  }
  render() {
    return <button onClick={this.handleClick}>+</button>
  }
}
```

해결은 세 가지입니다.

| 방법 | 코드 | 특징 |
|------|------|------|
| 생성자에서 bind | `this.handleClick = this.handleClick.bind(this)` | 인스턴스마다 한 번만 만듦 |
| 클래스 필드 화살표 함수 | `handleClick = () => { ... }` | 가장 흔한 방식 |
| 렌더에서 화살표 함수 | `onClick={() => this.handleClick()}` | 렌더마다 새 함수가 생김 |

```jsx
class Counter extends Component {
  state = { count: 0 }
  handleClick = () => {
    this.setState({ count: 1 }) // ✅ this는 인스턴스
  }
  // ...
}
```

화살표 함수 필드는 프로토타입이 아니라 인스턴스마다 생기는 자기 프로퍼티입니다. 렌더에서 만든 화살표 함수를 자식에게 props로 넘기면 매번 새 함수라서 자식의 최적화가 무력해집니다(아래 "PureComponent"). `this`가 호출 방식으로 정해지는 원리는 JavaScript 과목에서 다룹니다.

**흔한 실수:** 핸들러를 `onClick={this.handleClick()}`처럼 괄호까지 써서 렌더 중에 호출하는 것입니다. 함수 자체를 넘겨야 합니다.

## constructor

`constructor(props)`는 인스턴스가 만들어질 때 한 번 실행되고, 초기 state를 정하거나 메서드를 bind하는 데 씁니다. 첫 줄에서 반드시 `super(props)`를 호출해야 합니다. 호출하지 않으면 생성자 안에서 `this.props`가 `undefined`입니다.

```jsx
class Counter extends Component {
  constructor(props) {
    super(props)
    this.state = { count: props.initial }
    this.handleClick = this.handleClick.bind(this)
  }
  // ...
}
```

- 생성자에서 요청을 보내거나 구독을 시작하지 않습니다. 렌더 단계에서 실행되므로 부수 효과는 `componentDidMount`에 둡니다.
- 생성자에서 할 일이 state 초기화와 bind뿐이면 생성자를 쓰지 않고 클래스 필드(`state = {}`, 화살표 함수)로 대체합니다. 요즘 코드는 대부분 그렇게 씁니다.
- props를 state의 초기값으로 복사하면 이후 props가 바뀌어도 state는 따라가지 않습니다. 의도한 초기값일 때만 씁니다.

## this.state

`this.state`는 컴포넌트가 기억하는 값을 담은 객체입니다. 클래스 필드나 생성자에서 한 번 선언하고, 값은 `this.state.name`으로 읽습니다.

```jsx
class Profile extends Component {
  state = { name: 'Taylor', age: 42 }
  render() {
    return <p>{this.state.name}, {this.state.age}</p>
  }
}
```

- state는 하나의 객체이고 필드를 여러 개 담습니다. 함수 컴포넌트에서 `useState`를 값마다 호출하는 것과 다릅니다.
- `this.state`를 직접 바꾸면(`this.state.age = 43`) 화면이 다시 그려지지 않습니다. 변경은 항상 `setState`로 합니다.
- 초기 선언 이후에는 `this.state = ...`로 대입하지 않습니다. 대입은 생성자에서만 허용됩니다.
- 객체·배열 state를 불변으로 갱신하는 규칙은 함수 컴포넌트와 같습니다(자세히는 기초 11편).

## setState

`setState`는 state 변경을 큐에 넣고 다시 렌더링을 요청합니다. 즉시 실행되지 않으므로 호출 직후 `this.state`는 아직 이전 값입니다. 여러 번 호출은 한 번의 렌더링으로 묶입니다(자세히는 기초 10편).

```jsx
this.setState({ age: this.state.age + 1 })
this.setState((prev) => ({ age: prev.age + 1 }))
this.setState({ name: 'Robin' }, () => {
  // 갱신이 화면에 반영된 뒤 실행
})
```

- **객체 형태**는 전달한 필드만 기존 state에 얕게 병합합니다. 나머지 필드는 유지됩니다. `useState`의 setter가 값을 통째로 교체하는 것과 다릅니다.
- **함수 형태**는 가장 최근 state를 인자로 받습니다. 이전 값에서 다음 값을 계산할 때는 이 형태를 씁니다.
- **두 번째 인자 콜백**은 갱신 뒤에 실행됩니다. 갱신 뒤 작업은 보통 `componentDidUpdate`에 둡니다.
- 병합은 한 단계뿐입니다. 중첩 객체 안의 필드를 바꾸려면 중첩 객체를 직접 복사해서 넘깁니다.

```jsx
this.setState((prev) => ({
  user: { ...prev.user, age: prev.user.age + 1 },
}))
```

**흔한 실수:**

- `this.setState({ n: this.state.n + 1 })`을 연달아 두 번 호출하고 2가 늘기를 기대하는 것입니다. 둘 다 같은 스냅샷을 읽어 1만 늘어납니다. 함수 형태로 씁니다.
- `render()` 안에서 `setState`를 호출해 무한 렌더링을 만드는 것입니다.

## 생명주기

생명주기(lifecycle)는 컴포넌트가 화면에 추가되고(마운트), 갱신되고, 제거되는(언마운트) 시점에 React가 호출하는 메서드입니다. 클래스에서는 시점마다 메서드가 따로 있습니다.

| 단계 | 호출 순서 |
|------|-----------|
| 마운트 | `constructor` → `getDerivedStateFromProps` → `render` → `componentDidMount` |
| 업데이트 | `getDerivedStateFromProps` → `shouldComponentUpdate` → `render` → `getSnapshotBeforeUpdate` → `componentDidUpdate` |
| 언마운트 | `componentWillUnmount` |

- `render`까지는 DOM을 바꾸기 전의 렌더 단계이고, `componentDidMount`·`componentDidUpdate`·`componentWillUnmount`는 DOM에 반영된 뒤의 커밋 단계입니다. 부수 효과는 커밋 단계 메서드에 둡니다.
- `componentWillMount`, `componentWillReceiveProps`, `componentWillUpdate`는 이름 앞에 `UNSAFE_`를 붙인 형태로만 남았고 쓰지 않습니다. 렌더 단계는 중단되고 다시 시작될 수 있어서 거기서 부수 효과를 내면 안 되기 때문입니다(자세히는 09편). `rename-unsafe-lifecycles` codemod로 이름을 바꿉니다.
- 자식과 부모가 함께 마운트되면 자식의 `componentDidMount`가 부모보다 먼저 실행됩니다.
- 개발 중 StrictMode에서는 `componentDidMount` → `componentWillUnmount` → `componentDidMount` 순으로 한 번 더 호출해 정리 코드가 빠졌는지 검사합니다(자세히는 기초 18편).

### componentDidMount

컴포넌트가 화면에 처음 추가된 직후 한 번 실행됩니다. 데이터 요청 시작, 구독 시작, DOM 측정처럼 DOM이 있어야 하는 작업을 합니다.

```jsx
componentDidMount() {
  this.connection = createConnection(this.props.roomId)
  this.connection.connect()
}
```

- 여기서 `setState`를 호출하면 추가 렌더링이 일어나지만 브라우저가 화면을 그리기 전에 처리됩니다.
- 함수 컴포넌트에서는 의존성 배열이 빈 `useEffect`가 가장 가깝습니다.

### componentDidUpdate

props나 state가 바뀌어 다시 렌더링된 직후에 실행됩니다. 첫 렌더링에서는 실행되지 않습니다. 인자 `prevProps`, `prevState`, `snapshot`으로 무엇이 바뀌었는지 비교합니다.

```jsx
componentDidUpdate(prevProps) {
  if (this.props.roomId !== prevProps.roomId) {
    this.connection.disconnect()
    this.connection = createConnection(this.props.roomId)
    this.connection.connect()
  }
}
```

- 반드시 이전 값과 비교하는 조건을 걸어야 합니다. 조건 없이 `setState`를 호출하면 갱신이 갱신을 부르는 무한 루프가 됩니다.
- 이전 값과 비교하는 코드가 이 메서드의 대부분입니다. `useEffect`의 의존성 배열이 이 비교를 대신합니다(자세히는 기초 21편).

### componentWillUnmount

컴포넌트가 화면에서 제거되기 직전에 한 번 실행됩니다. `componentDidMount`에서 시작한 것을 정리합니다.

```jsx
componentWillUnmount() {
  this.connection.disconnect()
}
```

- 구독 해제, 타이머 해제, 연결 종료를 여기서 합니다. 빠뜨리면 메모리 누수와 제거된 컴포넌트에 대한 갱신이 남습니다.
- 함수 컴포넌트에서는 `useEffect`가 반환하는 정리 함수가 대응합니다.

**흔한 실수:** 설정은 `componentDidMount`에 쓰고 정리는 잊는 것, 그리고 같은 연결을 `componentDidUpdate`에서 바꿀 때 이전 연결을 끊지 않는 것입니다. 클래스는 설정과 정리가 세 메서드에 흩어져서 짝이 맞는지 보기 어렵고, 이것이 Effect 한 덩어리로 옮겨 간 이유입니다.

## PureComponent

`PureComponent`는 props와 state를 얕은 비교로 검사해서 바뀌지 않았으면 다시 렌더링하지 않는 클래스 컴포넌트입니다. `shouldComponentUpdate`에서 얕은 비교를 직접 구현한 것과 같습니다. 일반 `Component`는 부모가 다시 렌더링되면 항상 다시 렌더링됩니다.

```jsx
import { PureComponent } from 'react'

class Row extends PureComponent {
  render() {
    return <li>{this.props.label}</li>
  }
}
// label이 같으면 부모가 렌더링돼도 Row는 건너뜀
```

- 얕은 비교는 원시 값은 값으로, 객체·배열·함수는 참조로 비교합니다. 내용만 바뀐 객체를 참조는 그대로 두고 변경(mutate)하면 변화를 놓칩니다. 그래서 불변 갱신이 전제입니다.
- 렌더마다 `style={{ color: 'red' }}`, `onClick={() => ...}`처럼 새 객체·함수를 props로 넘기면 매번 참조가 달라져 건너뛰기가 일어나지 않습니다.
- 컨텍스트 값이 바뀌면 `PureComponent`도 다시 렌더링됩니다.
- 함수 컴포넌트에서는 `memo`가 대응합니다. `memo`는 props만 비교하고 state는 비교하지 않지만, 함수 컴포넌트는 같은 값으로 setter를 호출하면 이미 다시 렌더링하지 않습니다(자세히는 중급 18편).

```jsx
const Row = memo(function Row({ label }) {
  return <li>{label}</li>
})
```

## HOC

HOC(Higher-Order Component)는 컴포넌트를 받아 새 컴포넌트를 반환하는 함수입니다. 클래스 시대에 로직(구독, 인증 확인, 데이터 주입)을 컴포넌트 사이에서 재사용하던 주된 패턴입니다. 이름은 보통 `with`로 시작합니다.

```jsx
function withUser(Wrapped) {
  function WithUser(props) {
    const user = useCurrentUser()
    return <Wrapped {...props} user={user} />
  }
  WithUser.displayName = `WithUser(${Wrapped.name})`
  return WithUser
}
const ProfileWithUser = withUser(Profile)
```

HOC를 쓸 때 지킬 규칙은 다음과 같습니다(React 레거시 문서).

- 원본 컴포넌트를 변경하지 않고 감싸서 새 컴포넌트를 반환합니다. 원본의 프로토타입을 고치는 HOC는 다른 HOC와 충돌합니다.
- 자신이 쓰지 않는 props는 `{...props}`로 그대로 넘깁니다.
- DevTools에서 구별되도록 `displayName`을 정합니다.
- 렌더 안에서 HOC를 호출하지 않습니다. 렌더마다 새 컴포넌트 타입이 생겨 하위 트리가 매번 언마운트·마운트됩니다(자세히는 기초 13편). 모듈 최상위에서 한 번만 적용합니다.
- 정적 메서드는 자동으로 복사되지 않습니다. 복사하려면 `hoist-non-react-statics` 같은 도구를 씁니다.
- `ref`는 props로 전달되지 않는 값이어서 HOC가 가로챕니다. 클래스·`forwardRef` 시대에는 `forwardRef`로 우회했고, 함수 컴포넌트가 `ref`를 props로 받는 React 19에서는 `{...props}`에 포함됩니다.

오늘은 Hook과 Composition이 대체합니다. 데이터를 주입하는 HOC는 커스텀 Hook, 레이아웃을 감싸는 HOC는 `children` 컴포지션이 되고, 감싼 컴포넌트가 어떤 props를 받는지 읽기 어려운 문제도 사라집니다(자세히는 11편). 라이브러리가 제공하는 HOC(`connect`, `withRouter`)를 만나면 같은 기능의 Hook(`useSelector`, `useNavigate`)으로 바꿀 수 있는지부터 확인합니다.

## 클래스 에러 바운더리

에러 바운더리는 자식 트리의 렌더링 중 에러를 잡아 대체 UI를 보여 주는 컴포넌트이고, 두 정적·인스턴스 메서드 중 하나라도 가진 클래스 컴포넌트가 에러 바운더리가 됩니다. 함수 컴포넌트와 Hook으로는 만들 수 없습니다.

```jsx
class ErrorBoundary extends Component {
  state = { hasError: false }
  static getDerivedStateFromError(error) {
    return { hasError: true }
  }
  componentDidCatch(error, info) {
    logError(error, info.componentStack)
  }
  render() {
    return this.state.hasError
      ? this.props.fallback
      : this.props.children
  }
}
```

| 메서드 | 시점 | 역할 |
|--------|------|------|
| `getDerivedStateFromError(error)` | 렌더 단계 | 반환한 객체로 state를 갱신해 다음 렌더에서 대체 UI를 그림. 부수 효과 금지 |
| `componentDidCatch(error, info)` | 커밋 단계 | 에러 로깅·전송. `info.componentStack`에 컴포넌트 계층이 담김 |

에러 바운더리가 잡지 못하는 에러는 다음과 같습니다.

- 이벤트 핸들러 안의 에러(`try`/`catch`를 씁니다)
- 서버 사이드 렌더링 중의 에러
- 에러 바운더리 자기 자신이 던진 에러(바깥 바운더리가 잡습니다)
- `setTimeout`·`requestAnimationFrame` 같은 비동기 코드의 에러. 단, `startTransition` 안의 에러는 잡힙니다.

React 19부터 잡히지 않은 에러는 `window.reportError`로, 에러 바운더리가 잡은 에러는 `console.error`로 보고되고 다시 던져지지 않습니다. `createRoot`·`hydrateRoot`의 `onUncaughtError`, `onCaughtError` 옵션으로 보고 방식을 바꿀 수 있습니다.

직접 클래스를 쓰지 않으려면 `react-error-boundary` 패키지가 `ErrorBoundary` 컴포넌트와 재시도(리셋) 기능을 함수 컴포넌트 문법으로 제공합니다. 에러 바운더리를 어디에 둘지의 설계는 중급 13편에서 다룹니다.

## 클래스와 함수 컴포넌트 대응표

클래스 코드를 읽을 때 함수 컴포넌트의 어떤 코드에 해당하는지 대응시키면 이식이 쉽습니다.

| 클래스 | 함수 컴포넌트 |
|--------|---------------|
| `this.props` | 매개변수 구조 분해 |
| `this.state`, `this.setState` | `useState`, `useReducer` |
| 생성자의 state 초기화 | `useState(초기값)` 또는 초기화 함수 |
| `componentDidMount` | `useEffect(..., [])` |
| `componentDidUpdate` | 의존성을 가진 `useEffect` |
| `componentWillUnmount` | `useEffect`가 반환한 정리 함수 |
| `static contextType`, `this.context` | `useContext` |
| `createRef`, 인스턴스 필드 | `useRef` |
| `shouldComponentUpdate`, `PureComponent` | `memo` |
| `getSnapshotBeforeUpdate` | 대응하는 Hook 없음 |
| `getDerivedStateFromError`, `componentDidCatch` | 대응하는 Hook 없음 |

- 메서드 단위가 아니라 **관심사 단위**로 옮깁니다. 클래스에서는 한 관심사(연결)가 세 메서드에 흩어져 있고, 함수에서는 Effect 하나가 설정과 정리를 함께 가집니다. 서로 다른 관심사는 Effect를 나눕니다.
- `componentDidUpdate`의 이전 값 비교는 의존성 배열로 옮기되, 비교로 막던 불필요한 Effect가 있다면 먼저 Effect가 필요한지부터 따집니다(자세히는 기초 22편).
- 브라우저가 화면을 그리기 전에 실행해야 하는 코드는 `useEffect`가 아니라 `useLayoutEffect`로 옮깁니다(자세히는 중급 04편).
- 클래스 인스턴스 필드는 렌더링과 무관하면 `useRef`, 화면에 보이면 `useState`입니다.
- 기능이 같아도 동작이 완전히 같지는 않습니다. 이벤트 핸들러가 `this.props`로 항상 최신 props를 읽는 것과 달리 함수 컴포넌트의 핸들러는 렌더 시점의 값을 닫아 둡니다(자세히는 기초 10편).

한 번에 다 바꿀 필요는 없습니다. 클래스와 함수 컴포넌트는 한 트리에 섞여 동작하고, 새로 고치는 컴포넌트부터 함수로 바꾸는 점진적 이식이 안전합니다. 에러 바운더리 클래스는 그대로 두어도 됩니다.

## getSnapshotBeforeUpdate

`getSnapshotBeforeUpdate(prevProps, prevState)`는 React가 DOM을 갱신하기 직전에 호출되어 갱신 전 DOM 정보(스크롤 위치 등)를 읽어 반환하는 메서드입니다. 반환값은 `componentDidUpdate`의 세 번째 인자 `snapshot`으로 전달됩니다. 반환할 값이 없으면 `null`을 반환합니다.

```jsx
getSnapshotBeforeUpdate(prevProps) {
  if (prevProps.items.length < this.props.items.length) {
    return this.listRef.current.scrollHeight
  }
  return null
}
componentDidUpdate(prevProps, prevState, snapshot) {
  if (snapshot !== null) {
    const list = this.listRef.current
    list.scrollTop += list.scrollHeight - snapshot
  }
}
```

- 위 코드는 목록 위쪽에 항목이 추가돼도 보던 위치가 밀리지 않게 하는 예입니다. 갱신 전의 높이를 알아야 갱신 후의 차이를 계산할 수 있기 때문에 이 시점이 필요합니다.
- 공식 문서는 이 메서드에 대응하는 함수 컴포넌트 기능이 없다고 설명합니다. 쓰는 곳이 드물고, 에러 바운더리와 함께 클래스를 남겨 둔 두 이유입니다.
- 이식해야 한다면 `useLayoutEffect`에서 갱신 전 값을 `useRef`에 저장해 두고 비교하는 식으로 풀어야 하며, 완전히 같은 시점이 보장되지는 않으므로 동작을 확인합니다.

## 레거시 Context와 문자열 ref

둘 다 클래스 컴포넌트 시절의 오래된 API이고 React 19에서 제거되었습니다. 오래된 코드를 읽을 때 알아보아야 합니다.

### 레거시 Context

레거시 Context는 제공 쪽에 `childContextTypes`와 `getChildContext()`, 사용 쪽에 `contextTypes`를 선언해 값을 내려 보내는 API입니다.

```jsx
class Parent extends Component {
  static childContextTypes = { theme: PropTypes.string }
  getChildContext() {
    return { theme: 'dark' }
  }
}
class Child extends Component {
  static contextTypes = { theme: PropTypes.string }
  // this.context.theme
}
```

- 중간 컴포넌트가 `shouldComponentUpdate`에서 `false`를 반환하면 그 아래 사용자는 값이 바뀌어도 갱신되지 않는 결함이 있어서 React 16.3의 `createContext`로 대체되었습니다.
- 대체는 `createContext`로 Context를 만들고, 제공 쪽은 Provider로 감싸고, 클래스 사용 쪽은 `static contextType`으로 읽는 것입니다. 이 변환은 codemod가 없어 수동입니다(자세히는 중급 01편).

```jsx
const ThemeContext = createContext('light')
// 제공: Provider에 value를 전달
// 사용: static contextType = ThemeContext → this.context
```

### 문자열 ref

문자열 ref는 `ref="input"`처럼 문자열을 `ref`에 쓰고 `this.refs.input`으로 DOM 노드를 읽는 방식입니다. React 19에서 제거되었고 `this.refs`도 함께 사라졌습니다. 콜백 ref나 `createRef`로 바꿉니다(자세히는 중급 03편).

```jsx
// ❌ <input ref="input" /> + this.refs.input.focus()
// ✅ 콜백 ref
<input ref={(node) => (this.input = node)} />
// 사용: this.input.focus()
```

콜백 ref는 인라인으로 쓰면 렌더마다 새 함수라 갱신 때 `null`과 노드로 두 번 호출되는데, 위 방식은 이 점이 문제 되지 않는 단순한 경우입니다. `replace-string-ref` codemod가 자동으로 바꿉니다.

## React 19에서 제거된 API와 codemod

React 19는 이전 버전에서 경고만 내던 API를 제거했습니다. 제거된 API를 쓰면 호출이 실패하거나 동작하지 않습니다.

**React 패키지**

| 제거된 API | 대체 | codemod |
|------------|------|---------|
| 함수 컴포넌트의 `propTypes` | TypeScript 등 타입 검사 | `react/prop-types-typescript` |
| 함수 컴포넌트의 `defaultProps` | 기본 매개변수 | `react/prop-types-typescript` |
| 레거시 Context | `createContext` | 수동 |
| 문자열 ref | 콜백 ref, `createRef` | `react/19/replace-string-ref` |
| 모듈 패턴 팩토리 컴포넌트 | 일반 함수 컴포넌트 | 수동 |
| `React.createFactory` | JSX | 수동 |
| `react-test-renderer/shallow` | `react-shallow-renderer` 별도 설치 | 수동 |

**React DOM 패키지**

| 제거된 API | 대체 | codemod |
|------------|------|---------|
| `ReactDOM.render` | `createRoot(...).render` | `react/19/replace-reactdom-render` |
| `ReactDOM.hydrate` | `hydrateRoot` | `react/19/replace-reactdom-render` |
| `unmountComponentAtNode` | `root.unmount()` | `react/19/replace-reactdom-render` |
| `ReactDOM.findDOMNode` | `useRef`로 얻은 DOM ref | 수동 |
| `react-dom/test-utils`의 `act` | `react`에서 `act` import | `react/19/replace-act-import` |

- 클래스 컴포넌트의 `defaultProps`와 `UNSAFE_` 생명주기는 이 제거 목록에 없습니다.
- 모듈 패턴 팩토리는 컴포넌트 함수가 `render` 메서드를 가진 객체를 반환하던 오래된 형태입니다.
- UMD 빌드도 제거되어 `script` 태그로 불러오던 방식은 `esm.sh` 같은 ESM CDN으로 바꿔야 합니다.
- 새 JSX 변환(transform)이 필수입니다. 오래된 변환을 쓰면 경고가 나옵니다.
- `createRoot` 옵션의 에러 핸들러는 위 "클래스 에러 바운더리"를 참고합니다.

codemod는 `npx codemod@latest 이름`으로 실행하고, 한꺼번에 적용하는 레시피가 있습니다.

```bash
npx codemod@latest react/19/migration-recipe
npx types-react-codemod@latest preset-19 ./src
```

- 레시피는 `replace-reactdom-render`, `replace-string-ref`, `replace-act-import`, `replace-use-form-state`, `prop-types-typescript`를 실행합니다.
- 두 번째 줄은 TypeScript 프로젝트의 타입 변경용입니다. `useRef`는 인자가 필수가 되고, ref 콜백은 값을 암묵적으로 반환하면 안 되며, JSX 네임스페이스는 `React.JSX`로 옮겨졌고, `ReactElement`의 props 기본 타입이 `any`에서 `unknown`으로 바뀌었습니다.
- codemod 결과는 diff를 읽고 확인합니다. 수동 항목(레거시 Context, `createFactory`, `findDOMNode`, 얕은 렌더러)은 직접 바꿉니다.

## 버전 업그레이드 절차

기존 앱을 올릴 때는 한 번에 최신으로 건너뛰지 않고 경고가 알려 주는 순서대로 진행합니다. 17 이하에서 올라오는 경우를 포함한 순서입니다.

1. **18로 먼저 올립니다.** `render`·`hydrate`를 `createRoot`·`hydrateRoot`로 바꾸고(레거시 모드는 18에서 경고를 냅니다), 렌더 콜백은 `useEffect`로 옮깁니다. 18에서 자동 배칭과 StrictMode의 이중 마운트가 켜지므로 앱 동작을 확인합니다. TypeScript는 `children`을 props 타입에 직접 선언해야 합니다.
2. **18.3으로 올려 경고를 봅니다.** 18.3은 19에서 제거될 API에 대한 경고를 추가한 버전입니다. 콘솔 경고를 모두 해결하는 것이 목표입니다.
3. **의존 라이브러리의 호환 버전을 확인합니다.** `peerDependencies`에 React 19를 허용하는 버전으로 먼저 올립니다. 클래스·레거시 API에 의존하는 오래된 라이브러리가 가장 흔한 막힘입니다.
4. **19를 설치합니다.** TypeScript면 타입 패키지도 함께 올립니다.

```bash
npm install --save-exact react@^19.0.0 react-dom@^19.0.0
npm i -E @types/react@^19.0.0 @types/react-dom@^19.0.0
```

5. **codemod를 돌리고 수동 항목을 고칩니다.** 위 절의 순서입니다.
6. **테스트를 확인합니다.** `act`는 `react`에서 가져오고, 얕은 렌더러를 쓰던 테스트는 다시 씁니다(자세히는 중급 34편, 35편).
7. **에러 처리를 확인합니다.** 렌더 에러가 다시 던져지지 않으므로 모니터링이 `onUncaughtError`·`onCaughtError`나 `window.reportError`로 에러를 받는지 확인합니다(자세히는 26편).
8. **19.x 안에서는 올리기만 합니다.** 19.3 발표 글은 제거나 호환성을 깨는 변경이 없다고 밝힙니다. 마이너·패치는 변경 기록을 읽고 올립니다.

**흔한 실수:**

- 18.3을 건너뛰고 19로 올려서 어떤 코드가 문제인지 경고 없이 마주치는 것입니다.
- codemod를 실행하고 결과를 보지 않는 것입니다. 변환이 맞지 않는 코드를 만들 수 있으므로 diff를 읽고 테스트를 돌립니다.
- 클래스 컴포넌트를 함수로 모두 바꾸는 작업을 업그레이드와 한 번에 하는 것입니다. 둘은 별개이고 클래스는 19에서도 동작하므로 따로 진행합니다.

## 핵심 정리

- 클래스 컴포넌트는 `render()`, `this.props`, `this.state`로 동작하고 Hook을 쓸 수 없으며, 메서드를 핸들러로 넘길 때 `this` 바인딩이 필요합니다.
- `setState`는 비동기로 묶이고 객체를 얕게 병합하며, 이전 값 기반 갱신은 함수 형태로 씁니다.
- 마운트·업데이트·언마운트에 `componentDidMount`·`componentDidUpdate`·`componentWillUnmount`가 대응하고, 이 셋은 함수 컴포넌트에서 `useEffect`로 합쳐집니다.
- `PureComponent`는 `memo`, HOC는 커스텀 Hook과 Composition으로 대체합니다. 에러 바운더리와 `getSnapshotBeforeUpdate`는 함수 컴포넌트에 대응하는 Hook이 없습니다.
- 레거시 Context·문자열 ref·`ReactDOM.render` 등은 React 19에서 제거되었으며, `codemod@latest react/19/migration-recipe`가 일부를 자동 변환하고 나머지는 수동입니다.
- 업그레이드는 18, 18.3의 경고 해결, 19 설치, codemod, 테스트·에러 처리 확인 순서로 진행합니다.

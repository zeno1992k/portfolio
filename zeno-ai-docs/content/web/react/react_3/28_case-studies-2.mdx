## 경계와 검증을 읽는 틀

경계는 영향이 번지는 범위를 끊는 선입니다. 설계안에서 어떤 경계가 어디에 있는지 찾으면 구조가 보입니다.

| 경계 | 끊는 것 | 만드는 도구 |
|------|---------|-------------|
| 로딩 경계 | 기다림의 범위 | `Suspense` |
| 실패 경계 | 에러의 범위 | 에러 바운더리 |
| 실행 위치 경계 | 코드가 도는 곳(서버·클라이언트) | `use client`, `use server` |
| 출력 일치 경계 | 서버와 클라이언트 첫 출력 | Hydration 규칙 |
| 공개 범위 경계 | 외부에 약속한 API | 패키지 export, props |

검증은 경계가 지켜지는지 확인하는 방법이고, 층마다 잡는 것이 다릅니다.

| 방법 | 잡는 것 | 느린 정도 |
|------|---------|-----------|
| 타입·린트 | 규칙 위반, 잘못된 import | 가장 빠름 |
| 단위·컴포넌트 테스트 | 사용자가 보는 동작 | 빠름 |
| 스토리(Storybook) | 상태별 외형, 접근성 | 보통 |
| E2E | 핵심 흐름이 실제로 이어지는가 | 느림 |
| 프로파일링·실측 | 성능 수치 | 별도 |

## Suspense UI

**요구:** 프로필 페이지. 헤더(이름·사진)는 즉시, 게시글 목록과 추천 영역은 준비되는 대로 나타난다. 한 영역이 실패해도 나머지는 남는다.

**경계 설계:**

```text
ProfilePage
├─ Header                        (즉시, 경계 없음)
├─ [에러 경계 > Suspense] Posts
└─ [에러 경계 > Suspense] Recommendations
```

```jsx
<ErrorBoundary fallback={<PostsError />}>
  <Suspense fallback={<PostsSkeleton />}>
    <Posts userId={userId} />
  </Suspense>
</ErrorBoundary>
```

- 같은 시점에 나타나야 하는 것은 한 경계에, 독립적으로 나타나도 되는 것은 별도 경계에 둡니다. 경계를 너무 잘게 나누면 스켈레톤이 여기저기 따로 바뀌어 산만하고, 너무 크면 가장 느린 것이 전체를 가립니다.
- 에러 경계가 바깥, Suspense가 안쪽입니다. 로딩 중에는 안쪽 fallback이, 실패하면 바깥의 대체 UI가 보입니다.
- 한 Suspense 안에 중첩 경계를 두면 바깥 내용(`Biography`)이 먼저 나타나고 안쪽(`Albums`)은 자기 fallback을 보여 줍니다.

**무엇이 Suspense를 작동시키는가:** `lazy`로 불러오는 컴포넌트 코드, `use`로 읽는 Promise, `precedence`를 가진 스타일시트 로딩, 스트리밍 서버 렌더링입니다. **Effect나 이벤트 핸들러 안에서 가져오는 데이터는 감지하지 못합니다.** 그래서 `useEffect`로 가져오는 코드는 Suspense 설계에 들어맞지 않고, Suspense를 지원하는 데이터 라이브러리(`useSuspenseQuery`)나 `use`를 씁니다(자세히는 중급 11편, 15편).

**데이터 흐름의 함정:** 부모 컴포넌트가 데이터를 읽는 동안 자식은 렌더되지 않으므로, 자식이 또 요청하면 요청이 순차로 이어지는 워터폴이 됩니다. 독립적인 요청은 같은 레벨의 형제 컴포넌트로 나눠 병렬로 시작하거나 상위에서 Promise를 먼저 만듭니다(자세히는 06편).

**이미 보이는 내용을 가리지 않기:** 탭 전환이나 검색어 변경으로 다시 Suspense가 걸리면 이미 보이던 화면이 fallback으로 바뀝니다. 상태 변경을 `startTransition`으로 감싸거나 `useDeferredValue`를 쓰면 새 내용이 준비될 때까지 기존 화면을 유지합니다. 다른 사용자 프로필로 이동할 때처럼 내용이 완전히 바뀌면 경계에 `key={userId}`를 주어 초기화합니다(자세히는 중급 09편, 10편).

**검증:**

- 네트워크를 느리게 제한(DevTools Network throttling)해 영역별로 스켈레톤이 독립적으로 나타나는지 확인합니다.
- 한 영역의 요청을 실패시켜(요청 차단, 모킹) 나머지가 남고 해당 영역만 대체 UI가 되는지 확인합니다.
- 전환 시 이미 보이는 내용이 fallback으로 되돌아가지 않는지 확인합니다.
- 컴포넌트 테스트에서는 비동기 결과를 `findBy` 쿼리로 기다립니다.
- React는 Suspense로 감춘 내용을 드러내는 시점을 300밀리초에 한 번으로 묶으므로 준비가 거의 동시에 끝나는 경계는 함께 나타나는 것이 정상입니다.

**흔한 실수:** 앱 최상단에 Suspense 하나만 두는 것, 에러 경계 없이 Suspense만 두어 실패가 앱 전체로 번지는 것, 데이터를 Effect에서 가져오면서 Suspense가 동작하기를 기대하는 것입니다.

## SSR + Hydration

**요구:** 상품 상세 페이지를 서버에서 렌더해 검색 엔진과 첫 화면에 내용을 보이고, 이후 클라이언트에서 인터랙티브하게 만든다. 최근 본 상품(브라우저 저장소)과 현재 시각이 들어간다.

**경계 설계:** 서버가 만든 HTML과 클라이언트의 첫 렌더 출력이 **같아야** 합니다. 다르면 Hydration 불일치입니다. 컴포넌트마다 서버·클라이언트 출력이 같은지 판정합니다.

```text
ProductPage
├─ ProductInfo        서버 = 클라이언트 (같은 데이터)
├─ [Suspense] Reviews 스트리밍 (늦게 도착해도 됨)
├─ RecentlyViewed     클라이언트에만 존재하는 데이터
└─ PriceUpdatedAt     시각·시간대 의존
```

| 컴포넌트 | 문제 | 처리 |
|----------|------|------|
| `ProductInfo` | 없음 | 그대로 |
| `Reviews` | 서버에서 느림 | Suspense로 스트리밍, 셸을 먼저 전송 |
| `RecentlyViewed` | 서버에는 저장소가 없음 | 클라이언트에서만 렌더 |
| `PriceUpdatedAt` | 서버·클라이언트 시각, 시간대 차이 | 서버에서 포맷한 문자열을 props로 전달, 불가피하면 `suppressHydrationWarning` |

클라이언트 전용 내용을 처리하는 방법은 세 가지입니다.

```jsx
// 1) 두 번 렌더: 서버·첫 렌더는 빈 자리, 이후 채움
const [mounted, setMounted] = useState(false)
useEffect(() => setMounted(true), [])
return mounted ? <Recent /> : <RecentSkeleton />
```

```jsx
// 2) 19.3: 서버에서는 Suspense fallback, 클라이언트에서 렌더
function Recent() {
  use(browser()) // react-dom의 browser
  return <List items={readStorage()} />
}
```

- 첫 번째 방식은 컴포넌트가 두 번 렌더되어 Hydration이 약간 느려집니다.
- 두 번째 `browser()`는 React 19.3에서 정식입니다. 서버에서는 Suspense를 작동시켜 fallback을 HTML에 넣고 클라이언트에서는 정상 렌더하므로 불일치 없이 서버를 건너뜁니다(자세히는 03편).
- 외부 저장소의 값은 `useSyncExternalStore`의 서버 스냅샷으로 다룰 수 있습니다(자세히는 중급 05편).
- `suppressHydrationWarning`은 요소 하나, 한 단계 깊이까지만 경고를 끄는 탈출구입니다. 구조가 다른 불일치를 숨기지 못하고 남발하지 않습니다.

**서버·클라이언트 흐름:** 서버가 `renderToPipeableStream`으로 셸(Suspense 밖의 부분)을 먼저 보내고 경계 안 내용을 이어서 보냅니다. 브라우저는 HTML을 바로 그리고, 클라이언트는 `hydrateRoot`로 이벤트를 연결합니다. 경계 단위로 Hydration되므로 사용자가 먼저 상호작용한 부분이 우선입니다(자세히는 01편, 02편, 03편).

**불일치의 주된 원인:**

- `Date.now()`, `new Date()` 같은 시각, `Math.random()` 같은 난수
- `typeof window` 분기나 `matchMedia` 같은 브라우저 API를 렌더에서 읽음
- 서버·클라이언트에서 다른 데이터를 렌더
- 잘못된 HTML 중첩(`p` 안의 `div` 등)
- 브라우저 확장이 DOM을 수정

**검증:**

- 개발 모드 콘솔에 나타나는 Hydration 불일치 경고와 차이(diff)를 확인합니다.
- JavaScript를 끄거나 페이지 소스 보기로 서버 HTML에 핵심 내용이 들어 있는지 봅니다.
- `hydrateRoot`의 `onRecoverableError`를 모니터링에 연결해 운영에서 불일치 빈도를 추적합니다(자세히는 26편).
- LCP와 TTFB를 측정해 스트리밍 효과를 확인합니다.
- 시간대·로케일이 다른 환경에서 렌더해 시각 표기를 확인합니다.

**흔한 실수:** 렌더에서 `window`·`localStorage`를 바로 읽는 것(서버에서 에러), `typeof window` 분기로 출력을 나누는 것(불일치), 모든 경고를 `suppressHydrationWarning`으로 덮는 것입니다.

## Server Components

**요구:** 글 상세 페이지. 본문은 서버에서 DB와 파일을 읽고, 좋아요 버튼과 접고 펴는 영역은 인터랙티브해야 하며, 댓글은 늦게 도착해도 된다.

**경계 설계:** 기본은 서버 컴포넌트이고, 상호작용이 필요한 **말단**에서만 `use client`로 클라이언트 경계를 시작합니다.

```text
PostPage            (서버, async)  DB 읽기
├─ PostBody         (서버)         마크다운 → HTML
├─ LikeButton       (클라이언트)   useState, onClick
├─ Expandable       (클라이언트)   children으로 서버 UI 받음
│  └─ AuthorBio     (서버 컴포넌트가 children으로 전달됨)
└─ [Suspense] Comments (클라이언트)  use(commentsPromise)
```

```js
async function PostPage({ id }) {
  const post = await db.posts.get(id)
  const commentsPromise = db.comments.get(id) // await 안 함
  return (
    <article>
      <PostBody post={post} />
      <Suspense fallback={<p>Loading...</p>}>
        <Comments commentsPromise={commentsPromise} />
      </Suspense>
    </article>
  )
}
```

- 서버 컴포넌트는 `async`로 `await`할 수 있고, 서버 자원(DB, 파일, 비밀 값)에 접근하며, 브라우저로 코드가 전달되지 않습니다. Hook과 이벤트 핸들러, 브라우저 API는 쓸 수 없습니다.
- 마크다운 파서 같은 무거운 라이브러리를 서버 컴포넌트에서만 import하면 클라이언트 번들에 포함되지 않습니다. 이것이 번들 감소의 원리입니다.
- **Promise를 넘기는 패턴:** 서버가 Promise를 `await`하지 않고 클라이언트 컴포넌트에 props로 넘기면, 클라이언트가 `use`로 읽고 Suspense가 로딩을 처리합니다. 본문은 기다리지 않고 먼저 나갑니다(자세히는 06편).
- 서버 컴포넌트를 클라이언트 컴포넌트의 `children`으로 전달할 수 있습니다. `Expandable`이 클라이언트여도 그 안의 `AuthorBio`는 서버에서 렌더됩니다. 클라이언트 경계가 서버 컴포넌트를 import하는 것은 안 되고, children·props로 받는 것은 됩니다(자세히는 04편).
- 클라이언트 컴포넌트로 넘기는 props는 직렬화 가능해야 합니다. 함수(서버 함수 제외), 클래스 인스턴스는 넘길 수 없습니다.
- `use server`는 서버 컴포넌트의 표시가 아니라 **서버 함수**의 표시입니다. 글쓰기·좋아요 같은 변경은 서버 함수를 폼 액션으로 연결합니다(자세히는 05편).

**경계 판단 기준:** 이 컴포넌트에 `useState`, 이벤트 핸들러, 브라우저 API가 필요한가. 필요하면 클라이언트로 두되 가능한 가장 작은 조각만 클라이언트로 만들고, 필요 없으면 서버에 둡니다. 페이지 최상단에 `use client`를 붙이면 그 아래 전체가 클라이언트 번들에 포함됩니다.

**서버 전용 코드의 보호:** DB 접근 모듈에 `server-only` 패키지를 import하면 실수로 클라이언트 경계에서 가져올 때 빌드가 실패합니다. 비밀 값이 클라이언트 번들로 새는 사고를 막습니다(자세히는 23편).

**검증:**

- 서버 컴포넌트에 `useState`를 넣으면 빌드에서 에러가 나는지 확인합니다. 경계가 도구로 강제됩니다.
- 번들 분석(26편)으로 마크다운·DB 라이브러리가 클라이언트 청크에 없는지 봅니다.
- 네트워크 탭에서 RSC 페이로드가 스트리밍되는지, 댓글이 본문보다 늦게 도착해도 본문이 먼저 그려지는지 봅니다.
- 클라이언트 컴포넌트로 넘기는 props에 직렬화 불가능한 값이 없는지 경고를 확인합니다.

**RSC와 SSR의 차이:** SSR은 같은 컴포넌트를 서버에서 HTML로도 그리고 클라이언트에서 다시 실행(Hydration)합니다. 서버 컴포넌트는 서버에서만 실행되고 Hydration되지 않습니다. 둘은 대체 관계가 아니라 함께 쓰며, 클라이언트 컴포넌트도 서버에서 HTML로 렌더됩니다(자세히는 04편).

**흔한 실수:** 상호작용이 한 군데뿐인데 페이지 전체에 `use client`를 붙이는 것, 클라이언트 컴포넌트에서 서버 컴포넌트를 `import`하는 것, 서버 컴포넌트에서 받은 비밀 값을 props로 클라이언트에 넘기는 것입니다.

## Compiler 적용

**요구:** 목록 화면이 느린 기존 앱. 수동으로 `memo`·`useMemo`를 곳곳에 넣은 코드를 정리하지 않고 React Compiler를 도입하려 한다.

**경계 설계:** 컴파일러의 경계는 **Rules of React를 지키는가**입니다. React Compiler는 빌드 시점에 컴포넌트와 값을 자동으로 메모이제이션하는 도구이고, 규칙을 지키는 코드를 전제로 합니다. 규칙을 어긴 컴포넌트는 최적화 대상에서 빠지거나 의도와 다르게 동작할 수 있습니다.

**도입 순서:** 한 번에 전체를 켜지 않고 점진적으로 넓힙니다(자세히는 07편, 08편).

| 단계 | 방법 | 확인할 것 |
|------|------|-----------|
| 1. 진단 | ESLint의 컴파일러 규칙으로 위반 찾기 | props·state 변경, 렌더 중 부수 효과 |
| 2. 좁게 켜기 | 디렉터리 단위(Babel `overrides`) 또는 `compilationMode: 'annotation'` | 선택한 범위만 컴파일 |
| 3. 선택 적용 | 함수 첫 줄 `"use memo"`로 옵트인, 문제 컴포넌트는 `"use no memo"`로 제외 | 제외 사유 기록 |
| 4. 실험 | `gating`으로 런타임 플래그에 따라 켜고 끄기(A/B) | 실제 지표 비교 |
| 5. 확대 | 범위 확장 후 전체 | 회귀 없음 |

```js
// babel.config.js: 옵트인 모드
plugins: [
  ['babel-plugin-react-compiler', {
    compilationMode: 'annotation',
  }],
],
```

```jsx
function TodoList({ todos }) {
  'use memo' // 이 함수만 컴파일
  // ...
}
```

**기존 메모이제이션:** 코드에 있는 `memo`, `useMemo`, `useCallback`은 바로 지우지 않습니다. 지우면 컴파일 결과가 달라질 수 있으므로 지우기 전에 측정하며 확인합니다. 새 코드는 컴파일러에 맡기되 `useMemo`·`useCallback`은 탈출구로 남기고, 값이 Effect의 의존성으로 쓰여 안정적인 참조가 필요하면 계속 씁니다. 컴파일러 지원 React 버전은 17, 18, 19입니다.

**검증:**

- React DevTools에서 컴파일된 컴포넌트에 표시되는 배지(Memo ✨)로 컴파일 여부를 확인합니다.
- Profiler로 적용 전후 같은 시나리오를 측정합니다. `actualDuration`(최적화가 적용된 렌더 시간)과 `baseDuration`(최적화 없을 때 추정치)의 차이를 봅니다.
- 컴파일 이후 기존 테스트와 E2E가 모두 통과하는지 확인합니다.
- 속도가 이미 충분한 컴포넌트까지 컴파일해 얻는 이득은 작습니다. 병목이 어디인지부터 측정합니다.

**흔한 실수:** 컴파일러를 켜면 렌더 중 객체 변경이나 외부 변수 수정 같은 규칙 위반이 해결된다고 생각하는 것(위반이 컴파일을 건너뛰게 만듦), 적용 효과를 측정하지 않고 모든 `useMemo`를 일괄 삭제하는 것입니다.

## Design System

**요구:** 두 앱이 공유하는 `Button`, `Input`, `Dialog` 패키지. 접근성이 기본으로 지켜지고, 앱이 외형을 바꿀 수 있으며, 버전 단위로 배포한다.

**계층과 경계:** 디자인 시스템은 위로 갈수록 구체적이고 아래로 갈수록 규칙에 가깝습니다(자세히는 22편).

| 계층 | 내용 | 경계의 의미 |
|------|------|-------------|
| 토큰 | 색·간격·글꼴(CSS 변수) | 값의 단일 출처 |
| 프리미티브 | 스타일 없는 동작·접근성(Headless) | 키보드·ARIA 책임 |
| 컴포넌트 | 토큰과 프리미티브를 조합한 스타일 컴포넌트 | 앱이 쓰는 공개 API |
| 문서 | Storybook 스토리 | 상태별 명세 |

**공개 API 설계:** 패키지 밖으로 내보낸 것만 약속입니다. 내부 구현(프리미티브, 헬퍼)은 export하지 않아 바꿀 자유를 남깁니다(자세히는 10편).

```text
packages/ui/src
├─ tokens.css          (CSS 변수)
├─ primitives/         (내부, export 안 함)
├─ button/Button.tsx
├─ dialog/Dialog.tsx   (Root, Trigger, Content 합성)
└─ index.ts            (공개 export 목록)
```

- `Dialog`는 `Root`·`Trigger`·`Content`로 쪼갠 합성(Compound) 구조로 두어 앱이 구성을 바꿀 수 있게 합니다(자세히는 12편). 열림 상태는 제어·비제어 둘 다 지원합니다.
- 외형 변경은 variant props와 `className` 병합으로 허용하고, 접근성 동작(포커스 이동, `Esc`, ARIA)은 컴포넌트 안에서 보장해 앱이 깨뜨리지 못하게 합니다(자세히는 13편).
- 앱 코드 변경 없이 내부를 바꿀 수 있는 변경은 패치, 기능 추가는 마이너, 공개 API 변경은 메이저입니다. 버전은 changesets 같은 도구로 관리합니다(자세히는 26편).

**검증:** 스토리가 곧 명세이자 테스트입니다.

```tsx
export const Toggles: Story = {
  args: { label: 'Mute' },
  play: async ({ canvasElement }) => {
    const canvas = within(canvasElement)
    const button = canvas.getByRole('button')
    await userEvent.click(button)
    await expect(button).toHaveAttribute(
      'aria-pressed', 'true')
  },
}
// expect, userEvent, within은 'storybook/test'에서 import
```

- 상태마다 스토리(기본, 비활성, 에러, 로딩)를 만들어 외형 회귀를 비교합니다.
- 위 `Toggles`처럼 `play` 함수로 상호작용을 검증하고, 접근성 애드온(`@storybook/addon-a11y`, axe-core 기반)의 `parameters.a11y.test`를 `'error'`로 두면 위반이 테스트 실패가 됩니다. 기존 컴포넌트는 `'todo'`로 두고 하나씩 고칩니다. 자동 검사가 잡는 것은 일부이므로 키보드·스크린 리더 확인이 따로 필요합니다(자세히는 20편).
- 소비하는 앱에서 타입 검사와 빌드로 공개 API 호환을 확인합니다.

**흔한 실수:** 앱이 내부 모듈을 직접 import하게 두는 것, 접근성을 앱의 책임으로 넘기는 것, props를 끝없이 늘려 `variant` 조합이 폭발하는 것입니다. 스타일링 도구는 디자인 시스템의 핵심이 아닙니다.

## 테스트 포함 CRUD

**요구:** 사용자 목록 화면. 목록 조회, 추가, 수정, 삭제. 로딩·에러·빈 상태를 처리하고, 각 동작을 테스트로 보장한다.

**테스트 경계:** 같은 동작을 모든 층에서 검증하지 않고, 층마다 맡을 것을 나눕니다(자세히는 중급 34편, 35편, 21편).

| 대상 | 층 | 도구 |
|------|----|------|
| 검증 함수, Reducer | 단위 | Vitest |
| 목록·추가·삭제 흐름, 에러·빈 상태 | 컴포넌트 | Testing Library + MSW |
| 로그인 후 추가해 목록에서 확인하는 핵심 흐름 | E2E | Playwright |
| 라벨·키보드·역할 | 컴포넌트·스토리 | 쿼리, axe |

**네트워크 경계:** 컴포넌트 테스트에서 `fetch`나 훅을 직접 모킹하지 않고 MSW로 네트워크 계층에서 가로챕니다. 컴포넌트와 데이터 라이브러리는 실제 코드를 그대로 쓰고 서버 응답만 가짜입니다. 구현을 바꿔도 테스트가 깨지지 않습니다.

```tsx
test('adds a user', async () => {
  const body = { id: 1, name: 'Kim' }
  server.use(http.post('/api/users', () =>
    HttpResponse.json(body, { status: 201 }),
  ))
  render(<UsersPage />)
  await user.type(screen.getByLabelText('Name'), 'Kim')
  const add = screen.getByRole('button', { name: 'Add' })
  await user.click(add)
  expect(await screen.findByText('Kim')).toBeVisible()
})
```

- `server.use`는 그 테스트 안에서만 쓰는 응답입니다. 기본 핸들러는 공통으로 두고, 각 테스트 뒤 `server.resetHandlers()`로 원복합니다.
- 실패 시나리오는 같은 방식으로 500 응답을 주고 에러 알림이 나타나는지 확인합니다. 에러 경로 테스트가 없는 CRUD는 반쪽입니다.

**쿼리 선택 순서:** 사용자가 화면을 찾는 방식과 가깝게 고릅니다. `getByRole`, `getByLabelText`, `getByPlaceholderText`, `getByText`, `getByDisplayValue` 순서이고 `getByTestId`는 마지막 수단입니다. 역할 쿼리가 통과하면 접근 가능한 이름이 올바르다는 검증이 함께 됩니다.

| 변형 | 없을 때 | 용도 |
|------|---------|------|
| `getBy` | 에러를 던짐 | 지금 있어야 하는 요소 |
| `queryBy` | `null` 반환 | 없어야 하는 요소 확인 |
| `findBy` | 기다린 뒤 에러 | 비동기로 나타나는 요소 |

**상태 분기를 빠뜨리지 않기:** 테스트 케이스 목록이 곧 설계 체크리스트입니다. 처음 로딩 중 스켈레톤, 성공 시 목록, 빈 목록 안내, 조회 실패와 재시도, 추가 중 버튼 비활성, 추가 실패 메시지, 삭제 전 확인과 삭제 후 목록 갱신입니다(자세히는 17편).

**검증 범위의 한계:** 테스트가 통과해도 실제 브라우저의 레이아웃이나 실제 서버 계약은 보장되지 않습니다. 서버와의 계약(응답 형태)은 타입 공유나 스키마 검증, 계약 테스트로 따로 확인하고, 핵심 흐름은 E2E 몇 개로 남깁니다.

**흔한 실수:** 구현 세부(내부 state, 함수 호출 횟수)를 검증하는 것, 모킹이 실제 서버와 어긋나 있는 것, `getByTestId`에 기대 접근성 문제를 못 잡는 것, 비동기 결과를 `getBy`로 즉시 찾아 간헐적으로 실패하는 것입니다.

## 성능 개선

**요구:** 상품 목록 화면에서 검색어를 입력하면 글자가 늦게 나타나고(입력 지연), 첫 로딩이 느리다.

**접근:** 추측으로 `memo`를 흩뿌리지 않고 **측정 → 원인 → 처방 → 재측정** 순서를 지킵니다(자세히는 중급 20편). 처방은 비용이 작은 것부터 적용합니다.

**측정 도구와 지표:**

| 증상 | 지표 | 도구 |
|------|------|------|
| 입력·클릭 반응이 느림 | INP(200밀리초 이하가 좋음) | 필드 수집, DevTools 성능 탭 |
| 첫 화면이 느림 | LCP(2.5초 이내가 좋음) | Lighthouse, 필드 수집 |
| 어떤 컴포넌트가 오래 렌더되나 | 렌더 시간 | React DevTools Profiler, `Profiler` 컴포넌트 |
| 번들이 큰가 | 청크 크기 | 번들 분석(26편) |

- `Profiler`의 `onRender`는 `actualDuration`(실제 렌더 시간)과 `baseDuration`(최적화 없을 때 추정 시간)을 줍니다. 운영 빌드에서는 프로파일링이 기본으로 꺼져 있어 별도 프로파일링 빌드가 필요하고, 측정 자체에 비용이 있습니다.
- INP는 랩에서 측정할 수 없으므로 필드 데이터와 DevTools로 실제 상호작용을 재현합니다.

**원인과 처방 사다리:**

| 원인 | 처방 | 확인 방법 |
|------|------|-----------|
| 검색어 state가 너무 높아 화면 전체가 렌더됨 | state를 입력 컴포넌트로 내리거나 목록을 분리 | Profiler에서 렌더되는 컴포넌트 수 |
| 입력마다 큰 목록 재렌더 | `useDeferredValue`·Transition으로 목록 갱신을 뒤로 미룸 | 입력이 즉시 반영되는지 |
| 수천 행을 한 번에 렌더 | 가상화(보이는 행만 렌더) | DOM 노드 수 |
| 같은 props인데 자식이 재렌더 | `memo`나 Compiler(08편) | 자식 렌더 횟수 |
| 첫 로딩의 JS가 큼 | 라우트·무거운 라이브러리를 `lazy`로 분리 | 번들 분석, LCP |
| LCP 이미지가 늦게 시작 | 이미지 우선 로딩, 크기 지정 | LCP 요소 확인 |

```jsx
const [query, setQuery] = useState('')
const deferred = useDeferredValue(query)
const onChange = (e) => setQuery(e.target.value)
return (
  <>
    <input value={query} onChange={onChange} />
    <ProductList query={deferred} />
  </>
)
```

- 입력창은 즉시 갱신되는 `query`를 쓰고, 무거운 목록은 지연된 `deferred`를 씁니다. 목록 렌더가 중단 가능해서 새 입력이 오면 진행 중인 렌더를 버립니다(자세히는 중급 10편, 09편).
- `ProductList`를 `memo`로 감싸야 의미가 있습니다. 지연 값이 그대로인 동안 목록 렌더를 건너뛰기 때문입니다.
- 가상화는 목록이 정말 긴 경우의 처방이고, 수십 개를 렌더하는 목록에는 필요하지 않습니다(자세히는 중급 21편).

**검증:** 같은 시나리오(같은 데이터, 같은 입력, 같은 기기·네트워크 제한)로 전후를 측정해 수치를 비교합니다. 개선 효과가 측정 오차 안이면 그 처방은 되돌립니다. 운영에서는 Web Vitals를 계속 수집해 회귀를 감지하고(자세히는 26편), 성능 예산(번들 크기, INP 목표)을 CI에서 확인합니다.

**흔한 실수:** 측정 없이 `useMemo`를 남발하는 것(복잡도만 늘고 효과는 없음), 개발 모드(StrictMode의 이중 렌더, 최적화 없는 빌드)의 수치로 판단하는 것, 한 번 측정한 수치를 일반화하는 것, 입력 지연의 원인이 렌더가 아니라 네트워크나 레이아웃일 수 있음을 놓치는 것입니다.

## 핵심 정리

- 설계안은 로딩(Suspense), 실패(에러 경계), 실행 위치(`use client`), 출력 일치(Hydration), 공개 범위(export)의 경계가 어디에 있는지로 읽는다.
- Suspense는 Promise를 읽는 `use`, `lazy`, 스트리밍에서 작동하고 Effect의 데이터 요청은 감지하지 못하며, 에러 경계를 바깥에 짝지어 영역 단위로 끊는다.
- SSR은 서버와 클라이언트 첫 출력이 같아야 하고, 시각·난수·브라우저 API 의존 부분은 클라이언트에서만 렌더하거나 서버에서 값을 고정해 넘긴다.
- Server Component는 서버 전용으로 기본값으로 두고, 상호작용이 필요한 말단만 `use client`로 만들며, 서버 UI는 `children`으로 넘긴다.
- Compiler는 진단, 좁은 범위 적용, 측정, 확대 순서로 도입하고 기존 메모이제이션은 측정 후에 정리한다.
- 테스트는 층마다 맡을 것을 나눠 네트워크는 MSW, 쿼리는 역할 우선으로 하고, 성능은 측정, 원인, 처방, 재측정 순서로 개선한다.

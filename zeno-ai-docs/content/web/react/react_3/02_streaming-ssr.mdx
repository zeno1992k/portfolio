## Streaming Rendering

스트리밍 렌더링(Streaming Rendering)은 서버가 HTML 전체가 완성되기를 기다리지 않고, 준비된 부분부터 조각으로 나눠 보내는 방식입니다. React 18에서 Suspense와 결합해 도입되었습니다.

`renderToString`은 데이터가 모두 준비돼야 응답을 시작합니다(01편). React 17까지의 서버 렌더링에는 세 가지 병목이 있었습니다.

| 병목 | 내용 |
|------|------|
| 데이터 | 가장 느린 데이터가 도착해야 HTML 전체가 나간다 |
| 코드 로딩 | 모든 컴포넌트의 JS가 로드돼야 Hydration을 시작한다 |
| Hydration | 전체가 Hydration돼야 어디든 클릭할 수 있다 |

스트리밍 SSR은 이 병목을 Suspense 경계 단위로 쪼갭니다.

```jsx
<Layout>
  <Post />
  <Suspense fallback={<Spinner />}>
    <Comments />
  </Suspense>
</Layout>
```

1. 서버는 `Layout`과 `Post`, 그리고 `Comments` 자리의 `fallback`(`Spinner`)을 먼저 보낸다.
2. 댓글 데이터가 준비되면 `Comments`의 HTML을 추가 조각으로 보낸다.
3. 이 조각에는 `fallback`을 새 내용으로 바꾸는 작은 스크립트가 딸려 온다.
4. 브라우저는 JS 번들이 로드되기 전에도 교체된 내용을 보여 준다.

react.dev는 스트리밍이 브라우저에서 React가 로드되거나 앱이 상호작용 가능해지기를 기다리지 않는다고 설명합니다. HTML 내용은 어떤 `script` 태그가 로드되기도 전에 점진적으로 드러납니다.

- 첫 바이트를 보내는 시점이 가장 느린 데이터에 묶이지 않으므로 TTFB와 FCP가 좋아집니다(01편의 지표).
- 스트리밍 API는 문서 전체(`html` 태그 포함)를 렌더링한다고 가정합니다. 클라이언트는 `hydrateRoot(document, <App />)`로 이어받습니다.
- 개념은 같고 환경에 맞는 API가 다릅니다(아래 "renderToPipeableStream", "renderToReadableStream").

## Shell

Shell은 앱에서 어떤 `Suspense` 경계에도 속하지 않은 부분입니다. 사용자가 가장 먼저 보게 될 로딩 상태를 정하는 최소 화면입니다.

```jsx
function ProfilePage() {
  return (
    <ProfileLayout>        {/* shell */}
      <ProfileCover />     {/* shell */}
      <Suspense fallback={<PostsGlimmer />}>
        <Posts />          {/* shell 밖 */}
      </Suspense>
    </ProfileLayout>
  )
}
```

- Shell에는 경계 밖의 컴포넌트와 각 경계의 `fallback`이 들어갑니다.
- Shell이 렌더링을 마치면 스트리밍을 시작할 수 있습니다. Node에서는 `onShellReady`, Web Streams에서는 반환된 Promise가 해결되는 시점입니다.
- Shell에서 오류가 나면 보낼 HTML이 없으므로 서버가 직접 대체 응답을 만들어야 합니다(아래 "Error Handling").
- 상태 코드와 헤더는 스트리밍 시작 전에만 정할 수 있습니다. Shell이 나간 뒤에는 상태 코드를 바꿀 수 없습니다.
- 경계를 어디에 두느냐가 첫 화면의 크기를 정합니다. 경계가 하나도 없으면 Shell이 앱 전체이므로 스트리밍 효과가 없습니다.

## Suspense 단위 Streaming

스트리밍의 단위는 Suspense 경계입니다. 경계 하나가 서버에서 먼저 `fallback`으로 나가고, 내용이 준비되면 그 자리로 교체됩니다.

```jsx
<Suspense fallback={<HeaderSkeleton />}>
  <Header />
  <Suspense fallback={<FeedSkeleton />}>
    <Feed />
  </Suspense>
</Suspense>
```

- 중첩된 경계는 더 세밀한 로딩 순서를 만듭니다. 바깥 경계가 먼저 나가고, 안쪽 경계는 자기 내용이 준비될 때 나갑니다.
- 경계 안의 컴포넌트가 하나도 중단되지 않아도 HTML이 충분히 크면 경계가 스트리밍으로 나뉠 수 있습니다. 내용이 전송되는 데 시간이 걸리기 때문입니다.
- 클라이언트의 Suspense 동작은 중급 11편에서 다뤘습니다. 서버에서도 같은 경계가 쓰입니다.

React 19.2는 서버에서 렌더링된 Suspense 경계의 공개를 짧은 시간 동안 묶어서(batching) 보여 줍니다. 이전에는 내용이 준비되는 즉시 `fallback`을 대체했습니다. 이제 클라이언트 렌더링과 비슷하게 더 많은 내용을 한꺼번에 드러내며, `ViewTransition` 애니메이션과도 맞습니다. 페이지 로드가 2.5초(LCP 기준)에 가까워지면 묶기를 멈춥니다.

**흔한 실수:** 한 화면 전체를 경계 하나로 감싸는 것입니다. 가장 느린 데이터가 전체 화면의 공개를 늦춥니다. 독립적으로 로드되는 영역마다 경계를 둡니다.

## renderToPipeableStream

`renderToPipeableStream`은 Node.js 환경에서 React 트리를 Node 스트림으로 렌더링하는 API입니다. `react-dom/server`에서 가져옵니다.

```jsx
import { renderToPipeableStream } from 'react-dom/server'

app.use('/', (request, response) => {
  const { pipe } = renderToPipeableStream(<App />, {
    bootstrapScripts: ['/main.js'],
    onShellReady() {
      response.setHeader('content-type', 'text/html')
      pipe(response)
    },
  })
})
```

반환값은 두 메서드를 가진 객체입니다.

| 반환 | 역할 |
|------|------|
| `pipe` | HTML을 Node.js Writable 스트림(응답 객체)으로 흘려 보낸다 |
| `abort` | 서버 렌더링을 중단하고 나머지를 클라이언트에 맡긴다 |

주요 옵션은 다음과 같습니다.

| 옵션 | 용도 |
|------|------|
| `bootstrapScripts` | 응답에 넣을 `script` 태그의 URL 배열 |
| `bootstrapModules` | `type="module"` 스크립트로 넣을 URL 배열 |
| `bootstrapScriptContent` | 인라인 스크립트 내용 |
| `onShellReady` | Shell 렌더링 완료. 보통 여기서 `pipe`를 호출 |
| `onShellError` | Shell 렌더링 실패 |
| `onAllReady` | Shell과 모든 경계의 렌더링 완료. 크롤러·정적 생성에 사용 |
| `onError` | 복구 가능 여부와 상관없이 서버에서 난 모든 오류 |
| `identifierPrefix` | `useId` ID의 접두사. `hydrateRoot`와 같아야 한다 |
| `nonce` | `script-src` CSP용 nonce |
| `onHeaders` | 리소스 힌트(preconnect, preload)를 헤더로 받는 콜백 |
| `progressiveChunkSize` | 조각 크기(바이트). 기본은 내부 휴리스틱 |
| `importMap` | `imports`·`scopes`를 가진 import map 객체 |
| `formState` | Server Function 폼 제출에서 온 폼 상태 |

- `onShellReady` 안에서 `pipe`를 부르면 Shell이 완성된 뒤에 스트리밍이 시작됩니다.
- Node 전용 API입니다. Web Streams 환경에는 `renderToReadableStream`을 씁니다.

## renderToReadableStream

`renderToReadableStream`은 Web Streams 환경에서 React 트리를 `ReadableStream`으로 렌더링하는 API입니다. Deno, 엣지 런타임, 브라우저 호환 런타임이 대상입니다.

```jsx
import { renderToReadableStream } from 'react-dom/server'

async function handler(request) {
  const stream = await renderToReadableStream(<App />, {
    bootstrapScripts: ['/main.js'],
  })
  return new Response(stream, {
    headers: { 'content-type': 'text/html' },
  })
}
```

- 반환은 Promise입니다. Shell 렌더링에 성공하면 스트림으로 해결되고, 실패하면 거부됩니다.
- 반환된 스트림에는 `allReady` Promise가 붙어 있습니다. 모든 렌더링이 끝나면 해결됩니다. `onAllReady`에 대응합니다.
- 중단은 `signal` 옵션(`AbortSignal`)으로 합니다.
- `bootstrapScripts`, `bootstrapModules`, `bootstrapScriptContent`, `identifierPrefix`, `nonce`, `onError`, `onHeaders`, `progressiveChunkSize`, `importMap`, `formState`는 Node 쪽과 같은 뜻입니다.
- `onShellReady`, `onShellError`, `onAllReady` 콜백이 없는 이유는 Promise와 `allReady`가 같은 구실을 하기 때문입니다.

## Node Stream과 Web Stream

두 API의 차이는 스트림 객체의 종류와 오류를 받는 방식입니다. 렌더 내용은 같습니다.

| 항목 | `renderToPipeableStream` | `renderToReadableStream` |
|------|--------------------------|--------------------------|
| 스트림 종류 | Node.js 스트림 | Web Streams(`ReadableStream`) |
| 대상 환경 | Node.js | Deno, 엣지 런타임, 브라우저 호환 런타임 |
| 시작 시점 | `onShellReady`에서 `pipe` | `await`가 끝나면 스트림 반환 |
| Shell 오류 | `onShellError` | Promise 거부(`catch`) |
| 전부 준비됨 | `onAllReady` | `stream.allReady` |
| 중단 | 반환된 `abort()` | `signal` 옵션 |
| 반환 | `{ pipe, abort }` | `ReadableStream` |

- React 19.2부터 Node.js에서도 Web Streams API(`renderToReadableStream`, `prerender`, `resume`, `resumeAndPrerender`)를 쓸 수 있습니다.
- 그래도 Node.js에서는 Node 스트림 API(`renderToPipeableStream`, `resumeToPipeableStream`, `prerenderToNodeStream`, `resumeAndPrerenderToNodeStream`)를 권장합니다. 성능과 압축 지원이 더 낫다고 react.dev가 밝힙니다.

## Selective Hydration

선택적 Hydration(Selective Hydration)은 Suspense 경계 단위로 따로따로 Hydration하고, 사용자가 상호작용한 부분을 먼저 처리하는 방식입니다. React 18에서 스트리밍 SSR과 함께 들어왔습니다.

```jsx
const Comments = lazy(() => import('./Comments.js'))

<Suspense fallback={<Spinner />}>
  <Comments />
</Suspense>
```

- `lazy`로 나눈 컴포넌트도 서버 HTML에는 렌더링돼 들어갑니다. 코드가 도착하기 전에도 나머지 페이지는 Hydration됩니다.
- 한 경계의 Hydration이 다른 경계를 막지 않습니다.
- 아직 Hydration되지 않은 영역을 사용자가 클릭하면 React가 그 영역을 먼저 Hydration합니다. 이 작업은 이벤트의 캡처 단계에서 동기적으로 이뤄집니다. 나머지 영역은 계속 뒤에서 Hydration됩니다.
- react.dev는 이 최적화가 스트리밍 서버 렌더링 API와 Suspense에 통합되어 있다고 설명합니다.
- Hydration 자체의 규칙은 03편에서 다룹니다.

## Progressive Hydration

점진적 Hydration(Progressive Hydration)은 앱을 한꺼번에 깨우지 않고 조각 단위로 순차적으로 상호작용 가능하게 만드는 전략입니다. web.dev는 필수가 아닌 컴포넌트를 미루고 메인 스레드 막힘을 줄이는 방식이라고 설명합니다.

- React에서는 Suspense 경계와 `lazy`가 이 전략의 구현 단위입니다. 선택적 Hydration이 그 수단입니다.
- 정리하면 Progressive Hydration은 목표(점진적으로 상호작용 가능하게 만들기)이고, Selective Hydration은 React가 그 목표를 이루는 구체적 동작(경계별 Hydration과 상호작용 우선순위)입니다.
- 전통적 SSR의 "한 번에 전부 Hydration"과 비교하면 다음과 같습니다.

| 항목 | 한 번에 Hydration | Progressive·Selective |
|------|-------------------|-----------------------|
| 시작 조건 | 모든 컴포넌트의 JS가 로드됨 | 경계마다 자기 코드가 로드되면 |
| 클릭 가능 시점 | 전체 완료 후 | 경계마다 완료되는 대로 |
| 사용자 클릭 | 대기 | 클릭한 영역을 먼저 Hydration |
| 큰 작업의 메인 스레드 점유 | 한 덩어리 | 조각으로 분산 |

## Abort

`abort`는 서버 렌더링을 중단하고 아직 끝나지 않은 부분을 클라이언트에 맡깁니다. 서버에서 오래 걸리는 렌더링에 제한 시간을 걸 때 씁니다.

```jsx
const { pipe, abort } = renderToPipeableStream(<App />, {
  // ...
})

setTimeout(() => {
  abort() // 10초 뒤 서버 렌더링 포기
}, 10000)
```

- 동작은 다음과 같습니다. React는 남은 `fallback`을 HTML로 내보내고, 나머지 렌더링은 클라이언트에서 시도합니다.
- Web Streams에서는 `AbortController`의 `signal`을 옵션에 넘기고 `controller.abort()`를 호출합니다.
- 중단되는 것은 서버 렌더링뿐이고 앱이 실패한 것은 아닙니다. 클라이언트가 같은 컴포넌트를 렌더링해서 내용을 채웁니다. 그 렌더링이 실패하면 가장 가까운 Error Boundary가 처리합니다.
- `prerender` 계열은 `signal`로 중단하면 끝나지 않은 부분이 `postponed`로 남습니다(아래 "prerender와 resume").

**흔한 실수:** 제한 시간을 걸지 않는 것입니다. 느린 데이터 소스 하나가 응답 스트림을 끝까지 열어 둡니다.

## Error Handling

스트리밍 SSR의 오류는 어디서 났느냐에 따라 처리가 갈립니다. Shell 안이면 응답 자체가 불가능하고, Shell 밖(Suspense 경계 안)이면 일부만 클라이언트에 넘깁니다.

| 오류 위치 | 서버 동작 | 호출되는 콜백 |
|-----------|-----------|---------------|
| Shell 밖(경계 안) | 그 경계의 `fallback`을 HTML로 내보내고 서버 렌더링을 포기, 클라이언트가 재시도 | `onError`(Shell은 정상이라 `onShellReady`도 호출) |
| Shell 안 | 보낼 HTML이 없다. 서버가 대체 응답을 만들어야 함 | `onShellError`, `onError` |

경계 안 오류의 후속 처리는 다음 순서입니다.

1. 서버는 가장 가까운 Suspense의 `fallback`을 서버 HTML에 담는다. 사용자는 처음에 스피너를 본다.
2. 클라이언트가 JS를 로드하면 같은 컴포넌트를 다시 렌더링한다.
3. 클라이언트 렌더링이 성공하면 사용자는 오류를 보지 못한다.
4. 클라이언트에서도 실패하면 가장 가까운 Error Boundary(중급 13편)가 처리한다.

Shell 오류와 로깅은 다음과 같이 씁니다.

```jsx
const { pipe } = renderToPipeableStream(<App />, {
  onShellReady() {
    response.statusCode = 200
    response.setHeader('content-type', 'text/html')
    pipe(response)
  },
  onShellError(error) {
    response.statusCode = 500
    response.send('<h1>Something went wrong</h1>')
  },
  onError(error) {
    console.error(error) // 로그 수집
  },
})
```

- `onError`는 서버에서 난 모든 오류에 호출되므로 로깅 지점입니다. 복구 가능한 오류도 포함합니다.
- 상태 코드는 스트리밍 시작 전에만 정할 수 있어서 `pipe`를 호출하기 전에 설정합니다. 경계 안의 오류는 이미 200을 보낸 뒤일 수 있습니다.
- 오류에 따라 상태 코드를 다르게 하려면 `onError`에서 플래그를 세우고, 크롤러에는 `onAllReady`에서 `pipe`하면서 `didError`로 500을 정합니다.
- Web Streams에서는 Shell 오류가 Promise 거부로 나타나므로 `try`/`catch`로 대체 응답을 만듭니다.
- 렌더링 중 던진 오류로 서버 렌더링을 건너뛰는 방법은 03편의 Client-only Content와 연결됩니다. 19.3의 `use(browser())`는 같은 목적의 정식 API입니다.

크롤러나 정적 생성에서는 점진적 공개 대신 완성본이 필요합니다.

```jsx
onAllReady() {
  if (isCrawler) {
    response.statusCode = didError ? 500 : 200
    pipe(response)
  }
},
```

사용자에게는 `onShellReady`에서, 크롤러에게는 `onAllReady`에서 `pipe`를 호출하는 식으로 나눕니다.

## prerender와 resume

`prerender`는 정적 HTML을 미리 만들고, `resume`은 미리 만든 결과를 이어받아 나머지를 요청 시점에 렌더링하는 API입니다. 둘을 합친 흐름을 부분 프리렌더링(Partial Pre-rendering, PPR)이라 부릅니다. React 19.2에서 추가되었습니다.

`react-dom/static`의 `prerender`는 스트리밍 API와 달리 모든 데이터와 Suspense 경계가 해결될 때까지 기다리고 결과를 돌려줍니다. SSG용입니다.

```jsx
import { prerender } from 'react-dom/static'

const { prelude, postponed } = await prerender(<App />, {
  signal: controller.signal,
})
```

| 반환 | 내용 |
|------|------|
| `prelude` | 완성된 HTML의 Web Stream. 스트림으로 보내거나 문자열로 읽는다 |
| `postponed` | 끝나지 않은 부분을 이어갈 JSON 직렬화 가능한 불투명한 객체. 전부 완성되면 `null` |

- `signal`로 프리렌더를 중단하면 아직 해결되지 않은 부분은 보류(postponed)되고, 그 상태가 `postponed`에 담깁니다.
- `postponed`는 Redis, 파일, S3 같은 저장소에 보관할 수 있습니다.
- `nonce` 옵션은 없습니다. nonce는 요청마다 달라야 해서 프리렌더에 맞지 않습니다.

이어서 렌더링하는 방법은 두 가지입니다.

```jsx
// 요청 시점: 나머지를 SSR로 스트리밍
const postponed = await getPostponedState(request)
const stream = await resume(<App />, postponed)

// 다시 정적 생성: 나머지를 SSG로 마무리
const { prelude } = await resumeAndPrerender(<App />, postponed)
```

| API | 환경 | 결과 |
|-----|------|------|
| `resume` | Web Streams(`react-dom/server`) | 이어서 스트리밍 SSR |
| `resumeToPipeableStream` | Node 스트림(`react-dom/server`) | 이어서 스트리밍 SSR |
| `resumeAndPrerender` | Web Streams(`react-dom/static`) | 이어서 프리렌더(SSG) |
| `resumeAndPrerenderToNodeStream` | Node 스트림(`react-dom/static`) | 이어서 프리렌더(SSG) |
| `prerender` | Web Streams | 정적 프리렌더 |
| `prerenderToNodeStream` | Node 스트림 | 정적 프리렌더 |

- `resume`은 프리렌더 때 쓴 `reactNode`와 같은 노드를 받습니다. 루트부터 다시 렌더링하면서, 완전히 프리렌더된 컴포넌트는 건너뛰고 그렇지 않은 컴포넌트부터 렌더링합니다.
- `bootstrapScripts`, `bootstrapScriptContent`, `bootstrapModules`, `identifierPrefix`는 `resume`에 넘기지 않고 `prerender`에 넘깁니다. 같은 값이어야 합니다.
- `nonce`는 프리렌더에 스크립트를 넣지 않았을 때에만 `resume`에 넘깁니다.
- 흐름을 정리하면, 빌드나 캐시 시점에 정적 부분(Shell과 요청과 무관한 내용)을 프리렌더해 CDN에 올립니다. 요청이 오면 저장된 `postponed`로 `resume`해서 쿠키나 세션 같은 요청별 부분만 스트리밍합니다. 클라이언트는 `hydrateRoot`로 이어받습니다.
- 이 API들은 프레임워크가 감싸서 제공하는 경우가 많습니다. 프레임워크별 PPR 지원은 24편에서 비교 수준으로 다룹니다.

## 핵심 정리

- 스트리밍 SSR은 HTML을 Suspense 경계 단위로 나눠 보내며, 가장 느린 데이터가 첫 응답을 막지 않습니다.
- Shell은 경계 밖의 부분이고 완성되면 스트리밍을 시작할 수 있습니다. 상태 코드와 헤더는 그 전에만 정할 수 있습니다.
- Node에서는 `renderToPipeableStream`(`onShellReady`, `pipe`, `abort`), Web Streams에서는 `renderToReadableStream`(Promise, `allReady`, `signal`)을 씁니다. Node에서도 Node 스트림 API를 권장합니다.
- Selective Hydration은 경계별로 따로 Hydration하고 상호작용한 영역을 먼저 처리하며, Progressive Hydration이라는 전략을 React에서 구현하는 방식입니다.
- Shell 오류는 `onShellError`로 직접 응답하고, 경계 안 오류는 `fallback`을 내보낸 뒤 클라이언트가 재시도합니다.
- 19.2의 `prerender`가 정적 부분을 미리 만들고 `postponed`를 반환하면, `resume`이 요청 시점에 나머지를 이어서 렌더링합니다(PPR).

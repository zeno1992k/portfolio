## Props와 State

Props는 부모가 자식에게 넘기는 읽기 전용 입력이고, State는 컴포넌트가 스스로 기억하고 바꾸는 값입니다. 둘의 차이는 **누가 소유하고 누가 바꾸는가**입니다(자세히는 기초 05편, 09편).

| 항목 | Props | State |
|------|-------|-------|
| 소유자 | 부모 | 그 컴포넌트 |
| 변경 | 자식이 바꾸지 못함 | setter로 변경 |
| 변경 효과 | 부모가 다시 렌더링하며 새 값 전달 | 다시 렌더링 요청 |
| 용도 | 설정, 데이터 전달 | 시간에 따라 바뀌는 기억 |

값이 상태인지 판단하는 질문은 세 가지입니다. 시간이 지나도 변하지 않는가(그렇다면 상태 아님), 부모에게서 props로 받는가(그렇다면 상태 아님), 기존 state나 props로 계산할 수 있는가(그렇다면 상태 아님). 세 질문에 모두 해당하지 않을 때만 상태입니다(자세히는 기초 12편).

- 자식이 부모 값을 바꿔야 하면 부모가 `onChange` 같은 함수 props를 내려 줍니다(역방향 데이터 흐름).
- Props를 state의 초기값으로 복사하면 이후 props가 바뀌어도 state는 따라가지 않습니다. 의도한 경우만 씁니다.

**면접에서 묻는 방식:** "props와 state의 차이는?", "자식이 부모 state를 바꾸려면?"

## State Snapshot

State는 렌더마다 고정된 **스냅샷**입니다. setter는 현재 렌더의 변수를 바꾸지 않고 다음 렌더를 요청합니다. 이벤트 핸들러는 자신이 만들어진 렌더의 state 값을 닫아 둡니다(자세히는 기초 10편).

```jsx
function handleClick() {
  setCount(count + 1)
  alert(count) // 아직 이전 값
  setTimeout(() => alert(count), 3000) // 클릭 시점의 값
}
```

- 3초 사이에 컴포넌트가 다시 렌더링되어도 타이머의 `count`는 클릭 시점의 값입니다. 각 렌더가 자기 변수와 자기 핸들러를 가지기 때문입니다.
- 최신 값이 필요하면 updater 함수(`setCount((c) => c + 1)`)로 이전 값에서 계산하거나, 렌더와 무관한 최신 값은 `useRef`에 둡니다.
- 렌더 결과가 보여 주는 것은 항상 그 렌더의 state입니다. 비동기 코드 안에서 `state`를 읽을 때 "이 값은 어느 렌더의 것인가"를 묻습니다.

**면접에서 묻는 방식:** "`setCount(count + 1)`을 세 번 호출하면 얼마나 증가하는가?"(1입니다.)

## Batching

배칭(batching)은 한 이벤트 안의 여러 state 업데이트를 모아 한 번만 다시 렌더링하는 것입니다. React는 이벤트 핸들러의 코드가 모두 끝난 뒤 업데이트를 처리합니다.

```js
setNumber(number + 1) // number가 0일 때: 1로 교체
setNumber(number + 1) // 같은 스냅샷: 1로 교체
setNumber(number + 1) // 결과 1
```

```js
setNumber((n) => n + 1) // 큐에 쌓임: 0 → 1
setNumber((n) => n + 1) // 1 → 2
setNumber((n) => n + 1) // 결과 3
```

- 값을 직접 넘기면 "이 값으로 교체", 함수를 넘기면 "이전 결과로 계산"입니다. 이전 값에 의존하면 함수 형태를 씁니다.
- React 18부터 자동 배칭이라서 `setTimeout`, Promise, 네이티브 이벤트 안의 업데이트도 묶입니다. 묶지 않고 즉시 반영해야 할 때만 `flushSync`를 씁니다.
- 서로 다른 의도적 이벤트(두 번의 클릭)는 묶이지 않고 각각 처리됩니다.
- updater 함수는 순수해야 하고 부수 효과를 넣지 않습니다.

**면접에서 묻는 방식:** "배칭이란?", "React 18 이전과 달라진 점은?"

## key와 Identity

`key`는 형제 사이에서 항목의 정체성(identity)을 정하는 값이고, State는 컴포넌트 **종류와 트리 위치**에 묶입니다. 같은 위치에 같은 종류가 오면 state가 보존되고, 다른 종류가 오면 초기화됩니다(자세히는 기초 07편, 13편).

| 상황 | 결과 |
|------|------|
| 같은 위치, 같은 컴포넌트, props만 변경 | state 유지 |
| 같은 위치, 다른 컴포넌트 | state 초기화 |
| `key`가 바뀜 | 새 컴포넌트로 취급, state 초기화 |
| 리스트에서 `key`가 안정적인 id | 항목이 이동해도 state가 따라감 |
| 리스트에서 `key`가 인덱스 | 삭제·정렬 시 state가 엉뚱한 항목에 남음 |

```jsx
<Chat key={contact.id} contact={contact} /> // 대상 변경 시 초기화
```

- Effect로 state를 비우는 대신 `key`를 바꿔 초기화합니다.
- 컴포넌트 함수를 다른 컴포넌트 **안에서** 정의하면 렌더마다 새 타입이 되어 state가 매번 초기화됩니다. 항상 모듈 최상위에서 정의합니다.
- `key`는 렌더 사이에 안정적이어야 하고 렌더 중에 `Math.random()`으로 만들지 않습니다. 매번 바뀌면 전부 새로 마운트됩니다.

**면접에서 묻는 방식:** "리스트에 `key`가 필요한 이유는?", "인덱스를 `key`로 쓰면 무엇이 문제인가?"

## Effect가 필요한 경우

Effect는 렌더 결과를 **React 바깥의 시스템과 동기화**할 때 씁니다. 판단 질문은 하나입니다. **"이 코드는 컴포넌트가 화면에 표시되었기 때문에 실행되어야 하는가?"** 그렇다면 Effect이고, 사용자 상호작용 때문이라면 이벤트 핸들러입니다(자세히는 기초 20편, 22편).

| 필요한 경우 | 예 |
|-------------|----|
| 외부 시스템 동기화 | 채팅 연결, 서드파티 위젯, 브라우저 API(타이머, 구독) |
| 화면 표시에 따른 요청 | 페이지가 보일 때 분석 이벤트, 데이터 요청(정리 포함) |
| 외부 저장소 구독 | 단, `useSyncExternalStore`가 더 적합 |

```jsx
useEffect(() => {
  const conn = createConnection(roomId)
  conn.connect()
  return () => conn.disconnect() // 정리가 설정과 짝
}, [roomId])
```

- 정리 함수는 설정을 되돌립니다. 의존성이 바뀌면 이전 값으로 정리한 뒤 새 값으로 다시 설정합니다.
- 개발의 StrictMode는 설정 → 정리 → 설정을 한 번 더 실행해 정리가 빠졌는지 드러냅니다. 두 번 실행되어도 문제가 없게 씁니다.
- 데이터 요청은 경쟁 상태를 막는 무시(ignore) 플래그나 취소가 필요하고, 가능하면 데이터 라이브러리에 맡깁니다(자세히는 기초 23편, 중급 26편).
- 의존성 배열의 값은 Effect가 읽는 모든 반응형 값입니다. 린트 경고를 끄지 않습니다(자세히는 기초 21편).

**면접에서 묻는 방식:** "Effect는 언제 쓰는가?", "의존성 배열이 비면 무슨 뜻인가?"

## Effect가 필요 없는 경우

Effect로 state를 갱신하는 코드는 대부분 필요 없습니다. 렌더 중 계산하거나 이벤트 핸들러로 옮깁니다. Effect는 렌더 후 한 번 더 렌더링을 일으켜 느리고 값이 어긋나는 구간이 생깁니다.

| 하려는 일 | 대신 쓸 것 |
|-----------|------------|
| props·state에서 값 계산 | 렌더 중 계산 |
| 비싼 계산 캐시 | `useMemo` 또는 Compiler |
| props 변경 시 state 초기화 | `key` 바꾸기 |
| props 변경 시 일부 state 조정 | 렌더 중 이전 값과 비교해 조정 |
| 클릭·제출에 따른 처리 | 이벤트 핸들러 |
| 여러 핸들러의 공통 로직 | 함수로 추출 |
| 부모에게 변경 알림 | 같은 핸들러에서 부모 콜백 호출 |
| 자식이 가져온 데이터를 부모에게 | 부모가 가져와 내려 줌 |
| 연쇄 state 변경 | 핸들러에서 다음 state를 한 번에 계산 |

```jsx
// ❌ Effect에서 setFull(first + ' ' + last)
const full = first + ' ' + last // ✅ 렌더 중 계산
```

- 구분 기준은 "표시 때문에" 대 "상호작용 때문에"입니다. 장바구니 담기 알림은 담기 클릭이라는 사건 때문이므로 핸들러에 둡니다.
- `useEffect` 안에서 `setState`로 다른 state를 갱신하는 코드를 보면 의심합니다.

**면접에서 묻는 방식:** "이 Effect를 없앨 수 있는가?" 코드 리뷰 형태로 자주 나옵니다.

## Context vs Reducer

둘은 서로 대체하는 관계가 아니라 **다른 문제**를 풉니다. Reducer는 state가 **어떻게 바뀌는지**를 한곳에 모으고, Context는 값을 깊은 자손에게 **어떻게 전달하는지**를 해결합니다. 함께 쓰는 것이 흔합니다(자세히는 중급 01편, 02편).

| 문제 | 도구 |
|------|------|
| 갱신 규칙이 여러 곳에 흩어짐 | Reducer |
| props를 여러 단계 내려야 함(prop drilling) | Context 또는 컴포지션(`children`) |
| 둘 다 | Context로 `state`와 `dispatch`를 전달 |
| 갱신이 잦고 소비자가 많음 | 외부 스토어(Zustand 등) |

- Context는 값이 바뀌면 그것을 읽는 모든 컴포넌트를 다시 렌더링하고 일부 필드만 구독하지 못합니다.
- `state` Context와 `dispatch` Context를 나누면, 쓰기만 하는 컴포넌트가 상태 변화에 영향을 받지 않습니다.
- Context 도입 전에 컴포지션(`children`으로 내려보내기)으로 prop drilling이 풀리는지 먼저 봅니다.
- 서버 데이터는 Context에 담지 않고 쿼리 캐시에 둡니다(자세히는 27편, 중급 22편).

**면접에서 묻는 방식:** "Context와 Redux(Reducer)는 같은 것인가?", "Context의 성능 문제는?"

## useRef vs useState

둘 다 렌더 사이에 값을 유지하지만 **화면에 영향을 주는가**가 다릅니다. 화면에 보여 줄 정보는 state이고, 렌더와 무관한 값은 ref입니다(자세히는 기초 19편).

| 항목 | `useRef` | `useState` |
|------|----------|------------|
| 변경 시 다시 렌더링 | 안 함 | 함 |
| 변경 방식 | `ref.current`를 직접 변경 | setter 호출 |
| 렌더 중 읽기·쓰기 | 금지(초기화 예외) | 읽기 가능 |
| 용도 | DOM 노드, 타이머 id, 이전 값, 최신 값 보관 | 화면에 표시되는 값 |

- `ref.current`를 렌더 중에 읽거나 쓰면 렌더가 순수하지 않아 예측이 어긋납니다. 이벤트 핸들러와 Effect 안에서 다룹니다.
- 값이 화면에 영향을 주는데 ref에 두면 갱신해도 화면이 안 바뀌고, 영향이 없는데 state에 두면 불필요한 렌더링이 생깁니다.
- 비싼 객체의 초기화는 `if (ref.current === null)` 형태의 지연 초기화를 씁니다.

**면접에서 묻는 방식:** "ref가 변경되면 왜 렌더링되지 않는가?", "타이머 id는 어디에 저장하는가?"

## Transition vs Deferred Value

둘 다 무거운 갱신을 긴급하지 않은 것으로 표시해 입력 같은 긴급한 갱신이 먼저 처리되게 합니다. 차이는 **무엇을 감싸는가**입니다(자세히는 중급 09편, 10편).

| 항목 | `useTransition` | `useDeferredValue` |
|------|-----------------|--------------------|
| 감싸는 대상 | state를 바꾸는 **코드**(`startTransition`) | **값** 하나 |
| 적합한 때 | setter를 내가 호출할 수 있음 | 값을 props로 받아 setter가 없음 |
| 진행 여부 | `isPending` 제공 | 값 비교(`value !== deferred`)로 판단 |
| 입력 state | 텍스트 입력 제어에는 쓰지 않음 | 입력은 즉시 값, 목록은 지연 값 |

- 둘 다 갱신이 중단 가능하고, 새 입력이 오면 진행 중인 렌더를 버립니다. 고정 지연의 디바운스와 달리 기기 성능에 맞춰 적응합니다.
- `useDeferredValue`의 성능 효과는 지연 값을 받는 컴포넌트를 `memo`로 감싸야 나옵니다.
- 둘 다 이미 보이는 내용을 Suspense fallback으로 되돌리지 않게 합니다.
- 디바운스는 네트워크 요청 횟수를 줄이는 데, 이 둘은 렌더링 비용을 다루는 데 씁니다.

**면접에서 묻는 방식:** "검색 입력이 느릴 때 어떻게 개선하는가?", "`useTransition`과 `useDeferredValue`의 차이는?"

## Suspense 설계

Suspense는 **기다림의 범위**를 정하는 경계입니다. 자식이 준비되지 않으면 fallback을 보여 줍니다(자세히는 중급 11편, 28편).

- 경계는 **같이 나타나야 하는 단위**마다 둡니다. 독립된 영역은 별도 경계로 나눠 한 곳의 지연이 전체를 가리지 않게 합니다.
- Suspense를 작동시키는 것은 `lazy`, `use`로 읽는 Promise, Suspense 지원 데이터 라이브러리, 스트리밍 서버 렌더링입니다. Effect·이벤트 핸들러의 요청은 감지하지 못합니다.
- 이미 보이는 내용이 다시 fallback으로 바뀌는 것은 `startTransition`이나 `useDeferredValue`로 막습니다.
- 다른 내용으로 완전히 바뀔 때는 경계에 `key`를 주어 초기화합니다.
- 에러 경계를 짝으로 둡니다. 실패가 Suspense를 통과해 위로 번집니다.
- 부모가 읽고 난 뒤 자식이 요청하는 워터폴을 피하고 독립 요청은 병렬로 시작합니다.

**면접에서 묻는 방식:** "Suspense는 어디에 두는가?", "데이터 요청 로딩 상태를 어떻게 설계하는가?"

## Error Boundary 설계

에러 경계는 **실패의 범위**를 정하는 경계이고, 자식의 렌더링 중 에러를 잡아 대체 UI를 보여 줍니다. 클래스 컴포넌트(`getDerivedStateFromError`, `componentDidCatch`)로만 만들 수 있어서 보통 `react-error-boundary` 패키지를 씁니다(자세히는 25편, 중급 13편).

| 위치 | 잡는 것 | 대체 UI |
|------|---------|---------|
| 앱 최상단 | 예상 못 한 모든 에러 | 전체 오류 화면과 새로고침 |
| 라우트 단위 | 한 화면의 실패 | 그 화면의 오류와 이동 링크 |
| 위젯·섹션 단위 | 한 영역의 실패 | 그 영역만 오류와 재시도 |

- 잡지 못하는 것: 이벤트 핸들러의 에러(`try`/`catch`를 씁니다), 비동기 코드(`setTimeout` 등), 서버 렌더링 중 에러, 경계 자신의 에러입니다. `startTransition` 안의 에러는 잡힙니다.
- 재시도는 경계의 상태를 리셋하는 것이므로 리셋 후 다시 렌더할 때 같은 에러가 반복되지 않도록 원인(데이터, 입력)을 바꿉니다.
- 로깅은 `componentDidCatch`나 루트의 `onCaughtError`·`onUncaughtError`로 한곳에 모읍니다(자세히는 26편).
- 에러 경계는 **예상하지 못한 실패**용입니다. 사용자가 고칠 수 있는 입력 오류는 상태로 표시합니다.

**면접에서 묻는 방식:** "에러 경계가 잡지 못하는 에러는?", "왜 클래스로만 만들 수 있는가?"

## SSR/Hydration

SSR은 서버가 HTML을 만들어 보내 첫 화면과 검색 엔진에 내용을 주고, Hydration은 클라이언트가 그 HTML에 이벤트와 상태를 연결하는 것입니다. 서버 출력과 클라이언트 첫 출력이 **같아야** 합니다(자세히는 01편, 02편, 03편).

| 점검 | 기준 |
|------|------|
| 첫 출력 일치 | 시각, 난수, `window` 분기, 브라우저 API를 렌더에서 읽지 않음 |
| 클라이언트 전용 값 | 마운트 뒤에 채우거나(두 번 렌더), `useSyncExternalStore`, 19.3의 `browser()`로 분리 |
| 불가피한 불일치 | 요소 하나에 `suppressHydrationWarning` |
| 스트리밍 | Suspense 경계로 셸을 먼저 보내고 경계 안은 나중에 |
| 오류 추적 | `hydrateRoot`의 `onRecoverableError` 기록 |

- SSR의 장점은 초기 표시(LCP)와 SEO이고, 단점은 서버 비용과 복잡도, Hydration 전까지 상호작용 불가 구간입니다.
- Hydration이 끝나기 전에 클릭해도 Suspense 경계 단위의 선택적 Hydration으로 상호작용한 부분이 우선됩니다.
- 서버에서는 Effect가 실행되지 않습니다.

**면접에서 묻는 방식:** "Hydration 불일치는 왜 생기고 어떻게 고치는가?", "CSR과 SSR의 차이는?"

## Server/Client Component

기본은 서버 컴포넌트이고, 상호작용이 필요한 말단만 `use client`로 클라이언트 경계를 만듭니다(자세히는 04편, 05편, 06편).

| 질문 | 예 → | 아니오 → |
|------|------|----------|
| `useState`·이벤트 핸들러·브라우저 API가 필요한가 | 클라이언트 | 서버 |
| 서버 자원(DB, 파일, 비밀 값)이 필요한가 | 서버 | 어느 쪽이든 |
| 번들에 넣기 무거운 라이브러리인가 | 서버 | 어느 쪽이든 |

- 경계는 가능한 한 **잎(leaf)** 에 둡니다. 상위에 `use client`를 붙이면 아래 전체가 클라이언트 번들에 들어갑니다.
- 서버 UI를 클라이언트 컴포넌트 안에 넣으려면 `children`이나 props로 전달합니다. 클라이언트 파일이 서버 컴포넌트를 import할 수는 없습니다.
- 클라이언트로 넘기는 props는 직렬화 가능해야 합니다.
- 서버가 시작한 Promise를 클라이언트에 넘기고 `use`와 Suspense로 읽으면 기다리지 않고 먼저 그릴 수 있습니다.
- 변경은 서버 함수(`use server`)를 폼 액션으로 호출하고, 서버 함수는 공개 엔드포인트로 보고 입력 검증과 인가를 합니다(자세히는 23편).

**면접에서 묻는 방식:** "서버 컴포넌트와 SSR의 차이는?", "`use client`를 어디에 붙이는가?"

## Compiler와 Memoization

React Compiler는 빌드 시점에 컴포넌트와 값을 자동으로 메모이제이션하는 도구입니다. 수동 `memo`·`useMemo`·`useCallback`이 대부분 필요 없어지지만 **Rules of React를 지키는 코드**가 전제입니다(자세히는 07편, 08편).

| 상황 | 기준 |
|------|------|
| 새 코드 | 컴파일러에 맡기고, `useMemo`·`useCallback`은 탈출구로 |
| 기존 코드의 메모이제이션 | 바로 지우지 않고 측정 후 정리 |
| 값이 Effect의 의존성이라 안정적 참조 필요 | `useMemo`·`useCallback` 계속 사용 |
| 규칙 위반 컴포넌트 | 컴파일 제외(`"use no memo"`) 또는 코드 수정 |
| 도입 | 진단 → 일부 디렉터리·옵트인 → 확대 |

- 메모이제이션은 최적화 수단이지 정확성의 수단이 아닙니다. 메모이제이션이 없어도 결과가 같아야 합니다.
- 먼저 측정합니다. 느리지 않은 곳의 메모이제이션은 복잡도만 늘립니다(자세히는 28편, 중급 18편, 19편).
- `memo`는 props가 같으면 렌더를 건너뛰고, 새 객체·함수 props가 매번 들어오면 효과가 없습니다.

**면접에서 묻는 방식:** "`useMemo`와 `useCallback`은 언제 쓰는가?", "React Compiler가 하는 일은?"

## State 위치 결정

State는 **쓰는 컴포넌트들의 가장 가까운 공통 부모**에 둡니다. 그전에 이 값이 상태인지, 어떤 종류인지 가립니다(자세히는 기초 14편, 중급 22편, 27편).

위에서 아래로 내려가며 처음 맞는 곳에 둡니다.

| 순서 | 질문 | 위치 |
|------|------|------|
| 1 | 다른 값으로 계산할 수 있는가 | 상태 아님, 렌더 중 계산 |
| 2 | 서버가 원본인 데이터인가 | 쿼리 캐시(서버 상태) |
| 3 | 새로고침·공유에 살아남아야 하는가 | URL |
| 4 | 한 컴포넌트만 쓰는가 | 그 컴포넌트의 로컬 state |
| 5 | 형제 몇 개가 쓰는가 | 가장 가까운 공통 부모로 끌어올림 |
| 6 | 멀리 떨어진 여럿이 쓰는가 | Context(변경이 드묾) 또는 외부 스토어 |

- 끌어올릴 때 props 전달이 깊어지면 컴포지션(`children`)으로 풀고, 그래도 어려우면 Context를 씁니다.
- 반대로 state가 **필요 이상 높이** 있으면 변경마다 넓은 범위가 렌더링됩니다. 쓰는 곳으로 내립니다.
- 폼 입력처럼 제출 때만 값이 필요하면 상태를 두지 않고 `FormData`를 씁니다.
- 한 값의 원본은 하나입니다. 같은 값을 두 곳에 복사하면 어긋납니다.

**면접에서 묻는 방식:** "상태 관리는 어떻게 선택하는가?", "전역 상태가 정말 필요한가?"

## 면접 단골 질문

답변은 **정의 한 문장 → 동작 → 이유나 한계 → 실무 사례** 순서의 골격으로 합니다. 아래는 골격이고 자신의 경험을 채웁니다.

### Virtual DOM

- 정의: UI를 가리키는 자바스크립트 객체(React 엘리먼트) 트리입니다.
- 동작: 상태가 바뀌면 컴포넌트를 다시 호출해 새 트리를 만들고 이전 트리와 비교(재조정)해 바뀐 부분만 실제 DOM에 적용합니다. React는 렌더 결과가 이전과 다를 때만 DOM 노드를 바꿉니다.
- 한계: DOM을 직접 만지는 것보다 항상 빠른 것은 아닙니다. 가치는 선언적 UI(상태에서 화면을 계산)에 있습니다. 내부 구조(Fiber)는 09편입니다.

### key

- 정의: 형제 사이에서 항목의 정체성을 정하는 값입니다.
- 동작: React가 이전·다음 목록을 비교해 어떤 항목이 추가·삭제·이동됐는지 알아냅니다. `key`가 같으면 같은 항목으로 보고 state를 유지합니다.
- 이유: 인덱스를 쓰면 삭제·정렬 때 state가 다른 항목에 남습니다. 안정적인 고유 id를 씁니다. `key`를 바꿔 컴포넌트를 초기화하는 용도도 있습니다.

### 렌더링 과정

- 정의: 트리거 → 렌더 → 커밋의 세 단계입니다.
- 동작: 최초 렌더링이나 state 업데이트가 렌더를 일으키고(트리거), React가 컴포넌트를 호출해 UI를 계산하며(렌더, 순수해야 함), 차이를 DOM에 적용한 뒤(커밋) 브라우저가 화면을 그립니다.
- 이유: 렌더는 순수하므로 중단·재시작될 수 있고, 부수 효과는 커밋 뒤의 Effect나 이벤트 핸들러에서 합니다. StrictMode는 개발 중 컴포넌트를 두 번 호출해 순수하지 않은 코드를 드러냅니다.

### Effect 실행 시점

- 정의: 커밋 이후, 보통 브라우저가 화면을 그린 뒤 실행됩니다. 화면 그리기 전에 실행해야 하면 `useLayoutEffect`입니다.
- 동작: 마운트 후 설정(setup)이 실행되고, 의존성이 바뀌면 이전 값으로 정리(cleanup)한 뒤 새 값으로 설정이 다시 실행되며, 언마운트 때 정리가 한 번 실행됩니다. 의존성 배열을 생략하면 매 커밋 뒤 실행됩니다.
- 이유: 서버 렌더링에서는 실행되지 않고, 개발의 StrictMode는 설정 → 정리 → 설정을 한 번 더 실행합니다.

### 상태 관리 선택

- 골격: 상태의 **종류**를 먼저 가르고 종류마다 도구를 고릅니다. 파생 값은 계산, 서버 데이터는 TanStack Query 같은 서버 상태 도구, 공유할 화면 상태는 URL, 로컬 UI는 `useState`, 여러 화면이 공유하는 클라이언트 상태는 Context와 Reducer로 시작해 필요하면 Zustand 같은 스토어입니다.
- 근거: 서버 상태를 전역 스토어에 복사하면 캐시·갱신을 직접 만들게 됩니다. 도구는 문제가 생긴 뒤에 도입합니다(자세히는 중급 22편, 23편, 26편).

### CSR·SSR

- CSR: 빈 HTML과 JavaScript를 받아 브라우저에서 렌더합니다. 서버가 단순하고 상호작용이 빠르나, 첫 표시가 JavaScript 로드 이후이고 검색 엔진에 불리할 수 있습니다.
- SSR: 요청마다 서버가 HTML을 만들어 첫 표시와 SEO가 좋고, 서버 비용과 Hydration 비용이 듭니다. SSG는 빌드 때 미리 만들어 CDN에서 빠르게 제공하지만 내용 갱신에 재빌드가 필요합니다(자세히는 01편).
- 선택 기준: 내용이 공개되고 검색 노출이 중요하면 SSR·SSG, 로그인 뒤의 앱이면 CSR로 충분한 경우가 많습니다.

### RSC

- 정의: 번들링 전에 클라이언트 앱과 SSR 서버와 분리된 환경에서 미리 렌더되는 컴포넌트입니다. 요청마다 서버에서, 또는 빌드 때 한 번 실행됩니다.
- 동작: 서버 자원을 읽고 `await`할 수 있으며, 브라우저로 코드가 전달되지 않아 번들이 줄고 Hydration도 없습니다. 상호작용은 `use client` 경계의 클라이언트 컴포넌트가 맡습니다.
- 구분: SSR은 같은 컴포넌트를 서버에서 HTML로 그리고 클라이언트에서 다시 실행(Hydration)합니다. RSC는 서버에서만 실행됩니다. 대체 관계가 아니라 함께 씁니다(자세히는 04편).

### 최적화 경험

골격: **측정 → 원인 → 처방 → 검증**을 숫자와 함께 말합니다.

- 상황: "상품 목록에서 검색어를 입력하면 글자가 늦게 나타났다(INP가 기준 초과)."
- 원인: Profiler로 입력마다 목록 전체가 렌더되는 것을 확인했다.
- 처방: 목록 갱신을 `useDeferredValue`로 미루고 목록을 `memo`로 감쌌다.
- 검증: 같은 시나리오로 전후를 비교해 입력 지연이 줄었다. 운영에서는 Web Vitals로 회귀를 추적한다.
- 피할 답: "`memo`를 다 붙였다"처럼 측정 없는 처방, 수치 없는 "빨라졌다"입니다(자세히는 28편, 중급 20편).

## 과제 전형 점검 항목

과제는 기능이 돌아가는지만이 아니라 **판단의 근거가 코드와 문서에 보이는지**를 평가합니다. 제출 전에 점검합니다.

| 영역 | 점검 |
|------|------|
| 요구사항 | 명시된 기능이 모두 동작하고 빠진 것이 없다. 모호한 요구는 가정을 README에 적었다 |
| 상태 | 파생 값을 상태로 두지 않았다. 서버 데이터를 `useState`에 복사하지 않았다. 상태 위치에 근거가 있다 |
| 구조 | 폴더가 기능 단위로 나뉘고 컴포넌트가 한 가지 일을 한다. 의존 방향이 일정하다(자세히는 14편) |
| 화면 상태 | 로딩, 에러(재시도), 빈 상태가 모든 데이터 화면에 있다 |
| 접근성 | 의미 있는 HTML, 라벨, 키보드 조작, 포커스 표시가 있다 |
| Effect | 불필요한 Effect가 없고 정리 함수와 의존성이 정확하다 |
| 타입 | `any` 남용이 없고 API 응답 타입이 정의됐다 |
| 테스트 | 핵심 동작이 사용자 관점으로 테스트됐다(자세히는 21편, 중급 34편, 35편) |
| 성능 | 큰 리스트·번들·불필요한 렌더링을 점검했다. 측정 없는 최적화는 넣지 않았다 |
| 보안 | 비밀 값이 코드·저장소에 없다. 사용자 입력을 `dangerouslySetInnerHTML`로 넣지 않았다(자세히는 23편) |
| 운영 | 환경 변수 분리, 빌드가 성공, 실행 방법이 README에 있다(자세히는 26편) |
| 협업 | 커밋이 의미 단위이고 메시지가 변경을 설명한다. 린트·포맷이 통과한다 |

- 라이브러리를 더하기보다 요구사항에 맞는 가장 단순한 구성을 고르고 이유를 README에 한두 줄 적습니다. 필요 없는 상태 관리 도구나 과한 추상화는 감점 요인입니다.
- 못 한 것은 숨기지 않고 "미구현 목록과 이유, 시간이 있었다면 할 일"로 적습니다.
- 제출 전에 깨끗한 환경에서 설치부터 실행까지 한 번 따라 해 봅니다.
- 과제 이후 라이브 코딩이나 리뷰에서는 작성한 코드의 **선택 이유와 대안**을 묻습니다. 코드에 쓴 모든 줄을 설명할 수 있어야 합니다.

## 핵심 정리

- Props는 부모가 내리는 읽기 전용 입력이고 State는 자기가 기억하는 값이며, 계산할 수 있는 값은 상태가 아니다.
- State는 렌더마다 고정된 스냅샷이고 업데이트는 배칭되어 처리되므로, 이전 값에 기대는 갱신은 updater 함수로 쓴다.
- `key`와 트리 위치가 정체성을 정해 state의 보존과 초기화를 결정하고, 표시 때문에 필요한 외부 동기화만 Effect로 쓴다.
- Context는 전달, Reducer는 갱신 규칙이며, `useRef`는 화면과 무관한 값, `useState`는 화면에 보이는 값이다.
- Transition은 코드를, Deferred Value는 값을 미루며, Suspense는 기다림의 범위, 에러 경계는 실패의 범위를 정한다.
- SSR은 첫 출력의 일치가, 서버/클라이언트 경계는 상호작용이 있는 말단에만 `use client`를 두는 것이 기준이다.
- 최적화와 면접 답변은 측정, 원인, 처방, 검증의 순서로 근거를 보인다.

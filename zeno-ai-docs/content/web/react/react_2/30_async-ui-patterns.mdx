## Loading

Loading은 보여 줄 데이터가 아직 하나도 없는 상태입니다. 첫 요청이 끝나기 전의 화면입니다. 비동기 화면은 보통 네 가지 결과 중 하나에 놓입니다.

| 상태 | 뜻 | 화면 |
|------|----|------|
| Loading | 데이터 없음, 요청 중 | Skeleton 또는 Spinner |
| Error | 요청 실패 | 오류 메시지와 재시도 |
| Empty | 요청 성공, 결과 0건 | 빈 상태 안내 |
| Success | 요청 성공, 결과 있음 | 데이터 |

상태를 불리언 여러 개(`isLoading`, `isError`)로 두면 둘이 동시에 `true` 인 불가능한 조합이 생깁니다. 하나의 `status` 값으로 표현합니다(판별 유니온은 2편).

```jsx
// ❌ 서로 모순될 수 있다
const [loading, setLoading] = useState(false)
const [error, setError] = useState(null)

// ✅ 하나의 값
const [status, setStatus] = useState('idle')
// 'idle' | 'loading' | 'error' | 'success'
```

TanStack Query를 쓰면 이 상태를 라이브러리가 관리합니다. `status` 는 `pending`, `error`, `success` 중 하나이고 데이터 유무를 뜻합니다(27편).

```jsx
const { isPending, isError, data, error } = useQuery(opts)
if (isPending) return <ListSkeleton />
if (isError) return <ErrorBox error={error} />
return <List items={data} />
```

- 순서는 pending, error, 그다음 성공입니다. 이 뒤에서는 `data` 가 반드시 있다고 가정해도 됩니다.
- React Suspense를 쓰면 이 분기가 사라집니다. 로딩은 `Suspense` 의 `fallback` 이, 오류는 Error Boundary가 맡습니다(11편, 13편).

## Pending

Pending은 이미 화면이 있는 상태에서 어떤 작업이 진행 중인 상태입니다. 데이터가 아직 없는 Loading과 구분합니다. 폼 제출, 저장, 삭제, Transition 중의 화면이 해당합니다.

| 출처 | 신호 |
|------|------|
| Transition | `useTransition` 의 `isPending` (9편) |
| 폼 Action | `useFormStatus` 의 `pending`, `useActionState` 의 `isPending` (7편) |
| TanStack Query mutation | `mutation.isPending` (28편) |

```jsx
function SubmitButton() {
  const { pending } = useFormStatus()
  return (
    <button type="submit" disabled={pending}>
      {pending ? '저장 중' : '저장'}
    </button>
  )
}
```

- Pending 표시는 해당 작업 부근에 둡니다. 버튼 문구를 바꾸거나 해당 영역만 흐리게 하고, 화면 전체를 가리지 않습니다.
- `useFormStatus` 는 `form` 안에 렌더링된 자식 컴포넌트에서만 동작하고, 가장 가까운 부모 폼의 상태만 읽습니다.
- Pending 중에는 진행 중이라는 사실이 보여야 하고, 같은 동작을 다시 트리거할 수 없어야 합니다(아래 "중복 Submit 방지").

## Error

Error는 요청이 실패한 상태입니다. 무엇이 실패했는지와 다음에 할 일(재시도, 돌아가기)을 함께 보여 줍니다.

- `fetch` 는 HTTP 4xx·5xx에서도 reject하지 않습니다. `response.ok` 를 확인하고 직접 던져야 쿼리가 오류 상태가 됩니다(27편).
- 오류 종류에 따라 문구와 동작이 달라집니다. 네트워크 단절, 인증 만료(401), 권한 없음(403), 없음(404), 서버 오류(5xx)가 대표적입니다.
- 서버 메시지를 그대로 노출하지 않고 사용자용 문구로 바꿉니다.
- 위치는 범위로 정합니다. 목록 하나가 실패하면 그 영역만 오류로 바꾸고, 화면 전체를 오류로 바꾸는 것은 렌더링 중 예외처럼 화면이 성립하지 않을 때입니다(Error Boundary 위치는 13편).
- 이벤트 핸들러와 비동기 코드의 오류는 Error Boundary가 잡지 않습니다. 상태로 저장해 렌더링합니다.

```jsx
if (isError) {
  return (
    <div role="alert">
      <p>목록을 불러오지 못했습니다.</p>
      <button onClick={() => refetch()}>다시 시도</button>
    </div>
  )
}
```

`role="alert"` 는 스크린 리더가 즉시 읽어 주는 영역입니다(접근성은 32편).

## Empty

Empty는 요청이 성공했지만 결과가 0건인 상태입니다. Loading 상태에서 빈 목록을 보이는 것과는 다릅니다.

```jsx
if (isPending) return <ListSkeleton />
if (data.length === 0) {
  return <p>등록된 항목이 없습니다.</p>
}
```

- 빈 상태 판정은 성공 이후에만 합니다. `data` 가 없을 때 `[]` 로 대체해서 "항목 없음"을 먼저 보이면 로딩 중에 잠깐 빈 화면이 번쩍입니다.
- 이유별로 문구를 나눕니다. 처음부터 데이터가 없는 경우(만들기 유도)와 필터·검색 결과가 없는 경우(조건 해제 유도)는 다른 안내가 맞습니다.
- 다음에 할 행동(항목 추가, 필터 초기화) 버튼을 함께 둡니다.

## Success

Success는 데이터가 있어 정상적으로 그려지는 상태이고, 변경 작업(저장, 삭제)이 끝났다는 피드백도 포함합니다.

- 조회의 Success는 별도 표시 없이 데이터 자체가 신호입니다.
- 변경 작업의 Success는 결과를 알려야 합니다. 토스트, 인라인 메시지, 화면 이동이 쓰입니다. 화면 이동으로 이미 변화가 보이면 따로 알리지 않아도 됩니다.
- 메시지 영역은 `role="status"` 로 두면 스크린 리더가 정중하게(polite) 읽어 줍니다. 마우스로 사라지는 토스트만으로는 못 읽는 사용자가 있습니다.
- 변경 후에는 화면의 서버 데이터를 최신으로 맞춥니다. TanStack Query에서는 `invalidateQueries` 가 그 역할입니다(28편).

```jsx
{mutation.isSuccess && (
  <p role="status">저장했습니다.</p>
)}
```

## Skeleton

Skeleton은 데이터가 올 자리의 윤곽을 회색 블록으로 미리 그린 로딩 표시입니다. 최종 레이아웃과 비슷한 크기로 만들어서 데이터가 채워질 때 화면이 밀리지 않게 합니다.

```jsx
function ListSkeleton() {
  return (
    <ul aria-busy="true" aria-label="목록 불러오는 중">
      {[0, 1, 2].map((i) => (
        <li key={i} className="skeleton-row" />
      ))}
    </ul>
  )
}
```

- 적합한 경우: 목록, 카드, 프로필처럼 최종 모양이 정해져 있고 로딩이 비교적 긴 화면.
- 크기를 실제와 맞춥니다. 높이가 다르면 데이터가 들어올 때 레이아웃이 밀려 CLS가 생깁니다(20편).
- 장식용 반복 요소이므로 스크린 리더에는 한 번만 의미가 전달되게 합니다. 영역에 `aria-busy` 를 주고, 읽을 텍스트는 하나만 둡니다.
- `Suspense` 의 `fallback` 에 Skeleton을 넣는 것이 가장 흔한 조합입니다. 경계를 중첩하면 준비된 부분부터 보여 줍니다(11편).
- 로딩이 매우 짧으면 Skeleton이 번쩍였다 사라져 오히려 거슬립니다. 이럴 때는 표시를 약간 지연시킵니다.

## Spinner

Spinner는 진행도를 알 수 없는 작업을 보여 주는 회전 아이콘입니다. 윤곽을 알 수 없거나 범위가 작은 곳에 씁니다.

| 구분 | Skeleton | Spinner |
|------|----------|---------|
| 알려 주는 것 | 곧 올 내용의 모양 | 처리 중이라는 사실 |
| 어울리는 곳 | 페이지·목록·카드 최초 로딩 | 버튼 안, 모달, 짧은 작업, 모양을 알 수 없는 결과 |
| 레이아웃 | 최종과 같게 유지 | 자리를 따로 차지 |

- 아이콘만으로는 의미가 전달되지 않으니 "불러오는 중" 같은 텍스트를 함께 둡니다(화면에 안 보이게 두는 것도 가능합니다).
- 화면 전체를 덮는 Spinner는 이전 화면의 맥락까지 지웁니다. 필요한 영역에만 둡니다.
- 동시에 여러 Spinner가 돌면 산만하므로, 영역 하나에 하나만 보이게 합니다.

```jsx
<button disabled={pending}>
  {pending && <Spinner aria-hidden />}
  <span>{pending ? '저장 중' : '저장'}</span>
</button>
```

## Optimistic UI

Optimistic UI는 서버 응답을 기다리지 않고 성공할 것으로 가정해 화면을 먼저 바꾸는 방식입니다. 좋아요, 체크, 댓글 추가처럼 실패가 드문 작업에서 즉시 반응하는 느낌을 줍니다.

```jsx
const [optLiked, setOptLiked] = useOptimistic(liked)

function toggle() {
  startTransition(async () => {
    setOptLiked(!optLiked)      // 즉시 반영
    await saveLike(!optLiked)   // 서버 요청
    // 끝나면 실제 값으로 수렴한다
  })
}
```

- `useOptimistic` 은 Action 또는 Transition 안에서 호출해야 합니다. 밖에서 부르면 낙관적 값이 잠깐 보였다가 되돌아갑니다(자세히는 8편).
- Action이 끝나면 낙관적 값은 실제 값으로 되돌아옵니다. 실패하면 별도 코드 없이 원래 값으로 복구되므로, 오류 메시지를 함께 보여 줍니다.
- TanStack Query에서는 `onMutate` 에서 캐시를 바꾸고 `onError` 에서 롤백합니다(28편).
- 적합하지 않은 경우: 결제처럼 실패하면 곤란한 작업, 서버가 값을 정해 주는 작업(서버가 만드는 id, 계산 결과). 이럴 때는 Pending 표시로 기다립니다.
- 낙관적 항목에는 "전송 중" 표시를 약하게 달아서 확정 전임을 알립니다.

## Retry

Retry는 실패한 요청을 다시 보내는 것으로, 자동 재시도와 사용자 재시도로 나뉩니다.

| 방식 | 내용 |
|------|------|
| 자동 | TanStack Query의 `useQuery` 는 실패 시 기본 3회 재시도하고, 지연은 1초에서 시작해 두 배씩 늘며 최대 30초입니다. 서버에서는 기본 0회입니다 |
| 사용자 | 오류 화면의 "다시 시도" 버튼 |

- `retry` 옵션으로 횟수를 조정합니다(`false`, 숫자, `(failureCount, error) => boolean` 함수).
- 재시도해도 소용없는 오류(4xx)는 재시도에서 제외합니다. 인증·검증 오류를 반복해서 보내면 서버 부담만 늘립니다.
- 자동 재시도 중에는 사용자에게 오류가 보이지 않으므로, 모두 실패한 뒤에 Error 상태가 됩니다.
- 변경 요청(`useMutation`)의 `retry` 기본값은 0입니다. 같은 변경이 두 번 적용될 수 있어서, 서버가 중복을 막는(멱등한) API일 때만 켭니다.
- Error Boundary 안에서는 경계를 초기화하는 방식으로 다시 시도합니다(`react-error-boundary` 의 `resetErrorBoundary`, 13편).

```jsx
const { refetch, isFetching } = useQuery(opts)

<button onClick={() => refetch()} disabled={isFetching}>
  다시 시도
</button>
```

## Stale UI

Stale UI는 새 데이터를 기다리는 동안 이전 데이터를 화면에 그대로 두는 방식입니다. 로딩 화면으로 바꿔서 화면이 비는 것보다 맥락이 유지됩니다. 검색어를 바꾸거나 페이지를 넘길 때 효과가 큽니다.

| 도구 | 동작 |
|------|------|
| `useDeferredValue` | 지연된 값으로 렌더링해 이전 결과를 유지(10편) |
| Transition | 전환이 끝날 때까지 이전 화면 유지, `isPending` 으로 표시(9편) |
| `placeholderData` | 쿼리 키가 바뀌어도 이전 데이터를 자리 표시로 사용(28편) |

```jsx
const deferred = useDeferredValue(query)
const stale = query !== deferred

<div style={{ opacity: stale ? 0.5 : 1 }}>
  <Results query={deferred} />
</div>
```

- 이전 화면을 보여 주는 동안에는 낡은 데이터임을 알려야 합니다. 흐리게 하거나 작은 진행 표시를 겹칩니다.
- 이미 보이는 콘텐츠를 `fallback` 으로 갈아치우지 않으려면 상태 갱신을 `startTransition` 으로 감쌉니다(11편).
- 낡은 데이터에 대한 상호작용(예: 이전 결과의 항목 클릭)이 가능한지 정합니다. 위험한 동작은 막습니다.

**흔한 실수:** 이전 데이터를 보여 주면서 낡았다는 표시를 하지 않는 것입니다. 사용자가 새 결과로 착각해 잘못 판단합니다.

## Background Refresh

Background Refresh는 이미 보이는 데이터를 사용자 모르게 다시 가져와서 조용히 교체하는 것입니다. 창 포커스 복귀, 네트워크 재연결, 일정 주기마다 일어납니다(자동 refetch 조건은 27편).

TanStack Query에서는 `isPending`(처음 로딩)과 `isFetching`(가져오는 중이면 언제나)을 나눠서 씁니다.

```jsx
const { isPending, isFetching, data } = useQuery(opts)

if (isPending) return <ListSkeleton />
return (
  <>
    {isFetching && <span role="status">갱신 중</span>}
    <List items={data} />
  </>
)
```

- 갱신 중에는 Skeleton으로 되돌리지 않습니다. 이미 있는 데이터를 유지하고 작은 표시만 보입니다.
- 백그라운드 갱신이 실패하면 기존 데이터를 지우지 않고 알림만 띄우는 편이 낫습니다. TanStack Query는 이때 `data` 를 유지한 채 `status` 만 `error` 로 바꿉니다(`isRefetchError`). 위의 순서대로 `isError` 를 먼저 검사하면 데이터가 사라지므로, `data` 가 있는지 함께 확인합니다.
- 화면 전체의 갱신 상태는 `useIsFetching` 으로 모아서 상단 진행 표시줄 하나로 보입니다.
- 갱신으로 목록이 갑자기 바뀌면 읽던 위치가 바뀝니다. 사용자가 조작 중인 영역은 자동 갱신 결과로 덮어쓰지 않게 설계합니다.

## 중복 Submit 방지

중복 제출은 같은 요청이 두 번 이상 서버에 가는 문제입니다. 느린 응답, 더블 클릭, 엔터 연타가 원인입니다. 결제나 주문에서는 이중 처리로 이어집니다. 막는 층이 여러 겹입니다.

| 층 | 방법 |
|----|------|
| 화면 | Pending 동안 버튼을 `disabled`, 진행 중 표시 |
| 핸들러 | Pending이면 함수에서 바로 반환 |
| 서버 | 멱등 키(idempotency key)로 같은 요청을 한 번만 처리 |

```jsx
const mutation = useMutation({ mutationFn: save })

function onSubmit(e) {
  e.preventDefault()
  if (mutation.isPending) return // 핸들러에서도 막는다
  mutation.mutate(values)
}
// <button disabled={mutation.isPending}>저장</button>
```

- 폼 Action에서는 `useFormStatus` 의 `pending` 이나 `useActionState` 의 `isPending` 으로 버튼을 막습니다(7편).
- `disabled` 는 렌더링 이후에야 적용됩니다. 첫 클릭과 같은 틱의 두 번째 클릭은 `ref` 같은 동기 값으로 막아야 하는 경우가 있습니다.
- 클라이언트에서 막아도 네트워크 재시도나 여러 탭에서 중복이 생길 수 있어서, 중요한 작업은 서버가 중복을 걸러야 합니다.
- 버튼을 비활성화하면 포커스와 의미 전달이 바뀌므로, 문구로 진행 상태를 알립니다("저장 중").
- 변경 요청의 자동 재시도는 중복 제출과 같은 효과를 냅니다(위 "Retry").

**흔한 실수:** 버튼만 막고 Enter 제출 경로와 핸들러를 확인하지 않는 것입니다. 제출 경로가 하나가 아닌 화면에서 중복이 새 나갑니다.

## 핵심 정리

- 비동기 화면은 Loading(데이터 없음), Error, Empty(성공 0건), Success로 나누고, 불리언 여러 개가 아니라 하나의 상태 값으로 표현합니다.
- Pending은 화면이 있는 채로 진행 중인 작업이며 Transition, 폼 Action, mutation의 신호를 해당 영역에만 표시합니다.
- Skeleton은 최종 레이아웃과 같은 크기로 최초 로딩에, Spinner는 모양을 알 수 없는 짧은 작업에 쓰고 텍스트를 함께 둡니다.
- Optimistic UI는 실패가 드문 작업에 쓰고 실패 시 복구와 오류 알림을 함께 설계합니다. Retry는 자동과 사용자 방식으로 나뉘고 변경 요청의 자동 재시도는 기본이 꺼져 있습니다.
- 이전 데이터를 유지할 때는 낡았음을 표시하고, 백그라운드 갱신은 Skeleton으로 되돌리지 않고 작은 표시만 보입니다.
- 중복 제출은 화면, 핸들러, 서버 세 층에서 막습니다.

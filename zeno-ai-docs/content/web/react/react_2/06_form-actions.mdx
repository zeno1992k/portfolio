## form action

React 19부터 `form`의 `action` prop에 URL 문자열뿐 아니라 함수도 넘길 수 있습니다. 함수를 넘기면 제출 처리를 그 함수가 맡습니다.

```jsx
function Search() {
  function search(formData) {
    const query = formData.get('query')
    console.log(query) // 입력한 검색어
  }
  return (
    <form action={search}>
      <input name="query" />
      <button type="submit">검색</button>
    </form>
  )
}
```

| 항목 | `action`에 URL | `action`에 함수 | `onSubmit` |
|------|----------------|-----------------|------------|
| 제출 | 브라우저가 해당 URL로 이동 | React가 함수를 호출 | 이벤트 핸들러가 호출 |
| 페이지 이동 | 있음 | 없음 | `e.preventDefault()`를 직접 호출해야 막음 |
| 인자 | 없음 | `FormData` 하나 | 제출 이벤트 |
| Transition | 해당 없음 | Transition 안에서 실행 | 직접 감싸야 함 |

- 함수를 넘기면 `e.preventDefault()`를 쓰지 않습니다. 새로고침이 일어나지 않습니다.
- `method` prop은 무시되고 HTTP 메서드는 항상 POST입니다.
- 함수가 성공적으로 끝나면 폼의 비제어(uncontrolled) 입력 값이 자동으로 리셋됩니다. state로 값을 관리하는 제어 컴포넌트는 리셋 대상이 아닙니다(제어·비제어 입력은 기초 15편, 16편).
- 리셋을 직접 일으켜야 하면 React DOM의 `requestFormReset` API를 씁니다(React 19 발표 글에서 소개).
- `onSubmit`은 모든 React 버전에서 동작하고 제출 이벤트에 접근해야 할 때 여전히 쓰입니다. 다만 Server Function을 받을 수 없습니다.

## formAction

`formAction`은 `button`, `input type="submit"`, `input type="image"`에 붙여 그 제출 수단만 `form`의 `action`을 덮어쓰는 prop입니다. 폼 하나에 제출 방식이 여러 개일 때 씁니다.

```jsx
function Editor() {
  function publish(formData) { /* 발행 */ }
  function saveDraft(formData) { /* 임시 저장 */ }
  return (
    <form action={publish}>
      <textarea name="content" />
      <button type="submit">발행</button>
      <button formAction={saveDraft}>임시 저장</button>
    </form>
  )
}
```

- 어느 버튼을 눌렀는지는 누른 쪽의 `formAction`이 결정합니다. `formAction`이 없는 버튼은 `form`의 `action`을 씁니다.
- `formAction`에 함수를 넘겨도 동작은 `action`과 같습니다. Transition에서 실행되고 HTTP 메서드는 POST입니다.
- 같은 함수를 쓰고 버튼만 구분하려면 `name`과 `value`를 붙여 `FormData`로 읽습니다.

```jsx
<button name="intent" value="draft">임시 저장</button>
// formData.get('intent') === 'draft' (누른 버튼만 포함됨)
```

## Action 함수

Action은 Transition 안에서 호출되는 함수를 부르는 이름입니다. 비동기 전환(async transition)을 쓰는 함수를 관례상 Action이라고 합니다. React는 Action이 진행되는 동안 pending 상태를 추적하고, 낙관적 업데이트를 지원하고, 에러를 Error Boundary로 보내고, 폼을 리셋합니다(Transition은 09편).

`form`에 넘기는 함수가 대표적인 Action입니다. 부모가 자식에게 내려주는 함수 prop도 Action이면 이름 끝에 `Action`을 붙이는 관례(Action prop 패턴)가 있습니다.

```jsx
function Comment({ submitAction }) {
  // submitAction은 Transition 안에서 호출될 함수라는 표시
  return <form action={submitAction}>{/* ... */}</form>
}
```

- Action 안에서 하는 state 업데이트는 Transition으로 표시됩니다.
- `action`에 넘기는 함수는 인자로 `FormData` 하나를 받습니다. 값이 더 필요하면 `bind`로 앞쪽 인자를 채웁니다.

```jsx
// id가 먼저, formData가 마지막
function remove(id, formData) { /* ... */ }

<form action={remove.bind(null, item.id)}>
  <button>삭제</button>
</form>
```

- 이벤트 핸들러(`onClick` 등)는 Action이 아닙니다. 핸들러 안에서 Action을 만들려면 `startTransition`으로 직접 감쌉니다.

## FormData

`FormData`는 브라우저 표준 객체로, 폼 필드의 이름과 값 쌍을 담습니다. `action`에 넘긴 함수가 이것을 받으므로 입력마다 state를 두지 않고도 값을 읽습니다.

```js
function signup(formData) {
  const email = formData.get('email')   // 문자열 또는 File
  const tags = formData.getAll('tag')   // 같은 이름 전부
  const all = Object.fromEntries(formData) // 이름이 겹치면 마지막 값
}
```

- `get`은 첫 번째 값을 문자열이나 `File`로 반환하고, 없으면 `null`입니다. 숫자 입력도 문자열이므로 직접 변환합니다.
- `FormData`는 이터러블이라서 `for...of`와 `Object.fromEntries`에 쓸 수 있습니다.
- `name` 속성이 있는 필드만 담깁니다. 체크되지 않은 체크박스와 `disabled`인 입력은 빠집니다.
- 화면에는 보여도 값은 필요 없는 항목은 `input type="hidden"`으로 보냅니다.
- 입력을 `value`와 state로 제어하는 폼이라면 `FormData` 대신 state를 읽습니다.

**흔한 실수:** `name`을 빼먹는 것입니다. 입력창은 있는데 `formData.get('email')`이 `null`을 돌려줍니다.

## 비동기 Action

Action은 `async` 함수일 수 있습니다. `await`로 요청이 끝나기를 기다리는 동안 React는 그 Action이 진행 중인 Transition으로 취급합니다.

```jsx
async function save(formData) {
  const name = formData.get('name')
  await fetch('/api/profile', {
    method: 'PUT',
    body: JSON.stringify({ name }),
  })
  // 여기까지 끝나야 Transition이 끝나고 폼이 리셋됨
}
```

- Action이 끝날 때까지 pending 상태가 유지되고, 끝나면 최종 state가 반영될 때 자동으로 해제됩니다.
- Transition 도중에도 UI는 응답성을 유지합니다. 사용자가 다른 화면으로 이동할 수 있습니다.
- `await` 뒤에서 state를 바꾸려면 현재는 그 업데이트를 `startTransition`으로 한 번 더 감싸야 Transition으로 취급됩니다(공식 문서 Troubleshooting 항목). 이 규칙은 09편에서 다룹니다.

```jsx
async function save(formData) {
  const saved = await api.save(formData)
  startTransition(() => setProfile(saved)) // await 뒤는 다시 감쌈
}
```

**흔한 실수:** 사용자가 제출을 여러 번 빠르게 누르는 경우입니다. 요청이 겹치면 응답 순서가 뒤바뀔 수 있다는 한계가 공식 문서에도 적혀 있습니다. pending 동안 버튼을 막아 중복 제출을 줄입니다.

## Pending State

Action이 진행되는 동안 UI에 진행 중임을 보이는 정보를 pending state라고 합니다. 폼에서는 세 가지 방법이 있습니다.

| 방법 | 위치 | 용도 |
|------|------|------|
| `useFormStatus` | `form` 안쪽 자식 컴포넌트 | 제출 버튼 등이 부모 폼의 상태를 읽음 |
| `useActionState`의 `isPending` | 폼을 가진 컴포넌트 | Action 결과 state와 함께 pending을 얻음 |
| `useTransition`의 `isPending` | 직접 Transition을 시작하는 컴포넌트 | 폼이 아닌 Action |

```jsx
import { useFormStatus } from 'react-dom'

function Submit() {
  const { pending } = useFormStatus()
  return <button disabled={pending}>저장</button>
}
// 반드시 form 안에 렌더링되는 자식이어야 함
```

- `useFormStatus`는 자기 부모 `form`의 상태만 읽습니다. `form`을 렌더링하는 같은 컴포넌트에서 부르면 `pending`이 항상 `false`입니다.
- 자세한 사용법은 07편입니다.
- 낙관적 업데이트로 pending 표시를 즉시 띄우는 방법은 08편입니다.

## Action Error

Action 안에서 던진 에러는 가장 가까운 Error Boundary로 전달됩니다. 에러가 나면 Boundary의 fallback이 렌더링됩니다(Error Boundary는 13편).

```jsx
<ErrorBoundary fallback={<p>제출 중 문제가 생겼습니다.</p>}>
  <form action={search}>
    <input name="query" />
    <button>검색</button>
  </form>
</ErrorBoundary>
```

에러는 두 종류로 나눠 다룹니다.

| 종류 | 예 | 처리 |
|------|----|------|
| 예상한 에러 | 입력 검증 실패, 중복 이메일 | Action이 에러 값을 반환해 state로 화면에 표시(`useActionState`, 07편) |
| 예상 못한 에러 | 코드 버그, 네트워크 장애 | 던져서 Error Boundary가 처리 |

- Action이 성공해야 비제어 입력이 리셋됩니다. 실패한 제출은 입력을 지우지 않는 것이 사용자에게 유리하므로, 검증 실패는 던지지 말고 값으로 반환하는 편이 낫습니다.
- Action 안에서 `try`/`catch`로 직접 잡아서 에러 메시지를 state에 담는 방법도 있습니다.

## Progressive Enhancement

Progressive Enhancement는 JavaScript가 로드되기 전이나 꺼져 있어도 기본 기능이 동작하게 하고, JavaScript가 있으면 기능을 더 얹는 설계입니다. 폼은 원래 HTML만으로 제출되므로 이 설계에 가장 잘 맞습니다.

- `action`에 URL을 주면 브라우저 기본 동작이라 JavaScript 없이도 제출됩니다.
- `form`을 Server Component에서 렌더링하고 `action`에 Server Function을 넘기면 JavaScript 없이도, 코드가 로드되기 전에도 제출됩니다. 공식 문서는 이 조합을 progressively enhanced라고 설명합니다.
- 클라이언트 쪽 함수는 JavaScript가 실행돼야 호출되므로 이 보장이 없습니다.
- JavaScript가 오기 전에 서버가 돌려준 에러 메시지를 보이려면 세 조건이 필요합니다. `form`이 Client Component에서 렌더링되고, `action`이 Server Function이고, `useActionState`로 메시지를 표시해야 합니다.
- `useActionState`의 세 번째 인자 `permalink`는 이 흐름에서 쓰는 URL입니다(07편).
- Server Component·SSR은 이 과목 범위 밖이며, 대부분 프레임워크가 처리합니다.

## Client Action

Client Action은 브라우저에서 실행되는 일반 함수를 `action`에 넘기는 방식입니다. 서버 없이도, 어떤 번들러에서도 쓸 수 있고 Vite 같은 클라이언트 전용 앱의 기본 선택입니다.

```jsx
function Profile({ onSaved }) {
  async function save(formData) {
    const res = await fetch('/api/profile', {
      method: 'PUT',
      body: formData,
    })
    onSaved(await res.json())
  }
  return <form action={save}>{/* ... */}</form>
}
```

- 클라이언트에서 `fetch`로 API를 호출하는 구조 그대로입니다. 바뀌는 것은 제출 처리 방식입니다(`onSubmit`의 `preventDefault`와 상태 관리 코드가 줄어듭니다).
- Action 안에서 부모가 내려준 함수를 부르고 상태를 바꿀 수 있으므로 결과를 상위 state에 반영하기도 쉽습니다.
- `body: formData`로 `FormData`를 그대로 보내면 요청 본문은 `multipart/form-data`로 인코딩됩니다.
- JavaScript가 실행되기 전에는 제출이 동작하지 않습니다(위의 Progressive Enhancement).

## Server Function과 Action

Server Function은 서버에서 실행되고 Client Component가 호출할 수 있는 async 함수입니다. 함수에 `'use server'` 지시어를 붙여 표시하고, 호출하면 React가 서버로 요청을 보내 실행한 뒤 결과를 돌려줍니다. 폼의 `action`이나 Action 안에서 호출되는 Server Function을 Server Action이라고 부릅니다. 2024년 9월 전에는 모든 Server Function을 Server Action이라고 불렀습니다.

```jsx
async function addToCart(formData) {
  'use server'
  await updateCart(formData.get('productId'))
}

<form action={addToCart}>
  <input type="hidden" name="productId" value={id} />
  <button>담기</button>
</form>
```

- 추가 값은 숨은 필드나 `bind`로 전달합니다. `bind`로 값을 넘길 때 인자 순서는 바인딩한 값이 앞, `FormData`가 마지막입니다.
- Server Function은 Server Components를 지원하는 번들러나 프레임워크가 있어야 쓸 수 있습니다. 공식 문서에 따르면 그 구현 API는 semver를 따르지 않아 마이너 버전 사이에 깨질 수 있으니 React 버전을 고정하라고 권합니다.
- 인자와 반환값은 직렬화 가능한 값이어야 합니다.
- 서버 응답은 `useActionState`로 받아 화면에 표시합니다(07편).
- Vite로 만든 클라이언트 전용 앱에는 Server Function이 없습니다. 이 과목에서는 Client Action을 기준으로 쓰고, Server Function은 개념만 다룹니다.

## Optimistic Form

낙관적 폼은 제출 직후, 서버 응답을 기다리지 않고 화면에 예상 결과를 먼저 보여 주는 폼입니다. `useOptimistic`으로 만든 낙관적 state를 Action 시작 지점에서 갱신합니다. 자세히는 08편입니다.

```jsx
function Thread({ messages, sendMessage }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (state, text) => [...state, { text, sending: true }],
  )
  async function formAction(formData) {
    addOptimistic(formData.get('message'))
    await sendMessage(formData)
  }
  return <form action={formAction}>{/* ... */}</form>
}
```

- Action의 시작에서 낙관적 state를 갱신하면, 서버 응답을 기다리는 동안 목록에 "전송 중" 항목이 보입니다.
- Action이 끝나면 낙관적 state는 사라지고 실제 state가 렌더링됩니다. Action이 실패하면 낙관적 값이 자동으로 원래대로 돌아갑니다.
- `form`의 `action`에 넘긴 함수 안에서는 `startTransition` 없이 낙관적 setter를 부를 수 있습니다. 이미 Transition 안이기 때문입니다.

## 핵심 정리

- `action`에 함수를 넘기면 React가 `FormData`를 인자로 호출하고 Transition 안에서 실행하며, `preventDefault`가 필요 없고 HTTP 메서드는 POST이며 성공 후 비제어 입력을 리셋합니다.
- `formAction`은 버튼 단위로 `form`의 `action`을 덮어써서 한 폼에 여러 제출 방식을 둡니다.
- Action은 Transition 안에서 호출되는 함수이며 async로 쓸 수 있고, pending은 `useFormStatus`·`useActionState`·`useTransition`으로 읽습니다.
- 던진 에러는 Error Boundary로 가고, 검증 실패 같은 예상한 에러는 값으로 반환해 state로 보입니다.
- JavaScript 없이도 동작하는 Progressive Enhancement는 Server Function을 쓸 때 얻고, 클라이언트 함수 Action은 JavaScript가 필요합니다.
- 낙관적 폼은 Action 시작 때 `useOptimistic`의 setter를 부르는 구조입니다.

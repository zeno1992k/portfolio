## use()

`use`는 렌더 중에 Promise나 Context 같은 리소스의 값을 읽는 React API입니다. React 19에서 추가되었습니다.

```jsx
import { use } from 'react'

const value = use(resource)
```

- 인수로 받는 것은 Promise와 Context 객체입니다. 19.3에서는 서버에서 렌더하지 않을 컴포넌트를 표시하는 `use(browser())`도 추가되었습니다(`browser`는 `react-dom`에서 가져옴).
- 컴포넌트나 Hook 안에서만 호출합니다.
- Hook이 아닙니다. 이름이 `use`로 시작하지만 조건문과 반복문 안에서 호출할 수 있습니다(아래 두 절).
- Promise를 읽으면 값이 준비될 때까지 컴포넌트가 일시 중단(suspend)되고, 거부되면 오류가 던져집니다.

| 인수 | 반환값 | 연결되는 기능 |
|------|--------|---------------|
| Promise | 이행된 값 | Suspense, Error Boundary |
| Context | 가장 가까운 위쪽 Provider의 값 | Context 재렌더링 |

## Promise 읽기

`use(promise)`는 Promise가 이행될 때까지 기다렸다가 그 값을 돌려줍니다. `async`/`await`를 컴포넌트 렌더에 쓰지 못하는 클라이언트 컴포넌트에서 Promise를 읽는 방법입니다.

```jsx
import { use } from 'react'

function Albums({ albumsPromise }) {
  const albums = use(albumsPromise)
  return (
    <ul>
      {albums.map((a) => <li key={a.id}>{a.title}</li>)}
    </ul>
  )
}
```

- Promise는 부모가 만들어서 props로 내려 줍니다. `Albums`는 읽기만 합니다.
- Promise가 아직 이행되지 않았으면 `use`는 컴포넌트를 일시 중단하고 아래 코드는 실행되지 않습니다.
- 같은 Promise를 다시 렌더에서 받으면, 이미 이행된 값은 일시 중단 없이 동기적으로 읽힙니다. 그래서 Fallback이 다시 깜빡이지 않습니다.
- `try`/`catch`로 감쌀 수 없습니다. 오류 처리는 Error Boundary가 합니다(아래 "Reject와 Error Boundary").
- Promise의 `status`를 직접 확인하지 말고 항상 `use(promise)`로 읽습니다.

## Context 읽기

`use(Context)`는 `useContext`처럼 가장 가까운 위쪽 Provider의 값을 돌려줍니다. 위 방향으로만 찾아서 같은 컴포넌트가 렌더한 Provider는 보지 않습니다.

```jsx
const ThemeContext = createContext('light')

function Button() {
  const theme = use(ThemeContext)
  return <button className={theme}>확인</button>
}
// Provider가 없으면 createContext의 기본값 'light'
```

- Context 값이 바뀌면 `use`를 호출한 컴포넌트가 다시 렌더됩니다. `useContext`와 같습니다(자세히는 01편).
- 서버 컴포넌트에서는 `use(context)`를 지원하지 않습니다.

## 조건문에서 use

`use`는 `if`와 조기 `return` 뒤에서 호출할 수 있습니다. `useContext` 같은 Hook은 컴포넌트 최상위에서만 호출해야 하지만 `use`는 그 제한이 없습니다.

```jsx
function Heading({ children }) {
  if (children == null) return null

  const theme = use(ThemeContext) // 조기 return 뒤여도 가능
  return <h1 style={{ color: theme.color }}>{children}</h1>
}
```

- 값이 필요 없는 경로에서는 Context를 읽지 않으므로, 조건에 따라 Context를 구독할지 말지 결정할 수 있습니다.
- `useContext`는 같은 위치에 쓰면 Hook 규칙 위반입니다(기초 과목의 Hook 규칙 참조).

```jsx
function HorizontalRule({ show }) {
  if (show) {
    const theme = use(ThemeContext)
    return <hr className={theme} />
  }
  return false
}
```

**흔한 실수:** 조건문에서 호출할 수 있다는 점을 `try`/`catch` 안에서도 된다는 뜻으로 읽는 것입니다. `use`는 일시 중단하는 방법으로 내부에서 던지는 방식이라 `try`/`catch` 안에서는 쓸 수 없습니다. 쓰면 "Suspense Exception: This is not a real error!" 오류가 납니다.

## 반복문에서 use

`use`는 `for`나 `map` 안에서도 호출할 수 있습니다.

```jsx
function List({ items }) {
  return items.map((item) => {
    const theme = use(ThemeContext)
    return <Item key={item.id} item={item} theme={theme} />
  })
}
```

- 이 예처럼 Context를 반복해서 읽는 경우는 실무에서 드뭅니다. 반복문에서 쓸 수 있다는 점은 Hook과의 차이를 보여 주는 규칙입니다.

## Suspense와 Promise

`use`로 읽는 Promise가 이행되기 전에는 가장 가까운 위쪽 `Suspense`의 Fallback이 보입니다(Suspense는 11편).

```jsx
function Page({ albumsPromise }) {
  return (
    <Suspense fallback={<p>불러오는 중</p>}>
      <Albums albumsPromise={albumsPromise} />
    </Suspense>
  )
}
```

- `Albums`가 일시 중단되는 동안 `Suspense`가 Fallback을 보이고, 이행되면 `Albums`로 교체합니다.
- 새 Promise로 바꿔 다시 읽을 때 Fallback이 다시 뜨는 것이 싫으면 Transition으로 바꿉니다. 이전 화면을 유지한 채 새 값이 준비된 뒤 교체됩니다(자세히는 09편).

```jsx
const [promise, setPromise] = useState(
  () => fetchData('/albums'),
)
const [isPending, startTransition] = useTransition()

function refresh() {
  startTransition(() => {
    setPromise(refetchData('/albums')) // 새 Promise
  })
}
```

- `refetchData`는 캐시를 지우고 새 요청을 만드는 함수입니다. Transition이 끝나기 전에는 기존 화면이 유지되고 `isPending`이 `true`입니다.
- 사용자가 버튼에 마우스를 올릴 때 미리 요청을 시작하면(`onMouseEnter`에서 `fetchData` 호출), 클릭 시점에 이미 이행되어 있어 Fallback 없이 바로 표시됩니다.

## Reject와 Error Boundary

`use`가 읽는 Promise가 거부되면 오류가 던져져서 가장 가까운 위쪽 Error Boundary가 받습니다(자세히는 13편).

```jsx
<ErrorBoundary
  resetKeys={[albumsPromise]}
  fallbackRender={() => (
    <button onClick={handleRetry}>다시 시도</button>
  )}
>
  <Suspense fallback={<p>불러오는 중</p>}>
    <Albums albumsPromise={albumsPromise} />
  </Suspense>
</ErrorBoundary>
```

- `ErrorBoundary`는 `react-error-boundary` 패키지의 컴포넌트입니다. 이 구성이 공식 문서의 예제입니다.
- `try`/`catch`로 `use`를 감쌀 수 없으므로 오류 UI는 항상 경계의 Fallback으로 처리합니다.
- 재시도할 때는 새 Promise를 만들어 `startTransition`으로 갱신하고, `resetKeys`에 Promise를 넣어 경계가 새 Promise에서 다시 시작하게 합니다. 거부된 Promise를 그대로 다시 읽으면 같은 오류가 납니다.

## Server에서 Promise 전달

서버 컴포넌트가 만든 Promise를 클라이언트 컴포넌트에 props로 내려 주고, 클라이언트에서 `use`로 읽을 수 있습니다. 서버가 데이터를 끝까지 기다리지 않고 먼저 응답을 흘려보내는 스트리밍 방식입니다.

```jsx
// App.js (서버 컴포넌트)
export default function App() {
  const messagePromise = fetchMessage()
  return (
    <Suspense fallback={<p>메시지 기다리는 중</p>}>
      <Message messagePromise={messagePromise} />
    </Suspense>
  )
}
```

```jsx
// message.js
'use client'
import { use } from 'react'

export function Message({ messagePromise }) {
  const content = use(messagePromise)
  return <p>{content}</p>
}
```

- 서버 컴포넌트에서는 `await`로 Promise를 풀고, 클라이언트 컴포넌트에서는 렌더 중에 `await`를 쓸 수 없으므로 `use`로 풉니다.
- 서버에서 클라이언트로 넘기는 Promise의 이행 값은 직렬화 가능해야 합니다. 함수나 클래스 인스턴스는 넘길 수 없습니다.
- 어디서 풀든 Promise를 읽는 지점에서 일시 중단되고, 그 위쪽의 UI는 바로 표시됩니다. `Suspense`로 감싸면 나머지 화면이 먼저 나옵니다.
- 서버 컴포넌트의 동작 자체는 이 과목의 범위 밖입니다.

## use와 useContext

두 API는 Context 값을 읽는 결과가 같습니다. 호출 위치 규칙만 다릅니다.

| 항목 | `useContext` | `use` |
|------|--------------|-------|
| Context 읽기 | 가능 | 가능 |
| Promise 읽기 | 불가 | 가능 |
| 조건문·반복문 안 호출 | 불가(Hook 규칙) | 가능 |
| Provider 탐색 | 위쪽만 | 위쪽만 |

- Context만 읽고 조건 분기가 없다면 어느 쪽을 써도 됩니다. 조기 `return` 뒤나 조건 안에서 읽어야 할 때 `use`가 필요합니다.
- 두 API 모두 같은 컴포넌트가 렌더한 Provider의 영향은 받지 않습니다.

## 렌더 중 Promise를 생성하면 안 되는 이유

클라이언트 컴포넌트의 렌더 안에서 Promise를 만들어 `use`에 넘기면 안 됩니다. 렌더마다 새 Promise가 만들어져 Suspense Fallback이 계속 반복되기 때문입니다.

```jsx
function Albums() {
  const albums = use(fetch('/albums')) // ❌ 렌더마다 새 Promise
  // ...
}
```

- React는 마운트되기 전에 일시 중단된 렌더의 state를 보존하지 않습니다. 일시 중단되면 렌더를 처음부터 다시 시도하므로, 렌더 안에서 만든 Promise도 다시 만들어집니다.
- 새 Promise는 다시 대기 상태로 시작하므로 일시 중단하고, 다시 시도하고, 또 새 Promise를 만듭니다. 이 반복이 문제입니다.
- 이 경우 "A component was suspended by an uncached promise" 경고가 납니다.
- 렌더 안에서 새 Promise가 만들어지는 흔한 형태는 세 가지입니다.

```jsx
use(fetch('/albums'))                  // ❌ fetch가 새 Promise
use((async () => { /* ... */ })())     // ❌ 캐시 없는 async 호출
use(fetchData('/albums').then(toJson)) // ❌ then이 새 Promise
```

- 세 번째가 놓치기 쉽습니다. `fetchData`가 캐시된 Promise를 돌려줘도 `.then`이 매번 새 Promise를 만듭니다.
- 가장 좋은 방법은 Promise를 렌더 전에 만드는 것입니다. 이벤트 핸들러, 라우트 로더, 서버 컴포넌트에서 만들어 props로 내려 줍니다. 렌더 안에서 늦게 요청하면 요청이 늦게 시작하고 워터폴이 생깁니다.

## 캐시된 Promise

캐시된 Promise는 같은 입력에 대해 항상 같은 Promise 인스턴스를 돌려주는 함수나 저장소에서 가져온 Promise입니다. 인스턴스가 같아야 React가 재렌더에서 이행된 값을 바로 읽습니다.

```jsx
const cache = new Map()

export function fetchData(url) {
  if (!cache.has(url)) {
    cache.set(url, getData(url))
  }
  return cache.get(url)
}

const albums = use(fetchData('/albums')) // 같은 Promise 재사용
```

- 같은 URL이면 같은 Promise가 돌아오므로 재렌더에서 일시 중단 없이 값을 동기적으로 읽습니다.
- 캐시 방식은 쓰는 프레임워크에 따라 다릅니다. 프레임워크는 대개 자체 캐시를 제공합니다. 프레임워크 없이 직접 쓸 때는 위처럼 모듈 수준 캐시를 쓰거나 Suspense를 지원하는 데이터 소스를 씁니다.
- 직접 만든 캐시는 무효화, 오류 재시도, 메모리 해제를 직접 책임져야 해서 실무에서는 TanStack Query의 Suspense 지원 같은 라이브러리를 씁니다(자세히는 28편).
- Promise를 `useState`나 `useMemo`에 담아 두는 방법은 위의 `useState(() => fetchData(...))`처럼 초기값을 한 번만 만드는 경우에 한해 쓸 수 있습니다. 렌더마다 새로 만들지만 않으면 됩니다.

## 핵심 정리

- `use`는 렌더 중에 Promise와 Context를 읽는 API이며, 컴포넌트나 Hook 안에서 호출하고 조건문·반복문 안에서도 쓸 수 있습니다.
- Promise를 읽으면 대기 중에는 가장 가까운 `Suspense`의 Fallback이, 거부되면 가장 가까운 Error Boundary의 Fallback이 표시됩니다. `try`/`catch`로는 감쌀 수 없습니다.
- 서버 컴포넌트에서 만든 Promise를 클라이언트 컴포넌트로 내려 `use`로 읽을 수 있고, 이행 값은 직렬화 가능해야 합니다.
- `use(Context)`는 `useContext`와 같은 값을 돌려주지만 조건문과 조기 `return` 뒤에서도 호출할 수 있습니다.
- 클라이언트 컴포넌트의 렌더 안에서 Promise를 만들면 렌더마다 새 Promise가 되어 Fallback이 반복되므로, 렌더 전에 만들거나 캐시된 Promise를 씁니다.
- 새 Promise로 갱신할 때는 `startTransition`을 써서 Fallback 대신 기존 화면을 유지합니다.

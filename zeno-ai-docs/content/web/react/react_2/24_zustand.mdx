## create와 스토어 훅

Zustand는 훅 중심으로 설계된 작고 빠른 상태 관리 라이브러리입니다. `create`에 상태 생성 함수를 넘기면 React 훅이 반환됩니다. 이 훅이 스토어입니다. 작성 시점(2026-10) 공식 문서와 npm의 최신 버전은 5.0.x(5.0.15)이고, React 18 이상을 요구합니다. 설치는 `npm install zustand`입니다.

```js
import { create } from 'zustand'

const useBear = create((set) => ({
  bears: 0,
  increase: () => set((s) => ({ bears: s.bears + 1 })),
  reset: () => set({ bears: 0 }),
}))
```

- 상태 생성 함수가 돌려주는 객체에 상태 값과 액션(상태를 바꾸는 함수)을 함께 둡니다.
- 반환된 `useBear`는 컴포넌트에서 훅으로 호출합니다. Provider로 감쌀 필요가 없습니다.
- 스토어는 모듈 범위에 하나 만들어지는 전역 객체입니다. 컴포넌트가 사라져도 값이 남습니다.
- 훅 이름은 관례적으로 `use`로 시작합니다. 같은 파일에서 `export const useBear`로 내보냅니다.

```jsx
function BearCounter() {
  const bears = useBear((state) => state.bears)
  return <h1>{bears}</h1>
}
```

`create`가 돌려준 훅은 함수이면서 `getState`, `setState`, `getInitialState`, `subscribe` 메서드를 가진 객체입니다(아래 "set과 get"과 "vanilla store").

## set과 get

`set`은 상태를 바꾸고 구독자에게 알리는 함수이고, `get`은 현재 상태를 읽는 함수입니다. 둘 다 상태 생성 함수의 인자로 받습니다.

```js
const useStore = create((set, get) => ({
  count: 0,
  name: 'a',
  inc: () => set((s) => ({ count: s.count + 1 })),
  log: () => console.log(get().count),
  rename: (name) => set({ name }),
}))
```

| 호출 | 뜻 |
|------|----|
| `set({ name })` | 객체를 현재 상태에 얕게 병합 |
| `set((s) => ({ ... }))` | 이전 상태를 받아 계산한 객체를 병합 |
| `set(next, true)` | 병합하지 않고 상태 전체를 교체 |
| `get()` | 지금 시점의 상태를 반환 |

- 병합은 최상위 키에서만 일어납니다(얕은 병합). 중첩 객체를 바꾸려면 안쪽도 직접 복사해야 합니다.
- 상태는 불변으로 다룹니다. 객체와 배열을 직접 수정하지 않고 스프레드, `filter`, `map`으로 새로 만듭니다. 직접 수정하면 참조가 같아서 컴포넌트가 다시 렌더링되지 않습니다.
- `set`, `get`은 스토어 초기화 도중에 동기로 호출하면 안 됩니다. 스토어가 만들어진 뒤, 액션 안에서 호출합니다.
- 이전 상태에 의존하는 갱신은 `set((s) => ...)` 형태로 씁니다.

```js
// 중첩 갱신: 각 단계를 복사
set((s) => ({
  user: { ...s.user, address: { ...s.user.address, city } },
}))
```

## selector와 재렌더링

훅에 selector 함수를 넘기면 그 결과만 구독합니다. 선택한 값이 바뀔 때만 컴포넌트가 다시 렌더링됩니다. 결과는 `Object.is`로 비교합니다(원리는 23편).

```jsx
const bears = useBear((s) => s.bears)       // bears만 구독
const increase = useBear((s) => s.increase) // 액션도 따로 선택
```

- selector 없이 `useBear()`를 부르면 전체 상태를 구독해서 어떤 값이 바뀌어도 다시 렌더링됩니다. 값이 많은 스토어에서는 반드시 selector를 씁니다.
- 액션 함수는 스토어가 만들어진 뒤 바뀌지 않아서, 액션만 선택한 컴포넌트는 상태가 바뀌어도 다시 렌더링되지 않습니다.
- selector가 새 객체나 새 배열을 돌려주면 매번 "바뀜"으로 판정됩니다. 아래 `useShallow`로 해결합니다.
- 값마다 selector를 따로 부르면 가장 단순하고 안전합니다.

```jsx
const a = useStore((s) => s.a)
const b = useStore((s) => s.b)
```

**흔한 실수:** selector 안에서 파생 값을 매번 새로 만들어 돌려주는 것입니다. 파생 값이 객체·배열이면 selector 밖에서 `useMemo`로 계산하거나 `useShallow`를 씁니다.

## useShallow

`useShallow`는 selector가 돌려준 객체·배열을 얕게 비교하게 해 주는 훅입니다. 내용이 같으면 새 참조여도 다시 렌더링하지 않습니다.

```jsx
import { useShallow } from 'zustand/react/shallow'

const { a, b } = useStore(
  useShallow((s) => ({ a: s.a, b: s.b })),
)
const keys = useStore(useShallow((s) => Object.keys(s)))
```

- 여러 값을 한 번에 꺼낼 때, 배열을 변환해 돌려줄 때 씁니다.
- 얕은 비교는 각 키의 값이 `Object.is`로 같은지 보는 것입니다. 값이 중첩 객체이면 그 참조가 같아야 같다고 봅니다.
- 공식 문서는 selector가 렌더링마다 새 참조를 돌려주면 무한 업데이트 루프가 날 수 있다고 경고합니다. `useShallow`로 감싸거나 값을 각각 선택합니다.
- 전체 상태를 구독하는 용도로 쓰지 않습니다. 필요한 키만 골라 돌려줍니다.

## 액션을 두는 위치

공식 문서가 권하는 방식은 액션을 상태와 같은 스토어 안에 두는 것입니다. 상태와 갱신 로직이 한곳에 모이고, 캡슐화됩니다.

```js
// 권장: 스토어 안에 둠
const useStore = create((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}))

// 대안: 모듈 수준 함수
export const inc = () =>
  useStore.setState((s) => ({ count: s.count + 1 }))
```

| 항목 | 스토어 안 | 모듈 수준 |
|------|-----------|-----------|
| 호출 방법 | 훅으로 액션을 선택해서 호출 | 어디서든 함수를 호출 |
| 훅 필요 | 필요 | 불필요 |
| 코드 분할 | 스토어와 함께 묶임 | 쉬움 |

- 공식 문서는 모듈 수준 방식에 단점이 없다고 하면서도, 스토어 안에 두는 방식을 관례로 둡니다.
- 컴포넌트 밖(이벤트 리스너, 라우터 로더, 타이머)에서 액션을 불러야 하면 `useStore.getState().inc()`를 씁니다.
- 액션 이름은 "무슨 일이 일어났는가"를 드러내게 짓습니다. `setCount`보다 `incremented`나 `addItem`이 낫습니다.
- Redux처럼 dispatch와 reducer를 쓰고 싶으면 `redux` 미들웨어가 있습니다. 대부분의 앱에서는 필요 없습니다.

## 비동기 액션

Zustand는 동기와 비동기 액션을 구분하지 않습니다. 결과가 준비되었을 때 `set`을 호출하면 됩니다.

```js
const useFish = create((set) => ({
  fishes: [],
  loading: false,
  fetchFishes: async (pond) => {
    set({ loading: true })
    const res = await fetch(pond)
    set({ fishes: await res.json(), loading: false })
  },
}))
```

- `await` 앞뒤로 `set`을 여러 번 호출해도 됩니다. 각 호출이 구독자에게 알려집니다.
- 에러 처리와 로딩 상태를 직접 관리해야 합니다. 위 예제에 `try`/`catch`와 `error` 상태가 없으므로 실제로는 추가합니다.
- 요청 순서가 뒤바뀌는 경쟁 상태도 직접 막아야 합니다.
- 서버에서 가져온 데이터를 스토어에 담는 이 방식은 캐싱, 중복 요청 제거, 재시도를 직접 구현하게 됩니다. 서버 데이터는 TanStack Query에 맡기고, 스토어에는 클라이언트 상태만 두는 것이 이 과목이 권하는 분업입니다(자세히는 22편, 28편).
- 비동기 액션이 필요한 경우는 서버 데이터가 아닌 것(예: 로그인 후 클라이언트 세션 설정, 여러 단계의 클라이언트 작업 조합)입니다.

## slice 패턴

slice 패턴은 큰 스토어를 기능별 조각(slice)으로 나누어 파일을 분리하고, 하나의 스토어로 합치는 방식입니다. 각 slice는 `set`(필요하면 `get`)을 받아 상태 조각을 돌려주는 함수입니다.

```js
export const createFishSlice = (set) => ({
  fishes: 0,
  addFish: () => set((s) => ({ fishes: s.fishes + 1 })),
})
export const createBearSlice = (set) => ({
  bears: 0,
  addBear: () => set((s) => ({ bears: s.bears + 1 })),
})
```

```js
export const useBoundStore = create((...a) => ({
  ...createBearSlice(...a),
  ...createFishSlice(...a),
}))
```

- `...a`로 `set`, `get`, `store`를 모든 slice에 그대로 넘깁니다.
- slice가 다른 slice의 상태를 바꾸거나 부를 때는 `get()`으로 접근합니다. 예를 들어 `get().addBear()`를 호출하는 액션을 별도 slice에 둡니다.
- 미들웨어(`persist` 등)는 slice 안이 아니라 합쳐진 스토어에 한 번만 적용합니다. 공식 문서는 slice마다 적용하면 예기치 않은 문제가 생길 수 있다고 경고합니다.
- 스토어는 하나이므로 구독 대상도 하나입니다. selector로 필요한 slice의 값만 고릅니다.
- slice가 서로를 많이 참조하면 경계가 흐려진 것입니다. 별개의 스토어로 나누는 편이 나을 수 있습니다. Zustand는 스토어를 여러 개 만드는 것을 막지 않습니다.

## 미들웨어

미들웨어는 상태 생성 함수를 감싸 기능을 더하는 함수입니다. 안쪽 생성 함수를 인자로 받고 감싼 함수를 돌려줍니다.

| 미들웨어 | import | 하는 일 |
|----------|--------|---------|
| `persist` | `zustand/middleware` | 상태를 저장소에 저장하고 복원 |
| `devtools` | `zustand/middleware` | Redux DevTools에 연결 |
| `immer` | `zustand/middleware/immer` | draft를 직접 수정하는 문법으로 갱신 |
| `subscribeWithSelector` | `zustand/middleware` | 일부 값만 구독하는 `subscribe` 추가 |

### persist

```js
const useStore = create(
  persist(
    (set) => ({ count: 0, tmp: 'x' }),
    {
      name: 'app-storage',
      partialize: (s) => ({ count: s.count }),
    },
  ),
)
```

| 옵션 | 뜻 |
|------|----|
| `name` | 저장소 키. 필수이며 고유해야 함 |
| `storage` | 저장 방식. 기본값은 `createJSONStorage(() => localStorage)` |
| `partialize` | 저장할 필드만 골라냄 |
| `version`, `migrate` | 저장 형식이 바뀔 때 이전 데이터를 변환 |
| `skipHydration` | 초기화 때 자동 복원을 건너뜀 |
| `onRehydrateStorage` | 복원 전후에 실행할 코드 |

- 복원은 비동기일 수 있어서 `store.persist.hasHydrated`와 `store.persist.rehydrate()`로 상태를 확인하고 수동으로 복원합니다.
- 공식 문서는 `createJSONStorage`가 저장된 값을 검증하지 않는다고 주의합니다. 운영 환경에서는 Zod 같은 검증을 넣은 저장소를 직접 만듭니다.
- 토큰 같은 민감한 값을 `localStorage`에 저장하면 스크립트가 읽을 수 있습니다. 저장할 값을 `partialize`로 제한합니다.

### devtools

```js
const useStore = create(
  devtools(
    (set) => ({
      bears: 0,
      add: () =>
        set(
          (s) => ({ bears: s.bears + 1 }),
          undefined,
          'add',
        ),
    }),
    { name: 'BearStore' },
  ),
)
```

- 브라우저의 Redux DevTools 확장 프로그램과 연결해 상태 변화를 시간순으로 봅니다. 공식 문서는 `@redux-devtools/extension` 설치를 요구합니다.
- `set`의 세 번째 인자로 액션 이름을 붙입니다. 두 번째 인자는 `undefined`로 둡니다.
- `enabled` 옵션의 기본값은 개발 환경에서 `true`, 운영 환경에서 `false`입니다.

### immer

```js
import { immer } from 'zustand/middleware/immer'

const useStore = create(immer((set) => ({
  user: { first: 'a', last: 'b' },
  rename: (f) => set((s) => { s.user.first = f }),
})))
```

- `immer` 라이브러리를 따로 설치해야 합니다.
- `set` 안의 함수에서 draft를 직접 수정하는 것처럼 쓰면 Immer가 불변 갱신으로 바꿔 줍니다. 깊은 중첩 갱신에서 스프레드 중첩이 사라집니다.
- 중첩이 얕은 스토어에는 필요 없습니다. 의존성이 하나 늘어납니다.

### subscribeWithSelector

```js
const useStore = create(subscribeWithSelector((set) => ({
  count: 0,
})))

useStore.subscribe(
  (s) => s.count,
  (count, prev) => console.log(count, prev),
)
```

- 스토어에 selector 형태의 `subscribe`를 추가합니다. 선택한 값이 바뀔 때만 리스너가 호출됩니다.
- 옵션으로 `equalityFn`(비교 함수), `fireImmediately`(구독 즉시 한 번 호출)를 줍니다.
- React 컴포넌트 밖의 부수 효과(저장, 로깅, 외부 라이브러리 동기화)에 씁니다.

미들웨어는 겹쳐 쓸 수 있고 바깥에서 안쪽으로 감쌉니다. 공식 TypeScript 가이드는 타입 변형을 막으려고 `devtools`를 마지막에 두라고 안내합니다.

## vanilla store

`createStore`는 React와 무관한 순수 스토어를 만듭니다. `setState`, `getState`, `getInitialState`, `subscribe`를 가진 객체를 돌려줍니다.

```js
import { createStore, useStore } from 'zustand'

const counterStore = createStore((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}))

counterStore.getState().inc()
counterStore.subscribe((state) => console.log(state.count))
```

React에서는 `useStore(store, selector)` 훅으로 읽습니다.

```jsx
const count = useStore(counterStore, (s) => s.count)
```

- `create`가 돌려준 훅도 내부적으로 이 vanilla 스토어와 `useStore`로 만들어집니다.
- 스토어를 React 밖(모듈, 서버 로직, 테스트)에서 쓰거나, 아래의 Context 주입처럼 인스턴스를 직접 관리하고 싶을 때 씁니다.

## Context로 스토어 주입

전역 스토어 대신 컴포넌트 트리 단위로 스토어 인스턴스를 만들어야 할 때 Context를 씁니다. 스토어를 만드는 팩토리 함수를 두고, Provider에서 인스턴스를 만들어 Context로 내려 줍니다.

```tsx
const BearContext = createContext<BearStore | null>(null)

function BearProvider({ children, ...props }: Props) {
  const [store] = useState(() => createBearStore(props))
  return <BearContext value={store}>{children}</BearContext>
}
```

```tsx
function useBearContext<T>(
  selector: (s: BearState) => T,
): T {
  const store = useContext(BearContext)
  if (!store) throw new Error('Missing BearProvider')
  return useStore(store, selector)
}
```

- `useState`의 초기화 함수로 스토어를 만들어 Provider가 유지되는 동안 같은 인스턴스를 씁니다.
- Provider의 props를 초기값으로 넘기는 "props로 상태 초기화" 방식도 같은 구조입니다.
- 쓰는 이유는 세 가지입니다. 같은 컴포넌트를 여러 번 렌더링할 때 인스턴스를 분리하기, 테스트에서 격리된 스토어 주입하기, SSR에서 요청별 스토어 만들기.
- 이 방식에서도 selector로 필요한 값만 구독합니다. Context 값은 스토어 인스턴스이고 바뀌지 않으므로 Context 자체로는 재렌더링이 생기지 않습니다.

## Next.js·SSR 주의

서버에서 모듈 범위의 전역 스토어를 쓰면 안 됩니다. 서버는 여러 사용자의 요청을 처리하는데 전역 스토어는 요청 사이에 공유되어, 한 사용자의 상태가 다른 사용자의 응답에 섞입니다. 공식 Next.js 가이드의 해법은 요청별 스토어입니다.

- `createStore`로 스토어를 만드는 팩토리 함수를 둡니다.
- Provider에서 `useState`로 인스턴스를 한 번 만들어 Context로 내려 줍니다(위 절의 구조와 같습니다).
- 컴포넌트는 Context를 읽는 커스텀 훅으로 접근합니다.

```tsx
export const createCounterStore = (init = defaultInit) =>
  createStore<CounterStore>()((set) => ({
    ...init,
    increment: () => set((s) => ({ count: s.count + 1 })),
  }))
```

| 주의점 | 이유 |
|--------|------|
| Server Component에서 스토어를 읽거나 쓰지 않음 | 서버 컴포넌트는 훅과 Context를 쓸 수 없고 상태를 갖지 않음 |
| 서버와 클라이언트가 같은 초기값으로 시작 | 서버 렌더 결과와 달라지면 hydration 불일치 오류 |
| 스토어를 쓰는 컴포넌트는 `use client` | 훅을 쓰므로 Client Component |

- hydration 불일치는 서버가 만든 HTML과 클라이언트의 첫 렌더링 결과가 다를 때 생깁니다. 서버에는 `localStorage`가 없으므로 `persist`로 복원한 값을 첫 렌더링에서 바로 쓰면 달라집니다.
- 그래서 `persist`를 SSR에서 쓸 때는 첫 렌더링을 서버와 같은 초기값으로 맞추고, `skipHydration` 옵션과 `rehydrate()` 호출로 마운트 후에 복원합니다. 복원 여부는 `hasHydrated`로 확인해 그동안은 자리 표시를 보여 줍니다.
- `createJSONStorage`는 저장소 getter를 지연 평가해서, 서버에서 모듈을 불러오는 것만으로는 `localStorage` 에러가 나지 않습니다.
- Next.js의 서버·클라이언트 구분은 Next.js 과목에서 다룹니다.

## TypeScript 타이핑

TypeScript에서는 `create`를 두 번 호출하는 커링 형태 `create<T>()(...)`를 씁니다. 타입 인자를 먼저 주고, 상태 생성 함수를 다음에 줍니다.

```ts
interface BearState {
  bears: number
  feed: (n: number) => void
}

export const useBearStore = create<BearState>()((set) => ({
  bears: 2,
  feed: (n) => set((s) => ({ bears: s.bears + n })),
}))
```

- 상태와 액션 타입을 한 인터페이스에 정의하면 필드를 빠뜨리거나 잘못된 타입을 넣을 때 컴파일 오류가 납니다. 결과 타입은 `UseBoundStore<StoreApi<BearState>>`입니다.
- 미들웨어는 `create` 안에서 바로 감싸야 타입 추론이 동작합니다. `create<T>()(persist((set) => ..., opts))` 형태입니다.
- `combine` 미들웨어는 초기값에서 상태 타입을 추론해 타입 주석을 줄여 줍니다. 대신 초기 상태 객체와 액션 생성 함수를 따로 받는 구조라서 상태와 액션을 한 인터페이스로 묶는 방식과 모양이 다릅니다.
- slice에는 `StateCreator` 타입을 씁니다. 인자는 전체 상태 타입, 미들웨어 변이자 목록(없으면 빈 배열 둘), 이 slice의 타입 순서입니다.

```ts
const createBearSlice: StateCreator<
  BearSlice & FishSlice, [], [], BearSlice
> = (set) => ({
  bears: 0,
  addBear: () => set((s) => ({ bears: s.bears + 1 })),
})
```

- selector의 반환 타입은 자동으로 추론됩니다. `useBearStore((s) => s.bears)`는 `number`입니다.
- 미들웨어를 쓰면 `StateCreator`의 빈 배열 자리에 해당 미들웨어의 변이자(`['zustand/persist', State]` 등)를 채웁니다.

## 테스트와 스토어 초기화

스토어는 모듈 범위의 전역 객체라서 테스트 사이에 상태가 남습니다. 테스트마다 초기 상태로 되돌려야 합니다.

방법은 두 가지입니다.

- 단일 스토어: 초기 상태를 가져와 교체합니다.

```js
useStore.setState(useStore.getInitialState(), true)
```

- 여러 스토어: `create`를 감싸는 모의(mock) 파일을 두고, 스토어가 만들어질 때 초기 상태로 되돌리는 함수를 목록에 모은 뒤 `afterEach`에서 모두 실행합니다. Jest는 `__mocks__/zustand.ts`, Vitest는 같은 파일과 `vi.mock('zustand')`로 구성하고, 공식 가이드에 전체 코드가 있습니다. 초기화 함수는 React의 `act`로 감쌉니다.

두 번째 인자 `true`는 병합이 아닌 교체를 뜻합니다. 병합으로 되돌리면 테스트 중에 추가된 키가 남습니다.

- 컴포넌트 테스트에서는 화면의 결과를 확인합니다. React Testing Library로 렌더링하고 사용자 동작을 실행한 뒤 화면 텍스트를 확인합니다(자세히는 34편, 35편).
- 스토어 로직만 검사할 때는 컴포넌트 없이 `getState()`로 상태를 읽고 액션을 호출합니다.

```js
useCounterStore.getState().inc()
expect(useCounterStore.getState().count).toBe(1)
```

- Context로 스토어를 주입하는 구조라면 테스트마다 새 인스턴스를 만들어 Provider에 넘기므로 초기화가 필요 없습니다.
- 앱 코드에서 로그아웃 시 상태를 비우는 용도로도 같은 방식(`getInitialState()`로 교체)을 씁니다.

## v4에서 v5로의 변경점

v5는 React 18 이상을 요구하는 메이저 버전입니다. v4에서 올릴 때 확인할 항목은 다음과 같습니다.

| 변경 | 내용과 대응 |
|------|-------------|
| 요구 버전 | React 18 이상, TypeScript 4.5 이상. ES5와 UMD·SystemJS 지원 중단 |
| default export 제거 | `import create from 'zustand'`을 `import { create } from 'zustand'`으로 |
| 사용자 지정 비교 함수 제거 | `create`가 더 이상 두 번째 인자의 비교 함수를 받지 않음. 필요하면 `zustand/traditional`의 `createWithEqualityFn`(peer 의존성 `use-sync-external-store` 설치) 또는 `useShallow` |
| 불안정한 selector 금지 | selector가 새 참조를 돌려주면 무한 루프. `useShallow`를 쓰거나 안정된 폴백 값을 사용 |
| `setState`의 replace 타입 | `replace: true`일 때 상태 전체를 줘야 함(TypeScript 오류) |
| `persist` 동작 | 스토어 생성 시 초기 상태를 저장소에 자동 저장하지 않음 |
| 지원 중단 기능 제거 | v4의 deprecated 기능이 모두 삭제됨. 먼저 최신 v4로 올려 경고를 해결 |

```js
// v4 → v5: 새 참조를 만드는 selector
const [v, setV] = useStore((s) => [s.v, s.setV]) // ❌
const [v2, setV2] = useStore(                    // ✅
  useShallow((s) => [s.v, s.setV]),
)
```

- 가장 흔한 사고는 selector 안정성입니다. v4에서 조용히 넘어가던 `(s) => ({ ... })`와 `(s) => [ ... ]`가 v5에서는 렌더링 루프로 이어질 수 있습니다.
- 버전 이전 외에 v3에서 쓰던 `zustand/context`는 이전 버전용 문서로 분리되어 있습니다. 지금은 위의 `createStore`와 Context 조합을 씁니다.

## 핵심 정리

- `create`가 돌려주는 훅이 스토어이고 Provider가 필요 없으며, 상태와 액션을 한 객체에 둡니다.
- `set`은 최상위 키를 얕게 병합하고(교체는 `true`), 상태는 불변으로 다루며, 비동기 액션은 준비되면 `set`을 부르면 됩니다.
- selector로 필요한 값만 구독하고, 새 객체·배열을 돌려줄 때는 `useShallow`를 씁니다.
- slice로 파일을 나누고 미들웨어(`persist`, `devtools`, `immer`, `subscribeWithSelector`)는 합친 스토어에 적용합니다.
- 서버에서는 요청별 스토어를 `createStore`와 Context로 만들고, 서버와 클라이언트의 첫 렌더링 값을 같게 맞춥니다.
- 테스트마다 `setState(getInitialState(), true)`로 초기화하고, v5에서는 selector 안정성과 default export 제거를 확인합니다.

## Unit

단위 테스트(unit test)는 작은 코드 하나를 나머지에서 분리해서 검증하는 테스트입니다. 대상이 의존하는 것은 없거나 가짜로 바꿉니다.

```ts
// 순수 함수와 reducer가 가장 쉬운 대상
test('총액은 수량을 곱한다', () => {
  expect(totalPrice({ price: 1200, qty: 3 })).toBe(3600)
})
test('cleared는 목록을 비운다', () => {
  const state = { items: ['a'] }
  const next = reducer(state, { type: 'cleared' })
  expect(next).toEqual({ items: [] })
})
```

- React에서 단위 테스트의 전형적인 대상은 포맷 함수, 검증 함수, reducer(02편), 값만 계산하는 유틸입니다.
- 컴포넌트도 단위로 테스트할 수 있습니다. 이때 자식 컴포넌트, 훅, 네트워크를 가짜로 바꿔 그 컴포넌트만 봅니다.
- 빠르고 실패 원인이 좁게 드러나는 대신, 부품이 서로 맞물리는 방식은 검증하지 못합니다.

## Integration

통합 테스트(integration test)는 여러 단위가 함께 동작하는 것을 검증합니다. 단위 사이를 가짜로 끊지 않고 실제 코드로 연결합니다.

- React에서는 컴포넌트 트리 하나(페이지, 폼 + 목록)에 Context, 라우터, 데이터 캐시를 실제로 붙여 렌더하고 사용자 동작을 따라갑니다. 가짜로 바꾸는 곳은 네트워크 경계 정도입니다(아래 "MSW 네트워크 모킹").
- 테스트 하나가 부품 여러 개의 연결 오류(props 이름 불일치, Provider 누락)를 한 번에 잡습니다.
- 단위 테스트보다 느리고 준비할 것이 많습니다. 컴포넌트를 묶어서 테스트하는 구체적인 방법은 35편에서 다룹니다.

단위와 통합의 경계는 팀마다 정의가 다릅니다. Practical Test Pyramid 글도 용어에 매달리기보다 팀 안에서 범위 기준을 일관되게 쓰라고 정리합니다.

## E2E

E2E(end-to-end) 테스트는 실제 브라우저에서 실제에 가까운 환경 전체를 처음부터 끝까지 사용자처럼 조작하는 테스트입니다. 서버와 데이터베이스까지 가능한 한 가짜 없이 지나갑니다.

- 로그인 → 상품 선택 → 결제 같은 핵심 경로를 검증합니다.
- 가장 현실적인 대신 느리고, 환경 때문에 실패하는 일이 잦고, 실패했을 때 원인을 찾기 어렵습니다.
- React 앱의 E2E에는 Playwright가 많이 쓰입니다. Chromium, WebKit, Firefox를 모두 지원하는 테스트 프레임워크이며 `npm init playwright@latest`로 시작합니다. 이 과목에서는 다루지 않습니다.

| 구분 | 범위 | 실행 환경 | 속도 |
|------|------|-----------|------|
| 단위 | 함수·컴포넌트 하나 | Node + jsdom | 가장 빠름 |
| 통합 | 컴포넌트 트리, 모듈 묶음 | Node + jsdom | 빠름 |
| E2E | 앱 전체 | 실제 브라우저 | 느림 |

## 테스트 피라미드와 트로피

두 모델은 세 종류 테스트를 얼마나 배분할지에 대한 지침입니다.

| 모델 | 제안자 | 배분 |
|------|--------|------|
| 테스트 피라미드 | Martin Fowler 사이트의 Practical Test Pyramid 글 | 작고 빠른 단위 테스트를 많이, 굵은 테스트는 적게, 상위 UI 테스트는 아주 적게 |
| 테스트 트로피 | Kent C. Dodds | 정적 검사, 단위, 통합, E2E의 네 층. 통합 테스트의 비중이 가장 큼 |

- 피라미드는 속도와 유지 비용이 근거입니다. 아래층일수록 빠르고 고치기 쉽습니다.
- 트로피는 프런트엔드에서 통합 테스트가 비용 대비 신뢰를 가장 많이 준다는 주장입니다. 컴포넌트 단위로 가짜를 많이 쓸수록 실제 앱에서 깨지는 것을 놓친다고 봅니다.
- 트로피의 맨 아래 층인 정적 검사는 TypeScript와 ESLint입니다. 코드를 실행하지 않고 오타와 타입 오류를 잡습니다(자세히는 33편).
- React 컴포넌트가 중심인 앱에서는 통합에 가까운 컴포넌트 테스트를 중심으로, 계산 로직은 단위로, 핵심 경로 몇 개는 E2E로 두는 구성이 일반적입니다.

## 사용자 관점

Testing Library의 기본 원칙은 테스트가 소프트웨어를 쓰는 방식을 닮을수록 더 큰 신뢰를 준다는 것입니다. 컴포넌트 인스턴스가 아니라 DOM 노드를 대상으로, 사용자가 보고 누르는 것을 기준으로 씁니다.

| 사용자가 아는 것 (테스트 대상) | 구현 세부 (테스트 대상 아님) |
|-------------------------------|------------------------------|
| 화면의 글자, 버튼 이름, 입력의 레이블 | State 변수 이름, 내부 메서드 |
| 클릭하면 나타나는 결과 | 자식 컴포넌트의 이름과 개수 |
| 접근성 역할(button, heading) | CSS 클래스, DOM 구조 깊이 |

```tsx
// ❌ 구현 세부: 클래스·구조가 바뀌면 깨진다
container.querySelector('.btn-primary > span')
// ✅ 사용자 관점: 리팩터링해도 유지된다
screen.getByRole('button', { name: '저장' })
```

- 사용자 관점으로 쓴 테스트는 내부 구조를 바꿔도 동작이 같으면 통과합니다. 구현 세부를 따라가는 테스트는 리팩터링마다 깨집니다.
- 같은 이유로 `useState`가 몇 번 호출되었는지, 어떤 자식이 렌더됐는지를 단언하지 않습니다.
- 사용자 관점의 쿼리가 곧 접근성 검사입니다. 역할이나 레이블로 못 찾는 요소는 스크린 리더 사용자도 못 찾을 가능성이 높습니다(자세히는 32편).

## React Testing Library

React Testing Library(RTL)는 DOM Testing Library 위에 React용 `render` 등을 얹은 라이브러리입니다. 컴포넌트를 실제 DOM(jsdom)에 렌더하고 DOM 노드로 검사합니다.

```bash
npm install -D @testing-library/react @testing-library/dom
npm install -D @testing-library/jest-dom
npm install -D @testing-library/user-event
```

- `@testing-library/dom`은 `@testing-library/react`의 peer dependency라서 함께 설치합니다.
- `@testing-library/jest-dom`은 `toBeInTheDocument` 같은 DOM 전용 단언(matcher)을 추가합니다. `@testing-library/user-event`는 사용자 입력 시뮬레이션입니다(아래 "user-event").

```tsx
import { render, screen } from '@testing-library/react'

test('이름을 보여 준다', () => {
  render(<Greeting name="Kim" />)
  expect(screen.getByText('안녕하세요, Kim')).toBeInTheDocument()
})
```

- `render`는 컴포넌트를 `document.body` 안의 `div`에 렌더합니다. 반환값에는 `container`, `rerender`, `unmount`가 있습니다.
- `screen`은 `document.body`에 묶인 쿼리 모음입니다. `render` 결과에서 쿼리를 꺼내지 않고 `screen`을 쓰는 방식이 표준입니다.
- 각 테스트가 끝나면 렌더한 트리가 `cleanup`으로 정리됩니다. 테스트 프레임워크가 전역 `afterEach`를 제공하면 자동으로 호출됩니다.
- 자주 쓰는 jest-dom 단언은 다음과 같습니다.

| 단언 | 검사 |
|------|------|
| `toBeInTheDocument()` | 문서에 존재 |
| `toBeVisible()` | 화면에 보임 |
| `toBeDisabled()` / `toBeEnabled()` | 비활성 / 활성 |
| `toHaveTextContent(text)` | 텍스트 포함 |
| `toHaveValue(value)` | 입력의 값 |
| `toBeChecked()` | 체크 상태 |
| `toHaveAttribute(name, value)` | 속성 값 |

## Vitest / Jest

테스트 러너는 테스트 파일을 찾아 실행하고 `test`, `expect`, mock 같은 API를 제공합니다. Vite 기반 프로젝트에서는 Vitest를, Jest를 이미 쓰는 프로젝트에서는 Jest를 씁니다.

| 항목 | Vitest | Jest |
|------|--------|------|
| 공식 문서 기준 버전 | 5.0 | 30.5 |
| 설정 | `vite.config`를 그대로 공유, 별도 `vitest.config` 가능 | `jest.config` 별도 |
| 기본 환경 | `node` | `node` |
| DOM 환경 설정 | `environment: 'jsdom'` + `jsdom` 설치 | `testEnvironment: 'jsdom'` + `jest-environment-jsdom` 설치 |
| `test`·`expect` 전역 | 기본 꺼짐(`globals: true`로 켬) | 기본 제공 |
| mock 함수 | `vi.fn()`, `vi.mock()` | `jest.fn()`, `jest.mock()` |
| 요구 사항 | Vite 6.4 이상, Node 22.12 이상 | 별도 번들러 불필요, 변환은 Babel 또는 ts-jest |

- Vitest는 Jest API와 대부분 호환되어 대체가 쉽습니다. 이전할 때 바뀌는 대표 항목은 `jest.fn`이 `vi.fn`으로, `jest.requireActual`이 `vi.importActual`로 바뀌는 것과 전역이 기본 꺼짐이라는 점입니다.
- 테스트 파일 이름은 `.test.` 또는 `.spec.`을 포함해야 기본 설정에서 인식됩니다.
- 실행은 `vitest`(감시 모드)와 `vitest run`(한 번 실행)입니다.

Vitest + RTL의 최소 설정은 다음과 같습니다.

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: ['./vitest.setup.ts'],
  },
})
```

```ts
// vitest.setup.ts
import '@testing-library/jest-dom/vitest'
import { afterEach } from 'vitest'
import { cleanup } from '@testing-library/react'

afterEach(() => cleanup())
```

- `setupFiles`는 각 테스트 파일 실행 전에 돌아가서 공통 준비를 합니다.
- Vitest에서 전역이 꺼져 있으면 RTL이 전역 `afterEach`를 찾지 못해 자동 정리가 되지 않습니다. 위처럼 직접 `cleanup`을 호출하거나 `globals: true`를 켭니다. 정리가 안 되면 앞 테스트의 DOM이 남아 `getBy`가 여러 요소를 찾고 실패합니다.
- TypeScript에서 jsdom 환경 타입은 `tsconfig.json`의 `types`에 `vitest/jsdom`을 넣어 인식시킵니다. `globals: true`이면 `vitest/globals`도 넣습니다.
- Jest에서는 jest-dom을 `import '@testing-library/jest-dom'`으로 가져옵니다.

## getByRole

`getByRole`은 접근성 트리의 역할(role)과 이름으로 요소를 찾는 쿼리입니다. 사용자가 화면을 이해하는 방식과 가장 가깝습니다.

```tsx
screen.getByRole('button', { name: '저장' })
screen.getByRole('heading', { level: 2 })
screen.getByRole('checkbox', { checked: true })
screen.getByRole('textbox', { name: /이메일/i })
```

- 역할은 HTML 요소가 가진 암묵적 역할을 인식합니다. `button` 요소는 `role` 속성 없이도 `button`이고, `h1`–`h6`은 `heading`, `a`(href 있음)는 `link`, `input type=checkbox`는 `checkbox`입니다.
- `name`은 접근 가능한 이름입니다. 버튼 안의 글자, 연결된 레이블, `aria-label`이 해당합니다. 문자열 또는 정규식을 씁니다.
- 상태 옵션으로 `checked`, `pressed`, `selected`, `expanded`, `busy`를 걸 수 있고, 제목은 `level`로 구분합니다.
- `aria-hidden`이거나 화면에서 숨겨진 요소는 기본적으로 제외됩니다(`hidden: false`가 기본값). 숨겨진 요소도 찾으려면 `hidden: true`입니다.
- 못 찾았을 때 에러 메시지에 현재 DOM에서 접근 가능한 역할 목록이 출력됩니다. 어떤 역할로 쓸 수 있는지 이 목록으로 확인합니다.
- 접근성 트리 계산은 DOM이 클 때 비용이 큽니다. 느리면 `getByLabelText` 같은 쿼리로 바꾸는 것이 방법입니다.

**흔한 실수:** `name` 없이 `getByRole('button')`을 쓰는 것입니다. 버튼이 둘 이상이면 여러 요소가 찾아졌다는 에러가 납니다. 역할과 이름을 함께 씁니다.

## getByLabelText

`getByLabelText`는 레이블 텍스트로 폼 요소를 찾습니다. 사용자가 폼을 채울 때 레이블을 보고 칸을 찾는 방식 그대로입니다.

```tsx
// <label htmlFor="email">이메일</label>
// <input id="email" />
screen.getByLabelText('이메일')
screen.getByLabelText('이메일', { selector: 'input' })
```

- 다음 연결 방식이 모두 인식됩니다: `label`의 `htmlFor`와 입력의 `id`, `label`로 입력을 감싸는 형태, `aria-labelledby`, `aria-label`.
- 문자열은 기본적으로 정확히 일치해야 합니다(`exact: true`). 같은 레이블 텍스트가 여러 요소에 있으면 `selector`로 좁힙니다.
- 레이블이 없는 입력은 이 쿼리로 못 찾습니다. 그 실패는 테스트 문제가 아니라 접근성 결함의 신호이므로 `placeholder`로 우회하지 말고 레이블을 추가합니다. React에서 `htmlFor`와 `id`를 안정적으로 연결하는 방법은 05편(useId)입니다.
- 역할이 `textbox`처럼 분명한 입력은 `getByRole('textbox', { name: '이메일' })`도 같은 요소를 찾습니다. 폼 입력은 둘 중 편한 쪽을 씁니다.

## 쿼리 우선순위

쿼리는 이름의 접두사로 동작이 갈리고, 같은 접두사 안에서 무엇으로 찾는지에 우선순위가 있습니다.

| 접두사 | 0개 | 1개 | 2개 이상 | 재시도 |
|--------|-----|-----|----------|--------|
| `getBy` | 에러 | 요소 | 에러 | 없음 |
| `queryBy` | `null` | 요소 | 에러 | 없음 |
| `findBy` | 에러 | 요소 | 에러 | 있음 |
| `getAllBy` | 에러 | 배열 | 배열 | 없음 |
| `queryAllBy` | 빈 배열 | 배열 | 배열 | 없음 |
| `findAllBy` | 에러 | 배열 | 배열 | 있음 |

- 있어야 하는 요소는 `getBy`, 없음을 단언할 때는 `queryBy`(`expect(queryByText(...)).not.toBeInTheDocument()`), 나중에 나타날 요소는 `findBy`입니다.

권장 우선순위는 위에서 아래입니다.

| 순위 | 쿼리 | 용도 |
|------|------|------|
| 1 | `getByRole` | 접근성 트리의 모든 요소. 첫 선택 |
| 1 | `getByLabelText` | 폼 필드 |
| 1 | `getByPlaceholderText` | 레이블이 없을 때의 대안 |
| 1 | `getByText` | 버튼이 아닌 정적 텍스트 |
| 1 | `getByDisplayValue` | 입력에 채워진 값 |
| 2 | `getByAltText` | 이미지 등 대체 텍스트 |
| 2 | `getByTitle` | `title` 속성. 스크린 리더 지원이 일정하지 않음 |
| 3 | `getByTestId` | 다른 방법이 없는 경우의 최후 수단 |

- 1순위 쿼리는 모든 사용자에게 보이는 속성으로 찾고, 2순위는 의미는 있지만 환경에 따라 전달이 다르고, 3순위 `data-testid`는 사용자가 전혀 인식하지 못하는 속성입니다.
- 위 순위에서 아래로 내려가야 한다면 컴포넌트의 접근성부터 의심합니다.

## user-event

`user-event`는 클릭, 타이핑 같은 사용자 상호작용을 실제 사용자처럼 재현하는 라이브러리입니다. 한 동작에서 브라우저가 일으키는 이벤트 흐름(포커스, 키 입력, 입력 이벤트)을 함께 발생시킵니다.

```tsx
import userEvent from '@testing-library/user-event'

test('이름을 입력해 제출한다', async () => {
  const user = userEvent.setup() // render보다 먼저
  render(<SignupForm />)
  await user.type(screen.getByLabelText('이름'), 'Kim')
  const submit = screen.getByRole('button', { name: '가입' })
  await user.click(submit)
})
```

- v14의 권장 방식은 `userEvent.setup()`으로 인스턴스를 만들고 `user.click`, `user.type`처럼 호출하는 것입니다. `render` 앞에서 호출하고, `beforeEach` 같은 훅 안에서는 호출하지 않습니다.
- 모든 메서드는 비동기라서 `await`가 필요합니다.
- 자주 쓰는 메서드: `click`, `dblClick`, `type`, `clear`, `selectOptions`, `keyboard`, `tab`, `hover`, `upload`. `type`의 `{Enter}` 같은 표기로 특수 키를 보냅니다(`user.type(el, 'abc{Enter}')`).
- `fireEvent`는 지정한 DOM 이벤트 하나만 발생시킵니다. 실제 사용자 흐름에서는 여러 이벤트가 일어나므로 가능한 한 `user-event`를 씁니다.
- `user-event`는 보이지 않는 요소를 클릭하거나 비활성 입력에 타이핑하지 않습니다. 사용자가 못 하는 일은 테스트도 못 합니다.

**흔한 실수:** `await`를 빼먹는 것입니다. 동작이 끝나기 전에 단언이 실행되어 간헐적으로 실패합니다.

## act

`act`는 React의 업데이트(렌더, Effect, State 변경)를 모두 처리하고 DOM에 반영한 뒤에 코드를 이어가게 하는 테스트 도우미입니다. 이름은 Arrange-Act-Assert 패턴에서 왔습니다.

- React Testing Library의 `render`, 이벤트 발생, `findBy`, `waitFor`는 내부에서 `act`로 감싸 줍니다. 평소 테스트에서는 `act`를 직접 쓸 일이 거의 없습니다.
- 직접 써야 하는 경우는 React가 모르는 경로로 업데이트가 일어날 때입니다. 가짜 타이머를 직접 진행시키거나, 외부 스토어의 상태를 코드로 바꾸는 경우입니다.

```tsx
import { act, render, screen } from '@testing-library/react'

test('1초 뒤 숫자가 올라간다', () => {
  vi.useFakeTimers()
  render(<Clock />)
  act(() => { vi.advanceTimersByTime(1000) })
  expect(screen.getByText('1초')).toBeInTheDocument()
})
```

- 위 코드에서 `act` 없이 `vi.advanceTimersByTime`만 호출하면 타이머 콜백은 실행되지만 React가 업데이트를 반영하지 않아 DOM이 `0초` 그대로입니다.
- `act`는 `react`에서 가져오는 것이 공식 방식이고, RTL이 같은 함수를 `@testing-library/react`로도 제공합니다. RTL 환경에서는 `IS_REACT_ACT_ENVIRONMENT`가 자동으로 켜집니다. RTL 없이 직접 `createRoot`로 렌더하는 테스트에서는 이 전역 값을 `true`로 설정해야 `act` 경고가 사라집니다.
- 비동기 업데이트를 기다릴 때는 `await act(async () => { ... })` 형태입니다.

**흔한 실수:** RTL이 이미 감싸 주는 호출까지 `act`로 다시 감싸는 것입니다. 불필요하고 코드만 복잡해집니다. 또 `not wrapped in act(...)` 경고가 뜨는 것은 대개 테스트가 끝나기 전에 일어나는 비동기 업데이트를 기다리지 않았다는 신호입니다. `act`를 덧씌우기보다 `await findBy...`로 그 결과를 기다립니다.

## findBy와 waitFor

화면이 비동기로 바뀌는 경우(네트워크, 타이머)에는 결과가 나타날 때까지 기다리는 쿼리가 필요합니다.

```tsx
// findBy: 나타날 때까지 기다린다 (기본 최대 1000ms)
const h = await screen.findByRole('heading', {
  name: 'Kim',
})

// waitFor: 콜백이 에러를 던지지 않을 때까지 재시도
await waitFor(() => {
  const status = screen.getByRole('status')
  expect(status).toHaveTextContent('저장됨')
})
```

- `findBy`는 `getBy`와 `waitFor`를 합친 것입니다. 요소가 나타나기를 기다릴 때는 `findBy`가 `waitFor`보다 간결합니다.
- `waitFor`는 콜백을 즉시 한 번 실행하고, 이후 50ms 간격으로 재시도하며, 기본 제한 시간은 1000ms입니다. DOM 변경(자식 추가·제거, 속성 변경)을 감지하면 바로 다시 실행합니다.
- 콜백이 에러를 던지는 동안 재시도합니다. 거짓 값을 반환하는 것만으로는 재시도되지 않습니다. 반드시 `expect`처럼 던지는 코드여야 합니다.
- 사라지기를 기다릴 때는 `waitForElementToBeRemoved`입니다. 첫 인수에 요소 또는 요소를 반환하는 콜백을 넘기고, 이미 없으면 에러입니다.
- 시간 제한은 마지막 인수로 바꿉니다: `await findByText('완료', {}, { timeout: 3000 })`.

```tsx
// 로딩 문구가 사라지기를 기다린다
await waitForElementToBeRemoved(() =>
  screen.queryByText('저장 중'),
)
```

**흔한 실수:**

- `await waitFor(() => screen.getByText('x'))`처럼 `findBy`로 쓸 것을 `waitFor`로 쓰는 것. 동작은 같지만 `findByText`가 읽기 쉽습니다.
- `waitFor` 콜백 안에서 클릭 같은 부수 효과를 일으키는 것. 재시도할 때마다 반복 실행됩니다. 동작은 `waitFor` 밖에서 하고 안에는 단언만 둡니다.
- 이미 화면에 있는 요소를 확인하려고 `findBy`를 쓰는 것. 동기 상황은 `getBy`로 충분합니다.

## MSW 네트워크 모킹

MSW(Mock Service Worker)는 네트워크 요청을 가로채 가짜 응답을 돌려주는 라이브러리입니다. 컴포넌트가 쓰는 `fetch`나 데이터 라이브러리의 코드를 바꾸지 않고, 요청이 나가는 경계에서 응답만 대체합니다.

버전 차이: MSW 3.0에서 import 경로가 `msw/http`가 되었고 Node 22 이상이 필요합니다. 2.x에서는 `msw`에서 `http`와 `HttpResponse`를 가져옵니다.

```ts
// src/mocks/handlers.ts
import { http, HttpResponse } from 'msw/http'

export const handlers = [
  http.get('/api/user', () => {
    return HttpResponse.json({ id: 1, name: 'Kim' })
  }),
]
```

```ts
// src/mocks/node.ts
import { setupServer } from 'msw/node'
import { handlers } from './handlers'

export const server = setupServer(...handlers)
```

- 핸들러(`http.get`, `http.post`)가 어떤 요청을 어떤 응답으로 바꿀지 정하고, `setupServer`가 Node 프로세스(테스트)에서 이를 활성화합니다. 브라우저에서는 `setupWorker`를 씁니다.
- 테스트 설정 파일에서 세 시점에 연결합니다.

```ts
// vitest.setup.ts
import { afterAll, afterEach, beforeAll } from 'vitest'
import { server } from './src/mocks/node'

beforeAll(() => {
  server.listen({ onUnhandledFrame: 'error' })
})
afterEach(() => server.resetHandlers())
afterAll(() => server.close())
```

- `listen()`은 테스트 전에 가로채기를 시작하고, `resetHandlers()`는 테스트마다 추가한 핸들러를 되돌리고, `close()`는 끝에 원래 상태로 복구합니다.
- 핸들러가 없는 요청의 처리는 `onUnhandledFrame`으로 정합니다. 기본값은 경고 후 요청을 그대로 보내는 `'warn'`이고, `'error'`는 에러로 막으며, `'bypass'`는 조용히 통과시킵니다. 실수로 진짜 서버에 요청이 나가는 것을 막으려면 `'error'`로 둡니다. 2.x에서는 같은 옵션 이름이 `onUnhandledRequest`입니다.
- 특정 테스트에서만 다른 응답이 필요하면 `server.use()`로 핸들러를 덧씌웁니다. `resetHandlers()` 덕분에 다음 테스트에는 영향이 없습니다.

```tsx
test('서버 오류면 안내 문구를 보인다', async () => {
  server.use(
    http.get('/api/user', () => {
      return new HttpResponse(null, { status: 500 })
    }),
  )
  render(<Profile />)
  const alert = await screen.findByRole('alert')
  expect(alert).toBeInTheDocument()
})
```

- 응답 종류: `HttpResponse.json(...)`, `HttpResponse.text(...)`, 상태 코드를 가진 `new HttpResponse(null, { status: 500 })`, 네트워크 오류를 재현하는 `HttpResponse.error()`.
- `fetch`를 `vi.fn()`으로 바꾸는 방식보다 구현 세부(어떤 함수로 요청했는지)에 덜 묶이고, 같은 핸들러를 테스트와 개발 서버에서 함께 쓸 수 있습니다.

**흔한 실수:** `resetHandlers()`를 빼먹는 것입니다. 한 테스트의 `server.use()`가 다음 테스트로 새어서, 순서에 따라 결과가 달라집니다.

## 핵심 정리

- 단위는 작은 코드 하나, 통합은 여러 단위의 연결, E2E는 실제 브라우저의 앱 전체를 검증합니다. 피라미드는 단위를 많이, 트로피는 통합을 중심에 두라고 제안합니다.
- 테스트는 사용자가 보는 글자, 역할, 레이블로 쓰고 State 이름이나 CSS 클래스 같은 구현 세부는 단언하지 않습니다.
- 쿼리는 `getByRole`, `getByLabelText`, 텍스트 계열, 대체 텍스트 계열, `getByTestId` 순으로 고릅니다. 없음은 `queryBy`, 비동기는 `findBy`와 `waitFor`입니다.
- 상호작용은 `userEvent.setup()`을 `render` 앞에서 만들고 모든 호출에 `await`를 붙입니다.
- `act`는 RTL이 대부분 대신 처리하고, 가짜 타이머 같은 React 밖 업데이트에만 직접 씁니다.
- 네트워크는 MSW 핸들러로 경계에서 대체하고 `listen`, `resetHandlers`, `close`를 테스트 설정에 연결합니다.

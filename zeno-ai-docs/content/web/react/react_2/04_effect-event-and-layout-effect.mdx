## useEffectEvent

`useEffectEvent(callback)`는 Effect 안에서 호출하는 함수를 만드는 Hook입니다. 이 함수는 호출될 때 가장 최근 렌더링의 props와 state를 읽고, Effect의 의존성에는 들어가지 않습니다. React 19.2에서 정식 기능이 되었습니다. 린트로 규칙을 검사하려면 `eslint-plugin-react-hooks`를 최신으로 올려야 합니다(기초 21편에서 Effect 의존성을 다뤘습니다).

```jsx
function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification('Connected!', theme)
  })
  useEffect(() => {
    const connection = createConnection(roomId)
    connection.on('connected', () => onConnected())
    connection.connect()
    return () => connection.disconnect()
  }, [roomId]) // theme은 의존성이 아님
}
```

- `useEffectEvent`가 돌려주는 함수를 Effect Event라고 부릅니다. 인수와 반환 타입은 넘긴 `callback`과 같습니다.
- Effect Event는 Effect 안에서, 또는 같은 컴포넌트의 다른 Effect Event 안에서 호출합니다. `useLayoutEffect`, `useInsertionEffect` 안에서도 호출할 수 있습니다.
- `theme`이 바뀌어도 연결은 다시 만들어지지 않습니다. 알림이 뜰 때는 항상 최신 `theme`이 쓰입니다.
- Effect Event의 아이덴티티는 렌더링마다 바뀝니다. 의도된 동작이며, 잘못 의존성에 넣으면 Effect가 렌더링마다 다시 실행되어 실수를 드러냅니다.

## Effect Event

Effect Event는 이벤트 핸들러와 같은 성질의 코드를 Effect 안에 두는 장치입니다. 공식 문서는 "Effect Event는 이벤트 핸들러와 비슷하다"고 요약합니다.

| 구분 | 이벤트 핸들러 | Effect | Effect Event |
|------|---------------|--------|--------------|
| 실행 시점 | 사용자 상호작용 때 | 동기화가 필요할 때 | Effect가 호출할 때 |
| 반응형 여부 | 반응하지 않음 | 의존성이 바뀌면 다시 실행 | 반응하지 않음 |
| 최신 값 읽기 | 가능 | 의존성으로 선언한 값만 | 가능 |
| 의존성 배열 | 해당 없음 | 필요 | 넣지 않음 |

핵심 개념은 "Effect에서 호출되는 이벤트"입니다. 외부 시스템(연결, 타이머, 리스너)이 발생시키는 사건에 앱이 반응하는 코드는 렌더링 값을 읽지만 Effect를 다시 동기화할 이유는 아닙니다. 그 부분만 Effect Event로 뺍니다.

**흔한 실수:** 모든 Effect에 습관적으로 쓰는 것입니다. 공식 문서는 Effect에서 실제로 이벤트처럼 발생하는 로직에만 쓰라고 안내합니다.

## Reactive / Non-reactive 분리

반응형 값은 props, state, 컴포넌트 본문에서 선언한 변수처럼 렌더링마다 바뀔 수 있는 값입니다. 반응형 값을 읽는 Effect는 그 값을 의존성으로 선언해야 하고, 값이 바뀌면 다시 실행됩니다.

한 Effect 안에 두 종류의 코드가 섞여 있으면 분리합니다.

| 코드 | 성격 | 둘 곳 |
|------|------|-------|
| 어떤 방에 연결할지(`roomId`) | 바뀌면 다시 동기화해야 함: 반응형 | Effect 본문과 의존성 배열 |
| 연결됐을 때 알림 색(`theme`) | 바뀌어도 다시 연결할 이유가 없음: 비반응형 | Effect Event |

분리의 기준은 질문 하나입니다. "이 값이 바뀌었을 때 Effect가 정리하고 다시 시작해야 하는가?" 답이 예이면 의존성이고, 아니오이면 Effect Event로 읽습니다.

```jsx
// ❌ theme이 바뀔 때마다 재연결
useEffect(() => {
  const c = createConnection(roomId)
  c.on('connected', () => showNotification('OK', theme))
  c.connect()
  return () => c.disconnect()
}, [roomId, theme])
```

## 최신 Props/State 읽기

Effect Event는 호출되는 순간의 최신 값을 읽습니다. 값을 Effect 안에서 쓰면서도 Effect를 그 값에 반응시키지 않으려는 경우입니다.

```jsx
function Page({ url }) {
  const { items } = useContext(CartContext)
  const numberOfItems = items.length
  const onVisit = useEffectEvent((visitedUrl) => {
    logVisit(visitedUrl, numberOfItems) // 항상 최신 값
  })
  useEffect(() => {
    onVisit(url)
  }, [url]) // url이 바뀔 때만 실행
}
```

- 페이지 방문 기록은 `url`이 바뀔 때만 보내고, 그때의 장바구니 수량은 최신 값을 쓰려는 코드입니다.
- 공식 문서는 반응형 값을 Effect Event 안에서 읽지 말고 인수로 넘기라고 권합니다. 위 코드의 `url`처럼 인수로 받으면 어떤 값에 반응하는지 코드에 드러납니다.
- `numberOfItems`는 Effect Event 안에서 읽기 때문에 최신 값을 쓰지만 의존성은 아닙니다.

## Dependency 제외

Effect Event는 의존성 배열에 넣지 않습니다. 넣으면 린트가 경고하고, 아이덴티티가 렌더링마다 바뀌므로 Effect가 매번 다시 실행됩니다.

```jsx
// ❌ Effect Event를 의존성에 넣음
useEffect(() => { onVisit(url) }, [url, onVisit])
// ✅ 넣지 않음
useEffect(() => { onVisit(url) }, [url])
```

의존성에서 제외되는 것은 Effect Event 자신뿐입니다. Effect Event가 읽는 값도 의존성이 아니지만, Effect 본문이 직접 읽는 반응형 값은 여전히 의존성입니다.

**흔한 실수:** 의존성을 줄이려고 `useEffectEvent`를 쓰는 것입니다. 공식 문서는 의존성 배열을 피하려는 용도로 쓰지 말라고 경고합니다. 반응해야 하는 값을 Effect Event로 숨기면 버그가 숨습니다.

```jsx
// ❌ pageUrl 변경을 놓침
const logVisit = useEffectEvent(() => log(pageUrl))
useEffect(() => { logVisit() }, [])
```

다른 방법으로 의존성을 줄이는 경우도 있습니다.

- 이벤트 로직이면 이벤트 핸들러로 옮깁니다.
- 서로 무관한 두 작업이 한 Effect에 있으면 Effect를 나눕니다.
- 이전 state를 읽어서 갱신하는 코드는 업데이터 함수(`setMessages(prev => ...)`)로 바꿉니다.
- 객체와 함수는 Effect 안에서 만들거나 컴포넌트 밖으로 옮깁니다.

## Event Listener

외부 이벤트를 구독하는 Effect에서 리스너가 최신 값을 읽되, 값이 바뀔 때마다 구독을 다시 하지 않으려는 경우에 씁니다.

```jsx
const onMove = useEffectEvent((e) => {
  if (canMove) { // 최신 canMove
    setPosition({ x: e.clientX, y: e.clientY })
  }
})
useEffect(() => {
  window.addEventListener('pointermove', onMove)
  return () => {
    window.removeEventListener('pointermove', onMove)
  }
}, []) // 리스너는 한 번만 등록
```

- Effect Event 자체를 리스너로 등록해도 됩니다. 리스너가 최신 값을 읽습니다.
- `canMove`가 바뀌어도 `removeEventListener`와 `addEventListener`가 반복되지 않습니다.
- 타이머도 같습니다. `setInterval` 콜백에서 Effect Event를 호출하면 `count`와 `increment`가 바뀌어도 타이머가 다시 설정되지 않습니다.

```jsx
const onTick = useEffectEvent(() => {
  setCount(count + increment)
})
useEffect(() => {
  const id = setInterval(() => onTick(), 1000)
  return () => clearInterval(id)
}, [])
```

값이 아니라 콜백을 받는 커스텀 훅에서도 씁니다. 훅 안에서 콜백을 Effect Event로 감싸면 호출하는 쪽이 `useCallback`을 쓰지 않아도 Effect가 다시 실행되지 않습니다.

```jsx
function useInterval(callback, delay) {
  const onTick = useEffectEvent(callback)
  useEffect(() => {
    if (delay === null) return
    const id = setInterval(() => onTick(), delay)
    return () => clearInterval(id)
  }, [delay]) // 의존성은 delay뿐
}
```

## Stale Closure

클로저는 함수가 만들어진 렌더링의 값을 캡처합니다. Effect 안의 콜백은 그 Effect가 실행된 렌더링의 `props`와 `state`를 계속 봅니다. 의존성이 비어 있으면 첫 렌더링의 값만 영원히 봅니다. 이것이 stale closure(낡은 클로저)입니다.

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1) // count는 첫 렌더링의 0
  }, 1000)
  return () => clearInterval(id)
}, []) // 항상 0 + 1
```

세 가지로 해결합니다. 고르는 기준이 다릅니다.

| 해결 | 언제 | 비용 |
|------|------|------|
| 의존성에 추가 | 값이 바뀔 때 Effect를 다시 동기화해야 한다 | 타이머·연결이 다시 만들어진다 |
| 업데이터 함수 | 이전 state만 필요하다 | 없음 |
| Effect Event | 최신 값을 읽되 Effect는 다시 만들면 안 된다 | 이벤트처럼 쓰는 코드에만 적합 |

- 린트 규칙을 주석으로 끄는 것은 해결이 아닙니다. 공식 문서는 이 경우를 React를 속이는 것이라고 설명합니다. 위 예에서 Effect가 영원히 초기 `count`를 써서 카운터가 1에서 멈춥니다.
- 의존성은 코드에 맞춰 정해지는 것이지 고르는 것이 아닙니다. 의존성이 불만스러우면 Effect 코드를 바꿉니다.

## 사용 제한

Effect Event에는 규칙이 있습니다. 린트(`eslint-plugin-react-hooks`)가 대부분 검사합니다.

| 제한 | 이유 |
|------|------|
| 컴포넌트 최상위에서만 선언한다 | Hook이라서 반복문·조건문 안에서 호출할 수 없다 |
| 렌더링 중에 호출하지 않는다 | 호출하면 에러 |
| Effect와 다른 Effect Event 안에서만 호출한다 | 이벤트 핸들러에서 호출하면 에러 |
| 다른 컴포넌트나 Hook에 넘기지 않는다 | 호출 위치를 통제할 수 없다 |
| 의존성 배열에 넣지 않는다 | 아이덴티티가 렌더링마다 바뀐다 |
| 의존성을 피할 목적으로 쓰지 않는다 | 반응해야 할 변경을 놓친다 |

- 이벤트 핸들러나 자식에게 넘기는 콜백에는 일반 함수나 `useCallback`을 씁니다.
- 다른 Hook에 넘기고 싶으면 그 Hook 안에서 Effect Event로 감쌉니다(위의 `useInterval`).

```jsx
// ❌ 다른 Hook에 Effect Event를 넘김
const onTick = useEffectEvent(() => { /* ... */ })
useTimer(onTick, 1000)
// ✅ 콜백을 넘기고 Hook 안에서 Effect Event로 감쌈
useTimer(() => { /* ... */ }, 1000)
```

## useLayoutEffect

`useLayoutEffect(setup, dependencies?)`는 `useEffect`와 같은 시그니처를 가지지만, 브라우저가 화면을 다시 그리기 전에 실행되는 Hook입니다. DOM이 갱신된 직후, 페인트 전에 레이아웃을 읽고 반영해야 할 때 씁니다.

- 인수, 정리 함수, 의존성 비교(`Object.is`)는 `useEffect`와 같습니다.
- 컴포넌트 최상위에서만 호출합니다.
- StrictMode에서는 개발 중에 첫 설정 전에 설정과 정리를 한 번 더 실행합니다.
- 서버 렌더링에서는 실행되지 않습니다(아래 "SSR 고려").
- 공식 문서의 경고: 성능을 해칠 수 있으니 가능하면 `useEffect`를 쓰라고 합니다.

대부분의 Effect에는 필요 없고, 사용자가 중간 상태를 보면 안 되는 DOM 측정·보정에만 씁니다.

## Paint 이전 실행

React는 렌더링한 결과를 DOM에 반영(커밋)한 뒤 `useLayoutEffect`를 실행하고, 그 코드가 끝난 다음에 브라우저가 화면을 그립니다. 그 안에서 상태를 갱신하면 React가 곧바로 다시 렌더링하고, 사용자는 갱신이 반영된 화면만 봅니다.

```text
렌더링 → DOM 반영 → useLayoutEffect → (상태 갱신 시 재렌더링)
       → 브라우저 페인트 → useEffect
```

- 이 시점의 Effect와 거기서 예약한 상태 갱신은 모두 브라우저가 페인트하는 것을 막습니다. 오래 걸리면 화면이 그만큼 늦게 나타납니다.
- `useLayoutEffect` 안에서 상태 갱신을 일으키면 React는 남은 Effect를 즉시 모두 실행하고, 그 안에 `useEffect`도 포함됩니다.

## DOM 측정

DOM 측정은 렌더링된 요소의 크기와 위치를 읽는 일입니다. 요소가 렌더링되기 전에는 값이 없고 렌더링 중에는 이전 값이라서, 측정은 DOM이 반영된 뒤 Effect에서 합니다. 주로 `ref`로 노드를 잡고 `getBoundingClientRect()`를 씁니다.

```jsx
const ref = useRef(null)
const [height, setHeight] = useState(0)
useLayoutEffect(() => {
  const { height } = ref.current.getBoundingClientRect()
  setHeight(height)
}, [])
```

- 읽는 곳은 렌더링이 아니라 Effect입니다(Ref 사용법은 기초 19편).
- 측정한 값을 상태에 저장하면 그 값으로 다시 렌더링합니다. 측정 후 바로 다시 렌더링하는 흐름이 `useLayoutEffect`의 대표 사용입니다.
- 측정 결과가 화면에 반영되기 전 중간 모습을 보이면 안 되는 경우에만 `useLayoutEffect`를 씁니다. 단순히 측정만 하고 화면을 바꾸지 않으면 `useEffect`로 충분합니다.

## Layout 측정

레이아웃 값(`offsetHeight`, `getBoundingClientRect` 등)을 읽으면 브라우저는 보류 중인 스타일 변경을 반영해 레이아웃을 먼저 계산합니다. 이를 강제 동기 레이아웃(forced synchronous layout)이라고 합니다. web.dev는 읽기를 먼저 모두 하고 쓰기를 나중에 하라고 안내합니다.

```js
// ❌ 반복마다 쓰고 읽음: 매번 레이아웃 재계산
for (const el of items) {
  el.style.width = box.offsetWidth + 'px'
}
// ✅ 읽기를 한 번만
const w = box.offsetWidth
for (const el of items) el.style.width = w + 'px'
```

- 읽기와 쓰기가 반복해서 섞이면 매번 레이아웃을 다시 계산하는 layout thrashing이 됩니다.
- 한 Effect에서 여러 요소를 측정하면 읽기를 모아서 먼저 하고, 상태 갱신은 마지막에 한 번만 합니다.
- `ResizeObserver`는 크기 변화를 구독하는 API라서, 한 번 읽고 끝나는 측정이 아니라 변화에 계속 반응해야 할 때 씁니다.

## Tooltip 위치

툴팁은 `useLayoutEffect`의 대표 예입니다. 툴팁의 높이를 알아야 위쪽에 둘지 아래쪽에 둘지 정할 수 있는데, 높이는 렌더링한 뒤에야 알 수 있습니다.

```jsx
function Tooltip({ anchorRect, children }) {
  const ref = useRef(null)
  const [height, setHeight] = useState(0)
  useLayoutEffect(() => {
    setHeight(ref.current.getBoundingClientRect().height)
  }, [])
  const top = anchorRect.top - height
  return <div ref={ref} style={{ top }}>{children}</div>
}
```

공식 문서가 설명하는 단계는 다음과 같습니다.

1. 첫 렌더링은 `height`가 0이라 위치가 어긋납니다.
2. React가 DOM에 반영하고 `useLayoutEffect`를 실행합니다.
3. Effect가 높이를 측정해 상태를 갱신하고, React가 즉시 다시 렌더링합니다.
4. 두 번째 렌더링에서 올바른 위치가 DOM에 반영되고, 그 뒤에 브라우저가 화면을 그립니다.

사용자는 잘못된 위치를 보지 못합니다. `useEffect`로 같은 일을 하면 첫 위치가 잠깐 그려진 뒤 이동하는 깜박임이 생길 수 있습니다. 공식 문서도 툴팁을 측정하고 배치하는 일을 `useLayoutEffect`가 필요한 대표 사례로 듭니다.

## useEffect와 차이

두 Hook은 같은 문법이지만 실행 시점이 다릅니다.

| 항목 | `useEffect` | `useLayoutEffect` |
|------|-------------|-------------------|
| 실행 시점 | 보통 페인트 후 | DOM 반영 후, 페인트 전 |
| 페인트 | 막지 않음 | 막음 |
| 상태 갱신 시 | 사용자가 중간 화면을 볼 수 있음 | 중간 화면 없이 반영 |
| 용도 | 데이터 요청, 구독, 로깅 등 대부분 | 측정과 위치 보정 |
| 서버 렌더링 | 실행되지 않음 | 실행되지 않음 |

- 사용자 상호작용(클릭)이 원인인 Effect는 React가 페인트 전에 실행할 수도 있습니다. 이벤트 시스템에서 Effect의 결과를 관찰할 수 있게 하기 위해서입니다.
- 클릭이 원인이어도 Effect 안의 상태 갱신은 페인트가 먼저 일어날 수 있습니다. 페인트를 반드시 막아야 하면 `useLayoutEffect`로 바꿉니다.
- 판단 기준은 "중간 화면이 눈에 띄는가"입니다. 깜박이거나 어긋난 위치가 보이면 `useLayoutEffect`, 그렇지 않으면 `useEffect`입니다.

## SSR 고려

서버 렌더링에서는 Effect가 실행되지 않습니다. `useLayoutEffect`는 서버에 레이아웃 정보가 없어서 서버에서 호출하면 "useLayoutEffect does nothing on the server"라는 오류를 냅니다.

공식 문서가 안내하는 해결 방법입니다.

- `useEffect`로 바꿉니다. 측정이 페인트 전일 필요가 없을 때 가장 단순합니다.
- 컴포넌트를 클라이언트 전용으로 표시합니다(Suspense와 클라이언트 전용 콘텐츠 처리, 자세히는 11편).
- `useEffect`로 `isMounted` 불리언을 켜고, 하이드레이션 후에만 해당 내용을 렌더링합니다.
- 외부 저장소와 동기화하는 목적이면 `useSyncExternalStore`를 고려합니다(자세히는 05편).
- React 19.3부터 `use(browser())`로 컴포넌트를 브라우저 전용으로 표시하는 방법이 추가되었습니다.

서버 렌더링 자체는 이 과목의 범위 밖입니다. Next.js 같은 프레임워크 환경이라면 서버 컴포넌트와 클라이언트 컴포넌트의 구분이 먼저 필요합니다.

## 성능 비용

`useLayoutEffect`는 브라우저가 화면을 그리는 것을 막고, 그 안에서 예약한 상태 갱신도 마찬가지입니다. 과하게 쓰면 앱이 느려집니다.

- 코드가 오래 걸리면 그만큼 첫 페인트가 늦습니다.
- 안에서 상태를 갱신하면 렌더링이 한 번 더 일어나고, 그 결과가 반영된 뒤에야 페인트됩니다. 측정 후 갱신이 있는 구조는 렌더링 두 번이 기본 비용입니다.
- 레이아웃 읽기와 쓰기가 섞이면 강제 동기 레이아웃이 반복되어 비용이 커집니다(위 "Layout 측정").
- 반드시 필요한 곳에만 쓰고, 측정이 필요 없는 일은 `useEffect`에 남깁니다.
- 어긋난 중간 화면이 문제인지 확인하지 않고 습관적으로 `useLayoutEffect`로 바꾸지 않습니다. 필요 이상으로 페인트를 막습니다.

성능 병목은 추측하지 말고 측정해서 확인합니다(자세히는 20편).

## useInsertionEffect

`useInsertionEffect(setup, dependencies?)`는 CSS-in-JS 라이브러리가 스타일을 DOM에 주입하기 위해 만든 Hook입니다. 공식 문서는 CSS-in-JS 라이브러리 작성자만을 위한 것이라고 밝히며, 일반 앱 코드에서는 `useEffect`나 `useLayoutEffect`를 쓰라고 합니다.

```js
function useCSS(rule) {
  useInsertionEffect(() => {
    if (!isInserted.has(rule)) {
      isInserted.add(rule)
      document.head.appendChild(getStyleForRule(rule))
    }
  })
  return rule
}
```

- 레이아웃 Effect보다 먼저 실행됩니다. 스타일이 먼저 들어가 있어야 이후 레이아웃 Effect가 올바른 레이아웃을 읽습니다.
- 렌더링 중에 스타일을 주입하는 것보다 낫습니다. 비차단 업데이트에서 브라우저가 매 프레임 스타일을 다시 계산하는 일을 줄입니다.
- 이 Effect 안에서는 상태를 갱신할 수 없고, 실행 시점에 `ref`가 아직 연결되지 않았습니다.
- DOM이 특정 시점에 갱신되어 있다고 기대하면 안 됩니다.
- 서버 렌더링에서는 실행되지 않습니다.

## Effect 3종 실행 순서

한 번의 업데이트에서 세 Effect는 다음 순서로 실행됩니다.

| 순서 | Hook | 실행 시점 | 쓸 수 있는 것 | 주 사용자 |
|------|------|-----------|---------------|-----------|
| 1 | `useInsertionEffect` | 레이아웃 Effect보다 먼저 | 스타일 주입만. 상태 갱신·ref 불가 | CSS-in-JS 라이브러리 |
| 2 | `useLayoutEffect` | DOM 반영 후, 페인트 전 | DOM 읽기, 상태 갱신(페인트를 막음) | 측정·위치 보정 |
| 3 | `useEffect` | 보통 페인트 후 | 데이터 요청, 구독, 로깅 | 대부분의 Effect |

- 정리 함수는 같은 Hook의 다음 설정 전에 실행됩니다. 의존성이 바뀐 커밋에서 정리가 먼저, 설정이 다음입니다.
- 세 Hook 모두 클라이언트에서만 실행됩니다.
- `useEffectEvent`로 만든 함수는 세 Hook 안에서 모두 호출할 수 있습니다.
- 한 커밋에서 레이아웃 Effect 안의 상태 갱신이 일어나면 나머지 Effect(`useEffect` 포함)가 즉시 실행되고 렌더링이 한 번 더 일어납니다.

## 핵심 정리

- `useEffectEvent`는 Effect 안에서 최신 props·state를 읽는 비반응형 로직을 분리합니다. 의존성 배열에 넣지 않고, Effect와 다른 Effect Event 안에서만 호출합니다.
- 반응해야 하는 값은 Effect 의존성에 두고, 바뀌어도 재동기화가 필요 없는 값만 Effect Event로 읽습니다. 의존성을 피하려는 용도로 쓰면 버그를 숨깁니다.
- 의존성이 비면 클로저가 낡은 값을 보는 stale closure가 생기고, 의존성 추가·업데이터 함수·Effect Event 중 맞는 것으로 고칩니다.
- `useLayoutEffect`는 DOM 반영 후 페인트 전에 실행되어 측정과 위치 보정에 쓰지만, 페인트를 막으므로 꼭 필요한 곳에만 씁니다.
- 서버에서는 Effect가 실행되지 않아서 `useLayoutEffect`는 서버에서 오류를 냅니다. `useEffect`로 바꾸거나 클라이언트 전용으로 처리합니다.
- 실행 순서는 `useInsertionEffect`, `useLayoutEffect`, `useEffect`이고, 앞의 둘이 페인트 이전입니다.

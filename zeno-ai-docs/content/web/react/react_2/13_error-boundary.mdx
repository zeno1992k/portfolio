## Error Boundary

Error Boundary는 자식 컴포넌트 트리에서 렌더링 중에 발생한 오류를 잡아 Fallback UI(대체 화면)를 보여 주는 컴포넌트입니다. 오류가 하나 나도 화면 전체가 사라지지 않게 막습니다.

- 어떤 경계도 잡지 못한 오류는 React 트리 전체를 언마운트합니다. 화면이 비게 됩니다.
- 현재 Error Boundary는 클래스 컴포넌트로만 만들 수 있습니다. Hook으로 대체하는 API는 없습니다.
- 클래스를 직접 쓰지 않으려면 `react-error-boundary` 패키지를 씁니다(아래 절).

```jsx
<ErrorBoundary fallback={<p>문제가 생겼습니다</p>}>
  <Profile />
</ErrorBoundary>
```

`ErrorBoundary`는 React가 제공하는 컴포넌트가 아니라 아래 절에서 구현하는 클래스입니다.

## 렌더 오류 포착

경계는 자식 트리의 렌더링 중 오류를 잡습니다. 렌더링 함수, 생명주기 메서드, 생성자에서 던져진 오류가 대상입니다.

```jsx
function Profile({ user }) {
  return <p>{user.name}</p> // user가 null이면 TypeError
}
```

- `user`가 `null`이면 `Profile` 렌더 중에 `TypeError`가 던져지고, 가장 가까운 위쪽 경계가 받습니다.
- `throw`된 값은 `Error` 인스턴스가 아니어도 됩니다. 문자열이나 객체도 던질 수 있어서 `error.message`를 바로 읽지 않는 편이 안전합니다.
- 오류를 낸 컴포넌트와 그 아래 트리는 화면에서 사라지고, 경계가 Fallback을 대신 렌더합니다.
- 경계 바깥의 형제 컴포넌트는 영향을 받지 않습니다.

## Fallback

Fallback은 오류가 났을 때 경계가 대신 보여 주는 UI입니다. 경계의 state에 오류 여부를 기록해 두고 `render`에서 분기합니다.

```jsx
import * as React from 'react'

class ErrorBoundary extends React.Component {
  state = { hasError: false }

  static getDerivedStateFromError(error) {
    return { hasError: true }
  }

  render() {
    if (this.state.hasError) return this.props.fallback
    return this.props.children
  }
}
```

- 경계 컴포넌트는 `render`에서 `this.state`를 보고 정상일 때는 `children`, 오류일 때는 Fallback을 돌려줍니다.
- Fallback에는 무슨 일이 일어났는지와 다음 행동(다시 시도, 홈으로 이동)을 함께 안내합니다.
- Fallback도 렌더 중에 오류를 던지면 경계 자신의 오류가 되어 그 위의 경계로 넘어갑니다.

## getDerivedStateFromError

`static getDerivedStateFromError(error)`는 자식이 렌더 중 오류를 던졌을 때 호출되어, 다음 렌더에서 Fallback을 보이도록 state를 돌려주는 정적 메서드입니다.

- 인수는 던져진 오류 하나입니다.
- 반환값은 state에 병합할 객체입니다. 위 예제처럼 `{ hasError: true }`를 돌려줍니다.
- 렌더 단계에서 호출되므로 순수 함수여야 합니다. 로그 전송 같은 부수 효과는 넣지 않습니다.
- 오류 값 자체를 state에 담아 두면 Fallback에서 메시지를 보여 줄 수 있습니다.

```jsx
static getDerivedStateFromError(error) {
  return { hasError: true, error }
}
```

## componentDidCatch

`componentDidCatch(error, info)`는 오류가 잡힌 뒤 호출되는 메서드이며, 부수 효과(오류 로깅)를 하는 자리입니다.

```jsx
componentDidCatch(error, info) {
  logErrorToMyService(error, info.componentStack)
}
```

- `info.componentStack`은 오류를 낸 컴포넌트와 그 부모 컴포넌트의 이름·위치를 담은 문자열입니다. 프로덕션에서는 압축된 이름이라 소스맵으로 해석합니다.
- 반환값은 쓰지 않습니다.
- `componentDidCatch` 안에서 `setState`를 호출하는 방식은 더 이상 권장하지 않습니다. Fallback 전환은 `getDerivedStateFromError`가 맡습니다.
- 개발 모드에서는 오류가 `window`까지 전파되어 `window.onerror` 핸들러에도 잡힙니다. 프로덕션에서는 전파되지 않습니다.
- 개발 모드에서는 `React.captureOwnerStack()`으로 오너 스택(컴포넌트를 직접 만든 컴포넌트 목록)을 함께 얻을 수 있습니다. 프로덕션에서는 항상 `null`입니다.

두 메서드의 역할은 다음과 같이 나눕니다.

| 메서드 | 호출 시점 | 하는 일 |
|--------|-----------|---------|
| `getDerivedStateFromError` | 렌더 단계 | state 갱신으로 Fallback 전환(순수) |
| `componentDidCatch` | 커밋 단계 | 로깅 같은 부수 효과 |

## Event 오류 제외

Error Boundary는 이벤트 핸들러 안의 오류를 잡지 않습니다. 이벤트 핸들러는 렌더 중에 실행되는 코드가 아니어서 화면 구성에 영향을 주지 않기 때문입니다.

```jsx
function SaveButton() {
  const [error, setError] = useState(null)

  function handleClick() {
    try {
      save() // 던질 수 있는 코드
    } catch (e) {
      setError(e) // state로 에러 UI를 직접 그림
    }
  }
  // ...
  // {error && <p>저장하지 못했습니다</p>}
}
```

- 이벤트 핸들러 오류는 일반 JavaScript처럼 `try`/`catch`로 처리하고, 결과를 state에 담아 렌더에서 보여 줍니다.
- 서버 사이드 렌더링 중의 오류, 경계 컴포넌트 자신이 던진 오류도 그 경계는 잡지 못합니다. 자신의 오류는 위쪽 경계가 받습니다.

## Async 오류

`setTimeout`, `requestAnimationFrame` 콜백, `fetch` 뒤의 `then` 같은 비동기 코드의 오류도 Error Boundary가 잡지 못합니다. 렌더가 끝난 뒤에 실행되기 때문입니다. 처리 방법은 상황별로 다릅니다.

| 상황 | 방법 |
|------|------|
| 이벤트 핸들러·콜백 | `try`/`catch` 후 state에 저장 |
| 렌더 중 Promise 읽기 | `use`로 읽으면 거부된 오류가 경계로 전달됨(자세히는 15편) |
| Transition 안의 비동기 함수 | `startTransition`에 넘긴 함수의 오류는 경계가 받음 |
| 라이브러리 | `react-error-boundary`의 `useErrorBoundary`로 경계에 전달 |

```jsx
function SaveButton() {
  const [isPending, startTransition] = useTransition()

  function handleClick() {
    startTransition(async () => {
      await save() // 던지거나 거부되면 가장 가까운 경계로
    })
  }

  return <button onClick={handleClick}>저장</button>
}
```

- `startTransition`에 넘긴 함수가 오류를 던지거나 거부된 Promise를 돌려주면, `useTransition`을 호출한 컴포넌트를 감싼 경계의 Fallback이 표시됩니다(자세히는 09편).
- 이 방식이 통하는 범위는 `startTransition` 함수 안입니다. 그 안의 `await` 뒤에서 `setState`를 호출할 때는 다시 `startTransition`으로 감싸야 Transition으로 취급됩니다.

**흔한 실수:** `try`/`catch`로 `use`를 감싸는 것입니다. `use`는 내부적으로 던지는 방식으로 Suspense와 연동하므로 `try`/`catch`로 감싸면 안 되고, 오류는 경계로 처리합니다(자세히는 15편).

## Boundary 위치

경계는 하나만 두지 않고 여러 층에 둡니다. 경계를 둔 위치가 Fallback이 가리는 범위를 정합니다.

| 위치 | Fallback 범위 | 용도 |
|------|---------------|------|
| 앱 최상위 | 화면 전체 | 마지막 방어선. 오류 안내와 새로고침 |
| 라우트(페이지) 단위 | 해당 페이지 | 다른 페이지로 이동할 수 있게 유지 |
| 위젯 단위 | 해당 위젯 | 목록, 차트처럼 독립된 영역 |

```jsx
<ErrorBoundary fallback={<AppCrash />}>
  <Layout>
    <ErrorBoundary fallback={<p>목록을 불러오지 못했습니다</p>}>
      <ConversationList />
    </ErrorBoundary>
    <Chat />
  </Layout>
</ErrorBoundary>
```

- 오류는 가장 가까운 위쪽 경계가 잡습니다. 위 예제에서 `ConversationList`의 오류는 안쪽 경계가, `Chat`의 오류는 바깥 경계가 받습니다.
- 공식 문서의 예시는 채팅 앱에서 대화 목록 전체나 메시지 하나는 감싸되, 아바타마다 감싸지는 말라는 것입니다. 너무 잘게 나누면 Fallback이 화면 곳곳에 흩어지고, 너무 크게 잡으면 작은 오류에 화면 전체가 사라집니다.
- 데이터를 불러오는 단위와 경계 단위를 맞추면 Fallback의 의미가 분명해집니다.

## Retry와 Reset

재시도는 경계의 오류 상태를 되돌려 자식을 다시 렌더하는 것입니다. 오류 state를 초기화하는 메서드를 Fallback에 연결합니다.

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null }
  static getDerivedStateFromError(error) {
    return { error }
  }
  reset = () => this.setState({ error: null })
  render() {
    if (this.state.error) {
      return this.props.fallback(this.reset)
    }
    return this.props.children
  }
}
```

- `reset`을 호출하면 `error`가 `null`이 되고, 경계는 `children`을 다시 렌더합니다. 원인이 그대로면 다시 실패해서 Fallback으로 돌아옵니다.
- 원인이 입력 값에 있다면 `key`를 바꿔 경계를 새로 마운트하는 방법도 있습니다. `<ErrorBoundary key={userId}>`는 `userId`가 바뀔 때 오류 상태를 버립니다.
- 데이터 재요청이 필요하면 재시도 전에 원본 요청을 다시 만들어야 합니다. 거부된 Promise를 그대로 `use`에 다시 넘기면 같은 오류가 납니다(자세히는 15편).

## Suspense 조합

Suspense는 로딩 중 상태를, Error Boundary는 실패 상태를 맡습니다. 둘을 함께 두면 비동기 UI의 세 상태(로딩, 성공, 실패)가 채워집니다(Suspense 자체는 11편).

```jsx
<ErrorBoundary fallback={<p>불러오지 못했습니다</p>}>
  <Suspense fallback={<p>불러오는 중</p>}>
    <Albums albumsPromise={albumsPromise} />
  </Suspense>
</ErrorBoundary>
```

- 바깥에 `ErrorBoundary`, 안쪽에 `Suspense`를 두는 구성이 공식 문서의 예제입니다.
- 자식이 Promise를 기다리는 동안은 `Suspense`의 Fallback이, Promise가 거부되면 `ErrorBoundary`의 Fallback이 보입니다.
- 서버 렌더링 중 오류가 나면 React는 서버 렌더를 중단하지 않고 가장 가까운 `Suspense` Fallback을 HTML에 넣습니다. 클라이언트에서 다시 렌더해 같은 오류가 나면 그때 가장 가까운 Error Boundary가 처리하고, 성공하면 오류는 사용자에게 보이지 않습니다.
- 재시도할 때는 Promise를 새로 만들고 경계를 리셋해야 합니다. 다음 절의 `resetKeys`가 이 용도입니다.

## react-error-boundary

`react-error-boundary`는 Error Boundary를 함수형 코드에서 쓸 수 있게 해 주는 패키지입니다. React 공식 문서가 클래스 직접 작성의 대안으로 소개합니다.

```bash
npm install react-error-boundary
```

```jsx
import { ErrorBoundary } from 'react-error-boundary'

<ErrorBoundary
  fallbackRender={({ error, resetErrorBoundary }) => (
    <button onClick={resetErrorBoundary}>다시 시도</button>
  )}
  onError={(error, info) => report(error, info)}
  onReset={() => clearCache()}
  resetKeys={[userId]}
>
  <Profile />
</ErrorBoundary>
```

| prop | 역할 |
|------|------|
| `fallback` | 오류 때 보일 정적 요소 |
| `FallbackComponent` | 오류를 받아 Fallback을 그리는 컴포넌트 |
| `fallbackRender` | 오류와 `resetErrorBoundary`를 받는 render prop 함수 |
| `onError` | 오류와 컴포넌트 스택을 받는 콜백. 로깅용 |
| `onReset` | 경계가 리셋되어 재시도하기 직전에 호출 |
| `resetKeys` | 배열 값이 바뀌면 경계를 자동 리셋 |

- Fallback 지정 방법은 `fallback`, `FallbackComponent`, `fallbackRender` 중 하나를 씁니다. 재시도 버튼이 필요하면 `resetErrorBoundary`를 받는 뒤의 둘 중 하나를 씁니다.
- `resetKeys`는 오류가 특정 state에 묶여 있을 때 유용합니다. 사용자 ID나 Promise가 바뀌면 자동으로 다시 렌더합니다.
- 이벤트 핸들러와 비동기 콜백의 오류는 `useErrorBoundary` 훅으로 가까운 경계에 전달합니다. React 19에서는 `useTransition`의 Action이 대안이 될 수 있습니다.
- 이 패키지는 클라이언트 컴포넌트라서 `"use client"` 지시어가 있는 파일에서 씁니다. ES 모듈을 지원하지 않는 프레임워크에서는 버전 5를 쓰라고 안내합니다.

## onCaughtError와 onUncaughtError

React 19부터 `createRoot`와 `hydrateRoot`에 오류 처리 콜백 옵션을 줄 수 있습니다(자세히는 17편). 오류가 경계에 잡혔는지에 따라 호출되는 콜백이 다릅니다.

| 옵션 | 호출 시점 |
|------|-----------|
| `onCaughtError` | Error Boundary가 오류를 잡았을 때 |
| `onUncaughtError` | 어떤 경계도 잡지 못한 오류가 던져졌을 때 |
| `onRecoverableError` | React가 오류에서 자동 복구했을 때(기존 옵션) |

```jsx
import { createRoot } from 'react-dom/client'

const root = createRoot(document.getElementById('root'), {
  onCaughtError: (error, errorInfo) => {
    report('caught', error, errorInfo.componentStack)
  },
  onUncaughtError: (error, errorInfo) => {
    report('uncaught', error, errorInfo.componentStack)
  },
})
```

- 세 콜백 모두 `(error, errorInfo)`를 받고, `errorInfo.componentStack`에 컴포넌트 스택 문자열이 들어 있습니다.
- 옵션을 주지 않으면 기본 동작은 콘솔에 오류를 기록하는 것입니다.
- React 19는 같은 오류가 콘솔에 여러 번 찍히던 중복 로깅을 없애고, 오류 한 건을 한 번만 출력합니다.
- 경계마다 `componentDidCatch`를 붙이는 대신 루트에서 한 번에 수집할 수 있다는 점이 장점입니다.

## 에러 수집 서비스 연결

운영 환경의 오류는 Sentry 같은 수집 서비스에 보내야 발견할 수 있습니다. 수집 지점은 네 곳이며 잡는 오류가 다릅니다.

| 지점 | 잡는 오류 |
|------|-----------|
| 루트 `onCaughtError` | 경계에 잡힌 렌더 오류 |
| 루트 `onUncaughtError` | 경계 밖에서 던져진 오류 |
| 경계의 `componentDidCatch`·`onError` | 그 경계가 잡은 오류. 경계별 문맥을 붙일 때 |
| `window`의 `error`, `unhandledrejection` | 이벤트·비동기 오류 |

- 렌더 오류는 루트 콜백 하나로 모읍니다. 경계마다 따로 전송하면 한 오류가 두 번 기록될 수 있으므로 어느 한쪽으로 정합니다.
- 이벤트 핸들러와 `setTimeout`의 오류는 React가 모릅니다. `window.addEventListener('error', ...)`와 `'unhandledrejection'`으로 별도로 수집합니다.
- `componentStack`은 프로덕션에서 압축되므로 소스맵을 서비스에 올려 해석합니다.
- 수집 SDK의 전송 함수는 이 문서의 `report`처럼 얇은 함수로 한 번 감싸 두면 바꾸기 쉽습니다. 서비스별 설정은 해당 서비스의 문서를 따릅니다.

## 핵심 정리

- Error Boundary는 자식 트리의 렌더·생명주기·생성자 오류를 잡아 Fallback을 보여 주며, 클래스 컴포넌트로만 만들 수 있습니다.
- `getDerivedStateFromError`는 순수하게 Fallback용 state를 돌려주고, 로깅은 `componentDidCatch`에서 합니다.
- 이벤트 핸들러, 일반 비동기 콜백, SSR, 경계 자신의 오류는 잡지 못합니다. 이벤트·비동기는 `try`/`catch`나 `startTransition`으로 처리합니다.
- 경계는 앱·라우트·위젯 단위로 여러 층에 두고, 재시도는 오류 state 초기화, `key` 변경, `resetKeys`로 합니다.
- 비동기 UI는 `ErrorBoundary` 안에 `Suspense`를 두어 로딩과 실패를 나눕니다.
- React 19의 `onCaughtError`와 `onUncaughtError`로 루트에서 오류를 한곳에 수집해 외부 서비스로 보냅니다.

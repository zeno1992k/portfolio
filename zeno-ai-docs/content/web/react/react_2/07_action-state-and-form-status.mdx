## useActionState

`useActionState`는 Action의 결과를 state로 보관하는 Hook입니다. Action 함수가 반환한 값이 다음 렌더링의 state가 됩니다. `useReducer`와 비슷하지만 reducer 자리에 비동기 함수와 부수 효과를 쓸 수 있습니다.

```jsx
import { useActionState } from 'react'

const [state, formAction, isPending] =
  useActionState(action, initialState, permalink?)
```

| 인자·반환 | 의미 |
|-----------|------|
| `action` | 호출되는 함수. 이전 state와 전달된 값을 받아 새 state를 반환 |
| `initialState` | 첫 렌더링의 state |
| `permalink` | 선택. Server Function과 쓰는 Progressive Enhancement용 URL |
| `state` | 현재 state. 처음엔 `initialState`, 이후엔 `action`의 반환값 |
| `formAction` | `form`의 `action`에 넘기는 함수 |
| `isPending` | 이 Hook의 Action이 진행 중인지 |

- Hook이므로 컴포넌트 최상위에서만 부릅니다.
- `useReducer`는 순수한 UI state 계산에, `useActionState`는 사용자 Action의 부수 효과와 그 결과 state에 씁니다.
- Action은 순차 실행되므로 병렬로 요청을 보내야 하면 `useState`와 `useTransition`을 직접 씁니다.

## Action State

Action State는 마지막 Action이 돌려준 값입니다. 응답 본문, 성공 여부, 검증 에러, 카운터 등 Action의 결과로 화면에 필요한 값을 한 곳에 둡니다.

```js
// state의 모양을 하나로 정해 두면 렌더링이 단순해진다
// { ok: boolean, error: string | null, email: string }
```

- Action이 반환하는 값의 타입은 `initialState`와 같아야 합니다. TypeScript가 불일치를 추론하면 state 타입을 직접 지정합니다.
- 반환값 전체가 새 state이므로 이전 state의 일부를 유지하려면 `{ ...prevState, ... }`처럼 직접 복사해 돌려줍니다.
- Action이 끝날 때까지는 이전 state가 유지됩니다.

## 초기 State

`initialState`는 Action이 한 번도 호출되기 전에 보이는 state입니다. 첫 렌더링 결과를 정합니다.

```jsx
const initial = { ok: false, error: null, email: '' }
const [state, formAction] = useActionState(signup, initial)
// state는 첫 렌더링에서 initial
```

- 첫 `dispatchAction` 호출 이후에는 `initialState`가 무시됩니다.
- 초기값은 Action이 반환하는 모양과 같게 둡니다. 렌더링 코드가 첫 렌더링과 이후 렌더링을 구분하지 않아도 됩니다.
- Server Function과 쓸 때 `initialState`는 직렬화 가능한 값이어야 합니다.
- 상태를 처음 모양으로 되돌리는 내장 reset은 없습니다. Action이 신호 값(예: `null`)을 받으면 초기값을 반환하도록 직접 설계하거나, 컴포넌트에 `key`를 바꿔 다시 마운트합니다.

## Action 함수 인자

`useActionState`에 넘기는 함수는 첫 인자로 이전 state, 둘째 인자로 `dispatchAction`에 넘긴 값을 받습니다. `form`에 연결하면 둘째 인자는 `FormData`입니다.

```js
async function action(prevState, formData) {
  const email = formData.get('email')
  // prevState: 직전의 state (처음엔 initialState)
  // 반환값이 다음 state
  return { ...prevState, email }
}
```

- 일반 form Action은 `(formData)`지만 `useActionState`를 거치면 `(prevState, formData)`입니다. `formData`를 첫 인자로 쓰면 그 자리에 이전 state가 들어와 `formData.get` 호출이 실패합니다.
- 폼이 아닌 곳에서 직접 `dispatchAction`을 부르면 넘긴 값이 둘째 인자입니다. 관례상 `type`을 가진 객체를 쓰고 `switch`로 분기합니다.
- 직접 호출은 `startTransition`으로 감싸야 합니다. 안 감싸면 `isPending`이 갱신되지 않고 개발 모드에서 에러가 납니다.
- 렌더링 중에 `dispatchAction`을 부르면 "Cannot update action state while rendering" 에러입니다. 이벤트 핸들러에서 부릅니다.
- 이 함수는 부수 효과를 위한 것이라 `StrictMode`에서도 두 번 호출되지 않습니다.
- 여러 번 호출하면 큐에 쌓여 순서대로 실행되고, 각 호출은 앞 호출의 반환값을 `prevState`로 받습니다.

## Form Action 연결

`useActionState`가 돌려준 `formAction`을 `form`의 `action`에 넘깁니다. 폼이 제출되면 React가 `formAction`을 호출하고, 제출 값은 `FormData`로 Action에 전달됩니다.

```jsx
function SignupForm() {
  const [state, formAction, isPending] =
    useActionState(signup, initial)
  return (
    <form action={formAction}>
      <input name="email" defaultValue={state.email} />
      <button disabled={isPending}>가입</button>
    </form>
  )
}
```

- `form`의 `action`에 넘기면 React가 이미 Transition으로 감싸 호출하므로 `startTransition`이 필요 없습니다.
- `formAction`은 정체성이 안정적이라 Effect 의존성에 넣어도 Effect가 다시 실행되지 않습니다.
- 앞 편의 규칙대로 Action이 성공하면 비제어 입력이 리셋됩니다. 에러를 반환해도 "성공"이므로 입력이 지워지고, 리셋은 입력을 `defaultValue`로 되돌립니다. 위처럼 Action이 제출 값을 state에 담아 돌려주고 `defaultValue`로 쓰면 사용자 입력이 유지됩니다.
- 버튼마다 `name`과 `value`를 주면 같은 Action에서 어느 버튼이 눌렸는지 `FormData`로 구분합니다(`formAction` prop은 06편).

## Result 렌더링

Action이 반환한 state를 읽어 결과를 화면에 그립니다. 성공, 실패, 응답 데이터를 state의 필드로 구분합니다.

```jsx
return (
  <form action={formAction}>
    <input name="email" defaultValue={state.email} />
    <button disabled={isPending}>가입</button>
    {state.ok && <p>가입되었습니다.</p>}
  </form>
)
```

- state는 렌더링 중에 읽는 값이라 파생 값을 추가로 계산해도 됩니다. 별도 state에 복사해 두지 않습니다.
- 성공 메시지를 계속 보여 줄지는 설계 사항입니다. 사용자가 다시 입력하면 새 Action이 끝날 때까지 이전 결과가 남습니다.
- 낙관적으로 먼저 보이고 싶은 값은 `useOptimistic`과 조합합니다(08편).

## Error Result

예상한 에러는 던지지 않고 state에 담아 반환합니다. 대표적으로 서버가 돌려준 검증 에러, 중복 데이터, 권한 없음입니다.

```js
async function signup(prevState, formData) {
  const email = formData.get('email')
  const res = await api.signup(email)
  if (res.error) {
    return { ok: false, error: res.error, email }
  }
  return { ok: true, error: null, email: '' }
}
```

```jsx
{state.error && <p role="alert">{state.error}</p>}
```

| 종류 | 처리 |
|------|------|
| 알려진 에러(검증 실패 등) | 반환값 state에 담아 화면에 표시 |
| 알 수 없는 에러(버그 등) | 던짐. 가장 가까운 Error Boundary가 처리(13편) |

- 던지면 React는 큐에 쌓인 나머지 Action을 모두 취소하고 Error Boundary를 보여 줍니다.
- 이후 Action이 이유 없이 건너뛰어졌다면 앞의 Action이 던진 것입니다. 던지지 말고 에러 state를 반환해야 큐가 계속 진행됩니다.
- 에러 메시지에는 `role="alert"`를 붙이면 스크린 리더가 바로 읽습니다(접근성은 32편).
- 에러를 표시한 뒤 입력이 지워지지 않게 하려면 앞 절의 `defaultValue` 방식을 씁니다.

## Pending 조합

`useActionState`의 `isPending`은 이 Hook의 Action이 하나라도 진행 중이면 `true`입니다. `form`을 가진 컴포넌트가 곧바로 쓸 수 있습니다.

```jsx
const [state, formAction, isPending] =
  useActionState(signup, initial)
// 폼 컴포넌트 안에서 isPending으로 입력과 버튼을 제어
<fieldset disabled={isPending}>{/* ... */}</fieldset>
```

| 읽는 곳 | 쓰는 것 | 주의 |
|---------|---------|------|
| `form`을 렌더링하는 컴포넌트 | `isPending` | 이 Hook이 만든 `formAction`의 Action만 대상 |
| `form` 안의 자식 컴포넌트 | `useFormStatus().pending` | props를 내리지 않아도 되지만 부모 `form`만 대상 |

- 자식에서 상태가 필요하면 `isPending`을 props로 내리는 대신 `useFormStatus`를 씁니다.
- 폼 컴포넌트 본체에서 `useFormStatus`를 부르면 자기 `form`을 읽지 못해 항상 `false`입니다. 그곳에서는 `isPending`을 씁니다.
- 반대로 `form`을 직접 렌더링하지 않는 재사용 컴포넌트(제출 버튼 등)는 `useFormStatus`가 적합합니다.
- `isPending`이 `true`인 동안에도 이전 state가 보입니다. 새 결과는 Action이 끝나야 들어옵니다.

## Server Function과 사용

Server Function을 `useActionState`의 Action으로 넘길 수 있습니다. 서버가 돌려준 값이 그대로 state가 되어, 서버가 검증한 결과를 화면에 보이는 가장 짧은 경로가 됩니다.

```jsx
// 'use server' 파일에서 가져온 Server Function
import { signup } from './actions'

function Page() {
  const [msg, formAction] = useActionState(signup, null)
  return <form action={formAction}>{/* ... */}</form>
}
```

- Server Function과 함께 쓰면 JavaScript 번들이 로드되고 하이드레이션이 끝나기 전에 서버가 돌려준 응답도 화면에 보여 줄 수 있습니다.
- 이때 `initialState`와 Action에 넘기는 값은 직렬화 가능해야 합니다(객체·배열·문자열·숫자).
- 프레임워크가 구현하는 부분이 많습니다. Server Function 자체는 06편에서 다뤘습니다.

### permalink 인자

`permalink`는 Server Function이 Action일 때 쓰는 세 번째 인자로, 폼이 수정하는 페이지의 고유 URL입니다. JavaScript 번들이 로드되기 전에 폼이 제출되면 브라우저는 현재 URL이 아니라 이 URL로 이동합니다.

```jsx
useActionState(signup, null, '/signup')
// JS 로드 전 제출 시 /signup으로 이동
```

- 목적지 페이지에도 같은 폼 컴포넌트를 렌더링해야 합니다. `action`과 `permalink`가 같아야 React가 state를 이어 줍니다.
- 페이지가 상호작용 가능해지면 이 인자는 아무 효과가 없습니다.
- React Server Components와 Progressive Enhancement를 쓰는 페이지에서만 의미가 있고, 보통 프레임워크가 설정합니다.

## useFormStatus

`useFormStatus`는 부모 `form`의 마지막 제출 상태를 읽는 Hook입니다. `react-dom`에서 가져옵니다(`react`가 아닙니다).

```jsx
import { useFormStatus } from 'react-dom'

function SubmitButton() {
  const { pending, data, method, action } = useFormStatus()
  // ...
}
```

- 인자가 없고 `pending`, `data`, `method`, `action` 네 필드를 가진 객체를 돌려줍니다.
- 폼 안에 있는 컴포넌트가 props 없이 폼 상태를 읽도록 만든 Hook입니다. 내부적으로 Context처럼 동작합니다(React 19 발표 글).
- `form`의 `action`에 함수를 주든 `useActionState`의 `formAction`을 주든 읽을 수 있습니다.

## pending

`pending`은 부모 `form`이 제출 중이면 `true`, 아니면 `false`인 불리언입니다.

```jsx
function SubmitButton() {
  const { pending } = useFormStatus()
  return <button disabled={pending}>저장</button>
}
```

- `form`이 없거나 제출 중이 아니면 `false`입니다.
- Action이 끝나고 최종 state가 반영될 때 `false`로 돌아옵니다.

## data

`data`는 제출 중인 `FormData`입니다. 제출 중이 아니거나 부모 `form`이 없으면 `null`입니다.

```jsx
function Status() {
  const { pending, data } = useFormStatus()
  if (!pending) return null
  return <p>{data.get('username')} 확인 중...</p>
}
```

- 서버가 응답하기 전에 사용자가 보낸 값을 그대로 보여 줄 수 있습니다.
- 값이 문자열이나 `File`이므로 형식 검증과 변환은 따로 합니다(`FormData`는 06편).

## method

`method`는 부모 `form`이 사용하는 HTTP 메서드이며 `'get'` 또는 `'post'` 문자열입니다. `form`에 `method`를 지정하지 않으면 기본값은 GET입니다.

```jsx
function Info() {
  const { method } = useFormStatus()
  return <small>{method}</small> // 'get' 또는 'post'
}
```

- 사용처가 많지 않은 필드입니다. 제출 방식에 따라 문구를 달리 보일 때 씁니다.
- `action`에 함수를 넘기면 HTTP 메서드는 POST로 처리된다는 `form` 문서의 규칙이 있습니다(06편).

## action

`action`은 부모 `form`의 `action`에 넘긴 함수에 대한 참조입니다. 부모 `form`이 없거나, `action`이 URL 문자열이거나, 지정하지 않았으면 `null`입니다.

```jsx
function Info() {
  const { action } = useFormStatus()
  return action ? <small>함수 Action</small> : null
}
```

- 어떤 Action이 걸린 폼인지 자식이 알아야 할 때 씁니다. 대부분은 `pending`만으로 충분합니다.

## Submit Button 상태

제출 버튼은 `useFormStatus`가 가장 잘 맞는 자리입니다. 버튼 컴포넌트가 스스로 `pending`을 읽어 라벨과 비활성 상태를 바꿉니다. 폼마다 같은 로직을 쓰지 않고 한 컴포넌트로 재사용합니다.

```jsx
function SubmitButton({ children }) {
  const { pending } = useFormStatus()
  return (
    <button type="submit" disabled={pending}>
      {pending ? '저장 중...' : children}
    </button>
  )
}
```

```jsx
<form action={save}>
  <input name="title" />
  <SubmitButton>저장</SubmitButton>
</form>
```

- `SubmitButton`은 어떤 폼 안에 두든 그 폼의 상태를 읽습니다.
- 디자인 시스템의 버튼이 이런 식으로 폼 상태를 직접 읽는 것이 이 Hook의 의도입니다.

## 폼 내부 Context

`useFormStatus`는 호출한 컴포넌트의 부모 `form`만 읽습니다. 규칙은 두 가지입니다.

- 반드시 `form` 안에 렌더링되는 컴포넌트에서 호출합니다. `form` 밖이면 `pending`은 항상 `false`, `data`와 `action`은 `null`입니다.
- `form`을 렌더링하는 같은 컴포넌트에서 호출하면 그 `form`을 읽지 못합니다. 자식 컴포넌트로 분리해야 합니다.

```jsx
function Form() {
  const { pending } = useFormStatus() // ❌ 항상 false
  return <form action={save}>{/* ... */}</form>
}
function Submit() {
  const { pending } = useFormStatus() // ✅ 부모 form을 읽음
  return <button disabled={pending}>저장</button>
}
```

- 이 제약 때문에 `pending`이 안 바뀐다면 호출 위치부터 확인합니다. 공식 문서 Troubleshooting도 이 원인을 가장 먼저 듭니다.
- `form` 안이라면 몇 단계 아래의 자식에서도 부모 `form`을 읽습니다.

## 여러 Form

한 화면에 `form`이 여러 개 있어도 각 컴포넌트는 자기 부모 `form`의 상태만 읽습니다. 같은 `SubmitButton`을 모든 폼에 재사용해도 한 폼을 제출했을 때 다른 폼의 버튼은 영향을 받지 않습니다.

```jsx
<form action={saveProfile}>
  <SubmitButton>프로필 저장</SubmitButton>
</form>
<form action={savePassword}>
  <SubmitButton>비밀번호 변경</SubmitButton>
</form>
```

- 목록에서 항목마다 `form`을 두는 구조(삭제, 좋아요 버튼)에서 유용합니다. 항목마다 따로 pending이 됩니다.
- `useActionState`는 Hook 호출 하나가 state 하나이므로 폼마다 `useActionState`를 따로 둡니다. 항목마다 필요하면 항목 컴포넌트로 분리합니다.
- 화면 전체 폼을 한꺼번에 막는 상태가 필요하면 그 값을 별도 state나 상위의 Hook으로 둡니다.

## Pending UI

pending 동안 보여 주는 표시 방법은 여러 가지입니다. 목적별로 고릅니다.

| 방법 | 효과 |
|------|------|
| 버튼 라벨 교체 | 제출 중임을 버튼에서 알림 |
| 버튼·입력 비활성화 | 중복 제출과 입력 변경 방지 |
| `data`로 제출한 값 표시 | 보낸 내용을 먼저 확인시킴 |
| 스피너·스켈레톤 | 결과 영역이 곧 바뀔 것을 알림 |
| `useOptimistic` | 결과를 먼저 보여 줌(08편) |

```jsx
function Fields() {
  const { pending } = useFormStatus()
  return (
    <fieldset disabled={pending}>
      <input name="title" />
      <input name="body" />
    </fieldset>
  )
}
```

- `fieldset`에 `disabled`를 주면 안의 모든 입력이 한 번에 비활성화됩니다.
- pending 표시 영역의 크기가 바뀌면 레이아웃이 흔들립니다. 자리를 미리 확보해 둡니다.
- 즉시 끝나는 Action에는 번쩍이는 표시가 오히려 거슬립니다.

## Disabled Button

`disabled={pending}`은 가장 흔한 pending 처리입니다. 제출 중에 같은 폼을 다시 보내지 못하게 합니다.

- 버튼은 제출이 시작된 뒤 `pending`이 `true`가 되어 잠깁니다. `disabled`인 컨트롤은 `FormData`에서 빠지지만 이미 만들어진 제출 값에는 영향이 없습니다.
- 버튼을 비활성화해도 사용자가 입력을 바꿀 수는 있습니다. 필요하면 `fieldset`으로 묶어 같이 막습니다.
- `disabled`만으로 중복 제출을 완벽히 막는다고 믿지 않습니다. 서버에서도 중복을 처리해야 하는 요청이면 서버 쪽에서 막습니다.

## 핵심 정리

- `useActionState(action, initialState, permalink?)`는 `[state, formAction, isPending]`을 반환하며, Action이 반환한 값이 다음 state가 됩니다.
- Action 함수는 `(prevState, formData)` 순서로 인자를 받고, 여러 호출은 큐에서 순서대로 실행되며 던지면 남은 호출이 취소됩니다.
- 예상한 에러는 state로 반환해 렌더링하고, 예상 못한 에러는 던져 Error Boundary로 보냅니다.
- `useFormStatus`는 `react-dom`에서 가져오며 `form` 안에 있는 자식 컴포넌트에서만 부모 폼의 `pending`·`data`·`method`·`action`을 읽습니다.
- 폼을 렌더링하는 컴포넌트에서는 `isPending`을, 그 안의 제출 버튼 같은 자식에서는 `useFormStatus`를 씁니다.
- Server Function과 쓸 때 `permalink`는 JavaScript 로드 전 제출의 이동 URL이며, 인터랙티브해지면 효과가 없습니다.

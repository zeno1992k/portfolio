## Suspense와 fallback

`Suspense`는 자식이 준비될 때까지 대체 UI를 보여 주는 컴포넌트입니다. 준비되지 않은 동안 보여 줄 UI를 `fallback`에, 실제 UI를 `children`에 넣습니다.

```jsx
<Suspense fallback={<Loading />}>
  <Albums />
</Suspense>
```

- `fallback`에는 스피너, 스켈레톤처럼 가벼운 React 노드를 넣습니다.
- 자식이 준비되면 React가 fallback을 자식으로 바꿉니다. 직접 상태를 관리할 필요가 없습니다.
- `fallback` 자신이 중단되면 가장 가까운 바깥 Suspense 경계가 동작합니다.

## Boundary와 Suspend

경계(boundary)는 `Suspense` 컴포넌트가 감싸는 범위이고, 중단(suspend)은 렌더링 중인 컴포넌트가 "아직 못 그림"을 React에 알리는 일입니다.

- 컴포넌트가 중단되면 React는 그 컴포넌트에서 위로 올라가며 **가장 가까운** 부모 `Suspense`를 찾아 그 fallback을 보여 줍니다.
- 중단은 렌더링 중에 일어납니다. 이벤트 핸들러나 Effect 안에서는 일어나지 않습니다.
- 중단을 일으키는 것은 다음과 같습니다.

| 원인 | 설명 |
|------|------|
| `lazy` 컴포넌트 | 코드가 로드될 때까지 |
| `use`로 읽는 Promise | Promise가 끝날 때까지 |
| `precedence`가 있는 스타일시트 | 스타일시트가 로드될 때까지 |
| Suspense 호환 데이터 소스 | 프레임워크·라이브러리가 제공 |

- 처음 마운트되기 전에 중단된 렌더링은 state를 보존하지 않습니다. 준비되면 React가 처음부터 다시 렌더링합니다.
- 중단되는 동안 Effect는 실행되지 않습니다.
- 이미 보이던 내용이 다시 중단되어 가려지면, 그 안의 layout Effect는 정리(cleanup)되고 다시 보일 때 재실행됩니다. 가려진 동안 DOM을 측정하지 않게 하려는 것입니다.

## lazy

`lazy`로 만든 컴포넌트는 처음 렌더링될 때 코드를 불러오며, 그동안 중단됩니다. 그래서 반드시 `Suspense` 안에서 렌더링해야 합니다.

```jsx
const Chart = lazy(() => import('./Chart.js'))

<Suspense fallback={<Loading />}>
  <Chart />
</Suspense>
```

코드 분할의 전체 내용은 12편에서 다룹니다.

## Data Suspense

데이터를 읽는 동안 중단시키는 방식입니다. React가 직접 제공하는 방법은 `use`로 Promise를 읽는 것입니다(자세히는 15편).

```jsx
function Albums({ albumsPromise }) {
  const albums = use(albumsPromise)
  return <List items={albums} />
}
```

- Promise가 끝나기 전에는 `Albums`가 중단되고 가까운 경계의 fallback이 보입니다.
- Effect 안에서 데이터를 가져오는 코드는 Suspense를 작동시키지 않습니다. 이벤트 핸들러도 마찬가지입니다.

```jsx
useEffect(() => {
  fetchData().then(setData) // ❌ 경계가 모름
}, [])
const data = use(fetchData()) // ✅ 경계가 인식 (캐시된 Promise)
```

### 데이터 소스 조건

Suspense가 작동하려면 데이터 소스가 "아직 없음"을 렌더링 중에 React에 알리는 방식이어야 합니다.

- Suspense를 지원하는 프레임워크나 데이터 라이브러리(자세히는 28편의 `useSuspenseQuery`)가 제공하는 방법을 씁니다.
- 프레임워크 없이 쓰려면 `use`로 Promise를 읽되, Promise를 **캐시**해서 렌더링마다 같은 인스턴스를 돌려줘야 합니다.
- 렌더링 중에 Promise를 새로 만들면 매 렌더링마다 다른 Promise가 되어 fallback이 반복해서 나타나고, React가 uncached promise 경고를 냅니다.

```jsx
function Albums() {
  const albums = use(fetch('/albums')) // ❌ 매번 새 Promise
}
```

## Nested Suspense

경계를 중첩하면 로딩이 단계별로 나타납니다. 각 경계의 fallback은 다음 단계의 내용이 준비되면 채워집니다.

```jsx
<Suspense fallback={<BigSpinner />}>
  <Biography />
  <Suspense fallback={<AlbumsGlimmer />}>
    <Panel>
      <Albums />
    </Panel>
  </Suspense>
</Suspense>
```

순서는 다음과 같습니다.

1. `Biography`가 준비되지 않았으면 `BigSpinner`.
2. `Biography`가 준비되면 본문이 나타나고, `Albums`는 안쪽 `AlbumsGlimmer`.
3. `Albums`가 준비되면 최종 화면.

- 바깥 경계는 안쪽 경계의 내용을 기다리지 않습니다. 안쪽이 중단되어도 바깥 경계의 fallback으로 되돌아가지 않습니다.
- 안쪽 경계를 지우면 `Albums`는 바깥 경계에 속해, `Biography`와 `Albums`가 모두 준비될 때까지 `BigSpinner`가 유지됩니다.
- 경계는 트리의 어느 곳에든 추가·이동·삭제할 수 있으며, 앱의 다른 동작에는 영향을 주지 않습니다.

## Boundary 위치

경계를 어디에 두느냐가 사용자가 보는 로딩 순서를 정합니다.

- 한 경계 안의 모든 컴포넌트는 **함께** 나타납니다. 가장 늦은 컴포넌트가 준비될 때까지 전체가 fallback입니다.
- 따로 나타나게 하려면 경계를 나눕니다.
- 공식 문서의 원칙은 모든 컴포넌트를 감싸지 말라는 것입니다. 경계는 사용자가 겪게 하려는 로딩 순서보다 더 잘게 나누지 않습니다.
- 디자이너가 있으면 로딩 상태 위치를 물어봅니다. 와이어프레임에 이미 들어 있을 가능성이 높습니다.
- 공식 예제처럼 앱 최상단(라우터 바깥)에 큰 경계를 하나 두고, 그 안쪽에 필요한 만큼 경계를 추가하는 방식이 기본형입니다.

## Loading 전략과 Reveal Strategy

로딩을 보여 주는 방식은 두 가지입니다.

| 전략 | 구현 | 특징 |
|------|------|------|
| 한꺼번에 공개 | 경계 하나로 감쌈 | 깜박임·레이아웃 이동이 적음. 가장 느린 것을 기다림 |
| 순차 공개 | 경계를 중첩·분리 | 먼저 준비된 것부터 보임. 단계가 많으면 산만함 |

- React는 경계가 나타나는 시점을 제한합니다. 공식 문서는 마지막 공개로부터 최대 300ms에 한 번만 중단된 내용을 공개하고, 그 안에 준비된 경계는 함께 공개한다고 밝힙니다. 연달아 준비되는 경계들이 하나씩 튀어나오는 것을 막습니다.
- 다른 내용으로 이동할 때는 `key`로 경계를 초기화할 수 있습니다. `ProfilePage key={userId}`처럼 키를 바꾸면 이전 프로필을 같은 내용으로 보지 않고 새로 로딩합니다.

```jsx
<ProfilePage key={userId} />
// userId가 바뀌면 이전 화면 대신 fallback이 나타남
```

## Transition과 Suspense

이미 화면에 보이는 내용이 업데이트 때문에 다시 중단되면, 일반 업데이트에서는 fallback이 나타나 내용을 가립니다. Transition으로 일으킨 업데이트에서는 fallback으로 바꾸지 않고 이전 내용을 유지한 채 새 내용을 기다립니다(자세히는 09편).

```jsx
function navigate(url) {
  startTransition(() => {
    setPage(url)
  })
}
```

### 기존 UI 숨김 방지

- 이미 공개된 내용이 fallback으로 되돌아가면 레이아웃이 크게 바뀌고 사용자가 보던 정보를 잃습니다. Transition은 이를 막습니다.
- 대기 중임을 알리려면 `useTransition`의 `isPending`으로 이전 화면을 흐리게 하는 등의 표시를 합니다.
- 이 보호는 비긴급 업데이트에만 적용됩니다. 긴급 업데이트로 일으킨 중단은 fallback을 즉시 보입니다.
- Suspense와 연동된 라우터는 이동을 자동으로 Transition으로 감쌉니다.

## Stale Content

새 데이터를 기다리는 동안 이전 결과를 보여 주는 방식이 Stale Content입니다. `useDeferredValue`로 값을 지연시키면, 이미 보이던 경계가 새 값 때문에 중단되어도 fallback 대신 이전 값의 화면이 유지됩니다(자세히는 10편).

```jsx
const deferredQuery = useDeferredValue(query)
const isStale = query !== deferredQuery
```

`isStale`로 결과를 흐리게 처리해 낡은 내용임을 알립니다.

## Error Boundary 조합

Promise가 거부(reject)되거나 `lazy` 로드가 실패하면 렌더링이 에러를 던지고, 가장 가까운 Error Boundary가 이를 받습니다. Suspense는 로딩만 처리하고 에러는 처리하지 않습니다(자세히는 13편).

```jsx
<ErrorBoundary fallback={<p>불러오지 못했습니다.</p>}>
  <Suspense fallback={<Loading />}>
    <Albums />
  </Suspense>
</ErrorBoundary>
```

- Error Boundary를 Suspense **바깥**에 둡니다. 안쪽 컴포넌트의 로딩은 Suspense가, 에러는 바깥 Error Boundary가 맡습니다.
- `use`는 `try-catch`로 감쌀 수 없습니다. 에러 처리는 Error Boundary나 Promise 쪽 `catch`로 합니다.

## 요청 워터폴

요청 워터폴(waterfall)은 요청이 병렬로 나가지 못하고 앞 요청이 끝난 뒤에야 다음 요청이 시작되는 상태입니다.

- 부모가 데이터를 읽는 동안 중단되면 자식은 렌더링조차 시작하지 못합니다. 자식이 자기 데이터를 렌더링 중에 요청한다면 부모 데이터가 끝난 뒤에야 그 요청이 출발합니다.
- 예: 프로필 로딩 후에 그 사용자의 게시글 요청이 시작되고, 그 후에 댓글 요청이 시작되는 식으로 단계가 쌓입니다.
- 해결은 필요한 요청을 가능한 한 일찍, 한꺼번에 시작하는 것입니다. 라우터나 상위 컴포넌트에서 Promise를 만들어 하위에 내려 주고 `use`로 읽게 합니다.
- 서로 의존하지 않는 데이터는 각각의 경계로 나누면 병렬로 요청되고 준비되는 대로 나타납니다.
- 중첩 경계는 화면 표시를 단계적으로 만들 뿐이며, 요청 순서까지 자동으로 병렬로 바꾸지는 않습니다.

## Streaming SSR

스트리밍 서버 렌더링은 Suspense 경계를 기준으로 HTML을 나눠 서버에서 점진적으로 보냅니다(자세히는 SSR을 다루는 별도 과목).

- 경계 밖의 내용(셸)이 먼저 렌더링되어 fallback과 함께 전송됩니다.
- 경계 안의 내용이 준비되면 인라인 `script`가 붙은 HTML이 이어서 전송되어 fallback을 실제 내용으로 바꿉니다.
- 경계 안 컴포넌트가 서버에서 에러를 내면 React는 가장 가까운 fallback을 보내고, 그 컴포넌트는 클라이언트에서 다시 렌더링을 시도합니다.
- React 19.2부터 서버 스트리밍에서도 Suspense 경계의 공개가 짧은 시간 동안 묶여 처리됩니다. 클라이언트와 서버의 공개 방식 차이를 줄이기 위한 변경입니다.
- 클라이언트에서만 렌더링할 컴포넌트는 서버 환경에서 에러를 던지게 하면 됩니다. 서버는 fallback을 보내고 클라이언트가 실제 내용을 렌더링합니다.

## Server Components

Server Component는 서버에서 Promise를 만들어 Client Component에 props로 넘길 수 있고, Client Component가 `use`로 읽으면 Suspense 경계가 동작합니다.

```jsx
// Server Component
function App() {
  const messagePromise = fetchMessage()
  return (
    <Suspense fallback={<p>waiting...</p>}>
      <Message messagePromise={messagePromise} />
    </Suspense>
  )
}
```

- 넘기는 값은 직렬화할 수 있어야 합니다.
- Server Component 자체는 이 과목의 범위를 벗어나므로 개념만 다루고, 자세한 내용은 Next.js 과목에서 다룹니다.

## 핵심 정리

- 컴포넌트가 중단되면 가장 가까운 부모 `Suspense`의 fallback이 보이고, 준비되면 자식으로 교체됩니다.
- 중단 원인은 `lazy`, `use`로 읽는 Promise, 스타일시트, Suspense 호환 데이터 소스입니다. Effect·이벤트 핸들러의 데이터 요청은 중단을 일으키지 않습니다.
- 경계는 사용자가 겪을 로딩 순서만큼만 나눕니다. 한 경계 안은 함께 나타나고, 중첩 경계는 단계별로 나타납니다.
- Transition이나 지연된 값으로 일으킨 업데이트는 이미 보이는 내용을 fallback으로 되돌리지 않습니다.
- 에러는 Suspense가 아니라 바깥의 Error Boundary가 처리합니다.
- 요청 워터폴을 피하려면 요청을 일찍 시작하고, 서로 독립적인 데이터는 경계를 나눕니다.

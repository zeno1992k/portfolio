## Props를 State에 복사

`useState(props.value)`의 초깃값은 첫 렌더에서만 쓰입니다. 이후에 Props가 바뀌어도 State는 바뀌지 않아서 화면이 낡은 값에 머뭅니다.

```tsx
// ❌ color가 blue로 바뀌어도 화면은 red
function Message({ color }: { color: string }) {
  const [c, setC] = useState(color)
  return <p style={{ color: c }}>안녕</p>
}
// ✅ Props를 그대로 쓴다
function Message({ color }: { color: string }) {
  return <p style={{ color }}>안녕</p>
}
```

- 값을 바꾸는 쪽이 부모뿐이면 State가 필요 없습니다. Props를 직접 읽습니다.
- Props 변화를 따라가려고 `useEffect(() => setC(color), [color])`를 쓰면 다음 절의 문제가 생깁니다.
- 의도적으로 첫 값만 쓰고 이후 변화는 무시하려는 경우(편집 폼의 시작 값)에는 Props 이름을 `initialColor`, `defaultValue`처럼 지어 의도를 드러냅니다.
- 부모가 값을 바꿀 때 내부 State를 통째로 초기화하고 싶다면 `key`를 바꿉니다(아래 "Effect로 Derived State").

## Effect로 Derived State

다른 State나 Props에서 계산할 수 있는 값을 State로 따로 두고 Effect로 동기화하는 패턴입니다. 값이 바뀔 때마다 렌더가 한 번 더 일어나고, 그 사이에 낡은 값이 화면에 한 번 나타납니다.

```tsx
// ❌ 렌더 2번: 먼저 빈 값, Effect 뒤에 채워진 값
const [full, setFull] = useState('')
useEffect(() => {
  setFull(first + ' ' + last)
}, [first, last])
// ✅ 렌더 중에 계산: 렌더 1번
const full = first + ' ' + last
```

- 위 두 컴포넌트를 렌더해서 세어 보면 Effect 방식이 2번, 직접 계산이 1번입니다.
- 계산이 비싸면 `useMemo`로 캐시합니다(자세히는 19편). Effect와 State로 캐시하지 않습니다.
- 같은 원리로, 목록에서 선택한 항목은 객체를 State에 저장하지 말고 id만 저장해 렌더 중에 찾습니다.

```tsx
// ❌ 목록이 바뀌면 selected는 낡은 객체
const [selected, setSelected] = useState(items[0])
// ✅ id만 저장하고 파생
const [selectedId, setSelectedId] = useState(0)
const selected = items.find((i) => i.id === selectedId)
```

- Props가 바뀔 때 State를 초기화하려고 Effect에서 `setComment('')`를 부르지 말고, 컴포넌트에 `key`를 줍니다. `key`가 바뀌면 React는 새 컴포넌트로 보고 State를 모두 초기화합니다.

```tsx
// ✅ userId가 바뀌면 Profile의 모든 State가 초기화됨
<Profile key={userId} userId={userId} />
```

- 기준은 Effect가 외부 시스템(네트워크, 브라우저 API)과 맞추는 용도인지입니다. 렌더 중 계산이나 이벤트로 해결되면 Effect가 필요 없습니다(자세히는 기초 22편).

## State 직접 변경

State 객체나 배열을 직접 고치면 React가 변경을 알아채지 못합니다. React는 이전 값과 새 값을 참조로 비교하므로, 같은 객체를 고친 뒤 넘기면 변화가 없다고 보고 다시 그리지 않습니다.

```tsx
// ❌ 같은 객체를 변경: 화면이 안 바뀜
position.x = e.clientX
setPosition(position)
// ✅ 새 객체를 만들어 교체
setPosition({ ...position, x: e.clientX })
```

- 중첩된 값은 바꿀 경로의 단계마다 새로 만듭니다.

```tsx
// ❌ person을 직접 변경
person.artwork.city = 'Seoul'
// ✅ 경로의 각 단계를 복사
setPerson({
  ...person,
  artwork: { ...person.artwork, city: 'Seoul' },
})
```

- 배열은 원본을 바꾸는 메서드를 피하고 새 배열을 돌려주는 메서드를 씁니다.

| 하고 싶은 일 | ❌ 원본을 바꿈 | ✅ 새 배열 |
|--------------|----------------|-------------|
| 추가 | `push`, `unshift` | `[...arr, item]` |
| 삭제 | `splice` | `filter` |
| 교체 | `arr[i] = x` | `map` |
| 정렬·뒤집기 | `sort`, `reverse` | `toSorted`, `toReversed` (ES2023) |

- 렌더 중에 만든 새 객체는 얼마든지 고쳐도 됩니다. 이미 State에 들어 있는 객체를 고치지 않는 것이 규칙입니다.
- 중첩이 깊어 복사 코드가 길어지면 Immer를 씁니다(자세히는 25편). 스프레드는 얕은 복사라서 복사하지 않은 단계는 원본과 공유됩니다(자세히는 JavaScript 과목).
- 직접 변경하면 화면이 안 바뀌는 것 외에 `React.memo`, `useMemo`, Effect 의존성 비교도 같은 참조라서 변화를 놓칩니다.

## index key 남용

리스트의 `key`로 배열 인덱스를 쓰면, 항목이 추가·삭제·재정렬될 때 같은 자리의 항목이 같은 컴포넌트로 취급되어 State가 엉뚱한 항목에 남습니다.

```tsx
// ❌ index가 key
{items.map((item, i) => (
  <Row key={i} label={item} />
))}
// ✅ 데이터의 고유 id가 key
{items.map((item) => (
  <Row key={item.id} label={item.label} />
))}
```

- 직접 확인한 증상입니다. 각 행에 입력 칸이 있는 목록에서 첫 행 `A`에 글자를 입력한 뒤 맨 앞에 `Z`를 추가하면, 입력한 글자가 `Z` 행에 남고 `A` 행은 비어 있습니다. 위치(인덱스)가 같아서 React가 같은 컴포넌트로 재사용했기 때문입니다.
- 키 규칙: 형제 사이에서 유일하고, 렌더 사이에 바뀌지 않아야 합니다. 서버 데이터는 DB의 id를, 로컬에서 만든 항목은 만들 때 `crypto.randomUUID()`나 증가하는 카운터로 id를 붙입니다.
- `key={Math.random()}`은 더 나쁩니다. 렌더마다 키가 달라서 모든 컴포넌트와 DOM 노드가 매번 새로 만들어지고 입력 중인 값이 사라집니다.
- 항목이 추가·삭제·재정렬되지 않고 항목 안에 State도 없는 정적 목록에서는 인덱스 키의 문제가 드러나지 않습니다. 그래도 고유 id가 있으면 id를 씁니다.
- `key`는 Props로 전달되지 않습니다. 컴포넌트 안에서 id가 필요하면 `<Row key={id} id={id} />`처럼 따로 넘깁니다.

## 렌더 중 Side Effect

렌더링은 순수해야 합니다. 같은 Props, State, Context로는 항상 같은 JSX를 돌려주고, 렌더 전부터 있던 변수나 객체를 바꾸지 않아야 합니다. 렌더 중의 API 호출, DOM 수정, 외부 변수 변경, 다른 컴포넌트의 State 변경이 모두 위반입니다.

```tsx
let guest = 0
// ❌ 렌더할 때마다 외부 변수를 바꿈
function Cup() {
  guest = guest + 1
  return <h2>손님 {guest}</h2>
}
// ✅ 값은 Props로 받는다
function Cup({ guest }: { guest: number }) {
  return <h2>손님 {guest}</h2>
}
```

- 같은 컴포넌트를 두 번 렌더하면 결과가 달라집니다. React 개발 모드의 StrictMode는 컴포넌트를 두 번 호출해서 이런 비순수 코드를 드러냅니다(자세히는 기초 18편).
- `Date.now()`, `Math.random()`처럼 호출마다 값이 달라지는 함수를 렌더 중에 쓰는 것도 같은 문제입니다. 값은 State나 Effect, 이벤트 핸들러에서 만듭니다.
- 렌더 중에 새로 만든 배열이나 객체를 변경하는 것(지역 변경)은 안전합니다. 아직 아무도 모르는 값이기 때문입니다.
- 부수 효과는 이벤트 핸들러에 두는 것이 우선이고, 그래도 불가능할 때 Effect에 둡니다.
- 렌더 중 무조건 `setState`를 부르면 렌더가 끝나지 않고 반복됩니다.

```tsx
function Bad() {
  const [n, setN] = useState(0)
  setN(n + 1) // Error: Too many re-renders.
  return <p>{n}</p>
}
```

## 조건부 Hook

Hook은 항상 컴포넌트나 커스텀 Hook의 최상위에서, 매 렌더마다 같은 순서로 호출해야 합니다. React는 Hook을 호출 순서로 구분하기 때문에 순서가 바뀌면 State를 엉뚱한 Hook에 연결합니다.

```tsx
// ❌ early return 뒤에 Hook이 있다
function Bad({ id }: { id: number | null }) {
  const [n, setN] = useState(0)
  if (id === null) return null
  const [name, setName] = useState('')
  return <p>{name}{n}</p>
}
```

- 이 컴포넌트는 `id`가 `null`에서 숫자로 바뀌면 `Rendered more hooks than during the previous render.`를, 숫자에서 `null`로 바뀌면 `Rendered fewer hooks than expected.`로 시작하는 에러를 던집니다.
- 호출할 수 없는 자리: 조건문, 반복문, early return 뒤, 이벤트 핸들러, `useMemo`·`useEffect` 같은 콜백 안, `try`/`catch`/`finally`, 클래스 컴포넌트, 일반 JavaScript 함수.
- 해결은 Hook을 전부 위로 올리고 조건은 그 아래나 Hook 안에 두는 것입니다.

```tsx
// ✅ Hook을 먼저, 조건은 그 뒤에
function Good({ id }: { id: number | null }) {
  const [n, setN] = useState(0)
  const [name, setName] = useState('')
  if (id === null) return null
  return <p>{name}{n}</p>
}
```

- 조건에 따라 Hook이 필요한 경우는 컴포넌트를 나눕니다. 조건을 만족할 때만 렌더되는 자식 컴포넌트 안에 Hook을 둡니다.
- 예외로 `use`는 조건문과 반복문 안에서 호출할 수 있습니다(자세히는 15편).
- `eslint-plugin-react-hooks`가 이 규칙 위반을 자동으로 잡습니다(자세히는 기초 26편).

## 과도한 Context

모든 값을 하나의 Context에 넣거나, 가까운 곳에만 쓰는 값까지 Context로 올리는 패턴입니다. Context 값이 바뀌면 그 Context를 읽는 모든 컴포넌트가 다시 렌더되고, 값이 어디서 오는지 추적하기도 어려워집니다.

```tsx
// ❌ 서로 다른 변화 주기의 값을 한 덩어리로
const value = { user, theme, cart, search, setSearch }
<AppContext value={value}>
  <Layout />
</AppContext>
```

- 위 구조에서는 `search` 한 글자가 바뀔 때마다 `user`나 `theme`만 읽는 컴포넌트까지 다시 렌더됩니다. 변화 주기가 다른 값은 Context를 나눕니다(자세히는 01편).
- Context를 쓰기 전에 두 가지를 먼저 봅니다. 먼저 Props로 명시적으로 넘깁니다. 중간 컴포넌트가 값을 쓰지 않고 전달만 한다면 컴포넌트를 분리해 JSX를 `children`으로 넘깁니다.

```tsx
// 중간 컴포넌트에 posts를 끼워 넘기지 않는다
<Layout><Posts posts={posts} /></Layout>
```

- Context가 맞는 곳은 테마, 현재 계정, 라우팅처럼 트리 전체가 읽는 값입니다.
- 자주 바뀌는 값을 여러 곳에서 읽어야 하면 Context가 아니라 selector로 필요한 조각만 구독하는 외부 스토어를 씁니다(자세히는 23편).

## 과도한 Memoization

`React.memo`, `useMemo`, `useCallback`을 습관적으로 모든 곳에 붙이는 패턴입니다. 공식 문서는 메모이제이션이 가치 있는 경우를 몇 가지로 한정하고, 나머지 경우에는 코드 가독성만 떨어진다고 설명합니다.

```tsx
// ❌ 싼 계산, memo가 아닌 자식에게 전달
const total = useMemo(() => a + b, [a, b])
const onClick = useCallback(() => save(a), [a])
return <button onClick={onClick}>{total}</button>
```

- `useMemo`가 의미 있는 경우: 눈에 띄게 느린 계산이면서 의존성이 드물게 바뀔 때, `memo`로 감싼 자식에게 값을 넘길 때, 다른 Hook의 의존성으로 쓸 때입니다.
- `memo`가 의미 없는 경우: Props가 항상 새 객체나 함수라서 매번 달라질 때입니다. 한 곳이라도 매번 새로운 값을 넘기면 메모이제이션 전체가 무효가 됩니다.
- 계산이 비싼지는 `console.time`으로 재 보고, 대략 1ms 이상일 때 고려하라는 것이 공식 문서의 기준입니다(자세히는 19편, 20편).
- 메모이제이션 전에 구조를 먼저 고칩니다. `children`으로 JSX를 받아 렌더 범위를 줄이고, State를 필요한 곳까지만 올리고, 불필요한 Effect와 Effect 의존성을 없앱니다.
- 렌더가 느린 것이 문제가 아니라 다시 렌더되어 버그가 생기는 것이라면 렌더가 순수하지 않다는 신호입니다. 메모이제이션이 아니라 그 버그를 고칩니다.
- React Compiler를 쓰는 프로젝트에서는 컴파일러가 자동으로 메모이제이션하므로 수동 `memo`가 대부분 필요 없습니다(자세히는 18편).

## 거대한 Component

하나의 컴포넌트가 데이터 로딩, 폼 State, 목록 렌더, 모달 제어, 스타일 분기를 모두 맡아 수백 줄이 되는 패턴입니다. 읽기 어렵고, State 하나가 바뀌어도 화면 전체가 다시 렌더되며, 테스트하기 어렵습니다.

- 줄 수가 아니라 책임이 기준입니다. 공식 문서(Thinking in React)는 컴포넌트가 한 가지 일만 하는 것이 이상적이고, 커지면 하위 컴포넌트로 나누라고 안내합니다. 컴포넌트 구조는 데이터 모델의 구조와 대응시키면 자연스럽습니다.
- 분리 대상별 방법은 다음과 같습니다.

| 덩어리 | 분리 방법 |
|--------|-----------|
| 독립된 화면 조각 | 하위 컴포넌트 |
| 상태와 Effect를 묶은 로직 | 커스텀 Hook(자세히는 기초 26편) |
| 복잡한 상태 전이 | Reducer(자세히는 02편) |
| 서버 데이터 | 쿼리 Hook(자세히는 27편) |

```tsx
// ✅ 책임별로 나눈 구조
function OrderPage() {
  const order = useOrder(id)       // 데이터
  const form = useOrderForm(order) // 폼 로직
  return (
    <>
      <OrderHeader order={order} />
      <OrderItems items={order.items} />
      <OrderForm form={form} />
    </>
  )
}
```

- State는 쓰는 컴포넌트 안으로 내립니다. 나눈 뒤 하위 컴포넌트가 자기 State를 갖게 되면 부모가 렌더되는 범위도 줄어듭니다.
- 과하게 쪼개 Props를 여러 단계로 전달하게 되면 `children` 조합으로 풉니다(위 "과도한 Context").

## Boolean Props 폭증

버튼 하나가 `isPrimary`, `isLarge`, `isDanger`, `isOutline`, `isLoading`처럼 Boolean을 계속 늘려 가는 패턴입니다. 조합 수가 Boolean 개수의 거듭제곱으로 늘고, 동시에 켜면 안 되는 조합(`isPrimary`와 `isDanger`)이 타입으로 막히지 않습니다.

```tsx
// ❌ 조합이 늘고 모순된 값이 가능하다
<Button isPrimary isDanger isLarge isOutline />
// ✅ 서로 배타적인 선택은 하나의 값으로
<Button variant="danger" size="lg" />
```

- 배타적인 선택(`primary`/`danger`)은 리터럴 유니온 하나로 묶습니다. 모순된 조합이 만들어지지 않습니다. React의 State 구조 원칙인 "모순된 State를 피하라"와 같은 원리입니다.
- 타입으로 서로 맞물리는 Props는 판별 유니온으로 표현합니다(자세히는 33편).
- 내용을 바꾸는 Boolean(`hasIcon`, `showFooter`)은 슬롯으로 바꿉니다. `icon`이나 `footer`를 JSX로 받으면 Boolean이 필요 없습니다.

```tsx
<Card icon={<StarIcon />} footer={<Actions />}>
  내용
</Card>
```

- 독립적인 켜고 끄기(`disabled`, `loading`)는 Boolean이 맞습니다. 서로 영향을 주는 Boolean이 셋 이상 늘 때 설계를 의심합니다.

## 무분별한 fetch Effect

모든 컴포넌트가 `useEffect` 안에서 `fetch`를 부르고 `data`, `loading`, `error` State를 직접 관리하는 패턴입니다. 공식 문서는 Effect 안의 데이터 요청에 네 가지 한계를 꼽습니다.

| 한계 | 설명 |
|------|------|
| 서버 렌더링 불가 | 초기 HTML에는 로딩 상태만 있고, JavaScript가 돈 뒤에야 요청이 시작된다 |
| 네트워크 워터폴 | 부모가 가져온 뒤 자식이 렌더되어야 자식의 요청이 시작된다 |
| 캐시와 프리로드 없음 | 언마운트 후 다시 마운트하면 처음부터 다시 가져온다 |
| 보일러플레이트 | 경쟁 상태 같은 예외를 직접 처리해야 한다 |

```tsx
// ❌ 응답이 순서를 바꿔 도착하면 낡은 결과가 덮어쓴다
useEffect(() => {
  fetchResults(query).then(setResults)
}, [query])
// ✅ 부득이하게 Effect를 쓴다면 cleanup으로 무시
useEffect(() => {
  let ignore = false
  fetchResults(query).then((json) => {
    if (!ignore) setResults(json)
  })
  return () => { ignore = true }
}, [query])
```

- 개발 모드의 StrictMode는 Effect를 한 번 더 실행해서 요청이 두 번 나가는 것처럼 보입니다. cleanup이 있으면 낡은 응답은 무시되어 결과는 올바릅니다(자세히는 기초 23편).
- 대안은 프레임워크의 데이터 로딩이나 클라이언트 캐시(TanStack Query, SWR, React Router의 로더)입니다. 요청 중복 제거, 캐시, 프리로드, 워터폴 방지를 대신 처리합니다(자세히는 26편, 27편).
- Effect에서 직접 가져와야 하는 경우만 위처럼 정리 함수와 함께 씁니다.

## Effect 안 setState 연쇄

Effect가 State를 바꾸고, 그 State를 의존성으로 하는 다음 Effect가 또 State를 바꾸는 연쇄입니다. 단계마다 렌더가 일어나고 중간 상태가 화면에 비칩니다. 데이터 흐름도 코드에서 한눈에 안 읽힙니다.

```tsx
// ❌ card → goldCount → round 순으로 Effect가 이어짐
useEffect(() => {
  if (card.gold) setGoldCount((c) => c + 1)
}, [card])
useEffect(() => {
  if (goldCount > 3) setRound((r) => r + 1)
}, [goldCount])
```

- 해결은 원인이 되는 이벤트 핸들러 하나에서 다음 State를 한 번에 계산하는 것입니다.

```tsx
// ✅ 이벤트 한 번에 필요한 State를 모두 갱신
function handlePlaceCard(next: Card) {
  setCard(next)
  if (next.gold && goldCount < 3) {
    setGoldCount(goldCount + 1)
  } else if (next.gold) {
    setGoldCount(0)
    setRound(round + 1)
  }
}
```

- 렌더 한 번에 모든 State가 바뀌고, 로직이 한 함수에 모여 추적이 쉽습니다. 전이가 복잡하면 Reducer로 모읍니다(자세히는 02편).
- 판단 기준은 이 코드가 화면이 나타났기 때문에 실행되는가(Effect), 사용자의 동작 때문에 실행되는가(이벤트 핸들러)입니다. 사용자 동작이 원인인 연쇄는 이벤트 핸들러로 옮깁니다.
- 각 단계가 네트워크 요청처럼 외부 시스템과의 동기화라면 Effect가 필요할 수 있습니다. 순수하게 State를 계산하는 연쇄만 제거 대상입니다.

## 컴포넌트 안에서 컴포넌트 정의

컴포넌트 함수 안에 또 다른 컴포넌트를 선언하면, 바깥 컴포넌트가 렌더될 때마다 새 함수가 만들어집니다. React는 매번 다른 컴포넌트로 인식해서 이전 것을 언마운트하고 새로 마운트하므로 안쪽 State가 사라집니다.

```tsx
function Outer() {
  const [n, setN] = useState(0)
  // ❌ 렌더마다 새 Field 함수가 만들어진다
  function Field() {
    const [v, setV] = useState('')
    const onChange = (e) => setV(e.target.value)
    return <input value={v} onChange={onChange} />
  }
  const inc = () => setN(n + 1)
  return <><Field /><button onClick={inc}>{n}</button></>
}
```

- 직접 확인한 증상입니다. 위 코드에서 입력 칸에 `abc`를 입력한 뒤 버튼을 누르면 입력 값이 빈 문자열로 돌아갑니다. 포커스도 함께 잃고, 성능도 나빠집니다.
- 해결은 컴포넌트를 모듈의 최상위에 선언하는 것입니다. 바깥 값이 필요하면 Props로 받습니다.

```tsx
// ✅ 최상위에 선언
function Field() {
  const [v, setV] = useState('')
  const onChange = (e) => setV(e.target.value)
  return <input value={v} onChange={onChange} />
}
```

- 컴포넌트를 만드는 다른 호출(`memo`, `lazy`)을 렌더 중에 부르는 것도 같은 문제입니다. 렌더마다 새 컴포넌트 타입이 생깁니다(자세히는 12편).
- 안에서 함수를 호출해 JSX를 돌려받는 것(`renderRow()`를 `{renderRow()}`로 호출)은 컴포넌트가 아니라 일반 함수 호출이라서 이 문제가 없습니다. 다만 그 함수 안에서는 Hook을 쓸 수 없습니다.

## 전역 스토어에 서버 데이터 복제

서버에서 가져온 데이터를 Zustand나 Redux 같은 전역 스토어에 다시 복사해 두는 패턴입니다. 진실의 원천이 둘이 되어 어긋납니다. 캐시 갱신, 재요청, 낡은 데이터 처리를 직접 구현해야 합니다.

```tsx
// ❌ 쿼리 결과를 스토어로 복사
const { data } = useUsers()
useEffect(() => {
  if (data) useUserStore.getState().setUsers(data)
}, [data])
```

- 서버 데이터는 서버가 소유하고 클라이언트에는 그 스냅샷의 캐시가 있을 뿐입니다. TanStack Query 같은 도구가 이 캐시를 소유합니다. 데이터가 필요한 컴포넌트는 같은 쿼리 Hook을 호출하면 되고, 중복 요청은 하나로 합쳐집니다(자세히는 26편).
- 스토어에는 서버에서 오지 않는 클라이언트 상태(필터, 선택한 id, 모달 열림, 테마)만 둡니다. 선택한 항목은 id만 저장하고 서버 데이터에서 찾습니다(위 "Effect로 Derived State"의 원칙과 같습니다).

```tsx
// ✅ 서버 데이터는 쿼리, UI 상태만 스토어
const { data: users } = useUsers()
const selectedId = useUiStore((s) => s.selectedId)
const selected = users?.find((u) => u.id === selectedId)
```

- TanStack Query 문서도 서버 상태를 쿼리로 옮기면 남는 전역 상태가 크게 줄고, 테마나 사이드바 같은 UI 상태 정도가 남는다고 설명합니다(자세히는 22편, 28편).
- 예외: 편집 폼의 초안처럼 서버 값에서 출발해 사용자가 수정하는 값은 의도적인 복사입니다. 이 경우에도 `initialValues` 같은 이름으로 복사임을 드러내고, 서버 데이터가 바뀌어도 사용자 입력을 덮어쓰지 않는 것이 맞는지 정합니다.
- Redux Toolkit의 RTK Query처럼 스토어 안에 있어도 서버 상태를 소유하는 도구는 별도의 복사가 아니라 캐시 그 자체입니다(자세히는 25편).

## 핵심 정리

- Props를 State에 복사하거나(첫 값만 반영), Effect로 파생 State를 만들면(렌더 2번) 화면이 낡습니다. 렌더 중 계산이나 id 저장 + 조회, `key`로 해결합니다.
- State는 직접 바꾸지 않고 새 객체·배열로 교체합니다. index를 `key`로 쓰면 항목 이동 시 State가 엉뚱한 항목에 남으므로 고유 id를 씁니다.
- 렌더는 순수해야 하고(외부 변수·API·`Math.random` 금지) Hook은 최상위에서 같은 순서로만 호출합니다.
- Context·Memoization·컴포넌트 크기·Boolean Props는 과하지 않게 씁니다. Context는 나누거나 합성으로 풀고, 메모이제이션은 측정 뒤에 쓰고, 컴포넌트는 책임으로 나누고, 배타적 Boolean은 `variant` 하나로 묶습니다.
- 데이터 요청을 각 컴포넌트의 Effect에서 직접 처리하지 않고 클라이언트 캐시나 프레임워크에 맡기며, Effect 연쇄는 이벤트 핸들러로 옮깁니다.
- 컴포넌트는 최상위에 선언하고(안에 선언하면 State 초기화), 서버 데이터는 쿼리 캐시가 소유하며 전역 스토어에는 클라이언트 상태만 둡니다.

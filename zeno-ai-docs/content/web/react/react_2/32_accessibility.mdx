## Semantic HTML

시맨틱 HTML은 요소가 겉모양이 아니라 의미로 쓰이는 HTML입니다. 올바른 요소를 고르면 키보드 동작과 스크린 리더용 역할이 기본으로 따라옵니다. 접근성의 출발점이고, ARIA보다 먼저 고려합니다.

```jsx
// ❌ 의미가 없는 div 덩어리
<div onClick={save}>저장</div>

// ✅ 의미 있는 요소
<button type="button" onClick={save}>저장</button>
```

| 용도 | 요소 |
|------|------|
| 페이지 영역(landmark) | `header`, `nav`, `main`, `aside`, `footer` |
| 제목 위계 | `h1`–`h6`. 건너뛰지 않고 순서대로 |
| 목록 | `ul`, `ol`, `dl` |
| 표 | `table`, `caption`, `th scope` |
| 동작 / 이동 | `button` / `a href` |

- 스크린 리더 사용자는 제목과 landmark로 페이지를 훑습니다. `main` 은 페이지에 하나만 둡니다.
- 제목은 크기가 아니라 구조를 위한 것입니다. 크기는 CSS로 조절합니다.
- React에서 의미 없는 `div` 래퍼를 피하려면 Fragment를 씁니다. `dl` 안의 `dt`·`dd` 묶음이 대표적입니다.
- 문서 단위: `html` 에 `lang`, 페이지마다 의미 있는 `title` 을 둡니다.
- 건너뛰기 링크(`href="#main-content"` 가 `main` 의 `id` 로 이동)를 맨 앞에 두면 반복되는 내비게이션을 건너뜁니다.

## label

`label` 은 폼 컨트롤에 이름을 붙이는 요소입니다. 화면에 보이는 설명이자 스크린 리더가 읽는 이름이고, 클릭하면 컨트롤이 포커스됩니다.

```jsx
const id = useId()

<label htmlFor={id}>이메일</label>
<input id={id} type="email" />

<label>
  이름 <input type="text" />
</label>
```

- JSX에서는 `for` 대신 `htmlFor` 를 씁니다.
- 연결 방법은 `htmlFor`-`id` 와 중첩 두 가지입니다. 재사용 컴포넌트의 `id` 는 `useId` 로 만들면 중복되지 않습니다(자세히는 5편).
- `placeholder` 는 `label` 을 대신하지 못합니다. 입력을 시작하면 사라지고 대비도 낮기 쉽습니다.
- `label` 안에 링크나 버튼을 넣지 않습니다. 보조 기술이 혼란스러워합니다.
- 버튼에는 `label` 이 필요 없습니다. 버튼의 텍스트가 이름입니다.
- 라벨은 시각적으로 숨기더라도(CSS로) 스크린 리더에는 남깁니다. 숨길 수 없을 때는 `aria-label` 을 씁니다(아래 "접근 가능한 이름").

## button

`button` 은 동작(제출, 열기, 닫기, 토글)을 일으키는 요소입니다. `Tab` 으로 포커스되고 `Enter`·`Space` 로 활성화되는 동작이 기본 제공됩니다.

```jsx
<button type="button" onClick={open}>메뉴 열기</button>

<button type="button" aria-label="닫기" onClick={close}>
  <CloseIcon aria-hidden="true" />
</button>
```

- 폼 안의 `button` 은 `type` 을 생략하면 제출 버튼입니다. 제출이 아니면 `type="button"` 을 명시합니다.
- `div`·`span` 에 `onClick` 을 달면 포커스도, `Enter`·`Space` 동작도, 역할도 없습니다. 직접 만들려면 `role`, `tabIndex`, 키 핸들러를 모두 구현해야 하므로 `button` 을 씁니다.
- 아이콘만 있는 버튼은 접근 가능한 이름이 필요합니다. `aria-label` 을 주고 아이콘은 `aria-hidden` 으로 숨깁니다.
- 토글 상태는 `aria-pressed`, 펼침 상태는 `aria-expanded` 로 전달합니다.

## link

`a` 는 다른 주소나 위치로 이동하는 요소입니다. 동작을 일으키는 용도가 아니라 내비게이션 용도입니다.

| 구분 | 링크(`a href`) | 버튼(`button`) |
|------|----------------|----------------|
| 용도 | 이동 | 동작 실행 |
| 키보드 | `Enter` | `Enter`, `Space` |
| 새 탭으로 열기 | 가능 | 불가능 |

- `href` 가 없는 `a`, `href="#"` 에 `onClick` 을 단 `a` 는 링크도 버튼도 아닙니다. 동작이면 `button`, 이동이면 실제 주소를 `href` 에 둡니다.
- 라우터의 `Link` 컴포넌트는 `a` 로 렌더링됩니다. 클라이언트 라우팅에서도 링크를 `button` + `navigate` 로 바꾸지 않습니다.
- 링크 텍스트는 목적지를 설명합니다. "여기", "더보기"만 있는 링크는 링크 목록으로 읽는 사용자에게 의미가 없습니다.
- 현재 페이지를 나타내는 내비게이션 링크에는 `aria-current="page"` 를 줍니다.

## form

폼 접근성의 핵심은 모든 컨트롤에 이름이 있고, 에러가 입력과 연결되어 있고, 키보드만으로 제출이 되는 것입니다.

```jsx
<input
  id="email" type="email" required
  aria-invalid={!!error}
  aria-describedby={error ? 'email-err' : undefined}
/>
{error && <p id="email-err" role="alert">{error}</p>}
```

- 에러 메시지는 `aria-describedby` 로 입력과 연결합니다. 입력에 포커스했을 때 에러가 함께 읽힙니다.
- 오류 상태는 `aria-invalid` 로 전달합니다. 색만으로 오류를 표시하지 않고 텍스트와 아이콘을 함께 씁니다.
- 새로 나타나는 에러는 `role="alert"` 또는 `aria-live` 영역으로 알립니다(아래 "스크린 리더").
- 제출 실패 시 첫 번째 오류 입력으로 포커스를 옮기면 키보드·스크린 리더 사용자가 수정을 시작하기 쉽습니다(React Hook Form은 기본으로 `ref` 로 오류 포커스를 지원합니다, 31편).
- 필수 입력은 `required` 속성으로 표시하고, 입력 목적에 맞는 `type` 과 `autocomplete` 를 줍니다.
- 폼 컴포넌트 구현은 31편, 제출 중 상태 표시는 30편을 봅니다.

## fieldset / legend

`fieldset` 은 관련된 컨트롤을 묶고 `legend` 는 그 묶음의 이름입니다. 라디오·체크박스 그룹은 질문 자체가 이름이므로 필수입니다.

```jsx
<fieldset>
  <legend>배송 방법</legend>
  <label>
    <input type="radio" name="ship" value="std" /> 일반
  </label>
  <label>
    <input type="radio" name="ship" value="fast" /> 빠른
  </label>
</fieldset>
```

- 라디오 각각의 `label` 은 선택지 이름이고, `legend` 가 그룹의 질문 이름입니다. 스크린 리더는 두 가지를 함께 읽습니다.
- `fieldset` 의 암묵적 역할은 `group` 입니다. `legend` 는 첫 번째 자식이어야 합니다.
- `fieldset` 에 `disabled` 를 주면 안의 컨트롤이 모두 비활성이 됩니다. 예외로 `legend` 안의 컨트롤은 비활성이 되지 않습니다.
- 주소처럼 여러 입력이 한 의미를 이루는 묶음에도 씁니다. 묶는 것이 의미 없으면 쓰지 않습니다.

## ARIA

ARIA(WAI-ARIA)는 HTML이 표현하지 못하는 역할(role), 상태, 속성을 보조 기술에 전달하는 속성들입니다. 첫 번째 규칙은 네이티브 HTML로 가능하면 ARIA를 쓰지 않는다는 것입니다. APG는 "ARIA 없음이 잘못된 ARIA보다 낫다"고 말합니다.

- 역할은 약속입니다. `role="button"` 을 달면 키보드 동작을 직접 구현해야 하고, ARIA는 동작을 추가해 주지 않습니다.
- JSX에서 ARIA 속성은 `aria-label`, `aria-expanded` 처럼 하이픈 표기 그대로 씁니다.
- 대표 속성은 다음과 같습니다.

| 속성 | 용도 |
|------|------|
| `aria-label`, `aria-labelledby` | 이름 지정 |
| `aria-describedby` | 보조 설명 연결 |
| `aria-expanded` | 펼침·접힘 상태 |
| `aria-controls` | 제어 대상 연결 |
| `aria-current` | 현재 항목 |
| `aria-invalid`, `aria-required` | 입력 오류, 필수 |
| `aria-hidden` | 보조 기술에서 숨김 |
| `aria-live`, `role="alert"`, `role="status"` | 동적 변경 알림 |

- `aria-hidden="true"` 를 포커스 가능한 요소에 달지 않습니다. 보이지 않는 요소로 포커스가 들어갑니다.
- 상태를 나타내는 값은 코드와 일치시킵니다. `aria-expanded` 를 `useState` 와 연결하지 않으면 거짓이 됩니다.

```jsx
<button
  aria-expanded={open}
  aria-controls="menu"
  onClick={() => setOpen(!open)}
>
  메뉴
</button>
<ul id="menu" hidden={!open}>{/* ... */}</ul>
```

## Accessible Name

접근 가능한 이름(accessible name)은 보조 기술이 요소를 부를 때 쓰는 텍스트입니다. 버튼, 링크, 입력, 의미 있는 이미지는 모두 이름이 있어야 합니다. 이름은 다음 출처에서 계산됩니다.

| 출처 | 예 |
|------|----|
| `aria-labelledby` | 화면의 다른 요소를 이름으로 참조 |
| `aria-label` | 보이지 않는 이름 직접 지정 |
| 연결된 `label` | `label` 과 입력 |
| 요소 내용 | `button` 과 `a` 의 텍스트 |
| 속성 | 이미지의 `alt` |
| `title` | 최후의 대체. 신뢰하기 어려움 |

- 화면에 보이는 텍스트가 이름이 될 수 있으면 그것을 씁니다. `aria-label` 은 보이는 텍스트가 없을 때의 선택입니다.
- `aria-labelledby` 와 `aria-label` 을 함께 달면 `aria-labelledby` 가 우선합니다. 둘을 같이 쓰지 않습니다.
- `aria-label` 은 번역 도구가 번역하지 않습니다. 다국어 화면에서는 보이는 텍스트를 우선합니다.
- 장식용 이미지는 `alt=""`, 의미 있는 이미지는 내용을 설명하는 `alt` 를 줍니다.
- 이름은 같은 화면에서 구별되게 만듭니다. "삭제" 버튼이 여러 개면 `aria-label="상품 A 삭제"` 처럼 대상을 붙입니다.
- 계산된 이름은 브라우저 개발자 도구의 접근성 패널에서 확인합니다.

## Keyboard

모든 기능은 키보드만으로 쓸 수 있어야 합니다. 마우스를 못 쓰는 사용자와 스크린 리더 사용자가 해당합니다.

- 기본 포커스 요소: `a`(href 있음), `button`, `input`, `select`, `textarea`, `summary`. 네이티브 요소를 쓰면 `tabIndex` 가 필요 없습니다.
- `tabIndex`: `0` 은 탭 순서에 넣고, `-1` 은 탭 순서에서 빼되 `focus()` 로 이동은 가능하게 합니다. 양수 값은 순서를 어지럽히므로 쓰지 않습니다.
- 탭 순서는 DOM 순서입니다. CSS로 시각 순서만 바꾸면 포커스 순서와 어긋납니다.
- 포커스가 어디 있는지 보여야 합니다. `outline: none` 을 쓴다면 대체 표시를 반드시 줍니다.
- `onClick` 만 있는 비네이티브 요소는 키보드로 동작하지 않습니다. 네이티브 요소로 바꿉니다.
- 위젯별 키(메뉴의 방향키, 탭의 방향키, `Escape` 로 닫기)는 APG 패턴을 따릅니다(아래 "WAI-ARIA Authoring Practices").
- "바깥 클릭으로 닫기"는 키보드로 동작하지 않으므로 `Escape` 와 `onBlur`·`onFocus` 처리도 함께 구현합니다.

```jsx
function onKeyDown(e) {
  if (e.key === 'Escape') close()
}
<div role="dialog" onKeyDown={onKeyDown}>{/* ... */}</div>
```

## Focus Management

포커스 관리는 화면이 바뀔 때 포커스를 의도한 곳에 두는 일입니다. 브라우저는 DOM이 사라지거나 나타날 때 포커스를 알아서 옮겨 주지 않습니다.

```jsx
const ref = useRef(null)
useEffect(() => {
  if (open) ref.current?.focus()
}, [open])

<h2 ref={ref} tabIndex={-1}>삭제하시겠습니까?</h2>
```

- 포커스를 옮길 대상이 원래 포커스 불가 요소(제목, 컨테이너)면 `tabIndex={-1}` 을 주고 ref로 `focus()` 를 호출합니다(ref는 3편).
- 다이얼로그나 메뉴를 열면 안쪽으로 포커스를 옮기고, 닫으면 열었던 트리거로 되돌립니다.
- 오류가 생겼을 때 에러 요약이나 첫 오류 입력으로 포커스를 옮깁니다.
- 사라질 요소에 포커스가 있으면 포커스가 `body` 로 날아갑니다. 삭제 후 다음 항목이나 목록 제목으로 옮깁니다.
- 포커스를 일부러 가두는(trap) 곳은 모달뿐입니다. 그 밖에서는 가두지 않습니다.
- `autoFocus` 는 페이지 로드 때 스크린 리더 사용자의 맥락을 끊을 수 있으므로 다이얼로그처럼 의도가 분명한 곳에만 씁니다.

## Screen Reader

스크린 리더는 화면 대신 접근성 트리(역할, 이름, 상태)를 읽어 주는 보조 기술입니다. NVDA, JAWS(Windows), VoiceOver(macOS·iOS), TalkBack(Android)이 대표적입니다.

- 읽는 내용은 역할, 이름, 상태, 값입니다. "저장, 버튼", "이메일, 편집 필드, 필수" 같은 형태입니다.
- 화면에 보이지만 읽히지 않으면 안 되는 정보가 없도록 합니다. 색, 위치, 아이콘으로만 전달한 정보는 사라집니다.
- 읽혀야 하지만 화면에는 필요 없는 문구(예: 아이콘 버튼의 설명)는 `aria-label` 이나 시각적으로만 숨긴 텍스트(`sr-only` CSS)로 넣습니다. `display: none` 이나 `aria-hidden` 은 스크린 리더에서도 숨깁니다.
- 동적 변경 알림은 라이브 영역으로 합니다.

| 방식 | 읽는 시점 | 용도 |
|------|-----------|------|
| `role="status"`(`aria-live="polite"`) | 현재 읽기가 끝난 뒤 | 저장 완료, 갱신 중 |
| `role="alert"`(`aria-live="assertive"`) | 즉시 끼어듦 | 오류 |

- `aria-live` 와 `role="status"` 영역은 화면에 먼저 렌더링해 두고 내용만 바꾸는 방식이 변경을 놓치지 않습니다.
- 여러 부분이 비동기로 갱신되는 영역은 `aria-busy="true"` 로 표시했다가 끝나면 `false` 로 바꿔 중간 상태가 읽히지 않게 합니다(비동기 UI는 30편).
- 마우스를 빼고 `Tab` 으로 이동해 보는 점검, 실제 스크린 리더로 읽어 보는 점검을 함께 합니다. 자동 도구는 일부만 잡습니다.

## Color Contrast

색 대비는 글자와 배경의 명도 차이입니다. WCAG 2.2 AA 기준은 다음과 같습니다.

| 대상 | 최소 대비 |
|------|-----------|
| 일반 텍스트 | 4.5:1 |
| 큰 텍스트(18pt 이상, 또는 14pt 이상 굵게) | 3:1 |

- 비활성 컨트롤의 텍스트, 순수 장식, 로고는 기준에서 제외됩니다.
- 아이콘, 입력 테두리 같은 UI 요소와 그래픽에는 텍스트와는 별도 기준(1.4.11)이 있습니다.
- 색만으로 정보를 구별하지 않습니다. 오류를 빨간색만으로 표시하지 않고 문구와 아이콘을 함께 씁니다.
- 대비는 브라우저 개발자 도구의 색 선택기나 대비 검사 도구로 측정합니다. 눈대중으로 판단하지 않습니다.
- 디자인 토큰 단계에서 쓰는 색 조합의 대비를 미리 맞추면 컴포넌트마다 검사할 필요가 줄어듭니다.
- 다크 모드는 별도의 색 조합이므로 각각 대비를 확인합니다.

## Reduced Motion

일부 사용자는 큰 움직임으로 어지러움이나 불편을 겪습니다. OS의 "동작 줄이기" 설정을 `prefers-reduced-motion` 미디어 쿼리로 읽을 수 있습니다(값은 `no-preference`, `reduce`).

```css
.card { transition: transform 300ms; }

@media (prefers-reduced-motion: reduce) {
  .card { transition: none; }
}
```

JS에서는 `matchMedia` 로 읽습니다.

```jsx
const reduce = window.matchMedia(
  '(prefers-reduced-motion: reduce)',
).matches
// true면 이동·확대 애니메이션을 생략한다
```

- 줄일 대상은 확대·축소, 큰 이동, 패럴랙스, 빠른 전환입니다.
- 모든 애니메이션을 없애는 것이 아니라 투명도 변화처럼 작은 대체 효과로 바꿀 수 있습니다.
- 모든 브라우저에서 널리 지원됩니다(2020년 1월부터 Baseline).
- 값이 바뀔 수 있으므로 JS에서 쓰려면 `change` 이벤트를 구독해야 합니다. 렌더링에 쓰는 값이라면 `useSyncExternalStore` 로 구독합니다(5편).
- ViewTransition이나 라이브러리 애니메이션도 같은 설정을 따르도록 끕니다(16편).

## Portal 접근성

Portal은 DOM 위치만 옮기므로(14편) 접근성 트리와 포커스 순서도 새 DOM 위치를 따릅니다. 그래서 모달, 툴팁, 드롭다운에서는 직접 챙길 것이 있습니다.

| 항목 | 챙길 것 |
|------|---------|
| 역할과 이름 | `role="dialog"`, `aria-modal="true"`, `aria-labelledby` 로 제목 연결 |
| 초기 포커스 | 열릴 때 다이얼로그 안으로 이동 |
| 포커스 가두기 | `Tab`, `Shift+Tab` 이 안에서만 순환 |
| 닫기 | `Escape` 로 닫힘 |
| 포커스 복귀 | 닫으면 연 트리거로 복귀 |
| 배경 | 뒤쪽 콘텐츠를 `inert` 로 만들어 포커스와 보조 기술 접근 차단 |

- `aria-modal` 은 실제로 바깥 상호작용을 막고 시각적으로도 가릴 때만 달아야 합니다. 그렇지 않으면 보조 기술 사용자에게 심각한 문제가 생깁니다.
- 배경 차단에는 `inert` 속성을 씁니다. 포커스, 클릭, 보조 기술 접근을 모두 막습니다. React 19부터 JSX에서 `inert` 를 지원합니다.
- 네이티브 `dialog` 요소의 `showModal()` 은 `role="dialog"`, `aria-modal`, 배경 inert 처리, `Escape` 닫기, 닫을 때 포커스 복귀를 기본으로 제공합니다. 직접 구현하는 것보다 오류가 적습니다(Portal과의 비교는 14편).
- Portal의 DOM 위치가 `body` 끝이면 시각적으로 가까운 트리거와 DOM 순서가 멀어집니다. 툴팁은 `aria-describedby` 로 트리거와 연결합니다.
- React 트리에서는 이벤트와 Context가 Portal을 가로질러 전달되지만 DOM과 포커스는 그렇지 않습니다. 둘을 구별해서 생각합니다.

## WAI-ARIA Authoring Practices

WAI-ARIA Authoring Practices Guide(APG)는 W3C가 제공하는 위젯별 설계 패턴 모음입니다. 탭, 메뉴, 콤보박스, 다이얼로그, 아코디언 같은 복합 위젯이 갖춰야 할 역할, 속성, 키보드 동작을 정리합니다.

- 직접 만드는 위젯은 APG 패턴의 키보드 동작을 기준으로 삼습니다. 예를 들어 모달 다이얼로그는 `Tab` 순환, `Escape` 닫기, 포커스 복귀를 요구합니다.
- APG는 ARIA 1.2 기준의 이상적인 구현을 보여 주며, 브라우저와 보조 기술의 지원 차이를 보완하는 우회법은 다루지 않습니다. 실제 대상 환경에서 직접 테스트합니다.
- 복합 위젯을 처음부터 만들기보다 접근성을 구현해 둔 헤드리스 컴포넌트(Radix Primitives 등)를 쓰는 것이 일반적입니다. 그래도 라벨과 맥락은 직접 제공해야 합니다.
- 패턴이 요구하는 역할을 달았다면 그 역할의 키 동작은 코드로 구현해야 합니다.

## eslint-plugin-jsx-a11y

`eslint-plugin-jsx-a11y` 는 JSX의 접근성 문제를 정적으로 검사하는 ESLint 플러그인입니다. 개발 중에 빠르게 잡아 줍니다.

```js
// eslint.config.js (flat config)
import jsxA11y from 'eslint-plugin-jsx-a11y'

export default [
  jsxA11y.flatConfigs.recommended,
]
// 기존 설정 방식: extends: ['plugin:jsx-a11y/recommended']
```

- 프리셋은 `recommended` 와 `strict` 가 있습니다.
- 대표 규칙:

| 규칙 | 잡는 것 |
|------|---------|
| `alt-text` | 이미지 대체 텍스트 누락 |
| `anchor-is-valid` | 유효하지 않은 `a` |
| `click-events-have-key-events` | 클릭만 있고 키 핸들러 없음 |
| `no-static-element-interactions` | 역할 없는 요소에 이벤트 |
| `label-has-associated-control` | 연결되지 않은 `label` |
| `aria-props`, `role-has-required-aria-props` | 잘못된 ARIA |

- 직접 만든 컴포넌트를 DOM 요소로 매핑해야 규칙이 적용됩니다. 설정의 `settings` 안 `jsx-a11y.components` 에 `CustomButton: 'button'` 처럼 적습니다.
- JSX의 정적 검사라서 실제 렌더링 결과(색 대비, 포커스 순서, 동적 상태)는 잡지 못합니다. 런타임 도구(`axe-core` 계열)와 수동 점검을 함께 합니다.
- 컴포넌트 테스트에서 역할과 이름으로 요소를 찾는 습관은 접근성 점검이 됩니다(35편).

## 핵심 정리

- 네이티브 HTML이 먼저입니다. `button`, `a`, `label`, `fieldset`, `main` 같은 시맨틱 요소가 키보드 동작과 역할을 기본으로 제공하고, ARIA는 HTML로 표현할 수 없을 때만 씁니다.
- 모든 컨트롤은 접근 가능한 이름이 있어야 합니다. 보이는 텍스트가 우선이고 아이콘 버튼은 `aria-label` 입니다. 입력의 에러는 `aria-describedby` 와 `aria-invalid` 로 연결합니다.
- 키보드만으로 모든 기능을 쓸 수 있어야 하며, `tabIndex` 는 `0` 과 `-1` 만 쓰고, 화면이 바뀔 때 포커스를 이동하고 닫을 때 되돌립니다.
- 색 대비는 AA 기준으로 일반 텍스트 4.5:1, 큰 텍스트 3:1이고, `prefers-reduced-motion` 으로 큰 움직임을 줄입니다.
- 모달 Portal은 `role="dialog"`, 포커스 이동·가두기·복귀, `Escape`, 배경 `inert` 를 챙기거나 네이티브 `dialog` 의 `showModal()` 을 씁니다.
- 복합 위젯은 APG 패턴을 따르고, `eslint-plugin-jsx-a11y` 는 정적 문제만 잡으므로 런타임 도구와 수동 점검을 함께 합니다.

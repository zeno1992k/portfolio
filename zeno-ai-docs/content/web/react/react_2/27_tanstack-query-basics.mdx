## QueryClient와 Provider

`QueryClient`는 쿼리 캐시와 기본 옵션을 가진 객체이고, `QueryClientProvider`는 이 객체를 컴포넌트 트리에 내려주는 컴포넌트입니다. 패키지는 `@tanstack/react-query`이며 React 18 이상이 필요합니다.

```tsx
import { QueryClient, QueryClientProvider }
  from '@tanstack/react-query'

const queryClient = new QueryClient()

root.render(
  <QueryClientProvider client={queryClient}>
    <App />
  </QueryClientProvider>,
)
```

- `QueryClient`는 앱에서 하나만 만들어 모든 컴포넌트가 공유합니다. 컴포넌트 안에서 렌더링마다 새로 만들면 캐시가 매번 사라집니다. 모듈 최상위에 두거나 `useState`로 한 번만 만듭니다.
- 생성자에 `defaultOptions`를 주면 모든 쿼리의 기본값을 바꿀 수 있습니다.

```ts
new QueryClient({
  defaultOptions: { queries: { staleTime: 60_000 } },
})
```

- 컴포넌트 안에서는 `useQueryClient()`로 꺼내고, 컴포넌트 밖 코드에서는 만들어 둔 인스턴스를 직접 씁니다.
- `QueryClient`는 쿼리 캐시와 뮤테이션 캐시를 따로 가집니다(28편).

## useQuery

`useQuery`는 키와 함수를 받아 서버 데이터를 읽고, 로딩·에러·데이터 상태를 돌려주는 훅입니다. v5에서는 객체 하나만 인자로 받습니다.

```tsx
function Todos() {
  const { isPending, isError, error, data } = useQuery({
    queryKey: ['todos'],
    queryFn: fetchTodos,
  })
  if (isPending) return <p>Loading...</p>
  if (isError) return <p>{error.message}</p>
  const rows = data.map((t) => <li key={t.id}>{t.text}</li>)
  return <ul>{rows}</ul>
}
```

- 필수는 `queryKey`와 `queryFn`입니다.
- 이 순서로 확인하면 `isPending`과 `isError` 검사를 지난 아래에서 `data`가 있다는 것이 타입으로도 보장됩니다.
- 같은 키를 쓰는 컴포넌트가 여러 개여도 요청은 한 번이고 캐시는 공유됩니다(26편).
- 주요 반환값은 다음과 같습니다.

| 값 | 의미 |
|----|------|
| `data` | 마지막으로 성공한 데이터. 없으면 `undefined` |
| `error` | 실패했을 때의 에러. 없으면 `null` |
| `status` | 데이터가 있는지: `pending`, `error`, `success` |
| `fetchStatus` | 요청이 실행 중인지: `fetching`, `paused`, `idle` |
| `isPending` `isError` `isSuccess` | `status`의 불리언 버전 |
| `isFetching` | `fetchStatus`가 `fetching`인지 |
| `refetch` | 직접 다시 요청하는 함수 |

## queryKey 설계

쿼리 키는 캐시 항목의 이름이자 열쇠입니다. 키가 같으면 같은 데이터이고, 키가 바뀌면 다른 데이터로 취급해 다시 가져옵니다.

- 최상위는 배열이고, 요소는 `JSON.stringify`로 직렬화할 수 있어야 하며, 데이터에 대해 유일해야 합니다.
- 객체 안의 프로퍼티 순서는 무시되지만, 배열 요소의 순서는 의미가 있습니다.

```ts
['todos', { status, page }]  // 아래와 같은 키
['todos', { page, status }]
['todos', status, page]      // 아래와 다른 키
['todos', page, status]
```

- `queryFn`이 쓰는 변수는 모두 키에 넣습니다. 그러면 변수가 바뀔 때 자동으로 다시 요청하고, 변수 조합마다 캐시가 따로 쌓입니다.
- 관례는 큰 범위에서 좁은 범위 순서입니다. 목록은 `['todos']`, 필터가 있는 목록은 `['todos', { status: 'done' }]`, 한 개는 `['todos', id]`로 씁니다.
- 이 순서가 중요한 이유는 무효화입니다. `invalidateQueries({ queryKey: ['todos'] })`는 앞부분이 일치하는 키를 모두 대상으로 하므로 위 세 가지가 함께 무효화됩니다.

**흔한 실수:** 쓰는 변수를 키에서 빠뜨리는 것입니다. `queryKey: ['todo']`로 두고 `queryFn`이 `id`를 읽으면 `id`가 바뀌어도 같은 캐시를 보게 되어 옛 데이터가 나옵니다. 키 생성을 함수로 모으는 방법은 28편입니다.

## queryFn과 에러 던지기

`queryFn`은 데이터로 이행하거나 에러로 거부되는 Promise를 돌려주는 함수입니다. 쿼리의 성공과 실패는 이 Promise로 판단합니다.

```ts
async function fetchTodo(id: number) {
  const res = await fetch(`/api/todos/${id}`)
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
}
```

- 에러로 판단되려면 함수가 에러를 던지거나 거부된 Promise를 돌려줘야 합니다. `fetch`는 404나 500 응답에서도 거부되지 않으므로 `res.ok`를 확인해 직접 던져야 합니다. axios 같은 라이브러리는 기본적으로 상태 코드 에러를 던집니다.
- 데이터를 `undefined`로 돌려주면 안 됩니다. 값이 없음을 캐시하려면 `null`을 씁니다.
- 함수는 인자로 컨텍스트 객체를 받습니다. `queryKey`, `signal`(AbortSignal), `client`, `meta`가 들어 있어, 키의 변수를 꺼내 쓰거나 요청 취소에 연결할 수 있습니다(28편).

```tsx
useQuery({
  queryKey: ['todos', status],
  queryFn: ({ queryKey }) => fetchTodos(queryKey[1]),
})
```

## status와 fetchStatus

`status`는 데이터가 있는지를, `fetchStatus`는 `queryFn`이 실행 중인지를 나타냅니다. 둘은 독립적이라서 따로 봐야 합니다.

| 필드 | 값 | 의미 |
|------|----|------|
| `status` | `pending` | 아직 데이터가 없음 |
| | `error` | 쿼리가 실패함 |
| | `success` | 데이터가 있음 |
| `fetchStatus` | `fetching` | `queryFn`이 실행 중 |
| | `paused` | 요청하려 했지만 네트워크가 없어 멈춤 |
| | `idle` | 실행 중이 아님 |

- 백그라운드 재요청 때문에 모든 조합이 가능합니다. 성공한 쿼리가 `fetching`일 수 있고(갱신 중), 새 쿼리가 `pending`이면서 `paused`일 수 있습니다(오프라인).
- 불리언 파생값은 다음과 같습니다.

| 값 | 정의 |
|----|------|
| `isPending` | `status`가 `pending` |
| `isFetching` | `fetchStatus`가 `fetching` |
| `isLoading` | `isPending`이면서 `isFetching`. 처음 가져오는 중 |

- 로딩 화면은 `isPending`으로, 갱신 중 표시(작은 스피너)는 `isFetching`으로 나눠 쓰는 것이 기본입니다.
- 요청이 시작되지 않은 비활성 쿼리는 `isPending`이 `true`이고 `isLoading`은 `false`입니다. 로딩 스피너를 `isPending`으로 띄우면 비활성 쿼리에서 영원히 돕니다(아래 `enabled`).
- 오프라인 동작은 `networkMode`가 정합니다. 기본값 `online`은 오프라인에서 요청을 멈추고(`paused`), `always`는 네트워크 상태를 무시하고 요청하며, `offlineFirst`는 첫 요청은 하되 재시도는 오프라인이면 멈춥니다.

## staleTime과 gcTime

`staleTime`은 데이터를 신선하게 간주하는 시간이고, `gcTime`은 쓰는 곳이 없어진 캐시를 보관하는 시간입니다. 이름이 비슷하지만 하는 일이 다릅니다.

| 옵션 | 기본값 | 정하는 것 |
|------|--------|-----------|
| `staleTime` | 0 | 가져온 뒤 얼마 동안 다시 요청하지 않을지 |
| `gcTime` | 5분 | 사용하는 컴포넌트가 모두 사라진 뒤 캐시를 얼마나 남길지 |

- `staleTime`이 0이면 가져온 직후부터 오래된 데이터라서, 재요청 조건이 올 때마다 요청합니다. 값을 `60_000`(1분)으로 두면 그 시간 안에는 마운트나 포커스 복귀로 인한 재요청이 없습니다. 값을 `Infinity`로 두면 직접 무효화하기 전에는 오래된 데이터가 되지 않습니다.
- `gcTime`은 비활성(inactive) 시점부터 센 시간입니다. 이 시간 안에 다시 마운트되면 캐시를 즉시 보여 주고, 지나면 캐시가 삭제됩니다.

```ts
useQuery({
  queryKey: ['categories'],
  queryFn: fetchCategories,
  staleTime: 10 * 60_000, // 10분간 신선
})
```

v4의 `cacheTime`이 v5에서 `gcTime`으로 이름이 바뀌었습니다. 캐시를 보관하는 시간이 아니라 가비지 컬렉션 시점을 뜻한다는 점을 드러내기 위해서입니다.

## 자동 refetch 조건

오래된(stale) 쿼리는 세 가지 시점에 자동으로 다시 요청됩니다. 신선한 쿼리는 요청하지 않습니다.

| 조건 | 옵션 | 기본값 |
|------|------|--------|
| 쿼리를 쓰는 새 컴포넌트가 마운트됨 | `refetchOnMount` | `true` |
| 창이 다시 포커스를 받음 | `refetchOnWindowFocus` | `true` |
| 네트워크가 다시 연결됨 | `refetchOnReconnect` | `true` |

```ts
new QueryClient({
  defaultOptions: {
    queries: { refetchOnWindowFocus: false },
  },
})
```

- 옵션은 `QueryClient`의 `defaultOptions`에 전역으로 주거나, 쿼리마다 따로 줍니다.
- 포커스 감지는 브라우저의 `visibilitychange` 이벤트를 쓰며, 포커스 처리를 바꾸려면 `focusManager`를 씁니다.
- 개발 중 포커스 복귀 재요청이 동작하지 않으면 Chrome DevTools의 "Emulate a focused page" 설정을 꺼야 합니다. 이 설정이 `visibilitychange`를 막기 때문입니다.
- 사용자가 창을 오갈 때마다 요청이 나가는 것이 부담이면 끄기보다 `staleTime`을 늘리는 쪽이 의도에 맞습니다.

## enabled와 의존 쿼리

`enabled: false`는 쿼리의 자동 실행을 막는 옵션입니다. 어떤 값이 준비되기 전에는 요청하지 않고, 준비되면 요청하게 할 때 씁니다.

```tsx
const { data: user } = useQuery({
  queryKey: ['user', email],
  queryFn: () => getUserByEmail(email),
})
const userId = user?.id

const { data: projects } = useQuery({
  queryKey: ['projects', userId],
  queryFn: () => getProjectsByUser(userId!),
  enabled: !!userId,
})
```

- 두 번째 쿼리는 `userId`가 생길 때까지 실행되지 않습니다. 이처럼 앞 결과가 뒤 요청의 입력인 쿼리를 의존 쿼리라고 합니다.
- 비활성이고 캐시 데이터가 없으면 `status`는 `pending`, `fetchStatus`는 `idle`입니다. 캐시 데이터가 있으면 `success`로 시작합니다.
- 로딩 표시는 `isLoading`(`isPending && isFetching`)을 쓰면 비활성 쿼리에서 헛돌지 않습니다.
- 마운트·포커스 같은 자동 재요청은 막지만 `refetch()`로 직접 요청하는 것은 가능합니다. 클릭할 때만 요청하는 쿼리를 이렇게 만듭니다.
- TypeScript에서 값이 없을 때 타입을 좁히려면 `queryFn: userId ? () => get(userId) : skipToken`을 쓸 수 있습니다. 단 `skipToken`을 쓴 쿼리에서 `refetch()`를 부르면 `Missing queryFn` 에러가 납니다. 직접 요청이 필요하면 `enabled`를 씁니다.
- 의존 쿼리는 요청이 직렬이 되어 워터폴이 생깁니다. 서버 API를 고쳐 한 번에 가져올 수 있다면 그쪽이 더 빠릅니다.

## select

`select`는 `queryFn`이 돌려준 데이터를 컴포넌트가 쓰기 좋은 모양으로 변환하거나 일부만 뽑는 옵션입니다. 캐시에는 원본이 그대로 남습니다.

```tsx
const { data: doneCount } = useQuery({
  queryKey: ['todos'],
  queryFn: fetchTodos,
  select: (todos) => todos.filter((t) => t.done).length,
})
```

- 같은 키를 여러 컴포넌트가 다른 `select`로 읽어도 요청은 한 번이고, 컴포넌트마다 다른 모양의 데이터를 받습니다.
- `select`의 결과가 이전과 같으면 컴포넌트는 다시 렌더링되지 않습니다. 위 예에서는 할 일의 개수가 바뀔 때만 렌더링됩니다.
- 함수가 인라인이면 렌더링마다 새 함수라서 매번 다시 실행됩니다. 비용이 크면 컴포넌트 밖으로 빼거나 `useCallback`으로 고정합니다.
- 이와 별개로 TanStack Query는 데이터가 실제로 바뀌지 않았으면 이전 참조를 유지하는 구조적 공유(structural sharing)를 기본으로 하고, 사용하지 않는 반환 프로퍼티(예: `isFetching`)가 바뀌어도 렌더링하지 않는 프로퍼티 추적을 합니다.

## placeholderData와 initialData

둘 다 요청이 끝나기 전에 보여 줄 데이터를 미리 주는 옵션이지만, 캐시에 저장되는지가 다릅니다.

| 항목 | `placeholderData` | `initialData` |
|------|-------------------|---------------|
| 캐시에 저장 | 안 됨 | 저장됨 |
| 쿼리 상태 | `success`로 시작, `isPlaceholderData`가 `true` | `success`로 시작 |
| 재요청 | 항상 요청 | `staleTime`이 0이면 마운트 즉시 요청, 길면 그 시간 동안 신선 |
| 알맞은 데이터 | 미리보기, 이전 데이터 | 완전한 실제 데이터 |

```tsx
useQuery({
  queryKey: ['todo', id],
  queryFn: () => fetchTodo(id),
  placeholderData: () =>
    queryClient.getQueryData<Todo[]>(['todos'])
      ?.find((t) => t.id === id),
})
```

- 위는 목록 캐시에서 한 항목을 꺼내 상세 화면의 임시 데이터로 쓰는 예입니다. 상세 데이터가 오면 교체됩니다.
- `placeholderData`는 값이나 함수로 줍니다. 함수는 이전 쿼리의 데이터를 인자로 받으므로 키가 바뀔 때 이전 화면을 유지할 수 있습니다. 이 용도로 `keepPreviousData`를 넘기는 것이 페이지네이션 패턴입니다(26편, 28편).
- `initialData`는 캐시에 진짜 데이터로 저장되므로 부분적이거나 불완전한 데이터를 넣으면 안 됩니다.
- `initialData`에 `initialDataUpdatedAt`을 함께 주면 그 데이터가 만들어진 시각을 기준으로 신선도를 계산해, 필요할 때만 재요청합니다. 함수로 주면 쿼리가 만들어질 때 한 번만 실행됩니다.

**흔한 실수:** 미리보기용 불완전한 데이터를 `initialData`로 넣어, 실제 요청 없이 화면에 불완전한 데이터가 정상 값처럼 남는 것입니다. 임시 데이터는 `placeholderData`로 줍니다.

## retry

`retry`는 `queryFn`이 실패했을 때 자동으로 다시 시도하는 횟수를 정하는 옵션입니다. 기본값은 3회이고, 에러는 재시도가 모두 실패한 뒤에야 `error`로 나옵니다.

| 값 | 동작 |
|----|------|
| `false` | 재시도하지 않음 |
| 숫자 | 그 횟수만큼 재시도 |
| `true` | 성공할 때까지 무한 재시도 |
| 함수 | `(failureCount, error)`를 받아 `true`면 재시도 |

```ts
useQuery({
  queryKey: ['todos'],
  queryFn: fetchTodos,
  retry: (count, error) =>
    count < 3 && !(error instanceof NotFoundError),
})
```

- 재시도 간격은 `retryDelay`가 정하고, 기본은 지수 백오프입니다. `Math.min(1000 * 2 ** attemptIndex, 30000)`이라서 1초, 2초, 4초로 늘어나고 30초가 상한입니다.
- 404나 401처럼 다시 해도 소용없는 에러는 함수형 `retry`로 걸러 냅니다. 안 그러면 에러 화면이 나오기까지 수 초가 걸립니다.
- 서버 사이드 렌더링에서는 기본 재시도가 0입니다.
- 백그라운드 재요청의 재시도는 탭이 비활성이면 멈춥니다.
- 테스트에서는 `retry: false`로 두는 것이 일반적입니다(28편).
- 뮤테이션은 기본적으로 재시도하지 않습니다.

## DevTools

React Query Devtools는 캐시 안의 쿼리와 뮤테이션 상태를 화면에서 볼 수 있게 해 주는 개발 도구입니다.

```tsx
import { ReactQueryDevtools }
  from '@tanstack/react-query-devtools'

<QueryClientProvider client={queryClient}>
  <App />
  <ReactQueryDevtools initialIsOpen={false} />
</QueryClientProvider>
```

- 별도 패키지 `@tanstack/react-query-devtools`를 설치하고 `QueryClientProvider` 안에 둡니다.
- 캐시 안의 쿼리와 상태를 시각화해 캐시가 의도대로 동작하는지 확인하는 데 씁니다. v5부터 쿼리뿐 아니라 뮤테이션도 볼 수 있습니다.
- 프로덕션 빌드에는 자동으로 제외됩니다.
- 기본은 화면 모서리의 토글 버튼으로 여는 떠 있는 방식이고, `initialIsOpen`으로 처음에 열려 있을지 정합니다.

## v4에서 v5로의 변경점

v4 코드를 읽을 때 필요한 이름 변경과 제거 항목입니다.

| v4 | v5 |
|----|----|
| `useQuery(key, fn, options)` 여러 시그니처 | 객체 하나 `useQuery({ queryKey, queryFn, ... })` |
| `cacheTime` | `gcTime` |
| `status: 'loading'`, `isLoading` | `status: 'pending'`, `isPending` |
| `isLoading`(첫 로딩) | `isLoading`은 `isPending && isFetching`으로 재정의 |
| `keepPreviousData: true` | `placeholderData: keepPreviousData` |
| `useQuery`의 `onSuccess`·`onError`·`onSettled` | 제거(뮤테이션에는 남음) |
| `useErrorBoundary` | `throwOnError` |
| `useInfiniteQuery`의 `initialPageParam` 생략 | 필수 |
| `Hydrate` | `HydrationBoundary` |
| `isDataEqual` | `structuralSharing` 함수 |
| Suspense 옵션 | 전용 훅 `useSuspenseQuery` 등 |

- 최소 요구 버전은 React 18, TypeScript 4.7입니다.
- `useQuery`의 콜백이 제거됐으므로 `onSuccess`에서 `setState`로 데이터를 복사하던 코드는 `data`에서 파생해 계산하는 방식으로 바꿉니다. 전역 에러 처리는 `QueryCache`의 콜백으로 합니다(28편).
- `isPending`은 "아직 데이터가 없다"는 뜻이라서, v4의 `isLoading`을 그대로 `isPending`으로 바꾸면 비활성 쿼리에서 스피너가 영원히 도는 변화가 생깁니다. 첫 요청 중임을 말하려면 새 `isLoading`을 씁니다.

## 핵심 정리

- `QueryClient`는 앱에서 하나를 만들어 `QueryClientProvider`로 내려주고, `useQuery`는 `queryKey`와 `queryFn`을 객체로 받습니다.
- 쿼리 키는 직렬화 가능한 배열이며, `queryFn`이 쓰는 변수를 모두 넣고, 큰 범위에서 좁은 범위 순서로 짓습니다.
- `queryFn`은 실패 시 에러를 던져야 하고, `fetch`는 `res.ok`를 직접 확인합니다.
- `status`는 데이터 유무, `fetchStatus`는 요청 실행 여부이며, `isLoading`은 `isPending && isFetching`입니다.
- `staleTime`(기본 0)은 재요청 기준, `gcTime`(기본 5분)은 캐시 삭제 기준입니다. 오래된 쿼리는 마운트·포커스·재연결 때 다시 요청됩니다.
- `enabled`·`select`·`placeholderData`·`initialData`·`retry`로 실행 시점, 데이터 모양, 임시 데이터, 재시도를 조절합니다.
- v5에서는 객체 시그니처, `gcTime`, `pending`, `placeholderData`, `throwOnError`가 새 이름이고 `useQuery`의 콜백은 제거됐습니다.

## useMutation

`useMutation`은 서버의 데이터를 만들고 바꾸고 지우는 요청을 실행하는 훅입니다. `useQuery`와 달리 자동으로 실행되지 않고, `mutate`를 호출할 때 실행됩니다.

```tsx
const mutation = useMutation({
  mutationFn: (todo: NewTodo) => axios.post('/todos', todo),
})

mutation.mutate({ title: 'milk' })
```

- `mutationFn`은 변수 하나를 받아 Promise를 돌려줍니다. 변수가 여러 개면 객체로 묶어 넘깁니다.
- 상태는 `isIdle`(처음 또는 초기화 후), `isPending`(실행 중), `isError`(`error` 사용 가능), `isSuccess`(`data` 사용 가능)입니다. 상태를 비우려면 `mutation.reset()`을 부릅니다.
- `mutate`는 결과를 기다리지 않고 호출만 합니다. `mutateAsync`는 Promise를 돌려주므로 `try/catch`로 에러를 잡거나 다른 비동기 코드와 이어 쓸 수 있습니다.
- 생명주기 콜백은 실행 순서대로 `onMutate`(실행 직전), `onSuccess`, `onError`, `onSettled`(결과와 무관하게 마지막)입니다. Promise를 돌려주면 다음 콜백은 그것을 기다립니다.
- `mutate`의 두 번째 인자로도 콜백을 줄 수 있습니다. 이 콜백은 `useMutation` 쪽 콜백이 끝난 뒤에 실행됩니다.
- 뮤테이션은 기본적으로 재시도하지 않습니다. 필요하면 `retry`를 줍니다.

## invalidateQueries와 setQueryData

변경이 끝나면 서버와 어긋난 캐시를 맞춰야 합니다. 방법은 두 가지이고, 용도가 다릅니다.

| 방법 | 동작 | 적합한 경우 |
|------|------|-------------|
| `invalidateQueries` | 쿼리를 오래된 것으로 표시하고 화면에 쓰이는 쿼리를 다시 가져옴 | 서버가 계산한 결과가 필요하거나 영향 범위가 넓을 때 |
| `setQueryData` | 응답 데이터로 캐시를 직접 교체 | 변경 응답이 최신 전체 데이터일 때. 추가 요청이 없다 |

```tsx
const queryClient = useQueryClient()

useMutation({
  mutationFn: editTodo,
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['todos'] })
  },
})
```

- `invalidateQueries`는 두 가지를 합니다. 해당 쿼리에 `staleTime`을 무시하는 오래됨 표시를 하고, `useQuery`로 화면에 쓰이는 활성 쿼리는 백그라운드로 다시 가져옵니다. 화면에 쓰이지 않는 쿼리는 표시만 되어 다음에 마운트될 때 다시 가져옵니다.
- 키는 앞부분이 일치하는 쿼리를 모두 대상으로 합니다. `exact: true`를 주면 정확히 같은 키만, 필터가 더 필요하면 `predicate` 함수를 씁니다.

```ts
queryClient.invalidateQueries({ queryKey: ['todos'] })
// ['todos'], ['todos', 5], ['todos', { type: 'done' }] 모두
queryClient.invalidateQueries({
  queryKey: ['todos'],
  exact: true, // ['todos']만
})
```

- 변경의 응답이 갱신된 객체를 돌려주면 `setQueryData`로 캐시를 바로 고쳐 요청을 줄일 수 있습니다.

```tsx
useMutation({
  mutationFn: editTodo,
  onSuccess: (data, variables) => {
    queryClient.setQueryData(['todo', variables.id], data)
  },
})
```

- `setQueryData`는 함수형 갱신도 받으며 불변 방식이어야 합니다. 캐시 객체를 직접 수정하면 당장은 되는 것처럼 보여도 나중에 문제가 생깁니다.

```ts
// ❌ oldData.title = 'new title'
// ✅ 새 객체를 반환
queryClient.setQueryData(['todo', 5], (oldData) => ({
  ...oldData,
  title: 'new title',
}))
```

- 상세 캐시를 `setQueryData`로 고쳐도 목록 캐시는 그대로입니다. 목록도 영향을 받으면 함께 `invalidateQueries`합니다. 정규화된 캐시를 직접 관리하는 대신 무효화로 맞추는 것이 이 라이브러리의 방식입니다.

## 낙관적 업데이트와 롤백

낙관적 업데이트는 서버 응답 전에 성공을 가정하고 화면을 바꾸는 방식입니다(개념은 26편, React의 `useOptimistic`은 8편). TanStack Query에서는 두 가지로 구현합니다.

**UI 방식**은 캐시를 건드리지 않고, 뮤테이션이 실행 중일 때 `variables`로 임시 항목을 그립니다.

```tsx
const { isPending, variables, mutate } = useMutation({
  mutationFn: (text: string) =>
    axios.post('/api/data', { text }),
  onSettled: () =>
    queryClient.invalidateQueries({ queryKey: ['todos'] }),
})
```

```tsx
<ul>
  {todos.map((t) => <li key={t.id}>{t.text}</li>)}
  {isPending && <li className="dim">{variables}</li>}
</ul>
```

- 요청이 끝나면 `invalidateQueries`로 목록을 다시 가져오고 임시 항목은 사라집니다. 실패하면 임시 항목이 사라지므로 롤백 코드가 필요 없습니다.
- 낙관적 결과가 한 곳에만 보일 때 적합합니다. 다른 컴포넌트에서 같은 뮤테이션의 대기 상태를 읽어야 하면 `mutationKey`와 `useMutationState`를 씁니다.

**캐시 방식**은 `onMutate`에서 캐시를 먼저 고치고, 실패하면 저장해 둔 값으로 되돌립니다. 여러 화면에 한꺼번에 반영돼야 할 때 씁니다.

```tsx
const qc = useQueryClient()
const key = ['todos']
useMutation({
  mutationFn: updateTodo,
  onMutate: async (newTodo) => {
    await qc.cancelQueries({ queryKey: key })
    const previous = qc.getQueryData(key)
    qc.setQueryData(key, (old) => [...old, newTodo])
    return { previous }
  },
  onError: (err, newTodo, onMutateResult) => {
    qc.setQueryData(key, onMutateResult?.previous)
  },
  onSettled: () => qc.invalidateQueries({ queryKey: key }),
})
```

- 순서는 네 단계입니다. 진행 중인 재요청을 취소하고(`cancelQueries`, 안 하면 옛 응답이 낙관적 값을 덮어쓴다), 이전 데이터를 저장하고, 캐시를 새 값으로 바꾸고, 저장한 값을 반환합니다.
- `onMutate`가 반환한 값은 `onError`와 `onSettled`의 세 번째 인자로 전달됩니다. 롤백은 이 값으로 합니다.
- `onSettled`의 `invalidateQueries`는 성공이든 실패든 서버의 실제 상태로 최종 동기화합니다.
- 최신 문서의 예제는 콜백의 마지막 인자 `context`에서 `context.client`로 클라이언트를 꺼냅니다. 이 편은 `useQueryClient()`로 꺼낸 클라이언트를 씁니다.

**흔한 실수:** `cancelQueries`를 빼먹는 것입니다. 낙관적 값을 넣은 직후 먼저 시작된 재요청의 옛 응답이 도착하면 화면이 깜빡이며 되돌아갑니다.

## useInfiniteQuery

`useInfiniteQuery`는 쪽을 계속 이어 붙이는 목록을 위한 훅입니다. 앞서 가져온 쪽을 유지한 채 다음 쪽을 가져옵니다.

```tsx
const {
  data, fetchNextPage, hasNextPage, isFetchingNextPage,
} = useInfiniteQuery({
  queryKey: ['projects'],
  queryFn: ({ pageParam }) => fetchProjects(pageParam),
  initialPageParam: 0,
  getNextPageParam: (lastPage) => lastPage.nextCursor,
})
```

- `initialPageParam`은 v5에서 필수이고, 첫 쪽의 `pageParam` 값입니다.
- `getNextPageParam`은 마지막 쪽(과 전체 쪽 목록)에서 다음 `pageParam`을 계산합니다. `undefined`나 `null`을 돌려주면 `hasNextPage`가 `false`가 됩니다. API에 커서가 없으면 현재 `pageParam`에 1을 더하는 식으로 계산합니다.
- `data`는 `{ pages, pageParams }` 구조이고, 화면에는 `data.pages`를 쪽별로 순회해 그립니다.
- `isFetchingNextPage`로 다음 쪽 가져오는 중과 일반 백그라운드 갱신을 구분합니다.
- 진행 중인 요청이 있을 때 `fetchNextPage`를 부르면 갱신 중인 데이터를 덮어쓸 수 있으므로, 버튼은 `disabled={!hasNextPage || isFetching}`로 막습니다.
- 위로도 불러오려면 `getPreviousPageParam`과 `fetchPreviousPage`를 추가합니다.
- `maxPages`로 메모리에 둘 쪽 수를 제한할 수 있습니다.
- 무한 스크롤은 목록 끝의 요소가 보이면 `fetchNextPage`를 호출하도록 `IntersectionObserver`와 연결합니다(21편).
- 캐시 데이터를 직접 고칠 때는 `{ pages, pageParams }` 구조를 유지해야 합니다.
- 옵션을 재사용할 때는 `infiniteQueryOptions`를 씁니다.

## 페이지네이션과 이전 데이터 유지

쪽을 하나씩 교체하는 페이지네이션은 키에 페이지 번호를 넣은 일반 `useQuery`로 구현하고, 이전 쪽을 화면에 남겨 깜빡임을 막습니다.

```tsx
import { keepPreviousData, useQuery }
  from '@tanstack/react-query'

const { data, isPlaceholderData } = useQuery({
  queryKey: ['projects', page],
  queryFn: () => fetchProjects(page),
  placeholderData: keepPreviousData,
})
```

- 키가 바뀌면 새 쿼리라서 `success`와 `pending`을 오가며 화면이 깜빡입니다. `placeholderData: keepPreviousData`는 새 데이터가 오기 전까지 이전 쪽 데이터를 보여 줍니다.
- 이전 데이터를 보여 주는 동안 `isPlaceholderData`가 `true`입니다. 다음 쪽 버튼은 이 값이 `true`이거나 `hasMore`가 아닐 때 비활성화합니다.
- 주의할 점은 `placeholderData`가 항상 `success` 상태를 만든다는 것입니다. v4의 `keepPreviousData` 옵션은 이전 쿼리의 상태를 유지했지만 지금은 에러 상태가 그대로 이어지지 않습니다.
- 다음 쪽을 미리 가져오려면 `queryClient.prefetchQuery`로 `page + 1`을 요청해 둘 수 있습니다(아래 절).

## useSuspenseQuery와 Error Boundary

`useSuspenseQuery`는 데이터가 올 때까지 컴포넌트를 Suspense로 중단시키고, 실패하면 Error Boundary로 에러를 던지는 훅입니다. 로딩과 에러 UI를 컴포넌트 밖의 경계로 옮깁니다. 같은 계열로 `useSuspenseInfiniteQuery`, `useSuspenseQueries`가 있습니다.

```tsx
function Todos() {
  const { data } = useSuspenseQuery({
    queryKey: ['todos'],
    queryFn: fetchTodos,
  })
  return <List items={data} /> // data는 항상 정의됨
}
```

```tsx
<ErrorBoundary fallback={<p>failed</p>}>
  <Suspense fallback={<p>Loading...</p>}>
    <Todos />
  </Suspense>
</ErrorBoundary>
```

- `data`는 `undefined`가 아님이 타입으로 보장되어 `isPending` 분기가 필요 없습니다. 로딩은 가까운 `Suspense`의 fallback이, 실패는 Error Boundary가 맡습니다(11편, 13편).
- 제약이 있습니다. `enabled`로 조건부 실행을 할 수 없고, `placeholderData`는 쓸 수 없습니다. 의존 쿼리는 컴포넌트를 나눠 값이 준비된 쪽에서 렌더링하는 식으로 풉니다.
- 키가 바뀌는 상태 갱신은 `startTransition`으로 감싸야 합니다. 안 그러면 갱신 때마다 기존 화면이 fallback으로 바뀝니다(9편).
- 에러는 기본적으로 캐시된 데이터가 없을 때만 가까운 Error Boundary로 던져집니다. 이미 보이던 데이터가 있는데 백그라운드 재요청이 실패하면 기존 화면을 유지합니다. 규칙은 `throwOnError`의 기본값 `(error, query) => typeof query.state.data === 'undefined'`입니다.
- Error Boundary가 에러 화면에서 다시 시도할 때는 쿼리의 에러 상태도 함께 초기화해야 합니다. `QueryErrorResetBoundary`나 `useQueryErrorResetBoundary`의 `reset`을 Error Boundary의 재설정 동작에 연결합니다. 이 연결을 빠뜨리면 다시 시도해도 쿼리가 에러 상태로 남을 수 있습니다.
- 일반 `useQuery`도 `throwOnError: true`를 주면 에러를 Error Boundary로 던집니다(v4의 `useErrorBoundary`).
- 컴포넌트가 렌더링될 때 요청을 시작하는 fetch-on-render가 기본이므로, 중첩된 Suspense 컴포넌트가 순서대로 요청하면 워터폴이 생깁니다. 경로 이동 시점이나 사용자 상호작용 시점에 미리 요청하는 render-as-you-fetch로 줄입니다(다음 절).
- Suspense 훅은 요청 취소(signal)가 동작하지 않습니다(아래 절).

## prefetchQuery

프리페치는 화면이 데이터를 요구하기 전에 미리 요청해 캐시를 채워 두는 것입니다. 사용자가 화면에 도착했을 때 로딩 없이 바로 데이터를 보여 줍니다.

```tsx
function Link({ id }: { id: number }) {
  const queryClient = useQueryClient()
  const warm = () =>
    queryClient.prefetchQuery({
      queryKey: ['todo', id],
      queryFn: () => fetchTodo(id),
      staleTime: 60_000,
    })
  return <a href={`/todos/${id}`} onMouseEnter={warm}>열기</a>
}
```

- 프리페치의 결과는 캐시에만 저장되고 반환값이 없으며, 에러는 던지지 않고 삼킵니다. 실제 화면의 `useQuery`가 같은 키를 쓰면 캐시를 즉시 받습니다.
- `staleTime`을 주지 않으면 데이터가 이미 오래된 것이라 화면이 마운트될 때 다시 요청합니다. 프리페치한 값을 쓰려면 같은 `staleTime`을 둡니다. 옵션을 한곳에 두는 방법은 다음 절입니다.
- 시점은 세 가지입니다. 마우스를 올리거나 포커스를 줄 때 같은 이벤트 핸들러, 컴포넌트가 렌더링될 때, 라우터가 경로를 불러올 때입니다.
- Suspense 환경에서는 Suspense 경계 위에서 `usePrefetchQuery`나 `usePrefetchInfiniteQuery` 훅으로 미리 시작해 워터폴을 막습니다.
- 값이 이미 동기적으로 있으면 요청 대신 `setQueryData`로 캐시를 채웁니다.
- 이 편을 쓰는 시점의 최신 공식 문서는 `prefetchQuery`, `fetchQuery`, `ensureQueryData`를 deprecated로 표시하고, 같은 일을 `queryClient.query()`로 하라고 안내합니다. 프리페치는 `queryClient.query(options)`에 에러를 삼키는 `.catch`를 붙이고, `ensureQueryData`는 `staleTime: 'static'`을 준 `query`로 바꿉니다. 이 API들은 다음 메이저 버전에서 제거될 예정이며 지금은 계속 작동합니다. 새 코드를 쓸 때는 설치한 버전의 문서에서 어느 쪽인지 확인합니다.

## queryOptions와 키 팩토리

`queryOptions`는 `queryKey`와 `queryFn`을 비롯한 쿼리 옵션을 한곳에 정의하고 여러 곳에서 재사용하게 해 주는 헬퍼입니다. 런타임에서는 받은 객체를 그대로 돌려주고, 타입 추론과 타입 안전을 제공합니다.

```ts
import { queryOptions } from '@tanstack/react-query'

export const todoOptions = (id: number) =>
  queryOptions({
    queryKey: ['todos', id],
    queryFn: () => fetchTodo(id),
    staleTime: 60_000,
  })
```

```tsx
useQuery(todoOptions(5))
useSuspenseQuery(todoOptions(5))
queryClient.prefetchQuery(todoOptions(5))
queryClient.setQueryData(todoOptions(5).queryKey, newTodo)
```

- `useQuery`, `useSuspenseQuery`, `useQueries`, `prefetchQuery`, `setQueryData`가 같은 정의를 씁니다. 키와 함수가 어긋나는 일이 사라지고, `setQueryData`에는 키에서 추론된 타입이 적용됩니다.
- 컴포넌트에서 `select` 같은 옵션을 덧붙여도 타입이 유지되며, `data`의 타입은 `queryFn`이 아니라 `select`의 반환 타입이 됩니다.
- 무한 쿼리는 `infiniteQueryOptions`를 씁니다.

키는 문자열 리터럴을 여러 곳에 흩어 쓰면 오타와 불일치가 생기므로, 키 팩토리로 한곳에서 만듭니다. 팩토리는 커뮤니티 관례이고 라이브러리 API는 아닙니다.

```ts
export const todoKeys = {
  all: ['todos'] as const,
  lists: () => [...todoKeys.all, 'list'] as const,
  list: (filter: string) =>
    [...todoKeys.lists(), { filter }] as const,
  detail: (id: number) =>
    [...todoKeys.all, 'detail', id] as const,
}
```

- 계층이 `all`, `lists`, `list`, `detail`로 좁아지므로 `invalidateQueries({ queryKey: todoKeys.lists() })`처럼 필요한 범위만 무효화할 수 있습니다.
- `queryOptions`와 함께 쓰면 `todoOptions`가 `todoKeys.detail(id)`를 키로 쓰는 식으로, 키와 함수를 한 번에 관리합니다.

## 전역 에러 처리

v5에서는 `useQuery`의 `onError` 콜백이 제거됐으므로 전역 에러 처리는 `QueryCache`와 `MutationCache`의 콜백으로 합니다. 콜백은 쿼리가 실패할 때마다 한 번씩 호출됩니다.

```ts
const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      if (query.meta?.silent) return
      toast.error(error.message)
    },
  }),
})
```

- `QueryCache`의 `onError`는 `(error, query)`를 받습니다. 컴포넌트 수와 상관없이 쿼리 하나의 실패에 한 번 호출되므로 토스트가 중복되지 않습니다.
- 쿼리에 붙인 `meta` 객체로 쿼리별 동작을 바꿀 수 있습니다. 위 예는 `meta`로 알림을 건너뜁니다.
- 뮤테이션은 `MutationCache`에 같은 방식으로 콜백을 줍니다. 뮤테이션 콜백은 `useMutation`에도 그대로 있습니다.
- 세 층이 있습니다. 전역(`QueryCache`)은 공통 알림과 로깅, 컴포넌트 단위의 `throwOnError`는 Error Boundary 위임, 쿼리의 `error` 상태는 화면 안의 인라인 메시지에 씁니다.
- 에러 타입은 기본이 `Error`입니다. 다른 타입으로 던진다면 `Register` 인터페이스의 `defaultError`를 선언하거나 `unknown`으로 두어 사용하는 쪽에서 타입을 좁히게 합니다.

## SSR과 RSC의 hydration

서버에서 쿼리를 미리 가져와 HTML에 담고, 클라이언트가 그 캐시를 이어받는 흐름이 hydration입니다. 서버 렌더링 자체는 이 과정의 범위 밖이고, 여기서는 TanStack Query 쪽 규칙만 정리합니다.

1. 서버에서 쿼리를 프리페치해 캐시를 채운다.
2. `dehydrate(queryClient)`로 캐시를 직렬화 가능한 상태로 만든다.
3. 클라이언트에서 `HydrationBoundary`에 그 상태를 넘겨 캐시를 복원한다.

```tsx
const queryClient = getQueryClient()
await queryClient.prefetchQuery(todoOptions(5))

return (
  <HydrationBoundary state={dehydrate(queryClient)}>
    <TodoDetail id={5} />
  </HydrationBoundary>
)
```

- v5에서 `Hydrate` 컴포넌트는 `HydrationBoundary`로 이름이 바뀌었습니다.
- 서버에서는 요청마다 새 `QueryClient`를 만들어야 합니다. 파일 최상위에서 만들면 캐시가 모든 요청이 공유해 한 사용자의 데이터가 다른 사용자에게 전달됩니다. 브라우저에서는 하나를 재사용합니다.
- `staleTime`을 0보다 크게 둬야 합니다(가이드는 `60 * 1000`을 예로 듭니다). 0이면 hydration 직후 클라이언트가 곧바로 다시 요청합니다.
- 서버에서 `gcTime`의 기본값은 `Infinity`라서 요청이 끝나면 메모리가 정리됩니다. 값을 바꿨다면 직렬화 뒤에 `queryClient.clear()`를 호출하고, `gcTime: 0`은 hydration 오류를 일으킬 수 있으므로 피합니다.
- RSC 환경에서는 서버 컴포넌트에서 프리페치한 뒤 `HydrationBoundary`를 서버 컴포넌트에서 렌더링해 상태를 props처럼 넘깁니다. `HydrationBoundary` 자체는 클라이언트 컴포넌트입니다.
- v5.40.0 이상에서는 `dehydrate` 옵션으로 진행 중(pending)인 쿼리도 함께 직렬화할 수 있어서, 프리페치를 `await`하지 않고 시작만 해도 Suspense 경계가 끝나는 대로 스트리밍됩니다.
- `queryFn`에서 Server Action을 호출하지 않도록 권고합니다. Server Action은 순서대로 실행되어 병렬 요청이라는 이 라이브러리의 방식과 맞지 않습니다.
- 직렬화된 상태를 HTML에 심을 때는 `JSON.stringify`가 아니라 XSS를 막는 직렬화 도구(Serialize JavaScript, devalue)를 씁니다.

## 요청 취소

TanStack Query는 `queryFn`에 `AbortSignal`을 넘기고, 이 신호를 `fetch`에 연결하면 쿼리가 취소될 때 실제 요청도 중단됩니다.

```ts
useQuery({
  queryKey: ['todos'],
  queryFn: async ({ signal }) => {
    const res = await fetch('/todos', { signal })
    return res.json()
  },
})
```

- `signal`은 컨텍스트 객체에 항상 들어 있지만, 쿼리 함수가 이를 사용(소비)해야 취소가 일어납니다. 쓰지 않으면 요청은 끝까지 가고 결과만 캐시에 들어갑니다.
- 취소되는 때는 쿼리의 키가 바뀌어 이전 요청이 필요 없어졌을 때, 컴포넌트가 사라져 쿼리를 쓰는 곳이 없어졌을 때(신호를 소비한 경우), 그리고 `cancelQueries`를 호출했을 때입니다.
- 쓰는 컴포넌트가 사라져도 신호를 소비하지 않으면 요청이 취소되지 않고 결과가 캐시에 남아, 다시 마운트하면 빠르게 보입니다.
- axios는 v0.22.0부터 `signal` 옵션을 받습니다.
- `queryClient.cancelQueries({ queryKey })`로 직접 취소하며, `revert` 옵션(기본 `true`)은 쿼리를 이전 상태로 되돌리고 `silent`는 취소를 에러로 알리지 않습니다. 낙관적 업데이트 직전에 호출한 것이 이 함수입니다.
- Suspense 훅(`useSuspenseQuery` 등)에서는 취소가 작동하지 않습니다.

## 테스트용 QueryClient

테스트에서는 테스트마다 새 `QueryClient`를 만들어 캐시 공유로 인한 간섭을 막고, 재시도를 꺼서 에러 시나리오가 시간 초과로 끝나지 않게 합니다.

```tsx
function createWrapper() {
  const client = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  })
  return ({ children }: { children: React.ReactNode }) => (
    <QueryClientProvider client={client}>
      {children}
    </QueryClientProvider>
  )
}
```

```tsx
const { result } = renderHook(() => useTodos(), {
  wrapper: createWrapper(),
})
await waitFor(() => {
  expect(result.current.isSuccess).toBe(true)
})
expect(result.current.data).toEqual(['milk'])
```

- 기본 재시도는 지수 백오프로 3회라서, 실패 응답을 테스트하면 제한 시간 안에 끝나지 않습니다. `retry: false`가 필수입니다.
- 훅은 `QueryClientProvider` 안에서만 동작하므로 모든 테스트에 래퍼가 필요합니다. 컴포넌트 테스트에서는 `render`의 `wrapper` 옵션으로 같은 래퍼를 씁니다(35편).
- 비동기 결과는 `waitFor`로 기다린 뒤 확인합니다.
- Jest에서는 `gcTime`을 `Infinity`로 두면 "Jest did not exit one second after the test run completed" 경고를 막을 수 있습니다.

## Zustand와 역할 분담

TanStack Query는 서버 상태 도구이고 Zustand는 클라이언트 상태 도구라서 서로 대체하지 않고 함께 씁니다. 공식 문서도 TanStack Query가 클라이언트 상태 라이브러리를 완전히 대체하지는 않는다고 설명합니다.

| 종류 | 예 | 맡는 도구 |
|------|----|-----------|
| 서버 상태 | 목록, 상세, 사용자 정보 | TanStack Query |
| 클라이언트 전역 상태 | 테마, 사이드바 열림, 선택된 행, 다단계 폼 임시값 | Zustand |
| URL에 둘 상태 | 검색어, 필터, 페이지 번호 | 라우터(29편) |
| 지역 상태 | 입력값, 토글 | `useState` |

- 서버 데이터를 TanStack Query로 옮기면 남는 전역 상태는 테마나 UI 토글처럼 적습니다. 그래서 별도 상태 라이브러리가 필요 없는 앱도 많습니다. 응답을 스토어로 복사하지 않는 것이 핵심입니다. 복사본은 갱신되지 않아 두 곳이 어긋납니다.
- 클라이언트 상태가 서버 상태를 가리킬 때는 데이터가 아니라 식별자만 저장합니다. 선택된 항목은 스토어에 `selectedId`만 두고, 상세 데이터는 그 id를 키로 `useQuery`가 읽습니다.
- 필터·정렬 같은 클라이언트 값이 `queryKey`에 들어가면 값이 바뀔 때 자동으로 다시 요청됩니다. 값은 스토어나 URL에 있고, 쿼리는 그 값을 키로 구독하는 구조입니다.
- 서버 데이터를 가공한 파생 값은 `select`나 렌더링 중 계산으로 얻고 스토어에 넣지 않습니다.
- 채용 공고에서 TanStack Query와 Zustand 조합이 가장 자주 요구됩니다(22편).

## 핵심 정리

- `useMutation`은 `mutate`로 실행하고, 끝난 뒤 `invalidateQueries`로 다시 가져오거나 `setQueryData`로 캐시를 직접 고칩니다.
- 낙관적 업데이트는 UI 방식(`variables`로 임시 표시, 롤백 불필요)과 캐시 방식(`onMutate`에서 취소·저장·갱신·반환, `onError`에서 복원, `onSettled`에서 무효화)이 있습니다.
- `useInfiniteQuery`는 `initialPageParam`과 `getNextPageParam`이 필수이고 `data.pages`로 누적하며, 쪽 교체형 페이지네이션은 `placeholderData: keepPreviousData`로 깜빡임을 막습니다.
- `useSuspenseQuery`는 `data`가 항상 정의되고 로딩과 에러를 Suspense와 Error Boundary에 맡기며, 재시도 시 `QueryErrorResetBoundary`로 에러를 초기화합니다.
- `queryOptions`와 키 팩토리로 키와 함수를 한곳에 두고, 프리페치는 같은 옵션과 `staleTime`으로 합니다. 최신 문서는 `prefetchQuery` 대신 `queryClient.query()`를 안내합니다.
- 전역 에러는 `QueryCache`의 `onError`, 요청 취소는 `signal`을 `fetch`에 연결, 테스트는 테스트마다 새 `QueryClient`와 `retry: false`, SSR은 요청마다 새 클라이언트와 0보다 큰 `staleTime`입니다.
- 서버 상태는 TanStack Query, 클라이언트 전역 상태는 Zustand가 맡고 서버 데이터를 스토어로 복사하지 않습니다.

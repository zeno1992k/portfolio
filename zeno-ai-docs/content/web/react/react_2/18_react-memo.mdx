## React.memo

`memo`는 컴포넌트를 감싸 "부모가 다시 렌더링되어도 props가 같으면 다시 렌더링하지 않는" 컴포넌트를 돌려주는 함수입니다.

```jsx
import { memo } from 'react'

const Profile = memo(function Profile({ name, age }) {
  return <p>{name} ({age})</p>
})
```

- 시그니처는 `memo(Component, arePropsEqual?)`입니다. 두 번째 인수는 선택입니다(Custom Comparison 절).
- 반환값은 원래 컴포넌트와 똑같이 동작하는 새 컴포넌트입니다. 달라지는 점은 props가 이전과 같으면 재렌더링을 건너뛰는 것뿐입니다.
- 렌더링을 건너뛰는 대상은 "부모의 재렌더링 때문에 일어나는 재렌더링"입니다. 컴포넌트 자신의 state와 구독 중인 Context는 막지 못합니다(아래 "Memoized Component").
- 결과가 바뀌지 않는 최적화이고, 코드의 동작이 `memo`에 의존해서는 안 됩니다. 공식 문서도 `memo`는 성능 최적화로만 의존하라고 합니다. `memo`가 없으면 동작하지 않는 코드는 근본 원인부터 고쳐야 합니다.

기본 상황은 다음과 같습니다.

```jsx
function Parent() {
  const [count, setCount] = useState(0)
  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>
      <Profile name="Kim" age={20} />
    </>
  )
}
// memo 없음: 버튼을 누를 때마다 Profile도 재렌더링
// memo 있음: name과 age가 같으므로 Profile은 건너뜀
```

## Props 비교

`memo`는 부모가 재렌더링될 때마다 이전 props와 새 props를 비교합니다. 모두 같으면 이전 결과를 그대로 쓰고, 하나라도 다르면 다시 렌더링합니다.

- 비교는 prop 하나씩 `Object.is`로 합니다.
- `children`도 하나의 prop입니다.
- 함수형 컴포넌트가 받는 props 객체 전체를 비교하는 것이 아니라 prop 하나하나를 비교합니다. 부모가 매번 새 props 객체를 만들어도 안쪽 값이 같으면 같은 것으로 취급합니다.
- 비교에 걸리는 시간도 비용입니다. props가 거의 항상 바뀌는 컴포넌트에 `memo`를 쓰면 비교만 늘고 이득이 없습니다.

## 얕은 비교

얕은 비교(shallow equality)는 값의 내용이 아니라 참조가 같은지 보는 비교입니다. 원시 값은 값이 같으면 같고, 객체·배열·함수는 같은 참조일 때만 같습니다.

```js
Object.is(3, 3)   // true
Object.is('a', 'a') // true
Object.is({}, {}) // false (다른 객체)
const a = [1]
Object.is(a, a)   // true (같은 참조)
```

| prop 값 | 부모가 재렌더링될 때 | memo 비교 결과 |
|---------|----------------------|----------------|
| 숫자, 문자열, 불리언 | 값이 같으면 같음 | 같음 |
| 인라인 객체·배열 리터럴 | 매번 새로 만들어짐 | 다름 |
| 인라인 화살표 함수 | 매번 새로 만들어짐 | 다름 |
| JSX 요소(`children`) | 매번 새로 만들어짐 | 다름 |
| state에서 받은 객체 | `set` 하지 않으면 같은 참조 | 같음 |

- 내용이 같아도 참조가 다르면 다른 값입니다. `{ a: 1 }`을 매번 새로 만들어 넘기면 `memo`는 항상 "바뀜"으로 봅니다.
- 깊은 비교는 하지 않습니다. 객체 안의 값이 바뀌었는지를 보지 않습니다. 그래서 state는 객체를 직접 고치지 않고 새 객체로 교체해야 `memo`가 변경을 알아챕니다.

**흔한 실수:** 객체를 직접 고치고 같은 참조를 다시 넘기는 것입니다. 참조가 같으니 `memo`가 건너뛰어서 화면이 갱신되지 않습니다.

## Custom Comparison

두 번째 인수로 비교 함수 `arePropsEqual(oldProps, newProps)`를 주면 기본 비교를 대체합니다. `true`를 돌려주면 "같음"이라는 뜻이라 재렌더링을 건너뜁니다.

```jsx
const Chart = memo(function Chart({ dataPoints }) {
  // ...
}, arePropsEqual)

function arePropsEqual(oldProps, newProps) {
  return (
    oldProps.dataPoints.length ===
      newProps.dataPoints.length &&
    oldProps.dataPoints.every((p, i) => {
      const q = newProps.dataPoints[i]
      return p.x === q.x && p.y === q.y
    })
  )
}
```

- 비교 함수는 모든 prop을 비교해야 합니다. 함수 prop도 빼면 안 됩니다. 함수는 부모의 props와 state를 클로저로 붙잡고 있으므로 비교에서 빼면 오래된 값을 쓰는 버그가 생깁니다.
- 깊은 비교(deep equality)는 피합니다. 데이터 구조가 커지면 매우 느려지고 앱이 멈출 수 있습니다.
- 비교 함수가 렌더링 자체보다 빠르다는 것이 확실할 때만 씁니다. 배열의 길이와 각 원소를 비교하는 위 예처럼 얕고 값싼 비교가 목표입니다.
- 대부분의 경우 기본 비교로 충분합니다. 비교 함수가 필요해 보이면 먼저 props의 모양을 단순하게 바꿀 수 있는지 봅니다.
- 이득은 프로덕션 모드에서 프로파일러로 재서 확인합니다(자세히는 20편).

## Memoized Component

`memo`로 감싼 컴포넌트를 Memoized Component라고 부릅니다.

`memo`가 막아 주는 것과 막지 못하는 것은 다음과 같습니다.

| 상황 | 재렌더링 |
|------|----------|
| 부모가 재렌더링되고 props가 모두 같음 | 건너뜀 |
| 부모가 재렌더링되고 props 하나라도 다름 | 렌더링 |
| 컴포넌트 자신의 state가 바뀜 | 렌더링 |
| 컴포넌트가 읽는 Context 값이 바뀜 | 렌더링 |

- `memo`는 부모에서 오는 props 변화에만 관여합니다. 자신의 state가 바뀌면 재렌더링되고, 읽고 있는 Context 값이 바뀌어도 재렌더링됩니다(자세히는 1편).
- 건너뛰는 단위는 그 컴포넌트와 그 아래 하위 트리입니다. 비용이 큰 서브트리의 뿌리에 쓸 때 이득이 큽니다.
- 한 컴포넌트가 아니라 느린 구간 전체의 재렌더링을 줄이는 방법이 더 있습니다. state를 필요한 곳으로 내려 보내고, `children`으로 JSX를 받게 하면 `memo` 없이도 부모의 재렌더링이 자식에게 번지지 않습니다.

```jsx
// state를 쓰는 부분만 따로 분리하면 Slow는 영향받지 않음
function Page() {
  return (
    <Counter>
      <Slow />
    </Counter>
  )
}
```

- `Counter`가 state로 재렌더링돼도 `children`으로 받은 `Slow` 요소는 `Page`가 만든 같은 요소이므로 React가 다시 렌더링하지 않습니다.
- 마운트될 때는 `memo`가 아무 영향이 없습니다. 첫 렌더링은 항상 일어납니다.

## Object Props

객체나 배열을 prop으로 넘길 때, 부모가 렌더링될 때마다 새로 만들면 `memo`가 무력해집니다.

```jsx
function Parent({ name, age }) {
  // ❌ 렌더링마다 새 객체 → Profile의 memo가 항상 다름으로 판정
  return <Profile person={{ name, age }} />
}
```

해결 방법은 두 가지입니다.

```jsx
// 1) 값을 하나씩 prop으로 넘김 (가장 단순)
return <Profile name={name} age={age} />

// 2) useMemo로 참조를 유지
const person = useMemo(() => ({ name, age }), [name, age])
return <Profile person={person} />
```

- 객체가 꼭 필요한 이유가 없으면 원시 값으로 풀어 넘기는 것이 가장 단순합니다. 원시 값은 값이 같으면 같은 prop이 됩니다.
- 객체를 유지해야 하면 `useMemo`로 참조를 고정합니다(자세히는 19편).
- 객체가 부모의 state나 props에서 그대로 온 것이면 참조가 이미 안정적입니다. 렌더링 중에 새로 만든 파생 객체만 문제입니다.
- 컴포넌트 밖에서 만든 상수 객체(`const OPTIONS = { ... }`)도 참조가 고정됩니다.

## Function Props

함수 prop도 같습니다. 컴포넌트 본문에서 만든 함수는 렌더링마다 새로 만들어집니다.

```jsx
function Parent() {
  // ❌ 렌더링마다 새 함수
  return <Row onSelect={() => select()} />
}
```

해결 방법은 다음과 같습니다.

```jsx
// 1) 컴포넌트 밖에서 선언 (부모의 값을 쓰지 않을 때)
const handleSelect = () => { /* ... */ }
return <Row onSelect={handleSelect} />

// 2) useCallback으로 참조를 유지
const handle = useCallback(() => select(id), [id])
return <Row onSelect={handle} />
```

- 부모의 props나 state를 쓰지 않는 함수는 컴포넌트 밖으로 꺼내면 참조가 고정됩니다.
- 쓰는 값이 있으면 `useCallback`으로 감쌉니다. 의존성이 바뀔 때만 새 함수가 만들어집니다(자세히는 19편).
- `memo` 자식에게 넘기는 함수 중 하나만 불안정해도 그 자식은 매번 재렌더링됩니다. 모든 prop이 안정적이어야 효과가 있습니다.
- 목록에서는 항목마다 `onClick={() => remove(item.id)}`처럼 만들게 되므로 `memo`가 깨집니다. 항목 컴포넌트에 `id`와 함수를 넘기고 항목 안에서 `onClick`을 만들면 같은 함수를 공유할 수 있습니다.

## Compiler 환경에서 역할

React Compiler는 빌드 때 컴포넌트와 Hook을 분석해 자동으로 메모이제이션을 적용하는 도구입니다. 2025-10-07에 v1.0이 안정판으로 나왔습니다.

공식 문서의 안내는 다음과 같습니다.

- Compiler를 켜면 `memo`는 보통 필요 없습니다. 컴파일러가 모든 컴포넌트에 같은 효과의 최적화를 자동으로 넣습니다.
- 새 코드는 컴파일러에 맡기고, 정밀한 제어가 필요할 때만 `useMemo`·`useCallback`을 탈출구로 씁니다.
- 기존 코드의 메모이제이션은 그대로 두는 것이 안전합니다. 지우면 컴파일 결과가 달라질 수 있어서 지울 때는 꼼꼼히 테스트하라고 안내합니다.
- 인라인 화살표 함수처럼 `memo`를 깨던 코드도 컴파일러가 고쳐 줍니다.
- 컴파일러는 React 규칙(순수한 렌더링, state 불변성)을 지키는 코드를 전제로 합니다.

프로젝트에 따른 판단은 다음과 같습니다.

| 프로젝트 | `memo` 판단 |
|----------|-------------|
| Compiler 사용 | 새로 추가하지 않음. 기존 것은 둠 |
| Compiler 미사용 | 측정 후 필요한 곳에만 추가 |

- 이 과목의 Compiler 자체(동작 원리, 설정)는 범위 밖입니다.

## 남용 방지

`memo`는 비교 비용이 있고 코드를 복잡하게 하므로 측정으로 이득이 확인된 곳에만 씁니다. 공식 문서가 꼽는 쓸 만한 경우는 다음과 같습니다.

- 갱신이 자주 일어나고 재렌더링이 느린 컴포넌트(예: 그림 편집기처럼 세밀한 상호작용이 많은 화면)

쓰지 않아도 되는 경우는 다음과 같습니다.

- props가 거의 매번 달라지는 컴포넌트. 비교만 하고 매번 렌더링합니다.
- 재렌더링해도 눈에 띄는 지연이 없는 컴포넌트.
- `children`으로 JSX를 받는 컴포넌트. 부모가 매번 새 요소를 만들어 넘기므로 비교가 매번 실패합니다.

`memo`를 쓰기 전에 다음을 먼저 확인합니다.

1. `children`으로 JSX를 받게 해서 느린 부분이 부모의 재렌더링에서 벗어나게 한다.
2. state를 필요한 곳에 가깝게 둔다. 불필요하게 위로 올리지 않는다.
3. 렌더링을 순수하게 유지한다.
4. state를 바꾸는 불필요한 Effect를 없앤다.
5. Effect의 불필요한 의존성을 제거한다.

- 한 곳에서 `memo`로 막아도 부모가 객체·함수 prop을 새로 만들면 효과가 없습니다. `memo`와 참조 안정화는 항상 같이 점검합니다.
- 측정은 프로덕션 모드에서 브라우저 프로파일러로 합니다. 개발 모드의 수치로 판단하지 않습니다(자세히는 20편).

**흔한 실수:** 모든 컴포넌트에 `memo`를 일괄 적용하는 것입니다. 비교 비용만 늘고, 인라인 객체·함수 props 때문에 대부분 효과가 없습니다.

## 핵심 정리

- `memo`는 부모가 재렌더링될 때 props가 이전과 같으면 그 컴포넌트의 재렌더링을 건너뜁니다. 자신의 state와 Context 변경은 막지 못합니다.
- 비교는 prop 하나씩 `Object.is`로 하는 얕은 비교이며, 인라인 객체·배열·함수·JSX는 매번 새 참조라서 비교에 실패합니다.
- `arePropsEqual`은 모든 prop(함수 포함)을 비교해야 하고, 깊은 비교는 피합니다.
- 객체 props는 원시 값으로 풀거나 `useMemo`로, 함수 props는 컴포넌트 밖 선언이나 `useCallback`으로 참조를 고정합니다.
- React Compiler를 쓰면 `memo`는 보통 필요 없으며 기존 코드는 그대로 둡니다.
- `memo`는 측정으로 이득이 확인된 곳에만 씁니다.

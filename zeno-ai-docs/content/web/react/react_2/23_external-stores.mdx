## External Store

외부 스토어(external store)는 React 컴포넌트 바깥에 있는 변경 가능한 데이터 저장소입니다. 컴포넌트는 스토어를 구독해서 값을 읽고, 값이 바뀌면 다시 렌더링됩니다. 스토어는 컴포넌트 트리와 독립적으로 존재해서 컴포넌트가 아닌 코드에서도 읽고 쓸 수 있습니다.

스토어가 갖춰야 할 최소 구성은 세 가지입니다.

| 요소 | 역할 |
|------|------|
| 현재 값(스냅샷) | 지금 상태를 돌려주는 읽기 |
| 변경 | 값을 바꾸고 구독자에게 알림 |
| 구독 | 변경 알림을 받을 콜백을 등록하고 해제하는 방법 |

```js
let state = { count: 0 }
const listeners = new Set()

export const store = {
  getState: () => state,
  setState(next) {
    state = { ...state, ...next }     // 새 객체로 교체
    listeners.forEach((l) => l())     // 구독자에게 알림
  },
  subscribe(l) {
    listeners.add(l)
    return () => listeners.delete(l)  // 구독 해제 함수
  },
}
```

- 위 코드가 Redux, Zustand 같은 라이브러리의 공통 뼈대입니다. 라이브러리는 여기에 갱신 규칙, DevTools, 미들웨어, React 연결을 더합니다.
- 상태를 불변으로 교체하는 이유는 "바뀌었는지"를 참조 비교 한 번으로 알기 위해서입니다.
- 외부 스토어를 쓸지는 먼저 22편의 기준으로 판단합니다. 서버 데이터와 URL, 폼 값은 이 도구의 대상이 아닙니다.

## Redux 계열

Redux는 예측 가능하고 유지보수하기 쉬운 전역 상태 관리를 위한 라이브러리입니다. 공식 문서가 정하는 세 원칙은 다음과 같습니다.

| 원칙 | 내용 |
|------|------|
| 단일 진실 공급원 | 앱의 전역 상태를 하나의 스토어 안의 객체 트리에 둠 |
| 상태는 읽기 전용 | 상태를 바꾸는 유일한 방법은 일어난 일을 설명하는 객체(action)를 보내는 것 |
| 순수 함수로 변경 | 이전 상태와 action을 받아 다음 상태를 돌려주는 순수 reducer로 변환을 정의 |

```js
store.dispatch({ type: 'todos/completed', index: 1 })
// reducer가 (state, action) => nextState 로 계산
```

- 모든 변경이 action이라는 기록 가능한 단위로 흐르므로 로그, 재생, 시간 여행 디버깅이 가능합니다.
- 공식 문서는 Redux Toolkit을 Redux 로직을 작성하는 공식 권장 방식으로 둡니다. `configureStore`, `createSlice` 등으로 보일러플레이트를 줄입니다(자세히는 25편).
- React에서는 `Provider`로 스토어를 내려 주고 `useSelector`, `useDispatch`로 읽고 보냅니다.

## Zustand 계열

Zustand는 훅 중심으로 설계한 작은 스토어 라이브러리입니다. 스토어 하나를 `create`로 만들고 그 결과를 훅처럼 씁니다. 공식 문서는 한 개의 훅으로 스토어를 만드는 최소 API, 동시 렌더링에서 안전함, React Native와 순수 JavaScript에서도 쓸 수 있음, 선택적인 devtools·persist 미들웨어, 타입 추론, 작은 번들 크기를 특징으로 소개합니다.

```js
const useCount = create((set) => ({
  count: 0,
  inc: () => set((s) => ({ count: s.count + 1 })),
}))
// 컴포넌트: const count = useCount((s) => s.count)
```

- Provider 없이 어디서든 훅을 부릅니다.
- 상태는 불변으로 다루며, Redux와 같은 방식이지만 action·reducer 의식 없이 함수로 갱신합니다.
- 렌더링 최적화는 selector로 직접 합니다(아래 "Selector").
- 사용법 전체는 24편에서 다룹니다.

## Jotai 계열

Jotai는 atom이라는 작은 상태 단위를 조합해 쓰는 라이브러리입니다. 공식 문서는 "원시적이고 유연한 상태 관리"라고 소개하고, 아래에서 위로(bottom-up) 쌓는 방식이라고 설명합니다. 코어 API는 `atom`, `useAtom`, `Store`, `Provider` 정도입니다.

```jsx
const countAtom = atom(0)
const doubleAtom = atom((get) => get(countAtom) * 2) // 파생

function Counter() {
  const [count, setCount] = useAtom(countAtom)
  // doubleAtom을 읽으면 countAtom이 바뀔 때만 갱신
}
```

- atom 하나가 상태 하나입니다. 단순한 경우 `useState`를 대체하는 모양으로 쓰고, 다른 atom을 읽는 파생 atom으로 확장합니다.
- 컴포넌트는 자신이 읽는 atom이 바뀔 때만 다시 렌더링됩니다. atom 사이의 의존 관계가 최적화 단위입니다.
- 스토어를 하나로 모으지 않고, 상태를 잘게 나눠 필요한 곳에서 조합하는 철학입니다(자세히는 25편).
- `jotai/utils`에 `atomWithStorage` 같은 도우미가 있고, React Query·XState·Zustand 같은 라이브러리용 공식 확장이 있습니다.

## Selector

selector는 스토어의 전체 상태에서 컴포넌트가 필요한 조각만 골라내는 함수입니다. 외부 스토어에서 재렌더링을 줄이는 핵심 장치입니다. 선택한 값이 바뀔 때만 컴포넌트가 다시 렌더링됩니다.

```js
const count = useStore((s) => s.count)  // count만 구독
const name = useStore((s) => s.name)    // 별도로 구독
```

비교 방식은 도구마다 다릅니다.

| 도구 | 선택 결과를 비교하는 방식 |
|------|---------------------------|
| Redux `useSelector` | 기본은 엄격한 `===` 비교 |
| Zustand | `Object.is` 비교 |
| Jotai | atom 의존 관계로 결정(selector 함수를 쓰지 않음) |

- 비교가 참조 기준이므로 selector가 호출마다 새 객체나 배열을 만들면 매번 "바뀐 것"으로 판정되어 항상 다시 렌더링됩니다.

```js
// ❌ 매번 새 객체
useSelector((s) => ({ a: s.a, b: s.b }))
// ✅ 값을 각각 선택
const a = useSelector((s) => s.a)
const b = useSelector((s) => s.b)
```

- 여러 값이 필요하면 값을 하나씩 선택하거나, Redux는 `shallowEqual`, Zustand는 `useShallow`로 얕은 비교를 쓰거나, 메모이제이션된 selector(Redux의 `createSelector`)로 파생 값을 만듭니다.
- Redux는 selector가 같은 입력에 다른 참조를 돌려주거나 전체 상태(`state => state`)를 돌려주면 개발 모드에서 경고합니다.
- 파생 값을 계산하는 selector는 스토어에 저장하지 않고 읽을 때 계산합니다. 계산 가능한 값을 상태로 두지 않는 원칙과 같습니다.

## Subscription

구독(subscription)은 스토어가 바뀔 때 알림을 받도록 콜백을 등록하는 관계입니다. 알림이 오면 컴포넌트는 selector를 다시 실행해 이전 결과와 비교하고, 달라졌을 때만 렌더링합니다.

```js
const unsubscribe = store.subscribe(() => {
  console.log(store.getState().count)
})
unsubscribe() // 해제하지 않으면 메모리와 불필요한 호출이 남음
```

- 스토어는 값이 바뀔 때마다 모든 구독자를 호출하고, 선택한 조각이 같은지는 구독하는 쪽이 판단합니다. 구독자가 많으면 비교도 그만큼 늘어납니다.
- 컴포넌트가 사라지면 구독을 해제해야 합니다. React 연결 훅은 이 해제를 대신합니다.
- 구독은 React 밖에서도 가능합니다. 상태 변화에 따라 로컬 저장소에 쓰거나 로그를 남기는 일을 컴포넌트 없이 할 수 있습니다.
- 구독 해제 함수를 반환하는 형태는 `useSyncExternalStore`가 요구하는 `subscribe`의 형태와 같습니다(아래 절).

## Normalized State

정규화 상태(normalized state)는 중첩된 데이터를 종류별 "테이블"로 평평하게 펼치고, 관계는 ID로만 가리키는 구조입니다. 공식 Redux 문서가 권장하는 구조는 항목을 ID로 찾는 객체와, 순서를 나타내는 ID 배열입니다.

```js
const state = {
  posts: {
    byId: { p1: { id: 'p1', author: 'u1' } },
    allIds: ['p1'],
  },
  users: {
    byId: { u1: { id: 'u1', name: 'Kim' } },
    allIds: ['u1'],
  },
}
// 작성자 이름: users.byId[post.author].name
```

| 이점 | 이유 |
|------|------|
| 중복 제거 | 같은 사용자가 여러 곳에 있어도 한 곳에서만 수정 |
| 갱신 단순화 | 깊은 중첩 없이 ID로 바로 찾음 |
| 렌더링 성능 | 중첩된 데이터를 바꿔도 관계없는 UI가 다시 렌더링되지 않음 |

- 일대다 관계는 부모 항목에 자식 ID 배열을 둡니다. 다대다는 관계를 담는 별도의 표를 둡니다.
- Redux Toolkit의 `createEntityAdapter`가 `ids`와 `entities` 형태의 정규화와 reducer·selector 생성을 자동화합니다.
- 서버 데이터는 TanStack Query 같은 서버 상태 라이브러리가 캐시를 관리하므로 직접 정규화할 필요가 줄어듭니다. 정규화는 클라이언트가 소유한 관계형 데이터에서 주로 쓰입니다.
- React 공식 문서의 상태 구조 원칙(중복을 피하고 중첩을 평평하게)도 같은 이야기입니다. 이 구조는 ID로 찾는 코드를 요구하므로 읽는 쪽이 조금 늘어납니다.

## State Machine

상태 머신(state machine)은 가능한 상태와 상태 사이의 전이를 명시하고, 허용된 전이만 일어나게 하는 모델입니다. 불가능한 상태 조합이 생기지 않게 막아 줍니다(자세히는 02편).

```js
const transitions = {
  idle: { FETCH: 'loading' },
  loading: { RESOLVE: 'success', REJECT: 'error' },
  error: { RETRY: 'loading' },
  success: {},
}
const next = (s, e) => transitions[s][e] ?? s // 허용 안 되면 그대로
```

- `isLoading`, `isError`, `isSuccess`를 각각 불리언으로 두는 대신 `status` 하나로 두면 동시에 둘이 참인 모순이 사라집니다.
- 전이 표를 reducer 안에서 쓰면 외부 라이브러리 없이도 상태 머신이 됩니다.
- XState는 상태 머신, 상태 차트, 액터 모델을 구현한 라이브러리이고, `@xstate/react` 같은 프레임워크 연결 패키지가 있습니다. 복잡한 워크플로(결제 흐름, 다단계 위저드, 연결 상태 관리)를 시각화하고 검증해야 할 때 씁니다.
- 대부분의 화면은 `status` 필드와 reducer로 충분합니다. 상태 머신은 전역 스토어를 대체하는 것이 아니라 상태 변화 규칙을 표현하는 방법입니다.

## Context와 비교

Context도 컴포넌트 밖에서 값을 전달하지만 외부 스토어와는 다릅니다.

| 항목 | Context | 외부 스토어 |
|------|---------|-------------|
| 값의 출처 | `useState`·`useReducer`가 만든 React 상태 | 스토어 객체 |
| 일부만 구독 | 불가능. 값이 바뀌면 읽는 모든 곳이 렌더링 | selector로 가능 |
| React 밖 접근 | 불가능 | 가능 |
| Provider | 필요 | Redux는 필요, Zustand는 불필요 |
| 적합한 값 | 자주 바뀌지 않는 넓은 값(테마, 로케일) | 자주 바뀌거나 여러 곳이 읽고 쓰는 값 |
| 추가 의존성 | 없음 | 있음 |

- Context 값이 바뀌면 그 Context를 읽는 모든 컴포넌트가 다시 렌더링됩니다(자세히는 01편).
- Zustand 공식 비교 문서는 Zustand가 Redux와 달리 Context Provider를 요구하지 않는다고 설명합니다.
- 외부 스토어는 "Context의 재렌더링 문제를 풀려고 쓰는 것"이 아니라 상태가 앱 전역에서 자주 바뀌는 문제에 쓰는 도구입니다. 작은 앱은 Context와 Reducer로 충분합니다.

## useSyncExternalStore

`useSyncExternalStore`는 React가 외부 스토어를 구독하게 해 주는 공식 Hook입니다(자세히는 05편).

```js
const snap = useSyncExternalStore(subscribe, getSnapshot)
```

| 인자 | 역할 |
|------|------|
| `subscribe` | 콜백을 등록하고 해제 함수를 반환 |
| `getSnapshot` | 스토어의 현재 값을 반환 |
| `getServerSnapshot` | 서버 렌더링·hydration에 쓸 초기 값(선택) |

```js
const count = useSyncExternalStore(
  store.subscribe,
  () => store.getState().count,
)
```

- 직접 `useEffect`로 구독하면 렌더링 중간에 스토어가 바뀌어 같은 화면의 컴포넌트들이 서로 다른 값을 보여 줄 수 있습니다(tearing). 이 Hook은 그런 불일치가 없도록 React가 스냅샷을 일관되게 읽습니다.
- `getSnapshot`은 스토어가 바뀌지 않았으면 같은 값을 돌려줘야 합니다. 호출마다 새 객체를 만들면 안 됩니다.
- `subscribe`는 컴포넌트 밖에 두거나 `useCallback`으로 고정합니다. 매 렌더링마다 새 함수면 재구독합니다.
- 외부 스토어의 변경은 Transition으로 표시할 수 없어서 값에 따라 중단(suspend)하면 Suspense fallback이 나타납니다.
- 라이브러리가 이 Hook(또는 같은 원리)을 써서 구독을 처리하므로, 앱 코드에서 직접 부를 일은 브라우저 API 구독(예: 온라인 상태) 정도입니다. 공식 문서도 React 상태는 `useState`·`useReducer`를 쓰라고 권합니다.

## Flux·Atomic·Proxy 모델 구분

외부 스토어 라이브러리는 상태를 표현하는 모델로 구분하면 선택이 쉬워집니다.

| 모델 | 대표 | 상태 표현 | 갱신 | 렌더링 최적화 |
|------|------|-----------|------|---------------|
| Flux | Redux | 불변 객체 트리 하나 | action을 보내 reducer가 계산 | selector로 직접 |
| 단일 스토어 | Zustand | 불변 객체 하나 | `set` 함수로 직접 | selector로 직접 |
| Atomic | Jotai | 작은 atom 여러 개 | atom을 쓰는 함수 | atom 의존 관계로 자동 |
| Proxy | Valtio | 변경 가능한 proxy 객체 | 직접 대입(`store.count++`) | 읽은 속성 추적으로 자동 |

- Flux는 단방향 데이터 흐름과 action으로 변경을 기술하는 아키텍처입니다. Redux는 Flux에서 영감을 받았지만 dispatcher가 없고, 순수 함수 reducer와 불변성을 강제한다는 점이 다릅니다.
- Zustand 공식 비교 문서는 Valtio를 변경 가능(mutable) 상태 모델로 설명하고, Zustand는 불변 상태와 selector를 통한 수동 최적화를 쓴다고 비교합니다.
- Valtio는 `proxy`로 감싼 객체를 직접 바꾸면 변화가 전파되고, `useSnapshot`이 읽은 속성이 바뀔 때만 다시 렌더링합니다.
- 모델 선택은 "수동 최적화를 감수하고 예측 가능성을 얻을지", "자동 최적화를 얻고 모델을 바꿀지"의 문제입니다. 모델이 달라도 React와의 연결은 같은 구독 원리입니다.

## 선택 기준표

| 상황 | 알맞은 도구 |
|------|-------------|
| 전역 상태가 적고 거의 바뀌지 않음 | Context(+ Reducer) |
| 중소 규모 클라이언트 전역 상태, 보일러플레이트 최소화 | Zustand |
| 대규모 팀, 엄격한 흐름과 DevTools 추적, 비동기 규약 필요 | Redux Toolkit |
| 서로 의존하는 작은 상태가 많고 파생 값이 많음 | Jotai |
| 변경 가능한 코드 스타일을 선호 | Valtio |
| 복잡한 전이 규칙(결제·위저드) | Reducer 기반 상태 머신, XState |
| 서버 데이터 | TanStack Query 등 서버 상태 라이브러리 |

- 기존 코드베이스가 쓰는 도구를 따르는 것이 새 도구의 이점보다 큽니다.
- 한 앱에서 둘 이상을 쓸 수 있습니다. 예를 들어 서버 상태는 TanStack Query, UI 전역 상태는 Zustand입니다(자세히는 22편).
- 이 과목의 채용 공고 조사에서는 Zustand가 반복해서 요구되었습니다. Zustand는 24편, Redux Toolkit과 Jotai는 25편에서 다룹니다.

## Recoil 개발 중단

Recoil은 Meta가 만든 atom 기반 상태 라이브러리였습니다. GitHub의 `facebookexperimental/Recoil` 저장소는 2025년 1월 1일에 소유자에 의해 보관(archived)되어 읽기 전용이 되었습니다. 더 이상 개발이 이어지지 않고 PR도 병합되지 않습니다.

- Recoil은 Jotai처럼 atom을 쓰지만 문자열 키로 atom을 식별하고 Provider로 감싸야 했습니다. 이 차이는 Zustand 공식 비교 문서에도 나옵니다.
- 신규 프로젝트에는 쓰지 않습니다. 기존 프로젝트에서 만나면 같은 atom 모델인 Jotai로 옮기는 것이 개념상 가장 가깝습니다.
- 라이브러리를 고를 때는 저장소의 보관 여부, 최근 릴리스, React 최신 버전 지원을 확인합니다.

## 핵심 정리

- 외부 스토어는 값, 변경, 구독을 갖춘 React 바깥의 저장소이고, 컴포넌트는 구독해서 읽습니다.
- Redux는 action과 순수 reducer의 단방향 흐름, Zustand는 훅 하나로 만드는 단일 스토어, Jotai는 atom 조합, Valtio는 proxy 직접 변경 모델입니다.
- selector는 필요한 조각만 구독해 재렌더링을 줄이며, 참조 비교이므로 새 객체를 돌려주면 매번 렌더링됩니다.
- 정규화 상태는 데이터를 ID 기준의 평평한 표로 두어 중복과 중첩을 없애고, 상태 머신은 허용된 전이만 정의해 모순된 상태를 막습니다.
- Context는 일부 구독이 불가능해 자주 바뀌는 값에 부적합하고, 외부 스토어는 selector로 이를 해결합니다.
- 라이브러리는 `useSyncExternalStore`로 일관된 구독을 처리하며, Recoil은 2025-01-01 저장소 보관으로 신규 사용을 피합니다.

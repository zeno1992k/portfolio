## React DevTools Profiler

React Developer Tools는 브라우저 확장 프로그램으로 Components 패널과 Profiler 패널을 제공합니다. Components 패널은 컴포넌트 계층과 props·state를 보여 주고, Profiler 패널은 렌더링 성능을 기록합니다. Chrome, Firefox, Edge용 확장이 있고, Safari 같은 브라우저는 `react-devtools` npm 패키지를 씁니다.

기록하는 순서는 다음과 같습니다.

1. Profiler 패널에서 기록 버튼을 누른다.
2. 느린 동작(클릭, 입력, 탭 전환)을 한다.
3. 정지 버튼을 누른다. 렌더링이 한 번이라도 있었으면 결과가 표시된다.

| 화면 요소 | 보여 주는 것 |
|-----------|--------------|
| Commit 선택 막대 | 기록 중 모든 커밋. 막대가 높고 노란색일수록 느림 |
| Flamegraph | 선택한 커밋에서 컴포넌트별 렌더링 시간 |
| Ranked | 선택한 커밋에서 오래 걸린 컴포넌트를 위에서부터 정렬 |
| 컴포넌트 선택 | 그 컴포넌트가 왜 렌더링됐는지 |

- 기록 길이가 길면 지속 시간 기준을 정해 빠른 커밋을 숨겨서 느린 커밋만 봅니다.
- 개발 모드의 수치는 프로덕션과 달라서 절대 수치로 믿으면 안 됩니다. 프로덕션 환경에서 프로파일링하려면 `react-dom/profiling` 번들을 씁니다.
- 프로파일러는 React 렌더링을 보는 도구입니다. 렌더링 밖의 병목은 Chrome의 Performance 패널로 봅니다(CPU 병목 절).

## Profiler Component

`Profiler`는 트리의 일부분이 렌더링될 때마다 측정값을 코드로 받는 컴포넌트입니다. 측정 결과를 로그나 수집 서비스로 보낼 때 씁니다.

```jsx
import { Profiler } from 'react'

function onRender(id, phase, actualDuration) {
  console.log(id, phase, actualDuration)
}

<Profiler id="Sidebar" onRender={onRender}>
  <Sidebar />
</Profiler>
```

| prop | 설명 |
|------|------|
| `id` | 측정 대상 UI를 구분하는 문자열 |
| `onRender` | 트리 안 컴포넌트가 갱신될 때마다 React가 호출하는 콜백 |

`onRender`의 인수는 다음과 같습니다.

| 인수 | 의미 |
|------|------|
| `id` | 방금 커밋된 `Profiler`의 `id` |
| `phase` | `"mount"`, `"update"`, `"nested-update"` |
| `actualDuration` | 이번 갱신에서 `Profiler`와 하위 트리를 렌더링한 시간(ms) |
| `baseDuration` | 최적화 없이 전체 하위 트리를 다시 렌더링할 때의 추정 시간(ms) |
| `startTime` | 이번 갱신 렌더링을 시작한 시각 |
| `commitTime` | 이번 갱신을 커밋한 시각 |

- `Profiler`는 여러 개를 쓰고 서로 중첩해서 UI의 여러 구역을 따로 잴 수 있습니다.
- 프로덕션 빌드에서는 기본적으로 꺼져 있습니다. 쓰려면 프로파일링이 켜진 특수 프로덕션 빌드가 필요합니다.
- CPU와 메모리 오버헤드가 있으므로 필요한 곳에서만 씁니다.

## Render Duration

렌더링 시간은 `onRender`의 두 값으로 읽습니다. 두 값의 비교가 메모이제이션이 효과를 내는지 알려 줍니다.

- `actualDuration`은 이번 갱신에서 실제로 쓴 시간입니다. 하위 트리가 메모이제이션을 얼마나 잘 쓰는지 보여 줍니다.
- `baseDuration`은 메모이제이션 없이 전부 다시 렌더링한다고 가정한 추정 시간입니다. 최악의 경우를 나타냅니다.

| 비교 | 해석 |
|------|------|
| `actualDuration`이 `baseDuration`보다 훨씬 작음 | 일부만 렌더링했다. `memo` 같은 최적화가 동작 중 |
| `actualDuration`이 `baseDuration`과 비슷함 | 거의 전체를 렌더링했다. 최적화가 효과가 없거나 처음 마운트 |

- 마운트(`phase`가 `"mount"`)는 처음이라 모든 컴포넌트가 렌더링되므로 두 값이 비슷한 것이 정상입니다. 갱신에서 비교합니다.
- 단위는 밀리초이고, 컴포넌트 하나가 아니라 `Profiler` 아래 전체 서브트리의 합입니다.
- 한 번의 값이 아니라 여러 번 측정해서 비교합니다. 기기와 상태에 따라 흔들립니다.

## Commit

React는 업데이트를 두 단계로 처리합니다. 렌더링 단계에서 컴포넌트 함수를 호출해 무엇이 바뀔지 계산하고, 커밋 단계에서 계산 결과를 DOM에 반영합니다. 한 번 렌더링하고 DOM에 반영하는 단위가 커밋입니다.

| 순서 | 일어나는 일 |
|------|-------------|
| 1. 렌더링 | 컴포넌트 함수 호출 |
| 2. 커밋 | DOM 반영, `useLayoutEffect` 실행 |
| 3. 페인트 | 브라우저가 화면 그림 |
| 4. 이후 | `useEffect`(passive effect) 실행. 보통 페인트 뒤 |

- DevTools의 Commit 선택 막대는 기록 중에 일어난 커밋마다 막대 하나입니다. 막대의 높이와 색이 그 커밋의 렌더링 시간을 나타냅니다.
- 화살표 버튼이나 막대 클릭으로 커밋 사이를 넘기며 어느 커밋이 느린지 찾습니다.
- `onRender`의 `commitTime`은 커밋한 시각입니다. `startTime`과의 차이로 렌더링 구간의 길이를 알 수 있습니다.
- 한 번의 사용자 동작에서 커밋이 여러 번 나오면 연쇄 갱신(Effect 안의 `setState` 등)을 의심합니다.

## Flamegraph

Flamegraph는 한 커밋에서 컴포넌트 트리를 막대로 그린 그림입니다.

- 막대의 너비는 그 컴포넌트와 자식을 마지막으로 렌더링했을 때 걸린 시간입니다.
- 색은 이번 커밋에서 걸린 시간을 나타냅니다. 노란색은 오래 걸렸고, 파란색은 짧게 걸렸습니다.
- 회색 막대는 이 커밋에서 렌더링되지 않은 컴포넌트입니다.
- 읽는 순서는 넓고 노란 막대에서 아래로 내려가며 비싼 컴포넌트를 찾는 것입니다.

Ranked 차트는 같은 커밋의 컴포넌트를 렌더링 시간순으로 정렬합니다. 가장 오래 걸린 컴포넌트가 맨 위에 옵니다.

| 보고 싶은 것 | 쓰는 차트 |
|--------------|-----------|
| 트리 구조에서 어디가 넓은가 | Flamegraph |
| 개별 컴포넌트 중 가장 느린 것 | Ranked |

- 회색 막대가 많은 것은 좋은 신호입니다. 변하지 않은 부분을 건너뛰었다는 뜻입니다.
- 전부 노란색이고 모두 렌더링됐다면 갱신 범위가 너무 넓다는 신호입니다. state 위치나 `memo`를 점검합니다(자세히는 18편).

## Render 원인

"왜 렌더링됐는가"는 최적화 방향을 정합니다. DevTools에서 컴포넌트를 선택하고 커밋을 넘기면 어떤 props나 state가 바뀌었는지 보일 수 있습니다.

컴포넌트가 다시 렌더링되는 이유는 다음과 같습니다.

| 원인 | 설명 | 대응 |
|------|------|------|
| 자신의 state 변경 | 정상. 화면이 바뀌어야 하는 경우 | 필요한 범위만 렌더링하도록 state를 가까이 둠 |
| 부모의 재렌더링 | 부모가 렌더링되면 자식도 기본적으로 렌더링 | `memo`로 건너뜀 |
| props 변경 | 값이 달라지거나, 같은 내용의 새 객체·함수가 넘어옴 | 참조 안정화(19편) |
| 읽는 Context 변경 | `value`가 바뀜 | Context 분리(1편) |

- 개발 모드의 React Performance Tracks는 컴포넌트 항목을 눌렀을 때 바뀐 props를 보여 줘서, 불필요한 렌더링을 찾는 데 쓸 수 있습니다.
- "내용이 같은데 렌더링됨"을 찾는 것이 핵심입니다. props가 바뀌었다고 나오는데 값이 같다면 객체·함수 참조가 매번 새로 만들어지는 경우입니다.
- 원인을 찾기 전에 `memo`부터 붙이지 않습니다. 원인이 부모의 state 위치라면 구조를 고치는 것이 더 단순합니다.

## 렌더 횟수

렌더 횟수는 같은 컴포넌트가 한 동작에서 몇 번 렌더링되는지입니다. 횟수가 예상보다 많으면 불필요한 재렌더링이 있다는 신호입니다.

- Profiler로 기록해 한 동작에서 커밋이 몇 번 나오는지, 그 커밋에서 어느 컴포넌트가 렌더링됐는지 셉니다.
- `onRender`가 불린 횟수로도 셀 수 있습니다. `id`별로 호출 횟수를 모읍니다.
- 개발 모드의 Strict Mode는 순수성을 확인하려고 계산 함수를 두 번 호출합니다(자세히는 19편). 개발 모드의 횟수는 프로덕션과 다를 수 있으므로 프로덕션 프로파일링 빌드로 확인합니다.
- 렌더링이 많다고 항상 문제는 아닙니다. 한 번의 렌더링이 1ms 안에 끝나면 몇십 번이어도 체감되지 않습니다. 횟수와 시간을 함께 봅니다.

```jsx
// 횟수와 시간을 같이 기록
const counts = {}
function onRender(id, phase, actual) {
  counts[id] = (counts[id] ?? 0) + 1
  console.log(id, counts[id], actual)
}
```

## CPU 병목

렌더링이 빠른데도 화면이 느리면 병목이 렌더링 밖에 있는 것입니다. 브라우저의 Performance 패널에서 메인 스레드를 봅니다.

- 긴 작업(long task)은 메인 스레드를 오래 점유해 클릭·입력에 대한 반응을 늦춥니다. 입력 지연, 이벤트 핸들러 실행, 다음 프레임이 그려질 때까지의 지연이 모두 응답 시간에 포함됩니다.
- 병목이 컴포넌트 렌더링 안에 있으면 계산을 줄이거나 캐시합니다(자세히는 19편). 이벤트 핸들러 안에 있으면 작업을 나눕니다.
- 렌더링이 느린 상태 업데이트는 Transition으로 우선순위를 낮출 수 있습니다(자세히는 9편). 작업량 자체는 줄지 않습니다.
- 실제 사용자의 기기는 개발 기기보다 느립니다. Chrome DevTools의 CPU 스로틀링으로 느린 기기를 흉내 내서 확인합니다.
- 큰 목록의 DOM 노드 수가 병목이면 렌더링할 양을 줄여야 합니다(자세히는 21편).

| 병목 위치 | 확인 도구 |
|-----------|-----------|
| 컴포넌트 렌더링 시간 | React Profiler |
| 이벤트 핸들러, 긴 작업, 레이아웃 | Chrome Performance 패널 |
| 네트워크 대기 | 브라우저 네트워크 패널 |
| 번들 크기 | 빌드 결과, 번들 분석 |

## 측정 후 최적화

최적화는 측정, 원인 파악, 수정, 재측정의 순서로 합니다. 측정이 없는 최적화는 코드만 복잡하게 만듭니다.

1. 느린 동작을 정하고 재현한다(어떤 클릭이 몇 ms 걸리는가).
2. 프로덕션 모드와 CPU 스로틀링에서 기준선을 측정한다.
3. 병목을 찾는다. 렌더링인가, 네트워크인가, 번들인가.
4. 원인에 맞는 가장 단순한 수정을 한다. state 위치, `children` 구조, 그다음 `memo`·`useMemo`·`useCallback`이다.
5. 같은 방법으로 다시 측정해 개선량을 확인한다.
6. 이득이 없으면 되돌린다.

- 공식 문서는 `memo`와 `useMemo`를 프로덕션 모드에서 프로파일러로 재서 이득이 확인된 곳에만 쓰라고 안내합니다.
- 개발 모드 수치로 판단하지 않고 프로덕션 모드에서 잽니다.
- 한 번에 하나만 바꿉니다. 여러 개를 함께 바꾸면 무엇이 효과가 있었는지 알 수 없습니다.

**흔한 실수:** 측정 없이 모든 곳에 메모이제이션을 적용하는 것입니다. 비교 비용과 코드 복잡도만 늘 수 있습니다.

## Performance Tracks

React Performance Tracks는 React 19.2에서 추가된 기능입니다. Chrome DevTools의 Performance 패널에서 기록한 프로파일에 React 전용 트랙을 추가로 보여 줍니다. 브라우저의 일반 프로파일과 React의 스케줄링을 한 화면에서 맞춰 볼 수 있습니다.

| 트랙 | 보여 주는 것 |
|------|--------------|
| Scheduler | 우선순위별 작업(Blocking, Transition, Suspense, Idle), 업데이트를 일으킨 이벤트, 렌더링·커밋 시점 |
| Components | 컴포넌트 렌더링과 Effect에 걸린 시간을 flamegraph로 표시 |

- Scheduler 트랙의 우선순위는 Blocking(사용자 상호작용의 동기 업데이트), Transition(`startTransition` 안의 업데이트), Suspense(Suspense 경계 관련 작업), Idle(더 높은 우선순위가 없을 때)입니다(자세히는 9편).
- 한 업데이트의 단계는 Update(렌더링을 일으킨 것), Render(컴포넌트 함수 호출), Commit(DOM 반영과 레이아웃 Effect), Remaining Effects(`useEffect`)로 나뉩니다.
- Components 트랙의 Mount, Unmount, Reconnect·Disconnect(`Activity`와 함께) 라벨로 서브트리가 언제 붙고 떨어졌는지 봅니다. 렌더링이 React 밖의 작업에 양보하느라 멈춘 구간은 Blocked로 표시됩니다.
- 개발 모드에서는 모든 트랙이 기본으로 켜져 있습니다. 프로덕션 빌드에서는 오버헤드 때문에 꺼져 있고, 프로파일링 빌드(`react-dom/profiling`)에서는 Scheduler 트랙이 기본으로 켜집니다. 이때 Components 트랙은 `Profiler`로 감싼 컴포넌트만(또는 React DevTools 확장이 켜져 있으면 전체) 보여 줍니다.
- 개발 모드 한정 기능으로 바뀐 props 확인과 연쇄 갱신(렌더링 중 다른 업데이트를 예약한 컴포넌트) 표시가 있습니다.
- 0.05ms보다 짧거나 업데이트를 일으키지 않는 Effect는 기본으로 숨겨집니다.

## Core Web Vitals

Core Web Vitals는 실제 사용자 경험을 세 가지 지표로 나타낸 것입니다. 기준은 방문의 75번째 백분위(모바일·데스크톱 구분)에서 만족해야 합니다.

| 지표 | 측정 대상 | 좋음 | 나쁨 |
|------|-----------|------|------|
| LCP (Largest Contentful Paint) | 뷰포트에서 가장 큰 이미지·텍스트 블록·비디오가 그려진 시각 | 2.5초 이하 | 4초 초과 |
| INP (Interaction to Next Paint) | 방문 중 클릭·탭·키보드 상호작용의 응답 시간. 가장 긴 것을 보고 | 200ms 이하 | 500ms 초과 |
| CLS (Cumulative Layout Shift) | 예상치 못한 레이아웃 이동의 가장 큰 묶음 점수 | 0.1 이하 | 0.25 초과 |

- INP는 2024년에 안정적인 Core Web Vital이 되었고, 첫 입력의 지연만 보던 FID를 대체했습니다.
- LCP는 로딩 성능입니다. 번들이 크면 첫 렌더링이 늦어질 수 있습니다.
- INP는 반응성입니다. 입력 지연, 이벤트 핸들러 실행, 다음 프레임이 그려지기까지의 지연으로 이루어지고, 긴 작업과 느린 렌더링이 원인이 됩니다. React에서는 이 편의 Profiler로 렌더링 시간을 줄이는 작업이 INP 개선과 이어집니다.
- CLS는 시각적 안정성입니다. 크기를 지정하지 않은 이미지·비디오, 늦게 로드되는 콘텐츠, 기존 내용 앞에 끼어드는 DOM 요소가 원인입니다.
- Core Web Vitals는 사용자 환경의 측정값(필드 데이터)이 기준입니다. 로컬에서는 API가 빠르고 캐시가 있어서 문제가 가려질 수 있습니다.
- React DevTools Profiler는 렌더링 시간을 보고, Core Web Vitals는 사용자가 느끼는 결과를 봅니다. 둘은 보완 관계입니다.

## 번들 크기 측정

번들 크기는 JavaScript를 내려받고 해석하는 시간에 직접 영향을 줍니다. 렌더링이 빨라도 번들이 크면 첫 화면이 늦어집니다.

Vite를 예로 들면 빌드 출력에서 크기를 바로 확인할 수 있습니다.

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `build.chunkSizeWarningLimit` | 500(KB) | 압축 전 JavaScript 청크가 이 크기를 넘으면 경고. 큰 스크립트는 실행 시간에 영향 |
| `build.reportCompressedSize` | `true` | 빌드 출력에 gzip 압축 후 크기를 함께 표시 |
| `build.sourcemap` | `false` | 프로덕션 코드 디버깅용 소스맵 생성 |

- 청크 경고가 뜨면 큰 의존성이 들어갔는지 확인합니다. 라이브러리 하나가 번들 대부분을 차지하는 경우가 흔합니다.
- 번들 분석 도구로 어떤 모듈이 크기를 차지하는지 시각화합니다(자세히는 12편).
- 줄이는 방법은 라우트·컴포넌트 단위 코드 분할(`React.lazy`, 12편), 사용하지 않는 의존성 제거, 더 가벼운 대체 라이브러리 선택입니다.
- 크기는 압축 전(실행 시 해석 비용)과 압축 후(전송 비용) 두 가지로 봅니다.
- 번들 크기는 렌더링 성능과 별개의 문제이므로 Profiler에서는 보이지 않습니다.

## 면접 질문 "렌더링 최적화 경험"

이 질문은 최적화 기법의 이름을 아는지가 아니라 측정에 근거해 판단하는지를 봅니다. 답변은 문제, 측정, 원인, 조치, 결과의 순서로 구성합니다.

| 항목 | 담을 내용 |
|------|-----------|
| 문제 | 어떤 화면의 어떤 동작이 느렸는가(체감 또는 지표) |
| 측정 | 무엇으로 어떻게 쟀는가(Profiler, Performance 패널, Web Vitals), 기준값 |
| 원인 | 왜 느렸는가(불필요한 재렌더링, 큰 목록, 긴 계산, 큰 번들) |
| 조치 | 무엇을 했는가. 구조 변경이 먼저, 메모이제이션은 그다음 |
| 결과 | 같은 방법으로 다시 잰 개선 수치, 부작용이나 트레이드오프 |

가상의 예시 답변의 뼈대는 다음과 같습니다. 숫자는 설명용입니다.

- "검색 입력에서 타이핑할 때 목록이 멈칫했습니다. Profiler로 기록하니 한 글자마다 800개 행이 모두 렌더링되고 커밋이 40ms 걸렸습니다."
- "원인은 입력 state가 목록을 가진 부모에 있어서 매 입력마다 전체가 다시 렌더링되는 것이었습니다."
- "state를 입력 컴포넌트로 내리고, 행을 `memo`로 감싸 안정적인 props를 넘겼습니다."
- "같은 조건에서 다시 측정하니 커밋이 6ms로 줄었습니다."

- 숫자는 실제로 잰 값만 말합니다. 지어낸 수치는 꼬리 질문에서 드러납니다.
- "무조건 `useMemo`를 썼다"는 답은 약점입니다. 쓰지 않기로 한 판단, 측정해 보니 효과가 없어 되돌린 경험을 말하면 오히려 신뢰를 줍니다.
- React Compiler를 쓰는 환경이라면 수동 메모이제이션을 줄이고 구조와 측정에 집중했다고 설명할 수 있습니다(자세히는 19편).

## 핵심 정리

- DevTools Profiler는 기록 후 커밋 막대, Flamegraph, Ranked 차트로 느린 커밋과 컴포넌트를 찾고, 프로덕션 프로파일링은 `react-dom/profiling` 번들로 합니다.
- `Profiler` 컴포넌트의 `onRender`는 `actualDuration`(실제)과 `baseDuration`(최적화 없을 때 추정)을 주며, 두 값의 차이가 메모이제이션의 효과입니다.
- 렌더링의 원인(state, 부모, props, Context)을 찾아야 올바른 최적화를 고를 수 있고, 렌더 횟수는 시간과 함께 봅니다.
- 렌더링 밖의 병목은 Chrome Performance 패널로 보고, React 19.2의 Performance Tracks가 우선순위별 스케줄링을 같은 화면에서 보여 줍니다.
- Core Web Vitals는 LCP 2.5초, INP 200ms, CLS 0.1 이하가 좋음이며, 번들 크기는 빌드 출력과 분석 도구로 따로 확인합니다.
- 최적화는 프로덕션 모드에서 측정, 수정, 재측정의 순서이고, 면접에서도 이 근거를 말합니다.

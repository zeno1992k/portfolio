## Callback Ref

Callback Ref는 `ref`에 객체 대신 함수를 넘기는 방식입니다. React가 DOM 노드가 화면에 붙을 때 그 함수를 호출하면서 노드를 인수로 줍니다(`useRef`와 기본 사용법은 기초 19편).

```jsx
<input
  ref={(node) => {
    console.log('attached', node) // DOM 노드
  }}
/>
```

객체 ref는 `ref.current`에 값을 담아 둘 뿐이라 노드가 붙고 떨어지는 순간에 코드를 실행할 수 없습니다. Callback Ref는 그 순간에 실행할 코드를 직접 넣을 수 있습니다. 노드가 마운트될 때 크기를 읽거나, 외부 라이브러리에 노드를 등록하는 경우에 씁니다.

호출 시점은 다음과 같습니다.

| 시점 | React가 하는 일 |
|------|-----------------|
| 마운트 | 콜백을 DOM 노드와 함께 호출한다 |
| 언마운트 | 콜백이 돌려준 정리 함수를 호출한다 |
| 다른 함수가 넘어옴 | 이전 콜백을 정리하고, 새 콜백을 노드와 함께 호출한다 |

- ref는 렌더링 중이 아니라 커밋 단계에서 연결됩니다. 렌더링 중에는 `ref.current`가 `null`입니다.
- 이전 콜백에 정리 함수가 없으면 React는 이전 콜백을 `null`로 호출합니다. React 19에서도 하위 호환으로 남아 있고 앞으로 제거될 예정입니다.

**흔한 실수:** 렌더링마다 새로 만들어지는 인라인 화살표 함수를 쓰고 그 안에서 비용이 큰 일을 하는 것입니다. 함수가 다르므로 매 렌더링마다 정리와 재호출이 일어납니다. 매번 달라지면 안 되는 콜백은 `useCallback`으로 고정하거나 컴포넌트 밖에서 선언합니다(자세히는 19편).

## Ref Cleanup

React 19부터 Callback Ref가 정리 함수를 반환할 수 있습니다. 요소가 DOM에서 제거될 때 React가 그 함수를 호출합니다. Effect의 정리 함수와 같은 방식입니다.

```jsx
<div
  ref={(node) => {
    const observer = new ResizeObserver(onResize)
    observer.observe(node)
    return () => observer.disconnect() // 정리
  }}
/>
```

- 정리 함수를 반환하면 React는 언마운트 때 콜백을 `null`로 호출하지 않습니다.
- DOM ref뿐 아니라 클래스 컴포넌트 ref, `useImperativeHandle`로 만든 ref에도 적용됩니다.
- StrictMode에서는 개발 중에 첫 연결 전에 설정과 정리를 한 번 더 실행합니다. 정리가 설정을 되돌리는지 확인하는 장치입니다.
- 인라인 함수는 렌더링마다 정리와 설정이 반복됩니다. 비용이 큰 설정이면 함수 참조를 고정합니다.

TypeScript 타입이 정리 함수 이외의 값 반환을 거부합니다. 암시적 반환을 쓰던 코드는 블록으로 바꿉니다.

```jsx
// ❌ 대입 값을 암시적으로 반환
<div ref={(current) => (instance = current)} />
// ✅ 블록으로 반환 없음
<div ref={(current) => { instance = current }} />
```

## Ref as Prop

React 19부터 함수 컴포넌트는 `ref`를 일반 prop처럼 받습니다. 받은 `ref`를 내부 요소에 그대로 넘기면 부모가 그 요소에 접근합니다.

```jsx
function MyInput({ placeholder, ref }) {
  return <input placeholder={placeholder} ref={ref} />
}
// 사용
<MyInput ref={inputRef} placeholder="이름" />
```

- 새 함수 컴포넌트에는 `forwardRef`가 필요 없습니다.
- 다른 prop처럼 구조 분해하거나 `...rest`로 전달할 수 있습니다.
- 클래스 컴포넌트에 넘긴 `ref`는 prop으로 전달되지 않습니다. 컴포넌트 인스턴스를 가리키기 때문입니다.
- 컴포넌트가 `ref`를 어떤 요소에 연결하는가가 곧 노출 범위입니다. 연결하지 않으면 부모는 DOM에 접근할 수 없습니다.

**흔한 실수:** 19 미만 환경에서 `ref`를 prop처럼 읽는 것입니다. 이전 버전에서 `ref`는 예약된 이름이라 prop으로 오지 않고 `undefined`이며, `forwardRef`가 필요합니다.

## Ref Forwarding 역사

React 18까지는 `ref`가 `key`처럼 예약된 이름이라 함수 컴포넌트에 prop으로 전달되지 않았습니다. 자식의 DOM에 접근하려면 `forwardRef`로 컴포넌트를 감싸 두 번째 인수로 `ref`를 받아야 했습니다.

```jsx
const MyInput = forwardRef(function MyInput(props, ref) {
  return <input {...props} ref={ref} />
})
```

- 19에서 `ref`가 prop이 되면서 `forwardRef`는 필요 없어졌습니다.
- 공식 문서는 `forwardRef`가 앞으로 폐기될 예정이라고 안내하고, 기존 컴포넌트를 바꿔 주는 코드 변환 도구(codemod)를 공개할 예정이라고 밝혔습니다. 폐기 시점은 정해져 있지 않습니다.
- 지금도 `forwardRef`는 동작합니다. 18 이하와 19를 함께 지원하는 라이브러리 코드에서는 아직 보입니다.
- 마이그레이션은 `forwardRef(function(props, ref) { ... })`를 `function Comp({ ref, ...props })`로 바꾸는 것입니다.

기존 코드를 읽을 때는 두 형태를 모두 알아봐야 합니다. 새로 쓰는 코드는 `ref` prop으로 씁니다.

## DOM Node 노출

컴포넌트는 기본적으로 자기 DOM 노드를 부모에게 노출하지 않습니다. 부모가 `ref`를 넘겨도 컴포넌트가 내부 요소에 연결하지 않으면 `ref.current`는 `null`입니다.

```jsx
const inputRef = useRef(null)
<MyInput ref={inputRef} />
inputRef.current.focus() // MyInput이 ref를 input에 연결해야 동작
```

- `ref`를 DOM 요소에 바로 연결하면 부모는 그 노드의 모든 DOM API에 접근합니다. `focus`, `scrollIntoView`뿐 아니라 `remove`나 `style` 변경도 가능합니다.
- 입력 요소처럼 DOM 인터페이스 자체가 노출 대상인 컴포넌트는 노드를 그대로 노출해도 괜찮습니다.
- 내부 구조를 숨기고 싶은 컴포넌트는 노출 범위를 좁힙니다(아래 `useImperativeHandle`).

노출 방식은 기준이 갈립니다.

| 방식 | 부모가 받는 것 | 적합한 경우 |
|------|---------------|-------------|
| `ref`를 요소에 연결 | DOM 노드 전체 | 입력·버튼 같은 기본 요소 래퍼 |
| `useImperativeHandle` | 컴포넌트가 정한 메서드 | 내부 구조를 숨기고 동작만 노출 |
| props | 필요한 값 | 상태로 표현할 수 있는 모든 것 |

## useImperativeHandle

`useImperativeHandle(ref, createHandle, dependencies?)`는 부모가 받는 ref 값을 DOM 노드 대신 직접 정한 객체로 바꾸는 Hook입니다.

```jsx
function MyInput({ ref }) {
  const realRef = useRef(null)
  useImperativeHandle(ref, () => ({
    focus() { realRef.current.focus() },
    scrollIntoView() { realRef.current.scrollIntoView() },
  }), [])
  return <input ref={realRef} />
}
```

- 부모는 `ref.current.focus()`와 `scrollIntoView()`만 쓸 수 있고, 나머지 DOM API에는 접근할 수 없습니다.
- 두 번째 인수는 핸들을 만드는 함수입니다. 세 번째 인수인 의존성 배열의 값이 바뀌면 핸들을 다시 만듭니다.
- 핸들 객체에는 `focus`, `scrollIntoView`처럼 명령형으로만 표현되는 동작을 넣습니다. 상태처럼 쓰이는 값은 넣지 않습니다.
- 내부 `ref`(`realRef`)는 컴포넌트 안에서만 쓰고 바깥에 노출하지 않습니다.

```jsx
// 부모
const ref = useRef(null)
<MyInput ref={ref} />
<button onClick={() => ref.current.focus()}>편집</button>
```

**흔한 실수:** `open()`, `close()`, `setValue()` 같은 핸들을 만들어 상태를 바꾸는 것입니다. 상태로 표현할 수 있는 동작은 `isOpen` 같은 prop으로 받습니다. 핸들은 포커스·스크롤·애니메이션 시작처럼 prop으로 표현하기 어려운 동작에만 씁니다.

## 동적 리스트 Ref

항목 수가 렌더링 때 정해지는 리스트에서는 항목마다 `useRef`를 만들 수 없습니다. Hook은 반복문 안에서 호출할 수 없기 때문입니다. 대신 Callback Ref로 하나의 `Map`에 노드를 모읍니다.

```jsx
const itemsRef = useRef(null)
function getMap() {
  if (!itemsRef.current) itemsRef.current = new Map()
  return itemsRef.current
}
```

```jsx
{cats.map((cat) => (
  <li key={cat.id} ref={(node) => {
    const map = getMap()
    map.set(cat.id, node)
    return () => map.delete(cat.id) // 정리: 제거 시 삭제
  }} />
))}
// 필요할 때: getMap().get(id).scrollIntoView()
```

- `Map`은 렌더링 사이에 유지되는 `useRef` 하나에 담습니다. 키는 항목의 안정적인 ID입니다. 인덱스는 순서가 바뀌면 어긋납니다.
- 정리 함수에서 키를 삭제하지 않으면 사라진 노드가 `Map`에 남습니다.
- 인라인 콜백이라 렌더링마다 삭제와 등록이 반복됩니다. 항목이 많고 비용이 문제라면 콜백을 고정하는 구조를 고려합니다.
- 노드는 렌더링 중이 아니라 이벤트 핸들러나 Effect에서 읽습니다.
- 상태를 바꾼 직후 새로 생긴 노드를 읽어야 하면, 상태 반영이 끝나야 노드가 존재합니다. `flushSync`로 상태 갱신을 즉시 DOM에 반영한 뒤 읽습니다(`flushSync`는 17편).

```js
flushSync(() => setTodos([...todos, newTodo]))
listRef.current.lastChild.scrollIntoView()
```

## Ref와 Portal

Portal로 렌더링한 요소에도 `ref`는 일반 요소처럼 동작합니다. Portal은 DOM 위치만 바꾸므로, 그 안의 JSX는 React 트리에서 렌더링한 컴포넌트의 자식입니다(Portal은 14편).

```jsx
function Modal({ ref, children }) {
  return createPortal(
    <div ref={ref}>{children}</div>,
    document.body,
  )
}
```

- `ref.current`는 `document.body` 아래에 있는 실제 노드입니다. 부모의 DOM 자손이 아닙니다.
- 따라서 `parentRef.current.contains(portalNode)`는 `false`입니다. 바깥 클릭 감지처럼 DOM 포함 관계를 검사하는 코드는 Portal 노드의 `ref`도 함께 확인해야 합니다.
- 이벤트는 React 트리를 따라 부모로 버블링합니다. DOM 트리의 부모가 아닙니다.
- Portal의 대상 노드는 이미 존재해야 합니다. 대상을 다른 노드로 바꾸면 Portal 내용이 다시 만들어집니다.

## Ref 남용

`ref`는 React 바깥의 시스템을 다루는 탈출구입니다. 포커스, 스크롤, 텍스트 선택, 크기 측정, 브라우저 API 호출처럼 prop과 state로 표현할 수 없는 일에만 씁니다.

| 하지 말 것 | 이유 | 대신 |
|------------|------|------|
| `ref.current.style`로 화면 상태 바꾸기 | React가 아는 상태가 아니라 다음 렌더링과 어긋난다 | state로 클래스·스타일 결정 |
| 표시 여부를 `ref`에 저장 | 바뀌어도 렌더링되지 않는다 | `useState` |
| 렌더링 중 `ref.current` 읽기·쓰기 | 컴포넌트가 순수하지 않게 된다 | 이벤트 핸들러나 Effect에서 접근 |
| React가 관리하는 DOM 직접 제거 | React의 트리와 실제 DOM이 어긋난다 | 조건부 렌더링 |
| 부모가 자식 `ref`로 상태 조작 | 데이터 흐름이 숨는다 | props와 이벤트 콜백 |

- `ref.current`를 바꿔도 React는 다시 렌더링하지 않습니다.
- 초기화(`ref.current === null`일 때 한 번 채우기)만 렌더링 중에 허용되는 예외입니다.
- React가 갱신할 이유가 없는 DOM 부분은 직접 바꿔도 안전합니다. 포커스나 스크롤이 이에 해당합니다.

```js
// ❌ React가 모르는 사이에 DOM 제거
ref.current.remove()
setShow(true) // 이미 사라진 노드를 다시 표시하려다 오류
// ✅ 상태로 표시 여부를 결정
setShow(!show)
```

## Fragment ref

Fragment Ref는 `<Fragment>`에 `ref`를 달아, 래퍼 요소 없이 자식 DOM 노드 묶음을 한꺼번에 다루는 기능입니다. `ref.current`에는 `FragmentInstance` 객체가 들어옵니다.

**릴리스 상태:** React 19.3(2026-09-09)에서 정식 기능이 되었습니다. 공식 블로그가 안정판 19.3에 포함됐다고 밝히고, 이전에는 실험 기능으로 공유됐다고 설명합니다. 이 과목의 기준 버전인 19.2에는 없습니다. 19.2 이하에서는 쓸 수 없으며, 19.3 이상으로 올린 프로젝트에서 사용합니다. 사용 전에 프로젝트의 `react` 버전을 확인하세요.

```jsx
import { Fragment, useRef } from 'react'

function Component() {
  const fragmentRef = useRef(null)
  return <Fragment ref={fragmentRef}>{children}</Fragment>
}
```

- `ref`는 명시적인 `<Fragment>`에만 붙일 수 있습니다. 축약형 `<>...</>`에는 `ref`도 `key`도 줄 수 없습니다.
- `Fragment`를 `react`에서 import해야 합니다.
- 두 가지 문제를 풉니다. 형제 여러 개를 렌더링하는 컴포넌트에 단일 부모가 없는 문제, 그리고 컴포넌트가 `ref`를 내부 요소에 전달하지 않는 문제입니다.
- `<div>` 래퍼로 `ref`를 받으면 스타일과 레이아웃이 깨질 수 있어서, 이 기능은 DOM 구조를 바꾸지 않고 동작만 붙입니다.

## FragmentInstance

`FragmentInstance`는 Fragment의 자식 DOM을 한 묶음으로 다루는 메서드를 가진 객체입니다. 대상 범위가 메서드마다 다릅니다.

| 메서드 | 하는 일 | 대상 |
|--------|---------|------|
| `addEventListener`, `removeEventListener` | 이벤트 리스너 등록·해제 | 최상위 DOM 자식 전체 |
| `dispatchEvent` | Fragment에 이벤트 발생 | 등록된 리스너, 부모 DOM으로 버블링 |
| `focus`, `focusLast`, `blur` | 포커스 이동·해제 | 중첩 자손까지 깊이 우선 탐색 |
| `observeUsing`, `unobserveUsing` | `IntersectionObserver`·`ResizeObserver` 연결 | 최상위 DOM 자식 전체 |
| `getClientRects` | 사각형 배열 반환 | 최상위 DOM 자식 전체 |
| `getRootNode` | 부모 DOM 노드의 루트 노드 | Fragment 부모 |
| `compareDocumentPosition` | 다른 노드와 문서 위치 비교 | Fragment |
| `scrollIntoView` | 스크롤 이동 | 첫(또는 마지막) 자식 |

최상위 DOM 자식은 Fragment 바로 아래에 렌더링되는 DOM 요소를 말합니다. 중간에 컴포넌트가 끼어 있어도 그 컴포넌트가 렌더링한 최상위 DOM 요소는 포함되지만, 그 요소 안에 중첩된 요소는 제외됩니다.

```jsx
<Fragment ref={ref}>
  <div id="A" />           {/* 대상 */}
  <Wrapper>
    <div id="B">           {/* 대상 (Wrapper의 최상위 DOM) */}
      <div id="C" />       {/* 제외 (B 안에 중첩) */}
    </div>
  </Wrapper>
</Fragment>
```

- `FragmentInstance` 대상 요소에는 `reactFragments` 프로퍼티가 붙어서, 그 요소를 감싼 `FragmentInstance` 집합을 얻을 수 있습니다. 하나의 관찰자를 공유하는 구조에서 쓰입니다.
- 자식이 없는 Fragment나 Portal로 렌더링된 자식이 있는 Fragment에서는 `compareDocumentPosition` 결과에 구현 정의 플래그가 포함됩니다.
- 기본 DOM 요소의 메서드와 이름이 같지만 동작은 묶음 기준입니다.

## DOM Node 그룹 참조

Fragment Ref가 없을 때 형제 여러 개를 다루려면 각 요소에 ref를 따로 달거나, 부모가 `ref`로 컨테이너를 잡고 자식을 찾아야 했습니다. 이 방식은 다음 문제가 있습니다.

- 자식이 다른 컴포넌트이고 그 컴포넌트가 `ref`를 내부 요소에 전달하지 않으면 접근할 수 없습니다.
- 래퍼 `<div>`를 추가하면 CSS 레이아웃(flex, grid, 선택자)이 깨질 수 있습니다.
- 자식 목록이 바뀔 때 ref 등록·정리를 직접 관리해야 합니다.

Fragment Ref는 Fragment가 렌더링하는 자식 DOM 묶음을 `FragmentInstance` 하나로 참조합니다. 자식 컴포넌트의 내부를 고치지 않아도, 렌더링되는 DOM 구조도 바꾸지 않습니다.

```jsx
function Group({ children }) {
  const ref = useRef(null)
  const rects = () => ref.current.getClientRects()
  return <Fragment ref={ref}>{children}</Fragment>
}
```

참조하는 시점은 일반 ref와 같습니다. 렌더링 중에는 `null`일 수 있고, Effect와 이벤트 핸들러에서 쓰는 것이 안전합니다.

## Focus API

`focus(options?)`는 Fragment 안에서 포커스할 수 있는 첫 DOM 노드에 포커스를 줍니다. `focusLast`는 마지막 노드에 줍니다. 두 메서드는 최상위 자식만이 아니라 중첩된 자손까지 깊이 우선으로 탐색합니다.

```jsx
const f = fragmentRef.current
f.focus()                        // 첫 포커스 가능 요소
f.focusLast()                    // 마지막 포커스 가능 요소
f.focus({ preventScroll: true }) // 스크롤 없이
f.blur()                         // Fragment 안이면 해제
```

- `blur()`는 `document.activeElement`가 Fragment 안에 있을 때만 포커스를 해제하고, 아니면 아무것도 하지 않습니다.
- 폼 필드 묶음에서 "첫 필드로 이동", "마지막 필드로 이동" 버튼을 만들 때 씁니다.
- 래퍼 요소가 없으므로 `querySelector`로 포커스 가능한 요소를 찾을 컨테이너가 없는 구조에서 특히 유용합니다.

## Event API

`addEventListener(type, listener, options?)`는 Fragment의 모든 최상위 DOM 자식에 리스너를 붙이고, `removeEventListener`는 떼어 냅니다. Effect에서 등록하고 정리 함수에서 해제합니다.

```jsx
useEffect(() => {
  const fragment = fragmentRef.current
  fragment.addEventListener('click', onClick)
  return () => {
    fragment.removeEventListener('click', onClick)
  }
}, [onClick])
```

- `options`에는 DOM의 `addEventListener` 옵션 객체나 캡처 불리언을 줍니다.
- `dispatchEvent(event)`는 Fragment에 이벤트를 발생시킵니다. 등록된 리스너가 호출되고, `bubbles`가 `true`이면 Fragment의 부모 DOM으로 버블링합니다. 취소(`preventDefault`)되면 `false`를 반환합니다.
- 숨겨진 `Activity` 트리의 자식에는 리스너가 적용되지 않다가 보이게 될 때 자동으로 적용됩니다(자세히는 16편).
- 관찰자 연결도 같은 구조입니다. `observeUsing(observer)`로 `IntersectionObserver`나 `ResizeObserver`를 최상위 DOM 자식 전체에 연결하고, `unobserveUsing(observer)`로 해제합니다. 텍스트 노드는 관찰할 수 없습니다.

```jsx
useLayoutEffect(() => {
  const fragment = fragmentRef.current
  fragment.observeUsing(observer)
  return () => fragment.unobserveUsing(observer)
}, [])
```

## DOM 측정

Fragment에는 자기 자신의 박스가 없으므로 단일 크기가 아니라 자식별 사각형의 배열을 얻습니다.

```jsx
const rects = fragmentRef.current.getClientRects()
// DOMRect 배열. 최상위 DOM 자식마다 하나
```

- 전체를 감싸는 사각형이 필요하면 배열에서 직접 계산합니다. 가장 왼쪽 `left`, 가장 위 `top`, 가장 오른쪽 `right`, 가장 아래 `bottom`을 구하면 됩니다.
- 크기 변화를 감지하려면 `ResizeObserver`를 `observeUsing`으로 연결합니다.
- `scrollIntoView(alignToTop?)`는 첫 자식을 영역 위쪽으로(기본 `true`), `false`를 주면 마지막 자식을 아래쪽으로 스크롤합니다. `ScrollIntoViewOptions` 객체는 받지 않고, 객체를 넘기면 오류가 납니다. 자식이 없으면 가까운 형제나 부모를 대신 스크롤합니다.
- `getRootNode(options?)`와 `compareDocumentPosition(otherNode)`는 DOM의 같은 이름 메서드와 같은 의미입니다.
- 측정은 레이아웃이 끝난 뒤여야 합니다. 값에 따라 화면을 바꾸는 측정은 `useLayoutEffect`가 필요합니다(자세히는 04편).

**흔한 실수:** 렌더링 중에 `getClientRects()`를 호출하는 것입니다. 렌더링 중에는 아직 DOM이 갱신되기 전이거나 `ref.current`가 `null`입니다.

## Wrapper 없는 DOM 그룹 제어

Fragment Ref가 푸는 일은 래퍼 요소를 추가하지 않고 DOM 그룹에 행동을 붙이는 것입니다. 공식 블로그의 `InView` 예를 줄인 코드입니다. 자식이 화면에 들어오거나 나갈 때 `onChange`를 호출합니다. 원본은 화면에 보이는 요소의 집합을 직접 추적하고, 이 코드는 이번에 들어온 변화 항목만 봅니다.

```jsx
function InView({ onChange, children }) {
  const ref = useRef(null)
  useLayoutEffect(() => {
    const io = new IntersectionObserver((entries) => {
      onChange(entries.some((e) => e.isIntersecting))
    })
    const fragment = ref.current
    fragment.observeUsing(io)
    return () => fragment.unobserveUsing(io)
  }, [onChange])
  return <Fragment ref={ref}>{children}</Fragment>
}
```

- 사용하는 쪽은 `<InView onChange={...}><Card /><Card /></InView>`처럼 감쌀 뿐이고 DOM 구조는 그대로입니다.
- 감싸는 컴포넌트는 자식 컴포넌트의 내부를 알 필요가 없습니다.
- 이벤트, 포커스, 관찰, 측정, 스크롤이 모두 이 컴포넌트 한 곳에서 같은 방식으로 다뤄집니다.

사용 기준은 다음과 같습니다.

- 대상이 단일 DOM 요소이면 일반 `ref`를 씁니다.
- 대상이 형제 여러 개이거나 `ref`를 전달하지 않는 컴포넌트의 출력이면 Fragment Ref를 씁니다.
- 단일 요소를 노출하는 입력 컴포넌트에는 `ref` prop과 `useImperativeHandle`이 맞습니다.
- 이벤트와 관찰은 최상위 DOM 자식만 대상이므로, 중첩된 요소까지 필요하면 그 요소에 직접 `ref`를 둡니다.

## 핵심 정리

- Callback Ref는 노드가 붙을 때 호출되고, 19부터 정리 함수를 반환할 수 있습니다. 인라인 함수는 렌더링마다 정리와 재호출이 일어납니다.
- 19부터 함수 컴포넌트는 `ref`를 prop으로 받아서 `forwardRef`가 필요 없고, `forwardRef`는 앞으로 폐기될 예정입니다.
- 노출 범위를 좁히려면 `useImperativeHandle`로 포커스·스크롤 같은 명령형 동작만 내보내고, 상태로 표현할 수 있는 것은 props로 받습니다.
- 동적 리스트 ref는 Callback Ref와 `Map`으로 모으고 정리 함수에서 삭제합니다.
- Fragment Ref는 19.3(2026-09-09)에서 정식 도입되었고 19.2 이하에는 없습니다. 명시적 `Fragment`에만 붙일 수 있습니다.
- `FragmentInstance`는 이벤트·관찰·측정·스크롤은 최상위 DOM 자식에, 포커스는 중첩 자손까지 적용합니다.

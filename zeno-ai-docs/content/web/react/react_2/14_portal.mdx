## createPortal

`createPortal`은 자식을 부모의 DOM 위치가 아니라 지정한 다른 DOM 노드 안에 렌더하는 함수입니다. `react-dom`에서 가져옵니다.

```jsx
import { createPortal } from 'react-dom'

function Note() {
  return (
    <div className="card">
      <p>card 안에 렌더됩니다.</p>
      {createPortal(<p>body에 렌더됩니다.</p>, document.body)}
    </div>
  )
}
```

- 시그니처는 `createPortal(children, domNode, key?)`입니다. `children`은 렌더할 React 노드, `domNode`는 이미 존재하는 DOM 노드, `key`는 선택입니다.
- 반환값은 React 노드입니다. JSX 안에 넣거나 컴포넌트에서 반환합니다.
- 컴포넌트가 사라지면 Portal로 렌더한 DOM도 함께 제거됩니다.
- 다른 `domNode`를 넘기면 Portal 내용이 새로 만들어집니다.
- 공식 문서가 꼽는 용도는 `overflow: hidden` 부모 위에 뜨는 Modal, Tooltip, 서버가 만든 비 React 마크업과의 통합, 비 React DOM 노드에 React 내용 렌더입니다.

**흔한 실수:** 서버 렌더링 중에는 `document`가 없어서 `document.body`를 그대로 쓰면 오류가 납니다. 브라우저에서 마운트된 뒤에 컨테이너를 찾아 렌더합니다(아래 "Portal Container").

## DOM 위치와 React Tree

Portal은 DOM 위치만 바꾸고 React 트리에서의 위치는 바꾸지 않습니다. Portal로 렌더한 자식은 DOM에서는 `domNode`의 자식이지만, React에서는 `createPortal`을 쓴 컴포넌트의 자식입니다.

| 항목 | 따르는 트리 |
|------|-------------|
| 화면에 놓이는 위치 | DOM 트리(`domNode` 안) |
| CSS 상속(글꼴, 색) | DOM 트리 |
| CSS 선택자(`.card p`) | DOM 트리 |
| 이벤트 버블링 | React 트리 |
| Context 값 | React 트리 |
| state·Effect 생명주기 | React 트리 |

- `.card` 안의 스타일이 `body`로 옮긴 Portal 내용에는 적용되지 않습니다. 글꼴이나 색이 필요하면 Portal 안쪽에서 직접 지정합니다.
- 반대로 부모 컴포넌트가 언마운트되면 Portal 내용도 언마운트됩니다.

## Modal

Modal은 화면 위에 덮어 뜨는 대화상자입니다. 부모에 `overflow: hidden`이나 `transform`이 있으면 잘리거나 위치가 어긋나므로 `body`로 옮겨 렌더합니다.

```jsx
function Modal({ open, onClose, children }) {
  if (!open) return null
  return createPortal(
    <div className="backdrop" onClick={onClose}>
      <div
        role="dialog"
        aria-modal="true"
        onClick={(e) => e.stopPropagation()}
      >
        {children}
      </div>
    </div>,
    document.body,
  )
}
```

- 대화상자 요소에는 `role="dialog"`와 `aria-modal="true"`를 붙이고, 제목은 `aria-labelledby`로 연결합니다.
- 배경을 눌러 닫는 동작은 `backdrop`의 `onClick`이 하고, 안쪽 패널의 클릭은 `stopPropagation`으로 끊습니다.
- 열려 있는 동안의 포커스 처리는 아래 "Focus" 절에서 다룹니다. 접근성 전반은 32편에서 다룹니다.

## Tooltip

Tooltip은 대상 요소 옆에 뜨는 짧은 설명입니다. 대상 요소의 위치를 재서 `body`에 `position: fixed`나 `absolute`로 배치합니다.

```jsx
function Tooltip({ anchorRef, children }) {
  const [pos, setPos] = useState({ top: 0, left: 0 })

  useLayoutEffect(() => {
    const r = anchorRef.current.getBoundingClientRect()
    setPos({ top: r.bottom + 4, left: r.left })
  }, [anchorRef])

  return createPortal(
    <div style={{ position: 'fixed', ...pos }}>
      {children}
    </div>,
    document.body,
  )
}
```

- `getBoundingClientRect()`로 대상의 화면상 위치를 읽습니다. 페인트 전에 읽고 배치하려고 `useLayoutEffect`를 씁니다(자세히는 04편).
- 스크롤이나 창 크기가 바뀌면 위치를 다시 계산해야 합니다.
- 부모의 `overflow: hidden`에 잘리지 않는 것이 Portal을 쓰는 이유입니다.
- 화면 가장자리에서 뒤집거나 밀어 주는 충돌 처리는 직접 구현하면 번거로워서, 보통 Floating UI 같은 라이브러리를 씁니다.

## Overlay

Overlay는 Modal, Tooltip, 드롭다운, 토스트처럼 기존 화면 위에 겹쳐 뜨는 UI를 통틀어 부르는 말입니다. 공통 문제는 부모의 잘림과 쌓임 순서입니다.

| 종류 | 배경 막기 | 포커스 가두기 | 닫는 방법 |
|------|-----------|---------------|-----------|
| Modal | 예 | 예 | 닫기 버튼, Esc, 배경 클릭 |
| Tooltip | 아니오 | 아니오 | 포인터·포커스가 벗어날 때 |
| 드롭다운 메뉴 | 아니오 | 상황별 | 항목 선택, Esc, 바깥 클릭 |
| 토스트 | 아니오 | 아니오 | 시간 경과, 닫기 버튼 |

- 여러 Overlay를 쓰는 앱은 Portal을 쓰는 공통 컴포넌트 하나로 렌더 위치와 쌓임 순서를 정합니다.
- 토스트처럼 화면 한쪽에 모이는 UI는 전용 컨테이너를 하나 두고 그 안에 쌓습니다.

## Event Bubbling

Portal 안에서 일어난 이벤트는 DOM 트리가 아니라 React 트리를 따라 올라갑니다. Portal 안을 클릭하면 Portal을 감싼 React 부모의 `onClick`도 실행됩니다.

```jsx
function Parent() {
  return (
    <div onClick={() => console.log('parent')}>
      {createPortal(
        <button>눌러 보기</button>, // DOM에서는 body의 자식
        document.body,
      )}
    </div>
  )
}
// 버튼을 누르면 'parent'가 출력됨
```

- 공식 문서의 안내는 두 가지입니다. Portal 안에서 `stopPropagation()`으로 전파를 막거나, Portal 자체를 React 트리에서 더 위로 옮깁니다.
- 원치 않는 전파의 전형은 클릭하면 선택·펼침이 토글되는 카드 안의 Modal입니다. Modal을 누를 때마다 카드가 접히는 증상이 나옵니다.
- 이 동작은 장점이기도 합니다. 부모에 달아 둔 `onClick`으로 바깥 클릭을 판단하는 코드가 Portal 자식에도 동작합니다.
- 네이티브 `addEventListener`는 DOM 트리를 따릅니다. 문서 전체의 `click`을 직접 구독하는 코드는 Portal 위치를 DOM 기준으로 계산해야 합니다.

## Context 유지

Portal 안의 컴포넌트는 `createPortal`을 쓴 위치의 Context를 그대로 읽습니다. DOM에서 `Provider` 밖에 있어도 React 트리에서는 안에 있기 때문입니다.

```jsx
<ThemeContext value="dark">
  <Page />  {/* 안에서 Modal을 createPortal로 렌더 */}
</ThemeContext>
// Modal 안의 useContext(ThemeContext)는 'dark'
```

- 테마, 로케일, 인증 정보 같은 Context가 Modal 안에서도 동작합니다. Portal용 Provider를 따로 만들 필요가 없습니다.
- 반대로 CSS 변수나 `class`로 전달하는 테마는 DOM 상속이라서 끊깁니다. 테마를 CSS 상속으로 처리하면 `body` 아래로 옮긴 Portal에는 적용되지 않을 수 있습니다.
- Context를 두는 위치와 값 설계는 01편에서 다룹니다.

## Portal Container

Portal Container는 Portal 내용을 담을 `domNode`입니다. 가장 간단한 선택은 `document.body`이고, 용도별 전용 컨테이너를 두기도 합니다.

```html
<body>
  <div id="root"></div>
  <div id="modal-root"></div>
</body>
```

```jsx
const container = document.getElementById('modal-root')
createPortal(<Dialog />, container)
```

- `domNode`는 `createPortal`이 호출될 때 이미 존재해야 합니다. 존재하지 않는 노드를 넘기면 동작하지 않습니다.
- 컨테이너는 React가 렌더하는 루트 밖에 있어야 안전합니다. React가 만든 요소를 컨테이너로 넘기면 React의 갱신과 충돌할 수 있습니다.
- 서버 렌더링이나 마운트 이전 시점에는 컨테이너가 없습니다. 마운트 뒤에 찾도록 state에 담습니다.

```jsx
function useContainer(id) {
  const [el, setEl] = useState(null)
  useEffect(() => setEl(document.getElementById(id)), [id])
  return el
}
// el이 null인 동안 Portal을 렌더하지 않음
```

- 용도별로 컨테이너를 나누면(`modal-root`, `toast-root`) 쌓임 순서를 DOM 순서로 관리하기 쉽습니다.
- 컨테이너를 바꾸면 Portal 내용이 새로 만들어져 내부 state가 사라집니다.

## Focus

Portal은 DOM 위치를 옮기므로 포커스 이동 순서와 키보드 접근이 자동으로 맞춰지지 않습니다. Modal이라면 직접 처리해야 합니다. WAI-ARIA 가이드의 Modal 대화상자 패턴은 다음을 요구합니다.

- 열릴 때 포커스를 대화상자 안의 요소로 옮깁니다. 파괴적인 동작이라면 가장 덜 위험한 버튼에 둡니다.
- `Tab`과 `Shift+Tab`은 대화상자 안의 요소만 순환합니다.
- `Esc`는 대화상자를 닫습니다.
- 닫히면 포커스는 대화상자를 연 요소로 돌아갑니다.
- 컨테이너에 `aria-modal="true"`를 쓰고, 제목은 `aria-labelledby` 또는 `aria-label`로 붙입니다. `aria-modal`은 바깥과의 상호작용을 실제로 막고 시각적으로도 가릴 때만 씁니다.

```jsx
function Dialog({ onClose, children }) {
  const ref = useRef(null)
  const opener = useRef(document.activeElement)

  useEffect(() => {
    ref.current.focus()
    return () => opener.current?.focus()
  }, [])
  // ...
}
```

- 위 코드는 열릴 때 안쪽으로 포커스를 옮기고, 닫힐 때 연 요소로 되돌립니다. 대화상자 컨테이너에는 `tabIndex={-1}`이 있어야 `focus()`가 동작합니다.
- 포커스 가두기와 뒷배경 비활성화는 직접 만들기보다 네이티브 `dialog`나 접근성 라이브러리(Radix, React Aria 등)에 맡기는 편이 안전합니다.

**흔한 실수:** 포커스를 옮기지 않아서 키보드 사용자의 포커스가 Modal 뒤의 화면에 그대로 남는 것입니다. Modal이 DOM 끝에 있으면 `Tab` 순서도 뒤쪽에 놓입니다.

## z-index

`z-index`는 같은 쌓임 맥락(stacking context) 안의 요소끼리만 비교됩니다. 부모가 쌓임 맥락을 만들면 자식의 `z-index`가 아무리 커도 그 맥락 밖의 요소 위로 올라가지 못합니다.

- 쌓임 맥락을 만드는 대표적인 속성: `position: fixed`·`sticky`, `z-index`가 있는 `absolute`·`relative`, `opacity`가 1 미만, `transform`·`filter`·`perspective`가 `none`이 아님, `isolation: isolate`, `contain: layout`·`paint`, `will-change`.
- 카드에 `transform`이나 `opacity`를 줬다면 그 안의 Modal은 `z-index: 9999`여도 다른 영역 아래에 깔릴 수 있습니다.
- `transform`이 있는 조상 안의 `position: fixed` 요소는 화면이 아니라 그 조상을 기준으로 배치됩니다.
- Portal로 `body` 직계에 렌더하면 중간 조상의 쌓임 맥락과 `overflow` 잘림을 모두 피합니다. 이것이 Modal과 Tooltip에 Portal을 쓰는 가장 큰 이유입니다.

```css
.modal-root { position: relative; z-index: 1000; }
.toast-root { position: relative; z-index: 1100; }
```

- 컨테이너마다 숫자 하나로 층을 정하고, 앱 전체에서 층 값을 한곳에 모아 관리하면 `9999` 경쟁을 막을 수 있습니다.
- 브라우저의 최상위 레이어(top layer)에 올라가는 요소(`showModal()`의 `dialog`, 팝오버)는 `z-index`와 무관하게 다른 모든 내용 위에 표시됩니다.

## dialog 요소와 Popover API

네이티브 `dialog` 요소와 Popover API는 Portal로 직접 구현하던 Modal·Overlay를 브라우저가 대신 처리합니다. 둘 다 최상위 레이어에 렌더되어 `z-index`와 `overflow` 잘림 문제가 없습니다.

| 항목 | Portal 직접 구현 | `dialog` + `showModal()` | Popover API |
|------|------------------|--------------------------|-------------|
| 최상위 레이어 | 아니오(`z-index` 필요) | 예 | 예 |
| 배경 비활성화 | 직접 구현 | 자동(나머지가 inert) | 없음(항상 비모달) |
| 포커스 관리 | 직접 구현 | 브라우저가 처리 | 직접 처리 |
| Esc로 닫기 | 직접 구현 | 기본 지원 | `auto`에서 지원 |
| 배경 `::backdrop` | 직접 만든 요소 | 지원 | 지원 |
| 적합한 용도 | 정해진 위치·애니메이션 | Modal | 메뉴, 토스트, 선택기 |

- `dialog.showModal()`은 모달로, `dialog.show()`는 비모달로 엽니다. 모달 대화상자는 `Esc`로 닫히고 브라우저가 포커스를 관리합니다. `dialog`는 2022-03부터 모든 주요 브라우저에서 쓸 수 있습니다.
- Popover API는 `popover` 속성과 `popovertarget` 속성으로 선언합니다. `popover="auto"`는 바깥 클릭이나 `Esc`로 닫히는 라이트 디스미스를 지원하고, `"manual"`은 코드로만 닫습니다. Popover API는 2025-01부터 Baseline에 속하지만 일부 기능은 지원 정도가 다릅니다.
- Popover는 항상 비모달이라서 뒷배경을 막으려면 `dialog`를 씁니다.
- React에서 `dialog`는 `ref`로 `showModal()`을 호출하고, 닫힘은 `onClose`나 `onCancel`로 받습니다. `onCancel`·`onClose`는 React에서 버블링됩니다.

```jsx
function NativeModal({ open, onClose, children }) {
  const ref = useRef(null)
  useEffect(() => {
    if (open) ref.current.showModal()
    else ref.current.close()
  }, [open])
  return (
    <dialog ref={ref} onClose={onClose}>{children}</dialog>
  )
}
```

- 네이티브 요소로 충분하면 직접 만든 Portal보다 네이티브가 낫습니다. 다만 단계별 열고 닫는 애니메이션, 기존 디자인 시스템과의 통합, 브라우저 지원 범위 때문에 Portal 기반 구현이 남아 있습니다.
- `dialog`는 `body` 밖으로 옮기지 않아도 최상위 레이어에 놓이므로 대부분 Portal이 필요 없습니다. 다만 부모의 CSS가 `dialog` 스타일에 영향을 줄 수 있어 확인이 필요합니다.

## 핵심 정리

- `createPortal(children, domNode)`는 자식을 다른 DOM 노드 안에 렌더하며, 반환값을 JSX에 넣어 씁니다.
- DOM 위치만 옮기고 React 트리는 그대로여서 이벤트 버블링, Context, state는 React 트리를 따르고 CSS 상속과 선택자는 DOM 트리를 따릅니다.
- Portal의 이벤트는 React 부모까지 올라가므로 필요하면 `stopPropagation`으로 막습니다.
- `domNode`는 호출 시점에 존재해야 하므로 서버나 마운트 전에는 컨테이너를 state로 확보합니다.
- Modal은 열 때 안쪽으로 포커스를 옮기고, 포커스를 가두고, `Esc`로 닫고, 닫으면 연 요소로 되돌려야 합니다.
- `z-index`는 같은 쌓임 맥락 안에서만 비교되므로 Overlay는 `body` 가까이로 옮깁니다. 네이티브 `dialog`와 Popover API는 최상위 레이어로 이 문제를 줄입니다.

<Callout type="info">
  **이번 문서의 목표:** React 코드에서 자주 만나는 타입 문제 열다섯 가지를 직접 타입으로 쓸 수 있고, 타입 에러가 났을 때 어느 쪽을 고쳐야 하는지 판단합니다.
</Callout>

이 문서는 TypeScript의 기본 문법(유니온, 제네릭, `interface`)을 안다고 전제합니다. 타입은 `@types/react` 19.3 기준이고, 파일 확장자는 JSX가 들어 있으면 `.tsx`입니다. 모든 코드는 `strict` 모드를 전제합니다.

## Props 타입

Props 타입은 객체 타입입니다. `type`이든 `interface`든 상관없고, 컴포넌트 매개변수에 직접 붙입니다.

```tsx
type ButtonProps = {
  variant?: 'solid' | 'ghost' // 선택, 리터럴 유니온
  onSelect: (id: number) => void // 콜백
  disabled?: boolean
}

function Button(props: ButtonProps) {
  const { variant = 'solid', disabled } = props
  return <button className={variant} disabled={disabled} />
}
```

- 값이 정해진 문자열은 `string`이 아니라 리터럴 유니온으로 씁니다. 잘못된 값이 컴파일 단계에서 막힙니다.
- 콜백은 `() => void`처럼 매개변수와 반환을 함께 씁니다. 부모가 넘기는 함수의 반환값은 무시되므로 `void`로 충분합니다.
- 기본값은 구조 분해의 기본값(`variant = 'solid'`)으로 줍니다. 19에서는 `defaultProps`·`propTypes` 타입이 `@types/react`에서 제거됐습니다.
- 속성 위에 `/** 설명 */` JSDoc을 달면 에디터 자동완성에 설명이 뜹니다.

**흔한 실수:** `props: any`, 또는 타입이 `object`·`{}`인 Props입니다. 내부 접근은 되지만 호출하는 쪽의 검사가 사라집니다.

## children 타입

`children`이 무엇이든 받으면 `React.ReactNode`로 씁니다.

```tsx
import type { ReactNode } from 'react'

type CardProps = {
  title: string
  icon?: ReactNode // 슬롯 prop도 같은 타입
  children: ReactNode
  footer?: (count: number) => ReactNode // 렌더 prop
}
```

- `ReactNode`는 요소, 문자열, 숫자, 불리언, `null`, `undefined`, 배열(이터러블)을 모두 포함합니다.
- 요소 하나만 받아야 하면 `React.ReactElement`로 좁힙니다. 이때 문자열과 숫자는 거부됩니다.
- `PropsWithChildren<P>`는 `P & { children?: ReactNode }`입니다. 쓸 수 있지만 `children: ReactNode`를 직접 적는 쪽이 의도가 분명합니다.
- 함수를 자식으로 받는 렌더 prop은 `(arg) => ReactNode`로 씁니다.

**흔한 실수:** `children: JSX.Element`로 쓰는 것입니다. `<Card>텍스트</Card>`나 자식이 여러 개인 경우가 모두 에러가 됩니다. 이 타입은 `React.JSX.Element`입니다(아래 "ReactNode·ReactElement·JSX.Element").

## Event 타입

이벤트 객체 타입은 `React.이벤트이름Event<요소타입>` 형태입니다. 인라인으로 쓰면 타입이 추론되고, 핸들러를 밖으로 빼면 직접 적어야 합니다.

```tsx
function Search() {
  const [q, setQ] = useState('')
  // 인라인: e가 자동 추론됨
  // <input onChange={(e) => setQ(e.currentTarget.value)} />

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    setQ(e.currentTarget.value) // string
  }
  return <input value={q} onChange={handleChange} />
}
```

| 이벤트 | 타입 |
|--------|------|
| change | `React.ChangeEvent<HTMLInputElement>` |
| click | `React.MouseEvent<HTMLButtonElement>` |
| keydown | `React.KeyboardEvent<HTMLInputElement>` |
| submit | `React.SubmitEvent<HTMLFormElement>` |
| 위에 없는 이벤트 | `React.SyntheticEvent` (공통 기반) |

- 제네릭 인수는 핸들러를 붙인 요소입니다. `e.currentTarget`이 그 타입이 됩니다.
- `e.target`은 실제로 이벤트가 시작된 요소라서 `EventTarget`입니다. 값을 읽을 때는 `currentTarget`이 안전합니다.
- 핸들러 전체의 타입이 필요하면 `React.ChangeEventHandler<HTMLInputElement>`처럼 `이벤트이름EventHandler`를 씁니다. `useCallback`에 넘길 때 유용합니다.
- 폼은 `FormData`로 값을 읽습니다.

```tsx
function onSubmit(e: React.SubmitEvent<HTMLFormElement>) {
  e.preventDefault()
  const data = new FormData(e.currentTarget)
  const q = data.get('q') // FormDataEntryValue | null
}
// 19의 form action은 FormData를 직접 받는다
// <form action={(formData: FormData) => {}} />
```

**흔한 실수:** `React.FormEvent`를 쓰는 것입니다. `@types/react` 19.3에서 `FormEvent`와 `FormEventHandler`는 deprecated이고, submit에는 `SubmitEvent`를 쓰라고 안내합니다. 변경 이벤트는 `ChangeEvent`입니다.

## State 타입

`useState`는 초깃값에서 타입을 추론합니다. 추론이 부족한 경우에만 제네릭을 직접 씁니다.

```tsx
const [on, setOn] = useState(false) // boolean
type Status = 'idle' | 'loading' | 'done'
const [s, setS] = useState<Status>('idle')
const [user, setUser] = useState<User | null>(null)
const [list, setList] = useState<User[]>([])
```

- 처음에 `null`이나 `undefined`이다가 나중에 채워지는 값은 유니온으로 씁니다. 읽는 쪽에서 널 체크가 강제됩니다.
- 빈 배열은 요소 타입을 알 수 없어 반드시 제네릭을 줍니다.
- 업데이터 함수 `setList((prev) => [...prev, item])`의 `prev`는 State 타입으로 추론됩니다.
- 여러 상태가 서로 묶여 있으면 객체 하나에 유니온으로 모읍니다(아래 "Discriminated Union").

**흔한 실수:** `useState([])`입니다. 타입이 `never[]`가 되어 `setX([1])`이 에러가 납니다. `useState<number[]>([])`로 씁니다. 또 `useState({} as User)`는 비어 있는 객체를 `User`로 속이는 것이라 읽는 코드가 값이 있다고 믿다가 런타임에서 깨집니다. `User | null`로 씁니다.

## Ref 타입

DOM 요소를 가리키는 ref는 요소 타입과 `null` 초깃값을 씁니다.

```tsx
const inputRef = useRef<HTMLInputElement>(null)
inputRef.current?.focus() // current: 요소 또는 null
// <input ref={inputRef} />

const timerRef = useRef<number | undefined>(undefined)
const countRef = useRef(0) // 렌더와 무관한 값 보관
countRef.current += 1
```

- React 19 타입에서 `useRef`는 인수가 필수입니다. 인수 없이 `useRef()`를 쓰면 에러이고 `useRef(undefined)`로 씁니다.
- 19 타입에서는 모든 ref가 변경 가능합니다. `useRef<T>(null)`의 `current`에도 값을 대입할 수 있습니다. 예전의 읽기 전용 ref 구분이 사라졌고, `MutableRef`는 deprecated입니다.
- 마운트 전과 언마운트 후에는 `current`가 `null`이라서 옵셔널 체이닝이 필요합니다.
- 콜백 ref는 `(el) => { ... }`로 씁니다. 19부터 콜백 ref가 정리 함수를 반환할 수 있게 되면서 타입이 반환값을 엄격히 검사하므로, 화살표 함수의 암묵적 반환은 에러입니다.

```tsx
// ❌ 대입식이 암묵적으로 반환됨 (타입 에러)
<div ref={(el) => (instance = el)} />
// ✅ 중괄호로 반환을 막는다
<div ref={(el) => { instance = el }} />
```

- 19에서는 `ref`가 일반 prop입니다. 자식 컴포넌트가 ref를 받게 하려면 Props에 `ref?: Ref<HTMLInputElement>`를 적거나 `ComponentProps<'input'>`을 씁니다(아래 "ComponentProps"). `forwardRef`는 앞으로 deprecated되고 제거될 예정이며 새 코드에서는 쓰지 않습니다(자세히는 03편).

## Context 타입

`createContext`의 제네릭에 값 타입을 쓰고, 기본값이 의미 없으면 `| null`로 둔 뒤 커스텀 훅에서 걸러 냅니다.

```tsx
type ThemeValue = {
  theme: 'light' | 'dark'
  toggle: () => void
}
const ThemeContext = createContext<ThemeValue | null>(null)

function useTheme() {
  const value = useContext(ThemeContext)
  if (value === null) {
    throw new Error('ThemeProvider 안에서만 쓸 수 있습니다')
  }
  return value // ThemeValue (null 제거됨)
}
```

- 이 패턴으로 모든 사용처에서 `null` 체크를 반복하지 않고, Provider를 빼먹으면 즉시 에러가 납니다.
- 기본값이 실제로 쓸 만하면(`createContext<Theme>('system')`) `null`이 필요 없습니다.
- 19에서는 `Context.Provider` 대신 `Context` 자체를 Provider로 씁니다. 타입은 같은 값 타입입니다.
- 쓰기 함수 타입은 `Dispatch<Action>` 또는 `Dispatch<SetStateAction<T>>`입니다(자세히는 01편).

**흔한 실수:** `createContext({} as ThemeValue)`입니다. Provider가 없어도 에러 없이 빈 객체가 들어와 런타임에 깨집니다.

## Reducer Action

Action은 `type`을 판별자로 둔 유니온으로 씁니다. 리듀서의 매개변수에 State와 Action 타입을 적으면 `useReducer`가 나머지를 추론합니다.

```tsx
type State = { items: string[] }
type Action =
  | { type: 'added'; text: string }
  | { type: 'removed'; index: number }
  | { type: 'cleared' }
```

```tsx
function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'added': // action.text 접근 가능
      return { items: [...state.items, action.text] }
    case 'cleared':
      return { items: [] }
    default: // removed가 빠졌으므로 아래 줄이 에러
      const missing: never = action
      return missing
  }
}
```

- 각 `case` 안에서 `action`이 해당 모양으로 좁혀지므로 `action.text`를 안전하게 읽습니다.
- `default`에서 `never`에 대입하면 처리하지 않은 Action이 컴파일 에러가 됩니다(완전성 검사). 위 코드는 `removed`를 처리하지 않아 에러가 나고, 케이스를 추가하면 사라집니다.
- 호출 쪽도 검사됩니다. `dispatch({ type: 'added' })`는 `text`가 빠져서 에러입니다.
- React 19 타입에서는 `useReducer<React.Reducer<State, Action>>(...)`처럼 리듀서 타입 전체를 제네릭으로 넘기는 방식이 제거됐습니다. 제네릭 없이 `useReducer(reducer, initialState)`로 씁니다. 리듀서를 인라인으로 쓸 때는 `(state: State, action: Action) =>`로 매개변수에 타입을 붙입니다.
- 리듀서 설계는 02편을 봅니다.

## Discriminated Union

판별 유니온(discriminated union)은 공통 프로퍼티(판별자)에 리터럴 타입을 두어, 그 값을 검사하면 나머지 프로퍼티의 타입이 좁혀지는 유니온입니다. React에서는 비동기 상태와 모양이 갈리는 Props에 씁니다.

```tsx
type AsyncState<T> =
  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; data: T }

type Props = { state: AsyncState<User[]> }

function UserList({ state }: Props) {
  if (state.status === 'loading') return <Spinner />
  if (state.status === 'error') {
    return <p>{state.error.message}</p>
  }
  return <ul>{state.data.map(renderUser)}</ul> // User[]
}
```

- `isLoading`, `error`, `data`를 각각 선택 속성으로 두면 `data`가 있는데 `error`도 있는 불가능한 조합이 타입으로 허용됩니다. 유니온은 가능한 조합만 남깁니다(자세히는 02편).
- 판별자로 `if`나 `switch`를 쓰면 TypeScript가 분기마다 타입을 좁힙니다.

서로 배타적인 Props도 같은 원리로 씁니다. 반대쪽 속성을 `never`로 막으면 둘을 함께 줄 수 없습니다.

```tsx
type ActionProps =
  | { href: string; onClick?: never } // 링크
  | { href?: never; onClick: () => void } // 버튼
```

**흔한 실수:** 판별자를 `status: string`처럼 넓은 타입으로 쓰는 것입니다. 리터럴이 아니면 값을 검사해도 타입이 좁혀지지 않습니다. 함수가 객체를 반환할 때 반환 타입을 적지 않으면 `'loading'`이 `string`으로 넓어질 수 있으니 반환 타입에 유니온을 적습니다.

## Generic Component

컴포넌트 함수에 타입 매개변수를 붙이면 Props가 서로 연결됩니다. 한 Props에서 정한 타입이 다른 Props로 전파됩니다.

```tsx
type ListProps<T> = {
  items: T[]
  getKey: (item: T) => string | number
  renderItem: (item: T) => ReactNode
}
```

```tsx
function List<T>(props: ListProps<T>) {
  const { items, getKey, renderItem } = props
  return (
    <ul>
      {items.map((item) => (
        <li key={getKey(item)}>{renderItem(item)}</li>
      ))}
    </ul>
  )
}
// items가 User[]이면 renderItem의 인수가 User로 추론된다
```

- 사용하는 쪽은 타입을 적지 않습니다. `items`에서 `T`가 추론되고 `renderItem={(u) => u.name}`의 `u`가 `User`가 됩니다.
- 쓸 수 있는 값을 제한하려면 `T extends string`처럼 제약을 겁니다. 선택지와 값이 일치하는 `Select` 컴포넌트가 대표 예입니다.

```tsx
type SelectProps<T extends string> = {
  options: readonly T[]
  value: T
  onChange: (value: T) => void
}
```

- `.tsx`에서 화살표 함수에 제네릭을 쓰면 `<T>`가 JSX 태그로 읽힙니다. `<T,>` 또는 `<T extends unknown>`으로 씁니다. 그래서 제네릭 컴포넌트는 함수 선언을 쓰는 편이 간단합니다.

**흔한 실수:** 제네릭 컴포넌트를 `React.memo`로 감싸는 것입니다. `memo(List)`의 결과는 `T`를 `unknown`으로 잃어서 `renderItem`의 인수가 `unknown`이 됩니다. 제네릭을 유지하려면 `memo`의 결과를 `typeof List`로 단언해야 하는데, 단언은 컴파일러의 검사를 포기하는 것이라 꼭 필요한 곳에만 씁니다.

## ComponentProps

`ComponentProps<T>`는 HTML 태그 이름이나 컴포넌트에서 Props 타입을 꺼내는 유틸리티입니다. 기존 요소의 속성을 전부 물려받는 래퍼를 만들 때 씁니다.

```tsx
import type { ComponentProps } from 'react'

type FieldProps = ComponentProps<'input'> & {
  label: string
}

function Field({ label, ...rest }: FieldProps) {
  return <label>{label}<input {...rest} /></label>
}
// 컴포넌트에서 추출
type BtnProps = ComponentProps<typeof Button>
```

| 유틸리티 | 결과 |
|----------|------|
| `ComponentProps<T>` | T의 Props 전체 (함수 컴포넌트·태그 이름) |
| `ComponentPropsWithoutRef<T>` | `ref`를 제외한 Props |
| `ComponentPropsWithRef<T>` | `ref`를 포함한 Props |
| `ComponentRef<T>` | T가 가리키는 ref 대상 타입 |

- 19의 `ref`가 일반 prop이 되면서 `ComponentProps<'input'>`에 `ref`가 들어 있습니다. 구조 분해로 `ref`를 꺼내 `input`에 그대로 넘기면 `forwardRef` 없이 ref가 전달됩니다.
- `ref`를 받으면 안 되는 컴포넌트의 Props는 `ComponentPropsWithoutRef`로 `ref`를 제외합니다.
- `ComponentRef<'input'>`은 `HTMLInputElement`입니다. 예전의 `ElementRef`는 deprecated입니다.

**흔한 실수:** 같은 이름의 속성을 교차 타입(`&`)으로 덮어쓰는 것입니다. `input`에는 `size?: number`가 있어서 `& { size: 'sm' | 'lg' }`를 붙이면 두 타입이 교차되어 `size`가 사용할 수 없는 타입이 됩니다. 겹치는 키는 `Omit`으로 먼저 뺍니다.

```tsx
type InputProps = Omit<ComponentProps<'input'>, 'size'> & {
  size: 'sm' | 'lg'
}
```

## Polymorphic Component

폴리모픽 컴포넌트(polymorphic component)는 `as` prop으로 렌더할 태그나 컴포넌트를 바꿀 수 있는 컴포넌트입니다. 타입은 `as`로 받은 대상의 Props를 그대로 허용해야 합니다.

```tsx
type BoxProps<E extends ElementType> = {
  as?: E
  children?: ReactNode
} & Omit<ComponentProps<E>, 'as' | 'children'>

function Box<E extends ElementType = 'div'>(
  { as, children, ...rest }: BoxProps<E>,
) {
  const Tag: ElementType = as ?? 'div'
  return <Tag {...rest}>{children}</Tag>
}
```

```tsx
<Box as="a" href="/x">링크</Box> // ✅ a의 속성 href 허용
<Box as="div" href="/x">텍스트</Box> // ❌ div에는 href가 없음
<Box as={Button} onSelect={fn}>버튼</Box> // ✅ 컴포넌트도 가능
```

- `E`가 `as` 값에서 추론되고, 나머지 Props 타입이 `ComponentProps<E>`로 정해집니다.
- 기본 태그를 `E extends ElementType = 'div'`로 지정해서 `as`를 생략하면 `div`로 취급합니다.
- 구현 안쪽의 `const Tag: ElementType`은 타입 검사를 느슨하게 하는 지점입니다. 바깥 시그니처가 정확하면 사용자에게 보이는 타입은 안전합니다.
- 타입이 복잡해지고 에러 메시지가 읽기 어려워집니다. 변형이 두세 가지뿐이면 `as` 대신 별도 컴포넌트나 `href` 유무로 갈리는 판별 유니온이 단순합니다.

## React.FC를 쓰지 않는 이유

`React.FC`(`FunctionComponent`)는 함수 컴포넌트 전체에 붙이던 타입입니다. 지금은 일반 함수에 Props만 타이핑하는 방식이 표준이고, react.dev의 TypeScript 안내도 이 방식만 씁니다.

```tsx
// ✅ 일반 함수. 반환 타입은 추론
function Greeting({ name }: { name: string }) {
  return <h1>{name}</h1>
}
// 가능하지만 이점이 없음
type Props = { name: string }
const Greeting2: FC<Props> = ({ name }) => <h1>{name}</h1>
```

| 항목 | `React.FC` | 일반 함수 |
|------|------------|-----------|
| 제네릭 컴포넌트 | 불가능 (타입 매개변수를 붙일 수 없음) | 가능 |
| `children` | 자동 포함 안 됨 | 직접 선언 |
| 반환 타입 | `ReactNode` 계열로 고정 | 추론 |
| 정적 속성(`displayName` 등) | 타입 검사 | 별도 처리 |

- `FC`가 필요하던 이유였던 반환 타입 지정과 정적 속성 검사는 일반 함수의 추론으로 충분해서, 현재는 쓸 이유가 거의 없습니다. 커뮤니티 가이드(React TypeScript Cheatsheet)도 필요 없다는 입장입니다.
- 함수 선언에는 `FC`를 붙일 자리가 없으므로 `FC`를 쓰면 화살표 함수 표현식으로 통일해야 하고, 제네릭도 쓸 수 없습니다.
- 기존 코드에 `FC`가 있어도 동작에는 문제가 없습니다. 읽는 법만 알면 됩니다.
- 컴포넌트 자체를 값으로 받는 Props에는 `ComponentType`을 씁니다. 이 경우 컴포넌트 타입 표현이 필요한 것이라 `FC`와 같은 계열의 타입이 정당하게 쓰입니다.

```tsx
type RowProps = {
  icon: ComponentType<{ size: number }> // 컴포넌트를 받음
}
function Row({ icon: Icon }: RowProps) {
  return <Icon size={16} />
}
```

## ReactNode·ReactElement·JSX.Element

세 타입은 포함 범위가 다릅니다. 범위는 `ReactNode`가 가장 넓고 `JSX.Element`가 가장 좁습니다.

| 타입 | 정체 | 쓰는 곳 |
|------|------|---------|
| `ReactNode` | 렌더할 수 있는 모든 값. 요소, 문자열, 숫자, bigint, 불리언, `null`, `undefined`, 이터러블, 포털, Promise | `children`, 슬롯 prop, 렌더 prop 반환 |
| `ReactElement` | `type`, `props`, `key`를 가진 객체. JSX 한 줄의 결과 | 요소 하나만 받을 때, `cloneElement` |
| `React.JSX.Element` | `ReactElement<any, any>`를 확장한 타입. JSX 식 자체의 타입 | 변수·반환값이 JSX 식임을 표시할 때 |

```tsx
const el = <b>x</b> // React.JSX.Element
const nodes: ReactNode[] = ['글자', 3, null, el] // 모두 허용
const one: ReactElement = el // ✅
const bad: ReactElement = '글자' // ❌ 문자열은 요소가 아님
```

- `ReactNode`의 `Promise` 항목은 async 컴포넌트를 위한 것입니다. 함수 컴포넌트 타입의 반환도 `ReactNode`나 `Promise<ReactNode>`입니다.
- 컴포넌트 반환 타입은 적지 않고 추론에 맡기는 것이 기본입니다. 직접 적는다면 `ReactNode`가 맞습니다. TypeScript 5.1부터 `JSX.ElementType` 덕분에 컴포넌트가 `JSX.Element`가 아닌 값(문자열, Promise 등)을 반환해도 유효한 JSX 태그가 됩니다.
- 19 타입에서 전역 `JSX` 네임스페이스가 `React.JSX`로 옮겨졌습니다. 전역 `JSX.Element`로 쓰던 코드는 `React.JSX.Element`로 바꾸거나 반환 타입 표기를 지웁니다.
- 19 타입에서 `ReactElement['props']`의 기본 타입이 `any`에서 `unknown`으로 바뀌었습니다. 요소의 Props를 읽으려면 `ReactElement<{ id: string }>`처럼 타입 인수를 줍니다.

**흔한 실수:** 반환 타입을 `JSX.Element`로 적은 컴포넌트가 조건에 따라 `null`을 반환해 에러가 나는 경우입니다. 반환 타입 표기를 지우거나 `ReactNode`로 바꿉니다.

## as const와 satisfies

`as const`는 값을 리터럴 타입과 `readonly`로 고정하고, `satisfies`는 값이 어떤 타입에 맞는지 검사하되 값의 구체적인 타입을 유지합니다.

```tsx
const TABS = ['home', 'search', 'my'] as const
// readonly ['home', 'search', 'my']
type Tab = (typeof TABS)[number] // 'home' | 'search' | 'my'

const [tab, setTab] = useState<Tab>('home')
// TABS.map으로 버튼을 만들면 값과 타입이 하나의 출처가 된다
```

- `as const` 없이 `const req = { method: 'GET' }`이면 `method`가 `string`으로 넓어집니다. `as const`는 이 넓어짐을 막습니다.
- 객체에 붙이면 모든 프로퍼티가 `readonly` 리터럴이 됩니다.

```tsx
const routes = {
  home: { path: '/', title: '홈' },
  my: { path: '/my', title: '내 정보' },
} satisfies Record<string, { path: string; title: string }>

type RouteKey = keyof typeof routes // 'home' | 'my'
routes.home.title // string (구체 타입 유지)
```

- `satisfies`는 TypeScript 4.9에서 추가됐습니다. 형태를 검사해서 오타나 누락 속성은 에러로 잡습니다.
- 타입 표기(`const routes: Record<string, Route> = ...`)를 쓰면 키가 `string`으로 넓어져서 `keyof`가 `string`이 됩니다. `satisfies`는 키 `'home' | 'my'`를 유지합니다.
- 스타일 객체를 밖으로 뺄 때도 `satisfies React.CSSProperties`로 속성 검사와 자동완성을 받습니다.
- 타입 단언(`as Type`)은 컴파일 시점에만 존재하는 주장이고 런타임 검사가 없습니다. 타입 에러를 끄는 용도로 쓰면 틀린 값이 그대로 흘러갑니다.

**흔한 실수:** `as const`로 만든 배열은 `readonly`라서 `string[]`을 받는 Props에 넘기면 에러입니다. 읽기만 하는 Props는 `readonly string[]`로 받습니다.

## 커스텀 훅 반환 타입

반환값이 둘 이상이면 튜플이나 객체로 돌려줍니다. 튜플은 이름을 호출하는 쪽이 정하고, 객체는 이름이 고정됩니다.

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial)
  const toggle = useCallback(() => setOn((v) => !v), [])
  return [on, toggle] as const // readonly 튜플
}
const [open, toggleOpen] = useToggle()
```

- 튜플은 `as const`가 없으면 `(boolean | (() => void))[]`로 추론되어 `toggleOpen()`을 호출할 때 에러가 납니다. `as const`를 붙이거나 반환 타입을 적습니다.
- 값이 셋 이상이거나 순서가 의미 없으면 객체가 읽기 좋습니다. 객체는 `as const`가 필요 없습니다.
- 여러 프로젝트에서 공유하는 훅은 반환 타입을 직접 적어 두는 편이 안전합니다. 구현을 고쳐도 공개 타입이 의도치 않게 변하지 않습니다.
- 값과 setter를 돌려주는 제네릭 훅은 `useState`의 setter 타입을 그대로 씁니다.

```tsx
function useLocalStorage<T>(
  key: string,
  initial: T,
): [T, Dispatch<SetStateAction<T>>] {
  // ...useState<T>와 저장 로직
}
const [count, setCount] = useLocalStorage('count', 0)
setCount((prev) => prev + 1) // 업데이터 함수 가능
```

- 훅의 반환 타입을 다른 곳에서 쓰고 싶으면 `ReturnType<typeof useToggle>`로 꺼냅니다.
- 비동기 훅은 반환 타입을 판별 유니온(`AsyncState<T>`)으로 두면 `data`가 없는 상태에서 `data`를 읽는 실수가 막힙니다.

## 핵심 정리

- Props는 객체 타입으로 쓰고, 값이 정해진 문자열은 리터럴 유니온, 슬롯과 `children`은 `ReactNode`로 받습니다. 이벤트는 `React.이벤트Event<요소>`이며 submit에는 `SubmitEvent`를 씁니다.
- `useState`의 빈 배열과 `null` 초깃값, `createContext`의 `null` 기본값은 제네릭으로 타입을 주고, Context는 커스텀 훅에서 `null`을 걸러 냅니다. 19 타입의 `useRef`는 인수가 필수이고 모든 ref가 변경 가능합니다.
- Reducer Action과 비동기 상태는 판별 유니온으로 쓰고, `default`의 `never` 대입으로 누락을 잡습니다. 불가능한 상태 조합이 타입에서 사라집니다.
- 제네릭 컴포넌트와 `ComponentProps`는 Props를 연결하고 물려받는 도구이며, 겹치는 키는 `Omit`으로 뺍니다. `React.memo`는 제네릭을 잃습니다.
- `React.FC`는 필요 없습니다. 일반 함수에 Props만 타이핑합니다. 컴포넌트를 값으로 받을 때만 `ComponentType`을 씁니다.
- `as const`는 값을 리터럴로 고정하고 `satisfies`는 형태 검사와 구체 타입 유지를 함께 합니다. 튜플 반환 훅에는 `as const`를 붙입니다.

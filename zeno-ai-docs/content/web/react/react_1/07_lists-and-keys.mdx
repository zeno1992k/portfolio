## map

React에는 반복 전용 문법이 없습니다. 배열의 `map`으로 각 데이터를 JSX로 바꾼 배열을 만들어 중괄호 안에 넣으면, React가 그 배열의 요소를 차례로 그립니다.

```jsx
const people = ['Kim', 'Lee', 'Park']

function List() {
  return (
    <ul>
      {people.map((name) => <li key={name}>{name}</li>)}
    </ul>
  )
}
```

- `map`은 새 배열을 반환하고 원본은 바꾸지 않습니다(배열 메서드는 JavaScript 28편).
- 데이터가 객체이면 필요한 프로퍼티를 꺼내 JSX로 바꿉니다.

```jsx
{users.map((user) => (
  <li key={user.id}>{user.name}</li>
))}
```

- 화살표 함수 본문에 중괄호를 쓰면 `return`이 필요합니다. 빼먹으면 `undefined`가 반환되어 아무것도 그려지지 않습니다.

```jsx
users.map((u) => <li>{u.name}</li>)           // ✅ 암시적 반환
users.map((u) => { return <li>{u.name}</li> }) // ✅
users.map((u) => { <li>{u.name}</li> })        // ❌ 반환 없음
```

- `for` 문으로 JSX를 만들어 push해도 되지만, 대부분 `map`이 더 짧습니다.
- 반복 결과를 변수에 먼저 담아 두면 JSX가 짧아집니다. `const items = users.map(...)` 후 `<ul>{items}</ul>`로 씁니다.

## key

리스트의 각 요소에는 `key`를 줍니다. key는 React가 배열의 각 요소가 데이터의 어느 항목에 해당하는지 구분하기 위한 표식입니다.

```jsx
<li key={person.id}>{person.name}</li>
```

- `map` 안에서 반환하는 가장 바깥 엘리먼트에 붙입니다. 안쪽의 자식에 붙이면 효과가 없습니다.
- key가 없으면 개발 모드의 콘솔에 "Each child in a list should have a unique key prop." 경고가 나옵니다.
- key는 파일 이름과 같습니다. 파일 순서가 바뀌어도 이름으로 파일을 가리킬 수 있습니다. key가 있으면 항목이 추가·삭제·재정렬되어 위치가 달라져도 React는 어느 항목인지 알아보고, 그 항목에 딸린 state와 DOM을 그대로 이어 붙입니다.
- key를 주지 않으면 React는 배열의 순서(index)를 key로 씁니다. 순서가 바뀌지 않는 목록은 문제가 없지만, 순서가 바뀌면 문제가 됩니다(아래 "index key의 문제").
- 컴포넌트는 key를 prop으로 받지 못합니다. React가 내부에서 쓰는 힌트일 뿐입니다. 컴포넌트가 같은 값을 필요로 하면 다른 이름의 prop으로 따로 넘깁니다.

```jsx
<Profile key={id} userId={id} />
// Profile 안에서 props.key는 없다. props.userId를 쓴다
```

- key는 리스트에만 쓰는 것이 아닙니다. 같은 위치에서 컴포넌트를 구분하려고 key를 바꾸면 state를 초기화할 수 있습니다(자세히는 13편).
- 비교 알고리즘에서 key가 하는 일은 17편에서 다룹니다.

## 안정적인 key

좋은 key는 두 가지를 만족합니다. 형제 사이에서 유일하고, 같은 데이터 항목이면 렌더링마다 같은 값입니다.

| 데이터 출처 | key로 쓸 값 |
|-------------|-------------|
| 서버·데이터베이스 | 레코드의 id |
| 브라우저에서 만든 데이터 | 항목을 만들 때 한 번 붙인 id (증가하는 카운터, `crypto.randomUUID()`, `uuid` 패키지 등) |
| 중복 없는 문자열 목록 | 그 문자열 자체 |

공식 문서가 정리한 규칙입니다.

- key는 **형제 사이에서 유일**해야 합니다. 서로 다른 배열에서는 같은 key를 써도 됩니다.
- key는 **바뀌면 안 됩니다.** 렌더링 중에 만들지 않습니다.

```jsx
function handleAdd(text) {
  const item = { id: crypto.randomUUID(), text } // 만들 때 한 번
  setItems([...items, item])
}
```

- id는 항목을 만드는 시점(이벤트 핸들러)에 한 번 붙여서 데이터에 저장합니다. 렌더링 안에서 만들면 매번 달라져 key가 안정적이지 않습니다.
- key는 문자열로 변환되어 비교됩니다. `1`과 `'1'`은 같은 key입니다.
- 데이터에 마땅한 id가 없다면 항목을 추가하는 코드에서 id를 만들어 붙이는 것이 해결입니다. 렌더링 시점에 index나 임의 값으로 대신하는 것은 해결이 아닙니다.
- 같은 형제 안에서 key가 중복되면 개발 모드에서 경고가 나오고, 항목이 중복되거나 누락되는 문제가 생길 수 있습니다.

## index key의 문제

배열의 index를 key로 쓰면 항목이 아니라 자리에 key가 붙습니다. 그래서 항목의 순서가 바뀌거나 중간에 추가·삭제되면, 데이터와 state의 짝이 어긋납니다.

```jsx
{contacts.map((c, i) => (
  <li key={i}>
    <Contact contact={c} />   {/* 안에 state가 있다 */}
  </li>
))}
```

- 목록을 뒤집거나 맨 앞에 항목을 추가하면, index 0의 자리에는 다른 데이터가 오지만 key 0은 그대로입니다. React는 "같은 항목"으로 보고 state를 이어 붙입니다. 결과적으로 첫 항목에서 펼쳐 둔 상태가 다른 사람의 항목에 나타납니다.
- 문제가 눈에 띄는 것은 항목 안에 state가 있는 경우(펼침, 입력값, 체크, 포커스)입니다. 텍스트만 그리는 정적 항목은 증상이 약해서 버그를 놓치기 쉽습니다.
- 입력 필드가 있는 항목에서 증상이 두드러집니다. 첫 번째 항목을 삭제했는데 입력창에는 이전 항목의 글자가 남아 있는 식입니다.

```jsx
// ❌ 순서가 바뀔 수 있는 목록
<li key={i}>
// ✅ 항목의 id
<li key={c.id}>
```

- index를 key로 써도 되는 경우는 목록이 고정이고 순서 변경·삽입·삭제가 없으며 항목에 state가 없을 때뿐입니다. 공식 문서는 index를 key로 쓰지 말라고 안내합니다.
- `Math.random()`을 key로 쓰는 것은 더 나쁩니다. 렌더링마다 key가 달라져서 모든 항목이 새 항목으로 취급되고, 모든 컴포넌트와 DOM이 매번 다시 만들어집니다. state와 포커스도 매번 사라집니다.

## filter + map

일부 항목만 그릴 때는 `filter`로 걸러낸 뒤 `map`으로 그립니다.

```jsx
const chemists = people.filter((p) => p.job === 'chemist')

const items = chemists.map((p) => (
  <li key={p.id}>{p.name}</li>
))
```

- `filter`는 조건에 맞는 요소만 담은 새 배열을 반환하고, 원본은 그대로입니다. 원본은 모든 항목을 가진 채로 두고, 보여 줄 때만 걸러냅니다.
- 검색어, 탭, 완료 여부처럼 화면 조건에 따라 달라지는 목록은 걸러진 결과를 state로 따로 저장하지 않습니다. 원본 배열과 조건만 state로 두고 렌더링 중에 계산합니다(자세히는 12편).
- `filter` 결과가 빈 배열이면 아무것도 그려지지 않으므로, 빈 목록 안내가 필요하면 조건으로 분기합니다(자세히는 06편).
- 항목을 걸러낸 뒤에도 key는 원본 데이터의 id를 그대로 씁니다. 걸러진 결과의 index를 key로 쓰지 않습니다.
- 변환이 필요한 경우 `map` 안에서 조건 분기를 해도 되지만, 걸러내는 쪽이 의도가 분명합니다. `map`이 조건으로 `null`을 반환하면 key가 필요한 배열에 `null`이 섞입니다.

## 리스트 추가

state에 담긴 배열은 `push`로 고치지 않고, 새 요소를 포함한 새 배열을 만들어 setter에 넘깁니다(자세히는 11편).

```jsx
setItems([...items, newItem])           // 끝에 추가
setItems([newItem, ...items])           // 맨 앞에 추가
setItems([
  ...items.slice(0, index),             // 중간에 삽입
  newItem,
  ...items.slice(index),
])
```

- 원본을 바꾸면 React가 state가 바뀐 것을 알아채지 못해 화면이 갱신되지 않을 수 있고, 이전 렌더링의 값까지 오염됩니다.
- 새 항목에는 id를 붙입니다. 이 id가 key가 됩니다(위 "안정적인 key").
- 추가된 항목은 key가 새 값이라 React가 새로 만들고, 기존 항목은 key가 같아 그대로 유지됩니다. 그래서 맨 앞에 추가해도 기존 항목의 state가 어긋나지 않습니다. index key였다면 어긋납니다.

## 리스트 삭제

`filter`로 지울 항목만 뺀 새 배열을 만듭니다.

```jsx
function handleDelete(id) {
  setItems(items.filter((item) => item.id !== id))
}
```

- `splice`, `pop`, `shift`는 원본을 바꾸므로 쓰지 않습니다.
- 삭제 버튼에 인자를 전달하는 방법은 `onClick={() => handleDelete(item.id)}`입니다(자세히는 08편).
- 이전 state를 기반으로 연속해서 바꿀 때는 updater 함수 형태가 안전합니다(자세히는 10편).

```jsx
setItems((prev) => prev.filter((item) => item.id !== id))
```

## 리스트 수정

바꿀 항목만 새 객체로 교체하고, 나머지는 그대로 둔 새 배열을 `map`으로 만듭니다.

```jsx
setTodos(todos.map((todo) =>
  todo.id === id
    ? { ...todo, done: !todo.done }
    : todo
))
```

- `arr[i] = x`, `item.done = true`는 원본을 바꾸는 변경이라서 쓰지 않습니다.
- 항목을 복사해서 새 객체를 만드는 것을 빼먹지 않아야 합니다. 배열만 복사하고 안의 객체를 직접 바꾸면 원본이 함께 바뀝니다. 스프레드는 얕은 복사라서 안의 객체는 공유되기 때문입니다(자세히는 JavaScript 36편).

```jsx
const next = [...items]
next[0].done = true   // ❌ items[0]도 바뀐다
setItems(next)
```

- 안쪽이 깊은 구조라면 Immer가 복사를 대신해 줍니다(자세히는 11편).

## 정렬

`sort`와 `reverse`는 원본 배열을 바꿉니다. state나 props로 받은 배열에 직접 쓰면 안 되므로, 복사본을 만들어 정렬합니다.

```jsx
const sorted = [...items].sort((a, b) => a.price - b.price)

const sorted2 = items.toSorted((a, b) => a.price - b.price)
const reversed = items.toReversed()
```

- `toSorted`, `toReversed`는 ES2023에 추가된 메서드로 원본을 바꾸지 않습니다(자세히는 JavaScript 28편). 지원하지 않는 환경이면 `[...items]`로 복사한 뒤 `sort`합니다.
- 정렬은 두 방식이 있습니다. 화면 조건(정렬 기준)만 state로 두고 렌더링 중에 정렬된 복사본을 계산하는 방식이 단순합니다. 정렬 결과를 state에 저장하면 원본과 어긋날 수 있습니다.
- 정렬해도 key는 항목의 id 그대로입니다. 순서만 바뀌고 key는 같으니, React는 DOM을 재생성하지 않고 이동시킵니다.
- 비교 함수 없이 `sort()`를 쓰면 요소를 문자열로 바꿔 비교합니다. 숫자는 비교 함수가 필요합니다(자세히는 JavaScript 28편).

```jsx
[10, 9, 1].sort()                  // [1, 10, 9]
[10, 9, 1].sort((a, b) => a - b)   // [1, 9, 10]
```

## 중첩 리스트

배열 안에 배열이 있으면 `map` 안에서 다시 `map`을 씁니다. key는 각 배열의 형제 사이에서만 유일하면 됩니다.

```jsx
{categories.map((cat) => (
  <section key={cat.id}>
    <h2>{cat.name}</h2>
    <ul>
      {cat.items.map((item) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  </section>
))}
```

- 안쪽 리스트의 key는 바깥 리스트의 key와 겹쳐도 됩니다. 비교는 같은 부모 배열 안의 형제끼리만 하기 때문입니다.
- 중첩이 깊어지면 안쪽 `map`을 별도 컴포넌트로 뺍니다. 컴포넌트로 나눌 때 `key`는 `map` 안에서 쓰는 쪽(바깥)에 둡니다.

```jsx
{categories.map((cat) => (
  <Category key={cat.id} category={cat} />
))}
```

- 컴포넌트 안에서 반복하는 가장 바깥 엘리먼트가 `<Category>`이므로 key는 거기에 붙입니다. `Category` 함수 안의 `<section>`에 붙이지 않습니다.

## Fragment와 key

리스트 항목 하나가 DOM 요소 여러 개를 그려야 하면 `<Fragment>`로 감쌉니다. 짧은 문법 `<>...</>`에는 key를 줄 수 없으므로 `Fragment`를 명시해서 씁니다.

```jsx
import { Fragment } from 'react'

{posts.map((post) => (
  <Fragment key={post.id}>
    <h2>{post.title}</h2>
    <p>{post.body}</p>
  </Fragment>
))}
```

- Fragment는 DOM에 나타나지 않으므로 `h2`와 `p`가 같은 레벨에 나열됩니다. 불필요한 `div`를 늘리지 않을 때 씁니다.
- 짧은 문법에 key를 쓰려고 하면 에러입니다.
- 정의 리스트(`dl`)의 `dt`와 `dd`, 표의 `tr` 쌍처럼 부모가 자식 구조를 정해 두어 `div`로 감쌀 수 없을 때 필요합니다.
- Fragment의 `ref`(Fragment Ref)는 Canary 전용입니다. 작성 시점에 react.dev는 이를 React 19.3.0-canary에 있는 기능으로 표기하고 있고, 안정판 19.2에서는 쓸 수 없습니다.

## key의 유효 범위

key는 같은 부모 배열 안의 형제 사이에서만 의미가 있습니다. 전체 앱에서 유일할 필요는 없습니다.

```jsx
<ul>
  {tasks.map((t) => <li key={t.id}>{t.title}</li>)}
</ul>
<ul>
  {notes.map((n) => <li key={n.id}>{n.title}</li>)}
</ul>
// tasks의 id 3과 notes의 id 3이 같아도 된다
```

- 한 배열 안에서는 중복되면 안 됩니다. 서로 다른 종류를 한 배열로 합친다면 종류를 key에 붙여 구분합니다(`'task-3'`, `'note-3'`).
- 리스트 항목이 배열 밖의 고정 자식과 섞여 있어도, 배열 안의 요소끼리 key를 구분하면 됩니다.
- key는 `map`이 만든 배열의 요소에 붙입니다. `map` 바깥에서 컴포넌트에 key를 줘서 state를 초기화하는 것은 별개의 용법입니다.

## 렌더 중 key를 생성하면 안 되는 이유

key는 렌더링 사이에서 같은 항목을 같은 값으로 가리켜야 의미가 있습니다. 렌더링 중에 만든 key는 렌더링마다 달라집니다.

```jsx
// ❌ 매 렌더링마다 새 key
<li key={Math.random()}>
<li key={crypto.randomUUID()}>
<li key={Date.now()}>
```

- React는 이전 렌더링의 key와 비교해서 같은 key이면 컴포넌트와 DOM을 재사용합니다. key가 매번 다르면 비교할 짝이 없으므로 이전 항목을 모두 지우고 새로 만듭니다.
- 이 때문에 항목 안의 state가 사라지고, 입력창은 포커스를 잃으며, 이미지·애니메이션이 처음부터 다시 시작되고, 성능도 떨어집니다.
- 렌더링 함수는 같은 입력에 같은 결과를 내야 합니다. 렌더링 중에 난수나 시각을 읽는 것은 이 규칙에도 어긋납니다(자세히는 04편).
- 해결은 id를 데이터에 저장하는 것입니다. 항목을 만드는 이벤트 핸들러에서 한 번 만들어 항목에 넣어 두면, 이후 렌더링에서는 항상 같은 값을 읽습니다.

## 핵심 정리

- 리스트는 배열의 `map`으로 JSX 배열을 만들어 그리고, 일부만 그릴 때는 `filter`로 걸러낸 뒤 `map`합니다.
- key는 `map` 안의 가장 바깥 엘리먼트에 붙이는 항목의 식별자이며, 컴포넌트는 key를 prop으로 받지 못합니다.
- key는 형제 사이에서 유일하고 바뀌지 않아야 하므로 데이터의 id를 쓰고, id는 항목을 만드는 시점에 한 번 붙입니다.
- index key와 렌더 중 생성한 key(`Math.random()`)는 순서가 바뀔 때 state가 어긋나거나 항목이 매번 다시 만들어지는 문제를 일으킵니다.
- 추가는 스프레드, 삭제는 `filter`, 수정은 `map`, 정렬은 복사본에서 하며 원본 배열을 직접 바꾸지 않습니다.
- 항목 하나가 여러 DOM 노드를 그리면 `Fragment`에 key를 주고, 중첩 리스트의 key는 같은 부모 배열의 형제 사이에서만 유일하면 됩니다.

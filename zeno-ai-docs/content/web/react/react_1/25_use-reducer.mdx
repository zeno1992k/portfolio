## useReducer

`useReducer`는 State와 그 State를 바꾸는 `dispatch` 함수를 돌려주는 Hook입니다. State를 바꾸는 로직을 컴포넌트 밖의 `reducer` 함수 한 곳에 모읍니다. 이벤트 핸들러가 여러 개이고 State 갱신 방식이 복잡할 때 씁니다.

```jsx
const [state, dispatch] =
  useReducer(reducer, initialArg, init?)
```

| 인수 | 뜻 |
|------|----|
| `reducer` | 현재 State와 action을 받아 다음 State를 돌려주는 순수 함수 |
| `initialArg` | 초기 State를 정하는 값 |
| `init` | 선택. 있으면 초기 State는 `init(initialArg)` |

- 돌려주는 값은 정확히 두 개입니다. 현재 State와 `dispatch` 함수입니다.
- `useState`와 같은 Hook이므로 컴포넌트 최상위에서 호출합니다(자세히는 26편).

```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'incremented':
      return { count: state.count + 1 }
    default:
      throw Error('Unknown action: ' + action.type)
  }
}
```

```jsx
const init = { count: 0 }

function Counter() {
  const [state, dispatch] = useReducer(reducer, init)
  const add = () => dispatch({ type: 'incremented' })
  return <button onClick={add}>{state.count}</button>
}
```

- 클릭하면 `dispatch`가 action을 보내고, React가 현재 State와 action을 reducer에 넘겨 다음 State를 받습니다. 그 값으로 다시 렌더링합니다.
- `dispatch`는 값을 돌려주지 않습니다.

## reducer

reducer는 `(state, action) => nextState` 모양의 함수입니다. 현재 State에 action을 적용한 결과를 새 State로 돌려줍니다. 이름은 배열의 `reduce`에서 왔습니다. 이전 결과와 값 하나를 받아 새 결과를 만드는 구조가 같습니다.

```jsx
function tasksReducer(tasks, action) {
  switch (action.type) {
    case 'added':
      return [
        ...tasks,
        { id: action.id, text: action.text },
      ]
    case 'deleted':
      return tasks.filter((t) => t.id !== action.id)
    default:
      throw Error('Unknown action: ' + action.type)
  }
}
```

- 컴포넌트 밖에 정의합니다. 컴포넌트 안에 두면 렌더링마다 새로 만들어질 뿐 얻는 것이 없습니다.
- State의 모양은 자유입니다. 숫자, 객체, 배열 모두 됩니다.
- `switch`로 action type을 나누는 것이 관례입니다. `case` 안에서 변수를 선언하면 다른 `case`와 이름이 겹칠 수 있어 `case`마다 중괄호로 감쌉니다.
- `default`에서는 에러를 던집니다. 오타 난 action이 조용히 무시되는 것을 막습니다.
- 모든 경로에서 값을 반환해야 합니다. `return`을 빠뜨리면 State가 `undefined`가 됩니다.

```jsx
case 'renamed': {
  const trimmed = action.name.trim()
  return { ...state, name: trimmed }
}
```

## action

action은 "무슨 일이 일어났는가"를 담은 객체입니다. 관례로 `type` 프로퍼티를 가지고, 필요한 정보를 다른 프로퍼티에 담습니다. 실제로는 어떤 값이든 action이 될 수 있습니다.

```jsx
dispatch({ type: 'added', id: 3, text: 'Buy milk' })
dispatch({ type: 'deleted', id: 3 })
```

- action은 "State를 이렇게 바꿔라"가 아니라 "사용자가 이것을 했다"를 설명합니다. 어떻게 바꿀지는 reducer가 정합니다.
- 사용자 동작 하나는 action 하나로 표현합니다. 입력 세 개를 비우는 "폼 초기화"는 `dispatch({ type: 'reset_form' })` 한 번이지, 필드마다 따로 보내는 action 세 번이 아닙니다.

```jsx
// ❌ 한 동작에 action 세 개
dispatch({ type: 'set_name', value: '' })
dispatch({ type: 'set_email', value: '' })
dispatch({ type: 'set_age', value: '' })
// ✅ 동작 하나에 action 하나
dispatch({ type: 'reset_form' })
```

## dispatch

`dispatch(action)`은 action을 reducer에 전달해 State 갱신을 예약하는 함수입니다. 인수는 action 하나뿐입니다.

- 호출하는 즉시 State가 바뀌지 않습니다. 현재 렌더링의 State는 스냅샷이어서, 호출 직후에 읽어도 이전 값입니다(자세히는 10편).

```jsx
function handleClick() {
  console.log(state.age)            // 42
  dispatch({ type: 'incremented_age' })
  console.log(state.age)            // 여전히 42
}
```

- 이벤트 핸들러가 모두 끝난 뒤 한 번에 화면을 갱신합니다. `useState`의 Setter와 같은 배칭이 적용됩니다.
- reducer가 이전과 `Object.is`로 같은 값을 돌려주면 React는 자식 렌더링과 Effect 실행을 건너뜁니다.
- 다음 State를 미리 확인하고 싶으면 reducer를 직접 호출합니다.

```jsx
const nextState = reducer(state, action)
console.log(nextState)
```

**흔한 실수:** 이벤트 핸들러를 넘기지 않고 호출해 버리는 것입니다. 렌더링 중에 `dispatch`가 실행되어 렌더, dispatch, 렌더가 끝없이 반복되고 "Too many re-renders" 에러가 납니다.

```jsx
<button onClick={handleClick()}>Add</button> // ❌ 렌더 중 호출
<button onClick={handleClick}>Add</button>   // ✅
```

## initialState

초기 State는 `useReducer`의 두 번째 인수 `initialArg`로 정합니다. 처음 마운트될 때만 쓰이고 이후 렌더링에서는 무시됩니다.

```jsx
const initialState = { name: 'Taylor', age: 42 }

function Form() {
  const [state, dispatch] = useReducer(
    reducer,
    initialState,
  )
  // ...
}
```

- 상수를 컴포넌트 밖에 두면 reducer와 테스트에서도 같은 값을 재사용하기 쉽습니다.
- `initialArg`가 바뀌어도 State는 다시 초기화되지 않습니다. 새 값으로 되돌리려면 `key`로 컴포넌트를 새로 만들거나(자세히는 13편) reset action을 보냅니다.

### 초기화 함수(init)

초기 State를 계산해야 하면 세 번째 인수로 함수를 넘깁니다. React는 `init(initialArg)`의 결과를 초기 State로 씁니다. 이 함수는 마운트 때 한 번만 실행됩니다.

```jsx
function createInitialState(username) {
  const items = []
  for (let i = 0; i < 50; i++) {
    items.push({ id: i, text: username + ' ' + (i + 1) })
  }
  return { items, text: '' }
}

const [state, dispatch] = useReducer(
  reducer,
  username,
  createInitialState, // ✅ 함수 자체를 전달
)
```

- `createInitialState(username)`처럼 호출한 결과를 두 번째 인수에 넣으면, 초기 State는 처음 한 번만 쓰이는데도 매 렌더링마다 함수가 실행됩니다.

```jsx
// ❌ 렌더링마다 호출됨
useReducer(reducer, createInitialState(username))
```

- `init` 함수는 `reducer`처럼 순수해야 하고, 인수는 `initialArg` 하나만 받습니다.
- reset action에서도 같은 함수를 재사용할 수 있습니다.

```jsx
case 'reset':
  return createInitialState(action.username)
```

## Pure Reducer

reducer는 순수 함수여야 합니다. 같은 `state`와 `action`을 넣으면 항상 같은 결과를 돌려주고, 계산 말고는 아무것도 하지 않습니다(순수 함수 일반은 04편).

- State를 직접 변경하지 않고 새 객체나 배열을 돌려줍니다.
- 네트워크 요청, 타이머, `Math.random()`, `Date.now()`, DOM 접근을 하지 않습니다.
- 다른 State를 바꾸거나 `dispatch`를 부르지 않습니다.

```jsx
// ❌ 같은 객체를 변경해 반환
function reducer(state, action) {
  state.age = state.age + 1
  return state
}
// ✅ 새 객체를 반환
function reducer(state, action) {
  return { ...state, age: state.age + 1 }
}
```

- 변경한 객체를 그대로 돌려주면 `Object.is`로 같은 값이라 React가 변경이 없다고 판단해 화면이 갱신되지 않습니다. 새 State를 만드는 방법은 11편과 같습니다.
- Strict Mode의 개발 환경에서는 React가 reducer와 `init` 함수를 두 번씩 호출해 순수하지 않은 코드를 드러냅니다. 순수하면 두 번 호출해도 결과가 같아 문제가 없고, 프로덕션에서는 두 번 호출하지 않습니다(자세히는 18편).
- 부수 효과가 필요하면 이벤트 핸들러에서 하고, 결과를 action으로 보냅니다.

```jsx
async function handleSave() {
  const saved = await saveTask(draft)       // 부수 효과는 핸들러에서
  dispatch({ type: 'saved', task: saved })  // reducer는 반영만
}
```

- State가 깊게 중첩되면 `use-immer`의 `useImmerReducer`로 reducer 안에서 변경하는 문법을 쓸 수 있습니다. 외부 라이브러리이며 React에 내장되어 있지 않습니다(자세히는 11편).

**흔한 실수:** 의도치 않게 State를 변경하는 `push`, `splice`, `sort`, `reverse`를 reducer 안에서 State에 직접 쓰는 것입니다. 복사본에 하거나 `map`, `filter`, 복사형 메서드를 씁니다.

## Action Type

`type`은 어떤 일이 일어났는지 이름 붙인 문자열입니다. reducer는 `type`으로 갱신 방식을 고릅니다.

- 문자열이면 무엇이든 되지만, 사용자 관점에서 일어난 일을 과거형이나 이벤트 이름으로 씁니다. `'added'`, `'changed_name'`, `'deleted'`처럼 구체적이어야 합니다.
- `'set_count'`처럼 "State를 이렇게 만들어라"를 뜻하는 이름은 reducer의 의미를 없앱니다. 일어난 일을 이름에 담습니다.

| 이름 | 평가 |
|------|------|
| `'incremented_age'` | ✅ 일어난 일을 설명 |
| `'added'` | ✅ 컴포넌트 안에서 의미가 분명하면 충분 |
| `'set_state'` | ❌ 갱신 방법을 지시. 정보가 없다 |

- 오타를 막고 자동 완성을 받으려면 상수로 두거나 TypeScript의 유니온 타입으로 표현할 수 있습니다. 필수는 아닙니다.
- 모르는 `type`은 `default`에서 에러로 처리합니다. 오타를 가장 빨리 찾는 방법입니다.

```jsx
const ADDED = 'added'
dispatch({ type: ADDED, text })
```

## Payload

payload는 action에 실어 보내는 부가 정보입니다. React는 payload라는 이름을 요구하지 않습니다. `type` 외의 프로퍼티는 모양이 자유이므로 필요한 정보를 이름 붙여 담습니다.

```jsx
dispatch({ type: 'added', id: nextId++, text })
dispatch({ type: 'changed_name', nextName: e.target.value })
```

- reducer는 `action.text`, `action.nextName`처럼 읽습니다.
- Redux 관례처럼 `{ type, payload }` 한 필드에 모으는 방식도 쓰이지만 React 공식 예제는 프로퍼티를 펼쳐 씁니다. 한 프로젝트 안에서 통일합니다.
- 사건을 재현하는 데 필요한 최소한의 정보만 담습니다. 예를 들어 삭제는 `id`면 충분하고 객체 전체를 보낼 필요가 없습니다.
- `Date.now()`나 랜덤 id는 reducer 안에서 만들면 순수성이 깨집니다. 핸들러에서 만들어 payload로 보냅니다.

**흔한 실수:** 갱신 후의 State 전체를 payload로 보내는 것입니다. 그러면 reducer가 하는 일이 없고, 현재 State와 어긋날 위험만 생깁니다. 이벤트 정보만 보냅니다.

## useState와 비교

둘 다 State를 만드는 Hook이고 한 컴포넌트에 섞어 써도 됩니다. 차이는 갱신 로직을 어디에 두느냐입니다.

| 항목 | `useState` | `useReducer` |
|------|-----------|--------------|
| 코드 양 | 처음에는 적다 | 처음에는 reducer를 써야 해서 많다 |
| 갱신 로직 위치 | 이벤트 핸들러마다 흩어짐 | reducer 한 곳 |
| 가독성 | 단순한 갱신은 쉽다. 복잡해지면 컴포넌트가 커진다 | 무슨 일이 일어났는지와 어떻게 바뀌는지가 분리됨 |
| 디버깅 | State가 잘못 바뀐 지점을 찾기 어렵다 | reducer에 로그를 넣으면 모든 변경과 원인 action이 보인다 |
| 테스트 | 컴포넌트를 통해야 한다 | 순수 함수라 reducer만 따로 테스트한다 |

- 공식 문서의 권고는 State 갱신 버그가 잦거나 코드에 구조를 주고 싶을 때 reducer로 옮기라는 것입니다. 모든 State에 쓰라는 것이 아닙니다.
- 기준은 이렇습니다. 값 하나나 서로 독립인 몇 개, 갱신이 단순하면 `useState`. 여러 State가 같이 바뀌고 핸들러가 여러 군데에서 같은 State를 건드리면 `useReducer`.
- 다음 State가 이전 State에 의존하는 규칙이 많을수록 reducer가 유리합니다.
- `useState`로 쓴 코드를 reducer로 옮기는 순서는 세 단계입니다.

```jsx
// 1. setTasks 호출을 action 전달로 바꾼다
dispatch({ type: 'added', id: nextId++, text })
// 2. State 갱신 로직을 reducer로 옮긴다 (tasksReducer)
// 3. useState를 useReducer로 바꾼다
const [tasks, dispatch] = useReducer(tasksReducer, initial)
```

- 단점도 있습니다. 간단한 State에는 reducer가 불필요한 의식이 됩니다. 한 줄이면 되는 갱신에 `type` 문자열과 `switch`를 만들 필요가 없습니다.
- `useReducer`는 `useState` 위에 얹은 별개 기능이 아니라 같은 State 갱신 모델의 다른 인터페이스입니다. 둘 다 스냅샷, 배칭, `Object.is` 판정이 똑같이 적용됩니다.
- 여러 컴포넌트가 같은 State를 쓰면 reducer와 Context를 함께 씁니다. State용 Context와 `dispatch`용 Context를 따로 만들고, Provider 컴포넌트 안에서 `useReducer`를 호출하는 것이 공식 패턴입니다(자세히는 24편).

```jsx
function TasksProvider({ children }) {
  const [tasks, dispatch] = useReducer(
    tasksReducer,
    initial,
  )
  return (
    <TasksContext value={tasks}>
      <TasksDispatchContext value={dispatch}>
        {children}
      </TasksDispatchContext>
    </TasksContext>
  )
}
```

## Reducer 테스트

reducer는 순수 함수라서 컴포넌트를 렌더링하지 않고 함수 하나로 테스트할 수 있습니다. 입력(State, action)과 출력(다음 State)만 비교합니다. Vitest 같은 러너의 문법으로 쓰면 다음과 같습니다.

```jsx
import { expect, test } from 'vitest'
import { tasksReducer } from './tasksReducer'

test('added는 tasks 끝에 항목을 추가한다', () => {
  const before = [{ id: 0, text: 'A' }]
  const action = { type: 'added', id: 1, text: 'B' }
  expect(tasksReducer(before, action)).toEqual([
    { id: 0, text: 'A' },
    { id: 1, text: 'B' },
  ])
})
```

- 테스트할 reducer는 파일에서 `export`합니다. 컴포넌트와 같은 파일에 두어도 되지만 reducer만 불러오기 쉽게 분리하는 경우가 많습니다.
- `toEqual`은 객체의 구조를 재귀적으로 비교합니다. 참조가 같은지 보는 `toBe`는 `Object.is`를 씁니다. 새 State인지 확인하려면 이 차이를 이용합니다.

```jsx
const next = tasksReducer(before, action)
expect(next).not.toBe(before) // 새 배열이다
expect(before).toHaveLength(1) // 원본은 그대로다
```

- 테스트할 것: action마다 정상 결과, 원본 State가 변경되지 않는지, 모르는 `type`이 에러를 던지는지.
- 부수 효과가 없으니 mock이나 네트워크 설정이 필요 없습니다. 이것이 reducer로 옮기는 중요한 이유입니다.
- reducer 안에서 console 로그로 "이전 State, action, 다음 State"를 찍으면 어떤 action이 버그를 만들었는지 바로 찾을 수 있습니다.

## dispatch의 참조 안정성

`dispatch` 함수는 리렌더링되어도 같은 함수입니다. 렌더링마다 새로 만들어지지 않고 컴포넌트가 사는 동안 변하지 않습니다. `useState`의 Setter도 마찬가지입니다.

```jsx
const [state, dispatch] = useReducer(reducer, initialState)

useEffect(() => {
  const id = setInterval(() => {
    dispatch({ type: 'tick' })
  }, 1000)
  return () => clearInterval(id)
}, []) // dispatch를 넣어도 Effect가 다시 실행되지 않는다
```

- Effect의 의존성에 `dispatch`를 넣어도 되고 빼도 됩니다. 넣어도 Effect가 다시 실행되지 않습니다(자세히는 21편).
- `dispatch`를 Context로 내려보내면 그 Context의 값은 State가 바뀌어도 그대로입니다. 그래서 `dispatch`만 읽는 자식은 State 변경 때문에 Context 갱신 대상이 되지 않습니다. State와 `dispatch`를 별도 Context로 나누는 이유입니다.
- `dispatch`를 자식에게 Props로 넘겨도 `memo` 비교가 깨지지 않습니다.
- 반면 `() => dispatch({ ... })`처럼 핸들러를 렌더링 중에 새로 만들면 그 핸들러는 매번 새 함수입니다. 안정적인 것은 `dispatch` 자체이지 감싼 핸들러가 아닙니다.
- Effect 안에서 이전 State가 필요한 경우 reducer가 현재 State를 받으므로 State를 의존성에 넣지 않고 `dispatch`만 쓸 수 있습니다. `useState`의 업데이터 함수와 같은 효과입니다.

## 핵심 정리

- `useReducer(reducer, initialArg, init?)`은 State와 `dispatch`를 돌려주고, State 갱신 로직을 reducer 한 곳에 모읍니다.
- action은 사용자가 한 일을 설명하는 객체(관례로 `type`과 필요한 payload)이고, reducer가 현재 State와 action으로 다음 State를 계산합니다.
- reducer와 `init` 함수는 순수해야 합니다. State를 변경하지 않고 새 값을 돌려주며, 개발 모드 Strict Mode에서는 두 번 호출됩니다.
- 초기 State 계산은 함수를 호출하지 않고 `init`으로 넘겨야 마운트 때 한 번만 실행됩니다.
- 갱신이 복잡하고 핸들러가 여럿이면 `useReducer`, 단순하면 `useState`. reducer는 컴포넌트 없이 순수 함수로 테스트합니다.
- `dispatch`는 렌더링마다 바뀌지 않아 Effect 의존성과 Context 전달에 안전합니다.

## Effect란

Effect는 렌더링 자체 때문에 일어나는 부수 효과를 지정하는 코드입니다. 컴포넌트가 화면에 나타났거나 값이 바뀌어서 렌더링된 뒤에 실행됩니다. 부수 효과는 렌더링 계산 바깥의 일입니다. 네트워크 요청, 브라우저 API 호출, 서드파티 라이브러리 제어가 해당합니다.

- React 컴포넌트의 부수 효과는 두 종류로 나뉩니다. 클릭 같은 특정 상호작용이 일으키는 것은 이벤트 핸들러에, 렌더링이 일으키는 것은 Effect에 둡니다.
- 렌더링 중에는 부수 효과를 일으키지 않습니다. 렌더링은 순수해야 하기 때문입니다(자세히는 17편).
- 렌더링과 State만으로 표현할 수 있는 것에는 Effect가 필요 없습니다(자세히는 22편).

## useEffect

`useEffect`는 컴포넌트에 Effect를 추가하는 Hook입니다. 호출 형태는 `useEffect(setup, dependencies?)`입니다.

```jsx
import { useEffect } from 'react'

function Title({ text }) {
  useEffect(() => {
    document.title = text
  }, [text])
  return <h1>{text}</h1>
}
// text가 바뀔 때마다 렌더링이 끝난 뒤 탭 제목을 맞춘다
```

- `setup`은 Effect 코드가 담긴 함수입니다. 정리 함수(cleanup)를 반환해도 됩니다.
- `dependencies`는 선택이며 `setup` 안에서 읽는 반응형 값의 목록입니다. 생략하면 매 렌더링 뒤에 실행됩니다.
- 반환값은 `undefined`입니다.
- Hook이므로 컴포넌트나 Custom Hook의 최상위에서만 호출합니다. 반복문이나 조건문 안에서는 호출할 수 없습니다(자세히는 26편).
- Effect는 클라이언트에서만 실행됩니다. 서버 렌더링 중에는 실행되지 않습니다.
- 렌더링마다 Effect는 그 렌더링의 Props와 State를 클로저로 기억합니다. 각 렌더링은 자기 Effect를 가집니다.

## 외부 시스템 동기화

Effect는 React 컴포넌트를 React 바깥의 시스템과 맞추는 데 씁니다. 바깥이란 네트워크, 브라우저 API, 서드파티 라이브러리처럼 React가 제어하지 않는 것입니다.

| 용도 | 예 |
|------|----|
| 브라우저 API 제어 | 탭 제목, 비디오 `play()`와 `pause()` |
| 이벤트 구독 | `window`의 `scroll`, `resize` 리스너 |
| 서드파티 위젯 제어 | 지도의 줌 레벨 설정 |
| 서버 연결 | 채팅 방 연결, 웹소켓 |
| 데이터 가져오기 | Props에 따른 요청(자세히는 23편) |
| 애니메이션 시작 | DOM 노드 스타일을 바꿔 전환 시작 |

```jsx
useEffect(() => {
  if (isPlaying) {
    ref.current.play()
  } else {
    ref.current.pause()
  }
}, [isPlaying])
// isPlaying이 바뀌면 비디오 재생 상태를 맞춘다
```

- 비디오 재생 상태를 `isPlaying` State와 일치시키는 것이 동기화입니다. State가 바뀌면 React 바깥의 `<video>`가 따라갑니다.
- 외부 시스템이 관련되지 않는 일(한 State를 보고 다른 State를 계산하기)은 Effect가 필요하지 않습니다(자세히는 22편).

## Effect 실행 시점

Effect는 렌더링이 끝나고 화면에 반영된 커밋 뒤에 실행됩니다. 컴포넌트를 호출하는 렌더 단계에서는 실행되지 않습니다(렌더와 커밋은 17편).

```jsx
function Box() {
  console.log('1 render')
  useEffect(() => {
    console.log('2 effect')
  })
  return <div>Box</div>
}
// 출력 순서: 1 render → 2 effect
```

- 렌더링 결과가 DOM에 반영된 뒤라서 Effect 안에서는 ref에 DOM 노드가 채워져 있습니다(자세히는 19편).
- 상호작용 없이 일어난 렌더링이면 브라우저가 화면을 먼저 그린 뒤에 Effect를 실행할 수 있습니다. 화면이 그려지기 전에 실행해야 하는 코드는 `useLayoutEffect`를 씁니다.
- 클릭 같은 상호작용 때문에 일어난 렌더링이면 React가 브라우저의 페인트 전에 Effect를 실행할 수 있습니다. 이벤트 시스템이 결과를 관찰할 수 있게 하려는 것입니다.

## Setup

Setup은 Effect의 본문, 즉 `useEffect`에 넘기는 함수입니다. 외부 시스템과 동기화를 시작하는 코드를 둡니다.

```jsx
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect() // 동기화 시작
}, [roomId])
```

- setup은 컴포넌트가 화면에 추가된 뒤 처음 실행됩니다.
- 이후에는 의존성이 바뀐 렌더링의 커밋 뒤에 다시 실행됩니다. 이때 새 Props와 State를 봅니다.
- setup 안에서 State를 바꿀 수 있습니다. 바꾸면 재렌더링이 일어나므로 의존성 설계를 신경 써야 합니다(자세히는 21편).

## Cleanup

Cleanup은 setup이 시작한 것을 멈추거나 되돌리는 함수입니다. setup이 반환합니다.

```jsx
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect()
  return () => {
    conn.disconnect() // 동기화 중단
  }
}, [roomId])
```

- cleanup은 setup을 거울로 비춘 것이어야 합니다. 연결했으면 끊고, 구독했으면 해제하고, 시작한 타이머는 멈춥니다.
- cleanup이 실행되는 때는 두 가지입니다. 의존성이 바뀌어 setup이 다시 실행되기 직전과 컴포넌트가 화면에서 사라질 때입니다.
- 의존성이 바뀌었을 때의 cleanup은 이전 렌더링의 Props와 State를 사용합니다. 정리 대상은 이전에 시작한 것이기 때문입니다.
- cleanup이 필요 없는 Effect는 아무것도 반환하지 않아도 됩니다(탭 제목 설정처럼 되돌릴 것이 없는 경우).

## Dependency Array

의존성 배열은 Effect가 언제 다시 실행될지 정하는 목록입니다. `setup` 안에서 읽는 모든 반응형 값을 나열합니다. 반응형 값은 Props, State, 컴포넌트 본문에서 선언한 변수와 함수입니다(자세히는 21편).

| 형태 | 실행 시점 |
|------|-----------|
| 배열 생략 | 매 렌더링의 커밋 뒤 |
| 빈 배열 `[]` | 최초 커밋 뒤 한 번 |
| `[a, b]` | 최초 커밋 뒤, 그리고 `a`나 `b`가 바뀐 커밋 뒤 |

- React는 각 의존성을 이전 렌더링 값과 `Object.is`로 비교합니다. 하나라도 다르면 Effect를 다시 실행합니다.
- 나열할 값은 직접 고르지 않습니다. 코드가 읽는 값이 정합니다. 린터(`eslint-plugin-react-hooks`)가 빠진 의존성과 불필요한 의존성을 잡아 줍니다.
- 배열 생략과 빈 배열은 다릅니다. 생략하면 매 렌더링마다, 빈 배열은 최초 한 번만 실행됩니다. `[]`가 의미 있으려면 Effect가 반응형 값을 읽지 않아야 합니다.

```jsx
useEffect(() => { /* A */ })          // 매 렌더링 뒤
useEffect(() => { /* B */ }, [])      // 최초 한 번(개발 모드는 두 번)
useEffect(() => { /* C */ }, [id])    // 최초와 id가 바뀔 때
```

**흔한 실수:** Effect 안에서 읽는 값이 있는데 의존성을 `[]`로 두는 것입니다. 값이 바뀌어도 Effect가 다시 실행되지 않아 오래된 값을 쓰는 버그가 됩니다. 린터 경고를 끄지 말고 의존성을 추가합니다.

## Mount, Update, Unmount

컴포넌트의 생애에서 Effect는 마운트(처음 화면에 나타남), 업데이트(렌더링이 반복됨), 언마운트(화면에서 사라짐)에 각각 이렇게 대응합니다.

| 시점 | 실행되는 것 |
|------|-------------|
| 마운트 | setup |
| 업데이트(의존성이 바뀐 커밋) | 이전 값으로 cleanup, 새 값으로 setup |
| 업데이트(의존성이 그대로) | 아무것도 실행되지 않음 |
| 언마운트 | cleanup 한 번 |

```jsx
useEffect(() => {
  console.log('setup', roomId)
  return () => console.log('cleanup', roomId)
}, [roomId])
// 마운트 'general': setup general
// 'travel'로 변경: cleanup general → setup travel
// 언마운트: cleanup travel
```

- 의존성이 없는 형태(배열 생략)에서는 매 업데이트마다 cleanup → setup이 일어납니다.
- 의존성이 `[]`이면 업데이트에서는 아무 일도 없고 마운트에서 setup, 언마운트에서 cleanup만 실행됩니다.

## Effect와 이벤트 차이

이벤트 핸들러는 특정 상호작용에 반응해서 실행되고, Effect는 컴포넌트가 화면에 표시되었기 때문에 실행됩니다. 코드를 둘 곳은 왜 그 코드가 실행돼야 하는지로 정합니다.

| 구분 | 이벤트 핸들러 | Effect |
|------|---------------|--------|
| 실행 이유 | 사용자의 특정 동작 | 렌더링(화면 표시, 값 변경) |
| 알 수 있는 것 | 무슨 일이 일어났는지 | 렌더링됐다는 것뿐 |
| 예 | 구매 요청, 폼 전송 | 방문 기록, 연결 유지 |

```jsx
function handleBuy() {
  post('/api/buy') // ✅ 클릭 때문에 실행
}
useEffect(() => {
  post('/analytics', { name: 'visit_form' }) // ✅ 표시 때문에 실행
}, [])
```

- 구매 요청을 Effect에 두면 문제가 생깁니다. 구매는 렌더링 때문이 아니라 클릭 때문에 일어나야 하는데, Effect는 클릭이 아니라 렌더링에 반응해 실행됩니다(개발 모드에서는 두 번 실행되기도 합니다).
- Effect가 실행되는 시점에는 사용자가 무엇을 했는지 알 수 없습니다. 사용자의 행동에 대한 응답은 이벤트 핸들러에 둡니다.
- 화면에 표시된 것 때문에 일어나야 하는 일(방문 로그, 외부 시스템 동기화)만 Effect에 둡니다.

## Component Lifecycle과 차이

컴포넌트의 생애는 마운트, 업데이트, 언마운트이고, Effect의 생애는 동기화 시작과 동기화 중단의 반복입니다. 두 생애는 같지 않습니다.

- 컴포넌트는 마운트, 업데이트, 언마운트를 겪습니다.
- Effect는 두 가지만 합니다. 동기화를 시작하고, 동기화를 멈춥니다. 컴포넌트가 업데이트되는 동안 이 시작과 중단이 여러 번 반복될 수 있습니다.
- `useEffect(fn, [])`를 클래스 컴포넌트의 `componentDidMount`에 대응시키는 사고방식은 맞지 않습니다. 마운트와 언마운트를 생각하는 대신 Effect 하나가 무엇을 동기화하는지, 어떻게 시작하고 멈추는지를 생각합니다.
- 의존성이 바뀌면 Effect는 멈췄다가 새 값으로 다시 시작합니다. 컴포넌트가 마운트된 채로 있어도 일어납니다.

```jsx
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect()         // 시작
  return () => conn.disconnect() // 중단
}, [roomId])
// "마운트 때 연결"이 아니라 "roomId에 연결하고 끊는다"로 읽는다
```

### 동기화 시작

setup이 실행되는 것이 동기화의 시작입니다. 컴포넌트가 마운트될 때, 그리고 의존성이 바뀌어 새 값으로 다시 맞춰야 할 때입니다.

### 동기화 중단

cleanup이 실행되는 것이 동기화의 중단입니다. 의존성이 바뀌어 이전 값으로 맞춘 동기화를 끝낼 때, 그리고 컴포넌트가 언마운트될 때입니다.

### Cleanup → Setup

의존성이 바뀌면 React는 이전 값으로 cleanup을 실행해 이전 동기화를 끝내고, 이어서 새 값으로 setup을 실행해 새 동기화를 시작합니다. 두 동기화가 겹치지 않고 순서대로 이어집니다.

```jsx
// roomId: 'general' → 'travel'
// 1. cleanup(general): 연결 끊기
// 2. setup(travel): 새 연결
```

## 개발 모드 재실행

개발 모드에서 StrictMode가 켜져 있으면 React는 컴포넌트가 마운트될 때 모든 Effect를 setup, cleanup, setup으로 한 번 더 실행합니다. 마운트됐다가 언마운트되고 다시 마운트되는 상황을 흉내 내서 cleanup이 빠진 Effect를 개발 중에 찾아내려는 것입니다(자세히는 18편).

```jsx
// StrictMode, 개발 모드의 마운트
// setup → cleanup → setup
// cleanup이 있으면 연결 하나만 남고, 없으면 연결이 둘이 된다
```

- 프로덕션 빌드에서는 한 번만 실행됩니다.
- Effect가 두 번 도는 것을 막으려고 코드를 조작하지 않습니다. cleanup을 올바르게 쓰면 두 번 실행돼도 눈에 띄는 차이가 없습니다.
- Effect 안의 요청이 두 번 나가는 것은 Effect를 바꿔야 한다는 신호일 수 있습니다. 클릭 때문에 일어나야 하는 일은 이벤트 핸들러로 옮깁니다.

## 관심사별 Effect 분리

Effect 하나는 하나의 독립적인 동기화 과정을 나타내야 합니다. 서로 관련 없는 일은 의존성이 같아도 Effect를 나눕니다.

```jsx
// ❌ 방문 기록과 연결이 한 Effect에 섞임
useEffect(() => {
  logVisit(roomId)
  const conn = createConnection(serverUrl, roomId)
  conn.connect()
  return () => conn.disconnect()
}, [roomId])
```

```jsx
// ✅ 관심사별 분리
useEffect(() => {
  logVisit(roomId)
}, [roomId])
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect()
  return () => conn.disconnect()
}, [roomId])
```

- 섞여 있으면 한쪽 의존성을 바꿀 때 다른 쪽도 다시 실행됩니다. 예를 들어 방문 기록에 다른 값을 추가하면 연결이 끊겼다 다시 이어집니다.
- 분리하면 각 Effect가 자기 값이 바뀔 때만 실행되고, cleanup도 자기 일만 책임집니다.
- 반대로 한 일을 억지로 여러 Effect로 쪼개지 않습니다. 시작과 중단이 한 쌍인 일은 한 Effect 안에 둡니다.

## Subscription

구독은 외부 이벤트 소스에 리스너를 등록하는 일입니다. setup에서 등록하고 cleanup에서 해제합니다.

```jsx
useEffect(() => {
  function handleScroll() {
    console.log(window.scrollX, window.scrollY)
  }
  window.addEventListener('scroll', handleScroll)
  return () => {
    window.removeEventListener('scroll', handleScroll)
  }
}, [])
```

- 해제하지 않으면 컴포넌트가 사라진 뒤에도 리스너가 남아 누수가 되고, 개발 모드에서는 리스너가 두 번 등록되어 드러납니다.
- 등록과 해제에 같은 함수 참조를 써야 해제가 됩니다. 그래서 핸들러를 Effect 안에서 변수로 선언합니다.
- 읽기만 하는 외부 스토어(예: `navigator.onLine`)를 구독해 State처럼 쓰는 일은 `useSyncExternalStore`로 하는 편이 낫습니다(자세히는 22편).

## Connection

연결은 서버나 채널 같은 외부 자원과 연결을 맺고 유지하는 일입니다. setup에서 연결하고 cleanup에서 끊습니다.

```jsx
function ChatRoom({ roomId }) {
  useEffect(() => {
    const conn = createConnection(serverUrl, roomId)
    conn.connect()
    return () => conn.disconnect()
  }, [roomId])
  return <h1>Welcome to {roomId}</h1>
}
// roomId가 바뀌면 이전 방을 끊고 새 방에 연결한다
```

- 연결 대상(`roomId`)이 바뀌면 Effect가 멈췄다가 새 값으로 다시 시작합니다. 컴포넌트가 마운트된 채로 방만 바뀌는 상황입니다.
- `serverUrl`처럼 컴포넌트 바깥에서 선언한 상수는 반응형 값이 아니라서 의존성에 넣지 않습니다. 컴포넌트 안의 Props나 State로 만든 값은 모두 반응형이라 넣습니다.
- 연결 객체는 Effect 안에서 만들고 같은 Effect 안의 cleanup이 끊습니다. 컴포넌트 본문에서 만들면 렌더링마다 새로 만들어집니다.

## Timer

타이머는 일정 시간 뒤나 일정 간격으로 코드를 실행하는 일입니다. setup에서 시작하고 cleanup에서 멈춥니다.

```jsx
function Clock() {
  const [count, setCount] = useState(0)
  useEffect(() => {
    const id = setInterval(() => {
      setCount((c) => c + 1)
    }, 1000)
    return () => clearInterval(id)
  }, [])
  return <p>{count}</p>
}
```

- `setCount((c) => c + 1)`로 이전 State를 받으면 Effect가 `count`를 읽지 않아 의존성이 `[]`로 충분합니다. `setCount(count + 1)`로 쓰면 `count`가 의존성이 되어 값이 바뀔 때마다 타이머가 다시 만들어집니다(자세히는 21편).
- cleanup이 없으면 컴포넌트가 사라진 뒤에도 인터벌이 돌고, 개발 모드에서는 인터벌이 두 개가 돌아 숫자가 두 배로 오릅니다.
- 같은 Effect 안에서 만든 ID는 지역 변수에 두면 됩니다. 시작 함수와 중지 함수가 서로 다른 이벤트 핸들러일 때만 ref에 저장합니다(자세히는 19편).

## 핵심 정리

- Effect는 렌더링 때문에 일어나는 부수 효과를 렌더링이 끝난 커밋 뒤에 실행해 컴포넌트를 외부 시스템과 동기화하는 코드입니다.
- setup은 동기화를 시작하고 cleanup은 setup이 한 일을 되돌립니다. 의존성이 바뀌면 이전 값으로 cleanup한 뒤 새 값으로 setup하고, 언마운트에서는 cleanup만 실행됩니다.
- 의존성 배열은 생략하면 매 렌더링 뒤, `[]`이면 최초 한 번, 값이 있으면 그 값이 바뀔 때 실행되며 `Object.is`로 비교합니다.
- Effect는 마운트와 언마운트가 아니라 시작과 중단의 반복으로 생각하고, 독립적인 동기화는 Effect를 나눕니다.
- 클릭 같은 사용자 행동에 대한 반응은 이벤트 핸들러에, 화면 표시 때문에 필요한 동기화는 Effect에 둡니다.
- 개발 모드의 StrictMode는 마운트 시 setup, cleanup, setup을 실행하므로 구독, 연결, 타이머는 반드시 cleanup을 갖춥니다.

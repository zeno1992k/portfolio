## State 개념

State는 컴포넌트가 렌더링 사이에 기억하는 값입니다. 값이 바뀌면 React가 컴포넌트를 다시 렌더링해 화면을 갱신합니다. 카운터의 숫자, 입력창의 글자, 메뉴가 열렸는지 여부처럼 시간이 지나며 바뀌고 화면에 영향을 주는 값이 State입니다.

- State는 컴포넌트 인스턴스마다 따로 있습니다. 같은 컴포넌트를 두 번 쓰면 State도 둘이며 서로 영향을 주지 않습니다.
- State는 그 컴포넌트의 비공개 값입니다. 부모가 직접 읽거나 바꿀 수 없고, 필요하면 Props로 내려보냅니다(자세히는 14편).
- State를 바꾸는 계기는 대개 이벤트 핸들러입니다(자세히는 08편).

## 일반 변수와의 차이

컴포넌트 안의 일반 변수(`let`)는 State 역할을 하지 못합니다. 이유는 두 가지입니다.

1. 렌더링 사이에 값이 유지되지 않습니다. 컴포넌트 함수는 렌더링마다 처음부터 다시 실행되어 변수가 초기값으로 돌아갑니다.
2. 값을 바꿔도 렌더링이 일어나지 않습니다. React는 일반 변수가 바뀐 것을 알지 못합니다.

```jsx
function Counter() {
  let count = 0 // ❌ 렌더링마다 0으로 초기화
  function handleClick() {
    count = count + 1 // 값은 바뀌지만 화면은 그대로
  }
  return <button onClick={handleClick}>{count}</button>
}
```

State는 이 두 문제를 해결합니다. React가 값을 컴포넌트 함수 밖에 보관해 렌더링 사이에 유지하고, Setter를 호출하면 렌더링을 요청합니다.

| 항목 | 일반 변수 | State |
|------|-----------|-------|
| 렌더링 사이 유지 | 안 됨(초기값으로 복귀) | 됨 |
| 변경 시 렌더링 | 일어나지 않음 | Setter 호출 시 요청됨 |
| 컴포넌트 인스턴스마다 | 렌더링마다 새로 생성 | 인스턴스별로 따로 보관 |

렌더링 중에 만든 값이라도 State나 Props에서 계산할 수 있으면 일반 변수로 두는 것이 맞습니다(자세히는 12편).

## useState

`useState`는 State 변수를 선언하는 Hook입니다. 초기값을 받아 현재 값과 Setter 함수의 쌍을 배열로 반환합니다.

```jsx
import { useState } from 'react'

function Counter() {
  const [count, setCount] = useState(0)
  function handleClick() {
    setCount(count + 1)
  }
  return <button onClick={handleClick}>{count}</button>
}
// 처음 0 → 클릭 1 → 클릭 2 ...
```

- 반환값은 항상 원소 두 개인 배열이고, 배열 구조 분해로 이름을 붙입니다. 이름은 자유지만 `[something, setSomething]` 형태로 짓는 것이 관례입니다.
- 첫 렌더링에서 `useState(0)`은 `[0, setCount]`를 반환합니다. 이후 렌더링에서는 초기값 인수를 무시하고 React가 기억한 현재 값을 반환합니다.
- State 변수는 개수 제한 없이 선언할 수 있습니다.

```jsx
const [index, setIndex] = useState(0)
const [showMore, setShowMore] = useState(false)
```

React는 State 변수에 이름이 아니라 호출 순서로 값을 연결합니다. 그래서 Hook에는 규칙이 있습니다.

- 컴포넌트(또는 Custom Hook)의 최상위에서만 호출합니다.
- 조건문, 반복문, 중첩 함수 안에서 호출하면 안 됩니다. 호출 순서가 렌더링마다 달라지기 때문입니다(자세히는 26편).

```jsx
function Bad({ show }) {
  if (show) {
    const [n, setN] = useState(0) // ❌ 조건 안에서 호출
  }
}
```

## State 읽기

State 변수는 평범한 값입니다. JSX와 렌더링 중 계산에서 그대로 읽습니다.

```jsx
const [name, setName] = useState('Kim')
const upper = name.toUpperCase() // 'KIM'
return <p>{name}</p>             // Kim
```

- 렌더링마다 State 변수는 그 렌더링 시점의 값으로 고정됩니다. 같은 렌더링 안에서는 어디서 읽어도 같은 값입니다(자세히는 10편).
- 변수는 `const`로 선언합니다. State를 바꾸는 방법은 변수에 대입하는 것이 아니라 Setter 호출입니다.

**흔한 실수:** State 변수에 직접 대입하는 것입니다.

```jsx
count = count + 1    // ❌ 화면이 갱신되지 않고 const면 TypeError
setCount(count + 1)  // ✅
```

## Setter

Setter는 State를 새 값으로 바꾸도록 React에 요청하는 함수입니다. 값을 넘기면 다음 렌더링에서 State가 그 값이 됩니다.

```jsx
setName('Lee')   // 다음 렌더링의 name은 'Lee'
setCount(5)      // 다음 렌더링의 count는 5
```

- Setter는 현재 렌더링의 State 변수를 바꾸지 않습니다. 호출 직후 변수를 읽어도 이전 값입니다. 새 값은 다음 렌더링에서 보입니다.
- 반환값이 없습니다(`undefined`).
- 같은 이벤트 핸들러 안의 여러 Setter 호출은 모아서 한 번만 렌더링합니다. 이를 배칭(batching)이라 하며 10편에서 다룹니다.
- 값 대신 함수를 넘기면 이전 State를 받아 다음 State를 계산합니다(아래 "이전 State 기반 변경").

```jsx
function handleClick() {
  setCount(count + 1)
  console.log(count) // 0 (아직 이전 값)
}
```

**흔한 실수:** 핸들러를 전달하지 않고 호출해 버리는 것입니다. 호출 결과가 Setter 호출이라면 렌더링 중에 Setter가 실행되어 무한 렌더링이 일어납니다. React는 `Too many re-renders` 에러로 막습니다.

```jsx
<button onClick={handleClick()}>+</button> // ❌ 렌더링 중 실행
<button onClick={handleClick}>+</button>   // ✅ 함수를 전달
```

## 이전 State 기반 변경

다음 값이 이전 값에 의존할 때는 값 대신 업데이터 함수(updater function)를 넘깁니다. 업데이터는 대기 중인 최신 State를 유일한 인수로 받아 다음 State를 반환합니다.

```jsx
setCount((prev) => prev + 1)
setCount((c) => c * 2)
```

- 업데이터는 순수해야 합니다. 인수만으로 결과를 계산하고, 외부를 바꾸거나 State를 직접 변경하지 않습니다.
- 인수 이름은 State 변수 이름의 첫 글자(`c`)나 `prevCount` 형태가 관례입니다.
- 현재 렌더링의 State 변수로 계산하는 `setCount(count + 1)`을 한 핸들러에서 세 번 호출하면 3이 아니라 1만 늘어납니다. 세 호출 모두 같은 `count` 값을 쓰기 때문입니다. 업데이터를 쓰면 호출마다 앞 결과를 이어받아 3이 됩니다. 큐의 동작은 10편에서 자세히 다룹니다.

```jsx
setCount(count + 1)
setCount(count + 1) // 결과: 1 증가
setCount((c) => c + 1)
setCount((c) => c + 1) // 결과: 2 증가
```

- 새 값이 이전 값과 무관하면(`setName('Lee')`) 값을 그대로 넘깁니다.
- 업데이터에서 쓰는 이름이 State 변수와 같으면 안쪽 이름이 바깥을 가립니다. 헷갈리지 않게 짧은 별도 이름을 씁니다.

## Boolean State

참과 거짓 두 상태를 가진 State입니다. 열림·닫힘, 선택·해제, 로딩 중 여부에 씁니다. 초기값은 `false`로 두는 경우가 많습니다.

```jsx
const [isOpen, setIsOpen] = useState(false)

setIsOpen(true)          // 열기
setIsOpen(false)         // 닫기
setIsOpen((open) => !open) // 토글
```

- 토글은 이전 값에 의존하므로 `setIsOpen(!isOpen)`보다 업데이터 `(open) => !open`이 안전합니다. 한 핸들러에서 두 번 토글해도 올바르게 계산됩니다.
- 이름은 `is`, `has`, `show` 같은 접두사로 불리언임을 드러냅니다.
- 불리언 State가 여러 개이고 서로 배타적이면(`isSending`과 `isSent`가 동시에 참이 될 수 없는 경우) 하나의 `status` 값으로 합칩니다(자세히는 12편).

```jsx
return (
  <>
    <button onClick={() => setIsOpen((o) => !o)}>
      menu
    </button>
    {isOpen && <Menu />}
  </>
)
```

## 배열 State

배열도 State가 될 수 있습니다. 다만 배열 안의 요소를 바꾸는 `push`, `splice`, `arr[i] = x`는 쓰지 않고, 바뀐 새 배열을 만들어 Setter에 넘깁니다.

```jsx
const [items, setItems] = useState([])

setItems([...items, 'new'])               // 끝에 추가
setItems(items.filter((x) => x !== 'a'))  // 삭제
setItems(items.map((x) => (x === 'a' ? 'b' : x))) // 교체
```

- 변경하는 메서드(`push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`)는 State 배열에 직접 호출하지 않습니다.
- 새 배열을 반환하는 `concat`, 스프레드, `filter`, `map`, `slice`를 씁니다.
- 초기값은 보통 빈 배열 `[]`입니다.
- 추가·삭제·수정·정렬의 패턴은 11편에서 자세히 다룹니다.

**흔한 실수:** `push` 후 같은 배열을 Setter에 넘기는 것입니다.

```jsx
items.push('new')  // ❌ 배열을 직접 변경
setItems(items)    // ❌ 같은 참조라 렌더링이 일어나지 않음
```

## 객체 State

객체도 State가 될 수 있습니다. 일부 프로퍼티만 바꿀 때도 객체를 통째로 교체합니다. 기존 객체를 스프레드로 복사하고 바꿀 값만 덮어씁니다.

```jsx
const [form, setForm] = useState({ name: '', age: 0 })

setForm({ ...form, name: 'Kim' })
// { name: 'Kim', age: 0 }
```

- `setForm({ name: 'Kim' })`처럼 일부만 넘기면 나머지 프로퍼티가 사라집니다. Setter는 병합하지 않고 교체하기 때문입니다.
- 스프레드는 같은 이름의 키가 뒤에 오면 앞을 덮어쓰므로, `...form`을 앞에, 바꿀 값을 뒤에 씁니다(자세히는 JavaScript 과목 ECMAscript의 36편).
- 이전 값에 의존하면 업데이터로 씁니다.

```jsx
setForm((prev) => ({ ...prev, age: prev.age + 1 }))
```

- 입력창이 여러 개일 때 `name` 속성으로 키를 정하는 계산된 프로퍼티는 11편과 15편에서 다룹니다.

**흔한 실수:** 프로퍼티를 직접 바꾸는 것입니다.

```jsx
form.name = 'Kim'  // ❌ 직접 변경
setForm(form)      // ❌ 같은 참조라 렌더링이 일어나지 않음
```

## 중첩 State

객체 안에 객체가 있으면 스프레드로 복사하는 것은 최상위 한 단계뿐입니다(얕은 복사). 안쪽 값을 바꾸려면 바꿀 경로의 모든 단계를 새로 만듭니다.

```jsx
const [person, setPerson] = useState({
  name: 'Kim',
  address: { city: 'Seoul', zip: '04524' },
})

setPerson({
  ...person,
  address: { ...person.address, city: 'Busan' },
})
```

- 위 코드에서 `person`과 `person.address`가 새 객체가 되고, 바꾸지 않은 프로퍼티는 이전 객체와 같은 값을 공유합니다.
- `setPerson({ ...person, address: { city: 'Busan' } })`처럼 안쪽 객체를 일부만 쓰면 `zip`이 사라집니다.
- `person.address.city = 'Busan'` 같은 직접 변경은 금지입니다.
- 중첩이 깊을수록 코드가 길어지고 실수하기 쉽습니다. 구조를 평평하게 만들거나 Immer를 쓰는 방법은 11편과 12편에서 다룹니다.

## 불변성

불변성(immutability)은 State로 쓰는 객체와 배열을 만든 뒤 내용을 바꾸지 않는 규칙입니다. 바꿔야 하면 바뀐 새 객체나 배열을 만들어 Setter로 교체합니다. 숫자·문자열·불리언 같은 원시값은 원래 변경할 수 없으므로 이 규칙은 객체와 배열에 해당합니다.

```jsx
const a = { x: 1 }
const b = { ...a, x: 2 } // a는 그대로 { x: 1 }
// a !== b 이므로 변경을 감지할 수 있다
```

React가 불변성을 요구하는 이유는 다음과 같습니다.

- 변경 감지: React는 이전 값과 새 값을 `Object.is`로 비교합니다. 같은 객체를 고쳐서 넘기면 같다고 판단해 렌더링을 건너뜁니다.
- 디버깅: 이전 State가 보존되므로 변화 과정을 로그로 비교할 수 있습니다.
- 최적화: `memo` 같은 최적화가 이전 객체와 같은지 비교해 작업을 생략합니다.
- 새 기능: React의 기능들은 State를 렌더링 시점의 스냅샷으로 다룬다고 가정합니다.
- 실행 취소·다시 실행: 이전 State를 보관해 두면 쉽게 구현됩니다.
- 구현 단순성: 객체를 감시하는 별도 장치(Proxy 등)가 필요 없습니다.

State를 불변으로 다루는 것은 객체를 복사한다는 뜻이지 모든 값을 깊게 복사한다는 뜻이 아닙니다. 바뀐 경로만 새로 만들고 나머지는 참조를 공유해도 됩니다.

## 직접 변경 금지

State 변수가 가리키는 객체나 배열을 직접 고치면 안 됩니다. 이를 변이(mutation)라고 부르며, 프로퍼티 대입, `push`·`sort` 같은 변경 메서드, `delete`가 모두 해당합니다.

```jsx
const [point, setPoint] = useState({ x: 0, y: 0 })

point.x = 10         // ❌ 직접 변경: 화면 갱신 없음
setPoint(point)      // ❌ 같은 참조: 아무 일도 안 일어남
setPoint({ ...point, x: 10 }) // ✅
```

- 직접 변경하면 객체 내용은 이미 바뀌었지만 React는 렌더링을 하지 않습니다. 이후 다른 이유로 렌더링되면 그제야 바뀐 값이 나타나 화면과 State가 어긋난 것처럼 보입니다.
- 새로 만든 객체는 State에 넣기 전에 마음껏 고쳐도 됩니다. 이를 지역 변이(local mutation)라고 하며 문제가 없습니다.

```jsx
const next = {}        // 방금 만든 새 객체
next.x = e.clientX     // ✅ 아직 State가 아니므로 변경 가능
next.y = e.clientY
setPoint(next)
```

- `const`는 변수의 재대입만 막습니다. `const point = {...}`여도 `point.x = 10`은 막지 못합니다.
- Props도 같은 이유로 직접 변경하지 않습니다(자세히는 05편).
- Immer를 쓰면 변경하는 것처럼 코드를 쓰면서 불변성을 지킬 수 있습니다(자세히는 11편).

## 지연 초기화

`useState`의 초기값 자리에 함수를 넘기면 초기화 함수(initializer function)로 처리합니다. React는 첫 렌더링에서만 그 함수를 호출하고 반환값을 초기값으로 씁니다.

```jsx
useState(createTodos())       // ❌ 매 렌더링 실행
useState(createTodos)         // ✅ 첫 렌더링만
useState(() => createTodos()) // ✅ 첫 렌더링만
```

- `useState(createTodos())`는 결과가 첫 렌더링 이후 무시되더라도 함수가 매 렌더링 실행됩니다. 비용이 큰 계산이면 낭비입니다.
- 함수를 넘길 때는 호출하지 않고 함수 자체를 넘깁니다(`createTodos`). 또는 화살표 함수로 감쌉니다.
- 초기화 함수는 순수해야 하고 인수를 받지 않습니다. 값을 반환합니다.
- 개발 중 StrictMode에서는 순수성 검사를 위해 초기화 함수를 두 번 호출하고 한 번의 결과는 버립니다. 운영 빌드에서는 한 번만 호출합니다(자세히는 18편).
- 가벼운 값(`0`, `''`, `[]`)에는 필요 없습니다. `localStorage` 읽기나 큰 배열 생성처럼 비용이 큰 초기값에 씁니다.

```jsx
const [theme, setTheme] = useState(() => {
  return localStorage.getItem('theme') ?? 'light'
})
```

**흔한 실수:** 함수 자체를 State로 저장하려는 것입니다. `useState(fn)`은 `fn`을 초기화 함수로 호출하고, `setFn(other)`는 `other`를 업데이터로 호출합니다. 함수를 값으로 저장하려면 화살표 함수로 한 겹 감쌉니다.

```jsx
const [fn, setFn] = useState(() => someFunction)
setFn(() => otherFunction)
```

## 같은 값 set 시 렌더 생략

새 값이 현재 값과 `Object.is` 비교로 같으면 React는 해당 컴포넌트와 자식의 렌더링을 건너뜁니다.

```jsx
const [count, setCount] = useState(0)

setCount(0)       // 같은 값: 렌더링 생략
setCount(count)   // 같은 값: 렌더링 생략
```

`Object.is`는 `===`와 거의 같지만 두 가지가 다릅니다.

| 비교 | `===` | `Object.is` |
|------|-------|-------------|
| `NaN`과 `NaN` | false | true |
| `0`과 `-0` | true | false |

- 원시값은 값이 같으면 같습니다.
- 객체와 배열은 참조가 같아야 같습니다. 내용이 같은 새 객체(`{ x: 1 }`과 `{ x: 1 }`)는 다른 값이므로 렌더링됩니다.
- 이 규칙이 직접 변경이 통하지 않는 이유입니다. 고친 객체를 그대로 `set`하면 참조가 같아 렌더링이 생략됩니다.
- React가 렌더링을 건너뛰기 전에 컴포넌트 함수를 한 번 더 호출할 수 있습니다. 결과에는 영향이 없으며 건너뛴 렌더링의 자식 컴포넌트는 호출되지 않습니다.
- 렌더링 생략은 불필요한 렌더링을 줄이는 장치이지 로직에 기댈 보장이 아닙니다. 같은 값 설정이 부작용을 일으키지 않도록 코드를 순수하게 둡니다.

## 핵심 정리

- State는 렌더링 사이에 기억되는 값이며, 일반 변수와 달리 값이 유지되고 Setter 호출 시 렌더링이 요청됩니다.
- `useState(초기값)`은 `[현재 값, Setter]` 쌍을 반환하고, 컴포넌트 최상위에서만 호출합니다.
- Setter는 다음 렌더링의 값을 요청할 뿐이어서 호출 직후 변수는 이전 값입니다. 이전 값에 의존하면 업데이터 함수를 씁니다.
- 객체와 배열 State는 직접 변경하지 않고 복사해 바뀐 새 값으로 교체하며, 중첩이면 바뀐 경로의 모든 단계를 새로 만듭니다.
- 초기화 함수를 넘기면 첫 렌더링에서만 실행되고, 새 값이 `Object.is`로 같으면 렌더링을 건너뜁니다.

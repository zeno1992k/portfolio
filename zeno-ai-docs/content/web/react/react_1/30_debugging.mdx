## React DevTools

React DevTools는 React 컴포넌트를 검사하고 Props와 State를 확인·수정하며 성능 문제를 찾는 디버깅 도구입니다. 브라우저 확장으로 설치하는 방식을 공식 문서가 권장합니다.

| 환경 | 설치 |
|------|------|
| Chrome, Firefox, Edge | 각 스토어의 React Developer Tools 확장 |
| Safari와 기타 브라우저 | `npm install -g react-devtools` 후 `react-devtools` 실행, 앱 `head`에 `localhost:8097` 스크립트 태그 추가 |
| React Native | React Native DevTools(0.76 이상) |

- 설치하면 브라우저 개발자 도구에 **Components**와 **Profiler** 두 패널이 추가됩니다. React가 쓰인 페이지에서만 보입니다.
- 개발 서버로 띄운 앱에서 가장 정보가 많습니다. 프로덕션 빌드는 에러 메시지가 축약되고 일부 도구가 꺼져 있습니다(아래 "Minified error 해독", "Profiler").
- 에러는 브라우저 콘솔(Console), 네트워크는 Network 탭, 컴포넌트 구조는 DevTools가 봅니다. 문제의 종류에 따라 도구를 고릅니다.
- 설치와 개발 환경 구성은 02편에서 다뤘습니다.

## Components

Components 패널은 현재 화면의 컴포넌트 트리를 보여 주고, 컴포넌트를 선택하면 그 컴포넌트의 Props, State, Hook 값을 오른쪽에 보여 줍니다.

- 왼쪽은 DOM이 아니라 컴포넌트 트리입니다. HTML 요소뿐 아니라 내가 만든 컴포넌트, Provider, 라이브러리 컴포넌트가 모두 노드입니다.
- 선택한 컴포넌트는 브라우저 콘솔에서 `$r`로 접근할 수 있어서 Props나 State를 코드로 확인할 때 씁니다.
- 값을 직접 수정할 수 있습니다. 코드를 고치지 않고 State나 Props를 바꿔 보고 화면이 어떻게 반응하는지 확인하는 용도입니다. 새로고침하면 사라집니다.
- 트리에는 컴포넌트 이름이 나옵니다. 이름 없는 화살표 함수를 바로 내보낸 컴포넌트는 이름을 알아보기 어려우므로 이름 있는 함수로 선언합니다(자세히는 04편).

```jsx
// ❌ 이름 없는 함수
export default () => <h1>Hi</h1>
// ✅ 이름 있음
export default function Greeting() {
  return <h1>Hi</h1>
}
```

## Profiler

Profiler는 렌더링에 걸린 시간과 렌더링된 컴포넌트를 기록하는 도구입니다. DevTools의 Profiler 패널과 React의 `Profiler` 컴포넌트 두 형태가 있습니다.

DevTools Profiler의 사용법은 다음과 같습니다.

1. 기록(Record)을 시작하고, 확인하려는 동작(버튼 클릭, 입력 등)을 수행한 뒤 기록을 멈춥니다.
2. 기록 안에 커밋(commit)이 시간순으로 나열됩니다. 커밋은 React가 화면에 변경을 반영한 한 번의 작업입니다(자세히는 17편).
3. 커밋을 선택하면 그때 렌더링된 컴포넌트와 걸린 시간을 볼 수 있습니다.
4. 설정에서 켜면 컴포넌트마다 변경된 Props와 State가 기록됩니다(아래 "렌더 원인").

- 기록은 JSON으로 내보내고 불러올 수 있어서 동료에게 전달할 수 있습니다.
- 이 용도는 "무엇이 얼마나 렌더링되는지" 관찰하는 것입니다. 성능 최적화 기법은 이 과목 범위 밖이며 중급 과목에서 다룹니다.

코드에서 쓰는 `Profiler` 컴포넌트는 감싼 트리의 렌더링을 `onRender` 콜백으로 알려 줍니다.

```jsx
function onRender(id, phase, actualDuration) {
  console.log(id, phase, actualDuration)
}

<Profiler id="Sidebar" onRender={onRender}>
  <Sidebar />
</Profiler>
```

| 인수 | 뜻 |
|------|----|
| `id` | `Profiler`의 `id` Props |
| `phase` | `mount`, `update`, `nested-update` 중 하나 |
| `actualDuration` | 이번 렌더링에 쓴 시간(ms) |
| `baseDuration` | 최적화 없이 전체를 다시 그릴 때의 추정 시간(ms) |

- 프로덕션 빌드에서는 기본으로 꺼져 있고, 프로덕션 성능을 재려면 별도 프로파일링 빌드가 필요합니다.
- `Profiler`는 CPU와 메모리 부하를 추가하므로 필요한 곳에만 둡니다.

## Props

Props 문제는 부모가 넘긴 값이 자식이 기대한 값과 다른 경우입니다. 증상은 `undefined`, 빈 화면, 잘못된 표시입니다.

- Components 패널에서 문제의 컴포넌트를 선택하고 Props 목록을 봅니다. 이름 오타(`userName`과 `username`), 값 누락, 잘못된 타입(문자열 `'5'`와 숫자 `5`)이 가장 흔합니다.
- 부모에서 자식으로 갈 때 값이 사라지는 지점을 찾으려면 트리를 위로 올라가며 각 컴포넌트의 Props를 비교합니다. 중간 컴포넌트가 Props를 전달하지 않았을 수 있습니다.
- Props는 읽기 전용입니다. 자식이 Props를 고치려 하면 에러가 납니다. 값을 바꾸려면 부모의 State를 바꿉니다(자세히는 05편, 14편).
- 객체를 JSX에 직접 렌더링하면 `Objects are not valid as a React child` 에러가 납니다. 객체의 필드를 꺼내서 렌더링합니다.
- 구조 분해에서 틀린 이름을 쓰면 값은 `undefined`가 되고 에러가 나지 않습니다. DevTools의 실제 Props 이름과 코드의 이름을 대조합니다.

```jsx
function Avatar({ imageUrl }) {   // ❌ 부모는 src로 넘김
  return <img src={imageUrl} />   // src가 undefined
}
// <Avatar src="/me.png" />
```

## State

State 문제는 값이 바뀌지 않거나 예상과 다르게 바뀌는 경우입니다. 먼저 DevTools의 State 값이 바뀌었는지 봅니다. 구분이 원인 후보를 절반으로 줄여 줍니다.

| 관찰 | 의미 | 의심할 곳 |
|------|------|-----------|
| State가 안 바뀜 | Setter가 안 불렸거나 같은 값 | 이벤트 연결, 직접 변경, 같은 참조 |
| State는 바뀌는데 화면이 안 바뀜 | 화면 계산 쪽 문제 | 조건부 렌더링, key, 파생 값 |
| State가 바뀌지만 오래된 값이 보임 | 클로저가 이전 값을 잡음 | Stale Closure |
| 바뀌는 순간이 예상과 다름 | 스냅샷과 배칭 | 10편 |

- 직접 변경(`state.items.push(x)`)이 가장 흔한 원인입니다. 같은 참조라서 React가 변화를 못 보고 렌더링을 건너뜁니다(자세히는 09편, 11편).
- `setCount(count + 1)`을 연달아 호출하면 한 번만 증가합니다. 같은 스냅샷을 읽기 때문입니다(자세히는 10편).
- Setter 호출 직후 State를 읽으면 이전 값입니다. 값을 확인하려면 렌더링 중 `console.log`나 DevTools로 봅니다.
- DevTools에서 State를 직접 바꿔 화면이 맞게 반응하면 State 갱신 로직이, 안 맞으면 렌더링 쪽이 문제입니다.
- `useReducer`를 쓰면 reducer 안에서 `console.log(state, action)`으로 모든 변경과 원인 action을 볼 수 있습니다(자세히는 25편).
- 렌더링 중에 Setter를 무조건 호출하거나 이벤트 핸들러를 넘기지 않고 호출하면(`onClick={handle()}`) `Too many re-renders`가 납니다.

## Context

Context 문제는 값이 기본값으로 나오거나, 값이 바뀌어도 소비하는 컴포넌트가 반응하지 않는 경우입니다.

- Components 패널에서 Provider 노드를 선택하면 `value` Props로 현재 Context 값을 볼 수 있습니다. Provider가 트리에 있는지, 문제의 컴포넌트가 Provider 안쪽에 있는지 확인합니다.
- 값이 기본값(`createContext(기본값)`의 인수)으로 나오면 대부분 Provider 바깥에서 읽은 것입니다(자세히는 24편).
- Provider가 중첩되어 있으면 가장 가까운 Provider의 값이 쓰입니다. 의도하지 않은 안쪽 Provider가 값을 가리는지 봅니다.
- Provider의 `value`에 `{ a, b }` 객체를 렌더링마다 새로 만들어 넘기면 값이 같아도 새 객체라서 소비하는 모든 컴포넌트가 다시 렌더링됩니다.
- Context 값을 State로 보관한다면 State가 바뀌는지부터 Components 패널에서 확인합니다.

## 렌더 원인

컴포넌트가 다시 렌더링되는 원인은 세 가지입니다. State 변경, 부모의 렌더링, Context 값 변경입니다. Props 변경은 부모가 렌더링되면서 새 Props를 넘기는 결과입니다(자세히는 17편).

| 원인 | 확인 방법 |
|------|-----------|
| 자신의 State 변경 | Components 패널에서 State 값이 바뀌었는지 |
| 부모의 렌더링 | 부모에도 같은 시각에 렌더링이 일어났는지 |
| Context 변경 | 소비하는 Context의 Provider 값이 바뀌었는지 |

원하지 않는 렌더링을 추적하는 방법은 다음과 같습니다.

- DevTools Profiler 설정에서 변경된 Props와 State 기록을 켜고 기록하면, 커밋마다 어떤 값이 바뀌어 컴포넌트가 렌더링됐는지 표시됩니다.
- 렌더링 중에 `console.log('Item render', id)`를 넣어 호출 횟수와 순서를 확인합니다. 로그 출력은 렌더링 중 부수 효과이므로 확인이 끝나면 지웁니다.
- 특정 값이 바뀌는 시점을 알려면 Effect에서 그 값을 로그로 찍습니다.

```jsx
useEffect(() => {
  console.log('options changed', options)
}, [options]) // 찍힐 때마다 참조가 바뀐 것
```

- 렌더링이 많다는 것만으로는 버그가 아닙니다. 화면이 느리거나 입력이 끊기는 등 증상이 있을 때만 줄입니다. 부모가 렌더링되면 자식도 렌더링되는 것은 정상입니다.
- 같은 입력에 매번 다른 결과가 나오면 렌더링이 순수하지 않은 것입니다. `Math.random()`, `Date.now()`, 외부 변수 변경이 렌더링 중에 있는지 봅니다(자세히는 04편).

## Hook 순서 오류

Hook 순서 오류는 렌더링마다 Hook의 호출 횟수나 순서가 달라져 React가 State를 올바른 Hook에 연결하지 못하는 오류입니다(자세히는 26편).

| 에러 메시지 | 뜻 |
|-------------|----|
| `Rendered more hooks than during the previous render.` | 이번 렌더링이 이전보다 Hook을 더 많이 호출했다 |
| `Rendered fewer hooks than expected. This may be caused by an accidental early return statement.` | Hook이 예상보다 적게 호출됐다. 조기 return이 의심된다 |
| `Invalid hook call. Hooks can only be called inside of the body of a function component.` | Hook을 허용되지 않는 곳에서 호출했다 |

- 앞의 두 에러는 거의 항상 조건문, 반복문, 조기 return 뒤에서 Hook을 호출해서 생깁니다.

```jsx
function Profile({ user }) {
  if (!user) return null              // ❌ 이 뒤의 Hook이 건너뜀
  const [open, setOpen] = useState(false)
}
```

- 해결은 모든 Hook을 컴포넌트 최상위의 조기 return보다 위로 옮기는 것입니다.
- `Invalid hook call`의 원인 후보는 공식 메시지가 세 가지를 듭니다. React와 렌더러(React DOM)의 버전 불일치, Hook 규칙 위반, 앱에 React가 두 벌 이상 설치된 경우입니다.
- 이벤트 핸들러, 일반 함수, 클래스 컴포넌트 안에서 Hook을 호출해도 같은 에러가 납니다.
- 같은 Hook 규칙은 `eslint-plugin-react-hooks`의 `rules-of-hooks` 규칙이 편집 중에 잡아 줍니다. 린트 경고를 그대로 두지 않습니다(자세히는 26편).
- 패키지 중복은 `npm ls react`로 설치된 React 개수를 확인합니다.

## Hydration 오류

Hydration 오류는 서버가 만든 HTML과 브라우저에서 처음 렌더링한 결과가 달라서 생기는 오류입니다. 서버 렌더링을 쓰는 앱에서만 일어나며, Hydration 자체는 01편에서 소개했고 SSR 구성은 고급 과목의 범위입니다.

대표 메시지는 다음과 같습니다.

```text
Hydration failed because the server rendered HTML didn't
match the client. As a result this tree will be regenerated
on the client.
```

공식 에러 설명이 드는 원인은 다음과 같습니다.

- 서버와 브라우저를 나누는 분기(`typeof window !== 'undefined'`)로 서로 다른 결과를 렌더링했다.
- `Date.now()`, `Math.random()`처럼 호출할 때마다 달라지는 값을 렌더링에 썼다.
- 서버와 사용자의 로케일이 달라 날짜 형식이 다르게 나왔다.
- 변하는 외부 데이터를 HTML에 스냅샷으로 함께 보내지 않았다.
- 잘못된 HTML 태그 중첩(`p` 안에 `div`, `a` 안에 `a` 등)이 있다.
- 브라우저 확장이 React가 로드되기 전에 HTML을 바꿨다.

- React 19는 hydration 오류에 서버와 클라이언트 내용의 차이(diff)를 보여 주는 하나의 메시지를 출력합니다. 메시지의 diff에서 달라진 요소를 찾습니다.
- 첫 렌더링은 서버와 같아야 합니다. 브라우저에서만 알 수 있는 값(현재 시각, 화면 크기, `localStorage`)은 첫 렌더링에서는 서버와 같은 값을 쓰고, 마운트된 뒤 Effect에서 State로 갱신합니다.

```jsx
const [time, setTime] = useState(null) // 서버와 같은 첫 값
useEffect(() => setTime(new Date().toLocaleString()), [])
```

- 피할 수 없는 차이(타임스탬프)는 해당 요소에 `suppressHydrationWarning`을 쓸 수 있습니다. 한 단계 깊이까지만 효과가 있는 비상구입니다.
- 공식 문서는 hydration 불일치를 버그로 보고 고치라고 합니다. React가 복구하지 못하면 이벤트 핸들러가 엉뚱한 요소에 붙을 수 있습니다.
- 에러 `422`, `423`은 오류에서 복구해 가장 가까운 `Suspense` 경계 또는 루트 전체를 클라이언트에서 다시 렌더링했다는 메시지입니다.

## Effect 무한루프

Effect 무한 루프는 Effect가 State를 바꾸고, 그 변경이 다시 같은 Effect를 실행시키는 일이 끝없이 반복되는 현상입니다. 화면이 멈추거나 네트워크 요청이 쏟아집니다(원인 3가지는 21편).

| 형태 | 예 |
|------|----|
| 의존성 배열 없음 + Effect에서 State 변경 | `useEffect(() => { setCount(c => c + 1) })` |
| 렌더링마다 새로 만드는 값이 의존성 | `const opts = { id }` 를 `[opts]`에 넣음 |
| State를 읽고 쓰면서 의존성에 둠 | `setCount(count + 1)`을 하면서 `[count]` |

```jsx
function Bad({ id }) {
  const options = { id }          // 렌더링마다 새 객체
  useEffect(() => {
    fetchData(options).then(setData)
  }, [options])                   // ❌ 매번 새 값 → 무한 반복
}
```

- 개발 모드에서는 React가 `Maximum update depth exceeded. This can happen when a component calls setState inside useEffect, but useEffect either doesn't have a dependency array, or one of the dependencies changes on every render.`라는 경고를 콘솔에 냅니다. 이 문장이 형태 1과 2를 정확히 가리킵니다.
- 해결은 형태별로 다릅니다. 의존성 배열을 명시하고, 객체나 함수를 Effect 안으로 옮기거나 원시 값(`id`)만 의존성에 두고, State 갱신은 업데이터 함수(`setCount(c => c + 1)`)로 바꿔 의존성에서 State를 뺍니다.
- 먼저 질문합니다. 이 State 갱신이 정말 Effect에서 해야 하는 일입니까. 계산으로 만들 수 있거나 이벤트 핸들러에서 할 수 있다면 Effect를 없앱니다(자세히는 22편).
- 원인을 찾는 방법은 Effect 첫 줄에 `console.log`를 넣어 호출 빈도를 확인하고, 의존성 항목을 하나씩 로그로 찍어 매번 달라지는 값을 찾는 것입니다.
- 렌더링 중에 State를 무조건 바꾸면 `Too many re-renders`가 납니다. Effect가 아니라 렌더링 본문에서 일어난 루프입니다.

## Stale Closure

Stale Closure는 Effect나 콜백이 만들어질 때의 렌더링 값을 계속 쓰는 바람에 오래된 값을 읽는 현상입니다. 렌더링마다 Props, State, 함수는 그 렌더링 값을 담은 새 클로저를 가지는데, 오래 사는 콜백이 옛 클로저를 붙잡고 있는 것입니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0)
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1)          // count는 항상 0
    }, 1000)
    return () => clearInterval(id)
  }, [])                           // ❌ count를 빠뜨림
  return <p>{count}</p>            // 1에서 멈춤
}
```

- Effect는 만들어질 때 읽은 `count`(0)만 봅니다. 의존성 배열이 비어서 다시 만들어지지 않으므로 계속 `setCount(0 + 1)`을 호출합니다.
- 원인은 대부분 의존성을 빠뜨린 것입니다. `exhaustive-deps` 린트 경고를 무시하면 이런 버그가 생깁니다. 린트가 틀렸다고 판단하기 전에 코드의 의도를 바꾸는 쪽을 먼저 봅니다(자세히는 21편).
- 해결 방법은 상황에 따라 세 가지입니다.

| 방법 | 쓸 때 |
|------|-------|
| 업데이터 함수 `setCount(c => c + 1)` | 이전 State로 새 State를 만들 때. 의존성에서 State가 빠진다 |
| 의존성에 값을 넣음 | 값이 바뀔 때 Effect를 다시 동기화해야 할 때 |
| `useEffectEvent` | 최신 값을 읽되 값이 바뀌어도 Effect를 다시 실행하고 싶지 않을 때 |

```jsx
setInterval(() => setCount((c) => c + 1), 1000) // ✅ 업데이터
```

- 이벤트 핸들러에서 오래 걸리는 비동기 코드 안의 값이 클릭 시점 값인 것은 버그가 아니라 스냅샷 규칙입니다. 최신 값이 필요하면 업데이터 함수나 ref를 씁니다(자세히는 10편, 19편).
- `setTimeout`, 구독 콜백, 이벤트 리스너를 Effect에서 등록할 때도 같은 문제가 일어납니다. 콜백이 어느 렌더링의 값을 보는지 따져 봅니다.

## Key 문제

key 문제는 리스트의 `key`가 없거나 중복되거나 불안정해서 생기는 증상입니다. 콘솔 경고와 이상한 화면 동작으로 나타납니다(자세히는 07편).

- `Each child in a list should have a unique "key" prop.` 경고는 `map`으로 만든 요소에 `key`가 없다는 뜻입니다.
- 키는 형제 사이에서 유일해야 합니다. 다른 배열의 요소와 같은 키여도 괜찮습니다.
- 키는 바뀌면 안 됩니다. `Math.random()`처럼 렌더링 중 만든 키는 매번 달라서 모든 컴포넌트와 DOM을 다시 만들고, 리스트 안의 입력값도 잃습니다.
- 인덱스를 키로 쓰면 항목이 삽입·삭제·정렬될 때 키와 데이터의 짝이 어긋나서 입력값이나 State가 엉뚱한 항목에 남는 증상이 생깁니다. 데이터 기반의 안정적인 id를 씁니다.

```jsx
{items.map((item, i) => (
  <Row key={i} item={item} />   // ❌ 첫 항목 삭제 시 State가 밀림
))}
{items.map((item) => (
  <Row key={item.id} item={item} /> // ✅
))}
```

- `key`는 `map`이 반환하는 가장 바깥 요소에 붙입니다. 안쪽 요소에 붙이면 경고가 계속됩니다.
- 하나의 항목이 여러 요소를 반환하면 `<>`로는 `key`를 줄 수 없고 `Fragment`를 명시해 `key`를 붙입니다.

```jsx
<Fragment key={person.id}>
  <h1>{person.name}</h1>
  <p>{person.bio}</p>
</Fragment>
```

- 증상으로 의심할 수 있는 경우: 리스트의 입력값이 다른 항목으로 옮겨 감, 항목을 지웠는데 뒤쪽 항목의 State가 바뀜, 정렬하면 애니메이션이나 포커스가 이상함. 모두 인덱스 키가 첫 번째 용의자입니다.
- 키를 이용한 의도적인 State 초기화는 정상 기법입니다(자세히는 13편).

## StrictMode

StrictMode는 개발 모드에서만 추가 검사를 해서 순수하지 않은 코드와 Effect 정리 누락 같은 버그를 드러내는 도구입니다(자세히는 18편). `StrictMode`로 감싼 트리에서 다음 검사가 일어납니다.

| 검사 | 동작 |
|------|------|
| 이중 렌더링 | 컴포넌트를 한 번 더 렌더링해 순수하지 않은 렌더링을 찾는다 |
| Effect 재실행 | setup → cleanup → setup으로 정리 누락을 찾는다 |
| ref 콜백 재실행 | ref 콜백도 setup과 cleanup을 한 번 더 한다 |
| Deprecated API 검사 | `UNSAFE_` 생명주기 같은 사용 중단된 API를 경고한다 |

- 모든 검사는 개발 모드에서만 작동하고 프로덕션에는 영향이 없습니다.
- StrictMode가 드러낸 현상은 버그의 원인이 아니라 증상입니다. 이중 렌더링에서 결과가 달라지면 렌더링 중에 값을 변경하거나 부수 효과를 일으키고 있는 것이고, Effect 재실행에서 문제가 생기면 cleanup이 빠진 것입니다.
- 예를 들어 렌더링 중 Props 배열에 `push`하면 이중 렌더링에서 항목이 두 번 추가되어 문제가 드러납니다. `slice()`로 복사해서 고칩니다.
- StrictMode 안쪽 일부만 검사에서 빼는 방법은 없습니다. 검사를 끄려고 StrictMode를 제거하지 말고 코드를 고칩니다.
- 개발 중에만 동작이 다르게 보여 혼란스러운 점을 아래 "로그가 두 번 찍히는 이유"에서 다룹니다.

## 에러 메시지 읽는 법

에러 메시지는 무엇이 잘못됐는지(메시지), 어디서 일어났는지(스택)를 담고 있습니다. 정해진 순서로 읽으면 원인에 빠르게 접근합니다.

1. 첫 줄의 에러 이름과 메시지를 읽습니다. `TypeError: Cannot read properties of undefined (reading 'name')`은 `undefined`의 `name`을 읽으려 했다는 뜻이고, 어떤 값이 `undefined`인지가 문제입니다.
2. 스택 트레이스에서 내 코드가 나오는 첫 줄을 찾습니다. `node_modules`나 React 내부 코드는 건너뜁니다. 파일 이름과 줄 번호가 있습니다.
3. 개발 모드에서는 React가 경고에 컴포넌트 위치 정보를 덧붙입니다. 어느 컴포넌트에서 났는지 확인합니다.
4. 데이터가 원인이면 그 위치에서 값을 `console.log`로 찍어 실제 값을 봅니다.
5. 에러는 보통 첫 번째 것만 원인입니다. 뒤따르는 에러는 첫 에러의 결과일 수 있으므로 위에서부터 처리합니다.

| 메시지 | 흔한 원인 |
|--------|-----------|
| `Cannot read properties of undefined` | 아직 로딩 중인 데이터, 잘못된 Props 이름 |
| `Objects are not valid as a React child` | 객체나 `Promise`를 JSX에 그대로 렌더링 |
| `Too many re-renders` | 렌더링 중 Setter 호출, 핸들러를 호출해서 전달 |
| `Rendered more hooks than during the previous render` | 조건문 안의 Hook |
| `Each child in a list should have a unique "key" prop` | `map`에 `key` 누락 |
| `Hydration failed ...` | 서버와 클라이언트의 첫 렌더링 불일치 |

- React 19는 렌더링 에러를 한 번만 상세 정보와 함께 기록합니다. 이전 버전은 같은 에러를 여러 번 출력했습니다.
- 루트 생성 옵션 `onCaughtError`, `onUncaughtError`, `onRecoverableError`로 Error Boundary가 잡은 에러, 잡지 못한 에러, 자동 복구된 에러를 각각 처리할 수 있습니다.
- 에러가 화면 전체를 비우는 것은 렌더링 중 에러를 Error Boundary가 잡지 못해 트리를 제거하기 때문입니다. Error Boundary는 이 과목 범위 밖입니다(중급 과목).
- 에러 메시지를 검색할 때는 메시지 전체를 따옴표로 묶고 라이브러리 이름이나 버전을 덧붙이면 정확도가 올라갑니다.

## Minified error 해독

프로덕션 빌드의 React는 번들 크기를 줄이려고 에러 메시지 전문을 담지 않고 오류 코드와 링크만 남깁니다. 이것이 Minified error입니다.

```text
Minified React error #418; visit
https://react.dev/errors/418?args[]=HTML&args[]=
for the full message or use the non-minified dev
environment for full errors and additional helpful warnings.
```

- 링크의 `react.dev/errors/숫자`에서 전체 메시지와 설명을 볼 수 있습니다. URL의 `args[]` 값은 메시지의 `%s` 자리를 채우는 값입니다.
- 공식 문서는 로컬 개발에서는 개발 빌드로 디버깅해 전체 메시지를 받고, 배포 전에 프로덕션 빌드로 확인하라고 권합니다.
- 자주 보는 코드는 다음과 같습니다.

| 코드 | 메시지 |
|------|--------|
| 300 | Rendered fewer hooks than expected |
| 301 | Too many re-renders |
| 310 | Rendered more hooks than during the previous render |
| 321 | Invalid hook call |
| 418 | Hydration failed because the server rendered HTML didn't match the client |
| 423 | 오류에서 복구해 루트 전체를 클라이언트에서 다시 렌더링 |

- 프로덕션에서만 나는 에러는 개발 환경에서 재현되지 않을 수 있습니다. 같은 입력과 데이터로 `npm run build` 후 `npm run preview`(Vite)로 프로덕션 빌드를 로컬에서 실행해 확인합니다(자세히는 02편).
- 소스맵을 올려 두면 에러 추적 서비스가 압축된 스택 트레이스를 원래 파일과 줄 번호로 되돌려 줍니다. 서비스 선택과 설정은 이 과목 범위 밖입니다(고급 과목의 운영 편).

## 로그가 두 번 찍히는 이유

컴포넌트 안의 `console.log`가 두 번 찍히는 가장 흔한 이유는 개발 모드의 StrictMode가 컴포넌트를 한 번 더 렌더링하기 때문입니다. 버그가 아니라 의도된 동작입니다.

```jsx
function App() {
  console.log('render')   // 개발 모드: 두 번, 프로덕션: 한 번
  return <h1>Hi</h1>
}
```

- React DevTools를 설치했다면 두 번째 렌더링의 `console.log`는 약간 흐리게 표시됩니다. 설정으로 두 번째 렌더링의 로그를 완전히 숨길 수 있습니다(기본은 꺼짐).
- Effect 안의 로그가 마운트 때 두 번 나오는 것은 StrictMode가 setup → cleanup → setup을 한 번 더 실행하기 때문입니다. cleanup에서 정리가 제대로 되는지 검증하는 과정입니다.

```jsx
useEffect(() => {
  console.log('connect')       // 개발 모드 마운트 시 두 번
  return () => console.log('disconnect') // 그 사이에 한 번
}, [])
```

- StrictMode가 이중 렌더링하는 대상은 컴포넌트 본문, `useState`·`useMemo`·`useReducer`에 넘긴 함수, Setter에 넘긴 업데이터 함수입니다. 이벤트 핸들러는 실제 이벤트 때 한 번만 실행됩니다.
- 로그가 두 번 찍히는 다른 이유도 있습니다. 같은 컴포넌트가 두 번 마운트되었거나, State가 바뀌어 정상적으로 두 번 렌더링되었거나, 의존성이 바뀌어 Effect가 다시 실행된 경우입니다. 로그에 렌더링 횟수나 의존성 값을 같이 찍어 구분합니다.
- 두 번 실행되어 문제가 생기면 부수 효과가 렌더링 안에 있는 것입니다. 로그가 두 번 나오는 것을 없애려 StrictMode를 끄지 말고, 한 번 하는 일(예: 분석 이벤트 전송)은 이벤트 핸들러로 옮깁니다(자세히는 18편, 22편).

## 핵심 정리

- React DevTools의 Components 패널로 트리, Props, State, Provider 값을 확인하고 값을 바꿔 보며, Profiler로 커밋과 렌더링된 컴포넌트를 기록합니다.
- 렌더링의 원인은 자신의 State 변경, 부모의 렌더링, Context 값 변경 셋입니다. State가 바뀌었는지 먼저 확인해 원인을 좁힙니다.
- Hook 순서 오류(`Rendered more/fewer hooks`)는 조건문·조기 return 뒤 Hook에서, Effect 무한 루프는 의존성 배열 문제에서, Stale Closure는 의존성 누락에서 생깁니다.
- key 문제는 인덱스·랜덤 키가 원인이고, Hydration 오류는 서버와 첫 클라이언트 렌더링의 불일치입니다.
- StrictMode는 개발 모드에서만 이중 렌더링과 Effect 재실행으로 버그를 드러내므로 로그가 두 번 찍히는 것은 정상이며, 끄지 말고 코드를 고칩니다.
- 에러는 첫 줄의 메시지와 내 코드가 나오는 첫 스택 줄을 읽고, 프로덕션의 Minified error는 `react.dev/errors/코드`에서 전체 메시지를 확인합니다.

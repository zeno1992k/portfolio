## Create React App 지원 종료

Create React App(CRA)은 2025년 2월 14일 React 팀이 새 앱에 쓰지 말라고 공식 발표한(deprecated) 프로젝트 생성 도구입니다.

- 새로 설치하면 지원 종료 경고가 나옵니다.
- 유지보수 모드로 계속 동작하고 React 19와 호환되는 버전이 배포되었지만, 활발히 관리하는 사람이 없습니다.
- 라우팅, 데이터 요청, 코드 분할 같은 문제를 빌드 도구 단계에서 해결할 수 없다는 한계가 배경입니다.
- 공식 문서가 안내하는 이전 경로는 세 가지입니다.

| 선택 | 대상 |
|------|------|
| 프레임워크로 이전 | Next.js, React Router, Expo. 대부분의 운영 앱에 권장 |
| 빌드 도구로 이전 | Vite, Parcel, Rsbuild. 특수한 제약이 있는 앱 |
| 직접 구성 | 학습 목적이나 자체 프레임워크 |

**흔한 실수:** 오래된 블로그나 강의를 따라 `npx create-react-app`을 실행하는 것입니다. 이 과목은 Vite를 기준으로 합니다.

## 패키지 매니저(npm·pnpm)

패키지 매니저는 프로젝트가 쓰는 라이브러리를 내려받아 `node_modules`에 설치하고 버전을 관리하는 도구입니다. Node.js를 설치하면 npm이 함께 들어 있습니다.

| 작업 | npm | pnpm |
|------|-----|------|
| Vite 프로젝트 생성 | `npm create vite@latest` | `pnpm create vite` |
| 의존성 설치 | `npm install` | `pnpm install` |
| 개발 서버 실행 | `npm run dev` | `pnpm dev` |

- 프로젝트의 `package.json`에서 `dependencies`는 실행에 필요한 패키지(react 등), `devDependencies`는 개발 도구(타입, 린터, 빌드 도구)입니다. `scripts`에는 `dev`, `build` 같은 명령을 등록합니다.
- pnpm은 패키지를 컴퓨터에 한 번만 저장하고 하드 링크로 여러 프로젝트가 공유해서 디스크를 아끼고 설치가 빠릅니다. 또 프로젝트가 직접 선언한 패키지만 `node_modules` 최상위에 노출해서, 선언하지 않은 패키지를 우연히 가져다 쓰는 일을 막습니다.
- 한 프로젝트에서는 매니저 하나만 씁니다. 섞어 쓰면 각 매니저의 잠금 파일(`package-lock.json` 등)이 서로 어긋납니다.

## Vite

Vite는 개발 서버와 프로덕션 빌드를 제공하는 프런트엔드 빌드 도구입니다. 확인한 최신 버전은 Vite 8이며(2026-03-12 출시) 단일 번들러로 Rolldown을 씁니다. Node.js 20.19 이상 또는 22.12 이상이 필요합니다.

```bash
npm create vite@latest my-app -- --template react-ts
cd my-app
npm install
npm run dev
```

- `react-ts` 템플릿은 TypeScript, `react` 템플릿은 JavaScript입니다.
- 템플릿에는 `dev`, `build`, `preview` 세 스크립트가 들어 있습니다.
- `index.html`은 `public` 폴더가 아니라 프로젝트 루트에 있고, Vite가 모듈 그래프의 일부로 다룹니다.
- React 지원은 `@vitejs/plugin-react` 플러그인이 맡습니다. 개발 중 Fast Refresh(저장하면 상태를 유지한 채 컴포넌트만 갱신)와 자동 JSX 런타임을 설정합니다.
- Vite 자체는 클라이언트 전용 SPA의 뼈대만 제공합니다. 라우팅, 데이터 요청, SSR은 직접 고르거나 프레임워크를 써야 합니다(React 공식 문서의 설명).

## 개발 서버

개발 서버는 소스를 저장할 때마다 브라우저에 바로 반영해 주는 로컬 서버입니다. `npm run dev`로 시작합니다.

- 기본 주소는 `http://localhost:5173`입니다. 포트가 사용 중이면 다음 포트를 자동으로 시도하고, `server.strictPort`를 켜면 바로 종료합니다.
- HMR(Hot Module Replacement)은 바뀐 모듈만 교체해 전체 새로고침 없이 반영하는 기능입니다. React에서는 플러그인이 Fast Refresh로 이어 줍니다.
- 기본 호스트는 `localhost`라서 같은 네트워크의 다른 기기에서 접속하려면 `server.host`를 바꿔야 합니다.
- `server.proxy`는 `/api` 같은 경로의 요청을 다른 서버로 넘기는 설정입니다(API 통신은 27편).
- 개발 서버는 개발 편의용입니다. 배포 결과물의 동작과 성능은 프로덕션 빌드로 확인합니다.

## Production Build

프로덕션 빌드는 소스를 배포용 정적 파일로 묶는 과정입니다. `npm run build`는 내부적으로 `vite build`를 실행하고, 결과는 기본으로 `dist` 폴더에 생깁니다.

```bash
npm run build     # dist 폴더 생성
npm run preview   # dist를 로컬에서 확인
```

- `dist`는 정적 호스팅에 그대로 올릴 수 있습니다.
- `vite preview`는 빌드 결과를 로컬에서 확인하는 용도이고, 기본 주소는 `http://localhost:4173`입니다. 공식 문서는 운영 서버로 쓰지 말라고 명시합니다.
- 기본 빌드 대상 브라우저는 Chrome 111 이상, Edge 111 이상, Firefox 114 이상, Safari 16.4 이상입니다. `build.target`으로 바꿀 수 있습니다.
- 서비스를 도메인 루트가 아닌 하위 경로(`/app/`)에 올리면 `base` 옵션을 맞춰야 에셋 경로가 깨지지 않습니다. 기본값은 `/`입니다.
- 개발 서버와 프로덕션 빌드는 다릅니다. StrictMode의 이중 렌더링 같은 개발 전용 검사는 프로덕션에서 동작하지 않습니다.

**흔한 실수:** 개발 서버에서 되니까 빌드도 될 것이라고 믿고 배포 직전에야 빌드하는 것입니다. 타입 오류나 경로 문제는 빌드에서 처음 드러날 수 있어서 자주 실행해 봅니다.

## 환경 변수

환경 변수는 코드 밖에서 주입하는 설정값(API 주소 등)입니다. Vite에서는 `import.meta.env`로 읽습니다.

```js
const api = import.meta.env.VITE_API_URL
const isDev = import.meta.env.DEV
```

내장 값은 다음과 같습니다.

| 값 | 의미 |
|----|------|
| `MODE` | 현재 모드(`development`, `production` 등) |
| `DEV` / `PROD` | 개발 / 프로덕션 여부(불리언) |
| `BASE_URL` | `base` 옵션 값 |
| `SSR` | 서버 렌더링 환경 여부 |

`.env` 파일은 다음 순서로 합쳐지며, 아래로 갈수록 우선합니다. 이미 설정된 시스템 환경 변수가 가장 높습니다.

| 파일 | 적용 |
|------|------|
| `.env` | 항상 |
| `.env.local` | 항상, git에서 제외 |
| `.env.[mode]` | 해당 모드에서만 |
| `.env.[mode].local` | 해당 모드에서만, git에서 제외 |

- 모드와 `NODE_ENV`는 별개입니다. `vite build --mode staging`은 `.env.staging`을 읽지만 `NODE_ENV`는 여전히 production입니다.
- `.env.local`처럼 `.local`이 붙은 파일은 개인용이라 저장소에 올리지 않습니다.
- `.local` 파일은 저장소에 없으므로 배포하는 곳(빌드 서버)에는 값을 따로 넣어야 합니다.

## 환경 변수 접두사(VITE_)

Vite는 이름이 `VITE_`로 시작하는 변수만 브라우저 코드에 노출합니다. 나머지는 노출되지 않습니다.

```bash
# .env
VITE_API_URL=https://api.example.com
DB_PASSWORD=secret   # 브라우저 코드에서 읽을 수 없음
```

- 노출된다는 것은 번들에 들어가 누구나 볼 수 있다는 뜻입니다. 공식 문서는 `VITE_` 변수에 API 키 같은 민감한 정보를 넣지 말라고 경고합니다.
- 접두사는 `envPrefix` 옵션으로 바꿀 수 있습니다. 빈 문자열로 설정하면 모든 변수가 노출되므로 Vite가 오류를 냅니다.
- TypeScript에서는 `vite-env.d.ts`에서 `ImportMetaEnv` 인터페이스를 확장하면 변수 이름이 자동 완성됩니다.
- Next.js에서는 같은 역할을 `NEXT_PUBLIC_` 접두사가 합니다. 이 값은 `next build` 때 번들에 고정되어 들어갑니다.

**흔한 실수:** 비밀 키를 `VITE_SECRET_KEY`로 만드는 것입니다. 접두사가 붙는 순간 공개 값이 됩니다. 비밀 값은 서버에서만 다룹니다.

## 프로젝트 구조

Vite의 React 템플릿은 다음과 같은 구조로 만들어집니다(템플릿 버전에 따라 파일이 조금 다릅니다).

```text
my-app/
├─ index.html          # 진입 HTML (루트에 위치)
├─ package.json        # 의존성과 scripts
├─ vite.config.ts      # Vite 설정
├─ tsconfig.json       # TypeScript 설정
├─ public/             # 그대로 복사되는 정적 파일
└─ src/
   ├─ main.tsx         # 진입점: createRoot
   ├─ App.tsx          # 루트 컴포넌트
   └─ index.css        # 전역 스타일
```

진입점 `main.tsx`는 앞 편의 `createRoot`를 그대로 씁니다.

```tsx
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

- 끝의 `!`는 요소가 반드시 있다고 TypeScript에 알리는 단언입니다.
- `public`의 파일은 빌드 없이 그대로 제공되고, `src`에서 `import`한 에셋은 번들에 포함됩니다.
- 컴포넌트를 어떻게 나눌지는 React가 정해 두지 않습니다. 공식 문서가 소개하는 방식은 기능·라우트별로 묶는 방식과 파일 종류별로 묶는 방식 두 가지입니다.
- 같이 바뀌는 파일은 가까이 둡니다(colocation). 폴더 중첩은 3–4단계 이내로 하고, 구조를 고르는 데 5분 넘게 쓰지 말라는 것이 공식 권고입니다.
- 이 폴더 구조는 프레임워크가 정합니다. Next.js는 `app` 폴더의 `layout.tsx`와 `page.tsx` 같은 파일 이름이 규칙입니다(아래 "Next.js와 React").

## TypeScript

TypeScript는 JavaScript에 타입을 더한 언어이고, Vite 템플릿으로 바로 쓸 수 있습니다(문법은 별도 과목).

- JSX가 들어 있는 파일은 확장자를 `.tsx`로 씁니다. JSX가 없으면 `.ts`입니다.
- React 타입은 `@types/react`, `@types/react-dom` 패키지가 제공합니다. 템플릿에는 이미 들어 있습니다.
- `tsconfig.json`에서 `lib`에 `dom`이 있어야 하고 `jsx`가 유효한 값이어야 합니다.
- Vite는 `.ts`를 변환만 하고 타입 검사는 하지 않습니다. 타입 오류를 잡으려면 `tsc --noEmit`을 따로 실행해야 하며, 템플릿의 `build` 스크립트는 `tsc`를 먼저 실행하도록 되어 있습니다.

```tsx
type ButtonProps = { title: string; disabled?: boolean }

function MyButton({ title, disabled }: ButtonProps) {
  return <button disabled={disabled}>{title}</button>
}
```

- State 타입은 보통 초기값에서 추론됩니다. 값의 범위가 문자열 몇 개로 정해지면 `useState<Status>('idle')`처럼 타입을 명시합니다.
- 이 과목의 예시는 JavaScript(JSX)로 쓰고, TypeScript에서 달라지는 점은 필요한 곳에서만 언급합니다.

**흔한 실수:** 개발 서버가 에러 없이 동작하므로 타입이 맞다고 믿는 것입니다. Vite는 타입을 검사하지 않습니다.

## 경로 별칭

경로 별칭(path alias)은 `../../../components/Button`처럼 깊은 상대 경로를 `@/components/Button`처럼 프로젝트 루트 기준으로 줄여 쓰는 설정입니다.

Vite에서는 `resolve.alias`로 번들러에게 알려 줍니다.

```js
import { fileURLToPath } from 'node:url'

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
})
```

- 실제 모듈을 찾는 쪽이 번들러이므로 Vite 설정이 필요하고, TypeScript가 같은 규칙을 알도록 `tsconfig.json`의 `paths`도 맞춥니다. `paths`는 `tsc`가 내보내는 import 경로를 바꾸지 않습니다. 다른 도구가 같은 매핑을 처리한다고 TypeScript에 알려 주는 역할만 합니다.
- Vite 8에는 `resolve.tsconfigPaths` 옵션이 있어서 켜면 `tsconfig.json`의 `paths`를 그대로 씁니다. 기본값은 꺼짐(`false`)이고, tsconfig가 포함하는 파일에만 적용됩니다.
- `resolve.alias`는 먼저 적은 규칙이 먼저 적용됩니다.
- Next.js는 `tsconfig.json`의 `paths`를 기본 지원하며, `create-next-app` 기본값은 `@/*` 별칭입니다.

## ESLint

ESLint는 JavaScript 코드에서 버그가 될 수 있는 패턴과 일관성 문제를 찾아 알려 주는 린터입니다.

- 설정 파일은 `eslint.config.js`(또는 `.mjs`)의 flat config 형식입니다. 새로 설정할 때는 `npm init @eslint/config@latest`가 질문에 따라 만들어 줍니다.
- 실행은 `npx eslint 파일`입니다.
- React 프로젝트에서 중요한 것은 `eslint-plugin-react-hooks`입니다. `rules-of-hooks`는 Hook을 최상위에서만 호출했는지, `exhaustive-deps`는 의존성 배열에 필요한 값이 빠지지 않았는지 검사합니다(자세히는 21편, 26편).
- React 19.2부터 이 플러그인 v6의 `recommended` 프리셋은 flat config가 기본이며, React Compiler 기반 규칙도 포함합니다.
- 확인한 시점의 Vite `react-ts` 템플릿은 ESLint가 아니라 Oxlint로 린트합니다. 린터 구성은 템플릿 버전에 따라 다르므로 `package.json`의 `lint` 스크립트를 확인합니다.
- Next.js 16부터 `next build`는 린터를 자동 실행하지 않습니다. 린트는 스크립트로 직접 돌립니다.

**흔한 실수:** `exhaustive-deps` 경고를 `eslint-disable`로 끄는 것입니다. 경고는 대부분 실제 버그의 신호입니다(자세히는 21편).

## Prettier

Prettier는 코드 모양(줄바꿈, 따옴표, 들여쓰기)을 규칙대로 자동으로 맞추는 포매터입니다. 린터는 품질 문제를, Prettier는 서식을 맡는 것이 공식 권장 분담입니다.

```bash
npm install --save-dev --save-exact prettier
npx prettier --write .   # 파일을 수정
npx prettier --check .   # 검사만 (CI용)
```

- `--save-exact`는 버전을 고정합니다. Prettier가 릴리스마다 서식이 달라질 수 있어서, 팀원 간 결과를 맞추기 위한 권고입니다.
- 프로젝트 루트에 `.prettierrc`를 두면 편집기와 도구가 Prettier를 쓰는 프로젝트임을 알아봅니다. 제외할 파일은 `.prettierignore`에 적고, `.gitignore`가 있으면 그 규칙도 따릅니다.
- ESLint와 서식 규칙이 충돌하면 `eslint-config-prettier`로 겹치는 ESLint 규칙을 꺼 줍니다. `eslint-plugin-prettier`는 느리고 편집기 연동이 불편해 일반적으로 권장하지 않습니다.

## React DevTools

React Developer Tools는 컴포넌트 트리를 보고 Props와 State를 확인·수정하며 성능 문제를 찾는 브라우저 확장 프로그램입니다.

- Chrome, Firefox, Edge용 확장을 설치하면 React 사이트에서 개발자 도구에 Components와 Profiler 패널이 생깁니다.
- Safari처럼 확장을 못 쓰는 브라우저는 `react-devtools` 패키지를 전역 설치해 실행하고, 앱의 `head`에 스크립트 태그를 넣어 연결합니다.
- 모바일 React Native 앱은 React Native DevTools를 씁니다.
- 사용법과 렌더 원인 추적은 30편에서 다룹니다.

## StrictMode

StrictMode는 개발 중에만 추가 검사를 켜서 숨은 버그를 일찍 드러내는 컴포넌트입니다. Vite 템플릿의 `main.tsx`가 이미 `App`을 감싸고 있습니다.

```jsx
<StrictMode>
  <App />
</StrictMode>
```

- 개발 모드에서 컴포넌트를 두 번 렌더링하고, Effect의 setup과 cleanup을 한 번 더 실행하고, Ref 콜백을 한 번 더 실행하고, 폐기 예정 API를 경고합니다.
- 프로덕션 빌드에는 영향이 없습니다.
- 개발 중 콘솔 로그가 두 번 찍히는 것은 이 때문입니다. 버그가 아닙니다.
- 트리 일부만 감쌀 수 있지만, 감싼 안쪽에서 끌 방법은 없습니다.
- 각 검사의 의미와 대응은 18편에서 다룹니다.

## Next.js와 React

Next.js는 라우팅, 렌더링 방식, 데이터 요청, 번들링을 갖춘 React 풀스택 프레임워크입니다. React 공식 문서가 권하는 프레임워크 중 하나입니다.

```bash
npx create-next-app@latest my-app --yes
cd my-app
npm run dev
```

- 이 문서 작성 시점의 Next.js 문서는 16.3.8이며, Node.js 20.9 이상이 필요합니다. `--yes` 기본값은 TypeScript, ESLint, Tailwind CSS, App Router, Turbopack, `@/*` 별칭입니다.
- 파일 시스템 라우팅을 씁니다. `app/layout.tsx`가 모든 페이지를 감싸는 루트 레이아웃(필수, `html`과 `body` 포함)이고, `app/page.tsx`가 `/` 경로의 페이지입니다. 폴더가 URL 구간이 됩니다.
- 스크립트는 `next dev`, `next build`, `next start`이고, 개발 서버 기본 주소는 `http://localhost:3000`입니다.
- App Router는 React의 Canary 릴리스를 내장해서 쓰므로, `package.json`의 `react` 버전과 실제 동작 버전이 다를 수 있습니다. Pages Router는 `package.json`의 React 버전을 씁니다.
- 서버 컴포넌트와 SSR 설계는 이 과목의 범위 밖이고, Next.js는 별도 과목에서 다룹니다.

## React Router 기반 프로젝트

React Router v7은 라우팅 라이브러리이면서 Vite와 함께 쓰는 풀스택 프레임워크 모드를 제공합니다. 공식 문서가 권하는 프레임워크 중 하나입니다.

```bash
npx create-react-router@latest my-app
cd my-app
npm run dev
```

세 가지 모드가 있고, 뒤로 갈수록 이전 모드의 기능을 포함합니다.

| 모드 | 제공 | 적합한 경우 |
|------|------|-------------|
| Declarative | URL과 컴포넌트 매칭, `Link`, `useNavigate` | 최소 구성, 기존 데이터 계층 유지 |
| Data | `loader`, `action`, `RouterProvider` | 데이터 처리가 필요하면서 번들링을 직접 통제 |
| Framework | 타입 안전 라우트, 코드 분할, SPA·SSR·정적 렌더링 | 새 프로젝트 |

- 프레임워크 모드의 기본 파일은 `app/root.tsx`(루트 레이아웃), `app/routes.ts`(라우트 설정), `react-router.config.ts`(설정)입니다. 개발 서버는 `http://localhost:5173`에서 열리고, 스크립트는 `dev`, `build`, `start`입니다.
- 라우팅의 개념과 API는 29편에서 다룹니다.

## 핵심 정리

- CRA는 2025-02-14 새 앱에 쓰지 말라고 발표되었으며, 이전 경로는 프레임워크(Next.js·React Router·Expo) 또는 Vite 같은 빌드 도구입니다.
- Vite는 `npm run dev`(개발 서버, 5173), `npm run build`(dist 생성), `npm run preview`(빌드 확인, 4173)를 제공하고 라우팅·데이터 요청은 포함하지 않습니다.
- `import.meta.env`에서 `VITE_` 접두사 변수만 브라우저에 노출되며, 노출되는 값에 비밀 정보를 넣으면 안 됩니다.
- Vite는 TypeScript를 변환만 하고 검사하지 않으며, 경로 별칭은 번들러(`resolve.alias`)와 TypeScript(`paths`) 양쪽에 맞춰야 합니다.
- ESLint는 품질과 Hook 규칙을, Prettier는 서식을 맡고, React DevTools로 컴포넌트·Props·State를 확인합니다.
- StrictMode는 개발 모드에서만 이중 렌더링 같은 검사를 하고 프로덕션에는 영향이 없습니다.

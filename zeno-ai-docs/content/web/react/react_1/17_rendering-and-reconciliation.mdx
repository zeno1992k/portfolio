## 렌더링 개념

React에서 렌더링(rendering)은 React가 컴포넌트 함수를 호출해 화면이 어떻게 보여야 하는지 계산하는 일입니다. DOM을 바꾸는 일이 아니고, 브라우저가 화면을 그리는 일도 아닙니다. 화면 하나가 갱신되는 과정은 네 단계입니다.

| 단계 | 하는 일 |
|------|---------|
| 트리거(Trigger) | 렌더링을 요청한다 |
| 렌더(Render) | 컴포넌트를 호출해 UI 설명을 만든다 |
| 커밋(Commit) | 그 결과를 DOM에 반영한다 |
| 페인트(Paint) | 브라우저가 화면을 그린다 |

- 렌더링을 일으키는 이유는 두 가지뿐입니다. 컴포넌트가 처음 화면에 나타나는 최초 렌더링, 그리고 컴포넌트나 그 조상의 State가 `set` 함수로 바뀌는 경우입니다.
- 최초 렌더링은 `createRoot`로 루트를 만들고 `render()`를 호출할 때 시작됩니다(자세히는 01편).
- 렌더링 결과는 JSX가 만드는 엘리먼트 객체입니다. 엘리먼트는 UI 조각의 가벼운 설명이고 만들어도 DOM이 생기지 않습니다. 한번 만들어진 엘리먼트와 props는 바꾸지 않는 값으로 다룹니다. 개발 모드에서는 React가 이 객체를 얕게 동결합니다.

```jsx
const el = <h1 className="title">Hi</h1>
// el.type은 'h1', el.props는 { className, children }
// DOM 노드가 아니라 설명서일 뿐이다
```

## Render Phase

렌더 단계는 React가 컴포넌트 함수를 호출하고 반환된 JSX를 모으는 단계입니다.

- 최초 렌더링에서는 루트 컴포넌트부터 호출합니다.
- 재렌더링에서는 State가 바뀐 컴포넌트부터 호출합니다. 그 컴포넌트가 다른 컴포넌트를 반환하면 그것도 호출하며, 중첩된 컴포넌트가 더 없을 때까지 재귀적으로 이어집니다.
- 이 단계에서는 DOM을 건드리지 않습니다. 결과는 이전 렌더링의 결과와 비교할 재료가 됩니다.

렌더 단계는 계산만 하는 구간입니다. 그래서 렌더 중에 외부 값을 바꾸거나 요청을 보내면 안 됩니다(아래 "Pure Rendering").

## Commit Phase

커밋 단계는 렌더 결과를 실제 DOM에 반영하는 단계입니다.

- 최초 렌더링은 만들어 둔 DOM 노드를 `appendChild()`로 화면에 붙입니다.
- 재렌더링은 이번 결과와 맞추는 데 필요한 최소한의 DOM 작업만 합니다.
- 핵심 규칙은 렌더링 사이에 차이가 있을 때만 DOM 노드를 바꾼다는 것입니다. 컴포넌트가 다시 호출돼도 결과가 같으면 DOM은 그대로입니다.

```jsx
function Form({ title }) {
  return (
    <>
      <h1>{title}</h1>
      <input />
    </>
  )
}
// title이 바뀌면 h1의 글자만 갱신된다
// input은 건드리지 않아서 사용자가 친 글자가 남는다
```

- ref의 `current`는 커밋 단계에서 채워집니다. 첫 렌더링 중에는 `null`입니다(자세히는 19편).
- Effect는 커밋이 끝난 뒤에 실행됩니다(자세히는 20편).

## Browser Paint

페인트는 React가 DOM을 갱신한 뒤 브라우저가 그 결과를 화면에 그리는 단계입니다. React 문서는 혼동을 피하려고 이 단계를 렌더링이 아니라 페인팅이라고 부릅니다.

- 렌더링은 React의 계산, 페인팅은 브라우저의 그리기입니다. 둘은 별개의 단계입니다.
- 렌더 함수가 실행됐다고 화면이 바뀐 것은 아닙니다. 결과가 이전과 같으면 DOM도 바뀌지 않으므로 화면도 그대로입니다.
- Effect가 페인트 전에 실행될지 후에 실행될지는 Effect가 무엇 때문에 일어났는지에 따라 달라집니다(자세히는 20편).

## State와 재렌더링

State가 바뀌면 React는 그 State를 가진 컴포넌트의 재렌더링을 요청합니다. 최초 렌더링 이후의 렌더링 트리거는 State 변경입니다.

```jsx
function Counter() {
  const [n, setN] = useState(0)
  return <button onClick={() => setN(n + 1)}>{n}</button>
}
// 클릭 → setN → Counter 재렌더링 → n은 1 → 버튼 글자 갱신
```

- 같은 값으로 `set`을 호출하면 렌더링을 건너뛸 수 있습니다(자세히는 09편).
- 같은 이벤트 안의 여러 `set` 호출은 모아서 한 번만 렌더링합니다(자세히는 10편).
- 렌더링 중 변수는 그 렌더링의 State 스냅샷으로 고정됩니다(자세히는 10편).

## Props와 재렌더링

Props가 바뀌었다는 사실은 재렌더링의 트리거가 아닙니다. Props는 부모가 다시 렌더링되어 새 값을 내려보낼 때 바뀌고, 그 부모의 렌더링을 일으킨 것은 대개 어딘가의 State입니다.

- 자식은 Props가 같아도 부모가 재렌더링되면 같이 재렌더링됩니다(아래 "부모/자식 렌더링").
- Props가 바뀌어도 자식 안의 State는 유지됩니다. 같은 위치에 같은 타입이면 컴포넌트는 같은 것으로 취급되기 때문입니다(아래 "컴포넌트 타입").
- Props 비교로 자식 렌더링을 건너뛰는 도구가 `memo`입니다. 이 과목의 범위를 벗어나므로 중급 과목에서 다룹니다.

## 부모/자식 렌더링

컴포넌트가 재렌더링되면 그 아래의 자식 컴포넌트도 재귀적으로 모두 재렌더링됩니다. 자식의 Props가 그대로여도 마찬가지입니다.

```jsx
function Parent() {
  const [n, setN] = useState(0)
  return (
    <>
      <button onClick={() => setN(n + 1)}>+</button>
      <Child />
    </>
  )
}
// 클릭하면 Parent와 Child 함수가 모두 다시 호출된다
```

- 위로는 전파되지 않습니다. State가 바뀐 컴포넌트와 그 후손만 다시 호출되고 부모와 형제는 호출되지 않습니다.
- 다시 호출됐다는 것과 DOM이 바뀐다는 것은 다릅니다. 호출 결과가 같으면 커밋에서 DOM 변경이 없습니다.
- 자식에게 `memo`를 적용하면 Props가 같을 때 건너뜁니다. `memo`는 `Object.is`로 Props를 하나씩 비교합니다. React Compiler를 켜면 대부분 `memo`가 필요 없어집니다. 둘 다 이 과목의 범위 밖입니다.

## 함수 재실행

재렌더링은 컴포넌트 함수를 처음부터 다시 실행하는 일입니다. 함수 안의 지역 변수는 모두 새로 만들어지고, State만 React가 보관한 값으로 채워집니다.

```jsx
function Box() {
  let local = 0                 // 매번 0
  const [n, setN] = useState(0) // 보관된 값
  const list = []               // 매번 새 배열
  const handleClick = () => setN(n + 1) // 매번 새 함수
}
```

- 렌더링마다 함수, 객체, 배열은 새로 만들어지므로 이전 렌더링의 것과 `===`로 같지 않습니다.
- 이벤트 핸들러는 만들어진 렌더링의 State와 Props를 기억합니다(자세히는 10편).
- 컴포넌트를 직접 호출하면 안 됩니다. `Box()`가 아니라 `<Box />`로 쓰고 호출 시점은 React에 맡깁니다.

## 렌더 트리

렌더 트리(render tree)는 한 번의 렌더링에서 어떤 컴포넌트가 어떤 컴포넌트를 렌더링했는지 나타내는 트리입니다. 컴포넌트만 있고 `div` 같은 HTML 태그는 없습니다.

- 루트 노드는 첫 번째로 렌더링되는 루트 컴포넌트입니다.
- 루트에 가까운 상위 컴포넌트는 그 아래 전체의 렌더링에 영향을 줍니다. 자식 컴포넌트가 없는 맨 아래 컴포넌트는 리프이고 자주 재렌더링됩니다.
- 렌더 트리는 고정되지 않습니다. 조건부 렌더링과 데이터에 따라 렌더링마다 다른 컴포넌트가 들어가 트리 모양이 바뀝니다.
- 렌더 트리와 DOM 트리는 다릅니다. 컴포넌트 하나가 DOM 노드 여러 개나 0개를 만들 수 있습니다.
- State가 어디에 속하는지는 이 렌더 트리의 위치로 정해집니다(자세히는 13편).

## Pure Rendering

React는 모든 컴포넌트가 순수 함수라고 가정합니다. 순수 함수는 두 가지를 지킵니다.

- 자기 일만 합니다. 호출되기 전에 있던 객체나 변수를 바꾸지 않습니다.
- 같은 입력이면 같은 결과를 냅니다. 같은 Props, State, Context이면 같은 JSX를 반환합니다.

```jsx
let guest = 0
function Bad() {
  guest = guest + 1  // ❌ 렌더 중에 바깥 변수를 바꿈
  return <p>Guest {guest}</p>
}
function Good({ guest }) {
  return <p>Guest {guest}</p> // ✅ 입력으로 받음
}
```

- 렌더 중에 만든 지역 변수나 배열을 바꾸는 것(지역 변경)은 괜찮습니다. 렌더링 전부터 있던 값을 바꾸는 것이 문제입니다.
- Props, State, Context를 직접 바꾸지 않습니다. 바꿀 때는 `set` 함수를 씁니다.
- 컴포넌트가 렌더링되는 순서에 의존하면 안 됩니다. 컴포넌트는 서로 독립적입니다.
- 값을 바꾸는 코드는 이벤트 핸들러에 둡니다. 정말 맞는 곳이 없을 때만 Effect를 씁니다.
- 순수하지 않은 컴포넌트는 StrictMode가 두 번 호출해서 드러냅니다(자세히는 18편).

## Reconciliation

Reconciliation은 React가 이전 렌더링 결과와 이번 결과를 비교해 DOM에 어떤 변경이 필요한지 정하는 과정입니다. 렌더 단계의 결과를 커밋 단계의 DOM 작업으로 바꾸는 다리입니다.

- 두 트리를 완전히 비교하는 알고리즘은 요소가 n개일 때 O(n³)입니다. 요소 1000개면 10억 번 비교입니다. React는 두 가지 가정을 둔 휴리스틱으로 O(n)에 처리합니다.
- 가정 하나는 타입이 다른 두 엘리먼트는 다른 트리를 만든다는 것입니다. 다른 하나는 개발자가 `key`로 형제 중 렌더링 사이에 안정적인 것을 알려 줄 수 있다는 것입니다.
- 비교는 트리를 위에서 아래로 내려가며 같은 위치끼리 합니다.
- 이 과정을 흔히 Virtual DOM 비교라고 부릅니다. Virtual DOM은 UI의 이상적인 표현을 메모리에 두고 실제 DOM과 맞춘다는 프로그래밍 개념입니다. 브라우저의 Shadow DOM과는 별개입니다.
- Fiber는 React 16에서 도입된 재조정 엔진의 이름입니다. 렌더링을 쪼개고 우선순위를 줘서 한 번에 끝내지 않게 하는 점진적 렌더링이 목표였습니다. 내부 구현이라 컴포넌트를 쓸 때 직접 다루지 않습니다.

## Element 비교

React는 같은 위치의 이전 엘리먼트와 새 엘리먼트를 비교해 `type`이 같은지부터 봅니다.

| 비교 결과 | React의 처리 |
|-----------|--------------|
| 타입이 다름 | 이전 서브트리를 통째로 버리고 새로 만든다 |
| DOM 엘리먼트, 같은 타입 | 같은 DOM 노드를 두고 바뀐 attribute만 갱신한다 |
| 컴포넌트, 같은 타입 | 인스턴스(State)를 유지하고 Props만 새로 넘긴다 |

- 같은 DOM 엘리먼트에서 `style`이 바뀌면 바뀐 프로퍼티만 갱신합니다.
- 갱신 후에는 그 엘리먼트의 자식에 대해 같은 비교를 재귀적으로 합니다.
- 타입이 다르면 이전 서브트리의 DOM 노드는 삭제되고 그 안의 모든 컴포넌트는 언마운트되어 State를 잃습니다. 새 서브트리는 처음부터 마운트됩니다.

```jsx
// 이전
<div><Counter /></div>
// 이후
<section><Counter /></section>
// div → section 타입 변경 → Counter도 새로 만들어져 State 초기화
```

- 비교는 엘리먼트의 `type`과 `key`, 그리고 위치로 합니다. Props 값이 같은지는 보지 않습니다.

## 컴포넌트 타입

컴포넌트의 타입은 컴포넌트 함수 자체입니다. 같은 위치에 같은 함수가 오면 같은 컴포넌트이고, 다른 함수가 오면 다른 컴포넌트입니다.

```jsx
{isFancy ? <Counter fancy /> : <Counter />}
// 같은 위치, 같은 Counter → Props만 바뀌고 State 유지
{paused ? <p>Wait</p> : <Counter />}
// p와 Counter는 다른 타입 → 전환할 때마다 State 파괴
```

**흔한 실수:** 컴포넌트 안에서 컴포넌트를 선언하는 것입니다. 부모가 렌더링될 때마다 새 함수가 만들어지고, React는 타입이 달라졌다고 보고 서브트리를 버립니다. 입력창의 글자와 포커스가 매번 사라집니다.

```jsx
function Parent() {
  function Field() { /* useState... */ } // ❌ 매번 새 타입
  return <Field />
}
// ✅ Field를 Parent 밖, 파일 최상위로 옮긴다
```

## key와 Identity

`key`는 같은 위치 규칙 대신 엘리먼트의 정체성(identity)을 직접 지정하는 값입니다. key가 같으면 같은 것, 다르면 다른 것으로 봅니다.

- key가 바뀌면 같은 위치, 같은 타입이어도 이전 컴포넌트를 버리고 새로 만들어 State가 초기화됩니다. 폼을 대상이 바뀔 때마다 비우는 방법으로 씁니다.
- key를 그대로 두면 순서가 바뀌어도 State가 요소를 따라갑니다.
- key는 형제 사이에서만 유일하면 됩니다. 다른 배열의 key와 같아도 됩니다.
- key는 Props로 전달되지 않습니다. 컴포넌트 안에서 id가 필요하면 별도 Props로 넘깁니다.

```jsx
<Chat key={contact.id} contact={contact} />
// 대화 상대가 바뀌면 key가 바뀌어 Chat의 State가 초기화된다
```

key 부여 방식과 리스트 규칙은 07편에서, State를 key로 초기화하는 활용은 13편에서 다룹니다.

## 트리 위치

State는 컴포넌트 함수가 아니라 렌더 트리 안의 위치에 매달려 있습니다. React가 State를 찾는 기준은 코드에 쓴 위치가 아니라 렌더 트리에서의 위치입니다.

```jsx
function App() {
  const c = <Counter />
  return <div>{c}{c}</div> // 같은 엘리먼트라도 위치가 둘 → State 둘
}
```

- 위치가 다르면 같은 컴포넌트도 State가 따로입니다.
- 두 분기에 `Counter`가 같은 위치로 있으면 하나로 취급되어 State가 유지됩니다. 이를 원하지 않으면 key를 다르게 주거나 구조를 달리합니다.

```jsx
if (isFancy) {
  return <div><Counter fancy /></div>
}
return <div><Counter /></div>
// ❌ 두 분기 모두 div의 첫 자식이 Counter → State 공유
```

- 컴포넌트가 트리에서 사라지면 State도 함께 버려집니다. 다시 나타나면 처음부터 시작합니다.
- 조건부 렌더링에서 `null`도 자리를 차지하므로 `{cond && <A />}` 뒤의 요소 위치는 바뀌지 않습니다.

## DOM 재사용

React는 커밋에서 같은 것으로 판단한 DOM 노드를 새로 만들지 않고 재사용합니다. 입력 중인 글자, 포커스, 스크롤 위치처럼 사용자가 만든 상태가 DOM 노드에 들어 있으므로, 노드가 재사용되는지 버려지는지가 곧 화면 동작의 차이가 됩니다.

- 같은 위치, 같은 타입이면 DOM 노드를 재사용하고 바뀐 attribute만 고칩니다. 입력 중인 글자, 포커스, 스크롤 위치, 선택 영역은 DOM 노드에 있어서 유지됩니다.
- 타입이 다르거나 key가 달라지면 이전 DOM 노드를 삭제하고 새 노드를 만듭니다. 노드에 있던 입력값과 포커스가 사라집니다.
- 제어되지 않는 입력은 값이 DOM 노드에 있으므로 노드가 재사용되면 값이 남습니다. 제어되는 입력은 State가 값을 가지므로 State가 유지되는지가 기준입니다(자세히는 15편).

```jsx
{editing ? <input /> : <input />}
// 같은 위치, 같은 타입 → DOM 노드 재사용
// 글자와 포커스가 유지되어 두 입력이 같은 것처럼 동작한다
```

**흔한 실수:** React가 관리하는 DOM 노드를 `ref`로 직접 고치는 것입니다. 이후 렌더링의 DOM 갱신과 어긋나서 화면이 깨지거나 에러가 납니다. ref로는 포커스, 스크롤, 크기 측정처럼 DOM을 바꾸지 않는 동작만 합니다(자세히는 19편).

## 컴포넌트 교체

같은 자리에 다른 컴포넌트를 넣으면 이전 컴포넌트의 서브트리는 통째로 언마운트되고 새 컴포넌트가 마운트됩니다. 내용이 비슷해 보여도 같은 취급을 하지 않습니다.

```jsx
function Page({ admin }) {
  return admin ? <AdminForm /> : <UserForm />
}
// 같은 자리에서 AdminForm ↔ UserForm 전환
// 두 컴포넌트의 State는 서로 이어지지 않는다
```

- 이전 컴포넌트의 Effect는 정리(cleanup)되고 State는 버려집니다.
- 두 화면이 같은 입력값을 유지해야 하면 컴포넌트를 갈아 끼우지 말고 하나의 컴포넌트가 Props로 모양을 바꾸게 합니다. 값을 부모로 끌어올려도 됩니다(자세히는 14편).
- 반대로 전환할 때 State를 비우고 싶으면 같은 타입이라도 key를 다르게 줍니다.

## List Reconciliation

리스트에서는 배열 요소를 key로 이전 렌더링의 요소와 짝지어 비교합니다. key가 없으면 React는 위치(순서)로 짝을 짓습니다.

- 목록 끝에 추가하면 위치 기준 비교도 잘 동작합니다.
- 목록 앞에 추가하거나 순서를 바꾸면 위치 기준 비교는 모든 요소를 바뀐 것으로 봐서 불필요한 갱신이 일어납니다. key가 있으면 이동으로 인식해 노드를 옮기기만 합니다.
- key는 항목의 고유한 id처럼 바뀌지 않는 값으로 줍니다. 배열 인덱스는 정렬, 삽입, 삭제 때 요소와 key의 짝이 어긋납니다. 렌더 중에 `Math.random()`으로 만들면 key가 매번 달라서 전부 새로 만들어집니다.

```jsx
// 이전: [A, B] → 이후: [X, A, B] (앞에 추가)
items.map((it, i) => <Row key={i} item={it} />)
// ❌ 인덱스: 0번이 A에서 X로 바뀐 것으로 봐서 State가 밀린다
items.map((it) => <Row key={it.id} item={it} />)
// ✅ id: A, B를 그대로 두고 X만 새로 만든다
```

- 인덱스 key에서는 State를 가진 컴포넌트와 제어되지 않는 입력의 값이 다른 항목으로 넘어가 뒤섞입니다.
- 리스트 렌더링의 자세한 규칙은 07편에서 다룹니다.

## UI 버그 분석

State가 사라지거나 엉뚱하게 남는 버그는 대부분 "React가 같은 것으로 봤는가, 다른 것으로 봤는가"의 문제입니다. 증상으로 원인을 추적합니다.

| 증상 | 원인 | 해결 |
|------|------|------|
| 부모가 렌더링될 때마다 입력값과 포커스가 사라진다 | 컴포넌트 안에서 컴포넌트를 선언해 타입이 매번 바뀐다 | 최상위로 옮긴다 |
| 대상을 바꿨는데 이전 대상의 입력값이 남는다 | 같은 위치, 같은 타입이라 State가 유지된다 | key에 대상 id를 준다 |
| 목록에서 삭제하면 다른 행의 입력값이 사라지거나 밀린다 | 인덱스를 key로 써서 짝이 어긋난다 | 항목 id를 key로 쓴다 |
| 조건에 따라 다른 컴포넌트인데 State가 공유된다 | 분기마다 같은 위치에 같은 타입이다 | key를 다르게 하거나 구조를 나눈다 |
| 토글 때마다 State가 초기화된다 | 위치의 타입이 번갈아 바뀐다 | 같은 타입으로 두고 Props로 구분한다 |
| 화면의 값이 개발 모드에서만 두 번씩 늘어난다 | 렌더 중에 Props나 바깥 값을 바꿨다 | 렌더를 순수하게 고친다 |

진단 순서는 다음과 같습니다.

1. 문제가 되는 컴포넌트의 렌더 트리 위치를 확인합니다.
2. 전환 전후에 그 위치의 `type`과 `key`가 같은지 비교합니다.
3. 같으면 State와 DOM이 유지되고, 다르면 버려집니다. 이 결과가 증상과 맞는지 확인합니다.
4. React DevTools Components 탭에서 컴포넌트가 언마운트되고 새로 마운트되는지 확인합니다(자세히는 02편).

## 면접 질문: 렌더링 과정을 설명하라

답변은 네 단계를 순서대로 말하고, 각 단계가 무엇을 하고 무엇을 하지 않는지 덧붙이면 됩니다.

1. 트리거: 최초 렌더링이나 State 변경이 렌더링을 요청합니다.
2. 렌더: React가 컴포넌트 함수를 호출해 JSX를 모읍니다. State가 바뀐 컴포넌트와 그 후손을 재귀적으로 호출하고, 이 단계는 DOM을 바꾸지 않으며 순수해야 합니다.
3. 커밋: Reconciliation으로 이전 결과와 비교해 달라진 부분만 DOM에 반영하고 ref를 연결합니다. 그 뒤 Effect를 실행합니다.
4. 페인트: 브라우저가 바뀐 DOM을 화면에 그립니다.

- 추가로 말할 것: 비교는 같은 위치의 `type`과 `key`로 하고, 같으면 State와 DOM을 재사용하며 다르면 버립니다.
- 흔한 오해 바로잡기: 렌더링은 DOM 갱신이 아닙니다. 재렌더링되어도 결과가 같으면 DOM은 바뀌지 않습니다.

## 핵심 정리

- 화면 갱신은 트리거, 렌더, 커밋, 페인트 네 단계이고 렌더는 컴포넌트를 호출해 계산만 하며 DOM은 커밋에서 바뀝니다.
- 재렌더링의 트리거는 State 변경이고, 컴포넌트가 재렌더링되면 그 후손은 Props가 같아도 모두 다시 호출됩니다.
- 렌더링은 순수해야 합니다. 같은 입력이면 같은 JSX를 내고 렌더 중에 바깥 값을 바꾸지 않습니다.
- Reconciliation은 같은 위치의 `type`과 `key`를 비교합니다. 같으면 DOM 노드와 State를 재사용하고 다르면 서브트리를 버리고 새로 만듭니다.
- State는 렌더 트리의 위치에 매달려 있어서 위치, 타입, key로 보존과 초기화가 정해집니다.
- 컴포넌트 안에서의 컴포넌트 선언, 인덱스 key, 분기마다 같은 위치의 같은 타입이 대표적인 UI 버그 원인입니다.

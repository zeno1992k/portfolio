## fetch

`fetch(url, options)`는 브라우저에 내장된 HTTP 요청 함수입니다. 설치 없이 쓰고, `Response` 객체로 이행하는 Promise를 돌려줍니다. React의 API가 아니라 웹 표준이므로 컴포넌트 밖에서도 똑같이 동작합니다.

```js
const res = await fetch('https://api.example.com/todos')
const todos = await res.json()
```

- 첫 인수는 URL이고, 둘째 인수는 선택으로 `method`, `headers`, `body`, `credentials`, `signal` 같은 옵션 객체입니다.
- 옵션을 생략하면 GET 요청입니다.
- Promise는 응답 헤더를 받으면 이행됩니다. 본문은 `res.json()`, `res.text()` 등으로 따로 읽어야 하고 이것들도 Promise를 돌려줍니다.
- 본문은 스트림이라 한 번만 읽을 수 있습니다. 같은 `Response`에 `res.json()`을 두 번 부르면 TypeError입니다. 두 번 읽어야 하면 `res.clone()`을 씁니다.
- React에서는 이벤트 핸들러나 Effect 안에서 호출합니다. 렌더링 중에는 호출하지 않습니다. Effect에서 호출하는 방법과 Race Condition 처리는 23편에서 다룹니다.

## GET

GET은 데이터를 조회하는 요청입니다. 본문이 없고 조건은 URL의 쿼리 문자열로 전달합니다.

```js
async function getTodos(done) {
  const query = new URLSearchParams({ done })
  const res = await fetch('/api/todos?' + query)
  if (!res.ok) throw new Error('HTTP ' + res.status)
  return res.json()
}
```

- `URLSearchParams`가 값을 URL에 안전한 형태로 인코딩합니다. 문자열을 이어 붙이면 공백이나 `&`가 들어간 값에서 URL이 깨집니다.
- 서버 상태를 바꾸지 않는 요청이므로 같은 URL을 여러 번 호출해도 안전합니다.
- 경로 매개변수는 템플릿 문자열로 만듭니다. 사용자 입력이 섞이면 `encodeURIComponent`로 감쌉니다.

```js
fetch(`/api/users/${encodeURIComponent(id)}`)
```

## POST

POST는 서버에 새 리소스를 만들거나 처리를 요청하는 요청입니다. `method`를 지정하고 `body`에 데이터를 담습니다.

```js
const res = await fetch('/api/todos', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ text: 'Buy milk' }),
})
const created = await res.json()
```

- `body`는 문자열이어야 하므로 객체는 `JSON.stringify`로 직렬화합니다. 객체를 그대로 넣으면 `"[object Object]"`가 전송됩니다.
- JSON을 보낼 때는 `Content-Type: application/json` 헤더를 직접 붙입니다(아래 "JSON", "Headers").
- 같은 POST를 두 번 보내면 리소스가 두 개 생길 수 있습니다. 제출 버튼을 처리 중에 비활성화하는 이유입니다.
- 폼 파일 업로드는 `FormData`를 `body`로 넘깁니다. 이때 `Content-Type`은 브라우저가 `multipart/form-data`로 자동 설정하므로 직접 쓰지 않습니다.

```js
const form = new FormData()
form.append('file', file)
await fetch('/api/upload', { method: 'POST', body: form })
```

## PUT/PATCH

둘 다 기존 리소스를 수정하는 요청이며, 보내는 범위가 다릅니다.

| 메서드 | 의미 | 본문 |
|--------|------|------|
| PUT | 리소스 전체를 교체 | 리소스 전체 |
| PATCH | 일부 필드만 수정 | 바꿀 필드만 |

```js
// 일부만 수정: PATCH
await fetch('/api/todos/3', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ done: true }),
})
```

- PUT은 멱등입니다. 같은 요청을 여러 번 보내도 리소스는 같은 상태가 됩니다. PATCH는 멱등이 아닐 수 있습니다. 자동 증가 값을 건드리는 수정이 그 예입니다.
- PUT에 일부 필드만 보내면 서버 구현에 따라 나머지가 사라질 수 있습니다. 전체 교체인지 부분 수정인지는 API 문서를 따릅니다.
- 어느 메서드를 받는지는 서버가 정합니다. 프런트엔드는 API 명세에 맞춥니다. 같은 수정이라도 API마다 쓰는 쪽이 다릅니다.

## DELETE

DELETE는 리소스를 삭제하는 요청입니다. 본문 없이 URL로 대상을 지정합니다.

```js
const res = await fetch('/api/todos/3', {
  method: 'DELETE',
})
if (!res.ok) throw new Error('HTTP ' + res.status)
```

- 삭제 후 응답에 본문이 없는 경우가 많습니다. 성공 상태 코드가 `204 No Content`이면 `res.json()`을 부르지 않습니다. 빈 본문을 JSON으로 파싱하면 SyntaxError가 납니다.
- 같은 DELETE를 다시 보내도 서버의 최종 상태는 같습니다(멱등). 두 번째 요청은 이미 없다는 `404`를 받을 수 있습니다.
- 화면에서 목록 항목을 지우려면 서버 응답이 성공한 뒤 State를 바꿉니다(자세히는 11편). 응답 전에 먼저 지우는 낙관적 업데이트는 중급 과목에서 다룹니다.

## JSON

JSON은 API에서 가장 흔한 데이터 형식입니다. 보낼 때와 받을 때 변환이 한 번씩 필요합니다.

| 방향 | 변환 | 이유 |
|------|------|------|
| 보내기 | `JSON.stringify(obj)` | `body`는 문자열이어야 한다 |
| 받기 | `await res.json()` | JSON 텍스트를 JavaScript 값으로 파싱한다 |

- `res.json()`은 이름과 달리 JSON을 만들지 않고 JSON 텍스트를 파싱해서 객체, 배열, 숫자 같은 값을 돌려줍니다.
- 파싱은 비동기라서 `await`가 필요합니다.
- 본문이 JSON이 아니면 `res.json()`이 SyntaxError로 거부됩니다. 서버 에러 페이지가 HTML로 오는 경우가 그 예입니다. `res.json()`은 `Content-Type`을 검사하지 않고 파싱을 시도합니다.
- JSON에 들어갈 수 없는 값은 사라지거나 변환됩니다. `undefined`와 함수는 생략되고, `Date`는 문자열이 되어 받는 쪽에서 `Date`로 복원하지 않으면 문자열 그대로입니다.

```js
JSON.stringify({ a: undefined, d: new Date(0) })
// '{"d":"1970-01-01T00:00:00.000Z"}'
```

- 서버가 주는 필드 이름이나 형태를 믿고 그대로 렌더링하면 서버 변경에 화면이 깨집니다. 중요한 경계에서는 형태를 검증합니다(스키마 검증은 중급 과목의 Zod).

## HTTP Error

HTTP 에러는 서버가 응답은 했지만 상태 코드가 실패를 뜻하는 경우입니다. 4xx는 요청이 잘못된 경우(400 잘못된 요청, 401 인증 필요, 403 권한 없음, 404 없음), 5xx는 서버 쪽 문제입니다.

### fetch가 4xx·5xx에서 reject하지 않음

`fetch`는 네트워크 자체가 실패했을 때만 Promise를 거부합니다. 서버가 404나 500을 돌려줘도 Promise는 이행되고 `res.ok`가 `false`일 뿐입니다.

```js
try {
  const res = await fetch('/api/missing') // 404 응답
  console.log(res.ok, res.status)         // false 404
  const data = await res.json()           // 에러 본문이 데이터로 들어감
} catch (e) {
  // 404에서는 여기로 오지 않는다
}
```

- `res.ok`는 상태 코드가 200–299일 때 `true`입니다. `res.status`는 숫자 코드입니다.
- `catch`에 오는 경우는 네트워크 단절, DNS 실패, CORS 차단(아래 "CORS"), 요청 중단(`AbortError`), 타임아웃, `res.json()`의 파싱 실패입니다.
- `try`/`catch`만 쓰면 404 응답의 에러 본문이 정상 데이터처럼 State에 들어갑니다.

**흔한 실수:** `res.ok` 확인을 빼먹고 `catch`가 모든 에러를 잡는다고 믿는 것입니다. 응답을 받으면 먼저 `res.ok`를 확인합니다.

### 에러 던지기

`res.ok`가 `false`이면 직접 에러를 던져 `catch`로 일원화합니다. 에러에 상태 코드를 담아 두면 호출하는 쪽이 코드별로 분기할 수 있습니다.

```js
class HttpError extends Error {
  constructor(status, body) {
    super('HTTP ' + status)
    this.status = status
    this.body = body
  }
}

if (!res.ok) {
  throw new HttpError(res.status, await res.text())
}
```

- 에러 본문은 서버가 정한 형식(JSON이나 텍스트)으로 오므로 읽는 방법을 서버 명세에 맞춥니다.
- 호출하는 쪽은 `e instanceof HttpError && e.status === 401`처럼 구분해 로그인 화면으로 보내거나 메시지를 정합니다.
- 화면에 보일 에러 메시지는 서버가 준 문장을 그대로 노출하기보다 상태 코드별로 정리합니다.

## AbortController

`AbortController`는 진행 중인 `fetch`를 취소하는 표준 API입니다. 컨트롤러의 `signal`을 `fetch` 옵션에 넘기고, 취소할 때 `abort()`를 호출합니다.

```js
const controller = new AbortController()

fetch('/api/search?q=react', { signal: controller.signal })
  .catch((e) => {
    if (e.name === 'AbortError') return // 취소는 에러가 아니다
    throw e
  })

controller.abort() // 요청 취소
```

- `abort()`를 부르면 `fetch` Promise가 `AbortError`로 거부됩니다. 응답 본문을 읽는 중이어도 같습니다.
- 취소한 요청은 브라우저가 응답을 버립니다. 서버가 이미 처리했을 수도 있으므로 쓰기 요청(POST·PUT·DELETE)에서는 취소가 서버 작업까지 되돌린다고 가정하지 않습니다.
- 컨트롤러는 한 번 `abort()`하면 재사용할 수 없습니다. 요청마다 새로 만듭니다.
- React에서는 Effect의 Cleanup에서 `abort()`를 호출해 컴포넌트가 사라지거나 의존성이 바뀔 때 이전 요청을 취소합니다(자세히는 23편).

```jsx
useEffect(() => {
  const controller = new AbortController()
  load(url, controller.signal).then(setData)
  return () => controller.abort()
}, [url])
```

## Timeout

기본 `fetch`는 시간 제한이 없습니다. 서버가 응답하지 않으면 요청이 오래 대기합니다. 제한 시간은 `AbortSignal.timeout(ms)`로 만든 signal을 넘겨 설정합니다.

```js
try {
  const signal = AbortSignal.timeout(5000)
  const res = await fetch(url, { signal })
  return await res.json()
} catch (e) {
  if (e.name === 'TimeoutError') showError('응답이 늦습니다')
  else if (e.name === 'AbortError') return
  else throw e
}
```

- 시간이 지나면 `TimeoutError`로 거부됩니다. 사용자나 코드가 취소한 `AbortError`와 이름이 다르므로 구분해 처리할 수 있습니다.
- `AbortSignal.timeout()`은 2024년 4월부터 최신 브라우저에서 쓸 수 있는 기능(Baseline 2024)입니다. 오래된 기기를 지원하면 `AbortController`와 `setTimeout`으로 직접 만듭니다.
- 직접 취소와 타임아웃을 함께 걸려면 `AbortSignal.any()`로 두 signal을 합칩니다.

```js
const signal = AbortSignal.any([
  controller.signal,
  AbortSignal.timeout(5000),
])
fetch(url, { signal })
```

- 타임아웃이 지나 요청을 포기해도 서버는 작업을 끝냈을 수 있습니다. 재시도는 PUT·DELETE처럼 멱등인 요청부터 안전합니다.

## Credentials

`credentials` 옵션은 요청에 쿠키, TLS 인증서, 인증 헤더 같은 자격 증명을 포함할지 정합니다.

| 값 | 동작 |
|----|------|
| `omit` | 자격 증명을 보내지도 받지도 않는다 |
| `same-origin` | 같은 출처 요청에만 보내고 받는다 (기본값) |
| `include` | 다른 출처 요청에도 항상 포함한다 |

```js
await fetch('https://api.example.com/me', {
  credentials: 'include',
})
```

- 프런트엔드와 API가 다른 출처(프로토콜, 도메인, 포트 중 하나라도 다른 경우)이면서 쿠키 기반 로그인을 쓴다면 `include`가 필요합니다. 기본값으로는 쿠키가 전송되지 않습니다.
- `include`를 쓰려면 서버가 `Access-Control-Allow-Credentials: true`를 응답해야 하고, `Access-Control-Allow-Origin`은 `*`가 아니라 명시한 출처여야 합니다(아래 "CORS").
- 같은 출처만 쓴다면 기본값 `same-origin`으로 충분해 지정하지 않습니다.
- 쿠키 속성(`HttpOnly`, `SameSite`)은 서버가 설정하며, 이 옵션은 브라우저가 쿠키를 보낼지 정할 뿐입니다.

## Headers

헤더는 요청의 부가 정보입니다. `headers` 옵션에 일반 객체나 `Headers` 객체를 넣습니다.

```js
const headers = new Headers({ Accept: 'application/json' })
headers.set('Content-Type', 'application/json')
headers.set('Authorization', 'Bearer ' + token)

fetch('/api/todos', { method: 'POST', headers, body })
```

| 헤더 | 용도 |
|------|------|
| `Content-Type` | 보내는 본문의 형식(`application/json`) |
| `Accept` | 받고 싶은 응답 형식 |
| `Authorization` | 인증 정보. 토큰 방식에서 `Bearer 토큰` 형태가 흔하다 |

- 헤더 이름은 대소문자를 구분하지 않습니다. `Headers` 객체는 이름을 소문자로 정규화합니다.
- `Headers`의 `set`은 덮어쓰고, `append`는 같은 이름에 값을 추가하며, `get`과 `has`로 읽습니다.
- JSON 본문을 보낼 때 `Content-Type`을 빼면 서버가 본문 형식을 알지 못해 파싱하지 못할 수 있습니다.
- 다른 출처 요청에서 `Content-Type: application/json`이나 `Authorization` 같은 헤더를 붙이면 브라우저가 본 요청 전에 사전 요청(preflight)을 보냅니다(아래 "CORS").
- 토큰은 코드에 하드코딩하지 않고 로그인 후 받은 값을 씁니다. 저장 위치(메모리, 쿠키 등)는 보안 정책의 문제이며 이 과목 범위를 벗어납니다.

## API Client 분리

API Client는 `fetch` 호출을 컴포넌트에서 떼어 한 곳에 모은 모듈입니다. base URL, 헤더, 에러 처리, JSON 변환 같은 반복 코드를 한 번만 씁니다.

```js
// api/client.js (HttpError는 앞 절의 클래스)
const BASE_URL = import.meta.env.VITE_API_URL

async function request(path, options = {}) {
  const res = await fetch(BASE_URL + path, options)
  if (!res.ok) {
    throw new HttpError(res.status, await res.text())
  }
  return res.status === 204 ? null : res.json()
}
```

```js
export const api = {
  get: (path, signal) => request(path, { signal }),
  post: (path, body) =>
    request(path, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(body),
    }),
}
```

```jsx
const todos = await api.get('/todos')
await api.post('/todos', { text: 'Buy milk' })
```

- 컴포넌트는 URL, 헤더, `res.ok` 검사를 몰라도 됩니다. 인증 헤더를 추가하거나 에러 형식이 바뀌어도 `request` 한 곳만 고칩니다.
- 도메인별 함수(`getTodos`, `createTodo`)로 한 단계 더 묶으면 컴포넌트가 엔드포인트 문자열을 알 필요도 없어집니다.
- 이 모듈은 React에 의존하지 않는 일반 JavaScript라서 Hook과 컴포넌트 밖에서 테스트할 수 있습니다.
- 호출을 State와 연결하는 부분(로딩, 에러, 결과)은 Custom Hook으로 만듭니다(자세히는 26편).
- 요청 모듈을 만들 때 공통으로 처리하는 것: base URL, 공통 헤더, 상태 코드 검사, 에러 객체 통일, 204 처리, signal 전달.

## axios와 비교

axios는 HTTP 요청용 외부 라이브러리로, Promise 기반이며 브라우저와 Node.js 모두에서 쓰입니다. `fetch`와 쓰임새는 비슷하지만 편의 기능이 더 있습니다.

| 항목 | `fetch` | axios |
|------|---------|-------|
| 설치 | 브라우저 내장 | 패키지 설치 필요 |
| 4xx·5xx | Promise 이행. `res.ok`로 직접 확인 | 기본적으로 2xx 밖이면 거부 |
| 에러 접근 | 직접 만든 에러 | `error.response`(서버 응답), `error.request`(응답 없음) |
| 상태 코드 기준 변경 | 직접 구현 | `validateStatus` 옵션 |
| 인터셉터 | 없음. 래퍼를 직접 만든다 | `interceptors.request.use`, `interceptors.response.use` |

- 인터셉터는 모든 요청 직전과 모든 응답 직후에 끼어드는 함수입니다. 인증 헤더 자동 추가, 401 응답 일괄 처리, 로깅에 씁니다.

```js
const api = axios.create()

api.interceptors.request.use((config) => {
  config.headers.Authorization = 'Bearer ' + getToken()
  return config
})
```

- `axios.create()`로 만든 인스턴스는 자기만의 설정과 인터셉터 체인을 가집니다. 요청 인터셉터는 등록한 반대 순서로, 응답 인터셉터는 등록한 순서로 실행됩니다. `eject()`로 개별 제거합니다.
- `fetch`로도 앞 절의 API Client 래퍼에서 같은 일을 할 수 있습니다. 공통 헤더를 `request`에 넣고, 401을 `HttpError`로 던져 호출하는 쪽에서 처리합니다.
- 선택 기준: 의존성을 늘리고 싶지 않고 요구가 단순하면 `fetch`와 직접 만든 Client, 인터셉터와 에러 모델이 이미 필요한 큰 프로젝트라면 axios. 서버 데이터의 캐시와 재시도가 목적이면 둘 중 무엇을 쓰든 TanStack Query를 위에 얹습니다(중급 과목).

## 환경별 base URL

개발, 스테이징, 운영 환경마다 API 서버 주소가 다릅니다. 주소를 코드에 쓰지 않고 환경 변수로 분리해 환경별로 바꿉니다. Vite에서는 `import.meta.env`로 읽습니다.

```bash
# .env.development
VITE_API_URL=http://localhost:3000/api

# .env.production
VITE_API_URL=https://api.example.com
```

```js
const BASE_URL = import.meta.env.VITE_API_URL
```

- 변수 이름은 `VITE_`로 시작해야 브라우저 코드에 노출됩니다. 그 접두사가 없으면 읽을 수 없습니다(자세히는 02편).
- `.env.[mode]` 파일은 해당 모드에서만 로드됩니다. 개발 서버는 `development`, 빌드는 `production` 모드를 씁니다. `.env`는 모든 모드에서 로드되고, 모드별 파일의 값이 같은 이름이면 우선합니다.
- 번들에 값이 박히므로 API 키나 비밀 값을 `VITE_` 변수에 넣지 않습니다. 브라우저에 보이는 주소와 공개 설정만 둡니다.
- 환경 변수는 빌드할 때 코드에 치환되므로 값을 바꾸면 다시 빌드해야 합니다.
- 개발 중 CORS를 피하려면 개발 서버의 프록시를 씁니다. 브라우저는 같은 출처의 `/api`로 요청하고, 개발 서버가 실제 API 서버로 전달합니다.

```js
// vite.config.js
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:3000',
      changeOrigin: true,
    },
  },
},
```

- 프록시는 개발 서버에만 있습니다. 운영 환경은 서버 설정(리버스 프록시나 CORS 헤더)이 필요합니다.

## CORS

CORS(Cross-Origin Resource Sharing)는 서버가 HTTP 헤더로 자신의 리소스를 불러올 수 있는 다른 출처를 알리는 방식입니다. 브라우저는 보안 때문에 스크립트가 다른 출처로 보내는 요청을 기본으로 제한하며(동일 출처 정책), CORS 헤더가 이를 푸는 허가 신호입니다.

- 출처는 프로토콜, 도메인, 포트의 조합입니다. `http://localhost:5173`에서 `http://localhost:3000`으로 요청하면 포트가 달라 다른 출처입니다.
- 차단하는 주체는 브라우저입니다. 서버는 요청을 받고 응답할 수 있지만, 응답에 허가 헤더가 없으면 브라우저가 코드에 응답을 넘기지 않습니다.
- 허가의 핵심 헤더는 응답의 `Access-Control-Allow-Origin`입니다. 값은 허용하는 출처 하나이거나 `*`입니다.

```http
Access-Control-Allow-Origin: https://app.example.com
```

### 사전 요청

단순하지 않은 요청에는 브라우저가 본 요청 전에 `OPTIONS` 메서드의 사전 요청(preflight)을 먼저 보내 허가를 묻습니다. 다음 중 하나이면 사전 요청이 갑니다.

- 메서드가 PUT, DELETE, PATCH이거나 POST이면서 `Content-Type`이 `application/json` 같은 단순 요청이 허용하는 형식이 아닌 경우.
- `Authorization` 같은 사용자 지정 헤더를 붙인 경우.

서버는 `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`로 허용 범위를 응답하고, 허가되면 브라우저가 실제 요청을 보냅니다.

### 자격 증명이 있는 요청

`credentials: 'include'`로 쿠키를 보내려면 서버가 `Access-Control-Allow-Credentials: true`를 응답하고 `Access-Control-Allow-Origin`에 `*`가 아닌 명시한 출처를 써야 합니다. `Allow-Headers`와 `Allow-Methods`에도 와일드카드를 쓸 수 없습니다.

### CORS 에러

- CORS 실패는 JavaScript에서는 네트워크 에러로 보입니다. `fetch` Promise가 `TypeError`로 거부되고 상세 원인은 코드에서 알 수 없습니다. 브라우저 콘솔에서만 이유가 나옵니다(자세히는 30편).
- CORS는 서버가 응답 헤더로 고치는 문제입니다. 프런트엔드 코드에서 `mode`나 헤더를 바꿔도 해결되지 않습니다.
- 서버에 접근할 수 없는 상황에서는 개발 중 Vite 프록시를 쓰고, 운영 환경에서는 같은 출처로 맞추거나 서버에서 허용합니다.

**흔한 실수:** 응답이 서버에 도달했으니 서버가 정상이라고 판단하는 것입니다. CORS에서는 서버가 처리하고도 브라우저가 응답을 차단할 수 있습니다. 서버 로그와 브라우저 콘솔을 함께 봅니다.

## 핵심 정리

- `fetch`는 웹 표준 함수이고 Promise를 돌려주며, 본문은 `res.json()` 등으로 따로 한 번만 읽습니다. 보낼 때는 `JSON.stringify`와 `Content-Type: application/json`이 필요합니다.
- GET은 조회, POST는 생성, PUT은 전체 교체, PATCH는 부분 수정, DELETE는 삭제입니다.
- `fetch`는 네트워크 실패에서만 거부되고 4xx·5xx에서는 이행되므로 `res.ok`를 확인해 직접 에러를 던져야 합니다.
- 취소는 `AbortController`(`AbortError`), 제한 시간은 `AbortSignal.timeout()`(`TimeoutError`)이며, 쿠키는 `credentials`로 정합니다(기본값은 `same-origin`).
- 요청 코드는 API Client 모듈 한 곳에 모으고, base URL은 `VITE_` 환경 변수로 환경별로 분리합니다.
- CORS는 브라우저가 서버의 허가 헤더로 다른 출처 응답을 허용하는 구조이며, 서버 설정으로 해결하고 개발 중에는 프록시를 씁니다.

## StrictMode 목적

`StrictMode`는 감싼 컴포넌트 트리에 개발 전용 검사를 추가하는 컴포넌트입니다. 버그를 일으키는 코드를 일부러 두 번 실행해서 개발 중에 미리 드러냅니다.

```jsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

- 앱 전체를 감싸도 되고 일부만 감싸도 됩니다. 감싼 트리 안의 모든 컴포넌트가 검사 대상입니다.
- `StrictMode`는 props를 받지 않습니다.
- 감싼 트리 안에서는 검사를 끌 방법이 없습니다. 감싼 컴포넌트는 모두 검사받습니다.

```jsx
<StrictMode>
  <main>
    <Sidebar />
    <Content />
  </main>
</StrictMode>
// main 안의 Sidebar, Content만 검사하고 바깥 컴포넌트는 제외된다
```

찾아내는 버그는 네 종류입니다.

| 검사 | 찾는 버그 |
|------|-----------|
| 컴포넌트 이중 렌더링 | 렌더링이 순수하지 않아서 생기는 버그 |
| Effect 재실행 | Effect의 정리(cleanup) 누락 |
| ref 콜백 재실행 | ref 콜백의 정리 누락 |
| 지원 중단 API 경고 | 곧 쓸 수 없게 될 API의 사용 |

## Double Render

개발 모드에서 StrictMode는 렌더링 함수를 두 번 호출합니다. 순수한 컴포넌트는 두 번 호출해도 결과가 같으므로 차이가 없고, 순수하지 않은 컴포넌트는 결과가 달라져 버그가 눈에 띕니다.

두 번 호출되는 대상은 다음과 같습니다.

- 컴포넌트 함수 본문(최상위 로직)
- `useState`에 넘기는 초기화 함수와 `set` 함수에 넘기는 업데이터 함수
- `useMemo`에 넘기는 함수
- `useReducer`의 reducer와 초기화 함수
- 클래스 컴포넌트의 `constructor`, `render`, `shouldComponentUpdate`

- 이벤트 핸들러는 렌더링 함수가 아니므로 두 번 호출되지 않습니다.
- 두 번 호출한 결과 중 하나는 버려집니다.
- React 19에서는 `useMemo`와 `useCallback`이 두 번째 렌더링에서 첫 번째 렌더링에서 메모이제이션한 결과를 재사용합니다. 이미 StrictMode와 호환되는 컴포넌트는 차이를 느끼지 못합니다.
- React DevTools를 설치했다면 두 번째 렌더링 중의 `console.log`는 흐리게 표시됩니다. DevTools에는 이를 완전히 숨기는 설정이 있고 기본은 꺼져 있습니다.

```jsx
function Item({ label }) {
  console.log('render', label)
  return <li>{label}</li>
}
// 개발 모드에서는 한 번의 렌더링에 로그가 두 번 찍힌다
// 두 번째 로그는 DevTools에서 흐리게 보인다
```

**흔한 실수:** 로그가 두 번 찍히는 것을 버그로 오해해 `StrictMode`를 지우는 것입니다. 두 번 호출되는 것은 의도된 동작이고, 프로덕션에서는 한 번만 호출됩니다.

## Effect 재실행 검사

개발 모드에서 StrictMode는 컴포넌트가 마운트될 때 모든 Effect에 setup, cleanup, setup 순서로 한 번 더 실행합니다. 컴포넌트가 언마운트됐다가 다시 마운트되는 상황을 흉내 내서 정리 코드를 검사하는 것입니다.

```jsx
// 정리가 없는 Effect
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect()
}, [roomId])
// 개발 모드: connect → (cleanup 없음) → connect
// 연결이 두 개가 되어 누수가 곧바로 드러난다
```

정리 함수를 추가하면 두 번째 setup 전에 첫 연결이 끊겨서 연결이 하나만 남습니다.

```jsx
useEffect(() => {
  const conn = createConnection(serverUrl, roomId)
  conn.connect()
  return () => conn.disconnect() // ✅
}, [roomId])
// 개발 모드: connect → disconnect → connect
```

- 정리 함수는 setup이 한 일을 되돌리는 거울이어야 합니다. 구독이면 해제, 타이머면 해제, 연결이면 끊기입니다.
- 정리가 올바르면 한 번 더 실행해도 눈에 보이는 차이가 없어야 합니다. 차이가 보이면 정리가 빠졌거나 틀린 것입니다.
- 두 번 실행을 막으려고 우회하지 않습니다. 이 검사는 화면이 사라졌다 돌아오거나 값이 바뀔 때 일어나는 재동기화를 미리 보여 주는 것이라서, 막으면 버그가 숨을 뿐입니다.
- 의존성이 바뀌어 일어나는 재실행은 이 검사와 별개입니다. 마운트 시점의 추가 한 사이클만 StrictMode가 더하는 것입니다.
- Effect의 구조와 정리는 20편에서 다룹니다.

**흔한 실수:** 요청을 보내는 Effect가 두 번 실행된다고 막으려는 것입니다. 사용자 클릭으로 일어나는 일(구매, 전송)은 Effect가 아니라 이벤트 핸들러에 둡니다. 렌더링 때문에 일어나는 일은 정리까지 갖춘 Effect에 둡니다(자세히는 22편).

## Ref Callback 검사

개발 모드에서 StrictMode는 모든 콜백 ref(함수로 전달하는 `ref`)에도 setup, cleanup, setup을 한 사이클 더 실행합니다. 콜백 ref가 정리 함수를 반환하는 방식은 React 19에서 추가됐고, 컴포넌트가 언마운트되면 React가 그 정리 함수를 호출합니다.

```jsx
<li
  ref={(node) => {
    const item = { cat, node }
    itemsRef.current.push(item)
    return () => {
      const list = itemsRef.current
      list.splice(list.indexOf(item), 1) // ✅ 제거
    }
  }}
/>
```

- 정리 함수가 없거나 비어 있으면 setup이 두 번 실행되어 목록이 예상보다 길어집니다. 이것이 정리 누락의 신호입니다.
- React 19 업그레이드 가이드는 StrictMode가 초기 마운트에서 ref 콜백을 두 번 호출하는 이유를 컴포넌트가 Suspense 폴백으로 교체되는 상황을 흉내 내기 위해서라고 설명합니다.
- 일반 객체 ref(`useRef`)는 이 검사 대상이 아닙니다. 콜백으로 전달하는 ref만 해당합니다(자세히는 19편).

## Deprecated API 경고

StrictMode는 트리 안의 컴포넌트가 곧 지원이 끊길 API를 쓰면 경고를 냅니다. 대표적인 것은 클래스 컴포넌트의 안전하지 않은 생명주기 메서드입니다.

- `UNSAFE_componentWillMount`
- `UNSAFE_componentWillReceiveProps`
- `UNSAFE_componentWillUpdate`

- 주로 오래된 클래스 컴포넌트나 그것을 쓰는 라이브러리에서 발견됩니다. 함수 컴포넌트와 Hook 위주로 쓰는 코드에서는 거의 만나지 않습니다.
- React 19는 문자열 ref, Legacy Context(`contextTypes`, `getChildContext`), `ReactDOM.render`를 제거했습니다. `propTypes` 검사는 React 패키지에서 빠져서 써도 조용히 무시됩니다. `defaultProps`는 함수 컴포넌트에서 제거되어 기본 매개변수로 대체합니다. 이런 API를 쓰던 코드는 경고가 아니라 동작하지 않을 수 있습니다.
- `forwardRef`는 제거되지 않았습니다. React 19에서는 함수 컴포넌트가 `ref`를 props로 받을 수 있습니다(자세히는 05편).

## Pure Component 검사

이중 렌더링은 컴포넌트가 순수한지 확인하는 검사입니다. 순수한 컴포넌트는 같은 입력에 같은 JSX를 내므로 두 번 호출해도 화면이 같습니다(렌더링의 순수성은 17편).

```jsx
function StoryTray({ stories }) {
  const items = stories
  items.push({ id: 'create', label: 'Create Story' }) // ❌
  return (
    <ul>
      {items.map((s) => <li key={s.id}>{s.label}</li>)}
    </ul>
  )
}
// 개발 모드: Props 배열에 두 번 push되어 항목이 두 개 보인다
// 프로덕션: 한 번만 호출되어 버그가 드러나지 않는다
```

props로 받은 배열을 직접 바꿨기 때문입니다. 복사한 뒤 바꾸면 해결됩니다.

```jsx
function StoryTray({ stories }) {
  const items = stories.slice() // ✅ 복사
  items.push({ id: 'create', label: 'Create Story' })
  return (
    <ul>
      {items.map((s) => <li key={s.id}>{s.label}</li>)}
    </ul>
  )
}
```

- 렌더 중에 만든 값을 바꾸는 것은 괜찮습니다. 렌더링 전부터 있던 Props, State, 바깥 변수를 바꾸는 것이 문제입니다.
- `useState` 초기화 함수, 업데이터 함수, reducer도 순수해야 두 번 호출해도 같은 결과가 나옵니다.
- 업데이터 함수 안에서 다른 State를 바꾸거나 바깥 값을 바꾸면 두 번 호출 때문에 결과가 어긋납니다.

```jsx
setTodos((prev) => {
  count++            // ❌ 업데이터 두 번 호출로 두 번 증가
  return [...prev, next]
})
```

## Side Effect 탐지

StrictMode는 부수 효과가 렌더링 중에 새거나 정리 없이 남는 것을 드러냅니다. 부수 효과를 직접 찾아내 알려 주는 것이 아니라, 두 번 실행해 결과가 달라지는 것으로 드러납니다.

| 이중 실행의 증상 | 의심할 원인 |
|------------------|-------------|
| 목록에 같은 항목이 두 번 들어간다 | 렌더 중에 Props나 바깥 배열을 변경했다 |
| 카운터나 ID가 두 번씩 증가한다 | 렌더 중 바깥 변수를 변경했다 |
| 연결이나 구독 개수가 둘로 늘어난다 | Effect에 정리 함수가 없다 |
| 타이머가 두 번 돌고 한쪽이 안 멈춘다 | `setInterval`의 정리가 없다 |
| ref 목록이 예상보다 길다 | ref 콜백의 정리가 없다 |
| 요청이 두 번 나가 중복이 생긴다 | 이벤트로 해야 할 일을 Effect에 넣었다 |

- 이중 실행으로 개발 모드에서만 나타나는 버그는 실제로는 사용자 조작이나 값 변경으로 프로덕션에서도 일어날 수 있는 버그입니다. 컴포넌트가 화면에서 사라졌다 돌아오거나 Props가 바뀌면 같은 일이 생깁니다.
- 고치는 방향은 두 가지입니다. 렌더링에서는 부수 효과를 없애 순수하게 만들고, Effect와 ref 콜백에서는 setup이 한 일을 되돌리는 정리를 추가합니다.
- 부수 효과를 둘 곳은 이벤트 핸들러가 우선이고, 렌더링 때문에 필요한 동기화만 Effect에 둡니다(자세히는 20편).

## Production 차이

StrictMode의 모든 검사는 개발 모드에서만 일어나고 프로덕션 빌드에는 영향을 주지 않습니다.

| 항목 | 개발 모드 | 프로덕션 빌드 |
|------|-----------|---------------|
| 컴포넌트 렌더링 | 두 번 호출 | 한 번 호출 |
| Effect | setup, cleanup, setup | setup |
| 콜백 ref | setup, cleanup, setup | setup |
| 지원 중단 API 경고 | 표시 | 표시 안 함 |

- 프로덕션 빌드에서는 StrictMode가 있어도 성능이나 동작이 달라지지 않습니다. 감싼 채로 배포해도 됩니다(빌드는 02편).
- 개발 모드에서 렌더링과 Effect가 두 번 실행되는 것을 전제로 값을 세는 코드는 프로덕션에서 결과가 달라집니다. 호출 횟수에 의존하는 코드를 쓰지 않습니다.
- `StrictMode`를 지우면 두 번 호출이 사라져 버그가 숨겨질 뿐 사라지지 않습니다.

## 핵심 정리

- StrictMode는 개발 모드에서 감싼 트리를 일부러 두 번 실행해 순수성과 정리 누락 버그를 미리 드러내는 검사이고, props를 받지 않으며 트리 안에서 끌 수 없습니다.
- 컴포넌트 본문, 초기화 함수, 업데이터 함수, `useMemo`, reducer가 두 번 호출되고 이벤트 핸들러는 두 번 호출되지 않습니다.
- 마운트 시 Effect와 콜백 ref는 setup, cleanup, setup 한 사이클이 더 실행되어 정리 함수가 없으면 연결이나 목록이 두 배가 되는 것으로 드러납니다.
- 이중 실행으로 보이는 버그는 개발 환경만의 문제가 아니며, 렌더링은 순수하게, Effect와 ref 콜백은 정리를 추가해서 고칩니다.
- 안전하지 않은 클래스 생명주기 같은 지원 중단 API는 경고로 알려 주고, 모든 검사는 프로덕션 빌드에는 영향이 없습니다.

## Custom Hook

Custom Hook은 `useState`, `useEffect` 같은 Hook을 호출하는 함수로, State를 가진 로직을 여러 컴포넌트가 재사용하게 해 줍니다. 컴포넌트에서 Hook 호출 부분만 떼어 내 함수로 옮기면 됩니다.

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(true)
  useEffect(() => {
    const on = () => setIsOnline(true)
    const off = () => setIsOnline(false)
    window.addEventListener('online', on)
    window.addEventListener('offline', off)
    return () => {
      window.removeEventListener('online', on)
      window.removeEventListener('offline', off)
    }
  }, [])
  return isOnline
}
```

```jsx
function StatusBar() {
  const isOnline = useOnlineStatus()
  return <h1>{isOnline ? 'Online' : 'Disconnected'}</h1>
}
```

- 컴포넌트는 "온라인인가"만 알면 되고 이벤트 등록과 해제는 Hook이 맡습니다. 컴포넌트가 "무엇을"에 집중하고 Hook이 "어떻게"를 감춥니다.
- Custom Hook은 별도 React API가 아닙니다. 일반 함수에 Hook 규칙과 이름 규칙이 붙은 것입니다.
- Hook은 렌더링할 때마다 다시 실행됩니다. 그래서 컴포넌트처럼 순수해야 하고, 최신 Props와 State를 인수로 받습니다.
- 처음부터 만들지 않아도 됩니다. 같은 Effect 로직이 여러 컴포넌트에 나타나거나, 외부 시스템과 동기화하는 Effect가 컴포넌트를 읽기 어렵게 만들 때 뽑습니다.

### Stateful Logic 재사용

재사용 대상은 "State를 가진 로직"입니다. 값 계산만 있으면 일반 함수로 충분합니다. State, Effect, Context 같은 Hook이 로직 안에 있어야 Custom Hook이 필요합니다.

| 로직 | 형태 |
|------|------|
| 배열 정렬 | 일반 함수 `getSorted(items)` |
| 온라인 여부 구독 | Custom Hook `useOnlineStatus()` |
| 입력값 State와 핸들러 | Custom Hook `useFormInput(initial)` |

- 컴포넌트에 흩어져 있던 `useState` + `useEffect` 쌍이 한 이름 아래 모이면 코드를 읽는 쪽이 의도만 보게 됩니다.
- Custom Hook을 쓰면 나중에 구현을 바꿔도 컴포넌트를 고치지 않습니다. 공식 문서는 `useOnlineStatus`를 `useSyncExternalStore`로 바꿔도 컴포넌트가 그대로인 예를 보여 줍니다.

## 이름 규칙

Hook 이름은 `use` 다음에 대문자로 시작합니다. 이 형식으로 React 도구가 "이 함수는 Hook을 호출한다"를 알아봅니다.

```jsx
function useChatRoom() {}   // ✅ Hook
function useFormInput() {}  // ✅ Hook
function getOnlineStatus() {} // ❌ Hook을 부르면서 use가 없음
```

- 이름이 `use`로 시작하고 대문자가 이어지면 린터가 Hook으로 보고 규칙을 검사합니다. `use`가 없는 함수에서 Hook을 부르면 규칙 위반으로 잡힙니다.
- 반대로 Hook을 하나도 부르지 않는 함수에는 `use`를 붙이지 않습니다.

```jsx
function getSorted(items) { // ✅ Hook 없음, use 없음
  return items.slice().sort()
}
function useSorted(items) { // ❌ Hook을 안 부르는데 use
  return items.slice().sort()
}
```

- `use`가 붙으면 최상위에서만 호출해야 하는 제약이 따라옵니다. 필요 없는 제약을 일반 함수에 씌우지 않습니다.
- 이름은 목적을 말해야 합니다. `useChatRoom`은 좋고 `useEffectWrapper`나 `useMount`는 나쁩니다. `useMount(fn)` 같은 생명주기 Hook은 의존성 검사를 우회하는 원인이 되어 공식 문서가 피하라고 합니다(생명주기와의 차이는 20편).

## State를 공유하지 않음

Custom Hook은 로직을 공유하지 State를 공유하지 않습니다. Hook을 호출할 때마다 State가 따로 만들어집니다.

```jsx
function StatusBar() {
  const isOnline = useOnlineStatus() // 이 컴포넌트의 State
  return <h1>{isOnline ? 'Online' : 'Off'}</h1>
}
function SaveButton() {
  const isOnline = useOnlineStatus() // 별개의 State
  return <button disabled={!isOnline}>Save</button>
}
```

- 두 컴포넌트가 같은 Hook을 써도 `isOnline`은 각자의 State입니다. 한쪽 State가 바뀌어도 다른 쪽에 영향이 없습니다.
- 위 예는 값이 같게 보일 뿐입니다. 같은 브라우저 이벤트를 각자 구독해서 각자 갱신하기 때문입니다.
- 컴포넌트 사이에 State를 공유하려면 State를 공통 부모로 끌어올리거나(자세히는 14편) Context에 두고 Hook이 그 Context를 읽게 합니다(자세히는 24편).
- 같은 컴포넌트에서 한 Hook을 두 번 호출해도 State는 둘입니다. `useFormInput`을 이름용, 이메일용으로 두 번 부르면 서로 독립입니다.

**흔한 실수:** Custom Hook 안의 State가 앱 전체에서 하나일 것이라고 생각하는 것입니다. Hook 안의 `useState`는 호출한 컴포넌트 인스턴스에 속합니다.

## Event Hook

콜백(이벤트 핸들러)을 인수로 받는 Custom Hook에서는 그 콜백이 Effect의 의존성이 되지 않게 해야 합니다. 부모가 렌더링마다 새 함수를 만들어 넘기면 콜백이 의존성에 있는 Effect가 매번 다시 실행되기 때문입니다. 그 해결이 `useEffectEvent`입니다(Effect 의존성 전반은 21편).

```jsx
function useChatRoom({ serverUrl, roomId, onMessage: cb }) {
  const onMessage = useEffectEvent(cb)
  useEffect(() => {
    const conn = createConnection({ serverUrl, roomId })
    conn.connect()
    conn.on('message', (msg) => onMessage(msg))
    return () => conn.disconnect()
  }, [serverUrl, roomId]) // onMessage는 넣지 않는다
}
```

- `useEffectEvent`는 최신 렌더링의 값을 읽는 함수를 만듭니다. 값이 바뀌어도 Effect를 다시 동기화하지 않습니다.
- React 19.2에서 안정판이 되었습니다. 린트가 의존성에 넣으라고 요구하지 않으려면 `eslint-plugin-react-hooks` 6 이상이 필요합니다.
- 규칙이 있습니다. Effect 안(`useEffect`, `useLayoutEffect`, `useInsertionEffect`, 다른 Effect Event)에서만 호출하고, 렌더링 중에 호출하지 않으며, 다른 컴포넌트나 Hook에 넘기지 않고, 의존성 배열에 넣지 않습니다.
- Hook의 사용자는 `useChatRoom({ roomId, onMessage })`처럼 콜백을 그냥 넘기면 됩니다. 의존성 처리는 Hook 안에서 끝납니다.

**흔한 실수:** 의존성 경고를 없애려고 `useEffectEvent`로 감싸는 것입니다. 값이 바뀔 때 Effect를 다시 실행해야 하는 reactive한 값이면 의존성에 두어야 합니다.

## Fetch Hook

데이터를 요청하고 로딩·결과·에러 상태를 돌려주는 Hook입니다. 컴포넌트마다 반복되는 `fetch` + `useEffect` + State 세 가지를 한 곳에 모읍니다.

```jsx
function useFetch(url) {
  const [state, setState] = useState({ status: 'loading' })
  useEffect(() => {
    let ignore = false
    const done = (next) => !ignore && setState(next)
    setState({ status: 'loading' })
    fetch(url)
      .then((res) => res.json())
      .then((data) => done({ status: 'ok', data }))
      .catch((error) => done({ status: 'error', error }))
    return () => { ignore = true }
  }, [url])
  return state
}
```

- `url`이 바뀌면 이전 요청의 응답을 무시합니다. `ignore` 플래그가 Race Condition을 막습니다(자세히는 23편).
- 응답 상태 코드(4xx·5xx) 처리와 요청 취소는 이 짧은 예에 빠져 있습니다(자세히는 27편).
- 캐시, 재시도, 중복 요청 제거 같은 기능까지 직접 만들면 규모가 커집니다. 서버 데이터에는 TanStack Query 같은 라이브러리를 쓰는 것이 일반적입니다(중급 과목).
- 컴포넌트는 `const todos = useFetch('/api/todos')` 한 줄로 `status`에 따라 분기합니다.

## Form Hook

입력 State와 `onChange` 핸들러를 묶는 Hook입니다. 입력 필드마다 `useState` + 핸들러를 쓰는 반복을 줄입니다(Form 기초는 15편).

```jsx
function useFormInput(initialValue) {
  const [value, setValue] = useState(initialValue)
  function onChange(e) {
    setValue(e.target.value)
  }
  return { value, onChange }
}

function Form() {
  const first = useFormInput('Mary')
  const last = useFormInput('Poppins')
  return <input {...first} />
}
```

- 객체를 돌려주고 `{...first}`로 `value`와 `onChange`를 한 번에 Props로 펼칩니다.
- `useFormInput`을 두 번 호출하면 State가 둘입니다.
- 검증, touched, dirty 같은 폼 상태 설계는 16편에서 다루며, 폼이 커지면 폼 전용 라이브러리를 씁니다.

## Media Hook

브라우저의 미디어 쿼리 결과를 State로 알려 주는 Hook입니다. `window.matchMedia(query)`는 `MediaQueryList`를 돌려주고, `matches`가 현재 일치 여부이며 일치 여부가 바뀌면 `change` 이벤트가 발생합니다.

```jsx
function useMediaQuery(query) {
  const [matches, setMatches] = useState(
    () => window.matchMedia(query).matches,
  )
  useEffect(() => {
    const mql = window.matchMedia(query)
    const onChange = (e) => setMatches(e.matches)
    setMatches(mql.matches)
    mql.addEventListener('change', onChange)
    return () => mql.removeEventListener('change', onChange)
  }, [query])
  return matches
}
```

- `useMediaQuery('(min-width: 768px)')`나 `useMediaQuery('(prefers-color-scheme: dark)')`처럼 씁니다. 쿼리 문자열의 조건은 괄호로 감쌉니다.
- 서버에는 `window`가 없어서 서버에서 렌더링하는 환경에서는 이 코드가 그대로 동작하지 않습니다. 브라우저 같은 외부 값의 구독에는 `useSyncExternalStore`도 쓸 수 있습니다.
- CSS로 해결되는 반응형(크기 조정, 숨김)은 Hook 없이 CSS 미디어 쿼리로 처리합니다. 렌더링할 컴포넌트 자체가 달라질 때만 이 Hook을 씁니다(자세히는 28편).

## Storage Hook

State를 `localStorage`와 동기화해 새로고침 뒤에도 값을 유지하는 Hook입니다. `localStorage`는 문자열만 저장하므로 JSON으로 변환합니다.

```jsx
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    const saved = localStorage.getItem(key)
    return saved === null ? initial : JSON.parse(saved)
  })
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value))
  }, [key, value])
  return [value, setValue]
}
```

- 초기값은 지연 초기화 함수로 읽어 마운트 때 한 번만 저장소를 읽습니다(자세히는 09편).
- `getItem`은 키가 없으면 `null`을 돌려줍니다. 이때는 `initial`을 씁니다.
- 저장소 접근은 예외를 던질 수 있습니다. 브라우저 정책이나 사용자 설정이 저장을 막으면 `SecurityError`가 납니다. 실제 서비스에서는 `try`/`catch`로 감쌉니다.
- 저장된 문자열이 깨져 있으면 `JSON.parse`도 예외를 던집니다.
- `storage` 이벤트는 같은 문서가 아니라 다른 탭이나 창에서 값이 바뀔 때 발생합니다. 탭 사이 동기화가 필요하면 이 이벤트를 구독합니다.

## 자주 쓰는 훅

### useToggle

Boolean State와 뒤집는 함수를 묶습니다.

```jsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial)
  const toggle = () => setOn((v) => !v)
  return [on, toggle]
}
// const [open, toggleOpen] = useToggle()
```

### useDebounce

값이 바뀐 뒤 일정 시간 동안 더 바뀌지 않아야 새 값을 내보냅니다. 검색창 입력마다 요청이 나가는 것을 막을 때 씁니다.

```jsx
function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value)
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay)
    return () => clearTimeout(id)
  }, [value, delay])
  return debounced
}
```

- `value`가 바뀔 때마다 Cleanup이 이전 타이머를 지우고 새 타이머를 시작합니다. 마지막 변경 후 `delay`가 지나야 `debounced`가 갱신됩니다.

### usePrevious

직전 렌더링의 값을 돌려줍니다. 렌더링 중에 `ref.current`를 읽는 방식은 피하고, 이전 값을 State에 저장하는 방식으로 씁니다.

```jsx
function usePrevious(value) {
  const [current, setCurrent] = useState(value)
  const [previous, setPrevious] = useState(undefined)
  if (value !== current) {
    setPrevious(current)
    setCurrent(value)
  }
  return previous
}
```

- 값이 바뀐 렌더링에서 렌더링 중에 Setter를 호출하는 패턴입니다. 조건 안에서 자기 컴포넌트의 State만 바꿀 때만 허용되고, 조건이 없으면 무한 렌더링이 됩니다.
- `useRef`와 Effect로 `ref.current`에 값을 저장하는 구현이 흔하지만, 렌더링 중에 ref를 읽는 점이 규칙 위반입니다(자세히는 19편).
- 공식 문서는 이 패턴이 대개 피하는 편이 좋지만 Effect에서 State를 바꾸는 것보다는 낫다고 설명합니다. 이전 값이 정말 필요한지 먼저 확인합니다.

## Hook API 설계

Custom Hook의 인수와 반환 형태는 사용하는 쪽에서 보이는 API입니다. 몇 가지 기준이 있습니다.

| 결정 | 기준 |
|------|------|
| 이름 | 하는 일을 구체적으로. `useChatRoom`, `useOnlineStatus` |
| 목적 | 한 Hook이 한 가지 일. 생명주기 Hook(`useMount`) 금지 |
| 인수 | 바뀔 수 있는 값은 그대로 인수로 받는다. Hook이 다시 호출되며 최신 값이 들어온다 |
| 콜백 인수 | Effect에서 쓰면 `useEffectEvent`로 감싸 의존성에서 뺀다 |
| 반환 | 값이 1–2개면 배열(`[value, setValue]`), 여럿이면 객체 |

- 반환 값이 배열이면 사용하는 쪽이 이름을 마음대로 붙입니다(`useState`가 그렇습니다). 객체이면 이름이 고정되고 필요한 것만 꺼낼 수 있습니다.
- 인수가 여러 개이거나 옵션이 많으면 객체 하나로 받습니다. `useChatRoom({ serverUrl, roomId })`가 그 예입니다.
- Hook 안에서 의존성을 속이지 않습니다. 인수를 Effect 의존성에 정확히 넣어 두면 인수가 바뀔 때 자동으로 다시 동기화됩니다.
- 모든 중복을 Hook으로 뽑지 않습니다. 작은 반복은 그대로 두고, 외부 시스템과 동기화하는 Effect가 있을 때 우선 고려합니다.
- 구현이 바뀌어도 반환 형태가 같으면 사용하는 컴포넌트는 안 바뀝니다. 반환 형태는 신중히 정합니다.

## Hook Composition

Custom Hook 안에서 다른 Hook을 부를 수 있고, 이것이 Hook 합성입니다. 작은 Hook을 조합해 큰 Hook을 만듭니다.

```jsx
function useDebouncedSearch(keyword) {
  const debounced = useDebounce(keyword, 300)
  return useFetch('/api/search?q=' + debounced)
}

function SearchResult() {
  const [keyword, setKeyword] = useState('')
  const result = useDebouncedSearch(keyword)
  // ...
}
```

- 한 Hook의 반환값을 다음 Hook의 인수로 넘깁니다. 렌더링마다 최신 값이 흘러서, `keyword`가 바뀌면 `debounced`가 늦게 바뀌고 `useFetch`가 그 뒤에 요청합니다.
- 합성한 Hook도 Hook 규칙을 그대로 따릅니다. 안쪽 Hook 호출은 최상위에서, 항상 같은 순서로 합니다.
- 합성하면 이름이 길어지기 쉽습니다. 조합된 Hook이 하는 일을 한 문장으로 설명할 수 없다면 분리합니다.
- State와 Effect를 감싼 Custom Hook이 쌓여 컴포넌트가 단순해진다는 것이 공식 문서가 말하는 Custom Hook의 이점입니다.

## useDebugValue

`useDebugValue(value, format?)`는 Custom Hook의 값에 React DevTools에서 보이는 라벨을 붙입니다. Custom Hook의 최상위에서만 호출합니다.

```jsx
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(true)
  // ...
  useDebugValue(isOnline ? 'Online' : 'Offline')
  return isOnline
}
// DevTools: OnlineStatus: "Online"
```

- `format` 함수를 두 번째 인수로 주면 DevTools에서 해당 컴포넌트를 검사할 때만 실행됩니다. 비싼 변환을 렌더링마다 하지 않습니다.
- 공식 문서는 모든 Custom Hook에 붙이지 말라고 합니다. 공유 라이브러리의 Hook이나 내부 구조가 복잡해 검사하기 어려운 Hook에서 가치가 있습니다.
- 화면에는 영향을 주지 않는 개발 도구용 코드입니다(DevTools는 30편).

## Hook 규칙

Hook에는 두 가지 규칙이 있습니다. 컴포넌트 최상위에서 호출하고, React 함수에서만 호출합니다. 규칙의 이유는 하나입니다. React는 Hook이 호출된 순서로 각 State를 구분하기 때문입니다.

### 최상위 호출

Hook은 함수 컴포넌트나 Custom Hook의 최상위(조기 return보다 앞)에서 호출합니다.

```jsx
function Counter() {
  const [count, setCount] = useState(0) // ✅
}
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth) // ✅
}
```

- 공식 문서가 금지하는 위치는 다음과 같습니다. 조건문·반복문 안, 조기 return 뒤, 이벤트 핸들러 안, 클래스 컴포넌트 안, `useMemo`·`useReducer`·`useEffect`에 넘기는 콜백 안, `try`/`catch`/`finally` 안입니다.

### React Function에서 호출

Hook은 함수 컴포넌트와 Custom Hook 안에서만 부릅니다. 일반 JavaScript 함수에서는 부르지 않습니다.

```jsx
function FriendList() {
  const status = useOnlineStatus() // ✅ 컴포넌트
}
function setOnlineStatus() {
  const status = useOnlineStatus() // ❌ 일반 함수
}
```

- 이름이 `use`로 시작하지 않는 일반 함수에서 State가 필요하면 그 함수를 Custom Hook으로 바꿉니다(이름에 `use`를 붙입니다).

### 조건문 Hook 금지

조건에 따라 Hook을 부르거나 건너뛰면 호출 순서가 렌더링마다 달라집니다.

```jsx
function Profile({ isAdmin }) {
  if (isAdmin) {
    const [role, setRole] = useState('admin') // ❌
  }
  const [name, setName] = useState('') // 위치가 바뀜
}
```

- 조건은 Hook 안이나 뒤로 옮깁니다. Hook은 항상 부르고 결과를 조건에 쓰는 방식입니다.

```jsx
const [role, setRole] = useState('admin') // ✅ 항상 호출
return isAdmin ? <Admin role={role} /> : null
```

- 조기 return도 조건입니다. `if (loading) return null` 뒤에 Hook이 있으면 렌더링마다 호출 횟수가 달라질 수 있습니다. 모든 Hook을 return보다 위에 둡니다(자세히는 06편).

### 반복문 Hook 금지

반복 횟수가 바뀌면 호출 횟수도 바뀝니다. 반복 안에서 Hook을 부르지 않습니다.

```jsx
function List({ items }) {
  return items.map((item) => {
    const [open, setOpen] = useState(false) // ❌
    return <li key={item.id}>{item.name}</li>
  })
}
```

- 항목마다 State가 필요하면 항목을 별도 컴포넌트로 뽑고 그 컴포넌트 최상위에서 Hook을 호출합니다. 항목 수가 달라져도 각 컴포넌트의 Hook 순서는 일정합니다.

```jsx
function Item({ item }) {
  const [open, setOpen] = useState(false) // ✅
  return <li>{item.name}</li>
}
```

### 중첩 함수 Hook 금지

컴포넌트 안에 선언한 이벤트 핸들러, 콜백, 헬퍼 함수 안에서 Hook을 부르면 안 됩니다. 이런 함수는 렌더링 중에 호출된다는 보장이 없습니다.

```jsx
function Button() {
  function handleClick() {
    const theme = useContext(ThemeContext) // ❌
  }
  const style = useMemo(() => {
    const theme = useContext(ThemeContext) // ❌ 콜백 안
  }, [])
}
```

- Hook은 컴포넌트 최상위에서 부르고 결과 값을 핸들러에서 씁니다.

```jsx
const theme = useContext(ThemeContext) // ✅ 최상위
function handleClick() { console.log(theme) }
```

### 호출 순서

React는 Hook에 이름이 아니라 호출 순서로 State를 연결합니다. 첫 번째 `useState`는 첫 번째 State 슬롯, 두 번째는 두 번째 슬롯입니다. 렌더링마다 호출 순서가 같아야 슬롯이 어긋나지 않습니다.

| 렌더링 | 호출 순서 |
|--------|-----------|
| 1회 (`cond`가 `true`) | `useState(name)` → `useState(age)` → `useEffect` |
| 2회 (`cond`가 `false`) | `useState(name)` → `useEffect` |

- 2회차에는 `useEffect`가 두 번째 자리에 오게 되어 State 자리와 Effect 자리가 뒤섞입니다(Hook 순서 오류 분석은 30편).
- 규칙이 모두 "순서가 항상 같게"를 지키는 방법입니다. 조건·반복·중첩 함수·조기 return 뒤는 순서를 바꾸는 위치입니다.
- 조건을 쓰고 싶으면 Hook 호출은 그대로 두고, Hook이 돌려준 값이나 그 안의 로직에서 조건을 처리합니다.

## eslint-plugin-react-hooks

`eslint-plugin-react-hooks`는 Hook 규칙 위반을 코드 작성 시점에 잡는 공식 ESLint 플러그인입니다. 설치하면 규칙을 어긴 코드를 편집기에서 바로 표시합니다.

```js
import reactHooks from 'eslint-plugin-react-hooks'

export default [
  {
    plugins: { 'react-hooks': reactHooks },
    rules: reactHooks.configs.recommended.rules,
  },
]
```

| 규칙 | 검사 |
|------|------|
| `rules-of-hooks` | 위 두 가지 Hook 규칙(최상위 호출, React 함수에서 호출) |
| `exhaustive-deps` | Effect 등 의존성 배열에서 빠진 값(자세히는 21편) |

- `recommended` 프리셋에는 이 두 규칙 외에 React Compiler 기반 규칙(`purity`, `refs`, `set-state-in-render` 등)도 들어 있습니다.
- 플러그인 6은 React 19.2와 함께 안정판이 되었고, `recommended`가 flat config를 기본으로 씁니다. 이전 설정 형식은 `recommended-legacy`입니다.
- `useEffectEvent`를 의존성에 넣으라고 요구하지 않게 하려면 이 플러그인의 최신 버전이 필요합니다.
- 린트 경고를 `// eslint-disable-next-line`으로 끄는 것은 Hook 순서나 의존성 문제를 숨길 뿐입니다. 경고가 나는 코드를 고칩니다.

## use는 규칙의 예외

`use`는 Promise나 Context를 읽는 React API입니다(`use(resource)`). 이름이 `use`로 시작하지만 Hook이 아니고, 조건문과 반복문 안에서도 호출할 수 있습니다. React 19부터 안정 기능입니다.

```jsx
function Button({ show, children }) {
  if (show) {
    const theme = use(ThemeContext) // ✅ 조건 안에서도 가능
    return <button className={theme}>{children}</button>
  }
  return null
}
```

- `useContext`는 최상위에서만 호출할 수 있지만 `use(Context)`는 조기 return 뒤나 조건 안에서 읽을 수 있습니다.
- 그래도 컴포넌트나 Hook 안에서만 호출합니다. 일반 함수나 이벤트 핸들러 안에서는 쓸 수 없습니다.
- `try`/`catch` 안에서는 호출할 수 없습니다. Promise가 reject되었을 때의 처리는 Error Boundary나 `.catch`로 합니다.
- Promise와 함께 쓰면 Promise가 끝날 때까지 컴포넌트가 중단되므로 `Suspense`가 필요합니다. 렌더링 중에 만든 새 Promise를 넘기면 매번 다른 Promise라서 안 되고 캐시된 Promise를 넘깁니다. 이 부분은 중급 과목의 범위입니다.
- 이 예외를 이유로 일반 Hook에도 조건부 호출을 해도 된다고 생각하면 안 됩니다. `use` 외의 Hook은 규칙이 그대로입니다.

## 핵심 정리

- Custom Hook은 `use`로 시작하는 이름에 Hook을 호출하는 함수이며, State를 가진 로직만 재사용합니다. 호출마다 State는 따로 생깁니다.
- Hook을 부르지 않는 함수에는 `use`를 붙이지 않고, 생명주기 Hook(`useMount`)은 피합니다.
- 콜백을 받는 Hook은 `useEffectEvent`로 감싸 의존성에서 빼고, 인수는 reactive 값 그대로 받아 Hook을 합성합니다.
- Hook은 컴포넌트와 Custom Hook의 최상위에서만, 조건·반복·중첩 함수·조기 return 뒤를 피해 호출합니다. React가 호출 순서로 State를 구분하기 때문입니다.
- `eslint-plugin-react-hooks`의 `rules-of-hooks`와 `exhaustive-deps`로 위반을 잡고, `use`만 조건문·반복문 안에서 호출할 수 있는 예외입니다.

## 렌더 트리 위치

React는 JSX가 아니라 컴포넌트를 중첩한 렌더 트리로 UI를 관리합니다. State는 컴포넌트 함수 안이 아니라 React 안에 있고, 렌더 트리에서 그 컴포넌트가 놓인 위치에 연결됩니다.

```jsx
export default function App() {
  return (
    <div>
      <Counter />
      <Counter />
    </div>
  );
}
// Counter 두 개는 트리의 다른 위치 -> State가 따로 있다
```

- `Counter`가 `useState`로 가진 점수는 위치마다 독립적입니다. 하나를 올려도 다른 하나는 그대로입니다.
- 같은 컴포넌트를 같은 변수에 담아 두 번 렌더해도 위치가 다르면 State도 둘입니다.
- 컴포넌트가 화면에서 사라지면 React는 그 위치의 State를 버립니다.
- State는 JSX 코드의 위치가 아니라 렌더 트리의 위치를 따릅니다. 렌더 트리 자체는 17편에서 더 다룹니다.

## 같은 위치에서 State 보존

같은 위치에 같은 타입의 컴포넌트를 계속 렌더하면 props가 바뀌어도 State는 유지됩니다. React는 트리를 이전 렌더와 비교해 같은 자리에 같은 타입이 있으면 그대로 두고 props만 갱신합니다.

```jsx
{isFancy ? (
  <Counter isFancy={true} />
) : (
  <Counter isFancy={false} />
)}
// isFancy가 바뀌어도 Counter의 점수는 유지된다
```

- 삼항 연산자의 두 가지가 같은 자리의 같은 `Counter`이므로 한 컴포넌트로 취급됩니다.
- 이 규칙 덕분에 props로 표시만 바꾸는 경우(스타일, 문구)에 State가 사라지지 않습니다.

## 컴포넌트 타입 변경

같은 위치에 다른 타입이 오면 React는 이전 컴포넌트를 트리에서 제거하며 State를 버립니다. 그 위치에 새로 만든 컴포넌트의 State는 초기값에서 시작합니다.

```jsx
{isPaused ? <p>See you later!</p> : <Counter />}
// isPaused가 true: Counter 제거, State 폐기
// 다시 false: 새 Counter, 점수 0부터
```

- 타입이 달라지는 것은 `Counter`에서 `p`로 바뀌는 경우뿐 아니라 `div`에서 `section`으로 바뀌는 경우도 포함합니다.
- 자식뿐 아니라 부모 타입이 바뀌어도 그 아래 모든 State가 초기화됩니다. 감싸는 태그를 바꾸면 안쪽 컴포넌트가 새로 만들어집니다.

```jsx
// ❌ isFancy가 바뀌면 div가 section으로 바뀌어 State가 사라진다
if (isFancy) return <section><Counter /></section>;
return <div><Counter /></div>;
```

- 리렌더 사이에 State를 유지하려면 트리 구조(위치와 타입)가 같아야 합니다. 구조를 하나로 맞추고 달라지는 부분은 props로 넘깁니다.

```jsx
// ✅ 구조는 고정, 차이는 props로
return <div><Counter isFancy={isFancy} /></div>;
```

## key로 State Reset

`key`를 주면 위치 대신 key가 컴포넌트의 신원이 됩니다. key가 바뀌면 같은 위치와 같은 타입이어도 React는 다른 컴포넌트로 보고 State를 초기화합니다.

```jsx
{isPlayerA ? (
  <Counter key="Taylor" person="Taylor" />
) : (
  <Counter key="Sarah" person="Sarah" />
)}
// 전환할 때마다 점수가 0부터 시작한다
```

- key는 리스트에만 쓰는 값이 아닙니다. 형제가 하나뿐인 컴포넌트에도 쓸 수 있습니다(리스트의 key는 07편).
- key는 부모 안에서만 신원 구실을 하므로 전역적으로 고유할 필요가 없습니다.
- key 대신 서로 다른 위치에 렌더하는 방법도 있습니다. 두 컴포넌트를 `&&`로 각각 따로 쓰면 위치가 달라 State도 따로입니다. 컴포넌트가 둘뿐일 때만 간편하고, 그 밖에는 key가 일반적입니다.
- key를 바꾸면 컴포넌트와 그 DOM이 새로 만들어지므로 비용이 있습니다. 목적 없이 key를 바꾸지 않습니다.

key는 컴포넌트가 아닌 엘리먼트에도 쓸 수 있습니다. 이미지가 바뀔 때 이전 이미지가 남는 현상을 막습니다.

```jsx
<img key={image.src} src={image.src} />
// src가 바뀌면 DOM이 새로 만들어져 이전 이미지가 사라진다
```

## 조건부 렌더링

조건부 렌더링은 같은 위치를 두고 State를 버릴지 유지할지를 정하는 문제입니다. 결과는 조건의 모양이 아니라 렌더 트리의 위치에서 결정됩니다.

```jsx
<Counter />
{showB && <Counter />}
// showB가 false: 두 번째 Counter의 State 폐기
// 다시 true: 새 Counter, 점수 0
```

- `false`, `null`은 자리를 비우되 그 슬롯의 위치는 유지합니다. 그래서 `{cond && <A />}` 뒤의 형제는 위치가 밀리지 않고 State를 보존합니다.
- 반대로 `if`와 `return`으로 구조가 다른 트리를 돌려주면 위치가 달라질 수 있습니다. 위 "컴포넌트 타입 변경"의 예가 그 경우입니다.
- 렌더 결과에서 `null`, `false`, `0`이 어떻게 보이는지는 03편과 06편에 있습니다.

**흔한 실수:** 조건에 따라 같은 컴포넌트를 서로 다른 감싸는 태그 안에 렌더하는 것입니다. 안쪽 State가 매번 초기화되는데 원인을 찾기 어렵습니다.

## 중첩 컴포넌트 선언 문제

컴포넌트 함수 안에서 다른 컴포넌트를 선언하면 부모가 렌더될 때마다 새 함수가 만들어집니다. React는 함수가 다르면 다른 타입으로 보므로 State를 매번 버립니다.

```jsx
function MyComponent() {
  const [counter, setCounter] = useState(0);

  function MyTextField() { // ❌ 렌더마다 새로 만들어짐
    const [text, setText] = useState('');
    return (
      <input
        value={text}
        onChange={e => setText(e.target.value)}
      />
    );
  }
  return <MyTextField />;
}
```

- 증상은 부모가 리렌더될 때(예: 버튼으로 `counter` 증가)마다 입력한 글자가 사라지는 것입니다.
- 해결은 컴포넌트를 모듈 최상위에 선언하는 것입니다. 부모가 쓰는 값은 props로 받습니다.

```jsx
function MyTextField() { // ✅ 최상위 선언
  const [text, setText] = useState('');
  return (
    <input
      value={text}
      onChange={e => setText(e.target.value)}
    />
  );
}

function MyComponent() {
  return <MyTextField />;
}
```


## 폼 초기화

전환하는 대상이 바뀔 때 입력 중이던 폼을 비우려면 폼 컴포넌트에 `key`를 줍니다. 받는 사람을 바꿔도 같은 위치의 `Chat`이므로 key가 없으면 입력한 글이 남습니다.

```jsx
function Messenger() {
  const [to, setTo] = useState(contacts[0]);
  return (
    <>
      <ContactList contacts={contacts} onSelect={setTo} />
      <Chat key={to.id} contact={to} />
    </>
  );
}
```

- `key={to.id}`로 대상이 바뀌면 `Chat`이 새로 만들어져 안쪽의 `text` State가 비워집니다.
- 편집 폼에서도 같은 방법을 씁니다. 선택한 항목의 id를 key로 주면 `useState(initialData.name)`의 초기값이 새 항목 기준으로 다시 잡힙니다.
- useEffect로 초기화하는 방식은 필요 없습니다(22편).
- 사용자가 직접 비우는 reset 버튼은 15편에서 다룹니다.

## 탭 State 보존

key와 반대로 화면에서 숨겨도 State를 유지하려면 조건부 렌더링으로 컴포넌트를 제거하지 않아야 합니다. 방법은 네 가지입니다.

| 방법 | 동작 | 비용 |
|------|------|------|
| `Activity` (React 19.2) | 숨겨도 State와 DOM 유지, Effect는 정리됨 | 숨은 UI도 낮은 우선순위로 갱신 |
| CSS `display: none` | 모두 렌더하고 스타일로 숨김 | 모든 컴포넌트가 계속 렌더되고 DOM에 남음 |
| State 끌어올리기 | 값만 부모가 소유(14편) | 부모가 필요한 값을 직접 관리 |
| localStorage 등 | 외부 저장소에 보관 | 직렬화 가능한 값만, 읽고 쓰는 코드 필요 |

`Activity`는 React 19.2에서 안정판이 된 컴포넌트입니다.

```jsx
<Activity mode={tab === 'contact' ? 'visible' : 'hidden'}>
  <Contact />
</Activity>
// hidden이어도 Contact의 textarea 내용이 유지된다
```

- `mode`는 `'visible'`과 `'hidden'` 둘이고 기본값은 `'visible'`입니다.
- `hidden`이면 `display: none`으로 숨기고 State와 DOM은 유지하며 안쪽 Effect는 정리됩니다. 다시 `visible`이 되면 Effect를 새로 시작합니다.
- 숨은 동안에도 props가 바뀌면 낮은 우선순위로 다시 렌더합니다.
- `video`, `audio`, `iframe`은 숨겨도 계속 재생됩니다. 정리가 필요하면 언마운트 시점의 cleanup을 직접 둡니다.
- 입력값이 길지 않으면 부모로 끌어올리거나 key 방식으로 일부러 버리는 쪽이 단순합니다.

**흔한 실수:** 탭마다 `{tab === 'a' && <A />}`로 전환하면서 사용자가 입력한 값이 사라지는 것을 버그로 여기는 것입니다. 사라지는 것이 규칙대로의 동작이고, 유지하려면 위 방법 중 하나를 골라야 합니다.

## State Identity

컴포넌트의 신원(identity)은 같은 State를 쓰는 컴포넌트인지를 가르는 기준으로, 위치, 타입, key 세 가지의 조합입니다.

| 요소 | 같으면 | 달라지면 |
|------|--------|----------|
| 렌더 트리의 위치 | 같은 후보 | 별개의 컴포넌트 |
| 컴포넌트 타입 | 같은 후보 | State 폐기 후 새로 생성 |
| key | 같은 컴포넌트 | State 폐기 후 새로 생성 |

- 셋이 모두 같으면 React는 같은 컴포넌트로 보고 State를 보존하며 props만 갱신합니다.
- 하나라도 다르면 이전 컴포넌트의 State를 버리고 초기값에서 새로 시작합니다.
- State를 지키고 싶으면 신원이 바뀌는 원인(감싸는 태그, 선언 위치, key)을 없애고, 비우고 싶으면 key로 신원을 바꿉니다.
- 신원은 리렌더 단계에서 React가 이전 트리와 비교하며 판정합니다(자세히는 17편).

## 핵심 정리

- State는 컴포넌트 함수가 아니라 렌더 트리의 위치에 연결되며, 컴포넌트가 사라지면 함께 사라집니다.
- 같은 위치에 같은 타입이 있으면 props가 바뀌어도 State가 유지되고, 타입이 다르면 초기화됩니다. 부모 타입이 바뀌어도 아래 State는 초기화됩니다.
- key가 바뀌면 같은 위치와 타입이어도 State가 초기화되므로 폼과 입력을 비울 때 key를 씁니다.
- 컴포넌트 안에서 컴포넌트를 선언하면 렌더마다 타입이 달라져 State가 매번 사라집니다. 항상 최상위에 선언합니다.
- 숨기면서 State를 유지하려면 Activity, display none, 끌어올리기, 외부 저장소 중에서 고릅니다.
- 신원은 위치, 타입, key의 조합이며 하나라도 달라지면 State가 새로 시작됩니다.

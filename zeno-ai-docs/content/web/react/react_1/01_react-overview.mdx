## React란

React는 사용자 인터페이스(UI)를 만드는 JavaScript 라이브러리입니다. 화면을 컴포넌트라는 조각으로 나누고, 데이터가 바뀌면 화면을 다시 계산해 그리는 일을 맡습니다.

- 프레임워크가 아니라 라이브러리입니다. 라우팅, 데이터 요청, 빌드 같은 영역은 정해 두지 않습니다(아래 "React와 프레임워크의 차이").
- 웹 브라우저 전용이 아닙니다. 화면을 그리는 대상(브라우저 DOM, 모바일 네이티브 등)은 별도 패키지가 맡습니다.
- 쓰는 문법은 JavaScript와 JSX입니다. JSX는 03편에서 다룹니다.

```jsx
function Hello() {
  return <h1>Hello</h1>
}
```

## 선언적 UI

선언적(declarative) UI는 "어떻게 바꿀지"가 아니라 "상태마다 화면이 어떤 모습이어야 하는지"를 적는 방식입니다. 상태가 바뀌면 React가 변경 방법을 알아서 계산합니다. 반대 방식은 명령형(imperative)이며, 요소를 직접 찾아 보이고 숨기고 비활성화하는 단계를 하나씩 코드로 씁니다.

```js
// 명령형: 요소를 직접 조작
disable(button)
show(loadingMessage)

// 선언형(React): 상태만 바꾼다
setStatus('submitting')
```

선언적으로 생각하는 순서는 다섯 단계입니다.

1. 화면이 가질 수 있는 상태를 모두 나열한다(비어 있음, 입력 중, 전송 중, 성공, 오류).
2. 각 상태로 바뀌는 계기를 찾는다(사용자 입력, 네트워크 응답).
3. 기억해야 할 값을 State로 둔다.
4. 불필요한 State와 서로 모순되는 조합을 없앤다.
5. 이벤트 핸들러가 State를 바꾸게 연결한다.

State는 09편, State 구조 설계는 12편에서 다룹니다.

**흔한 실수:** React 안에서 `document.querySelector`로 요소를 찾아 직접 바꾸는 것입니다. React가 그린 DOM을 밖에서 고치면 다음 렌더링 때 덮어써지거나 어긋납니다.

## 컴포넌트 기반 개발

컴포넌트(component)는 마크업, 스타일, 동작을 하나로 묶은 재사용 가능한 UI 조각입니다. React에서는 JSX를 반환하는 JavaScript 함수가 컴포넌트입니다.

```jsx
function Profile() {
  return <img src="/kim.png" alt="Kim" />
}

function Gallery() {
  return (
    <section>
      <Profile />
      <Profile />
    </section>
  )
}
```

- 컴포넌트가 다른 컴포넌트를 포함하는 구조라서 앱 전체가 트리가 됩니다. 작은 버튼도, 페이지 전체도 컴포넌트입니다.
- 컴포넌트 이름은 대문자로 시작해야 합니다. 소문자 이름은 HTML 태그로 해석됩니다.
- 컴포넌트 안에 다른 컴포넌트를 정의하지 않습니다. 최상위에서 정의하고 Props로 데이터를 넘깁니다(자세히는 04편, 05편).

## react와 react-dom 패키지 분리

React는 코어와 렌더러가 분리되어 있습니다.

| 패키지 | 역할 |
|--------|------|
| `react` | 컴포넌트, Hook, JSX 요소 생성 등 렌더링 대상과 무관한 핵심 |
| `react-dom` | 컴포넌트를 브라우저 DOM에 그리는 웹 전용 기능 |
| `react-native` | 같은 컴포넌트 모델을 모바일 네이티브 뷰에 그리는 렌더러 |

그래서 같은 `useState`가 웹과 모바일에서 똑같이 동작합니다. 웹 앱은 두 패키지를 함께 설치합니다.

```js
import { useState } from 'react'
import { createRoot } from 'react-dom/client'
```

## React DOM

React DOM은 `react-dom` 패키지가 제공하는, React 컴포넌트를 브라우저 DOM과 연결하는 기능입니다. 공식 문서에서 이 패키지는 브라우저 DOM 환경의 웹 앱 전용이며 React Native에서는 지원하지 않는다고 설명합니다.

| 진입점 | 대표 API | 용도 |
|--------|----------|------|
| `react-dom/client` | `createRoot`, `hydrateRoot` | 브라우저에서 화면을 그리거나 서버 HTML에 연결 |
| `react-dom/server` | `renderToPipeableStream`, `renderToReadableStream` | 서버에서 HTML 생성 |
| `react-dom/static` | `prerender` | 정적 HTML 생성 |
| `react-dom` | `createPortal`, `flushSync` | DOM 위치 지정, 동기 반영 |

클라이언트 앱의 시작점은 `createRoot`입니다.

```jsx
import { createRoot } from 'react-dom/client'
import App from './App'

const root = createRoot(document.getElementById('root'))
root.render(<App />)
```

- `root.render`를 처음 호출하면 컨테이너 안의 기존 HTML을 지우고 React가 그린 결과로 채웁니다.
- 이후에는 바뀐 부분만 DOM에 반영합니다.
- 앱 전체를 React로 만들면 루트는 하나입니다. 페이지 일부만 React로 만들면 영역마다 루트를 따로 만들 수 있습니다.
- 서버가 만든 HTML을 재사용할 때는 `createRoot`가 아니라 `hydrateRoot`를 씁니다(아래 "Hydration").

## Virtual DOM 개념

Virtual DOM은 UI의 이상적인 모습을 메모리에 두고, 이것을 실제 DOM과 맞추는 프로그래밍 개념입니다. React 공식 문서(레거시)는 특정 기술이 아니라 설계 패턴으로 설명합니다. 맞추는 과정을 재조정(reconciliation)이라 부릅니다.

- React에서는 JSX가 만드는 React 엘리먼트 객체가 UI 설명에 해당합니다.
- React 16부터 쓰는 재조정 엔진 Fiber는 가상 DOM 렌더링을 조금씩 나눠 처리하도록 만든 구조입니다(자세히는 17편).
- Shadow DOM은 CSS 범위를 가르는 브라우저 기술이라 Virtual DOM과 무관합니다.

**흔한 실수:** "Virtual DOM이라서 항상 빠르다"고 이해하는 것입니다. 핵심 가치는 속도가 아니라, 상태에서 화면을 선언적으로 계산하게 해 주는 데 있습니다.

## SPA와 MPA

SPA(Single-Page Application)는 처음에 문서 하나만 불러오고, 이후 화면 전환을 JavaScript가 그 문서의 내용을 바꿔서 처리하는 앱입니다. MPA(Multi-Page Application)는 화면 전환마다 서버에서 새 HTML 문서를 받아 오는 전통적인 방식입니다.

| 항목 | SPA | MPA |
|------|-----|-----|
| 화면 전환 | 문서 안에서 내용 교체 | 새 문서 로드 |
| 전환 체감 | 빠르고 연속적 | 전체 새로고침 |
| 상태 유지 | 직접 관리해야 함 | 페이지마다 초기화 |
| 첫 화면 | JavaScript 실행 후 | 서버가 만든 HTML |
| SEO | 별도 대책 필요 | 상대적으로 유리 |

MDN은 SPA의 단점으로 SEO, 상태 유지, 내비게이션 구현, 성능 모니터링의 추가 노력을 꼽습니다. React는 SPA에 자주 쓰이지만 MPA 방식으로도 쓸 수 있습니다. 서버 렌더링을 쓰면 첫 화면은 서버가 만든 HTML로, 이후 전환은 SPA처럼 처리하는 혼합도 가능합니다.

## CSR

CSR(Client-Side Rendering)은 브라우저가 JavaScript로 DOM을 만들어 화면을 그리는 방식입니다. 로직, 데이터 요청, 라우팅이 모두 클라이언트에서 일어납니다.

```html
<body>
  <div id="root"></div>
  <script type="module" src="/main.jsx"></script>
</body>
```

- 서버가 보내는 HTML은 비어 있는 컨테이너뿐이고, JavaScript를 내려받아 실행한 뒤에야 내용이 나타납니다.
- 서버는 정적 파일만 제공하면 되어 배포가 단순합니다.
- 첫 화면이 JavaScript 실행에 의존하므로 첫 표시가 느려질 수 있고, 검색 엔진·미리보기가 내용을 못 읽을 수 있습니다.
- Vite로 만든 기본 React 프로젝트가 이 방식입니다(자세히는 02편).

## SSR

SSR(Server-Side Rendering)은 서버가 요청 시점에 컴포넌트를 HTML로 그려 보내는 방식입니다. 브라우저는 JavaScript가 도착하기 전에도 완성된 첫 화면을 보여 줍니다.

- 첫 화면이 빠르고 검색 엔진에 유리합니다.
- 요청마다 서버가 렌더링하므로 서버 비용과 응답 대기(TTFB)가 생깁니다.
- 서버 HTML만으로는 클릭에 반응하지 않습니다. 반응하게 하려면 브라우저에서 Hydration이 필요합니다.
- 서버에서 컴포넌트를 렌더링하는 API는 `react-dom/server`에 있고, 실무에서는 대개 프레임워크가 호출합니다.

**흔한 실수:** 서버 렌더링 중에 `window`, `localStorage` 같은 브라우저 전용 객체를 쓰는 것입니다. 서버에는 없어서 에러가 나거나, 서버와 브라우저의 결과가 달라집니다.

## SSG

SSG(Static Site Generation)는 빌드할 때 페이지를 미리 HTML 파일로 만들어 두는 방식입니다. 요청 때마다 렌더링하지 않고 만들어 둔 파일을 그대로 보냅니다.

- 응답이 가장 빠르고, 정적 호스팅·CDN에 올릴 수 있습니다.
- 데이터가 바뀌면 다시 빌드해야 합니다.
- 사용자마다 달라지는 내용(로그인 상태 등)은 정적 HTML만으로 만들 수 없어서 브라우저에서 따로 채워야 합니다.
- React에는 이를 위한 `react-dom/static`의 `prerender`가 있습니다. 모든 데이터가 로드될 때까지 기다린 뒤 완성된 HTML을 돌려줍니다. 빌드 시점에 자동으로 실행되지 않는 런타임 API라서, 빌드 과정에서 호출하는 일은 프레임워크가 합니다.

| 방식 | HTML이 만들어지는 곳과 때 | 첫 화면 |
|------|--------------------------|---------|
| CSR | 브라우저, 실행 시점 | JS 실행 후 |
| SSR | 서버, 요청 시점 | 빠름 |
| SSG | 서버(빌드 환경), 빌드 시점 | 가장 빠름 |

## Hydration

Hydration은 서버가 만든 HTML에 React가 이벤트 핸들러와 상태를 붙여 상호작용 가능한 앱으로 바꾸는 과정입니다. SSR, SSG로 받은 HTML은 이 과정을 거쳐야 동작합니다.

```jsx
import { hydrateRoot } from 'react-dom/client'

hydrateRoot(document.getElementById('root'), <App />)
```

- React는 기존 DOM 구조를 그대로 두고 로직만 연결합니다.
- 서버 HTML과 클라이언트가 그린 결과가 같아야 합니다. 어긋나면 서버 HTML을 지우고 클라이언트 렌더링으로 전환할 수 있고, 개발 모드에서는 경고가 나옵니다. 공식 문서는 불일치를 버그로 보고 고치라고 안내합니다.
- 불일치의 대표 원인은 `typeof window` 분기, 브라우저 전용 API, 서버와 클라이언트가 다른 데이터를 렌더링하는 경우입니다. 현재 시각처럼 어쩔 수 없이 다른 값에는 `suppressHydrationWarning`을 쓸 수 있는데, 한 단계 깊이에만 적용되는 탈출구입니다.
- React 19는 불일치 오류를 차이(diff)가 담긴 메시지 하나로 보여 줍니다. 디버깅은 30편에서 다룹니다.

**흔한 실수:** 렌더링 중에 `Math.random()`이나 `new Date()`를 그대로 출력하는 것입니다. 서버와 브라우저에서 값이 달라져 Hydration 불일치가 납니다.

## Streaming

Streaming은 서버가 HTML을 한 번에 보내지 않고 준비되는 대로 조각내어 보내는 SSR 방식입니다. 느린 부분 때문에 전체 화면이 기다리지 않게 합니다. React에서는 Suspense 경계로 조각을 나눕니다.

```jsx
<Layout>
  <Cover />
  <Suspense fallback={<PostsSkeleton />}>
    <Posts />
  </Suspense>
</Layout>
```

1. Suspense 바깥의 쉘(shell)이 먼저 도착하고, 느린 부분은 fallback으로 표시됩니다.
2. 데이터가 준비되면 서버가 인라인 스크립트와 함께 실제 내용을 보내 fallback을 교체합니다.
3. 클라이언트 JavaScript가 도착하면 Hydration이 일어납니다.

- 사용하는 API는 `renderToPipeableStream`(Node.js)과 `renderToReadableStream`(웹 스트림)입니다. `renderToString`, `renderToStaticMarkup`은 레거시이며 Suspense 스트리밍을 지원하지 않습니다.
- 쉘이 준비되면 `onShellReady`가 호출되고, 전체가 준비되면 `onAllReady`가 호출됩니다. 크롤러나 정적 생성처럼 완성본이 필요하면 `onAllReady`를 기다립니다.
- React 18에서 서버 Suspense 스트리밍이 도입되었습니다. Suspense 자체는 성능 최적화 영역의 심화 주제이므로 이 과목은 개념만 다룹니다.

## React와 프레임워크의 차이

React는 UI를 그리는 라이브러리이고, 프레임워크는 그 위에 라우팅, 데이터 요청, 렌더링 방식, 번들링, 배포를 묶어 정해 둔 도구입니다. React 공식 문서가 새 프로젝트에 권하는 것은 프레임워크입니다.

| 구분 | 도구 | 비고 |
|------|------|------|
| React 풀스택 프레임워크 | Next.js(App Router) | Vercel이 관리 |
| React 풀스택 프레임워크 | React Router v7 | Vite 기반, Shopify가 관리 |
| 네이티브 앱 | Expo | Android, iOS, 웹 |
| 빌드 도구 | Vite, Parcel, Rsbuild | 라우팅·데이터 요청은 직접 선택 |

- 공식 문서는 프레임워크가 라우팅, 데이터 요청 같은 흔한 문제의 해법을 내장한다고 설명합니다. 처음부터 직접 구성하는 것은 프레임워크가 못 맞추는 제약이 있거나, 직접 만들고 싶거나, React 기초를 배울 때에 한합니다.
- Create React App은 2025년 2월 14일 새 앱에서 사용하지 않도록 지원이 종료(deprecated)되었습니다(자세히는 02편).
- 이 과목은 React 자체를 배우므로 Vite 기반 클라이언트 앱을 기준으로 하고, Next.js는 별도 과목에서 다룹니다. 서버 컴포넌트와 SSR 설계는 이 과목의 범위 밖입니다.

## React Native 개요

React Native는 React의 컴포넌트 모델로 Android, iOS 같은 네이티브 앱을 만드는 프레임워크입니다. 슬로건은 "한 번 배워서 어디서나 쓴다(Learn once, write anywhere)"입니다.

```jsx
function HomeScreen() {
  return (
    <View>
      <Text>Hello</Text>
    </View>
  )
}
```

- 웹 뷰가 아니라 네이티브 뷰로 그립니다. `View`, `Text`, `Image` 같은 기본 요소가 각 플랫폼의 네이티브 UI 컴포넌트에 대응합니다.
- 웹의 `div`, `p`가 아니라 이 기본 요소를 쓰므로 웹 컴포넌트를 그대로 옮길 수는 없습니다. 컴포넌트, State, Hook, 선언적 사고방식은 공유합니다.
- 공식 문서는 새 React Native 앱에 프레임워크인 Expo를 권합니다.
- 이 과목에서는 다루지 않습니다.

## 버전 역사

| 버전 | 시기 | 핵심 변화 |
|------|------|-----------|
| 16 | 16.8 이전 | Fiber 재조정 엔진 도입(재조정 구조 개편) |
| 16.8 | 2019-02-06 | Hooks 안정 릴리스. 클래스 없이 함수 컴포넌트에서 State 사용 |
| 18 | 2022-03-29 | 동시성 렌더링, 자동 배칭, Transition, 서버 Suspense 스트리밍, `createRoot` |
| 19 | 2024-12-05 | Actions, `use`, ref를 Props로 전달, Context를 Provider 없이 사용, 문서 메타데이터 |
| 19.2 | 2025-10-01 | `Activity`, `useEffectEvent`, Performance Tracks, 부분 프리렌더링 |
| 19.3 | 2026-09-09 | `ViewTransition`, Fragment Ref가 안정 기능이 됨, `browser()`, Trusted Types 지원 |

- 16.8 이전의 State와 생명주기는 클래스 컴포넌트에서만 쓸 수 있었습니다. 이 과목은 함수 컴포넌트와 Hook만 다룹니다.
- 18의 동시성은 렌더링을 중단하고 재개할 수 있게 한 내부 방식이며, 자동 배칭은 이벤트 밖(타이머, 프로미스)의 State 변경도 묶어서 한 번 렌더링합니다(자세히는 10편).
- 19의 Actions는 비동기 변경 작업을 다루는 패턴으로 `<form>`의 `action`, `useActionState`, `useOptimistic` 등과 함께 쓰입니다. 이 과목의 범위 밖(중급)입니다. 19에서 프로덕션 수준이 된 서버 컴포넌트도 고급 범위입니다.
- 19.2의 `Activity`, `useEffectEvent`는 안정 기능입니다. `useEffectEvent`는 21편에서 의존성과 함께 만납니다.
- 이 과목의 기준 버전은 19.2입니다. 이 과목이 쓰는 기능은 19.3에서도 그대로 유효합니다. 이전에 Canary·실험 단계였던 `ViewTransition`과 Fragment Ref는 19.3 발표 글에서 안정(stable) 기능으로 표시되었습니다. 둘 다 이 과목의 범위 밖(중급 이상)입니다.

## 핵심 정리

- React는 UI를 만드는 JavaScript 라이브러리이며, 컴포넌트와 상태로 화면을 선언적으로 계산합니다.
- `react`는 렌더링 대상과 무관한 코어이고, `react-dom`은 브라우저 DOM에 그리는 웹 전용 패키지입니다.
- CSR은 브라우저, SSR은 서버가 요청 시점, SSG는 빌드 시점에 HTML을 만듭니다. 서버·빌드가 만든 HTML에는 Hydration이 필요하고, 결과가 어긋나면 버그입니다.
- Streaming은 Suspense 경계를 따라 HTML을 조각내어 보내는 SSR입니다.
- 새 프로젝트는 프레임워크(Next.js, React Router, Expo)가 공식 권장이고, Create React App은 2025-02-14 지원 종료되었습니다.
- 이 과목의 기준은 React 19.2의 함수 컴포넌트와 Hook입니다.

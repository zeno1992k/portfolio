## State Snapshot

State 스냅샷(snapshot)은 한 번의 렌더링이 사용하는 State 값의 고정된 묶음입니다. State는 계속 변하는 변수처럼 보이지만, React는 렌더링 하나당 State 값을 한 번 정해 그 렌더링 안에서 바꾸지 않습니다. 사진 한 장처럼 그 시점의 값이 찍혀 있다는 뜻입니다.

Setter를 호출해도 실행 중인 코드의 State 변수는 바뀌지 않습니다. 대신 React에 새 렌더링을 요청합니다. 렌더링 요청 뒤에는 세 단계가 이어집니다.

1. React가 컴포넌트 함수를 다시 호출한다.
2. 함수가 새 State 값으로 계산한 JSX(새 스냅샷)를 반환한다.
3. React가 화면을 그 스냅샷에 맞춰 갱신한다.

```jsx
const [count, setCount] = useState(0)

function handleClick() {
  setCount(count + 1)
  console.log(count) // 0 (지금 렌더링의 스냅샷)
}
// 다음 렌더링: count는 1
```

- 렌더링은 React가 컴포넌트를 호출하는 일이고, 화면 갱신(커밋)은 그 뒤에 일어납니다. 렌더링 단계와 커밋 단계는 17편에서 다룹니다.
- 새 값은 다음 렌더링에서 처음 보입니다.

## 렌더마다 고정된 State

렌더링 하나 안에서 State 변수는 그 JSX와 핸들러 어디서 읽어도 같은 값입니다. 핸들러 안에서 Setter를 몇 번 호출해도 변수는 그대로입니다.

```jsx
const [number, setNumber] = useState(0)

<button onClick={() => {
  setNumber(number + 1) // setNumber(0 + 1)
  setNumber(number + 1) // setNumber(0 + 1)
  setNumber(number + 1) // setNumber(0 + 1)
}}>+3</button>
// 한 번 클릭: 0 → 1 (3이 아니다)
```

- 세 호출 모두 `number`가 0인 스냅샷을 읽으므로 모두 "State를 1로 바꿔라"라는 같은 요청입니다.
- 렌더링마다 함수가 새로 실행되므로, 각 렌더링에는 그 렌더링 전용의 State 값, JSX, 이벤트 핸들러가 있습니다.
- State는 렌더링 중이 아니라 이벤트 핸들러 같은 계기에서 바꿉니다.

| 렌더링 | `number` | 그 렌더링의 핸들러가 읽는 값 |
|--------|----------|------------------------------|
| 첫 번째 | 0 | 항상 0 |
| 두 번째 | 1 | 항상 1 |
| 세 번째 | 2 | 항상 2 |

## 이벤트 Handler와 Snapshot

이벤트 핸들러는 만들어진 렌더링의 스냅샷에 묶여 있습니다. 핸들러는 렌더링 중에 만들어지는 함수이고, 그때의 State 변수를 클로저로 붙잡습니다. 사용자가 클릭한 시점의 화면에 해당하는 값을 쓰는 것입니다.

```jsx
const [number, setNumber] = useState(0)

<button onClick={() => {
  setNumber(number + 5)
  alert(number) // 0 (5가 아니다)
}}>+5</button>
```

- 알림에는 이전 값 0이 나옵니다. `setNumber(number + 5)`가 요청한 새 값은 다음 렌더링에서 쓰입니다.
- 이 동작 덕분에 핸들러 실행 도중 State가 바뀌어 계산이 어긋나는 일이 없습니다.
- 새 값이 필요하면 변수에 담아 둡니다.

```jsx
const next = number + 5
setNumber(next)
alert(next) // 5
```

**흔한 실수:** Setter 호출 직후 State 변수에 새 값이 들어 있다고 믿고 읽는 것입니다. 호출 직후의 `console.log`는 항상 이전 값을 보여 줍니다.

## 비동기 코드와 Snapshot

핸들러 안의 비동기 코드(`setTimeout`, `await` 뒤)도 같은 스냅샷을 씁니다. 몇 초가 지나 State가 이미 바뀌었더라도 그 코드가 읽는 변수는 핸들러가 만들어질 때의 값입니다.

```jsx
<button onClick={() => {
  setNumber(number + 5)
  setTimeout(() => {
    alert(number) // 3초 뒤에도 0
  }, 3000)
}}>+5</button>
```

- 3초 사이에 화면의 State가 5로 바뀌어도 알림은 0입니다. 변수는 그 렌더링에서 고정된 값이기 때문입니다.
- 비동기 뒤에 최신 값이 필요하면 업데이터 함수를 쓰거나(아래 "Functional Update") 렌더링과 무관하게 값을 보관하는 `useRef`를 씁니다(자세히는 19편).
- 비동기 처리와 Effect의 관계는 23편에서 다룹니다.

```jsx
async function handleSend() {
  setStatus('sending')
  await sendMessage(text)
  alert(text) // 클릭할 때의 text. 그 사이 입력이 바뀌어도 같음
}
```

## Batching

배칭(batching)은 한 이벤트 핸들러가 끝날 때까지 State 업데이트를 모아 두었다가 렌더링을 한 번만 하는 동작입니다. 핸들러의 코드가 다 실행된 뒤에 처리하므로 일부만 반영된 중간 상태가 화면에 나오지 않습니다.

```jsx
function handleSubmit() {
  setName('')
  setCount(count + 1)
  setStatus('sent')
}
// 세 번 호출해도 렌더링은 한 번
```

- 호출 횟수와 렌더링 횟수는 별개입니다. 렌더링은 업데이트가 모두 큐에 쌓인 뒤 한 번 일어납니다.
- 서로 다른 State 변수를 여러 개 바꿔도 마찬가지로 한 번에 처리됩니다.
- 별개의 이벤트는 배칭되지 않습니다. 사용자가 버튼을 두 번 클릭하면 클릭마다 따로 처리되고, 한 클릭의 업데이트가 끝난 뒤에 다음 클릭이 처리됩니다.

## 자동 배칭

React 18에서 배칭 범위가 넓어졌습니다. 이를 자동 배칭(automatic batching)이라 하며 이벤트 핸들러 밖에서 일어난 업데이트도 모읍니다.

| 업데이트가 일어난 곳 | React 17 | React 18 (`createRoot`) |
|----------------------|----------|-------------------------|
| React 이벤트 핸들러 | 배칭 | 배칭 |
| `setTimeout`, Promise | 매 호출 렌더링 | 배칭 |
| 네이티브 이벤트 핸들러 | 매 호출 렌더링 | 배칭 |

```jsx
setTimeout(() => {
  setCount((c) => c + 1)
  setFlag((f) => !f)
  // React 18: 렌더링 한 번 (17에서는 두 번)
}, 1000)
```

- 자동 배칭은 React 18의 `createRoot`로 앱을 시작할 때 적용됩니다. 예전 `ReactDOM.render`로 시작하면 적용되지 않습니다.
- 배칭을 끄고 싶을 때는 `flushSync`를 씁니다(아래 "flushSync 소개").

## Update Queue

업데이트 큐(update queue)는 React가 한 State 변수에 대한 Setter 호출을 호출 순서대로 쌓아 두는 줄입니다. 이벤트 핸들러가 끝나면 다음 렌더링 때 React가 큐를 처음부터 끝까지 차례로 처리해 최종 State 값을 정합니다.

- 큐에는 두 종류가 들어갑니다. 값을 그대로 넘긴 호출은 "값으로 교체", 함수를 넘긴 호출은 "업데이터 함수"입니다.
- 처리 방식은 앞에서 만든 State 값에서 출발해 항목을 하나씩 적용하는 것입니다. 앞 항목의 결과가 다음 항목의 입력이 됩니다.
- 큐 처리 결과가 마지막 항목의 결과이며, 이 값이 다음 렌더링의 State 변수가 됩니다.
- 큐는 State 변수마다 따로 있습니다. 다른 State 변수의 Setter 호출은 서로의 큐에 영향을 주지 않습니다.
- 큐는 렌더링 중에 처리되므로 업데이터 함수도 렌더링 중에 호출됩니다. 그래서 업데이터는 순수해야 합니다.

## Replace Update

값을 넘기는 호출은 "이전 값에 상관없이 State를 이 값으로 교체"하라는 큐 항목입니다. 큐 처리 중 이 항목은 입력 값을 무시하고 자기 값을 결과로 냅니다.

```jsx
setNumber(5)         // 교체: 5로
setNumber(number + 5) // 교체: 지금 스냅샷 기준의 값으로
```

- `setNumber(number + 5)`처럼 계산이 들어 있어도 호출 시점에 이미 값이 계산되므로 큐에는 계산 결과 하나가 교체로 들어갑니다.
- 교체 항목은 앞에 쌓인 모든 항목의 결과를 덮어씁니다. 뒤에 다른 항목이 오기 전까지는 이 값이 결과입니다.

| 큐 항목 | 입력 | 결과 |
|---------|------|------|
| 5로 교체 | 0 (사용 안 함) | 5 |

## Updater Function

업데이터 함수(updater function)는 Setter에 값 대신 넘기는 함수입니다. 큐에서 대기 중이던 State를 인수로 받아 다음 State를 반환합니다.

```jsx
setNumber((n) => n + 1)
```

- 인수는 큐에서 앞 항목들이 만든 값입니다. 현재 렌더링의 State 변수가 아닙니다.
- 반환한 값이 다음 항목의 입력이 되고, 마지막 반환값이 최종 State입니다.
- 순수 함수여야 합니다. 같은 입력이면 같은 결과를 내고, 외부 값을 바꾸거나 요청을 보내거나 State를 직접 변경하지 않습니다.
- StrictMode 개발 중에는 순수성 검사를 위해 업데이터를 두 번 호출하고 한 결과는 버립니다. 순수하면 영향이 없습니다(자세히는 18편).
- 인수 이름은 State 변수 이름의 첫 글자나 `prev` 접두사를 씁니다(`n`, `prevCount`).

```jsx
setEnabled((e) => !e)
setLastName((ln) => ln.toUpperCase())
setFriendCount((fc) => fc * 2)
```

**흔한 실수:** 업데이터 안에서 부수 효과를 일으키는 것입니다. 개발 중 두 번 호출되어 부수 효과도 두 번 일어납니다.

```jsx
setCount((c) => {
  sendLog(c)   // ❌ 부수 효과: 두 번 실행될 수 있음
  return c + 1
})
```

## Functional Update

함수형 업데이트(functional update)는 이전 State를 기반으로 다음 State를 계산하는 업데이트 방식입니다. 업데이터 함수를 쓰는 모든 경우가 해당하며, 한 핸들러에서 같은 State를 여러 번 바꾸거나 비동기 뒤에 바꿀 때 필요합니다.

```jsx
<button onClick={() => {
  setNumber((n) => n + 1)
  setNumber((n) => n + 1)
  setNumber((n) => n + 1)
}}>+3</button>
// 한 번 클릭: 0 → 3
```

| 큐 항목 | 입력 `n` | 결과 |
|---------|----------|------|
| `n => n + 1` | 0 | 1 |
| `n => n + 1` | 1 | 2 |
| `n => n + 1` | 2 | 3 |

비동기 코드에서는 업데이터가 현재 값을 읽는다는 점이 중요합니다. 요청 중인 개수를 세는 예입니다.

```jsx
async function handleClick() {
  setPending((p) => p + 1)   // ✅ 항상 최신 값 기준
  await delay(3000)
  setPending((p) => p - 1)   // ✅
}
// ❌ setPending(pending - 1)은 클릭 때의 값에서 뺀다
```

- 3초 사이에 다른 클릭이 `pending`을 늘렸더라도 업데이터는 그 값을 이어받습니다. 값을 바로 넘겼다면 클릭 시점의 스냅샷에서 계산해 다른 클릭의 변화를 지워 버립니다.
- 값이 이전 값과 무관하면(`setName('Lee')`) 업데이터는 필요 없습니다.

## Update 순서 추론

큐는 호출 순서대로 처리됩니다. 값 교체와 업데이터가 섞인 코드는 표를 그려 위에서 아래로 따라가면 결과를 알 수 있습니다. 시작 State는 0입니다.

```jsx
<button onClick={() => {
  setNumber(number + 5)
  setNumber((n) => n + 1)
  setNumber(42)
}}>go</button>
```

| 큐 항목 | 입력 | 결과 |
|---------|------|------|
| 5로 교체 | 0 (사용 안 함) | 5 |
| `n => n + 1` | 5 | 6 |
| 42로 교체 | 6 (사용 안 함) | 42 |

- 마지막 결과 42가 다음 렌더링의 `number`입니다.
- 마지막이 교체이면 앞의 결과는 모두 덮어써집니다. 마지막이 업데이터이면 앞 결과가 이어집니다.
- `setNumber(number + 5)` 뒤에 `setNumber((n) => n + 1)`을 두면 결과는 6입니다. 교체가 5를 만들고 업데이터가 1을 더합니다.
- 두 호출의 순서를 바꿔 `setNumber((n) => n + 1)` 뒤에 `setNumber(number + 5)`를 두면 업데이터 결과 1이 교체에 덮여 5가 됩니다.

추론 순서는 다음과 같습니다.

1. 시작 State를 쓴다(그 렌더링의 스냅샷 값).
2. 큐 항목을 호출 순서대로 적는다. 값은 "교체", 함수는 "업데이터".
3. 교체는 값으로 바꾸고, 업데이터는 이전 결과를 넣어 계산한다.
4. 마지막 결과가 다음 State다.

## flushSync 소개

`flushSync`는 콜백 안의 State 업데이트를 즉시 처리해 DOM에 반영하게 하는 `react-dom`의 함수입니다. 배칭의 예외를 만듭니다. 안정판 API이며 Canary 전용이 아닙니다.

```jsx
import { flushSync } from 'react-dom'

flushSync(() => {
  setTodos([...todos, newTodo])
})
// 이 줄에서는 DOM이 이미 갱신되어 있다
listRef.current.lastChild.scrollIntoView()
```

- 업데이트 직후의 DOM을 읽거나 DOM API를 호출해야 할 때만 씁니다. 예를 들어 새 항목을 추가한 뒤 그 항목으로 스크롤하는 경우입니다.
- 성능을 크게 해칠 수 있어서 최후의 수단으로만 씁니다.
- 콜백 밖의 보류 업데이트도 함께 처리될 수 있고, 대기 중인 Suspense 경계의 대체 UI가 나타나거나 보류된 Effect가 실행될 수 있습니다.
- 렌더링 중이나 Effect 안에서 호출하면 동작하지 않고 경고가 나옵니다.
- 반환값이 없습니다.
- 대부분의 경우 필요하지 않습니다. 배칭은 의도된 동작이며 끄는 것이 목적이 되어서는 안 됩니다.

## 핵심 정리

- State는 렌더링마다 고정된 스냅샷입니다. Setter는 현재 변수를 바꾸지 않고 다음 렌더링의 값을 요청합니다.
- 이벤트 핸들러와 그 안의 비동기 코드는 만들어진 렌더링의 State 값을 계속 읽습니다.
- 배칭은 핸들러가 끝날 때까지 업데이트를 모아 렌더링을 한 번만 합니다. React 18의 `createRoot`에서는 Promise, `setTimeout`, 네이티브 이벤트 안의 업데이트도 모읍니다.
- 업데이트는 State 변수별 큐에 쌓이고, 큐는 호출 순서대로 처리됩니다. 값 교체는 앞 결과를 덮고, 업데이터 함수는 앞 결과를 받아 이어 계산합니다.
- 이전 State에 의존하거나 비동기 뒤에 바꾸는 경우에는 업데이터 함수를 쓰고, 업데이터는 순수해야 합니다.
- `flushSync`는 업데이트를 즉시 DOM에 반영하는 예외 장치이며 성능을 해칠 수 있어 드물게 씁니다.

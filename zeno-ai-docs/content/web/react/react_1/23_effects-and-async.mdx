## fetch in Effect

컴포넌트가 화면에 표시되었기 때문에 데이터를 가져오는 요청은 Effect에서 보냅니다. 결과는 state에 저장해서 렌더에 씁니다(Effect 기본은 20편, 의존성은 21편).

```jsx
function Profile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then((data) => setUser(data));
  }, [userId]);
}
```

- 요청에 쓰는 reactive value(`userId`)는 의존성에 넣습니다. 값이 바뀌면 Effect가 다시 실행되어 새 요청을 보냅니다.
- 위 코드는 가장 짧은 형태일 뿐 요청이 겹치는 경우, 실패하는 경우를 처리하지 않습니다. 아래 절들이 그 빈틈을 채웁니다.
- 개발 모드에서는 StrictMode가 Effect를 한 번 더 실행하므로 요청이 두 번 나갑니다. 프로덕션에서는 한 번입니다(자세히는 18편).
- 사용자 동작(버튼 클릭, 제출)으로 보내는 요청은 Effect가 아니라 이벤트 핸들러에서 보냅니다(22편).

## Async 함수 직접 전달 금지

`useEffect`에 넘기는 함수는 아무것도 반환하지 않거나 cleanup 함수를 반환해야 합니다. `async` 함수는 항상 Promise를 반환하므로 직접 넘기면 안 됩니다.

```jsx
// ❌ Promise를 반환하는 함수를 Effect로 전달
useEffect(async () => {
  const res = await fetch(url);
  setData(await res.json());
}, [url]);
```

- React는 반환값을 cleanup 함수로 취급하는데 Promise는 함수가 아니라서 정리가 동작하지 않습니다. 린트도 경고합니다.
- 해결은 Effect 안에서 `async` 함수를 따로 선언해 호출하는 것입니다.

```jsx
useEffect(() => {
  let ignore = false;
  async function load() {
    const res = await fetch(url);
    const json = await res.json();
    if (!ignore) setData(json);
  }
  load();
  return () => { ignore = true; };   // 동기 cleanup
}, [url]);
```

- Effect 콜백은 동기 함수로 두고, `await`는 안에서 선언한 함수 안에서 씁니다.
- 안쪽 함수를 컴포넌트 밖으로 옮기고 인자로 값을 받게 하면 의존성이 줄어듭니다. Effect 안에서 선언하면 reactive value를 의존성으로 추적하기 쉽습니다.

## Race Condition

Race Condition(경쟁 상태)은 요청을 여러 번 보냈을 때 응답이 보낸 순서와 다르게 도착해서 결과가 요청 순서가 아니라 도착 순서에 좌우되는 문제입니다.

```jsx
// userId가 1 -> 2로 바뀌어 요청이 두 개 나간 경우
useEffect(() => {
  fetchUser(userId).then((data) => setUser(data));
}, [userId]);
// 요청 1: 느림, 요청 2: 빠름
// 응답 2가 먼저 와서 user는 2번, 곧이어 응답 1이 와서 1번으로 덮임
// 화면은 userId 2인데 1번 사용자가 표시된다
```

- 빠르게 입력하는 검색창, 탭·목록 전환처럼 의존성이 짧은 시간에 여러 번 바뀌는 곳에서 잘 생깁니다.
- 네트워크 응답 시간은 예측할 수 없어서 개발 환경에서는 재현되지 않다가 운영에서만 나타나는 경우가 많습니다.
- Effect가 다시 실행되어도 이전 요청의 `then`은 그대로 살아 있어서 응답이 오면 state를 갱신합니다. 이것이 원인입니다.

## Ignore Flag

Ignore Flag는 Effect 안의 `ignore` 변수로, cleanup에서 `true`로 바꿔 그 Effect가 보낸 요청의 응답을 무시하게 하는 방법입니다.

```jsx
useEffect(() => {
  let ignore = false;

  fetchUser(userId).then((data) => {
    if (!ignore) setUser(data);
  });

  return () => { ignore = true; };
}, [userId]);
```

- `userId`가 바뀌면 React는 새 Effect를 실행하기 전에 이전 Effect의 cleanup을 실행합니다. 이전 Effect의 `ignore`가 `true`가 되어 그 응답은 state를 바꾸지 못합니다.
- `ignore`는 Effect 실행마다 새로 만들어지는 지역 변수이므로 각 요청이 자기 변수를 닫습니다. 컴포넌트 전체에서 공유하는 변수가 아니라는 점이 핵심입니다.
- 요청 자체를 취소하지는 않습니다. 서버는 요청을 계속 처리하고 응답은 도착하지만 버려질 뿐입니다.
- React 공식 문서는 경쟁 상태를 막는 가장 확실한 방법으로 이 패턴을 보여 줍니다.

**흔한 실수:** `ignore`를 `useRef`나 컴포넌트 밖 변수에 둬서 모든 Effect 실행이 같은 변수를 공유하게 만드는 것입니다. 새 Effect가 `false`로 되돌려서 이전 응답도 통과합니다.

## Stale Response

Stale Response(오래된 응답)는 요청을 보낸 시점의 조건이 현재 화면의 조건과 달라진 뒤에 도착한 응답입니다. state에 반영하면 안 되는 응답입니다.

- 응답이 오래되었는지는 그 응답을 낳은 Effect의 cleanup이 실행되었는지로 판단합니다. 의존성이 바뀌었거나 컴포넌트가 사라졌다면 cleanup이 이미 실행된 상태입니다.
- Ignore Flag는 cleanup이 실행된 Effect의 응답을 버려서 Stale Response를 걸러냅니다.
- 의존성이 바뀐 직후에는 이전 값의 데이터가 화면에 남아 있습니다. 새 요청을 시작할 때 이전 데이터를 비워야 다른 대상의 데이터를 보여 주지 않습니다.

```jsx
useEffect(() => {
  let ignore = false;
  setUser(null);                       // 이전 사용자 데이터 비움
  fetchUser(userId).then((data) => {
    if (!ignore) setUser(data);
  });
  return () => { ignore = true; };
}, [userId]);
```

- 이전 데이터를 일부러 보여 주는 편이 나은 화면(목록 새로고침)도 있습니다. 어느 쪽인지는 화면의 의도에 따라 정합니다.
- 컴포넌트가 언마운트된 뒤에 응답이 와도 `ignore`로 state 갱신이 막힙니다.

## AbortController

AbortController는 진행 중인 `fetch` 요청을 중단하는 웹 표준 API입니다. 컨트롤러를 만들고 `signal`을 `fetch`에 넘기고, 필요할 때 `abort()`를 호출합니다.

```js
const controller = new AbortController();

fetch(url, { signal: controller.signal })
  .then((res) => res.json())
  .catch((err) => {
    if (err.name === 'AbortError') console.log('중단됨');
  });

controller.abort();   // 요청을 중단하고 fetch가 거부됨
```

- `new AbortController()`는 `signal` 프로퍼티(읽기 전용 `AbortSignal`)를 가집니다.
- `abort()`를 호출하면 `fetch`의 Promise가 `AbortError`라는 이름의 예외(DOMException)로 거부됩니다.
- 컨트롤러 하나는 한 번 중단하면 끝입니다. 다시 쓰려면 새로 만듭니다.
- `fetch` 외에도 응답 본문 읽기와 스트림 중단에 쓸 수 있습니다. 브라우저 지원은 2019년 3월부터 널리 쓸 수 있는 수준입니다(MDN).

## 요청 취소

Effect의 cleanup에서 `abort()`를 호출하면 의존성이 바뀌거나 언마운트될 때 이전 요청이 중단됩니다.

```jsx
useEffect(() => {
  const controller = new AbortController();
  const { signal } = controller;

  fetch(`/api/users/${userId}`, { signal })
    .then((res) => res.json())
    .then((data) => setUser(data))
    .catch((err) => {
      if (err.name !== 'AbortError') setError(err);
    });

  return () => controller.abort();
}, [userId]);
```

- 취소된 요청은 `AbortError`로 거부되므로 `catch`에서 이 에러는 에러 상태로 다루지 않고 무시합니다.
- 응답을 기다리는 중이어도 네트워크 사용을 멈춰서 불필요한 응답 처리를 줄입니다.
- 취소는 브라우저가 요청을 중단하는 것이어서, 이미 서버에 도착해 처리 중인 요청의 부작용(저장, 결제)까지 되돌리지는 않습니다. 쓰기 요청에는 취소로 안전을 기대하면 안 됩니다.
- 응답 본문(`res.json()`)을 읽는 도중에 취소돼도 같은 `AbortError`로 거부됩니다. 요청 단계만 보호한다고 생각하지 않습니다.
- React 공식 문서는 취소 방식도 보여 주지만 경쟁 상태를 막는 가장 확실한 방법으로는 `ignore` 패턴을 권합니다. 두 방법은 함께 쓸 수 있습니다.

| 방법 | 요청 | 응답 | 쓰임 |
|------|------|------|------|
| Ignore Flag | 계속 진행 | 도착해도 무시 | 모든 비동기 작업에 적용 |
| AbortController | 중단 | 오지 않음(`AbortError`) | `fetch`처럼 `signal`을 받는 API |

## Loading

Loading은 요청이 진행 중이라는 상태입니다. 별도 state로 두고 요청 시작과 끝에서 바꿉니다.

```jsx
const [user, setUser] = useState(null);
const [loading, setLoading] = useState(true);

useEffect(() => {
  let ignore = false;
  setLoading(true);
  fetchUser(userId).then((data) => {
    if (ignore) return;
    setUser(data);
    setLoading(false);
  });
  return () => { ignore = true; };
}, [userId]);
```

- 의존성이 바뀌어 새 요청이 시작될 때 `loading`을 다시 `true`로 되돌려야 합니다. 첫 렌더 값만 `true`로 두면 두 번째 요청부터 로딩 표시가 없습니다.
- 렌더에서는 `if (loading) return <Spinner />` 식으로 분기합니다(자세히는 06편).
- 로딩 여부를 `data === null`로 추론하는 방법도 있지만, 데이터가 원래 `null`일 수 있는 API에서는 구분되지 않습니다. 모호하면 별도 state를 둡니다.
- `loading`, `error`, `data`를 따로 두면 서로 모순되는 조합(로딩 중인데 에러)이 가능해집니다. 한 객체나 상태 값 하나(`'idle'`, `'loading'`, `'success'`, `'error'`)로 묶는 설계도 있습니다(State 구조 설계는 12편).

## Error

Error는 요청이 실패했다는 상태입니다. `fetch`는 HTTP 오류 상태(404, 500)에서도 거부되지 않으므로 직접 확인해야 합니다.

```jsx
async function load() {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const json = await res.json();
    if (!ignore) setData(json);
  } catch (err) {
    if (!ignore && err.name !== 'AbortError') setError(err);
  }
}
```

- `fetch`의 Promise는 네트워크 실패, 잘못된 URL, 중단 같은 경우에만 거부됩니다. 404나 500은 정상 응답이므로 `res.ok`나 `res.status`를 직접 검사하고 `throw`해야 합니다.
- 요청을 새로 시작할 때 이전 에러를 비웁니다(`setError(null)`). 그렇지 않으면 성공한 뒤에도 에러가 남습니다.
- 에러 상태도 `ignore`로 감쌉니다. 오래된 요청의 에러가 새 요청의 화면을 덮으면 안 됩니다.

**흔한 실수:** `fetch(...).then(res => res.json())`만 쓰고 `res.ok`를 확인하지 않는 것입니다. 404의 에러 응답 본문이 정상 데이터처럼 state에 들어갑니다.

## Retry

Retry는 실패한 요청을 다시 시도하는 기능입니다. 재시도 횟수를 state로 두고 의존성에 넣으면 값이 바뀔 때 Effect가 다시 실행되어 새 요청을 보냅니다.

```jsx
const [attempt, setAttempt] = useState(0);

useEffect(() => {
  let ignore = false;
  setError(null);
  fetchUser(userId)
    .then((data) => { if (!ignore) setUser(data); })
    .catch((err) => { if (!ignore) setError(err); });
  return () => { ignore = true; };
}, [userId, attempt]);

// 버튼: onClick={() => setAttempt((n) => n + 1)}
```

- `attempt`는 Effect 안에서 읽지 않아도 의존성에 넣는 의도적인 트리거입니다. 값이 바뀌면 Effect가 재실행되고, 먼저 실행된 Effect는 cleanup으로 정리됩니다.
- 사용자가 누르는 "다시 시도" 버튼은 이 방식으로 충분합니다.
- 자동 재시도(몇 초 뒤 몇 번까지)는 타이머, 횟수 한도, 대기 시간 증가를 직접 구현해야 해서 코드가 빠르게 늘어납니다.
- 쓰기 요청(주문, 결제)은 재시도하면 서버에서 중복 처리될 수 있으므로 읽기 요청과 구분합니다.

## 데이터 패칭 라이브러리를 쓰는 이유

Effect로 직접 가져오는 방식은 간단한 화면에는 충분하지만 요구가 늘수록 보일러플레이트가 많아집니다. React 공식 문서는 Effect로 직접 가져올 때의 단점을 다음과 같이 정리합니다.

| 단점 | 내용 |
|------|------|
| 서버에서 실행되지 않음 | 서버 렌더링 HTML에는 로딩 상태만 담기고 데이터는 클라이언트에서 JS가 로드된 뒤 가져옴 |
| 네트워크 워터폴 | 부모가 가져와 렌더한 뒤에야 자식이 요청을 시작해 순차적으로 느려짐 |
| 선로드·캐시 없음 | 컴포넌트가 언마운트됐다 다시 마운트되면 같은 데이터를 다시 가져옴 |
| 보일러플레이트 | 경쟁 상태를 막는 코드를 매번 작성해야 함 |

- 공식 문서의 권장은 프레임워크의 내장 데이터 가져오기를 쓰거나, TanStack Query, SWR, React Router 같은 클라이언트 캐시를 쓰는 것입니다. 어느 쪽도 맞지 않으면 Effect로 직접 가져와도 됩니다.
- TanStack Query는 서버 상태를 다루는 데 필요한 캐싱, 같은 요청의 중복 제거, 오래된 데이터의 백그라운드 갱신, 데이터가 낡았는지 판단, 메모리 정리, 페이지네이션 같은 기능을 제공한다고 소개합니다.
- 이 편에서 직접 만든 loading, error, ignore, retry가 라이브러리에서는 옵션과 반환 값으로 제공됩니다. 직접 구현해 보면 라이브러리가 무엇을 대신하는지 이해하기 쉽습니다.
- TanStack Query는 이 과목 범위 밖이며 React 중급 과목에서 다룹니다. 사용자 정의 Hook으로 이 로직을 묶는 방법은 26편, API 통신 구조는 27편에 있습니다.

## 핵심 정리

- 화면에 표시되었기 때문에 필요한 데이터 요청은 Effect에서 보내고, 요청에 쓰는 reactive value는 의존성에 넣습니다.
- Effect 콜백에 `async` 함수를 직접 넘기지 말고, 안쪽에 `async` 함수를 선언해 호출하며 cleanup은 동기 함수로 반환합니다.
- 요청이 겹쳐 오래된 응답이 새 응답을 덮는 경쟁 상태는 cleanup에서 `ignore`를 `true`로 바꾸는 Ignore Flag로 막습니다.
- `AbortController`의 `signal`을 `fetch`에 넘기고 cleanup에서 `abort()`하면 요청을 중단하며, 이때 생기는 `AbortError`는 에러 상태로 다루지 않습니다.
- `fetch`는 404·500에서 거부되지 않으므로 `res.ok`를 확인하고, loading과 error는 요청을 시작할 때마다 초기화합니다.
- 캐시, 중복 제거, 서버 렌더링, 워터폴 해결이 필요하면 프레임워크나 TanStack Query 같은 라이브러리를 씁니다.

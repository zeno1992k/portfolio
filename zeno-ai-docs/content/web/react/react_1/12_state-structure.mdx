## 관련 State 묶기

항상 함께 바뀌는 State 변수 둘 이상은 하나의 객체 State로 합칩니다. 따로 두면 한쪽만 바꾸고 다른 쪽을 빠뜨려 서로 어긋날 수 있습니다.

```jsx
// ❌ 함께 바뀌는 값을 따로 선언
const [x, setX] = useState(0)
const [y, setY] = useState(0)

// ✅ 하나로 묶음
const [position, setPosition] = useState({ x: 0, y: 0 })
setPosition({ x: e.clientX, y: e.clientY })
```

- 판단 기준은 "한 변경이 두 값을 같이 건드리는가"입니다. 마우스 좌표처럼 항상 쌍으로 바뀌면 묶고, 폼 필드처럼 따로 바뀌면 따로 두어도 됩니다.
- 얼마나 많은 값을 바꿀지 미리 알 수 없을 때(폼 필드가 가변적일 때)도 객체 하나로 묶으면 편합니다.
- 묶은 객체의 일부만 바꿀 때는 스프레드로 복사합니다(자세히는 11편).
- 서로 관계없는 값까지 하나로 묶지 않습니다. 묶을수록 객체를 통째로 교체해야 해서 복잡해집니다.
- 갱신 규칙이 복잡해지면 `useReducer`로 묶어 관리합니다(자세히는 25편).

```jsx
setPosition((prev) => ({ ...prev, x: 10 }))
// 일부만 바꿀 때는 나머지를 복사
```

## 모순 State 피하기

모순 State는 여러 State 변수가 동시에 참일 수 없는 조합을 표현할 수 있게 만든 구조입니다. 변수가 둘이면 네 가지 조합이 가능한데 그중 일부가 불가능한 상황이면 코드가 어긋날 여지를 남기는 것입니다.

```jsx
// ❌ isSending과 isSent가 둘 다 true가 될 수 있다
const [isSending, setIsSending] = useState(false)
const [isSent, setIsSent] = useState(false)

// ✅ 가능한 상태만 한 변수에 나열
const [status, setStatus] = useState('typing')
// 'typing' | 'sending' | 'sent'
const isSending = status === 'sending'
const isSent = status === 'sent'
```

- 화면이 가질 수 있는 상태를 먼저 나열하고, 그 상태를 값으로 갖는 변수 하나로 둡니다.
- 읽기 편하도록 `status === 'sending'`을 변수로 풀어 쓰는 것은 괜찮습니다. 렌더링 중 계산하는 값이라 State가 아니므로 어긋나지 않습니다.
- 로딩·오류·성공을 불리언 세 개로 두는 코드가 흔한 사례입니다. 하나의 `status`로 바꾸면 "로딩 중이면서 오류"인 조합이 사라집니다.
- 상태가 여럿이고 전환 규칙이 있으면 `useReducer`가 어울립니다(자세히는 25편).

**흔한 실수:** 성공 시 `setIsSending(false)`만 하고 `setIsSent(true)`를 빠뜨리는 것입니다. 변수가 둘이면 이런 누락이 생기고, 하나이면 `setStatus('sent')` 한 줄입니다.

## 중복 State 피하기

중복 State는 같은 정보가 State 여러 곳에 들어 있는 구조입니다. 한쪽을 갱신하면 다른 쪽이 옛 값으로 남아 어긋납니다.

```jsx
// ❌ items 안의 객체를 selectedItem에 또 저장
const [items, setItems] = useState(initialItems)
const [selectedItem, setSelectedItem] = useState(items[0])
```

위 코드에서 `items`의 이름을 수정해도 `selectedItem`은 이전 객체를 가리키고 있어서 화면에 옛 이름이 남습니다. 객체 대신 `id`만 저장하고 객체는 렌더링 중에 찾습니다.

```jsx
// ✅ id만 저장하고 객체는 계산
const [items, setItems] = useState(initialItems)
const [selectedId, setSelectedId] = useState(0)
const selectedItem = items.find((i) => i.id === selectedId)
```

- `items`를 바꾸면 `selectedItem`은 렌더링 때 다시 찾으므로 항상 최신입니다.
- 객체를 저장하면 같은 정보가 두 곳에 있게 됩니다. `id`는 정보가 아니라 가리키는 표시이므로 중복이 아닙니다.
- 선택 항목이 없을 수 있으면 `selectedId`를 `null`로 시작합니다.

## Derived State 피하기

파생 State(derived state)는 Props나 다른 State에서 계산할 수 있는 값을 별도 State로 저장한 것입니다. 렌더링 중에 계산하면 되고, State로 저장하면 원본이 바뀔 때 동기화를 직접 해야 합니다.

```jsx
const [firstName, setFirstName] = useState('')
const [lastName, setLastName] = useState('')
const fullName = firstName + ' ' + lastName // ✅ 계산
// ❌ const [fullName, setFullName] = useState('')
```

- 규칙은 한 줄입니다. 컴포넌트의 Props나 기존 State에서 렌더링 중에 계산할 수 있는 정보는 State에 넣지 않습니다.
- 필터링한 목록, 합계, 개수, 정렬 결과, 화면에 보일 문구가 대표적인 파생 값입니다.

```jsx
const [todos, setTodos] = useState(initialTodos)
const [filter, setFilter] = useState('all')
const visible = todos.filter((t) => matches(t, filter))
const doneCount = todos.filter((t) => t.done).length
```

- 계산 비용이 커도 먼저 일반 변수로 계산합니다. 느릴 때만 최적화를 고려합니다.
- Effect 안에서 State를 계산해 다른 State에 넣는 코드는 이 문제의 전형입니다(자세히는 22편).

Props를 State의 초기값으로 복사하는 것도 파생 State의 한 형태입니다. Props가 바뀌어도 State는 첫 렌더링 값을 유지합니다.

```jsx
function Message({ messageColor }) {
  // ❌ 부모가 messageColor를 바꿔도 color는 그대로
  const [color, setColor] = useState(messageColor)
}
```

- 값을 Props로 받아 그대로 쓰면 됩니다. Props를 렌더링마다 반영하려면 State로 복사하지 않습니다.
- 초기값으로만 쓰고 이후 갈라지는 것이 의도라면 Props 이름을 `initialColor`, `defaultColor`처럼 지어 의도를 드러냅니다.

```jsx
function Message({ initialColor }) {
  const [color, setColor] = useState(initialColor)
  // initialColor는 처음 한 번만 쓰인다
}
```

- Props가 바뀔 때 State를 초기화하려면 `key`를 바꿉니다(자세히는 13편).

## Minimal State

최소 State는 화면을 그리는 데 꼭 필요한 값만 State로 두고 나머지는 모두 계산하는 원칙입니다. State는 변하는 데이터 중 기억해야 할 최소 집합이며, 반복하지 않는다는 DRY 원칙으로 줄입니다.

각 값에 세 가지를 묻습니다. 하나라도 "예"이면 State가 아닙니다.

1. 시간이 지나도 변하지 않는가?
2. 부모가 Props로 내려 주는가?
3. 기존 State나 Props로 계산할 수 있는가?

검색 가능한 상품 표에서 적용하면 다음과 같습니다.

| 값 | State 여부 | 이유 |
|----|-----------|------|
| 전체 상품 목록 | 아니오 | Props로 받음 |
| 검색어 | 예 | 변하고 계산할 수 없음 |
| 재고 있는 것만 보기 체크 | 예 | 변하고 계산할 수 없음 |
| 필터링된 상품 목록 | 아니오 | 목록과 검색어에서 계산 |

- State 변수를 줄이면 갱신 코드가 줄고 어긋날 가능성도 줄어듭니다.
- 너무 줄이지는 않습니다. 계산만으로 복원할 수 없는 값(사용자가 입력한 값)은 State여야 합니다.
- State가 필요한 값인지 확신이 없으면 먼저 계산으로 시도하고, 불가능할 때 State로 올립니다.
- 위 원칙은 이 편의 앞선 네 절(묶기, 모순, 중복, 파생)을 한꺼번에 점검하는 체크 리스트입니다.

## Normalization

정규화(normalization)는 중첩된 State를 `id`를 키로 하는 평평한 구조로 바꾸는 설계입니다. 트리 모양 데이터를 중첩 그대로 저장하면 깊은 항목을 바꿀 때 경로 전체를 복사해야 하고, 같은 항목이 여러 곳에 있으면 중복이 됩니다.

```jsx
// ❌ 중첩: 깊은 항목 갱신이 번거롭다
const [plan, setPlan] = useState({
  id: 0,
  children: [{ id: 1, children: [{ id: 2 }] }],
})

// ✅ 평평: id로 바로 접근, 부모는 자식 id만 보관
const [places, setPlaces] = useState({
  0: { id: 0, title: 'Root', childIds: [1] },
  1: { id: 1, title: 'Earth', childIds: [2] },
  2: { id: 2, title: 'Africa', childIds: [] },
})
```

- 항목은 `id` 표에 한 번만 저장하고, 서로는 `id`로 가리킵니다. 데이터베이스 정규화와 같은 발상입니다.
- 항목 하나를 바꾸려면 그 항목과 그 항목이 든 표만 복사하면 됩니다. 갱신 코드는 11편의 "정규화"를 따릅니다.
- 삭제는 항목을 표에서 지우고, 그 항목을 가리키던 부모의 `childIds`에서도 지웁니다. 둘 중 하나를 빠뜨리면 존재하지 않는 `id`를 가리키게 됩니다.
- 정규화는 중첩이 깊거나 같은 항목이 여러 곳에 쓰일 때 이점이 큽니다. 한 단계 목록이면 배열로 충분합니다.
- 목록을 `id` 순서로 보여 줘야 하면 순서를 담은 `ids` 배열을 따로 둡니다.

## Single Source of Truth

단일 진실 공급원(single source of truth)은 각각의 정보를 하나의 정해진 곳에서만 소유하게 하는 원칙입니다. 모든 State를 한곳에 모으라는 뜻이 아니라, State 하나하나에 그것을 소유한 컴포넌트가 정확히 하나 있어야 한다는 뜻입니다.

- 소유자가 하나이므로 값이 달라질 곳도 하나입니다. 다른 곳은 Props로 받아 읽습니다.
- 두 컴포넌트가 같은 값을 보여야 하면 각자 State를 두지 않고, 가장 가까운 공통 부모가 State를 소유하고 Props로 내려 줍니다. 이를 State 끌어올리기라 하며 14편에서 다룹니다.
- 값을 바꾸는 쪽(자식)은 부모가 내려 준 이벤트 핸들러를 호출합니다. 데이터는 아래로, 변경 요청은 위로 흐릅니다.
- 같은 데이터를 두 곳에 두면 동기화 코드를 직접 짜야 하고, 이 편에서 본 중복·파생 State 문제가 생깁니다.

```jsx
function Parent() {
  const [text, setText] = useState('')
  return (
    <>
      <Input text={text} onChange={setText} />
      <Preview text={text} />
    </>
  )
}
```

## UI State

UI State는 화면의 모양과 상호작용 상태를 나타내는 값입니다. 서버나 도메인 데이터와 무관하게 화면 안에서만 의미가 있습니다. (이 구분은 이 과목의 분류이며 React의 공식 용어는 아닙니다.)

| 예 | 설명 |
|----|------|
| 모달·메뉴·아코디언의 열림 | `isOpen` |
| 선택된 탭 | `activeTab` |
| 입력 중인 검색어, 필터 | `query`, `filter` |
| 호버·포커스 같은 일시 상태 | 짧게 유지되는 값 |
| 정렬 방식, 보기 모드 | `sortBy`, `view` |

- 대개 그 UI를 그리는 컴포넌트가 소유하고 `useState`로 충분합니다.
- 여러 컴포넌트가 보여야 하면 공통 부모로 끌어올립니다. 멀리 떨어져 있으면 Context를 씁니다(자세히는 24편).
- 새로고침 후에도 유지되거나 링크로 공유되어야 하는 UI 상태(필터, 탭)는 주소 쿼리에 두는 것이 낫습니다(자세히는 29편).
- 컴포넌트가 사라지면 UI State도 사라집니다. 그 동작은 13편에서 다룹니다.

## Domain State

Domain State는 서비스가 다루는 업무 데이터를 나타내는 값입니다. 장바구니 상품, 할 일 목록, 작성 중인 글 같은 것입니다. UI State와 달리 화면이 바뀌어도 의미가 유지되고, 업무 규칙(합계 계산, 중복 금지)이 붙습니다. (이 구분도 이 과목의 분류입니다.)

- 다른 화면에서도 쓰이는 경우가 많아 소유 위치를 신중히 정해야 합니다. 쓰는 곳 중 가장 높은 공통 부모, 또는 앱 전체 저장소가 후보입니다.
- 객체와 배열로 이루어지므로 11편의 불변 업데이트와 이 편의 정규화가 모두 적용됩니다.
- 합계, 개수, 할인 금액 같은 값은 도메인 State에서 계산하는 파생 값입니다. 별도 State로 만들지 않습니다.
- 서버에서 가져온 데이터는 도메인 데이터이지만 성격이 달라서 따로 구분합니다(아래).

```jsx
const [cart, setCart] = useState([]) // Domain State
const total = cart.reduce((s, it) => s + it.price, 0) // 파생
```

## Server State와 Client State

Server State는 서버에 원본이 있고 화면은 그 복사본을 보관하는 데이터입니다. Client State는 브라우저 안에서만 존재하고 서버가 모르는 값입니다. 둘은 성격이 달라 다르게 다룹니다.

| 항목 | Server State | Client State |
|------|--------------|--------------|
| 원본 위치 | 서버(원격 저장소) | 브라우저 |
| 접근 방식 | 비동기 요청 | 동기 읽기·쓰기 |
| 소유 | 여러 사용자가 공유 | 현재 사용자만 |
| 낡을 가능성 | 있음(내가 모르게 서버에서 바뀜) | 없음 |
| 예 | 상품 목록, 사용자 프로필 | 메뉴 열림, 입력 중인 텍스트 |

- Server State는 원격에 저장되고 비동기로 가져오며 여러 사용자가 공유하므로, 가져온 값이 어느새 낡을 수 있습니다. 가져오기, 캐시, 동기화, 갱신이 모두 문제가 됩니다.
- 서버 응답을 `useState`에 넣고 `useEffect`로 가져오는 방식은 로딩, 오류, 중복 요청, 캐시를 모두 직접 짜야 합니다. 이 영역을 전담하는 라이브러리를 씁니다.
- Client State는 `useState`, Context 등으로 충분한 경우가 많습니다.
- 서버에서 받은 값을 그대로 다시 `useState`에 복사하면 파생 State의 문제가 생깁니다. 서버 데이터는 읽기만 하는 값으로 다룹니다.
- 서버 통신은 27편에서 다룹니다.

## 상태 종류별 도구 대응표

상태 종류별로 보관 위치와 도구가 다릅니다. 처음에는 가장 가까운 곳에서 `useState`로 시작하고, 필요가 생길 때 한 단계씩 넓힙니다.

| 상태 종류 | 기본 도구 | 확장할 때 |
|-----------|-----------|-----------|
| 컴포넌트 안 UI State | `useState` | 로직이 복잡하면 `useReducer` |
| 가까운 컴포넌트가 공유 | State 끌어올리기 | 멀면 Context |
| 폼 입력 | 제어 컴포넌트와 `useState` | React Hook Form |
| 앱 전역 Client State | Context | Zustand, Redux Toolkit, Jotai |
| Server State | `fetch`와 Effect | TanStack Query |
| 주소로 공유할 상태 | URL 쿼리 | React Router의 `useSearchParams` |

- Zustand는 Provider 없이 쓰는 작은 상태 저장소 라이브러리입니다.
- Redux Toolkit은 Redux를 쓰기 쉽게 만든 공식 도구 모음입니다.
- Jotai는 atom을 조합해 상태를 만드는 라이브러리입니다.
- TanStack Query는 서버 상태의 가져오기, 캐싱, 동기화, 갱신을 맡는 라이브러리입니다.
- React Hook Form은 폼 상태와 검증을 맡는 라이브러리입니다.
- 이 표는 개요입니다. 라이브러리는 이 과목 범위가 아니며 중급 과목에서 다룹니다. 폼은 15편과 16편에서 다룹니다.
- 외부 라이브러리 없이 `useState`와 Context만으로 충분한 앱도 많습니다. 도구는 필요가 확인된 뒤에 도입합니다.

## 핵심 정리

- 함께 바뀌는 값은 하나의 State로 묶고, 동시에 참일 수 없는 값들은 `status` 같은 하나의 변수로 합칩니다.
- 같은 정보를 두 곳에 저장하지 않습니다. 객체 대신 `id`를 저장하고, 계산할 수 있는 값은 State에 넣지 않고 렌더링 중에 계산합니다.
- State는 변하고, Props가 아니고, 계산할 수 없는 최소 집합만 둡니다. Props를 State에 복사하면 갱신되지 않으므로 초기값 용도라면 `initial` 이름을 씁니다.
- 깊게 중첩된 데이터는 `id`를 키로 하는 평평한 구조로 정규화하면 갱신이 쉽습니다.
- 각 State는 소유자가 하나여야 하며, 공유는 공통 부모로 끌어올려 Props로 내려 줍니다.
- 상태는 UI, 도메인, 서버 값으로 구분하고, 서버 상태는 전용 도구로, 나머지는 `useState`에서 시작해 필요할 때 넓힙니다.

## 뭐가 느린지 먼저 재기

성능 개선은 측정으로 시작합니다. 느리다고 짐작되는 곳이 실제 병목인 경우는 많지 않아서, 짐작으로 고치면 시간만 쓰고 효과가 없습니다. 먼저 병목이 어느 종류인지 가립니다.

| 병목 종류 | 증상 | 확인 수단 |
|-----------|------|-----------|
| CPU(이벤트 루프 점유) | 한 요청 때문에 전체가 느려짐 | 타이머 지연, `monitorEventLoopDelay`, `--cpu-prof` |
| 메모리·GC | RSS 증가, 응답 지연의 주기적 급등 | `process.memoryUsage()`, `PerformanceObserver`의 `gc` |
| 외부 대기(DB, HTTP) | 이벤트 루프는 한가한데 응답이 느림 | 구간별 `performance.now()` |
| 연결 비용 | 요청마다 연결 수립 시간이 붙음 | 연결 수 관찰, 구간 시간 |

```js
import { performance } from 'node:perf_hooks';

const t0 = performance.now();
await doWork();
const ms = performance.now() - t0;
console.log(`doWork ${ms.toFixed(1)}ms`);
```

- `performance.now()`는 프로세스 시작 시점을 0으로 하는 고해상도 밀리초 값입니다. `perf_hooks` 모듈의 안정성 지수는 2(Stable)입니다(중급 23편).
- 이벤트 루프가 막히는지는 `monitorEventLoopDelay()`가 알려 줍니다. 지연을 나노초 단위 히스토그램으로 샘플링합니다(v11.10.0에 추가).

```js
import { monitorEventLoopDelay } from 'node:perf_hooks';

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
// ... 부하를 거는 구간 ...
h.disable();
console.log(h.percentile(99) / 1e6, 'ms'); // p99 지연
console.log(h.max / 1e6, 'ms');            // 최대 지연
```

- 이벤트 루프가 얼마나 바쁜지는 `performance.eventLoopUtilization()`으로 보고, 함수 단위 시간은 `performance.timerify()`로 잽니다.
- 평균은 느린 요청을 가립니다. 부하 테스트와 p95·p99 읽는 법, 프로파일러 사용은 05편에서 다룹니다.
- 측정 조건은 운영과 비슷해야 합니다. 데이터 크기, 동시 요청 수, 네트워크 지연이 다르면 결과가 바뀝니다. JIT 컴파일 때문에 처음 몇 번의 실행은 느릴 수 있어서 반복해 재야 합니다(06편).
- 아래 절의 수치는 모두 이 문서를 쓰며 로컬(Node.js 24, Windows)에서 잰 값입니다. 절대 값이 아니라 방향을 보는 용도입니다.

## 동기 fs

동기 fs API(`readFileSync`, `writeFileSync` 등)는 작업이 끝날 때까지 이벤트 루프를 멈춥니다. 비동기 API는 libuv 스레드 풀이 처리하는 동안 루프가 다른 일을 합니다(기초 01편).

```js
import { readFileSync } from 'node:fs';
import { readFile } from 'node:fs/promises';

http.createServer((req, res) => {
  const a = readFileSync(path); // ❌ 읽는 동안 모든 요청이 멈춤
  readFile(path).then((b) => res.end(b)); // ✅
});
```

- 로컬 실험: 400 MiB 파일을 읽는 동안 10ms 타이머의 최대 간격이 `readFileSync`는 98–202ms(읽는 시간 전체)였고, `fs/promises`의 `readFile`은 16–20ms였습니다.
- Node.js 공식 가이드는 서버에서 동기 fs API를 쓰지 말라고 합니다. 접근 시간이 NFS 같은 분산 파일 시스템에서는 크게 달라질 수 있기 때문입니다.
- 같은 이유로 서버에서 피할 동기 API: `crypto.pbkdf2Sync`, `crypto.randomBytes`의 동기 형태, `zlib.inflateSync`·`deflateSync`, `execSync`·`spawnSync`·`execFileSync`(01편).
- 동기 API는 스크립트, CLI, 서버가 요청을 받기 전의 초기화(설정 파일 읽기)에서는 써도 됩니다. 기준은 이벤트 루프에서 다른 일이 기다리고 있는지입니다(기초 16편).

**흔한 실수:** 파일이 작다고 요청 핸들러에서 `readFileSync`를 쓰는 것입니다. 디스크나 네트워크 파일 시스템이 느려지는 순간 모든 요청이 같이 느려집니다.

## 큰 파일 readFile

`readFile`은 파일 전체를 메모리에 올립니다. 공식 문서도 메모리 비용을 줄이려면 가능한 경우 `fs.createReadStream()`을 쓰라고 안내합니다.

- 한도: `fs.readFile()`은 2 GiB를 넘는 파일을 읽을 수 없고 `ERR_FS_FILE_TOO_LARGE`가 납니다. `Buffer`의 한계가 아니라 내부 I/O 제약이며, 문서는 더 큰 파일에 스트림을 권합니다.
- 메모리는 파일 크기만큼 필요하고 동시 요청 수만큼 곱해집니다. 100 MiB 파일을 요청 10개가 동시에 읽으면 약 1 GiB입니다.
- 로컬 실험(400 MiB 파일): 최대 RSS가 `readFile`에서 452 MB, 스트림에서 80 MB였습니다.
- 대신 스트림은 시간이 더 걸렸습니다. 같은 실험에서 `readFile`이 120–128ms, 스트림은 335–393ms였습니다. 메모리를 줄이는 대신 속도를 일부 내주는 선택입니다.
- 작은 파일(설정, 템플릿)은 `readFile`이 더 간단하고 빠릅니다. 파일이 크거나 크기를 모르거나, 업로드·로그처럼 입력 크기를 통제하지 못할 때 스트림을 씁니다(기초 16편, 중급 27편).

## 큰 JSON

`JSON.parse`와 `JSON.stringify`는 동기 CPU 작업이고 걸리는 시간이 데이터 크기에 비례합니다. 이벤트 루프에서 실행되므로 큰 JSON을 처리하는 동안 다른 요청이 멈춥니다. 공식 가이드도 이 두 함수를 이벤트 루프를 막을 수 있는 연산으로 꼽습니다(가이드 예제에서 50 MB JSON의 stringify는 0.7초, parse는 1.3초).

```js
const text = JSON.stringify(items); // 500,000개 객체
JSON.parse(text);
// 36 MB 문자열: stringify 143ms, parse 209ms (이 환경)
```

- 이 시간 동안 루프가 돌지 않으므로 같은 프로세스의 다른 요청은 최소 이 시간만큼 기다립니다.
- 줄이는 방법
  - 데이터 자체를 줄입니다: 페이지네이션, 필요한 필드만 선택, 요청 본문 크기 제한(07편).
  - 한 덩어리 JSON 대신 줄 단위 JSON(NDJSON, 한 줄에 객체 하나)으로 저장하고 스트림으로 한 줄씩 파싱합니다.
  - 스트리밍 JSON 라이브러리를 씁니다. 공식 가이드는 JSONStream과 Big-Friendly JSON을 예로 듭니다.
  - 워커로 옮깁니다(02편). 다만 워커와 주고받을 때 직렬화 비용이 다시 듭니다.

```js
import { createReadStream } from 'node:fs';
import { createInterface } from 'node:readline';

const input = createReadStream(path);
const rl = createInterface({ input });
for await (const line of rl) {
  handle(JSON.parse(line)); // 한 줄씩 파싱, 전체를 올리지 않음
}
```

- 줄 단위로 나누면 한 번에 파싱하는 데이터가 파일 전체가 아니라 읽은 조각 분량으로 제한되고, 조각 사이에 이벤트 루프가 다른 일을 할 수 있습니다(중급 22편).
- 같은 큰 객체를 요청마다 `stringify`하지 않습니다. 변하지 않는 응답은 문자열로 한 번 만들어 캐시합니다.

## 이벤트 루프 블로킹

이벤트 루프 블로킹은 JavaScript 콜백 하나가 오래 실행되어 대기 중인 다른 콜백, 즉 다른 요청과 타이머가 실행되지 못하는 상태입니다(기초 03편). 모든 요청의 지연이 함께 늘어납니다.

| 원인 | 대응 |
|------|------|
| 동기 fs·crypto·zlib·child_process API | 비동기 API로 교체 |
| 큰 JSON 파싱·직렬화 | 크기 제한, 스트리밍, 워커 |
| 큰 배열 순회, 무거운 계산 | 분할(partitioning) 또는 워커(02편) |
| 정규식 폭주(ReDoS) | 정규식 단순화, 입력 길이 제한(07편) |

탐지는 위에서 본 `monitorEventLoopDelay`나 타이머 간격으로 합니다. 해결은 공식 가이드의 두 가지 방식입니다.

- 분할(partitioning): 계산을 조각으로 나누고 조각 사이에서 이벤트 루프에 순서를 양보합니다. 하나의 코어만 쓰므로 단순한 반복에 맞습니다.
- 오프로딩(offloading): 복잡한 계산은 워커 스레드나 별도 프로세스로 옮깁니다(02편, 01편). 통신(직렬화) 비용이 들지만 여러 코어를 쓰는 이득이 더 큽니다.

```js
import { setImmediate as tick } from 'node:timers/promises';

for (let i = 0; i < items.length; i++) {
  s += work(items[i]);
  if (i % 50_000 === 0) await tick(); // 대기 중인 이벤트에 양보
}
```

- 로컬 실험(300만 건 계산): 그냥 돌리면 10ms 타이머의 최대 간격이 156ms였고, 5만 건마다 양보하자 17ms였습니다. 총 시간은 비슷했습니다.
- 공식 가이드의 원칙은 이벤트 루프가 요청을 조율하는 일을 하고 처리 자체를 하지 않는다는 것입니다. 서버가 복잡한 계산에 크게 의존한다면 Node.js가 맞는 도구인지도 따져 보라고 합니다.

## 스트림으로 바꾸기

스트림은 데이터를 조각(chunk) 단위로 읽고 쓰면서, 한 번에 메모리에 올리는 양을 제한하는 방식입니다. 전체를 읽은 뒤 처리하는 코드를 스트림 파이프라인으로 바꾸면 메모리가 입력 크기와 무관해집니다.

```js
import {
  createReadStream, createWriteStream,
} from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

await pipeline(
  createReadStream(src),
  createGzip(),
  createWriteStream(dst),
);
```

- `pipeline`은 각 단계의 에러를 모으고 실패 시 모든 스트림을 정리합니다. 쓰는 쪽이 느리면 읽기를 늦추는 backpressure도 처리합니다(중급 02편).
- HTTP 응답도 같은 방식입니다. `await pipeline(createReadStream(path), res)`로 파일을 읽으며 곧바로 보냅니다.
- 바꾸기 전에 확인할 것: 입력이 크거나 크기를 모르는가, 변환 단계가 청크 단위로 가능한가. JSON처럼 전체가 있어야 파싱되는 형식은 줄 단위 형식으로 바꾸거나 스트리밍 파서를 써야 합니다.
- 입력이 작으면 스트림이 오히려 느리고 코드가 복잡해집니다. 위 실험에서 스트림의 총 시간이 길었던 것처럼 메모리와 시간의 교환입니다.

## 불필요한 await 순차

서로 의존하지 않는 비동기 작업을 `await`로 하나씩 기다리면 걸리는 시간이 모두 더해집니다. 독립된 작업은 함께 시작해서 `Promise.all`로 기다립니다(기초 24편).

```js
// ❌ 100 + 100 + 100 = 약 300ms
const user = await getUser(id);
const posts = await getPosts(id);
const stats = await getStats(id);

// ✅ 약 100ms
const [user, posts, stats] = await Promise.all([
  getUser(id), getPosts(id), getStats(id),
]);
```

- 로컬 실험(각 100ms 대기 작업 3개): 순차 312ms, 병렬 112ms.
- 앞 결과가 다음 입력이 되는 의존 관계는 순차로 둡니다. 순서가 필요한지부터 구분합니다.
- 반복문 안의 `await`는 순차 실행입니다. 항목이 독립이면 `map`으로 프로미스를 만들어 `Promise.all`에 넘깁니다.
- 한 번에 수천 개를 `Promise.all`로 시작하면 DB 연결, 소켓, 파일 핸들이 한꺼번에 몰립니다. 동시에 실행할 수에 상한을 둡니다(기초 24편의 동시성 제한).
- 일부 실패를 허용하려면 `Promise.allSettled`를 씁니다.

## 커넥션을 매번 새로 열기

연결을 요청마다 새로 맺으면 TCP 핸드셰이크(HTTPS이면 TLS 핸드셰이크도)와 인증이 매번 반복되어 지연과 서버 자원이 낭비됩니다. 연결은 만들어 두고 재사용합니다.

- HTTP 클라이언트: 요청마다 `agent: false`를 쓰거나, 호출할 때마다 `new http.Agent()`를 만들거나, 호출마다 새 클라이언트를 만들면 연결이 재사용되지 않습니다.
- DB와 Redis: 요청 처리 중에 연결하고 끊는 대신 앱 시작 시 커넥션 풀이나 클라이언트를 하나 만들어 공유합니다(중급 17편, 중급 18편).
- 로컬 실험(루프백, 같은 서버에 순차 요청 2000건): 연결을 재사용하지 않는 구성은 연결 2000개와 1.4–1.6초, 재사용하는 구성은 연결 1개와 0.38초였습니다. 루프백에는 네트워크 지연이 없어서 실제 네트워크와 TLS에서는 차이가 더 커집니다.
- 사용하지 않는 소켓은 OS 자원을 소비하므로, 문서도 쓰임이 끝난 `Agent`는 `destroy()`하라고 권합니다.

## Agent keep-alive

`http.Agent`는 HTTP 클라이언트의 연결 지속과 재사용을 관리하는 객체입니다. 같은 호스트와 포트로 가는 요청의 소켓을 대기열로 관리하다가, `keepAlive` 옵션에 따라 소켓을 닫거나 풀에 두고 재사용합니다.

| 생성 방법 | 연결 재사용 |
|-----------|--------------|
| 기본값(`http.globalAgent`) | 재사용함. v19.0.0부터 keep-alive와 5초 타임아웃이 기본 |
| `new http.Agent()` | 재사용 안 함. `keepAlive` 기본값이 `false` |
| `new http.Agent({ keepAlive: true })` | 재사용함 |
| 요청 옵션 `agent: false` | 요청 한 번용 새 Agent. 재사용 안 함 |

```js
import http from 'node:http';

const agent = new http.Agent({
  keepAlive: true,
  maxSockets: 50, // 호스트당 동시 연결 상한
});
http.get({ host, path, agent }, onResponse);
```

주요 옵션은 다음과 같습니다.

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `keepAlive` | `false` | 요청이 없어도 소켓을 유지해 재사용 |
| `keepAliveMsecs` | `1000` | TCP keep-alive 패킷의 초기 지연(ms) |
| `maxSockets` | `Infinity` | 호스트당 최대 소켓 수. 초과 요청은 대기열에서 기다림 |
| `maxFreeSockets` | `256` | 호스트당 유휴로 남겨 둘 소켓 수 |
| `maxTotalSockets` | `Infinity` | 전체 호스트 합계 상한 |
| `scheduling` | `'lifo'` | 유휴 소켓을 고르는 방식 |

- `Agent`는 모듈 수준에서 한 번 만들어 공유합니다. 요청마다 만들면 재사용이 되지 않습니다.
- `maxSockets` 기본값이 무제한이라서 동시 요청이 많은 코드에서는 상한을 두는 편이 안전합니다.
- 서버가 유휴 연결을 먼저 닫을 수 있습니다. 그러면 풀에서 제거되고 다음 요청에서 새로 연결합니다. 서버의 `keepAliveTimeout`과 로드 밸런서의 idle timeout 관계는 중급 06편을 참고합니다.
- 전역 `fetch`는 undici로 동작하고 undici의 `Agent`가 기본 dispatcher입니다. 출처(origin)마다 연결 풀을 만들어 재사용하며 `keepAliveTimeout` 기본값은 4000ms입니다.
- `fetch`의 연결 설정을 바꾸려면 `undici` 패키지를 설치해 전역 dispatcher를 교체합니다.

```js
import { Agent, setGlobalDispatcher } from 'undici';

setGlobalDispatcher(new Agent({ connections: 10 }));
```

## 클러스터로 코어 쓰기

Node.js 프로세스 하나는 JavaScript를 한 스레드에서 실행하므로 코어가 여러 개여도 하나만 바쁩니다. 프로세스를 여러 개 띄우면 여러 코어를 쓰고 처리량(초당 요청 수)이 늘어납니다(03편).

- 효과가 있는 경우: 코어가 남는데 이벤트 루프가 포화된 상태, 즉 요청 처리량이 CPU에서 막히는 경우입니다. `performance.eventLoopUtilization()`이 1에 가깝다면 후보입니다.
- 효과가 없는 경우: 병목이 DB·외부 API 대기이거나, 한 요청의 계산이 길어서 지연이 문제인 경우입니다. 프로세스를 늘려도 요청 하나의 지연은 줄지 않습니다. 그때는 계산을 워커로 나눕니다(02편).
- 프로세스가 늘면 자원도 곱해집니다. 메모리는 프로세스 수만큼, DB 연결은 프로세스별 풀 크기 곱하기 프로세스 수만큼 필요합니다. DB가 허용하는 연결 수를 넘지 않게 풀 크기를 정합니다.
- 프로세스 사이에서는 메모리를 공유하지 않으므로 상태는 외부 저장소에 둡니다(03편).
- 컨테이너 환경에서는 프로세스를 늘리는 대신 컨테이너를 복제하는 구성이 일반적입니다(03편).

## GC를 먼저 만지지 않기

V8의 가비지 컬렉션(GC)은 기본 설정으로 자동 조정됩니다. 성능 문제가 보일 때 GC 플래그부터 건드리는 것은 순서가 거꾸로입니다. 먼저 할당을 줄이거나 누수를 찾고, GC가 실제로 병목인지 측정한 뒤에 만집니다(프로파일링과 누수는 05편).

```js
import { PerformanceObserver } from 'node:perf_hooks';

let gcMs = 0;
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) gcMs += e.duration;
}).observe({ entryTypes: ['gc'] });
// 일정 시간 뒤 gcMs를 전체 시간과 비교
```

- 로컬 실험: 객체 300만 개를 만들고 버리는 149ms짜리 루프에서 GC가 38번 돌았고 합계는 15ms(약 10퍼센트)였습니다. 이런 비율이 보여야 GC를 의심합니다.
- 플래그는 마지막 수단입니다. `--max-old-space-size`는 Old Space 한도, `--max-semi-space-size`는 New Space 크기, `--gc-interval`은 GC 빈도, `--expose-gc`는 `global.gc()` 수동 호출을 열어 줍니다.
- 한도를 올리는 것은 누수를 고치지 않고 OOM을 늦출 뿐입니다. 공식 문서는 메모리가 한도에 가까워지면 V8이 해제를 위해 GC에 더 많은 시간을 쓴다고 설명하고, 2 GiB 머신이라면 다른 용도를 위해 1536 정도로 두는 것을 예로 듭니다.
- `global.gc()` 수동 호출은 자동 GC를 끄지 않고 보조할 뿐이며 남용하면 성능이 떨어집니다.
- 점검 순서는 측정, 할당·누수 줄이기, 그래도 부족하면 한도와 플래그입니다.

## Number 안전 정수

JavaScript의 `Number`는 64비트 부동소수점이라서 정수를 정확히 표현하는 범위에 한계가 있습니다. 안전 정수(safe integer)는 정확히 표현되고 올바르게 비교되는 정수로, 범위는 `-(2^53 - 1)`부터 `2^53 - 1`까지이고 `Number.MAX_SAFE_INTEGER`는 `9007199254740991`입니다.

```js
Number.MAX_SAFE_INTEGER;            // 9007199254740991
2 ** 53 === 2 ** 53 + 1;            // true
9007199254740993;                // 9007199254740992 (바뀜)
Number.isSafeInteger(2 ** 53);      // false
JSON.parse('{"id":9007199254740993}');
// { id: 9007199254740992 }
```

- 범위를 넘는 정수는 에러 없이 가장 가까운 표현 가능한 값으로 반올림됩니다. 조용히 값이 틀리는 것이 문제입니다.
- 흔히 부딪히는 곳: 64비트 정수 ID(DB의 `bigint`, 분산 ID 생성기), 나노초 타임스탬프, 큰 카운터, 파일 크기·inode입니다. `Date.now()`(밀리초)는 안전 범위 안입니다.
- `Number.isSafeInteger(n)`으로 범위를 확인합니다. 계산 결과도 `MAX_SAFE_INTEGER + 1`과 `+ 2`가 같아지는 식으로 틀릴 수 있어서 큰 값의 연산은 `BigInt`로 합니다.
- Node.js 안에서 `BigInt`가 쓰이는 대표 API: `process.hrtime.bigint()`(나노초 시각, 기초 06편), `fs.stat(path, { bigint: true })`.
- 금액은 부동소수점 소수 대신 최소 단위의 정수(원, 센트)로 저장하고, 그 정수가 안전 범위를 넘지 않는지 확인합니다.
- 외부와 주고받는 ID는 문자열로 다루는 것이 가장 안전합니다. 문자열은 정밀도를 잃지 않습니다.

## BigInt가 JSON에 안 들어가는 문제

`BigInt`는 정수 크기에 제한이 없는 숫자 타입입니다(`123n`). JSON에는 `BigInt` 타입이 없어서 `JSON.stringify`가 `BigInt`를 만나면 `TypeError`를 던집니다.

```js
JSON.stringify({ n: 1n });
// TypeError: Do not know how to serialize a BigInt
1n + 1; // TypeError: Cannot mix BigInt and other types
```

해결은 직렬화 방식을 정하는 것입니다. 받는 쪽이 무엇을 이해하는지에 따라 고릅니다.

| 방식 | 코드 | 결과와 특징 |
|------|------|--------------|
| 문자열로 직렬화 | `replacer`에서 `v.toString()` | `{"n":"1"}`. 어떤 언어의 수신자도 안전. 받는 쪽에서 `BigInt()`로 복원 |
| `toJSON` 패치 | `BigInt.prototype.toJSON = ...` | 전역에 영향. MDN은 이 경우 내장 객체 패치를 반대하지 않는다고 설명하지만 라이브러리와 충돌할 수 있음 |
| JSON 숫자로 직렬화 | `JSON.rawJSON(String(v))` | `{"n":1}` 숫자 그대로 출력. 수신자가 큰 정수를 지원할 때 |

```js
const replacer = (k, v) =>
  typeof v === 'bigint' ? v.toString() : v;

JSON.stringify({ n: 1n }, replacer);    // {"n":"1"}
JSON.stringify({ n: JSON.rawJSON('9007199254740993') });
// {"n":9007199254740993}
```

받는 쪽에서 정밀도를 잃지 않으려면 파서가 숫자의 원본 텍스트를 봐야 합니다. `JSON.parse`의 `reviver`는 세 번째 인수로 `context.source`(원본 JSON 텍스트)를 받습니다.

```js
const text = '{"id":9007199254740993}';
JSON.parse(text, (k, v, { source }) =>
  typeof v === 'number' && !Number.isSafeInteger(v)
    ? BigInt(source) : v);
// { id: 9007199254740993n }
```

- 위 `JSON.rawJSON`과 `context.source`는 Node.js 24(V8 13.6)에서 동작을 확인했습니다. `context.source`를 지원하지 않는 환경에서는 `reviver`가 호출될 때 이미 반올림된 값이어서 복원할 수 없고, 문자열 방식이 유일한 방법입니다(MDN).
- 안전하지 않은 큰 정수 ID를 API로 내보낼 때는 처음부터 문자열 필드로 설계하면 `rawJSON` 없이도 안전합니다.
- `BigInt`는 연산이 느립니다. 로컬 단순 덧셈 루프 2천만 회에서 `Number`는 15ms, `BigInt`는 3091ms였습니다. 안전 범위를 넘는 값에만 쓰고 일반 계산에는 `Number`를 씁니다.
- `BigInt`와 `Number`를 섞은 연산은 `TypeError`입니다. 변환은 `BigInt(n)`, `Number(b)`로 명시합니다. `Number(b)`는 안전 범위를 넘으면 정밀도를 잃습니다.
- `postMessage`와 IPC의 `serialization: 'advanced'`는 `BigInt`를 그대로 전달합니다(01편, 02편). JSON 경계에서만 문제가 됩니다.

## 핵심 정리

- 성능 개선은 측정으로 시작합니다. CPU(이벤트 루프 점유), 메모리·GC, 외부 대기, 연결 비용을 구분하고 `performance.now()`, `monitorEventLoopDelay`, `gc` 엔트리로 확인합니다.
- 이벤트 루프를 막는 것은 동기 API, 큰 JSON, 무거운 반복입니다. 비동기 API, 스트림·줄 단위 처리, 분할(`setImmediate`)이나 워커로 해결하고, `readFile`은 파일 크기와 동시성에 비례해 메모리를 씁니다.
- 독립된 await는 `Promise.all`로 병렬화하되 동시 실행 수에 상한을 둡니다.
- 연결은 재사용합니다. `new http.Agent()`와 `agent: false`는 keep-alive가 꺼져 있고, 공유하는 `keepAlive: true` Agent나 기본 `globalAgent`, DB 풀을 씁니다.
- 코어를 쓰는 클러스터는 이벤트 루프 포화일 때 효과가 있고, 자원이 곱해지므로 풀 크기를 맞춥니다. GC 플래그는 측정 뒤 마지막에 건드립니다.
- `Number`는 `2^53 - 1`까지만 정확해서 큰 정수 ID는 문자열이나 `BigInt`로 다루고, `BigInt`는 `JSON.stringify`가 `TypeError`를 던지므로 `replacer`나 `JSON.rawJSON`으로 직렬화합니다.

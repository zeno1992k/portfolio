## worker_threads

`node:worker_threads`는 JavaScript를 병렬로 실행하는 스레드를 만드는 모듈입니다. 안정성 지수는 2(Stable)이고 v10.5.0에서 추가되었습니다. 문서가 밝히는 용도는 CPU를 많이 쓰는 JavaScript 연산입니다.

| 항목 | `child_process`(01편) | `worker_threads` | `cluster`(03편) |
|------|------------------------|------------------|-----------------|
| 실행 단위 | 프로세스 | 같은 프로세스 안의 스레드 | 프로세스 |
| 메모리 공유 | 불가 | 가능(`SharedArrayBuffer`, `ArrayBuffer` 전달) | 불가 |
| 통신 | IPC 채널 | `MessagePort` | IPC 채널 |
| 주 용도 | 외부 프로그램, 격리 | CPU 바운드 JS 분산 | 서버 프로세스 복제 |

- 이벤트 루프와 V8 엔진 인스턴스는 스레드마다 따로 가집니다. 한 스레드의 동기 계산이 다른 스레드의 이벤트 루프를 막지 않습니다.
- 가져오기: `import { Worker } from 'node:worker_threads'`.

## 메인 스레드와 워커

메인 스레드는 프로그램이 처음 시작되는 스레드이고, 워커는 `new Worker(filename)`으로 만드는 별도 스레드입니다. 같은 파일을 두 스레드가 실행할 수 있어서 `isMainThread`로 구분합니다.

```js
import {
  Worker, isMainThread, parentPort,
} from 'node:worker_threads';

if (isMainThread) {
  const worker = new Worker(import.meta.filename);
  worker.on('message', (msg) => console.log(msg)); // hello
  worker.on('exit', (code) => console.log(code)); // 0
} else {
  parentPort.postMessage('hello');
}
```

- `filename`은 절대 경로, `./` 또는 `../`로 시작하는 상대 경로(작업 디렉터리 기준), `file:` 또는 `data:` URL 중 하나여야 합니다. `eval: true`이면 코드 문자열로 해석합니다.
- 워커 안에서는 `isMainThread`가 `false`이고, 부모와 통신하는 `parentPort`를 쓸 수 있습니다.

`Worker`가 내는 이벤트는 다음과 같습니다.

| 이벤트 | 시점 |
|--------|------|
| `online` | 워커가 JavaScript 실행을 시작함 |
| `message` | 워커가 `parentPort.postMessage()`를 호출함 |
| `messageerror` | 메시지 역직렬화에 실패함 |
| `error` | 워커에서 처리되지 않은 예외가 발생함. 워커는 종료됨 |
| `exit` | 워커가 멈춤. 마지막 이벤트이고 인수는 종료 코드 |

- 워커가 보낸 메시지는 모두 `exit`보다 먼저 발생합니다.
- 워커 안의 `process.exit()`는 프로그램 전체가 아니라 그 스레드만 끝냅니다. `exit` 코드는 그 값이고, `worker.terminate()`로 끝내면 `1`입니다.
- `worker.terminate()`는 가능한 한 빨리 실행을 멈추고, `exit`가 발생할 때 이행되는 프로미스를 돌려줍니다.
- `await using worker = new Worker(...)`로 선언하면 블록이 끝날 때 `terminate()`가 호출됩니다(v24.2.0에 추가).
- `worker.unref()`를 호출하면 워커가 유일하게 남은 핸들이어도 프로그램이 종료될 수 있습니다.

워커 환경은 메인 스레드와 다릅니다.

- `process.exit()`가 스레드 하나만 끝내고, `process.abort()`와 `process.chdir()`는 쓸 수 없습니다.
- `process.env`는 부모의 복사본입니다. 한쪽의 변경은 다른 쪽에 보이지 않습니다. `Worker`의 `env` 옵션에 `SHARE_ENV`를 주면 공유합니다.
- 시그널(`SIGINT` 등)은 워커의 `process.on()`으로 전달되지 않습니다.
- 부모 프로세스의 IPC 채널에 접근할 수 없습니다.
- 워커 안에서 다시 워커를 만들 수 있습니다.

**흔한 실수:** 호출마다 워커를 새로 만드는 것입니다. 문서도 이런 용도에는 워커 풀을 쓰라고 하며, 워커 생성 비용이 이득보다 클 수 있다고 경고합니다. 풀은 아래 "워커 풀(piscina)"에서 다룹니다. 참고로 로컬(Node.js 24, Windows)에서 `eval` 워커가 `online`까지 걸린 시간은 24ms였습니다.

## postMessage

`postMessage(value, transferList)`는 채널의 반대편으로 값을 보내는 메서드입니다. 부모는 `worker.postMessage()`, 워커는 `parentPort.postMessage()`를 쓰고, 받는 쪽은 `'message'` 이벤트로 값을 받습니다.

```js
// 부모
worker.postMessage({ id: 1, n: 21 });
worker.on('message', (msg) => console.log(msg));
// { id: 1, result: 42 }

// 워커
parentPort.on('message', ({ id, n }) => {
  parentPort.postMessage({ id, result: n * 2 });
});
```

- 값은 보내는 즉시 복제되므로 보낸 뒤 원본을 바꿔도 받는 쪽에는 영향이 없습니다.
- 리스너는 복제된 값 하나만 받습니다. 요청과 응답을 짝지으려면 `id` 같은 필드를 메시지에 넣습니다.
- 복제할 수 없는 값을 보내면 `DataCloneError`가 발생합니다(아래 "구조적 복제").
- `parentPort`에 `message` 리스너가 있는 동안 워커는 계속 살아 있습니다. 끝내려면 `terminate()`나 `process.exit()`, 또는 포트를 닫습니다.

## 구조적 복제

구조적 복제(structured clone)는 `postMessage`와 `workerData`가 값을 복사하는 방식으로, HTML 표준의 알고리즘입니다. JSON보다 복제할 수 있는 값이 많습니다.

| 값 | 결과 |
|----|------|
| 순환 참조 | 보존됨 |
| `Date`, `RegExp`, `BigInt`, `Map`, `Set` | 같은 타입으로 복제됨 |
| `ArrayBuffer`, `SharedArrayBuffer`, 타입 배열 | 복제됨(공유 버퍼는 메모리를 공유) |
| 함수 | `DataCloneError` |
| 클래스 인스턴스 | 일반 객체로 복제됨. 프로토타입, 접근자, 비열거 프로퍼티, private 필드 소실 |
| `Buffer` | 받는 쪽에서 `Uint8Array` |
| `URL` 같은 일부 내장 객체 | `DataCloneError` |

```js
class Foo {
  #a = 1;
  c = 3;
  get d() { return this.#a + 3; }
}
port2.postMessage(new Foo());
// 받는 쪽: { c: 3 }
port2.postMessage({ f() {} });
// DataCloneError
```

- 네이티브(C++) 객체는 `CryptoKey`, `FileHandle`, `Histogram`, `KeyObject`, `MessagePort`, `net.BlockList`, `net.SocketAddress`, `X509Certificate`와, `transferList`에 넣은 TCP `net.Server`·`net.Socket`만 보낼 수 있습니다.
- 복제는 객체 크기에 비례하는 비용이 듭니다. 큰 데이터를 자주 보내면 복사 시간이 계산 시간을 넘을 수 있습니다.
- 클래스 인스턴스는 보내기 전에 일반 객체로 바꾸고, 받은 뒤 필요하면 다시 클래스로 만듭니다.

**흔한 실수:** 메서드나 콜백이 든 객체를 `workerData`나 `postMessage`로 넘기는 것입니다. 함수는 복제되지 않습니다(중급 27편). 함수 자체가 아니라 워커 파일에 있는 함수의 이름이나 인수 데이터를 보냅니다.

## transferList

`transferList`는 복사하지 않고 소유권을 넘길 객체를 `postMessage`의 두 번째 인수로 나열하는 배열입니다. 전송된 객체는 보낸 쪽에서 쓸 수 없게 됩니다.

```js
const ab = new ArrayBuffer(8);
port2.postMessage(ab, [ab]);
console.log(ab.byteLength); // 0 (보낸 쪽에서 분리됨)
console.log(ab.detached);   // true
```

- 전송할 수 있는 것: `ArrayBuffer`, `MessagePort`, `FileHandle`, TCP `net.Server`·`net.Socket`, v26 문서 기준 `net.BoundSocket`. 목록에 없는 객체는 복제됩니다.
- `transferList`에 넣지 않은 `ArrayBuffer`는 복사됩니다.
- `SharedArrayBuffer`는 `transferList`에 넣을 수 없습니다. 어느 쪽이든 같은 메모리를 가리킵니다.
- 로컬 측정(Node.js 24): 256 MiB `ArrayBuffer`의 `postMessage`가 복제에서 약 79ms였고, 전송에서는 사실상 0ms였습니다.

타입 배열과 `Buffer`는 `ArrayBuffer` 위의 뷰라서 주의가 필요합니다.

- 한 `ArrayBuffer`를 전송하면 같은 버퍼를 보는 모든 타입 배열과 `Buffer`가 쓸 수 없게 됩니다.
- `Buffer.from()`이나 `Buffer.allocUnsafe()`로 만든 작은 `Buffer`는 내부 풀을 쓰는 경우가 있어 전송할 수 없습니다(기초 19편). 로컬에서 `Buffer.from('hi')`의 `buffer`를 `transferList`에 넣으니 `DataCloneError`가 발생했습니다. 풀 전체를 복사해 보내는 상황도 문서가 경고합니다.
- 전송하려는 `Buffer`는 `Buffer.alloc()`이나 `Buffer.allocUnsafeSlow()`로 만듭니다. 반대로 전송하면 안 되는 `ArrayBuffer`는 `markAsUntransferable()`로 표시할 수 있습니다.

## MessageChannel

`MessageChannel`은 서로 연결된 `MessagePort` 두 개(`port1`, `port2`)를 만드는 클래스로, 양방향 비동기 통신 채널을 이룹니다. 한쪽에서 보낸 메시지는 반대쪽 포트에서 받습니다.

```js
import { MessageChannel } from 'node:worker_threads';

const { port1, port2 } = new MessageChannel();
port1.on('message', (msg) => console.log('received', msg));
port2.postMessage({ foo: 'bar' });
// received { foo: 'bar' }
```

워커와 기본으로 연결된 채널(`worker.postMessage`)은 전역 채널 하나뿐입니다. 문서는 관심사를 나누기 위해 전용 채널을 만들어 포트 한쪽을 워커에 전송하는 방식을 권합니다.

```js
// 부모
const { port1, port2 } = new MessageChannel();
worker.postMessage({ port: port2 }, [port2]);
port1.on('message', (msg) => {
  console.log(msg); // from worker
});

// 워커
parentPort.once('message', ({ port }) => {
  port.postMessage('from worker');
});
```

- 포트는 `transferList`에 넣어 전송해야 합니다. 전송하면 보낸 쪽에서는 못 씁니다.
- 한쪽이 `port.close()`를 호출하면 양쪽 포트에서 `'close'` 이벤트가 발생하고 더는 보낼 수 없습니다.
- `'message'` 리스너를 붙이면 포트가 이벤트 루프를 붙잡고, 리스너를 모두 떼면 풀립니다. `port.ref()`, `port.unref()`로 직접 정할 수도 있습니다.
- `receiveMessageOnPort(port)`는 이벤트 없이 큐에서 메시지 하나를 동기로 꺼냅니다. 없으면 `undefined`입니다.
- 두 워커 사이에 직접 채널을 만들 때도 같은 방식으로 포트를 한쪽씩 전송합니다.
- `MessagePort`는 `EventTarget`을 상속합니다(v14.7.0부터). 브라우저의 `MessagePort`와 같은 규격입니다.

## CPU 작업을 워커로

CPU 바운드 작업은 계산하는 동안 이벤트 루프를 점유하는 작업입니다. 메인 스레드에서 오래 돌리면 다른 요청과 타이머가 모두 멈춥니다(기초 01편, 기초 03편). 워커로 옮기면 메인 이벤트 루프가 계속 돕니다.

```js
function runInWorker(n) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(workerUrl, { workerData: n });
    worker.once('message', resolve);
    worker.once('error', reject);
    worker.once('exit', (code) => {
      if (code !== 0) reject(new Error(`exit ${code}`));
    });
  });
}
```

- 이 형태는 문서의 예제와 같습니다. `error`는 워커의 예외, `exit`의 0이 아닌 코드는 비정상 종료를 알립니다.
- 워커 파일은 `workerData`로 입력을 받아 계산하고 `parentPort.postMessage(결과)`를 보낸 뒤 끝납니다.
- 실측(Node.js 24, `fib(38)`을 10ms 타이머와 함께 실행): 메인 스레드에서 계산하면 336ms 동안 타이머가 0번 실행되었고, 워커에서 계산하면 364ms 동안 24번 실행되었습니다. 계산 시간은 비슷하고 달라지는 것은 이벤트 루프가 막히는지 여부입니다.
- 코어 여러 개를 쓰려면 작업을 쪼개 워커 여러 개에 나눕니다. 개수는 `os.availableParallelism()`을 기준으로 잡습니다(중급 22편).
- 대상 작업의 예: 큰 데이터 파싱·집계, 순수 JavaScript로 짠 압축·해싱, 무거운 정렬과 수치 계산. 내장 `fs`, `zlib`, `crypto`의 비동기 API 일부는 이미 libuv 스레드 풀에서 실행되므로 워커가 필요 없는 경우가 많습니다(06편).

## 워커는 I/O 마법이 아님

문서는 워커가 I/O 집약 작업에는 큰 도움이 되지 않는다고 적습니다. Node.js의 내장 비동기 I/O가 워커로 만든 것보다 효율적이기 때문입니다.

- 네트워크·DB·파일 I/O는 이미 비동기로 처리되어 기다리는 동안 이벤트 루프를 막지 않습니다. 이것을 워커로 옮기면 스레드 생성, 메시지 복제, 결과 전달 비용만 더해집니다.
- 워커로 옮겨서 빨라지는 것은 이벤트 루프를 점유하는 JavaScript 계산입니다. 대기 시간이 긴 I/O의 속도는 변하지 않습니다.
- 워커의 `stdout`·`stderr` 출력은 메인 스레드로 메시지를 보내 처리됩니다. 메인 스레드가 동기 코드로 막혀 있으면 워커의 `console.log` 출력도 막힙니다.
- 워커마다 자기 메모리와 V8 인스턴스를 쓰므로 워커를 많이 만들수록 메모리가 늡니다.

| 작업 | 선택 |
|------|------|
| DB 쿼리, HTTP 호출, 파일 읽기 | 비동기 API 그대로 |
| 수백 ms 이상 걸리는 JS 계산 | 워커 |
| 여러 요청을 병렬로 처리하는 서버 확장 | 클러스터 또는 인스턴스 추가(03편) |
| 외부 프로그램 실행 | 자식 프로세스(01편) |

**흔한 실수:** 성능을 올리려고 요청 처리 전체를 워커로 옮기는 것입니다. I/O 대기는 줄지 않고 복제 비용과 메모리만 늘어납니다. 먼저 어디가 느린지 측정합니다(04편).

## SharedArrayBuffer 개념

`SharedArrayBuffer`는 여러 스레드가 같은 메모리 블록을 가리킬 수 있는 버퍼입니다. `ArrayBuffer`와 비슷하지만 전송이 아니라 공유합니다.

- `postMessage`나 `workerData`로 보내면 받는 쪽에 새 `SharedArrayBuffer` 객체가 만들어지고, 그 객체들은 같은 데이터 블록을 참조합니다. 한쪽의 쓰기는 다른 쪽에서 곧 보이게 됩니다.
- 복제도 전송도 아니므로 큰 데이터를 옮기는 비용이 없습니다. `transferList`에는 넣을 수 없습니다.
- 버퍼 자체는 바이트 덩어리라서, 읽고 쓰려면 `Int32Array` 같은 타입 배열 뷰를 씌웁니다.
- 브라우저에서는 `SharedArrayBuffer`를 쓰려면 교차 출처 격리(cross-origin isolation) 헤더가 필요하지만, 이 제약은 브라우저 환경의 것이고 위 로컬 실험은 Node.js에서 아무 설정 없이 동작했습니다.
- 공유하는 순간 데이터 경합(race condition)이 생깁니다. 일반 읽기·쓰기는 스레드 사이에서 순서나 원자성을 보장하지 않습니다.

```js
// 워커 4개가 각각 100000번 증가시킨 결과
view[0]++;                // 일반 증가: 159097 (실행마다 다름)
Atomics.add(view, 1, 1);  // 원자적 증가: 400000
```

위 결과는 4개 워커가 공유 버퍼 위의 `Int32Array`에서 같은 칸을 각각 100000번 증가시킨 로컬 실험입니다(`view[0]`은 일반 증가용, `view[1]`은 `Atomics` 증가용 칸). 일반 증가는 읽기와 쓰기 사이에 다른 스레드가 끼어들어 갱신이 사라졌고 값은 실행마다 달랐습니다.

## Atomics

`Atomics`는 공유 메모리에서 읽기·수정·쓰기를 쪼개지지 않는 한 단계로 실행하는 정적 메서드 모음입니다. 생성자가 아니고 `Math`처럼 정적 메서드만 가집니다.

| 메서드 | 하는 일 |
|--------|---------|
| `Atomics.add`, `sub`, `and`, `or`, `xor` | 값을 원자적으로 계산해 저장하고 이전 값을 반환 |
| `Atomics.load`, `store` | 원자적으로 읽기·쓰기 |
| `Atomics.exchange` | 값을 저장하고 이전 값을 반환 |
| `Atomics.compareExchange` | 현재 값이 기대 값과 같을 때만 저장 |
| `Atomics.wait` | 값이 기대 값과 같으면 잠들어 `notify`나 시간 초과를 기다림 |
| `Atomics.waitAsync` | 막지 않는 비동기 버전 |
| `Atomics.notify` | 같은 위치에서 기다리는 스레드를 깨우고 깨운 수를 반환 |

```js
// 워커
const flag = new Int32Array(workerData); // 공유 버퍼
console.log(Atomics.wait(flag, 0, 0)); // 깨어난 뒤: ok

// 메인
Atomics.store(flag, 0, 1);
Atomics.notify(flag, 0); // 1 (깨운 스레드 수)
```

- `wait`와 `notify`는 `Int32Array`(또는 `BigInt64Array`)가 공유 버퍼를 볼 때만 동작합니다. 반환값은 `'ok'`, `'not-equal'`, `'timed-out'` 중 하나입니다.
- `'ok'`는 값이 바뀌었다는 뜻이 아니라 `notify`로 깨어났다는 뜻입니다. 깨어난 뒤 값을 다시 확인합니다.
- `wait`는 스레드를 막습니다. MDN은 브라우저의 메인 스레드에서 쓸 수 없다고 설명하지만 Node.js 메인 스레드에서는 로컬 실험에서 실행되었습니다(타임아웃 50ms에서 `'timed-out'`). 서버의 메인 스레드에서 호출하면 이벤트 루프가 그 시간 동안 멈추므로 워커 안에서만 씁니다. 메인에서 기다려야 하면 `waitAsync`를 씁니다.
- 일반 데이터를 주고받는 용도로는 `postMessage`가 단순하고 안전합니다. 공유 메모리와 `Atomics`는 큰 배열을 여러 스레드가 갱신하거나 카운터·플래그처럼 작은 값을 공유할 때만 씁니다.

## 워커 풀(piscina)

워커 풀(worker pool)은 워커를 미리 만들어 두고 작업이 올 때마다 빈 워커에 배정해 재사용하는 구조입니다. 워커를 매번 만드는 비용을 없애고 동시에 도는 스레드 수를 제한합니다. piscina는 Node.js용 워커 풀 라이브러리입니다(`npm install piscina`). 저장소 README는 Node.js 24.x 이상을 대상으로 한다고 적습니다.

```js
// main.mjs
import { Piscina } from 'piscina';

const pool = new Piscina({
  filename: new URL('./worker.mjs', import.meta.url).href,
});
console.log(await pool.run({ n: 35 })); // 9227465
await pool.close();
```

```js
// worker.mjs
export default function fib({ n }) {
  const f = (k) => (k < 2 ? k : f(k - 1) + f(k - 2));
  return f(n);
}
```

- 워커 파일은 기본 export로 함수(또는 async 함수)를 내보냅니다. `pool.run(task)`의 `task`가 그 함수의 인수가 되고, 반환값이 프로미스의 결과가 됩니다. 함수가 던진 에러는 프로미스를 reject합니다.
- `filename`은 절대 경로나 `file://` URL이어야 합니다. 한 파일에서 이름 있는 함수 여러 개를 내보내고 `run(task, { name: 'add' })`로 고를 수 있습니다.
- 작업과 결과는 구조적 복제로 오갑니다. 반환값의 전송은 `Piscina.move(value)`로 감싸면 복제 대신 전송합니다. 입력 쪽 전송은 `run`의 `transferList` 옵션입니다.

주요 옵션은 다음과 같습니다.

| 옵션 | 의미 |
|------|------|
| `minThreads` | 항상 유지하는 스레드 수. 기본은 `os.availableParallelism()` |
| `maxThreads` | 최대 스레드 수. 기본은 `os.availableParallelism()`의 1.5배 |
| `idleTimeout` | 유휴 워커를 종료하기까지의 시간(ms). 기본은 즉시 종료. 반복적으로 재시작하는 비용이 있어 명시적으로 지정하면 성능에 도움이 됨 |
| `maxQueue` | 대기열에 쌓을 수 있는 작업 수. 기본은 제한 없음. `'auto'`는 `maxThreads`의 제곱 |
| `concurrentTasksPerWorker` | 한 스레드가 동시에 맡는 작업 수. 기본 1 |
| `resourceLimits` | `new Worker`의 `resourceLimits`와 같음 |
| `workerData` | 모든 워커에 복제되어 전달됨. `transferList`가 필요한 값은 안 됨 |

- `pool.run(task, { signal })`에 `AbortSignal`을 주면 작업을 취소할 수 있습니다. 이미 실행 중인 작업이면 해당 워커 스레드가 중단됩니다. 취소 가능한 작업은 스레드를 다른 작업과 공유하지 않습니다.
- `pool.close()`는 시작된 작업이 끝나길 기다린 뒤 모든 스레드를 종료하고, `pool.destroy()`는 작업을 즉시 중단하고 대기 중인 프로미스를 reject합니다.
- 풀은 앱 시작 시 한 번 만들어 재사용합니다. 요청마다 `new Piscina()`를 만들면 풀의 의미가 없습니다.
- 대기열 길이와 통계(`queueSize`, `completed`, `utilization`)를 노출하므로 풀이 포화되었는지 관찰할 수 있습니다.
- 코어 수보다 많은 스레드는 CPU 바운드 작업에서 처리량을 늘리지 못하므로 `maxThreads`를 코어 수 근처에서 시작합니다.
- 로컬 실험(Node.js 24, `maxThreads: 2`)에서 `fib` 35, 36, 37, 38 작업 네 개를 `Promise.all`로 보내 모두 정상 결과를 받았고 `pool.close()`로 종료되었습니다.

## workerData·resourceLimits

`workerData`는 워커를 만들 때 넘기는 초기 데이터이고, `resourceLimits`는 워커의 JS 엔진 메모리 한도입니다. 둘 다 `new Worker(filename, options)`의 옵션입니다.

```js
const worker = new Worker(import.meta.filename, {
  workerData: { limit: 5 },
  resourceLimits: { maxOldGenerationSizeMb: 16 },
});
// 워커 안: import { workerData } from 'node:worker_threads'
```

`workerData`는 다음 규칙을 따릅니다.

- 값은 구조적 복제로 복사되어 워커 안의 `workerData`로 노출됩니다. 복제할 수 없는 값(함수 등)이면 `new Worker()`에서 에러가 발생합니다.
- `MessagePort` 같은 전송 대상을 `workerData`에 넣으려면 `transferList` 옵션이 필요하고, 없으면 `ERR_MISSING_MESSAGE_PORT_IN_TRANSFER_LIST`가 발생합니다.
- 시작 시점에 한 번 전달하는 값입니다. 이후에 오가는 데이터는 `postMessage`입니다.
- 모든 새 워커가 받아야 하는 설정은 `setEnvironmentData(key, value)`로 두고 워커에서 `getEnvironmentData(key)`로 읽을 수 있습니다.

주요 `Worker` 옵션은 다음과 같습니다.

| 옵션 | 의미 |
|------|------|
| `workerData` | 시작 시 복제해 넘기는 데이터 |
| `env` | 워커의 초기 `process.env`. 기본은 부모의 복사본, `SHARE_ENV`면 공유 |
| `argv` | 워커의 `process.argv`에 덧붙일 인수 |
| `execArgv` | 워커에 줄 Node CLI 옵션. V8 옵션(`--max-old-space-size` 등)은 지원하지 않음 |
| `eval` | 첫 인수를 파일 경로가 아니라 코드 문자열로 해석 |
| `stdout`, `stderr` | `true`이면 부모의 stdout, stderr로 자동 연결하지 않음 |
| `resourceLimits` | JS 엔진 자원 한도 |
| `name` | 디버깅용 스레드 이름 |

`resourceLimits`의 필드는 다음과 같습니다.

| 필드 | 의미 |
|------|------|
| `maxOldGenerationSizeMb` | 메인 힙의 최대 크기(MB) |
| `maxYoungGenerationSizeMb` | 새로 만든 객체용 힙 공간의 최대 크기(MB) |
| `codeRangeSizeMb` | 생성된 코드를 위해 미리 확보하는 메모리 범위(MB) |
| `stackSizeMb` | 스레드의 기본 최대 스택 크기. 기본값 4. 너무 작으면 워커가 쓸 수 없게 됨 |

- 한도에 도달하면 해당 워커가 종료됩니다. 로컬 실험에서 `maxOldGenerationSizeMb: 16`인 워커가 배열을 계속 쌓자 `error` 이벤트로 `ERR_WORKER_OUT_OF_MEMORY`(Worker terminated due to reaching memory limit)가 오고 `exit` 코드는 1이었습니다. 메인 스레드는 영향을 받지 않았습니다.
- 한도는 JS 엔진에만 적용됩니다. `ArrayBuffer`를 포함한 외부 데이터에는 적용되지 않습니다. 시스템 전체가 메모리 부족이면 한도를 설정했어도 프로세스가 중단될 수 있습니다.
- 명령줄의 `--max-old-space-size`, `--max-semi-space-size`가 있으면 해당 필드 설정보다 우선합니다.
- 워커 안에서는 `resourceLimits`로, 부모에서는 `worker.resourceLimits`로 한도를 읽습니다.

**흔한 실수:** 한도를 지나치게 낮추는 것입니다. 특히 `stackSizeMb`가 작으면 쓸 수 없는 워커가 될 수 있습니다. 한도는 측정한 사용량에 여유를 두고 정합니다.

## 핵심 정리

- 워커 스레드는 같은 프로세스 안에서 JavaScript를 병렬 실행하는 스레드이며, CPU 바운드 JS 계산을 메인 이벤트 루프에서 떼어 내는 용도입니다. I/O는 내장 비동기 API가 더 효율적입니다.
- 메시지는 구조적 복제로 복사되어 함수, 프로토타입, 접근자, 일부 내장 객체가 사라지거나 에러가 되고, 큰 `ArrayBuffer`는 `transferList`로 복사 없이 넘기되 보낸 쪽에서는 쓸 수 없게 됩니다.
- `MessageChannel`로 전용 채널을 만들고 포트를 전송해 워커와 통신합니다.
- `SharedArrayBuffer`는 복사 없이 메모리를 공유하지만 경합이 생기므로 `Atomics`로 갱신하고, `wait`는 워커 안에서만 씁니다.
- 워커는 호출마다 만들지 않고 piscina 같은 풀을 한 번 만들어 재사용합니다.
- `workerData`는 시작 시 복제되는 초기 데이터이고, `resourceLimits`는 JS 힙·스택 한도로, 초과하면 그 워커만 `ERR_WORKER_OUT_OF_MEMORY`로 종료됩니다.

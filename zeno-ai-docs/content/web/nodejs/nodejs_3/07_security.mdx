## 입력 검증

입력 검증은 서버가 외부에서 받은 값을 사용하기 전에 형식과 의미가 기대에 맞는지 확인하고, 맞지 않으면 거부하는 것입니다. 본문, 쿼리 문자열, 경로 매개변수, 헤더, 쿠키, 파일 이름이 모두 외부 입력입니다.

OWASP 입력 검증 치트 시트의 원칙은 다음과 같습니다.

- 구문(syntax)과 의미(semantics)를 모두 검증합니다. 날짜 형식이 맞아도 종료일이 시작일보다 앞서면 의미가 틀립니다.
- 허용 목록(allowlist)으로 검증합니다. 위험한 문자열을 모두 알아내 막으려 하지 않고, 허용하는 형식을 정해 나머지를 거부합니다.
- 서버에서 검증합니다. 브라우저의 검증은 우회할 수 있으므로 즉시 피드백용입니다.
- 가장 이른 지점에서 검증합니다. 요청 크기 제한은 본문을 버퍼링하거나 파싱하기 전에 걸어야 합니다.
- 파일 이름과 Content-Type은 클라이언트가 보낸 신뢰할 수 없는 정보입니다. 확장자가 허용 목록에 있다는 사실만으로 안전한 내용이라고 볼 수 없습니다.

```js
const SORTABLE = new Set(['createdAt', 'name'])

function parsePage(query) {
  const page = Number(query.page ?? 1)
  const sort = query.sort ?? 'createdAt'
  if (!Number.isInteger(page) || page < 1) return null
  if (!SORTABLE.has(sort)) return null // 허용 목록
  return { page, sort }
}
```

- 검증 결과는 정해진 형태의 값으로 바꿔서 이후 코드에 넘깁니다. 원본 문자열을 그대로 쓰는 코드가 남으면 검증이 의미 없어집니다.
- 스키마 기반 검증이 규칙을 한곳에 모읍니다. Fastify는 내장 검증기로 Ajv(JSON Schema)를 쓰고 설정을 바꿀 수 있습니다. 검증 라이브러리의 선택은 프레임워크에 맞춥니다.
- 검증 실패는 400번대 상태 코드로 응답하고 상세한 내부 정보를 응답에 싣지 않습니다.

**흔한 실수:** 프런트엔드 폼 검증만 믿는 것입니다. API는 curl로도 호출되므로 서버 검증이 없으면 아무 값이나 들어옵니다.

## 경로 탈출

경로 탈출(path traversal)은 사용자가 준 파일 이름에 `../`나 절대 경로를 넣어 허용된 폴더 밖의 파일을 읽거나 쓰는 공격입니다.

```js
import path from 'node:path'

const base = path.resolve('/srv/uploads')
path.join(base, '../etc/passwd') // /srv/etc/passwd (밖으로 나감)
path.resolve(base, '/etc/passwd') // /etc/passwd (절대 경로가 이김)
```

`path.join`은 `..`를 정리할 뿐 폴더 안에 머무는지는 확인하지 않습니다. 정리된 최종 경로가 기준 폴더 안인지를 직접 검사합니다.

```js
function safePath(name) {
  const full = path.resolve(base, name)
  const inside = full.startsWith(base + path.sep)
  if (!inside) throw new Error('403')
  return full
}
safePath('a.png')            // /srv/uploads/a.png
safePath('../etc/passwd')    // Error 403
safePath('../uploads-evil/x') // Error 403
```

- 기준 경로 뒤에 구분자(`path.sep`)를 붙여 비교해야 `/srv/uploads-evil` 같은 이름이 앞부분만 같다는 이유로 통과하지 않습니다.
- 파일 이름을 URL에서 받으면 디코딩이 끝난 값으로 검사합니다. 검사한 값과 실제로 여는 값이 같아야 합니다.
- 경로에 널 문자가 있으면 Node.js가 `ERR_INVALID_ARG_VALUE`를 던집니다.
- 이 방법은 심볼릭 링크를 풀지 않습니다. 링크가 허용 폴더 밖을 가리킬 수 있는 환경이면 `fs.realpath` 결과로 다시 검사합니다.
- Express의 `res.sendFile()`은 `root` 옵션을 주면 상대 경로가 그 폴더 안으로 풀리는지 직접 검증합니다. `root` 없이 사용자 입력으로 만든 절대 경로를 넘기는 것은 위험하다고 Express 문서가 경고합니다.

```js
res.sendFile(req.params.name, {
  root: '/srv/uploads', // 이 폴더 밖이면 오류
  dotfiles: 'deny',
}, next)
```

**흔한 실수:** `name.replace('../', '')`처럼 문자열을 지우는 것입니다. `....//`가 지우고 나면 `../`가 되는 식으로 우회됩니다. 지우지 말고 해석한 결과를 검사합니다.

## 명령 주입

명령 주입(command injection)은 사용자 입력이 쉘 명령 문자열에 섞여 입력 속 쉘 문법이 실행되는 공격입니다. `child_process.exec()`가 문자열을 쉘에 넘기기 때문에 생깁니다(자세히는 01편).

```js
import { exec, execFile } from 'node:child_process'

const name = 'x & echo INJECTED' // 사용자 입력
exec(`echo hello ${name}`, cb)
// ❌ 쉘이 & 뒤를 별도 명령으로 실행: INJECTED 출력
execFile('node', ['-p', 'process.argv[1]', name], cb)
// ✅ name이 통째로 인자 하나: x & echo INJECTED
```

- 쉘을 켜지 않는 `execFile()`·`spawn()`에 인자를 배열로 넘기면 입력 속 `& ; |` 같은 문자가 쉘에서 해석되지 않고 인자 문자열 그대로 전달됩니다.
- 실행할 프로그램 이름 자체를 사용자가 정하게 하지 않습니다. 허용 목록에서 고릅니다.
- 인자는 인자대로 위험할 수 있습니다. 대상 프로그램이 `-`로 시작하는 값을 옵션으로 읽으면 의도하지 않은 옵션이 켜집니다. 값은 검증하고, 프로그램이 지원하면 옵션 끝 표시(`--`) 뒤에 둡니다.
- 쉘 기능(파이프, 리다이렉션)이 꼭 필요하면 명령을 고정 문자열로 두고 사용자 값은 환경변수나 인자로만 넘깁니다.
- OWASP Node.js 치트 시트도 `eval()`을 피하고 `child_process.exec`는 정제된 입력일 때만 신중히 쓰라고 합니다.

**흔한 실수:** 입력에서 `;` 같은 위험 문자를 걸러내는 방식으로 막으려는 것입니다. 쉘마다 특수 문자가 달라서(`&`, `|`, `$()`, 줄 바꿈 등) 허용 목록 방식이 아니면 빈틈이 생깁니다.

## SQL 인젝션과 파라미터 바인딩

SQL 인젝션은 사용자 입력이 SQL 문장 구조를 바꾸도록 쿼리 문자열에 이어 붙여지는 공격입니다. 방어는 쿼리 문장과 값을 분리하는 파라미터 바인딩(parameter binding)입니다.

```js
const id = req.query.id // "1 OR 1=1" 같은 값이 올 수 있음

// ❌ 문자열 결합
await client.query(`SELECT * FROM users WHERE id = ${id}`)

// ✅ 파라미터 바인딩
await client.query(
  'SELECT * FROM users WHERE id = $1', [id])
```

node-postgres 문서도 쿼리 텍스트에 매개변수를 직접 이어 붙이는 것을 SQL 인젝션 취약점의 원인으로 지목합니다. 값은 `$1`, `$2` 자리표시자로 넣고 배열로 따로 전달합니다.

- 바인딩한 값은 SQL 문법이 아니라 데이터로만 쓰입니다.
- PostgreSQL은 식별자(테이블명, 컬럼명)에 매개변수를 쓸 수 없습니다. 정렬 컬럼처럼 동적인 식별자는 허용 목록으로 고르고, 이스케이프가 필요하면 전용 도구를 씁니다.
- ORM은 기본 메서드에서 바인딩을 해 주지만 원시 쿼리 기능에 문자열을 이어 붙이면 똑같이 뚫립니다(드라이버와 ORM은 중급 17편).
- 입력을 숫자로 바꾸거나 형식을 검증하는 것은 보조 수단입니다. 바인딩이 우선입니다.
- 데이터베이스 계정은 필요한 권한만 줍니다. 앱 계정에 관리자 권한이 있으면 주입이 성공했을 때 피해가 커집니다.

**흔한 실수:** 템플릿 문자열로 쿼리를 만들면서 따옴표를 이스케이프했으니 안전하다고 여기는 것입니다. 이스케이프 규칙은 DB와 설정마다 달라서 바인딩을 쓰는 것이 확실합니다.

## 프로토타입 오염

프로토타입 오염(prototype pollution)은 입력으로 받은 객체를 재귀 병합하다가 `__proto__` 같은 키를 통해 `Object.prototype`에 속성이 심어지는 공격입니다. 이후 만드는 모든 객체가 그 속성을 상속합니다.

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object' && source[key]) {
      target[key] ??= {}
      merge(target[key], source[key])
    } else target[key] = source[key]
  }
}
merge({}, JSON.parse('{"__proto__":{"admin":true}}'))
console.log({}.admin) // true (모든 객체가 오염됨)
```

- `JSON.parse`는 `__proto__`를 일반 자기 프로퍼티로 만듭니다. 그 뒤 병합 함수가 `target['__proto__']`를 읽으면 `Object.prototype`에 닿고, 그 안에 값을 씁니다.
- 오염된 속성은 권한 검사(`user.admin`)나 옵션 객체의 기본값 조회에 그대로 나타납니다. OWASP는 권한 상승과 원격 코드 실행까지 이어질 수 있다고 설명합니다.
- 객체 스프레드와 `Object.assign({}, input)`는 이 방식으로 `Object.prototype`을 바꾸지 못합니다. `Object.assign`은 대상의 `__proto__` 설정자를 호출해 그 객체의 프로토타입만 바꿉니다. 위험은 직접 만든 재귀 병합과 오래된 병합 라이브러리에 있습니다.

| 방어 | 방법 |
|------|------|
| 입력 구조 검증 | 스키마로 허용한 키만 통과. 모르는 키는 거부 |
| 위험한 키 차단 | 병합 함수에서 `__proto__`, `constructor`, `prototype` 키를 건너뜀 |
| 프로토타입 없는 객체 | `Object.create(null)`로 만든 객체는 상속이 없음 |
| 다른 자료구조 | 키가 임의인 데이터는 `Map`이나 `Set`을 사용 |
| 프로토타입 동결 | `Object.freeze(Object.prototype)`. 내장 프로토타입을 고치는 라이브러리가 깨질 수 있음 |
| Node.js 플래그 | `--disable-proto=delete`로 `__proto__` 접근자를 제거. 심층 방어 수단 |

- `--disable-proto`의 `throw` 모드는 접근 시 `ERR_PROTO_ACCESS`를 던집니다. 이 플래그는 `Object.prototype.__proto__` 접근자만 막으므로 `constructor.prototype` 경로는 별도로 막아야 합니다.
- 병합·깊은 복사·경로 기반 설정(`set(obj, 'a.b.c', v)`) 라이브러리는 의존성 점검 대상입니다.

**흔한 실수:** 일반 객체를 키-값 저장소로 쓰는 것입니다. 키가 사용자 입력이면 `Map`을 씁니다.

## ReDoS 개념

ReDoS(Regular expression Denial of Service)는 입력 길이에 비해 매칭 시간이 지수적으로 늘어나는 정규식에 악의적 입력을 넣어 이벤트 루프를 장시간 막는 공격입니다. 정규식 매칭은 이벤트 루프 스레드에서 실행되므로 한 요청이 전체를 멈춥니다(자세히는 04편).

```js
const re = /^(a+)+$/
re.test('a'.repeat(28) + 'b') // 약 1.2초 (이 머신의 실측)
// 길이 20은 약 40ms, 24는 약 70ms. 4 늘리면 약 18배
```

- 일치하지 않는 입력에서 엔진이 `a+`를 나누는 모든 방법을 되짚어 보느라(백트래킹) 시간이 폭증합니다. 글자 하나를 더하면 시간이 몇 배로 늘어납니다.
- Node.js 문서의 점검 규칙 넷은 다음과 같습니다.
  - `(a+)*` 같은 중첩 수량자를 피합니다.
  - `(a|a)*`처럼 겹치는 선택지를 피합니다.
  - 역참조(`\1`)를 피합니다. 어떤 엔진도 선형 시간을 보장하지 않습니다.
  - 단순한 문자열 검색은 `indexOf`로 합니다. 최악의 경우에도 입력 길이에 비례합니다.
- 입력 길이를 먼저 제한하면 최악의 비용도 제한됩니다. 사용자 입력에 적용하는 정규식 앞에 길이 검사를 둡니다.
- 위험 패턴을 찾는 도구(safe-regex, rxxr2)와 백트래킹이 없는 RE2 엔진 바인딩(node-re2, 문법이 완전히 호환되지는 않음)이 Node.js 문서에 소개돼 있습니다.
- 사용자가 정규식 자체를 입력하게 두는 기능은 만들지 않습니다.

**흔한 실수:** 인터넷에서 복사한 이메일·URL 정규식을 그대로 쓰는 것입니다. 복잡한 형식은 검증된 라이브러리를 쓰거나 길이를 제한하고 단순하게 확인합니다.

## 본문 크기 제한

본문 크기 제한은 요청 본문이 정한 바이트를 넘으면 읽기를 멈추고 413으로 거절하는 것입니다. 제한이 없으면 큰 본문 하나가 메모리와 파싱 시간을 소모해 서비스 거부로 이어집니다.

- `http` 모듈은 본문을 스트림으로 넘길 뿐 본문 크기 제한 옵션을 제공하지 않습니다(`http` 문서에 해당 옵션이 없습니다). 제한은 프레임워크나 직접 작성한 코드가 겁니다.
- Express의 `express.json()`은 body-parser 기반이고 `limit` 기본값이 `'100kb'`입니다. 넘으면 상태 코드 413, 오류 종류 `entity.too.large`를 냅니다.
- Fastify의 `bodyLimit` 기본값은 1MiB(1048576바이트)이고 넘으면 413을 응답합니다.
- 파일 업로드 같이 큰 본문이 필요한 경로만 한도를 따로 올립니다. 전역 한도를 키우지 않습니다.
- Content-Type별로 한도를 다르게 두라고 OWASP가 권합니다. JSON은 작게, 업로드는 크게 둡니다.

```js
app.use(express.json({ limit: '100kb' }))
app.post('/upload', express.raw({ limit: '10mb' }), handler)
```

프레임워크 없이 직접 막으려면 읽은 바이트를 세다가 한도를 넘으면 중단합니다.

```js
let size = 0
for await (const chunk of req) {
  size += chunk.length
  if (size > 1024) {
    res.writeHead(413).end(); req.destroy(); break
  }
}
// 5000바이트 본문 POST: 413 (실측)
```

- `Content-Length` 헤더 값만 믿으면 안 됩니다. 청크 전송에서는 길이가 없고 거짓말도 가능하니 실제로 읽은 바이트를 셉니다.
- 압축된 본문은 풀린 크기가 훨씬 클 수 있습니다. 풀린 뒤의 크기에도 한도를 둡니다.
- 앞단의 리버스 프록시(Nginx, ALB 등)에서도 최대 본문 크기를 설정할 수 있습니다. 앱과 프록시 양쪽에 두면 앱까지 오기 전에 막습니다.
- JSON의 중첩 깊이처럼 크기 말고도 파서 한도가 있습니다. OWASP는 파서의 최대 중첩 깊이 같은 한도를 설정하라고 권합니다.

**흔한 실수:** 한도를 아주 크게(`'50mb'`) 열어 두는 것입니다. 필요한 만큼으로 라우트별로 정합니다.

## 헤더 크기 제한

헤더 크기 제한은 요청 헤더 전체 길이의 상한입니다. Node.js `http` 서버의 기본값은 16KiB(16384바이트)이고 넘으면 431(Request Header Fields Too Large)로 응답합니다.

```js
const opts = { maxHeaderSize: 1024 }
const server = http.createServer(opts, handler)
// 2000바이트 헤더를 보내면 431 (실측)
```

- 서버 단위로는 `maxHeaderSize` 옵션으로, 프로세스 전체로는 `--max-http-header-size` 플래그로 바꿉니다.
- 쿠키가 커지면 헤더 한도에 걸립니다. 세션 데이터를 쿠키에 쌓지 않고 서버에 저장합니다.
- 헤더를 천천히 보내 연결을 붙잡는 공격은 시간으로 막습니다. `server.headersTimeout`은 헤더를 전부 받기까지의 제한으로 기본값이 `min(requestTimeout, 60000)`ms이고 초과하면 408을 응답합니다. `server.requestTimeout`은 요청 전체의 제한으로 기본 300000ms(5분)입니다.
- Node.js 문서는 앞단에 리버스 프록시가 없는 배포에서는 `headersTimeout`을 0이 아닌 값으로 두라고 권합니다.
- 헤더 개수 상한은 `server.maxHeadersCount`입니다.

**흔한 실수:** 한도에 걸려 431이 난다고 한도부터 올리는 것입니다. 헤더가 왜 커졌는지(큰 쿠키, 중복 헤더) 먼저 봅니다.

## Rate limit 개념

Rate limit(요청 속도 제한)은 같은 클라이언트가 정해진 시간 안에 보낼 수 있는 요청 수를 제한하고, 넘으면 429(Too Many Requests)로 응답하는 방어입니다. 로그인 시도 무차별 대입, 비밀번호 재설정 남용, 비싼 API 호출을 막는 데 씁니다.

```js
import rateLimit from 'express-rate-limit'

app.use('/login', rateLimit({
  windowMs: 15 * 60 * 1000, // 15분
  limit: 10,                // 창당 10회
}))
```

- express-rate-limit은 공개 API나 비밀번호 재설정 같은 엔드포인트의 반복 요청을 제한하는 Express 미들웨어입니다. 기본 저장소는 메모리입니다.
- 서버가 여러 대이면 메모리 저장소로는 인스턴스별로 따로 세므로 실제 허용량이 설정값의 인스턴스 수 배까지 늘어납니다. 여러 서버이거나 재시작 뒤에도 상태를 유지하려면 외부 저장소(Redis 등)를 씁니다.
- 제한의 기준은 보통 클라이언트 IP입니다. 프록시 뒤에서는 Express의 `trust proxy` 설정이 꺼져 있으면 `req.ip`가 프록시 주소가 되어 모든 사용자가 한 묶음으로 세어집니다. 켤 때는 마지막으로 신뢰하는 프록시가 `X-Forwarded-For` 헤더를 덮어쓰는지 확인합니다. 그렇지 않으면 클라이언트가 값을 위조합니다.
- 로그인은 IP 외에 계정 기준 제한과 잠금도 함께 둡니다.
- 제한 알고리즘(고정 창, 슬라이딩 창, 토큰 버킷)은 13편에서 다룹니다. 로드 밸런서·API 게이트웨이 같은 앞단에서도 제한할 수 있습니다.

**흔한 실수:** 인증 전 엔드포인트에만 제한을 걸고 비싼 인증 후 API는 놔두는 것입니다. 비용이 큰 엔드포인트마다 제한을 둡니다.

## 보안 헤더 개념

보안 헤더는 서버가 응답에 붙여 브라우저의 동작을 제한하는 HTTP 헤더입니다. 서버가 만든 응답을 브라우저가 어떻게 다룰지 지시해 XSS, 클릭재킹, MIME 스니핑 같은 공격을 줄입니다.

| 헤더 | 하는 일 |
|------|---------|
| `Content-Security-Policy` | 문서가 불러올 수 있는 리소스(특히 스크립트)를 제한. 주로 XSS 방어 |
| `Strict-Transport-Security` | 이 호스트는 HTTPS로만 접속하도록 브라우저에 기억시킴(`max-age`는 초 단위) |
| `X-Content-Type-Options` | `nosniff`이면 선언한 Content-Type을 바꾸지 않고 따름 |
| `X-Frame-Options` | 다른 사이트의 프레임 안에 페이지가 열리는 것(클릭재킹)을 막음 |
| `Referrer-Policy` | 다른 곳으로 이동할 때 보내는 출처 정보의 양을 제어 |

```http
Content-Security-Policy: default-src 'self'
Strict-Transport-Security: max-age=31536000
X-Content-Type-Options: nosniff
```

- 첫 줄은 같은 출처의 리소스만 로드하라는 뜻입니다.
- 헤더는 서버 코드가 아니라 브라우저가 강제합니다. API만 제공하는 서버라도 HTML을 반환하는 경로가 있으면 의미가 있습니다.
- HSTS의 `max-age`를 길게 잡으면 HTTPS가 깨졌을 때 되돌리기 어렵습니다. HTTPS가 안정된 뒤에 늘립니다.
- CSP는 정책이 너무 엄격하면 정상 스크립트도 막습니다. 먼저 보고 전용 모드로 위반을 관찰한 뒤 적용하는 방식이 안전합니다.
- 응답 헤더로 서버 정보를 알리지 않습니다. Express는 기본으로 `X-Powered-By`를 보냅니다(helmet이 제거).

**흔한 실수:** 보안 헤더를 한 번 붙이면 끝이라고 생각하는 것입니다. 정책이 사이트의 실제 리소스와 맞는지 주기적으로 확인합니다.

## helmet

helmet은 Express 같은 Node.js 앱의 응답에 보안 헤더를 한꺼번에 설정하는 미들웨어입니다.

```js
import express from 'express'
import helmet from 'helmet'

const app = express()
app.use(helmet())
```

호출 하나로 기본 헤더가 설정됩니다. 공식 사이트가 소개하는 기본값은 다음과 같습니다.

| 헤더 | 하는 일 |
|------|---------|
| `Content-Security-Policy` | 리소스 로딩 제한 |
| `Strict-Transport-Security` | HTTPS 강제 |
| `X-Content-Type-Options` | MIME 스니핑 방지 |
| `X-Frame-Options` | 클릭재킹 방지 |
| `Referrer-Policy` | 기본값 `no-referrer` |
| `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `Origin-Agent-Cluster` | 프로세스·출처 격리 |
| `X-DNS-Prefetch-Control`, `X-Download-Options`, `X-Permitted-Cross-Domain-Policies` | 레거시 위험 완화 |
| `X-Powered-By` | 제거 |
| `X-XSS-Protection` | `0`으로 비활성화(역효과가 있는 레거시 헤더) |

- 각 헤더는 옵션으로 조정하거나 끌 수 있습니다. 기본 CSP가 서비스의 외부 스크립트나 이미지와 충돌하면 해당 지시문만 열어 줍니다.
- helmet은 응답 헤더만 다룹니다. 입력 검증, 인증, 인가는 대신해 주지 않습니다.
- Express 보안 모범 사례 문서도 helmet을 권하는 도구로 소개합니다. Fastify는 `@fastify/helmet` 플러그인을 씁니다.
- 리버스 프록시(Nginx 등)에서 같은 헤더를 이미 붙인다면 중복되지 않게 한쪽에서만 관리합니다.

**흔한 실수:** `app.use(helmet())`를 라우트 뒤에 두는 것입니다. 미들웨어는 선언 순서대로 실행되므로 라우트보다 앞에 둡니다.

## 디렉터리 리스팅 금지

디렉터리 리스팅(directory listing)은 폴더 경로로 접속했을 때 그 안의 파일 목록을 보여 주는 동작입니다. 백업, 설정 파일, 업로드 원본처럼 노출하려 하지 않은 파일이 드러나므로 켜지 않습니다.

- Express의 `express.static`(serve-static)은 폴더 요청에 `index.html`이 있으면 보내고 목록은 만들지 않습니다. 목록은 별도 미들웨어인 serve-index를 붙여야 생깁니다. 붙이지 않으면 됩니다.
- serve-static의 `dotfiles` 옵션 기본값은 `'ignore'`입니다. 점으로 시작하는 파일(`.env`, `.git`)을 없는 파일처럼 404로 응답합니다. 이 값을 `'allow'`로 바꾸지 않습니다.
- 정적 서버의 공개 폴더에는 공개할 파일만 둡니다. 프로젝트 루트(`.`)를 통째로 `express.static`에 지정하면 소스와 `package.json`, 락파일이 URL로 열립니다.
- `redirect` 옵션(기본 `true`)은 폴더 요청을 끝에 `/`가 붙은 주소로 보내는 것이고 목록과 무관합니다.
- Nginx 같은 웹 서버나 오브젝트 스토리지의 자동 목록 기능도 같은 이유로 꺼져 있는지 확인합니다.

```js
app.use(express.static('public', { dotfiles: 'deny' }))
// public 폴더만 공개. 점 파일은 403
```

**흔한 실수:** 업로드 폴더를 정적 경로로 공개해 둔 채 예측 가능한 이름으로 저장하는 것입니다. 이름이 추측되면 목록이 없어도 접근됩니다. 접근 권한 검사를 거치는 라우트로 내려 줍니다.

## 의존성 신뢰

의존성 신뢰 문제는 내 코드뿐 아니라 설치한 모든 패키지(간접 의존성 포함)의 코드가 서버 권한으로 실행된다는 점에서 나옵니다. Express 보안 문서는 앱의 보안이 가장 약한 의존성 수준이라고 설명합니다.

- 의존성 하나를 설치하면 그 패키지가 의존하는 수십–수백 개가 함께 들어옵니다. 어느 것이든 악성 코드나 취약점이 있으면 앱이 영향을 받습니다.
- 패키지는 설치 때 `preinstall`, `install`, `postinstall` 같은 스크립트를 실행할 수 있습니다. `ignore-scripts`를 `true`로 두면 npm이 `package.json`의 스크립트를 실행하지 않습니다. 기본값은 `false`입니다. `npm start`, `npm test`, `npm run`처럼 명시한 스크립트는 `ignore-scripts`여도 실행되지만 그 앞뒤의 pre·post 스크립트는 실행되지 않습니다.
- 정기적으로 `npm audit`을 실행해 알려진 취약점을 찾습니다. `audit-level` 설정으로 어느 심각도부터 실패(0이 아닌 종료 코드)로 볼지 정할 수 있어서 CI에 연결합니다.
- 새 의존성을 추가하기 전에 확인할 것: 정말 필요한가, 유지보수 중인가, 이름이 정확한가, 다운로드·사용 실적이 있는가, 대안으로 표준 라이브러리가 있는가.
- 쓰지 않는 의존성은 제거합니다. 공격 면이 줄어듭니다.
- 최신 Node.js는 `fetch`, 테스트 러너, `--watch`, `--env-file` 같은 기능을 내장합니다. 작은 편의 패키지는 내장 기능으로 대체할 수 있습니다(자세히는 15편).

```bash
npm audit --audit-level=high   # high 이상이면 비정상 종료
```

**흔한 실수:** `npm audit fix --force`를 읽지 않고 실행하는 것입니다. 메이저 버전이 올라가 호환성이 깨질 수 있어서 변경 내용을 보고 적용합니다.

## 락파일

락파일(`package-lock.json`)은 설치된 의존성 트리의 정확한 버전을 기록해 누가 어디서 설치해도 같은 트리가 나오도록 하는 파일입니다. 소스 저장소에 커밋하도록 만들어졌습니다.

- `package.json`의 `^1.2.0` 같은 범위는 설치할 때마다 새 버전을 받을 수 있습니다. 락파일이 있으면 기록된 버전을 설치합니다.
- 락파일의 `integrity` 필드에는 압축을 푼 패키지 파일의 `sha512`(오래된 것은 `sha1`) 해시가 들어 있습니다. 내려받은 내용이 기록과 다르면 설치가 실패하므로 같은 버전 이름으로 내용이 바뀌는 일을 감지합니다.
- 서버 배포와 CI에서는 `npm install`이 아니라 `npm ci`를 씁니다. `npm ci`는 `package-lock.json`이 반드시 있어야 하고, 기존 `node_modules`를 지우고 새로 설치하며, `package.json`이나 락파일을 절대 수정하지 않습니다. 락파일의 의존성이 `package.json`과 맞지 않으면 락파일을 고치지 않고 오류로 멈춥니다.
- 락파일을 `.gitignore`에 넣지 않습니다. 팀원과 배포 환경이 서로 다른 버전을 받아 재현할 수 없는 버그가 생깁니다.
- 락파일 변경은 코드 리뷰에서 봅니다. 의도하지 않은 의존성 추가나 레지스트리 주소 변경이 보이면 점검합니다.
- `save-exact` 설정을 켜면 `package.json`에 범위 대신 정확한 버전을 기록합니다.

```bash
npm ci   # 락파일 그대로 설치, 불일치하면 실패
```

**흔한 실수:** 배포 스크립트에서 `npm install`을 쓰는 것입니다. 그 사이 새 버전이 나오면 개발 때 테스트한 것과 다른 코드가 운영에 배포될 수 있습니다.

## 공급망 공격과 대응

공급망 공격(supply chain attack)은 앱이 아니라 앱이 의존하는 패키지, 빌드 도구, 배포 과정에 악성 코드를 심어 간접적으로 침투하는 공격입니다. OWASP Top 10:2025는 이를 A03 "소프트웨어 공급망 실패"(Software Supply Chain Failures)로 둡니다.

| 유형 | 내용 |
|------|------|
| 유지보수자 계정 탈취 | 인기 패키지의 관리자 계정이나 토큰을 빼앗아 악성 버전을 배포 |
| 이름 속임수 | 유명 패키지와 비슷한 이름(타이포스쿼팅)의 악성 패키지 |
| 설치 스크립트 | 설치 순간 실행되는 스크립트로 시크릿 탈취 |
| 간접 의존성 | 내가 고르지 않은 하위 패키지가 오염 |
| 빌드·배포 파이프라인 | CI 설정과 토큰을 노려 산출물을 변조 |

OWASP가 권하는 대응과 npm 도구를 연결하면 다음과 같습니다.

- 의존성 목록을 파악합니다. 간접 의존성까지 포함한 목록(SBOM)을 중앙에서 만들어 관리하고 새 취약점(CVE) 공지를 구독합니다.
- 업그레이드는 의도적으로 합니다. 필요할 때 올리고 모든 시스템에 한 번에 배포하지 않고 단계적(스테이지, 카나리) 배포를 합니다.
- 락파일과 `npm ci`로 버전을 고정합니다.
- `npm audit signatures`로 내려받은 패키지의 레지스트리 서명과 출처 증명(provenance)을 검증합니다. 서명을 지원하는 레지스트리에서 쓸 수 있고, 증명 형식이 바뀔 수 있어서 npm을 최신으로 유지하라고 문서가 안내합니다. Node.js에 포함된 npm보다 새 버전이 필요할 수 있습니다.
- 설치 스크립트가 필요하지 않은 환경(CI)에서는 `ignore-scripts`를 고려합니다.
- 개발·빌드 접근을 강화합니다. 코드를 쓴 사람이 감독 없이 운영까지 올릴 수 없도록 역할을 분리하고, 저장소·개발 PC·빌드 서버에 다단계 인증(MFA)을 적용합니다.
- 쓰지 않는 의존성을 정리하고 유지보수가 중단된 패키지는 대체합니다.
- CI/CD의 비밀값 취급은 9편에서 이어서 다룹니다.

**흔한 실수:** 취약점이 발표된 뒤에야 의존성을 점검하는 것입니다. 정기 점검과 알림을 일상 절차로 둡니다.

## 시크릿 커밋 금지

시크릿(secret)은 DB 비밀번호, API 키, 토큰, 서명 키처럼 노출되면 권한을 빼앗기는 값입니다. 소스 저장소에는 절대 커밋하지 않습니다.

- 저장소에 한 번 올라간 값은 지워도 Git 이력에 남고, 포크와 클론에 복제됩니다. 커밋을 되돌리거나 파일을 지우는 것으로는 회수되지 않습니다. 노출된 값은 즉시 폐기하고 새로 발급(교체)해야 합니다.
- `.env` 같은 파일은 `.gitignore`에 넣고, 값이 없는 `.env.example`만 커밋합니다.
- 코드에는 환경변수 이름만 쓰고 값은 실행 환경에서 주입합니다. Node.js는 `--env-file=.env`로 파일의 값을 환경변수로 읽을 수 있습니다(자세히는 08편).
- GitHub의 push protection은 명령줄 푸시, 웹 UI 커밋, 파일 업로드, REST API 요청에서 탐지된 시크릿을 저장소에 들어가기 전에 차단합니다. 이미 노출된 값을 되돌려 주는 기능은 아닙니다.
- 로그, 오류 응답, 프런트엔드 번들에 시크릿이 섞이지 않게 합니다. 환경변수 전체를 출력하는 디버그 코드는 지웁니다.
- 필요한 최소 권한만 가진 키를 쓰고, 용도별로 분리합니다. 노출돼도 피해가 제한됩니다.
- 이미지와 아티팩트에도 시크릿이 구워지지 않았는지 확인합니다(자세히는 09편).

```gitignore
.env
.env.*
!.env.example
```

**흔한 실수:** 실수로 올린 시크릿을 다음 커밋에서 지우고 안심하는 것입니다. 이력에 남아 있으므로 폐기와 교체가 필요합니다.

## 비밀값 관리 서비스

비밀값 관리 서비스는 시크릿을 코드와 분리된 보관소에 암호화해 두고, 앱이 실행할 때 호출해 가져오게 하는 서비스입니다. AWS Secrets Manager, HashiCorp Vault 같은 것이 있습니다.

AWS Secrets Manager 문서는 다음과 같이 설명합니다.

- DB 자격 증명, 애플리케이션 자격 증명, OAuth 토큰, API 키 같은 시크릿을 수명 주기 전체에 걸쳐 관리·조회·교체합니다.
- 코드에 하드코딩한 자격 증명을 런타임에 서비스를 호출해 동적으로 가져오는 방식으로 대체합니다.
- 자동 교체(rotation) 일정을 설정해 장기 비밀값을 단기 비밀값으로 바꿀 수 있습니다. 비밀값이 앱과 분리돼 있어서 교체할 때 앱을 다시 배포하지 않아도 됩니다.
- 접근은 IAM으로 제어하고 AWS 자격 증명 자체는 IAM, 암호화 키는 KMS를 쓰라고 권합니다(자세히는 10편).

```js
// 의사 코드: 시작할 때 한 번 가져와 메모리에 보관
const dbPassword = await getSecret('prod/db/password')
const pool = createPool({ password: dbPassword })
```

- 시작 시 한 번 읽어 메모리에 보관하고 요청마다 호출하지 않습니다. 교체 주기에 맞춰 다시 읽는 방식도 필요합니다.
- 환경변수로 주입하는 단순한 방식과 비교하면 교체·감사·접근 제어가 강하고, 서비스 의존성과 비용이 늘어납니다. 규모와 요구에 맞춰 고릅니다.
- 보관소 접근 권한이 곧 모든 시크릿의 열쇠입니다. 앱에는 필요한 시크릿 읽기 권한만 줍니다.
- 시크릿 로딩 실패는 시작 단계에서 즉시 드러나게 합니다. 비어 있는 값으로 계속 실행하지 않습니다.

**흔한 실수:** 비밀값 서비스에서 가져온 값을 로그로 출력하는 것입니다. 보관소가 안전해도 로그에서 새어 나옵니다.

## 권한 모델 --permission 개념

권한 모델(Permission Model)은 Node.js 프로세스가 접근할 수 있는 시스템 자원을 실행할 때 제한하는 기능입니다. `--permission` 플래그를 켜면 허용하지 않은 작업은 막힙니다. Node.js 23.5.0과 22.13.0부터 실험 기능이 아닌 Stable(안정성 지수 2)입니다.

```bash
node --permission --allow-fs-read=/app app.js
```

`--permission`을 켜면 다음이 제한됩니다.

| 제한 대상 | 허용 플래그 |
|-----------|-------------|
| 파일 시스템 읽기 | `--allow-fs-read` |
| 파일 시스템 쓰기 | `--allow-fs-write` |
| 자식 프로세스 | `--allow-child-process` |
| 워커 스레드 | `--allow-worker` |
| WASI | `--allow-wasi` |
| 네이티브 애드온 | `--allow-addons` |
| OpenSSL STORE 로더 | `--allow-openssl-store` |

- 허용 안 된 작업은 `ERR_ACCESS_DENIED` 오류를 던집니다. 직접 실험에서 `--permission`만 주면 `readFileSync`와 `spawn`이 모두 이 오류로 막혔고, `--allow-fs-read=<폴더>`를 주자 파일 읽기만 성공하고 `spawn`은 계속 막혔습니다.
- 시작 모듈과 `--require`로 지정한 모듈은 읽기 권한이 암묵적으로 허용됩니다. 실험에서도 실행 중인 스크립트 파일은 읽을 수 있었습니다.
- 경로는 플래그를 여러 번 써서 여러 폴더를 허용합니다. 쉼표로 구분하는 방식은 v20.7.0부터 지원되지 않습니다. `*`는 해당 범주 전체를 허용합니다.
- `process.permission.has('fs.read', 경로)`로 현재 권한을 확인하고 `process.permission.drop()`으로 되돌릴 수 없게 권한을 포기합니다. 초기화 때만 설정 파일을 읽고 나서 읽기 권한을 버리는 용도로 씁니다. 이미 열린 파일 디스크립터나 자식 프로세스는 닫히지 않습니다.
- 감사 모드(`--permission-audit`)는 거부하지 않고 위반 사항을 진단 채널에 기록합니다. 어떤 권한이 필요한지 파악한 뒤 강제 모드로 전환하는 용도이며 문서상 v24.20.0에서 추가됐습니다.
- 이 모델은 "안전벨트"입니다. 신뢰하는 코드가 실수로 파일을 바꾸거나 자원을 쓰는 것을 막을 뿐, 악성 코드에 대한 보안 보장은 없습니다. 악성 코드는 제한을 우회해 임의 코드를 실행할 수 있다고 Node.js 문서가 밝힙니다.
- 심볼릭 링크는 허용 경로 밖을 가리켜도 따라간다고 OWASP Node.js 치트 시트가 주의합니다. 허용 폴더 안에 외부를 가리키는 링크를 두지 않습니다.
- 네트워크 접근 제한은 Node.js 24 문서의 제한 대상에 없습니다(자세히는 15편).

**흔한 실수:** 권한 모델을 켜면 의존성이 안전해진다고 믿는 것입니다. 악성 의존성은 이 장벽을 우회할 수 있으니 의존성 점검과 최소 권한 계정, 컨테이너 격리를 함께 둡니다.

## OWASP Top 10 대응표

OWASP Top 10은 웹 애플리케이션의 가장 중대한 보안 위험을 10개 범주로 정리한 목록입니다. 현재판은 2025입니다. 아래 대응은 이 문서의 절을 범주에 연결한 것이며 OWASP가 만든 매핑이 아닙니다.

| 범주(2025) | 이 편의 대응 |
|------------|--------------|
| A01 접근 제어 실패(Broken Access Control) | 경로 탈출 방어, 디렉터리 리스팅 금지, 권한 모델과 최소 권한 |
| A02 보안 설정 오류(Security Misconfiguration) | helmet과 보안 헤더, 점 파일 차단, 본문·헤더 크기 제한 |
| A03 소프트웨어 공급망 실패(Software Supply Chain Failures) | 의존성 신뢰, 락파일과 `npm ci`, `npm audit`, 공급망 대응 |
| A04 암호화 실패(Cryptographic Failures) | 시크릿 커밋 금지, 비밀값 관리 서비스, HSTS로 HTTPS 강제 |
| A05 인젝션(Injection) | 입력 검증, 명령 주입, SQL 인젝션과 바인딩, 프로토타입 오염 |
| A06 안전하지 않은 설계(Insecure Design) | Rate limit, 요청 크기 제한, 허용 목록 중심 설계 |
| A07 인증 실패(Authentication Failures) | 로그인 요청 속도 제한과 계정 잠금(인증 구현은 중급 10편) |
| A08 소프트웨어·데이터 무결성 실패(Software or Data Integrity Failures) | 락파일의 integrity 해시, `npm audit signatures` |
| A09 보안 로깅·경보 실패(Security Logging and Alerting Failures) | 구조화 로그와 알림(자세히는 11편) |
| A10 예외 상황 처리 실패(Mishandling of Exceptional Conditions) | 오류 응답에 내부 정보를 싣지 않기, 모든 EventEmitter에 오류 리스너 부착 |

- ReDoS와 이벤트 루프 블로킹은 가용성 문제로 A06의 설계·한도 항목과 함께 점검합니다. 목록의 한국어 범주명은 이 문서의 번역입니다.
- 이 표는 점검 순서의 출발점입니다. 범주를 하나씩 대응하는 코드와 설정이 있는지 확인합니다.

## 핵심 정리

- 외부 입력은 허용 목록으로 서버에서 가장 이른 지점에 검증하고, 요청 본문·헤더 크기와 시간에 상한을 둡니다.
- 인젝션 계열은 문자열 결합을 구조로 막습니다. 경로는 해석 후 기준 폴더 안인지 검사하고, 명령은 `execFile`에 인자 배열로 넘기고, SQL은 파라미터 바인딩을 씁니다.
- 프로토타입 오염은 재귀 병합과 `__proto__`에서, ReDoS는 중첩 수량자 정규식에서 생깁니다. 입력 구조 검증, `Map`, 길이 제한으로 막습니다.
- 의존성은 락파일과 `npm ci`로 고정하고 `npm audit`·서명 검증으로 점검하며, 시크릿은 커밋하지 않고 노출되면 교체합니다.
- 보안 헤더(helmet), Rate limit, 권한 모델(`--permission`)은 방어 층을 더하는 수단이고 악성 코드에 대한 완전한 보장이 아닙니다.

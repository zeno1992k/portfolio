## child_process가 필요한 때

`node:child_process`는 Node.js 프로세스가 다른 프로세스를 만들어 실행하는 모듈입니다. 안정성 지수는 2(Stable)입니다. 자식 프로세스는 부모와 메모리를 공유하지 않는 별개의 OS 프로세스입니다.

| 하고 싶은 일 | 선택 |
|--------------|------|
| 외부 프로그램 실행(git, ffmpeg, 쉘 스크립트) | `exec`, `execFile`, `spawn` |
| Node 스크립트를 격리해서 실행, 부모와 메시지 교환 | `fork` |
| JS 계산이 무거워 메인 이벤트 루프를 막음 | 워커 스레드(02편) |
| 같은 서버를 여러 코어에서 실행 | 클러스터(03편) |

- 프로세스마다 메모리와 V8 인스턴스를 따로 쓰므로, 문서도 Node 자식 프로세스를 많이 만드는 것을 권하지 않습니다.
- `execSync`, `execFileSync`, `spawnSync`는 자식이 끝날 때까지 이벤트 루프를 막습니다. 서버 코드에서는 쓰지 않고, 스크립트나 CLI 도구에서만 씁니다.

비동기 API 네 가지의 차이는 다음과 같습니다. 모두 `ChildProcess` 객체를 반환합니다.

| API | 하는 일 | 출력을 받는 방식 |
|-----|---------|------------------|
| `exec` | 쉘을 열어 명령 문자열 실행 | 끝난 뒤 한 번에(콜백) |
| `execFile` | 실행 파일을 직접 실행 | 끝난 뒤 한 번에(콜백) |
| `spawn` | 실행 파일을 직접 실행 | 스트림 |
| `fork` | Node 모듈을 새 프로세스로 실행, IPC 채널 포함 | 스트림 |

## exec

`exec`은 쉘을 열어 명령 문자열을 실행하고, 출력을 모두 메모리에 모았다가 끝나면 콜백으로 줍니다.

```js
import { exec } from 'node:child_process';

exec('node -v', (error, stdout, stderr) => {
  console.log(stdout); // v24.15.0 (환경마다 다름)
});
```

`util.promisify`로 감싸면 `await`로 쓸 수 있습니다. 성공하면 `{ stdout, stderr }`를 돌려주고, 종료 코드가 0이 아니면 reject합니다.

```js
import { promisify } from 'node:util';

const run = promisify(exec);
const { stdout } = await run('node -v');
// reject된 error에도 stdout, stderr가 붙어 있음
```

- 콜백의 `error`는 성공이면 `null`입니다. 실패하면 `error.code`에 종료 코드가, `error.signal`에 종료시킨 시그널이 들어 있습니다.
- 기본값: `encoding`은 `'utf8'`, `maxBuffer`는 `1024 * 1024`바이트, `timeout`은 `0`(제한 없음), `killSignal`은 `'SIGTERM'`입니다.
- `timeout`이 0보다 크면 그 시간(밀리초)을 넘길 때 `killSignal`을 보냅니다.
- 출력 전체를 메모리에 쌓으므로 큰 출력에는 맞지 않습니다. 그럴 때는 `spawn`을 씁니다.
- POSIX의 exec(3)처럼 현재 프로세스를 대체하지 않습니다. 새 프로세스를 만듭니다.

## execFile

`execFile`은 쉘 없이 실행 파일을 직접 실행하고, `exec`처럼 출력을 모아 콜백으로 줍니다. 인수는 배열로 넘깁니다.

```js
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);
const { stdout } = await run('node', ['-p', '1 + 1']);
console.log(stdout); // 2
```

- 기본이 쉘을 쓰지 않는 방식이라 `exec`보다 조금 효율적이고, 인수에 공백이나 따옴표가 있어도 이스케이프할 필요가 없습니다.
- 옵션과 에러 형태는 `exec`과 거의 같습니다. 다른 점은 `shell`이 기본 `false`라는 것과 `windowsVerbatimArguments`가 있다는 것입니다.
- Windows에서 `.bat`과 `.cmd` 파일은 단독 실행 파일이 아니라서 `execFile`로 실행할 수 없습니다(아래 "쉘을 켜는 API와 안 켜는 API").

## spawn

`spawn`은 자식을 시작하고 즉시 `ChildProcess`를 돌려줍니다. 출력은 스트림으로 받습니다.

```js
import { spawn } from 'node:child_process';

const child = spawn('node', ['-p', '"hi"']);
child.stdout.on('data', (chunk) => {
  console.log(chunk.toString()); // hi
});
child.on('close', (code) => console.log(code)); // 0
```

`ChildProcess`가 내는 이벤트는 다음과 같습니다.

| 이벤트 | 시점 |
|--------|------|
| `spawn` | 자식이 성공적으로 시작된 직후. 실패하면 나오지 않음 |
| `error` | 시작 실패, 종료 신호 전송 실패, 메시지 전송 실패, `signal`로 중단됨 |
| `exit` | 자식 프로세스가 끝남 |
| `close` | 끝났고 stdio 스트림도 모두 닫힘 |

- 없는 명령이나 없는 `cwd`는 예외가 아니라 `error` 이벤트(`ENOENT`)로 알려집니다. `error` 리스너가 없으면 처리되지 않은 에러가 되어 부모가 죽습니다.
- `spawn` 이벤트는 쉘이 시작되기만 하면 나옵니다. `{ shell: true }`로 쉘 안에서 존재하지 않는 명령을 실행해도 `spawn`은 발생합니다.
- 옵션: `cwd`, `env`, `argv0`, `stdio`, `detached`, `timeout`, `killSignal`, `signal`, `serialization`, `shell`.
- 큰 출력을 다루거나 실행 중에 출력을 처리해야 하면 `spawn`입니다.

## fork

`fork`는 `spawn`의 특수한 형태로, 새 Node.js 프로세스에서 모듈 하나를 실행하고 부모와 메시지를 주고받는 IPC 채널을 함께 만듭니다.

```js
import { fork } from 'node:child_process';

const child = fork(new URL('./task.js', import.meta.url));
child.on('exit', (code) => console.log(code)); // 0
```

- 실행 파일은 부모의 `process.execPath`입니다. `execPath`로 바꿀 수 있고, `execArgv`의 기본값은 부모의 `process.execArgv`입니다.
- 모듈 경로에 `file:` URL 객체를 줄 수 있습니다(v17.4.0부터).
- `silent`가 `false`(기본)이면 자식의 stdin, stdout, stderr를 부모에서 상속합니다. `true`이면 파이프로 연결합니다.
- 자식은 별개의 V8 인스턴스와 메모리를 가집니다. POSIX의 fork(2)와 달리 현재 프로세스를 복제하지 않습니다.
- `shell` 옵션은 지원하지 않고 무시합니다.
- `stdio`를 배열로 줄 때는 `'ipc'`가 정확히 하나 있어야 합니다. 예: `[0, 1, 2, 'ipc']`.

## 쉘을 켜는 API와 안 켜는 API

쉘은 파이프(`|`), 리다이렉션(`>`), 글롭(`*`), 변수 확장(`$HOME`), `&&` 같은 문법을 해석하는 프로그램입니다. API마다 쉘을 쓰는지가 다릅니다.

| 호출 | 쉘 |
|------|----|
| `exec`, `execSync` | 항상 사용 |
| `execFile`, `execFileSync`, `spawn`, `spawnSync` | 기본은 사용 안 함. `shell: true` 또는 쉘 경로 문자열로 켬 |
| `fork` | 지원하지 않음. 옵션을 줘도 무시 |

- 쉘 기본값은 Unix에서 `/bin/sh`, Windows에서 `process.env.ComSpec`(없으면 `cmd.exe`)입니다.
- 쉘은 `-c` 스위치를 이해해야 하고, `cmd.exe`이면 `/d /s /c`를 이해해야 합니다.
- 쉘이 없으면 문자는 해석되지 않고 인수로 그대로 전달됩니다.

```js
const args = ['-p', 'process.argv[1]', '$HOME *'];
const r = await run('node', args);
console.log(r.stdout); // $HOME *  (확장되지 않음)
```

- Windows에서 `.bat`과 `.cmd`는 `exec`으로 실행하거나, `spawn('cmd.exe', ['/c', 'my.bat'])`처럼 `cmd.exe`에 넘겨 실행합니다. 파일 이름에 공백이 있으면 따옴표가 필요합니다.
- `execFile`과 `spawn`에 `shell`을 켜면서 `args` 배열을 함께 넘기는 것은 DEP0190으로 Node.js 24.0.0부터 런타임 지원 중단(deprecation) 경고가 납니다. 인수가 이스케이프되지 않고 공백으로 이어 붙여질 뿐이라 쉘 주입이 가능하기 때문입니다.

**흔한 실수:** 파이프가 필요해서 `shell: true`와 `args`를 같이 쓰는 것입니다. 파이프는 `spawn` 두 개를 stdout과 stdin으로 이어 쓰거나, 쉘이 꼭 필요하면 명령 전체를 하나의 문자열로 만들되 값을 직접 검증합니다.

## 명령 주입

명령 주입(command injection)은 사용자 입력이 쉘 명령 문자열에 섞여, 입력 속의 메타문자가 별도 명령으로 실행되는 취약점입니다. 문서도 `exec`에 검증되지 않은 입력을 넘기지 말라고 경고합니다.

```js
const name = 'a & echo INJECTED'; // 사용자 입력이라고 가정

await run1(`echo hello ${name}`);
// ❌ exec: 쉘이 & 뒤를 별도 명령으로 실행 → INJECTED 출력

await run2('node', ['-p', 'process.argv[1]', name]);
// ✅ execFile: 문자열 전체가 인수 하나 → a & echo INJECTED
```

(`run1`은 `promisify(exec)`, `run2`는 `promisify(execFile)`입니다. Windows `cmd.exe`에서 실제로 확인한 결과입니다.)

- 쉘 메타문자는 쉘마다 다릅니다. `;`, `&`, `|`, 백틱, `$( )`, `>`, `<`, 줄바꿈이 대표적입니다.
- 방어의 기본은 쉘을 거치지 않는 것입니다. `execFile`이나 `spawn`에 실행 파일과 인수 배열을 따로 넘깁니다.
- 쉘이 없어도 인수가 `-`로 시작하면 대상 프로그램이 옵션으로 해석할 수 있습니다. 프로그램이 허용하면 `--`로 옵션의 끝을 표시하고, 입력은 허용 목록으로 검증합니다.
- 입력 검증, 경로 탈출, 보안 전반은 07편에서 다룹니다.

**흔한 실수:** 문자열을 직접 따옴표로 감싸서 막았다고 믿는 것입니다. 입력 안의 따옴표로 쉽게 깨집니다. 이스케이프를 직접 짜지 말고 쉘을 쓰지 않습니다.

## stdio

`stdio` 옵션은 자식의 입출력(fd 0 = stdin, 1 = stdout, 2 = stderr)을 어디에 연결할지 정합니다. 기본은 `['pipe', 'pipe', 'pipe']`입니다.

| 값 | 의미 |
|----|------|
| `'pipe'` | 부모와 파이프 생성. `subprocess.stdin`, `subprocess.stdout`, `subprocess.stderr` 스트림으로 노출 |
| `'ignore'` | 버림(`/dev/null`에 연결) |
| `'inherit'` | 부모의 stdio를 그대로 사용 |
| `'ipc'` | 메시지용 IPC 채널 생성. 하나만 가능 |
| 스트림 객체 | fd를 가진 스트림(파일, 소켓, TTY 등)을 공유 |
| 양의 정수 | 부모에서 열려 있는 fd를 공유 |
| `null`, `undefined` | 기본값. 0–2는 `'pipe'`, 3 이상은 `'ignore'` |

```js
spawn('node', ['a.js'], { stdio: 'inherit' });
spawn('node', ['a.js'], {
  stdio: ['pipe', 'pipe', process.stderr],
});
spawn('node', ['a.js'], {
  stdio: ['ignore', logFd, logFd],
});
```

- 문자열 `'pipe'`, `'ignore'`, `'inherit'`는 세 fd 모두에 적용되는 축약형입니다. 배열이면 인덱스가 fd 번호입니다.
- `'pipe'`가 아닌 위치의 `subprocess.stdout` 등은 `null`입니다.
- `stdin`을 파이프로 두고 입력을 기다리는 자식(`grep`처럼)은 부모가 `child.stdin.end()`를 호출해야 입력이 끝났다고 알고 종료합니다.
- `exec`와 `execFile`에는 `stdio` 옵션이 없습니다. 출력은 항상 버퍼링해서 줍니다.

**흔한 실수:** `stdio: 'inherit'`로 만들고 `child.stdout.on('data', ...)`를 쓰는 것입니다. 이 경우 `child.stdout`이 `null`이라 TypeError가 납니다.

## stdout 버퍼가 꽉 차면 멈춤

부모와 자식 사이의 파이프는 용량이 제한되어 있고(용량은 플랫폼마다 다름), 부모가 읽지 않아 가득 차면 자식이 쓰기에서 멈춰 기다립니다. 쉘에서 파이프를 쓸 때와 같은 동작입니다.

```js
const child = spawn('node', ['big-output.js']); // 큰 출력을 씀
// 읽지 않고 멈춰 둠(pause)
child.stdout.pause();
setTimeout(() => console.log(child.exitCode), 1000);
// null: 파이프가 가득 차 자식이 쓰기에서 멈춘 상태
```

- 해결책은 둘 중 하나입니다. 출력을 읽거나(`data` 핸들러, `resume()`, `pipe()`), 필요 없으면 `stdio: 'ignore'` 또는 `'inherit'`로 파이프를 만들지 않습니다.
- stdout뿐 아니라 stderr도 같습니다. 한쪽만 읽고 다른 쪽을 방치하면 그쪽에서 막힙니다.
- `exec`과 `execFile`은 내부에서 읽어 주지만 `maxBuffer`(기본 1 MiB)를 넘으면 자식을 종료하고 출력이 잘립니다. 이때 `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` 에러가 납니다.
- `maxBuffer`는 문자 수가 아니라 바이트 수입니다. UTF-8 한글은 한 글자가 3바이트입니다.
- 실측(Node.js 24, 3,000,000바이트 출력): 기본 `maxBuffer`에서는 에러가 나고 `stdout`은 1048576바이트에서 잘렸고, `maxBuffer: 10_000_000`이면 전체를 받았습니다.

## 종료 코드

종료 코드(exit code)는 프로세스가 끝나면서 운영체제에 남기는 정수입니다. 관례상 `0`이 성공이고 다른 값은 실패입니다.

```js
import { once } from 'node:events';

const child = spawn('node', ['-e', 'process.exit(3)']);
const [code, signal] = await once(child, 'close');
console.log(code, signal); // 3 null
```

`exit`와 `close`의 차이는 다음과 같습니다.

| 이벤트 | 시점 | stdio |
|--------|------|-------|
| `exit` | 프로세스가 끝난 직후 | 아직 열려 있을 수 있음 |
| `close` | 프로세스가 끝나고 stdio도 모두 닫힌 뒤 | 닫힘 |

- 출력을 끝까지 받은 뒤 결과를 처리하려면 `close`를 씁니다. 여러 프로세스가 같은 stdio를 공유할 수 있어서 둘이 분리되어 있습니다.
- 두 이벤트의 인수는 `(code, signal)`이며 둘 중 정확히 하나만 `null`이 아닙니다. 자기 힘으로 끝났으면 `code`, 시그널로 끝났으면 `signal`입니다.
- `subprocess.exitCode`는 끝나기 전까지 `null`입니다.
- 실행에 실패하면 `error`가 나오고 `exit`는 나올 수도, 안 나올 수도 있습니다. 두 이벤트를 함께 듣는다면 핸들러가 두 번 실행되지 않게 방어합니다. `once(child, 'close')`는 `error`가 나오면 reject됩니다.
- Node.js 프로세스는 처리되지 않은 예외로 끝나면 코드 1을 냅니다.
- `exec`과 `execFile`은 코드가 0이 아니면 콜백에 `error`를 넘기고(`error.code`가 종료 코드), promisify 버전은 reject합니다.

## 시그널로 죽은 경우

시그널(signal)은 운영체제가 프로세스에 보내는 신호입니다. 시그널로 끝난 프로세스는 종료 코드가 없어서 `code`가 `null`이고 `signal`에 시그널 이름이 들어옵니다.

```js
const script = 'setInterval(() => {}, 1e3)';
const child = spawn('node', ['-e', script]);
child.on('exit', (code, signal) => {
  console.log(code, signal);
});
child.kill(); // 기본 SIGTERM
// null SIGTERM
```

| 항목 | 설명 |
|------|------|
| `subprocess.signalCode` | 자식을 끝낸 시그널. 시그널로 끝나지 않았으면 `null` |
| `subprocess.kill([signal])` | 시그널을 보냄. 기본 `'SIGTERM'`. 전달에 성공하면 `true` |
| `subprocess.killed` | 시그널 전달에 성공했는지 여부. 실제로 끝났다는 뜻이 아님 |
| `util.convertProcessSignalToExitCode(signal)` | 시그널을 `128 + 시그널 번호` 형태의 종료 코드로 변환 |

```js
import {
  convertProcessSignalToExitCode as toCode,
} from 'node:util';

toCode('SIGTERM'); // 143 (128 + 15)
toCode('SIGKILL'); // 137 (128 + 9)
```

- `convertProcessSignalToExitCode`는 v24.14.0과 v25.4.0에 추가되었습니다. 그보다 낮은 버전에는 없습니다.
- `SIGTERM`은 종료 요청이라 자식이 핸들러로 정리할 수 있고, `SIGKILL`은 핸들러 없이 강제로 끝냅니다. 이름은 `kill`이지만 보낸 시그널이 프로세스를 반드시 끝내지는 않습니다.
- Node.js 프로세스는 `SIGINT`, `SIGTERM` 핸들러를 기본으로 등록해 두고, 즉시 끝내지 않고 정리한 뒤 같은 시그널을 다시 일으킵니다.
- `timeout`, `signal` 옵션으로 끝난 자식도 `killSignal`(기본 `'SIGTERM'`)로 죽은 것이라 `signal`에 그 이름이 들어옵니다.
- Windows에는 POSIX 시그널이 없습니다. `SIGKILL`, `SIGTERM`, `SIGINT`, `SIGQUIT` 같은 알려진 시그널은 모두 프로세스를 강제로 즉시 끝냅니다.
- 이미 끝난 자식에게 `kill()`을 해도 에러는 아니지만, 그 PID가 다른 프로세스에 재할당되었다면 시그널이 그쪽으로 갑니다.

**흔한 실수:** 실패를 `if (code)`로만 판단하는 것입니다. 시그널로 죽으면 `code`가 `null`이라 실패가 통과합니다. `code !== 0 || signal !== null`로 판단합니다.

## IPC 채널

IPC(Inter-Process Communication) 채널은 부모와 자식이 메시지 객체를 주고받는 통로입니다. `fork`는 기본으로 만들고, `spawn`은 `stdio` 배열에 `'ipc'`를 넣으면 만들어집니다.

- 채널이 있으면 부모는 `subprocess.send()`와 `'message'` 이벤트를, Node.js 자식은 `process.send()`, `process.on('message')`, `process.connected`, `process.disconnect()`를 씁니다.
- 채널은 프로세스당 하나입니다. Node.js가 아닌 자식과의 IPC나 채널 fd를 직접 만지는 것은 지원하지 않습니다.
- 채널을 닫으면 양쪽에서 `'disconnect'` 이벤트가 나오고 `connected`가 `false`가 됩니다. 이후에는 메시지를 주고받을 수 없습니다.
- 채널이 열려 있으면 이벤트 루프를 붙잡습니다. 자식의 `message`·`disconnect` 리스너 수에 따라 자동 관리되고, `process.channel.ref()`와 `unref()`로 직접 정할 수도 있습니다. 부모 쪽은 `subprocess.channel.unref()`입니다.
- 메시지는 직렬화되어 전달되므로 받은 값이 보낸 값과 같지 않을 수 있습니다.

| `serialization` | 방식 | 지원 값 |
|-----------------|------|---------|
| `'json'`(기본) | JSON | JSON으로 표현되는 값만 |
| `'advanced'` | `node:v8` 직렬화(구조적 복제 기반) | `BigInt`, `Map`, `Set`, `Date`, `ArrayBuffer`, `Buffer`, `Error`, `RegExp` 등 |

- `'json'`에서는 `NaN`이 `null`로, `Date`가 문자열로, `Map`이 `{}`로 바뀝니다. `'advanced'`는 같은 값을 그대로 전달합니다(Node.js 24에서 확인).
- `'advanced'`는 JSON의 완전한 상위 호환이 아닙니다. 내장 타입 객체에 붙인 추가 프로퍼티는 전달되지 않고, 구조에 따라 JSON보다 느릴 수 있어서 옵트인입니다.
- `send()`의 두 번째 인수로 `net.Server`, `net.Socket`, `dgram.Socket` 핸들을 보낼 수 있습니다. 클러스터가 이 기능으로 소켓을 워커에 넘깁니다(03편). v26.10.0부터는 `net.BoundSocket`도 보낼 수 있습니다.

## 부모와 메시지

부모는 `child.send(message)`로 보내고 `'message'` 이벤트로 받습니다. 자식은 `process.send()`와 `process.on('message')`로 같은 일을 합니다. 요청과 응답을 짝지으려면 `id`를 메시지에 담습니다.

```js
// parent.mjs
import { fork } from 'node:child_process';

const child = fork(new URL('./child.mjs', import.meta.url));
child.on('message', (msg) => {
  console.log('parent got', msg); // { id: 1, result: 10 }
  child.disconnect(); // 채널을 닫으면 자식도 끝남
});
child.send({ id: 1, n: 5 });
```

```js
// child.mjs
process.on('message', ({ id, n }) => {
  process.send({ id, result: n * 2 });
});
```

- 자식은 `message` 리스너가 있는 동안 채널 때문에 살아 있습니다. 부모가 `disconnect()`하면 채널이 닫혀 자식이 종료됩니다(위 예제에서 종료 코드 0 확인).
- `send()`는 불리언을 돌려줍니다. 흐름 제어용 값이며, 선택 인수로 전송 완료 콜백도 받습니다.
- 자식이 이미 끝났거나 채널이 닫힌 뒤에 `send()`하면 `error` 이벤트로 알려집니다.
- 자식이 Node.js가 아니면 IPC를 쓸 수 없으므로 stdin과 stdout으로 한 줄에 JSON 하나씩 주고받는 방식을 씁니다.

## 자식 좀비 / 대기

좀비(zombie) 프로세스는 이미 끝났지만 부모가 종료 상태를 회수(wait)하지 않아서 프로세스 테이블에 항목이 남은 상태입니다. 고아(orphan) 프로세스는 부모가 먼저 끝나 PID 1에 입양된 살아 있는 프로세스입니다.

- Node.js는 자식이 끝나면 종료 상태를 수거해서 `exit`로 알립니다(문서는 waitpid(2) 참조). 그래서 `spawn`한 자식을 평소처럼 쓰는 코드에서 좀비가 쌓이는 일은 흔하지 않습니다.
- 문제는 손자 프로세스입니다. 자식이 만든 프로세스가 고아가 되어 PID 1에 입양되는데, PID 1이 회수를 하지 않으면 좀비로 남습니다. 컨테이너에서 Node.js가 PID 1일 때 겪는 문제입니다(08편).
- 자식을 기다리는 가장 단순한 방법은 `close`를 `await`하는 것입니다. 여러 개면 `Promise.all`로 모읍니다.

```js
const jobs = items.map((item) => {
  const child = spawn('node', ['job.js', item]);
  return once(child, 'close'); // [code, signal]
});
const results = await Promise.all(jobs);
```

- 부모가 끝나도 자식이 따라 죽지 않습니다. 문서에 따르면 Windows가 아닌 플랫폼에서는 `detached`가 아니어도 부모가 끝난 뒤 자식이 계속 실행될 수 있습니다. 부모가 시그널로 끝날 때 자식을 정리하려면 핸들러에서 직접 `kill()`합니다.

```js
for (const sig of ['SIGINT', 'SIGTERM']) {
  process.on(sig, () => {
    child.kill();
    process.exit(1);
  });
}
```

- `kill()`은 직계 자식만 대상으로 합니다. 문서에 따르면 Linux에서 쉘이나 `shell` 옵션으로 실행한 경우 쉘 아래의 손자 프로세스는 부모를 죽여도 종료되지 않습니다. 이 때문에 쉘 없이 대상 프로그램을 직접 실행하는 편이 정리하기 쉽습니다.

## execa

execa는 `child_process` 위에 만든 서드파티 라이브러리로, 스크립트에서 명령을 실행하는 용도에 맞춰 설계되었습니다. 설치는 `npm install execa`입니다.

```js
import { execa } from 'execa';

const { stdout } = await execa('node', ['-p', '1 + 1']);
console.log(stdout); // 2 (끝의 개행 제거됨)
await execa`node -p ${'a & echo X'}`; // 값은 인수 하나로 전달
```

| 항목 | 내장 `child_process` | execa |
|------|----------------------|-------|
| 결과 | 콜백·이벤트 조합 | 프로미스(결과 객체) |
| 인수 이스케이프 | 직접 신경 써야 함 | 배열·템플릿 값이 자동 이스케이프, 쉘 주입 위험 없음 |
| 실패 | 종료 코드 0이 아니어도 이벤트만 발생 | 프로미스 reject, `exitCode`, `isTerminated`, `timedOut`, `isCanceled`, `isMaxBuffer` 제공 |
| Windows | `.cmd`, `.bat`에 쉘 필요 | `shell: true` 없이 실행 |
| 취소 | `signal` 옵션 | `cancelSignal`, 정리 기회를 주는 `gracefulCancel` |

- 실패해도 던지지 않게 하려면 `{ reject: false }`를 주면 에러 객체가 결과로 반환됩니다.
- `$` 스크립트 문법, 여러 프로세스 파이프(`.pipe`), 줄 단위 출력 처리, 부모·자식 메시지 교환도 제공합니다.
- 쉘이 필요한 구문(파이프 `|`, 리다이렉션 `>`, 글롭 `*`, 변수 `$VAR`)만 `shell` 옵션을 켭니다. 문서도 가능하면 쉘을 피하라고 권합니다.
- Node 내장 API로 충분한 단발성 실행은 `execFile`이면 되고, 실패 처리와 Windows 호환이 반복되면 execa가 낫습니다.

## AbortSignal로 자식 종료

`exec`, `execFile`, `spawn`, `fork`는 `signal` 옵션으로 `AbortSignal`을 받습니다. `abort()`를 호출하면 `kill()`과 비슷하게 자식을 끝내고, 에러는 `AbortError`(`code`는 `'ABORT_ERR'`)로 전달됩니다.

```js
const controller = new AbortController();
const { signal } = controller;
const script = 'setInterval(() => {}, 1e3)';
const child = spawn('node', ['-e', script], { signal });
child.on('error', (err) => console.log(err.name));
// AbortError
child.on('close', (c, s) => console.log(c, s));
// null SIGTERM
controller.abort();
```

- 보내는 시그널은 `killSignal`(기본 `'SIGTERM'`)입니다.
- 제한 시간만 필요하면 `timeout` 옵션이 더 단순합니다. 시간이 지나면 `killSignal`로 끝냅니다.
- 오래 사는 자식을 자원 정리용으로 `AbortSignal`에 묶는 용법은 Node.js 26.8.2부터 문서상 지원 중단입니다(DEP0209, 문서 전용). 취소, 바깥에서 전파되는 중단, 제한 시간용 `signal`은 계속 권장됩니다.
- 정리 용도에는 `using` 선언을 권합니다. `ChildProcess`는 `Symbol.dispose`를 구현하고 `SIGTERM`으로 `kill()`합니다(v24.2.0부터 실험 딱지 없음).

```js
{
  using child = spawn('node', ['server.js']);
  await once(child, 'spawn');
} // 블록을 벗어나면 child.kill('SIGTERM')
```

## detached와 unref

기본적으로 부모의 이벤트 루프는 자식이 끝날 때까지 기다립니다. `detached`와 `unref()`는 자식이 부모와 따로 살게 만드는 옵션입니다.

- `detached: true`: 자식이 독립 실행 준비를 합니다. Windows에서는 자식이 부모가 끝난 뒤에도 계속 실행되고 자기 콘솔 창을 가지며 한 번 켜면 끌 수 없습니다. Windows가 아닌 곳에서는 자식이 새 프로세스 그룹과 세션의 리더가 됩니다.
- `subprocess.unref()`: 부모의 이벤트 루프가 자식을 기다리지 않게 합니다. IPC 채널이 있으면 채널이 부모를 붙잡으므로 효과가 없습니다. `subprocess.ref()`로 되돌립니다.
- 부모의 stdio를 상속한 채로는 자식이 부모의 터미널에 묶여 있어서, 배경에서 계속 실행하려면 부모와 연결되지 않는 `stdio`를 줍니다.

```js
const child = spawn('node', ['long-task.js'], {
  detached: true,
  stdio: 'ignore',
});
child.unref(); // 부모는 기다리지 않고 바로 끝날 수 있음
```

- 출력을 남기려면 파일 fd를 `stdio`에 줍니다. `stdio: ['ignore', out, err]`이고 `out`, `err`는 `fs.openSync('./out.log', 'a')`의 결과입니다.
- 로컬 확인(Node.js 24, Windows): 1.5초 뒤 파일을 쓰는 자식을 `detached` + `stdio: 'ignore'` + `unref()`로 띄우면 부모는 6ms 만에 끝났고 자식은 파일을 쓰고 끝났습니다. `unref()`를 빼면 부모가 1549ms까지 기다렸습니다.

**흔한 실수:** `unref()`만 하고 `stdio`를 `'pipe'`로 두는 것입니다. stdio 파이프가 부모의 이벤트 루프를 붙잡아 부모가 기다리게 됩니다(Node.js 24, Windows에서 1548ms 대기 확인). 백그라운드 실행은 `detached`, `stdio: 'ignore'`(또는 파일), `unref()`를 세트로 씁니다.

## 핵심 정리

- 외부 프로그램 실행은 `execFile`·`spawn`(쉘 없음)이 기본이고, `exec`은 쉘을 거치므로 사용자 입력을 넣으면 명령 주입이 됩니다. `fork`는 Node 스크립트 전용으로 IPC 채널이 따라옵니다.
- 출력이 크면 `spawn`으로 스트림을 소비하고, 안 읽을 출력은 `stdio: 'ignore'`로 끊습니다. 읽지 않은 파이프는 자식을 멈추고, `exec`의 `maxBuffer`(기본 1 MiB)는 초과 시 자식을 종료합니다.
- 결과는 `close`의 `(code, signal)`로 판단합니다. 시그널로 죽으면 `code`가 `null`입니다.
- IPC 메시지는 기본 JSON이라 값이 바뀔 수 있으므로 필요하면 `serialization: 'advanced'`를 씁니다.
- `kill()`은 직계 자식만 대상이고, 부모가 끝나도 자식은 살아남을 수 있으므로 종료 정리를 직접 합니다. 백그라운드 실행은 `detached`, `stdio: 'ignore'`, `unref()`를 같이 씁니다.
- 중단·취소는 `signal`·`timeout` 옵션으로 하고, 실패 처리와 Windows 호환이 반복되면 execa를 고려합니다.

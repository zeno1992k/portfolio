## Dockerfile

Dockerfile은 컨테이너 이미지를 만드는 명령 목록입니다. 명령 하나가 이미지의 레이어 하나가 됩니다. Node.js 서버용 Dockerfile의 뼈대는 "빌드 단계"와 "실행 단계"를 나누는 멀티 스테이지입니다.

### 멀티 스테이지

한 Dockerfile에 `FROM`을 여러 번 쓰면 단계(stage)가 여러 개 생깁니다. `AS 이름`으로 단계에 이름을 붙이고, `COPY --from=이름`으로 앞 단계의 결과물만 골라 가져옵니다. 마지막 단계만 최종 이미지가 되므로, 빌드 도구와 중간 파일은 이미지에 남지 않습니다.

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
```

위는 빌드 단계입니다. 의존성을 전부 설치하고 TypeScript 같은 소스를 `dist`로 컴파일합니다. 아래는 실행 단계입니다.

```dockerfile
FROM node:24-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

- 실행 단계는 운영 의존성(`--omit=dev`)과 빌드 결과물만 담습니다.
- `npm ci`는 락 파일(`package-lock.json`)대로만 설치하고, 락 파일과 `package.json`이 어긋나면 에러로 끝납니다. `package.json`과 락 파일은 고치지 않습니다. 이미 있는 `node_modules`는 지우고 시작합니다.
- `omit`의 기본값은 `NODE_ENV`가 `production`일 때 `dev`입니다. 위 예의 `--omit=dev`는 이를 명시한 것입니다.
- 특정 단계까지만 빌드하려면 `docker build --target build .`를 씁니다. 테스트용 단계와 운영 단계를 한 파일에 두고 골라 빌드할 수 있습니다.
- BuildKit은 대상 단계가 의존하지 않는 단계는 건너뜁니다.
- 첫 줄의 `# syntax=docker/dockerfile:1`은 Dockerfile 문법 버전을 고르는 파서 지시문입니다.

### 레이어 캐시와 명령 순서

레이어가 바뀌면 그 뒤의 레이어는 모두 다시 만들어집니다. 그래서 바뀌지 않는 명령을 위에, 자주 바뀌는 명령을 아래에 둡니다. 위 예가 `package*.json`을 먼저 복사해 `npm ci`를 실행하고 소스 전체(`COPY . .`)를 나중에 복사하는 이유입니다. 소스만 고치면 의존성 설치 레이어는 캐시를 재사용합니다.

**흔한 실수:** `COPY . .`를 `npm ci` 앞에 두는 것입니다. 코드 한 줄을 고칠 때마다 의존성을 처음부터 다시 설치합니다.

### non-root 사용자

Docker는 기본적으로 컨테이너 안에서 명령을 root로 실행합니다. 최소 권한 원칙에 어긋나므로 root가 꼭 필요하지 않으면 일반 사용자로 실행합니다. 공식 `node` 이미지에는 uid 1000인 `node` 사용자가 이미 있습니다. Dockerfile에서는 `USER node`로 전환합니다.

- `USER`는 그 단계의 이후 명령(`RUN`, `CMD` 등)을 지정한 사용자로 실행합니다.
- 파일이 root 소유로 복사되어도 `node` 사용자가 읽고 실행할 수는 있습니다. 앱이 파일을 써야 하는 디렉터리가 있으면 `COPY --chown=node:node`로 소유자를 지정합니다.
- 1024 미만 포트는 일반 사용자가 열기 어려우므로 컨테이너 안에서는 3000 같은 포트로 열고, 바깥 포트는 매핑으로 정합니다.

### .dockerignore

`.dockerignore`는 빌드 컨텍스트(`docker build`에 넘기는 디렉터리)에서 제외할 파일을 적는 파일입니다. 컨텍스트 루트에 둡니다. 형식은 줄마다 패턴을 적는 방식이고 `**`는 여러 단계의 디렉터리, `!`는 예외, `#`으로 시작하는 줄은 주석입니다. 마지막으로 일치한 규칙이 적용됩니다.

```text
node_modules/
dist/
.env
.git
npm-debug.log*
coverage/
```

- `node_modules/`를 제외하는 이유: 호스트에서 설치한 모듈은 OS와 아키텍처가 컨테이너와 다를 수 있습니다. 이미지 안에서 `npm ci`로 새로 설치합니다.
- `.env`와 `.git`을 제외하면 시크릿과 이력이 `COPY . .`로 이미지에 들어가는 것을 막습니다.
- 컨텍스트가 작아지면 빌드 시작이 빠르고, 불필요한 파일 변경으로 캐시가 깨지는 일도 줄어듭니다.

**흔한 실수:** `.dockerignore` 없이 `COPY . .`를 하는 것입니다. `.env`와 로컬 `node_modules`가 이미지에 그대로 들어갑니다.

## 베이스 이미지 선택과 이미지 크기

공식 `node` 이미지는 변형(variant)이 여러 가지입니다.

| 태그 | 바탕 | 특징 |
|------|------|------|
| `node:24` | Debian 기반(buildpack-deps) | 흔한 패키지와 빌드 도구 포함. 가장 크지만 호환성이 가장 넓음 |
| `node:24-slim` | Debian 최소 구성 | `node` 실행에 필요한 패키지만 포함 |
| `node:24-alpine` | Alpine Linux | 매우 작음(Alpine 자체가 약 5MB). glibc 대신 musl libc 사용 |
| `node:24-bookworm` | Debian 릴리스 이름 지정 | 추가 패키지를 설치할 때 릴리스를 고정해 깨짐을 줄임 |

- Alpine은 musl libc를 쓰므로 glibc를 전제로 한 일부 소프트웨어와 호환되지 않을 수 있습니다. 네이티브 애드온이나 미리 빌드된 바이너리를 쓰는 패키지가 있으면 먼저 확인합니다.
- slim은 공간이 정말 중요할 때 쓰도록 권장되는 변형입니다. 기본 태그에 들어 있는 흔한 패키지가 없습니다.
- 운영에는 Active LTS인 짝수 버전을 씁니다. `latest`나 메이저만 적은 태그는 시간이 지나면 다른 버전을 가리킬 수 있습니다.
- 태그는 재배포되며 가리키는 이미지가 바뀝니다. 완전히 고정하려면 다이제스트로 핀합니다(예: `FROM node:24-slim@sha256:...`).
- 신뢰할 수 있는 출처(Docker Official Images, Verified Publisher)의 이미지에서 시작합니다.

이미지 크기를 줄이는 수단은 다음과 같습니다.

| 수단 | 효과 |
|------|------|
| 멀티 스테이지 | 빌드 도구·devDependencies·소스를 최종 이미지에서 제거 |
| `npm ci --omit=dev` | 운영에 필요 없는 패키지 제거 |
| slim 또는 Alpine | 기본 OS 용량 감소 |
| `.dockerignore` | 불필요한 파일 유입 차단 |
| 필요한 패키지만 설치 | 용량과 취약점 면적 감소 |

패키지가 적을수록 파일 크기와 복잡도, 잠재적 취약점이 모두 줄어듭니다.

## PID 1과 tini

컨테이너 안에서 처음 시작되는 프로세스가 PID 1입니다. 리눅스에서 PID 1은 특별 취급을 받습니다. 시그널 기본 동작이 적용되지 않아서, 핸들러를 등록하지 않은 프로세스는 `SIGINT`나 `SIGTERM`을 받아도 종료하지 않습니다. 고아가 된 자식 프로세스(좀비)를 거두는 책임도 PID 1이 집니다. Node.js는 PID 1로 실행되도록 설계되지 않았다고 공식 Docker 이미지 문서가 설명합니다(08편에서 다룬 내용의 컨테이너 쪽 정리).

시그널이 Node 프로세스에 도달하려면 다음을 지킵니다.

- `CMD`와 `ENTRYPOINT`는 exec 형식(JSON 배열)으로 씁니다. 셸 형식은 `/bin/sh -c`의 하위 프로세스로 실행되어 시그널이 전달되지 않고, 그 경우 `docker stop`의 `SIGTERM`을 못 받습니다.
- `npm start`로 실행하면 npm이 시그널을 삼킬 수 있으므로 `CMD ["node", "dist/main.js"]`처럼 node를 직접 실행합니다.
- Node 코드에서 `SIGTERM`을 처리해 정상 종료합니다(자세히는 중급 25편).

`docker stop`은 `SIGTERM`을 보내고, 기본 10초(Linux) 안에 끝나지 않으면 `SIGKILL`로 강제 종료합니다. 신호는 이미지의 `STOPSIGNAL`로 바꿀 수 있고 Compose는 `stop_grace_period`로 유예 시간을 정합니다.

```dockerfile
STOPSIGNAL SIGTERM
```

PID 1 문제를 피하는 가장 단순한 방법은 init 프로세스를 앞에 두는 것입니다. tini는 자식 하나를 실행하고 그 종료를 기다리면서 시그널을 전달하고 좀비를 거두는 약 10KB의 init입니다.

```bash
docker run --init my-app
```

Compose에서는 서비스에 `init: true`를 씁니다. Dockerfile에 직접 넣을 수도 있습니다. Alpine이면 `apk add --no-cache tini`로 설치하며 경로는 `/sbin/tini`입니다.

```dockerfile
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "dist/main.js"]
```

**흔한 실수:** 로컬 터미널에서는 Ctrl+C로 잘 꺼지는데 컨테이너에서는 `docker stop`이 10초를 꽉 채워 기다린 뒤 죽는 경우입니다. 셸 형식 `CMD`나 `npm start`가 원인이고, 정상 종료 코드가 실행되지 않은 채 `SIGKILL`로 끝나 요청이 끊깁니다.

## 헬스체크

`HEALTHCHECK`는 컨테이너가 실제로 일을 하는지 검사하는 명령을 지정합니다. 서버 프로세스는 떠 있지만 무한 루프에 빠져 새 연결을 처리하지 못하는 상태를 잡아냅니다. 헬스체크가 있으면 컨테이너 상태에 `starting`, `healthy`, `unhealthy`가 더해집니다. 처음은 `starting`이고, 검사가 성공하면 `healthy`, 연속으로 정해진 횟수를 실패하면 `unhealthy`입니다.

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s \
  --start-period=10s --retries=3 \
  CMD ["node", "healthcheck.js"]
```

| 옵션 | 기본값 | 뜻 |
|------|--------|----|
| `--interval` | 30s | 검사 주기 |
| `--timeout` | 30s | 이 시간을 넘기면 실패. 검사 프로세스는 `SIGKILL`로 중단 |
| `--start-period` | 0s | 시작 유예. 이 기간의 실패는 재시도 횟수에 세지 않음 |
| `--start-interval` | 5s | 시작 유예 기간의 검사 주기(Docker Engine 25.0 이상) |
| `--retries` | 3 | 연속 실패 몇 번에 `unhealthy`로 보는지 |

- 검사 명령의 종료 코드가 판정입니다. 0은 정상, 1은 비정상이며 2는 예약이라 쓰지 않습니다.
- Dockerfile에는 `HEALTHCHECK`가 하나만 유효합니다. 여러 개를 쓰면 마지막 것만 적용됩니다. 베이스 이미지의 헬스체크를 끄려면 `HEALTHCHECK NONE`입니다.
- 검사 명령이 출력한 텍스트는 `docker inspect`로 볼 수 있습니다(처음 4096바이트만 저장).
- 검사 명령은 이미지 안에서 실행됩니다. 이미지에 `curl`이 없을 수 있으므로 Node.js 24의 전역 `fetch`로 검사하는 스크립트를 두면 추가 설치가 필요 없습니다.

```js
// healthcheck.js
try {
  const res = await fetch('http://127.0.0.1:3000/health')
  process.exit(res.ok ? 0 : 1)
} catch {
  process.exit(1)
}
```

헬스체크는 "살아 있는가"와 "요청을 받을 준비가 됐는가"를 구분해 설계합니다. 컨테이너 헬스체크는 한 가지 상태만 보므로, 의존 서비스(DB)까지 포함해 검사하면 DB 장애 때 컨테이너가 전부 `unhealthy`가 됩니다. 두 가지를 나누는 방법은 11편의 liveness·readiness 절을 봅니다.

**흔한 실수:** `--start-period` 없이 시작이 느린 앱을 검사하는 것입니다. 부팅 중 실패가 재시도 횟수에 세어져 정상 앱이 `unhealthy`로 표시됩니다.

## docker compose

Docker Compose는 여러 컨테이너로 이루어진 애플리케이션을 `compose.yaml` 한 파일로 정의하고 한 번에 실행하는 도구입니다. 로컬 개발과 통합 테스트에서 앱과 DB를 함께 띄울 때 씁니다.

```yaml
services:
  app:
    build: .
    ports: ["3000:3000"]
    init: true
    environment:
      DATABASE_URL: postgres://db:5432/app
    depends_on:
      db:
        condition: service_healthy
```

```yaml
  db:
    image: postgres:18
    healthcheck:
      test: ["CMD", "pg_isready"]
      interval: 10s
      timeout: 5s
      retries: 5
```

- `depends_on`만 쓰면 Compose는 컨테이너가 "실행 중"이 되기만 기다리고 "준비됨"은 기다리지 않습니다.
- `condition: service_healthy`는 의존 서비스의 `healthcheck`가 통과할 때까지 기다립니다. `service_started`(기본)와 `service_completed_successfully`(끝까지 성공 종료)도 있습니다.
- 서비스 간에는 서비스 이름이 호스트명입니다. 위 예에서 앱은 `db`로 DB에 접속합니다.
- `restart`는 `no`(기본), `always`, `on-failure`, `unless-stopped`입니다.
- Compose의 `healthcheck`는 Dockerfile의 `HEALTHCHECK`와 같은 일을 하며 속성은 `test`, `interval`, `timeout`, `retries`, `start_period`, `start_interval`입니다.
- 개발용 소스 동기화는 `develop.watch`로 설정하고, 이미지 빌드 단계 선택은 `build.target`으로 합니다.

**흔한 실수:** DB가 뜨기 전에 앱이 접속을 시도해 시작에 실패하는 것입니다. 헬스체크와 `service_healthy`를 쓰거나, 앱이 접속 재시도를 구현하도록 합니다.

## GitHub Actions 파이프라인

GitHub Actions는 저장소 이벤트로 워크플로를 실행하는 CI/CD 서비스입니다. 워크플로는 `.github/workflows/`의 YAML 파일이고, `on`(트리거), `jobs`(작업), 각 작업의 `steps`로 구성됩니다.

- `on`에는 `push`, `pull_request`, 수동 실행용 `workflow_dispatch` 등을 쓰며 브랜치·태그 필터를 줄 수 있습니다.
- 작업은 기본적으로 병렬입니다. `needs`로 순서를 지정합니다.
- `runs-on`이 실행 환경(GitHub 호스트 러너 또는 자체 러너)입니다.

먼저 테스트 작업입니다. 액션 버전은 공식 문서 예시 기준입니다.

```yaml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm test
```

- `cache: npm`은 `setup-node`가 npm 의존성 캐시를 저장하고 복원하게 합니다.
- CI에서는 `npm install`이 아니라 `npm ci`를 씁니다. 락 파일 그대로 설치하고 락 파일을 바꾸지 않아 재현성이 높습니다.
- 여러 Node 버전을 시험하려면 `strategy.matrix.node-version`에 버전 배열을 줍니다.

테스트가 통과한 `main` 브랜치에서만 이미지를 만들어 레지스트리에 올리는 작업을 이어 붙입니다.

```yaml
  image:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: docker/login-action@v4
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
```

이어서 같은 `steps` 안에 빌드와 푸시 단계를 둡니다.

```yaml
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: user/app:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

- `needs: test`는 테스트 작업이 성공해야 실행됩니다. `if`는 조건에 맞을 때만 실행합니다.
- 이미지 태그에 커밋 해시(`github.sha`)를 넣으면 배포된 이미지가 어느 커밋인지 추적할 수 있고, 되돌릴 때 이전 태그를 가리키면 됩니다.
- `cache-from`·`cache-to`의 `type=gha`는 GitHub 캐시를 빌드 레이어 캐시로 씁니다. 러너는 매번 새로 시작하므로 이 설정이 없으면 레이어 캐시가 매번 사라집니다.
- 비밀 값은 저장소의 secrets에, 민감하지 않은 값은 variables에 두고 `secrets`·`vars` 컨텍스트로 읽습니다. 로그에 평문으로 찍지 않습니다.
- `concurrency`의 `group`과 `cancel-in-progress: true`를 쓰면 같은 그룹의 이전 실행을 취소합니다. 배포 작업에는 한 번에 하나만 돌도록 `group`을 지정합니다.
- `jobs.작업이름.environment`로 배포 환경(예: production)을 지정하면 그 환경의 보호 규칙(승인자 등)과 환경별 secrets를 쓸 수 있습니다.
- `timeout-minutes`로 작업 최대 시간을 제한하고, `permissions`로 `GITHUB_TOKEN` 권한을 필요한 만큼만 줍니다.
- 클라우드에 배포할 때는 장기 자격 증명을 secrets에 복사하는 대신 OpenID Connect(OIDC)로 작업마다 만료되는 단기 토큰을 받는 방식이 권장됩니다. 클라우드 쪽 연동은 10편에서 AWS 기준으로 이어집니다.

**흔한 실수:** 이미지 태그를 항상 `latest` 하나로 올리는 것입니다. 배포한 버전을 구별할 수 없고 롤백 대상을 지정할 수 없습니다.

## 무중단 배포

새 버전을 배포하는 동안 서비스가 멈추지 않게 하는 방식입니다. 대표적인 두 가지를 AWS ECS 기준으로 정리합니다.

| 항목 | 롤링 업데이트 | 블루그린 |
|------|----------------|----------|
| 방식 | 기존 태스크를 새 태스크로 점진 교체 | 신버전(green) 환경을 따로 띄우고 트래픽을 옮김 |
| 추가 자원 | 교체 중 일부만 추가 | 교체 중 두 환경이 동시에 실행되어 자원이 최대 두 배 |
| 검증 | 교체가 진행되며 헬스체크로 판단 | 운영 트래픽을 보내기 전에 테스트 트래픽으로 검증 가능 |
| 롤백 | 이전 리비전으로 되돌림 | blue를 유지하다가 즉시 되돌림(bake time 동안) |

롤링 업데이트는 두 값으로 속도를 정합니다.

- `minimumHealthyPercent`: 배포 중 정상 상태로 유지할 태스크 수의 하한(원하는 수 대비, 올림). 50이고 원하는 수가 4면 기존 2개를 먼저 멈출 수 있습니다.
- `maximumPercent`: 배포 중 실행할 수 있는 태스크 수의 상한(내림). 200이고 원하는 수가 4면 신규 4개를 먼저 띄울 수 있습니다.
- 둘 다 최소 한 개의 태스크를 멈추거나 시작할 수 있게 값을 잡아야 배포가 막히지 않습니다.
- 실패를 빨리 알아채는 수단으로 배포 서킷 브레이커(태스크가 시작하지 못할 때 중단)와 CloudWatch 경보(애플리케이션 지표로 중단)가 있고, 둘 다 이전 리비전으로 롤백할 수 있습니다.

블루그린은 로드 밸런서의 리스너·규칙·타깃 그룹으로 트래픽을 옮기며, 라이프사이클 훅(Lambda 함수 또는 일시정지)으로 자동 검증을 끼워 넣을 수 있습니다.

Node.js 서버 쪽에서 무중단이 성립하려면 다음이 맞아야 합니다.

- 새 인스턴스는 준비된 뒤에만 트래픽을 받습니다. 헬스체크가 그 기준입니다.
- 교체되는 인스턴스는 `SIGTERM`을 받으면 새 연결을 받지 않고 진행 중인 요청을 마친 뒤 종료합니다(자세히는 중급 25편). 유예 시간은 종료 처리 시간보다 길어야 합니다.
- 구 버전과 신 버전이 동시에 같은 DB를 사용하는 구간이 생깁니다. 스키마 변경은 두 버전이 모두 동작하도록 단계를 나눠 적용합니다.
- 서버는 상태를 메모리에 두지 않아야 인스턴스가 교체되어도 영향이 없습니다(자세히는 03편).

**흔한 실수:** 헬스체크는 통과하지만 DB 연결이나 캐시 워밍이 끝나지 않은 인스턴스가 트래픽을 받는 것입니다. 준비 완료 기준을 헬스체크 엔드포인트에 반영합니다.

## 환경별 설정 주입

같은 이미지를 개발·스테이징·운영에 그대로 쓰고 설정만 바꿔 주입합니다(자세히는 중급 25편). 이미지 안에 환경별 값을 넣으면 환경마다 이미지를 따로 만들어야 하고 시크릿이 이미지에 남습니다.

| 방법 | 쓰임 |
|------|------|
| `docker run -e KEY=value` | 값을 직접 지정. 값 없이 `-e KEY`만 쓰면 호스트 환경의 값을 전달 |
| `docker run --env-file 파일` | 파일의 `KEY=value` 줄을 읽음. `#`은 주석 |
| Compose `environment` | `compose.yaml`에 직접 지정 |
| Compose `env_file` | 외부 파일을 참조 |
| Dockerfile `ENV` | 이미지의 기본값. 실행하는 컨테이너에도 남음 |

Compose에서 같은 변수가 여러 곳에 있을 때 우선순위는 높은 쪽부터 다음과 같습니다.

1. `docker compose run -e`
2. 셸 또는 환경 파일에서 보간된 `environment`·`env_file` 값
3. Compose 파일의 `environment`
4. Compose 파일의 `env_file`
5. 이미지 `ENV`

- Dockerfile의 `ENV` 값은 `docker inspect`로 누구나 볼 수 있고 컨테이너 실행 때 `docker run --env`로 덮어쓸 수 있습니다. 시크릿을 `ENV`에 넣지 않습니다.
- 빌드 중에 시크릿이 필요하면 `RUN --mount=type=secret`을 씁니다. 시크릿 값이 이미지에 남지 않습니다.
- 실행 시 시크릿은 Compose의 `secrets`(파일로 마운트)나 클라우드의 시크릿 저장소에서 주입합니다. PostgreSQL 이미지의 `POSTGRES_PASSWORD_FILE`처럼 `_FILE` 변수로 파일 경로를 받는 관례도 있습니다.
- 환경 이름만 다르고 코드는 같게 유지합니다. 환경별 `.env` 파일(`.env.production` 등)을 `.dockerignore`에 넣어 이미지에 굽지 않습니다.
- GitHub Actions에서는 `environment`별 secrets와 variables로 환경마다 다른 값을 주고, 서버 시작 시 설정을 검증합니다(자세히는 중급 25편).

**흔한 실수:** `.env`를 `COPY . .`로 이미지에 넣는 것입니다. 이미지를 공유하거나 레지스트리에 올리면 시크릿이 같이 나갑니다.

## 핵심 정리

- 멀티 스테이지로 빌드 도구를 최종 이미지에서 빼고, 의존성 설치를 소스 복사보다 위에 둬 레이어 캐시를 살립니다. 실행은 `USER node`, 컨텍스트는 `.dockerignore`로 줄입니다.
- 베이스 이미지는 LTS 짝수 버전의 slim이나 Alpine 중에서 고르고, Alpine은 musl 호환성을 확인하며 태그나 다이제스트를 고정합니다.
- `CMD`는 exec 형식으로 `node`를 직접 실행하고, PID 1 문제는 `--init`(tini)로 풉니다. `docker stop`은 `SIGTERM` 후 기본 10초 뒤 `SIGKILL`입니다.
- `HEALTHCHECK`의 종료 코드 0은 정상, 1은 비정상이며 느린 시작에는 `--start-period`가 필요합니다. Compose는 `service_healthy`로 준비 완료를 기다립니다.
- 파이프라인은 `npm ci`, 테스트, 이미지 빌드·푸시 순이며 `needs`로 연결하고 커밋 해시로 태그를 붙입니다. 롤링은 점진 교체, 블루그린은 환경 전환입니다.
- 설정과 시크릿은 이미지에 굽지 않고 실행 시점에 주입합니다.

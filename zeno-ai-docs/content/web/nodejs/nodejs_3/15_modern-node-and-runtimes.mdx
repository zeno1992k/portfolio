## 권한 모델

권한 모델(Permission Model)은 Node.js 프로세스가 접근할 수 있는 자원을 실행 시점에 제한하는 기능입니다. `--permission`을 켜면 기본이 전부 거부이고, 필요한 것만 `--allow-*` 플래그로 엽니다. 문서의 안정성 지수는 2(Stable)이며 v23.5.0, v22.13.0부터 실험 기능이 아닙니다.

```bash
node --permission \
  --allow-fs-read=./data \
  --allow-fs-write=./out \
  app.js
```

| 플래그 | 허용하는 것 |
|--------|-------------|
| `--allow-fs-read`, `--allow-fs-write` | 파일 시스템 읽기·쓰기(경로 지정) |
| `--allow-child-process` | 자식 프로세스 생성 |
| `--allow-worker` | 워커 스레드 생성 |
| `--allow-addons` | 네이티브 애드온 |
| `--allow-wasi` | WASI |
| `--allow-net` | 네트워크(v25.0.0 추가, 안정성 1.1) |

- 허용하지 않은 자원에 접근하면 `ERR_ACCESS_DENIED` 에러가 나고, `permission`과 `resource` 속성에 거부된 권한과 대상이 담깁니다.
- `--permission-audit`은 거부하지 않고 위반만 기록하는 감사 모드입니다. 도입 전에 어떤 권한이 필요한지 파악할 때 씁니다.
- 런타임에서 `process.permission.has('fs.read', path)`로 권한을 확인하고, `process.permission.drop(scope)`로 권한을 되돌릴 수 없게 내려놓습니다. 시작할 때 필요한 일을 마친 뒤 줄이는 용도입니다.
- 앱의 진입 파일은 v24.2.0, v22.17.0부터 암묵적으로 읽기가 허용됩니다.
- `--allow-fs-read`에 쉼표로 여러 경로를 잇는 방식은 v20.7.0부터 허용되지 않습니다. 플래그를 반복해서 씁니다.

문서가 밝히는 한계는 다음과 같습니다.

- 악의적인 코드를 막는 샌드박스가 아닙니다. 신뢰하는 코드의 실수를 막는 안전벨트로 설계되었고, 악성 코드는 우회해서 임의의 일을 할 수 있습니다.
- 심볼릭 링크는 허용된 경로 밖을 가리켜도 따라갑니다.
- 워커 스레드에는 상속되지 않습니다.
- 이미 열린 파일 디스크립터를 `node:fs`로 쓰는 것은 막지 못합니다.
- `--env-file`, `--openssl-config`처럼 권한 초기화 전에 파일을 읽는 플래그는 모델을 우회합니다.

그래서 권한 모델은 의존성 하나가 몰래 파일을 쓰거나 프로세스를 띄우는 것을 줄이는 방어 한 겹이지, 신뢰할 수 없는 코드를 실행하는 수단이 아닙니다. 그런 경우는 컨테이너나 VM 같은 OS 수준 격리를 씁니다(공급망 공격 대응은 07편, 컨테이너는 09편).

**흔한 실수:** 권한 모델을 켰으니 외부 코드를 안심하고 돌려도 된다고 믿는 것, 쓰기 경로를 너무 넓게(`/`) 허용하는 것, 앞의 플래그만 보고 시스템 모듈이 필요로 하는 읽기 경로(앱 디렉터리, 설정 파일)를 빠뜨려 시작부터 `ERR_ACCESS_DENIED`가 나는 것입니다.

## 단일 실행 파일(SEA)

단일 실행 파일 애플리케이션(Single Executable Application, SEA)은 스크립트를 Node.js 실행 파일에 넣어 Node.js가 설치되지 않은 환경에서도 실행되는 하나의 파일로 만드는 기능입니다. CLI 도구를 배포할 때 씁니다. 안정성 지수는 1.1(활발한 개발)입니다.

`--build-sea`(v25.5.0 추가, 안정성 1.1)로 설정 파일 하나에서 바로 만듭니다.

```bash
# sea-config.json: { "main": "hello.js", "output": "sea" }
node --build-sea sea-config.json
./sea world   # hello.js가 world를 인수로 실행됨
```

그 이전에는 `node --experimental-sea-config sea-config.json`으로 블롭을 만든 뒤 postject로 실행 파일에 주입하는 두 단계였고, `--build-sea`가 이를 자동화합니다. 사용하는 버전의 문서에서 `--build-sea`가 있는지 확인합니다.

설정 파일의 주요 필드는 다음과 같습니다.

| 필드 | 뜻 |
|------|----|
| `main` | 넣을 스크립트 경로 |
| `mainFormat` | `commonjs` 등 스크립트 형식 |
| `output` | 만들 실행 파일 경로 |
| `executable` | 기반이 될 Node 실행 파일 |
| `useSnapshot`, `useCodeCache` | 시작 속도 최적화 옵션 |
| `assets` | 실행 파일에 넣을 정적 파일 |

- 코드에서는 `node:sea` 모듈의 `isSea()`로 SEA 안에서 실행 중인지 확인하고, `getAsset(key, 'utf8')`로 넣어 둔 파일을 읽습니다.
- 넣을 수 있는 스크립트는 하나(CommonJS 또는 ESM)입니다. 기본으로 `require()`와 `import`는 내장 모듈만 불러오므로, 앱 전체를 하나의 파일로 번들링해야 합니다. 번들러는 별도 도구를 씁니다.
- 파일 시스템의 모듈을 읽으려면 `module.createRequire()`를 씁니다.
- 문서가 CI로 확인하는 플랫폼은 Windows, macOS(arm64만), Linux(Alpine과 s390x 제외)입니다.

**흔한 실수:** 여러 파일의 프로젝트를 번들 없이 그대로 넣으려는 것, 안정 기능으로 알고 배포 파이프라인에 고정하는 것(1.1 단계라 옵션이 바뀔 수 있음), 문서가 확인한 플랫폼 밖에서의 동작을 가정하는 것입니다.

## node:sqlite

`node:sqlite`는 SQLite 데이터베이스를 외부 패키지 없이 쓰는 내장 모듈입니다(v22.5.0 추가). 안정성 지수는 1.2(릴리스 후보)입니다. 처음에는 `--experimental-sqlite` 플래그가 필요했고 v23.4.0(22 계열은 v22.13.0)부터 필요하지 않습니다. 모든 API가 동기입니다.

```js
import { DatabaseSync } from 'node:sqlite';

const db = new DatabaseSync(':memory:'); // 또는 파일 경로
db.exec('CREATE TABLE t(id INTEGER PRIMARY KEY, n TEXT)');
const ins = db.prepare('INSERT INTO t (n) VALUES (?)');
ins.run('kim'); // { changes: 1, lastInsertRowid: 1 }
const sel = db.prepare('SELECT * FROM t WHERE id = ?');
sel.get(1);     // { id: 1, n: 'kim' }
db.prepare('SELECT * FROM t').all(); // 행 배열
db.close();
```

- `exec`는 결과 없는 SQL, `prepare`는 `StatementSync`를 만들고, 문장의 `run`은 변경 정보, `get`은 한 행(없으면 `undefined`), `all`은 전체 행, `iterate`는 이터레이터를 돌려줍니다.
- 값은 `?` 같은 파라미터로 바인딩합니다. 문자열을 이어 붙이면 SQL 인젝션이 됩니다(07편). 이름 있는 파라미터(`:name`, `$name`, `@name`)도 쓸 수 있습니다.
- 동기 API라서 쿼리가 길면 이벤트 루프가 멈춥니다. 요청을 받는 서버에는 작은 쿼리나 도구, 스크립트, 테스트 용도가 맞고, 큰 작업은 워커 스레드로 옮깁니다(02편).
- SQLite는 파일 하나의 임베디드 DB라서 서버를 여러 대로 늘리는 구조에는 맞지 않습니다. 이런 용도는 PostgreSQL 같은 서버형 DB를 씁니다(중급 17편). 안정성도 아직 1.2라 API가 바뀔 수 있습니다.
- 모듈이 생긴 배경은 중급 23편에서 다룹니다.

**흔한 실수:** 안정 API로 알고 운영 서비스의 핵심 저장소에 쓰는 것, `prepare`한 문장을 닫지 않는 것(`close()` 호출), 동기 호출이 요청 처리 지연이 되는 것을 모르는 것입니다.

## 내장 테스트·watch·env-file·타입 스트립 정리

개발 도구 몇 가지가 외부 패키지 없이 Node.js 안에 들어왔습니다. 안정성과 추가 버전을 한 표로 모읍니다.

| 기능 | 명령·API | 안정성 | 기준 버전 |
|------|----------|--------|-----------|
| 테스트 러너 | `node --test`, `node:test` | 2 | v20.0.0부터 안정 |
| watch 모드 | `node --watch` | 2 | v17.5.0 추가 |
| 환경 변수 파일 | `node --env-file=파일` | 2 | v20.6.0 추가, v24.10.0·v22.21.0부터 안정 |
| 없어도 되는 환경 변수 파일 | `--env-file-if-exists` | 2 | v22.9.0 추가 |
| 코드로 환경 변수 읽기 | `process.loadEnvFile()` | - | v21.7.0 추가 |
| 타입 스트립 | `node app.ts` | 2 | v23.6.0·v22.18.0부터 기본 활성, v25.2.0·v24.12.0에서 안정화 |
| 스크립트 실행 | `node --run 스크립트` | 1.2 | package.json의 scripts 실행 |

### 내장 테스트

`node:test`는 `test`, `describe`, `it`을 제공하고 `node --test`가 테스트 파일을 찾아 실행합니다(중급 24편).

- 필터는 `--test-name-pattern`, `--test-skip-pattern`, `--test-only`(`only: true`와 함께)입니다.
- `mock.fn()`, `t.mock.timers`로 목과 가짜 타이머를 쓰고, `--test-update-snapshots`로 스냅샷을 만듭니다.
- 리포터는 `spec`(기본), `tap`, `dot`, `junit`, `lcov`이고, `--test-reporter`로 고릅니다.
- 커버리지는 `--experimental-test-coverage` 플래그로 켭니다. 이름에 experimental이 붙어 있다는 점이 문서 기준입니다.
- 전역 준비·정리(`--test-global-setup`)는 v24.0.0부터입니다.
- `node --test --watch`로 변경 시 다시 실행합니다.

### watch

`node --watch app.js`는 작업 디렉터리의 파일이 바뀌면 프로세스를 다시 시작합니다. `--watch-path`로 감시 경로를 정하고(여러 번 지정 가능), `--watch-preserve-output`으로 화면을 지우지 않습니다. 개발용이며 운영에서는 켜지 않습니다(08편).

### env-file

`.env` 형식의 파일을 코드 없이 불러옵니다.

```bash
node --env-file=.env --env-file=.env.local app.js
```

- 줄마다 `KEY=값`이고 `#` 주석, 따옴표(작은·큰·백틱), 여러 줄 값을 지원합니다.
- 파일을 여러 개 주면 뒤에 오는 파일이 앞의 값을 덮어씁니다.
- `--env-file`은 파일이 없으면 에러를 던지고, `--env-file-if-exists`는 없어도 넘어갑니다.
- 파일 경로는 현재 작업 디렉터리 기준입니다. 개념은 기초 07편에서 다뤘습니다.
- 권한 모델은 이 플래그가 읽는 파일을 막지 못합니다(위 "권한 모델").

### 타입 스트립

타입 스트립(type stripping)은 TypeScript 파일에서 타입 표기를 공백으로 바꿔 지우고 JavaScript로 실행하는 방식입니다. 타입 검사는 하지 않습니다. 검사는 `tsc` 같은 도구가 따로 합니다(기초 27편).

```bash
node app.ts   # 플래그 없이 실행(v22.18.0 이상)
```

```ts
import type { User } from './types.ts'; // type 키워드 필수
import { load, type Options } from './load.ts'; // 확장자 필수
```

- 확장자는 `.ts`, `.mts`, `.cts`가 지원됩니다. `.tsx`는 지원하지 않습니다.
- 지울 수 있는 문법만 허용됩니다. `enum`, 런타임 코드가 있는 `namespace`, 매개변수 프로퍼티 같은 코드 생성이 필요한 문법은 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` 에러가 납니다. 이전의 `--experimental-transform-types` 플래그는 v26.0.0에서 제거되었습니다.
- 타입만 가져오는 `import`에는 `type` 키워드가 필수이고, 가져오는 경로에는 확장자를 적어야 합니다.
- `tsconfig.json`은 읽지 않습니다. `paths` 별칭이나 `target` 변환은 적용되지 않습니다.
- `node_modules` 안의 파일에는 적용되지 않습니다. 패키지는 JavaScript로 배포되어야 합니다.
- 소스맵은 만들지 않습니다. 타입이 있던 자리가 공백으로 바뀌어 줄 번호는 유지됩니다.
- `tsconfig`는 편집기·`tsc` 검사용으로 `noEmit`, `module: nodenext`, `erasableSyntaxOnly`, `verbatimModuleSyntax`처럼 지울 수 있는 문법만 쓰게 설정하는 방식이 문서에 권장되어 있습니다.

**흔한 실수:** 타입 스트립이 타입 검사까지 해 준다고 생각하는 것, 확장자 없는 import나 `enum`을 쓰다 에러가 나는 것, `node_modules` 안의 `.ts` 패키지가 실행되지 않는다는 점을 놓치는 것입니다.

## require(esm)

`require(esm)`은 CommonJS에서 `require()`로 ES 모듈을 불러오는 기능입니다. 이전에는 CommonJS에서 ESM을 쓰려면 비동기 `import()`뿐이었습니다. v22.12.0, v20.19.0부터 플래그 없이 동작하고, 문서는 v25.4.0부터 더 이상 실험 기능이 아니라고 적습니다(CJS와 ESM의 관계는 기초 09편).

```js
// distance.mjs (파일 이름은 예시)
export const add = (a, b) => a + b;
export default class Point {}

// app.cjs
const mod = require('./distance.mjs');
mod.add(1, 2); // 3
mod.default;   // Point 클래스
```

- 반환값은 모듈 네임스페이스 객체입니다. 기본 내보내기는 `default` 속성에 있습니다.
- 불러오는 모듈은 완전히 동기여야 합니다. 최상위 `await`가 있으면(자기 자신이든 의존하는 모듈이든) `ERR_REQUIRE_ASYNC_MODULE`이 납니다. 이때는 `import()`를 씁니다.
- 대상은 `.mjs` 파일, `"type": "module"`인 패키지의 `.js`, 또는 `"type": "commonjs"`가 아닌 곳에서 ES 모듈 문법을 가진 `.js`입니다.
- ESM이 `export { X as 'module.exports' }`로 내보내면 `require()`가 그 값을 그대로 돌려줍니다. CommonJS 사용자가 `.default` 없이 쓰게 하려는 라이브러리용 규약입니다.
- 지원 여부는 `process.features.require_module`로 확인합니다. `--no-require-module`로 끄고, `--trace-require-module`로 사용 위치를 출력합니다.
- 효과는 라이브러리 작성자에게 큽니다. ESM 전용 패키지를 CommonJS 프로젝트가 `await import()` 없이 쓸 수 있어서, 듀얼 패키지를 만들 필요가 줄어듭니다(기초 10편).

**흔한 실수:** 최상위 `await`를 쓰는 모듈에 `require()`를 쓰는 것, `require()` 결과의 기본 내보내기를 `.default` 없이 쓰는 것, 지원 버전(22.12 이상, 20.19 이상)을 확인하지 않고 쓰는 것입니다.

## Web 표준 API 채택

Node.js는 브라우저와 같은 이름의 Web 표준 API를 전역에 두어, 브라우저·엣지·서버에서 같은 코드를 쓸 수 있게 하고 있습니다. 문서가 밝힌 상태는 다음과 같습니다.

| API | 상태 |
|-----|------|
| `fetch`, `Request`, `Response`, `Headers`, `FormData` | Stable. v17.5.0 추가, v21.0.0에서 실험 해제. undici 기반 |
| Web Streams(`ReadableStream` 등) | Stable(v21.0.0), v18.0.0부터 전역 |
| `CompressionStream`, `TextDecoderStream` | v23.11.0, v22.15.0부터 stable |
| WebCrypto(`globalThis.crypto.subtle`) | Stable(v19.0.0), 일부 최신 알고리즘은 개발 중 |
| `WebSocket` 클라이언트 | Stable(v22.4.0), v21.0.0 추가 |
| `EventSource` | Experimental, `--experimental-eventsource` 필요 |
| `URLPattern` | Experimental(v24.0.0 추가) |
| `structuredClone`, `BroadcastChannel`, `EventTarget`, `Blob` | Stable |

### fetch

전역 `fetch`는 undici로 구현되어 있습니다(중급 07편). 요청은 `AbortSignal`로 취소하고 타임아웃은 `AbortSignal.timeout()`으로 겁니다(14편). 서버 코드에서는 HTTP 오류 상태(4xx·5xx)가 에러가 아니라 정상 응답으로 오므로 `res.ok`를 확인합니다.

### Web Streams

웹 스트림은 브라우저와 같은 `ReadableStream`, `WritableStream`, `TransformStream`입니다. Node 스트림과는 서로 바꾸는 헬퍼가 있습니다(`Readable.toWeb`, `Readable.fromWeb`, `Writable.toWeb`, `Writable.fromWeb`, `Duplex.toWeb`, `Duplex.fromWeb`). `fetch` 응답 본문이 웹 스트림이라 Node 스트림 파이프라인에 연결할 때 변환이 필요합니다(중급 02편). 서버 내부의 파일·소켓 처리는 여전히 Node 스트림이 주력이고, 이식성이 목적이면 웹 스트림을 씁니다.

### WebCrypto

`globalThis.crypto`에는 `getRandomValues()`, `randomUUID()`, `subtle`이 있습니다. 문서가 나열하는 알고리즘은 AES(CBC, CTR, GCM 등), RSA-OAEP, ECDSA, Ed25519, RSA-PSS, HMAC, HKDF, PBKDF2, ECDH, X25519, SHA-2 계열 해시이고, 최근 문서에는 Argon2, ML-KEM, ML-DSA 같은 새 알고리즘도 올라와 있습니다. 새 알고리즘은 개발 중이므로 `SubtleCrypto.supports()`로 지원 여부를 확인하고 PBKDF2 같은 대안을 준비합니다. 같은 코드가 브라우저와 서버에서 돌아가는 것이 장점이며, Node 전용 기능이 필요하면 `node:crypto`를 씁니다(중급 21편).

**흔한 실수:** 모든 전역이 안정이라고 가정하는 것(`EventSource`, `URLPattern`은 실험), 웹 스트림과 Node 스트림을 변환 없이 섞어 쓰는 것, 최신 알고리즘을 지원 확인 없이 쓰는 것입니다.

## Bun·Deno 비교

Bun과 Deno는 Node.js와 같은 자리를 노리는 대안 JavaScript 런타임입니다. 세 런타임은 목표와 설계가 다릅니다. 아래는 각 공식 문서에서 확인한 내용입니다.

| 항목 | Node.js | Deno | Bun |
|------|---------|------|-----|
| 성격 | 범용 런타임, 최대 생태계 | 보안 기본값, 표준 지향 런타임 | 런타임·패키지 매니저·테스트 러너·번들러를 합친 도구 |
| 엔진 | V8 | V8 | JavaScriptCore |
| 보안 | 기본은 전체 허용, 권한 모델은 `--permission`으로 선택 | 기본 거부, `--allow-read`, `--allow-net`, `--allow-env`, `--allow-run`으로 허용 | Node 호환이 목표이며 별도 권한 모델은 문서에서 확인하지 못함 |
| TypeScript | 타입 스트립으로 `.ts` 실행(지울 수 있는 문법만) | 설정 없이 `.ts` 실행 | 설정 없이 TypeScript·JSX 실행 |
| 패키지 | npm, `package.json` | `npm:` 지정자와 JSR, `package.json` 지원 | 내장 패키지 매니저 `bun install` |
| 내장 도구 | 테스트 러너, watch, env-file | 포매터, 린터, 테스트 러너, 벤치마크 | 테스트 러너(Jest 호환), 번들러 `bun build` |
| 단일 실행 파일 | SEA(안정성 1.1) | `deno compile` | `bun build --compile` |
| Node 호환 | 기준 구현 | `node:` 접두사로 내장 모듈, `npm:` 패키지 | 대부분 구현, 일부 모듈은 부분 구현 |

- Deno의 권한은 경로·호스트로 범위를 줄일 수 있습니다(`--allow-read=./data`). 문서는 `--allow-run`으로 만든 자식 프로세스는 제한을 받지 않고 `--allow-ffi`는 JavaScript 층의 권한을 우회한다고 경고합니다. 샌드박스의 허점은 Node 권한 모델과 같은 종류입니다.
- Deno는 Node API를 `node:` 접두사로 제공하고(Deno 2.9부터 접두사 없는 가져오기도 동작), `process`는 전역이며 `Buffer`는 가져와야 합니다. `__dirname` 대신 `import.meta.dirname`을 씁니다. Node-API 애드온은 로컬 `node_modules`와 `--allow-ffi`가 필요합니다.
- Bun은 "Node.js에서 되는 패키지가 Bun에서 안 되면 Bun의 버그"라는 입장이고, Node 테스트 스위트를 출시 전에 돌립니다. 다만 문서가 부분 구현으로 표시하는 모듈이 있습니다. `node:cluster`는 HTTP 로드 밸런싱이 Linux에서만, `node:async_hooks`는 `AsyncLocalStorage`만 동작하고 `createHook`은 빈 구현이며, `node:worker_threads`에는 `resourceLimits`가 없고, `node:test`는 스냅샷이 없습니다. `node:sea`는 없고 `bun build --compile`을 씁니다.
- 위 부분 구현 항목은 이 시리즈의 클러스터(03편), 워커(02편), 컨텍스트 전파(11편) 같은 주제와 직접 겹칩니다. 도입 전에 쓰는 모듈의 지원 상태를 확인합니다.

선택 기준은 다음과 같습니다.

| 상황 | 판단 |
|------|------|
| 채용·운영 안정성, 기존 생태계, 장기 지원 | Node.js(LTS 사용) |
| 기본 거부 권한과 표준 API, 자체 도구 일체 | Deno |
| 빠른 설치·실행 도구, 단일 도구 체인 | Bun(Node 호환 구멍을 확인 후) |
| 서버리스·엣지 | 플랫폼이 지원하는 런타임(10편) |

런타임을 바꾸는 비용은 코드가 아니라 운영에 있습니다. 모니터링 에이전트, 네이티브 모듈, 진단 도구, 장애 대응 경험이 Node.js 기준으로 쌓여 있기 때문입니다. 위 표는 공식 문서의 기능 비교이고 성능 수치는 비교하지 않았습니다. 성능은 자기 워크로드로 직접 측정합니다(05편).

**흔한 실수:** 벤치마크 한 줄로 런타임을 바꾸는 것, Node 호환이라는 말을 모든 API 동일로 받아들이는 것, 다른 런타임에서 개발하고 Node에 배포(또는 반대)해 환경 차이를 운영에서 발견하는 것입니다.

## WinterTC

WinterTC는 서버 측 JavaScript 런타임 사이에서, 특히 웹과 공통되는 API의 호환성을 높이는 것을 목적으로 하는 Ecma International 기술 위원회(TC55)입니다. 런타임마다 API가 달라 같은 코드를 옮기기 어려운 문제를 줄이려는 시도입니다.

대표 산출물이 Minimum Common Web Platform API이며, 서버 런타임이 구현해야 할 웹 API의 최소 공통 집합을 정합니다. 확인한 시점(2026-07-31)에는 초안(Draft)이었습니다. 포함하는 묶음은 다음과 같습니다.

| 묶음 | 예 |
|------|----|
| 이벤트 | `AbortController`, `AbortSignal`, `EventTarget`, `Event`, `CustomEvent` |
| 네트워크 | `fetch`, `Headers`, `Request`, `Response`, `FormData` |
| 데이터 | `Blob`, `File`, `TextEncoder`, `TextDecoder`, 압축 스트림 |
| 스트림 | `ReadableStream`, `WritableStream`, `TransformStream` |
| URL | `URL`, `URLSearchParams`, `URLPattern` |
| 암호 | Web Crypto(`Crypto`, `SubtleCrypto`, `CryptoKey`) |
| 타이밍·유틸 | `setTimeout`, `performance`, `structuredClone`, `console`, `queueMicrotask`, `atob`, `btoa` |
| 기타 | WebAssembly 인터페이스, `navigator.userAgent`, `globalThis` |

- 런타임별 확장은 허용하되 API 표면을 최소한만 건드려 이식성을 지키라는 방향입니다.
- WHATWG, W3C 같은 웹 표준 기구와 협력해 서버용 API를 웹 표준에 맞춥니다.
- 실무에서의 의미: 이식성이 필요한 코드(라이브러리, 엣지 함수)는 `node:` 모듈 대신 이 공통 API(`fetch`, `crypto.subtle`, 웹 스트림, `URL`)로 쓰면 런타임을 바꾸기 쉽습니다. 파일 시스템, 자식 프로세스 같은 서버 전용 기능은 이 표준 밖입니다.
- 이 문서의 위 절이 다룬 Web 표준 API 전역들이 이 최소 공통 집합과 겹치는 부분입니다.

**흔한 실수:** 초안 단계의 명세를 확정 표준으로 설명하는 것, 공통 API에 파일 시스템·네트워크 서버까지 포함된다고 오해하는 것입니다.

## 릴리스 일정 변경

Node.js 릴리스 일정이 바뀝니다. 공식 공지(Evolving the Release Schedule)에 따르면 Node.js 27부터 메이저 릴리스가 연 1회가 되고, 홀수·짝수 구분이 없어지며, 모든 메이저 버전이 LTS가 됩니다. 현재의 일정은 연 2회, 짝수 버전만 LTS이고 홀수 버전은 6개월 뒤 지원이 끝나는 방식입니다(기초 02편).

| 구분 | 이전 방식 | 새 방식(27부터) |
|------|-----------|-----------------|
| 메이저 릴리스 | 연 2회 | 연 1회 |
| LTS 대상 | 짝수 버전만 | 모든 메이저 |
| 단계 | Current 6개월, LTS 30개월(짝수) | Alpha 6개월, Current 6개월, LTS 30개월 |
| 지원 기간 | 짝수 버전은 Current 6개월 + LTS 30개월 | 첫 Current 릴리스부터 EOL까지 36개월 |

새 단계의 시기는 다음과 같습니다.

- Alpha: 10월–3월(6개월). 27의 Alpha는 2026년 10월에 시작합니다.
- Current: 4월–10월(6개월). 27은 2027년 4월에 릴리스됩니다.
- LTS: 10월부터 30개월.
- Alpha는 semver-major의 깨지는 변경도 허용하는 채널이며 `27.0.0-alpha.1` 같은 버전을 씁니다. 서명·태그된 릴리스를 CITGM으로 테스트하므로 라이브러리 작성자와 CI가 호환성을 미리 확인하는 용도입니다.
- 26은 이전 방식의 마지막 릴리스입니다. 공지는 2026년 4월 릴리스로, 릴리스 표는 최초 릴리스를 5월 5일로 적고 있으며, 2026년 10월에 LTS로 들어가고 EOL은 2029년 4월입니다.
- 25, 24, 22는 영향을 받지 않고 기존 일정대로 EOL까지 갑니다. 릴리스 표에서 25와 20은 EOL이고 24(Krypton)와 22(Jod)는 LTS, 26은 Current입니다.

운영 지침은 달라지지 않습니다. 공식 일정 페이지는 프로덕션 애플리케이션이 Active LTS나 Maintenance LTS만 쓰라고 안내합니다. 새 체계에서는 홀수·짝수 구분이 사라지므로, 버전 번호가 아니라 지금 LTS 단계인지를 기준으로 고릅니다. 버전은 `.nvmrc`, `engines`, 베이스 이미지 태그로 고정하고(기초 02편, 09편), EOL 전에 다음 LTS로 옮길 일정을 잡습니다.

**흔한 실수:** 새 일정이 이미 모든 버전에 적용된다고 보는 것(27부터), 26의 LTS 전환 전후를 헷갈리는 것(2026년 10월 전환 예정), EOL이 지난 버전을 계속 쓰는 것입니다.

## 핵심 정리

- 권한 모델(`--permission`)은 Stable이지만 신뢰하는 코드의 실수를 막는 안전벨트이고 악성 코드를 막는 샌드박스가 아니며, `--allow-net`은 v25.0.0 추가의 1.1 단계입니다.
- SEA는 안정성 1.1이고 스크립트 하나만 넣으므로 번들링이 필요하며, `--build-sea`는 v25.5.0부터입니다.
- `node:sqlite`는 플래그 없이 쓰지만 1.2 단계의 동기 API라 서버의 핵심 저장소에는 조심합니다.
- 내장 테스트·`--watch`·`--env-file`은 Stable이고, 타입 스트립은 타입을 검사하지 않고 지울 수 있는 문법만 허용합니다.
- `require(esm)`은 최상위 `await`가 없는 모듈에만 되고, `fetch`·웹 스트림·WebCrypto는 Stable이며 `EventSource`·`URLPattern`은 실험입니다.
- Bun·Deno는 Node 호환 범위와 보안·도구 설계가 다르고, WinterTC는 서버 런타임의 공통 웹 API를 정하는 초안 단계의 표준이며, Node.js 27부터 연 1회 릴리스와 전체 LTS로 바뀝니다.

## API 버전 관리

API 버전 관리는 이미 쓰이는 API를 바꿀 때 기존 클라이언트가 깨지지 않게 변경을 나눠 내보내는 방식입니다. 서버와 클라이언트를 한꺼번에 배포할 수 없을 때(모바일 앱, 외부 연동) 필요합니다.

먼저 그 변경이 기존 클라이언트를 깨는지 가릅니다. 호환되는 변경은 버전을 올리지 않습니다.

| 호환되는 변경 | 깨지는 변경 |
|---------------|-------------|
| 응답에 필드 추가 | 필드 삭제·이름 변경·타입 변경 |
| 선택 파라미터 추가 | 필수 파라미터 추가 |
| 새 엔드포인트 추가 | 상태 코드·에러 형식 변경 |
| 열거형 값 추가(클라이언트가 모르는 값을 견딜 때만) | 기존 필드 의미 변경 |

버전을 표시하는 자리는 세 가지입니다.

| 방식 | 예 | 특징 |
|------|----|------|
| URL 경로 | `/v2/orders` | 눈에 보이고 라우팅이 쉬움. 리소스 URL이 버전마다 달라짐 |
| 요청 헤더 | `Stripe-Version: 2026-09-30.endive` | URL 고정. 캐시·테스트에서 헤더를 챙겨야 함 |
| 미디어 타입 | `Accept: application/vnd.acme.v2+json` | 콘텐츠 협상과 맞지만 도구 지원이 약함 |

Stripe는 날짜 기반 버전을 `Stripe-Version` 헤더로 지정하고, 계정이 쓰는 기본 버전을 고정해 둡니다. 2024-09-30.acacia 릴리스부터는 매달 깨지는 변경 없는 버전을 내고, 깨지는 변경은 연 두 번 메이저 릴리스로만 냅니다. 한 가지 정답이 있는 것이 아니라 한 번 정한 방식을 일관되게 유지하는 것이 중요합니다.

폐기는 헤더로 알립니다.

```http
Deprecation: @1688169599
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
Link: <https://example.com/migrate>; rel="deprecation"
```

- `Deprecation`(RFC 9745)은 리소스가 폐기되었거나 폐기될 시점을 구조화 필드 날짜(`@` 뒤 유닉스 초)로 알립니다. 동작은 바꾸지 않는 정보용입니다.
- `Sunset`(RFC 8594)은 리소스가 응답하지 않게 될 것으로 예상되는 시점을 HTTP 날짜로 알립니다. 보장이 아니라 힌트입니다.
- 폐기 전에 사용 현황(버전별 호출 수, 클라이언트별 호출 수)을 지표로 보고, 호출이 남은 클라이언트에 연락한 뒤 닫습니다(지표는 11편).

**흔한 실수:** 호환되는 변경까지 버전을 올려 버전이 늘어나는 것, 그리고 구버전을 닫는 날짜 없이 영원히 유지하는 것입니다. 버전마다 테스트·문서·운영 비용이 듭니다.

## 페이지네이션(offset·cursor)

페이지네이션은 큰 목록을 한 번에 주지 않고 나눠서 응답하는 방식입니다. 두 방식이 있습니다.

| 항목 | offset | cursor(keyset) |
|------|--------|----------------|
| 요청 | `?limit=20&offset=40` | `?limit=20&cursor=abc` |
| 임의 페이지로 이동 | 가능 | 불가능(앞뒤로만) |
| 깊은 페이지의 비용 | 커짐 | 일정함(인덱스 사용) |
| 페이지 사이 데이터 변경 | 중복·누락 발생 | 영향 적음 |
| 적합한 곳 | 관리자 화면, 총 페이지 수 표시 | 무한 스크롤, 피드, 대량 순회 |

offset은 `LIMIT n OFFSET m`으로 구현합니다. PostgreSQL 문서는 OFFSET이 건너뛰는 행도 서버 안에서 계산해야 하므로 큰 OFFSET은 비효율적일 수 있다고 적습니다. 또 `LIMIT`을 쓸 때는 결과를 유일한 순서로 정하는 `ORDER BY`가 있어야 하고, 없으면 페이지마다 일관되지 않은 결과가 나옵니다.

cursor는 직전 페이지 마지막 행의 정렬 키를 "여기서부터 다음"의 기준으로 씁니다. 정렬 키가 겹칠 수 있으므로 유일한 열(id)을 함께 씁니다.

```sql
SELECT id, created_at, title FROM posts
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 21; -- 요청이 limit 20이면 하나 더 읽음
```

한 건을 더 읽어 다음 페이지가 있는지 판단합니다. 커서는 클라이언트가 해석하지 못하게 불투명한 문자열로 만듭니다.

```js
const encode = (row) =>
  Buffer.from(JSON.stringify([row.created_at, row.id]))
    .toString('base64url');
const decode = (cursor) =>
  JSON.parse(Buffer.from(cursor, 'base64url').toString());

const rows = await query(sql, [...decode(cursor)]);
const hasNext = rows.length > 20;
const items = rows.slice(0, 20);
const next = hasNext ? encode(items.at(-1)) : null;
```

- 응답에는 `items`와 `nextCursor`를 담거나, `Link` 헤더에 `rel="next"`·`rel="prev"`를 넣습니다(RFC 8288에 등록된 관계 이름).
- 커서 안에 권한 정보를 넣지 않습니다. 디코딩한 값은 반드시 다시 검증하고 SQL에는 바인딩으로 넘깁니다(보안은 07편).
- 정렬 기준이 바뀔 수 있는 목록(점수순)은 커서에 그 값을 포함하고 id를 보조 키로 둡니다.
- 총 개수가 필요하면 별도 비용이 듭니다. 매 요청마다 `COUNT(*)`를 세지 말고 필요한 화면에서만, 또는 근사값으로 줍니다.

**흔한 실수:** 정렬 기준에 유일하지 않은 열만 써서 페이지 경계에서 행이 빠지거나 중복되는 것, 그리고 `limit`에 상한을 두지 않아 한 번에 전체를 가져가게 하는 것입니다.

## 멱등 키

멱등 키(idempotency key)는 클라이언트가 요청마다 붙이는 고유 값으로, 서버가 같은 요청의 재시도를 알아보고 한 번만 처리하게 하는 장치입니다. HTTP에서 GET·PUT·DELETE는 정의상 멱등이지만 POST는 아닙니다(RFC 9110). 결제·주문 생성 같은 POST가 타임아웃으로 재시도되면 두 번 실행될 수 있어서 키가 필요합니다.

```http
POST /payments
Idempotency-Key: 8f1e4c2a-7b3d-4e6f-9a10-2c5d8e7b1a34
```

서버 동작은 다음과 같습니다.

1. 키가 처음이면 요청을 처리하고 결과(상태 코드와 본문)를 키와 함께 저장합니다.
2. 같은 키가 다시 오면 처리하지 않고 저장한 결과를 그대로 돌려줍니다.
3. 같은 키인데 요청 내용이 다르면 오류로 거절합니다.
4. 같은 키의 첫 요청이 아직 처리 중이면 거절하거나 기다리게 합니다.

```js
const saved = new Map(); // 운영에서는 DB·Redis
async function once(key, body, handler) {
  const fp = JSON.stringify(body);
  const hit = saved.get(key);
  if (hit && hit.fp !== fp) return { status: 422 };
  if (hit?.result) return hit.result; // 저장된 응답 재사용
  if (hit) return { status: 409 };    // 처리 중
  saved.set(key, { fp });
  const result = await handler(body);
  saved.set(key, { fp, result });
  return result;
}
```

- IETF 인터넷 초안(draft-ietf-httpapi-idempotency-key-header)은 `Idempotency-Key`를 문자열 값의 헤더로 정의하고, 키 누락은 400, 다른 페이로드에 키를 재사용하면 422, 첫 요청이 진행 중이면 409를 권합니다. 이 초안은 RFC가 아니며, 확인한 07 버전은 만료된 상태입니다.
- Stripe는 첫 요청의 상태 코드와 본문을 키별로 저장해 성공·실패와 무관하게(500 포함) 재요청에 같은 결과를 줍니다. 키는 최대 255자이고 24시간이 지나면 지울 수 있으며, 파라미터가 다르면 오류를 냅니다. 모든 POST가 키를 받고 GET·DELETE에는 효과가 없습니다.
- 키는 클라이언트가 만듭니다. 충돌하지 않는 UUID v4 같은 무작위 값을 쓰고 이메일 같은 개인 정보는 쓰지 않습니다.
- 위 코드는 인스턴스 하나의 메모리에서만 동작합니다. 여러 인스턴스에서는 DB의 유니크 제약이나 Redis의 `SET NX`로 키 선점을 원자적으로 해야 합니다(재시도 전략과 함께 14편).

**흔한 실수:** 결과를 저장하지 않고 "처리했다"는 표시만 남겨서 재시도에 다른 응답을 주는 것, 키를 서버가 만들어 매번 새로 발급하는 것(재시도를 알아볼 수 없음), 만료 정책이 없어 저장소가 계속 커지는 것입니다.

## rate limit 알고리즘

rate limit은 클라이언트별로 단위 시간당 요청 수를 제한해 서버를 보호하고 사용을 공평하게 나누는 장치입니다. 개념과 보안 쪽 이야기는 07편, Redis 구현은 중급 18편에서 다루고, 여기서는 알고리즘을 비교합니다.

| 알고리즘 | 동작 | 장점 | 단점 |
|----------|------|------|------|
| fixed window | 고정 구간(예: 1분)별 카운터, 한도 초과 시 거절 | 구현이 가장 쉬움 | 구간 경계에서 순간 두 배까지 허용 |
| sliding window | 최근 N초의 요청 수를 셈 | 경계 문제 없음 | 로그 방식은 저장이 크고, 카운터 방식은 근사값 |
| token bucket | 일정 속도로 토큰이 차고, 요청마다 토큰 소비 | 순간 몇 건의 버스트 허용 | 상태(토큰 수, 마지막 보충 시각) 저장 필요 |
| leaky bucket | 요청이 큐에 쌓이고 일정 속도로 처리 | 출력 속도가 일정 | 큐가 차면 거절, 지연이 생김 |

fixed window의 경계 문제는 한도가 분당 100일 때 12:00:59에 100건, 12:01:00에 100건이 오면 1초 사이 200건이 통과하는 것입니다. Redis 문서의 `INCR`와 `EXPIRE`를 쓰는 분 단위 키 방식이 이 fixed window입니다.

token bucket을 메모리에서 구현하면 다음과 같습니다.

```js
function createBucket(capacity, refillPerSec) {
  let tokens = capacity;
  let last = Date.now();
  return function tryTake() {
    const now = Date.now();
    const added = ((now - last) / 1000) * refillPerSec;
    tokens = Math.min(capacity, tokens + added);
    last = now;
    if (tokens < 1) return false; // 거절
    tokens -= 1;
    return true;
  };
}
```

- 키(IP, 사용자 ID, API 키)마다 버킷을 따로 둡니다. IP만 키로 쓰면 NAT 뒤의 많은 사용자가 한 묶음이 되고, 프록시 뒤에서는 `X-Forwarded-For`를 신뢰할 수 있는 프록시에서만 읽어야 합니다.
- 인스턴스가 여러 개이면 메모리 카운터는 인스턴스 수만큼 한도가 늘어납니다. Redis 같은 공유 저장소에서 원자적으로 갱신합니다.
- 초과 시 429 Too Many Requests(RFC 6585)로 응답하고 `Retry-After`로 대기 시간을 알립니다. 429 응답은 캐시하지 않습니다.
- 한도 정보를 알리는 헤더는 IETF 초안(draft-ietf-httpapi-ratelimit-headers)이 `RateLimit-Policy`와 `RateLimit`을 정의하고 있습니다. 확인한 시점(버전 11)에도 초안이므로, 널리 쓰이는 `X-RateLimit-*` 이름과 함께 운영 도구의 지원을 보고 고릅니다.
- 한도는 엔드포인트마다 다르게 둡니다. 로그인·결제 같은 민감한 경로는 더 엄격하게 둡니다.

**흔한 실수:** 클라이언트에게 한도 정보를 주지 않아 재시도 폭풍이 생기는 것입니다. 429를 받은 클라이언트는 `Retry-After`를 따르고 백오프와 지터를 적용해야 합니다(14편).

## 캐싱 헤더(ETag·Cache-Control)

HTTP 캐시는 응답을 저장해 재사용하는 장치이고, 서버는 헤더로 재사용 조건을 지정합니다. 두 축이 있습니다. 신선도(`Cache-Control`)는 재사용해도 되는 기간을, 검증(`ETag`)은 바뀌었는지 확인하는 방법을 정합니다.

`Cache-Control` 응답 지시어(RFC 9111)의 뜻은 다음과 같습니다.

| 지시어 | 뜻 |
|--------|----|
| `max-age=N` | N초 동안 신선하다고 간주 |
| `s-maxage=N` | 공유 캐시(CDN·프록시)에만 적용, `max-age`보다 우선 |
| `no-cache` | 저장은 하되 재사용 전에 반드시 서버에 검증 |
| `no-store` | 요청·응답 어느 쪽도 저장하지 않음 |
| `private` | 사용자 한 명의 캐시(브라우저)에만 저장 |
| `public` | 인증된 요청의 응답이라도 공유 캐시에 저장 가능 |
| `must-revalidate` | 낡은 뒤에는 검증에 성공하기 전까지 재사용 금지 |

`no-cache`는 "캐시하지 마라"가 아니라 "쓰기 전에 확인하라"입니다. 저장 자체를 막으려면 `no-store`입니다.

ETag는 표현의 버전을 나타내는 검증자입니다. 클라이언트가 `If-None-Match`에 받아 둔 ETag를 보내면, 서버는 같을 때 본문 없이 304 Not Modified로 답합니다(RFC 9110).

```js
import { createHash } from 'node:crypto';
function sendJson(req, res, data) {
  const body = JSON.stringify(data);
  const hash = createHash('sha1')
    .update(body).digest('base64url');
  const etag = `"${hash}"`;
  res.setHeader('ETag', etag);
  res.setHeader('Cache-Control', 'private, no-cache');
  if (req.headers['if-none-match'] === etag) {
    res.statusCode = 304;
    return res.end(); // 본문 없음
  }
  res.setHeader('Content-Type', 'application/json');
  res.end(body);
}
```

- ETag는 따옴표를 포함한 문자열입니다. `W/"..."`처럼 `W/`가 붙으면 약한 검증자로, 바이트가 같지는 않아도 의미가 같다는 뜻입니다.
- `If-Match`는 반대 방향입니다. 수정 요청에 현재 ETag를 보내고, 서버의 값과 다르면 412 Precondition Failed로 거절해 동시에 수정한 것을 덮어쓰지 않게 합니다(낙관적 동시성 제어).
- `Last-Modified`와 `If-Modified-Since`는 시각 기반의 검증 방식입니다.
- 304는 응답 생성 비용이 아니라 전송 비용을 줄입니다. 위 코드는 매번 본문을 만들므로 DB 조회는 줄지 않습니다. 버전 번호나 `updated_at`으로 ETag를 만들면 조회도 줄일 수 있습니다.

API에서 자주 쓰는 조합은 다음과 같습니다.

| 응답 | 헤더 |
|------|------|
| 사용자별 데이터 | `Cache-Control: private, no-cache` + ETag |
| 공개 목록(짧게 허용) | `Cache-Control: public, max-age=60` |
| 해시가 이름에 든 정적 파일 | `Cache-Control: public, max-age=31536000, immutable` |
| 민감 정보(토큰, 결제) | `Cache-Control: no-store` |

**흔한 실수:** 사용자별 응답에 `public`을 붙이거나 `private`을 빼서 CDN이 다른 사용자에게 내주는 것, 쿠키·`Authorization`에 따라 달라지는 응답에 `Vary`를 빠뜨리는 것입니다. 보안 헤더 전반은 07편에서 다룹니다. `immutable`은 신선한 동안 재검증 요청을 보내지 않아도 된다는 뜻의 지시어로 RFC 9111이 아니라 RFC 8246에 정의되어 있습니다.

## GraphQL 개요

GraphQL은 타입 시스템으로 정의한 스키마를 단일 엔드포인트로 노출하고, 클라이언트가 필요한 필드를 직접 골라 요청하는 쿼리 언어입니다. 공식 사이트가 "versionless API"를 장점으로 내세우는 이유는 필드를 추가해도 기존 쿼리가 영향받지 않기 때문입니다.

```graphql
query {
  user(id: "7") {
    name
    posts(first: 2) { title }
  }
}
```

- 연산은 세 종류입니다. query는 읽기, mutation은 쓰기, subscription은 실시간 푸시입니다.
- 스키마가 타입을 정의하고 introspection으로 스키마를 조회할 수 있어서 도구가 문서·자동 완성을 만듭니다.
- 해결하는 문제는 over-fetching(필요 없는 필드까지 받음)과 under-fetching(한 화면에 요청이 여러 번 필요함)입니다.
- 서버는 필드마다 resolver를 실행합니다. 목록의 각 항목에서 resolver가 DB를 따로 조회하면 N+1이 생기므로 짧은 시간 동안의 요청을 모아 한 번에 보내는 배치 기법(DataLoader)을 씁니다(N+1은 중급 17편).
- 단일 엔드포인트의 POST 중심이라 URL 단위 HTTP 캐시와 잘 맞지 않습니다. 객체 고유 ID로 클라이언트 캐시를 만들어 보완합니다.
- 클라이언트가 쿼리를 정하므로 비용을 미리 알기 어렵습니다. 공식 보안 안내는 쿼리 깊이 제한, 복잡도(비용) 분석, 비즈니스 로직 계층의 rate limit을 권합니다.
- 응답에 `data`가 있으면 `errors`가 함께 있어도 2xx로 응답하라는 것이 공식 안내입니다(HTTP에 부분 성공 코드가 없기 때문). 상태 코드만 보는 모니터링은 일부 필드의 실패를 놓칩니다. 실행 전 검증 오류는 보통 400입니다.
- POST는 모든 연산에 쓰고, GET은 query에만 쓸 수 있습니다. URL 길이 제한 때문에 긴 쿼리는 짧은 식별자로 대체하는 영속 문서(persisted documents)를 씁니다.
- 사양은 GraphQL Foundation이 관리하고, 확인한 시점의 최신 릴리스는 2025년 9월판입니다.

적합한 곳은 클라이언트 종류가 많고 화면마다 필요한 데이터가 달라 응답 모양을 서버가 미리 정하기 어려운 경우(BFF, 모바일 앱)입니다. 단순 CRUD이거나 파일 전송·캐시가 중요한 공개 API에는 REST가 간단합니다.

**흔한 실수:** 스키마를 DB 테이블 구조 그대로 노출하는 것, resolver마다 인가를 빠뜨리는 것, 깊이·비용 제한 없이 임의 쿼리를 운영에서 여는 것입니다. introspection을 닫는 것만으로는 부족하고(공식 안내는 이를 보안이 아닌 은폐로 봄) 인가가 근본 대책입니다.

## gRPC 개요

gRPC는 `.proto` 파일에 서비스와 메시지를 정의하고, 컴파일러로 클라이언트·서버 코드를 만들어 원격 메서드를 로컬 함수처럼 호출하는 RPC 프레임워크입니다. 직렬화는 기본이 Protocol Buffers(바이너리)이고, 전송은 HTTP/2입니다.

```proto
service Greeter {
  rpc SayHello (HelloRequest) returns (HelloReply);
}
message HelloRequest { string name = 1; }
message HelloReply { string message = 1; }
```

- 메서드 종류는 네 가지입니다. unary(요청 1, 응답 1), server streaming, client streaming, bidirectional streaming입니다.
- 메시지의 필드는 이름이 아니라 번호로 식별합니다. 번호를 유지하면 필드를 추가해도 구버전과 호환됩니다.
- 클라이언트가 deadline을 지정하고, 넘으면 `DEADLINE_EXCEEDED`(4)로 끝납니다. 취소는 양쪽 모두 언제든 할 수 있지만 이미 일어난 변경이 되돌려지지는 않습니다.
- 상태는 HTTP 상태 코드가 아니라 gRPC 상태 코드로 전달합니다. `INVALID_ARGUMENT`(3), `NOT_FOUND`(5), `PERMISSION_DENIED`(7), `UNAVAILABLE`(14), `UNAUTHENTICATED`(16) 등이 있고, 상태는 HTTP/2 트레일러의 `grpc-status`로 옵니다.
- 인증 정보 같은 부가 데이터는 메타데이터(키·값)로 보냅니다.
- 브라우저는 gRPC를 직접 호출하지 못합니다. gRPC-Web과 Envoy 같은 프록시가 필요합니다.
- Node.js에서는 `@grpc/grpc-js`로 서버·클라이언트를 만들고, `@grpc/proto-loader`로 `.proto`를 런타임에 읽을 수 있습니다.

적합한 곳은 서비스끼리 통신하는 내부 호출(마이크로서비스), 스트리밍, 다언어 환경입니다. 브라우저에 직접 공개하는 API, 사람이 curl로 확인해야 하는 API에는 불편합니다.

**흔한 실수:** deadline 없이 호출해서 하위 서비스 장애가 호출자 전체로 번지는 것(14편의 타임아웃), `UNAVAILABLE`과 `INVALID_ARGUMENT`를 구분하지 않고 모든 실패를 재시도하는 것입니다.

## tRPC

tRPC는 TypeScript 서버의 함수 타입을 클라이언트가 그대로 가져다 써서, 스키마 파일이나 코드 생성 없이 종단 간 타입 안전을 얻는 프레임워크입니다. 클라이언트는 서버 코드를 import하지 않고 라우터의 타입만 `import type`으로 가져옵니다.

```ts
// server
const appRouter = router({
  userById: publicProcedure
    .input(z.string())
    .query(({ input }) => db.user.find(input)),
});
export type AppRouter = typeof appRouter;
// client: createTRPCClient<AppRouter>(...)
```

- 서버가 정의한 procedure는 query(읽기)와 mutation(쓰기)로 나뉘고, 입력 검증에는 Zod 같은 검증 라이브러리를 씁니다.
- 서버 타입이 바뀌면 클라이언트의 컴파일이 즉시 깨져서 계약 불일치를 빌드 때 발견합니다.
- 서버와 클라이언트가 같은 저장소(모노레포)에서 TypeScript로 함께 배포될 때 가장 효과가 큽니다(모노레포는 12편).
- 공식 문서가 밝히듯, 비 TypeScript 클라이언트가 쓰는 공개 API나 프런트엔드·백엔드가 느슨하게 분리된 구조에는 맞지 않습니다. 그 경우 REST와 OpenAPI, 또는 GraphQL을 씁니다.
- 스키마가 계약 문서 구실을 하지 않으므로 외부에 공개할 때는 별도의 문서화가 필요합니다.

방식 선택은 다음처럼 정리합니다.

| 상황 | 선택 |
|------|------|
| 외부 공개, 다양한 클라이언트, HTTP 캐시 | REST + OpenAPI |
| 화면마다 필요한 필드가 다른 클라이언트 | GraphQL |
| 내부 서비스 간 호출, 스트리밍 | gRPC |
| 같은 저장소의 TypeScript 서버와 클라이언트 | tRPC |

## 웹훅 설계와 서명 검증

웹훅(webhook)은 서버가 이벤트가 일어났을 때 상대가 등록한 URL로 HTTP POST를 보내 알리는 방식입니다. 상대가 계속 조회(polling)하지 않아도 됩니다. 받는 쪽은 URL만 열어 두므로 누구든 그 URL로 요청을 보낼 수 있고, 그래서 서명 검증이 필요합니다.

보내는 쪽은 비밀 키로 본문을 서명해 헤더에 넣습니다. 받는 쪽은 같은 계산을 해서 비교합니다. 두 가지 사양이 있습니다.

| 항목 | GitHub | Standard Webhooks |
|------|--------|-------------------|
| 서명 헤더 | `X-Hub-Signature-256` | `webhook-signature` |
| 알고리즘 | HMAC-SHA256 | HMAC-SHA256 |
| 값 형식 | `sha256=` 뒤에 16진수 | `v1,` 뒤에 base64(공백으로 여러 개 구분) |
| 서명 대상 | 본문 원문 | `webhook-id.webhook-timestamp.본문` |
| 재전송 방지 | 사양에 없음 | `webhook-timestamp`를 허용 오차 안에서만 인정 |

GitHub 방식으로 받는 쪽 검증은 다음과 같습니다.

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

function verify(secret, rawBody, header) {
  const mac = createHmac('sha256', secret).update(rawBody);
  const expected = 'sha256=' + mac.digest('hex');
  const a = Buffer.from(header ?? '');
  const b = Buffer.from(expected);
  return a.length === b.length && timingSafeEqual(a, b);
}
// rawBody: 파싱 전의 Buffer. JSON.parse 후 다시 직렬화한 값은 안 됨
```

- 서명은 파싱하기 전의 바이트 원문에 대해 계산합니다. JSON으로 읽었다가 다시 문자열로 만들면 공백·키 순서가 달라져 검증에 실패합니다.
- 비교는 `===`가 아니라 `crypto.timingSafeEqual`로 합니다. 두 값의 길이가 다르면 이 함수가 예외(`ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH`)를 던지므로 길이를 먼저 확인합니다(HMAC은 중급 21편).
- 같은 요청을 다시 보내는 공격은 서명만으로 막지 못합니다. 서명 대상에 타임스탬프를 넣고 허용 오차(예: 몇 분)를 넘은 요청을 거절하며, 이벤트 ID를 저장해 중복을 걸러냅니다. 사양은 허용 오차의 값을 정하지 않습니다.
- 비밀 키는 엔드포인트마다 따로 두고, 교체할 수 있게 서명 여러 개를 허용합니다. 코드에 넣지 않고 비밀값 관리 서비스에 둡니다(07편).

보내는 쪽 설계에서 정할 것은 다음과 같습니다.

- 전달은 최소 한 번(at-least-once)이 현실적입니다. 받는 쪽이 같은 이벤트를 여러 번 받을 수 있으므로 이벤트 ID를 넣고 받는 쪽은 멱등하게 처리합니다.
- 2xx는 성공, 그 밖은 실패로 보고 재시도합니다. Standard Webhooks는 3xx를 실패로 보고 리다이렉트를 따라가지 않으며, 410 Gone이면 엔드포인트를 비활성화하고, 429·502·504에는 전송 속도를 낮추라고 안내합니다.
- 재시도는 지수 백오프로 합니다. 사양의 예시는 즉시, 5초, 5분, 30분, 2시간 순으로 늘어나 75시간 이상에 걸칩니다(14편). 계속 실패하는 엔드포인트는 비활성화하고 알립니다.
- 이벤트는 순서가 보장되지 않습니다. 받는 쪽은 이벤트의 타임스탬프나 버전을 보고 오래된 것을 무시하거나, 알림만 받고 최신 상태를 API로 다시 조회합니다.
- 사용자가 등록한 URL로 서버가 요청을 보내므로 내부망 주소를 막는 SSRF 방어가 필요합니다(SSRF는 중급 11편).

받는 쪽은 서명을 검증하고 이벤트를 큐에 넣은 뒤 즉시 2xx를 돌려줍니다. 처리가 길어지면 보내는 쪽이 타임아웃으로 보고 재전송합니다(큐는 14편).

**흔한 실수:** 파싱한 본문으로 서명을 검증하는 것, 서명 검증 없이 URL이 비공개라는 것만 믿는 것, 이벤트 중복 처리를 하지 않아 같은 주문을 두 번 처리하는 것입니다.

## OpenAPI 문서화

OpenAPI는 HTTP API를 사람과 도구가 모두 읽는 형식(YAML 또는 JSON)으로 기술하는 사양입니다. 경로, 파라미터, 요청·응답 본문, 인증을 적어 두면 문서, 클라이언트 코드, 목(mock) 서버, 검증기를 도구가 만듭니다. 사양 사이트가 확인한 시점의 최신판은 3.2.1이고 3.1 계열도 유지됩니다.

최상위 필드는 다음과 같습니다.

| 필드 | 내용 |
|------|------|
| `openapi` | 사양 버전(필수) |
| `info` | 제목·버전 등 메타데이터(필수) |
| `paths` | 경로와 연산 |
| `components` | 재사용할 스키마·응답·파라미터·보안 방식 |
| `webhooks` | API가 보내는 웹훅 설명 |
| `servers`, `security`, `tags` | 서버 주소, 인증 요구, 분류 |

```yaml
openapi: 3.1.0
info: { title: Orders API, version: 1.0.0 }
paths:
  /orders/{id}:
    get:
      parameters:
        - { name: id, in: path, required: true,
            schema: { type: string } }
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
```

- 스키마는 JSON Schema(2020-12)를 따르는 Schema Object입니다. 같은 모양은 `$ref`로 `components`에 한 번만 정의합니다.
- 오류 응답 형식은 RFC 9457의 `application/problem+json`을 스키마로 정의해 모든 연산에서 재사용합니다. 표준 멤버는 `type`, `title`, `status`, `detail`, `instance`이고, 알 수 없는 확장 멤버는 클라이언트가 무시해야 합니다. `status`는 참고용이며 실제 HTTP 상태 코드와 같아야 합니다.
- 문서를 만드는 두 방향이 있습니다. 문서를 먼저 쓰고 코드를 맞추는 계약 우선(design-first)과, 코드의 데코레이터나 스키마에서 문서를 뽑는 코드 우선(code-first)입니다. NestJS의 Swagger 모듈이 코드 우선의 예입니다(중급 15편).
- 문서와 구현이 어긋나는 것이 가장 큰 문제입니다. CI에서 문서로 요청·응답을 검증하는 계약 테스트를 돌리고, 이전 버전과 비교해 깨지는 변경을 자동으로 찾습니다(CI는 09편).
- 문서에는 예시 값, 오류 응답, 인증 방법, 각 에러 코드의 의미를 반드시 적습니다.

**흔한 실수:** 성공 응답만 적고 4xx·5xx를 빼는 것, 문서를 손으로만 관리해 구현과 어긋나는 것, 문서를 바꾸고 버전은 그대로 두는 것입니다.

## 핵심 정리

- 호환되는 변경(필드 추가)은 버전을 올리지 않고, 깨지는 변경만 버전으로 나눕니다. 폐기는 `Deprecation`·`Sunset` 헤더와 사용 현황 지표로 진행합니다.
- 큰 목록은 cursor(keyset)로 나눕니다. offset은 깊어질수록 비싸고 페이지 사이 변경에 중복·누락이 생기며, 두 방식 모두 유일한 정렬 기준과 `limit` 상한이 필요합니다.
- POST 재시도는 멱등 키로 막습니다. 첫 결과를 저장해 돌려주고, 다른 내용의 같은 키는 거절하며, 여러 인스턴스에서는 원자적 선점이 필요합니다.
- rate limit은 fixed window, sliding window, token bucket, leaky bucket 중 버스트 허용 여부로 고르고, 초과하면 429와 `Retry-After`로 답합니다.
- `no-cache`는 검증 후 재사용, `no-store`는 저장 금지이며 ETag와 `If-None-Match`는 304로 전송량을, `If-Match`는 412로 덮어쓰기를 막습니다.
- 웹훅은 원문 바이트에 HMAC-SHA256 서명을 검증하고, 상수 시간 비교와 타임스탬프·이벤트 ID 검사로 재전송과 중복을 막은 뒤 큐에 넣고 즉시 2xx로 답합니다.

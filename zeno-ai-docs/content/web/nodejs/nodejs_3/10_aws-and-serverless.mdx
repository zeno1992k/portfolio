## EC2·ECS·Fargate·Lambda 비교

네 가지는 "누가 어디까지 관리하는가"가 다릅니다. 09편에서 만든 컨테이너 이미지는 ECS(Fargate 또는 EC2)에서 실행하고, 이미지 없이 함수 코드만 올리면 Lambda입니다.

| 항목 | EC2 | ECS on EC2 | ECS on Fargate | Lambda |
|------|-----|------------|----------------|--------|
| 실행 단위 | 가상 서버(인스턴스) | 컨테이너(태스크) | 컨테이너(태스크) | 함수 |
| 서버 관리 | 인스턴스 유형·OS·용량을 직접 관리 | 인스턴스 유형·수·용량을 직접 관리 | 서버 관리 없음 | 서버 관리 없음 |
| 실행 시간 | 제한 없음 | 제한 없음 | 제한 없음 | 호출당 최대 15분 |
| 프로세스 | 상시 실행 | 상시 실행(서비스) 또는 일회성(태스크) | 상시 실행(서비스) 또는 일회성(태스크) | 요청이 올 때 실행 |
| 확장 | Auto Scaling 구성 | 서비스 오토스케일링과 인스턴스 용량 | 서비스 오토스케일링 | 요청 수에 따라 자동 |
| 과금 | 인스턴스 시간 | 인스턴스 시간 | 사용한 자원 기준 종량 | 호출과 실행 시간 기준 |

- EC2는 가상 서버입니다. 인스턴스 유형이 CPU·메모리·네트워크·스토리지 구성을 정하고, AMI로 OS와 소프트웨어 구성을 고릅니다. 보안 그룹은 인스턴스 앞의 가상 방화벽입니다.
- ECS는 컨테이너 오케스트레이션 서비스입니다. 용어는 세 가지입니다. 태스크 정의는 애플리케이션의 설계도, 태스크는 일을 하고 끝나는 단위(배치 작업 등), 서비스는 계속 실행되는 무상태 애플리케이션입니다. 컨테이너가 실제로 도는 인프라(capacity)는 EC2 인스턴스, Fargate, 온프레미스 중에서 고릅니다.
- Fargate는 서버리스 종량제 컴퓨트 엔진입니다. 서버 관리, 용량 계획, 컨테이너 격리를 직접 하지 않습니다. 롤링·블루그린 배포는 09편에서 다룬 ECS 방식 그대로 쓰입니다.
- Lambda는 함수를 올리면 요청이 올 때 실행 환경을 만들어 실행합니다. 용량 계획이 필요 없지만 호출당 제한(시간·페이로드·크기)을 지켜야 합니다.

| 상황 | 기본 선택 |
|------|-----------|
| 긴 연결(WebSocket)과 상시 서버가 필요한 API | ECS on Fargate |
| 트래픽이 들쭉날쭉하고 요청 단위로 끝나는 작업 | Lambda |
| 특정 인스턴스 유형(GPU 등)이나 OS 설정 제어 | EC2 또는 ECS on EC2 |
| 컨테이너 이미지로 이미 패키징한 서비스 | ECS on Fargate |

**흔한 실수:** 기존 Express 서버를 그대로 Lambda에 옮기는 것입니다. 서버가 항상 떠 있다는 가정(메모리 캐시, 장기 연결, 백그라운드 작업)이 깨지고, 호출당 실행 시간 제한에도 걸립니다.

## Lambda 핸들러와 콜드 스타트

### 핸들러

Lambda가 호출 때 실행하는 함수가 핸들러입니다. 설정값 `Handler`는 "파일 이름.내보낸 함수 이름"입니다. 콘솔이 만드는 기본값은 `index.handler`이고, `index.mjs`가 내보낸 `handler`를 가리킵니다.

```js
import { S3Client, PutObjectCommand }
  from '@aws-sdk/client-s3'

const s3 = new S3Client() // 초기화 단계에서 한 번만 실행
const bucket = process.env.RECEIPT_BUCKET

export const handler = async (event) => {
  await s3.send(new PutObjectCommand({
    Bucket: bucket,
    Key: `receipts/${event.orderId}.txt`,
    Body: `item: ${event.item}`,
  }))
  return { ok: true } // JSON으로 직렬화되어 호출자에게 전달
}
```

- 지원 런타임은 `nodejs26.x`, `nodejs24.x`, `nodejs22.x`이고 OS는 Amazon Linux 2023입니다. 지원 종료(deprecation) 예정일은 `nodejs24.x`가 2028-04-30, `nodejs22.x`가 2027-04-30입니다.
- 핸들러는 `async` 함수를 권장합니다. 인수는 `event`(입력 데이터)와 `context`(호출·함수·실행 환경 정보)입니다.
- 콜백 방식 핸들러(`event, context, callback`)는 Node.js 22까지만 지원합니다. Node.js 24부터는 비동기 작업을 `async` 핸들러로 작성합니다.
- 응답 스트리밍 핸들러는 `awslambda.streamifyResponse()`로 감싸며 인수가 `event`, `responseStream`, `context` 세 개입니다.
- ES Modules를 권장합니다. `.mjs` 확장자를 쓰거나 `package.json`에 `type`을 `module`로 지정합니다. Lambda는 `.js`를 CommonJS로 다룹니다. ES 모듈이어야 최상위 `await`를 쓸 수 있습니다.
- Lambda는 Node.js의 실험 기능 두 가지(ES 모듈에서 `require`, 모듈 형식 자동 감지)를 기본으로 끕니다. 켜려면 `NODE_OPTIONS`에 `--experimental-require-module` 또는 `--experimental-detect-module`을 지정하며, 켠 함수는 SLA와 지원 대상에서 빠집니다.
- 런타임에는 AWS SDK v3의 특정 마이너 버전이 포함되어 있지만 최신이 아닙니다. 호환성을 위해 필요한 SDK 클라이언트(`@aws-sdk/client-s3` 등)를 배포 패키지에 직접 넣는 것을 권장합니다.
- 환경변수는 `process.env`로 읽고, 전체 합이 4KB를 넘을 수 없습니다.

핸들러에서 핵심 로직을 분리하면 단위 테스트가 쉽습니다. 핸들러는 입력을 풀고 응답을 만드는 얇은 층으로 둡니다.

### 콜드 스타트

실행 환경의 수명은 Init, Invoke, Shutdown 단계입니다. Init에서는 확장 기능을 시작하고, 런타임을 준비하고, 핸들러 밖의 코드(import, SDK 클라이언트 생성)를 실행합니다. 새 실행 환경을 만들 때 코드 내려받기와 환경 준비, 초기화 코드 실행에 드는 시간이 콜드 스타트입니다. 이미 만들어진 환경을 재사용하는 호출이 웜 스타트입니다. 문서는 콜드 스타트가 보통 호출의 1퍼센트 미만에서 발생하고 100밀리초 미만에서 1초 이상까지 걸린다고 설명합니다.

- Init 단계는 10초로 제한됩니다. 이 제한은 프로비저닝된 동시성과 SnapStart를 쓰는 함수에는 적용되지 않습니다.
- 핸들러 밖에 만든 객체는 환경이 재사용되는 동안 유지됩니다. SDK 클라이언트와 DB 연결을 핸들러 밖에서 초기화하면 호출마다 다시 만들지 않습니다. 연결이 이미 있는지 확인하는 코드를 둡니다.
- `/tmp`는 512MB에서 10,240MB 사이이고 환경이 얼려져 있는 동안 내용이 남아 임시 캐시로 쓸 수 있습니다.
- Lambda는 연속 호출되는 함수라도 몇 시간마다 실행 환경을 종료합니다. 환경이 영구히 유지된다고 가정하면 안 됩니다.
- 호출 하나가 끝나면 환경이 얼려지고, 끝나지 않은 백그라운드 작업은 다음 재사용 때 이어서 실행됩니다. 코드가 끝나기 전에 모든 비동기 작업을 마칩니다.
- 사용자 데이터나 보안 정보를 환경의 전역 상태에 저장하지 않습니다. 호출 사이에 데이터가 새어 나갈 수 있습니다.
- 환경 초기화 중에 시작한 비동기 작업이 Init 안에 끝나지 않으면 첫 호출에서 값이 비어 있는 등 예기치 않은 동작이 생깁니다. ES 모듈의 최상위 `await`로 Init 안에서 끝냅니다.

```js
const config = await loadConfigFromParameterStore()
// Init 단계에서 완료되므로 핸들러가 항상 값을 가진다
export const handler = async () => ({ mode: config.mode })
```

콜드 스타트를 줄이는 방법은 다음과 같습니다.

| 방법 | 효과 |
|------|------|
| 의존성과 패키지 크기 줄이기 | 코드 내려받기와 초기화 시간 감소 |
| 필요한 SDK 클라이언트만 import | 초기화 코드 감소 |
| 프로비저닝된 동시성 | 지정한 수의 실행 환경을 미리 초기화(추가 요금) |
| 함수 분리 | 함수마다 초기화할 객체 수 감소 |

동시성은 동시에 처리 중인 요청 수입니다. 계산식은 평균 초당 요청 수에 평균 요청 시간(초)을 곱한 값입니다. 초당 100건이고 요청당 0.5초이면 동시성은 50입니다. 기본 계정 한도는 리전당 1,000이고, 초당 요청 한도는 동시성 한도의 10배입니다.

| 항목 | 예약된 동시성 | 프로비저닝된 동시성 |
|------|----------------|---------------------|
| 뜻 | 함수가 쓸 수 있는 동시성의 상한(동시에 하한) | 미리 초기화해 둔 실행 환경 수 |
| 콜드 스타트 | 생길 수 있음 | 미리 초기화된 범위에서는 없음 |
| 추가 요금 | 없음 | 있음 |

- 예약된 동시성은 다른 함수가 그 몫을 쓰지 못하게 하고, 함수가 DB 같은 하위 자원을 과부하시키지 않도록 상한을 거는 용도로도 씁니다.
- 주요 제한: 호출 시간 900초, 메모리 128–10,240MB(CPU는 메모리에 비례, 1,769MB가 vCPU 1개), 동기 호출 요청·응답 각 6MB, zip 배포 패키지 압축 해제 후 250MB, 컨테이너 이미지 10GB.

**흔한 실수:**

- 요청마다 SDK 클라이언트나 DB 연결을 핸들러 안에서 새로 만드는 것입니다. 핸들러 밖에서 한 번 만듭니다.
- 핸들러 안에서 시작한 비동기 작업을 `await`하지 않고 반환하는 것입니다. 작업이 끝나기 전에 환경이 얼려지고, 다음 재사용 때 뒤늦게 이어져 실행됩니다.

## API Gateway와 ALB

Lambda를 HTTP로 호출하게 하는 대표적인 두 가지입니다. 둘 다 요청을 JSON 이벤트로 바꿔 함수에 넘기고, 함수의 반환값을 HTTP 응답으로 바꿉니다.

| 항목 | API Gateway REST API | API Gateway HTTP API | ALB(Lambda 대상) |
|------|----------------------|----------------------|------------------|
| 성격 | 기능이 많은 API 제품 | 최소 기능으로 더 낮은 가격 | 로드 밸런서에 Lambda를 대상으로 등록 |
| API 키·사용량 계획·클라이언트별 제한 | 지원 | 미지원 | 해당 없음 |
| 요청 검증·캐시·WAF | 지원 | 미지원 | WAF는 ALB 쪽에서 구성 |
| JWT 인증기 | 미지원(Lambda 인증기로 대체) | 지원 | 해당 없음 |
| 페이로드 | Lambda 동기 호출 한도(요청·응답 각 6MB) 이내 | 같음 | 요청·응답 각 1MB |
| WebSocket | 해당 없음 | 해당 없음 | 미지원(업그레이드 요청을 400으로 거부) |

- API Gateway 문서의 선택 기준은 이렇습니다. API 키, 클라이언트별 제한, 요청 검증, AWS WAF 연동, 프라이빗 엔드포인트가 필요하면 REST API를, 그런 기능이 필요 없으면 HTTP API를 씁니다.
- HTTP API의 Lambda 연동에는 페이로드 형식 버전 1.0과 2.0이 있습니다. 2.0은 `multiValueHeaders`가 없고 중복 헤더를 쉼표로 합치며 `rawPath`와 `cookies` 필드가 있습니다.
- 2.0에서는 함수가 `statusCode` 없는 유효한 JSON을 반환하면 API Gateway가 상태 코드 200, `application/json`으로 간주해 응답을 만듭니다. 상태 코드와 헤더를 직접 정하려면 객체로 반환합니다.

```js
export const handler = async (event) => {
  const id = event.pathParameters?.id
  return {
    statusCode: id ? 200 : 400,
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ id }),
  }
}
```

- ALB는 Lambda를 대상 그룹의 대상으로 등록하고 리스너 규칙으로 요청을 전달합니다. 네트워크 연결이 아니라 직접 호출이라서 ALB 보안 그룹의 아웃바운드 규칙이 필요 없습니다.
- ALB 응답은 `isBase64Encoded`, `statusCode`, `headers`를 반드시 포함해야 하고 본문은 생략할 수 있습니다. 바이너리 본문은 Base64로 인코딩하고 `isBase64Encoded`를 `true`로 둡니다.
- 같은 헤더나 쿼리 키가 여러 번 올 때 다중값 헤더 설정을 켜지 않으면 마지막 값만 전달됩니다.
- 대상 그룹의 Lambda는 별칭(alias) ARN으로 등록해야 함수를 바꿔도 ALB가 현재 버전을 호출합니다. 대상 그룹당 함수는 하나입니다.
- 대상 그룹의 헬스체크는 기본으로 꺼져 있습니다. 켜면 헬스체크도 Lambda 호출이 되어 요금이 부과됩니다.
- 상시 서버를 ECS에 둘 때는 ALB 뒤에 태스크를 대상으로 등록합니다. 09편에서 다룬 `/health` 같은 엔드포인트를 ALB 헬스체크에 씁니다.

**흔한 실수:** API Gateway의 타임아웃과 Lambda 타임아웃을 따로 보지 않는 것입니다. 호출 경로의 가장 짧은 제한이 전체 제한이므로 각각의 값을 확인합니다. 또 응답 크기가 ALB에서는 1MB로 제한되는 것을 놓쳐 큰 응답이 실패합니다.

## RDS·ElastiCache·S3 연결

세 서비스에 연결하는 방법과 주의점이 서로 다릅니다.

| 서비스 | 접속 방식 | Node.js에서 | 주의 |
|--------|-----------|-------------|------|
| RDS | 네트워크 연결(VPC 안) | DB 드라이버·ORM(자세히는 중급 17편) | Lambda는 VPC에 연결해야 접근 가능. 연결 수 관리 필요 |
| ElastiCache | 네트워크 연결(VPC 연결 또는 공개 엔드포인트) | Redis 호환 클라이언트(자세히는 중급 18편) | 엔진과 연결 유형에 따라 인증·TLS 설정 |
| S3 | HTTPS API(SDK) | `@aws-sdk/client-s3` | 네트워크가 아니라 IAM 권한으로 접근 제어 |

- RDS는 관리형 관계형 데이터베이스입니다. Lambda가 RDS에 닿으려면 같은 VPC에 연결해야 하고, VPC 설정(서브넷과 보안 그룹)을 함수에 지정합니다. 
- Lambda는 동시 요청마다 실행 환경을 따로 만들므로 각 환경이 DB 연결을 열면 동시성이 높을 때 DB의 최대 연결 수를 소진합니다. RDS Proxy가 연결 풀을 두고 여러 함수가 연결을 공유하게 합니다. 
- ElastiCache는 Valkey, Memcached, Redis OSS 엔진을 지원하는 관리형 인메모리 저장소입니다. 서버리스 캐시와 노드 기반 클러스터 두 형태가 있습니다.
- ElastiCache Serverless의 연결 유형은 VPC와 공개입니다. 공개 엔드포인트는 인터넷으로 접속할 수 있지만 모든 연결에 IAM 인증과 TLS 1.3이 필요합니다(Valkey 9.0 이상).
- 컨테이너(ECS)에서 DB·캐시에 접속할 때도 보안 그룹으로 접근 범위를 제한합니다. 접속 정보는 09편에서 다룬 대로 이미지에 넣지 않고 실행 시점에 주입합니다.
- S3 클라이언트는 `new S3Client()`로 만들고 `send()`에 명령 객체(`PutObjectCommand` 등)를 넘깁니다. 자격 증명은 코드에 쓰지 않고 실행 환경의 IAM 역할에서 자동으로 가져옵니다.

**흔한 실수:** 요청마다 DB 연결을 열고 닫는 Lambda 코드입니다. 동시성이 올라가면 DB가 "연결이 너무 많음" 오류를 냅니다.

## presigned URL

presigned URL은 S3 객체에 대한 시간 제한 접근 권한을 담은 URL입니다. 버킷 정책을 바꾸지 않고 특정 객체의 다운로드나 업로드를 임시로 허용합니다. 서버를 거치지 않고 클라이언트가 S3와 직접 파일을 주고받게 하면 서버의 대역폭과 메모리를 쓰지 않습니다.

```js
import { S3Client, PutObjectCommand }
  from '@aws-sdk/client-s3'
import { getSignedUrl } from '@aws-sdk/s3-request-presigner'

const s3 = new S3Client()
const cmd = new PutObjectCommand({
  Bucket: 'my-bucket',
  Key: `uploads/${crypto.randomUUID()}.png`,
})
const url = await getSignedUrl(s3, cmd, { expiresIn: 300 })
// 클라이언트가 이 URL로 PUT 요청을 보내면 업로드된다
```

- URL을 만들 때 버킷, 객체 키, HTTP 메서드(다운로드 `GET`, 업로드 `PUT`), 만료 시간을 정합니다. `expiresIn`은 초 단위입니다.
- URL이 가진 권한은 URL을 만든 자격 증명의 권한입니다. 만든 주체에게 해당 작업 권한이 없으면 접근이 403으로 실패합니다.
- 만료 전에는 여러 번 쓸 수 있습니다. URL을 가진 사람은 누구나 쓸 수 있는 베어러 토큰이므로 유출되지 않게 다룹니다.
- 업로드 URL로 같은 키에 올리면 기존 객체가 교체됩니다. 키는 서버가 정하고(예: UUID) 클라이언트가 임의 키를 고르지 못하게 합니다.
- 만료 시간의 상한은 만든 자격 증명에 따릅니다. SDK나 CLI로는 최대 7일(SigV4)이지만 IAM 사용자 자격 증명일 때입니다. IAM 역할 같은 임시 자격 증명으로 만들면 자격 증명이 만료될 때 URL도 함께 만료됩니다. ECS 태스크나 Lambda의 역할 자격 증명은 몇 시간 단위로 교체되므로 URL이 설정한 시간보다 일찍 만료될 수 있습니다.
- S3는 만료 여부를 HTTP 요청 시점에 검사합니다. 만료 직전에 시작한 다운로드는 도중에 만료돼도 이어지지만, 연결이 끊겨 다시 시작하면 실패합니다.
- 서명 시점을 제한하려면 버킷 정책에서 `s3:signatureAge` 조건으로 오래된 서명을 거부할 수 있습니다.
- `SignatureDoesNotMatch` 오류의 흔한 원인은 시스템 시계 오차, 프록시가 헤더나 쿼리를 바꾼 경우, 생성 때와 사용 때 메서드·헤더·쿼리 불일치입니다.
- 업로드 무결성은 체크섬으로 검증할 수 있습니다. SigV4로 만든 URL은 SHA-256, CRC32 등 추가 알고리즘을 지원합니다.

**흔한 실수:** 로그에 presigned URL을 그대로 남기는 것입니다. 만료 전까지 URL 자체가 접근 권한이므로 로그를 볼 수 있는 사람이 파일에 접근할 수 있습니다.

## IAM 최소 권한

IAM(Identity and Access Management)은 누가 어떤 AWS 자원에 무엇을 할 수 있는지 정하는 권한 체계입니다. 최소 권한은 작업에 필요한 권한만 주는 원칙입니다. 정책은 "어떤 행동(Action)을 어떤 자원(Resource)에 어떤 조건에서 허용(Allow)하는가"로 정의합니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::my-bucket/uploads/*"
  }]
}
```

위 정책은 한 버킷의 `uploads/` 경로에 대한 읽기와 쓰기만 허용합니다.

- 워크로드는 장기 접근 키 대신 IAM 역할의 임시 자격 증명을 씁니다. EC2·ECS·Lambda 같은 컴퓨트 서비스는 역할의 임시 자격 증명을 실행 환경에 전달하고, AWS SDK가 이를 찾아 쓰므로 코드나 환경변수에 키를 넣을 필요가 없습니다. Lambda에서는 함수의 실행 역할이 이 역할입니다.
- 위 Lambda 예제에서 실행 역할은 `s3:PutObject`를 허용해야 합니다. 필요한 행동만 나열합니다.
- AWS 관리형 정책으로 시작하되, 모든 고객이 쓰는 정책이라 최소 권한이 아닐 수 있으므로 용도에 맞게 고객 관리형 정책으로 좁힙니다.
- 처음에는 넓게 시작해 필요한 권한을 파악한 뒤 줄여 나가는 방식도 문서가 설명합니다. IAM Access Analyzer가 CloudTrail에 기록된 접근 이력을 분석해 최소 권한 정책을 생성합니다. 마지막 접근 정보로 쓰지 않는 권한을 찾아 제거합니다.
- `Action`과 `Resource`에 `*`를 쓰는 정책은 피합니다. 조건(`Condition`)으로 TLS 사용 강제나 특정 서비스 경유만 허용하는 식의 제한을 더할 수 있습니다.
- AWS 밖에서 도는 CI(GitHub Actions 등)에는 장기 키를 저장하지 않고 OIDC로 단기 토큰을 받아 역할을 맡게 하는 방식이 있습니다(09편에서 소개). 클라우드 쪽에서 토큰의 조건을 검증하므로 역할을 맡을 수 있는 범위를 좁힐 수 있습니다.
- 역할과 정책은 서비스마다 분리합니다. 한 역할이 여러 서비스의 권한을 모두 가지면 한 곳이 뚫릴 때 피해가 커집니다.

**흔한 실수:** 동작하지 않을 때 `Action: *`, `Resource: *`로 열어 두고 그대로 두는 것입니다. 나중에 줄이는 일을 잊어 모든 권한이 열린 채 운영됩니다.

## CloudWatch 로그

Lambda는 별도 설정 없이 로그를 CloudWatch Logs로 보냅니다. 함수마다 로그 그룹(`/aws/lambda/함수이름`)이 만들어지고, 실행 환경 인스턴스마다 로그 스트림이 만들어집니다. 함수 코드가 `stdout`이나 `stderr`로 쓰는 것은 모두 수집되므로 `console` 메서드나 로깅 라이브러리를 그대로 씁니다(08편에서 정리한 "로그는 stdout"과 같은 원칙).

- 실행 역할에 CloudWatch Logs에 쓸 권한이 있어야 합니다.
- 런타임은 호출마다 `START`, `END`, `REPORT` 줄을 남깁니다. `REPORT`에는 `Duration`, `Billed Duration`, `Memory Size`, `Max Memory Used`가 있고, 새 환경의 첫 호출에는 `Init Duration`이 붙습니다. `Init Duration`이 보이면 콜드 스타트입니다.
- 텍스트 형식은 함수가 남기는 줄마다 타임스탬프, 요청 ID, 로그 레벨을 붙입니다. `console.log`와 `console.info`는 INFO, `console.warn`은 WARN, `console.error`는 ERROR입니다.
- 고급 로깅 제어에서 로그 형식(텍스트 또는 JSON), 로그 레벨, 로그 그룹을 정할 수 있습니다. JSON 형식이면 `console` 메서드 출력이 `timestamp`, `level`, `message`, `requestId`를 가진 JSON 객체로 전송됩니다.
- `console.log`에 객체 하나를 넘기면 `message`가 객체로, 인수를 둘 이상 넘기면 문자열로 기록됩니다. 에러 객체는 `errorMessage`, `errorType`, `stackTrace` 필드가 추가됩니다.
- 로그 수준 필터링은 JSON 형식일 때만 동작합니다. 선택한 수준 이하(예: WARN이면 WARN·ERROR·FATAL)의 로그만 보냅니다. 이미 JSON으로 출력하는 로거(Powertools 등)는 `level`과 RFC 3339 형식의 `timestamp`를 넣으면 같은 필터링을 받고, 두 번 인코딩되지 않습니다.
- 함수를 지워도 로그 그룹은 자동으로 삭제되지 않습니다. 보존 기간(retention)을 설정하지 않으면 로그가 계속 쌓여 비용이 됩니다.
- 입력값을 그대로 로그에 남기면 공격자가 로그를 위조할 수 있으므로 입력 검증과 출력 인코딩을 합니다. 시크릿과 토큰은 로그에 남기지 않습니다(자세히는 중급 25편, 07편).
- 로그를 JSON 구조로 남기는 방법과 상관 ID는 11편에서 다룹니다.

**흔한 실수:** 보존 기간 없이 DEBUG 수준 로그를 운영에 그대로 두는 것입니다. 로그 양이 비용으로 직결됩니다.

## 엣지 런타임과 Node 호환성

엣지 런타임은 사용자와 가까운 위치에서 코드를 실행하는 환경입니다. 지연이 줄지만 Node.js 전체가 아니라 제한된 환경인 경우가 많아서, 쓸 수 있는 API를 확인해야 합니다.

| 항목 | CloudFront Functions | Lambda@Edge |
|------|----------------------|-------------|
| 언어 | JavaScript(ECMAScript 5.1 호환) | Node.js, Python |
| 실행 시간 | 1밀리초 미만 | 최대 30초 |
| 네트워크·파일 시스템·요청 본문 | 불가 | 가능 |
| 함수 코드와 라이브러리 크기 | 10KB | 50MB |
| 메모리 | 최대 2MB | 128MB(뷰어), 최대 10GB(오리진) |

- CloudFront Functions는 캐시 키 정규화, 헤더 조작, URL 리다이렉트·재작성, 토큰(JWT) 검증처럼 가볍고 짧은 작업용입니다. 시작이 1밀리초 미만이고 초당 수백만 요청까지 확장되지만 네트워크, 파일 시스템, 요청 본문 접근이 안 됩니다.
- Lambda@Edge는 AWS Lambda의 확장입니다. 한 리전에 게시하면 CloudFront에 연결할 때 전 세계로 자동 복제됩니다. 서드파티 라이브러리(AWS SDK 포함), 네트워크, 파일 시스템, 요청 본문 접근, 조정 가능한 CPU와 메모리가 필요할 때 씁니다. 뷰어 요청·응답과 오리진 요청·응답 네 이벤트를 모두 지원합니다.
- Cloudflare Workers는 `nodejs_compat` 호환성 플래그를 켜면 `node:` 접두사로 Node.js API를 씁니다. 대부분 완전 구현이지만 `node:console`, `node:dns`, `node:os` 등은 부분 지원입니다. 지원하지 않는 API는 폴리필이 주입되어 import는 되어도 호출하면 "not implemented yet" 오류를 냅니다. 호환성 날짜가 2026-08-04 이후이면 이 플래그가 기본으로 켜집니다.
- 정리하면 엣지 환경의 Node 호환성은 세 가지로 확인합니다. 쓰려는 `node:` 모듈이 지원되는가, 네이티브 애드온(Node-API)이나 파일 시스템 의존이 없는가, 실행 시간·메모리·코드 크기 제한 안인가.
- 서버리스든 엣지든 요청 사이에 메모리를 공유하지 않는다고 가정하고 설계합니다(자세히는 03편의 무상태 설계).

**흔한 실수:** 로컬 Node.js에서 잘 동작한 패키지를 엣지에 올렸다가 `fs`, `net` 같은 모듈이 없어 실패하는 것입니다. 번들러로 의존성을 합치고 엣지에서 지원하는 모듈만 쓰는지 배포 전에 확인합니다.

## 핵심 정리

- EC2는 서버를 직접 관리하고, ECS는 컨테이너 오케스트레이션이며(Fargate는 서버 관리 없음), Lambda는 함수를 요청 단위로 실행하고 호출당 최대 15분입니다.
- Lambda 핸들러는 `async` 함수로 쓰고 SDK 클라이언트·DB 연결은 핸들러 밖에서 초기화합니다. 콜드 스타트는 새 실행 환경의 준비와 초기화 시간이며 프로비저닝된 동시성으로 줄입니다.
- API Gateway는 REST API와 HTTP API 중 필요한 기능으로 고르고, ALB의 Lambda 대상은 요청·응답 1MB 제한과 별도 응답 형식이 있습니다.
- DB 연결 수는 동시성에 비례해 늘어나므로 RDS Proxy 같은 풀이 필요하고, S3는 네트워크가 아니라 IAM 권한으로 접근합니다.
- presigned URL은 만든 자격 증명의 권한을 시간 제한으로 위임하는 베어러 토큰이며 임시 자격 증명이면 그 만료 때 함께 만료됩니다.
- 권한은 역할의 임시 자격 증명과 필요한 Action·Resource만 허용하는 방식으로 주고, 로그는 CloudWatch에 자동 수집되며 보존 기간을 정합니다. 엣지는 쓸 수 있는 Node API를 먼저 확인합니다.

## V8 실행 파이프라인

V8은 같은 함수를 실행 횟수와 안정성에 따라 단계별로 다르게 처리하는 티어(tier) 구조의 엔진입니다. 처음에는 싸게 실행하고, 자주 쓰이는 함수만 비싼 컴파일로 올립니다.

| 단계 | 역할 | 입력 |
|------|------|------|
| Ignition | 바이트코드 인터프리터. 모든 코드가 처음 여기서 실행됨 | JavaScript 소스에서 만든 바이트코드 |
| Sparkplug | 비최적화 베이스라인 컴파일러. 거의 즉시 기계어를 만듦 | 바이트코드 |
| Maglev | 중간 단계 최적화 컴파일러. 좋은 코드를 빠르게 만듦 | 바이트코드와 실행 피드백 |
| TurboFan | 최고 단계 최적화 컴파일러. 가장 공격적으로 최적화 | 바이트코드와 실행 피드백 |

- Sparkplug는 JavaScript 소스가 아니라 바이트코드에서 컴파일하며 중간 표현(IR)을 만들지 않고 곧바로 기계어를 냅니다. V8 9.1에 들어왔습니다.
- Maglev는 Chrome M117에 출시된 SSA 기반 최적화 컴파일러입니다. 컴파일 속도가 Sparkplug보다 약 10배 느리고 TurboFan보다 약 10배 빠르다고 V8 블로그가 설명합니다.
- 어느 단계로 올릴지는 함수의 호출 빈도 같은 "뜨거움"과 인터프리터가 모은 타입 피드백으로 정합니다.
- Node.js 24(V8 13.6)에서는 `--sparkplug`, `--maglev`, `--turbofan`이 모두 기본으로 켜져 있습니다. `node --v8-options`로 확인했습니다.

최적화 코드는 "이 함수는 항상 이런 타입으로 호출된다"는 추측 위에 만들어집니다. 추측이 깨지면 최적화 코드를 버리고 더 낮은 단계로 되돌립니다. 이를 탈최적화(deoptimization)라고 합니다.

```bash
node --trace-opt --trace-deopt app.js
# [marking ... for optimization to MAGLEV, ...
#   reason: hot and stable]
# [bailout (kind: deopt-eager, reason: wrong map): ...
```

- 위 옵션은 V8 옵션이라서 Node.js 문서에 따르면 안정성 보장이 없습니다. 출력 서식은 버전마다 바뀝니다.
- 최적화와 탈최적화가 몇 번 오가는 것은 정상입니다. 같은 함수가 계속 탈최적화되면 입력 타입이 불안정하다는 신호입니다.
- 워밍업이 필요하다는 점이 코드 성능에 영향을 줍니다. 프로세스를 막 띄운 직후에는 대부분의 코드가 낮은 단계에서 돌아서 느리고, 부하 테스트의 첫 몇 초가 느린 이유이기도 합니다(자세히는 05편).

**흔한 실수:** 마이크로벤치마크를 한 번만 실행해서 비교하는 것입니다. 인터프리터 단계의 속도를 재게 되어 운영 중의 최적화된 속도와 다릅니다.

## 히든 클래스와 인라인 캐시

히든 클래스(hidden class)는 객체의 모양(shape)을 기록한 V8 내부 구조로 V8에서는 맵(Map)이라고 부릅니다. 같은 모양의 객체는 속성 이름과 위치 정보를 하나의 맵으로 공유하고, 객체는 값만 따로 가집니다.

- 속성을 추가할 때마다 새 맵으로 전이(transition)하는 사슬이 생깁니다. 빈 객체, `x`가 있는 객체, `x`와 `y`가 있는 객체는 각각 다른 맵입니다.
- 속성을 추가하는 순서가 모양에 영향을 줍니다. 같은 순서로 초기화한 객체끼리만 맵을 공유합니다.

```js
const a = { x: 1, y: 2 }
const b = { y: 2, x: 1 }
const c = { x: 3, y: 4 }
// %HaveSameMap(a, c) true
// %HaveSameMap(a, b) false
```

위 결과는 `node --allow-natives-syntax`로 직접 확인한 값입니다. 속성이 같아도 순서가 다르면 모양이 다릅니다.

인라인 캐시(inline cache, IC)는 속성을 조회할 때 "어떤 모양에서 어느 위치를 읽었는지"를 호출 지점마다 기억해 두는 장치입니다. 같은 모양이 다시 오면 조회를 건너뛰고 기억한 위치를 바로 읽습니다. 최적화 컴파일러는 이 IC의 기록을 피드백으로 씁니다.

```js
function getX(o) { return o.x }
for (let i = 0; i < 1e5; i++) getX({ x: 1, y: 2 })
for (let i = 0; i < 1e5; i++) getX({ y: 2, x: 1 })
// trace-deopt: reason: wrong map  (getX)
```

- 처음에는 한 가지 모양만 보고 최적화한 `getX`가 다른 모양을 만나자 모양이 틀렸다는 이유(wrong map)로 탈최적화됐습니다. 실제 `--trace-deopt` 출력에서 확인했습니다.
- V8 공식 문서는 속성을 같은 순서로 초기화하면 객체가 같은 히든 클래스를 공유해 메모리와 시간이 절약된다고 설명합니다. 이 문서의 예처럼 같은 종류의 객체는 한 곳(생성자나 팩토리 함수)에서 같은 순서로 만듭니다.
- 생성자에서 속성을 항상 같은 순서로 정의하는 것이 그 규칙을 지키는 가장 쉬운 방법입니다.

**흔한 실수:** 선택적 속성을 조건에 따라 추가해서 같은 종류 객체가 여러 모양으로 갈라지는 것입니다. 처음부터 모든 속성을 정의하고 비어 있는 값을 `null`로 둡니다.

## libuv 스레드 풀이 처리하는 작업

libuv는 Node.js의 이벤트 루프와 비동기 I/O를 구현한 C 라이브러리입니다. 네트워크 I/O는 항상 이벤트 루프 스레드 한 곳에서 처리하고, 운영체제가 비동기 방식을 주지 않는 작업만 스레드 풀(Worker Pool)로 보냅니다.

libuv 문서가 스레드 풀이 처리하는 작업으로 드는 것은 세 가지입니다.

- 파일 시스템 작업
- DNS 함수(`getaddrinfo`, `getnameinfo`)
- `uv_queue_work`로 사용자가 지정한 코드

Node.js 문서는 이를 API 단위로 풀어서 적습니다.

| 분류 | 스레드 풀을 쓰는 API | 제외 |
|------|----------------------|------|
| fs | 모든 `fs` API | 파일 감시(`fs.FSWatcher`)와 명시적으로 동기인 API |
| dns | `dns.lookup()`, `dns.lookupService()` | `dns.resolve*()`와 `dns.reverse()` |
| crypto | `pbkdf2()`, `scrypt()`, `randomBytes()`, `randomFill()`, `generateKeyPair()` | 명시적으로 동기인 호출 |
| zlib | 모든 zlib 비동기 API | 명시적으로 동기인 API |

- 파일 I/O는 플랫폼에 기댈 수 있는 비동기 기본 요소가 없어서 블로킹 호출을 스레드 풀에서 실행하는 방식을 택합니다.
- `dns.lookup()`은 JavaScript에서는 비동기이지만 내부에서는 동기 호출인 `getaddrinfo(3)`을 스레드 풀에서 실행합니다. `dns.resolve*()`는 네트워크로 직접 DNS 질의를 하고 스레드 풀을 쓰지 않으므로 풀을 막지 않습니다. 호스트 이름을 주소로 바꾸는 방식이 달라서 `/etc/hosts` 설정은 `dns.lookup()`만 따릅니다.
- 여러 네트워킹 API가 호스트 이름 해석에 `dns.lookup()`을 내부에서 호출합니다. 문제가 되면 주소를 미리 구하거나 기본 해석기를 바꿀 수 있습니다.
- 스레드 풀은 프로세스 전체에서 공유됩니다. 이벤트 루프가 여럿이어도 풀은 하나입니다.
- 작업자 스레드의 기본 이름은 `libuv-worker`(libuv 1.50.0부터)이고 스레드마다 스택이 8MB입니다(1.45.0부터).
- 스레드 풀은 `worker_threads`의 Worker와 다른 것입니다. 사용자가 JavaScript를 돌리는 스레드가 아니라 Node.js 내부 작업용입니다(자세히는 02편).

**흔한 실수:**

- 네트워크 요청이 스레드 풀에서 돈다고 생각하는 것입니다. 소켓 I/O는 이벤트 루프 스레드에서 폴링하므로 풀과 무관합니다.
- 풀 안의 작업이 JavaScript 콜백까지 풀에서 실행한다고 보는 것입니다. 작업 본체만 풀에서 돌고 끝났다는 통지와 콜백은 이벤트 루프 스레드에서 실행됩니다.

## UV_THREADPOOL_SIZE

`UV_THREADPOOL_SIZE`는 libuv 스레드 풀의 스레드 수를 정하는 환경변수입니다. 기본값은 4이고 최대는 1024입니다(libuv 1.30.0부터, 그 전에는 128).

```bash
UV_THREADPOOL_SIZE=8 node server.js
```

풀의 모든 스레드가 오래 걸리는 작업으로 차면 뒤에 오는 풀 작업은 순서를 기다립니다. 직접 실험해서 확인했습니다. `pbkdf2`를 8번 동시에 호출했습니다(코어 24개인 머신, Node.js 24).

```js
import { pbkdf2 } from 'node:crypto'

for (let i = 0; i < 8; i++) {
  pbkdf2('pw', 'salt', 600_000, 64, 'sha512', () => {})
}
// 기본(4): 4개 약 240ms, 나머지 4개 약 460ms
// UV_THREADPOOL_SIZE=8: 8개 모두 약 370ms 안에 완료
```

- 풀이 4일 때는 4개씩 두 번에 나뉘어 끝났습니다. 8로 올리면 한 번에 모두 처리됐습니다.
- 풀을 쓰는 작업은 서로 기다리므로 암호화가 몰리면 같은 풀을 쓰는 `fs` 요청과 `dns.lookup()`까지 늦어집니다. 파일 읽기와 DNS 해석이 갑자기 느려지는 원인이 될 수 있습니다.
- `process.env.UV_THREADPOOL_SIZE`로 코드 안에서 정하는 것은 동작이 보장되지 않습니다. 풀은 런타임 초기화 중에 이미 만들어지기 때문입니다. 프로세스를 시작할 때 환경변수로 줍니다.
- 스레드를 늘리면 메모리가 늘고(스택은 대체로 필요할 때 커집니다), 코어 수보다 많이 늘려도 CPU 작업의 속도는 오르지 않습니다. CPU 작업이 많으면 워커 스레드를 고려합니다(자세히는 02편).
- crypto 문서는 `randomBytes()`와 `randomFill()`을 클라이언트 요청 처리에 쓸 때 풀 작업의 길이 편차를 줄이도록 큰 요청을 나누라고 권합니다.

**흔한 실수:** 풀 크기를 코어 수보다 무작정 크게 잡는 것입니다. 병목이 풀 대기인지 먼저 측정합니다.

## epoll·kqueue·IOCP

epoll, kqueue, IOCP는 운영체제가 제공하는 I/O 이벤트 통지 장치입니다. libuv는 플랫폼마다 가장 알맞은 것을 골라 소켓을 비차단(non-blocking) 방식으로 폴링합니다.

| 운영체제 | 폴링 방식 |
|----------|-----------|
| Linux | epoll |
| macOS와 기타 BSD | kqueue |
| SunOS | event ports |
| Windows | IOCP |

- 이벤트 루프는 한 번 돌 때 폴링 단계에서 감시 중인 소켓에 읽기·쓰기 가능 상태가 생기기를 기다리고, 생기면 그 핸들의 콜백을 호출합니다. 기다리는 동안 스레드는 잠들어 CPU를 쓰지 않습니다.
- 폴링 방식은 플랫폼마다 다르지만 libuv가 Unix와 Windows에서 실행 모델이 같도록 맞춥니다.
- 이 방식 덕에 연결 수만 개를 스레드 하나가 감시할 수 있습니다. 연결마다 스레드를 만드는 구조가 아닙니다.
- 네트워크 I/O는 항상 이벤트 루프 스레드 한 곳에서 수행됩니다(libuv 문서). 파일 I/O는 앞 절의 스레드 풀로 갑니다.

**흔한 실수:** "Node.js는 싱글 스레드라서 한 번에 하나만 처리한다"고 답하는 것입니다. JavaScript 실행은 한 스레드이지만 I/O는 OS 폴링과 스레드 풀이 병렬로 처리하고, 끝난 결과만 이벤트 루프가 JavaScript로 전달합니다.

## 이벤트 루프 단계의 구현

Node.js 이벤트 루프의 단계는 libuv의 루프 반복(iteration)을 그대로 따릅니다. Node.js 문서의 단계와 libuv 문서의 순서를 맞춰 보면 다음과 같습니다.

| 순서 | Node.js 단계 | libuv에서 하는 일 |
|------|--------------|-------------------|
| 1 | timers | 기한이 된 타이머 콜백 실행 |
| 2 | pending callbacks | 지난 반복에서 미뤄진 I/O 콜백 실행 |
| 3 | idle, prepare | idle 핸들과 prepare 핸들 콜백. 폴링 직전에 prepare가 호출됨 |
| 4 | poll | 대기 시간을 계산하고 I/O를 기다림. 준비된 I/O 콜백 실행 |
| 5 | check | check 핸들 콜백. `setImmediate()` 콜백이 여기서 실행됨 |
| 6 | close callbacks | `uv_close`로 닫은 핸들의 콜백 |

- libuv는 루프가 살아 있는지부터 확인합니다. 활성 상태이면서 ref된 핸들, 활성 요청, 닫히는 핸들이 하나도 없으면 루프는 즉시 끝나고 프로세스가 종료됩니다. 타이머와 열린 소켓이 프로세스를 붙잡는 이유입니다.
- poll 단계에서 기다리는 시간은 규칙으로 정해집니다. idle 핸들이 있거나, 닫을 핸들이 있거나, 활성 핸들과 요청이 없으면 0입니다. 그렇지 않으면 가장 가까운 타이머까지, 타이머가 없으면 무한정입니다.
- `setImmediate()`는 poll 직후의 check 단계에서 실행되므로 I/O 콜백 안에서 호출하면 타이머보다 항상 먼저 실행됩니다(Node.js 문서). `setTimeout(fn, 0)`과의 순서는 I/O 콜백 밖에서는 보장되지 않습니다.
- 타이머를 처리하는 도중에 새로 기한이 된 타이머는 다음 반복에서 실행됩니다(libuv 문서).
- `process.nextTick()`과 Promise 마이크로태스크는 libuv 단계가 아닙니다. Node.js 문서는 `nextTick` 큐가 현재 작업이 끝난 직후, 단계와 무관하게 처리되고 이벤트 루프가 계속되기 전에 모두 비워진다고 설명합니다.
- 어느 단계든 JavaScript 콜백 하나가 실행되는 동안 다른 단계는 진행되지 않습니다. 콜백 하나가 오래 걸리면 모든 단계가 밀립니다(자세히는 05편의 이벤트 루프 지연 측정).
- `monitorEventLoopDelay`의 `samplePerIteration` 옵션은 `uv_prepare_t`와 `uv_check_t` 훅으로 반복마다 표본을 잡는 방식입니다.

**흔한 실수:** 이벤트 루프의 단계가 큐 하나를 돌리는 것으로 생각하는 것입니다. 단계마다 자기 큐가 있어서 한 단계가 끝나야 다음 단계로 넘어갑니다.

## 네이티브 애드온(Node-API) 개요

애드온(addon)은 `require()`로 불러오는 동적 연결 공유 객체(`.node` 파일)입니다. JavaScript와 C·C++ 같은 네이티브 코드 사이의 연결 통로입니다. Node.js 문서는 구현 방법을 셋으로 나눕니다.

| 방법 | 특징 |
|------|------|
| Node-API | 권장. V8과 독립된 C API이고 Node.js 버전이 바뀌어도 ABI가 안정적 |
| nan | Native Abstractions for Node.js. V8 API를 추상화한 방식 |
| V8·libuv 직접 사용 | 엔진과 Node.js 내부 API에 직접 의존. 버전마다 깨질 수 있음 |

- Node-API(옛 이름 N-API)는 Stability 2(Stable)입니다. 한 메이저 버전에서 컴파일한 애드온이 이후 메이저 버전에서도 다시 컴파일하지 않고 돌아가도록 설계됐습니다.
- 호출은 모두 `napi_status`를 반환하고, 값은 출력 인자로 전달합니다. JavaScript 값은 불투명한 `napi_value`로 다룹니다.
- 공식 C++ 래퍼인 `node-addon-api`는 헤더만 있는 라이브러리라서 C++ 코드를 더 간결하게 쓰게 해 줍니다.
- 빌드는 `binding.gyp`와 `node-gyp`로 합니다. `node-gyp`는 npm에 포함되어 있습니다.
- 오래 걸리는 작업은 `napi_create_async_work`로 비동기 작업을 만들어 실행합니다. `execute` 콜백은 Node-API 호출을 피해야 하고, 결과는 `complete` 콜백에서 다룹니다.
- Node-API에는 버전이 있습니다. 버전 10은 Node.js 22.14.0 이상과 23.6.0 이상에서 지원됩니다. 8 이후 버전은 애드온이 `NAPI_VERSION`으로 새 기능을 명시해 선택합니다.
- 애드온이 이벤트 루프에서 오래 블로킹하면 JavaScript 코드와 똑같이 서비스가 멈춥니다. 네이티브라고 병렬이 되지 않습니다.

**흔한 실수:** 새 애드온을 V8 헤더로 직접 쓰는 것입니다. V8 API는 버전에 따라 바뀌므로 Node-API를 먼저 검토합니다.

## 면접 질문 정리

내부 동작 질문은 "누가, 어느 스레드에서, 언제" 세 가지로 답을 구성합니다.

| 질문 | 답의 뼈대 |
|------|-----------|
| Node.js는 싱글 스레드인가 | JavaScript 실행은 메인 스레드 하나. I/O는 OS 폴링(epoll 등)과 libuv 스레드 풀이 처리하고 GC·컴파일도 별도 스레드가 있음 |
| 이벤트 루프 단계 순서 | timers, pending, idle·prepare, poll, check, close. nextTick과 마이크로태스크는 단계가 아니라 현재 작업 직후에 비움 |
| 스레드 풀이 처리하는 작업 | fs, dns.lookup, crypto 일부, zlib. 소켓 I/O는 아님. 기본 4개, `UV_THREADPOOL_SIZE`로 변경 |
| 풀을 막으면 어떤 증상인가 | 파일 읽기, DNS 해석, 암호화 콜백이 함께 느려짐. 풀 크기 상향이나 작업 분할 |
| `dns.lookup`과 `dns.resolve` 차이 | lookup은 `getaddrinfo`를 풀에서 실행하고 OS 설정을 따름. resolve는 네트워크 질의이고 풀을 안 씀 |
| V8은 JavaScript를 어떻게 실행하나 | Ignition이 바이트코드를 실행하고 자주 쓰이는 함수를 Sparkplug, Maglev, TurboFan으로 올림 |
| 탈최적화란 | 타입·모양에 대한 추측이 깨져서 최적화 코드를 버리고 낮은 단계로 돌아가는 것 |
| 히든 클래스와 인라인 캐시 | 객체 모양을 공유하는 구조와 속성 조회 결과를 호출 지점에 기억하는 장치. 속성 초기화 순서를 통일 |
| 애드온은 어떻게 만드나 | Node-API(ABI 안정)를 우선. `binding.gyp`와 `node-gyp`로 빌드 |
| 이벤트 루프가 종료되는 조건 | 활성 핸들·요청·닫히는 핸들이 더는 없을 때 |

- "왜 Node.js는 CPU 작업에 약한가"는 이벤트 루프 스레드 하나가 JavaScript 콜백을 차례로 실행하기 때문이라고 답하고, 해법으로 워커 스레드나 자식 프로세스를 듭니다(자세히는 01편, 02편).
- 질문의 끝이 열려 있으면 직접 재 본 경험을 한 문장 붙입니다. "스레드 풀 4개일 때 `pbkdf2` 8개가 두 번에 나뉘어 끝났다" 같은 실측이 암기보다 설득력이 큽니다.

## 핵심 정리

- V8은 Ignition에서 시작해 뜨거운 함수를 Sparkplug, Maglev, TurboFan으로 올리고, 추측이 깨지면 탈최적화합니다. 같은 순서로 초기화한 객체는 히든 클래스를 공유합니다.
- libuv 스레드 풀(기본 4, `UV_THREADPOOL_SIZE`로 변경)이 처리하는 것은 fs, `dns.lookup`, 일부 crypto, zlib입니다. 네트워크 I/O는 항상 이벤트 루프 스레드의 폴링(epoll·kqueue·IOCP)입니다.
- 이벤트 루프 한 번의 반복은 timers, pending, idle·prepare, poll, check, close 순입니다.
- 애드온은 ABI가 안정적인 Node-API로 만드는 것이 권장 방식입니다.

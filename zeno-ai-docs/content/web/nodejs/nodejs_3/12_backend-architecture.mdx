이 편의 예제는 TypeScript입니다. 프레임워크 사용법은 Express(중급 13편)와 NestJS(중급 14편, 15편)에서 다뤘고, 여기서는 어떤 프레임워크에서도 통하는 구조 원칙을 다룹니다.

## 계층형 구조(Controller·Service·Repository)

계층형 구조는 요청 처리를 책임별 층으로 나누는 가장 흔한 구조입니다. 요청은 위에서 아래로만 흐릅니다.

| 층 | 책임 | 알아도 되는 것 | 몰라야 하는 것 |
|----|------|----------------|----------------|
| Controller | HTTP 요청을 읽고 응답을 만듦(상태 코드, 헤더) | 서비스, DTO | SQL, 비즈니스 규칙 |
| Service | 비즈니스 규칙과 유스케이스 흐름 | 리포지토리, 도메인 객체 | `req`, `res`, SQL |
| Repository | 저장소 접근. 도메인 객체를 컬렉션처럼 다룸 | DB 드라이버·ORM | HTTP, 비즈니스 규칙 |

Repository는 도메인 계층과 데이터 매핑 계층 사이에서 도메인 객체를 컬렉션 같은 인터페이스로 접근하게 해 주는 패턴입니다(Fowler). 질의 로직이 한곳에 모여 중복이 줄고 비즈니스 로직과 데이터 접근이 분리됩니다.

```ts
app.post('/orders', async (req, res) => {
  const order = await orderService.place(req.body)
  res.status(201).json(order)
})
```

```ts
export class OrderService {
  constructor(private readonly orders: OrderRepository) {}

  async place(input: PlaceOrderInput) {
    if (input.items.length === 0) {
      throw new EmptyOrderError()
    }
    return this.orders.save(Order.create(input))
  }
}
```

- 컨트롤러는 입력을 서비스가 이해하는 형태로 넘기고 결과를 HTTP로 바꾸는 얇은 층입니다. 규칙은 서비스에 둡니다.
- 서비스는 HTTP를 모릅니다. 같은 서비스를 HTTP 컨트롤러, 큐 소비자, 스케줄러가 모두 호출할 수 있어야 합니다.
- 위층은 아래층을 호출하지만 반대는 안 됩니다. 아래층이 위층을 import하면 순환 의존이 생깁니다.
- 서비스가 `OrderRepository`라는 이름만 알고 구현(PostgreSQL, 인메모리)을 모르게 하면 테스트에서 가짜 리포지토리를 넣을 수 있습니다(다음 절).
- NestJS에서는 `@Controller`, `@Injectable` 서비스, 리포지토리 프로바이더가 이 층에 대응합니다.

**흔한 실수:**

- 컨트롤러에 규칙과 쿼리를 쓰는 것입니다. 같은 로직이 큐 소비자에서 필요해지면 복사하게 됩니다.
- 서비스가 리포지토리 호출만 그대로 전달하는 빈 층이 되는 것입니다. 규칙이 없는 단순 CRUD라면 층을 줄입니다.
- ORM 엔티티를 컨트롤러까지 그대로 올려 보내는 것입니다. DB 구조가 API 응답에 노출됩니다(DTO 절 참고).

## 의존성 역전과 DI

의존성 역전 원칙(DIP)은 상위 정책이 하위 구현에 의존하지 않고, 둘 다 추상화에 의존하게 하는 원칙입니다. 서비스(상위)가 PostgreSQL 리포지토리(하위)를 직접 import하면 서비스가 DB 기술에 묶입니다. 서비스가 인터페이스(포트)를 정의하고 리포지토리 구현이 그 인터페이스를 따르게 하면 소스 코드 의존 방향이 뒤집힙니다. 호출은 서비스에서 구현으로 가지만, 소스 코드 의존은 구현에서 인터페이스로 향합니다.

```ts
export interface OrderRepository {
  save(order: Order): Promise<Order>
  findById(id: string): Promise<Order | null>
}

export class PgOrderRepository implements OrderRepository {
  constructor(private readonly pool: Pool) {}
  async save(order: Order) { /* INSERT ... */ return order }
  async findById(id: string) { /* SELECT */ return null }
}
```

의존성 주입(DI)은 객체가 필요로 하는 의존 객체를 스스로 만들지 않고 밖에서 받는 방식입니다. 보통 생성자 인수로 받습니다. 제어 역전(IoC)은 객체 생성과 연결을 코드 바깥(컨테이너나 조립 코드)이 맡는 구조 자체를 가리킵니다.

조립은 앱의 시작 지점(composition root) 한곳에서 합니다. 서비스 안에서 `new PgOrderRepository()`를 만들지 않습니다.

```ts
const pool = new Pool({ connectionString: url })
const orders = new PgOrderRepository(pool)
const orderService = new OrderService(orders)

// 테스트에서는 구현만 바꿔 끼움
const fake = new InMemoryOrderRepository()
const testService = new OrderService(fake)
```

NestJS는 이 조립을 IoC 컨테이너가 맡습니다. TypeScript의 인터페이스는 컴파일 후 사라지므로 런타임 토큰이 필요합니다. 문자열이나 심벌을 토큰으로 쓰는 비클래스 토큰을 `@Inject()`로 받습니다.

```ts
export const ORDER_REPOSITORY = Symbol('ORDER_REPOSITORY')

@Module({
  providers: [
    OrderService,
    {
      provide: ORDER_REPOSITORY,
      useClass: PgOrderRepository,
    },
  ],
})
export class OrderModule {}
// 주입: @Inject(ORDER_REPOSITORY) orders: OrderRepository
```

- 프로바이더 종류: `useClass`(클래스로 해석, 환경별로 다른 구현 선택에 유용), `useValue`(상수나 목 객체, 외부 라이브러리 객체를 컨테이너에 넣을 때), `useFactory`(함수가 반환한 값, `inject`로 다른 프로바이더를 받음), `useExisting`(기존 프로바이더의 별칭).
- `providers: [CatsService]`는 `{ provide: CatsService, useClass: CatsService }`의 줄임 표기입니다.
- 커스텀 프로바이더는 선언한 모듈 안에서만 보입니다. 다른 모듈에서 쓰려면 `exports`에 토큰을 내보냅니다.
- DI의 효과는 테스트 용이성(가짜 구현 주입)과 구현 교체(DB 변경, 환경별 구현)입니다.

**흔한 실수:**

- 서비스 안에서 컨테이너에 직접 "이 클래스를 달라"고 요청하는 것(서비스 로케이터)입니다. 의존이 생성자에 드러나지 않아 숨은 의존이 됩니다.
- 인터페이스를 만들었지만 구현이 하나뿐이고 바뀔 일도 없는데 모든 클래스에 인터페이스를 두는 것입니다. 경계(DB, 외부 API)에 두면 충분합니다.

## 도메인 모델

도메인 모델은 업무 개념과 규칙을 코드의 객체로 표현한 것입니다. 서비스에 `if`가 흩어지는 대신, 규칙을 그 규칙을 가진 객체가 지킵니다.

| 개념 | 뜻 | 예 |
|------|----|----|
| Entity | 식별자로 구별되는 객체. 속성이 바뀌어도 같은 객체 | 주문, 사용자 |
| Value Object | 값이 같으면 같은 객체. 변경하지 않고 새로 만듦 | 금액(수량과 통화), 기간 |
| Aggregate | 하나의 단위로 다루는 객체 묶음. 루트를 통해서만 접근 | 주문과 주문 항목 |

Value Object는 문자열이나 숫자 같은 원시 값을 의미 있는 객체로 바꿔 검증을 담고 부적절한 연산을 막습니다. Aggregate는 외부에서 루트만 참조하고, 트랜잭션은 Aggregate를 넘어 걸지 않는 것을 원칙으로 합니다.

```ts
export class Order {
  private constructor(
    readonly id: string,
    private items: OrderItem[],
    private status: OrderStatus,
  ) {}

  pay() {
    if (this.status !== 'placed') {
      throw new InvalidOrderStateError(this.status)
    }
    this.status = 'paid'
  }
}
```

- 상태 전이 규칙(`placed`에서만 `paid`로)이 주문 객체 안에 있어서 어떤 호출 경로로도 우회할 수 없습니다.
- 서비스는 흐름을 맡습니다. 리포지토리에서 불러오고, `order.pay()`를 호출하고, 저장합니다.
- 도메인 객체는 프레임워크와 DB를 모릅니다. 데코레이터나 ORM 어노테이션 없이 순수 클래스로 둡니다.
- 도메인 모델과 ORM 엔티티를 같은 클래스로 쓸지 나눌지는 선택입니다. 나누면 DB 구조 변경이 도메인에 번지지 않지만 매핑 코드가 늘어납니다.

**흔한 실수:** 빈약한 도메인 모델(anemic domain model)입니다. 객체가 getter와 setter만 가지고 로직은 전부 서비스에 있어서, 도메인 모델의 비용(매핑)만 들고 이득은 얻지 못합니다. 반대로 규칙이 없는 단순 CRUD에 도메인 모델을 억지로 도입하는 것도 비용만 키웁니다.

## 헥사고날·클린 아키텍처

두 아키텍처는 같은 핵심을 말합니다. 업무 로직을 중앙에 두고, 프레임워크·DB·UI 같은 외부 기술이 중앙에 의존하게 합니다.

헥사고날 아키텍처(포트와 어댑터)는 애플리케이션 로직을 중심에 두고, 외부와의 접점을 포트로 정의하며, 포트마다 외부 기술에 맞는 어댑터를 둡니다. 어댑터는 두 종류입니다.

| 종류 | 역할 | 예 |
|------|------|----|
| Primary(driving) | 애플리케이션을 호출하는 쪽 | HTTP 컨트롤러, 큐 소비자, 테스트 |
| Secondary(driven) | 애플리케이션이 호출하는 쪽 | DB 리포지토리, 외부 API 클라이언트, 목 객체 |

클린 아키텍처는 의존성 규칙을 중심에 둡니다. 소스 코드 의존은 안쪽으로만 향합니다.

| 층(안쪽부터) | 내용 |
|--------------|------|
| Entities | 업무 전반에 적용되는 규칙 |
| Use Cases | 애플리케이션 고유 규칙. 엔티티를 조율 |
| Interface Adapters | 데이터 형식 변환(컨트롤러, DB 어댑터) |
| Frameworks & Drivers | DB, 웹 프레임워크 같은 외부 도구 |

- 경계를 넘는 데이터는 단순한 구조여야 합니다. 엔티티나 프레임워크 객체를 그대로 넘기면 안쪽이 바깥에 의존하게 됩니다.
- 제어 흐름과 의존 방향이 반대인 부분은 의존성 역전으로 풉니다. 유스케이스가 포트(인터페이스)를 소유하고, 바깥 어댑터가 구현합니다.
- 계층형에서는 서비스가 아래의 리포지토리에 의존해 업무 로직이 저장 기술에 묶이기 쉽습니다. 헥사고날은 이 방향을 뒤집어 업무 로직이 새지 않게 합니다.

Node.js 프로젝트에 대응시키면 폴더는 다음과 같습니다.

```text
src/
  domain/          엔티티, 값 객체, 도메인 에러
  application/     유스케이스, 포트(인터페이스)
  adapters/
    http/          컨트롤러 (primary)
    persistence/   리포지토리 구현 (secondary)
  main.ts          조립(composition root)
```

- `domain`은 아무것도 import하지 않고, `application`은 `domain`만 import합니다. `adapters`가 둘을 import합니다.
- 장점은 DB와 프레임워크를 바꾸거나 도메인 로직을 DB 없이 테스트하기 쉬운 것입니다. 목 어댑터로 인프라 없이 테스트합니다.
- 비용은 인터페이스와 매핑 코드, 파일 수의 증가입니다. 도메인 규칙이 단순한 서비스에는 과합니다. 계층형으로 시작해 경계가 아픈 곳(DB, 외부 API)부터 포트를 도입하는 방식이 현실적입니다.

**흔한 실수:** 폴더 이름만 `domain`, `application`으로 나누고 `domain`이 ORM 데코레이터나 `express`를 import하는 것입니다. 의존 방향이 지켜지지 않으면 구조가 아니라 이름만 바뀐 것입니다.

## 모듈 경계

모듈 경계는 한 기능의 코드를 묶고 공개할 것만 밖에 내보이는 선입니다. 경계가 선명하면 한 기능을 바꿀 때 영향 범위가 그 모듈 안에 머뭅니다. NestJS는 이를 모듈로 표현합니다.

- `@Module()`의 속성은 `providers`(DI가 만드는 서비스), `controllers`, `imports`(필요한 다른 모듈), `exports`(다른 모듈에 공개할 프로바이더)입니다.
- 모듈은 기본적으로 싱글턴이라서 `exports`한 프로바이더를 import한 모든 모듈이 같은 인스턴스를 씁니다.
- 기능 모듈(feature module)은 한 기능의 코드를 모아 경계를 분명히 합니다.
- `@Global()`로 전역 등록할 수 있지만 문서가 모든 것을 전역으로 만드는 것은 권장되는 설계가 아니라고 설명합니다. 명시적인 `imports`가 구조를 드러내고 공개 범위를 통제합니다.
- 동적 모듈은 `forRoot()` 같은 정적 메서드로 런타임 설정을 받습니다. 한 번 설정해 공유하려면 핵심 모듈에서 한 번만 호출하고 다시 내보냅니다.

Nest가 아니어도 같은 원칙을 씁니다.

- 모듈마다 공개 진입점 하나(`index.ts`)를 두고, 다른 모듈은 그것만 import합니다. 다른 모듈의 리포지토리나 내부 파일을 직접 import하지 않습니다.
- 다른 모듈의 DB 테이블을 직접 조회하지 않고 그 모듈의 서비스(공개 API)를 호출합니다.
- 패키지로 나눈 경우 `package.json`의 `exports` 필드가 공개 진입점을 정의합니다. 목록에 없는 내부 파일 import는 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 막힙니다. `imports` 필드(`#`로 시작하는 키)는 패키지 내부 전용 경로입니다(자세히는 기초 11편).
- 의존 방향은 한쪽으로만 둡니다. 모듈 A가 B를 쓰면서 B가 A를 쓰는 순환 의존은 경계가 틀렸다는 신호입니다. 공통 부분을 제3의 모듈로 빼거나 이벤트로 느슨하게 연결합니다.

경계가 선명한 단일 배포 단위를 모듈러 모놀리스라고 부릅니다. 마이크로서비스로 나눌 때 이 경계가 서비스 경계 후보가 됩니다(아래 "모놀리식과 마이크로서비스").

**흔한 실수:** `exports`를 쓰지 않아도 되도록 모듈 전부를 `@Global()`로 두는 것입니다. 모든 모듈이 모든 모듈에 의존할 수 있게 되어 경계가 사라집니다.

## DTO와 매핑

DTO(Data Transfer Object)는 프로세스 사이에 데이터를 실어 나르는 객체입니다. 원래 원격 호출의 횟수를 줄이려고 여러 인수를 한 객체로 묶는 데서 시작했고, 직렬화 로직을 핵심 코드와 분리하는 효과도 있습니다. 백엔드에서는 API 경계의 입력과 출력 모양을 정의하는 객체로 쓰입니다. 서버 쪽 어셈블러(매퍼)가 DTO와 도메인 객체 사이를 변환합니다.

| 객체 | 위치 | 모양을 정하는 것 |
|------|------|------------------|
| 요청 DTO | 컨트롤러 입력 | API 계약. 검증 대상(중급 08편, 중급 14편) |
| 도메인 객체 | 서비스와 도메인 | 업무 규칙 |
| 영속 모델(ORM 엔티티) | 리포지토리 | DB 스키마 |
| 응답 DTO | 컨트롤러 출력 | API 계약. 클라이언트에 보여 줄 필드 |

```ts
export function toOrderResponse(o: Order): OrderResponse {
  return {
    id: o.id,
    status: o.status,
    total: o.total.amount, // 값 객체를 숫자로 풀어 노출
  }
}
```

- 모양이 다른 이유가 다르기 때문에 객체를 나눕니다. API는 클라이언트 호환성 때문에, DB는 저장 효율 때문에, 도메인은 업무 규칙 때문에 바뀝니다.
- 응답 DTO는 노출할 필드만 골라 담습니다. 도메인·ORM 객체를 그대로 직렬화하면 비밀번호 해시나 내부 식별자가 응답에 섞입니다.
- 요청 DTO는 컨트롤러 경계에서 검증한 뒤에만 서비스로 넘깁니다. 요청 본문을 엔티티에 통째로 펼쳐 넣으면 클라이언트가 보내지 말아야 할 필드(권한, 상태)를 덮어쓰는 취약점이 됩니다.
- 직렬화에 안 맞는 값(`BigInt`, `Date`, 값 객체)은 매핑 단계에서 문자열이나 숫자로 바꿉니다(`BigInt`와 JSON은 04편).
- NestJS에서는 클래스로 DTO를 정의하고 `ValidationPipe`로 검증합니다. 매핑 함수는 서비스나 별도 매퍼 클래스에 둡니다.
- 층마다 모델을 모두 나누면 필드를 옮기는 코드가 늘어납니다. 단순 CRUD는 DTO와 ORM 모델을 공유하는 편이 낫고, 복잡해질 때 나눕니다.

**흔한 실수:** 응답에 ORM 엔티티를 그대로 반환하는 것입니다. 컬럼을 추가할 때마다 API 응답이 바뀌고 민감한 컬럼이 노출될 수 있습니다.

## 에러 계층

에러 계층은 애플리케이션이 던지는 에러를 공통 기반 클래스 아래 종류별로 정리한 구조입니다. 에러의 종류를 타입으로 구별해 한곳에서 일관되게 처리할 수 있습니다(에러 기본은 기초 25편).

```ts
export abstract class AppError extends Error {
  abstract readonly code: string
  constructor(message: string, options?: ErrorOptions) {
    super(message, options)
    this.name = new.target.name
  }
}
export class NotFoundError extends AppError {
  readonly code = 'NOT_FOUND'
}
export class ConflictError extends AppError {
  readonly code = 'CONFLICT'
}
```

- 도메인과 서비스는 HTTP 상태 코드를 모릅니다. `NotFoundError`처럼 업무 의미로 던지고, HTTP 상태로의 변환은 경계(컨트롤러, 에러 핸들러)에서 한 번만 합니다.
- 저수준 에러(DB 오류)는 잡아서 의미 있는 에러로 바꾸되 `cause` 옵션으로 원인을 이어 붙입니다. 원인을 버리면 로그에서 추적이 끊깁니다.
- 예상한 에러(검증 실패, 없음, 충돌)와 예상하지 못한 에러(버그)를 구별합니다. 예상하지 못한 에러는 500으로 응답하고 로그와 에러 추적(11편)에 남기며 내부 메시지와 스택은 응답에 싣지 않습니다.

| 에러 | 의미 | HTTP 상태 |
|------|------|-----------|
| 검증 에러 | 입력이 계약을 어김 | 400 |
| 인증·인가 에러 | 신원 없음, 권한 없음 | 401, 403 |
| NotFoundError | 대상 없음 | 404 |
| ConflictError | 현재 상태와 충돌 | 409 |
| 그 밖의 에러 | 예상하지 못한 실패 | 500 |

NestJS는 예외 계층을 내장합니다. `HttpException`과 그 하위(`BadRequestException`, `NotFoundException` 등)가 처리되지 않은 에러를 받는 전역 예외 필터에 의해 `statusCode`와 `message`를 가진 JSON으로 응답됩니다. 도메인 에러를 HTTP로 바꾸려면 `@Catch()`와 `ExceptionFilter`를 구현한 커스텀 필터를 씁니다.

```ts
@Catch(AppError)
export class AppErrorFilter implements ExceptionFilter {
  catch(err: AppError, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse()
    res.status(statusOf(err)).json({ code: err.code })
  }
}
// 전역 등록: providers에
// { provide: APP_FILTER, useClass: AppErrorFilter }
```

- 필터는 메서드, 컨트롤러, 전역 단위로 걸 수 있습니다. DI가 필요하면 `APP_FILTER` 토큰으로 등록합니다. `@Catch()`에 인수가 없으면 모든 예외를 처리합니다.
- Express에서는 에러 처리 미들웨어가 같은 역할을 합니다(중급 13편).
- 응답의 `code`는 클라이언트가 분기하는 안정적인 식별자입니다. 메시지 문구는 바꿔도 코드는 유지합니다.

**흔한 실수:** 서비스에서 `NotFoundException` 같은 HTTP 예외를 직접 던지는 것입니다. 서비스가 HTTP에 묶여 큐 소비자나 스케줄러에서 같은 서비스를 쓸 수 없게 됩니다.

## 설정 계층

설정 계층은 환경에 따라 달라지는 값을 코드 한곳에서 읽고, 검증하고, 필요한 곳에 내려 주는 구조입니다. 설정은 코드와 분리해 환경변수로 두는 것이 Twelve-Factor App의 원칙이고, 판단 기준은 저장소를 지금 공개해도 자격 증명이 새지 않는가입니다. 읽는 방법은 중급 25편에서 다뤘습니다.

설정이 쌓이는 층과 우선순위는 다음과 같습니다.

| 층 | 예 | 우선순위 |
|----|----|----------|
| 코드의 기본값 | 포트 3000, 타임아웃 | 낮음 |
| 환경 파일 | `.env` | 중간 |
| 실행 환경의 환경변수 | 컨테이너·플랫폼이 주입 | 높음 |
| 시크릿 저장소 | 비밀번호, 키 | 환경변수로 주입(07편, 10편) |

- NestJS의 `ConfigModule`에서도 실행 환경 변수가 `.env` 파일의 값보다 우선합니다(`override: true`로 뒤집을 수 있음).
- Twelve-Factor는 환경 이름별 묶음(`staging`, `production`)보다 변수 하나하나를 독립된 제어값으로 두라고 권합니다. 환경이 늘어도 설정이 조합 폭발하지 않습니다.
- 도메인과 애플리케이션 계층은 `process.env`를 읽지 않습니다. 설정 객체를 시작 지점에서 한 번 만들어 필요한 값만 생성자로 내려 줍니다.
- 시작할 때 모두 검증합니다. 잘못된 설정은 서버가 뜨기 전에 에러로 끝나야 합니다.

NestJS는 `ConfigModule.forRoot()`가 옵션을 받습니다. `isGlobal`(전역 모듈), `envFilePath`(여러 파일 가능), `load`(커스텀 설정), `validationSchema`(Zod 등 Standard Schema 호환 검증기), `cache`입니다. 네임스페이스별 설정은 `registerAs()`로 만듭니다.

```ts
export default registerAs('database', () => ({
  host: process.env.DATABASE_HOST,
  port: Number(process.env.DATABASE_PORT ?? 5432),
}))

// 사용: configService.get('database.host')
// 필수 값: configService.getOrThrow('DATABASE_URL')
```

- `ConfigService.get()`은 값이 없으면 `undefined`를 주고, `getOrThrow()`는 에러를 던집니다. 필수 값에 씁니다.
- `ConfigType` 유틸리티로 네임스페이스 설정에 타입을 붙입니다.
- 설정 객체를 전역 싱글턴으로 아무 데서나 import하면 도메인이 설정에 묶입니다. 의존으로 주입해 테스트에서 바꿔 끼울 수 있게 합니다.

**흔한 실수:** 서비스 코드 곳곳에서 `process.env.X`를 직접 읽는 것입니다. 이름 오타와 변환 누락이 흩어지고, 테스트마다 환경변수를 조작해야 합니다.

## 모놀리식과 마이크로서비스

모놀리식은 모든 기능을 하나의 배포 단위로 만들고, 마이크로서비스는 각자 프로세스에서 돌고 가벼운 수단(흔히 HTTP API)으로 통신하는 작은 서비스 모음입니다. 서비스는 업무 기능 단위로 나뉘고 독립적으로 배포됩니다.

| 항목 | 모놀리식 | 마이크로서비스 |
|------|----------|----------------|
| 배포 | 하나로 묶여 한 번에 | 서비스별 독립 |
| 확장 | 전체를 확장 | 필요한 서비스만 확장 |
| 호출 | 함수 호출(프로세스 내부) | 네트워크 호출(지연, 실패 가능) |
| 데이터 | 하나의 DB와 트랜잭션 | 서비스별 데이터. 결과적 일관성 |
| 운영 | 단순 | 서비스 수만큼 배포·모니터링·장애 대응 |
| 팀 | 작은 팀에 유리 | 팀별 독립 작업에 유리 |

- 모놀리스의 문제는 작은 변경에도 전체를 다시 빌드·배포해야 하고, 확장이 전체 단위라는 점입니다.
- 마이크로서비스는 분산 시스템의 비용을 가져옵니다. 원격 호출이 느리고 실패하며, 트랜잭션 대신 결과적 일관성을 다뤄야 하고, 서비스 경계를 넘는 변경을 조율해야 합니다. 이런 복잡도를 감당할 역량이 있어야 이득이 납니다.
- Fowler의 MonolithFirst는 성공한 마이크로서비스 사례의 거의 전부가 커진 모놀리스를 쪼갠 것이고, 처음부터 마이크로서비스로 만든 시스템은 심각한 어려움에 빠진 경우가 많다고 관찰합니다. 이유는 초기에는 올바른 서비스 경계를 정하기 어렵고, 경계를 잘못 잡았을 때 서비스 사이에서 기능을 옮기는 일이 모놀리스 안에서보다 훨씬 어렵기 때문입니다.
- 권장 경로는 경계가 선명한 모듈러 모놀리스(모듈 경계 절)로 시작해, 경험으로 분리 지점을 찾은 뒤 필요한 부분을 서비스로 떼는 것입니다.

Node.js에서 서비스를 나눌 때 따라오는 일은 다음과 같습니다.

- 서비스 사이 통신: HTTP API, 또는 메시지 큐(중급 18편의 BullMQ 같은 작업 큐)를 통한 비동기 이벤트.
- 서비스마다 자기 데이터를 갖고, 다른 서비스의 DB를 직접 읽지 않습니다.
- 한 요청이 여러 서비스를 거치므로 트레이스 전파와 상관 ID가 필요합니다(11편).
- 서비스마다 이미지와 배포 파이프라인, 헬스체크가 필요합니다(09편). 모듈 하나가 서비스 하나가 되는 것이 아니라, 배포·확장 요구가 다른 단위가 서비스가 됩니다.
- 한 서비스의 장애가 다른 서비스로 번지지 않게 타임아웃·재시도·차단기가 필요합니다(14편).

**흔한 실수:** 코드를 정리하려는 목적으로 서비스를 나누는 것입니다. 모듈로 풀 수 있는 문제를 네트워크로 풀어 지연과 장애 지점만 늘립니다. 서비스를 나눴는데 항상 함께 배포해야 하고 서로의 DB를 읽는다면 분산의 비용만 지고 독립성은 얻지 못한 것입니다.

## 모노레포

모노레포는 여러 앱과 패키지를 하나의 저장소에서 관리하는 방식입니다. Node.js에서는 패키지 매니저의 워크스페이스로 시작합니다. npm은 루트 `package.json`의 `workspaces` 필드에 패키지 경로를 적으면 `npm install` 때 워크스페이스를 `node_modules`에 심볼릭 링크로 연결해 `npm link`가 필요 없습니다(자세히는 기초 14편).

```text
repo/
  apps/
    api/           NestJS 또는 Express 서버
    worker/        큐 소비자
  packages/
    domain/        공유 도메인 모델
    config/        공통 설정, 린트·tsconfig
  package.json     "workspaces": ["apps/*", "packages/*"]
```

```bash
npm install                    # 워크스페이스를 한 번에 설치·연결
npm run build -w api           # 한 워크스페이스에서 실행
npm run test --workspaces --if-present   # 전체 실행
```

- `-w 이름`은 특정 워크스페이스에, `--workspaces`는 전체에 명령을 실행합니다. 스크립트가 없는 곳은 `--if-present`로 건너뜁니다.
- 워크스페이스는 의존 설치와 연결을 해 줄 뿐, 작업 순서나 캐시는 관리하지 않습니다. 빌드 순서와 캐시는 Turborepo 같은 빌드 시스템이 맡습니다. Turborepo는 JavaScript·TypeScript 모노레포용 빌드 시스템이고 npm·pnpm·yarn 워크스페이스와 함께 씁니다.
- Turborepo의 작업 그래프는 `turbo.json`의 작업 의존 선언으로 정해지고(빌드가 먼저, 그다음 테스트 등), 병렬 실행하며 결과를 캐시해 같은 작업을 다시 하지 않습니다. 원격 캐시를 두면 CI에서도 재사용합니다.
- 장점은 앱과 패키지가 타입과 코드를 공유하고, 공통 모듈 변경과 그 사용처 수정을 한 번의 변경으로 처리하며, 도구 설정을 한곳에 두는 것입니다.
- 비용은 저장소가 커지면 CI 시간이 늘어난다는 점(변경된 부분만 빌드·테스트하는 캐시와 필터가 필요)과, 패키지 경계가 지켜지지 않으면 모든 코드가 모든 코드를 import해 의존이 엉킨다는 점입니다.
- 패키지 경계는 `exports`로 공개 진입점을 정의해 지킵니다(모듈 경계 절).
- 앱별로 배포하려면 앱마다 Dockerfile을 두되, 공유 패키지를 복사해야 하므로 빌드 컨텍스트가 저장소 루트가 됩니다. `.dockerignore`로 컨텍스트를 줄이는 일이 더 중요해집니다(09편).
- 모노레포와 마이크로서비스는 별개의 선택입니다. 모노레포 안에 여러 서비스를 두고 각각 독립 배포할 수도 있고, 모듈러 모놀리스를 모노레포의 패키지로 나눌 수도 있습니다.

**흔한 실수:** 공통 코드를 `packages/shared` 하나에 몰아넣어 모든 앱이 의존하는 만능 패키지로 만드는 것입니다. 한 곳을 고치면 모든 앱이 다시 빌드되고, 공통 패키지가 앱의 업무 로직까지 끌어안게 됩니다.

## 핵심 정리

- 계층형은 Controller(HTTP), Service(규칙), Repository(저장)로 나누고 요청이 위에서 아래로만 흐르게 합니다. 서비스는 HTTP를 모릅니다.
- 의존성 역전은 상위 정책이 인터페이스를 소유하고 구현이 따르게 하며, DI는 의존 객체를 생성자로 주입받습니다. 조립은 시작 지점 한곳에서 합니다.
- 도메인 모델은 규칙을 객체에 두고(Entity, Value Object, Aggregate) 헥사고날·클린은 의존 방향을 안쪽으로만 향하게 합니다. 단순 CRUD에는 과합니다.
- 모듈은 `exports`로 공개 범위를 좁히고, 다른 모듈의 내부와 DB를 직접 건드리지 않습니다. 요청·응답 DTO는 도메인·DB 모델과 분리합니다.
- 에러는 공통 기반 클래스 아래 업무 의미로 던지고 HTTP 변환은 경계에서 한 번만 하며, 설정은 시작 지점에서 읽고 검증해 주입합니다.
- 구조는 처음부터 가장 큰 것을 고르지 않고 모듈러 모놀리스와 계층형으로 시작해, 배포·확장·팀 요구가 생길 때 서비스와 포트로 나눕니다. 모노레포는 워크스페이스와 빌드 캐시로 관리합니다.

## 타임아웃·재시도·백오프·지터

네트워크 호출은 실패하거나 응답이 없을 수 있다고 가정해야 합니다. 이 네 가지는 한 묶음으로 쓰입니다. 타임아웃이 무한 대기를 끊고, 재시도가 일시적 실패를 넘기고, 백오프와 지터가 재시도가 장애를 키우지 않게 합니다.

### 타임아웃

타임아웃은 클라이언트가 요청 하나를 기다리는 최대 시간입니다. 없으면 응답 없는 요청이 연결, 메모리, 이벤트 루프의 콜백 같은 자원을 계속 붙잡고, 그런 요청이 쌓이면 자원이 고갈됩니다. 서버가 설정하는 타임아웃은 중급 06편에서 다루고, 여기서는 나가는 호출을 다룹니다.

Node.js의 `AbortSignal.timeout(ms)`는 지정한 시간이 지나면 `TimeoutError`로 중단되는 신호를 만듭니다(Stable, v17.3.0 추가). `fetch`에 넘기면 요청이 중단됩니다.

```js
try {
  const signal = AbortSignal.timeout(2000);
  const res = await fetch(url, { signal });
  console.log(res.status);
} catch (err) {
  if (err.name === 'TimeoutError') console.log('2초 초과');
}
```

- 사용자 취소 신호와 합칠 때는 `AbortSignal.any([a, b])`(v20.3.0 추가)를 씁니다. 먼저 중단된 쪽이 `reason`이 됩니다.
- 값은 호출 대상의 지연 시간 분포에서 정합니다. AWS Builders' Library는 다운스트림의 p99.9 같은 높은 백분위 지연에 여유를 더해 정하라고 안내합니다. 너무 짧으면 정상 요청이 실패하고, 너무 길면 보호 효과가 없습니다.
- 호출 체인에서는 바깥 호출의 남은 시간(deadline)을 안쪽 호출에 전달해, 안쪽이 바깥보다 오래 기다리지 않게 합니다.
- DB 쿼리, 캐시 호출, 큐 발행에도 모두 타임아웃을 둡니다(중급 16편). 연결 시간과 응답 시간을 따로 두는 라이브러리도 많습니다.
- 타임아웃은 호출한 쪽이 기다리기를 멈출 뿐, 상대 서버의 작업을 되돌리지 않습니다. 쓰기 요청이 타임아웃되면 "처리됐는지 모르는 상태"이므로 멱등해야 재시도할 수 있습니다(아래 "멱등성").

### 재시도

재시도는 일시적 실패(순간적인 네트워크 끊김, 과부하로 인한 거절)가 곧 사라진다는 가정에 기대어 같은 호출을 다시 하는 것입니다. Azure의 Retry 패턴 문서는 전략을 세 가지로 나눕니다.

| 전략 | 쓰는 때 |
|------|---------|
| 취소 | 실패가 일시적이 아니거나 반복해도 성공할 가능성이 낮을 때 |
| 즉시 재시도 | 패킷 손상처럼 드물게 생기는 실패 |
| 지연 후 재시도 | 연결 문제나 과부하처럼 잠시 뒤 풀리는 실패 |

- 재시도 가능한 실패와 아닌 실패를 가립니다. 연결 오류, 타임아웃, 429, 502·503·504는 재시도 후보이고, 400·401·403·404·422는 같은 요청을 반복해도 결과가 같으므로 재시도하지 않습니다. gRPC라면 `UNAVAILABLE`은 후보, `INVALID_ARGUMENT`는 대상이 아닙니다.
- 멱등한 연산만 재시도합니다. AWS 문서는 부수 효과가 있는 API는 멱등성을 제공하지 않으면 재시도가 안전하지 않다고 적습니다. 서버가 요청을 처리하고 응답만 잃었을 수 있기 때문입니다. POST는 멱등 키로 만듭니다(13편).
- 재시도 횟수에 상한을 둡니다. 서버가 `Retry-After`를 주면 그 값을 따릅니다.
- 재시도는 계층마다 곱해집니다. AWS 문서의 계산에 따르면 호출 깊이 5단계에서 단계마다 3번씩 재시도하면 가장 안쪽 DB의 부하가 243배가 되어 복구하기 어려워집니다. 그래서 한 계층(보통 가장 바깥이나 SDK)에서만 재시도하고 나머지는 빨리 실패시킵니다.
- 재시도 총량을 제한하는 방법으로 토큰 버킷을 씁니다. AWS SDK가 이 방식으로 재시도 트래픽을 제한합니다.

### 백오프

백오프는 재시도 사이의 대기를 점점 늘리는 것입니다. 지수 백오프는 대기를 `base × 2^시도 횟수`로 늘리되 최대값(cap)을 둡니다. 바로 다시 보내면 과부하인 서버가 회복할 틈이 없습니다.

### 지터

지터(jitter)는 대기 시간에 무작위성을 더하는 것입니다. 지터가 없으면 같은 시점에 실패한 클라이언트들이 같은 시점에 재시도해서 부하가 파도처럼 반복됩니다(thundering herd). AWS Architecture Blog는 세 가지 방식을 비교합니다.

| 방식 | 대기 시간 | 특징 |
|------|-----------|------|
| Full Jitter | 0과 min(cap, base × 2^시도) 사이의 무작위 | 전체 작업량이 가장 적어 권장됨 |
| Equal Jitter | 계산값의 절반 + 무작위 절반 | 최소 대기를 보장 |
| Decorrelated Jitter | min(cap, 0과 이전 대기의 3배 사이 무작위) | 이전 대기에 의존 |

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function retry(fn, o = {}) {
  const { tries = 4, base = 200, cap = 5000 } = o;
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (err) {
      if (i + 1 >= tries || !err.retryable) throw err;
      const max = Math.min(cap, base * 2 ** i);
      await sleep(Math.random() * max); // Full Jitter
    }
  }
}
```

- `err.retryable`은 호출 코드가 연결 오류·타임아웃·5xx에 붙이는 표시입니다. 모든 에러를 재시도하지 않도록 판단을 분리합니다.
- 재시도 사이의 대기도 취소되어야 합니다. `timers/promises`의 `setTimeout(ms, undefined, { signal })`을 쓰면 종료 신호에 맞춰 멈출 수 있습니다(기초 22편).
- 작업 큐 라이브러리가 대신 해 주기도 합니다. BullMQ는 `attempts`로 횟수를, `backoff`로 fixed·exponential 지연을 정하고 `jitter` 옵션(0–1)으로 무작위성을 더합니다(중급 18편).

**흔한 실수:** 타임아웃 없이 재시도만 두는 것(재시도가 영원히 대기), 모든 에러를 재시도하는 것(400도 반복), 계층마다 재시도해 부하를 곱하는 것, 지터 없는 백오프입니다.

## 서킷 브레이커

서킷 브레이커는 실패가 기준을 넘은 호출을 잠시 막고 즉시 실패시켜, 고장 난 의존 서비스에 계속 요청을 보내 자원을 낭비하거나 복구를 방해하는 일을 막는 패턴입니다. 재시도는 "곧 성공할 것"을 기대하고, 서킷 브레이커는 "실패할 가능성이 큰 호출을 하지 않는 것"이 목적이라서 서로 다릅니다. 둘을 함께 쓸 때는 브레이커가 열려 있다는 오류가 오면 재시도를 멈춥니다.

상태는 세 가지이고 상태 기계로 동작합니다(Azure Circuit Breaker 패턴).

| 상태 | 동작 | 전이 |
|------|------|------|
| Closed | 요청을 그대로 통과시키고 최근 실패 수를 셈 | 정해진 기간 안에 실패가 임계값을 넘으면 Open |
| Open | 호출하지 않고 즉시 오류 반환, 타임아웃 타이머 시작 | 타이머가 끝나면 Half-Open |
| Half-Open | 제한된 수의 시험 요청만 통과 | 성공하면 Closed(카운터 초기화), 하나라도 실패하면 Open |

```js
function breaker(fn, max = 5, wait = 10_000) {
  let fails = 0, at = 0; // fails가 max 이상이면 Open
  return async (...args) => {
    const open = fails >= max;
    if (open && Date.now() - at < wait) throw Error('open');
    try {
      const r = await fn(...args); // open이면 Half-Open 시험
      fails = 0; return r;         // 성공 시 Closed
    } catch (e) {
      fails = open ? max : fails + 1; at = Date.now();
      throw e;
    }
  };
}
```

- 이 코드는 상태를 `fails`와 시각으로 유도하는 개념용 구현입니다. 대기 시간이 지나면 Half-Open에서 동시에 여러 요청이 통과하고 실패 종류도 가리지 않습니다. 실제로는 시험 요청 수를 제한하는 검증된 라이브러리를 씁니다.
- Closed 상태의 실패 카운터는 일정 간격으로 초기화되도록 시간 기반으로 둡니다. 가끔 나는 실패로 열리지 않게 하기 위해서입니다.
- 실패의 종류를 구분합니다. 400대 오류(호출자 잘못)는 의존 서비스의 고장이 아니므로 세지 않고, 타임아웃·연결 오류·5xx만 셉니다.
- 의존 대상(서비스, 샤드)별로 브레이커를 따로 둡니다. 하나로 합치면 멀쩡한 대상까지 막힙니다.
- Open일 때의 처리를 미리 정합니다. 오류를 돌려주거나, 캐시·기본값을 돌려줍니다(아래 "graceful degradation").
- 상태 전이를 메트릭과 로그로 남기고 Open이 되면 알림을 받습니다(11편).
- 타임아웃이 너무 길면 브레이커가 실패를 판단하기 전에 요청이 자원을 오래 붙잡습니다. 타임아웃이 먼저입니다.
- 서비스 메시나 프록시 계층에서 같은 기능을 제공하기도 합니다. 애플리케이션 코드와 겹쳐 중복 적용하지 않도록 정합니다.
- 메시지 기반 구조에서는 실패한 메시지를 데드 레터 큐로 보내는 것으로 충분한 경우가 많고, 로컬 메모리 같은 내부 자원에는 오버헤드만 늘립니다.

**흔한 실수:** 비즈니스 오류(재고 없음)까지 실패로 세서 정상 서비스를 막는 것, Half-Open 없이 일정 시간 뒤 모든 트래픽을 한꺼번에 돌려 회복 중인 서비스를 다시 쓰러뜨리는 것입니다.

## 벌크헤드

벌크헤드는 자원을 칸막이로 나눠, 한 부분의 과부하나 장애가 다른 부분까지 번지지 않게 하는 패턴입니다. 이름은 배의 선체 격벽에서 왔습니다. 한 칸이 침수돼도 배가 가라앉지 않습니다.

한 서비스가 응답하지 않을 때 그 호출이 연결·스레드 같은 공유 자원을 다 쓰면, 다른 서비스를 부르는 요청까지 막힙니다. 칸막이를 두는 단위는 다음과 같습니다.

| 나누는 대상 | 예 |
|-------------|----|
| 호출 대상별 | 대상 서비스마다 별도의 커넥션 풀·동시 실행 한도 |
| 소비자(테넌트)별 | 고객 등급이나 테넌트마다 한도·인스턴스 분리 |
| 작업 종류별 | 중요한 요청과 배치 작업의 워커·큐 분리 |
| 프로세스·컨테이너별 | CPU·메모리 한도가 있는 별도 컨테이너 |

Node.js에서는 대상별 동시 실행 수를 제한하는 세마포어가 가장 작은 구현입니다. 한도를 넘으면 대기시키거나 즉시 거절합니다.

```js
class Bulkhead {
  active = 0;
  constructor(limit) { this.limit = limit; }
  async run(fn) {
    if (this.active >= this.limit) {
      throw new Error('bulkhead full'); // 대기 대신 거절
    }
    this.active++;
    try { return await fn(); }
    finally { this.active--; }
  }
}
const payApi = new Bulkhead(20);
const mailApi = new Bulkhead(5);
```

- 결제 API가 느려져도 `payApi`의 20칸만 차고, `mailApi`나 다른 경로는 영향을 받지 않습니다.
- 대기열을 두면 요청이 쌓여 지연이 늘어나므로, 한도를 넘으면 빨리 거절하는 쪽이 보호에 유리한 경우가 많습니다.
- HTTP 클라이언트의 커넥션 수를 대상 호스트별로 나누는 방법도 있습니다. undici의 `Pool`은 하나의 origin에 대한 연결을 관리하고 `connections` 옵션으로 최대 연결 수를 정합니다(중급 07편).
- Node.js는 이벤트 루프가 하나라서 CPU 작업이 모든 요청을 막습니다. CPU 작업은 워커 스레드로 격리합니다(02편).
- 컨테이너나 Kubernetes의 CPU·메모리 한도, API 게이트웨이의 rate limit 같은 플랫폼 기능이 있으면 코드로 다시 만들지 않습니다.
- 칸막이가 많을수록 자원 활용률이 떨어지고 운영이 복잡해집니다. 핵심 경로와 위험한 의존성부터 나눕니다.
- 벌크헤드는 서킷 브레이커·재시도·rate limit과 함께 씁니다.

**흔한 실수:** 한도를 정한 근거 없이 임의의 숫자로 두는 것, 칸마다 사용량 지표를 보지 않는 것, 칸막이를 나눴지만 DB 같은 하위 공유 자원이 그대로여서 결국 같이 막히는 것입니다.

## 멱등성

멱등성(idempotency)은 같은 연산을 여러 번 해도 한 번 한 것과 결과가 같은 성질입니다. 재시도, 중복 전달, 사용자의 더블 클릭이 모두 같은 요청을 여러 번 보내기 때문에 안정성 패턴의 바탕이 됩니다. HTTP에서는 GET·PUT·DELETE가 멱등이고 POST는 아닙니다(RFC 9110, API 쪽은 13편).

| 연산 | 멱등 여부 |
|------|-----------|
| `SET balance = 100` | 멱등 |
| `balance = balance + 10` | 멱등 아님 |
| `INSERT`(유니크 제약 없음) | 멱등 아님 |
| `INSERT ... ON CONFLICT DO NOTHING` | 멱등 |
| 주문 상태를 PAID로 바꾸기 | 멱등(이미 PAID면 변화 없음) |

멱등하게 만드는 방법은 세 가지입니다.

1. 연산을 절대 값 지정(PUT, upsert)으로 바꿉니다. 증가 연산을 "이 값으로 설정"으로 바꿉니다.
2. 자연 키로 중복을 막습니다. 주문 번호나 결제 ID에 유니크 제약을 걸어 두 번째 삽입을 거부하거나 무시합니다.
3. 처리한 요청의 ID를 기록하고 중복을 건너뜁니다. 클라이언트의 멱등 키(13편)나 메시지의 고유 ID가 키가 됩니다.

메시지 소비자는 같은 메시지를 두 번 받을 수 있다고 가정합니다. 대부분의 큐가 최소 한 번(at-least-once) 전달이기 때문입니다. 처리 기록과 비즈니스 변경을 같은 DB 트랜잭션에 넣어야 "처리는 했는데 기록은 안 남음"이 생기지 않습니다.

```js
await db.transaction(async (tx) => {
  const ins = await tx.query(
    'INSERT INTO processed(msg_id) VALUES ($1) ' +
      'ON CONFLICT DO NOTHING',
    [msg.id],
  );
  if (ins.rowCount === 0) return; // 이미 처리됨
  await applyPayment(tx, msg.body);
});
```

- 처리 기록 테이블은 무한히 커지지 않게 보관 기간을 정해 지웁니다. 보관 기간은 재전달이 일어날 수 있는 최대 기간보다 길어야 합니다.
- 외부 API 호출 같은 부수 효과는 트랜잭션으로 되돌릴 수 없습니다. 외부 API가 멱등 키를 지원하면 메시지 ID를 키로 넘깁니다.

**흔한 실수:** "중복 확인 후 처리"를 두 단계로 나눠 두 요청이 동시에 통과하는 것, 증가·추가 연산을 재시도하는 것, 서버가 매번 새 키를 만드는 것입니다.

## 트랜잭션 아웃박스

트랜잭션 아웃박스(transactional outbox)는 DB 변경과 메시지 발행을 하나의 DB 트랜잭션 안에서 일어나게 하는 패턴입니다. 서비스가 DB를 갱신하고 이어서 브로커에 메시지를 보내는 "이중 쓰기"는 원자적이지 않아서, 커밋 후 발행 전에 프로세스가 죽으면 메시지가 사라지고, 발행 후 커밋이 실패하면 없는 데이터에 대한 메시지가 나갑니다. 분산 트랜잭션(2PC)으로 묶는 방법은 결합이 강하고 안정적이지 않습니다.

해법은 메시지를 브로커에 바로 보내지 않고, 같은 DB의 outbox 테이블에 행으로 저장하는 것입니다.

```sql
BEGIN;
UPDATE orders SET status = 'PAID' WHERE id = 42;
INSERT INTO outbox(id, topic, payload)
  VALUES (gen_random_uuid(), 'order.paid',
          '{"orderId":42}');
COMMIT; -- 둘 다 반영되거나 둘 다 취소됨
```

별도 프로세스인 메시지 릴레이가 outbox를 읽어 브로커에 발행하고 발행 표시를 남깁니다. 방법은 두 가지입니다(microservices.io).

| 방식 | 동작 | 특징 |
|------|------|------|
| 폴링 퍼블리셔 | 주기적으로 발행 안 된 행을 조회해 발행 | 구현이 단순, 지연과 조회 부하 |
| 트랜잭션 로그 테일링(CDC) | DB의 변경 로그를 읽어 발행 | 지연이 짧고 별도 도구 필요 |

```js
setInterval(async () => {
  const rows = await db.query(
    `SELECT * FROM outbox WHERE sent_at IS NULL
     ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED`,
  );
  for (const r of rows) {
    await broker.publish(r.topic, r.payload);
  }
  // 발행 후 sent_at 갱신(같은 트랜잭션 안에서)
}, 1000);
```

- 릴레이가 발행한 뒤 `sent_at`을 기록하기 전에 죽으면 같은 메시지를 다시 발행합니다. 전달은 최소 한 번이고, 소비자가 멱등해야 합니다(위 "멱등성"). 메시지에 고유 ID를 넣는 이유입니다.
- 한 번에 한 릴레이만 같은 행을 가져가게 하려면 행 잠금(`FOR UPDATE SKIP LOCKED`)을 씁니다. 이 문법은 PostgreSQL 등 일부 DB가 지원하므로 쓰는 DB의 문서를 확인합니다.
- 순서가 중요하면 키(예: 주문 ID)별로 순서를 유지하도록 발행합니다.
- 발행이 끝난 행은 주기적으로 지워 테이블이 커지지 않게 합니다.
- 인바운드의 멱등 소비자와 쌍으로 쓰면 "DB 변경은 정확히 한 번, 메시지는 최소 한 번 전달되고 처리는 한 번만 반영"되는 효과를 얻습니다.

**흔한 실수:** 트랜잭션 안에서 브로커를 호출하는 것(이중 쓰기가 그대로 남음), 릴레이가 하나뿐이라는 단일 장애점을 잊는 것, 소비자 쪽 멱등 처리를 빠뜨리는 것입니다.

## 사가 개요

사가(saga)는 여러 서비스에 걸친 작업을 서비스별 로컬 트랜잭션의 연속으로 나누고, 중간에 실패하면 이미 끝난 단계를 되돌리는 보상 트랜잭션으로 정리하는 패턴입니다. 서비스마다 DB가 따로면 하나의 DB 트랜잭션으로 묶을 수 없기 때문에 씁니다(구조는 12편).

주문 예시는 이렇습니다.

| 단계 | 로컬 트랜잭션 | 실패 시 보상 |
|------|---------------|--------------|
| 1 | 주문 서비스: 주문 생성(PENDING) | 주문 취소 |
| 2 | 재고 서비스: 재고 예약 | 재고 예약 해제 |
| 3 | 결제 서비스: 결제 승인 | 결제 취소(환불) |
| 4 | 주문 서비스: 주문 확정(CONFIRMED) | - |

3단계에서 결제가 실패하면 2단계의 재고 예약 해제, 1단계의 주문 취소를 역순으로 실행합니다.

조율 방식은 두 가지입니다.

| 방식 | 동작 | 장단점 |
|------|------|--------|
| 코레오그래피(choreography) | 각 서비스가 이벤트를 발행하고 다음 서비스가 그 이벤트를 받아 동작 | 중앙 조정자가 없어 결합이 낮지만 전체 흐름을 파악하기 어려움 |
| 오케스트레이션(orchestration) | 조정자가 각 서비스에 다음 로컬 트랜잭션을 지시 | 흐름이 한곳에 보이지만 조정자가 복잡해짐 |

- 사가는 ACID 중 격리(I)를 제공하지 않습니다. 사가가 진행되는 도중의 중간 상태를 다른 요청이 볼 수 있어서, 데이터 이상이 생기지 않도록 별도의 대책을 설계해야 합니다. 예: 상태 값으로 PENDING 구간을 명시하고 그 상태의 주문은 수정하지 못하게 막기.
- 보상은 롤백이 아닙니다. 이미 외부에 나간 이메일이나 결제처럼 되돌릴 수 없는 일은 "취소"라는 새로운 일을 하는 것입니다. 보상 자체도 실패할 수 있어서 멱등하고 재시도 가능해야 합니다.
- 각 단계의 상태 전이를 DB에 저장하고, 단계 사이의 메시지 전달은 아웃박스로 보장합니다.
- 사가가 필요 없게 하는 것이 먼저입니다. 서로 자주 함께 바뀌는 데이터는 한 서비스(한 DB)에 두는 편이 단순합니다. 모놀리식이면 일반 DB 트랜잭션으로 충분합니다.

**흔한 실수:** 보상 트랜잭션 없이 정상 경로만 만드는 것, 사가의 중간 상태를 노출해 사용자에게 잘못된 정보를 보이는 것, 보상을 재시도할 수 없게 만드는 것입니다.

## 큐 기반 비동기 처리

큐 기반 비동기 처리는 요청을 받은 쪽이 작업을 큐에 넣고 바로 응답하고, 별도의 워커가 큐에서 꺼내 처리하는 방식입니다. 큐가 요청 수신과 처리 속도 사이의 완충 장치가 되어 순간적인 폭주를 평탄하게 만듭니다(Azure의 Queue-Based Load Leveling 패턴).

```js
// API: 접수만 하고 즉시 응답
app.post('/reports', async (req, res) => {
  const opts = { attempts: 5 };
  const job = await queue.add('report', req.body, opts);
  res.status(202).json({ jobId: job.id }); // 202 Accepted
});
// 워커: 별도 프로세스에서 처리
new Worker('report', async (job) => build(job.data));
```

- 얻는 것: 서비스가 잠시 죽어도 요청을 받아 둘 수 있고(가용성), 워커 수로 처리량을 조절하고(확장성), 평균 부하에 맞춰 자원을 잡을 수 있습니다(비용).
- 접수 응답은 202 Accepted와 작업 ID를 주고, 결과는 조회 API, 웹훅(13편), 푸시로 알립니다. 호출자가 즉시 결과가 필요한 경우에는 맞지 않습니다.
- 워커 수를 무작정 늘리면 부하가 큐에서 하위 시스템(DB, 외부 API)으로 옮겨갈 뿐입니다. 워커 동시성과 처리 속도에 상한을 둡니다.
- 생산 속도가 소비 속도보다 계속 빠르면 큐가 쌓여 지연이 늘어납니다. 큐 길이와 가장 오래된 메시지의 나이를 감시하고, 한계를 넘으면 생산 쪽에서 요청을 거절합니다(11편).
- 큐는 내구성이 있어야 합니다. 메모리 큐는 프로세스가 죽으면 작업을 잃으므로 Redis나 메시지 브로커처럼 저장하는 큐를 씁니다(중급 18편).
- 전달은 대부분 최소 한 번이므로 작업은 멱등해야 합니다. 병렬 소비자 사이의 순서는 보장되지 않습니다. 순서가 필요하면 순서 보장 기능을 쓰거나, 순서 없이도 맞게 설계합니다.
- 워커가 종료 신호를 받으면 처리 중인 작업을 마치고 나서 종료하고, 못 마친 작업은 다시 큐에 돌아가게 합니다(중급 25편).
- 큐에 들어가기 전에 DB에 변경을 저장했다면 둘 사이가 이중 쓰기가 되므로 아웃박스를 씁니다.

**흔한 실수:** 큐를 넣고 최종 실패를 감시하지 않는 것, 큐에 큰 데이터를 통째로 넣는 것(ID만 넣고 워커가 조회), 사용자가 기다리는 요청을 큐로 돌려 오히려 느리게 만드는 것입니다.

## 데드 레터 큐

데드 레터 큐(DLQ)는 정해진 횟수만큼 처리에 실패한 메시지를 따로 옮겨 두는 큐입니다. 계속 실패하는 메시지(독이 든 메시지, poison message)가 원래 큐에서 재시도를 반복하며 뒤의 정상 메시지를 막는 일을 막고, 실패한 메시지를 보관해 원인을 분석하게 합니다.

Amazon SQS의 예로 동작은 다음과 같습니다.

- 소스 큐에 redrive policy를 두고 `maxReceiveCount`를 정합니다. 소비자가 메시지를 그 횟수만큼 받고도 삭제하지 못하면 DLQ로 이동합니다.
- 값을 너무 낮게 잡으면 일시적 실패 한 번에 DLQ로 가므로, 충분한 재시도가 가능한 값으로 둡니다.
- DLQ의 메시지는 로그의 예외 확인, 내용 분석, 소비자의 처리 시간이 충분했는지 점검에 쓰고, 원인을 고친 뒤 redrive로 원래 큐에 되돌립니다.
- DLQ는 같은 계정·리전의 별도 큐로 먼저 만들어야 합니다. 표준 큐에서는 메시지의 만료가 원래 큐에 들어간 시각을 기준으로 하므로, DLQ의 보관 기간은 원래 큐보다 길게 잡는 것이 좋습니다.
- 메시지 순서가 중요한 FIFO 큐에 DLQ를 쓰면 순서가 깨질 수 있으므로 주의하라고 문서가 안내합니다.

운영 규칙은 다음과 같습니다.

- DLQ에 메시지가 들어오면 알림을 받습니다. 쌓이기만 하고 아무도 보지 않으면 데이터를 조용히 버리는 것과 같습니다.
- 메시지에 실패 이유, 시도 횟수, 원래 큐 이름, 추적 ID를 붙여 분석할 수 있게 합니다.
- 재처리(redrive)는 소비자가 멱등하다는 전제에서 합니다. 일부만 골라 다시 보내는 도구도 준비합니다.
- 실패를 구분합니다. 일시적 실패는 백오프로 재시도하고, 영구 실패(형식 오류, 없는 참조)는 재시도 없이 바로 DLQ로 보냅니다. BullMQ는 사용자 정의 백오프 함수가 -1을 반환하면 재시도하지 않고 작업을 실패로 표시합니다. 실패한 메시지를 보관하는 방식은 도구마다 다르므로 쓰는 도구의 문서를 확인합니다.

**흔한 실수:** DLQ를 만들고 알림을 달지 않는 것, 모든 실패를 `maxReceiveCount` 횟수만큼 재시도해 영구 실패에 자원을 쓰는 것, DLQ 보관 기간이 짧아 분석하기 전에 사라지는 것입니다.

## graceful degradation

graceful degradation(우아한 성능 저하)은 의존하는 구성 요소가 실패해도 핵심 기능은 유지하고 나머지를 줄여 제공하는 설계입니다. AWS Well-Architected는 오래된 데이터, 대체 데이터, 심지어 데이터 없음으로 응답하더라도 핵심 가치는 전달하는 것을 목표로 두고, 필수 의존성(hard)을 선택 의존성(soft)으로 바꾸라고 안내합니다.

| 의존성 실패 | 저하된 응답 |
|-------------|-------------|
| 개인화 추천 서비스 | 인기 상품 목록(고정 기본값) |
| 캐시 서버 | DB에서 직접 조회(느리지만 동작) |
| 부가 정보(리뷰, 배송 예상일) | 해당 영역을 빼고 나머지 렌더링 |
| 외부 환율 API | 마지막으로 성공한 값(오래됨 표시) |
| 로그·메트릭 전송 | 비즈니스 처리는 계속, 전송은 버퍼링·건너뜀 |
| 쓰기용 DB의 일시 장애 | 요청을 큐에 접수하고 나중에 반영(읽기는 복제본) |

```js
async function getHome(userId) {
  const rec = await recommend(userId).catch(() => null);
  const items = rec ?? POPULAR_DEFAULT;
  return { items, degraded: rec === null };
}
```

- 먼저 핵심 기능과 부가 기능을 구분합니다. 이것은 기술이 아니라 비즈니스 결정입니다. 결제는 일관성이, 실시간 서비스는 가용성이 우선일 수 있습니다.
- 저하 경로는 정상 경로보다 훨씬 단순해야 하고, 장애를 주입해 테스트해야 합니다. 테스트하지 않은 대체 경로는 필요할 때 동작하지 않기 쉽습니다. AWS 문서는 일반적으로 복잡한 폴백은 피하라고 덧붙입니다.
- 도구는 앞의 패턴들입니다. 타임아웃으로 빠르게 실패하고, 서킷 브레이커가 열려 있는 동안 기본값이나 캐시를 반환하고, 벌크헤드로 부가 기능의 자원 사용을 제한합니다.
- 일부 결과만 반환하는 경우 응답에 저하 상태를 표시해 클라이언트가 알 수 있게 합니다. 오래된 데이터를 쓸 때는 얼마나 오래됐는지 보여 줍니다.
- 캐시를 비우는 로직이 갱신 실패 시 로컬 상태를 지워 버리면 오히려 장애를 키웁니다. 갱신에 실패하면 이전 값을 유지합니다.
- 부분 실패를 일관성 없는 상태로 남기지 않습니다. 쓰기 작업은 전체 성공 또는 전체 실패(또는 보상)로 끝나야 합니다.
- 저하 상태가 얼마나 자주, 얼마나 오래 일어나는지 메트릭으로 봅니다(11편). 눈에 안 띄는 저하가 계속되면 장애를 가리게 됩니다.

**흔한 실수:** 부가 기능 하나가 죽었다고 페이지 전체가 500이 되는 것, 모든 의존성을 필수로 취급하는 것, 로그 전송 같은 비필수 호출이 요청 경로를 막는 것입니다.

## 분산 락의 한계

분산 락은 여러 프로세스나 서버가 하나의 자원을 동시에 건드리지 않도록 서로 배타적으로 접근하게 하는 장치입니다. 흔히 Redis에 키를 만들어 구현합니다. 단일 인스턴스 방식은 다음과 같습니다(Redis 문서).

```text
SET resource_name my_random_value NX PX 30000
```

- `NX`는 키가 없을 때만 설정하고, `PX 30000`은 30초 뒤 자동으로 해제되게 합니다. 락을 쥔 프로세스가 죽어도 영원히 잠기지 않도록 만료가 필요합니다.
- 값은 클라이언트마다 고유한 무작위 값입니다. 해제할 때 키의 값이 내 값일 때만 지워야, 만료된 뒤 다른 클라이언트가 얻은 락을 내가 지우는 사고를 막습니다. 이를 위해 Lua 스크립트(Redis 8.4부터는 `DELEX`)를 씁니다.

락의 문제는 만료(리스) 때문에 "락을 가졌다고 믿는 시간"과 "실제로 가진 시간"이 어긋난다는 데 있습니다.

| 한계 | 설명 |
|------|------|
| 프로세스 정지 | GC나 지연으로 멈춘 사이 락이 만료되면, 깨어난 프로세스는 락을 잃은 줄 모르고 쓰기를 진행함. 쓰기 직전에 만료를 확인해도 확인과 쓰기 사이에 멈출 수 있음 |
| 복제의 비동기성 | 마스터가 락을 기록하고 복제 전에 죽어 복제본이 승격되면 다른 클라이언트가 같은 락을 얻음 |
| 시계 가정 | Redlock은 프로세스 시계가 대략 같은 속도로 흐른다고 가정하고, Redis의 TTL은 단조 시계가 아님. 시간이 점프하면 락이 둘이 될 수 있음 |
| 가용성 | 락을 쥔 클라이언트가 분리되면 TTL만큼 기다려야 하고, 락 서버가 죽으면 락 자체를 못 얻음 |

Redlock은 독립된 Redis 마스터 N대(예: 5대)의 과반수에서 락을 얻는 알고리즘입니다. Redis 문서는 정합성이 중요하면 펜싱 토큰을 구현하고, Redis TTL이 단조 시계를 쓰지 않는다는 점을 유의하라고 적습니다. Martin Kleppmann은 락의 용도를 둘로 나눕니다.

- 효율용: 같은 일을 중복해서 하지 않으려는 것. 가끔 실패하면 이메일이 두 번 가는 정도. 단일 Redis로 충분합니다.
- 정합성용: 동시에 쓰면 데이터가 깨지는 것. 락만으로는 위험하고 펜싱 토큰이 필요합니다.

펜싱 토큰(fencing token)은 락을 얻을 때마다 단조 증가하는 번호를 발급하고, 저장소가 쓰기 요청의 번호를 확인해 이미 더 큰 번호를 본 적이 있으면 오래된 요청을 거절하는 방식입니다. 락을 얻고 번호 33을 받은 클라이언트가 멈춘 사이 다른 클라이언트가 34를 받아 쓰면, 깨어난 쪽의 33번 쓰기는 거절됩니다. 단, 저장소가 토큰을 검사할 수 있어야 하고 Redlock은 단조 증가하는 토큰을 만들지 않습니다.

락이 필요 없도록 설계하는 것이 먼저입니다.

- DB의 유니크 제약, 조건부 갱신(`UPDATE ... WHERE version = $1`), 낙관적 락(버전 컬럼)으로 충돌을 감지합니다. 충돌하면 재시도합니다.
- 한 번에 하나만 처리해야 하는 일은 큐의 키별 순차 처리(파티션)나 단일 소비자로 풀 수 있습니다.
- 중복 실행이 무해하도록 연산을 멱등하게 만듭니다(위 "멱등성"). 효율용 락은 이 위에 최적화로 얹습니다.
- 반드시 락을 써야 하면 DB의 행 잠금이나 어드바이저리 락처럼 같은 저장소의 트랜잭션과 묶이는 수단을 우선 검토합니다.
- 락을 쓸 때는 만료를 작업 시간보다 충분히 길게 잡고, 필요하면 연장하되 횟수를 제한하며, 락을 쥔 채 외부 호출을 하지 않습니다.

**흔한 실수:** 락이 있으니 절대 동시에 실행되지 않는다고 믿는 것, 만료 시간이 작업보다 짧은 것, 해제할 때 값을 확인하지 않고 키를 지우는 것, 정합성이 필요한 곳에 효율용 락을 쓰는 것입니다.

## 핵심 정리

- 모든 나가는 호출에 타임아웃을 두고, 멱등한 연산의 일시적 실패만 상한이 있는 지수 백오프와 Full Jitter로 한 계층에서만 재시도합니다.
- 서킷 브레이커는 Closed·Open·Half-Open 상태 기계로 실패하는 호출을 막고, 벌크헤드는 대상별로 자원을 나눠 장애 전파를 막습니다.
- 재시도·중복 전달에 대비해 연산을 멱등하게 만들고, DB 변경과 메시지 발행은 아웃박스로 묶고 소비자는 중복을 걸러냅니다.
- 여러 서비스에 걸친 작업은 사가의 로컬 트랜잭션과 보상 트랜잭션으로 나누되, 격리가 없다는 점을 설계로 보완합니다.
- 큐는 폭주를 완충하고 DLQ는 계속 실패하는 메시지를 격리하며, DLQ에는 알림과 재처리 절차가 있어야 합니다.
- 부가 기능 실패는 기본값·캐시로 저하시켜 핵심을 유지하고, 분산 락은 만료와 정지 때문에 정합성을 보장하지 못하므로 펜싱 토큰, DB 제약, 멱등성으로 대체합니다.

## cluster

`node:cluster`는 서버 포트를 공유하는 Node.js 자식 프로세스를 쉽게 만들게 해 주는 모듈입니다. 안정성 지수는 2(Stable)이고 v0.10.0부터 있습니다. 프로세스를 여러 개 띄워 여러 CPU 코어를 쓰는 것이 목적입니다.

- 처음 실행되는 프로세스를 primary(주 프로세스), 그가 만든 자식을 worker(워커)라고 부릅니다. 워커는 `child_process.fork()`로 만들어져서 primary와 IPC 채널로 통신합니다(01편).
- 프로세스 격리가 필요 없으면 문서는 `worker_threads`를 쓰라고 안내합니다(02편).
- 워커 수는 자동으로 관리되지 않습니다. 죽은 워커를 다시 띄우는 것도 애플리케이션이 직접 합니다.

```js
import cluster from 'node:cluster';
import http from 'node:http';
import { availableParallelism } from 'node:os';

if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) {
    cluster.fork();
  }
} else {
  http.createServer((req, res) => {
    res.end(`worker ${cluster.worker.id}\n`);
  }).listen(8000);
}
```

같은 파일을 primary와 워커가 모두 실행합니다. `cluster.isPrimary`로 역할을 나눕니다(v16.0.0에 추가되었고 이전 이름 `isMaster`는 지원 중단 상태입니다).

| API | 설명 |
|-----|------|
| `cluster.fork([env])` | 워커 생성. primary에서만 호출 |
| `cluster.workers` | primary에서 살아 있는 워커 객체 모음 |
| `cluster.worker` | 워커 안에서 자기 자신의 `Worker` 객체 |
| `worker.id`, `worker.process` | 워커 번호, 내부 `ChildProcess` |
| `worker.send(msg)` | primary가 워커에 메시지 전송 |
| `worker.disconnect()` | 서버를 닫고 연결이 끝나면 IPC 채널을 닫아 정상 종료시킴 |
| `worker.kill([signal])` | 정상 종료를 기다리지 않고 종료(기본 `'SIGTERM'`) |
| `worker.exitedAfterDisconnect` | `disconnect()`로 자발적으로 종료했으면 `true` |
| 이벤트 | `fork`, `online`, `listening`, `message`, `disconnect`, `exit` |

워커가 죽으면 `exit` 이벤트로 알 수 있고, 비정상 종료인지는 `exitedAfterDisconnect`로 구분합니다.

```js
cluster.on('exit', (worker, code, signal) => {
  if (!worker.exitedAfterDisconnect) {
    cluster.fork(); // 비정상 종료만 다시 띄움
  }
});
```

- 로컬 확인(Node.js 24): `process.exit(1)`로 끝난 워커는 `exitedAfterDisconnect`가 `false`였고, `worker.disconnect()`로 끝난 워커는 `true`였습니다.
- 위 재시작 코드에는 상한이 없습니다. 시작하자마자 죽는 워커는 무한히 다시 만들어지므로 횟수나 간격을 제한합니다.
- 워커가 하나라도 살아 있으면 서버는 연결을 계속 받습니다. 하나도 없으면 기존 연결은 끊기고 새 연결은 거부됩니다.
- 워커는 서로 독립된 프로세스라서 하나를 죽이거나 다시 띄워도 나머지에 영향이 없습니다. 이 성질이 무중단 재시작의 바탕입니다. 새 워커를 먼저 띄우고 기존 워커를 `disconnect()`하면, 닫힌 서버의 새 연결은 다른 워커가 받습니다.
- `disconnect()`는 서버 연결만 기다립니다. 워커가 직접 연 클라이언트 연결은 자동으로 닫히지 않고, 오래 사는 연결은 종료를 막을 수 있습니다. 문서는 타임아웃 후 `kill()`하는 방식을 권합니다.
- `cluster.setupPrimary({ exec, args, silent })`로 워커가 실행할 파일과 인수를 바꿀 수 있습니다. 이미 실행 중인 워커에는 영향이 없습니다.

## 같은 포트를 여러 프로세스가

보통 서로 다른 프로세스가 같은 포트를 `listen()`하면 두 번째는 `EADDRINUSE` 에러가 납니다(로컬 확인). cluster는 워커의 `server.listen()` 호출을 primary에 넘겨서 이 문제를 해결합니다. 포트를 실제로 여는 쪽은 primary이고, 워커들은 그 소켓의 연결을 나눠 받습니다.

- 워커가 `listen()`을 호출하면 메시지가 primary로 전달됩니다. 대부분의 일을 primary가 하므로 일반 프로세스와 다른 경우가 셋 있습니다.

| 호출 | 클러스터 워커에서의 동작 |
|------|--------------------------|
| `listen({ fd: 7 })` | 워커가 아니라 primary의 7번 fd를 열고 핸들을 워커에 전달 |
| `listen(handle)` | 넘긴 핸들을 워커가 직접 사용. primary와 통신하지 않음 |
| `listen(0)` | 무작위 포트이지만 모든 워커가 같은 포트를 받음(처음만 무작위, 이후는 예측 가능) |

- 워커마다 다른 포트가 필요하면 워커 `id`로 포트 번호를 계산합니다.
- Windows에서는 워커에서 이름 있는 파이프(named pipe) 서버를 만들 수 없습니다.
- TCP 서버뿐 아니라 워커 프로세스가 필요한 다른 용도에도 쓸 수 있지만 주 용도는 네트워크 서버입니다.

클러스터 없이도 OS 차원에서 같은 포트를 공유하는 방법이 있습니다. `net`의 `listen()`에 `reusePort: true`를 주면 같은 호스트의 여러 소켓이 한 포트에 바인딩되고, 들어오는 연결을 OS가 분배합니다(v23.1.0, v22.12.0에 추가). 지원하는 플랫폼은 Linux 3.9 이상, FreeBSD 12.0 이상 등으로 제한되고 지원하지 않는 플랫폼에서는 에러가 납니다. 로컬 Windows에서는 `ENOTSUP`이 발생했습니다.

## 라운드 로빈 개념

라운드 로빈(round-robin)은 요청을 대기열 순서대로 하나씩 돌아가며 배정하는 분배 방식입니다. 워커 3개이면 연결이 1, 2, 3, 1, 2, 3번 워커 순으로 갑니다.

cluster는 연결 분배 방식을 두 가지 지원합니다.

| 정책 | 상수 | 동작 |
|------|------|------|
| 라운드 로빈 | `cluster.SCHED_RR` | primary가 포트를 열고 새 연결을 받아 워커에 돌아가며 분배. 한 워커에 과부하가 걸리지 않게 하는 보호 장치가 있음 |
| OS 위임 | `cluster.SCHED_NONE` | primary가 만든 listen 소켓을 워커에 넘기고, 워커가 직접 `accept` |

- `SCHED_RR`이 Windows를 제외한 모든 OS의 기본값입니다. Windows의 기본값은 `SCHED_NONE`입니다.
- OS 위임 방식은 이론상 성능이 가장 좋지만, 문서에 따르면 실제로는 OS 스케줄러 때문에 분배가 매우 불균형해집니다. 8개 프로세스 중 2개가 연결의 70퍼센트 이상을 받은 사례가 관찰되었다고 합니다.
- 정책은 `cluster.schedulingPolicy`로 바꾸거나 환경변수 `NODE_CLUSTER_SCHED_POLICY`(`'rr'` 또는 `'none'`)로 정합니다. 첫 워커를 만들거나 `setupPrimary()`를 호출하는 순간 사실상 고정됩니다.
- 분배 단위는 요청이 아니라 연결입니다. HTTP keep-alive로 연결을 재사용하는 클라이언트는 같은 워커에 계속 붙습니다(중급 06편).

```js
cluster.schedulingPolicy = cluster.SCHED_RR; // fork 전에 설정
// 연결을 매번 새로 열면 워커가 돌아가며 응답
// w1:1 w2:1 w3:1 w1:2 w2:2 w3:2 w1:3 w2:3 w3:3
```

- 로컬 실험(Node.js 24, Windows, 워커 3개, 연결 9개를 `agent: false`로 매번 새로 엶): 기본값(`SCHED_NONE`)에서는 9개가 모두 한 워커로 갔고, `SCHED_RR`로 바꾸자 위 결과처럼 고르게 돌아갔습니다.
- 라운드 로빈은 요청의 비용 차이를 모릅니다. 느린 요청이 한 워커에 몰리면 다른 워커가 놀아도 순서대로 배정됩니다. 문서가 말하는 보호 장치는 이를 일부 완화할 뿐입니다.

## 프로세스 간 메모리는 안 공유

워커는 별개의 프로세스라서 각자 자기 힙과 변수를 가집니다. 한 워커가 바꾼 모듈 변수, 캐시, 카운터는 다른 워커에 보이지 않습니다.

```js
let count = 0; // 워커마다 따로 존재
http.createServer((req, res) => {
  res.end(`w${cluster.worker.id}:${++count}`);
}).listen(8000);
// w1:1 w2:1 w3:1 w1:2 w2:2 w3:2 ... (전체 합이 아니라 워커별 카운트)
```

- 메모리 사용량도 합산됩니다. 워커 N개는 코드와 의존성을 N번 로드하므로 대략 N배의 메모리를 씁니다.
- 문서는 Node.js가 라우팅 로직을 제공하지 않으니 세션과 로그인 같은 상태를 메모리에 두는 설계에 크게 의존하지 말라고 경고합니다. 같은 사용자의 요청이 다음에는 다른 워커로 갈 수 있기 때문입니다.
- 공유가 필요하면 방법은 둘입니다.
  - 프로세스 사이의 메시지: 워커의 `process.send()`와 primary의 `cluster.on('message')`. 집계처럼 소량의 값에 맞습니다.
  - 외부 저장소: Redis나 DB에 상태를 둡니다. 세션, 캐시, 소켓 연결 정보가 여기에 속합니다(중급 18편).
- `SharedArrayBuffer`는 한 프로세스 안의 스레드끼리의 공유 메모리이고 프로세스 경계를 넘지 못합니다(02편).

```js
// 워커
process.send({ type: 'hit' });
// primary
cluster.on('message', (worker, msg) => {
  if (msg.type === 'hit') hits++;
});
```

**흔한 실수:** 메모리 캐시나 `Map`에 담은 세션을 클러스터 전체가 공유한다고 믿는 것입니다. 로그인 직후 다음 요청이 다른 워커로 가면 세션이 없다고 나옵니다(중급 27편).

## 스케일 아웃과 클러스터 차이

스케일 업(scale up)은 한 대의 성능을 올리는 것이고, 스케일 아웃(scale out)은 같은 일을 하는 인스턴스를 더 늘려 분산하는 것입니다. 클러스터는 한 호스트 안에서 프로세스를 늘리지만 같은 호스트의 CPU와 메모리를 나눠 쓰므로, 호스트나 컨테이너를 늘리는 스케일 아웃과는 범위가 다릅니다.

| 항목 | 클러스터 | 인스턴스·컨테이너 복제 |
|------|----------|--------------------------|
| 범위 | 한 호스트의 CPU 코어 | 여러 호스트·여러 컨테이너 |
| 분배 | primary 프로세스(`cluster`) | 외부 로드 밸런서 |
| 장애 범위 | 호스트가 죽으면 전부 중단 | 일부 인스턴스만 중단 |
| 상태 공유 | 프로세스 간 불가(메시지만) | 외부 저장소만 가능 |
| 한계 | 호스트 자원 | 인스턴스 수와 외부 저장소 |
| 관리 | 애플리케이션이 직접 | 오케스트레이터·클라우드 서비스 |

- 둘은 배타적이지 않습니다. 한 대의 큰 서버에서 클러스터로 코어를 모두 쓰고, 그 서버를 여러 대 두고 로드 밸런서로 묶을 수 있습니다.
- 12-factor 앱은 프로세스를 일급 시민으로 보고, 같은 프로세스를 여러 개·여러 머신에 늘리는 수평 확장을 전제합니다. 개별 VM은 한계까지만 커질 수 있다고 설명합니다.
- 코어를 쓰는 데 클러스터를 먼저 고르기 전에, CPU 바운드 계산이 병목이면 워커 스레드(02편)가, 외부 대기가 병목이면 확장이 도움이 되지 않을 수 있으니 병목부터 측정합니다(04편).

## PM2 클러스터 모드

PM2는 Node.js용 프로덕션 프로세스 매니저이고, 클러스터 모드는 코드를 고치지 않고 네트워크 애플리케이션(http, https, tcp, udp 서버)을 CPU 코어 전체로 확장하는 기능입니다. 내부는 Node.js의 `cluster` 모듈을 사용합니다.

```sh
pm2 start app.js -i max
```

`-i` 옵션(설정 파일에서는 `instances`)의 값은 다음과 같습니다.

| 값 | 의미 |
|----|------|
| `0` 또는 `max` | 모든 CPU에 분산 |
| `-1` | 모든 CPU에서 하나 뺀 수 |
| 숫자 | 지정한 수만큼 |

```js
// ecosystem 파일 (PM2 문서의 CommonJS 형식)
module.exports = {
  apps: [{
    script: 'api.js',
    instances: 'max',
    exec_mode: 'cluster',
  }],
};
```

- `instances`를 지정하면 클러스터 모드가 자동으로 켜집니다. `exec_mode: 'cluster'`는 생략해도 되지만 명확하게 하려고 쓰는 것을 문서가 권합니다.
- `pm2 reload <앱 이름>`은 프로세스를 죽였다 띄우는 `restart`와 달리 다운타임 없이 다시 로드합니다. 로드에 실패하면 시간 초과 후 일반 재시작으로 돌아갑니다.
- 정상 종료(graceful shutdown)를 위해 `SIGINT`를 받아 DB 연결 등을 정리한 뒤 `process.exit()`합니다. PM2가 종료 때 가장 먼저 보내는 시그널이 `SIGINT`입니다.
- PM2는 애플리케이션이 무상태(stateless)여야 한다고 안내합니다. 세션과 웹소켓 연결 같은 상태를 프로세스에 두지 말고 Redis, Mongo 같은 곳에 둡니다.
- PM2 설정 파일은 08편에서 이어서 다룹니다.

## 로드 밸런서와 무상태 설계

로드 밸런서(load balancer)는 들어오는 요청을 여러 인스턴스에 나눠 보내는 장치입니다. nginx 같은 소프트웨어일 수도 있고, 클라우드의 ALB 같은 관리형 서비스일 수도 있습니다. 클러스터의 primary가 하는 일을 호스트 바깥에서 하는 것과 같습니다.

- 로드 밸런서는 기본적으로 각 요청을 독립적으로 분배합니다. 같은 사용자의 연속된 요청이 다른 인스턴스로 갈 수 있다는 뜻입니다.
- 무상태(stateless) 설계는 프로세스가 요청과 요청 사이의 상태를 자기 메모리나 디스크에 기대지 않는 설계입니다. 어느 인스턴스가 요청을 받아도 같은 결과가 나옵니다.
- 12-factor는 프로세스를 무상태·공유 없음으로 두고 유지해야 할 데이터는 데이터베이스 같은 백엔드 서비스에 저장하라고 설명합니다. 메모리나 디스크 캐시는 한 요청 안의 임시 용도로만 쓰고, 다음 요청이 같은 프로세스에 도달할 것이라고 가정하지 않습니다.
- 재시작, 배포, 재배치로도 로컬 상태는 사라집니다. 무상태여야 인스턴스를 늘리거나 버리는 것이 쉽습니다.

| 상태 종류 | 프로세스 메모리에 둘 때의 문제 | 둘 곳 |
|-----------|-----------------------------|-------|
| 로그인 세션 | 다른 인스턴스에서 세션이 없음 | 쿠키 기반 토큰, 또는 Redis 세션 저장소 |
| 캐시 | 인스턴스마다 값이 달라지고 무효화가 어려움 | Redis 같은 공유 캐시 |
| 업로드 파일 | 다른 인스턴스에서 파일을 못 찾음 | 객체 스토리지 |
| 실시간 연결 정보 | 연결이 있는 인스턴스만 알고 있음 | 브로커나 어댑터로 인스턴스 간 전달 |

## sticky session

sticky session(session affinity)은 로드 밸런서가 한 사용자의 세션을 특정 대상에 묶어 그 사용자의 요청을 계속 같은 대상으로 보내는 기능입니다. AWS ALB 문서도 상태 정보를 유지하는 서버에서 연속된 경험을 주기 위해 쓰는 기능이라고 설명하고, 사용하려면 클라이언트가 쿠키를 지원해야 한다고 적습니다.

| 방식 | 설명 |
|------|------|
| 쿠키 기반 | 로드 밸런서가 만든 쿠키(또는 애플리케이션 쿠키)로 대상을 식별. ALB는 기간 기반과 애플리케이션 기반을 지원 |
| IP 기반 | 클라이언트 IP로 대상을 정함. nginx `ip_hash`는 같은 클라이언트 주소의 요청을 같은 서버로 보냄 |
| 식별자 기반 | URL이나 헤더의 세션 식별자를 사용 |

- 꼭 필요한 대표 사례는 Socket.IO의 HTTP long-polling처럼 같은 세션 ID의 요청이 처음 연결을 맺은 프로세스로 가야 하는 프로토콜입니다. Socket.IO 문서는 sticky session, long-polling 비활성화, 클라이언트 측 분산을 선택지로 제시합니다.
- 12-factor는 메모리에 세션을 두고 같은 프로세스로 라우팅되기를 기대하는 sticky session을 12-factor 위반으로 규정하고, 세션 상태는 만료를 지원하는 Redis나 Memcached에 두라고 권합니다.
- sticky는 분산을 불균형하게 만들 수 있습니다. 한 대상이 죽으면 거기에 묶인 세션의 메모리 상태는 사라집니다. ALB는 쿠키가 만료되면 더는 sticky가 아니라고 설명합니다.
- 클러스터에는 sticky 기능이 내장되어 있지 않습니다. 앞단 로드 밸런서에서 처리하거나, 필요하면 별도 라이브러리를 씁니다.
- 판단 순서는 먼저 무상태로 만들 수 있는지 검토하고, 프로토콜 때문에 어쩔 수 없을 때만 sticky를 씁니다.

## 컨테이너 환경에서 클러스터를 쓰지 않는 이유

컨테이너에서는 컨테이너 안에서 프로세스를 늘리지 않고 컨테이너 자체를 늘리는 쪽이 일반적입니다. 문서가 클러스터를 금지하는 것은 아닙니다. Docker 문서도 컨테이너당 하나의 서비스를 권장하지만 그 서비스가 여러 프로세스로 갈라지는 것은 허용된다고 적습니다. 아래는 선택을 굳히는 설계 근거입니다.

- **복제는 바깥의 일입니다.** Docker 모범 사례는 컨테이너 하나에 관심사 하나만 두면 수평 확장이 쉬워진다고 설명합니다. 컨테이너를 몇 개 띄울지, 죽은 컨테이너를 다시 띄울지는 오케스트레이터(Kubernetes 등)나 서비스(ECS 등)가 맡습니다. 클러스터는 같은 일을 컨테이너 안에서 한 번 더 합니다.
- **CPU 한도가 보통 작습니다.** 컨테이너에 CPU 한도를 주면 워커를 많이 만들어도 한도 안에서 시간을 나눠 쓸 뿐입니다. `os.availableParallelism()`이 의존하는 libuv 문서는 Linux에서 CPU 친화도 마스크를 확인한다고만 적고 컨테이너의 CPU 쿼터는 언급하지 않습니다. 쿼터로 제한된 컨테이너에서 호스트의 코어 수가 나와 워커가 과하게 만들어질 수 있으니 값을 직접 확인해서 씁니다.
- **관측과 장애 단위가 흐려집니다.** 컨테이너 하나가 프로세스 하나일 때 메모리 사용량, 재시작 횟수, 헬스체크, 로그가 컨테이너 단위로 정확히 대응합니다. 워커 하나가 메모리 한도를 넘으면 컨테이너 전체가 영향받을 수 있습니다.
- **시그널과 종료 처리가 복잡해집니다.** 컨테이너의 주 프로세스가 PID 1이 되는데, primary가 PID 1이면 종료 시그널을 받아 워커들을 정상 종료시키고 고아 프로세스를 정리하는 일을 맡아야 합니다. Docker 문서도 주 프로세스가 자식 정리를 제대로 못 하는 경우를 경고합니다(08편).
- **무상태와 빠른 시작·종료가 전제입니다.** 12-factor의 폐기 가능성(disposability)은 프로세스가 `SIGTERM`을 받으면 새 연결을 거부하고 진행 중인 요청을 마친 뒤 끝나기를 요구합니다. 컨테이너 하나에 프로세스 하나이면 이 책임이 단순합니다.

| 환경 | 선택 |
|------|------|
| 컨테이너(ECS, Kubernetes 등)에서 코어가 작게 할당됨 | 프로세스 하나로 실행하고 컨테이너(Pod)를 복제 |
| 코어가 많은 큰 컨테이너 하나로 운영해야 함 | 클러스터 또는 PM2가 선택지. 시그널과 메모리 한도를 직접 검증 |
| 컨테이너 없이 VM 한 대에 직접 배포 | PM2 클러스터 모드나 `cluster`로 코어 사용 |
| 서버리스 | 인스턴스 분배를 플랫폼이 담당하므로 해당 없음(10편) |

- PM2는 컨테이너용 `pm2-runtime`을 제공합니다. 컨테이너가 받은 종료 시그널을 애플리케이션에 전달하고, 기본적으로 1600ms 뒤에 `SIGKILL`을 보냅니다(`kill_timeout`으로 조정). 컨테이너 안에서 PM2를 쓰는 것은 가능하지만 클러스터 모드까지 켜는 이유는 위 근거로 따로 따져야 합니다.
- 컨테이너 구성은 09편에서 다룹니다.

## 핵심 정리

- cluster는 primary가 `fork()`로 워커 프로세스를 만들고, 워커의 `listen()`을 primary가 받아 포트 하나를 여러 프로세스가 공유하게 합니다. 워커 수와 재시작은 애플리케이션이 관리합니다.
- 연결 분배는 라운드 로빈(Windows를 뺀 기본값)과 OS 위임이 있고, 분배 단위는 요청이 아니라 연결입니다. OS 위임은 실제로 불균형해지기 쉽습니다.
- 워커는 메모리를 공유하지 않으므로 세션·캐시 같은 상태는 외부 저장소(Redis, DB)에 두고, 소량의 값은 IPC 메시지로 주고받습니다.
- 클러스터는 한 호스트 안의 확장이고, 스케일 아웃은 여러 인스턴스를 로드 밸런서로 묶는 확장입니다. 둘은 함께 쓸 수 있습니다.
- PM2 클러스터 모드는 `-i max`나 `instances`로 코드 변경 없이 `cluster`를 쓰고 `pm2 reload`로 무중단 재시작을 합니다. 무상태 설계가 전제입니다.
- sticky session은 같은 사용자를 같은 대상에 묶는 최후의 수단이며, 컨테이너에서는 프로세스 하나를 복제하는 구성이 일반적입니다.

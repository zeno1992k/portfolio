## 시맨틱 버전

시맨틱 버전(Semantic Versioning, semver)은 버전을 `MAJOR.MINOR.PATCH` 세 숫자로 쓰고, 어느 자리가 올랐는지로 변경의 크기를 알리는 규칙입니다. npm은 패키지를 `1.0.0`에서 시작하라고 안내합니다.

| 변경 | 올리는 자리 | 예 |
|------|-------------|----|
| 하위 호환되는 버그 수정 | PATCH | `1.0.0` → `1.0.1` |
| 하위 호환되는 기능 추가 | MINOR | `1.0.0` → `1.1.0` |
| 호환되지 않는 변경 | MAJOR | `1.0.0` → `2.0.0` |

- MAJOR나 MINOR를 올리면 오른쪽 자리는 0으로 되돌립니다. `1.4.2`에서 MINOR를 올리면 `1.5.0`입니다.
- `1.2.3-beta.2`처럼 뒤에 `-`를 붙인 것은 프리릴리스(prerelease)입니다. 정식 `1.2.3`보다 낮은 버전으로 취급합니다.
- semver는 패키지 작성자의 약속입니다. 실제로 지켜졌는지는 도구가 검증하지 못합니다.
- `package.json`의 의존성에는 버전 하나가 아니라 허용하는 버전의 범위를 적습니다. 범위 문법은 다음 절부터 봅니다. 설치 명령은 12편, 의존성 필드는 11편에서 다룹니다.

## 캐럿 범위

캐럿(`^`)은 가장 왼쪽의 0이 아닌 자리를 바꾸지 않는 범위입니다. `1.0.0` 이상에서는 MINOR와 PATCH 변경을 허용합니다. `npm install`이 `package.json`에 적는 기본 접두사이기도 합니다.

```text
^1.2.3  :=  >=1.2.3 <2.0.0
^1.2    :=  >=1.2.0 <2.0.0
^1      :=  >=1.0.0 <2.0.0
```

```js
// ^1.2.3 이 허용하는가
// 1.2.9  → 허용 (PATCH)
// 1.9.0  → 허용 (MINOR)
// 2.0.0  → 거부 (MAJOR)
```

- 프리릴리스는 기본으로 제외됩니다. `^1.2.3`은 `1.3.0-beta.1`을 허용하지 않습니다. 범위에 같은 `1.2.3` 튜플의 프리릴리스(`^1.2.3-beta.2`)를 적으면 그 튜플의 프리릴리스만 허용됩니다.
- 범위가 허용하는 버전 중 무엇이 설치되는지는 lock 파일이 정합니다(자세히는 12편).

## 0.x 버전의 캐럿 규칙

캐럿은 `0.x` 버전을 다르게 취급합니다. 가장 왼쪽의 0이 아닌 자리가 호환성 경계이기 때문입니다. 많은 작성자가 `0.x`에서는 MINOR를 호환성이 깨지는 자리로 쓴다는 관행을 반영한 규칙입니다.

| 범위 | 풀어 쓴 범위 | 허용하는 변경 |
|------|--------------|---------------|
| `^1.2.3` | `>=1.2.3 <2.0.0` | MINOR, PATCH |
| `^0.2.3` | `>=0.2.3 <0.3.0` | PATCH만 |
| `^0.0.3` | `>=0.0.3 <0.0.4` | 없음(정확히 `0.0.3`) |
| `^0.0` | `>=0.0.0 <0.1.0` | PATCH |
| `^0.x` | `>=0.0.0 <1.0.0` | MINOR, PATCH |

- `^0.2.3`은 `0.2.9`를 허용하지만 `0.3.0`은 거부합니다.
- 자리를 생략하면 그 자리는 0으로 보되 유연하게 허용합니다. 그래서 `^0.0.3`과 `^0.0`은 결과가 다릅니다.

**흔한 실수:** `^`가 항상 MINOR까지 올려 준다고 믿는 것입니다. `0.x` 패키지에서는 `^0.2.3`이 `0.3.0`으로 올라가지 않아, 새 버전이 나왔는데 설치되지 않는 것처럼 보입니다.

## 틸드 범위

틸드(`~`)는 MINOR가 적혀 있으면 PATCH 변경만, 없으면 MINOR 변경까지 허용합니다.

```text
~1.2.3  :=  >=1.2.3 <1.3.0
~1.2    :=  >=1.2.0 <1.3.0   (1.2.x 와 같음)
~1      :=  >=1.0.0 <2.0.0   (1.x 와 같음)
~0.2.3  :=  >=0.2.3 <0.3.0
```

- `~1.2.3`은 `1.2.9`를 허용하고 `1.3.0`은 거부합니다.
- 같은 버전에서 캐럿이 더 넓습니다. `^1.2.3`은 `<2.0.0`, `~1.2.3`은 `<1.3.0`까지입니다.
- npm 문서는 PATCH만 허용하는 표기로 `1.0`, `1.0.x`, `~1.0.4`를, MINOR와 PATCH를 허용하는 표기로 `1`, `1.x`, `^1.0.4`를 안내합니다.
- 일부 자리를 비운 `1.2`, `1`은 X-range로 처리됩니다. `x`, `X`, `*`가 그 자리에 어떤 숫자든 허용한다는 뜻입니다.

| 표기 | 의미 |
|------|------|
| `1.2.x` | `>=1.2.0 <1.3.0` |
| `1.x` | `>=1.0.0 <2.0.0` |
| `*` 또는 빈 문자열 | 모든 정식 버전 |

그 밖의 문법도 있습니다.

| 문법 | 예 | 의미 |
|------|----|------|
| 비교 | `>=1.2.0 <2.0.0` | 공백으로 이으면 AND |
| 구간 | `1.2.3 - 2.3.4` | `>=1.2.3 <=2.3.4` |

- 합집합은 `||`로 잇습니다. `^1.0.0 || ^2.0.0`은 둘 중 하나를 만족하면 됩니다.

## 정확한 버전

`"1.2.3"`처럼 범위 기호 없이 적으면 그 버전과 정확히 일치해야 합니다. 새 버전이 자동으로 허용되지 않습니다.

```bash
npm install lodash@4.17.21 --save-exact
# package.json: "lodash": "4.17.21"
```

- `--save-exact`(`-E`)는 설치한 버전을 범위 연산자 없이 그대로 적습니다.
- 정확한 버전은 `package.json`만 보고도 어떤 버전인지 알 수 있고 의도하지 않은 업그레이드가 없습니다. 대신 보안 패치를 직접 올려야 합니다.
- 직접 의존성을 정확히 고정해도 그 패키지가 가진 하위 의존성은 범위로 풀립니다. 전체 재현성은 lock 파일이 보장합니다.
- 애플리케이션은 lock 파일로 고정하고 범위를 쓰는 편이 흔합니다. 다른 프로젝트가 가져다 쓰는 라이브러리는 범위를 지나치게 좁히지 않는 편이 낫습니다.

## latest와 dist-tag

dist-tag는 버전 번호 대신 쓰는 이름표(alias)입니다. `latest`는 기본 태그로, 패키지를 발행하면 `--tag`를 따로 주지 않는 한 그 버전에 `latest`가 붙습니다. 버전을 지정하지 않은 `npm install pkg`는 `latest` 태그의 버전을 설치합니다.

```bash
npm install express          # latest 태그가 가리키는 버전
npm dist-tag ls express      # 태그 목록과 가리키는 버전
```

- `latest`는 이름표이지 "가장 높은 번호"가 아닙니다. 작성자가 다른 버전으로 옮길 수 있습니다.
- `package.json`에 `"pkg": "latest"`를 적을 수도 있지만, 설치할 때마다 달라지는 버전을 받게 되므로 의존성에는 권하지 않습니다.

## 태그로 설치

`npm install pkg@tag`는 그 태그가 가리키는 버전을 설치합니다. 같은 자리에 정확한 버전(`pkg@1.2.3`)이나 범위(`pkg@^1.2.0`)도 쓸 수 있습니다.

```bash
npm install react@next       # next 태그의 버전
npm install react@18.3.1     # 정확한 버전
npm install react@^18.0.0    # 범위에 맞는 최신 버전
```

- 많은 프로젝트가 곧 나올 버전을 `next` 태그로 공개합니다. `next`는 관례일 뿐 특별한 의미는 아닙니다.
- 작성자는 `npm publish --tag beta`로 `latest` 대신 다른 태그로 발행할 수 있습니다. 그러면 일반 `npm install pkg`는 그 버전을 받지 않습니다.
- `npm dist-tag add`와 `npm dist-tag rm`으로 태그를 붙이고 뗍니다. `ls`가 기본 동작입니다.
- 태그 이름은 유효한 semver 범위로 해석되면 안 되고 숫자나 `v`로 시작할 수 없습니다. `v1.4`는 거부됩니다.

## npx

`npx`는 npm 패키지의 실행 파일을 실행하는 명령입니다. 로컬에 설치된 것이든 원격에서 받아 오는 것이든 `npm run`과 비슷한 환경에서 실행합니다.

```bash
npx eslint .                 # 로컬에 설치돼 있으면 그것을 실행
npx create-vite@latest app   # 없으면 내려받아 실행
npx -p typescript tsc -v     # -p: 패키지 지정
```

- 먼저 프로젝트의 로컬 의존성에서 찾습니다. 없으면 npm 캐시에 내려받고 PATH에 추가해 실행합니다.
- 실행 파일 이름은 패키지의 `bin` 필드에서 정합니다(자세히는 10편). 이름이 패키지와 다르면 `-p`(`--package`)로 패키지를 지정합니다.
- 로컬에 없는 패키지를 받을 때는 확인을 묻습니다. `--yes`는 묻지 않고 진행하고 `--no`는 거부합니다.
- 패키지 이름 뒤에 `@버전`을 붙여 버전을 지정합니다. `npx pkg@1.2.3`입니다.
- `--`는 npm의 옵션 해석을 끝내고 나머지를 명령에 그대로 넘깁니다.
- `npm exec`와 기능이 같습니다. `npx`는 옵션을 위치 인수보다 앞에 써야 하고, `npm exec`는 `--`로 둘을 나눕니다.

**흔한 실수:** 오타 난 패키지 이름을 `--yes`로 실행하는 것입니다. 이름이 비슷한 다른 패키지를 받아 실행하게 됩니다. 원격에서 받는 패키지는 설치 후 곧바로 실행되므로 출처를 확인합니다.

## npm run

`npm run <이름>`은 `package.json`의 `scripts`에 적힌 명령을 실행합니다(별칭은 `run-script`, `rum`, `urn`). 이름 없이 `npm run`만 쓰면 사용 가능한 스크립트 목록을 보여 줍니다.

```json
{
  "scripts": {
    "build": "tsc",
    "lint": "eslint .",
    "test": "node --test"
  }
}
```

```bash
npm run build
npm run test -- --test-name-pattern=add
```

- 스크립트는 현재 위치가 어디든 패키지 루트에서 실행됩니다. 기본 셸은 Unix에서 `/bin/sh`, Windows에서 `cmd.exe`이고 `--script-shell`로 바꿉니다.
- `--` 뒤의 인수는 npm이 해석하지 않고 스크립트에 넘깁니다. 이 인수는 `pre`·`post` 스크립트에는 전달되지 않습니다.
- `--if-present`를 주면 스크립트가 없어도 에러를 내지 않습니다. 선택적인 단계를 CI에서 부를 때 씁니다.
- `--ignore-scripts`는 스크립트 실행을 막습니다.
- `npm test`, `npm start`처럼 `run` 없이 쓸 수 있는 이름이 있습니다(`test`, `start`, `stop`, `restart`).
- `npm start`는 `start` 스크립트가 없고 `server.js` 파일이 있으면 `node server.js`를 실행합니다.
- npm이 스크립트 실행 중 환경변수를 설정합니다. `npm_package_name`, `npm_package_version`, `npm_lifecycle_event`(실행 중인 단계), `INIT_CWD`(npm을 부른 디렉터리)가 그 예입니다.

## pre와 post 스크립트

스크립트 이름 앞에 `pre`나 `post`를 붙인 스크립트는 그 스크립트의 앞뒤에서 npm이 자동으로 실행합니다. 내장 스크립트와 직접 만든 스크립트 모두 해당합니다.

```json
{
  "scripts": {
    "prebuild": "node clean.mjs",
    "build": "tsc",
    "postbuild": "node copy-assets.mjs"
  }
}
```

`npm run build`는 `prebuild`, `build`, `postbuild` 순서로 실행합니다. 앞 단계가 실패하면 뒤 단계는 실행되지 않습니다.

npm이 특정 명령에서 부르는 수명 주기(life cycle) 스크립트도 있습니다.

| 명령 | 실행 순서 |
|------|-----------|
| `npm install` | `preinstall`, `install`, `postinstall`, `prepublish`, `preprepare`, `prepare`, `postprepare` |
| `npm publish` | `prepublishOnly`, `prepack`, `prepare`, `postpack`, `publish`, `postpublish` |
| `npm test` | `pretest`, `test`, `posttest` |
| `npm start` | `prestart`, `start`, `poststart` |

- `prepare`는 패키징 전과 인수 없는 로컬 `npm install` 때 실행됩니다. 빌드 결과물을 만드는 용도로 씁니다.
- `prepublishOnly`는 `npm publish` 때만 실행됩니다.
- `prepublish`는 사용을 권하지 않는(deprecated) 이름입니다. 발행 때와 설치 때 모두 실행되어 혼란을 줬습니다.
- 의존성 패키지의 `install` 계열 스크립트도 설치 중 실행됩니다. 공급망 위험이라서 `--ignore-scripts`로 끄는 방법을 14편에서 다룹니다.

**흔한 실수:** `npm run build -- --watch`처럼 넘긴 인수가 `prebuild`와 `postbuild`에도 전달된다고 가정하는 것입니다. `--` 뒤의 인수는 지정한 스크립트에만 전달됩니다.

## 로컬 설치

로컬 설치는 `npm install pkg`로 현재 프로젝트의 `node_modules`에 설치하는 기본 방식입니다. `package.json`에 의존성으로 기록되어 팀원과 CI가 같은 것을 받습니다.

- 패키지는 `./node_modules`에, 그 패키지가 제공하는 실행 파일은 `./node_modules/.bin`에 링크됩니다.
- 코드에서 `import`나 `require`로 쓰려면 로컬에 설치해야 합니다.
- 프로젝트마다 다른 버전을 쓸 수 있습니다.
- 개발 중에만 쓰는 도구(린터, 빌드 도구)는 `--save-dev`로 설치해 `devDependencies`에 기록합니다(자세히는 11편).
- 현재 프로젝트의 `node_modules` 위치는 `npm root`로 확인합니다.

## 전역 설치

전역 설치는 `-g` 옵션으로 `prefix` 폴더에 설치해 어느 디렉터리에서든 명령으로 쓰게 하는 방식입니다.

```bash
npm install -g typescript
npm root -g       # 전역 node_modules 위치
npm prefix -g     # 전역 prefix 위치
```

| 구분 | Unix | Windows |
|------|------|---------|
| 패키지 | `{prefix}/lib/node_modules` | `{prefix}/node_modules` |
| 실행 파일 | `{prefix}/bin` | `{prefix}` |
| 기본 prefix | `/usr/local` | `%AppData%\npm` |

- npm 문서의 지침은 코드에서 불러 쓸 것은 로컬에, 명령줄에서 실행할 것은 전역에 설치하라는 것입니다.
- 코드에서 `import`나 `require`로 불러 쓰려면 로컬에 설치해야 합니다.
- 전역 패키지는 프로젝트 `package.json`에 기록되지 않아서 환경마다 버전이 다르고 팀이 재현하기 어렵습니다. 프로젝트가 쓰는 도구는 로컬에 설치하고 `npm run`이나 `npx`로 실행하는 편이 안전합니다.
- 전역 설치 위치는 `prefix` 설정이 정합니다. Node.js 버전 관리자를 쓰는 환경은 02편을 봅니다.

## PATH와 로컬 bin

실행 파일을 이름만으로 실행할 수 있는 것은 그 파일이 있는 디렉터리가 `PATH` 환경변수에 들어 있기 때문입니다. 셸은 `PATH`의 디렉터리를 순서대로 훑어 이름이 같은 파일을 찾습니다.

- 전역 설치한 명령은 전역 `bin` 디렉터리가 `PATH`에 있어야 실행됩니다.
- 로컬 설치한 명령은 `node_modules/.bin`에 있고, 이 디렉터리는 기본으로 `PATH`에 없습니다. 셸에서 `eslint`를 바로 치면 찾지 못합니다.
- `npm run`으로 실행하는 스크립트에서는 npm이 `PATH`에 `node_modules/.bin`을 자동으로 추가합니다. 그래서 스크립트에는 `eslint .`만 적어도 됩니다.
- 셸에서 직접 실행하려면 `npx eslint .`이나 `./node_modules/.bin/eslint .`로 씁니다.
- 로컬 `bin`에 있는 항목은 패키지의 `bin` 필드가 만든 링크입니다(자세히는 10편).

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:abs": "./node_modules/.bin/eslint ."
  }
}
```

두 스크립트는 같은 파일을 실행합니다. 첫 번째 방식을 씁니다.

**흔한 실수:** 로컬에만 설치한 도구를 셸에 그대로 쳐서 `command not found`를 만나는 것입니다. 해결은 `npx`, `npm run`, 또는 전역 설치 중 하나입니다.

## node --run

`node --run <스크립트>`는 `package.json`의 `scripts`를 npm 없이 Node.js가 직접 실행하는 옵션입니다. Node.js 22.0.0에서 추가되었습니다.

```bash
node --run build
node --run test -- --verbose
```

- 현재 디렉터리에서 위로 올라가며 `package.json`을 찾고, 그 파일이 있는 디렉터리에서 실행합니다.
- 각 상위 디렉터리의 `node_modules/.bin`이 디렉터리로 존재하면 `PATH` 앞에 붙입니다.
- `--` 뒤의 인수는 스크립트 끝에 덧붙습니다.
- `NODE_RUN_SCRIPT_NAME`(실행 중인 스크립트 이름)과 `NODE_RUN_PACKAGE_JSON_PATH`(처리 중인 `package.json` 경로) 환경변수를 설정합니다.

`npm run`과 같게 동작하도록 만든 기능이 아니고, 가장 흔한 용도에서 빠르게 실행하려고 일부러 기능을 제한했습니다. 다음은 제외된 기능입니다.

| 항목 | `npm run` | `node --run` |
|------|-----------|--------------|
| `pre`, `post` 스크립트 | 함께 실행 | 실행하지 않음 |
| 패키지 관리자 환경변수(`npm_*`) | 설정 | 설정하지 않음 |

- `--env-file`로 불러온 환경변수는 `--run`이 실행하는 명령에는 적용되지 않습니다.
- Node.js 26 문서에는 v26.9.0에서 이름 없이 `--run`을 실행하면 사용 가능한 스크립트를 나열하고 0이 아닌 종료 코드로 끝난다는 변경이 기록되어 있습니다.

**흔한 실수:** `npm run build`를 `node --run build`로 바꾸고 `prebuild`가 실행되지 않는 것을 놓치는 것입니다. `pre`와 `post`에 의존하는 프로젝트는 스크립트에 단계를 직접 이어 적어야 합니다.

## 핵심 정리

- semver는 `MAJOR.MINOR.PATCH`이고 범위 기호가 허용하는 변경의 크기를 정합니다. 캐럿은 가장 왼쪽의 0이 아닌 자리를 고정하고, 틸드는 MINOR가 있으면 PATCH만 허용합니다.
- `^0.2.3`은 `0.3.0`을 허용하지 않고 `^0.0.3`은 그 버전만 허용합니다.
- `latest`는 기본 dist-tag이며 번호가 가장 높은 버전이 아니라 작성자가 가리킨 버전입니다. `pkg@tag`, `pkg@버전`, `pkg@범위`로 설치합니다.
- `npx`는 로컬 실행 파일을 우선 실행하고 없으면 내려받아 실행합니다. `npm run`은 `scripts`를 실행하며 `pre`와 `post` 스크립트를 앞뒤로 자동 실행합니다.
- 코드에서 불러 쓸 것은 로컬, 명령줄 도구는 전역이지만 프로젝트 도구는 로컬이 안전합니다. `node_modules/.bin`은 `npm run`·`npx`·`node --run` 안에서만 `PATH`에 들어갑니다.
- `node --run`은 `pre`와 `post`를 실행하지 않고 `npm_*` 변수를 설정하지 않습니다.

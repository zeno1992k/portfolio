## 에러 우선 콜백

에러 우선 콜백(error-first callback)은 Node.js의 오래된 비동기 규약입니다. 비동기 함수가 마지막 인수로 콜백을 받고, 콜백의 첫 번째 인수에 에러를, 두 번째 인수부터 결과를 담아 호출합니다.

```js
import { readFile } from 'node:fs'

readFile('a.txt', 'utf8', (err, data) => {
  if (err) {
    console.error(err.code) // 예: ENOENT
    return
  }
  console.log(data)
})
```

- 성공하면 `err`는 `null`이고, 실패하면 `Error` 객체입니다. 공식 문서는 첫 인수가 `null`이 아니고 `Error`의 인스턴스이면 에러가 난 것이라고 설명합니다.
- 콜백 안에서 에러 검사를 먼저 하고 `return`으로 빠져나옵니다. `return`을 빼먹으면 에러 뒤에 성공 처리 코드까지 실행됩니다.
- 콜백이 호출되는 시점의 에러는 `try`와 `catch`로 잡을 수 없습니다. 함수를 부른 코드가 이미 끝난 뒤에 호출되기 때문입니다. 에러는 첫 인수로만 전달됩니다.
- 콜백은 항상 비동기로 호출해야 합니다. 결과가 캐시에 있다고 콜백을 즉시 호출하고, 없을 때만 나중에 호출하면, 호출하는 쪽이 실행 순서를 예측하지 못합니다. 즉시 줄 수 있어도 `process.nextTick`이나 `queueMicrotask`로 미룹니다(자세히는 04편).

```js
function get(key, cb) {
  if (cache.has(key)) {
    process.nextTick(cb, null, cache.get(key)) // ✅ 항상 비동기
    return
  }
  load(key, cb)
}
```

## 콜백을 두 번 호출하면 안 되는 이유

콜백은 "작업이 끝났다"는 신호로 한 번만 호출되어야 합니다. 두 번 호출하면 호출한 쪽의 후속 처리가 두 번 실행됩니다.

```js
function bad(cb) {
  doWork((err, data) => {
    if (err) cb(err)        // ❌ return이 없어 아래도 실행됨
    cb(null, data)          // 에러 뒤에 성공 콜백이 또 호출됨
  })
}
```

- 결제를 두 번 처리하거나, 이미 보낸 응답에 헤더를 다시 쓰려다 `ERR_HTTP_HEADERS_SENT`가 나거나, 같은 자원을 두 번 해제하는 식으로 터집니다.
- 대부분 에러 분기에 `return`을 빼먹어서 생깁니다. `if (err) return cb(err)`로 쓰면 막을 수 있습니다.
- 성공 콜백 호출 자체를 `try` 안에 넣는 구조도 위험합니다. 콜백이 던진 예외를 `catch`가 받아서 `cb(err)`를 한 번 더 호출합니다.

```js
function bad2(cb) {
  try {
    cb(null, compute())  // cb 안에서 예외가 나면
  } catch (err) {
    cb(err)              // ❌ cb가 다시 호출됨
  }
}
```

- Promise는 한 번 이행되거나 거부되면 상태가 고정되어 이 문제를 구조적으로 막습니다(아래 "Promise").

## 콜백 지옥

콜백 지옥(callback hell)은 순서대로 해야 하는 비동기 작업을 콜백 안에 콜백으로 이어 붙여 코드가 오른쪽으로 계속 들여쓰기되는 형태입니다.

```js
readFile('a.json', 'utf8', (err, a) => {
  if (err) return done(err)
  readFile('b.json', 'utf8', (err, b) => {
    if (err) return done(err)
    writeFile('c.json', a + b, (err) => {
      if (err) return done(err)
      done(null)
    })
  })
})
```

- 문제는 들여쓰기만이 아닙니다. 단계마다 에러 검사를 반복해야 하고, 한 곳에서 빠뜨리면 에러가 사라지며, 반복·병렬·조건 분기를 짜기 어렵습니다.
- 임시로 완화하는 방법은 콜백에 이름을 붙여 평평하게 펴는 것입니다. 이름 있는 함수로 분리하면 들여쓰기는 줄지만 흐름은 여전히 여러 함수에 흩어집니다.
- 근본 해결은 Promise와 `async`/`await`로 바꾸는 것입니다. 같은 작업이 위에서 아래로 읽힙니다(아래 "async와 await").

## promisify

`util.promisify(original)`은 에러 우선 콜백을 마지막 인수로 받는 함수를 Promise를 반환하는 함수로 바꿉니다(v8.0.0, `node:util`은 Stable). 콜백이 `err`를 받으면 거부, 아니면 두 번째 인수로 이행합니다.

```js
import { readFile } from 'node:fs'
import { promisify } from 'node:util'

const readFileP = promisify(readFile)
try {
  const text = await readFileP('a.txt', 'utf8')
} catch (err) {
  console.error(err.code)
}
```

규칙은 다음과 같습니다.

- `promisify`는 마지막 인수가 콜백이라고 항상 가정합니다. 콜백을 받지 않는 함수에 쓰면 Promise가 영원히 이행되지 않을 수 있습니다.
- 콜백이 결과를 여러 개 받아도 Promise는 첫 번째 결과만 돌려줍니다. 여러 값이 필요한 API는 `original[util.promisify.custom]`으로 변환 방식이 따로 정해져 있습니다.
- 메서드를 꺼내서 넘기면 `this`를 잃습니다. 공식 문서도 클래스 메서드에 `promisify`를 쓸 때 별도 처리가 필요하다고 안내합니다.

```js
const bar = promisify(foo.bar)
await bar()            // ❌ TypeError (this가 undefined)
await bar.call(foo)    // ✅
await promisify(foo.bar.bind(foo))() // ✅
```

- 이미 Promise를 반환하는 함수에 `promisify`를 쓰는 것은 v20.8.0부터 문서상 사용 중단(deprecated)입니다.
- 많은 Node.js 모듈은 처음부터 Promise 버전을 제공합니다(`node:fs/promises`, `node:timers/promises` 등). 있다면 `promisify`보다 그것을 씁니다(자세히는 16편, 22편).
- 반대 방향의 `util.callbackify(asyncFn)`은 Promise를 반환하는 함수를 에러 우선 콜백 함수로 바꿉니다. 콜백을 요구하는 옛 API에 `async` 함수를 넘길 때 씁니다.

## Promise

Promise는 비동기 작업의 최종 결과(성공 값 또는 실패 이유)를 나중에 받는 객체입니다. 상태는 세 가지입니다.

| 상태 | 뜻 |
|------|----|
| pending | 아직 끝나지 않음 |
| fulfilled | 성공해서 값이 정해짐 |
| rejected | 실패해서 이유가 정해짐 |

```js
const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve('ok'), 100)
})
p.then((v) => console.log(v))   // ok
 .catch((e) => console.error(e))
 .finally(() => console.log('끝'))
```

- 상태는 한 번 fulfilled나 rejected가 되면 바뀌지 않습니다. `resolve`나 `reject`를 여러 번 불러도 첫 번째만 적용됩니다. 콜백의 두 번 호출 문제가 생기지 않는 이유입니다.
- 실행자(executor) 함수 안에서 던진 예외는 자동으로 거부로 바뀝니다.
- `then`, `catch`, `finally`는 새 Promise를 반환해서 체이닝됩니다. `then` 안에서 값을 반환하면 다음 `then`의 입력이 되고, Promise를 반환하면 그것이 끝나기를 기다립니다.
- `then` 안에서 던진 예외는 체인 아래의 `catch`로 갑니다.
- `then`, `catch`, `finally`의 콜백은 마이크로태스크로 실행됩니다(자세히는 04편).

```js
Promise.resolve(1)
  .then((v) => v + 1)
  .then((v) => { throw new Error(`fail ${v}`) })
  .catch((e) => e.message)   // 'fail 2' 반환
  .then((v) => console.log(v)) // fail 2
```

**흔한 실수:** 체인 중간의 `then` 안에서 값을 `return`하지 않는 것입니다. 다음 `then`은 `undefined`를 받습니다. 중첩된 Promise 앞에 `return`을 빼먹으면 그 Promise를 기다리지 않고 지나갑니다.

## async와 await

`async` 함수는 항상 Promise를 반환하는 함수이고, `await`는 Promise가 끝날 때까지 `async` 함수의 실행을 멈추고 결과 값을 꺼냅니다. 콜백 지옥의 예를 다시 쓰면 다음과 같습니다.

```js
import { readFile, writeFile } from 'node:fs/promises'

async function merge() {
  const a = await readFile('a.json', 'utf8')
  const b = await readFile('b.json', 'utf8')
  await writeFile('c.json', a + b)
}
```

- `async` 함수가 값을 `return`하면 그 값으로 이행하는 Promise가 반환되고, 예외를 던지면 거부된 Promise가 반환됩니다.
- `await`는 Promise가 이행되면 값을 돌려주고, 거부되면 그 이유를 예외로 던집니다. 그래서 `try`와 `catch`로 잡을 수 있습니다.
- `await`는 이벤트 루프를 막지 않습니다. 그 `async` 함수만 멈추고 다른 코드는 계속 실행되며, 함수 본문은 `await`를 만나기 전까지는 호출 즉시 동기로 실행됩니다.
- `await` 뒤에 Promise가 아닌 값을 써도 됩니다. 그 값이 그대로 돌아오지만 마이크로태스크 한 번만큼은 양보합니다.
- ES Modules의 최상위에서는 `async` 함수 없이 `await`를 쓸 수 있습니다(top-level await, 자세히는 09편). CommonJS에서는 안 됩니다.

```js
async function run() {
  console.log('1')       // 호출 즉시 실행
  await null
  console.log('3')       // 마이크로태스크에서 이어서 실행
}
run()
console.log('2')
// 1, 2, 3
```

## 동기 throw

동기 throw는 함수가 Promise를 돌려주기 전에 즉시 던지는 예외입니다. `async`가 아닌 함수가 인수를 검사하다 던지는 경우가 해당합니다.

```js
function load(id) {
  if (!id) throw new Error('id required') // 동기 throw
  return fetchUser(id)                    // Promise 반환
}
load().catch(() => {}) // ❌ 함수가 던져서 .catch에 닿지 못함
```

- 같은 함수가 어떤 때는 던지고 어떤 때는 거부된 Promise를 반환하면, 호출하는 쪽이 `try`/`catch`와 `.catch` 두 가지를 모두 써야 합니다.
- `async` 함수는 이 문제를 없앱니다. 본문에서 동기로 던진 예외도 호출자에게 던져지지 않고 거부된 Promise가 됩니다.

```js
async function load(id) {
  if (!id) throw new Error('id required')
  return fetchUser(id)
}
load().catch((e) => console.log(e.message)) // id required
```

- Promise를 반환하는 함수는 `async`로 선언해서 실패를 항상 거부로 통일합니다.
- 일부러 즉시 던지는 API도 있습니다. `setTimeout`에 함수가 아닌 값을 주면 `ERR_INVALID_ARG_TYPE` 코드의 `TypeError`를 동기로 던집니다. 공식 문서의 에러 설명이 어느 쪽인지 확인합니다(자세히는 25편).
- 콜백 안이나 `setTimeout` 콜백 안의 동기 throw는 바깥 `try`/`catch`로 잡히지 않고 처리되지 않은 예외가 됩니다(자세히는 24편).

## rejected promise

거부된 Promise(rejected promise)는 실패 이유를 가진 채 끝난 Promise입니다. 거부를 만드는 길은 세 가지입니다.

- 실행자에서 `reject(err)`를 호출하거나 예외를 던진다.
- `then`, `catch` 안에서 예외를 던진다.
- `async` 함수 안에서 예외를 던지거나 거부된 Promise를 `await`한다.

거부는 어디선가 처리되어야 합니다. `await` 주위의 `try`/`catch`나 `.catch()`로 처리합니다. 처리되지 않으면 처리되지 않은 거부(unhandled rejection)가 됩니다. Node.js 15.0.0부터 기본 모드가 `throw`라서 `unhandledRejection` 핸들러가 없으면 처리되지 않은 예외로 올라가 프로세스가 종료됩니다(자세히는 24편).

```js
async function job() {
  try {
    await mightFail()
  } catch (err) {
    console.error('failed:', err.message)
  }
}
```

**흔한 실수:** `try` 안에서 Promise를 `await` 없이 `return`하는 것입니다. `async` 함수가 Promise를 그대로 반환하면 거부가 함수 밖에서 일어나서 안쪽 `catch`에 닿지 않습니다.

```js
async function f1() {
  try { return rejects() }        // ❌ catch가 실행되지 않음
  catch { return 'handled' }
}
async function f2() {
  try { return await rejects() }  // ✅ catch가 실행됨
  catch { return 'handled' }
}
```

- 거부 이유와 던지는 값은 `Error` 객체(또는 그 하위 클래스)로 통일합니다. 문자열이나 `null`을 거부 이유로 쓰면 스택과 `code`가 없습니다(자세히는 25편).

## await 빼먹기

`await`를 빼먹으면 Promise 객체 자체를 값으로 쓰게 되어, 값을 쓰는 코드가 조용히 틀립니다. 에러도 나지 않는 경우가 많아서 찾기 어렵습니다.

```js
const user = getUser()      // ❌ await 누락 (Promise 객체)
console.log(user.name)      // undefined
console.log(`hi ${user}`)   // hi [object Promise]
if (getUser()) { /* 항상 참 (Promise 객체는 truthy) */ }
```

- 반환된 거부가 아무도 처리하지 않으면 에러가 `await`한 곳이 아니라 한참 뒤 처리되지 않은 거부로 나타납니다. 이때 `try`/`catch`로는 잡히지 않습니다.

```js
try {
  save()       // ❌ await 없음
} catch (e) {
  // save가 거부해도 여기에 오지 않음
}
```

- `await` 없이 일부러 시작만 하는 작업(fire-and-forget)은 반드시 `.catch()`를 붙여서 거부를 처리합니다.
- 실행 순서도 바뀝니다. `await`가 없으면 다음 줄이 작업 완료 전에 실행됩니다. 저장하고 바로 읽는 코드에서 이전 값을 읽는 식으로 터집니다.

## forEach 안에서 await

`Array.prototype.forEach`는 콜백이 반환한 Promise를 기다리지 않습니다. MDN도 `forEach`는 동기 함수를 기대하며 Promise를 기다리지 않는다고 명시합니다. `forEach(async ...)` 뒤의 코드는 반복 작업이 끝나기 전에 실행됩니다.

```js
const out = []
items.forEach(async (i) => {
  await sleep(10)
  out.push(i)
})
console.log(out.length) // 0 (아직 아무도 안 끝남)
```

- `forEach`는 반환값이 `undefined`라서 Promise 목록을 모을 수도 없습니다.
- 콜백 안의 거부는 아무도 처리하지 않아 처리되지 않은 거부가 됩니다.
- 같은 문제가 `filter`, `some`, `every`의 `async` 콜백에도 있습니다. `async` 콜백은 항상 Promise를 반환하는데 Promise 객체는 truthy라서 `filter(async ...)`는 모든 요소를 통과시킵니다.
- 해결은 원하는 실행 방식에 따라 두 가지입니다. 순서대로 하려면 `for...of`(아래), 동시에 하려면 `map`과 `Promise.all`(자세히는 24편)입니다.

```js
// 동시에 실행하고 모두 끝나기를 기다림
const results = await Promise.all(
  items.map(async (i) => {
    await sleep(10)
    return i * 2
  }),
)
```

**흔한 실수:** `map(async ...)`만 쓰고 `await Promise.all`을 빼는 것입니다. 결과는 값이 아니라 Promise의 배열입니다.

## for...of 순차 실행

`for...of`와 `await`를 함께 쓰면 비동기 작업을 한 번에 하나씩 순서대로 실행합니다. 반복이 `await`에서 실제로 멈추기 때문입니다.

```js
const done = []
for (const item of items) {
  await sleep(10)     // 하나가 끝나야 다음으로 넘어감
  done.push(item)
}
console.log(done)     // 반복이 모두 끝난 뒤에 실행됨
```

- 순서가 중요하거나, 앞 결과가 다음 입력이 되거나, 서버에 동시에 너무 많은 요청을 보내면 안 될 때 씁니다.
- 작업이 서로 독립이면 순차 실행은 느립니다. 작업 시간이 각각 T라면 순차는 개수 곱하기 T, 동시 실행은 대략 T입니다. `forEach`, `map`과 달리 `for...of`는 `break`, `continue`, `return`도 쓸 수 있습니다.
- `for await (const x of asyncIterable)`는 비동기 이터러블을 한 항목씩 `await`하며 돕니다. 이벤트 스트림이나 `events.on`이 이에 해당합니다(자세히는 21편).
- 전통적인 `for (let i = 0; ...)`와 `while` 반복에서도 `await`는 같은 방식으로 순차 실행됩니다.
- 동시 실행의 개수를 제한하면서 빠르게 하는 방법은 24편에서 다룹니다.

## 핵심 정리

- 에러 우선 콜백은 첫 인수가 에러, 둘째부터 결과이며, 에러 분기에서 `return`하지 않으면 콜백이 두 번 호출되고, 항상 비동기로 호출해야 합니다.
- 콜백 지옥은 중첩과 단계별 에러 검사의 문제이며, `util.promisify`로 콜백 API를 Promise로 바꾸고 `async`/`await`로 위에서 아래로 읽히게 만듭니다.
- Promise는 한 번 정해진 상태가 바뀌지 않고, `async` 함수는 항상 Promise를 반환하며 동기 throw도 거부로 바꿉니다.
- 거부는 `try`/`catch` 또는 `.catch()`로 처리해야 하고, `try` 안에서는 `return await`로 써야 안쪽 `catch`에 닿습니다.
- `await`를 빼먹으면 Promise 객체를 값으로 쓰게 되어 조용히 틀리고, 에러는 처리되지 않은 거부가 됩니다.
- `forEach`는 `async` 콜백을 기다리지 않으므로 순차는 `for...of`와 `await`로, 동시 실행은 `map`과 `Promise.all`로 씁니다.

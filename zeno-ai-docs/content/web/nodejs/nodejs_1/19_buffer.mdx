## Buffer가 필요한 이유

`Buffer`는 고정 길이의 바이트 열을 다루는 Node.js의 클래스입니다. JavaScript 문자열은 글자(UTF-16)를 담는 값이라서 이미지, 압축 파일, 네트워크 패킷 같은 임의의 바이트를 그대로 담지 못합니다. 파일과 네트워크는 바이트로 오가므로 그 경계에서 `Buffer`를 씁니다.

```js
import { readFile } from 'node:fs/promises'

const data = await readFile('logo.png') // 인코딩을 주지 않음
Buffer.isBuffer(data) // true
data.length           // 파일의 바이트 수
```

- 인코딩을 주지 않고 읽으면 `Buffer`가 돌려집니다(자세히는 16편). 소켓과 `crypto` 같은 많은 API도 `Buffer`를 받고 돌려줍니다.
- `Buffer`는 `Uint8Array`의 하위 클래스입니다. 값은 0–255의 정수 바이트이며 길이는 만들 때 정해지고 늘어나지 않습니다.
- `Buffer`는 전역에 있지만 공식 문서는 `import { Buffer } from 'node:buffer'`로 가져다 쓰기를 권합니다.
- 콘솔에 출력하면 `<Buffer 68 69>`처럼 바이트가 16진수로 나옵니다. 50바이트를 넘으면 `... 50 more bytes`로 줄여 보여 줍니다(`buffer.INSPECT_MAX_BYTES`).
- `new Buffer()`는 인수 타입에 따라 동작이 달라 보안 문제를 일으켜 폐기(Deprecated)되었습니다. `Buffer.from()`, `Buffer.alloc()`, `Buffer.allocUnsafe()`를 씁니다.

문자열과 바이트 사이의 변환 규칙은 20편에서 다룹니다.

## Buffer.from

`Buffer.from()`은 이미 있는 데이터로 `Buffer`를 만듭니다. 인수 종류마다 복사인지 공유인지가 다릅니다.

| 인수 | 결과 |
|------|------|
| 문자열 `[, encoding]` | 인코딩한 바이트의 복사(기본 UTF-8) |
| 배열 | 각 요소를 바이트로 복사 |
| `Buffer` 또는 `Uint8Array` | 내용을 복사 |
| `ArrayBuffer [, byteOffset[, length]]` | 같은 메모리를 공유 |

```js
const a = Buffer.from('hi')           // <Buffer 68 69>
const b = Buffer.from([72, 105])      // <Buffer 48 69>
const c = Buffer.from(a)              // a의 복사본
const d = Buffer.from([256, -1, 257.5]) // <Buffer 00 ff 01>
```

- 배열의 값은 0–255로 잘립니다. `256`은 `0`, `-1`은 `255`, `257.5`는 `1`이 됩니다(`값 & 255`).
- `Buffer.from(buffer)`는 복사라서 한쪽을 바꿔도 다른 쪽은 변하지 않습니다.
- `ArrayBuffer`를 주면 메모리를 공유하므로 한쪽의 변경이 양쪽에 보입니다(아래 "Buffer와 Uint8Array·ArrayBuffer").
- `Uint16Array` 같은 다른 TypedArray를 주면 바이트가 아닌 요소 값이 하나씩 잘려 복사됩니다. 메모리 바이트 그대로 복사하려면 `Buffer.copyBytesFrom(view)`를 씁니다.
- 숫자를 `Buffer.from(5)`처럼 주면 `TypeError`입니다. 크기로 만들려면 `alloc`을 씁니다.

## Buffer.alloc

`Buffer.alloc(size)`는 `size` 바이트짜리 `Buffer`를 만들고 0으로 채웁니다. 이전 메모리 내용이 남지 않는 안전한 방법입니다.

```js
Buffer.alloc(4)            // <Buffer 00 00 00 00>
Buffer.alloc(4, 1)         // <Buffer 01 01 01 01>
Buffer.alloc(5, 'ab')      // <Buffer 61 62 61 62 61>
Buffer.alloc(3, 'aGk=', 'base64') // 'aGk='를 base64로 해석해 채움
```

- 두 번째 인수 `fill`은 숫자, 문자열, `Buffer`, `Uint8Array`이며 반복해서 채웁니다. 문자열이면 세 번째 인수가 인코딩입니다(기본 UTF-8).
- `size`가 음수이거나 `buffer.constants.MAX_LENGTH`(64비트에서 2의 53제곱 - 1, Node.js 22부터)보다 크면 `ERR_OUT_OF_RANGE`입니다. 숫자가 아니면 `ERR_INVALID_ARG_TYPE`입니다.
- `alloc`은 내부 풀을 쓰지 않고 항상 새로 할당합니다.
- 용도가 불분명하면 `alloc`을 고릅니다. 0으로 채우는 비용은 `allocUnsafe`보다 조금 크지만 측정해 보고 병목일 때만 바꿉니다.

## Buffer.allocUnsafe

`Buffer.allocUnsafe(size)`는 메모리를 0으로 초기화하지 않은 채 `Buffer`를 만듭니다. 그만큼 빠릅니다. 내용은 알 수 없는 이전 데이터입니다.

```js
const buf = Buffer.allocUnsafe(4)
// 내용은 실행마다 다름: <Buffer a0 8b 28 3f>
buf.fill(0)    // 전체를 직접 채우면 안전
```

- 만든 뒤 반드시 전체를 덮어쓴 다음에 읽습니다. `fill()`, `write()`, `copy()`, 인덱스 대입으로 모든 바이트를 채웁니다.
- 작은 `Buffer`는 내부 공유 풀에서 잘라 쓰므로 더 빠릅니다. `Buffer.poolSize`의 절반보다 작은 크기일 때 풀을 씁니다(자세히는 20편).
- `Buffer.allocUnsafeSlow(size)`는 초기화하지 않는 것은 같지만 풀을 쓰지 않고 독립된 메모리를 할당합니다.
- Node.js 26.8에서 `allocUnsafe(size, alignment)`의 정렬 인수가 추가되었습니다. 특수한 저수준 입출력에 쓰는 기능입니다.
- `node --zero-fill-buffers` 옵션을 주면 `allocUnsafe`도 0으로 채우지만 성능이 떨어집니다.

## allocUnsafe가 위험한 이유

초기화하지 않은 메모리에는 같은 프로세스가 앞서 쓰던 데이터가 남아 있을 수 있습니다. 비밀번호, 토큰, 다른 사용자의 응답 같은 민감한 값일 수 있고, 덮어쓰지 않은 부분을 읽거나 응답으로 내보내면 그대로 유출됩니다.

```js
function makePacket(len) {
  const buf = Buffer.allocUnsafe(len)
  buf.write('OK', 0)  // 앞 2바이트만 채움
  return buf          // ❌ 나머지는 이전 메모리 내용
}
```

- 일부만 채운 `Buffer`를 소켓이나 HTTP 응답으로 보내거나 파일에 쓰면 이전 데이터가 함께 나갑니다.
- 안전하게 쓰려면 길이를 정확히 아는 상태에서 처음부터 끝까지 덮어쓰거나, 처음에 `fill(0)`합니다. 그럴 자신이 없으면 `alloc`을 씁니다.
- 필요한 길이가 사용자 입력이면 크기를 검증합니다. 입력을 그대로 `alloc`·`allocUnsafe`에 넘기면 매우 큰 버퍼가 할당되어 메모리가 고갈될 수 있습니다.
- 과거의 `new Buffer(size)`는 Node.js 8.0 이전에 초기화되지 않은 메모리를 돌려주었고, 그래서 이 보안 문제가 널리 알려졌습니다. 8.0부터는 초기화되지만 생성자 자체가 폐기되었습니다.

## Buffer.concat

`Buffer.concat(list[, totalLength])`는 `Buffer`(또는 `Uint8Array`) 배열을 이어 붙인 새 `Buffer`를 돌려줍니다. 원본은 바뀌지 않습니다.

```js
const parts = [Buffer.from('ab'), Buffer.from('cd')]
Buffer.concat(parts)            // <Buffer 61 62 63 64>
Buffer.concat(parts, 2)         // <Buffer 61 62> (잘림)
Buffer.concat([parts[0]], 4)    // <Buffer 61 62 00 00>
Buffer.concat([])               // <Buffer > (길이 0)
```

- `totalLength`를 주지 않으면 길이 합을 직접 계산합니다. 미리 알면 주는 편이 계산을 줄입니다.
- `totalLength`가 합보다 작으면 잘리고, 크면 남는 부분이 0으로 채워집니다.
- 문자열 같은 `Buffer`가 아닌 요소가 있으면 `ERR_INVALID_ARG_TYPE`입니다.
- 조각 여러 개를 모아 하나로 합칠 때 씁니다. 조각을 모아 둔 배열을 한 번만 `concat`하는 것이 반복해서 이어 붙이는 것보다 효율적입니다.

```js
const chunks = []
chunks.push(Buffer.from('a'))
chunks.push(Buffer.from('b'))
const all = Buffer.concat(chunks) // 한 번에 합침
```

**흔한 실수:** 청크를 `+=`로 문자열에 이어 붙이는 것입니다. 한 글자가 여러 청크에 걸쳐 쪼개지면 글자가 깨집니다. 먼저 `Buffer.concat`으로 합친 뒤 한 번에 문자열로 바꿉니다(자세히는 20편).

## 길이

`buf.length`는 `Buffer`의 바이트 수입니다. 만들 때 정해지고 바뀌지 않습니다. 안에 쓴 데이터가 짧아도 `length`는 그대로입니다.

```js
const buf = Buffer.alloc(10)
buf.write('abc')
buf.length // 10 (쓴 길이가 아니라 할당한 크기)
```

- 쓴 만큼만 필요하면 `write`가 돌려주는 바이트 수를 기억해 `subarray(0, n)`으로 자릅니다.
- 문자열의 `length`는 UTF-16 코드 유닛 수이고 `Buffer`의 `length`는 바이트 수라서 다를 수 있습니다.

```js
'안녕'.length                  // 2
Buffer.from('안녕').length     // 6 (UTF-8에서 한글 한 글자는 3바이트)
```

### Buffer.byteLength

`Buffer.byteLength(string[, encoding])`는 문자열을 그 인코딩으로 바꿨을 때의 바이트 수를 `Buffer`를 만들지 않고 계산합니다. 기본 인코딩은 UTF-8입니다.

```js
Buffer.byteLength('안녕')              // 6
Buffer.byteLength('€')                 // 3
Buffer.byteLength('€', 'utf16le')      // 2
Buffer.byteLength('aGk=', 'base64')    // 2
```

- `Content-Length` 같은 헤더에 바이트 수를 써야 할 때, 쓰기 전에 크기를 알아야 할 때 씁니다.
- `Buffer`, `TypedArray`, `ArrayBuffer`를 주면 그 `byteLength`를 돌려줍니다.
- `'base64'`, `'base64url'`, `'hex'`는 올바른 입력을 가정하므로 공백이 섞인 문자열이면 실제 `Buffer`보다 클 수 있습니다.

## 인덱스

`buf[i]`로 `i`번째 바이트(0–255 정수)를 읽고 씁니다. `Uint8Array`의 규칙을 그대로 따릅니다.

```js
const buf = Buffer.from('hello')
buf[0]      // 104
buf[5]      // undefined (범위 밖)
buf.at(-1)  // 111 (뒤에서 첫 번째)
buf[0] = 72 // 'H'
buf[1] = 256 + 69 // 69로 저장됨 ('E')
buf[10] = 1 // 범위 밖 쓰기는 무시됨
```

- 범위를 벗어난 읽기는 `undefined`이고, 쓰기는 에러 없이 무시됩니다. 길이 검사를 하지 않으면 조용히 틀립니다.
- 값은 `& 255`로 잘립니다. `300`을 쓰면 `44`가 저장됩니다.
- `for (const byte of buf)`로 순회하면 숫자 바이트가 나옵니다. 인덱스 접근 대신 `buf.at()`·`forEach`·`map` 같은 TypedArray 메서드도 쓸 수 있습니다.
- `buf1 === buf2`나 `==`는 같은 객체인지만 비교합니다. 내용 비교는 `buf1.equals(buf2)`입니다.
- `JSON.stringify(buf)`는 `{"type":"Buffer","data":[104,105]}` 형태가 됩니다.

## subarray

`buf.subarray(start, end)`는 같은 메모리를 가리키는 새 `Buffer`를 돌려줍니다. 복사하지 않으므로 빠르고, 한쪽을 바꾸면 다른 쪽에도 보입니다. `end`는 포함하지 않습니다.

```js
const buf = Buffer.from('hello')
const part = buf.subarray(1, 3)   // 'el'
part[0] = 0x45                    // 'E'
buf.toString()                    // 'hEllo' (원본도 바뀜)
buf.subarray(-2).toString()       // 'lo' (음수는 뒤에서부터)
```

- `end`가 `length`보다 크면 `length`로 취급합니다. 인수를 생략하면 전체입니다.
- 독립된 복사본이 필요하면 `Buffer.from(buf.subarray(1, 3))`로 복사합니다.
- 원본이 클 때 일부만 오래 들고 있으면 원본 메모리 전체가 해제되지 않습니다. 오래 보관할 조각은 복사합니다.
- 헤더와 본문처럼 한 `Buffer`를 구조에 따라 나눠 읽을 때 유용합니다.

## slice가 예전과 다른 점

`buf.slice(start, end)`도 `subarray`처럼 복사하지 않고 같은 메모리를 가리키는 `Buffer`를 돌려줍니다. 이것이 `Uint8Array`의 `slice`와 다릅니다. `Uint8Array.prototype.slice()`는 복사본을 만듭니다.

```js
const buf = Buffer.from('buffer')
const view = buf.slice(0, 3)      // Buffer의 slice: 공유
view[0]++                         // 'cuf'
buf.toString()                    // 'cuffer' (원본이 바뀜)
const copy = Uint8Array.prototype.slice.call(buf, 0, 3)
copy[0]++                         // 원본은 그대로
```

- 같은 이름이 `Buffer`에서는 공유, `Uint8Array`에서는 복사라서 혼동을 부릅니다. 예전부터 있던 동작이라 호환성 때문에 남아 있습니다.
- `buf.slice()`는 Node.js 17.5(16.15)부터 문서에서 폐기(Deprecated)로 표시되었고 `buf.subarray()`를 쓰라고 안내합니다. Node.js 24에서 실행해 보니 경고는 나오지 않았지만 새 코드에서는 쓰지 않습니다.
- `subarray`는 `TypedArray`의 표준 메서드라서 `Buffer`와 일반 `Uint8Array`에서 같은 동작(공유)을 합니다. `slice`의 `Buffer` 동작이 필요한 자리는 `subarray`로 바꿉니다.
- 복사가 필요하면 `Buffer.from(buf.subarray(...))`로 명시합니다.

## Buffer와 Uint8Array·ArrayBuffer

세 가지는 한 메모리를 보는 층이 다릅니다.

| 타입 | 역할 |
|------|------|
| `ArrayBuffer` | 바이트 덩어리 그 자체. 직접 읽고 쓰는 메서드가 없음 |
| `Uint8Array` | `ArrayBuffer`의 일부를 0–255 정수 배열처럼 보는 뷰(view) |
| `Buffer` | `Uint8Array`를 확장한 Node.js 클래스. `toString`, `write`, `readUInt32BE` 같은 메서드가 추가됨 |

```js
const buf = Buffer.from('hi')
buf instanceof Uint8Array // true
buf.buffer                // ArrayBuffer (이 Buffer가 올라탄 메모리)
buf.byteOffset            // 그 안에서 시작하는 위치
```

- `Buffer`는 `Uint8Array`의 모든 메서드를 씁니다. Node.js API는 `Buffer`를 받는 자리에 일반 `Uint8Array`도 받습니다.
- 일부는 호환되지 않습니다. `toString()`은 `Buffer`에서 인코딩을 받는 별개의 메서드이고 `slice()`는 앞서 본 대로입니다.
- 작은 `Buffer`는 내부 풀의 일부라서 `buf.buffer`는 `buf`보다 훨씬 큰 `ArrayBuffer`이고 `byteOffset`이 0이 아닙니다. 이 환경(Node.js 24.15)에서 `Buffer.from('hi').buffer.byteLength`는 `8192`였습니다.

변환할 때 복사인지 공유인지가 중요합니다.

| 코드 | 방식 |
|------|------|
| `Buffer.from(u8)` | 복사 |
| `Buffer.from(arrayBuffer, offset, length)` | 공유 |
| `new Uint8Array(buf)` | 복사 |
| `new Uint8Array(buf.buffer, buf.byteOffset, buf.length)` | 공유 |

```js
const buf = Buffer.from('abcdef')
const view = new Uint8Array(
  buf.buffer, buf.byteOffset, buf.length,
)
view[0] = 0x7a      // buf.toString()은 'zbcdef'
```

**흔한 실수:** `new Uint8Array(buf.buffer)`로 `Buffer`의 메모리를 넘기는 것입니다. 풀에 있는 `Buffer`는 `buf.buffer`가 다른 `Buffer`의 데이터까지 포함하므로 `byteOffset`과 `length`를 함께 줘야 합니다.

## 핵심 정리

- `Buffer`는 `Uint8Array`를 확장한 고정 길이 바이트 열이며, 파일·네트워크 같은 바이트 입출력의 경계에서 쓰입니다.
- `Buffer.from`은 데이터를 복사해(`ArrayBuffer`만 공유) 만들고, `Buffer.alloc`은 0으로 채우며, `Buffer.allocUnsafe`는 초기화하지 않아 빠르지만 전체를 덮어쓴 뒤에만 읽어야 합니다.
- 일부만 채운 `allocUnsafe` 버퍼를 내보내면 이전 메모리의 민감한 데이터가 유출될 수 있습니다.
- `Buffer.concat`은 조각들을 이은 새 `Buffer`를 만들며, `length`는 바이트 수이고 문자열 길이와 다릅니다. 문자열의 바이트 수는 `Buffer.byteLength`로 구합니다.
- 인덱스는 0–255 바이트이며 범위 밖 읽기는 `undefined`, 쓰기는 무시되고 값은 `& 255`로 잘립니다.
- `subarray`와 `Buffer.slice`는 복사하지 않고 메모리를 공유하며, `slice`는 폐기되어 `subarray`로 대체합니다. 복사하려면 `Buffer.from`으로 감쌉니다.

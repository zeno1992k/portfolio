## setTimeout

`setTimeout(callback, delay, ...args)`는 지정한 시간(ms)이 지난 뒤에 콜백을 한 번 실행하도록 예약하고 `Timeout` 객체를 반환합니다(Stable). 콜백은 timers 단계에서 실행됩니다(자세히는 03편).

```js
setTimeout((name) => console.log('hi', name), 100, 'node')
// 약 100ms 뒤: hi node
```

- `delay`의 기본값은 1입니다. 1보다 작거나, `NaN`이거나, 2147483647(2³¹−1)보다 크면 1로 바뀝니다. 소수는 정수로 잘립니다.
- 세 번째 인수부터는 콜백에 그대로 전달됩니다.
- 지정한 시간에 정확히 실행된다는 보장은 없습니다. 공식 문서는 정확한 실행 시각과 콜백끼리의 순서를 보장하지 않는다고 밝힙니다.
- 반환된 `Timeout` 객체로 `clearTimeout`을 호출해 취소합니다(자세히는 22편).

**흔한 실수:**

- 함수를 넘기지 않고 호출한 결과를 넘기는 것입니다. `setTimeout(fn(), 100)`은 `fn`을 지금 실행합니다. `setTimeout(fn, 100)` 또는 `setTimeout(() => fn(), 100)`으로 씁니다.
- 지연을 2147483647보다 크게 지정하는 것입니다. `TimeoutOverflowWarning` 경고가 나고 지연이 1ms로 바뀌어 콜백이 곧바로 실행됩니다.

## setInterval

`setInterval(callback, delay, ...args)`는 지정한 간격으로 콜백을 반복 실행하도록 예약하고 `Timeout` 객체를 반환합니다(Stable). `delay`의 규칙은 `setTimeout`과 같습니다.

```js
let n = 0
const id = setInterval(() => {
  console.log(++n)
  if (n === 3) clearInterval(id)
}, 100)
// 1 2 3 (약 100ms 간격으로 출력되고 종료)
```

- `clearInterval`로 멈추지 않으면 계속 반복하고, 활성 타이머가 있는 동안 프로세스는 종료되지 않습니다(자세히는 22편).
- 이벤트 루프가 막혀서 한 번이 늦어지면, 실행해 보면 밀린 횟수를 몰아서 실행하지 않고 한 번만 늦게 실행합니다(아래 "이벤트 루프를 막는 코드").
- 콜백이 비동기 작업을 시작하는 경우 작업이 끝나기 전에 다음 호출이 일어나 겹칠 수 있습니다(자세히는 22편).

## setImmediate

`setImmediate(callback, ...args)`는 현재 poll 단계가 끝난 직후, 즉 check 단계에서 콜백을 실행하도록 예약합니다(Stable). 반환값은 `Immediate` 객체이고 `clearImmediate`로 취소합니다.

```js
setImmediate(() => console.log('immediate'))
console.log('sync')
// sync immediate
```

- 여러 개를 예약하면 만든 순서대로 큐에 쌓이고, 이벤트 루프 한 바퀴마다 큐 전체를 처리합니다.
- 실행 중인 콜백 안에서 새로 예약한 `setImmediate`는 같은 바퀴가 아니라 다음 바퀴에 실행됩니다. 그래서 이벤트 루프를 한 번씩 돌려 주는 양보 수단으로 쓸 수 있습니다.
- I/O 콜백 안에서는 `setImmediate`가 `setTimeout(fn, 0)`보다 항상 먼저 실행됩니다. 메인 모듈 최상위에서는 둘의 순서가 실행마다 달라질 수 있습니다(자세히는 03편).

## process.nextTick

`process.nextTick(callback, ...args)`는 nextTick 큐에 콜백을 넣습니다. 이 큐는 현재 실행 중인 JavaScript가 끝난 직후, 이벤트 루프가 계속되기 전에 전부 비워집니다.

```js
console.log('start')
process.nextTick(() => console.log('tick'))
console.log('end')
// start end tick
```

- nextTick은 이벤트 루프의 단계가 아닙니다. 어느 단계에 있든 현재 작업이 끝나면 곧바로 처리됩니다.
- 콜백 안에서 `nextTick`을 재귀로 계속 호출하면 큐가 비지 않아서 이벤트 루프가 다음 단계로 넘어가지 못합니다. I/O와 타이머가 실행되지 않습니다.
- 쓰는 이유는 콜백을 항상 비동기로 호출하기 위해서입니다. 어떤 때는 동기로, 어떤 때는 비동기로 호출하는 API는 예측하기 어렵습니다. 예를 들어 생성자에서 이벤트를 바로 `emit`하면 리스너를 붙이기 전에 끝나므로, `nextTick`으로 미루면 리스너를 등록할 기회가 생깁니다(자세히는 21편).
- `process.nextTick`의 안정성 지수는 Legacy(3)입니다. v22.7.0과 v20.18.0에서 바뀌었고, 공식 문서는 `queueMicrotask`를 쓰라고 안내합니다.

## queueMicrotask

`queueMicrotask(callback)`은 마이크로태스크 큐에 콜백을 넣는 전역 함수입니다(v11.0.0에서 추가). 마이크로태스크 큐는 V8이 관리하고 Promise 핸들러가 쓰는 큐와 같습니다.

```js
queueMicrotask(() => console.log('micro'))
console.log('sync')
// sync micro
```

- 현재 JavaScript가 끝난 직후, 이벤트 루프의 다음 작업보다 먼저 실행됩니다.
- 콜백이 예외를 던지면 `process`의 `'uncaughtException'` 이벤트가 발생합니다(자세히는 24편).
- `nextTick`과 달리 추가 인수를 받지 않습니다. 값을 넘기려면 클로저나 `bind`를 씁니다.
- 브라우저에도 있는 표준 API라서 이식성이 좋고, 공식 문서는 대부분의 경우 `process.nextTick`보다 이쪽을 쓰라고 권합니다.

```js
function deferred(a, b) { console.log('micro', a + b) }
queueMicrotask(deferred.bind(undefined, 1, 2))
// micro 3
```

## Promise then이 마이크로태스크인 이유

Promise의 `then`·`catch`·`finally` 핸들러는 항상 마이크로태스크로 실행됩니다. ECMAScript는 핸들러 실행을 Job으로 정의하고 그 Job을 어떻게 큐에 넣을지는 호스트에 맡기는데(자세히는 01편), V8과 Node.js는 이것을 마이크로태스크 큐로 처리합니다.

```js
Promise.resolve().then(() => console.log('then'))
console.log('sync')
// sync then (이미 이행된 Promise여도 동기로 실행되지 않음)
```

마이크로태스크여야 하는 이유는 두 가지입니다.

- **항상 비동기:** `then` 콜백은 이미 이행된 Promise에서도 현재 실행이 끝나기 전에는 호출되지 않습니다. 호출하는 쪽이 "이 콜백이 지금 실행될지 나중에 실행될지"를 걱정할 필요가 없습니다.
- **빠르고 일관됨:** 이벤트 루프의 다음 작업(타이머, I/O)보다 먼저 실행되므로, 같은 연쇄 안의 `then`들은 사이에 다른 작업이 끼어들지 않고 이어서 실행됩니다.

```js
async function f() {
  console.log(1)
  await null
  console.log(2)
}
f()
console.log(3)
// 1 3 2
```

`await` 뒤의 코드도 마이크로태스크로 이어집니다. `async` 함수의 본문은 첫 `await`까지 동기로 실행됩니다(자세히는 23편).

**흔한 실수:** 마이크로태스크 안에서 계속 마이크로태스크를 만드는 것입니다. 큐가 비는 것을 기다리므로 타이머와 I/O가 영원히 실행되지 않습니다.

## nextTick과 Promise 순서

CommonJS에서는 `nextTick` 큐를 먼저 비우고 이어서 마이크로태스크 큐(Promise, `queueMicrotask`)를 비웁니다. 공식 문서는 한 번의 이벤트 루프 턴 안에서 nextTick 큐가 항상 마이크로태스크 큐보다 먼저 처리된다고 설명합니다.

```js
// CommonJS (.cjs)
Promise.resolve().then(() => console.log('promise'))
queueMicrotask(() => console.log('microtask'))
process.nextTick(() => console.log('nextTick'))
// nextTick promise microtask
```

- 마이크로태스크끼리는 등록한 순서대로 실행됩니다. `promise`와 `microtask`는 같은 큐라서 먼저 등록한 쪽이 앞입니다.
- 타이머나 I/O 콜백 안에서 예약하면 모듈 종류와 관계없이 이 순서(`nextTick`이 먼저)입니다.
- 모듈의 최상위에서는 ES Modules인지에 따라 순서가 뒤집힙니다(아래 "ESM 최상위에서의 순서 차이").

## setTimeout(0)이 0ms가 아닌 이유

`setTimeout(fn, 0)`의 콜백은 0ms 뒤에 실행되지 않습니다. 세 가지가 겹칩니다.

1. **0은 1로 바뀝니다.** 지연이 1보다 작으면 1ms로 처리됩니다.
2. **timers 단계에 도달해야 합니다.** 지금 실행 중인 동기 코드가 모두 끝나고, `nextTick`과 마이크로태스크가 비워지고, 이벤트 루프가 timers 단계에 와야 콜백이 실행됩니다.
3. **정밀도와 스케줄링.** 지정한 시간은 "그 이후 실행될 수 있다"는 기준일 뿐이고, 운영체제 스케줄링과 다른 콜백 때문에 더 늦어집니다.

```js
const start = performance.now()
setTimeout(() => {
  console.log((performance.now() - start).toFixed(1))
}, 0)
// 0이 아닌 값 (한 PC에서 3.7–12.5를 측정, 실행마다 다름)
```

```js
setTimeout(() => console.log('timeout'), 0)
Promise.resolve().then(() => console.log('promise'))
console.log('sync')
// sync promise timeout
```

**흔한 실수:** `setTimeout(fn, 0)`을 "지금 바로 다음"으로 여기는 것입니다. Promise 핸들러와 `nextTick`은 항상 이보다 먼저 실행되고, 타이머 사이의 순서와 시각은 보장되지 않습니다.

## 이벤트 루프를 막는 코드

이벤트 루프를 막는 코드는 콜백 하나가 오래 실행되어 다른 콜백이 기다리게 만드는 코드입니다. 이벤트 루프는 한 번에 콜백 하나만 실행하므로, 막히는 동안 타이머 콜백, 응답 전송, 다른 요청 처리가 모두 멈춥니다. 공식 문서는 클라이언트당 처리 작업이 작을 때 Node.js가 빠르다고 설명합니다.

```js
let last = performance.now()
const id = setInterval(() => {
  const now = performance.now()
  console.log(Math.round(now - last))
  last = now
}, 100)
setTimeout(() => {
  const s = performance.now()
  while (performance.now() - s < 400) {} // 400ms 점유
}, 250)
setTimeout(() => clearInterval(id), 900)
// 104 111 448 105 111 (점유된 동안 한 번도 실행되지 못함)
```

막는 코드의 유형은 다음과 같습니다.

| 유형 | 예 |
|------|----|
| 오래 도는 동기 연산 | 큰 반복문, 중첩 반복문(O(n²)), 큰 배열 정렬 |
| 큰 JSON 처리 | `JSON.parse`, `JSON.stringify` |
| 동기 API | `readFileSync`, `pbkdf2Sync`, 동기 `zlib`, `spawnSync` |
| 지수 시간 정규식 | 중첩 수량자 `(\/.+)+$` 같은 패턴(ReDoS) |
| 끝나지 않는 큐 | 재귀 `nextTick`, 재귀 마이크로태스크 |

- 비동기 API를 써도 안 됩니다. Promise나 `await`로 감싼 CPU 작업은 여전히 메인 스레드에서 실행됩니다.
- 사용자가 입력 크기를 정하게 두면 서비스 거부(DoS) 공격 경로가 됩니다. 입력 크기에 상한을 둡니다.

## 긴 JSON.parse

`JSON.parse`와 `JSON.stringify`는 동기 함수라서 데이터가 클수록 끝날 때까지 이벤트 루프가 멈춥니다. 공식 문서는 50MB 객체에서 `stringify`가 약 0.7초, `parse`가 약 1.3초 걸린 예를 듭니다. 이 PC에서 51MB 문자열을 파싱했을 때는 약 360ms였고, 그동안 0ms로 예약한 타이머도 그만큼 늦게 실행됐습니다.

```js
const start = performance.now()
JSON.parse(text) // text는 약 51MB 문자열
// 파싱이 끝나야 다른 콜백이 실행됨
console.log(Math.round(performance.now() - start))
// 약 360 (한 PC 측정, 환경마다 다름)
```

- 외부에서 들어오는 JSON은 크기에 상한을 둡니다.
- 큰 데이터는 줄 단위(NDJSON)나 조각으로 나눠 처리하거나, 스트리밍 파서를 쓰거나, 워커 스레드로 넘깁니다(스트림은 Node.js 중급, 워커는 고급 과목).

## 긴 동기 루프

반복 횟수가 입력에 비례해 커지는 동기 루프는 같은 문제를 일으킵니다. 해결 방법은 작업을 조각으로 나누고, 조각 사이에 `setImmediate`로 이벤트 루프에 양보하는 것입니다.

```js
function sumAsync(n, done) {
  let sum = 0
  let i = 0
  function chunk() {
    const end = Math.min(i + 1e6, n)
    for (; i < end; i++) sum += i
    if (i < n) setImmediate(chunk) // 양보
    else done(sum)
  }
  chunk()
}
sumAsync(1e8, (s) => console.log(s)) // 4999999950000000
```

- 조각 사이에 이벤트 루프가 돌아서 타이머와 I/O 콜백이 실행됩니다. 이 예를 실행하며 1ms 간격 타이머를 같이 돌리면 중간중간 실행됩니다.
- 양보에 `setImmediate`를 쓰는 것이 핵심입니다. `await null`이나 `process.nextTick`은 마이크로태스크 쪽이라 이벤트 루프로 돌아가지 못합니다. 같은 구조를 `await null`로 짜면 1ms 타이머가 한 번도 실행되지 않았습니다.
- 계산 자체가 무거우면 워커 스레드나 자식 프로세스로 넘깁니다(Node.js 고급 과목).

## 블로킹을 찾는 감

막는 코드는 증상과 코드 단서로 의심합니다.

| 증상 | 의심할 것 |
|------|-----------|
| `setInterval` 간격이 지정한 값보다 크게 벌어짐 | 그 사이에 오래 실행된 콜백 |
| 한 요청이 느린 동안 다른 요청도 같이 느림 | 해당 요청 경로의 동기 작업 |
| CPU 코어 하나가 100%인데 다른 코어는 한가함 | 메인 스레드의 계산 |
| 로그의 시각 사이에 긴 공백 | 공백 앞뒤의 동기 코드 |

코드에서 먼저 보는 단서는 다음과 같습니다.

- 이름이 `Sync`로 끝나는 호출이 요청 처리 경로에 있는가.
- 반복 횟수나 처리량이 입력 크기에 비례하는가. 반복문 안에 반복문이 있는가.
- 큰 JSON, 정렬, 복사, 정규식이 사용자 입력에 적용되는가.
- 사용하는 npm 패키지의 비용이 문서에 나와 있는가(공식 문서는 서드파티 모듈의 API 비용을 확인하라고 권합니다).

측정은 `performance.now()`로 구간 시간을 재거나, `node:perf_hooks`의 `monitorEventLoopDelay()`(v11.10.0에서 추가)로 이벤트 루프 지연을 기록합니다. 프로파일러로 원인 위치를 찾는 방법은 29편에서 다룹니다.

## 실행 순서 예측 문제

출력 순서 문제는 다음 순서로 풉니다.

1. 스크립트의 동기 코드를 끝까지 실행합니다(함수 호출, `async` 함수의 첫 `await` 앞까지 포함).
2. `nextTick` 큐를 비웁니다. 그다음 마이크로태스크 큐(Promise 핸들러, `await` 뒤, `queueMicrotask`)를 비웁니다. 비우는 도중 새로 생긴 것도 같은 차례에 실행합니다.
3. 이벤트 루프로 들어가 timers → poll → check 순으로 하나씩 실행하고, 콜백 하나가 끝날 때마다 2번을 반복합니다.

**문제 1:** CommonJS와 ES Modules에서의 출력은?

```js
console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
process.nextTick(() => console.log('D'))
console.log('E')
// CommonJS: A E D C B
// ES Modules: A E C D B
```

**문제 2:** `async`와 Promise가 섞인 경우입니다.

```js
async function a() {
  console.log('a1')
  await b()
  console.log('a2')
}
async function b() { console.log('b') }
a()
Promise.resolve().then(() => console.log('p'))
console.log('end')
// a1 b end a2 p
```

`a()`가 `a1`을 출력하고 `b()`를 호출해 `b`를 출력한 뒤 `await`에서 멈춥니다. `await` 뒤의 `a2`가 마이크로태스크로 먼저 등록되고 `p`가 그다음에 등록되므로 `a2`가 앞입니다.

**문제 3:** 마이크로태스크 안에서 타이머를 예약합니다.

```js
setTimeout(() => console.log('T1'), 0)
Promise.resolve().then(() => {
  console.log('P1')
  setTimeout(() => console.log('T2'), 0)
  Promise.resolve().then(() => console.log('P2'))
})
console.log('S')
// S P1 P2 T1 T2
```

`P1` 안에서 만든 `P2`는 같은 마이크로태스크 차례에 실행되고, 타이머는 등록한 순서(`T1`, `T2`)대로 실행됩니다.

**함정:**

- 메인 모듈 최상위에서 `setTimeout(fn, 0)`과 `setImmediate`의 순서를 단정하면 안 됩니다. 실행마다 달라질 수 있습니다.
- I/O 콜백 안에서는 `setImmediate`가 항상 먼저입니다.
- 모듈 종류에 따라 `nextTick`과 Promise의 순서가 다릅니다.

## ESM 최상위에서의 순서 차이

ES Modules는 평가 자체가 마이크로태스크 큐를 처리하는 도중에 일어납니다. 그래서 모듈 최상위에서 예약한 Promise와 `queueMicrotask`는 이미 마이크로태스크를 비우는 중에 들어가 먼저 실행되고, `nextTick` 큐는 그 뒤에 처리됩니다. CommonJS에서는 반대입니다.

```js
// ES Modules (.mjs)
Promise.resolve().then(() => console.log('resolve'))
queueMicrotask(() => console.log('microtask'))
process.nextTick(() => console.log('nextTick'))
// resolve microtask nextTick
```

| 위치 | 순서 |
|------|------|
| CommonJS 최상위 | `nextTick` → Promise·`queueMicrotask` |
| ES Modules 최상위 | Promise·`queueMicrotask` → `nextTick` |
| 타이머·I/O 콜백 안(모듈 종류 무관) | `nextTick` → Promise·`queueMicrotask` |

- 파일이 CommonJS인지 ES 모듈인지는 확장자와 `package.json`의 `type`으로 정해집니다(자세히는 08편, 09편). 같은 코드를 `.cjs`와 `.mjs`로 저장해 실행하면 순서가 다르게 나옵니다.
- 이 차이는 모듈 최상위에서만 생깁니다. 콜백 안에서는 순서가 같습니다.
- 순서에 의존하는 코드는 취약합니다. `nextTick` 대신 `queueMicrotask`로 통일하면 모듈 종류와 관계없이 Promise와 등록 순서대로 실행됩니다.

## 핵심 정리

- `setTimeout`과 `setInterval`은 timers 단계, `setImmediate`는 check 단계에서 실행됩니다. 지연은 기준선일 뿐 정확한 시각이 아니고, 0은 1ms로 바뀝니다.
- `process.nextTick`은 nextTick 큐, Promise 핸들러와 `queueMicrotask`는 마이크로태스크 큐를 쓰고, 둘 다 현재 작업이 끝난 직후 이벤트 루프의 다음 작업 전에 비워집니다. `nextTick`은 Legacy라서 `queueMicrotask`를 권장합니다.
- 풀이 순서는 동기 코드, `nextTick` 큐, 마이크로태스크 큐, 이벤트 루프 단계 순입니다. 모듈 최상위에서는 CommonJS가 `nextTick` 먼저, ES Modules가 Promise 먼저입니다.
- 이벤트 루프를 막는 것은 긴 동기 루프, 큰 `JSON.parse`, `Sync` API, 지수 시간 정규식, 끝나지 않는 마이크로태스크 같은 동기 작업이며, 비동기 문법으로 감싸도 막힙니다.
- 오래 걸리는 계산은 `setImmediate`로 조각을 나눠 양보하거나 워커로 넘기고, 막힘은 타이머 간격 이상, 전체 응답 지연, 입력에 비례하는 코드, `Sync` 호출로 찾습니다.

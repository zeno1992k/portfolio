## Node는 원래 TS 런타임이 아님

Node.js는 JavaScript를 실행하는 런타임이고, TypeScript는 JavaScript에 타입 문법을 더한 언어입니다. 둘은 별개이며 TypeScript 소스는 JavaScript로 바꿔야 실행됩니다. 오랫동안 Node.js는 `.ts` 파일을 열 수 없었습니다(`ERR_UNKNOWN_FILE_EXTENSION`).

- Node.js가 실행하는 것은 V8이 이해하는 JavaScript뿐입니다. `: number` 같은 타입 표기는 JavaScript 문법이 아닙니다.
- TypeScript 컴파일러 `tsc`가 타입을 검사하고 JavaScript로 변환합니다. 이 두 일은 별개의 작업입니다.
- 최신 Node.js는 타입 문법을 지우는 방식으로 `.ts`를 직접 실행하는 기능을 내장했습니다(아래 "최신 Node의 타입 스트립 개념"). 이때도 Node.js는 타입을 검사하지 않고 지우기만 합니다.
- 실행 방법은 세 가지로 나뉩니다.

| 방법 | 설명 |
|------|------|
| `tsc`로 빌드 후 `node` 실행 | 변환한 `.js`를 실행. 배포의 표준 방식 |
| 타입 스트립 (`node file.ts`) | Node.js가 타입 문법을 지우고 실행. 설정 없이 가능 |
| 서드파티 도구 (`tsx`, `ts-node`) | 실행하면서 변환. 더 많은 TypeScript 기능 지원 |

## 타입은 지워진다

TypeScript의 타입은 컴파일 시점에만 존재하고 실행 시점에는 없습니다. 변환 결과에서 타입 표기, `interface`, `type` 별칭, 제네릭 인수가 모두 사라집니다.

```ts
type User = { id: number }
function show(u: User): string {
  return `user ${u.id}`
}
// 지운 뒤: function show(u) { return `user ${u.id}` }
```

- 타입을 검사해도 실행되는 JavaScript에는 영향이 없습니다. 타입이 틀린 코드도 실행하면 JavaScript로서 그대로 돕니다.

```ts
const n: number = 'x' // tsc는 에러, node는 에러 없이 실행
console.log(typeof n) // 'string'
```

- 그래서 런타임에는 타입 정보를 쓸 수 없습니다. `typeof`, `instanceof`, `in`, `Array.isArray`처럼 값을 검사하는 JavaScript 연산만 가능하고 `x is User` 같은 판별은 직접 코드로 써야 합니다.
- 외부에서 들어오는 데이터(요청 본문, 파일, 환경변수)는 타입을 단언해도 실제 값이 그 타입이라는 보장이 없습니다. 런타임 검증 코드가 별도로 필요합니다.
- `process.env.PORT`의 타입은 `string | undefined`입니다. 타입이 `number`라고 적어도 값은 문자열입니다(자세히는 05편).
- 타입은 개발 중 오류를 빨리 찾게 돕는 도구입니다. 실행 중의 안전은 값 검사가 맡습니다.

## 트랜스파일

트랜스파일(transpile)은 한 언어의 소스를 다른 형태의 소스로 바꾸는 일입니다. TypeScript에서는 `.ts`를 `.js`로 바꾸는 것을 가리킵니다. `tsc`가 대표 도구입니다.

- 타입을 지우는 것이 기본이고, 필요하면 최신 문법을 낮은 버전 문법으로 내리거나 `enum`, `namespace`, 매개변수 프로퍼티 같은 TypeScript 전용 문법을 실행 가능한 JavaScript 코드로 바꿉니다.
- 한 번에 두 가지를 할 수도 있고 따로 할 수도 있습니다. 타입 검사만 하고 파일은 만들지 않으려면 `noEmit`을 씁니다.

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "tsc",
    "start": "node dist/main.js"
  }
}
```

- 배포용 빌드는 `tsc`가 `outDir`에 `.js`를 만들고 Node.js가 그 파일을 실행하는 구조입니다. 실행 환경에는 `.ts`와 TypeScript가 필요 없습니다.
- 변환만 하고 타입 검사를 건너뛰는 모드는 더 빠릅니다. `ts-node --transpileOnly`가 예이며 README는 TypeScript의 `transpileModule`을 쓴다고 설명합니다. 대신 타입 검사는 `tsc --noEmit`으로 따로 돌려야 합니다.
- 타입 검사와 실행을 분리하면 CI에서는 검사를, 개발 중에는 빠른 실행을 취할 수 있습니다.
- 변환된 코드의 줄 번호가 원본과 달라지면 에러 스택을 읽기 어렵습니다. 소스 맵(source map)이 변환 후 위치를 원본 위치로 되돌려 줍니다.

## tsx와 ts-node는 도구

`tsx`와 `ts-node`는 `.ts`를 실행하면서 즉석에서 변환해 주는 서드파티 도구입니다. Node.js에 내장된 것이 아니라 npm으로 설치합니다.

```sh
npm install --save-dev tsx
npx tsx src/main.ts
node --import=tsx src/main.ts
```

| 항목 | tsx | ts-node |
|------|-----|---------|
| 실행 | `tsx file.ts` | `ts-node file.ts` |
| 타입 검사 | 하지 않음 | 기본으로 함 (`--transpileOnly`로 끔) |
| `tsconfig.json` | 읽음 (`paths` 지원) | 읽음 |

- Node.js 공식 문서도 `tsconfig.json`을 포함한 모든 TypeScript 기능이 필요하면 서드파티 패키지를 쓰라고 안내하며, 예로 `tsx`를 듭니다. 실행은 `npx tsx 파일.ts`나 `node --import=tsx 파일.ts`입니다.
- 도구는 개발 의존성(`devDependencies`)으로 설치합니다(자세히는 11편). `tsx`는 `tsx watch`로 파일을 저장할 때마다 다시 실행하는 감시 모드도 제공합니다.
- 운영 서버에서 `.ts`를 변환하며 실행하면 실행 환경에도 변환 도구가 필요해집니다. 배포는 빌드한 `.js`를 권장합니다.
- 도구가 하는 일은 변환과 실행입니다. `tsx`가 에러 없이 돌아도 타입이 맞다는 뜻은 아닙니다.
- 로컬에서 확인한 결과 `tsx`는 `enum`이 있는 파일도 실행했습니다(타입 스트립은 에러). 기능 범위가 다릅니다.

**흔한 실수:** 실행이 되니 타입도 통과한 것으로 착각하는 것입니다. `tsx`와 타입 스트립은 타입 검사를 하지 않으므로 `tsc --noEmit`을 스크립트와 CI에 넣어야 합니다.

## @types/node

`@types/node`는 Node.js의 내장 API(`fs`, `path`, `process`, `Buffer`...)에 대한 타입 정의 패키지입니다. 런타임 코드가 없고 `.d.ts`(선언 파일)만 들어 있습니다. TypeScript는 Node.js의 API를 스스로 알지 못하기 때문에 이 패키지가 있어야 `import { readFile } from 'node:fs/promises'`의 타입을 압니다.

```sh
npm install --save-dev @types/node
```

- 없으면 `node:fs`나 `process`를 찾을 수 없다는 TypeScript 에러(예: `TS2591`)가 납니다. 로컬에서 TypeScript 7.0.2로 확인하니 에러 메시지가 `@types/node` 설치와 tsconfig의 `types` 필드에 `'node'`를 넣으라고 안내했습니다.
- 개발 의존성으로 설치하며 런타임에는 필요 없습니다.
- 메이저 버전은 쓰는 Node.js 메이저와 맞춥니다. npm 레지스트리에 `@types/node`의 24.x와 26.x 버전이 모두 있습니다. 더 높은 버전의 타입을 쓰면 타입에는 있지만 실행 중인 Node.js에는 없는 API를 호출하게 될 수 있습니다.
- 타입 정의는 Node.js 프로젝트가 아니라 DefinitelyTyped 저장소에서 별도로 관리합니다. Node.js 문서와 어긋날 수 있습니다.
- 서드파티 라이브러리의 타입은 라이브러리가 자체 포함하거나 `@types/라이브러리이름`으로 따로 제공됩니다.

## 최신 Node의 타입 스트립 개념

타입 스트립(type stripping)은 Node.js가 `.ts` 파일에서 타입 문법을 공백으로 바꿔 지우고 나머지를 JavaScript로 실행하는 기능입니다. 타입 검사는 하지 않습니다.

```sh
node src/main.ts
```

- 지운 자리를 같은 길이의 공백으로 채웁니다. 그래서 줄과 열 위치가 원본과 같고 소스 맵이 필요 없습니다. 로컬에서 에러를 내면 스택의 줄 번호가 `.ts` 원본과 일치했습니다.
- `module.stripTypeScriptTypes()`로 결과를 볼 수 있습니다(안정성 지수 1.2 Release candidate).

```js
import { stripTypeScriptTypes } from 'node:module'

stripTypeScriptTypes('const a: number = 1;')
// 'const a         = 1;'
```

- 지울 수 있는 문법(erasable syntax)만 지원합니다. 코드 생성이 필요한 문법은 지원하지 않습니다.
- `tsconfig.json`을 읽지 않습니다. `paths`나 낮은 버전 문법으로 내리는 설정은 의도적으로 지원하지 않습니다.
- 타입 스트립을 끄려면 `--no-strip-types`를 씁니다. 끄면 `.ts`는 `ERR_UNKNOWN_FILE_EXTENSION`입니다.
- `process.features.typescript`는 기본값이 `"strip"`이고 `--no-strip-types`로 끄면 `false`입니다.

### 안정화 상태

| Node.js 버전 | 상태 |
|--------------|------|
| 22.6.0 | 기능 추가 (실험 플래그 필요) |
| 23.6.0 | 기본으로 활성화 |
| 24.3.0 | 실험 경고(experimental warning) 제거 |
| 24.12.0, 25.2.0 | 안정화(Stable). 끄는 플래그가 `--no-strip-types`로 바뀜 |
| 26.0.0 | `--experimental-transform-types` 플래그 제거 |

- Node.js 24(24.12.0 이상)와 26에서 타입 스트립은 Stable(안정성 지수 2)입니다. Node.js 문서의 TypeScript 항목 기준입니다.
- 24에서 `--experimental-transform-types`는 아직 있고(안정성 지수 1.2) 쓰면 실험 경고가 나옵니다. 이 플래그는 `enum` 같은 문법을 JavaScript로 변환합니다. 26에서는 이 플래그가 제거되었으므로 코드를 지울 수 있는 문법으로만 쓰는 쪽이 이후 버전에도 안전합니다.

### 제약

코드 생성이 필요한 TypeScript 문법은 에러가 납니다. 로컬 Node.js 24.15에서 모두 확인했습니다.

| 문법 | 결과 |
|------|------|
| `enum` | `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` |
| 값을 가진 `namespace` | `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` |
| 매개변수 프로퍼티 (`constructor(private x)`) | `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` |
| import alias (`import A = NS.T`, `import fs = require(...)`) | `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` |
| 데코레이터 | 변환하지 않아 파싱 에러 |
| `.tsx` | 지원 안 함 |
| `node_modules` 아래의 `.ts` | `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING` |
| REPL, `--check`, `inspect` | TypeScript 문법 미지원 |

- 타입만 담은 `namespace`는 동작합니다. 값을 내보내는 `namespace`만 에러입니다.
- 패키지 작성자가 TypeScript 소스를 그대로 배포하지 못하게 하려고 `node_modules` 아래는 막혀 있습니다. 배포 전에 `.js`로 빌드해야 합니다.
- `enum`은 `as const` 객체와 유니온 타입으로 대체합니다.

```ts
const Color = { Red: 0, Green: 1 } as const
type Color = (typeof Color)[keyof typeof Color]
```

- 가져오는 대상이 타입이면 `type` 키워드가 필요합니다. 없으면 값으로 가져오려 해서 런타임 에러가 납니다.

```ts
import { greet, type User } from './util.ts' // ✅
import { greet, User } from './util.ts'      // ❌ 런타임 에러
// SyntaxError: ... does not provide an export named 'User'
```

- tsconfig의 `verbatimModuleSyntax`를 켜면 TypeScript가 같은 규칙으로 검사해 줍니다. `erasableSyntaxOnly`는 지울 수 없는 문법을 TypeScript 단계에서 에러로 만듭니다.
- 이 옵션들은 Node.js 문서가 타입 스트립용으로 권하는 설정에 들어 있습니다. 문서는 TypeScript 5.8 이상을 권장합니다.

## ESM과 모듈 해석

타입 스트립에서 `.ts` 파일의 모듈 시스템은 `.js`와 같은 규칙으로 정해집니다(자세히는 09편, 10편). Node.js는 CommonJS와 ES Modules를 서로 변환하지 않고 쓴 문법 그대로 실행합니다.

| 파일 | 모듈 시스템 |
|------|-------------|
| `.ts` | 가장 가까운 `package.json`의 `"type"`을 따름 (`"module"`이면 ESM) |
| `.mts` | 항상 ES Modules (`.mjs`와 같음) |
| `.cts` | 항상 CommonJS (`.cjs`와 같음) |

- 파일 확장자는 생략할 수 없습니다. `import './file.ts'`처럼 `.ts`까지 씁니다. `import './file'`은 `ERR_MODULE_NOT_FOUND`입니다. `require('./file.ts')`도 확장자가 필수입니다.
- TypeScript의 기본 동작은 `.ts`를 import하는 것을 허용하지 않고 `.js`로 쓰게 합니다. Node.js에서 `.ts`를 직접 실행하려면 두 옵션 중 하나가 필요합니다.

| 옵션 | 효과 |
|------|------|
| `allowImportingTsExtensions` | `.ts` 확장자 import를 허용 (`noEmit` 필요) |
| `rewriteRelativeImportExtensions` | 빌드 때 상대 경로의 `.ts`를 `.js`로 바꿔 출력 |

- `tsc`로 빌드해서 `.js`를 실행하는 경우에는 `import './file.js'`처럼 소스에서 `.js`를 쓰는 방법도 있습니다. 실행 시 존재하는 파일을 가리켜야 하기 때문입니다.

### tsconfig의 module과 moduleResolution

`module`은 출력할 모듈 형식을, `moduleResolution`은 import 경로를 파일로 찾는 알고리즘을 정하는 옵션입니다. Node.js용으로는 `nodenext`를 씁니다.

```json
{
  "compilerOptions": {
    "target": "esnext",
    "module": "nodenext",
    "rewriteRelativeImportExtensions": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true,
    "noEmit": true
  }
}
```

- `module: nodenext`는 `moduleResolution: nodenext`를 함께 지정한 것과 같습니다. `moduleResolution`의 기본값은 `module`에 따라 정해지며 `module`이 `NodeNext`이면 `NodeNext`입니다.
- `nodenext`는 Node.js가 보게 될 출력이 `import`인지 `require`인지에 맞춰 알고리즘을 고릅니다. 파일 확장자와 가장 가까운 `package.json`의 `"type"`으로 CommonJS와 ES Modules 출력을 결정합니다.
- 상대 경로 import에 확장자가 필수입니다. Node.js의 ESM 규칙과 같습니다.
- TypeScript 공식 문서는 `nodenext`가 Node.js 최신 동작에 맞춰 바뀔 수 있다고 밝히며, `--module nodenext`는 떠다니는(floating) `--target esnext`를 함의합니다.
- 번들러를 쓰는 프로젝트는 `moduleResolution: bundler`를 씁니다. 확장자 생략을 허용하는 등 번들러의 해석을 따릅니다. Node.js가 직접 실행하는 코드에는 `nodenext`가 맞습니다.
- `moduleResolution: node`(`node10`)는 오래된 방식이라 ESM과 `exports` 필드를 이해하지 못합니다. 새 프로젝트에는 쓰지 않습니다.

**흔한 실수:** `"type": "module"` 없이 `.ts`에서 `import`를 쓰는 것입니다. Node.js 24.15는 모듈 문법을 감지해 ESM으로 다시 해석하되 `MODULE_TYPELESS_PACKAGE_JSON` 경고를 내고, `nodenext`의 `tsc`는 이 파일을 CommonJS로 보고 `import.meta`에 `TS1470` 에러를 냈습니다. `package.json`에 `"type": "module"`을 넣어 둘을 일치시킵니다.

## 경로 alias는 런타임이 모름

경로 alias(`@app/utils`처럼 상대 경로 대신 쓰는 별칭)는 tsconfig의 `paths`로 정하며, TypeScript가 타입 검사 때만 이해합니다. 출력되는 JavaScript의 import 경로는 바꾸지 않습니다.

```json
{
  "compilerOptions": {
    "paths": { "@app/*": ["./src/*"] }
  }
}
```

```ts
import { hello } from '@app/lib/hello.ts'
// tsc: 통과 / node: Cannot find package '@app/lib'
```

- Node.js는 `tsconfig.json`을 읽지 않습니다. 로컬에서 `@app/...` import를 실행하면 `ERR_MODULE_NOT_FOUND`가 났고 Node.js 문서도 `paths`는 변환되지 않고 에러를 일으킨다고 설명합니다.
- `tsc`로 빌드해도 `paths` 별칭이 `.js` 출력에 남아서 실행 시 같은 에러가 납니다.
- `tsx` 같은 도구는 `paths`를 해석해서 개발 중에는 되지만, 빌드 결과를 `node`로 실행하면 깨집니다. 개발과 운영에서 동작이 달라지는 원인이 됩니다.
- 대안은 `package.json`의 `"imports"` 필드(서브패스 임포트)입니다. Node.js가 직접 해석하는 표준 방식이고, 키는 반드시 `#`으로 시작해야 합니다(자세히는 10편).

```json
{
  "imports": { "#lib/*": "./src/lib/*" }
}
```

```ts
import { hello } from '#lib/hello.ts' // node가 해석함
```

- 로컬에서 위 방식은 `node src/main.ts`로 실행되었습니다. 단 `rewriteRelativeImportExtensions`를 켠 TypeScript 7.0.2는 `#` 경로의 `.ts` 확장자에 TS2877 에러를 냈습니다. 이 조합은 설정을 확인한 뒤에 씁니다.
- 번들러를 쓰면 번들러가 `paths`를 해석합니다. 번들러 없이 Node.js가 직접 실행하는 코드라면 상대 경로나 `imports`를 씁니다.

## 핵심 정리

- Node.js는 JavaScript 런타임이고 타입은 실행 전에 지워집니다. 타입이 틀려도 실행은 되므로 `tsc --noEmit`으로 따로 검사합니다.
- 실행 방법은 `tsc` 빌드 후 `node`, 타입 스트립(`node file.ts`), `tsx`·`ts-node` 같은 서드파티 도구입니다. 도구는 변환과 실행을 맡을 뿐 타입 검사를 보장하지 않습니다.
- `@types/node`는 Node.js API의 타입 정의이며 개발 의존성으로 설치하고 Node.js 메이저와 맞춥니다.
- 타입 스트립은 Node.js 24.12 이상과 26에서 Stable이며 지울 수 있는 문법만 지원합니다. `enum`, 값이 있는 `namespace`, 매개변수 프로퍼티는 에러이고 `node_modules` 아래 `.ts`와 `tsconfig.json`은 처리하지 않습니다.
- `.ts` import에는 확장자가 필수이고, 모듈 시스템은 `"type"`과 `.mts`·`.cts`로 정해집니다. Node.js용 tsconfig는 `module`과 `moduleResolution`을 `nodenext`로 둡니다.
- `paths` 별칭은 TypeScript만 이해하고 런타임은 모르므로 Node.js가 직접 실행하는 코드에는 `#`으로 시작하는 `imports`를 씁니다.

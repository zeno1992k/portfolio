## Promise.all

`Promise.all(iterable)`은 모든 Promise가 이행되면 결과 값의 배열로 이행하고, 하나라도 거부되면 그 첫 번째 거부 이유로 즉시 거부되는 Promise를 반환합니다.

```js
const [user, posts] = await Promise.all([
  getUser(1),
  getPosts(1),
])
```

- 결과 배열의 순서는 완료 순서가 아니라 입력 순서입니다.
- 입력에 Promise가 아닌 값이 섞여 있어도 됩니다. 그대로 결과에 들어갑니다. 빈 배열이면 빈 배열로 이행합니다.
- 하나가 거부되어도 나머지 작업은 취소되지 않고 계속 실행됩니다. Promise는 취소할 수 없고, `Promise.all`은 결과를 무시할 뿐입니다. 취소가 필요하면 `AbortSignal`을 작업에 넘깁니다(자세히는 22편).
- 첫 거부 이후에 일어난 다른 거부는 `Promise.all`이 내부에서 처리하므로 처리되지 않은 거부로 나타나지 않습니다. 다만 어느 쪽이 실패했는지는 첫 이유만 알 수 있습니다.
- 결과가 모두 필요하고 하나라도 실패하면 의미가 없는 경우(필요한 데이터를 한꺼번에 가져오기)에 맞습니다.

## Promise.allSettled

`Promise.allSettled(iterable)`은 모든 Promise가 이행이든 거부든 끝날 때까지 기다린 뒤, 각 결과를 설명하는 객체의 배열로 이행합니다. 거부되지 않습니다.

```js
const results = await Promise.allSettled([ok(), fail()])
// [
//   { status: 'fulfilled', value: 'a' },
//   { status: 'rejected', reason: Error }
// ]
const failed = results.filter(
  (r) => r.status === 'rejected',
)
```

- 각 항목은 `status`가 `'fulfilled'`이면 `value`, `'rejected'`이면 `reason`을 가집니다.
- 일부가 실패해도 나머지 결과를 쓰고 싶을 때, 또는 모든 작업의 성공과 실패를 집계하고 싶을 때 맞습니다(알림 일괄 발송, 여러 서버 상태 점검).
- 실패를 걸러내는 일은 직접 해야 합니다. 결과를 확인하지 않으면 실패가 조용히 사라집니다.

## Promise.race

`Promise.race(iterable)`은 가장 먼저 끝난(이행이든 거부든) Promise의 결과를 그대로 따라가는 Promise를 반환합니다.

```js
const winner = await Promise.race([
  sleep(200, 'slow'),
  sleep(20, 'fast'),
]) // 'fast'
```

- 먼저 끝난 것이 거부면 `race`도 거부됩니다. 이행한 것이 거부보다 늦게 끝나면 이행 값은 버려집니다.
- 입력이 빈 배열이면 영원히 끝나지 않는 Promise가 됩니다.
- 진 쪽 작업은 취소되지 않고 계속 실행됩니다.
- 시간 제한에 자주 쓰지만 제한 시간 타이머가 남는 문제가 있습니다. 시간 제한은 `AbortSignal.timeout`을 작업에 직접 넘기는 방식이 더 깔끔합니다(자세히는 22편).

```js
// sleep의 타이머는 work가 먼저 끝나도 남음
const timeout = sleep(5000).then(() => {
  throw new Error('timeout')
})
await Promise.race([work(), timeout])
```

- 이 예의 `sleep` 타이머는 `work`가 먼저 끝나도 정리되지 않습니다. 타이머를 `AbortController`로 취소하거나 위 신호 방식을 씁니다.

## Promise.any

`Promise.any(iterable)`은 가장 먼저 이행한 Promise의 값으로 이행합니다. 거부는 무시하고, 모두 거부되면 그때 거부됩니다.

```js
const data = await Promise.any([
  fetchFromA(),
  fetchFromB(),
]) // 먼저 성공한 쪽의 값
```

- 모두 거부되면 `AggregateError`로 거부되고, 각 거부 이유는 `err.errors` 배열에 입력 순서대로 담깁니다.
- 빈 배열을 주면 즉시 `AggregateError`로 거부됩니다.
- 같은 데이터를 여러 곳에서 받을 수 있을 때 가장 빠른 성공만 쓰는 용도에 맞습니다(미러 서버, 캐시와 원본).

```js
try {
  await Promise.any([fail1(), fail2()])
} catch (err) {
  console.log(err.constructor.name) // AggregateError
  console.log(err.errors.length)    // 2
}
```

네 메서드의 차이는 다음과 같습니다.

| 메서드 | 이행 조건 | 거부 조건 | 반환 값 |
|--------|-----------|-----------|---------|
| `Promise.all` | 모두 이행 | 하나라도 거부 (첫 이유) | 값의 배열 |
| `Promise.allSettled` | 모두 끝남 | 거부되지 않음 | 상태 객체의 배열 |
| `Promise.race` | 가장 먼저 끝난 것이 이행 | 가장 먼저 끝난 것이 거부 | 그 값 또는 이유 |
| `Promise.any` | 하나라도 이행 | 모두 거부 (`AggregateError`) | 첫 이행 값 |

## 병렬과 순차

Promise는 만들어지는 순간 작업을 시작합니다. 병렬이 되는지 순차가 되는지는 `await`를 어디에 두는지로 정해집니다.

```js
// 순차: a가 끝나야 b를 시작 (시간 합계)
const a = await getA()
const b = await getB()

// 병렬: 둘을 먼저 시작하고 함께 기다림 (가장 긴 시간)
const [a2, b2] = await Promise.all([getA(), getB()])
```

- 서로 독립인 작업은 병렬로 합니다. 각각 100ms 걸리는 작업 세 개를 직접 실행하면 순차는 약 300ms, `Promise.all`은 약 100ms입니다.
- 앞 결과가 다음 입력이 되거나 순서가 중요하면 순차로 합니다.
- 병렬은 CPU 병렬이 아닙니다. I/O 대기를 겹쳐서 줄이는 것이며, JavaScript 코드 자체는 한 번에 하나씩 실행됩니다(자세히는 01편).

**흔한 실수:** 병렬로 시작한 Promise를 하나씩 순서대로 `await`하는 것입니다. 나중에 `await`할 Promise가 그사이에 거부되면 그 시점에는 처리기가 없어서 처리되지 않은 거부가 발생합니다.

```js
const p1 = fail(10)         // 10ms 뒤 거부
const p2 = sleep(50)
await p2                     // 이 사이에 p1이 거부됨
await p1                     // ❌ 너무 늦음 (unhandledRejection)
```

- 여러 Promise를 먼저 시작했다면 `Promise.all`이나 `allSettled`로 한꺼번에 기다려서 처리기를 곧바로 붙입니다.
- 반복문 안에서 `await`로 순차 실행하는 방법은 23편에서 다뤘습니다.

## 동시성 제한

수천 개의 작업을 `Promise.all(items.map(...))`으로 한꺼번에 시작하면 서버나 DB가 감당하지 못하거나, 파일 디스크립터와 메모리가 한계를 넘습니다. 동시에 실행되는 개수에 상한을 두는 것이 동시성 제한입니다.

가장 간단한 방법은 정해진 수의 작업자(worker)가 공유 인덱스에서 다음 작업을 가져가는 풀입니다.

```js
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length)
  let next = 0
  async function worker() {
    while (next < items.length) {
      const i = next++
      results[i] = await fn(items[i], i)
    }
  }
  await Promise.all(Array.from({ length: limit }, worker))
  return results
}
// 동시에 최대 limit개만 실행되고, 결과는 입력 순서를 유지
```

- `next++`는 동기 코드라서 두 작업자가 같은 항목을 가져갈 일이 없습니다(자바스크립트는 한 번에 하나씩 실행).
- 6개 작업을 `limit` 2로 돌렸을 때 동시 실행 수의 최대는 2였습니다(Node.js 24에서 실행).
- 한 작업이 실패해도 다른 작업자는 남은 항목을 계속 처리합니다. 첫 실패에 멈추려면 실패 플래그를 두고 `while` 조건에서 확인합니다.
- 동시성의 상한은 대상(DB 풀 크기, 외부 API 허용량, 파일 디스크립터 한도)에 맞춥니다. 값을 정하는 기준은 정해진 숫자가 아니라 하위 시스템의 한계입니다.
- 간단한 대안은 항목을 `limit`개씩 잘라 묶음마다 `Promise.all`로 기다리는 방식입니다. 구현은 쉽지만 묶음 안의 가장 느린 작업을 기다리느라 놀고 있는 자리가 생깁니다.

### p-limit

`p-limit`은 같은 일을 하는 npm 패키지입니다. ESM 전용(`"type": "module"`)이고 `package.json`의 `engines`는 Node.js 20 이상입니다. 설치는 12편의 `npm install`로 합니다.

```js
import pLimit from 'p-limit'

const limit = pLimit(2) // 동시에 최대 2개
const results = await Promise.all(
  urls.map((url) => limit(() => fetchOne(url))),
)
```

- `limit(fn, ...args)`는 `fn`을 대기열에 넣고, 실행 순서가 되면 `fn(...args)`를 호출해서 그 Promise를 돌려줍니다.
- `limit.map(iterable, mapper)`는 위 `Promise.all`과 `map` 조합을 줄인 것이고, `limit.activeCount`와 `limit.pendingCount`로 실행 중과 대기 중인 개수를 볼 수 있습니다.
- 이미 `limit`으로 제한된 함수 안에서 같은 `limit`을 다시 호출하면 교착될 수 있다고 README가 경고합니다. 안쪽 작업에는 별도의 제한기를 씁니다.
- 직접 구현할 간단한 풀로 충분한지, 취소·우선순위·재시도까지 필요한지로 도입 여부를 정합니다.

## Promise.withResolvers

`Promise.withResolvers()`는 새 Promise와 그것을 이행·거부하는 함수 두 개를 담은 객체를 반환하는 정적 메서드입니다. Promise 생성자 바깥에서 `resolve`와 `reject`를 호출해야 할 때 씁니다.

```js
const { promise, resolve, reject } = Promise.withResolvers()
setTimeout(() => resolve('later'), 100)
console.log(await promise) // later
```

생성자로 같은 일을 하려면 변수를 바깥에 선언하고 실행자 안에서 대입해야 했습니다.

```js
let resolve, reject
const promise = new Promise((res, rej) => {
  resolve = res
  reject = rej
})
```

- 콜백이나 이벤트가 먼저 일어나고 Promise는 나중에 소비되는 구조에 맞습니다. 요청과 응답을 짝지어 기다리는 코드가 그렇습니다.
- 반환 객체의 `promise`, `resolve`, `reject`는 구조 분해로 꺼냅니다.
- `resolve`와 `reject`를 여러 번 불러도 처음 한 번만 적용됩니다.
- Node.js 24에서 동작을 확인했습니다. MDN은 브라우저에서 2024년 3월부터 쓸 수 있다고 안내합니다.

## unhandledRejection

`'unhandledRejection'`은 Promise가 거부되었는데 이벤트 루프 한 바퀴 안에 처리기(`catch` 등)가 붙지 않았을 때 `process`가 발생시키는 이벤트입니다.

```js
process.on('unhandledRejection', (reason, promise) => {
  console.error('unhandled:', reason)
})
Promise.reject(new Error('lost'))
// unhandled: Error: lost
```

- 리스너는 거부 이유 `reason`과 거부된 Promise를 받습니다. 이유는 보통 `Error`이지만 어떤 값이든 될 수 있습니다.
- 리스너가 없을 때 기본 동작은 `throw` 모드입니다. 거부를 처리되지 않은 예외로 올려 프로세스를 종료합니다(Node.js 15.0.0부터 기본. 이전에는 경고만 출력).
- 리스너가 있으면 그 리스너가 호출되고 프로세스는 종료되지 않고 계속 실행됩니다.
- 처리기가 나중에 붙으면 `'rejectionHandled'` 이벤트가 발생합니다. 공식 문서는 거부 처리가 이벤트 루프 한 바퀴보다 한참 뒤에 일어날 수도 있다고 설명합니다.
- 나타나는 흔한 원인은 `await` 누락, `forEach` 안의 `async`, 반환값 없는 `.then` 체인, 먼저 시작한 Promise를 나중에 `await`하는 구조입니다(23편, 위 "병렬과 순차").
- 특정 거부가 정당하게 무시되어야 하면 그 Promise에 `.catch(() => {})`를 붙여서 명시합니다. 이벤트 리스너로 모두 삼키지 않습니다.

## --unhandled-rejections 모드

`--unhandled-rejections=mode` 옵션은 처리되지 않은 거부를 어떻게 다룰지 정합니다(v12.0.0, v15.0.0에서 기본이 `throw`로 바뀜).

| 모드 | 동작 |
|------|------|
| `throw` (기본) | `unhandledRejection`을 발생. 리스너가 없으면 처리되지 않은 예외로 올림 |
| `strict` | 먼저 처리되지 않은 예외로 올림. 그 예외가 처리되면 `unhandledRejection`을 발생 |
| `warn` | 리스너 유무와 관계없이 항상 경고 출력 |
| `warn-with-error-code` | `unhandledRejection`을 발생. 리스너가 없으면 경고를 출력하고 종료 코드를 1로 설정 |
| `none` | 경고를 모두 숨김 |

```bash
node --unhandled-rejections=strict app.js
NODE_OPTIONS=--unhandled-rejections=warn node app.js
```

- Node.js 24에서 실행한 결과, 리스너가 없을 때 `throw`와 `strict`는 둘 다 스택을 출력하고 종료 코드 1로 끝났습니다. `warn`은 경고만 출력하고 계속 실행해 종료 코드 0, `warn-with-error-code`는 경고 후 계속 실행하고 종료 코드 1, `none`은 아무 출력 없이 종료 코드 0이었습니다.
- 명령행 진입점의 ES 모듈 정적 로딩 단계에서 일어난 거부는 모드와 관계없이 항상 처리되지 않은 예외로 올라갑니다(공식 문서).
- 기본(`throw`)을 유지하는 것이 안전합니다. `warn`이나 `none`은 거부를 숨겨서 버그를 늦게 발견하게 만듭니다. 옛 코드를 옮기는 중에 임시로만 씁니다.

## uncaughtException

`'uncaughtException'`은 JavaScript 예외가 어디서도 잡히지 않고 이벤트 루프까지 올라왔을 때 `process`가 발생시키는 이벤트입니다.

```js
process.on('uncaughtException', (err, origin) => {
  console.error('fatal:', err.message, origin)
})
setTimeout(() => { throw new Error('boom') }, 10)
// fatal: boom uncaughtException
```

- 리스너가 없을 때 기본 동작은 스택을 `stderr`에 출력하고 종료 코드 1로 프로세스를 종료하는 것입니다. 종료 코드는 먼저 설정한 `process.exitCode`보다 우선합니다.
- 리스너를 등록하면 이 기본 동작이 사라집니다. 그러면 프로세스는 계속 실행되고, 별도로 `process.exitCode`를 바꾸지 않으면 종료 코드 0으로 끝납니다.
- 리스너는 `(err, origin)`을 받습니다. `origin`은 동기 예외면 `'uncaughtException'`, 처리되지 않은 거부가 올라온 것이면 `'unhandledRejection'`입니다.
- 리스너 안에서 예외가 나면 무한 재귀를 막기 위해 잡히지 않고, 프로세스가 0이 아닌 코드로 종료됩니다(종료 코드 7, "Internal Exception Handler Run-Time Failure").
- `try`/`catch`로 잡을 수 없는 곳에서 난 예외가 도착합니다. 콜백 안, 타이머 콜백 안, 이벤트 리스너 안의 동기 throw, 리스너 없는 `'error'` 이벤트가 그렇습니다.

**공식 문서의 경고:** `'uncaughtException'`은 최후의 수단이며 `On Error Resume Next`(에러를 무시하고 계속 진행)처럼 쓰면 안 됩니다. 처리되지 않은 예외는 애플리케이션이 정의되지 않은 상태에 있다는 뜻이고, 복구 없이 실행을 이어가면 예측할 수 없는 문제가 생깁니다. 올바른 용도는 종료 전에 할당한 자원(파일 디스크립터, 핸들)을 동기적으로 정리하는 것입니다.

## uncaughtExceptionMonitor

`'uncaughtExceptionMonitor'`는 프로세스의 종료 동작을 바꾸지 않고 처리되지 않은 예외를 관찰만 하는 이벤트입니다(v13.7.0). `'uncaughtException'` 리스너나 캡처 콜백이 호출되기 전에 먼저 발생합니다.

```js
process.on('uncaughtExceptionMonitor', (err, origin) => {
  reportSync(err, origin) // 기록만 하고 흐름은 건드리지 않음
})
nonexistentFunc() // 모니터가 호출된 뒤 프로세스는 여전히 종료됨
```

- `'uncaughtException'` 리스너가 없으면 모니터가 있어도 프로세스는 평소대로 종료됩니다. Node.js 24에서 모니터의 로그가 먼저 찍힌 뒤 종료 코드 1로 끝나는 것을 확인했습니다.
- 리스너가 둘 다 있으면 모니터가 먼저 호출되고 그다음에 `'uncaughtException'` 리스너가 호출됩니다.
- 인수는 `'uncaughtException'`과 같은 `(err, origin)`입니다.
- 에러 수집 도구(모니터링 SDK)에 보고하는 용도에 맞습니다. 종료를 막지 않는 점이 안전합니다.
- 프로세스가 곧 종료될 수 있으므로 내부에서 비동기 전송을 시작하면 끝나기 전에 사라질 수 있습니다. 동기로 기록하거나 도구의 flush 기능을 따로 확인합니다.

## 프로세스를 살릴지 죽일지

처리되지 않은 거부와 처리되지 않은 예외는 코드가 예상하지 못한 상태가 되었다는 신호입니다. 기본 원칙은 기록하고, 정리하고, 종료하고, 외부 감시자가 다시 띄우게 하는 것입니다.

| 상황 | 권장 |
|------|------|
| 예상 가능한 실패(네트워크 오류, 잘못된 입력, 없는 파일) | 그 자리에서 `try`/`catch`나 `.catch()`로 처리하고 계속 실행 |
| 처리되지 않은 거부, 처리되지 않은 예외 | 동기로 기록하고 정리한 뒤 종료 코드 1로 종료 |
| 종료 후 복구 | 프로세스 밖의 감시자(컨테이너 재시작 정책, systemd 등)가 재시작 |
| 로그와 알림만 필요 | `uncaughtExceptionMonitor` |

```js
import { writeSync } from 'node:fs'

process.on('uncaughtException', (err, origin) => {
  writeSync(2, `fatal (${origin}): ${err.stack}\n`)
  process.exit(1) // 정리가 필요하면 이 앞에서 동기로 수행
})
process.on('unhandledRejection', (reason) => {
  throw reason // 처리되지 않은 예외로 올려 위 리스너가 처리
})
```

- 종료를 선택하는 이유는 상태가 깨졌을 수 있기 때문입니다. 반쯤 처리된 요청, 열린 채 남은 자원, 일관성 없는 메모리 상태 위에서 계속 서비스하면 더 큰 오류가 납니다.
- 공식 문서도 같은 입장입니다. 재시작은 `'uncaughtException'` 발생 여부와 관계없이 별도 프로세스의 외부 모니터로 하는 편이 안정적이라고 설명합니다.
- 위 예에서 `unhandledRejection` 리스너가 `reason`을 던지면 처리되지 않은 예외가 되어 `uncaughtException` 리스너로 갑니다. Node.js 24에서 `fatal` 로그가 찍히고 종료 코드 1로 끝나는 것을 확인했습니다. `process.exit` 전에 비동기 정리(서버 닫기, 연결 해제)를 기다리고 싶으면 제한 시간을 두고 강제 종료를 병행합니다.
- 서버에서 요청 하나의 실패가 전체를 죽이지 않아야 합니다. 이는 이 이벤트를 삼키는 방식이 아니라 요청 단위의 `try`/`catch`나 프레임워크의 에러 처리 미들웨어로 해결합니다.
- 리스너로 살려 두는 편이 맞는 경우는 거의 없습니다. 살려 둬야 하면 어떤 거부를 왜 무시하는지 코드 옆에 남기고, 그 Promise에 `.catch`를 직접 붙이는 쪽이 낫습니다.
- 종료 코드 규약과 에러 분류(운영 에러와 프로그래머 에러)는 25편에서 이어서 다룹니다.

## 핵심 정리

- `Promise.all`은 모두 이행되면 값 배열(입력 순서)로 이행하고 하나라도 거부되면 첫 이유로 거부되며, `allSettled`는 거부되지 않고 상태 객체 배열로 이행합니다.
- `race`는 가장 먼저 끝난 결과를, `any`는 가장 먼저 이행한 값을 따라가고 모두 거부되면 `AggregateError`로 거부됩니다. 진 작업은 취소되지 않습니다.
- Promise는 만들어질 때 시작하므로 `await`의 위치가 병렬과 순차를 정하고, 동시에 실행되는 개수는 작업자 풀이나 `p-limit`으로 제한합니다.
- `unhandledRejection`은 처리기 없는 거부에, `uncaughtException`은 잡히지 않은 예외에 발생하며, 기본 `throw` 모드에서는 리스너가 없으면 종료 코드 1로 프로세스가 종료됩니다.
- `uncaughtExceptionMonitor`는 종료 동작을 바꾸지 않고 먼저 호출되는 관찰용 이벤트입니다.
- 처리되지 않은 실패 뒤에는 이어서 실행하지 않고, 동기로 기록·정리한 뒤 종료해서 외부 감시자가 재시작하게 합니다.

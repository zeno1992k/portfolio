## package.json

`package.json`은 프로젝트나 패키지의 이름·버전·스크립트·의존성을 JSON으로 적은 설명서입니다. npm과 Node.js가 모두 읽습니다. 프로젝트 루트에 둡니다.

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": { "start": "node index.js" },
  "dependencies": { "express": "^5.1.0" }
}
```

| 읽는 쪽 | 쓰는 필드 |
|---------|-----------|
| Node.js | `type`, `main`, `exports`, `imports`, `name`(자기 참조) |
| npm | `name`, `version`, `scripts`, 의존성 필드, `files`, `bin`, `engines`, `private` |

- 파일은 JSON입니다. 주석과 마지막 쉼표가 허용되지 않습니다.
- Node.js는 파일에서 가장 가까운 상위 `package.json`을 찾아 읽습니다(09편, 10편).
- 직접 쓰기보다 `npm init`으로 만들고 `npm install`이 의존성을 자동으로 추가·갱신하게 둡니다(12편).
- 설치가 끝난 정확한 버전은 `package-lock.json`에 기록되며 `package.json`에는 범위만 적힙니다(12편).

**흔한 실수:** JSON 문법 오류입니다. 홑따옴표, 키에 따옴표 없음, 마지막 항목 뒤 쉼표는 모두 `npm`이 읽지 못하는 원인이 됩니다.

## name

`name`은 패키지의 식별자입니다. 게시하려면 필수이고, 설치되는 폴더 이름과 `import` 지정자가 됩니다.

```json
{ "name": "my-app" }
{ "name": "@myorg/my-lib" }
```

npm 문서의 규칙은 다음과 같습니다.

- 스코프를 포함해 214자 이하입니다.
- 새 패키지는 대문자를 쓸 수 없습니다.
- URL에 안전하지 않은 문자를 쓸 수 없습니다. 이름이 URL과 명령줄 인수에 들어가기 때문입니다.
- 스코프 패키지(`@scope/이름`)는 점이나 밑줄로 시작할 수 있고, 스코프 없는 이름은 안 됩니다.
- 코어 모듈 이름과 `js`·`node` 접미사는 피합니다.

Node.js에서는 `exports`와 함께 쓰면 패키지가 자기 이름으로 자신을 불러올 수 있습니다(v13.1.0, 10편).

## version

`version`은 패키지의 버전입니다. node-semver가 해석할 수 있는 형식이어야 하며 `주.부.수`(예: `1.4.2`)로 씁니다. `name`과 `version`의 조합이 패키지를 유일하게 식별합니다.

```json
{ "version": "1.4.2" }
```

- 게시하려면 필수입니다. 같은 `name`과 `version`을 다시 게시할 수 없어서 변경이 있을 때마다 올려야 합니다.
- 올리는 규칙(주·부·수의 의미)은 시맨틱 버저닝입니다(자세히는 13편).
- 게시하지 않는 앱에서는 형식적인 값으로 둡니다.

## private

`"private": true`는 `npm publish`를 막는 설정입니다. 앱 프로젝트나 모노레포 루트처럼 npm 레지스트리에 올리면 안 되는 패키지에 겁니다.

```json
{ "name": "my-app", "version": "1.0.0", "private": true }
```

- 실수로 게시하는 사고를 막습니다.
- 레지스트리에 올릴 계획이 없는 프로젝트는 `private`을 둡니다.

## scripts

`scripts`는 이름이 붙은 셸 명령의 모음입니다. `npm run 이름`으로 실행합니다.

```json
{
  "scripts": {
    "start": "node index.js",
    "dev": "node --watch index.js",
    "test": "node --test",
    "build": "tsc"
  }
}
```

- 실행 시 `PATH`에 `node_modules/.bin`이 자동으로 추가됩니다. 로컬에 설치한 도구를 `tsc`처럼 이름만으로 부를 수 있습니다.
- 셸은 POSIX에서 `/bin/sh`, Windows에서 `cmd.exe`입니다. 셸 문법이 운영체제마다 다릅니다.
- 현재 작업 디렉터리는 패키지 루트입니다.
- 명령이 0이 아닌 종료 코드로 끝나면 스크립트가 실패한 것으로 처리합니다.
- `test`, `start`, `stop`, `restart`는 `npm run` 없이 `npm test`, `npm start`로 실행됩니다. 나머지 이름은 `npm run`이 필요합니다.
- `pre이름`, `post이름` 스크립트는 자동으로 앞뒤에 실행됩니다. 설치·게시 때 실행되는 `postinstall`, `prepare`, `prepublishOnly` 같은 생명주기 스크립트도 있습니다. 모두 13편에서 자세히 다룹니다.
- `start`는 정의하지 않아도 루트에 `server.js`가 있으면 `node server.js`가 기본입니다.

**흔한 실수:** 의존성의 `postinstall` 스크립트는 설치 때 자동 실행되므로 신뢰하지 않는 패키지의 스크립트가 실행될 수 있습니다(공급망 문제, 자세히는 14편).

## dependencies

`dependencies`는 앱이 실행될 때 필요한 패키지입니다. 패키지 이름과 버전 범위의 짝입니다. `npm install 패키지`가 기본으로 여기에 추가합니다.

```json
{
  "dependencies": {
    "express": "^5.1.0",
    "zod": "~3.23.0"
  }
}
```

값에는 버전 범위 말고도 여러 형태를 쓸 수 있습니다.

| 값의 형태 | 예 |
|-----------|----|
| 버전 범위 | `^1.0.0`, `~1.2`, `>=1.0.2 <2.1.2`, `1.2.x` |
| 정확한 버전 | `1.2.3` |
| 태그 | `latest` |
| 로컬 경로 | `file:../local-package` |
| GitHub 약어 | `user/repo` |
| Git URL | `git+ssh://git@github.com:npm/cli.git#v1.0.27` |
| 별칭 | `npm:@scope/pkg@1.0.0` |

- `^`와 `~`의 의미는 13편에서 다룹니다.
- 라이브러리의 `dependencies`는 그 라이브러리를 설치한 사용자의 프로젝트에도 함께 설치됩니다.
- 테스트 도구나 트랜스파일러를 여기에 넣지 말라는 것이 npm 문서의 권고입니다.
- `require`·`import`하는 코드가 실제로 실행에 쓰는 패키지만 둡니다.
- 설치하지 않은 패키지를 `import`하면 `ERR_MODULE_NOT_FOUND`입니다(10편).

## devDependencies

`devDependencies`는 개발·빌드·테스트에만 쓰는 패키지입니다. `npm install` 때는 설치되지만 운영 환경 설치에서는 제외할 수 있습니다.

```json
{
  "devDependencies": {
    "typescript": "^5.6.0",
    "eslint": "^9.0.0"
  }
}
```

| 항목 | dependencies | devDependencies |
|------|--------------|-----------------|
| 용도 | 실행 | 개발·빌드·테스트 |
| `npm install` | 설치 | 설치 |
| `npm install --omit=dev` | 설치 | 제외 |
| 라이브러리 사용자 설치 | 함께 설치 | 설치 안 됨 |
| `npm install -D 패키지` | 추가 안 됨 | 추가됨 |

- `NODE_ENV=production`일 때도 `devDependencies`가 제외됩니다.
- 대표 예는 타입스크립트 컴파일러, 린터, 테스트 러너, `@types/*` 패키지입니다(자세히는 27편).
- 앱을 번들·컴파일한 결과만 배포하면 실행 환경에는 필요 없습니다. 반면 런타임에서 `import`하는 패키지를 `devDependencies`에 넣으면 운영 설치에서 빠져 `ERR_MODULE_NOT_FOUND`로 죽습니다.

**흔한 실수:** 런타임에 필요한 패키지를 `devDependencies`에 넣는 것입니다. 로컬에서는 동작하고 운영에서만 실패합니다.

## peerDependencies

`peerDependencies`는 이 패키지를 쓰는 쪽(호스트)이 직접 설치해 두어야 하는 패키지와 그 버전 범위를 선언합니다. 플러그인이나 프레임워크 확장 패키지가 주로 씁니다.

```json
{
  "name": "react-datepicker-lite",
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"
  }
}
```

- 호스트와 플러그인이 같은 인스턴스를 공유해야 할 때 씁니다. 플러그인이 `dependencies`에 자기 `react`를 두면 앱의 `react`와 별개의 복사본이 생겨 문제가 됩니다.
- npm v3–v6에서는 자동 설치되지 않고 경고만 했습니다. npm v7부터 기본으로 자동 설치됩니다. 직접 설치한 결과, npm 11에서도 설치되었습니다.
- 범위는 넓게 씁니다. npm 문서가 패치 버전 고정 대신 `"^1.0"` 같은 넓은 범위를 권합니다.
- 호스트 프로젝트가 다른 버전을 이미 설치했다면 버전이 충돌해 설치가 실패할 수 있습니다.

필수가 아닌 피어는 `peerDependenciesMeta`로 표시합니다.

```json
{
  "peerDependenciesMeta": {
    "react-native": { "optional": true }
  }
}
```

`optional: true`이면 자동 설치하지 않고, 호스트가 있으면 연동합니다.

## optionalDependencies

`optionalDependencies`는 설치에 실패해도 전체 설치를 중단하지 않는 의존성입니다. 플랫폼별 네이티브 가속 패키지처럼 없어도 돌아가야 할 때 씁니다.

```json
{
  "optionalDependencies": {
    "fsevents": "^2.3.0"
  }
}
```

- 설치가 실패하면 npm이 건너뛰고 계속합니다. 직접 확인한 결과, 존재하지 않는 버전을 적어도 설치는 성공하고 `npm ls`에 UNMET OPTIONAL DEPENDENCY로 표시됩니다.
- 코드가 그 패키지가 없는 경우를 직접 처리해야 합니다. 설치되지 않았는데 불러오면 에러입니다.
- 같은 이름이 `dependencies`에도 있으면 `optionalDependencies`의 값이 이깁니다. 한 곳에만 둡니다.
- `npm install --omit=optional`로 설치 자체를 건너뜁니다.

```js
let fast = null
try {
  fast = await import('fast-native')
} catch {
  // 없으면 JS 구현으로 대체
}
```

네 필드의 차이를 정리합니다.

| 필드 | 누가 설치 | 없을 때 | 대표 용도 |
|------|-----------|---------|-----------|
| `dependencies` | 이 패키지 설치 시 함께 | 설치 실패 | 실행에 필요한 패키지 |
| `devDependencies` | 이 프로젝트에서 개발할 때만 | 영향 없음 | 빌드·테스트 도구 |
| `peerDependencies` | 호스트가 설치 (npm 7부터 자동) | 충돌·경고 | 플러그인의 호스트 |
| `optionalDependencies` | 이 패키지 설치 시, 실패 허용 | 건너뜀 | 플랫폼별 선택 기능 |

## packageManager 필드

`packageManager`는 프로젝트가 쓸 패키지 매니저와 정확한 버전을 선언하는 필드입니다. Corepack이 읽습니다. 형식은 `이름@버전`이고, 값 끝에 해시를 붙일 수 있습니다.

```json
{
  "packageManager": "pnpm@9.12.0"
}
```

- 지원하는 매니저는 `yarn`, `npm`, `pnpm`입니다.
- Corepack은 선언된 버전을 내려받아 캐시하고, 다른 매니저로 실행하려 하면 올바른 것을 쓰라고 요청합니다. `corepack enable`로 Yarn·pnpm 실행 파일을 PATH에 연결합니다.
- 팀원과 CI가 같은 매니저 버전을 쓰게 하는 것이 목적입니다.
- Corepack은 Node.js 14.19.0부터 25.0.0 미만에 포함되어 배포됩니다. Node.js 24는 포함이고, 25.0.0부터는 포함되지 않아 별도로 설치합니다(자세히는 14편).
- 이 필드는 npm 공식 `package.json` 문서에 없습니다. 근거는 Corepack 문서입니다.

## license와 repository 필드

`license`는 패키지의 사용 조건을, `repository`는 소스 코드 위치를 알립니다. 둘 다 게시할 때 채우는 메타데이터이며 앱 실행에는 영향이 없습니다.

```json
{
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "git+https://github.com/me/my-lib.git"
  }
}
```

| 필드 | 값 |
|------|----|
| `license` | SPDX 식별자(`MIT`, `BSD-3-Clause`), 표현식(`(ISC OR GPL-3.0)`) |
| `license` 특수값 | `UNLICENSED`는 사용을 허락하지 않음, `SEE LICENSE IN 파일명`은 사용자 정의 약관 |
| `repository` | `type`·`url`을 가진 객체, 또는 `user/repo` 같은 약어 |

- 라이선스를 적지 않으면 사용 조건이 불명확해서 다른 사람이 쓰기 어렵습니다. 비공개 코드라면 `UNLICENSED`와 `private: true`를 함께 씁니다.
- `repository`가 있으면 `npm repo` 명령으로 저장소를 열 수 있습니다.
- 그 밖에 `description`, `keywords`, `homepage`, `bugs`, `author`, `engines` 같은 메타데이터 필드가 있습니다. `engines`는 Node.js·npm 버전 요건이며 `engine-strict` 설정이 없으면 조언일 뿐입니다(자세히는 14편).

## 핵심 정리

- `package.json`은 이름·버전·스크립트·의존성을 적은 JSON 설명서이고 npm과 Node.js가 모두 읽는다.
- `name`과 `version`은 게시에 필수이며 둘의 조합이 패키지를 식별한다. 게시하면 안 되는 프로젝트는 `private: true`를 건다.
- `scripts`는 `npm run`으로 실행하며 `node_modules/.bin`이 PATH에 들어간다.
- `dependencies`는 실행, `devDependencies`는 개발·빌드·테스트용이고 `--omit=dev`나 `NODE_ENV=production`에서는 제외된다.
- `peerDependencies`는 호스트가 설치할 패키지(npm 7부터 자동 설치), `optionalDependencies`는 설치 실패를 허용하는 선택 패키지다.
- `packageManager`는 Corepack이 읽는 매니저 버전 고정이고, `license`·`repository`는 게시용 메타데이터다.

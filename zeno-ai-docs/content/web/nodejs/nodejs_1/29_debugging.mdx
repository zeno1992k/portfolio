## 스택 읽기

스택 트레이스(stack trace)는 에러가 만들어진 지점까지의 함수 호출 경로입니다. 문제를 찾는 출발점이고 `error.stack`에 들어 있습니다(자세히는 25편).

```text
file:///app/main.mjs:3
  throw new Error('boom')
        ^

Error: boom
    at add (file:///app/main.mjs:3:9)
    at main (file:///app/main.mjs:7:3)
    at async file:///app/main.mjs:9:1

Node.js v24.15.0
```

- 처리되지 않은 에러는 먼저 에러가 난 소스 줄과 위치 표시(`^`)를 보여 주고, 이어서 `이름: 메시지`와 프레임 목록, 마지막에 Node.js 버전을 출력합니다.
- 프레임 형식은 `at 함수이름 (위치)`이고 위치는 `파일:줄:열`입니다. 함수 이름이 없으면 위치만 나옵니다.
- 가장 위의 프레임이 에러를 만든 곳이고 아래로 갈수록 호출한 쪽입니다. 먼저 내가 작성한 코드의 첫 프레임을 찾아 거기서부터 읽습니다.
- 위치 표기는 모듈 시스템에 따라 다릅니다. ES Modules는 `file:///...` URL, CommonJS는 절대 경로이고, Node.js 내부는 `node:internal/...`입니다.
- `at async 함수이름`은 `await`로 이어진 비동기 호출입니다. 비동기 경계를 넘어도 이어지지만 이벤트 루프의 다른 틱에서 시작된 콜백은 호출자가 스택에 남지 않습니다.
- `node:internal/...` 프레임은 Node.js 내부 코드입니다. 대개는 건너뛰고 내 코드와 의존성 코드의 프레임을 봅니다.
- 캡처되는 프레임은 `Error.stackTraceLimit`(기본 10)까지입니다. 깊은 호출에서 원인이 잘리면 값을 늘려서 다시 재현합니다.

```js
Error.stackTraceLimit = 50 // 이후에 만드는 에러부터 적용
```

- 트랜스파일러(TypeScript, 번들러)를 거친 코드는 스택이 변환된 코드의 위치를 가리킵니다. `--enable-source-maps`를 주면 가능한 한 원본 소스 위치로 보여 줍니다(최선 노력). 타입 스트립은 위치를 보존하므로 필요 없습니다(자세히는 27편).
- 스택은 에러를 만든 곳을 보여 줄 뿐 던진 곳은 아닐 수 있습니다. 던진 값이 `Error`가 아니거나 만든 곳과 던진 곳이 다르면 `--trace-uncaught`로 던진 지점의 스택도 출력합니다. 이 옵션은 가비지 컬렉션에 부정적 영향을 줄 수 있다고 문서가 밝히므로 디버깅 때만 씁니다.

## 원인 체인 따라가기

원인 체인(cause chain)은 `error.cause`로 연결된 에러 목록입니다. 가장 바깥 에러는 증상이고, 가장 안쪽 `cause`가 근본 원인인 경우가 많습니다(자세히는 25편).

```js
function causes(err) {
  const seen = new Set()
  const list = []
  for (let e = err; e && !seen.has(e); e = e.cause) {
    seen.add(e)
    list.push(e)
  }
  return list
}
// 'load failed' -> 'ENOENT: no such file ...' 순서
```

- `console.log(err)`와 `util.inspect`는 `cause`를 재귀적으로 `[cause]: ...`로 출력합니다. 스택이 같은 부분은 `... N lines matching cause stack trace ...`로 줄여 줍니다.
- `JSON.stringify(err)`에는 `cause`가 나오지 않습니다. 로그에는 체인을 직접 풀어서 필드로 남깁니다(자세히는 26편).
- 읽는 순서는 바깥 에러의 메시지로 어떤 작업이 실패했는지 파악하고, 안쪽으로 내려가며 `code`, `syscall`, `path` 같은 구체적 정보를 찾는 것입니다.
- 가장 안쪽 에러의 스택이 실제 문제 지점입니다. 바깥 에러의 스택은 감싸서 다시 던진 곳입니다.
- `cause`에는 에러가 아닌 값이 들어 있을 수 있으므로 속성을 읽기 전에 확인합니다. 순환 참조로 무한 반복하지 않도록 방문 기록을 둡니다.
- `AggregateError`는 `errors` 배열에 여러 에러가 담기므로 `cause`와 별개로 각 요소를 확인합니다.

## node inspect

`node inspect`는 Node.js에 내장된 명령줄 디버거입니다(안정성 지수 Stable). 완전한 기능의 디버거는 아니고 단계 실행과 값 확인 정도를 제공합니다.

```sh
node inspect app.mjs
```

- 시작하면 첫 실행 줄에서 멈추고 `debug>` 프롬프트가 나옵니다. 스크립트의 `debugger` 문까지 바로 실행하려면 `NODE_INSPECT_RESUME_ON_START=1`을 설정합니다.
- 주요 명령은 다음과 같습니다.

| 명령 | 뜻 |
|------|----|
| `cont`, `c` | 다음 중단점까지 실행 |
| `next`, `n` | 다음 줄로 (함수 안으로 들어가지 않음) |
| `step`, `s` | 함수 안으로 들어감 |
| `out`, `o` | 현재 함수에서 나옴 |
| `bt` | 호출 스택(backtrace) 출력 |
| `exec expr`, `p expr` | 현재 위치에서 식을 평가해 출력 |
| `repl` | 현재 문맥에서 값을 평가하는 대화형 모드 (Ctrl+C로 나감) |
| `watch('expr')` | 중단할 때마다 값을 보여 줄 식 등록 |
| `help` | 전체 명령 보기 |

- 아무것도 입력하지 않고 Enter를 누르면 직전 명령을 반복합니다.
- 서버에 접속해 간단히 확인할 때, GUI 도구를 쓸 수 없는 환경에서 유용합니다. 일상적인 디버깅에는 아래의 `--inspect` 방식이 더 편합니다.
- `profile`, `takeHeapSnapshot()` 명령으로 CPU 프로파일과 힙 스냅샷도 저장할 수 있습니다.
- 안정성 지수 1(Experimental)인 프로브 모드(`--probe`)는 코드를 고치지 않고 지정한 위치의 식 값을 출력합니다. 문서 기준 24.16.0과 26.1.0에서 추가되었습니다.

## --inspect

`--inspect`는 V8 인스펙터를 켜서 외부 디버거가 TCP 포트로 접속하게 하는 옵션입니다. Chrome DevTools나 VS Code 같은 도구가 이 포트에 붙어 디버깅과 프로파일링을 합니다. 통신은 Chrome DevTools Protocol로 합니다.

```sh
node --inspect app.mjs
# Debugger listening on ws://127.0.0.1:9229/<uuid>
```

| 옵션 | 동작 |
|------|------|
| `--inspect[=[host:]port]` | 인스펙터를 켜고 코드는 바로 실행. 기본 `127.0.0.1:9229` |
| `--inspect-brk` | 사용자 코드의 첫 줄에서 멈춤 |
| `--inspect-wait` | 디버거가 붙을 때까지 기다린 뒤 실행 (22.2.0에서 추가) |

- 포트 `0`을 주면 사용 가능한 임의의 포트를 씁니다. 실제 주소는 시작 때 출력됩니다.
- `--inspect`는 디버거가 붙기 전에 코드를 실행합니다. 시작 부분을 디버깅하려면 `--inspect-brk`나 `--inspect-wait`를 씁니다.
- 디버거가 붙지 않은 상태에서 `debugger` 문은 아무 일도 하지 않습니다. 로컬에서 `node --inspect app.mjs`로 확인하면 결과가 그냥 출력됩니다.
- 실행 중인 프로세스에는 `SIGUSR1` 시그널을 보내 인스펙터를 켤 수 있습니다(Windows에서는 안 됨). 포트는 `--inspect-port`로 정합니다.

**보안 경고:** 인스펙터에 접속하면 해당 프로세스에서 임의의 코드를 실행할 수 있습니다. 기본값은 `127.0.0.1`에만 바인딩합니다. 공개 IP나 `0.0.0.0`에 열면 원격 코드 실행 공격에 노출되므로 운영 서버에서 열지 않습니다. 원격 서버는 SSH 터널로 접속합니다.

```sh
ssh -L 9221:localhost:9229 user@remote.example.com
# 로컬에서 localhost:9221로 접속
```

- 같은 컴퓨터의 다른 프로그램은 제한 없이 접속할 수 있습니다. 공유 환경에서 `--inspect`를 켜 둔 채로 두지 않습니다.

## Chrome DevTools로 붙기

Chrome이나 Edge의 DevTools로 `--inspect`로 띄운 Node.js 프로세스에 붙어 소스 보기, 중단점, 호출 스택, 변수 검사, 프로파일링을 합니다.

1. `node --inspect app.mjs`(필요하면 `--inspect-brk`)로 시작합니다.
2. 브라우저에서 `chrome://inspect`(Edge는 `edge://inspect`)를 엽니다.
3. Configure에서 대상 호스트와 포트(예: `localhost:9229`)가 목록에 있는지 확인합니다.
4. Remote Target 목록에 Node.js 프로세스가 나타나면 inspect를 눌러 DevTools를 엽니다.

- 수동 연결도 가능합니다. `http://localhost:9229/json/list`에서 `devtoolsFrontendUrl`을 복사해 주소창에 붙여 넣습니다.
- DevTools의 Sources 탭에서 파일을 열어 줄 번호를 눌러 중단점을 걸고, Scope 패널에서 지역 변수를, Call Stack 패널에서 호출 경로를 봅니다. Console에서는 중단된 지점의 변수를 식으로 평가할 수 있습니다.
- Memory 탭에서 Heap snapshot 유형을 고르고 Take snapshot으로 힙 스냅샷을 찍습니다. 인스펙터는 프로파일링에도 쓰입니다.
- 프로세스가 끝나면 연결이 끊깁니다. 짧게 끝나는 스크립트는 `--inspect-brk`로 시작하는 것이 편합니다.
- VS Code(1.10 이후)는 같은 인스펙터에 붙는 디버거를 내장합니다(아래 "VS Code 디버거 연결").

## 브레이크포인트

브레이크포인트(breakpoint)는 실행이 그 줄에 도달하면 멈추게 하는 표시입니다. 멈춘 시점의 변수와 호출 스택을 볼 수 있고 한 줄씩 실행할 수 있습니다.

```js
function add(a, b) {
  const sum = a + b
  debugger // 디버거가 붙어 있으면 여기서 멈춤
  return sum
}
```

- `debugger` 문은 코드에 직접 적는 브레이크포인트입니다. 디버거가 없으면 무시됩니다. 커밋 전에 지웁니다.
- 디버거 UI에서 줄 번호를 눌러 거는 방식은 코드를 수정하지 않습니다.
- 조건부 브레이크포인트는 식이 참일 때만 멈춥니다(`num < 0`). 반복문 안의 특정 경우만 잡을 때 씁니다. `node inspect`에서는 `setBreakpoint('main.js', 4, 'num < 0')`입니다.
- VS Code에는 멈추지 않고 메시지만 남기는 로그포인트(logpoint), 횟수 조건의 히트 카운트 브레이크포인트도 있습니다.
- 멈춘 뒤의 조작은 같습니다. 한 줄 실행(step over), 함수 안으로(step into), 함수 밖으로(step out), 계속(continue)입니다.
- 비동기 코드는 `await` 뒤에서 이어지는 흐름을 따라가면서 스택의 `async` 프레임을 봅니다.
- 타이밍에 민감한 버그는 멈추면 상황이 바뀝니다. 그때는 브레이크포인트 대신 로그를 씁니다(자세히는 26편).

## NODE_DEBUG

`NODE_DEBUG`는 Node.js 코어 모듈이 내부 동작을 stderr에 출력하게 하는 환경변수입니다. 값은 쉼표로 구분한 모듈 이름 목록입니다.

```sh
NODE_DEBUG=module node app.mjs
# MODULE 30604: Module._load REQUEST ./x.cjs ...
```

- 코드를 고치지 않고 켤 수 있고 모듈 이름은 대문자 접두사로 나옵니다(`module` → `MODULE`, 뒤에 프로세스 아이디).
- 모듈 해석이 어떻게 진행되는지 볼 때(`module`)처럼 코어 모듈의 동작을 추적할 때 씁니다. 지원하는 이름의 전체 목록은 CLI 문서에 없으므로 해당 모듈 문서에서 확인합니다.
- 출력 형식은 내부 구현이라 버전 사이에 바뀔 수 있습니다. 사람이 읽는 용도로만 씁니다.
- 앱 코드는 `util.debuglog('이름')`으로 같은 방식의 조건부 출력을 만들 수 있습니다. 해당 이름이 `NODE_DEBUG`에 있을 때만 출력합니다.
- `NODE_DEBUG_NATIVE`는 C++ 코어 모듈용입니다.
- 운영 환경에서 켜 두면 출력량과 성능, 정보 노출을 고려해야 합니다.

## --trace-warnings

Node.js는 프로세스 경고(process warning)를 stderr에 한 줄로 출력합니다. 사용 중단 예고(deprecation), 리스너 누수 경고가 대표적입니다. 경고가 어디서 발생했는지 모를 때 `--trace-warnings`를 줍니다.

```sh
node --trace-warnings app.mjs
```

```text
(node:43924) [DEP0005] DeprecationWarning: Buffer() ...
    at showFlaggedDeprecation (node:buffer:222:11)
    at new Buffer (node:buffer:305:3)
    at file:///app/dep.mjs:1:11
```

- 기본 출력은 경고 이름과 메시지 한 줄에 `--trace-deprecation`을 쓰라는 안내입니다. `--trace-warnings`를 주면 경고가 만들어진 곳의 스택이 함께 출력됩니다. 사용 중단 경고만이면 `--trace-deprecation`입니다.
- 로컬 Node.js 24.15에서 `new Buffer(2)`를 쓰면 `DEP0005` 경고가 났고 `--trace-warnings`로 내 파일의 줄이 스택에 나타났습니다.
- 경고 코드(`DEP0005`)로 Node.js 문서의 사용 중단 목록에서 대체 방법을 찾습니다.
- 경고는 `process.emitWarning()`으로 직접 낼 수도 있고, `process.on('warning', ...)` 리스너로 받을 수 있습니다.
- `--no-warnings`는 모든 경고를 끕니다. 문제를 없애는 것이 아니라 숨기는 것이므로 원인을 확인한 뒤에만 씁니다. 옵션을 매번 줄 수 없으면 `NODE_OPTIONS` 환경변수에 넣습니다.

## 경고를 에러로

경고를 에러로 바꾸면 놓치기 쉬운 문제를 개발·CI 단계에서 실패로 드러낼 수 있습니다.

```sh
node --throw-deprecation app.mjs
```

- `--throw-deprecation`은 사용 중단 경고를 에러로 던집니다. 로컬 확인에서 `new Buffer(2)`가 `DeprecationWarning`을 던지며 종료 코드 `1`로 끝났습니다. 에러는 경고가 발행되는 시점(현재 동기 코드가 끝난 뒤)에 던져져서 그 앞의 동기 출력은 먼저 나옵니다.
- 이 옵션은 사용 중단 경고만 대상입니다. 모든 종류의 경고를 에러로 만드는 옵션은 문서에서 확인하지 못했습니다. 직접 `warning` 이벤트에서 던지는 방법을 쓸 수 있습니다.

```js
process.on('warning', (warning) => {
  throw warning // 처리되지 않은 예외가 되어 종료 코드 1
})
```

- 로컬에서 `process.emitWarning('x', 'CustomWarning', 'W001')`을 위 리스너로 받자 처리되지 않은 예외로 종료 코드 `1`이 되었습니다.
- 개발과 CI에서만 켭니다. 의존성이 내는 경고 때문에 운영이 죽지 않도록 운영 환경에는 적용하지 않습니다.
- 처리되지 않은 Promise rejection은 별도 옵션으로 제어합니다. 기본 동작과 `--unhandled-rejections` 모드는 24편에서 다룹니다.

## 메모리 스냅샷 개념

힙 스냅샷(heap snapshot)은 특정 시점에 V8 힙에 있는 모든 객체와 참조 관계를 기록한 파일입니다. 메모리가 계속 늘어나는 문제(누수 의심)에서 무엇이 메모리를 차지하는지 보는 도구입니다.

| 방법 | 설명 |
|------|------|
| `v8.writeHeapSnapshot(파일)` | 코드에서 호출해 `.heapsnapshot` 파일을 씀 |
| `--heapsnapshot-signal=SIGUSR2` | 지정한 시그널을 받으면 스냅샷을 씀 (기본은 꺼져 있음) |
| Chrome DevTools의 Memory 탭 | `--inspect`로 붙어 스냅샷을 찍음 |

```js
import { writeHeapSnapshot } from 'node:v8'

const file = writeHeapSnapshot('./before.heapsnapshot')
// 파일 경로를 돌려줌. DevTools Memory 탭에서 열어 봄
```

- 파일은 Chrome DevTools의 Memory 탭에서 열어 봅니다. 형식(JSON)의 스키마는 문서화되어 있지 않고 V8 버전에 따라 바뀔 수 있습니다.
- 누수는 스냅샷 두 장을 비교해서 찾습니다. 같은 작업을 여러 번 반복하기 전과 후에 찍어 늘어난 객체를 봅니다. 증가한 객체를 잡고 있는 참조 경로(retainers)가 원인입니다.
- 스냅샷은 비용이 큽니다. 문서는 생성에 힙 크기의 약 두 배의 메모리가 필요해 OOM 킬러가 프로세스를 종료시킬 위험이 있고, 생성하는 동안 이벤트 루프가 막힌다고 밝힙니다. 운영 서버에서는 신중히 찍습니다.
- 스냅샷에는 메모리 안의 데이터가 그대로 들어 있어서 비밀번호와 토큰 같은 값이 포함될 수 있습니다. 파일을 외부에 공유할 때 주의합니다.
- 프로파일링과 누수 분석은 고급 과정에서 더 다룹니다.

## CPU 프로파일 개념

CPU 프로파일(CPU profile)은 일정 시간 동안 어떤 함수가 CPU 시간을 얼마나 썼는지 표본을 모은 기록입니다. 느린 코드나 이벤트 루프를 막는 코드를 찾을 때 씁니다.

```sh
node --cpu-prof --cpu-prof-dir=./prof app.mjs
# ./prof/CPU.날짜.시각.pid....cpuprofile 생성
```

- `--cpu-prof`는 시작 때 V8 CPU 프로파일러를 켜고 종료 전에 프로파일을 파일(`.cpuprofile`)로 씁니다. `--cpu-prof-dir`로 폴더를, `--cpu-prof-name`으로 파일 이름을 정합니다. 이 옵션들은 22.4.0에서 Stable이 되었습니다.
- 힙 프로파일은 같은 방식의 `--heap-prof`입니다.
- 로컬에서 재귀 `fib(30)`을 실행하자 `.cpuprofile` 파일이 생성되었습니다. 이 파일은 CPU 프로파일을 보여 주는 도구(DevTools나 IDE)로 열어 시간을 많이 쓴 함수를 찾습니다. `--inspect`로 붙어 DevTools에서 직접 기록해도 됩니다.
- 읽는 법: Chrome DevTools 문서의 정의로 Self Time은 그 함수가 직접 실행한 시간(하위 호출 제외), Total Time은 하위 호출까지 합한 시간입니다. Self Time이 큰 함수가 병목 후보입니다.
- 프로파일은 앱을 실제로 실행하는 동안의 표본입니다. 문제가 일어나는 작업을 충분한 시간 동안 실행한 뒤 종료해야 의미가 있습니다.
- 프로파일러를 켜면 앱이 느려질 수 있으므로 측정은 운영 환경과 비슷한 조건에서 하되 켜고 끄는 시점을 한정합니다.

## 이벤트 루프 지연 측정

이벤트 루프 지연(event loop delay)은 이벤트 루프가 다음 반복으로 넘어가기까지 밀린 시간입니다. 동기 코드가 오래 돌면 타이머와 I/O 콜백이 늦게 실행되고, 이 지연이 응답 시간 저하로 나타납니다(자세히는 04편).

`perf_hooks.monitorEventLoopDelay()`는 지연을 히스토그램으로 표본 수집합니다(`node:perf_hooks`, Stable). 값은 나노초 단위입니다.

```js
import { monitorEventLoopDelay } from 'node:perf_hooks'

const h = monitorEventLoopDelay({ resolution: 10 })
h.enable()
// ... 일정 시간 동안 앱 실행 ...
h.disable()
const ms = (ns) => Math.round(ns / 1e6)
console.log('max', ms(h.max), 'p99', ms(h.percentile(99)))
```

- `resolution`은 표본을 뽑는 간격(밀리초)이며 기본은 10입니다. `enable()`과 `disable()`로 수집을 켜고 끕니다.
- `min`, `max`, `mean`, `stddev`, `percentile(n)`, `percentiles`로 분포를 읽습니다. 평균보다 `p99`와 `max`가 막힘을 드러냅니다.
- 로컬에서 루프를 300밀리초 막는 반복문을 실행하자 `max`가 약 299밀리초로 기록됐습니다. 막힌 시간만큼 지연이 늘어난다는 뜻입니다. 정상일 때의 중앙값은 이 환경에서 16밀리초 안팎이었습니다.
- 24.19.0부터 `samplePerIteration: true`로 반복마다 한 번씩 표본을 뽑는 방식을 고를 수 있습니다. 두 방식은 결과가 크게 달라 서로 비교하면 안 된다고 문서가 밝힙니다.
- `performance.eventLoopUtilization()`은 루프가 일한 시간과 쉰 시간의 비율(`idle`, `active`, `utilization`)을 돌려줍니다. 지연이 한 번의 막힘을 보여 준다면 이 값은 전체 부하를 보여 줍니다.
- 지연이 크면 CPU 프로파일로 막는 함수를 찾고, 동기 호출·큰 JSON 처리·긴 반복문을 비동기로 나눕니다(자세히는 04편).

## 재현 절차 만들기

재현 절차는 같은 문제를 다른 사람이나 미래의 내가 같은 방식으로 다시 일으키는 단계 목록입니다. 재현이 되면 절반은 해결된 것이고, 재현이 안 되면 고쳤는지 확인할 방법이 없습니다.

- 기록할 항목은 다음과 같습니다.

| 항목 | 담는 것 |
|------|---------|
| 환경 | `node --version`, 운영체제, 패키지 매니저와 lock 파일 |
| 입력 | 실행 명령, 인수, 환경변수(비밀 값은 제외), 입력 데이터 |
| 기대 결과 | 어떻게 동작해야 하는가 |
| 실제 결과 | 에러 메시지 전문, 스택, `cause`까지 |
| 빈도 | 항상인지, 가끔인지, 특정 조건에서만인지 |

- 문제를 가장 작은 코드로 줄입니다. 관련 없는 코드를 지워도 문제가 그대로이면 지운 것이 원인이 아닙니다. 줄이는 과정에서 원인이 드러나는 경우가 많습니다.
- 한 번에 하나만 바꾸고 결과를 비교합니다. Node.js 버전(`process.versions`), 의존성 버전, 입력 중 하나씩 바꿉니다.
- 가끔만 일어나는 문제는 타이밍과 순서가 원인인 경우가 많습니다. 동시 실행, 타이머, 네트워크 지연, 데이터 크기를 의심하고 같은 작업을 반복해서 빈도를 셉니다.
- 에러 메시지는 요약하지 않고 전문을 복사합니다. 메시지와 `code`, 스택의 첫 프레임이 단서입니다.
- 재현 코드를 테스트로 만들어 두면 고친 뒤 회귀를 막습니다(테스트는 중급 과정에서 다룹니다).
- 로그에서 같은 요청 아이디로 한 요청의 흐름을 모으고(26편), 진단 리포트로 당시의 환경을 남깁니다(아래 "process.report").

## VS Code 디버거 연결

VS Code는 인스펙터에 붙는 디버거를 내장하고 있어서 편집기 안에서 중단점, 변수 보기, 호출 스택을 씁니다. `launch.json` 설정(`.vscode/launch.json`)으로 실행과 연결을 정합니다.

```json
{
  "type": "node",
  "request": "launch",
  "program": "${workspaceFolder}/app.mjs"
}
```

| 방식 | 설정 | 설명 |
|------|------|------|
| 실행(launch) | `"request": "launch"` + `program` | VS Code가 프로세스를 시작하며 디버깅 |
| 연결(attach) | `"request": "attach"` + `"port": 9229` | 먼저 `node --inspect`로 띄운 프로세스에 붙음 |

- 자동 연결(Auto Attach)은 통합 터미널에서 실행한 Node.js 프로세스를 자동으로 디버깅합니다. 모드는 `smart`, `always`, `onlyWithFlag`입니다. JavaScript Debug Terminal을 열면 그 터미널에서 실행한 프로세스가 자동으로 디버깅됩니다.
- 중단점 종류는 조건부, 로그포인트, 히트 카운트, 트리거 방식입니다.
- 연결 설정에 `"restart": true`를 주면 프로세스가 재시작될 때 다시 붙습니다.
- 구체적인 설정 항목은 VS Code 문서를 따릅니다.

## --watch와 함께 쓰기

`--watch`는 파일이 바뀌면 Node.js 프로세스를 자동으로 다시 시작하는 감시 모드입니다(22.0.0과 20.13.0에서 Stable). 기본으로 진입점과 `require`·`import`된 모듈을 감시합니다.

```sh
node --watch app.mjs
node --watch-path=./src app.mjs
```

- `--watch-path`는 감시할 경로를 지정하며 이 경우 모듈 자동 감시는 꺼집니다. 파일 경로 인수가 필요하고 `--check`, `--eval`, `--interactive`, REPL과는 함께 쓸 수 없습니다. 파일 없이 실행하면 종료 코드 `9`입니다.
- 다시 시작할 때 콘솔을 지웁니다. 이전 출력을 남기려면 `--watch-preserve-output`을 줍니다.
- 로컬에서 파일을 수정하자 `Restarting 'w.mjs'`가 출력되고 다시 실행되었습니다.
- `--inspect`와 함께 쓸 수 있습니다. 재시작할 때마다 인스펙터가 새로 열립니다. 로컬에서 `--inspect=0`을 쓰자 재시작할 때마다 포트가 달라졌으므로 디버거를 다시 붙이기 쉽게 고정 포트(`--inspect=9229`)를 쓰고, VS Code의 `restart` 옵션과 함께 씁니다.
- 변경 후 바로 확인하고 싶은 개발 중의 디버깅에 맞습니다. 운영 환경에서는 쓰지 않습니다.

## process.report

진단 리포트(diagnostic report)는 프로세스의 상태를 JSON 파일로 남기는 기능입니다(Stable). JavaScript와 네이티브 스택, 힙 통계, 플랫폼 정보, 자원 사용량, 이벤트 루프(libuv) 상태가 담깁니다. 크래시나 멈춤을 사후에 분석할 때 씁니다.

```sh
node --report-uncaught-exception \
     --report-on-fatalerror app.mjs
```

| 옵션 | 시점 |
|------|------|
| `--report-uncaught-exception` | 처리되지 않은 예외로 종료될 때 |
| `--report-on-fatalerror` | 메모리 부족 같은 런타임 치명 오류 때 |
| `--report-on-signal` | 시그널을 받을 때 (기본 `SIGUSR2`, Windows 미지원) |
| `process.report.writeReport()` | 코드에서 직접 호출 |

```js
process.report.directory = './reports'
process.report.filename = 'my-report.json'
const file = process.report.writeReport()
```

- 로컬에서 `writeReport()`가 만든 파일의 최상위 키는 `header`, `javascriptStack`, `javascriptHeap`, `nativeStack`, `resourceUsage`, `libuv`, `workers`, `environmentVariables` 등이었고, `--report-uncaught-exception`으로 낸 크래시 리포트에는 에러 메시지와 JavaScript 스택이 담겼습니다.
- `--report-directory`, `--report-filename`, `--report-compact`(한 줄 JSON)로 위치와 형식을 정합니다. `process.report.reportOnUncaughtException = true`처럼 코드에서도 켤 수 있습니다.
- 리포트에는 환경변수가 그대로 포함됩니다. 비밀 값이 들어 있을 수 있으므로 `--report-exclude-env`로 제외할 수 있고(23.3.0과 22.13.0에서 추가), 로컬에서 켜자 `environmentVariables`가 빠졌습니다. 파일을 공유하기 전에 확인합니다.
- 힙 스냅샷이 메모리의 객체를, CPU 프로파일이 시간의 분포를 보여 준다면 리포트는 한 시점의 전반적 상태 요약입니다.

## 핵심 정리

- 스택은 위에서부터 내 코드의 첫 프레임을 찾아 읽고, `cause` 체인은 바깥(증상)에서 안쪽(근본 원인)으로 내려가며 `code`와 `syscall`을 봅니다.
- `node inspect`는 내장 명령줄 디버거이고, `--inspect`는 인스펙터를 열어 Chrome DevTools와 VS Code가 붙게 하며 `--inspect-brk`는 첫 줄에서 멈춥니다. 인스펙터는 공개 IP에 열지 않습니다.
- 브레이크포인트는 `debugger` 문이나 디버거 UI로 걸고, 조건부 중단점으로 특정 경우만 잡습니다.
- `NODE_DEBUG`로 코어 모듈의 내부 로그를, `--trace-warnings`로 경고의 발생 위치를 보고, `--throw-deprecation`으로 사용 중단 경고를 에러로 바꿉니다.
- 힙 스냅샷은 메모리 점유와 누수를, CPU 프로파일(`--cpu-prof`)은 느린 함수를, `monitorEventLoopDelay`는 이벤트 루프 막힘을 보여 줍니다.
- 재현 절차(환경, 입력, 기대와 실제 결과)를 남기고 최소 코드로 줄이며, 진단 리포트(`process.report`)는 크래시 시점의 상태를 JSON으로 저장합니다.

## 내장 모듈

내장 모듈은 Node.js 실행 파일에 포함되어 설치 없이 쓰는 모듈입니다. `fs`, `path`, `os`, `http`, `events`가 해당합니다.

```js
import { readFile } from 'node:fs/promises'
import path from 'node:path'
```

- 지정자가 내장 모듈 이름이면 다른 어떤 검색보다 먼저 내장 모듈을 돌려줍니다. 같은 이름의 `node_modules` 패키지나 로컬 파일이 있어도 내장 모듈이 이깁니다.
- 목록은 `module.builtinModules`로, 이름 확인은 `module.isBuiltin()`으로 합니다.

```js
import { isBuiltin } from 'node:module'
isBuiltin('fs')        // true
isBuiltin('node:fs')   // true
isBuiltin('wss')       // false
```

- `module.builtinModules`는 v23.5.0부터 `node:` 접두사로만 쓰는 모듈도 목록에 포함합니다.
- 내장 모듈이 아닌 이름은 `ERR_MODULE_NOT_FOUND`(ESM) 또는 `MODULE_NOT_FOUND`(CommonJS)입니다.

## node: 접두사

`node:` 접두사는 지정자가 내장 모듈임을 명시하는 표기입니다. `fs`와 `node:fs`는 같은 모듈을 돌려줍니다.

- 접두사가 있으면 `require.cache`에 같은 이름의 항목이 있어도 항상 내장 모듈을 돌려줍니다. 캐시를 우회합니다.
- 접두사를 붙이면 내장 모듈인지 npm 패키지인지 이름만으로 드러납니다. 같은 이름의 npm 패키지와 혼동되지 않습니다.
- 일부 내장 모듈은 접두사가 있어야만 불러올 수 있습니다.

| 접두사 필수 모듈 | 용도 |
|------------------|------|
| `node:test` | 테스트 러너 |
| `node:sqlite` | SQLite |
| `node:sea` | 단일 실행 파일 애플리케이션 |

```js
import test from 'node:test' // ✅
import test from 'test'      // ❌ ERR_MODULE_NOT_FOUND
import x from 'node:nope'    // ❌ ERR_UNKNOWN_BUILTIN_MODULE
```

이 문서의 예제는 내장 모듈에 항상 `node:`를 붙입니다.

## 로컬 파일 모듈

로컬 파일 모듈은 프로젝트 안의 파일을 경로로 가리키는 모듈입니다. 지정자가 `./`, `../`, `/`로 시작하거나 `.`이면 로컬 경로로 해석합니다.

```js
import { add } from './math.js'
import config from '../config/app.js'
```

경로는 가져오는 파일 위치 기준입니다. 현재 작업 디렉터리(`process.cwd()`)와 무관합니다. ESM과 CommonJS의 확장자 처리가 다릅니다.

| 항목 | CommonJS `require` | ESM `import` |
|------|--------------------|--------------|
| 확장자 생략 | 허용. 정확한 파일, `.js`, `.json`, `.node` 순으로 시도 | 불허. 확장자까지 씀 |
| 폴더 지정 | 허용. `package.json`의 `main`, 없으면 `index.js` | 불허. `ERR_UNSUPPORTED_DIR_IMPORT` |
| `.json` 불러오기 | 바로 객체로 파싱 | `with { type: 'json' }` 필요(09편) |

```js
// CommonJS
require('./ext/m')    // m이 있으면 m, 없으면 m.js, m.json, m.node
require('./ext/dir')  // dir/package.json의 main, 없으면 dir/index.js
```

**흔한 실수:** `./`를 빼먹으면 로컬 파일이 아니라 패키지 이름으로 해석됩니다. `import x from 'utils/a.js'`는 `node_modules`를 찾습니다.

## 서드파티 모듈

서드파티 모듈은 npm에서 설치한 패키지입니다. 내장 모듈도 아니고 경로로 시작하지도 않는 지정자(bare specifier)가 패키지 이름으로 해석됩니다.

```js
import express from 'express'
import { z } from 'zod'
import { Router } from '@scope/pkg'      // 스코프 패키지
import util from 'lodash/get.js'         // 패키지 안의 하위 경로
```

- 지정자는 패키지 이름과 하위 경로로 나뉩니다. `@scope/pkg/sub`에서 이름은 `@scope/pkg`, 하위 경로는 `/sub`입니다.
- 패키지는 `node_modules` 폴더 안에서 찾습니다. 설치는 npm이 하고(12편), Node.js는 설치된 폴더 구조만 읽습니다.
- 패키지의 진입점은 `package.json`의 `exports` 또는 `main`이 정합니다(아래 해당 절).
- 설치하지 않은 패키지는 `ERR_MODULE_NOT_FOUND` 또는 `MODULE_NOT_FOUND`입니다. `package.json`의 `dependencies`에 적혀 있어도 설치되지 않았으면 같습니다.

## 모듈 해석 순서

`require(X)`의 해석 순서입니다. 위에서 아래로 처음 맞는 규칙을 적용합니다.

| 순서 | 조건 | 동작 |
|------|------|------|
| 1 | X가 내장 모듈 | 내장 모듈 반환 |
| 2 | X가 `./`, `../`, `/`로 시작하거나 `.` | 파일로 찾고, 없으면 폴더로 찾음. 둘 다 없으면 에러 |
| 3 | X가 `#`로 시작 | `package.json`의 `imports`에서 찾음 |
| 4 | 패키지 자신의 이름으로 시작 | `exports`로 자기 참조 |
| 5 | 그 외 | `node_modules` 폴더들을 차례로 탐색 |
| 6 | 못 찾음 | `MODULE_NOT_FOUND` |

- 파일로 찾기: X 자체가 파일이면 그것을, 아니면 `X.js`, `X.json`, `X.node` 순서로 찾습니다.
- 폴더로 찾기: `X/package.json`의 `main`이 가리키는 파일을 찾고, 없으면 `X/index.js`, `X/index.json`, `X/index.node` 순서로 찾습니다.
- `import`(ESM)는 확장자 보충과 폴더 해석을 하지 않고, 상대 경로는 정확한 파일만 봅니다. 내장 모듈, `#` 지정자, 패키지 해석 순서는 비슷합니다.
- ESM에서는 `file:`과 `data:` URL 지정자도 쓸 수 있습니다.
- 해석 결과는 `require.resolve()`로 로드 없이 확인합니다. 찾는 경로 목록은 `require.resolve.paths()`입니다. ESM에서는 `import.meta.resolve()`가 같은 일을 합니다.

```js
require.resolve('express')  // 절대 경로 문자열
require.resolve.paths('fs') // null (내장 모듈)
```

- 모든 탐색이 실패한 뒤 마지막으로 전역 폴더를 봅니다. 환경변수 `NODE_PATH`에 적힌 경로, 그다음 `$HOME/.node_modules`, `$HOME/.node_libraries`, `$PREFIX/lib/node`입니다. 이 방식은 권장하지 않습니다.
- ESM은 `NODE_PATH`를 쓰지 않습니다.

## node_modules를 위로 찾아 올라가는 규칙

`node_modules`는 현재 파일이 있는 폴더부터 시작해 한 단계씩 상위 폴더로 올라가며, 각 단계의 `node_modules`를 확인합니다. 루트까지 올라가면 멈춥니다. 문서의 예는 다음과 같습니다.

`/home/ry/projects/foo.js`에서 `require('bar.js')`를 하면 순서대로 찾습니다.

```text
/home/ry/projects/node_modules/bar.js
/home/ry/node_modules/bar.js
/home/node_modules/bar.js
/node_modules/bar.js
```

- 가까운 `node_modules`가 먼저입니다. 같은 이름의 패키지가 여러 단계에 있으면 가장 가까운 것이 쓰입니다.
- 이 규칙 덕분에 패키지마다 자기 의존성의 다른 버전을 안쪽 `node_modules`에 둘 수 있습니다.
- 경로에 `node_modules`라는 폴더가 있으면 그 폴더 안에서 다시 `node_modules/node_modules`를 찾지 않고 건너뜁니다.
- 모노레포에서는 프로젝트 하위 폴더에서도 루트에 설치한 패키지를 찾을 수 있습니다(자세히는 14편).
- 의도하지 않게 상위 폴더에 설치된 패키지가 잡히기도 합니다. `package.json`에 적지 않은 패키지가 우연히 동작하는 경우가 이렇게 생깁니다.

```js
console.log(require.resolve.paths('x'))
// [ '.../project/node_modules', '.../node_modules', ... ]
```

**흔한 실수:** 한 프로젝트에 같은 패키지가 서로 다른 위치에 설치되어 두 인스턴스가 생기는 것입니다. `instanceof`와 전역 상태가 어긋납니다(아래 "듀얼 패키지 위험").

## package exports

`exports` 필드는 패키지가 밖에 공개하는 진입점을 선언하는 필드입니다. v12.7.0에 추가되었고 안정 상태입니다. `main`과 달리 여러 진입점과 조건을 선언할 수 있고 패키지 내부를 캡슐화합니다.

```json
{
  "name": "pkg",
  "exports": {
    ".": "./index.js",
    "./feature": "./src/feature.js",
    "./utils/*.js": "./src/utils/*.js",
    "./package.json": "./package.json"
  }
}
```

| 사용 | 해석 |
|------|------|
| `import 'pkg'` | `./index.js` |
| `import 'pkg/feature'` | `./src/feature.js` |
| `import 'pkg/utils/a.js'` | `./src/utils/a.js` |
| `import 'pkg/src/feature.js'` | `ERR_PACKAGE_PATH_NOT_EXPORTED` |

- `exports`가 있으면 선언하지 않은 하위 경로는 불러올 수 없습니다. 내부 파일을 직접 가져가는 것을 막는 효과가 있습니다.
- 키는 `.`(루트) 또는 `./`로 시작하는 하위 경로입니다. 값은 `./`로 시작하는 상대 경로입니다. `..`나 `.` 구간이 들어간 대상은 허용되지 않습니다.
- 값이 문자열 하나면 루트만 선언하는 축약형입니다. `"exports": "./index.js"`는 `".": "./index.js"`와 같습니다.
- 하위 경로 패턴은 `*`를 문자열 치환으로 처리합니다(v14.13.0). 글롭이 아니며 `*`에 슬래시가 들어갈 수 있습니다.
- 값을 `null`로 두면 그 경로를 내보내기에서 제외합니다.
- `"./package.json"`은 자동으로 공개되지 않아서 필요하면 직접 선언합니다.
- 자기 이름으로 자기 패키지를 `exports`를 통해 불러올 수 있습니다(self-referencing).
- `exports`는 `import`와 `require` 모두에 적용됩니다.

## package imports

`imports` 필드는 패키지 안에서만 쓰는 내부 별칭을 정의하는 필드입니다. 키는 반드시 `#`로 시작합니다. v14.6.0에 추가되었습니다.

```json
{
  "imports": {
    "#lib/*": "./src/lib/*.js",
    "#cfg": {
      "node": "./src/cfg-node.js",
      "default": "./src/cfg.js"
    }
  }
}
```

```js
import { name } from '#lib/x'  // ./src/lib/x.js
import cfg from '#cfg'         // 조건에 따라 선택
import o from '#other'         // ERR_PACKAGE_IMPORT_NOT_DEFINED
```

- `../../../utils/x.js` 같은 긴 상대 경로를 줄입니다.
- 패키지 안의 파일에서만 동작합니다. 이 패키지를 쓰는 다른 패키지는 `#` 별칭을 쓸 수 없습니다.
- `exports`와 달리 외부 패키지를 대상으로 지정할 수 있습니다. 위 예에서 `"node"` 조건 값을 `"dep-node-native"` 같은 패키지 이름으로 쓸 수 있습니다.
- 조건과 `*` 패턴(v14.13.0)을 지원합니다.
- 정의하지 않은 별칭은 `ERR_PACKAGE_IMPORT_NOT_DEFINED`입니다.
- TypeScript의 `paths` 별칭과 다릅니다. `imports`는 런타임이 직접 해석합니다(자세히는 27편).

## exports의 import / require 조건

조건부 내보내기는 `exports` 값을 객체로 쓰고, 불러오는 방식이나 환경에 따라 다른 파일을 고르는 기능입니다. v13.2.0과 v12.16.0에 추가되었습니다.

```json
{
  "exports": {
    "import": "./dist/index.mjs",
    "require": "./dist/index.cjs"
  }
}
```

| 조건 | 매칭되는 경우 |
|------|---------------|
| `node-addons` | 네이티브 애드온을 지원하는 Node.js |
| `node` | Node.js 환경 |
| `import` | `import` 또는 `import()`로 불러올 때 |
| `require` | `require()`로 불러올 때 |
| `module-sync` | `import`, `import()`, `require()` 모두. 대상은 top-level await 없는 ESM |
| `default` | 항상 매칭하는 대체값. 마지막에 둠 |

- 조건은 위에서 아래로 처음 맞는 것을 씁니다. 객체 안의 키 순서가 우선순위입니다.
- `import`와 `require`는 동시에 매칭되지 않습니다.
- 조건을 중첩할 수 있습니다. `node` 안에 `import`·`require`를 둘 수 있습니다.
- `module-sync`는 한 ESM 파일을 `import`와 `require`가 같이 쓰게 하는 조건입니다. top-level await가 있으면 `require()`에서 `ERR_REQUIRE_ASYNC_MODULE`입니다.
- 사용자가 `--conditions=development`로 조건을 추가할 수 있습니다(v14.9.0).
- 커뮤니티 조건으로 `types`, `browser`, `development`, `production`이 있습니다.

로컬에서 확인한 결과입니다. 같은 패키지가 불러오는 방식에 따라 다른 파일을 돌려줍니다.

```js
import d from 'dual'                // 'esm' (import 조건)
const c = createRequire(import.meta.url)('dual')
// 'cjs' (require 조건)
```

### types 조건

`types` 조건은 TypeScript가 이 진입점의 타입 선언 파일을 찾을 때 쓰는 조건입니다. Node.js가 직접 쓰지는 않습니다. 조건은 위에서 아래로 처음 맞는 것을 쓰므로 항상 맨 앞에 둡니다.

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

TypeScript는 `moduleResolution`이 `nodenext`일 때 `exports`가 있으면 `exports`만 따라 해석하고, 없을 때 `types`, `main` 순으로 찾습니다.

### 듀얼 패키지 위험

듀얼 패키지는 `import` 조건과 `require` 조건에 서로 다른 파일을 두어 ESM·CommonJS 둘 다 지원하는 패키지입니다. 위험은 한 프로세스에서 두 형식이 모두 불러와지면 파일이 둘이라 모듈 인스턴스도 둘이 된다는 점입니다.

```js
// ctr 패키지: import는 i.mjs, require는 i.cjs. 각자 n = 0
import { inc } from 'ctr'
const cjs = createRequire(import.meta.url)('ctr')
inc(); inc()
console.log(cjs.inc()) // 1 (카운터가 따로 있음)
```

- 같은 이름의 상태(싱글턴, 캐시, `instanceof` 대상 클래스)가 둘로 갈라집니다.
- 앱은 ESM으로, 의존하는 다른 패키지는 CommonJS로 불러올 때 흔히 생깁니다.
- 대응은 상태를 두지 않거나, 하나의 파일을 두 조건에 모두 쓰는 것입니다. `module-sync` 조건에 ESM 파일 하나만 두면 인스턴스가 하나입니다(로컬 확인: 두 방식 호출 후 카운터 값이 `3`).

## main 필드

`main` 필드는 패키지의 대표 진입점 파일을 가리키는 필드입니다. 값은 패키지 루트에서의 경로이고, 없으면 루트의 `index.js`입니다.

```json
{
  "name": "oldpkg",
  "main": "./lib/entry.js"
}
```

- `require('oldpkg')`와 `import 'oldpkg'`가 이 파일을 불러옵니다.
- `main`은 모든 Node.js 버전이 지원하지만 진입점이 하나뿐입니다.
- `exports`가 함께 있으면 `exports`가 우선합니다. `main`은 `exports`를 모르는 오래된 도구와 Node.js 12.7 이전을 위한 대체입니다.
- `exports` 없이 `main`만 있으면 패키지 안의 다른 파일을 `pkg/lib/other.js`로 자유롭게 불러올 수 있습니다.
- 폴더 해석에서 `main`은 `require('./dir')`처럼 폴더를 가리킬 때도 쓰입니다. `main`이 없으면 `index.js`입니다.
- `main`이 가리키는 파일은 `files`에 없어도 항상 패키지에 포함됩니다.

```json
{
  "main": "./index.js",
  "exports": "./index.js"
}
```

위처럼 둘을 함께 쓰면 옛 Node.js 호환을 유지합니다.

## bin 필드

`bin` 필드는 패키지가 설치될 때 PATH에서 실행할 명령으로 노출되는 파일을 선언합니다. 값은 문자열 하나 또는 명령 이름과 파일 경로를 짝지은 객체입니다.

```json
{ "bin": "./cli.js" }
```

```json
{ "bin": { "mytool": "./bin/cli.js", "mt": "./bin/cli.js" } }
```

- 문자열이면 명령 이름이 패키지 이름이 됩니다.
- 가리키는 파일 첫 줄에 쉬뱅(`#!/usr/bin/env node`)이 있어야 합니다.
- 설치할 때 Unix에서는 심볼릭 링크가, Windows에서는 `.cmd` 래퍼가 만들어집니다.
- 로컬 설치는 `node_modules/.bin`에, 전역 설치는 전역 bin 폴더에 연결됩니다(자세히는 13편).
- `bin` 대상 파일은 `files`에 없어도 항상 패키지에 포함됩니다.
- 개념 설명은 28편에서 이어서 다룹니다.

```js
#!/usr/bin/env node
console.log('hello cli')
```

## files 필드

`files` 필드는 `npm publish` 때 패키지에 담을 파일 목록입니다. `.gitignore`와 같은 패턴 문법의 배열입니다. 생략하면 `["*"]`로 간주해 전부 담습니다.

```json
{
  "files": ["dist", "bin", "!dist/**/*.test.js"]
}
```

항상 포함되는 파일(`files` 설정과 무관):

- `package.json`
- `README`
- `LICENSE` 또는 `LICENCE`
- `main`이 가리키는 파일
- `bin`이 가리키는 파일

항상 제외되는 파일(바꿀 수 없음): `.git`, `.npmrc`, `node_modules`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`.

- 지정하지 않으면 `.npmignore`를 쓰고, 그것도 없으면 `.gitignore`를 씁니다. 다만 루트의 `files`가 있으면 그 목록이 기준입니다.
- 허용 목록 방식이라서 새 파일이 실수로 포함되는 일이 줄어듭니다.
- 게시 전에 `npm pack --dry-run`으로 포함될 파일을 확인합니다(자세히는 14편).
- `exports`가 가리키는 파일이 `files`에 빠지면 설치한 쪽에서 `ERR_MODULE_NOT_FOUND`가 납니다.

**흔한 실수:** `dist`만 `files`에 넣고 `exports`가 `./src/...`를 가리키는 식의 불일치입니다. 게시된 패키지는 로컬에서 되던 경로가 깨집니다.

## 핵심 정리

- 지정자는 내장 모듈, 상대·절대 경로, `#` 별칭, 패키지 이름 순으로 해석하고, 내장 모듈은 `node:`를 붙여 이름을 명시한다. `node:test`·`node:sqlite`·`node:sea`는 접두사가 필수다.
- `require`는 확장자와 폴더를 보충하지만 ESM `import`는 상대 경로에 확장자까지 쓰며 폴더를 가져올 수 없다.
- 패키지 이름은 현재 폴더부터 상위로 올라가며 `node_modules`를 찾고 가장 가까운 것이 이긴다.
- `exports`는 공개 진입점을 선언하고 나머지를 캡슐화하며 `main`보다 우선한다. `imports`는 `#` 별칭으로 패키지 내부 경로만 줄인다.
- 조건은 위에서 아래로 처음 맞는 것이 쓰이고 `types`는 맨 앞, `default`는 맨 뒤에 둔다. 듀얼 패키지는 인스턴스가 둘이 될 위험이 있다.
- `bin`은 PATH에 노출할 실행 파일, `files`는 게시할 파일의 허용 목록이다.

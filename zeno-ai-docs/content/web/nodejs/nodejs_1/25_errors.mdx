## Error

`Error`는 무엇이 잘못됐는지와 그 시점의 호출 경로(스택)를 담는 JavaScript 내장 객체입니다. Node.js가 던지는 JavaScript 에러와 시스템 에러는 모두 `Error`의 인스턴스이거나 그것을 상속합니다.

```js
const err = new Error('disk full')
err instanceof Error // true
err.name             // 'Error'
```

Node.js 문서가 분류하는 에러는 다섯 가지입니다.

| 분류 | 예 |
|------|----|
| 표준 JavaScript 에러 | `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError` |
| `DOMException` | `fetch`, `AbortSignal` 같은 웹 플랫폼 API가 던짐 |
| 시스템 에러 | 없는 파일 열기, 닫힌 소켓에 쓰기 (`code`, `syscall` 보유) |
| `AssertionError` | `node:assert`가 논리 위반을 감지했을 때 |
| 사용자 정의 에러 | 애플리케이션 코드가 직접 만든 에러 |

에러가 전달되는 길은 API 스타일에 따라 다릅니다(자세히는 21편, 23편).

| API 스타일 | 에러 전달 |
|------------|-----------|
| 동기 API (`readFileSync`) | `throw` |
| Promise API | reject, `await`에서 `throw`로 바뀜 |
| 콜백 API | 콜백의 첫 번째 인수 |
| `EventEmitter` 기반 객체 | `'error'` 이벤트 |

- 던지는 값이 `Error`일 필요는 없습니다. 문자열이나 객체도 던질 수 있지만 스택이 없어서 추적할 수 없습니다. 항상 `Error`(또는 그 하위 클래스)를 던집니다.

```js
try { throw 'oops' } catch (e) {
  e instanceof Error // false
  e.stack            // undefined
}
```

- `catch`로 받은 값이 에러라고 가정하지 못합니다. 라이브러리가 아무 값이나 던질 수 있어서, 속성을 읽기 전에 `e instanceof Error`로 확인합니다. `Error.isError(e)`는 `vm` 컨텍스트처럼 다른 realm에서 만든 내장 에러도 `true`로 판별합니다. 이때 `instanceof Error`는 `false`입니다(Node.js 24.15에서 확인).
- `try...catch`는 같은 호출 흐름의 던짐만 잡습니다. 이미 호출이 끝난 뒤 `'error'` 이벤트로 발생한 에러는 잡지 못합니다.
- 처리하지 않은 예외는 프로세스를 즉시 종료시킵니다. `'error'` 리스너 없이 `emit('error')`를 해도 같습니다.

## message

`message`는 사람이 읽는 설명 문자열이며 `new Error(message)`로 정합니다. 객체를 넘기면 `String(값)`의 결과가 됩니다.

```js
const err = new Error('The message')
err.message // 'The message'
new Error(404).message // '404'
```

- 에러 이름과 함께 `stack` 첫 줄에 들어갑니다.
- Node.js 문서는 Node.js가 던지는 에러의 `message`가 어느 버전에서든 바뀔 수 있다고 밝힙니다. `message`를 문자열 비교나 정규식으로 분기하면 업데이트 때 깨질 수 있습니다. 종류를 구별할 때는 `code`나 `instanceof`를 씁니다.
- 생성 뒤에 `message`를 바꿔도 `stack` 첫 줄은 바뀌지 않을 수 있습니다. 문서는 `stack`을 먼저 읽은 뒤 바꾸는 경우를 예로 듭니다. 새 메시지가 필요하면 에러를 다시 만들고 원본은 `cause`로 연결합니다.
- 메시지에는 무엇이 실패했는지와 식별에 필요한 값(파일 경로, 아이디)을 담습니다. 비밀번호·토큰 같은 값은 넣지 않습니다(자세히는 26편).

## stack

`stack`은 에러를 만든 지점의 호출 경로를 담은 문자열입니다. 첫 줄은 `이름: 메시지`이고, 그 아래에 `at`으로 시작하는 프레임이 한 줄씩 이어집니다.

```text
Error: boom
    at a (file:///app/main.mjs:2:9)
    at async b (file:///app/main.mjs:5:3)
```

- 프레임의 위치 표기는 CommonJS면 절대 경로, ES Modules면 `file:///...` URL, Node.js 내부 코드면 `node:...`입니다.
- 스택은 가장 위(에러를 만든 곳)에서 시작해 호출한 쪽으로 내려갑니다. 읽는 방법은 29편에서 다룹니다.
- `await`를 거치면 `at async 함수이름` 프레임으로 이어집니다. 이벤트 루프의 다른 틱에서 시작된 콜백은 호출자가 스택에 남지 않아, 그 위쪽 경로가 보이지 않습니다.
- 캡처되는 프레임은 `Error.stackTraceLimit`(기본 10)과 동기 실행의 시작점 중 작은 쪽까지입니다. 값을 키우면 이후에 만드는 에러부터 더 많이 담습니다.
- 값이 0이거나 숫자가 아니거나 음수이면 프레임을 담지 않습니다.
- `stack`에는 파일 경로와 내부 구조가 드러나므로 외부 응답에 그대로 내보내지 않습니다.
- `stack`은 내장 에러 객체에만 붙은 숨은 내부 값을 읽는 접근자입니다. 내장 에러가 아닌 객체(`Proxy` 등)에서 호출하면 `undefined`입니다.

## cause

`cause`는 이 에러를 일으킨 원래 에러입니다(Node.js 16.9.0 추가). 낮은 층의 에러를 잡아 의미 있는 메시지의 새 에러로 바꿔 던질 때, 원본을 잃지 않으려고 씁니다.

```js
import { readFile } from 'node:fs/promises'

async function loadConfig(path) {
  try {
    return JSON.parse(await readFile(path, 'utf8'))
  } catch (cause) {
    throw new Error(`load failed: ${path}`, { cause })
  }
}
// err.cause는 원본 ENOENT 또는 SyntaxError
```

- 생성자의 두 번째 인수 `{ cause }`로 지정합니다. 옵션을 주지 않으면 `cause` 프로퍼티 자체가 생기지 않습니다.
- `cause`에는 에러가 아닌 값도 넣을 수 있습니다.
- `console.log`와 `util.inspect`는 `cause`를 재귀적으로 `[cause]: ...` 형태로 출력해서 원인 체인이 로그에 남습니다. `JSON.stringify(err)`는 `{}`입니다. `message`, `stack`, `cause`가 열거 불가라서 구조화 로그에서는 직접 꺼내 씁니다(자세히는 26편).
- 원인 체인은 `while (e.cause)`로 따라 내려가며 읽습니다(29편).

**흔한 실수:** 에러를 잡아 새 에러를 던지면서 `cause`를 빼는 것입니다. 원래 스택과 `code`가 사라져 원인을 찾을 수 없게 됩니다. 반대로 같은 층에서 이미 로깅한 에러를 `cause`로 다시 감싸 던지면 같은 에러가 로그에 여러 번 남습니다. 한 에러는 한 번만 기록합니다.

## 커스텀 에러

커스텀 에러는 `Error`를 상속한 애플리케이션 전용 클래스입니다. `instanceof`와 `code`로 종류를 구별할 수 있게 하는 것이 목적입니다.

```js
class AppError extends Error {
  constructor(code, message, options) {
    super(message, options)
    this.name = new.target.name
    this.code = code
  }
}
class NotFoundError extends AppError {
  constructor(what, options) {
    super('NOT_FOUND', `${what} not found`, options)
  }
}
```

- `super(message, options)`를 가장 먼저 호출하고, `options`를 그대로 넘겨야 `cause`가 이어집니다.
- `name`을 따로 정하지 않으면 모든 하위 클래스의 `name`이 `'Error'`로 나옵니다. `this.name = new.target.name`으로 실제로 생성한 클래스 이름을 씁니다.
- 필드 선언(`name = 'X'`)이나 `this.name =` 대입은 열거 가능한 자기 프로퍼티를 만들어서 `Object.keys`와 로그에 나타납니다. 보이지 않게 하려면 `Object.defineProperty`나 프로토타입에 정의합니다.
- 클래스마다 `code`를 하나씩 둡니다. 클래스가 너무 많아지면 `AppError` 하나에 `code`만 달리하는 방식이 더 단순합니다.

## 에러 코드 code

`error.code`는 에러 종류를 가리키는 문자열 라벨입니다. Node.js 문서는 `code`를 에러를 식별하는 가장 안정적인 방법으로 정하고, `code`는 메이저 버전이 바뀔 때만 바뀐다고 밝힙니다.

| 종류 | 예 |
|------|----|
| 시스템 에러 코드 | `ENOENT`, `EACCES`, `EADDRINUSE`, `ECONNREFUSED` |
| Node.js 에러 코드 | `ERR_INVALID_ARG_TYPE`, `ERR_MODULE_NOT_FOUND` |
| 중단 | `ABORT_ERR` (`AbortError`의 `name`은 `'AbortError'`) |

- Node.js의 `ERR_*` 코드는 문서의 Node.js error codes 목록에 정리되어 있습니다.
- `AbortSignal`을 쓰는 API 중 `fetch`는 `DOMException`을, `events.once()` 같은 Node.js 전용 API는 `name`이 `'AbortError'`이고 `code`가 `'ABORT_ERR'`인 일반 에러를 던집니다. 어느 쪽이든 `err?.name === 'AbortError'`로 판별합니다(자세히는 22편).
- `DOMException`의 `code`는 문자열이 아니라 숫자입니다. 종류는 `name`으로 판별합니다.
- 애플리케이션 에러에도 `code`를 달아 두면 호출 측이 `message`가 아니라 `code`로 분기할 수 있습니다.

```js
try {
  await readFile(path)
} catch (err) {
  if (err.code === 'ENOENT') return null // 없으면 null
  throw err                              // 나머지는 위로
}
```

**흔한 실수:** `err.message.includes('no such file')`로 분기하는 것입니다. 메시지는 운영체제와 버전에 따라 달라집니다.

## syscall

시스템 에러는 `Error`에 운영체제 호출 정보가 더해진 객체입니다. `syscall`은 실패한 시스템 호출의 이름입니다.

| 속성 | 뜻 |
|------|----|
| `code` | 문자열 코드 (`'ENOENT'`) |
| `errno` | libuv가 정한 음수 번호 |
| `syscall` | 실패한 시스템 호출 (`'open'`) |
| `path` | 관련 파일 경로 (파일 시스템 에러) |
| `dest` | 목적지 경로 (복사·이름 변경 에러) |
| `address`, `port` | 실패한 네트워크 주소·포트 |

```js
try { await readFile('nope.txt') } catch (e) {
  e.code    // 'ENOENT'
  e.syscall // 'open'
  e.path    // 'nope.txt' 를 절대 경로로 풀어 쓴 값
  e.errno   // Linux는 -2, Windows는 -4058
}
```

- `errno`는 운영체제마다 값이 달라서 비교에 쓰지 않습니다. 이름이 필요하면 `util.getSystemErrorName(err.errno)`를 씁니다. 분기는 `code`로 합니다.
- 어떤 호출에서 어떤 경로로 실패했는지 `syscall`과 `path`로 알 수 있습니다. 같은 `ENOENT`라도 `open`과 `scandir`이 다른 상황입니다.
- 파일 시스템 에러 코드는 18편에서, 로그에 `path`를 남길 때의 주의는 26편에서 다룹니다.

## 운영 에러

운영 에러(operational error)는 코드가 올바르게 작성됐어도 실행 환경 때문에 생기는 에러입니다. 프로그램이 실행되는 동안 일어날 수 있다고 예상하고 처리해야 하는 대상입니다. Node.js 공식 문서가 정의한 용어는 아니고 Node.js 커뮤니티에서 널리 쓰는 구분입니다.

- 파일이 없다 (`ENOENT`), 권한이 없다 (`EACCES`)
- 포트가 이미 사용 중이다 (`EADDRINUSE`)
- 상대 서버가 연결을 거부하거나 응답하지 않는다 (`ECONNREFUSED`, `ETIMEDOUT`)
- 사용자 입력이 규칙에 맞지 않는다, 요청한 데이터가 DB에 없다
- 디스크나 파일 디스크립터가 부족하다 (`EMFILE`)

운영 에러는 버그가 아니므로 프로세스를 죽이지 않고 호출 경로에서 처리합니다. 재시도하거나, 기본값으로 대체하거나, 호출자에게 실패를 알립니다.

## 프로그래머 에러

프로그래머 에러(programmer error)는 코드의 결함 때문에 생기는 에러입니다. 올바른 코드라면 일어나지 않아야 하는 일입니다.

| 에러 | 전형적인 원인 |
|------|---------------|
| `TypeError` | `undefined`의 프로퍼티 읽기, 잘못된 타입의 인수 |
| `ReferenceError` | 선언하지 않은 변수 사용, 오타 |
| `RangeError` | 범위를 벗어난 인수 |
| `ERR_INVALID_ARG_TYPE` | Node.js API에 잘못된 타입 전달 |
| `AssertionError` | 절대 일어나지 않아야 할 조건 위반 |

- Node.js 문서는 `ReferenceError`가 대개 코드나 의존성의 버그를 뜻한다고 설명하고, `SyntaxError`는 `eval`·`vm`·`require`로 코드를 평가하다가 생기며 거의 항상 깨진 프로그램을 가리킨다고 설명합니다.
- 구분 기준은 에러의 클래스가 아니라 원인입니다. 사용자 입력을 `JSON.parse`하다가 난 `SyntaxError`는 운영 에러이고, 자기 코드의 객체가 `undefined`라서 난 `TypeError`는 프로그래머 에러입니다.
- 프로그래머 에러는 그 자리에서 복구하려고 하지 않습니다. 상태가 어긋나 있을 수 있기 때문입니다. 고치는 방법은 코드 수정입니다. 입력 검증(운영 에러로 처리)을 앞에 두면 잘못된 입력이 프로그래머 에러로 번지는 일을 막습니다.

## 예상 가능한 실패

예상 가능한 실패는 설계 단계에서 일어날 수 있다고 알 수 있는 실패입니다. 이름과 표현을 미리 정해 두고 호출자가 구별할 수 있게 합니다.

- 예상 가능한 실패의 목록은 호출 대상의 문서와 `code`에서 얻습니다. 파일을 읽는 함수는 `ENOENT`, `EACCES`, `EISDIR`을 낼 수 있습니다.
- 실패가 흔한 정상 흐름이면 던지지 않고 값으로 돌려줄 수 있습니다. `null`, `undefined`, `{ ok: false }` 같은 결과 객체입니다. 드문 예외 상황이면 던집니다.
- 에러를 던지는 함수는 어떤 `code`를 던지는지 문서화하거나 클래스로 노출합니다.
- 예상한 에러만 잡고 나머지는 다시 던집니다. 예상하지 못한 에러를 같이 잡으면 프로그래머 에러가 가려집니다.

```js
// ✅ 예상한 에러만 처리하고 나머지는 위로 보냄
catch (err) {
  if (err.code === 'ENOENT') return defaults
  throw err
}
```

**흔한 실수:** 모든 에러를 `catch (err)`로 받아 "파일 없음" 처리를 하는 것입니다. 권한 문제나 코드 버그도 "파일 없음"으로 보고되어 원인을 놓칩니다.

## 복구 가능한 실패

복구 가능한 실패는 그 자리에서 다른 방법으로 계속 진행할 수 있는 실패입니다. 복구 방법은 대표적으로 네 가지입니다.

| 방법 | 예 |
|------|----|
| 재시도 | 일시적 네트워크 오류 (`ECONNRESET`, `ETIMEDOUT`) |
| 대체 | 설정 파일이 없으면 기본값 사용 |
| 우회 | 캐시 실패 시 원본 DB 조회 |
| 사용자에게 알림 | 입력을 고쳐서 다시 제출하게 안내 |

```js
import { setTimeout } from 'node:timers/promises'

const RETRYABLE = new Set(['ECONNRESET', 'ETIMEDOUT'])

async function withRetry(fn, tries = 3) {
  for (let i = 1; ; i++) {
    try { return await fn() } catch (err) {
      if (i >= tries || !RETRYABLE.has(err.code)) throw err
      await setTimeout(100 * 2 ** i) // 200, 400ms 대기
    }
  }
}
```

- 재시도할 에러는 일시적인 것만 고릅니다. `EACCES`나 `ENOENT`는 다시 해도 결과가 같습니다.
- 재시도에는 횟수 상한과 대기 간격이 있어야 합니다. 없으면 장애 중인 상대 서버에 요청이 몰립니다.
- 같은 요청을 다시 보내도 결과가 한 번 보낸 것과 같은지(멱등성)를 확인한 뒤에 재시도합니다. 결제처럼 한 번만 실행되어야 하는 작업은 중복 실행될 수 있습니다.
- 복구했다면 그 사실을 경고 수준으로 기록합니다. 아무 흔적 없이 복구하면 문제가 쌓이는 줄 모릅니다.
- 복구할 수 없다고 판단되면 에러를 새로 감싸지 말고 `cause`를 이어서 위로 던집니다.

## 로깅 후 종료

프로그래머 에러나 원인 불명의 에러가 처리되지 않은 채 올라오면 상태를 신뢰할 수 없으므로 기록하고 프로세스를 종료합니다. Node.js 문서는 `'uncaughtException'`을 최후의 수단으로 부르며, 예외 이후에 정상 동작을 이어 가는 것은 안전하지 않다고 밝힙니다. 이 이벤트의 올바른 용도는 종료 전에 자원을 동기적으로 정리하는 것입니다.

```js
import { writeSync } from 'node:fs'

process.on('uncaughtException', (err, origin) => {
  writeSync(2, `FATAL ${origin}: ${err.stack}\n`)
  // 열린 파일·핸들을 동기적으로 정리
  process.exit(1)
})
```

- 리스너 안에서는 동기 작업만 합니다. 비동기 작업은 완료되기 전에 프로세스가 끝납니다.
- 로그를 `console.error`로 남기면 POSIX에서 파이프로 연결된 stderr는 비동기라서 `process.exit()`가 쓰기보다 먼저 끝낼 수 있습니다(자세히는 06편). 위 코드는 `fs.writeSync(2, ...)`로 쓴 뒤 종료합니다.
- 리스너 안에서 던진 예외는 잡히지 않고, 프로세스가 0이 아닌 종료 코드로 끝납니다.
- 종료 코드는 0이 아닌 값(보통 1)으로 둡니다. 컨테이너 오케스트레이터와 프로세스 관리자가 종료 코드로 실패를 판단하고 재시작합니다(자세히는 05편).
- 종료 뒤의 재시작은 애플리케이션 안이 아니라 별도 프로세스의 감시 도구가 맡습니다. Node.js 문서도 외부 모니터를 권장합니다.
- 처리되지 않은 Promise rejection은 기본 설정에서 예외로 바뀌어 같은 리스너에 `origin`이 `'unhandledRejection'`으로 전달됩니다(Node.js 24.15에서 확인, 자세히는 24편).

**흔한 실수:** `'uncaughtException'` 리스너에서 로그만 남기고 프로세스를 계속 두는 것입니다. 문서가 말하는 `On Error Resume Next`가 되어 상태가 어긋난 채로 다음 요청을 처리합니다.

## 에러를 삼키면 안 되는 곳

에러를 삼킨다는 것은 잡고도 기록하지도 다시 던지지도 않아서 에러가 없던 일이 되는 것입니다. 실패가 사라지면 데이터가 어긋나도 알아채지 못합니다.

```js
try { await save(order) } catch {}       // ❌ 빈 catch
promise.catch(() => {})                  // ❌ 빈 핸들러
fs.readFile(p, (err, data) => use(data)) // ❌ err 무시
```

삼키기 쉬운 자리와 대응은 다음과 같습니다.

| 자리 | 문제 | 대응 |
|------|------|------|
| 빈 `catch` | 실패가 증발 | 예상한 `code`만 처리, 나머지는 `throw` |
| `.catch(() => {})` | 같은 문제 | 처리 또는 기록 후 전파 |
| 콜백의 `err` 무시 | `data`가 `undefined` | 첫 줄에서 `err`를 검사 |
| `finally` 안의 `return`·`throw` | 앞선 에러를 덮어씀 | `finally`에서는 정리만 |
| `await` 없는 Promise | 실패가 호출자에게 안 옴 | `await` 하거나 `.catch`로 연결 (23편) |
| `forEach` 안의 `async` | 아무도 기다리지 않음 | `for...of`나 `Promise.all` (23편) |
| `'error'` 리스너 없음 | 프로세스 종료 | 리스너 등록 (21편) |

- 삼켜도 되는 경우는 의도가 분명한 때뿐입니다. 이때도 처리할 `code`를 지정하고 이유를 주석으로 남깁니다. 로깅이나 자원 정리 같은 부가 작업이 본 작업을 막지 않게 하려는 경우가 예입니다.
- `catch`에서 로그만 남기고 계속 진행하면 호출자는 성공한 줄 압니다. 호출자가 알아야 하는 실패는 다시 던집니다.
- 정리 코드가 에러를 던지는 경우는 `finally` 안에서 따로 `try...catch`로 감싸서 원래 에러가 가려지지 않게 합니다.

## 도메인 에러와 HTTP 상태 매핑

도메인 에러는 업무 규칙이 깨졌음을 나타내는 에러입니다(재고 부족, 중복 가입, 권한 없음). 웹 서버는 이를 HTTP 상태 코드로 바꿔 응답합니다. 이 변환을 한 곳에 모으면 상태 코드가 코드 곳곳에 흩어지지 않습니다. 서버 자체는 중급 과정에서 다룹니다.

| 도메인 에러 | 상태 | 뜻 |
|-------------|------|----|
| 입력 검증 실패 | 400 | 요청 자체가 잘못됨 |
| 인증 필요 | 401 | 누구인지 확인되지 않음 |
| 권한 없음 | 403 | 누구인지는 알지만 허용하지 않음 |
| 대상 없음 | 404 | 리소스를 찾을 수 없음 |
| 현재 상태와 충돌 | 409 | 중복, 동시 수정 충돌 |
| 의미상 처리 불가 | 422 | 형식은 맞지만 규칙 위반 |
| 요청 횟수 초과 | 429 | 속도 제한 |
| 서버 내부 결함 | 500 | 예상하지 못한 에러 |
| 업스트림의 잘못된 응답·시간 초과 | 502, 504 | 게이트웨이로서 상대 서버 문제 |
| 일시적 불가 | 503 | 점검·과부하 |

```js
const STATUS = {
  VALIDATION: 400,
  NOT_FOUND: 404,
  CONFLICT: 409,
}

function toHttp(err) {
  const status = err instanceof AppError
    ? (STATUS[err.code] ?? 500)
    : 500
  const code = status === 500 ? 'INTERNAL' : err.code
  return { status, body: { code } }
}
```

- 도메인 코드는 HTTP를 알지 못하게 둡니다. 에러에는 `code`만 담고, `code`를 상태로 바꾸는 표는 웹 계층에 둡니다. 같은 도메인 코드를 CLI나 배치 작업에서 재사용할 수 있습니다.
- 알 수 없는 에러(`AppError`가 아닌 것)는 500으로 응답하고, 내용은 서버 로그에만 남깁니다. `message`나 `stack`을 응답에 내보내지 않습니다. 내부 경로와 구조가 노출됩니다.
- 응답 본문에는 클라이언트가 분기할 안정적인 `code`를 담습니다.
- 4xx는 클라이언트가 고칠 수 있는 문제이고, 5xx는 서버가 책임지는 문제입니다. 운영 에러와 프로그래머 에러의 구분이 이 경계와 대체로 맞아떨어집니다.

## 에러 클래스 계층 예

에러 클래스를 계층으로 설계하면 `instanceof` 하나로 넓은 범위를, 구체 클래스로 좁은 범위를 잡을 수 있습니다.

```text
Error
└─ AppError (code, cause)
   ├─ ValidationError   (VALIDATION)
   ├─ NotFoundError     (NOT_FOUND)
   ├─ ConflictError     (CONFLICT)
   └─ UpstreamError     (UPSTREAM)
```

```js
if (err instanceof NotFoundError) return null    // 좁게
if (err instanceof AppError) log.warn(err)       // 넓게
else throw err                                   // 그 밖: 버그
```

- 루트 `AppError` 하나를 두고, 직접 던진 에러와 외부에서 온 에러를 구분합니다. 루트가 아니면 예상하지 못한 에러입니다.
- 계층은 얕게 유지합니다. 호출자가 서로 다르게 처리해야 하는 종류만 클래스로 나누고, 나머지는 `code`로 구별합니다.
- 라이브러리나 DB 드라이버의 에러는 경계에서 우리 계층의 에러로 감싸고 원본은 `cause`에 둡니다. 안쪽 코드가 특정 드라이버의 에러 형식에 의존하지 않게 하기 위해서입니다.
- 같은 패키지가 중복 설치되거나 `vm` 컨텍스트처럼 realm이 다르면 같은 이름의 클래스라도 `instanceof`가 `false`입니다. 경계를 넘는 에러는 `code`로 식별하는 편이 안전합니다.

## AggregateError

`AggregateError`는 여러 에러를 하나로 묶은 에러이고, 묶인 에러는 `errors` 배열에 있습니다. 표준 JavaScript에 속하며 Node.js 문서가 따로 정의하지 않습니다.

```js
const err = new AggregateError(
  [new Error('a'), new Error('b')],
  'multiple failures',
)
err.name          // 'AggregateError'
err.errors.length // 2
```

- `Promise.any`는 전부 reject되면 `AggregateError`로 reject합니다. `errors`는 입력 순서를 따릅니다. 메시지는 `'All promises were rejected'`입니다(자세히는 24편).
- `Promise.all`은 첫 번째 에러만 전달하고 `AggregateError`를 쓰지 않습니다. 모든 실패를 모으려면 `Promise.allSettled`로 결과를 모아 직접 만듭니다.
- 검증 에러를 한 번에 모아 돌려줄 때 씁니다. 필드 하나씩 실패하는 대신 전체 목록을 보여 줄 수 있습니다.
- `Promise.any`에서는 reject 값이 에러가 아닐 수 있어서 `errors`의 요소도 타입을 확인한 뒤 씁니다.

## Error.captureStackTrace

`Error.captureStackTrace(target[, constructorOpt])`는 `target` 객체에 `stack` 프로퍼티를 만듭니다. 읽으면 이 함수를 호출한 위치를 문자열로 돌려줍니다. 첫 줄은 `target.name: target.message`입니다.

```js
const obj = {}
Error.captureStackTrace(obj)
obj.stack // new Error().stack과 비슷한 문자열
```

두 번째 인수 `constructorOpt`에 함수를 주면, 그 함수와 그보다 위쪽 프레임이 스택에서 빠집니다. 에러를 만드는 내부 구현이 스택에 노출되지 않게 할 때 씁니다.

```js
function assertPositive(n) {
  if (n <= 0) {
    const err = new RangeError('n must be positive')
    Error.captureStackTrace(err, assertPositive)
    throw err // 첫 프레임이 assertPositive를 호출한 곳
  }
}
```

- `Error`를 상속한 커스텀 에러는 `super()` 호출만으로 스택이 만들어지고, Node.js 24.15에서 확인하면 에러 클래스의 생성자 프레임도 스택에 보이지 않습니다. 생성자에서 따로 부를 필요가 대개 없습니다.
- 스택 캡처는 비용이 있습니다. 문서의 예는 `Error.stackTraceLimit`을 0으로 낮춰 에러를 만든 뒤 복원하고 `captureStackTrace`로 한 번만 캡처해, 스택을 두 번 계산하지 않게 합니다.
- V8의 스택 트레이스 API에 의존하는 기능입니다. 다른 JavaScript 엔진에는 없을 수 있습니다.

## 핵심 정리

- 에러는 `Error`(또는 하위 클래스)를 던지고, `message`는 설명용, 분기는 `code`와 `instanceof`로 합니다. Node.js는 `message`를 어느 버전에서든 바꿀 수 있습니다.
- `stack`은 호출 경로이고 기본 10프레임까지 담으며, `cause`는 원본 에러를 연결해 체인을 남깁니다. 에러를 감싸 던질 때 `cause`를 빼지 않습니다.
- 시스템 에러는 `code`, `errno`, `syscall`, `path`를 가지며 분기는 `code`로 합니다. `errno`는 운영체제마다 다릅니다.
- 운영 에러는 환경 때문에 생겨서 처리하고, 프로그래머 에러는 코드 결함이라 고칩니다. 예상한 `code`만 잡고 나머지는 다시 던집니다.
- 처리되지 않은 예외는 동기적으로 기록하고 정리한 뒤 0이 아닌 코드로 종료하며, 재시작은 외부 감시 도구가 맡습니다. 빈 `catch`처럼 에러를 삼키는 자리를 만들지 않습니다.
- 도메인 에러는 `code`만 갖고 HTTP 상태 변환은 웹 계층에서 하며, 알 수 없는 에러는 500과 안정적인 코드로만 응답합니다.

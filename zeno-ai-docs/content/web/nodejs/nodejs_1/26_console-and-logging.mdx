## console.log

`console.log()`는 인수를 문자열로 만들어 줄바꿈과 함께 `process.stdout`에 씁니다. `node:console` 모듈의 전역 `console` 인스턴스가 제공하며 안정성 지수는 Stable입니다. `import` 없이 씁니다.

```js
console.log('count:', 5)       // count: 5
console.log('count: %d', 5)    // count: 5
console.log({ a: 1 }, [1, 2])  // { a: 1 } [ 1, 2 ]
```

- 첫 인수에 포맷 지정자가 있으면 `printf`처럼 뒤의 인수로 채웁니다. 지정자가 없으면 문자열이 아닌 인수는 `util.inspect()`로, 문자열은 그대로 공백으로 이어 붙입니다.
- 객체는 JSON이 아니라 `util.inspect()` 형식으로 출력됩니다. 깊이 2를 넘는 중첩은 `[Object]`로 줄어듭니다.

| 지정자 | 변환 |
|--------|------|
| `%s` | 문자열. 객체는 `util.inspect`(깊이 0), BigInt는 끝에 `n` |
| `%d` | `Number`로 변환 |
| `%i` | `parseInt(값, 10)` |
| `%f` | `parseFloat(값)` |
| `%j` | JSON. 순환 참조는 `'[Circular]'` |
| `%o` | `util.inspect` (숨은 속성과 프록시까지 표시) |
| `%O` | `util.inspect` (옵션 없이) |
| `%%` | 문자 `%` 하나 (인수를 소비하지 않음) |
| `%c` | 무시됨 (CSS 인수를 건너뜀) |

- 지정자에 대응하는 인수가 없으면 치환되지 않고 그대로 남습니다. `util.format('%s:%s', 'foo')`는 `'foo:%s'`입니다.
- 지정자보다 인수가 많으면 남은 인수가 뒤에 이어 붙습니다.
- `console.info()`와 `console.debug()`는 `console.log()`의 별칭입니다. 이름이 달라도 stdout에 같은 방식으로 씁니다.
- `Console` 클래스로 임의의 스트림에 쓰는 별도 인스턴스를 만들 수 있습니다(`new console.Console(out, err)`).

**흔한 실수:** 사용자 입력을 첫 인수에 넣는 것입니다. 입력에 `%s`가 들어 있고 뒤에 인수가 더 있으면 지정자로 해석되어 뒤의 인수가 치환됩니다(`console.log('50%s', 'X')`는 `50X`). 외부 값은 `console.log('input: %s', userInput)`처럼 인수로 넘깁니다.

## console.error

`console.error()`는 `console.log()`와 같은 방식으로 포맷하지만 `process.stderr`에 씁니다. 에러 객체를 넘기면 메시지와 스택(그리고 `cause`)이 출력됩니다.

```js
console.error('error #%d', 5)       // stderr: error #5
console.error(new Error('Whoops'))  // stderr: 스택 포함
```

- `Error`를 문자열에 이어 붙이지 말고(`'failed: ' + err`) 인수로 따로 넘깁니다. 문자열로 바꾸면 `name: message`만 남고 스택과 `cause`가 사라집니다.
- `console.error`는 에러를 던지거나 프로세스를 종료하지 않습니다. 출력만 합니다.

## console.warn

`console.warn()`은 `console.error()`의 별칭이라서 stderr에 씁니다. 에러는 아니지만 사람이 알아야 하는 상황에 씁니다(곧 제거될 옵션 사용, 복구했지만 재시도가 필요했던 호출).

```js
console.warn('retry %d/%d', 2, 3) // stderr: retry 2/3
```

- `console.log`/`info`/`debug`는 stdout, `console.error`/`warn`은 stderr입니다. `console.trace`와 `console.assert`의 출력도 stderr로 갑니다.
- 레벨이라는 개념은 없습니다. 메서드 이름에 따라 stream만 갈립니다. 어느 메서드든 항상 출력되고 환경에 따라 끌 수 없습니다.

| 메서드 | 스트림 |
|--------|--------|
| `log`, `info`, `debug`, `dir`, `table` | stdout |
| `time`·`timeEnd`·`timeLog`, `count`, `group` | stdout |
| `error`, `warn`, `trace`, `assert` | stderr |

## time과 timeEnd

`console.time(label)`은 `label`이라는 이름의 타이머를 시작하고, `console.timeEnd(label)`은 타이머를 멈춰 경과 시간을 stdout에 출력합니다. `label`의 기본값은 `'default'`입니다.

```js
console.time('load')
await loadUsers()
console.timeLog('load', 'users') // load: 12.5ms users
await loadOrders()
console.timeEnd('load')                 // load: 40.1ms
```

- 경과 시간은 알맞은 단위로 표시됩니다(예: 3869ms는 `3.869s`).
- `console.timeLog()`는 타이머를 멈추지 않고 중간 시각을 출력합니다. 뒤에 붙인 인수도 함께 출력합니다.
- `timeEnd`가 끝나면 그 `label`의 타이머는 사라집니다. 같은 `label`로 다시 `time`을 호출해야 합니다.
- 시작하지 않은 `label`에 `timeEnd`를 부르면 에러가 나지 않고 프로세스 경고(`No such label`)가 stderr에 출력됩니다. 같은 `label`로 `time`을 두 번 호출해도 경고입니다.
- 비동기 작업을 동시에 재려면 `label`을 서로 다르게 합니다(`'load:' + id`).
- 정밀한 측정이나 값 자체가 필요하면 `process.hrtime.bigint()`나 `performance.now()`를 씁니다(자세히는 06편).

## console.log는 디버그용

`console.log`는 개발 중 값을 확인하는 데 알맞은 도구이고, 운영 로그의 수단으로는 부족합니다. 이유는 다음과 같습니다.

| 한계 | 설명 |
|------|------|
| 레벨이 없음 | 중요도로 거를 수 없고 항상 출력됨 |
| 시간·위치 정보 없음 | 언제 어디서 났는지 직접 적어야 함 |
| 구조가 없음 | 사람이 읽는 문장이라 검색·집계가 어려움 |
| 여러 줄 출력 | 스택 같은 여러 줄이 줄 단위 수집기에서 조각남 |
| 기본 깊이 제한 | 객체가 `[Object]`로 줄어 정보가 사라짐 |
| 동기·비동기가 환경 의존 | 파이프(POSIX)에서는 비동기라 종료 직전 출력이 유실될 수 있음 |
| 쓰고 지우기 어려움 | 디버그용 출력이 코드에 남아 비밀 값까지 새어 나감 |

- Node.js 문서는 전역 `console`의 메서드가 브라우저처럼 항상 동기도, 다른 스트림처럼 항상 비동기도 아니라고 경고합니다. 스트림이 무엇에 연결됐는지(파일, 터미널, 파이프)와 운영체제에 따라 달라집니다(자세히는 06편).
- 동기 쓰기는 쓰기가 끝날 때까지 이벤트 루프를 막습니다. 수신 쪽이 읽지 않는 파이프나 느린 디스크에서는 심각한 성능 저하가 될 수 있다고 문서가 경고합니다. 운영에서 호출이 잦은 자리에 무분별한 로그를 넣지 않습니다.
- 디버그 출력은 디버거나 `--inspect`로 대체할 수 있으면 대체합니다(자세히는 29편).

## stdout과 stderr 나누기

stdout은 프로그램의 결과 데이터, stderr는 진단 메시지(로그, 경고, 에러)를 위한 스트림입니다. 두 스트림은 별개의 파이프라서 따로 리다이렉트할 수 있습니다.

```sh
node app.mjs > result.txt 2> error.log
node app.mjs | jq .      # stdout만 파이프로 넘어감
```

- CLI는 결과를 stdout, 로그와 에러를 stderr에 씁니다. 그래야 `node tool.mjs | next-tool`처럼 파이프로 연결할 때 로그가 데이터에 섞이지 않습니다(자세히는 28편).
- 장기 실행 서비스는 구분이 다릅니다. Twelve-Factor App은 앱이 로그를 파일로 관리하지 않고 이벤트 스트림으로 stdout에 곧바로 쓰고, 수집과 보관은 실행 환경에 맡기라고 설명합니다. 
- 로그 수집기가 stdout과 stderr를 어떻게 다루는지는 실행 환경마다 다릅니다. 서비스 안에서는 어느 스트림에 무엇을 쓸지 규칙을 하나로 정하고 환경의 설정과 맞춥니다.

## 로그 레벨

로그 레벨은 로그의 중요도 등급이며 최소 레벨보다 낮은 로그를 걸러 냅니다. `console`은 레벨 필터가 없으므로 로거를 두거나 직접 만듭니다.

| 레벨 | 쓰는 때 |
|------|---------|
| `fatal` | 프로세스가 계속될 수 없음 (종료 직전) |
| `error` | 요청·작업이 실패했고 사람이 봐야 함 |
| `warn` | 실패는 아니지만 이상 징후 (재시도, 곧 한계에 도달) |
| `info` | 정상적인 주요 이벤트 (시작, 종료, 요청 완료) |
| `debug` | 문제 분석용 상세 정보 |
| `trace` | 더 세밀한 흐름 추적 |

- 운영 기본은 `info`, 장애 분석 중에만 `debug`로 낮춥니다. 환경변수(`LOG_LEVEL`)로 조절하면 재배포 없이 바꿀 수 있습니다.
- 라이브러리마다 숫자가 다릅니다. pino는 `trace` 10, `debug` 20, `info` 30, `warn` 40, `error` 50, `fatal` 60이고 숫자가 클수록 심각합니다. winston의 기본(npm 레벨)은 `error` 0부터 `silly` 6까지로 숫자가 작을수록 심각합니다.
- 예상한 운영 에러(사용자 입력 오류)는 `warn`이나 `info`, 프로그래머 에러와 처리 못한 실패는 `error`로 구분합니다(자세히는 25편).
- 같은 에러를 여러 층에서 반복해 기록하지 않습니다. 처리하는 곳에서 한 번 남깁니다.

```js
const LEVELS = { debug: 10, info: 20, warn: 30, error: 40 }
const min = LEVELS[process.env.LOG_LEVEL ?? 'info']

function shouldLog(level) {
  return LEVELS[level] >= min
}
// LOG_LEVEL 미설정이면 info 이상만 통과
```

## 구조화 로그

구조화 로그는 문장 하나가 아니라 이름이 붙은 필드의 모음으로 남기는 로그입니다. 기계가 필드로 검색하고 집계할 수 있습니다.

```js
// ❌ 문장에 값을 섞음
console.log(`user ${id} paid ${amount} won`)
// ✅ 필드로 분리
log('info', 'payment done', { userId: id, amount })
```

- 메시지(`msg`)는 고정된 문장으로 두고 가변 값은 필드에 넣습니다. 고정 문장이어야 같은 이벤트를 묶어 셀 수 있습니다.
- 필드 이름을 일관되게 정합니다(`userId`를 어디는 `uid`, 어디는 `user_id`로 쓰지 않습니다).
- 공통 필드는 시각, 레벨, 메시지, 서비스 이름, 요청 아이디, 에러 정보입니다.
- 사람이 읽기 불편해진 대신 개발 중에는 포맷터(pino의 `pino-pretty`)로 보기 좋게 바꿔서 봅니다.

## JSON 로그

JSON 로그는 로그 한 건을 JSON 객체 한 개로 한 줄에 쓰는 형식(줄마다 JSON, JSON Lines)입니다. 대부분의 로그 수집 도구가 이 형식을 기본으로 파싱합니다.

```js
function log(level, msg, fields) {
  const line = JSON.stringify({
    time: new Date().toISOString(), level, msg, ...fields,
  })
  process.stdout.write(line + '\n')
}
log('info', 'user created', { userId: 7 })
// {"time":"2026-10-06T00:49:58.099Z","level":"info", ...}
```

- 한 건이 반드시 한 줄이어야 합니다. 줄바꿈이 있으면 수집기가 조각냅니다. `JSON.stringify`는 문자열 안의 줄바꿈을 `\n`으로 이스케이프하므로 한 줄이 유지됩니다.
- 시각은 ISO 8601(`toISOString()`)이나 에포크 밀리초로 남깁니다. 시간대를 포함한 하나의 형식으로 통일합니다.
- `Error`는 `JSON.stringify`에서 `{}`가 됩니다. `message`와 `stack`이 열거 불가 프로퍼티이기 때문입니다. 에러는 필드를 직접 꺼내 담습니다(`name`, `message`, `code`, `stack`, `cause`).
- 순환 참조가 있는 객체는 `JSON.stringify`가 `TypeError`를 던집니다. 로그 함수가 앱을 죽이지 않도록 방어하거나 순환을 처리하는 라이브러리를 씁니다.
- 큰 객체를 통째로 넣지 않습니다. 요청 본문 전체나 DB 결과 전체는 크기와 개인정보 문제를 함께 만듭니다.

```js
function replacer(key, value) {
  if (!(value instanceof Error)) return value
  const { name, message, code, stack, cause } = value
  return { name, message, code, stack, cause }
}
JSON.stringify({ err: new Error('x') }, replacer)
```

## 요청 아이디

요청 아이디는 요청 하나에서 생긴 모든 로그에 붙이는 고유 값입니다. 같은 값으로 검색하면 한 요청의 처음부터 끝까지를 모아 볼 수 있습니다. 동시에 많은 요청을 처리하는 서버에서는 로그가 뒤섞이므로 꼭 필요합니다.

- 아이디는 요청이 들어올 때 만들고(`crypto.randomUUID()`), 앞단(게이트웨이, 프록시)이 이미 보낸 아이디가 있으면 그것을 이어 씁니다. 헤더 이름은 조직마다 정하는 관례(`X-Request-Id` 등)입니다.
- 함수마다 아이디를 인수로 넘기면 시그니처가 지저분해집니다. 두 가지 방법이 있습니다.

| 방법 | 설명 |
|------|------|
| 자식 로거 | 아이디가 붙은 로거를 만들어 넘김 (pino·winston의 `child`) |
| `AsyncLocalStorage` | 비동기 흐름 전체에 저장소를 연결해 어디서든 읽음 |

`AsyncLocalStorage`(`node:async_hooks`, Stable)는 `run(store, callback)`으로 실행한 콜백과 그 안에서 만든 모든 비동기 작업에서 `getStore()`로 같은 저장소를 읽게 합니다.

```js
import { AsyncLocalStorage } from 'node:async_hooks'

const als = new AsyncLocalStorage()
function log(msg) {
  const requestId = als.getStore()
  console.log(JSON.stringify({ requestId, msg }))
}
async function handle() {
  log('start')
  await null
  log('end')
}
await als.run('req-1', handle) // 두 줄 모두 requestId는 req-1
```

- 저장소는 `run` 콜백 밖에서는 `undefined`입니다. 위 `log`가 `als.run` 바깥에서 불리면 `requestId`가 비어 있습니다.
- 아이디는 응답 헤더로도 돌려줍니다. 클라이언트가 문의할 때 아이디를 알려 주면 로그를 바로 찾을 수 있습니다.
- 다른 서비스를 호출할 때는 같은 아이디를 헤더로 전달해서 서비스 사이에서도 이어지게 합니다.

## 시크릿을 로그에 안 남기기

비밀번호, 토큰, API 키, 쿠키, 세션 아이디, 개인정보는 로그에 남기지 않습니다. 로그는 접근 권한이 넓고 오래 보관되며 외부 수집 서비스로 전송됩니다. 한번 남으면 지우기 어렵습니다.

- 새는 경로를 알아 둡니다.

| 경로 | 예 |
|------|----|
| 요청·응답 전체 로깅 | `Authorization`, `Cookie` 헤더, 로그인 본문의 비밀번호 |
| 설정·환경변수 출력 | `console.log(process.env)`, 설정 객체 덤프 |
| 에러 객체 | URL 쿼리의 토큰이 `message`에 들어 있음, 연결 문자열 |
| 디버그 출력 | 개발 중 넣은 `console.log(user)`가 운영에 남음 |

- 원칙은 허용 목록입니다. 남길 필드를 직접 고르는 편이 안전합니다. 차단 목록은 새 필드가 추가될 때 빠지기 쉽습니다.
- 경계에서 걸러 냅니다. 로그 함수에서 민감한 키 이름을 마스킹합니다. 아래는 `JSON.stringify`의 replacer로 키 이름에 따라 값을 가리는 예입니다.

```js
const SECRET = /pass|token|secret|authorization|cookie/i
function mask(key, value) {
  return SECRET.test(key) ? '[Redacted]' : value
}
JSON.stringify({ user: 'kim', password: 'x1' }, mask)
// {"user":"kim","password":"[Redacted]"}
```

- 키 이름 기반 마스킹은 값 안에 섞인 비밀(`message`에 들어간 토큰, URL의 쿼리 문자열)을 막지 못합니다. 에러 메시지에 외부 입력 전체를 넣지 않습니다.
- pino에는 `redact` 옵션이 있습니다. 경로(`'req.headers.authorization'`)를 지정하면 그 값을 `'[Redacted]'`(기본 censor)로 바꾸거나 `remove: true`로 키를 삭제합니다. pino 문서는 사용자 입력이 redact 경로를 정하게 하면 안 된다고 경고합니다.
- 사용자 식별 값(이메일, 전화번호)은 목적상 필요한 만큼만 남기고 가능하면 아이디로 대체합니다.
- 이미 로그에 남은 비밀은 로그에서 지우는 것으로 끝나지 않습니다. 해당 키를 폐기하고 새로 발급합니다.

## pino와 winston 비교

`console`로 직접 만드는 대신 로깅 라이브러리를 쓰면 레벨, JSON 출력, 자식 로거, 전송 대상이 이미 갖춰져 있습니다. 가장 널리 쓰는 두 가지는 pino와 winston입니다. 둘 다 npm으로 설치하는 서드파티 패키지이고 Node.js 내장이 아닙니다.

| 항목 | pino | winston |
|------|------|---------|
| 기본 출력 | JSON 한 줄 (`level`, `time`, `pid`, `hostname`, `msg`) | 포맷을 조립해 선택 (`format.json()` 등) |
| 레벨 | `trace` 10 ... `fatal` 60 (클수록 중요) | `error` 0 ... `silly` 6 (작을수록 중요) |
| 출력 대상 | transport. 별도 워커 스레드에서 처리하도록 권장 | transport (`Console`, `File` 등)를 여러 개 동시 사용 |
| 자식 로거 | `logger.child({ requestId })` | `logger.child({ requestId })` |
| 시크릿 | `redact` 옵션으로 경로 지정 | 포맷 함수로 직접 구현 |
| 개발용 출력 | `pino-pretty` | 포맷으로 구성 |
| 처리 못한 예외 | 직접 `uncaughtException`에 연결 | `exceptionHandlers` 옵션 (기본은 로깅 후 종료, `exitOnError: false`로 변경) |

- pino는 로그 처리를 메인 스레드 밖에서 하는 설계를 강조합니다. README는 이벤트 루프가 하나라서 전송·알림·가공은 별도 프로세스나 스레드에서 하라고 권합니다.
- winston은 포맷과 transport를 자유롭게 조합하는 유연함이 특징입니다. 한 로거가 여러 대상(콘솔, 파일)에 레벨을 달리해 쓸 수 있습니다.
- 어느 쪽이든 JSON을 stdout에 쓰고 수집은 실행 환경에 맡기면 코드가 단순합니다. 파일 로그를 직접 회전·보관하는 설정은 실행 환경이 하게 두는 편이 낫습니다.
- 라이브러리를 고르는 기준은 팀이 쓰는 프레임워크의 기본 로거, 필요한 전송 대상, 시크릿 처리 지원입니다. 이 문서의 수준(레벨, JSON, 요청 아이디, 시크릿)을 지키면 어느 라이브러리든 같은 결과를 얻습니다.

## console.table·dir·trace

디버깅에서 `console.log` 대신 쓸 만한 출력 메서드입니다.

### console.table

`console.table(data[, columns])`는 배열이나 객체를 표로 출력합니다. 두 번째 인수로 보일 열을 고릅니다. 표로 만들 수 없는 값은 그냥 출력합니다.

```js
const rows = [
  { id: 1, name: 'kim' },
  { id: 2, name: 'lee' },
]
console.table(rows)
// ┌─────────┬────┬───────┐
// │ (index) │ id │ name  │
// ├─────────┼────┼───────┤
// │ 0       │ 1  │ 'kim' │
// │ 1       │ 2  │ 'lee' │
// └─────────┴────┴───────┘
console.table(rows, ['name']) // name 열만
```

### console.dir

`console.dir(obj[, options])`는 `util.inspect()`로 객체를 출력하고 옵션을 직접 줍니다. 객체에 정의된 사용자 지정 `inspect` 함수는 무시합니다.

| 옵션 | 기본값 | 뜻 |
|------|--------|----|
| `depth` | `2` | 재귀 깊이. `null`이면 끝까지 |
| `showHidden` | `false` | 열거 불가·심벌 프로퍼티 표시 |
| `colors` | `false` | ANSI 색 사용 |

```js
const deep = { a: { b: { c: { d: 1 } } } }
console.log(deep)
// { a: { b: { c: [Object] } } }
console.dir(deep, { depth: null }) // 끝까지 펼침
```

### console.trace

`console.trace(message)`는 `Trace: 메시지`와 현재 위치의 스택을 stderr에 출력합니다. 에러를 던지지 않고 이 코드에 어떤 경로로 도달했는지만 확인할 때 씁니다.

```js
function save() { console.trace('who called save?') }
save()
// stderr: Trace: who called save?
//     at save (file:///app.mjs:1:...)
//     at file:///app.mjs:2:1 ...
```

그 밖에 알아 둘 메서드는 다음과 같습니다.

- `console.assert(조건, ...메시지)`: 조건이 거짓이면 `Assertion failed`로 시작하는 메시지를 stderr에 출력합니다. 실행을 멈추지 않습니다. `node:assert`와 다릅니다.
- `console.count(label)`: 같은 `label`로 호출한 횟수를 출력합니다(`default: 2`).
- `console.group(label)`과 `console.groupEnd()`: 사이의 출력을 들여씁니다.

## 핵심 정리

- `console.log`·`info`·`debug`는 stdout, `console.error`·`warn`·`trace`·`assert`는 stderr에 쓰고 레벨 필터는 없습니다. 객체는 `util.inspect` 형식이라 깊이 2를 넘으면 `[Object]`입니다.
- `console.time`/`timeEnd`는 `label`로 경과 시간을 재고, 없는 `label`은 에러가 아니라 경고입니다. `console.log`는 디버그용이고 운영 로그에는 레벨·시각·구조가 필요합니다.
- 결과 데이터는 stdout, 진단 메시지는 stderr가 CLI의 규칙이고 서비스는 stdout으로 내보내 실행 환경이 수집하게 하는 방식이 흔합니다.
- 구조화 JSON 로그는 한 건이 한 줄이며, 메시지는 고정하고 가변 값은 필드로 두며, `Error`는 필드를 직접 꺼내 담습니다.
- 요청 아이디는 자식 로거나 `AsyncLocalStorage`로 모든 로그에 붙이고, 비밀번호·토큰·쿠키는 허용 목록과 마스킹으로 로그에서 뺍니다.
- pino와 winston은 레벨·JSON·자식 로거·전송을 제공하는 서드파티 패키지이며 pino는 기본 JSON과 `redact`, winston은 포맷·transport 조합이 특징입니다.

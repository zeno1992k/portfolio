## symlink 개념

심볼릭 링크(symbolic link)는 다른 경로를 가리키는 특별한 파일입니다. 내용은 대상 경로 문자열이고, 운영체제가 경로를 해석할 때 그 문자열을 따라갑니다. 바로가기와 비슷하지만 파일 시스템 수준에서 동작합니다.

```js
import { symlink } from 'node:fs/promises'

await symlink('./mew', './mewtwo')
// mewtwo -> ./mew  (링크 mewtwo가 mew를 가리킴)
```

- 인수 순서는 `symlink(target, path)`입니다. 가리킬 대상이 먼저이고 만들 링크 경로가 나중입니다.
- 상대 경로 `target`은 현재 작업 디렉터리가 아니라 링크가 있는 디렉터리를 기준으로 해석됩니다. 만들 때 대상이 존재할 필요는 없고, 없으면 끊어진 링크가 됩니다.
- 대부분의 함수는 링크를 따라갑니다. `stat`, `readFile`, `access`, `existsSync`가 그렇습니다. 링크 자체를 다루는 함수는 `lstat`, `readlink`, `unlink`, `rename`입니다(자세히는 17편).
- `readdir`의 `Dirent`와 `lstat`의 `Stats`에서 `isSymbolicLink()`로 링크를 알아봅니다. `cp`는 기본적으로 링크를 따라가지 않고 `dereference: true`를 주면 따라갑니다.
- `unlink`로 링크를 지우면 링크만 사라지고 대상은 남습니다.
- `realpath(path)`는 링크를 모두 풀어 실제 경로를 돌려줍니다.

Windows에서는 세 가지가 다릅니다.

- `type` 인수(`'file'`, `'dir'`, `'junction'`)는 Windows에서만 쓰입니다. `null`이면 대상을 보고 `'file'`이나 `'dir'`을 고르며, 대상이 없으면 `'file'`입니다.
- 정션(junction)은 NTFS의 디렉터리 전용 링크입니다. 대상 경로가 절대 경로여야 하며 `'junction'`을 주면 자동으로 절대 경로로 바뀝니다.
- 심볼릭 링크를 만들 권한이 없으면 `EPERM`이 납니다. 관리자 권한 없는 Windows 환경에서 실행해 보니 `symlink`가 `EPERM`으로 실패했습니다.

**흔한 실수:** 상대 경로 대상을 현재 디렉터리 기준으로 생각하는 것입니다. `symlink('a.txt', 'dir/link')`의 링크는 `dir/a.txt`를 가리킵니다.

## readlink

`readlink(path)`는 링크에 저장된 대상 경로 문자열을 그대로 돌려줍니다. 링크를 따라가지 않고, 그 문자열이 가리키는 곳이 실제로 있는지도 확인하지 않습니다.

```js
import { readlink, realpath } from 'node:fs/promises'

await readlink('mewtwo') // './mew' (만들 때 준 문자열)
await realpath('mewtwo') // '/abs/path/mew' (끝까지 풀어낸 경로)
```

- 링크가 아닌 경로에 쓰면 에러입니다. 이 환경에서는 `EINVAL`이었습니다.
- `encoding: 'buffer'`를 주면 `Buffer`로 받습니다.
- Windows 정션은 만들 때 준 경로가 아니라 절대 경로로 저장되어 절대 경로가 돌아옵니다.
- 대상이 실제로 있는지는 `stat`, 절대 경로는 `realpath`로 얻습니다.

## chmod

`chmod(path, mode)`는 파일의 권한을 바꿉니다. `mode`는 숫자 비트마스크이며 8진수 리터럴(`0o644`)로 씁니다.

```js
import { chmod } from 'node:fs/promises'

await chmod('run.sh', 0o755) // 실행 가능하게
await chmod('secret.txt', 0o600) // 소유자만 읽기·쓰기
```

- 대상이 없으면 `ENOENT`로 거부됩니다.
- Windows에서는 쓰기 권한만 바꿀 수 있고 소유자·그룹·기타의 구분이 구현되어 있지 않습니다.
- `0o777`을 넘는 값은 플랫폼마다 동작이 달라서 `S_ISUID` 같은 상수는 `fs.constants`에 제공하지 않습니다.
- 새로 만들 때의 권한은 `open`·`writeFile`·`mkdir`의 `mode` 옵션으로 정합니다. `open`의 `mode`는 파일이 새로 만들어질 때만 적용됩니다.

## 권한 비트

권한은 읽기(r), 쓰기(w), 실행(x) 세 가지를 소유자·그룹·기타 세 대상에게 각각 주는 아홉 개의 비트입니다. 8진수 세 자리로 쓰며 왼쪽부터 소유자, 그룹, 기타입니다.

| 숫자 | 뜻 | 계산 |
|------|----|------|
| 7 | 읽기·쓰기·실행 | 4 + 2 + 1 |
| 6 | 읽기·쓰기 | 4 + 2 |
| 5 | 읽기·실행 | 4 + 1 |
| 4 | 읽기만 | 4 |
| 0 | 없음 | 0 |

읽기가 4, 쓰기가 2, 실행이 1입니다. 그래서 `0o765`는 소유자 rwx, 그룹 rw, 기타 rx입니다.

| 자주 쓰는 값 | 용도 |
|--------------|------|
| `0o644` | 일반 파일: 소유자 읽기·쓰기, 나머지 읽기 |
| `0o600` | 비밀 파일: 소유자만 읽기·쓰기 |
| `0o755` | 실행 파일, 디렉터리 |
| `0o444` | 읽기 전용 |

- 디렉터리에서 실행(x) 비트는 안으로 들어가 이름을 찾을 수 있는 권한(search)입니다. 목록을 읽으려면 r, 항목을 만들거나 지우려면 w와 x가 필요합니다.
- `fs.constants.S_IRUSR`(`0o400`)처럼 비트마다 이름 붙은 상수도 있습니다. `|`로 합쳐 씁니다.

현재 권한은 `stat`의 `mode`에서 읽습니다. `mode`에는 파일 종류 비트도 섞여 있으므로 `& 0o777`로 권한만 남깁니다.

```js
const info = await stat('run.sh')
const mode = info.mode
mode.toString(8)            // '100755' (앞 100은 일반 파일)
(mode & 0o777).toString(8)  // '755'
```

권한이 부족해서 실패하는 접근은 에러 코드로 나타납니다(아래 `EACCES`).

## truncate

`truncate(path, len)`는 파일을 `len` 바이트 길이로 맞춥니다. `len` 기본값은 `0`이라서 인수 없이 부르면 내용을 모두 비웁니다.

```js
import { writeFile, truncate } from 'node:fs/promises'
import { readFile } from 'node:fs/promises'

await writeFile('t.txt', 'hello world')
await truncate('t.txt', 5)
await readFile('t.txt', 'utf8') // 'hello'
await truncate('t.txt', 8)
await readFile('t.txt') // <Buffer 68 65 6c 6c 6f 00 00 00>
```

- 현재보다 짧게 맞추면 앞 `len` 바이트만 남기고 나머지를 버립니다.
- 현재보다 길게 맞추면 늘어난 부분이 널 바이트(`0x00`)로 채워집니다.
- 음수 `len`은 `0`으로 취급합니다.
- 파일을 완전히 새 내용으로 바꾸려면 `writeFile`이 truncate와 쓰기를 한 번에 합니다(자세히는 16편). 열린 파일 핸들에는 `filehandle.truncate(len)`이 있습니다.

## watch

`watch(path)`는 파일이나 디렉터리의 변경을 운영체제의 알림 기능으로 받습니다. `node:fs/promises`의 `watch`는 비동기 이터레이터를, `node:fs`의 `watch`는 `FSWatcher`를 돌려줍니다.

```js
import { watch } from 'node:fs/promises'

const ac = new AbortController()
setTimeout(() => ac.abort(), 10_000)
try {
  const events = watch('src', { signal: ac.signal })
  for await (const ev of events) {
    console.log(ev.eventType, ev.filename) // change a.js
  }
} catch (err) {
  if (err.name !== 'AbortError') throw err
}
```

콜백 형태는 다음과 같습니다.

```js
import { watch } from 'node:fs'

const watcher = watch('src', (eventType, filename) => {
  console.log(eventType, filename)
})
watcher.close() // 감시 중단
```

- `eventType`은 `'rename'`과 `'change'` 둘뿐입니다. 대부분의 플랫폼에서 이름이 생기거나 사라지면 `'rename'`이 옵니다. 파일 이동과 삭제도 `'rename'`이고, 내용 수정은 `'change'`입니다.
- `filename`은 `null`일 수 있습니다. 플랫폼이 알려 주지 않거나 알려 주지 못한 경우를 대비해 대체 처리를 둡니다.
- 감시를 멈추려면 `watcher.close()`를 부르거나 `AbortSignal`을 넘깁니다. `signal`을 주면 중단 시 이터레이터가 `AbortError`를 던집니다(자세히는 22편).
- 존재하지 않는 경로는 `ENOENT`를 던집니다. 콜백 형태의 `fs.watch`에는 Node.js 26.1에서 `throwIfNoEntry` 옵션이 추가되었습니다.
- `persistent`의 기본값 `true`는 감시 중에 프로세스가 종료되지 않게 합니다.
- `recursive: true`로 하위 디렉터리까지 감시하는 것은 지원하는 플랫폼에서만 동작합니다. Linux에서는 19.1부터 지원합니다.
- `encoding: 'buffer'`를 주면 `filename`이 `Buffer`입니다.
- 이벤트 큐가 넘칠 때의 동작은 `maxQueue`와 `overflow` 옵션으로 정합니다(`fs/promises`의 `watch`).

한 번의 저장이 여러 이벤트로 오는 일이 흔합니다. 이 환경(Windows, Node.js 24)에서 `writeFile` 한 번에 `change`가 두 번 왔고, 새 파일을 만들 때는 `rename` 뒤에 `change`가 왔습니다. 그래서 이벤트마다 곧바로 처리하지 말고 잠깐 모았다가(디바운스) 처리합니다. 감시한 디렉터리의 하위 디렉터리 변경은 `recursive` 없이는 오지 않습니다.

## watch는 플랫폼마다 다름

`fs.watch`는 운영체제가 제공하는 변경 알림에 기대고 있어서 플랫폼마다 동작이 다릅니다. 공식 문서도 100% 일관되지 않고 일부 상황에서는 쓸 수 없다고 적습니다.

| 플랫폼 | 내부 방식 |
|--------|-----------|
| Linux | inotify |
| BSD | kqueue |
| macOS | 파일은 kqueue, 디렉터리는 FSEvents |
| Windows | ReadDirectoryChangesW |
| IBM i | 지원하지 않음 |

주의할 점은 다음과 같습니다.

- Windows에서 감시 중인 디렉터리를 이동하거나 이름을 바꾸면 이벤트가 오지 않고, 지우면 `EPERM`이 보고됩니다.
- Linux와 macOS는 경로를 inode로 바꿔 감시합니다. 감시하던 경로를 지우고 같은 이름으로 다시 만들면 삭제 이벤트는 오지만, 이후에는 원래 inode를 계속 보기 때문에 새 파일의 이벤트는 오지 않습니다.
- 네트워크 파일 시스템(NFS, SMB)과 가상화 도구(Vagrant, Docker)의 호스트 공유 폴더에서는 불안정하거나 동작하지 않을 수 있습니다.
- `filename` 인수는 Linux, macOS, Windows, AIX에서만 지원하며 그 안에서도 항상 오지는 않습니다.
- `fs.watch`는 악의적인 파일 조작을 막지 못합니다. Windows에서는 디렉터리 단위로 감시하므로, 파일이 다른 파일로 대체되어도 같은 이름이면 새 파일의 변경이 보고될 수 있습니다.

대안으로 `fs.watchFile(path, listener)`가 있습니다. 주기적으로 `stat`을 읽어 비교하는 폴링 방식이라서 어디서나 쓸 수 있지만 느리고 덜 정확합니다. `interval` 기본값은 5007ms이고 `listener`는 현재와 이전 `Stats`를 받습니다. 공식 문서는 가능하면 `fs.watch`를 쓰라고 안내합니다.

### chokidar

chokidar는 `fs.watch`의 불일치를 감싼 서드파티 라이브러리입니다. 별도 설치가 필요합니다(자세히는 12편). README에 따르면 `fs.watch`가 한 번의 변경을 두 번 보고하거나 많은 변경을 `rename`으로 뭉뚱그리는 문제를 다음처럼 해결합니다.

- 모든 플랫폼에서 `add`, `change`, `unlink`, `addDir`, `unlinkDir` 이벤트를 중복 없이 제공합니다.
- 기본은 네이티브 `fs.watch`이고, 네트워크 파일 시스템에서는 폴링 방식으로 바꿀 수 있습니다.
- 에디터의 임시 파일 저장(`atomic`)과 큰 파일을 나눠 쓰는 경우(`awaitWriteFinish`)를 처리합니다.

```js
import chokidar from 'chokidar'

chokidar
  .watch('src', { ignoreInitial: true })
  .on('add', (path) => console.log('added', path))
  .on('change', (path) => console.log('changed', path))
```

개발 서버나 빌드 도구의 감시 기능은 대부분 이런 라이브러리 위에 만들어집니다. 직접 만들 때는 `fs.watch`의 한계를 알고 쓰거나 라이브러리를 씁니다.

## glob

글롭(glob)은 `*`, `**` 같은 와일드카드로 경로 집합을 표현하는 패턴입니다. `glob(pattern)`은 패턴에 맞는 경로를 비동기 이터레이터로 돌려줍니다. Node.js 22.0에서 추가되었고 24.0에서 안정(Stable)이 되었습니다.

```js
import { glob } from 'node:fs/promises'

for await (const file of glob('src/**/*.js')) {
  console.log(file) // src/a.js, src/sub/b.js
}
const all = await Array.fromAsync(glob('*.md'))
```

- 패턴은 문자열이나 문자열 배열이고, 배열이면 어느 하나에 맞으면 됩니다.
- 콜백 형태 `fs.glob`은 결과 배열을, 동기 형태 `fs.globSync`는 배열을 돌려줍니다.
- 결과의 구분자는 운영체제를 따릅니다(Windows에서는 `src\sub\b.js`). 결과 순서는 약속되지 않으므로 필요하면 정렬합니다.

옵션은 다음과 같습니다.

| 옵션 | 기본값 | 뜻 |
|------|--------|----|
| `cwd` | `process.cwd()` | 패턴의 기준 디렉터리 |
| `exclude` | 없음 | 제외할 항목을 고르는 함수, 또는 글롭 패턴의 배열 |
| `withFileTypes` | `false` | `true`이면 경로 문자열 대신 `Dirent`를 돌려줌 |
| `followSymlinks` | `false` | `**` 전개 때 디렉터리 링크를 따라감(26.1에서 추가) |
| `maxDepth` | `Infinity` | 내려갈 디렉터리 깊이. `cwd`가 깊이 0(26.9에서 추가) |

- `exclude` 배열에서는 `!foo.js` 같은 부정 패턴을 지원하지 않습니다. 제외할 패턴을 적습니다.
- 반환 목록에는 파일뿐 아니라 패턴에 맞는 디렉터리도 들어갑니다. 파일만 필요하면 패턴을 `*.js`처럼 좁히거나 `withFileTypes`로 걸러냅니다.
- 이미 기준 디렉터리 하나를 훑는다면 `readdir`의 `recursive` 옵션이 간단합니다(자세히는 17편). 확장자나 이름 패턴이 있으면 `glob`이 알맞습니다.
- 경로 하나가 패턴에 맞는지만 판단하는 `path.matchesGlob`은 15편에서 다룹니다.

## 임시 파일

임시 파일과 디렉터리는 작업 중에만 쓰고 지우는 파일입니다. 이름이 겹치면 안 되므로 무작위 문자를 붙여 새로 만듭니다. `node:fs`가 제공하는 것은 임시 디렉터리를 만드는 `mkdtemp`입니다.

```js
import { mkdtemp, writeFile, rm } from 'node:fs/promises'
import { tmpdir } from 'node:os'
import { join } from 'node:path'

const dir = await mkdtemp(join(tmpdir(), 'app-'))
// .../app-Ab12Cd (접두사 뒤에 무작위 6글자)
await writeFile(join(dir, 'work.txt'), 'data')
await rm(dir, { recursive: true, force: true }) // 정리
```

- `os.tmpdir()`는 운영체제의 임시 디렉터리 경로를 돌려줍니다. 임시 디렉터리 밖에 만들려면 `prefix`에 디렉터리를 포함해 줍니다.
- 무작위 문자는 `prefix` 뒤에 그대로 붙습니다. 그래서 `'/tmp'`처럼 구분자 없이 주면 `/tmpAb12Cd`가 만들어집니다. 안에 만들려면 `'/tmp/'`처럼 구분자로 끝내야 합니다.
- 플랫폼에 따라 무작위 문자가 6개보다 많거나 `prefix` 끝의 `X`가 바뀌므로 끝에 `X`를 쓰지 않습니다.
- 정리는 직접 해야 합니다. `mkdtemp`가 만든 디렉터리는 프로세스가 끝나도 남습니다.
- Node.js 24.4에서 추가된 `mkdtempDisposable`은 `await using`과 함께 블록을 벗어날 때 자동으로 지웁니다.

```js
import { mkdtempDisposable } from 'node:fs/promises'
import { tmpdir } from 'node:os'
import { join } from 'node:path'

{
  const prefix = join(tmpdir(), 'app-')
  await using tmp = await mkdtempDisposable(prefix)
  // tmp.path 안에서 작업
} // 블록이 끝나면 디렉터리와 내용이 삭제됨
```

- 임시 파일 하나만 필요하면 `mkdtemp`로 디렉터리를 만들고 그 안에 파일을 둡니다. 이름이 겹치지 않아 안전합니다.
- 예측 가능한 이름(`/tmp/out.txt`)은 다른 프로세스와 충돌하고 보안 문제의 원인이 됩니다.

## 원자적 교체 개념

원자적(atomic) 교체는 파일을 바꿀 때 다른 프로세스가 반쯤 쓰인 파일을 읽지 못하게 하는 방법입니다. 설정 파일이나 데이터 파일을 직접 `writeFile`로 덮어쓰면, 쓰는 도중에 읽는 쪽이 일부만 보거나 쓰다가 비정상 종료하면 파일이 망가집니다.

순서는 이렇습니다. 같은 디렉터리에 임시 파일을 완전히 쓴 다음, `rename`으로 원래 이름에 덮어씁니다.

```js
import { writeFile, rename } from 'node:fs/promises'

async function atomicWrite(path, data) {
  const tmp = `${path}.${process.pid}.tmp`
  await writeFile(tmp, data) // 임시 파일에 완전히 쓴다
  await rename(tmp, path)    // 한 번에 교체
}
await atomicWrite('config.json', '{"v":2}')
```

- 이 성질은 POSIX `rename(2)`에서 옵니다. 대상이 이미 있으면 원자적으로 교체되어, 그 사이에 새 이름을 여는 프로세스가 파일이 없는 순간을 보지 않습니다. Node.js 문서는 `rename`의 원자성을 직접 약속하지 않고 `rename(2)`를 가리킵니다.
- 임시 파일은 같은 디렉터리(같은 파일 시스템)에 둬야 합니다. 다른 파일 시스템 사이의 `rename`은 `EXDEV`로 실패하며, 이때는 원자성이 없습니다.
- 임시 이름이 겹치지 않아야 합니다. 같은 프로세스에서 같은 파일을 동시에 쓰려면 이름에 무작위 값을 더합니다.
- 도중에 실패하면 임시 파일이 남으므로 에러 때 `rm(tmp, { force: true })`로 정리합니다.
- 정전 같은 상황에서도 내용이 남아야 하면 `rename` 전에 임시 파일 핸들에 `sync()`를 불러 디스크에 내려 씁니다.
- 새 파일을 만들 때 이미 있으면 안 되는 경우는 교체가 아니라 `'wx'` 플래그로 연 `EEXIST`를 씁니다(자세히는 16편).

`copyFile`은 복사 중 에러가 나면 대상을 지우려고 시도할 뿐 원자성을 보장하지 않습니다(자세히는 17편).

## 에러 코드

파일 시스템 에러는 `Error`의 하위 객체로, 시스템 에러 속성이 붙습니다.

| 속성 | 뜻 |
|------|----|
| `code` | 문자열 에러 코드(`'ENOENT'`) |
| `syscall` | 실패한 시스템 호출 이름(`'open'`) |
| `path` | 관련 경로 |
| `dest` | `rename`·`copyFile`의 목적지 경로 |
| `errno` | 시스템 에러 번호(음수) |
| `message` | 사람이 읽는 설명 |

`errno` 숫자는 플랫폼마다 달라서 이 환경(Windows)의 `ENOENT`는 `-4058`입니다. 문자열 `code`로 분기합니다. 숫자를 이름으로 바꾸려면 `util.getSystemErrorName(errno)`를 씁니다.

### ENOENT

`ENOENT`(No such file or directory)는 경로의 어느 한 구성 요소라도 없을 때 납니다. 파일 시스템에서 가장 흔한 에러입니다.

- `readFile`, `stat`, `access`, `open`(읽기), `rename`의 원본, `watch`에서 납니다.
- `mkdir`에서는 부모 디렉터리가 없다는 뜻입니다. `recursive: true`로 해결합니다.
- 경로 오타, 상대 경로의 기준 디렉터리(`process.cwd()`) 착각, 아직 만들어지지 않은 파일이 흔한 원인입니다.
- "없으면 기본값을 쓴다" 같은 정상 흐름에서는 에러로 처리하지 않고 `code`로 분기합니다.

### EACCES

`EACCES`(Permission denied)는 파일 권한이 허용하지 않는 방식으로 접근했을 때 납니다.

- 읽기 권한이 없는 파일을 읽거나, 쓰기 권한이 없는 파일·디렉터리에 쓰거나, 실행 비트가 없는 디렉터리에 들어갈 때 납니다.
- `chmod`로 권한을 고치거나, 올바른 사용자로 실행하거나, 쓸 수 있는 위치(`os.tmpdir()` 등)를 사용합니다. 에러를 피하려고 `0o777`로 풀어 놓지 않습니다.
- 플랫폼마다 코드가 다릅니다. 이 환경(Windows)에서는 읽기 전용 파일에 쓸 때 `EACCES`가 아니라 `EPERM`이었습니다.

### EEXIST

`EEXIST`(File exists)는 없어야 하는 대상이 이미 있을 때 납니다.

- `mkdir`(`recursive` 없이), `'wx'` 플래그로 `open`·`writeFile`, `COPYFILE_EXCL`을 준 `copyFile`에서 납니다.
- 원자적으로 "없을 때만 만든다"를 구현하는 데 쓸 수 있습니다. 확인 후 생성 대신 만들기를 시도하고 `EEXIST`를 받습니다.

```js
try {
  const pid = String(process.pid)
  await writeFile('lock', pid, { flag: 'wx' })
  // 내가 만들었음
} catch (err) {
  if (err.code !== 'EEXIST') throw err
  // 이미 누가 만들었음
}
```

## 에러 코드로 분기

에러 `message`는 문장이고 플랫폼과 버전에 따라 달라질 수 있으니 `code`로 분기합니다. 처리할 코드만 다루고 나머지는 다시 던집니다.

```js
import { readFile } from 'node:fs/promises'

async function readConfig(path) {
  try {
    return JSON.parse(await readFile(path, 'utf8'))
  } catch (err) {
    if (err.code === 'ENOENT') return {} // 없으면 기본값
    throw err // 그 밖의 에러는 호출자에게
  }
}
```

- `catch`에서 모든 에러를 삼키지 않습니다. 예상한 코드만 처리하고 `throw err`로 나머지를 넘깁니다.
- `JSON.parse`의 `SyntaxError`처럼 파일 시스템이 아닌 에러에는 `code`가 없으므로 위 코드는 그대로 던집니다.
- `readFile` 하나에서 읽기 에러와 파싱 에러가 섞이니, 처리 범위가 넓으면 `try` 블록을 나눕니다.
- 에러 객체와 에러 처리 전반은 25편에서 다룹니다.

### 그 밖의 에러 코드

| 코드 | 뜻 | 예 |
|------|----|----|
| `EISDIR` | 파일을 기대했는데 디렉터리 | 디렉터리를 `readFile`, 디렉터리에 `writeFile` |
| `ENOTDIR` | 디렉터리를 기대했는데 아님 | 파일을 `readdir`, 경로 중간 구성 요소가 파일 |
| `ENOTEMPTY` | 비어 있어야 하는데 안 비었음 | 내용이 있는 디렉터리를 `rmdir` |
| `EMFILE` | 열 수 있는 파일 수 한계 도달 | 수천 개 파일을 동시에 `open` |
| `EPERM` | 높은 권한이 필요한 작업이 허용되지 않음 | 권한 없이 Windows에서 `symlink` |

- `EISDIR`과 `ENOTDIR`은 경로의 종류를 잘못 가정했다는 뜻입니다. 코드로 분기하기보다 경로를 고칩니다. 종류는 `stat`으로 확인합니다(자세히는 17편).
- `EMFILE`은 프로세스의 파일 디스크립터 한계에 닿았다는 뜻입니다. 파일 수천 개를 `Promise.all`로 한꺼번에 열면 납니다. 동시에 여는 수를 제한하고(자세히는 24편), 쉘에서 `ulimit -n`으로 한도를 올릴 수 있습니다. 열었으면 반드시 닫습니다.
- `EACCES`와 `EPERM`은 비슷하지만 `EPERM`은 관리자 권한 같은 특별한 권한이 필요한 작업에서 나는 경우를 가리킵니다. Windows에서는 `EACCES` 상황이 `EPERM`으로 나타나기도 합니다.
- `ENOTEMPTY`가 나는 `rmdir`은 `rm(path, { recursive: true })`로 바꿉니다.
- `fs.rm`은 디렉터리에 `recursive` 없이 쓰면 `ERR_FS_EISDIR` 같은 Node.js 고유 코드를 던지고, `cp`도 `ERR_FS_CP_EEXIST` 같은 고유 코드가 있습니다. 시스템 에러 코드와 같은 `code` 속성으로 확인합니다.

## 핵심 정리

- 심볼릭 링크는 대상 경로 문자열을 담은 파일이며 상대 대상은 링크 위치 기준입니다. `stat`·`readFile`은 따라가고 `lstat`·`readlink`·`unlink`는 따라가지 않습니다.
- 권한은 r=4, w=2, x=1을 소유자·그룹·기타 순으로 이은 8진수 세 자리이고, `chmod`로 바꾸고 `stat().mode & 0o777`로 읽습니다. Windows는 쓰기 비트만 바뀝니다.
- `truncate`는 파일을 지정한 바이트 길이로 줄이거나 널 바이트로 늘립니다.
- `watch`는 운영체제 알림에 기대므로 플랫폼마다 다르고 한 번의 변경이 여러 이벤트로 올 수 있습니다. 안정적인 감시가 필요하면 chokidar를 씁니다.
- `glob`은 패턴으로 경로를 찾으며 24에서 안정입니다. 임시 작업은 `mkdtemp`로 무작위 이름의 디렉터리를 만들고 직접 정리합니다.
- 파일을 안전하게 바꾸려면 같은 디렉터리의 임시 파일에 다 쓴 뒤 `rename`으로 교체합니다.
- 파일 시스템 에러는 `err.code`(`ENOENT`, `EACCES`, `EEXIST` 등)로 분기하고, 처리하지 않는 에러는 다시 던집니다.

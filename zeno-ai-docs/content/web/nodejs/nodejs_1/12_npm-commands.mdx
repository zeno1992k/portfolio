## npm init

`npm init`은 `package.json`을 만드는 명령입니다. 인수 없이 실행하면 이름·버전·설명 등을 묻는 질문을 거쳐 파일을 만듭니다. `-y`(`--yes`)를 붙이면 질문 없이 기본값으로 만듭니다.

```bash
npm init -y
```

npm 11에서 만든 기본 파일입니다.

```json
{
  "name": "app",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": { "test": "echo ... && exit 1" },
  "license": "ISC",
  "type": "commonjs"
}
```

- `name`은 현재 폴더 이름에서 가져옵니다.
- 기본 `type`이 `commonjs`이므로 ESM을 쓰려면 `"type": "module"`로 바꿉니다(09편).
- 기본값은 `--init-version`, `--init-license`, `--init-author-name` 같은 설정으로 바꿉니다.
- `npm init 이름`은 `create-이름` 패키지를 내려받아 실행하는 뜻입니다. `npm init vite`는 `npm exec create-vite`와 같습니다. 이미 전역에 `create-이름` 패키지가 있으면 그것을 씁니다.
- `npm init -w packages/foo`는 워크스페이스 하위 패키지를 만듭니다(자세히는 14편).
- `--scope`로 스코프 패키지 이름을 만듭니다.

## npm install

`npm install`(별칭 `npm i`)은 인수 없이 실행하면 `package.json`의 의존성을 `node_modules`에 설치합니다. 의존성의 종류는 11편에서 다룹니다.

```bash
npm install
```

동작 순서는 다음과 같습니다.

1. `package.json`에 적힌 의존성 범위를 읽습니다.
2. `package-lock.json`이 있고 그 버전이 `package.json`의 범위를 만족하면 lock 파일의 정확한 버전을 설치합니다.
3. lock 파일이 없거나 범위를 벗어나면 범위에 맞는 최신 버전을 찾아 설치합니다.
4. `node_modules`를 채우고 `package-lock.json`을 만들거나 갱신합니다.

- 개발용 의존성도 기본으로 함께 설치합니다. `--omit=dev`로 제외합니다.
- `--omit=optional`, `--omit=peer`로 해당 종류를 제외할 수 있습니다.
- `--ignore-scripts`는 설치 중 패키지 스크립트 실행을 건너뜁니다.
- `--legacy-peer-deps`는 피어 의존성 충돌을 무시하고 설치합니다.
- `package.json`을 고치지 않고 이미 있는 목록을 설치하므로 저장소를 받은 뒤 처음 하는 명령입니다.

## npm install 패키지

`npm install 패키지`는 패키지를 설치하고 `package.json`에 기록합니다.

```bash
npm install express        # 최신 버전, dependencies에 추가
npm install express@4.21.2 # 특정 버전
npm install express@latest # 태그로 지정
npm install -D typescript  # devDependencies에 추가
npm install -E zod         # 정확한 버전으로 기록
```

| 옵션 | 효과 |
|------|------|
| `-P`, `--save-prod` | `dependencies`에 저장(기본값) |
| `-D`, `--save-dev` | `devDependencies`에 저장 |
| `-E`, `--save-exact` | 범위 접두사 없이 정확한 버전으로 저장 |
| `--no-save` | `package.json`에 쓰지 않음 |
| `-g`, `--global` | 전역 폴더에 설치 |

- 기본으로 `^` 접두사가 붙은 범위로 저장합니다. `npm install is-odd@2.0.0`을 실행하면 `package.json`에는 `"is-odd": "^2.0.0"`이 적힙니다(로컬 확인).
- 접두사는 `save-prefix` 설정, 정확한 버전 저장은 `save-exact` 설정으로 기본값을 바꿉니다. `^`와 `~`의 의미는 13편에서 다룹니다.
- 지정자로 버전, 범위, 태그, Git 주소, 로컬 경로(`file:`)를 쓸 수 있습니다.
- 한 번에 여러 패키지를 공백으로 이어 설치합니다. `npm i a b c`.
- 설치 후 `node_modules`, `package.json`, `package-lock.json` 셋이 모두 바뀝니다.
- 전역 설치(`-g`)와 로컬 설치의 차이는 13편에서 다룹니다.

## npm uninstall

`npm uninstall 패키지`는 패키지를 `node_modules`에서 지우고 `package.json`과 `package-lock.json`에서도 뺍니다. 별칭은 `rm`, `remove`, `un`, `r`입니다.

```bash
npm uninstall is-even
# package.json과 package-lock.json에서 is-even 항목 삭제
```

- `--no-save`를 붙이면 `node_modules`에서만 지우고 `package.json`과 lock 파일은 그대로 둡니다.
- 지우는 패키지가 끌고 온 하위 의존성도 다른 곳에서 쓰지 않으면 함께 사라집니다. 로컬 확인 결과 `is-even`을 지우자 `removed 5 packages`로 하위 패키지까지 제거되었습니다.
- 전역 패키지는 `-g`로 지웁니다. 이때 `--no-save`는 무시됩니다.
- `node_modules` 폴더를 손으로 지워도 `package.json`에는 남아 있어서 `npm install`로 복구됩니다.

## npm update

`npm update`는 `package.json`의 범위 안에서 가능한 가장 새 버전으로 올립니다. 범위를 넘어서는 메이저 업그레이드는 하지 않습니다.

| `package.json`의 범위 | `npm update`가 올리는 곳 |
|----------------------|--------------------------|
| `^1.1.1` | `1.x.x` 중 최신 |
| `~1.1.1` | `1.1.x` 중 최신 |
| `^0.2.0` | 0.x 버전에서는 더 좁은 범위(`0.2.x`) |

```bash
npm update              # 전체
npm update is-odd       # 특정 패키지
npm update -g           # 전역 패키지
```

- 기본으로 `package.json`의 범위 표기는 바꾸지 않습니다. 설치된 버전과 lock 파일만 갱신합니다. 범위 표기까지 바꾸려면 `--save`를 붙입니다.
- 범위를 넘어 올리려면 `npm install 패키지@latest`를 씁니다. 로컬 확인: `is-odd`가 `^2.0.0`일 때 `npm update`는 2.0.0 그대로, `npm install is-odd@latest`는 `^3.0.1`로 바뀌었습니다.
- 무엇을 올릴 수 있는지는 `npm outdated`로 먼저 봅니다(아래 절).

**흔한 실수:** `npm update`가 최신 버전으로 올려 주지 않는다고 오해하는 것입니다. 범위가 허용하는 데까지만 올립니다.

## npm ls

`npm ls`는 설치된 패키지를 트리로 보여 줍니다. 물리적 `node_modules` 배치가 아니라 의존 관계를 기준으로 그립니다.

```text
$ npm ls --all
ex@1.0.0
+-- is-even@1.0.0
| `-- is-odd@0.1.2
|   `-- is-number@3.0.0
`-- is-odd@2.0.0
  `-- is-number@4.0.0
```

| 옵션 | 효과 |
|------|------|
| 없음 | 직접 의존성만(깊이 0) |
| `--all` | 모든 하위 의존성까지 |
| `--depth=N` | 깊이를 지정 |
| `--prod`, `--omit=dev` | 개발용 의존성 제외 |
| `--json` | JSON으로 출력 |
| `--long` | 설명 등 부가 정보 |
| 패키지 이름 | 그 패키지를 포함하는 경로만 |

- `npm ls is-odd`처럼 이름을 주면 그 패키지가 어디서 몇 버전 쓰이는지 확인할 수 있습니다. 위 예에서는 `is-odd`가 0.1.2와 2.0.0 두 버전으로 설치되어 있습니다.
- 문제가 있으면 `extraneous`(package.json에 없는데 설치됨), `missing`, `invalid`(범위에 맞지 않음)로 표시하고, 0이 아닌 종료 코드를 반환합니다.
- 선택 의존성이 설치되지 않았으면 `UNMET OPTIONAL DEPENDENCY`로 보입니다.

## npm ci

`npm ci`(clean install)는 `package-lock.json`을 그대로 따라 의존성을 설치하는 명령입니다. 자동화 환경(CI/CD, 배포)을 위한 것입니다.

```bash
npm ci
```

- `package-lock.json`(또는 `npm-shrinkwrap.json`)이 반드시 있어야 합니다.
- lock 파일과 `package.json`이 맞지 않으면 갱신하지 않고 실패합니다.
- 시작할 때 기존 `node_modules`를 먼저 지우고 새로 설치합니다.
- `package.json`과 lock 파일을 절대 쓰지 않습니다. 결과가 매번 같습니다.
- 프로젝트 전체만 설치하며 개별 패키지를 추가할 수 없습니다.
- `--omit=dev`, `--ignore-scripts` 같은 옵션을 쓸 수 있습니다.
- lock 파일을 `--legacy-peer-deps` 같은 옵션으로 만들었으면 `npm ci`에도 같은 옵션을 줍니다. `.npmrc`에 적어 두면 자동 적용됩니다.

직접 해 본 결과입니다. `package.json`에 `extra` 의존성을 추가하고 lock 파일을 그대로 두면 이렇게 실패합니다.

```text
npm error code EUSAGE
npm error `npm ci` can only install packages when your
package.json and package-lock.json are in sync.
npm error Missing: extra@1.0.0 from lock file
```

## install과 ci 차이

| 항목 | `npm install` | `npm ci` |
|------|---------------|----------|
| lock 파일 | 없어도 됨. 있으면 존중하고 필요하면 갱신 | 반드시 있어야 하고 일치해야 함 |
| 불일치할 때 | lock 파일을 고쳐서 진행 | 에러로 중단 |
| `package.json`·lock 수정 | 수정함 | 수정하지 않음 |
| `node_modules` | 있는 것을 재사용·갱신 | 먼저 삭제 후 새로 설치 |
| 패키지 추가 | `npm install 패키지` 가능 | 불가 |
| 용도 | 개발 중 의존성 추가·변경 | CI, 배포, 재현 가능한 설치 |

- 개발 중에는 `npm install`, 빌드 서버와 Docker 이미지에서는 `npm ci`를 씁니다.
- `npm ci`는 lock 파일이 정답이라고 보고 설치만 합니다. 그래서 팀원과 서버가 같은 버전 트리를 얻습니다.
- 둘 다 설치 후 `node_modules`가 채워집니다. 달라지는 것은 판단 기준입니다. install은 `package.json`과 lock을 조정하고, ci는 lock만 믿습니다.

## package-lock.json

`package-lock.json`은 npm이 설치를 끝낸 의존성 트리를 정확한 버전으로 기록한 파일입니다. npm이 `node_modules`나 `package.json`을 바꿀 때 자동으로 만들고 갱신하므로 직접 고치지 않습니다.

```json
{
  "name": "app",
  "lockfileVersion": 3,
  "packages": {
    "node_modules/is-odd": {
      "version": "2.0.0",
      "resolved": "https://registry.npmjs.org/is-odd/-/is-odd-2.0.0.tgz",
      "integrity": "sha512-..."
    }
  }
}
```

기록되는 내용입니다.

- 패키지의 정확한 버전과 내려받은 위치(`resolved`: 레지스트리 URL, Git 커밋, 로컬 경로)
- 무결성 해시(`integrity`: SHA-512 또는 SHA-1 체크섬). 내려받은 파일이 변조되지 않았는지 검증합니다.
- 의존 관계, 개발용·선택·번들 여부 표시
- `bin`, `license`, `engines`, 운영체제·CPU 제한 같은 메타데이터

`lockfileVersion`은 형식 버전입니다.

| lockfileVersion | npm 버전 |
|-----------------|----------|
| 1 | v5–v6 |
| 2 | v7–v8 (1과 호환) |
| 3 | v9 이상 (v7 이상과 호환) |

- `package.json`은 의도(범위), lock 파일은 결과(정확한 버전)입니다.
- lock 파일은 npm 레지스트리에 게시되지 않습니다. 배포되는 락이 필요하면 `npm-shrinkwrap.json`을 쓰며 둘 다 있으면 shrinkwrap이 우선합니다.
- npm v7부터 `node_modules/.package-lock.json`이라는 숨은 lock 파일이 있습니다. 매번 `node_modules`를 다시 읽지 않기 위한 캐시이며 건드리지 않습니다.
- 다른 패키지 매니저는 자기 lock 파일을 씁니다(`pnpm-lock.yaml`, `yarn.lock`). 한 프로젝트에서 매니저를 섞지 않습니다.

## lock 파일을 커밋하는 이유

`package-lock.json`은 소스 저장소에 커밋합니다. npm 문서가 권장합니다. 이유는 다음과 같습니다.

| 이유 | 설명 |
|------|------|
| 일관성 | 팀원, CI, 서버가 모두 같은 의존성 트리를 설치 |
| 재현 | 과거 시점의 의존성 상태를 `node_modules`를 커밋하지 않고도 복원 |
| 변경 가시성 | 의존성 변경이 읽기 쉬운 diff로 남음 |
| 속도 | npm이 이미 알려진 패키지의 메타데이터 조회를 건너뜀 |

- lock 파일이 없으면 `^1.2.0` 같은 범위가 설치 시점의 최신 버전으로 풀립니다. 어제 되던 빌드가 오늘 새 패키지 버전 때문에 깨질 수 있습니다.
- `npm ci`는 lock 파일을 필요로 하므로 커밋하지 않으면 쓸 수 없습니다.
- `integrity` 해시로 내려받은 파일이 기록된 것과 같은지 검증합니다.
- lock 파일은 게시되지 않으므로 라이브러리의 사용자에게는 전달되지 않습니다.
- `node_modules`는 커밋하지 않고 `.gitignore`에 넣습니다.

## node_modules

`node_modules`는 설치된 패키지 파일이 놓이는 폴더입니다. 프로젝트 루트에 만들어집니다. 파일 위치 탐색 규칙은 10편에서 다룹니다.

```text
node_modules/
  is-odd/            ← 설치된 패키지
  is-number/         ← is-odd가 쓰는 하위 의존성
  .bin/              ← 패키지가 제공하는 실행 파일 링크
  .package-lock.json ← 숨은 lock 파일
```

- npm v3부터 평평한 구조(hoisting)로 설치합니다. 하위 의존성도 가능하면 최상위 `node_modules`에 올려 중복을 줄입니다. 버전이 충돌하는 경우에만 패키지 안쪽 `node_modules`에 따로 둡니다.
- 순환 의존은 Node.js가 상위 폴더로 올라가며 `node_modules`를 찾는 규칙 덕분에 처리됩니다.
- 로컬 모드에서 실행 파일은 `node_modules/.bin`에 링크되고 npm 스크립트의 PATH에 들어갑니다.
- 전역 설치(`-g`)는 프로젝트가 아니라 prefix 폴더에 둡니다. Unix는 `{prefix}/lib/node_modules`, Windows는 `%AppData%\npm`입니다.
- 패키지 내용은 `~/.npm`(Unix) 또는 `%LocalAppData%/npm-cache`(Windows)에 캐시됩니다.
- 용량이 크고 재생성 가능한 폴더라서 저장소에 올리지 않습니다. 지우고 `npm install`이나 `npm ci`로 복구합니다.
- 상위 폴더에 설치된 패키지도 `require`가 찾을 수 있어서, `package.json`에 적지 않은 패키지가 우연히 동작하기도 합니다(10편).

## npm outdated

`npm outdated`는 새 버전이 나온 의존성을 표로 보여 줍니다. 직접 의존성만 기본이며 전이 의존성까지 보려면 `--all`입니다.

```text
$ npm outdated
Package  Current  Wanted  Latest  Location
is-odd     2.0.0   2.0.0   3.0.1  node_modules/is-odd
```

| 열 | 뜻 |
|----|----|
| Current | 지금 설치된 버전 |
| Wanted | `package.json`의 범위를 만족하는 최대 버전 |
| Latest | 레지스트리에서 `latest` 태그가 붙은 버전 |
| Location | `node_modules`에서의 위치 |
| Depended by | 이 패키지를 쓰는 쪽 |

- Wanted가 Current보다 높으면 `npm update`로 올릴 수 있습니다. Latest만 높으면 범위를 넘는 변경(대개 메이저)이라 `npm install 패키지@latest`가 필요합니다.
- 색으로도 구분합니다. 빨강은 범위 안에서 올릴 수 있음, 노랑은 범위 밖 새 버전입니다.
- 오래된 패키지가 있으면 종료 코드 1을 반환합니다. CI에서 검사로 쓸 때 주의합니다.
- `--long`은 의존성 종류와 홈페이지를 더 보여 주고, `--json`은 JSON으로 출력합니다. `-g`는 전역 패키지를 봅니다.

## npm dedupe

`npm dedupe`(별칭 `ddp`)는 이미 설치된 트리에서 중복을 줄이는 명령입니다. 여러 패키지가 호환되는 버전을 각자 안쪽에 따로 두었다면 하나를 위로 끌어올려 함께 쓰도록 재배치합니다.

```bash
npm dedupe
npm find-dupes   # 실제로 바꾸지 않고 결과만 보기(--dry-run과 같음)
```

- 새 패키지를 설치하지 않고 `package.json`의 버전 범위도 바꾸지 않습니다. 배치만 바꿉니다.
- 설치 중에 중복을 우선 줄이려면 `npm install --prefer-dedupe` 또는 `prefer-dedupe` 설정을 씁니다(기본값 false).
- 버전이 서로 호환되지 않으면 합칠 수 없습니다. 위 `ls` 예의 `is-odd` 0.1.2와 2.0.0은 범위가 달라 그대로 남습니다.
- 버전 자체를 올리는 일은 `npm update --save`가 합니다.

## lock 파일 충돌 해결

여러 브랜치에서 의존성을 바꾼 뒤 병합하면 `package-lock.json`에 충돌이 납니다. 파일이 크고 기계가 만든 것이라서 손으로 충돌 표시를 지우지 않습니다.

절차는 다음과 같습니다(npm 문서: npm 5.7.0부터).

1. `package.json`의 충돌을 먼저 직접 해결합니다. 의도(범위)가 정리되어야 합니다.
2. `npm install`을 실행합니다. 두 브랜치의 의존성을 모두 포함한 lock 파일을 npm이 다시 만들어 줍니다.
3. `node_modules`는 건드리지 않고 lock 파일만 정리하려면 `npm install --package-lock-only`를 씁니다.
4. 결과를 확인하고 커밋합니다.

```bash
# package.json 충돌을 직접 해결한 뒤
npm install --package-lock-only
git add package.json package-lock.json
```

- `--package-lock-only`는 `package-lock.json`만 쓰고 `node_modules`를 무시하는 설정(`package-lock-only`, 기본값 false)입니다.
- git 병합 시 자동으로 해결해 주는 `npm-merge-driver` 도구가 있다고 npm 문서가 안내합니다.

**흔한 실수:** lock 파일 충돌을 한쪽 브랜치 파일로 통째로 덮어쓰는 것입니다. 다른 브랜치가 추가한 의존성이 lock에서 빠져 `package.json`과 어긋나고 `npm ci`가 실패합니다.

## 핵심 정리

- `npm init -y`는 기본값으로 `package.json`을 만들고, `npm install`은 의존성을 설치하며 `npm install 패키지`는 `^` 범위로 `dependencies`에 기록한다(`-D`, `-E`로 변경).
- `npm uninstall`은 파일과 기록을 함께 지우고, `npm update`는 범위 안에서만 올리며 범위를 넘으려면 `@latest`로 설치한다.
- `npm ls`는 설치 트리를, `npm outdated`는 Current·Wanted·Latest를, `npm dedupe`는 중복 배치를 정리한다.
- `npm ci`는 lock 파일이 정답이라고 보고 `node_modules`를 지운 뒤 그대로 설치하며 불일치하면 실패한다. CI와 배포에서 쓴다.
- `package-lock.json`은 정확한 버전과 무결성 해시를 기록하는 파일이며 일관성·재현을 위해 커밋하고 `node_modules`는 커밋하지 않는다.
- lock 파일 충돌은 `package.json`을 먼저 해결하고 `npm install`(`--package-lock-only`)로 다시 만든다.

## utf8

UTF-8은 유니코드 글자를 1–4바이트로 표현하는 가변 길이 인코딩입니다. 웹과 대부분의 파일 형식이 쓰며, Node.js `Buffer`와 문자열 변환의 기본값입니다.

```js
const buf = Buffer.from('Hi 안')
buf // <Buffer 48 69 20 ec 95 88>
buf.length // 6
```

| 글자 | 바이트 수 |
|------|-----------|
| 영문자·숫자·기본 기호(ASCII) | 1 |
| 한글, 대부분의 한자·가나 | 3 |
| 대부분의 이모지 | 4 |

- 글자 수와 바이트 수가 다르므로 `Buffer`의 `length`와 문자열의 `length`는 일치하지 않습니다(자세히는 19편).
- 인코딩 이름은 `'utf8'`과 별칭 `'utf-8'`이며 대소문자를 구분하지 않습니다.
- 인코딩을 생략하면 `Buffer.from(string)`, `buf.toString()`, `buf.write()` 모두 UTF-8로 동작합니다.
- 올바르지 않은 UTF-8 바이트는 `toString`에서 `U+FFFD`(�)로 바뀝니다(아래 "잘못된 인코딩").

## base64

base64는 바이트를 영문 대소문자, 숫자, `+`, `/` 64글자와 패딩 `=`로 표현하는 텍스트 인코딩입니다. 이진 데이터를 텍스트로 보내야 하는 JSON, 이메일, 데이터 URL에 쓰입니다. 3바이트가 4글자가 되어 크기가 약 4/3배로 커집니다.

```js
const buf = Buffer.from('Hi 안')
buf.toString('base64')               // 'SGkg7JWI'
Buffer.from('SGkg7JWI', 'base64')    // 원래 바이트
Buffer.from('a').toString('base64')  // 'YQ==' (패딩)
```

- 길이가 3의 배수가 아니면 `=`로 4글자 단위를 맞춥니다.
- 문자열에서 `Buffer`를 만들 때 공백, 탭, 줄바꿈은 무시됩니다. 줄바꿈이 섞인 base64도 읽을 수 있습니다.
- 올바르지 않은 글자를 만나면 에러 없이 거기까지만 해석합니다. `'SGk$$$g'`는 `Hi `까지만 나왔습니다(Node.js 24 확인).
- 문자열에서 만들 때는 URL 안전 문자(`-`, `_`)도 받아들입니다.
- base64는 암호화가 아닙니다. 누구나 되돌릴 수 있는 표현 방식입니다.

## base64url

base64url은 URL과 파일 이름에 안전하도록 `+`를 `-`로, `/`를 `_`로 바꾼 변형입니다(RFC 4648 5절). JWT와 URL 파라미터에 쓰입니다. Node.js 15.7과 14.18에서 추가되었습니다.

```js
const bin = Buffer.from([0xfb, 0xff, 0xfe, 0x3e])
bin.toString('base64')    // '+//+Pg=='
bin.toString('base64url') // '-__-Pg' (패딩 없음)
Buffer.from('-__-Pg', 'base64url') // 원래 바이트
```

- `Buffer`를 문자열로 바꿀 때 `'base64url'`은 패딩 `=`를 붙이지 않습니다.
- 문자열을 `Buffer`로 바꿀 때는 `'base64'`와 `'base64url'`이 서로의 형태를 모두 받아들입니다. 어느 쪽 이름으로 읽어도 위 예제의 결과가 같습니다.
- 경로나 쿼리에 넣을 값에 일반 base64를 쓰면 `+`, `/`, `=`가 의미를 가지므로 `base64url`을 씁니다.

## hex

hex는 바이트 하나를 두 개의 16진수 글자(`00`–`ff`)로 표현합니다. 해시 값, 바이너리 디버깅 출력, 색상 값에 쓰입니다. 크기는 정확히 2배입니다.

```js
const buf = Buffer.from('Hi 안')
buf.toString('hex')              // '486920ec9588'
Buffer.from('48692c', 'hex')     // <Buffer 48 69 2c>
Buffer.from('1a7', 'hex')        // <Buffer 1a> (홀수 자리는 잘림)
Buffer.from('1ag123', 'hex')     // <Buffer 1a> (g에서 멈춤)
```

- 문자열이 짝수 개의 16진수 글자로만 이루어지지 않으면 에러 없이 해석 가능한 앞부분만 남습니다. 입력을 먼저 검증합니다.
- 읽을 때는 대소문자를 모두 받고, 출력은 소문자입니다.

## latin1

latin1은 ISO-8859-1입니다. 글자 하나를 1바이트로 표현하며 `U+0000`–`U+00FF`만 담을 수 있습니다. `'binary'`는 별칭이고 이름이 오해를 부르는 만큼 쓰지 않습니다.

```js
Buffer.from('é', 'latin1')       // <Buffer e9> (1바이트)
Buffer.from('é')                 // <Buffer c3 a9> (UTF-8)
Buffer.from('안', 'latin1')      // <Buffer 48> (범위 밖은 잘림)
Buffer.from([0xc3, 0xa9]).toString('latin1') // 'Ã©' (깨짐)
```

- 범위를 벗어난 글자는 하위 바이트만 남도록 잘려서 전혀 다른 글자가 됩니다. 한글이나 이모지가 들어갈 수 있는 문자열에는 쓸 수 없습니다.
- UTF-8 바이트를 latin1로 읽으면 위처럼 `Ã©`로 깨집니다. 인코딩이 서로 맞지 않을 때 나타나는 대표적인 증상입니다.
- 오래된 시스템과 이진 프로토콜의 1바이트 문자열을 다룰 때 씁니다.
- 웹 표준(WHATWG)은 `latin1`과 `ISO-8859-1`을 `windows-1252`의 별칭으로 취급합니다. 서버가 `windows-1252`로 보낸 데이터를 `latin1`로 읽으면 일부 글자가 다르게 해석될 수 있습니다.

Node.js의 나머지 인코딩은 다음과 같습니다.

| 이름 | 설명 |
|------|------|
| `'utf16le'`(별칭 `'ucs2'`) | 글자당 2 또는 4바이트. 리틀 엔디언만 지원 |
| `'ascii'` | 7비트 ASCII 전용. 레거시이며 UTF-8이나 `latin1`로 대신함 |
| `'binary'` | `latin1`의 별칭 |

## 문자열로 바꾸기

`buf.toString([encoding[, start[, end]]])`은 `Buffer`의 바이트를 지정한 인코딩으로 해석해 문자열로 만듭니다. 기본 인코딩은 `'utf8'`이고 `start`, `end`(바이트 위치, `end`는 미포함)로 일부만 바꿀 수 있습니다.

```js
const buf = Buffer.from('tést')
buf.toString()              // 'tést'
buf.toString('hex')         // '74c3a97374'
buf.toString('utf8', 0, 3)  // 'té' (앞 3바이트)
buf.toString('utf8', 0, 2)  // 't�' (é가 중간에서 잘림)
```

문자열과 `Buffer` 사이 변환은 두 방향이고 같은 인코딩 이름을 씁니다.

| 방향 | 코드 |
|------|------|
| 문자열 → `Buffer` | `Buffer.from(str, encoding)`, `buf.write(str, ..., encoding)` |
| `Buffer` → 문자열 | `buf.toString(encoding)` |

- 용어가 헷갈리는 이유는 방향에 따라 부르는 이름이 다르기 때문입니다. 문자 인코딩(utf8, latin1)은 문자열을 바이트로 바꾸는 것이 인코딩이고, 바이트 텍스트 인코딩(base64, hex)은 바이트를 문자열로 바꾸는 것이 인코딩입니다. 이 문서에서는 방향을 코드로 구분합니다.
- 인코딩 이름은 대소문자를 구분하지 않습니다(`'UTF8'`, `'uTf8'`도 같음).
- 바이트 범위를 자를 때는 글자 경계를 확인해야 합니다. 멀티바이트 글자의 중간에서 자르면 깨집니다.
- 문자열 하나의 최대 길이는 `buffer.constants.MAX_STRING_LENGTH`(UTF-16 코드 유닛 수)로 제한됩니다. 큰 파일을 통째로 문자열로 바꾸지 않습니다.
- `buffer.atob()`·`btoa()`는 레거시(Stability 3)이며 base64에는 `Buffer.from(str, 'base64')`와 `buf.toString('base64')`를 쓰라고 안내합니다.

## 숫자 읽기: readUInt8, readUInt32BE

이진 데이터(파일 헤더, 네트워크 패킷)에서 정수를 꺼낼 때는 `buf.readXxx(offset)`을 씁니다. 이름은 부호, 비트 수, 엔디언으로 구성됩니다.

```js
const buf = Buffer.from([0x12, 0x34, 0x56, 0x78, 0xff])
buf.readUInt8(0)                  // 18 (0x12)
buf.readUInt16BE(0)               // 4660 (0x1234)
buf.readUInt32BE(0).toString(16)  // '12345678'
buf.readInt8(4)                   // -1 (부호 있는 8비트)
```

| 이름 요소 | 뜻 |
|-----------|----|
| `UInt` | 부호 없는 정수 |
| `Int` | 부호 있는 정수(2의 보수) |
| `8`, `16`, `32` | 비트 수. 각각 1, 2, 4바이트 |
| `BE`, `LE` | 빅 엔디언, 리틀 엔디언(8비트에는 없음) |
| `BigInt64`, `BigUInt64` | 64비트 정수. 결과가 `bigint` |
| `Float`, `Double` | 32비트·64비트 부동소수점 |

- `offset`의 기본값은 0이고, `0 <= offset <= 길이 - 읽을 바이트 수`여야 합니다. 벗어나면 `ERR_OUT_OF_RANGE`(RangeError)입니다.
- 별칭으로 `readUint32BE`처럼 `Uint`를 소문자로 쓴 이름도 있습니다.
- 가변 길이 정수는 `readUIntBE(offset, byteLength)`로 1–6바이트를 읽습니다.
- 64비트 정수는 JavaScript 숫자(안전 정수 범위 2의 53제곱 - 1)를 넘을 수 있어서 `readBigUInt64BE`가 `bigint`를 돌려줍니다.
- 읽기는 `Buffer`를 바꾸지 않고 offset을 기억하지도 않습니다. 구조를 순서대로 읽으려면 offset을 직접 키웁니다.

```js
const hdr = Buffer.from([1, 0, 10, 0, 0, 1, 0])
const version = hdr.readUInt8(0)  // 1
const length = hdr.readUInt16BE(1) // 10
const id = hdr.readUInt32BE(3)     // 256
```

## write

`Buffer`에 쓰는 방법은 문자열과 숫자 두 가지입니다.

문자열은 `buf.write(string[, offset[, length]][, encoding])`입니다. 쓴 바이트 수를 돌려줍니다.

```js
const buf = Buffer.alloc(8)
buf.write('ab', 2)    // 2 (쓴 바이트 수)
buf // <Buffer 00 00 61 62 00 00 00 00>
Buffer.alloc(5).write('안녕') // 3 (한 글자만 들어감)
```

- 공간이 모자라면 들어가는 만큼만 쓰되, 글자의 중간까지 쓰지는 않습니다. 5바이트에 `'안녕'`(6바이트)을 쓰면 `'안'`의 3바이트만 쓰고 3을 돌려줍니다.
- 반환값을 확인하지 않으면 잘림을 알아채지 못합니다. 크기는 `Buffer.byteLength(str)`로 미리 계산할 수 있습니다.

숫자는 `writeUInt8`, `writeUInt32BE`, `writeInt16LE`처럼 읽기와 같은 이름 규칙으로 씁니다. 반환값은 쓰기 시작한 `offset`에 쓴 바이트 수를 더한 값입니다.

```js
const buf = Buffer.alloc(8)
buf.writeUInt8(255, 0)           // 1
buf.writeUInt32BE(0x12345678, 1) // 5 (다음 offset)
buf // <Buffer ff 12 34 56 78 00 00 00>
```

- 값이 형에 맞지 않으면 에러입니다. Node.js 24에서 `writeUInt8(256)`과 `writeUInt8(-1)`은 `ERR_OUT_OF_RANGE`를 던졌습니다. 문서는 범위를 벗어난 값의 동작을 정의되지 않은 것으로 설명하므로 범위를 직접 지킵니다.
- 반환값이 다음 `offset`이라서 여러 필드를 이어 쓸 수 있습니다.

```js
let offset = 0
offset = buf.writeUInt8(1, offset)
offset = buf.writeUInt16BE(300, offset)
offset = buf.writeUInt32BE(7, offset) // offset은 7
```

## 엔디언

엔디언(endianness)은 여러 바이트로 된 정수를 메모리에 놓는 순서입니다. 빅 엔디언(BE)은 큰 자리 바이트를 먼저, 리틀 엔디언(LE)은 작은 자리 바이트를 먼저 놓습니다.

`0x12345678`을 4바이트로 쓰면 다음과 같습니다.

| 방식 | 바이트 순서 |
|------|-------------|
| 빅 엔디언 | `12 34 56 78` |
| 리틀 엔디언 | `78 56 34 12` |

```js
const buf = Buffer.alloc(4)
buf.writeUInt32BE(0x12345678) // <Buffer 12 34 56 78>
buf.writeUInt32LE(0x12345678) // <Buffer 78 56 34 12>
buf.readUInt32LE(0).toString(16) // '78563412' (BE→LE)
```

- 같은 바이트를 반대 엔디언으로 읽으면 전혀 다른 값이 됩니다. 쓰는 쪽과 읽는 쪽의 엔디언이 같아야 합니다.
- 네트워크 프로토콜은 관례적으로 빅 엔디언(네트워크 바이트 순서)이고, x86과 ARM 같은 대부분의 CPU는 리틀 엔디언입니다. 파일 형식과 프로토콜 명세에서 엔디언을 확인해 `BE`나 `LE`를 고릅니다.
- 현재 호스트의 엔디언은 `os.endianness()`가 `'LE'` 또는 `'BE'`로 알려 줍니다.
- 1바이트 정수에는 엔디언이 없어서 `readUInt8`에는 `BE`, `LE`가 없습니다.
- `swap16()`, `swap32()`, `swap64()`는 `Buffer`의 바이트 순서를 제자리에서 뒤집습니다. `Buffer.from([1,2,3,4]).swap16()`은 `02 01 04 03`입니다.
- Node.js가 지원하는 UTF-16 인코딩은 리틀 엔디언뿐입니다.

## TextEncoder

`TextEncoder`는 문자열을 UTF-8 바이트로 인코딩하는 웹 표준(WHATWG) 클래스입니다. 전역에 있어서 가져오지 않고 쓰며, 브라우저에서도 같은 코드가 동작합니다. 결과는 `Buffer`가 아닌 `Uint8Array`입니다.

```js
const encoder = new TextEncoder()
const bytes = encoder.encode('안')
bytes // Uint8Array(3) [ 236, 149, 136 ]
encoder.encoding // 'utf-8' (항상 UTF-8)
```

- UTF-8만 지원합니다. 다른 인코딩이 필요하면 `Buffer.from(str, encoding)`을 씁니다.
- `encodeInto(src, dest)`는 새 배열을 만들지 않고 기존 `Uint8Array`에 씁니다. 읽은 코드 유닛 수 `read`와 쓴 바이트 수 `written`을 담은 객체를 돌려줍니다. 공간이 모자라면 글자 단위로 들어가는 만큼만 씁니다.

```js
const dest = new Uint8Array(4)
encoder.encodeInto('안녕', dest)
// { read: 1, written: 3 } (한 글자만 들어감)
```

Node.js 전용 코드에서는 `Buffer.from(str)`이 간단하고 풍부한 메서드를 줍니다. 브라우저와 공유하는 코드에서는 `TextEncoder`를 씁니다.

## TextDecoder

`TextDecoder`는 바이트를 문자열로 디코딩하는 웹 표준 클래스이고 전역에 있습니다. 입력은 `ArrayBuffer`, `DataView`, `TypedArray`(`Buffer` 포함)입니다.

```js
const decoder = new TextDecoder()
decoder.decode(new Uint8Array([72, 105])) // 'Hi'
const euckr = new TextDecoder('euc-kr')
euckr.decode(new Uint8Array([0xbe, 0xc8]))
// '안' (다른 인코딩도 읽음)
```

- 기본 인코딩은 `'utf-8'`입니다. `buf.toString()`과 달리 UTF-8 외에 `'utf-16le'`, `'euc-kr'`, `'shift_jis'`, `'windows-1252'` 등 WHATWG가 정한 많은 인코딩을 읽습니다. 지원 목록은 Node.js 빌드(ICU 설정)에 따라 다릅니다. 기본 빌드는 전체 목록을 지원합니다.
- 인코딩이 서로 다른 레거시 파일(예: EUC-KR로 저장된 텍스트)을 읽을 때 `Buffer.toString`에는 없는 이 기능이 필요합니다.
- UTF-8 앞의 BOM(바이트 순서 표시, `EF BB BF`)은 기본적으로 제거됩니다. `{ ignoreBOM: true }`를 주면 결과에 남습니다. `buf.toString()`은 BOM을 남깁니다.
- `{ fatal: true }`는 잘못된 바이트를 만나면 `U+FFFD`로 바꾸는 대신 `TypeError`(`ERR_ENCODING_INVALID_ENCODED_DATA`)를 던집니다.
- `decode(input, { stream: true })`는 끝이 잘린 멀티바이트 시퀀스를 내부에 보관했다가 다음 호출과 합칩니다(아래 "청크 경계에서 깨지는 멀티바이트").

## 잘못된 인코딩

바이트 열이 해당 인코딩의 규칙에 맞지 않을 때 일어나는 일은 방식마다 다릅니다.

| 방법 | 잘못된 UTF-8 바이트 |
|------|----------------------|
| `buf.toString()` | 각 오류를 `U+FFFD`(�)로 바꿈 |
| `new TextDecoder()` | 각 오류를 `U+FFFD`로 바꿈 |
| `new TextDecoder('utf-8', { fatal: true })` | `TypeError`를 던짐 |
| `buffer.isUtf8(buf)` | 유효한지 `true`/`false`로 알려 줌 |

```js
import { isUtf8 } from 'node:buffer'

const bad = Buffer.from([0x48, 0xff, 0x49])
bad.toString()   // 'H�I' (0xff는 UTF-8에 없는 바이트)
isUtf8(bad)      // false
Buffer.from(bad.toString()) // <Buffer 48 ef bf bd 49>
```

- 오류가 `U+FFFD`로 치환되면 원래 바이트로 되돌릴 수 없습니다. 위 마지막 줄처럼 다시 `Buffer`로 만들어도 `ff`는 `ef bf bd`가 되어 있습니다. 이진 데이터를 `toString()`으로 문자열로 바꿨다가 되돌리면 데이터가 망가집니다.
- 이진 데이터를 문자열로 다뤄야 한다면 `'base64'`나 `'hex'`를 씁니다. 어느 바이트든 손실 없이 왕복합니다.
- 잘못된 입력을 걸러내야 하는 곳(업로드된 텍스트 검증)에서는 `isUtf8()`이나 `fatal: true`를 씁니다. `isUtf8`은 Node.js 19.4와 18.14에서 추가되었고 `buffer.isAscii()`도 있습니다.
- 인코딩이 맞지 않는 증상은 두 가지로 나뉩니다. UTF-8이 아닌 바이트를 UTF-8로 읽으면 `�`가 나오고, UTF-8 바이트를 latin1로 읽으면 `Ã©` 같은 문자가 나옵니다.
- 잘못된 base64나 hex는 에러 없이 앞부분만 해석되므로 별도로 검증합니다.

## 청크 경계에서 깨지는 멀티바이트

파일이나 소켓에서 데이터는 조각(chunk)으로 도착하고, 조각의 끝은 글자 경계와 무관합니다. 멀티바이트 글자의 바이트가 두 조각에 나뉘었는데 조각마다 `toString()`하면 글자가 깨집니다.

```js
const bytes = Buffer.from('안녕') // 6바이트
const first = bytes.subarray(0, 4)  // 안 + 녕의 첫 바이트
const second = bytes.subarray(4)    // 녕의 나머지 2바이트
first.toString() + second.toString() // '안�' + '��'
```

해결 방법은 두 가지입니다.

- **조각을 모두 모아 `Buffer.concat`한 뒤 한 번에 변환**합니다. 가장 간단하지만 전체를 메모리에 올립니다.
- **`StringDecoder`로 조각마다 변환**합니다. 끝에 잘린 바이트를 내부에 보관했다가 다음 조각과 합칩니다.

```js
import { StringDecoder } from 'node:string_decoder'

const decoder = new StringDecoder('utf8')
decoder.write(first)  // '안' (녕의 첫 바이트는 보관)
decoder.write(second) // '녕'
decoder.end()         // '' (남은 바이트 없음)
```

- `write(buffer)`는 완성된 글자만 문자열로 돌려주고 불완전한 끝부분은 보관합니다.
- `end()`는 보관 중인 바이트를 문자열로 돌려줍니다. 입력이 불완전하게 끝났다면 `U+FFFD`로 치환됩니다. `end()`를 부른 뒤에는 새 입력에 다시 쓸 수 있습니다.
- 인코딩은 `'utf8'`, `'utf16le'`, `'base64'` 등을 지정합니다. base64도 3바이트 단위가 조각에 걸릴 때 같은 문제가 있어서 필요합니다.
- 웹 표준 방식으로는 `new TextDecoder().decode(chunk, { stream: true })`가 같은 일을 합니다. 마지막 조각은 `stream`을 빼고 부릅니다.
- 읽기 스트림에 `setEncoding('utf8')`을 부르면 스트림이 멀티바이트 글자를 올바르게 처리해서 문자열 조각을 줍니다(공식 문서. 스트림은 중급 과목에서 다룹니다).

**흔한 실수:** 조각을 `data += chunk`로 문자열에 이어 붙이는 것입니다. `chunk`가 `Buffer`이면 자동으로 `toString()`되므로 경계에서 글자가 깨집니다. 영문만 테스트하면 이 문제가 드러나지 않고, 한글이 들어가는 큰 데이터에서만 가끔 발생합니다.

## Buffer 풀

`Buffer` 풀은 작은 `Buffer`를 만들 때마다 메모리를 따로 할당하지 않도록 미리 잡아 둔 내부의 큰 `Buffer`(`ArrayBuffer`)입니다. 작은 `Buffer`는 이 풀에서 조각을 잘라 씁니다.

```js
const a = Buffer.from('hi')
const b = Buffer.from('yo')
a.buffer === b.buffer // true (같은 풀을 공유)
a.buffer.byteLength   // 8192 (풀 전체 크기)
Buffer.poolSize       // 8192
```

- 풀의 크기는 `Buffer.poolSize`이며 Node.js 24에서 기본값은 `8192`입니다. Node.js 26.3에서 `65536`으로 올랐습니다. 이 값은 바꿀 수 있습니다.
- 풀을 쓰는 API는 `Buffer.allocUnsafe()`, `Buffer.from(array)`, `Buffer.from(string)`, `Buffer.concat()`입니다. 크기가 풀 크기의 절반보다 작을 때만 풀에서 가져옵니다.
- `Buffer.alloc()`과 `Buffer.allocUnsafeSlow()`는 풀을 쓰지 않고 항상 독립된 메모리를 할당합니다.
- 풀 덕분에 작은 `Buffer`를 자주 만들어도 빠릅니다. 이것이 `allocUnsafe`가 빠른 이유 중 하나입니다.

풀 때문에 알아야 할 점은 다음과 같습니다.

- 작은 `Buffer`의 `buf.buffer`는 `buf`보다 훨씬 큰 `ArrayBuffer`이고 `buf.byteOffset`이 0이 아닙니다. `new Uint8Array(buf.buffer)`처럼 `byteOffset` 없이 만들면 이웃 `Buffer`의 데이터가 섞입니다(자세히는 19편).
- 풀의 조각을 오래 들고 있으면 풀 전체가 해제되지 않습니다. 오래 보관할 작은 데이터는 `Buffer.alloc()`으로 독립시키거나 `allocUnsafeSlow()`를 씁니다.
- 풀의 이전 사용 흔적은 `allocUnsafe`로 새로 받은 조각에 남을 수 있습니다(자세히는 19편).

## 핵심 정리

- 문자열과 `Buffer` 변환은 `Buffer.from(str, enc)`과 `buf.toString(enc)`이며 기본은 UTF-8입니다. 한글은 UTF-8에서 3바이트이고 latin1은 범위 밖 글자를 잘라 망가뜨립니다.
- base64와 hex는 이진 데이터를 손실 없이 텍스트로 옮깁니다. URL과 JWT에는 패딩 없는 `base64url`을 씁니다. 잘못된 입력은 에러 없이 앞부분만 해석됩니다.
- 이진 데이터의 정수는 `readUInt8`, `readUInt32BE`, `writeUInt32LE`처럼 비트 수와 엔디언을 이름에 담아 읽고 쓰며, 쓰기와 읽기의 엔디언이 같아야 합니다.
- `TextEncoder`는 UTF-8 `Uint8Array`를 만들고, `TextDecoder`는 여러 인코딩을 읽으며 BOM 처리와 `fatal`, `stream` 옵션이 있습니다.
- 잘못된 UTF-8 바이트는 `U+FFFD`로 치환되어 복구할 수 없으므로 이진 데이터를 `toString()`으로 왕복하지 않습니다.
- 조각 경계에서 멀티바이트 글자가 깨지는 문제는 `Buffer.concat` 후 변환하거나 `StringDecoder`(또는 `TextDecoder`의 `stream`)로 해결합니다.
- 작은 `Buffer`는 내부 풀을 공유하므로 `buf.buffer`를 쓸 때 `byteOffset`과 `length`를 함께 줘야 합니다.

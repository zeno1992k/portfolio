## Node.js 정의

Node.js는 브라우저 밖에서 JavaScript를 실행하는 오픈 소스·크로스 플랫폼 런타임 환경입니다. 네트워크 애플리케이션을 만들기 위한 비동기 이벤트 기반 런타임으로 설계되었습니다.

Node.js는 세 부분으로 이루어집니다.

| 구성 요소 | 역할 | 작성 언어 |
|-----------|------|-----------|
| V8 | JavaScript를 해석·실행하는 엔진 | C++ |
| libuv | 이벤트 루프, 비동기 I/O, 스레드 풀 | C |
| Node API | `fs`, `http`, `path`, `process` 같은 내장 모듈 | JavaScript와 C++ |

```js
// hello.mjs
console.log('hello') // hello
```

`node hello.mjs`로 실행하면 스크립트를 끝까지 실행하고, 대기 중인 콜백이 없으면 프로세스가 종료됩니다. 타이머나 열린 소켓처럼 콜백을 기다리는 작업이 남아 있으면 종료되지 않고 이벤트 루프에서 기다립니다.

## JavaScript 런타임

런타임은 엔진과 그 엔진이 쓸 수 있는 API, 코드를 실행하는 방식을 합친 실행 환경입니다. 엔진은 언어 자체를 실행할 뿐이고, 파일 읽기나 네트워크 같은 기능은 런타임이 제공합니다.

| 층 | 하는 일 | Node.js에서 | 브라우저에서 |
|----|---------|-------------|--------------|
| 엔진 | 문법 실행, 메모리 관리 | V8 | V8 등 |
| 런타임 API | 입출력, 타이머, 모듈 | `fs`, `http`, `process` | DOM, `fetch`, `localStorage` |
| 실행 모델 | 콜백을 실행하는 순서 | 이벤트 루프(libuv) | 이벤트 루프(브라우저) |

Node.js 버전이 곧 쓸 수 있는 ECMAScript 기능의 범위를 정합니다. 번들된 V8 버전은 `process.versions`로 확인합니다(자세히는 02편).

```js
console.log(process.versions.v8)
// 13.6.233.17-node.48 (Node.js 24.15.0 기준)
```

## ECMAScript와 Node API 구분

ECMAScript는 언어 명세(ECMA-262)입니다. 문법, `Array`, `Map`, `Promise`, `JSON`, `async`/`await`가 여기에 속합니다. Node API는 Node.js가 추가로 제공하는 기능이며 명세에 없습니다.

| 구분 | 예 | 누가 정하는가 |
|------|----|---------------|
| ECMAScript | 문법, `Array`, `Map`, `Promise`, `JSON` | ECMA-262 |
| 웹 호환 API | `fetch`, `URL`, `AbortController`, `TextEncoder`, `structuredClone`, `queueMicrotask` | 웹 표준을 Node가 구현 |
| Node 고유 API | `fs`, `path`, `process`, `Buffer`, `http` | Node.js |

```js
Promise.resolve()      // ECMAScript
setTimeout(() => {})   // 호스트가 제공하는 API
```

- 명세에는 입력과 출력에 대한 규정이 없습니다. 파일을 읽고 화면에 쓰는 기능은 전부 호스트가 제공합니다.
- `Promise` 객체는 ECMAScript가 정의하지만, 그 콜백(Job)을 언제 실행할지는 호스트가 정합니다. 명세는 이 지점을 호스트 훅(`HostEnqueuePromiseJob`)으로 남겨 둡니다. Node.js가 이것을 어떻게 처리하는지는 04편에서 다룹니다.
- `setTimeout`은 ECMAScript가 아닙니다. 브라우저와 Node.js가 각자 구현한 호스트 API입니다.

## 브라우저 JS와 Node JS 차이

문법과 내장 객체는 같고, 주변 환경이 다릅니다.

| 항목 | 브라우저 | Node.js |
|------|----------|---------|
| 전역 객체 | `window`(`globalThis`) | `globalThis`(`global`은 레거시) |
| DOM, `document` | 있음 | 없음 |
| 파일 시스템 | 샌드박스로 제한 | `fs`로 접근 |
| 프로세스 정보 | 없음 | `process` |
| 모듈 | ES Modules | CommonJS와 ES Modules |
| 최상위 `var` | 스크립트에서는 전역 프로퍼티 | 모듈 지역 변수 |
| `setTimeout` 반환값 | 숫자 | `Timeout` 객체 |

```js
typeof window     // 'undefined'
typeof document   // 'undefined'
typeof process    // 'object'
typeof fetch      // 'function'
typeof setTimeout(() => {}, 0) // 'object'
```

- Node.js는 모듈의 최상위 스코프를 전역 스코프로 보지 않습니다. CommonJS든 ES Modules든 `var x`는 그 모듈 안에서만 보입니다.
- `fetch`, `URL`, `AbortController`, `TextEncoder`, `structuredClone`, `queueMicrotask`는 Node.js에서도 전역으로 씁니다.
- `require`, `module`, `exports`, `__dirname`, `__filename`은 전역이 아니라 CommonJS 모듈에서만 있는 변수입니다. ES Modules에서는 `typeof require`가 `'undefined'`입니다(자세히는 07편, 08편).

**흔한 실수:** 브라우저용 코드를 그대로 가져오는 것입니다. `window`를 읽으면 `ReferenceError: window is not defined`가 납니다. 환경을 검사해야 하면 `typeof window`를 씁니다. `typeof`는 선언되지 않은 이름에도 에러를 내지 않습니다.

## 호스트 환경

호스트 환경(host environment)은 ECMAScript 코드를 실행하면서 입출력, 타이머, 이벤트 같은 기능을 제공하는 환경입니다. 브라우저와 Node.js가 모두 호스트입니다.

- 명세는 호스트가 정하는 부분을 host-defined로 표시합니다. 전역 객체의 구성, 모듈 로딩 방식, 작업 큐 처리 시점이 이에 해당합니다.
- 같은 코드가 호스트마다 다르게 동작할 수 있습니다. 위의 `setTimeout` 반환값이 그 예입니다.
- Node.js는 호스트로서 `process`, `Buffer`, `fs`를 제공하고, 처리할 콜백이 남아 있는 동안 이벤트 루프를 돌립니다.

코드가 어느 호스트에서 도는지 모르면 어떤 API가 있는지 알 수 없습니다. 공용 라이브러리는 전역을 읽기 전에 존재 여부를 검사합니다.

## V8

V8은 Google의 오픈 소스 JavaScript·WebAssembly 엔진이고 C++로 작성되었습니다. Chrome과 Node.js가 이 엔진을 씁니다. C++ 애플리케이션에 내장할 수 있어서, Node.js는 V8을 내장한 프로그램입니다.

- V8이 하는 일: JavaScript 파싱과 실행, 객체 메모리 관리(가비지 컬렉션). 콜스택과 힙은 03편에서 다룹니다.
- V8이 하지 않는 일: 파일·네트워크 접근, 타이머, 이벤트 루프. 이것들은 libuv와 Node API가 맡습니다.
- V8 버전이 올라가면 ECMAScript 기능 지원이 늘어납니다. 그래서 Node.js 버전이 곧 지원 문법을 정합니다.

엔진 내부의 컴파일과 최적화는 Node.js 고급 과목에서 다룹니다.

## libuv

libuv는 Node.js를 위해 만들어진 크로스 플랫폼 지원 라이브러리이고, 이벤트 기반 비동기 I/O 모델을 중심에 둡니다. 운영체제마다 다른 비동기 I/O 방식을 하나의 인터페이스로 감싸서 Node.js가 같은 코드로 어느 OS에서나 돌게 합니다.

| OS | 네트워크 I/O 감시 방식 |
|----|------------------------|
| Linux | epoll |
| macOS, BSD | kqueue |
| SunOS | event ports |
| Windows | IOCP |

- 이벤트 루프는 libuv가 제공합니다. 루프는 스레드 하나에 묶여 있습니다.
- 네트워크 I/O는 항상 루프의 스레드 하나에서, 비차단 소켓과 위의 감시 방식으로 처리됩니다.
- 파일 I/O에는 플랫폼 공통의 비동기 기본 기능이 없어서, 차단되는 파일 작업을 스레드 풀에서 실행합니다. DNS 조회 함수(`getaddrinfo`, `getnameinfo`)도 스레드 풀을 씁니다.

```js
console.log(process.versions.uv)
// 1.51.0 (Node.js 24.15.0 기준)
```

## 싱글 스레드 오해

"Node.js는 싱글 스레드다"는 절반만 맞습니다. 스레드가 하나인 것은 JavaScript 코드를 실행하는 메인 스레드입니다. Node.js 프로세스 전체가 스레드 하나로 도는 것이 아닙니다.

| 오해 | 사실 |
|------|------|
| 한 번에 요청 하나만 처리한다 | 응답을 기다리는 동안 다른 콜백을 실행하므로 대기 중인 작업이 동시에 진행된다 |
| 스레드를 전혀 쓰지 않는다 | 스레드 풀이 파일·DNS·일부 암호화 작업을 실행한다 |
| CPU 코어를 하나만 쓴다 | `child_process`, `cluster`, `worker_threads`로 여러 코어를 쓸 수 있다 |

```js
import { setTimeout as sleep } from 'node:timers/promises'

const start = performance.now()
await Promise.all([sleep(100), sleep(100), sleep(100)])
Math.round(performance.now() - start) // 약 100 (300이 아님)
```

- 대기 시간 100ms 세 개가 겹쳐서 약 100ms에 끝납니다. 대기는 스레드를 점유하지 않기 때문입니다.
- JavaScript 콜백은 한 번에 하나씩만 실행됩니다. 락과 데드락을 신경 쓸 일이 없는 이유입니다.
- `await` 사이에는 다른 콜백이 끼어들 수 있어서, 공유 상태를 읽고 쓰는 사이에 값이 바뀌는 문제는 여전히 생깁니다(자세히는 23편).

**흔한 실수:** 싱글 스레드라서 멀티코어를 못 쓴다고 단정하는 것입니다. 코어를 쓰려면 별도 프로세스나 워커 스레드를 만듭니다(Node.js 고급 과목).

## 메인 스레드와 스레드 풀

Node.js는 스레드를 두 종류로 씁니다. 메인 스레드는 JavaScript 콜백과 이벤트 루프를 실행합니다. 스레드 풀(Worker Pool)은 libuv가 관리하는 스레드 집합으로, 시간이 오래 걸리는 작업을 대신 실행합니다.

스레드 풀을 쓰는 API는 다음과 같습니다.

| 분류 | API |
|------|-----|
| 파일 시스템 | 파일 감시와 동기 API를 제외한 모든 `fs` API |
| DNS | `dns.lookup()`, `dns.lookupService()` |
| 암호화 | 비동기 `crypto.pbkdf2()`, `crypto.scrypt()`, `crypto.randomBytes()`, `crypto.randomFill()`, `crypto.generateKeyPair()` |
| 압축 | 비동기 `zlib` API |

- 기본 크기는 4개입니다. `UV_THREADPOOL_SIZE` 환경변수로 바꿉니다. libuv가 허용하는 절대 최대는 1024입니다.
- 풀은 프로세스가 시작될 때 만들어집니다. 코드 안에서 `process.env.UV_THREADPOOL_SIZE`를 바꿔도 적용되지 않을 수 있으므로 실행 전에 환경변수로 지정합니다.
- 소켓 통신은 풀이 아니라 OS의 비동기 기능을 쓰므로 풀을 점유하지 않습니다.

```js
import { pbkdf2 } from 'node:crypto'

const start = performance.now()
for (let i = 0; i < 5; i++) {
  pbkdf2('pw', 'salt', 400_000, 64, 'sha512', () => {
    console.log(i, Math.round(performance.now() - start))
  })
}
// 4개는 거의 같이 끝나고, 다섯째는 약 2배 뒤에 끝난다
```

풀의 스레드가 4개라서 다섯째 작업은 앞의 작업이 끝나기를 기다립니다. `UV_THREADPOOL_SIZE=8`로 실행하면 다섯 개가 함께 끝납니다(실행 환경에 따라 시간은 다릅니다).

`worker_threads`는 이와 별개로 JavaScript를 실행하는 스레드를 따로 만드는 모듈입니다(Stable). CPU를 많이 쓰는 JavaScript 작업에 유용하고, I/O 작업에는 내장 비동기 I/O가 더 효율적이라고 공식 문서가 안내합니다.

**흔한 실수:** 느린 `fs` 작업이나 해시 계산이 풀 4개를 모두 차지하면 다른 파일 읽기와 DNS 조회까지 줄줄이 지연된다는 점을 놓치는 것입니다.

## 이벤트 루프

이벤트 루프는 메인 스레드가 콜백을 하나씩 꺼내 실행하는 반복 구조입니다. Node.js는 시작하면 입력 스크립트를 먼저 실행하고, 그다음 이벤트 루프에 들어갑니다. 처리할 콜백이 없으면 루프를 빠져나와 종료합니다.

```js
console.log('A')
setTimeout(() => console.log('C'), 0)
console.log('B')
// A B C
```

- I/O 작업은 운영체제 커널이나 스레드 풀에 맡깁니다. 작업이 끝나면 그 콜백이 큐에 들어가고, 메인 스레드가 한가해질 때 이벤트 루프가 꺼내 실행합니다.
- 콜백 하나가 끝나야 다음 콜백이 실행됩니다. 한 콜백이 오래 걸리면 뒤의 모든 콜백이 기다립니다.
- 루프는 여러 단계로 나뉘어 있고 단계마다 큐가 있습니다(자세히는 03편). 타이머와 마이크로태스크의 실행 순서는 04편에서 다룹니다.

## 블로킹과 논블로킹

블로킹(blocking)은 비JavaScript 작업이 끝날 때까지 이벤트 루프가 JavaScript를 더 실행하지 못하고 기다리는 상태입니다. 논블로킹(non-blocking)은 작업을 맡겨 두고 이벤트 루프가 계속 JavaScript를 실행하는 방식입니다.

- 이름이 `Sync`로 끝나는 메서드가 블로킹 방식입니다.
- Node.js 표준 라이브러리의 I/O 메서드는 모두 비동기(논블로킹) 버전을 제공합니다.

```js
import { readFileSync, readFile } from 'node:fs'

const data = readFileSync('a.txt') // 여기서 멈춘다
console.log('1: 동기 읽기 끝')
readFile('a.txt', () => console.log('3: 콜백'))
console.log('2: 다음 줄')
// 1, 2, 3 순서
```

- 동기 방식은 읽는 동안 다른 요청을 전혀 처리하지 못합니다. 서버에서는 요청 처리 경로에서 `Sync` API를 쓰지 않습니다.
- 동기 방식은 CLI 스크립트나 서버 시작 시 설정 파일 읽기처럼 동시성이 필요 없는 곳에서 씁니다.
- 블로킹과 논블로킹을 섞으면 순서가 꼬여서 경쟁 상태가 생길 수 있습니다. 예를 들어 비동기로 읽기를 시작한 뒤 바로 동기로 파일을 지우면, 읽기 전에 파일이 사라질 수 있습니다.
- 순서가 필요한 비동기 작업은 콜백 안에서 이어 붙이거나 `await`로 순서를 보장합니다(자세히는 23편).

동시성(concurrency)은 한 작업을 기다리는 동안 이벤트 루프가 다른 콜백을 실행하는 능력입니다. 논블로킹 작업이 많을수록 처리량(throughput)이 늘어납니다.

## I/O 바운드

I/O 바운드는 작업 시간의 대부분을 디스크, 네트워크, 데이터베이스 응답을 기다리는 데 쓰는 작업입니다. 계산은 거의 하지 않으므로 CPU는 놀고 있습니다.

- 예: HTTP 요청 보내기, DB 쿼리, 파일 읽기, 외부 API 호출.
- 논블로킹 API로 기다림을 맡겨 두면 이벤트 루프는 그동안 다른 요청을 처리합니다. Node.js가 가장 잘 맞는 유형입니다.
- 성능은 기다림을 얼마나 겹치느냐에 달려 있습니다. 서로 독립인 작업을 `await`로 하나씩 순차 실행하면 대기 시간이 합산됩니다(자세히는 24편).

**흔한 실수:** I/O 작업인데 `Sync` API로 처리해 이벤트 루프를 세워 두는 것입니다. 기다리는 시간이 곧 전체 서버의 정지 시간이 됩니다.

## CPU 바운드

CPU 바운드는 작업 시간의 대부분을 계산에 쓰는 작업입니다. JavaScript로 계산하는 동안 메인 스레드가 점유되어 이벤트 루프가 돌지 못합니다.

```js
const start = performance.now()
setTimeout(() => console.log('timer'), 10)
while (performance.now() - start < 500) {} // 500ms 점유
// timer는 10ms가 아니라 약 500ms 뒤에 실행된다
```

- 예: 큰 JSON 파싱, 반복문 계산, 복잡한 정규식, 이미지 처리, 대량 정렬.
- 한 요청의 계산이 길어지면 같은 프로세스의 모든 요청이 그만큼 늦어집니다. 공식 문서는 클라이언트당 처리 작업이 작을 때 Node.js가 빠르다고 설명합니다.
- 대응은 두 가지입니다. 작업을 잘게 나눠 `setImmediate`로 중간에 이벤트 루프에 양보하거나, 워커 스레드나 자식 프로세스에 넘깁니다. 이벤트 루프를 막는 코드의 예는 04편, 워커는 Node.js 고급 과목에서 다룹니다.

| 항목 | I/O 바운드 | CPU 바운드 |
|------|------------|------------|
| 시간을 쓰는 곳 | 외부 응답 대기 | JavaScript 계산 |
| 메인 스레드 | 대기 중에는 비어 있음 | 계산 내내 점유됨 |
| Node.js 적합도 | 높음 | 낮음(분리 필요) |
| 대응 | 비동기 API, 병렬 실행 | 분할, 워커, 자식 프로세스 |

## Node.js가 쓰이는 곳

| 영역 | 설명 | 맞는 이유 |
|------|------|-----------|
| API 서버 | HTTP 요청을 받아 DB·외부 서비스를 호출하고 JSON으로 응답 | 대부분 I/O 바운드 |
| BFF | 프런트엔드 화면에 맞춰 여러 백엔드 응답을 모아 주는 중간 서버 | 프런트엔드와 같은 언어 |
| 개발 도구 | CLI, 빌드 도구, 린터, 번들러 | 파일 처리와 npm 생태계 |
| 서버리스 | 함수 단위로 실행되는 배포 형태. AWS Lambda가 Node.js 22·24·26 런타임을 제공 | 시작이 가볍고 이벤트 기반 |

- 브라우저용 JavaScript를 쓰던 개발자가 같은 언어로 서버 코드를 쓸 수 있다는 점이 공식 문서가 꼽는 장점입니다.
- 영상 인코딩이나 대규모 수치 계산처럼 CPU 바운드가 중심인 서비스는 Node.js 단독으로는 맞지 않아서 워커나 다른 언어와 나눠 씁니다.

## 핵심 정리

- Node.js는 V8(엔진), libuv(이벤트 루프·비동기 I/O·스레드 풀), Node API로 이루어진 JavaScript 런타임이며, 언어는 ECMAScript, 입출력과 타이머는 호스트가 제공합니다.
- 브라우저와 Node.js는 문법은 같고 전역과 API가 다릅니다. `window`와 DOM은 Node.js에 없고, `process`와 `fs`는 브라우저에 없습니다.
- JavaScript 실행 스레드만 하나입니다. 프로세스에는 스레드 풀(기본 4개)이 있고, 파일 I/O·DNS·비동기 암호화·압축이 여기서 실행됩니다.
- 이벤트 루프는 메인 스레드가 큐의 콜백을 하나씩 실행하는 반복이며, 콜백이 끝나야 다음 콜백이 실행됩니다.
- `Sync`로 끝나는 블로킹 API는 이벤트 루프를 세웁니다. 기다림이 큰 I/O 바운드에는 Node.js가 맞고, 계산이 큰 CPU 바운드는 메인 스레드를 점유하므로 분리해야 합니다.

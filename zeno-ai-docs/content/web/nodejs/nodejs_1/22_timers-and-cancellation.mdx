## setTimeout

`setTimeout(callback, delay, ...args)`는 `delay` 밀리초 뒤에 `callback`을 한 번 호출하도록 예약하고 `Timeout` 객체를 반환합니다. `require`나 `import` 없이 쓰는 전역 함수이고 안정성 지수는 Stable(2)입니다. 실행 순서의 규칙은 04편에서 다룹니다.

```js
setTimeout((a, b) => console.log(a, b), 100, 'x', 'y')
// 약 100ms 뒤: x y
```

- `delay`의 기본값은 `1`입니다. `1`보다 작거나, `NaN`이거나, `2147483647`(약 24.8일)보다 크면 `1`로 바뀝니다. 소수는 버립니다.
- 정확히 `delay`ms 뒤에 실행된다는 보장은 없습니다. 최소 대기 시간이며, 이벤트 루프가 다른 일을 하고 있으면 더 늦어집니다.
- 두 번째 인수 뒤의 값은 `callback`의 인수로 전달됩니다.
- `callback`이 함수가 아니면 `ERR_INVALID_ARG_TYPE` 코드의 `TypeError`를 던집니다(v18.0.0부터. 이전에는 `ERR_INVALID_CALLBACK`).
- 반환값이 숫자가 아니라 `Timeout` 객체인 점이 브라우저와 다릅니다. 이 객체를 `+timeout`처럼 숫자로 바꾸면 `clearTimeout`에 쓸 수 있는 번호가 됩니다(`Symbol.toPrimitive`, v14.9.0). 같은 스레드에서만 유효합니다.

**흔한 실수:** 콜백 인수가 있을 때 함수를 호출한 결과를 넘기는 것입니다.

```js
setTimeout(run(1), 100)          // ❌ run을 즉시 실행하고 결과를 넘김
setTimeout(() => run(1), 100)    // ✅
setTimeout(run, 100, 1)          // ✅
```

## clearTimeout

`clearTimeout(timeout)`은 예약된 타이머를 취소합니다. `setTimeout`이 돌려준 `Timeout` 객체, 또는 그 객체를 숫자나 문자열로 바꾼 값을 받습니다.

```js
const timer = setTimeout(() => console.log('run'), 100)
clearTimeout(timer) // 호출되지 않음
```

- 이미 실행된 타이머나 `undefined`, `null`을 넘겨도 에러가 아닙니다. 아무 일도 하지 않습니다.
- 취소한 타이머는 다시 살릴 수 없습니다. 새로 만들거나 `refresh`를 씁니다(아래 "ref, unref, refresh").
- `timeout.close()`도 취소하지만 Legacy(3)라서 `clearTimeout`을 씁니다.
- `Timeout` 객체는 `Symbol.dispose`도 가지고 있어서(v24.2.0에서 실험 단계 해제) `using` 선언으로 블록을 벗어날 때 자동 취소할 수 있습니다.

```js
{
  using timer = setTimeout(() => console.log('x'), 20)
} // 블록이 끝나면 취소되어 x는 출력되지 않음
```

## setInterval

`setInterval(callback, delay, ...args)`는 `delay`ms마다 `callback`을 반복 호출하도록 예약하고 `Timeout` 객체를 반환합니다. 인수와 `delay` 규칙은 `setTimeout`과 같습니다.

```js
let count = 0
const timer = setInterval(() => {
  console.log(++count)
  if (count === 3) clearInterval(timer) // 1 2 3 후 종료
}, 100)
```

- 멈추는 코드가 없으면 프로세스가 끝나지 않습니다. 반복 타이머는 이벤트 루프를 계속 살려 둡니다.
- 한 번에 하나만 호출되는 것이 아닙니다. 콜백이 끝나기를 기다리지 않고 시간이 되면 다음 호출이 이어집니다(아래 "인터벌이 겹치는 경우").
- 콜백 안에서 `clearInterval(timer)`를 부를 수 있습니다. 콜백 안에서 쓰려면 `const timer`가 먼저 선언되어 있어야 합니다.

## clearInterval

`clearInterval(timeout)`은 `setInterval`로 예약한 반복을 취소합니다. 받는 값과 규칙은 `clearTimeout`과 같습니다.

- 반환된 `Timeout` 객체를 변수에 보관하지 않으면 취소할 방법이 없습니다.
- 공식 문서는 `setTimeout`과 `clearTimeout`, `setInterval`과 `clearInterval`을 짝으로 정의합니다. 의도가 드러나게 짝에 맞는 이름을 씁니다.
- 반복이 필요 없어지는 경로(에러, 종료, 연결 끊김)마다 취소가 호출되는지 확인합니다. 빠뜨리면 프로세스가 종료되지 않거나 객체가 계속 살아 있습니다.

## 인터벌이 겹치는 경우

`setInterval`은 콜백이 끝났는지와 관계없이 일정 간격으로 호출을 예약합니다. 콜백이 간격보다 오래 걸리면 겹치거나 몰립니다.

- 동기 콜백이 간격보다 오래 걸리면 겹치지는 않지만, 다음 호출이 앞 호출이 끝난 직후 곧바로 이어져서 사이에 쉬는 시간이 없습니다. 이벤트 루프도 그동안 막힙니다.
- 비동기 콜백은 Promise를 기다리지 않아서 앞 작업이 끝나기 전에 다음 작업이 시작됩니다.

```js
// 작업이 35ms, 간격이 10ms
setInterval(async () => {
  running++                  // 동시에 실행 중인 작업 수
  await sleep(35)
  running--
}, 10)
// running이 3까지 올라감 (직접 실행해 확인)
```

작업이 끝난 뒤에 다음을 예약하면 겹치지 않습니다. 재귀 `setTimeout`이나 `timers/promises`의 `setInterval`을 씁니다.

```js
async function poll() {
  try {
    await fetchStatus()
  } finally {
    setTimeout(poll, 1000) // 끝난 뒤 1초 후에 다음 실행
  }
}
poll()
```

- 재귀 `setTimeout`의 간격은 작업 시간에 더해집니다. 작업이 200ms 걸리고 간격이 1000ms이면 주기는 1200ms입니다.
- 작업 사이에 쉬는 시간을 보장하려면 재귀 `setTimeout`이, 일정한 박자가 필요하면서 작업이 짧은 경우에는 `setInterval`이 맞습니다.
- 어느 쪽이든 실패 시 다음 예약을 하는 `finally`나 에러 처리를 빠뜨리지 않아야 합니다.

## setImmediate

`setImmediate(callback, ...args)`는 현재 이벤트 루프 단계의 I/O 콜백 처리가 끝난 뒤 `callback`을 호출하도록 예약하고 `Immediate` 객체를 반환합니다(check 단계, 자세히는 03편).

```js
setImmediate((msg) => console.log(msg), 'later')
console.log('now')
// now
// later
```

- 여러 개를 예약하면 만든 순서대로 호출됩니다. 이벤트 루프 한 바퀴에 큐 전체가 처리됩니다.
- 실행 중인 콜백 안에서 새로 예약한 `setImmediate`는 현재 바퀴가 아니라 다음 바퀴에서 실행됩니다.
- 긴 작업을 쪼개서 사이사이에 다른 이벤트가 처리되게 할 때 씁니다.
- `setTimeout(fn, 0)`과의 순서는 호출 위치에 따라 달라집니다(자세히는 04편).
- `callback`이 함수가 아니면 `TypeError`입니다.

## clearImmediate

`clearImmediate(immediate)`는 `setImmediate`가 돌려준 `Immediate` 객체를 받아 예약을 취소합니다.

```js
const im = setImmediate(() => console.log('x'))
clearImmediate(im) // 호출되지 않음
```

- `Immediate`도 `Symbol.dispose`를 가져서 `using`과 함께 쓸 수 있습니다(v24.2.0에서 실험 단계 해제).
- `Immediate` 객체에도 `ref()`, `unref()`, `hasRef()`가 있습니다.

## timers/promises

`node:timers/promises`는 타이머를 Promise로 쓰는 함수 모음입니다(v15.0.0, v16.0.0에서 실험 단계 해제). `async` 함수 안에서 `await`와 함께 쓰는 것이 목적입니다.

```js
import {
  setTimeout as sleep,
  setImmediate as yieldNow,
  setInterval as every,
} from 'node:timers/promises'
```

| 함수 | 반환 | 이행 값 |
|------|------|---------|
| `setTimeout(delay, value, options)` | Promise | `value` |
| `setImmediate(value, options)` | Promise | `value` |
| `setInterval(delay, value, options)` | 비동기 이터레이터 | 반복마다 `value` |

- 모두 `options`에 `signal`(취소)과 `ref`(이벤트 루프를 붙잡을지, 기본 `true`)를 받습니다.
- 전역 `setTimeout`과 같은 이름이므로 위처럼 `as`로 별칭을 붙이거나 `timersPromises.setTimeout`으로 씁니다. 이름이 겹치면 인수 순서가 다른 함수를 잘못 부르게 됩니다.
- `scheduler.wait(delay, options)`는 `setTimeout(delay, undefined, options)`와 같고 `scheduler.yield()`는 인수 없는 `setImmediate()`와 같습니다. 둘 다 Experimental(1)이라 일반 코드에서는 쓰지 않습니다.

## setTimeout promise

`timers/promises`의 `setTimeout(delay, value, options)`는 `delay`ms 뒤에 `value`로 이행하는 Promise를 반환합니다. 일정 시간 기다리는 `sleep`으로 쓰는 것이 가장 흔합니다.

```js
import { setTimeout as sleep } from 'node:timers/promises'

console.log('a')
const v = await sleep(100, 'done')
console.log(v) // done (100ms 뒤)
```

- 값 없이 `await sleep(1000)`만 써도 됩니다. 이행 값은 `undefined`입니다.
- 거부되는 경우는 취소할 때뿐입니다. `signal`이 중단되면 `AbortError`로 거부됩니다.

```js
const ac = new AbortController()
const p = sleep(1000, 'v', { signal: ac.signal })
ac.abort()
try { await p } catch (e) { console.log(e.name, e.code) }
// AbortError ABORT_ERR
```

- 이미 중단된 신호를 주면 기다리지 않고 바로 거부됩니다.
- `abort(reason)`에 이유를 넘기면 에러의 `cause` 프로퍼티에 담깁니다. 이유 없이 `abort()`하면 `cause`는 기본 `DOMException`(`AbortError`)입니다.
- `await sleep(...)`은 이벤트 루프를 막지 않습니다. `while` 반복으로 시간을 기다리는 방식(바쁜 대기)과 다릅니다.

## AbortController

`AbortController`는 비동기 작업에 취소를 알리는 클래스입니다. 웹 표준 API를 따르며 v15.0.0부터 전역 클래스이고 v15.4.0부터 실험 단계가 아닙니다. 두 가지로 이루어집니다.

- `controller.signal`: 취소 여부를 알려 주는 `AbortSignal`. 작업 쪽에 넘깁니다.
- `controller.abort([reason])`: 취소를 요청하는 메서드. 호출하는 쪽이 가집니다.

```js
const ac = new AbortController()
ac.signal.addEventListener('abort', () => {
  console.log('aborted')
}, { once: true })
ac.abort() // aborted
console.log(ac.signal.aborted) // true
```

- 역할 분리가 핵심입니다. 취소를 요청하는 쪽은 `controller`를, 취소에 반응하는 쪽은 `signal`만 갖습니다. 작업 쪽은 스스로 취소를 일으킬 수 없습니다.
- 한 `AbortController`는 한 번만 취소됩니다. `abort()`를 여러 번 호출해도 `'abort'` 이벤트는 한 번만 발생합니다.
- 한 번 취소된 컨트롤러는 되돌릴 수 없습니다. 다시 쓰려면 새로 만듭니다.
- 하나의 `signal`을 여러 작업에 넘기면 `abort()` 한 번으로 모두 취소됩니다.
- `abort(reason)`의 `reason`은 값이면 무엇이든 되고 `signal.reason`으로 읽습니다.

## AbortSignal

`AbortSignal`은 취소가 요청되었는지 알려 주는 객체로 `EventTarget`을 상속합니다. 작업 쪽이 받는 것은 항상 이 객체입니다.

| 멤버 | 설명 |
|------|------|
| `signal.aborted` | 취소되었으면 `true` |
| `signal.reason` | 취소 이유. `abort()`에 이유를 안 주면 `AbortError` 이름의 `DOMException` |
| `signal.throwIfAborted()` | 취소되었으면 `signal.reason`을 던짐 |
| `'abort'` 이벤트 | 취소되는 순간 한 번 발생 |
| `signal.onabort` | `'abort'` 이벤트 핸들러 프로퍼티 |
| `AbortSignal.abort(reason)` | 이미 취소된 신호를 만듦 |

```js
const ac = new AbortController()
ac.abort(new Error('stop'))
console.log(ac.signal.reason.message) // stop

function work(signal) {
  signal.throwIfAborted() // 이미 취소였다면 여기서 던짐
}
```

- 이벤트는 취소되는 순간에만 한 번 발생하므로, 이미 취소된 신호에 나중에 리스너를 달면 호출되지 않습니다. 리스너를 달기 전에 `signal.aborted`를 먼저 확인합니다(공식 문서의 권장).
- `'abort'` 리스너는 `{ once: true }`로 등록합니다. 신호가 오래 살아 있는데 리스너를 해제하지 않으면 메모리 누수가 됩니다(공식 문서의 경고). EventEmitter 방식이라면 `once()`를 씁니다.
- `AbortSignal.abort()`는 테스트나 "이미 취소된 상태에서 시작" 경로를 만들 때 쓰는 정적 메서드입니다.
- 이벤트 리스너 해제를 `AbortSignal`로 묶는 방법은 21편에서 다룹니다.

## AbortSignal.timeout

`AbortSignal.timeout(delay)`는 `delay`ms 뒤에 자동으로 취소되는 신호를 반환합니다(v17.3.0). 컨트롤러가 필요 없어서 제한 시간을 거는 가장 짧은 방법입니다.

```js
const signal = AbortSignal.timeout(2000)
// 2초 뒤 signal.aborted가 true, signal.reason은 TimeoutError

await fetch('https://example.com', { signal })
```

- 시간 초과로 취소되면 `signal.reason`은 이름이 `TimeoutError`인 `DOMException`입니다. 직접 `abort()`했을 때의 `AbortError`와 구분됩니다.
- 신호를 받은 API는 보통 `reason`을 그대로 던지거나 `AbortError`로 거부합니다. API에 따라 다르므로 에러 이름을 확인해서 분기합니다.

```js
const signal = AbortSignal.timeout(100)
try {
  await sleep(5000, null, { signal })
} catch (err) {
  if (err.name === 'TimeoutError') console.log('시간 초과')
  else if (err.name === 'AbortError') console.log('취소됨')
  else throw err
}
```

- 신호는 만든 시점부터 시간이 흐릅니다. 미리 만들어 두고 나중에 쓰면 그만큼 시간이 줄어 있습니다. 쓰는 자리에서 바로 만듭니다.
- `AbortSignal.timeout`은 신호만 취소 상태로 바꿉니다. 작업을 강제로 멈추지는 않으므로 작업이 신호를 확인하지 않으면 계속 실행됩니다(아래 "취소 가능한 비동기 작업").

## AbortSignal.any

`AbortSignal.any(signals)`는 주어진 신호 중 하나라도 취소되면 취소되는 새 신호를 반환합니다(v20.3.0). 사용자 취소와 시간 제한처럼 취소 조건이 여럿일 때 합칩니다.

```js
const user = new AbortController()
const signal = AbortSignal.any([
  user.signal,
  AbortSignal.timeout(5000),
])
// user.abort() 또는 5초 경과 중 먼저 일어난 쪽으로 취소
```

- 새 신호의 `reason`은 실제로 취소를 일으킨 신호의 이유입니다. 어느 쪽 때문인지 `signal.reason.name`으로 구분합니다.
- 합친 신호를 작업에 넘기면, 작업은 신호가 하나라고만 알면 됩니다.
- 이 편의 기준(Node.js 24)에서 인수는 `AbortSignal`의 배열입니다.

## 취소 가능한 비동기 작업

비동기 작업을 취소 가능하게 만든다는 것은 `AbortSignal`을 받아서 취소되면 일을 멈추고, 자원을 정리하고, 약속한 방식으로 알리는 것입니다. Node.js의 많은 API가 이미 이를 지원합니다.

| API | 사용 |
|-----|------|
| `timers/promises`의 함수 | `{ signal }` 옵션, `AbortError`로 거부 |
| `events.once`, `events.on` | `{ signal }` 옵션 |
| `fs/promises`의 `readFile`, `writeFile` | `{ signal }` 옵션 |
| `fetch` | `{ signal }` 옵션 |

```js
import { readFile } from 'node:fs/promises'

const ac = new AbortController()
const p = readFile('./big.txt', { signal: ac.signal })
ac.abort()
try { await p } catch (e) { console.log(e.name, e.code) }
// AbortError ABORT_ERR
```

직접 만드는 함수는 같은 규칙을 따라 `{ signal }` 옵션을 받습니다.

```js
function wait(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    signal?.throwIfAborted() // 이미 취소되었으면 시작하지 않음
    const onAbort = () => {
      clearTimeout(timer) // 정리
      reject(signal.reason)
    }
    const timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort)
      resolve('ok')
    }, ms)
    signal?.addEventListener('abort', onAbort)
  })
}
```

규칙은 다음과 같습니다.

- 시작할 때 `signal.throwIfAborted()` 또는 `signal.aborted` 확인으로 이미 취소된 경우를 처리합니다.
- 취소되면 타이머, 리스너, 열린 파일 같은 자원을 정리하고 `signal.reason`으로 거부합니다.
- 정상 종료 때는 `abort` 리스너를 제거합니다. 안 지우면 같은 신호를 오래 쓰는 코드에서 리스너가 쌓입니다.
- 내부에서 다른 비동기 API를 부르면 받은 `signal`을 그대로 넘깁니다. 취소가 아래까지 전파됩니다.
- 취소는 협력적입니다. 작업이 신호를 확인하지 않으면 `abort()`를 불러도 작업은 계속됩니다. 이미 시작된 동기 계산은 신호로 멈출 수 없습니다.
- 취소로 인한 `AbortError`는 실패가 아니라 정상적인 중단이므로, 호출한 쪽이 이름으로 구분해 로그와 에러 처리에서 제외합니다.

## 요청이 끊기면 작업 취소

서버에서 클라이언트가 응답을 받기 전에 연결을 끊으면, 그 요청을 위해 하던 일은 낭비입니다. 응답 객체의 `'close'` 이벤트로 이를 감지해서 `AbortController`로 작업을 멈춥니다. HTTP 서버 자체는 중급 과정에서 다루고, 여기서는 패턴만 봅니다.

```js
const server = http.createServer(async (req, res) => {
  const ac = new AbortController()
  res.on('close', () => {
    if (!res.writableFinished) ac.abort() // 응답 완료 전 종료
  })
  try {
    await sleep(300, null, { signal: ac.signal })
    res.end('done')
  } catch (err) {
    if (err.name !== 'AbortError') throw err
  }
})
```

- `res`의 `'close'`는 응답이 정상으로 끝났을 때도, 연결이 끊겼을 때도 발생합니다. `res.writableFinished`가 `false`일 때만 중단 처리를 합니다.
- 요청 객체 `req`의 `'close'`는 v16.0.0부터 "요청이 모두 수신되었을 때" 발생하므로 연결 끊김 감지에 쓰면 안 됩니다. 공식 문서도 그렇게 바뀌었다고 밝힙니다.
- 이 `signal`을 하위 작업(DB 조회, 외부 API 호출, 파일 읽기)에 넘기면 요청이 끊긴 순간 모두 취소됩니다.
- 제한 시간까지 걸려면 `AbortSignal.any([ac.signal, AbortSignal.timeout(5000)])`로 합쳐서 넘깁니다.
- 취소된 뒤에는 응답을 쓸 상대가 없으므로 `res.end`를 호출하지 않는 편이 안전합니다.

## ref, unref, refresh

`Timeout`과 `Immediate` 객체는 이벤트 루프를 살려 둘지(ref), 재설정할지(refresh) 정하는 메서드를 가집니다.

| 메서드 | 동작 |
|--------|------|
| `timeout.unref()` | 이 타이머만 남아 있으면 프로세스가 종료되어도 됨 |
| `timeout.ref()` | 이벤트 루프를 붙잡는 기본 상태로 되돌림 |
| `timeout.hasRef()` | 붙잡고 있으면 `true` |
| `timeout.refresh()` | 시작 시각을 지금으로 바꿔 같은 `delay`로 다시 예약 |

기본은 ref 상태입니다. 활성 타이머가 있으면 프로세스가 끝나지 않습니다.

```js
setTimeout(() => console.log('never'), 100).unref()
console.log('end')
// end (남은 일이 없어 프로세스가 종료되고 never는 출력되지 않음)
```

- `unref()`한 타이머도 다른 이유로 프로세스가 살아 있는 동안에는 정상적으로 실행됩니다. "프로세스를 붙잡지 않는다"는 뜻이지 취소가 아닙니다.
- 상태 점검 같은 백그라운드 타이머가 종료를 막지 않게 할 때 씁니다. `ref()`와 `unref()`는 여러 번 불러도 효과가 한 번과 같고 객체 자신을 반환합니다.
- `timers/promises`의 함수는 `{ ref: false }` 옵션으로 같은 일을 합니다.

`refresh()`는 새 객체를 만들지 않고 타이머를 처음부터 다시 셉니다. 유휴 타임아웃(마지막 활동 후 일정 시간 무입력이면 처리)에 맞습니다.

```js
const idle = setTimeout(() => close(), 60_000)
function onActivity() {
  idle.refresh() // 활동이 있을 때마다 60초를 다시 셈
}
```

- 이미 콜백이 실행된 타이머에 `refresh()`를 부르면 다시 활성화됩니다.
- 활동마다 `clearTimeout`과 `setTimeout`을 새로 부르는 방식도 되지만 `refresh`는 객체를 새로 할당하지 않습니다.

## timers/promises의 setInterval

`timers/promises`의 `setInterval(delay, value, options)`는 `delay`ms마다 `value`를 내놓는 비동기 이터레이터를 반환합니다(v15.9.0). `for await`로 돕니다.

```js
import { setInterval as every } from 'node:timers/promises'

let n = 0
for await (const v of every(1000, 'tick')) {
  console.log(v, ++n) // tick 1, tick 2, tick 3
  if (n === 3) break
}
```

- 루프 본문이 끝나야 다음 값을 받으므로 본문이 겹쳐 실행되지 않습니다. 전역 `setInterval`의 겹침 문제가 없습니다(위 "인터벌이 겹치는 경우").
- `break`나 예외로 루프를 빠져나오면 반복 타이머가 정리됩니다. 전역 `setInterval`처럼 `clear` 호출을 따로 챙기지 않아도 됩니다.
- `signal` 옵션으로 취소하면 루프가 `AbortError`를 던지므로 `try`와 `catch`로 감쌉니다.

```js
const ac = new AbortController()
const { signal } = ac
setTimeout(() => ac.abort(), 3500)
try {
  for await (const _ of every(1000, null, { signal })) {
    await doWork()
  }
} catch (err) {
  if (err.name !== 'AbortError') throw err
}
```

- `ref`가 `true`(기본)이면 이터레이터의 `next()`가 호출되어야 이벤트 루프가 유지됩니다. 이벤트 루프를 붙잡지 않으려면 `{ ref: false }`를 줍니다.

## 핵심 정리

- `setTimeout`과 `setInterval`은 `Timeout` 객체를, `setImmediate`는 `Immediate` 객체를 반환하고 각각 `clearTimeout`, `clearInterval`, `clearImmediate`로 취소하며, 지연은 최소 보장일 뿐 정확하지 않습니다.
- `setInterval`은 콜백이 끝나기를 기다리지 않아 비동기 작업이 겹칠 수 있고, 겹치면 안 될 때는 재귀 `setTimeout`이나 `timers/promises`의 `for await` 반복을 씁니다.
- `timers/promises`는 타이머를 Promise와 비동기 이터레이터로 제공하며, `signal` 옵션으로 취소하면 `AbortError`로 거부됩니다.
- `AbortController`가 `abort()`로 취소를 요청하고 `AbortSignal`이 취소 여부를 알립니다. `AbortSignal.timeout`은 제한 시간(`TimeoutError`), `AbortSignal.any`는 여러 취소 조건을 합칩니다.
- 취소 가능한 함수는 `signal`을 받아 이미 취소됐는지 확인하고, 취소 시 자원을 정리한 뒤 `signal.reason`으로 거부하며, 하위 호출에 신호를 전달합니다.
- 서버의 요청 취소는 응답 객체의 `'close'`와 `writableFinished`로 감지하고, `unref`는 타이머가 종료를 막지 않게 하며 `refresh`는 타이머를 처음부터 다시 셉니다.

## NODE_ENV

`NODE_ENV`는 실행 환경의 이름(`development`, `production`, `test`)을 알리려고 쓰는 환경변수 이름입니다. Node.js가 해석하는 변수가 아니라 생태계의 관례입니다. 읽는 쪽은 프레임워크와 라이브러리, 그리고 직접 쓴 코드입니다.

```bash
NODE_ENV=production node app.mjs
```

```js
if (process.env.NODE_ENV === 'production') {
  // 운영 환경 전용 설정
}
```

- 값을 지정하지 않으면 `process.env.NODE_ENV`는 `undefined`입니다. 기본값을 채워 주는 쪽은 없습니다.
- Express는 `production`일 때 뷰 템플릿을 캐시하고 에러 메시지를 덜 자세하게 만듭니다. 이처럼 라이브러리가 동작을 바꾸는 신호로 씁니다.
- 값은 문자열이므로 `'production'`처럼 정확히 비교합니다. 오타(`prod`)는 어느 분기에도 걸리지 않습니다.
- 환경변수라서 `process.env`의 규칙을 그대로 따릅니다(자세히는 05편).
- 권한 모델(`--permission`)로 실행하면 `NODE_ENV`는 기본적으로 유지되지 않아서 읽으려면 `--allow-env=NODE_ENV`가 필요합니다.

**흔한 실수:** `NODE_ENV`로 개발·운영의 모든 설정 차이를 분기하는 것입니다. 비밀번호와 접속 주소 같은 값은 환경 이름이 아니라 개별 환경변수로 주입합니다. `process.env.NODE_ENV`를 조건문마다 직접 읽기보다 시작할 때 한 번 읽어 설정 객체로 만들어 쓰는 편이 안전합니다.

## .env 파일과 실제 환경변수

`.env` 파일은 `이름=값` 형식으로 환경변수를 적어 두는 텍스트 파일입니다. 운영체제의 환경변수가 아니라, 프로그램이 읽어서 `process.env`에 채워 넣는 입력 파일입니다.

```text
# .env
PORT=3000
NAME="kim"        # 주석
export MODE=dev
```

| 항목 | 실제 환경변수 | `.env` 파일 |
|------|---------------|-------------|
| 위치 | 운영체제·셸·컨테이너가 프로세스에 전달 | 디스크의 텍스트 파일 |
| 적용 시점 | 프로세스 시작 시 | 누군가 파일을 읽어 `process.env`에 넣을 때 |
| 읽는 주체 | Node.js가 시작할 때 자동으로 | `--env-file`, `loadEnvFile`, 또는 라이브러리 |
| 자식 프로세스 전파 | 전달됨 | `process.env`에 넣은 뒤라면 전달됨 |
| 버전 관리 | 해당 없음 | 비밀이 있으면 커밋하지 않음 |

- 파일을 읽는 코드가 없으면 `.env`는 아무 효과가 없습니다. 파일이 있다고 `process.env`에 저절로 채워지지 않습니다.
- 값은 환경변수와 같이 모두 문자열입니다.
- 이미 환경에 같은 이름의 변수가 있으면 환경의 값이 우선합니다. 파일이 덮어쓰지 않습니다.
- 비밀 값(DB 비밀번호, API 키)이 든 `.env`는 저장소에 커밋하지 않습니다.
- 운영 환경에서는 파일 대신 배포 도구나 컨테이너가 환경변수를 주입하는 방식이 일반적입니다.

### --env-file

`node --env-file=파일`은 프로그램을 시작하기 전에 파일을 읽어 `process.env`에 넣습니다(v20.6.0). 현재 디렉터리 기준의 경로입니다.

```bash
node --env-file=.env app.mjs
node --env-file=.env --env-file=.dev.env app.mjs
node --env-file-if-exists=.env.local app.mjs
```

```js
console.log(process.env.PORT) // '3000' (문자열)
```

- 옵션은 스크립트 이름보다 앞에 씁니다. 뒤에 쓰면 스크립트의 인수가 됩니다.
- 여러 번 쓸 수 있고, 뒤에 오는 파일이 앞 파일의 같은 변수를 덮어씁니다.
- 파일이 없으면 에러입니다. 없어도 되는 파일은 `--env-file-if-exists`(v22.9.0)를 씁니다.
- 파일 형식은 한 줄에 `이름=값`입니다. `#` 뒤는 주석이고, 값은 `` ` ``, `"`, `'` 따옴표로 감쌀 수 있으며(따옴표는 값에서 빠짐), 따옴표 안에서는 여러 줄 값이 가능하고, 키 앞의 `export`는 무시됩니다.
- `NODE_OPTIONS` 같은 Node.js 설정 변수도 파일에서 읽어 적용됩니다.
- `--env-file`과 `--env-file-if-exists`는 v24.10.0에서 실험 단계가 끝났습니다.

### process.loadEnvFile

`process.loadEnvFile([path])`는 코드 안에서 `.env` 파일을 읽어 `process.env`에 넣습니다(v21.7.0). `path`의 기본값은 `./.env`입니다.

```js
import { loadEnvFile } from 'node:process'

loadEnvFile()              // ./.env
loadEnvFile('./.env.test') // 지정한 파일
```

- 파일이 없으면 에러를 던집니다(`ENOENT`). 선택 파일이면 `try`로 감쌉니다.
- 이미 있는 환경변수는 덮어쓰지 않습니다.
- 이 함수는 `NODE_OPTIONS`를 반영하지 않습니다. 파일에 있어도 효과가 없습니다.
- 호출 시점 이후에 읽는 코드만 값을 봅니다. 값을 읽는 모듈보다 먼저 호출해야 합니다.
- v24.10.0에서 실험 단계가 끝났습니다.

파일을 읽어 객체로만 바꾸고 싶으면 `util.parseEnv(content)`가 문자열을 파싱해 객체로 돌려줍니다. `process.env`는 바뀌지 않습니다.

```js
import { parseEnv } from 'node:util'

parseEnv('HELLO=world\nHELLO=oh my\n')
// { HELLO: 'oh my' } (같은 키는 뒤의 값)
```

### dotenv와 비교

`dotenv`는 같은 일을 하는 서드파티 패키지입니다. `.env`를 읽어 `process.env`에 채웁니다. 내장 기능이 생기기 전부터 널리 쓰였습니다.

```js
import 'dotenv/config'
// 또는
import dotenv from 'dotenv'
dotenv.config({ path: '.env.local', override: true })
```

| 항목 | 내장(`--env-file`, `loadEnvFile`) | dotenv |
|------|-----------------------------------|--------|
| 설치 | 불필요 | `npm install dotenv` |
| 기존 환경변수 | 환경이 우선 | 기본은 환경이 우선, `override: true`로 덮어쓰기 |
| 여러 파일 | `--env-file`을 여러 번 | `path`에 배열 |
| 로드 시점 | 시작 전(플래그), 또는 호출 시 | import 또는 `config()` 호출 시 |

- 내장 기능으로 충분하면 의존성을 하나 줄일 수 있습니다. 기존 프로젝트가 dotenv를 쓰고 있으면 바꿀 필요는 없습니다.
- 위 표의 dotenv 항목은 dotenv의 README를 기준으로 했습니다. 상세 옵션은 해당 문서를 확인합니다.

## 전역 객체 global과 globalThis

`global`은 Node.js의 전역 객체(global object)를 가리키는 이름입니다. 전역 객체의 프로퍼티는 import 없이 어디서나 쓸 수 있는 전역 변수가 됩니다(`process`, `console`, `setTimeout` 등).

```js
global.myFlag = 1
console.log(myFlag) // 1 (전역 변수로 보임)
```

- `global`의 안정성 지수는 3(Legacy)입니다. 공식 문서는 `globalThis`를 쓰라고 안내합니다.
- 브라우저는 `window`, 워커는 `self`로 달라서 환경마다 이름이 다릅니다. 표준 이름이 필요해서 생긴 것이 `globalThis`입니다.
- 모듈의 최상위 스코프는 전역이 아닙니다. 브라우저의 스크립트와 달리 `var`로 선언해도 전역 객체의 프로퍼티가 되지 않고 그 모듈에 지역적입니다. CommonJS와 ESM 모두 그렇습니다.
- 다른 모듈에서 읽히는 전역 상태를 만드는 건 피합니다. 어디서 바뀌었는지 추적하기 어려워집니다.

### globalThis

`globalThis`는 실행 환경과 상관없이 전역 객체를 가리키는 표준 이름입니다(ES2020). Node.js에서는 `global`과 같은 객체입니다.

```js
globalThis === global // true
var v = 1             // 모듈 최상위
globalThis.v          // undefined (전역이 아님)
globalThis.shared = 5
console.log(shared)   // 5
```

- 새로 쓰는 코드에는 `globalThis`를 씁니다. 브라우저와 Node.js에서 같은 코드가 동작합니다.
- 전역에 값이 있는지 확인할 때도 씁니다. 예를 들어 `typeof fetch`나 `'fetch' in globalThis`로 기능 유무를 판별합니다.

**흔한 실수:** `node -e`로 실험할 때 `var` 변수가 `globalThis`에 보이는 것을 보고 파일에서도 같다고 믿는 것입니다. 파일(모듈)에서는 보이지 않습니다.

## __dirname과 __filename

`__filename`은 현재 모듈 파일의 절대 경로, `__dirname`은 그 파일이 있는 디렉터리의 절대 경로입니다. CommonJS 모듈에서만 쓸 수 있습니다.

```js
// /Users/mjr/example.js (CommonJS)
console.log(__filename) // /Users/mjr/example.js
console.log(__dirname)  // /Users/mjr
```

- `__dirname`은 `path.dirname(__filename)`과 같습니다.
- `__filename`은 심볼릭 링크를 해석한 절대 경로입니다. 메인 프로그램이면 명령행에서 쓴 파일 이름과 다를 수 있습니다.
- 모듈마다 값이 다릅니다. 전역 변수가 아니라 각 CommonJS 모듈에 주입되는 값입니다(자세히는 08편).
- `process.cwd()`와 다릅니다. `cwd`는 실행한 위치이고 `__dirname`은 파일의 위치라서 어디서 실행해도 같습니다.

```js
const path = require('node:path')

path.join(__dirname, 'data.json') // ✅ 실행 위치와 무관
'./data.json'                     // fs 호출에서는 cwd 기준
```

- 파일 기준 경로가 필요하면 `path.join(__dirname, ...)`으로 만듭니다(자세히는 15편).
- ESM에서는 이 변수가 없어서 참조하면 `ReferenceError`입니다. 아래 두 절이 대체 방법입니다.

## ESM에서 import.meta.url

`import.meta`는 ES Modules 안에서만 쓸 수 있는 메타 객체이고, `import.meta.url`은 현재 모듈의 절대 `file:` URL 문자열입니다. 브라우저의 같은 속성과 같은 정의입니다.

```js
console.log(import.meta.url)
// file:///work/app/src/main.mjs
```

- 경로가 아니라 URL이라서 `/work/app/src/main.mjs`가 아니라 `file://` 접두사가 붙습니다. 공백이나 한글은 퍼센트 인코딩됩니다.
- 이 값으로 `new URL()`의 기준을 삼아 같은 위치의 파일을 가리킬 수 있습니다.

```js
import { readFileSync } from 'node:fs'

const url = new URL('./data.json', import.meta.url)
const text = readFileSync(url, 'utf8')
```

- `fs`는 `file:` URL 객체를 경로 자리에 받습니다. 그래서 URL을 문자열 경로로 바꾸지 않고 바로 넘길 수 있습니다.
- `import.meta`는 ES Modules에서만 지원됩니다. CommonJS 파일에서는 쓸 수 없습니다.

## ESM에서 디렉터리 경로 얻기

ESM에는 `__dirname`과 `__filename`이 없습니다. 공식 문서는 대체로 `import.meta.dirname`과 `import.meta.filename`을 안내합니다.

```js
import path from 'node:path'

const file = import.meta.filename // 절대 경로(파일)
const dir = import.meta.dirname   // 절대 경로(디렉터리)
const data = path.join(dir, 'data.json')
```

| ESM | CommonJS | 비고 |
|-----|----------|------|
| `import.meta.filename` | `__filename` | 심볼릭 링크 해석된 절대 경로 |
| `import.meta.dirname` | `__dirname` | `path.dirname(import.meta.filename)`과 같음 |
| `import.meta.url` | 없음 | `file:` URL 문자열 |

- `import.meta.dirname`과 `import.meta.filename`은 v21.2.0, v20.11.0에서 추가됐고 v24.0.0, v22.16.0에서 실험 단계가 끝났습니다.
- 두 속성은 `file:` 모듈에서만 있습니다. 다른 스킴(예: `data:`)으로 불러온 모듈에는 없습니다.
- `import.meta.filename`은 `url.fileURLToPath(import.meta.url)`과 같은 값입니다.

이 두 속성이 없는 환경(오래된 Node.js)에서는 URL을 경로로 변환해 직접 만듭니다.

```js
import { fileURLToPath } from 'node:url'
import path from 'node:path'

const __filename = fileURLToPath(import.meta.url)
const __dirname = path.dirname(__filename)
```

- 자주 보이는 이 관용구는 `import.meta.filename`이 생기기 전부터 쓰던 방식입니다. 지원하는 Node.js 범위가 24 이상이면 `import.meta.dirname`으로 충분합니다.
- `import.meta.url.replace('file://', '')`처럼 문자열로 자르면 안 됩니다. Windows 드라이브 문자와 퍼센트 인코딩 때문에 틀립니다. 변환은 `fileURLToPath`로 합니다(자세히는 15편).

**흔한 실수:** ESM에서 `__dirname`을 그대로 쓰는 것입니다.

```js
console.log(__dirname)
// ReferenceError: __dirname is not defined
//   in ES module scope
```

## 핵심 정리

- `NODE_ENV`는 Node.js가 아니라 생태계의 관례이며 기본값은 없고(`undefined`), 읽는 쪽이 `'production'` 같은 문자열로 비교합니다.
- `.env` 파일은 읽는 코드가 있어야 효과가 있습니다. `--env-file`(시작 전)이나 `process.loadEnvFile()`(코드에서)로 읽고, 이미 있는 환경변수는 덮어쓰지 않으며 값은 문자열입니다.
- 비밀이 든 `.env`는 커밋하지 않습니다. 내장 기능이 하는 일은 `dotenv`와 같아서 새 코드에는 설치가 필요 없습니다.
- `global`은 Legacy이고 `globalThis`가 표준 이름이며, 모듈의 최상위 `var`는 전역이 되지 않습니다.
- CommonJS는 `__filename`·`__dirname`, ESM은 `import.meta.filename`·`import.meta.dirname`이 현재 파일의 절대 경로이고 `import.meta.url`은 `file:` URL입니다.
- 이전 버전 호환이 필요하면 `fileURLToPath(import.meta.url)`로 경로를 만듭니다.

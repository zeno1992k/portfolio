## 쉬뱅

쉬뱅(shebang, 해시뱅)은 파일 첫 줄의 `#!`로 시작하는 줄로, 유닉스 계열 운영체제가 그 파일을 어떤 인터프리터로 실행할지 알려 줍니다. Node.js 스크립트에서는 다음 줄을 씁니다.

```js
#!/usr/bin/env node
console.log('hello')
```

- `/usr/bin/env node`는 `PATH`에서 `node`를 찾아 실행합니다. `node`의 경로를 고정하지 않아서 nvm 같은 버전 관리자 아래에서도 동작합니다(자세히는 02편).
- 파일의 맨 처음 글자여야 합니다. 앞에 공백, 빈 줄, BOM이 있으면 셸이 인식하지 못합니다. 파일은 BOM 없는 UTF-8로 저장합니다.
- 파일마다 한 번만 쓸 수 있습니다.
- 쉬뱅은 ECMAScript에서 표준화된 해시뱅 주석입니다. JavaScript 엔진이 한 줄 주석처럼 무시하므로 스크립트와 ES Modules 모두에서 허용됩니다. `node file.mjs`로 직접 실행할 때도 문제가 없습니다.
- 쉬뱅은 셸이 읽는 정보입니다. `node file.js`로 실행하면 Node.js는 이를 주석으로 넘깁니다.
- npm 문서도 `bin`에 등록한 파일은 `#!/usr/bin/env node`로 시작해야 한다고 밝힙니다. 없으면 `node` 없이 스크립트가 실행됩니다.

**흔한 실수:** 쉬뱅을 빼먹는 것입니다. 셸이 JavaScript 파일을 셸 스크립트로 해석해서 문법과 상관없는 엉뚱한 에러가 납니다.

## 실행 권한

유닉스 계열에서 파일을 명령으로 실행하려면 실행 권한(execute bit)이 있어야 합니다. 쉬뱅이 있어도 권한이 없으면 `Permission denied`입니다.

```sh
chmod +x hello.mjs
./hello.mjs
```

- `ls -l`에서 `-rwxr-xr-x`처럼 `x`가 보이면 실행 권한이 있습니다.
- 현재 폴더의 파일은 `./`를 붙여 경로로 실행합니다. 이름만 쓰면 셸이 `PATH`에서만 찾습니다.
- Windows에는 실행 권한 비트가 없고 쉬뱅을 셸이 해석하지도 않습니다. `node hello.mjs`로 실행하거나, npm이 만드는 `.cmd` 실행 파일을 씁니다(아래 "bin 필드와 npm link 개념").
- Git은 실행 권한 비트를 저장합니다. 윈도우에서 만든 파일이라면 `git update-index --chmod=+x 파일`로 기록할 수 있습니다.
- npm으로 설치하는 패키지의 `bin` 파일은 npm이 연결을 만들어 주므로 사용자가 `chmod`를 할 필요가 없습니다.
- 권한 비트의 읽기 방법은 18편에서 다룹니다.

## argv 파싱

CLI는 `node app.mjs build --out dist -v`처럼 인수를 받습니다. `process.argv`는 실행 파일 경로와 스크립트 경로 뒤에 인수를 문자열 배열로 담고 있고, 그것을 해석하는 일이 인수 파싱입니다(자세히는 05편).

```js
// node app.mjs build --out dist -v
process.argv.slice(2) // ['build', '--out', 'dist', '-v']
```

- 인수는 모두 문자열입니다. 숫자나 불리언은 직접 변환해야 합니다.
- 용어는 다음과 같이 씁니다.

| 용어 | 예 | 뜻 |
|------|----|----|
| 옵션 | `--out dist`, `-v` | 이름이 붙은 인수. 값이 없으면 플래그 |
| 긴 옵션 / 짧은 옵션 | `--verbose` / `-v` | 두 하이픈 / 한 하이픈과 한 글자 |
| 위치 인수 | `build` | 옵션이 아닌 인수. 순서가 의미를 가짐 |
| 옵션 종결자 | `--` | 이후 인수는 옵션이 아니라 위치 인수로 취급 |

- `--out=dist`처럼 `=`로 값을 붙이는 형태와 `-abc`처럼 짧은 옵션을 묶는 형태가 관례입니다.
- 수동으로 `argv`를 `startsWith('--')`로 나누면 `=` 처리, 묶음, `--` 종결자 같은 규칙을 놓치기 쉽습니다. 파서를 씁니다.

### util.parseArgs

`util.parseArgs()`는 Node.js 내장 인수 파서입니다(`node:util`, 20.0.0부터 실험 딱지가 없는 정식 API). 기대하는 옵션을 선언하면 파싱 결과를 구조화해서 돌려줍니다.

```js
import { parseArgs } from 'node:util'

const { values, positionals } = parseArgs({
  options: {
    name: { type: 'string', short: 'n', default: 'world' },
    shout: { type: 'boolean', short: 's' },
  },
  allowPositionals: true,
})
// node app.mjs -n kim -s a b
// values: { name: 'kim', shout: true }
// positionals: ['a', 'b']
```

| 옵션 | 뜻 |
|------|----|
| `args` | 파싱할 배열. 기본은 `process.argv`에서 실행 파일과 스크립트 경로를 뺀 것 |
| `options` | 옵션 선언. `type`(`'string'` 또는 `'boolean'`), `short`(한 글자), `multiple`, `default` |
| `strict` | 선언하지 않은 옵션이나 타입이 맞지 않으면 에러. 기본 `true` |
| `allowPositionals` | 위치 인수 허용. 기본은 `strict`가 `true`이면 `false` |
| `allowNegative` | `--no-이름`으로 불리언을 `false`로 지정 허용. 기본 `false` |
| `tokens` | 파싱 상세 정보(`tokens`)도 반환 |

- Node.js 24.15에서 확인한 동작입니다.

| 입력 | 결과 |
|------|------|
| `-ab` | `a`, `b` 둘 다 `true` (짧은 옵션 묶음) |
| `-nkim`, `--name=lee` | `name`이 `'kim'`, `'lee'` |
| `--tag x --tag y` | `multiple: true`이면 `['x', 'y']`, 아니면 마지막 값 |
| `--` 뒤의 `-a` | 위치 인수 `'-a'` |
| `--no-color` | `allowNegative: true`이면 `color`가 `false` |

- `values`는 프로토타입이 없는 객체(`[Object: null prototype]`)입니다.
- `default`는 옵션이 나타나지 않을 때만 적용됩니다. 값이 거짓이어도 옵션이 나타나면 기본값을 쓰지 않습니다.
- 값이 없는 문자열 옵션(`-n`만 쓰기)이나 `--name -a`처럼 다음 인수가 옵션이면 에러입니다.
- strict 모드의 에러는 `TypeError`이고 `code`가 붙습니다. 예: `ERR_PARSE_ARGS_UNKNOWN_OPTION`, `ERR_PARSE_ARGS_INVALID_OPTION_VALUE`, `ERR_PARSE_ARGS_UNEXPECTED_POSITIONAL`. CLI에서는 이 에러를 잡아서 사용자용 메시지와 사용법을 출력하고 종료합니다.

```js
let args
try {
  args = parseArgs({ options, allowPositionals: true })
} catch (err) {
  console.error(`error: ${err.message}`)
  process.exit(2)
}
```

- 서브커맨드, 자동 도움말, 값 검증은 제공하지 않습니다. 필요하면 `commander` 같은 라이브러리를 씁니다(아래).

## 도움말

도움말은 `-h`, `--help`로 사용법을 보여 주는 출력입니다. 실행 방법을 문서 없이 알려 주는 CLI의 기본 인터페이스입니다.

```js
const HELP = `Usage: upper [options] [file]

Options:
  -n, --number  prefix line numbers
  -h, --help    show this help
`
if (values.help) {
  console.log(HELP)
  process.exit(0)
}
```

- `--help`는 요청받은 정상 출력이므로 stdout에 쓰고 종료 코드는 0입니다. 잘못된 사용으로 사용법을 보여 줄 때는 stderr에 쓰고 0이 아닌 코드로 끝냅니다.
- 도움말에는 사용법 한 줄, 옵션 목록(짧은 이름, 긴 이름, 설명, 기본값), 위치 인수를 담습니다.
- `parseArgs`는 도움말을 만들어 주지 않으므로 직접 작성하고 `options` 선언과 어긋나지 않게 관리합니다.
- 인수가 하나도 없을 때도 도움말을 보여 줄지 동작을 정합니다. 위치 인수가 필수인 도구는 도움말과 에러를 함께 내는 편이 친절합니다.
- 버전은 `--version`이나 `-V`로 출력합니다. `package.json`의 `version`을 읽어 쓰면 두 값이 어긋나지 않습니다(자세히는 11편).

## stdout에 결과

stdout(표준 출력)에는 프로그램의 결과 데이터만 씁니다. 다른 프로그램이 파이프나 리다이렉트로 받아 쓰는 값입니다.

```sh
upper notes.txt > out.txt   # 결과만 파일로
upper notes.txt | wc -l     # 결과만 다음 명령으로
```

- 진행 상황, 안내, 로그를 stdout에 섞으면 `| jq`나 `> file`로 받는 쪽의 데이터가 깨집니다.
- 기계가 읽을 출력이 필요하면 `--json` 같은 옵션으로 JSON을 출력합니다. 사람이 읽는 표나 색은 별도 모드로 둡니다.
- `console.log`는 stdout에 씁니다. 출력이 아주 많을 때는 스트림으로 흘려보내는 방식이 알맞습니다(스트림은 중급 과정에서 다룹니다).
- 파이프에서 출력이 비동기로 처리될 수 있어서 `process.exit()`를 호출하면 출력이 잘릴 수 있습니다. 종료 코드는 `process.exitCode`로 정하고 이벤트 루프가 끝나게 두는 방식이 안전합니다(자세히는 05편, 06편).
- 파이프 반대편(예: `head`)이 먼저 닫히면 stdout 쓰기에서 `EPIPE` 에러가 날 수 있습니다. Node.js 문서가 `EPIPE`를 "읽는 프로세스가 없는 파이프에 쓰기"로 설명합니다.

## stderr에 에러

stderr(표준 에러)에는 에러 메시지와 경고, 진행 상황 같은 진단 정보를 씁니다. 결과 데이터 스트림과 분리되어 있어서 stdout이 파이프로 넘어가도 사람이 터미널에서 에러를 볼 수 있습니다.

```js
console.error(`upper: ${err.code ?? err.message}`)
process.exitCode = 1
```

```sh
upper missing.txt > out.txt   # 에러는 터미널에, out.txt는 비어 있음
upper missing.txt 2> err.log  # 에러만 파일로
```

- `console.error`와 `console.warn`이 stderr에 씁니다(자세히는 26편).
- 에러 메시지는 `프로그램이름: 무슨 일이 일어났는지` 형태가 관례이고, 사용자가 고칠 수 있는 정보(파일 경로, 잘못된 옵션 이름)를 담습니다.
- 스택 트레이스는 사용자에게 보여 줄 필요가 없는 경우가 많습니다. 예상한 에러(`ENOENT`, 잘못된 옵션)는 한 줄 메시지로, 예상하지 못한 에러는 스택까지 출력합니다. `--verbose`나 환경변수로 스택을 켜는 방식도 흔합니다(예상 가능한 에러와 프로그래머 에러의 구분은 25편).
- 에러를 stderr에 쓰고도 종료 코드가 0이면 호출한 스크립트가 실패를 모릅니다. 둘은 항상 함께 갑니다.

### util.styleText

`util.styleText(format, text)`는 터미널에서 텍스트에 색과 스타일을 입히는 ANSI 이스케이프 코드를 붙여 줍니다(`node:util`, Stable). 이 함수는 출력 스트림의 상태를 보고 색을 적용합니다.

```js
import { styleText } from 'node:util'

console.log(styleText('green', 'done'))
const opt = { stream: process.stderr }
console.error(styleText('red', 'failed', opt))
console.log(styleText(['bold', 'underline'], 'title'))
```

- `format`에는 `'red'`, `'green'`, `'bold'`, `'underline'` 같은 `util.inspect.colors`의 이름이나 그 배열을 줍니다. 배열은 왼쪽에서 오른쪽으로 적용되어 뒤의 색이 앞의 색을 덮어씁니다.
- `stream` 옵션의 기본값은 `process.stdout`이고, 이 스트림이 색을 처리할 수 있는지 검사합니다. stderr에 쓸 문자열이면 `{ stream: process.stderr }`를 줍니다. `validateStream: false`로 검사를 끌 수 있습니다.
- 스트림이 터미널이 아니거나(파이프, 파일), `NO_COLOR`나 `NODE_DISABLE_COLORS` 환경변수가 설정됐으면 색 코드를 붙이지 않습니다. `FORCE_COLOR`가 설정되면 색을 붙입니다. Node.js 24.15에서 파이프로 출력했을 때 색 코드가 없는 것을 확인했습니다.
- `FORCE_COLOR`와 `NO_COLOR`를 동시에 설정하면 `NO_COLOR`가 무시된다는 경고가 나옵니다.
- 16진수 색(`'#ff5733'`, `'#RGB'`)은 24.16.0과 26.1.0에서 추가되었습니다.
- 색은 의미 전달의 보조 수단이어야 합니다. 색을 못 보는 환경에서도 `error:`, `warning:` 같은 글자로 구분됩니다.

## 종료 코드 규약

종료 코드(exit code)는 프로세스가 끝날 때 운영체제에 돌려주는 0–255 정수입니다. 0은 성공, 0이 아닌 값은 실패를 뜻하는 것이 관례이며 셸과 CI가 이 값으로 성공 여부를 판단합니다.

```sh
upper notes.txt && echo ok   # 종료 코드 0일 때만 실행
echo $?                      # 직전 명령의 종료 코드
```

- Node.js는 처리되지 않은 예외가 있으면 `1`로 끝나고, 일이 모두 끝나면 `0`으로 끝납니다. Node.js 문서가 정한 코드는 다음과 같습니다.

| 코드 | 뜻 |
|------|----|
| `0` | 성공 (처리할 비동기 작업이 남지 않음) |
| `1` | 처리되지 않은 치명적 예외 |
| `9` | 잘못된 인수. 알 수 없는 옵션이나 값이 없는 옵션 (`node` 자신의 옵션) |
| `13` | 최상위 `await`의 Promise가 끝나지 않음 |
| `128`+n | 시그널 n으로 종료 (`SIGKILL`이면 137) |

- CLI가 어떤 코드를 쓸지는 도구가 정하고 문서에 적습니다. 흔한 구성은 `0` 성공, `1` 일반 실패, `2` 사용법 오류(잘못된 옵션)입니다. 이 문서의 예제도 이 구성을 씁니다. Node.js 문서는 `2`를 "사용하지 않음(Bash가 내장 명령의 잘못된 사용용으로 예약)"으로 설명합니다.
- 호출하는 쪽이 실패 종류를 구분해야 하면 코드를 더 나눕니다(예: 입력 파일 없음, 네트워크 실패). 코드 목록은 도움말이나 문서에 둡니다.
- 종료 코드를 정하는 두 방법이 있습니다. `process.exit(code)`는 즉시 종료하고, `process.exitCode = code`는 대기 중인 작업을 마친 뒤 그 코드로 종료합니다(자세히는 05편). 출력이 남아 있을 수 있으면 `exitCode`가 안전합니다.
- 에러를 `catch`로 잡아 메시지만 찍고 끝내면 종료 코드가 `0`이 됩니다. 실패라면 `exitCode`를 설정합니다.

**흔한 실수:** 잘못된 입력을 받아 에러 메시지를 출력하고도 종료 코드를 설정하지 않는 것입니다. `my-tool && deploy`가 실패한 도구 뒤에 배포를 실행합니다.

## 파이프 입력

CLI는 파일 경로 인수 대신 표준 입력(stdin)으로 데이터를 받을 수 있습니다. 셸 파이프(`|`)나 리다이렉트(`<`)로 다른 프로그램의 출력을 입력으로 받는 방식입니다(자세히는 06편).

```sh
cat notes.txt | upper
upper < notes.txt
```

- 입력이 터미널이면 `process.stdin.isTTY`가 `true`이고, 파이프나 파일이면 `undefined`입니다. 파일 인수도 없고 터미널이라면 사용자가 입력을 기다리게 되므로 도움말을 보여 주고 끝내는 편이 낫습니다.
- `process.stdin`은 읽기 스트림이라서 `for await`로 청크를 모읍니다.

```js
async function readStdin() {
  let text = ''
  process.stdin.setEncoding('utf8')
  for await (const chunk of process.stdin) text += chunk
  return text
}
```

- 파이프 입력은 청크 단위로 도착합니다. 한 번에 다 읽은 뒤 처리하거나, 줄 단위로 흘려 처리할 수 있습니다. 줄 단위는 `node:readline`의 `createInterface({ input: process.stdin })`을 `for await`로 순회합니다.
- 파일 인수와 stdin이 함께 올 때의 우선순위를 정하고 도움말에 적습니다.
- 로컬에서 Node.js 24.15로 `printf 'a\nb\n' | ./upper.mjs -n`을 실행하면 `1: A`, `2: B`가 나왔습니다.
- 파이프의 앞 프로그램이 오래 걸리면 뒤 프로그램은 입력이 끝날 때까지 기다립니다. 인코딩을 지정하지 않으면 청크가 `Buffer`이므로 문자열로 이어 붙일 때 `setEncoding`으로 멀티바이트 문자가 청크 경계에서 깨지지 않게 합니다(자세히는 20편).

## bin 필드와 npm link 개념

`package.json`의 `bin`은 명령 이름과 실행할 파일을 연결하는 필드입니다. 패키지를 설치하면 npm이 그 이름의 명령을 `PATH`에 만들어 줍니다(필드 자체는 10편에서 다뤘습니다).

```json
{
  "name": "upper-cli",
  "type": "module",
  "bin": { "upper": "./bin/upper.mjs" }
}
```

- 설치 방식에 따라 만들어지는 위치가 다릅니다. npm 문서 기준입니다.

| 설치 | 결과 |
|------|------|
| 전역 설치 | 전역 bin 디렉터리에 연결(유닉스 계열은 심볼릭 링크, Windows는 `.cmd` 파일). `upper`로 실행 |
| 다른 패키지의 의존성 | 그 패키지에서 `npm exec`, `npm run` 스크립트 안에서 이름으로 사용 가능 |

- 문자열 하나(`"bin": "./cli.js"`)로 쓰면 패키지 이름이 명령 이름이 됩니다.
- `bin` 파일은 쉬뱅으로 시작해야 하고, 파일이 ES Modules이면 `"type": "module"`이나 `.mjs` 확장자가 필요합니다(자세히는 09편).
- `bin`에 쓴 파일이 배포에 포함되도록 `files` 필드도 확인합니다(자세히는 10편).

`npm link`는 개발 중인 패키지를 설치한 것처럼 쓰게 해 주는 명령입니다. 배포하지 않고 명령을 시험할 때 씁니다.

```sh
cd upper-cli
npm link            # 전역에 링크를 만들고 bin을 PATH에 연결
upper notes.txt     # 어디서든 실행됨. 소스를 고치면 바로 반영
npm link upper-cli  # 다른 프로젝트에서 이 패키지를 링크로 사용
```

- npm 문서에 따르면 인수 없는 `npm link`는 전역 폴더(`{prefix}/lib/node_modules/<package>`)에 이 패키지로 연결되는 심볼릭 링크를 만들고 `bin`을 `{prefix}/bin/{name}`에 연결합니다.
- 다른 프로젝트에서 `npm link 패키지이름`을 하면 전역에 설치된 그 패키지로 연결되는 링크가 `node_modules`에 생깁니다. 이름은 폴더 이름이 아니라 `package.json`의 `name`입니다.
- 링크는 실제 설치가 아니라 원본을 가리키므로 편집 결과가 즉시 반영됩니다. 반대로 원본 폴더를 지우면 깨집니다.
- 시험이 끝나면 링크를 풀고 실제 설치로 확인합니다. `npm pack`으로 만든 묶음을 설치해 보면 `files` 누락을 찾을 수 있습니다.
- `npx 패키지이름`은 설치 없이 `bin`을 실행하는 방법입니다(자세히는 13편).

## commander 소개

`commander`는 Node.js CLI를 만들기 위한 널리 쓰는 서드파티 라이브러리입니다(npm으로 설치). 옵션과 인수를 선언하면 인수 파싱, 사용법 에러, 도움말 생성, 서브커맨드까지 처리합니다.

```js
import { program } from 'commander'

program
  .option('--first')
  .option('-s, --separator <char>')
  .argument('<string>')
program.parse()
const options = program.opts()
console.log(program.args[0].split(options.separator))
```

```text
$ node split.js -s - --fits a-b-c
error: unknown option '--fits'
(Did you mean --first?)
```

- 위 코드와 출력은 commander README의 예입니다. 알 수 없는 옵션에는 오류와 비슷한 옵션 제안을 보여 줍니다.
- 서브커맨드는 `program.command('split')`으로, 버전은 `.version('0.8.0')`으로 선언합니다. `-h`와 `--help`로 도움말이 자동 생성되고 `-V`와 `--version`으로 버전을 출력합니다.
- `parseArgs`와 비교하면 다음과 같습니다.

| 항목 | `util.parseArgs` | `commander` |
|------|------------------|-------------|
| 설치 | 내장 (`node:util`) | `npm install commander` |
| 도움말 | 직접 작성 | 선언에서 자동 생성 |
| 서브커맨드 | 직접 구현 | 지원 |
| 사용 오류 | `TypeError`를 던짐 (직접 처리) | 오류를 표시 (README) |
| 의존성 | 없음 | 추가됨 |

- 옵션이 몇 개 안 되는 작은 도구는 `parseArgs`로 충분합니다. 서브커맨드가 있거나 도움말을 많이 다듬어야 하면 라이브러리가 덜 번거롭습니다.

## 핵심 정리

- CLI 스크립트는 첫 줄에 `#!/usr/bin/env node`를 쓰고 유닉스 계열에서는 `chmod +x`로 실행 권한을 줍니다. Windows는 `node 파일`이나 npm이 만든 `.cmd`로 실행합니다.
- `process.argv`의 인수는 모두 문자열이며, `util.parseArgs`는 옵션 선언으로 `values`와 `positionals`를 돌려주고 strict 모드에서 잘못된 입력에 에러를 던집니다.
- 결과 데이터는 stdout, 에러와 진단은 stderr에 씁니다. `--help` 출력은 stdout에 0으로 끝내고 사용법 오류는 stderr에 0이 아닌 코드로 끝냅니다.
- 종료 코드는 0이 성공이고, 실패는 0이 아닌 값입니다. 출력이 남아 있을 수 있으면 `process.exitCode`를 쓰고 에러를 찍은 뒤 코드를 설정하는 것을 잊지 않습니다.
- `util.styleText`는 스트림이 터미널이 아니거나 `NO_COLOR`가 있으면 색을 붙이지 않습니다. 파이프 입력은 `process.stdin`을 `for await`로 읽고 `isTTY`로 구분합니다.
- `bin` 필드가 명령 이름과 파일을 연결하고 `npm link`가 개발 중 패키지를 전역과 다른 프로젝트에 링크합니다. 서브커맨드나 자동 도움말이 필요하면 `commander`를 씁니다.

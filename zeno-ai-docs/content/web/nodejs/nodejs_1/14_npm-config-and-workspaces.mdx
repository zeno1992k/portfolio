## .npmrc

`.npmrc`는 npm의 설정을 담는 ini 형식 파일입니다. `키=값` 한 줄이 설정 하나이고 `;`나 `#`로 시작하는 줄은 주석입니다.

```ini
; .npmrc
registry=https://registry.npmjs.org/
save-exact=true
engine-strict=true
```

npm은 설정을 다음 순서로 읽고 앞쪽이 우선합니다.

| 순위 | 출처 | 예 |
|------|------|----|
| 1 | 명령줄 옵션 | `--save-exact` |
| 2 | 환경변수 | `npm_config_` 접두사. 하이픈은 밑줄로 씀 |
| 3 | `.npmrc` 파일 | 프로젝트, 사용자, 전역, 내장 순 |
| 4 | npm 기본값 | `save-prefix`는 `^` |

`.npmrc` 파일은 네 곳에 둘 수 있고 위쪽이 이깁니다.

| 위치 | 경로 |
|------|------|
| 프로젝트 | 프로젝트 루트의 `.npmrc` |
| 사용자 | `~/.npmrc` |
| 전역 | `$PREFIX/etc/npmrc` |
| 내장 | npm 설치 폴더의 `npmrc`(수정 불가) |

- 값 안에서 `${변수명}`으로 환경변수를 끼워 넣습니다. 변수가 없을 때 빈 문자열로 쓰려면 `${변수명?}`입니다.
- 인증 토큰은 레지스트리 주소에 묶어서 적습니다. `//registry.npmjs.org/:_authToken=${NPM_TOKEN}` 형태입니다.
- `npm config`는 사용자·전역 `.npmrc`를 읽고 씁니다. 패키지 단위 값은 `.npmrc`가 아니라 `package.json`의 `config` 필드에 두면 지원하지 않는 키 경고가 없습니다.
- 자주 쓰는 설정의 기본값은 다음과 같습니다.

| 설정 | 기본값 | 뜻 |
|------|--------|----|
| `registry` | `https://registry.npmjs.org/` | 패키지를 받는 레지스트리 주소 |
| `save-exact` | `false` | `true`면 범위 연산자 없이 저장 |
| `save-prefix` | `^` | 저장할 때 붙이는 접두사 |
| `engine-strict` | `false` | `true`면 호환되지 않는 패키지 설치 거부 |
| `ignore-scripts` | `false` | `true`면 스크립트 실행 안 함 |
| `package-lock` | `true` | `false`면 lock 파일 무시 |

**흔한 실수:** 토큰을 `.npmrc`에 그대로 적어 저장소에 올리는 것입니다. 프로젝트 `.npmrc`는 커밋되므로 토큰은 `${NPM_TOKEN}`처럼 환경변수로 참조하고 값은 CI의 비밀 저장소에 둡니다.

## 스코프 패키지

스코프 패키지는 `@스코프/이름` 형태로 이름 앞에 소유자 이름을 붙인 패키지입니다. 사용자나 조직마다 자기 스코프가 있고 그 스코프에는 소유자만 패키지를 추가할 수 있습니다.

```bash
npm install @myorg/utils
```

```js
import { slug } from '@myorg/utils'
// node_modules/@myorg/utils 에 설치됨
```

- 설치 위치는 `node_modules/@myorg/utils`입니다. 코드에서도 스코프를 포함한 이름 전체로 불러옵니다.
- 이름이 겹치지 않게 하고, 한 조직의 패키지를 묶어 보여 주는 용도로 씁니다. 모노레포의 내부 패키지 이름에도 흔히 씁니다.
- 스코프를 다른 레지스트리에 연결할 수 있습니다. 한 스코프는 레지스트리 하나만 가리킵니다.

```ini
@myorg:registry=https://npm.my-company.example/
```

- 스코프 패키지는 기본으로 공개되지 않습니다. 처음 공개할 때 `npm publish --access public`을 줍니다. 이후 새 버전은 이 옵션이 필요 없습니다.

## engines

`engines`는 패키지가 동작하는 Node.js와 npm의 버전 범위를 적는 `package.json` 필드입니다.

```json
{
  "engines": {
    "node": ">=24",
    "npm": ">=11"
  }
}
```

- 기본은 권고(advisory)입니다. 이 패키지를 의존성으로 설치한 환경이 범위를 벗어나면 경고만 냅니다.
- `engine-strict=true`를 설정하면 현재 Node.js와 호환되지 않는다고 적힌 패키지의 설치를 거부합니다. 프로젝트 `.npmrc`에 두면 팀 전체에 적용됩니다.
- 범위 문법은 13편의 semver 범위와 같습니다.
- `engines`는 어떤 Node.js로 실행할지 정하지 않습니다. 버전을 고정하는 도구는 02편의 `.nvmrc`와 `.node-version`입니다.

**흔한 실수:** `engines`만 적으면 설치가 막힐 것이라고 기대하는 것입니다. `engine-strict`를 켜지 않으면 경고뿐이라 CI에서는 로그를 읽지 않으면 지나칩니다.

## overrides

`overrides`는 의존성 트리 안의 어느 깊이에 있든 특정 패키지의 버전이나 대상 패키지를 바꾸는 필드입니다. 의존성의 의존성에 알려진 취약점이 있을 때 그 버전을 올리거나, 포크로 바꾸거나, 같은 버전을 어디서나 쓰게 만드는 데 씁니다.

```json
{
  "overrides": {
    "foo": "1.0.0",
    "bar": { "baz": "^2.0.0" },
    "qux@3.0.0": { "foo": "1.0.1" }
  }
}
```

| 키 | 의미 |
|----|------|
| `"foo": "1.0.0"` | 트리 어디서든 `foo`를 이 버전으로 |
| `"bar": { "baz": ... }` | `bar`의 하위에 있는 `baz`만 |
| `"qux@3.0.0": { ... }` | 부모가 `qux@3.0.0`일 때만 |
| `"foo": "$foo"` | 직접 의존성 `foo`의 명세를 그대로 따름 |
| `".": "1.0.0"` | 중첩 객체에서 그 패키지 자신 |

- 루트 `package.json`의 `overrides`만 효력이 있습니다. 설치된 의존성이나 워크스페이스에 적힌 `overrides`는 무시됩니다.
- 직접 의존성에 적은 것과 다른 명세로 같은 패키지를 override하면 `EOVERRIDE` 에러가 납니다. 같은 명세를 쓰거나 `$이름`으로 참조합니다.
- 값에는 범위 외에 `npm:` 접두사로 다른 패키지(`"foo": "npm:@scope/fork@1.0.0"`), GitHub 저장소, `file:` 경로도 쓸 수 있습니다.
- override한 버전은 그 패키지가 선언한 호환 범위를 무시하고 강제하는 것입니다. 하위 패키지가 깨질 수 있으므로 테스트가 필요합니다.

## workspaces

워크스페이스(workspaces)는 한 저장소 안의 여러 패키지를 하나의 루트 아래에서 함께 설치하고 연결하는 npm 기능입니다. 루트 `package.json`에 `workspaces`로 위치를 적습니다.

```json
{
  "name": "root",
  "private": true,
  "workspaces": ["packages/*"]
}
```

```text
root/
  package.json
  packages/a/package.json   (name: @demo/a)
  packages/b/package.json   (name: @demo/b)
```

- `packages/*`처럼 글롭으로 적으면 그 아래에서 유효한 `package.json`이 있는 폴더가 워크스페이스가 됩니다.
- 루트에서 `npm install`을 하면 각 워크스페이스가 루트 `node_modules`에 심볼릭 링크로 들어갑니다. 그래서 `@demo/b`가 `"@demo/a": "^1.0.0"`을 의존성으로 적으면 레지스트리가 아니라 `packages/a`가 연결됩니다.
- 설치된 모습은 `npm ls`에서 `@demo/a@1.0.0 -> .\packages\a`처럼 경로로 보입니다.
- lock 파일은 루트에 하나만 만들어집니다.
- 루트는 발행하지 않는 컨테이너라서 `"private": true`로 둡니다.

워크스페이스를 고르는 옵션은 다음과 같습니다.

| 옵션 | 뜻 |
|------|----|
| `-w <이름 또는 경로>` | 지정한 워크스페이스에만 적용 |
| `--workspaces` | 모든 워크스페이스에 적용 |
| `--if-present` | 해당 스크립트가 없는 워크스페이스는 건너뜀 |

```bash
npm install abbrev -w @demo/a
npm run test -w @demo/a
npm run test --workspaces --if-present
npm init -w ./packages/c
```

## corepack

corepack은 프로젝트가 지정한 패키지 관리자(Yarn, pnpm)를 따로 설치하지 않고 쓰게 해 주는 도구입니다. 프로젝트 `package.json`의 `packageManager` 필드를 읽어 그 버전을 내려받아 실행합니다.

```json
{
  "packageManager": "pnpm@10.0.0+sha224.0123abcd..."
}
```

- 형식은 `이름@버전`이고 뒤에 `+sha224.해시`를 붙이면 내려받은 파일을 검증합니다. 해시는 선택이지만 보안상 권장됩니다. 값으로 쓸 수 있는 이름은 `yarn`, `npm`, `pnpm`입니다.
- `corepack enable`은 Yarn과 pnpm의 실행 파일(shim)을 `PATH`에 만듭니다. npm shim은 요청해야 만들어집니다.
- 프로젝트가 다른 패키지 관리자로 지정돼 있으면 corepack이 다른 도구로 설치하는 것을 막고 알려 줍니다.
- 주요 명령은 다음과 같습니다.

| 명령 | 하는 일 |
|------|---------|
| `corepack enable` | shim을 만듦 |
| `corepack use pnpm@버전` | 최신 일치 버전을 `packageManager`에 기록하고 설치 |
| `corepack install` | 프로젝트가 지정한 도구를 내려받음 |
| `corepack up` | 같은 메이저 안에서 최신으로 갱신 |

**버전 상태:** Node.js 24 문서에서 corepack은 Stability 1(Experimental)이고 "Node.js v25부터 corepack을 배포하지 않는다"고 안내합니다. Node.js 24에는 들어 있고 Node.js 26 문서에는 corepack 페이지가 없습니다. 그 이후에는 `npm install -g corepack`으로 corepack 프로젝트의 패키지를 직접 설치합니다.

## pnpm과 yarn을 나중에 보는 이유

npm을 먼저 익히는 이유는 다음과 같습니다.

- npm은 Node.js와 함께 설치되어 별도 설치가 필요 없습니다.
- 개념(`package.json`, 의존성 종류, semver, lock 파일, scripts)이 도구마다 공통이고, 차이는 이 개념 위에서 설명됩니다.
- pnpm과 yarn은 같은 `package.json`을 읽지만 lock 파일 이름과 `node_modules` 구성, 명령 일부가 다릅니다.

| 도구 | lock 파일 |
|------|-----------|
| npm | `package-lock.json` |
| pnpm | `pnpm-lock.yaml` |
| yarn | `yarn.lock` |

- 프로젝트가 어떤 도구를 쓰는지는 저장소에 있는 lock 파일과 `packageManager` 필드로 알 수 있습니다.
- 한 프로젝트에서는 도구 하나만 씁니다. lock 파일이 둘 이상 생기면 설치 결과가 서로 달라질 수 있습니다.

**흔한 실수:** 팀이 pnpm을 쓰는 저장소에서 습관대로 `npm install`을 실행해 `package-lock.json`을 만드는 것입니다.

## pnpm의 저장 방식과 엄격한 node_modules

pnpm은 패키지 파일을 컴퓨터 전체에서 공유하는 하나의 저장소(content-addressable store)에 두고, 프로젝트에는 하드 링크로 연결합니다. 같은 파일은 디스크에 한 번만 저장됩니다. 다른 버전이 필요하면 달라진 파일만 저장소에 추가합니다.

| 항목 | npm 기본(hoisted) | pnpm |
|------|-------------------|------|
| 파일 저장 | 프로젝트마다 복사 | 공유 저장소에 한 번, 프로젝트에 하드 링크 |
| 루트 `node_modules` | 의존성이 평평하게 펼쳐짐 | 직접 의존성만 심볼릭 링크로 놓임 |
| 실제 패키지 위치 | 루트 `node_modules` | `node_modules/.pnpm` |

- npm의 `--install-strategy` 기본값은 `hoisted`입니다. 하위 의존성까지 루트에 평평하게 올라옵니다.
- pnpm은 `package.json`에 적지 않은 패키지를 불러오면 찾지 못해서 실패합니다. 이렇게 선언하지 않은 의존성을 우연히 쓰는 문제를 유령 의존성(phantom dependency)이라 하고, pnpm의 구조는 그것을 막습니다.
- 평평한 구조에서는 다른 패키지의 하위 의존성이 우연히 루트에 올라와 있어서, 선언하지 않아도 동작하는 코드가 만들어질 수 있습니다. 다른 환경에서 구조가 달라지면 그때 깨집니다.

## npm audit의 한계

`npm audit`은 프로젝트의 의존성 구성을 레지스트리에 보내 알려진 취약점(known vulnerabilities) 보고서를 받는 명령입니다.

```bash
npm audit                       # 취약점 보고
npm audit fix                   # 가능한 수정 적용
npm audit --audit-level=high    # high 이상이면 실패
npm audit signatures            # 서명과 출처 증명 검증
```

- 레지스트리에 이미 등록된 취약점만 보고합니다. 알려지지 않은 취약점이나 의도적으로 심은 악성 코드를 찾는 도구가 아닙니다.
- 보고하는 단위는 의존성 트리입니다. lock 파일이 필요합니다. 기본으로 lock 파일이 있어야 실행되고, `--no-package-lock`으로 우회하면 실행할 때마다 트리를 다시 만들어 결과가 달라질 수 있습니다.
- 취약점이 하나라도 있으면 기본으로 0이 아닌 종료 코드를 반환합니다. `--audit-level`은 실패 기준만 바꿀 뿐 출력을 걸러 내지 않습니다.
- `npm audit fix`는 내부적으로 `npm install`을 실행하므로 설치에 쓰이는 설정이 그대로 적용됩니다. 자동으로 고칠 수 없는 취약점은 직접 검토해야 합니다.
- 수정이 SemVer 메이저 변경을 요구하면 `--force`가 필요합니다. 메이저 업그레이드는 동작이 바뀔 수 있어서 테스트가 필요합니다.
- `npm audit signatures`는 별도 기능입니다. 레지스트리 서명과 출처 증명(provenance attestation)을 검증합니다.

**흔한 실수:** `npm audit` 결과가 깨끗하면 안전하다고 읽는 것입니다. 그 결과는 알려진 취약점이 없다는 뜻이지 의존성이 안전하다는 보증이 아닙니다.

## 패키지를 직접 공개하는 개념

패키지를 공개(publish)하는 것은 `npm publish`로 패키지 묶음(tarball)을 레지스트리에 올려 누구나 이름으로 설치하게 하는 일입니다.

```bash
npm publish --dry-run     # 실제 변경 없이 올릴 내용을 보고
npm publish               # 공개
npm publish --access public   # 스코프 패키지를 처음 공개할 때
```

- 이름과 버전의 조합은 한 번 공개하면 영원히 다시 쓸 수 없습니다. `npm unpublish`로 지워도 마찬가지입니다. 실수한 버전은 고쳐서 새 버전으로 올립니다.
- 올라가는 파일은 `package.json`의 `files` 목록으로 정하고, `.gitignore`나 `.npmignore`에 걸리는 파일은 제외됩니다. 올리기 전에 `--dry-run`으로 목록을 확인합니다.
- `"private": true`인 패키지는 `npm publish`가 거부됩니다. 실수로 공개하는 것을 막는 안전장치입니다.
- 기본 태그는 `latest`이고 `--tag`로 다른 태그에 올릴 수 있습니다(자세히는 13편).
- 2단계 인증이 켜져 있으면 `--otp`로 일회용 코드를 넘깁니다.
- 공개 때 실행되는 스크립트는 `prepublishOnly`, `prepack`, `prepare` 순입니다(자세히는 13편).
- 의존성을 선언하는 규칙은 11편의 `dependencies`와 `peerDependencies`를 따릅니다. 진입점과 실행 파일 필드는 10편에서 다룹니다.

## 공급망 공격 대응

공급망 공격(supply chain attack)은 내가 쓰는 의존성 또는 그 하위 의존성이 변조되거나 악성 버전으로 교체되어 내 환경에서 코드가 실행되는 공격입니다. 설치할 때 실행되는 스크립트(`preinstall`, `install`, `postinstall`)가 그 통로가 될 수 있습니다. 대응은 한 가지가 아니라 겹겹입니다.

| 수단 | 막는 것 | 방법 |
|------|---------|------|
| lock 파일 고정 | 설치할 때마다 달라지는 버전 | 커밋하고 CI는 `npm ci` |
| 스크립트 차단 | 설치 중 임의 코드 실행 | `ignore-scripts=true` |
| 출처 증명 | 누가 어디서 빌드했는지 불명 | `provenance`, `npm audit signatures` |
| 취약점 검사 | 알려진 취약한 버전 | `npm audit` |

### lock 파일

lock 파일은 설치된 정확한 버전을 기록하므로, 커밋하고 CI에서 `npm ci`로 설치하면 lock에 적힌 버전만 설치됩니다(자세히는 12편). 범위가 `^1.2.3`이어도 새 악성 버전이 자동으로 들어오지 않습니다. 의존성을 올릴 때는 lock 파일의 변경 내용을 코드 리뷰에서 봅니다.

### ignore-scripts

`ignore-scripts=true`이면 npm은 `package.json`의 스크립트를 실행하지 않습니다. 명령줄에서는 `npm ci --ignore-scripts`로 씁니다.

```ini
; .npmrc
ignore-scripts=true
```

- 의존성의 `postinstall` 같은 스크립트가 실행되지 않으므로 설치 때 코드가 실행되는 경로가 막힙니다.
- 이 설정은 의존성의 스크립트와 내 프로젝트의 스크립트를 구분하지 않고 막습니다. 네이티브 모듈을 빌드하는 `install` 스크립트에 의존하는 패키지는 정상 동작하지 않을 수 있어서 필요한 것만 따로 실행해야 합니다.
- pnpm 10은 의존성의 `postinstall` 자동 실행을 기본으로 끕니다. 문서 기준으로 `strictDepBuilds`는 v10.3.0에서 추가되어 기본이 `true`이고 검토하지 않은 빌드 스크립트가 있으면 설치가 비정상 종료합니다. `allowBuilds`(v10.26.0에서 추가)에 패키지별로 `true`나 `false`를 적어 허용 여부를 정합니다. 모두 허용하는 `dangerouslyAllowAllBuilds`의 기본은 `false`입니다.

### provenance

provenance는 패키지가 어떤 소스와 빌드 절차에서 만들어졌는지를 레지스트리에 연결해 두는 출처 증명입니다. 서명은 Sigstore가 하고 공개 투명성 기록에 남습니다.

```bash
npm publish --provenance
npm audit signatures
```

- 공개하는 쪽은 지원하는 CI(GitHub Actions, GitLab CI/CD)의 클라우드 호스팅 러너에서 `--provenance`를 주거나 설정 `provenance=true`를 씁니다. npm 9.5.0 이상이 필요하고 GitHub Actions에서는 `id-token: write` 권한이 필요합니다.
- `package.json`의 `repository`가 실제 빌드 위치와 일치해야 합니다.
- 소비하는 쪽은 `npm audit signatures`로 내려받은 패키지의 레지스트리 서명과 출처 증명을 검증합니다.
- provenance는 어디서 빌드했는지를 보여 줍니다. 코드가 안전하다는 보증은 아닙니다.

**흔한 실수:** 모든 대응이 `npm audit`로 끝난다고 보는 것입니다. 이 표의 수단은 서로 다른 위험을 막으므로 겹쳐서 씁니다.

## 핵심 정리

- 설정은 명령줄, 환경변수, `.npmrc`(프로젝트, 사용자, 전역, 내장), 기본값 순으로 우선합니다. 토큰은 `${NPM_TOKEN}`처럼 환경변수로 참조합니다.
- `engines`는 기본이 경고뿐이고 `engine-strict=true`여야 설치를 막습니다. `overrides`는 루트 `package.json`에서만 효력이 있습니다.
- 워크스페이스는 루트 `node_modules`에 각 패키지를 심볼릭 링크로 연결하고, `-w`와 `--workspaces`로 대상을 고릅니다.
- corepack은 `packageManager` 필드로 pnpm·yarn 버전을 지정하며 Node.js 24까지 들어 있고 25부터는 배포되지 않습니다. pnpm은 공유 저장소와 하드 링크, 직접 의존성만 노출하는 `node_modules`가 특징입니다.
- `npm audit`은 알려진 취약점만 보고합니다. 공급망 대응은 lock 고정, `ignore-scripts`, provenance 검증을 겹쳐 씁니다.
- 공개한 이름과 버전은 다시 쓸 수 없고, 스코프 패키지는 처음 공개할 때 `--access public`이 필요합니다.

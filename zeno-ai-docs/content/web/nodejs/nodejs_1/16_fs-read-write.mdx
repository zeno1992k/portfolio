## fs가 웹 API가 아닌 이유

`node:fs`는 POSIX 파일 함수를 본뜬 Node.js 내장 모듈이고 안정성 지수는 Stable(2)입니다. ECMAScript 언어 명세에도 웹 표준에도 없는 Node.js의 호스트 API입니다(자세히는 01편).

- 브라우저 JavaScript에는 `fs`가 없습니다. 웹 페이지가 사용자 컴퓨터의 파일을 마음대로 읽고 쓰면 위험하기 때문에 브라우저는 파일 접근을 막고 사용자가 고른 파일만 다룹니다.
- Node.js는 서버·도구 같은 신뢰하는 환경에서 실행되고 프로세스에 운영체제 권한이 있어서 파일 시스템에 직접 접근하게 합니다.
- 그래서 브라우저 코드를 Node.js로 옮길 때 `fetch`나 `console`은 대부분 그대로 쓰이지만, 파일 입출력은 `fs`로 바꿔 써야 합니다.
- 파일 이름은 문자열, `Buffer`, `file:` `URL` 객체로 줄 수 있습니다. 상대 경로는 소스 파일이 아니라 현재 작업 디렉터리를 기준으로 합니다(자세히는 15편).

```js
import { readFile } from 'node:fs/promises'

await readFile('data.txt', 'utf8')            // 경로 문자열
await readFile(new URL('./a.txt', import.meta.url)) // URL
```

## 세 가지 API

`fs`의 거의 모든 작업은 같은 이름으로 세 가지 형태를 제공합니다.

| 형태 | 가져오는 곳 | 이름 | 결과를 받는 방식 |
|------|-------------|------|------------------|
| 콜백 | `node:fs` | `readFile` | 마지막 인수로 넘긴 콜백 |
| 동기 | `node:fs` | `readFileSync` | 반환값, 실패하면 예외 |
| 프로미스 | `node:fs/promises` | `readFile` | `Promise`, 실패하면 거부 |

```js
import { readFile, readFileSync } from 'node:fs'
import { readFile as read } from 'node:fs/promises'
```

### 콜백 fs

콜백 API는 작업을 시작하고 바로 돌아오며, 끝나면 콜백을 호출합니다. 콜백의 첫 인수는 에러이고 성공이면 `null`입니다(자세히는 23편).

```js
import { readFile } from 'node:fs'

readFile('a.txt', 'utf8', (err, data) => {
  if (err) return console.error(err.code)
  console.log(data)
})
console.log('먼저 출력')
```

- 이벤트 루프를 막지 않고 작업은 스레드 풀에서 실행됩니다(자세히는 01편).
- `readFile` 호출 뒤의 코드가 먼저 실행되므로 `'먼저 출력'`이 파일 내용보다 앞에 나옵니다.
- 콜백이 중첩되기 쉬워서 새 코드에는 프로미스 API를 씁니다.

### 동기 fs

동기 API는 이름 끝에 `Sync`가 붙고 작업이 끝날 때까지 이벤트 루프를 막은 채 기다립니다. 결과를 반환하고 실패하면 예외를 던집니다.

```js
import { readFileSync } from 'node:fs'

try {
  const data = readFileSync('a.txt', 'utf8')
} catch (err) {
  console.error(err.code) // 'ENOENT'
}
```

### fs/promises

프로미스 API는 `node:fs/promises`에서 가져오며 프로미스를 반환합니다. `await`로 쓰고 실패는 `try/catch`로 잡습니다. 이 API도 스레드 풀에서 실행되어 이벤트 루프를 막지 않습니다.

```js
import { readFile } from 'node:fs/promises'

try {
  const data = await readFile('a.txt', 'utf8')
} catch (err) {
  console.error(err.code)
}
```

- 프로미스 API는 Node.js 11.14.0과 10.17.0부터 실험적 표시가 없습니다.
- `import * as fs from 'node:fs'`와 `import { promises } from 'node:fs'`로도 접근하지만, 프로미스 형태는 `node:fs/promises`에서 바로 가져오는 방식이 흔합니다.
- 같은 파일을 대상으로 한 쓰기 호출을 기다리지 않고 여러 번 겹쳐 실행하면 안전하지 않습니다. 콜백과 프로미스 API는 동기화나 스레드 안전성을 제공하지 않아서 동시에 같은 파일을 고치면 데이터가 손상될 수 있습니다.

## 동기 API를 서버에서 피해야 하는 이유

JavaScript는 이벤트 루프 스레드 하나에서 코드를 실행하므로 동기 `fs` 호출이 끝날 때까지 다른 요청 처리, 타이머, 콜백이 모두 멈춥니다(자세히는 03편, 04편).

```js
import { readFileSync } from 'node:fs'

server.on('request', (req, res) => {
  const data = readFileSync('big.json') // ❌ 그 동안 모든 요청 대기
})
```

| 상황 | 동기 API |
|------|----------|
| 요청을 계속 받는 서버 코드 | 피함. 파일 하나가 느리면 전체가 느려짐 |
| 시작할 때 한 번 읽는 설정 | 허용. 아직 요청을 받기 전 |
| 한 번 실행하고 끝나는 스크립트·CLI | 허용. 기다려도 다른 일이 없음 |

- 디스크가 느리거나 네트워크 드라이브면 대기 시간이 길어집니다. 그 시간이 서버 전체의 지연이 됩니다.
- 동기 API의 장점은 코드가 단순하고 예외로 실패를 잡는다는 점입니다.

**흔한 실수:** 요청 핸들러 안에서 편의상 `readFileSync`를 쓰는 것입니다. 개발 중 파일이 작고 요청이 하나뿐이면 문제가 보이지 않다가 운영에서 동시 요청이 늘면 지연이 쌓입니다.

## readFile

`readFile`은 파일 전체를 한 번에 읽어 반환합니다.

```js
import { readFile } from 'node:fs/promises'

const buf = await readFile('a.txt')          // Buffer
const text = await readFile('a.txt', 'utf8') // string
const same = await readFile('a.txt', { encoding: 'utf8' })
```

| 옵션 | 기본값 | 뜻 |
|------|--------|----|
| `encoding` | `null` | `null`이면 `Buffer`, 지정하면 문자열 |
| `flag` | `'r'` | 파일을 여는 방식(아래 "flag") |
| `signal` | 없음 | `AbortSignal`로 진행 중인 읽기를 취소(자세히는 22편) |

- 옵션 자리에 문자열을 주면 그것이 인코딩입니다. `readFile(path, 'utf8')`이 `{ encoding: 'utf8' }`과 같습니다.
- 첫 인수는 경로 문자열, `Buffer`, `URL`, 또는 `FileHandle`입니다.
- 파일이 없으면 `ENOENT`, 디렉터리를 읽으면 `EISDIR` 에러입니다. 에러 코드는 18편에서 정리합니다.
- 알 수 없는 인코딩 이름은 `ERR_INVALID_ARG_VALUE` 에러입니다.
- 파일 전체를 메모리에 올리므로 큰 파일에는 맞지 않습니다. 큰 파일은 스트림으로 조각씩 읽습니다(스트림은 중급 과목).
- 읽은 JSON을 파싱할 때는 문자열로 받아 `JSON.parse(await readFile(path, 'utf8'))`로 씁니다.

**흔한 실수:** 파일 앞의 BOM을 놓치는 것입니다. UTF-8 BOM(`﻿`)이 붙은 JSON 파일을 `'utf8'`로 읽으면 BOM이 문자열 맨 앞에 그대로 남아 `JSON.parse`가 `SyntaxError`를 냅니다. 문자열에서 앞의 `﻿`를 제거한 뒤 파싱합니다.

## writeFile

`writeFile`은 파일에 데이터를 쓰고, 파일이 이미 있으면 내용을 통째로 교체합니다. 파일이 없으면 만듭니다.

```js
import { writeFile } from 'node:fs/promises'

await writeFile('out.txt', 'hello\n')           // 문자열
await writeFile('out.bin', new Uint8Array([1, 2])) // 바이너리
```

| 옵션 | 기본값 | 뜻 |
|------|--------|----|
| `encoding` | `'utf8'` | 문자열을 바이트로 바꾸는 방식. 데이터가 버퍼면 무시 |
| `mode` | `0o666` | 새로 만드는 파일의 권한. 이미 있으면 영향 없음 |
| `flag` | `'w'` | 열기 방식 |
| `flush` | `false` | `true`면 다 쓴 뒤 디스크로 내보내는(sync) 동작을 함 |
| `signal` | 없음 | 취소. 최선을 다하는 방식이라 일부 데이터는 쓰였을 수 있음 |

- `data`는 문자열, `Buffer`, `TypedArray`, `DataView`, 이터러블, 비동기 이터러블입니다. 숫자나 객체는 문자열로 바꿔 주지 않고 `ERR_INVALID_ARG_TYPE`입니다. `JSON.stringify`로 직접 변환합니다.
- 기본 `flag`가 `'w'`라서 파일이 있으면 길이 0으로 자르고 새로 씁니다. 파일 일부를 수정하려면 `'r+'`가 필요합니다(아래 "flag").
- 내부적으로 `write`를 여러 번 호출하는 편의 함수입니다. 쓰는 도중 프로세스가 죽으면 파일이 일부만 쓰인 상태로 남을 수 있습니다(안전한 교체는 18편).
- 같은 파일에 `writeFile`을 기다리지 않고 여러 번 호출하면 안전하지 않습니다.

```js
const user = { name: 'Kim' }
await writeFile('user.json', JSON.stringify(user, null, 2))
```

## appendFile

`appendFile`은 파일 끝에 데이터를 덧붙이고, 파일이 없으면 만듭니다.

```js
import { appendFile } from 'node:fs/promises'

await appendFile('log.txt', 'line 1\n')
await appendFile('log.txt', 'line 2\n')
// log.txt: 'line 1\nline 2\n'
```

- 옵션과 `data`의 형태는 `writeFile`과 같고 기본 `flag`만 `'a'`입니다. 기본 `encoding`은 `'utf8'`, `mode`는 `0o666`입니다.
- 줄바꿈은 자동으로 붙지 않으므로 `'\n'`을 직접 넣습니다.
- 한 줄씩 여러 번 덧붙이는 로그는 호출마다 파일을 열고 닫으므로 비용이 큽니다. 자주 쓰는 로그는 스트림이나 로그 라이브러리를 씁니다(자세히는 26편).

## open

`open`은 파일을 열어 `FileHandle`(프로미스 API) 또는 파일 디스크립터 숫자(콜백·동기 API)를 돌려줍니다. 파일 일부를 읽거나 쓰거나, 여러 번 읽고 쓸 때 씁니다.

```js
import { open } from 'node:fs/promises'

const fh = await open('a.txt')        // 기본 flag 'r'
const fh2 = await open('a.txt', 'r+') // 읽기와 쓰기
```

| 항목 | 값 |
|------|----|
| `flags` 기본값 | `'r'` |
| `mode` 기본값 | `0o666`(파일을 새로 만들 때만 적용) |
| 콜백 형태 | `fs.open(path, flags, mode, callback)`에서 `(err, fd)` |
| 동기 형태 | `fs.openSync(path, flags, mode)`가 `fd` 반환 |

- 파일 디스크립터(fd)는 운영체제가 열린 파일마다 붙이는 정수 번호입니다.
- 열린 파일은 운영체제가 관리하는 자원이라 열었으면 반드시 닫아야 합니다. 열린 개수에는 제한이 있습니다.
- Windows는 파일 이름에 `< > : " / \ | ? *`를 쓸 수 없습니다. NTFS에서 이름에 `:`가 있으면 Node.js는 파일 시스템 스트림을 엽니다.

## close

`close`는 열린 파일을 닫아 운영체제 자원을 돌려줍니다. `FileHandle`은 `filehandle.close()`, 숫자 fd는 `fs.close(fd, callback)`과 `fs.closeSync(fd)`입니다.

```js
let fh
try {
  fh = await open('a.txt')
  // 읽기·쓰기 작업
} finally {
  await fh?.close()  // 에러가 나도 반드시 닫음
}
```

- `close`는 그 핸들에서 진행 중인 작업이 끝나기를 기다린 뒤 닫습니다.
- 닫지 않은 `FileHandle`은 자동으로 닫으려 시도하고 프로세스 경고를 냅니다. 문서는 이 동작을 믿지 말고 항상 직접 닫으라고 하며 동작이 바뀔 수 있다고 적습니다.
- 닫은 핸들로 다시 읽으면 `EBADF` 에러입니다.
- `await using`을 쓰면 블록을 벗어날 때 자동으로 닫힙니다. `FileHandle`의 `Symbol.asyncDispose`는 20.4.0과 18.18.0에서 추가되었고 24.2.0부터 실험적 표시가 없습니다.

```js
{
  await using fh = await open('a.txt')
  const text = await fh.readFile('utf8')
} // 여기서 fh.close() 자동 호출
```

**흔한 실수:** 중간에 예외가 나서 `close`가 실행되지 않는 것입니다. `finally`나 `await using`으로 닫기를 보장합니다.

## FileHandle

`FileHandle`은 숫자 파일 디스크립터를 감싼 객체이고 `fsPromises.open()`이 만듭니다. `EventEmitter`라서 닫히면 `'close'` 이벤트를 냅니다(자세히는 21편).

```js
const fh = await open('a.txt', 'r+')
fh.fd            // 숫자 파일 디스크립터
await fh.readFile('utf8')
await fh.close()
```

주요 메서드는 다음과 같습니다.

| 메서드 | 하는 일 |
|--------|---------|
| `read` | 파일의 일부를 버퍼로 읽음 |
| `write` | 버퍼나 문자열을 씀 |
| `readFile`, `writeFile`, `appendFile` | 핸들로 전체를 읽고 씀. `appendFile`은 `writeFile`의 별칭 |
| `close` | 핸들을 닫음 |

- 핸들은 열 때 정한 `flag`와 `mode`를 따릅니다. 핸들의 `appendFile`로 권한을 바꾸지 못합니다.
- `fsPromises.readFile`과 `fsPromises.writeFile`의 첫 인수에 `FileHandle`을 줄 수도 있습니다.
- 한 핸들은 현재 파일 위치(position)를 가지고 있어서 `read`와 `write`가 위치를 이어서 진행합니다.

## read

`filehandle.read`는 파일의 일부를 버퍼에 채웁니다. 읽은 바이트 수와 버퍼를 담은 객체를 반환합니다.

```js
const buf = Buffer.alloc(4)
const { bytesRead } = await fh.read(buf, 0, 4, 0)
// bytesRead: 읽은 바이트 수 (파일 끝이면 0)
// buf: 읽은 내용으로 채워진 같은 Buffer
```

| 인수 | 기본값 | 뜻 |
|------|--------|----|
| `buffer` | 필수 | 데이터를 채울 버퍼 |
| `offset` | `0` | 버퍼의 어디서부터 채울지 |
| `length` | `buffer.byteLength - offset` | 읽을 바이트 수 |
| `position` | `null` | 파일의 어디서부터 읽을지 |

- `position`이 `null`이나 `-1`이면 현재 파일 위치에서 읽고 위치를 갱신합니다. 0 이상의 정수를 주면 그 위치에서 읽고 현재 위치는 바뀌지 않습니다.
- 객체로 옵션을 주는 형태(`fh.read({ buffer, position })`)도 있습니다. 이때 `buffer`를 생략하면 `Buffer.alloc(16384)`로 읽습니다.
- 반환값의 `bytesRead`가 0이면 파일 끝입니다(파일이 동시에 바뀌지 않았다면).
- 버퍼 크기보다 파일이 길면 한 번에 다 읽지 못하므로 `bytesRead`가 0이 될 때까지 반복합니다.

```js
const buf = Buffer.alloc(4)
for (;;) {
  const { bytesRead } = await fh.read(buf, 0, 4, null)
  if (bytesRead === 0) break
  console.log(buf.toString('utf8', 0, bytesRead))
}
// 'abcdefghij' 파일: abcd, efgh, ij
```

- 버퍼 전체가 아니라 `bytesRead`만큼만 쓰도록 `toString('utf8', 0, bytesRead)`처럼 범위를 줍니다. 마지막 읽기는 버퍼를 다 채우지 못합니다.
- 바이트 단위로 읽으므로 한글처럼 여러 바이트인 문자가 조각 경계에서 잘릴 수 있습니다(자세히는 20편).

## write

`filehandle.write`는 버퍼나 문자열을 파일에 씁니다. 쓴 바이트 수와 쓴 데이터를 담은 객체를 반환합니다.

```js
await fh.write('XY', 2)              // 문자열, position 2
await fh.write(buf, 0, buf.length)   // 버퍼
// 반환: { bytesWritten, buffer }
```

| 형태 | 인수 |
|------|------|
| 버퍼 | `write(buffer, offset, length, position)` 또는 `write(buffer, options)` |
| 문자열 | `write(string, position, encoding)` (`encoding` 기본 `'utf8'`) |

- `position`이 숫자가 아니면 현재 파일 위치에 씁니다. 숫자를 주면 그 위치에 씁니다.
- 문자열이 아닌 값을 문자열 형태로 주면 거부됩니다. 암묵적 변환은 하지 않습니다.
- 같은 파일에 `write`를 기다리지 않고 연속 호출하면 안전하지 않습니다. 한 줄씩 `await`합니다.
- Linux에서는 `'a'`(append) 모드로 연 파일에 위치를 지정해도 커널이 무시하고 항상 끝에 씁니다.
- 파일 일부를 덮어쓰려면 `'r+'`로 열어 `position`을 줍니다.

```js
// a.txt: 'abcdef'
const fh = await open('a.txt', 'r+')
await fh.write('XY', 2)
await fh.close()
// a.txt: 'abXYef'
```

## flag

`flag`는 파일을 여는 방식을 정하는 문자열이고 `readFile`, `writeFile`, `appendFile`, `open`의 옵션으로 줍니다.

| flag | 읽기 | 쓰기 | 파일이 없으면 | 파일이 있으면 |
|------|------|------|---------------|---------------|
| `'r'` | O | X | 에러 | 열기 |
| `'r+'` | O | O | 에러 | 열기(내용 유지) |
| `'w'` | X | O | 만듦 | 내용 삭제 |
| `'w+'` | O | O | 만듦 | 내용 삭제 |
| `'a'` | X | O(끝에 덧붙임) | 만듦 | 열기(내용 유지) |
| `'a+'` | O | O(끝에 덧붙임) | 만듦 | 열기(내용 유지) |

- `'x'`를 붙인 `'wx'`, `'wx+'`, `'ax'`, `'ax+'`는 경로가 이미 있으면 에러입니다(`EEXIST`). 기존 파일을 덮어쓰지 않으려고 쓰며 네트워크 파일 시스템에서는 동작하지 않을 수 있습니다.
- 기본값은 `readFile`과 `open`이 `'r'`, `writeFile`이 `'w'`, `appendFile`이 `'a'`입니다.
- 파일을 교체하지 않고 수정하려면 기본 `'w'`가 아니라 `'r+'`를 줍니다.
- `'s'`가 들어간 flag(`'rs'`, `'as'` 등)는 동기 모드로 열라는 뜻이고 `'rs+'`는 로컬 캐시를 건너뜁니다. 입출력 성능에 큰 영향이 있어서 필요할 때만 씁니다.
- 숫자 flag도 받습니다. `fs.constants`의 값(`O_WRONLY` 등)을 조합합니다.
- 플랫폼별 차이가 있습니다. macOS와 Linux에서 디렉터리를 `'a+'`로 열면 `EISDIR` 에러이고, Windows와 FreeBSD에서는 열립니다. Windows에서 숨김 파일을 `'w'`로 열면 `EPERM` 에러이고 `'r+'`로는 열 수 있습니다.

```js
await writeFile('a.txt', 'x', { flag: 'wx' })
// a.txt가 이미 있으면 EEXIST
```

## encoding을 빼면 Buffer

`encoding` 옵션을 주지 않거나 `null`이면 `readFile`은 문자열이 아니라 `Buffer`를 반환합니다. `Buffer`는 원본 바이트를 그대로 담은 객체입니다(자세히는 19편, 20편).

```js
const buf = await readFile('a.txt')
console.log(buf)        // <Buffer 68 65 6c 6c 6f>
console.log(buf.length) // 5 (바이트 수)

const text = await readFile('a.txt', 'utf8')
console.log(text)       // 'hello'
console.log(text.length) // 5 (문자 수)
```

- 문자열이 필요하면 `readFile(path, 'utf8')`이나 `buf.toString('utf8')`로 변환합니다.
- 바이너리 파일(이미지, 압축 파일)은 인코딩을 주지 않고 `Buffer`로 읽어야 합니다. 문자열로 읽으면 바이트가 바뀌어 원본을 복원할 수 없습니다.
- 바이트 수와 문자 수는 다릅니다. `'한글'`을 쓴 파일은 UTF-8로 6바이트이고 문자열 길이는 2입니다.
- `console.log(buf)`는 `<Buffer ...>`로 보여 줍니다. 템플릿 문자열에 넣으면 UTF-8로 변환되어 에러 없이 문자열이 되므로 인코딩을 지정하지 않았다는 사실을 놓치기 쉽습니다.
- `writeFile`의 `encoding`은 반대 방향으로 문자열을 어떤 바이트로 쓸지 정합니다(기본 `'utf8'`). 데이터가 `Buffer`이면 무시합니다.

**흔한 실수:** 인코딩 없이 읽은 결과를 문자열처럼 쓰는 것입니다. `Buffer`에도 `includes`가 있어서 `data.includes('x')`는 동작하는 것처럼 보이지만, `data.split('\n')`은 `TypeError`이고 `data.length`는 문자 수가 아니라 바이트 수입니다.

## 핵심 정리

- `fs`는 Node.js 호스트 API이며 브라우저에는 없습니다. 같은 작업을 콜백, 동기(`Sync`), 프로미스(`node:fs/promises`) 세 형태로 제공합니다.
- 콜백과 프로미스 API는 스레드 풀에서 실행되어 이벤트 루프를 막지 않고, 동기 API는 끝날 때까지 이벤트 루프를 막으므로 요청을 받는 서버 코드에서는 피합니다.
- `readFile`은 기본 `'r'`, `writeFile`은 기본 `'w'`(기존 내용 삭제), `appendFile`은 기본 `'a'`(끝에 덧붙임)입니다. 같은 파일을 기다리지 않고 동시에 쓰면 안전하지 않습니다.
- `open`이 돌려주는 `FileHandle`은 `read`와 `write`로 일부를 다루고 반드시 `close`해야 하며, `finally`나 `await using`으로 보장합니다.
- `flag`가 열기 방식(`'r+'`는 수정, `'wx'`는 덮어쓰기 금지)을 정하고, `encoding`을 빼면 `Buffer`가 반환됩니다.

## Windows 경로 구분자

경로 구분자는 Windows가 `\`, POSIX(Linux·macOS)가 `/`입니다. `node:path`는 실행 중인 운영체제에 맞춰 동작합니다. 개발은 Windows, 배포는 Linux인 경우 경로를 문자열로 직접 다루는 코드가 한쪽에서만 깨집니다.

```js
import path from 'node:path'

path.join('a', 'b')  // Windows: a\b, POSIX: a/b
path.sep             // Windows: \, POSIX: /
'a/b'.split(path.sep) // Windows: ['a/b'] (나뉘지 않음)
```

| 하려는 일 | 문자열로 직접 | 안전한 방법 |
|-----------|---------------|-------------|
| 경로 잇기 | `dir + '/' + name` | `path.join(dir, name)` |
| 파일 이름 얻기 | `p.split('/').pop()` | `path.basename(p)` |
| 경로 비교 | `p === 'a/b'` | `path.normalize()` 후 비교, 또는 `path.resolve()` |
| 실행 위치와 무관한 기준 | 상대 경로 | `import.meta.dirname` 기준으로 `path.join` |

- Windows에서 `path.join('a', 'b') === 'a/b'`는 거짓입니다. 같은 경로가 문자열로는 다르게 보입니다.
- POSIX에서는 `\`가 구분자가 아니라 파일 이름에 쓸 수 있는 일반 문자입니다. `path.basename('C:\\temp\\myfile.html')`은 POSIX에서 전체 문자열을 그대로 돌려주고 Windows에서는 `myfile.html`을 돌려줍니다.
- 실행 환경과 상관없이 한 형식을 다뤄야 하면 `path.posix`나 `path.win32`를 명시합니다. 압축 파일 안의 항목 이름, URL 경로, 로그에 남기는 경로는 `path.posix`가 맞습니다.
- URL 경로는 운영체제와 무관하게 `/`를 씁니다. Windows 경로를 그대로 URL에 붙이지 않습니다.
- Windows는 `/`도 받아들이므로 문자열로 이어 붙인 경로가 열리는 경우가 많습니다. 그래서 로컬에서 통과하다가 비교·분리·정규식 같은 코드에서 뒤늦게 깨집니다.
- 환경변수 `PATH`의 구분자도 다릅니다. Windows는 `;`, POSIX는 `:`이고 `path.delimiter`가 알려 줍니다.
- Windows는 파일 이름의 대소문자를 구분하지 않으므로 `foo.html`과 `foo.HTML`이 같은 파일이지만, `path` 함수는 문자열로 비교해서 둘을 다르게 봅니다.

**흔한 실수:** 경로를 정규식이나 `split('/')`으로 쪼개는 것입니다. Windows에서 `import.meta.url`의 `pathname`을 경로로 쓰는 것도 같은 문제를 냅니다. 경로 조작은 `node:path`로, URL과의 변환은 `fileURLToPath()`로 합니다(자세히는 기초 15편).

## exists 체크 후 생성 사이의 경합

"파일이 없으면 만든다"를 `exists`로 확인한 뒤 쓰기로 나누면, 확인과 쓰기 사이에 다른 요청이나 프로세스가 파일을 만들 수 있습니다. 이런 확인과 사용 사이의 틈을 경합 상태(race condition, 확인 시점과 사용 시점의 불일치라서 TOCTOU)라고 합니다.

```js
if (!existsSync('y.txt')) {      // ❌ 확인
  await writeFile('y.txt', text) // 쓰기: 그 사이에 누가 만들었을 수 있음
}
```

두 작업이 동시에 같은 코드를 실행하면 둘 다 "없음"을 보고 둘 다 씁니다. 실행해 보면 두 쪽 모두 `wrote`가 출력되고 나중에 쓴 쪽이 앞의 내용을 덮어씁니다. 해결은 확인과 생성을 하나의 원자적(atomic) 동작으로 합치는 것입니다. 파일 시스템이 한 번에 처리하므로 틈이 없습니다.

```js
try {
  await writeFile('y.txt', text, { flag: 'wx' }) // 있으면 실패
} catch (err) {
  if (err.code !== 'EEXIST') throw err
  // 이미 있음: 정상 경로의 한 갈래로 처리
}
```

| 의도 | 확인 후 실행 ❌ | 한 번에 ✅ |
|------|----------------|-----------|
| 없을 때만 만들기 | `existsSync` 후 `writeFile` | 플래그 `'wx'`(있으면 `EEXIST`) |
| 있으면 읽기 | `existsSync` 후 `readFile` | `readFile`을 `try`/`catch`로 감싸 `ENOENT` 처리 |
| 없으면 폴더 만들기 | `existsSync` 후 `mkdir` | `mkdir(p, { recursive: true })`(이미 있어도 에러 아님) |
| 있으면 지우기 | `existsSync` 후 `rm` | `rm(p, { force: true })`(없어도 에러 아님) |

- Node.js 문서는 `fs.access()`와 `fs.exists()`를 `open`·`readFile`·`writeFile` 전에 호출해서 확인하는 것을 권장하지 않습니다. 파일을 직접 열고 에러를 처리하라고 안내합니다.
- `fs.exists()`(콜백 방식)는 deprecated이며 콜백이 `(err, ...)` 규약을 따르지 않습니다. `fs.existsSync()`는 deprecated는 아니지만 위의 경합 문제는 같습니다.
- 존재 확인 자체가 목적(상태 표시, 존재 여부만 반환)이면 `existsSync`나 `access`를 써도 됩니다. 그 결과를 근거로 다음 동작을 하는 것이 문제입니다.
- 파일을 덮어쓰다 중간에 실패하면 반쪽 파일이 남습니다. 같은 폴더에 임시 파일로 쓴 뒤 `rename`으로 교체하는 방식이 안전합니다.
- 프로세스가 여러 개이면(cluster, 컨테이너 여러 개) 프로세스 안의 변수나 잠금으로는 막을 수 없습니다. 파일 시스템 수준의 원자적 동작이나 DB·Redis의 잠금이 필요합니다(자세히는 18편).

**흔한 실수:** `if (!exists) mkdir`처럼 "에러를 피하려는" 확인이 오히려 경합을 만드는 것입니다. 실패를 막지 말고 실패한 결과(`EEXIST`, `ENOENT`)를 처리합니다.

## 큰 파일 readFile로 메모리 폭발

`readFile`은 파일 전체를 메모리에 올려 한 번에 돌려줍니다. 파일이 크면 그 크기만큼 메모리를 쓰고, 요청마다 호출하면 동시 요청 수만큼 곱해집니다.

```js
const buf = await readFile('big.bin') // 300MB 파일
// 메모리(rss)가 약 301MB 증가 (실행 결과)

for await (const c of createReadStream('big.bin')) {}
// 메모리 증가 약 18MB (조각 단위로 처리)
```

- 스트림은 파일을 조각(기본 64 KiB)으로 읽어 처리합니다. 파일 크기와 무관하게 메모리가 일정합니다(자세히는 1편, 2편).
- `fs.readFile()`에는 별도 한계가 있습니다. 2 GiB보다 큰 파일은 `ERR_FS_FILE_TOO_LARGE`입니다. Node.js 문서는 `Buffer`의 한계가 아니라 내부 I/O의 제약이라고 설명하고 큰 파일에는 `fs.createReadStream()`을 쓰라고 안내합니다.
- `Buffer`의 최대 크기(`buffer.constants.MAX_LENGTH`)는 64비트 환경에서 2의 53제곱 − 1이므로 이 한계에 먼저 걸리지 않습니다.
- 파일을 응답으로 보낼 때는 `createReadStream(path).pipe(res)`보다 `pipeline`을 써서 에러와 연결 종료를 처리합니다(자세히는 2편).
- 줄 단위 처리는 `readline`과 스트림을 결합하고(자세히는 22편), 변환이 필요하면 `Transform`을 씁니다.
- 작은 설정 파일이나 크기가 정해진 파일은 `readFile`이 단순하고 적절합니다. 크기를 모르거나 사용자가 올리는 파일이면 스트림이 안전합니다.
- 요청 본문과 업로드에도 크기 상한을 둡니다(자세히는 4편, 11편).

**흔한 실수:** 로컬의 작은 파일로 시험하고 운영에서 수백 MB 로그나 업로드 파일을 만나는 것입니다. `readFile`로 `JSON.parse`까지 하면 파일 크기에 더해 문자열 변환과 객체 생성에 메모리가 더 듭니다.

## 동기 함수로 이벤트 루프 정지

JavaScript 코드는 한 번에 하나만 실행됩니다. `readFileSync`, `execSync`, `pbkdf2Sync`, 긴 반복문, 거대한 `JSON.parse` 같은 동기 작업은 끝날 때까지 다른 모든 요청과 타이머를 멈춥니다(자세히는 기초 04편).

```js
setInterval(() => console.log('tick'), 100)
pbkdf2Sync('pw', 'salt', 2_000_000, 64, 'sha512')
// 이 호출 동안 tick이 멈춤 (실행 결과: 틱 간격 728ms)

pbkdf2('pw', 'salt', 2_000_000, 64, 'sha512', cb)
// 비동기 버전은 틱이 계속 약 100ms로 유지됨
```

| 동기 | 비동기 대체 |
|------|-------------|
| `fs.readFileSync` | `fs/promises`의 `readFile`, 큰 파일은 스트림 |
| `child_process.execSync` | `execFile`·`spawn`(Promise 버전) |
| `crypto.pbkdf2Sync`, `scryptSync` | `pbkdf2`, `scrypt`(비동기, 스레드 풀) |
| `zlib.gzipSync` | 스트림이나 비동기 `gzip` |
| 큰 `JSON.parse` | 크기 제한, 스트리밍 파서 |

- 동기 함수 자체가 나쁜 것은 아닙니다. 서버가 요청을 받기 전의 시작 단계(설정 읽기, 초기화)와 단발성 스크립트에서는 문제가 없습니다. 요청을 처리하는 동안 호출되는 경로가 문제입니다.
- 한 요청의 동기 작업이 700ms이면 그동안 들어온 모든 요청이 700ms 이상 대기합니다. 서버 전체의 응답이 한꺼번에 느려지는 증상으로 나타납니다.
- 비동기 `pbkdf2`·`scrypt`·`zlib`·파일 I/O는 libuv의 스레드 풀에서 실행되어 이벤트 루프를 막지 않습니다. 단, 스레드 풀 크기는 한정되어 있습니다.
- CPU를 오래 쓰는 순수 JavaScript 계산(이미지 처리, 큰 정렬)은 비동기 버전이 없습니다. 작업을 잘게 나눠 `setImmediate`로 양보하거나 워커 스레드로 옮깁니다(자세히는 아래 "워커에 함수를 그냥 넘길 수 없음").
- 이벤트 루프 지연은 `perf_hooks`의 `monitorEventLoopDelay`로 측정합니다(자세히는 23편).
- 알고리즘이 입력 크기에 비해 지나치게 느려지는 경우(정규식 재귀 등)도 같은 방식으로 서버를 멈춥니다. 외부 입력을 정규식에 넣을 때는 길이를 제한합니다.

**흔한 실수:** "`Sync`는 빠르다"는 인상으로 요청 핸들러 안에서 쓰는 것입니다. 한 사용자 요청에서는 빨라도 동시 사용자가 늘면 전체가 줄 서서 기다립니다.

## 테스트 포트 충돌

테스트가 고정 포트(`listen(3000)`)로 서버를 띄우면 다른 테스트 파일이나 이미 떠 있는 개발 서버와 충돌해 `EADDRINUSE`가 납니다(자세히는 26편). 테스트 러너는 파일을 병렬로 실행합니다. `node:test`는 프로세스 격리가 켜져 있으면 테스트 파일마다 자식 프로세스를 만들고, 동시 실행 수 기본값은 `os.availableParallelism() - 1`입니다.

```js
const server = http.createServer(handler)
await new Promise((r) => server.listen(0, r))
const { port } = server.address() // 운영체제가 정한 빈 포트

// 테스트 끝에서
server.closeAllConnections() // keep-alive 연결이 닫기를 막지 않게
await new Promise((r) => server.close(r))
```

- 포트 0으로 띄우면 운영체제가 사용 중이 아닌 포트를 배정하므로 병렬 실행에도 충돌하지 않습니다. 실제 포트는 `server.address().port`로 읽어 요청 URL에 씁니다.
- 서버는 테스트 파일(또는 테스트 묶음) 단위로 만들고 `after` 훅에서 닫습니다. 닫지 않으면 열린 핸들이 남아 러너가 끝나지 않습니다(다음 절).
- 포트를 환경변수로 받는 앱이라면 테스트에서 `PORT=0`을 주는 방법도 있습니다(자세히는 25편).
- 포트를 고정해야 하는 통합 환경(외부 서비스가 호출하는 주소)에서는 테스트 러너의 동시 실행 수를 1로 줄이는 방법이 있지만, 가능하면 포트 0이 낫습니다.
- 테스트 DB나 임시 파일 경로도 같은 이유로 테스트마다 분리합니다. 같은 파일 이름을 공유하면 병렬 실행에서 서로를 덮어씁니다(자세히는 24편).

**흔한 실수:** 테스트가 혼자 실행하면 통과하고 전체 실행에서만 실패하는 경우입니다. 포트나 파일 같은 공유 자원을 쓰는지 가장 먼저 확인합니다.

## 핸들을 안 닫아 프로세스가 안 죽음

Node.js 프로세스는 이벤트 루프에 활성 자원(핸들)이 남아 있으면 종료하지 않습니다. 코드는 끝났는데 프로세스가 돌아오지 않으면 어떤 자원이 열려 있는 것입니다.

| 열려 있는 것 | 닫는 방법 |
|--------------|-----------|
| HTTP·TCP 서버 | `server.close()` |
| 소켓·keep-alive 연결 | `socket.destroy()`, `server.closeAllConnections()` |
| `setInterval`·긴 `setTimeout` | `clearInterval`·`clearTimeout` |
| DB 커넥션 풀, Redis 클라이언트 | 라이브러리의 `end()`·`quit()`·`close()` |
| `readline` 인터페이스 | `rl.close()` |
| 자식 프로세스와 그 stdio | 종료를 기다리거나 `kill()` |
| 워커 스레드 | `worker.terminate()` |

```js
import process from 'node:process'

console.log(process.getActiveResourcesInfo())
// [ 'TCPServerWrap', 'Timeout' ]처럼 붙잡고 있는 자원의 종류
// (환경에 따라 stdout 관련 항목이 더 나옴)
```

- `process.getActiveResourcesInfo()`는 이벤트 루프를 붙잡고 있는 자원의 종류를 문자열 배열로 돌려줍니다. Node.js 24.0.0에서 안정성 지수가 Stable이 되었습니다.
- 테스트가 끝나지 않는 이유도 대부분 이것입니다. 테스트에서 연 서버와 DB 연결을 `after` 훅에서 닫습니다(자세히는 24편).
- 닫을 수 없는 백그라운드 타이머라면 `timer.unref()`로 "이것만 남으면 종료해도 된다"고 표시합니다. 서버에는 `server.unref()`, 소켓에는 `socket.unref()`가 있습니다.
- `process.exit()`로 강제 종료하는 것은 마지막 수단입니다. 처리 중인 비동기 작업과 쓰기 중인 출력이 중단됩니다. 서비스 코드에서는 닫아야 할 것을 닫고 자연스럽게 끝나게 합니다(자세히는 25편).
- 종료 시그널을 받아 정리한 뒤에도 프로세스가 남는 경우는 이 목록의 항목 하나를 닫지 않은 것입니다.

**흔한 실수:** 안 끝나는 프로세스를 `process.exit()`로만 해결하고 원인을 남겨 두는 것입니다. 나중에 같은 코드를 라이브러리나 테스트로 쓰면 자원이 새는 코드가 됩니다.

## 환경변수 "false"가 참처럼 쓰임

환경변수의 값은 항상 문자열입니다. 비어 있지 않은 문자열은 모두 참이므로 `'false'`, `'0'`, `'no'`도 참입니다.

```js
// DEBUG=false 로 실행
process.env.DEBUG                    // 'false' (문자열)
Boolean(process.env.DEBUG)           // true  ❌
process.env.DEBUG ? 'on' : 'off'     // 'on'  ❌
process.env.DEBUG === 'true'         // false ✅
```

- 불리언 변수는 허용하는 값을 정해 명시적으로 비교합니다. `=== 'true'`만 참으로 보는 방식이 가장 단순합니다. `'1'`, `'yes'`도 허용하려면 집합으로 만듭니다.

```js
const TRUE = new Set(['1', 'true', 'yes', 'on'])
const flag = (v) => TRUE.has(String(v ?? '').toLowerCase())
flag(process.env.DEBUG) // 'false'와 미설정 모두 false
```

- 숫자는 `Number()`로 변환하고 `Number.isNaN`·범위를 검증합니다. `Number('')`은 `0`이므로 빈 문자열이 0이 됩니다. 값이 없음과 0을 구분해야 하면 빈 문자열을 먼저 걸러냅니다.
- 변수가 설정되지 않으면 `undefined`입니다. `PORT=''`처럼 설정되었지만 비어 있는 경우와 다르므로 둘 다 처리합니다.
- 이 변환은 시작 시 설정 검증 한 곳에서 하고, 나머지 코드에는 이미 변환된 값을 넘깁니다(자세히는 25편).
- `process.env`에 값을 대입하면 문자열로 바뀝니다. `process.env.DEBUG = false`는 `'false'`가 되며 이 암묵 변환은 deprecated입니다.

**흔한 실수:** `if (process.env.DEBUG)`로 켜진 기능을 끄려고 `DEBUG=false`를 주는 것입니다. 기능을 끄려면 변수 자체를 설정하지 않아야 하는 코드입니다. 값으로 켜고 끄는 방식이라면 코드가 값을 해석해야 합니다.

## 자식 프로세스 쉘 인젝션

`child_process.exec()`는 명령 문자열을 쉘에 넘겨 실행합니다. 문자열에 사용자 입력이 들어가면 쉘 메타문자(`;`, `&`, `|`, `$()` 등)로 다른 명령이 끼어들 수 있습니다. Node.js 문서도 `exec`에 정제하지 않은 사용자 입력을 넘기지 말라고 경고합니다.

```js
const input = 'a.txt & echo INJECTED'
await run(`echo ${input}`)
// "a.txt \r\nINJECTED\r\n" ❌ 두 명령이 실행됨 (Windows 실행 결과)
await runFile('node', ['-p', 'process.argv[1]', input])
// "a.txt & echo INJECTED\n" ✅ 문자열 전체가 인수 하나
```

- `execFile()`과 `spawn()`은 기본적으로 쉘 없이 프로그램을 직접 실행하고 인수를 배열로 따로 받습니다. 사용자 입력이 인수 하나로 전달되어 메타문자가 해석되지 않습니다.
- `spawn(cmd, args, { shell: true })`나 `execFile(..., { shell: true })`는 쉘을 다시 켭니다. 이때 args 배열은 이스케이프되지 않고 공백으로 이어 붙여질 뿐이라서 인젝션이 가능합니다. 이 사용은 DEP0190으로 Node.js 24.0.0부터 런타임 deprecation입니다.
- 인수 배열을 써도 대상 프로그램이 인수를 옵션으로 해석할 수 있습니다. 파일 이름이나 옵션 값은 허용 목록으로 검증합니다.
- Windows에서 `.bat`·`.cmd` 파일은 `execFile()`로 실행할 수 없습니다. 문서가 안내하는 방법은 `exec()`를 쓰거나 `cmd.exe`에 `/c`와 파일을 인수로 넘기는 것이고, 이때도 인수에 사용자 입력이 들어가지 않게 해야 합니다.
- 자식 프로세스에는 부모의 환경변수가 기본으로 전달됩니다. 시크릿이 필요 없는 명령에는 `env` 옵션으로 필요한 변수만 넘깁니다(자세히는 25편).
- 코드 검토에서 `exec`, `execSync`, `shell: true`를 검색해 입력이 섞이는지 확인합니다.

**흔한 실수:** 입력을 따옴표로 감싸는 것으로 막으려 하는 것입니다. 입력에 따옴표가 들어 있으면 빠져나옵니다. 쉘을 거치지 않는 `execFile`이 확실합니다.

## allocUnsafe로 쓰레기 바이트 유출

`Buffer.allocUnsafe(size)`는 메모리를 0으로 초기화하지 않고 빠르게 할당합니다. 이전에 그 메모리를 쓰던 다른 데이터가 남아 있을 수 있고, 문서는 이 내용에 민감한 데이터가 있을 수 있다고 경고합니다.

```js
const buf = Buffer.allocUnsafe(8)
buf.write('hi')           // 2바이트만 씀
buf.toString('hex')       // 68697ed6a8030000 (실행 결과)
// 뒤의 6바이트는 이전에 있던 메모리 내용
Buffer.alloc(8).toString('hex') // 0000000000000000
```

- 앞의 `68 69`가 `hi`이고 나머지는 이전 사용자의 데이터일 수 있습니다. 이 버퍼 전체를 응답이나 파일로 보내면 다른 요청의 데이터가 새어 나갑니다.
- `Buffer.alloc(size)`는 0으로 채워서 돌려줍니다. 안전이 기본이고 `allocUnsafe`는 성능이 필요하고 전체를 덮어쓴다고 확신할 때만 씁니다.
- `allocUnsafe`로 만든 버퍼는 쓴 길이만큼만 사용합니다. `const n = buf.write(text)`로 쓴 바이트 수를 받아 `buf.subarray(0, n)`만 전송합니다. 이 경우 `fill(0)`이나 전체 덮어쓰기를 먼저 해도 됩니다.
- 크기가 `Buffer.poolSize`의 절반 미만인 `allocUnsafe`와 `Buffer.from(문자열)`, `Buffer.concat()`은 내부 풀에서 잘라 쓰므로 다른 버퍼와 같은 메모리 영역을 공유합니다.
- 실행 옵션 `--zero-fill-buffers`는 새로 할당되는 모든 `Buffer`를 자동으로 0으로 채워 줍니다. 방어 수단이지만 코드가 의도를 드러내는 편이 낫습니다.
- 일반적인 코드는 `allocUnsafe`를 직접 부를 일이 거의 없습니다. `Buffer.from(string)`이나 `Buffer.concat()`이 필요한 값으로 만들어 줍니다.
- 크기에 사용자 입력을 쓸 때는 상한을 둡니다. `Buffer.alloc(userSize)`는 큰 값으로 메모리를 소진시킬 수 있습니다.

**흔한 실수:** 고정 크기 버퍼를 `allocUnsafe`로 만들어 일부만 채우고 통째로 전송하는 것입니다. 개발 중에는 이전 메모리가 우연히 0이라 문제가 보이지 않습니다.

## error 이벤트 미처리로 프로세스 종료

`EventEmitter`가 `'error'` 이벤트를 내보내는데 리스너가 하나도 없으면 에러가 그대로 던져지고, 스택이 출력되며 프로세스가 종료됩니다. 스트림, 소켓, 서버, 자식 프로세스가 모두 `EventEmitter`라서 가장 흔한 크래시 원인입니다(기초 21편).

```js
const s = createReadStream('missing.txt')
// 'error' 리스너 없음 → ENOENT가 던져져 프로세스 종료
s.on('error', (e) => console.log(e.code)) // ✅ 'ENOENT'
```

- 실행해 보면 리스너가 없는 `createReadStream('missing.txt')`는 `Emitted 'error' event on ReadStream instance`와 함께 프로세스를 종료시키고, 리스너를 달면 에러 코드를 출력하고 계속됩니다.
- `emit('error', 값)`의 값이 `Error`가 아니면 `ERR_UNHANDLED_ERROR`(`Unhandled error. ('str')`)로 감싸서 던집니다.
- 에러가 비동기로 나오므로 `try`/`catch`로는 잡을 수 없습니다. 이벤트 리스너나 `pipeline`의 콜백으로 받아야 합니다.
- `net.Socket`과 HTTP 요청·응답, 자식 프로세스(`spawn`에서 명령을 못 찾을 때 `'error'`)도 마찬가지입니다. 클라이언트가 연결을 갑자기 끊으면 서버 쪽 소켓에 `ECONNRESET`이나 `EPIPE`가 나옵니다(자세히는 19편).
- 스트림을 연결할 때는 `pipe`보다 `pipeline`을 씁니다. 에러를 한 곳으로 모으고 중간 스트림을 모두 정리합니다(자세히는 2편).
- 이벤트를 한 번만 기다릴 때는 `events.once()`가 편합니다. 기다리는 동안 `'error'`가 나오면 그 Promise가 거부됩니다.
- `process.on('uncaughtException')`는 마지막 안전망입니다. 문서는 이 이벤트 뒤에 정상 동작을 이어 가는 것은 안전하지 않다고 하며, 동기 정리를 하고 프로세스를 종료하는 데 쓰라고 안내합니다. 재시작은 외부 프로세스 관리자가 맡습니다.

**흔한 실수:** `uncaughtException`에서 로그만 남기고 계속 실행하는 것입니다. 에러가 난 객체와 자원이 불완전한 상태로 남아 이후 동작이 예측 불가능해집니다.

## 워커에 함수를 그냥 넘길 수 없음

워커 스레드는 별도의 JavaScript 실행 환경이라서 메인 스레드와 값을 공유하지 않고 복사해서 주고받습니다. `postMessage()`와 `workerData`는 구조화 복제(structured clone) 알고리즘으로 값을 복사하는데, 함수는 복제할 수 없습니다.

```js
const w = new Worker(new URL(import.meta.url))
w.postMessage({ task: (x) => x * 2 })
// DataCloneError: (x) => x * 2 could not be cloned.

w.postMessage({ task: 'double', value: 21 }) // ✅ 데이터만
```

- 함수를 넘기려 하면 `DataCloneError`입니다. `workerData`에 함수가 들어 있어도 같은 에러가 납니다.
- 해결은 "코드는 워커 파일에, 데이터는 메시지로" 나누는 것입니다. 워커 파일에 작업을 이름으로 정의해 두고, 메시지로 작업 이름과 입력값만 보냅니다.
- 구조화 복제는 프로토타입, 접근자, 열거 불가 프로퍼티를 보존하지 않습니다. 클래스 인스턴스는 일반 객체로, `Buffer`는 일반 `Uint8Array`로 도착합니다. 메서드가 필요하면 받은 쪽에서 다시 만들어 씁니다.
- 큰 데이터는 복사 비용이 있습니다. `ArrayBuffer`는 전송(transfer)하거나 `SharedArrayBuffer`로 공유할 수 있습니다.
- 워커마다 자체 `process.env` 복사본을 가집니다. 메인 스레드에서 환경변수를 바꿔도 이미 만들어진 워커에는 반영되지 않습니다.
- 워커 사용은 CPU를 오래 쓰는 작업을 이벤트 루프에서 떼어 낼 때 의미가 있습니다. 입출력 대기가 대부분인 작업은 비동기 API로 충분합니다. 워커 심화는 이 과정의 범위 밖입니다.

**흔한 실수:** `new Worker(() => { ... })`처럼 함수를 직접 넘기려는 것입니다. `Worker`는 파일 경로(또는 URL)를 받습니다. 인라인 코드가 필요하면 `eval: true` 옵션으로 문자열 코드를 쓸 수 있지만 모듈과 타입 검사를 잃으므로 별도 파일을 권장합니다.

## cluster에서 메모리 공유라고 착각

`cluster`는 같은 서버 포트를 공유하는 여러 Node.js 프로세스를 만듭니다. 워커는 `child_process.fork()`로 만들어진 별개의 프로세스이므로 메모리가 서로 완전히 분리됩니다. 한 워커가 바꾼 변수를 다른 워커나 주 프로세스가 볼 수 없습니다.

```js
let counter = 0 // 모듈 변수
// primary: counter = 0
// worker 1: counter += 100 → 100
// worker 2: counter += 100 → 100 (서로 합쳐지지 않음)
```

실행해 보면 두 워커가 각자 `counter=100`을 보고했고 주 프로세스의 `counter`는 0이었습니다.

- 요청 수 카운터, 메모리 캐시, 세션 저장소, 레이트 리미트 맵, 접속자 목록 같은 프로세스 안의 상태는 워커마다 따로 존재합니다. 같은 사용자의 연이은 요청이 서로 다른 워커로 가면 로그인 상태나 캐시가 보였다 안 보였다 합니다.
- Windows를 제외한 플랫폼에서는 연결을 라운드 로빈으로 워커에 분배하는 것이 기본입니다. 한 클라이언트의 요청이 어느 워커로 갈지 예측할 수 없다고 생각하는 것이 안전합니다.
- 공유가 필요한 상태는 Redis나 DB 같은 외부 저장소에 둡니다(자세히는 18편). 메모리 캐시는 워커 수만큼 중복되어 메모리를 더 씁니다.
- 프로세스 사이의 소통은 `worker.send()`·`process.send()`로 주고받는 메시지(IPC)입니다.
- 프로세스 격리가 필요 없으면 문서도 `worker_threads`를 권합니다. 워커 스레드는 `SharedArrayBuffer`로 메모리를 공유할 수 있습니다. 같은 프로세스 안의 스레드라 `cluster`와 다릅니다.
- 컨테이너나 오케스트레이터가 인스턴스를 여러 개 띄우는 환경에서도 상태가 분리된다는 점은 같습니다. 메모리 상태에 의존하지 않는 설계(stateless)가 확장의 전제입니다.
- 클러스터 심화는 이 과정의 범위 밖입니다.

**흔한 실수:** 단일 프로세스에서 잘 되던 인메모리 세션·캐시를 그대로 두고 워커 수만 늘리는 것입니다. 개발 중 워커 하나로 테스트하면 문제가 보이지 않다가 운영에서 간헐적으로 실패합니다.

## fetch 실패와 HTTP 4xx를 같은 것으로 착각

`fetch`가 거부(reject)되는 경우는 요청 자체가 실패했을 때뿐입니다. 서버가 404나 500을 돌려줘도 HTTP 응답을 받았으므로 `fetch`는 정상 이행되고, 상태는 `res.status`와 `res.ok`로 판단합니다(자세히는 7편).

| 상황 | `fetch` 결과 | 확인할 곳 |
|------|--------------|-----------|
| 서버가 404·500 응답 | 이행됨, `res.ok`가 `false` | `res.status`, `res.ok` |
| 연결 거부(서버가 죽음) | `TypeError: fetch failed`로 거부, `cause`에 `ECONNREFUSED` | `err.cause.code` |
| 시간 초과(`AbortSignal.timeout`) | `TimeoutError`로 거부 | `err.name` |
| 직접 취소(`abort()`) | `AbortError`로 거부 | `err.name` |

```js
async function getJson(url) {
  const signal = AbortSignal.timeout(5000)
  const res = await fetch(url, { signal })
  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
}
```

- `catch`만 있으면 404를 성공으로 처리합니다. `res.ok`(상태 코드 200–299)를 확인하지 않고 `res.json()`을 부르면, 에러 응답 본문을 정상 데이터로 파싱합니다.
- `fetch failed`의 실제 원인은 `err.cause`에 있습니다. 실행 결과 서버를 닫은 뒤 호출하면 `TypeError`, 메시지 `fetch failed`, `cause.code`가 `ECONNREFUSED`였습니다. `err.message`만 로그에 남기면 원인이 사라집니다.
- 4xx와 5xx의 처리는 다릅니다. 4xx는 요청이 잘못된 것이라 재시도해도 같은 결과이고, 5xx와 네트워크 오류, 시간 초과는 일시적일 수 있어 재시도 후보입니다(자세히는 16편).
- 에러 응답의 본문(`res.text()`)을 읽어 에러 메시지에 담으면 원인 파악이 쉽습니다.
- 시간 제한이 없으면 응답이 영영 오지 않는 요청이 쌓입니다. 모든 `fetch`에 `AbortSignal.timeout()`을 붙입니다(자세히는 6편).
- 같은 구분은 `http.request`에도 있습니다. 응답 상태는 `statusCode`에서 확인하고 `'error'` 이벤트는 연결 수준의 실패에만 옵니다.

**흔한 실수:** `try { await fetch(...) } catch { /* 실패 처리 */ }`만 쓰고 404·500을 성공으로 지나치는 것입니다. 응답을 받은 뒤 `res.ok` 확인이 두 번째 절반입니다.

## 핵심 정리

- 경로는 `node:path`로만 다루고, 확인 후 생성하는 코드는 `wx` 플래그나 `try`/`catch`로 원자적으로 바꿉니다(`exists`는 경합을 만듭니다).
- 큰 파일은 `readFile` 대신 스트림으로, 요청 처리 경로의 동기 함수(`*Sync`)는 비동기 버전으로 바꿔 이벤트 루프를 막지 않습니다.
- 테스트는 포트 0으로 서버를 띄우고 끝에 닫습니다. 프로세스가 안 끝나면 `process.getActiveResourcesInfo()`로 열린 핸들을 찾아 닫습니다.
- 환경변수는 전부 문자열이므로 `'false'`도 참입니다. 변환은 명시적으로 합니다. 자식 프로세스는 쉘을 거치는 `exec` 대신 인수 배열을 받는 `execFile`·`spawn`을 씁니다.
- `Buffer.allocUnsafe`는 이전 메모리 내용이 남아 있으므로 `Buffer.alloc`을 기본으로 씁니다. `'error'` 이벤트에는 항상 리스너를 달아야 프로세스가 죽지 않습니다.
- 워커에는 함수가 아니라 복제 가능한 데이터만 보내고, `cluster` 워커는 별개 프로세스라 메모리를 공유하지 않으며, `fetch`는 HTTP 4xx·5xx에서 거부되지 않으므로 `res.ok`를 확인합니다.

## HTTP 메시지

HTTP는 클라이언트가 요청(request) 메시지를 보내고 서버가 응답(response) 메시지로 답하는 프로토콜입니다. HTTP/1.1의 메시지는 텍스트이며 네 부분으로 이루어집니다.

1. 시작줄(요청이면 요청줄, 응답이면 상태줄)
2. 헤더(0줄 이상)
3. 빈 줄: 헤더가 끝났다는 표시
4. 본문(없을 수 있음)

시작줄과 헤더를 합쳐 헤드(head), 본문을 메시지 내용(content)이라고 부릅니다. 줄은 CRLF(`\r\n`)로 구분합니다. 아래는 Node.js 서버에 TCP로 직접 보낸 요청과 받은 응답입니다(일부 헤더 생략).

```http
GET /a?b=1 HTTP/1.1
Host: localhost:3000
X-Test: A

```

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Date: Tue, 06 Oct 2026 00:55:19 GMT
Content-Length: 2

hi
```

- 위 요청은 본문이 없어서 빈 줄로 끝납니다. 응답은 본문 `hi`가 빈 줄 뒤에 옵니다.
- HTTP/2는 같은 의미를 바이너리 프레임에 담습니다. 시작줄 대신 `:method`, `:path`, `:status` 같은 의사 헤더(pseudo-header)를 쓰고, 한 연결에서 여러 요청을 동시에 처리합니다. Node.js의 `node:http`는 HTTP/1.1을 다루며 HTTP/2는 별도 모듈입니다.
- Node.js의 `node:http` 모듈은 Stable(안정성 지수 2)이며 클라이언트와 서버를 모두 포함합니다. 메시지를 헤더와 본문으로 나누는 파싱까지만 하고, 헤더 값의 해석과 본문의 해석(JSON 등)은 하지 않습니다.
- 요청 전체나 응답 전체를 버퍼링하지 않고 스트림으로 다룹니다. 본문이 크거나 청크로 나뉘어도 처리할 수 있습니다.

## 시작줄

요청줄은 `메서드 요청대상 HTTP버전`을 공백으로 구분한 한 줄이고, 상태줄은 `HTTP버전 상태코드 이유문구`입니다.

```http
POST /users HTTP/1.1
HTTP/1.1 201 Created
```

요청 대상(request target)은 네 가지 형태가 있습니다.

| 형태 | 사용처 | 예 |
|------|--------|----|
| origin form | 가장 흔함. 경로와 쿼리 | `GET /docs?id=1 HTTP/1.1` |
| absolute form | 프록시로 보내는 요청 | `GET http://a.com/x HTTP/1.1` |
| authority form | `CONNECT`(터널링) | `CONNECT a.com:443 HTTP/1.1` |
| asterisk form | `OPTIONS`로 서버 전체 대상 | `OPTIONS * HTTP/1.1` |

- 이유문구(reason phrase)는 사람이 읽는 설명이며 선택 사항입니다. 상태 코드가 의미를 정합니다.
- Node.js에서 요청줄의 각 부분은 `req.method`, `req.url`, `req.httpVersion`으로, 상태줄은 `res.statusCode`와 `res.statusMessage`로 대응합니다.
- `req.url`에는 요청에 실린 대상 문자열만 들어 있습니다. origin form이면 경로와 쿼리(`/status?name=ryan`)이고 호스트나 프로토콜은 없습니다. 이를 `URL`로 분해하는 방법은 5편에서 다룹니다.
- `req.httpVersion`은 문자열이며 보통 `'1.1'` 또는 `'1.0'`입니다. `httpVersionMajor`와 `httpVersionMinor`는 숫자입니다.

## 헤더

헤더는 `이름: 값` 형식의 한 줄이며, 메시지에 대한 메타데이터를 담습니다. 이름은 대소문자를 구분하지 않습니다.

| 헤더 | 방향 | 의미 |
|------|------|------|
| `Host` | 요청 | 대상 호스트와 포트(HTTP/1.1에서 필수) |
| `Accept` | 요청 | 받고 싶은 응답 형식 |
| `Authorization` | 요청 | 인증 정보 |
| `User-Agent` | 요청 | 클라이언트 식별 |
| `Content-Type` | 둘 다 | 본문의 형식 |
| `Content-Length` | 둘 다 | 본문의 바이트 수 |
| `Location` | 응답 | 리다이렉트 대상 또는 새로 만든 리소스의 위치 |
| `Set-Cookie`, `Cookie` | 응답, 요청 | 쿠키(자세히는 9편) |

헤더는 종류로도 나눕니다. 요청·응답 자체의 맥락을 알리는 요청 헤더·응답 헤더가 있고, 본문의 형식과 인코딩을 설명하는 표현(representation) 헤더(`Content-Type`, `Content-Encoding`, `Content-Length`)가 있습니다.

Node.js는 받은 헤더를 `req.headers` 객체로 줍니다.

```js
console.log(req.headers)
// { host: 'localhost:3000', 'x-test': 'A' }
console.log(req.rawHeaders)
// [ 'Host', 'localhost:3000', 'X-Test', 'A' ]
```

- `req.headers`의 키는 모두 소문자이고 값은 수정되지 않습니다. 대문자로 읽으면 `undefined`입니다(`req.headers.Host`는 안 됨).
- `req.rawHeaders`는 받은 그대로의 이름과 값이 번갈아 나오는 평평한 배열입니다. 이름의 대소문자와 중복이 유지됩니다.
- `req.headersDistinct`는 병합 없이 모든 값을 문자열 배열로 줍니다.
- 같은 헤더가 여러 번 오면 이름에 따라 처리가 다릅니다.

| 헤더 | 처리 |
|------|------|
| `content-length`, `content-type`, `host`, `user-agent`, `authorization`, `location` 등 | 첫 값만 남기고 나머지는 버림 |
| `set-cookie` | 항상 배열 |
| `cookie` | `; `로 이어 붙임 |
| 그 밖의 헤더 | `, `로 이어 붙임 |

- 위 목록의 헤더도 `createServer`의 옵션 `joinDuplicateHeaders: true`를 주면 버리지 않고 `, `로 이어 붙입니다.
- 요청 헤더 전체 크기는 기본 16 KiB(`maxHeaderSize`)로 제한됩니다.
- `Host` 헤더가 없는 HTTP/1.1 요청에는 `requireHostHeader` 옵션(기본 `true`)에 따라 서버가 400을 응답합니다. 직접 보낸 `Host`가 없는 요청에서 확인했습니다.
- 응답 헤더는 `res.setHeader(name, value)`로 정하고, `Date` 헤더는 `res.sendDate`가 `true`(기본값)이면 자동으로 붙습니다(자세히는 4편).

**흔한 실수:** `req.headers['Content-Type']`처럼 대문자로 읽는 것입니다. 항상 소문자(`'content-type'`)로 읽습니다.

## 본문

본문은 빈 줄 뒤에 오는 데이터이며 없을 수도 있습니다. 어떤 형식인지는 `Content-Type`이, 어디까지가 본문인지는 `Content-Length`나 `Transfer-Encoding: chunked`가 알려 줍니다.

| 본문 종류 | 경계를 아는 방법 |
|-----------|------------------|
| 단일 리소스 | `Content-Length`로 길이를 미리 알림 |
| 청크(chunked) | `Transfer-Encoding: chunked`로 조각마다 크기를 붙여 보내고 끝을 표시(자세히는 4편) |
| 다중 리소스 | `multipart` 형식으로 여러 부분을 한 본문에 담음(파일 업로드, 11편) |

- 일반적인 본문 형식은 JSON(`application/json`), HTML(`text/html`), 폼(`application/x-www-form-urlencoded`), 멀티파트(`multipart/form-data`)입니다.
- `GET`과 `HEAD` 요청에는 보통 본문이 없습니다. 본문을 싣는 것은 주로 `POST`, `PUT`, `PATCH`입니다.
- 응답에도 본문이 없는 경우가 있습니다. `HEAD`에 대한 응답, `204`와 `304` 응답이 그렇습니다. `HEAD` 요청에 `res.end('ok')`로 본문을 써도 본문이 나가지 않는 것을 확인했습니다. `createServer`의 옵션 `rejectNonStandardBodyWrites`를 `true`로 두면 이런 응답에 본문을 쓰려는 시도가 `ERR_HTTP_BODY_NOT_ALLOWED` 에러가 됩니다.
- Node.js에서 요청 본문은 `req`를 스트림으로 읽어 얻고, 응답 본문은 `res.write()`와 `res.end()`로 씁니다. 파싱(JSON 등)은 직접 해야 합니다(4편).
- 본문 바이트 수와 `Content-Length`가 다르면 안 됩니다. 글자 수가 아니라 바이트 수입니다(`Buffer.byteLength()`).

## 메서드

메서드(method)는 요청이 대상 리소스에 하려는 동작을 나타냅니다. 서버는 의미를 따르는 것이 관례이고 Node.js가 강제하지는 않습니다.

두 가지 성질이 중요합니다. 안전(safe)한 메서드는 서버 상태를 바꾸지 않고 읽기만 합니다. 멱등(idempotent)한 메서드는 한 번 보내든 여러 번 보내든 서버에 남는 결과가 같습니다.

| 메서드 | 용도 | 안전 | 멱등 | 요청 본문 |
|--------|------|------|------|-----------|
| `GET` | 리소스 조회 | O | O | 보통 없음 |
| `HEAD` | `GET`과 같되 본문 없는 응답 | O | O | 없음 |
| `OPTIONS` | 대상이 지원하는 통신 옵션 조회 | O | O | 없음 |
| `POST` | 데이터를 제출, 생성·처리 | X | X | 있음 |
| `PUT` | 리소스를 요청 내용으로 통째로 교체 | X | O | 있음 |
| `PATCH` | 리소스 일부 수정 | X | X | 있음 |
| `DELETE` | 리소스 삭제 | X | O | 보통 없음 |
| `CONNECT` | 서버까지 터널 수립 | X | X | 있음 |
| `TRACE` | 경로 루프백 테스트 | O | O | 없음 |

- `req.method`는 문자열입니다(`'GET'`, `'DELETE'`). 읽기 전용이며 서버가 받은 요청에서만 유효합니다.
- `http.METHODS`는 Node.js의 HTTP 파서가 지원하는 메서드 이름의 배열입니다. 위 표의 메서드 외에도 `ACL`, `BIND`, `COPY` 등이 들어 있습니다.
- 지원하지 않는 메서드에는 `405 Method Not Allowed`와 `Allow` 헤더로 허용 메서드를 알립니다.
- `POST`와 `PATCH`는 멱등하지 않으므로 같은 요청을 재시도하면 결과가 중복될 수 있습니다. `GET`으로 서버 상태를 바꾸는 API를 만들지 않습니다(자세히는 8편).

## 상태 코드

상태 코드(status code)는 요청이 어떻게 처리됐는지를 알리는 3자리 숫자이며, 첫 자리로 다섯 종류로 나뉩니다.

| 범위 | 종류 | 의미 |
|------|------|------|
| 100–199 | 정보 | 요청을 받았고 계속 진행 |
| 200–299 | 성공 | 요청이 처리됨 |
| 300–399 | 리다이렉션 | 클라이언트가 추가 동작을 해야 함 |
| 400–499 | 클라이언트 오류 | 요청에 문제가 있음 |
| 500–599 | 서버 오류 | 유효한 요청을 서버가 처리하지 못함 |

자주 쓰는 코드는 다음과 같습니다.

| 코드 | 이름 | 쓰임 |
|------|------|------|
| 200 | OK | 성공 |
| 201 | Created | 리소스 생성 성공, 보통 `Location` 헤더 동반 |
| 204 | No Content | 성공했지만 본문 없음 |
| 301 | Moved Permanently | 영구 이동 |
| 302 | Found | 임시 이동 |
| 304 | Not Modified | 캐시를 그대로 사용 |
| 400 | Bad Request | 잘못된 요청 |
| 401 | Unauthorized | 인증이 필요함 |
| 403 | Forbidden | 인증은 됐지만 권한 없음 |
| 404 | Not Found | 리소스 없음 |
| 405 | Method Not Allowed | 허용되지 않는 메서드 |
| 409 | Conflict | 현재 상태와 충돌 |
| 413 | Content Too Large | 요청 본문이 한도를 넘음 |
| 415 | Unsupported Media Type | 지원하지 않는 본문 형식 |
| 429 | Too Many Requests | 요청이 너무 많음 |
| 500 | Internal Server Error | 서버 내부 오류 |
| 502 | Bad Gateway | 상위 서버로부터 잘못된 응답 |
| 503 | Service Unavailable | 서비스를 일시적으로 처리할 수 없음 |
| 504 | Gateway Timeout | 상위 서버의 응답 지연 |

- 리다이렉션에서 `303`은 `GET`으로 다시 요청하게 하고, `307`과 `308`은 메서드를 유지한 채 다시 요청하게 합니다. `308`은 영구 이동입니다.
- `101 Switching Protocols`는 `Upgrade` 요청에 응해 다른 프로토콜(WebSocket 등)로 전환할 때 씁니다(자세히는 20편).
- `http.STATUS_CODES`는 코드와 이유문구를 묶은 객체입니다(`http.STATUS_CODES[404]`는 `'Not Found'`). Node.js가 기본 `statusMessage`를 이 표에서 가져옵니다. 이 표의 일부 문구는 최신 표준 명칭과 다릅니다(확인한 것: 413은 `'Payload Too Large'`).
- `res.statusCode`의 기본값은 `200`입니다. 100–999 범위 밖의 숫자를 `writeHead()`에 주면 `RangeError`(`ERR_HTTP_INVALID_STATUS_CODE`)입니다.
- 401과 403의 구분은 "누구인지 모름"과 "누구인지 알지만 허용하지 않음"입니다(자세히는 10편).

**흔한 실수:** 에러에도 `200`으로 응답하고 본문에 에러를 담는 것입니다. 클라이언트와 중간 장치(캐시, 모니터링)는 상태 코드를 먼저 봅니다.

## http.createServer

`http.createServer([options][, requestListener])`는 HTTP 서버(`http.Server`)를 만들어 돌려줍니다. `requestListener`는 `'request'` 이벤트의 리스너로 자동 등록되며, 요청이 올 때마다 `(req, res)`로 호출됩니다. `http.Server`는 `net.Server`를 확장한 클래스입니다.

```js
import http from 'node:http'

const server = http.createServer((req, res) => {
  res.end('hello')
})
server.listen(3000, () => console.log('listening'))
```

- 한 연결(connection)에서 요청이 여러 번 올 수 있습니다(keep-alive). `'request'`는 연결이 아니라 요청마다 발생합니다.
- 리스너를 인수로 주는 대신 `server.on('request', (req, res) => {})`로 등록해도 같습니다.
- `server.listen(port[, host][, callback])`로 접속을 받기 시작합니다. 포트를 `0`으로 주면 운영체제가 남는 포트를 정해 주고, `'listening'` 이벤트 뒤에 `server.address().port`로 확인합니다. 테스트에서 포트 충돌을 피하는 방법입니다.
- `server.listening`은 현재 접속을 받는 중인지를 나타내는 불리언입니다.
- 이미 쓰는 포트에 `listen()`하면 서버에서 `'error'` 이벤트(`EADDRINUSE`)가 발생합니다.
- `server.close([callback])`는 새 연결을 받지 않고, 요청을 보내고 있거나 응답을 기다리는 중이 아닌 연결을 닫습니다(v19.0.0부터 유휴 keep-alive 연결도 닫음). 남은 연결이 모두 끝나 서버가 닫히면 `'close'`가 발생하고 콜백이 호출됩니다. `server.closeAllConnections()`는 진행 중인 것까지 모두 강제로 닫습니다.
- 첫 인수로 옵션 객체를 줄 수 있습니다. 자주 보는 옵션은 다음과 같습니다.

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `maxHeaderSize` | 16384 | 요청 헤더 최대 바이트 수 |
| `headersTimeout` | 60000 | 헤더 전체를 받는 제한 시간(ms) |
| `requestTimeout` | 300000 | 요청 전체를 받는 제한 시간(ms) |
| `keepAliveTimeout` | 65000 | 마지막 응답 뒤 연결을 유지하는 시간(ms) |
| `requireHostHeader` | `true` | `Host` 없는 HTTP/1.1 요청에 400 응답 |
| `joinDuplicateHeaders` | `false` | 중복 헤더를 버리지 않고 `, `로 결합 |
| `noDelay` | `true` | Nagle 알고리즘 비활성(v18.0.0부터 기본 `true`) |

- 타임아웃 옵션은 6편에서 자세히 다룹니다.

**흔한 실수:**

- 리스너가 `res.end()`를 호출하지 않는 것입니다. 클라이언트가 응답을 끝까지 기다립니다. 모든 응답은 반드시 끝나야 합니다.
- `async` 리스너 안에서 던진 에러를 잡지 않는 것입니다. `http`는 리스너의 반환값을 보지 않으므로 처리되지 않은 거부가 되어 프로세스가 종료됩니다(Node.js 24에서 확인). 리스너 안에서 `try/catch`로 500 응답을 만들어 줍니다.

## IncomingMessage

`http.IncomingMessage`는 서버가 받은 요청을 나타내는 객체이며 `'request'` 이벤트의 첫 인수 `req`입니다. 클라이언트가 받은 응답도 이 클래스입니다(6편). `stream.Readable`을 상속하므로 본문이 스트림으로 들어옵니다.

```js
http.createServer((req, res) => {
  console.log(req.method)      // 'GET'
  console.log(req.url)         // '/a?b=1'
  console.log(req.httpVersion) // '1.1'
  console.log(req.headers.host)
  res.end()
})
```

| 속성 | 의미 |
|------|------|
| `method` | 요청 메서드(서버 요청에서만 유효) |
| `url` | 요청 대상 문자열(서버 요청에서만 유효) |
| `httpVersion` | HTTP 버전 문자열 |
| `headers`, `rawHeaders`, `headersDistinct` | 헤더(앞의 헤더 절) |
| `trailers`, `rawTrailers` | 본문 뒤에 오는 트레일러. `'end'` 이후에 채워짐 |
| `socket` | 연결을 나타내는 `net.Socket` |
| `complete` | 완전한 메시지를 받아 파싱했으면 `true` |
| `statusCode`, `statusMessage` | 클라이언트가 받은 응답에서만 유효 |

- `req`는 소켓이 아닙니다. 소켓은 `req.socket`이며 `stream.Duplex`의 하위 클래스입니다. keep-alive에서는 같은 소켓으로 여러 요청이 오고 요청마다 `IncomingMessage`가 따로 만들어지기 때문에 둘을 분리합니다.
- `req.socket`으로 연결 정보(`remoteAddress` 등)를 얻습니다(자세히는 4편).
- `req.destroy()`는 요청을 받은 소켓을 `destroy()`합니다.
- `'close'` 이벤트는 요청이 끝났을 때 발생합니다(v16.0.0부터 소켓이 닫힐 때가 아님). `'aborted'` 이벤트와 `req.aborted`는 Deprecated이므로 `'close'`와 `req.destroyed`를 씁니다.
- `req.signal`은 요청이 완료 전에 파괴되거나 소켓이 먼저 닫히면 중단되는 `AbortSignal`입니다(v24.16.0 추가). 클라이언트가 끊었을 때 DB 쿼리나 `fetch`를 취소하는 데 씁니다.

## ServerResponse

`http.ServerResponse`는 서버가 클라이언트에 보낼 응답을 쓰는 객체이며 `'request'` 이벤트의 두 번째 인수 `res`입니다. 서버가 내부적으로 만들며 직접 `new`하지 않습니다. `OutgoingMessage`를 상속하고 `write()`와 `end()`로 본문을 씁니다.

```js
http.createServer((req, res) => {
  res.statusCode = 200
  res.setHeader('Content-Type', 'text/plain; charset=utf-8')
  res.end('hello')
})
// 응답: 200 OK, Content-Type, Date, Content-Length: 5 헤더와
// 본문 hello (헤더 값은 자동 계산)
```

| 멤버 | 역할 |
|------|------|
| `statusCode`, `statusMessage` | 상태줄. 기본 `200`, 이유문구는 `STATUS_CODES`에서 |
| `setHeader()`, `getHeader()`, `hasHeader()`, `removeHeader()`, `getHeaders()` | 헤더를 보내기 전에 읽고 바꿈. 이름은 대소문자 무시 |
| `headersSent` | 헤더가 이미 나갔는지 |
| `writeHead()` | 상태 코드와 헤더를 한 번에 지정 |
| `write()` | 본문 조각을 씀 |
| `end()` | 응답을 끝냄. 모든 응답에서 반드시 호출 |

- 헤더를 따로 보내지 않고 `write()`나 `end()`를 호출하면 `statusCode`와 `setHeader()`로 쌓아 둔 값으로 헤더가 자동으로 전송됩니다(암시적 헤더 모드). `res.end('hello')`만으로 `Content-Length: 5`가 붙는 것을 확인했습니다.
- `writeHead()`로 명시한 헤더는 `setHeader()` 값과 합쳐지며 `writeHead()` 쪽이 우선합니다.
- `'finish'`는 응답의 마지막 부분을 운영체제에 넘겼을 때 발생하며 클라이언트가 받았다는 뜻이 아닙니다. `'close'`는 응답이 끝났거나 연결이 중간에 끊겼을 때 발생합니다.
- `res.req`는 원본 요청, `res.socket`은 연결입니다. `req.socket`과 `res.socket`은 같은 객체입니다.
- 공식 문서는 응답을 Writable 스트림의 예로 듭니다. `write()`가 `false`를 돌려주면 `'drain'`을 기다리는 backpressure 규칙을 같은 방식으로 따르고(2편), `pipeline()`의 목적지로 쓸 수 있습니다. 다만 상속 구조는 `stream.Writable`이 아니라서 `res instanceof Writable`은 `false`였습니다(확인).
- 헤더를 보낸 뒤에는 헤더를 바꿀 수 없어 `setHeader()`가 `ERR_HTTP_HEADERS_SENT` 에러를 냅니다. `end()`한 뒤 `write()`하면 `ERR_STREAM_WRITE_AFTER_END` 에러입니다(자세히는 4편).
- `res.sendDate`(기본 `true`)는 `Date` 헤더를 자동으로 붙입니다. 테스트가 아니면 끄지 않습니다.
- `res.strictContentLength`를 `true`로 두면 `Content-Length` 값과 실제 본문 바이트 수가 다를 때 `ERR_HTTP_CONTENT_LENGTH_MISMATCH` 에러가 납니다(v18.10.0 추가, 기본 `false`).

## 핵심 정리

- HTTP/1.1 메시지는 시작줄, 헤더, 빈 줄, 본문으로 이루어지며 Node.js의 `http`는 이를 헤더와 본문으로 나누기까지만 하고 내용은 해석하지 않습니다.
- 요청줄은 메서드·요청 대상·버전이고(`req.method`, `req.url`, `req.httpVersion`), 상태줄은 버전·상태 코드·이유문구입니다(`res.statusCode`, `res.statusMessage`).
- `req.headers`의 키는 항상 소문자이고, 중복 헤더는 이름에 따라 버리거나 이어 붙이거나 배열로 둡니다. 원본은 `rawHeaders`에 있습니다.
- 메서드는 안전·멱등 성질로 구분하고, 상태 코드는 첫 자리로 정보·성공·리다이렉션·클라이언트 오류·서버 오류를 나눕니다.
- `http.createServer()`의 리스너는 요청마다 `(req, res)`로 호출되고 모든 응답은 `res.end()`로 끝나야 하며, `server.listen(0)`으로 임의 포트를 얻을 수 있습니다.
- `req`(IncomingMessage)는 소켓과 분리된 Readable이며, `res`(ServerResponse)는 상태줄·헤더·본문을 쓰는 객체입니다.

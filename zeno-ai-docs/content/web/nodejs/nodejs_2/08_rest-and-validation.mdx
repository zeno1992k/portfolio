## REST

REST(Representational State Transfer)는 분산 시스템을 효율적이고 확장 가능하게 만드는 아키텍처 제약의 모음입니다. 리소스를 표현(representation)으로 주고받는다는 것이 핵심 발상입니다. 실무에서 "REST API"는 HTTP 메서드·URL·상태 코드로 리소스를 다루는 HTTP API를 느슨하게 가리키는 말로 쓰이고, 모든 제약을 지키지는 않는 경우가 많습니다.

Fielding의 논문이 꼽는 제약은 다음과 같습니다.

| 제약 | 의미 |
|------|------|
| 클라이언트-서버 | 관심사를 분리 |
| 무상태(stateless) | 요청 하나에 이해에 필요한 정보가 모두 들어 있고, 서버가 저장한 문맥에 기대지 않음 |
| 캐시 | 응답이 캐시 가능한지 표시 |
| 균일한 인터페이스 | 리소스 식별, 표현을 통한 조작, 자기 서술적 메시지, 하이퍼미디어 |
| 계층화 시스템 | 프록시·게이트웨이를 끼워도 인터페이스가 변하지 않음 |

HTTP 메서드는 리소스에 대한 동작을 표준화합니다.

| 메서드 | 의미 | 안전 | 멱등 |
|--------|------|------|------|
| `GET` | 조회 | O | O |
| `POST` | 생성·처리 | X | X |
| `PUT` | 전체 교체(없으면 생성) | X | O |
| `PATCH` | 부분 수정 | X | 보장 안 됨 |
| `DELETE` | 삭제 | X | O |

- 안전(safe)은 서버 상태를 바꾸지 않는다는 뜻이고, 멱등(idempotent)은 같은 요청을 여러 번 보내도 서버에 미치는 효과가 한 번과 같다는 뜻입니다(아래 `멱등성` 절).
- `PUT`은 리소스 전체를 교체하고 `PATCH`는 수정 지시를 보냅니다. HTTP 메서드와 데이터베이스 CRUD는 일대일 대응이 아닙니다.
- 무상태 제약은 세션을 서버에 저장하지 않는 토큰 방식과 이어집니다(자세히는 10편).

## 리소스

리소스는 URL로 식별하는 명사 단위의 대상입니다. URL에는 명사를 쓰고 동작은 HTTP 메서드로 표현합니다.

| 목적 | 요청 |
|------|------|
| 목록 조회 | `GET /users` |
| 생성 | `POST /users` |
| 단건 조회 | `GET /users/42` |
| 전체 교체 | `PUT /users/42` |
| 부분 수정 | `PATCH /users/42` |
| 삭제 | `DELETE /users/42` |
| 하위 목록 | `GET /users/42/orders` |

```text
❌ POST /createUser, GET /getUser?id=42
✅ POST /users,      GET /users/42
```

- 컬렉션은 복수 명사(`/users`)로 쓰고 개별 항목은 그 아래 식별자(`/users/42`)로 가리키는 것이 관례입니다.
- 식별자와 계층은 경로에, 필터·정렬·페이지는 쿼리에 둡니다(`GET /users?role=admin&sort=name`).
- 중첩은 두세 단계로 제한합니다. `/users/42/orders/7`까지는 읽히지만 더 깊어지면 `/orders/7`처럼 최상위 리소스로 끌어올립니다.
- CRUD에 맞지 않는 동작은 하위 리소스를 만들어 `POST`로 처리합니다. 주문 취소는 `POST /orders/7/cancellation`처럼 씁니다.
- URL은 한번 공개하면 바꾸기 어려운 계약입니다. 내부 구현(테이블 이름)이 아니라 도메인 용어로 짓습니다.
- 경로를 직접 나누는 방법은 05편에서 다뤘습니다.

## JSON API

JSON API는 요청과 응답 본문을 JSON으로 주고받는 HTTP API입니다. 헤더로 형식을 명시하고 응답 보내기는 한 함수로 모읍니다.

```js
function sendJson(res, status, body, headers = {}) {
  const json = JSON.stringify(body)
  res.writeHead(status, {
    'Content-Type': 'application/json; charset=utf-8',
    'Content-Length': Buffer.byteLength(json),
    ...headers,
  })
  res.end(json)
}
```

- `Content-Length`에는 글자 수가 아니라 바이트 수를 넣어야 합니다. `'한글'`은 2글자지만 6바이트입니다(`Buffer.byteLength`).
- 요청 쪽에서는 `Content-Type`이 `application/json`인지 확인합니다. 아니면 415 Unsupported Media Type입니다. 본문이 JSON으로 파싱되지 않으면 400입니다.

```js
class HttpError extends Error {
  constructor(status, detail) {
    super(detail)
    this.status = status
  }
}
```

```js
async function readJson(req) {
  const type = req.headers['content-type'] ?? ''
  if (!type.startsWith('application/json'))
    throw new HttpError(415, 'JSON only')
  const chunks = []
  for await (const c of req) chunks.push(c)
  const text = Buffer.concat(chunks).toString()
  try { return JSON.parse(text) }
  catch { throw new HttpError(400, 'Malformed JSON') }
}
```

본문을 읽고 크기를 제한하는 방법은 04편에서 다뤘습니다. 위 코드는 설명을 위해 크기 제한을 생략했습니다.

JSON에는 표현의 함정이 있습니다. 실행해서 확인한 결과입니다.

| 값 | `JSON.stringify` 결과 |
|----|----------------------|
| `new Date(0)` | `"1970-01-01T00:00:00.000Z"` (ISO 8601 문자열) |
| `{ a: undefined, b: null }` | `{"b":null}` (`undefined`는 사라짐) |
| `{ n: 10n }` | `TypeError: Do not know how to serialize a BigInt` |
| `12345678901234567890` | `12345678901234567000` (안전한 정수 범위를 넘으면 정밀도 손실) |

- JSON에는 날짜 타입이 없어서 ISO 8601 문자열로 주고받습니다. 시간대가 있는 형식(`Z` 또는 오프셋)을 씁니다.
- 아주 큰 정수나 BigInt는 문자열로 보냅니다.
- 값이 없음을 `null`로 보낼지 필드를 생략할지는 API 전체에서 하나로 정합니다.
- 최상위를 배열 대신 객체로 감싸면(`{ "data": [...] }`) 나중에 `nextCursor` 같은 필드를 덧붙여도 형식이 깨지지 않습니다.
- 필드 이름 스타일(`camelCase`)과 오류·목록의 모양은 모든 엔드포인트에서 같아야 합니다.

## 상태 코드 고르기

응답 상태 코드는 성공·클라이언트 오류·서버 오류를 알리는 첫 신호입니다. 4xx는 클라이언트가 잘못한 것으로 보일 때, 5xx는 서버가 오류를 인지했을 때 씁니다.

| 상황 | 코드 |
|------|------|
| 조회·수정 성공, 결과를 본문으로 | 200 OK |
| 생성 성공 | 201 Created + `Location` 헤더 |
| 접수했고 처리는 나중에 | 202 Accepted |
| 성공했고 보낼 본문 없음(`DELETE`, `PUT`) | 204 No Content |
| 요청 문법·형식 오류 | 400 Bad Request |
| 인증 없음·실패 | 401 Unauthorized |
| 인증됐지만 권한 없음 | 403 Forbidden |
| 대상 리소스 없음 | 404 Not Found |
| 경로는 있으나 메서드 미지원 | 405 + `Allow` 헤더 |
| 현재 상태와 충돌(중복 등) | 409 Conflict |
| 지원하지 않는 `Content-Type` | 415 Unsupported Media Type |
| 문법은 맞지만 의미상 처리 불가(검증 실패) | 422 Unprocessable Content |
| 요청이 너무 많음 | 429 + `Retry-After` |
| 서버 내부 오류 | 500 Internal Server Error |
| 업스트림 오류·시간 초과 | 502, 504 (06편) |
| 일시적 과부하·점검 | 503 + `Retry-After` |

- 201은 새 리소스를 요청 URL이나 `Location`으로 찾을 수 있어야 합니다. `Location: /users/1`이 대표적입니다.
- 204는 본문과 `Content-Length` 헤더를 넣지 않습니다. 첫 번째 `DELETE`는 204, 이미 지워진 대상에 보내는 두 번째 `DELETE`는 404가 되는 설계가 흔한데, 응답이 달라도 서버 상태의 효과는 같아 멱등으로 취급합니다.
- 405는 `Allow` 헤더를 반드시 보냅니다(05편).
- 404는 접근 권한이 없는 리소스의 존재를 숨기고 싶을 때 403 대신 쓸 수 있습니다.
- `Retry-After`는 재시도까지 기다릴 시간을 알려 줍니다(429, 503).

**흔한 실수:** 오류도 `200`으로 보내고 본문에 `{ "success": false }`를 담는 것입니다. 클라이언트의 `res.ok`가 `true`가 되고(07편) 캐시와 모니터링이 오류를 성공으로 셉니다. 상태 코드와 본문이 모순되면 안 됩니다.

## 검증

검증은 서버가 외부에서 받은 입력을 처리하기 전에 형식과 규칙에 맞는지 확인하는 일입니다. 서버는 클라이언트를 신뢰하지 않으므로 본문, 쿼리, 경로 매개변수, 헤더 모두 요청이 들어오는 입구에서 한 번 검증합니다.

| 단계 | 확인할 것 | 실패 시 |
|------|-----------|---------|
| 구문 | 본문이 JSON으로 파싱되는가, `Content-Type`이 맞는가 | 400, 415 |
| 구조·타입 | 필드 존재, 타입, 길이, 범위, 형식 | 422 (또는 400) |
| 의미·상태 | 이메일 중복, 재고 부족 같은 비즈니스 규칙 | 409, 422 |

- TypeScript 타입은 컴파일 때만 있고 런타임에는 사라집니다. 외부 입력은 타입이 있어도 반드시 런타임에 검증해야 합니다.
- 오류는 첫 번째에서 멈추지 말고 모두 모아 한 번에 돌려줍니다. 클라이언트가 고칠 때마다 반복해서 요청하게 만들지 않기 위해서입니다.
- 알 수 없는 필드는 거부하거나 제거하고, 그대로 저장하지 않습니다. 클라이언트가 `{ "role": "admin" }`을 몰래 끼워 넣어 권한을 올리는 일을 막기 위해서입니다.
- 검증한 뒤의 값(변환·기본값이 적용된 값)을 이후 코드에서 씁니다. 원본 본문을 다시 쓰면 검증이 무의미해집니다.
- 쿼리와 경로 값은 항상 문자열이므로 숫자 변환 뒤에 검증합니다(05편).

## 400과 422

400 Bad Request는 요청을 이해할 수 없을 때(구문·형식 오류), 422 Unprocessable Content는 구문은 올바르지만 내용을 처리할 수 없을 때 씁니다. RFC 9110은 422를 "내용 형식은 지원되고(그래서 415가 아니고) 구문도 올바르지만(그래서 400이 아니고) 담긴 지시를 처리할 수 없는" 경우로 정의합니다.

| 상황 | 코드 |
|------|------|
| 본문이 깨진 JSON | 400 |
| 쿼리 문자열이나 필수 헤더 형식이 잘못됨 | 400 |
| `Content-Type`이 `text/plain` | 415 |
| JSON은 올바르지만 `email` 형식이 틀림, `age`가 음수 | 422 |

- 400과 422의 경계는 팀 규칙입니다. 검증 실패에도 400을 쓰는 API가 많고 어느 쪽이든 틀린 것은 아닙니다. 중요한 것은 한 API 안에서 일관되게 쓰는 것이고, 문서(OpenAPI)에 적는 것입니다.
- 두 코드 모두 같은 요청을 고치지 않고 다시 보내면 같은 오류가 납니다.
- 422의 공식 이름은 "Unprocessable Content"(RFC 9110)입니다. Node 24.15의 `http.STATUS_CODES[422]`는 이전 이름인 `'Unprocessable Entity'`를 돌려줍니다. 클라이언트는 숫자 코드를 기준으로 처리합니다.

## 401과 403

401 Unauthorized는 유효한 인증 자격이 없다는 응답이고, 403 Forbidden은 서버가 요청을 이해했지만 수행하기를 거부한다는 응답입니다. 이름과 달리 401이 인증(authentication) 문제입니다.

```js
// 토큰이 없거나 유효하지 않음
res.writeHead(401, { 'WWW-Authenticate': 'Bearer' })
res.end()

// 로그인은 됐지만 관리자가 아님
sendJson(res, 403, { title: 'Forbidden' })
```

| 구분 | 401 | 403 |
|------|-----|-----|
| 의미 | 인증이 없거나 틀림 | 인증은 됐지만 권한이 없음 |
| 필수 헤더 | `WWW-Authenticate`로 방식을 알림 | 없음 |
| 클라이언트의 다음 행동 | 새 자격으로 다시 시도 가능 | 같은 자격으로는 재시도해도 소용없음 |

- RFC 9110은 401 응답이 `WWW-Authenticate` 헤더를 보내야 한다고 정합니다.
- 리소스가 있다는 사실 자체를 숨기고 싶다면 403 대신 404를 보내도 됩니다.
- 인증 방법(세션·JWT)과 권한 검사(RBAC)는 10편에서 다룹니다.

## Zod 스키마 검증

Zod는 TypeScript용 스키마 검증 라이브러리로, 스키마 하나로 런타임 검증과 정적 타입을 함께 얻습니다. 아래는 Zod 4(npm 최신 4.6.5에서 실행 확인) 기준입니다.

```js
import * as z from 'zod'

const CreateUser = z.object({
  name: z.string().min(1).max(50),
  email: z.email(),
  age: z.int().min(0).optional(),
})

const result = CreateUser.safeParse(body)
if (!result.success) {
  // result.error.issues: 위반 목록
}
const data = result.data // 검증을 통과한 값
```

실행해서 확인한 결과입니다.

| 입력 | 결과 |
|------|------|
| `{ name: 'kim', email: 'a@b.co', extra: 1 }` | 성공. `extra`는 제거됨 |
| `{ name: '', email: 'x', age: 1.5 }` | 실패. `name`, `email`, `age` 세 개의 `issues` |
| 문자열 `'not object'` | 실패. `Invalid input: expected object, received string` |

- `parse()`는 실패하면 `ZodError`를 던지고, `safeParse()`는 `{ success, data }` 또는 `{ success: false, error }`를 돌려줍니다. 서버 입구에서는 던지지 않는 `safeParse()`가 다루기 쉽습니다.
- `error.issues`의 각 항목은 `code`, `path`(필드 경로 배열), `message`를 가집니다. 이를 응답의 오류 목록으로 바꿉니다(아래 `에러 응답 형식` 절).
- 객체 스키마는 알 수 없는 키를 기본으로 제거(strip)합니다. 거부하려면 `z.strictObject()`를 쓰고(`unrecognized_keys` 이슈), 통과시키려면 `z.looseObject()`입니다.
- 오류 가공 도구가 있습니다. `z.treeifyError(error)`는 스키마 모양의 중첩 객체, `z.flattenError(error)`는 `{ formErrors, fieldErrors }`의 평평한 객체, `z.prettifyError(error)`는 사람이 읽는 문자열을 만듭니다.
- TypeScript에서는 `type CreateUserInput = z.infer<typeof CreateUser>`로 같은 스키마에서 타입을 얻습니다.
- 비동기 검증(`async` refinement)이 있는 스키마는 `parseAsync()`와 `safeParseAsync()`를 씁니다.

쿼리스트링은 문자열이라 `z.coerce`로 변환하면서 검증합니다.

```js
const ListQuery = z.object({
  limit: z.coerce
    .number().int().min(1).max(100).default(20),
  cursor: z.coerce.number().int().min(0).default(0),
})
const raw = Object.fromEntries(url.searchParams)
ListQuery.safeParse(raw).data // { limit: 20, cursor: 0 }
```

- `?limit=50`은 숫자 50으로, 생략하면 기본값 20으로 바뀝니다. `?limit=1000`은 최대값 위반, `?cursor=abc`는 `NaN`이라 실패합니다.
- `z.coerce`는 JavaScript의 변환 규칙을 그대로 씁니다. `z.coerce.number()`는 `null`과 빈 문자열을 `0`으로, `z.coerce.boolean()`은 문자열 `'false'`를 `true`로 바꿉니다(실행 확인). 불리언 쿼리와 환경 변수는 직접 문자열을 비교하는 변환을 씁니다(자세히는 27편).
- 같은 스키마를 JSON Schema로 내보낼 수도 있습니다(아래 `OpenAPI 개념` 절).

## 멱등성

멱등성(idempotency)은 같은 요청을 여러 번 보내도 서버에 미치는 효과가 한 번 보낸 것과 같은 성질입니다. RFC 9110에서 `PUT`, `DELETE`, 그리고 안전한 메서드(`GET`, `HEAD`, `OPTIONS`)는 멱등이고 `POST`와 `PATCH`는 그렇지 않습니다.

- 응답까지 같아야 하는 것은 아닙니다. 첫 `DELETE`는 200이고 이어지는 `DELETE`는 404일 수 있습니다. 멱등은 의도된 효과가 같다는 뜻입니다.
- 멱등 메서드는 응답을 받기 전에 연결이 끊겼을 때 자동으로 다시 보낼 수 있습니다. 비멱등 메서드(`POST`)는 요청이 적용되지 않았음을 알거나 멱등임을 알 때만 자동 재시도합니다. 06편에서 본 유휴 연결의 `ECONNRESET` 재시도도 멱등한 요청에만 합니다.
- 응답을 못 받은 `POST /payments`를 다시 보내면 이중 결제가 날 수 있습니다. 이를 막으려고 `Idempotency-Key` 헤더로 `POST`를 멱등하게 만듭니다.

```js
const key = req.headers['idempotency-key']
const fp = JSON.stringify(parsed.data)
if (key && seen.has(key)) {
  const prev = seen.get(key)
  if (prev.fp !== fp) throw new HttpError(422, 'Key reused')
  return sendJson(res, prev.status, prev.body)
}
// ... 처음 보는 요청이면 처리한 뒤
if (key) seen.set(key, { fp, status: 201, body: user })
```

| 상황 | 응답 |
|------|------|
| 처음 보는 키 | 정상 처리하고 결과를 저장 |
| 같은 키, 같은 내용으로 재요청 | 저장해 둔 이전 결과를 그대로 반환 (실행 확인: 같은 `id: 2`) |
| 같은 키, 다른 내용 | 422 (실행 확인) |
| 같은 키의 요청이 아직 처리 중 | 409 Conflict |

- `Idempotency-Key`는 IETF 인터넷 드래프트(draft-ietf-httpapi-idempotency-key-header-07)이고 아직 표준이 아닙니다. 드래프트는 키를 클라이언트가 UUID 같은 고유한 값으로 만들고, 같은 키를 다른 요청 내용에 재사용하지 말라고 정합니다. 서버는 키의 만료 정책을 문서로 공개해야 합니다.
- 위 코드의 `Map`은 단일 프로세스 메모리라서 서버를 재시작하거나 여러 대로 늘리면 사라집니다. 운영에서는 Redis나 데이터베이스에 키를 저장합니다(자세히는 18편).
- 키를 저장하는 일과 요청 처리가 원자적이지 않으면 동시에 도착한 두 요청이 모두 처리될 수 있으므로 저장소의 원자적 연산이나 유니크 제약으로 막아야 합니다.

## 페이지네이션 규약

페이지네이션은 큰 목록을 나눠서 돌려주는 규칙입니다. 표준 쿼리 이름은 정해져 있지 않으므로 API 안에서 하나로 정해 문서화합니다.

| 방식 | 요청 | 특징 |
|------|------|------|
| 오프셋 | `?page=3&limit=20` 또는 `?offset=40&limit=20` | 임의의 쪽으로 점프 가능. 중간에 항목이 추가·삭제되면 중복·누락 발생 |
| 커서 | `?cursor=abc&limit=20` | 마지막으로 본 항목 뒤부터 이어서 가져옴. 쪽 번호로 점프 불가 |

최신순 목록 `[6, 5, 4, 3, 2, 1]`을 3개씩 나눠 가져오는 중에 첫 쪽을 받고 새 항목 7이 추가된 경우를 실행해 보았습니다.

| 방식 | 두 번째 쪽 결과 |
|------|-----------------|
| 오프셋 (3번째부터 3개) | `[4, 3, 2]` — 첫 쪽의 `4`가 중복 |
| 커서 (마지막으로 본 `4`보다 작은 것) | `[3, 2, 1]` — 중복도 누락도 없음 |

```js
const ListQuery = z.object({
  limit: z.coerce
    .number().int().min(1).max(100).default(20),
  cursor: z.coerce.number().int().min(0).default(0),
})
// ... 검증 뒤
const after = users.filter((u) => u.id > cursor)
const page = after.slice(0, limit)
const next = page.length === limit ? page.at(-1).id : null
sendJson(res, 200, { data: page, nextCursor: next })
```

- `limit`에는 기본값과 상한을 둡니다. 상한이 없으면 `?limit=1000000` 한 번에 서버가 무너집니다. 위 실행에서 `limit=1000`은 400으로 거부되었습니다.
- 커서는 정렬 기준이 고유하고 안정적이어야 합니다. 정렬 기준이 같은 값이 많으면 `(생성 시각, id)`처럼 합쳐서 정합니다.
- 응답은 `{ data, nextCursor }`처럼 객체로 감싸고 다음 쪽이 없으면 `nextCursor`가 `null`입니다.
- 링크로 알릴 때는 `Link` 헤더(RFC 8288)에 `rel`로 관계를 씁니다. 예: `Link: <https://api.example.com/users?cursor=20>; rel="next"`.
- 전체 개수(`total`)는 매번 세어야 해서 비용이 큽니다. 필요한 API에서만 제공합니다.
- 오프셋과 커서를 SQL로 구현하는 방법은 데이터베이스 편에서 다룹니다(자세히는 17편).

## 에러 응답 형식(RFC 9457)

RFC 9457의 "problem details"는 HTTP API 오류 응답을 기계가 읽을 수 있는 하나의 형식으로 정한 표준입니다. 오류 형식을 API마다 새로 만들 필요가 없게 하려는 것이고, RFC 7807을 대체합니다. 미디어 타입은 `application/problem+json`입니다.

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://example.com/probs/validation",
  "title": "Your request is not valid.",
  "status": 422,
  "detail": "2 fields failed validation.",
  "instance": "/users",
  "errors": [
    { "pointer": "/email", "detail": "Invalid email" }
  ]
}
```

| 멤버 | 의미 |
|------|------|
| `type` | 문제 유형을 식별하는 URI. 없으면 `about:blank`. 가능하면 절대 URI |
| `title` | 문제 유형의 짧은 요약. 같은 유형이면 매번 같아야 함 |
| `status` | HTTP 상태 코드. 실제 응답 상태와 같아야 함 |
| `detail` | 이번 발생에 대한 설명. 클라이언트가 고칠 수 있게 돕는 내용 |
| `instance` | 이번 발생을 가리키는 URI |
| 확장 멤버 | `errors`, `balance` 등 유형별로 덧붙이는 필드 |

- 클라이언트는 모르는 확장 멤버를 무시해야 하므로 필드를 추가해도 하위 호환이 유지됩니다.
- `detail` 문자열을 파싱해서 정보를 얻으라고 하지 않습니다. 필요한 정보는 확장 멤버로 줍니다. RFC 예제는 검증 오류를 `errors` 배열에 `detail`과 JSON Pointer(`pointer`)로 담습니다.
- 스택 트레이스, SQL, 내부 경로 같은 구현 내부를 오류 응답에 넣지 않습니다. RFC도 구현 세부 정보 노출의 위험을 경고합니다.
- `type`을 생략하거나 `about:blank`로 두면 `title`은 HTTP 상태 문구와 같아야 합니다(SHOULD). 자체 `title`을 쓰려면 자체 `type` URI를 정합니다.

Zod 이슈를 이 형식으로 바꿔 보내는 코드입니다.

```js
import http from 'node:http'

function sendProblem(res, status, problem = {}) {
  const body = JSON.stringify({
    type: 'about:blank',
    title: http.STATUS_CODES[status],
    status,
    ...problem,
  })
  res.writeHead(status, {
    'Content-Type': 'application/problem+json',
    'Content-Length': Buffer.byteLength(body),
  })
  res.end(body)
}
```

```js
const pointer = (path) => '/' + path.join('/')
const errors = result.error.issues.map((i) => ({
  pointer: pointer(i.path),
  detail: i.message,
}))
sendProblem(res, 422, {
  type: 'https://example.com/probs/validation',
  title: 'Your request is not valid.',
  errors,
})
```

`{ name: '', email: 'x', age: -1 }`을 보냈을 때 `errors`에는 필드마다 `pointer`(`/name`, `/email`, `/age`)와 `detail`(예: `Invalid email address`)이 담겼습니다. 구문 오류는 `detail`만 채웁니다.

```json
{ "type": "about:blank", "title": "Bad Request",
  "status": 400, "detail": "Malformed JSON" }
```

- 서버의 모든 오류(400, 401, 404, 409, 500)를 같은 함수로 보내면 클라이언트가 오류 처리를 한 곳에서 합니다.
- 핸들러 바깥의 `catch`에서 `HttpError`는 `sendProblem(res, err.status, { detail: err.message })`로, 그 밖의 예외는 로그를 남기고 `sendProblem(res, 500)`으로 처리합니다. 예외 메시지를 그대로 내보내지 않습니다.

## OpenAPI 개념

OpenAPI Specification(OAS)은 HTTP API를 프로그래밍 언어와 무관한 형식(JSON 또는 YAML)으로 기술하는 표준입니다. 소스 코드나 네트워크 트래픽을 보지 않고도 사람과 도구가 API의 기능을 이해하게 합니다. 이 문서 작성 시점의 최신 버전은 3.2.1입니다.

```yaml
openapi: 3.1.0
info:
  title: Users API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        '200': { description: OK }
        '404': { description: Not Found }
```

| 최상위 필드 | 내용 |
|-------------|------|
| `openapi` | 사용한 OAS 버전 |
| `info` | API 이름, 버전 등 메타데이터 |
| `paths` | 경로와 그 아래 오퍼레이션(`get`, `post` 등) |
| `components` | 재사용할 스키마·응답·매개변수 정의 |

- 오퍼레이션은 `parameters`(경로·쿼리·헤더), `requestBody`, `responses`(상태 코드별 응답)를 기술합니다. 경로 매개변수는 `required: true`여야 합니다.
- 스키마 객체는 JSON Schema 2020-12의 상위 집합이라서 요청·응답의 모양을 JSON Schema로 적습니다. Zod 4는 `z.toJSONSchema()`로 같은 스키마를 JSON Schema로 내보냅니다. `CreateUser`를 변환하면 `required: ['name', 'email']`, `email`의 `format: 'email'`, `age`의 `type: 'integer'`가 나옵니다(실행 확인). 이를 OpenAPI 문서의 `components`에 넣을 수 있습니다.
- 문서로 쓰면(Swagger UI 같은 도구가 렌더링) 개발자가 API를 탐색하고, 같은 문서로 클라이언트 코드·서버 틀을 생성하고, 목 서버와 계약 테스트를 만들 수 있습니다.
- 만드는 방식은 두 가지입니다. 코드에서 문서를 뽑는 코드 우선(code-first)은 NestJS의 Swagger 모듈이 대표적입니다(자세히는 15편). 문서를 먼저 쓰고 코드를 맞추는 설계 우선(design-first)도 있습니다.
- 문서와 구현이 어긋나면 문서가 거짓말이 됩니다. 검증 스키마에서 문서를 생성하거나 테스트로 일치를 확인합니다(테스트는 24편).

## 핵심 정리

- URL은 명사(리소스), 동작은 HTTP 메서드로 표현하고, JSON 응답은 `Content-Type`·바이트 길이·날짜 형식·객체 래핑을 일관되게 지킵니다.
- 상태 코드는 상황에 맞게 고르고 오류를 200으로 보내지 않습니다. 생성은 201과 `Location`, 본문 없는 성공은 204입니다.
- 모든 외부 입력은 입구에서 한 번 검증하고 오류는 모아서 돌려주며, Zod의 `safeParse`와 `z.coerce`로 구조와 변환을 함께 처리합니다.
- 400은 구문·형식, 422는 의미상 처리 불가에 쓰고(일관성이 핵심), 401은 인증 실패와 `WWW-Authenticate`, 403은 인증된 사용자의 권한 부족입니다.
- `PUT`, `DELETE`는 멱등이고 `POST`는 `Idempotency-Key`(드래프트)로 멱등하게 만들며, 페이지네이션은 `limit` 상한과 안정적인 정렬을 갖추고 변화가 잦은 목록에는 커서 방식이 안전합니다.
- 오류 본문은 RFC 9457의 `application/problem+json` 형식으로 통일하고, API는 OpenAPI로 기술합니다.

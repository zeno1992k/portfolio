## req.method

`req.method`는 요청 메서드 문자열입니다(`'GET'`, `'POST'`). 읽기 전용이고 서버가 받은 요청에서만 유효합니다. 표준 메서드는 대문자이므로 대문자 문자열과 비교합니다.

```js
if (req.method !== 'GET' && req.method !== 'HEAD') {
  res.writeHead(405, { Allow: 'GET, HEAD' })
  return res.end()
}
```

- 처리하지 않는 메서드에는 `405`와 허용하는 메서드를 알리는 `Allow` 헤더를 보냅니다.
- `HEAD`는 `GET`과 같은 경로로 처리해도 됩니다. Node.js는 `HEAD` 응답에 본문을 보내지 않습니다(3편).
- 메서드와 경로 조합으로 처리기를 고르는 방식이 라우팅입니다(5편).

## req.url

`req.url`은 요청줄에 실린 요청 대상 문자열입니다. origin form이면 경로와 쿼리 문자열(`/status?name=ryan`)이며, 디코딩되지 않은 원본입니다. 프래그먼트(`#...`)는 서버로 오지 않습니다.

```js
const url = new URL(req.url, 'http://localhost')
url.pathname              // '/status'
url.searchParams.get('name') // 'ryan'
```

- `req.url === '/users'`로 비교하면 쿼리 문자열이 붙은 요청(`/users?page=2`)과 맞지 않습니다. 경로와 쿼리를 나눈 뒤 `pathname`으로 비교합니다(자세히는 5편).
- `URL`의 두 번째 인수는 고정된 기준 주소여야 합니다. 공식 문서는 `req.headers.host`로 기준 주소를 만들려면 검증이 필요하다고 경고합니다. 클라이언트가 임의의 `Host`를 보낼 수 있기 때문입니다.
- `//evil.com/x`처럼 `//`로 시작하는 `req.url`은 `new URL(req.url, 'http://localhost')`에서 호스트가 `evil.com`으로 해석됩니다(Node.js 24에서 확인). 호스트를 쓰는 곳이 있다면 `url.origin`이 기준 주소와 같은지 확인합니다.
- 프록시를 거치면 absolute form(`http://a.com/x`)이 올 수 있고, `OPTIONS *`에서는 `'*'`가 옵니다.

## req.headers는 소문자

`req.headers`는 받은 헤더를 담은 객체이며 키는 모두 소문자, 값은 수정되지 않은 문자열입니다(자세히는 3편).

```js
const type = req.headers['content-type']
const length = Number(req.headers['content-length'])
const agent = req.headers['user-agent'] ?? 'unknown'
```

- 대문자 키(`req.headers['Content-Type']`)로 읽으면 `undefined`입니다. 점 표기는 하이픈이 든 이름에 쓸 수 없어서 대괄호 표기를 씁니다.
- 없는 헤더는 `undefined`입니다. 기본값이 필요하면 `??`를 씁니다.
- 값은 항상 문자열입니다. `content-length`는 `Number()`로 바꿔 씁니다. `set-cookie`만 문자열 배열입니다.
- 클라이언트가 보낸 값이므로 신뢰하지 않습니다. 길이 제한과 형식 검증을 거칩니다.
- 원본 이름의 대소문자와 중복은 `req.rawHeaders`, 병합하지 않은 값은 `req.headersDistinct`에 있습니다.

## host

`req.headers.host`는 클라이언트가 접속하려는 호스트와 포트(`localhost:3000`)입니다. HTTP/1.1에서는 `Host` 헤더가 필수라서, 없으면 서버가 400으로 응답합니다(`requireHostHeader` 기본값 `true`).

```js
const host = req.headers.host // 'example.com:3000'
if (host === 'api.example.com') {
  // 호스트별로 다른 처리(가상 호스트)
}
```

- 값에 포트가 포함될 수 있습니다. 포트 없이 비교하려면 분리해야 하며, IPv6 주소는 대괄호로 감싸 오므로(`[::1]:3000`) 단순히 `:`로 자르지 않습니다.
- 클라이언트가 임의로 정할 수 있는 값입니다. 이 값으로 리다이렉트 주소나 비밀번호 재설정 링크 같은 절대 URL을 만들면 조작될 수 있습니다. 서비스의 공식 주소는 설정으로 정해 둡니다.
- 한 서버가 여러 도메인을 받을 때 도메인별 분기에 쓰입니다.
- 프록시나 로드 밸런서 뒤에서는 원래 호스트가 `Host`에 그대로 오지 않을 수 있습니다. 어떤 헤더를 믿을지는 신뢰하는 프록시를 정해서 결정합니다.

## socket

`req.socket`은 이 요청이 들어온 연결을 나타내는 `net.Socket`(Duplex)입니다. `res.socket`과 같은 객체입니다.

```js
const { remoteAddress, remotePort } = req.socket
console.log(remoteAddress) // '127.0.0.1'
console.log(req.socket.encrypted) // undefined (HTTPS면 true)
```

| 속성 | 의미 |
|------|------|
| `remoteAddress`, `remotePort` | 상대(클라이언트 또는 프록시)의 주소와 포트 |
| `localAddress`, `localPort` | 서버 쪽 주소와 포트 |
| `encrypted` | TLS 연결일 때 `true`, 평문 HTTP에서는 `undefined` |

- 서버가 IPv6로 listen하고 IPv4 클라이언트가 접속하면 `remoteAddress`가 `::ffff:127.0.0.1`처럼 IPv4-mapped 형식으로 옵니다(확인).
- 프록시 뒤에서는 `remoteAddress`가 프록시의 주소입니다. 실제 클라이언트 주소를 `X-Forwarded-For` 같은 헤더로 받는다면 그 헤더는 위조될 수 있으므로 신뢰하는 프록시가 붙인 값만 씁니다.
- keep-alive에서는 하나의 소켓으로 요청이 여러 번 옵니다. 소켓 객체에 요청 단위 상태를 저장하지 않습니다.
- 소켓을 직접 읽거나 쓰지 않습니다. `req.destroy()`는 요청을 받은 소켓을 `destroy()`합니다.

## res.statusCode

`res.statusCode`는 암시적 헤더 모드에서 헤더가 전송될 때 쓰일 상태 코드이며 기본값은 `200`입니다. 헤더를 보내기 전에 대입합니다.

```js
res.statusCode = 404
res.setHeader('Content-Type', 'text/plain; charset=utf-8')
res.end('찾을 수 없습니다')
```

- `res.statusMessage`로 이유문구를 바꿀 수 있습니다. 지정하지 않으면 코드에 맞는 표준 문구를 씁니다.
- 값은 100–999의 숫자여야 합니다. 범위 밖이면 `writeHead()` 시점에 `RangeError`(`ERR_HTTP_INVALID_STATUS_CODE`)입니다.
- 헤더가 이미 나간 뒤의 대입은 효과가 없습니다. 에러 없이 무시되고 응답은 이미 나간 코드 그대로입니다(확인).
- 본문이 없는 응답(`204`, `304`)에는 본문을 쓰지 않습니다.

**흔한 실수:** 에러 처리에서 `res.statusCode = 500`만 쓰고 `res.end()`를 빼먹는 것입니다. 상태 코드는 끝내지 않으면 전송되지 않습니다.

## res.setHeader

`res.setHeader(name, value)`는 보낼 헤더 하나를 정합니다. 같은 이름이 이미 있으면 값을 교체합니다. 헤더가 전송되기 전까지만 쓸 수 있고, 응답 객체를 돌려주므로 체이닝됩니다.

```js
res.setHeader('Content-Type', 'application/json')
res.setHeader('Set-Cookie', ['a=1', 'b=2']) // 같은 이름 두 줄
res.getHeader('content-type')   // 'application/json'
res.hasHeader('X-Missing')      // false
res.removeHeader('Content-Type')
```

- 이름은 대소문자를 구분하지 않고, `getHeaders()`는 소문자 이름을 키로 한 객체를 돌려줍니다. `getHeaderNames()`는 소문자 이름의 배열입니다.
- 같은 이름의 헤더를 여러 줄 보내려면 값에 문자열 배열을 줍니다. 위 `Set-Cookie`가 두 줄로 나갑니다.
- 문자열이 아닌 값은 그대로 저장되어 `getHeader()`가 숫자를 돌려줄 수 있지만, 전송할 때 문자열로 바뀝니다.
- 이름이나 값에 유효하지 않은 문자가 있으면 `TypeError`입니다. 공백이 든 이름은 `ERR_INVALID_HTTP_TOKEN`, 줄바꿈이 든 값은 `ERR_INVALID_CHAR`였습니다(확인). 사용자 입력을 헤더 값에 넣을 때 줄바꿈으로 헤더를 끼워 넣는 공격을 이 검사가 막아 줍니다.
- `res.appendHeader(name, value)`는 기존 값을 두고 값을 추가합니다(v18.3.0 추가). `res.setHeaders(headers)`는 `Headers`나 `Map`으로 여러 개를 한 번에 정합니다(v19.6.0 추가).
- `setHeader()`로 정한 값은 `writeHead()`에 준 헤더와 합쳐지며 같은 이름이면 `writeHead()` 쪽이 우선합니다.

## res.writeHead

`res.writeHead(statusCode[, statusMessage][, headers])`는 상태 코드와 헤더를 한 번에 지정해 응답 헤더를 확정합니다.

```js
res
  .writeHead(200, {
    'Content-Type': 'text/plain; charset=utf-8',
    'Content-Length': Buffer.byteLength('안녕'),
  })
  .end('안녕')
```

- 메시지에서 한 번만, `end()` 전에 호출합니다. `res`를 돌려주므로 `.end()`를 이어 쓸 수 있습니다(v11.10.0부터).
- `write()`나 `end()`를 먼저 호출하면 암시적 헤더가 계산되어 이 함수가 자동으로 불립니다.
- `headers`에는 객체를 주거나, 이름과 값이 번갈아 나오는 평평한 배열(`rawHeaders` 형식)을 줄 수 있습니다(v14.14.0 추가).
- `setHeader()` 없이 `writeHead()`를 부르면 헤더를 내부에 저장하지 않고 바로 씁니다. 그래서 `getHeader()`가 기대한 값을 주지 않을 수 있습니다. 헤더를 나중에 읽거나 바꿔야 하면 `setHeader()`를 씁니다.
- `writeHead()`로 명시한 헤더 뒤에 `end(body)`를 호출해도 `Content-Length`를 자동으로 계산하지 않습니다. `Content-Length`를 직접 주지 않으면 청크 인코딩으로 나갑니다(확인, 아래 절).
- 상태 코드가 100–999 밖이면 `RangeError`입니다.

## res.write

`res.write(chunk[, encoding][, callback])`는 응답 본문의 일부를 보냅니다. 여러 번 호출해 본문을 나눠 보낼 수 있습니다.

```js
res.write('a')
res.write('bc')
res.end('def')
```

- 처음 호출될 때 `writeHead()`를 부르지 않았다면 암시적 헤더를 확정해서 첫 조각과 함께 보냅니다.
- `chunk`는 문자열, `Buffer`, `Uint8Array`입니다. 문자열의 `encoding` 기본값은 `'utf8'`입니다.
- 반환값이 `true`이면 데이터가 커널 버퍼에 모두 들어갔다는 뜻이고, `false`이면 일부가 사용자 메모리에 쌓였다는 뜻입니다. `false`이면 `'drain'`을 기다립니다(자세히는 2편).
- `callback`은 그 조각이 flush되면 호출됩니다.
- 호출이 두 번 이상이거나 `Content-Length`가 없으면 청크 인코딩으로 나갑니다(아래 chunked 절).
- `end()` 뒤에 `write()`하면 `ERR_STREAM_WRITE_AFTER_END`가 발생합니다. 콜백과 `'error'` 이벤트로 전달됩니다(확인).
- 큰 파일이나 스트림은 `res.write()`를 직접 반복하기보다 `pipeline(stream, res)`로 보냅니다(2편).

## res.end

`res.end([data[, encoding]][, callback])`는 헤더와 본문을 모두 보냈다고 서버에 알립니다. 모든 응답에서 반드시 호출해야 합니다.

```js
res.end()                  // 본문 없이 끝
res.end('done')            // write('done') 후 end()
res.end('done', () => {})  // 응답이 끝나면 콜백
```

- `data`를 주면 `write(data)` 다음에 `end()`한 것과 같습니다. `data`는 문자열, `Buffer`, `Uint8Array`입니다.
- 헤더가 아직 나가지 않았고 `write()`한 적이 없다면 `end(data)`가 `Content-Length`를 자동으로 계산합니다(확인: `res.end('ok')`가 `Content-Length: 2`로 나감).
- 호출하지 않으면 클라이언트는 응답이 끝나기를 계속 기다립니다. 에러 경로를 포함한 모든 분기에서 호출되는지 확인합니다.
- 두 번째 `end()`는 에러 없이 무시됩니다(확인). 응답 두 개를 보내려는 코드의 버그가 숨어 있을 수 있어서 분기마다 `return`합니다.
- `'finish'` 이벤트는 응답을 운영체제에 넘겼을 때 발생하며 클라이언트가 받았다는 뜻은 아닙니다.

**흔한 실수:** 분기에서 `res.end()` 뒤에 `return`을 빼먹고 아래 코드가 다시 응답을 쓰는 것입니다. 두 번째 쓰기는 `ERR_STREAM_WRITE_AFTER_END`이거나 `ERR_HTTP_HEADERS_SENT`입니다.

## writeHead 이후 헤더 수정 불가

HTTP 메시지에서 헤더는 본문보다 앞에 오므로, 헤더가 확정되어 전송되기 시작하면 상태 코드와 헤더를 바꿀 수 없습니다. `res.headersSent`가 `true`이면 이미 확정된 것입니다.

```js
res.writeHead(200)
res.headersSent    // true
res.setHeader('X-A', '1')
// ERR_HTTP_HEADERS_SENT: Cannot set headers after they are
// sent to the client
```

- `writeHead()`, 첫 `write()`, `end()` 중 먼저 호출된 것이 헤더를 확정합니다. `writeHead()` 직후에 `res.headersSent`가 이미 `true`였습니다(확인).
- 확정 뒤의 `setHeader()`와 `writeHead()`는 `ERR_HTTP_HEADERS_SENT` 에러를 던집니다. `statusCode` 대입은 에러 없이 무시됩니다.
- 이 에러가 나는 전형적인 원인은 두 가지입니다. 하나는 `await`를 지난 뒤나 콜백 안에서 이미 응답이 나간 사실을 모르고 헤더를 바꾸는 것입니다. 다른 하나는 한 요청에 두 코드 경로가 응답을 쓰는 것입니다.
- 본문을 스트리밍하던 중 에러가 나면 상태 코드를 `500`으로 바꿀 수 없습니다. `res.headersSent`로 구분하고, 이미 나갔다면 `res.destroy()`로 연결을 끊습니다.

```js
} catch (err) {
  if (res.headersSent) return res.destroy()
  res.writeHead(500).end()
}
```

- 본문 뒤에 보낼 수 있는 헤더는 트레일러(trailer)뿐입니다. `res.addTrailers()`는 청크 인코딩일 때만 전송되고, 응답 헤더에 `Trailer`로 이름을 미리 알려야 합니다. 거의 쓰지 않습니다.

## Content-Type

`Content-Type`은 본문이 어떤 형식인지 알려 주는 헤더입니다. 값은 미디어 타입이며 `; charset=utf-8` 같은 매개변수가 붙을 수 있습니다.

| 값 | 본문 |
|----|------|
| `text/plain; charset=utf-8` | 일반 텍스트 |
| `text/html; charset=utf-8` | HTML |
| `application/json` | JSON |
| `application/x-www-form-urlencoded` | 폼 입력(`a=1&b=2`) |
| `multipart/form-data; boundary=...` | 파일 업로드를 포함한 폼 |
| `application/octet-stream` | 형식을 모르는 바이너리 |

- 응답에서는 직접 정해야 합니다. Node.js는 `Content-Type`을 자동으로 붙이지 않았고(확인), 없으면 클라이언트가 본문을 추측합니다.
- 텍스트 형식에는 `charset=utf-8`을 붙여 인코딩을 분명히 합니다.
- 요청에서는 본문을 파싱하기 전에 확인합니다. 값에 매개변수가 붙을 수 있으므로 `;` 앞부분만 잘라 소문자로 비교합니다. 기대한 형식이 아니면 `415 Unsupported Media Type`으로 응답합니다.

```js
const raw = req.headers['content-type'] ?? ''
const type = raw.split(';')[0].trim().toLowerCase()
if (type !== 'application/json') {
  res.writeHead(415).end()
  return
}
```

- 헤더가 없는 요청은 빈 문자열이 되어 같은 분기로 갑니다. 본문이 없는 요청(`GET`)에서는 확인하지 않아도 됩니다.
- `multipart/form-data`의 `boundary` 매개변수는 본문 분리에 필요하므로 버리지 않습니다(자세히는 11편).

## Content-Length

`Content-Length`는 본문의 바이트 수입니다. 글자 수가 아닙니다.

```js
const body = '안녕'
body.length               // 2 (글자 수)
Buffer.byteLength(body)   // 6 (UTF-8 바이트 수)
```

- 응답에서 `res.end(body)`만 쓰면 Node.js가 계산해서 붙입니다. `writeHead()`나 `write()`가 먼저 나갔다면 자동 계산이 일어나지 않으므로 직접 정하거나 청크로 보냅니다.
- 직접 정할 때는 `Buffer.byteLength(body)`를 씁니다.
- 선언한 길이와 실제 본문이 다르면 메시지가 깨집니다. `Content-Length: 2`로 `'hello'`를 보내도 Node.js 24는 에러 없이 5바이트를 모두 보냈습니다(확인). `res.strictContentLength = true`로 두면 길이가 다를 때 `ERR_HTTP_CONTENT_LENGTH_MISMATCH` 에러를 던집니다(v18.10.0 추가, 기본 `false`).
- 요청에서는 `req.headers['content-length']`가 문자열로 옵니다. `Number()`로 바꿔서 본문 크기 제한의 1차 검사에 씁니다(아래 크기 제한 절).
- `Content-Length`가 없는 요청 본문은 청크 인코딩이거나 본문이 없는 것입니다. 두 헤더(`Content-Length`와 `Transfer-Encoding`)를 함께 보내지 않습니다.

## chunked

청크 인코딩(chunked transfer encoding)은 본문의 전체 길이를 모를 때 본문을 조각으로 나눠 보내는 방식이며, 헤더 `Transfer-Encoding: chunked`로 표시합니다. 각 조각 앞에 16진수 크기를 붙이고, 크기 0인 조각이 끝을 나타냅니다.

```text
HTTP/1.1 200 OK
Transfer-Encoding: chunked

1
a
2
bc
3
def
0

```

위는 `res.write('a')`, `res.write('bc')`, `res.end('def')`가 실제로 나간 모양입니다(조각마다 `크기 CRLF 데이터 CRLF`, 마지막은 `0 CRLF CRLF`).

- Node.js는 `Content-Length`가 없고 HTTP/1.1이면 자동으로 청크로 보냅니다. `write()`를 여러 번 부르는 스트리밍 응답이 해당합니다. 헤더를 `writeHead()`로 먼저 보낸 뒤 `end(body)`로 끝내는 응답도 같은 이유로 청크가 됩니다(확인).
- 받는 쪽 Node.js 서버는 청크 요청을 자동으로 디코딩합니다. `req.headers['transfer-encoding']`이 `'chunked'`이고 `content-length`는 `undefined`이며, `'data'`에는 조각 헤더가 빠진 본문이 옵니다(확인).
- HTTP 청크 경계와 `'data'` 이벤트 경계는 같지 않습니다. 스트림 조각 단위에 의미를 두지 않습니다.
- 청크 요청은 길이를 미리 알 수 없어서 `Content-Length` 검사만으로는 크기를 제한할 수 없습니다(아래 크기 제한 절).
- 응답 뒤에 트레일러를 붙이려면 청크 인코딩이어야 합니다.

## req.on('data')

`req`는 `stream.Readable`이므로 본문은 `'data'` 이벤트로 조각이 오고 `'end'` 이벤트로 끝납니다(1편). 조각은 `Buffer`입니다.

```js
req.on('data', (chunk) => {
  console.log(chunk.length) // 이번 조각의 바이트 수
})
req.on('end', () => {
  res.end('모두 받음')
})
```

- `'data'` 리스너를 붙이면 flowing 모드로 바뀌어 본문을 읽기 시작합니다. `setEncoding('utf8')`을 부르면 문자열 조각이 옵니다.
- 본문이 없는 `GET`도 읽는 쪽이 붙으면 `'end'`가 발생합니다. 다만 `createServer`의 옵션 `optimizeEmptyRequests`를 `true`로 두면(v24.12.0 추가, 기본 `false`) 본문이 없는 요청은 이미 끝난 스트림으로 시작해서 `'data'`와 `'end'`가 나오지 않습니다. 이때는 `req.readableEnded`로 확인합니다.
- 클라이언트가 중간에 끊으면 `'end'` 없이 `'close'`가 옵니다. `req.complete`가 `false`이면 메시지를 끝까지 받지 못한 것입니다. `'error'` 리스너도 둡니다.
- `for await (const chunk of req)`로 같은 일을 할 수 있고 에러가 예외로 던져집니다(자세히는 2편). 이터레이션을 `break`나 예외로 끝내면 `req`가 `destroy`됩니다.
- 이벤트 방식과 `for await`를 섞어 쓰지 않습니다.

## 본문을 Buffer로 모으기

조각을 배열에 모아 `Buffer.concat()`으로 합친 뒤, 필요하면 마지막에 문자열로 바꿉니다.

```js
async function readBody(req) {
  const chunks = []
  for await (const chunk of req) {
    chunks.push(chunk)
  }
  return Buffer.concat(chunks)
}
const buf = await readBody(req)
const text = buf.toString('utf8')
```

- 조각을 문자열에 `+=`로 이으면 `Buffer`가 매번 문자열로 바뀝니다. 여러 바이트 문자가 조각 경계에 걸리면 글자가 깨집니다. 한글 `안녕하세요`를 4바이트 지점에서 나눠 받았을 때 `+=` 결과는 `안���하세요`였고 `Buffer.concat()` 결과는 정상이었습니다(확인).
- `setEncoding('utf8')`을 먼저 호출하면 경계에 걸린 문자를 스트림이 올바르게 처리하므로 문자열 조각을 이어 붙여도 됩니다. 바이너리 본문에는 쓸 수 없습니다.
- 합칠 때 전체 길이를 알면 `Buffer.concat(chunks, totalLength)`로 계산을 줄일 수 있습니다(기초 19편).
- 본문 전체가 메모리에 올라갑니다. 크기를 제한하지 않으면 큰 요청 하나가 서버 메모리를 소진합니다(아래 크기 제한 절).
- 업로드처럼 큰 본문은 모으지 않고 스트림으로 파일에 씁니다(2편, 11편).

## JSON 파싱

모은 `Buffer`를 문자열로 바꿔 `JSON.parse()`로 파싱합니다. Node.js는 본문을 파싱해 주지 않으므로 파싱과 에러 처리가 서버 코드의 몫입니다.

```js
let data
try {
  data = JSON.parse(buf.toString('utf8'))
} catch {
  res.writeHead(400).end('invalid json')
  return
}
```

- 잘못된 JSON은 `SyntaxError`입니다. 클라이언트의 잘못이므로 `500`이 아니라 `400`으로 응답합니다. 메시지는 `Unexpected token 'o', "not json" is not valid JSON` 같은 형태이고, 빈 본문은 `Unexpected end of JSON input`입니다(확인).
- 파싱 전에 `Content-Type`이 `application/json`인지 확인합니다. 아니면 `415`입니다.
- 파싱 결과가 객체라는 보장이 없습니다. `null`, 숫자, 배열일 수도 있어서 필요한 구조를 직접 검증합니다(자세히는 8편).
- 에러 응답의 상세 메시지를 그대로 내보낼지는 정책으로 정합니다.
- JSON 응답은 `JSON.stringify()`로 만들고 `Content-Type`을 지정해 보냅니다.

```js
function sendJson(res, status, data) {
  const body = JSON.stringify(data)
  res.writeHead(status, {
    'Content-Type': 'application/json',
    'Content-Length': Buffer.byteLength(body),
  })
  res.end(body)
}
```

## 본문 크기 제한

요청 본문을 모두 메모리에 모으는 코드에는 상한이 반드시 있어야 합니다. 상한이 없으면 큰 본문 하나가 서버 메모리를 소진하게 만들 수 있습니다. 두 단계로 막습니다.

1. `Content-Length`가 선언한 크기가 상한을 넘으면 본문을 읽지 않고 `413`으로 거절합니다.
2. 선언이 없거나(청크 요청) 거짓일 수 있으므로, 받으면서 누적 바이트를 세어 상한을 넘으면 중단합니다.

```js
const LIMIT = 1024 * 1024 // 1 MiB

async function readBody(req, limit) {
  if (Number(req.headers['content-length']) > limit) {
    throw new HttpError(413, 'too large')
  }
  const chunks = []
  let size = 0
  for await (const chunk of req) {
    size += chunk.length
    if (size > limit) throw new HttpError(413, 'too large')
    chunks.push(chunk)
  }
  return Buffer.concat(chunks, size)
}
```

- `HttpError`는 `status` 속성을 가진 직접 만든 `Error` 하위 클래스입니다. 요청 처리 바깥의 `catch`에서 `err.status`로 응답 코드를 정합니다.
- 상한을 넘으면 `for await`가 예외로 끝나고 `req`가 `destroy`됩니다. 이 상태에서도 `res`로 `413`을 쓸 수 있었습니다(확인). 응답 헤더에 `Connection: close`를 주어 연결을 끊게 합니다.

```js
res.writeHead(413, { Connection: 'close' }).end('too large')
```

- 이벤트 방식에서는 `'data'`에서 누적 크기를 세고, 초과하면 응답을 보낸 뒤 `req.destroy()`를 호출합니다. 실험에서 클라이언트는 `413`을 받았습니다.
- 헤더 크기의 상한은 `maxHeaderSize`(기본 16 KiB)이고, 본문 전체를 받는 제한 시간은 `requestTimeout`(기본 300000ms)입니다. 느린 전송으로 자원을 묶어 두는 공격을 막는 설정은 6편에서 다룹니다.
- 상한은 형식에 따라 다르게 둡니다. JSON API는 작게(예: 수십 KB–1 MB), 파일 업로드는 크게 두고 업로드는 메모리에 모으지 않습니다.
- 프록시나 로드 밸런서가 먼저 본문 크기를 제한하는 경우가 많아서, 서버의 상한과 함께 설계합니다.

## 핵심 정리

- `req.method`, `req.url`, `req.headers`, `req.socket`으로 요청을 읽고, `req.headers`의 키는 소문자이며 `Host`와 `X-Forwarded-For` 같은 값은 클라이언트가 정한 것이라 신뢰하지 않습니다.
- 응답은 `res.statusCode`와 `res.setHeader()` 또는 `res.writeHead()`로 헤더를 정하고 `res.write()`, `res.end()`로 본문을 쓰며, 모든 분기에서 `res.end()`가 한 번 호출되어야 합니다.
- 헤더는 `writeHead()`, 첫 `write()`, `end()` 중 먼저 호출된 것이 확정하고, 이후 `setHeader()`와 `writeHead()`는 `ERR_HTTP_HEADERS_SENT` 에러입니다.
- `Content-Type`은 본문 형식을, `Content-Length`는 본문의 바이트 수를 알리며, 길이를 모르는 스트리밍 응답은 `Transfer-Encoding: chunked`로 나갑니다.
- 요청 본문은 `req`의 `'data'` 조각을 `Buffer`로 모아 `Buffer.concat()`으로 합치고(문자열 `+=`는 문자가 깨질 수 있음), `JSON.parse()` 실패는 `400`으로 응답합니다.
- 본문 크기는 `Content-Length` 선언과 누적 바이트 두 단계로 제한하고, 초과하면 `413`으로 응답합니다.

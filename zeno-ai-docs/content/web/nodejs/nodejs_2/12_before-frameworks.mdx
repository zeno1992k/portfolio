## 프레임워크가 감추는 것

웹 프레임워크는 `http.createServer`의 요청 리스너 `(req, res)` 하나를 감싸서 라우팅, 본문 파싱, 에러 처리, 응답 도우미를 제공하는 라이브러리입니다. 프레임워크 없이 쓰는 코어는 이렇게 생겼습니다.

```js
createServer((req, res) => {
  const { pathname } = new URL(req.url, 'http://x')
  if (req.method === 'GET' && pathname === '/ping') {
    res.writeHead(200).end('pong')
    return
  }
  res.writeHead(404).end()
})
```

프레임워크가 대신 해 주는 일과 코어에서 직접 하는 일의 대응입니다.

| 프레임워크의 기능 | 코어에서 하는 일 |
|-------------------|------------------|
| 라우팅 | `req.method`와 `req.url`을 비교해 분기(05편) |
| 본문 파싱 | 청크를 모으고 크기를 제한한 뒤 `JSON.parse`(04편) |
| 쿼리·경로 매개변수 | `URL`, `URLSearchParams`로 직접 추출 |
| 응답 도우미(`res.json` 등) | 헤더 설정과 직렬화를 직접 작성 |
| 에러 처리 | `try`/`catch` 후 응답을 직접 작성 |
| 공통 처리 | 함수를 순서대로 호출하는 체인(11편) |

- 프레임워크가 감추는 대상은 리스너 연결, 본문 스트림 소비, 헤더 전송 여부, 에러 전달 경로입니다.
- 감춰도 사라지지 않습니다. 서버 타임아웃(06편), 연결 종료와 정리(25편), 본문을 한 번만 읽는 제약(11편)은 그대로 `http.Server`의 규칙입니다. 프레임워크가 이상하게 동작할 때 원인은 대부분 이 층에 있습니다.
- 반대로 프레임워크가 주는 것이 코어에는 없습니다. 검증, 구조 강제, 의존성 주입, 테스트 도구가 그렇습니다. 어디까지가 Node이고 어디부터가 프레임워크인지 구분하는 것이 이 편의 목표입니다.

**흔한 실수:** 프레임워크의 `req`와 `res`를 Node의 것과 별개의 객체로 생각하는 것입니다. Express의 `req`와 `res`는 Node 객체를 확장한 것이라 `res.headersSent`, `req.socket` 같은 코어 속성이 그대로 있습니다.

## Express가 얇은 이유

Express의 핵심은 라우팅과 미들웨어 실행뿐이고 나머지 기능은 미들웨어 모듈로 덧붙이는 구조이기 때문입니다. 공식 소개는 Express를 "fast, unopinionated, minimalist web framework"이라 하고, 최소한의 핵심 기능을 미들웨어 모듈로 확장하는 가볍고 유연한 라우팅 프레임워크로 설명합니다.

- `express()`가 돌려주는 `app`은 Node HTTP 서버에 콜백으로 넘기도록 설계된 JavaScript 함수입니다. `app.listen`은 `http.Server.listen`과 같습니다.
- `req`와 `res`는 Node의 요청·응답 객체를 확장한 것입니다.
- Express 5는 Node 18 이상을 요구합니다.

```js
import express from 'express'
import { createServer } from 'node:http'

const app = express()
app.get('/', (req, res) => res.send('hi'))
createServer(app).listen(3000) // app.listen(3000)과 같다
```

본문 파싱(`express.json()`), 쿠키, CORS, 세션, 검증은 코어가 아니라 미들웨어입니다. 얇다는 것은 기능이 적다는 뜻이 아니라 코어가 맡는 층이 작다는 뜻입니다. 이어지는 절에서 그 코어를 직접 만들어 봅니다. Express 자체는 13편에서 다룹니다.

## 라우터

라우터는 요청의 메서드와 경로를 규칙 목록과 대조해 해당 핸들러를 고르는 부분입니다. 경로 규칙의 `:id` 같은 부분은 값을 뽑아 `req.params`에 넣습니다.

```js
function matchPath(keys, req) {
  const { pathname } = new URL(req.url, 'http://x')
  const parts = pathname.split('/')
  if (parts.length !== keys.length) return false
  const params = {}
  for (const [i, key] of keys.entries()) {
    if (key.startsWith(':')) params[key.slice(1)] = parts[i]
    else if (key !== parts[i]) return false
  }
  req.params = params
  return true
}
// keys: '/users/:id'.split('/') 과 요청 /users/7 → { id: '7' }
```

- Express의 `Router`는 독립된 미들웨어와 라우트 묶음이며 "미니 앱"이라 불립니다. 앱에 `app.use('/birds', birds)`로 붙입니다.
- 라우터도 `(req, res, next)` 함수라서 미들웨어와 같은 방식으로 체인에 들어갑니다. 붙일 때 접두사를 `req.url`에서 떼어 내고, 하위 라우터를 빠져나오면 복원합니다.

```js
function mount(prefix, sub) {
  const inside = new RegExp(`^${prefix}(?=[/?]|$)`)
  return (req, res, next) => {
    if (!inside.test(req.url)) return next()
    const original = req.url
    req.url = req.url.slice(prefix.length) || '/'
    sub(req, res, (err) => {
      req.url = original
      next(err)
    })
  }
}
```

- 접두사 뒤에 `/`, `?`, 문자열 끝이 올 때만 일치로 봅니다. 이 경계 검사가 없으면 `/apple`이 `/api`에 걸립니다.
- Express 5의 경로 문법은 4와 다릅니다. `*`는 `*splat`, 선택 구간 `:file.:ext?`는 `:file{.:ext}` 형태입니다.

**흔한 실수:** 직접 만든 매처를 정규식 하나로 대충 처리해 `/users/7/`처럼 끝 슬래시가 있거나 `/users/7?x=1`처럼 쿼리가 붙은 경로를 놓치는 것입니다. 경로는 `URL`로 파싱한 `pathname`만 비교합니다.

## 미들웨어 체인

미들웨어 체인은 함수 배열을 순서대로 호출하고, 각 함수가 넘겨받은 `next`를 부르면 다음 함수로 진행하는 구조입니다. 핵심은 인덱스를 하나 가진 `next` 클로저입니다.

```js
function createApp() {
  const stack = []
  const app = (req, res, done = finish) => {
    let i = 0
    const next = (err) => {
      const layer = stack[i++]
      if (!layer) return done(err, res)
      run(layer, err, req, res, next)
    }
    next()
  }
  app.use = (fn) => { stack.push({ fn }); return app }
  return app
}
```

- `app`은 `(req, res)` 함수라서 `http.createServer(app)`에 그대로 넘길 수 있습니다. Express가 같은 구조입니다.
- `next()`를 부를 때마다 `i`가 하나씩 올라가 다음 계층을 꺼냅니다. 계층이 끝나면 처리되지 않은 요청이므로 404(에러가 있으면 500 계열)를 응답합니다.
- 라우트 등록은 같은 스택에 경로 조건을 붙인 계층을 넣는 일입니다.

```js
app.get = (path, ...fns) => {
  const keys = path.split('/')
  const match = (req) =>
    req.method === 'GET' && matchPath(keys, req)
  for (const fn of fns) stack.push({ fn, match })
  return app
}
```

- 조건이 맞지 않는 계층은 건너뛰고 `next`로 넘어갑니다. 라우트와 미들웨어는 같은 스택 위의 같은 종류의 계층입니다. 하나의 경로에 핸들러 여러 개(예: 인증 후 조회)를 쓸 수 있는 것도 이 때문입니다.
- 순서가 곧 정책입니다. 먼저 등록한 계층이 먼저 실행되므로 CORS와 인증, 본문 파싱 순서를 의도대로 둡니다(11편).

**흔한 실수:** 라우트를 등록한 뒤에 공통 미들웨어를 등록하는 것입니다. 앞에서 응답을 끝낸 라우트에는 뒤에 등록한 미들웨어가 실행되지 않습니다.

## next

`next`는 현재 계층의 일을 끝내고 제어를 다음 계층에 넘기는 함수입니다. 호출 형태에 따라 뜻이 다릅니다.

| 호출 | 동작 |
|------|------|
| `next()` | 다음 계층으로 진행 |
| `next(err)` | 에러가 생겼다고 알리고 에러 처리 계층으로 건너뜀 |
| `next('route')` | (Express) 이 라우트의 남은 핸들러를 건너뛰고 다음 라우트로 |
| `next('router')` | (Express) 현재 라우터를 빠져나감 |

- 응답을 끝내지 않았으면 `next()`를 반드시 불러야 합니다. 부르지 않으면 요청이 매달립니다(Express 문서).
- 응답을 끝낸 뒤에 `next()`를 부르거나 두 번 부르면 뒤쪽 계층이 중복 실행되어 응답이 겹칠 수 있습니다. 습관적으로 `return next()`로 씁니다.
- 동기 함수가 던진 에러는 체인 실행기가 `try`/`catch`로 잡아 `next(e)`로 넘깁니다. 비동기 함수는 반환된 Promise가 거부될 때 `next`로 넘겨야 합니다.

```js
function run({ fn, match }, err, req, res, next) {
  if (match && !match(req)) return next(err)
  if ((fn.length === 4) !== Boolean(err)) return next(err)
  try {
    const args = [req, res, next]
    if (err) args.unshift(err)
    const out = fn(...args)
    if (out?.catch) out.catch(next) // 거부된 Promise를 next로
  } catch (e) {
    next(e)
  }
}
```

- Express 5는 반환된 Promise가 거부되면 자동으로 `next(err)`를 부릅니다. 위의 `out.catch(next)`가 같은 동작입니다. Express 4에서는 `async` 핸들러의 거부를 직접 `next`로 넘겨야 했습니다(자세히는 13편).
- Fastify는 `async` 핸들러가 던지거나 거부하면 에러 응답으로 처리하고, Hono는 `(c, next)`에서 `await next()`를 호출합니다. 호출 형태는 달라도 "다음으로 넘기기"라는 구조는 같습니다.

**흔한 실수:** `res.send()`로 응답을 끝내고도 `next()`를 부르는 것입니다. 뒤쪽 404 처리가 다시 응답을 쓰려다 `ERR_HTTP_HEADERS_SENT`가 납니다.

## 에러 미들웨어 시그니처

에러 미들웨어는 인수가 네 개인 `(err, req, res, next)` 함수입니다. 프레임워크는 함수의 인수 개수(`fn.length`)가 4인지로 일반 미들웨어와 구분합니다. 위 `run`의 `fn.length === 4`가 그 판정입니다.

```js
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err)
  res.writeHead(err.status ?? 500).end('error')
})
```

- 에러 계층은 에러가 없을 때는 건너뛰고, 에러가 있을 때는 일반 계층을 건너뛰고 에러 계층만 실행합니다. `next(err)`를 부르면 일반 계층이 모두 건너뛰어지는 이유입니다.
- Express 문서의 규칙: 에러 처리기는 다른 `app.use`와 라우트 호출 뒤, 가장 마지막에 정의합니다. 에러 처리기에서 `next(err)`를 부르지 않으면 응답을 직접 끝내야 하고, 끝내지 않으면 요청이 매달립니다.
- 응답 헤더를 이미 보낸 뒤라면 새 상태를 쓸 수 없으므로 `res.headersSent`를 확인해 `next(err)`로 기본 처리기에 넘깁니다. Express의 기본 처리기는 이때 연결을 닫습니다. 기본 처리기는 `err.status`나 `err.statusCode`를 응답 코드로 쓰고 없으면 500이며, 개발 모드에서만 스택을 보여 줍니다(`NODE_ENV=production`이면 숨김).
- 인수 개수로 판정하므로 `next`를 쓰지 않더라도 네 개를 모두 선언해야 합니다.

```js
const a = (err, req, res, next) => {}
const b = (err, req, res, next = null) => {}
const c = (...args) => {}
a.length // 4
b.length // 3 (기본값이 있는 인수부터 세지 않는다)
c.length // 0
```

**흔한 실수:**

- 에러 처리기에서 `next`를 지우거나 기본값을 주거나 나머지 인수로 받는 것입니다. 일반 미들웨어로 취급되어 에러가 와도 호출되지 않고 기본 처리기가 응답합니다.
- 에러 처리기를 라우트보다 앞에 등록하는 것입니다. 뒤에서 발생한 에러가 이 계층까지 오지 않습니다.
- 모든 에러를 500으로 응답하는 것입니다. 입력이 잘못된 요청(예: 깨진 URL 인코딩)은 400이어야 하므로 에러에 `status`를 담아 던집니다.

## 정적 미들웨어

정적 미들웨어는 요청 경로를 디스크의 파일로 바꿔 읽어 응답하고, 파일이 없으면 `next()`로 넘기는 미들웨어입니다. 파일을 못 찾았다고 직접 404를 쓰지 않고 넘기는 것이 핵심입니다. 그래야 뒤에 등록한 라우트가 처리할 수 있습니다.

```js
function serveStatic(root) {
  const base = resolve(root)
  return async (req, res, next) => {
    if (req.method !== 'GET') return next()
    const { pathname } = new URL(req.url, 'http://x')
    const file = join(base, decodeURIComponent(pathname))
    if (!file.startsWith(base + sep)) return next()
    const info = await stat(file).catch(() => null)
    if (!info?.isFile()) return next()
    res.writeHead(200, { 'content-length': info.size })
    await pipeline(createReadStream(file), res)
  }
}
```

- 경로를 `join`한 결과가 루트 디렉터리 안에 있는지 확인해 `../` 탈출을 막습니다(자세히는 05편). `URL` 파싱이 `/%2e%2e/`를 먼저 `/`로 정규화하기도 하지만 검사를 생략하면 안 됩니다.
- 파일 전송은 `pipeline`으로 스트림에 연결합니다(자세히는 02편).
- 실제 구현에는 `Content-Type` 결정, ETag·조건부 요청, `Range` 지원이 더 있습니다. 위 코드는 이를 생략했습니다(자세히는 05편).
- `decodeURIComponent`는 깨진 인코딩(`%E0%A4%A`)에서 `URIError`를 던집니다. 비동기 미들웨어의 거부라서 에러 처리기까지 가고, 처리기가 `status`를 모르면 500이 됩니다. 400으로 바꾸려면 잡아서 `status`를 붙여 던집니다.

Express의 `express.static(root, [options])`는 같은 일을 합니다.

| 항목 | Express |
|------|---------|
| 가상 경로 | `app.use('/static', express.static('public'))`. 파일 시스템에 없는 접두사 |
| 루트 경로 | 상대 경로는 프로세스를 시작한 디렉터리 기준이므로 절대 경로를 씀 |
| 디렉터리 여러 개 | `express.static`을 여러 번 호출하면 등록 순서대로 찾음 |
| 점 파일 | Express 5는 기본으로 무시(`dotfiles: 'ignore'`), `.well-known` 등은 `{ dotfiles: 'allow' }` |
| 운영 | 리버스 프록시 캐시를 앞에 두라고 권장 |

**흔한 실수:** `express.static('public')`처럼 상대 경로를 쓰고 다른 디렉터리에서 서버를 시작해 파일을 못 찾는 것입니다.

## 프레임워크 없이 같은 구조

위의 조각을 조립하면 Express와 같은 모양의 앱이 됩니다. 의존성 없이 `node:http`만 씁니다.

```js
const app = createApp()
app.use(serveStatic('./public'))

const api = createApp()
api.get('/users/:id', (req, res) => {
  res.end(`user ${req.params.id}`)
})
app.use(mount('/api', api))
app.use((err, req, res, next) => {
  const status = err.status ?? 500
  res.writeHead(status).end(`error ${err.message}`)
})
createServer(app).listen(3000)
```

위 코드에 `api`의 `/boom` 라우트(아래)를 더하고 앞 절의 함수들과 한 파일에 묶어 포트 0으로 실행해 확인한 결과입니다.

```js
api.get('/boom', async () => {
  throw Object.assign(new Error('bad'), { status: 400 })
})
```

| 요청 | 결과 |
|------|------|
| `/api/users/7` | 200, `user 7` |
| `/a.css` (public 안의 파일) | 200, 파일 내용 |
| `/nope` | 404 |
| `/apple` | 404 (`/api` 접두사에 걸리지 않음) |
| `/%2e%2e/secret.txt` | 404 (루트 밖은 거부) |
| `/api/boom` (비동기 핸들러가 `status: 400` 에러를 던짐) | 400, `error bad` |

Express와의 대응입니다.

| 직접 만든 것 | Express |
|--------------|---------|
| `createApp()` | `express()` |
| `app.use(fn)` | `app.use(fn)` |
| `app.get(path, ...fns)` | `app.get(path, ...fns)` |
| `createApp()`을 `mount`로 붙임 | `express.Router()`와 `app.use(prefix, router)` |
| `serveStatic(root)` | `express.static(root)` |
| 네 인수 함수 | 에러 처리 미들웨어 |

직접 만든 코드에 없는 것도 분명합니다. `path-to-regexp` 기반의 풍부한 경로 문법, 쿼리 파서, 본문 파서, 콘텐츠 협상, `res.json` 같은 도우미, HEAD·OPTIONS 자동 처리가 그렇습니다. 얇다고 해도 이 부분이 Express가 해 주는 일입니다.

**흔한 실수:** 이 구현을 운영에 쓰는 것입니다. 목적은 구조를 이해하는 것이고, 경로 문법과 보안 검토, 성능이 검증된 라이브러리를 쓰는 편이 안전합니다.

## Fastify

Fastify는 낮은 오버헤드와 높은 성능을 목표로 하는 Node.js 웹 프레임워크이고, 플러그인 구조와 JSON Schema 기반 검증이 특징입니다.

```js
import Fastify from 'fastify'

const app = Fastify({ logger: true })
const opts = { schema: { body: {
  type: 'object',
  required: ['name'],
  properties: { name: { type: 'string' } },
} } }
app.post('/users', opts, async () => ({ ok: true }))
await app.listen({ port: 3000 })
```

- 요청 처리는 등록 순서가 아니라 정해진 생명주기 단계를 따릅니다. 라우팅, `onRequest`, `preParsing`, 파싱, `preValidation`, 검증(실패는 400), `preHandler`, 핸들러, `preSerialization`, `onSend`, 응답, `onResponse`입니다. 각 단계에 훅을 답니다. Express의 단일 체인과 다른 점입니다.
- `route` 옵션의 `schema`로 본문, 쿼리, 경로 매개변수, 헤더를 검증합니다. 위 예에서 `name`이 없는 요청은 핸들러에 닿기 전에 400(`FST_ERR_VALIDATION`)으로 응답했습니다(직접 실행해 확인).
- "모든 것이 플러그인"입니다. `register`로 플러그인을 불러오며 캡슐화(encapsulation) 범위가 만들어져, 한 플러그인에서 만든 데이터베이스 연결을 이후 플러그인이 쓸 수 있고 범위 밖으로는 새지 않습니다.
- 로깅은 Pino를 씁니다(`logger: true`).
- Fastify 5는 Node 20 이상만 지원하고, `listen`에 옵션 객체를 요구하며, 검증 스키마에 완전한 JSON Schema를 요구합니다.
- 핸들러가 `async`이므로 값을 반환하면 응답이 되고, 던지면 에러 응답이 됩니다.

## Nest

NestJS는 모듈, 컨트롤러, 프로바이더와 의존성 주입으로 서버의 구조를 강제하는 프레임워크이고, 기본 언어는 TypeScript입니다. 직접 HTTP를 처리하지 않고 Express(기본)나 Fastify 같은 HTTP 프레임워크를 어댑터로 감싸 그 위에서 동작합니다.

```ts
// main.ts
const app = await NestFactory.create(AppModule)
await app.listen(process.env.PORT ?? 3000)
```

```ts
@Controller('cats')
export class CatsController {
  @Get()
  findAll(): string {
    return 'This action returns all cats'
  }
}
```

- 컨트롤러는 모듈의 `controllers` 배열에 등록해야 인식됩니다. 서비스 같은 클래스는 `@Injectable()`을 붙여 프로바이더로 만들고, 생성자 인수의 타입을 보고 IoC 컨테이너가 주입합니다.
- 기본 방식은 핸들러가 값을 반환하면 Nest가 JSON으로 직렬화하고 상태 코드를 정합니다. `@Res()`로 플랫폼의 응답 객체를 직접 받으면 응답 관리를 직접 해야 하고 Nest 기능을 일부 잃습니다.
- 어댑터는 `ExpressAdapter`와 `FastifyAdapter`이며 Express와 Fastify 중 하나를 바꿔도 앱 코드는 유지됩니다.
- 공식 문서 기준 실행에 Node.js 20.19 이상이 필요하고, CLI는 더 최근 버전(22.22.3 이상, 24.15 이상, 26 이상)을 요구합니다.
- 모듈, 프로바이더, 요청 생명주기는 14편, 가드와 인터셉터, 어댑터 교체는 15편에서 다룹니다.

**흔한 실수:** Nest를 별도의 HTTP 서버로 오해하는 것입니다. 아래에는 Express나 Fastify가 있고, 요청 헤더·타임아웃·종료 같은 문제는 그 아래의 `node:http`까지 내려가야 풀립니다.

## Hono

Hono는 웹 표준(`Request`, `Response`) 위에 만든 작고 빠른 프레임워크이고, 같은 코드가 여러 런타임에서 돕니다. 공식 문서에 나열된 환경은 Cloudflare Workers, Fastly Compute, Deno, Bun, Vercel, Netlify, AWS Lambda, Node.js(어댑터 필요)입니다.

```ts
import { Hono } from 'hono'
import { serve } from '@hono/node-server'

const app = new Hono()
app.get('/', (c) => c.text('Hono'))
serve(app) // Node에서는 어댑터가 서버를 만든다
```

- 핸들러는 `(c)`를 받아 `Response`를 반환합니다. 미들웨어는 `(c, next)`이고 `await next()`를 불러야 다음으로 가며, `next` 앞의 코드는 등록 순서로, 뒤의 코드는 역순으로 실행됩니다.
- Node에서는 `@hono/node-server`의 `serve()`가 `node:http`를 감싸 서버를 만들어 줍니다. 서버를 닫는 일(`SIGINT`, `SIGTERM` 처리)은 직접 해야 합니다(25편).
- JWT, CORS, 로깅, 압축 같은 미들웨어와 쿠키 도우미가 기본으로 들어 있습니다.
- Express·Fastify·Nest가 `node:http`의 `req`/`res`를 전제로 하는 것과 달리 Hono는 `Request`/`Response`를 전제로 해서, 엣지 런타임과 Node를 오가는 코드에 맞습니다.

## 프레임워크를 고르기 전에 코어를 보는 이유

모든 프레임워크가 같은 코어 개념의 변형이기 때문입니다. 라우팅, 미들웨어(훅), 에러 전달, 본문 처리, 정적 파일은 이름만 달라지고, 그 아래의 `http.Server`, 스트림, 이벤트 루프는 바뀌지 않습니다.

- 문제를 층으로 나눌 수 있습니다. 응답이 매달리면 `next()` 누락, `ERR_HTTP_HEADERS_SENT`면 응답 중복, 업로드가 끊기면 서버 타임아웃, 에러 처리기가 안 불리면 인수 개수처럼 증상에서 원인으로 바로 갑니다.
- 프레임워크를 갈아타는 비용이 줄어듭니다. 개념을 알면 Express에서 Fastify나 Nest로 옮길 때 문법만 바뀝니다.
- 프레임워크의 기본값을 의심할 수 있습니다. 본문 크기 제한, 신뢰하는 프록시, 정적 파일의 점 파일 같은 기본 동작은 보안과 직결됩니다.
- 면접에서 "Express의 미들웨어는 어떻게 동작하나요", "Nest는 내부에서 무엇을 쓰나요" 같은 질문은 코어를 알아야 답할 수 있습니다.

**흔한 실수:** 프레임워크 문서의 사용법만 익히고 코어를 건너뛰는 것입니다. 장애는 대개 프레임워크가 감춘 층에서 납니다.

## 채용 공고와 선택 기준표

이 과목의 조사(2026-10, 랠릿·사람인·잡코리아의 Node.js 백엔드 공고)에서 요건으로 반복된 것은 TypeScript 이해와 Node.js 프레임워크(NestJS, Express) 기반 백엔드 경험이었습니다. Fastify와 Hono는 같은 조사에서 반복 요건으로 확인되지 않았습니다. 프레임워크별 공고 수치(비율)는 이번에 확인하지 않아서 싣지 않았습니다.

| 기준 | Express | Fastify | NestJS | Hono |
|------|---------|---------|--------|------|
| 성격 | 최소 코어, 미들웨어로 확장 | 성능과 플러그인 구조 | 구조와 DI를 강제 | 웹 표준, 멀티 런타임 |
| 검증 | 외부 라이브러리(08편) | JSON Schema 내장 | DTO와 파이프(14편) | 외부 라이브러리 또는 미들웨어 |
| TypeScript | 선택 | 지원 | 기본 | 지원 |
| 기반 | `node:http` | `node:http` | Express 또는 Fastify | `Request`/`Response` |
| 공고 반복 요건 | 있음 | 확인되지 않음 | 있음 | 확인되지 않음 |
| 어울리는 경우 | 작은 API, 기존 코드, 학습 | 성능과 스키마가 중요한 API | 팀 규모가 크고 구조 통일이 필요한 서비스 | 엣지·서버리스, 여러 런타임 |

- 취업을 목표로 하면 NestJS와 Express를 먼저 익히는 것이 공고 요건과 맞습니다. 다음 편들이 Express(13편), NestJS 기초(14편)와 심화(15편) 순서인 이유입니다.
- 이미 운영 중인 코드가 있다면 기존 선택을 따르고, 새 프로젝트라면 팀 규모와 구조 요구에 맞춰 고릅니다.
- 어떤 선택이든 코어는 같습니다. 이 편의 구조를 이해하면 선택을 바꿔도 대부분 그대로 통합니다.

## 핵심 정리

- 프레임워크는 `(req, res)` 리스너를 감싸 라우팅, 본문, 에러, 공통 처리를 제공하지만, 타임아웃과 종료 같은 `http.Server`의 규칙은 그대로 남습니다.
- Express는 라우팅과 미들웨어 실행만 코어로 두고 나머지를 미들웨어로 덧붙이며, `app`은 `http.createServer`에 넘기는 함수입니다.
- 미들웨어 체인은 인덱스를 가진 `next` 클로저로 함수 배열을 순서대로 호출하는 구조이고, 라우트와 라우터도 같은 스택의 계층입니다.
- `next(err)`는 에러 처리 계층으로 건너뛰며, 에러 미들웨어는 인수가 네 개(`fn.length === 4`)여야 하고 가장 마지막에 둡니다.
- 정적 미들웨어는 루트 밖 접근을 막고, 파일이 없으면 직접 404를 쓰지 않고 `next()`로 넘깁니다.
- Fastify는 생명주기 훅과 JSON Schema, NestJS는 Express나 Fastify 위의 구조와 DI, Hono는 웹 표준 기반 멀티 런타임이며, 선택은 팀과 배포 환경의 요구로 정합니다.

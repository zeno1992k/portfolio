## net 모듈

`node:net`은 TCP 연결과 IPC(Unix 도메인 소켓·Windows 명명된 파이프)를 위한 모듈입니다. TCP는 연결을 먼저 맺고, 그 연결 위에서 순서대로 빠짐없이 바이트를 주고받는 프로토콜입니다. HTTP, PostgreSQL, Redis 같은 프로토콜이 모두 그 위에 올라가 있고, Node의 `http` 서버도 `net` 서버를 바탕으로 합니다(03편).

| 클래스·함수 | 역할 |
|-------------|------|
| `net.createServer()` | 연결을 받는 `net.Server` 생성 |
| `net.connect()`, `net.createConnection()` | 서버에 연결하는 클라이언트 `net.Socket` 생성 |
| `net.Socket` | 연결 한 개. 읽기·쓰기가 모두 되는 Duplex 스트림(자세히는 01편) |
| `net.isIP()` | 문자열이 IP 주소인지 검사(4, 6, 0 반환) |

- 연결 양쪽 끝에 각각 `Socket`이 있습니다. 서버가 받은 연결은 `connection` 이벤트로 `Socket`을 넘겨 받고, 클라이언트는 `net.connect()`가 `Socket`을 돌려줍니다.
- 소켓은 스트림이므로 `pipe`와 `pipeline`, backpressure 규칙이 그대로 적용됩니다(자세히는 02편).

## TCP 서버

`net.createServer()`의 콜백은 새 연결마다 한 번 실행되고 그 연결의 `Socket`을 받습니다. `listen()`으로 포트를 열면 서버가 시작됩니다.

```js
import net from 'node:net'

const server = net.createServer((socket) => {
  socket.write('hello\n')   // 연결되면 인사
  socket.pipe(socket)       // 받은 것을 그대로 돌려줌 (에코)
})
server.listen(0, '127.0.0.1', () => {
  console.log(server.address().port) // OS가 고른 빈 포트 번호
})
```

- 포트에 `0`을 주면 OS가 빈 포트를 골라 줍니다. 실제 번호는 `listening` 이벤트 뒤에 `server.address().port`로 읽습니다. 테스트에서 포트 충돌을 피하는 방법입니다(24편).
- 호스트에 `127.0.0.1`을 주면 같은 컴퓨터에서만 접속됩니다. 외부에서 받으려면 `0.0.0.0`이고, 이 선택은 25편에서 다룹니다.
- 이미 쓰는 포트를 열면 서버에 `error` 이벤트가 `EADDRINUSE`로 발생합니다.
- `server.close()`는 새 연결을 더 받지 않을 뿐, 이미 열린 연결은 끝날 때까지 유지합니다. 모든 연결이 끝나야 `close` 이벤트가 발생합니다. 연결을 강제로 끊으려면 각 소켓에 `destroy()`를 호출합니다.
- `server.maxConnections`로 동시 연결 수 상한을 둘 수 있습니다.

**흔한 실수:** 테스트나 스크립트에서 서버를 닫지 않아 프로세스가 끝나지 않는 것입니다. 열린 서버와 소켓은 이벤트 루프를 붙잡습니다(자세히는 27편).

## Socket

`net.Socket`은 TCP 연결 한 개를 나타내는 Duplex 스트림입니다. 쓰면 상대에게 가고, 상대가 보낸 바이트는 읽을 수 있는 데이터로 나옵니다. 클라이언트는 `net.connect()`로 만듭니다.

```js
import net from 'node:net'

const socket = net.connect(8124, 'localhost')
socket.on('connect', () => socket.write('ping'))
socket.on('data', (chunk) => console.log(chunk.toString()))
socket.setEncoding('utf8')   // 이후 data는 문자열
```

| 멤버 | 설명 |
|------|------|
| `socket.write(data)` | 데이터 전송. 내부 버퍼가 차면 `false`를 반환하고 비면 `drain` 이벤트 |
| `socket.end()` | 쓰기 쪽을 닫음(FIN 전송). 상대는 계속 보낼 수 있음 |
| `socket.destroy()` | 즉시 연결을 끊고 스트림을 파괴 |
| `socket.resetAndDestroy()` | RST 패킷을 보내며 파괴. 상대 쪽에서 `ECONNRESET` |
| `socket.remoteAddress`, `remotePort` | 상대의 주소와 포트 |
| `socket.setNoDelay()` | 작은 쓰기를 모으지 않고 바로 전송(Nagle 알고리즘 끔) |

- `connect`는 연결이 맺어졌을 때, `ready`는 그 직후 발생합니다.
- `write()`가 `false`를 반환하면 `drain` 이벤트까지 쓰기를 멈춥니다(자세히는 02편).
- `end()`와 `destroy()`는 다릅니다. `end()`는 보낼 것을 다 보내고 닫는 정상 종료이고, `destroy()`는 대기 중인 쓰기가 있어도 즉시 끊습니다.

## data, end, close

소켓의 생애는 세 이벤트로 구분됩니다.

| 이벤트 | 시점 |
|--------|------|
| `data` | 데이터가 도착함. 인자는 `Buffer`(`setEncoding` 후에는 문자열) |
| `end` | 상대가 더 보내지 않겠다고 알림(FIN). 읽기 쪽이 끝남 |
| `close` | 소켓이 완전히 닫힘. 인자 `hadError`는 전송 에러로 닫혔는지 여부 |

```js
// 클라이언트가 'ping'을 보내고 end()한 뒤 서버 쪽에서 본 순서
// server data ping
// server end
// server close false
```

- 기본값(`allowHalfOpen: false`)에서는 상대의 `end`를 받으면 이쪽도 쓰기 대기열을 비운 뒤 자동으로 `end()`하고 연결을 정리합니다. `allowHalfOpen: true`이면 자동으로 닫지 않으므로 `end()`를 직접 호출해야 합니다.
- `error`가 발생하면 곧바로 `close`가 이어집니다. 정리 코드는 `close`에 두면 정상 종료와 에러 종료를 모두 잡습니다.
- 소켓에 `error` 리스너가 없으면 에러가 처리되지 않은 예외가 되어 프로세스가 죽습니다. 소켓마다 `error`를 듣습니다.
- 서버는 연결마다 소켓을 얻으므로, 클라이언트 한 명의 에러가 서버 전체를 죽이지 않게 하려면 `connection` 콜백 안에서 `socket.on('error', ...)`를 등록합니다.

## 바이트 스트림이라 메시지 경계가 없음

TCP는 바이트를 순서대로 전달할 뿐, 어디서 한 메시지가 끝나는지는 모릅니다. 보낸 쓰기 횟수와 받는 `data` 이벤트 횟수는 일치하지 않습니다.

```js
// 클라이언트
socket.write('AAA')
socket.write('BBB')

// 서버의 data 이벤트
// 한 번에 "AAABBB"가 올 수도, "AAA"와 "BBB"로 나뉘어 올 수도,
// "AA"와 "ABBB"처럼 어긋나 올 수도 있다
```

- 로컬에서 실행하면 `AAABBB` 한 덩어리로 도착하는 일이 흔합니다. 개발 중에는 잘 되다가 네트워크가 느려지거나 메시지가 클 때 깨지는 버그의 원인입니다.
- 한 메시지가 여러 `data`로 쪼개지기도 하고, 여러 메시지가 한 `data`에 합쳐지기도 합니다.
- 그래서 `data` 한 번을 메시지 하나로 가정하면 안 됩니다. 수신 쪽은 받은 바이트를 모아 두고 메시지 단위로 잘라야 합니다.
- HTTP에서 `Content-Length`나 청크 방식이 있는 이유가 이것입니다(04편).

## 프레임 나누기

프레임은 바이트 스트림에서 메시지 하나의 시작과 끝을 알 수 있게 하는 규칙입니다. 대표적인 방식은 세 가지입니다.

| 방식 | 규칙 | 예 |
|------|------|----|
| 구분자 | 특정 바이트(줄바꿈 등)로 끝을 표시 | HTTP 헤더(`\r\n`), Redis 일부 응답 |
| 길이 접두사 | 메시지 앞에 본문 길이를 고정 크기로 붙임 | 많은 바이너리 프로토콜 |
| 고정 길이 | 모든 메시지가 같은 크기 | 단순한 센서 프로토콜 |

길이 접두사 방식을 직접 구현하면 이렇습니다. 앞 4바이트가 본문 길이(빅 엔디언 부호 없는 정수)입니다.

```js
function frameReader(onMessage) {
  let buf = Buffer.alloc(0)
  return (chunk) => {
    buf = Buffer.concat([buf, chunk])
    while (buf.length >= 4) {
      const len = buf.readUInt32BE(0)
      if (buf.length < 4 + len) break      // 아직 덜 옴
      onMessage(buf.subarray(4, 4 + len))
      buf = buf.subarray(4 + len)
    }
  }
}
const onFrame = (msg) => console.log(msg.toString())
socket.on('data', frameReader(onFrame))
```

- 도착한 청크를 버퍼에 이어 붙이고, 헤더를 읽을 만큼 쌓이면 길이를 확인하고, 본문이 다 모였을 때만 메시지를 꺼냅니다. 남은 바이트는 다음 청크와 이어 붙입니다.
- 보내는 쪽은 길이를 `writeUInt32BE`로 적은 4바이트와 본문을 이어서 씁니다. `hello`와 `world`를 합쳐 중간에서 쪼개 보내도 `hello`, `world` 순서로 두 메시지가 나옵니다.
- 줄 단위 프로토콜은 `node:readline`으로 소켓을 감싸 줄 단위로 읽을 수 있습니다(22편).
- 길이 값을 검증하지 않으면 상대가 큰 값을 보내 메모리를 소진시킬 수 있습니다. 허용 최대 길이를 정하고 넘으면 연결을 끊습니다.
- 수신 버퍼에 `Buffer.concat`을 반복하면 큰 메시지에서 복사가 늘어납니다. 대량 트래픽에서는 청크 목록을 모았다가 한 번에 합치는 방식이 낫습니다.

**흔한 실수:** 문자열로 바꿔 이어 붙이면서 길이를 문자 수로 세는 것입니다. 한글처럼 한 글자가 여러 바이트이면 길이가 어긋납니다. 길이는 항상 바이트 수입니다.

## dgram과 UDP

UDP는 연결 없이 데이터그램(독립된 패킷) 단위로 보내는 프로토콜입니다. `node:dgram` 모듈이 UDP 소켓을 제공합니다.

| 기준 | TCP | UDP |
|------|-----|-----|
| 연결 | 먼저 연결을 맺음 | 연결 없음 |
| 단위 | 바이트 스트림(경계 없음) | 데이터그램(보낸 단위 그대로 도착) |
| 전달 | 순서 보장, 유실 시 재전송 | 유실·중복·순서 바뀜 가능, 재전송 없음 |
| 용도 | 웹, DB, 파일 전송 | DNS, 실시간 음성·영상, 로그·메트릭 전송 |

```js
import dgram from 'node:dgram'

const server = dgram.createSocket('udp4')
server.on('message', (msg, rinfo) => {
  console.log(msg.toString(), rinfo.address, rinfo.family)
  // hi 127.0.0.1 IPv4
})
server.bind(0, '127.0.0.1')   // 포트 0이면 OS가 고름

const client = dgram.createSocket('udp4')
const { port } = server.address()
client.send('hi', port, '127.0.0.1', () => client.close())
```

- `createSocket('udp4')`는 IPv4, `'udp6'`는 IPv6 소켓입니다.
- 수신은 `message` 이벤트의 `(msg, rinfo)`로 합니다. `rinfo`는 보낸 쪽의 `address`, `family`, `port`, `size`를 담습니다.
- 보낼 때마다 목적지(`send(msg, port, address, callback)`)를 지정합니다. 연결 상태가 없으므로 상대가 듣고 있는지 알 수 없고, 아무도 듣지 않는 포트로 보내도 콜백의 에러는 `null`입니다. 전달 확인이 필요하면 애플리케이션이 응답 메시지를 직접 설계합니다.
- 메시지 경계가 있으므로 TCP와 달리 `message` 한 번이 보낸 데이터그램 하나입니다.
- 한 데이터그램의 크기는 네트워크 MTU(이더넷에서 보통 1500바이트)에 제한받습니다. 문서는 MTU를 넘는 데이터그램이 조용히 버려질 수 있다고 설명합니다. 작게 유지합니다.
- 브로드캐스트는 `socket.setBroadcast(true)`로 켭니다.
- `close()`로 소켓을 닫습니다. 닫지 않으면 TCP 서버처럼 프로세스가 끝나지 않습니다.

## dns

`node:dns`는 도메인 이름을 IP 주소로 바꾸는 이름 해석 기능을 제공합니다. 콜백 API(`node:dns`)와 Promise API(`node:dns/promises`)가 있습니다.

```js
import dns from 'node:dns/promises'

const { address, family } = await dns.lookup('localhost')
// { address: '::1', family: 6 }  (환경에 따라 127.0.0.1)
```

- 이름 해석은 `net.connect()`와 `fetch`가 호스트 이름으로 연결할 때 내부에서 자동으로 일어납니다. `dns` 모듈을 직접 쓰는 일은 주소를 미리 확인하거나 레코드를 조회할 때입니다.
- 이름이 없으면 `ENOTFOUND`(`getaddrinfo`)로 실패합니다. 이 코드는 표준 POSIX 에러가 아니라 Node가 DNS 실패(`EAI_NODATA`, `EAI_NONAME`)를 묶어 부르는 이름입니다.

## dns.lookup과 dns.resolve 차이

| 기준 | `dns.lookup()` | `dns.resolve*()`, `dns.reverse()` |
|------|----------------|-----------------------------------|
| 구현 | OS의 `getaddrinfo(3)` | c-ares 라이브러리로 DNS 서버에 직접 질의 |
| 설정 파일 | `/etc/hosts`, `nsswitch.conf` 등 OS 설정을 따름 | 사용하지 않음. hosts 파일을 보지 않음 |
| 실행 방식 | libuv 스레드 풀에서 실행 | 스레드 풀을 쓰지 않는 비동기 네트워크 I/O |
| 반환 | 주소 하나(`all: true`이면 전부) | 레코드 종류별(`resolve4`, `resolve6`, `resolveMx`, `resolveTxt` 등) |
| 용도 | `ping`처럼 OS와 같은 결과가 필요할 때 | DNS 레코드 자체를 조회할 때 |

- `net.connect()`와 `fetch`는 기본으로 `dns.lookup()`을 씁니다. 그래서 `/etc/hosts`에 적은 이름이 연결에는 통하지만 `dns.resolve4()`로는 찾아지지 않습니다.
- `dns.lookup()`은 비동기 API처럼 보여도 스레드 풀에서 도는 동기 함수를 부릅니다. 스레드 풀(기본 4개)을 파일 시스템 작업 등과 나눠 쓰므로 DNS 지연이 쌓이면 다른 작업도 느려질 수 있다고 문서가 경고합니다.
- `lookup`의 `family`는 `4`, `6`, `0`(둘 다)이고, `all: true`이면 주소 배열을 돌려줍니다.
- 결과 순서는 `order` 옵션이 정합니다. 기본값은 `verbatim`으로, DNS가 돌려준 순서 그대로입니다. `dns.setDefaultResultOrder('ipv4first')`로 전역 기본값을 바꿉니다.

```js
await dns.lookup('localhost', { all: true })
// [{ address: '::1', family: 6 },
//  { address: '127.0.0.1', family: 4 }]
await dns.lookup('no-such-host.invalid')
// ENOTFOUND (syscall: 'getaddrinfo')
await dns.resolve4('example.com') // IPv4 주소 배열
```

**흔한 실수:** `dns.resolve`로 확인한 결과가 실제 연결과 같다고 믿는 것입니다. 연결은 `lookup`(hosts 파일, OS 설정 포함)을 쓰므로 둘의 결과가 다를 수 있습니다.

## 타임아웃

TCP에는 타임아웃이 기본으로 없습니다. 상대가 응답하지 않아도 소켓은 무한정 열려 있습니다. `socket.setTimeout(ms)`가 유휴 시간 제한을 둡니다.

```js
const socket = net.connect({ port, host })
socket.setTimeout(3000)
socket.on('timeout', () => {
  socket.destroy(new Error('idle timeout'))
})
```

- 마지막 활동 이후 `ms` 동안 읽고 쓰기가 없으면 `timeout` 이벤트가 발생합니다. 활동이 있으면 시간이 다시 시작됩니다.
- `timeout` 이벤트는 알림일 뿐 연결을 끊지 않습니다. 직접 `end()`나 `destroy()`를 호출해야 합니다. 이 호출이 빠지면 타임아웃을 설정해도 소켓은 계속 열려 있습니다.
- `setTimeout(0)`은 타임아웃을 끕니다. `net.createConnection()`의 `timeout` 옵션은 연결을 시작하기 전에 `setTimeout`을 호출하는 것과 같습니다.
- `setTimeout`은 유휴 시간 제한입니다. 연결을 맺는 데 걸리는 시간 제한이 아니므로 연결 단계의 제한은 `AbortSignal.timeout()` 같은 별도 수단과 함께 씁니다(HTTP 쪽은 06편).
- 서버의 소켓에도 같은 방식으로 적용합니다. 아무것도 보내지 않는 연결이 쌓여 자원을 잡는 것을 막습니다.

**흔한 실수:** `timeout` 리스너 없이 `setTimeout`만 호출하는 것입니다. 이벤트를 듣는 코드가 없으면 아무 일도 일어나지 않습니다.

## 소켓 에러

소켓 에러는 `error` 이벤트로 전달되고 직후 `close`가 발생합니다. 에러 객체의 `code`(문자열), `syscall`, `address`, `port`로 원인을 구분합니다.

```js
socket.on('error', (err) => {
  console.error(err.code, err.syscall, err.address)
  // ECONNREFUSED connect 127.0.0.1
})
```

- `code`로 분기하고 `message` 문자열 비교는 하지 않습니다.
- 에러가 나면 소켓은 더 쓸 수 없으므로 재연결은 새 소켓을 만들어서 합니다.
- 서버에서는 연결마다 `error` 리스너를 달아 한 연결의 에러가 프로세스 전체에 퍼지지 않게 합니다.

| 코드 | 뜻 | 보통의 원인 |
|------|----|-------------|
| `ECONNREFUSED` | 대상이 연결을 적극적으로 거부 | 그 포트에서 서비스가 떠 있지 않음 |
| `ETIMEDOUT` | 연결이나 전송에 상대가 응답하지 않음 | 방화벽 차단, 호스트 다운, 경로 문제 |
| `ECONNRESET` | 상대가 연결을 강제로 끊음(RST) | 상대 프로세스 종료·재시작, 상대의 타임아웃 |
| `EPIPE` | 상대가 닫은 소켓에 씀 | 상대가 이미 끊은 연결에 계속 `write` |
| `EADDRINUSE` | 이미 사용 중인 주소에 바인드 | 같은 포트로 서버를 두 번 띄움 |
| `ENOTFOUND` | 이름 해석 실패 | 도메인 오타, DNS 문제 |

### ECONNREFUSED

닫힌 포트로 연결하면 상대 OS가 즉시 거절 신호를 돌려줘서 바로 실패합니다.

```js
const bad = net.connect(closedPort, '127.0.0.1')
bad.on('error', (e) => console.log(e.code, e.syscall))
// ECONNREFUSED connect
```

- 거부 응답이 즉시 오므로 오래 기다리지 않고 실패합니다. 서비스가 아직 안 떴거나, 포트·호스트 설정이 틀렸거나, 서비스가 `127.0.0.1`에만 열려 있어 외부에서 접속한 경우입니다.
- 컨테이너 안에서 `localhost`는 그 컨테이너 자신입니다. 다른 컨테이너의 DB에 `localhost`로 접속하면 `ECONNREFUSED`가 납니다.
- 호스트 이름이 여러 주소로 풀릴 때는 시도한 주소마다의 실패가 `AggregateError`로 묶여 나옵니다(아래 "Happy Eyeballs"). 그때 `err.code`가 `ECONNREFUSED`이고 `err.errors`에 주소별 에러가 있습니다.
- 외부 서비스가 일시적으로 내려갔을 때를 대비해 재시도에 지연을 둡니다(재시도는 16편).

### ETIMEDOUT

`ETIMEDOUT`은 연결 요청이나 전송에 상대가 정해진 시간 안에 응답하지 않았을 때입니다. 거부(`ECONNREFUSED`)와 달리 응답 자체가 없습니다.

- 방화벽이 패킷을 조용히 버리거나 호스트가 꺼져 있으면 응답이 없어 OS의 연결 제한 시간이 지난 뒤에 실패하므로 오래 걸립니다.
- Node 문서는 이 에러가 소켓에 `end()`를 제대로 호출하지 않은 신호일 수도 있다고 덧붙입니다.
- 애플리케이션이 `socket.setTimeout()`으로 정한 시간이 지나면 에러가 아니라 `timeout` 이벤트가 발생하는 것과 구분합니다. `ETIMEDOUT`은 OS가 올리는 에러입니다.
- 대응은 연결 타임아웃을 짧게 걸고, 재시도에 상한을 두는 것입니다. 오래 걸리는 실패는 서버 전체의 요청 처리를 붙잡습니다(06편).

### EPIPE와 ECONNRESET

두 에러는 이미 끊어진 연결을 쓸 때 납니다.

- `EPIPE`는 상대가 닫은 소켓에 쓴 경우입니다. 문서는 스트림의 원격 쪽이 닫혔다는 신호라고 설명합니다.
- `ECONNRESET`은 상대가 연결을 강제로 끊었다는 뜻입니다. 상대가 `resetAndDestroy()`를 호출하거나 프로세스가 비정상 종료되면 이쪽에서 보입니다.

```js
// 상대가 RST로 끊으면 이쪽 소켓의 error 이벤트에서
// err.code === 'ECONNRESET'
```

- 운영체제에 따라 같은 상황에서 다른 코드가 나옵니다. 상대가 닫은 연결에 쓰면 Linux에서는 `EPIPE`가 흔하고, Windows에서 같은 상황을 재현하면 `ECONNABORTED`가 나왔습니다. 하나의 코드만 검사하지 말고 "이미 끊긴 연결에 대한 에러"로 묶어 처리합니다.
- 이 에러들은 클라이언트가 먼저 끊고 서버가 응답을 쓰는 경쟁 때문에 서버에서 정상적으로도 자주 발생합니다. 로그에 심각한 에러로 남기지 말고 연결 종료로 취급합니다.
- 연결 풀의 유휴 소켓이 상대(DB, 로드 밸런서)의 유휴 제한 시간에 끊긴 뒤 재사용되면 `ECONNRESET`이 납니다. 풀의 유휴 시간 제한을 상대보다 짧게 둡니다(06편, 17편).

## Happy Eyeballs

Happy Eyeballs는 호스트가 IPv6와 IPv4 주소를 모두 가질 때 한쪽이 막혀 있어도 빠르게 연결되도록 여러 주소를 번갈아 시도하는 알고리즘입니다(RFC 8305). Node에서는 `net.connect()`의 `autoSelectFamily` 옵션이 담당합니다.

```js
const socket = net.connect({
  port: 443,
  host: 'example.com',
  autoSelectFamily: true,                // 기본값
  autoSelectFamilyAttemptTimeout: 250,   // 시도 간격(ms)
})
socket.on('connectionAttemptFailed', (ip, p, fam, err) => {
  console.log(ip, err.code)
})
```

- `autoSelectFamily`는 Node 20부터 기본값이 `true`입니다. 전역 기본값은 `net.setDefaultAutoSelectFamily(false)`로 바꿀 수 있습니다.
- 주소 목록을 순서대로 시도하되, 한 시도가 끝나기를 기다리지 않고 `autoSelectFamilyAttemptTimeout` 간격이 지나면 다음 주소를 시작합니다. 앞선 시도는 계속 진행되며 먼저 성공한 연결을 씁니다. 최소값은 10ms이고 Node 24에서 기본값은 250ms입니다. `net.getDefaultAutoSelectFamilyAttemptTimeout()`으로 현재 값을 읽습니다.
- 모든 시도가 실패하면 시도별 에러를 모은 `AggregateError`가 `error`로 발생합니다.

```js
// localhost에 연결했는데 아무도 듣지 않을 때
// AggregateError, code 'ECONNREFUSED'
// err.errors의 주소: ['::1', '127.0.0.1']
```

- 관련 이벤트는 `connectionAttempt`, `connectionAttemptFailed`, `connectionAttemptTimeout`이며 시도 단위 로그를 남길 때 씁니다.
- IPv6가 깨진 환경에서 연결이 몇 초씩 걸리던 문제를 줄여 줍니다. 그럼에도 느리면 `dns.setDefaultResultOrder('ipv4first')`로 IPv4를 먼저 시도하게 할 수 있습니다.
- `localhost`가 `::1`로 풀리는데 서버가 `127.0.0.1`에만 열려 있으면 첫 시도가 거부되고 다음 주소에서 성공하는 식으로 가려져 있었다가, 모든 주소가 막혔을 때 `AggregateError`로 드러납니다.

## 핵심 정리

- `node:net`의 `Server`는 연결마다 `Socket`을 만들고, `Socket`은 Duplex 스트림이며 포트 0으로 열면 OS가 빈 포트를 골라 준다.
- 소켓은 `data`, `end`, `close` 순으로 끝나고, `error` 뒤에는 `close`가 오며, `error` 리스너가 없으면 프로세스가 죽는다.
- TCP는 메시지 경계가 없어 `data` 한 번이 메시지 하나가 아니므로 구분자나 길이 접두사로 프레임을 직접 나눈다.
- UDP(`dgram`)는 연결 없이 데이터그램 단위로 보내고 유실·순서 바뀜을 보장하지 않으며 `message` 한 번이 데이터그램 하나다.
- `dns.lookup()`은 OS의 `getaddrinfo`(hosts 파일 포함, 스레드 풀)이고 `dns.resolve*()`는 DNS 서버에 직접 질의하며 연결에는 `lookup`이 쓰인다.
- `setTimeout`은 유휴 알림일 뿐 직접 닫아야 하고, 에러 코드는 `ECONNREFUSED`(거부)·`ETIMEDOUT`(무응답)·`ECONNRESET`과 `EPIPE`(끊긴 연결)를 구분하며, `autoSelectFamily`는 IPv6·IPv4를 번갈아 시도한다.

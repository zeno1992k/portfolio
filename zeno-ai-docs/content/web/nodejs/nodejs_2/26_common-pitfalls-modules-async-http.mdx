## CJS와 ESM을 섞다 죽음

Node.js에는 모듈 시스템이 둘 있습니다. CommonJS(CJS)는 `require()`와 `module.exports`를, ES Modules(ESM)는 `import`와 `export`를 씁니다. 파일이 어느 쪽으로 해석되는지는 확장자와 가장 가까운 `package.json`의 `"type"`이 정합니다(자세히는 기초 08편, 09편).

| 파일 | 해석 |
|------|------|
| `.mjs` | 항상 ESM |
| `.cjs` | 항상 CJS |
| `.js` + `"type": "module"` | ESM |
| `.js` + `"type": "commonjs"` | CJS |
| `.js` + `"type"` 없음 | CJS로 먼저 실행해 보고, ESM 문법 때문에 실패하면 ESM으로 다시 해석(구문 감지, 안정성 지수 1.2) |

섞어 쓸 때 나는 에러는 방향별로 정해져 있습니다.

| 증상 | 원인 | 해결 |
|------|------|------|
| `ReferenceError: require is not defined in ES module scope` | ESM 파일에서 `require` 호출 | `import`로 바꾸거나 `createRequire` 사용 |
| `SyntaxError: Cannot use import statement outside a module` | CJS로 해석되는 파일에 `import` | `"type": "module"` 지정 또는 `.mjs` |
| `ERR_REQUIRE_ASYNC_MODULE` | `require()`한 ESM에 top-level await가 있음 | `import()`로 로드 |
| `SyntaxError: Named export 'a' not found` | CJS 모듈에서 named import가 감지되지 않음 | default import 후 구조 분해 |

```js
import { createRequire } from 'node:module'

const require = createRequire(import.meta.url)
const legacy = require('./old.cjs') // ESM 안에서 require
const mod = await import('./new.mjs') // CJS에서는 import()를 씀
```

- ESM에서 CJS를 `import`하는 것은 항상 됩니다. CJS 모듈의 `module.exports` 값이 `default`로 들어오고, 소스를 정적 분석해 찾아낸 이름은 named export로도 제공됩니다. 분석은 흔한 패턴만 인식하므로 `module.exports = { a: 1 }`처럼 값이 리터럴이면 `a`를 named import할 수 없습니다. default로 받아 구조 분해하면 됩니다.
- CJS에서 ESM을 `require()`하는 것은 Node.js 24에서 동기 ESM에 한해 가능합니다. 22.12·20.19부터 플래그 없이 되고, 문서상 Node.js 24.15.0에서 실험적 표시가 사라졌습니다. `require()`는 모듈 네임스페이스 객체를 돌려줍니다.
- 정적 `import` 문은 최상위에서만 쓸 수 있어서 CJS 파일에서는 동적 `import()`(Promise 반환)로 ESM을 불러옵니다.
- `package.json`에 `"type"`이 없는 상태에서 ESM 문법을 쓰면 실행은 되지만 `MODULE_TYPELESS_PACKAGE_JSON` 경고가 나고 파싱을 두 번 합니다. 새 프로젝트는 `"type": "module"`을 명시합니다.
- `"type": "commonjs"`를 명시한 프로젝트에서는 위 감지가 일어나지 않고 `Cannot use import statement outside a module`이 납니다.

**흔한 실수:** 에러가 났다고 `"type"`을 오가며 바꾸는 것입니다. 프로젝트 전체의 `"type"`을 바꾸면 모든 `.js`의 해석이 바뀌어 다른 파일이 깨집니다. 한 파일만 예외라면 확장자(`.cjs`, `.mjs`)로 구분합니다.

## `__dirname`이 ESM에 없음

`__dirname`과 `__filename`은 CJS 모듈 래퍼가 주입하는 변수라서 ESM에는 없습니다. ESM에서 쓰면 `ReferenceError: __dirname is not defined in ES module scope`입니다. `require`, `exports`, `module`도 마찬가지입니다.

| CJS | ESM 대체 |
|-----|----------|
| `__filename` | `import.meta.filename` |
| `__dirname` | `import.meta.dirname` |
| `require.main === module` | `import.meta.main` |
| `require.resolve(x)` | `import.meta.resolve(x)` 또는 `new URL(x, import.meta.url)` |

```js
import { join } from 'node:path'

const file = join(import.meta.dirname, 'data.json')
// /app/data.json (이 모듈이 있는 디렉터리 기준)
```

- `import.meta.dirname`과 `import.meta.filename`은 Node.js 20.11·21.2에서 추가됐고 24.0.0에서 실험적 표시가 사라졌습니다. 이 모듈이 `file:` URL일 때만 있습니다.
- `import.meta.main`은 Node.js 24.2.0에서 추가됐고 안정성 지수가 1.0(초기 개발)입니다. 운영 코드에서는 쓰기 전에 현재 문서의 상태를 확인합니다.
- 더 오래된 버전도 지원해야 하면 `fileURLToPath(import.meta.url)`로 파일 경로를 얻고 `dirname()`을 적용합니다.
- `process.cwd()`는 모듈 위치가 아니라 프로세스를 시작한 디렉터리입니다. 상대 경로를 `cwd` 기준으로 읽는 코드는 어디서 실행하느냐에 따라 깨집니다. 모듈 기준 경로가 필요하면 위 값을 씁니다.

**흔한 실수:** `new URL('./data.json', import.meta.url).pathname`을 파일 경로로 쓰는 것입니다. Windows에서는 `/C:/...` 형태가 되어 퍼센트 인코딩이 남습니다. 경로가 필요하면 `fileURLToPath()`로 바꿉니다.

## 확장자 누락

ESM의 `import`는 상대·절대 경로에서 확장자를 반드시 써야 합니다. 디렉터리 인덱스(`./sub/index.js`)도 전체 경로로 적어야 합니다. CJS의 `require('./util')`처럼 확장자를 보충해 주지 않습니다.

```js
import { x } from './util'     // ❌ ERR_MODULE_NOT_FOUND
import { x } from './util.js'  // ✅
import { y } from './sub'  // ❌ ERR_UNSUPPORTED_DIR_IMPORT
import { y } from './sub/index.js' // ✅
```

- 에러 메시지에 `Did you mean to import "./util.js"?`처럼 고칠 경로가 함께 나옵니다.
- 이 규칙은 브라우저에서의 `import` 동작과 같은 것입니다.
- 패키지 이름만 쓰는 `import 'express'`는 해당하지 않습니다. 그 경우는 패키지의 `exports`가 해석합니다(다음 절, 기초 10편).
- TypeScript로 쓴 ESM을 `tsc`로 컴파일해 `.js`를 실행하는 구성에서는 `.ts` 파일을 `./util.js`로 import합니다. 실행되는 파일이 `.js`이기 때문이고, TypeScript는 `.js` 지정자를 같은 이름의 `.ts` 파일로 연결해 타입을 찾습니다. 옵션(`module`, `moduleResolution`)은 TypeScript 문서를 따릅니다.
- 같은 에러가 `Cannot find module` 형태로 나오는 경우는 CJS의 `require`에서 파일이 없을 때(`MODULE_NOT_FOUND`)입니다. ESM에서는 `ERR_MODULE_NOT_FOUND`입니다.

**흔한 실수:** 확장자 없는 import가 되던 CJS 코드를 ESM으로 옮기면서 수십 개 파일의 import를 고치는 것을 빠뜨리는 것입니다. 실행 시점의 첫 에러만 보이므로 한 파일씩 고쳐서는 오래 걸립니다. 린터나 코드 검색으로 상대 경로 import를 한꺼번에 점검합니다.

## exports 맵에 경로가 없음

패키지의 `package.json`에 `"exports"`가 있으면 그 맵에 적힌 경로만 import할 수 있습니다. 적히지 않은 파일은 디스크에 있어도 접근할 수 없습니다. 에러는 `ERR_PACKAGE_PATH_NOT_EXPORTED`입니다.

```js
// pkg의 exports: { ".": "./index.js" }
import a from 'pkg'         // ✅
import b from 'pkg/lib/x.js' // ❌ NOT_EXPORTED
import c from 'pkg/package.json' // ❌ (JSON도 예외 아님)
```

에러 메시지는 `Package subpath './lib/x.js' is not defined by "exports"` 형태입니다.

- `"exports"`와 `"main"`이 둘 다 있으면 `"exports"`가 우선합니다.
- 패키지가 나중에 `"exports"`를 추가하면 정의하지 않은 진입점을 쓰던 사용자 코드가 깨집니다. 그래서 패키지 저자는 이전에 되던 경로를 모두 `exports`에 넣어야 합니다. 폴더 전체는 `"./lib/*": "./lib/*.js"` 같은 패턴으로 엽니다.
- `import`와 `require`의 조건을 나눠서 정의한 패키지에서 한쪽 조건만 있으면 다른 방식으로 불러올 때 같은 에러가 납니다. 예를 들어 `"exports": { "import": "./i.mjs" }`만 있는 패키지를 `require('cond')`하면 `No "exports" main defined`로 `ERR_PACKAGE_PATH_NOT_EXPORTED`입니다(실행으로 확인).
- 해결책은 소비자 쪽에서는 공개된 진입점만 쓰는 것입니다. 패키지 문서가 안내하는 경로를 확인하고, 없으면 패키지 이슈로 공개를 요청합니다. `node_modules` 안의 파일을 직접 가리키는 것은 피합니다.
- 소비자 쪽에서 자주 쓰는 `pkg/package.json` 읽기도 `exports`에 `"./package.json"`이 있어야 합니다.
- 자기 패키지의 `exports`를 고칠 수 있다면 필요한 하위 경로를 추가합니다.

**흔한 실수:** 패키지의 내부 파일 경로(`pkg/dist/internal/x.js`)를 import하는 것입니다. 한 버전에서 우연히 되어도 `exports`로 막히거나 파일 구조가 바뀌면 업그레이드 때 깨집니다.

## await 누락

`async` 함수는 항상 Promise를 반환합니다. 호출할 때 `await`를 빼면 값 대신 Promise 객체가 변수에 들어가고, 그 코드는 에러 없이 이상한 값으로 흘러갑니다.

```js
async function getUser() { return { id: 1 } }

const user = getUser()
console.log(user)    // Promise { <pending> }
console.log(user.id) // undefined
if (user) {}         // 항상 참 (Promise 객체)
```

- `if (user)`처럼 Promise를 조건으로 쓰면 항상 참입니다. 권한 검사나 존재 확인에서 `await`를 빼면 검사가 항상 통과합니다.
- `await`를 빼면 `try`/`catch`가 에러를 잡지 못합니다. Promise가 거부(reject)되는 시점은 `try` 블록이 끝난 뒤입니다.
- 거부된 Promise에 처리기가 없으면 unhandled rejection이 됩니다. Node.js 15부터 기본 모드(`--unhandled-rejections=throw`)는 `unhandledRejection` 이벤트 리스너가 없으면 잡히지 않은 예외로 올려서 프로세스가 종료 코드 1로 끝납니다.

```js
async function fail() { throw new Error('boom') }
try {
  fail() // ❌ await 누락
} catch (e) { /* 실행되지 않음 */ }
// Error: boom 으로 프로세스 종료 (종료 코드 1)
```

- 의도적으로 기다리지 않고 실행만 시키는 경우("fire and forget")에도 `.catch()`를 붙여서 거부를 처리합니다.
- 반환 시점에 따라 에러 처리 위치가 달라집니다. `try` 안에서 `return promise`는 `try`가 못 잡고, `return await promise`는 잡습니다.
- 정적 검사로 잡을 수 있습니다. typescript-eslint의 `no-floating-promises` 규칙은 에러 처리가 없는 Promise 문을 보고합니다.
- 반대로 `await` 대상이 Promise가 아니어도 에러는 아닙니다. 값을 그대로 돌려줄 뿐이라서 누락과 달리 필요 없는 `await`는 증상 없이 숨어 있습니다.

**흔한 실수:** 콜백 안에서 `await`를 빼는 것입니다. `array.map(async ...)`의 결과는 값 배열이 아니라 Promise 배열입니다. 값이 필요하면 `await Promise.all(...)`로 받습니다.

## forEach + async

`Array.prototype.forEach`는 콜백의 반환값을 쓰지 않고 기다리지도 않습니다. 콜백이 `async`여도 `forEach`는 Promise를 버리고 즉시 끝나서, 뒤의 코드가 작업이 끝나기 전에 실행됩니다.

```js
list.forEach(async (n) => { await save(n) })
console.log('after forEach') // save가 끝나기 전에 출력
```

```js
await Promise.all(list.map((n) => save(n))) // ✅ 병렬
for (const n of list) await save(n)         // ✅ 순차
```

| 방법 | 실행 | 에러 | 용도 |
|------|------|------|------|
| `forEach(async ...)` | 기다리지 않음 | 거부가 처리되지 않음 | 쓰지 않는다 |
| `for...of` + `await` | 순차 | `try`/`catch`로 잡음 | 순서가 중요하거나 하나씩 처리 |
| `Promise.all(map(...))` | 병렬, 모두 완료까지 대기 | 하나가 거부되면 즉시 거부 | 서로 독립적이고 전부 필요 |
| `Promise.allSettled(map(...))` | 병렬, 모두 완료까지 대기 | 거부해도 결과 배열에 담김 | 일부 실패를 허용 |

- 실행에서 `forEach`는 `after forEach`가 먼저 출력되고 저장 로그가 나중에 나왔습니다. `for...of`는 항상 순서대로입니다.
- `Promise.all`은 요소 수만큼 작업을 동시에 시작합니다. 수천 건의 DB·HTTP 요청을 한꺼번에 시작하면 연결 한도나 서버를 압박합니다. 동시 실행 수를 제한하려면 배열을 일정 크기로 나눠 묶음마다 `Promise.all`을 하거나, 제한 기능이 있는 라이브러리를 씁니다.
- `forEach` 안의 `async`에서 던진 에러는 호출한 쪽에서 잡을 수 없고 unhandled rejection이 되어 프로세스를 끝낼 수 있습니다.
- `filter`, `reduce`, `some`, `every`도 콜백이 `async`이면 같은 문제가 있습니다. Promise가 항상 참이라 `filter(async ...)`는 아무것도 거르지 않습니다.

**흔한 실수:** `filter(async (x) => await check(x))`입니다. 반환값이 Promise라서 모든 요소가 통과합니다. 먼저 `await Promise.all(list.map(check))`로 결과 배열을 얻은 뒤 그 결과로 거릅니다.

## 에러를 빈 catch로 삼킴

`catch {}`처럼 비워 둔 `catch`는 에러를 조용히 없앱니다. 실패가 일어나도 로그도 종료도 없어서, 나중에 이상한 값과 만나서야 원인 없는 증상으로 나타납니다.

```js
try {
  await writeFile(path, data)
} catch {}  // ❌ 쓰기 실패가 사라짐
```

- 에러를 삼켜도 되는 경우는 "실패가 정상 경로의 한 갈래"일 때뿐입니다. 그런 경우도 기대하는 에러만 좁혀서 무시합니다.

```js
try {
  return await readFile(path, 'utf8')
} catch (err) {
  if (err.code !== 'ENOENT') throw err // 다른 에러는 다시 던짐
  return null
}
```

- 처리할 수 없는 에러는 다시 던지거나 `cause`로 감싸서 던집니다. `new Error('설정 로드 실패', { cause: err })`처럼 쓰면 원래 에러가 보존됩니다.
- 로그만 남기고 넘어가는 경우에도 에러 객체 전체(메시지와 스택)를 남기고, 메시지 문자열만 찍지 않습니다.
- `.catch(() => {})`도 같은 문제입니다. 특히 `fire and forget` 호출에 이를 붙이면 실패가 영원히 보이지 않습니다.
- 에러 판별은 메시지 문자열이 아니라 `err.code`나 `err.name`으로 합니다. 메시지는 버전과 환경에 따라 바뀝니다.
- 프로세스가 에러로 죽는 것이 나쁜 것이 아닙니다. 복구할 수 없는 상태에서 계속 실행하는 것이 더 나쁩니다. 그때는 시작 시 설정 검증처럼 일찍 크게 실패하게 둡니다(자세히는 25편).

**흔한 실수:** 테스트를 통과시키려고 `catch`에서 에러를 지우는 것입니다. 테스트는 통과하지만 실패 경로의 원인이 숨습니다.

## 콜백과 Promise를 같이 완료

하나의 작업이 콜백도 부르고 Promise도 이행(resolve)·거부(reject)하게 만들면 같은 결과를 두 번 전달하게 되고, 한쪽에서 난 에러가 다른 쪽을 연쇄적으로 호출합니다.

```js
function load(path, cb) {
  return new Promise((resolve, reject) => {
    readFile(path, 'utf8', (err, text) => {
      if (err) { cb(err); return reject(err) }
      try { cb(null, text); resolve(text) }
      catch (e) { cb(e); reject(e) } // ❌ cb가 두 번 호출됨
    })
  })
}
```

- 콜백 `cb(null, text)`가 던진 에러를 `catch`가 잡아 `cb(e)`를 다시 호출합니다. 콜백은 성공 한 번, 실패 한 번으로 모두 두 번 불립니다(실행으로 확인). Promise는 첫 결과만 확정되고 이후의 `resolve`·`reject` 호출은 무시됩니다.
- 콜백은 정확히 한 번만 호출해야 합니다. 두 번 호출하면 호출한 쪽의 완료 로직이 두 번 돌아가고, 스트림 구현에서는 `ERR_MULTIPLE_CALLBACK` 에러가 납니다.
- Promise는 한 번 확정되면 값이 바뀌지 않습니다. `resolve(1); reject(err)`에서 `reject`는 조용히 무시되므로 에러가 사라집니다.
- 콜백과 Promise를 하나의 함수에서 겸하는 API를 만들지 않습니다. Node.js도 `fs`(콜백)와 `fs/promises`로 나눴습니다.
- 콜백 API를 Promise로 바꿀 때는 직접 감싸지 말고 `util.promisify`를 쓰고, 반대 방향은 `util.callbackify`를 씁니다(자세히는 22편).
- 사용자 콜백 안에서 던져진 에러를 라이브러리가 삼키거나 다시 콜백으로 돌려 보내지 않아야 합니다. 콜백 호출은 `try` 바깥에 둡니다.

**흔한 실수:** `if (err) cb(err)` 뒤에 `return`을 빼는 것입니다. 에러 처리 후에도 아래 코드가 이어져 `cb(null, result)`가 한 번 더 불립니다.

## 본문을 두 번 읽기

요청 본문(`req`)은 스트림이라서 한 번 읽으면 사라집니다. 두 번째 읽기는 빈 값을 주거나 영원히 기다립니다(자세히는 4편, 11편).

```js
for await (const c of req) first.push(c) // 본문 전체
for await (const c of req) second.push(c) // 아무것도 없음
// first는 5바이트, second는 0바이트 (실행 결과)
```

- 이미 끝난 스트림에서 `'end'`나 `'data'` 이벤트를 새로 기다리면 이벤트가 다시 발생하지 않아서 요청이 응답 없이 멈춥니다. 클라이언트는 타임아웃까지 기다립니다.
- 흔한 원인은 미들웨어와 핸들러가 둘 다 본문을 읽는 구성입니다. 앞에서 파서가 본문을 읽고 `req.body`에 넣었다면, 뒤에서는 `req.body`를 씁니다.
- 읽은 결과는 변수에 보관해서 쓰고, 한 곳에서만 읽습니다. 여러 곳이 필요하면 처음 읽을 때 `Buffer`로 모아 저장합니다.
- 서명 검증처럼 파싱 전의 원본 바이트가 필요하면 파서보다 먼저 원본을 보관하는 단계를 둡니다.

`fetch`의 `Response`도 같습니다. 본문을 한 번 읽으면 소비되어 다시 읽을 수 없습니다.

```js
const res = await fetch(url)
await res.json()
await res.text() // TypeError: Body is unusable
```

- 두 번 읽어야 하면 읽기 전에 `res.clone()`으로 복제본을 만듭니다. 복제하면 데이터를 메모리에 두 벌 보관하므로 큰 응답에는 맞지 않습니다.
- 본문을 JSON으로 읽을지 텍스트로 읽을지 모를 때는 `res.text()`로 한 번 읽고 직접 `JSON.parse`합니다.

**흔한 실수:** 디버깅하려고 `console.log(await res.text())`를 넣었다가 이후의 `await res.json()`이 깨지는 것입니다. 로그 한 줄이 본문을 소비합니다.

## JSON이 아닌데 JSON.parse

`JSON.parse`는 JSON이 아닌 문자열에 `SyntaxError`를 던집니다. 외부에서 온 값(요청 본문, 서버 응답, 파일)은 JSON이라는 보장이 없습니다.

| 입력 | 에러 메시지(Node.js 24) |
|------|-------------------------|
| `<html>` (HTML 에러 페이지) | `Unexpected token '<', "<html>" is not valid JSON` |
| 빈 문자열 | `Unexpected end of JSON input` |
| `undefined` | `"undefined" is not valid JSON` |
| `{'a':1}` (작은따옴표) | `Expected property name or '}' in JSON at position 1` |
| `{"a":1,}` (끝 쉼표) | `Expected double-quoted property name in JSON at position 7` |

- `Unexpected token '<'`는 JSON을 기대한 자리에 HTML이 왔다는 신호입니다. 보통 API가 에러 페이지나 로그인 페이지를 돌려준 경우입니다.
- 메시지의 형식은 V8 버전에 따라 달라질 수 있으니 문자열이 아니라 `err.name`(`SyntaxError`)으로 구분합니다.
- 서버에서 클라이언트 입력을 파싱할 때는 `try`/`catch`로 감싸고 실패하면 400으로 응답합니다. 처리하지 않으면 비동기 핸들러 안의 에러가 요청을 끝내지 못하고 프로세스를 끝낼 수 있습니다.

```js
let body
try {
  body = JSON.parse(raw)
} catch {
  res.statusCode = 400
  return res.end('invalid JSON')
}
```

- 파싱에 성공해도 모양이 맞는다는 보장은 아닙니다. `JSON.parse('null')`은 `null`을, `JSON.parse('1')`은 숫자를 돌려줍니다. 파싱 뒤에 스키마 검증이 필요합니다(자세히는 8편).
- 클라이언트로 `fetch`할 때는 `res.ok`와 `Content-Type`을 확인한 뒤 `res.json()`을 호출합니다. 에러 응답이 JSON이 아닐 수 있습니다.
- `JSON.parse(undefined)`가 에러인 이유는 인수를 문자열 `'undefined'`로 바꾸기 때문입니다. 값이 없는 경우를 먼저 걸러냅니다.

**흔한 실수:** `res.json()`이 실패한 이유를 파싱 코드에서 찾는 것입니다. 먼저 상태 코드와 실제 응답 본문을 확인합니다. 대부분 서버가 JSON이 아닌 에러 페이지를 돌려준 경우입니다.

## 헤더를 end 이후에 설정

HTTP 응답은 상태줄과 헤더가 먼저 전송되고 본문이 이어집니다. 헤더가 한 번 나가면 수정할 수 없습니다. 응답을 끝낸 뒤에 헤더나 상태 코드를 바꾸려 하면 `ERR_HTTP_HEADERS_SENT`입니다(자세히는 4편).

```js
res.end('done')
res.setHeader('X-Late', '1') // ❌ ERR_HTTP_HEADERS_SENT
res.writeHead(500)           // ❌ ERR_HTTP_HEADERS_SENT
res.write('more')            // ❌ ERR_STREAM_WRITE_AFTER_END
```

- 에러 메시지는 `Cannot set headers after they are sent to the client`입니다. `res.write`·`res.end`로 본문을 보낸 시점에 헤더가 확정됩니다.
- `res.end()` 뒤에 `res.write()`를 하면 `write after end`(`ERR_STREAM_WRITE_AFTER_END`)이고, 이 에러는 응답 객체의 `'error'` 이벤트로도 전달됩니다.
- 가장 흔한 원인은 응답한 뒤 `return` 없이 코드가 이어지는 것입니다. 에러 응답을 보내고도 아래의 정상 응답 코드가 한 번 더 실행됩니다.

```js
if (!user) {
  res.statusCode = 404
  res.end('not found')
  return // ❌ 이것을 빼면 아래도 실행되어 ERR_HTTP_HEADERS_SENT
}
res.end(JSON.stringify(user))
```

- 비동기 코드에서는 타이밍 문제도 있습니다. 타임아웃 핸들러가 응답한 뒤 원래 작업이 끝나서 또 응답하려는 경우입니다. 응답 객체의 `res.headersSent`와 `res.writableEnded`로 이미 응답했는지 확인할 수 있습니다.
- Express의 `res.json()`과 `res.send()`도 같은 응답 객체를 쓰므로 한 요청에 두 번 호출하면 같은 에러가 납니다(자세히는 13편).
- 에러 처리 미들웨어에서 `res.headersSent`가 참이면 새 응답을 쓰지 말고 `next(err)`로 Express 기본 에러 핸들러에 넘깁니다. 기본 핸들러는 연결을 닫고 요청을 실패로 처리합니다.

**흔한 실수:** `try` 블록에서 응답한 뒤 `catch`에서 에러 응답을 또 보내는 것입니다. 응답 쓰기 자체가 던지는 에러에는 `catch`가 헤더 에러를 하나 더 만듭니다. 응답은 한 곳에서 한 번만 하도록 구조를 잡습니다.

## 포트 점유 EADDRINUSE

같은 주소와 포트를 이미 다른 소켓이 쓰고 있으면 `listen`이 `EADDRINUSE` 에러를 냅니다. `'error'` 이벤트로 전달되고, 리스너가 없으면 잡히지 않은 예외로 프로세스가 종료됩니다.

```js
const server = http.createServer(handler)
server.on('error', (err) => {
  console.error(err.code, err.message)
  // EADDRINUSE listen EADDRINUSE: address already in use
  process.exit(1)
})
server.listen(3000)
```

- 에러 객체에는 `code`(`EADDRINUSE`), `syscall`(`listen`), `port`가 있습니다. `Emitted 'error' event on Server instance`라는 출력이 보이면 서버의 `'error'` 리스너가 없다는 뜻입니다.
- 원인은 대개 이전에 띄운 프로세스가 남아 있는 것입니다. 이전 실행이 정상 종료되지 않았거나(종료 처리 부재, 25편), 개발 서버를 터미널 두 곳에서 띄웠거나, 다른 프로그램이 같은 포트를 씁니다.
- 어느 프로세스가 점유하는지는 운영체제 도구로 찾습니다. Windows는 `netstat -ano`에서 포트 줄의 마지막 열이 PID이고, Linux·macOS는 `lsof -i :3000`을 씁니다. PID를 확인한 뒤 프로세스를 종료합니다.
- 서버를 정리하지 않고 코드를 다시 실행하는 경우(테스트 파일 여러 개, 감시 모드)에도 납니다. 서버를 닫는 것을 잊지 않습니다.
- 테스트에서는 포트 0으로 띄우면 충돌이 없습니다(자세히는 24편, 27편).
- 포트를 환경변수로 받으면 충돌 시 다른 값으로 바꿔 띄울 수 있습니다(자세히는 25편).

**흔한 실수:** `EADDRINUSE`가 났을 때 포트 번호만 바꾸고 넘어가는 것입니다. 이전 프로세스가 계속 떠서 리소스를 쓰고 있거나, 같은 일을 하는 서버가 두 개 떠서 요청이 나뉘어 처리됩니다.

## CORS를 서버 크래시로 착각

브라우저 콘솔에 `blocked by CORS policy`가 보이면 서버가 죽었다고 오해하기 쉽습니다. CORS는 브라우저가 적용하는 정책이라서 서버는 정상으로 응답했는데 브라우저가 스크립트에 응답을 넘기지 않는 상황입니다(자세히는 9편).

| 구분 | CORS 문제 | 서버 크래시 |
|------|-----------|-------------|
| 서버 프로세스 | 살아 있음 | 종료됨 |
| 서버 로그 | 요청이 찍히거나 OPTIONS 요청만 보임 | 에러 스택과 종료 메시지 |
| `curl`·Postman·Node `fetch` | 정상 응답 | 연결 거부(`ECONNREFUSED`) |
| 브라우저 증상 | 콘솔에 CORS 메시지, JS에서는 일반 네트워크 에러(`Failed to fetch`)만 보임 | 네트워크 에러, 연결 실패 |
| 해결 | 서버가 CORS 응답 헤더와 preflight 처리를 추가 | 크래시 원인 수정 |

- 브라우저 밖에서는 CORS 검사가 없습니다. `curl`이나 Node.js의 `fetch`로 같은 URL을 호출했을 때 정상이면 서버는 살아 있고 문제는 CORS입니다.
- 보안상 CORS 실패의 구체적인 이유는 JavaScript 코드에 전달되지 않고 브라우저 콘솔에만 표시됩니다. 코드의 `catch`에서 얻는 에러만 보고는 판단할 수 없습니다.
- `Authorization` 헤더나 `application/json` 본문, `PUT`·`DELETE` 같은 요청에서는 브라우저가 본 요청 전에 `OPTIONS` preflight를 보냅니다. 서버가 `OPTIONS`를 처리하지 않아 404나 405를 돌려주면 본 요청은 나가지 않습니다. 서버 로그에 `OPTIONS`만 찍히는 이유입니다.
- 단순 요청은 서버가 요청을 받아 처리한 뒤 응답을 브라우저가 막습니다. 요청이 서버에 도달해 부작용(DB 쓰기)이 일어났을 수 있으므로 "CORS 에러면 서버는 아무것도 안 했다"고 단정하지 않습니다.
- 서버가 에러 상태 코드(500 등)를 응답할 때 CORS 헤더가 빠지면 그 에러도 CORS 에러로 보입니다. 에러 응답에도 CORS 헤더를 붙여야 진짜 원인(500)이 클라이언트에 보입니다.
- 확인 순서: ① 서버 프로세스와 로그, ② `curl`로 직접 호출, ③ 브라우저 개발자 도구의 Network 탭에서 `OPTIONS` 요청과 응답 헤더, ④ 콘솔 메시지의 이유 문구.

**흔한 실수:** 서버 코드의 CORS 설정은 그대로 두고 프런트엔드 쪽에서 `mode: 'no-cors'`로 에러를 피하는 것입니다. 에러는 사라지지만 응답을 읽을 수 없는 불투명 응답이 되어 문제를 가립니다.

## 핵심 정리

- 모듈 에러는 방향으로 판별합니다. ESM에서는 `require`·`__dirname`이 없고(`import.meta.dirname`, `createRequire`), 상대 import는 확장자를 써야 하며, `exports` 맵에 없는 경로는 `ERR_PACKAGE_PATH_NOT_EXPORTED`입니다.
- `await`를 빼면 Promise 객체가 값 자리에 들어가고 거부는 `try`/`catch`를 지나쳐 프로세스를 끝낼 수 있습니다. `forEach`는 `async` 콜백을 기다리지 않으므로 `for...of`나 `Promise.all(map)`을 씁니다.
- 에러는 삼키지 않고, 기대한 에러만 좁혀서 처리하며, 나머지는 다시 던집니다. 한 작업은 콜백이든 Promise든 한 경로로 한 번만 완료합니다.
- 요청·응답 본문은 한 번만 읽을 수 있고, 외부 입력의 `JSON.parse`는 `try`/`catch`로 감쌉니다. 응답을 끝낸 뒤에는 헤더를 바꿀 수 없어서 `return`으로 흐름을 끊어야 합니다.
- `EADDRINUSE`는 같은 포트의 점유자를 찾아 정리하고 서버의 `'error'` 이벤트를 처리하며, 테스트는 포트 0을 씁니다.
- CORS 에러는 브라우저의 정책이라서 `curl`이나 Node `fetch`로 호출해 정상이면 서버 크래시가 아닙니다.

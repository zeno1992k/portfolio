## 설정을 코드와 분리

설정은 배포 환경마다 달라지는 값(포트, DB 주소, 외부 서비스 키)이고, 코드는 환경이 바뀌어도 그대로인 부분입니다. 둘을 분리하면 같은 코드를 개발·테스트·운영에 그대로 배포할 수 있습니다. 환경변수에 설정을 두는 방식은 Twelve-Factor App의 "Config" 항목이 정리한 것이며, Node.js에서는 `process.env`로 읽습니다.

```js
import { env } from 'node:process'

const port = env.PORT      // '3000' (문자열) 또는 undefined
const dbUrl = env.DATABASE_URL
```

- `process.env`의 값은 항상 문자열입니다. 숫자·불리언을 대입해도 문자열로 바뀝니다. 이 암묵 변환은 deprecated이며 이후 버전에서 에러가 될 수 있습니다.
- `process.env`를 바꿔도 현재 프로세스에서만 유효합니다. 부모 셸이나 다른 프로세스에는 반영되지 않습니다.
- Windows에서는 환경변수 이름의 대소문자를 구분하지 않습니다.
- 분리가 됐는지 확인하는 기준은 "코드 저장소를 지금 공개해도 자격 증명이 새지 않는가"입니다.

설정을 코드 곳곳에서 `process.env.X`로 읽으면 이름 오타와 변환 누락이 흩어집니다. 설정은 시작할 때 한 곳에서 읽어 객체로 만들고(아래 "설정 스키마 검증"), 나머지 코드는 그 객체만 import합니다.

**흔한 실수:** 환경별 값을 `if (host === 'prod')` 같은 분기로 코드에 넣는 것입니다. 환경이 늘 때마다 코드를 고쳐야 하고, 운영 값이 저장소에 남습니다.

## 개발 / 테스트 / 운영

환경(개발·테스트·운영)별 차이는 같은 코드에 다른 환경변수를 주는 것으로 표현합니다. 환경 이름을 나타내는 관례적 변수가 `NODE_ENV`입니다.

- Node.js 자체는 `NODE_ENV`를 해석하지 않습니다. 값의 의미는 Express 같은 라이브러리와 애플리케이션이 정합니다.
- 라이브러리가 `NODE_ENV`로 동작을 바꾸므로 운영 환경에는 `production`을 지정하는 것이 관례입니다.
- 환경별 차이는 `NODE_ENV` 분기보다 값 자체(포트, DB 주소, 로그 수준)를 환경변수로 주는 편이 단순합니다.

`.env` 파일은 환경변수를 파일로 적어 두고 읽어 오는 방식입니다. Node.js 24는 별도 패키지 없이 이를 지원합니다.

| 방법 | 설명 | 안정성 |
|------|------|--------|
| `node --env-file=.env app.js` | 시작 전에 파일을 읽어 `process.env`에 넣음 | 24.10부터 Stable |
| `--env-file-if-exists=파일` | 같은 동작이지만 파일이 없어도 에러가 아님 | 24.10부터 Stable |
| `process.loadEnvFile(path)` | 코드에서 호출. 기본 경로는 `./.env` | 24.10부터 Stable |
| `util.parseEnv(content)` | 파일 내용 문자열을 객체로 파싱만 함. 적용하지 않음 | 24.10부터 Stable |

```bash
node --env-file=.env --env-file=.env.local app.js
```

- 같은 변수가 실제 환경과 파일에 모두 있으면 실제 환경의 값이 우선합니다. 배포 환경이 파일의 기본값을 덮어쓸 수 있다는 뜻입니다.
- `--env-file`을 여러 번 쓰면 뒤 파일이 앞 파일의 값을 덮어씁니다.
- 파일이 없으면 `--env-file`과 `process.loadEnvFile()`는 에러입니다. 선택적 파일에는 `--env-file-if-exists`를 씁니다.
- 파일 형식은 한 줄에 `KEY=value`입니다. `#` 뒤는 주석이고, 값은 따옴표로 감쌀 수 있으며 `export KEY=value`의 `export`는 무시됩니다.
- 파일 안의 `NODE_OPTIONS`는 `process.loadEnvFile()`에서는 효과가 없지만, `--env-file`에서는 Node.js 설정으로 적용됩니다.

```js
import { parseEnv } from 'node:util'

parseEnv('A=1\n# memo\nB="x y"') // { A: '1', B: 'x y' }
```

테스트에서는 `NODE_ENV=test`와 테스트 전용 `.env` 파일을 주고, 포트는 0으로 둡니다(자세히는 24편).

**흔한 실수:** `.env`를 저장소에 올리는 것입니다. 실제 값이 든 파일은 `.gitignore`에 넣고, 키 이름만 적은 예시 파일(`.env.example`)을 올립니다.

## 시크릿

시크릿은 DB 비밀번호, API 키, 토큰, 서명 키처럼 새면 피해가 생기는 설정 값입니다. 일반 설정과 같은 경로(환경변수)로 주입하되 노출 지점을 줄입니다.

- 저장소에 두지 않습니다. 코드, `.env`, 테스트 픽스처, 설정 파일 모두 해당합니다. 한 번 커밋된 값은 이력에 남으므로 폐기하고 재발급해야 합니다.
- 로그와 에러 메시지에 찍지 않습니다. 설정 객체를 통째로 `console.log`하거나 에러에 담지 않습니다. 검증 에러에는 값이 아니라 변수 이름만 적습니다.
- 클라이언트 응답에 포함하지 않습니다. 에러 응답에 설정 객체나 연결 문자열을 넣지 않습니다.
- 이미지나 빌드 결과물에 굽지 않습니다. 실행 시점에 주입합니다.
- 환경별로 다른 값을 씁니다. 개발용 키로 운영 데이터에 접근하지 않도록 분리합니다.
- 운영에서는 실행 환경이 제공하는 시크릿 저장소(클라우드의 비밀 관리 서비스, 오케스트레이터의 시크릿)에서 주입하는 방식이 일반적입니다.

환경변수는 그 프로세스가 만드는 자식 프로세스에도 기본으로 전달됩니다. 외부 명령을 실행할 때 필요한 변수만 넘기려면 `env` 옵션을 명시합니다(자세히는 27편).

**흔한 실수:** 시작 로그에 설정을 디버깅용으로 출력하는 것입니다. 개발 중에 넣은 한 줄이 운영 로그 수집 시스템까지 시크릿을 보냅니다.

## 설정 스키마 검증(시작 시 실패)

설정은 서버가 요청을 받기 전에, 시작할 때 전부 검증합니다. 잘못된 설정은 시작 직후 에러로 끝나야 합니다. 첫 요청이 들어와서야 `undefined`로 터지면 배포는 성공한 것처럼 보이고 장애는 나중에 납니다.

```js
import { env } from 'node:process'

function loadConfig() {
  const errors = []
  const port = Number(env.PORT ?? 3000)
  if (!Number.isInteger(port) || port < 0 || port > 65535) {
    errors.push(`PORT is invalid: ${env.PORT}`)
  }
  if (!env.DATABASE_URL) errors.push('DATABASE_URL missing')
  if (errors.length > 0) {
    throw new Error('Invalid config: ' + errors.join(', '))
  }
  return Object.freeze({ port, dbUrl: env.DATABASE_URL })
}
export const config = loadConfig()
```

실행 결과(`PORT=abc`이고 `DATABASE_URL`이 없을 때)는 시작 직후 이렇게 끝납니다.

```text
Error: Invalid config: PORT is invalid: abc,
  DATABASE_URL missing
```

- 첫 오류에서 멈추지 말고 모아서 한 번에 알려 줍니다. 배포할 때 고치고 다시 실행하는 횟수가 줄어듭니다.
- 모듈 최상위에서 `loadConfig()`를 호출하면 import하는 순간 검증됩니다. 잘못되면 서버가 `listen()`을 호출하기 전에 끝납니다.
- 변환은 검증 단계에서 끝냅니다. 문자열을 숫자·불리언으로 바꾸고, 기본값을 채우고, 결과를 `Object.freeze`로 고정합니다.
- 검증 에러 메시지에는 값이 아니라 이름을 씁니다. 위 예의 `PORT` 값은 시크릿이 아니라서 보여도 되지만, 시크릿 변수에는 값을 적지 않습니다.
- 스키마가 커지면 Zod 같은 검증 라이브러리로 같은 일을 선언적으로 합니다(자세히는 8편).

**흔한 실수:**

- `Number(env.PORT ?? 3000)`에서 `PORT=''`(빈 문자열)이면 `Number('')`이 `0`이라서 검증을 통과하고 포트 0, 즉 임의 포트로 뜹니다. 빈 문자열을 "없음"으로 취급하려면 `env.PORT || 3000`이나 별도 검사가 필요합니다.
- `Number('3000a')`는 `NaN`입니다. `Number.isInteger`로 걸러야 합니다.
- 불리언 변수를 `Boolean(env.DEBUG)`로 읽으면 안 됩니다(자세히는 27편).

## 포트

포트는 한 호스트에서 서버 하나를 구별하는 번호(0–65535)이고, `server.listen(port)`로 지정합니다. 운영에서는 하드코딩하지 않고 환경변수로 받습니다.

```js
import http from 'node:http'
import { config } from './config.js'

const server = http.createServer((req, res) => {
  res.end('ok')
})
server.listen(config.port, () => {
  console.log(`listening on ${server.address().port}`)
})
```

- `port`를 생략하거나 `0`을 주면 운영체제가 사용 중이 아닌 포트를 임의로 배정합니다. 실제 번호는 `'listening'` 이벤트 이후 `server.address().port`로 읽습니다.
- 테스트는 포트 0을 쓰면 다른 테스트나 이미 떠 있는 서버와 충돌하지 않습니다(자세히는 24편).
- 같은 호스트와 포트를 이미 다른 프로세스가 쓰고 있으면 `listen`이 `EADDRINUSE` 에러를 냅니다(자세히는 26편).
- 환경변수로 받은 값은 문자열이므로 정수로 변환·검증한 뒤 씁니다(위 절).

**흔한 실수:** 포트를 코드에 박아 두는 것입니다. 컨테이너나 PaaS는 실행 시점에 포트를 정해 환경변수로 알려 주는 경우가 많아서, 하드코딩하면 그 환경에서 접속되지 않습니다.

## 호스트 0.0.0.0과 127.0.0.1

`listen`의 호스트 인수는 서버가 받아들일 네트워크 인터페이스를 정합니다.

| 호스트 | 뜻 | 접속 가능한 범위 |
|--------|----|------------------|
| `127.0.0.1` | 루프백 주소 | 같은 기기에서만 |
| `0.0.0.0` | 모든 IPv4 인터페이스(미지정 주소) | 이 기기에 닿는 모든 곳 |
| `::` | 모든 IPv6 인터페이스. IPv4도 함께 받는 운영체제가 많음 | 이 기기에 닿는 모든 곳 |
| 생략 | IPv6가 되면 `::`, 아니면 `0.0.0.0` | 모든 인터페이스 |

```js
server.listen(0, '127.0.0.1') // 로컬 전용
// address: '127.0.0.1', family: 'IPv4'
server.listen(0)              // 호스트 생략
// address: '::', family: 'IPv6'
```

- 호스트를 생략하면 모든 인터페이스에 열립니다. 로컬 개발용 서버나 관리용 포트는 `127.0.0.1`을 명시해 외부 접근을 막는 것이 안전합니다.
- 컨테이너 안에서 `127.0.0.1`로만 열면 컨테이너 밖에서는 접속할 수 없습니다. 컨테이너 안의 서버는 `0.0.0.0`으로 열어야 외부에서 닿습니다.
- 호스트는 환경변수(`HOST`)로 받고 기본값을 환경에 맞게 정하는 방식이 흔합니다.
- 이 값은 "누가 접속할 수 있는가"를 정할 뿐 인증이 아닙니다. 모든 인터페이스에 여는 서버는 방화벽과 인증이 따로 필요합니다.

**흔한 실수:** 로컬에서 되는데 배포하면 접속되지 않을 때 호스트를 의심하지 않는 것입니다. `127.0.0.1`로 열었는지, 포트가 실제로 열렸는지를 먼저 확인합니다.

## SIGINT

시그널(signal)은 운영체제가 프로세스에 보내는 짧은 알림입니다. Node.js에서는 `process.on('시그널 이름', 핸들러)`로 받습니다. `process` 객체는 Stable(안정성 지수 2)입니다. `SIGINT`는 터미널에서 Ctrl+C를 눌렀을 때 발생하는 인터럽트 시그널입니다.

```js
import process from 'node:process'

process.on('SIGINT', (signal) => {
  console.log(`got ${signal}`) // got SIGINT
})
```

- 핸들러는 시그널 이름 문자열(`'SIGINT'`)을 첫 인수로 받습니다.
- 리스너가 없으면 기본 동작은 종료입니다. 터미널 모드를 복원하고 종료 코드 `128 + 시그널 번호`로 끝납니다. `SIGINT`는 번호 2이므로 130입니다.
- 리스너를 하나라도 달면 기본 동작이 사라집니다. 핸들러가 직접 종료하지 않으면 Ctrl+C를 눌러도 프로세스는 계속 살아 있습니다.
- `SIGINT`는 모든 플랫폼에서 터미널로 받을 수 있습니다. 터미널이 raw 모드이면 Ctrl+C로는 발생하지 않습니다.
- 시그널 리스너만 달려 있어도 프로세스는 이벤트 루프가 비면 끝납니다. 서버가 열려 있는 동안 살아 있는 것은 서버 핸들 때문입니다.
- 같은 시그널이 두 번 오면 핸들러가 두 번 호출됩니다. 종료 절차를 한 번만 시작하도록 막아야 합니다(아래 "graceful shutdown").

**흔한 실수:** 리스너만 달고 종료하지 않는 것입니다. 정리 코드를 붙였는데 `process.exit()`나 핸들 정리가 없어 Ctrl+C가 먹히지 않는 프로세스가 됩니다. 그때는 강제로 끄는 수밖에 없습니다.

## SIGTERM

`SIGTERM`은 "정상적으로 종료해 달라"는 요청입니다. 프로세스 매니저와 컨테이너 런타임이 종료를 요청할 때 보내는 기본 시그널이고, `docker stop`도 먼저 `SIGTERM`을 보냅니다. 유예 시간이 지나도 끝나지 않으면 `SIGKILL`로 강제 종료합니다.

| 시그널 | 번호 | 받을 수 있나 | 보내는 쪽의 의도 |
|--------|------|--------------|------------------|
| `SIGINT` | 2 | 예 | 사용자의 중단(Ctrl+C) |
| `SIGTERM` | 15 | 예 | 정상 종료 요청 |
| `SIGHUP` | 1 | 예 | 터미널·콘솔이 끊김 |
| `SIGKILL` | 9 | 아니오 | 즉시 강제 종료 |

- `SIGTERM`에도 기본 핸들러가 있어서 리스너가 없으면 종료 코드 143(128 + 15)으로 끝나지만, 정리할 기회는 없습니다.
- `SIGKILL`은 리스너를 달 수 없고 모든 플랫폼에서 무조건 종료합니다. 정리 코드가 실행되지 않습니다.
- Windows는 `SIGTERM`을 지원하지 않습니다. 리스너를 달 수는 있지만 시그널이 오지는 않습니다. `process.kill()`로 `SIGINT`·`SIGTERM`·`SIGKILL`을 보내면 대상 프로세스는 핸들러 없이 즉시 종료됩니다.
- 개발은 Windows, 운영은 Linux인 경우 종료 절차를 Windows에서 시그널로 시험할 수 없습니다. 핸들러를 호출 가능한 함수로 분리해 테스트합니다.
- 보통 `SIGINT`와 `SIGTERM`에 같은 종료 함수를 연결합니다.

```js
process.on('SIGINT', shutdown)
process.on('SIGTERM', shutdown)
```

**흔한 실수:** `SIGTERM`을 처리하지 않는 것입니다. 로컬에서 Ctrl+C로는 끝나서 문제를 못 느끼고, 배포에서 매번 유예 시간 뒤 `SIGKILL`로 죽어 처리 중이던 요청이 끊깁니다.

## SIGHUP

`SIGHUP`은 터미널이 끊겼을 때 발생하는 시그널입니다. Windows에서는 콘솔 창을 닫을 때 생기고, 다른 플랫폼에서는 비슷한 상황에서 생깁니다.

- 비 Windows에서 리스너가 없으면 기본 동작은 종료입니다. 리스너를 달면 기본 동작이 사라집니다.
- Windows에서는 리스너를 달아도 약 10초 뒤 운영체제가 프로세스를 무조건 종료합니다. 이 시간 안에 정리를 끝내야 합니다.
- 터미널에서 서버를 띄운 채 창을 닫으면 `SIGHUP`으로 서버가 끝납니다. 서버는 터미널이 아니라 프로세스 매니저로 띄웁니다.
- 일부 데몬은 `SIGHUP`을 "설정 다시 읽기" 신호로 쓰는 관례가 있습니다. 필요하면 핸들러에서 설정을 다시 읽도록 구현할 수 있지만, Node.js가 정한 동작이 아닙니다. `process.env`는 시작 이후 바뀌지 않으므로 파일을 다시 읽어서 설정 객체를 새로 만들어야 합니다.
- 종료 목적이라면 `SIGINT`·`SIGTERM`과 같은 종료 함수에 연결하는 구성이 일반적입니다.

```js
process.on('SIGHUP', () => shutdown('SIGHUP'))
```

**흔한 실수:** `SIGHUP` 리스너로 설정 재적용을 만들어 놓고 Windows에서도 되는 줄 아는 것입니다. Windows에서 이 시그널은 콘솔 창이 닫힐 때 오는 것이라서, 그 뒤 약 10초 안에 프로세스가 끝납니다.

## graceful shutdown

graceful shutdown은 종료 요청을 받았을 때 하던 일을 마무리하고 끝내는 절차입니다. 반대는 요청이 처리되던 중간에 프로세스가 죽는 것입니다. 순서는 다음과 같습니다.

1. 종료 시그널을 받는다.
2. 새 연결과 요청을 받지 않는다(다음 절).
3. 처리 중인 요청과 열린 연결이 끝나기를 기다린다.
4. DB 연결 풀, 큐, 캐시 클라이언트 같은 외부 자원을 닫는다.
5. 제한 시간 안에 못 끝나면 강제로 끝낸다.
6. 종료 코드를 정해 끝낸다. 정상이면 0, 비정상이면 1.

뼈대는 이렇습니다.

```js
let closing = false

function shutdown(signal) {
  if (closing) return // 중복 호출 방지
  closing = true
  console.log(`${signal}: shutting down`)
  server.close((err) => {
    // 외부 자원(DB 풀 등)을 여기서 닫는다
    process.exitCode = err ? 1 : 0
  })
}
process.on('SIGINT', shutdown)
process.on('SIGTERM', shutdown)
```

- `closing` 플래그로 시그널이 여러 번 와도 한 번만 시작합니다.
- 종료 코드는 `process.exit(code)`보다 `process.exitCode = code`로 정하고 이벤트 루프가 비어 저절로 끝나게 두는 방식이 안전합니다. `process.exit()`는 처리 중인 비동기 작업과 쓰기 중인 출력을 기다리지 않고 끝냅니다.
- 시그널로 끝나는 프로세스의 종료 코드는 관례로 `128 + 번호`입니다. 오케스트레이터가 종료 코드를 보는 환경이 아니라면 0 또는 1이면 충분합니다.
- 서버를 닫은 뒤에 DB를 닫습니다. 순서를 바꾸면 처리 중인 요청이 닫힌 DB에 쿼리를 보냅니다.
- 닫을 대상이 많으면 `Promise.allSettled`로 병렬로 닫고, 하나가 실패해도 나머지를 끝까지 시도합니다.

**흔한 실수:** 종료 함수가 `async`인데 에러를 처리하지 않는 것입니다. 시그널 핸들러에서 던진 에러나 reject는 종료 절차를 중간에서 끊습니다. 종료 함수는 내부에서 `try`/`catch`로 감싸고 실패해도 종료 코드를 정해 끝내야 합니다.

## 새 요청 거부

종료가 시작되면 새 연결과 새 요청을 더 받지 않아야 합니다. `server.close()`가 이를 시작합니다. 새 연결을 받지 않고, 지금 요청을 주고받고 있지 않은 연결(유휴 연결)을 닫습니다(Node.js 19부터).

```js
server.close()
// 이후 새 클라이언트의 연결 시도는 거부됨
// → ECONNREFUSED (실행 결과)
```

- `server.close()`는 비동기이며, 열린 연결이 모두 끝나면 `'close'` 이벤트가 발생하고 콜백이 호출됩니다. 서버가 열려 있지 않을 때 닫으면 콜백이 `Error`를 받습니다.
- 닫는 순간 리스닝 소켓이 닫혀서 새 TCP 연결은 거부됩니다. 앞단에 로드 밸런서가 있으면 닫히는 인스턴스로 새 요청을 보내지 않도록, 상태 확인(health check) 응답부터 바꿉니다.
- 이미 맺어진 keep-alive 연결로 오는 다음 요청은 `server.close()`만으로 막히지 않습니다. 처리 중이던 요청을 마친 연결은 그대로 열려 있을 수 있습니다.
- 그래서 종료 중에는 응답에 `Connection: close` 헤더를 붙여 클라이언트가 그 연결을 더 쓰지 않게 합니다.

```js
const server = http.createServer((req, res) => {
  if (closing) res.setHeader('Connection', 'close')
  // ... 요청 처리 ...
  res.end('ok')
})
```

- 헤더는 응답을 쓰기 직전의 시점에 확인해야 합니다. 요청이 들어올 때만 확인하면, 처리하는 도중에 종료가 시작된 요청은 `keep-alive`로 응답합니다(실행으로 확인).
- 종료 중에 도착하는 요청을 거부하려면 상태 코드 503과 `Retry-After`로 응답하는 방식이 일반적입니다.

**흔한 실수:** `server.close()`만 호출해 놓고 종료 시간이 길다고 이유를 찾는 것입니다. 연결이 하나라도 남아 있으면 `'close'`가 오지 않습니다.

## 기존 연결 대기

`server.close()`를 호출해도 처리 중인 요청은 끊기지 않습니다. 서버는 연결이 모두 끝날 때까지 기다리다가 `'close'` 이벤트를 냅니다. 이 기다림이 "처리 중인 요청을 마치는 것"입니다.

```js
server.close((err) => {
  console.log('closed', err?.code) // closed undefined
})
```

- 처리 시간이 200ms인 요청이 진행 중일 때 `SIGTERM`을 받으면 그 요청은 정상 응답(200)을 받고, 그 뒤 `'close'`가 호출됩니다(실행으로 확인).
- keep-alive 연결이 응답을 끝낸 뒤 유휴 상태로 남으면 `'close'`는 연결이 닫힐 때까지 지연됩니다. 연결은 `server.keepAliveTimeout`(기본 5초)에 `server.keepAliveTimeoutBuffer`(기본 1초, Node.js 24.6에 추가)를 더한 시간이 지나면 닫힙니다. 실제로 응답 직후의 keep-alive 연결이 남아 있으면 약 6초 뒤에 `'close'`가 호출됐습니다.
- 처리 도중 종료가 시작된 요청은 위의 `Connection: close`로 응답하면 응답 직후 연결이 닫혀서 대기가 짧아집니다.
- 또 다른 방법은 응답이 끝난 뒤 `server.closeIdleConnections()`를 호출하는 것입니다(아래 절).
- 연결이 끝나지 않는 요청(느린 클라이언트, 끝나지 않는 스트림)이 있으면 영원히 기다릴 수 있습니다. 대기에는 제한 시간이 필요합니다.
- 웹소켓처럼 다른 프로토콜로 업그레이드된 소켓은 `closeAllConnections()`도 닫지 않으므로 직접 닫아야 합니다(자세히는 20편).

**흔한 실수:** 종료 로그의 순서를 믿고 "모든 요청이 끝났다"고 판단하는 것입니다. 요청의 완료는 응답 쓰기가 끝난 시점이지, 핸들러 함수가 반환된 시점이 아닙니다. 응답 객체의 `'finish'`·`'close'`와 서버의 `'close'`로 판단합니다.

## 타임아웃 후 강제 종료

정상 종료가 끝나지 않을 때를 대비해 제한 시간을 둡니다. 시간이 지나면 남은 연결을 끊고 프로세스를 끝냅니다. 오케스트레이터의 유예 시간(`docker stop`의 기본 대기 시간 등)보다 짧게 잡아야, 그쪽에서 `SIGKILL`로 죽이기 전에 스스로 끝낼 수 있습니다.

```js
const FORCE_MS = 10_000

setTimeout(() => {
  console.error('shutdown timed out, forcing exit')
  server.closeAllConnections()
  process.exit(1)
}, FORCE_MS).unref()
```

- `unref()`가 핵심입니다. 타이머가 이벤트 루프를 붙잡지 않으므로, 모든 정리가 일찍 끝나면 타이머를 기다리지 않고 프로세스가 끝납니다.
- 타이머는 `shutdown`에서 `server.close()`를 호출한 직후에 설정합니다. 시그널을 받은 시점부터 센다는 뜻입니다.
- 시간이 만료되면 `server.closeAllConnections()`로 처리 중인 연결까지 끊고, 비정상 종료를 알리도록 종료 코드 1로 끝냅니다. 이때는 남은 연결을 포기한다는 로그를 남깁니다.
- 연결만 끊어서는 프로세스가 끝나지 않을 수 있습니다. DB 풀이나 타이머처럼 열린 핸들이 남아 있으면 `process.exit()`로 끝냅니다(자세히는 27편).
- 제한 시간은 가장 긴 정상 요청 시간보다 길어야 합니다. 너무 짧으면 정상 요청이 끊기고, 너무 길면 유예 시간 안에 `SIGKILL`을 맞습니다.

처리 시간 5초짜리 요청을 보내 놓고 1초 제한으로 `SIGTERM`을 보내면 `timeout: force` 로그 뒤 종료 코드 1로 끝났습니다(실행으로 확인).

**흔한 실수:** 강제 종료 타이머에 `unref()`를 빼는 것입니다. 정리가 일찍 끝나도 타이머가 남아서 프로세스가 제한 시간까지 살아 있게 되고, 종료가 매번 느려집니다.

## beforeExit만 믿고 정리하면 안 되는 이유

`'beforeExit'`은 이벤트 루프가 비어 더 할 일이 없을 때 발생하는 이벤트입니다. 종료 직전이라는 이름과 달리, 서버 프로세스의 정리용으로는 쓸 수 없습니다.

```js
process.on('beforeExit', (code) => {
  console.log('beforeExit', code)
})
```

- 서버가 열려 있는 동안은 이벤트 루프가 비지 않아서 `'beforeExit'`이 발생하지 않습니다. 서버를 열어 둔 채 리스너를 달면 `server.close()`가 끝나기 전까지 호출되지 않습니다(실행으로 확인).
- `process.exit()` 호출이나 잡히지 않은 예외 같은 명시적 종료에서는 발생하지 않습니다.
- 핸들러 안에서 비동기 작업을 예약하면 프로세스가 계속되고, 그 작업이 끝나 루프가 다시 비면 `'beforeExit'`이 또 발생합니다. 정리 코드가 여러 번 실행될 수 있습니다.

```js
let n = 0
process.on('beforeExit', () => {
  if (++n < 3) setTimeout(() => console.log('work'), 10)
})
// beforeExit이 세 번 발생
```

- 시그널로 죽는 프로세스(`SIGKILL`, 리스너 없는 `SIGTERM`)는 정리 코드를 실행할 기회가 없습니다.
- 정리가 필요한 시점은 "종료가 시작되는 시점", 즉 시그널 핸들러입니다. `'beforeExit'`은 종료 요청을 받지 못한 상태에서 일이 끝났을 때만 동작하는 이벤트입니다.
- `'exit'` 이벤트는 프로세스가 끝나기 직전에 발생하지만 리스너 안에서는 동기 코드만 실행됩니다. 비동기 정리(네트워크, DB 닫기)는 거기서 할 수 없습니다.

| 이벤트 | 발생 시점 | 비동기 작업 | 비고 |
|--------|-----------|-------------|------|
| 시그널 리스너 | 시그널 수신 | 가능 | 정리의 시작점 |
| `'beforeExit'` | 루프가 빌 때 | 가능, 루프를 다시 돌림 | `process.exit()`·잡히지 않은 예외에서는 안 옴 |
| `'exit'` | 종료 직전 | 불가 | 동기 정리만 |

**흔한 실수:** DB 연결 닫기를 `process.on('beforeExit')`에 두는 것입니다. 서버가 시그널로 끝날 때는 호출되지 않아서 연결이 정리되지 않은 채 프로세스가 사라집니다.

## closeIdleConnections와 closeAllConnections

`http.Server`는 연결을 직접 닫는 메서드 두 개를 제공합니다. 둘 다 Node.js 18.2.0에 추가됐습니다.

| 메서드 | 닫는 대상 | 용도 |
|--------|-----------|------|
| `server.closeIdleConnections()` | 요청을 보내는 중이거나 응답을 기다리는 중이 아닌 연결 | keep-alive로 놀고 있는 연결 정리 |
| `server.closeAllConnections()` | 처리 중인 연결을 포함한 모든 HTTP(S) 연결 | 제한 시간 뒤 강제 종료 |

- `server.close()`는 Node.js 19부터 호출하는 순간 유휴 연결을 닫습니다. 그래서 19 이상에서는 `closeIdleConnections()`를 `server.close()`와 같이 부를 필요가 없습니다. 이전 버전을 함께 지원하는 코드에서는 호출해도 해가 없습니다.
- 문서는 둘 다 `server.close()` 뒤에 호출할 것을 권합니다. 먼저 호출하면 그 사이 새 연결이 생기는 경쟁 상태가 생길 수 있습니다.
- `closeAllConnections()`는 처리 중인 응답을 끊으므로 정상 종료가 아니라 강제 종료 수단입니다.
- `closeAllConnections()`는 웹소켓이나 HTTP/2처럼 다른 프로토콜로 업그레이드된 소켓은 닫지 않습니다.
- 두 메서드는 HTTP 서버(`http.Server`)에 있고 `net.Server`에는 없습니다.

```js
server.close()                 // 새 연결 거부, 유휴 연결 닫기
// 응답이 끝날 때마다 유휴 연결을 다시 정리
res.on('finish', () => server.closeIdleConnections())
setTimeout(() => {
  server.closeAllConnections()
}, 10_000).unref()
```

**흔한 실수:** 정상 종료 단계에서 `closeAllConnections()`를 호출하는 것입니다. 처리 중인 요청을 끊어서 graceful shutdown의 목적이 사라집니다. 정상 종료에는 `close()`와 `Connection: close`, 마지막 수단에만 `closeAllConnections()`를 씁니다.

## 핵심 정리

- 설정은 환경변수로 받아 시작할 때 한 곳에서 변환·검증하고, 잘못되면 서버를 띄우기 전에 에러로 끝냅니다. 시크릿은 저장소·로그·응답에 넣지 않습니다.
- `--env-file`은 여러 번 쓸 수 있고 뒤 파일이 앞 파일을 덮어쓰며, 실제 환경변수가 파일보다 우선합니다. `process.env`의 값은 항상 문자열입니다.
- 포트는 환경변수로 받고 0은 임의 배정입니다. 호스트를 생략하면 모든 인터페이스에 열리고, 로컬 전용은 `127.0.0.1`, 컨테이너 안에서는 `0.0.0.0`입니다.
- `SIGINT`·`SIGTERM`·`SIGHUP`은 리스너를 달면 기본 종료 동작이 사라지므로 핸들러가 종료까지 책임집니다. `SIGKILL`은 받을 수 없습니다.
- graceful shutdown은 `server.close()`로 새 연결을 막고, 처리 중인 요청을 기다리고, 외부 자원을 닫은 뒤 끝내며, `unref()`한 타이머로 제한 시간 뒤 `closeAllConnections()`와 `process.exit(1)`로 강제 종료합니다.
- `'beforeExit'`은 이벤트 루프가 비어야 발생하고 `process.exit()`·잡히지 않은 예외에서는 오지 않아서 정리의 시작점이 될 수 없습니다. 정리는 시그널 핸들러에서 시작합니다.

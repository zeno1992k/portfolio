## pipe

`readable.pipe(destination)`은 Readable의 출력을 Writable에 연결합니다. 호출하면 Readable이 flowing 모드가 되고, 데이터가 목적지로 자동 전달됩니다. 목적지가 느리면 알아서 속도를 맞춥니다.

```js
import { createReadStream } from 'node:fs'
import { createWriteStream } from 'node:fs'
import { createGzip } from 'node:zlib'

createReadStream('app.log')
  .pipe(createGzip())
  .pipe(createWriteStream('app.log.gz'))
```

- 반환값은 목적지입니다. 목적지가 Duplex나 Transform이면 이어서 `pipe()`를 체이닝할 수 있습니다.
- 기본값으로 원본이 `'end'`되면 목적지의 `end()`를 호출합니다. 옵션 `{ end: false }`로 끌 수 있습니다.
- `process.stdout`과 `process.stderr`는 이 옵션과 관계없이 프로세스가 끝날 때까지 닫히지 않습니다.
- 하나의 Readable에 여러 목적지를 연결할 수 있습니다.
- `unpipe()`로 연결을 끊습니다. 연결이 모두 끊기면 Readable은 paused가 됩니다.

**흔한 실수:** `pipe()`가 에러까지 이어 준다고 생각하는 것입니다. 에러 처리는 아래 "스트림 에러"와 "pipeline이 pipe보다 나은 이유"에서 설명합니다.

## pipeline

`pipeline()`은 스트림 여러 개를 이어 붙이고, 끝났을 때 한 번 알려 주며, 어느 하나가 실패하면 나머지를 모두 정리하는 함수입니다. `node:stream/promises`의 Promise 버전을 쓰는 것이 기본입니다.

```js
import { pipeline } from 'node:stream/promises'
import { createReadStream } from 'node:fs'
import { createWriteStream } from 'node:fs'
import { createGzip } from 'node:zlib'

await pipeline(
  createReadStream('archive.tar'),
  createGzip(),
  createWriteStream('archive.tar.gz'),
)
// 성공하면 이행, 하나라도 실패하면 그 에러로 거부
```

- 인수는 `source`, 0개 이상의 변환 단계, `destination` 순서이며 배열 하나로 줄 수도 있습니다. 각 자리에는 스트림뿐 아니라 Iterable, AsyncIterable, 함수(async 제너레이터 포함), 웹 스트림이 올 수 있습니다.
- 마지막 인수에 옵션을 줄 수 있습니다. `signal`은 `AbortSignal`이고, `end`는 원본이 끝나면 목적지를 끝낼지 정합니다(기본 `true`, Transform은 `false`여도 끝남).
- 실패하면 이미 끝나지 않은 모든 스트림에 `destroy(err)`를 호출합니다. 이미 `'end'`·`'close'`한 Readable과 `'finish'`·`'close'`한 Writable은 제외됩니다.
- `signal`이 중단되면 `AbortError`로 거부되고 파이프라인 전체가 `destroy`됩니다.
- 중간 단계에 async 제너레이터 함수를 두면 변환기처럼 동작합니다.

```js
// 제너레이터를 변환 단계로 쓰기
await pipeline(
  createReadStream('in.txt', { encoding: 'utf8' }),
  async function* (source) {
    for await (const chunk of source) {
      yield chunk.toUpperCase()
    }
  },
  createWriteStream('out.txt'),
)
```

- 제너레이터를 첫 단계(원본)로 쓸 때는 받은 `signal`을 내부 비동기 작업에 전달해야 합니다. 그렇지 않으면 중단되어도 끝나지 않을 수 있습니다.
- 콜백 버전은 `node:stream`의 `pipeline(...streams, callback)`이며 마지막 스트림을 돌려줍니다.

```js
import { pipeline } from 'node:stream'

pipeline(src, gzip, dst, (err) => {
  if (err) console.error('실패', err) // 성공이면 err 없음
})
```

- 콜백 없이 콜백 버전을 `await`하면 `ERR_INVALID_ARG_TYPE`이므로 `await`할 때는 `node:stream/promises`에서 가져옵니다.
- `pipeline()`은 콜백이 호출된 뒤에도 스트림에 리스너를 남깁니다. 실패한 스트림을 재사용하면 리스너 누수와 삼켜진 에러가 생길 수 있습니다.

## finished

`finished(stream)`은 스트림이 더 이상 읽히거나 쓰이지 않게 되었을 때, 즉 끝났거나 에러가 났거나 중간에 닫혔을 때 알려 줍니다. 한 스트림의 최종 상태를 기다리는 함수입니다.

```js
import { finished } from 'node:stream/promises'

const rs = createReadStream('archive.tar')
rs.resume() // 소비 방법이 있어야 끝까지 간다
await finished(rs)
console.log('읽기 끝')
```

- 정상 종료면 이행하고, `'error'`나 중간 파괴이면 거부합니다. `'end'` 전에 `'close'`가 오면 `ERR_STREAM_PREMATURE_CLOSE` 에러입니다.
- 이미 끝난 스트림에 호출해도 결과가 나옵니다.
- 옵션: `error`(`false`면 `'error'`를 종료로 보지 않음), `readable`, `writable`(`false`로 해당 쪽을 기다리지 않음), `signal`(기다림만 취소하고 스트림은 중단하지 않음, `AbortError`), `cleanup`.
- `finished()`는 끝난 뒤에도 `'error'`, `'end'`, `'finish'`, `'close'` 리스너를 남깁니다. 잘못 구현된 스트림의 뒤늦은 에러가 프로세스를 죽이지 않게 하려는 의도입니다. 리스너를 지우려면 `{ cleanup: true }`를 줍니다(Promise 버전의 `cleanup` 기본값은 `false`).
- 콜백 버전은 `node:stream`의 `finished(stream, callback)`이고 정리 함수를 반환합니다.
- HTTP 요청이 중간에 끊겼을 때처럼 `'end'`나 `'finish'`가 오지 않는 상황을 처리하는 데 특히 유용합니다.

## backpressure

backpressure는 소비하는 쪽이 생산하는 쪽보다 느릴 때 생산 속도를 늦추는 흐름 제어입니다. 이것이 없으면 처리하지 못한 데이터가 메모리에 계속 쌓입니다.

쓰기 쪽에서는 `write()`의 반환값이 신호입니다.

```js
import { once } from 'node:events'

for (const line of lines) {
  if (!writable.write(line)) {
    await once(writable, 'drain') // 버퍼가 비워질 때까지 대기
  }
}
writable.end()
```

- `write()`가 `false`를 돌려주면 내부 버퍼가 `highWaterMark` 이상입니다. 그때부터는 `'drain'` 이벤트가 오기 전까지 쓰지 않습니다.
- 읽기 쪽에서는 `push()`가 `false`를 돌려주면 `_read()` 호출이 멈추고, 버퍼가 소비되면 다시 호출됩니다(1편).
- `pipe()`와 `pipeline()`이 이 과정을 자동으로 처리합니다. 직접 `write()`를 반복하거나 `'data'`에서 다른 스트림에 쓸 때만 직접 신경 씁니다.
- `false`를 무시하고 계속 쓰면 쓴 데이터는 모두 메모리에 쌓입니다. 공식 문서는 최대 메모리에 이르면 프로세스가 비정상 종료되고 GC 성능이 나빠진다고 경고하며, 원격 상대가 읽지 않는 소켓에 계속 쓰는 것은 원격에서 악용될 수 있는 취약점이 될 수 있다고 설명합니다.
- `'drain'`은 `write()`가 `false`를 반환한 뒤에만 옵니다.
- Transform은 출력을 소비하지 않으면 입력 쪽도 멈추므로 `pipe`·`pipeline`·`'data'` 등으로 소비해야 합니다.

**흔한 실수:** `await`·`for` 루프에서 `write()`의 반환값을 확인하지 않는 것입니다. 작은 데이터에서는 드러나지 않다가 큰 입력에서 메모리가 급증합니다.

## highWaterMark

`highWaterMark`는 스트림이 내부 버퍼에 쌓아 두는 양의 기준값입니다. 한계(limit)가 아니라 문턱(threshold)입니다. 읽기 쪽은 이 값에 닿으면 하위 자원에서 더 읽기를 멈추고, 쓰기 쪽은 닿으면 `write()`가 `false`를 돌려줍니다.

```js
import { getDefaultHighWaterMark } from 'node:stream'

getDefaultHighWaterMark(false) // 바이트 스트림: 16384 (Windows)
getDefaultHighWaterMark(true)  // 객체 모드: 16
```

- 단위는 바이트 스트림에서 바이트, 객체 모드에서 객체 개수입니다. 디코딩하지 않고 문자열을 다루는 스트림에서는 UTF-16 코드 유닛 개수입니다.
- 바이트 스트림의 기본값은 Windows 이외에서 64 KiB(65536), Windows에서 16 KiB(16384)입니다. v22.0.0에서 기본값이 올랐습니다.
- `fs.createReadStream()`의 기본값은 `64 * 1024`이고, 이 값이 읽는 조각의 크기가 됩니다. `fs.createWriteStream()`은 `getDefaultHighWaterMark()`를 따릅니다.
- 생성 시 옵션 `highWaterMark`로 정합니다. Duplex는 `readableHighWaterMark`와 `writableHighWaterMark`로 양쪽을 따로 정할 수 있고, `highWaterMark`를 주면 둘 다 그 값입니다.
- 전체 기본값은 `stream.setDefaultHighWaterMark(objectMode, value)`로 바꿀 수 있습니다(v19.9.0, v18.17.0 추가).
- 엄격한 메모리 상한이 아닙니다. 한 번에 이 값보다 큰 조각이 들어오면 그대로 버퍼에 들어갑니다.
- `readable.setEncoding()` 뒤에는 읽기 버퍼를 바이트가 아닌 문자 수로 측정합니다. 여러 바이트 문자가 섞인 문자열에서는 주의합니다.
- 값을 키우면 호출 횟수가 줄어 처리량이 늘 수 있지만 메모리를 더 씁니다. 실제 워크로드로 측정해 정합니다.

## objectMode

객체 모드(objectMode)는 스트림이 바이트나 문자열이 아니라 임의의 JavaScript 값을 조각 하나로 다루게 하는 옵션입니다. Node.js가 만드는 스트림은 기본적으로 문자열, `Buffer`, `TypedArray`, `DataView`만 다룹니다.

```js
import { Writable } from 'node:stream'

const sink = new Writable({
  objectMode: true,
  write(obj, enc, cb) { console.log(obj.id); cb() },
})
sink.write({ id: 1 }) // 1
```

- `null`은 끝 신호라서 객체 모드에서도 조각이 될 수 없습니다.
- `highWaterMark` 기본값은 객체 16개입니다. 조각의 크기와 관계없이 개수로 셉니다.
- 객체 모드에서 `read(size)`는 `size`와 관계없이 항목 하나를 돌려줍니다. 객체 모드 Writable은 `write()`의 `encoding` 인수를 무시합니다.
- 이미 만든 스트림을 객체 모드로 바꾸는 것은 안전하지 않습니다. 생성 시 옵션으로 정합니다.
- Transform은 `readableObjectMode`와 `writableObjectMode`로 입력과 출력을 따로 정합니다. 바이트를 받아 객체를 내보내는 파서에 씁니다.

```js
const toObj = new Transform({
  readableObjectMode: true, // 출력은 객체
  transform(chunk, enc, cb) {
    cb(null, { len: chunk.length }) // 입력은 바이트
  },
})
```

- 객체 모드와 flowing·paused는 서로 다른 개념입니다.
- `Readable.from()`은 기본적으로 객체 모드입니다(아래 `Readable.from` 절).

## for await로 스트림 읽기

Readable은 비동기 이터러블이라서 `for await...of`로 조각을 순서대로 읽을 수 있습니다. 이벤트 리스너 없이 `try/catch`로 에러까지 처리할 수 있어 읽기 방식으로 가장 간단합니다.

```js
const rs = createReadStream('a.txt', { encoding: 'utf8' })
let text = ''
for await (const chunk of rs) {
  text += chunk
}
console.log(text.length)
```

- 읽는 조각의 크기는 `highWaterMark`입니다. 파일이 64 KiB보다 작으면 한 조각입니다.
- 스트림이 에러를 내면 루프에서 예외가 던져집니다. 반복자가 에러 핸들러를 항상 등록해 두므로 파괴된 뒤의 에러가 처리되지 않은 에러로 남지 않습니다.
- 루프가 `break`, `return`, `throw`로 끝나면 스트림이 `destroy`됩니다. 일부만 읽고 나머지를 버릴 때는 편하지만, 이어서 같은 스트림을 쓸 수 없습니다.
- `'data'`, `'readable'`, `pipe()`와 섞어 쓰지 않습니다. 하나의 소비 방식만 고릅니다.
- `setEncoding()`이나 `encoding` 옵션을 주면 문자열을, 안 주면 `Buffer`를 받습니다.
- 반복자는 `readable[Symbol.asyncIterator]()`이며 v10.0.0에 추가되었고 v11.14.0부터 실험 단계가 아닙니다.

## createReadStream

`fs.createReadStream(path[, options])`는 파일을 조각 단위로 읽는 `fs.ReadStream`(Readable)을 돌려줍니다. 파일 전체를 메모리에 올리지 않고 읽을 수 있습니다.

```js
import { createReadStream } from 'node:fs'

const rs = createReadStream('big.log', {
  encoding: 'utf8',
  highWaterMark: 1024 * 1024, // 조각 크기 1 MiB
})
const part = createReadStream('big.log', {
  start: 90,
  end: 99,
})
// 90번째부터 99번째 바이트까지 (양 끝 포함)
```

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `flags` | `'r'` | 파일 열기 모드 |
| `encoding` | `null` | 지정하면 문자열, 아니면 `Buffer` |
| `start`, `end` | 처음, `Infinity` | 읽을 바이트 범위, 0부터 세고 양 끝 포함 |
| `highWaterMark` | `64 * 1024` | 조각 크기 |
| `autoClose` | `true` | `'error'`나 `'end'`에서 파일 디스크립터를 자동으로 닫음 |
| `emitClose` | `true` | 파괴된 뒤 `'close'` 발생 |
| `signal` | `null` | `AbortSignal`로 중단(v15.5.0 추가) |

- 경로는 문자열, `Buffer`, `file:` URL이 가능합니다. `options`를 문자열로 주면 인코딩입니다.
- `fd`를 주면 `path`는 무시되고 `'open'` 이벤트는 나오지 않습니다.
- `autoClose`가 `false`이면 에러가 나도 디스크립터가 닫히지 않으므로 직접 닫아야 합니다.
- 없는 파일은 호출 시점이 아니라 비동기로 `'error'`(`ENOENT`)가 발생합니다. `'error'` 핸들러가 없으면 처리되지 않은 에러입니다.
- 파일 전체 내용이 필요하면 `fs.promises.readFile()`이 간단합니다(기초 16편). 스트림은 크거나 읽으면서 처리할 때 씁니다.

## createWriteStream

`fs.createWriteStream(path[, options])`는 파일에 조각 단위로 쓰는 `fs.WriteStream`(Writable)을 돌려줍니다.

```js
import { createWriteStream } from 'node:fs'

const ws = createWriteStream('out.log', { flags: 'a' })
ws.write('line 1\n')
ws.end('line 2\n')
ws.on('finish', () => console.log('기록 완료'))
```

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `flags` | `'w'` | 쓰기 모드. 파일이 있으면 비움. `'a'`는 이어 쓰기 |
| `encoding` | `'utf8'` | 문자열의 인코딩 |
| `start` | 처음 | 쓰기 시작 위치. 기존 파일을 일부 수정하려면 `flags: 'r+'` |
| `highWaterMark` | 전체 기본값 | 버퍼 기준값 |
| `autoClose` | `true` | `'error'`나 `'finish'`에서 디스크립터를 자동으로 닫음 |
| `flush` | `false` | `true`면 닫기 전에 디스크립터를 플러시(v21.0.0, v20.10.0 추가) |
| `signal` | `null` | `AbortSignal`로 중단 |

- `write()`는 파일 쓰기가 끝나기 전에 반환합니다. 반환값이 `false`이면 `'drain'`을 기다립니다.
- 모든 쓰기를 마치려면 반드시 `end()`를 호출합니다. 호출하지 않으면 `'finish'`가 오지 않고 디스크립터가 열려 있습니다.
- 파일에 실제로 반영된 것을 확인한 뒤 다음 작업을 해야 하면 `'finish'`(또는 `'close'`)를 기다립니다. `pipeline()`은 이를 대신 기다려 줍니다.
- 같은 파일을 읽으면서 쓸 때 `flags`를 `'w'`로 두면 시작과 동시에 내용이 비워집니다.

## 대용량 파일

메모리에 다 올릴 수 없거나 올리고 싶지 않은 파일은 읽기, 변환, 쓰기를 `pipeline()`으로 이어 조각 단위로 처리합니다. 사용하는 메모리가 파일 크기가 아니라 `highWaterMark`와 변환 단계의 상태에 비례합니다.

```js
await pipeline(
  createReadStream('big.csv'),
  transformStep,              // 조각마다 변환
  createWriteStream('out.csv'),
)
```

- 약 137 MB의 텍스트 파일을 기본 설정으로 읽으면 조각이 2083개였고(대부분 65536바이트), `highWaterMark`를 1 MiB로 올리면 131개였습니다(Windows, Node.js 24에서 측정).
- 텍스트는 줄이 조각 경계에서 잘립니다. 줄 단위로 처리하려면 조각 끝에 남은 부분을 다음 조각으로 넘기거나 `readline`을 씁니다(자세히는 22편).

```js
let rest = ''
const rs = createReadStream('big.log', { encoding: 'utf8' })
for await (const chunk of rs) {
  const lines = (rest + chunk).split('\n')
  rest = lines.pop() // 마지막은 잘렸을 수 있어 보관
  for (const line of lines) handle(line)
}
if (rest) handle(rest)
```

- `encoding`을 지정하면 여러 바이트 문자가 조각 경계에 걸려도 스트림이 올바르게 디코딩합니다. `Buffer`를 직접 `toString()`하면 경계에서 글자가 깨질 수 있습니다.
- 단순 복사에는 스트림 대신 `fs.copyFile()`이 낫습니다(기초 17편).
- 쓰기가 느리면 읽기가 따라 느려지는 것이 정상입니다(backpressure). 우회하려고 `highWaterMark`를 크게 올려 메모리를 늘리지 않습니다.
- 한 번에 열어 두는 스트림 수에는 운영체제의 파일 디스크립터 한도가 있습니다. 많은 파일을 동시에 열 때는 동시 처리 수를 제한합니다.

## 스트림 에러

스트림에서 에러가 나면 `'error'` 이벤트가 발생하고, 기본 설정(`autoDestroy`)에서는 스트림이 파괴되어 `'close'`가 이어집니다. 에러 뒤에는 `'close'` 외의 이벤트가 오지 않는 것이 규칙입니다.

```js
const rs = createReadStream('missing.txt')
rs.on('error', (err) => {
  console.error(err.code) // ENOENT
})
```

- `'error'` 리스너가 없으면 처리되지 않은 에러로 프로세스가 종료됩니다(기초 21편).
- 에러를 일으키려면 `stream.destroy(err)`를 씁니다. 직접 만든 Readable의 `read` 구현에서는 `throw`하지 않고 `this.destroy(err)`로, Writable의 `write` 구현에서는 `callback(err)`로 알립니다.
- `pipe()`는 에러를 전달하지 않습니다. 원본이 에러를 내면 목적지는 닫히지 않고, 목적지가 에러를 내면 원본은 연결이 풀린 채 열려 있습니다. 직접 모두 `destroy`해야 합니다.
- `for await`는 에러를 예외로 던지고 스트림을 파괴합니다.
- `pipeline()`과 `finished()`는 에러를 한 곳으로 모읍니다.
- `end()`한 Writable에 `write()`하면 `ERR_STREAM_WRITE_AFTER_END`, 파괴된 스트림에 쓰면 `ERR_STREAM_DESTROYED`, 끝난 Readable에 `push()`하면 `ERR_STREAM_PUSH_AFTER_EOF` 에러입니다.
- 중간에 닫힌 스트림을 `pipeline()`이 감지하면 `ERR_STREAM_PREMATURE_CLOSE`로 거부됩니다.
- HTTP 응답(`res`)을 `pipeline()` 목적지로 쓸 때 에러가 나면 `pipeline()`이 응답과 소켓을 파괴해서 에러 응답을 보낼 수 없습니다. 에러가 날 수 있는 작업(파일 존재 확인 등)을 먼저 하고 헤더를 보냅니다(자세히는 4편).

## pipeline이 pipe보다 나은 이유

`pipe()`는 데이터 전달과 backpressure만 맡고, 에러 전파와 정리는 맡지 않습니다. `pipeline()`은 이를 포함해 전체 수명주기를 맡습니다.

| 항목 | `pipe()` | `pipeline()` |
|------|----------|--------------|
| backpressure | 처리함 | 처리함 |
| 에러 전파 | 없음. 단계마다 `'error'` 필요 | 한 곳(콜백 또는 `await`)으로 모음 |
| 실패 시 정리 | 없음. 나머지 스트림이 열린 채 남음 | 남은 스트림 모두 `destroy` |
| 완료 알림 | 마지막 스트림의 `'finish'`를 직접 구독 | 콜백 또는 Promise |
| `async`/`await` | 직접 감싸야 함 | `stream/promises`로 바로 사용 |
| 제너레이터·이터러블 | 연결 불가 | 단계로 사용 가능 |
| 중단 | 직접 구현 | `signal` 옵션 |
| 웹 스트림 | 연결 불가 | 단계로 사용 가능(v19.7.0) |

```js
src.pipe(a).pipe(b)  // ❌ 하나가 실패해도 나머지는 열려 있음
await pipeline(src, a, b) // ✅ 실패하면 모두 정리되고 에러 하나로 거부
```

- 새 코드는 `pipeline()`을 쓰고 `pipe()`는 기존 코드를 읽을 때 이해하는 용도로 둡니다.

## 웹 스트림과 Node 스트림

웹 스트림(web streams)은 WHATWG Streams Standard를 구현한 표준 스트림 API입니다. `ReadableStream`, `WritableStream`, `TransformStream`이 있고, 브라우저와 여러 런타임에서 같은 API를 씁니다. Node.js에서는 Stable(안정성 지수 2)이며 v21.0.0부터 실험 단계가 아니고, 클래스는 v18.0.0부터 전역 객체로 노출됩니다.

| 항목 | Node 스트림 | 웹 스트림 |
|------|-------------|-----------|
| 모듈 | `node:stream` | 전역 또는 `node:stream/web` |
| 기반 | `EventEmitter`(이벤트) | Promise와 리더(reader) |
| 조각 | `Buffer`, 문자열(객체 모드는 임의 값) | 바이트는 `Uint8Array`, 임의 값 가능 |
| 연결 | `pipe()`, `pipeline()` | `pipeTo()`, `pipeThrough()` |
| 읽기 | 이벤트, `read()`, `for await` | `getReader()`, `for await` |
| 사용처 | `fs`, `net`, `http` 서버의 `req`·`res`, `zlib` | `fetch`의 `response.body`, 브라우저와 공유하는 코드 |

```js
const res = await fetch('https://example.com/')
const reader = res.body.getReader() // 웹 ReadableStream
const { value, done } = await reader.read()
```

- 둘은 서로 다른 객체이며 메서드가 다릅니다. `req.pipe()`는 Node 스트림, `res.body.pipeTo()`는 웹 스트림의 API입니다.
- 웹 스트림도 비동기 이터러블이라서 `for await`로 읽을 수 있습니다.
- Node.js 서버 코드는 대부분 Node 스트림이고, `fetch`·`Response`·`CompressionStream` 같은 웹 표준 API를 쓸 때 웹 스트림을 만납니다.

## 둘 사이 변환

`stream.Readable.toWeb()`·`fromWeb()`, `Writable.toWeb()`·`fromWeb()`, `Duplex.toWeb()`·`fromWeb()`이 Node 스트림과 웹 스트림을 서로 바꿉니다. v17.0.0에 추가되었고 v24.0.0(v22.17.0)부터 Stable입니다.

```js
import { Readable } from 'node:stream'

// Node 스트림 → 웹 스트림
const web = Readable.toWeb(createReadStream('a.txt'))
// 웹 스트림 → Node 스트림
const node = Readable.fromWeb(res.body)
await pipeline(node, createWriteStream('b.txt'))
```

- `Duplex.toWeb()`은 `{ readable, writable }` 쌍을 돌려주고, `Duplex.fromWeb()`은 그런 쌍을 받습니다.
- `fromWeb()`은 `encoding`, `highWaterMark`, `objectMode` 옵션을, `Readable.toWeb()`은 `strategy`(`highWaterMark`, `size`) 옵션을 받습니다.
- 바이트 조각의 타입이 바뀝니다. `toWeb()`한 결과는 `Uint8Array`를, `fromWeb()`한 결과는 `Buffer`를 내놓는 것을 확인했습니다(Node.js 24).
- 변환 없이 `pipeline()`이 웹 스트림을 직접 받으므로, 한 번만 연결한다면 `await pipeline(res.body, createWriteStream('b.txt'))`로 충분합니다.

## 압축 스트림 zlib

`node:zlib`는 Gzip, Deflate/Inflate, Brotli, Zstd 압축을 제공하며 압축·해제 스트림은 Transform입니다. `pipeline()` 중간에 끼우면 파일이 크더라도 조각 단위로 압축합니다.

```js
import { createGzip, createGunzip } from 'node:zlib'

await pipeline(
  createReadStream('big.log'),
  createGzip(),
  createWriteStream('big.log.gz'),
)
await pipeline(
  createReadStream('big.log.gz'),
  createGunzip(),
  createWriteStream('big.copy.log'),
)
```

- 생성 함수는 `createGzip()`/`createGunzip()`, `createDeflate()`/`createInflate()`, `createBrotliCompress()`/`createBrotliDecompress()`, `createZstdCompress()`/`createZstdDecompress()`입니다.
- 작은 버퍼는 한 번에 처리하는 `zlib.gzip(buffer, callback)`, `zlib.gunzip()` 등이 간단합니다. `util.promisify`로 Promise 버전을 만들 수 있습니다.
- 동기 API를 제외한 `zlib` API는 내부 스레드 풀을 씁니다. 압축 객체를 한꺼번에 수만 개 만들면 메모리 단편화가 생기므로 동시에 만드는 수를 제한하고 결과를 캐시합니다.
- 웹 표준의 `CompressionStream`도 있습니다(포맷 `deflate`, `deflate-raw`, `gzip`, `brotli`). 웹 스트림이므로 웹 스트림의 `pipeThrough()`로 연결합니다.
- HTTP에서는 `Accept-Encoding`을 보고 `Content-Encoding` 헤더와 함께 압축 스트림을 응답에 연결합니다. 이때도 `pipeline()`을 쓰고, 헤더를 보낸 뒤 에러가 나면 응답을 즉시 종료하는 것이 최선입니다.
- 압축 효과는 데이터에 따라 다릅니다. 반복이 많은 텍스트 약 137 MB가 약 0.46 MB가 된 측정이 있지만 이미 압축된 이미지·영상은 거의 줄지 않습니다.

## stream/promises

`node:stream/promises`는 `pipeline()`과 `finished()`의 Promise 버전을 내보내는 모듈입니다(v15.0.0 추가). `require('node:stream').promises`로도 접근할 수 있습니다.

```js
import { pipeline, finished } from 'node:stream/promises'
```

| 함수 | 반환 | 용도 |
|------|------|------|
| `pipeline(...streams[, options])` | Promise | 연결하고 끝날 때까지 대기 |
| `finished(stream[, options])` | Promise | 한 스트림의 종료 대기 |

- `node:stream`에서 가져오는 같은 이름의 함수는 콜백 버전입니다. 어느 모듈에서 가져왔는지로 구분합니다.
- `async` 함수 안에서 `await`와 `try/catch`로 에러를 처리하므로 콜백 중첩이 사라집니다.
- 옵션에 `AbortSignal`을 주어 중단할 수 있습니다.

## Readable.from

`Readable.from(iterable[, options])`는 이터러블이나 비동기 이터러블을 Readable로 바꿉니다(v12.3.0, v10.17.0 추가). 배열, 제너레이터, async 제너레이터로 스트림을 만드는 가장 짧은 방법입니다.

```js
import { Readable } from 'node:stream'

async function* generate() {
  yield 'hello'
  yield 'streams'
}
Readable.from(generate()).on('data', (c) => console.log(c))
// hello
// streams
```

- 기본값으로 `objectMode`가 `true`입니다. 요소 하나가 조각 하나이고 문자열 요소도 `Buffer`로 바뀌지 않습니다. 바이트 스트림으로 쓰려면 `{ objectMode: false }`를 줍니다.
- 문자열이나 `Buffer` 하나를 넘기면 글자나 바이트별로 순회하지 않고 통째로 하나의 조각이 됩니다.
- `null`을 넘기면 `'error'`가 발생합니다.
- Promise를 담은 이터러블을 넘기면 처리되지 않은 거부가 생길 수 있으니 값을 `await`한 뒤 `yield`하는 async 제너레이터를 씁니다.
- 테스트용 입력 만들기, 배열을 `pipeline()`의 원본으로 쓰기, 큰 파일을 생성해서 쓰기 등에 유용합니다.
- 두 번째 인수의 옵션은 `new Readable()`에 전달됩니다.

## 스트림 compose

`stream.compose(...streams)`는 여러 스트림을 하나의 Duplex로 합칩니다. 첫 번째 스트림에 쓰고 마지막 스트림에서 읽으며, 내부는 `pipeline()`으로 이어집니다.

```js
import { compose } from 'node:stream'

async function* toUpper(source) {
  for await (const chunk of source) {
    yield String(chunk).toUpperCase()
  }
}
const step = compose(toUpper, createGzip(), createGunzip())
step.end('hello')
for await (const c of step) console.log(String(c)) // HELLO
```

- 하나라도 에러가 나면 합쳐진 Duplex를 포함해 모두 `destroy`됩니다.
- `pipeline()`은 처음이 Readable, 끝이 Writable인 닫힌 회로입니다. `compose()`는 열린 Duplex를 돌려주어 다른 곳에서 다시 `pipe`하거나 재사용할 수 있습니다.
- 인수로 `AsyncIterable`(읽기 Duplex로 변환, `null` yield 불가), async 제너레이터 함수(변환 Duplex, 첫 매개변수로 소스를 받음), `AsyncFunction`(쓰기 Duplex, `null` 또는 `undefined` 반환)을 줄 수 있습니다.
- `readable.compose(stream)`은 `stream.compose(readable, stream)`과 같은 단축 메서드입니다. v19.1.0에 추가되었고 v24.0.0부터 Stable입니다.
- `stream.compose()` 자체는 Node.js 24.19.0과 26.2.0에서 Stable이 되었고, 그 이전의 24.x에서는 Experimental이었습니다. 쓰는 마이너 버전을 확인합니다.
- 재사용할 변환 묶음(압축 후 암호화 등)을 하나의 부품으로 만들 때 씁니다.

## 핵심 정리

- `pipe()`는 데이터와 backpressure만 이어 주고 에러 전파·정리를 하지 않으므로, 새 코드는 `stream/promises`의 `pipeline()`을 씁니다.
- `pipeline()`은 실패 시 모든 스트림을 `destroy`하고 에러 하나로 거부하며, 제너레이터·웹 스트림·`signal`도 받습니다. `finished()`는 한 스트림의 종료를 기다립니다.
- backpressure는 `write()`가 `false`이면 `'drain'`까지 멈추는 규칙이며, `highWaterMark`는 한계가 아니라 문턱입니다(바이트는 Windows 16 KiB, 그 외 64 KiB, 객체는 16개).
- 객체 모드는 `null`을 뺀 임의 값을 조각으로 다루고, `for await`는 에러를 던지고 중단 시 스트림을 파괴합니다.
- 큰 파일은 `createReadStream`과 `createWriteStream`을 `pipeline()`으로 이어 조각 단위로 처리하고, 텍스트는 조각 경계에서 줄이 잘리는 것을 처리합니다.
- 웹 스트림과 Node 스트림은 `toWeb`·`fromWeb`으로 변환하고, `zlib` 압축 스트림, `Readable.from`, `compose`는 `pipeline()`의 부품이 됩니다.

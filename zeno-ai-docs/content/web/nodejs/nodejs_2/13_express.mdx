## 앱과 Router

Express는 `node:http` 위에서 라우팅과 미들웨어 체인을 제공하는 최소한의 웹 프레임워크입니다. `express()`가 돌려주는 앱은 `http.createServer()`에 넘길 수 있는 요청 핸들러 함수입니다(핸들러와 체인의 원리는 12편). 이 문서는 npm에서 `latest` 태그인 5.x를 기준으로 하며, 5.x는 Node.js 18 이상이 필요합니다.

```js
import express from 'express'

const app = express()
app.get('/health', (req, res) => {
  res.json({ ok: true })
})
app.listen(3000) // 3000번 포트에서 요청 대기
```

- `app.get`, `app.post`, `app.put`, `app.delete`처럼 HTTP 메서드 이름으로 라우트를 등록합니다. `app.all`은 모든 메서드에, `app.use`는 경로 접두사에 맞는 모든 요청에 반응합니다.
- 핸들러를 여러 개, 또는 배열로 넘길 수 있고 앞 핸들러가 `next()`를 호출해야 다음으로 넘어갑니다.
- 같은 경로의 메서드들은 `app.route('/book').get(a).post(b)`로 묶을 수 있습니다.

`express.Router()`는 경로 접두사 아래에 마운트하는 미니 앱입니다. 라우트와 미들웨어를 파일 단위로 나누는 기본 도구입니다.

```js
// routes/users.js
import { Router } from 'express'

export const usersRouter = Router()
usersRouter.get('/', (req, res) => res.json([]))
usersRouter.get('/:id', (req, res) => {
  res.json({ id: req.params.id })
})

// app.js
app.use('/users', usersRouter) // GET /users, GET /users/7
```

| `Router` 옵션 | 기본값 | 의미 |
|---------------|--------|------|
| `mergeParams` | `false` | 부모 경로의 `req.params`를 자식 Router에서도 보이게 함 |
| `caseSensitive` | `false` | 대소문자를 구분 |
| `strict` | `false` | 끝의 슬래시를 구분 |

`mergeParams`가 꺼져 있으면 `app.use('/users/:uid/posts', router)`로 마운트해도 router 안의 `req.params`에 `uid`가 없습니다(`{}`). 켜면 `{ uid: '7' }`이 들어옵니다.

### 경로 문법

Express 5의 경로는 path-to-regexp 8 문법입니다.

| 목적 | 4.x | 5.x |
|------|-----|-----|
| 이름 있는 매개변수 | `/:id` | `/:id` (같음) |
| 와일드카드 | `/*` | `/*splat` (이름 필수) |
| 루트까지 포함한 와일드카드 | `/*` | `/{*splat}` |
| 선택 구간 | `/:file.:ext?` | `/:file{.:ext}` |
| 정규식 문자 | `/[ab]/:slug` | 지원 안 함, 경로 배열로 분리 |

```js
app.get('/files/*splat', (req, res) => {
  // GET /files/a/b
  res.json(req.params) // { splat: ['a', 'b'] } (배열)
})
app.get('/opt/:file{.:ext}', (req, res) => {
  // /opt/img.png → { file: 'img', ext: 'png' }
  // /opt/img     → { file: 'img' }
  res.json(req.params)
})
```

경로 대신 정규식 리터럴 `app.get(/.*fly$/, ...)`은 계속 쓸 수 있습니다. 예약 문자 `()[]?+!`를 글자 그대로 쓰려면 `\`로 이스케이프합니다.

## 미들웨어 순서

미들웨어는 `(req, res, next)`를 받는 함수이고, 등록한 순서대로 실행됩니다. 개념은 11편, 직접 구현한 체인은 12편에서 다뤘고 Express에서는 `app.use()`와 라우트 메서드가 그 체인을 만듭니다.

```js
app.use((req, res, next) => {
  console.log(req.method, req.url) // 1. 모든 요청
  next()
})
app.use(express.json()) //           2. 본문 파싱
app.use('/users', usersRouter) //    3. 라우터
app.use((req, res) => {
  res.status(404).json({ error: 'not found' }) // 4. 404
})
```

- 요청은 위에서 아래로 내려가다 응답을 보내는 핸들러에서 멈춥니다. `next()`를 부르지도 응답하지도 않으면 요청이 그대로 걸려 있습니다.
- 종류는 앱 수준(`app.use`·`app.METHOD`), 라우터 수준(`router.use`), 에러 처리(인자 4개), 내장(`express.json` 등), 서드파티(`cors` 등) 다섯 가지입니다.
- 라우트가 하나도 맞지 않으면 Express가 기본 404를 응답합니다. 위처럼 마지막에 `app.use`를 두면 JSON 404로 바꿀 수 있습니다.
- `next('route')`는 현재 라우트의 남은 핸들러를 건너뛰고 다음 라우트로 갑니다. `app.METHOD`·`router.METHOD`에서만 동작합니다. `next('router')`는 현재 Router를 빠져나갑니다. `next(err)`는 에러 미들웨어로 갑니다.

**흔한 실수:** 파서·로거·인증 같은 공통 미들웨어를 라우트 뒤에 등록하는 것입니다. 이미 응답이 나간 뒤라서 실행되지 않거나, 라우트가 파싱 전의 `req.body`(`undefined`)를 읽습니다. 공통 미들웨어는 라우트보다 위에, 404와 에러 핸들러는 맨 아래에 둡니다.

## req·res 확장

Express는 `http.IncomingMessage`와 `http.ServerResponse`를 확장한 `req`, `res`를 핸들러에 넘깁니다. 코어 객체의 메서드(`res.end`, `req.on`)도 그대로 쓸 수 있습니다.

| 이름 | 내용 |
|------|------|
| `req.params` | 경로 매개변수. 5.x에서는 프로토타입이 없는 객체 |
| `req.query` | 쿼리스트링을 파싱한 객체. 5.x에서는 읽기 전용 |
| `req.body` | 본문 파서가 채움. 파서가 없으면 `undefined` |
| `req.originalUrl` | 마운트 접두사까지 포함한 원래 URL |
| `req.baseUrl` | 이 Router가 마운트된 경로 |
| `req.app` | 이 요청을 처리하는 앱 |
| `req.ip`, `req.protocol` | 클라이언트 IP, `http` 또는 `https` |

```js
app.use('/a', router)
// router 안에서 GET /a/b?x=1 을 받으면
// req.baseUrl     '/a'
// req.originalUrl '/a/b?x=1'
// req.url         '/b?x=1' (마운트 경로가 잘림)
// req.path        '/b'
```

- 5.x의 기본 쿼리 파서는 simple입니다. `?c=1&c=2`는 `{ c: ['1', '2'] }`이지만 `?a[b]=1`은 중첩되지 않고 키가 `'a[b]'`입니다. 중첩이 필요하면 `app.set('query parser', 'extended')`를 씁니다.
- `req.ip`는 기본적으로 소켓의 원격 주소입니다. 리버스 프록시 뒤에서는 `app.set('trust proxy', 1)`처럼 신뢰할 프록시 단계 수를 정해야 `X-Forwarded-For`, `X-Forwarded-Proto`를 반영합니다. 기본값은 `false`입니다. `true`는 헤더를 그대로 믿어 클라이언트가 IP를 위조할 수 있으므로 쓰지 않습니다.

응답 쪽 대표 메서드입니다.

| 메서드 | 동작 |
|--------|------|
| `res.status(code)` | 상태 코드 설정(체이닝). 100–999 정수만 허용 |
| `res.json(obj)` | JSON 직렬화, `Content-Type: application/json` 설정 후 전송 |
| `res.send(body)` | 문자열·Buffer·객체를 타입에 맞게 전송 |
| `res.sendStatus(code)` | 상태 코드와 그 문구(`Not Found` 등)를 본문으로 전송 |
| `res.set(name, value)` | 헤더 설정 |
| `res.redirect(status, url)` | 리다이렉트 |
| `res.sendFile(path)` | 파일 전송(`root` 옵션 또는 절대 경로 필요) |

`res.locals`는 한 요청 동안만 사는 저장소입니다. 앞 미들웨어가 채운 값을 뒤 핸들러가 읽는 데 씁니다(`res.locals.user = user`). 앱 전체에서 공유하는 값은 `app.locals`입니다.

**흔한 실수:** `res.json()`을 부르고 `return` 없이 아래 코드를 이어 써서 `res.send()`를 또 부르는 것입니다. 두 번째 호출은 `ERR_HTTP_HEADERS_SENT`를 일으킵니다(26편).

## 에러 처리

Express는 핸들러에서 던진 동기 에러와 `next(err)`로 넘긴 에러를 모두 에러 처리 미들웨어로 보냅니다. 에러 처리 미들웨어는 인자가 정확히 네 개인 함수이고, 다른 라우트와 미들웨어보다 아래에 등록합니다.

```js
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err) // 이미 일부 전송됨
  const status = err.status ?? 500
  res.status(status).json({ error: err.message })
})
```

- 인자 개수로 에러 핸들러를 구분하므로 `next`를 쓰지 않아도 매개변수에서 빼면 안 됩니다(3개면 일반 미들웨어).
- 에러 핸들러를 여러 개 두고 `next(err)`로 이어 갈 수 있습니다(로깅 → 응답).
- 에러 핸들러가 없거나 `next(err)`로 위임하면 기본 에러 핸들러가 응답합니다. 상태 코드는 `err.status` 또는 `err.statusCode`에서 가져오고 4xx–5xx 범위 밖이면 500입니다. `NODE_ENV=production`이면 HTML 상태 문구만, 그 외에는 스택 트레이스까지 응답합니다.
- 응답 헤더가 이미 나간 뒤(`res.headersSent`)에는 상태 코드를 바꿀 수 없으므로 기본 핸들러에 위임합니다.

### Express 5의 async 에러 전파

Express 5는 핸들러와 미들웨어가 반환한 Promise가 reject되면 자동으로 `next(err)`를 호출합니다. async 함수에서 `throw`하거나 `await`가 실패하면 에러 핸들러로 갑니다.

```js
// Express 4: try/catch로 감싸 next를 직접 호출해야 했음
app.get('/users/:id', async (req, res) => {
  // reject되면 에러 핸들러로 이동
  const user = await findUser(req.params.id)
  if (!user) {
    const err = new Error('user not found')
    err.status = 404
    throw err // 에러 핸들러가 404로 응답
  }
  res.json(user)
})
```

- 자동 전파는 Promise를 반환할 때만 일어납니다. `.then()` 체인을 쓸 때는 반드시 `return`합니다. 반환하지 않으면 `.catch(next)`를 직접 붙입니다.
- 콜백 API(`fs.readFile(path, cb)`)나 타이머 안에서 난 에러는 Promise가 아니므로 자동으로 잡히지 않습니다. 콜백에서 `next(err)`를 호출하거나 Promise 버전(`node:fs/promises`)을 `await`합니다.
- Promise를 반환하지 않는 곳에서 던진 에러가 잡히지 않으면 `uncaughtException`으로 프로세스가 종료될 수 있습니다.

**흔한 실수:** 에러 핸들러에서 응답하지 않고 로그만 남기고 끝내는 것입니다. 에러 핸들러도 `res`로 응답하거나 `next(err)`로 넘겨야 요청이 끝납니다.

## 본문 파싱

Express 5는 본문을 자동으로 읽지 않습니다. 내장 미들웨어를 등록해야 `req.body`가 채워집니다. `Content-Type`이 맞는 요청만 처리하고 나머지는 건너뛰며, 건너뛴 요청의 `req.body`는 `undefined`입니다.

| 미들웨어 | 처리하는 본문 | `req.body` |
|----------|---------------|------------|
| `express.json()` | `application/json` | 파싱한 객체·배열 |
| `express.urlencoded()` | `application/x-www-form-urlencoded` | 객체 |
| `express.text()` | `text/plain` | 문자열 |
| `express.raw()` | `application/octet-stream` | Buffer |

```js
app.use(express.json({ limit: '10kb' }))
app.post('/echo', (req, res) => {
  res.json(req.body) // {"a":1} 을 보내면 { a: 1 }
})
```

- `limit` 기본값은 `'100kb'`입니다. 넘으면 413, JSON 문법 오류면 400으로 에러가 `next`에 전달됩니다(에러 객체의 `type`은 각각 `entity.too.large`, `entity.parse.failed`). 직접 구현했던 크기 제한(4편)을 이 옵션이 대신합니다.
- `express.json()`의 `strict`는 기본 `true`라 객체와 배열만 받습니다. `type`으로 처리할 `Content-Type`을 바꾸고, `verify(req, res, buf)`로 파싱 전에 원본 Buffer를 볼 수 있습니다(웹훅 서명 검증에 씁니다).
- `express.urlencoded()`는 5.x에서 `extended` 기본값이 `false`입니다(Node의 `querystring` 파싱). 중첩 객체 형식(`a[b]=1`)이 필요하면 `{ extended: true }`를 줍니다.
- 파서는 본문 스트림을 한 번만 읽습니다(11편). 같은 요청에 JSON 파서를 두 번 거쳐도 두 번째는 이미 읽힌 본문을 건너뜁니다.
- 파일 업로드(`multipart/form-data`)는 이 파서들이 처리하지 않습니다. `multer` 같은 별도 미들웨어를 씁니다(11편).
- 본문의 형식·타입 검증은 파서의 일이 아닙니다. 핸들러나 미들웨어에서 Zod 같은 스키마로 검증합니다(8편).

**흔한 실수:** `express.json()` 없이 `req.body.name`을 읽는 것입니다. 4.x에서는 `{}`라 `undefined`가 조용히 나왔지만 5.x에서는 `req.body` 자체가 `undefined`라 `TypeError`가 납니다.

## 정적 파일

`express.static(root)`는 `root` 폴더의 파일을 요청 경로대로 응답하는 미들웨어입니다. 파일이 없으면 `next()`를 호출해 뒤의 라우트로 넘깁니다. 경로 탈출(`..`)은 막아 줍니다(직접 구현은 5편).

```js
import { fileURLToPath } from 'node:url'

const url = new URL('./public', import.meta.url)
const pub = fileURLToPath(url)
app.use(express.static(pub)) //            GET /logo.png
app.use('/assets', express.static(pub, { maxAge: '1d' }))
// GET /assets/logo.png → max-age=86400
```

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `dotfiles` | `'ignore'` | 점으로 시작하는 파일 처리(`allow`, `deny`, `ignore`) |
| `index` | `['index.html']` | 폴더 요청 시 보낼 파일 |
| `maxAge` | `0` | `Cache-Control: max-age` |
| `etag` | `true` | ETag 헤더 생성 |
| `extensions` | `[]` | 확장자를 생략한 요청에 시도할 확장자 |
| `redirect` | `true` | 폴더 요청에 끝 슬래시를 붙여 리다이렉트 |

- `root`에 상대 경로를 쓰면 실행 위치(`process.cwd()`) 기준으로 해석됩니다. ESM에는 `__dirname`이 없으므로 위처럼 `import.meta.url`에서 절대 경로를 만듭니다(26편).
- 5.x는 `dotfiles` 기본이 `'ignore'`라 `/.well-known/` 같은 점 폴더가 404입니다. 필요한 경로에만 `{ dotfiles: 'allow' }`로 따로 엽니다.
- 한 개의 파일을 보낼 때는 `res.sendFile(path, { root })`를 씁니다.

## helmet·cors·rate limit 미들웨어

세 가지 모두 서드파티 패키지이며 `npm install helmet cors express-rate-limit`으로 설치합니다. 공통 미들웨어이므로 라우트보다 위에 등록합니다.

```js
import helmet from 'helmet'
import cors from 'cors'
import { rateLimit } from 'express-rate-limit'

app.use(helmet())
app.use(cors({ origin: 'https://app.example.com' }))
app.use(rateLimit({ windowMs: 60_000, limit: 100 }))
```

**helmet**은 보안 관련 응답 헤더를 한 번에 설정합니다. `helmet()` 기본값이 켜는 항목에는 `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`와 `X-Powered-By` 제거가 들어 있습니다. 항목별로 옵션을 주거나 `null`로 끌 수 있습니다.

```js
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      'script-src': ["'self'", 'cdn.example.com'],
    },
  },
}))
```

**cors**는 CORS 응답 헤더를 붙이고 `OPTIONS` preflight에 응답합니다(원리는 9편).

- 인자 없이 `cors()`만 쓰면 `Access-Control-Allow-Origin: *`이라 모든 출처를 허용합니다. 운영에서는 `origin`에 문자열·배열·정규식·함수로 허용 출처를 적습니다.
- `methods` 기본값은 `GET,HEAD,PUT,PATCH,POST,DELETE`입니다. 쿠키를 보내는 요청에는 `credentials: true`와 구체적인 `origin`이 함께 필요합니다.
- CORS는 브라우저가 지키는 정책입니다. curl 같은 클라이언트는 영향을 받지 않으므로 접근 제어는 인증과 인가로 합니다.

**express-rate-limit**은 시간 창당 요청 수를 제한하고 초과하면 429를 응답합니다.

- `windowMs`는 시간 창 길이(ms), `limit`은 창당 최대 요청 수입니다(예전 이름 `max`가 아니라 `limit`입니다).
- `standardHeaders: 'draft-8'`은 `RateLimit` 헤더를, `legacyHeaders`는 `X-RateLimit-*` 헤더를 켜고 끕니다.
- 기본 저장소는 프로세스 메모리라 인스턴스가 여러 개면 카운트가 따로 쌓입니다. 공유하려면 `store` 옵션에 Redis 같은 외부 저장소를 씁니다(18편).
- 기본 키는 클라이언트 IP입니다. 프록시 뒤에서 `trust proxy`를 설정하지 않으면 모든 요청이 프록시 IP 하나로 집계됩니다. 로그인 같은 민감한 경로에는 더 엄격한 제한기를 따로 겁니다.

```js
const loginLimiter = rateLimit({
  windowMs: 15 * 60_000,
  limit: 5,
})
app.post('/login', loginLimiter, loginHandler) // 경로별 제한
```

## router·controller·service로 나누기

핸들러에 HTTP 처리, 업무 규칙, 데이터 접근을 모두 쓰면 테스트가 어렵습니다. 세 계층으로 나눕니다.

| 계층 | 책임 | HTTP를 아는가 |
|------|------|---------------|
| router | 경로·메서드와 미들웨어를 컨트롤러에 연결 | 예 |
| controller | `req`에서 값을 꺼내 서비스를 부르고 `res`로 응답 | 예 |
| service | 업무 규칙과 데이터 접근 호출 | 아니오 |

```js
// users.service.js — req, res를 모름
export async function getUser(id) {
  const user = await db.findUser(id)
  if (!user) {
    const err = new Error('not found')
    err.status = 404
    throw err
  }
  return user
}
```

```js
// users.controller.js
export async function show(req, res) {
  res.json(await getUser(req.params.id))
}

// users.routes.js — 에러는 async 전파로 에러 핸들러에 도달
router.get('/:id', show)
```

- 서비스가 `req`, `res`를 모르면 HTTP 없이 함수 호출만으로 테스트할 수 있습니다(24편).
- 서비스는 에러를 던지고, HTTP 상태 코드로의 변환은 에러 핸들러 한 곳에서 합니다. Express 5에서는 컨트롤러에 `try/catch`가 필요 없습니다.
- 폴더는 기능별(`users/`에 `routes`, `controller`, `service`)이나 계층별(`routes/`, `controllers/`) 중 하나로 일관되게 나눕니다. 앱 조립(`createApp()`)과 `listen()`을 파일로 분리하면 테스트에서 포트 0으로 서버를 띄우기 쉽습니다.
- 데이터 접근 코드는 다시 저장소(repository)로 분리할 수 있습니다(16편, 17편). 이 구조가 14편의 NestJS 모듈·컨트롤러·프로바이더 구분과 그대로 대응합니다.

## Express 4에서 5로의 변경점

4.x에서 올릴 때 확인할 항목을 모았습니다. 5.x는 Node.js 18 이상이 필요합니다.

| 영역 | 4.x | 5.x |
|------|-----|-----|
| async 핸들러 에러 | `next`로 직접 전달 | reject된 Promise를 자동 전달 |
| 와일드카드 | `/*` | `/*splat`, 루트 포함은 `/{*splat}` |
| 선택 구간 | `?` | `{}` 구간 |
| 경로의 정규식 문자 | 일부 지원 | 지원 안 함 |
| `req.body` | 파서 없으면 `{}` | 파서 없으면 `undefined` |
| `express.urlencoded` `extended` | `true` | `false` |
| 기본 쿼리 파서 | extended | simple |
| `req.query` | 쓰기 가능 | 읽기 전용 |
| `req.params` | 일반 객체, 와일드카드는 문자열 | 프로토타입 없는 객체, 와일드카드는 배열 |
| `express.static` `dotfiles` | 점 파일도 서빙 | 기본 `ignore` |
| `req.host` | 포트를 잘라냄(버그) | 포트 포함 |
| `app.listen` 콜백 | 서버 에러는 던져짐 | 에러가 콜백 인자로 전달 |

제거되거나 시그니처가 바뀐 API입니다.

| 4.x | 5.x |
|-----|-----|
| `app.del()` | `app.delete()` |
| `req.param(name)` | `req.params`, `req.body`, `req.query` 중 직접 선택 |
| `res.json(obj, status)` | `res.status(status).json(obj)` |
| `res.send(body, status)` | `res.status(status).send(body)` |
| `res.send(200)` | `res.sendStatus(200)` |
| `res.redirect(url, status)` | `res.redirect(status, url)` |
| `res.redirect('back')` | `res.redirect(req.get('Referrer') ?? '/')` |
| `res.sendfile()` | `res.sendFile()` |
| `hidden`, `from` 옵션 | `dotfiles: 'allow'`, `root` 옵션 |
| `req.acceptsCharset()` 등 | `req.acceptsCharsets()` 등 복수형 |
| `app.param(fn)`, `router.param(fn)` | 제거(이름을 지정한 `app.param(name, fn)`은 유지) |

- 새 동작 두 가지: `res.status()`가 100–999 범위 밖의 정수나 숫자가 아닌 값을 받으면 에러를 던지고, `res.clearCookie()`는 `maxAge`, `expires` 옵션을 무시합니다.
- `express.json()`, `express.urlencoded()`, `express.text()`, `express.raw()`는 Brotli(`Content-Encoding: br`) 본문을 풀 수 있습니다.
- `.js` 파일의 MIME 타입이 `text/javascript`로 바뀌었습니다.
- 4.x는 최신 4.x 계열이 `latest-4` 태그로 따로 관리됩니다. 4.x에서 5.x로 올릴 때는 코드 변환 도구 대신 위 표의 항목을 검색해 하나씩 고칩니다.

## 핵심 정리

- Express는 앱과 Router가 미들웨어 체인을 만드는 얇은 프레임워크이며, 등록 순서가 곧 실행 순서입니다. 공통 미들웨어는 위, 404와 에러 핸들러는 아래에 둡니다.
- 에러 핸들러는 인자가 네 개인 함수이고, Express 5는 async 핸들러의 reject를 자동으로 에러 핸들러에 전달합니다.
- `req.body`는 `express.json()` 등을 등록해야 채워지고, `limit` 기본값은 100kb입니다.
- helmet(보안 헤더), cors(출처 허용), express-rate-limit(요청 횟수 제한)은 라우트 위에 두는 서드파티 미들웨어입니다.
- router는 연결, controller는 HTTP 입출력, service는 업무 규칙으로 나누면 서비스를 HTTP 없이 테스트할 수 있습니다.
- 4에서 5로 올릴 때는 경로 문법(`/*splat`), `req.body`와 `extended` 기본값, 제거된 API를 확인합니다.

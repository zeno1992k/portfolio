## Server timeout

`server.timeout`은 소켓이 오가는 데이터 없이 유휴 상태로 있을 수 있는 시간(밀리초)입니다. 기본값은 0(제한 없음)이고, Node 13.0.0에서 120초에서 0으로 바뀌었습니다. 서버에는 이 값 말고도 타임아웃이 셋 더 있고, 각각 지키는 대상이 다릅니다.

| 이름 | 기본값(Node 24) | 지키는 구간 | 만료 시 |
|------|-----------------|-------------|---------|
| `timeout` | 0 (없음) | 소켓의 유휴 시간 | `'timeout'` 이벤트, 리스너가 없으면 소켓 파괴 |
| `headersTimeout` | 60000 | 요청 헤더 전체 수신 | 408 응답 후 연결 종료 |
| `requestTimeout` | 300000 | 요청 전체(헤더와 본문) 수신 | 408 응답 후 연결 종료 |
| `keepAliveTimeout` | 5000 | 응답 뒤 다음 요청 대기 | 소켓 파괴 |

```js
server.timeout = 30_000
// 또는 만료 시 직접 처리
server.setTimeout(30_000, (socket) => {
  socket.end('HTTP/1.1 408 Request Timeout\r\n' +
    'Connection: close\r\n\r\n')
})
```

- 만료되면 서버가 `'timeout'` 이벤트를 소켓과 함께 발생시킵니다. 리스너가 없으면 소켓을 파괴하고, 리스너를 달면 닫는 일까지 직접 해야 합니다. 응답 없이 파괴하면 클라이언트는 응답을 못 받고 연결이 끊긴 것만 봅니다.
- 이 값은 연결이 만들어질 때 적용되므로 바꿔도 이미 열린 연결에는 영향이 없습니다.
- 요청 하나에만 걸고 싶으면 `res.setTimeout(ms, callback)`으로 그 응답의 소켓 타임아웃을 설정합니다.
- 소켓이 유휴인 시간을 재는 값이지 요청 처리 시간의 상한이 아닙니다. 핸들러가 오래 걸리는 것은 이 값으로 막을 수 없습니다. 처리 시간 상한이 필요하면 핸들러 안에서 `AbortSignal.timeout()` 같은 타이머를 직접 걸고 504나 503으로 응답합니다.

## headersTimeout

`headersTimeout`은 요청 헤더가 모두 도착할 때까지 파서가 기다리는 최대 시간입니다. 헤더를 아주 천천히 보내 연결을 붙잡는 공격(Slowloris)을 막습니다.

```js
const server = http.createServer({
  headersTimeout: 20_000,
  requestTimeout: 60_000,
}, handler)
```

헤더를 끝내지 않은 채 기다리게 해 확인한 결과는 이렇습니다.

```text
GET / HTTP/1.1
Host: x
(빈 줄을 보내지 않음)
→ HTTP/1.1 408 Request Timeout 후 연결 종료
```

- 기본값은 `requestTimeout`과 60000 중 작은 값이라 보통 60초입니다(Node 18.14와 19.4부터).
- 만료되면 서버는 요청 리스너를 호출하지 않고 408을 보낸 뒤 연결을 닫습니다. 핸들러는 이 요청의 존재를 모릅니다.
- `requestTimeout`이 0이 아닐 때 `headersTimeout`이 더 크면 서버를 만들 때 `ERR_OUT_OF_RANGE`가 발생합니다. 항상 `headersTimeout <= requestTimeout`이어야 합니다.
- 만료 검사는 `connectionsCheckingInterval`(기본 30000)마다 돌기 때문에 실제로 끊기는 시점은 설정값보다 늦을 수 있습니다. `headersTimeout`을 100ms로, 검사 간격을 1000ms로 두었더니 약 1초 뒤에 끊겼습니다.
- 응답을 보낸 뒤 쉬고 있는 keep-alive 연결은 대상이 아닙니다. 두 값을 100ms로 두고 500ms 쉰 뒤에도 같은 연결이 재사용되었습니다.
- 문서는 리버스 프록시가 앞에 없는 서버라면 0이 아닌 값(예: 120초)으로 두라고 안내합니다.

## requestTimeout

`requestTimeout`은 요청 전체(헤더와 본문)를 다 받을 때까지 허용하는 시간입니다. 기본값은 300000(5분)이며 Node 18.0.0에서 무제한에서 바뀌었습니다.

```js
const server = http.createServer({
  requestTimeout: 120_000,
}, handler)
```

본문을 느리게 보내는 요청으로 확인한 결과입니다.

```text
POST / HTTP/1.1
Content-Length: 10
(본문을 3바이트만 보내고 멈춤)
→ HTTP/1.1 408 Request Timeout 후 연결 종료
```

- 만료되면 `headersTimeout`과 같이 408을 보내고 연결을 닫습니다.
- 재는 대상은 요청을 받는 시간뿐입니다. 요청을 다 받은 뒤 핸들러가 오래 걸리거나 응답을 천천히 보내는 시간은 포함하지 않습니다. `requestTimeout`을 200ms로 두고 600ms 걸리는 핸들러를 호출해도 200 응답이 나갔습니다.
- 대용량 업로드를 받는 서버는 업로드에 걸리는 최대 시간보다 크게 잡아야 합니다. 너무 짧으면 느린 네트워크의 정상 업로드가 408로 끊깁니다.
- 0으로 두면 헤더·본문 수신 시간 제한이 사라집니다. 문서는 서버가 리버스 프록시 없이 노출된다면 0이 아닌 값을 쓰라고 권합니다.

## 연결 유지 keep-alive

keep-alive는 응답을 보낸 뒤에도 TCP 연결을 닫지 않고 다음 요청에 재사용하는 방식으로, 영속 연결(persistent connection)이라고도 합니다. 요청마다 TCP(와 TLS) 연결을 새로 맺는 비용을 줄입니다. HTTP/1.1에서는 기본이고, 끄려면 `Connection: close`를 보냅니다. HTTP/1.0은 기본이 비영속이라 따로 협상해야 합니다.

```js
const server = http.createServer({
  keepAliveTimeout: 65_000,
}, handler)
server.maxRequestsPerSocket = 1000
```

| 설정 | 기본값 | 의미 |
|------|--------|------|
| `keepAliveTimeout` | 5000 | 마지막 응답 뒤 다음 요청을 기다리는 시간. 0이면 이 타임아웃을 끔 |
| `keepAliveTimeoutBuffer` | 1000 | 실제 소켓 타임아웃은 `keepAliveTimeout`에 이 값을 더한 값 (Node 24.6.0 추가) |
| `maxRequestsPerSocket` | 0 (무제한) | 연결 하나로 처리할 요청 수. 한도에 닿으면 `Connection: close`를 보내고 이후 요청에는 503 |

- 서버는 응답에 `Keep-Alive: timeout=5` 같은 헤더로 클라이언트에 대기 시간을 알려 줍니다. 기본 서버에서 응답 헤더를 확인했을 때 `connection: keep-alive`와 `keep-alive: timeout=5`가 있었고, 클라이언트 Agent를 끄면(`agent: false`) `connection: close`였습니다.
- `keepAliveTimeoutBuffer`는 서버가 알린 시간보다 소켓을 조금 더 살려 두어 클라이언트와 엇갈리는 `ECONNRESET`을 줄이는 완충입니다.
- 타임아웃 값들은 연결을 만들 때 적용되므로 바꿔도 기존 연결에는 영향이 없습니다.
- 기본 Agent로 같은 서버에 요청 3개를 보냈을 때 서버에는 연결이 1개만 생겼고, `keepAlive: false`인 Agent로 보냈을 때는 3개가 생겼습니다.
- `createServer`의 `keepAlive` 옵션(기본 false)은 TCP 수준의 keep-alive 프로브 설정이라 HTTP의 연결 유지와 다른 개념입니다.
- HTTP/2에서는 `Connection`과 `Keep-Alive` 헤더를 쓸 수 없습니다(자세히는 07편).

**버전 주의:** `server.keepAliveTimeout` 기본값은 Node 24.15에서 직접 확인한 값이 5000입니다. Node 24와 26 문서의 `createServer` 옵션 항목에는 65000이라고 적혀 있어 같은 문서 안에서 어긋나는데, 서버 속성 쪽 설명(5000)과 실제 동작이 맞습니다. 개발 중인 main 브랜치 문서에는 기본값을 5초에서 65초로 올리는 변경이 기록되어 있고 적용 버전은 아직 정해지지 않았습니다. 버전에 기대지 말고 값을 코드에서 명시합니다.

## http.Agent

`http.Agent`는 HTTP 클라이언트의 연결 재사용을 관리하는 객체입니다. 호스트와 포트별로 요청 대기열과 소켓 풀을 두고, 요청이 끝난 소켓을 닫지 않고 풀에 넣었다가 다음 요청에 내줍니다.

```js
const agent = new http.Agent({
  keepAlive: true,
  maxSockets: 50,
  maxFreeSockets: 10,
})
http.get({ host, port, path: '/', agent }, onResponse)
```

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `keepAlive` | false | 요청이 없어도 소켓을 풀에 남겨 재사용 |
| `maxSockets` | Infinity | 호스트당 동시 소켓 수. 넘는 요청은 대기열에서 기다림 |
| `maxTotalSockets` | Infinity | 모든 호스트를 합친 동시 소켓 수 |
| `maxFreeSockets` | 256 | 호스트당 풀에 남겨 둘 유휴 소켓 수 (`keepAlive`일 때만) |
| `scheduling` | `'lifo'` | 유휴 소켓 선택 방식. `'lifo'`는 가장 최근에 쓴 소켓을 먼저 사용 |
| `timeout` | 없음 | 소켓이 만들어질 때 거는 소켓 타임아웃 |
| `agentKeepAliveTimeoutBuffer` | 1000 | 서버가 알린 keep-alive 시간에서 빼는 값. 서버보다 먼저 닫으려는 완충 (Node 24.7.0 추가) |

- 기본으로 쓰이는 `http.globalAgent`는 `keepAlive`가 켜져 있고 `timeout`이 5초입니다(Node 19.0.0부터). 직접 `new http.Agent()`를 만들면 기본값이 `keepAlive: false`입니다. 로컬에서 두 값을 직접 출력해 확인했습니다.
- 요청별로 `agent` 옵션에 지정합니다. `agent: false`는 그 요청 한 번만 쓰는 새 Agent를 만들어 재사용을 하지 않습니다.
- 서버가 연결을 닫으면 그 소켓은 풀에서 빠지고 다음 요청이 새 연결을 맺습니다.
- Agent는 모듈 수준에서 하나 만들어 공유합니다. 요청마다 `new http.Agent({ keepAlive: true })`를 만들면 풀이 공유되지 않아 연결이 쌓입니다.
- 현재 상태는 `agent.sockets`(사용 중), `agent.freeSockets`(유휴), `agent.requests`(대기)로 볼 수 있습니다.
- 응답 본문을 소비하지 않으면(`'data'` 리스너, `read()`, `res.resume()`) `'end'`가 오지 않아 소켓이 풀로 돌아가지 못합니다. 필요 없는 응답도 `res.resume()`으로 버립니다.
- 다 쓴 Agent는 `agent.destroy()`로 정리합니다. 풀의 유휴 소켓은 `unref`되어 프로세스 종료를 막지는 않지만 OS 자원을 차지합니다.
- 유휴 소켓을 재사용하려는 순간 서버가 막 닫았다면 `ECONNRESET`이 날 수 있습니다. `req.reusedSocket`이 `true`일 때만 안전하게 다시 시도합니다(멱등한 요청에 한해서).
- 전역 `fetch`는 `http.Agent`를 쓰지 않고 undici의 자체 연결 풀을 씁니다(자세히는 07편).

## 서버에서 나가는 요청

서버 코드가 다른 서버(외부 API, 내부 서비스)에 요청하는 것도 흔합니다. 이때 서버는 클라이언트 역할을 합니다. `http.request()`는 `ClientRequest`(쓰기 스트림)를 돌려주고 `http.get()`은 GET으로 `end()`까지 호출해 줍니다. 응답은 `'response'` 이벤트의 `IncomingMessage`로 옵니다.

```js
function getJson(options) {
  return new Promise((resolve, reject) => {
    const req = http.get(options, (res) => {
      const chunks = []
      res.on('data', (c) => chunks.push(c))
      res.on('error', reject)
      res.on('end', () => resolve({
        status: res.statusCode,
        body: Buffer.concat(chunks).toString(),
      }))
    })
    req.on('error', reject)
  })
}
```

핸들러에서 쓸 때는 업스트림 실패를 게이트웨이 오류로 바꿔 응답합니다.

```js
const signal = AbortSignal.timeout(2000)
try {
  const opts = { host, port, path, agent, signal }
  const up = await getJson(opts)
  res.writeHead(up.status)
  res.end(up.body)
} catch (err) {
  const timeout = err.cause?.name === 'TimeoutError'
  res.writeHead(timeout ? 504 : 502)
  res.end()
}
```

실행 결과, 정상 경로는 200, 업스트림이 2초 안에 답하지 않으면 504, 업스트림이 꺼져 연결이 거부되면 502였습니다.

| 상태 | 의미 |
|------|------|
| 502 Bad Gateway | 게이트웨이 역할의 서버가 업스트림에서 유효한 응답을 받지 못함 |
| 504 Gateway Timeout | 업스트림이 제때 응답하지 않음 |

- `'error'` 리스너를 반드시 답니다. DNS, TCP, 파싱 오류가 모두 `req`의 `'error'`로 오고, 리스너가 없으면 예외로 던져져 프로세스가 죽을 수 있습니다.
- `http.request()`를 쓰면 `req.end()`를 직접 호출해야 합니다. 본문이 없어도 마찬가지입니다.
- 응답을 끝까지 소비하거나 `res.resume()`, 요청을 `req.destroy()`해야 연결이 풀로 돌아갑니다.
- 클라이언트가 먼저 끊었는데 업스트림 요청이 계속되면 자원이 낭비됩니다. 들어온 응답 객체의 `'close'`에서 업스트림 요청을 중단하게 연결합니다.
- 연결 거부(`ECONNREFUSED`)와 타임아웃 같은 소켓 오류 코드는 19편에서 다룹니다.
- 같은 일을 더 짧게 쓰려면 `fetch`를 씁니다(자세히는 07편).

## 클라이언트 타임아웃

나가는 요청에는 기본 타임아웃이 없어서 상대가 응답하지 않으면 무한정 기다립니다. 타임아웃을 거는 방법은 세 가지이고 동작이 서로 다릅니다.

| 방법 | 재는 대상 | 만료 시 |
|------|-----------|---------|
| `timeout` 옵션, `req.setTimeout(ms)` | 소켓의 유휴 시간 | `'timeout'` 이벤트만 발생, 요청은 계속됨 |
| Agent의 `timeout` | 소켓의 유휴 시간 | 같음 (`globalAgent`는 5초) |
| `signal: AbortSignal.timeout(ms)` | 그 시간까지 끝나지 않은 요청 전체 | 요청이 파괴되고 `'error'` 발생 |

```js
// 1) 'timeout' 이벤트에서 직접 끊기
const req = http.get({ ...opts, timeout: 2000 })
req.on('timeout', () => req.destroy(new Error('timeout')))
req.on('error', onError)

// 2) AbortSignal로 전체 시간 제한
http.get({ ...opts, signal: AbortSignal.timeout(2000) })
  .on('error', (err) => {
    err.name       // 'AbortError'
    err.code       // 'ABORT_ERR'
    err.cause.name // 'TimeoutError'
  })
```

- `timeout` 옵션만 주면 `'timeout'` 이벤트가 나올 뿐 요청을 끊지 않습니다. 문서도 이 점을 밝힙니다. 응답에 600ms가 걸리는 서버에 `timeout: 200`을 주었을 때 이벤트는 발생했지만 응답은 그대로 도착했습니다.
- 같은 이유로 `globalAgent`의 5초 타임아웃도 요청을 끊지 않습니다. 6.5초 뒤에 답하는 서버에 기본 Agent로 요청했더니 5초에 `'timeout'`이 났고 응답은 6.5초에 도착했습니다.
- `AbortSignal.timeout()`은 시간이 되면 요청이 어느 단계(연결, 응답 대기, 본문 수신)에 있든 파괴합니다. 그래서 요청 단위 마감 시간에는 이 방법이 맞습니다. 에러의 `name`이 아니라 `cause.name`이 `TimeoutError`입니다.
- 전역 `fetch`도 같은 `AbortSignal.timeout()`을 씁니다. 이 경우 `TimeoutError`가 바로 던져집니다. undici 문서의 기본값은 헤더 대기와 본문 청크 간격이 각각 300초, 연결이 10초라서 사실상 마감 시간을 직접 걸어야 합니다(자세히는 07편).
- 재시도할 때는 멱등한 요청에만 하고 마감 시간을 전체 한도 안에 둡니다. 재시도가 각자 새 타임아웃을 받으면 전체 시간이 늘어납니다.

## keepAliveTimeout과 로드 밸런서 idle timeout

서버의 `keepAliveTimeout`은 앞단 로드 밸런서(LB)의 idle timeout보다 길어야 합니다. 연결을 먼저 닫는 쪽이 서버이면, LB는 이미 닫힌 연결을 재사용하려다 오류를 냅니다.

| 구성 | idle 한도 | 결과 |
|------|-----------|------|
| AWS ALB(기본) | 60초 | LB가 60초 동안 연결을 열어 둠 |
| Node 기본 서버 | 5초(+버퍼 1초) | 서버가 먼저 연결을 닫음 |
| 문제 | | LB가 닫힌 연결로 요청을 보내 502 Bad Gateway |

- AWS 문서는 ALB의 idle timeout 기본값이 60초이고, 애플리케이션의 idle timeout을 LB 값보다 크게 설정하라고 안내합니다. 그렇지 않으면 애플리케이션이 연결을 비정상적으로 닫은 뒤 LB가 요청을 보내 502를 반환할 수 있습니다.
- 그래서 LB가 60초이면 Node는 그보다 큰 값을 씁니다. 흔히 65초를 씁니다.

```js
const server = http.createServer({
  keepAliveTimeout: 65_000,
  requestTimeout: 300_000,
}, handler)
```

- 이 기본값 불일치를 줄이려고 Node main 브랜치에서는 `keepAliveTimeout` 기본값을 65초로 올리는 변경이 문서에 기록되어 있습니다. 릴리스에 반영되기 전까지는 직접 지정해야 합니다.
- 반대 방향(Node가 클라이언트)에서는 상대 서버의 keep-alive 시간이 더 짧을 수 있습니다. Agent는 서버가 알린 `Keep-Alive: timeout=...`에서 `agentKeepAliveTimeoutBuffer`를 뺀 시간 안에 소켓을 닫아 이 엇갈림을 줄입니다.
- 프록시와 LB 제품마다 기본값과 이름이 다릅니다. 앞단 구성의 문서에서 값을 확인한 뒤 서버 값을 정합니다.
- 배포 중 연결을 정리하는 `server.close()`와 `closeIdleConnections()`는 25편에서 다룹니다.

## 핵심 정리

- 서버 타임아웃은 넷입니다. `timeout`은 소켓 유휴, `headersTimeout`은 헤더 수신, `requestTimeout`은 요청 전체 수신, `keepAliveTimeout`은 응답 뒤 대기를 지킵니다.
- `headersTimeout`과 `requestTimeout`이 만료되면 408로 끊고, `headersTimeout`은 `requestTimeout` 이하여야 합니다. 핸들러 처리 시간은 어느 것으로도 제한되지 않습니다.
- `keepAliveTimeout` 기본은 Node 24에서 5초이고, 값은 코드에서 명시합니다.
- `http.Agent`는 연결을 재사용하는 풀입니다. 하나를 공유하고, 응답을 소비하고, 다 쓰면 `destroy()`합니다.
- 나가는 요청의 `timeout`은 이벤트만 일으킵니다. 마감 시간은 `AbortSignal.timeout()`으로 걸고 실패는 502나 504로 바꿉니다.
- `keepAliveTimeout`은 LB의 idle timeout보다 크게 잡아 502를 피합니다.

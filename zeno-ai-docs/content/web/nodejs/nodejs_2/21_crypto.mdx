## crypto 모듈

`node:crypto`는 해시, HMAC, 암호화·복호화, 서명·검증, 키 파생, 난수 생성을 제공하는 모듈입니다. OpenSSL의 함수를 감싸는 형태이고 안정성 지수는 2(Stable)입니다.

```js
import { createHash, randomBytes } from 'node:crypto'
```

- 쓸 수 있는 알고리즘 이름은 Node가 연결한 OpenSSL의 버전과 설정에 따라 달라집니다. `crypto.getHashes()`로 해시 목록을 확인합니다.
- 암호는 직접 고안하지 않습니다. 검증된 알고리즘을 정해진 방식대로 조합하는 것이 원칙입니다.
- 많은 API가 문자열 입력을 받지만, 키·IV·솔트처럼 바이트열이어야 하는 값은 `Buffer`로 만들어 넘깁니다. 임의 바이트열은 유효한 UTF-8 문자열이 아니라서 문자열로 바꾸면 엔트로피가 줄고 값이 변할 수 있습니다.

## 해시

해시(hash)는 임의 길이의 입력을 고정 길이의 값(다이제스트)으로 바꾸는 단방향 함수입니다. 성질은 다음과 같습니다.

- 같은 입력은 항상 같은 출력을 냅니다.
- 입력이 한 비트만 달라도 출력은 전혀 달라집니다.
- 출력에서 입력을 되돌릴 수 없습니다.
- 출력 길이는 입력 길이와 무관합니다. SHA-256은 항상 32바이트입니다.

해시는 암호화가 아닙니다. 되돌릴 키가 없고, 무결성 확인(파일이 변조되지 않았는지)이나 식별자 만들기에 씁니다. 해시에는 비밀 키가 없으므로 공격자도 같은 값을 만들 수 있습니다(인증이 필요하면 HMAC, 아래).

## createHash

`createHash(algorithm)`는 `Hash` 객체를 만듭니다. `update()`로 데이터를 넣고 `digest()`로 결과를 꺼냅니다.

```js
import { createHash } from 'node:crypto'

const h = createHash('sha256')
h.update('hel')
h.update('lo')               // 여러 번 이어 넣을 수 있음
h.digest('hex')
// '2cf24dba5fb0a3...2938b9824' (64자)
```

- `update()`는 문자열을 기본 UTF-8로 인코딩합니다. 다른 인코딩이면 `Buffer`로 바꿔 넘깁니다.
- `Hash`는 스트림이기도 해서 파일을 `pipe`로 흘려 보낼 수 있습니다. 큰 파일을 메모리에 올리지 않고 해시할 때 씁니다(스트림은 1편).
- `digest()`는 한 번만 호출할 수 있습니다. 두 번째 호출은 `ERR_CRYPTO_HASH_FINALIZED` 에러입니다. 중간 값이 필요하면 `hash.copy()`로 내부 상태를 복제한 뒤 복제본에서 꺼냅니다.

```js
import { hash } from 'node:crypto'

hash('sha256', 'hello')   // hex 문자열이 바로 반환됨
hash('sha256', 'hello', 'base64')
```

`crypto.hash(algorithm, data[, options])`는 한 번에 계산하는 함수입니다. v21.7.0에서 추가되었고 v24.13.1부터 실험 단계를 벗어났습니다. 공식 문서는 5MB 이하 데이터는 `createHash`보다 빠를 수 있고, 크거나 스트림으로 들어오는 데이터에는 `createHash`를 쓰라고 안내합니다. 반환 인코딩의 기본값은 `'hex'`입니다.

## sha256

SHA-256은 SHA-2 계열의 해시로 출력이 256비트(32바이트)입니다. 무결성 확인과 서명에 널리 쓰입니다.

| 알고리즘 | 출력 길이 | 용도 |
|----------|-----------|------|
| `sha256` | 32바이트 | 기본 선택 |
| `sha512` | 64바이트 | 더 긴 출력이 필요할 때 |
| `sha1`, `md5` | 20, 16바이트 | 충돌 공격이 알려져 보안 용도로 쓰지 않음 |

- `md5`와 `sha1`은 체크섬이나 레거시 호환에만 쓰고 서명·인증에는 쓰지 않습니다.
- 알고리즘 이름은 문자열이라 오타가 나면 런타임에 에러가 납니다.

## hex digest

`digest()`에 인코딩을 주면 문자열을, 생략하면 `Buffer`를 돌려줍니다.

```js
const h = () => createHash('sha256').update('hello')

h().digest().length         // 32 (Buffer)
h().digest('hex').length    // 64 (16진수 문자열)
h().digest('base64')        // 'LPJNul+wow4m...pOLmCQ='
h().digest('base64url')     // URL에 넣을 수 있는 변형
```

- hex는 바이트 하나가 문자 두 개라서 길이가 2배(64자)입니다. 가장 읽기 쉽고 로그·파일 체크섬 표기에 많이 씁니다.
- base64는 33퍼센트 정도만 늘어나서 더 짧습니다. 헤더·토큰에 넣을 때는 `+`, `/`, `=`가 없는 base64url을 씁니다.
- 두 다이제스트를 비교할 때는 같은 인코딩으로 맞춥니다. 비밀과 관련된 값은 `===` 대신 `timingSafeEqual`로 비교합니다(아래 "타이밍 공격").

## hmac

HMAC(Hash-based Message Authentication Code)은 비밀 키를 섞은 해시입니다. 키를 아는 쪽만 같은 값을 만들 수 있어서 메시지의 변조 여부와 키 소유 여부를 함께 확인합니다.

```js
import { createHmac } from 'node:crypto'

const mac = createHmac('sha256', 'secret-key')
  .update('payload')
  .digest('hex')
// 키가 다르면 전혀 다른 값
```

| 구분 | 일반 해시 | HMAC |
|------|-----------|------|
| 비밀 키 | 없음 | 있음 |
| 확인하는 것 | 내용이 같은지 | 내용이 같고 키를 가진 쪽이 만들었는지 |
| 쓰임 | 체크섬, 중복 판별 | 웹훅 서명 검증, 쿠키·토큰 서명 |

- 웹훅이 오면 받은 본문으로 HMAC을 다시 계산해 헤더의 서명과 비교합니다. 이때 본문은 파싱하기 전의 원본 바이트여야 합니다. JSON을 다시 직렬화하면 값이 달라집니다.
- 키는 `randomBytes(32)` 같은 난수로 만든 값을 씁니다. 짧거나 추측 가능한 문자열을 키로 쓰지 않습니다.
- `Hmac`도 `digest()`를 한 번만 호출할 수 있습니다.
- 계산한 값과 받은 값의 비교는 반드시 `timingSafeEqual`로 합니다.

## randomBytes

`randomBytes(size)`는 암호학적으로 안전한 난수 바이트를 `Buffer`로 돌려줍니다. 토큰, 솔트, IV, 키를 만들 때 씁니다.

```js
import { randomBytes } from 'node:crypto'

const token = randomBytes(32).toString('hex')
// 64자 16진수 문자열 (256비트)
const id = randomBytes(16).toString('base64url')
// 22자 (128비트)
```

- 콜백을 주면 비동기로 생성하고, 콜백 없이 호출하면 `Buffer`를 바로 반환합니다.
- 길이는 바이트 단위입니다. 세션 ID나 토큰은 128비트(16바이트) 이상으로 만듭니다.

**흔한 실수:** 보안 값에 `Math.random()`을 쓰는 것입니다. `Math.random()`은 예측 가능한 난수라서 토큰, 비밀번호 재설정 코드, 세션 ID에 쓰면 안 됩니다. 시간(`Date.now()`)을 섞어도 안전해지지 않습니다.

## randomUUID

`randomUUID()`는 RFC 4122 버전 4 UUID 문자열을 만듭니다. 난수는 암호학적 난수 생성기에서 옵니다.

```js
import { randomUUID } from 'node:crypto'

randomUUID()
// '3b241101-e2bb-4255-8caf-4136c566a962' (36자)
```

- 성능을 위해 UUID 128개를 만들 분량의 난수를 캐시합니다. `{ disableEntropyCache: true }`를 주면 캐시를 쓰지 않습니다.
- 값이 무작위라서 DB의 기본 키로 쓰면 삽입 위치가 흩어집니다. 시간순 정렬이 필요하면 UUID v7이 대안이며, `crypto.randomUUIDv7()`이 v26.1.0과 v24.16.0에 추가되었습니다. 그보다 낮은 24.x에는 없습니다. v7의 시간 부분은 비단조 시계에 의존하므로 엄격하게 증가한다고 보장되지 않습니다.
- UUID는 식별자이지 비밀이 아닙니다. 추측이 어렵다는 점에 기대 접근 제어를 대신하지 않습니다.

## randomInt

`randomInt([min,] max)`는 `min <= n < max` 범위의 암호학적으로 안전한 난수 정수를 돌려줍니다. 기본 `min`은 0입니다.

```js
import { randomInt } from 'node:crypto'

randomInt(6)          // 0–5
randomInt(1, 7)       // 1–6 (주사위)
const code = String(randomInt(0, 1_000_000))
  .padStart(6, '0')   // 인증 번호 6자리
```

- 모듈로 편향(modulo bias)을 피하도록 구현되어 있습니다. `randomBytes` 값에 `%`를 해서 범위를 줄이면 앞쪽 값이 더 자주 나오는 편향이 생깁니다.
- `max`는 미포함입니다. 범위(`max - min`)는 2의 48제곱보다 작아야 하고 두 값은 안전한 정수여야 합니다.
- 콜백을 주면 비동기, 생략하면 동기입니다.

## 전역 crypto와 node:crypto

전역 `crypto`는 Node 모듈이 아니라 Web Crypto API의 구현입니다. `node:crypto`와는 다른 객체입니다. 전역 `crypto`는 `node:crypto`의 `webcrypto`와 같은 객체입니다.

```js
import { webcrypto } from 'node:crypto'

globalThis.crypto === webcrypto   // true
crypto.randomUUID()               // 전역에서 바로 사용
crypto.getRandomValues(new Uint8Array(8))
await crypto.subtle.digest('SHA-256', data)
```

| 구분 | `node:crypto` | 전역 `crypto` |
|------|---------------|---------------|
| 정체 | Node 전용 모듈 | Web Crypto API |
| 가져오기 | `import` 필요 | 불필요 |
| 해시 | `createHash` (동기, 스트림) | `crypto.subtle.digest` (Promise) |
| 이식성 | Node 중심 | 브라우저·Deno·Bun과 공통 |

- 전역 `crypto`는 v19.0.0부터 플래그 없이 쓸 수 있고 v23.0.0부터 실험 단계가 아닙니다.
- 브라우저와 공유할 코드는 전역 `crypto`(Web Crypto)로, Node 서버 코드는 `node:crypto`로 씁니다. `createHash`, `scrypt`, `timingSafeEqual`은 `node:crypto`에만 있습니다.
- `import crypto from 'node:crypto'`로 가져오면 그 모듈 객체가 전역 `crypto`를 가립니다. 어느 쪽을 쓰는지 헷갈리지 않게 이름을 구분합니다.

## 타이밍 공격

타이밍 공격(timing attack)은 비교에 걸리는 시간 차이로 비밀 값을 알아내는 공격입니다. `===`나 `Buffer.compare`는 처음 다른 바이트에서 비교를 멈춰서, 앞쪽이 많이 맞을수록 응답이 아주 조금 늦어집니다. 공격자는 응답 시간을 반복 측정해 한 글자씩 추측합니다.

```js
// ❌ 처음 다른 지점에서 끝남
if (receivedSignature === expectedSignature) { /* ... */ }
```

- 대상은 HMAC 서명, API 키, 세션·재설정 토큰처럼 공격자가 추측하는 비밀 값과의 비교입니다.
- 네트워크 지연이 크면 어려워 보이지만 반복 측정으로 통계적으로 걸러낼 수 있어서 비교는 일정 시간으로 해야 합니다.
- 비밀이 아닌 값(공개 ID 비교 등)에는 필요 없습니다.

## timingSafeEqual

`crypto.timingSafeEqual(a, b)`는 두 값의 바이트를 걸리는 시간이 같게 비교해 `boolean`을 돌려줍니다. 입력은 `Buffer`, `TypedArray`, `DataView`, `ArrayBuffer`입니다.

```js
import { createHmac, timingSafeEqual } from 'node:crypto'

function verify(body, signatureHex, key) {
  const expected = createHmac('sha256', key)
    .update(body)
    .digest()
  const received = Buffer.from(signatureHex, 'hex')
  if (received.length !== expected.length) return false
  return timingSafeEqual(received, expected)
}
```

- 두 입력의 바이트 길이가 다르면 `false`가 아니라 `ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH` 에러가 납니다. 길이를 먼저 확인합니다. 길이 비교로 드러나는 정보는 다이제스트 길이처럼 공개된 값이어야 합니다.
- 문자열이 아니라 `Buffer`로 바꿔서 넣습니다. 서로 인코딩이 다른 문자열을 그대로 `Buffer.from`하면 길이가 어긋납니다.
- 공식 문서는 이 함수를 써도 주변 코드가 타이밍에 안전해지지는 않는다고 경고합니다. 값에 따라 분기하거나 조기 `return`하는 코드를 비교 앞뒤에 두지 않습니다.

## 비밀번호를 일반 해시만으로 저장하면 안 되는 이유

SHA-256 같은 일반 해시는 빠르게 계산하도록 설계되었기 때문에 비밀번호 저장에 쓰면 안 됩니다. DB가 유출되었을 때 공격자가 초당 수십억 번 추측을 시도할 수 있습니다.

| 문제 | 설명 |
|------|------|
| 너무 빠름 | 짧은 비밀번호는 모든 후보를 대입해 금방 찾음 |
| 같은 입력은 같은 출력 | 해시를 미리 계산한 표(레인보 테이블)와 대조하면 즉시 복원 |
| 같은 비밀번호는 같은 해시 | 두 사용자의 비밀번호가 같은지 DB만 봐도 드러남 |

해결책은 두 가지입니다.

- **솔트(salt)**: 사용자마다 다른 난수를 비밀번호에 섞어 같은 비밀번호도 다른 해시가 나오게 합니다. 솔트는 비밀이 아니라서 해시와 함께 저장합니다.
- **느린 키 파생 함수**: 일부러 계산 시간과 메모리를 많이 쓰게 만든 함수(scrypt, pbkdf2, argon2, bcrypt)를 씁니다. 추측 한 번의 비용이 커집니다.

`sha256(password)`도, `sha256(password + 고정 문자열)`도 안 됩니다. 솔트는 사용자마다 달라야 합니다. 서비스 전체의 인증 구조는 10편에서 다룹니다.

## scrypt와 pbkdf2

`scrypt`와 `pbkdf2`는 `node:crypto`에 내장된 비밀번호 기반 키 파생 함수(KDF)입니다. 비밀번호와 솔트에서 지정한 길이의 키를 뽑고, 그 키를 비밀번호 해시로 저장합니다.

| 항목 | scrypt | pbkdf2 |
|------|--------|--------|
| 부담 | CPU와 메모리 | CPU만 |
| 조절 값 | `cost`(N), `blockSize`(r), `parallelization`(p) | `iterations`, `digest` |
| 기본값 | N 16384, r 8, p 1 | 기본값 없음. 모두 직접 지정 |
| 하드웨어 병렬 공격 | 메모리 부담이 있어 불리 | 상대적으로 쉬움 |
| 추가 | v10.5.0 | v0.5.5 |

```js
import {
  scrypt, randomBytes, timingSafeEqual,
} from 'node:crypto'
import { promisify } from 'node:util'

const scryptAsync = promisify(scrypt)

async function hashPassword(pw) {
  const salt = randomBytes(16)
  const key = await scryptAsync(pw, salt, 64)
  return `${salt.toString('hex')}:${key.toString('hex')}`
}
```

저장한 문자열에서 솔트를 꺼내 같은 방식으로 다시 계산한 뒤 `timingSafeEqual`로 비교합니다.

```js
async function verifyPassword(pw, stored) {
  const [salt, key] = stored.split(':')
  const saltBuf = Buffer.from(salt, 'hex')
  const test = await scryptAsync(pw, saltBuf, 64)
  return timingSafeEqual(test, Buffer.from(key, 'hex'))
}
// verifyPassword('pw1', stored) true, 다른 값은 false
```

- 공식 문서는 솔트를 가능한 한 고유하게 하고 16바이트 이상의 난수로 만들라고 권합니다.
- `pbkdf2`의 `iterations`는 "가능한 한 높게" 잡으라는 것이 공식 문서의 안내입니다. OWASP는 PBKDF2-HMAC-SHA256에 600,000회를 권장하고 scrypt는 N 2의 17제곱, r 8, p 1을 권장합니다. 권장 값은 바뀌므로 도입 시점의 OWASP 비밀번호 저장 치트시트를 확인합니다.
- scrypt는 메모리가 약 `128 * N * r`바이트 필요합니다. 기본 `maxmem`은 32MiB라서 N을 2의 17제곱으로 올리면 `maxmem`을 함께 올리지 않으면 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS` 에러가 납니다.
- 콜백 버전과 `Sync` 버전이 있습니다. 콜백(비동기) 버전은 libuv 스레드 풀에서 실행되고, `Sync` 버전은 이벤트 루프를 막으므로 요청 처리 중에는 비동기를 씁니다. 풀 크기는 기본 4개라서 로그인 요청이 몰리면 다른 풀 작업(파일, DNS)까지 늦어질 수 있습니다.
- Node.js는 v24.7.0에 `crypto.argon2()`와 `argon2Sync()`를 추가했습니다. 변형은 `argon2d`, `argon2i`, `argon2id` 중 하나이고 OWASP의 1순위 권장은 `argon2id`입니다(최소 설정 m 19456, t 2, p 1). 이 값은 `memory`(KiB), `passes`, `parallelism` 매개변수에 대응합니다. `nonce`(솔트)는 8바이트 이상 필수이고 16바이트 이상의 난수를 권장합니다. 라이브러리 선택은 10편에서 다룹니다.
- 저장 형식에 알고리즘과 파라미터를 함께 적어 두면 나중에 비용을 올릴 때 구 해시를 구분할 수 있습니다.

## 대칭 암호 AES-GCM

대칭 암호는 암호화와 복호화에 같은 키를 쓰는 방식입니다. 해시와 달리 복호화로 원문을 되돌립니다. AES-GCM은 암호화와 함께 변조 감지용 인증 태그(authentication tag)를 만드는 AEAD 방식이라, 널리 쓰입니다.

```js
import { createCipheriv, randomBytes } from 'node:crypto'

const key = randomBytes(32)   // AES-256 키, 비밀로 보관
const iv = randomBytes(12)    // 매번 새로, 암호문과 함께 저장
const c = createCipheriv('aes-256-gcm', key, iv)
const enc = Buffer.concat([
  c.update('secret', 'utf8'),
  c.final(),
])
const tag = c.getAuthTag()    // 16바이트, final() 뒤에 호출
```

복호화는 `createDecipheriv`로 같은 키·IV를 주고, `update()` 전에 `setAuthTag()`로 태그를 넣습니다.

```js
import { createDecipheriv } from 'node:crypto'

const d = createDecipheriv('aes-256-gcm', key, iv)
d.setAuthTag(tag)
const plain = Buffer.concat([d.update(enc), d.final()])
// plain.toString() === 'secret'
// 암호문이 한 비트라도 바뀌면 final()이 에러:
// 'Unsupported state or unable to authenticate data'
```

- 키는 AES-256이면 32바이트 난수입니다. 비밀번호에서 키를 얻으려면 scrypt 같은 KDF로 파생합니다.
- IV(초기화 벡터)는 비밀일 필요는 없지만 예측 불가능하고 같은 키로 재사용하지 않아야 합니다. 공식 문서도 IV는 고유하고 예측 불가능하게, 가급적 난수로 만들고 암호문 메시지에 평문으로 붙여 두라고 안내합니다. 이 편의 예제는 12바이트를 씁니다.
- 같은 키와 IV로 두 메시지를 암호화하면 GCM의 보안이 깨집니다. IV는 메시지마다 새로 만듭니다.
- 복호화 쪽은 인증에 실패하면 결과를 쓰지 않아야 합니다. `final()`에서 던져지는 에러를 잡아 요청을 거부합니다.
- 태그 길이 16바이트가 아닌 값을 쓸 때는 `createDecipheriv`에 `authTagLength`를 명시합니다. 명시하지 않으면 짧은 태그가 허용되어 위조가 쉬워지고, 이 동작은 v22.0.0과 v20.13.0에서 사용 중단 예정으로 표시되었습니다.
- 저장 형식은 보통 IV, 암호문, 태그를 이어 붙인 값입니다. 길이가 고정이라 잘라 쓸 수 있습니다.
- 암호화가 있다고 인증·인가가 생기는 것은 아닙니다. 키 관리(환경 변수, 비밀 관리 서비스)가 안전성의 대부분을 결정합니다.

## 서명과 검증

디지털 서명은 개인 키로 서명하고 공개 키로 검증하는 비대칭 방식입니다. 공개 키는 누구에게나 배포할 수 있고 개인 키는 서명하는 쪽만 가집니다. HMAC과 달리 검증하는 쪽이 서명을 위조할 수 없습니다.

```js
import {
  generateKeyPairSync, sign, verify,
} from 'node:crypto'

const { publicKey, privateKey } =
  generateKeyPairSync('ed25519')
const data = Buffer.from('msg')
const sig = sign(null, data, privateKey)      // 64바이트
verify(null, data, publicKey, sig)            // true
verify(null, Buffer.from('msx'), publicKey, sig) // false
```

- `sign(algorithm, data, key)`와 `verify(algorithm, data, key, signature)`는 v12.0.0에 추가되었습니다. 콜백을 주면 스레드 풀에서 비동기로 실행됩니다.
- Ed25519에서는 `algorithm`을 `null`이나 `undefined`로 줍니다. RSA는 `'sha256'`처럼 해시 이름을 줍니다.
- 공개 키는 개인 키에서 유도할 수 있어서 `verify`의 `key`에는 개인 키를 줘도 됩니다. 검증하는 쪽에는 공개 키만 배포합니다.
- 키는 PEM 문자열이나 `KeyObject`로 다룹니다. `generateKeyPairSync`에 `publicKeyEncoding`, `privateKeyEncoding`을 주면 PEM 문자열로 내보낼 수 있고, 개인 키는 파일이나 비밀 관리 서비스에 보관합니다.
- 변조된 데이터이거나 다른 키이면 `verify`는 에러가 아니라 `false`를 돌려줍니다.
- JWT의 RS256, ES256, EdDSA 서명이 이 방식입니다. 공개 키를 가진 여러 서비스가 토큰을 검증하고 발급은 한 곳만 하는 구조에 씁니다(자세히는 10편).

| 구분 | HMAC | 서명 |
|------|------|------|
| 키 | 공유 비밀 키 하나 | 개인 키와 공개 키 쌍 |
| 검증하는 쪽이 위조 가능한가 | 가능 | 불가능 |
| 속도 | 빠름 | 느림 |
| 쓰임 | 한 서비스 안, 웹훅 | 서로 다른 조직·서비스 간 |

## 핵심 정리

- 해시는 단방향 고정 길이 값이고 `createHash(알고리즘).update().digest(인코딩)`으로 만들며 `digest()`는 한 번만 호출됩니다. 소량 데이터는 `crypto.hash()`로 한 번에 계산합니다.
- 변조와 키 소유까지 확인하려면 HMAC을 쓰고, 계산한 값은 `timingSafeEqual`(같은 길이의 `Buffer`)로 비교합니다.
- 보안 값은 `randomBytes`, `randomUUID`, `randomInt`로 만들고 `Math.random()`은 쓰지 않습니다.
- 비밀번호는 일반 해시가 아니라 사용자별 솔트와 느린 KDF(scrypt, pbkdf2, argon2)로 저장하며 비동기 버전을 씁니다.
- AES-GCM은 암호화와 변조 감지를 함께 하고 IV는 메시지마다 새 난수로, 태그는 복호화 전에 `setAuthTag()`로 넣습니다.
- 서명은 개인 키로 만들고 공개 키로 검증합니다. 전역 `crypto`는 Web Crypto API이고 `node:crypto`와 다른 객체입니다.

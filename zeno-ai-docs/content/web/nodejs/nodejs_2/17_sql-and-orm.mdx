## 드라이버와 파라미터 바인딩

드라이버는 DB 서버의 네트워크 프로토콜로 SQL을 보내고 결과를 JavaScript 값으로 바꾸는 라이브러리입니다(개념은 16편). PostgreSQL은 `pg`(node-postgres), MySQL은 `mysql2`가 표준입니다. 두 라이브러리 모두 Promise를 지원합니다.

```js
import pg from 'pg'
const url = process.env.DATABASE_URL
const pool = new pg.Pool({ connectionString: url })

const sql = 'SELECT id, name FROM users WHERE email = $1'
const { rows } = await pool.query(sql, ['kim@example.com'])
console.log(rows) // [{ id: 1, name: 'Kim' }]
```

```js
import mysql from 'mysql2/promise'
const pool = mysql.createPool(process.env.DATABASE_URL)

const sql = 'SELECT id, name FROM users WHERE email = ?'
const [rows] = await pool.execute(sql, ['kim@example.com'])
```

| 항목 | pg | mysql2 |
|------|----|--------|
| 자리표시자 | `$1`, `$2` (번호) | `?` (순서) |
| 결과 | `{ rows, rowCount, ... }` 객체 | `[rows, fields]` 배열 |
| 준비된 문장 | 값을 SQL과 따로 서버에 전달 | `execute()`가 prepared statement 사용, LRU 캐시 |

- **파라미터 바인딩**(parameter binding)은 SQL 문자열과 값을 분리해서 보내는 방식입니다. pg 문서는 쿼리 텍스트를 바꾸지 않고 값과 함께 서버에 넘겨, 서버 안의 치환 코드가 값을 안전하게 넣는다고 설명합니다. 값이 SQL 문법으로 해석되지 않아 SQL 인젝션이 막힙니다.
- 식별자(테이블명, 컬럼명)에는 바인딩을 쓸 수 없습니다. pg 문서는 PostgreSQL이 식별자 파라미터를 지원하지 않는다고 밝히고, 동적 식별자는 `pg-format` 같은 이스케이프 도구나 허용 목록 검사로 처리하라고 안내합니다.
- pg의 파라미터 쿼리는 문장 하나만 보냅니다. 여러 문장은 쿼리를 나눠 호출합니다.

```js
// ❌ 문자열 이어 붙이기: email이 "' OR 1=1 --" 이면 전체 조회
const bad = `SELECT * FROM users WHERE email = '${email}'`
await pool.query(bad)
// ✅ 바인딩
const ok = 'SELECT * FROM users WHERE email = $1'
await pool.query(ok, [email])
```

**흔한 실수:** `ORDER BY ${column}`처럼 정렬 컬럼을 요청값으로 직접 넣는 것입니다. 바인딩이 안 되는 자리이므로 `['name', 'created_at']` 같은 허용 목록과 대조한 뒤 넣습니다.

## 커넥션 풀 설정

풀은 DB 연결을 미리 열어 두고 빌려 주는 객체입니다. 요청마다 연결을 새로 맺으면 TCP·인증 비용이 매번 듭니다. 풀 크기는 DB 서버의 동시 연결 한도 안에서 정합니다.

| 옵션 | pg 기본값 | mysql2 기본값 |
|------|-----------|---------------|
| 최대 연결 수 | `max`: 10 | `connectionLimit`: 10 |
| 유휴 연결 정리 | `idleTimeoutMillis`: 10000 (0이면 끔) | `idleTimeout`: 60000 |
| 연결 대기 | `connectionTimeoutMillis`: 0 (무제한 대기) | `waitForConnections`: true, `queueLimit`: 0 (무제한) |

- 풀이 꽉 차면 요청은 연결이 반납될 때까지 줄을 섭니다. pg는 대기 제한이 기본으로 꺼져 있으므로 `connectionTimeoutMillis`를 설정해야 무한 대기가 에러가 됩니다.
- mysql2는 연결을 미리 다 열지 않고 상한까지 필요할 때 만듭니다.
- PostgreSQL의 `max_connections` 기본값은 100이고, 일부는 슈퍼유저용으로 예약됩니다. 풀 크기 × 서버 인스턴스 수가 이 한도를 넘으면 연결이 거부됩니다. 인스턴스를 늘릴 때 풀 크기도 함께 계산합니다.
- 풀이 클수록 빠른 것이 아닙니다. DB가 동시에 처리하는 일의 양이 정해져 있어서 연결이 많아도 대기만 DB 쪽으로 옮겨집니다.
- pg의 풀은 유휴 클라이언트가 백엔드 장애로 끊기면 풀의 `error` 이벤트로 에러를 내보냅니다. 리스너가 없으면 처리되지 않은 `error` 이벤트로 프로세스가 죽습니다.

```js
const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000,
})
pool.on('error', (err) => console.error('idle client', err))
await pool.end() // 종료 시 모든 연결을 닫는다 (자세히는 25편)
```

**흔한 실수:** `pool.connect()`로 받은 클라이언트를 `release()`하지 않는 것입니다. 반납하지 않은 연결이 쌓이면 풀이 비고 모든 요청이 대기합니다. `try`/`finally`에서 반납합니다. 단일 쿼리는 `pool.query()`가 빌림과 반납을 알아서 합니다.

## Prisma

Prisma는 스키마 파일 하나에서 타입이 붙은 클라이언트와 마이그레이션을 만드는 ORM입니다. ORM(Object-Relational Mapper)은 테이블을 코드의 모델로 다루게 해 주는 라이브러리입니다.

버전 상태를 먼저 확인해 둡니다(2026-10 기준).

| 계열 | 상태 | 특징 |
|------|------|------|
| Prisma ORM 7 | 7.10.0까지 안정 릴리스, 공식 문서가 계속 유지(`/orm/v7`) | `schema.prisma`, `prisma.config.ts`, 드라이버 어댑터 필수 |
| Prisma ORM 8 | 8.0.0 릴리스 후보(rc.20), 공식 문서의 기본 버전 | `contract.prisma`, 새 쿼리 API로 재설계 |

Prisma 8은 설정 파일, 쿼리 API, 마이그레이션 명령이 7과 다릅니다. 아래는 7 계열 기준이며, 8로 올릴 때는 공식 업그레이드 가이드를 따릅니다.

### 스키마

```prisma
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

```prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

model Post {
  id       Int  @id @default(autoincrement())
  author   User @relation(fields: [authorId],
                          references: [id])
  authorId Int
}
```

- Prisma 7에서 DB 접속 URL은 스키마가 아니라 프로젝트 루트의 `prisma.config.ts`에 둡니다.
- 생성기 `prisma-client`는 `output` 경로에 클라이언트 코드를 만듭니다. 스키마를 바꾸면 `prisma generate`를 다시 실행합니다.

```ts
// prisma.config.ts
import 'dotenv/config'
import { defineConfig } from 'prisma/config'

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations' },
  datasource: { url: process.env['DATABASE_URL'] },
})
```

### Client

Prisma 7부터 직접 DB에 연결하려면 드라이버 어댑터가 필수입니다. PostgreSQL은 `@prisma/adapter-pg`를 씁니다.

```ts
import { PrismaPg } from '@prisma/adapter-pg'
import { PrismaClient } from '../generated/prisma/client'

const adapter = new PrismaPg({ connectionString })
export const prisma = new PrismaClient({ adapter })

const user = await prisma.user.create({
  data: { email: 'kim@example.com', posts: { create: {} } },
  include: { posts: true },
})
```

- 쿼리 결과의 타입은 스키마에서 생성됩니다. `include`와 `select`에 따라 반환 타입이 달라집니다.
- `PrismaClient`는 프로세스에 하나만 만들어 공유합니다. 요청마다 만들면 연결이 불어납니다.

### 마이그레이션

| 명령 | 용도 |
|------|------|
| `prisma migrate dev` | 개발용. 변경분으로 마이그레이션 파일을 만들고 적용. 섀도 DB로 드리프트를 검사. 운영에서 쓰지 않음 |
| `prisma migrate deploy` | 운영·CI용. 아직 적용되지 않은 마이그레이션만 적용. 섀도 DB를 쓰지 않음 |
| `prisma migrate reset` | 개발 DB를 지우고 처음부터 다시 적용. 개발 전용 |

운영 마이그레이션은 `migrate deploy`만 씁니다(아래 "마이그레이션 운영").

버전 차이: 7은 타임스탬프가 붙은 SQL 마이그레이션 파일을 순서대로 쌓아 적용하는 방식입니다. 8(RC)은 선형 파일 체인 대신 상태에서 계획을 세우는 모델로 바뀌어, `prisma migration plan --name 이름`으로 계획하고 `prisma db migrate`로 적용하며, 운영에서는 `prisma migration check`와 `prisma db migrate --show`(미리보기)를 거칩니다. 8의 공식 문서도 CI와 운영에서는 계획을 만들지 않고 저장소에서 리뷰된 마이그레이션만 적용한다고 밝힙니다.

## TypeORM

TypeORM은 클래스와 데코레이터로 엔티티를 정의하는 ORM입니다. 최신 메이저는 1.0이고(npm `latest`는 1.1.1) Node.js 20.19 이상을 요구합니다. 0.3과 달라진 점이 많으므로 옛 글의 코드를 그대로 쓰지 않습니다.

| 0.3 | 1.0 |
|-----|-----|
| `Connection`, `createConnection` | `DataSource`, `dataSource.initialize()` |
| `getRepository()` 전역 함수 | `dataSource.getRepository()` |
| `relations: ['posts']` | `relations: { posts: true }` |
| `findOneById`, `findByIds` | `findOneBy`, `findBy`와 `In()` |
| where에 `null`·`undefined`는 조용히 무시 | 기본으로 에러 |

### 엔티티

```ts
import {
  Entity, PrimaryGeneratedColumn, Column,
} from 'typeorm'

@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number

  @Column({ unique: true })
  email: string
}
```

- 데코레이터를 쓰려면 `tsconfig.json`에서 `experimentalDecorators`와 `emitDecoratorMetadata`를 켭니다(TypeScript 4.5 이상).
- 연결은 `DataSource` 인스턴스가 담당합니다. 풀 크기는 `poolSize`로, 드라이버 고유 옵션은 `extra`로 넘깁니다.

```ts
const dataSource = new DataSource({
  type: 'postgres',
  url: process.env.DATABASE_URL,
  entities: [User],
  poolSize: 10,
  synchronize: false, // 운영에서는 항상 false
})
await dataSource.initialize()
```

### 리포지토리

```ts
const users = dataSource.getRepository(User)

await users.save({ email: 'kim@example.com' })
const one = await users.findOneBy({ email: 'a@b.c' })
const list = await users.find({
  where: { email: 'kim@example.com' },
  relations: { posts: true },
})
```

- `save()`는 기본키가 있으면 수정, 없으면 삽입합니다.
- 복잡한 쿼리는 `createQueryBuilder()`로 SQL에 가깝게 씁니다.
- `synchronize: true`는 앱이 시작할 때 스키마를 엔티티에 맞춥니다. 공식 문서는 데이터가 있는 운영 DB에서 안전하지 않다고 경고하므로 마이그레이션을 씁니다(아래 "마이그레이션 운영").

## Drizzle 개요

Drizzle은 SQL 문법과 비슷한 쿼리 빌더를 가진 TypeScript ORM입니다. 공식 문서는 스스로를 "머리가 달린 헤드리스 ORM"이라 소개하고, SQL을 알면 Drizzle도 안다는 점을 내세웁니다. 의존성이 없고 서버리스 환경을 염두에 둔 가벼운 라이브러리입니다.

```ts
import {
  integer, pgTable, varchar,
} from 'drizzle-orm/pg-core'
import { drizzle } from 'drizzle-orm/node-postgres'
import { eq } from 'drizzle-orm'

export const users = pgTable('users', {
  id: integer().primaryKey().generatedAlwaysAsIdentity(),
  email: varchar({ length: 255 }).notNull().unique(),
})

const db = drizzle(process.env.DATABASE_URL)
const rows = await db
  .select().from(users).where(eq(users.email, email))
```

- 스키마를 TypeScript 코드(`pgTable`)로 정의하고, `drizzle-kit generate`로 SQL 마이그레이션을 만들어 `drizzle-kit migrate`로 적용합니다. 개발 중 빠른 반영에는 `drizzle-kit push`가 있습니다.
- 쿼리가 SQL 구조(`select`, `from`, `where`)를 그대로 따르므로 어떤 SQL이 나가는지 예측하기 쉽습니다. 중첩 데이터는 관계형 쿼리 API로 한 번에 가져옵니다.
- 버전: npm의 `latest`는 0.45.3이고 1.0은 릴리스 후보(`rc` 태그)입니다. 공식 시작 가이드의 설치 명령은 `@rc` 태그를 씁니다. 1.0이 안정화되기 전에는 메이저 전환 가능성을 감안합니다.
- 연결은 pg 풀 등 드라이버가 맡으므로 풀 설정은 앞 절의 규칙이 그대로 적용됩니다.

## 트랜잭션과 격리 수준

트랜잭션은 여러 SQL을 전부 반영하거나 전부 취소하는 단위입니다(개념은 16편). 핵심 규칙은 한 트랜잭션의 모든 문장이 같은 연결에서 실행되어야 한다는 것입니다.

```js
const client = await pool.connect()
try {
  await client.query('BEGIN')
  await client.query(debit, [100, fromId])
  await client.query(credit, [100, toId])
  await client.query('COMMIT')
} catch (err) {
  await client.query('ROLLBACK')
  throw err
} finally {
  client.release()
}
```

- `pool.query()`로 `BEGIN`을 보내면 이후 문장은 다른 연결로 갈 수 있어서 트랜잭션이 되지 않습니다. pg 문서도 트랜잭션에는 `pool.connect()`로 받은 같은 클라이언트를 쓰라고 합니다.
- ORM은 콜백 형태로 감쌉니다. 콜백이 정상 반환하면 커밋하고 예외를 던지면 롤백합니다.

```ts
await prisma.$transaction(async (tx) => {
  await tx.account.update(debit)
  await tx.account.update(credit)
}, { isolationLevel: 'Serializable' })

await db.transaction(async (tx) => { /* Drizzle */ })
await dataSource.transaction(async (m) => { /* TypeORM */ })
```

- 콜백 안에서는 바깥의 `prisma`나 `db`가 아니라 `tx`로 쿼리해야 합니다. 바깥 객체로 보낸 쿼리는 트랜잭션 밖에서 실행되어 롤백되지 않습니다.
- Prisma 7의 대화형 트랜잭션은 `maxWait`(기본 2000ms)와 `timeout`(기본 5000ms) 옵션이 있고 시간이 지나면 롤백됩니다. 트랜잭션은 짧게 유지합니다. 안에서 외부 HTTP를 호출하면 연결을 오래 점유합니다.
- Prisma 8의 `db.transaction()`은 콜백만 받고 `isolationLevel`, `timeout`, `maxWait` 옵션이 없습니다.
- 배열 형태 `$transaction([...])`은 한 연결에서 순서대로 실행됩니다.

### 격리 수준

격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경을 얼마나 볼 수 있는지를 정합니다.

| 수준 | 읽는 방식 | PostgreSQL | MySQL(InnoDB) |
|------|-----------|-----------|---------------|
| READ UNCOMMITTED | 커밋 전 변경도 읽음 | READ COMMITTED처럼 동작 | 지원 |
| READ COMMITTED | 문장마다 새 스냅샷 | 기본값 | 지원 |
| REPEATABLE READ | 트랜잭션의 첫 읽기 스냅샷 유지 | 지원 | 기본값 |
| SERIALIZABLE | 순차 실행과 같은 결과 보장 | 지원 | 지원(일반 SELECT를 잠금 읽기로 바꿈) |

- READ COMMITTED에서는 같은 트랜잭션 안의 두 SELECT가 서로 다른 데이터를 볼 수 있습니다.
- PostgreSQL의 REPEATABLE READ와 SERIALIZABLE은 동시 변경 충돌 때 직렬화 실패(SQLSTATE `40001`)를 냅니다. 트랜잭션 전체를 처음부터 다시 시도해야 합니다.
- 격리 수준을 올리면 일관성은 강해지지만 충돌과 재시도가 늘어납니다. 기본값으로 충분한 곳이 대부분이고, 잔액 계산처럼 읽고 쓰는 로직은 `SELECT ... FOR UPDATE` 행 잠금이나 `UPDATE`의 증감식으로 푸는 편이 단순합니다.

**흔한 실수:** 두 DB의 기본 격리 수준이 다르다는 것을 모르고 코드를 옮기는 것입니다. PostgreSQL에서 통과한 동시성 테스트가 MySQL에서는 다르게 동작할 수 있습니다.

## N+1과 해결

N+1은 목록 쿼리 한 번(1)에 항목마다 연관 데이터 쿼리 한 번씩(N)이 붙는 패턴입니다. 항목이 100개면 쿼리가 101번 나갑니다. ORM에서는 연관 객체에 접근하는 순간 쿼리가 숨어서 나가기 때문에 코드만 봐서는 보이지 않습니다.

```js
const users = await prisma.user.findMany()
for (const u of users) {
  // ❌ 사용자마다 쿼리 한 번
  const where = { authorId: u.id }
  u.posts = await prisma.post.findMany({ where })
}
// ✅ 한 번에 가져오기
const withPosts = await prisma.user.findMany({
  include: { posts: true },
})
```

| ORM | 해결 방법 |
|-----|-----------|
| Prisma | `include`·`select`로 연관 데이터를 함께 요청. `relationLoadStrategy`는 기본 `join`(한 쿼리), `query`는 테이블별 쿼리를 보내 앱에서 합침 |
| TypeORM | `find`의 `relations` 옵션 또는 `leftJoinAndSelect`. 즉시 로딩(eager)은 `find*`에서만 동작하고 `relationLoadStrategy: 'query'`로 분리 가능 |
| Drizzle | 관계형 쿼리 API의 `with`, 또는 SQL `join` 직접 작성 |
| 드라이버 | `WHERE author_id = ANY($1)`로 ID 배열을 한 번에 조회한 뒤 코드에서 묶음 |

- Prisma의 fluent API(`prisma.user.findUnique(...).posts()`)는 쿼리를 둘로 나눕니다. 목록 안에서 반복하면 N+1이 됩니다.
- TypeORM의 지연 로딩(lazy)은 접근할 때마다 쿼리를 보내므로 반복문 안에서 N+1을 만듭니다.
- 찾는 방법은 쿼리 로그입니다. ORM의 로깅을 개발 환경에서 켜서 한 요청에 나가는 쿼리 수를 셉니다.
- 가져올 필요가 없는 컬럼과 관계까지 `include`하면 반대로 데이터가 불어납니다. 필요한 필드만 `select`합니다.

## 인덱스 기초

인덱스는 컬럼 값에서 행 위치를 빠르게 찾는 보조 자료구조입니다. 인덱스가 없으면 DB는 테이블 전체를 읽는 순차 스캔(Seq Scan)을 합니다. PostgreSQL의 기본 인덱스는 B-tree입니다.

```sql
CREATE INDEX idx_posts_author_id ON posts (author_id);
EXPLAIN ANALYZE
SELECT * FROM posts WHERE author_id = 7;
-- Index Scan using idx_posts_author_id ...
```

- 기본키와 유니크 제약은 유니크 B-tree 인덱스를 자동으로 만듭니다.
- 외래키는 참조하는 쪽 컬럼에 인덱스를 자동으로 만들지 않습니다. PostgreSQL 문서가 명시한 점입니다. 위처럼 `author_id`를 직접 인덱싱해야 조인과 `WHERE author_id = ...`가 빨라집니다.
- 복합 인덱스 `(a, b)`는 앞쪽 컬럼에 조건이 있을 때 가장 효율적입니다. 선행 컬럼의 동등 조건과 그다음 컬럼의 범위 조건이 스캔 범위를 줄입니다. 문서는 세 컬럼을 넘는 복합 인덱스는 특수한 경우가 아니면 도움이 안 되기 쉽다고 합니다.
- 인덱스는 쓰기를 느리게 합니다. 삽입·수정·삭제 때마다 인덱스도 갱신해야 하므로 쓰이지 않는 인덱스는 지웁니다.
- `EXPLAIN`은 계획을 보여 주고, `EXPLAIN ANALYZE`는 쿼리를 실제로 실행해 실제 시간과 행 수를 보여 줍니다. `UPDATE`나 `DELETE`에 붙이면 정말 실행됩니다.
- 데이터가 적은 개발 DB에서는 인덱스가 있어도 순차 스캔이 선택되기도 합니다. 계획은 운영과 비슷한 데이터 양에서 확인합니다.

**흔한 실수:** 쓰는 쿼리를 확인하지 않고 모든 컬럼에 인덱스를 거는 것입니다. 인덱스는 실제 쿼리의 `WHERE`, `JOIN`, `ORDER BY`에 맞춰 만듭니다. 큰 테이블에 운영 중 인덱스를 만들 때는 기본 `CREATE INDEX`가 쓰기를 막으므로 `CREATE INDEX CONCURRENTLY`를 씁니다. 이 명령은 트랜잭션 블록 안에서 실행할 수 없고, 실패하면 무효 인덱스가 남아 지우고 다시 만들어야 합니다.

## 마이그레이션 운영

마이그레이션은 스키마 변경을 순서가 있는 파일로 저장해 모든 환경에 같은 순서로 적용하는 방식입니다. 변경 내역이 저장소에 남고 리뷰할 수 있습니다.

| 도구 | 만들기 | 적용 |
|------|--------|------|
| Prisma 7 | `prisma migrate dev` | `prisma migrate deploy` |
| TypeORM | `migration:generate` | `migration:run`, 되돌리기는 `migration:revert` |
| Drizzle | `drizzle-kit generate` | `drizzle-kit migrate` |

- 운영 규칙은 같습니다. 파일은 개발에서 만들어 저장소에 커밋하고, 운영에서는 만들지 않고 적용만 합니다. 이미 적용한 마이그레이션 파일은 고치지 않습니다. Prisma는 수정된 파일을 경고합니다.
- `prisma migrate deploy`는 섀도 DB와 드리프트 검사를 쓰지 않고 클라이언트 생성도 하지 않습니다. 동시에 두 곳에서 실행되지 않게 어드바이저리 락(PostgreSQL·MySQL·SQL Server)을 쓰며 제한 시간은 10초입니다.
- `drizzle-kit push`와 TypeORM `synchronize`는 파일 없이 DB를 스키마에 맞추는 방식입니다. 개발에서만 쓰고 운영에서는 쓰지 않습니다.
- 배포 파이프라인에서 마이그레이션은 새 앱을 띄우기 전에 한 번 실행합니다. 앱 인스턴스가 시작할 때마다 실행하게 두면 여러 인스턴스가 경쟁합니다.
- 컬럼 삭제나 이름 변경은 구버전 앱이 아직 돌고 있을 때 깨집니다. 먼저 새 컬럼을 추가해 두 버전이 모두 동작하게 하고, 앱을 전환한 뒤 옛 컬럼을 지우는 식으로 나눠 배포합니다.
- 큰 테이블의 컬럼 추가나 인덱스는 잠금 시간이 길 수 있습니다. 적용 전에 변경될 SQL을 읽습니다.

**흔한 실수:** 운영 DB에 `migrate dev`나 `synchronize: true`를 쓰는 것입니다. `migrate dev`는 개발용이라고 공식 문서가 운영 사용을 금지하고, `synchronize`는 데이터가 있는 DB에서 안전하지 않다고 경고합니다.

## ORM 선택 기준표

| 기준 | 드라이버(pg·mysql2) | Prisma | TypeORM | Drizzle |
|------|--------------------|--------|---------|---------|
| 스키마 정의 | 없음(SQL) | 전용 스키마 파일 | 클래스와 데코레이터 | TypeScript 코드 |
| 타입 | 직접 지정 | 스키마에서 생성 | 엔티티 클래스 | 스키마에서 추론 |
| SQL 통제 | 완전 | 낮음 | 중간(QueryBuilder) | 높음 |
| 마이그레이션 | 별도 도구 | 내장 | 내장 CLI | drizzle-kit |
| 진입 장벽 | SQL 지식 필요 | 낮음 | 중간(데코레이터·옵션) | SQL을 알면 낮음 |
| 현재 버전 상태 | 안정 | 7 안정, 8 RC | 1.x 안정 | 0.45 안정, 1.0 RC |
| 어울리는 곳 | 복잡한 SQL, 최소 의존 | 빠른 개발, 팀 규약 | NestJS(`@nestjs/typeorm`) 기반 서비스 | SQL 친화, 서버리스 |

- 정답은 없고 팀이 쿼리를 얼마나 직접 통제하고 싶은지가 기준입니다. 복잡한 리포트 쿼리가 많으면 SQL을 직접 쓸 수 있는 선택지(드라이버, Drizzle, TypeORM QueryBuilder)가 편합니다.
- 어느 ORM을 써도 필요하면 원시 SQL로 내려갈 수 있습니다. ORM 하나로 모든 쿼리를 표현하려고 하지 않습니다.
- ORM을 쓴다고 SQL을 몰라도 되는 것은 아닙니다. N+1, 인덱스, 격리 수준, 마이그레이션 잠금은 ORM이 가려 주지 않습니다.
- 프레임워크와 짝도 고려합니다. NestJS는 `@nestjs/typeorm` 패키지로 TypeORM을 통합합니다(자세히는 14편).

## 핵심 정리

- 드라이버는 SQL과 값을 분리해 보내는 파라미터 바인딩으로 인젝션을 막고, 식별자는 바인딩이 안 되므로 허용 목록으로 검사한다.
- 풀은 기본 10개이며 인스턴스 수와 DB 연결 한도를 함께 계산하고, pg는 `connectionTimeoutMillis`와 `error` 리스너를 설정하며 빌린 연결은 반드시 반납한다.
- Prisma 7은 `schema.prisma`와 `prisma.config.ts`와 드라이버 어댑터를 쓰고 8은 RC로 API가 바뀌었으며, TypeORM은 1.0에서 `DataSource` 중심이 되고, Drizzle은 SQL에 가까운 쿼리 빌더다.
- 트랜잭션은 같은 연결에서 실행해야 하고 콜백 안에서는 `tx`로 쿼리하며, PostgreSQL은 READ COMMITTED가 기본이고 MySQL InnoDB는 REPEATABLE READ가 기본이다.
- N+1은 `include`·`relations`·조인으로 한 번에 가져와 해결하고, 외래키 컬럼은 PostgreSQL이 자동으로 인덱싱하지 않으므로 직접 만든다.
- 마이그레이션은 개발에서 만들어 커밋하고 운영에서는 적용만 하며, `synchronize`·`push`·`migrate dev`는 운영에서 쓰지 않는다.

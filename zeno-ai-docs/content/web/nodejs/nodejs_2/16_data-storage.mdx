## Node는 DB가 아님

Node.js 프로세스는 요청을 처리하는 동안만 의미 있는 상태를 가지는 실행 환경이고, 데이터를 영구적이고 안전하게 보관하는 저장소가 아닙니다. 프로세스 메모리의 데이터는 다음 이유로 믿을 수 없습니다.

- 재시작, 배포, 크래시, 메모리 부족 종료(OOM)로 사라집니다.
- 서버 인스턴스를 둘 이상 띄우면 인스턴스마다 값이 다릅니다. 로드 밸런서가 요청을 어느 인스턴스로 보내느냐에 따라 같은 사용자가 다른 데이터를 봅니다.
- 메모리는 제한되어 있고, 크게 쌓으면 가비지 컬렉션 부담과 힙 한계 문제가 생깁니다.

```js
const orders = [] // 모듈 수준 배열을 DB처럼 사용
app.post('/orders', (req, res) => {
  orders.push(req.body) // 재시작하면 소실, 인스턴스마다 따로 쌓임
  res.status(201).end()
})
```

그래서 애플리케이션 서버는 상태를 갖지 않게(stateless) 만들고, 데이터는 DB·캐시·객체 저장소 같은 별도 프로세스에 둡니다. 서버를 늘리거나 교체해도 데이터가 그대로이고, 서버는 요청마다 저장소에 접속해 읽고 씁니다. 세션도 같습니다. 메모리 세션은 인스턴스 사이에서 공유되지 않으므로 외부 저장소가 필요합니다(10편, 18편).

모듈 수준 변수는 짧게 쓰는 캐시나 설정처럼 잃어도 되는 값에만 씁니다.

## 파일 저장의 한계

JSON이나 텍스트 파일에 읽고 쓰면 DB 없이 영구 저장이 됩니다. 한 사람이 쓰는 스크립트, 설정, 로그에는 충분합니다. 여러 요청이 동시에 읽고 쓰는 서버의 데이터 저장소로는 다음이 문제입니다.

```js
// 카운터 파일을 읽고 1을 더해 다시 쓰기
async function inc() {
  const d = JSON.parse(await readFile('c.json', 'utf8'))
  d.n += 1
  await writeFile('c.json', JSON.stringify(d))
}
await Promise.all([inc(), inc(), inc()])
// 결과 n은 3이 아니라 1 — 세 요청이 같은 값을 읽고 덮어씀
```

| 한계 | 설명 |
|------|------|
| 동시성 | 읽고 수정해 쓰는 사이에 다른 요청이 끼어들어 갱신이 사라짐(lost update) |
| 원자성 | 쓰는 도중 프로세스가 죽으면 파일이 반쯤 쓰인 상태로 남을 수 있음 |
| 조회 | 조건 검색이 전체 파일을 읽고 필터링하는 방식뿐이고 인덱스가 없음 |
| 크기 | 일부만 바꾸려 해도 전체를 읽고 다시 써야 함 |
| 다중 인스턴스 | 파일은 서버 한 대의 디스크에 있으므로 다른 인스턴스와 공유되지 않음 |
| 제약 | 중복 방지, 외래 키, 타입 검사 같은 규칙을 직접 구현해야 함 |

- 파일 이름 바꾸기(임시 파일에 쓰고 `rename`)로 쓰기 도중 손상은 줄일 수 있지만 동시성과 조회 문제는 남습니다.
- 사용자가 올린 이미지·동영상 같은 큰 바이너리는 DB 행이 아니라 파일이나 객체 저장소(S3 등)에 두고, DB에는 경로나 키만 저장하는 구성이 일반적입니다(11편).
- 파일 하나로 쓰는 DB가 필요하면 SQLite가 대안입니다. Node는 `node:sqlite`를 내장합니다(아래 드라이버 절).

## SQL / NoSQL

저장소는 데이터 모델에 따라 크게 둘로 나눕니다.

| 구분 | SQL(관계형) | NoSQL(문서형 예: MongoDB) |
|------|-------------|---------------------------|
| 모델 | 테이블의 행과 열, 관계는 키로 연결 | 문서형은 중첩 객체와 배열을 담는 문서(BSON) |
| 스키마 | 미리 정의하고 변경은 마이그레이션 | 같은 컬렉션 안에서도 필드가 달라도 됨, 선택적 검증 가능 |
| 관계 | JOIN으로 조합 | 함께 읽는 데이터는 문서 안에 내장(embedding), 아니면 참조 |
| 질의 | SQL | 제품 고유의 쿼리 API |
| 예 | PostgreSQL, MySQL, SQLite | MongoDB, Redis(키-값) |

- NoSQL은 하나의 기술이 아니라 문서, 키-값, 그래프 등 비관계형 저장소를 묶어 부르는 이름입니다.
- 관계가 많고 정합성이 중요한 업무 데이터(주문, 결제, 계정)는 SQL을 기본으로 합니다. 채용 공고에서도 PostgreSQL·MySQL 경험이 반복해서 요구됩니다.
- 문서 DB는 스키마가 자주 바뀌거나 문서 단위로 통째로 읽고 쓰는 데이터에 어울립니다. MongoDB도 여러 문서에 걸친 ACID 트랜잭션을 지원하므로 NoSQL이면 트랜잭션이 없다는 말은 일반화하면 안 됩니다.
- 이 과목에서는 SQL(17편)과 Redis·MongoDB 개요(18편)를 다룹니다.

**흔한 실수:** 스키마가 없어 편하다는 이유로 문서 DB를 고르고, 필드 이름과 형태가 제각각인 데이터를 쌓은 뒤 코드에서 방어 로직을 늘리는 것입니다. 스키마가 없는 것이 아니라 스키마 책임이 애플리케이션으로 넘어오는 것입니다.

## 드라이버

드라이버(driver)는 Node 코드가 DB 서버와 통신 프로토콜로 대화하게 해 주는 클라이언트 라이브러리입니다. 연결, 쿼리 전송, 결과 변환을 맡고, DB마다 다릅니다.

| 대상 | 대표 패키지 |
|------|-------------|
| PostgreSQL | `pg` (node-postgres) |
| MySQL, MariaDB | `mysql2` |
| MongoDB | `mongodb` |
| Redis | `redis`, `ioredis` |
| SQLite | `node:sqlite`(내장), `better-sqlite3` |

- ORM과 쿼리 빌더(Prisma, TypeORM, Drizzle, Knex)는 이 드라이버 위에서 동작합니다(17편).
- `node:sqlite`는 Node 22.5.0에서 추가되었고, Node 24에서는 플래그 없이 `node:` 접두사로 가져옵니다. 안정성 지수는 1.2(Release Candidate)입니다. 동기 API(`DatabaseSync`)라서 요청을 처리하는 서버에서 쓰면 이벤트 루프를 막을 수 있어, 스크립트·도구·테스트 용도로 적합합니다(23편).
- 값은 쿼리 문자열에 이어 붙이지 않고 매개변수로 넘깁니다. 드라이버가 값을 SQL과 분리해 전달하므로 SQL 인젝션이 막힙니다.

```js
import { DatabaseSync } from 'node:sqlite'

const db = new DatabaseSync(':memory:')
db.exec('CREATE TABLE users(id INTEGER, name TEXT)')
db.prepare('INSERT INTO users(name) VALUES (?)').run('kim')

const evil = "x' OR '1'='1"
const safe = 'SELECT * FROM users WHERE name = ?'
db.prepare(safe).all(evil) // ✅ []

const bad = `SELECT * FROM users WHERE name = '${evil}'`
db.prepare(bad).all() // ❌ 전부 반환
```

- 매개변수 표기는 드라이버마다 다릅니다. `pg`는 `$1, $2`, `mysql2`와 `node:sqlite`는 `?`입니다.
- 테이블·컬럼 이름은 매개변수로 넘길 수 없습니다. 동적으로 정해야 하면 허용 목록과 비교한 뒤에만 이어 붙입니다.
- 드라이버 호출은 모두 비동기(Promise)입니다. `await`를 빠뜨리면 쿼리 결과가 아니라 Promise를 사용하게 됩니다(26편).

## 커넥션 풀

DB 연결은 만드는 비용이 큽니다(TCP, TLS, 인증). 커넥션 풀(connection pool)은 연결을 미리 몇 개 만들어 두고 쿼리마다 빌려 쓰고 반납하는 구조입니다. 요청마다 연결을 새로 만들면 느리고, DB 서버가 받을 수 있는 연결 수에도 한계가 있습니다.

```js
import pg from 'pg'

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10, // 동시 연결 상한(기본값)
})
const sql = 'SELECT $1::int AS n'
const { rows } = await pool.query(sql, [1])
// rows: [{ n: 1 }]
```

`pg`의 `Pool` 기본값은 `max` 10, `idleTimeoutMillis` 10,000(놀고 있는 연결을 10초 뒤 닫음), `connectionTimeoutMillis` 0(빌리려고 기다리는 시간 제한 없음)입니다.

- `pool.query()`는 한 번의 쿼리에 풀의 연결을 빌렸다가 자동으로 반납합니다.
- 여러 쿼리를 같은 연결에서 해야 하면(트랜잭션) `pool.connect()`로 연결(client)을 빌리고 반드시 `client.release()`로 반납합니다. 반납을 빠뜨리면 풀이 고갈되어 이후 요청이 모두 대기합니다.
- 풀이 가득 차면 새 쿼리는 대기열에서 기다립니다. `pool.totalCount`, `pool.idleCount`, `pool.waitingCount`로 상태를 봅니다. `waitingCount`가 계속 크면 풀이 모자라거나 쿼리가 느린 것입니다.
- 풀 크기는 서버 한 대의 `max`에 인스턴스 수를 곱한 값이 DB의 `max_connections`(PostgreSQL 기본 약 100)를 넘지 않게 정합니다. 큰 풀이 항상 빠른 것은 아닙니다. 연결이 늘면 DB 쪽 부담이 커집니다.
- 풀은 프로세스에 하나만 만들어 모듈 수준에서 공유합니다. 요청 핸들러 안에서 `new Pool()`을 만들면 요청마다 풀이 생겨 연결이 폭증합니다.
- 놀고 있는 연결도 DB 재시작이나 네트워크 단절로 에러를 낼 수 있습니다. 풀의 `error` 이벤트에 리스너를 달지 않으면 처리되지 않은 에러로 프로세스가 종료될 수 있습니다(26편).
- 종료할 때는 `pool.end()`로 연결을 모두 닫습니다(25편).

**흔한 실수:** 트랜잭션을 `pool.query()`로 `BEGIN`, `COMMIT`을 따로 보내는 것입니다. 각 호출이 다른 연결로 갈 수 있어 트랜잭션이 성립하지 않습니다.

## 쿼리와 HTTP 핸들러 분리

DB 접근 코드를 HTTP 핸들러에 섞으면 테스트가 어렵고 재사용이 안 됩니다. 쿼리는 별도 계층(repository 또는 데이터 접근 모듈)으로 빼고, 핸들러는 요청을 해석해 그 계층을 호출하고 응답만 만듭니다(13편의 router·controller·service 구분).

```js
// users.repo.js — SQL만 알고 HTTP는 모름
export async function findById(pool, id) {
  const { rows } = await pool.query(
    'SELECT id, name FROM users WHERE id = $1', [id])
  return rows[0] ?? null
}

// 핸들러 — HTTP만 알고 SQL은 모름
app.get('/users/:id', async (req, res) => {
  const user = await findById(pool, req.params.id)
  if (!user) return res.status(404).json({ error: 'none' })
  res.json(user)
})
```

- 풀을 인자로 받거나 주입하면 테스트에서 가짜 저장소로 바꿀 수 있습니다(24편). Nest에서는 이 구성이 프로바이더 주입입니다(14편).
- 필요한 컬럼만 선택하고(`SELECT *` 지양) 비밀번호 해시 같은 내부 컬럼이 응답으로 새지 않게 계층 경계에서 걸러 냅니다.
- 입력 검증은 쿼리 앞, 핸들러 경계에서 합니다(8편).

## 트랜잭션은 DB 책임

트랜잭션(transaction)은 여러 SQL 문을 전부 성공하거나 전부 취소되는 하나의 작업 단위로 묶는 DB의 기능입니다. 원자성(atomicity), 격리성(isolation), 지속성(durability)을 DB가 보장합니다. Node 코드에서 `try/catch`로 되돌리려는 시도로는 대체할 수 없습니다. 두 번째 쿼리가 실패했을 때 첫 번째 쿼리의 변경을 되돌릴 수단이 코드에는 없기 때문입니다.

```sql
BEGIN;
UPDATE accounts SET bal = bal - 100 WHERE name = 'A';
UPDATE accounts SET bal = bal + 100 WHERE name = 'B';
COMMIT; -- 중간에 실패하면 ROLLBACK, 둘 다 없던 일이 됨
```

- `BEGIN` 없이 보낸 문장은 각각 자동으로 하나의 트랜잭션으로 처리됩니다(autocommit). 여러 문장을 묶으려면 명시적으로 `BEGIN`~`COMMIT`을 씁니다.
- Node에서는 한 연결에서 모든 문장을 실행해야 하고, 오류 시 `ROLLBACK`, 마지막에 연결 반납을 보장합니다.

```js
const client = await pool.connect()
try {
  await client.query('BEGIN')
  await debit(client, from, amount) // 같은 client로 전달
  await credit(client, to, amount)
  await client.query('COMMIT')
} catch (e) {
  await client.query('ROLLBACK')
  throw e
} finally {
  client.release()
}
```

- 트랜잭션 안에서는 외부 HTTP 호출처럼 오래 걸리는 작업을 하지 않습니다. 열린 트랜잭션은 잠금을 쥐고 연결을 점유합니다. PostgreSQL에는 열린 채 놀고 있는 세션을 끊는 `idle_in_transaction_session_timeout` 설정이 있습니다.
- 트랜잭션 경계는 서비스 계층이 정하고, 같은 연결을 저장소 함수에 넘깁니다. 그래서 위 `debit`, `credit`은 풀이 아니라 `client`를 인자로 받습니다.
- 한 트랜잭션 안에서 일부만 되돌리려면 `SAVEPOINT`와 `ROLLBACK TO`를 씁니다.
- 격리 수준과 동시 갱신 처리는 17편에서 다룹니다.

**흔한 실수:** 돈 이동처럼 둘 이상의 쓰기가 한 덩어리인 작업을 트랜잭션 없이 쿼리 두 번으로 처리하는 것입니다. 두 번째에서 실패하면 데이터가 어긋난 채로 남습니다.

## N+1 개념

N+1은 목록 하나를 가져오는 쿼리 1번에 이어, 목록의 항목마다 관련 데이터를 가져오는 쿼리를 N번 더 보내는 패턴입니다. 항목이 늘수록 쿼리 수가 비례해 늘어 응답이 느려집니다.

```js
const users = db.prepare('SELECT * FROM users').all() // 1번
for (const u of users) { // 사용자 N명 → N번
  u.posts = db.prepare(
    'SELECT * FROM posts WHERE user_id = ?').all(u.id)
}
// 사용자 3명이면 쿼리 4번, 1000명이면 1001번
```

해결은 쿼리 수를 항목 수와 무관하게 만드는 것입니다.

```js
const ids = users.map((u) => u.id)
const marks = ids.map(() => '?').join(',')
const q = `SELECT * FROM posts WHERE user_id IN (${marks})`
const posts = db.prepare(q).all(...ids)
// 쿼리 2번 — 메모리에서 user_id로 묶음
```

- JOIN으로 한 번에 가져오는 방법도 있습니다. 1:N 결과는 행이 중복되므로 묶는 코드가 필요합니다.
- ORM에서는 관계를 따라가는 코드(`user.posts`)가 보이지 않는 쿼리를 만들어 N+1이 숨기 쉽습니다. 쿼리 로그로 요청 한 번에 나가는 쿼리 수를 확인합니다(17편의 해결책).
- 한 건씩 보면 빠른 쿼리라 개발 환경의 작은 데이터에서는 드러나지 않고, 운영 데이터에서 느려집니다.
- 반복문 안의 `await db.query(...)`가 N+1의 신호입니다.

## 마이그레이션

마이그레이션(migration)은 DB 스키마의 변경을 순서가 있는 파일로 기록하고 환경마다 같은 순서로 적용하는 방식입니다. 코드는 Git으로 버전을 관리하지만 DB 구조는 서버에 있으므로, 구조 변경도 코드처럼 추적해야 합니다.

```js
const migrations = [
  [1, 'CREATE TABLE users(id INTEGER PRIMARY KEY)'],
  [2, 'ALTER TABLE users ADD COLUMN name TEXT'],
]
// 적용된 번호는 migrations 표에 기록하고 건너뜀
for (const [v, sql] of migrations) {
  if (applied.has(v)) continue
  db.exec('BEGIN'); db.exec(sql)
  db.prepare('INSERT INTO migrations VALUES (?)').run(v)
  db.exec('COMMIT')
}
```

- 마이그레이션 도구(Prisma, TypeORM, Knex 등)는 위 구조를 갖춥니다. 적용 이력을 DB의 별도 표에 기록하고, 아직 적용되지 않은 것만 순서대로 실행합니다(17편).
- 이미 운영에 적용된 마이그레이션 파일은 고치지 않습니다. 고칠 일이 생기면 새 마이그레이션을 추가합니다. 환경마다 적용 이력이 달라져 어긋납니다.
- 마이그레이션은 앱 코드와 별개로 실행합니다(배포 단계에서 한 번). 서버가 여러 대일 때 시작할 때마다 각자 마이그레이션을 돌리면 동시 실행으로 충돌합니다.
- 컬럼 삭제·이름 변경은 구버전 코드가 아직 돌고 있는 동안 적용하면 장애가 납니다. 먼저 새 구조를 추가하고, 코드를 배포하고, 나중에 옛 구조를 지우는 단계적 방식으로 나눕니다.
- 테이블 구조를 손으로 운영 DB에 직접 바꾸지 않습니다. 환경 사이의 차이(drift)가 생깁니다.

**흔한 실수:** 개발 중에 로컬 DB를 손으로 고쳐 놓고 마이그레이션 파일을 만들지 않는 것입니다. 동료와 운영 환경에는 그 변경이 없어 같은 코드가 다른 DB에서 실패합니다.

## 캐시

캐시(cache)는 비싼 조회 결과를 빠른 저장소에 임시로 두고 다시 쓰는 기법입니다. DB는 느린 쿼리와 부하가 큰 읽기에 약하므로, 같은 데이터를 자주 읽는 경우 앞단의 메모리나 Redis가 부담을 줄입니다. 가장 흔한 형태는 cache-aside입니다.

```js
const cache = new Map() // 단일 인스턴스 예. 여러 대면 Redis
async function getUser(id, load, ttlMs = 60_000) {
  const hit = cache.get(id)
  if (hit && hit.exp > Date.now()) return hit.value // 캐시 히트
  const value = await load(id) // 미스 → DB에서 읽음
  const exp = Date.now() + ttlMs
  if (value) cache.set(id, { value, exp })
  return value
}
// 쓸 때: DB를 먼저 갱신한 뒤 cache.delete(id)로 무효화
```

- 읽을 때는 캐시를 먼저 보고, 없으면(미스) DB에서 읽어 캐시에 채웁니다. 쓸 때는 DB를 갱신한 뒤 캐시 항목을 지웁니다(무효화). 순서가 중요합니다. 캐시를 먼저 지우면 그 사이 읽기가 옛 데이터를 다시 채울 수 있습니다.
- 만료(TTL)를 둡니다. 너무 짧으면 효과가 없고, 너무 길면 오래된 값이 남습니다.
- cache-aside는 DB와 캐시의 일치를 보장하지 않습니다. 쓰기와 다음 읽기 사이에 잠깐 오래된 값이나 미스가 있을 수 있고, 다른 프로세스가 DB를 바꾸면 TTL이 지날 때까지 캐시가 모릅니다.
- 프로세스 메모리 캐시는 인스턴스마다 따로 있어 값이 어긋납니다. 여러 인스턴스가 공유해야 하면 Redis 같은 외부 캐시를 씁니다(18편).
- 민감한 데이터와 거의 항상 미스가 나는 데이터는 캐시에 맞지 않습니다. 없는 값(null)은 캐시하지 않거나 짧은 TTL로 둡니다.
- 캐시는 저장소가 아닙니다. 사라져도 DB에서 다시 만들 수 있는 값만 둡니다.

## 재시도

재시도(retry)는 일시적인 오류로 실패한 DB 호출을 다시 시도하는 것입니다. 모든 실패를 재시도하는 것이 아니라 시간이 지나면 성공할 수 있는 것만 대상으로 합니다.

| 재시도 대상 | 코드(PostgreSQL) | 이유 |
|-------------|------------------|------|
| 직렬화 실패 | `40001` | 동시 트랜잭션 충돌, 다시 하면 통과 가능 |
| 교착 상태 | `40P01` | DB가 한쪽을 중단시킴 |
| 접속 불가 | `57P03` | 서버가 아직 연결을 받지 못하는 상태 |
| 재시도 불가 | `23505`(유일 제약 위반), `23503`(외래 키 위반) | 같은 입력이면 반복해도 실패 |

```js
// TRANSIENT = new Set(['40001', '40P01', '57P03'])
async function withRetry(fn, tries = 3, base = 50) {
  for (let i = 1; ; i++) {
    try { return await fn() } catch (e) {
      if (i >= tries || !TRANSIENT.has(e.code)) throw e
      const wait = base * 2 ** (i - 1) // 50, 100, 200 ms
      await sleep(wait + Math.random() * base) // 지터 추가
    }
  }
}
```

- 대기 시간을 점점 늘리는 지수 백오프(exponential backoff)에 무작위 값(지터)을 더합니다. 여러 요청이 같은 시각에 몰려 다시 부딪히는 것을 막습니다.
- 횟수와 총 시간에 상한을 둡니다. 무한 재시도는 DB가 이미 힘들 때 부하를 더합니다.
- 트랜잭션은 실패한 지점부터가 아니라 `BEGIN`부터 통째로 다시 실행합니다. 재시도 함수에 트랜잭션 전체를 넘깁니다.
- 쓰기 재시도는 같은 작업이 두 번 적용되지 않아야 합니다. 응답이 유실된 경우 DB에는 이미 반영되었을 수 있으므로 멱등하게 설계합니다(유일 키, 요청 ID, 8편의 멱등성).
- 일부 드라이버·ORM·클라이언트는 재시도 옵션을 이미 가집니다. 겹쳐서 이중으로 재시도하지 않습니다.

**흔한 실수:** 모든 에러를 재시도하는 것입니다. 중복 키나 문법 오류는 몇 번을 다시 해도 실패하고 불필요한 부하만 만듭니다.

## 타임아웃을 DB 호출에도

HTTP 서버와 클라이언트에 타임아웃을 두듯(6편) DB 호출에도 둡니다. 시간제한이 없으면 느린 쿼리나 잠금 대기 하나가 연결을 붙잡고, 풀이 고갈되어 모든 요청이 대기하는 연쇄 장애로 번집니다.

| 설정 | 위치 | 의미 |
|------|------|------|
| `connectionTimeoutMillis` | `pg` 클라이언트·풀 | 연결을 얻는 데 기다리는 시간(기본 제한 없음) |
| `statement_timeout` | PostgreSQL 서버 | 문장 하나의 실행 시간 상한(기본 0, 무제한) |
| `lock_timeout` | PostgreSQL 서버 | 잠금을 기다리는 시간 상한 |
| `idle_in_transaction_session_timeout` | PostgreSQL 서버 | 트랜잭션을 연 채 놀고 있는 세션 종료 |
| `query_timeout` | `pg` 클라이언트 | 쿼리 호출 하나가 넘기면 안 되는 시간 |

```js
const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  connectionTimeoutMillis: 2_000, // 풀에서 연결을 못 얻으면 2초 뒤 실패
  statement_timeout: 5_000, // 서버가 5초 넘는 쿼리를 중단
})
```

- 서버 쪽 제한(`statement_timeout`)이 쿼리를 실제로 중단합니다. 클라이언트에서 `Promise.race`로 타임아웃 응답만 보내면 DB에서는 쿼리가 계속 돌아 연결과 자원을 점유합니다.
- `statement_timeout`을 `postgresql.conf`에 걸면 모든 세션에 적용되므로 PostgreSQL 문서는 권하지 않습니다. 세션이나 역할(role) 단위로 설정합니다.
- HTTP 요청 전체의 제한 시간보다 DB 호출의 제한을 짧게 둡니다. 그렇지 않으면 클라이언트가 이미 포기한 요청의 쿼리가 계속 실행됩니다. 취소 신호(`AbortSignal`)를 받는 API에는 `AbortSignal.timeout(ms)`를 전달합니다(6편, 7편).
- 타임아웃 에러(`57014` query_canceled 등)는 재시도 대상인지 따로 판단합니다. 느린 쿼리를 반복하면 문제가 커집니다.
- 풀 대기 시간(`connectionTimeoutMillis`)과 쿼리 시간(`statement_timeout`)은 목적이 다르므로 둘 다 둡니다.

**흔한 실수:** 타임아웃을 하나만 걸고 안심하는 것입니다. 연결 획득, 잠금 대기, 쿼리 실행, 열린 트랜잭션은 각각 다른 지점에서 멈출 수 있습니다.

## 핵심 정리

- Node 프로세스는 저장소가 아닙니다. 상태는 DB·캐시·객체 저장소에 두고 서버는 stateless로 만듭니다.
- 파일 저장은 동시 쓰기에서 갱신이 사라지고 조회·다중 인스턴스에 맞지 않습니다. 관계형 데이터는 SQL을 기본으로 하고 NoSQL은 데이터 모델에 따라 고릅니다.
- 드라이버는 값을 매개변수로 넘기고, 풀은 프로세스당 하나로 공유하며, 빌린 연결은 반드시 반납합니다.
- 트랜잭션은 같은 연결에서 `BEGIN`~`COMMIT`, 오류 시 `ROLLBACK`으로 DB가 보장합니다. 쿼리는 핸들러에서 분리합니다.
- N+1은 반복문 안의 쿼리가 신호이고 `IN`·JOIN으로 줄이며, 스키마 변경은 마이그레이션 파일로 기록하고 적용된 파일은 고치지 않습니다.
- 캐시는 TTL과 무효화(DB 갱신 뒤 삭제)를 갖추고, 재시도는 일시적 오류에만 백오프로 하며, DB 호출에도 연결·쿼리·잠금 타임아웃을 둡니다.

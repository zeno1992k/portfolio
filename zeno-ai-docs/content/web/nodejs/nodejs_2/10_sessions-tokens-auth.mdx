## 인증

인증(authentication)은 요청한 쪽이 누구인지 확인하는 일입니다. 확인 수단은 알고 있는 것(비밀번호), 가진 것(기기, OTP), 외부 서비스의 보증(소셜 로그인)으로 나뉩니다. 서버는 인증이 끝나면 이후 요청을 같은 사용자로 알아볼 수단(세션 ID나 토큰)을 클라이언트에 줍니다.

- 인증에 실패한 요청에는 `401`을 응답합니다. 이름은 Unauthorized이지만 뜻은 "인증되지 않음"입니다. MDN에 따르면 `401`에는 기대하는 방식을 알리는 `WWW-Authenticate` 헤더를 함께 보내야 합니다.

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer
```

- 로그인 실패 응답은 계정이 없는 경우와 비밀번호가 틀린 경우를 구분하지 않고 같은 메시지로 냅니다. 계정 존재 여부가 드러나지 않습니다(OWASP).
- OWASP는 비밀번호 최소 길이를 MFA 사용 시 8자, 미사용 시 15자로 권하고, 최대 길이는 64자 이상을 허용하며, 대문자·숫자 같은 조합 규칙은 요구하지 않고, 긴 비밀번호를 조용히 잘라 저장하지 말라고 합니다.
- 무차별 대입을 막으려면 MFA가 가장 효과적이고, 계정 단위 잠금과 요청 횟수 제한을 겹칩니다(rate limit은 18편).
- 로그인 화면과 인증된 세션은 TLS 위에서만 다룹니다(자세히는 07편).

**흔한 실수:** 비밀번호 변경이나 결제처럼 위험한 작업을 로그인 상태만 믿고 처리하는 것입니다. OWASP는 이런 작업 앞에서 비밀번호를 다시 확인하라고 권합니다.

## 비밀번호 해시

비밀번호는 복원할 수 없는 해시로 저장합니다. 이때 쓰는 해시는 일부러 느리고 메모리를 많이 쓰도록 만든 비밀번호 전용 알고리즘이어야 합니다. SHA-256 같은 범용 해시는 빨라서 유출된 해시에 대한 대입 공격에 취약합니다(해시 함수는 21편).

OWASP의 권장 순서와 최소 설정입니다.

| 순위 | 알고리즘 | 최소 설정 |
|------|----------|-----------|
| 1 | Argon2id | 메모리 19 MiB, 반복 2, 병렬도 1 |
| 2 | scrypt | N=2의 17제곱(128 MiB), r=8, p=1 |
| 3 | bcrypt(기존 시스템용) | 작업 계수 10 이상 |
| 4 | PBKDF2-HMAC-SHA256(FIPS 필요 시) | 600,000회 이상 |

- 솔트(salt)는 비밀번호마다 따로 만든 무작위 값입니다. 같은 비밀번호도 다른 해시가 되어 미리 계산한 표(레인보우 테이블)를 막습니다. 솔트는 해시와 함께 저장해도 됩니다.
- 페퍼(pepper)는 모든 비밀번호가 공유하는 비밀 값으로, 해시와 다른 곳(시크릿 저장소)에 둡니다.
- bcrypt는 입력을 72바이트까지만 쓰므로 그보다 긴 비밀번호는 뒷부분이 해시에 반영되지 않습니다.
- Node 24.7.0부터 `node:crypto`에 `argon2()`와 `argon2Sync()`가 있습니다. `scrypt()`는 v10.5.0부터 있습니다. 문서는 nonce(솔트)를 무작위 16바이트 이상으로 권합니다. 이전 버전이나 PHC 문자열 형식이 필요하면 argon2, bcrypt 패키지를 씁니다.

```js
const enc = (b) => b.toString('base64url')
const P = {
  parallelism: 1, tagLength: 32, memory: 19456, passes: 2,
}

async function hashPassword(pw) {
  const nonce = randomBytes(16)
  const opts = { ...P, message: pw, nonce }
  const tag = await argon2p('argon2id', opts)
  return `${enc(nonce)}.${enc(tag)}`
}
```

`argon2p`는 `promisify(argon2)`이고 `enc`는 base64url 변환입니다. 저장값은 솔트와 해시를 이어 붙인 문자열이고, 설정값 `P`는 코드나 저장값에 함께 기록해 나중에 올릴 수 있게 합니다.

```js
async function checkPassword(pw, stored) {
  const [n, t] = stored.split('.')
  const nonce = Buffer.from(n, 'base64url')
  const opts = { ...P, message: pw, nonce }
  const tag = await argon2p('argon2id', opts)
  return timingSafeEqual(tag, Buffer.from(t, 'base64url'))
}
// checkPassword('올바른 값', stored) // true
```

해시는 같은 솔트와 설정으로 다시 계산해 비교합니다. 비교는 일반 `===` 대신 `timingSafeEqual`을 써서 응답 시간 차이가 정보가 되지 않게 합니다(자세히는 21편).

**흔한 실수:**

- 비밀번호를 SHA-256 한 번이나 솔트 없는 해시로 저장하는 것입니다.
- 동기 함수(`argon2Sync`, `scryptSync`)를 요청 핸들러에서 호출하는 것입니다. 해시 계산이 끝날 때까지 이벤트 루프가 막혀 모든 요청이 멈춥니다. 비동기 함수를 씁니다.
- 비밀번호나 해시를 로그에 남기는 것입니다.

## 세션

세션(session)은 서버가 로그인 상태를 기억하는 방식입니다. 로그인하면 서버가 무작위 세션 ID를 만들어 사용자 정보와 함께 서버에 저장하고, 세션 ID만 쿠키로 보냅니다. 이후 요청의 쿠키에서 세션 ID를 꺼내 저장소를 조회해 사용자를 알아냅니다.

```js
const sessions = new Map() // 운영에서는 Redis 같은 외부 저장소
const attrs = 'HttpOnly; Secure; Path=/; SameSite=Lax'

function login(res, userId) {
  const sid = randomBytes(32).toString('base64url')
  const expiresAt = Date.now() + 30 * 60_000
  sessions.set(sid, { userId, expiresAt })
  const cookie = `__Host-sid=${sid}; ${attrs}`
  res.setHeader('Set-Cookie', cookie)
}
```

```js
const clear = '__Host-sid=; Max-Age=0; Path=/; Secure'
function sidOf(req) {
  return parseCookies(req.headers.cookie).get('__Host-sid')
}
function auth(req) {
  const s = sessions.get(sidOf(req))
  return s && s.expiresAt > Date.now() ? s : null
}
function logout(req, res) {
  sessions.delete(sidOf(req))
  res.setHeader('Set-Cookie', clear)
}
```

`parseCookies`는 09편의 함수입니다. OWASP의 세션 관리 권장 사항입니다.

- 세션 ID는 CSPRNG로 만들고 엔트로피가 64비트 이상이어야 하며, 사용자 정보를 담지 않은 의미 없는 값이어야 합니다. 위 코드의 `randomBytes(32)`는 256비트입니다.
- 로그인 직후 세션 ID를 새로 발급합니다. 공격자가 미리 심어 둔 ID를 이어받는 세션 고정(fixation)을 막습니다.
- 쿠키에는 `Secure`, `HttpOnly`, `SameSite`, `__Host-`를 씁니다(자세히는 09편).
- 데이터는 서버에 두고, 쿠키에는 ID만 둡니다.
- 유휴 만료와 절대 만료를 둘 다 적용하고, 로그아웃은 서버 저장소에서 세션을 지워야 끝납니다. 브라우저 쿠키만 지우면 탈취된 ID는 계속 유효합니다.

세션의 장점은 서버가 즉시 무효화할 수 있다는 점입니다. 단점은 요청마다 저장소를 조회해야 하고, 서버가 여러 대이면 저장소를 공유해야 한다는 점입니다(저장소는 18편). 메모리 `Map`은 서버를 재시작하면 사라지고 인스턴스끼리 공유되지 않습니다.

## 토큰

토큰(token)은 서버가 발급해 클라이언트가 들고 다니며 요청마다 제시하는 증표입니다. 두 종류가 있습니다.

| 종류 | 내용 | 검증 방법 |
|------|------|-----------|
| 불투명(opaque) 토큰 | 의미 없는 무작위 문자열. 세션 ID와 같은 성격 | 서버 저장소 조회 |
| 자기 완결형 토큰(JWT 등) | 사용자와 만료 정보를 담고 서명됨 | 서명만 확인, 저장소 불필요 |

클라이언트는 보통 `Authorization` 헤더에 실어 보냅니다.

```http
GET /api/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

```js
const header = req.headers.authorization ?? ''
const [scheme, token] = header.split(' ')
if (scheme !== 'Bearer' || !token) {
  res.setHeader('WWW-Authenticate', 'Bearer')
  res.writeHead(401).end()
  return
}
```

세션과 비교하면 다음과 같습니다.

| 항목 | 서버 세션 | 자기 완결형 토큰 |
|------|-----------|------------------|
| 서버 상태 | 저장소 필요 | 없음(서명 검증만) |
| 즉시 폐기 | 저장소에서 삭제 | 만료 전에는 어려움 |
| 전달 방식 | 쿠키(자동 전송) | 보통 `Authorization` 헤더(수동 전송) |
| CSRF | 쿠키라서 대상 | 헤더에 직접 넣으면 대상 아님 |
| 인스턴스 확장 | 저장소 공유 필요 | 키만 공유 |

- 토큰을 쿠키에 담으면 세션과 똑같이 CSRF를 신경 써야 합니다(자세히는 09편).
- 토큰을 `localStorage`에 두면 JavaScript가 읽을 수 있어 XSS 한 번에 유출됩니다. `HttpOnly` 쿠키는 읽지 못하게 막습니다.
- 브라우저 앱은 세션 쿠키가 단순하고 안전한 선택인 경우가 많습니다. 토큰은 모바일 앱, 외부 API 호출, 서버 간 호출, 여러 서비스가 공통 인증을 공유할 때 유리합니다.

**흔한 실수:** 서버 상태가 없다는 이유만으로 JWT를 고르는 것입니다. 로그아웃과 권한 회수가 필요해지는 순간 폐기 목록이라는 서버 상태가 다시 생깁니다.

## JWT 구조와 검증

JWT(JSON Web Token, RFC 7519)는 클레임(claim)을 담은 JSON을 서명해 점(`.`)으로 이은 문자열입니다. 세 부분이 각각 base64url로 인코딩됩니다.

```text
header.payload.signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.<서명>
```

| 부분 | 내용 |
|------|------|
| header | 서명 알고리즘 `alg`, 형식 `typ` |
| payload | 클레임 |
| signature | header와 payload를 키로 서명한 값 |

- 서명은 위변조를 막을 뿐 내용을 숨기지 않습니다. payload는 누구나 디코딩해서 읽을 수 있으므로 비밀번호나 개인 정보를 넣지 않습니다(RFC 7519).

```js
const body = token.split('.')[1]
JSON.parse(Buffer.from(body, 'base64url')) // { sub: '1' }
```

등록된 클레임입니다. 전부 선택 항목이지만, 검증에는 아래 항목을 씁니다.

| 클레임 | 뜻 |
|--------|----|
| `iss` | 발급자 |
| `sub` | 주체(사용자 식별자) |
| `aud` | 이 토큰을 받아야 하는 대상 |
| `exp` | 이 시각 이후에는 받아들이면 안 되는 만료 시각 |
| `nbf` | 이 시각 이전에는 받아들이면 안 되는 시각 |
| `iat` | 발급 시각 |
| `jti` | 토큰 고유 ID(재사용 방지용) |

시각은 1970-01-01 UTC부터의 초 단위 정수(NumericDate)입니다. 밀리초가 아닙니다.

검증은 서명 확인에서 끝나지 않습니다. RFC 8725(JWT 모범 사례)를 따라 다음을 모두 확인합니다.

- 서명을 서버가 정한 알고리즘과 키로 검증합니다. 토큰 header의 `alg`를 믿고 알고리즘을 고르면 안 됩니다. `alg`를 `none`으로 바꾸거나 RS256 토큰을 HS256으로 바꿔 서명을 우회하는 공격이 있습니다.
- `exp`가 지났으면 거부합니다. `nbf`도 확인합니다.
- `iss`가 기대한 발급자인지, `aud`에 자기 서비스가 있는지 확인합니다. 다른 서비스용 토큰이 통과하는 것을 막습니다.
- 대칭 키(HS256)는 추측할 수 없는 무작위 값이어야 합니다. 사람이 외울 수 있는 문자열을 쓰면 무차별 대입으로 깨집니다.
- 여러 서비스가 검증만 해야 하면 비대칭 키(RS256, ES256)로 발급 서버만 개인 키를 갖게 합니다.

```js
const sig = (h, b) => createHmac('sha256', secret)
  .update(`${h}.${b}`).digest()

function verify(token) {
  const [h, b, s] = token.split('.')
  const header = JSON.parse(Buffer.from(h, 'base64url'))
  if (header.alg !== 'HS256') throw new Error('alg')
  const given = Buffer.from(s, 'base64url')
  const want = sig(h, b)
  if (given.length !== want.length) throw new Error('sig')
  if (!timingSafeEqual(given, want)) throw new Error('sig')
}
```

이 코드는 서명과 알고리즘 검증까지입니다. 이어서 payload를 파싱해 `exp`, `iss`, `aud`를 확인해야 합니다. 직접 만들기보다 검증된 라이브러리를 씁니다. 예를 들어 `jose`는 Node.js와 브라우저, Deno, Bun 등에서 JWT·JWS·JWE·JWK를 다루고, `jwtVerify(jwt, secret, { issuer, audience })`로 발급자와 대상까지 확인합니다.

**흔한 실수:**

- `jwt.decode`처럼 서명을 확인하지 않는 디코딩 함수 결과를 인증된 값으로 쓰는 것입니다.
- 만료를 몇 달로 길게 잡는 것입니다. 유출되면 만료까지 폐기할 수 없습니다.
- 사용자의 권한을 토큰에 넣고 그대로 믿는 것입니다. 권한을 바꿔도 이미 발급된 토큰에는 반영되지 않습니다.

## access·refresh 토큰

access 토큰은 API 요청에 쓰는 짧은 수명의 토큰이고, refresh 토큰은 새 access 토큰을 받기 위한 긴 수명의 토큰입니다. RFC 6749는 refresh 토큰을 access 토큰이 만료됐을 때 사용자가 다시 로그인하지 않고 새로 받는 용도로 정의합니다.

| 항목 | access 토큰 | refresh 토큰 |
|------|-------------|--------------|
| 수명 | 분 단위(예: 15분) | 일 단위 이상 |
| 전송 대상 | 모든 API 요청 | 토큰 재발급 엔드포인트 하나 |
| 검증 | 서명 검증(저장소 불필요) | 서버 저장소 조회 |
| 폐기 | 만료를 기다림 | 저장소에서 삭제 |

- access 토큰의 수명을 짧게 해 유출 피해 기간을 줄이고, 폐기는 서버가 저장한 refresh 토큰을 지워서 합니다. 이렇게 해서 자기 완결형 토큰의 폐기 문제를 완화합니다.
- refresh 토큰은 DB에 평문이 아닌 해시로 저장하는 편이 안전합니다. 유출돼도 그대로 쓸 수 없습니다.
- 회전(rotation)은 refresh 토큰을 쓸 때마다 새 토큰을 발급하고 이전 것을 무효로 하는 방식입니다. RFC 9700은 공개 클라이언트(브라우저 앱, 모바일 앱)가 발신자 제한이나 회전을 써야 한다고 정합니다. 이미 쓴 refresh 토큰이 다시 오면 탈취로 보고 그 사용자의 토큰 계열을 모두 폐기하는 것이 일반적입니다.
- 브라우저 앱에서는 access 토큰을 메모리에 두고, refresh 토큰은 `HttpOnly` 쿠키에 담아 재발급 경로(`Path`)에서만 전송하는 구성이 흔합니다. 쿠키이므로 그 엔드포인트는 CSRF를 막아야 합니다(자세히는 09편).

```js
// POST /auth/refresh
const old = refreshStore.take(refreshToken) // 조회와 삭제를 한 번에
if (!old) return res.writeHead(401).end()
const next = issueRefresh(old.userId)       // 회전
const access = issueAccess(old.userId, 15 * 60)
```

**흔한 실수:** 회전 없이 refresh 토큰을 몇 달 동안 그대로 쓰게 두는 것입니다. 탈취당하면 그 기간 내내 새 access 토큰이 계속 발급됩니다.

## OAuth 2.0·OIDC 개요

OAuth 2.0은 사용자의 비밀번호를 넘기지 않고 제3의 앱에 자원 접근 권한을 위임하는 프레임워크입니다(RFC 6749). 네 가지 역할이 있습니다.

| 역할 | 뜻 | 예 |
|------|----|----|
| 리소스 소유자 | 접근을 허락하는 사용자 | 구글 계정 사용자 |
| 클라이언트 | 접근을 요청하는 앱 | 우리 서비스 |
| 인가 서버 | 사용자를 인증하고 토큰을 발급 | 구글 로그인 서버 |
| 리소스 서버 | 토큰을 받고 자원을 제공 | 구글 API |

OAuth 2.0은 인가를 위한 프로토콜입니다. "누구인가"를 알려 주는 로그인 표준이 OpenID Connect(OIDC)이고, OAuth 2.0 위에 얹은 신원 계층입니다. 요청에 `scope=openid`를 포함하면 access 토큰과 함께 ID 토큰이 옵니다.

| 항목 | access 토큰 | ID 토큰 |
|------|-------------|---------|
| 용도 | 리소스 서버 접근 | 클라이언트가 사용자를 확인 |
| 대상 | 리소스 서버 | 클라이언트 |
| 형식 | 불투명 문자열이거나 JWT | JWT |

ID 토큰의 필수 클레임은 `iss`, `sub`, `aud`(클라이언트의 `client_id`), `exp`, `iat`입니다. 클라이언트는 `iss`, `aud`, `exp`, `nonce`, 서명을 검증해야 하고, 더 많은 사용자 정보는 access 토큰으로 UserInfo 엔드포인트에서 가져옵니다.

현재 웹과 모바일 앱의 표준 흐름은 인가 코드(authorization code) 방식에 PKCE를 더한 것입니다.

1. 클라이언트가 사용자를 인가 서버의 인가 엔드포인트로 보냅니다. 요청에는 `response_type=code`, `client_id`, `redirect_uri`, `scope`, `state`, PKCE 값이 들어갑니다.
2. 사용자가 인가 서버에서 로그인하고 동의합니다.
3. 인가 서버가 `redirect_uri`로 일회용 코드와 `state`를 돌려보냅니다.
4. 클라이언트가 `state`가 처음 보낸 값과 같은지 확인하고, 토큰 엔드포인트에 `grant_type=authorization_code`로 코드와 PKCE 검증값을 보내 토큰을 받습니다.

PKCE(RFC 7636)는 코드가 중간에서 가로채여도 토큰으로 바꾸지 못하게 합니다. 클라이언트가 요청마다 무작위 `code_verifier`를 만들고, 그 해시인 `code_challenge`를 1단계에서 보냅니다. 4단계에서 원본 `code_verifier`를 보내므로 코드만 훔친 공격자는 교환할 수 없습니다. 길이는 43–128자(32바이트를 base64url로 인코딩하면 43자)이고 S256 방식(SHA-256 후 base64url)을 씁니다.

```js
const verifier = randomBytes(32).toString('base64url')
const challenge = createHash('sha256')
  .update(verifier).digest('base64url')
const state = randomBytes(16).toString('base64url')
// 세션에 verifier와 state를 저장하고 인가 URL로 이동한다
```

- RFC 9700(OAuth 2.0 보안 모범 사례)은 인가 코드 흐름에 PKCE를 모든 클라이언트에 권하고, 공개 클라이언트에는 필수로 둡니다. 리디렉션 URI는 등록된 값과 정확히 문자열이 일치할 때만 허용해야 합니다.
- 암시적(implicit) 승인은 쓰지 말고(SHOULD NOT), 리소스 소유자 비밀번호 자격 증명 승인은 쓰면 안 됩니다(MUST NOT).
- 클라이언트 자격 증명(client credentials) 승인은 사용자 없이 서버가 자기 이름으로 접근할 때 씁니다.
- 인가·토큰 엔드포인트는 TLS가 필수입니다.
- `state`는 요청과 응답을 묶는 값으로, 확인하지 않으면 공격자가 자기 코드를 피해자 세션에 끼워 넣을 수 있습니다.

**흔한 실수:** 소셜 로그인으로 받은 access 토큰을 우리 서비스의 로그인 증명으로 쓰는 것입니다. 그 토큰은 다른 서비스의 API를 부르기 위한 것입니다. 사용자 확인은 ID 토큰을 검증해서 하고, 이후 우리 서비스의 세션이나 토큰을 새로 발급합니다.

## 인가

인가(authorization)는 인증된 사용자가 이 작업을 해도 되는지 판단하는 일입니다. 인증이 끝난 뒤의 단계이고, 거부 응답은 `403`입니다.

| 상태 | 뜻 | 상황 |
|------|----|------|
| `401` | 인증 안 됨 | 자격 증명이 없거나 유효하지 않음 |
| `403` | 권한 없음 | 누구인지는 알지만 허용되지 않음 |

- 다른 사용자의 자원이 있는지 존재 자체를 숨기려면 `403` 대신 `404`를 줄 수도 있습니다. 서비스 정책으로 정합니다.
- OWASP의 원칙은 세 가지입니다. 최소 권한(필요한 만큼만 부여), 기본 거부(허용을 명시한 것만 통과), 모든 요청에서 검사(한 번이라도 빠지면 뚫림)입니다.
- 인가 검사는 서버에서 해야 합니다. 클라이언트에서 버튼을 숨기는 것은 사용성일 뿐 보안이 아닙니다.
- 인가는 두 층입니다. 엔드포인트 단위(관리자만 이 경로에 접근)와 객체 단위(이 주문이 내 주문인가)입니다.

```js
// 객체 단위 인가: 소유자인지 확인한다
const order = await db.findOrder(req.params.id)
if (!order || order.userId !== user.id) {
  return res.writeHead(404).end()
}
```

**흔한 실수:** 객체 단위 검사를 빠뜨리는 것입니다. 경로의 ID만 바꿔도 남의 데이터가 열리는 IDOR(insecure direct object reference) 취약점이 됩니다. 로그인했다는 사실만으로 통과시키지 않고, 매번 소유자나 권한을 조회해서 비교합니다.

## RBAC

RBAC(Role-Based Access Control)는 권한을 역할에 묶고 사용자에게 역할을 부여하는 모델입니다. 사용자와 권한을 직접 잇지 않아서 관리가 단순합니다.

```js
const grants = new Map([
  ['admin', ['user:read', 'user:write']],
  ['member', ['user:read']],
])
const can = (user, perm) =>
  user.roles.some((r) => grants.get(r)?.includes(perm))

can({ roles: ['member'] }, 'user:write') // false
```

- 코드에서는 역할 이름이 아니라 권한(`user:write`)을 검사합니다. 역할을 새로 만들거나 합쳐도 검사 코드가 바뀌지 않습니다.
- 역할을 JWT 클레임에 넣으면 편하지만, 역할 변경이 토큰 만료까지 반영되지 않습니다. 짧은 access 토큰 수명이나 서버 조회로 보완합니다.
- 알 수 없는 역할이나 빈 권한은 거부합니다(기본 거부).

OWASP는 RBAC가 단순하지만 세밀한 판단에는 약하고 역할이 늘면 관리가 어려워진다고 설명합니다. 대안은 다음과 같습니다.

| 모델 | 판단 근거 | 적합한 경우 |
|------|-----------|-------------|
| RBAC | 사용자의 역할 | 직무별 권한이 뚜렷한 관리 도구 |
| ABAC | 역할, 시간, 위치, 기기 같은 속성의 조합 | 복잡한 조건, 멀티 테넌트 |
| ReBAC | 사용자와 자원의 관계 | 문서 공유, 소셜 서비스 |

가드 단위로 인가를 걸어 주는 방식은 프레임워크가 제공합니다(자세히는 15편).

## 핵심 정리

- 인증은 누구인지 확인(실패는 `401`)이고 인가는 해도 되는지 판단(실패는 `403`)이며, 인가는 서버에서 모든 요청과 모든 객체에 적용합니다.
- 비밀번호는 솔트를 넣어 Argon2id, scrypt 같은 느린 해시로 저장하고 `timingSafeEqual`로 비교하며, 동기 함수는 핸들러에서 쓰지 않습니다.
- 세션은 무작위 ID만 쿠키로 보내고 상태는 서버에 두어 즉시 폐기할 수 있고, 토큰은 서버 상태 없이 검증하는 대신 만료 전 폐기가 어렵습니다.
- JWT는 서명되지만 암호화되지 않으므로 payload에 비밀을 넣지 않고, 서버가 정한 알고리즘으로 서명을 검증한 뒤 `exp`, `iss`, `aud`까지 확인합니다.
- access 토큰은 짧게, refresh 토큰은 서버에 저장해 회전하며 폐기 수단으로 씁니다.
- OAuth 2.0은 권한 위임, OIDC는 그 위의 로그인 계층이며 표준 흐름은 인가 코드와 PKCE입니다. 역할 기반 인가(RBAC)는 역할이 아니라 권한을 검사합니다.

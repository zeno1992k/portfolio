## URL 파싱

`req.url`은 요청 시작줄의 요청 대상(request-target) 문자열입니다. 서버가 받는 값은 경로와 쿼리뿐이고(`/status?name=ryan`), 스킴·호스트는 없으며 프래그먼트(`#...`)는 브라우저가 보내지 않습니다(`req.url`은 04편). 기준 URL을 붙여 `URL`로 파싱합니다.

```js
const url = URL.parse(req.url, 'http://localhost')
if (!url) return send(res, 400)
url.pathname // '/status'
url.search   // '?name=ryan'
```

- 기준 URL은 코드에 고정한 문자열입니다. `Host` 헤더는 클라이언트가 마음대로 보낼 수 있어서 기준으로 쓰지 않습니다(자세히는 11편).
- `URL.parse()`는 파싱에 실패하면 `null`을 돌려줍니다(Node 22.1.0 추가). `new URL()`은 같은 경우 `TypeError`를 던지므로 요청 핸들러에서는 `null` 검사가 편합니다.
- `req.url`이 `//`로 시작하면 기준 URL의 호스트가 무시됩니다.

```js
const url = new URL('//evil.com/x', 'http://localhost')
url.hostname // 'evil.com'
url.pathname // '/x'
```

그래서 요청 URL에서는 `pathname`과 `search`만 쓰고 `host`·`origin`은 신뢰하지 않습니다.

## 쿼리스트링

쿼리스트링은 `?` 뒤에서 `#` 앞까지의 부분으로, `key=value`를 `&`로 이은 문자열입니다. `url.searchParams`가 이를 `URLSearchParams` 객체로 파싱해 줍니다.

```js
const href = '/p?page=2&tag=a&tag=b&q=a+b'
const sp = new URL(href, 'http://x').searchParams
sp.get('page')    // '2'
sp.getAll('tag')  // ['a', 'b']
sp.get('none')    // null
sp.has('tag', 'b') // true
sp.get('q')       // 'a b'
```

| 메서드 | 동작 |
|--------|------|
| `get(name)` | 첫 값, 없으면 `null` |
| `getAll(name)` | 같은 이름의 모든 값 배열 |
| `has(name[, value])` | 존재 여부(`value`는 Node 20.2.0 추가) |
| `size` | 항목 수(Node 19.8.0 추가) |
| `append`·`set`·`delete` | 추가·교체·삭제 |
| `toString()` | 인코딩된 문자열로 되돌림 |

- 값은 항상 문자열입니다. 퍼센트 인코딩은 풀리고 `+`는 공백이 됩니다.
- `Object.fromEntries(sp)`는 같은 이름의 값 중 마지막 하나만 남깁니다. 반복되는 키가 필요하면 `getAll`을 씁니다.
- 레거시 `node:querystring` 대신 `URLSearchParams`를 씁니다(자세히는 22편).

**흔한 실수:** 문자열을 숫자로 착각하는 것입니다.

```js
sp.get('page') + 1         // '21' (문자열 이어 붙임)
Number(sp.get('none'))     // 0 (null이 0으로 변환됨)
Number(sp.get('page') ?? '1') // ✅ 없으면 1
```

숫자 변환과 범위 검사는 검증 단계에서 합니다(자세히는 08편).

## WHATWG URL

`URL`은 브라우저와 같은 WHATWG URL Standard를 구현한 클래스입니다. 전역으로 쓸 수 있고 `node:url`에서도 가져올 수 있습니다. `node:url` 모듈은 Stable(Stability 2)입니다.

```js
const raw = 'http://User@EXAMPLE.com:80/a/./b/../c?x=1#h'
const u = new URL(raw)
u.href     // 'http://User@example.com/a/c?x=1#h'
u.origin   // 'http://example.com'
u.port     // '' (스킴의 기본 포트는 빈 문자열)
```

| 속성 | 값의 모양 |
|------|-----------|
| `protocol` | `'http:'` (콜론 포함) |
| `host` / `hostname` | `'localhost:3000'` / `'localhost'` |
| `port` | `'3000'` 또는 `''` |
| `pathname` | `'/a/c'` (항상 `/`로 시작) |
| `search` | `'?x=1'` (없으면 `''`) |
| `hash` | `'#h'` (없으면 `''`) |
| `searchParams` | `URLSearchParams` |

- 파싱하면서 호스트를 소문자로 바꾸고, 기본 포트를 지우고, 경로의 `.`·`..` 세그먼트를 제거합니다. `/a/%2e%2e/b`도 `/b`가 됩니다.
- 경로의 `%2F`는 디코딩되지 않습니다. `/a%2Fb`는 그대로이고 `decodeURIComponent`를 거쳐야 `/a/b`가 됩니다.
- 파싱 방식은 세 가지입니다.

| 방식 | 실패 시 |
|------|---------|
| `new URL(input, base)` | `TypeError`(`ERR_INVALID_URL`) |
| `URL.canParse(input, base)` | `false` (Node 19.9.0 추가) |
| `URL.parse(input, base)` | `null` (Node 22.1.0 추가) |

- 레거시 `url.parse()`는 Legacy(Stability 3)입니다. Node 24.0.0부터 `node_modules` 밖의 코드에서 호출하면 DEP0169 경고가 뜹니다. 파싱 동작이 표준이 아니고 보안 문제로 이어질 수 있다는 이유이며, 이 취약점에는 CVE도 발급되지 않습니다. `url.format()`·`url.resolve()`도 같은 레거시 API입니다.

## 라우팅을 직접 나누기

라우팅은 메서드와 경로를 보고 어떤 핸들러를 실행할지 고르는 일입니다. 프레임워크 없이는 경로를 키로 한 표를 만들면 됩니다.

```js
const table = {
  '/users': { GET: listUsers, POST: createUser },
  '/health': { GET: health },
}
const methods = Object.hasOwn(table, url.pathname)
  ? table[url.pathname]
  : null
```

- `methods`가 `null`이면 경로 자체가 없으니 404, 경로는 있는데 메서드 핸들러가 없으면 405입니다(아래 두 절).
- 객체 키 조회에는 `Object.hasOwn`을 씁니다. `table['constructor']`처럼 프로토타입의 프로퍼티가 걸려 나오는 것을 막기 위해서입니다.
- `/users/42`처럼 경로에 값이 들어가는 패턴은 `startsWith`와 `split('/')`로 나누거나 정규식·`URLPattern`을 씁니다(아래 `URLPattern` 절).
- `/users`와 `/users/`를 같은 경로로 볼지 정해야 합니다. 정하지 않으면 한쪽이 404가 됩니다. 한쪽으로 redirect하는 것이 일반적입니다.
- 라우팅 표가 커지면 미들웨어와 라우터가 필요해집니다(자세히는 12편).

## 404

404 Not Found는 대상 리소스를 찾지 못했다는 응답입니다. 라우팅 표에 경로가 없거나, 정적 파일이 없을 때 보냅니다.

```js
function notFound(res) {
  const body = JSON.stringify({ error: 'not_found' })
  res.writeHead(404, {
    'Content-Type': 'application/json; charset=utf-8',
    'Content-Length': Buffer.byteLength(body),
  })
  res.end(body)
}
```

- 모든 경로의 마지막 분기에서 반드시 응답해야 합니다. 응답하지 않으면 클라이언트는 연결이 끊기거나 타임아웃이 날 때까지 기다립니다.
- 접근 권한이 없는 리소스의 존재를 숨기려고 403 대신 404를 쓰기도 합니다.

## 405

405 Method Not Allowed는 경로는 있지만 그 메서드를 지원하지 않는다는 응답입니다. 서버는 반드시 `Allow` 헤더에 지원하는 메서드 목록을 넣어야 합니다.

```js
if (!methods) return notFound(res)
const handler = Object.hasOwn(methods, req.method)
  ? methods[req.method]
  : null
if (!handler) {
  const allow = Object.keys(methods).join(', ')
  res.writeHead(405, { Allow: allow })
  return res.end()
}
```

- `Allow: GET, POST`처럼 쉼표로 이어 씁니다.
- `GET`을 지원하면 `HEAD`도 지원하는 것이 관례입니다. HEAD 응답은 본문 없이 헤더만 보내고, `Allow`에도 `HEAD`를 넣습니다. Node는 `HEAD` 요청에 `res.end(body)`를 해도 본문을 보내지 않습니다.
- 405와 404를 구분하지 않으면 클라이언트는 URL 오타인지 메서드 오류인지 알 수 없습니다.

## 정적 파일

정적 파일 서빙은 URL 경로를 디스크 경로로 바꿔 파일 내용을 응답 본문으로 보내는 일입니다. 파일 전체를 읽어 올리지 않고 스트림으로 흘려 보냅니다(`pipeline`은 02편).

```js
import { createReadStream } from 'node:fs'
import { stat } from 'node:fs/promises'
import { pipeline } from 'node:stream/promises'

const st = await stat(file)        // 없으면 ENOENT
if (!st.isFile()) return notFound(res)
const type = TYPES[path.extname(file)]
res.writeHead(200, {
  'Content-Type': type ?? 'application/octet-stream',
  'Content-Length': st.size,
})
await pipeline(createReadStream(file), res)
```

- `Content-Type`는 확장자로 정합니다. 표(`TYPES`)에 없는 확장자는 `application/octet-stream`으로 보냅니다.
- 요청 경로가 디렉터리를 가리키면 `index.html`을 찾습니다. 슬래시 없이 디렉터리를 요청하면 슬래시를 붙여 redirect합니다(아래 `redirect` 절).
- 헤더를 보낸 뒤 스트림이 실패하면 상태 코드를 바꿀 수 없습니다. 연결을 `res.destroy()`로 끊습니다.
- `stat`과 `createReadStream` 사이에 파일이 지워질 수 있으므로 `ENOENT`는 두 곳 모두에서 처리합니다.
- 운영 환경에서는 Nginx나 CDN이 정적 파일을 맡는 것이 일반적입니다. 직접 구현하는 것은 원리를 이해하기 위해서입니다(프레임워크의 정적 미들웨어는 12편).

**흔한 실수:** `readFile`로 파일 전체를 메모리에 올려 보내는 것입니다. 큰 파일 몇 개를 동시에 요청받으면 메모리가 폭발합니다(자세히는 27편).

## 경로 탈출 막기

경로 탈출(path traversal)은 `../`를 이용해 공개 폴더 밖의 파일을 읽어 가는 공격입니다. URL 파서가 `..` 세그먼트를 제거하지만 `%2f`로 인코딩된 슬래시는 남기 때문에, 디코딩한 뒤에 다시 검사해야 합니다.

```js
const ROOT = await realpath('public')

function toFilePath(pathname) {
  let rel
  try { rel = decodeURIComponent(pathname) }
  catch { return null }
  if (rel.includes('\0')) return null
  const abs = path.join(ROOT, rel)
  const prefix = ROOT + path.sep
  const inside = abs === ROOT || abs.startsWith(prefix)
  return inside ? abs : null
}
```

`/..%2fsecret.txt`는 디코딩하면 `/../secret.txt`이고 `path.join`이 `ROOT` 밖으로 올라갑니다. 마지막 비교가 이를 걸러냅니다. 요청별 결과는 다음과 같았습니다.

| 요청 경로 | 결과 |
|-----------|------|
| `/..%2fsecret.txt` | 밖으로 나가므로 `null`, 404 |
| `/%2e%2e%2fsecret.txt` | 같음 |
| `/%E0%A4%A` | `decodeURIComponent`가 `URIError`, `null` |
| `/ten.txt%00` | `\0` 포함, `null` (검사하지 않으면 `fs`가 에러를 던져 500) |

- `ROOT + path.sep`로 비교해야 합니다. `ROOT`가 `/srv/public`일 때 `startsWith('/srv/public')`만 보면 `/srv/public-secret/x`도 통과합니다.
- `path.join(ROOT, rel)`은 `rel`이 `/`로 시작해도 `ROOT` 아래에 붙입니다. 반면 `path.resolve(ROOT, rel)`은 `rel`이 절대 경로이면 `ROOT`를 버립니다(`path.resolve('/srv/public', '/etc/passwd')`는 `/etc/passwd`).
- 심볼릭 링크는 `path.join`이 따라가지 않습니다. 공개 폴더 안의 링크가 밖을 가리킬 수 있으므로 열기 전에 `realpath`로 실제 경로를 얻어 한 번 더 검사합니다.
- `.env` 같은 점(`.`)으로 시작하는 파일은 따로 막습니다.
- Windows는 `\`도 구분자이므로 `..\..\`로도 탈출을 시도할 수 있습니다. `path.join`이 정규화하므로 같은 검사로 막힙니다.

## redirect

redirect는 `Location` 헤더에 새 주소를 담은 3xx 응답으로 클라이언트에게 다른 주소로 다시 요청하게 하는 것입니다.

```js
function redirect(res, status, location) {
  res.writeHead(status, { Location: location })
  res.end()
}
redirect(res, 308, '/docs/' + url.search)
```

| 코드 | 의미 | 메서드 |
|------|------|--------|
| 301 | 영구 이동 | POST가 GET으로 바뀔 수 있음 |
| 308 | 영구 이동 | 바뀌지 않음 |
| 302 | 임시 이동 | POST가 GET으로 바뀔 수 있음 |
| 307 | 임시 이동 | 바뀌지 않음 |
| 303 | 다른 주소를 GET으로 조회 | 항상 GET |

- 구분 기준은 두 가지입니다. 주소가 영구적으로 바뀌면 301·308, 임시이면 302·307·303입니다. 메서드와 본문을 유지해야 하면 307·308입니다.
- 폼 제출(POST) 뒤에 결과 페이지로 보낼 때는 303을 씁니다. 새로고침이 POST를 다시 보내지 않게 하기 위해서입니다.
- `Location`에는 `/docs/`처럼 상대 경로를 써도 됩니다. 쿼리를 잃지 않으려면 `url.search`를 붙입니다.

**흔한 실수:** 요청에서 받은 주소로 그대로 redirect하는 것입니다(open redirect). `?next=//evil.com`을 그대로 `Location`에 넣으면 공격자의 사이트로 보내게 됩니다. 같은 origin의 경로인지 검사합니다.

```js
function safeNext(next) {
  const base = 'http://localhost'
  const u = new URL(next ?? '/', base)
  return u.origin === base ? u.pathname + u.search : '/'
}
safeNext('/a?b=1')       // '/a?b=1'
safeNext('//evil.com/x') // '/'
safeNext('https://evil.com') // '/'
```

## URLPattern

`URLPattern`은 URL의 각 부분을 패턴과 맞춰 보고 이름 붙인 그룹을 꺼내 주는 전역 클래스입니다. Node 23.8.0에 추가되었고 Stability 1(Experimental)입니다. 문서 기준으로 Node 24와 현재 개발 문서(main) 모두 Experimental이며, 로컬 Node 24.15에서는 플래그 없이 전역으로 쓸 수 있었습니다.

```js
const p = new URLPattern({ pathname: '/users/:id' })
p.test({ pathname: '/users/42' })           // true
p.exec({ pathname: '/users/42' }).pathname.groups
// { id: '42' }
p.test({ pathname: '/users' })              // false
```

| 문법 | 의미 | 예 |
|------|------|----|
| `:name` | 이름 있는 그룹(슬래시를 뺀 한 세그먼트) | `/users/:id` |
| `*` | 와일드카드 | `/files/*`가 `a/b.txt`를 잡음 |
| `(정규식)` | 그룹의 매칭 규칙을 정규식으로 지정 | `/users/:id([0-9]+)` |
| `{...}?` | 선택적 부분 | `/posts{/:id}?` |

- 메서드 정보는 없으므로 405 처리는 직접 합니다. `URLPattern`은 경로에서 값을 꺼내는 데만 씁니다.
- `/users/:id`는 `/users/`(빈 값)와 `/users/42/`(끝 슬래시)에 맞지 않습니다.
- `new URLPattern('/users/:id', 'http://localhost')`처럼 문자열과 기준 URL로도 만들 수 있고, 그때는 `exec`에 전체 URL 문자열을 넘깁니다. `ignoreCase` 옵션으로 대소문자를 무시할 수 있습니다.
- Node 24.15에서 확인한 결과, `:id(\\d+)`는 정규식 `\d`가 아니라 글자 `d`로 해석되어 숫자가 매칭되지 않았습니다. `[0-9]`를 썼을 때는 의도대로 동작했습니다.
- Experimental이므로 운영 코드에서는 동작 변경에 대비해야 합니다.

## ETag와 조건부 요청

ETag는 리소스의 한 버전을 나타내는 식별자이고, 조건부 요청은 그 식별자가 바뀌지 않았으면 본문을 다시 보내지 않는 방식입니다. 서버는 응답에 `ETag`를 넣고, 클라이언트는 다음 요청에 그 값을 `If-None-Match`로 돌려보냅니다. 값이 같으면 서버는 본문 없이 304 Not Modified를 보냅니다.

```js
const etag = `W/"${st.size}-${Math.trunc(st.mtimeMs)}"`
const inm = req.headers['if-none-match']
if (inm && etagMatches(inm, etag)) {
  res.writeHead(304, { ETag: etag })  // 본문 없음
  return res.end()
}
```

```js
const bare = (t) => t.trim().replace(/^W\//, '')
function etagMatches(header, etag) {
  if (header.trim() === '*') return true
  const tags = header.split(',')
  return tags.some((t) => bare(t) === bare(etag))
}
```

- `ETag` 값은 큰따옴표로 감싸며, 앞에 `W/`가 붙으면 약한(weak) 검증자입니다. 약한 ETag는 의미가 같으면 같은 것으로 보고, 강한 ETag는 바이트가 같아야 같다고 봅니다.
- 위 코드는 크기와 수정 시각으로 만들기 때문에 내용 해시가 아니라 약한 ETag로 표시했습니다. 강한 ETag는 내용을 해시해야 해서 큰 파일에서는 비용이 큽니다.
- `If-None-Match`는 약한 비교를 쓰고, 목록(`"a", "b"`)과 `*`를 받을 수 있습니다.
- 조건이 맞으면(리소스가 같으면) 304이고, 아니면 평소처럼 200으로 전체를 보냅니다. 304 응답에는 200이었다면 보냈을 `ETag`, `Cache-Control`, `Vary` 같은 헤더를 포함해야 합니다.
- GET과 HEAD에서만 304를 씁니다. 쓰기 메서드에서 조건이 어긋나면 412 Precondition Failed입니다(`If-Match`와 함께 동시 수정 충돌을 막는 데 씁니다).
- 날짜 기반 짝도 있습니다. 응답에 `Last-Modified`를 넣으면 클라이언트가 `If-Modified-Since`를 보냅니다. 둘 다 오면 `If-None-Match`가 우선합니다.

| 검증자 | 응답 헤더 | 요청 헤더 |
|--------|-----------|-----------|
| 식별자 | `ETag` | `If-None-Match` |
| 시각 | `Last-Modified` | `If-Modified-Since` |

## Range 요청

Range 요청은 리소스의 일부 바이트만 요청하는 것으로, 동영상 탐색과 이어받기에 쓰입니다. 서버가 지원하면 응답에 `Accept-Ranges: bytes`를 넣고, 요청이 `Range: bytes=시작-끝`으로 오면 206 Partial Content로 그 구간만 보냅니다.

| 요청 | 의미 |
|------|------|
| `bytes=0-499` | 처음 500바이트 |
| `bytes=500-` | 500번째부터 끝까지 |
| `bytes=-100` | 마지막 100바이트 |

바이트 위치는 0부터 시작하고 끝 위치도 포함합니다. `fs.createReadStream`의 `start`·`end`도 둘 다 포함이라 그대로 대응합니다. 10바이트 파일(`0123456789`)로 확인한 결과는 다음과 같습니다.

| Range | 상태 | 본문 | Content-Range |
|-------|------|------|---------------|
| `bytes=2-5` | 206 | `2345` | `bytes 2-5/10` |
| `bytes=-3` | 206 | `789` | `bytes 7-9/10` |
| `bytes=2-99` | 206 | `23456789` | `bytes 2-9/10` |
| `bytes=20-30` | 416 | 없음 | `bytes */10` |
| `bytes=0-1,3-4` | 200 | 전체 | 없음 |

범위를 해석하는 함수는 세 가지 결과를 돌려줍니다. 구간이면 객체, 무시해야 하면 `null`, 만족할 수 없으면 `false`입니다.

```js
function parseRange(header, size) {
  const m = /^bytes=(\d*)-(\d*)$/.exec(header ?? '')
  if (!m || (!m[1] && !m[2])) return null // 무시, 200
  let start = m[1] ? Number(m[1]) : size - Number(m[2])
  let end = m[1] && m[2] ? Number(m[2]) : size - 1
  start = Math.max(start, 0)
  end = Math.min(end, size - 1)
  if (start > end) return false           // 416
  return { start, end }
}
```

```js
const size = st.size
const range = parseRange(req.headers.range, size)
if (range === false) {
  res.writeHead(416, { 'Content-Range': `bytes */${size}` })
  return res.end()
}
const { start, end } = range ?? { start: 0, end: size - 1 }
const head = { 'Accept-Ranges': 'bytes' }
head['Content-Length'] = end - start + 1
const cr = `bytes ${start}-${end}/${size}`
if (range) head['Content-Range'] = cr
res.writeHead(range ? 206 : 200, head)
await pipeline(createReadStream(file, { start, end }), res)
```

- 206 응답에는 `Content-Range: bytes 시작-끝/전체크기`를 넣고, `Content-Length`는 구간의 길이(`끝 - 시작 + 1`)입니다.
- 범위를 만족할 수 없으면 416이고 `Content-Range: bytes */전체크기`를 보냅니다.
- 서버는 `Range`를 무시하고 200으로 전체를 보내도 됩니다. 알 수 없는 단위(`items=...`)는 반드시 무시해야 합니다. 위 코드는 여러 구간(`0-1,3-4`)도 무시하고 전체를 보내는 단순한 선택입니다. 여러 구간을 처리하려면 `multipart/byteranges` 응답이 필요합니다.
- `Range`는 GET에서만 의미가 있고, 조건부 요청의 평가 뒤에 처리합니다. 304가 나는 요청에서는 `Range`가 무시됩니다.
- `If-Range`는 `Range`에 조건을 붙입니다. 리소스가 그대로이면 구간을, 바뀌었으면 전체를 보냅니다. 이 비교는 강한 비교만 인정하므로 약한 `W/` ETag는 맞지 않아 항상 200이 됩니다. 이어받기를 제대로 지원하려면 강한 ETag나 `Last-Modified`가 필요합니다.
- 빈 파일은 `end`가 -1이 되어 `createReadStream`이 `ERR_OUT_OF_RANGE`를 던집니다. 크기 0은 먼저 `Content-Length: 0`으로 끝냅니다.
- 압축한 응답에서 바이트 위치는 압축된 바이트 기준입니다.

## 핵심 정리

- `req.url`은 경로와 쿼리뿐이므로 고정 기준 URL과 함께 `URL.parse`로 해석하고, 요청 URL의 `host`는 신뢰하지 않습니다.
- 쿼리 값은 항상 문자열이며 없으면 `null`입니다. 레거시 `url.parse`와 `querystring` 대신 `URL`과 `URLSearchParams`를 씁니다.
- 경로가 없으면 404, 경로는 있고 메서드가 없으면 405와 `Allow` 헤더입니다.
- 정적 파일은 디코딩 뒤 `path.join`과 `ROOT + path.sep` 비교로 경로 탈출을 막고, 스트림으로 보냅니다.
- redirect는 영구(301·308)와 임시(302·307·303), 메서드 유지(307·308)로 구분하며, 사용자가 준 주소로 그대로 보내지 않습니다.
- ETag와 `If-None-Match`는 304로, `Range`는 206과 416으로 응답합니다. `URLPattern`은 Experimental입니다.

## Node 전역 fetch

`fetch`는 브라우저와 같은 모양의 HTTP 요청 함수로, Node에서는 전역으로 제공됩니다. Node 18.0.0부터 플래그 없이 쓸 수 있고 Node 21.0.0부터 실험 단계가 아닙니다. 같은 전역으로 `Request`, `Response`, `Headers`, `FormData`도 있습니다.

```js
const res = await fetch('https://example.com/api/users')
console.log(res.status) // 200
const users = await res.json()
```

- 반환값은 `Response`로 이행하는 Promise입니다.
- 네트워크 오류나 잘못된 URL에서만 reject됩니다. 연결 거부는 `TypeError: fetch failed`이고 원인은 `err.cause`에 있습니다(`err.cause.code`는 `'ECONNREFUSED'`). 문자열 `'not a url'`은 `ERR_INVALID_URL`입니다.
- 서버가 404나 500으로 응답해도 reject되지 않습니다(아래 `res.ok` 절).
- 리다이렉트는 기본으로 따라갑니다. 로컬 서버에서 302를 따라가 최종 200을 받았고 `res.redirected`가 `true`였습니다.
- 기본 요청 헤더는 `user-agent: node`, `accept: */*`, `accept-encoding: gzip, deflate`, `connection: keep-alive` 등이며 압축 응답은 자동으로 풉니다.
- 기본 타임아웃이 사실상 없으므로 마감 시간은 직접 겁니다(아래 `AbortSignal` 절).

## undici

undici는 Node.js를 위해 처음부터 새로 쓴 HTTP/1.1 클라이언트이고, 전역 `fetch`가 이것을 구현으로 씁니다. Node 안에 번들되어 있으며 버전은 `process.versions.undici`로 확인합니다(Node 24.15에서 7.24.4).

- npm 패키지 `undici`를 따로 설치하면 번들보다 새 버전과 추가 API(`request()`, `Agent`, `Pool`, `ProxyAgent`, 인터셉터 등)를 쓸 수 있습니다.
- 번들된 undici의 클래스는 import할 수 없습니다. `node:undici`는 존재하지 않는 내장 모듈이라 `ERR_UNKNOWN_BUILTIN_MODULE`이 납니다. `Agent` 같은 클래스가 필요하면 npm 패키지를 설치합니다(아래 `undici Agent·Pool과 dispatcher` 절).
- `FormData`는 `fetch`와 같은 구현끼리 씁니다. 전역 `fetch`에는 전역 `FormData`, npm undici의 `fetch`에는 undici의 `FormData`를 씁니다. 섞으면 오류가 날 수 있습니다.

## fetch와 http.request 차이

둘 다 HTTP 요청을 보내지만 추상 수준이 다릅니다. `fetch`가 표준 객체와 Promise를 쓰는 고수준 API이고, `http.request`는 이벤트와 스트림을 직접 다루는 저수준 API입니다.

| 항목 | `fetch` | `http.request` |
|------|---------|----------------|
| 호출 방식 | Promise, `await` | 콜백과 이벤트, `req.end()` 직접 호출 |
| 요청·응답 객체 | `Request`, `Response` (웹 표준) | `ClientRequest`, `IncomingMessage` |
| 본문 | `res.json()`, `res.text()`, 웹 `ReadableStream` | `'data'` 이벤트, Node `Readable` |
| 4xx·5xx | reject하지 않음 | 에러 아님 |
| 리다이렉트 | 기본으로 따라감 | 따라가지 않고 3xx를 그대로 돌려줌 |
| 압축 해제 | 자동 | 하지 않음 (gzip 바이트가 그대로 옴) |
| 연결 풀 | undici `Agent` | `http.Agent` (06편) |
| 기본 타임아웃 | undici 기본값(헤더·본문 300초, 연결 10초) | 없음 |
| 프로토콜 | HTTP/1.1 | HTTP/1.1 |

- `fetch`로 같은 일을 훨씬 짧게 쓸 수 있어서 새 코드는 `fetch`를 기본으로 씁니다. 소켓 단위 제어나 `http.Agent` 설정이 필요할 때 `http.request`를 씁니다.
- 로컬에서 같은 서버에 요청했을 때 `http.get`은 302를 그대로 받았고, gzip 응답의 본문은 압축된 바이트(앞 두 바이트 `1f 8b`) 그대로 도착했습니다.
- 두 API의 연결 풀 설정은 서로 영향을 주지 않습니다. `http.Agent`를 조정해도 `fetch`에는 적용되지 않습니다.

## Request / Response

`Request`와 `Response`는 요청과 응답을 나타내는 웹 표준 클래스입니다. `fetch`는 `Request`나 URL을 받고 `Response`를 돌려줍니다.

```js
const res = await fetch(url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'kim' }),
  signal: AbortSignal.timeout(5000),
})
```

| 옵션 | 의미 |
|------|------|
| `method` | 메서드 (기본 `GET`) |
| `headers` | 객체, 배열, `Headers` |
| `body` | 문자열, `Buffer`, `Uint8Array`, `Blob`, `FormData`, `URLSearchParams`, `ReadableStream` |
| `signal` | 취소·타임아웃 (아래 `AbortSignal` 절) |
| `redirect` | `'follow'`(기본), `'manual'`(3xx를 그대로 받음), `'error'` |
| `dispatcher` | 연결을 담당할 undici 디스패처(아래 `undici Agent·Pool과 dispatcher` 절) |
| `duplex` | 스트림 본문을 보낼 때 `'half'` |

- 문자열 본문의 `Content-Type`은 `text/plain;charset=UTF-8`로 자동 설정됩니다. JSON은 헤더를 직접 지정해야 하며, 확인해 보니 서버에는 `text/plain`으로 도착했습니다.
- `Response`의 주요 속성은 `status`, `statusText`, `ok`, `headers`, `url`, `redirected`, `body`, `bodyUsed`입니다.
- 직접 만들 수도 있습니다. `new Response('hi', { status: 201 })`, `Response.json({ a: 1 })`(`Content-Type: application/json`이 붙음), `new Request(url, { method: 'PUT' })`입니다. 테스트에서 가짜 응답을 만들 때 유용합니다.
- 본문은 한 번만 읽을 수 있습니다. 읽은 뒤에는 `bodyUsed`가 `true`이고, 다시 읽으면 `TypeError: Body is unusable`입니다. 두 번 읽어야 하면 읽기 전에 `res.clone()`으로 복제합니다(자세히는 26편).

## 헤더 객체

`Headers`는 HTTP 헤더를 담는 컬렉션으로, 이름의 대소문자를 구분하지 않습니다. `res.headers`와 요청의 `headers` 옵션이 모두 이 타입입니다.

```js
const h = new Headers({ 'Content-Type': 'text/html' })
h.append('X-List', 'a')
h.append('X-List', 'b')
h.get('content-type') // 'text/html'
h.get('x-list')       // 'a, b'
h.has('CONTENT-TYPE') // true
```

| 메서드 | 동작 |
|--------|------|
| `get(name)` | 값 문자열, 없으면 `null`. 같은 이름이 여럿이면 `', '`로 이어 붙임 |
| `has(name)` | 존재 여부 |
| `set(name, value)` | 교체 |
| `append(name, value)` | 추가 |
| `delete(name)` | 삭제 |
| `getSetCookie()` | `Set-Cookie` 값 전체 배열 |

- 순회(`for...of`, `[...h]`)하면 이름이 소문자로, 정렬된 순서로 나옵니다.
- `Set-Cookie`는 값에 쉼표가 들어갈 수 있어서 `get()`으로 합치면 구분할 수 없습니다. 서버 환경에서는 `getSetCookie()`를 씁니다. `Object.fromEntries(h)`로 객체로 바꾸면 같은 이름의 헤더가 하나만 남습니다.
- `http.IncomingMessage`의 `res.headers`는 `Headers`가 아니라 소문자 키를 가진 일반 객체입니다(04편). 두 API의 접근 방식이 다릅니다.

## res.ok

`res.ok`는 상태 코드가 200–299이면 `true`인 불리언입니다. `fetch`는 4xx·5xx에도 reject하지 않으므로 이 값으로 직접 걸러야 합니다.

```js
const res = await fetch(url)
if (!res.ok) {
  throw new Error(`HTTP ${res.status} ${res.statusText}`)
}
const data = await res.json()
```

- 404 응답에서 `res.ok`는 `false`, `res.status`는 404, `res.statusText`는 `'Not Found'`이고 본문은 읽을 수 있었습니다. 에러 응답의 본문(JSON 에러 형식)을 읽어 메시지에 쓰는 일이 흔합니다.
- 리다이렉트를 따라갔다면 최종 응답이 기준입니다. `redirect: 'manual'`이면 302를 그대로 받고 `ok`는 `false`입니다.
- 네트워크 실패(reject)와 HTTP 오류 상태(resolve)를 같은 것으로 취급하면 안 됩니다. 둘을 구분해 처리합니다(자세히는 27편).

## res.json

`res.json()`은 본문을 끝까지 읽어 `JSON.parse`한 결과로 이행하는 Promise를 돌려줍니다.

```js
const user = await res.json()
user.name // 파싱된 객체의 값
```

- `Content-Type`을 검사하지 않습니다. 서버가 JSON 대신 HTML 에러 페이지를 주면 `SyntaxError`입니다. `Unexpected token`으로 시작하는 메시지가 이 경우입니다. `res.ok`를 먼저 확인합니다.
- 204처럼 본문이 없는 응답에 호출하면 `SyntaxError: Unexpected end of JSON input`입니다. 204는 `res.json()`을 호출하지 않습니다.
- 본문 전체를 메모리에 올립니다. undici 문서는 이 방식이 사용자 입력처럼 믿을 수 없는 출처의 본문에는 맞지 않으니 크기 제한을 두고 스트림으로 처리하라고 안내합니다.
- 파싱된 값의 형태는 보장되지 않습니다. 필요한 필드가 있는지는 검증해야 합니다(자세히는 08편).

## res.text

`res.text()`는 본문을 문자열로 읽습니다. 항상 UTF-8로 디코딩하며 `Content-Type`의 `charset`을 따르지 않습니다.

```js
const html = await res.text()
```

| 메서드 | 결과 |
|--------|------|
| `text()` | 문자열 (UTF-8) |
| `json()` | 파싱된 값 |
| `arrayBuffer()` | `ArrayBuffer` |
| `bytes()` | `Uint8Array` |
| `blob()` | `Blob` |

- 위 메서드는 모두 본문을 한 번만 읽고 전체를 메모리에 올립니다. 큰 파일은 아래 스트림 방식으로 읽습니다.
- UTF-8이 아닌 인코딩(EUC-KR 등)은 `arrayBuffer()`로 받아 `TextDecoder`로 직접 디코딩합니다.

## 스트림 응답

`res.body`는 웹 `ReadableStream`이어서 본문을 도착하는 대로 조각 단위로 처리할 수 있습니다. 본문이 없는 응답(204 등)에서는 `null`입니다.

```js
const res = await fetch(url)
let total = 0
for await (const chunk of res.body) {
  total += chunk.length // chunk는 Uint8Array
}
```

Node 스트림으로 바꿔 파일에 저장할 때는 `Readable.fromWeb()`과 `pipeline`을 씁니다(자세히는 02편).

```js
import { Readable } from 'node:stream'
import { pipeline } from 'node:stream/promises'
import { createWriteStream } from 'node:fs'

await pipeline(
  Readable.fromWeb(res.body),
  createWriteStream('out.bin'),
)
```

- 100000바이트 응답을 `Readable.fromWeb`으로 흘려 보냈을 때 100000바이트가 그대로 도착했습니다.
- 크기 제한은 읽으면서 합계를 세다가 넘으면 `break`로 빠져나옵니다. `for await`에서 `break`하면 스트림이 취소되어 연결도 정리됩니다. 이미 `for await`가 잠근 스트림에 `res.body.cancel()`을 호출하면 `ReadableStream is locked` 오류가 납니다.
- `res.headers.get('content-length')`는 미리 크기를 알려 주지만 거짓일 수 있으므로 실제로 읽은 바이트도 세어야 합니다.

## AbortSignal로 fetch 취소

`signal` 옵션에 `AbortSignal`을 넘기면 진행 중인 요청을 취소하거나 시간 제한을 걸 수 있습니다.

```js
const ac = new AbortController()
const p = fetch(url, { signal: ac.signal })
ac.abort() // 취소

await fetch(url, { signal: AbortSignal.timeout(3000) })
// 3초 뒤 TimeoutError
```

| 방법 | reject되는 에러 |
|------|-----------------|
| `ac.abort()` | `AbortError` (메시지 `This operation was aborted`) |
| `ac.abort(reason)` | `reason`으로 넘긴 값 |
| `AbortSignal.timeout(ms)` | `TimeoutError` (메시지 `The operation was aborted due to timeout`) |
| `AbortSignal.any([a, b])` | 먼저 중단된 쪽의 사유 (Node 20.3.0 추가) |

- 응답 헤더를 받은 뒤 본문을 읽는 중에 중단되어도 `res.text()` 등이 reject됩니다(수동 취소는 `AbortError`, 시간 초과는 `TimeoutError`). 그래서 마감 시간 하나로 헤더 대기와 본문 읽기를 함께 묶을 수 있습니다.
- 타임아웃을 구분해 처리하려면 `err.name === 'TimeoutError'`로 비교합니다.
- 사용자가 직접 취소하는 것과 시간 제한을 함께 쓰려면 `AbortSignal.any([ac.signal, AbortSignal.timeout(3000)])`입니다.
- `http.request`의 `signal`은 같은 신호를 받지만 에러가 `AbortError`이고 사유는 `err.cause`에 들어 있습니다(06편).

## https 모듈

`node:https`는 TLS 위에서 HTTP를 쓰는 모듈입니다(Stable). `http`와 API가 같고, 요청·서버 생성에 TLS 옵션이 더해집니다.

```js
import https from 'node:https'

https.get('https://example.com/', (res) => {
  console.log(res.statusCode)
  res.resume()
}).on('error', console.error)
```

| 항목 | 내용 |
|------|------|
| `https.request()`, `https.get()` | `http`와 같은 `ClientRequest`. 기본 포트 443, 기본 에이전트 `https.globalAgent` |
| `https.Agent` | `http.Agent` 옵션에 `maxCachedSessions`(TLS 세션 캐시 수, 기본 100), `servername` 추가 |
| `https.createServer(options, listener)` | `key`와 `cert`를 받는 HTTPS 서버 |
| 추가 옵션 | `tls.connect()`의 `ca`, `cert`, `key`, `rejectUnauthorized`, `servername` 등 |

서버는 키와 인증서 파일이 필요합니다.

```js
import { createServer } from 'node:https'
import { readFileSync } from 'node:fs'

createServer({
  key: readFileSync('private-key.pem'),
  cert: readFileSync('certificate.pem'),
}, handler).listen(8443)
```

- `https.createServer`는 `http.createServer`의 옵션(06편의 타임아웃 등)도 받습니다.
- 운영 환경에서는 로드 밸런서나 리버스 프록시가 TLS를 종료하고 Node에는 평문 HTTP로 넘기는 구성이 많습니다. 그래서 앱이 직접 `https.createServer`를 쓰는 일은 적습니다.
- 클라이언트로는 `fetch`를 쓰면 되고, `https`는 소켓 수준의 TLS 옵션이나 `https.Agent`가 필요할 때 씁니다.

## TLS 개념

TLS(Transport Layer Security)는 두 프로그램이 인터넷에서 도청, 변조, 메시지 위조를 막으며 통신하게 해 주는 프로토콜이고(RFC 8446), HTTPS는 HTTP를 TLS 위에 올린 것입니다. 연결 직후 핸드셰이크에서 쓸 버전과 암호 방식을 정하고, 서버가 인증서로 신원을 증명한 뒤 이후 데이터를 암호화합니다.

```js
// 핸드셰이크 뒤의 소켓에서 확인한 값
socket.getProtocol()  // 'TLSv1.3'
socket.authorized     // true (인증서 검증 통과)
socket.alpnProtocol   // 'h2' 또는 'http/1.1'
```

- Node의 기본 허용 버전은 최소 TLSv1.2, 최대 TLSv1.3입니다(`tls.DEFAULT_MIN_VERSION`, `tls.DEFAULT_MAX_VERSION`). 로컬 TLS 서버와의 연결에서 `TLSv1.3`이 협상되었습니다.
- SNI(Server Name Indication)는 클라이언트가 접속하려는 호스트 이름을 핸드셰이크에서 알려 주는 확장입니다. `https.Agent`의 `servername` 기본값은 대상 호스트 이름이고, IP로 접속하면 보내지 않습니다.
- ALPN(Application-Layer Protocol Negotiation)은 TLS 안에서 쓸 상위 프로토콜(`h2`, `http/1.1`)을 정하는 확장입니다(아래 HTTP/2 절).
- 핸드셰이크는 비용이 있어서 연결을 재사용하고(06편의 keep-alive), TLS 세션 재사용(`maxCachedSessions`)으로 줄입니다.

## 인증서

인증서는 CA(인증 기관)가 "이 공개키는 이 도메인의 것"이라고 서명한 문서입니다. 클라이언트는 인증서 체인을 따라가 신뢰하는 루트 CA까지 이어지는지, 기간이 유효한지, 접속한 호스트가 인증서의 SAN(subjectAltName)에 있는지를 확인합니다. `rejectUnauthorized`의 기본값은 `true`라서 검증에 실패하면 연결이 끊기고 오류가 발생합니다.

| 오류 코드 | 의미 |
|-----------|------|
| `DEPTH_ZERO_SELF_SIGNED_CERT` | 자체 서명 인증서 |
| `SELF_SIGNED_CERT_IN_CHAIN` | 체인 안에 자체 서명 인증서 |
| `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | 서버 인증서를 검증하지 못함 |
| `CERT_HAS_EXPIRED` | 유효 기간 만료 |
| `ERR_TLS_CERT_ALTNAME_INVALID` | 호스트 이름이 인증서의 SAN과 맞지 않음 |

로컬 자체 서명 서버로 실행해 확인한 결과입니다.

| 상황 | 결과 |
|------|------|
| 인증서를 신뢰시키지 않고 `fetch`·`https.get` | `DEPTH_ZERO_SELF_SIGNED_CERT` |
| `ca`에 그 인증서를 지정 | 200, `socket.authorized`는 `true` |
| `localhost` 인증서에 `127.0.0.1`로 접속 | `ERR_TLS_CERT_ALTNAME_INVALID` |
| `NODE_EXTRA_CA_CERTS`로 인증서를 추가해 `fetch` | 200 |

신뢰할 CA를 늘리는 방법은 네 가지입니다.

| 방법 | 범위 |
|------|------|
| 요청의 `ca` 옵션 | 그 요청(에이전트)만. 지정하면 기본 CA는 모두 쓰지 않음 |
| `NODE_EXTRA_CA_CERTS=파일` | 프로세스 전체. 기본 CA에 추가. 프로세스 시작 시에만 읽음 |
| `--use-system-ca` 또는 `NODE_USE_SYSTEM_CA=1` | 운영체제 신뢰 저장소 사용 (Node 23.8.0 / 24.6.0 추가) |
| `tls.setDefaultCACertificates(certs)` | 기본 CA 목록을 코드에서 교체 (Node 24.5.0 추가) |

- 기본 신뢰 목록은 Node에 번들된 Mozilla CA 목록입니다(`tls.rootCertificates`). 현재 쓰이는 목록은 `tls.getCACertificates()`로 볼 수 있습니다.
- 인증서 오류 메시지는 로컬에 설치된 루트 CA라면 `--use-system-ca`를 시도해 보라는 힌트를 덧붙입니다. 위험한 우회 대신 안전한 해결책을 안내하려는 것입니다.
- 서버 쪽에서 `https.createServer`에 쓰는 개발용 자체 서명 인증서는 `openssl req -x509 -newkey rsa:2048 -nodes -sha256 -subj '/CN=localhost' -keyout private-key.pem -out certificate.pem`으로 만듭니다(Node 문서의 예). 호스트 이름 검사는 SAN을 보므로 SAN도 넣어야 합니다.
- 인증서 정보는 `socket.getPeerCertificate()`로 읽습니다(`subject`, `issuer`, `valid_to`, `subjectaltname`). 인증서 핀닝은 `checkServerIdentity` 옵션으로 구현합니다.

## NODE_TLS_REJECT_UNAUTHORIZED를 끄면 안 되는 이유

`NODE_TLS_REJECT_UNAUTHORIZED=0` 환경 변수는 TLS 연결의 인증서 검증을 끕니다. 공식 문서도 TLS와 HTTPS를 안전하지 않게 만드니 쓰지 말라고 강하게 권고합니다.

```bash
# ❌ 프로세스의 모든 TLS 연결이 검증 없이 통과
NODE_TLS_REJECT_UNAUTHORIZED=0 node app.js
```

- 검증을 끄면 위조된 인증서로 중간에서 가로채는 공격(MITM)을 막을 수 없습니다. 암호화는 되지만 상대가 진짜 서버인지 확인하지 않습니다.
- 영향이 프로세스 전체입니다. 로컬 서버 하나를 위해 켜면 같은 프로세스의 외부 API 호출, 결제, 로그인 연결까지 전부 검증이 꺼집니다.
- 자체 서명 인증서(로컬 `127.0.0.1`)에 대한 요청이 호스트 이름 불일치까지 포함해 통과했습니다. 체인 오류와 호스트 오류가 모두 무시됩니다.
- 실행하면 시작 시 `Setting the NODE_TLS_REJECT_UNAUTHORIZED environment variable to '0' makes TLS connections and HTTPS requests insecure...` 경고가 출력됩니다.
- 개발 중 설정을 `.env`나 CI 설정에 넣고 운영까지 가져가는 사고가 흔합니다.
- 요청별 `rejectUnauthorized: false`도 같은 효과를 그 요청에만 냅니다. 이것도 쓰지 않습니다.

| 원인 | 올바른 해결 |
|------|-------------|
| 자체 서명·사설 CA 인증서 | `ca` 옵션 또는 `NODE_EXTRA_CA_CERTS`로 그 인증서만 신뢰 |
| 운영체제에는 설치된 사내 루트 CA | `--use-system-ca` |
| 호스트 이름 불일치 | SAN에 호스트를 넣어 인증서를 다시 발급, 또는 올바른 호스트로 접속 |
| 만료 | 인증서 갱신 |
| TLS를 가로채는 사내 프록시 | 프록시의 CA를 `NODE_EXTRA_CA_CERTS`로 등록 |

## HTTP/2 개념

HTTP/2는 HTTP의 의미(메서드, 상태 코드, 헤더)는 그대로 두고 연결 위에서 주고받는 방식을 바꾼 버전입니다(RFC 9113). 헤더를 압축하고, 한 연결 안에서 여러 요청·응답(스트림)을 동시에 주고받을 수 있게 해 지연을 줄입니다.

| 항목 | HTTP/1.1 | HTTP/2 |
|------|----------|--------|
| 한 연결의 요청 | 순차(파이프라이닝은 실무에서 쓰이지 않음) | 여러 스트림을 동시에 |
| 헤더 | 평문 텍스트, 매번 전송 | 압축 |
| 연결 헤더 | `Connection`, `Keep-Alive` 사용 | 사용 금지 |
| 요청 정보 | 시작줄과 헤더 | 의사 헤더 `:method`, `:path`, `:scheme`, `:authority`, 응답은 `:status` |
| 협상 | URL 스킴 | TLS 안에서 ALPN으로 `h2` 선택 |

- 브라우저는 암호화되지 않은 HTTP/2를 지원하지 않으므로 사실상 TLS가 전제입니다(Node 문서). 암호화되지 않은 변형(h2c)도 있지만 브라우저가 쓰지 않습니다.
- HTTP 수준에서는 스트림 하나가 느려도 같은 연결의 다른 스트림이 막히지 않습니다. 앞 요청이 막으면 뒤가 막히는 HTTP/1.1 파이프라이닝의 한계를 푼 것입니다.
- 서버는 같은 포트에서 ALPN으로 `h2`와 `http/1.1` 클라이언트를 함께 받을 수 있습니다.

## http2 모듈이 따로 있는 이유

`node:http2`가 별도 모듈인 이유는 HTTP/2가 메시지를 주고받는 구조(프레임, 스트림, 의사 헤더)가 달라서 `http` 모듈의 API로는 담을 수 없기 때문입니다. `http`는 HTTP/1.1용입니다. `http2`는 Stable이고(Node 10.10.0부터) 두 가지 API를 제공합니다.

| API | 모양 |
|-----|------|
| Core API | 세션·스트림 중심. 클라이언트와 서버가 대칭적 |
| Compatibility API | `http`와 비슷한 `req`·`res`. HTTP/1과 HTTP/2를 함께 지원하기 쉽게 만듦 |

```js
import { createSecureServer } from 'node:http2'

const server = createSecureServer({ key, cert })
server.on('stream', (stream, headers) => {
  stream.respond({ ':status': 200 })
  stream.end('hello')
})
```

```js
import { createSecureServer } from 'node:http2'

// 호환 API + HTTP/1.1 클라이언트도 허용
createSecureServer({ key, cert, allowHTTP1: true },
  (req, res) => res.end('ok')).listen(8443)
```

- 클라이언트는 `http2.connect(url)`로 세션을 만들고 `client.request({ ':path': '/' })`로 요청합니다. 로컬 TLS 서버에 연결했을 때 서버가 `httpVersion=2.0`, ALPN `h2`로 인식했습니다.
- 같은 서버에 `allowHTTP1: true`를 주면 `fetch`는 `http/1.1`로, `http2.connect`는 `h2`로 붙었습니다. Node 24.15의 전역 `fetch`는 h2를 지원하는 서버에도 `http/1.1`로 협상했습니다. Node 문서도 undici를 HTTP/1.1 클라이언트로 설명합니다.
- 브라우저와 서버 사이에서는 HTTP/2가 흔하지만, Node 서버가 직접 `http2`를 쓰는 일은 드뭅니다. 보통은 프록시나 로드 밸런서가 HTTP/2를 처리하고 Node에는 HTTP/1.1로 전달합니다.
- 호환 API는 `http`의 공개 API만 대상으로 하며 내부 구현을 쓰는 모듈은 동작하지 않을 수 있습니다.

## undici Agent·Pool과 dispatcher

디스패처(dispatcher)는 undici에서 요청을 실제로 보내는 계층입니다. `fetch`의 `dispatcher` 옵션으로 요청마다 지정할 수 있고, 지정하지 않으면 전역 디스패처를 씁니다.

| 클래스 | 역할 |
|--------|------|
| `Client` | 한 origin에 연결 하나 |
| `Pool` | 한 origin에 여러 `Client`. `connections`가 최대 수(기본 `null`, 무제한) |
| `Agent` | 여러 origin. origin마다 `Pool`을 만들고 재사용. `fetch`의 기본 디스패처 |
| `ProxyAgent`, `EnvHttpProxyAgent` | 프록시 경유 (아래 `프록시 설정` 절) |

번들된 undici의 클래스는 import할 수 없으므로 npm `undici`를 설치해서 씁니다(문서 기준이며 이 문서에서는 실행하지 않았습니다).

```js
import { Agent, setGlobalDispatcher } from 'undici'
import { readFileSync } from 'node:fs'

const agent = new Agent({
  connections: 20,
  headersTimeout: 10_000,
  bodyTimeout: 30_000,
  connect: { ca: readFileSync('ca.pem') },
})
setGlobalDispatcher(agent)       // 전역으로
await fetch(url, { dispatcher: agent }) // 또는 요청마다
```

| undici 옵션 | 기본값 | 의미 |
|-------------|--------|------|
| `connections` | `null` (무제한) | origin당 최대 연결 수 |
| `pipelining` | 1 | 한 연결에서 동시에 보낼 요청 수. 0이면 keep-alive 끔 |
| `keepAliveTimeout` | 4000 | 요청이 없는 소켓을 유지하는 시간(서버의 힌트가 덮어씀) |
| `headersTimeout` | 300000 | 응답 헤더를 기다리는 시간 |
| `bodyTimeout` | 300000 | 본문 조각 사이의 최대 간격 |
| `connectTimeout` | 10000 | 연결을 맺는 시간 |
| `connect` | `null` | `tls.connect()` 옵션(`ca`, `rejectUnauthorized` 등)과 `timeout` 등 |

- `setGlobalDispatcher()`를 npm undici에서 호출하면 undici와 Node 전역 `fetch` 양쪽에 영향을 줍니다(Node 문서).
- `http.Agent`의 `maxSockets`에 해당하는 undici 옵션이 `connections`입니다. 두 설정은 서로 별개입니다(06편).
- 다 쓴 디스패처는 `await agent.close()`로 정리합니다.
- 표의 기본값은 undici 문서(main 기준)이며, 실제 적용되는 값은 `process.versions.undici`의 버전에 따라 다를 수 있습니다.
- undici 문서는 `allowH2`(기본 `true`)로 ALPN에서 HTTP/2를 고르게 설명하지만, 로컬 Node 24.15의 전역 `fetch`는 `http/1.1`로 협상했습니다. 버전에 따라 다르므로 HTTP/2가 필요하면 설치한 undici의 문서와 동작을 확인합니다.

## 프록시 설정

프록시 설정은 아웃바운드 요청을 사내 프록시 같은 중간 서버로 보내는 설정입니다. Node는 `HTTP_PROXY` 같은 환경 변수를 기본으로 읽지 않습니다. 환경 변수만 설정한 프로세스는 프록시를 쓰지 않았습니다.

```bash
NODE_USE_ENV_PROXY=1 \
HTTP_PROXY=http://proxy.corp:8080 \
HTTPS_PROXY=http://proxy.corp:8080 \
NO_PROXY=localhost,127.0.0.1 \
node app.js
```

| 방법 | 추가된 버전 |
|------|-------------|
| 환경 변수 `NODE_USE_ENV_PROXY=1` | Node 24.0.0 |
| 실행 옵션 `--use-env-proxy` (환경 변수보다 우선) | Node 24.5.0 |
| 에이전트 옵션 `proxyEnv` (`http.Agent`, `https.Agent`) | Node 24.5.0 |
| `http.setGlobalProxyFromEnv([proxyEnv])` (코드에서 켜고 복구 함수를 반환) | Node 24.14.0 |

- 내장 프록시 지원은 Stability 1.1(Active development)입니다.
- 읽는 변수는 `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`와 소문자 형태입니다. 둘 다 있으면 소문자가 우선합니다.
- 전역 `fetch`와 `http`·`https` 요청에 모두 적용됩니다. 로컬 프록시로 확인했을 때 `fetch`는 `CONNECT` 터널로, `http.get`은 절대 URL 형식(`GET http://...`)으로 프록시에 도착했습니다.
- `NO_PROXY`는 프록시를 거치지 않을 대상입니다. `*`(전부), 정확한 호스트, `.example.com`(접미사), `*.example.com`, IP, IP 범위, `호스트:포트` 형식을 받으며 쉼표로 구분합니다. `NO_PROXY=127.0.0.1`을 주자 로컬 요청이 프록시를 거치지 않았습니다.
- 프록시 URL은 `http://`, `https://`, `http://user:pass@host:port`(인증 포함)를 받습니다.
- 프록시는 연결 메타데이터를 볼 수 있고, 평문 HTTP이거나 TLS를 종료하는 프록시이면 요청·응답 내용도 볼 수 있습니다. 문서는 신뢰하고 허가된 프록시만 설정하라고 안내합니다.
- undici를 직접 쓸 때는 `ProxyAgent`(프록시 URI 지정. HTTPS 대상은 `CONNECT` 터널)나 `EnvHttpProxyAgent`(환경 변수 `http_proxy`, `https_proxy`, `no_proxy`를 읽음)를 디스패처로 지정합니다.
- TLS를 가로채는 프록시를 만났다면 `NODE_TLS_REJECT_UNAUTHORIZED=0`이 아니라 프록시의 CA를 `NODE_EXTRA_CA_CERTS`로 등록합니다.

## 핵심 정리

- 전역 `fetch`는 undici로 구현된 Promise API입니다. 네트워크 오류만 reject하므로 4xx·5xx는 `res.ok`로 직접 걸러내고, 본문은 한 번만 읽으며, 마감 시간은 `AbortSignal.timeout()`으로 겁니다.
- `res.json()`과 `res.text()`는 본문 전체를 메모리에 올립니다. 큰 본문이나 믿을 수 없는 출처는 `res.body` 스트림으로 읽으며 크기를 제한합니다.
- `http.request`는 이벤트·스트림 기반 저수준 API이고 리다이렉트와 압축 해제를 하지 않으며, 연결 풀은 `http.Agent`로 따로 설정합니다.
- HTTPS는 TLS 위의 HTTP이고 인증서 체인·유효 기간·호스트 이름을 검증합니다. 사설 인증서는 `ca`, `NODE_EXTRA_CA_CERTS`, `--use-system-ca`로 해결하고 `NODE_TLS_REJECT_UNAUTHORIZED=0`은 쓰지 않습니다.
- HTTP/2는 한 연결의 다중 스트림과 헤더 압축을 제공하고 ALPN으로 협상하며, 구조가 달라 `node:http2`가 따로 있습니다. 전역 `fetch`는 Node 24.15에서 HTTP/1.1로 연결했습니다.
- undici의 `Agent`·`Pool`은 npm 패키지를 설치해 `dispatcher`로 넘기고, 프록시는 `NODE_USE_ENV_PROXY=1`과 `HTTP_PROXY`·`NO_PROXY`로 켭니다.

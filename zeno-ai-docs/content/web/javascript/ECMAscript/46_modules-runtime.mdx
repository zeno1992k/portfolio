문법(`import`·`export`, 라이브 바인딩, `import()`, `import.meta`)은 45편에서 다룹니다. 이 편은 그 문법이 실행될 때 일어나는 일과 환경별 차이를 다룹니다.

## 모듈 로딩 3단계

ES 모듈은 구성(construction), 인스턴스화(instantiation), 평가(evaluation) 세 단계로 처리됩니다. 한 모듈의 본문은 세 단계를 모두 거친 뒤에야 실행되기 시작합니다.

| 단계 | 하는 일 | 코드 실행 |
|------|---------|-----------|
| 구성 | 지정자를 URL로 해석하고, 파일을 가져와 파싱하고, 그 안의 `import`를 찾아 의존 모듈을 재귀로 가져온다. 결과는 모듈 그래프 | 없음 |
| 인스턴스화 | 모듈마다 export 바인딩의 메모리 칸을 만들고, import 바인딩을 상대 모듈의 칸에 연결한다 | 없음 |
| 평가 | 본문을 실행해 칸에 값을 채운다 | 있음 |

- **구성**: 의존 모듈은 파싱한 뒤에야 알 수 있으므로 그래프는 한 층씩 내려가며 만들어집니다. 브라우저에서는 이 층마다 네트워크 왕복이 생깁니다. 지정자를 못 찾거나 구문 오류가 있으면 이 단계에서 실패합니다.
- **인스턴스화**: import 바인딩은 값의 복사가 아니라 export 쪽 칸을 가리키는 연결입니다. 그래서 라이브 바인딩이 됩니다. 함수 선언은 이 단계에서 초기화되고, `let`·`const`·`class`는 TDZ 상태(값이 들어가기 전 접근하면 에러)로 만들어집니다(TDZ는 13편).
- **평가**: 의존 모듈이 먼저, 자신이 나중에 실행됩니다. 의존 모듈은 `import` 문이 적힌 순서대로 깊이 우선 후위 순회로 실행됩니다.

```js
// o0.mjs
console.log('o0 start')
import './o1.mjs' // 본문: console.log('o1')
import './o2.mjs' // 본문: console.log('o2')
console.log('o0 end')
// 출력: o1, o2, o0 start, o0 end
```

`import`는 문 위치와 관계없이 호이스팅되어 평가 전에 처리되므로 `o0 start`보다 `o1`이 먼저 출력됩니다.

인스턴스화에서 연결이 안 되면 어떤 코드도 실행되기 전에 실패합니다.

```js
// main.mjs
console.log('start') // 출력되지 않는다
import { nope } from './lib.mjs'
// SyntaxError: The requested module './lib.mjs'
// does not provide an export named 'nope'
```

- ES 명세는 인스턴스화를 `Link()`, 평가를 `Evaluate()`라는 연산으로 정의합니다. 구성(파일을 가져오는 방법)은 호스트가 맡습니다. 브라우저는 HTML 표준, Node.js는 자체 구현을 따릅니다.
- 브라우저는 구성 단계를 네트워크 때문에 따로 분리하고, Node.js는 로컬 파일을 읽으므로 세 단계가 이어서 진행됩니다.
- `import()`는 호출되는 시점에 그 모듈에 대해 세 단계를 수행하고 프로미스를 반환합니다.
- CommonJS의 `require`는 파일을 읽고 바로 실행합니다. 의존 관계를 실행 전에 알 수 없다는 점이 가장 큰 차이입니다.

## 단일 실행과 캐싱

한 모듈은 같은 환경에서 한 번만 평가되고, 모든 importer가 같은 인스턴스를 공유합니다. 로더가 모듈 맵(module map)에 해석된 URL을 키로 기록해 두고, 이미 있으면 다시 가져오지도 실행하지도 않습니다.

```js
// once.mjs
console.log('once evaluated')
export let n = 0
export const inc = () => { n++ }

// main.mjs
import './once.mjs'              // once evaluated
import { n, inc } from './once.mjs' // 실행 안 함
await import('./once.mjs')       // 실행 안 함
await import('./once.mjs?v=2')   // once evaluated (다른 URL)
```

- 키는 해석이 끝난 URL입니다. 상대 경로가 달라도 같은 URL로 해석되면 같은 모듈이고, 쿼리 문자열만 달라도 다른 모듈입니다.
- 모듈 최상위의 변수는 모든 importer가 공유하는 싱글톤 상태가 됩니다. 설정 객체나 연결 풀을 모듈에 두는 패턴이 이 성질에 기댑니다.
- 평가 중 에러가 나면 그 실패도 기록됩니다. 같은 모듈을 다시 import하면 본문을 다시 실행하지 않고 같은 에러를 다시 던집니다.
- 모듈 맵은 전역 환경(Window, Worker 등)마다 따로 있습니다. 브라우저의 iframe은 같은 URL이어도 별도로 평가합니다.
- Node.js의 ES 모듈 캐시는 `require.cache`와 별개이고 코드에서 접근할 수 없습니다. 캐시를 지우는 API가 없으므로, 쿼리 문자열로 다시 불러오면 이전 인스턴스가 메모리에 남습니다.
- 같은 패키지가 CommonJS와 ESM 두 파일로 배포되면 두 번 평가되어 상태가 둘이 됩니다(이중 패키지 위험, 아래 exports 절).

흔한 실수는 `import`가 호출 시마다 실행된다고 가정하는 것입니다. 초기화 코드를 다시 실행해야 하면 모듈 최상위에 두지 말고 함수로 export합니다.

## 순환 참조

순환 참조는 모듈 A가 B를 import하고 B가 다시 A를 import하는 관계입니다. ESM은 에러 없이 로드되지만, 평가 순서 때문에 아직 값이 채워지지 않은 바인딩을 읽을 수 있습니다.

진입점이 A라면 평가는 A → B 순으로 내려가다가 B가 A를 import하는 지점에서 A가 이미 진행 중이므로 건너뜁니다. 따라서 B 본문이 A 본문보다 먼저 실행됩니다.

```js
// a.mjs (진입점)
import { b } from './b.mjs'
export const a = 'A'
export function greet() { return 'hi' }

// b.mjs
import { a, greet } from './a.mjs'
console.log(greet()) // 'hi' — 함수 선언은 인스턴스화에서 초기화
console.log(a)       // ReferenceError: Cannot access 'a'
                     // before initialization
export const b = 'B'
```

| 선언 | 순환 중 B가 먼저 실행될 때 |
|------|----------------------------|
| `function` 선언 | 사용 가능 |
| `let`·`const`·`class` | TDZ. 읽으면 ReferenceError (`typeof`도 에러) |
| `var` | `export var`는 `undefined` |

- 같은 코드라도 진입점이 B면 순서가 뒤집혀 A가 먼저 TDZ에 걸립니다. 에러가 어느 파일을 먼저 로드하느냐에 달려 있어서 재현이 까다롭습니다.
- 값을 로드 시점이 아니라 함수 안에서 나중에 읽으면 문제가 없습니다. 모든 평가가 끝난 뒤에는 바인딩이 채워져 있기 때문입니다.
- `class B extends A`처럼 평가 시점에 즉시 필요한 의존은 순환에서 가장 깨지기 쉽습니다.
- 해결 방법은 공통 코드를 제3의 모듈로 빼는 것이 가장 좋고, 그다음이 함수 안에서 지연 사용하는 것, 마지막이 `import()`입니다.
- 순환은 ESLint의 `import/no-cycle` 규칙(eslint-plugin-import)으로 탐지할 수 있습니다.

CommonJS의 순환은 동작이 다릅니다. `require`가 상대 모듈의 현재까지 채워진 `exports` 객체를 반환하므로, 에러 없이 비어 있는 값을 조용히 읽습니다.

```js
// x.cjs: exports.done = false; require('./y.cjs') 후 true
// y.cjs: exports.done = false; require('./x.cjs') 후 true
// 진입점 x.cjs 실행 시 y는 x.done을 false로 본다
```

| 구분 | ESM | CommonJS |
|------|-----|----------|
| 미완성 값을 읽으면 | ReferenceError(let·const) | `undefined`나 중간 값 |
| 값 전달 | 라이브 바인딩 | 반환 시점의 exports 객체 |

시험에서는 라이브 바인딩 때문에 ESM 순환이 되는 이유와, TDZ 때문에 에러가 나는 조건을 함께 묻습니다.

## Top-level await와 모듈 그래프

Top-level await(ES2022)는 모듈 최상위에서 `await`를 쓰는 기능입니다. 사용한 모듈은 비동기 모듈이 되어, 그 모듈의 평가가 프로미스가 끝날 때까지 이어집니다.

```js
// config.mjs
const res = await fetch('/config.json')
export const config = await res.json()

// app.mjs
import { config } from './config.mjs'
console.log(config) // config.mjs의 평가가 끝난 뒤에 실행
```

그래프에 미치는 규칙은 다음과 같습니다.

- 비동기 모듈을 import한 모듈은 그 모듈의 평가가 끝날 때까지 기다린 뒤 실행됩니다. 간접 의존도 마찬가지로, 그래프의 위쪽 전체가 지연됩니다.
- 서로 의존하지 않는 형제 모듈은 기다리지 않고 진행됩니다. 형제들의 `await`는 병렬로 대기합니다.
- 비동기 모듈 자체의 본문은 첫 `await` 전까지는 순서대로 동기 실행됩니다.

```js
// main.mjs: s1(await 50ms), s2(await 10ms), s3(동기) 순서로 import
// 출력: s1 start, s2 start, s3 sync, s2 end, s1 end, main
```

`s1`이 기다리는 동안 `s2`와 `s3`이 시작합니다. `main`은 세 모듈이 모두 끝난 뒤 마지막에 실행됩니다.

- await한 프로미스가 reject되면 그 모듈의 평가가 실패하고, 그 모듈에 의존하는 모듈도 같은 에러로 실패합니다. 모듈 맵에 실패가 기록되므로 다시 import해도 같은 에러가 납니다.
- 프로미스가 영영 끝나지 않으면 의존하는 모듈은 실행되지 않습니다. Node.js는 실행이 멈춘 채 종료되며 `unsettled top-level await` 경고와 함께 종료 코드 13을 반환합니다.
- 순환에서 서로를 기다리면 교착 상태가 됩니다. A가 B를 import하고 B가 `await import('./a.mjs')`를 하면, A는 B의 평가를, B는 A의 평가를 기다립니다. Node.js에서 종료 코드 13으로 끝납니다.
- 모듈 최상위에서만 쓸 수 있습니다. 일반 함수 안의 `await`와 클래식 스크립트(`type="module"`이 없는 `script`), CommonJS에서는 SyntaxError입니다. `async` 함수 안에서는 원래부터 가능했습니다(43편).
- `require()`로는 비동기 모듈을 불러올 수 없습니다(아래 `require`로 ESM 불러오기 절).

흔한 실수는 여러 모듈이 import하는 공용 모듈에 느린 `await`를 넣는 것입니다. 그 모듈에 의존하는 모든 모듈의 시작이 늦어집니다. 즉시 필요하지 않은 값은 값 대신 프로미스를 export하고 사용하는 쪽에서 await합니다.

## 정적 분석과 트리 셰이킹

ESM의 `import`·`export`는 모듈 최상위에만 쓸 수 있고 지정자는 문자열 리터럴이어야 합니다. 그래서 도구가 코드를 실행하지 않고도 의존 그래프와 각 모듈의 export 목록을 알아낼 수 있습니다. 이것이 정적 분석입니다.

| 구분 | 의존 관계를 알 수 있는 시점 |
|------|----------------------------|
| `import x from './a.js'` | 파싱만으로 정적 확정 |
| `import(path)` | 실행해야 확정 (동적) |
| `require(path)` | 실행해야 확정 (동적) |

**트리 셰이킹**(tree shaking)은 번들러가 정적 분석으로 사용되지 않는 export를 번들에서 제거하는 최적화입니다.

```js
// math.js
export const add = (a, b) => a + b
export const sub = (a, b) => a - b

// app.js
import { add } from './math.js'
console.log(add(1, 2)) // 번들에는 add만 남고 sub는 제거
```

트리 셰이킹이 되려면 다음 조건이 필요합니다.

- **ESM 문법이 유지되어야 합니다.** Babel이 `import`를 `require`로 바꾸면 정적 정보가 사라집니다. 번들러 앞단에서는 모듈 변환을 끕니다(Babel의 `modules: false`).
- **제거해도 되는 코드여야 합니다.** 모듈 최상위에 호출이나 프로퍼티 대입이 있으면 부수 효과일 수 있어 번들러가 보수적으로 남깁니다.
- **프로덕션 빌드에서 동작합니다.** 개발 모드에서는 보통 제거하지 않으므로 반드시 프로덕션 모드로 확인합니다.

번들러에게 부수 효과가 없음을 알리는 방법이 두 가지 있습니다.

| 방법 | 위치 | 효과 |
|------|------|------|
| `sideEffects` | package.json | `false`면 쓰지 않는 모듈 파일 전체를 통째로 제거. 배열이면 부수 효과가 있는 파일만 지정 |
| `/* @__PURE__ */` | 호출식 앞 | 그 호출은 결과를 쓰지 않으면 제거해도 된다고 표시 |

```json
{ "sideEffects": ["*.css", "./src/polyfill.js"] }
```

- `sideEffects`는 Node.js나 ECMAScript가 아니라 번들러(webpack, Rollup 등)가 읽는 관례입니다.
- `sideEffects: false`를 과하게 쓰면 CSS import나 폴리필이 사라집니다. 부수 효과로 쓰는 파일은 배열에 반드시 적습니다.
- 파일 단위로 건너뛰는 `sideEffects`가 개별 export를 지우는 방식보다 훨씬 효과적입니다. 의존 트리 전체를 통째로 빼기 때문입니다.
- `export default { a, b }`처럼 객체 하나로 내보내면 멤버를 개별로 제거하기 어렵습니다. 이름 있는 export가 유리합니다.
- `import * as ns`는 `ns.add`처럼 정적으로 접근하면 괜찮지만, `ns[key]` 같은 동적 접근은 대부분의 번들러가 전부 남깁니다.
- Node.js 런타임은 트리 셰이킹을 하지 않습니다. 빌드 단계의 최적화입니다(번들러는 51편).

## 배럴 파일의 비용

배럴 파일(barrel file)은 여러 모듈의 export를 한곳에서 다시 내보내는 `index.js`입니다.

```js
// components/index.js
export { Button } from './Button.js'
export { Modal } from './Modal.js'
export * from './icons.js'

// 사용처
import { Button } from './components' // 하나만 쓰려는 import
```

배럴은 import 경로를 짧게 만들지만 다음 비용이 듭니다.

- **전체 로드**: `Button` 하나를 import해도 배럴이 재내보내는 모든 모듈이 구성·평가됩니다. 각 모듈의 본문이 부수 효과를 가질 수 있으므로 번들 없이 실행하는 환경(Node.js, 테스트 러너, 번들하지 않는 개발 서버)은 모두 로드해야 합니다.
- **번들 크기**: 번들러가 `sideEffects` 정보 없이 판단하면 쓰지 않는 모듈이 번들에 남습니다. 제거에 성공해도 분석 시간이 듭니다.
- **순환 참조**: 배럴이 있는 폴더 안의 모듈이 같은 배럴에서 import하면 순환이 생깁니다.
- **느린 도구**: 테스트와 개발 서버의 시작이 느려지고, 파일 하나를 고쳐도 배럴을 거쳐 다시 불러오는 범위가 넓어집니다.

| 대응 | 방법 |
|------|------|
| 직접 경로 import | `import { Button } from './components/Button.js'` |
| 라이브러리 배럴 | `sideEffects: false`를 선언해 번들러가 통째로 제거할 수 있게 한다 |
| 큰 아이콘·유틸 패키지 | Next.js는 `experimental.optimizePackageImports`로 쓰는 모듈만 로드하게 한다. lucide-react, date-fns, lodash-es 등은 기본 적용 (문서상 실험 기능) |
| 배럴을 쓸 곳 | 패키지의 공개 진입점으로만. 앱 내부 폴더에는 쓰지 않는 쪽이 안전 |

`export * from`은 어떤 이름이 나가는지 대상 파일을 열어 봐야 알 수 있습니다. 가능하면 이름을 명시한 `export { X } from`을 씁니다.

## 브라우저의 ESM

브라우저는 `<script type="module">`로 ES 모듈을 실행합니다. 클래식 스크립트와 다음이 다릅니다.

| 항목 | 모듈 스크립트 |
|------|---------------|
| 실행 시점 | 기본이 defer. HTML 파싱이 끝난 뒤 문서 순서대로 실행 (`defer` 속성은 무의미) |
| `async` 속성 | 의존 모듈까지 병렬로 가져와 준비되는 즉시 실행. 인라인 모듈에도 적용 |
| 같은 URL 중복 | 여러 번 써도 한 번만 실행 |
| 모드 | 항상 strict mode, 최상위 `this`는 `undefined` |
| 스코프 | 모듈 스코프. 최상위 `var`·함수가 `window` 프로퍼티가 되지 않음 |
| 교차 출처 | CORS 필수 |

```html
<script type="module" src="/main.js"></script>
<script nomodule src="/legacy.js"></script>
```

- `nomodule`이 붙은 스크립트는 모듈을 지원하는 브라우저가 무시합니다. 구형 브라우저용 대체 코드에 씁니다.
- 서버는 JavaScript MIME 타입(`text/javascript`)으로 응답해야 합니다.
- `file://`로 연 페이지에서는 CORS 때문에 모듈 로드가 실패합니다. 로컬 서버가 필요합니다.
- 지정자는 URL이어야 합니다. `./`·`../`·`/`로 시작하는 경로나 절대 URL만 가능하고, 확장자를 자동으로 붙이지 않습니다.
- `import()`는 클래식 스크립트에서도 쓸 수 있습니다. Worker는 `new Worker(url, { type: 'module' })`로 모듈로 실행합니다.

**맨 지정자**(`'lodash'` 같은 이름만 있는 지정자)는 브라우저가 해석하지 못해 에러가 납니다. 임포트 맵(import map)이 이름을 URL에 대응시킵니다.

```html
<script type="importmap">
  { "imports": {
      "lodash": "/vendor/lodash-es/lodash.js",
      "lodash/": "/vendor/lodash-es/" } }
</script>
<script type="module">import _ from 'lodash'</script>
```

- 임포트 맵은 모듈 로딩이 시작되기 전에 선언해야 합니다.
- 지원 여부는 `HTMLScriptElement.supports('importmap')`으로 확인합니다.

구성 단계가 층마다 네트워크 왕복을 만들기 때문에, 의존이 깊으면 요청이 줄줄이 이어지는 폭포(waterfall)가 생깁니다. `<link rel="modulepreload" href="...">`로 필요한 모듈을 미리 받아 두거나 번들러로 파일 수를 줄입니다.

## Node.js의 ESM

Node.js는 기본이 CommonJS이고, 다음 중 하나일 때 ESM으로 실행합니다.

| 조건 | 예 |
|------|----|
| 확장자 `.mjs` | `app.mjs` (항상 ESM) |
| package.json의 `"type": "module"` | 같은 패키지의 `.js`가 ESM |
| `--input-type=module` | 표준 입력·`-e` 코드 |
| 문법 감지 | `type` 없는 `.js`에 `import`·`export`가 있으면 ESM으로 판단 (최근 버전) |

- `.cjs`는 `type`과 관계없이 항상 CommonJS입니다.
- 문법 감지는 최근 버전에서만 동작합니다. 구버전은 CommonJS로 실행하다가 SyntaxError가 나므로 `type` 필드로 명시하는 편이 안전합니다.

CommonJS와 다른 규칙은 다음과 같습니다.

- 상대·절대 지정자는 **확장자를 반드시 적습니다.** `'./util'`은 `ERR_MODULE_NOT_FOUND`이고, 디렉터리 `index` 자동 해석도 없습니다(`'./util/index.js'`).
- 내장 모듈은 `node:fs`처럼 `node:` 접두사로 가져옵니다.
- 맨 지정자는 `node_modules`에서 찾고 package.json의 `exports`를 따릅니다. `#`로 시작하면 `imports` 필드로 해석합니다(아래 exports 절).
- JSON은 import attributes를 붙여 가져옵니다. default export만 있습니다.
- 최상위 `await`를 쓸 수 있습니다.

```js
import data from './data.json' with { type: 'json' }
console.log(data) // { a: 1 }
```

CommonJS에만 있던 값은 ESM에서 사라집니다.

| CommonJS | ESM에서 |
|----------|---------|
| `require()` | `import`, `import()`, `createRequire` |
| `module.exports`, `exports` | `export` |
| `__filename`, `__dirname` | `import.meta.filename`, `import.meta.dirname` |
| `require.resolve()` | `import.meta.resolve()` |
| `require.main === module` | `import.meta.main` |
| `require.cache` | 접근 불가 (별도 캐시) |

```js
// app.mjs
console.log(typeof __dirname, typeof require) // undefined undefined
```

- `import.meta.main`은 Node.js 24.2·22.18에서 추가되었고 안정성 등급이 아직 초기 개발(1.0)입니다.
- 캐시 키는 URL이라 `./foo.mjs?q=1`과 `./foo.mjs?q=2`는 별개 모듈입니다.

## import.meta.dirname

`import.meta.dirname`은 현재 모듈 파일이 있는 디렉터리의 절대 경로이고, `import.meta.filename`은 파일 자체의 절대 경로입니다. CommonJS의 `__dirname`·`__filename`에 대응합니다.

```js
import { readFileSync } from 'node:fs'
import { join } from 'node:path'

const path = join(import.meta.dirname, 'data.txt')
readFileSync(path, 'utf8') // 이 파일 옆의 data.txt
```

- Node.js 21.2와 20.11에서 추가되었고, 24.0과 22.16부터 실험 단계가 아닙니다.
- `file:` 프로토콜 모듈에서만 존재합니다. 다른 프로토콜의 모듈에서는 `undefined`입니다. 브라우저도 이 프로퍼티를 제공하지 않습니다.
- 이전에는 `import.meta.url`(현재 모듈의 `file:` URL)을 경로로 바꿔서 썼습니다.

```js
import { fileURLToPath } from 'node:url'
import { dirname } from 'node:path'

const __filename = fileURLToPath(import.meta.url)
const __dirname = dirname(__filename)
```

- 브라우저와 공통으로 쓰려면 `new URL('./data.txt', import.meta.url)`이 이식성이 높습니다.
- `import.meta.resolve('./dep.js')`는 지정자를 URL 문자열로 동기 해석합니다(`file:///.../dep.js`).
- 흔한 실수는 `dirname`과 `process.cwd()`를 같은 것으로 보는 것입니다. `cwd`는 프로세스를 실행한 위치이고, `dirname`은 파일의 위치입니다.

## ESM과 CommonJS 상호 운용

두 시스템은 로드 방식, 값 전달, 캐시가 모두 다르지만 Node.js는 서로 불러오는 경로를 제공합니다.

| 구분 | CommonJS | ESM |
|------|----------|-----|
| 로드 | 동기 (`require`) | 비동기 가능 (최상위 `await`) |
| 값 전달 | `module.exports` 객체의 참조 | 라이브 바인딩 |
| 의존 파악 | 실행 중 | 실행 전 (정적) |
| 최상위 `this` | `module.exports` | `undefined` |
| strict mode | 선택 | 항상 |
| 캐시 | `require.cache` | URL 기반 별도 캐시 |

**ESM에서 CommonJS를 import**하는 규칙입니다.

- 기본 import는 항상 `module.exports` 전체입니다.
- 이름 있는 import는 Node.js가 파일을 정적 분석(cjs-module-lexer)해서 찾은 이름만 가능합니다. 동적으로 만든 이름은 찾지 못해 SyntaxError가 납니다.
- 이름 있는 import는 가져온 시점의 값이며 라이브가 아닙니다. 이후 `module.exports`가 바뀌는 것은 반영되지 않습니다.
- `import * as ns`의 키에는 `default`와 `module.exports`가 들어 있습니다.

```js
// lib.cjs
exports.count = 0
exports.inc = function () { exports.count++ }

// main.mjs
import lib, { count, inc } from './lib.cjs'
inc()
console.log(count, lib.count) // 0 1 — 이름 import는 복사
```

```js
// dyn.cjs: module.exports = { [k]: 1 } (계산된 키)
import { x } from './dyn.cjs'
// SyntaxError: Named export 'x' not found.
import pkg from './dyn.cjs' // ✅ 기본 import 후 구조 분해
const { x } = pkg
```

- Babel·TypeScript로 변환한 CommonJS는 `exports.__esModule = true`와 `exports.default`를 갖지만, Node.js의 기본 import는 `__esModule`을 보지 않고 `module.exports` 전체를 줍니다. 그래서 `import x from`의 `x`가 `{ default: ... }` 객체일 수 있습니다.
- 번들러와 TypeScript의 상호 운용 설정은 Node.js와 다를 수 있으므로 실제 실행 환경 기준으로 확인합니다.

**CommonJS에서 ESM을 로드**하는 방법은 두 가지입니다.

- `import()`: CommonJS에서도 쓸 수 있고 프로미스를 반환합니다. 최상위 `await`가 있는 모듈도 가능합니다.
- `require()`: 동기 ESM에 한해 가능합니다(다음 절).

**ESM에서 `require`가 필요할 때**는 `createRequire`로 만듭니다.

```js
import { createRequire } from 'node:module'

const require = createRequire(import.meta.url)
const pkg = require('./package.json')
```

## require로 ESM 불러오기

`require()`는 ES 모듈 파일을 동기적으로 불러와 모듈 네임스페이스 객체를 반환할 수 있습니다. ESM 전용으로 배포된 패키지를 CommonJS 코드가 그대로 쓰게 해 줍니다.

```js
// esm.mjs
export const a = 1
export default function f() {}

// main.cjs
const m = require('./esm.mjs')
console.log(m.a, m.default.name) // 1 'f'
```

- 반환값은 `import()`와 같은 네임스페이스 객체이고, default export는 `.default`에 있습니다.
- default export가 있으면 `__esModule: true`가 자동으로 붙습니다. 변환 도구가 알아보기 위한 것이라 사용자 코드가 의존하지 않는 편이 좋습니다.
- ESM에서 `export { Point as 'module.exports' }`로 내보내면 `require()`의 결과를 그 값으로 바꿀 수 있습니다. 다만 이 경우 이름 있는 export는 사라집니다.
- 로드 대상이 되는 파일은 `.mjs`, `type: module`의 `.js`, 또는 ESM 문법을 가진 `type` 없는 `.js`입니다.

| 조건 | 결과 |
|------|------|
| 그래프에 최상위 `await`가 있음 | `ERR_REQUIRE_ASYNC_MODULE` |
| `require`하는 ESM 사이에 순환이 있음 | `ERR_REQUIRE_CYCLE_MODULE` |

- 비동기 모듈이 필요하면 `import()`를 써야 합니다.
- 최상위 `await` 하나가 의존 그래프 어디에든 있으면 그 패키지 전체가 `require`로 불러올 수 없게 됩니다.
- 플래그 없이 쓸 수 있게 된 버전은 Node.js 23.0, 22.12, 20.19입니다. 25.4부터 실험 단계가 아닙니다.
- 지원 여부는 `process.features.require_module`로 확인하고, `--no-require-module`로 끌 수 있습니다.
- 흔한 실수는 `.default`를 빠뜨리고 default export를 곧바로 쓰려는 것입니다.

## package.json exports와 조건부 exports

`exports`는 패키지가 외부에 공개하는 진입점을 선언하는 package.json 필드입니다. `main`보다 우선하고, 선언하지 않은 경로는 접근할 수 없도록 패키지를 캡슐화합니다.

```json
{
  "name": "pkg",
  "exports": {
    ".": "./dist/index.js",
    "./feature": "./dist/feature.js",
    "./package.json": "./package.json"
  }
}
```

- `"."`는 `import 'pkg'`에 대응하고, `"./feature"`는 `import 'pkg/feature'`에 대응합니다.
- 값은 `./`로 시작하는 상대 경로여야 하고 `..`과 `node_modules`는 쓸 수 없습니다.
- 목록에 없는 경로를 불러오면 `ERR_PACKAGE_PATH_NOT_EXPORTED`입니다. `pkg/dist/index.js`처럼 내부 파일을 직접 import하던 코드도 막힙니다.
- 문자열 하나만 쓰는 축약형(`"exports": "./index.js"`)은 `"."` 하나와 같습니다.
- package.json 자체를 읽어야 하는 사용자가 있다면 `"./package.json"`을 명시해서 열어 줍니다.
- 기존 패키지가 `exports`를 추가하면 이전에 접근하던 내부 경로가 막히므로 호환성이 깨지는 변경입니다.
- `main`은 `exports`를 모르는 구버전을 위한 대체 값으로 남깁니다. `module` 필드는 Node.js가 아니라 번들러의 관례입니다.

**서브패스 패턴**은 `*`로 여러 경로를 한 줄로 선언합니다. 값을 `null`로 하면 그 경로를 제외합니다.

```json
{
  "exports": {
    "./utils/*": "./dist/utils/*.js",
    "./utils/internal/*": null
  }
}
```

`import 'pkg/utils/a'`는 `./dist/utils/a.js`가 됩니다. `internal` 아래는 막힙니다.

**조건부 exports**는 값을 객체로 쓰고 키를 조건 이름으로 해서, 불러오는 방식과 환경에 따라 다른 파일로 연결합니다.

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.cjs"
    }
  }
}
```

| 조건 | 뜻 |
|------|----|
| `import` | `import`·`import()`로 불러올 때 |
| `require` | `require()`로 불러올 때 |
| `node` | Node.js 환경 |
| `module-sync` | `import`와 `require` 양쪽에서 쓸 수 있는 동기 ESM |
| `types` | TypeScript가 읽는 타입 선언. 먼저 써야 한다 |
| `browser`, `development`, `production` | 번들러가 쓰는 관례. Node.js에서는 사용자 정의 조건 |
| `default` | 어느 조건도 맞지 않을 때의 대체. 항상 마지막 |

- **키 순서가 우선순위입니다.** 위에서부터 맞는 첫 조건이 선택됩니다. `default`를 앞에 쓰면 뒤의 조건은 무시됩니다. 실제로 `default`가 `import`보다 앞에 있으면 `import` 로드도 `default`가 가리키는 파일을 사용합니다.
- `import`와 `require`는 동시에 맞지 않습니다. 불러오는 방식에 따라 하나만 해당됩니다.
- 조건은 중첩할 수 있습니다(`"node": { "import": ..., "require": ... }`).
- `node --conditions=development app.js`로 사용자 정의 조건을 켭니다.
- 번들러와 TypeScript도 `exports`를 읽습니다.

**이중 패키지 위험**(dual package hazard): 한 패키지가 `import`용과 `require`용으로 다른 파일을 가리키면, 한 프로그램 안에서 두 파일이 모두 로드되어 상태가 이중으로 생기고 `instanceof` 검사가 틀립니다. 한 프로그램에서 두 방식이 섞일 때 문제가 됩니다. 이를 피하려면 ESM 한 벌만 배포하고 `require(esm)`에 맡기거나, `module-sync` 조건으로 같은 파일을 가리키게 합니다.

**`imports` 필드**는 패키지 내부에서만 쓰는 `#` 접두사 별칭입니다.

```json
{
  "type": "module",
  "imports": { "#lib": "./lib.js", "#internal/*.js": "./src/*.js" }
}
```

```js
import v from '#lib' // ./lib.js
```

- 반드시 `#`로 시작해야 외부 패키지와 구분됩니다.
- `exports`와 달리 외부 패키지 이름도 가리킬 수 있고, 조건과 패턴을 지원합니다.
- 패키지 자신의 이름으로 자기 `exports`를 import하는 자기 참조도 가능합니다(`import 'a-package'`).

## 핵심 정리

- 모듈은 구성(그래프 구축) → 인스턴스화(바인딩 연결) → 평가(본문 실행) 순서로 처리되고, 구문·연결 오류는 어떤 코드도 실행되기 전에 드러납니다.
- 모듈은 URL을 키로 한 번만 평가되고 결과가 공유됩니다. 순환에서는 `let`·`const`·`class`가 TDZ에 걸려 ReferenceError가 날 수 있습니다.
- Top-level await는 의존하는 모듈을 지연시키고 형제 모듈은 병렬로 진행합니다. 영원히 끝나지 않으면 Node.js가 종료 코드 13을 반환합니다.
- 정적 분석 덕분에 번들러가 트리 셰이킹을 하며, 배럴 파일은 `sideEffects` 선언이 없으면 불필요한 모듈을 로드하게 만듭니다.
- 브라우저는 `type="module"`과 임포트 맵, Node.js는 `.mjs`·`type: module`과 필수 확장자를 씁니다. CommonJS에서는 `require(esm)`이 동기 ESM에 한해 가능하고, `exports` 조건은 키 순서대로 평가됩니다.

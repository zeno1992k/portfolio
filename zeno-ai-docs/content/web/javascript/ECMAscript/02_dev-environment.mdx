## 브라우저 개발자 도구

개발자 도구(DevTools)는 브라우저에 내장된 검사·디버깅 도구입니다. 실행 중인 페이지의 DOM, 스타일, 네트워크 요청, JavaScript 상태를 보고 바꿀 수 있습니다. 아래는 Chrome 기준이며, 같은 Chromium 기반인 Edge도 거의 같습니다. Firefox와 Safari(Web Inspector)에도 같은 역할의 도구가 있고 패널 이름이 조금 다릅니다.

여는 방법은 다음과 같습니다.

- `F12`, 또는 `Ctrl+Shift+I` (Mac은 `Cmd+Option+I`)
- `Ctrl+Shift+J` (Mac은 `Cmd+Option+J`): Console 패널로 바로 열기
- `Ctrl+Shift+C` (Mac은 `Cmd+Option+C`): 화면의 요소를 클릭해 Elements 패널에서 선택
- 페이지 요소를 우클릭한 뒤 검사(Inspect)
- `Ctrl+Shift+P` (Mac은 `Cmd+Shift+P`): 도구 안의 명령을 이름으로 검색하는 Command Menu

| 패널 | 하는 일 | 이 과목에서 쓰는 경우 |
|------|---------|-----------------------|
| Elements | DOM과 CSS를 보고 수정 | 코드가 만든 요소 확인 |
| Console | 메시지 출력, 코드 즉시 실행 | 출력·에러 확인, 짧은 실험 |
| Sources | 소스 보기, 브레이크포인트, 스니펫 | 디버깅 |
| Network | 요청·응답과 소요 시간 | fetch 결과, 상태 코드 확인 |
| Performance | 실행 시간을 기록해 병목 확인 | 느린 코드 찾기 |
| Memory | 힙 스냅샷과 메모리 할당 기록 | 메모리 누수 추적 (49편) |
| Application | localStorage, 쿠키, 캐시 등 저장소 | 저장된 값 확인 |

패널별로 알아 둘 규칙은 다음과 같습니다.

- Elements에서 고친 DOM과 CSS는 화면에만 반영됩니다. 소스 파일은 바뀌지 않고, 새로고침하면 사라집니다.
- Console은 `Esc`로 다른 패널 아래에 서랍(drawer) 형태로 띄울 수 있습니다. 입력줄에서 `Enter`는 실행, `Shift+Enter`는 줄 바꿈입니다.
- Console에 입력한 코드는 현재 페이지의 전역 스코프에서 실행됩니다. 디버거로 멈춘 상태에서는 멈춘 위치의 스코프에서 실행됩니다.
- Sources의 Snippets에 코드를 저장해 두고 반복 실행할 수 있습니다.
- Network의 Disable cache 옵션은 개발자 도구가 열려 있는 동안만 적용됩니다.
- Console과 Network에는 Preserve log 옵션이 있습니다. 켜면 페이지를 이동하거나 새로고침해도 기록이 남습니다.
- 번들·트랜스파일된 코드는 소스 맵이 있으면 Sources에 원본 파일로 나타나 원본 줄에서 디버깅할 수 있습니다 (자세히는 51편).

Console 입력줄에서만 쓰는 도구 모음(Console Utilities API)이 있습니다. 소스 파일에 넣는 코드가 아닙니다.

| 도구 | 동작 |
|------|------|
| `$0` | Elements에서 마지막으로 선택한 요소 |
| `$_` | 직전에 평가한 식의 결과 |
| `$(css)` | `document.querySelector`와 같음 |
| `$$(css)` | 일치하는 요소 전부를 배열로 반환 |
| `copy(value)` | 값을 문자열로 클립보드에 복사 |
| `keys(obj)`, `values(obj)` | 프로퍼티 이름 배열, 값 배열 |
| `debug(fn)` | `fn`이 호출되면 멈춤 (`undebug(fn)`으로 해제) |
| `monitor(fn)` | `fn`이 호출될 때마다 인수를 출력 |
| `getEventListeners(el)` | 요소에 등록된 이벤트 리스너 목록 |

## console 메서드

`console`은 메시지를 출력하는 호스트 API입니다. ECMAScript가 아니라 Console Standard(WHATWG)가 정의하고, 브라우저와 Node.js가 같은 이름으로 제공합니다 (자세히는 01편).

### 출력 수준: log·info·debug·warn·error

| 메서드 | 브라우저 콘솔의 수준 | Node.js 출력 대상 |
|--------|----------------------|-------------------|
| `log` | Info | stdout |
| `info` | Info | stdout |
| `debug` | Verbose | stdout |
| `warn` | Warnings | stderr |
| `error` | Errors | stderr |

- 인수는 여러 개를 넘길 수 있고 공백으로 이어서 출력됩니다. 객체는 문자열로 바꾸지 않고 검사 형식으로 출력합니다.
- `warn`과 `error`는 출력만 합니다. 예외를 던지거나 실행을 멈추지 않습니다.
- Chrome 콘솔의 기본 필터에는 Verbose가 빠져 있어 `debug` 출력이 보이지 않을 수 있습니다. Log levels 드롭다운에서 켭니다.
- Node.js에서 stdout과 stderr는 별개 스트림입니다. `node app.js > out.txt`로 리다이렉트하면 `log` 계열만 파일에 들어가고 `error`·`warn`은 터미널에 남습니다.

```js
console.log('a', 1, { x: 1 }) // a 1 { x: 1 }
```

### 서식 지정자

첫 인수가 문자열이고 뒤에 인수가 더 있으면, 문자열 안의 `%` 지정자를 뒤 인수로 치환합니다.

| 지정자 | 변환 | 비고 |
|--------|------|------|
| `%s` | 문자열 | |
| `%d` | 숫자 | 표준은 정수 변환 |
| `%i` | 정수 | `parseInt`와 같은 방식 |
| `%f` | 실수 | `parseFloat`와 같은 방식 |
| `%o`, `%O` | 객체를 검사 형식으로 출력 | |
| `%c` | CSS 스타일 적용 | 브라우저 전용. Node.js는 인수만 소비하고 무시 |
| `%j` | JSON 문자열 | Node.js가 추가한 지정자 (표준에 없음) |

```js
console.log('%s: %i', 'Kim', 30.9) // Kim: 30
console.log('%f', '3.14abc')       // 3.14
console.log('%c hi', 'color: red') // 브라우저: 빨간 글자
console.log(5, '%s', 'x')          // 5 %s x
console.log('%s %s', 'one')        // one %s
```

- 지정자는 첫 인수에서만 해석됩니다. 두 번째 이후 인수에 든 `%s`는 그대로 출력됩니다.
- 지정자보다 인수가 적으면 남은 지정자가 그대로 출력됩니다.
- Node.js에서 `%d`는 소수를 그대로 출력합니다(`30.9`). 정수로 자르려면 `%i`를 씁니다.

### 객체와 표: dir·dirxml·table

`dir(obj)`는 객체의 프로퍼티를 목록으로 출력합니다. 브라우저에서 DOM 요소에 `log`를 쓰면 HTML 트리로 보이고, `dir`을 쓰면 객체의 프로퍼티로 보입니다. `dirxml(obj)`은 반대로 DOM 요소를 HTML·XML 트리 형태로 출력하며, Node.js에서는 `log`와 같습니다.

Node.js의 `log`와 `dir`은 중첩을 기본 깊이 2까지만 펼칩니다. 더 깊은 객체는 `[Object]`로 줄여 보여 줍니다.

```js
const o = { a: { b: { c: { d: 1 } } } }
console.log(o) // { a: { b: { c: [Object] } } }
console.dir(o, { depth: null }) // d: 1까지 전부 출력
```

`table(data, columns)`는 배열이나 객체를 표로 출력합니다. 두 번째 인수로 보여 줄 열을 고릅니다.

```js
const users = [
  { name: 'Kim', age: 30 },
  { name: 'Lee', age: 25 },
]
console.table(users)
// (index) | name  | age
// 0       | 'Kim' | 30
// 1       | 'Lee' | 25
console.table(users, ['name']) // name 열만 출력
```

### 그룹: group·groupCollapsed·groupEnd

`group(label)`을 호출하면 이후 출력이 한 단계 들여쓰기되고, `groupEnd()`로 한 단계 되돌립니다. 중첩할 수 있습니다.

```js
console.group('Outer')
console.log('a')     // (들여쓰기) a
console.group('Inner')
console.log('b')     // (두 단계 들여쓰기) b
console.groupEnd()
console.groupEnd()
```

- `groupCollapsed`는 브라우저에서 접힌 상태로 시작합니다. Node.js에서는 `group`과 같습니다.
- `groupEnd`를 빠뜨리면 이후 모든 출력이 들여쓰기된 채로 남습니다.
- Node.js의 들여쓰기는 2칸입니다.

### 횟수와 시간: count·countReset·time·timeLog·timeEnd

`count(label)`은 호출 횟수를 세어 `label: N`으로 출력합니다. 라벨을 생략하면 `default`입니다. `countReset(label)`은 그 라벨의 횟수를 0으로 되돌립니다.

```js
console.count()    // default: 1
console.count()    // default: 2
console.count('x') // x: 1
console.countReset()
console.count()    // default: 1
```

`time(label)`은 타이머를 시작하고, `timeLog(label, ...data)`는 타이머를 유지한 채 경과 시간을 출력하며, `timeEnd(label)`은 경과 시간을 출력하고 타이머를 끝냅니다. 라벨을 생략하면 `default`입니다.

```js
console.time('sum')
let s = 0
for (let i = 0; i < 1e6; i++) s += i
console.timeLog('sum', 'mid') // sum: 1.2ms mid
console.timeEnd('sum')        // sum: 1.3ms
```

- 출력되는 시간 값은 실행마다 다릅니다.
- 이미 끝났거나 없는 라벨에 `timeEnd`·`timeLog`를 부르면 에러가 아니라 경고만 출력됩니다.
- 코드 몇 줄의 대략적인 시간을 볼 때만 씁니다. 정밀한 측정은 Performance 패널이나 `performance.now()`를 씁니다.

### 조건과 추적: assert·trace·clear

`assert(condition, ...message)`는 조건이 거짓일 때만 `Assertion failed:` 뒤에 메시지를 오류 수준으로 출력합니다. 서식 지정자를 쓸 수 있습니다.

```js
console.assert(1 === 1, 'hidden')   // 출력 없음
console.assert(1 === 2, 'x=%s', 1)  // Assertion failed: x=1
console.log('still running')        // 실행은 계속됨
```

`trace(...message)`는 호출된 위치까지의 스택 트레이스를 출력합니다. Node.js에서는 `Trace:`로 시작하고 stderr로 나갑니다. 에러 없이 현재 호출 경로만 확인할 때 씁니다.

```js
function f() { console.trace('here') }
f()
// Trace: here
//     at f (app.js:1:24)
//     at Object.<anonymous> (app.js:2:1)
```

`clear()`는 콘솔을 지웁니다. Node.js에서는 stdout이 터미널일 때만 동작합니다.

### 표준이 아닌 메서드

`timeStamp`, `profile`, `profileEnd`는 Console Standard에 없는 메서드입니다. 브라우저 개발자 도구나 Node.js 검사기(`--inspect`)에 연결되어 있을 때만 의미가 있습니다. `timeStamp(label)`은 Performance 패널의 타임라인에 이벤트를 표시하고, `profile`·`profileEnd`는 CPU 프로파일 기록을 시작하고 끝냅니다.

### 흔한 실수

- **객체의 시점**: Chrome 콘솔은 `console.log(obj)`로 출력한 객체를 펼치는 순간의 값을 읽습니다. 출력 뒤에 객체를 바꿨다면 펼친 값이 출력 시점과 다를 수 있습니다. 시점의 값을 고정하려면 `console.log(JSON.stringify(obj))`나 `console.log(structuredClone(obj))`로 복사본을 출력합니다. Node.js는 출력 시점에 문자열로 만들기 때문에 이 문제가 없습니다.
- **`console.assert`와 `assert` 혼동**: `console.assert`는 메시지만 출력하고 실행을 이어 갑니다. Node.js의 `node:assert` 모듈의 `assert()`는 조건이 거짓이면 `AssertionError`를 던집니다.
- **배포 코드에 남은 `console.log`**: ESLint의 `no-console` 규칙으로 잡습니다 (이 문서의 ESLint와 Prettier 절).

## 디버깅

디버깅은 결함의 원인을 찾아 고치는 과정입니다. 순서는 다음과 같습니다.

1. 같은 결과가 반복해서 나오는 최소 조건을 만듭니다.
2. 에러가 났다면 에러 이름, 메시지, 내 코드의 첫 번째 줄 위치를 읽습니다.
3. 의심 지점에서 실행을 멈추거나 값을 출력합니다.
4. 값이 기대와 처음 달라지는 지점을 찾습니다.
5. 고친 뒤 1번 조건으로 다시 확인합니다.

### 에러 메시지 읽기

에러 메시지는 `에러 이름: 설명` 형식입니다. 브라우저 콘솔과 Node.js REPL은 처리되지 않은 에러 앞에 `Uncaught`를 붙입니다. 에러 이름은 에러의 종류를 뜻합니다 (자세히는 44편).

| 에러 이름 | 의미 | 메시지 예 |
|-----------|------|-----------|
| SyntaxError | 문법 위반. 실행 전 파싱 단계에서 발생 | `Unexpected token '='` |
| ReferenceError | 존재하지 않거나 아직 초기화되지 않은 이름을 참조 | `x is not defined` |
| TypeError | 값의 타입이 연산에 맞지 않음 | `x is not a function` |
| RangeError | 허용 범위를 벗어난 값 | `Invalid array length` |
| URIError | 잘못된 URI 처리 | `URI malformed` |

자주 보는 메시지(V8 엔진 기준)는 다음과 같습니다.

| 메시지 | 원인 | 확인할 것 |
|--------|------|-----------|
| `Cannot read properties of undefined (reading 'x')` | `undefined`의 프로퍼티 `x`를 읽음 | 괄호 안 `x`가 아니라 그 앞 값이 `undefined`인 이유 |
| `Cannot set properties of undefined (setting 'x')` | `undefined`의 프로퍼티에 대입 | 위와 같음 |
| `o.run is not a function` | 함수가 아닌 값을 호출 | 이름 오타, `o.run`이 `undefined`인 이유 |
| `x is not defined` | 선언 없는 이름 참조 | 오타, 스코프 밖 참조 |
| `Cannot access 'x' before initialization` | `let`·`const` 선언 줄 이전에 접근 | 선언 위치 |
| `Assignment to constant variable.` | `const` 재대입 | `let`으로 바꿀지, 재대입이 맞는지 |
| `x is not iterable` | 이터러블이 아닌 값에 `for...of`, 스프레드, 구조 분해 | 배열이어야 하는 값이 아닌 이유 (자세히는 35편) |
| `Maximum call stack size exceeded` | 무한 재귀 | 재귀의 종료 조건 |
| `Unexpected token` | 문법 오류 | 보고된 줄의 앞 줄에 빠진 괄호·쉼표 |

Node.js에서 문법 오류가 나면 파일과 줄, 해당 소스 줄, 위치 표시(`^`), 에러 종류와 메시지 순으로 출력됩니다.

```text
sx.js:2
const = 1
      ^

SyntaxError: Unexpected token '='
```

읽는 규칙은 다음과 같습니다.

- 에러에 적힌 줄은 에러가 감지된 위치입니다. 잘못된 값이 만들어진 위치는 더 앞일 수 있습니다.
- 엔진마다 메시지 문구가 다릅니다 (01편). 에러 이름과 파일·줄 번호를 먼저 보고, 문구는 검색어로 씁니다.
- `NaN`이나 `undefined`가 나오는 의미 오류는 에러 메시지가 없습니다. 값을 직접 검사해 추적해야 합니다.
- 흔한 실수: `catch (e) { console.log(e.message) }`는 메시지만 남기고 스택을 버립니다. 에러 객체 자체를 `console.error(e)`로 출력합니다.

### 브레이크포인트

브레이크포인트는 지정한 지점에서 실행을 멈추는 표시입니다. 멈춘 시점의 변수 값과 호출 경로를 볼 수 있습니다. Chrome에서는 Sources 패널의 줄 번호를 클릭해 줄 브레이크포인트를 설정합니다. 줄 브레이크포인트는 그 줄이 실행되기 직전에 멈춥니다.

| 종류 | 설정 방법 | 멈추는 조건 |
|------|-----------|-------------|
| 줄(Line-of-code) | 줄 번호 클릭 | 그 줄이 실행되기 직전 |
| 조건부(Conditional) | 줄 번호 우클릭, Add conditional breakpoint | 입력한 식이 참일 때 |
| 로그포인트(Logpoint) | 줄 번호 우클릭, Add logpoint | 멈추지 않고 콘솔에 출력 |
| DOM 변경 | Elements에서 요소 우클릭, Break on | 하위 트리 수정, 속성 수정, 노드 제거 |
| XHR/fetch | Sources의 XHR Breakpoints에 URL 문자열 추가 | URL에 그 문자열이 든 요청 |
| 이벤트 리스너 | Event Listener Breakpoints에서 이벤트 선택 | 해당 이벤트의 리스너가 실행될 때 |
| 예외 | Pause on uncaught(또는 caught) exceptions | 예외가 던져질 때 |
| 함수 | 콘솔에서 `debug(fn)` | 그 함수가 호출될 때 |

- 조건부 브레이크포인트는 반복문에서 `i === 500`처럼 특정 반복에서만 멈출 때 씁니다.
- 로그포인트는 코드를 고치지 않고 값을 출력합니다. 지워야 할 `console.log`가 남지 않습니다.
- uncaught는 처리되지 않은 예외에서만, caught는 `try...catch`로 처리되는 예외에서도 멈춥니다.

멈춘 뒤 실행을 이어 가는 조작은 네 가지입니다.

| 동작 | Chrome | VS Code | 설명 |
|------|--------|---------|------|
| Resume / Continue | `F8` | `F5` | 다음 브레이크포인트까지 실행 |
| Step over | `F10` | `F10` | 현재 줄을 실행하고, 함수 호출은 통째로 넘김 |
| Step into | `F11` | `F11` | 현재 줄의 함수 호출 안으로 들어감 |
| Step out | `Shift+F11` | `Shift+F11` | 현재 함수가 끝날 때까지 실행하고 호출한 곳으로 나옴 |

라이브러리 코드로 들어가고 싶지 않으면 Call Stack이나 파일 목록에서 해당 스크립트를 우클릭해 무시 목록(ignore list)에 추가합니다. 이후 Step into가 그 코드를 건너뜁니다.

### 변수 검사

멈춘 상태에서 값을 확인하는 방법은 네 가지입니다.

- **Scope 패널**: 현재 위치에서 접근할 수 있는 지역(Local), 클로저(Closure), 전역(Global) 변수의 값을 보여 줍니다. 값을 더블클릭해 바꾼 뒤 이어서 실행할 수 있습니다.
- **Watch 패널**: 등록한 식을 멈출 때마다, 그리고 Step 조작 때마다 다시 평가합니다.
- **Console**: 멈춘 위치의 스코프에서 식을 평가합니다. 고칠 값을 미리 시험해 볼 수 있습니다.
- **Call Stack 패널**: 호출 경로를 보여 줍니다. 프레임을 선택하면 그 시점의 변수를 볼 수 있습니다.

멈춘 위치의 값은 현재 줄이 실행되기 전 상태입니다. 현재 줄의 대입은 아직 반영되지 않았습니다.

### Node.js에서 디버깅하기

Node.js는 V8 검사기(inspector)를 내장하고 있어서 Chrome 개발자 도구로 같은 방식의 디버깅을 할 수 있습니다.

```bash
node --inspect app.js       # 검사기를 켜고 바로 실행
node --inspect-brk app.js   # 첫 줄에서 멈춘 채 연결 대기
# Chrome 주소창에 chrome://inspect 입력, inspect 클릭
node inspect app.js         # 터미널 안의 간이 디버거
```

- 검사기의 기본 포트는 9229입니다. 공인 IP에 바인딩하면 외부에서 접속할 수 있어 위험하므로 로컬에서만 씁니다.
- 터미널 디버거는 `c`(continue), `n`(next), `s`(step into), `o`(step out), `bt`(호출 경로), `repl`(현재 스코프에서 식 평가) 명령을 씁니다.
- VS Code에서 같은 일을 하는 방법은 이 문서의 VS Code 설정 절에 있습니다.

## 스택 트레이스 읽는 법

스택 트레이스는 에러가 만들어진 시점의 함수 호출 경로를 한 줄에 하나씩 나열한 것입니다 (호출 스택은 22편).

```js
const user = { profile: null }
function getCity(u) { return u.profile.city }
function render(u) { return getCity(u).toUpperCase() }
render(user)
```

위 코드를 `app.js`로 실행하면 다음과 같이 출력됩니다.

```text
TypeError: Cannot read properties of null (reading 'city')
    at getCity (/app/app.js:2:40)
    at render (/app/app.js:3:29)
    at Object.<anonymous> (/app/app.js:4:1)
    at Module._compile (node:internal/...)
```

- 첫 줄은 에러 이름과 메시지입니다.
- V8 형식의 프레임은 `at 함수 이름 (파일:줄:열)`입니다. 줄과 열은 1부터 셉니다.
- **맨 위 프레임이 에러가 발생한 지점**이고, 아래로 갈수록 그 함수를 호출한 쪽입니다. 맨 아래가 실행의 시작점입니다.
- 위 예에서 `null`을 읽다 에러가 난 곳은 `getCity`의 2번째 줄이지만, `null`을 만든 곳은 스택에 없는 1번째 줄의 `user` 정의입니다. 스택은 에러 지점까지의 경로이고 원인의 위치는 아닙니다.
- `node:internal/...`이나 `node_modules/...` 경로는 런타임과 라이브러리 코드입니다. 맨 위가 라이브러리 안이면, 그 아래에서 처음 나오는 내 파일 줄이 잘못된 호출을 한 지점입니다.

프레임의 표기는 다음과 같이 읽습니다.

| 표기 | 의미 |
|------|------|
| `Object.<anonymous>` | CommonJS 파일의 최상위 코드 (파일 전체가 함수로 감싸져 실행되기 때문) |
| `at 파일:줄:열` (이름과 괄호 없음) | 이름 없는 함수(콜백으로 넘긴 화살표 함수 등), 또는 ES 모듈의 최상위 코드 |
| `new User` | 생성자 호출 |
| `User.greet` | `User`의 메서드 호출 |
| `Array.map (<anonymous>)` | 내장 함수 프레임. 소스 위치가 없음 |
| `at async run` | `await` 이후 이어진 비동기 함수의 호출 경로 |

규칙과 한계는 다음과 같습니다.

- `at 함수 (파일:줄:열)` 형식은 V8의 것입니다. Firefox와 Safari는 `함수@파일:줄:열` 형식입니다. 에러의 `stack` 프로퍼티는 표준이 아니고 엔진마다 문자열 형식이 다르므로, 코드에서 문자열을 파싱하는 방식은 피합니다.
- 비동기 함수는 `await` 앞의 호출자를 `at async`로 이어 보여 줍니다. 반면 `setTimeout` 콜백이나 이벤트 핸들러는 호출 스택이 빈 상태에서 새로 시작하므로, 콜백을 등록한 함수가 스택에 나타나지 않습니다 (자세히는 40편).
- V8은 기본으로 10개 프레임까지만 기록합니다(`Error.stackTraceLimit`). 깊은 재귀의 에러는 위쪽 10개만 보입니다. `Error.stackTraceLimit = 50` 또는 `node --stack-trace-limit=50`으로 늘립니다. 이 옵션은 V8의 비표준 기능입니다.
- 번들·트랜스파일된 코드의 스택은 생성된 파일의 줄을 가리킵니다. 브라우저 개발자 도구는 소스 맵이 있으면 원본 위치로 보여 주고, Node.js는 `--enable-source-maps`를 켜면 됩니다 (자세히는 51편).
- 에러에 `cause`를 달아 원인 에러를 이어 붙일 수 있습니다(ES2022). `new Error('설정 로드 실패', { cause: e })` 형태이며 Node.js는 원인의 스택도 함께 출력합니다 (자세히는 44편).
- 에러 없이 현재 호출 경로만 보려면 `console.trace()`를 씁니다. 에러 객체에서는 `err.stack`을 읽습니다.
- 흔한 실수: 잡은 에러를 `throw new Error(e.message)`로 다시 던지면 원래 스택이 사라집니다. 그대로 `throw e`를 하거나 `cause`로 연결합니다.

## debugger 문

`debugger`는 ECMAScript가 정의한 문(statement)입니다. 디버거가 연결되어 있으면 그 위치에서 브레이크포인트처럼 멈추고, 연결되어 있지 않으면 아무 효과가 없습니다.

```js
function total(items) {
  let sum = 0
  for (const item of items) {
    debugger // 디버거가 있으면 매 반복마다 여기서 멈춤
    sum += item.price
  }
  return sum
}
```

- 브라우저는 개발자 도구가 열려 있을 때 멈추고, 닫혀 있으면 무시합니다.
- Node.js는 `node app.js`로 그냥 실행하면 무시하고, `--inspect`, `node inspect`, VS Code 디버거로 실행하면 멈춥니다.
- 조건부 멈춤은 `if (item.price < 0) debugger`처럼 조건문과 함께 씁니다.
- 개발자 도구에서 소스 파일을 찾기 어려운 곳(번들 결과, 동적으로 만든 코드)에 브레이크포인트를 코드로 심을 때 유용합니다.
- 흔한 실수: 지우지 않고 배포하면 사용자가 개발자 도구를 열었을 때 멈춥니다. ESLint의 `no-debugger` 규칙이 추천 설정에 들어 있어 이를 잡아 줍니다.

## Node.js와 npm

### Node.js

Node.js는 브라우저 밖에서 JavaScript를 실행하는 런타임입니다 (자세히는 01편). V8 엔진에 파일, 네트워크, 프로세스 같은 API와 이벤트 루프를 더한 것이고, npm이 함께 설치됩니다.

```bash
node -v   # v24.15.0 같은 설치된 Node.js 버전
npm -v    # 함께 설치된 npm 버전
```

- `import fs from 'node:fs'`처럼 `node:` 접두사를 붙이면 npm 패키지가 아니라 내장 모듈임을 분명히 할 수 있습니다.
- Node.js는 CommonJS(`require`)와 ES 모듈(`import`) 두 방식을 모두 지원합니다. `.js` 파일을 어느 쪽으로 해석할지는 가장 가까운 `package.json`의 `"type"` 값이 정합니다. `"module"`이면 ES 모듈이고, 값이 없으면 CommonJS입니다. `.mjs`는 항상 ES 모듈, `.cjs`는 항상 CommonJS입니다 (자세히는 45·46편).

### package.json

npm은 Node.js의 기본 패키지 매니저입니다. 패키지(package)는 `package.json`이 있는 코드 묶음 단위이고, `package.json`은 프로젝트의 메타데이터, 의존성, 스크립트를 적는 JSON 파일입니다. `npm init -y`가 질문 없이 기본값으로 만들어 줍니다.

```json
{
  "name": "demo",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node app.js",
    "dev": "node --watch app.js"
  },
  "dependencies": { "lodash": "^4.17.21" },
  "devDependencies": { "eslint": "^10.0.0" }
}
```

| 필드 | 뜻 |
|------|----|
| `name`, `version` | 패키지 식별자. 레지스트리에 배포하는 패키지는 필수 |
| `type` | `.js` 파일을 `"module"`(ES 모듈) 또는 `"commonjs"`(기본)로 해석 |
| `scripts` | 이름을 붙인 명령 모음 |
| `dependencies` | 실행에 필요한 패키지 |
| `devDependencies` | 개발·빌드·테스트에만 필요한 패키지 |
| `peerDependencies` | 이 패키지를 쓰는 쪽이 제공해야 하는 패키지. 플러그인 제작자가 씀 |
| `engines` | 지원하는 Node.js·npm 버전. 기본은 권고일 뿐이고 `engine-strict` 설정을 켜야 강제 |
| `private` | `true`이면 실수로 배포하는 것을 막음 |

### 설치와 의존성 관리

| 명령 | 동작 |
|------|------|
| `npm install` | `package.json`과 lock 파일에 적힌 의존성을 모두 설치 |
| `npm install lodash` | 설치하고 `dependencies`에 기록 |
| `npm install -D eslint` | 설치하고 `devDependencies`에 기록 |
| `npm uninstall lodash` | 제거하고 기록에서도 삭제 |
| `npm ci` | lock 파일 그대로 설치. CI·배포용 |
| `npm outdated` | 최신 버전과 다른 패키지 목록 |
| `npm audit` | 알려진 취약점 점검 |

- 설치된 패키지는 `node_modules` 폴더에 들어갑니다. 의존성의 의존성까지 모두 설치되어 크기가 크므로 Git에 올리지 않습니다.
- `package-lock.json`은 설치된 정확한 버전 트리를 기록합니다. 팀원과 CI가 같은 의존성을 설치하도록 Git에 올립니다.
- `npm ci`는 lock 파일이 반드시 있어야 하고, `package.json`과 lock이 어긋나면 갱신하지 않고 에러로 끝납니다. `node_modules`가 있으면 먼저 지우고, `package.json`과 lock을 수정하지 않습니다. `npm install`은 상황에 따라 lock을 갱신할 수 있습니다.
- `-g`로 전역 설치한 패키지는 프로젝트 의존성으로 기록되지 않습니다. 프로젝트에 필요한 도구는 `-D`로 로컬에 설치합니다.

의존성 버전은 시맨틱 버저닝(semver)을 따릅니다. `MAJOR.MINOR.PATCH` 형식이고, 호환을 깨는 변경은 MAJOR, 호환되는 기능 추가는 MINOR, 버그 수정은 PATCH를 올립니다.

| 범위 | 허용하는 버전 |
|------|---------------|
| `1.2.3` | 정확히 1.2.3 |
| `^1.2.3` | 1.2.3 이상 2.0.0 미만 |
| `~1.2.3` | 1.2.3 이상 1.3.0 미만 |
| `^0.2.3` | 0.2.3 이상 0.3.0 미만 (0.x는 MINOR가 호환 단위) |
| `*` | 모든 버전 |

`npm install`이 기록하는 기본 범위는 `^`입니다. lock 파일이 있으면 범위 안의 최신이 아니라 lock에 기록된 버전이 설치됩니다.

### 스크립트와 npx

`npm run <이름>`은 `scripts`의 명령을 실행합니다. 이때 `node_modules/.bin`이 PATH에 추가되므로 로컬에 설치한 도구(`eslint` 등)를 이름만으로 호출할 수 있습니다. `start`와 `test`는 `run`을 생략하고 `npm start`, `npm test`로 실행합니다. Node.js 자체의 `node --run <이름>`(v22.0.0 추가)도 `scripts`를 실행합니다.

`npx <명령>`은 `node_modules/.bin`의 로컬 명령을 실행하고, 없으면 패키지를 임시로 내려받아 실행합니다. 오타로 엉뚱한 패키지를 설치하지 않도록 기본으로 설치 전에 확인을 묻고, `-y`가 이 확인을 건너뜁니다. `npm init vite`는 `create-vite` 패키지를 실행해 프로젝트 틀을 만드는 식으로, `npm init <이름>`은 `create-<이름>` 패키지를 실행합니다.

yarn, pnpm, bun도 같은 `package.json`을 읽는 패키지 매니저입니다. lock 파일 이름이 다르므로(`yarn.lock`, `pnpm-lock.yaml`) 한 프로젝트에서는 하나만 씁니다.

흔한 실수는 다음과 같습니다.

- 서버 실행에 필요한 패키지를 `devDependencies`에 넣으면, 개발 의존성을 빼고 설치하는 환경(`npm install --omit=dev`)에서 모듈을 찾지 못합니다.
- CI에서 `npm install`을 쓰면 lock이 의도치 않게 바뀔 수 있습니다. `npm ci`를 씁니다.
- `node_modules`를 커밋하거나 `package-lock.json`을 지웁니다.

## Node.js LTS와 버전 관리

LTS(Long-Term Support)는 일정 기간 버그와 보안 수정을 보장하는 릴리스 라인입니다. Node.js의 메이저 번호 하나가 한 라인이고, 라인은 세 단계를 거칩니다.

| 단계 | 기간 | 성격 |
|------|------|------|
| Current | 6개월 | 새 메이저. 라이브러리 제작자가 지원을 준비하는 기간 |
| Active LTS | 12개월 | 일반 사용을 권장하는 단계 |
| Maintenance | 18개월 | 중요한 버그와 보안 수정만 반영 |

LTS는 Active와 Maintenance를 합해 30개월입니다. Node.js 26까지의 규칙은 다음과 같습니다.

- 짝수 메이저(22, 24, 26)는 4월에 나오고 10월에 LTS가 됩니다.
- 홀수 메이저(23, 25)는 Current 6개월만 지원하고 LTS가 되지 않습니다.

2026년 10월 초 기준 일정은 다음과 같습니다 (Node.js 공식 릴리스 일정).

| 라인 | 단계 | 일정 |
|------|------|------|
| 26 | Current | 2026-10-28 LTS 진입 예정, 2029-04-30 종료 |
| 24 (Krypton) | Active LTS | 2026-10-20 Maintenance 진입, 2028-04-30 종료 |
| 22 (Jod) | Maintenance | 2027-04-30 종료 |
| 20 | 종료 | 2026년 4월 |

Node.js 27부터 일정이 바뀝니다. 메이저를 연 1회(4월) 내고, 모든 메이저가 LTS가 되며 홀수·짝수 구분이 없어집니다. 출시 전 6개월의 Alpha 단계(10월~3월)가 생기고, 이어서 Current 6개월, LTS 30개월로 총 36개월 지원합니다. 버전 번호는 첫 Current 출시 연도에 맞춰 27(2027), 28(2028)이 됩니다. Alpha는 `27.0.0-alpha.1` 같은 prerelease 버전이며 라이브러리 제작자와 CI용이고 프로덕션에는 쓰지 않습니다. Node.js 27은 2026년 10월에 Alpha가 시작될 예정이고, 2027년 4월에 27.0.0이 나오며, 같은 해 10월에 LTS가 됩니다.

사용 기준은 다음과 같습니다.

- 학습과 프로덕션에는 LTS를 씁니다. Current는 새 기능을 확인할 때만 씁니다.
- 종료(EOL)된 라인은 보안 수정을 받지 못하므로 쓰지 않습니다.
- 설치된 버전은 `node -v`로, 실행 중에는 `process.version`과 `process.versions.v8`로 확인합니다.
- 새 문법과 API를 쓰기 전에 MDN의 호환성 표에서 Node.js 지원 버전을 확인합니다. 낮은 버전에서는 새 문법이 `SyntaxError`, 없는 API 호출이 `TypeError`가 됩니다.

### 버전 관리 도구

버전 관리 도구는 여러 Node.js 버전을 설치해 두고 프로젝트마다 전환하게 해 줍니다.

| 도구 | 특징 | 버전 고정 파일 |
|------|------|----------------|
| nvm | POSIX 셸용(macOS, Linux, WSL). Windows 네이티브는 별개 프로젝트인 nvm-windows | `.nvmrc` |
| fnm | Rust로 만든 크로스 플랫폼 도구. 빠름 | `.node-version`, `.nvmrc` |
| mise | Node.js 외에 여러 도구를 함께 관리 | `mise.toml` |

mise는 `.nvmrc`와 `.node-version`을 읽으려면 별도 설정을 켜야 합니다. Volta는 README에서 더 이상 유지보수하지 않는다고 밝히고 mise를 권장합니다.

```bash
nvm install --lts      # 최신 LTS 설치
nvm use 24             # 현재 셸에서 24 사용
nvm alias default 24   # 새 셸의 기본 버전
echo 24 > .nvmrc       # 프로젝트 버전 고정, nvm use가 읽음
```

- `fnm`의 같은 명령은 `fnm install 24`, `fnm use 24`, `fnm default 24`입니다.
- `.nvmrc`에는 버전 하나만 적고, `lts/*`처럼 LTS 별칭도 쓸 수 있습니다.
- 팀은 `.nvmrc`와 함께 `package.json`의 `engines.node`를 적어 요구 버전을 문서화합니다.

## REPL과 파일 실행

### REPL

REPL(Read-Eval-Print Loop)은 입력을 읽고, 평가하고, 결과를 출력하는 일을 반복하는 대화형 환경입니다. Node.js에서는 인수 없이 `node`를 실행하면 REPL이 시작되고, `.exit`이나 `Ctrl+D`로 끝냅니다. 브라우저의 Console 패널도 같은 역할을 합니다.

```text
> 1 + 2
3
> _ * 10
30
> const a = 5
undefined
> foo()
Uncaught ReferenceError: foo is not defined
> _error.message
'foo is not defined'
```

- 식의 값은 자동으로 출력됩니다. `const a = 5` 같은 선언문은 값이 없어 `undefined`가 출력됩니다. `console.log('x')`는 `x`를 출력한 뒤 반환값 `undefined`도 출력됩니다.
- `_`는 직전 식의 결과이고 `_error`는 마지막으로 발생한 에러입니다. `_`에 직접 대입하면 자동 갱신이 멈춥니다.
- 열린 괄호가 닫히지 않은 입력은 다음 줄로 이어집니다. 입력을 포기하려면 `.break`나 `Ctrl+C`를 씁니다.
- `Tab`은 자동 완성이고, 위·아래 방향키는 히스토리입니다. 히스토리는 홈 폴더의 `.node_repl_history`에 저장되며 `NODE_REPL_HISTORY` 환경 변수로 경로를 바꾸거나 빈 문자열로 끌 수 있습니다.
- 내장 모듈은 `require` 없이 이름으로 바로 씁니다. `fs`, `path`가 그 예입니다.
- 최상위 `await`를 쓸 수 있습니다. `await Promise.resolve(7)`은 `7`을 출력합니다. 다만 `await`를 쓴 입력에서는 `const`의 렉시컬 스코프가 깨지는 한계가 있다고 Node.js 문서에 적혀 있습니다.

| 점 명령 | 동작 |
|---------|------|
| `.help` | 점 명령 목록 출력 |
| `.editor` | 여러 줄 편집 모드. `Ctrl+D`로 실행, `Ctrl+C`로 취소 |
| `.break` | 입력 중인 여러 줄 식을 취소 |
| `.clear` | 기본 REPL에서는 `.break`와 같음 |
| `.load 파일` | 파일의 코드를 현재 세션에 불러와 실행 |
| `.save 파일` | 현재 세션에 입력한 명령을 파일로 저장 |
| `.exit` | REPL 종료 |

### 파일 실행

```bash
node app.js            # app.js를 실행하고 끝나면 종료
node app.js one two    # 인수 전달
node --check app.js    # 실행 없이 문법만 검사
```

- 인수는 `process.argv` 배열로 받습니다. 0번은 node 실행 파일 경로, 1번은 스크립트 경로이고 2번부터가 넘긴 인수입니다. 위 예에서 `process.argv.slice(2)`는 `['one', 'two']`입니다.
- 이벤트 루프에 남은 작업(타이머, 열린 소켓 등)이 없으면 프로세스가 스스로 종료합니다.
- 종료 코드는 정상 종료가 0이고, 처리되지 않은 예외는 1입니다. `process.exitCode = 3`으로 지정할 수 있습니다. `process.exit(n)`은 즉시 종료하므로 대기 중이던 비동기 작업이 중단됩니다.
- 문법 오류가 있으면 파일의 한 줄도 실행되지 않습니다. 첫 줄의 `console.log`도 출력되지 않습니다 (01편).
- `node -e "코드"`는 문자열 코드를 실행하고, `node -p "식"`은 식의 결과를 출력합니다. `node -p "1 + 2"`는 `3`을 출력합니다.
- `node --env-file=.env app.js`는 `.env` 파일의 `KEY=value` 줄을 `process.env`에 넣습니다(v20.6.0 추가, v24.10.0과 v22.21.0에서 안정화). 셸에 이미 있는 환경 변수가 파일 값보다 우선합니다.
- 파일 경로는 스크립트 위치가 아니라 `node`를 실행한 작업 디렉터리 기준입니다. 스크립트 파일 기준 경로가 필요하면 CommonJS는 `__dirname`, ES 모듈은 `import.meta.dirname`을 씁니다.
- 브라우저에서는 HTML의 `<script>` 태그가 파일을 실행합니다 (자세히는 46편).

## node --watch

`node --watch`는 파일이 바뀌면 프로세스를 자동으로 다시 시작하는 Node.js 내장 모드입니다. v18.11.0에 추가되었고 v22.0.0과 v20.13.0에서 안정화되었습니다.

```bash
node --watch app.js
# v1
# Completed running 'app.js'. Waiting for file changes ...
# (파일 저장 후)
# Restarting 'app.js'
# v2
```

- 기본 감시 대상은 진입 파일과, 그 파일이 `require`·`import`하는 모듈입니다.
- `--watch-path=./src`로 감시할 경로를 직접 지정합니다. 여러 번 쓸 수 있고, 지정하면 `require`·`import`된 모듈의 자동 감시는 꺼집니다. `--watch-path`만 써도 watch 모드가 켜집니다.
- `--watch-path`는 macOS와 Windows에서만 지원합니다. 다른 플랫폼에서는 `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM` 예외가 납니다.
- 재시작할 때 화면을 지우는 것이 기본이고, `--watch-preserve-output`이 이를 끕니다.
- 핫 리로드가 아니라 프로세스를 끝내고 새로 시작하는 방식입니다. 메모리의 상태는 모두 사라집니다.
- 스크립트가 끝나도 watch는 종료하지 않고 변경을 기다립니다. `Ctrl+C`로 끝냅니다.
- 실행할 파일 경로가 필요합니다. `-e`, `--check`, `-i`(대화형)나 REPL과는 함께 쓸 수 없습니다.
- 개발 중 스크립트로 `"dev": "node --watch app.js"`를 만들어 `npm run dev`로 씁니다.
- 브라우저 화면을 자동 갱신하는 기능은 별개입니다. 개발 서버의 HMR이 맡습니다 (자세히는 51편).

## VS Code 설정

VS Code는 JavaScript를 별도 설치 없이 지원하는 코드 편집기입니다. TypeScript 언어 서비스가 IntelliSense(자동 완성, 정의로 이동, 시그니처 도움말)를 제공하고, 디버거와 통합 터미널을 내장합니다.

### 설정 파일과 범위

설정은 `Ctrl+,`(Mac은 `Cmd+,`)로 여는 설정 화면이나 JSON 파일로 바꿉니다. 명령 팔레트(`Ctrl+Shift+P`)에서 Preferences: Open User Settings (JSON)을 실행하면 JSON 파일이 열립니다.

| 범위 | 위치 | 용도 |
|------|------|------|
| 사용자(User) | Windows `%APPDATA%\Code\User\settings.json`, macOS `~/Library/Application Support/Code/User/settings.json`, Linux `~/.config/Code/User/settings.json` | 모든 프로젝트에 적용 |
| 작업 영역(Workspace) | 프로젝트의 `.vscode/settings.json` | 그 프로젝트에만 적용. Git으로 팀과 공유 |

- 우선순위는 기본값, 사용자, 작업 영역 순이고 뒤쪽이 앞쪽을 덮어씁니다.
- `"[javascript]"`처럼 언어를 대괄호로 지정한 설정은 범위와 관계없이 언어를 지정하지 않은 설정보다 우선합니다.

```json
{
  "files.autoSave": "onFocusChange",
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "files.insertFinalNewline": true,
  "files.trimTrailingWhitespace": true,
  "[javascript]": {
    "editor.tabSize": 2
  }
}
```

| 설정 | 동작 |
|------|------|
| `files.autoSave` | `off`, `afterDelay`(기본 지연 1000ms), `onFocusChange`, `onWindowChange` 중 선택 |
| `editor.formatOnSave` | 저장할 때 포맷. 기본은 꺼짐 |
| `editor.defaultFormatter` | 포맷을 맡을 확장의 ID |
| `editor.codeActionsOnSave` | 저장할 때 실행할 코드 액션. ESLint 자동 수정에 사용 |
| `editor.tabSize`, `editor.insertSpaces` | 들여쓰기 칸 수(기본 4)와 공백 사용 여부(기본 켜짐) |
| `editor.detectIndentation` | 파일을 열 때 기존 들여쓰기를 감지해 적용 |
| `files.eol` | 새 파일의 줄 끝 문자 |

`source.fixAll.eslint`의 값은 `"explicit"`이거나 `true`입니다. ESLint로 고칠 때는 `editor.formatOnSave`보다 `editor.codeActionsOnSave`를 쓰라고 ESLint 확장 문서가 안내합니다.

### 확장과 프로젝트 파일

- ESLint 확장의 ID는 `dbaeumer.vscode-eslint`, Prettier 확장의 ID는 `esbenp.prettier-vscode`입니다.
- ESLint 확장은 열어 둔 프로젝트에 설치된 `eslint` 패키지를 사용합니다. 확장만 설치하고 `npm install -D eslint`를 하지 않으면 동작하지 않습니다.
- Prettier 확장은 `.prettierrc` 같은 Prettier 설정 파일, `.editorconfig`, VS Code 설정 순서로 읽고, 앞의 것이 있으면 뒤의 것은 쓰지 않습니다. 프로젝트에 `.prettierrc`가 있으면 VS Code의 Prettier 관련 설정은 무시됩니다.
- `.vscode/extensions.json`의 `recommendations`에 확장 ID를 적어 두면 팀원에게 설치를 권장합니다.
- 프로젝트 루트의 `jsconfig.json`은 IntelliSense가 보는 범위를 정합니다. `exclude`에 `node_modules`를 넣는 것이 기본입니다.
- 파일 첫 줄의 `// @ts-check`는 그 JavaScript 파일의 타입 검사를 켜고, JSDoc 주석을 타입 정보로 읽습니다.

### 디버거 설정

Run and Debug 패널에서 `F5`로 실행하거나, `.vscode/launch.json`에 실행 구성을 적습니다.

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "launch",
      "name": "Launch Program",
      "program": "${workspaceFolder}/app.js",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
```

- `program`은 실행할 파일, `skipFiles`는 단계 이동에서 건너뛸 파일입니다. `<node_internals>`는 Node.js 내부 코드입니다.
- 명령 팔레트의 Debug: Create JavaScript Debug Terminal로 만든 터미널에서는 실행하는 Node.js 프로세스가 자동으로 디버깅됩니다.
- Auto Attach 모드는 `smart`, `always`, `onlyWithFlag`(`--inspect`나 `--inspect-brk`를 붙인 경우만)가 있습니다.
- 줄 번호 왼쪽을 클릭해 브레이크포인트를 설정하고 `F9`로 켜고 끕니다. 조건부, 로그포인트, 히트 카운트(`>10`, `%2` 같은 조건) 브레이크포인트를 지원합니다.
- 멈추면 Variables, Watch, Call Stack 뷰와 Debug Console에서 값을 확인합니다. 단축키는 앞의 조작 표와 같습니다.

## ESLint와 Prettier

### ESLint

ESLint는 JavaScript 코드를 실행하지 않고 읽어서 문제가 될 만한 패턴을 찾아 보고하는 린터(linter)입니다. 선언하지 않은 변수, 쓰지 않는 변수, `const` 재대입 같은 버그 가능성이 큰 코드를 잡습니다. 규칙마다 심각도를 `"off"`(0), `"warn"`(1), `"error"`(2)로 정합니다. `error`가 하나라도 있으면 종료 코드가 1이고, `warn`만 있으면 종료 코드에 영향이 없습니다.

설정 파일은 프로젝트 루트의 `eslint.config.js`(flat config)입니다. ESLint 9부터 기본이고, ESLint 10에서는 예전 `.eslintrc` 방식이 완전히 제거되었습니다.

```js
// eslint.config.js
import js from '@eslint/js'
import globals from 'globals'
import { defineConfig } from 'eslint/config'

export default defineConfig([
  {
    files: ['**/*.js'],
    plugins: { js },
    extends: ['js/recommended'],
    languageOptions: { globals: globals.node },
    rules: { eqeqeq: 'error', 'no-console': 'warn' },
  },
])
```

```bash
npx eslint .          # 검사
npx eslint . --fix    # 자동으로 고칠 수 있는 것만 수정
```

- 설정 객체는 배열 순서대로 적용되고 뒤의 것이 앞의 것을 덮어씁니다. `files`는 적용할 파일, `ignores`는 제외할 파일입니다.
- `node_modules`와 `.git`은 기본으로 제외됩니다. 기본 검사 대상은 `.js`, `.cjs`, `.mjs` 파일입니다.
- `js/recommended`에는 `no-undef`, `no-unused-vars`, `no-const-assign`, `no-debugger`가 들어 있습니다. `eqeqeq`(`==` 금지), `no-console`, `no-var`, `prefer-const`는 들어 있지 않아 직접 켭니다.
- 기본 `languageOptions`는 `ecmaVersion: 'latest'`이고, `sourceType`은 `.js`와 `.mjs`가 `module`, `.cjs`가 `commonjs`입니다.
- `console`, `document`, `process`는 ECMAScript가 아닌 호스트 API입니다 (01편). `languageOptions.globals`에 `globals.browser`나 `globals.node`로 알려 주지 않으면 `no-undef`가 에러를 냅니다.
- 최신 ESLint는 Node.js `^20.19.0`, `^22.13.0`, `>=24` 이상을 요구합니다.

### Prettier

Prettier는 의견이 강한(opinionated) 코드 포맷터입니다. 코드를 파싱한 뒤 정해진 규칙으로 다시 출력해서 줄 바꿈, 들여쓰기, 따옴표, 세미콜론, 쉼표의 모양을 통일합니다. 코드의 동작은 바꾸지 않습니다. 버그를 고치거나, import를 정렬하거나, 쓰지 않는 코드를 지우지 않고 모양만 다룹니다.

```bash
npx prettier --write .   # 파일을 직접 고쳐 씀
npx prettier --check .   # 검사만. 다르면 실패 (CI용)
```

설정은 `.prettierrc` 같은 파일에 적고, 적지 않은 옵션은 기본값을 씁니다.

| 옵션 | 기본값 |
|------|--------|
| `printWidth` | 80 |
| `tabWidth` | 2 |
| `useTabs` | false |
| `semi` | true |
| `singleQuote` | false |
| `trailingComma` | `"all"` (Prettier 3.0부터. 이전은 `"es5"`) |
| `arrowParens` | `"always"` |
| `endOfLine` | `"lf"` |

`printWidth`는 엄격한 한계가 아니라 목표치입니다. 긴 식별자처럼 줄이면 오히려 읽기 어려운 경우에는 이를 넘기기도 합니다.

### 역할 구분

| 구분 | ESLint | Prettier |
|------|--------|----------|
| 하는 일 | 문제 있는 코드를 탐지 (품질) | 코드 모양을 통일 (서식) |
| 잡는 예 | 선언 없는 변수, 쓰지 않는 변수, `debugger` | 들여쓰기, 따옴표, 줄 바꿈 |
| 자동 수정 | 고칠 수 있는 규칙만 `--fix` | 항상 전체를 다시 출력 |
| 설정 파일 | `eslint.config.js` | `.prettierrc` |

- ESLint에도 서식 규칙이 있어서 Prettier와 충돌하면 저장할 때마다 서로의 결과를 되돌립니다. `eslint-config-prettier`를 설정에 넣으면 충돌하는 ESLint 규칙이 꺼집니다.
- Prettier를 ESLint 규칙으로 실행하는 `eslint-plugin-prettier` 방식은 느리고 편집기에 서식 경고가 넘쳐 Prettier 문서가 권장하지 않습니다. 둘은 따로 실행합니다.
- 권장 흐름은 저장할 때 Prettier로 포맷하고 ESLint로 자동 수정하며, 커밋 전이나 CI에서 `prettier --check .`와 `eslint .`를 실행하는 것입니다.
- ESLint를 통과해도 버그가 없다는 뜻은 아닙니다. 린터는 정해진 패턴만 검사하므로 로직 오류는 잡지 못합니다.

## 핵심 정리

- 개발자 도구에서 Console은 출력과 즉시 실행, Sources는 브레이크포인트와 단계 실행, Network는 요청 확인에 씁니다. `console`은 ECMAScript가 아닌 호스트 API이고, `log`·`warn`·`error` 외에 `table`, `group`, `count`, `time`, `assert`, `trace`가 있습니다.
- 에러는 이름, 메시지, 내 코드의 첫 위치 순으로 읽습니다. 스택 트레이스는 맨 위 프레임이 발생 지점이고, 아래로 갈수록 호출한 쪽입니다.
- 멈춘 시점의 값은 Scope, Watch, Console로 확인합니다. `debugger` 문은 디버거가 연결되었을 때만 멈추고, 없으면 아무 효과가 없습니다.
- Node.js는 브라우저 밖의 런타임이고 npm은 `package.json`과 `package-lock.json`으로 의존성을 관리합니다. 프로덕션에는 LTS를 쓰며, Node.js 27부터는 모든 메이저가 LTS가 됩니다.
- `node`(REPL), `node 파일`, `node --watch 파일`로 실행하고, 개발 중 재시작은 `--watch`가 맡습니다.
- ESLint는 품질 문제를 찾고 Prettier는 서식만 통일합니다. 둘은 역할이 달라 충돌하는 규칙만 꺼서 함께 씁니다.

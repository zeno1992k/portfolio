## 콜백 패턴의 한계

콜백 패턴은 비동기 작업이 끝났을 때 실행할 함수를 인수로 넘기는 방식입니다. 중첩이 깊어지는 문제(콜백 헬)는 40편에서 다뤘습니다. 중첩을 펴도 남는 구조적 한계는 네 가지입니다.

**제어의 역전.** 콜백을 언제, 몇 번 호출할지는 호출받는 쪽(라이브러리)이 정합니다. 호출자는 다음을 보장할 수 없습니다.

- 정확히 한 번만 호출된다 (0번이나 2번 이상 호출될 수 있습니다).
- 항상 비동기로 호출된다 (어떤 경로에서는 동기로 호출될 수 있습니다).

```js
function getUser(id, cb) {
  if (cache.has(id)) cb(cache.get(id)) // 동기 호출
  else fetchUser(id, cb)               // 비동기 호출
}

let x = 'before'
getUser(1, () => console.log(x))
x = 'after'
// 캐시 적중: before / 캐시 미스: after
```

캐시에 있으면 콜백이 `x = 'after'`보다 먼저 실행되고, 없으면 나중에 실행되기 때문입니다.

**에러를 전달할 수 없음.** 콜백은 `try` 블록이 끝난 뒤 새 호출 스택에서 실행되므로 바깥의 `try...catch`가 콜백 안의 에러를 받지 못합니다.

```js
try {
  setTimeout(() => { throw new Error('x') }, 0)
} catch (e) {
  console.log('여기에 오지 않는다')
}
// 에러는 전역 오류(uncaught exception)가 된다
```

Node.js는 콜백의 첫 인수를 에러 자리로 약속하는 error-first 관례로 이 문제를 우회합니다. 이 관례는 모든 단계에서 `if (err)`를 직접 검사해야 하고, 하나라도 빠뜨리면 에러가 조용히 사라집니다.

**합성의 어려움.** 순차 실행은 중첩으로, 병렬 실행 뒤 결과 합치기는 카운터 변수로 직접 구현해야 합니다.

```js
let left = 2
const out = []
a((err, x) => { out[0] = x; if (--left === 0) done(out) })
b((err, y) => { out[1] = y; if (--left === 0) done(out) })
```

여기에 에러 처리와 조기 종료를 더하면 코드가 급격히 늘어납니다.

**값이 아님.** 비동기 결과는 콜백 안에서만 존재합니다. 변수에 담거나 함수에서 반환하거나 다른 함수에 인수로 넘길 수 없습니다.

프로미스(Promise)는 이 네 가지를 언어 차원의 규칙으로 해결합니다.

| 콜백의 문제 | 프로미스의 보장 |
|-------------|-----------------|
| 여러 번 호출 | 한 번만 정착하고, 이후의 resolve·reject 호출은 무시 |
| 동기·비동기 혼재 | then 콜백은 항상 비동기(마이크로태스크)로 호출 |
| 에러 유실 | 거부가 체인을 따라 전파 |
| 합성 어려움 | 체이닝과 `Promise.all` 같은 정적 메서드 |
| 값이 아님 | 프로미스는 객체이므로 변수·반환값·인수로 전달 가능 |

프로미스도 내부적으로는 콜백(then의 인수)을 씁니다. 차이는 호출 규칙을 호출받는 쪽이 아니라 표준 구현이 보장한다는 점입니다.

## 프로미스 생성

프로미스는 비동기 작업의 최종 결과(성공 값 또는 실패 이유)를 나타내는 객체입니다. `new Promise(executor)`로 만듭니다.

```js
const p = new Promise((resolve, reject) => {
  console.log('executor') // 즉시 실행된다
  resolve('done')
})
console.log('after')
// executor
// after
```

- executor는 생성자가 반환되기 전에 동기로 실행됩니다. 프로미스는 지연 실행이 아니므로 `then`을 호출하지 않아도 작업이 이미 시작되어 있습니다. "나중에 실행할 작업"은 프로미스가 아니라 프로미스를 반환하는 함수로 표현합니다.
- `resolve`와 `reject`는 엔진이 만들어 executor에 넘기는 함수이고, 각각 인수를 하나만 받습니다. 값이 여러 개면 객체나 배열로 묶습니다.
- 두 함수는 합쳐서 한 번만 효력이 있습니다. 첫 호출 뒤의 호출은 에러 없이 무시됩니다.
- `resolve`를 호출해도 executor는 멈추지 않습니다. 뒤에 코드가 있으면 계속 실행됩니다.
- executor가 반환하는 값은 무시됩니다.
- `new` 없이 `Promise(...)`를 호출하거나 함수가 아닌 값을 executor로 넘기면 `TypeError`입니다.

```js
new Promise((resolve, reject) => {
  resolve('first')
  reject(new Error('ignored')) // 무시
  console.log('still runs')    // 출력된다
}).then(console.log)           // first
```

## 프로미스 상태

프로미스는 세 상태 중 하나입니다.

| 상태 | 뜻 | 가진 값 |
|------|----|---------|
| pending | 대기. 초기 상태 | 없음 |
| fulfilled | 이행. 작업 성공 | 성공 값(value) |
| rejected | 거부. 작업 실패 | 실패 이유(reason) |

- pending에서 fulfilled나 rejected로 단 한 번만 바뀝니다. 정착한 뒤에는 상태도 값도 바뀌지 않습니다.
- 정착(settled)은 pending이 아닌 상태, 즉 fulfilled 또는 rejected를 가리킵니다.
- 정착한 프로미스에 나중에 `then`을 걸어도 보존된 값을 받습니다.
- 상태를 동기로 읽는 API는 없습니다. 값은 `then`으로만 꺼냅니다.

```js
const a = new Promise(() => {})
const b = Promise.resolve(1)
const c = Promise.reject(2)
console.log(a) // Promise { <pending> }
console.log(b) // Promise { 1 }
console.log(c) // Promise { <rejected> 2 }
```

콘솔에 보이는 표기는 개발자 도구와 런타임이 만든 것이고 형식은 환경마다 다릅니다. 거부 이유에는 어떤 값이든 쓸 수 있지만 `Error` 객체를 쓰는 것이 관례입니다. 스택 트레이스가 붙기 때문입니다(자세히는 44편).

## executor 안의 throw

executor는 엔진이 예외를 잡는 상태로 실행하므로 동기 `throw`는 그 프로미스의 거부로 바뀝니다.

```js
new Promise(() => { throw new Error('boom') })
  .catch((e) => console.log(e.message)) // boom
```

- `resolve`나 `reject`를 이미 호출한 뒤의 `throw`는 무시됩니다. 이미 결정된 프로미스이기 때문입니다.

```js
new Promise((resolve) => {
  resolve('ok')
  throw new Error('late') // 무시
}).then(console.log)      // ok
```

- 비동기 콜백 안의 `throw`는 거부로 바뀌지 않습니다. 콜백은 executor의 호출 스택이 끝난 뒤 실행되므로 예외를 잡아 줄 주체가 없고, 전역 오류가 됩니다. 그 안에서 `reject`를 호출해야 합니다.

```js
new Promise((resolve, reject) => {
  setTimeout(() => { throw new Error('x') }, 0)       // ❌
  setTimeout(() => reject(new Error('x')), 0)         // ✅
})
```

- `async` 함수를 executor로 쓰는 문제는 안티패턴 절에서 다룹니다.
- `then` 콜백 안의 `throw`도 같은 원리로 거부가 됩니다(반환값 규칙 절).

## then·catch·finally

`then(onFulfilled, onRejected)`는 프로미스가 정착했을 때 호출할 콜백을 등록하고, 새 프로미스를 반환합니다.

```js
p.then(
  (value) => { /* 이행되면 호출 */ },
  (reason) => { /* 거부되면 호출 */ },
)
```

- 두 인수는 모두 선택입니다. 함수가 아닌 값(`undefined`, `null`, `2` 등)은 무시되고, 값이나 이유가 그대로 다음으로 전달됩니다. 이행 쪽이 비면 값을 그대로 넘기고, 거부 쪽이 비면 이유를 그대로 다시 던집니다.
- 콜백은 항상 비동기로 호출됩니다. 이미 정착한 프로미스에 걸어도 현재 동기 코드가 끝난 뒤 호출됩니다.
- 한 프로미스에 `then`을 여러 번 걸 수 있습니다. 콜백은 등록한 순서대로 호출되고 서로 독립입니다.

```js
const p = Promise.resolve(1)
p.then((v) => console.log('A', v))
p.then((v) => console.log('B', v))
console.log('sync')
// sync → A 1 → B 1
```

`catch(onRejected)`는 `then(undefined, onRejected)`와 같습니다.

`finally(onFinally)`(ES2018)는 이행·거부와 관계없이 정착하면 호출됩니다.

- 콜백에 인수가 전달되지 않습니다. 값이나 이유를 볼 수 없습니다.
- 콜백의 반환값은 무시되고, 원래의 값이나 이유가 그대로 다음으로 전달됩니다.
- 콜백이 프로미스를 반환하면 그 프로미스가 정착할 때까지 기다린 뒤 전달합니다.
- 콜백이 `throw`하거나 거부된 프로미스를 반환하면 그 이유가 원래 결과를 덮어씁니다.

```js
Promise.resolve(1).finally(() => 2)
  .then((v) => console.log(v))          // 1
Promise.resolve(1).finally(() => { throw new Error('F') })
  .catch((e) => console.log(e.message)) // F
```

| 메서드 | 호출 시점 | 콜백 인수 | 반환 프로미스의 결과 |
|--------|-----------|-----------|----------------------|
| `then(f, r)` | 이행(f) 또는 거부(r) | 값 또는 이유 | 콜백의 반환값 규칙을 따름 |
| `catch(r)` | 거부 | 이유 | 콜백이 값을 반환하면 이행으로 복구 |
| `finally(f)` | 정착 | 없음 | 원래 결과 유지, 콜백이 던지면 그 이유로 거부 |

흔한 실수는 `finally`의 반환값으로 결과를 바꾸려는 것입니다. 결과를 바꾸려면 `then`이나 `catch`를 씁니다. `finally`는 로딩 표시 끄기나 자원 해제처럼 결과와 무관한 정리 작업에 씁니다.

## then 콜백의 반환값 규칙

`then`이 반환하는 프로미스(이하 파생 프로미스)의 결과는 콜백이 무엇을 하는지로 정해집니다. `catch`와 `finally`의 콜백에도 같은 규칙이 적용됩니다.

| 콜백이 | 파생 프로미스 |
|--------|---------------|
| 값을 반환 | 그 값으로 이행 |
| 아무것도 반환하지 않음 | `undefined`로 이행 |
| 프로미스나 thenable을 반환 | 그 프로미스가 정착할 때까지 대기한 뒤 같은 결과로 정착 |
| `throw` | 던진 값으로 거부 |
| 호출되지 않음(해당 인수가 함수가 아님) | 앞 프로미스의 결과를 그대로 전달 |

thenable은 `then` 메서드를 가진 객체입니다(자세한 규칙은 thenable 절).

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms))

Promise.resolve(1)
  .then((v) => v + 1)                     // 2
  .then(() => {})                         // undefined
  .then(() => sleep(100).then(() => 'x')) // 100ms 뒤 'x'
  .then((v) => { throw new Error(v) })    // 거부
```

- 프로미스를 반환하면 한 겹 풀려서 전달됩니다. 다음 `then`은 프로미스가 아니라 그 값을 받습니다. 반환한 프로미스가 거부되면 파생 프로미스도 거부됩니다.
- 파생 프로미스 자기 자신을 반환하면 순환이므로 `TypeError`로 거부됩니다.
- 프로미스를 반환할 때와 일반 값을 반환할 때는 파생 프로미스가 정착하기까지 걸리는 마이크로태스크 횟수가 다릅니다(마이크로태스크 절).

흔한 실수는 `return`을 빠뜨리는 것입니다.

```js
getUser()
  .then((user) => { getPosts(user.id) }) // ❌ return 없음
  .then((posts) => console.log(posts))   // undefined

getUser()
  .then((user) => getPosts(user.id))     // ✅ 프로미스를 반환
  .then((posts) => console.log(posts))   // 게시글 배열
```

❌ 코드에서는 다음 `then`이 `getPosts`를 기다리지 않고 바로 `undefined`를 받습니다. `getPosts`가 거부되어도 이 체인과 연결되지 않으므로 그 에러는 체인 밖으로 새어 나가 미처리 거부가 됩니다.

## 체이닝

체이닝은 `then`·`catch`·`finally`가 새 프로미스를 반환한다는 점을 이용해 비동기 단계를 순서대로 이어 붙이는 방식입니다.

```js
getUser(1)
  .then((user) => getPosts(user.id))
  .then((posts) => posts.filter((p) => p.published))
  .then((list) => console.log(list.length))
  .catch((e) => console.error(e))
```

- 각 단계의 반환값이 다음 단계의 입력입니다.
- 각 단계는 앞 단계가 정착한 뒤에 실행되므로 순서가 보장됩니다.
- 중첩 대신 `return`으로 평탄하게 유지합니다. 앞 단계의 값을 뒤에서도 써야 할 때만 안쪽에서 `then`을 한 번 더 걸어 클로저로 접근합니다.

```js
getUser(1)
  .then((user) =>
    getPosts(user.id).then((posts) => ({ user, posts })))
  .then(({ user, posts }) => render(user, posts))
```

**분기.** 같은 프로미스에 `then`을 두 번 걸면 두 체인이 독립적으로 생깁니다. 한쪽의 반환값이나 에러는 다른 쪽에 영향을 주지 않습니다. 체인의 결과를 이어받으려면 `then`이 반환한 프로미스에 이어 걸어야 합니다.

```js
const p = Promise.resolve(1)
p.then((v) => v + 1)           // 반환값은 어디에도 전달되지 않는다
p.then((v) => console.log(v))  // 1 (2가 아니다)
```

**순차 반복.** 배열의 비동기 작업을 하나씩 순서대로 실행할 때는 `reduce`로 체인을 만듭니다.

```js
const ids = [1, 2, 3]
ids.reduce(
  (chain, id) => chain.then(() => save(id)),
  Promise.resolve(),
) // save(1)이 끝나면 save(2), 끝나면 save(3)
```

`ids.map(save)`처럼 한꺼번에 시작하는 방식은 병렬 실행입니다. 순차와 병렬의 선택은 43편에서 다시 다룹니다.

## 에러 처리

프로미스의 거부는 체인을 따라 내려가다가 거부 핸들러를 가진 가장 가까운 `then`이나 `catch`에서 처리됩니다. 거부 핸들러가 없는 중간 `then`은 건너뜁니다.

```js
Promise.reject(new Error('x'))
  .then(() => console.log('건너뜀'))
  .catch((e) => 'fallback')
  .then((v) => console.log(v)) // fallback
```

- `catch`가 값을 반환하면 체인은 이행 상태로 복구됩니다. 다시 `throw`하면 거부가 이어집니다.
- `catch`는 체인 끝에 두는 것이 기본이고, 중간의 `catch`는 에러를 복구해 체인을 이어 갈 때만 씁니다.
- `then(a, b)`의 `b`는 같은 `then`의 `a`가 던진 에러를 받지 못합니다. 앞 프로미스의 거부만 처리합니다.

```js
const p = Promise.resolve()

p.then(
  () => { throw new Error('a') },
  () => console.log('b'),            // 호출되지 않는다
) // a의 에러는 처리되지 않고 거부로 남는다

p.then(() => { throw new Error('a') })
  .catch((e) => console.log(e.message)) // a
```

- 에러를 로그만 남기고 삼키면 안 됩니다. `.catch((e) => console.log(e))`는 `undefined`를 반환하므로 체인이 성공으로 바뀌고, 호출자는 실패를 알 수 없습니다. 처리할 수 없는 에러는 다시 `throw`합니다(처리·기록·다시 던지기는 44편).
- `try...catch`는 `await` 없이는 프로미스의 거부를 잡지 못합니다. 거부는 비동기로 일어납니다.

```js
try {
  Promise.reject(new Error('x')) // 기다리지 않는다
} catch (e) {
  console.log('실행되지 않는다')  // 거부는 미처리가 된다
}
```

`await`와 `try...catch`의 조합은 43편, 비동기 에러의 한계는 44편에서 다룹니다.

## 처리되지 않은 거부

거부된 프로미스에 거부 핸들러가 하나도 없으면 미처리 거부입니다. ECMAScript는 프로미스가 거부될 때와 처음으로 핸들러가 붙을 때 호스트에 알리는 훅(HostPromiseRejectionTracker)만 정하고, 그 알림을 어떻게 처리할지는 호스트가 정합니다. 프로미스는 `then`이 한 번이라도 호출되면 처리된 것으로 칩니다(`catch`와 `finally`도 내부에서 `then`을 호출합니다). 그래서 `p.then(f)`처럼 거부 핸들러 없이 `then`만 걸면 `p`는 처리된 것이 되지만, `then`이 반환한 파생 프로미스가 같은 이유로 거부되어 그쪽이 미처리 거부가 됩니다. `finally`도 같습니다. 거부 핸들러는 체인의 마지막 프로미스에 있어야 합니다.

| 환경 | 통지 방식 | 기본 동작 |
|------|-----------|-----------|
| 브라우저 | `window`·워커에 `unhandledrejection` 이벤트(`promise`, `reason`) | 콘솔에 오류 출력. `preventDefault()`로 억제 가능 |
| Node.js | `process.on('unhandledRejection', (reason, promise) => ...)` | 처리하는 핸들러가 없으면 처리되지 않은 예외로 승격되어 프로세스 종료 (Node.js 15부터) |

- 판정 시점은 거부가 일어난 작업과 그 뒤 마이크로태스크가 끝난 시점입니다. 그 안에 핸들러를 붙이면 미처리가 아닙니다. `setTimeout` 같은 이후 작업에서 붙이면 이미 이벤트가 발생한 뒤입니다.
- 이미 통지된 프로미스에 나중에 핸들러가 붙으면 브라우저는 `rejectionhandled` 이벤트를, Node.js는 `'rejectionHandled'` 이벤트를 발생시킵니다.

```js
const p = Promise.reject(new Error('B'))
p.catch(() => {})                       // 같은 동기 구간: 정상 처리
const q = Promise.reject(new Error('Q'))
setTimeout(() => q.catch(() => {}), 10) // 너무 늦다
// q: unhandledRejection 발생 후 rejectionHandled 발생
```

- 서버 프로세스는 미처리 거부 한 번에 종료될 수 있으므로 모든 프로미스 체인은 끝에서 거부를 처리하거나 `await`와 `try...catch`로 감쌉니다.
- 전역 이벤트는 최후의 기록용 방어선이고 정상적인 에러 처리를 대신하지 않습니다.
- `Promise.all`로 묶은 프로미스들은 `all`이 각각에 핸들러를 붙이므로, 먼저 거부된 하나 이후의 거부가 미처리 거부로 보고되지 않습니다.

## Promise.resolve·reject

`Promise.resolve(value)`는 인수에 따라 세 가지로 동작합니다.

- 같은 생성자로 만든 프로미스면 그 객체를 그대로 반환합니다.
- thenable이면 그 상태를 따라가는 새 프로미스를 반환합니다.
- 그 밖의 값이면 그 값으로 이행된 새 프로미스를 반환합니다.

```js
const p = Promise.resolve(1)
Promise.resolve(p) === p       // true
new Promise((r) => r(p)) === p // false (항상 새 프로미스)
```

`Promise.reject(reason)`은 항상 새 거부 프로미스를 만들고, 프로미스를 넘겨도 풀지 않습니다.

```js
const r = Promise.reject(Promise.resolve(1))
r.catch((reason) => console.log(reason))
// Promise { 1 } — 이유가 프로미스 객체 자체
```

용도는 다음과 같습니다.

- **값 정규화.** 일반 값과 프로미스를 모두 받는 함수에서 `Promise.resolve(x).then(...)`으로 한 경로로 처리합니다.
- **이미 아는 값 반환.** 캐시 적중 시 `return Promise.resolve(cached)`로 반환 타입을 프로미스로 통일합니다.
- **동기 검증 실패를 거부로 전달.** 프로미스를 반환하는 함수는 실패도 거부로만 알려야 합니다. `throw`와 거부를 섞으면 호출자가 `try...catch`와 `.catch`를 모두 써야 합니다.
- **체인 시작.** `Promise.resolve().then(fn)`은 `fn`을 마이크로태스크로 미룹니다.

```js
function load(id) {
  if (!id) return Promise.reject(new TypeError('id 필요'))
  return fetchItem(id)
}
```

두 메서드는 `this`를 생성자로 사용하므로 변수로 떼어내 호출하면 `TypeError`입니다. `[1, 2].map(Promise.resolve)`는 에러가 나고 `.map((x) => Promise.resolve(x))`로 써야 합니다.

## thenable

thenable은 함수인 `then` 프로퍼티를 가진 객체입니다. Promises/A+ 규격이 정한 프로미스 구현 사이의 호환 규약이며, ES2015부터 표준 프로미스도 이 규약을 따릅니다.

```js
const thenable = {
  then(resolve) { resolve(42) },
}
Promise.resolve(thenable).then(console.log) // 42
```

`resolve(x)`, `Promise.resolve(x)`, `then` 콜백의 반환값, `await`는 값이 thenable이면 `x.then(resolveFn, rejectFn)`을 호출해 그 상태를 따라갑니다.

- `then`은 동기로 호출되지 않고 마이크로태스크에서 호출됩니다.
- thenable이 `resolve`를 여러 번 호출하거나 호출한 뒤 `throw`해도 첫 호출만 유효하고 나머지는 무시됩니다.
- `x.then`을 읽다가 던져도(getter 예외) 그 프로미스는 거부됩니다.
- `then`이 함수가 아니면 일반 객체이므로 `{ then: 5 }`는 그 객체 값으로 이행됩니다.
- thenable은 프로미스가 아닙니다. `instanceof Promise`가 `false`이고 `catch`·`finally` 메서드도 없습니다. `Promise.resolve(thenable)`로 감싸야 프로미스가 됩니다.

흔한 실수는 이름이 우연히 `then`인 메서드를 가진 객체를 값으로 쓰는 것입니다. 그런 객체를 `resolve`·`return`·`await`에 넘기면 값이 아니라 thenable로 취급되어 풀립니다. 프로미스로 전달할 데이터 객체에는 `then`이라는 이름을 쓰지 않습니다.

## resolve와 fulfill의 차이

fulfill은 프로미스를 fulfilled 상태로 확정하는 것이고, resolve는 프로미스의 운명을 결정하는 것입니다. 인수가 일반 값이면 resolve는 곧 fulfill이지만, 프로미스나 thenable이면 그 결과를 따라가도록 프로미스를 잠급니다. 잠긴 프로미스는 이미 resolved이지만 상태는 아직 pending일 수 있습니다.

```js
const inner = new Promise((r) => setTimeout(r, 100, 'x'))
const outer = new Promise((resolve) => resolve(inner))
// outer: resolve 호출은 끝났지만(잠김) 아직 pending
// 100ms 뒤 inner가 이행되면 outer도 'x'로 이행
```

| 호출 | 결과 |
|------|------|
| `resolve(일반 값)` | 그 값으로 fulfilled |
| `resolve(프로미스·thenable)` | 잠긴 뒤 그 결과를 따라감. 이행되면 fulfilled, 거부되면 rejected |
| `resolve(자기 자신)` | `TypeError`로 rejected |
| `reject(x)` | `x` 그대로 rejected. `x`가 프로미스여도 풀지 않음 |

용어의 범위는 다음과 같습니다.

- settled: fulfilled 또는 rejected.
- resolved: settled이거나, 다른 프로미스에 잠긴 상태.
- 따라서 resolved이면서 pending인 프로미스가 있고, fulfilled는 resolved의 부분 집합입니다.

잠긴 뒤에는 `resolve`·`reject`를 다시 호출해도 무시되므로 다른 값으로 바꿀 수 없습니다. 이름과 달리 `resolve`에 거부된 프로미스를 넘기면 거부로 끝납니다.

프로미스로 resolve하면 일반 값으로 resolve할 때보다 비용이 있습니다. thenable의 `then`을 호출하는 작업과 그 결과를 구독하는 작업이 마이크로태스크로 추가되어 두 번 더 기다립니다(마이크로태스크 절).

## Promise.all

`Promise.all(iterable)`은 모든 프로미스가 이행되면 이행 값의 배열로 이행하고, 하나라도 거부되면 거부하는 프로미스를 반환합니다.

```js
const t = (ms, v) =>
  new Promise((r) => setTimeout(r, ms, v))

Promise.all([t(30, 'a'), t(10, 'b'), 'c'])
  .then(console.log) // ['a', 'b', 'c']
```

- 입력은 이터러블이면 됩니다(배열, `Set`, 문자열 등). 요소는 `Promise.resolve`로 감싸지므로 프로미스가 아닌 값과 thenable도 섞을 수 있습니다.
- 결과 배열은 완료 순서가 아니라 입력 순서입니다.
- fail-fast: 가장 먼저 거부된 프로미스의 이유로 즉시 거부합니다. 이후의 거부는 무시됩니다.
- 나머지 프로미스는 취소되지 않고 끝까지 실행되며, 그 결과만 버려집니다.
- 빈 이터러블이면 `[]`로 이미 이행된 프로미스를 반환합니다.
- 이터러블이 아닌 값을 넘기면 던지지 않고 `TypeError`로 거부된 프로미스를 반환합니다.
- 프로미스는 만들어진 순간 작업이 시작되므로 `Promise.all`이 병렬 실행을 만드는 것이 아닙니다. 이미 시작된 작업들을 함께 기다릴 뿐입니다.

흔한 실수는 일부 실패를 허용해야 하는 상황에서 `all`을 쓰는 것입니다. 하나가 실패하면 다른 성공 결과도 모두 받을 수 없습니다. 이럴 때는 `allSettled`를 씁니다.

## Promise.allSettled

`Promise.allSettled(iterable)`(ES2020)은 모든 프로미스가 정착할 때까지 기다린 뒤 각 결과를 기술한 객체의 배열로 이행합니다. 입력 프로미스가 거부되어도 거부되지 않습니다.

```js
Promise.allSettled([
  Promise.resolve(1),
  Promise.reject('no'),
]).then(console.log)
// [
//   { status: 'fulfilled', value: 1 },
//   { status: 'rejected', reason: 'no' },
// ]
```

- 결과 객체는 `status`가 `'fulfilled'`이면 `value`를, `'rejected'`이면 `reason`을 가집니다. 반대쪽 프로퍼티는 없습니다.
- 입력 순서가 유지되고, 빈 이터러블이면 `[]`로 이행합니다.
- 이터러블이 아닌 값을 넘긴 경우처럼 입력 순회 자체가 실패할 때만 거부됩니다.
- 성공한 것만 추리려면 `results.filter((r) => r.status === 'fulfilled')`를 씁니다.

독립적인 여러 작업의 부분 실패를 허용할 때 씁니다. 여러 위젯 데이터 불러오기나 로그 일괄 전송이 예입니다. 흔한 실수는 `status`를 확인하지 않고 `r.value`를 바로 쓰는 것입니다. 거부 항목은 `value`가 `undefined`입니다.

## Promise.race

`Promise.race(iterable)`은 가장 먼저 정착한 프로미스의 결과를 이행이든 거부든 그대로 따르는 프로미스를 반환합니다.

```js
Promise.race([t(30, 'slow'), t(5, 'fast')])
  .then(console.log) // fast
```

- 가장 먼저 정착한 것이 거부면 거부됩니다. 이 점이 `any`와 다릅니다.
- 빈 이터러블이면 영원히 pending 상태로 남습니다.
- 프로미스가 아닌 값이나 이미 정착한 프로미스가 있으면 입력 순서상 앞선 것이 이깁니다. `Promise.race([1, Promise.resolve(2)])`는 `1`입니다.
- 지고 난 프로미스는 취소되지 않습니다. 결과만 무시되고 작업은 계속됩니다.

대표 용도는 타임아웃입니다.

```js
const timeout = (ms) =>
  new Promise((_, reject) =>
    setTimeout(() => reject(new Error('timeout')), ms))

Promise.race([fetchData(), timeout(3000)])
```

이긴 쪽이 `fetchData()`일 때 `timeout`의 타이머는 그대로 남습니다. Node.js에서는 남은 타이머가 프로세스 종료를 늦추므로 `clearTimeout`으로 정리하거나, 취소 가능한 타이머(취소가 없는 이유 절의 `AbortSignal.timeout`)를 씁니다. 시간이 초과되어도 `fetchData()`가 하던 작업은 중단되지 않습니다.

## Promise.any

`Promise.any(iterable)`(ES2021)은 가장 먼저 이행된 프로미스의 값으로 이행합니다. 거부는 무시하고, 모두 거부되었을 때만 `AggregateError`로 거부합니다.

```js
Promise.any([Promise.reject(1), t(5, 'ok')])
  .then(console.log)  // ok

Promise.any([Promise.reject(1), Promise.reject(2)])
  .catch((e) => console.log(e.errors)) // [1, 2]
```

- `AggregateError`는 여러 에러를 하나로 묶는 에러 클래스이고, `errors` 프로퍼티에 거부 이유들이 담깁니다. 순서는 완료 순서가 아니라 입력 순서입니다(자세히는 44편).
- 빈 이터러블이면 즉시 `errors`가 빈 배열인 `AggregateError`로 거부됩니다.
- 입력에 프로미스가 아닌 값이 있으면 이행된 것으로 취급됩니다.
- 성공이 하나라도 있으면 거부는 어디에도 전달되지 않습니다.

미러 서버나 여러 데이터 출처 중 가장 빠른 성공 응답만 필요할 때 씁니다.

## 정적 메서드 선택 기준

네 메서드 모두 이터러블을 받아 새 프로미스를 반환하고, 입력 요소를 `Promise.resolve`로 감쌉니다. 차이는 정착 조건입니다.

| 메서드 | 이행되는 때 | 거부되는 때 | 빈 입력 |
|--------|-------------|-------------|---------|
| `all` | 전부 이행. 값 배열(입력 순서) | 첫 거부 이유로 즉시 | `[]`로 이행 |
| `allSettled` | 전부 정착. 결과 객체 배열 | 거부되지 않음 | `[]`로 이행 |
| `race` | 첫 정착이 이행 | 첫 정착이 거부 | 영원히 pending |
| `any` | 첫 이행 | 전부 거부(`AggregateError`) | `AggregateError`로 거부 |

| 하고 싶은 일 | 선택 |
|--------------|------|
| 결과를 전부 모아서 써야 하고, 하나라도 실패하면 의미가 없다 | `all` |
| 성공과 실패를 각각 처리하고, 일부 실패는 허용한다 | `allSettled` |
| 가장 먼저 끝나는 쪽(성공이든 실패든)을 쓴다. 타임아웃 | `race` |
| 가장 먼저 성공하는 쪽만 쓴다. 실패는 무시한다 | `any` |

- `race`에서 "첫 성공"을 기대하는 것이 가장 흔한 오판입니다. `race`는 첫 정착이므로 먼저 실패하면 실패입니다.
- 어느 메서드도 입력 프로미스를 취소하지 않습니다.
- 동시에 실행할 작업 수를 제한하는 기능은 정적 메서드에 없습니다(자세히는 43편).

## Promise.try (ES2025)

`Promise.try(fn, ...args)`는 `fn`을 즉시 동기로 호출하고 그 결과를 프로미스로 감싸 반환합니다. 값을 반환하면 이행, 동기로 `throw`하면 거부, 프로미스를 반환하면 그 결과를 따라갑니다.

```js
function load(id) {
  if (id < 0) throw new RangeError('id')
  return fetchItem(id) // 프로미스를 반환
}

Promise.try(load, -1).catch((e) => console.log(e.name))
// RangeError — 동기 throw가 거부로 바뀐다
```

동기로 던질 수도 있고 프로미스를 반환할 수도 있는 함수의 결과를 하나의 `.then`·`.catch` 경로로 처리하기 위한 메서드입니다.

| 방법 | `fn` 호출 시점 | 동기 `throw` |
|------|----------------|--------------|
| `fn()` | 즉시 | 호출한 곳에서 던져짐 |
| `Promise.resolve().then(fn)` | 마이크로태스크(한 틱 뒤) | 거부 |
| `new Promise((r) => r(fn()))` | 즉시 | 거부 |
| `Promise.try(fn)` | 즉시 | 거부 |

- `Promise.resolve().then(fn)`은 `fn`이 한 틱 늦게 실행되어 코드 순서가 바뀝니다. 동기 호출을 유지하려면 `Promise.try`나 `new Promise`를 씁니다.
- `fn`이 프로미스를 반환해도 같은 객체를 돌려주지 않습니다. 그 결과를 따라가는 새 프로미스를 반환합니다.
- 인수를 `Promise.try(fn, a, b)`로 넘기면 `fn(a, b)`로 호출됩니다.
- 지원: ES2025입니다. 아직 지원하지 않는 환경에서는 `new Promise((r) => r(fn()))`로 대체합니다.

## Promise.withResolvers (ES2024)

`Promise.withResolvers()`는 프로미스와 그 `resolve`·`reject` 함수를 한 번에 객체로 반환합니다.

```js
const { promise, resolve, reject } = Promise.withResolvers()
setTimeout(() => resolve('done'), 100)
promise.then(console.log) // done (100ms 뒤)
```

이전에는 executor 밖에서 쓰려고 함수를 바깥 변수에 옮겨 담아야 했습니다.

```js
let resolve, reject
const promise = new Promise((res, rej) => {
  resolve = res
  reject = rej
})
```

프로미스를 정착시키는 주체가 executor 바깥에 있을 때 씁니다. 이벤트 리스너나 외부 콜백이 대표 예입니다.

```js
function nextClick(el) {
  const { promise, resolve } = Promise.withResolvers()
  el.addEventListener('click', resolve, { once: true })
  return promise // 첫 클릭 이벤트로 이행
}
```

- `Promise`를 `this`로 호출해야 하므로 `const { withResolvers } = Promise`처럼 떼어내면 `TypeError`입니다. 서브클래스에서 호출하면 그 클래스의 인스턴스를 만듭니다.
- executor 밖에서 정착시키므로 executor의 `throw`를 거부로 바꿔 주는 안전망이 없습니다. 정착시키는 코드가 여러 곳에 흩어지면 추적이 어려우므로 executor 안에서 끝낼 수 있으면 `new Promise`를 씁니다.
- 한 프로미스는 한 번만 정착하므로 반복되는 이벤트에는 호출마다 새 프로미스가 필요합니다.

## Promisify

Promisify는 콜백을 받는 함수를 프로미스를 반환하는 함수로 감싸는 변환입니다. 대상은 콜백을 마지막 인수로 받고 `(err, result)` 형식으로 호출하는 error-first 함수입니다.

```js
const promisify = (fn) => (...args) =>
  new Promise((resolve, reject) => {
    fn(...args, (err, result) => {
      if (err) reject(err)
      else resolve(result)
    })
  })
```

```js
// readLater(name, cb)는 콜백 기반 함수라고 가정
const read = promisify(readLater)
read('a.txt').then(console.log) // data:a.txt
read('').catch((e) => console.log(e.message)) // no name
```

- 콜백이 한 번만 호출되는 함수에만 맞습니다. `addEventListener`나 스트림의 `data` 콜백처럼 여러 번 호출되는 API는 프로미스가 첫 호출만 반영하므로 변환할 수 없습니다.
- 콜백 인수가 `(err, a, b)`처럼 둘 이상이면 첫 결과만 전달됩니다. 모두 필요하면 객체로 묶어 `resolve`합니다.
- 위 구현은 `this`를 전달하지 않습니다. 메서드를 변환할 때는 `fn.call(this, ...args, cb)`로 호출합니다.
- 변환은 콜백 API가 있는 가장 안쪽 한 곳에서 한 번만 합니다. 이미 프로미스를 반환하는 함수를 다시 감싸지 않습니다.
- ECMAScript에는 `promisify`가 없습니다. Node.js에는 `util.promisify`(호스트 API)가 있고, `fs/promises`처럼 처음부터 프로미스 버전을 제공하는 모듈이 있으면 그것을 씁니다.

## 마이크로태스크 큐와 프로미스

프로미스의 후속 처리 콜백은 마이크로태스크로 실행됩니다. 이벤트 루프와 큐의 일반 동작은 40편에서 다뤘으므로 여기서는 프로미스가 큐에 작업을 넣는 시점과 순서만 정리합니다. ECMAScript는 반응 작업(Job)을 등록한다는 것까지 정하고, 그 작업을 마이크로태스크로 실행하는 것은 호스트입니다.

- 콜백은 프로미스가 정착하는 시점에 큐에 들어갑니다. 이미 정착한 프로미스에 `then`을 걸면 그 호출 시점에 들어갑니다.
- 마이크로태스크는 현재 동기 코드가 끝난 뒤, 다음 매크로태스크(`setTimeout`, 이벤트 콜백 등)보다 먼저 큐가 빌 때까지 모두 실행됩니다. 실행 중에 추가된 것도 같은 라운드에서 실행됩니다.
- 정착된 값이 있어도 `then` 콜백은 동기로 실행되지 않습니다.

```js
setTimeout(() => console.log('timeout'), 0)
Promise.resolve().then(() => console.log('then'))
console.log('sync')
// sync
// then
// timeout
```

**체인 사이의 순서.** 큐는 등록 순서입니다. 두 체인은 한 단계씩 번갈아 실행됩니다.

```js
Promise.resolve().then(() => log('a1'))
  .then(() => log('a2'))
Promise.resolve().then(() => log('b1'))
  .then(() => log('b2'))
// a1 b1 a2 b2
```

`a2`는 `a1`이 끝난 뒤에야 등록되므로 이미 큐에 있던 `b1` 뒤에 섭니다.

**프로미스를 반환하는 비용.** 프로미스를 `resolve`하거나 `then` 콜백에서 반환하면 마이크로태스크가 두 번 더 필요합니다. thenable의 `then`을 호출하는 작업이 한 번, 그 결과를 구독하는 작업이 한 번입니다. 일반 값은 이 두 번이 없습니다.

```js
const p = Promise.resolve()
new Promise((r) => r(p)).then(() => log('A'))
p.then(() => log('1'))
  .then(() => log('2'))
  .then(() => log('3'))
// 1 2 A 3
```

`A`가 첫 번째 틱이 아니라 세 번째 자리에 오는 이유가 이 추가 두 번입니다.

`queueMicrotask(fn)`은 프로미스 없이 마이크로태스크를 직접 등록하는 호스트 API입니다(브라우저와 Node.js가 제공). 마이크로태스크 안에서 계속 마이크로태스크를 만들면 큐가 비지 않아 매크로태스크가 실행되지 못합니다(마이크로태스크 기아, 40편).

## 취소가 없는 이유

프로미스에는 취소 기능이 없습니다. 상태는 pending·fulfilled·rejected뿐이고, pending인 프로미스를 중단하는 메서드도 없습니다.

- 프로미스는 작업이 아니라 결과를 나타내는 값입니다. 작업은 프로미스가 만들어질 때 이미 시작되었고, 프로미스 객체에는 그 작업을 제어할 수단이 없습니다.
- 하나의 프로미스를 여러 소비자가 공유합니다. 한 소비자가 프로미스를 취소하면 같은 프로미스를 쓰는 다른 소비자의 결과도 사라집니다.
- 취소 가능한 프로미스(Cancelable Promises) 제안은 TC39 1단계에서 2016년에 철회되었습니다.

`Promise.race`로 타임아웃을 걸어도 지는 쪽의 작업은 계속 실행됩니다. 결과를 무시할 뿐 취소가 아닙니다.

**대안은 작업 쪽에 취소 신호를 전달하는 것입니다.** `AbortController`와 `AbortSignal`이 그 표준이며, ECMAScript가 아니라 DOM 표준의 호스트 API입니다(브라우저와 Node.js가 제공).

```js
const ac = new AbortController()
fetch(url, { signal: ac.signal })
  .catch((e) => console.log(e.name))
ac.abort() // AbortError
```

- 취소를 지원하는 API는 `signal` 옵션을 받고, 취소되면 반환한 프로미스를 신호의 취소 이유(기본은 `AbortError`)로 거부합니다. 취소는 거부로 표현되므로 에러 처리에서 `e.name === 'AbortError'`를 구분해야 합니다.
- `AbortSignal.timeout(ms)`는 지정한 시간이 지나면 `TimeoutError`로 취소되는 신호를 만듭니다. `fetch`처럼 `signal`을 받는 API에 넘기면 `race`와 달리 작업 자체가 중단됩니다.
- 내 함수가 취소를 지원하려면 `signal`을 받아 취소 시 정리하고 `signal.reason`으로 거부합니다.

```js
function wait(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    signal?.throwIfAborted()
    const id = setTimeout(resolve, ms)
    signal?.addEventListener('abort', () => {
      clearTimeout(id)
      reject(signal.reason)
    }, { once: true })
  })
}
```

`throwIfAborted()`가 executor 안에서 던지므로 이미 취소된 신호는 거부로 바뀝니다(executor 안의 throw 절).

## 흔한 안티패턴

### 프로미스 중첩

```js
getUser().then((user) => {      // ❌ 콜백 헬의 재현
  getPosts(user.id).then((posts) => {
    render(posts)
  })
})

getUser()                       // ✅ 반환해서 평탄하게
  .then((user) => getPosts(user.id))
  .then((posts) => render(posts))
```

안쪽 프로미스를 `return`하지 않으면 바깥 체인이 기다리지 않고, 안쪽의 에러가 바깥 `catch`에 닿지 않습니다.

### 이미 프로미스인 것을 `new Promise`로 감싸기

```js
const load = () =>              // ❌
  new Promise((resolve, reject) => {
    fetchData().then(resolve).catch(reject)
  })

const load = () => fetchData()  // ✅
```

`new Promise`는 콜백 API를 감쌀 때만 씁니다. 감싸면 코드가 길어지고 에러 전달 경로가 하나 늘어납니다.

### async 함수를 executor로 쓰기

```js
new Promise(async (resolve) => { // ❌
  const data = await load()      // load가 거부되면?
  resolve(data)
})
```

`async` 함수 안의 에러는 그 함수가 반환하는 프로미스를 거부시킬 뿐 executor의 `throw`가 아닙니다. 바깥 프로미스는 영원히 pending으로 남고, 안쪽 프로미스의 거부는 아무도 처리하지 않아 미처리 거부가 됩니다. 이미 프로미스를 반환하는 `load()`가 있으므로 감쌀 필요 없이 `load()`를 바로 반환합니다.

### 함수 대신 호출 결과를 넘기기

```js
p.then(console.log('done'))      // ❌ 즉시 출력. 인수는 undefined
p.then(() => console.log('done')) // ✅
```

`then`에 함수가 아닌 값을 넘기면 에러 없이 무시되고 앞의 결과가 그대로 전달되어 실수를 알아채기 어렵습니다.

### 에러 삼키기와 `catch` 누락

- `.catch((e) => console.log(e))`로 끝내면 체인이 성공으로 바뀝니다. 호출자에게 실패를 알려야 하면 다시 던집니다.
- 체인 끝에 `catch`가 없으면 미처리 거부가 됩니다. `then(a, b)`의 `b`는 `a`의 에러를 받지 못하므로 `a`가 던진 에러가 미처리로 남습니다(에러 처리 절).

### 독립 작업을 순차로 실행

```js
getA().then((a) =>               // ❌ getB가 getA를 기다린다
  getB().then((b) => use(a, b)))

Promise.all([getA(), getB()])    // ✅ 병렬
  .then(([a, b]) => use(a, b))
```

`getB`가 `a`에 의존하지 않을 때입니다. 대기 시간이 합산에서 최댓값으로 줄어듭니다.

### 반복문에서 프로미스를 기다리지 않기

```js
items.forEach((x) => save(x))               // ❌ 끝을 알 수 없다
Promise.all(items.map((x) => save(x)))      // ✅
```

`forEach`는 콜백이 반환한 프로미스를 사용하지 않으므로 완료를 기다릴 방법이 없고 거부도 처리되지 않습니다.

### 프로미스 배열로 실행 시점을 미루려는 시도

```js
const tasks = urls.map((u) => fetch(u))       // ❌ 이미 전부 시작
const tasks = urls.map((u) => () => fetch(u)) // ✅ 호출 시점에 시작
```

프로미스는 만들어지는 순간 작업이 시작됩니다. 시작 시점을 제어하려면 프로미스가 아니라 프로미스를 반환하는 함수를 모읍니다.

### 프로미스를 조건식에 쓰기

```js
if (isAdmin(user)) { /* ... */ } // ❌ 항상 true
```

`isAdmin`이 프로미스를 반환하면 객체이므로 어떤 결과든 참입니다. 결과를 꺼낸 뒤 판단해야 합니다(`await`는 43편).

## 핵심 정리

- 프로미스는 pending에서 fulfilled나 rejected로 한 번만 정착하는 값이고, executor는 생성 즉시 동기로 실행됩니다.
- `then`은 새 프로미스를 반환하며 콜백의 반환값·`throw`가 다음 단계의 결과를 정합니다. 프로미스를 반환하면 풀려서 전달되고, 거부는 처리하는 핸들러를 만날 때까지 체인을 따라갑니다.
- `all`은 전부 필요할 때, `allSettled`는 부분 실패를 허용할 때, `race`는 첫 정착, `any`는 첫 성공을 쓰며 어느 것도 입력을 취소하지 않습니다.
- `then` 콜백은 항상 마이크로태스크로 실행되고, 프로미스를 `resolve`하거나 반환하면 마이크로태스크가 두 번 더 듭니다.
- 프로미스에는 취소가 없으므로 `AbortSignal`을 작업 쪽에 전달합니다. 처리되지 않은 거부는 호스트가 통지하고 Node.js에서는 프로세스를 종료시킬 수 있습니다.

## 모듈의 개념과 모듈 스코프

**모듈**은 자기만의 스코프를 갖고, export한 것만 다른 파일에 보여 주는 코드 단위입니다. ES2015가 "파일 하나가 모듈 하나"인 문법을 표준에 넣었습니다. 이 문서에서 모듈은 ES 모듈(ESM)을 뜻합니다.

모듈이 해결하는 문제는 두 가지입니다.

- 이름 충돌: 일반 스크립트는 최상위 선언이 전역 스코프를 공유하므로 파일이 늘수록 같은 이름이 서로를 덮어씁니다.
- 의존 순서: `<script>` 태그의 순서를 사람이 맞춰야 합니다. 모듈은 의존 관계를 코드에 적고, 실행 순서는 엔진이 정합니다.

```js
// 일반 스크립트 (브라우저)
var total = 0
console.log(window.total) // 0

// 모듈
var total = 0
console.log(globalThis.total) // undefined
```

모듈 스코프의 규칙은 다음과 같습니다.

- 모듈 최상위의 `var`·`let`·`const`·`function`·`class` 선언은 모듈 스코프에 머뭅니다. 전역 객체의 프로퍼티가 되지 않습니다(전역 변수의 동작은 13편).
- 모듈 스코프의 바깥은 전역 스코프이므로 `document`, `Math` 같은 전역 이름은 그대로 읽을 수 있습니다.
- export하지 않은 선언은 다른 모듈에서 접근할 수 없습니다.
- 모듈은 한 번만 평가되고, 모든 importer가 같은 인스턴스를 공유합니다. 그래서 모듈 최상위 변수는 앱 전체에서 하나뿐인 상태가 됩니다(자세히는 46편).

| 구분 | 일반 스크립트 | 모듈 |
|------|---------------|------|
| 최상위 `var`·함수 선언 | 전역 객체의 프로퍼티(브라우저) | 모듈 스코프에 머문다 |
| strict mode | 선택 | 항상 켜짐 |
| 최상위 `this` | 전역 객체 | `undefined` |
| `import`·`export` 문 | SyntaxError | 사용 가능 |
| 최상위 `await` | 사용 불가 | 사용 가능(ES2022, 43편) |
| 평가 횟수 | 로드할 때마다 | 한 번 |

ECMAScript는 소스 텍스트를 Script로 파싱할지 Module로 파싱할지를 호스트에 맡깁니다. 브라우저는 `<script type="module">`, Node.js는 `.mjs` 확장자나 `package.json`의 `"type": "module"`로 구분합니다(자세히는 46편). 모듈 문법을 일반 스크립트에서 쓰면 파싱 단계에서 거부됩니다.

```js
import x from './x.js'
// SyntaxError: Cannot use import statement outside a module
```

## CommonJS·AMD·ESM

ES2015 이전의 언어에는 모듈이 없었고, 서로 다른 해결책이 쓰였습니다.

**IIFE 모듈 패턴**은 함수 스코프(12편)와 클로저(23편)로 변수를 숨기고 객체 하나만 노출하는 관례입니다. 의존 관계를 선언할 방법이 없어 로드 순서는 사람이 관리했습니다.

```js
const counter = (function () {
  let n = 0 // 클로저로 감춘 상태
  return { inc: () => ++n }
})()
counter.inc() // 1
```

**CommonJS**(CJS)는 서버 측 JavaScript용 모듈 규약이며 Node.js의 기본 모듈 시스템입니다. `require()`가 파일을 동기적으로 읽어 실행하고, `module.exports`에 대입한 값을 돌려줍니다.

```js
// math.cjs
const add = (a, b) => a + b
module.exports = { add }

// app.cjs
const { add } = require('./math.cjs')
add(1, 2) // 3
```

CJS 파일은 `(function (exports, require, module, __filename, __dirname) { ... })` 형태의 함수로 감싸져 실행됩니다. `require`·`module`·`__dirname`은 이 래퍼가 주는 인수라서 언어 문법이 아니고, 최상위 `this`는 `module.exports`를 가리킵니다.

**AMD**(Asynchronous Module Definition)는 브라우저에서 모듈을 비동기로 불러오기 위한 규약이고, RequireJS가 대표 구현입니다. 의존 모듈 배열을 먼저 로드한 뒤 팩토리 함수를 실행하고, 그 반환값이 모듈의 값이 됩니다.

```js
define(['./util'], function (util) {
  return { run: () => util.log('run') }
})
```

**UMD**(Universal Module Definition)는 규약이 아니라 CJS·AMD·전역 변수 중 환경에 맞는 방식으로 자신을 내보내는 래퍼 패턴입니다. 라이브러리 배포에 쓰였습니다.

**ESM**은 언어 문법으로 들어간 모듈입니다.

```js
// math.js
export const add = (a, b) => a + b

// app.js
import { add } from './math.js'
```

| 항목 | CommonJS | ESM |
|------|----------|-----|
| 정체 | Node.js의 구현 | ECMA-262 문법 |
| 가져오는 방식 | `require()` 호출 시점에 동기 실행 | 실행 전에 의존 관계를 정적으로 파악 |
| 위치 | 어디서나, 조건부 가능 | `import` 선언은 최상위만 |
| 가져오는 대상 | `module.exports` 값의 복사 | 바인딩 참조(라이브) |
| 최상위 `this` | `module.exports` | `undefined` |
| 기본 모드 | sloppy | strict |
| 전용 변수 | `require`, `module`, `__dirname` | 없음(`import.meta`) |

CJS가 값을 복사한다는 것은 `module.exports = { count }`처럼 객체를 만드는 순간의 값이 담긴다는 뜻입니다.

```js
// counter.cjs
let count = 0
module.exports = { count, inc: () => { count++ } }

// main.cjs
const m = require('./counter.cjs')
m.inc()
console.log(m.count) // 0 — 객체를 만들 때 복사된 값
```

ESM의 `import`·`export`는 문법이므로 코드를 실행하지 않고도 의존 그래프를 알 수 있습니다. 번들러의 트리 셰이킹이 이 성질에 기대고 있습니다(자세히는 46편).

ECMAScript가 정하는 것은 모듈 문법과 링크·평가 규칙까지입니다. 파일을 어디서 어떻게 가져오는지는 호스트가 정합니다. ESM과 CJS를 섞어 쓰는 규칙도 46편에서 다룹니다.

흔한 실수는 다음과 같습니다.

- CJS 파일에서 `import` 문을 쓰면 SyntaxError입니다.
- ESM 파일에서 `require`나 `__dirname`을 쓰면 ReferenceError입니다.
- CJS에서 `exports = { ... }`로 대입하면 지역 변수 `exports`만 바뀌고 내보내는 값은 그대로입니다. `module.exports = ...`를 써야 합니다.

## export

**export**는 모듈 안의 바인딩에 이름을 붙여 외부에 공개하는 선언입니다. 모듈 최상위에서만 쓸 수 있습니다.

선언 앞에 붙이는 형태입니다.

```js
export const PI = 3.14
export let count = 0
export function add(a, b) { return a + b }
export class User {}
```

이미 선언한 이름을 목록으로 공개하는 형태입니다. `as`로 공개 이름을 바꿀 수 있습니다.

```js
const a = 1, b = 2
export { a, b }
export { a as alpha }
```

공개 이름은 문자열 리터럴이어도 됩니다(ES2022). 식별자가 아닌 이름은 가져오는 쪽에서 `as`로 별칭을 붙여야 합니다.

```js
export { a as "a-b" }
```

규칙은 다음과 같습니다.

- 공개되는 것은 값이 아니라 바인딩입니다. `export { a, b }`의 중괄호는 객체 리터럴이 아니라 이름 목록입니다.
- 블록·함수 안의 `export`는 SyntaxError입니다.
- 같은 공개 이름을 두 번 쓰면 SyntaxError입니다. `export { a }`를 두 번 쓰거나, `a`와 `b`를 모두 `as c`로 공개하는 경우입니다.
- 목록에 적은 이름이 모듈 안에 선언돼 있지 않으면 SyntaxError입니다.
- 목록 export는 선언보다 앞에 써도 됩니다. export는 값을 읽지 않고 바인딩만 등록하므로 TDZ(13편)에 걸리지 않습니다.

```js
export { x }
const x = 1 // 정상
```

- `export const x = 1, y = 2`처럼 선언 하나에 변수가 여럿이면 모두 공개됩니다.
- 표현식 자체는 `export 1`처럼 공개할 수 없습니다. 값 하나를 내보내려면 default export를 씁니다.

```js
export a // ❌ SyntaxError
export { a } // ✅
```

## import

**import**는 다른 모듈이 공개한 바인딩을 현재 모듈 스코프의 이름으로 들여오는 선언입니다.

| 형태 | 구문 | 가져오는 것 |
|------|------|-------------|
| named | `import { a, b } from './m.js'` | 이름이 `a`, `b`인 export |
| default | `import x from './m.js'` | default export(이름은 자유) |
| namespace | `import * as ns from './m.js'` | 모든 export를 담은 객체 |
| 부수 효과 | `import './m.js'` | 없음. 모듈 실행만 |
| 조합 | `import x, { a } from './m.js'` | default와 named |
| 조합 | `import x, * as ns from './m.js'` | default와 namespace |

규칙은 다음과 같습니다.

- `from` 뒤의 지정자(specifier)는 문자열 리터럴만 가능합니다. 변수·템플릿 리터럴·표현식은 SyntaxError이고, 실행 중에 정해지는 경로는 `import()`로 가져옵니다.
- `import` 선언은 최상위에서만 쓸 수 있습니다.
- default와 나머지를 같이 가져올 때는 default가 앞에 와야 합니다.
- 모듈이 공개하지 않은 이름을 가져오면 SyntaxError이고, 코드가 한 줄도 실행되기 전에 발견됩니다. 같은 이름을 namespace 객체로 읽으면 에러 없이 `undefined`입니다.
- 가져온 이름은 현재 모듈 스코프의 식별자입니다. 같은 이름을 `const`로 다시 선언하거나 두 번 가져오면 SyntaxError입니다.

```js
const path = './m.js'
import x from path // ❌ SyntaxError
import { nope } from './m.js' // ❌ SyntaxError (링크 단계)
```

지정자 문자열을 해석하는 방법은 ECMAScript가 정하지 않고 호스트에 맡깁니다.

| 종류 | 예 | 해석 |
|------|----|------|
| 상대 | `./a.js`, `../b.js` | 현재 모듈 기준 경로. 브라우저와 Node.js 모두 확장자까지 적는다 |
| 절대 | `/lib/a.js`, `https://...` | 루트 경로나 URL |
| 베어 | `react` | 호스트가 정한다. Node.js는 패키지로 해석하고, 브라우저는 import map이 필요하다 |

(해석 규칙은 46편)

## named·default export

| 구분 | named export | default export |
|------|--------------|----------------|
| 모듈당 개수 | 여러 개 | 하나 |
| 가져오는 이름 | 공개된 이름 그대로(`as`로 변경) | 가져오는 쪽이 자유롭게 정함 |
| import 구문 | 중괄호 필요 | 중괄호 없음 |
| 이름 오타 | 링크 단계에서 SyntaxError | 발견되지 않음 |

default export의 형태는 네 가지입니다.

```js
export default function () {}  // 익명 함수 선언
export default class {}        // 익명 클래스 선언
export default 1 + 2           // 표현식: 평가 결과 3
export { greet as default }    // 목록에서 default로
```

규칙은 다음과 같습니다.

- default export는 이름이 `default`인 named export입니다. `import x from './m.js'`와 `import { default as x } from './m.js'`는 같은 뜻입니다.
- 함수·클래스 형태는 선언으로 취급됩니다. 이름이 없어도 되고, 이름이 있으면 모듈 안에서 그 이름으로 참조할 수 있으며, 함수는 호이스팅됩니다. 익명일 때 `.name`은 `'default'`입니다.
- `export default 표현식`은 평가한 결과를 이름 없는 내부 바인딩에 저장합니다. 모듈 안에서 이름으로 참조할 수 없고, 저장 시점의 값에 고정됩니다.
- `export default const x = 1`과 `export default let y = 1`은 SyntaxError입니다. 변수는 먼저 선언한 뒤 `export default x`로 내보냅니다.
- 한 모듈에 default export가 둘이면 SyntaxError입니다.

표현식 형태와 목록 형태는 갱신이 반영되는지에서 갈립니다.

```js
// def.js
export let n = 1
export default n        // 1이 저장된다
export function bump() { n++ }

// main.js
import d, { n, bump } from './def.js'
bump()
console.log(d, n) // 1 2
```

`export { n as default }`로 내보내면 바인딩 자체가 공개되므로 `d`도 2가 됩니다.

named export는 이름이 고정되어 검색·자동 완성·오타 검출에 유리합니다. default는 가져오는 쪽마다 이름이 달라질 수 있어 같은 값을 파일마다 다르게 부르게 됩니다.

## namespace·alias import

**namespace import**(`import * as ns`)는 모듈의 모든 export를 프로퍼티로 가진 module namespace 객체를 만듭니다. default export는 `ns.default`입니다.

```js
import * as m from './m.js'
m.add(1, 2) // named export
m.default   // default export
```

namespace 객체의 성질은 다음과 같습니다.

| 항목 | 값 |
|------|----|
| 프로토타입 | `null` |
| 키 | export 이름, 코드 유닛 순으로 정렬 |
| `Symbol.toStringTag` | `'Module'`, 즉 `[object Module]` |
| 프로퍼티 속성 | writable `true`, enumerable `true`, configurable `false` |
| 확장 | 불가 |
| 존재하지 않는 이름 | `undefined` |

writable이 `true`로 보이지만 값 쓰기는 항상 실패합니다. strict 코드(모듈은 항상 해당)에서는 쓰기·추가·삭제가 모두 TypeError입니다.

```js
import * as m from './m.js'
m.add = null  // TypeError: 읽기 전용
m.extra = 1   // TypeError: 확장 불가
delete m.add  // TypeError
m.nope        // undefined
```

`{ ...m }`은 그 시점의 값을 복사한 일반 객체를 만들고, 이 복사본은 라이브가 아닙니다.

**alias**(별칭)는 `as`로 가져오는 이름이나 공개하는 이름을 바꾸는 문법입니다.

```js
import { add as sum } from './math.js'
import { default as User } from './user.js'
import { "a-b" as ab } from './m.js' // ES2022
export { sum as total }
```

- `as` 뒤의 이름이 모듈 스코프에 만들어지는 식별자입니다. 원래 이름 `add`는 만들어지지 않으므로 쓰면 ReferenceError입니다.
- 쓰는 곳은 이름 충돌 해소, 의미 명확화, 문자열 export 이름의 식별자화입니다.

흔한 실수는 namespace 객체의 프로퍼티에 대입해 설정을 바꾸려는 것입니다. 바뀌어야 하는 상태는 export하는 쪽에서 함수나 객체로 노출해야 합니다.

## re-export

**re-export**는 다른 모듈의 export를 가져와 내 모듈의 export로 곧바로 내보내는 문법입니다. 여러 파일의 공개 API를 한 파일로 모을 때 씁니다.

| 구문 | 효과 |
|------|------|
| `export { a, b } from './m.js'` | `a`, `b`를 그대로 재공개 |
| `export { a as x } from './m.js'` | 이름을 바꿔 재공개 |
| `export { default } from './m.js'` | m의 default를 내 default로 |
| `export { default as Foo } from './m.js'` | m의 default를 named `Foo`로 |
| `export * from './m.js'` | m의 named export 전부(default 제외) |
| `export * as ns from './m.js'` | m의 namespace 객체를 `ns`로(ES2020) |

```js
// index.js (배럴 파일)
export { Button } from './Button.js'
export { default as Modal } from './Modal.js'
export * from './utils.js'
export * as icons from './icons.js'
```

규칙은 다음과 같습니다.

- re-export는 현재 모듈 스코프에 이름을 만들지 않습니다. 같은 파일에서 쓰려면 별도로 `import`해야 합니다.

```js
export { x } from './a.js'
console.log(x) // ReferenceError
```

- `export *`는 default를 넘기지 않습니다. default까지 공개하려면 `export { default } from`을 따로 씁니다.
- 서로 다른 `export *`가 같은 이름을 내보내면 그 이름은 어느 쪽도 재공개되지 않습니다. 이 충돌은 그 자체로는 에러가 아니고, namespace 객체에서는 `undefined`가 됩니다. 그 이름을 `import { dup }`처럼 직접 가져올 때 SyntaxError입니다.
- 현재 모듈이 직접 공개한 이름은 `export *`로 들어오는 같은 이름보다 우선합니다.
- re-export도 라이브 바인딩입니다. 원본이 바뀌면 재공개된 이름에서도 바뀐 값이 보입니다.
- import attributes를 붙일 수 있습니다.

```js
export { default } from './cfg.json' with { type: 'json' }
```

배럴 파일이 번들 크기와 로딩에 미치는 영향은 46편에서 다룹니다.

## Dynamic import

**동적 import**는 `import(지정자)` 형태로 모듈을 실행 중에 비동기로 불러오는 구문입니다. 해당 모듈의 namespace 객체로 이행되는 프로미스를 반환합니다(ES2020).

```js
const ns = await import('./math.js')
ns.add(1, 2) // 3

const { default: User, add } = await import('./user.js')
```

(`await`는 43편, 프로미스는 41편)

| 구분 | `import` 선언 | `import()` |
|------|---------------|------------|
| 위치 | 최상위만 | 어디서나 |
| 지정자 | 문자열 리터럴 | 임의의 표현식 |
| 시점 | 모듈 실행 전 | 호출한 시점 |
| 결과 | 바인딩 | namespace로 이행되는 프로미스 |
| 사용할 수 있는 코드 | 모듈 | 모듈, 일반 스크립트, CJS 파일 |

규칙은 다음과 같습니다.

- `import()`는 함수가 아니라 구문입니다. 변수에 담거나 `import.call(...)`처럼 호출할 수 없습니다.
- 실패는 던져지지 않고 프로미스가 거부됩니다. 파일을 찾지 못한 경우와 모듈 평가 중 에러가 난 경우 모두 해당합니다.

```js
try {
  await import('./nope.js')
} catch (e) {
  // 로드·평가 실패가 여기로 온다
}
```

- 같은 모듈을 여러 번 불러도 같은 namespace 객체가 돌아오고, 모듈은 한 번만 평가됩니다.
- 상대 지정자는 `import()`를 호출한 모듈 기준으로 해석됩니다.
- default export는 `.default` 프로퍼티에 있습니다. 구조 분해로 꺼낼 때는 `default`가 예약어이므로 `{ default: User }`처럼 이름을 붙입니다.
- 두 번째 인수로 import attributes를 넘깁니다(아래 import attributes 절).
- 모듈에 `then`이라는 이름의 함수 export가 있으면 namespace 객체가 thenable로 취급됩니다. 프로미스 해소 과정이 `then`을 호출하므로 `await import()`의 결과가 namespace가 아니라 `then`이 넘긴 값이 됩니다. 모듈에서 `then`을 export하지 않아야 합니다.

쓰는 곳은 세 가지입니다.

- 사용자 동작이 있을 때만 필요한 코드의 지연 로드
- 환경이나 설정에 따라 달라지는 조건부 로드
- 번들러가 호출 지점에서 별도 청크(chunk)로 분리하는 코드 분할(51편)

```js
button.onclick = async () => {
  const { render } = await import('./chart.js')
  render()
}
```

여러 모듈을 동시에 불러올 때는 `await Promise.all([import('./a.js'), import('./b.js')])`처럼 프로미스를 묶습니다.

흔한 실수는 반환값을 모듈 안의 함수나 default 값으로 착각하는 것입니다. `const add = await import('./math.js')`의 `add`는 함수가 아니라 namespace 객체입니다.

## import.meta

**`import.meta`**는 현재 모듈의 메타데이터를 담은 객체를 가리키는 메타 프로퍼티입니다(ES2020). ECMAScript는 이 객체의 존재만 정하고, 어떤 프로퍼티를 넣을지는 호스트가 정합니다.

```js
console.log(import.meta.url)
// https://example.com/js/app.js  (브라우저)
// file:///project/app.js         (Node.js)
```

| 프로퍼티 | 의미 | 제공 |
|----------|------|------|
| `url` | 모듈의 절대 URL 문자열(쿼리·해시 포함) | 브라우저, Node.js |
| `resolve(지정자)` | 지정자를 현재 모듈 기준 절대 URL로 해석해 문자열로 반환 | 브라우저, Node.js(20.0.0부터 동기) |
| `dirname`, `filename` | 모듈 파일의 디렉터리와 전체 경로 | Node.js 20.11, 21.2부터 |

규칙은 다음과 같습니다.

- 모듈 밖에서 쓰면 SyntaxError입니다. 모듈 안의 `eval` 문자열에서도 마찬가지입니다.
- 객체의 프로토타입은 `null`이고, 확장과 쓰기가 가능합니다. 모듈마다 객체 하나가 있고 그 모듈 안에서는 항상 같은 객체입니다.
- 호스트가 제공하지 않는 프로퍼티를 읽으면 에러 없이 `undefined`입니다.
- `import.meta.env`는 Vite가 넣는 프로퍼티입니다. 표준이 아니므로 다른 환경에서는 존재하지 않습니다.

파일 경로는 `import.meta.url`을 기준으로 만듭니다. CJS의 `__dirname`을 대신하는 방법입니다.

```js
const url = new URL('./data.txt', import.meta.url)
// url.href: 현재 모듈과 같은 폴더의 data.txt
```

Node.js에서의 활용은 46편에서 다룹니다.

## import attributes와 JSON 모듈

**import attributes**는 `with { 키: '값' }` 형태로 모듈 요청에 정보를 덧붙이는 구문이고, **JSON 모듈**은 이 구문으로 `.json` 파일을 모듈로 가져오는 기능입니다. 둘 다 ES2025에 포함됐습니다.

```js
import data from './data.json' with { type: 'json' }
console.log(data.name) // 'Alice'
```

속성은 세 위치에 쓸 수 있습니다.

```js
import cfg from './cfg.json' with { type: 'json' }
export { default } from './cfg.json' with { type: 'json' }
const m = await import('./cfg.json', {
  with: { type: 'json' },
})
m.default.name // 'Alice'
```

JSON 모듈의 규칙은 다음과 같습니다.

- 공개되는 것은 default export 하나이고, 값은 JSON을 파싱한 결과(객체·배열·원시값)입니다. 이름을 지정한 import는 SyntaxError입니다.

```js
import { name } from './data.json' with { type: 'json' }
// ❌ SyntaxError: 'name'이라는 export가 없다
```

- `type: 'json'`이 없거나 모듈의 종류와 맞지 않으면 에러입니다.
- 같은 JSON 모듈은 한 번만 평가되어 모든 importer가 같은 객체를 공유합니다. 한 곳에서 프로퍼티를 바꾸면 다른 곳에서도 바뀐 값이 보입니다. 복사본이 필요하면 `structuredClone`을 씁니다(39편).
- import 바인딩은 읽기 전용이지만 JSON 객체 자체는 수정할 수 있습니다.

속성 키와 값의 의미는 호스트가 정합니다. ECMAScript는 `with` 구문과 "키와 값은 문자열"이라는 형식, 그리고 JSON 모듈을 정의하고, 호스트가 모르는 속성은 거부됩니다. `type: 'css'`로 CSS를 가져오는 기능은 ECMAScript가 아니라 HTML 표준이 정의합니다.

옛 제안은 `with` 대신 `assert { type: 'json' }`을 썼습니다. `assert`는 검증만 할 뿐 HTTP 요청 헤더 같은 로딩 과정에 영향을 줄 수 없다는 문제가 있어 `with`로 바뀌었습니다. V8은 12.3(Chrome 123)에서 `with`를 지원하면서 `assert`를 폐기 예고했고 12.6까지 제거할 계획이라고 공지했습니다. 예전 글의 `assert`는 `with`로 바꿔 써야 합니다. Node.js는 v22.12.0과 v20.18.3 등에서 import attributes와 JSON 모듈의 실험 표시를 풀었습니다.

## 라이브 바인딩

**라이브 바인딩**은 import한 이름이 값의 복사본이 아니라 export한 모듈 안의 바인딩을 가리키는 읽기 전용 참조라는 규칙입니다. 원본이 바뀌면 import한 쪽에서도 바뀐 값이 보입니다. 명세 용어로는 import 바인딩이 export한 모듈의 바인딩을 가리키는 간접 바인딩입니다.

```js
// counter.js
export let count = 0
export function inc() { count++ }

// main.js
import { count, inc } from './counter.js'
console.log(count) // 0
inc()
console.log(count) // 1
```

규칙은 다음과 같습니다.

- 값을 바꿀 수 있는 쪽은 export한 모듈뿐입니다. import한 쪽에서 대입하면 TypeError입니다.
- 읽기 전용인 것은 바인딩이지 값이 아닙니다. 객체를 export하면 참조가 공유되어 importer가 프로퍼티를 바꿀 수 있습니다.

```js
// config.js: export const config = { debug: false }
import { config } from './config.js'
config.debug = true // 허용: 모든 importer에게 보인다
config = {}         // TypeError
```

- re-export와 namespace 객체를 거쳐도 라이브입니다. `ns.count`는 읽는 시점의 값입니다.
- `export default 표현식`은 라이브가 아닙니다. 평가 시점의 값에 고정됩니다.
- 모듈 평가가 끝나기 전에(순환 import에서) 읽으면 ReferenceError입니다. 바인딩은 있지만 아직 초기화되지 않은 TDZ 상태이기 때문입니다(자세히는 46편).

흔한 실수는 가져온 값을 지역 변수에 담고 계속 최신이라고 믿는 것입니다. 변수에 담는 순간은 복사입니다.

```js
const snapshot = count // 이 시점의 값
inc()
console.log(count, snapshot) // 2 1
```

위 코드는 이전 예에서 `inc()`가 한 번 호출된 뒤라는 전제입니다.

## import 호이스팅과 읽기 전용

**import 호이스팅**은 `import` 선언이 코드 위치와 관계없이 모듈 본문보다 먼저 처리된다는 규칙입니다.

```js
console.log(early) // 'E' (early.js가 먼저 실행된 뒤)
import { early } from './early.js'
```

`var`나 함수 선언의 호이스팅과 다르게, import는 바인딩 연결만이 아니라 의존 모듈의 실행까지 본문보다 앞섭니다.

실행 순서의 규칙은 다음과 같습니다.

- 모듈 하나가 실행되기 전에 그 모듈이 import하는 모듈이 모두 먼저 실행됩니다.
- 의존 모듈은 import 선언이 적힌 순서대로 깊이 우선으로 실행되고, 각 모듈은 한 번만 실행됩니다.

```js
// a.js가 b.js, c.js를 import하고 b.js가 d.js를 import한다
// a.js 본문에 console.log가 있어도 실행 순서:
// d → b → c → a
```

- 엔진은 본문을 실행하기 전에 모든 `import`·`export`를 훑어 의존 그래프를 만들고 이름을 연결합니다. 그래서 없는 이름의 import가 코드 실행 전에 SyntaxError가 됩니다(로딩 3단계는 46편).
- `import` 선언은 최상위에서만 쓸 수 있으므로 `if` 안의 조건부 import는 불가능합니다. 조건부 로드는 `import()`로 합니다.

위치는 동작에 영향을 주지 않지만 관례로 파일 맨 위에 모읍니다.

**읽기 전용**은 import한 이름에 재대입할 수 없다는 규칙으로, `const`와 같은 효과입니다. `=`, `++`, `+=`, 구조 분해 대입이 모두 TypeError입니다.

```js
import { x } from './a.js'
x = 1 // TypeError
x++   // TypeError
```

가져온 이름과 같은 이름을 같은 스코프에서 다시 선언하는 것은 SyntaxError입니다.

```js
import { x } from './a.js'
const x = 2 // SyntaxError: 'x' has already been declared
```

## 모듈의 자동 strict와 최상위 this

모듈 코드는 `'use strict'`가 없어도 항상 strict mode로 실행되고, 끌 수 없습니다(strict mode는 19편).

| 항목 | 일반 스크립트(sloppy) | 모듈(strict) |
|------|-----------------------|--------------|
| 선언 없는 변수에 대입 | 전역 변수가 생긴다 | ReferenceError |
| 읽기 전용 프로퍼티에 대입 | 조용히 무시 | TypeError |
| `with` 문 | 허용 | SyntaxError |
| 중복된 매개변수 이름 | 허용 | SyntaxError |
| 일반 함수 호출의 `this` | 전역 객체 | `undefined` |
| 8진수 리터럴 `010` | 8 | SyntaxError |

모듈 최상위의 `this`는 `undefined`입니다. 모듈은 전역 객체에 속하지 않으므로 `this`를 전역 객체로 채우지 않습니다.

```js
console.log(this) // undefined (모듈)
```

| 코드 종류 | 최상위 `this` |
|-----------|---------------|
| 일반 스크립트(브라우저) | `window`(전역 객체) |
| CommonJS | `module.exports` |
| ES 모듈 | `undefined` |

- 모듈에서 전역 객체가 필요하면 `globalThis`를 씁니다.
- `this.x = 1`처럼 최상위 `this`에 프로퍼티를 다는 코드는 모듈에서 TypeError입니다. 최상위 `this`가 전역 객체라고 가정한 옛 라이브러리가 모듈로 불러올 때 이 이유로 깨집니다.
- `require`, `module`, `exports`, `__filename`, `__dirname`은 CJS 래퍼가 주는 값이라 모듈에는 없습니다.
- 함수 안의 `this` 규칙은 모듈이어도 21편과 같습니다. 달라지는 것은 최상위와, strict라서 `undefined`가 되는 일반 함수 호출입니다.

## 부수 효과 import

**부수 효과 import**는 바인딩을 가져오지 않고 모듈을 실행하기 위해서만 쓰는 `import` 선언입니다.

```js
import './polyfills.js'
import './register-components.js'
```

- 가져오는 이름이 없고, 의존 모듈이 먼저 실행된다는 효과만 남습니다. 호이스팅과 실행 순서 규칙은 같고, 이미 다른 곳에서 실행된 모듈은 다시 실행되지 않습니다.
- 이름을 쓰지 않는 `import { x } from './m.js'`도 `m.js`는 평가됩니다. 이름을 안 쓴다고 모듈 실행이 생략되지 않습니다.
- 쓰는 곳은 폴리필 설치, 전역 객체 확장, 커스텀 엘리먼트 등록처럼 실행 자체가 목적인 모듈입니다.
- `import './style.css'`로 CSS를 적용하는 방식은 번들러의 기능이며 표준 동작이 아닙니다.
- 번들러는 사용하지 않는 import를 제거할 수 있지만 부수 효과 import는 지우면 안 됩니다. 번들러가 어떤 모듈을 지워도 되는지 판단하는 방법은 46편의 트리 셰이킹에서 다룹니다.

흔한 실수는 순서입니다. 폴리필을 설치하는 모듈은 그 폴리필이 필요한 모듈보다 앞에 적어야 합니다. 호이스팅은 import 선언끼리의 순서를 바꾸지 않습니다.

## import defer 제안 상태

**import defer**는 모듈을 로드하되, 평가(최상위 코드 실행)는 그 모듈의 export에 처음 접근할 때까지 미루는 import 구문 제안입니다. TC39 3단계(Stage 3)이며 아직 ECMAScript 표준이 아닙니다.

```js
import defer * as heavy from './heavy.js'
// 여기까지 heavy.js는 로드만 되고 실행되지 않는다

button.onclick = () => {
  heavy.run() // 처음 접근할 때 동기적으로 실행된다
}
```

| 구분 | 정적 import | `import defer` | `import()` |
|------|-------------|----------------|------------|
| 로드 | 시작 시 | 시작 시 | 호출 시 |
| 평가 | 시작 시 | 첫 접근 시 | 호출 시 |
| 사용하는 코드 | 동기 | 동기 | 비동기(`await`) |

목적은 시작 시 초기화 비용이 큰 모듈의 실행을 실제로 쓸 때까지 미루는 것입니다. `import()`는 async 코드를 강요하지만 `import defer`는 접근하는 코드가 동기 그대로입니다.

규칙은 다음과 같습니다.

- 구문은 namespace 형태만 허용됩니다. `import defer { a } from`이나 default 형태는 복잡도 때문에 제외됐습니다.
- 평가를 일으키는 것은 namespace 객체의 프로퍼티 접근입니다.
- 최상위 `await`를 쓰는 모듈과 그 비동기 의존 모듈은 지연할 수 없고, 로드 때 즉시 평가됩니다.
- 지연된 모듈의 평가가 에러를 던지면, 접근할 때마다 그 에러가 던져집니다.

3단계 제안이므로 문법이 바뀔 수 있습니다. TypeScript 5.9는 구문만 통과시키고 변환하지 않으며, Babel과 webpack은 변환을 지원합니다. 실행 환경의 지원 여부는 환경마다 다르므로 쓰기 전에 확인해야 합니다. 모듈을 평가하지 않고 소스 단계 객체만 가져오는 `import source`도 별개의 3단계 제안입니다.

## 핵심 정리

- 모듈은 자기 스코프를 갖고 항상 strict mode로 실행되며, 최상위 `this`는 `undefined`이고, 한 번만 평가됩니다.
- named export는 여러 개, default export는 하나이며 이름이 `default`인 named export입니다. `export *`는 default를 넘기지 않고, 이름이 충돌하면 그 이름을 재공개하지 않습니다.
- import한 이름은 값 복사가 아니라 읽기 전용 라이브 바인딩이고, `import` 선언은 호이스팅되어 의존 모듈이 본문보다 먼저 실행됩니다.
- `import()`는 namespace 객체로 이행되는 프로미스를 반환하고, `import.meta`는 호스트가 채우는 메타데이터 객체입니다.
- JSON 모듈은 `with { type: 'json' }`로 가져오며(ES2025) default export만 있습니다. import defer는 3단계 제안입니다.

## 객체 리터럴

객체 리터럴은 `{}` 안에 프로퍼티를 적어 객체 하나를 직접 만드는 방식입니다(문법은 09편). 틀 없이 값을 그대로 적으므로 객체가 하나뿐일 때 가장 짧고 분명합니다.

```js
const config = {
  host: 'localhost',
  port: 3000,
  url() { return `http://${this.host}:${this.port}` }
}
config.url() // 'http://localhost:3000'
```

패턴으로 쓰이는 용도는 다음과 같습니다.

- **설정·상수 묶음**: 관련 값을 한 객체에 모읍니다.
- **이름 공간**: 전역 이름 하나 아래에 기능을 모아 이름 충돌을 줄입니다.
- **싱글턴**: 리터럴은 평가될 때 객체 하나를 만들 뿐이라, 여러 곳에서 참조하면 모두 같은 객체를 봅니다. 한 곳에서 바꾸면 모든 사용처에 반영됩니다.
- **사전**: 키가 임의 문자열인 저장소가 필요하면 `Object.create(null)`로 프로토타입 없는 객체를 만듭니다. `'toString' in {}`은 `true`지만 `'toString' in Object.create(null)`은 `false`입니다. 키-값 저장이 목적이면 `Map`이 더 적합합니다(자세히는 38편).

규칙은 다음과 같습니다.

- 리터럴은 평가될 때마다 새 객체를 만듭니다. 함수 안에 두면 호출마다 다른 객체가 나오고, 이것이 팩토리 함수의 출발점입니다.

```js
const make = () => ({ n: 0 })
make() === make() // false
```

- 모든 프로퍼티가 공개됩니다. `_name`처럼 밑줄을 붙이는 관례는 접근을 막지 못합니다.
- 변경을 막으려면 `Object.freeze`를 쓰지만 얕은 동결입니다(자세히는 14편). 동결된 객체의 프로퍼티를 바꾸면 엄격 모드에서 TypeError이고 비엄격 모드에서는 조용히 무시됩니다.

```js
const frozen = Object.freeze({ a: 1, inner: { b: 2 } })
frozen.a = 2       // 엄격 모드 TypeError, 비엄격 모드 무시
frozen.inner.b = 3 // 허용: 중첩 객체는 동결되지 않는다
```

- 같은 구조의 객체를 여러 개 만들 때 생기는 구조 중복과 메서드 중복은 15편에서 다룹니다.

**흔한 실수:** 스프레드(`...`)로 복사한 객체가 서로 독립이라고 믿는 것입니다. 복사는 얕아서 중첩 객체와 배열은 같은 참조를 공유합니다(자세히는 10편).

```js
const base = { tags: [] }
const a = { ...base }
const b = { ...base }
a.tags.push('x')
b.tags // ['x']: 같은 배열
```

## 팩토리 함수

팩토리 함수(factory function)는 객체를 만들어 반환하는 일반 함수입니다. `new`도 `this`도 필요 없고, 호출할 때마다 새 객체가 나옵니다. 이름은 관례로 `create`나 `make`로 시작하는 camelCase를 씁니다(생성자 함수는 PascalCase).

```js
const createUser = (name, age) => ({ name, age })
createUser('Kim', 30) // { name: 'Kim', age: 30 }
```

규칙은 다음과 같습니다.

- 인수 검증, 기본값, 파생 값 계산을 함수 본문 한곳에 둘 수 있습니다. 리터럴에는 없는 초기화 로직입니다.
- 반환 객체가 리터럴이면 프로토타입이 `Object.prototype`이라서 어떤 팩토리에서 나왔는지 객체에 남지 않습니다. `instanceof`로 확인할 수 없고, 화살표 함수 팩토리에 쓰면 `prototype`이 없어서 TypeError입니다.

```js
function createBox() { return {} }
createBox() instanceof createBox // false
createUser('Kim', 30) instanceof createUser
// TypeError: 화살표 함수에는 prototype이 없다
```

- `new`를 붙여도 함수가 객체를 반환하면 그 객체가 결과입니다(자세히는 15편의 return 규칙). 화살표 함수 팩토리에 `new`를 붙이면 non-constructor라서 TypeError입니다.
- 호출 형태가 `new`가 아니므로 인수에 따라 다른 모양의 객체나 캐시해 둔 객체를 돌려줘도 호출자가 오해하지 않습니다.

### 클로저로 비공개 상태 만들기

함수 지역 변수는 그 함수 안에서 만든 함수(클로저, 자세히는 23편)만 접근할 수 있습니다. 반환 객체의 메서드가 클로저가 되면 지역 변수가 비공개 상태가 됩니다.

```js
function createCounter() {
  let count = 0
  return {
    increment() { return ++count },
    get value() { return count }
  }
}
const c = createCounter()
c.increment() // 1
c.value       // 1
c.count       // undefined
```

- `count`로 가는 경로가 코드에 없으므로 바깥에서 읽거나 바꿀 수 없습니다.
- 메서드가 `this`를 쓰지 않아서 변수로 분리해도 동작합니다. `const { increment } = c`로 꺼낸 뒤 `increment()`를 호출하면 `2`가 나옵니다.
- 호출할 때마다 메서드 함수 객체가 새로 만들어집니다. `createCounter().increment === createCounter().increment`는 `false`입니다.

**흔한 실수:** 비공개 변수를 단축 프로퍼티로 담으면 그 시점의 값이 복사됩니다. 이후 변수가 바뀌어도 프로퍼티는 갱신되지 않습니다.

```js
function createCounter() {
  let count = 0
  return { count, increment() { count++ } } // ❌ 0의 복사
}
const c = createCounter()
c.increment()
c.count // 0
```

현재 값을 노출하려면 위 예처럼 getter(`get value()`)를 씁니다.

### 프로토타입에 메서드를 위임하기

메서드를 담은 객체 하나를 만들어 두고 `Object.create`로 각 객체의 프로토타입에 연결하면 메서드를 공유합니다.

```js
const userMethods = {
  greet() { return `Hi, ${this.name}` }
}
function createUser(name) {
  const user = Object.create(userMethods)
  user.name = name
  return user
}
const u1 = createUser('Kim')
u1.greet() // 'Hi, Kim'
userMethods.isPrototypeOf(u1) // true
```

- 메서드 함수 객체는 `userMethods`에 하나만 있고 모든 객체가 프로토타입 체인으로 찾아 씁니다(자세히는 17편).
- 대신 `this`를 쓰고 데이터는 공개 프로퍼티입니다. 클로저 방식의 비공개는 포기합니다.

### 객체 조합하기

상속 계층 없이 동작(능력)별 팩토리를 만들고 한 객체에 합치는 방식입니다.

```js
const canWalk = (s) => ({ walk: () => `${s.name} walks` })
const canSwim = (s) => ({ swim: () => `${s.name} swims` })

function createDuck(name) {
  const duck = { name }
  return Object.assign(duck, canWalk(duck), canSwim(duck))
}
createDuck('Don').swim() // 'Don swims'
```

- `Object.assign`은 첫 인수 객체에 프로퍼티를 직접 추가하고 그 객체를 반환합니다. 능력 함수가 참조하는 `duck`과 반환 객체가 같아서, 나중에 `duck.name`을 바꾸면 `walk()`에도 반영됩니다.
- `{ ...state, ...canWalk(state) }`처럼 스프레드로 새 객체를 만들면 능력 함수가 참조한 객체와 반환 객체가 달라집니다. 공유할 상태는 별도 객체로 두고 모든 능력 함수에 같은 참조를 넘겨야 합니다.

## 모듈 패턴

모듈 패턴(module pattern)은 IIFE(자세히는 11편)가 반환한 객체를 변수 하나에 담아, 공개할 API만 그 객체에 넣고 나머지는 함수 스코프에 감추는 패턴입니다. ES 모듈(ES2015)이 나오기 전에 전역 오염을 막고 정보 은닉을 얻는 표준 방법이었습니다. 전역 변수 해결책으로서의 소개는 13편에 있습니다.

```js
const auth = (function () {
  let token = null // 비공개 상태
  const isValid = (t) => typeof t === 'string'
  return {
    login(t) { if (isValid(t)) token = t },
    isLoggedIn() { return token !== null }
  }
})()
auth.login('abc')
auth.isLoggedIn() // true
auth.token        // undefined
```

규칙은 다음과 같습니다.

- 모듈 패턴은 즉시 한 번만 호출한 팩토리 함수입니다. 객체가 하나뿐이므로 싱글턴이 되고, 같은 구조를 여러 개 만들려면 이름 붙은 팩토리 함수로 바꿔야 합니다.
- 반환 객체가 공개 API의 전부입니다. `token`과 `isValid`에는 접근 경로가 없습니다.
- 모든 함수를 비공개로 정의하고 마지막 `return`에서 공개할 이름만 매핑하는 변형이 노출 모듈 패턴(revealing module pattern)입니다. 공개 목록이 한곳에 모이고, 내부 함수끼리 `this` 없이 서로 직접 호출합니다.
- 노출 모듈 패턴에서 외부가 공개 함수를 교체해도 내부 호출은 원래 함수를 부릅니다. 내부는 스코프의 지역 바인딩을 참조하고 반환 객체의 프로퍼티를 거치지 않기 때문입니다.

```js
const m = (function () {
  function inner() { return 'original' }
  function outer() { return inner() }
  return { inner, outer }
})()
m.inner = () => 'patched'
m.inner() // 'patched'
m.outer() // 'original'
```

- 내부 호출을 반환 객체를 거쳐 하면(`api.inner()`) 교체가 반영되지만, 그러면 객체 참조에 의존하게 됩니다.

현대 코드에서는 ES 모듈이 같은 일을 합니다. 파일 스코프가 곧 비공개 영역이고 `export`한 것만 공개되며, 모듈은 한 번만 평가되어 싱글턴이 됩니다(자세히는 45·46편).

```js
// counter.js (ES 모듈)
let count = 0                    // 비공개
export const inc = () => ++count // 공개
```

모듈 패턴이 남아 있는 곳은 모듈을 쓸 수 없는 일반 스크립트와 번들러의 `iife` 출력 형식입니다. Rollup의 `output.format`에는 `iife`가 있고, `script` 태그로 바로 넣을 수 있는 자기 실행 함수로 번들을 감쌉니다.

**흔한 실수:**

- 앞 줄이 세미콜론 없이 끝나면 `(`가 그 줄의 호출로 이어집니다(자세히는 11편).

```js
const a = 1
(function () {})() // TypeError: 1 is not a function
```

- 상태가 하나뿐이라 테스트 사이에 값이 남을 수 있습니다. 테스트마다 초기 상태가 필요하면 팩토리 함수로 만듭니다.

## 생성자 함수와 prototype

생성자 함수 방식은 인스턴스마다 다른 데이터는 생성자에서 `this`에 붙이고, 모든 인스턴스가 같은 메서드는 생성자의 `prototype`에 한 번만 두는 구조입니다. `new`가 하는 일은 15편, 프로토타입 체인은 17편에서 다루고 여기서는 생성 패턴으로서의 구조와 함정을 봅니다.

```js
function Person(name) {
  this.name = name // 인스턴스마다
}
Person.prototype.greet = function () {
  return `Hi, ${this.name}` // 모두 공유
}
const a = new Person('Kim')
const b = new Person('Lee')
a.greet()                 // 'Hi, Kim'
a.greet === b.greet       // true
Object.hasOwn(a, 'greet') // false
```

- `Object.hasOwn`(ES2022)이 `false`인 것은 `greet`가 인스턴스가 아니라 프로토타입에 있기 때문입니다.
- 메서드 호출 시 `this`는 점 앞의 객체입니다. 메서드를 변수로 꺼내 호출하면 `this`를 잃습니다(자세히는 21편).

### 프로토타입 상속

ES5 방식의 상속은 세 가지 작업으로 이루어집니다.

```js
function Student(name, school) {
  Person.call(this, name) // 1. 부모 생성자로 데이터 초기화
  this.school = school
}
// 2. 체인 연결
Student.prototype = Object.create(Person.prototype)
// 3. constructor 복구
Student.prototype.constructor = Student
Student.prototype.study = function () {
  return `${this.name} studies`
}
const s = new Student('Park', 'SNU')
s.greet() // 'Hi, Park'
s instanceof Person // true
```

- 2번이 `prototype`을 새 객체로 통째로 바꾸므로 원래 있던 `constructor` 프로퍼티가 사라집니다. 3번을 빼면 `s.constructor`가 상속받은 `Person`을 가리킵니다.
- 3번의 단순 대입은 열거 가능한 프로퍼티를 만들어 `for...in`에 `constructor`가 나타납니다. 열거되지 않게 하려면 `defineProperty`를 씁니다.

```js
Object.defineProperty(Student.prototype, 'constructor', {
  value: Student, writable: true, configurable: true
})
```

- `class`의 `extends`와 `super`는 이 과정 전체를 대신합니다(자세히는 25편).

### 흔한 실수

**`prototype`을 객체 리터럴로 통째로 바꾸기**

```js
function A() {}
const before = new A()
A.prototype = { hi() {} }
const after = new A()
before.hi          // undefined
after.constructor === Object // true
```

- 교체 이전에 만든 인스턴스는 옛 프로토타입에 연결된 채로 남아 새 메서드를 얻지 못합니다.
- 새 객체의 `constructor`는 `Object.prototype`에서 상속한 `Object`입니다.

**`prototype`에 배열·객체 두기**

```js
function B() {}
B.prototype.hobbies = []
const b1 = new B()
const b2 = new B()
b1.hobbies.push('golf')
b2.hobbies // ['golf']: 모든 인스턴스가 같은 배열
```

- 원시 값은 이런 문제가 없습니다. `b1.count++`는 프로토타입 값을 읽어 인스턴스에 새 프로퍼티를 만들어(가리기) 다른 인스턴스에 영향이 없습니다.
- 인스턴스마다 달라야 하는 참조 값은 생성자 안에서 `this`에 만듭니다.

**프로토타입 메서드를 화살표 함수로 쓰기**

```js
Person.prototype.greet = () => this.name
// ❌ 화살표 함수의 this는 바깥의 this
```

화살표 함수는 자기 `this`가 없어서 인스턴스를 가리키지 못합니다(자세히는 21편).

**`new` 누락:** 비엄격 모드에서 `Person('x')`를 호출하면 `this`가 전역 객체라서 전역에 `name`이 생기고, 엄격 모드에서는 `this`가 `undefined`라 TypeError입니다(자세히는 15편).

### 정보 은닉

생성자 함수 방식에는 비공개 문법이 없습니다. 밑줄 접두사(`_balance`)는 관례일 뿐 접근을 막지 못합니다. 실제로 감추는 방법은 두 가지입니다.

- **생성자 안에서 메서드 정의**: 지역 변수를 클로저로 캡처합니다. 대신 `this.inc = function () { ... }`처럼 정의한 메서드가 `new`마다 새 함수 객체가 되어 `prototype` 공유의 이점이 사라집니다. 두 인스턴스의 `inc`를 비교하면 `false`입니다.
- **모듈 스코프 `WeakMap`**: 인스턴스를 키로 비공개 데이터를 저장합니다. 메서드는 `prototype`에 둘 수 있습니다.

```js
const priv = new WeakMap()
function Account(balance) {
  priv.set(this, { balance })
}
Account.prototype.getBalance = function () {
  return priv.get(this).balance
}
new Account(100).getBalance() // 100
```

`WeakMap`은 키가 약한 참조라서 인스턴스가 사라지면 항목도 회수됩니다(자세히는 38편). 같은 일을 클래스는 `#` 필드로 합니다.

## ES6 클래스

클래스(class, ES2015)는 생성자 함수와 `prototype` 패턴을 선언적 문법으로 쓰게 한 것입니다. 새로운 객체 모델이 아니라서 `typeof Person`은 `'function'`이고 메서드는 `prototype`에 놓입니다. 문법은 24편, 상속은 25편에서 다룹니다.

```js
class Person {
  #age // 비공개 필드 (ES2022)
  constructor(name, age) {
    this.name = name
    this.#age = age
  }
  greet() { return `Hi, ${this.name}` } // prototype에 정의
  get isAdult() { return this.#age >= 18 }
  static create(name, age) { return new Person(name, age) }
}
const p = Person.create('Kim', 20)
p.greet()   // 'Hi, Kim'
p.isAdult   // true
```

생성자 함수 방식과의 차이는 다음과 같습니다.

| 항목 | 생성자 함수 + prototype | class |
|------|--------------------------|-------|
| `new` 없이 호출 | 일반 함수로 실행된다 | TypeError |
| 선언 전 사용 | 함수 선언문은 호이스팅되어 가능 | TDZ로 ReferenceError |
| strict mode | 선택 | 본문은 항상 strict |
| 메서드 열거 | `prototype`에 대입한 메서드는 열거 가능 | 열거 불가 |
| 메서드를 `new`로 호출 | 가능 (함수 표현식이므로) | TypeError (non-constructor) |
| `prototype` 교체 | 가능 | 불가 (`writable: false`) |
| 비공개 | 없음 (관례) | `#` 필드·메서드 |
| 상속 | 세 단계를 직접 작성 | `extends`·`super` |

- 클래스 `prototype`은 쓰기 불가이므로 `Person.prototype = {}`은 비엄격 모드에서 조용히 무시되고 엄격 모드에서 TypeError입니다.
- 열거 불가 덕분에 인스턴스를 `for...in`으로 돌 때 메서드가 섞여 나오지 않습니다.

### 클래스 필드와 메모리

클래스 필드(ES2022)는 인스턴스마다 프로퍼티를 만듭니다. 값이 화살표 함수이면 인스턴스마다 함수 객체가 생깁니다.

```js
class Btn {
  label = 'ok'
  onClick = () => this.label // 인스턴스마다 함수 객체
  onHover() { return this.label } // prototype에서 공유
}
const b1 = new Btn()
const b2 = new Btn()
b1.onClick === b2.onClick // false
b1.onHover === b2.onHover // true
```

화살표 함수 필드는 `this`가 인스턴스에 고정되어 `const { onClick } = b1`로 분리해도 동작합니다. 그 대가로 클로저 방식과 같은 메모리 비용을 냅니다. 일반 메서드는 분리하면 `this`를 잃습니다.

**흔한 실수:** 클래스 메서드를 변수로 꺼내 호출하는 것입니다. 클래스 본문은 strict mode라서 `this`가 `undefined`입니다.

```js
const { greet } = p
greet() // TypeError: Cannot read properties of undefined
```

## 방식별 비교

### 메모리

| 방식 | 데이터 | 메서드 함수 객체 |
|------|--------|------------------|
| 리터럴 | 객체마다 | 리터럴을 평가할 때마다 새로 생성 |
| 팩토리 (클로저) | 객체마다 | 호출마다 새로 생성, 클로저 컨텍스트도 함께 |
| 팩토리 (`Object.create`) | 객체마다 | 프로토타입 객체 하나를 공유 |
| 모듈 패턴 | 하나 | 하나 (인스턴스가 하나뿐) |
| 생성자 + prototype | 객체마다 | `prototype`에서 공유 |
| class | 객체마다 | `prototype`에서 공유. 화살표 함수 필드는 인스턴스마다 |

- 명세상 함수 표현식과 화살표 함수는 평가될 때마다 새 함수 객체를 만듭니다. 인스턴스마다 메서드를 만드는 방식은 인스턴스 수 곱하기 메서드 수만큼 함수 객체가 생깁니다. 엔진이 내부적으로 코드를 공유하더라도 함수 객체 자체는 늘어납니다.
- 프로토타입 공유 방식은 인스턴스 수와 상관없이 메서드 수만큼만 생깁니다.
- 인스턴스가 많지 않으면 차이가 문제 되는 경우는 드뭅니다. 실제로 문제인지는 측정으로 확인합니다.

### 정보 은닉

| 방식 | 비공개 수단 | 강제 여부 |
|------|-------------|-----------|
| 리터럴 | 없음 (`_` 관례) | 아니오 |
| 팩토리 | 클로저 지역 변수 | 예 |
| 모듈 패턴 | 클로저 지역 변수 | 예 |
| 생성자 + prototype | `_` 관례, 생성자 안 클로저, 모듈 스코프 `WeakMap` | 관례는 아니오, 나머지는 예 |
| class | `#` 필드·메서드 (ES2022) | 예 |

- `#`는 문법 수준입니다. 클래스 본문 밖에서 `obj.#x`를 쓰면 실행 전 파싱 단계에서 SyntaxError입니다. 반대로 `_x`는 `Object.keys`와 `JSON.stringify`에 나타나고, `#x`는 둘 다 나타나지 않습니다.
- 클로저 방식은 은닉을 얻는 대신 메서드를 인스턴스마다 만듭니다. `#`는 메서드가 `prototype`에서 공유되면서 비공개이므로 메모리와 은닉을 함께 얻습니다.
- `#` 멤버는 서브클래스에서도 접근할 수 없고 선언한 클래스 본문 안에서만 보입니다. 서브클래스에 열어 주려면 메서드로 노출합니다.
- `#x in obj`(ES2022)로 객체가 그 클래스로 만들어졌는지 확인할 수 있습니다. 클래스 본문 안에서만 쓸 수 있습니다.
- Symbol 키는 은닉이 아닙니다. `Object.keys`에는 나오지 않지만 `Object.getOwnPropertySymbols`로 꺼낼 수 있습니다(자세히는 34편).

### 상속

| 방식 | 상속 수단 | 비고 |
|------|-----------|------|
| 리터럴 | `Object.create(parent)`, `__proto__` 키, `Object.setPrototypeOf` | 객체가 객체를 직접 상속 |
| 팩토리 | `Object.create` 위임, 객체 조합 | 조합은 복사라서 이후 원본 변경이 반영되지 않음 |
| 모듈 패턴 | 없음 | 반환 객체에 프로퍼티를 덧붙이는 정도 |
| 생성자 + prototype | `Parent.call(this)` + `Object.create(Parent.prototype)` + `constructor` 복구 | `instanceof` 동작 |
| class | `extends`·`super` | 내장 타입 상속 가능 |

- 내장 타입(`Array`, `Error`, `Map` 등) 상속은 `class`의 `extends`가 정석입니다. ES5 방식의 `Parent.call(this)`는 내장 생성자가 `this`를 무시해서 초기화가 일어나지 않습니다.

```js
function MyErr(m) { Error.call(this, m) }
MyErr.prototype = Object.create(Error.prototype)
new MyErr('boom').message // '' (설정되지 않음)

class MyErr2 extends Error {}
new MyErr2('boom').message // 'boom'
```

- 배열도 같습니다. ES5 방식으로 `Array.prototype`을 이은 객체는 `Array.isArray`가 `false`이고 `length`가 자동으로 갱신되지 않습니다. `x[5] = 1` 뒤 `x.length`는 ES5 방식에서 `0`, `class MyArr extends Array`에서 `6`입니다.
- 팩토리 조합은 계층이 아니라 능력의 합입니다. 클래스 상속은 부모를 바꾸면 모든 하위 클래스에 영향이 퍼집니다. 이 때문에 "상속보다 조합"이 객체 지향 설계에서 널리 쓰이는 지침입니다.

### 그 밖의 차이

| 방식 | `new` | 메서드 분리 시 `this` 소실 | `instanceof` |
|------|-------|----------------------------|--------------|
| 리터럴 | 불필요 | `this`를 쓰는 메서드만 | 불가 (`Object`뿐) |
| 팩토리 (클로저) | 불필요 | 없음 | 불가 |
| 모듈 패턴 | 불필요 | 없음 | 불가 |
| 생성자 + prototype | 필수 | 있음 | 가능 |
| class | 필수 (없으면 TypeError) | 있음 | 가능 |

## 선택 기준

방식은 다음 질문 순서로 정합니다.

1. 같은 모양의 객체가 여러 개 필요한가? 아니면 리터럴이나 모듈입니다.
2. 비공개 상태가 필요한가? 필요하면 클로저(팩토리·모듈 패턴)나 `#` 필드(class)입니다.
3. 인스턴스가 많고 메서드를 공유해야 하는가? 그러면 `prototype` 공유(class)입니다.
4. 계층 관계나 내장 타입 확장이 있는가? 그러면 class와 `extends`입니다.

| 조건 | 선택 | 이유 |
|------|------|------|
| 객체 하나, 구조 단순 | 리터럴 | 틀이 필요 없다 |
| 비공개 상태 하나와 공개 함수 묶음 | ES 모듈 (모듈 불가 환경이면 모듈 패턴) | 파일 스코프가 비공개, 한 번만 평가 |
| 같은 모양 여러 개, 비공개 필요, 인스턴스 수 적음 | 팩토리 (클로저) | `new`와 `this`가 없어 단순하다 |
| 같은 모양 많이, 메서드 공유, 타입 확인 필요 | class | `prototype` 공유와 `instanceof` |
| 비공개와 메서드 공유를 함께, 인스턴스 많음 | class의 `#` 필드 | 메모리와 은닉을 함께 얻는다 |
| is-a 계층, 내장 타입 확장 | class와 `extends` | 내장 타입 상속은 이 방식만 정상 동작 |
| 여러 능력의 조합 | 팩토리와 객체 조합 | 계층 없이 합성한다 |

- 새 코드에서 생성자 함수와 `prototype`을 직접 쓸 이유는 거의 없습니다. `class`가 같은 구조에 `new` 강제, strict mode, 열거 불가 메서드, `#` 비공개를 더해 줍니다. 기존 코드와 라이브러리를 읽기 위해서는 이해해야 합니다.
- 인스턴스를 만들지 않는 클래스(`static` 멤버만 있는 클래스)는 틀의 역할이 없으므로 리터럴이나 모듈의 함수로 충분합니다.
- 한 코드베이스 안에서는 방식을 섞지 않습니다. 호출하는 쪽이 `new`가 필요한지, `instanceof`가 되는지를 방식으로 짐작하기 때문입니다.
- 메모리 때문에 방식을 고를 때는 인스턴스 수와 측정 결과를 근거로 삼습니다.

## 핵심 정리

- 리터럴은 하나뿐인 객체에, 팩토리 함수는 `new` 없이 같은 모양을 찍어 낼 때 씁니다. 팩토리는 클로저로 비공개 상태를 만들지만 호출마다 메서드 함수 객체가 새로 생기고 `instanceof`를 쓸 수 없습니다.
- 모듈 패턴은 즉시 호출한 팩토리 함수이며 싱글턴입니다. 노출 모듈 패턴에서는 공개 함수를 교체해도 내부 호출이 원본을 부릅니다. 현대 코드에서는 ES 모듈이 이 역할을 맡습니다.
- 생성자 함수 방식은 데이터를 `this`에, 메서드를 `prototype`에 두어 메서드를 공유합니다. 비공개 문법이 없고 `prototype` 교체와 상속에서 `constructor` 복구 같은 함정이 있습니다.
- class는 같은 `prototype` 구조에 `new` 강제, strict mode, 열거 불가 메서드, `#` 비공개, `extends`를 더한 문법입니다. 화살표 함수 필드는 인스턴스마다 함수 객체를 만듭니다.
- 메모리는 메서드 공유 여부, 은닉은 클로저와 `#`, 상속은 `extends`(내장 타입 포함)와 조합이 기준입니다. 새 코드의 기본 선택은 하나면 리터럴, 여러 개면 class나 팩토리입니다.

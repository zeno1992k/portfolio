## 클로저의 개념

**클로저**(closure)는 함수와, 그 함수가 정의된 곳의 바깥 환경(변수 바인딩)을 묶어서 부르는 말입니다. 함수는 만들어질 때 바깥 환경에 대한 참조를 함께 가지므로, 바깥 함수가 이미 끝났어도 그 변수를 읽고 쓸 수 있습니다.

```js
function makeGreeter(greeting) {
  return name => `${greeting}, ${name}`
}
const hello = makeGreeter('Hello')
hello('Kim') // 'Hello, Kim' — makeGreeter는 이미 끝났다
```

`makeGreeter`의 호출이 끝나면 매개변수 `greeting`도 사라질 것 같지만, 반환된 함수가 참조하고 있어서 남습니다.

클로저라는 말은 두 가지 범위로 쓰입니다.

| 범위 | 정의 | 쓰이는 곳 |
|------|------|-----------|
| 넓은 의미 | 모든 함수. 함수 객체는 만들어진 시점의 환경에 닫혀 있다 | 명세, MDN |
| 좁은 의미 | 바깥 변수를 참조하면서 바깥 함수보다 오래 사는 중첩 함수 | 개발 현장, 많은 입문서 |

이 문서에서 "클로저 현상"은 좁은 의미를 가리킵니다.

- 명세는 ECMAScript 함수 객체를 렉시컬 환경에 닫힌(closed over) 코드를 캡슐화한 객체로 설명하고, 함수 객체를 만드는 알고리즘의 변수 이름도 `closure`입니다.
- 바깥 변수를 하나도 참조하지 않는 함수는 기억할 것이 없어 클로저 효과가 보이지 않습니다.
- 전역에 정의한 함수도 전역 환경에 닫혀 있지만, 전역 환경은 프로그램이 끝날 때까지 살아 있어서 특별한 현상이 없습니다.
- 클로저를 만드는 별도 문법은 없습니다. 선언문, 표현식, 화살표 함수, 메서드, 제너레이터, async 함수 모두 같은 방식입니다.
- `new Function`으로 만든 함수는 호출한 곳이 아니라 전역 환경에 닫히므로 지역 변수를 보지 못합니다(자세히는 11편).

클로저는 값이 아니라 변수(바인딩) 자체를 참조합니다.

```js
let n = 1
const read = () => n
n = 2
read() // 2 — 만들 때의 1이 아니라 지금의 값
```

흔한 오해는 "클로저가 만들어질 때의 값을 복사해 간다"입니다. 복사가 아니라 공유이므로, 바깥에서 값을 바꾸면 클로저가 바뀐 값을 보고, 클로저가 값을 바꾸면 바깥에서도 보입니다. 값이 복사된 것처럼 보이는 경우는 그 시점에 변수가 새로 만들어졌기 때문입니다(반복문과 오래된 클로저 절).

## 렉시컬 스코프와 `[[Environment]]`

렉시컬 스코프(lexical scope)는 함수의 상위 스코프를 호출한 위치가 아니라 정의한 위치로 정하는 규칙입니다(자세히는 12편). 명세는 이 규칙을 함수 객체의 `[[Environment]]` 내부 슬롯으로 구현합니다.

- 함수 객체가 만들어지는 순간, 실행 중이던 환경 레코드(Environment Record)가 그 함수의 `[[Environment]]`에 저장됩니다.
- 함수를 호출하면 새 환경 레코드가 만들어지고, 그 `[[OuterEnv]]`는 호출한 곳이 아니라 함수 객체의 `[[Environment]]`로 정해집니다. 이 연결이 스코프 체인입니다.

| 슬롯 | 가진 쪽 | 값 | 정해지는 때 |
|------|---------|----|-------------|
| `[[Environment]]` | 함수 객체 | 함수가 정의된 환경 레코드 | 함수 객체가 만들어질 때 한 번 |
| `[[OuterEnv]]` | 환경 레코드 | 바로 바깥의 환경 레코드 | 환경 레코드가 만들어질 때 |

```js
const a = 1
function outer() {
  const b = 2
  return function inner() {
    const c = 3
    return a + b + c
  }
}
outer()() // 6
```

```text
inner 호출 환경 { c }
  └ [[OuterEnv]] → outer 호출 환경 { b }
      └ [[OuterEnv]] → 전역 환경 { a }
```

`inner`의 `[[Environment]]`는 `outer`를 호출할 때 만들어진 환경을 가리킵니다. `inner` 안에서 `b`를 찾으면 자기 환경에 없으므로 `[[OuterEnv]]`를 따라 그 환경에서 찾습니다.

- `[[Environment]]`는 함수 객체를 만드는 연산(OrdinaryFunctionCreate)에서 한 번 정해지고 이후 바뀌지 않습니다.
- 내부 슬롯이라 코드에서 읽거나 바꿀 수 없습니다. 클로저가 붙잡은 변수를 바깥에서 꺼내는 방법은 없습니다.
- 화살표 함수는 자기 `this`와 `arguments`가 없어서, 식별자처럼 `[[OuterEnv]]` 체인을 따라 바깥 함수의 것을 찾습니다(자세히는 21편).
- 호출한 위치는 `[[Environment]]`에 영향을 주지 않습니다.

```js
const x = 'global'
function makeReader() {
  const x = 'maker'
  return () => x
}
function caller(fn) {
  const x = 'caller'
  return fn()
}
caller(makeReader()) // 'maker' — 호출한 곳의 x가 아니다
```

환경 레코드의 종류와 구조는 22편에서 다룹니다.

## 클로저의 생성 과정

클로저는 함수 객체가 만들어지는 시점에 생깁니다. 반환하는 시점도, 호출하는 시점도 아닙니다.

```js
function outer() {
  const x = 'outer'
  function inner() { return x }
  return inner
}
const fn = outer()
fn() // 'outer'
```

1. `outer()`를 호출하면 실행 컨텍스트와 함수 환경 레코드 `{ x }`가 만들어집니다. 이 레코드의 `[[OuterEnv]]`는 `outer`의 `[[Environment]]`, 곧 전역 환경입니다.
2. `inner`의 정의가 평가되어 함수 객체가 만들어지고, `inner`의 `[[Environment]]`에 현재 환경 `{ x }`가 저장됩니다. 함수 선언문은 `outer`에 진입할 때, 함수 표현식과 화살표 함수는 그 식을 평가할 때 만들어집니다(자세히는 22편).
3. `return inner`로 `outer`의 실행 컨텍스트가 콜 스택에서 제거됩니다.
4. 환경 레코드 `{ x }`는 `inner`의 `[[Environment]]`가 참조하고 있어서 회수되지 않고 남습니다.
5. `fn()`을 호출하면 새 환경 레코드가 만들어지고, 그 `[[OuterEnv]]`는 남아 있던 `{ x }`입니다. `x`를 찾으면 이 체인에서 `'outer'`가 나옵니다.

실행 컨텍스트가 사라져도 환경 레코드가 남는 것은 두 대상의 수명을 정하는 기준이 다르기 때문입니다.

| 대상 | 수명 |
|------|------|
| 실행 컨텍스트 | 호출이 시작될 때부터 반환될 때까지(콜 스택) |
| 환경 레코드 | 어딘가에서 참조하는 동안(가비지 컬렉션 대상) |

규칙은 다음과 같습니다.

- 바깥 함수를 호출할 때마다 환경 레코드가 새로 만들어지고, 그 안에서 평가된 중첩 함수도 새 함수 객체입니다.

```js
const f1 = outer()
const f2 = outer()
f1 === f2 // false — 환경도 서로 별개
```

- 클로저가 이어 가는 것은 바로 바깥 환경만이 아니라 `[[OuterEnv]]`로 연결된 체인 전체입니다.
- 중첩 함수가 바깥 함수보다 오래 살려면 바깥 함수의 호출이 끝난 뒤에도 그 함수에 도달할 수 있어야 합니다. 대표적인 경로는 다음과 같습니다.
  - 반환값으로 돌려준다
  - 바깥 변수나 객체의 프로퍼티에 대입한다
  - 타이머, 이벤트, 프로미스 콜백으로 등록한다(자세히는 40편)

흔한 오해는 "바깥 함수가 반환될 때 클로저가 만들어진다"입니다. 반환하지 않고 `setTimeout`에 넘기기만 해도 같은 현상이 일어납니다.

## 상태 유지

**상태 유지**는 함수 호출이 끝나도 값이 사라지지 않고 다음 호출로 이어지는 성질입니다. 일반 지역 변수는 호출마다 새로 만들어져 초기화되지만, 클로저가 참조하는 환경은 호출 사이에 남아 값을 보관합니다.

```js
function plain() {
  let count = 0
  return ++count
}
plain() // 1
plain() // 1 — 호출마다 count가 새로 만들어진다

function makeCounter() {
  let count = 0
  return () => ++count
}
const next = makeCounter()
next() // 1
next() // 2 — 같은 환경의 count를 계속 쓴다
```

상태의 단위는 바깥 함수의 호출 한 번입니다. `makeCounter()`를 호출할 때마다 독립된 `count`를 가진 클로저가 나옵니다.

```js
const a = makeCounter()
const b = makeCounter()
a() // 1
a() // 2
b() // 1 — a와 별개의 환경
```

같은 호출에서 만든 클로저들은 환경을 공유합니다.

```js
function make() {
  let n = 0
  return { inc: () => ++n, dec: () => --n, get: () => n }
}
const c = make()
c.inc(); c.inc(); c.dec()
c.get() // 1 — 세 함수가 하나의 n을 본다
```

- 클로저의 쓰임은 두 가지입니다. 읽기만 하면 설정을 기억하는 용도(`makeGreeter`)이고, 바꾸기까지 하면 상태를 유지하는 용도(`makeCounter`)입니다.
- 상태는 변수에 들어 있으므로 값을 바꾸려면 `let`으로 선언해야 합니다. `const` 변수는 재할당할 수 없습니다. 객체를 담은 `const`는 내용을 바꿀 수 있습니다.

흔한 실수는 호출할 때마다 클로저를 새로 만드는 것입니다.

```js
makeCounter()() // 1
makeCounter()() // 1 — 호출마다 새 환경이라 이어지지 않는다
```

상태를 이어 가려면 반환된 함수를 변수에 저장해 재사용해야 합니다.

## 캡슐화와 정보 은닉

**캡슐화**(encapsulation)는 데이터와 그 데이터를 다루는 함수를 하나로 묶는 것이고, **정보 은닉**(information hiding)은 내부 데이터를 외부에서 직접 건드리지 못하게 막고 공개된 인터페이스로만 다루게 하는 것입니다. 함수의 지역 변수는 클로저 말고는 접근할 방법이 없으므로 진짜 비공개 변수로 쓸 수 있습니다.

```js
function createAccount(balance) {
  return {
    deposit(amount) {
      if (amount <= 0) throw new RangeError('invalid')
      balance += amount
      return balance
    },
    get balance() { return balance },
  }
}
```

```js
const acc = createAccount(100)
acc.deposit(50) // 150
acc.balance     // 150
acc.balance = 0 // 무시된다 (strict mode에서는 TypeError)
acc.balance     // 150
```

- 반환된 객체에는 `balance`라는 데이터 프로퍼티가 없고 getter만 있습니다. 변수 `balance` 자체를 `acc`에서 꺼낼 방법은 없고, getter를 거친 읽기만 됩니다.
- 값을 바꾸는 길이 `deposit` 하나뿐이라서 검증을 우회할 수 없습니다. 데이터가 항상 지켜야 하는 조건(여기서는 입금액이 양수)을 보장할 수 있습니다.
- 메서드가 `this`를 쓰지 않으므로 객체에서 떼어 내도 동작합니다.

```js
const { deposit } = acc
deposit(10) // 160 — this 없이도 balance를 본다
```

한 번만 만드는 객체는 즉시 실행 함수(IIFE)로 환경을 하나 만들어 공유합니다. 이 방식이 모듈 패턴입니다(자세히는 13편). 인스턴스를 여러 개 만들 때는 위처럼 함수를 호출할 때마다 새 환경을 만드는 팩토리를 씁니다.

비공개를 구현하는 방법은 여러 가지입니다.

| 방식 | 외부에서 접근 | 메서드가 놓이는 곳 | 자세히 |
|------|---------------|--------------------|--------|
| `_name` 관례 | 가능(관례일 뿐) | 프로토타입 공유 | 17편 |
| 클로저 | 불가능 | 인스턴스마다 함수 객체 | 이 편 |
| `#private` 필드 | 불가능(문법 오류) | 프로토타입 공유 | 24편 |
| WeakMap | 맵을 모르면 불가능 | 프로토타입 공유 | 38편 |

흔한 실수는 비공개 변수의 객체나 배열을 그대로 반환하는 것입니다. 변수에는 접근할 수 없어도 그 변수가 가리키는 객체는 바깥에서 바꿀 수 있습니다.

```js
function createList() {
  const items = []
  return {
    add: x => items.push(x),
    get items() { return items }, // ❌ 원본을 노출
    // get items() { return [...items] }, // ✅ 복사본
  }
}
const list = createList()
list.add(1)
list.items.push('hack') // items가 [1, 'hack']이 된다
```

값이 원시 값이면 복사되어 안전하고, 객체·배열이면 복사본(스프레드는 36편)이나 `Object.freeze`(14편)로 보호합니다.

## 고차 함수와 클로저

**고차 함수**(higher-order function)는 함수를 인수로 받거나 함수를 반환하는 함수입니다. 함수를 값으로 다룰 수 있는 일급 함수 덕분에 가능합니다(자세히는 16편). 배열 메서드로 쓰는 고차 함수는 29편, 함수형 프로그래밍 관점은 50편에서 다룹니다. 두 방향 모두 클로저가 동작합니다.

### 함수를 반환하는 고차 함수

반환된 함수는 인수를 기억합니다. 설정이 다른 함수를 찍어 내는 팩토리가 됩니다.

```js
const multiplyBy = n => x => x * n
const double = multiplyBy(2)
const triple = multiplyBy(3)
double(5) // 10
triple(5) // 15
```

```js
const gt = min => x => x > min
const nums = [1, 5, 10]
nums.filter(gt(4)) // [5, 10] — gt(4)가 min을 4로 기억한다
```

### 함수를 받는 고차 함수

콜백은 자신이 정의된 곳의 변수를 읽습니다. 콜백이 호출되는 시점에 따라 의미가 다릅니다.

- `map`, `filter` 같은 동기 콜백은 바깥 함수가 아직 실행 중일 때 호출되어, 평범한 스코프 체인 검색입니다.
- `setTimeout`, 이벤트, 프로미스 콜백 같은 비동기 콜백은 바깥 함수가 끝난 뒤에 호출되어, 좁은 의미의 클로저 현상이 일어납니다.

### 함수를 감싸는 래퍼

함수를 받아 같은 모양의 새 함수를 반환하면서 동작을 덧붙이는 방식입니다. 원본 함수는 클로저로 보관됩니다.

```js
function withLog(fn) {
  return function (...args) {
    console.log('call', fn.name, args)
    return fn.apply(this, args)
  }
}
const add = (a, b) => a + b
withLog(add)(1, 2) // 'call add [1, 2]' 출력 후 3
```

- 래퍼는 `this`, 인수, 반환값을 원본에 그대로 전달해야 합니다. 전달하지 않으면 원본의 동작이 바뀝니다(`apply`는 21편).

래퍼가 호출 사이에 유지할 상태를 클로저에 두는 예가 디바운스입니다.

```js
function debounce(fn, ms) {
  let timer
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), ms)
  }
}
```

`timer`는 호출 사이에 이어지는 클로저 상태입니다. 마지막 호출 뒤 `ms`가 지나야 `fn`이 한 번 실행됩니다(`setTimeout`은 호스트 API, 40편).

## 반복문과 클로저

반복문 안에서 만든 클로저가 모두 같은 값을 보는 현상은 클로저가 값이 아니라 변수를 참조하기 때문에 생깁니다.

```js
const fs = []
for (var i = 0; i < 3; i++) fs.push(() => i)
fs.map(f => f()) // [3, 3, 3]
```

`var i`는 하나뿐이고 세 함수의 `[[Environment]]`가 모두 그 변수가 있는 같은 환경입니다. 함수는 반복이 끝난 뒤 호출되므로 그때의 `i`인 `3`을 읽습니다.

`let`은 반복마다 새 환경을 만들고 이전 값을 복사합니다(ES2015). 각 함수가 서로 다른 환경에 닫힙니다.

```js
const gs = []
for (let j = 0; j < 3; j++) gs.push(() => j)
gs.map(g => g()) // [0, 1, 2]
```

반복별 바인딩의 세부 동작(증감식, 초기화 식 안의 함수)은 13편에서 다룹니다.

해결 방법은 모두 "반복마다 새 환경을 만든다"는 같은 원리입니다.

| 방법 | 새 환경이 생기는 곳 |
|------|---------------------|
| `for (let ...)` | 반복마다 |
| 반복 본문 안의 `const`·`let` | 본문 블록이 실행될 때마다 |
| `forEach`·`map` 콜백 | 콜백을 호출할 때마다. 매개변수가 반복별 변수 |
| IIFE (ES5 방식) | 즉시 실행 함수를 호출할 때마다 |
| `bind(null, i)` | 반복마다 만든 바운드 함수의 내부 슬롯에 인수가 저장됨 |

```js
const hs = [0, 1, 2].map(k => () => k)
hs.map(h => h()) // [0, 1, 2]
```

```js
const is = []
for (var q = 0; q < 3; q++) {
  (function (n) { is.push(() => n) })(q) // n은 호출마다 새 변수
}
is.map(f => f()) // [0, 1, 2]
```

`for...of`는 `let`·`const`로 선언하면 반복마다 새 바인딩이 만들어지고, `var`로 선언하면 하나를 공유합니다.

```js
const cs = []
for (var e of [10, 20, 30]) cs.push(() => e)
cs.map(c => c()) // [30, 30, 30]
```

흔한 실수는 다음과 같습니다.

- 루프 밖에서 선언한 변수를 루프 헤더에서 재사용하면 `let`이어도 하나를 공유합니다.

```js
let m
const ks = []
for (m = 0; m < 3; m++) ks.push(() => m)
ks.map(k => k()) // [3, 3, 3] — m은 루프 밖의 하나
```

- 본문 안에서 `var`로 값을 옮기면 `var`가 함수 스코프라서 다시 공유됩니다. 같은 모양을 `const`로 쓰면 반복마다 새 변수입니다.

```js
const vs = []
for (let k = 0; k < 3; k++) {
  var v = k // const v = k 이면 [0, 1, 2]
  vs.push(() => v)
}
vs.map(f => f()) // [2, 2, 2] — var v는 하나
```

- `while` 루프도 같습니다. 본문 블록 안의 `const`·`let`은 반복마다 새 환경에 놓입니다.

## 클로저와 메모리

클로저는 환경을 유지하므로, 환경 안 변수가 가리키는 값도 그 함수가 살아 있는 동안 메모리에 남습니다.

```js
const handlers = []
function register(data) {
  handlers.push(() => data.length)
}
register(new Array(1e6).fill(0))
handlers.length = 0 // 참조를 끊어야 data가 회수 대상이 된다
```

규칙은 다음과 같습니다.

- 환경은 도달 가능한 함수 객체가 `[[Environment]]`로 참조하는 동안 유지됩니다. 그 함수에 도달할 수 없게 되면 환경과 변수의 값도 회수 대상이 됩니다. 실제 회수 시점은 엔진이 정합니다(자세히는 49편).
- 클로저 자체는 누수가 아닙니다. 누수는 더 이상 필요 없는 클로저에 도달할 수 있는 경로가 남아 있을 때 생깁니다.
  - 제거하지 않은 이벤트 리스너, 해제하지 않은 `setInterval`
  - 전역 배열·맵에 계속 쌓이는 콜백
  - 크기 제한 없이 커지는 메모이제이션 캐시
- 함수와 환경이 서로를 참조하는 순환 구조는 문제가 아닙니다. 현대 엔진은 참조 횟수가 아니라 루트에서 도달 가능한지로 판단합니다.
- 클로저를 만들 때마다 함수 객체와 환경이 생깁니다. 팩토리로 객체를 수천 개 만들면 메서드도 그 수만큼 별도의 함수 객체가 되므로, 대량으로 만드는 객체는 메서드를 프로토타입에 두는 편이 메모리를 덜 씁니다(클래스는 24편).

더 필요 없는 값은 참조를 끊어서 회수할 수 있게 합니다.

- 변수에 `null`을 대입합니다. 클로저가 변수를 계속 참조해도 큰 값은 회수 대상이 됩니다.
- 배열·맵에서 제거하고, 리스너와 타이머를 해제합니다.
- 해제하려면 등록할 때 쓴 것과 같은 함수 객체가 필요합니다. 팩토리가 호출마다 새 함수를 만드므로 반환된 함수를 변수에 보관해 둡니다.

```js
const onTick = () => console.log('tick')
const id = setInterval(onTick, 1000)
clearInterval(id) // 타이머가 onTick을 더 붙잡지 않는다
```

흔한 실수는 `removeEventListener('click', () => {})`처럼 새 함수를 만들어 넘기는 것입니다. 등록한 것과 다른 함수 객체라서 아무것도 제거되지 않습니다.

## 엔진의 미사용 변수 제거

엔진은 클로저가 실제로 쓰는 변수만 환경 객체에 남기는 최적화를 합니다. 명세의 설명 모델에서 환경 레코드는 선언된 모든 바인딩을 담고 클로저는 그 환경 전체에 닫혀 있지만, 값이 언제 회수되는지는 엔진에 맡겨져 있습니다.

- 엔진은 코드를 컴파일할 때 스코프 분석으로 안쪽 함수가 어떤 바깥 변수를 참조하는지 알아냅니다.
- 참조되는 변수만 함수 호출이 끝난 뒤에도 남는 환경 객체에 두고, 참조되지 않는 변수는 스택 같은 임시 저장소에 둡니다. 임시 저장소의 변수는 함수가 끝나면 사라집니다.
- 결과적으로 클로저가 살아 있어도 그 클로저가 쓰지 않는 큰 변수는 회수될 수 있습니다.

```js
function setup() {
  const big = new Array(1e6).fill(0)
  const small = 1
  return () => small // big을 참조하지 않는다
}
const fn = setup() // V8: big은 setup이 끝나면 회수 대상
```

V8(Node.js 24)에서 `WeakRef`(대상 객체의 회수를 막지 않는 참조)로 큰 객체 `big`이 회수되는지 직접 관찰한 결과입니다.

| 상황 | big | 이유 |
|------|-----|------|
| 어떤 함수도 big을 참조하지 않음 | 회수됨 | 환경 객체에 big이 없다 |
| 반환된 클로저가 big을 참조 | 유지 | 필요한 변수 |
| 같은 스코프의 다른 함수가 big을 참조하고, 반환된 클로저는 참조하지 않음 | 유지 | 같은 스코프의 클로저는 환경 객체 하나를 공유한다 |
| big을 참조하는 함수가 안쪽 블록에만 있음 | 회수됨 | 블록 환경이 따로 있고 반환된 클로저의 체인에 없다 |
| 같은 스코프 안 어느 함수에든 직접 eval이 있음 | 유지 | eval 코드가 어떤 변수든 참조할 수 있다 |
| 간접 eval, `new Function` | 영향 없음 | 전역 스코프에서 실행되어 지역 변수를 보지 못한다 |

같은 스코프의 다른 함수가 변수를 붙잡는 경우가 가장 놓치기 쉽습니다.

```js
function setup() {
  const big = new Array(1e6).fill(0)
  const small = { v: 1 }
  const useBig = () => big.length // 밖으로 나가지 않는다
  const useSmall = () => small.v
  return useSmall // V8: 그래도 big이 유지된다
}
```

`useBig`은 버려지지만, 두 함수가 같은 환경 객체를 공유하므로 `useSmall`이 살아 있는 동안 `big`도 남습니다.

- 위 결과는 V8에서 확인한 것입니다. 이 최적화는 명세가 보장하지 않으며 엔진과 버전에 따라 다릅니다. 회수에 의존하는 코드를 쓰지 않습니다.
- 직접 eval은 호출 형태가 `eval(...)`인 경우입니다. 간접 호출 `(0, eval)(...)`은 전역 스코프에서 실행되므로 해당하지 않습니다(자세히는 19편).
- 큰 데이터를 다루는 코드는 별도 함수나 안쪽 블록으로 분리하면 오래 사는 클로저와 환경을 나눌 수 있습니다.

흔한 실수는 "클로저는 안 쓰는 변수도 항상 붙잡는다"와 "엔진이 알아서 항상 지워 준다"를 둘 중 하나로 단정하는 것입니다. 위 표처럼 조건에 따라 갈립니다.

## 오래된 클로저

**오래된 클로저**(stale closure)는 클로저가 변수의 최신 값이 아니라 이미 지나간 시점의 값을 계속 보는 현상입니다. 원인은 두 가지입니다.

1. 변수의 값을 다른 지역 변수로 복사해 두고, 클로저가 그 복사본을 읽습니다.
2. 새 환경과 새 함수가 만들어졌는데도 등록해 둔 옛 함수가 계속 쓰입니다.

```js
function setup(state) {
  const { count } = state // 이 시점의 값을 복사
  return () => count
}
const state = { count: 1 }
const read = setup(state)
state.count = 2
read() // 1 — 오래된 값
```

```js
let handler
function render(count) {
  handler = () => console.log(count) // 호출마다 새 환경
}
render(0)
const old = handler // 첫 환경 { count: 0 }에 닫힌 함수
render(1)
old()     // 0 — 옛 환경의 count
handler() // 1
```

`render`를 부를 때마다 새 환경과 새 함수가 생깁니다. `old`는 첫 환경에 닫혀 있으므로, 이 함수를 타이머나 이벤트에 등록해 두었다면 계속 `0`을 봅니다.

해결은 "무엇을 최신으로 읽을지"에 따라 고릅니다.

| 방법 | 내용 |
|------|------|
| 클로저 안에서 직접 읽기 | 복사하지 않고 `state.count`처럼 호출 시점에 읽는다 |
| 읽는 함수나 객체를 넘기기 | `() => state.count`를 넘겨 호출할 때마다 최신 값을 얻는다 |
| 인수로 전달 | 호출하는 쪽이 최신 값을 인수로 준다 |
| 다시 등록 | 값이 바뀔 때 새 함수를 만들고 옛 함수는 해제한다 |

```js
function setup2(state) {
  return () => state.count // 호출 시점에 읽는다
}
setup2(state)() // 2
```

- 옛 값이 필요한 경우도 있습니다. 반복문의 인덱스처럼 그 시점의 값을 의도적으로 붙잡는 것은 오래된 클로저가 아니라 의도한 스냅샷입니다.
- React의 함수 컴포넌트는 렌더마다 그 렌더의 값을 읽는 핸들러를 새로 만듭니다. 비동기 콜백이 옛 렌더의 값을 보는 문제는 위의 두 번째 원인과 같은 구조입니다.

## 클로저 활용

### once

`once`는 함수를 처음 호출할 때만 실행하고, 이후에는 처음의 결과를 그대로 돌려주는 래퍼입니다. 호출 여부와 결과를 클로저 변수에 저장합니다.

```js
function once(fn) {
  let called = false
  let result
  return function (...args) {
    if (called) return result
    called = true
    result = fn.apply(this, args)
    return result
  }
}
```

```js
const init = once(() => { console.log('init'); return 42 })
init() // 'init' 출력, 42
init() // 출력 없음, 42 — 저장된 결과
```

- `called`를 `fn` 호출 전에 `true`로 바꾸면, `fn`이 예외를 던진 뒤의 호출은 실행하지 않고 `undefined`를 돌려줍니다. 실패도 한 번 실행한 것으로 취급합니다.
- `called`를 호출 뒤에 바꾸면 예외 후 재시도할 수 있지만, `fn` 안에서 자신을 다시 호출하면 플래그가 아직 `false`라서 `fn`이 중첩 실행됩니다.
- 초기화 코드나 한 번만 실행해야 하는 핸들러에 씁니다.

### 메모이제이션

**메모이제이션**(memoization)은 같은 인수로 호출하면 계산을 다시 하지 않고 이전 결과를 재사용하는 기법입니다. 결과 캐시를 클로저 변수에 둡니다.

```js
function memoize(fn) {
  const cache = new Map()
  return function (arg) {
    if (cache.has(arg)) return cache.get(arg)
    const result = fn.call(this, arg)
    cache.set(arg, result)
    return result
  }
}
const square = memoize(n => {
  console.log('calc')
  return n * n
})
square(4) // 'calc' 출력, 16
square(4) // 출력 없음, 16 — 캐시
```

재귀 함수에 적용하면 중복 계산이 사라집니다. 재귀 호출이 메모이즈된 함수를 부르도록 변수 이름을 맞춥니다.

```js
const fib = memoize(n => {
  return n < 2 ? n : fib(n - 1) + fib(n - 2)
})
fib(50) // 12586269025 — 캐시가 없으면 약 400억 번 호출
```

규칙은 다음과 같습니다.

- 같은 입력에 항상 같은 출력을 내고 부수 효과가 없는 함수에만 씁니다. `Date.now()`나 바깥 상태에 의존하는 함수에 쓰면 캐시된 옛 값을 돌려줍니다. 오래된 클로저와 같은 문제입니다.
- 캐시 확인은 `cache.has`로 합니다. `if (cache.get(arg))`로 확인하면 결과가 `0`, `''`, `undefined`일 때 캐시가 없는 것으로 오인해 매번 다시 계산합니다.
- `Map`은 키를 SameValueZero로 비교합니다. `NaN`은 같은 키이고 `0`과 `-0`도 같은 키입니다. 객체 키는 참조로 비교합니다.
- 인수가 여럿이면 키를 직접 설계해야 합니다. `JSON.stringify(args)`는 `undefined`·함수·`Symbol`을 모두 `null`로 바꿔 `[undefined]`와 `[null]`을 구분하지 못하고, 순환 구조와 BigInt는 TypeError를 냅니다.
- 캐시가 무제한으로 커집니다. 항목 수를 제한하거나, 객체를 키로 쓸 때는 `WeakMap`을 써서 키 객체가 회수되면 항목도 사라지게 합니다(자세히는 38편).

### 부분 적용

**부분 적용**(partial application)은 함수의 인수 일부를 미리 고정한 새 함수를 만드는 것입니다. 고정한 인수는 클로저가 기억합니다.

```js
function partial(fn, ...preset) {
  return (...later) => fn(...preset, ...later)
}
const add3 = (a, b, c) => a + b + c
const add10 = partial(add3, 10)
add10(1, 2) // 13
```

- 커링(currying)은 `f(a, b, c)`를 `f(a)(b)(c)`처럼 인수를 하나씩 받는 함수의 연쇄로 바꾸는 것입니다. 부분 적용은 몇 개든 한 번에 고정합니다(자세히는 50편).
- `Function.prototype.bind`가 내장 부분 적용입니다. `add3.bind(null, 10)(1, 2)`도 `13`입니다. 고정한 인수는 클로저가 아니라 바운드 함수 객체의 내부 슬롯에 저장되고, 첫 인수로 `this`도 고정합니다(자세히는 21편).
- 고정한 인수가 객체나 배열이면 참조가 공유되므로 이후 바깥에서 한 변경이 함수의 동작에 반영됩니다.

## 핵심 정리

- 클로저는 함수와 그 함수가 정의된 환경의 조합입니다. 함수 객체의 `[[Environment]]`가 정의 시점의 환경 레코드를 가리키고, 호출 위치는 영향을 주지 않습니다.
- 클로저는 값이 아니라 변수를 참조합니다. 같은 호출에서 만든 클로저는 환경을 공유하고, 바깥 함수를 호출할 때마다 새 환경이 생깁니다.
- 반복문의 클로저가 같은 값을 보는 것은 하나의 변수를 공유하기 때문이며, `let`·블록 안 선언·콜백·IIFE는 반복마다 새 환경을 만들어 해결합니다.
- 환경은 그 환경에 닫힌 함수에 도달할 수 있는 동안 메모리에 남습니다. 엔진은 참조되지 않는 변수를 제거하지만 같은 스코프의 다른 클로저나 직접 eval이 있으면 유지합니다.
- 오래된 클로저는 복사해 둔 값이나 옛 환경의 함수가 계속 쓰여 생기며, 호출 시점에 읽거나 새 함수로 교체해 해결합니다.

## 변수의 생명 주기

변수의 생명 주기(life cycle)는 변수가 생성되어 값을 담을 수 있게 된 시점부터 메모리가 회수되기까지의 기간입니다. 시작과 끝은 변수가 선언된 스코프가 정합니다(자세히는 12편).

| 변수 | 생성 | 회수 가능 시점 |
|------|------|----------------|
| 전역 변수 | 스크립트 실행 직전 | 전역 환경이 사라질 때. 브라우저는 페이지를 벗어날 때, Node.js는 프로세스가 끝날 때 |
| 함수 지역 변수 | 함수를 호출할 때마다 | 호출이 끝나고 아무도 참조하지 않을 때 |
| 블록 지역 변수 | 블록에 들어갈 때마다 | 블록이 끝나고 아무도 참조하지 않을 때 |

```js
function counter() {
  let n = 0 // 호출할 때마다 새로 생성된다
  n++
  return n
}
counter() // 1
counter() // 1 — 이전 호출의 n과 무관한 별개의 변수
```

- 변수는 선언문이 실행될 때가 아니라 스코프에 들어갈 때 생성됩니다. 스코프 안의 코드가 한 줄도 실행되기 전에 그 스코프의 모든 선언이 먼저 등록됩니다(호이스팅, 자세히는 03편).
- 생성과 초기화는 별개입니다. 초기화 시점은 선언 종류마다 다릅니다.

| 선언 | 생성 | 초기화 |
|------|------|--------|
| var | 스코프 진입 | 생성 즉시 `undefined` |
| let | 스코프 진입 | 선언문을 실행할 때. 초기값이 없으면 `undefined` |
| const | 스코프 진입 | 선언문을 실행할 때. 초기값 필수 |

- 스코프가 끝나도 변수가 곧바로 사라지지는 않습니다. 클로저가 변수를 참조하면 함수가 끝난 뒤에도 유지됩니다(자세히는 23편). 실제 회수 시점은 엔진의 가비지 컬렉터가 정합니다(자세히는 49편).

## 전역 변수의 문제점

전역 변수는 일반 스크립트(모듈이 아닌 스크립트)의 최상위, 곧 어떤 함수나 블록에도 속하지 않는 위치에서 선언한 변수입니다. 같은 페이지의 모든 스크립트가 하나의 전역 스코프를 공유하고, 전역 스코프는 스코프 체인의 끝이라 어디서든 보입니다.

| 문제 | 내용 |
|------|------|
| 암묵적 결합 | 어느 코드에서나 읽고 바꿀 수 있어서, 값이 바뀐 원인을 찾으려면 모든 코드를 봐야 한다 |
| 긴 생명 주기 | 프로그램이 끝날 때까지 메모리를 차지하고, 남은 상태가 이후 동작에 영향을 준다 |
| 이름 충돌 | 같은 이름의 전역 변수는 하나뿐이라 다른 파일·라이브러리의 변수를 덮어쓴다 |
| 검색 경로 | 스코프 체인 맨 끝에 있어 검색할 환경이 가장 많다 |
| 테스트 | 전역 상태가 테스트 사이에 남아 서로 영향을 준다 |

이름 충돌은 한 페이지에 스크립트가 여러 개일 때 일어납니다.

```js
// a.js
var total = 10
// b.js — 같은 페이지에 함께 로드
var total = 'none' // a.js의 total을 덮어쓴다
// 이후 a.js의 코드에서
total + 5 // 'none5'
```

변수 선언을 빠뜨린 할당은 더 조용히 전역을 오염시킵니다.

```js
function calc() {
  result = 1 + 2 // 선언 누락 → 전역 객체에 프로퍼티가 생긴다
}
calc()
result // 3
```

- 이것이 암묵적 전역(implicit global)입니다. 비엄격 모드에서만 허용되고, strict mode에서는 ReferenceError입니다(자세히는 19편).
- 암묵적 전역은 변수가 아니라 전역 객체의 프로퍼티입니다. 호이스팅되지 않아 할당 전에 읽으면 ReferenceError이고, `delete`로 지울 수 있습니다.
- 흔한 실수: `reslut = 3`처럼 변수 이름을 잘못 쓰면 에러 없이 새 전역이 생기고, 원래 변수는 갱신되지 않습니다.

## 전역 변수 억제

전역 변수를 줄이는 원칙은 두 가지입니다. 변수의 스코프를 가능한 좁게 하고, 전역에 남겨야 하는 것은 하나로 묶습니다. 라이브러리가 전역에 소수의 이름만 노출하는 것이 이 방식입니다.

| 방법 | 전역에 남는 것 | 정보 은닉 | 한계 |
|------|----------------|-----------|------|
| IIFE | 없음 | 가능 | 결과를 밖에서 쓰려면 전역 변수에 대입해야 한다 |
| 네임스페이스 | 객체 1개 | 불가 | 모든 멤버가 공개되고 누구나 덮어쓸 수 있다 |
| 모듈 패턴 | 객체 1개 | 가능 | 의존 관계와 로드 순서를 직접 관리한다 |
| ES 모듈 | 없음 | 가능 | 모듈을 지원하는 환경이 필요하다 |

### 즉시 실행 함수 (IIFE)

IIFE(Immediately Invoked Function Expression)는 정의와 동시에 한 번 실행하는 함수입니다. 내부 변수가 함수 스코프에 갇혀 전역에 남지 않습니다.

```js
(function () {
  var secret = 1
  console.log(secret) // 1
}())
typeof secret // 'undefined'
```

`function`으로 시작하는 문장은 함수 선언문으로 파싱되고, 선언문에는 이름이 필요합니다. 그래서 `function () {}()`는 SyntaxError입니다. 괄호(그룹 연산자)로 감싸면 표현식이 되어 바로 호출할 수 있습니다(자세히는 11편).

| 형태 | 비고 |
|------|------|
| `(function () {})()` | 함수 표현식만 괄호로 감싼다 |
| `(function () {}())` | 호출까지 괄호로 감싼다 |
| `(() => {})()` | 화살표 함수 |
| `(async () => {})()` | 모듈이 아닌 스크립트에서 await를 쓸 때 |

- 이름을 붙여도(`function init() {}`) 그 이름은 함수 안에서만 보이므로 전역에 남지 않습니다.
- 값을 인수로 넘겨 쓸 수 있습니다. `(function (g) { /* ... */ }(globalThis))`
- 앞 문장이 세미콜론 없이 끝나면 `(`가 그 문장의 호출로 이어집니다. 그래서 IIFE 앞에 `;`를 붙이는 관례가 있습니다.

```js
const a = 1
(function () {})() // TypeError: 1 is not a function
;(function () {})() // ✅ 앞에 세미콜론
```

- let·const와 블록(`{ const tmp = 1 }`)으로 임시 변수를 가둘 수 있게 되어 IIFE의 필요는 줄었습니다. 블록 밖으로 새는 var가 있는 코드에서는 여전히 IIFE를 씁니다.

### 네임스페이스 객체

네임스페이스(namespace)는 전역에 객체 하나만 만들고 모든 변수와 함수를 그 객체의 프로퍼티로 담는 방식입니다.

```js
globalThis.MYAPP ??= {} // 이미 있으면 재사용 (ES2021)
MYAPP.util = {}
MYAPP.util.sum = (a, b) => a + b
MYAPP.util.sum(1, 2) // 3
```

- ES2021 이전에는 `var MYAPP = MYAPP || {}`로 썼습니다. 파일마다 이 줄을 두면 로드 순서와 무관하게 같은 객체를 공유합니다.
- 객체를 중첩(`MYAPP.util.date`)해 영역을 나눕니다.

### 모듈 패턴

모듈 패턴(module pattern)은 IIFE가 반환한 객체를 변수 하나에 담고, 공개할 것만 그 객체에 넣는 방식입니다. 나머지는 클로저로 감춥니다(자세히는 23편).

```js
const counter = (function () {
  let count = 0 // 비공개
  return {
    inc() { return ++count },
    get value() { return count },
  }
}())
counter.inc()   // 1
counter.inc()   // 2
counter.value   // 2
counter.count   // undefined — 밖에서는 보이지 않는다
```

- 비공개 함수를 IIFE 안에서 이름 붙여 정의하고, 마지막에 공개할 이름만 객체로 반환하는 변형이 노출 모듈 패턴(revealing module pattern)입니다.

### ES 모듈과 블록 스코프

ES 모듈(ES2015)은 파일 하나가 하나의 모듈 스코프를 가집니다(자세히는 45편). 가장 직접적인 해결책입니다.

- 모듈 최상위의 var·let·const는 전역 객체에 붙지 않습니다. 밖에 공개할 것만 `export`합니다.
- 모듈 코드는 자동으로 strict mode이고 최상위 `this`는 `undefined`입니다(자세히는 46편).
- Node.js의 CommonJS 파일도 파일 단위 스코프라서 최상위 var가 전역 객체에 붙지 않습니다.
- 모듈을 쓸 수 없는 일반 스크립트에서는 `{ }` 블록과 let·const로 임시 변수를 가둡니다.

## var의 문제점

var는 ES5까지 유일한 변수 선언 키워드였습니다. let·const(ES2015)가 필요해진 이유가 다음 문제들입니다.

### 중복 선언 허용

```js
var user = 'kim'
var user = 'lee' // 에러 없이 덮어쓴다
user             // 'lee'
```

- 초기값이 없는 중복 선언은 기존 값을 유지합니다. `var x = 1; var x; x`는 `1`입니다. 함수 매개변수와 같은 이름의 `var a`도 값을 지우지 않습니다.
- 같은 이름을 실수로 다시 선언해도 에러가 없습니다. 중첩 루프에서 같은 카운터를 쓰면 안쪽 루프가 바깥 카운터를 망가뜨립니다.

```js
let n = 0
for (var i = 0; i < 2; i++) {
  for (var i = 0; i < 3; i++) n++ // 같은 i를 다시 선언
}
n // 3 — 바깥 루프는 한 번만 돈다
```

### 함수 레벨 스코프

var의 스코프는 가장 가까운 함수 본문이고, 함수가 없으면 전역입니다. `{ }` 블록은 var의 스코프가 아닙니다(자세히는 12편).

```js
if (true) {
  var leaked = 1
}
leaked // 1 — 블록 밖에서도 보인다

for (var i = 0; i < 3; i++) {}
i // 3 — 루프 변수가 루프 밖에 남는다
```

블록 안에서만 쓰려던 임시 변수가 같은 함수의 다른 변수와 충돌할 수 있습니다.

### 선언 전 접근

var는 스코프에 들어갈 때 `undefined`로 초기화되므로 선언문보다 앞에서 읽어도 에러가 없습니다.

```js
console.log(price) // undefined
var price = 100
```

선언문이 실행되지 않아도 변수는 생성됩니다.

```js
function f() {
  console.log(v) // undefined
  if (false) { var v = 1 } // 실행되지 않는 분기의 var도 선언된다
}
```

에러 없이 틀린 값이 흘러가는 의미 오류의 전형입니다(01편).

### 전역 객체 오염과 루프 변수 공유

- 일반 스크립트 최상위의 var는 전역 객체의 프로퍼티가 되어 내장 프로퍼티·다른 스크립트와 충돌합니다(아래 "전역 객체와 let").
- 반복문 안의 클로저가 모두 같은 var 변수를 참조합니다(아래 "for 문의 반복별 바인딩").

## let과 블록 레벨 스코프

let(ES2015)은 재할당할 수 있는 블록 스코프 변수를 선언합니다. 블록 레벨 스코프는 `{ }`로 둘러싼 코드 블록이 스코프를 만든다는 뜻입니다. 함수 본문, if·for·while·switch 본문, try·catch·finally, 단독 블록이 모두 해당합니다.

```js
if (true) {
  let inBlock = 1
}
typeof inBlock // 'undefined' — 블록 밖에서는 보이지 않는다
```

- 같은 스코프에서 같은 이름을 다시 선언하면 SyntaxError이고, 그 스크립트는 한 줄도 실행되지 않습니다. var·const·class·함수 선언과 섞어도 같습니다.

```js
let a = 1
let a = 2 // ❌ SyntaxError
var a = 3 // ❌ SyntaxError — var도 같은 스코프에 놓인다
```

- 스코프가 다르면 같은 이름을 쓸 수 있습니다. 안쪽 선언이 바깥 선언을 가리는 것을 섀도잉(shadowing)이라고 합니다(자세히는 12편).
- 안쪽 블록의 var도 함수 스코프로 올라가므로 바깥의 같은 이름 let과 충돌합니다. `{ let x; { var x } }`는 SyntaxError입니다.
- 함수 매개변수와 같은 이름의 let을 함수 본문 최상위에서 선언해도 SyntaxError입니다.
- 초기값 없이 선언하면 선언문을 실행할 때 `undefined`로 초기화됩니다. `let u; u`는 `undefined`입니다.
- `if (x) let y = 1`처럼 단일 문 자리에는 let 선언을 쓸 수 없습니다. SyntaxError입니다.
- let도 호이스팅됩니다. 스코프에 들어가는 순간 이름이 등록되지만 초기화되기 전에는 접근할 수 없습니다(다음 TDZ 절).

### for 문의 반복별 바인딩

`for (let ...)`는 반복마다 새 바인딩(per-iteration binding)을 만듭니다. 각 반복에서 만든 클로저는 그 반복의 변수만 봅니다.

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i))
// 3 3 3 — 콜백이 모두 하나의 i를 본다
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j))
// 0 1 2 — 반복마다 별개의 j
```

동작 규칙은 다음과 같습니다.

- 초기화 식은 루프 시작 전에 한 번만 실행됩니다.
- 매 반복 직전에 새 환경을 만들어 직전 반복의 변수 값을 복사합니다.
- 증감식(`j++`)은 새 환경에서 실행되므로 이미 만들어진 클로저가 보는 값은 바뀌지 않습니다.
- 본문에서 바꾼 값은 다음 반복으로 복사됩니다.

```js
const fs = []
for (let i = 0; i < 3; i++) {
  fs.push(() => i)
  i++ // 본문에서 변경
}
fs.map(f => f()) // [1, 3]
```

- 초기화 식 안에서 만든 함수는 반복 환경이 아니라 초기화 전용 환경의 변수를 봅니다. 이 변수는 갱신되지 않습니다.

```js
for (let i = 0, get = () => i; i < 3; i++) {
  console.log(get()) // 0 0 0
}
```

- `for...of`·`for...in`은 let·const 모두 반복마다 새 바인딩을 만듭니다. var로 선언하면 하나를 공유해서 클로저가 모두 마지막 값을 봅니다.
- 초기화·조건·증감식을 갖춘 일반 for 문의 선언부에서 const를 쓰면 반복마다 복사되지 않고, 첫 반복 뒤 증감식에서 TypeError입니다.
- var 시절에는 IIFE로 값을 복사해 가두는 방식으로 해결했습니다.

```js
const fs = []
for (var i = 0; i < 3; i++) {
  (function (n) { fs.push(() => n) })(i) // n은 호출마다 새 변수
}
fs.map(f => f()) // [0, 1, 2]
```

클로저가 변수를 붙잡는 원리는 23편에서 다룹니다.

## TDZ

TDZ(Temporal Dead Zone, 일시적 사각지대)는 스코프에 들어간 순간부터 let·const·class 선언문이 실행되어 초기화되기까지의 구간입니다. 이 구간에서 그 변수를 읽거나 쓰면 ReferenceError가 발생합니다.

```js
{
  // a의 TDZ 시작
  console.log(a) // ReferenceError: Cannot access 'a'
                 //   before initialization
  let a = 1      // 여기서 TDZ가 끝난다
}
```

- "Temporal"은 코드 위치가 아니라 실행 시점을 뜻합니다. 선언문보다 위에 쓴 함수라도 호출이 초기화보다 먼저면 TDZ입니다.

```js
function show() { return v } // 선언문보다 위에 있어도 된다
let v = 1
show() // 1 — 초기화 이후에 호출했으므로 정상
```

`show()`를 `let v = 1` 위에서 호출하면 ReferenceError입니다.

- let·const도 호이스팅됩니다. 같은 스코프에 let이 있으면 바깥 변수를 가리고, 초기화 전까지는 TDZ입니다.

```js
let x = 1
{
  console.log(x) // ReferenceError — 바깥 x(1)가 아니다
  let x = 2
}
```

- 읽기뿐 아니라 쓰기도 에러입니다. `x = 1; let x`는 ReferenceError입니다.
- 자기 자신을 초기값에서 참조해도 TDZ입니다. `let y = y`는 ReferenceError입니다.
- 적용 대상은 let·const·class입니다. `new Foo(); class Foo {}`는 ReferenceError입니다(자세히는 24편). 매개변수 기본값에도 적용됩니다. `function f(a = b, b = 1) {}`를 `f()`로 호출하면 뒤 매개변수를 먼저 참조해 ReferenceError입니다(자세히는 27편).
- var와 함수 선언에는 TDZ가 없습니다.
- 이유: const는 초기화 뒤 값이 바뀌면 안 되므로, var처럼 `undefined`로 먼저 초기화됐다가 값이 바뀌는 단계를 둘 수 없습니다. 초기화 전 접근을 막으면 선언 전 사용도 에러로 드러납니다.
- 에러 메시지 문구는 엔진마다 다릅니다. 위 문구는 V8의 것입니다.

### typeof와 TDZ

`typeof`는 선언되지 않은 이름에는 에러 없이 `'undefined'`를 반환하지만, TDZ에 있는 변수에는 ReferenceError를 던집니다. 선언된 식별자는 정상적으로 해석되기 때문입니다.

```js
typeof undeclared // 'undefined' — 선언 자체가 없다
{
  typeof a // ReferenceError — a는 선언됐지만 TDZ
  let a
}
```

- "typeof는 언제나 안전하다"는 ES5 시절의 가정은 let·const·class에는 맞지 않습니다.
- 전역 기능의 존재 검사(`typeof window !== 'undefined'`)는 선언되지 않았을 수 있는 이름에 쓰므로 계속 안전합니다.

### switch case의 TDZ

switch 문 전체가 하나의 블록이고, case 절은 스코프를 만들지 않는 레이블입니다. 한 case에서 선언한 let·const는 다른 case에서도 같은 스코프로 보입니다.

```js
switch (1) {
  case 0:
    let a = 'zero'
    break
  case 1:
    console.log(a) // ReferenceError
}
```

값이 `1`이면 `case 0`의 선언문을 건너뛰고 `case 1`로 바로 이동하므로 `a`는 초기화되지 않은 채 TDZ에 남습니다. 선언이 있는 case가 실제로 실행되면 정상입니다.

- 다른 case에서 같은 이름을 선언하면 같은 블록에서의 중복이라 SyntaxError입니다.
- 해결: case마다 `{ }`로 감싸 별도 블록을 만듭니다.

```js
switch (1) {
  case 0: { let a = 'zero'; break }
  case 1: { let a = 'one'; console.log(a) } // 'one'
}
```

ESLint의 `no-case-declarations` 규칙이 case 안의 선언을 잡아 줍니다. switch 문 자체는 07편에서 다룹니다.

## 전역 객체와 let

전역 객체(global object)는 실행 환경이 전역 스코프를 위해 만드는 객체입니다. 브라우저는 `window`, Node.js는 `global`, 어디서든 `globalThis`(ES2020)로 가리킵니다(자세히는 01편).

일반 스크립트 최상위에서 var는 전역 객체의 프로퍼티가 되고, let·const·class는 되지 않습니다.

```js
var a = 1
let b = 2
globalThis.a // 1
globalThis.b // undefined
b            // 2 — 이름으로는 접근할 수 있다
```

- ES 모듈과 Node.js CommonJS 파일의 최상위는 이 규칙의 대상이 아닙니다. 둘 다 var도 전역 객체에 붙지 않습니다.
- var가 전역 객체의 프로퍼티가 되면 내장 프로퍼티와 충돌합니다. 브라우저의 `window.name`은 대입값을 문자열로 바꾸는 접근자라서 다음과 같습니다.

```js
var name = 1
typeof name // 'string' — window.name에 대입되어 '1'이 된다
```

`let name = 1`은 전역 객체와 별개의 바인딩이라 `window.name`을 건드리지 않고, `name`은 숫자 `1`입니다.

- 이름 충돌은 스크립트의 첫 문장이 실행되기 전에 검사되고, 위반하면 그 스크립트 전체가 SyntaxError로 실행되지 않습니다.
  - 다른 스크립트에서 이미 var·함수·let·const·class로 선언한 이름을 let·const·class로 다시 선언하면 SyntaxError입니다.
  - 반대로 let이 먼저 있고 나중 스크립트가 같은 이름을 var로 선언해도 SyntaxError입니다.
  - 전역 객체의 삭제할 수 없는 프로퍼티(`undefined`, `NaN`, `Infinity`)와 같은 이름의 let·const도 SyntaxError입니다.
- 삭제할 수 있는(configurable) 프로퍼티와 같은 이름은 허용되고, let이 그 이름을 가립니다.

```js
globalThis.foo = 1 // 삭제할 수 있는 프로퍼티
let foo = 2        // 허용
foo                // 2 — let 바인딩이 먼저 검색된다
globalThis.foo     // 1
```

### 전역 선언적 환경 레코드

전역 환경 레코드(Global Environment Record)는 전역 스코프의 이름과 값을 저장하는 명세상의 구조입니다. 전역 객체와 연결된 객체 환경 레코드와, let·const·class를 저장하는 선언적 환경 레코드를 합친 형태입니다.

- `[[ObjectRecord]]`: 전역 객체를 감싼 객체 환경 레코드입니다. var·함수 선언, 암묵적 전역, 내장 전역(`Array` 등)이 여기로 보입니다.
- `[[DeclarativeRecord]]`: 최상위 let·const·class의 바인딩을 담는 선언적 환경 레코드입니다.
- `[[VarNames]]`: 최상위 var·함수 선언으로 만든 이름의 목록입니다. 충돌 검사에 쓰입니다.
- `[[GlobalThisValue]]`: 전역 코드의 `this` 값입니다.

| 선언 | 저장 위치 | 전역 객체 프로퍼티 | delete |
|------|-----------|--------------------|--------|
| 최상위 var, 함수 선언 | 객체 레코드, `[[VarNames]]` | O (configurable: false) | 불가 |
| 최상위 let, const, class | 선언적 레코드 | X | 해당 없음 |
| 암묵적 전역, `globalThis.x = 1` | 객체 레코드 | O (configurable: true) | 가능 |

- 식별자를 검색하면 선언적 레코드를 먼저 확인하고, 없을 때 객체 레코드를 확인합니다. 같은 이름이면 let·const가 이기는 이유입니다.
- 스크립트를 실행하기 전에 모든 최상위 선언을 검사하는 단계(GlobalDeclarationInstantiation)가 있습니다. 앞 절의 SyntaxError 규칙이 여기서 적용됩니다.
- 페이지의 전역 환경은 하나라서 모든 일반 스크립트가 선언적 레코드를 공유합니다. 한 스크립트의 최상위 let·const는 다음 스크립트에서 이름으로 읽을 수 있지만, 전역 객체의 프로퍼티는 아니라서 `window.x`로는 읽을 수 없습니다.
- 함수·모듈 등 다른 환경 레코드는 22편에서 다룹니다.

## const와 상수

const(ES2015)는 재할당할 수 없는 블록 스코프 변수를 선언합니다. 상수(constant)는 한 번 정한 뒤 바뀌지 않는 값에 붙인 이름입니다. 원시 값은 그 자체가 불변이라(자세히는 10편) 원시 값을 담은 const는 값까지 고정된 상수입니다.

```js
const PI = 3.14159
PI = 3 // TypeError: Assignment to constant variable.
```

- 선언과 동시에 초기화해야 합니다. `const c`는 SyntaxError(Missing initializer)이고, 값이 없다는 표시가 필요하면 `const c = undefined`로 씁니다.
- 재할당 시도는 실행 중에 TypeError가 납니다. `=`뿐 아니라 `+=`, `++`도 마찬가지이고, strict mode 여부와 무관하게 에러입니다.
- 블록 스코프, TDZ, 같은 스코프 중복 선언 불가, 최상위 선언이 전역 객체 프로퍼티가 되지 않는 점은 let과 같습니다.
- `for...of`·`for...in`에서는 반복마다 새 바인딩이라 `for (const x of list)`를 쓸 수 있습니다. 일반 for 문의 `for (const i = 0; i < 3; i++)`는 증감식에서 TypeError입니다.
- 네이밍 관례: 설정값·매직 넘버에 이름을 붙인 상수는 `MAX_RETRY`처럼 대문자 스네이크 표기를 쓰고, 실행 중에 정해지는 값은 `const now = Date.now()`처럼 camelCase로 씁니다(자세히는 03편).

흔한 실수는 재할당이 필요한 곳에 const를 쓰는 것입니다.

```js
const items = [1, 2, 3]
items = items.filter(n => n > 1) // ❌ TypeError
const big = items.filter(n => n > 1) // ✅ 새 이름에 담는다
```

## const와 객체 변경

const는 변수와 값의 연결(바인딩)을 고정할 뿐, 값의 내용을 고정하지 않습니다. 변수에는 객체 자체가 아니라 객체를 가리키는 참조가 저장되고(자세히는 10편), const는 그 참조를 바꾸지 못하게 합니다.

```js
const user = { name: 'Kim' }
user.name = 'Lee' // ✅ 프로퍼티 변경
user.age = 20     // ✅ 프로퍼티 추가
user = {}         // ❌ TypeError — 변수에 재할당
```

배열도 같습니다. `const list = []`에 `list.push(1)`은 가능하고, `list = []`는 TypeError입니다.

- 객체의 변경까지 막으려면 `Object.freeze`를 씁니다. freeze는 얕아서 바로 아래 프로퍼티만 막고, 중첩 객체는 막지 못합니다(깊은 동결은 14편).

```js
const cfg = Object.freeze({ a: 1, nested: { b: 2 } })
cfg.a = 9        // 비엄격 모드: 무시 / strict mode: TypeError
cfg.nested.b = 9 // 통과 — 중첩 객체는 얼려지지 않는다
```

- 함수에 const 객체를 넘기면 함수 안에서 그 객체가 바뀔 수 있습니다. const는 호출한 쪽의 변수만 보호합니다.
- 값을 바꾸는 대신 바뀐 사본을 새로 만들어 쓰면 const를 유지할 수 있습니다. 새 객체를 만들어 다른 const에 담거나, 재할당이 필요한 변수라면 let으로 선언합니다(스프레드는 36편).

## 사용 기준

| 항목 | var | let | const |
|------|-----|-----|-------|
| 스코프 | 함수 | 블록 | 블록 |
| 같은 스코프 재선언 | 가능 | 불가 | 불가 |
| 재할당 | 가능 | 가능 | 불가 |
| 초기값 | 선택 | 선택 | 필수 |
| 선언 전 접근 | `undefined` | ReferenceError | ReferenceError |
| 최상위가 전역 객체 프로퍼티 | O | X | X |

선택 규칙은 세 줄입니다.

1. 기본은 const로 선언합니다. 객체·배열의 내용을 바꾸는 것은 재할당이 아니므로 const로 충분합니다.
2. 재할당이 필요한 변수만 let으로 선언합니다. 카운터, 누적값, 일반 for 문의 인덱스가 해당합니다.
3. var는 새 코드에서 쓰지 않습니다.

```js
const list = [3, 5, 7] // 재할당 없음 → const
let total = 0          // 누적 → let
for (const n of list) total += n
total // 15
```

- 조건에 따라 값이 정해지는 경우는 let에 나중에 대입하기보다 삼항 연산자나 함수로 값을 만들어 const에 담는 편이 재할당 없이 끝납니다.
- 변수는 사용하는 위치에 가깝게, 가장 좁은 블록 안에 선언합니다. var 시절의 "함수 맨 위에 선언을 모으는" 관례는 필요 없습니다.
- ESLint의 `no-var`, `prefer-const` 규칙으로 이 기준을 강제할 수 있습니다.
- ES2015보다 오래된 환경을 지원해야 하면 직접 var로 쓰지 않고 트랜스파일러가 변환하게 합니다(자세히는 51편).

기존 코드의 var를 let·const로 바꿀 때 동작이 달라지는 지점은 다음과 같습니다.

| 지점 | 바뀌는 동작 |
|------|-------------|
| 선언 전 사용 | `undefined` 대신 ReferenceError |
| 블록 밖에서 쓰는 var | 블록 밖에서 접근할 수 없게 되므로 선언을 바깥으로 옮겨야 한다 |
| 최상위 var를 `window.x`로 읽는 코드 | `undefined`가 된다 |
| 반복문 안의 클로저 | 모두 마지막 값을 보던 것이 반복별 값을 보게 된다 |

## 핵심 정리

- 변수는 선언문이 실행될 때가 아니라 스코프에 들어갈 때 생성되고, var는 즉시 `undefined`로 초기화되지만 let·const는 선언문 실행 시 초기화됩니다.
- 전역 변수는 이름 충돌과 암묵적 결합을 일으키므로 IIFE·네임스페이스·모듈 패턴으로 줄이고, 지금은 ES 모듈과 블록 스코프가 기본 해법입니다.
- var는 중복 선언, 함수 레벨 스코프, 선언 전 `undefined` 접근, 전역 객체 오염이 문제이고, let은 블록 스코프·중복 선언 금지·TDZ로 이를 막습니다.
- 일반 스크립트 최상위의 var·함수 선언은 전역 객체 프로퍼티가 되고, let·const·class는 선언적 환경 레코드에 저장되어 전역 객체에 나타나지 않습니다.
- const는 재할당만 막으므로 객체의 프로퍼티는 바뀔 수 있습니다. 기본은 const, 재할당이 필요하면 let, var는 쓰지 않습니다.
- `for (let ...)`는 반복마다 새 바인딩을 만들고, switch의 case는 별도 스코프가 아니며, TDZ 변수에는 `typeof`도 ReferenceError를 던집니다.

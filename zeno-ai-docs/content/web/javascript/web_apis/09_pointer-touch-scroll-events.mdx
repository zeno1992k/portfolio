## MouseEvent 좌표 체계

MouseEvent는 마우스 이벤트(`click`, `mousemove` 등)가 전달하는 이벤트 객체이고, 위치를 네 가지 기준으로 제공합니다. PointerEvent와 WheelEvent도 MouseEvent를 상속하므로 같은 프로퍼티를 가집니다.

| 프로퍼티 | 기준 | 스크롤하면 |
|----------|------|------------|
| `clientX`, `clientY` | 뷰포트 왼쪽 위 | 같은 화면 위치면 값이 같다 |
| `pageX`, `pageY` | 문서 왼쪽 위 | 스크롤한 만큼 커진다 |
| `offsetX`, `offsetY` | `event.target`의 padding edge 왼쪽 위 | 요소 기준이라 변하지 않는다 |
| `screenX`, `screenY` | 모니터 화면 왼쪽 위 | 창을 옮기면 변한다 |

`x`, `y`는 `clientX`, `clientY`의 별칭입니다. `movementX`, `movementY`는 직전 `mousemove`와의 이동량입니다.

```js
// 세로로 300px 스크롤한 상태에서 뷰포트 (120, 50)을 클릭
e.clientX // 120
e.clientY // 50
e.pageY   // 350 (clientY + scrollY)
```

- `pageX` = `clientX` + `scrollX`, `pageY` = `clientY` + `scrollY`입니다.
- `offsetX`의 기준은 `currentTarget`이 아니라 `target`입니다. 자식 요소를 클릭하면 값이 그 자식 기준으로 바뀝니다.
- `offsetX`는 padding edge 기준이라 테두리(border) 두께만큼 border box 기준 값과 어긋납니다.
- 이벤트를 받은 요소 안에서의 위치가 필요하면 `e.clientX - el.getBoundingClientRect().left`처럼 직접 계산하는 편이 안전합니다(요소 기하는 06편).
- PointerEvent의 좌표 값은 소수일 수 있습니다.

흔한 실수는 `offsetX`를 요소 안쪽 좌표라고 믿고 쓰는 것입니다. 내부에 자식이 있으면 클릭한 위치에 따라 기준이 바뀌어 값이 튑니다.

## button·buttons와 수정 키

`button`은 이벤트를 일으킨 버튼 하나이고, `buttons`는 이벤트 시점에 눌려 있는 모든 버튼의 비트 마스크입니다.

| 값 | `button` | `buttons` 비트 |
|----|----------|----------------|
| 주 버튼(보통 왼쪽) | 0 | 1 |
| 오른쪽 버튼 | 2 | 2 |
| 가운데(휠) 버튼 | 1 | 4 |
| 뒤로 버튼 | 3 | 8 |
| 앞으로 버튼 | 4 | 16 |

`button`에서는 가운데가 1, 오른쪽이 2인데 `buttons`에서는 오른쪽이 2, 가운데가 4입니다. 두 프로퍼티의 번호 체계가 다릅니다.

```js
// 왼쪽 + 가운데 버튼을 동시에 누른 상태
e.buttons               // 5 (1 + 4)
Boolean(e.buttons & 1)  // true
Boolean(e.buttons & 2)  // false
Boolean(e.buttons & 4)  // true
```

- `mousedown`, `mouseup`에서 `button`은 상태가 바뀐 버튼을 가리킵니다.
- `mousemove`에서 `button`은 의미가 없어 0입니다. 드래그 중 어떤 버튼이 눌려 있는지는 `buttons`로 봅니다.
- `pointermove`처럼 버튼 상태가 바뀌지 않은 포인터 이벤트에서는 `button`이 -1입니다.
- 펜 지우개 버튼은 `buttons`의 32입니다.

수정 키는 이벤트가 발생한 시점의 키 상태입니다.

| 프로퍼티 | 키 |
|----------|----|
| `ctrlKey` | Ctrl |
| `shiftKey` | Shift |
| `altKey` | Alt (macOS는 Option) |
| `metaKey` | Windows 키 (macOS는 Command) |

`getModifierState('CapsLock')`처럼 호출하면 잠금 키(CapsLock, NumLock 등) 상태도 읽습니다. macOS에서 Ctrl+클릭은 오른쪽 클릭으로 취급되어 `contextmenu`가 발생하므로, "다중 선택" 단축키는 `e.ctrlKey || e.metaKey`로 두 플랫폼을 함께 처리합니다.

흔한 실수는 `mousemove`에서 `e.button === 2`로 오른쪽 드래그를 판별하는 것입니다. 항상 0이므로 `e.buttons & 2`를 써야 합니다.

## click·dblclick·auxclick·contextmenu

네 이벤트는 모두 클릭 계열이지만 발생 조건이 다릅니다.

| 이벤트 | 발생 조건 |
|--------|-----------|
| `click` | 주 버튼의 누름과 뗌이 같은 요소에서 끝났을 때 |
| `dblclick` | 짧은 간격으로 두 번째 `click`이 끝났을 때 |
| `auxclick` | 주 버튼이 아닌 버튼(가운데, 오른쪽, 뒤로, 앞으로)을 눌렀다 뗐을 때 |
| `contextmenu` | 컨텍스트 메뉴를 열려는 입력이 있을 때 |

```js
// 더블 클릭 시 이벤트 순서
// mousedown → mouseup → click
// mousedown → mouseup → click → dblclick
```

- `click`의 `detail`은 연속 클릭 횟수(1, 2, 3)입니다. 키보드(Enter, Space)나 `el.click()`으로 발생한 `click`은 `detail`이 0이므로 사용자의 마우스 클릭과 구분할 수 있습니다.
- 누른 요소와 뗀 요소가 다르면 `click`은 둘의 가장 가까운 공통 조상에 발생합니다.
- 가운데 버튼 클릭은 `click`이 아니라 `auxclick`입니다. `click` 리스너에서 가운데 클릭을 기대하면 동작하지 않습니다.
- `contextmenu`는 오른쪽 클릭, 터치 길게 누르기, 키보드 메뉴 키(또는 Shift+F10)로 발생하며 `preventDefault()`로 기본 메뉴를 막을 수 있습니다. 발생 시점(버튼을 누를 때인지 뗄 때인지)은 플랫폼마다 다릅니다.
- `click`, `auxclick`, `contextmenu`의 이벤트 객체는 PointerEvent입니다(Baseline 2020).

흔한 실수는 동작을 `mousedown`에 연결하는 것입니다. 키보드로는 `mousedown`이 발생하지 않으므로 버튼 동작은 `click`에 연결해야 키보드 사용자도 쓸 수 있습니다(자세히는 28편). 또 `contextmenu`를 막는 것은 접근 경로 하나를 없애는 일이므로 커스텀 메뉴에는 키보드 진입 방법을 함께 제공해야 합니다.

## mouseenter·mouseleave와 mouseover·mouseout

두 쌍 모두 포인터가 요소의 경계를 넘을 때 발생하지만 버블링과 자손 처리가 다릅니다.

| 구분 | `mouseenter` / `mouseleave` | `mouseover` / `mouseout` |
|------|------------------------------|---------------------------|
| 버블링 | 하지 않는다 | 한다 |
| 자손 요소로 이동 | 발생하지 않는다 | 발생한다 |
| 용도 | 요소 전체의 hover 진입·이탈 | 이벤트 위임, 자손 단위 추적 |

- 바깥에서 중첩된 요소 안으로 한 번에 들어오면 `mouseenter`는 바깥 조상부터 안쪽 순서로 각 요소에 한 번씩 발생합니다.
- `relatedTarget`은 포인터가 어디에서 왔는지(`mouseover`, `mouseenter`) 또는 어디로 갔는지(`mouseout`, `mouseleave`)를 가리킵니다. 창 밖이면 `null`입니다.
- `mouseover`와 `mouseout`을 `mouseenter`와 `mouseleave`처럼 쓰려면 `relatedTarget`으로 걸러야 합니다.

```js
list.addEventListener('mouseout', (e) => {
  if (list.contains(e.relatedTarget)) return // 내부 이동 무시
  console.log('list를 완전히 벗어남')
})
```

`mouseenter`와 `mouseleave`는 버블링하지 않으므로 상위 요소에 위임할 수 없습니다. 위임이 필요하면 `mouseover`와 `closest()`를 쓰거나, 캡처 단계로 등록합니다(리스너 옵션은 07편).

흔한 실수는 툴팁을 `mouseover`와 `mouseout`에 연결하는 것입니다. 자식 요소 위를 지나갈 때마다 `mouseout`이 먼저 발생해 툴팁이 깜빡입니다. 요소 전체 hover라면 `mouseenter`와 `mouseleave`를 씁니다. 터치 기기에서는 hover가 없으므로 이 이벤트들이 탭 직후에만 호환용으로 발생합니다.

## Pointer Events

Pointer Events는 마우스, 펜, 터치를 하나의 이벤트 모델로 다루는 API입니다(Baseline 2020, 널리 지원 2023). 이벤트 이름만 `pointerdown`, `pointermove`, `pointerup`처럼 바꾸면 세 입력이 같은 코드로 처리됩니다.

| 프로퍼티 | 의미 |
|----------|------|
| `pointerId` | 활성 포인터의 식별자. 접촉이 유지되는 동안 같다 |
| `pointerType` | `'mouse'`, `'pen'`, `'touch'` 중 하나(알 수 없으면 빈 문자열) |
| `isPrimary` | 해당 `pointerType`의 주 포인터인지 |
| `pressure` | 압력, 0–1 |
| `width`, `height` | 접촉면 크기(CSS px) |
| `tiltX`, `tiltY`, `twist` | 펜의 기울기와 회전 |

```js
el.addEventListener('pointerdown', (e) => {
  e.pointerType // 'touch'
  e.pointerId   // 접촉마다 다른 숫자
  e.isPrimary   // 첫 손가락이면 true, 두 번째면 false
  e.pressure    // 0.5 (압력을 못 읽는 장치의 눌림 상태)
})
```

- 압력 센서가 없는 장치는 버튼이 눌린 동안 `pressure`가 0.5, 아니면 0입니다. 마우스는 누르는 동안 0.5입니다. 따라서 `pressure > 0`을 "세게 눌렀다"로 해석하면 안 됩니다.
- `isPrimary`는 입력 종류마다 하나씩 있습니다. 마우스는 항상 `true`이고, 멀티터치에서는 처음 닿은 손가락이 뗄 때까지 주 포인터입니다.
- 멀티터치는 손가락마다 `pointerId`가 다르므로 `Map`에 `pointerId`를 키로 상태를 저장합니다. 단일 포인터 제스처는 `isPrimary`가 아닌 이벤트를 무시하면 간단해집니다.
- `pointerId`는 접촉이 끝나면 재사용될 수 있으므로 장기 식별자로 쓰지 않습니다.
- 모든 포인터 이벤트는 MouseEvent를 상속하므로 `clientX`, `buttons`, 수정 키도 그대로 있습니다.

## 포인터 이벤트 순서와 호환 마우스 이벤트

포인터 이벤트는 대응하는 마우스 이벤트보다 먼저 발생합니다.

| 상황 | 순서 |
|------|------|
| 마우스가 요소에 들어옴 | `pointerover` → `pointerenter` → `pointermove`… |
| 누름 | `pointerdown` |
| 이동 | `pointermove`… |
| 뗌 | `pointerup` |
| 마우스가 요소를 나감 | `pointerout` → `pointerleave` |

hover가 없는 터치와 펜 접촉은 `pointerover`, `pointerenter`가 `pointerdown` 직전에, `pointerout`, `pointerleave`가 `pointerup` 직후에 한꺼번에 발생합니다. 접촉 하나는 반드시 `pointerup`과 `pointercancel` 중 하나로 끝납니다. `pointerenter`와 `pointerleave`는 버블링하지 않습니다.

기존 마우스 이벤트만 듣는 코드가 깨지지 않도록 브라우저는 포인터 이벤트 뒤에 호환 마우스 이벤트(compatibility mouse events)를 이어서 발생시킵니다.

```text
마우스: pointerdown → mousedown → pointermove → mousemove
        → pointerup → mouseup → click
터치 탭: pointerdown → pointerup → (손가락 뗀 뒤)
        mouseover → mouseenter → mousemove → mousedown
        → mouseup → click
```

- 터치의 호환 마우스 이벤트는 손가락을 뗀 뒤 탭으로 인식될 때만 몰아서 발생합니다. 스크롤이나 드래그로 끝나면 발생하지 않습니다.
- 주 포인터의 `pointerdown`을 `preventDefault()`하면 이후의 `mousedown`, `mousemove`, `mouseup` 호환 이벤트가 발생하지 않습니다. `click`과 `contextmenu`, `mouseover`·`mouseout` 계열은 막히지 않습니다.
- 포인터 이벤트를 `preventDefault()`해도 스크롤은 막히지 않습니다. 스크롤과 줌은 `touch-action`으로만 제어합니다.

흔한 실수는 `pointerdown`과 `mousedown`에 같은 핸들러를 모두 등록하는 것입니다. 한 번 누르면 두 번 실행됩니다. 포인터 이벤트 하나만 씁니다.

## setPointerCapture·releasePointerCapture

`el.setPointerCapture(pointerId)`는 지정한 포인터의 이후 이벤트를 포인터 위치와 상관없이 `el`로 전달하게 하고, `releasePointerCapture(pointerId)`는 그 지정을 해제합니다.

```js
thumb.addEventListener('pointerdown', (e) => {
  thumb.setPointerCapture(e.pointerId)
})
thumb.addEventListener('pointermove', (e) => {
  // 포인터가 thumb 밖으로 나가도 계속 호출된다
})
```

- 캡처 중에는 `target`이 항상 캡처한 요소이고, `pointerup`도 그 요소로 옵니다.
- `hasPointerCapture(pointerId)`로 현재 캡처 여부를 확인합니다.
- 캡처를 얻으면 `gotpointercapture`, 잃으면 `lostpointercapture`가 발생합니다.
- `pointerup`이나 `pointercancel`이 오면 캡처는 자동으로 해제되며 `lostpointercapture`가 뒤따릅니다. 정리 코드는 `lostpointercapture`에 두면 종료 경로가 하나로 모입니다.
- 활성 포인터가 아닌 `pointerId`를 넘기면 `NotFoundError` 예외가 발생합니다. 마우스는 버튼을 누른 동안(보통 `pointerdown` 핸들러 안)에 호출해야 합니다.
- 터치 포인터는 `pointerdown` 직전에 대상 요소에 암묵적으로 캡처됩니다. 마우스는 암묵적 캡처가 없습니다.
- 캡처 중에는 다른 요소의 `pointerenter`·`pointerleave`가 발생하지 않습니다. 터치에서 손가락 아래 요소를 따라 hover 효과를 내려면 `pointerdown`에서 `releasePointerCapture`로 암묵적 캡처를 풀어야 합니다.

흔한 실수는 캡처 없이 `document`에 `mousemove`와 `mouseup` 리스너를 붙였다 떼는 구식 패턴을 유지하는 것입니다. 캡처를 쓰면 리스너를 요소 하나에 두고 해제 코드를 줄일 수 있습니다.

## pointercancel과 touch-action

`pointercancel`은 브라우저가 해당 포인터의 이벤트 흐름을 더 이어갈 수 없다고 판단해 접촉을 취소할 때 발생합니다. `pointerup` 대신 오며, 뒤이어 `pointerout`과 `pointerleave`가 옵니다.

발생 원인은 다음과 같습니다.

- 브라우저가 그 포인터로 스크롤, 핀치 줌 같은 기본 동작을 시작함
- 네이티브 드래그(이미지·링크·선택 텍스트 끌기)가 시작됨
- 화면 회전, 대화 상자나 메뉴 표시, 장치 연결 해제
- 동시 접촉이 너무 많거나 손바닥 접촉으로 판정됨

`pointercancel`을 받으면 진행 중이던 제스처를 `pointerup`과 달리 확정하지 않고 되돌려야 합니다.

`touch-action`은 터치가 시작된 요소에서 브라우저가 처리할 제스처를 CSS로 지정합니다(Baseline 2019).

| 값 | 브라우저가 처리하는 제스처 |
|----|----------------------------|
| `auto` | 모든 기본 터치 동작(기본값) |
| `none` | 없음. 모든 제스처를 스크립트가 받는다 |
| `pan-x`, `pan-y` | 가로 또는 세로 팬(스크롤)만 |
| `pinch-zoom` | 핀치 줌만 |
| `manipulation` | 팬과 핀치 줌만. 더블 탭 줌 같은 추가 제스처는 끈다 |

```css
.slider { touch-action: pan-y; }  /* 세로만 스크롤 */
.canvas { touch-action: none; }   /* 전부 JS */
.button { touch-action: manipulation; }
```

- 값은 터치가 시작되는 시점에 정해집니다. 팬이나 줌이 시작된 뒤 값을 바꿔도 그 동작에는 반영되지 않습니다.
- 터치한 요소부터 기본 터치 동작을 가진 가장 가까운 조상까지의 `touch-action`을 교집합으로 계산합니다. 자식에 `pan-y`를 두어도 부모가 `none`이면 팬은 허용되지 않습니다.
- `touch-action`이 허용하지 않은 방향의 이동은 `pointermove`로 계속 전달됩니다. 허용한 방향으로 브라우저가 스크롤을 시작하는 순간 `pointercancel`이 발생하고 이후 이동은 전달되지 않습니다.
- 가로 슬라이더에 `touch-action`을 지정하지 않으면 손가락이 조금만 비스듬히 움직여도 `pointercancel`이 와서 드래그가 끊깁니다.
- `touch-action: manipulation`은 탭 지연 없이 버튼을 반응하게 하는 용도로도 쓰입니다.

## getCoalescedEvents·getPredictedEvents

`getCoalescedEvents()`는 하나의 `pointermove`로 합쳐진 이전 포인터 이벤트들을 배열로 돌려주고, `getPredictedEvents()`는 브라우저가 속도와 궤적으로 예측한 앞으로의 이벤트를 돌려줍니다. 두 메서드 모두 Safari 18.2 지원으로 Baseline 2024가 되었습니다.

브라우저는 성능을 위해 `pointermove`를 프레임당 한 번으로 합쳐 전달합니다. 기기의 입력 샘플링은 더 촘촘하므로, 합쳐진 이벤트 하나만 쓰면 빠르게 그린 곡선이 꺾인 선으로 보입니다.

```js
canvas.addEventListener('pointermove', (e) => {
  for (const p of e.getCoalescedEvents()) {
    path.push([p.clientX, p.clientY]) // 합쳐지기 전 모든 점
  }
  for (const p of e.getPredictedEvents()) {
    ghost.push([p.clientX, p.clientY]) // 임시로만 그릴 예측점
  }
})
```

- 합쳐진 이벤트가 없으면 배열에는 이벤트 자신 하나만 들어 있습니다.
- 예측 이벤트는 실제 입력이 아닙니다. 다음 프레임에 실제 점이 오면 예측으로 그린 부분을 지우고 다시 그립니다.
- `getCoalescedEvents`는 보안 컨텍스트(HTTPS)에서만 노출됩니다.
- `pointerrawupdate`는 합치지 않은 원시 이벤트를 즉시 전달하는 별도 이벤트이며 Safari가 지원하지 않습니다(Chrome·Edge·Firefox만).

흔한 실수는 용도 없이 항상 호출하는 것입니다. 단순한 드래그 이동은 합쳐진 이벤트 하나로 충분하고, 필기·그리기처럼 경로의 정밀도가 중요한 경우에만 필요합니다.

## Touch Events와 지원 상태

Touch Events는 터치 화면 전용의 구형 입력 API로 `touchstart`, `touchmove`, `touchend`, `touchcancel` 네 이벤트를 제공합니다. 현재는 포인터 이벤트로 대체하는 것이 권장됩니다.

TouchEvent는 접촉 목록 세 가지를 가집니다. 각 목록은 `Touch` 객체의 배열 비슷한 `TouchList`입니다.

| 프로퍼티 | 내용 |
|----------|------|
| `touches` | 화면에 닿아 있는 모든 접촉 |
| `targetTouches` | `touches` 중 `touchstart` 대상이 현재 이벤트의 `target`과 같은 접촉 |
| `changedTouches` | 이 이벤트로 시작·이동·종료·취소된 접촉 |

```js
// 손가락 A는 box 위, 손가락 B는 다른 요소 위에 닿은 상태
// B를 뗄 때 B의 touchend
e.touches.length        // 1 (A만 남음)
e.targetTouches.length  // 0 (B의 대상 요소에는 남은 접촉 없음)
e.changedTouches.length // 1 (B)
```

- `touchend`와 `touchcancel`에서 끝난 접촉은 `touches`에서 이미 빠져 있고 `changedTouches`에만 있습니다. 뗀 손가락의 위치를 읽으려면 `changedTouches`를 봅니다.
- `Touch` 객체는 `identifier`, `clientX`, `pageX`, `screenX`, `target`, `radiusX`, `force` 등을 가집니다. 접촉은 `identifier`로 추적합니다.
- 접촉의 `target`은 `touchstart` 시점의 요소로 고정됩니다. 손가락이 요소 밖으로 나가도 `touchmove`는 처음 요소로 옵니다(마우스와 다른 점).
- `touchstart`를 `preventDefault()`하면 스크롤, 줌, 호환 마우스 이벤트(`click` 포함)가 모두 막힙니다. 리스너가 passive가 아니어야 가능합니다.

지원 상태는 Baseline이 아닙니다.

| 환경 | 지원 |
|------|------|
| Chrome·Edge | 지원 (터치 화면이 있는 환경 중심) |
| Firefox | 지원 (터치 장치가 없는 환경에서는 꺼져 있을 수 있음) |
| iOS Safari | 지원 |
| macOS Safari | 미지원 |

터치 이벤트로 모바일 기기를 판별하는 사이트가 많아서, 데스크톱 브라우저는 터치 화면이 없으면 이 이벤트를 꺼 두기도 합니다. 터치 이벤트는 새 코드에서 쓰지 않고 포인터 이벤트를 씁니다. 터치 가능 여부는 `navigator.maxTouchPoints`나 CSS `(pointer: coarse)` 미디어 쿼리로 판단합니다. `'ontouchstart' in window`는 기기 판별 수단으로 부정확합니다.

## 터치·휠 리스너의 passive 기본값

passive 리스너는 `preventDefault()`를 호출하지 않겠다고 약속한 리스너이며, 약속 덕분에 브라우저가 리스너 실행을 기다리지 않고 스크롤을 시작할 수 있습니다.

```js
el.addEventListener('touchmove', handler, { passive: false })
el.addEventListener('wheel', handler, { passive: true })
```

DOM 표준의 기본값 규칙은 다음과 같습니다.

- `touchstart`, `touchmove`, `wheel`, `mousewheel` 이벤트이고
- 대상이 `Window`, `Document`, `document.documentElement`, `document.body`이면 기본값이 `passive: true`입니다.
- 그 밖의 경우는 `false`입니다. 즉 일반 요소에 등록한 `touchmove` 리스너는 기본이 non-passive입니다.

핵심은 **가장 바깥 요소에 건 리스너만** 기본이 passive라는 점입니다. 기본값이 `true`일 때 `preventDefault()`를 호출하면 무시되고 콘솔에 경고가 남습니다.

```js
// ❌ window 대상은 기본 passive. 스크롤이 막히지 않는다
window.addEventListener('touchmove', (e) => {
  e.preventDefault()
})

// ✅ 명시적으로 passive: false
window.addEventListener(
  'touchmove',
  (e) => e.preventDefault(),
  { passive: false },
)
```

- non-passive 터치·휠 리스너는 스크롤이 시작되기 전에 리스너를 실행해 `preventDefault()` 여부를 확인해야 하므로 스크롤이 지연되고 버벅일 수 있습니다.
- 스크롤을 막아야 할 때는 가능하면 `touch-action`이나 CSS `overflow` 같은 선언적 방법을 쓰고, `passive: false`는 마지막 수단으로 씁니다.
- `scroll` 이벤트는 취소할 수 없는 이벤트라 `passive`와 무관합니다.
- 포인터 이벤트는 `preventDefault()`로 스크롤을 막지 못하므로 passive 문제가 없습니다.

## wheel 이벤트와 deltaMode

`wheel`은 마우스 휠이나 트랙패드 스크롤 같은 회전 입력이 일어날 때 발생하는 WheelEvent이고, 스크롤은 그 뒤에 일어나는 기본 동작입니다. `mousewheel`과 `DOMMouseScroll`은 비표준이므로 쓰지 않습니다.

| 프로퍼티 | 의미 |
|----------|------|
| `deltaX`, `deltaY`, `deltaZ` | 회전량. `deltaY`가 양수면 아래로 스크롤하는 방향 |
| `deltaMode` | 델타의 단위 |

| `deltaMode` | 상수 | 단위 |
|-------------|------|------|
| 0 | `DOM_DELTA_PIXEL` | 픽셀 |
| 1 | `DOM_DELTA_LINE` | 줄 |
| 2 | `DOM_DELTA_PAGE` | 페이지 |

```js
function toPixels(e) {
  if (e.deltaMode === 1) return e.deltaY * 16 // 줄 높이 가정
  if (e.deltaMode === 2) return e.deltaY * innerHeight
  return e.deltaY
}
// deltaMode 1, deltaY 3 → 48
```

- 엔진과 입력 장치에 따라 같은 휠 한 칸이 픽셀 값이나 줄 값으로 올 수 있습니다. 델타를 픽셀로 가정하고 계산하면 브라우저마다 속도가 달라집니다.
- 줄 높이 16은 임의의 환산값입니다. 정확한 줄 높이를 돌려주는 표준 API는 없습니다.
- 트랙패드 핀치 줌은 `ctrlKey`가 `true`인 `wheel` 이벤트로 전달됩니다(Chrome 31, Firefox 55, Safari 15부터). Ctrl+휠 줌과 구분되지 않으므로 지도·캔버스의 줌 처리는 `ctrlKey`를 확인하고 `preventDefault()`합니다.
- `preventDefault()`로 스크롤을 막으려면 대상이 `Window`·`Document`·`body`일 때 `passive: false`가 필요합니다.
- 스크롤할 수 없는 끝에 도달해도 `wheel`은 발생합니다. 스크롤 발생 여부는 `scroll`로 판단합니다.

흔한 실수는 `deltaY`의 부호나 크기를 그대로 스크롤 거리로 쓰는 것입니다. 장치와 설정에 따라 값이 크게 달라지므로 방향(부호)만 쓰거나 `deltaMode`로 환산해야 합니다.

## scroll·scrollend·resize 이벤트

`scroll`은 스크롤 위치가 바뀐 뒤에, `scrollend`는 스크롤이 완전히 끝난 뒤에, `resize`는 창 뷰포트 크기가 바뀐 뒤에 발생합니다.

**scroll**

- 문서 스크롤은 `document`에서 발생해 `window`로 버블링하고, 요소 스크롤은 그 요소에서 발생하며 버블링하지 않습니다. 모든 요소의 스크롤을 한곳에서 듣고 싶으면 `document`에 캡처 단계로 등록합니다.
- 사용자 입력, `scrollTo()` 같은 스크립트 호출, 키보드, 앵커 이동 모두 `scroll`을 일으킵니다.
- 이벤트는 취소할 수 없으므로 `preventDefault()`로 스크롤을 막을 수 없습니다. 막으려면 `wheel`·`touchmove`를 취소하거나 CSS `overflow`를 씁니다.
- 브라우저가 렌더링을 갱신하는 단계에서 프레임당 최대 한 번 발생하므로 별도의 throttle 없이도 빈도가 제한됩니다(렌더링 갱신 순서는 08편).
- 핸들러에서 무거운 계산이나 레이아웃을 강제하는 읽기(`offsetTop` 등, 06편)를 반복하면 스크롤이 끊깁니다. 요소가 화면에 보이는지는 `IntersectionObserver`로 판단합니다(43편).

**scrollend (Baseline 2025)**

`scrollend`는 스크롤 위치가 더 바뀌지 않고 사용자의 입력도 끝났을 때 발생합니다. Chrome 114, Firefox 109, Safari 26.2부터 지원하며 Baseline 2025입니다(2025년 12월).

```js
box.addEventListener('scrollend', () => {
  console.log(box.scrollTop) // 스크롤이 멈춘 최종 위치
})
```

- 터치는 손가락을 떼고 관성 이동이 끝난 뒤, 스무스 스크롤(`behavior: 'smooth'`)은 애니메이션이 끝난 뒤에 발생합니다. 휠, 키보드, 스크롤바 조작 뒤에도 발생합니다.
- 스크롤 위치가 바뀌지 않았으면 발생하지 않습니다. 이미 끝에 있는 상태에서 더 스크롤해도 오지 않습니다.
- 문서 스크롤의 `scrollend`는 `document`에서 발생해 `window`로 올라갑니다. 요소의 `scrollend`는 버블링하지 않습니다.
- Safari 26.2 이전 환경을 지원해야 하면 `'onscrollend' in window`로 감지하고, 없을 때는 `scroll`마다 타이머를 갱신하는 디바운스로 대체합니다.

**resize**

`resize`는 `window`에서만 발생하며 뷰포트(창 안쪽) 크기가 바뀔 때 일어납니다.

- 브라우저 줌 변경, 창 크기 조절, 기기 회전이 원인입니다. 렌더링 갱신 단계에서 프레임당 한 번 처리됩니다.
- 요소의 크기 변화는 `resize`로 알 수 없습니다. `ResizeObserver`를 씁니다(43편).
- 핀치 줌은 레이아웃 뷰포트를 바꾸지 않으므로 `window`의 `resize`가 발생하지 않습니다. 이때는 `visualViewport`(Baseline 널리 지원)의 `resize`와 `scroll` 이벤트를 씁니다.
- 현재 크기는 `innerWidth`, `innerHeight`로 읽습니다. 스크롤바를 제외한 크기는 `document.documentElement.clientWidth`입니다.

흔한 실수는 반응형 분기를 `resize` 핸들러에서 `innerWidth`로 판정하는 것입니다. 구간 판정은 `matchMedia()` 변화 이벤트가 더 정확하고 호출도 적습니다.

## 포인터 이벤트 기반 드래그·스와이프 제스처

포인터 이벤트로 제스처를 만드는 기본 틀은 `touch-action` 지정, `pointerdown`에서 캡처, `pointermove`로 이동량 추적, `pointerup`·`pointercancel`로 종료 처리입니다.

```js
let startX = 0, startT = 0
box.style.touchAction = 'pan-y' // 세로 스크롤은 브라우저에 맡김

box.addEventListener('pointerdown', (e) => {
  if (!e.isPrimary || e.button !== 0) return
  startX = e.clientX
  startT = e.timeStamp
  box.setPointerCapture(e.pointerId)
})
```

```js
box.addEventListener('pointermove', (e) => {
  if (!box.hasPointerCapture(e.pointerId)) return
  const dx = e.clientX - startX
  box.style.transform = `translateX(${dx}px)`
})
```

```js
box.addEventListener('pointerup', (e) => {
  const dx = e.clientX - startX
  const v = Math.abs(dx) / (e.timeStamp - startT) // px/ms
  const swiped = Math.abs(dx) > 80 || v > 0.5
  box.style.transform = ''
  console.log(swiped ? (dx > 0 ? 'right' : 'left') : 'stay')
})
box.addEventListener('pointercancel', () => {
  box.style.transform = '' // 확정하지 않고 되돌린다
})
```

스와이프 판정은 거리와 속도 둘 중 하나가 기준을 넘으면 성립하게 합니다.

| 이동 거리 dx | 시간 | 속도 | 판정 |
|--------------|------|------|------|
| 100px | 400ms | 0.25px/ms | right (거리 초과) |
| –40px | 50ms | 0.8px/ms | left (속도 초과) |
| 30px | 300ms | 0.1px/ms | stay |

- 짧고 빠른 플릭은 거리가 짧아도 스와이프로 인정하려고 속도 기준을 함께 둡니다.
- `touch-action`이 `pan-y`이면 가로 이동은 계속 전달되고 세로로 시작하면 브라우저가 스크롤하며 `pointercancel`이 옵니다. 세로 이동이 우세해지면 그 제스처를 포기하는 동작입니다.
- 가로 슬라이더를 직접 구현하지 않고 CSS `scroll-snap`과 네이티브 가로 스크롤로 만들 수 있으면 그쪽이 접근성과 관성 처리에서 유리합니다.
- 이미지나 링크를 끌면 마우스에서는 네이티브 드래그가 시작되어 `pointercancel`이 발생합니다. 요소를 `draggable="false"`로 하거나 `user-select: none`을 지정합니다(Drag and Drop API는 49편).
- 드래그 중 `pointermove`에서 DOM을 직접 읽고 쓰기를 반복하면 끊깁니다. 위치는 `transform`으로 갱신하고, 읽기 비용이 큰 작업은 `requestAnimationFrame` 안에서 한 번에 처리합니다(08편).
- 키보드로 같은 동작을 할 방법이 없으면 포인터 전용 제스처는 접근성 결함입니다(자세히는 28편).

## scrollsnapchange·scrollsnapchanging

`scrollsnapchange`는 스크롤이 끝나 새 스냅 대상이 선택되었을 때, `scrollsnapchanging`은 스크롤이 진행되는 중 앞으로 선택될 스냅 대상이 바뀌었을 때 스크롤 컨테이너에서 발생하는 SnapEvent입니다. Chrome·Edge 129부터 지원하며 Baseline이 아닙니다(Firefox·Safari 미지원).

```js
carousel.addEventListener('scrollsnapchange', (e) => {
  e.snapTargetInline?.classList.add('active')
})
```

- SnapEvent는 `snapTargetBlock`과 `snapTargetInline`을 가집니다. 각각 블록 축과 인라인 축에서 선택된 스냅 대상 요소이며 해당 축에 스냅이 없으면 `null`입니다.
- `scrollsnapchange`는 스크롤이 끝날 때 `scrollend` 바로 앞에 발생합니다. 스냅 대상이 이전과 달라졌을 때만 옵니다.
- `scrollsnapchanging`은 사용자가 아직 손을 떼기 전에도 "여기서 놓으면 이 슬라이드에 멈춘다"는 예측을 알려 주므로, 페이지 표시기(인디케이터)를 미리 갱신하는 용도에 맞습니다.
- 이 이벤트는 CSS `scroll-snap-type`이 적용된 컨테이너에서만 의미가 있습니다.
- `'onscrollsnapchange' in window`로 감지해 점진적 향상으로 쓰고, 미지원 환경에서는 `scrollend`에서 스냅된 요소를 계산하거나 컨테이너를 `root`로 하는 `IntersectionObserver`로 대체합니다(43편).

## 핵심 정리

- 좌표는 `clientX`(뷰포트), `pageX`(문서, `clientX` + 스크롤), `offsetX`(`target`의 padding edge), `screenX`(화면)로 구분하고, `button`(변경된 버튼)과 `buttons`(비트 마스크)는 번호 체계가 다릅니다.
- 입력 처리는 포인터 이벤트 하나로 통일합니다. 터치는 암묵적 포인터 캡처를 받고, 브라우저가 스크롤을 시작하면 `pointercancel`로 끝나며, 스크롤·줌 제어는 `touch-action`으로만 합니다.
- Touch Events는 Baseline이 아니며(macOS Safari 미지원) 새 코드에는 쓰지 않습니다. `touchstart`·`touchmove`·`wheel`은 `window`·`document`·`body`에서 기본이 passive라서 `preventDefault()`에는 `passive: false`가 필요합니다.
- `wheel`의 델타는 `deltaMode`에 따라 픽셀·줄·페이지이며, `scroll`은 취소할 수 없고 프레임당 한 번 발생하고, `scrollend`는 Baseline 2025, `scrollsnapchange`·`scrollsnapchanging`은 Chromium 계열만 지원합니다.

## XSS

XSS(Cross-Site Scripting)는 공격자가 넣은 스크립트가 피해자가 보고 있는 사이트의 출처에서 실행되는 취약점입니다. 실행된 스크립트는 그 사이트의 스크립트와 권한이 같아서 DOM, 저장소, 같은 출처 `fetch`, 로그인 상태를 모두 쓸 수 있습니다(동일 출처 정책은 62편).

### 유형

| 유형 | 입력이 실행되기까지 |
|------|---------------------|
| 저장형(stored) | 입력이 서버 DB에 저장되고, 그 페이지를 여는 모든 사용자에게 실행됨(댓글, 프로필) |
| 반사형(reflected) | 요청의 URL 매개변수가 응답 HTML에 그대로 반사됨. 공격자가 만든 링크를 클릭하게 유도 |
| DOM 기반 | 서버는 무해한 응답을 주고, 클라이언트 스크립트가 입력을 위험한 DOM API로 넣어서 실행됨 |

```js
const q = new URLSearchParams(location.search)
const user = q.get('user')
welcome.innerHTML = `Welcome back, ${user}!` // ❌ DOM 기반 XSS
// ?user=<img src=x onerror=alert(1)> 이 실행됨
welcome.textContent = `Welcome back, ${user}!` // ✅
```

DOM 기반 XSS의 입력(소스)은 `location.search`, `location.hash`, `document.referrer`, `window.name`, `postMessage` 데이터, 저장소 값, `fetch` 응답 같은 외부에서 온 값입니다. 서버 코드에 취약점이 없어도 생길 수 있어서 서버 검사로는 막을 수 없습니다.

### 위험한 DOM 싱크

싱크(sink)는 문자열을 HTML이나 코드로 해석하는 API입니다. 신뢰할 수 없는 문자열이 여기에 닿으면 안 됩니다.

| 종류 | 싱크 |
|------|------|
| HTML 해석 | `innerHTML`, `outerHTML`, `insertAdjacentHTML()`, `document.write()`, `iframe.srcdoc`, `Range.createContextualFragment()`, `setHTMLUnsafe()`, `DOMParser`로 만든 노드를 문서에 삽입 |
| 코드 실행 | `eval()`, `new Function()`, `setTimeout(문자열)`, `setInterval(문자열)` |
| 스크립트 요소 | `script.src`, `script.text`, `script.textContent` |
| URL 컨텍스트 | `a.href`·`location`에 대입하는 `javascript:` URL, `iframe.src` |
| 속성 | `onclick`·`onerror` 같은 이벤트 핸들러 속성(`setAttribute`로 만들 때 포함) |

안전한 대안은 문자열을 해석하지 않는 API입니다.

- 텍스트: `textContent`(HTML로 해석하지 않음), `createTextNode()`
- 구조: `createElement()`와 `append()`, `<template>`(자세히는 05편, 22편)
- 속성: `setAttribute()`로 이벤트 핸들러 속성이 아닌 값만 지정하고, URL은 스킴을 검사한 뒤 대입

```js
const a = document.createElement('a')
const url = new URL(input, location.origin)
if (url.protocol === 'https:') a.href = url.href
a.textContent = label
```

### 방어의 층

한 가지로 막을 수 없어서 겹쳐서 씁니다.

1. 출력 이스케이프: 값이 놓이는 컨텍스트(HTML 본문, 속성, URL)에 맞게 인코딩합니다. 템플릿 엔진은 기본적으로 이를 합니다. 속성값은 항상 따옴표로 감쌉니다.
2. 정화(sanitize): HTML 자체를 받아야 할 때 검증된 정화기로 위험한 부분을 제거합니다(아래).
3. Trusted Types: 위험한 싱크가 정화를 거친 값만 받게 강제합니다(아래).
4. CSP: 주입이 일어나도 실행을 막는 최후 방어선입니다(아래).
5. 쿠키의 `HttpOnly`: 스크립트가 세션 쿠키를 읽지 못하게 해 피해를 줄입니다.

**흔한 실수:** 입력에서 `<script>`만 지우는 블랙리스트입니다. `onerror` 속성, `javascript:` URL 등 우회가 많아서 허용 목록 방식의 정화기를 씁니다.

## HTML Sanitizing

정화(sanitizing)는 신뢰할 수 없는 HTML 문자열에서 스크립트 실행으로 이어지는 요소와 속성을 제거해 안전한 HTML로 바꾸는 과정입니다. 사용자가 서식 있는 글을 입력해야 할 때 필요합니다. 정규식으로 직접 만들지 않고 검증된 라이브러리(DOMPurify 등)나 브라우저 내장 기능을 씁니다.

```js
const clean = DOMPurify.sanitize(userHtml)
box.innerHTML = clean // 정화 결과만 싱크에 넣음
```

- 정화는 삽입 직전, 결과를 쓰는 곳에서 합니다. 저장 시점에 한 정화는 나중에 규칙이 바뀌면 낡습니다.
- 정화한 결과를 다시 문자열로 가공(연결, 치환)하면 안전성이 깨질 수 있습니다.
- 서식이 필요 없으면 정화가 아니라 `textContent`로 충분합니다.

### Sanitizer API와 setHTML

Sanitizer API는 브라우저가 정화를 내장으로 제공합니다. 미Baseline이며 Chrome 146과 Firefox 148 이상이 지원하고 Safari는 아직 지원하지 않습니다(2026-10 데이터). 기능 검사 후 쓰고 없으면 라이브러리로 대체합니다.

| 메서드 | 동작 |
|--------|------|
| `Element.setHTML()`, `ShadowRoot.setHTML()`, `Document.parseHTML()` | 항상 XSS에 안전하지 않은 요소와 속성을 제거(사용자 설정으로도 되살릴 수 없음) |
| `Element.setHTMLUnsafe()`, `ShadowRoot.setHTMLUnsafe()`, `Document.parseHTMLUnsafe()` | 사용자 지정 `Sanitizer` 규칙만 따름. 안전을 보장하지 않으므로 필요할 때만 사용 |

```js
box.setHTML('abc <script>alert(1)</script> def')
// box의 내용: abc  def (script 제거)
const s = new Sanitizer({ elements: ['p', 'b', 'a'] })
box.setHTML(html, { sanitizer: s }) // 허용 목록 방식
```

- 기본 정화는 `script`, `iframe`, `embed`, `frame`, `object`, `use` 요소, 모든 이벤트 핸들러 속성, 주석, `data-*` 속성을 제거합니다. 기본 `Sanitizer`는 여기에 더해 클릭재킹·스푸핑에 쓰이는 것도 제거합니다.
- `Sanitizer` 설정은 허용 방식(`elements`, `attributes`로 지정한 것만 남김)과 제거 방식(`removeElements`, `removeAttributes`로 지정한 것만 제거)을 지원합니다. 허용 방식을 권장합니다.
- `setHTMLUnsafe()`와 `parseHTMLUnsafe()`는 05편에서 다룬 HTML 해석 API이고, 이름의 Unsafe는 사용자가 안전성을 책임진다는 뜻입니다.

## CSP

CSP(Content Security Policy)는 페이지가 불러오거나 실행할 수 있는 리소스의 출처와 방식을 서버가 선언하고 브라우저가 강제하는 정책입니다. XSS 방어의 마지막 층이며, 주입이 일어나도 실행을 막는 것이 목적입니다. Baseline 널리 지원합니다.

설정 방법은 응답 헤더가 기본입니다.

```http
Content-Security-Policy: default-src 'self';
  img-src 'self' cdn.example
```

- `<meta http-equiv="Content-Security-Policy">`도 있지만 일부 지시어(`frame-ancestors`, `report-to`, `sandbox`)는 지원하지 않습니다. 정적 SPA처럼 헤더를 못 줄 때만 씁니다.
- `Content-Security-Policy-Report-Only` 헤더는 차단하지 않고 위반만 보고해서 정책을 시험하는 용도입니다.

### 지시어

| 범주 | 지시어 | 통제하는 것 |
|------|--------|-------------|
| 가져오기 | `default-src` | 다른 가져오기 지시어가 없을 때의 기본값 |
| | `script-src` | JavaScript(`script-src-elem`은 요소, `script-src-attr`은 인라인 핸들러) |
| | `style-src`, `img-src`, `font-src`, `media-src` | 해당 리소스 |
| | `connect-src` | `fetch`, XHR, WebSocket, EventSource 대상 |
| | `object-src`, `worker-src`, `manifest-src` | 각 대상 |
| 문서 | `base-uri` | `base` 요소가 지정할 수 있는 URL |
| 탐색 | `form-action` | 폼 제출 대상 |
| | `frame-ancestors` | 이 문서를 감쌀 수 있는 부모(아래 클릭재킹) |
| 기타 | `upgrade-insecure-requests` | HTTP 요청을 HTTPS로 올림 |
| | `require-trusted-types-for`, `trusted-types` | Trusted Types 강제와 정책 이름 허용 목록 |
| | `sandbox`, `report-to` | iframe sandbox와 같은 제한, 위반 보고 대상 |

- 정책에 `default-src`나 `script-src`가 있으면 인라인 `script`, `onclick` 같은 인라인 핸들러, `javascript:` URL, `eval()`이 기본으로 차단됩니다. 핸들러는 `addEventListener`로 옮깁니다.
- `'self'`는 같은 출처, `'none'`은 전부 차단, `https:`는 스킴, `*.example.org`는 서브도메인 와일드카드입니다.
- `'unsafe-inline'`과 `'unsafe-eval'`은 인라인 실행과 `eval` 계열을 허용합니다. CSP의 효과를 크게 깎으므로 쓰지 않습니다. `'wasm-unsafe-eval'`은 WebAssembly 컴파일만 허용하는 더 좁은 키워드입니다(자세히는 55편).
- 두 정책이 함께 있으면 둘 다 만족해야 합니다.

## CSP nonce·hash·strict-dynamic

호스트 허용 목록(`script-src cdn.example`)은 허용된 호스트에 우회 가능한 스크립트가 있으면 뚫려서 정책이 길고 약합니다. 지금 권장하는 방식은 어떤 스크립트를 실행할지 nonce나 hash로 개별 지정하는 엄격한(strict) CSP입니다.

### nonce

nonce는 응답마다 새로 만드는 추측 불가능한 난수입니다. 헤더와 `script` 요소의 `nonce` 속성이 일치하는 스크립트만 실행됩니다.

```http
Content-Security-Policy: script-src 'nonce-4Zx9kQ'
```

```html
<script nonce="4Zx9kQ">init()</script>
```

- 요청마다 암호학적으로 안전한 난수로 새로 만들어야 합니다. 고정하거나 재사용하면 공격자가 추측해 주입한 스크립트에 붙입니다.
- 서버가 HTML을 렌더링할 때 넣는 방식이라 정적으로 캐시되는 페이지에는 맞지 않습니다. 그런 페이지는 hash를 씁니다.

### hash

스크립트 내용의 해시(`sha256`, `sha384`, `sha512`를 base64로 적고 알고리즘 접두어를 붙임)를 정책에 적는 방식입니다. 내용이 그 해시와 일치하는 인라인 스크립트만 실행됩니다.

```http
Content-Security-Policy: script-src 'sha256-B2yPHKaXn...='
```

- 스크립트 내용이 한 글자만 바뀌어도 해시를 갱신해야 합니다.
- 해시는 인라인 이벤트 핸들러에는 적용되지 않습니다. 레거시를 위해 `'unsafe-hashes'`와 핸들러 코드의 해시를 함께 쓰는 방법이 있지만 가급적 `addEventListener`로 옮깁니다.
- 외부 스크립트의 `integrity` 속성 해시도 CSP에 쓸 수 있으며, `integrity`에 나열한 모든 유효한 해시가 CSP에 있어야 로드됩니다.

### strict-dynamic

`'strict-dynamic'`은 nonce나 hash로 신뢰된 스크립트가 동적으로 불러오는 스크립트에도 신뢰를 전파합니다. 이 키워드가 있으면 호스트 허용 목록, `'self'`, `'unsafe-inline'`은 무시됩니다. 스크립트 로더가 다른 스크립트를 주입하는 현대 앱에 맞습니다.

```http
Content-Security-Policy: script-src 'nonce-4Zx9kQ'
  'strict-dynamic' https: 'unsafe-inline';
  object-src 'none'; base-uri 'none'
```

- 위 예처럼 `https:`와 `'unsafe-inline'`을 함께 두는 것은 구형 브라우저용 대체입니다. `strict-dynamic`을 이해하는 브라우저는 둘을 무시하고 nonce만 따릅니다.
- `object-src 'none'`과 `base-uri 'none'`은 엄격한 CSP의 짝입니다. `base` 요소를 주입해 상대 경로 스크립트의 출처를 바꾸는 공격을 막습니다.
- 신뢰는 nonce나 hash로 허용된 스크립트에서 시작해 그 스크립트가 불러오는 스크립트로만 이어집니다.

## Trusted Types 개요

Trusted Types는 위험한 DOM 싱크에 일반 문자열 대신 정책이 만든 신뢰된 값만 넣도록 브라우저가 강제하는 API입니다. 개발자가 정화 코드를 놓칠 수 있는 DOM 기반 XSS를 구조적으로 막습니다. Baseline 2026이고 Chrome 83, Firefox 148, Safari 26 이상이 지원합니다.

| 신뢰된 타입 | 받는 싱크 |
|-------------|-----------|
| `TrustedHTML` | `innerHTML`, `outerHTML`, `insertAdjacentHTML()`, `document.write()` 등 HTML 싱크 |
| `TrustedScript` | `eval()`, `new Function()`, `setTimeout(문자열)` 등 코드 실행 싱크 |
| `TrustedScriptURL` | `script.src`, `new Worker()` 등 스크립트 URL 싱크 |

강제는 CSP로 켭니다.

```http
Content-Security-Policy: require-trusted-types-for 'script';
  trusted-types app-policy
```

- `require-trusted-types-for 'script'`는 위 싱크에 문자열을 직접 넣으면 `TypeError`를 던지게 합니다.
- `trusted-types`는 만들 수 있는 정책 이름의 허용 목록입니다. 같은 이름의 정책을 여러 번 만들려면 `'allow-duplicates'`가 필요합니다.
- `Content-Security-Policy-Report-Only`로 먼저 위반만 보고받아 코드를 고칠 수 있습니다.

### 정책 만들기

정책은 `trustedTypes.createPolicy(이름, 변환 함수들)`로 만들고, 그 정책의 `createHTML()` 등이 문자열을 신뢰된 값으로 바꿉니다.

```js
const policy = trustedTypes.createPolicy('app-policy', {
  createHTML: (s) => DOMPurify.sanitize(s),
  createScriptURL: (s) => {
    if (s.startsWith('/js/')) return s
    throw new TypeError('blocked')
  },
})
el.innerHTML = policy.createHTML(userHtml) // ✅
el.innerHTML = userHtml // ❌ TypeError
```

- 정책 함수가 검증·정화의 유일한 장소가 되어, 감사할 코드가 정책 몇 개로 줄어듭니다.
- 이름이 `default`인 정책은 정책 없이 문자열을 넣은 모든 싱크에서 자동으로 호출됩니다. 레거시 코드를 점진적으로 옮길 때 쓰고, 값이 `null`이나 `undefined`가 되면 `TypeError`입니다.
- `trustedTypes.isHTML()`, `isScript()`, `isScriptURL()`로 값이 신뢰된 타입인지 확인하고, `emptyHTML`은 빈 `TrustedHTML`입니다. 라이브러리와 컴포넌트는 `createPolicy`로 자기 정책을 만들되 허용 목록(`trusted-types`)에 등록합니다.
- 워커에서도 쓸 수 있습니다. 지원하지 않는 환경을 위해 `window.trustedTypes` 존재를 확인합니다.

## frame-ancestors와 클릭재킹

클릭재킹(clickjacking)은 공격자 페이지가 대상 사이트를 투명한 iframe으로 올려놓고, 그 위에 미끼 버튼을 겹쳐서 사용자가 모르게 대상 사이트의 버튼을 누르게 하는 공격입니다. 방어는 내 페이지를 다른 사이트가 감싸지 못하게 하는 것입니다.

```http
Content-Security-Policy: frame-ancestors 'none'
Content-Security-Policy: frame-ancestors 'self'
  https://partner.example
```

- `frame-ancestors`는 `frame`, `iframe`, `object`, `embed`로 이 문서를 감쌀 수 있는 부모를 정합니다(Baseline 널리 지원). `'none'`은 어떤 부모도 허용하지 않습니다.
- 헤더에서만 동작하고 `meta`와 Report-Only에서는 동작하지 않습니다. `default-src`로 대체되지 않으므로 직접 써야 합니다.
- 중첩된 프레임은 모든 조상이 허용 목록에 있어야 합니다.
- 구형 헤더 `X-Frame-Options: DENY`(전체 금지)와 `SAMEORIGIN`(같은 출처만)도 같은 역할을 합니다. 둘 다 있으면 `frame-ancestors`를 이해하는 브라우저는 `X-Frame-Options`를 무시합니다.
- `frame-src`는 반대로 이 문서가 불러올 iframe의 출처를 제한합니다. 헷갈리지 않게 합니다.
- 세션 쿠키에 `SameSite=Lax`나 `Strict`를 주면 감싸진 상태에서 인증 쿠키가 실리지 않아 피해가 줄어듭니다.

## Subresource Integrity

SRI(Subresource Integrity)는 외부(CDN) 스크립트와 스타일시트가 변조되지 않았는지 브라우저가 해시로 확인하는 기능입니다. Baseline 널리 지원합니다.

```html
<script src="https://cdn.example/lib.js"
  integrity="sha384-oqVuAfXRKap7..."
  crossorigin="anonymous"></script>
```

- `integrity` 값은 `sha256`, `sha384`, `sha512` 중 하나의 base64 해시입니다. 공백으로 여러 개를 나열할 수 있고 브라우저는 가장 강한 알고리즘의 해시만 비교하며, 하나라도 일치하면 로드합니다.
- 일치하는 해시가 없으면 리소스를 로드하지 않고 네트워크 오류로 처리합니다.
- 교차 출처 리소스는 `crossorigin` 속성이 필요합니다. 없으면 `no-cors` 요청이 되어 무결성을 검사할 수 없고 로드에 실패합니다. 해당 서버는 CORS를 허용해야 합니다(자세히는 62편).
- 적용 대상은 `script`와 `link`의 `rel`이 `stylesheet`, `preload`, `modulepreload`인 요소입니다.
- 해시는 `openssl dgst -sha384 -binary 파일 | openssl base64 -A`로 만듭니다. 파일이 바뀌면(CDN의 `latest` 경로 등) 로드가 깨지므로 버전을 고정한 URL에만 씁니다.

```http
Content-Security-Policy: script-src 'sha384-oqVuAfXRKap7...'
```

CSP에 같은 해시를 넣으면 `integrity`와 함께 해당 스크립트만 허용하는 정책을 만들 수 있습니다.

## Reporting API와 위반 보고

Reporting API는 CSP 위반, 폐기 예정 기능 사용, 브라우저 개입, COEP 위반, 충돌 같은 문제를 일관된 방식으로 받는 구조입니다. Baseline 2026입니다. 보고를 받는 방법은 두 가지입니다.

### 서버 엔드포인트

`Reporting-Endpoints` 헤더로 이름과 URL을 정의하고, 정책 쪽에서 이름을 지정합니다.

```http
Reporting-Endpoints: csp="https://example.com/reports"
Content-Security-Policy: default-src 'self'; report-to csp
```

브라우저가 `Content-Type: application/reports+json`으로 POST합니다. 레거시 `report-uri` 지시어와 `Report-To` 헤더는 폐기 대상이라 새 코드는 `report-to`와 `Reporting-Endpoints`를 씁니다. 보고 유형은 `csp-violation`, `deprecation`, `intervention`, `coep`, `crash`, `permissions-policy-violation`, `integrity-violation` 등입니다.

### ReportingObserver

페이지 안에서 보고를 직접 받는 JavaScript 인터페이스입니다.

```js
const ro = new ReportingObserver(
  (reports) => reports.forEach((r) => console.log(r.type)),
  { types: ['deprecation'], buffered: true },
)
ro.observe()
// ro.takeRecords(), ro.disconnect()
```

- `types`로 받을 유형을 거르고 `buffered: true`는 옵저버 생성 전에 만들어진 보고도 받습니다. `takeRecords()`는 쌓인 보고를 꺼내고 `disconnect()`는 중단합니다. 워커에서도 쓸 수 있습니다.

### securitypolicyviolation 이벤트

CSP 위반은 `document`(실제로는 `window`까지 버블링)에서 `securitypolicyviolation` 이벤트로도 받을 수 있습니다. Baseline 널리 지원합니다.

```js
addEventListener('securitypolicyviolation', (e) => {
  console.log(e.violatedDirective, e.blockedURI)
  // 'script-src-elem' 'inline'
})
```

이벤트 객체는 `blockedURI`, `violatedDirective`, `effectiveDirective`, `originalPolicy`, `disposition`(enforce 또는 report), `sourceFile`, `lineNumber`를 가집니다. 정책을 배포하기 전에 Report-Only와 보고 수집으로 어떤 기존 코드가 막히는지 확인합니다.

## CSRF

CSRF(Cross-Site Request Forgery)는 사용자가 로그인한 사이트에 공격자 페이지가 사용자의 브라우저로 요청을 보내게 해서, 자동으로 실리는 쿠키를 이용해 상태를 바꾸는 공격입니다. XSS와 달리 응답을 읽지 못하고 요청을 일으키는 데 그칩니다.

```html
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
</form>
<script>document.forms[0].submit()</script>
```

폼 제출은 CORS의 대상이 아닌 단순 요청이라 막히지 않고, 대상 사이트의 쿠키가 실립니다(자세히는 62편). 방어 수단은 다음과 같습니다.

| 수단 | 방법 |
|------|------|
| CSRF 토큰 | 서버가 예측 불가능한 토큰을 페이지에 심고, 상태를 바꾸는 요청에 그 토큰을 함께 보내게 해 서버가 검증. 공격자는 토큰을 알 수 없음 |
| `SameSite` 쿠키 | `Strict`는 교차 사이트 요청에 쿠키를 싣지 않음. `Lax`는 안전한(GET) 최상위 이동에만 실음. `None`은 보호 없음(`Secure` 필요) |
| Fetch Metadata 검사 | 서버가 `Sec-Fetch-Site`가 `same-origin`이나 `same-site`가 아니면 상태 변경 요청을 거부(자세히는 62편) |
| 단순 요청 회피 | `fetch`에 `Content-Type: application/json`이나 사용자 지정 헤더를 써서 프리플라이트를 거치게 함. 폼에는 쓸 수 없음 |

- 상태를 바꾸는 요청에 `GET`을 쓰면 안 됩니다. 이미지 태그나 링크만으로 교차 출처에서 보낼 수 있고 헤더 방어도 불가능합니다.
- `SameSite`는 같은 사이트 공격을 막지 못합니다. 서브도메인은 같은 사이트라서 모든 서브도메인을 신뢰해야 합니다(자세히는 40편).
- 가장 흔한 조합은 `SameSite` 쿠키에 토큰 또는 Fetch Metadata 검사를 더하는 것입니다. 광범위한 `Access-Control-Allow-Origin`과 `Access-Control-Allow-Credentials: true` 조합은 피합니다.

**흔한 실수:** CORS를 CSRF 방어로 착각하는 것입니다. CORS는 응답을 읽을 수 있는지를 정할 뿐, 단순 요청은 서버로 이미 전송됩니다.

## Shadow DOM은 보안 경계가 아님

Shadow DOM은 스타일과 DOM 구조의 캡슐화 기능이지 접근 통제 수단이 아닙니다(Shadow DOM 자체는 21편). `mode: 'closed'`도 마찬가지입니다.

```js
const root = host.attachShadow({ mode: 'closed' })
host.shadowRoot // null
root.querySelector('input') // 참조를 가진 코드는 접근 가능
```

- `closed`는 `host.shadowRoot`를 `null`로 만들 뿐입니다. `attachShadow()`가 돌려준 참조를 가진 코드는 그대로 접근하고, MDN은 브라우저 확장 등으로 우회할 수 있어 강한 보안 수단으로 여기지 말라고 명시합니다.
- 같은 문서에서 실행되는 모든 스크립트는 같은 권한입니다. 한 컴포넌트의 Shadow DOM 안에 비밀 값이나 인증 토큰을 두어도, 페이지의 다른 스크립트(서드파티, 주입된 XSS)가 DOM과 전역 객체를 통해 접근할 수 있습니다.
- Shadow DOM 안에도 XSS가 가능합니다. 정화되지 않은 문자열을 `shadowRoot.innerHTML`에 넣으면 `onerror` 같은 핸들러가 그대로 실행됩니다. CSP와 Trusted Types는 Shadow DOM 안쪽 싱크에도 적용됩니다.
- 스타일 캡슐화도 보안이 아닙니다. CSS 사용자 정의 속성과 `::part()`, 슬롯으로 바깥에서 영향을 줄 수 있습니다(자세히는 23편).
- 실제 격리가 필요하면 출처가 다른 iframe(필요하면 `sandbox`, 62편)이나 워커 같은 별도 실행 컨텍스트를 씁니다.

`closed`는 "내부를 직접 건드리지 말라"는 의도 표시로만 취급하고, 신뢰 경계를 그 위에 세우지 않습니다.

## 컴포넌트 입력값 신뢰 경계

컴포넌트가 받는 모든 입력은 신뢰 경계를 넘어 들어온 값이므로 사용하는 지점에서 검증합니다. 입력 경로는 다음과 같습니다.

| 입력 경로 | 위험 |
|-----------|------|
| 속성(attribute)과 프로퍼티 | 문자열이 렌더링에 쓰이면 HTML·URL 컨텍스트로 해석될 수 있음 |
| 슬롯으로 들어온 노드 | 호스트 페이지가 넣은 것이므로 컴포넌트가 내용을 통제할 수 없음 |
| 이벤트 `detail`, `postMessage` 데이터 | 외부가 보낸 임의 값(출처 검증은 62편) |
| URL, 저장소, `fetch` 응답 | 사용자와 서버 데이터가 섞여 있음 |

컴포넌트 설계 규칙은 다음과 같습니다.

- 사용자 문자열은 `textContent`로 넣습니다. 렌더링에 `innerHTML`을 쓰는 템플릿 함수가 속성값을 그대로 끼워 넣으면 컴포넌트 자체가 XSS 싱크가 됩니다.
- 속성으로 받은 URL은 스킴(`https:`, `http:`, 상대 경로)을 허용 목록으로 검사한 뒤 `href`·`src`에 넣습니다. `javascript:`는 거부합니다.
- HTML을 받는 API가 필요하면 이름에 `unsafe`나 `html`을 드러내고, 내부에서 정화하거나 `TrustedHTML`만 받게 합니다.
- 컴포넌트가 Trusted Types 환경에서 동작하도록 자기 정책을 `createPolicy`로 만들고(이름을 `trusted-types` 허용 목록에 등록하도록 문서화), 정책이 없는 환경에서도 동작하게 합니다.
- 속성 변경 콜백(`attributeChangedCallback`)에 들어오는 값은 항상 문자열이므로 타입 변환과 범위 검사를 거칩니다(자세히는 18편, 19편).
- 입력 검증을 호출하는 쪽에 맡기지 않습니다. 컴포넌트는 어떤 값이 와도 안전하게 렌더링해야 합니다.

```js
class UserCard extends HTMLElement {
  set name(v) {
    const b = this.shadowRoot.querySelector('b')
    b.textContent = String(v)
  }
}
```

## 핵심 정리

- XSS는 저장형·반사형·DOM 기반으로 나뉘고, `innerHTML`·`eval` 같은 싱크에 신뢰할 수 없는 문자열이 닿을 때 일어납니다. 텍스트는 `textContent`로 넣고, HTML이 필요하면 정화합니다.
- `setHTML()`(Sanitizer API)은 안전하지 않은 요소를 항상 제거하지만 미Baseline이라 기능 검사 후 라이브러리로 대체합니다.
- 엄격한 CSP는 nonce나 hash와 `strict-dynamic`, `object-src 'none'`, `base-uri 'none'`으로 구성하며 호스트 허용 목록과 `'unsafe-inline'`에 의존하지 않습니다.
- Trusted Types(Baseline 2026)는 `require-trusted-types-for 'script'`로 싱크에 정책이 만든 값만 허용하게 강제하고, `frame-ancestors`는 클릭재킹을 막고, SRI는 외부 리소스 변조를 막습니다.
- 위반은 `Reporting-Endpoints`와 `report-to`, `ReportingObserver`, `securitypolicyviolation` 이벤트로 수집합니다.
- CSRF는 토큰, `SameSite` 쿠키, `Sec-Fetch-Site` 검사로 막고 상태 변경에 `GET`을 쓰지 않습니다. Shadow DOM(`closed` 포함)은 보안 경계가 아니므로 컴포넌트는 모든 입력을 사용 지점에서 검증합니다.

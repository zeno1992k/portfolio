## Component Tree

컴포넌트 트리는 컴포넌트가 다른 컴포넌트를 포함하는 부모·자식 관계를 나타낸 구조입니다. Web Components에서는 별도의 자료구조가 아니라 DOM 트리 자체입니다(DOM 트리는 03편).

```html
<todo-app>
  <todo-list>
    <todo-item></todo-item>
    <todo-item></todo-item>
  </todo-list>
  <todo-footer></todo-footer>
</todo-app>
```

- 각 컴포넌트의 Shadow Root는 그 컴포넌트 내부의 하위 트리입니다. 바깥에서 쓴 자식(라이트 DOM)과 안쪽 구조(그림자 트리)가 따로 있습니다(자세히는 21편).
- 데이터가 이동하는 길은 트리의 간선입니다. 부모에서 자식으로, 자식에서 부모로 이동하고 형제끼리는 부모를 거칩니다(자세히는 25편).
- 역할로 나누면 루트(앱 수준 상태), 중간 노드(배치와 전달), 잎(표시와 입력)입니다. 잎에 가까울수록 상태를 모르는 쪽이 재사용에 유리합니다.
- 트리가 깊을수록 한 값이 지나가는 컴포넌트가 늘어납니다. 깊이는 상태 위치를 정할 때 비용이 됩니다.

## 단방향 데이터 흐름

단방향 데이터 흐름은 상태가 한 방향(상태 → 화면)으로만 흐르고, 화면에서 상태를 바꾸려면 이벤트라는 별도의 경로로 요청하는 규칙입니다.

```js
// 상태 → 화면
render(state)
// 화면 → 이벤트 → 상태 → 화면
view.addEventListener('add', (e) => {
  state = { ...state, items: [...state.items, e.detail] }
  render(state)
})
```

- 변경은 한 곳(상태 소유자)에서만 일어납니다. 값이 이상하면 그 소유자에서만 찾으면 됩니다.
- 양방향 바인딩(화면이 상태를 직접 쓰는 구조)은 코드가 짧지만 누가 값을 바꿨는지 추적하기 어렵고, 갱신이 서로를 다시 부르는 순환이 생기기 쉽습니다.
- 자식은 받은 객체나 배열을 직접 고치지 않습니다. 그 객체는 부모의 상태이므로 고치면 부모가 변경을 모르고 화면이 어긋납니다. 변경은 이벤트로 요청합니다.

## Props Down / Events Up

Props Down은 부모가 자식에게 데이터를 프로퍼티·속성·슬롯으로 내려 주는 것이고, Events Up은 자식이 일어난 일을 이벤트로 올려 보내는 것입니다.

| 방향 | 수단 | 담을 수 있는 것 |
|------|------|------------------|
| 아래로 | 프로퍼티 | 객체, 배열, 함수 등 모든 값 |
| 아래로 | 속성 | 문자열(스타일·선택자에 쓰는 단순 값) |
| 아래로 | 슬롯 | 마크업 |
| 위로 | CustomEvent | `detail`에 임의 값 |

```js
// 부모: 내려 주고, 올라온 이벤트를 듣는다
list.items = state.items
list.addEventListener('item-toggle', (e) => {
  toggle(e.detail.id)
})
```

```js
// 자식: 일어난 일을 알린다
this.dispatchEvent(new CustomEvent('item-toggle', {
  detail: { id: this.item.id },
  bubbles: true,
  composed: true,
}))
```

- `CustomEvent`의 `bubbles`와 `composed` 기본값은 둘 다 `false`입니다. 부모가 아닌 조상이 듣거나 Shadow 경계를 넘으려면 직접 켭니다(자세히는 25편).
- 이벤트 이름은 일어난 사실을 나타냅니다(`item-toggle`, `save-requested`). 부모가 해야 할 일을 이름에 넣지 않으면 자식이 부모를 몰라도 됩니다.
- `detail`에는 필요한 최소한(식별자, 새 값)만 담습니다. 상태 객체 전체나 DOM 노드를 담으면 결합이 강해집니다.
- 자식이 `this.parentElement.method()`로 부모를 직접 부르면 방향 규칙이 깨지고 그 자식은 그 부모 아래에서만 동작합니다.

**흔한 실수:** 자식에서 `bubbles`와 `composed`를 켜지 않고 부모에서 이벤트를 듣는 것입니다. 이벤트가 자식 요소에서 멈춥니다.

## Local State vs Shared State

Local State는 한 컴포넌트(와 그 자식)만 쓰는 상태이고, Shared State는 여러 컴포넌트가 함께 읽거나 쓰는 상태입니다. 구분 기준은 "이 값을 읽는 컴포넌트가 몇 개이고 서로 어떤 관계인가"입니다.

| 구분 | 예 | 위치 |
|------|----|------|
| Local | 드롭다운 열림, 호버, 입력 중인 초안 | 그 컴포넌트 안(자세히는 20편) |
| Shared | 선택된 항목, 검색어, 장바구니 | 사용하는 컴포넌트들의 공통 조상 |
| App-wide | 로그인 사용자, 테마, 언어 | 앱 수준(컨텍스트나 스토어) |

- 처음에는 로컬로 시작합니다. 다른 컴포넌트가 읽어야 하는 일이 생길 때 위로 올립니다.
- 같은 상태를 두 컴포넌트가 각각 로컬로 들고 있으면 둘이 어긋납니다.
- 로컬 상태는 외부에서 알 필요가 없으므로 `#field`로 숨깁니다(자세히는 20편).

## 상태 끌어올리기

상태 끌어올리기는 형제 컴포넌트가 같은 상태를 필요로 할 때 상태를 가장 가까운 공통 조상으로 옮기는 것입니다. 조상이 소유하고 자식에게 내려 주고, 자식은 변경을 이벤트로 요청합니다.

```html
<search-page>          <!-- query를 소유 -->
  <filter-bar></filter-bar>      <!-- query 입력 -->
  <result-list></result-list>    <!-- query로 필터 -->
</search-page>
```

```js
class SearchPage extends HTMLElement {
  #query = ''
  connectedCallback() {
    this.bar.addEventListener('query-change', (e) => {
      this.#query = e.detail
      this.list.query = this.#query
    })
  }
}
```

- 순서: 상태를 쓰는 컴포넌트를 모두 찾고, 그 공통 조상을 찾고, 거기서 소유하고, 변경 이벤트를 연결합니다.
- 올릴수록 상태가 지나가는 중간 컴포넌트가 늘어나 값을 그대로 넘기기만 하는 코드(prop drilling)가 생깁니다.
- 중간 전달이 부담이면 컨텍스트로 건너뜁니다. Lit의 컨텍스트는 소비자가 `context-request` 이벤트(버블링되고 `composed`)를 보내면 조상의 제공자가 응답하는 방식이며, W3C Web Components 커뮤니티 그룹의 Context 프로토콜을 따르므로 Lit이 아닌 구현과도 연동됩니다(자세히는 25편).

## 상태 소유권 결정

소유자는 그 상태를 바꿀 수 있는 유일한 컴포넌트입니다. 읽는 쪽은 많아도 쓰는 쪽은 소유자 하나이고, 다른 컴포넌트는 변경을 요청만 합니다. 소유자는 다음 질문으로 정합니다.

| 질문 | 답이 이럴 때 | 소유 위치 |
|------|--------------|-----------|
| 누가 읽는가 | 한 컴포넌트뿐 | 그 컴포넌트 |
| 누가 읽는가 | 형제·사촌 여럿 | 가장 가까운 공통 조상 |
| 화면을 새로고침하거나 공유해도 유지돼야 하는가 | 예(탭, 필터, 정렬) | URL(자세히는 34편) |
| 다음 방문에도 유지돼야 하는가 | 예(설정) | 저장소(자세히는 40편) |
| 서버에서 온 데이터인가 | 예 | 데이터 계층(자세히는 37편) |
| 앱 전체가 읽는가 | 예(사용자, 테마) | 앱 수준 |

- 같은 상태의 소유자가 둘이면 어긋납니다. 하나를 고르고 나머지는 읽기만 합니다.
- 소유 위치가 정해지면 쓰기 경로도 정해집니다. 쓰기 경로는 이벤트나 메서드 한 가지로 통일합니다.

**흔한 실수:** 값을 쓰는 컴포넌트와 읽는 컴포넌트를 구분하지 않고 "편하니까" 앱 수준에 올리는 것입니다(뒤의 전역 상태 절).

## Source of Truth

Source of Truth(진실의 원천)는 어떤 데이터가 "정답"으로 저장된 단 하나의 위치입니다. 다른 곳의 값은 그 원천에서 계산한 것이거나 의도적으로 만든 스냅샷입니다.

```js
// ❌ 복사본이 생겨 원본과 갈라진다
connectedCallback() { this.#name = this.user.name }
// ✅ 원본을 읽는다
render() { this.$name.textContent = this.user.name }
```

- 프로퍼티로 받은 값을 로컬 상태에 복사하면 부모가 값을 바꿔도 복사본은 낡은 채 남습니다.
- 의도적인 복사는 "편집 중 초안"입니다. 원본은 두고, 초안은 취소하면 버리고 저장하면 이벤트로 올립니다. 복사임을 코드와 이름(`draft`)에 드러냅니다.
- DOM도 원천이 될 수 있습니다. 비제어 입력은 DOM이 값을 가집니다(뒤의 폼 절). 이때 상태에도 같은 값을 두지 않습니다.
- 속성과 프로퍼티가 같은 값을 나타낼 때는 한쪽을 원천으로 정하고 다른 쪽은 반영만 합니다(자세히는 19편).

## Derived Data

Derived Data는 원천 상태에서 계산할 수 있는 값입니다. 저장하지 않고 필요할 때 계산합니다. 저장하면 원천이 바뀔 때 함께 갱신해야 하고, 빠뜨리면 어긋납니다.

| 저장하지 말 것 | 원천 | 파생 |
|----------------|------|------|
| 완료된 개수 | 항목 배열 | 항목에서 완료인 것의 수 |
| 비어 있는지 | 항목 배열 | 길이가 0인지 |
| 선택된 항목 객체 | 선택된 id와 항목 목록 | 목록에서 id로 찾은 항목 |
| 합계 | 단가와 수량 | 곱의 합 |

```js
get doneCount() {
  return this.items.filter((i) => i.done).length
}
render() {
  this.$count.textContent = this.doneCount
}
```

- 선택 상태는 객체가 아니라 id를 저장합니다. 객체를 저장하면 목록이 갱신될 때 선택 객체가 낡은 복사본이 됩니다.
- 계산이 비싸면 입력이 바뀔 때만 다시 계산하도록 캐시합니다. 반응형 구조에서는 computed가 이 역할을 합니다(자세히는 31편).
- 파생값을 `render` 안에서 계산하고 상태에 쓰지 않습니다. render가 상태를 바꾸면 갱신이 순환합니다.

## 컴포넌트 경계 결정

컴포넌트 경계는 어디까지를 하나의 컴포넌트로 묶고 어디서 나눌지 정하는 일입니다. 경계는 곧 공개 API(자세히는 19편), Shadow 경계(자세히는 21편), 스타일 경계(자세히는 23편)가 됩니다.

| 나눌 신호 | 나누지 않을 신호 |
|-----------|------------------|
| 두 곳 이상에서 같은 구조를 씀 | 한 곳에서만 쓰고 앞으로도 그럴 것 |
| 독립된 상태나 갱신 단위가 있음 | 부모의 상태를 모두 필요로 해서 속성이 줄줄이 늘어남 |
| 한 컴포넌트를 설명하는 문장에 "그리고"가 여러 번 들어감 | 마크업이 길다는 이유만 있음 |
| 독립적으로 시험하거나 접근성 단위(탭, 대화상자)가 됨 | 나누면 부모와 서로의 내부를 알아야 함 |

- 경계가 너무 잘면 컴포넌트마다 속성 목록이 길어지고 데이터가 여러 단계를 통과합니다.
- 경계가 너무 크면 한 상태 변경이 불필요하게 큰 영역을 다시 그리게 하고, 재사용이 어려워집니다.
- 좋은 경계는 상태 소유권과 맞물립니다. 어떤 상태를 소유하는 단위가 한 컴포넌트가 되면 갱신 범위와 책임이 같아집니다(합성 방식은 29편).
- 경계 안쪽의 상세는 숨기고 바깥에는 속성·프로퍼티·이벤트·슬롯만 열어서 내부 구조를 바꿔도 사용하는 쪽이 영향받지 않게 합니다.

## 과도한 전역 상태 피하기

전역 상태는 모든 컴포넌트가 읽고 쓸 수 있는 앱 수준 상태입니다. 편하지만 의존 관계가 보이지 않고, 쓰는 곳이 늘어날수록 바꾸기 어렵습니다.

| 문제 | 설명 |
|------|------|
| 숨은 결합 | 속성·이벤트에 나타나지 않아 컴포넌트가 무엇에 의존하는지 코드만으로 알 수 없음 |
| 쓰기 경로 난립 | 누구나 고칠 수 있어 변경 원인 추적이 어려움 |
| 재사용 곤란 | 컴포넌트가 그 전역 객체를 전제함 |
| 시험 곤란 | 시험마다 전역을 초기화해야 함 |
| 갱신 범위 확대 | 한 값이 바뀌면 구독자 전체가 영향받음 |

- 다음 순서로 위쪽 방법을 먼저 씁니다: 로컬 상태 → 가까운 조상으로 끌어올리기 → 컨텍스트(서브트리 범위) → 앱 수준 스토어.
- 전역이 알맞은 것은 정말로 앱 전체가 읽는 값(로그인 사용자, 테마, 언어)입니다. 화면 한 구석에서 쓰는 값은 전역이 아닙니다.
- 전역으로 둘 때도 읽기는 열고 쓰기는 한 경로(메서드나 이벤트)로 제한합니다.
- 컨텍스트는 서브트리에만 값을 제공하므로 같은 컴포넌트를 두 곳에서 다른 값으로 쓸 수 있습니다.

## 폼 입력의 제어·비제어 방식

제어 입력은 상태가 값의 원천이고 입력창은 상태를 보여 주는 표시 장치이며, 비제어 입력은 DOM이 값을 갖고 필요할 때(제출 시) 읽어 오는 방식입니다.

```js
// 제어: 상태 ↔ 입력
input.value = state.name
input.addEventListener('input', () => {
  state = { ...state, name: input.value }
})
```

```js
// 비제어: 제출 때 DOM에서 읽음
form.addEventListener('submit', (e) => {
  e.preventDefault()
  save(Object.fromEntries(new FormData(form)))
})
```

| 구분 | 제어 | 비제어 |
|------|------|--------|
| 값의 원천 | 컴포넌트 상태 | DOM(입력 요소) |
| 매 입력마다 반응 | 가능(검증, 서식, 다른 필드 연동) | 어려움 |
| 구현량 | 많음 | 적음 |
| 맞는 경우 | 입력 중 화면이 값에 의존함 | 제출만 필요한 단순 폼 |

- 입력 요소의 현재 값은 `value` 프로퍼티이고, 처음 값은 `value` 속성(`defaultValue` 프로퍼티)입니다. 체크박스는 `checked`와 `defaultChecked`가 그렇습니다.
- 사용자가 입력하거나 스크립트가 `value` 프로퍼티를 바꾸면 입력 요소의 dirty 플래그가 켜지고, 그 뒤에는 `value` 속성을 바꿔도 현재 값이 바뀌지 않습니다. 제어 입력은 속성이 아니라 프로퍼티(`input.value`)를 써야 합니다.
- 폼 `reset`은 dirty 플래그를 끄고 값을 `value` 속성값으로 되돌립니다. 비제어 입력의 초기값은 `defaultValue`로 정하면 reset과 맞습니다(자세히는 11편).
- 제어 입력은 `render`에서 `input.value !== state.name`일 때만 값을 쓰면 불필요한 대입을 피합니다.
- 한 필드 안에서 제어와 비제어를 섞지 않습니다. 상태와 DOM이 모두 원천이 되어 어긋납니다. 폼 전체에서는 혼용해도 됩니다. 값이 필요 없는 필드는 비제어로 두고 제출 때 `FormData`로 합칩니다.
- 입력 요소가 사용자 정의 요소이면 폼 연동은 `ElementInternals`로 합니다(자세히는 26편).

## 상태 정규화

상태 정규화는 중첩된 데이터를 종류별 테이블로 펼치고, 항목끼리는 중첩하지 않고 id로 참조하게 만드는 것입니다. 같은 데이터가 여러 곳에 복사되는 문제를 없애서 원천을 하나로 만듭니다.

```js
// ❌ 중첩: 같은 사용자가 글마다 복사됨
{ posts: [{ id: 1, author: { id: 7, name: 'Kim' } }] }
// ✅ 정규화: 사용자는 한 곳, 글은 id로 참조
{
  users: { 7: { id: 7, name: 'Kim' } },
  posts: { 1: { id: 1, authorId: 7 } },
  postIds: [1],
}
```

- 각 종류를 id를 키로 하는 객체(또는 `Map`)에 담고, 순서는 id 배열로 따로 둡니다. 객체의 정수 형태 키는 만든 순서가 아니라 오름차순으로 정렬되므로 순서를 객체에 기대지 않습니다.
- 이점: 사용자 이름을 바꿀 때 한 곳만 고치면 모든 글에 반영되고, id로 한 번에 찾을 수 있으며, 깊게 중첩된 객체를 복사해서 갱신할 필요가 없습니다. 중첩 갱신은 바꿀 항목의 상위 객체까지 모두 복사하게 만들어 관련 없는 UI의 재렌더링을 부른다고 Redux 문서가 설명하는데, 정규화하면 이 복사가 줄어듭니다.
- 비용: 화면에 필요한 모양은 읽을 때 조합해야 합니다(`users[post.authorId]`). 이 조합이 파생 데이터입니다.
- 한 번 가져오고 끝나는 작은 데이터나 읽기 전용 데이터는 정규화하지 않아도 됩니다. 같은 항목이 여러 곳에서 보이고 수정될 때 효과가 큽니다.
- 선택 상태를 id로 저장하는 방식(파생 데이터 절)과 키가 있는 목록 렌더링(자세히는 30편)이 이 구조와 잘 맞습니다.

## 핵심 정리

- 컴포넌트 트리는 DOM 트리이며, 데이터는 부모에서 자식으로 프로퍼티·속성·슬롯으로 내려가고 자식에서 부모로는 CustomEvent로 올라갑니다.
- `CustomEvent`의 `bubbles`와 `composed` 기본값은 `false`라서 조상이 듣거나 Shadow 경계를 넘으려면 직접 켭니다.
- 상태는 로컬로 시작하고, 형제가 함께 필요하면 가장 가까운 공통 조상으로 끌어올리며, 소유자는 유일한 쓰기 주체입니다.
- 모든 데이터에는 원천이 하나이고, 계산할 수 있는 값은 저장하지 않고 파생하며, 선택은 객체가 아니라 id로 저장합니다.
- 전역 상태는 숨은 결합을 만드므로 로컬, 끌어올리기, 컨텍스트, 스토어 순서로 필요한 만큼만 올립니다.
- 제어 입력은 상태가 원천이고 `value` 프로퍼티를 쓰며, 비제어 입력은 DOM이 원천이고 `FormData`로 읽습니다. 중첩 데이터는 id로 참조하게 정규화합니다.

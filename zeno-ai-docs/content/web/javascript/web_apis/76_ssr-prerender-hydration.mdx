## SSR과 Web Components

SSR(Server-Side Rendering)은 서버가 요청을 받을 때 화면의 HTML을 만들어 응답하는 방식입니다. 브라우저는 JavaScript 실행 전에 내용을 그립니다. 렌더링 방식은 HTML이 만들어지는 시점으로 구분합니다.

| 방식 | HTML이 만들어지는 때 | 특징 |
|------|----------------------|------|
| CSR | 브라우저에서 JavaScript 실행 후 | 첫 화면이 JavaScript에 의존 |
| SSR | 서버가 요청을 받을 때 | 요청마다 최신 데이터 반영, 서버 비용 |
| Prerender(정적 생성) | 빌드 때 한 번 | 정적 파일로 배포, 데이터가 빌드 시점에 고정 |

SSR의 효과는 첫 콘텐츠가 빨리 보이는 것(LCP 개선, 자세히는 65편), JavaScript 없이도 내용이 있는 것, 크롤러가 내용을 읽을 수 있는 것입니다.

Web Components에는 SSR을 막는 두 가지 장벽이 있었습니다.

- 서버(Node.js 같은 환경)에는 `document`, `HTMLElement`, `customElements`가 없습니다. 컴포넌트 클래스를 서버에서 그대로 실행할 수 없습니다. 서버는 클래스 대신 최종 HTML 문자열을 만들어야 합니다.
- shadow tree의 내용은 HTML 마크업으로 표현할 방법이 없었습니다. 이 문제는 Declarative Shadow DOM(Baseline 2024)이 해결했습니다.

```html
<x-card>
  <template shadowrootmode="open">
    <style>h2 { margin: 0 }</style>
    <h2><slot name="title"></slot></h2>
  </template>
  <span slot="title">제목</span>
</x-card>
```

- 서버는 컴포넌트를 실행하지 않고 호스트 요소와 그 shadow tree의 마크업을 문자열로 출력합니다. 이 문자열을 만드는 방법은 직접 쓰는 템플릿 함수나 렌더러 라이브러리입니다.
- Lit의 SSR(`@lit-labs/ssr`)은 비브라우저 환경에서 Lit 템플릿과 컴포넌트를 정적 HTML로 렌더링하고 선언형 shadow DOM을 씁니다. Labs 단계의 실험적 기능이며 shadow DOM 컴포넌트만 지원하고 비동기 작업을 지원하지 않습니다.
- shadow DOM을 쓰지 않는 컴포넌트(Light DOM 컴포넌트)는 일반 HTML이라서 DSD 없이 SSR됩니다. 대신 스타일 캡슐화와 슬롯을 잃습니다(자세히는 21편).

## Declarative Shadow DOM

Declarative Shadow DOM(DSD)은 HTML만으로 shadow root를 만드는 문법입니다. `shadowrootmode` 속성이 있는 `template`을 HTML 파서가 부모 요소의 shadow root로 바꿉니다. Baseline 2024이며 Chrome 111, Firefox 123, Safari 16.4부터 지원합니다. 널리 지원됩니다.

`template`에 쓰는 속성은 `attachShadow()`의 옵션에 대응합니다.

| 속성 | 대응 옵션 | 지원 |
|------|-----------|------|
| `shadowrootmode` (`open` 또는 `closed`) | `mode` | Baseline 2024 |
| `shadowrootdelegatesfocus` | `delegatesFocus` | Baseline 2024 |
| `shadowrootclonable` | `clonable` | Baseline 2024 (Chrome 124, Firefox 125, Safari 17.5) |
| `shadowrootserializable` | `serializable` | 속성 지원은 Chrome 125, Safari 18에서 확인되고 Firefox는 확인하지 못함 |

- `shadowrootmode`가 있어야 DSD로 처리됩니다. 값은 `open`이나 `closed`이고, MDN은 대부분의 경우 `open`을 권장합니다.
- `shadowrootdelegatesfocus`가 있으면 shadow 안의 포커스 불가 요소를 눌렀을 때 포커스가 첫 포커스 가능 요소로 위임됩니다. 기본은 꺼짐입니다.
- `shadowrootclonable`이 있으면 `cloneNode()`와 `importNode()`로 복제한 호스트가 shadow root도 갖습니다.
- `shadowrootserializable`이 있으면 `getHTML({ serializableShadowRoots: true })`로 이 root가 직렬화됩니다. 기본은 꺼짐입니다(자세히는 21편).

파서는 `shadowrootmode`가 있는 `template`의 시작 태그를 만나는 즉시 shadow root를 만듭니다. HTML 표준의 규칙은 다음과 같습니다.

- 문서를 만드는 파서에서만 동작합니다. 파서에 "선언형 shadow root 허용" 플래그가 꺼져 있으면 일반 `template` 요소가 됩니다.
- `template`이 `html` 요소 바로 아래이면 일반 `template`입니다. 호스트가 될 부모 요소가 있어야 합니다.
- 부모가 이미 shadow host이면(첫 번째 DSD로 root가 만들어진 뒤) 두 번째 `template`은 root 안의 일반 `template`으로 남습니다.
- 부모 요소에 shadow root를 붙일 수 없어서(예: `input`) `attachShadow()`에 해당하는 동작이 예외를 던지면 일반 `template`이 됩니다. 콘솔에 오류가 보고될 수 있습니다.
- 성공하면 `template` 요소는 DOM에 남지 않고, 그 내용이 shadow root의 자식으로 파싱됩니다.
- 한 번 일반 `template`으로 만들어진 요소는 나중에 `shadowRootMode` 프로퍼티를 바꿔도 shadow root가 되지 않습니다.

브라우저의 DSD 지원은 다음처럼 확인합니다.

```js
const ok = HTMLTemplateElement.prototype
  .hasOwnProperty('shadowRootMode')
```

지원하지 않는 브라우저를 위한 폴리필은 문서 로드 후 `template[shadowrootmode]`를 찾아 부모에 root를 붙이고 내용을 옮기는 방식입니다. 파싱 시점이 아니라 이후에 변환되므로 처음 화면에는 DSD의 이점이 없고, 중첩된 구조는 재귀로 처리합니다(web.dev).

```js
const sel = 'template[shadowrootmode]'
for (const t of document.querySelectorAll(sel)) {
  const mode = t.getAttribute('shadowrootmode')
  const root = t.parentNode.attachShadow({ mode })
  root.append(t.content)
  t.remove()
}
```

## 서버에서 Shadow DOM 출력

서버가 Shadow DOM 컴포넌트를 출력한다는 것은, 호스트 요소 안에 shadow tree를 담은 `template shadowrootmode`를 쓰고 그 뒤에 슬롯으로 들어갈 자식을 쓰는 것입니다.

```js
const esc = (s) => String(s).replace(/[&<>"']/g,
  (c) => `&#${c.charCodeAt(0)};`)

export function renderXCard({ title, body }) {
  return `<x-card title="${esc(title)}">
  <template shadowrootmode="open">
    <link rel="stylesheet" href="/css/x-card.css">
    <h2 part="title">${esc(title)}</h2><slot></slot>
  </template>${esc(body)}</x-card>`
}
```

- 출력 순서는 호스트 시작 태그, `template`, 슬롯 자식, 호스트 종료 태그입니다. `template`을 호스트의 첫 자식으로 두면 shadow root가 먼저 만들어져서 이어지는 자식이 곧바로 슬롯에 배정됩니다.
- 사용자 입력은 속성 값과 텍스트 모두 HTML 이스케이프합니다. 이스케이프하지 않으면 서버가 XSS를 만듭니다(자세히는 63편).
- shadow 안의 스타일은 `style` 요소나 `link`로 씁니다. 마크업만으로는 `adoptedStyleSheets`를 지정할 수 없습니다(web.dev). 같은 컴포넌트가 페이지에 수십 개 있으면 `style`이 그만큼 반복되어 HTML이 커집니다. 외부 `link`는 캐시되고, 같은 스타일시트가 여러 DSD에 있으면 한 번만 로드·파싱된다고 web.dev가 설명합니다.
- 서버는 속성과 자식으로만 결과가 정해지는 순수 함수(`props`로 HTML 문자열)로 출력을 만드는 것이 가장 단순합니다. 같은 컴포넌트의 클라이언트 클래스와 서버 출력 함수는 같은 마크업을 내야 합니다.
- 브라우저나 헤드리스 브라우저 같은 DOM이 있는 환경에서는 `getHTML({ serializableShadowRoots: true })`로 shadow root가 포함된 HTML을 얻을 수 있습니다. root를 만들 때 `serializable: true`(또는 `shadowrootserializable`)여야 합니다(자세히는 21편).
- Lit SSR 같은 렌더러를 쓰면 템플릿 함수를 직접 쓰지 않고 컴포넌트 정의에서 같은 출력을 얻습니다. 지원 범위(shadow DOM만, 비동기 미지원)를 확인합니다.

## innerHTML로는 선언형 shadow root가 생성되지 않는 규칙

`innerHTML`로 문자열을 넣으면 DSD가 처리되지 않고 일반 `template` 요소가 만들어집니다. 문서를 파싱할 때와 달리 조각 파싱에서는 선언형 shadow root 처리가 꺼져 있습니다.

```js
host.innerHTML = html // html에 DSD가 들어 있음
host.querySelector('x-card').shadowRoot // null
// template 요소가 자식으로 남아 있음
```

- `setHTMLUnsafe()`와 `Document.parseHTMLUnsafe()`는 DSD를 shadow root로 처리합니다. `setHTMLUnsafe`와 `parseHTMLUnsafe`는 Baseline 2025입니다(2025년 9월부터 핵심 브라우저 전체 지원).

```js
host.setHTMLUnsafe(html) // DSD가 shadow root로 처리됨
```

- 서버에서 받은 HTML 조각을 `fetch`로 받아 화면 일부를 바꾸는 방식(부분 갱신)에서 이 규칙이 문제가 됩니다. 조각에 DSD가 있으면 `innerHTML` 대신 `setHTMLUnsafe`를 써야 shadow root가 생깁니다.
- 이름의 Unsafe는 XSS가 되는 HTML을 제거하지 않는다는 뜻입니다. 기본 상태에서 입력을 정제하지 않습니다. 신뢰할 수 없는 문자열이면 Trusted Types의 `TrustedHTML`을 넘기거나 sanitizer를 지정합니다(자세히는 63편).
- 한 호스트에 DSD가 여러 개 있으면 `setHTMLUnsafe`에서도 첫 번째만 root가 되고 나머지는 일반 `template`입니다.
- 일반 `template`으로 이미 들어간 뒤에 shadow root로 바꾸려면 `attachShadow()`를 부르고 `template.content`를 옮깁니다(위 폴리필과 같은 방식).

## 선언형 root가 있을 때 attachShadow()의 동작

DSD로 이미 shadow root가 있는 요소에서 `attachShadow()`를 호출하면, mode가 같을 때 예외 없이 그 root를 반환하되 기존 내용을 비웁니다.

| 상황 | 결과 |
|------|------|
| DSD root가 있고 mode가 같음 | 기존 root를 비우고 반환 |
| DSD root가 있고 mode가 다름 | `NotSupportedError` |
| DSD가 아닌 방법으로 만든 root가 있음 | `NotSupportedError` |

- 서버 렌더링 때문에 이미 root가 있는 상태에서 클라이언트 코드가 다시 root를 붙이려 하는 경우를 허용하려는 설계입니다.
- 문제는 내용이 비워진다는 점입니다. 생성자가 항상 `attachShadow()`를 호출하면 서버가 그린 shadow 내용이 없어지고 화면이 깜빡이거나 서버 렌더링의 의미가 사라집니다.
- 이미 있는 root를 먼저 확인합니다. `this.shadowRoot`는 `open`일 때만 값을 주므로 `closed`도 처리하려면 `ElementInternals.shadowRoot`를 씁니다. `ElementInternals.shadowRoot`는 선언형으로 만든 root에 대해서도 호스트가 shadow host이면 root를 돌려줍니다.

```js
class XCard extends HTMLElement {
  #internals = this.attachInternals()
  constructor() {
    super()
    this.root = this.#internals.shadowRoot
      ?? this.attachShadow({ mode: 'open' })
  }
}
```

- 서버가 만든 root가 없는 경우(JavaScript로 만든 요소, DSD 미지원 브라우저)에는 `attachShadow()`가 새 root를 만듭니다. 이 두 경로를 모두 지원하는 것이 SSR 가능한 컴포넌트의 조건입니다.
- 이전에 DSD가 비어 있지 않은 root를 만들었다면 컴포넌트가 처음 렌더링할 때 root 안에 서버가 그린 내용이 있다는 것을 알아야 합니다. 있으면 다시 그리지 않고 재사용합니다(아래 "Hydration 개념").

## Custom Element Upgrade

업그레이드(upgrade)는 이미 문서에 있던 요소를 정의가 등록되는 시점에 커스텀 요소로 바꾸는 과정입니다. 서버가 보낸 HTML의 `x-card`는 `customElements.define('x-card', ...)`이 실행되기 전까지 정의되지 않은 요소(undefined)이고, 정의가 실행되면 문서 순서대로 업그레이드됩니다(자세히는 17편, 18편).

- 업그레이드에서는 기존 요소 인스턴스에 대해 생성자가 실행되고, 이어서 이미 있던 속성마다 `attributeChangedCallback`, 연결되어 있으면 `connectedCallback`이 호출됩니다. 속성과 자식은 이미 존재합니다.
- 서버 렌더링된 요소는 shadow root가 이미 있는 채로 업그레이드됩니다. 생성자와 `connectedCallback`이 root가 있는 경우와 없는 경우를 모두 처리해야 합니다(위 절).
- 정의 전에는 요소가 `:not(:defined)`로 선택됩니다. 이 상태를 스타일로 다루는 방법은 아래 "FOUC / Layout Shift 방지"입니다.
- `customElements.whenDefined(name)`은 정의가 끝나면 이행되는 약속입니다. 정의 전에 요소의 프로퍼티를 읽거나 쓰려면 이를 기다립니다. 업그레이드 전에 대입된 프로퍼티는 인스턴스 자신의 프로퍼티로 남아서 접근자를 가립니다(자세히는 19편).
- `customElements.upgrade(root)`는 `root` 아래의 요소 가운데 정의가 있는데 아직 업그레이드되지 않은 것을 업그레이드합니다. 문서에 연결되지 않은 트리(템플릿을 복제한 조각)에서도 동작합니다.
- 한 `define()` 호출은 문서에 있는 해당 태그의 요소를 모두 업그레이드하므로, 정의 순서가 곧 초기화 순서입니다. 자식을 먼저 정의하고 부모를 나중에 정의합니다(자세히는 33편).

## Hydration 개념

Hydration은 서버가 만든 HTML에 클라이언트의 JavaScript가 이벤트와 상태를 연결해 상호작용이 가능하게 만드는 과정입니다. HTML은 이미 화면에 그려져 있으므로 DOM을 새로 만들지 않고 기존 노드를 재사용하는 것이 핵심입니다.

- 서버가 보낸 HTML은 보이기만 하고 동작하지 않습니다. 버튼을 눌러도 이벤트 리스너가 없습니다.
- Web Components에서는 업그레이드가 그 역할의 대부분을 합니다. 요소 인스턴스가 기존 DOM 노드에 붙기 때문에 노드를 만들고 지우는 일이 없고, 별도의 가상 DOM 대조도 필요하지 않습니다.
- 컴포넌트가 Hydration에서 하는 일은 다음 세 가지입니다.

| 할 일 | 방법 |
|-------|------|
| 상태 복구 | 속성, 자식, 서버가 직렬화한 JSON에서 초기 상태 읽기 |
| 이벤트 연결 | 기존 shadow root의 요소에 리스너 등록(이벤트 위임이면 root에 하나만) |
| 필요한 갱신만 | 서버 출력과 같은 부분은 다시 그리지 않음 |

```js
connectedCallback() {
  if (this.root.childElementCount === 0) this.#render()
  this.root.addEventListener('click', this.#onClick)
}
```

- 서버 렌더링 결과를 지우고 `innerHTML`로 다시 그리면 깜빡임이 생기고 입력 중이던 값, 포커스, 스크롤 위치를 잃습니다. 서버 렌더링의 이점이 사라집니다.
- 서버와 클라이언트의 결과가 다르면 불일치가 생깁니다. 서버가 렌더링할 때와 클라이언트가 렌더링할 때 값이 달라지는 입력(현재 시각, 난수, 로케일, 화면 크기)은 속성으로 서버가 정한 값을 받아 같은 결과를 내게 합니다.
- Lit 같은 라이브러리의 Hydration은 `@lit-labs/ssr-client` 패키지가 담당합니다. 라이브러리를 쓰면 기존 shadow 내용을 재사용하는 처리를 라이브러리가 대신하지만 Labs 단계입니다.
- 사용자가 업그레이드 전에 이미 입력한 값(텍스트 입력 등)이 있을 수 있습니다. Hydration에서 값을 덮어쓰지 않도록 현재 값을 읽어 이어받습니다.

## 부분 Hydration

부분 Hydration(partial hydration)은 페이지의 모든 컴포넌트가 아니라 상호작용이 필요한 일부만 JavaScript를 실행해 Hydration하는 방식입니다. 나머지는 서버가 만든 정적 HTML로 남습니다.

- Web Components에서는 정의를 등록하지 않은 컴포넌트가 곧 Hydration하지 않은 컴포넌트입니다. DSD로 모양은 이미 렌더링되어 있고 정의가 실행될 때 업그레이드됩니다. 정의를 실행하는 시점을 컴포넌트마다 다르게 정하면 그것이 곧 부분 Hydration입니다.
- 필요 없는 컴포넌트의 JavaScript는 내려받지도 실행하지도 않으므로 전송량과 메인 스레드 작업이 줄어듭니다(자세히는 66편).
- 정의 파일을 동적 `import()`로 불러오면 불러온 모듈이 실행되면서 `define()`을 호출하고 그 순간 업그레이드됩니다.

```js
const io = new IntersectionObserver((entries) => {
  for (const e of entries) {
    if (!e.isIntersecting) continue
    io.unobserve(e.target)
    import('./x-chart.js') // define 실행 시 업그레이드
  }
})
for (const el of document.querySelectorAll('x-chart')) {
  io.observe(el)
}
```

- 정의 전의 요소는 입력에 반응하지 않습니다. 보이는 시점에 로드하는 컴포넌트는 로드 중에 눌릴 수 있는 위험이 있어서 이벤트를 다시 처리하는 방법(정의 후 이벤트를 다시 전달)이나 눌리지 않는 영역에만 적용하는 방법이 필요합니다.
- 컴포넌트 사이에 의존이 있으면 한쪽만 Hydration하면 깨집니다. 예를 들어 부모가 자식의 메서드를 부르는 구조면 자식을 먼저 정의해야 합니다(자세히는 33편).

## Islands 아키텍처

Islands 아키텍처는 페이지 대부분을 정적 HTML로 두고, 상호작용이 필요한 부분만 독립된 "섬"으로 만들어 각각 Hydration하는 구조입니다. 서버가 HTML을 렌더링하고 동적인 영역 둘레에 자리를 표시하면 그 영역이 클라이언트에서 자기완결적인 작은 위젯으로 Hydration된다는 설명을 Astro 문서가 인용합니다.

| 항목 | 설명 |
|------|------|
| 정적 영역 | JavaScript 없이 서버 HTML만으로 완성 |
| 섬 | 독립적으로 Hydration되는 상호작용 영역 |
| 로딩 시점 | 즉시, 브라우저가 한가할 때, 화면에 보일 때 등을 섬마다 지정 |
| 이점 | 보내는 JavaScript가 줄고, 섬이 서로를 막지 않고 병렬로 로드됨 |

- Astro는 `client:load`(즉시), `client:idle`(브라우저가 한가할 때), `client:visible`(화면에 들어올 때) 같은 클라이언트 지시어로 섬마다 시점을 정합니다.
- Web Components는 섬의 경계에 알맞습니다. 태그 하나가 섬이고, 정의 파일을 언제 불러오느냐가 Hydration 시점이며 프레임워크가 달라도 같은 방식입니다. 위 `IntersectionObserver` 코드가 `client:visible`에 해당하는 동작입니다.
- 섬은 서로의 상태를 모릅니다. 섬 사이의 통신은 이벤트나 같은 모듈을 가져와 공유하는 저장소로 합니다(자세히는 25편, 31편). 모듈은 같은 URL이면 한 번만 평가되므로 공유 저장소 모듈은 섬이 달라도 한 인스턴스입니다.
- 섬이 많으면 로드와 Hydration이 흩어져서 전체적인 일관성(초기 상태, 의존 순서)을 관리하기 어렵습니다. 페이지의 상호작용 비율이 낮을 때 이점이 큽니다.

## 클라이언트 초기화 시점

컴포넌트 정의가 실행되는 시점이 Hydration 시점입니다. 시점은 스크립트 로딩 방식과 트리거로 정합니다.

| 방식 | 시점 | 비고 |
|------|------|------|
| 모듈 스크립트(`type="module"`) | 문서 파싱이 끝난 뒤, `DOMContentLoaded` 전 | 기본으로 지연됨(자세히는 14편) |
| `defer` | 파싱 끝난 뒤 순서대로 | 일반 스크립트의 지연 |
| `async` | 다운로드가 끝나는 즉시 | 파싱 도중일 수 있어 실행 시점이 달라짐 |
| 동적 `import()` | 호출하는 시점 | 트리거를 직접 정함 |

트리거로 쓰는 신호는 다음과 같습니다.

| 트리거 | 구현 |
|--------|------|
| 즉시 | 정적 `import` 또는 모듈 스크립트 |
| 화면에 보일 때 | `IntersectionObserver`(Baseline 2019) |
| 상호작용할 때 | `pointerenter`, `focusin` 같은 첫 입력 이벤트 |
| 조건이 맞을 때 | `matchMedia()`의 결과 |
| 한가할 때 | `requestIdleCallback`은 Safari가 지원하지 않아 Baseline이 아님. 타이머로 대체 |

- 업그레이드는 `define()`을 호출하는 때 문서 순서대로 한꺼번에 일어납니다. 같은 태그의 요소가 수백 개면 한 번에 업그레이드되는 비용이 한 작업(task)에 몰리므로 긴 작업이 됩니다(자세히는 66편).
- `async` 스크립트로 정의를 불러오면 요소가 만들어진 뒤에 업그레이드되는지 만들어질 때 바로 정의되는지가 실행마다 달라질 수 있습니다. 컴포넌트는 두 경로를 모두 견뎌야 합니다(자세히는 18편).
- 정의가 실행되기 전의 입력은 사라집니다. 사용자가 누른 버튼이 정의 전이면 이벤트 리스너가 없어서 아무 일도 일어나지 않습니다. 상호작용 지연이 중요한 컴포넌트는 먼저 정의하고, 중요하지 않은 컴포넌트를 나중에 정의합니다.
- 서버 렌더링 결과를 보여 주는 시점부터 정의가 실행되는 시점까지의 간격을 줄이는 것이 중요합니다. 간격이 길면 보이는데 눌리지 않는 상태가 오래갑니다. 첫 화면에서 눌리는 컴포넌트는 같은 스크립트 번들에서 가장 먼저 정의합니다.
- 다른 컴포넌트가 정의되기를 기다릴 때는 `customElements.whenDefined()`를 씁니다(자세히는 33편).

## 스트리밍 HTML과 DSD

스트리밍은 서버가 HTML 전체를 완성하기 전에 만들어진 부분부터 조각으로 보내고, 브라우저가 도착하는 대로 파싱해서 그리는 방식입니다. HTML 파서는 증분으로 동작하기 때문에 가능합니다.

- DSD의 shadow root는 `template`의 시작 태그를 만나는 즉시 붙고, 그 안의 내용은 root에 바로 파싱됩니다. 그래서 컴포넌트 내용도 도착하는 대로 그려집니다(web.dev). 종료 태그를 기다리지 않습니다.
- 서버는 문서의 앞부분(`head`의 CSS, 레이아웃, 즉시 보이는 컴포넌트)을 먼저 보내고, 느린 데이터가 필요한 컴포넌트를 뒤에 보냅니다. 서버 응답 본문을 만드는 데 `ReadableStream`을 쓸 수 있습니다(자세히는 38편).

```js
const enc = new TextEncoder()
const stream = new ReadableStream({
  async start(c) {
    c.enqueue(enc.encode(shellHtml))      // 먼저 보냄
    c.enqueue(enc.encode(await slowHtml())) // 데이터 후
    c.close()
  },
})
```

- 파서는 문서 순서대로 DOM에 추가합니다. 먼저 나온 자리에 나중에 도착한 내용을 끼워 넣는 순서 바꾸기(out-of-order streaming)는 DSD만으로는 되지 않습니다. 느린 컴포넌트는 늦게 나타나도 되는 위치에 두거나 클라이언트에서 가져오게 합니다. HTML 표준에는 `template`의 `for` 속성을 쓰는 패칭이 정의되어 있지만 현재 Chrome 150 이상에서만 구현되어 있어 의존하지 않습니다.
- 응답 상태 코드와 헤더는 첫 조각에 담겨 나가므로 본문을 스트리밍하는 중에 오류가 생겨도 상태 코드를 바꿀 수 없습니다. 오류 표시는 본문 안에서 처리합니다.
- 중간 프록시나 서버가 응답을 모아서 보내는 설정(버퍼링)이면 스트리밍의 이점이 없어집니다.
- 정의 스크립트를 `head`에 두면 HTML이 도착하는 동안 내려받기가 겹칩니다. 다만 모듈 스크립트는 파싱이 끝난 뒤에 실행되므로 스트림이 끝나야 Hydration이 시작됩니다.

## FOUC / Layout Shift 방지

FOUC(Flash of Unstyled Content)는 스타일이 적용되기 전의 내용이 잠깐 보였다가 바뀌는 현상이고, Layout Shift는 이미 그려진 내용이 뒤늦게 크기나 위치가 바뀌며 밀리는 현상입니다. 커스텀 요소에서는 정의 전후의 외형 차이가 원인입니다.

- 정의되지 않은 커스텀 요소는 `display: inline`인 이름 모를 요소입니다. 정의가 실행되어 shadow tree와 스타일이 붙으면 크기가 갑자기 바뀝니다.
- DSD를 쓰면 정의 전에도 shadow tree의 내용과 스타일이 처음부터 그려집니다. 이것이 서버 렌더링으로 FOUC와 이동을 줄이는 가장 큰 방법입니다.
- DSD를 쓰지 않거나 서버에서 모양을 만들 수 없는 컴포넌트는 `:not(:defined)`로 정의 전의 자리를 미리 확보합니다. `:defined`는 Baseline 2020입니다.

```css
x-chart:not(:defined) {
  display: block;
  aspect-ratio: 16 / 9;
  background: var(--color-surface-sunken);
}
```

- `aspect-ratio`(Baseline 2021)나 `min-height`로 최종 크기와 같은 공간을 잡아 두면, 정의된 뒤에 내용이 채워져도 주변이 밀리지 않습니다.
- 정의 전에 `visibility: hidden`으로 감추면 깜빡임은 없지만 공간은 유지됩니다. `display: none`은 공간이 없어져서 나타날 때 이동이 생깁니다. 정의가 영영 실패할 수도 있으므로 숨김을 영구적으로 두지 않고, 제한 시간 뒤에는 보이게 하는 방법이 있어야 합니다.
- 정의된 시점을 JavaScript에서 알아 표시 상태를 바꿀 수 있습니다.

```js
const waits = tags.map((t) => customElements.whenDefined(t))
await Promise.all(waits)
document.documentElement.classList.add('ready')
```

- 이미지, 임베드, 광고처럼 뒤늦게 크기가 정해지는 내용은 `width`와 `height` 속성이나 `aspect-ratio`로 공간을 예약합니다. 웹 폰트는 `font-display`(Baseline 2020)와 `@font-face`의 `size-adjust`로 대체 글꼴과의 크기 차이를 줄입니다.
- CLS(Cumulative Layout Shift)의 기준은 75번째 백분위에서 0.1 이하입니다. 사용자 입력 후 500ms 안에 일어난 이동은 CLS에 포함되지 않습니다(자세히는 65편, 66편).
- 슬롯으로 받는 내용이 정의 전에는 호스트의 자식으로 그냥 보이다가 정의 후 shadow tree의 슬롯 위치로 옮겨지므로 이동이 생길 수 있습니다. DSD로 정의 전에도 같은 배치를 만들면 이 문제가 없어집니다.

## Prerender

Prerender는 화면을 미리 렌더링해 두는 방식으로, 서로 다른 두 가지를 가리킵니다.

| 종류 | 누가, 언제 | 결과 |
|------|------------|------|
| 정적 Prerender(정적 생성) | 빌드 도구가 빌드 때 | 페이지별 HTML 파일. 서버 렌더링과 같은 출력을 파일로 배포 |
| 브라우저 Prerender | 브라우저가 사용자가 이동하기 전에 | 숨겨진 상태로 페이지를 로드해 두었다가 이동 때 활성화 |

정적 Prerender는 SSR과 같은 렌더러를 빌드 단계에서 한 번 실행하는 것이라 DSD 출력과 Hydration은 같습니다. 요청마다 달라지는 데이터가 없는 페이지에 알맞고 서버 비용이 없습니다. 데이터가 빌드 시점에 고정되므로 갱신하려면 다시 빌드해야 합니다.

브라우저 Prerender는 Speculation Rules API의 `prerender` 규칙으로 요청합니다. 페이지의 모든 하위 리소스와 JavaScript를 로드한 상태로 숨겨 두었다가 사용자가 이동하면 그 탭을 앞으로 가져옵니다. 현재 Chromium 계열(Chrome, Edge 109 이상)만 지원하고 Baseline이 아닙니다. 점진적 향상으로 다룹니다.

```html
<script type="speculationrules">
{ "prerender": [{ "urls": ["/checkout"] }] }
</script>
```

- 숨겨진 상태에서도 페이지 스크립트가 실행되므로 컴포넌트의 정의, 생성자, `connectedCallback`이 활성화 전에 실행됩니다. 로그 전송, 읽음 표시, 로그인 상태에 따른 요청, 자동 재생 같은 부작용은 활성화 뒤로 미룹니다.
- 지금 Prerender 중인지는 `document.prerendering`으로 알고, 활성화 시점은 `prerenderingchange` 이벤트로 압니다. 성능 측정에서는 `PerformanceNavigationTiming.activationStart`로 활성화 시점을 구분합니다.
- 서버는 Prerender 요청의 `Sec-Purpose: prefetch;prerender` 헤더로 알아볼 수 있습니다. 로그인 해제, 장바구니 변경처럼 부작용이 있는 페이지는 Prerender하지 않습니다.
- 기본은 같은 출처이고, 다른 사이트로 이동하는 Prerender는 폐기됩니다. 위치·알림·파일 접근 같은 일부 API는 활성화 전까지 지연됩니다.
- 브라우저 Prerender로 활성화된 페이지는 이미 Hydration이 끝나 있어서 이동 직후 바로 상호작용이 됩니다.

```js
if (document.prerendering) {
  document.addEventListener('prerenderingchange',
    start, { once: true })
} else {
  start()
}
```

## SSR 가능한 컴포넌트 API 설계

SSR이 가능한 컴포넌트는 서버가 같은 입력으로 같은 마크업을 만들 수 있고, 클라이언트가 그 마크업을 다시 그리지 않고 이어받을 수 있는 컴포넌트입니다. 설계 기준은 다음과 같습니다.

| 기준 | 이유 |
|------|------|
| 입력은 속성과 자식(슬롯)으로 받음 | 서버는 프로퍼티나 객체를 전달할 수 없고 마크업만 만듦 |
| 상태는 직렬화 가능한 값 | 문자열, 숫자, 불리언, JSON만 서버에서 클라이언트로 갈 수 있음 |
| 같은 입력은 같은 출력 | 서버·클라이언트 결과가 달라지면 불일치가 생김 |
| 모듈 로드 시 DOM에 접근하지 않음 | 서버에서 모듈을 불러올 때 `document`가 없음 |
| 이미 있는 shadow root를 재사용 | DSD가 있으면 다시 그리지 않음 |
| 정의 전에도 의미가 있는 마크업 | JavaScript 없이도 내용이 보임 |

- 입력은 속성으로 받습니다. 객체나 배열이 필요하면 속성에 JSON 문자열로 쓰거나 `script type="application/json"`으로 서버가 직렬화한 데이터를 같이 보내고, 클라이언트가 읽어 프로퍼티로 변환합니다. 서버 출력이 객체 프로퍼티에 의존하지 않게 합니다(자세히는 19편).
- 서버에서 불러오는 코드에 브라우저 전용 API를 최상위에서 쓰지 않습니다. 렌더링 함수와 클래스를 파일로 분리해서, 서버는 렌더링 함수 파일만 불러옵니다.

```js
// 서버에서도 안전하게 불러올 수 있는 파일
export const tag = 'x-card'
export const render = (props) => `<x-card>...</x-card>`
```

```js
// 브라우저 전용 파일
import { tag } from './x-card.render.js'
customElements.define(tag, class extends HTMLElement {})
```

- 생성자에서 속성이나 자식을 읽지 않습니다. 파서가 만드는 경로에서는 자식이 아직 없을 수 있습니다. 초기화는 `connectedCallback`에서 합니다(자세히는 18편).
- 중복 정의를 막습니다. `customElements.get(tag)`로 확인한 뒤 `define()`을 호출하고, 같은 코드가 두 번 불러와져도 `NotSupportedError`가 나지 않게 합니다(자세히는 29편).
- 폼 컨트롤은 서버가 만든 일반 `input`을 Light DOM에 두고 정의가 실행되면 향상시키는 방식이 안전합니다. 서버에는 `ElementInternals`가 없어 폼에 참여하는 값을 마크업으로 만들 수 없기 때문입니다(자세히는 26편, 71편).
- 서버가 만든 `id` 참조(`aria-labelledby`)는 shadow 경계를 넘지 못하므로 같은 트리 안에서 이름을 연결합니다(자세히는 27편).
- 서버에서 출력하는 스타일은 DSD 안의 `style`이나 `link`입니다. 클라이언트가 공유 `CSSStyleSheet`를 `adoptedStyleSheets`로 쓰는 컴포넌트이면 Hydration 이후 서버의 `style`을 제거하고 공유 시트로 바꿀 수 있습니다(자세히는 24편).
- 서버가 입력을 이스케이프하는 책임과 클라이언트가 속성을 읽어 DOM에 넣을 때의 책임(`textContent` 사용, 신뢰할 수 없는 HTML 정제)은 따로 지킵니다(자세히는 63편).

## 핵심 정리

- 서버에는 `HTMLElement`와 `customElements`가 없어 컴포넌트를 실행하지 못하므로 서버는 호스트와 shadow tree를 담은 HTML 문자열을 출력하며, Shadow DOM 내용은 Declarative Shadow DOM(Baseline 2024)의 `template shadowrootmode`로 표현합니다.
- DSD는 문서 파서가 `template` 시작 태그를 만나는 즉시 부모를 호스트로 만들며, 첫 번째 DSD만 root가 되고 `innerHTML`로는 생성되지 않아 `setHTMLUnsafe()`(Baseline 2025)를 써야 합니다.
- DSD root가 있는 요소에서 `attachShadow()`는 mode가 같으면 root를 비우고 반환하므로, 생성자는 `ElementInternals.shadowRoot`로 먼저 확인해 서버 출력을 지우지 않습니다.
- Hydration은 기존 DOM을 재사용하며 이벤트와 상태를 연결하는 일이고, Web Components에서는 업그레이드가 그 대부분을 하며 정의 실행 시점이 곧 Hydration 시점이어서 부분 Hydration과 Islands는 정의를 지연해 구현합니다.
- 스트리밍 HTML에서는 DSD가 도착하는 대로 그려지고, FOUC와 Layout Shift는 DSD, `:not(:defined)`의 공간 확보, `aspect-ratio`와 크기 지정으로 줄입니다.
- 정적 Prerender는 빌드 때 만든 HTML이고 브라우저 Prerender(Speculation Rules)는 Chromium 전용이며, SSR 가능한 컴포넌트는 속성·슬롯 입력, 직렬화 가능한 상태, 같은 입력 같은 출력, 기존 root 재사용을 지킵니다.

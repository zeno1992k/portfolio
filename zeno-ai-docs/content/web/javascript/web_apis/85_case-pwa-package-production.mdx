## 사례를 읽는 방법

앞의 사례가 앱 안의 구조였다면 이 편은 앱과 패키지를 세상에 내놓는 구조를 다룹니다. 기능 구현은 앞선 편의 몫이고, 여기서는 그 조각을 어떻게 배치하고 무엇으로 검증하는지에 집중합니다.

| 사례 | 묻는 것 | 관련 편 |
|------|---------|---------|
| PWA 오프라인 앱 | 네트워크 없이 무엇이 동작하고 어떻게 다시 맞추는가 | 56, 57, 41, 42 |
| Design System 패키지 | 여러 앱이 같은 UI를 어떻게 안전하게 받는가 | 72, 73, 74, 75 |
| 재사용 가능한 Web Components 패키지 | 프레임워크가 달라도 같은 요소를 어떻게 쓰게 하는가 | 77, 76 |
| 프로덕션 구조 | 성능·접근성·테스트를 어디서 막고 어디서 관찰하는가 | 65, 66, 68, 69, 71 |

- 코드는 모두 설계를 읽기 위한 축약본입니다.
- 앱 코드는 81편의 코어와 82편의 서비스·부트스트랩 위에 있다고 가정합니다.

## PWA 오프라인 앱

주문 메모 앱을 예로 듭니다. 목록을 읽고 새 메모를 쓰는 일이 오프라인에서도 되어야 하고, 연결이 돌아오면 서버와 맞춰야 합니다. 서비스 워커로 캐시를 쓰는 것은 시작일 뿐이고, 어려움은 쓰기를 잃지 않는 것과 새 버전으로 안전하게 넘어가는 것에 있습니다.

### 층별 책임

| 층 | 책임 | 저장 위치 |
|----|------|-----------|
| manifest | 이름, 아이콘, `start_url`, `scope` | 파일 |
| 서비스 워커 | 앱 셸 선캐시, 요청 가로채기, 업데이트 | Cache Storage |
| 읽기 데이터 | 마지막으로 받은 API 응답 | Cache Storage 또는 스토어 |
| 쓰기 큐(outbox) | 서버에 못 보낸 변경 | IndexedDB |
| 앱 서비스 | 연결 상태, 큐 비우기, 업데이트 알림 | 메모리 |
| UI | 상태 표시(오프라인, 동기화 대기, 새 버전) | 없음 |

- 서비스 워커와 페이지는 메모리를 공유하지 않습니다. 둘 사이의 데이터는 IndexedDB, 캐시, `postMessage`로만 오갑니다(자세히는 57편).
- 쓰기 큐를 IndexedDB에 두는 이유는 서비스 워커가 종료되어도, 탭을 닫아도 남아야 하기 때문입니다(자세히는 41편).

### 요청 종류별 캐시 전략

| 요청 | 전략 | 이유 |
|------|------|------|
| 내비게이션(HTML) | 캐시된 앱 셸을 반환 | SPA는 모든 경로가 같은 HTML |
| 해시가 붙은 JS·CSS·글꼴·이미지 | Cache First | 내용이 바뀌면 이름이 바뀜 |
| 읽기 API(`GET /api/`) | Network First + 타임아웃, 실패 시 캐시 | 최신이 우선이되 오프라인에서는 마지막 값 |
| 쓰기 API(`POST` 등) | 가로채지 않음 | 앱의 쓰기 큐가 책임 |
| 인증, 결제 | Network Only | 캐시하면 안 됨 |

- 표의 기준은 "낡은 응답이 해로운가"입니다. 정적 파일은 이름에 버전이 있어 안전하고, 사용자 데이터는 낡을 수 있어서 네트워크를 먼저 시도합니다(자세히는 56편의 Cache Strategy).
- 서비스 워커는 `GET`만 다룹니다. 쓰기를 서비스 워커에서 재생하려는 설계도 있지만, 사용자에게 실패를 보여 주고 충돌을 다루려면 앱이 쥐고 있는 편이 낫습니다.

### 서비스 워커: 선캐시와 라우팅

```js
const VERSION = 'v2026-10-05.1'      // 빌드가 주입
const SHELL = `shell-${VERSION}`
const DATA = 'data-v1'
const FILES = self.__PRECACHE__      // 빌드가 만든 파일 목록

self.addEventListener('install', (e) => {
  e.waitUntil(
    caches.open(SHELL).then((c) => c.addAll(FILES)),
  )
})
```

```js
self.addEventListener('activate', (e) => {
  e.waitUntil((async () => {
    const keep = new Set([SHELL, DATA])
    for (const k of await caches.keys()) {
      if (!keep.has(k)) await caches.delete(k)
    }
  })())
})
```

```js
self.addEventListener('fetch', (e) => {
  const r = e.request
  const url = new URL(r.url)
  if (r.method !== 'GET') return
  if (url.origin !== location.origin) return
  if (r.mode === 'navigate') return e.respondWith(shell(r))
  if (url.pathname.startsWith('/api/')) {
    return e.respondWith(api(e))
  }
  e.respondWith(cacheFirst(r))
})
```

- 선캐시 목록은 사람이 적지 않고 빌드가 만듭니다. 해시가 붙은 파일 이름 목록과 버전이 빌드마다 바뀌어야 서비스 워커 스크립트가 변경되어 업데이트가 일어납니다(자세히는 56편).
- `cache.addAll`은 하나라도 실패하면 설치 전체가 실패합니다. 선캐시 대상은 앱 셸에 꼭 필요한 파일로 제한합니다.
- `activate`에서 현재 버전 외의 캐시를 지웁니다. 이름에 버전을 넣지 않은 `DATA`는 응답 형식이 바뀔 때 이름을 올립니다.
- `GET`이 아니거나 다른 출처이면 `respondWith`를 부르지 않고 브라우저의 기본 처리에 맡깁니다.

```js
async function shell(req) {
  const hit = await caches.match('/index.html')
  return hit ?? fetch(req)
}
```

```js
async function api(event) {
  const req = event.request
  const cache = await caches.open(DATA)
  const signal = AbortSignal.timeout(3000)
  try {
    const res = await fetch(req, { signal })
    if (res.ok) event.waitUntil(cache.put(req, res.clone()))
    return res
  } catch {
    return (await cache.match(req)) ?? Response.error()
  }
}
```

- 모든 내비게이션에 캐시된 `/index.html`을 주면 어떤 경로로 들어와도 오프라인에서 앱이 뜹니다. 대신 HTML이 갱신되는 시점은 서비스 워커 업데이트 때입니다.
- 읽기 API는 3초 안에 응답이 없으면 캐시로 물러섭니다. 느린 네트워크에서 화면이 멈추는 것을 막고, 캐시도 없으면 `Response.error()`로 앱이 네트워크 오류를 받게 합니다. 앱의 Fetch Client는 이를 `network` 종류로 분류합니다(자세히는 82편).
- 응답 본문은 한 번만 읽을 수 있어서 캐시에 넣을 때 `clone()`하고, 캐시 쓰기는 `waitUntil`로 응답 뒤에도 끝나게 합니다.
- 사용자별 응답을 캐시하므로 로그아웃하면 `DATA` 캐시를 비웁니다. 앱이 `postMessage({ type: 'CLEAR_USER' })`를 보내고 서비스 워커가 `caches.delete(DATA)`를 합니다. 다른 사용자에게 이전 사용자의 데이터가 보이면 안 됩니다.

### 쓰기 큐

오프라인에서 한 변경을 IndexedDB의 outbox에 쌓고, 온라인이 되면 순서대로 서버에 보냅니다. 화면은 즉시 낙관적으로 갱신하고 "동기화 대기" 표시를 붙입니다.

```js
export async function enqueue(method, url, body) {
  const item = {
    id: crypto.randomUUID(),     // 요청 ID: 중복 방지 키
    method, url, body, at: Date.now(), state: 'pending',
  }
  await db.put('outbox', item)
  return item
}
```

```js
let busy = false
export async function flush() {
  if (busy) return
  busy = true
  try {
    for (const m of await db.getAll('outbox')) {
      if (m.state !== 'pending') continue
      if (!(await deliver(m))) break   // 네트워크 실패: 중단
    }
  } finally { busy = false }
}
```

```js
async function deliver(m) {
  const body = JSON.stringify(m.body)
  const headers = { 'X-Request-Id': m.id }
  const init = { method: m.method, body, headers }
  let res
  try {
    res = await fetch(m.url, init)
  } catch { return false }
  if (res.ok) await db.delete('outbox', m.id)
  else if (res.status >= 500) return false
  else await markFailed(m, res.status)
  return true
}
```

- 변경마다 요청 ID를 만들어 헤더로 보냅니다. 응답을 받기 전에 연결이 끊겨서 다시 보내더라도 서버가 같은 ID를 한 번만 처리하게 하는 계약입니다(서버와 합의가 필요합니다).
- 순서가 중요하므로 한 건씩 차례로 보내고, 네트워크 실패나 5xx에서는 중단해 다음 기회로 미룹니다. 큐 안의 순서가 바뀌면 같은 항목에 대한 변경이 뒤집힙니다.
- 4xx는 다시 보내도 같은 결과이므로 `failed`로 표시하고 큐를 계속 진행합니다. 충돌(409)이나 검증 실패는 사용자가 보고 결정해야 하므로 UI가 `failed` 항목을 보여 줍니다.
- `busy` 플래그로 `flush`가 동시에 둘 돌지 않게 합니다. 같은 변경을 두 번 보내는 일을 막습니다.
- `markFailed(m, code)`는 항목을 `failed` 상태와 응답 코드로 다시 저장하는 함수입니다.
- `flush`는 DOM에 의존하지 않게 작성해서 페이지와 서비스 워커가 함께 씁니다.
- 큐가 비어 있지 않은 채로 새 버전으로 바뀌어도 IndexedDB의 큐는 유지됩니다. 큐 항목의 스키마가 바뀌면 `upgradeneeded`에서 옛 항목을 변환합니다(자세히는 41편).

### 큐를 비우는 시점

| 시점 | 수단 |
|------|------|
| 앱 시작 | 부트스트랩에서 `flush()` |
| 연결 복구 | `window`의 `online` 이벤트 |
| 탭이 다시 보임 | `visibilitychange` |
| 변경 직후 | 온라인이라고 보이면 바로 `flush()` |
| 탭이 닫혀 있을 때 | Background Sync의 `sync` 이벤트(Chromium 전용) |

- `navigator.onLine`이 `false`면 확실히 오프라인이지만 `true`는 연결을 보장하지 않습니다. 이 값으로 기능을 끄지 말고, 실제 요청이 실패하는 것을 기준으로 상태를 정합니다(자세히는 60편).
- Background Sync(`registration.sync.register`)는 Baseline이 아닙니다. 지원하지 않는 브라우저를 기준으로 위 다른 시점이 기본이고, 있으면 보강으로 씁니다(자세히는 57편).
- 연결 상태(`online`, `offline`, `syncing`)는 앱 서비스가 스토어에 두고, 배지와 "동기화 대기 N건"을 `role="status"` 영역으로 알립니다.

### 업데이트와 설치

```js
export async function watchUpdates(reg, onReady) {
  if (reg.waiting) onReady(reg.waiting)
  reg.addEventListener('updatefound', () => {
    const w = reg.installing
    w.addEventListener('statechange', () => {
      const had = navigator.serviceWorker.controller
      if (w.state === 'installed' && had) onReady(w)
    })
  })
}
```

- 새 버전이 설치되어 대기 중이면 "새 버전이 있어요" 배너를 보이고, 사용자가 수락하면 대기 워커에 `SKIP_WAITING`을 보낸 뒤 `controllerchange`에서 새로고침합니다(자세히는 56편).
- 자동으로 새로고침하지 않습니다. 입력 중인 폼이 사라질 수 있기 때문입니다. 작성 중인 내용은 초안으로 저장해 두는 설계가 안전합니다.
- 장시간 열려 있는 앱은 탭이 다시 보일 때 `registration.update()`를 불러 새 버전을 확인합니다.
- manifest는 `name`, 192px·512px 아이콘, `start_url`, `display`, `scope`를 갖추면 설치 대상이 됩니다. 설치 버튼은 `beforeinstallprompt`가 올 때만 보입니다. 이 이벤트는 Chromium 전용이라서 설치 서비스가 일찍 받아 보관합니다(자세히는 57편).
- 저장소는 `navigator.storage.persist()`로 영속 저장을 요청합니다. 브라우저가 거부할 수 있고(`false`), 거부되면 저장 공간이 부족할 때 데이터가 지워질 수 있습니다. 쓰기 큐처럼 잃으면 안 되는 데이터가 있는 앱은 이 결과를 확인하고, 쓰기 중 `QuotaExceededError`를 사용자에게 알립니다(자세히는 42편).

### 검증

- 오프라인 시나리오를 자동화합니다. 처음 방문, 설치 뒤 네트워크 끊기, 오프라인 쓰기, 연결 복구 후 동기화, 새 버전 배포 후 업데이트를 E2E로 확인합니다(자세히는 69편).
- 서비스 워커는 오래 남으므로 이전 버전 사용자가 새 서버와 만나는 경우를 시험합니다. 서버 API가 바뀌면 큐에 쌓인 옛 형식의 요청이 거부될 수 있습니다.

**흔한 실수:**

- 선캐시에 해시 없는 파일 이름을 넣어 갱신해도 캐시된 옛 파일이 계속 나가는 것입니다.
- 서비스 워커를 한 번 배포하고 업데이트 경로를 시험하지 않는 것입니다. 서비스 워커 스크립트 자체가 오래 캐시되면 새 버전을 감지하지 못합니다.
- 쓰기를 메모리 배열에만 쌓아 탭을 닫으면 잃는 것입니다.

## Design System 패키지

여러 앱이 같은 UI를 쓰도록 컴포넌트와 디자인 토큰을 패키지로 배포하는 사례입니다. 내부 구조 설계는 72편, 배포와 버전은 73편, 토큰은 74편, 컴포넌트 규칙은 75편에서 다뤘습니다. 여기서는 그것들을 하나의 저장소 구조와 릴리스 흐름으로 묶습니다.

### 패키지 분할

| 패키지 | 내용 | 소비자 |
|--------|------|--------|
| `@acme/tokens` | 디자인 토큰 원본과 빌드 결과(`tokens.css`, `tokens.json`) | 앱, 디자이너 도구, 다른 패키지 |
| `@acme/ui` | Web Components, 클래스·정의 진입점, 매니페스트, 타입 | 앱 |
| `@acme/ui-react` 등 | 프레임워크 어댑터(다음 사례) | 해당 프레임워크 앱 |
| 문서 사이트 | 데모, API 문서(배포하지 않는 비공개 패키지) | 사람 |

```text
packages/
  tokens/        src/*.json → dist/tokens.css
  ui/
    src/x-button/  x-button.js, define.js, x-button.test.js
    src/index.js
    custom-elements.json   (빌드가 생성)
  ui-react/      어댑터(생성)
apps/docs/       매니페스트로 만든 문서와 데모
```

- 토큰을 컴포넌트와 별도 패키지로 둡니다. 토큰만 필요한 곳(문서, 비 Web Components 화면)이 컴포넌트를 받지 않아도 되고, 디자인 변경을 컴포넌트 릴리스와 분리해 낼 수 있습니다(자세히는 74편).
- 작업 영역(워크스페이스)으로 묶어 로컬에서 서로를 연결해 개발합니다. 배포할 때는 각 패키지가 독립된 버전을 가집니다.

### 토큰과 컴포넌트의 계약

컴포넌트는 토큰을 CSS 사용자 정의 속성으로 읽고, 기본값을 함께 둡니다.

```css
:host {
  background: var(
    --acme-button-bg, var(--acme-color-brand, #2563eb));
  padding-inline: var(
    --acme-button-px, var(--acme-space-3, 12px));
}
```

- 컴포넌트 토큰은 의미 토큰을, 의미 토큰은 원시 토큰을 가리키는 계층을 둡니다. 테마와 다크 모드는 의미 토큰 층의 값만 바꿉니다(자세히는 74편).
- 기본값을 두면 앱이 `tokens.css`를 가져오지 않아도 컴포넌트가 최소한 보입니다. 변수는 shadow 경계를 통과하므로 앱이 `:root`에서 값을 바꾸면 모든 컴포넌트에 적용됩니다(자세히는 23편).
- 토큰 이름과 `::part` 이름, 슬롯 이름, 이벤트 이름이 공개 API입니다. 이름을 바꾸면 호환성을 깨는 변경입니다.

### 진입점과 exports

```json
{
  "name": "@acme/ui",
  "type": "module",
  "sideEffects": ["./dist/define/*.js", "**/*.css"],
  "customElements": "custom-elements.json",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    },
    "./x-button": "./dist/x-button/x-button.js",
    "./define/*": "./dist/define/*.js",
    "./custom-elements.json": "./custom-elements.json"
  }
}
```

- 루트 진입점은 클래스를, `define/*`은 가져오기만으로 등록되는 파일을 줍니다. 부수 효과를 `sideEffects`에 적어 번들러가 등록 파일을 지우지 않게 합니다(자세히는 72편).
- `exports`에 없는 경로는 가져올 수 없어서 내부 파일 구조를 마음대로 바꿀 수 있습니다.
- 모든 정의 진입점은 같은 중복 정의 가드를 거칩니다. 같은 이름을 두 번 `define()`하면 `NotSupportedError`이기 때문입니다.
- 매니페스트(`custom-elements.json`)는 빌드가 만들고, 문서 사이트, IDE, 어댑터 생성기가 읽습니다. 컴포넌트 소스의 JSDoc이 문서의 원본입니다(자세히는 75편).

### 릴리스와 호환성

| 변경 | 버전 | 예 |
|------|------|----|
| 호환성 깨짐 | 주(major) | 속성·이벤트·슬롯·파트·토큰 이름 변경 또는 삭제, 접근성 동작 변경, `exports` 경로 제거 |
| 기능 추가 | 부(minor) | 새 컴포넌트, 새 속성, 새 토큰 |
| 수정 | 수(patch) | 버그 수정, 내부 구현 변경 |

- 공개 API의 범위를 문서로 정해 두어야 위 표가 적용됩니다. 비공개 경로와 내부 CSS 클래스는 범위 밖입니다.
- 없애기 전에 한 주기 동안 폐기 예고 경고를 개발 모드에서 냅니다. 옛 속성 이름을 쓰면 새 이름을 안내하는 경고를 한 번만 출력합니다(자세히는 73편).
- 변경 기록에는 주 버전마다 옮겨 가는 방법을 적습니다. 매니페스트를 이전 릴리스와 비교해 공개 API가 사라졌는데 주 버전이 오르지 않은 경우를 CI에서 막을 수 있습니다.
- CDN으로 쓰는 앱이 있으면 버전을 고정한 URL과 SRI를 문서에 안내합니다(자세히는 73편).

### 품질 게이트

패키지의 모든 변경이 통과해야 하는 검사입니다.

| 검사 | 확인하는 것 | 편 |
|------|-------------|----|
| 단위·통합 | 속성, 이벤트, 폼 값, 등록 | 68 |
| 접근성 | axe, 키보드 조작, 접근성 트리 | 69 |
| 시각 회귀 | 상태별 컴포넌트 화면 | 69 |
| 번들 크기 | 컴포넌트별, 전체 | 66 |
| API 변경 | 매니페스트 비교와 버전 일치 | 73 |
| 호환성 | 지원 브라우저 기준 동작 | 71 |

- 접근성 검사의 통과는 자동 검사 가능한 규칙 안에서 위반이 없다는 뜻입니다. 새 컴포넌트는 키보드와 스크린 리더로 사람이 한 번 확인합니다(자세히는 69편).
- 컴포넌트마다 접근성 계약(역할, 키 조작, 이름 규칙)을 문서에 적어 그대로 테스트합니다.

**흔한 실수:**

- 토큰 이름을 정리하다가 앱이 쓰던 변수를 지워 주 버전 없이 배포하는 것입니다.
- 문서 사이트의 예제를 사람이 직접 써서 컴포넌트 API와 어긋나는 것입니다. 매니페스트와 테스트가 원본이 되게 합니다.

## Framework에서 재사용 가능한 Web Components 패키지

한 번 만든 컴포넌트를 React, Vue, Angular, Svelte, 프레임워크 없는 페이지에서 모두 쓰게 하는 사례입니다. 핵심은 요소 자체를 프레임워크와 무관하게 두고, 프레임워크 쪽의 부족을 얇은 어댑터로 메우는 것입니다.

### 층 구조

| 층 | 내용 | 프레임워크 의존 |
|----|------|----------------|
| 요소(core) | 클래스, 속성·프로퍼티, 이벤트, 슬롯, 폼 참여 | 없음 |
| 타입 | 태그 이름 맵, 이벤트 맵, JSX·템플릿 타입 선언 | 선택 |
| 어댑터 | 프로퍼티 대입, 이벤트 연결, ref | 있음(얇게) |
| 스타일 | 토큰 CSS, 사용자 정의 속성, `::part` | 없음 |

- 논리는 모두 요소에 둡니다. 어댑터는 프로퍼티 대입, 이벤트 연결, 타입 제공만 합니다. 어댑터가 얇아야 프레임워크마다 동작이 달라지지 않습니다(자세히는 77편).

### 공개 계약

| 계약 | 규칙 |
|------|------|
| 입력 | 원시 값은 속성과 프로퍼티 양쪽, 객체·배열은 프로퍼티만 |
| 출력 | `CustomEvent`, 이름은 kebab-case, 데이터는 `detail`, `bubbles`와 `composed` |
| 명령 | 공개 메서드(`open()`, `focus()`)를 문서화 |
| 구성 | 슬롯. 렌더 prop이나 스코프드 슬롯을 요구하지 않음 |
| 폼 | `formAssociated`와 `ElementInternals`. 값은 `value`와 `input`·`change` 이벤트 |
| 등록 | 클래스와 정의 분리, 호출하는 쪽이 이름과 시점을 정함 |

- 이 계약은 플랫폼 표준만으로 이루어져서 어느 프레임워크에서든 같습니다. 프레임워크가 달라 생기는 차이는 값이 프로퍼티와 속성 중 어디로 가는지, 이벤트 이름을 어떻게 받는지, ref를 어떻게 얻는지에 모입니다(자세히는 77편).
- 이벤트 이름은 소문자와 대시로 짓습니다. 대소문자가 섞인 이름은 프레임워크별 변환 규칙에 걸립니다.
- 업그레이드 전에 프로퍼티가 대입되는 경우를 요소가 흡수합니다. 정의가 늦게 로드되는 프레임워크 앱에서도 값이 사라지지 않습니다(자세히는 19편).

### 서버 렌더링에서 가져와도 터지지 않기

프레임워크가 서버에서 렌더링하면서 패키지를 가져오면 서버에는 `HTMLElement`와 `customElements`가 없습니다. 모듈이 평가되는 순간 오류가 나지 않게 설계합니다.

```js
const Base = globalThis.HTMLElement ?? class {}

export class XButton extends Base {
  /* ... */
}
```

```js
export function defineAll() {
  if (typeof customElements === 'undefined') return
  defineElement('x-button', XButton)
}
```

- 정의 함수는 서버에서 아무 일도 하지 않습니다. 서버에서 컴포넌트 안쪽의 HTML은 만들어지지 않으므로 필요하면 Declarative Shadow DOM을 출력하는 별도 도구를 씁니다(자세히는 76편, 77편).
- 모듈 최상위에서 `document`나 `window`를 참조하지 않습니다. 가져오기만으로 서버가 깨집니다.

### 어댑터

React 19는 커스텀 요소의 프로퍼티와 이벤트를 직접 지원해서 어댑터가 필요 없는 경우도 많습니다. 어댑터가 가치를 갖는 곳은 타입, 이벤트 이름 표기, 상위 버전 미만의 환경입니다.

```jsx
function useEvent(ref, name, fn) {
  useEffect(() => {
    const el = ref.current
    if (!el || !fn) return
    el.addEventListener(name, fn)
    return () => el.removeEventListener(name, fn)
  }, [ref, name, fn])
}
```

- 어댑터는 소스에서 직접 쓰지 않고 매니페스트에서 생성합니다. 컴포넌트가 늘수록 수작업 어댑터에는 누락이 생깁니다(자세히는 72편, 77편).
- Vue, Svelte, Angular는 값 전달과 이벤트 문법이 서로 다르며 대부분 어댑터 없이 쓰고 타입 선언만 제공합니다. 프레임워크별 규칙은 77편의 표를 따릅니다.
- 폼 연결 요소는 네이티브 폼 제출과 `FormData`에는 그대로 참여합니다. 프레임워크의 양방향 바인딩에 연결하려면 `value` 프로퍼티와 `input`·`change` 이벤트를 어떻게 이을지 어댑터나 문서가 보여 줍니다.

### 패키지 메타데이터

```json
{
  "name": "@acme/ui-react",
  "peerDependencies": {
    "@acme/ui": "^2.0.0",
    "react": ">=18"
  }
}
```

- 어댑터는 요소 패키지를 `peerDependencies`로 선언합니다. 앱이 요소 패키지를 두 벌 받으면 같은 태그를 두 번 `define()`하는 충돌이 납니다.
- 요소와 어댑터는 같은 주 버전을 맞춥니다. 요소의 공개 API가 깨지면 어댑터도 깨지기 때문입니다.

### 상호 운용 검증

| 환경 | 확인할 것 |
|------|-----------|
| 프레임워크 없음(CDN, 정의 진입점) | 등록, 속성, 이벤트, 슬롯 |
| React | 객체 prop, 이벤트, ref, 서버 렌더링 |
| Vue | `.prop`, 이벤트, 슬롯, 폼 |
| Angular | 속성·프로퍼티 바인딩, 스키마 설정, 폼 |
| 서버 렌더링 | 가져오기 오류 없음, 업그레이드 후 상태 |

- 환경마다 작은 예제 앱을 만들어 CI에서 실행합니다. 계약(값, 이벤트, 슬롯, 폼, 서버 렌더링)을 각 환경에서 한 번씩 확인하는 스모크 테스트입니다.
- 공개 계약이 흔들릴 때 가장 먼저 깨지는 곳이 프레임워크 연동이므로 이 검증이 변경의 안전망입니다.

**흔한 실수:**

- 요소 안에 특정 프레임워크의 가정(렌더 prop, 특정 이벤트 시스템)을 넣는 것입니다.
- 객체를 속성으로만 받도록 만들어 프레임워크에서 문자열로 깨지는 것입니다.
- 어댑터가 요소를 감싸며 로직을 더해 프레임워크별로 동작이 달라지는 것입니다.

## 성능 / 접근성 / 테스트까지 포함한 프로덕션 구조

앱과 패키지를 운영에 내놓을 때 필요한 것은 기능이 아니라 기준과 강제 장치입니다. 기준은 숫자나 규칙으로 적고, 강제는 CI에서, 확인은 운영에서 합니다.

### 저장소 구조

```text
apps/web/            앱(81, 82편의 코어 + 기능 모듈)
packages/tokens/     토큰
packages/ui/         컴포넌트 라이브러리
tests/
  e2e/               사용자 시나리오
  visual/            시각 회귀 기준 이미지
tools/
  check-size.js      번들 크기 검사
  budgets.json       성능·크기 한도
```

- 한도와 기준을 코드 저장소에 파일로 둡니다. 논의가 문서 밖에서 사라지지 않고, 변경 이력이 남습니다.
- 앱과 라이브러리는 같은 검사 도구를 공유하되 한도는 각자 가집니다.

### 기준과 수단

| 영역 | 기준 | 사전 강제(CI) | 운영 관찰 |
|------|------|---------------|-----------|
| 성능 | LCP 2.5초, INP 200밀리초, CLS 0.1 이하(75번째 백분위) | JS 크기 예산, 실험실 측정 | 현장 데이터(RUM) |
| 접근성 | 키보드로 모든 기능 조작, 이름·역할·상태 | axe, 키보드·트리 테스트 | 사용자 신고 경로, 수동 점검 |
| 정확성 | 핵심 경로가 깨지지 않음 | 단위·통합·E2E | 오류 보고 |
| 외관 | 의도하지 않은 시각 변경 없음 | 컴포넌트 단위 시각 회귀 | 없음 |
| 보안 | 삽입 공격 완화 | CSP, Trusted Types 위반 보고 | 위반 보고 수집 |
| 호환성 | 지원 브라우저에서 동작 | 엔진별 E2E, 기능 검사 | 오류 보고의 브라우저 분포 |

- 성능 지표는 현장 데이터로 판정합니다. 실험실 수치는 재현과 원인 분석용입니다(자세히는 65편).
- 자동 검사로 잡을 수 없는 접근성 문제가 있으므로 릴리스 전에 사람이 핵심 흐름을 확인하는 단계를 둡니다(자세히는 69편).

### CI 파이프라인

```mermaid
flowchart LR
  A[정적 검사] --> B[단위·통합]
  B --> C[빌드]
  C --> D[크기 예산]
  D --> E[접근성·E2E]
  E --> F[시각 회귀]
  F --> G[배포 후보]
```

- 싼 검사가 앞, 느린 검사가 뒤입니다. 앞 단계가 실패하면 뒤를 돌리지 않아 시간을 줄입니다.
- 크기 예산은 빌드 결과를 기준으로 하므로 빌드 뒤에 둡니다. 시각 회귀는 환경에 민감해서 기준 이미지를 만든 것과 같은 환경(보통 CI 컨테이너)에서만 비교합니다(자세히는 69편).

```js
import { readFileSync } from 'node:fs'
import { gzipSync } from 'node:zlib'

const cfg = readFileSync('budgets.json', 'utf8')
const { file, max } = JSON.parse(cfg)
const size = gzipSync(readFileSync(file)).length
if (size > max) {
  console.error(`${file}: ${size}B > ${max}B`)
  process.exit(1)
}
```

- 한도를 넘으면 빌드를 실패시킵니다. 예산은 지켜야 하는 한도이지 권고가 아닙니다(자세히는 66편).
- 크기는 전송 크기에 가까운 압축 후 값으로 잽니다. 한도는 서비스의 사용자 환경에 맞춰 정하고, 처음에는 현재 값에서 시작해 늘어나지 못하게 막는 것도 방법입니다.

### 운영 계측

```js
const rows = []
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) rows.push(e.startTime)
}).observe({
  type: 'largest-contentful-paint',
  buffered: true,
})

addEventListener('visibilitychange', () => {
  if (document.visibilityState !== 'hidden') return
  const lcp = rows.at(-1)
  const path = location.pathname
  const body = JSON.stringify({ lcp, path })
  navigator.sendBeacon('/_vitals', body)
})
```

- 마지막 LCP 엔트리가 LCP이고, 페이지가 숨겨질 때 한 번 보냅니다(자세히는 65편, 82편).
- INP와 CLS는 계산 규칙이 복잡하므로 이 계산을 정확히 맞춘 검증된 구현(web.dev가 권하는 `web-vitals` 라이브러리)을 쓰는 편이 안전합니다. 결과를 같은 경로로 보냅니다.
- 보내는 값에는 경로, 기기 종류, 브라우저 정도만 넣고 개인 정보는 넣지 않습니다. 75번째 백분위로 집계해 기준과 비교합니다.
- 오류 보고(82편)와 함께 릴리스 버전을 실어 보내면 어느 배포에서 나빠졌는지 알 수 있습니다.

### 배포와 캐시

| 대상 | 캐시 정책 | 이유 |
|------|-----------|------|
| 해시가 붙은 JS·CSS·이미지 | `Cache-Control: max-age=31536000, immutable` | 내용이 바뀌면 이름이 바뀜 |
| `index.html` | `Cache-Control: no-cache` | 항상 재검증해 새 파일 이름을 받음 |
| 서비스 워커 스크립트 | 오래 캐시하지 않음 | 업데이트 감지 |
| 매니페스트(`custom-elements.json` 등) | 버전별 파일 | 문서와 도구 |

- `no-cache`는 저장하지 말라는 뜻이 아니라 쓰기 전에 서버에 확인하라는 뜻입니다. 저장 자체를 막는 것은 `no-store`입니다(자세히는 37편).
- 새 배포 직후 열려 있던 탭이 사라진 옛 해시 파일을 지연 로딩하면 실패합니다. 동적 `import()` 실패를 잡아 새로고침을 안내하고, 옛 파일을 한동안 서버에 남겨 둡니다(자세히는 73편).
- 롤백이 가능하도록 이전 빌드를 보관하고, 기능 플래그로 위험한 변경을 일부 사용자에게만 먼저 열 수 있게 합니다(자세히는 82편의 설정).
- 외부 스크립트에는 SRI와 버전 고정을 적용하고, 앱에는 CSP를 두며, 위반은 보고로 모읍니다(자세히는 63편, 82편).

### 점진적 향상과 최종 점검

- 핵심 내용은 스크립트 없이도 HTML로 읽히고, 미지원 API는 기능 검사로 가르며, 정의가 늦거나 실패해도 화면이 비지 않게 합니다(자세히는 71편).
- 릴리스 전 점검은 표 한 장으로 둡니다.

| 점검 | 통과 기준 |
|------|-----------|
| 크기 | 예산 이내 |
| 접근성 | 자동 검사 위반 없음, 핵심 흐름을 키보드와 스크린 리더로 확인 |
| 테스트 | 단위·통합·E2E 통과, 시각 회귀 차이는 검토 후 승인 |
| 오프라인 | 설치, 오프라인, 복구 시나리오 통과 |
| 호환성 | 지원 브라우저 목록에서 핵심 경로 동작 |
| 운영 준비 | 오류 보고·RUM 수신 확인, 롤백 경로 확인 |

**흔한 실수:**

- 기준 없이 "빠르게", "접근 가능하게"를 목표로 삼는 것입니다. 숫자나 검사로 적지 않은 기준은 지켜지지 않습니다.
- 경고만 하고 막지 않는 검사를 두는 것입니다. 한도를 넘어도 병합되면 예산은 의미가 없습니다.
- 실험실 측정만 보고 사용자 환경의 성능을 안다고 믿는 것입니다.

## 핵심 정리

- 오프라인 PWA는 앱 셸 선캐시, 요청 종류별 전략, IndexedDB 쓰기 큐, 업데이트 알림으로 층을 나누고, 서비스 워커는 `GET`만 다루며 쓰기는 앱이 요청 ID와 순서를 지켜 큐에서 보냅니다.
- 연결 상태는 `navigator.onLine`이 아니라 실제 요청 실패로 판단하고, 새 버전은 사용자가 수락할 때 반영하며, 영속 저장은 요청해도 거부될 수 있습니다.
- 디자인 시스템 패키지는 토큰, 컴포넌트, 어댑터, 문서를 나누고, 속성·이벤트·슬롯·파트·토큰 이름을 공개 API로 보아 변경 종류에 따라 버전을 올리며, 품질 게이트를 CI에서 강제합니다.
- 재사용 패키지는 요소를 프레임워크와 무관하게 두고 어댑터는 값 전달과 이벤트 연결만 하며, 서버에서 가져와도 깨지지 않게 하고, 어댑터는 요소 패키지를 `peerDependencies`로 선언합니다.
- 프로덕션 구조는 기준을 숫자와 규칙으로 파일에 두고, 싼 검사를 앞에 둔 CI에서 막으며, 현장 데이터와 오류 보고로 운영에서 확인하고, 해시 파일은 오래, `index.html`은 재검증하게 캐시합니다.

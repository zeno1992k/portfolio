## Primitive Component

Primitive Component는 네이티브 요소 하나(또는 역할 하나)를 감싸고 비즈니스 로직을 갖지 않는 가장 작은 단위입니다. 버튼, 아이콘, 입력창, 배지가 해당합니다. 다른 컴포넌트가 이 위에 쌓입니다.

```js
class UiButton extends HTMLElement {
  connectedCallback() {
    if (this.shadowRoot) return
    const root = this.attachShadow({ mode: 'open' })
    root.innerHTML =
      '<button part="button"><slot></slot></button>'
  }
}
customElements.define('ui-button', UiButton)
```

- 공개 API는 속성·프로퍼티·이벤트와 슬롯으로 한정하고, 데이터를 가져오거나 앱 상태를 읽지 않습니다.
- 스타일 확장 지점은 CSS 사용자 정의 속성과 `part`로 열어 둡니다(자세히는 23편).
- 접근성은 가능하면 네이티브 요소(`button`)에 맡깁니다(자세히는 27편).

**흔한 실수:** Primitive에 "저장 중이면 비활성"처럼 업무 규칙을 넣는 것입니다. 규칙이 들어가면 재사용할 수 없습니다. 상태는 바깥에서 속성으로 받습니다.

## Compound Component

Compound Component는 여러 컴포넌트가 한 묶음으로만 의미가 있고, 공유 상태를 서로 암묵적으로 나누는 패턴입니다. 사용하는 쪽은 부품을 조립하기만 하고 내부 연결은 하지 않습니다. 탭이 대표적입니다.

```html
<ui-tabs>
  <ui-tab for="a" selected>개요</ui-tab>
  <ui-tab for="b">상세</ui-tab>
  <ui-tab-panel id="a">...</ui-tab-panel>
  <ui-tab-panel id="b" hidden>...</ui-tab-panel>
</ui-tabs>
```

- 부모가 선택 상태의 단일 출처이고, 자식은 `closest('ui-tabs')`로 부모를 찾거나 버블링하는 이벤트로 알립니다(자세히는 25편).
- 부모는 `slotchange`나 `querySelectorAll`로 자식을 찾습니다. 자식이 아직 업그레이드되기 전일 수 있으므로 자식의 메서드를 호출하기 전에 `customElements.whenDefined`를 기다리거나 속성으로 전달합니다.
- 접근성 역할과 키보드 동작은 부품 전체가 지켜야 합니다. WAI-ARIA 탭 패턴은 `tablist`, `tab`, `tabpanel` 역할, `aria-selected`, `aria-controls`, `aria-labelledby` 관계와 화살표·Home·End 키 이동을 정합니다(자세히는 27편, 28편).

**흔한 실수:** 부품을 부모 밖에 단독으로 쓰면 깨지게 만드는 것입니다. 부모가 없으면 조용히 아무것도 하지 않게 하고, 개발 중에는 경고를 남깁니다.

## Container / Presentational 분리

Container는 데이터를 가져오고 상태를 보관하며, Presentational은 받은 값을 그리고 사용자 동작을 이벤트로 알립니다.

| 구분 | Container | Presentational |
|------|-----------|----------------|
| 하는 일 | fetch, 상태 보관, 이벤트 처리 | 값을 화면으로 변환 |
| 입력 | URL, 서비스 객체 | 속성·프로퍼티 |
| 출력 | 하위에 값 전달 | CustomEvent |
| 재사용 | 낮음(앱에 묶임) | 높음 |

```js
// Container: 데이터와 상태
class UserPage extends HTMLElement {
  async connectedCallback() {
    const view = document.createElement('user-card')
    view.user = await fetchUser(this.dataset.id)
    view.addEventListener('follow', () => this.#follow())
    this.replaceChildren(view)
  }
}
```

- Presentational은 같은 입력에는 같은 화면을 그립니다. 그래서 값만 바꿔 가며 단독으로 시험할 수 있습니다.
- 두 계층의 이벤트·속성 흐름은 32편의 데이터 흐름과 같은 방향입니다.

**흔한 실수:** Presentational 안에서 `fetch`를 호출하는 것입니다. 재사용할 때마다 요청이 따라옵니다.

## Headless Component

Headless Component는 상태 전이, 키보드 처리, ARIA 속성 같은 동작만 제공하고 마크업과 스타일은 사용하는 쪽이 정하는 방식입니다. 동작은 DOM을 만들지 않는 객체나 함수로 두고, 화면은 사용자가 붙입니다.

```js
function createDisclosure(trigger, panel) {
  let open = false
  const sync = () => {
    trigger.setAttribute('aria-expanded', String(open))
    panel.hidden = !open
  }
  const toggle = () => { open = !open; sync() }
  trigger.addEventListener('click', toggle)
  sync()
  return { toggle }
}
```

- 사용자는 어떤 요소든 `trigger`와 `panel`로 넘길 수 있습니다. 동작 규칙(`aria-expanded`, `hidden`)만 고정됩니다.
- Presentational과 달리 동작(접근성, 키보드, 포커스)이 컴포넌트의 핵심 가치입니다.
- 표시 책임이 없으므로 디자인 시스템이 달라도 같은 동작을 재사용할 수 있습니다.

**흔한 실수:** 헤드리스를 표방하면서 내부에 스타일 가정을 남기는 것입니다. 특정 클래스명이나 DOM 구조를 요구하면 사실상 헤드리스가 아닙니다.

## Controller / View 분리

Controller는 상태, 전이 규칙, 부수 효과(타이머, 요청)를 소유하는 DOM 없는 객체이고, View는 컨트롤러의 상태를 그리고 입력을 컨트롤러에 전달하는 컴포넌트입니다.

```js
class CounterController extends EventTarget {
  #n = 0
  get value() { return this.#n }
  inc() {
    this.#n++
    this.dispatchEvent(new Event('change'))
  }
}
```

```js
class CounterView extends HTMLElement {
  ctrl = new CounterController()
  #on = () => this.#render()
  connectedCallback() {
    this.ctrl.addEventListener('change', this.#on)
    this.#render()
  }
  disconnectedCallback() {
    this.ctrl.removeEventListener('change', this.#on)
  }
  #render() { this.textContent = this.ctrl.value }
}
```

- 변경 알림은 `EventTarget` 상속으로 만들 수 있습니다(자세히는 31편).
- 구독은 `connectedCallback`에서 하고 `disconnectedCallback`에서 해제합니다(자세히는 18편).
- Container와의 차이: Container는 컴포넌트 트리 안의 요소이고, Controller는 트리와 무관한 객체라서 여러 View가 공유하거나 DOM 없이 시험할 수 있습니다.

## Slot 기반 Composition

Slot 기반 합성은 컴포넌트가 "여기에 외부 내용을 넣을 수 있다"는 확장 지점을 슬롯으로 열어 두고, 사용하는 쪽이 라이트 DOM 자식으로 내용을 채우는 방식입니다(슬롯의 규칙은 22편).

```html
<ui-card>
  <h3 slot="title">제목</h3>
  <p>본문(기본 슬롯)</p>
  <button slot="actions">확인</button>
</ui-card>
```

- 이름 있는 슬롯으로 위치를 구분하고, 슬롯 안의 기본 내용은 아무것도 배정되지 않았을 때 표시됩니다.
- 슬롯에 배정된 노드는 라이트 DOM에 남아 있어서 바깥 문서의 스타일을 받고, 컴포넌트는 `::slotted()`로 제한적으로만 꾸밀 수 있습니다.
- 배정이 바뀌면 `slotchange` 이벤트가 슬롯에서 발생하고, `assignedElements()`로 현재 배정된 요소를 읽습니다.
- `attachShadow({ slotAssignment: 'manual' })`로 만들면 이름 대신 `slot.assign(...nodes)`로 직접 배정합니다. Baseline 2023입니다.

```js
const slot = root.querySelector('slot')
slot.addEventListener('slotchange', () => {
  this.#count = slot.assignedElements().length
})
```

**흔한 실수:** 슬롯 내용이 바뀌는데 `slotchange`로 갱신하지 않고 최초 한 번만 읽는 것입니다. `slotchange`는 요소 자신이 아니라 슬롯에서 발생합니다.

## Renderless 패턴

Renderless 컴포넌트는 화면을 그리지 않고 동작과 데이터만 제공한 뒤, 표시는 자식이나 호출자에게 맡깁니다. 프레임워크의 render props에 해당합니다.

Web Components에서는 두 가지 형태가 있습니다. 하나는 슬롯만 감싸고 자신은 박스를 만들지 않는 요소입니다.

```js
class DataLoader extends HTMLElement {
  connectedCallback() {
    this.style.display = 'contents'
    fetch(this.getAttribute('src'))
      .then((r) => r.json())
      .then((data) => {
        this.dispatchEvent(
          new CustomEvent('loaded', { detail: data }))
      })
  }
}
```

`display: contents`는 요소 자신의 박스를 만들지 않고 자식을 부모의 자식처럼 배치합니다(Baseline 널리 지원). 다만 일부 브라우저가 이 값을 가진 요소를 접근성 트리에서 잘못 제거하는 문제가 MDN에 기록돼 있어서, 의미 있는 역할을 가진 요소에는 쓰지 않습니다.

다른 하나는 렌더 함수를 프로퍼티로 받는 형태입니다.

```js
const list = document.querySelector('item-list')
list.items = [{ id: 1, name: 'A' }]
list.renderItem = (item) => {
  const li = document.createElement('li')
  li.textContent = item.name
  return li
}
```

- 컴포넌트는 순회와 선택 상태 같은 동작을 맡고, 항목 모양은 함수가 정합니다.
- 헤드리스는 "마크업 없이 동작"이고 렌더리스는 "자기 렌더링 없이 하위·호출자의 렌더링을 활용"한다는 점에서 겹칩니다. 헤드리스는 보통 동작 객체를 쓰는 쪽이 주도하고, 렌더리스는 요소 하나가 트리 안에서 동작을 제공합니다.

**흔한 실수:** 렌더 함수가 반환하는 노드에 이벤트 리스너를 달고 정리하지 않는 것입니다. 항목이 다시 그려질 때 이전 노드의 리스너가 남습니다(자세히는 30편).

## Adapter Component

Adapter Component는 호환되지 않는 인터페이스(서드파티 라이브러리, 레거시 위젯)를 우리 컴포넌트 규약(속성·프로퍼티·CustomEvent)으로 변환하는 얇은 컴포넌트입니다. 규약이 바뀌지 않으면 내부 라이브러리를 교체해도 사용하는 쪽은 그대로입니다.

```js
class ChartAdapter extends HTMLElement {
  #chart
  connectedCallback() {
    this.#chart = new ThirdPartyChart(this, {
      onSelect: (p) => this.dispatchEvent(
        new CustomEvent('select', { detail: p.id })),
    })
  }
  set data(v) { this.#chart?.setData(v) }
  disconnectedCallback() { this.#chart.destroy() }
}
```

- 입력은 라이브러리가 받는 형식으로, 출력은 라이브러리의 콜백을 CustomEvent로 변환합니다.
- 라이브러리가 만든 DOM·타이머·리스너는 `disconnectedCallback`에서 정리합니다.
- 외부 라이브러리 객체를 공개 API로 노출하지 않습니다. 노출하면 교체할 때 호환이 깨집니다.

## Wrapper / Facade Component

세 패턴은 비슷해 보이지만 목적이 다릅니다.

| 패턴 | 목적 | 인터페이스 |
|------|------|------------|
| Adapter | 맞지 않는 인터페이스를 변환 | 바뀜 |
| Wrapper | 같은 대상에 기능을 덧붙임 | 그대로 |
| Facade | 여러 부품을 하나의 단순한 입구로 묶음 | 단순해짐 |

Wrapper Component는 슬롯으로 받은 요소를 감싸서 기능(툴팁, 로딩 표시, 오류 경계)을 더하되 감싸진 요소의 사용법은 바꾸지 않습니다.

```html
<ui-tooltip text="저장">
  <button>저장</button>
</ui-tooltip>
```

Facade Component는 자주 함께 쓰는 여러 컴포넌트를 미리 조립한 하나의 고수준 컴포넌트입니다. 예를 들어 `ui-date-field`가 입력창, 팝오버, 달력을 내부에서 조립하고 `value`와 `change`만 노출합니다.

- Facade는 편의를 위한 층이므로 저수준 부품(Compound·Primitive)을 직접 쓰는 길을 막지 않습니다. 사용자가 조립을 바꿔야 할 때 Facade에 옵션을 계속 추가하면 인터페이스가 비대해집니다.
- Wrapper는 감싼 요소의 접근성 의미를 가리지 않아야 합니다. 래퍼가 `role`을 덮어쓰면 안쪽 요소의 의미가 사라집니다.

## Decorator 패턴

Decorator는 기존 요소나 컴포넌트를 수정하거나 상속하지 않고 동작을 덧붙이는 패턴입니다. 원본은 그대로 두고 기능을 겹쳐 쌓을 수 있습니다. 구현 방식은 세 가지입니다.

| 방식 | 예 | 특징 |
|------|----|------|
| 감싸는 요소 | `ui-tooltip` | 구조가 바뀜 |
| 요소를 받아 리스너를 붙이는 함수 | `withLogging(el)` | 구조 변경 없음 |
| 속성 선언 + 레지스트리 | `data-copy` 속성 | 마크업만으로 적용 |

```js
function withClickLog(el, log) {
  const on = (e) => log(e.type, el.id)
  el.addEventListener('click', on)
  return () => el.removeEventListener('click', on)
}
const off = withClickLog(button, console.log)
// 해제는 off()
```

- 데코레이터는 해제 함수를 돌려주어 `disconnectedCallback`에서 정리할 수 있게 합니다.
- 언어 문법의 데코레이터(`@` 표기)와는 다른 개념입니다. 여기서의 Decorator는 객체 합성 패턴입니다.

**흔한 실수:** 같은 요소에 같은 데코레이터를 두 번 적용해 리스너가 중복되는 것입니다. 적용 여부를 `WeakSet`에 기록해 둡니다.

## Component Registry 패턴

브라우저에는 요소 이름과 클래스를 연결하는 레지스트리가 하나 있고, `customElements`가 그것입니다. Component Registry 패턴은 이 등록을 앱이 직접 관리하는 방식입니다. 이름 충돌을 막고, 필요할 때만 등록하고, 접두사를 일괄 적용합니다.

```js
const registry = new Map()
export function register(tag, ctor) {
  if (customElements.get(tag)) return
  customElements.define(tag, ctor)
  registry.set(tag, ctor)
}
export async function lazyDefine(tag, loader) {
  if (customElements.get(tag)) return
  const { default: ctor } = await loader()
  register(tag, ctor)
}
```

- `define()`은 같은 이름이나 같은 생성자가 이미 등록돼 있으면 `NotSupportedError`를, 유효하지 않은 이름이면 `SyntaxError`를 던집니다. 한 문서의 전역 레지스트리에는 이름 하나당 정의 하나만 존재합니다.
- 등록 전에 이미 문서에 있는 요소는 `define()` 시점에 업그레이드됩니다. 그래서 컴포넌트 코드를 늦게 불러오는 지연 정의가 가능합니다(자세히는 17편).
- 다른 컴포넌트가 아직 정의되지 않았을 수 있으면 `customElements.whenDefined(tag)`로 기다립니다.
- 같은 라이브러리의 두 버전이나 두 번 로드된 번들이 같은 이름을 정의하면 충돌합니다. 태그 접두사를 버전이나 팀 단위로 나누거나 위의 `register`처럼 방어합니다.

### 범위 지정 레지스트리

전역 레지스트리 대신 `new CustomElementRegistry()`로 별도 레지스트리를 만들어 Shadow Root에 연결할 수 있습니다. 그 Shadow Root 안에서는 같은 이름을 다른 클래스로 정의해도 충돌하지 않습니다.

```js
const scoped = new CustomElementRegistry()
scoped.define('x-item', LocalItem)
const root = host.attachShadow({
  mode: 'open',
  customElementRegistry: scoped,
})
```

- 지원 상태: Chrome·Edge 146, Safari 26. Firefox는 아직 지원하지 않아서 Baseline이 아닙니다. 점진적 향상으로 다루고 전역 레지스트리 방식을 대체 경로로 둡니다.
- 범위 지정 레지스트리에서는 `define()`의 `extends` 옵션을 쓸 수 없습니다.
- `customElementRegistry`에 전역 레지스트리를 넘기면 `NotSupportedError`입니다.

## Composition over Inheritance

상속(is-a)은 부모의 구현을 자식이 그대로 이어받아 결합이 강하고, 합성(has-a)은 필요한 기능을 가진 객체를 소유해서 위임하므로 결합이 느슨합니다. 컴포넌트 설계에서는 합성을 먼저 고려합니다.

| 기준 | 상속 | 합성 |
|------|------|------|
| 관계 | is-a | has-a |
| 변경 파급 | 부모를 바꾸면 모든 자식에 영향 | 위임 대상만 교체 |
| 다중 기능 | 단일 상속이라 한계 | 여러 객체를 조합 |
| 런타임 변경 | 어려움 | 가능 |

- 커스텀 요소 클래스는 `HTMLElement`(또는 내장 요소) 하나만 확장할 수 있어서 여러 기능을 섞으려면 합성이나 믹스인이 필요합니다.
- 상속 체계가 깊어지면 `connectedCallback`처럼 재정의되는 생명주기 훅에서 `super` 호출을 빠뜨려 부모 동작이 사라집니다.
- 상속이 맞는 경우: 진짜 is-a 관계이고 기반 클래스가 확장을 전제로 설계됐을 때(예: 팀 공통 `BaseElement`). 이때도 계층은 얕게 유지합니다.
- 내장 요소를 상속하는 방식(customized built-in)은 Safari가 지원하지 않습니다. 내장 요소의 동작이 필요하면 상속 대신 감싸는 합성(`<button>`을 Shadow DOM 안에 두기)이 안전합니다.

## 믹스인 함수로 클래스 기능 합치기

믹스인은 슈퍼클래스를 받아 기능을 더한 서브클래스를 반환하는 함수입니다. 여러 믹스인을 겹쳐 하나의 클래스에 기능을 합칩니다.

```js
const Disableable = (Base) => class extends Base {
  get disabled() { return this.hasAttribute('disabled') }
  set disabled(v) { this.toggleAttribute('disabled', !!v) }
}
const Focusable = (Base) => class extends Base {
  focusFirst() { this.querySelector('[tabindex]')?.focus() }
}
class MyField extends Focusable(Disableable(HTMLElement)) {}
customElements.define('my-field', MyField)
```

- 믹스인을 적용할 때마다 새 클래스가 만들어집니다. 한 번 만든 결과를 재사용하지 않으면 같은 믹스인이 여러 클래스로 늘어납니다.
- 같은 이름의 멤버가 둘 이상의 믹스인에 있으면 나중에 적용한 쪽이 이깁니다. 이름이 겹치지 않게 짓습니다.
- 생명주기 훅을 믹스인에서 재정의할 때는 `super.connectedCallback?.()`를 호출해 연쇄를 끊지 않습니다.
- 믹스인은 클래스가 그 기능 자체가 되는 is-a 합성이고, 아래 컨트롤러는 has-a 합성입니다. Lit 문서도 두 방식을 이렇게 구분합니다.

## 호스트에 붙는 컨트롤러 객체

컨트롤러 객체 패턴은 기능을 컴포넌트와 분리된 객체에 넣고, 컴포넌트(호스트)가 그것을 소유해 생명주기 이벤트를 전달하는 방식입니다. 믹스인과 달리 호스트의 클래스 체인이 바뀌지 않고, 한 호스트가 여러 컨트롤러를 가질 수 있습니다.

Lit의 `ReactiveController`가 이 패턴의 표준적인 구현입니다. 컨트롤러는 호스트를 생성자로 받아 `host.addController(this)`로 등록하고, 선택적으로 `hostConnected`, `hostDisconnected`, `hostUpdate`, `hostUpdated` 콜백을 정의합니다. 상태가 바뀌면 `host.requestUpdate()`로 갱신을 요청합니다.

같은 구조를 순수한 `HTMLElement`에서 직접 만들 수도 있습니다.

```js
class ControlledElement extends HTMLElement {
  #ctrls = new Set()
  addController(c) {
    this.#ctrls.add(c)
    if (this.isConnected) c.hostConnected?.()
  }
  connectedCallback() {
    for (const c of this.#ctrls) c.hostConnected?.()
  }
  disconnectedCallback() {
    for (const c of this.#ctrls) c.hostDisconnected?.()
  }
}
```

```js
class ResizeController {
  constructor(host) {
    this.host = host
    host.addController(this)
  }
  hostConnected() {
    this.ro = new ResizeObserver(() => this.host.render())
    this.ro.observe(this.host)
  }
  hostDisconnected() { this.ro.disconnect() }
}
```

- 리스너·옵저버 등록과 해제를 컨트롤러가 짝지어 관리하므로, 호스트 코드에 정리 로직이 흩어지지 않습니다.
- 앞의 Controller / View 분리와의 차이: 그쪽은 상태를 소유하는 객체를 뷰가 구독하는 구조이고, 여기서는 컨트롤러가 호스트의 생명주기에 붙어서 호스트를 움직입니다.

**흔한 실수:** `hostConnected`에서 만든 자원을 `hostDisconnected`에서 해제하지 않는 것입니다. 요소가 떼였다 다시 붙을 수 있으므로(자세히는 18편) 연결 때마다 만들고 해제 때마다 정리하는 짝을 지킵니다.

## 핵심 정리

- Primitive는 업무 로직 없는 최소 단위이고, Compound는 부모가 상태를 소유하고 자식들이 한 묶음으로 동작하는 구성입니다.
- Container / Presentational과 Controller / View는 데이터·상태 책임과 표시 책임을 나누고, Headless와 Renderless는 표시 책임을 쓰는 쪽에 넘깁니다.
- Adapter는 인터페이스를 변환하고, Wrapper는 같은 인터페이스에 기능을 더하며, Facade는 여러 부품을 단순한 입구로 묶습니다. Decorator는 상속 없이 동작을 겹칩니다.
- 전역 레지스트리는 이름당 정의 하나만 허용하므로 `customElements.get`으로 방어하고 필요할 때 지연 정의합니다. 범위 지정 레지스트리는 Chrome·Edge 146, Safari 26부터이며 Baseline이 아닙니다.
- 기능 공유는 상속보다 합성을 먼저 고려하며, 믹스인은 클래스에 기능을 합치고 컨트롤러는 호스트가 소유한 객체로 기능을 위임합니다.

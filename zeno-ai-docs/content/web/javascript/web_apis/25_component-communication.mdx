## 부모 → 자식 Property 전달

부모가 자식 요소 객체의 프로퍼티에 값을 대입해 데이터를 내려보내는 방식입니다. 값의 타입에 제한이 없어서 객체, 배열, 함수, DOM 노드를 그대로 넘길 수 있습니다.

```js
const list = document.querySelector('item-list')
list.items = [{ id: 1, label: 'A' }, { id: 2, label: 'B' }]
list.selected = new Set([1])
```

자식은 프로퍼티를 접근자(setter)로 정의하고, 값이 바뀌면 다시 그립니다(공개 프로퍼티 설계는 19편).

```js
class ItemList extends HTMLElement {
  #items = []
  set items(value) {
    this.#items = value
    this.#render()
  }
  get items() { return this.#items }
  #render() { /* shadow DOM 갱신 */ }
}
```

- 프로퍼티는 HTML 마크업에 쓸 수 없습니다. 자바스크립트로만 설정합니다.
- 객체와 배열은 참조가 전달되므로 부모가 내부를 바꿔도 대입이 일어나지 않아 setter가 호출되지 않습니다. 새 값을 만들어 다시 대입해야 변경이 전달됩니다.
- 요소가 정의되기 전에 대입한 프로퍼티는 요소 객체 자신의 프로퍼티로 남고, 나중에 클래스의 setter가 적용된 뒤에도 그 값이 setter보다 앞서 조회됩니다. 업그레이드 시점에 값을 꺼내 지우고 setter로 다시 대입하는 처리가 필요합니다(업그레이드는 17편, 18편).

```js
connectedCallback() {
  for (const key of ['items', 'selected']) {
    if (Object.hasOwn(this, key)) {
      const value = this[key]
      delete this[key]
      this[key] = value
    }
  }
}
```

## 부모 → 자식 Attribute 전달

HTML 어트리뷰트로 값을 내려보내는 방식입니다. 마크업에 바로 쓸 수 있고, `setAttribute`로 바꾸면 자식이 `attributeChangedCallback`으로 변경을 받습니다. 받으려면 `observedAttributes`에 이름을 적어야 합니다.

```js
class UserBadge extends HTMLElement {
  static observedAttributes = ['name', 'size']
  attributeChangedCallback(name, oldValue, newValue) {
    // newValue는 문자열 또는 null (제거됨)
  }
}
```

- 어트리뷰트 값은 항상 문자열입니다. 숫자·불리언은 자식이 변환해야 합니다.
- 불리언은 값이 아니라 존재 여부로 표현합니다(`hidden`, `disabled`처럼). 어트리뷰트가 있으면 참, 없으면 거짓이고 `disabled="false"`도 참입니다.
- 객체나 배열은 JSON 문자열로 넘길 수 있지만 매번 파싱 비용이 들고 큰 데이터에는 맞지 않습니다.
- 파싱 중 어트리뷰트가 이미 있으면 `attributeChangedCallback`이 요소가 업그레이드될 때 한 번씩 호출됩니다.

두 방식은 대응하는 쌍으로 만들고 방향을 정해 둡니다. 보통 프로퍼티가 값의 원천이고, 단순한 값은 어트리뷰트로 반영(reflect)합니다.

| 항목 | Property | Attribute |
|------|----------|-----------|
| 값의 타입 | 제한 없음 | 문자열 |
| 마크업에서 지정 | 불가 | 가능 |
| CSS 선택자 | 사용 불가 | `[name]`으로 선택 가능 |
| 변경 감지 | setter | `attributeChangedCallback` |
| 적합한 값 | 객체, 배열, 함수, 노드 | 문자열, 숫자, 불리언, 열거 값 |

```js
set size(value) { this.setAttribute('size', value) }
get size() { return this.getAttribute('size') ?? 'md' }
```

한쪽이 다른 쪽을 갱신하는 코드가 서로를 다시 호출하지 않도록, 값이 같으면 갱신을 건너뜁니다.

## 자식 → 부모 CustomEvent

자식은 부모를 직접 호출하지 않고 이벤트를 발생시킵니다. 자식은 누가 듣는지 모르고, 부모는 필요한 이벤트만 구독합니다. 데이터가 필요하면 `CustomEvent`의 `detail`에 담습니다.

```js
this.dispatchEvent(
  new CustomEvent('item-select', {
    detail: { id: 7 },
    bubbles: true,
  }),
)
```

`new CustomEvent(type, options)`에서 `detail`의 기본값은 `null`이고 `bubbles`, `cancelable`, `composed`의 기본값은 모두 `false`입니다. 부모는 `addEventListener`로 듣습니다.

```js
list.addEventListener('item-select', (e) => {
  console.log(e.detail.id) // 7
})
```

- `cancelable: true`이면 리스너가 `preventDefault()`로 기본 동작을 막을 수 있고, `dispatchEvent`는 막혔을 때 `false`를 반환합니다. 변경을 확정하기 전에 부모의 동의를 구하는 흐름에 씁니다.
- `dispatchEvent`는 동기로 모든 리스너를 실행한 뒤 반환합니다.
- 일반 `Event`로도 보낼 수 있지만 데이터를 실을 `detail`이 필요하면 `CustomEvent`를 씁니다. 이벤트 시스템 자체는 07편에서 다룹니다.

## Event bubbling 기반 통신

`bubbles: true`인 이벤트는 발생한 요소에서 조상 쪽으로 올라갑니다. 중간에 어떤 컴포넌트가 끼어 있어도 상관없이 상위 요소 한 곳에서 받을 수 있어서, 부모가 자식마다 리스너를 달 필요가 없습니다.

```js
document.querySelector('item-list').addEventListener(
  'item-select',
  (e) => console.log(e.target.localName), // 'list-item'
)
```

- 항목이 많은 목록에서는 컨테이너 한 곳에 리스너를 달고 `event.target`으로 발생 위치를 구분하는 이벤트 위임을 씁니다(07편).
- 자식이 Shadow DOM 안에 있어도 `bubbles`와 `composed`가 모두 참이면 호스트 밖으로 올라가고, 바깥 리스너가 보는 `event.target`은 호스트로 바뀝니다(리타깃팅). 내부 구조는 외부에 드러나지 않습니다.
- 어느 지점에서 `stopPropagation()`을 호출하면 그 위쪽은 이벤트를 받지 못합니다. 통신용 이벤트를 중간에서 멈추면 상위 컴포넌트가 반응하지 않는 원인이 됩니다.

```js
// 리스너가 컴포넌트 자신에게 있을 때
this.addEventListener('item-select', (e) => {
  if (e.target === this) return // 내가 보낸 이벤트는 무시
})
```

## composed 이벤트와 Shadow Boundary

`composed`는 이벤트가 Shadow DOM 경계를 넘을 수 있는지를 정합니다. 이벤트가 shadow 트리 안에서 발생했을 때 경계를 넘어 바깥 트리까지 전파되려면 `composed`와 `bubbles`가 둘 다 참이어야 합니다.

| 이벤트 | composed 기본값 |
|--------|-----------------|
| 사용자 입력으로 브라우저가 발생시킨 UI 이벤트(click, pointerdown, keydown 등) | `true` |
| 그 밖의 대부분의 이벤트 | `false` |
| `new CustomEvent()`, `new Event()`로 만든 이벤트 | `false` |

```js
// shadow 트리 안의 버튼에서 호스트 밖으로 알리기
button.dispatchEvent(
  new CustomEvent('item-select', {
    detail: { id: 7 },
    bubbles: true,
    composed: true,
  }),
)
```

- `composed: false`인 이벤트는 shadow 루트에서 멈춥니다. 같은 shadow 트리 안의 요소만 듣고, 호스트와 바깥은 받지 못합니다.
- 호스트 자신에서 `this.dispatchEvent`로 보낸 이벤트는 호스트가 바깥 트리에 속하므로 `composed`가 거짓이어도 바깥 리스너가 받습니다. `composed`가 필요한 경우는 shadow 트리 안쪽 요소에서 발생시킬 때입니다.
- 컴포넌트의 공개 이벤트는 호스트에서 한 번 발생시키는 것이 원칙입니다. 내부 이벤트를 `composed: true`로 그대로 내보내면 내부 요소 구조가 바깥에서 관찰됩니다.
- `event.composedPath()`는 전파 경로를 배열로 돌려줍니다. 열린(open) shadow 루트는 내부 노드가 포함되고, 닫힌(closed) shadow 루트는 내부 노드가 빠집니다. 열림·닫힘은 `composedPath()`에 보이는 범위를 바꿀 뿐 이벤트가 경계를 넘는지는 `composed`가 정합니다.
- click 같은 UI 이벤트는 기본적으로 composed입니다. 바깥에서 `event.target`을 보면 호스트로 보이므로 내부 어느 요소가 눌렸는지는 `composedPath()[0]`으로 확인합니다(열린 루트일 때).

## 형제 컴포넌트 통신

형제 컴포넌트는 서로를 직접 알지 못하게 두고, 공통 부모가 중계합니다. 한 형제가 이벤트를 올리면 부모가 받아서 다른 형제의 프로퍼티나 어트리뷰트로 내려보냅니다(상태 끌어올리기).

```js
const filter = document.querySelector('search-filter')
const results = document.querySelector('result-list')

filter.addEventListener('filter-change', (e) => {
  results.query = e.detail.query // 부모가 중계
})
```

```text
search-filter ──이벤트──▶ 부모(중계) ──프로퍼티──▶ result-list
```

- 데이터는 위로 한 번 올라갔다가 아래로 내려갑니다. 각 컴포넌트는 부모와만 통신합니다.
- 중계 코드는 두 컴포넌트를 아는 쪽(페이지, 상위 컴포넌트)에 둡니다. 형제 안에 상대의 선택자나 이름을 적지 않습니다.
- 부모가 멀리 있거나 중계할 컴포넌트가 많아지면 공유 상태나 Context를 씁니다. 다만 형제가 직접 서로를 호출하는 구조는 피합니다.

```js
// ❌ 형제가 서로의 위치를 안다
this.parentElement.querySelector('result-list').query = q
```

## 공유 상태 Store

여러 컴포넌트가 같은 데이터를 읽고 바꿔야 할 때 상태를 컴포넌트 밖의 한 객체(store)에 두고 각자 구독하게 합니다. 컴포넌트는 서로 직접 통신하지 않고 store만 압니다.

```js
const store = {
  state: { count: 0 },
  listeners: new Set(),
  set(patch) {
    this.state = { ...this.state, ...patch }
    this.listeners.forEach((fn) => fn(this.state))
  },
  subscribe(fn) {
    this.listeners.add(fn)
    return () => this.listeners.delete(fn)
  },
}
```

- 상태를 갱신할 때 새 객체를 만들어 대입하면 변경 여부를 참조 비교로 판별할 수 있습니다.
- 컴포넌트는 `connectedCallback`에서 구독하고 `disconnectedCallback`에서 구독 해제 함수를 호출합니다. 해제하지 않으면 DOM에서 제거된 컴포넌트가 store에 매달려 메모리에 남고 계속 갱신됩니다.

```js
connectedCallback() {
  this.unsub = store.subscribe((s) => this.#render(s))
}
disconnectedCallback() { this.unsub?.() }
```

- store는 모듈 스코프의 단일 객체라서 전역 상태와 같은 성질을 가집니다. 컴포넌트가 특정 store에 묶여 재사용성이 떨어지고, 테스트에서 상태가 남을 수 있습니다.
- 모듈 하나가 한 번만 평가되므로 같은 URL의 모듈을 import한 모든 곳이 같은 store를 공유합니다. 상태 설계 전체는 31편, 데이터 흐름은 32편에서 다룹니다.

## Context 패턴 설계

Context는 컴포넌트 트리의 조상이 값을 제공하고, 후손이 중간 컴포넌트를 거치지 않고 가장 가까운 조상의 값을 가져오는 패턴입니다. 테마, 로케일, 인증 정보처럼 트리 전체가 공유하되 범위마다 다를 수 있는 값에 맞습니다.

| 항목 | 공유 상태 Store | Context |
|------|------------------|---------|
| 값의 범위 | 전역 한 곳 | 제공자의 하위 트리 |
| 같은 값의 다중 인스턴스 | 어렵다 | 하위 트리마다 다른 제공자를 둘 수 있다 |
| 컴포넌트가 아는 것 | store 객체 | 컨텍스트 키 |
| 중간 컴포넌트 | 무관 | 값을 몰라도 된다(props 전달 불필요) |

설계에서 정할 것은 세 가지입니다.

- **키:** 어떤 값을 요청하는지 나타내는 식별자. 문자열보다 `Symbol`이나 모듈에서 내보낸 객체가 충돌하지 않습니다.
- **제공자:** 값을 갖고 요청에 응답하는 조상.
- **소비자:** 연결되는 시점에 요청하고 값이 바뀌면 갱신하는 후손.

DOM 이벤트가 조상 방향으로 올라가는 성질을 이용하면 별도 라이브러리 없이 구현할 수 있고, 그 규약이 다음 절의 프로토콜입니다. 제공자가 요소의 위치(트리)에 묶여 있어서, 요소를 다른 위치로 옮기면 다른 제공자의 값을 받습니다.

## Context Community Protocol (context-request 이벤트)

Context Community Protocol은 Web Components Community Group가 정리한 규약으로, 라이브러리가 달라도 소비자와 제공자가 호환되게 하는 이벤트 약속입니다. 표준(WHATWG·W3C)이 아니라 커뮤니티 프로토콜입니다. 핵심은 소비자가 `context-request` 이벤트를 발생시키고, 제공자가 이를 가로채 응답하는 것입니다.

이벤트는 `bubbles: true`, `composed: true`로 발생합니다. 필드는 세 개입니다.

| 필드 | 뜻 |
|------|-----|
| `context` | 요청하는 값의 키. `===`로 비교한다 |
| `callback` | 제공자가 값을 넘겨 호출하는 함수 |
| `subscribe` | 참이면 값이 바뀔 때마다 계속 받겠다는 뜻 |

```js
class ContextRequestEvent extends Event {
  constructor(context, callback, subscribe) {
    super('context-request', {
      bubbles: true,
      composed: true,
    })
    this.context = context
    this.callback = callback
    this.subscribe = subscribe
  }
}
```

소비자는 연결될 때 이벤트를 발생시킵니다.

```js
connectedCallback() {
  this.dispatchEvent(
    new ContextRequestEvent(themeKey, (theme, off) => {
      this.unsubscribe = off
      this.#apply(theme)
    }, true),
  )
}
```

제공자는 자기 요소에서 `context-request`를 듣고, 키가 맞으면 이벤트를 멈추고 콜백을 호출합니다.

```js
provider.addEventListener('context-request', (e) => {
  if (e.context !== themeKey) return
  e.stopImmediatePropagation()
  e.callback(currentTheme, unsubscribe)
})
```

- 프로토콜은 제공자가 요청을 처리하기로 하면 즉시 `stopImmediatePropagation()`을 호출하도록 요구합니다. 더 위의 제공자나 같은 요소의 다른 리스너가 같은 요청에 중복 응답하지 않게 하기 위해서입니다.
- 콜백은 값이 있으면 동기로 호출합니다. 소비자는 `dispatchEvent`가 돌아온 시점에 값이 이미 들어와 있을 수 있습니다.
- `subscribe`가 참이면 제공자가 콜백을 보관했다가 값이 바뀔 때마다 다시 호출할 수 있고, 콜백의 두 번째 인수로 구독 해제 함수를 넘깁니다. 소비자는 `disconnectedCallback`에서 이 함수를 호출합니다.
- `subscribe`가 거짓이면 제공자는 콜백을 보관하면 안 됩니다. 한 번만 값을 받는 요청입니다.
- 응답하는 제공자가 없으면 이벤트는 문서까지 올라가도 아무도 처리하지 않고 콜백은 호출되지 않습니다. 소비자는 기본값을 따로 가져야 합니다.
- 이벤트가 `composed`이므로 소비자가 Shadow DOM 안에 있어도 호스트 바깥의 제공자에 닿습니다.

## DOM을 이용한 느슨한 결합

컴포넌트끼리 클래스나 모듈을 import하지 않고 DOM이 제공하는 관계와 규약만으로 연결하면 결합이 느슨해집니다. 쓸 수 있는 수단은 다음과 같습니다.

| 수단 | 방식 |
|------|------|
| 이벤트 | 알리는 쪽은 듣는 쪽을 모른다 |
| 슬롯과 자식 요소 | 부모가 자식 요소를 넣고, 컴포넌트는 `slotchange`로 구성을 읽는다(22편) |
| ID 참조 어트리뷰트 | 다른 요소의 `id`를 문자열로 지정한다(`for`, `popovertarget`처럼) |
| 조상 탐색 | `closest('tab-group')`으로 상위 컨테이너를 찾는다 |
| 어트리뷰트·CSS 사용자 정의 속성 | 값은 문자열로, 표현은 CSS로 주고받는다 |

```js
// ID 참조: 대상의 클래스가 아니라 id만 안다
const target = this.getRootNode().getElementById(
  this.getAttribute('for'),
)
target?.setAttribute('hidden', '')
```

- `getRootNode()`로 자신이 속한 트리(문서 또는 shadow 루트)에서 찾습니다. `document.getElementById`는 shadow 안의 요소를 찾지 못합니다.
- 상대가 `tab-panel` 같은 특정 태그여야 한다고 가정하면 결합이 생깁니다. 필요한 최소한(어트리뷰트, 메서드 이름)만 약속하고 그 약속을 문서화합니다.
- 상대 요소가 아직 정의되지 않았을 수 있으므로 `customElements.whenDefined(name)`으로 기다리거나 존재 여부를 확인합니다(자세히는 17편).
- Shadow 경계는 ID 참조를 막습니다. 다른 트리의 요소를 `id`로 가리킬 수 없다는 점은 27편에서 접근성 관점으로 다시 다룹니다.

## Imperative handle / public method

선언적으로 표현하기 어려운 동작은 요소의 public method로 호출합니다. 부모가 요소 참조를 잡고 직접 메서드를 부르는 방식입니다.

```js
class MediaPlayer extends HTMLElement {
  play() { /* 재생 시작 */ }
  pause() { /* 일시정지 */ }
  seek(seconds) { /* 위치 이동 */ }
}
player.seek(30)
```

- `focus()`, `click()`, `showModal()`, `scrollIntoView()`처럼 기본 요소도 같은 형태를 씁니다. 일회성 명령과 결과를 받아야 하는 호출에 맞습니다.
- 상태를 메서드로 바꾸게 하면(`setOpen(true)`) 같은 상태를 프로퍼티와 어트리뷰트로도 바꿀 수 있어 출처가 여럿이 됩니다. 지속되는 상태는 프로퍼티·어트리뷰트로, 동작(행위)은 메서드로 나눕니다.
- 메서드는 요소가 연결되어 있고 정의가 끝난 뒤에만 안전합니다. 정의 전에 호출하면 `TypeError`입니다. 호출 전에 `customElements.whenDefined`로 확인합니다.
- 메서드가 많아지는 것은 컴포넌트 경계가 큰 신호입니다. 공개 표면 설계는 19편에서 다룹니다.

| 구분 | 선언적(프로퍼티·어트리뷰트·이벤트) | 명령적(메서드) |
|------|------------------------------------|----------------|
| 표현하는 것 | 상태, 변경 알림 | 동작, 명령 |
| 타이밍 | 값이 바뀌면 컴포넌트가 반응 | 호출한 시점에 실행 |
| 반환값 | 없음 | 있을 수 있음 |

## 전역 이벤트 남용 피하기

`window`나 `document`에 커스텀 이벤트를 발생시키고 듣는 방식은 컴포넌트가 어디에 있든 통신할 수 있어서 편하지만, 규모가 커지면 문제가 됩니다.

- 누가 보내고 누가 듣는지 코드에서 추적하기 어렵습니다. 전역에 퍼진 암묵적 계약입니다.
- 이벤트 이름이 전역 공간에서 충돌합니다. 다른 컴포넌트나 라이브러리가 같은 이름을 쓰면 오동작합니다.
- 범위가 없습니다. 같은 컴포넌트가 두 개 있으면 한쪽의 이벤트를 양쪽이 모두 받습니다.
- 리스너가 `window`에 남습니다. 컴포넌트가 제거될 때 `removeEventListener`를 하지 않으면 누수와 중복 실행이 생깁니다.

```js
// ❌ 전역 이벤트로 형제에게 알림
window.dispatchEvent(new CustomEvent('cart-change'))

// ✅ 가장 가까운 요소에서 올려 보내고 부모가 중계
this.dispatchEvent(
  new CustomEvent('cart-change', { bubbles: true }),
)
```

- 기본은 이벤트를 발생한 요소에서 올려 보내고(버블링) 필요한 조상이 듣는 것입니다.
- 전역 이벤트가 맞는 경우는 문서 전체에 속한 사건(`resize`, `online`, `visibilitychange`, `popstate`)이나 앱 전체 알림 하나입니다. 이때도 이름에 접두어를 붙이고, 리스너는 `connectedCallback`에서 달고 `disconnectedCallback`에서 해제하며, `AbortController`의 signal로 한꺼번에 정리할 수 있습니다(자세히는 07편).

```js
connectedCallback() {
  this.ac = new AbortController()
  window.addEventListener('online', () => this.#sync(), {
    signal: this.ac.signal,
  })
}
disconnectedCallback() { this.ac.abort() }
```

## 이벤트 이름과 detail 설계 규칙

이벤트는 컴포넌트의 공개 API입니다. 이름과 `detail`의 모양을 한 번 정하면 바꾸기 어려우므로 규칙을 정해 둡니다.

**이름**

- 소문자와 하이픈으로 씁니다(`item-select`). 대소문자를 구분하므로 하나로 통일합니다.
- 네이티브 이벤트와 이름이 겹치면 안 됩니다. `click`, `change`, `input`을 같은 이름의 커스텀 이벤트로 재정의하면 네이티브와 구분이 안 됩니다.
- 조직의 접두어를 붙여 충돌을 줄입니다(`ui-item-select`).
- 일어난 일을 과거형·명사형으로 씁니다(`item-select`, `value-change`). 컴포넌트는 알리기만 하고 부모가 무엇을 할지는 이름에 넣지 않습니다.
- 값이 바뀌기 전에 승인을 받는 이벤트는 `before-` 같은 접두어와 `cancelable: true`를 씁니다.

**detail**

- 객체로 만들어 필드에 이름을 붙입니다. `detail: 7`보다 `detail: { id: 7 }`가 필드를 추가할 때 호환을 깨지 않습니다.
- 직렬화 가능한 최소 데이터를 넣습니다. 내부 DOM 요소나 내부 상태 객체를 그대로 넣으면 내부 구조가 공개 계약이 됩니다.
- 값 형태(타입)를 문서화합니다. 컴포넌트 문서에 이벤트 이름, 발생 시점, `detail`, `bubbles`·`composed`·`cancelable` 여부를 한 곳에 적습니다.

```js
// ✅ 안정적인 계약
new CustomEvent('value-change', {
  detail: { value: 3, previous: 2 },
  bubbles: true,
  composed: true,
})
```

- `change`나 `input`처럼 네이티브 이벤트를 흉내 낼 때는 발생 시점과 `bubbles`·`composed` 값을 네이티브와 맞춥니다. 폼 컨트롤은 26편에서 다룹니다.
- 이벤트는 상태가 바뀐 뒤에 발생시킵니다. 리스너가 호출될 때 요소의 프로퍼티가 이미 새 값이어야 합니다.

## 이벤트와 콜백 프로퍼티의 선택 기준

통신을 `onselect` 같은 함수 프로퍼티(콜백)로도 만들 수 있습니다. 부모가 자식 프로퍼티에 함수를 넘기고 자식이 필요할 때 호출합니다.

```js
// 콜백 프로퍼티
list.onItemSelect = (id) => console.log(id)

// 자식 내부
this.onItemSelect?.(7)
```

| 기준 | 이벤트 | 콜백 프로퍼티 |
|------|--------|---------------|
| 리스너 수 | 여러 개를 달 수 있다 | 하나(대입하면 덮어쓴다) |
| 버블링·위임 | 가능 | 불가 |
| 취소(`preventDefault`) | 가능 | 반환값으로 약속해야 한다 |
| 반환값 사용 | 어렵다 | 가능(검증 함수 등) |
| 호출 대상 | 모르는 상대에게 방송 | 넘겨준 한 상대 |

- 웹 플랫폼의 관례는 이벤트입니다. 네이티브 요소는 모두 이벤트로 알리고, 외부 도구(프레임워크 바인딩, 이벤트 위임)와도 맞습니다. 사용자 상호작용과 상태 변경 알림은 이벤트로 설계합니다.
- 콜백은 자식이 부모에게서 값을 되돌려 받아야 할 때(`filter(item) 함수`, 비교 함수, 렌더링 함수) 씁니다. 이때 콜백은 알림이 아니라 정책을 주입하는 입력입니다.
- 둘을 같이 제공할 때는 같은 계약으로 연결하고 이벤트를 기본으로 합니다.

## EventTarget을 상속한 서비스 객체

`EventTarget`은 `new`로 만들 수 있는 생성자이고 상속할 수 있습니다(2020년 9월부터 널리 지원). 이를 상속한 일반 객체는 DOM 노드가 아니면서도 `addEventListener`, `removeEventListener`, `dispatchEvent`를 가집니다. 컴포넌트 밖의 서비스(상태, 네트워크 연결, 인증)를 구독 가능한 객체로 만들 때 씁니다.

```js
class Cart extends EventTarget {
  #items = []
  add(item) {
    this.#items = [...this.#items, item]
    this.dispatchEvent(
      new CustomEvent('change', { detail: this.#items }),
    )
  }
  get items() { return this.#items }
}
export const cart = new Cart()
```

컴포넌트는 직접 구독하고 연결이 끊기면 해제합니다.

```js
connectedCallback() {
  this.ac = new AbortController()
  cart.addEventListener(
    'change',
    (e) => this.#render(e.detail),
    { signal: this.ac.signal },
  )
}
disconnectedCallback() { this.ac.abort() }
```

- 직접 만든 구독 목록(`Set`)과 비교해, DOM 이벤트 API를 그대로 쓰므로 `once`, `signal` 옵션과 동일한 사용법을 공유하고 별도의 규칙을 배울 필요가 없습니다.
- 이 객체는 DOM 트리에 없으므로 버블링·캡처링이 없습니다. 이벤트는 그 객체의 리스너에게만 전달됩니다.
- 앞의 공유 상태 Store와 같은 구조이며, store에 이벤트 인터페이스를 입힌 형태입니다. 컴포넌트는 이 서비스를 import하거나 Context 프로토콜로 받습니다. 후자는 컴포넌트가 서비스 모듈에 직접 묶이지 않습니다.
- `EventTarget`은 웹 워커에서도 쓸 수 있어서 같은 서비스 구조를 DOM 없는 환경에도 둘 수 있습니다.

## 핵심 정리

- 데이터는 아래로(프로퍼티·어트리뷰트), 알림은 위로(이벤트)가 기본입니다. 객체·함수는 프로퍼티로, 문자열 값은 어트리뷰트로 보내고 어트리뷰트는 `observedAttributes`에 적어야 감지됩니다.
- 이벤트가 Shadow 경계를 넘으려면 `bubbles`와 `composed`가 모두 참이어야 하고, `CustomEvent`의 `composed` 기본값은 거짓입니다. 호스트에서 직접 발생시키면 `composed`가 필요 없습니다.
- 형제는 부모가 중계하고, 범위가 넓으면 공유 상태 Store나 Context로 해결합니다. Context Community Protocol은 `context-request` 이벤트로 소비자와 제공자를 느슨하게 잇습니다.
- 동작은 public method, 상태는 프로퍼티·어트리뷰트, 알림은 이벤트로 나누고 전역 이벤트는 문서 전체의 사건에만 씁니다.
- 이벤트 이름과 `detail`은 공개 API입니다. 소문자 하이픈 이름과 객체 형태 `detail`로 안정적인 계약을 만듭니다.

## CSSStyleSheet

`CSSStyleSheet`는 스타일시트 하나를 나타내는 CSSOM 객체입니다. `style`이나 `link` 요소가 만드는 시트도 이 인터페이스이고, `new CSSStyleSheet()`로 JavaScript에서 직접 만든 시트를 **constructed stylesheet**라고 합니다. 이 방식을 Constructable Stylesheets라고 부르며, 문서와 여러 shadow root에 공유할 수 있습니다. Baseline 2023, 널리 지원됩니다.

```js
const sheet = new CSSStyleSheet({ media: 'screen' })
sheet.replaceSync('p { color: teal }')
sheet.insertRule('a { color: navy }', 0)
sheet.cssRules.length // 2
```

생성자 옵션은 다음과 같습니다.

| 옵션 | 기본값 | 효과 |
|------|--------|------|
| `media` | 빈 목록 | 시트가 적용되는 미디어 조건(문자열 또는 `MediaList`) |
| `disabled` | `false` | `true`이면 만들어졌지만 적용되지 않음 |
| `baseURL` | 문서의 기준 URL | 시트 안 상대 `url()`을 해석하는 기준 |

- constructed stylesheet는 소유 노드가 없습니다(`ownerNode`가 `null`). DOM의 어느 요소에도 붙지 않고, 어느 root가 `adoptedStyleSheets`로 채택할 때 적용됩니다.
- 규칙은 `cssRules`로 읽고, `insertRule(rule, index)`와 `deleteRule(index)`로 바꿉니다. `replace()`와 `replaceSync()`는 전체를 교체합니다.
- `style`·`link` 요소가 만든 시트는 constructed가 아니므로 `replace()` 계열을 쓰면 `NotAllowedError`가 발생하고, 채택도 할 수 없습니다.

## replace와 replaceSync

두 메서드는 시트의 내용 전체를 새 CSS 텍스트로 교체합니다.

| 항목 | `replaceSync(text)` | `replace(text)` |
|------|---------------------|-----------------|
| 실행 | 동기 | 비동기 |
| 반환 | `undefined` | 시트로 이행되는 `Promise` |
| 적용 대상 | constructed stylesheet만 | constructed stylesheet만 |
| `@import` | 제거됨 | 제거됨 |

```js
sheet.replaceSync('@import "a.css"; p { margin: 0 }')
sheet.cssRules.length // 1 (@import 규칙은 빠짐)
const done = await sheet.replace('b { color: red }')
done === sheet // true
```

- 파싱할 수 없는 규칙은 건너뛰고 나머지만 남깁니다. 전체가 잘못되면 빈 시트가 됩니다.
- constructed stylesheet의 `@import`는 제한됩니다. `replace()`와 `replaceSync()`는 텍스트의 `@import` 규칙을 제거하고 콘솔에 경고를 냅니다. `insertRule('@import ...')`는 `SyntaxError`입니다.
- 다른 CSS 파일이 필요하면 JavaScript에서 각각의 시트로 만들어 `adoptedStyleSheets` 배열에 순서대로 넣습니다. 또는 `fetch()`로 받은 텍스트를 `replaceSync()`에 넘깁니다.
- `replace()`가 진행 중인 동안에는 시트가 수정 불가 상태가 되어 `insertRule()` 같은 변경이 `NotAllowedError`를 던집니다. 즉시 결과가 필요하면 `replaceSync()`를 씁니다.

## adoptedStyleSheets

`adoptedStyleSheets`는 `Document`와 `ShadowRoot`가 가진 프로퍼티로, 그 root에 적용할 constructed stylesheet의 배열입니다.

```js
const root = host.attachShadow({ mode: 'open' })
root.adoptedStyleSheets = [sheet]
```

- 배열의 시트는 root 안의 모든 요소에 적용되며, 규칙은 해당 shadow tree의 컨텍스트에서 동작합니다(우선순위 규칙은 23편).
- 같은 시트 객체를 여러 root와 문서가 동시에 채택할 수 있습니다.
- 시트의 내용을 바꾸면(`replaceSync()`, `insertRule()`) 그 시트를 채택한 모든 root에 즉시 반영됩니다. root마다 따로 갱신할 필요가 없습니다.

### 배열 조작 규칙

`adoptedStyleSheets`는 통째로 대입하거나 배열처럼 직접 바꿀 수 있는 관찰 가능한 배열(`ObservableArray`)입니다.

```js
root.adoptedStyleSheets = [base, theme]  // 전체 교체
root.adoptedStyleSheets.push(extra)      // 끝에 추가
root.adoptedStyleSheets = root.adoptedStyleSheets
  .filter((s) => s !== theme)            // 제거
```

- 원소를 넣을 때마다 검사합니다. constructed stylesheet가 아니거나 다른 문서에서 만든 시트(예: iframe)이면 `NotAllowedError`가 발생합니다. `style`·`link` 요소의 시트나 `@import`로 불러온 시트는 채택할 수 없습니다.
- 적용 순서는 root의 `style`·`link` 시트가 먼저이고 `adoptedStyleSheets`가 배열 순서대로 그 뒤입니다. 명시도가 같으면 뒤에 오는 시트가 이기므로 채택한 시트가 `style` 요소의 규칙을 이깁니다.
- 배열 안에서도 뒤쪽 원소가 앞쪽을 이깁니다. 기본 → 테마 → 사용자 순으로 놓습니다.
- 시트의 채택을 해제하려면 배열에서 빼야 합니다. 시트를 `disabled`로 두는 방법도 있습니다.
- `Document.adoptedStyleSheets`는 문서 전체에 적용되고 shadow tree에는 영향을 주지 않습니다. 문서에 채택한 시트를 shadow root에도 쓰려면 root의 배열에도 넣어야 합니다.

## Constructable Stylesheets 공유

컴포넌트의 스타일을 모듈에서 한 번만 만들고 모든 인스턴스의 shadow root가 같은 객체를 채택합니다.

```js
// styles.js
export const sheet = new CSSStyleSheet()
sheet.replaceSync(`
  :host { display: block }
  p { margin: 0 }
`)
```

```js
import { sheet } from './styles.js'
class Note extends HTMLElement {
  constructor() {
    super()
    const root = this.attachShadow({ mode: 'open' })
    root.adoptedStyleSheets = [sheet]
    root.innerHTML = '<p><slot></slot></p>'
  }
}
```

- 인스턴스가 수백 개여도 시트 객체는 하나입니다. 각 인스턴스가 `style` 요소를 따로 가지는 방식과 달리 시트 객체가 공유됩니다.
- 여러 컴포넌트가 함께 쓰는 리셋·토큰 시트도 같은 방식입니다. `[resetSheet, componentSheet]`로 채택하면 공용 규칙과 컴포넌트 규칙이 합쳐집니다.
- 문서의 `style`·`link` 시트는 constructed가 아니라 shadow root에 그대로 채택할 수 없습니다. 같은 CSS 텍스트로 constructed stylesheet를 따로 만들어야 합니다.
- 시트를 바꾸는 코드는 모든 채택자에 영향을 줍니다. 공유 시트를 한 컴포넌트에서만 바꾸고 싶다면 그 컴포넌트용 시트를 따로 둡니다.

## style·link·adopted 방식 비교

shadow root에 스타일을 연결하는 방법은 세 가지입니다.

| 항목 | `style` 요소 | `link` 요소 | `adoptedStyleSheets` |
|------|--------------|-------------|----------------------|
| 정의 위치 | shadow tree 안의 마크업 | shadow tree 안의 마크업 | JavaScript 객체 |
| 외부 파일 | 불가(텍스트 인라인) | 가능(별도 요청) | CSS 텍스트나 모듈로 불러와 채택 |
| root 간 공유 | 불가(root마다 요소가 있음) | 불가(root마다 요소가 있음) | 가능(같은 객체) |
| 내용 수정 | `textContent` 변경 | `href` 변경 | `replaceSync()`, `insertRule()` |
| `@import` | 가능 | 가능 | 제거됨 |
| `shadowRoot.styleSheets` | 나타남 | 나타남 | 나타나지 않음 |
| 직렬화(`getHTML()`, 선언적 shadow root) | 포함됨 | 포함됨 | 포함되지 않음 |

- 마크업이 아닌 시트는 DOM 노드가 아니라서 `getHTML()`이나 서버 렌더링의 선언적 shadow root(76편)에는 `style` 요소가 필요합니다.
- 스타일을 템플릿에 인라인으로 쓰면 컴포넌트 하나가 파일 하나로 끝납니다(22편). 인스턴스가 많거나 같은 시트를 여러 컴포넌트가 공유하면 채택 방식이 낫습니다.
- 한 root에서 섞어 써도 됩니다. 이때 `style`·`link`가 먼저, 채택한 시트가 나중에 적용됩니다.

## CSS 모듈 스크립트

CSS 모듈 스크립트는 `.css` 파일을 JavaScript 모듈로 import해서 constructed stylesheet를 얻는 방식입니다. 기본 export가 `CSSStyleSheet`입니다.

```js
import sheet from './card.css' with { type: 'css' }
shadow.adoptedStyleSheets = [sheet]
```

```js
const m = await import('./card.css', {
  with: { type: 'css' },
})
shadow.adoptedStyleSheets = [m.default]
```

- 파일은 `text/css` MIME 타입으로 제공되어야 합니다. 같은 URL을 여러 곳에서 import해도 모듈은 한 번만 평가되므로 하나의 시트를 공유합니다.
- 미Baseline입니다. web-features 3.40.1 기준으로 Chrome·Edge 123, Firefox 147부터 지원하고 Safari는 지원하지 않습니다. import 속성 문법(`with`) 자체는 Baseline 2025이지만 `type: 'css'`는 별개입니다.
- 대개 윈도우 컨텍스트에서만 지원됩니다(MDN).
- Safari를 지원해야 하면 번들러가 CSS를 문자열로 변환해 `replaceSync()`로 시트를 만들도록 하거나, `fetch()`한 텍스트를 `replaceSync()`에 넘기는 방식을 씁니다(점진적 향상은 71편).

## 스타일 캡슐화 vs 테마 확장성

Shadow DOM은 스타일을 기본적으로 막기 때문에 컴포넌트를 외부에서 바꾸려면 컴포넌트가 의도적으로 통로를 열어야 합니다. 통로가 넓을수록 확장은 쉬워지지만 내부 구조를 바꿀 때 사용자에게 미치는 영향도 커집니다.

| 통로 | 노출되는 것 | 내부 변경 시 부담 |
|------|-------------|--------------------|
| 커스텀 속성(토큰) | 이름과 값 | 낮음. 이름만 유지하면 됨 |
| host 속성 변형 | 열거 값 | 낮음 |
| 슬롯 | 내용이 들어갈 영역 | 중간. 슬롯 이름과 기대 요소 유지 |
| `::part()` | 요소와 part 이름 | 중간. 요소 구조와 이름 유지 |
| 스타일시트 주입 | 내부 선택자 전체 | 높음. 내부 구조가 사실상 API가 됨 |

- 가장 좁은 통로부터 엽니다. 대부분의 테마는 커스텀 속성과 host 속성 변형으로 충분합니다.
- 구조 수준의 조정이 필요한 지점만 `part`로 열고, 내부 클래스 이름을 바깥이 직접 쓰게 하는 스타일시트 주입은 마지막에 둡니다.
- 주입을 허용하려면 임의의 시트를 받는 메서드를 공개 API로 제공하고 채택 순서(기본 → 주입)를 문서화합니다.

```js
class ThemableCard extends HTMLElement {
  #root = this.attachShadow({ mode: 'open' })
  adoptStyles(sheet) {
    this.#root.adoptedStyleSheets =
      [...this.#root.adoptedStyleSheets, sheet]
  }
}
```

- 테마 주입의 구체적인 방법은 23편, 토큰 계층과 디자인 시스템 관점은 74편에서 다룹니다.

## Dark Mode와 prefers-color-scheme

`prefers-color-scheme`은 사용자가 OS나 브라우저에서 고른 밝기 설정을 `light`나 `dark`로 알려 주는 미디어 기능입니다. Baseline 2020, 널리 지원됩니다. 값이 `light`이면 밝은 테마를 원하거나 설정이 없는 경우입니다.

```css
:host { --x-bg: #fff; --x-fg: #222 }
@media (prefers-color-scheme: dark) {
  :host { --x-bg: #1b1b1f; --x-fg: #eee }
}
```

- 미디어 쿼리는 스타일시트가 어느 트리에 있든 사용자 설정을 기준으로 평가됩니다. shadow tree 안의 스타일시트에서도 그대로 씁니다.
- JavaScript에서는 `matchMedia('(prefers-color-scheme: dark)')`의 `matches`와 `change` 이벤트로 읽고 구독합니다.
- 사용자가 앱 안에서 테마를 직접 고르는 기능이 있으면 미디어 쿼리만으로는 부족합니다. OS 설정과 별개로 바꾸려면 속성이나 `color-scheme`을 써야 합니다.

### color-scheme과 light-dark()

`color-scheme`은 요소가 지원하는 색 구성표를 선언하는 속성입니다. 값은 `normal`, `light`, `dark`, `light dark`이고 `only`는 브라우저의 자동 다크 변환을 막습니다. 상속되는 속성이라서 shadow 경계를 통과합니다. Baseline 2022입니다.

- 브라우저가 그리는 요소(폼 컨트롤, 스크롤바, 기본 캔버스 색)가 선언한 구성표에 맞춰집니다.
- 문서에는 `<meta name="color-scheme" content="light dark">`나 `:root { color-scheme: light dark }`를 둡니다.

`light-dark(밝은 값, 어두운 값)`은 현재 적용되는 구성표에 따라 두 값 중 하나를 고르는 함수입니다. 요소의 `color-scheme`에 `light`와 `dark`가 모두 있어야 동작하며, 그때 OS 설정을 따릅니다. `light`나 `dark` 하나로 고정되어 있으면 그쪽 값을 씁니다. Baseline 2024로 새로 지원되는 단계입니다. 이미지 값을 받는 형태는 Baseline 2026입니다.

```css
:root { color-scheme: light dark }
:root[data-theme="dark"] { color-scheme: dark }
```

```css
/* 컴포넌트의 shadow tree */
.card { background: light-dark(#fff, #1b1b1f) }
```

- `color-scheme`을 host나 조상에서 바꾸면 그 아래 컴포넌트의 `light-dark()`가 함께 바뀝니다. 컴포넌트마다 미디어 쿼리를 쓰지 않고, 사용자가 고른 테마도 한 곳에서 적용됩니다.
- `prefers-color-scheme`은 사용자의 OS·브라우저 설정만 반영하므로 앱 안의 수동 토글에는 `color-scheme`과 `light-dark()` 조합이 편합니다.
- 색 이외의 값(크기, 이미지)이 테마마다 다르면 커스텀 속성을 테마 단위로 바꿉니다(자세히는 74편).

## 컨테이너 쿼리와 컴포넌트

컨테이너 쿼리는 뷰포트가 아니라 가장 가까운 컨테이너의 크기나 스타일에 따라 규칙을 적용합니다. 컴포넌트가 놓이는 칸의 폭에 맞춰 스스로 바뀌게 만들 수 있습니다. Baseline 2023, 널리 지원됩니다.

```css
:host {
  display: block;
  container-type: inline-size;
}
.card { display: grid }
@container (width > 480px) {
  .card { grid-template-columns: 1fr 2fr }
}
```

- 쿼리 대상은 flat tree에서 가장 가까운 조상 중 `container-type`이 지정된 요소입니다. shadow tree 안 요소의 조상에는 host와 그 바깥 조상이 포함되므로 host를 컨테이너로 지정할 수 있습니다.
- 컨테이너는 자기 자신을 쿼리할 수 없습니다. `:host` 규칙은 host 자신이 아니라 host의 조상 컨테이너를 쿼리합니다. host의 크기에 따라 안쪽을 바꾸려면 안쪽 요소의 규칙에서 쿼리합니다.
- `inline-size`는 컨테이너의 가로 크기를 내용이 아닌 문맥으로 정하게 합니다. 부모 폭을 따르는 `display: block` 같은 박스에 지정하고, 폭이 내용에서 정해지는 요소에는 쓰지 않습니다.
- `::slotted()`는 shadow tree 안의 컨테이너를 쿼리할 수 있고(슬롯 자신 포함), `::part()`도 shadow tree 안의 컨테이너를 쿼리합니다. 슬롯된 요소나 part를 컨테이너의 크기에 맞게 바꿀 수 있습니다.
- 컨테이너 이름(`container-name`)은 트리에 한정되지 않습니다. 바깥 문서에서 정한 이름을 shadow tree 안에서 쓸 수 있고 반대도 가능하므로 이름이 겹치지 않게 컴포넌트 접두사를 붙입니다.
- 크기 단위 `cqi`, `cqw` 등은 쿼리 컨테이너를 기준으로 합니다.
- 컨테이너 쿼리 덕분에 같은 컴포넌트가 사이드바, 본문, 모달 어디서든 폭에 맞게 배치됩니다. 미디어 쿼리는 뷰포트 기준이라 컴포넌트가 놓일 칸의 폭과 무관합니다.
- 커스텀 속성 값으로 질의하는 스타일 쿼리는 `:host-context()`의 대안이 됩니다(23편).

## @layer·@scope와 Shadow DOM 캡슐화 비교

`@layer`와 `@scope`도 스타일 충돌을 줄이는 도구이지만 Shadow DOM과 막는 대상이 다릅니다.

| 항목 | Shadow DOM | `@layer` | `@scope` |
|------|------------|----------|----------|
| 하는 일 | 선택자와 규칙이 트리 경계를 못 넘게 함 | 스타일시트 그룹의 우선순위 순서를 정함 | 규칙이 적용될 DOM 하위 트리의 범위를 제한 |
| 바깥 스타일의 유입 | 차단(상속 제외) | 허용 | 허용 |
| 안쪽 스타일의 유출 | 차단 | 허용 | 범위 안으로 제한 |
| 선택자 한정 | 트리 단위 | 없음 | 범위 시작(root)과 끝(limit) 지정 |
| 지원 | Baseline 2020 | Baseline 2022 | Baseline 2026(새로 지원) |

- `@layer`는 우선순위만 조정하며 선택자의 도달 범위는 바꾸지 않습니다. 컨텍스트 비교가 레이어 비교보다 앞서므로 바깥과 안쪽 사이의 우선순위는 레이어로 바꿀 수 없습니다. 한 root 안에서 리셋, 기본, 변형 스타일의 순서를 정하는 용도로 씁니다.
- 레이어에 속하지 않은 선언은 마지막 암시적 레이어에 들어가 일반 선언에서는 모든 명명된 레이어보다 우선합니다.
- `@scope (루트) to (한계)`는 선택자를 하위 트리에 묶고 안쪽 한계 아래를 제외하는 "도넛" 범위를 만들 수 있습니다. 명시도가 같을 때 경쟁하는 범위 중 범위 루트에 더 가까운 쪽이 이깁니다. 바깥에서 오는 스타일과 상속은 막지 못합니다.
- 컴포넌트가 Shadow DOM 없이 light DOM으로 만들어진 경우(21편)에는 `@scope`와 `@layer` 조합이 가장 가까운 대체재입니다. 완전한 격리가 필요하면 Shadow DOM을 씁니다.
- 한 컴포넌트에서 함께 쓰는 것도 가능합니다. shadow tree 안 스타일시트의 `@layer`는 그 트리 안에서만 순서를 정합니다.

## 핵심 정리

- constructed stylesheet는 `new CSSStyleSheet()`로 만들고 `replaceSync()`·`insertRule()`로 바꾸며, `replace()`와 `replaceSync()`는 `@import`를 제거하고 `insertRule()`은 `@import`에 `SyntaxError`를 냅니다.
- `adoptedStyleSheets`는 같은 문서에서 만든 constructed stylesheet만 받는 배열이며 `style`·`link` 뒤, 배열 순서대로 적용되고, 한 시트를 여러 root가 공유해서 수정이 모두에 반영됩니다.
- adopted 방식은 인스턴스 간 공유가 되지만 마크업이 아니라서 직렬화에서 빠지고, `style`·`link`는 root마다 별도 시트입니다. CSS 모듈 스크립트는 Safari 미지원이라 미Baseline입니다.
- 캡슐화와 확장성은 통로의 폭으로 조절하며 커스텀 속성, host 속성, 슬롯, `part`, 스타일시트 주입 순으로 좁은 것부터 엽니다.
- 다크 모드는 상속되는 `color-scheme`과 `light-dark()`로 한 곳에서 제어하고, `prefers-color-scheme`은 OS 설정만 반영합니다.
- 컨테이너 쿼리는 flat tree의 조상 컨테이너를 쿼리해 컴포넌트가 놓인 칸에 맞춥니다. `@layer`와 `@scope`는 우선순위와 범위만 다루고 Shadow DOM처럼 경계를 만들지 않습니다.

## Service Worker 등록

서비스 워커는 웹 앱과 네트워크 사이에서 프록시처럼 동작하는 워커입니다. 페이지가 보내는 요청을 가로채 캐시 응답을 주거나 직접 만든 응답을 줄 수 있고, 페이지를 닫아도 푸시나 동기화 이벤트를 받을 수 있습니다(자세히는 57편). 전용 워커(54편)와 달리 페이지 하나에 속하지 않고 origin의 특정 범위(scope)에 등록되어 오래 남습니다.

등록은 `navigator.serviceWorker.register(scriptURL, options)`입니다. 등록 API는 Baseline 2018입니다.

```js
if ('serviceWorker' in navigator) {
  const sw = navigator.serviceWorker
  const reg = await sw.register('/sw.js', { scope: '/' })
  console.log(reg.scope) // https://example.com/
}
```

- `register()`는 `ServiceWorkerRegistration`으로 이행되는 Promise를 돌려줍니다. 같은 scope에 같은 스크립트를 다시 등록해도 안전하며 새 버전이 있으면 업데이트 확인으로 이어집니다.
- HTTPS(보안 컨텍스트)에서만 등록할 수 있고 개발용 `localhost`는 예외입니다. 스크립트는 JavaScript MIME 타입으로 서빙되어야 합니다.
- `register()`는 워커에서도 호출할 수 있습니다. 스크립트 URL은 Trusted Types가 강제되면 `TrustedScriptURL`이어야 합니다(자세히는 63편).

**등록이 실패하는 흔한 원인:** HTTPS가 아님, 스크립트 경로 오류, 앱과 다른 origin의 스크립트, 스크립트 위치보다 넓은 scope 요청, 브라우저 설정(시크릿 모드, 쿠키 차단 등).

### scope와 Service-Worker-Allowed 헤더

scope는 서비스 워커가 제어할 URL 범위입니다. 기본값은 스크립트가 있는 디렉터리입니다. 스크립트가 `/js/sw.js`이면 기본 scope는 `/js/`이고, 이 범위 밖의 페이지는 제어하지 못합니다. 그래서 서비스 워커는 보통 루트(`/sw.js`)에 둡니다.

- `scope` 옵션으로 범위를 좁힐 수는 있지만, 스크립트 위치보다 넓히려면 스크립트 응답에 `Service-Worker-Allowed` 헤더로 허용해야 합니다.
- scope 안의 페이지는 그 서비스 워커가 제어하는 클라이언트(controlled client)가 됩니다. 제어되는 페이지가 보내는 모든 요청이 fetch 이벤트의 대상입니다.
- 페이지가 scope 안에 있어야 제어됩니다. 스크립트와 scope는 앱과 같은 origin이어야 합니다.

### 모듈 서비스 워커

`type: 'module'` 옵션을 주면 ES 모듈로 서비스 워커를 등록합니다. 스크립트 안에서 정적 `import`를 쓸 수 있습니다. 모듈 서비스 워커는 Baseline 2026입니다(Chrome·Edge 91, Firefox 147, Safari 15).

```js
await navigator.serviceWorker.register('/sw.js', {
  type: 'module',
})
```

- 서비스 워커 전역에서는 동적 `import()`가 오류입니다. 정적 `import` 문만 허용됩니다.
- 모듈을 쓰지 않는 기본값은 `classic`입니다.

## 생명주기

서비스 워커 버전 하나는 다음 상태를 차례로 거칩니다(`ServiceWorker.state`).

| 상태 | 의미 |
|------|------|
| `parsed` | 스크립트를 불러와 해석함 |
| `installing` | `install` 이벤트 처리 중 |
| `installed` | 설치 완료. 이전 버전이 있으면 대기(waiting) |
| `activating` | `activate` 이벤트 처리 중 |
| `activated` | 활성. fetch 같은 기능 이벤트를 받음 |
| `redundant` | 설치 실패 또는 새 버전에 밀려남. 더 이상 이벤트를 받지 않음 |

`ServiceWorkerRegistration`은 현재 단계의 워커를 `installing`, `waiting`, `active` 속성으로 보여 줍니다. 새 워커가 `installing`에 들어오면 `updatefound` 이벤트가 발생합니다.

```js
reg.addEventListener('updatefound', () => {
  const sw = reg.installing
  sw.addEventListener('statechange', () => {
    console.log(sw.state)
    // installed → activating → activated
  })
})
```

- 처음 등록할 때는 대기 없이 설치 뒤 바로 활성화됩니다. 그래도 그 페이지는 등록 전에 이미 로드되었으므로 제어되지 않고, 새로 고침해야 제어를 받습니다. 활성화 단계에서 `clients.claim()`을 부르면 바로 제어를 가져옵니다.
- 새 버전이 설치되면 이전 버전이 제어하는 페이지가 모두 닫힐 때까지 `waiting`에서 기다립니다(아래 업데이트 전략).
- 서비스 워커는 처리할 이벤트가 없으면 브라우저가 언제든 종료할 수 있습니다. 전역 변수는 유지되지 않으므로 상태는 Cache API나 IndexedDB에 저장하고, 이벤트가 올 때마다 다시 시작될 수 있다고 가정해 설계합니다(저장소는 41편, 42편).
- 서비스 워커에는 DOM, `localStorage`, `sessionStorage`, 동기 XHR이 없습니다. 모든 비동기 작업은 Promise 기반입니다.

## install / activate

`install`은 새 버전이 처음 실행될 때 버전당 한 번 발생합니다. 앱 셸처럼 필수 리소스를 미리 캐시에 넣는 단계입니다. `activate`는 이전 버전이 물러난 뒤 이 버전이 활성화될 때 발생하고, 옛 캐시를 지우는 단계입니다.

두 이벤트는 `ExtendableEvent`라서 `event.waitUntil(promise)`로 작업이 끝날 때까지 단계를 붙잡아 둘 수 있습니다.

```js
const CACHE = 'static-v2'
self.addEventListener('install', (event) => {
  const files = ['/', '/offline.html', '/app.js']
  event.waitUntil(
    caches.open(CACHE).then((c) => c.addAll(files)),
  )
})
```

```js
self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    const keys = await caches.keys()
    await Promise.all(
      keys.filter((k) => k !== CACHE)
        .map((k) => caches.delete(k)),
    )
  })())
})
```

`waitUntil()`의 규칙은 다음과 같습니다.

- 이벤트 콜백 안에서 동기적으로 처음 호출해야 합니다. 여러 번 호출할 수 있고 모든 Promise가 끝날 때까지 기다립니다.
- `install`에서는 Promise가 끝날 때까지 `installing` 단계에 머뭅니다. Promise가 거부되면 설치가 실패하고 그 워커는 버려집니다. 그래서 `cache.addAll`의 URL 하나만 404여도 설치 전체가 실패합니다.
- `activate`에서는 Promise가 끝날 때까지 `fetch`, `push` 같은 기능 이벤트를 버퍼에 쌓아 둡니다. 스키마 업데이트와 옛 캐시 삭제를 끝낸 뒤에야 요청을 처리하게 만들 수 있습니다.
- 캐시 이름에 버전을 붙이고(`static-v2`), `activate`에서 현재 버전 외의 캐시를 삭제하는 것이 기본 패턴입니다.

**흔한 실수:** `waitUntil` 없이 비동기 작업을 시작하는 것입니다. 이벤트 처리가 끝났다고 판단되면 브라우저가 서비스 워커를 종료해 캐시 채우기가 중간에 끊깁니다.

## fetch 가로채기

`fetch` 이벤트는 서비스 워커가 제어하는 페이지의 요청마다 발생합니다. 명시적 `fetch()` 호출뿐 아니라 내비게이션, 스크립트, CSS, 이미지 같은 브라우저의 암묵적 요청도 포함됩니다. 이벤트는 취소할 수 없고 버블링되지 않습니다.

`event.respondWith(response)`로 기본 처리를 대체합니다.

```js
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request)
      .then((hit) => hit ?? fetch(event.request)),
  )
})
```

- `respondWith()`는 `Response`나 `Response`로 이행되는 Promise를 받습니다. 거부되거나 `Response`가 아니면 네트워크 오류가 페이지에 전달됩니다.
- 이벤트 디스패치 중에 동기적으로 호출해야 하며 이벤트당 한 번만 호출할 수 있습니다. `await` 뒤나 `then` 콜백 안에서 처음 호출하면 `InvalidStateError`입니다. 비동기 결과는 `respondWith`에 Promise로 넘깁니다.
- `respondWith()`를 호출하지 않으면 브라우저의 기본 네트워크 처리가 이어집니다. 가로채지 않을 요청은 핸들러에서 그냥 반환합니다.
- 응답 종류에는 요청 모드에 따른 제약이 있습니다. `opaque` 응답은 `no-cors` 요청에만, `opaqueredirect`는 `manual` 요청에만 쓸 수 있고, `cors` 응답은 `same-origin` 요청에 쓸 수 없습니다. 어기면 `NetworkError`입니다.
- 응답 본문은 한 번만 읽을 수 있으므로 캐시에 저장하면서 반환하려면 `response.clone()`을 씁니다.
- 캐시에 쓰는 비동기 작업은 `event.waitUntil()`로 붙잡아 응답 뒤에도 끝나게 합니다.
- 응답은 `caches.match()`로 찾은 캐시, `Response.json()`·`new Response()`로 만든 합성 응답, `Response.error()`(네트워크 오류)가 될 수 있습니다.

처리할 요청을 가려내는 기준은 `event.request`의 `method`, `mode`, `destination`, URL입니다.

```js
self.addEventListener('fetch', (event) => {
  const { request } = event
  if (request.method !== 'GET') return // 기본 처리에 맡김
  const url = new URL(request.url)
  if (url.pathname.startsWith('/api/')) {
    event.respondWith(networkFirst(request))
  } else {
    event.respondWith(cacheFirst(request))
  }
})
```

## Cache Strategy

캐시 전략은 요청마다 캐시와 네트워크를 어떤 순서로 쓸지 정하는 규칙입니다(Cache API는 42편).

| 전략 | 동작 | 적합한 대상 |
|------|------|-------------|
| Cache First | 캐시에 있으면 반환, 없으면 네트워크 | 해시가 붙은 정적 파일, 폰트, 이미지 |
| Network First | 네트워크 우선, 실패하면 캐시 | 자주 바뀌는 API 데이터, HTML |
| Stale While Revalidate | 캐시를 즉시 반환하고 뒤에서 네트워크로 갱신 | 조금 오래돼도 되는 데이터, 아바타 |
| Cache Only | 캐시만 사용 | 설치 때 미리 넣은 앱 셸 |
| Network Only | 가로채지 않고 네트워크 | 결제, 로그인 등 캐시하면 안 되는 요청 |

```js
async function cacheFirst(req) {
  const hit = await caches.match(req)
  return hit ?? fetch(req)
}

async function networkFirst(req) {
  try {
    const res = await fetch(req)
    const cache = await caches.open('dyn-v1')
    await cache.put(req, res.clone())
    return res
  } catch {
    return (await caches.match(req)) ?? Response.error()
  }
}
```

```js
async function swr(event) {
  const cache = await caches.open('dyn-v1')
  const hit = await cache.match(event.request)
  const fresh = fetch(event.request).then((res) => {
    cache.put(event.request, res.clone())
    return res
  })
  event.waitUntil(fresh.catch(() => {}))
  return hit ?? fresh
}
```

- Cache First는 캐시가 영원히 남으므로 파일 이름에 해시를 붙이거나 캐시 이름에 버전을 두어 갱신 경로를 만들어야 합니다.
- Network First는 네트워크가 느리면 그만큼 기다립니다. 타임아웃을 두고 캐시로 물러서는 변형을 씁니다.
- Stale While Revalidate는 갱신 결과가 다음 요청에야 보입니다.
- 요청 종류별로 전략을 나눕니다. 예를 들어 `request.destination`이 `script`나 `style`이면 Cache Only나 Cache First를 씁니다.

**흔한 실수:** 인증이 필요한 응답이나 사용자별 응답을 공용 캐시에 저장하는 것입니다. 다른 사용자에게 보일 수 있으니 제외하거나 Network Only로 둡니다.

## Navigation Preload

서비스 워커가 꺼져 있다가 내비게이션 요청 때 시작되면 부팅 시간만큼 요청이 늦어집니다. navigation preload는 서비스 워커가 부팅되는 동안 브라우저가 내비게이션 요청을 병렬로 미리 보내 두는 기능입니다. 2022년 4월부터 Baseline입니다.

```js
self.addEventListener('activate', (event) => {
  const nav = self.registration.navigationPreload
  if (nav) event.waitUntil(nav.enable())
})
```

```js
self.addEventListener('fetch', (event) => {
  if (event.request.mode !== 'navigate') return
  event.respondWith((async () => {
    const hit = await caches.match(event.request)
    if (hit) return hit
    const pre = await event.preloadResponse
    return pre ?? fetch(event.request)
  })())
})
```

- `registration.navigationPreload`(`NavigationPreloadManager`)의 메서드는 `enable()`, `disable()`, `setHeaderValue()`, `getState()`입니다. `setHeaderValue()`로 `Service-Worker-Navigation-Preload` 요청 헤더의 값을 바꿉니다.
- 미리 받은 응답은 `event.preloadResponse` Promise로 얻습니다. 미리 받은 응답이 없으면 `undefined`로 이행하므로 네트워크 `fetch`로 물러섭니다.
- 이미 나간 preload 요청은 쓰지 않아도 낭비된 채 남습니다. 캐시 응답을 반환하는 경로에서도 `waitUntil`로 `preloadResponse`를 붙잡아 두는 것이 안전합니다.

## Offline Fallback

네트워크가 없을 때 브라우저의 기본 오류 화면 대신 앱이 만든 대체 응답을 보여 주는 것이 오프라인 대체(offline fallback)입니다. 설치 때 대체 페이지를 캐시에 넣어 두고, 내비게이션 요청이 실패하면 그 페이지를 줍니다.

```js
async function navigate(req) {
  try {
    return await fetch(req)
  } catch {
    return caches.match('/offline.html')
  }
}
self.addEventListener('fetch', (event) => {
  if (event.request.mode === 'navigate') {
    event.respondWith(navigate(event.request))
  }
})
```

- `fetch()`는 네트워크 자체가 실패하면 Promise를 거부하므로 `catch`가 대체 경로가 됩니다. 404나 500 같은 HTTP 오류 응답은 거부가 아니라 정상 응답이므로 따로 검사합니다(자세히는 36편).
- 대체 페이지(`/offline.html`)와 거기서 쓰는 CSS·이미지는 `install`에서 `addAll`로 캐시에 넣어야 오프라인에서 열립니다.
- 이미지처럼 리소스 종류마다 대체물이 다릅니다. `request.destination`으로 구분해 이미지에는 자리 표시 이미지를, API에는 `Response.json({ offline: true })` 같은 합성 응답을 돌려줍니다.
- 캐시에도 없고 대체 페이지도 없으면 `Response.error()`나 상태 408 응답처럼 의도한 실패를 돌려줍니다.

## 업데이트 전략

브라우저는 scope 안의 페이지로 내비게이션할 때, 그리고 `fetch`·`push` 같은 기능 이벤트가 발생할 때 서비스 워커 스크립트의 업데이트를 확인합니다. 마지막 확인으로부터 24시간(86400초)이 지나면 그 등록은 오래된(stale) 것으로 취급합니다. 스크립트가 이전과 한 바이트라도 다르면 새 버전으로 설치합니다.

- `registration.update()`는 서버에서 새 스크립트가 있는지 즉시 확인합니다. 장시간 열려 있는 단일 페이지 앱에서는 주기적으로 또는 탭이 다시 보일 때 호출합니다.
- `updateViaCache` 옵션은 스크립트 확인에 HTTP 캐시를 쓸지 정합니다. `register()`의 옵션이고 `registration.updateViaCache`로도 읽습니다.

| 값 | 동작 |
|----|------|
| `imports`(기본) | 메인 스크립트는 네트워크에서 확인, 가져온 스크립트는 HTTP 캐시 질의 |
| `all` | 메인과 가져온 스크립트 모두 HTTP 캐시 질의 |
| `none` | 항상 네트워크에서 확인 |

- `all`에서는 메인 스크립트의 HTTP 캐시 설정이 업데이트 확인에 영향을 줍니다. 짧게 두거나 `imports`·`none`을 씁니다.
- 새 버전은 설치되면 이전 버전이 제어하는 클라이언트가 하나도 없을 때까지 `waiting`에서 기다립니다. 같은 탭을 새로 고침해도 이전 워커가 새 페이지를 불러오는 동안 제어를 유지하므로 새 버전이 활성화되지 않습니다. 모든 탭을 닫았다가 다시 열어야 합니다.

기다리지 않으려면 두 가지 수단이 있습니다.

| 수단 | 호출 위치 | 동작 |
|------|-----------|------|
| `self.skipWaiting()` | 서비스 워커(보통 `install`) | 대기를 건너뛰고 바로 활성화 |
| `clients.claim()` | 서비스 워커(`activate`) | 제어되지 않던 페이지를 즉시 제어. 페이지에서 `controllerchange` 발생 |

```js
// sw.js
self.addEventListener('message', (e) => {
  if (e.data?.type === 'SKIP_WAITING') self.skipWaiting()
})
self.addEventListener('activate', (e) => {
  e.waitUntil(self.clients.claim())
})
```

```js
// page.js: 새 버전을 알리고 사용자가 수락하면 반영
if (reg.waiting) showUpdateBanner(() => {
  reg.waiting.postMessage({ type: 'SKIP_WAITING' })
})
const container = navigator.serviceWorker
container.addEventListener('controllerchange', () => {
  location.reload() // 새 워커가 제어를 시작함
})
```

- `skipWaiting()`을 설치 즉시 호출하면 이전 버전의 캐시와 에셋으로 로드된 열려 있는 페이지가 새 코드와 맞지 않는 상태가 될 수 있습니다. 페이지가 새 버전을 받아들일 준비가 되었을 때(사용자가 수락한 뒤)만 호출하는 방식이 안전합니다.
- `skipWaiting()`과 `clients.claim()`을 함께 쓰면 모든 열린 페이지가 즉시 새 버전으로 바뀝니다.
- 새 버전의 캐시는 새 이름으로 만들고, 옛 캐시는 새 버전의 `activate`에서 삭제합니다.

## Clients API와 postMessage

서비스 워커 안의 `self.clients`(`Clients`)는 서비스 워커가 다루는 페이지(클라이언트)에 접근하는 수단입니다.

| 메서드 | 동작 |
|--------|------|
| `clients.matchAll(options)` | 클라이언트 목록. `type`으로 종류를 거르고 `includeUncontrolled`로 제어되지 않는 페이지도 포함 |
| `clients.get(id)` | ID로 클라이언트 하나 조회 |
| `clients.openWindow(url)` | 새 창을 열고 `WindowClient`를 돌려줌 |
| `clients.claim()` | 범위 안의 모든 클라이언트를 제어 |

서비스 워커와 페이지는 `postMessage`로 양방향 통신합니다(복제 규칙은 54편).

```js
// sw.js → 모든 페이지에 알림
async function notifyAll(msg) {
  const all = await clients.matchAll({ type: 'window' })
  for (const client of all) client.postMessage(msg)
}
```

```js
// page.js ← 서비스 워커의 메시지
navigator.serviceWorker.addEventListener('message', (e) => {
  console.log(e.data)
})
// page.js → 서비스 워커
const ctrl = navigator.serviceWorker.controller
ctrl?.postMessage({ type: 'PING' })
```

- 페이지에서 서비스 워커로 보낼 때 대상은 `navigator.serviceWorker.controller`(현재 제어하는 워커) 또는 `registration.waiting`·`registration.active`입니다. 제어되지 않는 페이지에서는 `controller`가 `null`입니다.
- 서비스 워커는 `message` 이벤트로 받고 보낸 클라이언트는 `event.source`입니다.
- 푸시 알림을 눌렀을 때 이미 열린 창을 찾아 포커스하고 없으면 `clients.openWindow()`로 새로 여는 것이 전형적인 용례입니다(자세히는 57편).
- 서비스 워커는 언제든 종료될 수 있으므로 메시지를 받으면 필요한 상태를 다시 읽는다고 가정합니다.

## 정적 라우팅

정적 라우팅(static routing)은 서비스 워커 스크립트를 시작하지 않고도 특정 요청을 네트워크나 캐시로 보내도록 `install` 시점에 미리 선언하는 기능입니다. 서비스 워커가 꺼져 있으면 부팅을 건너뛰어 응답이 빨라집니다. **미Baseline**입니다. web-features 3.40.1 기준으로 Chrome·Edge 123, Safari 27에서 지원하고 Firefox는 지원 기록이 없습니다.

`InstallEvent.addRoutes(rules)`에 조건(`condition`)과 원천(`source`)을 가진 규칙을 줍니다.

```js
addEventListener('install', (event) => {
  event.addRoutes({
    condition: {
      urlPattern: '/articles/*',
      runningStatus: 'not-running',
    },
    source: 'network',
  })
})
```

| 구분 | 값 |
|------|-----|
| 조건 | `urlPattern`, `requestMethod`, `requestMode`, `requestDestination`, `runningStatus`(`running` 또는 `not-running`), 조합용 `or`·`not` |
| 원천 | `network`, `cache`, `fetch-event`(서비스 워커 핸들러로), `race-network-and-fetch-handler`, `{ cacheName }` |

- 조건에 맞는 요청은 원천에 따라 처리되고, `fetch-event`이면 평소처럼 `fetch` 핸들러로 갑니다.
- 지원하지 않는 브라우저에서는 `addRoutes`가 없으므로 `if (event.addRoutes)`로 검사하고 기존 `fetch` 핸들러가 그대로 동작하게 둡니다. 점진적 향상 방식입니다(자세히는 71편).

## 핵심 정리

- 서비스 워커는 `register()`로 등록하며 HTTPS가 필요하고, scope는 기본이 스크립트 디렉터리이며 넓히려면 `Service-Worker-Allowed` 헤더가 필요합니다.
- 생명주기는 installing, installed(waiting), activating, activated, redundant이며, `waitUntil()`로 `install`·`activate` 작업을 붙잡고 실패하면 설치가 취소됩니다.
- `fetch` 이벤트에서 `respondWith()`는 동기적으로 한 번만 호출하고 Promise를 넘기며, 호출하지 않으면 기본 네트워크 처리가 이어집니다.
- 캐시 전략은 대상에 맞게 Cache First, Network First, Stale While Revalidate 등을 나눠 쓰고, 오프라인 대체 페이지는 `install`에서 캐시해 두고 내비게이션 실패 때 돌려줍니다.
- 새 버전은 이전 버전의 클라이언트가 모두 닫힐 때까지 대기하며, `skipWaiting()`·`clients.claim()`으로 건너뛸 수 있지만 사용자가 수락한 뒤에 반영하는 것이 안전합니다.
- 모듈 서비스 워커는 Baseline 2026이고 navigation preload는 부팅 지연을 줄이며 정적 라우팅은 미Baseline이라 기능 검사 뒤에 씁니다.

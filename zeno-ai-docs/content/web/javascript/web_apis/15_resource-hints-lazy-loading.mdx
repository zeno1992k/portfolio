## 리소스 힌트의 종류

리소스 힌트는 브라우저에 "곧 이 리소스가 필요하다"고 미리 알리는 선언입니다. `<head>`의 `<link>` 요소, HTTP `Link` 응답 헤더, 스크립트로 삽입한 `<link>` 모두 같은 효과를 냅니다. 힌트는 지시가 아니므로 브라우저가 네트워크·메모리 상태에 따라 무시하거나 늦출 수 있습니다.

| 힌트 | 하는 일 | 대상 | 시점 |
|------|---------|------|------|
| `dns-prefetch` | DNS 조회만 | 다른 출처 | 현재 페이지 |
| `preconnect` | DNS + TCP + TLS 연결 | 다른 출처 | 현재 페이지 |
| `preload` | 리소스를 높은 우선순위로 가져와 캐시 | 현재 페이지가 곧 쓸 리소스 | 현재 페이지 |
| `modulepreload` | 모듈을 가져와 파싱·컴파일까지 | ES 모듈 | 현재 페이지 |
| `prefetch` | 낮은 우선순위로 가져와 HTTP 캐시에 저장 | 다음 탐색의 리소스 | 다음 페이지 |

문서 전체를 미리 준비하는 일은 `prefetch` 대신 Speculation Rules가 맡습니다(아래 절). 렌더링 단계에서 리소스가 어디서 막히는지는 02편, 스크립트 로딩 속성(`defer`·`async`)은 14편에서 다룹니다.

## preload

`<link rel="preload">`는 현재 페이지에서 곧 쓸 리소스를 일반 발견 시점보다 일찍 가져오게 합니다. 브라우저는 HTML을 훑으며 `<img>`와 `<script>`를 일찍 찾지만, CSS 안의 폰트·배경 이미지나 스크립트가 시작한 요청은 해당 코드가 실행된 뒤에야 알게 됩니다. preload는 이런 늦게 발견되는 리소스를 앞당깁니다.

```html
<link rel="preload" href="/fonts/body.woff2"
      as="font" type="font/woff2" crossorigin>
<link rel="preload" href="/hero.avif" as="image"
      type="image/avif" fetchpriority="high">
```

- `as`는 필수입니다. 리소스 종류를 알려 주어 우선순위, `Accept` 헤더, CSP 검사, 캐시 매칭에 쓰입니다. 값은 `font`, `image`, `script`, `style`, `fetch`, `track` 외에 `audio`, `video`, `worker`, `document` 등이 있습니다.
- `type`: 브라우저가 그 MIME 타입을 지원할 때만 가져옵니다. AVIF처럼 지원이 갈리는 형식에 씁니다.
- `media`: 미디어 쿼리가 참일 때만 가져옵니다. 화면 폭별로 다른 이미지를 고를 때 씁니다.
- `imagesrcset`·`imagesizes`: `as="image"`일 때 `<img>`의 `srcset`·`sizes`와 같은 문법으로 반응형 이미지의 후보를 고르게 합니다.
- `onload`·`onerror`: 가져오기 성공·실패 시 이벤트가 발생합니다.
- preload는 가져오기만 합니다. 스크립트를 실행하지 않고 스타일을 적용하지 않으므로, 실제 사용은 `<script>`나 `<link rel="stylesheet">`가 따로 해야 합니다.
- 모듈 스크립트는 `preload` 대신 `modulepreload`를 씁니다.

preload할 만한 대상은 늦게 발견되는 핵심 리소스입니다: CSS가 참조하는 폰트, CSS 배경으로 쓰는 LCP 이미지, 시작 시 호출하는 `fetch()` 데이터.

흔한 실수는 다음과 같습니다.

- HTML에 이미 쓰인 `<img>`나 `<script src>`를 preload하는 것: 브라우저가 이미 일찍 발견하므로 이득이 없습니다.
- 너무 많이 preload하는 것: 정작 중요한 리소스와 대역폭을 두고 경쟁합니다.
- 쓰지 않는 리소스를 preload하는 것: 몇 초 안에 사용되지 않으면 브라우저가 콘솔에 경고를 냅니다.
- AVIF와 WebP처럼 같은 리소스의 여러 형식을 모두 preload하는 것: 대다수 사용자가 쓰는 형식 하나만 합니다.

preload는 Baseline 2021입니다.

## preload의 as·crossorigin 일치 규칙

preload로 가져온 응답은 나중에 같은 요청이 올 때만 재사용됩니다. 요청의 종류(`as`)와 CORS 모드·자격 증명 모드가 다르면 다른 요청으로 보고 다시 가져옵니다.

```html
<!-- ❌ as가 소비 방식과 다름: file.js를 두 번 요청 -->
<link rel="preload" href="/file.js" as="style">
<script src="/file.js"></script>
```

CORS 모드는 `crossorigin` 속성으로 정합니다. 소비하는 쪽 요청의 모드와 같아야 합니다.

| 소비하는 쪽 | 요청 방식 | preload |
|-------------|-----------|---------|
| `@font-face` 폰트 | CORS(익명) | `as="font" crossorigin` |
| `<img>`·`<script src>`·`<link rel="stylesheet">` (crossorigin 속성 없음) | no-cors | `crossorigin` 없음 |
| 같은 요소에 `crossorigin`이 있음 | CORS | 같은 값의 `crossorigin` |
| `fetch(url)` 기본 | CORS(same-origin 자격 증명) | `as="fetch" crossorigin` |

- 폰트는 항상 CORS 모드로 요청되므로, 같은 출처의 폰트라도 `crossorigin`이 필요합니다. 빠뜨리면 preload와 실제 폰트 요청이 따로 나가 두 번 받습니다.
- 값 없는 `crossorigin`은 `anonymous`와 같고 쿠키를 같은 출처에만 보냅니다. `use-credentials`는 교차 출처에도 보냅니다. 소비하는 쪽과 이 값까지 같아야 합니다(CORS는 62편).
- 일치 여부는 개발자 도구의 Network 탭에서 같은 URL이 두 번 나타나는지로 확인합니다.

## modulepreload

`<link rel="modulepreload">`는 ES 모듈을 가져와 파싱·컴파일한 뒤 모듈 맵에 넣어, 실행만 하면 되는 상태로 만듭니다. `preload`는 파일을 캐시에 넣는 데서 끝나므로 이후 파싱·컴파일 비용이 남습니다.

```html
<link rel="modulepreload" href="/app/main.js">
<link rel="modulepreload" href="/app/chart.js">
<script type="module" src="/app/main.js"></script>
```

- 의존 관계의 모듈은 `import` 문을 실행해야 발견되므로 파일을 하나씩 순서대로 받게 됩니다(워터폴). 의존 모듈도 각각 `modulepreload`로 나열하면 병렬로 받습니다.
- `crossorigin` 기본값은 `anonymous`입니다. 모듈 스크립트가 원래 CORS 모드로 요청되기 때문입니다.
- `as`는 생략하면 `script`이고, `worker`, `sharedworker`, `serviceworker`, `audioworklet`, `paintworklet`, `style`, `json`, `text` 등도 허용합니다. 잘못된 값이면 `error` 이벤트가 발생합니다.
- 번들러가 파일명에 해시를 붙이면 `href`를 손으로 쓸 수 없으므로 빌드 매니페스트에서 생성합니다.
- 모듈 문법과 동적 `import()`는 14편에서 다룹니다. Baseline 2023입니다.

## prefetch

`<link rel="prefetch">`는 사용자가 곧 이동할 가능성이 높은 다음 탐색에서 쓸 리소스를 낮은 우선순위로 미리 받아 HTTP 캐시에 저장합니다. 우선순위는 `fetch()`의 `priority: "low"`에 해당하므로 현재 페이지 로딩을 방해하지 않습니다.

```html
<link rel="prefetch" href="/checkout.js">
<link rel="prefetch" href="/next-page">
```

- 대상은 다음 페이지가 쓸 하위 리소스(JS·CSS 등)나 다음 문서입니다.
- 요청에 `Sec-Purpose: prefetch` 헤더가 붙습니다. 서버는 이것으로 사전 요청을 구분할 수 있습니다.
- 브라우저의 캐시 분할 때문에 교차 사이트 리소스를 prefetch해도 다른 사이트에서는 쓰이지 않습니다. 같은 사이트의 리소스에만 유효합니다.
- 일부 브라우저가 지원하지 않아 Baseline이 아닙니다. 문서 단위 사전 로딩은 Speculation Rules를 쓰는 편이 낫습니다.
- `preload`와 혼동하지 않습니다. preload는 현재 페이지용, prefetch는 다음 페이지용입니다. 현재 페이지에서 쓸 리소스를 prefetch하면 우선순위가 낮아 오히려 늦어집니다.

## preconnect와 dns-prefetch

`<link rel="preconnect">`는 다른 출처에 요청을 보내기 전에 DNS 조회, TCP 연결, (HTTPS면) TLS 협상을 미리 끝냅니다. `dns-prefetch`는 첫 단계인 DNS 조회만 합니다.

```html
<link rel="preconnect" href="https://cdn.example.com">
<link rel="preconnect" href="https://fonts.gstatic.com"
      crossorigin>
<link rel="dns-prefetch"
      href="https://analytics.example.net">
```

| 항목 | preconnect | dns-prefetch |
|------|------------|--------------|
| 비용 | 연결 유지(소켓·TLS) | DNS 조회 한 번 |
| 효과 | 첫 요청의 연결 지연 제거 | DNS 지연만 제거 |
| 쓰는 곳 | 곧 확실히 요청할 핵심 출처 1–2곳 | 나머지 서드파티 출처 |

- 연결은 요청의 자격 증명 모드별로 따로 관리됩니다. CORS 익명 요청(폰트 등)은 `crossorigin` 없는 preconnect로 만든 연결을 재사용하지 못할 수 있으므로, 그런 리소스의 출처에는 `crossorigin`을 붙입니다.
- 쓰지 않은 연결은 브라우저가 일정 시간 뒤 닫습니다. 시간은 구현마다 다릅니다.
- 문서와 같은 출처는 이미 연결되어 있으므로 힌트가 필요 없습니다.
- 많은 출처에 preconnect하면 연결 자체가 부담이 되어 역효과입니다.
- `Link: <https://cdn.example.com>; rel=preconnect` 응답 헤더로도 지정합니다.
- preconnect는 Baseline 2020입니다.

## fetchpriority

`fetchpriority` 속성은 같은 종류의 리소스들 사이에서 이 요청의 우선순위를 올리거나 내리는 힌트입니다. 값은 `high`, `low`, `auto`(기본)입니다.

```html
<img src="/hero.avif" fetchpriority="high" alt="...">
<img src="/slide2.avif" fetchpriority="low" alt="...">
<script src="/ga.js" async fetchpriority="low"></script>
```

- 속성을 쓸 수 있는 곳은 `<img>`, `<link>`(preload 등), `<script>`입니다. 자바스크립트에서는 `img.fetchPriority = 'high'`처럼 읽고 씁니다. `fetch()`에도 `priority` 옵션이 있습니다(36편).
- 브라우저의 기본 우선순위는 이렇습니다.

| 리소스 | 기본 우선순위 |
|--------|---------------|
| `<img>` | 처음엔 낮음, 레이아웃 후 뷰포트 안이면 높음으로 상향 |
| `async`·`defer` 스크립트 | 낮음 |
| 문서 앞부분의 블로킹 스크립트 | 높음 |
| preload | 대상 종류(`as`)의 우선순위를 따름 |

- 이미지는 레이아웃이 끝나야 높음으로 올라가므로, LCP 이미지에 `fetchpriority="high"`를 주면 그 대기를 건너뜁니다.
- preload는 일찍 발견만 시킬 뿐 기본 우선순위로 가져옵니다. LCP 배경 이미지처럼 preload하면서 `fetchpriority="high"`를 함께 줍니다.
- 첫 화면 밖이지만 가까워서 우선순위가 올라가는 캐러셀 이미지에는 `low`를 줍니다.
- 상대 우선순위의 힌트이지 명령이 아닙니다. 브라우저가 자체 판단으로 무시할 수 있습니다.
- 모든 것에 `high`를 주면 아무것도 높지 않은 것과 같습니다. 첫 화면의 소수에만 씁니다.
- Baseline 2024입니다(Chrome 101, Safari 17.2, Firefox 132).

## blocking="render"

`blocking="render"`는 해당 리소스가 로드·실행되기 전까지 화면 렌더링을 막는 속성입니다. 기본값이 렌더링을 막지 않는 요소를 명시적으로 렌더링 차단으로 바꿉니다.

```html
<head>
  <link rel="stylesheet" href="/t.css" blocking="render">
  <script async src="/theme.js" blocking="render"></script>
  <link rel="expect" href="#hero" blocking="render">
</head>
```

- 적용 대상은 `<link rel="stylesheet">`, `<style>`, `<script>`, `<link rel="expect">`입니다. `rel="expect"`는 지정한 요소(`href`의 fragment)가 DOM에 생길 때까지 렌더링을 보류합니다.
- 효과는 `<head>` 안의 요소에만 있고, `text/html` 문서에서만 동작합니다.
- 스크립트에서는 `async` 스크립트에 의미가 있습니다. 일반 스크립트(`async`·`defer` 없음, `type="module"` 아님)는 이미 파싱을 막으므로 효과가 없습니다.
- 동적으로 삽입한 스타일시트나 스크립트는 렌더링을 막지 않는 것이 기본이라, 막으려면 `blocking="render"`를 직접 지정해야 합니다.
- 렌더링을 무기한 막지는 않습니다. 브라우저가 정한 시간 제한이 있습니다.
- 용도는 첫 화면이 잘못된 상태로 깜박이는 일을 막는 것입니다. 저장된 테마를 적용하거나 A/B 테스트 변형을 고르는 스크립트가 예입니다. 첫 렌더링이 그만큼 늦어지므로(LCP는 65편) 꼭 필요한 곳에만 씁니다.
- 지원: Chrome·Edge 105, Safari 18.2, Firefox 미지원이라 Baseline이 아닙니다. 미지원 브라우저에서는 속성이 무시되어 렌더링이 막히지 않고 화면이 먼저 그려질 뿐이므로 점진적 향상으로 쓸 수 있습니다.

```js
const link = document.createElement('link')
link.blocking?.supports('render')
// 지원하면 true, 미지원이면 falsy
```

## Speculation Rules API

Speculation Rules API는 사용자가 이동할 가능성이 높은 문서를 브라우저가 미리 `prefetch`하거나 `prerender`하도록 JSON 규칙으로 알립니다. Chromium 계열(Chrome 109부터)만 지원하고, Firefox는 미지원이며 Safari 26.2는 플래그 뒤에서 prefetch만 시험 중이므로 Baseline이 아닙니다.

```html
<script type="speculationrules">
{
  "prerender": [{ "urls": ["/next"] }],
  "prefetch": [{
    "where": { "href_matches": "/articles/*" },
    "eagerness": "moderate"
  }]
}
</script>
```

규칙은 두 방법으로 선언합니다.

- 인라인 `<script type="speculationrules">`: CSP가 걸려 있으면 `'inline-speculation-rules'` 키워드, 해시, 논스 중 하나가 필요합니다(CSP는 63편).
- `Speculation-Rules: "/rules.json"` 응답 헤더: 외부 파일은 `application/speculationrules+json` MIME 타입이어야 합니다.

### prefetch와 prerender

| 항목 | prefetch | prerender |
|------|----------|-----------|
| 하는 일 | 문서 응답 본문만 받음 | 문서와 하위 리소스를 받아 보이지 않는 탭에서 렌더링·스크립트 실행 |
| 이동 시 | 응답이 이미 있어 빠름 | 즉시 전환에 가까움 |
| 비용 | 낮음 | 높음(iframe 하나에 준함) |
| 용도 | 넓게 적용 | 이동 확률이 높은 한두 페이지 |

### 규칙의 두 형태와 eagerness

- 목록 규칙: `"urls": ["/a", "/b"]`처럼 URL을 직접 적습니다. 기본 `eagerness`는 `immediate`입니다.
- 문서 규칙: `"where"` 조건(`href_matches`, `selector_matches`, `and`·`or`·`not`)으로 문서의 링크를 고릅니다. 기본 `eagerness`는 `conservative`입니다.

| eagerness | 시작 시점 |
|-----------|-----------|
| `immediate` | 규칙이 발견되는 즉시 |
| `eager` | 데스크톱은 포인터를 10ms 올렸을 때, 모바일은 링크가 뷰포트에 들어온 뒤 짧은 시간 후 |
| `moderate` | 데스크톱은 200ms 호버 또는 pointerdown, 모바일은 스크롤이 멈춘 뒤 |
| `conservative` | 포인터·터치를 누르는 순간 |

Chrome은 동시에 유지할 수 있는 개수를 제한합니다. `immediate`는 prefetch 50개·prerender 10개, 그 밖의 값은 각각 2개이며, 넘으면 가장 오래된 것부터 대체합니다.

### 제약과 안전

- 교차 사이트 prefetch는 대상 사이트의 쿠키가 없을 때만 동작합니다. prerender는 같은 출처가 기본이고, 같은 사이트의 다른 출처는 대상이 `Supports-Loading-Mode: credentialed-prerender` 헤더를 보내야 하며, 교차 사이트는 불가합니다.
- 서버 부작용이 있는 URL(로그아웃, 장바구니 담기, 언어 전환, 일회용 인증 요청)은 규칙에서 `not`으로 제외합니다. 서버는 `Sec-Purpose: prefetch`(prerender는 `prefetch;prerender`) 헤더로 사전 요청을 알아봅니다.
- prerender 중인 페이지는 사용자가 보기 전에 스크립트가 실행됩니다. 분석 전송, 광고 노출 집계, 저장소 쓰기는 `document.prerendering`이 `false`가 되는 `prerenderingchange` 이벤트까지 미룹니다.
- prerender 중에는 위치·알림 같은 API와 전체 화면, 클립보드처럼 사용자 상호작용이 필요한 API가 지연되거나 막힙니다. 교차 출처 iframe 로딩과 다운로드는 활성화 때까지 지연됩니다.
- 데이터 절약 모드, 에너지 절약 모드, 메모리 부족, 설정에서 미리 로드 끔, 배경 탭이면 prerender가 취소됩니다.
- 하위 리소스의 prefetch는 Speculation Rules의 대상이 아닙니다. 그것은 `<link rel="prefetch">`가 맡습니다.

```js
if (document.prerendering) {
  document.addEventListener('prerenderingchange', sendView)
} else {
  sendView()
}
// 이동으로 활성화되었는지: navigation entry의 activationStart > 0
```

## 지연 로딩 전략

지연 로딩은 지금 필요하지 않은 리소스의 로딩을 필요해질 때까지 미루는 전략입니다. 초기 로딩 경로가 짧아지고 전송량이 줄어듭니다. 미루는 시점의 기준에 따라 도구가 다릅니다.

| 대상 | 미루는 기준 | 도구 |
|------|-------------|------|
| 화면 밖 이미지·iframe | 뷰포트 접근 | `loading="lazy"` |
| 화면 밖 컴포넌트 | 뷰포트 진입 | IntersectionObserver + `import()` |
| 큰 기능(에디터·차트) | 사용자 동작 | 이벤트 시 `import()` |
| 다른 화면의 코드 | 라우트 이동 | 라우트 단위 `import()` |
| 중요하지 않은 스크립트 | 파싱 이후 | `defer`·`async` (14편) |
| 다음 페이지 | 이동 가능성 | prefetch·Speculation Rules |

네이티브 지연 로딩은 속성 하나로 켭니다.

```html
<img src="/photo.avif" loading="lazy"
     width="800" height="600" alt="...">
<iframe src="/map" loading="lazy" title="지도"></iframe>
```

- `<img>`와 `<iframe>`에 쓰며, 값은 `eager`(기본)와 `lazy`입니다. 모든 핵심 브라우저가 지원합니다.
- 뷰포트에 얼마나 가까워지면 시작할지는 브라우저가 정합니다. 보이기 직전이 아니라 약간 앞서 시작합니다.
- 화면 밖에서 아직 시작하지 않은 lazy 이미지는 `complete`가 `false`입니다.
- 첫 화면에 보이는 이미지, 특히 LCP 후보에는 `lazy`를 쓰지 않습니다. 가져오기 시작이 늦어져 LCP가 나빠집니다.
- `width`·`height`(또는 CSS `aspect-ratio`)로 공간을 예약합니다. 없으면 로드될 때 레이아웃이 밀립니다(CLS는 65편).
- 더 세밀하게 제어하려면 IntersectionObserver(43편)로 요소가 보일 때 `src`를 채웁니다. `rootMargin`을 크게 주면 화면에 닿기 전에 시작합니다.
- 지연할 것과 서두를 것을 같이 정합니다. 첫 화면 필수 리소스는 `preload`·`fetchpriority`로 앞당기고, 나머지는 미루는 것이 기본 구도입니다.
- 지연 로딩의 부작용은 늦게 나타나는 지연입니다. 스크롤 도중 빈 영역이 보이면 `rootMargin`을 키우거나 상호작용 직전(호버·포커스)에 미리 시작합니다.
- 성능 최적화 전반은 66편에서 다룹니다.

## 컴포넌트 단위 코드 스플리팅

코드 스플리팅은 하나의 큰 번들을 여러 조각(청크)으로 나눠 필요할 때 가져오는 방식이고, 컴포넌트 단위는 컴포넌트 모듈 하나를 청크의 경계로 삼는 것입니다. 경계는 동적 `import()`가 만듭니다. 정적 `import` 문은 같은 청크에 합쳐지고, `import()`는 Promise를 반환하며 번들러가 별도 청크로 분리합니다(`import()`의 동작은 14편).

```js
const loaders = {
  'x-chart': () => import('./x-chart.js'),
  'x-editor': () => import('./x-editor.js'),
}
```

Custom Element는 정의 모듈이 `customElements.define()`을 실행하는 순간 동작하므로, 모듈을 로드하는 시점이 곧 정의 시점입니다(17편).

```js
function defineWhenVisible(tag, load) {
  const io = new IntersectionObserver((entries) => {
    if (entries.some((e) => e.isIntersecting)) {
      io.disconnect()
      load()
    }
  })
  document.querySelectorAll(tag)
    .forEach((el) => io.observe(el))
}
defineWhenVisible('x-chart', loaders['x-chart'])
```

- 정의 전의 `<x-chart>`는 알 수 없는 사용자 정의 요소로 DOM에 존재하다가, `define()`이 실행되면 업그레이드됩니다(18편). `customElements.whenDefined('x-chart')`는 정의가 끝나면 이행되는 Promise를 반환합니다.
- 정의되기 전에 자리를 비워 두면 로드 순간 레이아웃이 밀립니다. `:not(:defined)` 선택자로 예상 크기를 미리 잡습니다.

```css
x-chart:not(:defined) { display: block; min-height: 240px; }
```

- 같은 모듈 지정자는 모듈 맵에 한 번만 올라 평가됩니다. `import()`를 여러 번 호출해도 정의는 한 번만 일어나므로 `customElements.define()` 중복 오류가 나지 않습니다.
- 분할 경계는 라우트와, 에디터·차트처럼 무거운 컴포넌트에 둡니다. 작은 컴포넌트까지 모두 나누면 요청 수와 지연이 늘어 손해입니다.
- `A`가 `import()`로 `B`를, `B`가 다시 `C`를 부르면 요청이 순서대로 이어집니다. 알려진 의존 청크는 `modulepreload`로 앞당기거나 번들러 설정으로 묶습니다.
- 첫 화면에 필요한 컴포넌트를 `import()`로 미루면 오히려 늦어집니다. 첫 화면에 보이는 컴포넌트는 정적으로 포함합니다.
- 청크 로딩은 네트워크 오류나 배포로 이전 청크 파일이 사라지면 거부됩니다. `catch`로 처리해 재시도하거나 안내를 보입니다.

## 상호작용 시 로딩

상호작용 시 로딩(import on interaction)은 사용자가 클릭·포커스 같은 동작을 하는 순간에 `import()`로 코드를 가져오는 패턴입니다. 쓰지 않을 수도 있는 기능의 비용을 첫 로딩에서 없앱니다.

```js
let editorPromise
const loadEditor = () =>
  (editorPromise ??= import('./editor.js'))

const btn = document.querySelector('#open-editor')
btn.addEventListener('pointerenter', loadEditor,
  { once: true })
btn.addEventListener('focus', loadEditor,
  { once: true })
btn.addEventListener('click', async () => {
  const { openEditor } = await loadEditor()
  openEditor()
})
```

- 클릭 때 처음 `import()`하면 그만큼 지연이 보입니다. 클릭 직전 신호인 `pointerenter`(마우스 호버, 터치 시작), `focus`로 미리 시작하면 클릭 시점에는 대개 끝나 있습니다.
- `??=`(ES2021)로 Promise를 한 번만 만들어 재사용합니다. 여러 이벤트가 겹쳐도 요청은 하나입니다.
- `{ once: true }`는 리스너를 한 번 실행하고 제거합니다. 메모이즈와 함께 쓰면 중복 호출이 없습니다.
- 청크 주소를 알면 호버 때 `modulepreload` 링크를 삽입해 네트워크 요청만 먼저 시작할 수도 있습니다. 이후 `import()`는 같은 URL을 모듈 맵에서 사용합니다.
- 서드파티 위젯(동영상 임베드, 채팅)은 정적 미리보기(facade)를 두고 클릭하면 실제 위젯을 로드하는 방식이 같은 원리입니다.
- 느린 네트워크에서는 `import()` 대기 중 로딩 표시를 띄우고, 실패하면 오류를 안내해야 합니다(비동기 UI는 39편).

## Image() 생성자와 HTMLImageElement

`new Image(width, height)`는 `document.createElement('img')`와 같은 `HTMLImageElement`를 만들고 `width`·`height` 속성을 지정합니다. DOM에 붙이지 않아도 `src`를 지정하는 순간 로딩을 시작하므로 이미지 사전 로딩에 쓰입니다.

```js
const img = new Image()
img.src = '/next.avif' // DOM에 없어도 요청이 시작된다
```

### decode()

`img.decode()`는 이미지를 디코딩해 화면에 칠할 수 있는 상태가 되면 이행되는 Promise를 반환합니다(값은 `undefined`). 디코딩이 끝난 뒤 DOM에 넣으면 빈 이미지가 보이는 구간이 없습니다.

```js
async function preloadImage(url) {
  const img = new Image()
  img.src = url
  await img.decode() // 실패 시 EncodingError
  return img
}
document.body.append(await preloadImage('/a.avif'))
```

- 거부되는 경우(`EncodingError`): 요청이 실패했을 때, `decode()` 호출 뒤 `src`가 바뀌었을 때, 이미지 데이터가 손상됐을 때입니다.
- DOM에 이미 있는 이미지에도 쓸 수 있습니다.
- `load` 이벤트는 파일을 받았다는 뜻이고 디코딩 완료는 보장하지 않습니다. 첫 페인트 지연이 문제라면 `decode()`입니다.
- Baseline 2020입니다.

### complete·currentSrc·naturalWidth

| 속성 | 의미 |
|------|------|
| `complete` | 로딩이 끝났는가 (성공 또는 실패) |
| `currentSrc` | 선택된 이미지 URL. 선택 전엔 빈 문자열 |
| `naturalWidth`·`naturalHeight` | 이미지 고유 크기(px). 로드 전·실패 시 0 |

`complete`가 `true`인 경우는 다음과 같습니다.

- `src`와 `srcset`이 모두 없거나, `srcset` 없이 `src`가 빈 문자열일 때
- 이미지를 모두 받아 렌더링 준비가 끝났을 때
- 이미지가 깨진(broken) 상태일 때. 로드 실패나 이미지 비활성화가 원인입니다.

```js
const ok = img.complete && img.naturalWidth > 0
// true: 로드 성공 / false: 로딩 중이거나 실패
```

- `complete`만으로는 성공을 판단할 수 없습니다. 실패한 이미지도 `true`입니다. `naturalWidth > 0`을 함께 봅니다.
- `load` 리스너를 늦게 달면 이미 지나간 이벤트를 놓칩니다. 리스너를 달기 전에 `complete`를 먼저 확인합니다.
- `currentSrc`는 `srcset`·`sizes`·`<picture>`로 브라우저가 실제 고른 후보를 알려 줍니다. 뷰포트나 해상도가 바뀌어 다시 선택되면 값이 바뀔 수 있습니다.
- `naturalWidth`는 표시 크기와 다릅니다. 표시 크기는 `width` 속성·CSS·`clientWidth`가 정하고, 고유 크기는 파일이 정합니다. 두 값을 비교해 필요 이상으로 큰 이미지를 찾습니다.
- `decoding` 속성(`sync`, `async`, `auto`)은 디코딩을 페인트와 동기로 할지에 대한 힌트이고, `decode()`는 명시적으로 기다리는 방법입니다.

## 로딩 기능 검사

힌트와 속성은 브라우저마다 지원이 갈리므로, 쓰기 전에 기능을 검사해 지원할 때만 쓰고 아니면 대체합니다. 이름이나 `User-Agent`로 추측하지 않고 지원 여부를 직접 묻습니다.

### relList.supports()

`link.relList`는 `rel` 속성의 토큰 목록(`DOMTokenList`)이고, `supports(token)`은 그 토큰을 브라우저가 지원하면 `true`를 반환합니다. 모르는 토큰은 오류 없이 `false`입니다. Baseline 2018입니다.

```js
const link = document.createElement('link')

if (link.relList.supports('modulepreload')) {
  link.rel = 'modulepreload'
} else {
  link.rel = 'preload'
  link.as = 'script'
}
link.href = '/app/main.js'
document.head.append(link)
```

- 검사하는 것은 `rel` 토큰 이름뿐입니다. `as`나 `type` 값의 지원 여부는 알려 주지 않습니다.
- 같은 방식으로 `iframe.sandbox.supports()`, `link.blocking?.supports()`가 있습니다. 속성마다 정해진 토큰 목록이 있는 경우에만 `supports()`가 존재합니다.

### HTMLScriptElement.supports()

정적 메서드 `HTMLScriptElement.supports(type)`은 그 `<script>` 유형을 지원하는지 반환합니다. 유형은 `classic`, `module`, `importmap`, `speculationrules` 네 가지이고 대소문자를 구분하며, 다른 값은 `false`입니다. Baseline 2022입니다.

```js
HTMLScriptElement.supports('module')           // true
HTMLScriptElement.supports('importmap')        // 지원 시 true
HTMLScriptElement.supports('speculationrules')
// Chromium만 true
HTMLScriptElement.supports('Module')
// false (대소문자 구분)
```

- `speculationrules`는 지원할 뿐 아니라 활성화되어 있을 때 `true`입니다.
- 스크립트로 `<script type="speculationrules">`를 삽입하는 코드는 이 검사를 앞에 둡니다. 미지원 브라우저는 알 수 없는 유형의 스크립트를 실행하지 않고 무시하므로 해가 없지만, 불필요한 DOM 작업을 피할 수 있습니다.
- 호환성 대응 전반은 71편에서 다룹니다.

## 핵심 정리

- preload는 현재 페이지가 곧 쓸 늦게 발견되는 리소스를 앞당기고, prefetch는 다음 페이지용 리소스를 낮은 우선순위로 받으며, modulepreload는 모듈을 컴파일까지 해 둡니다.
- preload의 `as`·`crossorigin`이 소비하는 쪽 요청과 다르면 두 번 받습니다. 폰트는 같은 출처여도 `crossorigin`이 필요합니다.
- `fetchpriority`는 상대 우선순위 힌트(Baseline 2024)이고, `blocking="render"`와 Speculation Rules는 Baseline이 아니라 점진적 향상으로 씁니다.
- 지연 로딩은 `loading="lazy"`, 뷰포트 기반 `import()`, 상호작용 직전 `import()`로 나뉘며 LCP 이미지는 미루지 않습니다.
- `complete`는 실패한 이미지에도 `true`이므로 `naturalWidth`와 함께 보고, 지원이 갈리는 기능은 `relList.supports()`·`HTMLScriptElement.supports()`로 검사합니다.

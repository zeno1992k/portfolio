## Web Components가 해결하는 문제

HTML에는 `<button>`, `<video>`처럼 브라우저가 제공하는 요소만 있습니다. 탭, 모달, 날짜 선택기 같은 UI를 만들려면 `div` 여러 개와 CSS, 스크립트를 조합해야 하고, 이 조합에는 세 가지 문제가 따릅니다.

| 문제 | 증상 |
|------|------|
| 재사용 불가 | 마크업, 스타일, 스크립트가 흩어져 있어 복사해 붙이게 됨 |
| 이름 충돌 | 전역 CSS 선택자와 `id`가 페이지의 다른 부분과 겹침 |
| 프레임워크 종속 | 컴포넌트가 특정 프레임워크에서만 동작해서 다른 곳에서 못 씀 |

Web Components는 브라우저가 기본으로 제공하는 API의 묶음이며, 재사용할 수 있는 커스텀 요소를 만들고 이름 충돌과 스타일 충돌을 피하게 해 줍니다. 컴포넌트 기능이 라이브러리가 아니라 웹 플랫폼에 들어 있다는 점이 핵심입니다.

```html
<user-card name="Kim">
  <span slot="bio">개발자</span>
</user-card>
<!-- 일반 HTML 요소처럼 쓰는 커스텀 요소 -->
```

## Custom Elements + Shadow DOM + Template / Slot

Web Components는 세 가지 기술이 함께 쓰이는 이름입니다. 하나의 기술이 아닙니다.

| 기술 | 역할 | 핵심 API |
|------|------|----------|
| Custom Elements | 새 HTML 태그와 그 동작을 정의 | `customElements.define()`, 생명주기 콜백 |
| Shadow DOM | 요소 내부 DOM과 스타일을 바깥과 분리 | `attachShadow()`, `ShadowRoot` |
| HTML Templates와 Slots | 재사용할 마크업 틀과 외부 콘텐츠를 끼울 자리 | `template`, `slot` |

- 세 기술은 독립적입니다. Custom Elements만 쓸 수도 있고 Shadow DOM만 다른 요소에 붙일 수도 있습니다. 함께 쓸 때 효과가 가장 큽니다.
- Custom Elements는 17편, Shadow DOM은 21편, Template과 Slot은 22편에서 자세히 다룹니다.

만드는 순서는 다음과 같습니다.

1. `HTMLElement`를 상속한 클래스로 동작을 정의합니다.
2. `customElements.define()`으로 태그 이름에 등록합니다.
3. 필요하면 `attachShadow()`로 Shadow DOM을 붙입니다.
4. 필요하면 `template`과 `slot`으로 구조를 정합니다.
5. HTML에서 그 태그를 씁니다.

```js
class HelloBox extends HTMLElement {
  connectedCallback() {
    const root = this.attachShadow({ mode: 'open' })
    root.innerHTML = '<p>Hello, <slot></slot></p>'
  }
}
customElements.define('hello-box', HelloBox)
// <hello-box>Kim</hello-box> → Hello, Kim
```

## 브라우저 네이티브 컴포넌트 모델

Web Components의 컴포넌트 모델은 브라우저 안에 있습니다. 컴포넌트를 구성하는 개념이 모두 DOM의 개념으로 매핑됩니다.

| 컴포넌트 개념 | 브라우저 네이티브 대응 |
|---------------|------------------------|
| 컴포넌트 | 커스텀 요소(DOM 요소) |
| 입력(props) | 속성(attribute)과 프로퍼티(property) |
| 출력(events) | DOM 이벤트(`CustomEvent`) |
| 자식 콘텐츠(children) | Light DOM 자식과 `slot` |
| 내부 구조 | Shadow DOM 트리 |
| 스타일 캡슐화 | Shadow DOM 경계, CSS 사용자 정의 속성 |
| 생명주기 | `connectedCallback` 등 콜백 |

- 컴포넌트가 곧 DOM 요소라서 `querySelector`, `addEventListener`, `appendChild`, 개발자 도구 같은 기존 도구를 그대로 씁니다.
- 라이브러리의 런타임이 필요 없습니다. 브라우저가 요소를 만들고 생명주기를 호출합니다.
- 컴포넌트는 HTML 파서가 만나는 순간에도 동작합니다. 정의가 나중에 등록되면 이미 문서에 있던 요소가 그때 업그레이드됩니다(자세히는 17편).
- 컴포넌트 정의 파일은 `type="module"` 스크립트(14편)로 불러오는 것이 일반적인 방식입니다.

## Autonomous Custom Element

자율적 커스텀 요소(autonomous custom element)는 `HTMLElement`를 직접 상속해 만드는 완전히 새로운 요소입니다. 기본 동작이 없어서 모든 것을 스스로 구현합니다.

```js
class PopupInfo extends HTMLElement {}
customElements.define('popup-info', PopupInfo)
```

```html
<popup-info></popup-info>
```

- 태그 이름은 소문자 ASCII 알파벳으로 시작하고, 대문자를 포함하지 않으며, 하이픈(-)을 하나 이상 포함해야 합니다. 하이픈 규칙은 이름 충돌을 막고 앞으로 HTML에 추가될 표준 요소와의 호환을 보장하기 위한 것입니다.
- `annotation-xml`, `color-profile`, `font-face`, `font-face-src`, `font-face-uri`, `font-face-format`, `font-face-name`, `missing-glyph`는 예약된 이름이라 쓸 수 없습니다.
- 접근성에 필요한 것(포커스, ARIA 역할, 키보드 조작)을 직접 구현해야 합니다. 기본 의미가 없는 요소이기 때문입니다(자세히는 27편, 28편).
- Baseline 2020(Chrome 54, Firefox 63, Safari 10.1부터)입니다. 널리 지원됩니다.

**흔한 실수:** 이름에 하이픈을 빼먹는 것입니다. `define('popup', ...)`은 `SyntaxError`입니다.

## Customized Built-in Element

확장된 기본 요소(customized built-in element)는 `<p>`, `<button>` 같은 기존 HTML 요소의 클래스(`HTMLParagraphElement` 등)를 상속해서 그 요소의 기능을 확장합니다. 정의할 때 `extends` 옵션으로 확장할 태그를 알리고, 마크업에서 `is` 속성으로 사용합니다.

```js
class WordCount extends HTMLParagraphElement {}
customElements.define('word-count', WordCount, {
  extends: 'p',
})
```

```html
<p is="word-count"></p>
```

- 태그는 그대로 `p`이고 `is` 속성이 사용자 정의 동작을 지정합니다. 포커스, 키보드 조작, 접근성 의미를 확장 대상 요소에서 그대로 물려받는 것이 장점입니다. HTML 표준은 자율적 요소보다 접근성 구현이 훨씬 쉽다고 설명합니다.
- 지원 상태: Baseline이 아닙니다. web-features 데이터 기준으로 Chrome 67, Edge 79, Firefox 63부터 지원하고 Safari는 지원하지 않습니다. MDN은 Safari가 지원할 계획이 없다고 안내합니다.
- 그래서 Safari에서도 동작해야 하는 코드에서는 Customized built-in 대신 자율적 요소를 쓰고, 내부에 기본 요소(`button` 등)를 넣어 감싸는 방식을 택합니다.
- `extends`에는 기본 요소만 쓸 수 있습니다. 커스텀 요소를 가리키면 `NotSupportedError`입니다.
- Shadow DOM은 모든 요소에 붙일 수는 없습니다(허용 목록은 21편). 자세한 정의와 업그레이드는 17편에서 다룹니다.

| 구분 | Autonomous | Customized Built-in |
|------|------------|---------------------|
| 상속 대상 | `HTMLElement` | `HTMLParagraphElement` 등 기본 요소 클래스 |
| 마크업 | `<popup-info>` | `<p is="word-count">` |
| 기본 동작·접근성 | 없음(직접 구현) | 기본 요소의 것을 물려받음 |
| `define`의 `extends` | 쓰지 않음 | 필수 |
| 지원 | Baseline 2020 | 미Baseline, Safari 미지원 |

## Light DOM vs Shadow DOM

Light DOM은 문서의 일반 DOM 트리입니다. 페이지 작성자가 요소의 자식으로 넣는 콘텐츠와 일반 DOM이 여기 속합니다. Shadow DOM은 요소(shadow host)에 붙는 분리된 DOM 트리입니다. 구조 용어는 다음과 같습니다.

| 용어 | 뜻 |
|------|----|
| shadow host | Shadow DOM이 붙는 일반 DOM 노드 |
| shadow root | 그림자 트리의 루트 노드(`ShadowRoot`) |
| shadow tree | 그림자 안의 DOM 트리 |
| shadow boundary | 그림자 DOM이 끝나고 일반 DOM이 시작되는 경계 |

```js
const host = document.querySelector('#host')
const shadow = host.attachShadow({ mode: 'open' })
shadow.innerHTML = '<span>내부</span>'
document.querySelector('span') // null (그림자 안은 보이지 않음)
```

```html
<div id="host">
  <template shadowrootmode="open">
    <span>내부</span>
  </template>
</div>
```

- 외부의 `document.querySelectorAll()`은 그림자 안의 요소를 찾지 못합니다. 페이지 CSS 선택자도 그림자 안의 요소에 적용되지 않고, 그림자 안의 스타일도 페이지에 새어 나가지 않습니다.
- `mode: 'open'`이면 `element.shadowRoot`로 접근할 수 있고, `'closed'`면 `shadowRoot`가 `null`입니다. 이는 우발적 접근을 막는 수준이지 보안 장치가 아닙니다(자세히는 21편, 63편).
- 선언적 Shadow DOM(`template`의 `shadowrootmode`)은 JavaScript 없이 HTML만으로 그림자를 만듭니다. 서버에서 렌더링한 HTML에 포함할 수 있고 Baseline 2024입니다.
- Light DOM의 자식은 `slot`을 통해 그림자 안의 정해진 자리에 표시됩니다. 자식 노드는 여전히 Light DOM에 있고 보이는 위치만 슬롯 자리입니다(자세히는 22편).

| 비교 | Light DOM | Shadow DOM |
|------|-----------|------------|
| 스타일 | 페이지 CSS의 영향을 받음 | 바깥 CSS와 분리 |
| 선택 | `querySelector`로 찾음 | 바깥에서 안 찾아짐 |
| 용도 | 사용자 제공 콘텐츠 | 컴포넌트 내부 구조 |
| 외부 커스터마이징 | 자유로움 | `::part`, CSS 사용자 정의 속성, 슬롯 등 정해진 통로만 |

Shadow DOM을 쓰지 않고 Light DOM에 직접 그리는 컴포넌트도 만들 수 있습니다. 페이지 CSS를 그대로 적용받아야 하는 경우입니다(자세히는 21편).

## 컴포넌트 경계와 public API

컴포넌트 경계는 컴포넌트의 안과 밖을 가르는 선입니다. 경계 바깥에 약속으로 노출하는 부분이 public API이고, 나머지는 내부 구현이라 언제든 바꿔도 됩니다. Web Components에서 사용자가 접하는 통로는 정해져 있습니다.

| 통로 | 방향 | 예 |
|------|------|----|
| 속성(attribute) | 밖에서 안으로 | `<my-btn size="large">` |
| 프로퍼티(property) | 밖에서 안으로 | `el.value = 3` |
| 메서드 | 밖에서 안으로 | `dialog.open()` |
| 이벤트 | 안에서 밖으로 | `CustomEvent`('selected') |
| 슬롯 | 밖의 콘텐츠를 안에 | `<span slot="title">` |
| CSS 사용자 정의 속성 | 밖의 스타일을 안에 | `--accent: red` |
| `part` | 밖에서 내부 요소 스타일링 | `my-btn::part(label)` |

- 내부 DOM, 내부 클래스 이름, 비공개 필드(`#state`)는 public API가 아닙니다. 그림자 안의 구조는 바깥이 의존할 수 없어서 바꾸기 쉽습니다.
- 속성은 문자열만 담고 프로퍼티는 어떤 값이든 담습니다. 객체나 배열을 넘기려면 프로퍼티를 씁니다(자세히는 19편).
- 스타일 통로는 23편, 이벤트와 통신은 25편에서 다룹니다.
- public API를 한 번 공개하면 바꾸기 어렵습니다. 이름 변경과 제거는 하위 호환성 문제가 됩니다(자세히는 19편).

## 프레임워크 컴포넌트와의 차이

프레임워크 컴포넌트(React, Vue 등)는 프레임워크의 런타임과 렌더링 모델 위에서 동작하는 컴포넌트입니다. Web Components는 브라우저 표준 위에서 동작하는 DOM 요소입니다. 프레임워크 내부는 이 과목의 범위가 아니라서 개념 수준의 차이만 비교합니다.

| 항목 | Web Components | 프레임워크 컴포넌트 |
|------|----------------|---------------------|
| 실행 기반 | 브라우저 표준 API | 프레임워크 런타임 |
| 상태·반응형 갱신 | 내장 없음. 직접 만들거나 라이브러리 사용 | 프레임워크가 제공 |
| 템플릿 | `template`, 문자열, 태그드 템플릿 등을 직접 선택 | 프레임워크의 템플릿 문법 |
| 데이터 전달 | 속성(문자열), 프로퍼티, 이벤트 | 프레임워크의 props 모델 |
| 스타일 캡슐화 | Shadow DOM(브라우저가 보장) | CSS 모듈, 스코프 CSS 등(규칙은 도구마다 다름) |
| 재사용 범위 | 어떤 프레임워크, 일반 HTML에서도 | 해당 프레임워크 안 |
| 렌더링 | 직접 DOM을 갱신 | 가상 DOM 비교나 컴파일된 갱신 코드 |

- Web Components에는 상태가 바뀔 때 화면을 자동으로 갱신하는 기능이 없습니다. 이 부분은 직접 구현하거나(30편, 31편) 라이브러리를 씁니다.
- 프레임워크 안에서 커스텀 요소를 쓸 수도 있습니다. 커스텀 요소는 일반 DOM 요소여서 프레임워크가 이를 어떻게 다루는지(프로퍼티 전달, 이벤트 연결)는 프레임워크마다 다릅니다.
- 대체 관계가 아닙니다. 프레임워크로 만든 앱에서 공통 UI 부품만 Web Components로 만들거나, 반대로 Web Components로만 앱을 만들 수 있습니다.

## 언제 Web Components를 선택할지

Web Components가 맞는 경우와 맞지 않는 경우를 판단하는 기준입니다.

| 맞는 경우 | 이유 |
|-----------|------|
| 여러 프레임워크나 일반 HTML 페이지에서 쓰는 공통 UI 부품(디자인 시스템) | 프레임워크에 묶이지 않음 |
| 제3자 페이지에 삽입되는 위젯 | Shadow DOM으로 호스트 페이지의 CSS와 분리 |
| 수명이 길어서 프레임워크 교체에 영향받지 않아야 하는 부품 | 브라우저 표준에 의존 |
| 서버가 렌더링한 HTML에 점진적으로 기능을 얹는 경우 | 요소 업그레이드 방식 |

| 맞지 않거나 불리한 경우 | 이유 |
|-------------------------|------|
| 상태가 복잡하고 화면 갱신이 잦은 대규모 앱 전체 | 반응형 상태와 갱신을 직접 만들거나 라이브러리를 더해야 함 |
| 팀이 이미 프레임워크 하나로 통일되어 있고 재사용 범위가 그 안뿐인 경우 | 얻는 이점이 적음 |
| 페이지 전체 CSS를 그대로 적용받아야 하는 컴포넌트 | Shadow DOM 분리가 방해가 됨(Light DOM 방식 고려) |

- 접근성과 폼 연동처럼 기본 요소가 해 주던 일을 직접 구현해야 합니다(자세히는 26편, 27편, 28편).
- 선택은 이분법이 아닙니다. 표준 위에 얇은 라이브러리를 얹는 중간 선택지가 있습니다(아래 Lit).

## v0 폐기와 v1 표준의 역사

Web Components에는 초기 버전(v0)과 표준화된 v1이 있고, 지금의 표준은 v1입니다.

| 구분 | v0(폐기) | v1(현재 표준) |
|------|----|---------------|
| 커스텀 요소 등록 | `document.registerElement()` | `customElements.define()` |
| 그림자 생성 | `createShadowRoot()` | `attachShadow()` |
| HTML 파일 가져오기 | HTML Imports | ES 모듈(`import`) |

- Chrome 블로그는 v0 API(Custom Elements v0, Shadow DOM v0, HTML Imports)를 Chrome 80(2020년 2월경)에서 제거하는 것을 목표로 한다고 2019년에 안내했습니다.
- v1은 Chrome, Safari, Firefox가 모두 구현한 웹 플랫폼 표준입니다. 지금 쓰는 모든 문서와 라이브러리는 v1을 기준으로 합니다.
- 옛 글에서 `registerElement`, `createShadowRoot`, `<link rel="import">`, `::shadow`, `/deep/`을 보면 v0 시절 내용입니다. 따라 쓰면 동작하지 않습니다.
- HTML Imports가 없어졌으므로 컴포넌트 정의 파일은 ES 모듈로 불러옵니다(자세히는 14편).

## 관련 명세의 위치

Web Components는 하나의 명세가 아니라 여러 표준에 나뉘어 있습니다. 문제가 생겼을 때 어느 문서를 볼지 알아 두면 좋습니다.

| 기능 | 정의된 곳 |
|------|-----------|
| Custom Elements(`CustomElementRegistry`, 생명주기, `ElementInternals`) | HTML 표준 |
| `template`, `slot` 요소, Declarative Shadow DOM 파싱 | HTML 표준 |
| Shadow DOM 트리(ShadowRoot, 슬롯 할당, 이벤트 리타깃팅) | DOM 표준 |
| `:host`, `::slotted`, `::part` 등 스타일링 | CSS Scoping 등 CSS 명세 |

- 레퍼런스는 MDN의 Web components 문서가 정리되어 있고, 규칙의 정확한 근거는 HTML 표준과 DOM 표준입니다.
- 접근성 패턴은 WAI-ARIA Authoring Practices를 따릅니다(27편, 28편).

## Lit 같은 라이브러리가 더해 주는 것

Lit은 Web Components를 쉽게 만들도록 돕는 작은 라이브러리입니다. 결과물은 표준 커스텀 요소여서 어떤 프레임워크나 일반 HTML에서도 동작합니다. 공식 문서는 압축 후 약 5KB 정도라고 소개합니다. 표준 API만으로 직접 만들 때 번거로운 부분을 채웁니다.

| 직접 만들면 | Lit이 제공 |
|-------------|------------|
| 프로퍼티가 바뀔 때 직접 렌더링 호출 | 반응형 프로퍼티: 바뀌면 자동 재렌더링 |
| `innerHTML`이나 DOM 코드로 직접 갱신 | 선언적 템플릿(JavaScript 태그드 템플릿 리터럴) |
| 스타일 캡슐화를 직접 설정 | 기본으로 범위가 정해진 스타일 |
| 보일러플레이트가 많은 기본 클래스 | `HTMLElement`를 확장한 `LitElement` 기반 클래스 |

- Lit은 동적으로 바뀌는 부분만 추적해서 그 부분만 갱신합니다. 가상 DOM을 만들지 않습니다.
- 라이브러리를 쓰든 안 쓰든 플랫폼 개념(생명주기, 속성과 프로퍼티, 슬롯, Shadow DOM)은 같습니다. 이 과목은 그 기반 개념을 다룹니다. 직접 만드는 렌더링 구조는 30편과 31편에서 다룹니다.

## 구성 기술별 지원 상태

web-features 데이터(3.40.1) 기준입니다. Baseline 20XX는 모든 핵심 브라우저가 지원하기 시작한 해입니다.

| 기술 | 지원 상태 | 비고 |
|------|-----------|------|
| Autonomous Custom Elements | Baseline 2020 | Chrome 54, Firefox 63, Safari 10.1 |
| Shadow DOM | Baseline 2020 | Chrome 53, Firefox 63, Safari 10 |
| `slot` | Baseline 2020 | 같은 시기 |
| `template` 요소 | Baseline 2015 | |
| `::part()` | Baseline 2020 | Chrome 73, Firefox 72, Safari 13.1 |
| 수동 슬롯 할당(`slotAssignment`) | Baseline 2023 | |
| Form-associated Custom Elements | Baseline 2023 | 자세히는 26편 |
| Declarative Shadow DOM | Baseline 2024 | Chrome 111, Firefox 123, Safari 16.4 |
| `:state()` | Baseline 2024 | 자세히는 20편 |
| Customized Built-in Elements | 미Baseline | Safari 미지원 |
| Scoped Custom Element Registries | 미Baseline | Chrome 146, Safari 26부터(자세히는 17편) |

- 핵심 기능(커스텀 요소, Shadow DOM, 슬롯, 템플릿)은 널리 지원되므로 현재 브라우저에서는 폴리필 없이 쓸 수 있습니다.
- 미Baseline 기능은 지원 엔진을 확인하고 점진적 향상으로 다룹니다.

## 핵심 정리

- Web Components는 Custom Elements, Shadow DOM, Template과 Slot이라는 세 브라우저 표준 기술의 묶음이고, 재사용 가능한 요소를 만들고 이름·스타일 충돌을 막습니다.
- 컴포넌트는 곧 DOM 요소이며 입력은 속성과 프로퍼티, 출력은 이벤트, 자식은 슬롯, 캡슐화는 Shadow DOM으로 브라우저가 제공합니다.
- 자율적 요소는 `HTMLElement`를 상속하고 태그 이름에 하이픈이 필요하며, 확장된 기본 요소는 `is` 속성으로 쓰고 Safari는 지원하지 않습니다.
- Light DOM은 페이지의 일반 DOM, Shadow DOM은 분리된 내부 트리이고, 외부와의 통로는 속성, 프로퍼티, 메서드, 이벤트, 슬롯, CSS 사용자 정의 속성, `part`뿐입니다.
- Web Components에는 반응형 상태 갱신이 없어서 프레임워크 컴포넌트와 역할이 다르며, 프레임워크 간 공유 부품, 삽입 위젯, 디자인 시스템에 알맞습니다.
- v0(`registerElement`, `createShadowRoot`, HTML Imports)는 폐기되었고 v1이 표준이며, 핵심 기능은 모두 Baseline으로 널리 지원됩니다.

## Same-Origin Policy

동일 출처 정책(Same-Origin Policy)은 한 출처의 문서나 스크립트가 다른 출처의 리소스를 읽는 것을 제한하는 브라우저의 기본 보안 모델입니다. 쓰기와 삽입은 허용하고 읽기는 막는 것이 핵심입니다.

출처(origin)는 스킴, 호스트, 포트 세 값의 조합입니다. 셋이 모두 같아야 같은 출처입니다.

| URL | `https://a.com/x` 와의 관계 |
|-----|------------------------------|
| `https://a.com/y` | 같은 출처(경로만 다름) |
| `http://a.com/x` | 다른 출처(스킴) |
| `https://b.a.com/x` | 다른 출처(호스트) |
| `https://a.com:8443/x` | 다른 출처(포트) |

| 교차 출처 동작 | 기본 허용 여부 |
|----------------|----------------|
| 링크 이동, 리다이렉트, 폼 제출(쓰기) | 허용 |
| `script`, `link`(CSS), `img`, `video`, `audio`, `iframe`, `@font-face`로 삽입 | 허용(`iframe`은 `X-Frame-Options`나 CSP로 막을 수 있음) |
| `fetch`·`XMLHttpRequest`로 응답 읽기, 다른 출처 DOM·저장소 접근 | 차단 |

- 삽입은 되지만 내용 읽기는 막혀 있습니다. 이미지의 크기나 스크립트 실행 여부 같은 부수 정보는 새어 나갈 수 있어서 이 차이를 악용한 공격이 있습니다(자세히는 아래 COOP·CORP).
- 저장소(Web Storage, IndexedDB)는 출처별로 분리됩니다(자세히는 40편, 41편). 쿠키는 별도 규칙이라 호스트와 경로 단위이며 포트를 구분하지 않습니다.
- `about:blank`와 `javascript:` URL의 문서는 이를 만든 문서의 출처를 상속합니다.
- `file:` URL은 현대 브라우저에서 불투명 출처로 취급되어 같은 폴더의 파일끼리도 같은 출처로 보지 않습니다.
- 다른 출처 창 객체에는 `postMessage()`, `location` 쓰기, `frames`, `closed`, `focus()`, `close()` 같은 제한된 멤버만 접근할 수 있고 나머지는 `SecurityError`입니다.
- 서로 다른 출처가 소통하는 표준 수단은 `postMessage()`이고, 서버 데이터는 CORS로 허용합니다.

`document.domain`에 상위 도메인을 대입해 서브도메인끼리 출처를 맞추는 방식은 폐기되었습니다. 쓰지 않습니다.

### origin과 site

사이트(site)는 등록 가능한 도메인(eTLD+1, Public Suffix List 기준)을 기준으로 합니다. 출처보다 느슨한 개념입니다.

| 비교 | 같은 출처 | 같은 사이트 |
|------|-----------|-------------|
| `https://a.example.com` vs `https://b.example.com` | 아니오 | 예 |
| `https://example.com` vs `https://example.com:8443` | 아니오 | 예(포트는 무시) |
| `http://example.com` vs `https://example.com` | 아니오 | 스킴을 따지면(schemeful same-site) 아니오 |
| `https://a.github.io` vs `https://b.github.io` | 아니오 | 아니오(`github.io`가 공개 접미사) |

- 같은 출처 판단은 CORS와 `postMessage`, Web Storage가 쓰고, 같은 사이트 판단은 `SameSite` 쿠키, `Sec-Fetch-Site`, COOP·CORP의 `same-site`가 씁니다.
- 서브도메인은 같은 사이트라서 한 서브도메인의 XSS가 다른 서브도메인을 위협합니다. 신뢰 경계는 출처가 아니라 사이트로 그어지는 곳이 있다는 뜻입니다.

## 보안 컨텍스트와 혼합 콘텐츠

보안 컨텍스트(secure context)는 HTTPS나 loopback(`localhost`, `127.0.0.1`)처럼 전달 과정이 기밀이라고 볼 수 있는 환경입니다. 서비스 워커, Clipboard, 위치 정보, Web Crypto의 `subtle` 같은 강력한 API는 보안 컨텍스트에서만 노출됩니다.

```js
if (window.isSecureContext) {
  await navigator.serviceWorker.register('/sw.js')
}
```

- iframe은 자신의 URL이 신뢰할 만하고 상위 문서도 보안 컨텍스트일 때만 보안 컨텍스트입니다. HTTP 문서 안의 HTTPS iframe은 보안 컨텍스트가 아닙니다.
- 워커는 만든 컨텍스트의 상태를 이어받고, 워커에서도 `isSecureContext`를 읽을 수 있습니다.
- Baseline 널리 지원(`isSecureContext`, 2018).

HTTPS 문서가 HTTP 리소스를 불러오는 것이 혼합 콘텐츠(mixed content)입니다. 현재 브라우저는 두 갈래로 처리합니다.

| 구분 | 대상 | 처리 |
|------|------|------|
| 업그레이드 가능 | `img`, `audio`, `video`, CSS 배경 이미지 | 자동으로 HTTPS로 올림(IP 주소 URL은 차단) |
| 차단 | `script`, 스타일시트, `iframe`, `fetch`·XHR, 웹 폰트, `sendBeacon`, `srcset` 이미지 | 요청 자체를 차단 |

CSP의 `upgrade-insecure-requests`는 문서의 모든 HTTP 요청을 HTTPS로 올립니다. `block-all-mixed-content`는 폐기되었습니다.

## CORS

CORS(Cross-Origin Resource Sharing)는 서버가 응답 헤더로 "이 출처의 스크립트가 응답을 읽어도 좋다"고 알리는 프로토콜입니다. 동일 출처 정책을 서버가 선택적으로 푸는 수단이며, 차단은 응답을 받은 뒤 브라우저가 합니다. 서버로 요청은 이미 도착했을 수 있습니다. Baseline 널리 지원합니다.

```js
const res = await fetch('https://api.example.com/items')
// 응답에 Access-Control-Allow-Origin이 없으면
// TypeError: Failed to fetch (본문·헤더를 읽을 수 없음)
```

CORS 오류의 거의 전부는 서버 설정으로만 해결됩니다. 브라우저 쪽 우회는 없습니다. 서버를 고칠 수 없으면 자기 서버가 대신 요청하는 프록시로 같은 출처 요청으로 바꿉니다.

### 단순 요청 조건

아래를 모두 만족하면 프리플라이트 없이 바로 전송됩니다(Fetch 표준의 CORS 안전 목록).

| 항목 | 허용 범위 |
|------|-----------|
| 메서드 | `GET`, `HEAD`, `POST` |
| 요청 헤더 | `Accept`, `Accept-Language`, `Content-Language`, `Content-Type`(제한), 단일 범위의 `Range`. 값 길이 128바이트 이하. 브라우저가 붙이는 헤더 제외 |
| `Content-Type` | `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`만 |
| 기타 | `XMLHttpRequest.upload`에 리스너가 없고, 요청 본문에 `ReadableStream`을 쓰지 않음 |

`application/json` 본문이나 `Authorization` 같은 사용자 지정 헤더는 단순 요청이 아니라서 프리플라이트가 따릅니다.

### 응답 헤더

| 헤더 | 뜻 |
|------|----|
| `Access-Control-Allow-Origin` | 허용하는 출처 하나, 또는 `*`(자격 증명 없는 요청만) |
| `Access-Control-Allow-Methods` | 프리플라이트 응답: 허용하는 메서드 |
| `Access-Control-Allow-Headers` | 프리플라이트 응답: 허용하는 요청 헤더 |
| `Access-Control-Max-Age` | 프리플라이트 결과를 캐시할 초 |
| `Access-Control-Expose-Headers` | 스크립트가 읽을 수 있게 노출할 응답 헤더 |
| `Access-Control-Allow-Credentials` | `true`면 자격 증명 포함 요청을 허용 |
| `Vary: Origin` | 응답이 요청의 `Origin`에 따라 달라짐을 캐시에 알림 |

- 요청에는 항상 `Origin` 헤더가 붙습니다. 값은 스킴·호스트·포트이며 불투명 출처면 `null`입니다.
- 서버가 허용 출처를 동적으로 정할 때는 반드시 `Vary: Origin`을 붙입니다. 안 붙이면 CDN이 한 출처용 응답을 다른 출처에 내줍니다.
- 스크립트가 기본으로 읽을 수 있는 응답 헤더는 7개(`Cache-Control`, `Content-Language`, `Content-Length`, `Content-Type`, `Expires`, `Last-Modified`, `Pragma`)뿐입니다. 나머지는 `Access-Control-Expose-Headers`에 나열해야 읽힙니다.

```http
Access-Control-Allow-Origin: https://app.example
Vary: Origin
Access-Control-Expose-Headers: X-Request-Id
```

### opaque 응답과 no-cors

`fetch`의 요청 모드는 네 가지입니다.

| 모드 | 동작 |
|------|------|
| `cors` | 기본값. CORS 프로토콜을 따르고 통과해야 응답을 읽음 |
| `same-origin` | 교차 출처 요청을 거부 |
| `no-cors` | 안전 목록 메서드·헤더만 허용. 응답은 읽을 수 없는 opaque 응답 |
| `navigate` | 문서 이동용(스크립트가 직접 지정하지 않음) |

```js
const r = await fetch(url, { mode: 'no-cors' })
console.log(r.type, r.status, r.ok) // 'opaque' 0 false
```

opaque 응답은 상태 코드 `0`, 빈 헤더, 읽을 수 없는 본문입니다. 요청은 보내지만 결과를 못 읽으므로 로그 전송 같은 용도뿐이고, CORS 오류를 우회하는 수단이 아닙니다. 서비스 워커의 캐시에 넣을 수는 있으나 내용을 검증할 수 없습니다. `<img crossorigin>`처럼 `crossorigin` 속성을 주면 요청이 `cors` 모드가 됩니다.

## Preflight

프리플라이트(preflight)는 단순 요청이 아닌 요청을 보내기 전에 브라우저가 먼저 `OPTIONS` 요청으로 서버의 허락을 확인하는 단계입니다. 스크립트가 직접 보내지 않고 브라우저가 자동으로 보냅니다.

```http
OPTIONS /items HTTP/1.1
Origin: https://app.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type,x-token
```

서버는 허용 범위를 응답해야 합니다.

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Methods: GET, PUT
Access-Control-Allow-Headers: Content-Type, X-Token
Access-Control-Max-Age: 600
```

- 프리플라이트가 필요한 경우: `PUT`·`DELETE`·`PATCH` 같은 안전 목록 밖의 메서드, 사용자 지정 헤더나 `Authorization`, `application/json` 같은 안전 목록 밖의 `Content-Type`.
- 응답 상태가 200–299(성공 범위)가 아니면 실패합니다. 서버 프레임워크가 `OPTIONS`에 404나 401을 주지 않게 합니다.
- 프리플라이트 요청에는 쿠키와 `Authorization`이 실리지 않습니다. 그래서 인증이 필요한 서버도 `OPTIONS`는 인증 없이 응답해야 합니다.
- 프리플라이트에 대한 리다이렉트는 일부 브라우저가 오류로 처리합니다. 최종 URL을 직접 호출합니다.
- `Access-Control-Max-Age`의 기본값은 5초입니다. 브라우저는 상한을 두어 Chromium은 2시간(7200초), Firefox는 24시간(86400초)까지만 캐시합니다. 상한은 브라우저 구현 값이라 바뀔 수 있습니다.
- 와일드카드 `*`는 `Authorization` 헤더를 포함하지 못합니다. `Authorization`은 목록에 명시해야 합니다.

**흔한 실수:** 프리플라이트가 매번 나가서 지연이 생기는 것입니다. `Access-Control-Max-Age`를 지정하고, 가능하면 요청을 단순 요청 형태로 바꿉니다.

## credentials

기본적으로 교차 출처 `fetch`에는 쿠키·HTTP 인증·TLS 클라이언트 인증서 같은 자격 증명(credentials)이 실리지 않습니다. 요청 옵션 `credentials`가 정합니다.

| 값 | 동작 |
|----|------|
| `omit` | 어떤 요청에도 자격 증명을 보내지 않음 |
| `same-origin` | 기본값. 같은 출처 요청에만 보냄 |
| `include` | 교차 출처에도 보냄 |

```js
fetch('https://api.example.com/me', {
  credentials: 'include',
})
// XMLHttpRequest는 xhr.withCredentials = true
```

자격 증명 요청이 성공하려면 서버가 두 조건을 모두 만족해야 합니다.

```http
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true
```

- 자격 증명 요청에서는 `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, `Access-Control-Expose-Headers`에 `*`를 쓸 수 없고 명시적 목록이어야 합니다.
- 요청 `Origin`을 그대로 되돌려주는 "반사" 구현은 임의 사이트에 자격 증명 접근을 허락하므로 허용 목록과 비교한 뒤에만 반사합니다.
- 교차 사이트 요청에 쿠키가 실리려면 쿠키가 `SameSite=None; Secure`여야 하고, 서드파티 쿠키를 막는 브라우저에서는 그래도 실리지 않습니다(아래 서드파티 쿠키 절).

## postMessage Origin 검증

`window.postMessage()`는 출처가 다른 창·iframe 사이에 메시지를 주고받는 표준 방법입니다. 메시지는 구조적 복제로 전달됩니다(자세히는 59편). 보내는 쪽은 받는 쪽 출처를, 받는 쪽은 보낸 쪽 출처를 검증해야 합니다.

```js
// 보내는 쪽: 대상 출처를 명시
popup.postMessage({ token }, 'https://pay.example')
// ❌ popup.postMessage({ token }, '*')

// 받는 쪽: 출처를 정확히 비교
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://app.example') return
  if (e.source !== iframe.contentWindow) return
  handle(e.data)
})
```

- `targetOrigin`을 생략하면 `/`(보내는 문서와 같은 출처)로 취급됩니다. `*`는 수신 창의 현재 출처가 무엇이든 전달하므로 민감한 데이터에는 쓰지 않습니다. 창이 이동한 뒤 다른 출처가 되었을 수 있기 때문입니다.
- 받는 쪽은 `event.origin`을 허용 목록과 완전 일치로 비교합니다. `indexOf`, `endsWith`, 앵커 없는 정규식은 `https://app.example.evil.com` 같은 값을 통과시킵니다.
- 필요하면 `event.source`로 보낸 창을 확인하고, `event.data`의 형식과 값도 검증합니다. 메시지 내용은 신뢰된 입력이 아닙니다.
- 기대하지 않는 메시지를 처리하지 않습니다. 리스너를 필요한 기간에만 두고 끝나면 제거합니다.
- 보내는 쪽 출처가 불투명(sandbox 등)이면 `event.origin`이 `'null'`입니다. 이 값을 허용 목록에 넣지 않습니다.
- 받은 데이터를 `innerHTML`에 그대로 넣으면 XSS입니다(자세히는 63편).

## Fetch Metadata 요청 헤더

Fetch Metadata는 브라우저가 요청에 자동으로 붙이는 `Sec-Fetch-*` 헤더로, 서버가 요청의 맥락을 보고 거부할 수 있게 합니다. `Sec-`로 시작하는 헤더는 스크립트가 바꿀 수 없습니다(금지된 요청 헤더). 신뢰할 수 있는 URL(HTTPS)로만 보냅니다. `Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`는 Baseline 2023, `Sec-Fetch-User`는 미Baseline입니다.

| 헤더 | 값 |
|------|----|
| `Sec-Fetch-Site` | `same-origin`, `same-site`, `cross-site`, `none`(주소창 입력·북마크 같은 사용자 시작) |
| `Sec-Fetch-Mode` | 요청 모드(`cors`, `navigate`, `no-cors`, `same-origin`, `websocket`) |
| `Sec-Fetch-Dest` | 요청 대상 종류(`document`, `iframe`, `image`, `script`, `empty` 등) |
| `Sec-Fetch-User` | 사용자 활성화로 시작된 이동이면 `?1` |

서버는 이 값으로 리소스 격리 정책을 구현합니다. 상태를 바꾸는 엔드포인트가 `cross-site` 요청을 거부하는 방식이 CSRF 방어에도 쓰입니다(자세히는 63편).

```js
// 서버 쪽 의사 코드
if (req.get('Sec-Fetch-Site') === 'cross-site') {
  return res.status(403).end()
}
```

헤더가 없는 구형 브라우저의 요청은 막지 않고 다른 방어에 맡깁니다.

## COOP·COEP·CORP와 교차 출처 격리

세 헤더는 문서를 다른 출처로부터 격리해, 강력한 API를 켜는 조건(교차 출처 격리)을 만듭니다.

| 헤더 | 정하는 것 |
|------|-----------|
| `Cross-Origin-Opener-Policy`(COOP) | 문서가 다른 출처의 창과 브라우징 컨텍스트 그룹을 공유할지 |
| `Cross-Origin-Embedder-Policy`(COEP) | 문서가 불러오는 교차 출처 리소스에 허가를 요구할지 |
| `Cross-Origin-Resource-Policy`(CORP) | 이 리소스를 어느 출처·사이트가 `no-cors`로 불러올 수 있는지 |

### COOP

| 값 | 동작 |
|----|------|
| `unsafe-none` | 기본값. `window.opener`가 유지될 수 있음 |
| `same-origin-allow-popups` | 같은 출처 창과만 그룹을 공유. 자신이 연 `unsafe-none` 팝업과는 관계 유지(OAuth, 결제 팝업) |
| `same-origin` | 같은 출처이면서 같은 값인 문서와만 그룹 공유. 다른 출처와는 `opener` 관계가 끊김 |
| `noopener-allow-popups` | 항상 새 그룹. `opener`가 끊기고 `window.closed`가 `true`. 같은 출처 앱끼리도 격리 |

`rel=noopener`는 나가는 이동에만 적용되지만 COOP는 `window.open()`과 이동 양쪽에 적용됩니다.

### COEP와 CORP

| COEP 값 | 동작 |
|---------|------|
| `unsafe-none` | 기본값. 교차 출처 `no-cors` 리소스를 자유롭게 로드 |
| `require-corp` | 교차 출처 `no-cors` 리소스는 CORP가 허용할 때만 로드. `cors` 모드 요청은 CORS를 통과하면 됨 |
| `credentialless` | CORP 없이도 로드하되 자격 증명(쿠키)을 빼고 요청 |

CORP의 값은 `same-origin`, `same-site`, `cross-origin`입니다. CORS가 요청한 쪽의 읽기 허가라면 CORP는 리소스 소유자가 "누가 나를 로드할 수 있는가"를 정하는 정책이고, `no-cors` 요청을 대상으로 합니다. `same-site`는 서브도메인까지 허용해 `same-origin`보다 느슨합니다.

```html
<img src="https://cdn.example/a.png" crossorigin>
```

`require-corp` 환경에서 서드파티 리소스는 CORP 헤더가 붙은 것만 로드됩니다. 서드파티가 헤더를 줄 수 없으면 `crossorigin` 속성으로 `cors` 모드로 요청하거나(서버가 CORS를 허용해야 함) `credentialless`를 씁니다. `Cross-Origin-Embedder-Policy-Report-Only`로 막기 전에 위반만 보고받아 점검할 수 있습니다.

### crossOriginIsolated

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

두 헤더가 갖춰지면 `window.crossOriginIsolated`가 `true`가 되고(Permissions-Policy `cross-origin-isolated`가 막지 않은 경우), 다음이 켜집니다.

- `SharedArrayBuffer` 생성과 `postMessage` 전달(자세히는 55편)
- 고해상도 `performance.now()`
- `performance.measureUserAgentSpecificMemory()`

```js
if (crossOriginIsolated) {
  const buf = new SharedArrayBuffer(16)
}
```

격리된 문서의 모든 하위 리소스와 iframe이 위 조건을 만족해야 하므로 기존 서비스에 도입하기 어렵습니다. `unsafe-none` 서드파티 팝업이 필요하면 COOP를 `same-origin-allow-popups`로 두지만 그러면 격리가 성립하지 않습니다. 이 세 헤더는 Spectre류 부채널 공격과 XS-Leaks를 줄이기 위한 것입니다.

## iframe sandbox

`sandbox` 속성은 iframe 안의 문서에 제한을 걸고, 토큰으로 필요한 능력만 푸는 방식입니다. Baseline 널리 지원합니다. 값을 비우면 가장 강한 제한입니다.

```html
<iframe sandbox src="https://widget.example"></iframe>
<iframe sandbox="allow-scripts allow-forms"
        src="https://widget.example"></iframe>
```

빈 `sandbox`는 스크립트 실행, 폼 제출, 팝업, 상위 이동을 막고 문서를 불투명 출처로 취급합니다(저장소·쿠키 접근 불가).

| 토큰 | 허용하는 것 |
|------|-------------|
| `allow-scripts` | 스크립트 실행 |
| `allow-same-origin` | 원래 출처를 유지(저장소·쿠키·동일 출처 fetch) |
| `allow-forms` | 폼 제출 |
| `allow-modals` | `alert`, `confirm`, `prompt`, `print` |
| `allow-popups` | `window.open`, `target="_blank"` |
| `allow-popups-to-escape-sandbox` | 열린 팝업이 sandbox를 상속하지 않음 |
| `allow-top-navigation` | 최상위 문서 이동 |
| `allow-top-navigation-by-user-activation` | 사용자 활성화가 있을 때만 최상위 이동 |
| `allow-downloads` | 다운로드 |
| `allow-pointer-lock`, `allow-orientation-lock`, `allow-presentation` | 각각 Pointer Lock, 방향 잠금, Presentation API |
| `allow-storage-access-by-user-activation` | Storage Access API 사용 |

**흔한 실수:** `allow-scripts`와 `allow-same-origin`을 함께 주는 것입니다. 같은 출처 문서가 자기 iframe의 `sandbox` 속성을 스스로 지울 수 있어서 격리가 무의미해집니다. 신뢰할 수 없는 콘텐츠는 `allow-scripts`만 주고 별도 출처에서 서빙합니다. `frame-ancestors`와 클릭재킹은 63편에서 다룹니다.

## Referrer-Policy

`Referer` 요청 헤더(철자가 틀린 채 굳은 이름)에 이전 페이지의 URL이 얼마나 담길지 정하는 정책입니다. Baseline 2021이며 브라우저 기본값은 `strict-origin-when-cross-origin`입니다.

| 정책 | 보내는 값 |
|------|-----------|
| `no-referrer` | 보내지 않음 |
| `no-referrer-when-downgrade` | HTTPS에서 HTTP로 내려갈 때만 보내지 않고 나머지는 전체 URL |
| `origin` | 항상 출처만 |
| `origin-when-cross-origin` | 같은 출처는 전체 URL, 교차 출처는 출처만 |
| `same-origin` | 같은 출처만 전체 URL, 교차 출처는 보내지 않음 |
| `strict-origin` | 출처만, 다운그레이드면 보내지 않음 |
| `strict-origin-when-cross-origin` | 같은 출처는 전체 URL, 교차 출처는 출처만, 다운그레이드면 보내지 않음 |
| `unsafe-url` | 항상 전체 URL(쿼리 노출 위험) |

지정 방법은 여러 가지이고, 더 가까운 요소 쪽 설정이 우선합니다.

```html
<meta name="referrer" content="strict-origin">
<a href="/a" referrerpolicy="no-referrer">링크</a>
<a href="/a" rel="noreferrer">링크</a>
```

- 응답 헤더 `Referrer-Policy`, `meta name="referrer"`, 요소의 `referrerpolicy` 속성, 링크의 `rel="noreferrer"`(no-referrer와 같음), `fetch`의 `referrerPolicy` 옵션.
- 요청 URL의 쿼리나 경로에 토큰·개인 정보를 두면 `Referer`로 제3자에 새어 나갑니다. 기본값을 유지하고 더 엄격히 줄이는 쪽으로 설정합니다.
- 속성의 `rel="noreferrer"`는 하이픈 없이, `meta`의 값 `no-referrer`는 하이픈과 함께 씁니다.

## 서드파티 쿠키 제한과 Storage Access API

서드파티 쿠키는 주소창의 사이트와 다른 사이트가 설정·전송하는 쿠키입니다(크로스 사이트 쿠키). 크로스 사이트 추적에 쓰여서 브라우저가 제한합니다.

| 브라우저 | 기본 동작(MDN 기준) |
|----------|---------------------|
| Firefox | 기본 차단(Total Cookie Protection) |
| Safari | 기본 차단(ITP) |
| Chrome | 기본 차단하지 않음 |

- 교차 사이트 맥락에서 쿠키를 쓰려면 `SameSite=None; Secure`가 필요합니다. `SameSite` 기본값은 Chromium에서 `Lax`입니다(자세히는 40편).
- 대안은 두 가지입니다. 파티션된 쿠키(CHIPS)는 `Partitioned` 속성을 붙여 상위 사이트별로 쿠키 저장소를 분리합니다. 위젯 상태 유지에 쓰고 사이트 간 추적에는 쓸 수 없습니다. Storage Access API는 아래와 같습니다.

```http
Set-Cookie: w=1; SameSite=None; Secure; Partitioned
```

### Storage Access API

Storage Access API(Baseline 2023)는 iframe 안의 서드파티 콘텐츠가 사용자 동의를 받아 파티션되지 않은 쿠키와 저장소에 접근하는 방법입니다.

```js
if (!(await document.hasStorageAccess())) {
  await document.requestStorageAccess() // 클릭 안에서
  location.reload() // 쿠키가 실린 상태로 다시 로드
}
```

- `hasStorageAccess()`는 현재 접근 가능 여부(불리언 프라미스), `requestStorageAccess()`는 접근 요청입니다. 거부되면 프라미스가 거부됩니다.
- 첫 요청에는 사용자 활성화(클릭 등)가 필요합니다. 이미 허가된 `상위 사이트, 임베드 사이트` 쌍이면 활성화 없이 이행합니다.
- 보안 컨텍스트여야 하고, 브라우저에 따라 그 사이트와 먼저 최상위로 상호작용한 이력이 있어야 합니다(Firefox와 Chrome은 30일 이내).
- sandbox된 iframe에는 `allow-storage-access-by-user-activation`이 필요합니다.
- 허가 범위와 만료는 브라우저마다 다르고 Safari는 같은 사이트의 모든 임베드에 적용합니다.

## Privacy Sandbox 계열 API의 현황

Privacy Sandbox는 서드파티 쿠키 없이 광고·측정·사기 방지를 하려던 Chrome 중심의 API 묶음입니다. MDN의 현재 문서는 다음과 같이 정리합니다.

| 구분 | API |
|------|-----|
| 유지 | CHIPS(파티션된 쿠키), Private State Token, 바운스 추적 완화 |
| 폐기(Chrome 152 이후 제거·차단) | Topics, Attribution Reporting, Shared Storage, Fenced Frame, Protected Audience, Private Aggregation, Related Website Sets |

- 새 조직의 Privacy Sandbox 콘솔 등록이 중단되었고, 폐기 API는 Chrome에서 오류를 던지거나 비활성입니다. 새 코드에서 의존하지 않습니다.
- web-features 데이터에서 이들은 모두 미Baseline입니다.
- 서드파티 쿠키를 대체하는 실용적 수단은 CHIPS, Storage Access API, 서버 측 처리입니다.

## Private Network Access와 Local Network Access

공개 웹사이트가 사용자의 내부망(공유기, 사설 IP, `.local`, loopback)에 요청을 보내면 내부 기기를 대상으로 한 CSRF가 가능합니다. Chromium은 이를 막는 장치를 단계적으로 바꿨습니다.

| 이름 | 방식 | 상태 |
|------|------|------|
| Private Network Access(PNA) | 내부망 서버가 프리플라이트로 직접 동의 | Local Network Access로 대체됨 |
| Local Network Access(LNA) | 사용자에게 권한 프롬프트로 확인 | Chrome 142에서 기본 적용, 미Baseline |

- LNA는 공개 사이트에서 로컬 IP, `.local`, loopback으로 가는 요청에 "로컬 네트워크의 기기를 찾아 연결" 권한을 묻습니다.
- `fetch`의 `targetAddressSpace: 'local'` 옵션으로 로컬 대상임을 표시하고, 이 경우 혼합 콘텐츠 제한이 면제됩니다.
- WebSocket·WebTransport·WebRTC는 아직 이 권한으로 막지 않고, 서비스 워커는 출처가 이미 권한을 받았어야 합니다(Chrome 문서 기준).
- 내부망 도구는 CORS 허용 헤더를 최소화하고 인증을 둡니다. 사용자는 브라우저 권한 화면에서 거부할 수 있습니다.

## Private State Token API

Private State Token은 사용자를 식별하지 않으면서 이 브라우저가 신뢰할 만하다는 사실을 사이트 사이에 전달하는 API입니다. 미Baseline이며 실험적이고 Chromium 한정입니다. 서드파티 쿠키 없이 봇 판별 결과를 넘기는 용도입니다.

| 단계 | 하는 일 |
|------|---------|
| 발급(issue) | 발급자가 사용자를 신뢰한다고 판단해 암호화된 토큰을 브라우저에 저장 |
| 상환(redeem) | 상환자가 브라우저에 발급자의 토큰이 있는지 확인해 상환 기록을 받음 |
| 전달 | 상환 기록을 다른 쪽에 넘겨 재인증 없이 신뢰를 보여 줌 |

```js
const ok = await document.hasPrivateToken({
  issuer: 'https://issuer.example',
})
await fetch(url, {
  privateToken: { operation: 'token-request' },
})
```

`operation` 값은 `token-request`, `token-redemption`, `send-redemption-record`입니다. 요청·응답에는 `Sec-Private-State-Token`과 `Sec-Redemption-Record` 헤더가 쓰이고, Permissions-Policy의 `private-state-token-issuance`와 `private-state-token-redemption`이 iframe 사용을 제어합니다.

## 핵심 정리

- 출처는 스킴·호스트·포트의 조합이고, 사이트는 등록 가능한 도메인 기준입니다. SOP는 삽입과 쓰기는 허용하고 읽기를 막습니다.
- CORS는 서버 응답 헤더로 읽기를 허용하는 프로토콜입니다. 단순 요청이 아니면 프리플라이트(`OPTIONS`, 2xx 응답)를 거치고, 자격 증명 요청에는 `*`를 쓸 수 없습니다.
- `no-cors` 응답은 읽을 수 없는 opaque 응답이며 CORS 오류의 해결책이 아닙니다.
- postMessage는 보낼 때 `targetOrigin`을 명시하고 받을 때 `event.origin`을 완전 일치로 검증합니다.
- COOP `same-origin`과 COEP `require-corp`(또는 `credentialless`)가 갖춰져야 `crossOriginIsolated`가 되고 `SharedArrayBuffer`가 켜집니다.
- sandbox에 `allow-scripts`와 `allow-same-origin`을 함께 주지 않습니다. 서드파티 쿠키는 브라우저마다 다르고 Privacy Sandbox 계열 API 대부분은 폐기되었습니다.

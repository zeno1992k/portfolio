## Web App Manifest

Web App Manifest는 사이트의 이름, 아이콘, 시작 주소, 표시 방식을 적은 JSON 파일입니다. 브라우저는 이 파일을 읽어 사이트를 독립된 앱처럼 설치하고 실행합니다. 서비스 워커(자세히는 56편)와 함께 PWA(Progressive Web App)를 이루는 두 축입니다.

```html
<link rel="manifest" href="/app.webmanifest" />
```

```json
{
  "name": "Notes",
  "short_name": "Notes",
  "start_url": "/",
  "display": "standalone",
  "icons": [
    {
      "src": "/i-192.png",
      "sizes": "192x192",
      "type": "image/png"
    }
  ]
}
```

- 권장 확장자는 `.webmanifest`이고 MIME 타입은 `application/manifest+json`입니다. `.json`과 `application/json`도 동작합니다.
- 페이지가 여럿이면 모든 페이지의 `head`에 `link` 요소가 있어야 합니다.
- manifest 요청에 쿠키 같은 자격 증명이 필요하면 `crossorigin="use-credentials"`를 붙입니다.
- 지원 상태는 미Baseline입니다. Chrome·Edge는 설치를 지원하고, Safari는 17부터 데스크톱 Dock 추가를 지원하고 iOS Safari는 15.4부터 지원 대상으로 집계됩니다. Firefox는 manifest로 설치할 수 없습니다.

## manifest 주요 멤버

| 멤버 | 역할 | 기본값과 규칙 |
|------|------|---------------|
| `id` | 앱의 고유 식별자 | 없으면 `start_url`. `start_url`의 origin 기준으로 해석되고 fragment는 무시 |
| `start_url` | 앱을 실행할 때 여는 주소 | `scope` 안에 있어야 함 |
| `scope` | 앱에 속하는 주소 범위 | 없으면 `start_url`에서 파일명·쿼리·조각을 뺀 경로 |
| `display` | 표시 방식 | 기본 `browser` |
| `icons` | 앱 아이콘 목록 | `src`, `sizes`, `type`, `purpose` |

### id

`id`가 같으면 브라우저는 새 manifest를 같은 앱의 업데이트로 봅니다. `start_url`을 바꿔도 `id`를 유지하면 새 앱으로 설치를 요구하지 않습니다. `id`가 다른 origin을 가리키면 무시하고 `start_url`로 대체합니다. `"id": "/myapp/"`처럼 슬래시로 시작하는 값이 해석이 분명합니다.

### scope

`scope`는 단순 접두사 일치입니다. `"/prefix"`는 `/prefix-of/index.html`과도 일치하므로 끝에 슬래시를 붙여 `"/prefix/"`로 씁니다. 범위 밖으로 이동하면 이동은 막히지 않고, 대신 주소 표시줄 같은 브라우저 UI가 나타납니다.

### display

| 값 | 의미 |
|----|------|
| `fullscreen` | 브라우저 UI를 모두 숨김 |
| `standalone` | 독립 창, 주소 표시줄 없음 |
| `minimal-ui` | 독립 창에 최소한의 이동 버튼 |
| `browser` | 일반 탭 (기본값) |

브라우저가 값을 지원하지 않으면 `fullscreen`, `standalone`, `minimal-ui`, `browser` 순으로 내려갑니다. `display_override` 배열을 쓰면 이 순서 앞에 시도할 값을 둘 수 있습니다. CSS에서는 `@media (display-mode: standalone)`로 표시 방식을 구분합니다. Fullscreen API와는 별개 기능입니다.

### icons

- `sizes`는 공백으로 구분한 `192x192 512x512` 형태이고, SVG는 `any`를 씁니다.
- `purpose`의 기본은 `any`입니다. `maskable`은 OS가 모양을 잘라 내는 안전 영역을 고려한 아이콘이고, `monochrome`은 알파 채널만 쓰는 단색 아이콘입니다. 둘을 `"monochrome maskable"`처럼 함께 적을 수 있습니다.
- `type`을 적어 두면 브라우저가 형식을 추측하지 않습니다.

## 설치 조건과 beforeinstallprompt

Chromium 계열(Chrome·Edge·Samsung Internet)이 설치 가능한 앱으로 판단하려면 다음이 필요합니다.

- `name` 또는 `short_name`
- 192px과 512px 아이콘
- `start_url`
- `display` 또는 `display_override`
- `prefer_related_applications`가 `false`이거나 없음
- HTTPS (`localhost`와 `127.0.0.1`은 예외)

`beforeinstallprompt` 이벤트는 Chromium 전용(미Baseline)입니다. 브라우저가 설치 가능하다고 판단하면 발생하고, 기본 설치 안내를 막은 뒤 사용자가 누르는 버튼에서 직접 띄울 수 있습니다.

```js
let installEvent = null
window.addEventListener('beforeinstallprompt', (e) => {
  e.preventDefault()   // 기본 안내를 막음
  installEvent = e     // 나중에 쓰려고 보관
  installButton.hidden = false
})
installButton.addEventListener('click', async () => {
  const { outcome } = await installEvent.prompt()
  installEvent = null  // outcome: 'accepted' 또는 'dismissed'
})
```

- 이벤트가 없는 브라우저(Safari, Firefox)가 있으므로 설치 버튼은 기본적으로 숨기고 이벤트가 왔을 때만 보여 줍니다.
- Android의 설치 안내에는 `description`과 `screenshots` 멤버가 쓰입니다.

**흔한 실수:** `beforeinstallprompt`가 모든 브라우저에서 온다고 가정하는 것입니다. iOS에서는 오지 않으며, 사용자가 공유 메뉴에서 직접 추가합니다.

## iOS 홈 화면 웹 앱과 푸시

iOS와 iPadOS 16.4부터 홈 화면에 추가한 웹 앱에서 Web Push와 알림을 쓸 수 있습니다. 조건은 다음과 같습니다.

- 홈 화면 웹 앱이어야 합니다. 일반 Safari 탭에서는 푸시를 구독할 수 없습니다.
- manifest의 `display`가 `standalone` 또는 `fullscreen`이어야 합니다. manifest가 없는 사이트는 홈 화면에 북마크로만 추가됩니다.
- 알림 권한 요청은 구독 버튼 탭 같은 직접적인 사용자 조작 안에서 해야 합니다.
- 16.4부터 Safari 외에 다른 브라우저에서도 공유 메뉴로 홈 화면에 추가할 수 있습니다(해당 브라우저가 조건을 충족할 때).
- 배지(`setAppBadge`)는 알림 권한을 받은 뒤 표시됩니다.
- `beforeinstallprompt`는 없습니다.

macOS Ventura의 Safari 16.1에서 Web Push가 먼저 도입되었고, iOS 구현은 같은 표준 기반입니다.

## Notification API

Notification API는 운영체제의 알림 시스템으로 메시지를 보여 줍니다. 보안 컨텍스트(HTTPS)에서만 동작합니다.

```js
Notification.permission // 'default' | 'granted' | 'denied'
const result = await Notification.requestPermission()
// result: 'granted' 또는 'denied' 또는 'default'
```

| `permission` 값 | 의미 |
|-----------------|------|
| `default` | 사용자가 아직 선택하지 않음. 브라우저는 거부된 것처럼 동작 |
| `granted` | 알림 허용 |
| `denied` | 알림 거부 |

- `requestPermission()`은 Promise를 반환하며, 클릭 같은 사용자 조작 안에서 호출해야 합니다(Firefox는 72부터 강제).
- 알림은 두 방법으로 만듭니다. 페이지에서 `new Notification()`을 쓰는 방법과, 서비스 워커 등록의 `showNotification()`을 쓰는 방법입니다.
- 생성자 방식은 지원이 제한적이어서 미Baseline입니다. 서비스 워커의 `showNotification()`은 Baseline 2023입니다. 푸시 알림은 서비스 워커에서 표시해야 하므로 실무에서는 `showNotification()`을 씁니다.
- 생성자 방식의 알림은 `show`, `click`, `close`, `error` 이벤트를 가집니다.

권한을 언제·어떻게 요청할지는 60편에서 다룹니다.

## showNotification()과 notificationclick

`registration.showNotification(title, options)`는 서비스 워커가 활성화 중이거나 활성화된 상태에서 호출하며, 권한이 `granted`여야 합니다. 반환값은 `undefined`로 이행되는 Promise입니다.

| 옵션 | 설명 |
|------|------|
| `body`, `icon`, `image` | 본문, 아이콘, 큰 이미지 |
| `badge` | 안드로이드 상태 표시줄용 작은 아이콘 |
| `tag` | 같은 `tag`의 알림은 새 알림이 이전 것을 대체 |
| `renotify` | 대체될 때도 다시 알림. `tag`가 필요함 |
| `requireInteraction` | 사용자가 조작할 때까지 유지 |
| `silent` | 소리·진동 없음. `vibrate`와 함께 `true`면 TypeError |
| `data` | 구조화 복제 가능한 임의 값. 클릭 때 꺼내 씀 |
| `actions` | `action`, `title`, `icon`을 가진 버튼 목록 |

`actions`는 개수가 브라우저마다 제한됩니다(`Notification.maxActions`).

```js
// sw.js
self.addEventListener('notificationclick', (event) => {
  event.notification.close()
  if (event.action === 'reply') {
    event.waitUntil(clients.openWindow('/reply'))
  } else {
    const url = event.notification.data.url
    event.waitUntil(clients.openWindow(url))
  }
})
```

- 본문을 누르면 `event.action`은 빈 문자열이고, 버튼을 누르면 그 버튼의 `action` 값입니다.
- 클릭 처리에서는 보통 `notification.close()`로 알림을 직접 닫습니다.
- 비동기 작업은 `event.waitUntil()`로 감싸야 서비스 워커가 끝나지 않습니다. 열려 있는 창을 재사용하려면 `clients.matchAll()`로 찾아 포커스합니다(자세히는 56편).

**흔한 실수:** 알림에 필요한 URL을 서비스 워커 전역 변수에 넣어 두는 것입니다. 서비스 워커는 언제든 종료되므로 `data` 옵션에 담아야 합니다.

## Push API

Push API는 서버가 보낸 메시지를 앱이 열려 있지 않아도 서비스 워커가 받게 합니다. 지원 상태는 Baseline 2023입니다. 흐름은 네 단계입니다.

1. 서비스 워커를 등록합니다.
2. 사용자에게 알림 권한을 받습니다.
3. `registration.pushManager.subscribe()`로 구독하고, 결과(`PushSubscription`)를 앱 서버에 저장합니다.
4. 서버가 푸시 서비스로 메시지를 보내면 서비스 워커에서 `push` 이벤트가 발생합니다.

```js
const sub = await registration.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: vapidPublicKey,
})
await fetch('/api/push', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(sub), // sub.toJSON()과 같음
})
```

```js
// sw.js
self.addEventListener('push', (event) => {
  const data = event.data ? event.data.json() : {}
  event.waitUntil(
    self.registration.showNotification(data.title ?? 'New'),
  )
})
```

- `userVisibleOnly: true`는 필수입니다. 푸시를 받으면 사용자에게 보이는 알림을 띄워야 한다는 약속이며, 소리 없는 몰래 푸시는 허용되지 않습니다.
- 메시지 본문은 `event.data`(`PushMessageData`)에서 `json()`, `text()`, `arrayBuffer()`, `blob()`으로 읽습니다.
- 구독이 만료되거나 무효가 되면 서비스 워커에 `pushsubscriptionchange` 이벤트가 발생하므로 다시 구독해 서버에 알립니다.
- 보안 컨텍스트와 활성 서비스 워커, 알림 권한이 모두 필요합니다.
- 구독 관리 요청에는 CSRF 방어가 필요합니다.

**흔한 실수:** `push` 이벤트에서 알림을 띄우지 않고 끝내는 것입니다. `userVisibleOnly: true`는 보이는 알림을 띄우겠다는 약속이므로 알림 없는 푸시 처리는 이 약속과 맞지 않습니다.

## PushSubscription과 VAPID

`PushSubscription`에는 푸시 서비스의 `endpoint` 주소와, 메시지 암호화에 쓰는 키 `p256dh`와 `auth`가 들어 있습니다. 서버는 이 세 값을 저장해 두었다가 메시지를 암호화해 `endpoint`로 보냅니다.

- `endpoint`는 이 주소를 아는 사람이 메시지를 보낼 수 있는 비밀 URL(capability URL)입니다. 외부에 노출하지 않습니다.

VAPID(Voluntary Application Server Identification, RFC 8292)는 앱 서버가 푸시 서비스에 자신을 증명하는 방식입니다. 키 한 쌍을 만들어 공개 키는 `applicationServerKey`로 구독에 쓰고, 개인 키는 서버에서 서명에 씁니다.

| 항목 | 내용 |
|------|------|
| 키 | ECDSA P-256 (`ES256`) |
| 전송 | 요청의 `Authorization` 헤더에 `vapid t=토큰, k=공개 키` |
| 토큰 클레임 | `aud` 푸시 서비스의 origin, `exp` 만료 시각(요청 시점부터 24시간 이내), `sub` 연락처(선택, `mailto:` 또는 `https:`) |

구독이 `applicationServerKey`로 만들어지면 그 구독으로 가는 모든 전송은 대응하는 개인 키로 서명해야 합니다. 구독 주소가 유출되어도 다른 서버가 보낼 수 없게 막는 장치입니다. 키를 바꾸면 기존 구독은 쓸 수 없으니 다시 구독해야 합니다.

## Background Sync

Background Sync는 오프라인에서 보낼 수 없던 작업을, 연결이 돌아왔을 때 서비스 워커가 대신 실행하게 합니다. Chromium 전용(미Baseline)이며 보안 컨텍스트가 필요합니다.

```js
// 페이지
const reg = await navigator.serviceWorker.ready
await reg.sync.register('send-outbox')
```

```js
// sw.js
self.addEventListener('sync', (event) => {
  if (event.tag === 'send-outbox') {
    event.waitUntil(sendOutbox())
  }
})
```

- `register(tag)`는 문자열 태그로 작업을 예약하고, 네트워크가 연결되면 `sync` 이벤트가 발생합니다.
- 전송할 데이터는 IndexedDB에 쌓아 두고(자세히는 41편) 이벤트에서 읽어 보냅니다. 서비스 워커는 페이지 변수에 접근할 수 없기 때문입니다.
- `register()`가 없는 브라우저에서는 `online` 이벤트(자세히는 60편)에서 직접 다시 보내는 방식으로 대체합니다.

## Background Fetch와 Periodic Background Sync

두 API 모두 Chromium 전용(미Baseline)입니다.

Background Fetch는 영상·음원 같은 큰 파일을 탭을 닫거나 연결이 끊겨도 이어서 내려받게 합니다. 사용자가 브라우저 UI로 진행률을 보고 취소할 수 있습니다. 짧은 작업용인 Background Sync로는 맞지 않는 긴 다운로드를 위한 API입니다.

```js
const reg = await navigator.serviceWorker.ready
const bg = await reg.backgroundFetch.fetch(
  'ep-5',
  ['/ep-5.mp3'],
  { title: 'Episode 5', downloadTotal: 60 * 1024 * 1024 },
)
```

| 서비스 워커 이벤트 | 시점 |
|--------------------|------|
| `backgroundfetchsuccess` | 모든 요청이 끝남 |
| `backgroundfetchfail` | 요청 하나 이상이 실패 |
| `backgroundfetchabort` | 사용자나 앱이 취소 |
| `backgroundfetchclick` | 사용자가 다운로드 UI를 누름 |

기능 감지는 `'BackgroundFetchManager' in self`입니다.

Periodic Background Sync는 서비스 워커가 주기적으로 깨어나 데이터를 갱신하게 합니다.

```js
await reg.periodicSync.register('news', {
  minInterval: 24 * 60 * 60 * 1000, // 최소 간격(ms)
})
// sw.js: addEventListener('periodicsync', e => ...)
```

- `minInterval`은 바라는 최소 간격일 뿐이고, 실제 간격은 브라우저가 사이트 참여도와 네트워크 상태 등으로 정합니다.
- Chrome에서는 설치된 PWA에서만 동작합니다.
- 권한은 Permissions API의 `periodic-background-sync` 이름으로 조회합니다(자세히는 60편).

## Badging API

Badging API는 설치된 웹 앱의 아이콘에 숫자나 점 형태의 배지를 표시합니다. 알림 없이 읽지 않은 항목이 있음을 알릴 때 씁니다. 미Baseline이며 Chrome·Edge 81, Safari 17(iOS 16.4)부터 지원합니다.

```js
navigator.setAppBadge(12) // 숫자 12
navigator.setAppBadge()   // 숫자 없는 점
navigator.setAppBadge(0)  // 배지 제거
navigator.clearAppBadge() // 배지 제거
```

- 창과 워커(서비스 워커 포함) 모두에서 쓸 수 있어 `push` 이벤트에서 갱신할 수 있습니다.
- 큰 숫자는 브라우저가 `99+`처럼 줄여 표시할 수 있습니다.
- 배지는 설치된 앱 아이콘에 붙고 탭에는 붙지 않습니다.
- iOS에서는 알림 권한을 받은 뒤에 표시됩니다.

## 앱 통합 기능 개요

아래 기능은 모두 설치된 PWA를 OS와 연결하는 manifest 기반 기능이며 미Baseline입니다. 사용 전에 지원 여부를 확인하고, 없을 때도 앱이 동작하게 만듭니다.

| 기능 | manifest 멤버 | 하는 일 | 지원 |
|------|---------------|---------|------|
| 파일 처리기 | `file_handlers` | 특정 파일 형식을 이 앱으로 열게 등록 | Chromium 데스크톱 |
| 공유 대상 | `share_target` | 시스템 공유 창에서 이 앱을 선택지로 표시 | Chromium |
| Launch Handler | `launch_handler` | 앱 실행 시 창을 새로 열지 재사용할지 결정 | Chromium |
| Window Controls Overlay | `display_override` | 제목 표시줄 영역까지 콘텐츠 확장 | Chromium 데스크톱 |
| Content Index | 없음(API) | 오프라인 콘텐츠를 브라우저 UI에 노출 | Android의 Chrome |

### 파일 처리기

`file_handlers`의 각 항목은 `action`(범위 안의 주소)과 `accept`(MIME 타입별 확장자 목록)를 가집니다. 파일을 열면 `action` 주소가 열리고, 페이지가 `launchQueue`로 파일을 받습니다. 서비스 워커가 아니라 메인 스레드에서 처리합니다.

```js
if ('launchQueue' in window) {
  launchQueue.setConsumer(async (params) => {
    for (const handle of params.files) {
      const file = await handle.getFile() // File 객체
    }
  })
}
```

### 공유 대상

`share_target`은 `action`, `method`(기본 `GET`), `enctype`, `params`로 구성됩니다. `params`는 공유 데이터의 `title`, `text`, `url`, `files`를 어떤 쿼리·폼 이름으로 받을지 정합니다. 파일을 받으려면 `POST`와 `multipart/form-data`를 쓰고 서비스 워커의 `fetch` 이벤트에서 `request.formData()`로 읽습니다. 앱이 공유를 시작하는 `navigator.share()`와 반대 방향 기능입니다(자세히는 61편).

### Launch Handler

`launch_handler.client_mode`는 다음 값을 가집니다. 배열로 쓰면 첫 번째 유효한 값을 씁니다.

| 값 | 동작 |
|----|------|
| `auto` | 브라우저가 결정(기본값). 보통 모바일은 기존 창을 쓰고 데스크톱은 새 창을 엶 |
| `navigate-new` | 항상 새 창에서 목표 주소를 엶 |
| `navigate-existing` | 열려 있는 앱을 포커스하고 목표 주소로 이동. 없으면 새 창 |
| `focus-existing` | 열려 있는 앱을 포커스만 하고 이동하지 않음. 없으면 새 창 |

어느 값이든 목표 주소는 `launchQueue`로 전달됩니다.

### Window Controls Overlay

`display_override`에 `window-controls-overlay`를 넣으면 데스크톱 설치 앱의 제목 표시줄이 사라지고 콘텐츠가 창 전체로 확장됩니다. 최소화·최대화·닫기 버튼은 위에 겹쳐 남습니다. `navigator.windowControlsOverlay`의 `visible`, `getTitlebarAreaRect()`, `geometrychange` 이벤트로 영역 변화를 읽고, CSS에서는 `env(titlebar-area-x)`, `env(titlebar-area-y)`, `env(titlebar-area-width)`, `env(titlebar-area-height)`로 위치를 잡습니다.

### Content Index

서비스 워커 등록의 `index.add()`로 오프라인에서 열 수 있는 콘텐츠(`id`, `title`, `description`, `category`, `icons`, `url`)를 브라우저 UI에 등록합니다. `getAll()`, `delete(id)`로 관리하고, 사용자가 브라우저 UI에서 지우면 `contentdelete` 이벤트가 발생합니다. 색인할 수 있는 URL은 HTML 문서뿐이고, 항목은 저절로 만료되지 않습니다. 현재 Android의 Chrome에서만 동작합니다.

## 프로토콜 핸들러

프로토콜 핸들러는 `mailto:` 같은 주소 스킴을 열 때 이 사이트가 처리하도록 등록하는 기능입니다. 미Baseline이며 Firefox와 Chromium 계열이 지원하고 Safari는 지원하지 않습니다.

```js
navigator.registerProtocolHandler(
  'web+burger',
  'https://burgers.example.org/?burger=%s',
)
```

- 스킴은 허용 목록(`mailto`, `tel`, `sms`, `magnet`, `xmpp` 등)이거나 `web+` 뒤에 소문자 ASCII 알파벳이 오는 사용자 정의 스킴이어야 합니다.
- 핸들러 주소는 등록하는 페이지와 같은 origin의 HTTPS이고, 호출된 전체 URL로 바뀌는 `%s` 자리를 가져야 합니다.
- 어긴 경우 origin·스킴·HTTPS 위반은 `SecurityError`, `%s` 누락은 `SyntaxError`입니다.
- 브라우저가 사용자에게 확인을 요청할 수 있습니다.

설치된 PWA는 manifest의 `protocol_handlers`로 선언할 수도 있습니다. 이 방식은 설치된 앱에만 적용됩니다.

```json
{
  "protocol_handlers": [
    {
      "protocol": "web+burger",
      "url": "/handle?protocol=%s"
    }
  ]
}
```

## PWA와 컴포넌트 앱 구조

PWA 기능은 대부분 페이지 밖, 서비스 워커나 manifest에서 동작합니다. 이를 컴포넌트 앱에 넣을 때는 책임을 층으로 나눕니다.

| 층 | 담당 | 예 |
|----|------|----|
| manifest | 앱 정체성과 OS 통합 | `id`, `scope`, `icons`, `share_target` |
| 서비스 워커 | 오프라인, 푸시, 백그라운드 작업 | 캐시, `push`, `sync` |
| 앱 셸 | 항상 필요한 뼈대 컴포넌트(자세히는 33편) | 헤더, 라우터 |
| 기능 서비스 | 브라우저 API를 감싼 모듈 | 알림·설치·배지 서비스 |
| UI 컴포넌트 | 서비스를 호출하고 상태만 표시 | 설치 버튼, 알림 설정 스위치 |

- UI 컴포넌트가 `Notification`이나 `beforeinstallprompt`를 직접 다루지 않고 서비스를 거치게 하면, 지원 여부 확인과 폴백이 한곳에 모입니다.
- `beforeinstallprompt`처럼 앱 시작 직후 한 번 발생하는 이벤트는 컴포넌트가 생기기 전에 올 수 있으므로 서비스가 일찍 받아 보관하고 컴포넌트는 나중에 구독합니다.
- 서비스 워커와 페이지는 메모리를 공유하지 않으므로 둘 사이의 데이터는 IndexedDB, 캐시, `postMessage`로 주고받습니다.
- 푸시와 배지, 알림 클릭 이동 주소는 manifest의 `scope` 안에 있어야 사용자가 앱 안에서 열립니다.
- 오프라인 앱의 전체 구조는 85편에서 사례로 다룹니다.

## 핵심 정리

- manifest는 `id`로 앱을 식별하고, `start_url`은 `scope` 안에 있어야 하며, `scope`는 접두사 일치라서 끝에 슬래시를 붙입니다.
- 설치 가능 조건과 `beforeinstallprompt`는 Chromium 중심이고 iOS에서는 공유 메뉴로만 설치합니다. iOS 푸시는 홈 화면에 추가한 앱에서만 됩니다.
- 알림은 사용자 조작 안에서 권한을 받고, 푸시 알림은 서비스 워커의 `showNotification()`으로 표시하며 `notificationclick`에서 `data`로 이동 주소를 꺼냅니다.
- 푸시는 구독(`endpoint`, `p256dh`, `auth`)을 서버에 저장하고, VAPID 서명으로 전송하며, `userVisibleOnly: true`로 보이는 알림을 약속합니다.
- Background Sync, Background Fetch, Periodic Background Sync, 파일 처리기, 공유 대상, Content Index는 Chromium 중심의 미Baseline 기능이라 점진적 향상으로 씁니다.
- 컴포넌트 앱에서는 브라우저 API를 서비스로 감싸고 UI 컴포넌트는 그 서비스만 호출합니다.

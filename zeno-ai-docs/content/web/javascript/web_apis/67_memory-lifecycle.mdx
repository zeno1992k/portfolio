## Garbage Collection 기본

JavaScript는 값을 만들 때 메모리를 자동으로 할당하고, 더 쓸 수 없게 되면 가비지 컬렉터가 회수합니다. 개발자가 직접 해제하지 않습니다(언어 측면은 ECMAScript 과목).

- 현대 엔진은 mark-and-sweep 방식입니다. 루트(전역 객체 등)에서 출발해 참조를 따라 닿는 객체에 표시하고, 닿지 못한 객체를 회수합니다.
- 기준은 도달 가능성(reachability)입니다. 서로 참조하는 순환 참조도 루트에서 닿지 않으면 회수됩니다.
- 회수 시점은 엔진이 정합니다. 코드에서 GC를 호출하거나 시점을 알 수 없습니다.
- 메모리 누수는 더 쓰지 않는 객체가 루트에서 여전히 닿는 상태입니다. 쓰지 않는데 참조가 남아 있는 것이 원인이고, 시간이 지날수록 메모리가 계속 늘어납니다.

```js
let big = { data: new Array(1e6).fill(0) }
big = null  // 다른 참조가 없으면 회수 대상
```

브라우저에서 누수를 일으키는 단골 원인은 다음 여섯 가지입니다. 전역 변수를 제외한 다섯 가지는 아래 절에서 하나씩 다룹니다. 전역 변수는 `let`·`const`로 선언하고 모듈 안에서 쓰면 피할 수 있습니다.

| 원인 | 루트까지 이어지는 길 |
|------|----------------------|
| 분리된 DOM | JS 변수·컬렉션이 제거된 노드를 가리킴 |
| 이벤트 리스너 | 오래 사는 대상(`window`, `document`)이 컴포넌트를 캡처한 핸들러를 가짐 |
| 옵저버 | 전역·오래 사는 옵저버의 콜백이 컴포넌트를 캡처 |
| 타이머 | 해제되지 않은 타이머가 콜백을 붙들고 있음 |
| 클로저 | 살아 있는 함수가 큰 스코프 값을 붙들고 있음 |
| 전역 변수 | 의도치 않게 만든 전역이 객체를 붙들고 있음 |

## Detached DOM

Detached DOM은 문서 트리에서 제거됐지만 JavaScript 참조가 남아 있어서 회수되지 않는 노드입니다. 노드 하나가 자기 하위 트리 전체와 거기 붙은 데이터를 붙들기 때문에 크기가 큽니다.

```js
const cache = []
function show() {
  const el = document.createElement('ul')
  document.body.append(el)
  cache.push(el)       // 참조를 남김
}
function hide() {
  document.body.lastChild.remove() // DOM에서는 제거
  // cache는 여전히 노드를 가리킴 ❌ 회수되지 않음
}
```

- DOM에서 지우는 것(`remove()`)과 메모리에서 해제하는 것은 다릅니다. 참조까지 끊어야 합니다(`cache.length = 0`, 변수에 `null` 대입).
- 자주 생기는 곳: 모듈 수준 배열·Map에 노드를 저장, 컴포넌트가 자식 노드를 인스턴스 필드로 보관, 지워진 노드를 가리키는 리스너 콜백의 클로저.
- 하위 노드 하나만 참조해도 그 노드의 조상 쪽 트리까지 연결되어 큰 덩어리가 남습니다.
- 진단은 힙 스냅샷에서 Detached 노드를 찾는 것입니다(아래 "힙 스냅샷 비교법").
- 참조를 오래 두어야 하는 메타데이터는 `WeakMap`의 키로 노드를 씁니다(아래 "WeakMap과 WeakSet").

## 이벤트 리스너 누수

리스너는 대상이 가진 참조입니다. 대상이 죽으면 리스너도 함께 사라지므로 문제가 되는 경우는 대상이 컴포넌트보다 오래 사는 때입니다.

```js
class UiPanel extends HTMLElement {
  connectedCallback() {
    window.addEventListener('resize', () => this.layout())
    // ❌ 컴포넌트가 제거돼도 window가 핸들러를 쥐고 있고,
    //    핸들러가 this를 캡처하므로 컴포넌트가 회수되지 않음
  }
}
```

- `window`, `document`, `document.body`, 전역 이벤트 버스, 오래 사는 상위 요소에 단 리스너가 전형적인 원인입니다.
- 컴포넌트 자신이나 그 자식 요소에 단 리스너는, 서로 참조해도 루트에서 닿지 않으면 같이 회수됩니다. 이 경우는 정리하지 않아도 새지 않습니다.
- 연결·해제가 반복되면 `connectedCallback`이 돌 때마다 리스너가 하나씩 더 쌓여 누수와 중복 실행이 함께 생깁니다(생명주기는 18편).
- `removeEventListener`는 등록할 때와 같은 함수 참조와 같은 `capture` 값이 있어야 제거됩니다. 화살표 함수를 그 자리에서 만들어 등록했다면 제거할 수 없습니다.

```js
el.addEventListener('click', () => go())
el.removeEventListener('click', () => go()) // ❌ 다른 함수
```

- 해결은 함수 참조를 필드에 두거나, 아래 `AbortController`로 한꺼번에 제거하는 것입니다.

## Observer 누수

옵저버는 `IntersectionObserver`, `ResizeObserver`, `MutationObserver`, `PerformanceObserver`처럼 콜백을 등록해 두는 객체입니다(자세히는 43편). 옵저버는 관찰 대상 요소를 살려 두지 않지만, 옵저버가 오래 살고 콜백이 컴포넌트를 캡처하면 컴포넌트가 붙들립니다.

```js
const ro = new ResizeObserver(() => this.layout())
ro.observe(this)
// 해제: ro.disconnect() 또는 ro.unobserve(this)
```

- `disconnect()`는 모든 관찰을 멈추고, `unobserve(target)`은 하나만 멈춥니다. 옵저버 객체는 다시 `observe()`로 재사용할 수 있습니다.
- `MutationObserver.disconnect()`는 아직 전달되지 않은 기록을 버립니다. 필요하면 먼저 `takeRecords()`로 꺼냅니다.
- 관찰 대상이 `document`·`window`처럼 오래 사는 것이면 컴포넌트가 사라져도 관찰이 이어지므로 `disconnectedCallback`에서 반드시 해제합니다.
- 전역 하나를 여러 컴포넌트가 공유하는 옵저버(싱글턴)는 `observe`한 요소를 `unobserve`하지 않으면 요소 목록이 계속 커집니다.
- `PerformanceObserver`는 버퍼가 쌓이는 만큼 메모리를 쓰므로 쓰지 않을 때 `disconnect()`합니다.

## Timer 누수

`setInterval`·`setTimeout`은 콜백이 실행되거나 해제될 때까지 브라우저가 콜백을 붙들고 있습니다. 콜백이 컴포넌트를 캡처하면 컴포넌트가 제거돼도 회수되지 않고 계속 실행됩니다.

```js
connectedCallback() {
  this.timer = setInterval(() => this.poll(), 1000)
}
disconnectedCallback() {
  clearInterval(this.timer)  // ✅ 해제
}
```

- 한 번만 실행되는 `setTimeout`은 실행이 끝나면 풀리지만, 아직 실행되기 전에 컴포넌트가 사라지면 그때까지 붙들립니다. 보통은 짧아서 무시하지만 지연이 긴 경우에는 해제합니다.
- `requestAnimationFrame`을 재귀적으로 반복하는 애니메이션 루프도 멈추는 조건이 없으면 같은 문제입니다. `cancelAnimationFrame(id)`로 끊습니다.
- 타이머 외에 `fetch` 완료 후 콜백이 사라진 컴포넌트를 갱신하려는 경우도 같은 구조입니다. 취소는 `AbortController`로 합니다(자세히는 37편).

## Closure와 참조 유지

클로저는 만들어진 스코프의 변수를 참조로 유지하는 함수입니다. 살아 있는 클로저가 있으면 그 스코프에서 쓰는 변수가 회수되지 않습니다(언어 측면은 ECMAScript 과목).

```js
function make() {
  const huge = new Array(1e6).fill(0)
  const el = document.querySelector('#a')
  el.onclick = () => console.log(huge.length)
  // huge는 el.onclick이 살아 있는 동안 유지됨
}
```

- 큰 값은 다 쓴 뒤 `null`을 대입해 참조를 끊어 두면 클로저가 오래 살아도 그 값은 회수됩니다.
- 핸들러가 캡처한 `this`, 큰 배열, DOM 노드가 누수의 연결 고리가 되는 경우가 많습니다. 어떤 변수를 캡처하는지 의식합니다.
- 오래 사는 콜백(전역 리스너, 타이머, 옵저버 콜백)에서는 컴포넌트 전체 대신 필요한 값만 캡처하거나, 약한 참조(`WeakRef`)를 쓸 수 있습니다.

```js
const ref = new WeakRef(this)
const id = setInterval(() => {
  const self = ref.deref()
  if (!self) return clearInterval(id)
  self.poll()
}, 1000)
```

`WeakRef.deref()`는 대상이 회수됐으면 `undefined`를 돌려줍니다. 회수 시점은 보장되지 않고 명세도 가능하면 피하라고 권하므로, 정상 경로는 명시적 정리이고 이것은 보조 수단입니다.

## AbortController를 Cleanup 도구로 사용

`addEventListener`의 `signal` 옵션에 `AbortSignal`을 넘기면, `abort()` 한 번으로 그 신호를 쓴 모든 리스너가 제거됩니다. 정리할 것이 많은 컴포넌트에서 가장 간결한 방법입니다.

```js
class UiPanel extends HTMLElement {
  #ac = null
  connectedCallback() {
    this.#ac = new AbortController()
    const { signal } = this.#ac
    window.addEventListener('resize', this.#onResize, { signal })
    document.addEventListener('keydown', this.#onKey, { signal })
    fetch('/api', { signal }).then(this.#render)
  }
  disconnectedCallback() {
    this.#ac.abort() // 리스너 둘과 fetch를 한꺼번에 취소
  }
  #onResize = () => {}
  #onKey = () => {}
  #render = () => {}
}
```

- 같은 신호를 `fetch`에도 넘기면 진행 중인 요청도 취소됩니다. 취소된 `fetch`는 `AbortError`로 거부되므로 처리합니다.
- 한 번 `abort()`한 컨트롤러는 다시 쓸 수 없습니다. `connectedCallback`마다 새로 만듭니다. 위 코드가 그렇게 합니다.
- 여러 조건을 합치려면 `AbortSignal.any([a, b])`로 둘 중 하나가 중단될 때 중단되는 신호를 만듭니다(Baseline 2024). `AbortSignal.timeout(ms)`는 시간이 지나면 중단되는 신호입니다.
- `AbortSignal.any()`로 만든 신호에 단 `abort` 리스너도 작업이 끝나면 제거해야 합니다.
- 타이머는 `signal`을 받지 않으므로 `signal.addEventListener('abort', () => clearInterval(id))`로 연결합니다.

## disconnectedCallback Cleanup

`disconnectedCallback`은 커스텀 요소가 문서에서 제거될 때마다 호출되는 정리 지점입니다. `connectedCallback`에서 만든 것은 여기서 모두 해제합니다.

| `connectedCallback`에서 만든 것 | `disconnectedCallback`에서 할 일 |
|---------------------------------|----------------------------------|
| 전역·상위 대상의 리스너 | `abort()` 또는 `removeEventListener` |
| 옵저버 | `disconnect()` |
| 타이머·애니메이션 루프 | `clearInterval`, `cancelAnimationFrame` |
| 진행 중인 요청 | `abort()` |
| 구독(스토어, 이벤트 버스) | 구독 해제 함수 호출 |
| 외부 라이브러리 인스턴스 | 해당 라이브러리의 `destroy()` |

- 요소를 이동(`insertBefore` 등)하면 `disconnectedCallback`과 `connectedCallback`이 연달아 호출됩니다. 그래서 `connectedCallback`은 반복 호출되어도 중복되지 않게 만들고, `disconnectedCallback`은 반드시 짝이 맞게 정리해야 합니다.
- `Element.moveBefore()`로 이동하면 `connectedMoveCallback`이 정의된 요소는 그 콜백만 호출되고 두 콜백은 호출되지 않아 상태를 유지한 채 이동합니다.
- 페이지가 닫힐 때는 `disconnectedCallback`이 호출되지 않습니다. 닫을 때의 정리는 `pagehide` 같은 이벤트를 씁니다(자세히는 66편의 bfcache).
- 생성자에서는 전역 리스너나 타이머를 만들지 않습니다. 문서에 붙은 적이 없는데 정리 호출이 오지 않기 때문입니다.
- 만드는 코드와 해제하는 코드를 같은 순서로 나란히 두면 해제를 빠뜨리는 일이 줄어듭니다.

## WeakMap과 WeakSet

`WeakMap`과 `WeakSet`은 키(또는 원소)를 약한 참조로 가지는 컬렉션입니다. 키 객체를 다른 곳에서 더 이상 참조하지 않으면 항목이 자동으로 회수됩니다. Baseline 널리 지원(2015년 7월부터)입니다.

```js
const meta = new WeakMap()
function track(el) {
  meta.set(el, { clicks: 0 })
}
track(button)
// button이 DOM에서 제거되고 다른 참조가 없으면
// meta의 항목도 함께 회수됨
```

- 키는 객체나 등록되지 않은 심벌이어야 합니다. 원시 값은 키가 될 수 없습니다.
- 반복할 수 없고 `size`가 없습니다. 반복 가능하면 객체의 생사를 관찰하게 되기 때문입니다. 메서드는 `set`, `get`, `has`, `delete`입니다.
- `WeakSet`은 `add`, `has`, `delete`만 있는 집합으로, 처리한 노드 표시("이미 초기화한 요소") 같은 용도에 씁니다.
- 용도: DOM 요소에 붙이는 외부 메타데이터, 객체별 캐시(메모이제이션), 비공개 데이터.
- 값이 키를 다시 참조해도(`meta.set(el, { el })`) 키가 다른 곳에서 닿지 않으면 항목은 회수됩니다. 값은 키가 살아 있을 때만 유지됩니다.
- 항목의 목록이 필요하거나 문자열·숫자 키이면 `Map`을 쓰고 직접 정리해야 합니다.

**흔한 실수:** 캐시를 `Map`으로 만들고 키로 DOM 요소를 쓰는 것입니다. `Map`은 키를 강하게 붙들어서 요소가 제거돼도 영원히 남습니다.

## FinalizationRegistry 활용과 한계

`FinalizationRegistry`는 등록한 객체가 가비지 컬렉션된 뒤에 콜백을 요청하는 API입니다. Baseline 널리 지원(2021년 4월부터)입니다.

```js
const reg = new FinalizationRegistry((id) => {
  releaseNativeResource(id)  // 보조 정리
})
reg.register(obj, 'res-1')     // 대상, 전달할 값
reg.register(obj, 'res-1', obj) // 세 번째 인수는 해제 토큰
reg.unregister(obj)             // 토큰으로 등록 취소
```

한계가 크므로 필수 로직에 쓰면 안 됩니다.

- 콜백은 동기적으로 호출되지 않고, 한참 뒤에 호출되거나 아예 호출되지 않을 수 있습니다. 엔진마다 다릅니다.
- 탭을 닫을 때, 레지스트리 자신이 회수된 때는 호출되지 않습니다.
- 현재 작업(JavaScript job)이 끝나기 전에는 대상이 회수되지 않습니다.
- 명세도 가능하면 쓰지 말라고 권합니다. 쓰더라도 메모리 사용을 줄이는 선택적 정리에만 씁니다. 예를 들어 `WeakRef`로 캐시한 값이 회수되면 `Map`에 남은 빈 항목을 지우는 용도입니다.

```js
const cache = new Map()
const reg = new FinalizationRegistry((k) => cache.delete(k))
function put(k, v) {
  cache.set(k, new WeakRef(v))
  reg.register(v, k)
}
```

정리의 정석은 `disconnectedCallback`과 `AbortController`이고, 이 API는 그것을 대체하지 못합니다.

## 오래 사는 캐시의 크기 제한

앱이 사는 동안 쌓이는 캐시(응답, 계산 결과, 이미지 디코드 결과)는 상한이 없으면 사실상 누수입니다. 항목 수나 바이트 수에 상한을 두고 넘으면 오래 안 쓴 항목부터 버립니다. 이것이 LRU(least recently used)입니다.

`Map`은 삽입 순서를 유지하는 점을 이용해 간단히 구현합니다.

```js
class Lru {
  #max; #map = new Map()
  constructor(max) { this.#max = max }
  get(k) {
    if (!this.#map.has(k)) return undefined
    const v = this.#map.get(k)
    this.#map.delete(k); this.#map.set(k, v) // 최신으로
    return v
  }
  set(k, v) {
    this.#map.delete(k); this.#map.set(k, v)
    if (this.#map.size > this.#max) {
      this.#map.delete(this.#map.keys().next().value) // 가장 오래된
    }
  }
}
```

- 키가 객체이고 그 객체가 사라질 때 같이 지워지길 원하면 `WeakMap`으로 충분하지만, 상한을 지키는 것은 아닙니다. 문자열 키 캐시는 LRU 같은 직접 제한이 필요합니다.
- 상한은 항목 수보다 바이트 크기로 두는 편이 정확한 경우가 많습니다. 큰 `Blob`이나 비트맵을 담는다면 크기를 합산합니다.
- 브라우저 저장소(Cache API, IndexedDB)는 별도의 할당량이 있습니다(자세히는 42편).

## 컴포넌트 생성과 제거 반복 테스트

누수는 한 번 만들고 지우는 것으로는 안 보입니다. 같은 동작을 여러 번 반복해도 메모리가 늘지 않는지 확인합니다.

```js
for (let i = 0; i < 200; i++) {
  const el = document.createElement('ui-panel')
  document.body.append(el)
  await nextFrame()
  el.remove()
}
// 반복 후 힙에 UiPanel 인스턴스가 쌓여 있지 않아야 한다
```

- 기대 결과는 반복 횟수와 무관하게 인스턴스 수가 일정(0에 가까움)한 것입니다. 횟수에 비례해 늘면 누수입니다.
- 매번 `connectedCallback`과 `disconnectedCallback` 호출 횟수를 세어 짝이 맞는지도 검사합니다.
- 자동 테스트에서는 리스너 등록·해제 횟수, 타이머 남은 수, 옵저버 `disconnect` 호출을 스파이로 검증합니다(자세히는 68편).
- 메모리 수치 자체는 엔진 GC 시점에 좌우되어 불안정하므로, 단위 테스트에서는 호출 짝을 검증하고 메모리 비교는 DevTools로 합니다.

### 힙 스냅샷 비교법

Chrome DevTools의 Memory 패널 힙 스냅샷은 그 시점에 도달 가능한 객체를 모두 기록합니다. 두 시점을 비교해 늘어난 객체를 찾습니다.

1. 앱을 로드하고 의심 동작을 한 번 수행해 초기화 비용을 먼저 소화합니다.
2. Memory 패널에서 Heap snapshot을 찍습니다(스냅샷 1).
3. 컴포넌트 생성과 제거를 여러 번 반복합니다.
4. 스냅샷 2를 찍고 Comparison 보기에서 스냅샷 1과 비교합니다.
5. 늘어난 항목에서 해당 컴포넌트 클래스, `Detached` 노드, 클로저를 찾고, 하나를 선택해 Retainers에서 어디서 붙들고 있는지 따라갑니다.

- 보기: Summary(생성자별 묶음), Comparison(두 스냅샷 차이), Containment(객체 계층), Statistics(분류별 비중).
- Retainers는 선택한 객체를 참조하는 경로를 보여 줍니다. 그 경로의 끝이 `window`나 모듈 변수이면 거기가 정리 누락 지점입니다.
- 생성자 필터로 분리된 노드가 붙들고 있는 객체나 중복 문자열도 걸러 볼 수 있습니다.
- 실시간 증가 추세는 성능 패널의 HEAP 그래프와 Chrome 작업 관리자의 JavaScript 메모리 열로 봅니다. 자세한 도구 사용은 70편에서 다룹니다.

## performance.measureUserAgentSpecificMemory

`performance.measureUserAgentSpecificMemory()`는 페이지(iframe과 워커 포함)의 메모리 사용량을 추정하는 API입니다. Baseline이 아니며 Chromium 계열 중심의 실험 기능입니다.

```js
if (crossOriginIsolated) {
  const m = await performance.measureUserAgentSpecificMemory()
  m.bytes      // 전체 바이트
  m.breakdown  // [{ bytes, attribution, types }]
}
```

- 보안 컨텍스트이면서 교차 출처 격리된 문서여야 합니다(COOP·COEP 헤더, 62편). `crossOriginIsolated`로 확인합니다.
- 결과는 Promise이며 `bytes`와 `breakdown`을 가집니다. `breakdown`의 `attribution`은 메모리를 쓰는 영역(URL, 컨테이너, `scope`), `types`는 `DOM`, `JS` 같은 종류입니다.
- 값은 구현에 따라 달라서 브라우저와 버전을 가로질러 비교할 수 없습니다. 같은 환경의 추세 비교(누수 탐지, 회귀 감지)에 씁니다.
- 현장 모니터링에서는 측정 시점을 무작위로 흩뿌려 호출하는 것이 MDN의 예시입니다.
- 지원되지 않는 환경이 많으므로 기능 탐지 후에만 호출하고, 없으면 지표를 수집하지 않습니다.

## 핵심 정리

- 가비지 컬렉터는 루트에서 닿지 않는 객체만 회수하므로, 쓰지 않는 객체가 참조로 이어져 있으면 누수입니다. 시점은 제어할 수 없습니다.
- 누수의 주원인은 분리된 DOM, 오래 사는 대상에 단 리스너, 옵저버, 타이머, 큰 스코프를 잡은 클로저입니다.
- 정리는 `connectedCallback`에서 만든 것을 `disconnectedCallback`에서 짝으로 해제하는 것이며, `AbortController`의 `signal`로 리스너와 요청을 한꺼번에 끊을 수 있습니다.
- 객체에 붙이는 메타데이터는 `WeakMap`·`WeakSet`을 쓰고, `WeakRef`와 `FinalizationRegistry`는 회수 시점을 보장하지 않으므로 보조 수단으로만 씁니다.
- 오래 사는 캐시는 LRU 같은 크기 제한이 필요하고, 누수는 생성·제거를 반복해 힙 스냅샷 두 장을 비교해 찾습니다.
- `measureUserAgentSpecificMemory()`는 교차 출처 격리와 Chromium이 필요한 미Baseline API입니다.

## KeyboardEvent key와 code의 차이

`KeyboardEvent`는 키를 누르고 뗄 때 발생하는 이벤트 객체입니다. 어떤 키인지는 두 속성으로 알려 줍니다.

| 속성 | 뜻 | 자판 배열에 따라 | 예 |
|------|----|-------------------|----|
| `key` | 입력된 값(문자나 기능 이름) | 달라짐 | `'a'`, `'A'`, `'Enter'`, `'ArrowUp'`, `'Escape'` |
| `code` | 눌린 물리적 키 위치 | 같음 | `'KeyA'`, `'Digit1'`, `'NumpadEnter'` |

```js
addEventListener('keydown', (e) => {
  console.log(e.key, e.code)
})
// QWERTY에서 Q 위치 키: 'q' 'KeyQ'
// AZERTY에서 같은 위치 키: 'a' 'KeyQ'
```

- `key`는 Shift나 CapsLock에 따라 `'a'`와 `'A'`로 달라집니다. 대소문자를 구분하지 않으려면 `e.key.toLowerCase()`로 비교합니다.
- 글자를 입력받거나 단축키 문자를 확인할 때는 `key`, 게임의 WASD 이동처럼 키 위치가 중요할 때는 `code`를 씁니다.
- `code`만으로는 어떤 문자가 입력되는지 알 수 없습니다. 같은 `'KeyQ'`가 배열에 따라 다른 문자가 됩니다.
- 스페이스 키의 `key`는 `' '`(공백 문자)이고 `code`는 `'Space'`입니다.
- `keyCode`, `charCode`, `which`는 지원 중단된 레거시 속성입니다. 새 코드에서는 쓰지 않습니다.

**흔한 실수:** 한글 자판 상태에서 `key`로 영문 단축키를 비교하는 것입니다. 한글이 입력되는 배열에서는 `key`가 영문이 아니라서 어긋날 수 있습니다. 위치로 판단하려면 `code`를 쓰고, 글자로 판단하려면 `key`를 씁니다.

## repeat·location·getModifierState

키를 계속 누르고 있으면 `keydown`이 반복해서 발생합니다. 첫 번째 이후의 이벤트는 `repeat`이 `true`입니다.

```js
addEventListener('keydown', (e) => {
  if (e.repeat) return  // 길게 눌러서 생긴 반복은 무시
  fire()
})
```

`location`은 같은 `key` 값을 가진 키 중 어느 쪽인지 알려 줍니다.

| 상수 | 값 | 뜻 |
|------|----|----|
| `DOM_KEY_LOCATION_STANDARD` | 0 | 일반 키 |
| `DOM_KEY_LOCATION_LEFT` | 1 | 왼쪽 수정 키 |
| `DOM_KEY_LOCATION_RIGHT` | 2 | 오른쪽 수정 키 |
| `DOM_KEY_LOCATION_NUMPAD` | 3 | 숫자 키패드 |

- 왼쪽 Shift와 오른쪽 Shift는 `key`가 둘 다 `'Shift'`이고 `location`이 1과 2로 다릅니다. 숫자 키패드의 `'1'`은 `location`이 3입니다.
- 수정 키 상태는 `shiftKey`, `ctrlKey`, `altKey`, `metaKey` 불리언으로 읽습니다.

`getModifierState(name)`은 이 네 가지 외의 상태까지 읽습니다. 대소문자를 구분하는 이름을 받습니다.

```js
addEventListener('keydown', (e) => {
  if (e.getModifierState('CapsLock')) {
    showCapsWarning()
  }
})
```

- 지원 이름에는 `'Alt'`, `'AltGraph'`, `'CapsLock'`, `'Control'`, `'Meta'`, `'NumLock'`, `'ScrollLock'`, `'Shift'`가 있습니다.
- `'CapsLock'`처럼 눌린 순간이 아니라 켜져 있는 상태(락 키)를 읽는 데 주로 씁니다. 비밀번호 입력창의 Caps Lock 경고가 대표적입니다.
- `'Meta'`는 Mac에서 Command(⌘), Windows와 Linux에서 Windows 로고 키입니다.
- `'Alt'`는 Alt 또는 AltGr를, `'Control'`은 Ctrl 또는 AltGr를 가리킵니다. AltGr를 쓰는 배열에서는 Ctrl이 눌린 것처럼 보일 수 있습니다.
- 가상의 `'Accel'`(Ctrl 또는 Command)은 지원 중단 상태입니다.

## keydown·keyup과 keypress 폐기

UI Events 표준이 정한 한 키의 이벤트 순서는 다음과 같습니다.

| 순서 | 이벤트 | 비고 |
|------|--------|------|
| 1 | `keydown` | 키를 누름. 누르고 있으면 반복됨 |
| 2 | `beforeinput` | 문자를 만드는 키에서만 |
| 3 | `input` | DOM이 실제로 바뀐 경우에만 |
| 4 | `keyup` | 키를 뗌 |

- `keydown`에서 `preventDefault()`를 호출하면 해당 키의 `beforeinput`과 `input`이 발생하지 않습니다. `keyup`은 막히지 않습니다.
- 수정 키(Shift, Ctrl)나 방향키처럼 문자를 만들지 않는 키는 `beforeinput`과 `input` 없이 `keydown`과 `keyup`만 발생합니다.
- `keydown`과 `keyup`은 Baseline 널리 지원(2015년부터)입니다.

```js
input.addEventListener('keydown', (e) => {
  if (e.key === 'Enter') submit()     // 키 동작
})
input.addEventListener('input', () => {
  validate(input.value)               // 값 변화
})
```

`keypress`는 폐기되었습니다. 문자를 만드는 키와 Enter에서만 발생했고 수정 키나 방향키에서는 발생하지 않아 일관성이 없었습니다. 대체 수단은 키 동작에는 `keydown`, 입력될 텍스트에는 `beforeinput` 또는 `input`입니다.

**흔한 실수:** `keydown` 핸들러에서 입력창의 `value`를 읽는 것입니다. `keydown` 시점에는 아직 문자가 반영되지 않아서 직전 값이 읽힙니다. 입력 후의 값은 `input`에서 읽습니다.

## 단축키 처리와 플랫폼별 수정 키

단축키는 수정 키 상태와 `key`를 함께 검사해서 구현합니다. 저장 단축키는 Windows·Linux에서 Ctrl+S, Mac에서 Command+S입니다. 표준 속성만으로 이 차이를 처리하려면 두 키 중 하나를 허용합니다.

```js
addEventListener('keydown', (e) => {
  const mod = e.ctrlKey || e.metaKey
  if (mod && e.key.toLowerCase() === 's') {
    e.preventDefault() // 브라우저 저장 대화상자 막기
    save()
  }
})
```

- `e.key.toLowerCase()`를 쓰는 이유는 Shift나 CapsLock이 켜지면 `'S'`가 되기 때문입니다.
- 정확한 조합을 원하면 다른 수정 키가 눌리지 않았는지도 확인합니다(`!e.altKey` 등). Ctrl+Shift+S와 Ctrl+S를 구분해야 하는 경우입니다.
- `e.repeat`이 `true`면 길게 누른 반복입니다. 한 번만 실행해야 하는 동작이면 걸러 냅니다.
- 입력창에서 글자를 칠 때 단축키가 가로채지 않도록 `e.target`이 입력 요소나 편집 가능 요소인지 확인합니다.
- 한글 조합 중(`e.isComposing`)에는 단축키를 처리하지 않습니다(다음 절).
- 브라우저와 운영체제가 예약한 단축키(탭 닫기, 창 전환 등)는 페이지가 가로채지 못할 수 있고, 가로채는 것은 사용자 경험상 권장하지 않습니다.
- 화면에 단축키를 표시할 때 `code`는 배열마다 글자가 다릅니다. 배열에 맞는 글자는 Keyboard Map으로 구합니다(아래 "Keyboard Map").

## 조합 이벤트와 한글 IME 입력 함정

한글, 일본어, 중국어는 여러 키를 눌러 글자 하나를 완성하는 입력기(IME)를 거칩니다. 완성되기 전의 임시 글자를 조합 중(composition)이라 부르고, 이 구간을 알리는 이벤트가 조합 이벤트입니다.

| 이벤트 | 시점 |
|--------|------|
| `compositionstart` | 조합 세션 시작 |
| `compositionupdate` | 조합 중인 글자가 바뀔 때마다 |
| `compositionend` | 조합 확정 또는 취소 |

`CompositionEvent.data`는 현재 조합 중인(`compositionend`에서는 확정된) 문자열입니다. 조합 이벤트는 Baseline 널리 지원입니다.

표준이 정한 순서에서 중요한 점은 다음과 같습니다.

1. 조합을 시작시키는 `keydown`은 `isComposing`이 `false`입니다.
2. 조합 세션 중의 `keydown`과 `keyup`은 `isComposing`이 `true`입니다.
3. 조합 중 글자가 바뀔 때는 `beforeinput`, `compositionupdate`, `input` 순서로 발생합니다.
4. `compositionend`에는 DOM 변경이 없어서 `beforeinput`과 `input`이 따로 발생하지 않습니다.

`KeyboardEvent.isComposing`은 조합 세션 안에서 발생한 이벤트인지 알려 줍니다. `InputEvent.isComposing`도 같습니다.

**한글 IME의 대표 함정은 Enter 처리입니다.** 채팅 입력창에서 한글을 입력하다 Enter를 누르면, 마지막 글자가 조합 중인 상태에서 `keydown`이 발생합니다. 이를 그대로 전송으로 처리하면 조합이 확정되기 전에 전송이 처리되어 마지막 글자가 어긋나거나 한 번 더 전송될 수 있습니다.

```js
input.addEventListener('keydown', (e) => {
  if (e.isComposing || e.keyCode === 229) return // 조합 중
  if (e.key === 'Enter') send(input.value)
})
```

- 조합 중에는 Enter, 방향키, 단축키 등 `keydown` 기반 동작을 건너뜁니다.
- `keyCode === 229`는 IME가 처리 중이라는 레거시 신호입니다. MDN은 Safari에서 `compositionend`와 `keydown`의 순서가 다르다고 안내하므로 `isComposing`만으로 부족한 경우를 위한 보조 검사로 씁니다. `keyCode`는 지원 중단된 속성입니다.
- 조합 중 `input` 이벤트에서 값을 검증하거나 글자 수를 제한하면 아직 확정되지 않은 글자까지 검사합니다. 검증을 조합 확정 뒤로 미루려면 `input`의 `isComposing`을 확인하고 `compositionend`에서 처리합니다.

```js
let composing = false
el.addEventListener('compositionstart', () => {
  composing = true
})
el.addEventListener('compositionend', () => {
  composing = false
  validate(el.value)   // 확정된 뒤에 검증
})
el.addEventListener('input', () => {
  if (!composing) validate(el.value)
})
```

- `keydown`에서 `preventDefault()`로 취소하면 그 키에서 시작될 조합 이벤트도 발생하지 않습니다.
- 대부분의 IME는 조합 세션 중의 갱신을 취소하는 것을 지원하지 않습니다.
- `compositionstart` 이후 상황은 입력기와 운영체제에 따라 다르므로 실제 입력기로 확인해야 합니다.

## beforeinput과 InputEvent.inputType

`beforeinput`은 `<input>`, `<textarea>`, `contenteditable` 요소의 내용이 바뀌기 직전에 발생하는 `InputEvent`입니다. Baseline 널리 지원(2021년 3월부터)입니다. 취소하면 입력이 일어나지 않습니다.

```js
input.addEventListener('beforeinput', (e) => {
  if (e.inputType === 'insertText' && /\D/.test(e.data)) {
    e.preventDefault() // 숫자가 아닌 문자 입력 차단
  }
})
```

| 속성 | 뜻 |
|------|----|
| `data` | 삽입될 문자열(없으면 `null`) |
| `inputType` | 변경의 종류 |
| `isComposing` | 조합 세션 중 여부 |
| `dataTransfer` | 붙여넣기·드롭으로 들어오는 데이터 |
| `getTargetRanges()` | 변경이 적용될 범위의 배열 |

- `inputType` 값의 예: `insertText`, `insertCompositionText`, `insertFromPaste`, `deleteContentBackward`, `deleteContentForward`, `historyUndo`, `historyRedo`, `formatBold`.
- 모든 사용자 변경에서 `beforeinput`이 발생하는 것은 아닙니다. 발생해도 취소할 수 없는 경우가 있습니다(자동 완성, 맞춤법 교정, 비밀번호 관리자 채우기, IME 입력 등).
- 따라서 입력 제한을 `beforeinput` 취소에만 맡기지 말고, `input`에서 값을 검사해 되돌리는 방어 코드를 함께 둡니다.
- 텍스트 편집기는 `beforeinput`에서 `inputType`별로 동작을 정하는 방식으로 만들 수 있습니다(자세히는 13편).

`beforeinput`의 시점이 `keydown`보다 나은 점은 키 종류가 아니라 입력 결과를 기준으로 하기 때문입니다. 붙여넣기, 드롭, 음성 입력, 가상 키보드의 입력도 같은 경로로 잡힙니다.

## input과 change의 차이

두 이벤트 모두 값의 변경을 알리지만 시점이 다릅니다.

| 구분 | `input` | `change` |
|------|---------|----------|
| 텍스트 입력 | 편집할 때마다 | 값이 확정될 때(포커스를 잃을 때 등) |
| 체크박스·라디오 | 토글될 때(과거에는 일관되지 않음) | 토글될 때 |
| `select` | 선택이 바뀔 때 | 선택이 확정될 때 |
| 버블링 | 함 | 함 |
| 취소 | 가능 | 불가 |

- 실시간 반응(검색어 자동 완성, 글자 수 표시)은 `input`, 입력이 끝난 값 처리(저장)는 `change`를 씁니다.
- 체크박스와 라디오는 `change`를 쓰면 안전합니다. MDN은 `input`이 과거에 일관되지 않았다고 설명합니다.
- 스크립트로 `value`를 바꾸거나 `selectedIndex`를 바꾸면 두 이벤트 모두 발생하지 않습니다. 직접 `dispatchEvent`로 보내야 합니다.
- 폼 리셋은 `reset` 이벤트를 발생시키고 `input`은 발생시키지 않습니다.
- `input`은 Baseline 널리 지원(2020년부터)입니다.

**흔한 실수:** 값 변화 감지를 `keyup`으로 구현하는 것입니다. 마우스 붙여넣기, 음성 입력, 자동 완성은 `keyup`이 발생하지 않거나 값과 맞지 않습니다. 값의 변화는 `input`으로 받습니다.

## 포커스 이벤트 순서와 focusin·focusout·relatedTarget

포커스 이벤트는 요소가 키보드 입력을 받는 상태가 되거나 잃을 때 발생하는 `FocusEvent`입니다. 이벤트가 네 가지입니다.

| 이벤트 | 시점 | 버블링 |
|--------|------|--------|
| `focus` | 요소가 포커스를 받음 | 안 함 |
| `blur` | 요소가 포커스를 잃음 | 안 함 |
| `focusin` | 요소가 포커스를 받음(`focus` 뒤) | 함 |
| `focusout` | 요소가 포커스를 잃음(`blur` 뒤) | 함 |

- UI Events 표준이 정한 순서는 한 요소에서 다른 요소로 포커스가 옮겨갈 때 `blur`, `focusout`(이전 요소), `focus`, `focusin`(새 요소)입니다.
- MDN은 표준이 정한 순서와 실제 브라우저가 구현한 순서가 다르다고 안내합니다. `focusin`·`focusout`과 `focus`·`blur`의 상대 순서에 의존하지 않는 것이 안전합니다. 이전 요소의 이벤트가 새 요소의 이벤트보다 먼저라는 점이 기준입니다.
- `focus`와 `blur`는 버블링하지 않아서 부모에서 자식 입력창의 포커스를 감지할 수 없습니다. 부모에 리스너를 하나만 두려면 `focusin`과 `focusout`을 씁니다(이벤트 위임은 07편). `focus`와 `blur`도 캡처 단계에서는 부모가 받을 수 있습니다.
- `focusin`은 Baseline 널리 지원(2017년부터)입니다.

`FocusEvent.relatedTarget`은 포커스 이동의 반대편 요소입니다.

| 이벤트 | `target` | `relatedTarget` |
|--------|----------|-----------------|
| `focus`, `focusin` | 포커스를 받는 요소 | 포커스를 잃는 요소 |
| `blur`, `focusout` | 포커스를 잃는 요소 | 포커스를 받는 요소 |

```js
form.addEventListener('focusout', (e) => {
  if (!form.contains(e.relatedTarget)) {
    console.log('폼 바깥으로 포커스가 나감')
  }
})
```

- 포커스를 받는 쪽이 포커스를 받을 수 없는 요소이거나, 페이지 바깥으로 나가는 경우에는 `relatedTarget`이 `null`입니다. 보안상 중첩된 문서(iframe)로 드나들 때도 `null`입니다.
- 위 코드처럼 컴포넌트 안에서 바깥으로 포커스가 나갔는지(드롭다운 닫기, 폼 검증)를 `focusout`과 `relatedTarget`으로 판단합니다. `null`일 수 있어서 `contains(null)`이 `false`가 되는 점을 감안합니다.
- 포커스를 가진 요소가 `hidden`이 되거나 문서에서 제거되면 포커스가 `body`로 옮겨집니다. 이때 Chromium 계열은 `blur`를 발생시키고 Firefox는 발생시키지 않습니다.
- 포커스 관리와 Shadow DOM에서의 포커스는 28편에서 다룹니다.

## 사용자 활성화(일시적·지속적)와 navigator.userActivation

사용자 활성화(user activation)는 사용자가 페이지와 실제로 상호작용했다는 창(window)의 상태입니다. 팝업 열기, 전체 화면, 클립보드 접근처럼 남용되기 쉬운 API는 이 상태를 요구합니다. 두 종류가 있습니다.

| 종류 | 뜻 | 속성 |
|------|----|------|
| 일시적 활성화(transient) | 상호작용 직후 짧은 시간 동안만 참 | `navigator.userActivation.isActive` |
| 지속적 활성화(sticky) | 한 번이라도 상호작용하면 이후 계속 참 | `navigator.userActivation.hasBeenActive` |

- 활성화로 인정되는 입력은 신뢰된(`isTrusted`) `keydown`(Esc와 브라우저 예약 단축키, Caps Lock 등 제외), `mousedown`, 마우스가 아닌 `pointerup`, 마우스의 `pointerdown`, `touchend`입니다.
- 일시적 활성화의 지속 시간은 HTML 표준이 브라우저에 맡기며, 최대 몇 초 정도를 기대한다고 적습니다. 일부 API는 사용하면 일시적 활성화를 소모(consume)합니다.
- 일시적 활성화를 요구하는 API 예: `window.open()`, `requestFullscreen()`, 클립보드 읽기·쓰기, `navigator.share()`. 지속적 활성화를 요구하는 예: `navigator.vibrate()`, 미디어 자동 재생, `beforeunload` 이벤트.
- `navigator.userActivation`은 Baseline 2023(Chrome 72, Firefox 120, Safari 16.4부터)입니다.

```js
button.addEventListener('click', () => {
  if (navigator.userActivation.isActive) {
    video.play()  // 활성화 직후이므로 재생 허용
  }
})
```

**흔한 실수:** 사용자 입력 직후가 아닌 곳(`setTimeout` 긴 지연 뒤, 네트워크 응답 후)에서 활성화 필요 API를 부르는 것입니다. 일시적 활성화가 만료되어 거부됩니다. 입력 이벤트 핸들러 안에서 부릅니다.

## 모바일 가상 키보드와 inputmode·enterkeyhint

가상 키보드(소프트 키보드)의 종류와 Enter 키 모양은 HTML 속성으로 힌트를 줄 수 있습니다. 둘 다 힌트일 뿐이라 값 검증이나 입력 제한을 하지 않습니다.

`inputmode`는 어떤 가상 키보드를 띄울지 알려 줍니다. Baseline 널리 지원(2021년 12월부터)입니다.

| 값 | 키보드 |
|----|--------|
| `none` | 가상 키보드를 띄우지 않음(페이지가 자체 키보드를 구현할 때) |
| `text` | 사용자 로케일의 기본 키보드(기본값) |
| `decimal` | 숫자와 소수점 구분 기호 |
| `numeric` | 숫자 0–9 |
| `tel` | 전화 키패드 |
| `search` | 검색에 맞춘 키보드 |
| `email` | `@` 등이 있는 이메일용 키보드 |
| `url` | `/`가 눈에 띄는 URL용 키보드 |

`enterkeyhint`는 Enter 키에 표시할 동작을 정합니다. Baseline 널리 지원(2021년 11월부터)입니다. `<input>`, `<textarea>`, 편집 가능 요소에 쓸 수 있습니다.

| 값 | 의미 |
|----|------|
| `enter` | 줄바꿈 |
| `done` | 입력 끝, 입력기를 닫음 |
| `go` | 입력한 대상으로 이동 |
| `next` | 다음 입력 칸으로 |
| `previous` | 이전 입력 칸으로 |
| `search` | 검색 결과 표시 |
| `send` | 전송 |

```html
<input inputmode="numeric" enterkeyhint="next" />
<input type="search" enterkeyhint="search" />
```

- 전화번호, 이메일, URL처럼 맞는 `type`이 있으면 `type`을 쓰고 검증과 키보드를 함께 얻습니다. 숫자만 입력하는 인증 번호, 금액처럼 `type="number"`의 스피너나 숫자 서식이 맞지 않는 곳에 `type="text"`와 `inputmode`를 조합합니다.
- 입력 칸이 여럿인 폼은 마지막 칸에 `enterkeyhint="done"` 또는 `send`, 나머지는 `next`로 지정하면 키 라벨이 흐름에 맞아집니다.

## VirtualKeyboard API

VirtualKeyboard API는 가상 키보드가 나타날 때 레이아웃을 페이지가 직접 조정하게 해 주는 API입니다. Baseline이 아니며, web-features 데이터 기준으로 Chrome·Edge 94부터 지원하는 Chromium 전용이고 보안 컨텍스트(HTTPS)가 필요합니다. MDN은 실험적 기능으로 표시합니다. Firefox와 Safari에서는 `navigator.virtualKeyboard`가 없으므로 기능 검사 후 쓰고 점진적 향상으로 다룹니다.

```js
if ('virtualKeyboard' in navigator) {
  navigator.virtualKeyboard.overlaysContent = true
}
```

- `overlaysContent`를 `true`로 하면 키보드가 나타날 때 브라우저가 뷰포트를 자동으로 줄이지 않고, 키보드가 콘텐츠 위에 겹칩니다. 레이아웃은 직접 조정합니다.
- `boundingRect`는 키보드의 위치와 크기(`DOMRect`)이고, 크기가 바뀌면 `navigator.virtualKeyboard`에서 `geometrychange` 이벤트가 발생합니다.
- CSS 환경 변수 `keyboard-inset-height`, `keyboard-inset-top` 등으로 키보드 영역을 레이아웃에 반영합니다.

```css
.composer {
  padding-bottom: env(keyboard-inset-height, 0px);
}
```

- `contenteditable` 요소에 `virtualkeyboardpolicy="manual"`을 주면 키보드 표시를 자동에 맡기지 않고 `navigator.virtualKeyboard.show()`와 `hide()`로 직접 제어합니다. `auto`가 기본값입니다.
- 가상 키보드 때문에 보이는 영역이 줄어드는 문제는 `visualViewport`로도 대응합니다(자세히는 06편).

## Keyboard Map

Keyboard Map은 물리적 키(`code`)가 현재 자판 배열에서 어떤 문자인지 알려 주는 API입니다. `navigator.keyboard.getLayoutMap()`이 `KeyboardLayoutMap`으로 이행되는 Promise를 돌려줍니다. Baseline이 아니며, web-features 데이터 기준으로 Chrome 69, Edge 79부터 지원하는 Chromium 전용입니다. 보안 컨텍스트가 필요하고 MDN은 실험적 기능으로 표시합니다.

```js
const map = await navigator.keyboard.getLayoutMap()
map.get('KeyW')  // QWERTY: 'w', AZERTY: 'z'
```

- `KeyboardLayoutMap`은 `Map`과 비슷한 읽기 전용 객체이고 키는 `code` 값입니다.
- WASD 이동 같은 위치 기반 조작을 `code`로 구현한 게임이 안내 문구에 실제 글자를 보여 줄 때 씁니다.
- `keyboard-map` 권한 정책이 막으면 `SecurityError`로 거부됩니다.
- 미지원 브라우저에서는 `navigator.keyboard`가 없으므로 기능 검사 후 `code` 이름이나 기본 QWERTY 글자를 대신 보여 줍니다.

## 핵심 정리

- `key`는 입력된 값(배열에 따라 변함), `code`는 물리적 키 위치(배열과 무관)이고, 글자 입력은 `key`, 위치 기반 조작은 `code`를 씁니다.
- 한 키의 순서는 `keydown`, `beforeinput`, `input`, `keyup`이고 `keydown`을 취소하면 `beforeinput`과 `input`이 막힙니다. `keypress`는 폐기되었습니다.
- 한글 IME 조합 중의 `keydown`은 `isComposing`이 `true`이므로 Enter 전송과 단축키 처리에서 걸러야 합니다.
- 값 변화는 `input`, 확정된 값은 `change`이며, `beforeinput`은 취소할 수 없는 경우가 있어서 `input`에서 다시 검사합니다.
- `focus`와 `blur`는 버블링하지 않고 `focusin`과 `focusout`은 버블링하며, `relatedTarget`은 포커스 이동의 반대편 요소(없으면 `null`)입니다.
- 사용자 활성화는 일시적(`isActive`)과 지속적(`hasBeenActive`)이 있고, `inputmode`와 `enterkeyhint`는 모바일 키보드 힌트이며, VirtualKeyboard API와 Keyboard Map은 Chromium 전용입니다.

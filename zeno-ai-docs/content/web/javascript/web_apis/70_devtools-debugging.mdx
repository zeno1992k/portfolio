이 문서의 패널 이름과 조작은 Chrome DevTools 기준이고, 다른 브라우저는 마지막 절에서 비교합니다. 개발자 도구의 UI는 자주 바뀌므로 이름이 다르면 명령 메뉴(Ctrl+Shift+P, macOS는 Cmd+Shift+P)에서 패널 이름으로 검색합니다.

## Elements 패널

Elements 패널은 파싱된 DOM과 적용된 CSS를 보고 고치는 도구입니다. 소스 HTML이 아니라 스크립트가 바꾼 뒤의 현재 DOM을 보여 줍니다.

- 요소를 우클릭해 Inspect로 이동하고, Ctrl+F 검색은 텍스트·CSS 선택자·XPath를 받습니다.
- 텍스트와 속성은 더블클릭으로, 구조는 Edit as HTML이나 드래그로 고칩니다. 고친 내용은 새로고침하면 사라집니다.
- Styles 탭은 규칙과 선택자의 명시도를, Computed 탭은 실제로 적용된 값만 보여 줍니다.
- `:hover`·`:focus` 같은 의사 상태를 강제로 켜 두고 스타일을 확인할 수 있습니다.
- 선택한 노드는 Console에서 `$0`으로 참조합니다. Copy JS path는 `querySelector` 식을 만들어 줍니다.
- H 키로 요소를 숨기고, Capture node screenshot으로 요소 단위 이미지를 저장합니다.

**흔한 실수:** Elements 패널에서 고친 값을 소스에 반영하는 것을 잊는 것입니다. 개발자 도구의 편집은 현재 페이지 메모리에만 적용됩니다.

## Shadow DOM 검사

Elements 패널은 Shadow DOM 호스트 아래에 `#shadow-root` 노드를 보여 주고, 그 안의 트리를 일반 DOM처럼 펼쳐 검사·편집하게 합니다. `closed` 모드 루트도 개발자 도구에서는 볼 수 있습니다.

```js
$0.shadowRoot               // open이면 ShadowRoot
$0.shadowRoot.querySelector('button')
$0.shadowRoot.activeElement // 안쪽에서 포커스를 가진 요소
```

- `closed` 루트는 스크립트에서 `el.shadowRoot`가 `null`이므로 Console로는 접근하지 못합니다. 트리 검사와 Styles 탭은 그대로 쓸 수 있습니다.
- Styles 탭에서 Shadow 안쪽 요소를 고르면 그 루트의 스타일시트와 상속된 외부 값(CSS 변수 등)이 함께 보입니다(자세히는 23편).
- 슬롯된 자식은 라이트 DOM에 있으면서 슬롯 위치에 렌더링됩니다. 그 요소에 걸리는 규칙은 호스트 문서의 스타일과 `::slotted()` 규칙입니다(자세히는 22편).
- `input` 같은 내장 요소의 사용자 에이전트 Shadow DOM은 기본으로 감춰져 있습니다. 개발자 도구 설정에서 보이게 할 수 있습니다.

## Event Listener 검사

요소에 어떤 리스너가 붙어 있는지는 세 곳에서 확인합니다.

| 방법 | 용도 |
|------|------|
| Elements 패널의 Event Listeners 탭 | 선택한 요소(조상 포함)의 리스너와 정의 위치로 이동 |
| Console의 `getEventListeners(el)` | 리스너 정보를 객체로 받아 코드로 가공 |
| Console의 `monitorEvents(el, 'click')` | 이후 발생하는 해당 이벤트를 로깅 |

```js
getEventListeners($0)
// { click: [{ listener: ƒ, useCapture: false, ... }] }
monitorEvents($0, 'click')   // 클릭할 때마다 이벤트 출력
unmonitorEvents($0, 'click') // 로깅 중지
```

- 이벤트 위임을 쓰면 리스너는 대상이 아니라 조상에 있습니다(7편). 대상 요소에 리스너가 없어 보이면 조상의 Event Listeners 탭이나 조상 포함 옵션을 확인합니다.
- `getEventListeners`와 `monitorEvents`는 개발자 도구 Console에서만 동작하는 유틸리티입니다. 페이지 스크립트에서는 쓸 수 없습니다.
- Shadow DOM에서는 이벤트가 호스트로 리타깃팅되어 보입니다. 실제 발생 지점은 이벤트 객체의 `composedPath()`로 확인합니다.
- 이벤트가 발생한 순간에 멈추려면 이벤트 리스너 중단점(다음 절)을 씁니다.

## Breakpoints

중단점은 실행을 특정 조건에서 멈추고 호출 스택·스코프 변수를 보게 하는 기능입니다. Chrome DevTools는 8가지 유형을 제공합니다.

| 유형 | 멈추는 시점 |
|------|-------------|
| 코드 줄 | 지정한 줄에 도달 |
| 조건부 코드 줄 | 지정한 줄에서 조건식이 참일 때 |
| Logpoint | 멈추지 않고 Console에 메시지만 기록 |
| DOM 변경 | 노드의 하위 트리 수정, 속성 수정, 노드 제거 |
| XHR/fetch | 요청 URL에 지정 문자열이 포함 |
| 이벤트 리스너 | 지정한 이벤트나 이벤트 범주 발생 |
| 예외 | 잡힌 예외·잡히지 않은 예외 |
| 함수 | `debug(fn)`으로 지정한 함수가 호출됨 |

- 반복문 안의 특정 반복에서만 멈추려면 조건부 중단점을, 코드를 고치지 않고 값을 찍으려면 Logpoint를 씁니다. `console.log`를 추가해 배포하는 실수를 막습니다.
- 소스에 `debugger;` 문을 쓰면 개발자 도구가 열려 있을 때 그 자리에서 멈춥니다. 커밋하기 전에 제거합니다.
- 비동기 코드를 따라가려면 호출 스택에서 비동기 스택 정보를 확인합니다.
- Trusted Types 위반 지점에서 멈추는 중단점도 있습니다(자세히는 63편).

## Network 패널

Network 패널은 개발자 도구가 열려 있는 동안의 모든 요청을 기록합니다.

- Waterfall은 요청 간 시간 관계를, 상세의 Timing은 DNS 조회·연결·대기(TTFB)·다운로드 단계를 보여 줍니다.
- 필터는 도메인, MIME 타입, 상태 코드, 리소스 종류(JS·CSS·이미지)로 거릅니다. 검색은 헤더·페이로드·응답 본문을 찾습니다.
- Preserve log를 켜면 페이지 이동 후에도 기록이 남습니다. Disable cache는 개발자 도구가 열려 있는 동안 캐시를 쓰지 않아 첫 방문 상태를 재현합니다.
- 요청 하나를 cURL, PowerShell, fetch 코드로 복사해 재현할 수 있고, 전체를 HAR 파일로 저장할 수 있습니다.
- Initiator는 그 요청을 일으킨 코드·리소스를 가리키고, WebSocket 메시지와 이벤트 스트림도 볼 수 있습니다.
- CORS 실패(62편)는 Console 오류와 함께 요청·응답 헤더를 대조해 원인을 찾습니다. 프리플라이트 `OPTIONS` 요청이 따로 기록됩니다.
- 캐시 응답(36편, 42편)은 Size 열에 디스크·메모리 캐시로 표시됩니다.

## Performance 패널

Performance 패널은 기록 구간 동안 메인 스레드 활동, 프레임, 네트워크를 시간 축으로 보여 줍니다.

- Main 트랙의 플레임 차트는 호출 스택을 시간 순으로 그리고, 막대가 넓을수록 오래 걸린 작업입니다.
- 긴 작업과 강제 동기 레이아웃은 빨간 삼각형으로 표시됩니다. 위치를 눌러 원인 코드로 이동합니다(자세히는 2편, 8편).
- CPU 스로틀링(4배 느리게 등)과 네트워크 스로틀링으로 저사양 기기를 흉내 냅니다. 개발 PC 기준의 수치는 실제 사용자보다 낙관적입니다.
- Rendering 탭의 Core Web Vitals 오버레이로 LCP·INP·CLS를 화면에서 바로 확인합니다(자세히는 65편).
- 읽는 순서: 긴 막대를 찾고, 그 안에서 스크립트·스타일 재계산·레이아웃·페인트 중 무엇이 큰지 구분합니다.

**흔한 실수:** 개발자 도구를 연 채로 한 번 측정한 값을 기준으로 삼는 것입니다. 확장 프로그램과 캐시 상태에 따라 결과가 달라지므로 같은 조건에서 반복 측정하고, 실제 사용자 데이터(필드 데이터)와 구분합니다.

## Memory 패널

Memory 패널은 JavaScript 힙을 분석해 메모리 누수와 낭비를 찾습니다(원리는 67편).

| 도구 | 보여 주는 것 |
|------|--------------|
| Heap snapshot | 특정 시점의 힙 전체. 생성자별 객체 수, 얕은 크기, 보유 크기 |
| Allocation timeline | 기록 동안의 새 할당. 파란 막대가 아직 해제되지 않은 새 할당 |
| Allocation sampling | 함수별 메모리 할당량 |

- 얕은 크기(shallow size)는 객체 자체가 차지하는 메모리이고, 보유 크기(retained size)는 그 객체를 지웠을 때 함께 해제될 수 있는 메모리입니다.
- 누수 찾는 순서: 스냅샷 1을 찍고, 의심 동작(컴포넌트 열기)을 한 뒤 되돌리고(닫기), 스냅샷 2를 찍어 Comparison 보기로 차이를 봅니다.
- Class filter에 `Detached`를 입력하면 DOM에서 제거됐지만 JS 참조 때문에 남은 분리된 노드를 찾습니다. 컴포넌트가 `disconnectedCallback`에서 리스너·타이머를 정리하지 않을 때 흔합니다(18편).
- 객체를 고르면 Retainers 영역에서 그 객체를 붙잡고 있는 참조 경로를 확인합니다.
- Console의 `queryObjects(Constructor)`는 해당 생성자로 만든 객체를 모아 줍니다. 컴포넌트 인스턴스가 닫은 뒤에도 남았는지 빠르게 확인합니다.
- Performance 패널의 Memory 체크박스는 힙과 DOM 노드 수의 추이를 그려 줍니다. 계속 우상향하면 누수를 의심합니다.

## Coverage

Coverage 패널은 페이지가 실제로 실행·적용한 JavaScript와 CSS의 비율을 보여 줍니다. 명령 메뉴에서 coverage를 검색해 열고, 계측 단위(함수 단위 또는 블록 단위)를 정한 뒤 새로고침하거나 상호작용합니다.

- 리소스별 전체 크기, 미사용 크기, 사용 비율이 표시됩니다. 행을 누르면 Sources에서 미사용 줄이 표시됩니다.
- URL과 리소스 종류(CSS·JavaScript)로 거를 수 있습니다.
- 기록 구간에 실행되지 않은 코드를 모두 불필요한 코드로 보면 안 됩니다. 아직 하지 않은 상호작용이나 다른 경로의 코드일 수 있습니다. 여러 시나리오를 실행한 뒤 판단합니다.
- 결과는 코드 분할·지연 로딩 대상을 고르는 근거입니다(자세히는 15편, 66편, 72편). 패널은 제거 방법까지 알려 주지 않습니다.

## Accessibility Tree

Elements 패널의 Accessibility 탭은 선택한 요소의 접근성 정보를 보여 줍니다. 계산된 이름과 역할, ARIA 속성, 그리고 Show accessibility tree로 전환하는 접근성 트리 보기가 있습니다.

- 브라우저가 DOM에서 계산한 트리이므로 `role`, `aria-label`, `ElementInternals`로 만든 의미가 의도대로 반영됐는지 확인합니다(자세히는 27편).
- Shadow DOM 안쪽 요소도 같은 트리에 들어갑니다. 이름이 비어 있거나 역할이 `generic`이면 의미가 전달되지 않는 것입니다.
- 색 대비가 낮은 텍스트는 자동으로 식별되고 개선 색 조합을 제안합니다.
- 키보드 이동과 스크린 리더 사용성은 개발자 도구가 대신 확인해 주지 못합니다. 실제 보조 기술로 확인합니다(자동 검사의 한계는 69편).

## Custom Element 디버깅

커스텀 요소 문제는 대부분 정의가 안 됐거나, 업그레이드 시점이 어긋났거나, 생명주기 콜백이 의도와 다르게 불린 경우입니다.

```js
customElements.get('x-card')           // 클래스 또는 undefined
await customElements.whenDefined('x-card')
$0.matches(':defined')                 // 업그레이드 완료 여부
$0 instanceof customElements.get('x-card')
```

| 증상 | 확인할 것 |
|------|-----------|
| 요소가 일반 `HTMLElement`처럼 동작 | `customElements.get`이 `undefined`인지, 정의 스크립트가 로드됐는지 |
| 속성이 바뀌어도 반응이 없음 | `observedAttributes`에 이름이 있는지(18편) |
| 콜백이 두 번 불림 | 이동·재삽입으로 `connectedCallback`이 반복 호출되는지 |
| 스타일이 안 먹음 | 요소가 `:defined` 상태인지, Shadow 안팎 중 어디의 규칙인지 |

- 콜백에 중단점을 걸려면 `debug(customElements.get('x-card').prototype.render)`처럼 함수 중단점을 씁니다. 소스 파일을 찾기 어려울 때 편합니다.
- Firefox Inspector는 커스텀 요소에 `custom` 배지를 표시하고 누르면 클래스 정의로 이동합니다.
- `connectedCallback`에서 `console.trace()`를 호출하면 누가 요소를 DOM에 넣었는지 스택으로 확인됩니다.

## 컴포넌트 업데이트 추적

컴포넌트가 언제, 얼마나 자주, 왜 갱신되는지 추적하는 방법은 다음과 같습니다.

| 목적 | 방법 |
|------|------|
| 렌더링 횟수 | 렌더 함수에서 `console.count('render')` |
| 갱신 호출 경로 | 렌더 함수에서 `console.trace()` |
| 누가 DOM을 바꿨나 | 호스트·Shadow 루트의 DOM 변경 중단점(하위 트리·속성·제거) |
| 어느 영역이 다시 그려지나 | Rendering 탭의 Paint flashing |
| 어떤 갱신이 비싼가 | Performance 패널의 스타일 재계산·레이아웃·페인트 구간 |
| 속성 변경 흐름 | `attributeChangedCallback`에 Logpoint |

```js
render() {
  console.count('x-list render') // x-list render: 1
  console.trace('render caused by')
  this.shadowRoot.replaceChildren(buildList(this.items))
}
```

한 번의 상태 변경에 렌더가 여러 번 불리면 갱신 일괄 처리(31편, 30편)가 빠졌다는 신호입니다. 변경한 부분만 다시 그려졌는지는 Paint flashing으로 확인합니다.

## Console 유틸리티

Console 유틸리티는 개발자 도구 Console에서만 쓸 수 있는 편의 함수입니다. 페이지 스크립트에서는 정의돼 있지 않습니다.

| 이름 | 하는 일 |
|------|---------|
| `$0`–`$4` | 최근 선택한 요소·힙 객체(`$0`이 가장 최근) |
| `$_` | 직전에 평가한 식의 값 |
| `$(sel)`, `$$(sel)` | `querySelector`, `querySelectorAll`(배열 반환) |
| `$x(path)` | XPath로 요소 찾기 |
| `getEventListeners(obj)` | 등록된 이벤트 리스너 |
| `monitorEvents(obj, type)` | 이벤트 발생을 로깅. `unmonitorEvents`로 중지 |
| `debug(fn)`, `undebug(fn)` | 함수 호출 시 중단 |
| `monitor(fn)`, `unmonitor(fn)` | 함수 호출과 인수를 로깅 |
| `inspect(obj)` | 해당 요소·객체를 패널에서 열기 |
| `copy(obj)` | 문자열 표현을 클립보드로 복사 |
| `keys(obj)`, `values(obj)` | 프로퍼티 이름·값 배열 |
| `queryObjects(Ctor)` | 해당 생성자로 만든 객체 모음 |

페이지에 같은 이름의 전역(예: jQuery의 `$`)이 있으면 페이지의 것이 우선할 수 있습니다. 이 유틸리티들은 코드에 쓰지 않고 조사할 때만 씁니다.

## Application 패널

Application 패널은 웹 앱이 브라우저에 남기는 상태를 검사하고 고칩니다.

| 영역 | 내용 |
|------|------|
| Manifest | 웹 앱 매니페스트의 파싱 결과와 설치 가능 여부(57편) |
| Service Workers | 등록·활성 상태, 업데이트, 해제(56편) |
| Storage | Local storage, Session storage, IndexedDB, Cookies, Cache storage의 조회·편집·삭제(40–42편) |
| Background Services | bfcache, 백그라운드 동기화, 푸시, 추측 로딩 |
| Frames | 프레임별 리소스, 보안·CSP, API 사용 가능 여부 |

bfcache(뒤로 가기 캐시) 검사는 Back/forward cache 항목에서 Run Test를 누릅니다. 개발자 도구가 페이지에서 나갔다 돌아오는 이동을 시도하고, 복원되면 복원됐다는 결과를, 안 되면 이유를 보여 줍니다. 개발자가 고칠 수 있는 이유는 Actionable로 표시됩니다. 예를 들어 `unload` 리스너를 쓰면 복원되지 않으므로 `pagehide`로 바꿉니다(60편).

**흔한 실수:** Service Worker가 옛 버전을 계속 서빙하는 것을 모르고 코드를 고치는 것입니다. 이 패널에서 업데이트·해제와 저장소 비우기로 상태를 초기화한 뒤 확인합니다.

## Rendering 탭

Rendering 탭은 렌더링을 시각화하거나 사용자 설정을 에뮬레이션합니다. 명령 메뉴에서 Show Rendering으로 엽니다.

| 항목 | 효과 |
|------|------|
| Paint flashing | 다시 페인트되는 영역을 녹색으로 깜박임 |
| Layout Shift Regions | 레이아웃 이동이 일어난 영역을 보라색으로 강조(CLS 원인 찾기) |
| Layer borders | 레이어와 타일 경계를 오버레이 |
| Frame Rendering Stats | FPS, 프레임 타임라인, GPU 래스터 상태, 메모리 |
| Scrolling performance issues | 스크롤 성능에 해로울 수 있는 리스너가 달린 요소 |
| Core Web Vitals | LCP·INP·CLS 실시간 표시 |

에뮬레이션 항목: 색각 이상, `prefers-color-scheme`(다크·라이트), 강제 색상(forced-colors), 대비 선호, `prefers-reduced-motion`, 투명도 감소. 미디어 쿼리와 접근성 대응을 기기 설정을 바꾸지 않고 확인합니다(24편, 74편).

## Layers·Animations 패널

Layers 패널은 페이지의 합성 레이어를 트리와 3D 다이어그램으로 보여 줍니다. 레이어마다 합성된 이유, 메모리 추정치, 페인트 횟수가 나오고 느린 스크롤 영역도 표시됩니다. 레이어가 너무 많거나 큰지, `will-change`·`transform`이 의도한 레이어를 만들었는지 확인합니다(자세히는 2편). Paint Profiler로 페인트 비용을 분석합니다.

Animations 패널은 열려 있는 동안 CSS 애니메이션, CSS 전환, Web Animations, View Transitions를 자동으로 잡아 그룹으로 보여 줍니다. 재생·되감기·배속 조절이 되고, 길이·키프레임 시점·시작 지연을 끌어서 바꿔 볼 수 있습니다(자세히는 46편, 47편).

## Lighthouse

Lighthouse는 URL 하나를 분석해 Performance, Accessibility, Best Practices, SEO 감사 결과와 개선 방법을 보고서로 만드는 자동 감사 도구입니다.

- 실행 위치: DevTools의 Lighthouse 패널(로그인이 필요한 페이지에 적합), 명령줄, Node 모듈(CI 연동), PageSpeed Insights 웹.
- 결과는 JSON으로 저장해 Lighthouse Viewer에서 열 수 있습니다.
- 한 번의 시뮬레이션 측정(랩 데이터)이라서 실제 사용자 데이터와 다를 수 있습니다. 회귀 감지와 개선 항목 발견에 쓰고, 지표 판단은 필드 데이터와 함께 합니다(65편).
- 접근성 감사는 자동 검사의 범위 안에서만 동작합니다(69편).

## 센서·네트워크 조건 에뮬레이션

| 도구 | 에뮬레이션 대상 |
|------|-----------------|
| Sensors 패널 | 위치(preset 도시·좌표), 기기 방향(alpha·beta·gamma), 터치 이벤트 강제, 유휴 상태, 하드웨어 동시성, CPU 압력 상태 |
| Network 패널 스로틀링 | Fast 4G, Slow 4G, 3G, 사용자 정의 프로파일, 오프라인 |
| Network conditions 서랍 | 캐시 끄기, User-Agent 문자열 재정의 |
| Performance 패널 | CPU 스로틀링(4배 느리게 등) |

- 위치·방향·유휴 같은 API는 실제 기기 없이 해당 분기 코드를 검증하는 데 씁니다(60편, 61편).
- 오프라인 선택은 Service Worker·PWA의 오프라인 동작을 점검하는 가장 빠른 방법입니다(56편).
- 에뮬레이션은 근사치입니다. 실제 기기 센서, 실제 네트워크, 브라우저 엔진 차이는 실기기에서 확인합니다.

## Firefox·Safari 개발자 도구의 차이

같은 표준 API를 쓰므로 개념은 같고, 패널 이름·기능·유틸리티가 다릅니다.

| 항목 | Chrome | Firefox | Safari |
|------|--------|---------|--------|
| DOM·CSS | Elements | Page Inspector. 배지 표시(event·custom·scroll·grid·flex), Grid 검사 | Elements |
| 디버거 | Sources | JavaScript Debugger | Sources |
| 네트워크 | Network | Network Monitor | Network |
| 성능 | Performance, Memory | Performance, Memory | Timelines |
| 접근성 | Accessibility 탭 | Accessibility Inspector | Elements의 접근성 속성 |
| 저장소·PWA | Application | Storage Inspector, Application | Storage |
| 그 밖 | Layers, Lighthouse, Rendering | Style Editor, Responsive Design Mode | Graphics, Layers, Audit |

- Firefox Inspector의 `event` 배지는 리스너가 붙은 요소를 표시하고 누르면 Debugger로 이동합니다. `custom` 배지는 커스텀 요소의 클래스 정의로 이동합니다.
- Safari Web Inspector는 Console·Elements·Network·Sources·Timelines·Storage·Graphics·Layers·Audit 탭으로 구성됩니다. 활성화 방법은 Safari 문서를 확인합니다.
- Console 유틸리티(`$0`, `getEventListeners` 등)는 표준이 아니라 각 도구가 제공하는 기능이라 이름과 범위가 다를 수 있습니다. 반면 Console API(다음 절)는 WHATWG 표준이라 어디서나 같습니다.
- 엔진별로 다르게 나타나는 렌더링·API 문제는 그 엔진의 도구로 재현해야 합니다(자세히는 71편).

## Console API와 서식 지정자

Console API는 WHATWG Console 표준이 정의한 `console` 객체의 메서드입니다. 스크립트에서 쓰는 표준 API입니다.

| 메서드 | 동작 |
|--------|------|
| `log`, `info`, `debug` | 일반 메시지(디버그는 상세 수준이 낮은 레벨) |
| `warn`, `error` | 경고·오류 수준. 개발자 도구에서 구분되어 필터링됨 |
| `table(data, columns)` | 배열·객체를 표로 출력. `columns`로 열을 제한 |
| `group`, `groupCollapsed`, `groupEnd` | 들여쓴 묶음 출력(접힌 상태로 시작하는 변형 포함) |
| `time`, `timeLog`, `timeEnd` | 같은 레이블로 경과 시간 측정 |
| `count`, `countReset` | 레이블별 호출 횟수(기본 레이블은 `default`) |
| `assert(cond, ...data)` | 조건이 거짓일 때만 오류로 출력 |
| `trace` | 호출 스택 출력 |
| `dir`, `dirxml` | 객체를 프로퍼티 목록으로, 요소를 XML 형태로 출력 |

```js
console.table(rows, ['id', 'name'])
console.assert(items.length > 0, 'empty list', items)
console.time('load')
await load()
console.timeEnd('load')  // load: 경과 시간 출력
```

문자열 맨 앞 인수에 서식 지정자를 쓰면 뒤 인수가 치환됩니다.

| 지정자 | 의미 |
|--------|------|
| `%s` | 문자열 |
| `%d`, `%i` | 정수 |
| `%f` | 부동소수점 수 |
| `%o` | 보기 좋게 정리한 객체 |
| `%O` | 일반 객체 형태 |
| `%c` | 뒤 인수를 CSS 스타일로 적용 |

```js
console.log('%s: %d건', 'Kim', 3)        // Kim: 3건
console.log('%cWARN', 'color: red')      // 빨간 글씨
```

- `console.log(el)`은 요소를 DOM 형태로, `console.dir(el)`은 프로퍼티 목록으로 보여 줍니다.
- `console.log(obj)`로 찍은 객체는 개발자 도구에서 펼칠 때의 값이 보일 수 있습니다. 그 시점의 값이 필요하면 `structuredClone`으로 복사해 찍습니다.
- `console.error`는 스택 트레이스와 함께 오류 수준으로 표시됩니다.
- `console.clear()`는 Preserve Log가 켜져 있으면 동작하지 않습니다.

## 핵심 정리

- 증상별 패널: 구조·스타일은 Elements, 이벤트는 Event Listeners·중단점, 요청은 Network, 느림은 Performance, 메모리 증가는 Memory.
- 중단점은 코드 줄, 조건부, Logpoint, DOM 변경, XHR/fetch, 이벤트 리스너, 예외, 함수(`debug(fn)`) 8가지이며 코드를 고치지 않고 값을 찍을 때는 Logpoint를 씁니다.
- 메모리 누수는 스냅샷을 동작 전후로 찍어 Comparison으로 비교하고, `Detached`로 분리된 DOM 노드를 찾습니다.
- Rendering 탭의 Paint flashing, Layout Shift Regions로 갱신 범위를 보고, Application·Sensors·Network 도구로 저장소·기기·네트워크 조건을 에뮬레이션합니다.
- `$0`, `getEventListeners`, `monitorEvents` 같은 Console 유틸리티는 개발자 도구 안에서만 쓰며, `console` 메서드와 서식 지정자는 표준 API입니다.
- Firefox와 Safari는 패널 구성이 다르고(배지, Timelines 등), 엔진 고유 문제는 해당 엔진의 도구로 재현합니다.

## 컴포넌트별 ES Module

컴포넌트 하나를 파일(모듈) 하나로 만들고 그 모듈이 클래스를 내보내게 합니다. 사용자는 필요한 컴포넌트 모듈만 가져오고, 번들러와 브라우저는 가져오지 않은 모듈을 내려받지 않습니다(모듈 문법과 로딩은 14편).

```text
src/
  x-button/
    x-button.js        // 클래스만 export
    x-button.css.js    // 스타일 문자열 또는 시트
    define.js          // 등록 부수 효과
  x-dialog/
    ...
  index.js             // 공개 진입점
```

- 모듈 최상위에서 DOM을 만지거나 전역을 바꾸지 않습니다. 가져오기만으로 일어나는 일이 적을수록 제어하기 쉽습니다.
- 브라우저는 모듈 지정자를 파일 경로 그대로 해석합니다. 확장자를 포함한 상대 경로(`./x-button.js`)를 쓰고, 패키지 이름 같은 베어 지정자는 번들러나 import map이 풀어 줘야 합니다.
- 컴포넌트 사이의 의존은 단방향으로 둡니다. 공통 코드는 별도 모듈(`shared/`)로 빼서 순환 참조를 피합니다.
- 빌드 결과도 모듈 단위를 유지합니다(번들 하나로 합치지 않고 파일별로 출력). 합치면 사용하지 않는 컴포넌트까지 받게 됩니다.

## Public Entry Point

공개 진입점은 패키지 사용자가 가져올 수 있다고 약속한 모듈입니다. 나머지는 내부 구현이며 언제든 바뀔 수 있습니다.

```js
// index.js
export { XButton } from './x-button/x-button.js'
export { XDialog } from './x-dialog/x-dialog.js'
export { defineAll } from './define-all.js'
```

- 진입점은 두 종류를 둡니다. 루트 진입점은 모든 컴포넌트 클래스를 이름으로 내보내고, 서브패스 진입점은 컴포넌트 하나만 노출합니다(`@acme/ui/x-button`).
- 내보내는 대상: 컴포넌트 클래스, 공개 이벤트·타입, 등록 함수. 내보내지 않는 대상: 내부 헬퍼, 템플릿 조각, 스타일 상수.
- 한 파일이 여러 모듈을 다시 내보내는 배럴 파일은 편하지만 번들러가 사용하지 않는 부분을 제거하지 못하면 번들이 커집니다(아래 Tree Shaking과 Side Effects).
- 공개한 이름·속성·이벤트는 버전 정책의 대상입니다. 비공개 경로(`dist/internal/...`)를 사용자가 가져오지 못하게 막는 것이 다음 절의 exports입니다(자세히는 73편).

## Package exports

`package.json`의 `exports` 필드는 패키지의 진입점을 정하고, 목록에 없는 경로는 가져오지 못하게 막습니다(캡슐화). 옛 `main` 필드에는 이 기능이 없습니다.

```json
{
  "name": "@acme/ui",
  "type": "module",
  "exports": {
    ".": "./dist/index.js",
    "./x-button": "./dist/x-button/x-button.js",
    "./define/*": "./dist/define/*.js",
    "./style.css": "./dist/style.css"
  }
}
```

- 목록에 없는 경로(`@acme/ui/dist/internal/util.js`)를 가져오면 Node.js는 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 던집니다. 번들러도 대체로 같은 규칙을 따릅니다.
- 대상 경로는 `./`로 시작하는 패키지 안쪽 상대 경로여야 합니다. `..`이나 절대 경로는 안 됩니다.
- `*` 패턴으로 서브패스를 한꺼번에 노출하고, 값을 `null`로 지정해 일부를 막을 수 있습니다.
- 조건부 exports로 환경별 파일을 고릅니다. `types`는 맨 앞, `default`는 맨 뒤에 둡니다.

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js"
    }
  }
}
```

- `exports`를 쓰면 `package.json`이나 `custom-elements.json` 같은 파일도 목록에 넣어야 읽을 수 있습니다.
- `type: "module"`은 패키지 안의 `.js`를 ES Module로 취급하게 합니다. 구형 도구를 위해 `main`을 함께 쓰는 경우가 있습니다.

**흔한 실수:** `exports`를 도입하면서 기존 사용자가 쓰던 깊은 경로를 막아 버리는 것입니다. 이는 호환성을 깨는 변경이므로 주 버전을 올립니다.

## Tree Shaking

트리 셰이킹은 가져오지 않거나 사용하지 않는 코드를 번들에서 제거하는 최적화입니다. ES Module의 `import`와 `export`가 정적 구조라서 빌드 시점에 사용 여부를 알 수 있다는 점에 의존합니다.

트리 셰이킹이 되려면 다음이 필요합니다.

- 소스와 배포물이 ES Module 문법이어야 합니다. 도구가 CommonJS로 바꿔 버리면 제거가 어려워집니다.
- 번들러의 프로덕션 모드(최적화 켜짐)에서 빌드합니다. 개발 모드에서만 확인하면 효과를 놓칩니다.
- 모듈이 부수 효과가 없다고 표시돼 있어야 모듈 전체를 건너뛸 수 있습니다(다음 절).
- 함수 호출이 부수 효과가 없다는 주석 `/*#__PURE__*/`로 호출 결과가 쓰이지 않을 때 제거해도 된다고 알릴 수 있습니다.

컴포넌트 라이브러리에서 효과를 높이는 구조는 다음과 같습니다.

- 컴포넌트마다 모듈을 나눠 서브패스로도 노출한다.
- 클래스 정의와 `customElements.define`을 다른 파일에 둔다.
- 루트 진입점은 클래스만 내보내고 등록은 따로 둔다.

## Side Effects 관리

부수 효과(side effect)는 모듈이 가져와지는 것만으로 일어나는, 내보내는 값 밖의 변화입니다. 커스텀 요소 라이브러리의 부수 효과는 대표적으로 다음과 같습니다.

| 부수 효과 | 예 |
|-----------|-----|
| 요소 등록 | 모듈 최상위의 `customElements.define(...)` |
| 전역 스타일 주입 | `document.head`에 `style` 추가 |
| 폴리필 설치 | 전역 객체에 메서드 추가 |
| CSS 가져오기 | `import './x-button.css'` |

번들러는 `package.json`의 `sideEffects`로 이를 판단합니다. `false`는 어떤 모듈도 부수 효과가 없다는 뜻이라서 가져온 값을 쓰지 않으면 모듈 전체를 제거합니다. 배열은 부수 효과가 있는 파일만 지정합니다.

```json
{
  "sideEffects": ["./dist/define/*.js", "**/*.css"]
}
```

- `sideEffects: false`인 패키지에서 `import '@acme/ui/define/x-button'`처럼 값을 받지 않는 가져오기는 제거될 수 있습니다. 그러면 요소가 등록되지 않아 화면에 일반 요소로 남습니다. 등록 파일은 배열에 명시합니다.
- CSS 파일을 배열에서 빼면 스타일 가져오기가 제거되어 스타일이 사라질 수 있습니다.
- 안전한 설계는 부수 효과를 소수의 파일(`define`, 폴리필, CSS)에 몰고, 나머지 모듈은 순수하게 만든 뒤 위 배열로 지정하는 것입니다.
- 제3자 패키지의 `sideEffects` 표시가 틀린 경우도 있으므로 프로덕션 빌드 결과를 확인합니다.

**흔한 실수:** 부수 효과가 있는 패키지에 `sideEffects: false`를 붙이는 것입니다. 개발 모드에서는 동작하다가 프로덕션 빌드에서만 컴포넌트가 사라집니다.

## define 부수 효과와 자동 등록·수동 등록 진입점

`customElements.define`은 호출하는 순간 전역 레지스트리를 바꾸는 부수 효과입니다. 클래스를 가져오는 것과 등록을 한 모듈에서 하면 사용자가 등록 시점과 태그 이름을 정하지 못합니다. 그래서 진입점을 둘로 나눕니다.

| 진입점 | 동작 | 용도 |
|--------|------|------|
| 클래스 진입점 | 클래스만 내보냄. 등록하지 않음 | 수동 등록, 태그 이름 변경, 상속 |
| 정의(define) 진입점 | 가져오면 기본 태그 이름으로 등록 | 빠른 사용, CDN·HTML만 쓰는 환경 |

```js
// x-button/x-button.js : 등록 없음
export class XButton extends HTMLElement { /* ... */ }

// x-button/define.js : 자동 등록
import { XButton } from './x-button.js'
customElements.define('x-button', XButton)
```

- 사용자는 필요에 따라 `import '@acme/ui/define/x-button'`(자동) 또는 `import { XButton } from '@acme/ui/x-button'`과 `customElements.define('my-button', XButton)`(수동)을 고릅니다.
- 같은 클래스는 한 이름에만 등록할 수 있습니다. 같은 클래스를 두 태그 이름으로 등록하려면 `class Alias extends XButton {}`처럼 상속한 새 클래스를 씁니다.
- `define`이 한 번 호출되면 취소할 수 없습니다. 테스트와 문서 도구에서 다시 로드할 때를 고려해야 합니다.

### 중복 정의 방지 가드

이미 등록된 이름에 `define`을 다시 호출하면 `NotSupportedError`가 던져집니다. 같은 패키지가 두 번 로드되거나(번들 중복, 버전 두 개), 사용자가 이미 등록해 둔 경우에 발생합니다.

```js
export function defineElement(name, ctor) {
  const existing = customElements.get(name)
  if (!existing) return customElements.define(name, ctor)
  if (existing !== ctor) {
    console.warn(`${name} is already defined`)
  }
}
```

- 가드는 `customElements.get(name)`으로 먼저 확인합니다. 이미 있으면 건너뛰고, 생성자가 다르면 경고해 버전 충돌을 드러냅니다.
- 가드는 오류를 숨길 뿐 충돌을 해결하지 않습니다. 먼저 등록된 클래스가 계속 쓰이므로 버전이 다르면 동작이 달라질 수 있습니다. 라이브러리는 번들에 한 번만 들어가도록 의존성을 한 곳으로 모읍니다.
- 가드를 모든 `define` 진입점에서 같은 헬퍼로 처리하면 일관됩니다.

## CSS 포함 전략

Shadow DOM의 스타일은 바깥 문서의 스타일시트가 닿지 않으므로 컴포넌트 스타일은 컴포넌트와 함께 Shadow 안으로 들어가야 합니다(자세히는 24편). 패키지에서 CSS를 넣는 방법은 다음과 같습니다.

| 방법 | 내용 | 특징 |
|------|------|------|
| JS 문자열 + 공유 시트 | `new CSSStyleSheet()`에 `replaceSync(css)` 후 `adoptedStyleSheets`에 연결 | 한 파일에 자기 완결, 추가 요청 없음, 인스턴스 간 공유 |
| CSS 모듈 스크립트 | `import sheet from './x.css' with { type: 'css' }` | 시트 객체를 바로 사용. 번들러·브라우저 지원을 확인 |
| Shadow 안의 `link` | `link rel="stylesheet"` | 요청이 추가되고 스타일 적용 전 깜박임 가능 |
| 별도 CSS 파일 | `./style.css`를 exports로 노출 | 문서 전역의 토큰·리셋·라이트 DOM 컴포넌트용 |

```js
const sheet = new CSSStyleSheet()
sheet.replaceSync(`:host { display: inline-block }`)

class XButton extends HTMLElement {
  #root = this.attachShadow({ mode: 'open' })
  connectedCallback() {
    this.#root.adoptedStyleSheets = [sheet]
  }
}
```

- 생성 가능한(constructable) 스타일시트는 2023년 3월부터 널리 지원됩니다. `replaceSync`는 생성자로 만든 시트에만 쓸 수 있습니다.
- Import attributes의 `with { type: 'css' }`는 CSS 파일을 `CSSStyleSheet`로 가져옵니다. 가져오기 문법 자체는 Baseline 2025이고, CSS 형식이 미지원이면 동작하지 않으므로 지원 환경을 확인하거나 번들러가 문자열로 바꿔 주도록 합니다. 워커에서는 쓸 수 없습니다.
- 번들러의 라이브러리 모드는 가져온 CSS를 별도 파일로 출력하는 경우가 많습니다(예: Vite). 이 파일은 `exports`의 `./style.css`로 노출해 사용자가 명시적으로 가져오게 합니다.
- 테마는 CSS 사용자 정의 속성(변수)으로 열고, 컴포넌트 CSS에는 기본값을 둡니다(자세히는 74편).
- 부수 효과 목록에 CSS가 있으므로 `sideEffects`에 CSS 패턴을 포함하는지 확인합니다.

## Asset URL 처리

아이콘, 이미지, 글꼴 같은 에셋은 패키지에서 위치가 바뀌므로, 사용자의 문서 위치가 아니라 모듈 파일 위치를 기준으로 가리켜야 합니다.

### import.meta.url 기준 에셋 경로

`import.meta.url`은 현재 모듈 파일의 URL입니다(브라우저에서는 스크립트를 가져온 URL). ES Module 안에서만 쓸 수 있고 모듈 밖에서는 문법 오류입니다.

```js
const icon = new URL('./icons/close.svg', import.meta.url)

class XDialog extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `<img src="${icon.href}" alt="">`
  }
}
```

- 상대 경로 `./icons/close.svg`를 그대로 `img src`에 쓰면 모듈이 아니라 문서의 URL을 기준으로 해석됩니다. 라이브러리가 어디에 설치돼도 `new URL(경로, import.meta.url)`은 모듈 기준으로 맞습니다.
- 많은 번들러가 `new URL('...', import.meta.url)` 패턴을 인식해 에셋을 출력 폴더로 복사하고 해시된 경로로 바꿉니다. 번들러마다 지원 방식이 다르니 사용 중인 도구의 문서를 확인합니다.
- 번들러를 거치지 않고 파일을 그대로 배포하면 에셋을 모듈 옆 상대 위치에 두고 이 패턴으로 가리킵니다.

선택지는 다음과 같습니다.

| 방법 | 특징 |
|------|------|
| `new URL(..., import.meta.url)` | 모듈 기준 경로. 추가 요청이 생김 |
| 인라인(작은 SVG를 문자열, data URI) | 요청이 없고 경로 문제가 없음. JS 크기가 늘어남 |
| 사용자가 경로를 속성으로 지정 | CDN·커스텀 위치 지원. 문서화 필요 |
| CSS 사용자 정의 속성으로 이미지 지정 | 테마·교체 용이 |

- 작은 아이콘은 인라인이 안전하고, 큰 이미지·글꼴은 URL로 분리합니다.
- 번들러를 쓰는 사용자의 빌드에서 패키지 안 에셋이 출력에 포함되는지는 번들러 설정에 달려 있으므로 README에 사용법을 적어 둡니다.

## Custom Elements Manifest

Custom Elements Manifest는 패키지에 포함된 커스텀 요소를 설명하는 표준 JSON 형식의 파일(`custom-elements.json`)입니다. 도구가 컴포넌트의 공개 API를 코드 실행 없이 읽게 합니다.

- 구조: `schemaVersion`(현재 2.1.0)과 `modules` 배열이 있고, 모듈마다 클래스 선언(`kind: "class"`, `customElement: true`)과 속성·이벤트·슬롯·CSS 파트·CSS 사용자 정의 속성을 적습니다. `custom-element-definition` 내보내기는 태그 이름과 클래스를 연결합니다.
- 생성: Open Web Components의 분석기(`cem analyze`)가 소스에서 만들어 줍니다. JSDoc 주석이 설명으로 들어갑니다.
- 활용: IDE 자동 완성, 문서 생성, 템플릿 검증, 프레임워크 래퍼 생성(자세히는 75편, 77편).

패키지가 매니페스트를 알리는 방법은 `package.json`의 `customElements` 필드입니다. 이 필드가 있으면 도구가 패키지 전체를 내려받지 않고 매니페스트 위치를 찾습니다.

```json
{
  "customElements": "custom-elements.json",
  "exports": {
    "./custom-elements.json": "./custom-elements.json"
  }
}
```

`exports`를 쓰는 패키지는 `./custom-elements.json`을 목록에 넣어야 도구가 읽을 수 있습니다. 매니페스트는 빌드 때마다 다시 생성해 소스와 어긋나지 않게 합니다.

## TypeScript 선언 파일 제공 개요

TypeScript 사용자는 `.d.ts` 선언 파일이 있어야 컴포넌트의 타입을 쓸 수 있습니다. TypeScript 문법은 이 시리즈의 범위 밖이고, 패키지가 해야 할 일만 정리합니다.

- 자동 생성: 소스에서 타입을 만든다면 `tsconfig.json`의 `declaration: true`로 선언 파일을 생성해 패키지에 포함합니다.
- 위치 지정: `package.json`의 `types` 필드(`typings`와 같은 뜻)로 진입 선언 파일을 가리킵니다. `exports`를 쓰면 각 진입점의 조건에 `types`를 먼저 적습니다.
- 서브패스마다 선언 파일: 서브패스 진입점(`./x-button`)에도 각각 `types` 조건을 둡니다.
- 타입 의존: 선언 파일이 쓰는 타입 패키지는 `devDependencies`가 아니라 `dependencies`에 둡니다.
- 태그 이름 매핑: 전역 `HTMLElementTagNameMap` 인터페이스에 `'x-button': XButton`을 추가하는 선언을 제공하면 `document.createElement('x-button')`이 올바른 타입을 돌려줍니다.

```ts
declare global {
  interface HTMLElementTagNameMap {
    'x-button': XButton
  }
}
```

JavaScript로 배포하는 패키지도 JSDoc 주석과 매니페스트를 제공하면 대부분의 도구가 같은 정보를 얻습니다.

## 핵심 정리

- 컴포넌트마다 ES Module을 나누고 가져오기만으로 일어나는 일을 최소화하며, 빌드 결과도 모듈 단위로 유지합니다.
- 공개 진입점을 정하고 `package.json`의 `exports`로 노출 경로를 제한합니다(`types`는 앞, `default`는 뒤).
- 트리 셰이킹은 ES Module 구조와 `sideEffects` 표시에 의존하며, 등록과 CSS 파일은 부수 효과로 지정해야 제거되지 않습니다.
- 클래스 진입점(수동 등록)과 define 진입점(자동 등록)을 나누고, 중복 정의는 `customElements.get`으로 가드합니다.
- CSS는 생성 가능한 스타일시트나 CSS 모듈로 Shadow 안에 넣고, 에셋은 `new URL(경로, import.meta.url)`로 모듈 기준으로 가리킵니다.
- `custom-elements.json`과 `package.json`의 `customElements` 필드, `.d.ts`와 `types` 조건으로 도구와 TypeScript 사용자에게 API를 알립니다.

## 명령형 DOM 업데이트

명령형 업데이트는 "무엇이 어떻게 바뀌는지"를 코드가 직접 DOM 조작 명령으로 적는 방식입니다. 이벤트 핸들러가 상태와 DOM을 함께 고칩니다.

```js
let count = 0
button.addEventListener('click', () => {
  count++
  label.textContent = count
  label.classList.toggle('big', count > 9)
  reset.disabled = count === 0
})
```

- 바뀌는 곳이 적으면 가장 단순하고 빠릅니다.
- 상태를 바꾸는 경로가 늘어날수록 각 경로가 영향받는 DOM을 모두 기억해야 합니다. 한 곳에서 `reset.disabled` 갱신을 빠뜨리면 화면이 상태와 어긋납니다.
- DOM이 상태의 사본이 되어 "무엇이 진실인가"가 흐려집니다(자세히는 32편).

## 선언형 Render 함수

선언형 방식은 상태 전체를 받아 "화면이 어떤 모습이어야 하는지"를 한 곳에서 기술하고, 바꾸는 쪽은 상태만 고치고 `render()`를 부릅니다.

```js
class CounterBox extends HTMLElement {
  #state = { count: 0 }
  render() {
    const { count } = this.#state
    this.$label.textContent = count
    this.$label.classList.toggle('big', count > 9)
    this.$reset.disabled = count === 0
  }
}
```

- render는 같은 상태로 몇 번을 호출해도 같은 화면이 되어야 합니다(멱등).
- 모든 상태 변경 경로가 같은 `render()`를 거치므로 갱신 누락이 사라집니다.
- render 안에서는 상태를 바꾸지 않습니다. 바꾸면 다시 render가 호출될 수 있습니다(자세히는 31편).

**흔한 실수:** `innerHTML`에 사용자 입력이 섞인 문자열을 넣어 render를 만드는 것입니다. 입력이 마크업으로 해석되어 스크립트가 실행될 수 있으므로 텍스트는 `textContent`나 이후 절의 템플릿 바인딩으로 넣습니다(자세히는 05편).

## 초기 Render와 Update Render

초기 render는 DOM 뼈대를 한 번 만들고, update render는 만든 뼈대에서 값만 고칩니다. 둘을 같은 코드로 섞어 쓰면 매번 뼈대를 새로 만들게 됩니다.

```js
class UserBadge extends HTMLElement {
  #ready = false
  render() {
    if (!this.#ready) {
      this.replaceChildren(tpl.content.cloneNode(true))
      this.$name = this.querySelector('.name')
      this.#ready = true
    }
    this.$name.textContent = this.user.name
  }
}
```

- 뼈대는 `<template>`을 복제해 만들고(자세히는 03편) 동적으로 바뀌는 노드의 참조를 저장해 둡니다.
- 첫 render 시점은 `connectedCallback`입니다. 생성자에서는 속성과 자식이 아직 준비되지 않았을 수 있습니다(자세히는 18편).
- update render는 저장한 참조로 곧장 접근하므로 `querySelector`를 반복하지 않습니다.

## 전체 재렌더링 vs 부분 갱신

전체 재렌더링은 컴포넌트의 DOM을 지우고 새로 만드는 방식(예: `innerHTML = ...`, `replaceChildren()`)이고, 부분 갱신은 바뀐 노드의 값만 고치는 방식입니다.

| 항목 | 전체 재렌더링 | 부분 갱신 |
|------|----------------|-----------|
| 구현 | 단순 | 바인딩 관리 필요 |
| 비용 | 파싱·생성이 매번 발생 | 바뀐 만큼 |
| 입력값·포커스·선택 | 사라짐 | 유지됨 |
| 스크롤 위치·재생 상태 | 사라지는 일이 잦음 | 유지됨 |
| 이벤트 리스너 | 새 노드에 다시 연결 | 유지됨 |

- 입력창에 타이핑하는 중에 재렌더링하면 입력창이 새 요소로 바뀌어 포커스와 입력 중인 값이 사라집니다.
- 변경이 드물고 DOM이 작으면 전체 재렌더링이 더 안전한 선택일 수 있습니다. 목록이나 폼이 있으면 부분 갱신으로 갑니다.
- 부분 갱신으로 가는 방법은 아래 두 절(변경점 추적, 템플릿 기반 렌더)이 다룹니다.

## DOM Diff 없이 변경점 추적하기

가상 DOM 비교(diff) 없이도 어디가 바뀌었는지 알 수 있습니다. 템플릿을 만들 때 "동적인 자리"를 미리 알아 두고, 값이 바뀌었는지만 검사합니다.

```js
const bindings = [
  { node: $name, get: (s) => s.name, last: undefined,
    set: (n, v) => { n.textContent = v } },
]
function update(state) {
  for (const b of bindings) {
    const v = b.get(state)
    if (Object.is(v, b.last)) continue
    b.set(b.node, v)
    b.last = v
  }
}
```

- 정적인 부분은 다시 비교하지 않습니다. 비교 대상은 바인딩의 개수뿐이라 DOM 크기와 무관합니다.
- 이전 값 비교는 `Object.is`로 합니다. 객체는 내용이 아니라 참조로 비교되므로 같은 객체를 직접 고쳐서 넘기면 변경이 감지되지 않습니다. 새 객체로 교체합니다.
- 변경점을 비교 대신 알려 받는 방식이 반응형 상태입니다. 값이 바뀌는 순간 어떤 바인딩이 영향받는지 추적합니다(자세히는 31편).

## Render Scheduling

Render Scheduling은 상태가 바뀐 뒤 render를 언제 실행할지 정하는 일입니다. 선택지는 실행 시점으로 나뉩니다.

| 방식 | 실행 시점 | 특징 |
|------|-----------|------|
| 즉시(동기) | 상태 변경 직후 | 변경 N번이면 render N번 |
| Microtask | 현재 콜백이 끝난 직후, 렌더링 전 | 같은 콜백 안의 변경을 합침 |
| requestAnimationFrame | 다음 repaint 직전 | 프레임당 최대 한 번 |
| Idle·타이머 | 한가할 때, 지연 후 | 급하지 않은 갱신 |

- 즉시 방식은 상태를 읽을 때 항상 화면과 일치하지만 낭비가 큽니다.
- 같은 이벤트 처리 안에서 상태를 여러 번 바꾸는 일이 흔하므로 갱신 요청을 모아서 한 번만 render하는 것이 기본입니다(다음 절).
- 이벤트 루프와 렌더링 기회의 관계는 08편에서 다룹니다.

## Batch Update

Batch Update는 한 번의 render로 여러 상태 변경을 처리하는 것입니다. "갱신 예약" 플래그 하나로 구현합니다.

```js
#pending = false
set(key, value) {
  this.#state[key] = value
  if (this.#pending) return
  this.#pending = true
  queueMicrotask(() => {
    this.#pending = false
    this.render()
  })
}
```

- 첫 변경이 render를 예약하고, 같은 콜백 안의 이후 변경은 예약 플래그에 막혀 아무것도 하지 않습니다.
- 예약 이후에 render가 실행되므로 render는 항상 가장 최신 상태를 봅니다.
- 배치의 부작용으로 `set` 직후에는 아직 DOM이 갱신되지 않았습니다. DOM을 읽어야 하면 갱신이 끝난 뒤를 기다립니다. Lit은 이를 위해 `updateComplete` 프라미스를 제공합니다.

**흔한 실수:** 배치가 켜진 상태에서 `set` 직후 `this.$label.textContent`를 읽고 새 값일 것으로 기대하는 것입니다.

## Microtask 기반 업데이트

`queueMicrotask(fn)`는 현재 스크립트·콜백이 끝난 뒤 이벤트 루프가 제어를 얻기 전에 `fn`을 실행합니다. 실행 시점은 브라우저가 화면을 그리기 전입니다. Baseline 2020입니다(자세히는 08편).

- 마이크로태스크 큐는 끝까지 비워집니다. 실행 중에 새로 추가된 마이크로태스크도 같은 차례에 실행됩니다.
- 장점: 한 이벤트 처리 안의 모든 변경을 합치면서도 그 처리가 끝나자마자(화면이 그려지기 전) 반영합니다. 사용자는 중간 상태를 보지 못합니다.
- 숨은 탭에서도 실행됩니다. rAF처럼 멈추지 않습니다.
- Lit은 속성이 바뀌면 `requestUpdate()`가 갱신을 마이크로태스크로 예약합니다. 예약 후 갱신 시작 전에 속성이 더 바뀌면 같은 갱신에 포함됩니다.

```js
// 변경 3번 → render 1번 (같은 콜백 안)
el.set('a', 1); el.set('b', 2); el.set('c', 3)
```

**흔한 실수:** render가 다시 갱신을 예약하는 구조입니다. 마이크로태스크가 계속 새로 추가되면 큐가 끝나지 않아 렌더링이 막힙니다. Lit도 `updated()` 안에서 속성을 바꾸면 갱신이 한 번 더 일어나므로 무한 루프에 주의하라고 안내합니다.

## requestAnimationFrame 기반 업데이트

`requestAnimationFrame(cb)`는 다음 repaint 직전에 `cb`를 호출합니다. 호출 주기는 화면 주사율을 따르고, 콜백은 한 번만 실행되므로 계속 반복하려면 콜백 안에서 다시 예약합니다. 숨은 탭이나 보이지 않는 iframe에서는 멈춥니다. Baseline 2015입니다.

- 콜백의 인수는 프레임 시작 시각입니다. 한 프레임의 모든 콜백이 같은 값을 받습니다. 애니메이션 진행은 이 값으로 계산해야 주사율이 높은 화면에서 빨라지지 않습니다.
- 스크롤·포인터 이동처럼 프레임보다 자주 발생하는 입력에는 가장 최근 값만 저장하고 rAF에서 한 번 반영합니다.

```js
let latest, queued = false
addEventListener('pointermove', (e) => {
  latest = e.clientX
  if (queued) return
  queued = true
  requestAnimationFrame(() => {
    queued = false
    bar.style.transform = `translateX(${latest}px)`
  })
})
```

- 일반 상태 변경에는 microtask, 프레임에 맞춘 연속 갱신에는 rAF로 나눕니다. rAF만 쓰면 숨은 탭에서 갱신이 멈추고, 테스트에서 렌더 완료를 기다리기 어렵습니다.
- rAF 콜백 안에서 쓰기와 읽기(`getBoundingClientRect` 등)를 섞으면 강제 레이아웃이 일어납니다. 읽기를 먼저 모으고 쓰기를 나중에 합니다(자세히는 02편, 06편).
- 취소는 `cancelAnimationFrame(id)`입니다. 요소가 DOM에서 떼어질 때 예약된 프레임이 있으면 취소합니다.

## Keyed List Rendering

Keyed List Rendering은 목록 항목마다 안정적인 고유 키를 두고, 키로 이전 DOM 노드와 새 데이터를 짝지어 노드를 재사용하는 방식입니다. 키가 없으면 위치로 짝짓기 때문에 항목이 삽입되거나 순서가 바뀌면 엉뚱한 노드가 엉뚱한 데이터를 받습니다.

```js
function renderList(parent, items, nodes) {
  const next = new Map()
  let ref = parent.firstChild
  for (const it of items) {
    const li = nodes.get(it.id) ?? makeItem(it)
    patchItem(li, it)
    if (li === ref) ref = ref.nextSibling
    else parent.insertBefore(li, ref)
    next.set(it.id, li)
  }
  for (const [id, li] of nodes) {
    if (!next.has(id)) li.remove()
  }
  return next
}
```

- 키는 항목의 고유 식별자(`id`)를 씁니다. 배열 인덱스는 순서가 바뀌면 키 구실을 못 하고, 렌더마다 새로 만드는 난수는 모든 노드를 다시 만들게 합니다.
- 키는 같은 목록 안에서 중복되면 안 됩니다.
- 위치로 갱신하는 방식에서는 체크박스, 입력창, 포커스 같은 DOM 쪽 상태가 위치에 남고 데이터만 이동합니다. Lit 문서는 `map`이 노드를 재사용하며 값만 다시 배정한다고 하고, 노드 이동이 값 갱신보다 싸거나 DOM에 상태가 있으면 `repeat` 디렉티브(키 기반)를 쓰라고 안내합니다. 그 외에는 `map`이 기본입니다.
- `insertBefore`는 노드를 뗐다 다시 붙이므로 애니메이션·iframe 로드·포커스·popover·모달 `dialog` 상태가 초기화됩니다. `parent.moveBefore(node, ref)`는 이 상태를 유지한 채 노드를 옮깁니다. Chrome·Edge 133, Firefox 144에서 지원하고 Safari는 지원하지 않아서 Baseline이 아닙니다. 같은 문서의 연결된 부모 사이에서만 쓸 수 있습니다.

## 조건부 렌더링

조건부 렌더링은 조건에 따라 DOM을 보이거나 감추거나 만들거나 없애는 것입니다. 방법은 세 가지이고 비용과 상태 보존이 다릅니다.

| 방법 | 방식 | 상태 | 쓸 때 |
|------|------|------|-------|
| 숨김 | `hidden` 속성이나 CSS | DOM과 상태 유지 | 자주 토글, 상태 보존 필요 |
| 추가·제거 | 노드를 만들고 지움 | 제거 시 사라짐 | 드물게 보이는 무거운 내용 |
| 템플릿 전환 | 조건별 다른 템플릿 | 템플릿 바뀌면 DOM 재생성 | 서로 완전히 다른 화면 |

- `hidden`은 브라우저 기본 스타일에서 `display: none`을 적용합니다. 작성자 CSS의 `display` 값이 이를 덮어쓰므로 `.card { display: flex }`가 있으면 `hidden`이 무시됩니다. 의미적으로는 스크린 리더에서도 숨깁니다.
- 거짓일 때 아무것도 그리지 않으려면 Lit에서는 `undefined`, `null`, 빈 문자열, `nothing`이 모두 노드를 만들지 않습니다. 속성은 `nothing`을 넣으면 제거됩니다.
- 템플릿 전환이 잦고 무거우면 Lit의 `cache` 디렉티브처럼 이전 DOM을 보관했다가 되살립니다.

```js
// ❌ 두 조건이 겹치는 상태가 가능
state = { loading: true, error: true }
// ✅ 상태 하나로 표현 (다음 절)
state = { status: 'error' }
```

**흔한 실수:** 조건이 거짓일 때 `0`이나 빈 문자열을 그대로 렌더해서 화면에 `0`이 찍히는 것입니다. 조건은 불리언으로 만들어서 씁니다(`items.length > 0`).

## 빈 상태 / 로딩 / 에러 상태

데이터를 쓰는 화면은 정상 결과 외에 로딩 중, 빈 결과, 오류 상태를 따로 그려야 합니다. 상태를 `loading`, `error` 같은 불리언 여러 개로 두면 모순되는 조합이 생기므로 `status` 하나로 표현합니다.

```js
// html은 태그드 템플릿 (아래 절)
function view(s) {
  switch (s.status) {
    case 'loading': return html`<p role="status">불러오는 중</p>`
    case 'error':
      return html`<p role="alert">${s.message}</p>`
    case 'ready':
      return s.items.length ? list(s.items) : emptyView()
  }
}
```

| 상태 | 화면 | 접근성 |
|------|------|--------|
| 로딩 | 스피너나 스켈레톤 | `role="status"`로 진행 알림 |
| 빈 결과 | 이유와 다음 행동(검색 초기화, 추가) | 일반 텍스트 |
| 오류 | 원인과 재시도 버튼 | `role="alert"`로 즉시 알림 |

- 스켈레톤은 실제 내용과 같은 크기의 자리를 미리 차지해서 CLS(레이아웃 이동) 기준 0.1 이하를 지키는 데 도움이 됩니다(`aria-live` 알림은 27편).
- 새로고침 중에는 이전 데이터를 유지한 채 진행 표시만 덧붙이면 화면이 깜빡이지 않습니다. 최초 로딩과 갱신 로딩을 구분합니다.
- 오류에는 원인을 알 수 있는 문구와 복구 수단(재시도)을 같이 둡니다. 빈 상태는 오류가 아니므로 문구와 시각 처리를 다르게 합니다.
- 요청이 겹쳐 오래된 응답이 최신 화면을 덮는 문제는 39편에서 다룹니다.

## 태그드 템플릿 기반 렌더 (lit-html 방식)

태그드 템플릿은 템플릿 리터럴 앞에 함수(태그)를 붙이는 문법입니다. 태그 함수는 고정 문자열 배열과 `${}` 자리의 값들을 따로 받습니다. 이 분리가 선언형 렌더의 핵심입니다. 템플릿의 정적인 부분은 같고 값만 바뀌기 때문입니다.

```js
const html = (strings, ...values) => ({ strings, values })
const view = (name) => html`<p>안녕, ${name}</p>`
// strings: ['<p>안녕, ', '</p>'], values: [name]
```

- 같은 위치의 태그드 템플릿은 평가될 때마다 같은 `strings` 배열 객체를 받습니다. 이 배열과 `raw`는 동결되어 있고, 태그가 배열의 동일성을 키로 결과를 캐시하도록 만든 장치라고 MDN이 설명합니다.
- Lit은 이 동일성으로 같은 템플릿임을 알아보고 내부 표현을 재사용하며, 갱신 때는 바뀐 동적 값에 해당하는 DOM만 고칩니다. `TemplateResult`는 렌더되기 전까지는 템플릿 설명일 뿐입니다.
- 값은 텍스트나 속성값으로 바인딩되므로 마크업으로 해석되지 않아 `innerHTML` 문자열 조립보다 안전합니다(자세히는 05편).

## 템플릿 캐시와 바인딩 위치 기억

템플릿 기반 렌더는 두 가지를 기억합니다. 한 번 파싱한 `template` 요소(템플릿 캐시)와, 그 안에서 동적 값이 들어갈 노드의 위치(바인딩 위치)입니다. 첫 렌더에서만 파싱과 탐색을 하고 이후에는 복제와 값 쓰기만 합니다. 아래는 이 원리를 보이는 최소 구현입니다(자식 위치 바인딩만 지원).

```js
const prepared = new WeakMap()
function prepare(strings) {
  let t = prepared.get(strings)
  if (!t) {
    t = document.createElement('template')
    t.innerHTML = strings.join('<!--part-->')
    prepared.set(strings, t)
  }
  return t
}
```

```js
function instantiate(strings) {
  const root = prepare(strings).content.cloneNode(true)
  const SC = NodeFilter.SHOW_COMMENT
  const w = document.createTreeWalker(root, SC)
  const marks = []
  while (w.nextNode()) marks.push(w.currentNode)
  const parts = marks.map((c) => {
    const t = new Text('')
    c.replaceWith(t)
    return t
  })
  return { root, parts }
}
```

```js
function render({ strings, values }, container) {
  let inst = container.__inst
  if (inst?.strings !== strings) {
    inst = { strings, ...instantiate(strings) }
    container.replaceChildren(inst.root)
    container.__inst = inst
  }
  inst.parts.forEach((t, i) => {
    if (t.data !== String(values[i])) t.data = values[i]
  })
}
```

- `WeakMap`의 키가 `strings` 배열이라서 템플릿이 사라지면 캐시도 함께 정리됩니다.
- 파트는 주석 마커를 텍스트 노드로 바꾼 것이어서 갱신 때 탐색 없이 참조로 곧장 씁니다.
- 첫 호출에서 `container.__inst`가 없거나 다른 템플릿이면 새로 만들고, 같은 템플릿이면 값만 씁니다.
- 한계: 주석 마커는 속성값이나 `<table>` 안에서는 쓸 수 없습니다. 실제 라이브러리는 속성 위치와 특수 위치를 다른 방식으로 표시합니다.

## DOM Parts·Template Instantiation 제안 상태

DOM Parts는 위의 "바인딩 위치 기억"을 브라우저가 직접 지원하자는 제안입니다. DOM 파트는 DOM 트리에서 바뀌는 단위(요소의 속성, 노드의 자식, 요소의 JavaScript 프로퍼티)를 가리키는 개념이고, 프레임워크가 이 위치를 찾고 갱신하는 과정을 최적화하는 것이 목적입니다.

- 제안 문서는 `template` 요소가 복제만 돕고 동적 값의 위치를 찾고 캐시하는 일은 프레임워크가 직접 한다는 문제를 동기로 듭니다. 프레임워크는 DOM 탐색이나 쿼리로 위치를 찾아야 합니다.
- 구성은 DOM 파트를 만드는 명령형 API와, `template` 안에서 선언적으로 파트를 만드는 선언형 API 두 가지입니다.
- 출처는 Apple과 Google 기여자의 공동 제안으로 WICG 저장소에 올라 있습니다.
- 상태: 제안 문서는 표준화나 브라우저 출시 상태를 밝히지 않습니다. web-features 3.40.1에도 이 기능 항목이 없으므로 지금은 쓸 수 있는 API가 아니고, 프레임워크가 위 절의 방식으로 직접 처리합니다.
- `template` 안에서 선언적으로 파트를 만드는 방식이 제안의 선언형 API이며, 이것이 Template Instantiation에 해당하는 부분입니다. 같은 이름의 별도 제안 상태는 공식 문서로 확인하지 못해 적지 않습니다.

## 핵심 정리

- 명령형 갱신은 변경 경로마다 DOM을 고쳐 누락이 생기기 쉽고, 선언형 render는 상태를 받아 한 곳에서 화면을 기술합니다.
- 뼈대는 첫 render에서 한 번만 만들고, 이후에는 저장한 노드 참조에 변경된 값만 씁니다. 전체 재렌더링은 입력값·포커스·선택을 잃습니다.
- 변경 감지는 DOM 비교 없이 바인딩별 이전 값 비교나 반응형 추적으로 할 수 있고, 갱신은 플래그로 예약해 microtask로 합칩니다.
- 프레임에 맞춘 연속 갱신은 rAF로 하고, 목록은 안정적인 고유 키로 노드를 재사용합니다.
- 화면 상태는 `status` 하나로 표현하고 로딩·빈 결과·오류를 각각 그립니다.
- 태그드 템플릿은 `strings` 동일성으로 템플릿을 캐시하고 바인딩 위치를 기억해 값만 갱신하며, DOM Parts는 이를 브라우저가 지원하자는 제안 단계입니다.

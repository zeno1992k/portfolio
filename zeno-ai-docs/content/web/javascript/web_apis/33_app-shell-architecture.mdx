## 층 나누기

애플리케이션 Shell은 페이지가 바뀌어도 유지되는 앱의 뼈대입니다. 루트, 헤더, 내비게이션, 본문 자리, 푸터가 여기에 속합니다. 뼈대 안에 들어가는 컴포넌트는 책임에 따라 다섯 층으로 나눕니다.

| 층 | 책임 | 아는 것 | 모르는 것 |
|----|------|---------|-----------|
| 루트 | 앱 전체 설정, 레이아웃 선택 | 라우터, 스토어 | 개별 화면 내용 |
| 레이아웃 | 화면 틀(랜드마크) 제공 | 슬롯, 내비게이션 | 어떤 페이지가 들어올지 |
| 페이지 | 한 URL에 대응하는 화면 | 라우트 값, 데이터 로딩 | 다른 페이지 |
| 기능 | 하나의 업무 단위 | 도메인 데이터·서비스 | 라우트, 어느 페이지에 놓일지 |
| UI | 도메인과 무관한 표현 | 속성, 슬롯, 이벤트 | 앱 데이터 전부 |

의존은 위에서 아래로만 흐릅니다. 페이지는 기능과 UI를 쓰고, 기능은 UI를 쓰지만, UI가 기능을 알면 안 됩니다. 상태를 어디에 둘지는 31편과 32편에서 다뤘습니다.

## App Root Component

앱 루트는 문서에 딱 한 번 놓이는 최상위 컴포넌트입니다. 앱 전체에 걸린 일만 맡습니다.

```html
<body>
  <app-root></app-root>
  <script type="module" src="/main.js"></script>
</body>
```

```js
class AppRoot extends HTMLElement {
  connectedCallback() {
    const layout = document.createElement('app-layout')
    this.replaceChildren(layout)
  }
}
customElements.define('app-root', AppRoot)
```

- 루트의 책임: 레이아웃 선택, 라우터 시작, 전역 스토어와 서비스 연결, 앱 전역 이벤트(오프라인 전환, 전역 단축키) 수신, 전역 오류 경계.
- 루트가 하지 않는 일: 화면별 데이터 가져오기, 도메인 규칙. 이런 것이 쌓이면 루트가 모든 것을 아는 컴포넌트가 됩니다.
- 루트의 하위 요소는 문서의 일반 DOM(Light DOM)에 두는 쪽이 단순합니다. 전역 CSS, 랜드마크, 건너뛰기 링크가 모두 문서 트리 기준으로 동작하기 때문입니다(아래 절 참고).
- 루트를 Shadow DOM으로 감싸면 문서의 전역 스타일이 안으로 들어가지 못하고, 안쪽 요소는 문서의 `#id` 조각 이동으로 찾을 수 없습니다(자세히는 21편).

**흔한 실수:** 루트에 데이터 로딩과 화면 분기를 계속 추가해 수백 줄짜리 파일로 키우는 것입니다. 루트는 조립만 하고 내용은 아래 층에 맡깁니다.

## Layout Component

레이아웃은 여러 페이지가 공유하는 화면의 틀입니다. 헤더, 내비게이션, 본문 자리(outlet), 푸터를 배치하고 페이지가 들어갈 자리를 노출합니다.

```js
class AppLayout extends HTMLElement {
  connectedCallback() {
    if (this.firstElementChild) return
    this.innerHTML = `
      <a class="skip" href="#main">본문으로 건너뛰기</a>
      <app-header></app-header>
      <main id="main" tabindex="-1"></main>
      <app-footer></app-footer>`
  }
  get outlet() { return this.querySelector('main') }
}
```

- 페이지를 바꿀 때는 `outlet.replaceChildren(page)`로 본문 자리만 교체합니다. 헤더와 푸터는 그대로라서 상태와 포커스가 유지됩니다.
- 화면 종류가 다르면 레이아웃도 여럿 둡니다. 예를 들어 로그인 화면은 내비게이션 없는 레이아웃을, 대시보드는 사이드바 있는 레이아웃을 씁니다. 어느 레이아웃을 쓸지는 라우트 정의가 정하고 루트가 고릅니다(자세히는 35편).
- 레이아웃이 Shadow DOM을 쓰면 슬롯으로 내용을 받습니다(자세히는 22편). 이때 랜드마크와 건너뛰기 링크는 같은 shadow root 안에 둬야 하고, 링크의 `href="#main"`은 문서 기준이라 동작하지 않으므로 클릭 핸들러로 `focus()`를 호출해야 합니다.
- 위 코드의 `firstElementChild` 검사는 요소가 문서에서 빠졌다 다시 붙을 때 중복 렌더링을 막습니다(자세히는 18편).

## Header, Navigation, Main, Footer

레이아웃의 네 영역은 의미 있는 HTML 요소로 만듭니다. 요소 자체가 접근성 트리에서 랜드마크 역할을 맡습니다.

| 영역 | 요소 | 랜드마크 역할 |
|------|------|---------------|
| 머리글 | `header` | banner (body 직속일 때) |
| 내비게이션 | `nav` | navigation |
| 본문 | `main` | main |
| 바닥글 | `footer` | contentinfo (body 직속일 때) |

```html
<header>
  <a href="/">Home</a>
  <nav aria-label="주 메뉴">
    <a href="/orders" aria-current="page">주문</a>
    <a href="/stats">통계</a>
  </nav>
</header>
```

- Header: 로고, 전역 검색, 사용자 메뉴처럼 모든 페이지에 있는 것을 둡니다. 페이지 제목은 본문 안의 `h1`에 둡니다.
- Navigation: 링크 목록입니다. 현재 위치의 링크에는 `aria-current="page"`를 붙여 스크린 리더에 알립니다. 내비게이션이 둘 이상이면 `aria-label`로 서로 구별합니다.
- Main: 문서의 중심 내용입니다. 보이는 `main`은 문서에 하나만 둡니다. 반복되는 사이드바나 내비게이션은 넣지 않습니다.
- Footer: 저작권, 보조 링크 같은 전역 정보를 둡니다.
- 앱 안에서 `article`이나 `section` 안에 놓인 `header`와 `footer`는 랜드마크가 아니라 일반 요소로 처리됩니다.

접근성 역할과 키보드 설계는 27편과 28편에서 다룹니다.

## 랜드마크 요소와 건너뛰기 링크

랜드마크는 스크린 리더 사용자가 화면 영역 사이를 바로 이동할 때 쓰는 이정표입니다. 시맨틱 요소를 쓰면 역할이 자동으로 붙으므로 `role` 속성을 덧붙이지 않습니다.

| 요소 | 역할 | 조건 |
|------|------|------|
| `aside` | complementary | 항상 |
| `section` | region | 접근 가능한 이름이 있을 때만 |
| `form` | form | 접근 가능한 이름이 있을 때만 |

- 같은 종류의 랜드마크가 여럿이면 `aria-label`이나 `aria-labelledby`로 이름을 붙여 구분합니다.
- 이름 없는 `section`은 일반 컨테이너일 뿐입니다. 이름이 필요 없는 묶음이면 `div`를 씁니다.

건너뛰기 링크(skip link)는 반복되는 헤더와 내비게이션을 건너뛰고 본문으로 바로 가는 링크입니다. 키보드로 이동할 때 첫 번째로 포커스를 받는 컨트롤이어야 합니다. 평소에는 숨겨 두고 포커스를 받았을 때 보이게 해도 됩니다.

```css
.skip {
  position: absolute;
  inset-block-start: 0;
  transform: translateY(-100%);
}
.skip:focus { transform: none; }
```

- 숨길 때 `display: none`이나 `visibility: hidden`을 쓰면 포커스를 받을 수 없으므로 화면 밖으로 옮기는 방식을 씁니다.
- 링크 대상인 `main`에 `tabindex="-1"`을 두면 스크립트에서 `focus()`로 포커스를 옮길 수 있습니다. 라우트를 전환한 뒤 본문으로 포커스를 옮길 때 씁니다(자세히는 35편).
- 링크와 대상은 같은 트리에 있어야 합니다. 다른 shadow root의 요소는 `#id`로 찾지 못합니다.

## Page Component

페이지는 URL 하나에 대응하는 화면 단위 컴포넌트입니다. 라우터가 URL을 보고 알맞은 페이지를 만들어 outlet에 넣습니다.

```js
class OrdersPage extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `
      <h1>주문</h1>
      <order-filter></order-filter>
      <order-list></order-list>`
  }
}
customElements.define('orders-page', OrdersPage)
```

- 페이지의 책임: 라우트 값(경로 매개변수, 쿼리) 읽기, 필요한 데이터 불러오기, 기능 컴포넌트 조립, 로딩·오류·빈 상태 표시, 문서 제목 설정.
- 데이터는 페이지가 받아 속성과 프로퍼티로 아래에 내려 보냅니다(자세히는 32편).
- 페이지는 라우트에 한 번 매이는 컴포넌트라서 다른 곳에서 재사용하지 않습니다. 재사용이 필요해지면 그 부분을 기능 컴포넌트로 뺍니다.
- 페이지가 떠날 때 `disconnectedCallback`에서 타이머, 구독, 진행 중인 요청을 정리합니다(자세히는 18편, 67편).

## Feature Component

기능 컴포넌트는 하나의 업무 단위를 맡습니다. 장바구니 요약, 주문 목록, 댓글 영역이 예입니다. 도메인을 알고 서비스를 통해 데이터를 다루지만, 어떤 URL에 놓이는지는 모릅니다.

- 입력은 속성·프로퍼티로 받고, 결과는 이벤트로 알립니다(자세히는 25편).
- 내부 상태는 자기 안에 두고, 여러 기능이 공유하는 상태만 스토어에 연결합니다.
- 서비스(데이터 요청 담당 모듈)를 직접 만들지 않고 주입받거나 가져와 씁니다. 그래야 테스트에서 가짜 서비스로 바꿀 수 있습니다.
- 라우터를 직접 호출하지 않습니다. 이동이 필요하면 `navigate-request` 같은 이벤트를 올리고 페이지나 루트가 처리하게 합니다.

페이지와의 구분은 재사용 여부입니다. 한 페이지에서만 쓰이는 조립 코드는 페이지에, 여러 페이지에서 같은 모습과 동작으로 쓰이는 업무 단위는 기능에 둡니다.

## UI Component

UI 컴포넌트는 도메인을 모르는 표현 단위입니다. 버튼, 입력 필드, 카드, 탭, 모달이 해당합니다.

- 입력은 속성, 프로퍼티, 슬롯뿐입니다. 출력은 이벤트뿐입니다.
- 데이터를 가져오지 않고, 스토어를 읽지 않고, 라우터를 모릅니다.
- 판별 기준은 이동 가능성입니다. 파일을 다른 앱에 그대로 복사해 쓸 수 있으면 UI 컴포넌트입니다. 주문이나 사용자 같은 도메인 이름이 코드에 나오면 기능 컴포넌트입니다.
- UI 컴포넌트는 디자인 시스템의 재료입니다(자세히는 75편).

**흔한 실수:** `user-button`처럼 UI 컴포넌트에 도메인을 끌어들이는 것입니다. 그 순간 다른 곳에서 쓸 수 없고, UI 층이 기능 층에 의존하게 됩니다.

## 폴더 구조와 책임 분리

폴더는 층과 기능을 드러내야 합니다. 기능 코드는 기능 폴더 하나에 모으고, 층 사이의 의존 방향이 폴더 경로에서 읽히게 합니다.

```text
src/
  main.js          # 부트스트랩
  app/             # 루트, 레이아웃, 라우트 정의
  pages/           # 페이지 컴포넌트
  features/
    orders/        # 기능 폴더 (아래 절)
    cart/
  ui/              # 도메인을 모르는 컴포넌트
  shared/          # 서비스, 유틸리티, 스토어
```

폴더별로 가져올 수 있는 대상을 정합니다.

| 폴더 | 가져올 수 있는 곳 |
|------|--------------------|
| `app` | `pages`, `features`, `ui`, `shared` |
| `pages` | `features`, `ui`, `shared` |
| `features` | `ui`, `shared`와 자기 폴더 |
| `ui` | `ui` 안과 도메인 없는 유틸리티 |
| `shared` | 다른 층을 가져오지 않음 |

- 위에서 아래로만 가져옵니다. 역방향 가져오기가 생기면 순환 의존이 되고 모듈 평가 순서 문제가 생깁니다(자세히는 14편).
- 층별 폴더와 기능별 폴더는 두 가지 축입니다. 규모가 작으면 층별로 시작하고, 기능이 늘면 기능 폴더 안에 컴포넌트·서비스·스타일을 함께 두는 방식으로 옮깁니다.
- 파일 이름은 컴포넌트 태그 이름과 맞춥니다. `order-list.js` 안에 `order-list`가 정의되면 검색이 쉽습니다.

## Feature 단위 모듈화

기능 하나를 폴더 하나로 묶고, 바깥에는 진입점 파일 하나만 공개합니다.

```text
features/orders/
  index.js           # 공개 진입점
  order-list.js
  order-filter.js
  orders-service.js  # 내부 구현
```

```js
// features/orders/index.js
import { OrderList } from './order-list.js'
import { OrderFilter } from './order-filter.js'

export function registerOrders() {
  if (!customElements.get('order-list')) {
    customElements.define('order-list', OrderList)
  }
  if (!customElements.get('order-filter')) {
    customElements.define('order-filter', OrderFilter)
  }
}
```

- 바깥은 `index.js`만 가져옵니다. 폴더 내부 파일을 직접 가져오면 기능의 내부 구조를 바꿀 때 바깥이 깨집니다.
- 가져오기만으로 `define()`이 실행되는 부수 효과 대신 `register` 함수를 내보내면 정의 시점을 호출하는 쪽이 정합니다. 정의 순서가 중요하기 때문입니다(아래 절).
- 같은 이름을 두 번 `define()`하면 NotSupportedError입니다. `customElements.get(name)`으로 확인한 뒤 정의하면 두 번 호출해도 안전합니다.
- 기능끼리는 서로의 내부를 가져오지 않습니다. 필요한 연결은 이벤트나 공유 스토어를 거칩니다(자세히는 25편, 31편).
- 기능 폴더가 독립 단위라서 지연 로딩이 쉽습니다. 라우트가 활성화될 때 `import('./features/orders/index.js')`로 불러오고 `registerOrders()`를 호출합니다(자세히는 35편).

## 정의 순서와 whenDefined 대기 전략

`customElements.define()`을 호출하면 문서에 이미 있는 해당 태그의 요소가 업그레이드됩니다. 업그레이드는 문서 트리 순서(shadow를 포함한 순서)로 진행되고, 이때 `connectedCallback`이 호출됩니다. 업그레이드가 모두 끝난 뒤에 `whenDefined()`의 약속이 이행됩니다. 따라서 정의 순서가 곧 초기화 순서입니다.

- 부모를 먼저 정의하면 부모의 `connectedCallback`이 실행되는 시점에 자식은 아직 정의되지 않은 일반 요소입니다. 자식의 메서드를 호출하면 TypeError이고, 자식에 프로퍼티를 대입해도 클래스의 접근자가 아니라 단순 인스턴스 프로퍼티로 만들어집니다.
- 자식을 먼저 정의하면 부모가 실행될 때 이미 자식이 업그레이드되어 있습니다.
- 그래서 정의 순서는 UI, 기능, 페이지, 레이아웃, 루트처럼 아래 층에서 위로 합니다.

```js
registerUi()        // 1. UI
registerOrders()    // 2. 기능
registerPages()     // 3. 페이지
registerLayout()    // 4. 레이아웃
customElements.define('app-root', AppRoot) // 5. 루트
```

정의 순서를 정할 수 없을 때 `customElements.whenDefined(name)`으로 기다립니다. 이 약속은 정의가 끝나면 생성자로 이행하고, 이미 정의되어 있으면 즉시 이행합니다. 이름이 유효하지 않으면 SyntaxError로 거부됩니다. Baseline 2020입니다.

```js
const tags = ['app-header', 'order-list']
const waits = tags.map((t) => customElements.whenDefined(t))
await Promise.all(waits)
// 두 요소가 모두 정의되어 사용할 수 있음
```

- 정의되지 않은 요소는 `:not(:defined)` 선택자로 모을 수 있습니다. 모은 태그 이름으로 `whenDefined()`를 호출하면 필요한 만큼만 기다립니다.
- 정의가 끝내 오지 않으면 약속은 이행도 거부도 되지 않고 계속 대기합니다. 지연 로딩하는 정의는 `Promise.race`로 제한 시간을 걸어 둡니다.
- CSS `:defined`로 정의 전 요소를 가리거나 자리표시자를 보여 주면 정의 전의 깜빡임을 줄입니다. `app-root:not(:defined)`에 최소 높이와 배경을 줍니다(`:defined`는 Baseline 2020).
- 업그레이드 전에 부모가 자식에 프로퍼티를 대입한 경우를 대비해, 컴포넌트는 `connectedCallback`에서 이미 있는 인스턴스 프로퍼티를 지우고 다시 대입해 접근자를 거치게 합니다(자세히는 19편).

```js
connectedCallback() {
  if (Object.hasOwn(this, 'items')) {
    const value = this.items
    delete this.items
    this.items = value   // 클래스의 setter를 거침
  }
}
```

## Bootstrap 과정

부트스트랩은 문서가 로드된 뒤 앱이 첫 화면을 그릴 때까지의 시작 절차입니다. 진입 파일 `main.js` 하나가 순서를 책임집니다.

1. HTML을 파싱하고 `app-root` 요소를 만든다(아직 정의 전).
2. 모듈 스크립트가 실행된다. 모듈은 `defer`처럼 파싱이 끝난 뒤 실행되고, 이어서 `DOMContentLoaded`가 발생한다.
3. 초기 상태를 읽어 스토어를 만든다.
4. 서비스(API 클라이언트 등)를 만들고 스토어와 연결한다.
5. 컴포넌트를 아래 층부터 정의한다.
6. 루트가 정의되며 연결되고, 레이아웃과 헤더가 그려진다.
7. 라우터를 시작하고 현재 URL의 페이지를 outlet에 넣는다.
8. 첫 화면이 그려진 뒤 지연 작업(분석, 보조 기능)을 시작한다.

```js
// main.js
import { createStore } from './shared/store.js'
import { registerAll } from './app/register.js'
import { startRouter } from './app/router.js'

const store = createStore(readInitialState())
registerAll({ store })
startRouter({ store })
```

- 모듈 스크립트는 `DOMContentLoaded` 전에 실행되므로 문서가 이미 파싱된 상태에서 시작한다고 가정해도 됩니다. 일반 스크립트에서 쓸 때는 `document.readyState === 'loading'`이면 이벤트를 기다리고 아니면 바로 실행합니다(자세히는 14편).
- 단계 3과 4에서 만든 스토어와 서비스는 전역 변수에 두지 않고 인자나 컨텍스트로 아래 층에 전달합니다. 테스트에서 바꿔 끼울 수 있습니다(자세히는 82편).
- 초기 단계에서는 화면에 필요한 것만 하고 나머지는 미룹니다. 첫 화면과 무관한 기능은 지연 로딩합니다(자세히는 15편, 66편).
- 부트스트랩 중 오류는 한곳에서 잡아 오류 화면을 보여 줍니다. 실패한 채 빈 화면으로 남지 않게 합니다.

## 앱 초기 상태 구성

초기 상태는 첫 화면을 그리는 데 필요한 값을 첫 렌더링 전에 모은 것입니다. 여러 출처에서 모아 우선순위를 두고 합칩니다.

| 출처 | 예 | 읽는 방법 |
|------|----|-----------|
| 기본값 | 테마, 언어 | 코드 상수 |
| 환경 설정 | 다크 모드 선호 | `matchMedia('(prefers-color-scheme: dark)')` |
| 저장된 값 | 마지막에 쓴 설정 | Web Storage(자세히는 40편) |
| 서버가 심은 값 | 로그인 사용자, 설정 | HTML 안의 JSON |
| URL | 필터, 선택된 항목 | `location`(자세히는 34편) |

```js
function readInitialState() {
  const el = document.getElementById('boot-data')
  const server = el ? JSON.parse(el.textContent) : {}
  const dark = matchMedia('(prefers-color-scheme: dark)')
  const theme = dark.matches ? 'dark' : 'light'
  return { theme, ...server, path: location.pathname }
}
```

- 서버가 값을 심을 때는 `type="application/json"`인 스크립트 요소를 씁니다. 브라우저는 알 수 없는 MIME 타입의 스크립트를 실행하지 않고, `textContent`로 문자열을 읽어 `JSON.parse`합니다. 서버는 값 안의 `</script>`가 요소를 끝내지 않도록 이스케이프해야 합니다(자세히는 63편).
- 합치는 순서는 뒤쪽이 앞쪽을 덮습니다. 일반적으로 기본값, 저장된 값, 서버 값, URL 순입니다. URL은 사용자가 공유한 의도이므로 가장 높습니다.
- 저장소 읽기는 실패할 수 있습니다(비공개 모드, 용량 제한). `try`/`catch`로 감싸고 실패하면 기본값을 씁니다.
- 초기 상태에는 직렬화 가능한 값만 담습니다. 컴포넌트 인스턴스나 함수는 넣지 않습니다.
- 서버에서 비동기로 받는 값(사용자 정보)은 초기 상태에 "로딩 중"으로 표시하고, 도착하면 상태를 갱신합니다. 도착을 기다리느라 첫 렌더링을 늦추지 않습니다.
- 서버가 첫 HTML을 만들어 보낼 때의 초기 상태 전달은 76편에서 다룹니다.

## 핵심 정리

- 앱은 루트, 레이아웃, 페이지, 기능, UI 다섯 층으로 나누고 의존은 위에서 아래로만 흐릅니다. UI 컴포넌트는 도메인을 모릅니다.
- 레이아웃은 랜드마크 요소(`header`, `nav`, `main`, `footer`)로 틀을 만들고, 보이는 `main`은 하나, 같은 종류의 랜드마크가 여럿이면 이름으로 구분합니다. 건너뛰기 링크는 첫 포커스 대상이며 대상과 같은 트리에 둡니다.
- 폴더는 층과 기능을 드러내고, 기능 폴더는 진입점 하나만 공개하며 `register` 함수로 정의 시점을 호출자가 정하게 합니다.
- 컴포넌트는 아래 층부터 정의합니다. 정의 순서를 못 정할 때는 `whenDefined()`로 기다리되, 정의가 오지 않을 때를 위해 제한 시간을 둡니다.
- 부트스트랩은 상태 읽기, 서비스 연결, 정의, 루트 연결, 라우터 시작, 지연 작업 순서입니다. 초기 상태는 기본값, 저장값, 서버 값, URL 순으로 덮어씁니다.

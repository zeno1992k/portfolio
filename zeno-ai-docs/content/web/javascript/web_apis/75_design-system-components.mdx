## Base Components

기반 컴포넌트(base component)는 디자인 시스템의 맨 아래 층으로, 더 쪼갤 수 없는 단일 역할의 UI 요소입니다. 다른 컴포넌트는 이 위에 쌓입니다(자세히는 29편의 Primitive Component).

| 종류 | 예 |
|------|----|
| 동작 | Button, Link, Icon Button |
| 입력 | Input, Checkbox, Radio, Switch, Select |
| 표시 | Text, Icon, Badge, Spinner, Avatar |

```html
<!-- x-button 의 shadow tree -->
<button part="control" type="button">
  <slot name="icon"></slot>
  <slot></slot>
</button>
```

- 스타일은 토큰만 읽습니다. 색, 간격, 글꼴을 고정 값으로 쓰지 않습니다(자세히는 74편).
- 업무 지식과 데이터 접근이 없습니다. "저장 중이면 비활성" 같은 규칙은 바깥에서 속성으로 받습니다.
- 가능하면 네이티브 요소를 shadow 안에 두어 역할, 키보드, 포커스, 폼 동작을 그대로 얻습니다. 네이티브 요소로 표현할 수 없는 컨트롤은 `ElementInternals`로 폼 값과 역할을 직접 구현합니다(자세히는 26편).
- 내용은 슬롯으로 받고, 외형 훅은 컴포넌트 토큰과 `part` 몇 개로 한정합니다.
- 접근성 이름이 필요한 컴포넌트(아이콘만 있는 버튼 등)는 이름을 받는 속성이나 슬롯을 API에 포함하고, 비어 있으면 개발 중 경고합니다.

## Composite Components

합성 컴포넌트(composite component)는 기반 컴포넌트를 조합해 한 가지 사용 패턴을 완성한 컴포넌트입니다. 기반 요소 사이의 배치, 연결, 공유 상태를 책임집니다(자세히는 29편의 Compound Component).

| 종류 | 구성 |
|------|------|
| Form Field | Label, Input, 도움말, 오류 메시지 |
| Card | 헤더, 본문, 동작 영역 |
| Dialog | 제목, 본문, 버튼 묶음, 닫기 버튼 |
| Tabs | Tab 목록과 Panel |
| Pagination | 이전·다음 Button, 번호 목록 |

```html
<x-field label="이메일" hint="회사 메일을 입력">
  <x-input slot="control" name="email"></x-input>
</x-field>
```

- 의존 방향은 한쪽입니다. 합성은 기반을 쓰고 기반은 합성을 모릅니다. 서로를 가져오면 순환이 생겨 단독 사용과 트리 셰이킹이 어려워집니다(자세히는 72편).
- 합성이 기반을 내부에 가질지 슬롯으로 받을지 정합니다. 내부에 두면 일관성이 높고 슬롯으로 받으면 사용자가 다른 기반(자기 컴포넌트)을 끼울 수 있습니다. 위 예의 `control` 슬롯은 후자입니다.
- 내부 기반 컴포넌트의 외형 훅을 사용자에게 전달해야 하면 `exportparts`로 내보내고, 토큰은 상속으로 흘러갑니다(자세히는 23편).
- 라벨과 입력처럼 요소를 잇는 ID 참조는 shadow 경계를 넘지 못하므로 이름과 설명 연결 방식을 합성 단에서 정합니다(자세히는 27편).
- 부분들 사이의 통신은 이벤트와 컨텍스트로 합니다(자세히는 25편).
- 합성 컴포넌트가 늘어나는 기준은 반복입니다. 같은 조합이 여러 화면에서 반복될 때만 합성 컴포넌트로 승격합니다.

## Component Variants

변형(variant)은 같은 컴포넌트의 시각·의미 차이입니다. 버튼의 `solid`, `outline`, `ghost`가 대표적입니다. 변형은 열거형 속성으로 받는 것이 기본입니다.

```js
static observedAttributes = ['variant']
get variant() {
  return this.getAttribute('variant') ?? 'solid'
}
set variant(v) { this.setAttribute('variant', v) }
```

```css
:host([variant='outline']) button {
  background: transparent;
  border: 1px solid var(--_accent);
}
```

- 허용 값 목록은 공개 API입니다. 값을 추가하는 것은 MINOR, 제거나 이름 변경은 MAJOR입니다(자세히는 73편).
- 기본값을 명시합니다. 속성이 없거나 알 수 없는 값이면 기본값으로 동작하고, 개발 중에는 경고합니다. 예외를 던져 화면 전체를 깨뜨리지 않습니다.
- 속성은 프로퍼티와 함께 반영합니다. 선택자 `:host([variant])`가 동작하려면 프로퍼티 대입이 속성에도 쓰여야 합니다(자세히는 19편).
- 변형은 값 세트만 바꾸고 구조는 같아야 합니다. 렌더하는 요소나 동작이 달라지면(링크로 동작하는 버튼 등) 변형이 아니라 별도 컴포넌트나 별도 속성(`href`)입니다.
- 변형 수는 의도적으로 적게 유지합니다. 시스템에 변형이 늘수록 모든 조합의 문서, 테스트, 대비 확인 비용이 곱해집니다.
- 변형이 바꾸는 것은 내부 비공개 토큰입니다. `:host([variant])` 선택자 안에서 `--_accent` 같은 내부 값을 정하고, 실제 속성은 한 곳에서 그 값을 읽게 하면 변형이 늘어도 규칙이 한곳에 모입니다.

## Size / Tone / State

크기, 톤, 상태는 변형과 직교하는 세 축입니다. 한 축을 바꿔도 다른 축의 값이 그대로 유지되어야 조합이 자유롭습니다.

| 축 | 무엇이 다른가 | 예 | 입력 방식 |
|----|----------------|----|-----------|
| 변형(variant) | 시각 스타일 | `solid`, `outline`, `ghost` | 속성 |
| 크기(size) | 치수 | `sm`, `md`, `lg` | 속성 |
| 톤(tone) | 의미 색 | `neutral`, `info`, `success`, `warning`, `danger` | 속성 |
| 상태(state) | 현재 상황 | `disabled`, `loading`, `selected`, `invalid` | 속성, 내부 상태, 브라우저 |

```css
:host([size='sm']) { --_height: var(--size-control-sm) }
:host([size='lg']) { --_height: var(--size-control-lg) }
:host([tone='danger']) { --_accent: var(--color-danger) }
```

- 크기는 토큰 스케일의 단계를 선택하는 것입니다. 높이, 안쪽 여백, 글꼴 크기를 함께 묶어 한 크기 이름이 정합니다. 크기 최솟값은 터치 대상 기준(WCAG 2.5.8, 24 x 24 CSS 픽셀)을 지키도록 정합니다.
- 톤은 의미를 나타내는 축이라 색에만 의존하지 않습니다. 오류 톤이면 아이콘이나 텍스트로도 오류임을 알립니다. 색 구분이 안 되는 사용자와 forced-colors 모드를 고려합니다(자세히는 74편).
- 상태는 출처로 나눕니다.

| 출처 | 예 | 표현 |
|------|----|------|
| 사용자가 설정 | `disabled`, `loading`, `readonly` | 속성 + 접근성 상태(`aria-disabled`, `aria-busy`) |
| 컴포넌트가 계산 | 열림, 선택됨, 검증 실패 | `ElementInternals.states`의 `:state()` |
| 브라우저가 제공 | hover, active, focus | `:hover`, `:active`, `:focus-visible` |

```js
this.#internals.states.add('loading')
```

```css
:host(:state(loading)) button { cursor: progress }
```

- `:state()`는 Baseline 2024입니다(Chrome 125, Firefox 126, Safari 17.4). 외부가 바꿀 수 없는 읽기 전용 상태를 CSS에 노출하기에 알맞습니다(자세히는 20편).
- 포커스 표시는 `:focus-visible`로 키보드 사용자에게만 보이게 하고, 그 윤곽선은 대비 기준(인접 색과 3:1)을 지킵니다(자세히는 28편).
- 상태가 겹칠 때의 우선순위를 정합니다. `disabled`는 `hover`나 `active` 스타일을 받지 않아야 하고, `loading`은 클릭을 막아야 합니다.
- 조합 수는 곱입니다. 변형 3 x 크기 3 x 톤 5이면 45가지에 상태가 곱해집니다. 모든 조합이 유효하지는 않으므로 지원하는 조합과 지원하지 않는 조합을 문서에 표시합니다.

## 변형 API 수단 비교

변형이나 외형 차이를 외부에 여는 수단은 속성, 클래스, part, 토큰입니다. 무엇을 열고 싶은지에 따라 고릅니다.

| 수단 | 사용자가 하는 일 | 적합한 것 | 부담 |
|------|------------------|-----------|------|
| 속성 | `variant="outline"` | 정해진 선택지(열거) | 선택지가 컴포넌트에 고정. 프레임워크와 SSR에서 가장 호환이 좋음 |
| 클래스 | `class="primary"` | 사용자 쪽 스타일 훅 | 컴포넌트는 host의 `class`를 바꾸지 않아야 함. 외부 CSS에 의존 |
| part | `::part(control)` 규칙 | 구조 안의 요소 외형을 임의로 | 요소 구조가 공개 API가 됨 |
| 토큰 | `--x-button-bg: red` | 값 하나(색, 길이) | 이름과 값의 종류가 공개 API가 됨 |

- 선택지가 정해진 구분(변형, 크기, 톤)은 속성입니다. 검증과 문서화가 가능하고 마크업에 드러납니다.
- 자유로운 값(특정 색, 둥글기)은 토큰입니다. 열거할 수 없고 연속적인 값이라서 속성에 어울리지 않습니다.
- 구조 안의 요소를 사용자가 꾸며야 하는 지점만 part로 엽니다. 가장 넓은 통로이므로 마지막에 씁니다(자세히는 24편의 통로별 부담 표).
- 클래스는 컴포넌트의 API로 쓰지 않습니다. `class`는 사용자가 마음대로 쓰는 속성이라서 컴포넌트가 읽거나 쓰면 충돌합니다. 사용자가 자기 CSS에서 호스트를 고르는 훅으로만 둡니다.
- 한 가지 외형 변화를 여러 수단으로 동시에 열지 않습니다. 같은 일을 속성과 토큰으로 열면 어느 쪽이 우선인지 규칙이 필요하고 API 범위가 두 배가 됩니다.

## ::part 기반 외부 스타일 확장

`::part()`는 shadow tree 안에서 `part`를 붙인 요소를 바깥 CSS가 선택하는 통로입니다. 선택 문법과 `exportparts`는 23편에서 다룹니다. 이 절은 디자인 시스템에서 무엇을 part로 열지의 규칙입니다.

```css
x-button::part(control) { border-radius: 999px }
x-button::part(control):hover { filter: brightness(1.1) }
```

- part 이름은 역할로 짓습니다(`control`, `label`, `icon`, `header`). 모양이나 위치(`blue-box`, `left`)는 쓰지 않습니다.
- 모든 내부 요소에 part를 주지 않습니다. 사용자가 실제로 바꿔야 하는 것만 엽니다. part마다 요소의 존재와 역할을 약속하는 셈입니다.
- 이름과 가리키는 요소를 바꾸면 breaking 변경입니다(자세히는 73편). 내부 구조를 리팩터링해도 part가 가리키는 요소는 유지합니다.
- 외부의 `::part()` 일반 선언은 shadow 안의 같은 요소 규칙보다 이깁니다(`!important`는 반대). 컴포넌트가 지키려는 기본값이 쉽게 덮이므로 접근성에 필요한 스타일(포커스 윤곽, 최소 크기)을 사용자가 덮을 수 있다는 점을 문서에 적습니다.
- 구조 의사 클래스(`:first-child`)와 자손 선택(`::part(a) span`)은 쓸 수 없고, `:hover`, `:focus`, `::before`는 쓸 수 있습니다. 상태별 외형은 `::part(control):state(loading)`처럼 `:state()`로 열거나 part 이름(`control active`)으로 노출합니다.
- 합성 컴포넌트는 안쪽 기반 컴포넌트의 part를 `exportparts`로 내보낼 때 접두사를 붙여(`field-label`) 이름 충돌을 막습니다.
- `::part()`가 컴포넌트마다 자기 스타일을 가진다는 전제로 쓰이면 사이트의 CSS가 컴포넌트 구조에 묶입니다. 반복되는 조정은 part가 아니라 토큰이나 속성으로 올려 받습니다.
- 공개한 part 목록은 `@csspart` JSDoc 태그로 문서화합니다(아래 "Custom Elements Manifest로 문서 자동 생성").

## 접근성 규칙

디자인 시스템에서는 접근성을 컴포넌트마다 다시 구현하지 않고 시스템의 규칙으로 정해 모든 컴포넌트가 지키게 합니다. 컴포넌트 사용자가 접근성을 위해 해야 할 일은 최소화합니다.

| 규칙 | 시스템에서 보장하는 방법 |
|------|--------------------------|
| 네이티브 요소 우선 | 가능한 곳은 `button`, `input`, `dialog`를 shadow 안에서 사용 |
| 접근성 이름 | 이름이 필요한 컴포넌트는 API에 라벨 속성이나 슬롯을 두고, 비면 경고 |
| 키보드 조작 | 위젯별 패턴의 키 조작을 구현하고 문서에 표로 기록 |
| 포커스 표시 | 모든 포커스 가능 요소에 `:focus-visible` 스타일을 토큰으로 제공 |
| 색 대비 | 토큰 조합이 4.5:1, 비텍스트 3:1을 지키도록 토큰 단계에서 검증 |
| 터치 대상 | 크기 토큰의 최솟값이 24 x 24 CSS 픽셀 이상 |
| 색만으로 전달하지 않기 | 톤·상태는 아이콘, 텍스트, 모양과 함께 |
| 움직임 | `prefers-reduced-motion`을 존중(자세히는 27편) |
| 고대비 | forced-colors에서 경계와 포커스가 사라지지 않게 함(자세히는 74편) |

- 역할을 쓰기 시작하면 그 역할의 키보드 조작을 모두 구현할 책임이 생깁니다. WAI-ARIA Authoring Practices(APG)의 패턴(Accordion, Combobox, Dialog, Disclosure, Menu, Radio Group, Slider, Switch, Tabs, Tooltip, Tree View 등)이 역할, 상태, 키 조작의 기준입니다(자세히는 27편, 28편).
- APG의 원칙은 잘못된 ARIA를 쓰느니 쓰지 않는 편이 낫다는 것입니다. 네이티브 요소로 충분하면 ARIA를 더하지 않습니다.
- 컴포넌트마다 접근성 계약(역할, 이름 규칙, 키 조작, 포커스 관리)을 문서에 적고 같은 항목으로 검사합니다(자세히는 69편).
- 접근성 상태 속성(`aria-expanded`, `aria-selected` 등)은 컴포넌트의 상태와 항상 일치해야 합니다. 상태를 바꾸는 한 곳에서만 갱신해 어긋남을 막습니다.

## 디자인 시스템 문서화

문서화는 컴포넌트를 사용하는 사람이 코드를 읽지 않고도 쓸 수 있게 하는 일입니다. 컴포넌트 문서는 같은 구성을 반복해서 쓰면 읽기 쉽습니다.

| 항목 | 내용 |
|------|------|
| 개요 | 무엇이고 언제 쓰는지, 쓰지 말아야 할 때 |
| 예제 | 변형, 크기, 톤, 상태를 보여 주는 실행 예 |
| API 표 | 속성, 프로퍼티, 메서드, 이벤트, 슬롯, part, 토큰, 상태 |
| 접근성 | 역할, 이름 규칙, 키 조작, 포커스 |
| 사용 지침 | 권장 사용과 피해야 할 사용 |
| 변경 이력 | 추가, 폐기, 제거된 버전(자세히는 73편) |

- API 표는 코드에서 자동으로 만들고, 사람이 쓰는 부분(언제 쓰는지, 지침)은 따로 씁니다. 코드와 문서가 어긋나는 가장 흔한 원인은 API 표를 손으로 관리하는 것입니다.
- 토큰도 문서화 대상입니다. 이름, 값(테마별), 용도, 대비 조합을 표로 둡니다(자세히는 74편).
- 버전마다 문서를 유지합니다. 사용자는 자기가 쓰는 버전의 문서가 필요합니다.
- 문서의 예제는 실제 컴포넌트로 렌더해서 항상 최신 동작을 보여야 합니다. 이미지로 캡처한 예제는 낡습니다.

## Custom Elements Manifest로 문서 자동 생성

Custom Elements Manifest(CEM)는 컴포넌트의 공개 API를 기계가 읽는 JSON(`custom-elements.json`)으로 기술하는 형식입니다. 소스 코드를 분석해 이 파일을 생성하고, 이를 입력으로 문서나 도구를 만듭니다.

```bash
npm i -D @custom-elements-manifest/analyzer
npx cem analyze
```

- 분석기(analyzer)가 소스의 클래스와 JSDoc을 읽어 `custom-elements.json`을 만듭니다. 설정은 `custom-elements-manifest.config.mjs`에 적고, `--litelement`처럼 프레임워크용 옵션과 플러그인으로 확장합니다.
- 패키지에 포함해 배포하고 `package.json`의 `customElements` 필드로 위치를 알립니다(자세히는 73편).
- 분석기가 코드에서 읽지 못하는 것은 JSDoc 태그로 보충합니다.

| JSDoc 태그 | 기술하는 것 |
|------------|-------------|
| `@attr`, `@attribute` | 속성 |
| `@fires`, `@event` | 발생시키는 이벤트 |
| `@slot` | 슬롯 |
| `@csspart` | `::part()`로 연 요소 |
| `@cssprop`, `@cssproperty` | CSS 커스텀 속성(토큰) |
| `@cssState` | `:state()` 상태 |
| `@tag`, `@tagname` | 태그 이름 |
| `@summary`, `@default` | 요약, 기본값 |
| `@internal`, `@ignore` | 문서에서 제외 |

```js
/**
 * @tag x-button
 * @slot - 버튼 내용
 * @csspart control - 안쪽 button 요소
 * @cssprop --x-button-bg - 배경색
 * @cssState loading - 로딩 중
 */
```

매니페스트의 주요 필드는 다음과 같습니다.

| 위치 | 필드 |
|------|------|
| 패키지 | `schemaVersion`, `modules`, `readme`, `deprecated` |
| 요소 선언 | `tagName`, `customElement`, `attributes`, `events`, `slots`, `cssParts`, `cssProperties`, `cssStates`, `demos` |
| 속성 | `name`, `type`, `default`, `fieldName`, `description`, `deprecated` |
| CSS 커스텀 속성 | `name`, `syntax`, `default`, `description` |

- 거의 모든 항목에 `deprecated` 필드가 있어서 폐기 예고를 기계가 읽을 수 있게 남길 수 있습니다(자세히는 73편).
- JSON을 읽는 간단한 스크립트로 API 표를 만들 수 있습니다.

```js
const all = manifest.modules.flatMap((m) => m.declarations)
for (const d of all.filter((d) => d.customElement)) {
  for (const p of d.cssProperties ?? []) {
    console.log(`| ${p.name} | ${p.default ?? ''} |`)
  }
}
```

- 이 파일은 문서 생성 같은 여러 도구의 입력으로 쓸 수 있습니다. 분석기는 플러그인 구조라서 필요한 출력(readme, 프레임워크용 래퍼)에 맞춰 확장합니다.
- 배포 전에 CI에서 생성하고, 이전 버전의 매니페스트와 비교해 제거된 속성·이벤트가 있으면 MAJOR가 필요한지 검토하는 데 활용할 수 있습니다.

## Story / Demo 페이지

Story는 컴포넌트의 한 상태를 렌더한 예이고, Demo 페이지는 그 예들을 모아 보여 주는 페이지입니다. 디자인 시스템에서는 개발, 리뷰, 문서, 시각 검사의 공통 무대입니다.

Storybook은 이를 위한 대표 도구입니다. 웹 컴포넌트는 `@storybook/web-components-vite` 프레임워크 패키지로 쓰고 Vite 5 이상이 필요합니다.

- 스토리 파일은 컴포넌트 옆에 `*.stories.js`처럼 둡니다. Component Story Format(CSF)에서 기본 내보내기(default export)는 컴포넌트와 제목을 기술하는 메타이고, 이름 붙인 내보내기(named export)가 스토리 하나입니다.
- 스토리는 `args`(컴포넌트의 입력 값)를 받고, 이 값이 Storybook UI의 컨트롤이 되어 값을 바꿔 가며 확인할 수 있습니다.
- `play` 함수는 렌더 후 상호작용(입력, 클릭)을 자동으로 실행해 동작을 검사합니다.

Storybook이 아니어도 정적 HTML 한 장으로 Demo 페이지를 만들 수 있습니다. 변형·크기·톤·상태 조합을 한 화면에 격자로 놓습니다.

```html
<section>
  <x-button variant="solid" tone="danger">삭제</x-button>
  <x-button variant="outline" tone="danger">삭제</x-button>
  <x-button disabled>삭제</x-button>
</section>
```

- 스토리를 변형·크기·톤·상태의 매트릭스로 만들면 한 컴포넌트의 모든 조합이 한눈에 보이고, 한 축을 바꿨을 때 다른 축이 깨졌는지 즉시 보입니다.
- 테마(밝게, 어둡게, 고대비)를 전환하는 도구를 붙여서 같은 스토리를 모든 테마에서 확인합니다(자세히는 74편).
- 스토리는 시각 회귀 테스트와 접근성 검사의 입력으로도 씁니다. 렌더 결과를 이미지로 비교하거나 접근성 규칙을 자동 검사합니다(자세히는 69편).
- 매니페스트의 `demos` 필드는 요소 선언에 데모의 위치를 연결합니다.
- 스토리는 사용자가 실제로 쓰는 조합을 보여야 합니다. 내부 구현 검증용 특수 상태를 문서 예제와 섞지 않습니다.

## 디자인 시스템 거버넌스와 기여 절차

거버넌스는 컴포넌트 시스템을 누가, 어떤 절차로 바꾸는지에 대한 합의입니다. 웹 표준이 정하는 절차는 없고 조직이 정합니다. 목적은 공개 API가 임의로 변하거나 비슷한 컴포넌트가 중복해서 생기는 것을 막는 것입니다.

- 소유를 정합니다. 시스템을 유지하는 팀과 기여하는 팀의 역할, 최종 승인자를 문서에 적습니다.
- 기여는 제안에서 시작합니다. 해결하려는 문제, 기존 컴포넌트로 안 되는 이유, 공개 API 초안을 적어 승인을 받은 뒤 구현합니다.
- 공개 API(속성, 이벤트, 슬롯, part, 토큰)를 바꾸는 변경은 일반 코드 변경보다 엄격하게 검토합니다(자세히는 73편).
- 새 컴포넌트가 승격하는 단계를 둡니다. 실험 단계에서는 API가 바뀔 수 있다고 표시하고 별도 진입점으로 격리하며, 안정 단계에서만 유의적 버전의 호환 보장을 합니다(자세히는 71편).

기여 완료의 기준을 체크리스트로 둡니다.

| 항목 | 확인 |
|------|------|
| API | 속성·이벤트·슬롯·part·토큰의 이름과 기본값이 규칙을 따름 |
| 토큰 | 고정 값 없이 토큰만 사용 |
| 접근성 | 역할, 이름, 키 조작, 포커스, 대비 검사 통과 |
| 테마 | 밝게, 어둡게, 고대비에서 확인 |
| 문서 | JSDoc으로 API 표 생성, 사용 지침 작성 |
| 테스트 | 단위, 접근성, 시각 회귀(자세히는 68편, 69편) |
| 스토리 | 변형·크기·톤·상태 매트릭스 |
| 변경 기록 | 변경 기록과 필요하면 마이그레이션 문서 |

- 이 목록은 자동으로 검사할 수 있는 항목(API 표 생성, 접근성 규칙, 테스트)은 CI에 넣고, 사람이 판단할 항목(API 이름, 사용 지침)만 리뷰에서 봅니다.
- 폐기와 제거는 폐기 예고, 제거 버전, 마이그레이션 안내를 정해진 절차로 합니다(자세히는 73편).
- 결정은 기록합니다. 왜 이 변형을 만들지 않았는지, 왜 이 이름인지를 남겨 두면 같은 논의가 반복되지 않습니다.

## 핵심 정리

- 기반 컴포넌트는 토큰만 읽는 단일 역할 요소이고, 합성 컴포넌트는 기반을 조합하며 의존은 합성에서 기반으로 한쪽으로만 흐릅니다.
- 변형·크기·톤은 열거형 속성으로, 상태는 출처에 따라 속성, `:state()`, 브라우저 의사 클래스로 나누며 이 축들은 서로 독립이어야 합니다.
- 변형 수단은 정해진 선택지는 속성, 연속 값은 토큰, 구조 안의 요소는 part이며 클래스는 컴포넌트의 API로 쓰지 않습니다.
- part는 역할 이름으로 필요한 요소에만 열고, 이름과 가리키는 요소를 바꾸는 것은 breaking 변경입니다.
- 접근성은 네이티브 요소 우선, 이름 API, 키 조작, 포커스 표시, 대비, 터치 대상, 고대비를 시스템 규칙으로 정해 모든 컴포넌트가 지키게 합니다.
- Custom Elements Manifest를 소스와 JSDoc에서 생성해 API 문서를 자동화하고, Story·Demo는 조합 매트릭스로 만들며, 기여는 제안과 체크리스트 절차로 관리합니다.

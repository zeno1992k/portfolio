## 시각과 시간 원점

`performance.now()`는 `performance.timeOrigin`부터 지금까지 흐른 시간을 밀리초(소수점 포함)로 돌려줍니다. 시스템 시계가 바뀌어도 줄어들지 않는 단조 시계입니다.

```js
const t0 = performance.now()
doWork()
const elapsed = performance.now() - t0 // 예: 12.4 (ms)
```

- `timeOrigin`은 창에서는 내비게이션이 시작된 시각이고, 워커에서는 워커가 만들어진 시각입니다. 창과 워커는 원점이 다릅니다.
- 벽시계 시각이 필요하면 `performance.timeOrigin + performance.now()`입니다.
- 해상도는 교차 출처 격리된 페이지(`crossOriginIsolated`가 `true`)에서 5마이크로초, 그 밖에서는 100마이크로초입니다(교차 출처 격리는 62편).
- `Date.now()`는 에포크 기준 밀리초이고 시계 조정의 영향을 받으므로 경과 시간 측정에는 쓰지 않습니다.

## Performance Timeline 조회

Performance API는 모든 측정값을 `PerformanceEntry`로 표현합니다. 엔트리는 `name`, `entryType`, `startTime`, `duration`을 가지고, 브라우저가 쌓아 둔 목록이 Performance Timeline입니다. 창과 워커 모두에서 쓸 수 있습니다.

| 메서드 | 반환 |
|--------|------|
| `performance.getEntries()` | 모든 엔트리 |
| `performance.getEntriesByType(type)` | 해당 `entryType`의 엔트리 |
| `performance.getEntriesByName(name, type?)` | 해당 `name`의 엔트리 |

```js
const marks = performance.getEntriesByType('mark')
const one = performance.getEntriesByName('boot')
// 결과는 startTime 오름차순 배열. 없으면 []
```

- 호출한 시점에 타임라인에 있는 엔트리만 돌려줍니다. 앞으로 생길 엔트리는 알려 주지 않습니다.
- `element`, `event`, `largest-contentful-paint`, `layout-shift`, `longtask`는 `getEntriesByType`으로 조회할 수 없습니다. `PerformanceObserver`를 써야 합니다.
- 브라우저가 지원하는 타입은 `PerformanceObserver.supportedEntryTypes`로 확인합니다.

## PerformanceObserver와 buffered

`PerformanceObserver`는 엔트리가 기록될 때마다 콜백을 호출합니다. 성능 엔트리를 수집하는 기본 방법입니다.

```js
const po = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.entryType, entry.startTime)
  }
})
po.observe({ type: 'resource', buffered: true })
```

| 옵션 | 뜻 |
|------|----|
| `type` | 관찰할 엔트리 타입 하나 |
| `entryTypes` | 타입 여러 개의 배열. `type`과 함께 쓸 수 없다 |
| `buffered` | `true`이면 `observe()` 전에 이미 기록된 엔트리도 전달한다. `type`과 함께만 쓴다 |
| `durationThreshold` | `type: 'event'`일 때 최소 지속 시간. 기본 104ms, 최소 16ms |

- 스크립트가 늦게 실행되어도 앞서 일어난 페인트·리소스 엔트리를 받으려면 `buffered: true`를 씁니다.
- 타입이 여러 개이면 `entryTypes`로는 `buffered`를 쓸 수 없으므로, 타입마다 `observe()`를 따로 호출합니다.
- 관찰이 끝나면 `po.disconnect()`로 해제합니다. `po.takeRecords()`는 아직 콜백에 전달되지 않은 엔트리를 꺼냅니다.
- 모르는 타입 이름은 에러 없이 무시됩니다(콘솔 경고가 날 수 있음). 미지원 브라우저에서도 안전하게 호출할 수 있습니다.
- `PerformanceObserver`는 Baseline 널리 지원(2020년 1월부터)입니다.

## User Timing — mark와 measure

User Timing은 코드가 직접 타임라인에 표식과 구간을 남기는 API입니다. 둘 다 Baseline 널리 지원입니다.

```js
performance.mark('fetch-start')
await load()
performance.mark('fetch-end')
const m = performance.measure(
  'fetch', 'fetch-start', 'fetch-end',
)
m.duration // 예: 83.2
```

- `mark(name, { startTime, detail })`는 `PerformanceMark`를 만듭니다. `startTime`을 생략하면 지금 시각이고, `detail`에는 구조화 복제 가능한 값을 붙일 수 있습니다.
- `measure(name, startMark, endMark)`는 두 표식 사이의 구간을 `PerformanceMeasure`로 만듭니다. 이름 대신 옵션 객체 `{ start, end, duration, detail }`도 받습니다.
- 존재하지 않는 표식 이름을 넘기면 `SyntaxError`입니다. `start`, `end`, `duration`을 모순되게 주면 `TypeError`입니다.
- 이벤트 시각부터 재려면 `performance.measure('click', { start: e.timeStamp })`처럼 옵션을 씁니다.
- 쌓인 엔트리는 `performance.clearMarks(name)`, `performance.clearMeasures(name)`으로 지웁니다.
- 표식과 구간은 DevTools 성능 패널의 타이밍 트랙에도 표시됩니다.

## Navigation Timing과 Resource Timing

두 API는 같은 모델을 공유합니다. `PerformanceNavigationTiming`이 `PerformanceResourceTiming`을 확장합니다.

### Navigation Timing

현재 문서의 내비게이션 한 번을 기록하는 엔트리이며, 페이지당 하나입니다. Baseline 널리 지원(2021년 10월부터)입니다.

```js
const [nav] = performance.getEntriesByType('navigation')
nav.type                // 'navigate' | 'reload' | 'back_forward'
nav.responseStart       // 첫 바이트 도착 (TTFB)
nav.domInteractive      // readyState가 interactive가 된 시각
nav.domContentLoadedEventEnd
nav.loadEventEnd
```

타임라인 순서는 `fetchStart`, `responseStart`, `responseEnd`, `domInteractive`, `domContentLoadedEventStart`와 `End`, `domComplete`, `loadEventStart`와 `End`입니다. `activationStart`는 프리렌더링된 문서가 활성화된 시각이고, `redirectCount`는 리다이렉트 횟수입니다. 구형 `performance.timing`은 쓰지 않습니다.

### Resource Timing

문서가 불러온 리소스(이미지, 스크립트, 스타일시트, `fetch`, XHR) 하나마다 엔트리가 하나 생깁니다. Baseline 널리 지원(2017년 9월부터)입니다.

| 프로퍼티 | 뜻 |
|----------|----|
| `initiatorType` | 요청을 시작한 기능(`img`, `script`, `fetch` 등) |
| `domainLookupStart`/`End`, `connectStart`/`End`, `secureConnectionStart` | DNS·연결·TLS 구간 |
| `requestStart`, `responseStart`, `responseEnd` | 요청 송신과 응답 수신 |
| `transferSize` | 헤더를 포함한 전송 바이트. 캐시에서 읽었으면 0 |
| `encodedBodySize`, `decodedBodySize` | 압축된 본문 크기와 풀린 크기 |
| `nextHopProtocol` | `h2`, `h3` 같은 프로토콜 |
| `renderBlockingStatus` | `blocking` 또는 `non-blocking` |
| `responseStatus` | HTTP 상태 코드 |

- 교차 출처 리소스는 기본적으로 시작·종료 시각 외의 상세 값(크기, 구간)이 0으로 가려집니다. 서버가 `Timing-Allow-Origin` 응답 헤더로 허용해야 노출됩니다(교차 출처는 62편).
- 버퍼 기본 크기는 250개입니다. 가득 차면 `resourcetimingbufferfull` 이벤트가 발생하고, `performance.setResourceTimingBufferSize(n)`으로 늘립니다. 자주 쓰는 방법은 `PerformanceObserver`로 계속 수집하는 것입니다.

```js
const e = performance.getEntriesByType('resource')[0]
const dns = e.domainLookupEnd - e.domainLookupStart
const compressed = e.decodedBodySize !== e.encodedBodySize
```

## Server-Timing 헤더

서버가 `Server-Timing` 응답 헤더에 처리 시간을 적으면, 클라이언트가 같은 요청의 네비게이션·리소스 엔트리에서 읽습니다. 서버 시간과 네트워크 시간을 한 곳에서 비교할 수 있습니다. Baseline 널리 지원(2023년 3월부터)입니다.

```http
Server-Timing: db;dur=53, cache;desc="Cache Read";dur=23.2
```

```js
const [nav] = performance.getEntriesByType('navigation')
for (const t of nav.serverTiming) {
  console.log(t.name, t.duration, t.description)
}
// db 53 '' / cache 23.2 Cache Read
```

- 각 항목은 `PerformanceServerTiming`이고 프로퍼티는 `name`, `duration`(기본 0), `description`(없으면 빈 문자열)입니다.
- 교차 출처 응답은 `Timing-Allow-Origin`이 있어야 읽을 수 있습니다.

## Paint Timing

`paint` 엔트리는 첫 렌더링 시점을 알려 줍니다. Baseline 널리 지원(2021년 4월부터)입니다.

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.name, e.startTime)
  }
}).observe({ type: 'paint', buffered: true })
// first-paint 120 / first-contentful-paint 180
```

- `first-contentful-paint`(FCP)는 텍스트나 이미지 같은 DOM 콘텐츠가 처음 그려진 시각입니다.
- `first-paint`는 무엇이든 처음 그려진 시각이며, 모든 브라우저가 보고하는 것은 아닙니다.
- `duration`은 항상 0입니다.

## Core Web Vitals

Core Web Vitals는 구글이 정의한 사용자 경험 지표 세 개이며 모두 75번째 백분위로 판정합니다. 방문의 75퍼센트가 기준을 만족해야 통과입니다. 모바일과 데스크톱을 따로 봅니다.

| 지표 | 측정 대상 | 좋음 |
|------|-----------|------|
| LCP | 로딩: 가장 큰 콘텐츠가 그려진 시각 | 2.5초 이하 |
| INP | 응답성: 상호작용의 지연 | 200ms 이하 |
| CLS | 시각 안정성: 예기치 않은 이동량 | 0.1 이하 |

- LCP는 4초 초과, INP는 500ms 초과이면 나쁨이고 그 사이가 개선 필요입니다.
- INP는 2024년에 FID(First Input Delay)를 대체했습니다. FID는 첫 상호작용의 입력 지연만 쟀지만 INP는 방문 전체의 모든 상호작용을 봅니다.

### 현장 데이터와 실험실 데이터

| 구분 | 출처 | 특징 |
|------|------|------|
| 현장 데이터(field) | 실제 사용자의 브라우저에서 수집 | 실제 기기·네트워크·상호작용을 반영한다. Core Web Vitals 판정은 이 데이터로 한다 |
| 실험실 데이터(lab) | 정해진 환경에서 도구로 측정 | 재현과 디버깅이 쉽다. 사용자 입력이 없어 INP를 직접 재지 못한다 |

현장 데이터는 `PerformanceObserver`로 직접 모아 서버로 보냅니다. 실험실 수치와 어긋나는 것은 정상입니다.

### LCP와 엔트리

LCP는 뷰포트 안에서 가장 큰 이미지·텍스트 블록·비디오가 그려진 시각입니다. `largest-contentful-paint` 엔트리로 관찰하며 Baseline 2025(2025년 12월 기준 모든 핵심 브라우저)입니다.

```js
new PerformanceObserver((list) => {
  const last = list.getEntries().at(-1)
  console.log('LCP', last.startTime, last.element)
}).observe({ type: 'largest-contentful-paint', buffered: true })
```

- 더 큰 요소가 나타날 때마다 새 엔트리가 오므로 마지막 엔트리가 LCP입니다. 사용자가 스크롤하거나 입력하면 더 이상 새 엔트리가 오지 않습니다.
- 후보는 `img`, SVG의 `image`, 비디오 포스터, `background-image`가 있는 요소, 텍스트 노드 묶음입니다.
- 엔트리 프로퍼티: `element`, `size`, `url`, `renderTime`, `loadTime`, `id`. 교차 출처 이미지의 `renderTime`은 `Timing-Allow-Origin`이 없으면 거칠게 처리됩니다.
- LCP는 TTFB, 리소스 로드 지연, 로드 시간, 렌더 지연의 합입니다. 어느 구간이 긴지 나눠서 봅니다.

### INP와 Event Timing

INP는 클릭, 탭, 키 입력의 지연을 방문 내내 재고, 대부분은 가장 긴 값을 보고합니다. 상호작용이 아주 많으면 50개당 가장 긴 것 하나를 제외합니다. 호버, 스크롤, 확대는 대상이 아닙니다. 한 상호작용의 지연은 세 단계의 합입니다.

1. 입력 지연: 이벤트 발생부터 핸들러가 시작될 때까지.
2. 처리 시간: 핸들러 실행.
3. 표시 지연: 핸들러 종료부터 다음 프레임이 그려질 때까지.

`event` 엔트리(`PerformanceEventTiming`)로 관찰하며 Baseline 2025입니다.

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const delay = e.processingStart - e.startTime
    const handler = e.processingEnd - e.processingStart
    console.log(e.name, e.duration, delay, handler)
  }
}).observe({ type: 'event', durationThreshold: 16, buffered: true })
```

- `duration`은 이벤트 발생부터 다음 페인트까지이며 8ms 단위로 반올림됩니다.
- `interactionId`가 같은 엔트리는 한 상호작용입니다. `first-input` 타입은 첫 입력 엔트리입니다.
- 기본 임계값(104ms) 아래의 이벤트는 노출되지 않으므로 `durationThreshold`를 낮춰야 짧은 이벤트까지 봅니다.
- `mousemove`, `pointermove`, `touchmove` 같은 연속 이벤트는 포함되지 않습니다.

### CLS와 Layout Instability

CLS는 뷰포트 안 요소가 예기치 않게 움직인 정도의 누적값입니다. `layout-shift` 엔트리로 관찰하며 **Chromium 계열에서만** 지원됩니다(Layout Instability API).

```js
let cls = 0
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (!e.hadRecentInput) cls += e.value
  }
}).observe({ type: 'layout-shift', buffered: true })
// 단순 합산. 실제 CLS는 아래 세션 창 규칙
```

- 이동 한 번의 점수는 영향 비율 곱하기 거리 비율입니다. 영향 비율은 이동한 요소가 차지한 뷰포트 면적의 비율이고, 거리 비율은 가장 많이 움직인 거리를 뷰포트의 긴 변으로 나눈 값입니다.
- 이동은 세션 창으로 묶습니다. 이동 사이 간격이 1초 미만이고 창 전체가 5초 이하이면 같은 창입니다. CLS는 가장 큰 창의 합입니다. 위 코드는 전체 합이므로 근사치입니다.
- 클릭·탭·키 입력 후 500ms 안의 이동은 `hadRecentInput`이 `true`이고 제외합니다. 스크롤과 핀치 확대는 입력으로 치지 않습니다.
- `sources`로 어떤 요소가 어디서 어디로 움직였는지(`node`, `previousRect`, `currentRect`) 알 수 있습니다.

## Long Task와 Long Animation Frames

### Long Task

`longtask` 엔트리는 메인 스레드를 50ms 이상 차지한 작업입니다. Baseline이 아니며 Chromium 계열에서 쓸 수 있습니다.

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.duration, e.name, e.attribution)
  }
}).observe({ type: 'longtask', buffered: true })
```

- `name`은 일을 한 컨텍스트(`self`, `same-origin-ancestor`, `cross-origin-unreachable` 등)입니다.
- `attribution`은 원인 컨테이너를 가리키지만 어느 스크립트인지는 알려 주지 않는 거친 정보입니다.
- 긴 작업은 입력 지연과 INP를 키웁니다(분할 방법은 66편, 스케줄링은 08편).

### Long Animation Frames(LoAF)

`long-animation-frame` 엔트리는 렌더링 갱신이 50ms를 넘긴 프레임입니다. **Chromium 전용**이며 Baseline이 아닙니다. Long Task보다 원인을 자세히 알려 줍니다.

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.duration, e.blockingDuration)
    console.log(e.renderStart, e.scripts)
  }
}).observe({ type: 'long-animation-frame', buffered: true })
```

| 프로퍼티 | 뜻 |
|----------|----|
| `blockingDuration` | 입력 같은 우선 작업을 막은 시간 |
| `renderStart` | 렌더링 단계(rAF 콜백, 스타일·레이아웃, 옵저버 콜백) 시작 |
| `styleAndLayoutStart` | 스타일·레이아웃 계산 시작 |
| `firstUIEventTimestamp` | 프레임 중 큐에 쌓인 첫 UI 이벤트 시각 |
| `scripts` | 프레임에 기여한 스크립트 목록(`PerformanceScriptTiming`) |

## JS Self-Profiling API

`Profiler`는 JavaScript 호출 스택을 주기적으로 샘플링해 어디서 시간이 쓰이는지 알려 줍니다. **Chromium 전용**이며 Baseline이 아닙니다. 문서를 `Document-Policy: js-profiling` 헤더와 함께 내려 보내야 합니다.

```js
const profiler = new Profiler({
  sampleInterval: 10, // ms
  maxBufferSize: 10000, // 샘플 수
})
runHeavyTask()
const trace = await profiler.stop()
```

- 오버헤드가 있으므로 짧은 구간만 샘플링하고, 수집한 샘플은 클라이언트에서 집계한 뒤 보냅니다.
- 압축·난독화된 코드의 스택은 소스맵으로 복원합니다.

## Element Timing

`elementtiming` 속성을 붙인 요소가 그려진 시각을 `element` 엔트리로 받습니다. **Chromium 전용**이며 Baseline이 아닙니다. LCP 후보가 아닌 특정 요소(히어로 이미지, 핵심 문구)의 표시 시각을 직접 재고 싶을 때 씁니다.

```html
<img src="hero.jpg" elementtiming="hero" />
```

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.identifier, e.renderTime)
  }
}).observe({ type: 'element', buffered: true })
```

- 대상은 `img`, SVG `image`, 비디오 포스터, 배경 이미지가 있는 요소, 텍스트 노드 묶음입니다.
- `identifier`는 `elementtiming` 속성의 값이고, `intersectionRect`와 `naturalWidth`·`naturalHeight`도 제공합니다.

## 컴포넌트별 성능 측정

컴포넌트 단위 측정은 User Timing을 생명주기 콜백에 끼워 넣어 구현합니다. 컴포넌트 이름이 들어간 표식 이름을 쓰고, `detail`에 식별 정보를 남깁니다(생명주기는 18편).

```js
class UiList extends HTMLElement {
  connectedCallback() {
    performance.mark('ui-list:start')
    this.render()
    performance.mark('ui-list:end')
    performance.measure('ui-list:render', {
      start: 'ui-list:start',
      end: 'ui-list:end',
      detail: { rows: this.rows },
    })
  }
}
```

- 동기 렌더링은 `render()` 전후에 표식을 두면 됩니다. 비동기이면 데이터를 다 그린 시점에 끝 표식을 찍습니다.
- 수집은 `PerformanceObserver`로 `measure`를 관찰해 `name` 접두사별로 집계합니다.
- 표식을 찍기만 하고 지우지 않으면 타임라인에 쌓입니다. 집계 후 `clearMarks`·`clearMeasures`로 비웁니다.
- 사용자 체감과 이어서 보려면 `measure`의 구간을 Long Task·LoAF·INP 엔트리의 시각과 겹쳐 봅니다.
- 컴포넌트 렌더링을 재는 행위 자체가 비용이므로, 운영 환경에서는 샘플링하거나 개발용 플래그로 켭니다.

**흔한 실수:**

- `buffered: true` 없이 늦게 `observe()`해서 이미 지나간 FCP·LCP를 놓칩니다.
- `getEntriesByType('layout-shift')`처럼 조회할 수 없는 타입을 `getEntries` 계열로 읽으려 합니다. 항상 빈 배열입니다.
- 실험실 점수가 좋다고 Core Web Vitals를 통과했다고 판단합니다. 판정은 현장 데이터입니다.
- 크로스 오리진 리소스의 크기가 0으로 나오는 것을 캐시 적중으로 오해합니다. `Timing-Allow-Origin`이 없는 것일 수 있습니다.

## 핵심 정리

- `performance.now()`는 `timeOrigin` 기준 단조 시계이며, 모든 측정값은 `PerformanceEntry`로 Performance Timeline에 쌓입니다.
- 엔트리 수집은 `PerformanceObserver`가 기본이고, 이미 지나간 엔트리는 `buffered: true`로 받습니다. `getEntries` 계열은 호출 시점의 스냅샷이며 일부 타입은 조회되지 않습니다.
- Navigation·Resource·Server·Paint Timing은 Baseline 널리 지원이고, LCP와 Event Timing은 Baseline 2025입니다. Layout Shift, Long Task, LoAF, Element Timing, JS Self-Profiling은 Chromium 계열 중심입니다.
- Core Web Vitals는 LCP 2.5초, INP 200ms, CLS 0.1 이하를 75번째 백분위 현장 데이터로 판정하며, INP는 2024년에 FID를 대체했습니다.
- 컴포넌트별 측정은 생명주기 콜백에서 `mark`와 `measure`로 구간을 남기고, 관찰자로 집계합니다.

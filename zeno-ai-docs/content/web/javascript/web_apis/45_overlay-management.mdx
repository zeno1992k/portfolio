## Focus Management

오버레이가 열리면 키보드 포커스를 오버레이 안으로 옮기고, 닫히면 열기 직전 위치로 되돌립니다. 모달이면 포커스가 오버레이 밖으로 나가지 못하게 막습니다. 마우스 사용자에게는 보이지 않지만 키보드·스크린 리더 사용자에게는 오버레이가 쓸 수 있는지를 가르는 기준입니다(키보드 포커스 일반 규칙은 28편, 네이티브 요소는 44편).

네이티브 오버레이는 이를 대부분 대신 처리합니다.

| 종류 | 열릴 때 | 닫힐 때 |
|------|---------|---------|
| 모달 `dialog` | 첫 포커스 가능 요소, `autofocus` 요소가 있으면 그 요소, 없으면 `dialog` 자체 | 열기 전 요소로 복귀 |
| popover | `autofocus` 요소가 있으면 그 요소로 이동, 없으면 포커스를 옮기지 않음 | 포커스가 팝오버 안에 있었다면 열기 전 요소로 복귀 |

`popovertarget` 버튼으로 연 팝오버는 포커스를 옮기지 않아도 다음 Tab이 팝오버 안으로 들어갑니다(MDN).

직접 만든 오버레이는 열기 전 요소를 기억했다가 닫을 때 돌려줍니다.

```js
let opener = null
function openPanel() {
  opener = document.activeElement
  panel.hidden = false
  panel.querySelector('[autofocus], button, input')?.focus()
}
function closePanel() {
  panel.hidden = true
  if (opener?.isConnected) opener.focus()
  opener = null
}
```

- 오버레이 안에 포커스할 요소가 없으면 패널에 `tabindex="-1"`을 주고 패널 자체에 포커스를 줍니다.
- 열기 전 요소가 이미 DOM에서 사라졌다면(`isConnected`가 `false`) 복귀할 곳이 없습니다. 목록 항목처럼 사라질 수 있는 요소가 열었다면 가까운 안정된 요소(목록 컨테이너 등)로 복귀시킵니다.
- Shadow DOM 안의 버튼은 `document.activeElement`가 호스트 요소를 돌려줍니다. 정확한 요소가 필요하면 `shadowRoot.activeElement`를 따라 내려갑니다(자세히는 21편).

모달에서 포커스를 가두는 가장 안전한 방법은 배경을 `inert`로 만드는 것입니다. `inert` 요소는 클릭·포커스·검색·텍스트 선택이 막히고 접근성 트리에서도 빠집니다. Baseline 2023부터 널리 지원됩니다.

```js
const dimmed = [...document.body.children]
  .filter((el) => el !== overlayRoot)
dimmed.forEach((el) => (el.inert = true))
// 닫을 때: dimmed.forEach((el) => (el.inert = false))
```

**흔한 실수:** Tab 키 핸들러로 첫·마지막 요소 사이를 순환시키는 직접 구현입니다. 동적으로 추가되는 요소, 숨겨진 요소, Shadow DOM 경계를 모두 따라가야 해서 쉽게 어긋납니다. 가능하면 `inert`나 `showModal()`을 씁니다.

## Escape 처리

Escape 키는 "닫기 요청"의 대표 입력입니다. 네이티브 모달 `dialog`와 `auto`·`hint` popover는 Escape에 스스로 반응하고, 직접 만든 오버레이는 `keydown`으로 처리합니다.

```js
document.addEventListener('keydown', (e) => {
  if (e.key !== 'Escape' || e.isComposing) return
  if (panel.hidden) return
  e.preventDefault()
  closePanel()
})
```

- `isComposing`은 한글·일본어·중국어 입력기의 조합 중에 `true`입니다. 조합 중의 Escape는 입력기에 맡기고 오버레이를 닫지 않습니다.
- 브라우저는 Escape를 닫기 요청으로 처리하기 전에 `keydown`을 먼저 발생시키고, 그 이벤트가 `preventDefault()`로 취소되면 이후 처리를 멈춥니다(HTML 표준). 안쪽의 커스텀 패널이 Escape를 처리했다면 `preventDefault()`로 바깥의 `dialog`까지 닫히는 일을 막습니다.
- 여러 오버레이가 열려 있을 때 Escape 한 번은 가장 위의 것 하나만 닫아야 합니다(아래 "중첩 Overlay 관리").

`dialog`는 닫히기 전에 `cancel` 이벤트를 발생시키고, 이 이벤트는 취소할 수 있습니다. 작성 중인 내용이 있을 때 확인 없이 닫히지 않게 할 때 씁니다. 코드로 닫을 때 `requestClose()`를 부르면 같은 `cancel` 흐름을 탑니다.

```js
dialog.addEventListener('cancel', (e) => {
  if (form.dirty) e.preventDefault() // 닫기 취소
})
```

**흔한 실수:** Escape를 `keyup`으로 처리하는 것입니다. 플랫폼은 키를 누르는 순간을 닫기 요청으로 해석하므로 `keydown`을 기준으로 맞춥니다.

## 외부 클릭 처리

외부 클릭 처리는 오버레이 바깥을 눌렀을 때 닫는 동작입니다. 직접 구현할 때는 이벤트 종류, 안쪽의 정의, Shadow DOM 세 가지를 정해야 합니다.

```js
let downInside = false
const inside = (e) => {
  const path = e.composedPath()
  return path.includes(panel) || path.includes(trigger)
}
document.addEventListener('pointerdown', (e) => {
  downInside = inside(e)
}, true)
document.addEventListener('pointerup', (e) => {
  if (!downInside && !inside(e)) closePanel()
}, true)
```

- `click`만 쓰면 안쪽에서 눌러 바깥에서 놓는 드래그(텍스트 선택 등)에서 `click`이 둘의 공통 조상에 발생해 잘못 닫힙니다. `pointerdown`과 `pointerup`이 모두 바깥일 때만 닫습니다. 네이티브 light dismiss도 같은 방식입니다(HTML 표준).
- 안쪽에는 오버레이 자신뿐 아니라 여는 버튼을 포함합니다. 포함하지 않으면 버튼 클릭에서 바깥 클릭이 먼저 닫고 버튼 클릭이 다시 여는 깜빡임이 생깁니다.
- 이벤트 대상 `e.target`은 Shadow DOM 경계에서 호스트로 바뀝니다. 경로 전체를 담은 `e.composedPath()`로 포함 여부를 판별합니다(자세히는 7편, 21편).
- 캡처 단계(`true`)로 `document`에 등록하면 안쪽 요소가 `stopPropagation()`을 호출해도 놓치지 않습니다.
- `iframe` 안쪽 클릭은 별도 문서의 이벤트라서 부모 문서에 도착하지 않습니다. 바깥 클릭 감지가 되지 않는다는 점을 알고 설계합니다.

모달 `dialog`의 backdrop 클릭은 `dialog` 요소 자신이 대상이 됩니다. `dialog`의 padding 영역을 눌러도 대상이 `dialog`이므로, 안쪽인지는 `getBoundingClientRect()`의 좌표와 비교해 판별합니다(자세히는 6편). 네이티브 속성 `closedby="any"`는 바깥 클릭 닫기를 선언으로 처리하며, Baseline이 아닙니다(Chrome·Edge 134, Firefox 141).

## light dismiss 규칙과 popover 스택

light dismiss는 오버레이 바깥을 누르거나 Escape를 눌러 별도 닫기 버튼 없이 닫는 방식입니다. popover는 `popover` 속성의 값에 따라 규칙이 다릅니다. popover는 Baseline 2025입니다.

| 값 | light dismiss | 다른 popover와의 관계 |
|----|---------------|-----------------------|
| `auto` (기본) | 바깥 클릭·Escape로 닫힘 | 열리면 조상이 아닌 다른 `auto`를 닫음 |
| `hint` | 바깥 클릭·Escape로 닫힘 | `auto`를 닫지 않고 다른 `hint`만 닫음 |
| `manual` | 닫히지 않음 | 서로 독립적으로 동시에 열림 |

- 브라우저는 `auto` 스택과 `hint` 스택을 따로 관리합니다. 열릴 때 스택에 쌓이고 닫힐 때 빠집니다. `manual`은 스택에 들어가지 않습니다.
- `showModal()`과 `requestFullscreen()`을 호출하면 열려 있는 `auto` popover가 닫힙니다.
- 한 팝오버를 닫으면 그 후손이 먼저 닫힙니다.
- 바깥 클릭은 눌린 지점에서 가장 가까운 열린 팝오버(또는 그것을 가리키는 버튼이 가리키는 팝오버)를 기준으로, 그 조상이 아닌 `auto`·`hint`를 모두 닫습니다.
- 팝오버가 닫힐 때 포커스가 팝오버 안에 있었다면 열기 전 요소로 복귀합니다.
- `auto`·`hint`는 Escape 같은 닫기 요청에 반응하는 close watcher를 만들고 `manual`은 만들지 않습니다(아래 "CloseWatcher와 Android 뒤로 가기").
- `hint`는 Baseline이 아닙니다(Chrome·Edge 151, Firefox 153). 지원하지 않는 브라우저에서는 `manual`처럼 동작하므로 닫기 수단을 따로 둡니다.

상태 변화는 `beforetoggle`(열릴 때는 취소 가능)과 `toggle` 이벤트로 알 수 있습니다. 둘 다 `oldState`, `newState`를 가집니다. `beforetoggle` 안에서 `showPopover()`·`hidePopover()`를 호출하면 `InvalidStateError`입니다.

**흔한 실수:** 툴팁에 `auto`를 쓰는 것입니다. 툴팁이 열리면서 사용자가 열어 둔 메뉴 같은 `auto` 팝오버를 닫아 버립니다. 툴팁은 `hint`가 맞는 용도이고, `hint`를 쓸 수 없으면 `manual`로 직접 닫기를 구현합니다.

## 중첩 Overlay 관리

중첩 오버레이는 오버레이 안에서 다시 오버레이를 여는 구조입니다(모달 안의 확인 대화상자, 메뉴 안의 하위 메뉴). 규칙은 "가장 위의 것만 반응한다"와 "부모는 자식의 안쪽으로 본다" 두 가지입니다.

네이티브 쪽에서는 이미 지켜집니다.

- top layer에는 나중에 들어간 요소가 위에 놓입니다. top layer 요소에는 `z-index`가 적용되지 않으므로 `z-index` 경쟁이 필요 없습니다(top layer 요소는 자체 스태킹 컨텍스트를 가집니다).
- 모달이 여러 개 열려 있으면 Escape는 가장 위의 모달 하나만 닫습니다.
- popover의 부모-자식 관계는 세 방법 중 하나로 만들어집니다. 이 관계가 있어야 자식 안의 클릭이 부모를 닫지 않습니다.

```html
<!-- 1. DOM 후손 -->
<div popover>부모 <div popover>자식</div></div>
<!-- 2. 부모 안의 버튼이 자식을 가리킴 -->
<div popover>부모 <button popovertarget="c">열기</button></div>
<div popover id="c">자식</div>
<!-- 3. anchor 속성으로 부모 지정 -->
<div popover id="p">부모</div>
<div popover anchor="p">자식</div>
```

- `auto` 팝오버가 `hint` 팝오버의 자식이 되면 `hint`로 낮춰집니다.
- 사용자 조작 없이 연이어 열린 오버레이는 같은 close watcher 그룹으로 묶여 닫기 요청 한 번에 함께 닫힐 수 있습니다(아래 CloseWatcher 절).

직접 만든 오버레이에서는 스택을 배열로 관리합니다. 열면 `push`, 닫으면 해당 항목과 그 뒤(자식)를 위에서부터 닫습니다. Escape와 바깥 클릭은 맨 위 항목에만 적용하고, 그 항목의 후손 영역을 누른 클릭은 안쪽으로 취급합니다(구현은 "Overlay Manager 설계").

**흔한 실수:**

- 부모를 닫을 때 자식을 남겨 두는 것입니다. 부모가 사라지면 자식의 위치 기준과 포커스 복귀 대상이 없어집니다.
- 자식 안에서 누른 클릭을 바깥 클릭으로 판단해 부모를 닫는 것입니다. 부모의 안쪽에 자식 영역을 포함해야 합니다.
- 오버레이마다 `z-index`를 올려 가며 쌓는 것입니다. 네이티브 top layer를 쓰면 필요 없고, 쓸 수 없다면 스택 순서에 따라 한 곳에서 값을 부여합니다.

## CloseWatcher와 Android 뒤로 가기

CloseWatcher는 오버레이의 닫기 요청을 직접 받는 API입니다. 닫기 요청은 사용자가 "화면에 보이는 것을 닫겠다"고 브라우저에 보내는 신호로, 플랫폼마다 다른 입력으로 들어옵니다.

- 데스크톱의 Escape 키
- Android 등 일부 모바일 플랫폼의 뒤로 가기 버튼·제스처
- 보조 기술의 닫기 제스처(iOS VoiceOver의 두 손가락 Z 동작 등)
- 게임 컨트롤러의 뒤로 버튼

```js
const ac = new AbortController()
const watcher = new CloseWatcher({ signal: ac.signal })
watcher.oncancel = (e) => {
  if (form.dirty) e.preventDefault()
}
watcher.onclose = () => closePanel()
// 닫기 버튼 등 다른 경로: watcher.requestClose()
// 요소를 다른 방식으로 제거할 때: ac.abort() 또는 destroy()
```

| 멤버 | 동작 |
|------|------|
| `cancel` 이벤트 | `close` 직전에 발생. 취소하면 닫기가 중단됨 |
| `close` 이벤트 | 닫기가 확정될 때 발생. 이후 감시자는 비활성화 |
| `requestClose()` | `cancel`을 발생시키고 취소되지 않으면 `close`로 이어짐 |
| `close()` | `cancel` 없이 바로 `close`를 발생시킴 |
| `destroy()` | 감시자를 해제. 새 독립 CloseWatcher를 만들 수 있게 됨 |

- 모든 닫기 경로가 `requestClose()`를 부르면 취소·닫기 로직을 `cancel`·`close` 핸들러 한 곳에 모을 수 있습니다.
- 감시자가 있으면 Android 뒤로 가기는 페이지 이동 대신 닫기 요청이 됩니다. 활성 감시자가 없으면 브라우저는 이를 히스토리 한 칸 뒤로 이동하는 것 같은 다른 동작으로 해석할 수 있습니다(HTML 표준). 닫기 요청이 뒤로 가기로 쓰이는 환경에서 오버레이가 사용자를 페이지 밖으로 내보내지 않게 해 줍니다.
- 모달 `dialog`와 `auto`·`hint` popover도 같은 장치를 씁니다.

남용 방지 규칙 때문에 감시자는 그룹으로 묶입니다(HTML 표준).

- 사용자 활성화 없이 만든 감시자는 이미 활성인 감시자(CloseWatcher, 모달 `dialog`, popover 포함)와 같은 그룹이 되어 닫기 요청 한 번에 함께 닫힙니다.
- 독립 그룹의 수는 최대 1 + 사용자 활성화 횟수입니다. 클릭 같은 사용자 조작 안에서 만들어야 독립 그룹이 됩니다.
- 사용자 활성화 없이 같은 감시자의 닫기를 반복 요청하면 `cancel` 이벤트는 취소할 수 없게 됩니다.

CloseWatcher는 Baseline이 아닙니다(Chrome·Edge 126, Firefox 149). 지원하지 않으면 `keydown` Escape 처리로 대체합니다.

```js
if ('CloseWatcher' in window) {
  // CloseWatcher 사용
} else {
  // keydown Escape 처리
}
```

**흔한 실수:** 타이머나 `fetch` 응답 안에서 CloseWatcher를 만드는 것입니다. 사용자 활성화가 없어서 앞서 열린 감시자와 한 그룹이 됩니다. 요소를 제거할 때 `destroy()`나 `abort()`를 빠뜨리면 죽은 감시자가 뒤로 가기를 가로챕니다.

## Tooltip / Dropdown / Menu

세 가지는 겉모습이 비슷해도 열고 닫는 조건과 포커스 규칙이 다릅니다.

| 종류 | 열림 | 닫힘 | 포커스 | ARIA | 네이티브 수단 |
|------|------|------|--------|------|---------------|
| Tooltip | 호버·키보드 포커스 | 마우스 이탈·blur·Escape | 이동하지 않음 | `role="tooltip"`, 트리거에 `aria-describedby` | `popover="hint"` + `interestfor` |
| Dropdown(패널) | 클릭 | 바깥 클릭·Escape·선택 | 패널 안으로 이동하거나 Tab으로 진입 | 트리거에 `aria-expanded`, `aria-controls` | `popover="auto"` + `popovertarget` |
| Menu(메뉴 버튼) | 클릭·Enter·Space·방향키 | Escape·항목 선택·바깥 클릭 | 첫 항목으로 이동, 방향키로 이동 | 버튼에 `aria-haspopup`, `aria-expanded`, 목록에 `role="menu"` | `popover="auto"` + 직접 키보드 구현 |

Tooltip은 포커스를 받지 않는 보조 설명입니다(WAI-ARIA 패턴은 작업 중 문서입니다). 안에 링크나 버튼을 넣을 수 없고, 필수 정보를 tooltip에만 두면 호버가 없는 터치 환경에서 볼 수 없습니다. WCAG 1.4.13(AA)은 호버·포커스로 나타나는 내용에 세 가지를 요구합니다.

- 해제 가능: 포인터나 포커스를 옮기지 않고 닫을 수 있어야 합니다(예: Escape).
- 포인터 이동 가능: 포인터를 내용 위로 옮겨도 사라지지 않아야 합니다.
- 유지: 호버·포커스가 사라지거나 사용자가 닫을 때까지 보여야 합니다.

Menu 버튼 패턴(WAI-ARIA)에서 Enter와 Space는 메뉴를 열고 첫 항목에 포커스를 줍니다. 방향키 아래·위(선택)는 첫·마지막 항목으로 열기도 합니다. 항목 사이는 방향키로 이동하는 것이 `role="menu"`의 약속이라서 이 role을 쓰면 방향키를 구현해야 합니다(roving tabindex는 28편). 단순히 패널을 펼치는 용도라면 `role="menu"` 없이 `aria-expanded` 버튼과 일반 링크·버튼 조합이 더 맞습니다.

```html
<button aria-haspopup="menu" aria-expanded="false"
        aria-controls="m">작업</button>
<ul id="m" role="menu" hidden>
  <li role="menuitem" tabindex="-1">복사</li>
  <li role="menuitem" tabindex="-1">삭제</li>
</ul>
```

**흔한 실수:** 닫을 때 `aria-expanded`를 `false`로 되돌리지 않는 것, 메뉴를 닫은 뒤 포커스를 버튼으로 돌려주지 않는 것, Tab으로 메뉴를 벗어났는데 메뉴가 열려 있는 것입니다. 이름과 역할 설정은 27편에서 다룹니다.

## CSS 앵커 포지셔닝과 JS 위치 계산

오버레이는 기준이 되는 요소(앵커) 옆에 놓입니다. 위치를 정하는 방법은 CSS 앵커 포지셔닝과 JS 계산 두 가지입니다.

CSS 앵커 포지셔닝은 앵커에 이름을 주고 위치 지정 요소가 그 이름을 참조해 배치하는 방식입니다. 위치 지정 요소는 `position: absolute` 또는 `fixed`여야 합니다.

```css
.btn { anchor-name: --btn; }
.tip {
  position: fixed;
  position-anchor: --btn;
  position-area: bottom;
  position-try-fallbacks: flip-block;
}
```

- `position-area`는 앵커 주변 3×3 격자 중 어디에 놓을지 정하고, `position-try-fallbacks`는 공간이 모자랄 때 시도할 대체 위치를 정합니다. `anchor()`와 `anchor-size()` 함수로 앵커 가장자리·크기를 직접 참조할 수도 있습니다.
- popover는 `popovertarget` 버튼을 암시적 앵커로 가집니다.
- 지원: Baseline이 아닙니다. `anchor-name`·`anchor()`는 Chrome·Edge 125, Firefox 147, Safari 26부터이고 `position-area`는 Chrome·Edge 129부터입니다. `position-anchor` 속성이 Chrome·Edge·Firefox 151, Safari 27에서 지원되어 기능 전체가 Baseline 조건을 채우지 못합니다(web-features 3.40.1 기준).

미지원 환경에서는 JS로 계산합니다. 앵커의 뷰포트 기준 사각형을 읽고 오버레이 크기를 더해 위치를 정합니다.

```js
function place(panel, anchor, gap = 8) {
  const a = anchor.getBoundingClientRect()
  const p = panel.getBoundingClientRect()
  let top = a.bottom + gap
  if (top + p.height > innerHeight) {
    top = a.top - gap - p.height // flip
  }
  const left = Math.min(a.left, innerWidth - p.width)
  panel.style.top = `${Math.max(0, top)}px`
  panel.style.left = `${Math.max(0, left)}px`
}
```

- 오버레이는 `position: fixed`이고, popover는 기본 스타일이 가운데 정렬이므로 `inset: auto`와 `margin: 0`으로 초기화합니다.
- 위 코드는 아래로 놓다 공간이 모자라면 위로 뒤집는(flip) 처리와 화면 밖으로 밀리지 않게 하는(shift) 처리를 담았습니다.
- 위치는 열 때 한 번 계산하고, 앵커나 오버레이 크기가 바뀌거나(`ResizeObserver`, 43편) 스크롤·리사이즈가 있을 때 다시 계산합니다. `scroll` 이벤트는 버블링하지 않으므로 `window`에 캡처 단계로 등록해야 중첩된 스크롤 영역의 스크롤을 잡을 수 있습니다(자세히는 9편, 기하는 6편).

**흔한 실수:** 오버레이를 만든 직후 크기를 읽는 것입니다. `hidden` 상태에서는 크기가 0이라서 먼저 보이게 한 뒤 측정합니다. 또 `getBoundingClientRect()`는 뷰포트 기준이라서 `position: absolute`에 그대로 쓰면 스크롤 양만큼 어긋납니다.

## interestfor 호버 트리거

`interestfor` 속성은 사용자가 요소에 관심을 보일 때(호버, 포커스, 길게 누르기) 대상 요소를 보여 주는 선언형 트리거입니다. `a`, `button`, `area`에 쓰고 값은 대상 요소의 `id`입니다. 대상은 `popover` 속성을 가진 요소여야 합니다.

```html
<a href="/docs" interestfor="tip">문서</a>
<p id="tip" popover="hint">문서 목록으로 이동합니다</p>
```

- `hint`와 짝지어 쓰면 다른 `auto` 팝오버를 닫지 않는 툴팁이 됩니다.
- 대상에는 `interest`, `loseinterest` 이벤트가 발생하고 `event.source`가 트리거를 가리킵니다.
- CSS `interest-delay-start`, `interest-delay-end`(단축형 `interest-delay`)로 나타나고 사라지기까지의 지연을 정합니다.
- 호버만 있는 방식과 달리 포커스와 길게 누르기도 관심으로 취급하므로 키보드·터치 사용자도 같은 내용에 접근합니다. 정확한 동작은 브라우저에 따라 다를 수 있습니다.
- Baseline이 아닙니다. Chrome·Edge 142에서만 지원합니다(web-features 3.40.1 기준).

지원 여부는 속성 존재로 감지합니다.

```js
const ok = Object.hasOwn(
  HTMLButtonElement.prototype, 'interestForElement',
)
```

미지원 환경에서는 `mouseenter`·`focus`로 열고 `mouseleave`·`blur`·Escape로 닫는 코드를 폴리필처럼 둡니다. 트리거에서 대상으로 포인터를 옮겨도 닫히지 않게(WCAG 1.4.13) 닫기에 짧은 지연을 둡니다.

## 배경 스크롤 잠금

오버레이가 열린 동안 뒤 페이지가 스크롤되는 문제를 막는 일입니다. 모달 `dialog`의 `showModal()`은 배경을 `inert`로 만들지만 스크롤 잠금은 별도로 처리해야 합니다. CSS 한 줄로 시작합니다.

```css
html:has(dialog:modal),
html.scroll-locked {
  overflow: hidden;
  scrollbar-gutter: stable;
}
```

- `:modal` 의사 클래스는 `showModal()`로 열린 `dialog`에 매치되며 Baseline 2022부터, `:has()`는 Baseline 2023부터 지원합니다.
- `overflow: hidden`만 걸면 스크롤바가 사라지면서 페이지가 스크롤바 너비만큼 옆으로 밀립니다. `scrollbar-gutter: stable`은 스크롤바 자리를 항상 확보해 이동을 막습니다(Baseline 2024). 오버레이 스크롤바가 쓰이는 환경에서는 자리가 생기지 않습니다.
- 스크롤 위치는 `overflow: hidden`이어도 유지됩니다. 해제하면 같은 위치에서 이어집니다.
- 오버레이 안에 스크롤 영역이 있을 때는 끝에 닿은 스크롤이 뒤 페이지로 넘어가는 스크롤 체이닝도 막아야 합니다. `overscroll-behavior: contain`을 오버레이 스크롤 영역에 지정합니다. 이 속성은 `overflow: hidden`처럼 스크롤 가능한 내용이 없는 요소도 스크롤 경계에 있다고 보아 체이닝을 막습니다. Baseline이 아닙니다(web-features 3.40.1은 Chrome·Edge 144, Firefox 150을 완전 지원으로 기록하고 Safari를 지원 목록에 올리지 않음).
- 비모달 오버레이(`popover`, 커스텀 패널)는 `:modal`이 해당하지 않으므로 직접 클래스를 붙입니다.

오버레이가 중첩되면 잠금도 여러 번 걸립니다. 먼저 닫히는 오버레이가 잠금을 풀어 버리지 않도록 횟수를 셉니다.

```js
let locks = 0
const root = document.documentElement
const lockScroll = () => {
  if (locks++ === 0) root.classList.add('scroll-locked')
}
const unlockScroll = () => {
  if (--locks === 0) root.classList.remove('scroll-locked')
}
```

**흔한 실수:** 닫는 경로 중 하나(Escape, 라우트 이동, 컴포넌트 제거)에서 해제를 빠뜨려 페이지가 스크롤되지 않는 채로 남는 것입니다. 해제는 닫기 경로마다 흩어 놓지 말고 한 곳(Overlay Manager)에서만 합니다.

## Overlay Manager 설계

Overlay Manager는 열려 있는 오버레이를 하나의 스택으로 관리하고 위의 규칙을 한 곳에서 적용하는 객체입니다. 오버레이마다 같은 코드를 복사하지 않고, 서로 충돌하는 전역 리스너(Escape, 바깥 클릭, 스크롤 잠금)를 하나로 줄입니다.

**원칙:** 네이티브가 해 주는 일은 네이티브에 맡깁니다. `dialog`·popover를 쓰면 top layer, Escape, 포커스 복귀, 모달 `inert`는 이미 해결되어 있습니다. 매니저는 네이티브가 처리하지 못하는 일(정책, 스택 동기화, 스크롤 잠금, 커스텀 오버레이)을 맡습니다.

| 책임 | 내용 |
|------|------|
| 스택 | 열린 순서 기록, 맨 위 판별, 닫으면 후손도 함께 닫음 |
| 닫기 정책 | 오버레이별로 `any`(바깥 클릭·Escape), `closerequest`(Escape만), `none`(코드로만). 네이티브 `closedby`와 같은 이름 |
| 닫기 사유 | `escape`, `outside`, `action`, `route` 등을 `close`에 전달해 호출자가 구분 |
| 포커스 | 열기 전 요소 저장, 닫을 때 복귀 |
| 스크롤 잠금 | 첫 오버레이에서 잠그고 마지막에서 해제 |
| 정리 | 요소 제거(`disconnectedCallback`)·라우트 이동 시 해당 오버레이를 닫아 리스너와 잠금 해제(18편, 67편) |

오버레이는 `el`(요소), `trigger`(여는 요소), `policy`, `show()`, `hide()`를 가진 객체로 등록합니다. 스택과 열기·닫기는 다음과 같습니다.

```js
class OverlayManager {
  #stack = []
  open(o) {
    o.returnFocus = document.activeElement
    this.#stack.push(o)
    o.show()
    if (this.#stack.length === 1) lockScroll()
  }
  // close는 아래
}
```

닫을 때는 `o`와 그 뒤(자식)를 한꺼번에 꺼내 가장 안쪽부터 닫습니다.

```js
class OverlayManager {
  close(o, reason = 'action') {
    const i = this.#stack.indexOf(o)
    if (i < 0) return
    const closing = this.#stack.splice(i).reverse()
    closing.forEach((x) => x.hide(reason))
    if (o.returnFocus?.isConnected) o.returnFocus.focus()
    if (!this.#stack.length) unlockScroll()
  }
}
```

전역 리스너는 맨 위 항목에만 적용합니다. Escape는 다음과 같습니다.

```js
#onKey = (e) => {
  const top = this.#stack.at(-1)
  if (e.key !== 'Escape' || e.isComposing || !top) return
  if (top.policy === 'none') return
  e.preventDefault() // 바깥 dialog의 닫기 요청 차단
  this.close(top, 'escape')
}
```

바깥 클릭은 `pointerup` 시점에 판별합니다.

```js
#onPointerUp = (e) => {
  const top = this.#stack.at(-1)
  if (top?.policy !== 'any') return
  const path = e.composedPath()
  const hit = (n) => top.el.contains(n) || n === top.trigger
  if (!this.#downPath.some(hit) && !path.some(hit)) {
    this.close(top, 'outside')
  }
}
```

- `#downPath`는 `pointerdown`에서 저장한 `composedPath()`입니다. 리스너는 스택이 처음 비어 있다가 채워질 때 등록하고, 비워지면 해제합니다(캡처 단계, `AbortController`의 `signal`로 일괄 해제하면 편합니다).
- 맨 위 항목만 판별 대상이므로 자식 안의 클릭은 자식 기준으로 안쪽입니다. 부모를 코드로 닫으면 `close(parent)`가 자식까지 모두 닫습니다.
- 네이티브 `dialog`·popover를 등록하는 오버레이는 사용자가 매니저를 거치지 않고도 닫을 수 있습니다(`auto` popover의 light dismiss 등). 따라서 `close`·`toggle` 이벤트를 구독해 스택에서 제거하고 스크롤 잠금을 맞춥니다.

```js
dialogEl.addEventListener('close', () => {
  manager.close(entry, 'native')
})
```

- 같은 오버레이를 이중으로 닫아도 안전해야 합니다. 위 `close`는 스택에 없으면 즉시 반환합니다.

**설계 판단 기준:**

- 오버레이가 하나뿐이고 모달이라면 매니저 없이 `dialog`로 충분합니다.
- 서로 다른 종류(모달, 메뉴, 토스트)가 겹치거나 커스텀 오버레이가 있을 때 매니저가 필요합니다.
- 전역 상태이므로 애플리케이션에서 인스턴스를 하나만 두고 컴포넌트가 주입받습니다(자세히는 82편). 오버레이 컴포넌트의 구조 설계는 79편에서 다룹니다.

## 핵심 정리

- 포커스는 열 때 오버레이 안으로, 닫을 때 열기 전 요소로 옮기고, 모달의 배경은 `inert`나 `showModal()`로 막습니다.
- Escape는 `keydown`에서 입력기 조합 중이 아닐 때 맨 위 오버레이 하나만 닫으며, 이벤트를 취소하면 브라우저의 닫기 요청 처리도 멈춥니다.
- 바깥 클릭은 `pointerdown`과 `pointerup`이 모두 바깥일 때만 닫고, 안쪽 판별에는 `composedPath()`와 여는 버튼을 포함합니다.
- popover는 `auto`·`hint`·`manual`에 따라 light dismiss와 스택 규칙이 다르며, 조상 관계가 있어야 자식 클릭이 부모를 닫지 않습니다.
- CloseWatcher(미Baseline), 앵커 포지셔닝(미Baseline), `interestfor`(Chrome·Edge 전용)는 점진적 향상으로 쓰고 대체 구현을 둡니다.
- Overlay Manager는 스택·닫기 정책·포커스·스크롤 잠금 횟수를 한 곳에서 관리하고 네이티브가 하는 일은 네이티브에 맡깁니다.

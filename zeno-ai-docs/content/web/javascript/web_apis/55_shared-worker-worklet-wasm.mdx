## Shared Worker

Shared Worker는 같은 origin의 여러 창·탭·iframe·워커가 하나의 인스턴스를 함께 쓰는 워커입니다. 전용 워커(54편)는 만든 스크립트 하나만 접근하지만, Shared Worker는 탭마다 연결이 생기고 코드와 상태는 하나만 존재합니다. 예를 들어 서버 연결 하나를 모든 탭이 공유할 때 씁니다.

지원 상태는 Baseline 2026입니다. 2026년 5월에 핵심 브라우저 전체에서 쓸 수 있게 되었고, web-features 3.40.1 기준으로 Chrome Android는 148부터 지원합니다. 새 코드에서도 지원 범위를 확인하고 씁니다.

```js
// 각 탭에서
const sw = new SharedWorker('shared.js', { name: 'app' })
sw.port.onmessage = (e) => console.log(e.data)
sw.port.postMessage('hello')
```

- `new SharedWorker(url, options)`의 옵션은 `name`, `type`(`classic` 또는 `module`), `credentials`, `extendedLifetime`입니다. 이름만 문자열로 주는 `new SharedWorker(url, name)` 형태도 됩니다.
- URL과 `name`이 같으면 이미 실행 중인 인스턴스에 연결합니다. 이름을 다르게 주면 같은 스크립트로 별도 인스턴스가 만들어집니다.
- 한 번 실행 중인 인스턴스의 `type`, `credentials`, `extendedLifetime`은 고정됩니다. 다른 값으로 같은 URL·이름을 요청하면 오류가 나므로, 다른 옵션이 필요하면 이름을 바꿉니다.
- 같은 origin이어야 합니다(`blob:`·`data:` URL 예외).
- 통신은 `port`(`MessagePort`)로만 합니다. `addEventListener('message')`로 받을 때는 `port.start()`를 호출해야 하고, `onmessage`에 대입하면 자동으로 시작됩니다.

워커 쪽은 `SharedWorkerGlobalScope`입니다. 전용 워커와 달리 전역에 `message` 이벤트가 없고, 새 탭이 연결될 때마다 `connect` 이벤트가 발생해 그 탭 전용 포트를 `e.ports[0]`로 줍니다.

```js
// shared.js
const ports = new Set()
self.onconnect = (e) => {
  const port = e.ports[0]
  ports.add(port)
  port.onmessage = (m) => {
    for (const p of ports) p.postMessage(m.data) // 모든 탭에 전달
  }
}
```

- `self.close()`는 대기 중인 태스크를 버리고 워커를 닫습니다.
- `error` 이벤트는 `SharedWorker` 객체에서 받습니다.
- `extendedLifetime: true`는 모든 연결이 끊긴 뒤에도 워커를 잠시(브라우저에 따라 10초에서 300초) 살려 정리 작업(상태 저장, 분석 전송)을 허용합니다. web-features 기준으로 Chrome·Edge 148만 지원하며 Baseline이 아닙니다.
- 디버깅은 Chrome의 `chrome://inspect/#workers`, Firefox의 `about:debugging#workers`에서 합니다.

**흔한 실수:** `port.addEventListener('message', ...)`만 쓰고 `port.start()`를 빼먹는 것입니다. 메시지가 영원히 도착하지 않습니다.

## SharedArrayBuffer와 Atomics

`SharedArrayBuffer`(SAB)는 여러 스레드(메인과 워커)가 같은 메모리를 직접 읽고 쓰는 버퍼입니다. `ArrayBuffer`는 전송하면 원본이 분리되지만, SAB는 `postMessage`로 보내면 양쪽이 같은 메모리를 가리킵니다. 전송 가능한 객체가 아닙니다.

```js
const sab = new SharedArrayBuffer(1024)
const view = new Int32Array(sab)
worker.postMessage(sab) // 복사가 아니라 공유
view[0] = 42            // 워커에서도 보임(동기화 필요)
```

### 사용 조건

SAB는 Spectre 취약점 때문에 2018년에 브라우저에서 꺼졌다가 2020년에 더 엄격한 조건과 함께 다시 켜졌습니다. 쓰려면 둘을 만족해야 합니다.

| 조건 | 내용 |
|------|------|
| 보안 컨텍스트 | HTTPS(자세히는 62편) |
| cross-origin isolation | `window.crossOriginIsolated`가 `true` |

문서가 cross-origin isolated 상태가 되려면 응답에 `Cross-Origin-Opener-Policy: same-origin`과 `Cross-Origin-Embedder-Policy: require-corp`(또는 `credentialless`) 헤더가 필요하고, `Permissions-Policy`가 이 기능을 막지 않아야 합니다. 같은 상태에서 `performance.now()`의 정밀도와 `performance.measureUserAgentSpecificMemory()`도 풀립니다(헤더 해설은 62편).

```js
if (crossOriginIsolated) {
  worker.postMessage(new SharedArrayBuffer(16))
} else {
  worker.postMessage(new ArrayBuffer(16)) // 공유 불가
}
```

- 격리 헤더가 있으면 다른 origin의 리소스를 불러올 때 CORS 또는 CORP 동의가 필요해서 외부 임베드가 깨질 수 있습니다.
- `maxByteLength`를 주면 늘릴 수 있는 SAB가 됩니다. `grow()`는 늘리기만 되고 줄이지 못합니다.

### Atomics

여러 스레드가 같은 메모리를 동시에 쓰면 일반 연산은 중간 상태가 섞입니다(`ta[0] += 1`은 읽고 쓰는 두 단계). `Atomics`는 나눠지지 않는 연산을 제공하는 네임스페이스 객체입니다.

| 분류 | 메서드 |
|------|--------|
| 읽기·쓰기 | `load`, `store`, `exchange` |
| 연산 | `add`, `sub`, `and`, `or`, `xor` (이전 값을 반환) |
| 비교 교환 | `compareExchange` |
| 대기·깨우기 | `wait`, `waitAsync`, `notify` |
| 기타 | `isLockFree`, `pause` |

대기·깨우기가 스레드 동기화의 핵심입니다. `Atomics.wait(int32, index, expected, timeout)`은 그 칸의 값이 `expected`와 같으면 알림이 올 때까지 스레드를 잠재웁니다. 반환값은 `'ok'`(깨워짐), `'not-equal'`(값이 이미 다름), `'timed-out'`입니다. `Atomics.notify(int32, index, count)`는 대기 중인 스레드를 깨우고 깨운 수를 돌려줍니다.

```js
// worker.js: 신호를 기다린다
const int32 = new Int32Array(sab)
Atomics.wait(int32, 0, 0) // 값이 0인 동안 잠듦
console.log(int32[0])     // 123

// main.js: 값을 쓰고 깨운다
Atomics.store(int32, 0, 123)
Atomics.notify(int32, 0, 1)
```

- `Atomics.wait()`은 스레드를 막으므로 메인 스레드에서 쓸 수 없고 워커에서만 씁니다. 메인 스레드에서 기다리려면 Promise를 돌려주는 `Atomics.waitAsync()`를 씁니다. `waitAsync`는 Baseline 2025입니다(Chrome 90, Firefox 145, Safari 16.4).
- 대기·알림 대상은 정수 타입 배열(`Int32Array` 등)의 칸입니다.
- 같은 칸을 여러 스레드가 쓰는 코드는 모두 `Atomics`로 접근해야 합니다. 일부만 일반 대입을 쓰면 경쟁이 남습니다.
- 조건을 만족하지 못하면 `postMessage`와 전송으로 충분한 작업이 대부분입니다. SAB는 메시지 왕복 지연을 피해야 하는 큰 계산(WebAssembly 스레드, 병렬 처리)에 씁니다.

**흔한 실수:** 격리 헤더 없이 `new SharedArrayBuffer`를 호출하는 것입니다. 격리되지 않은 문서에서는 SAB를 쓸 수 없으므로, 헤더를 설정하지 않은 환경에서 코드가 실패합니다. 사용 전에 `crossOriginIsolated`를 검사하고 `ArrayBuffer` 전송으로 물러서는 경로를 둡니다.

## Worklet의 개념과 종류

Worklet은 렌더링 파이프라인의 낮은 단계에 끼어들어 JavaScript나 WebAssembly 코드를 실행하는 가벼운 워커입니다. 브라우저가 렌더링 파이프라인의 해당 단계에서 직접 호출합니다.

- 보안 컨텍스트(HTTPS)에서만 동작합니다.
- DOM에 접근할 수 없고 자신만의 전역 스코프에서 실행됩니다.
- `worklet.addModule(url)`이 Promise를 돌려주며 스크립트를 모듈로 불러옵니다. 정적 `import`는 되지만 동적 `import()`는 오류입니다.
- 진입점은 용도마다 정해져 있습니다(`audioContext.audioWorklet`, `CSS.paintWorklet`).

| 종류 | 용도 | 실행 위치 | 지원 상태 |
|------|------|-----------|-----------|
| AudioWorklet | 오디오 노드를 직접 처리 | Web Audio 렌더 스레드 | Baseline 2021 |
| PaintWorklet | `paint()`로 배경·테두리를 그림 | 렌더링 파이프라인 | 미Baseline. Chrome·Edge만 지원 |
| LayoutWorklet | 요소의 배치 알고리즘을 직접 작성 | 메인 스레드 | 실험적. Chrome Canary에서 부분 지원 |

지원 상태는 web-features 3.40.1과 MDN으로 확인했습니다. AudioWorklet만 모든 핵심 브라우저가 지원하고, 나머지는 점진적 향상 대상입니다(자세히는 71편).

AudioWorklet은 `AudioWorkletProcessor`를 상속해 `process()`에서 오디오 블록(128프레임)을 직접 처리합니다. `process()`가 `true`를 반환하면 프로세서가 유지되고, 메인 스레드와는 `port`로 메시지를 주고받습니다.

```js
// processor.js (worklet 안)
class Gain extends AudioWorkletProcessor {
  process(inputs, outputs) {
    const [inp] = inputs, [out] = outputs
    for (let c = 0; c < out.length; c++) {
      for (let i = 0; i < out[c].length; i++) {
        out[c][i] = (inp[c]?.[i] ?? 0) * 0.5
      }
    }
    return true // 계속 유지
  }
}
registerProcessor('gain', Gain)
```

```js
// main.js
await ctx.audioWorklet.addModule('processor.js')
const node = new AudioWorkletNode(ctx, 'gain')
source.connect(node).connect(ctx.destination)
```

PaintWorklet은 `registerPaint()`로 그리기 클래스를 등록하고 CSS에서 `paint()` 함수로 씁니다. 읽을 CSS 변수는 `inputProperties`로 선언합니다.

```js
// main.js
CSS.paintWorklet.addModule('boxbg.js')
// boxbg.js
registerPaint('boxbg', class {
  static get inputProperties() { return ['--box-color'] }
  paint(ctx, size, props) {
    ctx.fillStyle = props.get('--box-color')
    ctx.fillRect(0, 0, size.width * 0.4, size.height)
  }
})
/* CSS: li { background-image: paint(boxbg); } */
```

**흔한 실수:** Worklet 안에서 `fetch`나 DOM, 타이머를 쓰려는 것입니다. Worklet은 제한된 전역이라 일반 워커의 API를 기대하면 안 됩니다. 무거운 준비 작업은 워커나 메인 스레드에서 하고 결과만 `port`로 넘깁니다.

## WebAssembly JS API 개요

WebAssembly(Wasm)는 C·C++·Rust 같은 언어를 컴파일한 이진 코드를 브라우저에서 빠르게 실행하는 형식입니다. 코어는 Baseline 2017입니다. JavaScript는 `WebAssembly` 네임스페이스로 이진 모듈을 불러오고 실행합니다.

| 객체 | 역할 |
|------|------|
| `WebAssembly.Module` | 컴파일된 상태 없는 코드. 여러 번 인스턴스화하고 워커에 보낼 수 있음 |
| `WebAssembly.Instance` | `Module`의 실행 인스턴스. `exports`로 함수를 노출 |
| `WebAssembly.Memory` | Wasm이 읽고 쓰는 선형 메모리. `buffer`가 `ArrayBuffer` |
| `WebAssembly.Table` | 함수 참조 같은 참조의 배열 |
| `WebAssembly.Global` | JS와 Wasm이 함께 쓰는 전역 변수 |
| `WebAssembly.Tag` | Wasm 예외의 종류 |

정적 함수는 `compile`, `compileStreaming`, `instantiate`, `instantiateStreaming`, `validate`입니다. 오류는 `CompileError`(디코딩·검증 실패), `LinkError`(인스턴스화 실패), `RuntimeError`(트랩)입니다.

### instantiateStreaming()

`WebAssembly.instantiateStreaming(response, importObject)`는 네트워크에서 내려받는 동안 컴파일해 `{ module, instance }`를 Promise로 돌려주는 가장 효율적인 로딩 방법입니다. Baseline 2021입니다.

```js
const imports = { env: { log: (n) => console.log(n) } }
const { instance } = await WebAssembly.instantiateStreaming(
  fetch('calc.wasm'),
  imports,
)
instance.exports.add(1, 2) // 3
```

- `.wasm`은 `application/wasm` MIME 타입으로 서빙되어야 합니다. 아니면 스트리밍이 실패하므로 `fetch(...).then((r) => r.arrayBuffer())` 뒤 `WebAssembly.instantiate(bytes, imports)`로 물러섭니다.
- `importObject`는 모듈이 import로 선언한 함수·메모리·테이블·전역을 JS에서 채워 주는 객체입니다. 모듈이 요구하는 것이 빠지면 `LinkError`입니다.
- 엄격한 CSP는 Wasm 컴파일을 막을 수 있습니다(자세히는 63편).
- 모듈이 요구하는 import·export는 `WebAssembly.Module.imports(module)`·`exports(module)`로 확인할 수 있습니다.

### Memory

`new WebAssembly.Memory({ initial, maximum })`는 선형 메모리를 만듭니다. 단위는 페이지이고 한 페이지는 64KiB입니다. `buffer`로 `ArrayBuffer`를 얻어 `DataView`나 타입 배열로 읽고 씁니다. Wasm 메모리는 항상 리틀 엔디언입니다.

```js
const mem = new WebAssembly.Memory({
  initial: 10,
  maximum: 100,
})
const view = new DataView(mem.buffer)
view.setUint32(0, 42, true) // true: 리틀 엔디언
mem.grow(1) // 한 페이지 늘림. 이전 buffer는 분리됨
const view2 = new DataView(mem.buffer) // 새로 얻어야 함
```

- `grow(delta)`는 이전 `buffer`를 분리(detach)합니다. 성장 뒤에는 `mem.buffer`를 다시 읽어야 합니다. 이전 `buffer`를 캐시한 코드가 가장 흔한 버그입니다.
- `shared: true`이면 `buffer`가 `SharedArrayBuffer`가 되어 여러 워커가 같은 Wasm 메모리를 씁니다. 이 경우에도 cross-origin isolation이 필요합니다.
- 숫자 타입은 `i32`, `f32`, `f64`이고 `i64`는 JavaScript에서 `BigInt`입니다. 문자열 같은 복합 값은 메모리에 쓰고 위치와 길이를 넘겨 전달합니다.

## 워커와 WebAssembly 결합 패턴

Wasm 계산은 메인 스레드에서 실행하면 일반 JavaScript처럼 UI를 막습니다. 무거운 Wasm은 워커에서 돌리는 것이 기본입니다.

| 패턴 | 구성 | 쓰는 경우 |
|------|------|-----------|
| 워커가 직접 로드 | 워커 안에서 `instantiateStreaming`. 메인은 메시지만 주고받음 | 가장 단순. 계산 하나를 격리 |
| Module 전달 | 메인에서 `compileStreaming`으로 `Module`을 만들어 `postMessage`. 워커가 `instantiate` | 여러 워커가 같은 모듈을 쓰되 컴파일은 한 번만 |
| 공유 메모리 | `Memory({ shared: true })`와 `Module`을 워커 여러 개에 전달 | Wasm 스레드. 같은 선형 메모리를 병렬로 처리 |

```js
// main.js: 컴파일은 한 번, 워커에는 Module을 보냄
const res = fetch('calc.wasm')
const mod = await WebAssembly.compileStreaming(res)
const mem = new WebAssembly.Memory({
  initial: 10, maximum: 100, shared: true,
})
for (const w of workers) w.postMessage({ mod, mem })
```

```js
// worker.js
self.onmessage = async ({ data: { mod, mem } }) => {
  const imports = { js: { mem } }
  const inst = await WebAssembly.instantiate(mod, imports)
  inst.exports.run()
}
```

- `Module`은 구조화된 복제로 전달됩니다. 상태가 없는 코드라서 복사 비용 없이 공유됩니다.
- 공유 메모리 패턴은 SAB와 같은 조건이 필요하고 동기화는 Wasm의 원자적 명령이나 `Atomics`로 합니다. Wasm 스레드는 Baseline 2021입니다.
- 큰 입력은 전송 가능한 `ArrayBuffer`로 보내 워커에서 Wasm 메모리에 복사합니다. 결과도 같은 방식으로 돌려줍니다(전송은 54편).
- 워커 풀(54편)과 합치면 `Module` 하나를 컴파일해 풀의 모든 워커가 인스턴스화합니다.

## Shared Worker와 BroadcastChannel·Web Locks의 역할 비교

탭 사이를 조정하는 수단은 셋입니다. 풀려는 문제가 다릅니다.

| 항목 | Shared Worker | BroadcastChannel | Web Locks |
|------|---------------|------------------|-----------|
| 하는 일 | 코드와 상태, 연결을 하나로 두고 탭이 요청 | 같은 이름의 채널에 메시지를 뿌림 | 이름 붙은 자원에 대한 상호 배제 |
| 상태·실행 | 있음. 독립된 실행 컨텍스트 | 없음. 전달만 함 | 없음. 락 보유 중에 콜백이 실행 |
| 통신 | 탭마다 `MessagePort` 1:1 | 1:N 전체 전달. 보낸 곳은 제외 | 메시지 없음. 순서만 조정 |
| 같은 origin 필요 | 예 | 예 | 예 |
| 워커에서 사용 | 예(워커도 연결 가능) | 예 | 예 |
| 지원 | Baseline 2026 | Baseline 2022 | Baseline 2022 |

- BroadcastChannel은 같은 origin의 창, iframe, 워커에 메시지를 전달하는 가장 가벼운 수단입니다(자세히는 59편). 메시지는 저장되지 않아서 이후에 열린 탭은 이전 메시지를 받지 못합니다.
- Web Locks는 `navigator.locks.request(name, callback)`으로 락을 얻고, 콜백이 반환한 Promise가 끝나면 락이 풀립니다. 모드는 `exclusive`(기본)와 `shared`, 옵션은 `ifAvailable`, `steal`, `signal`입니다. 락 상태는 `navigator.locks.query()`로 봅니다.
- 선택 기준은 이렇습니다. 상태나 연결을 소유한 중앙 객체가 필요하면 Shared Worker, 이벤트를 알리기만 하면 BroadcastChannel, 한 번에 한 탭만 해야 하는 일이면 Web Locks입니다.
- 조합도 흔합니다. Web Locks로 리더 탭 하나를 뽑고, 리더가 작업한 결과를 BroadcastChannel로 나머지 탭에 알립니다.

```js
const bc = new BroadcastChannel('sync')
bc.onmessage = (e) => render(e.data) // 다른 탭의 결과
navigator.locks.request('leader', async () => {
  // 락을 가진 탭 하나만 실행
  const data = await syncWithServer()
  bc.postMessage(data)
  await new Promise(() => {}) // 락을 계속 유지
})
```

**흔한 실수:** BroadcastChannel을 상태 저장소로 쓰는 것입니다. 보낸 탭 자신은 메시지를 받지 못하고, 늦게 연결한 탭은 이전 값을 알 수 없습니다. 현재 상태가 필요하면 Shared Worker나 저장소(IndexedDB 등)에 두고 BroadcastChannel은 변경 알림에만 씁니다.

## 핵심 정리

- Shared Worker는 같은 origin의 여러 탭이 하나의 워커를 공유하며, 탭마다 `connect` 이벤트로 받은 `MessagePort`로 통신하고 Baseline 2026입니다.
- `SharedArrayBuffer`는 복사나 전송 없이 메모리를 공유하며, HTTPS와 `crossOriginIsolated`(COOP·COEP 헤더)가 필요합니다.
- 공유 메모리는 `Atomics`로 접근해야 안전하고, `Atomics.wait()`는 워커에서만, 메인 스레드에서는 `waitAsync()`를 씁니다.
- Worklet은 렌더링 파이프라인용 제한된 워커로, AudioWorklet만 Baseline이고 PaintWorklet은 Chrome·Edge, LayoutWorklet은 실험 단계입니다.
- WebAssembly는 `instantiateStreaming`으로 로딩하고, `Memory`는 64KiB 페이지 단위이며 `grow()`가 이전 `buffer`를 분리하고, 무거운 Wasm은 워커에서 `Module`을 공유해 실행합니다.
- 탭 조정은 상태 소유는 Shared Worker, 알림은 BroadcastChannel, 상호 배제는 Web Locks로 나눠 씁니다.

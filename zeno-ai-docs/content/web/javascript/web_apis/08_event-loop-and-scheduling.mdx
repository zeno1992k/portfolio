## Call Stack

호출 스택(call stack)은 현재 실행 중인 함수들을 쌓아 두는 후입선출(LIFO) 구조입니다. 함수를 호출하면 프레임이 쌓이고, 반환하면 꺼내집니다. 스택이 비어야 다음 작업이 시작됩니다.

```js
function a() { b() }
function b() { console.log('b') }
a()
// 스택: [전역] → [a] → [b] → [a] → [전역]
```

- 메인 스레드는 하나이고 스택도 하나입니다. 한 작업은 끝까지 실행된 뒤에야 다른 작업이 실행됩니다(run-to-completion). 중간에 끼어들 수 없습니다.
- 스택이 오래 차 있으면 그동안 입력 처리와 화면 갱신이 모두 멈춥니다(아래 "Long Task와 UI 블로킹").
- 스택 깊이에는 상한이 있고, 넘으면 RangeError입니다. 상한은 엔진마다 다릅니다.
- 언어 쪽 규칙(실행 컨텍스트, Promise 잡)은 ECMAScript 과목에서 다룹니다. 이 편은 브라우저가 그 위에 얹은 이벤트 루프를 다룹니다.

## Task Queue

이벤트 루프(event loop)는 스택이 빌 때마다 다음에 실행할 작업을 골라 오는 반복문입니다. 그 작업 중 하나가 태스크(task)입니다. HTML 표준이 정한 처리 모델은 다음 순서를 반복합니다.

1. 실행할 수 있는 태스크가 있는 태스크 큐 하나를 고릅니다. 어느 큐를 고를지는 브라우저가 정합니다.
2. 그 큐의 가장 오래된 태스크 하나를 꺼내 실행합니다.
3. 마이크로태스크 체크포인트를 수행합니다(다음 절).
4. 렌더링 기회가 있으면 렌더링을 업데이트합니다(아래 "렌더링 타이밍").

태스크 큐는 하나가 아니라 태스크 소스별로 여럿입니다. 같은 소스의 태스크는 먼저 들어온 순서대로 실행되지만, 소스가 다르면 순서가 보장되지 않습니다. 브라우저는 사용자 입력 큐를 타이머 큐보다 먼저 고를 수 있습니다.

| 태스크 소스 | 쓰이는 곳 |
|-------------|-----------|
| 사용자 상호작용 | 클릭·키 입력 등 사용자 입력에 대한 이벤트 |
| DOM 조작 | 요소가 문서에 삽입될 때의 비동기 처리 등 |
| 네트워킹 | 네트워크 활동에 대한 반응 |
| 내비게이션과 히스토리 이동 | 페이지 이동, 히스토리 탐색 |
| 렌더링 | 렌더링 업데이트만을 위한 소스 |

타이머, 포트 메시지(`MessagePort`) 같은 다른 기능도 각자의 태스크 소스를 가집니다.

```js
console.log('A')
setTimeout(() => console.log('C'), 0) // 새 태스크
console.log('B')
// A B C
```

- 이벤트 리스너 호출, `setTimeout` 콜백, 스크립트 최초 실행은 각각 하나의 태스크입니다.
- `dispatchEvent`로 직접 보낸 이벤트는 새 태스크가 아니라 현재 코드 안에서 동기적으로 실행됩니다(자세히는 07편).

**흔한 실수:** 태스크 큐를 하나의 FIFO 큐로 생각하는 것입니다. 소스 안에서는 순서가 있지만 소스끼리는 브라우저가 고릅니다.

## Microtask Queue

마이크로태스크 큐(microtask queue)는 현재 태스크가 끝난 직후, 다음 태스크가 시작되기 전에 실행되는 작업들을 담는 큐입니다. 태스크 큐와 별개이며 마이크로태스크는 태스크가 아닙니다.

마이크로태스크 체크포인트는 JavaScript 스택이 비었을 때 수행되고, 큐에 쌓인 마이크로태스크를 모두 실행합니다. 실행 중에 새로 추가된 마이크로태스크도 같은 체크포인트 안에서 이어서 실행합니다.

```js
setTimeout(() => console.log('task'), 0)
Promise.resolve().then(() => console.log('micro'))
console.log('sync')
// sync micro task
```

- 순서는 동기 코드, 마이크로태스크 전부, 다음 태스크입니다.
- 체크포인트는 태스크 사이뿐 아니라 콜백 실행이 끝나 스택이 빌 때마다 수행됩니다. 클릭 리스너가 여러 개면 리스너 하나가 끝날 때마다 마이크로태스크가 실행됩니다.
- 마이크로태스크가 자기 자신을 계속 다시 예약하면 큐가 비지 않아서 다음 태스크, 렌더링, 입력 처리가 영원히 시작되지 못합니다.

```js
function loop() { queueMicrotask(loop) } // ❌ 페이지가 멈춤
loop()
```

## Promise와 Microtask

Promise의 `then`·`catch`·`finally` 콜백과 `await` 이후의 코드는 마이크로태스크로 실행됩니다. Promise가 이미 이행된 상태여도 콜백은 현재 코드가 끝난 뒤에 실행됩니다.

```js
console.log(1)
Promise.resolve().then(() => console.log(2))
console.log(3)
// 1 3 2
```

```js
async function f() {
  console.log('a')
  await null          // 여기서 함수가 멈추고 스택을 비움
  console.log('c')    // 마이크로태스크로 재개
}
f()
console.log('b')
// a b c
```

- `async` 함수는 첫 `await`까지 동기로 실행됩니다.
- `fetch`가 돌려준 Promise는 네트워크 태스크에서 이행되고, 그 뒤의 `then` 콜백이 마이크로태스크로 실행됩니다.
- 마이크로태스크 큐가 태스크보다 먼저 비워지므로 `Promise.resolve().then(f)`는 `setTimeout(f, 0)`보다 항상 먼저 실행됩니다.
- Promise 자체는 ECMAScript 과목에서 다룹니다.

## queueMicrotask

`queueMicrotask(callback)`은 콜백을 마이크로태스크 큐에 넣습니다. 반환값은 `undefined`입니다. Baseline 널리 지원(2020년 7월부터 모든 핵심 브라우저)입니다.

```js
queueMicrotask(() => console.log('micro'))
console.log('sync')
// sync micro
```

- Promise를 만들지 않고 마이크로태스크를 쓸 때 씁니다. 같은 태스크 안의 여러 호출을 모아서 한 번에 처리하는 일괄 처리(batching)가 대표적입니다.
- 콜백이 예외를 던지면 예외로 보고됩니다.
- 동기로 끝날 수도 있고 비동기로 끝날 수도 있는 함수에서 쓰면 결과가 항상 비동기가 되어 호출 순서가 일정해집니다.

```js
let queued = false
function schedule(flush) {
  if (queued) return
  queued = true
  queueMicrotask(() => { queued = false; flush() })
}
// 같은 태스크에서 schedule을 여러 번 불러도 flush는 한 번
```

## setTimeout / setInterval

`setTimeout(fn, ms)`은 최소 `ms`밀리초 뒤에 콜백을 실행하는 태스크를 예약하고, `setInterval(fn, ms)`은 그 일을 반복합니다. 반환값은 양의 정수 ID이고 `clearTimeout`·`clearInterval`에 넘겨 취소합니다. Baseline 널리 지원(2015년부터)입니다.

```js
const id = setTimeout(() => console.log('late'), 1000)
clearTimeout(id) // 취소
setTimeout(console.log, 0, 'x') // 세 번째 인수부터 콜백 인수
```

- `ms`는 정확한 실행 시각이 아니라 "이 시간 이후 가능한 때"입니다. 스택이 차 있거나 앞선 태스크가 길면 더 늦게 실행됩니다.
- 지연 0도 즉시 실행이 아니라 다음 태스크입니다.
- 지연값은 부호 있는 32비트 정수로 변환되어서 최대 2,147,483,647ms(약 24.8일)입니다. 그보다 크면 오버플로가 일어납니다.
- 메서드를 그대로 넘기면 `this`를 잃습니다. 화살표 함수로 감싸거나 `bind`를 씁니다.
- 반복 간격을 정확히 지키지 못합니다. 콜백이 끝난 뒤 다음 실행을 직접 예약하려면 `setTimeout`을 재귀로 씁니다.

### 중첩 최소 지연

HTML 표준은 타이머 중첩 수준(nesting level)이 5를 넘고 지연이 4ms 미만이면 4ms로 올리라고 정합니다. 타이머 콜백 안에서 다시 타이머를 예약하면 수준이 1씩 올라갑니다. `setTimeout`과 `setInterval`이 같은 카운터를 씁니다. 그래서 `setTimeout(f, 0)`을 연쇄로 호출하면 처음에는 거의 즉시 실행되다가 몇 번 뒤부터 4ms 간격이 됩니다.

### 백그라운드 탭 스로틀링

보이지 않는 탭에서는 브라우저가 타이머를 늦춥니다. 최소 간격은 브라우저마다 다릅니다.

- Firefox 데스크톱: 비활성 탭은 최소 1초입니다.
- Chrome: 가시성과 활동에 따라 단계적으로 늦춥니다. 중첩 수준이 5 이상이고 5분 넘게 보이지 않으며 30초 넘게 무음이고 WebRTC를 쓰지 않는 페이지는 분당 한 번 수준(Chrome 88부터)으로 늦춥니다.

타이머로 경과 시간을 세면 백그라운드에서 어긋납니다. 시간은 `Date.now()`나 `performance.now()` 차이로 계산합니다.

## requestAnimationFrame

`requestAnimationFrame(callback)`(rAF)은 다음 렌더링 직전에 콜백을 실행합니다. 반환값은 ID이고 `cancelAnimationFrame(id)`로 취소합니다. Baseline 널리 지원(2015년부터)입니다.

```js
function step(now) {
  box.style.transform = `translateX(${now / 10}px)`
  requestAnimationFrame(step) // 한 번만 실행되므로 다시 예약
}
requestAnimationFrame(step)
```

- 콜백은 한 번만 호출됩니다. 애니메이션을 이어 가려면 콜백 안에서 다시 예약합니다.
- 인수 `now`는 `DOMHighResTimeStamp`(밀리초)입니다. 같은 프레임에서 실행되는 모든 rAF 콜백이 같은 값을 받습니다.
- 호출 빈도는 화면 주사율을 따릅니다. 60Hz면 약 16.7ms마다이고 120Hz나 144Hz 화면도 있습니다. 프레임 수로 속도를 정하면 고주사율 화면에서 더 빨라지므로 `now`의 차이로 진행도를 계산합니다.
- 백그라운드 탭과 숨겨진 iframe에서는 대부분의 브라우저가 rAF를 멈춥니다.
- DOM 변경을 rAF 안에 모으면 프레임당 한 번의 스타일·레이아웃 계산으로 처리됩니다(자세히는 02편).

**흔한 실수:** 프레임마다 일정한 픽셀씩 움직이는 코드입니다. 주사율에 따라 속도가 달라집니다.

## requestIdleCallback

`requestIdleCallback(callback, options)`은 브라우저가 한가한 때 콜백을 실행하는 API입니다. 반환값은 ID이고 `cancelIdleCallback(id)`로 취소합니다. 콜백은 `IdleDeadline` 객체를 받습니다.

```js
function run(deadline) {
  while (deadline.timeRemaining() > 0 && jobs.length) {
    jobs.shift()()
  }
  if (jobs.length) requestIdleCallback(run) // 남으면 재예약
}
requestIdleCallback(run, { timeout: 2000 })
```

- `deadline.timeRemaining()`은 이번 유휴 구간에 남은 밀리초입니다. 표준은 유휴 구간의 상한을 50ms로 둡니다. 입력에 반응해야 하는 시간을 확보하기 위해서입니다.
- `deadline.didTimeout`은 `timeout` 옵션 시간이 지나 강제로 실행되었는지를 알려 줍니다.
- `timeout`이 없으면 바쁜 페이지에서는 콜백이 오래 실행되지 않을 수 있습니다. 반드시 실행해야 하는 작업이면 `timeout`을 줍니다.
- 유휴 구간에서의 DOM 변경은 레이아웃을 다시 계산하게 해서 끊김을 만들 수 있으므로 피합니다. 분석 전송, 캐시 준비 같은 낮은 우선순위 작업에 맞습니다.
- 지원 상태: Baseline이 아닙니다. Chrome 47, Firefox 55부터 지원하고 Safari는 지원하지 않습니다. 쓰려면 기능 검사 후 `setTimeout`으로 대체합니다.

```js
const idle = window.requestIdleCallback
  ?? ((fn) => setTimeout(() => fn({
    timeRemaining: () => 0,
  }), 1))
```

## 렌더링 타이밍

브라우저는 매 이벤트 루프 반복마다 렌더링하지 않습니다. 렌더링 기회가 있을 때만 "렌더링 업데이트" 단계를 수행합니다. 기회는 화면 주사율에 맞춰 규칙적으로 오고, 보이지 않는 페이지나 그릴 것이 없는 문서는 건너뜁니다. 표준은 60Hz에서 약 16.7ms 간격을 예로 들고, 유지하지 못하면 초당 30회로 낮추거나 보이지 않는 페이지는 훨씬 낮출 수 있다고 적습니다.

렌더링 업데이트 단계의 순서는 다음과 같습니다(표준의 단계 중 이 편과 관련된 것).

| 순서 | 단계 |
|------|------|
| 1 | resize 이벤트 실행 |
| 2 | scroll 이벤트 실행 |
| 3 | 미디어 쿼리 평가와 변경 보고 |
| 4 | 애니메이션 갱신과 이벤트 전송 |
| 5 | 전체 화면 단계 |
| 6 | `requestAnimationFrame` 콜백 실행 |
| 7 | 스타일 재계산과 레이아웃, `ResizeObserver` 콜백(변화가 없을 때까지 반복) |
| 8 | `IntersectionObserver` 관찰 갱신 |
| 9 | 화면에 그리기 |

- 순서가 중요한 이유: rAF 안에서 바꾼 스타일은 바로 뒤의 스타일·레이아웃 단계에 반영되어 같은 프레임에 그려집니다.
- 렌더링 업데이트는 태스크 하나로 실행됩니다. 앞선 태스크가 길어서 16.7ms를 넘기면 프레임을 놓칩니다(프레임 예산, 자세히는 02편).
- 마이크로태스크는 렌더링 업데이트보다 먼저 비워지므로 그 안의 DOM 변경은 같은 프레임에 반영됩니다.

```js
box.style.opacity = '0'
Promise.resolve().then(() => { box.style.opacity = '1' })
// 마이크로태스크에서 되돌렸으므로 화면에는 0이 그려지지 않음
```

## Long Task와 UI 블로킹

롱 태스크(long task)는 메인 스레드를 50ms 이상 연속으로 점유한 작업입니다. 그동안 입력 처리, 애니메이션, 스크롤이 지연되어 입력 지연과 끊김이 생깁니다. 표준의 이벤트 루프 처리 모델은 태스크가 끝날 때마다 롱 태스크를 보고하는 단계를 둡니다.

`PerformanceObserver`로 관찰합니다(자세히는 65편).

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.log(e.duration)
}).observe({ type: 'longtask', buffered: true })
```

- `longtask` 엔트리는 Baseline이 아닙니다. 지원 브라우저를 확인해야 합니다.

해결은 긴 작업을 짧은 태스크 여러 개로 쪼개서 사이마다 이벤트 루프에 제어를 돌려주는 것입니다. 쪼개는 방법은 아래 세 가지입니다.

| 방법 | 특징 |
|------|------|
| `setTimeout(fn, 0)` | 어디서나 동작. 중첩 4ms 지연이 있고 다른 태스크 뒤로 밀림 |
| `scheduler.yield()` | 이어 달리는 작업이 먼저 실행되도록 우선순위를 올려 줌(아래) |
| 워커로 이동 | 계산 자체를 메인 스레드 밖으로 이동(자세히는 54편) |

```js
async function processAll(items) {
  for (const item of items) {
    handle(item)
    await new Promise((r) => setTimeout(r, 0)) // 양보
  }
}
```

**흔한 실수:** 항목마다 양보하는 것입니다. 양보 자체에 비용이 있으니 일정 시간(예: 50ms 미만)마다만 양보합니다.

```js
let last = performance.now()
for (const item of items) {
  handle(item)
  if (performance.now() - last > 40) {
    await scheduler.yield() // 지원되는 곳에서
    last = performance.now()
  }
}
```

## Debounce / Throttle

디바운스(debounce)는 짧은 간격으로 반복되는 호출을 모아서 마지막 호출 뒤 일정 시간이 지나면 한 번만 실행합니다. 스로틀(throttle)은 연속 호출을 일정 간격에 최대 한 번만 실행하도록 제한합니다. 둘은 표준 API가 아니라 `setTimeout`으로 만드는 패턴입니다.

| 구분 | 실행 시점 | 적합한 이벤트 |
|------|-----------|---------------|
| 디바운스 | 호출이 멈춘 뒤 한 번 | 검색어 입력, 창 크기 조절 완료 |
| 스로틀 | 일정 간격마다 | 스크롤, 마우스 이동 |

```js
function debounce(fn, ms) {
  let id
  return (...args) => {
    clearTimeout(id)
    id = setTimeout(() => fn(...args), ms)
  }
}
```

```js
function throttle(fn, ms) {
  let last = 0
  return (...args) => {
    const now = performance.now()
    if (now - last < ms) return
    last = now
    fn(...args)
  }
}
```

- 디바운스는 보통 마지막 호출 뒤(trailing)에 실행합니다. 첫 호출에서 바로 실행하는(leading) 변형도 있습니다.
- 화면 갱신이 목적이면 시간 간격 대신 rAF로 프레임당 한 번만 처리하는 방식이 더 맞습니다.

```js
let queued = false
addEventListener('scroll', () => {
  if (queued) return
  queued = true
  requestAnimationFrame(() => { queued = false; update() })
})
```

**흔한 실수:** 디바운스된 함수를 렌더링할 때마다 새로 만드는 것입니다. 타이머 ID가 공유되지 않아서 디바운스가 동작하지 않습니다. 한 번만 만들어 재사용합니다. 요청을 거르는 데 쓴다면 이전 요청 취소(자세히는 37편)도 함께 고려합니다.

## MessageChannel로 태스크 예약

`MessageChannel`은 연결된 두 포트(`port1`, `port2`)를 만들고, 한쪽에 보낸 메시지를 다른 쪽이 받는 API입니다(자세히는 54편). 메시지 전달은 태스크로 이뤄집니다. 이 성질을 이용하면 `setTimeout`의 4ms 최소 지연 없이 다음 태스크를 예약할 수 있습니다. Baseline 널리 지원(2015년 9월부터)입니다.

```js
const { port1, port2 } = new MessageChannel()
port1.onmessage = () => console.log('task')
port2.postMessage(null)
console.log('sync')
// sync task
```

- 포트의 메시지 큐는 `onmessage` 속성을 처음 설정하거나 `start()`를 호출해야 활성화됩니다. `addEventListener('message', ...)`만 쓰면 `start()`를 불러야 합니다.
- 메시지 태스크는 타이머가 아니므로 `setTimeout`의 중첩 4ms 클램프를 받지 않습니다.
- 표준은 쓰지 않는 포트를 `close()`로 닫기를 권장합니다. 닫지 않으면 메모리 사용량이 늘 수 있습니다.
- 새 코드에서는 지원되는 환경이면 `scheduler.postTask`나 `scheduler.yield`를 먼저 고려합니다.

## Prioritized Task Scheduling API

Prioritized Task Scheduling API는 우선순위가 있는 태스크를 예약하는 API입니다. 전역 `scheduler` 객체의 `postTask()`로 예약합니다. 지원 상태: Baseline이 아닙니다. web-features 데이터 기준으로 `scheduler`는 Chrome·Edge 129, Firefox 142부터 지원하고 Safari는 지원하지 않습니다. 워커에서도 쓸 수 있습니다. 쓰기 전에 기능 검사를 합니다.

```js
if ('scheduler' in globalThis) {
  scheduler.postTask(work, { priority: 'background' })
}
```

`postTask(callback, options)`는 Promise를 돌려줍니다. 콜백의 반환값으로 이행되고, 콜백이 예외를 던지거나 취소되면 거부됩니다.

| 옵션 | 뜻 |
|------|----|
| `priority` | `'user-blocking'`, `'user-visible'`(기본), `'background'`. 고정 우선순위 |
| `delay` | 큐에 넣기까지의 최소 대기(밀리초, 기본 0) |
| `signal` | `AbortSignal` 또는 `TaskSignal`. 취소와 우선순위 변경에 사용 |

| 우선순위 | 용도 |
|----------|------|
| `user-blocking` | 사용자 상호작용을 막거나 체감에 직접 영향 |
| `user-visible` | 보이지만 막지는 않는 작업(기본값) |
| `background` | 급하지 않은 작업(로그 전송, 서드파티 초기화) |

우선순위를 나중에 바꾸려면 `TaskController`를 만들어 그 `signal`을 넘기고 `setPriority()`를 호출합니다. 이때 `postTask`에는 `priority`를 함께 주지 않습니다. `TaskSignal`은 `prioritychange` 이벤트를 발생시킵니다.

```js
const ctrl = new TaskController({
  priority: 'user-blocking',
})
scheduler.postTask(() => work(), { signal: ctrl.signal })
ctrl.setPriority('background') // 대기 중이면 우선순위 변경
ctrl.abort()                   // 취소하면 Promise가 거부됨
```

- 같은 우선순위의 태스크는 예약한 순서대로 실행됩니다.
- 취소(`abort`)로 거부된 Promise는 `AbortError` 등 중단 사유로 거부됩니다. 처리하지 않으면 `unhandledrejection`이 발생하므로 `catch`를 붙입니다(자세히는 37편).

## scheduler.yield()로 긴 작업 쪼개기

`scheduler.yield()`는 메인 스레드에 제어를 돌려주고, 다른 대기 작업(입력 처리 등)이 실행된 뒤에 `await` 아래 코드를 이어서 실행하는 Promise를 돌려줍니다. 인수는 없고 `undefined`로 이행됩니다. 지원 상태는 `scheduler`와 같습니다(Chrome·Edge 129, Firefox 142부터, Safari 미지원).

```js
button.addEventListener('click', async () => {
  showSpinner()          // 먼저 화면에 반영
  await scheduler.yield()
  doSlowContentSwap()    // 양보한 뒤 이어서 실행
})
```

- 이어지는 작업은 우선순위가 올라간 큐에 들어갑니다. 같은 우선순위로 새로 예약된 `postTask` 태스크보다 먼저 실행되고, 더 높은 우선순위 태스크보다는 뒤에 실행됩니다. `setTimeout(0)`으로 양보하면 다른 태스크들 뒤로 밀리는 것과 다릅니다.
- 기본 우선순위는 `'user-visible'`입니다. `postTask` 콜백 안에서 부르면 그 태스크의 우선순위를 이어받습니다.
- `yield()`를 여러 번 부르면 부른 순서대로 이어집니다.
- `postTask`의 `signal`로 태스크를 취소하면 그 안에서 대기 중인 `yield()`도 중단되고 `await` 줄에서 예외가 납니다.
- 미지원 환경에서는 기능 검사 후 `setTimeout` 기반 양보로 대체합니다.

```js
const yieldToMain = globalThis.scheduler?.yield
  ? () => scheduler.yield()
  : () => new Promise((r) => setTimeout(r, 0))
```

## navigator.scheduling.isInputPending()

`navigator.scheduling.isInputPending()`은 처리 대기 중인 입력 이벤트가 있는지 `boolean`으로 알려 줍니다. 대기 중이면 양보하고 아니면 계속 달리는 방식으로 쓰도록 만든 API입니다.

```js
while (tasks.length) {
  if (navigator.scheduling.isInputPending()) {
    await yieldToMain() // 입력이 기다리면 양보
  } else {
    tasks.shift()()
  }
}
```

- 옵션 `includeContinuous`(기본 `false`)가 `true`면 `mousemove`, `wheel`, `touchmove`, `drag`, `pointermove`, `pointerrawupdate` 같은 연속 이벤트도 대기 입력에 포함합니다.
- 지원 상태: Baseline이 아닙니다. web-features 데이터 기준으로 Chrome·Edge 87부터 지원하는 Chromium 전용이고, MDN은 이 API를 지원 중단(deprecated)·실험적 기능으로 표시하며 `false`를 잘못 돌려줄 수 있어 새 프로젝트에서는 피하라고 안내합니다. 대안은 `scheduler.yield()`입니다.
- 쓴다면 `navigator.scheduling?.isInputPending` 존재를 먼저 확인합니다.

## 핵심 정리

- 이벤트 루프는 스택이 비면 태스크 하나를 실행하고, 마이크로태스크를 모두 비운 뒤, 렌더링 기회가 있으면 렌더링합니다.
- 태스크 큐는 소스별로 여럿이고 같은 소스 안에서만 순서가 보장됩니다. 마이크로태스크(Promise 콜백, `queueMicrotask`)는 다음 태스크보다 먼저 전부 실행됩니다.
- `setTimeout`은 "최소 이 시간 뒤"이며 중첩 수준이 5를 넘으면 4ms, 백그라운드 탭에서는 더 길게 늦춰집니다.
- rAF는 렌더링 직전에, `requestIdleCallback`은 한가할 때(Safari 미지원) 실행되고, 렌더링 업데이트는 rAF 이후 스타일·레이아웃, 관찰자 콜백, 그리기 순입니다.
- 50ms 이상의 롱 태스크는 입력을 막으므로 `scheduler.yield()`, `setTimeout`, 워커로 쪼개거나 옮깁니다.
- `scheduler`(Chrome·Edge 129, Firefox 142부터)와 `isInputPending()`(Chromium 전용, 지원 중단 표시)은 Baseline이 아니라서 기능 검사가 필요합니다.

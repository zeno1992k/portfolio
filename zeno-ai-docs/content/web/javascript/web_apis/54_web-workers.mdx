## Web Worker 개념

Web Worker는 메인 스레드와 별개의 스레드에서 스크립트를 실행하는 브라우저 기능입니다. 메인 스레드는 렌더링과 입력 처리를 맡으므로 오래 걸리는 계산이 끼어들면 화면이 멈춥니다(자세히는 08편). 워커에서 계산하면 메인 스레드는 계속 반응합니다.

- 워커는 자기만의 이벤트 루프와 전역 객체를 가집니다. 메인 스레드와 변수를 공유하지 않고 메시지로만 데이터를 주고받습니다.
- 워커에서는 DOM을 만지지 못합니다. 화면 갱신은 결과를 받은 메인 스레드가 합니다.
- 종류는 세 가지입니다.

| 종류 | 접근 범위 | 다루는 편 |
|------|-----------|-----------|
| Dedicated Worker | 만든 스크립트 하나만 | 이 편 |
| Shared Worker | 같은 origin의 여러 창·iframe·워커 | 55편 |
| Service Worker | 네트워크 요청을 가로채는 프록시 | 56편 |

이 편은 전용 워커를 기준으로 설명하며, 메시지 전달 규칙은 나머지 종류에도 공통으로 쓰입니다.

## Dedicated Worker

전용 워커는 `new Worker(url)`로 만듭니다. 만든 스크립트만 그 워커와 통신할 수 있습니다. 워커 안의 전역 객체는 `window`가 아니라 `self`이고, 인터페이스는 `DedicatedWorkerGlobalScope`입니다.

```js
// main.js
const worker = new Worker('worker.js')
worker.postMessage('ping')
worker.onmessage = (e) => console.log(e.data) // pong

// worker.js
self.onmessage = (e) => self.postMessage('pong')
```

- 워커 스크립트의 URL은 문서와 같은 origin이어야 합니다. `blob:`·`data:` URL은 예외로 허용됩니다. 상대 URL은 문서 기준으로 해석됩니다.
- 응답의 MIME 타입이 JavaScript가 아니면 `NetworkError`, 같은 origin 규칙을 어기면 `SecurityError`, URL을 파싱하지 못하면 `SyntaxError`가 납니다.
- 워커 안에서 다른 워커를 만들 수 있습니다(서브워커). 서브워커의 URL은 부모 워커 위치를 기준으로 해석됩니다.
- 페이지 CSP의 `worker-src`가 워커 URL을 제한합니다. 워커 스크립트 자신의 CSP는 그 스크립트의 응답 헤더로 정합니다(자세히는 63편).
- 지원 여부는 `window.Worker`로 확인합니다.

### 모듈 워커

`type: 'module'` 옵션을 주면 ES 모듈로 실행됩니다. 워커 안에서 `import`·`export`를 쓰고, 항상 엄격 모드입니다. 모듈 워커는 Baseline 2023입니다(Chrome·Edge 80, Firefox 114, Safari 15).

```js
const w = new Worker('worker.js', { type: 'module' })
// bundler 환경에서는 URL을 번들러가 해석하게 쓴다
const url = new URL('./worker.js', import.meta.url)
const w2 = new Worker(url, { type: 'module' })
```

| 항목 | 클래식 워커(기본) | 모듈 워커 |
|------|-------------------|-----------|
| 의존성 불러오기 | `importScripts()` | `import` 문 |
| 실행 모드 | 비엄격 모드 | 엄격 모드 |
| 의존성 로딩 | 동기 | 비동기로 해결한 뒤 실행 |
| 자격 증명 옵션 `credentials` | 해당 없음 | `omit`, `same-origin`(기본), `include` |

옵션 `name`은 디버깅용 이름입니다.

### importScripts()

`importScripts(url, ...)`은 클래식 워커에서 스크립트를 동기로 불러와 실행합니다. 모든 스크립트가 로드될 때까지 다음 줄로 넘어가지 않고, 인수 순서대로 실행됩니다.

```js
// classic worker 안에서
importScripts('lib-a.js', 'lib-b.js')
// 모듈 워커에서 호출하면 TypeError
```

- 상대 URL은 워커 진입 스크립트 기준입니다.
- 다른 origin의 스크립트도 `no-cors`로 불러올 수 있습니다. 대신 CORP, CSP 같은 보안 장치가 막을 수 있습니다.
- MIME 타입이 JavaScript가 아니면 `NetworkError`입니다.
- 새 코드에서는 모듈 워커와 `import`를 씁니다(모듈 문법은 14편).

## 워커에서 쓸 수 있는 API와 없는 API

워커의 전역은 `WorkerGlobalScope`이며 `window`, `location`, `navigator` 대신 `self`, `WorkerLocation`, `WorkerNavigator`를 씁니다. 화면과 관련된 것은 없고, 네트워크·저장소·계산 계열은 대부분 있습니다.

| 구분 | 있음 | 없음 |
|------|------|------|
| 전역·DOM | `self`, `console`, `URL`, `Performance` | `window`, `document`, DOM 조작 |
| 타이머·스케줄 | `setTimeout`, `setInterval`, `queueMicrotask`, `structuredClone` | 대화상자(`alert`, `confirm`, `prompt`) |
| 네트워크 | `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`(서버 전송 이벤트) | |
| 저장소 | `IndexedDB`, File API | `localStorage`, `sessionStorage` |
| 통신 | `postMessage`, Channel Messaging, `BroadcastChannel` | 부모 창 접근 |
| 계산·그래픽 | Web Crypto, Streams, 압축 스트림, `OffscreenCanvas`·WebGL·WebGPU, `createImageBitmap` | |

- `requestAnimationFrame`은 전용 워커에서만 쓸 수 있습니다(`OffscreenCanvas`와 함께 씀).
- Cookie Store API는 서비스 워커에서만 쓸 수 있습니다.
- Web Locks, WebCodecs, Permissions, Notifications 같은 API도 워커에서 쓸 수 있습니다. 정확한 목록은 MDN의 워커 API 목록을 확인합니다.

**흔한 실수:** 워커 안에서 `document`나 `window`를 참조하는 것입니다. `ReferenceError`가 납니다. DOM이 필요한 라이브러리는 워커에서 쓸 수 없습니다.

## postMessage / onmessage

워커와 메인 스레드는 `postMessage(data)`로 보내고 `message` 이벤트로 받습니다. 받는 쪽의 `event.data`가 보낸 값입니다.

```js
// main.js
worker.postMessage({ type: 'sum', nums: [1, 2, 3] })
worker.onmessage = (e) => console.log(e.data) // 6

// worker.js
self.onmessage = (e) => {
  const total = e.data.nums.reduce((a, b) => a + b, 0)
  self.postMessage(total)
}
```

- 메인 스레드에서는 `worker.postMessage`, `worker.onmessage`를 쓰고, 워커 안에서는 `self.postMessage`(또는 `postMessage`), `self.onmessage`를 씁니다.
- `addEventListener('message', ...)`도 같습니다. 이벤트 처리는 각자의 이벤트 루프에서 일어나므로 메시지는 비동기로 도착합니다.
- 기본은 복제입니다. 보낸 값은 구조화된 복제 알고리즘으로 복사되어 양쪽이 서로 다른 객체를 가집니다. 복제 비용은 데이터 크기에 비례합니다.
- 메시지에 `type`이나 `id` 필드를 넣어 종류를 구분하는 것이 일반적입니다. 규모가 커지면 아래 RPC 패턴을 씁니다.

**흔한 실수:** 객체를 보낸 뒤 원본을 바꾸면 워커의 값도 바뀐다고 생각하는 것입니다. 복제이므로 원본을 바꿔도 워커의 복사본은 그대로입니다.

## Structured Clone

구조화된 복제(structured clone)는 `postMessage`, `structuredClone()`, IndexedDB가 값을 복사할 때 쓰는 알고리즘입니다. 순환 참조를 유지하며 깊이 복사합니다.

```js
const a = { name: 'MDN' }
a.self = a
const b = structuredClone(a)
b.self === b // true (순환 참조 유지)
b === a      // false
```

`structuredClone(value, { transfer })`는 Baseline 2022부터 널리 지원되고, 워커 안에서도 쓸 수 있습니다.

| 복제된다 | 복제되지 않는다 |
|----------|-----------------|
| 원시 값(`Symbol` 제외), `Date`, `RegExp`, `Map`, `Set` | 함수 |
| 일반 객체, 배열, 에러 객체 | DOM 노드 |
| `ArrayBuffer`, 타입 배열, `DataView` | `Symbol` 값 |
| `Blob`, `File`, `ImageBitmap`, `ImageData`, `DOMRect` 등 직렬화 가능한 Web API 객체 | |

복제할 수 없는 값이 있으면 `postMessage`와 `structuredClone`이 `DataCloneError`를 던집니다. 복제 과정에서 잃는 것은 다음과 같습니다.

- 프로토타입 체인. 클래스 인스턴스는 일반 객체가 되고 메서드가 사라집니다.
- 접근자와 프로퍼티 어트리뷰트. getter·setter는 값이 되고 읽기 전용도 읽기·쓰기가 됩니다.
- 클래스의 private 요소와 `RegExp.lastIndex`.

```js
class User { constructor() { this.n = 1 } hi() {} }
const c = structuredClone(new User())
c instanceof User // false
c.hi              // undefined
c                 // { n: 1 }
```

**흔한 실수:** 함수나 DOM 노드가 들어 있는 객체를 보내는 것입니다. 호출 시점에 `DataCloneError`가 납니다. 함수는 이름 문자열로 바꿔 보내고 받는 쪽에서 매핑합니다.

## Transferable

전송 가능한(transferable) 객체는 복사하지 않고 소유권을 통째로 넘길 수 있는 객체입니다. 자원이 한 곳에만 존재하므로 큰 데이터를 빠르게 넘길 수 있고, 넘긴 쪽의 객체는 쓸 수 없게 됩니다. `postMessage`의 두 번째 인수에 전송할 객체 배열을 줍니다.

```js
const bytes = new Uint8Array(8 * 1024 * 1024)
worker.postMessage(bytes, [bytes.buffer])
bytes.byteLength // 0 (버퍼가 분리됨)
```

- `ArrayBuffer`를 전송하면 메모리가 새 쪽으로 옮겨지고 원본 `ArrayBuffer`는 분리(detached)됩니다. 길이는 0이 되고 접근하면 예외가 납니다.
- 타입 배열은 직렬화 가능하지만 전송 가능하지 않습니다. 전송 대상은 그 밑의 `.buffer`입니다.
- `structuredClone(value, { transfer: [buf] })`로도 전송합니다.
- 전송 가능한 객체는 다음과 같습니다.

| 분류 | 객체 |
|------|------|
| 메모리·미디어 | `ArrayBuffer`, `ImageBitmap`, `AudioData`, `VideoFrame`, `MediaStreamTrack`, `MediaSourceHandle` |
| 그래픽 | `OffscreenCanvas` |
| 통신 | `MessagePort`, `RTCDataChannel`, `MIDIAccess` |
| 스트림 | `ReadableStream`, `WritableStream`, `TransformStream`, `WebTransportReceiveStream`, `WebTransportSendStream` |

- `SharedArrayBuffer`는 전송이 아니라 양쪽이 같은 메모리를 공유합니다(자세히는 55편).
- 값 속에 들어 있는 `ArrayBuffer`도 전송 목록에 넣어야 전송됩니다. 목록에 없으면 복제됩니다.

**흔한 실수:** 전송한 `ArrayBuffer`를 이후 코드에서 읽는 것입니다. 이미 분리되어 길이가 0이므로 필요하면 전송 전에 복사해 두거나, 워커가 결과를 다시 전송해 돌려주게 만듭니다.

## error·messageerror 이벤트

워커 객체에는 오류 이벤트가 두 가지 있습니다.

| 이벤트 | 발생 조건 |
|--------|-----------|
| `error` | 워커 안의 스크립트 오류, 워커 로드 실패 |
| `messageerror` | 받은 메시지를 역직렬화하지 못함 |

```js
worker.onerror = (e) => {
  console.error(e.message, e.filename, e.lineno)
}
worker.onmessageerror = (e) => {
  console.error('역직렬화 실패', e)
}
```

- 워커의 잡히지 않은 예외는 메인 스레드의 `try`/`catch`로 잡히지 않습니다. 반드시 `error` 이벤트로 받습니다.
- `error`의 `message`, `filename`, `lineno`로 위치를 알 수 있습니다.
- 요청 단위 오류는 `error` 이벤트에 맡기지 말고 메시지에 담아 돌려주는 방식이 안전합니다(아래 RPC 패턴).

## MessageChannel·MessagePort

`MessageChannel`은 두 개의 `MessagePort`(`port1`, `port2`)를 만들어 양방향 전용 통로를 만듭니다. 한쪽 포트를 `postMessage`의 전송 목록에 넣어 워커에게 넘기면, 두 곳이 기본 메시지 경로와 별개의 전용 통로로 통신합니다. 2015년 9월부터 널리 지원됩니다.

```js
const { port1, port2 } = new MessageChannel()
port1.onmessage = (e) => console.log(e.data) // from worker
worker.postMessage({ hello: 1 }, [port2]) // port2 전송

// worker.js
self.onmessage = (e) => {
  const [port] = e.ports
  port.postMessage('from worker')
}
```

- `port.onmessage`에 핸들러를 대입하면 포트가 자동으로 시작됩니다. `addEventListener`로 받을 때는 `port.start()`를 직접 호출해야 합니다.
- `MessagePort`는 전송 가능하므로 다른 워커나 iframe에 다시 넘길 수 있습니다. 워커끼리 직접 통신하게 하거나 요청마다 응답 전용 포트를 만드는 데 씁니다.
- 더 이상 쓰지 않는 포트는 `close()`로 닫습니다.

## 요청·응답 RPC 래퍼 패턴

`postMessage`는 응답과 요청을 짝짓지 못합니다. 요청마다 `id`를 붙이고 `id`로 대기 중인 Promise를 찾아 완료하는 래퍼를 만들면 워커 함수를 `await`로 호출할 수 있습니다.

```js
function rpc(worker) {
  let seq = 0
  const pending = new Map()
  worker.onmessage = ({ data }) => {
    const { resolve, reject } = pending.get(data.id)
    pending.delete(data.id)
    if (data.error) reject(new Error(data.error))
    else resolve(data.result)
  }
  return (method, params) => new Promise((ok, fail) => {
    pending.set(++seq, { resolve: ok, reject: fail })
    worker.postMessage({ id: seq, method, params })
  })
}
```

워커 쪽은 메서드 표를 두고 결과나 오류를 같은 `id`로 돌려줍니다.

```js
const methods = {
  sum: ({ nums }) => nums.reduce((a, b) => a + b, 0),
}
self.onmessage = async ({ data }) => {
  const { id, method, params } = data
  try {
    const result = await methods[method](params)
    self.postMessage({ id, result })
  } catch (e) {
    self.postMessage({ id, error: String(e) })
  }
}
```

```js
const call = rpc(worker)
const total = await call('sum', { nums: [1, 2, 3] }) // 6
```

- 요청 단위 오류가 Promise 거부로 연결되어 일반 비동기 코드처럼 처리할 수 있습니다.
- 전송할 버퍼가 있으면 `postMessage`의 두 번째 인수로 전송 목록을 추가로 받게 확장합니다.
- 워커가 `error` 이벤트로 죽었을 때를 대비해 `pending`의 모든 항목을 거부하는 처리를 `onerror`에 둡니다. 없으면 호출한 쪽이 영원히 기다립니다.

## CPU 작업 분리

CPU를 오래 쓰는 계산(이미지 처리, 대용량 파싱, 정렬·검색 색인 생성, 암호화, 압축)은 메인 스레드에서 돌리면 렌더링과 입력이 멈춥니다. 이런 작업을 워커로 옮기는 것이 CPU 작업 분리입니다.

- 워커로 옮긴다고 계산이 빨라지지는 않습니다. 메인 스레드가 막히지 않는 것이 이득입니다.
- 분리 대상 판단 기준은 입력이 큰데 계산 시간도 긴 작업, 즉 긴 태스크로 UI를 막는 작업입니다(자세히는 08편, 65편). 몇 밀리초짜리 작업은 메시지 왕복 비용이 더 큽니다.
- 데이터가 크면 복제 비용을 피하려고 `ArrayBuffer`를 전송합니다. 이미지는 `ImageBitmap`이나 `OffscreenCanvas`를 전송해 워커에서 그립니다.
- 긴 작업은 중간 진행률을 `postMessage`로 주기적으로 보내고, 취소가 필요하면 취소 메시지를 받아 플래그를 확인하게 합니다. 워커의 계산 루프 도중에는 새 메시지를 처리하지 못하므로 청크 단위로 나눠 이벤트 루프에 양보합니다.
- 결과를 받은 메인 스레드가 DOM을 갱신합니다.

```js
// 큰 버퍼를 전송하고 결과를 전송으로 돌려받는다
worker.postMessage({ pixels: buf }, [buf])
worker.onmessage = (e) => {
  const out = new Uint8ClampedArray(e.data.pixels)
  // 결과를 화면에 반영
}
```

## Worker Pool 개념

워커를 만드는 것은 비용이 듭니다. 스크립트를 내려받고 새 실행 환경을 초기화해야 하므로 작업마다 만들고 버리지 않고, 정해진 수의 워커를 미리 만들어 재사용하는 구조가 워커 풀입니다. 풀은 놀고 있는 워커 목록과 대기 작업 큐로 구성됩니다.

워커 수는 `navigator.hardwareConcurrency`로 정합니다. 논리 프로세서 수를 알려 주는 읽기 전용 값으로 Baseline 2022부터 널리 지원됩니다. 브라우저가 개인정보 보호나 현실적인 워커 수를 반영해 실제보다 작게 보고할 수 있어서 정확한 코어 수로 믿으면 안 됩니다.

```js
const idle = []   // 놀고 있는 워커
const queue = []  // 대기 중인 작업
function next() {
  if (!idle.length || !queue.length) return
  const w = idle.pop()
  const { msg, done } = queue.shift()
  w.onmessage = (e) => {
    idle.push(w)
    done(e.data)
    next()
  }
  w.postMessage(msg)
}
```

```js
const size = Math.max(1, navigator.hardwareConcurrency - 1)
for (let i = 0; i < size; i++) {
  idle.push(new Worker('task.js', { type: 'module' }))
}
const run = (msg) => new Promise((done) => {
  queue.push({ msg, done })
  next()
})
```

- 메인 스레드를 위해 코어 하나를 비워 두려고 `hardwareConcurrency`에서 1을 뺍니다.
- 위 예시는 오류 처리를 생략했습니다. 실제로는 `error`를 받으면 해당 워커를 풀에서 빼고 작업을 거부 또는 재시도해야 합니다.
- 워커 수가 많을수록 빠른 것이 아닙니다. 워커마다 메모리를 쓰고 코어 수를 넘으면 문맥 전환 비용이 늘어납니다.
- 작업이 드물면 풀 없이 하나의 워커를 재사용하는 것으로 충분합니다.

## 컴포넌트와 Worker 통신

커스텀 요소가 워커를 소유하면 워커의 수명을 요소의 연결 상태에 맞춥니다(자세히는 18편). 연결될 때 만들고 끊길 때 종료하며, 외부와는 메서드·프로퍼티·이벤트로만 통신해서 `postMessage`를 컴포넌트 안에 숨깁니다(자세히는 25편).

```js
class FileHasher extends HTMLElement {
  #worker
  connectedCallback() {
    this.#worker = new Worker('hash.js', { type: 'module' })
    this.#worker.onmessage = ({ data }) => {
      const e = new CustomEvent('hashed', { detail: data })
      this.dispatchEvent(e)
    }
  }
  disconnectedCallback() { this.#worker.terminate() }
  hash(buf) { this.#worker.postMessage(buf, [buf]) }
}
```

- 여러 컴포넌트가 같은 워커를 써야 하면 컴포넌트마다 만들지 않고 모듈 최상위에 하나를 두는 서비스 객체를 공유합니다. 이때는 컴포넌트가 아니라 서비스가 수명을 관리하고 컴포넌트는 구독만 합니다.
- `connectedCallback`은 요소를 이동할 때도 다시 호출됩니다. 연결 해제 때 종료하면 이동 시 진행 중이던 작업을 잃으므로 재연결에 대비한 설계가 필요합니다.
- 응답을 컴포넌트에 연결할 때는 요청 `id`로 짝짓습니다. 컴포넌트가 사라진 뒤 도착한 응답은 무시합니다.
- 오래 걸리는 요청의 응답이 오기 전에 입력이 바뀌면 이전 응답을 버립니다(경쟁 상태는 39편).

## Worker 종료와 생명주기

워커의 수명은 만든 쪽과 워커 양쪽에서 끝낼 수 있습니다.

| 방법 | 호출 위치 | 동작 |
|------|-----------|------|
| `worker.terminate()` | 메인 스레드 | 즉시 중단. 워커에게 정리할 기회를 주지 않음 |
| `self.close()` | 워커 안 | 워커 이벤트 루프에 쌓인 대기 태스크를 버리고 닫음 |

```js
// 정리 후 종료하려면 메시지로 협의한다
worker.postMessage({ type: 'shutdown' })
// worker.js: 'shutdown'을 받으면 자원을 정리하고 self.close()
```

- `terminate()`는 진행 중인 계산과 열린 연결을 강제로 끊습니다. 저장해야 할 상태가 있으면 종료 메시지로 정리한 뒤 `close()`하게 합니다.
- 워커는 소유 문서가 사라지면 종료 대상이 됩니다. 브라우저가 실제 종료를 늦출 수 있으므로 의존하지 말고 명시적으로 종료합니다.
- 워커를 쓰고 버리는 코드에서 종료를 빼먹으면 스레드와 메모리가 남습니다. 컴포넌트는 `disconnectedCallback`에서, 풀은 앱 종료 시점에 모든 워커를 `terminate()`합니다(메모리 관리는 67편).
- 종료한 워커는 다시 쓸 수 없습니다. 필요하면 새로 만듭니다.
- 워커마다 자기 오류 이벤트를 가지므로 여러 개를 관리할 때는 `error`를 워커별로 연결합니다.

## 핵심 정리

- 워커는 메인 스레드와 별개의 스레드와 이벤트 루프에서 실행되며 DOM과 `window`가 없고 `self`가 전역입니다.
- 전용 워커는 `new Worker(url)`로 만들고 같은 origin이어야 하며, `type: 'module'`(Baseline 2023)이면 `import`를 쓰고 `importScripts()`는 클래식 워커에서만 됩니다.
- `postMessage`는 구조화된 복제로 값을 복사하며, 함수·DOM 노드·`Symbol`은 `DataCloneError`가 나고 프로토타입과 접근자는 사라집니다.
- `ArrayBuffer`, `MessagePort`, `OffscreenCanvas` 같은 전송 가능한 객체는 전송 목록에 넣으면 소유권이 넘어가고 원본은 분리됩니다.
- 워커 오류는 `error`·`messageerror` 이벤트로 받고, 요청과 응답은 `id` 기반 RPC 래퍼로 짝지으며, 큰 작업만 워커로 분리하고 수는 `hardwareConcurrency`를 참고해 정합니다.
- 컴포넌트가 소유한 워커는 `disconnectedCallback`에서 `terminate()`로 끝내고, 정리가 필요하면 종료 메시지 뒤 `self.close()`를 씁니다.

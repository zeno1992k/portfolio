## IntersectionObserver

IntersectionObserver는 대상 요소가 기준 영역(루트)과 얼마나 겹치는지 변화를 비동기로 알려 주는 Observer입니다. 스크롤 이벤트에서 위치를 계산하던 일을 대신하며 Baseline 2019입니다.

```js
const io = new IntersectionObserver((entries, observer) => {
  for (const entry of entries) {
    console.log(entry.target.id, entry.isIntersecting)
  }
})
io.observe(document.querySelector('#box'))
```

| 메서드 | 동작 |
|--------|------|
| `observe(el)` | 대상 관찰 시작 |
| `unobserve(el)` | 대상 하나의 관찰 중단 |
| `disconnect()` | 모든 대상의 관찰 중단 |
| `takeRecords()` | 아직 전달하지 않은 엔트리를 콜백 없이 꺼냄 |

- 콜백은 `(entries, observer)`를 받고 `entries`는 바뀐 대상의 `IntersectionObserverEntry` 배열입니다.
- `observe()` 직후 처음 한 번은 대상이 보이지 않아도 콜백이 호출됩니다. 초기 상태를 알려 주는 호출입니다.
- 콜백은 메인 스레드에서 실행되므로 무거운 작업은 `requestIdleCallback()`으로 미룹니다(MDN).

### 옵션: root·rootMargin·threshold

| 옵션 | 기본값 | 의미 |
|------|--------|------|
| `root` | `null` | 기준 요소. 대상의 조상이어야 하며 `null`이면 뷰포트 |
| `rootMargin` | `'0px'` | 루트 영역을 CSS 여백 문법으로 키우거나 줄임. 단위는 px 또는 퍼센트 |
| `threshold` | `0` | 콜백을 호출할 겹침 비율. 숫자 하나 또는 0–1 배열 |

```js
const io = new IntersectionObserver(callback, {
  root: document.querySelector('#scroller'),
  rootMargin: '200px 0px',
  threshold: [0, 0.5, 1],
})
```

- `threshold`는 비율이 그 값을 지나갈 때마다 콜백이 호출된다는 뜻입니다. 기본값 0은 1픽셀이라도 닿는 순간입니다.
- `rootMargin`을 양수로 주면 화면에 닿기 전에 미리 감지하고, 음수로 주면 화면 안쪽에서 감지합니다.
- 명세에 따르면 `rootMargin`과 `scrollMargin`은 같은 origin 도메인의 대상에만 적용되고 교차 출처 대상에는 무시됩니다.
- `scrollMargin`은 중첩 스크롤 컨테이너에 적용하는 여백 옵션입니다.

### 엔트리 필드

| 필드 | 값 |
|------|----|
| `target` | 관찰 중인 요소 |
| `isIntersecting` | 현재 루트와 겹치는지 |
| `intersectionRatio` | 보이는 비율(0–1) |
| `intersectionRect` | 겹치는 영역의 `DOMRect` |
| `boundingClientRect` | 대상 전체의 `DOMRect` |
| `rootBounds` | 루트 영역의 `DOMRect`(`rootMargin` 반영) |
| `time` | 관찰 시각(`DOMHighResTimeStamp`) |

**흔한 실수:** `isIntersecting`을 확인하지 않고 콜백이 호출됐다는 이유만으로 로드하는 것입니다. 처음 호출과 화면을 벗어나는 호출에도 콜백이 실행되므로 조건 확인이 필요합니다.

## IntersectionObserver v2 가시성 추적 (Chromium 전용)

v2는 대상이 겹치는지에 더해 다른 요소에 가려지지 않고 실제로 보이는지를 알려 줍니다. 광고 노출 확인 같은 용도입니다. 미Baseline이며 Chromium 계열에서만 쓰입니다.

```js
const io = new IntersectionObserver(callback, {
  threshold: 1,
  trackVisibility: true,
  delay: 100,
})
// entry.isVisible: 가려지지 않고 보이는지
```

- `trackVisibility: true`이면 엔트리에 `isVisible`이 계산되어 들어옵니다. 계산 비용이 커서 필요한 곳에만 씁니다.
- `delay`는 알림 사이의 최소 간격(밀리초)이고, `trackVisibility`가 켜져 있으면 100 미만의 값이 100으로 올려집니다.
- 지원하지 않는 브라우저에서는 `isVisible`을 신뢰하지 않고 `isIntersecting`만으로 동작하게 설계합니다.

## ResizeObserver

ResizeObserver는 요소의 크기가 바뀔 때 알려 주는 Observer로 Baseline 2020입니다. `window`의 `resize` 이벤트는 뷰포트 크기만 알려 주지만 ResizeObserver는 요소 자체의 크기 변화를 감지합니다.

```js
const ro = new ResizeObserver((entries) => {
  for (const entry of entries) {
    const box = entry.contentBoxSize[0]
    console.log(box.inlineSize, box.blockSize)
  }
})
ro.observe(document.querySelector('#panel'))
```

- 콜백은 `observe()` 직후 처음에도 호출됩니다. 마지막으로 보고한 크기의 초기값이 실제 크기와 다르게 설정되어 있어서 첫 관찰이 항상 변화로 인식됩니다.
- 요소 크기는 내용, 스타일 변경, 창 크기 조정, 부모 레이아웃 등 어떤 이유로든 바뀌면 감지됩니다.
- `Element`와 `SVGElement`에 쓸 수 있고, 비치환 인라인 요소는 관찰하지 못합니다.

### box 옵션과 크기 필드

`observe(el, { box })`로 어느 박스의 크기를 볼지 정합니다.

| `box` 값 | 관찰 대상 |
|----------|-----------|
| `'content-box'` (기본) | 패딩과 테두리를 뺀 콘텐츠 영역 |
| `'border-box'` | 패딩과 테두리를 포함한 영역 |
| `'device-pixel-content-box'` | 콘텐츠 영역을 장치 픽셀 단위로 |

| 엔트리 필드 | 내용 |
|-------------|------|
| `contentRect` | `DOMRectReadOnly`. 옛 호환용으로 콘텐츠 영역을 담음 |
| `contentBoxSize` | `ResizeObserverSize`(`inlineSize`, `blockSize`) 배열 |
| `borderBoxSize` | 같은 형태, 테두리 박스 |
| `devicePixelContentBoxSize` | 같은 형태, 장치 픽셀 단위 |

- 크기 필드가 배열인 이유는 다단(multi-column) 레이아웃에서 요소가 여러 조각으로 나뉠 수 있기 때문입니다. 일반 요소는 첫 항목 `[0]`만 봅니다.
- `inlineSize`는 가로쓰기에서 너비, `blockSize`는 높이에 해당합니다.
- `devicePixelContentBoxSize`는 캔버스의 픽셀을 물리 픽셀과 1대 1로 맞출 때 씁니다. 미Baseline이므로 지원 여부를 확인하고 없으면 `contentBoxSize`에 `devicePixelRatio`를 곱해 근사합니다.

```js
ro.observe(canvas, { box: 'device-pixel-content-box' })
// entry.devicePixelContentBoxSize[0].inlineSize
```

### ResizeObserver 루프 오류

콜백 안에서 관찰 중인 요소의 크기를 다시 바꾸면 콜백이 끝없이 이어질 수 있습니다. 브라우저는 얕은 깊이의 요소부터 처리하고 더 깊은 요소는 다음 프레임으로 미룹니다. 같은 프레임에 전달하지 못한 알림이 남으면 `window`에서 `error` 이벤트가 발생하고 메시지는 `ResizeObserver loop completed with undelivered notifications`입니다.

```js
const ro = new ResizeObserver((entries) => {
  requestAnimationFrame(() => {
    for (const e of entries) {
      const w = e.contentBoxSize[0].inlineSize
      e.target.style.width = w + 10 + 'px'
    }
  })
})
```

- 위 코드는 같은 요소의 너비를 키워서 크기가 계속 바뀌는 순환의 예입니다. MDN은 변경을 `requestAnimationFrame`으로 미루는 것을 해결책으로 안내합니다.
- 근본 해결은 관찰 대상의 크기를 콜백이 바꾸지 않게 설계하는 것입니다. 자식 요소의 크기나 클래스를 바꾸거나 부모 크기가 자식에 의존하지 않게 합니다.
- 전역 `error` 핸들러가 이 메시지를 오류 리포트로 보내고 있다면 필터링을 고려합니다.

## MutationObserver

MutationObserver는 DOM 트리의 변경(자식 추가·삭제, 속성 변경, 텍스트 변경)을 감시하는 Observer로 Baseline 2015입니다.

```js
const mo = new MutationObserver((records, observer) => {
  for (const r of records) console.log(r.type, r.target)
})
mo.observe(document.body, {
  childList: true,
  subtree: true,
})
mo.disconnect() // 감시 중단
```

### 옵션

| 옵션 | 효과 |
|------|------|
| `childList` | 자식 노드의 추가·삭제 |
| `attributes` | 속성 변경 |
| `characterData` | 텍스트 노드 내용 변경 |
| `subtree` | 대상의 모든 후손까지 |
| `attributeFilter` | 지정한 속성 이름만(배열) |
| `attributeOldValue` | 속성의 변경 전 값을 기록(`oldValue`) |
| `characterDataOldValue` | 텍스트의 변경 전 값을 기록 |

- `childList`, `attributes`, `characterData` 중 적어도 하나가 `true`여야 합니다. 아니면 `TypeError`입니다.
- `attributeFilter`와 `attributeOldValue`를 쓰면 `attributes`가 자동으로 `true`로 간주됩니다.
- `subtree`가 없으면 대상 노드 자신과 그 자식 목록만 해당됩니다.

```js
mo.observe(el, {
  attributes: true,
  attributeFilter: ['class', 'hidden'],
  attributeOldValue: true,
})
```

### MutationRecord와 takeRecords()

| 필드 | 내용 |
|------|------|
| `type` | `'childList'`, `'attributes'`, `'characterData'` |
| `target` | 변경된 노드 |
| `addedNodes`, `removedNodes` | `childList`에서 추가·삭제된 노드 목록 |
| `attributeName` | 바뀐 속성 이름 |
| `oldValue` | 옵션으로 요청했을 때의 이전 값 |

- `takeRecords()`는 대기 중인 레코드를 콜백 없이 즉시 꺼내고 큐를 비웁니다. `disconnect()` 직전에 호출하면 아직 전달되지 않은 변경을 놓치지 않습니다.
- 관찰자가 일으킨 변경도 다시 감지되므로 콜백 안에서 같은 대상을 고치면 무한 반복이 됩니다. 고치기 전에 `disconnect()`하거나 변경이 멱등이 되게 조건을 둡니다.

## Mutation Events 제거

Mutation Events(`DOMNodeInserted`, `DOMAttrModified` 등)는 MutationObserver 이전의 DOM 변경 이벤트입니다. 지금은 폐기되었고 MDN에 따르면 Interop 2025에서 브라우저 제거 대상으로 선정되었습니다.

- 리스너를 붙이면 이후의 DOM 변경이 1.5–7배 느려지고 리스너를 떼어도 회복되지 않는다고 MDN이 설명합니다.
- 변경 시점마다 동기로 실행되므로 일괄 처리가 되지 않습니다. MutationObserver는 변경을 모아 마이크로태스크로 한 번에 전달합니다.
- 대체는 `childList`와 `subtree`를 켠 MutationObserver입니다. 새 코드에 Mutation Events를 쓰지 않습니다.

## PerformanceObserver

PerformanceObserver는 성능 타임라인에 쌓이는 엔트리(리소스 로딩, 페인트, 긴 작업 등)를 구독합니다. Baseline 2020이고 Worker에서도 쓸 수 있습니다(자세히는 65편).

```js
const po = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.name, e.startTime)
  }
})
po.observe({
  type: 'largest-contentful-paint',
  buffered: true,
})
```

| 옵션 | 의미 |
|------|------|
| `type` | 관찰할 엔트리 종류 하나 |
| `entryTypes` | 종류 여러 개(배열). 다른 옵션과 함께 쓰면 `TypeError` |
| `buffered` | 관찰을 시작하기 전에 쌓인 엔트리도 받음. `type`과 함께만 사용 |
| `durationThreshold` | 이 길이(밀리초) 이상인 엔트리만 |

- `PerformanceObserver.supportedEntryTypes`로 현재 브라우저가 지원하는 종류를 확인할 수 있습니다. 지원하지 않는 종류는 기능 감지 후에 구독합니다.
- 콜백은 성능 타임라인 태스크 소스의 태스크로 비동기 전달되어 여러 엔트리가 모여 옵니다.
- `takeRecords()`와 `disconnect()`는 다른 Observer와 같습니다.
- 앞의 세 Observer가 UI 반응용이라면 PerformanceObserver는 측정용입니다. 측정 지표 해석은 65편에서 다룹니다.

## 관찰 콜백의 실행 시점

Observer마다 콜백이 이벤트 루프에서 실행되는 위치가 다릅니다(자세히는 08편).

| Observer | 실행 시점 |
|----------|-----------|
| MutationObserver | 변경을 일으킨 스크립트가 끝난 직후의 마이크로태스크 |
| ResizeObserver | 렌더링 갱신 중 레이아웃 계산 뒤, 페인트 전 |
| IntersectionObserver | 렌더링 갱신 중 겹침을 계산하고 알림 태스크를 큐에 넣어 비동기로 전달 |
| PerformanceObserver | 성능 타임라인 태스크 소스의 태스크 |

- MutationObserver는 DOM을 고치는 코드 바로 뒤에 반응하므로 같은 태스크 안에서 변경 후 처리를 하기에 좋습니다. 변경 여러 개가 레코드 배열로 모입니다.
- ResizeObserver 콜백에서 스타일을 바꾸면 같은 프레임 안에서 레이아웃을 다시 계산합니다. 그래서 순환이 생기면 앞의 루프 오류가 납니다.
- IntersectionObserver는 스크롤마다가 아니라 프레임 단위로 계산되며, 겹침 상태가 바뀐 경우에만 알림이 큐에 들어갑니다.
- 콜백 안에서 `getBoundingClientRect()` 같은 레이아웃 읽기를 반복하면 성능이 떨어집니다. 엔트리가 이미 크기와 위치를 담고 있으니 그 값을 씁니다(자세히는 66편).

## Lazy Loading

화면에 가까워진 요소만 로드하는 지연 로딩은 IntersectionObserver로 구현할 수 있습니다. 로드할 주소를 `data-src`에 두고 겹치면 `src`로 옮깁니다.

```js
const io = new IntersectionObserver((entries, obs) => {
  for (const e of entries) {
    if (!e.isIntersecting) continue
    e.target.src = e.target.dataset.src
    obs.unobserve(e.target) // 한 번만 로드
  }
}, { rootMargin: '300px' })
const imgs = document.querySelectorAll('img[data-src]')
imgs.forEach((img) => io.observe(img))
```

- `rootMargin`을 양수로 주면 화면에 닿기 전에 미리 로드해서 빈 칸이 보이는 시간을 줄입니다.
- 로드를 시작하면 `unobserve`해서 같은 요소를 다시 처리하지 않습니다.
- 이미지는 `width`와 `height`를 미리 지정해 자리를 예약해야 합니다. 로드 전 크기가 0이라 로드 후 레이아웃이 밀립니다.
- 같은 방식으로 iframe, 동영상, 무거운 컴포넌트의 초기화도 화면에 들어올 때까지 미룰 수 있습니다.

### loading="lazy"와 비교

`img`와 `iframe`의 `loading="lazy"` 속성은 브라우저가 지연 로딩을 처리합니다. 이미지의 `loading="lazy"`는 Baseline 2023입니다(자세히는 15편).

| 항목 | `loading="lazy"` | IntersectionObserver |
|------|------------------|----------------------|
| 코드 | 속성 하나 | 직접 구현 |
| 시작 거리 | 브라우저가 정함(표준 값 없음) | `rootMargin`으로 지정 |
| 대상 | `img`, `iframe` | 아무 요소와 임의의 동작 |
| JavaScript | 꺼져 있으면 동작하지 않음 | 필요 |

- 기본 선택은 `loading="lazy"`입니다. 이미지·iframe만이면 속성으로 충분하고, 시작 거리를 조절하거나 요소 단위 동작(컴포넌트 초기화, 데이터 요청)이 필요할 때 IntersectionObserver를 씁니다.
- 화면 첫 영역(LCP 후보 이미지)에는 지연 로딩을 쓰지 않습니다(자세히는 66편).
- `loading="lazy"` 이미지는 `load` 이벤트 시점에 아직 로드되지 않았을 수 있습니다.

## Infinite Scroll

무한 스크롤은 목록 끝에 센티널(sentinel) 요소를 두고, 그 요소가 보이면 다음 페이지를 불러와 붙이는 방식입니다.

```js
let loading = false
const io = new IntersectionObserver(async ([entry]) => {
  if (!entry.isIntersecting || loading) return
  loading = true
  const done = await loadNextPage() // 항목을 목록에 추가
  loading = false
  if (done) io.disconnect()
}, { rootMargin: '400px' })
io.observe(document.querySelector('#sentinel'))
```

- `loading` 플래그로 한 번에 한 번만 요청해서 같은 페이지의 중복 요청을 막습니다.
- 새 항목은 센티널 앞에 붙입니다. 센티널이 다시 화면 밖으로 밀려나야 다음 겹침 변화가 생깁니다. 한 페이지가 화면보다 작으면 센티널이 계속 보여 콜백이 다시 오지 않으므로 로드 뒤 센티널이 아직 보이면 한 번 더 불러오는 확인이 필요합니다.
- 마지막 페이지에 도달하면 `disconnect()`하고, 요청이 실패하면 재시도 버튼을 보여 줍니다(자세히는 37편).
- 항목이 계속 쌓이면 DOM 노드가 늘어 성능과 메모리가 나빠집니다. 오래된 항목을 제거하거나 가상 스크롤을 씁니다(자세히는 66편, 80편).
- 푸터나 목록 아래의 링크에 키보드로 닿을 수 없게 되는 문제가 있어서 "더 보기" 버튼을 함께 두는 설계도 고려합니다.

## 요소 크기 반응형 컴포넌트

컴포넌트가 화면 폭이 아니라 자신이 놓인 공간의 크기에 맞춰 모양을 바꾸게 하려면 ResizeObserver를 씁니다. 같은 컴포넌트가 사이드바에도 본문에도 놓이기 때문입니다. 스타일만으로 해결되면 CSS 컨테이너 쿼리가 먼저입니다. 크기에 따라 JavaScript 동작(렌더링할 항목 수, 캔버스 크기, 레이아웃 계산)이 달라질 때 ResizeObserver를 씁니다.

```js
class ResponsiveCard extends HTMLElement {
  #ro = new ResizeObserver(([e]) => {
    const w = e.contentBoxSize[0].inlineSize
    this.toggleAttribute('compact', w < 400)
  })
  connectedCallback() { this.#ro.observe(this) }
  disconnectedCallback() { this.#ro.disconnect() }
}
```

- 크기는 숫자를 직접 쓰기보다 `compact` 같은 상태 속성이나 클래스로 바꾸고 모양은 스타일이 결정하게 합니다.
- 콜백이 자신의 크기를 바꾸는 변경을 하지 않게 합니다(앞의 루프 오류).
- 같은 요소에 여러 소비자가 있으면 한 관찰자를 공유하는 편이 비용이 적습니다.
- 연결할 때 `observe`, 분리할 때 `disconnect`를 짝으로 둡니다(자세히는 18편).

## DOM 변경 감지

외부 스크립트나 서드파티 위젯이 DOM을 바꾸는 상황에서 MutationObserver로 반응합니다. 내가 만든 컴포넌트의 변경은 이벤트나 상태로 알리는 편이 낫고, 내가 제어할 수 없는 변경을 볼 때 씁니다.

- 요소가 DOM에 나타나기를 기다리기: `childList`와 `subtree`로 감시하다가 선택자와 일치하는 노드가 오면 처리하고 `disconnect()`합니다.
- 속성 변경에 반응하기: `attributeFilter`로 필요한 속성만 지정합니다. 범위를 좁힐수록 콜백 횟수가 줄어듭니다.
- 텍스트 변경: `characterData`와 `subtree`를 씁니다.
- 레코드는 모여서 오므로 `addedNodes`를 순회하며 새 노드와 그 후손에서 대상을 찾습니다.
- Shadow DOM 안쪽의 변경은 바깥 노드의 `subtree`로 보이지 않으므로 ShadowRoot를 따로 관찰합니다(자세히는 21편). 슬롯에 들어오는 노드는 `slotchange` 이벤트가 더 알맞습니다(자세히는 22편).

```js
const mo = new MutationObserver((records) => {
  for (const r of records) {
    for (const n of r.addedNodes) {
      if (n.nodeType === 1 && n.matches('.ad')) n.remove()
    }
  }
})
mo.observe(document.body, {
  childList: true,
  subtree: true,
})
```

- 위 예에서 `remove()`가 다시 레코드를 만들 수 있으므로 조건이 맞을 때만 동작해 순환을 막습니다.
- 가능하면 `document.body` 전체보다 좁은 대상을 관찰합니다.

## Observer 정리와 생명주기

Observer는 만들면 끝이 아니라 정리까지 포함해서 설계합니다. 관찰을 멈추지 않으면 콜백이 계속 호출되고, 콜백이 잡은 값은 계속 유지됩니다(자세히는 67편).

| 정리 대상 | 호출 |
|-----------|------|
| 대상 하나 | `unobserve(el)` (IntersectionObserver, ResizeObserver) |
| 관찰자 전체 | `disconnect()` (모든 Observer) |
| 전달 전 레코드 | `takeRecords()` |

- 컴포넌트에서는 `connectedCallback`에서 관찰을 시작하고 `disconnectedCallback`에서 `disconnect()`합니다. 다시 연결될 수 있으므로 연결 때마다 `observe`합니다.
- 일회성 작업(지연 로딩, 처음 한 번만 보이면 되는 경우)은 처리 직후 `unobserve`합니다.
- 관찰자를 컴포넌트 필드로 만들어 두면 정리 시점에 참조할 수 있습니다. 지역 변수에만 두면 해제할 방법이 없습니다.
- 대상이 많을 때는 요소마다 관찰자를 만들지 않고 하나의 관찰자에 여러 대상을 `observe`합니다.

**흔한 실수:** `disconnectedCallback`에서 `disconnect()`를 빼먹어, 제거된 컴포넌트의 콜백이 계속 동작하며 메모리에 남는 것입니다.

## Observer를 이용한 렌더링 최적화

Observer는 스크롤·리사이즈 이벤트에서 레이아웃을 읽던 방식을 브라우저가 계산해 주는 값으로 바꿔 성능을 높입니다.

| 기존 방식 | Observer 방식 |
|-----------|---------------|
| `scroll` 이벤트에서 `getBoundingClientRect()` | IntersectionObserver |
| `window.resize`에서 요소 크기 읽기 | ResizeObserver |
| 타이머로 DOM 폴링 | MutationObserver |

- 화면 밖 요소의 애니메이션, 타이머, 캔버스 그리기는 IntersectionObserver로 멈추고 돌아오면 재개합니다.
- 변경이 잦은 DOM은 MutationObserver 콜백에서 레코드를 모아 한 번에 처리하고, 콜백 안에서 레이아웃을 강제하는 읽기를 피합니다.
- 콜백이 무거우면 필요한 값만 저장하고 실제 작업은 `requestAnimationFrame`이나 `requestIdleCallback`으로 넘깁니다.

### contentvisibilityautostatechange 이벤트

CSS `content-visibility: auto`를 쓴 요소는 화면 밖일 때 브라우저가 렌더링을 건너뜁니다. 이 상태가 바뀔 때 해당 요소에 `contentvisibilityautostatechange` 이벤트가 발생합니다. Baseline 2024입니다.

```js
el.style.contentVisibility = 'auto'
const type = 'contentvisibilityautostatechange'
el.addEventListener(type, (e) => {
  if (e.skipped) pauseWork(el) // 건너뛰는 중
  else resumeWork(el)
})
```

- 이벤트 타입은 `ContentVisibilityAutoStateChangeEvent`이고 `skipped`가 `true`이면 내용을 건너뛰는 중, `false`이면 렌더링하는 중입니다.
- IntersectionObserver는 뷰포트 겹침을, 이 이벤트는 브라우저가 렌더링을 건너뛰는지를 알려 줍니다. 건너뛰는 동안은 접근성 트리에는 남아 있습니다(MDN).
- 캔버스 그리기, 애니메이션, 타이머처럼 화면에 보이지 않을 때 멈출 작업에 씁니다(자세히는 66편).

## 핵심 정리

- IntersectionObserver는 `root`·`rootMargin`·`threshold`로 겹침 변화를 알려 주고, 관찰을 시작하면 첫 콜백이 한 번 호출되므로 `isIntersecting`을 확인합니다.
- ResizeObserver는 `box` 옵션과 배열 형태의 크기 필드로 요소 크기를 알려 주며, 콜백에서 관찰 대상의 크기를 바꾸면 루프 오류가 납니다.
- MutationObserver는 옵션 중 하나 이상이 `true`여야 하고 콜백은 마이크로태스크로 레코드를 모아 받으며, Mutation Events는 폐기되어 대체되었습니다.
- PerformanceObserver는 `type` 또는 `entryTypes`로 성능 엔트리를 구독하는 측정용 Observer입니다.
- 지연 로딩은 이미지·iframe이면 `loading="lazy"`가 기본이고, 요소 단위 동작은 IntersectionObserver로 구현합니다. 무한 스크롤은 센티널과 로딩 플래그로 만듭니다.
- Observer는 `connectedCallback`에서 시작하고 `disconnectedCallback`에서 `disconnect()`로 정리하며, 화면 밖 작업은 Observer와 `contentvisibilityautostatechange`로 멈춥니다.

## Promise 기반 UI 흐름

비동기 UI는 사용자 동작 → 요청 시작 → 상태 변경 → 응답 도착 → 상태 변경 → 화면 갱신의 흐름입니다. 요청은 Promise로 표현하고, 상태는 요청의 진행에 따라 직접 바꿉니다. 프라미스 자체의 문법은 ECMAScript 과목에서 다루고, 이 편은 그것을 UI 상태와 연결하는 방법을 다룹니다.

```js
button.addEventListener('click', async () => {
  setState({ status: 'loading' })
  try {
    const data = await repo.getUser(id)
    setState({ status: 'success', data })
  } catch (error) {
    setState({ status: 'error', error })
  }
})
```

- `setState`는 상태를 바꾸고 화면을 갱신하는 함수입니다(상태 설계는 31편, 요청 계층은 37편).
- `addEventListener`는 리스너가 돌려주는 프라미스를 기다리지 않습니다. 리스너 안에서 거부를 처리하지 않으면 처리되지 않은 거부가 되므로 `try`/`catch`를 반드시 둡니다.
- 요청 하나의 생애는 시작, 성공, 실패 세 갈래입니다. 어느 갈래로 끝나도 "진행 중" 표시가 꺼지도록 `catch`와 `finally`를 설계합니다.
- 응답은 요청을 보낸 순서가 아니라 도착한 순서로 처리됩니다. 이 점이 경쟁 상태의 원인입니다(아래 절).
- 사용자 입력이 계속 바뀌는 UI에서는 "이 응답이 지금 화면이 기다리는 응답인가"를 항상 확인해야 합니다.

## Loading / Success / Error

비동기 UI의 상태는 보통 네 가지입니다: 아직 시작하지 않음(idle), 진행 중(loading), 성공(success), 실패(error). 상태 하나(`status`)로 표현하면 불가능한 조합이 생기지 않습니다.

```js
// ❌ 불리언 여러 개: 로딩 중인데 에러가 있는 상태가 가능
const bad = { isLoading: true, error: err, data: null }
// ✅ status 하나: 항상 네 상태 중 하나
const good = { status: 'error', error: err, data: null }
```

| status | 화면 | 보관하는 값 |
|--------|------|-------------|
| `idle` | 안내 문구 또는 빈 화면 | 없음 |
| `loading` | 로딩 표시 | 이전 데이터(있다면) |
| `success` | 데이터 | `data` |
| `error` | 오류 메시지와 재시도 | `error`, 이전 데이터(있다면) |

- 성공했지만 결과가 비어 있는 상태(빈 상태)는 `success`의 하위 경우로 따로 그립니다(렌더링은 30편).
- 이미 데이터가 있는 화면을 새로고침할 때는 `loading`으로 바꾸며 데이터를 지우지 말고, 이전 데이터를 유지한 채 갱신 중 표시만 보여 줍니다. 화면이 깜빡이며 비는 것을 막습니다.
- 처음 불러오는 로딩과 갱신 로딩은 구분해서 표현합니다.
- 오류 상태에는 사용자에게 보일 메시지와 다시 시도할 방법(재시도 버튼)을 함께 둡니다.

### 로딩 표시 지연으로 깜빡임 막기

응답이 빠르면 로딩 표시가 잠깐 켜졌다 꺼져서 화면이 깜빡입니다. 로딩 표시를 일정 시간(예: 200ms) 뒤에 켜면 빠른 응답에서는 표시가 나타나지 않습니다.

```js
const timer = setTimeout(showSpinner, 200) // 빠르면 안 보임
try {
  return await task()
} finally {
  clearTimeout(timer)
  hideSpinner()
}
```

- 지연 시간은 앱이 정하는 값이며 표준이 있지 않습니다.
- 반대로 한 번 켠 표시는 최소 시간(예: 500ms)은 유지해서 번쩍이는 느낌을 줄이는 방법도 같이 씁니다.
- 레이아웃 높이가 바뀌어 화면이 밀리지 않게, 로딩 영역의 자리를 미리 확보하거나 스켈레톤(내용 모양의 자리표시자)을 둡니다(CLS는 65편).

### aria-busy와 로딩 상태 알림

화면을 보지 못하는 사용자에게는 상태 변화를 보조 기술로 알려야 합니다.

```html
<ul id="results" aria-busy="false"></ul>
<p role="status" id="msg"></p>
```

```js
results.ariaBusy = 'true'     // 갱신 시작
msg.textContent = '검색 중'
// ...응답 후 목록 갱신...
results.ariaBusy = 'false'    // 갱신 끝
msg.textContent = '3건을 찾았습니다'
```

- `aria-busy="true"`는 요소가 갱신 중임을 알려, 보조 기술이 갱신이 끝날 때까지(`false`가 될 때까지) 변경 알림을 미룹니다. `Element.ariaBusy` 프로퍼티는 Baseline 2023이며 값은 문자열 `'true'`·`'false'`입니다.
- `role="status"`는 암묵적으로 `aria-live="polite"`와 `aria-atomic="true"`를 가진 라이브 영역으로, 로딩 중·완료 같은 급하지 않은 상태를 읽어 줍니다. 급한 오류는 `role="alert"`를 씁니다.
- 라이브 영역은 내용이 바뀌기 전에 DOM에 있어야 알림이 갑니다. 상태 메시지 요소는 처음부터 두고 텍스트만 바꿉니다.
- 상태 메시지를 위해 포커스를 옮기지 않습니다.
- 오류로 끝났을 때도 `aria-busy`를 `false`로 되돌려야 합니다. `finally`에서 처리합니다.
- 라이브 영역과 접근성 전반은 27편에서 다룹니다.

## Race Condition

경쟁 상태(race condition)는 비동기 작업들이 끝나는 순서에 따라 결과가 달라지는 문제입니다. UI에서는 먼저 보낸 요청의 응답이 나중에 도착해 최신 응답을 덮어쓰는 형태로 나타납니다.

```js
async function onInput(q) {
  const res = await fetch(`/search?q=${q}`)
  render(await res.json()) // 도착 순서대로 화면을 덮어씀
}
// 'a' 요청이 느리고 'ab' 요청이 빠르면 마지막에 'a' 결과가 남음
```

- 입력창은 'ab'인데 결과는 'a'의 것이 보이는 상태가 됩니다.
- 네트워크 지연은 요청마다 달라서 보낸 순서와 응답 순서가 같다는 보장이 없습니다. 개발 환경(빠르고 안정적인 네트워크)에서는 재현되지 않다가 운영에서 나타납니다.
- 같은 문제는 검색, 탭 전환, 페이지 이동, 필터 변경처럼 입력이 연달아 바뀌는 모든 곳에서 생깁니다.
- 해결의 원칙은 응답이 도착했을 때 "지금도 이 응답이 필요한가"를 확인하고, 필요 없으면 버리는 것입니다. 방법은 아래 두 가지(최신 요청 판별, 이전 요청 취소)이며 함께 씁니다.

## 최신 요청만 반영하기

요청마다 번호를 매기고, 응답이 왔을 때 자기 번호가 가장 최신인지 비교해 아니면 무시합니다. 취소 신호를 받지 않는 작업에도 쓸 수 있습니다.

```js
let seq = 0
async function search(q) {
  const id = ++seq
  const data = await load(q)
  if (id !== seq) return // 그사이 더 새 요청이 있었음
  render(data)
}
```

- 오래된 응답은 도착은 하지만 화면에는 반영되지 않습니다. 요청은 그대로 끝까지 진행되므로 네트워크 낭비는 남습니다.
- 로딩 상태도 같은 기준으로 다룹니다. 오래된 요청의 `finally`가 로딩 표시를 꺼 버리면 최신 요청이 진행 중인데 로딩이 사라지므로, `finally`에서도 `id === seq`일 때만 끕니다.
- 번호 대신 요청마다 만든 고유 객체를 `current`에 저장하고 `current === mine`으로 비교해도 같습니다.
- 입력값이 바뀌었는지를 직접 비교(`q === input.value`)하는 방식은 입력이 같은 값으로 되돌아간 경우 오래된 응답을 허용할 수 있어, 번호 방식이 더 정확합니다.

## AbortController로 이전 요청 취소

새 요청을 시작할 때 이전 요청을 취소하면 오래된 응답이 아예 오지 않고 네트워크 낭비도 줄입니다(AbortController는 37편).

```js
let ctrl
async function search(q) {
  ctrl?.abort()                   // 이전 요청 취소
  ctrl = new AbortController()
  const { signal } = ctrl
  try {
    const data = await load(q, { signal })
    if (!signal.aborted) render(data)
  } catch (e) {
    if (e.name !== 'AbortError') showError(e)
  }
}
```

- 취소된 요청은 `AbortError`로 거부되며 의도한 취소이므로 오류 화면을 띄우지 않고 무시합니다.
- 신호를 받지 않는 작업이나 이미 응답을 다 받은 뒤의 지점에는 취소가 닿지 않으므로, 화면에 반영하기 직전에 `signal.aborted`를 한 번 더 검사합니다.
- 취소해도 서버가 요청을 이미 처리 중일 수 있어서, 읽기 요청에 쓰고 쓰기 요청에는 신중해야 합니다.
- `finally`로 로딩을 끄는 코드에서는 취소된 요청이 최신 요청의 로딩 표시를 끄지 않게 `signal.aborted`를 검사합니다.
- 번호 방식과 취소는 대체가 아니라 겹쳐 쓰는 방어선입니다. 취소가 요청 자원을 줄이고, 번호나 `aborted` 검사가 마지막 반영을 막습니다.

## 컴포넌트 제거 후 응답 처리 방지

컴포넌트가 DOM에서 빠진 뒤에 응답이 도착해 상태를 바꾸거나 DOM을 갱신하면 오류가 나거나 낭비가 생기고, 사라진 컴포넌트가 참조를 붙들어 메모리 누수가 됩니다. 제거될 때 진행 중인 요청을 취소합니다.

```js
class UserCard extends HTMLElement {
  #ac = new AbortController()
  connectedCallback() {
    this.#ac = new AbortController() // 재연결마다 새로
    this.#load(this.#ac.signal)
  }
  disconnectedCallback() {
    this.#ac.abort() // 제거되면 요청 취소
  }
}
```

- `connectedCallback`에서 컨트롤러를 새로 만드는 이유는 같은 요소가 DOM에서 빠졌다 다시 붙을 수 있고, 취소된 컨트롤러는 재사용할 수 없기 때문입니다(생명주기는 18편).
- `#load`에서는 응답 처리 전에 `signal.aborted`를 검사합니다. 신호를 받지 않는 작업에는 `this.isConnected`로 검사할 수도 있습니다.
- 타이머, 디바운스 대기 중인 호출, 이벤트 리스너도 같은 시점에 정리합니다. 리스너는 같은 컨트롤러의 `signal` 옵션으로 한꺼번에 제거할 수 있습니다(정리 전반은 67편).
- 전체 요청을 취소하기보다 응답만 무시하고 싶다면(예: 캐시를 채우는 요청) 취소하지 않고 `isConnected` 검사만 둡니다.

## Debounced Search

디바운스(debounce)는 입력이 멈추고 일정 시간이 지났을 때만 함수를 실행해, 타이핑마다 요청을 보내는 것을 막습니다. 디바운스의 원리는 08편에서 다루고, 여기서는 검색에 적용합니다.

```js
function debounce(fn, ms) {
  let id
  return (...args) => {
    clearTimeout(id)
    id = setTimeout(() => fn(...args), ms)
  }
}
const run = debounce((q) => search(q), 300)
input.addEventListener('input', (e) => run(e.target.value))
```

- 디바운스는 요청 횟수를 줄일 뿐 경쟁 상태를 없애지 못합니다. 지연이 지난 뒤 연달아 나간 요청들은 여전히 순서가 뒤바뀔 수 있으므로 `search` 안에 취소나 최신 판별이 필요합니다.
- 지연 시간(수백 ms 단위가 흔함)은 앱이 정합니다. 짧으면 요청이 많고 길면 반응이 느립니다.
- 입력이 비면 대기 중인 호출을 버리고 진행 중 요청도 취소해서 목록을 비웁니다.
- 직전에 검색한 값과 같으면 요청하지 않습니다. 앞뒤 공백을 `trim()`한 값을 비교합니다.
- 엔터나 검색 버튼은 디바운스를 거치지 않고 바로 실행합니다.
- 한글 같은 조합 입력은 조합 중에도 `input` 이벤트가 오므로, 조합이 끝난 뒤에만 검색하려면 `isComposing`을 확인합니다(자세히는 10편).
- 컴포넌트가 제거될 때 대기 중인 타이머를 `clearTimeout`으로 지웁니다. 디바운스 함수에 `cancel` 메서드를 달아 두면 편합니다.

## Optimistic UI

낙관적 UI(Optimistic UI)는 서버 응답을 기다리지 않고 성공할 것으로 가정하고 화면을 먼저 바꾼 뒤, 실패하면 되돌리는 방식입니다. 좋아요, 체크 토글, 목록 추가처럼 성공 확률이 높고 되돌릴 수 있는 동작에서 체감 속도를 높입니다.

```js
async function toggleLike(post) {
  const prev = post.liked
  setLiked(post.id, !prev)           // 먼저 반영
  try {
    await api.setLiked(post.id, !prev)
  } catch (err) {
    setLiked(post.id, prev)          // 실패하면 롤백
    toast('실패했습니다. 다시 시도해 주세요')
  }
}
```

### 낙관적 업데이트 롤백 설계

- **되돌릴 값을 먼저 보관합니다.** 이전 값을 지역 변수에 잡아 두거나, 되돌리는 동작(역연산)을 함께 만듭니다.
- **전체 스냅샷으로 롤백하면 다른 변경을 지웁니다.** 그사이 다른 낙관적 업데이트가 있었다면 요청별로 해당 항목만 되돌립니다. 아니면 실패 시 서버 상태를 다시 불러와 맞춥니다.
- **같은 항목의 동시 변경은 순서를 지킵니다.** 항목별로 요청을 줄 세우거나 이전 요청이 끝나기 전에는 막습니다. 아니면 늦게 끝난 요청이 최신 값을 덮어씁니다.
- **서버가 정한 값으로 바꿉니다.** 성공 응답에 서버가 만든 id나 갱신 시각이 있으면 임시 값을 그것으로 교체합니다. 임시 항목에는 "저장 중" 표시를 둡니다.
- **실패를 알립니다.** 조용히 되돌리면 사용자는 영문을 모릅니다. 메시지와 재시도 수단을 줍니다.
- **네트워크 오류는 재시도할 수 있습니다.** 요청이 멱등이면 자동 재시도 후에도 실패할 때 롤백합니다(37편).
- **쓰지 않을 곳:** 결제, 삭제 확정처럼 되돌릴 수 없거나 서버 검증 결과에 따라 화면이 크게 달라지는 동작은 응답을 기다린 뒤 반영합니다.

## 동시 요청 조합

화면 하나가 여러 데이터를 필요로 하면 독립적인 요청은 동시에 보냅니다. 하나씩 `await`하면 서로 기다리는 폭포(waterfall)가 되어 전체 시간이 합산됩니다.

```js
// ❌ 순차: 시간 = a + b
const user = await getUser(id)
const posts = await getPosts(id)
// ✅ 동시: 시간 = max(a, b)
const [user2, posts2] = await Promise.all([
  getUser(id),
  getPosts(id),
])
```

- 두 번째 요청이 첫 번째 응답 값을 필요로 하면 순차가 맞습니다. 그렇지 않은 요청만 동시로 보냅니다.
- 동시에 보낼 수 있는 요청 수에는 브라우저와 서버의 한계가 있으므로, 목록 항목마다 요청하는 식으로 많아지면 개수를 제한합니다.
- 요청마다 경쟁 상태와 취소를 따로 챙길 필요가 없도록, 신호 하나를 공유해 한꺼번에 취소합니다.

### Promise.all / allSettled

| 메서드 | 이행 조건 | 거부 조건 | 결과 |
|--------|-----------|-----------|------|
| `Promise.all` | 모두 이행 | 하나라도 거부(즉시) | 입력 순서의 값 배열 |
| `Promise.allSettled` | 모두 끝남(성공·실패 무관) | 거부되지 않음 | `status`와 `value`·`reason`을 가진 객체 배열 |
| `Promise.race` | 처음 끝난 것이 이행 | 처음 끝난 것이 거부 | 처음 끝난 결과 |
| `Promise.any` | 처음 이행된 것 | 모두 거부(`AggregateError`) | 처음 이행된 값 |

- `Promise.all`의 결과 순서는 완료 순서가 아니라 입력 순서입니다. 하나가 거부되면 바로 거부되지만 나머지 요청이 취소되지는 않고 계속 진행됩니다. 취소하려면 신호를 공유해 직접 `abort()`합니다.

```js
const ac = new AbortController()
try {
  const [user, posts] = await Promise.all([
    getUser(id, { signal: ac.signal }),
    getPosts(id, { signal: ac.signal }),
  ])
} catch (e) {
  ac.abort() // 남은 요청 정리
  throw e
}
```

- `Promise.allSettled`는 일부가 실패해도 성공한 부분을 쓸 수 있을 때 씁니다. 대시보드처럼 위젯이 서로 독립적이면 실패한 위젯만 오류를 보여 주고 나머지는 정상 표시합니다.

```js
const rs = await Promise.allSettled([a(), b(), c()])
rs.forEach((r, i) => {
  if (r.status === 'fulfilled') show(i, r.value)
  else showError(i, r.reason)
})
```

- 서로 필수 관계인 데이터(둘 다 있어야 화면이 성립)는 `Promise.all`, 부분 표시가 가능하면 `allSettled`를 고릅니다.
- `Promise.race`로 타임아웃을 만들면 지고 난 요청이 계속 진행되므로, 요청 타임아웃은 신호의 `AbortSignal.timeout()`을 씁니다(37편). `Promise.any`는 같은 데이터를 여러 곳에서 받을 때 가장 빠른 성공을 쓰는 용도입니다.
- 빈 배열을 넣으면 `all`과 `allSettled`는 바로 빈 배열로 이행하고, `race`는 영원히 대기하며, `any`는 거부됩니다.

## 비동기 Error Boundary 패턴

브라우저에는 React의 Error Boundary 같은 컴포넌트 단위 오류 경계가 내장되어 있지 않습니다. 비동기 오류를 잡아 그 컴포넌트의 오류 상태로 바꾸는 경계를 직접 만듭니다. 경계는 `try`/`catch`를 한 곳에 모아, 컴포넌트가 로딩·성공·오류를 같은 방식으로 다루게 하는 래퍼입니다.

```js
async #run(task) {
  this.#set({ status: 'loading' })
  try {
    this.#set({ status: 'success', data: await task() })
  } catch (e) {
    if (e.name === 'AbortError') return // 의도한 취소
    this.#set({ status: 'error', error: e })
  }
}
// 재시도 버튼: this.#run(() => repo.getUser(id))
```

- 경계는 위젯 단위로 둡니다. 한 위젯의 실패가 페이지 전체를 오류 화면으로 만들지 않게 하고, 각 위젯이 재시도 수단을 갖습니다.
- 오류 화면은 사용자가 할 수 있는 일(재시도, 돌아가기)을 보여 줍니다. 오류의 종류(네트워크, 시간 초과, 서버 오류, 권한)는 데이터 계층에서 정규화해 두면 경계가 종류별로 메시지를 고를 수 있습니다(37편).
- `AbortError`는 오류가 아니라 취소이므로 경계에서 무시합니다.
- 재시도할 때는 이전 오류를 지우고 `loading`으로 돌아갑니다. 같은 경계가 처음 실행과 재시도를 같은 함수로 처리하게 합니다.
- 처리하지 않은 프라미스 거부가 새어 나가는 경우를 위해 최후의 방어선을 둡니다. `window`의 `unhandledrejection` 이벤트는 거부 핸들러가 없을 때 발생하며 `event.reason`으로 이유를 얻고, `event.preventDefault()`로 콘솔 오류 출력을 막을 수 있습니다.

```js
addEventListener('unhandledrejection', (e) => {
  report(e.reason) // 로깅 서비스로 전송
})
```

- 이 이벤트는 로깅과 계측용이며 화면 복구용이 아닙니다. 복구는 각 경계가 맡습니다.
- 워커에서도 같은 이벤트가 있습니다. 교차 출처 스크립트에서 난 거부는 정보 노출을 막으려고 이 이벤트로 오지 않습니다.

## 핵심 정리

- 비동기 UI는 요청의 시작·성공·실패를 상태로 옮기는 흐름이며, 상태는 불리언 여러 개 대신 `status` 하나로 표현하고 `finally`로 로딩 표시를 반드시 끕니다.
- 경쟁 상태는 응답 도착 순서가 요청 순서와 달라 오래된 응답이 최신 응답을 덮어쓰는 문제이며, 요청 번호 비교와 이전 요청 취소를 겹쳐 막습니다.
- 컴포넌트가 제거되면 진행 중인 요청을 취소하고, 재연결을 위해 연결할 때마다 컨트롤러를 새로 만듭니다.
- 디바운스는 요청 수를 줄일 뿐 경쟁 상태를 없애지 못하고, 낙관적 업데이트는 되돌릴 값을 보관하고 실패를 알리는 롤백을 설계해야 합니다.
- 독립 요청은 `Promise.all`로 동시에 보내되 실패가 나머지를 취소하지 않으므로 신호를 공유하고, 부분 성공이 허용되면 `Promise.allSettled`를 씁니다.
- 로딩 표시는 지연으로 깜빡임을 줄이고 `aria-busy`·`role="status"`로 알리며, 비동기 오류는 위젯 단위 경계에서 잡고 `unhandledrejection`은 최후의 로깅에 씁니다.

## Observable 상태 개념

Observable 상태는 값을 보관하면서 값이 바뀌면 구독자에게 알리는 객체입니다. 옵저버 패턴이며 반응형 구조의 가장 단순한 형태입니다.

```js
function createStore(initial) {
  let value = initial
  const subs = new Set()
  const set = (next) => {
    if (Object.is(next, value)) return
    value = next
    subs.forEach((fn) => fn(value))
  }
  const subscribe = (fn) => {
    subs.add(fn)
    return () => subs.delete(fn)
  }
  return { get: () => value, set, subscribe }
}
```

- 값이 같으면(`Object.is`) 알리지 않아서 불필요한 갱신을 막습니다.
- `subscribe`가 해제 함수를 돌려주므로 요소가 DOM에서 떼어질 때 구독을 끊을 수 있습니다. 끊지 않으면 떼어진 요소가 계속 호출됩니다(자세히는 18편).
- 한계: 누가 어떤 값에 의존하는지 사람이 직접 구독해야 합니다. 파생값이 늘면 구독 연결이 늘어납니다.
- "Observable"이라는 이름은 이 개념 외에 웹 플랫폼의 `Observable` API(뒤의 절)와 RxJS 같은 라이브러리의 이름으로도 쓰입니다. 개념과 API를 구분합니다.

## Signal 개념

Signal은 현재 값 하나를 담는 반응형 값 상자이고, 읽는 동작이 자동으로 의존성으로 기록되는 점이 Observable 상태와 다릅니다. 스트림(시간에 따른 값의 흐름)이 아니라 "지금의 값" 하나를 나타냅니다.

```js
const count = signal(0)   // 값 상자
count.get()               // 0 (읽는 순간 의존성 기록)
count.set(1)              // 의존하는 계산과 effect에 알림
```

- 상태 Signal은 쓰기 가능한 값이고, Computed는 다른 Signal에서 계산된 읽기 전용 값입니다.
- 구독 코드가 없습니다. effect나 computed 안에서 `get()`을 부르기만 하면 연결됩니다(의존성 추적 절).
- 연속으로 두 번 `set`하면 중간 값을 관찰하지 못하고 최종 값만 반영됩니다. Signal은 값의 이력이 아니라 현재 값을 나타냅니다.
- 표준화 제안은 TC39 Signals입니다(뒤의 절).

## Proxy 기반 반응성

Proxy 반응성은 객체를 `Proxy`로 감싸고, `get` 트랩에서 읽기를 추적하고 `set` 트랩에서 변경을 알리는 방식입니다. 상태를 일반 객체처럼 쓸 수 있습니다.

```js
function reactive(target) {
  return new Proxy(target, {
    get(t, key, r) {
      track(t, key)
      const v = Reflect.get(t, key, r)
      return typeof v === 'object' && v ? reactive(v) : v
    },
    set(t, key, value, r) {
      const ok = Reflect.set(t, key, value, r)
      trigger(t, key)
      return ok
    },
  })
}
```

- `set` 트랩은 성공을 뜻하는 `true`를 반환해야 합니다. 엄격 모드에서 `false`는 TypeError입니다.
- 중첩 객체는 자동으로 감싸지지 않습니다. 위 코드처럼 읽을 때 감쌉니다. 읽을 때마다 새 프록시를 만들지 않도록 `WeakMap`으로 캐시합니다.
- 프록시는 원본과 다른 객체입니다(`proxy !== target`). 원본을 직접 고치면 변경이 감지되지 않습니다.
- 프록시는 private 필드와 내부 슬롯에 접근하지 못합니다. `Map`, `Set`, `Date` 같은 내장 객체는 메서드를 호출할 때 `this`가 프록시이면 TypeError이므로 메서드를 원본에 바인딩해서 꺼냅니다.
- 속성 추가·삭제·`in`·`Object.keys`를 추적하려면 `set` 외에 `has`, `deleteProperty`, `ownKeys` 트랩이 필요합니다.
- Baseline 2016입니다(자세히는 ECMAScript 과목의 Proxy 편).

**흔한 실수:** 프록시 안의 값을 구조 분해로 꺼내서 쓰면 원시 값 복사본이 되어 이후 변경을 따라가지 못합니다.

## Getter / Setter 기반 반응성

접근자 기반 반응성은 속성마다 `get`/`set`을 정의해서 읽기와 쓰기를 가로채는 방식입니다. 클래스 접근자나 `Object.defineProperty`로 만듭니다.

```js
class Counter {
  #n = 0
  get n() { track(this, 'n'); return this.#n }
  set n(v) {
    if (Object.is(v, this.#n)) return
    this.#n = v
    trigger(this, 'n')
  }
}
```

- 접근자는 속성을 정의한 시점에 이미 있는 이름만 가로챕니다. 나중에 추가한 속성이나 삭제는 감지하지 못합니다.
- private 필드에 값을 두므로 Proxy와 달리 내장 객체나 `this` 문제가 없고 동작이 예측 가능합니다. 대신 속성마다 접근자를 직접 써야 해서 상용구가 늘어납니다.
- 컴포넌트의 공개 프로퍼티(자세히는 19편)는 보통 이 방식입니다. 프로퍼티 설정자에서 `requestRender()`를 호출하는 구조입니다.

## Dependency Tracking

의존성 추적은 계산이 실행되는 동안 읽은 값을 자동으로 기록해서, 그 값이 바뀔 때만 계산을 다시 실행하게 하는 장치입니다. "지금 실행 중인 계산"을 전역 변수 하나에 두고, 읽기 때 그 계산을 구독자로 등록합니다.

```js
let active = null            // 지금 실행 중인 effect
const deps = new WeakMap()   // 객체 → 키 → 구독자 집합
function track(t, k) {
  if (!active) return
  let m = deps.get(t) ?? deps.set(t, new Map()).get(t)
  let s = m.get(k) ?? m.set(k, new Set()).get(k)
  s.add(active)
}
function trigger(t, k) {
  deps.get(t)?.get(k)?.forEach(schedule)
}
```

- 의존성은 실행할 때마다 달라질 수 있습니다. `if (a.get()) b.get()`에서 `a`가 거짓이면 `b`는 의존성이 아닙니다. 그래서 실행 전에 이전 구독을 지우고 다시 모읍니다.
- 구독 집합은 `WeakMap`으로 객체에 매달아 객체가 사라지면 함께 정리되게 합니다.
- 비동기 코드(`await` 뒤)에서 읽은 값은 `active`가 이미 해제되어 추적되지 않습니다. 필요한 값은 `await` 전에 읽습니다.
- 추적하지 않고 읽는 탈출구가 `untrack`(또는 `peek`)입니다. TC39 제안도 `untrack`을 제공하면서 안전하지 않다고 명시합니다.

## Effect

Effect는 함수를 즉시 한 번 실행하고, 그 함수가 읽은 값이 바뀔 때마다 다시 실행하는 부수 효과 단위입니다. DOM 쓰기, 로그, 저장, 요청 같은 바깥 세계와의 연결을 맡습니다.

```js
function effect(fn) {
  let alive = true
  const run = () => {
    if (!alive) return
    const prev = active
    active = run
    try { fn() } finally { active = prev }
  }
  run()
  return () => { alive = false } // 해제 함수
}
effect(() => { label.textContent = count.get() })
count.set(5) // label이 갱신됨
```

- 첫 실행에서 의존성을 수집합니다. 이후에는 의존 값이 바뀔 때마다 예약됩니다.
- 해제 방법이 있어야 합니다. 컴포넌트가 떼어질 때 effect를 멈추지 않으면 계속 실행됩니다. 실제 구현은 해제 함수를 반환하고 이전 실행의 정리(cleanup) 함수를 지원합니다.
- 예외는 `try`/`finally`로 `active`를 복구해야 합니다. 복구하지 않으면 이후 모든 읽기가 잘못된 effect에 연결됩니다.
- TC39 제안은 `effect` 함수를 일부러 포함하지 않습니다. 실행 시점이 프레임워크의 렌더링 주기와 얽혀 있기 때문입니다.

## Computed / Derived State

Computed는 다른 값에서 계산되는 값으로, 읽을 때 필요하면 계산하고 결과를 캐시합니다. 의존 값이 바뀌면 캐시를 무효화만 하고, 다시 읽는 순간에 계산합니다(지연 평가).

```js
function computed(fn) {
  let value, dirty = true
  const subs = new Set()
  const self = () => { dirty = true; subs.forEach(notify) }
  self.sync = true
  return { get() {
    if (active) subs.add(active)
    if (dirty) {
      const prev = active; active = self
      try { value = fn() } finally { active = prev }
      dirty = false
    }
    return value
  } }
}
```

- 의존 값이 바뀌어도 아무도 읽지 않으면 계산하지 않습니다. 여러 번 읽어도 의존 값이 같으면 재계산하지 않습니다(메모이제이션).
- 무효화는 즉시(동기) 처리해야 합니다. 그래야 값을 바꾼 직후에 읽어도 최신 값이 나옵니다. effect만 모아서 나중에 실행합니다(`notify`는 다음 절의 배치에서 정의).
- 계산 함수는 순수해야 합니다. DOM이나 다른 상태를 쓰면 언제 몇 번 실행되는지 보장되지 않아 결과가 불안정해집니다.
- 파생값을 별도 상태로 복사해서 effect로 동기화하는 대신 computed로 선언합니다. 두 값이 어긋날 일이 없습니다(자세히는 32편).
- TC39 제안의 Computed도 지연 평가와 캐시를 정의하고, 불필요한 계산이 없는 글리치 없는 실행을 목표로 합니다.

## Batching

배치는 여러 번의 상태 변경을 모아서 effect를 한 번만 실행하는 것입니다. 변경 시점이 아니라 변경이 끝난 시점에 한 번 반영합니다.

```js
const queue = new Set()
let scheduled = false
const notify = (s) => (s.sync ? s() : schedule(s))
function schedule(fx) {
  queue.add(fx)
  if (scheduled) return
  scheduled = true
  queueMicrotask(() => {
    scheduled = false
    const batch = [...queue]
    queue.clear()
    batch.forEach((fx) => fx())
  })
}
```

- 집합(`Set`)이 같은 effect의 중복 예약을 하나로 합칩니다.
- 실행 시점을 microtask로 두면 같은 이벤트 처리 안의 변경이 합쳐지고 화면을 그리기 전에 반영됩니다(자세히는 30편, 08편).
- 중간 상태가 렌더에 노출되지 않습니다. `a`를 바꾼 뒤 `b`를 바꾸는 사이의 어긋난 조합이 화면에 나타나지 않습니다.
- TC39 제안은 변경 알림(`Watcher`의 `notify`)을 `set` 도중에 동기로 호출하고, 그 안에서는 Signal을 읽거나 쓰지 못하게 합니다. 실제 실행은 프레임워크가 알맞은 시점으로 미룹니다.
- 배치를 우회해 즉시 반영하려면 별도의 동기 flush 함수를 제공합니다. 일반 코드가 쓸 일은 드뭅니다.

## 상태 변경 루프 방지

루프는 effect가 자신이 읽은 값을 다시 써서 자기 자신을 예약하는 구조에서 생깁니다. 마이크로태스크가 계속 추가되면 큐가 끝나지 않아 화면이 멈춥니다.

```js
// ❌ count를 읽고 쓰는 effect: 끝나지 않음
effect(() => count.set(count.get() + 1))
// ✅ effect는 읽기만, 쓰기는 이벤트 핸들러에서
effect(() => { label.textContent = count.get() })
button.onclick = () => count.set(count.get() + 1)
```

방지책은 다음과 같습니다.

- 같은 값이면 알리지 않습니다. `Object.is`로 비교하면 수렴하는 갱신(`set(Math.min(v, 10))`)은 저절로 멈춥니다.
- 파생값은 effect에서 상태에 써 넣지 말고 computed로 만듭니다.
- effect 안에서 읽기만 하고 싶은 값은 추적하지 않고 읽습니다(`untrack`).
- 두 값을 양방향으로 맞추는 코드는 한쪽 갱신이 다른 쪽을 되돌리지 않도록 같은 값 비교나 진행 중 플래그를 둡니다.
- 방어선으로 한 갱신 주기에서 같은 effect의 실행 횟수에 상한을 두고 넘으면 에러를 던집니다.
- Lit에서는 `updated()` 안에서 속성을 바꾸면 갱신이 한 번 더 일어나므로 같은 이유로 주의하라고 안내합니다.
- TC39 제안 문서도 `notify`가 예약한 작업이 Signal을 읽고 쓸 수 있어서 effect 안에서 상태를 쓰는 안티패턴이 재현될 수 있다고 경고합니다.

## 렌더링과 Effect 분리

렌더링은 현재 상태를 화면으로 바꾸는 순수한 함수이고, effect는 그 함수를 "언제 다시 부를지" 정하는 연결 장치입니다. 둘을 나누면 각각 시험하고 바꿀 수 있습니다.

```js
class TodoView extends HTMLElement {
  #stop = []
  connectedCallback() {
    this.#stop.push(effect(() => this.render(todos.get())))
    this.#stop.push(effect(() => save(todos.get())))
  }
  disconnectedCallback() {
    this.#stop.forEach((stop) => stop())
    this.#stop = []
  }
  render(list) { /* 상태 → DOM만 */ }
}
```

- `render`는 상태를 받아 DOM만 고칩니다. 요청, 저장, 로그를 넣지 않습니다(자세히는 30편).
- 관심사마다 effect를 따로 둡니다. 렌더 effect와 저장 effect가 서로의 의존성을 오염시키지 않습니다.
- effect는 연결될 때 만들고 떼어질 때 해제합니다. 요소가 다시 붙을 수 있으므로 `connectedCallback`에서 새로 만들고 `disconnectedCallback`에서 정리하는 짝을 지킵니다(자세히는 18편).

## 작은 Reactive Core 직접 구현

위 조각을 합치면 작은 반응형 코어가 됩니다. Signal, Computed, Effect와 배치 큐로 구성됩니다.

```js
function signal(v) {
  const subs = new Set()
  return {
    get() { if (active) subs.add(active); return v },
    set(n) {
      if (Object.is(n, v)) return
      v = n
      subs.forEach(notify)
    },
  }
}
```

`active`, `notify`, `schedule`, `effect`, `computed`는 앞 절의 코드를 그대로 씁니다. 사용 예는 다음과 같습니다.

```js
const price = signal(10)
const qty = signal(2)
const total = computed(() => price.get() * qty.get())
effect(() => { out.textContent = total.get() }) // 20
price.set(20)
qty.set(3)
// 마이크로태스크 뒤 effect 1회 실행: 60
```

- `set` 두 번에 effect는 한 번만 실행됩니다. `total`은 `set`마다 즉시 무효화되고 effect만 모아서 실행됩니다.
- 이 구현은 학습용입니다. 실행마다 이전 구독을 지우지 않아서 조건 분기에 따라 의존성이 달라지면 낡은 구독이 남고, 순환 감지와 해제 처리도 없습니다. 실제 서비스에는 검증된 구현을 씁니다.

## TC39 Signals 제안 상태

TC39 Signals는 Signal을 JavaScript 언어에 내장하자는 제안입니다. 제안 저장소 기준으로 Stage 1입니다. 저장소는 Stage 2를 요청하기 전에 여러 프레임워크에 통합해 보는 시험을 충분히 하겠다는 계획을 밝힙니다. 엔진에 내장돼 있지 않고 폴리필로만 써 볼 수 있습니다.

```js
const count = new Signal.State(0)
const doubled = new Signal.Computed(() => count.get() * 2)
const w = new Signal.subtle.Watcher(() => {
  console.log('변경됨') // 읽기·쓰기 금지, 예약만
})
w.watch(doubled)
count.set(5) // notify 콜백이 동기로 호출됨
```

- 구성: `Signal.State`(쓰기 가능), `Signal.Computed`(지연·캐시), `Signal.subtle.Watcher`(변경 알림), `Signal.subtle.untrack`.
- 같은 값 판정의 기본은 `Object.is`이고 `equals` 옵션으로 바꿉니다.
- 내장 `effect`는 없습니다. Watcher의 `notify`로 프레임워크가 직접 만듭니다.
- `notify`는 `set` 도중에 동기 호출되고 그 안에서 Signal을 읽거나 쓸 수 없습니다.

## Observable API (Chromium 전용)

웹 플랫폼의 `Observable`은 이벤트나 값의 흐름을 구독하고 연산자로 가공하는 객체입니다. 앞의 Signal과 달리 "현재 값"이 아니라 시간에 따른 값의 스트림입니다.

```js
if ('Observable' in globalThis) {
  box.when('pointermove')
    .filter((e) => e.buttons === 1)
    .map((e) => e.clientX)
    .subscribe((x) => { bar.style.left = `${x}px` })
}
```

- 만드는 방법은 `new Observable(subscriber => ...)`, `EventTarget`의 `when(type)`, `Observable.from()`입니다. 구독자에는 `next()`, `error()`, `complete()`, `addTeardown()`이 있습니다.
- 연산자로 `map`, `filter`, `take`, `drop`, `flatMap`, `switchMap`, `catch`, `finally`, `takeUntil` 등이 있습니다.
- 지원 상태: Chrome·Edge 135부터이며 다른 엔진은 지원하지 않아 Baseline이 아닙니다. MDN은 실험적 기능으로 분류합니다. 점진적 향상으로만 쓰고 기능 검사 뒤에 사용합니다.
- 이벤트 스트림 처리에 알맞고 상태 값 자체의 반응성에는 Signal이 알맞습니다.

## EventTarget 기반 변경 알림

`EventTarget`을 상속하면 별도 라이브러리 없이 표준 이벤트 API로 Observable 상태를 만들 수 있습니다. 생성자는 직접 호출하거나 상속해서 쓸 수 있고 Baseline 2020입니다.

```js
class Store extends EventTarget {
  #s = { count: 0 }
  get state() { return this.#s }
  set(patch) {
    this.#s = { ...this.#s, ...patch }
    this.dispatchEvent(
      new CustomEvent('change', { detail: this.#s }))
  }
}
```

- 구독은 `addEventListener('change', fn)`이고 해제는 `removeEventListener`나 `{ signal }` 옵션, `{ once: true }`로 합니다(자세히는 07편).
- `dispatchEvent`는 리스너를 동기로 실행합니다. 배치가 필요하면 알림을 `queueMicrotask`로 모읍니다.
- DOM 노드가 아니므로 버블링은 없고 이름으로 구독합니다. 상태 객체를 새로 교체해서 이전 값과 `Object.is`로 비교할 수 있게 합니다.
- 의존성 추적이 없어서 파생값은 직접 구독해 다시 계산합니다.

## 반응성 방식 비교표

| 방식 | 추적 단위 | 추적 방법 | 새 속성 | 내장 객체 | 표준 상태 |
|------|-----------|-----------|---------|-----------|-----------|
| Proxy | 객체의 모든 접근 | `get`/`set` 트랩 | 감지 가능(`has`, `ownKeys` 트랩) | `this` 바인딩 필요 | Baseline 2016 |
| Getter / Setter | 선언한 속성 | 접근자 | 감지 불가 | 영향 적음 | 언어 기본 기능 |
| Signal | 값 상자 하나 | `get()` 호출 | 값 상자를 새로 만듦 | 영향 없음 | TC39 Stage 1 |
| EventTarget | 직접 지정한 이벤트 | 수동 구독 | 해당 없음 | 해당 없음 | Baseline 2020 |
| Observable API | 이벤트 흐름 | `subscribe` | 해당 없음 | 해당 없음 | Chromium 전용 |

- 구분 기준: 읽기를 자동으로 추적하는지(Proxy, 접근자, Signal)와 구독을 직접 하는지(EventTarget, Observable).
- 객체 전체를 일반 객체처럼 쓰고 싶으면 Proxy, 속성이 정해진 컴포넌트 필드에는 접근자, 개별 값과 파생값 그래프에는 Signal, 이벤트 처리와 외부 알림에는 EventTarget이나 Observable이 알맞습니다.

## 핵심 정리

- Observable 상태는 변경을 구독자에게 알리는 객체이고, Signal은 읽기가 자동으로 의존성으로 기록되는 값 상자입니다.
- Proxy는 객체 전체의 읽기·쓰기를 트랩으로 추적하지만 중첩 객체와 내장 객체에 주의해야 하고, 접근자는 정의된 속성만 추적합니다.
- 의존성 추적은 실행 중인 effect를 전역에 두고 읽기 때 등록하며, 실행할 때마다 다시 수집합니다.
- Computed는 지연 평가와 캐시, Effect는 부수 효과이고, 변경은 배치로 모아 microtask에서 effect를 한 번만 실행합니다.
- effect가 자기가 읽은 값을 쓰면 무한 루프가 되므로 같은 값 비교, computed, 읽기 전용 effect로 막고 렌더와 부수 효과는 effect를 나눕니다.
- TC39 Signals는 Stage 1이라 엔진에 내장돼 있지 않고, Observable API는 Chrome·Edge 135 이상에서만 지원됩니다.

## ECMAScript와 Browser API의 경계

ECMAScript는 언어 자체를 정의하는 표준입니다. 문법, 타입, `Object`·`Array`·`Promise`·`Map`·`JSON`·`Math` 같은 내장 객체가 여기에 속합니다. 브라우저 API는 언어 위에 브라우저가 얹어 주는 기능이며 HTML·DOM·Fetch 등 별도 표준이 정의합니다.

| 구분 | ECMAScript | Browser API |
|------|-----------|-------------|
| 예 | `Promise`, `Map`, `JSON`, `Math`, `Symbol` | `document`, `fetch`, `setTimeout`, `localStorage`, `URL`, `console` |
| 정의하는 곳 | Ecma TC39 | WHATWG(HTML·DOM·Fetch 등), W3C |
| 실행 환경 | 어디서나 같음 | 브라우저(와 워커)에만 있음 |

```js
typeof Promise   // 'function' (언어)
typeof fetch     // 'function' (브라우저 API)
typeof document  // 'object'   (Node.js에서는 'undefined')
```

- 언어 표준에는 이벤트 루프가 없습니다. 이벤트 루프, 태스크 큐, 타이머는 HTML 표준이 정의하며 `Promise` 콜백을 마이크로태스크로 실행하는 일도 HTML 표준의 몫입니다(자세히는 08편).
- 연결 지점은 호스트 정의 훅입니다. ECMAScript가 "호스트가 정한다"고 비워 둔 자리를 HTML 표준이 채웁니다. `HostEnqueuePromiseJob`(프라미스 작업 예약)과 `HostPromiseRejectionTracker`(처리되지 않은 거부 추적)가 그 예입니다.
- 브라우저 API 객체는 Web IDL 규칙에 따라 JavaScript 객체로 노출됩니다(아래 "Living Standard와 Web IDL 읽는 법").

**흔한 실수:** `setTimeout`, `console`, `structuredClone`을 언어 기능으로 여기는 것입니다. 모두 호스트가 제공합니다. 같은 코드가 Node.js나 워커에서 다르게 동작하는 원인이 됩니다.

## 브라우저 런타임 구조

브라우저는 렌더링 엔진, JavaScript 엔진, 네트워크·저장소·그래픽 같은 하위 시스템을 묶은 프로그램입니다. 엔진은 계열이 정해져 있습니다.

| 렌더링 엔진 | 쓰는 브라우저 | JavaScript 엔진 |
|-------------|---------------|-----------------|
| Blink | Chrome, Edge, Opera 등 Chromium 계열 | V8 |
| Gecko | Firefox | SpiderMonkey |
| WebKit | Safari | JavaScriptCore |

- 렌더링 엔진은 HTML·CSS·리소스를 화면으로 바꿉니다(자세히는 02편).
- JavaScript 엔진은 코드를 파싱하고 JIT 컴파일로 실행합니다.
- 표준이 같아도 엔진마다 구현 시점이 달라서 지원 상태를 확인해야 합니다. 이 과목은 Baseline으로 표기합니다(아래 "웹 표준과 WHATWG / W3C").

### 프로세스 모델과 사이트 격리

현대 브라우저는 여러 프로세스로 나뉩니다. Chromium 문서 기준 구성은 다음과 같습니다.

| 프로세스 | 역할 |
|----------|------|
| 브라우저 프로세스 | 주소창·탭 UI, 보안 정책 관리, 오작동하는 렌더러 종료 |
| 렌더러 프로세스 | 웹 콘텐츠 실행. 샌드박스 안에서 동작 |
| GPU 프로세스 | 그래픽 처리 |

- 사이트 격리(Site Isolation)는 서로 다른 사이트의 페이지를 항상 다른 렌더러 프로세스에 넣는 구조입니다. Chrome은 데스크톱에서 사이트마다 전용 렌더러를 둡니다.
- 사이트는 스킴과 등록 가능한 도메인(공개 접미사 포함)이며 서브도메인·포트·경로는 무시합니다. `https://foo.example.com:8080`은 `https://example.com` 사이트에 속합니다. 출처(origin)보다 느슨한 단위입니다(자세히는 62편).
- 다른 사이트의 iframe도 별도 프로세스에서 실행됩니다(out-of-process iframe).
- 교차 사이트 데이터(HTML·JSON 등)는 서버가 CORS로 허용하지 않으면 페이지의 프로세스로 전달되지 않습니다(자세히는 62편).

한 문서의 스크립트 실행, DOM 조작, 스타일 계산, 레이아웃은 기본적으로 렌더러의 메인 스레드 하나에서 이뤄집니다. 무거운 계산이 화면을 멈추는 이유이며, 워커가 필요한 이유입니다(자세히는 54편).

## Window / Document / GlobalThis

브라우저에서 스크립트의 전역 객체는 `Window`입니다. HTML 표준은 전역 객체를 `Window`(브라우징 컨텍스트), `WorkerGlobalScope`(워커), `WorkletGlobalScope`(워클릿) 세 종류로 나눕니다. 전역 객체는 실행 환경(realm)마다 정확히 하나입니다.

### 전역 객체에 접근하는 방법

| 표현 | 쓸 수 있는 곳 |
|------|---------------|
| `window` | 문서(iframe 포함). 워커에는 없음 |
| `self` | 문서와 워커 |
| `frames` | 문서. `window`와 같은 객체 |
| `global` | Node.js만 |
| `globalThis` | 모든 환경 |

`globalThis`는 ES2020에 추가되었고 2020년 1월에 Baseline이 되었습니다. 환경별 이름 차이를 없애므로 환경을 가리지 않는 코드는 `globalThis`를 씁니다.

```js
window === self           // true (문서)
window === globalThis     // true (문서)
self === globalThis       // true (워커에서도)
```

- 최상위 `var`와 함수 선언은 전역 객체의 프로퍼티가 됩니다. `let`, `const`, `class`는 되지 않습니다. 모듈 스크립트의 최상위 선언은 전역이 아닌 모듈 스코프입니다(자세히는 14편).
- 함수 안이 아닌 곳의 `this`는 일반 스크립트에서는 전역 객체이고 모듈에서는 `undefined`입니다.

### Window가 가진 것

`Window`는 문서 전체를 다루는 입구입니다. 주요 구성은 다음과 같습니다.

| 프로퍼티 | 가리키는 것 | 자세히 |
|----------|-------------|--------|
| `document` | 현재 `Document` | 03편 |
| `location` | 현재 URL과 이동 | 34편 |
| `history` | 세션 히스토리 | 34편 |
| `navigator` | 브라우저·기기 정보와 여러 API의 진입점 | 각 편 |
| `screen` | 화면 크기 | 06편 |
| `localStorage`, `sessionStorage` | Web Storage | 40편 |
| `innerWidth`, `scrollY` 등 | 뷰포트 크기와 스크롤 위치 | 06편 |

`document`는 `Window`에 속한 속성이고 DOM 트리의 루트입니다. 문서가 아니라 창이 전역이라는 점이 중요합니다. `fetch`, `setTimeout`, `addEventListener`도 `Window`의 메서드입니다.

### 브라우징 컨텍스트와 iframe

iframe은 자체 `Window`와 `Document`를 가진 별도의 브라우징 컨텍스트를 만듭니다. 창 사이의 관계는 프로퍼티로 이어집니다.

| 프로퍼티 | 값 |
|----------|-----|
| `window.frames` | 자기 자신(`WindowProxy`). `frames[0]`처럼 자식 프레임 접근 |
| `window.length` | 자식 프레임 수 |
| `window.parent` | 바로 위 부모 창 |
| `window.top` | 최상위 창 |
| `window.opener` | 이 창을 `window.open()`으로 연 창 |
| `window.frameElement` | 이 창을 품은 `iframe` 요소(교차 출처면 `null`) |

- 다른 창을 가리키는 값은 `WindowProxy`라는 특수 객체입니다. 같은 출처면 `Window`의 동작을 그대로 위임하고, 교차 출처면 표준이 정한 제한된 프로퍼티만 허용합니다.
- 자식 프레임은 `frames[0]`처럼 삽입 순서 인덱스로도, 프레임 이름으로도 접근됩니다.
- 교차 출처 창과의 통신은 `postMessage`를 씁니다(자세히는 59편).

### id로 만들어지는 전역 이름

문서의 요소가 `Window`의 프로퍼티로 노출됩니다(named access).

```html
<div id="box"></div>
<script>
  window.box   // div 요소
  box          // 같은 요소
</script>
```

표준이 정한 조회 순서는 다음과 같습니다.

1. 자식 프레임의 이름(같은 출처인 것만, 첫 번째 일치)
2. `embed`, `form`, `img`, `object` 요소의 `name` 속성
3. 문서 안 모든 요소의 `id`

- 이 이름들은 `Window`의 프로토타입 쪽에 있어서, 같은 이름의 전역 변수나 내장 프로퍼티(`location` 등)가 있으면 그쪽이 먼저 잡힙니다.
- `id`를 바꾸거나 요소를 추가·삭제하면 전역 이름도 바뀝니다. 코드가 의도하지 않은 요소를 잡는 사고가 납니다.
- 공격자가 `id`로 전역 값을 가로채는 기법(DOM clobbering)에 악용됩니다(자세히는 63편).

**흔한 실수:** `id="data"`를 달아 놓고 스크립트에서 `data`를 바로 쓰는 것입니다. 전역 변수 `data`가 선언되면 요소가 가려지고, 선언되지 않았다면 요소가 잡혀서 동작은 하지만 읽는 사람이 출처를 알 수 없습니다. 요소는 `document.getElementById()`로 가져옵니다(자세히는 04편).

## 웹 표준과 WHATWG / W3C

웹 플랫폼은 하나의 문서가 아니라 여러 표준 기관이 나눠 맡은 표준의 묶음입니다.

| 기관·문서 | 맡은 것 |
|-----------|---------|
| Ecma TC39 | ECMAScript(언어) |
| WHATWG | HTML, DOM, Fetch, Streams, URL, Web IDL 등 |
| W3C | CSS, WAI-ARIA, WebAuthn, Web Crypto 등 |

- WHATWG는 2004년에 Apple, Mozilla, Opera가 만든 모임입니다. 2017년에 Apple, Google, Microsoft, Mozilla가 IPR 정책과 운영 구조를 만들고 운영 위원회(Steering Group)를 꾸렸습니다.
- WHATWG 표준은 CC BY 4.0 라이선스입니다.

### Living Standard

WHATWG 표준은 Living Standard입니다. 버전 번호 없이 피드백과 구현 현황에 따라 계속 수정되는 문서이며, 최신본이 곧 표준입니다. 문서 상단의 갱신일이 기준 시점입니다. 특정 시점이 필요하면 약 6개월마다 나오는 스냅숏을 씁니다. 이 과목의 본문은 최신 Living Standard를 기준으로 합니다.

### Baseline

Baseline은 어떤 기능이 핵심 브라우저에서 쓸 수 있는지 한 단어로 표시하는 체계입니다. 핵심 브라우저는 Chrome(데스크톱·Android), Edge, Firefox(데스크톱·Android), Safari(macOS·iOS)입니다.

| 표기 | 의미 |
|------|------|
| Baseline 20XX(newly available) | 핵심 브라우저 전부가 지원하기 시작함. 20XX는 그 연도 |
| widely available | newly available이 된 지 30개월이 지남 |
| 미Baseline | 일부 엔진만 지원. 점진적 향상으로 다룸 |

이 과목의 "Baseline 20XX" 표기는 이 정의를 따릅니다.

### Living Standard와 Web IDL 읽는 법

표준 문서에서 API 모양은 Web IDL이라는 인터페이스 정의 언어로 적습니다. 아래는 읽는 법을 보이기 위해 단순화한 예입니다.

```
[Exposed=Window]
interface Sample : EventTarget {
  readonly attribute DOMString name;
  attribute boolean enabled;
  undefined start(optional boolean fast = false);
};
```

| Web IDL | JavaScript에서의 모습 |
|---------|-----------------------|
| `interface Sample` | 생성자 함수와 프로토타입. `: EventTarget`은 상속 |
| `attribute` | 프로토타입의 접근자 프로퍼티(getter와 setter) |
| `readonly attribute` | getter만 있음. 대입은 무시되고 엄격 모드에서는 TypeError |
| 오퍼레이션 | 프로토타입의 메서드 |
| `optional`, `= 값` | 생략 가능한 인수와 기본값 |
| `partial interface` | 같은 인터페이스를 표준 문서의 여러 곳에 나눠 적은 것. 동작은 같음 |
| `mixin`과 `includes` | 여러 인터페이스가 공유하는 멤버 묶음 |
| `[Exposed=Window]` | 노출되는 전역 객체. 워커에서는 보이지 않음 |
| `[SecureContext]` | HTTPS 같은 보안 컨텍스트에서만 노출 |
| `[SameObject]` | 읽을 때마다 같은 객체를 반환 |

- 표준 문서는 동작을 알고리즘 단계로 적습니다. 예외는 "throw a NotAllowedError"처럼 DOMException 이름으로 나옵니다.
- 메서드 반환형 `undefined`는 값이 없다는 뜻입니다.

### MDN 문서와 호환성 표 읽는 법

MDN은 개발자용 설명서이고 표준 문서는 구현자용 규격입니다. 사용법과 예는 MDN에서, 정확한 동작 규칙은 표준에서 확인합니다. MDN 호환성 표에는 다음 표지가 붙습니다.

| 표지 | 의미 |
|------|------|
| Experimental | 개발 중이라 바뀔 수 있음 |
| Deprecated | 낡아서 새 프로젝트에서 쓰지 않음 |
| Non-standard | 표준이 아님 |
| Partial implementation | 일부 동작만 구현 |
| Prefix | 벤더 접두사가 필요 |
| Flags | 브라우저 설정을 켜야 동작 |

- 칸의 숫자는 지원이 시작된 브라우저 버전입니다.
- 표를 볼 때는 사용하려는 하위 기능(메서드, 옵션)의 행을 따로 봅니다. 인터페이스 전체가 지원돼도 일부 멤버는 아닐 수 있습니다.

## 브라우저 기능을 컴포넌트로 캡슐화하기

브라우저 API를 화면 곳곳에서 직접 호출하면 권한 처리, 지원 검사, 정리 코드가 흩어집니다. 한 컴포넌트가 API 하나를 맡고 바깥에는 속성·프로퍼티·이벤트만 보이게 하는 방식이 캡슐화입니다.

```js
class ViewportWatcher extends HTMLElement {
  #io
  connectedCallback() {
    if (!('IntersectionObserver' in window)) return
    this.#io = new IntersectionObserver(([e]) => {
      this.dispatchEvent(new CustomEvent('visibility',
        { detail: e.isIntersecting }))
    })
    this.#io.observe(this)
  }
  disconnectedCallback() { this.#io?.disconnect() }
}
```

컴포넌트가 책임지는 일은 다음과 같습니다.

- 지원 여부 확인과 대체 동작(위 코드의 `in` 검사)
- 자원의 획득과 해제. 연결될 때 만들고 분리될 때 정리합니다(자세히는 18편).
- 권한 요청과 거부 상태 처리(자세히는 60편)
- 바깥에 보이는 계약. 속성·프로퍼티·메서드·이벤트(자세히는 19편)
- 내부 구현 숨기기. `#io` 같은 private 필드는 바깥에서 읽을 수 없습니다.

바깥 코드는 `visibility` 이벤트만 알면 되고 `IntersectionObserver`가 쓰였는지는 모릅니다. 구현을 다른 API로 바꿔도 계약이 같으면 사용하는 쪽은 그대로입니다. 요소 정의와 생명주기는 17편, 18편에서 다룹니다.

## Feature Detection

기능 감지는 브라우저 이름이 아니라 쓰려는 기능이 있는지를 직접 검사하는 방식입니다. User-Agent 문자열로 브라우저를 추정하는 방식(sniffing)은 쓰지 않습니다. 브라우저를 안다고 그 기능의 지원을 아는 것은 아니기 때문입니다.

```js
'geolocation' in navigator             // 객체의 멤버
typeof window.ResizeObserver === 'function'  // 생성자
!!document.createElement('canvas').getContext // 요소 프로퍼티
CSS.supports('grid-template-columns', 'subgrid') // CSS
```

| 검사 대상 | 방법 |
|-----------|------|
| 객체의 멤버 | `in` 연산자 |
| 전역 생성자·함수 | `typeof x === 'function'` |
| 요소가 제공하는 기능 | 요소를 만들어 프로퍼티·메서드 확인 |
| CSS | CSS에서는 `@supports`, JavaScript에서는 `CSS.supports()` |
| 미디어 특성 | `matchMedia()` |

- CSS 기능은 가능하면 JavaScript 없이 `@supports`로 분기합니다. `and`, `or`, `not`을 쓸 수 있습니다.
- 정적 `supports()` 메서드를 제공하는 API가 있어서 하위 기능까지 검사됩니다(자세히는 15편).
- 검사는 사용하는 기능 단위로 합니다. 한 API가 있다고 같은 시기에 나온 다른 API도 있다고 가정하지 않습니다.

```js
if ('geolocation' in navigator) {
  navigator.geolocation.getCurrentPosition(show)
} else {
  showStaticMap() // 대체 경로
}
```

**흔한 실수:**

- 존재만 확인하고 동작을 가정하는 것입니다. `[SecureContext]` API는 HTTP 페이지에서 아예 노출되지 않아 `undefined`입니다(예: `navigator.serviceWorker`). 노출돼도 권한이 거부되면 `NotAllowedError`가 납니다. 감지는 "있다"까지만 보장합니다.
- 기능이 없을 때의 대체 경로를 만들지 않는 것입니다. 검사 결과가 거짓일 때 무엇을 할지가 설계의 절반입니다.
- 부분 구현을 놓치는 것입니다. 객체가 있어도 하위 옵션이 빠질 수 있으므로 호환성 표에서 쓰려는 멤버의 행을 확인합니다.

## Progressive Enhancement

점진적 향상은 모든 브라우저에서 동작하는 기본 기능을 먼저 만들고, 지원하는 브라우저에만 고급 기능을 더하는 설계입니다. 구형 환경에서는 단순하지만 쓸 수 있고, 최신 환경에서는 더 풍부해집니다. 기능 감지와 폴리필(없는 기능을 JavaScript로 채우는 코드)이 수단입니다.

| 방식 | 출발점 | 방향 |
|------|--------|------|
| 점진적 향상 | 모든 브라우저가 받는 기본 | 지원하는 곳에 기능 추가 |
| 우아한 성능 저하(graceful degradation) | 최신 브라우저 | 구형을 위한 대체 추가 |

둘은 서로 보완할 수 있지만 점진적 향상은 기본을 단단히 한다는 점에서 방향이 반대입니다.

층으로 보면 다음과 같습니다.

1. HTML: 콘텐츠와 기본 동작(링크, 폼 전송)
2. CSS: 표현. 새 기능은 `@supports`로 분기
3. JavaScript: 상호작용. 기능 감지 후에 연결

웹 컴포넌트에도 같은 원칙이 적용됩니다.

```html
<my-tabs>
  <a href="#a">첫째</a>
  <a href="#b">둘째</a>
</my-tabs>
```

- 정의되지 않은 커스텀 요소는 알 수 없는 `HTMLElement`로 취급되어 자식 콘텐츠가 그대로 보입니다. 스크립트가 로드되지 않거나 실패해도 링크 목록은 남습니다.
- 정의되기 전 상태는 `:defined` 의사 클래스로 구분해 스타일을 줄 수 있습니다(자세히는 17편).
- 기본 제공 요소를 확장하는 방식(Customized built-in)은 Safari가 지원하지 않습니다. 확장에 실패하면 원래 요소로 동작하므로 향상 방식으로는 자연스럽지만, 지원 여부를 믿고 필수 기능을 얹으면 안 됩니다(자세히는 17편).

**흔한 실수:** 콘텐츠 자체를 스크립트로만 그리는 것입니다. 스크립트 로드 실패, 네트워크 지연, 검색 엔진·보조 기술이 읽는 시점에 빈 화면이 됩니다. 필수 콘텐츠와 핵심 동작은 HTML에 두고 스크립트는 그 위에 얹습니다. 지원 범위 전략은 71편에서 다룹니다.

## 컴포넌트 아키텍처의 목표: 재사용성 / 캡슐화 / 조합성

웹 컴포넌트는 재사용 가능한 커스텀 요소를 만드는 기술의 묶음입니다. 커스텀 요소, 섀도 DOM, 템플릿과 슬롯 세 기술로 구성됩니다(자세히는 16편). 컴포넌트 아키텍처는 세 목표를 기준으로 판단합니다.

| 목표 | 의미 | 브라우저가 주는 수단 | 깨지는 경우 |
|------|------|----------------------|-------------|
| 재사용성 | 페이지 상황에 상관없이 어디서나 같게 동작 | 커스텀 요소(17편), 속성·프로퍼티 API(19편) | 전역 id·전역 CSS·특정 부모 구조에 의존 |
| 캡슐화 | 내부 구현을 바깥이 건드리지 못함 | 섀도 DOM(21편), private 필드, 이벤트 | 바깥 스타일이 내부를 덮음. 내부 DOM을 직접 조작 |
| 조합성 | 작은 컴포넌트를 끼워 큰 UI를 만듦 | 슬롯(22편), 이벤트(25편), 중첩 | 내부 구조를 알아야만 조립 가능 |

- 세 목표는 서로 당깁니다. 캡슐화를 강하게 하면 바깥 스타일 조정이 어려워져 재사용성이 떨어지고, 조합성을 위해 열수록 캡슐화가 약해집니다. 열어 줄 부분(슬롯, `::part`, CSS 사용자 정의 속성)을 계약으로 정하는 것이 설계입니다(자세히는 23편).
- 컴포넌트의 공개 면은 속성, 프로퍼티, 메서드, 이벤트, 슬롯, CSS 사용자 정의 속성입니다. 그 밖은 내부입니다.
- 이 과목의 뒤쪽 편(합성 패턴 29편, 데이터 흐름 32편, 설계 사례 83–85편)은 이 세 기준으로 설계 판단을 합니다.

## DOMException과 표준 오류 이름

DOMException은 브라우저 API가 던지는 표준 오류 객체입니다. `Error`를 상속하며 오류의 종류는 `name`으로 구분합니다.

| 프로퍼티 | 의미 |
|----------|------|
| `name` | 오류 이름 문자열(`'NotAllowedError'` 등) |
| `message` | 설명 문자열 |
| `code` | 구형 숫자 코드. 해당하는 것이 없으면 0 |

- 생성자는 `new DOMException(message, name)`입니다. 인수 순서가 `Error`와 달리 메시지가 먼저, 이름이 나중입니다.
- 분기는 `name`으로 합니다. `code`는 구형 호환용이라 새 이름에는 값이 없습니다.

```js
try {
  localStorage.setItem('k', hugeString)
} catch (e) {
  if (e.name === 'QuotaExceededError') {
    // 저장 용량 초과
  }
}
```

| 이름 | 뜻 | 대표 상황 |
|------|-----|-----------|
| `NotAllowedError` | 사용자 에이전트나 플랫폼이 허용하지 않음 | 권한 거부, 사용자 활성화 없이 호출 |
| `SecurityError` | 안전하지 않은 동작 | 교차 출처 프레임의 문서 접근 |
| `QuotaExceededError` | 할당량 초과 | 저장소 용량 초과 |
| `InvalidStateError` | 객체가 호출할 수 없는 상태 | 끝난 트랜잭션·닫힌 연결에 사용 |
| `NotSupportedError` | 지원하지 않는 동작 | 이미 쓰인 이름으로 커스텀 요소 정의 |
| `DataCloneError` | 복제할 수 없는 값 | `postMessage`·`structuredClone`에 함수 전달 |
| `AbortError` | 작업이 중단됨 | `AbortController.abort()` |
| `TimeoutError` | 시간 초과 | `AbortSignal.timeout()` |
| `SyntaxError` | 문자열이 기대한 형식이 아님 | 잘못된 선택자 |

- `QuotaExceededError`는 현재 `DOMException`을 상속하는 독립 인터페이스입니다. 이름 문자열만 있던 예전과 다르지만 `e.name` 비교는 그대로 동작합니다.
- 모든 오류가 DOMException은 아닙니다. 인수의 타입이 잘못되면 ECMAScript의 `TypeError`가 납니다. 두 종류를 모두 처리해야 하는 경우가 있습니다.
- 각 API가 던지는 이름은 해당 편(저장소 40–42편, 취소 37편, 복제 54편)에서 다룹니다.

## 핵심 정리

- ECMAScript는 언어를, 브라우저 API는 호스트 기능을 정의하며 이벤트 루프·`setTimeout`·`fetch`는 HTML·Fetch 표준 소관입니다.
- 브라우저는 렌더링 엔진(Blink·Gecko·WebKit)과 JS 엔진을 가지며, Chrome은 사이트마다 렌더러 프로세스를 분리합니다.
- 문서의 전역 객체는 `Window`이고 `globalThis`가 환경 차이를 없앱니다. `id`와 `name`은 전역 이름으로도 노출됩니다.
- WHATWG 표준은 버전 없는 Living Standard이고, Web IDL은 JavaScript 객체 모양으로 읽으며, 지원 상태는 Baseline과 MDN 호환성 표로 확인합니다.
- 기능 감지는 쓰려는 기능을 직접 검사하고, 점진적 향상은 HTML 기본 위에 기능을 얹습니다.
- 컴포넌트 아키텍처는 재사용성·캡슐화·조합성의 균형이며, 브라우저 API 오류는 `DOMException`의 `name`으로 구분합니다.

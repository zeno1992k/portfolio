## 키보드 조작 모델

키보드 사용자는 화면의 요소 중 하나에 있는 포커스를 Tab, 방향키 같은 키로 옮기고 Enter, Space로 조작합니다. 네이티브 요소는 이 조작을 기본으로 지원하고, 커스텀 컴포넌트는 직접 구현합니다. 시각 포커스, 키 처리, 보조 기술에 알리는 상태가 서로 맞아야 합니다.

| 키 | 일반적인 역할 |
|----|---------------|
| `Tab` / `Shift+Tab` | 컴포넌트 사이의 이동(다음/이전) |
| 방향키 | 한 컴포넌트 안의 항목 사이 이동 |
| `Enter` | 실행(버튼, 링크), 선택 확정 |
| `Space` | 버튼 실행, 체크박스·스위치 토글 |
| `Escape` | 열린 것(대화상자, 메뉴, 팝업) 닫기 |
| `Home` / `End` | 첫 항목 / 마지막 항목 |

핵심 규칙은 한 컴포넌트가 탭 순서에서 한 칸만 차지하는 것입니다. 탭 목록, 라디오 그룹, 메뉴, 리스트박스처럼 항목이 여럿인 복합 위젯(composite widget)은 Tab으로 들어와서 방향키로 항목을 옮기고, Tab으로 다시 나갑니다. 항목마다 Tab을 눌러야 하면 위젯 뒤의 요소에 도달하기 어렵습니다.

위젯별 키 조합은 WAI-ARIA Authoring Practices(APG)의 패턴에 정리되어 있습니다. 같은 이름의 위젯이면 사용자가 기대하는 키가 같아야 합니다.

```js
this.addEventListener('keydown', (e) => {
  if (e.key === 'Escape') this.close()
  if (e.key === 'ArrowDown') {
    e.preventDefault() // 스크롤 방지
    this.#next()
  }
})
```

- 키 판별은 `e.key`를 씁니다(`key`와 `code`의 차이는 10편).
- 방향키의 기본 동작은 스크롤이므로 위젯이 처리하면 `preventDefault()`로 막습니다. Tab은 막지 않습니다(막으면 포커스가 갇힙니다).
- 마우스로만 되는 동작이 없어야 합니다. 클릭으로 하는 모든 조작에 키보드 대응이 있어야 합니다.
- 네이티브 `button`을 쓰면 Enter와 Space 처리가 이미 되어 있으므로 키 처리가 필요 없습니다(27편의 시맨틱 우선 원칙).
- 키 이벤트는 포커스를 가진 요소에서 시작해 위로 올라가고 `composed`라서, shadow 안의 요소에 포커스가 있어도 호스트의 `keydown` 리스너가 받습니다.

## Tab 순서

Tab 순서(sequential focus navigation order)는 Tab을 누를 때 포커스가 이동하는 순서입니다. 기본은 문서의 소스 순서(DOM 순서)입니다.

- 기본으로 Tab 대상인 요소는 `href`가 있는 `a`, `button`, 숨김이 아닌 `input`, `select`, `textarea`, `details`의 첫 `summary`, 편집 가능한 요소(contenteditable), `iframe` 같은 것입니다. 브라우저와 플랫폼의 관례에 따라 일부는 다를 수 있습니다.
- 비활성(`disabled`) 요소와 `inert`인 요소는 포커스되지 않습니다.
- `display: none`, `visibility: hidden`인 요소는 포커스되지 않습니다.
- 화면 배치를 CSS로 바꾸면(`order`, 그리드 배치, 절대 위치) 시각 순서와 Tab 순서가 어긋납니다. 순서는 DOM에서 맞춥니다.

```html
<button>A</button>
<span>글자</span>             <!-- 건너뜀 -->
<button disabled>B</button>   <!-- 건너뜀 -->
<a href="/x">C</a>
<!-- Tab 순서: A → C -->
```

- Tab 순서는 슬롯을 거친 평탄화된 구조를 따릅니다. 슬롯에 들어온 요소는 슬롯 자리에서, shadow 안의 요소는 호스트 자리에서 순서에 들어갑니다(shadow 안은 아래 "Shadow DOM과 포커스").

## tabindex 값(0·-1·양수)의 의미

`tabindex`는 요소가 포커스를 받는지, Tab 순서에 들어가는지, 순서가 어디인지를 정합니다. 정수 값에 따라 다음과 같습니다.

| 값 | 포커스 가능 | Tab 순서 | 용도 |
|----|-------------|----------|------|
| 없음 | 요소의 기본값에 따름 | 요소의 기본값에 따름 | 네이티브 컨트롤 |
| `0` | 가능 | 소스 순서에 포함 | 비네이티브 요소를 Tab 대상으로 |
| `-1` | 가능(스크립트·클릭) | 제외 | `focus()`로만 이동시킬 요소 |
| 양수 | 가능 | 값 오름차순, 0이나 없음보다 앞 | 쓰지 않는다 |

```html
<div tabindex="0">Tab으로 도달</div>
<div tabindex="-1" id="msg">focus()로만 도달</div>
```

- `tabindex="-1"`은 클릭이나 `focus()`로는 포커스할 수 있게 하고 Tab 순서에서만 뺍니다. 오류 메시지 영역이나 제목으로 포커스를 옮기고 싶을 때 씁니다.
- `tabindex`로 요소를 포커스 불가로 만들 수는 없습니다. 포커스를 막으려면 요소를 `disabled`로 하거나 `inert`로 만듭니다.
- 양수 값은 문서 전체의 순서를 바꿉니다. 한 요소의 값을 바꾸면 다른 요소의 순서까지 영향을 받아 유지하기 어렵고, 시각 순서와도 어긋납니다. 표준도 0과 -1 외의 값은 정확히 쓰기 어렵다고 경고합니다.
- 양수 값의 순서는 같은 범위 안에서만 의미가 있습니다. shadow 트리는 호스트와 별도의 포커스 이동 범위를 가지므로, 그 안의 값이 바깥 요소와 섞여 정렬되지 않습니다.
- 네이티브 컨트롤(`button`, `a[href]`, `input`)에는 `tabindex`를 붙이지 않습니다.
- JS에서는 `el.tabIndex`(정수)로 읽고 씁니다. 어트리뷰트가 없는 `div`의 `tabIndex`는 `-1`입니다.

**흔한 실수:** 커스텀 요소 호스트에 `tabindex="0"`을 주고 내부에도 포커스 가능한 `button`을 두는 것입니다. Tab 정류장이 둘이 되고 동작이 중복됩니다. 포커스는 한 곳에만 둡니다.

## focus / blur

요소가 포커스를 받으면 `focus`, 잃으면 `blur` 이벤트가 발생합니다. 둘은 버블링하지 않습니다. 버블링하는 짝이 `focusin`과 `focusout`입니다.

| 이벤트 | 시점 | 버블링 | composed |
|--------|------|--------|----------|
| `focus` | 포커스를 받음 | 안 함 | 예 |
| `blur` | 포커스를 잃음 | 안 함 | 예 |
| `focusin` | 포커스를 받음(`focus` 뒤) | 함 | 예 |
| `focusout` | 포커스를 잃음 | 함 | 예 |

```js
this.addEventListener('focusin', (e) => {
  console.log('안쪽 어딘가에 포커스', e.target)
})
this.addEventListener('focusout', (e) => {
  console.log('다음 대상', e.relatedTarget)
})
```

- 컨테이너가 안쪽 요소의 포커스를 감지하려면 `focusin`·`focusout`을 씁니다. `focus`를 쓰려면 캡처 단계(`true` 옵션)로 듣습니다.
- `relatedTarget`은 이동 상대입니다. `focus`·`focusin`에서는 포커스를 잃은 쪽, `blur`·`focusout`에서는 포커스를 받는 쪽이고, 없으면 `null`입니다.
- 컨테이너 밖으로 포커스가 나갔는지 판단할 때는 `focusout`의 `relatedTarget`이 컨테이너 안에 있는지 확인합니다. 안쪽 요소 사이를 오갈 때도 `focusout`이 발생하기 때문입니다.

```js
this.addEventListener('focusout', (e) => {
  if (!this.contains(e.relatedTarget)) this.#onLeave()
})
```

- `mousedown`에서 `preventDefault()`를 호출하면 클릭해도 포커스가 옮겨지지 않습니다. 팝업 안의 버튼을 눌러도 입력창의 포커스를 유지하고 싶을 때 씁니다.
- macOS Safari는 설정에 따라 클릭이나 Tab으로 버튼 같은 비텍스트 컨트롤에 포커스가 가지 않을 수 있습니다. 포커스에 의존하는 동작은 이 경우를 고려합니다.

## focus() 옵션

`el.focus(options)`는 요소에 포커스를 줍니다. 요소가 포커스 가능해야 하고, 문서에 연결되어 보여야 합니다. 옵션은 두 가지입니다.

| 옵션 | 값 | 동작 |
|------|-----|------|
| `preventScroll` | `true` | 포커스를 줄 때 요소를 화면으로 스크롤하지 않음. 기본은 스크롤함 |
| `focusVisible` | `true` / `false` | 포커스 표시(`:focus-visible`)를 강제로 켜거나 끔. 생략하면 브라우저가 판단 |

```js
dialog.focus({ preventScroll: true })
input.focus({ focusVisible: true })
```

- `focusVisible`은 `focus()`가 어떤 입력 방식으로 호출되었는지에 따라 달라지는 표시 여부를 코드에서 지정합니다. Baseline 2026(Chrome·Edge 145, Firefox 104, Safari 18.4)이고 이전 브라우저는 옵션을 무시합니다.
- `preventScroll`은 고정 헤더나 스크롤 컨테이너 안에서 의도하지 않은 점프를 막을 때 씁니다.
- 포커스 불가능한 요소에 `focus()`를 호출하면 아무 일도 없습니다. 에러는 발생하지 않습니다.
- `blur()`는 포커스를 해제합니다. 대부분의 경우 포커스를 없애기보다 다른 곳으로 옮기는 것이 접근성에 맞습니다.
- 화면 전환, 요소 삭제 후에는 포커스가 `body`로 돌아가 키보드 사용자가 위치를 잃습니다. 새 화면의 제목이나 관련 요소로 `focus()`를 호출해 위치를 이어 줍니다.

## focus-visible

`:focus-visible`은 요소가 포커스를 가졌고 브라우저가 포커스 표시가 필요하다고 판단할 때 맞는 의사 클래스입니다(Baseline 2022). 키보드로 이동했을 때는 보이고, 마우스 클릭으로 버튼에 포커스가 갔을 때는 보이지 않는 식입니다. 텍스트 입력은 입력 방식과 관계없이 보입니다.

```css
button:focus-visible {
  outline: 2px solid royalblue;
  outline-offset: 2px;
}
button:focus:not(:focus-visible) { outline: none; }
```

| 선택자 | 매칭 |
|--------|------|
| `:focus` | 포커스를 가진 모든 경우 |
| `:focus-visible` | 포커스를 가졌고 표시가 필요한 경우 |

- 포커스 표시를 완전히 없애지 않습니다. `outline: none`만 쓰면 키보드 사용자가 현재 위치를 볼 수 없습니다. 지울 때는 대체 표시를 반드시 둡니다.
- 표시는 배경과 3:1 이상의 명도 대비를 가져야 합니다(WCAG 2.1 비텍스트 대비).
- `focus()`로 프로그램이 이동시킨 포커스는 직전 입력 방식(키보드를 썼는지)에 따라 표시 여부가 정해집니다. 코드에서 지정하려면 앞의 `focusVisible` 옵션을 씁니다.
- 컴포넌트 안에서는 호스트가 아니라 포커스를 받는 내부 요소에 적용합니다. 호스트에 보이려면 `:host(:focus-visible)`를 씁니다(23편).

## :focus-within

`:focus-within`은 요소 자신이나 후손 중 하나가 포커스를 가질 때 맞는 의사 클래스입니다(Baseline 2020). shadow 트리 안의 후손도 포함됩니다. 컨테이너를 통째로 강조하거나 안쪽 입력에 포커스가 있을 때만 보조 UI를 보이는 데 씁니다.

```css
form:focus-within { background: #ffffee; }
.search:focus-within .clear { visibility: visible; }
```

- `:focus`는 요소 자신이 포커스일 때, `:focus-within`은 자신 또는 후손이 포커스일 때입니다.
- 컴포넌트의 호스트에서는 shadow 안의 요소에 포커스가 있어도 `:host(:focus-within)`이 맞습니다. 호스트 쪽 스타일을 안쪽 포커스에 반응시킬 때 유용합니다.
- 자바스크립트로 "포커스가 이 컴포넌트 안에 있는가"를 확인하려면 `this.matches(':focus-within')`을 쓸 수 있습니다.

## roving tabindex

roving tabindex는 복합 위젯에서 현재 항목만 `tabindex="0"`, 나머지는 `tabindex="-1"`로 두고 방향키로 `0`을 옮겨 다니며 `focus()`를 호출하는 방식입니다. Tab 순서에는 위젯이 한 칸으로만 나타납니다.

```html
<div role="tablist">
  <button role="tab" tabindex="0">개요</button>
  <button role="tab" tabindex="-1">상세</button>
  <button role="tab" tabindex="-1">후기</button>
</div>
```

```js
#move(next) {
  this.#items[this.#index].tabIndex = -1
  this.#index = next
  this.#items[next].tabIndex = 0
  this.#items[next].focus()
}
```

방향키 처리는 목록 끝에서 처음으로 돌아가게 하고 `Home`·`End`를 지원합니다.

```js
onKeydown(e) {
  const n = this.#items.length
  const step = { ArrowRight: 1, ArrowLeft: -1 }[e.key]
  if (step) this.#move((this.#index + step + n) % n)
  if (e.key === 'Home') this.#move(0)
  if (e.key === 'End') this.#move(n - 1)
}
```

- 실제 DOM 포커스가 항목으로 이동하므로 `focus()`가 스크롤과 포커스 표시를 처리합니다.
- 위젯에서 Tab으로 나갔다가 돌아오면 마지막에 있던 항목이 `tabindex="0"`이라 그 항목으로 돌아옵니다.
- 항목이 동적으로 추가되거나 삭제될 때 `0`이 하나만 존재하도록 보정해야 합니다. `0`이 하나도 없으면 위젯으로 Tab이 들어오지 못합니다.
- 항목을 비활성화할 때는 건너뛰고 이동하게 합니다.

## aria-activedescendant

`aria-activedescendant`는 컨테이너가 DOM 포커스를 가진 채로 현재 항목을 가리키는 방식입니다. 컨테이너에 `tabindex="0"`을 두고, 방향키가 눌리면 `aria-activedescendant`의 값을 항목의 `id`로 바꿉니다. 보조 기술은 그 항목에 포커스가 있는 것처럼 다룹니다.

```html
<div role="listbox" tabindex="0"
     aria-activedescendant="o1">
  <div role="option" id="o1">사과</div>
  <div role="option" id="o2">배</div>
</div>
```

```js
list.setAttribute('aria-activedescendant', 'o2')
// DOM 포커스는 list에 그대로. 시각 표시는 직접 그린다
```

| 항목 | roving tabindex | aria-activedescendant |
|------|-----------------|-----------------------|
| DOM 포커스 | 항목으로 이동 | 컨테이너에 고정 |
| 스크롤과 포커스 표시 | 브라우저가 처리 | 직접 구현 |
| 적합한 경우 | 탭, 툴바, 라디오 그룹 | 입력창이 포커스를 유지하는 콤보박스, 검색 제안 목록 |

- 콤보박스에서는 입력창이 계속 키 입력을 받아야 하므로 이 방식을 씁니다. 입력창의 `aria-activedescendant`가 팝업 목록의 활성 항목을 가리킵니다.
- 활성 항목은 시각적으로 강조해야 하고, 화면 밖이면 `scrollIntoView`로 보이게 합니다. 이 표시는 `:focus-visible`이 대신해 주지 않습니다.
- 가리키는 항목은 컨테이너의 후손이거나 `aria-owns`나 `aria-controls`로 연결된 요소여야 합니다.
- 이 어트리뷰트도 ID 참조라서 shadow 경계를 넘지 못합니다. 같은 트리 안에 두거나 요소 참조 프로퍼티 `ariaActiveDescendantElement`를 씁니다(Baseline 2025, 27편).

## Shadow DOM과 포커스

shadow 트리 안의 요소도 일반 요소와 같이 포커스를 받고 Tab 순서에 들어갑니다. 달라지는 점은 바깥에서 보이는 모습입니다.

- 바깥 트리의 리스너는 shadow 안에서 일어난 포커스 이벤트의 `event.target`을 호스트로 봅니다(리타깃팅). `focus`, `blur`, `focusin`, `focusout`은 모두 `composed`라서 경계를 넘습니다. 안쪽 요소를 알아내려면 `event.composedPath()[0]`을 씁니다(열린 shadow 루트일 때).
- `relatedTarget`도 같은 방식으로 호스트로 바뀝니다.
- Tab 순서에서 shadow 안의 요소는 호스트의 자리에 들어갑니다. 호스트 자체가 `tabindex` 때문에 Tab 정류장이면 호스트에 한 번 멈춘 뒤 안쪽 요소들로 들어갑니다.
- 호스트를 `:focus` 상태로 볼 수 있느냐는 아래 `delegatesFocus`와 `:focus-within`에 달려 있습니다.
- `focus()`를 호스트에 호출하면 호스트가 포커스 가능한 경우에만 호스트가 포커스를 받습니다. 호스트가 포커스 가능하지 않으면 아무 일도 없습니다(delegatesFocus일 때는 다음 절).
- 내부 요소가 포커스 가능하게 만든 컴포넌트에서는 호스트를 `tabindex="0"`으로 만들 필요가 없습니다. 이중 Tab 정류장이 생깁니다.

```js
// 바깥 트리에서
document.addEventListener('focusin', (e) => {
  e.target                  // 호스트(my-input)
  e.composedPath()[0]       // 안쪽의 실제 input (open일 때)
})
```

## document.activeElement와 shadowRoot.activeElement

`document.activeElement`는 현재 키보드 이벤트를 받는 요소입니다. 포커스된 요소가 없으면 `body`(없으면 `documentElement`)입니다. 포커스가 shadow 트리 안에 있으면 안쪽 요소가 아니라 가장 바깥 호스트를 돌려줍니다. 안쪽 요소는 그 트리의 `shadowRoot.activeElement`로 읽습니다.

```js
const host = document.querySelector('my-input')
host.shadowRoot.querySelector('input').focus()

document.activeElement                 // host
host.shadowRoot.activeElement          // 안쪽 input
```

| 질의 위치 | 반환 |
|-----------|------|
| `document.activeElement` | 문서 트리에서 포커스를 가진 요소(안쪽이면 최상위 호스트) |
| `shadowRoot.activeElement` | 그 shadow 트리 안에서 포커스를 가진 요소. 없으면 `null` |
| 중첩 shadow | 각 루트가 자기 트리의 호스트를 반환. 끝까지 따라가려면 반복 |

```js
function deepActive() {
  let el = document.activeElement
  while (el?.shadowRoot?.activeElement) {
    el = el.shadowRoot.activeElement
  }
  return el
}
```

- 이 반복은 `open` shadow 루트에서만 됩니다. `closed`에서는 `shadowRoot`가 `null`이라 안쪽에 접근하지 못합니다.
- 컴포넌트 안에서 "내 안에 포커스가 있나"는 `this.shadowRoot.activeElement`의 존재로 알 수 있습니다.
- iframe 안에 포커스가 있으면 `document.activeElement`는 그 `iframe` 요소입니다. 다른 문서의 안쪽 요소는 보이지 않습니다.
- `activeElement`는 포커스 이벤트를 대신하지 않습니다. 변화를 감지하려면 `focusin`·`focusout`을 듣고 현재 상태를 읽을 때 `activeElement`를 씁니다.

## delegatesFocus

`delegatesFocus`는 shadow 루트를 만들 때 켜는 옵션으로, 호스트에 대한 포커스를 shadow 안의 첫 번째 포커스 가능한 요소에 위임합니다(Baseline 2020).

```js
this.attachShadow({ mode: 'open', delegatesFocus: true })
// 선언형: template의 shadowrootdelegatesfocus
// 읽기: this.shadowRoot.delegatesFocus
```

`true`이면 다음과 같이 동작합니다.

| 상황 | 동작 |
|------|------|
| 호스트에서 `focus()` 호출 | shadow 안의 첫 포커스 가능한 요소가 포커스를 받음 |
| shadow 안의 포커스 불가능한 부분을 클릭 | 첫 포커스 가능한 요소가 포커스를 받음 |
| 안쪽 요소가 포커스를 가짐 | 호스트에도 `:focus` 스타일이 적용됨 |
| Tab 이동 | 호스트 자체는 정류장이 아니고 안쪽 요소들이 순서에 들어감 |

- 위임 대상은 shadow 트리를 트리 순서로 훑어서 처음 만나는 포커스 가능한 요소입니다. 그 요소가 `tabindex="-1"`이거나 처음 포커스를 줄 요소가 따로 있으면 `autofocus`로 대상을 지정합니다.
- 내부에 `input`을 감싸는 컴포넌트에서 호스트에 `focus()`를 호출하거나 컴포넌트의 빈 부분을 클릭했을 때 입력창으로 포커스가 가게 하려고 씁니다.
- 위임을 켠 컴포넌트는 일반적으로 호스트에 `tabindex`를 주지 않고 포커스를 내부 요소에 맡깁니다.
- 호스트에 `:focus` 스타일이 적용되므로 `:host(:focus)`로 컴포넌트 외곽에 포커스 표시를 그릴 수 있습니다. 안쪽 요소도 `outline`을 그리면 표시가 이중으로 보이니 한쪽만 정합니다.
- `delegatesFocus`가 없으면 호스트는 포커스 가능한 요소가 아니라서 `focus()`를 호출해도 안쪽으로 가지 않습니다.

## autofocus 속성

`autofocus`는 페이지가 로드되거나 `dialog`·popover가 열릴 때 그 요소에 자동으로 포커스를 주는 불리언 전역 어트리뷰트입니다. 폼 컨트롤뿐 아니라 어느 요소에나 쓸 수 있고, 포커스 가능한 요소여야 합니다.

```html
<dialog id="d">
  <button>취소</button>
  <input name="q" autofocus>
</dialog>
```

- 문서, 대화상자, 팝오버마다 `autofocus`는 하나만 유효합니다. 여러 개이면 처음의 포커스 가능한 요소가 받습니다.
- URL에 조각(`#id`)이 있으면 그 요소가 우선합니다.
- 대화상자가 열리면 `autofocus` 요소에 포커스가 갑니다. 없으면 대화상자 안의 첫 포커스 가능한 요소가 대상이 됩니다. 취소 버튼처럼 파괴적이지 않은 쪽을 초기 포커스로 지정할 때 씁니다.
- shadow 트리의 포커스 위임(`delegatesFocus`)에서는 `autofocus`가 있는 후손이 먼저 위임 대상이 됩니다.
- 페이지 로드 시 `autofocus`는 화면 낭독기 사용자를 맥락 없이 입력창으로 옮기고, 모바일에서는 키보드를 띄우며 스크롤을 일으킬 수 있습니다. 페이지의 주된 목적이 그 입력일 때만 씁니다(Baseline 널리 지원).

## Focus Trap

포커스 트랩(focus trap)은 모달 대화상자 같은 영역이 열려 있는 동안 Tab 이동이 그 영역 안에서만 순환하게 하는 것입니다. 모달이 열렸는데 Tab으로 뒤쪽 페이지에 가게 되면 키보드 사용자가 화면에 보이지 않는 곳을 조작하게 됩니다.

우선은 직접 만들지 않고 플랫폼이 제공하는 기능을 씁니다.

- `dialog` 요소의 `showModal()`은 대화상자를 열고 나머지 문서를 inert로 만들어 포커스가 안에 머물게 합니다. 열릴 때 안쪽(`autofocus` 또는 첫 포커스 가능한 요소)으로 포커스가 이동하고, 닫히면 열기 전에 포커스가 있던 요소로 돌아갑니다(자세히는 44편).
- `inert` 어트리뷰트는 요소와 그 후손을 포커스, 클릭, 선택, 접근성 트리에서 제외합니다(Baseline 2023). 모달 밖의 영역에 `inert`를 걸어 같은 효과를 낼 수 있습니다.

```js
// 모달 밖 영역을 비활성화
document.querySelector('main').inert = true
// 닫을 때 해제하고 포커스를 되돌린다
document.querySelector('main').inert = false
opener.focus()
```

직접 구현해야 한다면 Tab 키를 가로채서 처음과 끝을 이어 줍니다.

```js
function trap(root, e) {
  if (e.key !== 'Tab') return
  const items = root.querySelectorAll(FOCUSABLE)
  const first = items[0]
  const last = items[items.length - 1]
  const active = root.getRootNode().activeElement
  if (e.shiftKey && active === first) {
    e.preventDefault(); last.focus()
  } else if (!e.shiftKey && active === last) {
    e.preventDefault(); first.focus()
  }
}
```

- `FOCUSABLE`은 포커스 가능한 요소를 고르는 선택자 목록입니다(`a[href]`, `button:not([disabled])`, `input:not([disabled])`, `select`, `textarea`, `[tabindex]:not([tabindex="-1"])` 등).
- `querySelectorAll`은 중첩된 shadow 트리 안의 요소를 찾지 못합니다. 안쪽에 포커스 가능한 요소를 둔 컴포넌트가 있으면 직접 shadow 루트를 순회해야 합니다. 이 때문에 `inert`나 `dialog` 쪽이 안정적입니다.
- 트랩에는 항상 탈출구가 필요합니다. `Escape`로 닫을 수 있어야 하고, 닫을 때 열기 전에 포커스가 있던 요소로 돌려줍니다.
- 모달이 아닌 영역(드롭다운, 인라인 패널)에는 트랩을 걸지 않습니다. 키보드로 빠져나갈 수 없는 상태는 접근성 오류입니다.
- 포커스를 가진 요소가 사라지면(삭제, `hidden`) 포커스가 `body`로 이동합니다. 트랩이 열린 동안 내용이 바뀌면 포커스를 안쪽의 적절한 곳으로 다시 줍니다.
- 오버레이 전체의 설계(스택, 배경 처리, 포커스 복귀)는 45편에서 다룹니다.

## 핵심 정리

- 복합 위젯은 Tab 순서에서 한 칸만 차지하고, 안에서는 방향키로 이동하며 Home·End·Escape·Enter·Space를 지원합니다. 위젯별 키는 APG 패턴을 따릅니다.
- `tabindex`는 `0`(Tab 순서에 포함)과 `-1`(`focus()`로만 이동)만 쓰고, 양수 값은 쓰지 않습니다. `tabindex`로 포커스를 막을 수는 없고 `disabled`나 `inert`를 씁니다.
- `focus`·`blur`는 버블링하지 않으므로 컨테이너에서는 `focusin`·`focusout`을 쓰고, `:focus-visible`로 표시를 정하며 `focus()`의 `preventScroll`·`focusVisible` 옵션으로 조절합니다.
- 항목 이동은 roving tabindex(DOM 포커스 이동) 또는 `aria-activedescendant`(포커스 고정, 활성 항목 가리킴)로 구현합니다.
- shadow 안의 포커스는 바깥에서 호스트로 보이므로 `document.activeElement`는 호스트, `shadowRoot.activeElement`는 안쪽 요소입니다. `delegatesFocus`는 호스트에 대한 포커스를 첫 포커스 가능한 내부 요소로 넘깁니다.
- 모달의 포커스 트랩은 `dialog`의 `showModal()`이나 `inert`를 우선 쓰고, 직접 구현할 때는 탈출구와 포커스 복귀를 갖춥니다.

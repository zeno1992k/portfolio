## AbortController

AbortController는 진행 중인 비동기 작업에 취소를 알리는 객체입니다. `signal`(AbortSignal)을 작업에 넘기고, 취소하고 싶을 때 컨트롤러의 `abort()`를 부릅니다. 취소하는 쪽(컨트롤러)과 취소를 받는 쪽(신호)이 분리되어 있어서, 신호만 넘기면 작업은 취소 권한을 갖지 못합니다.

```js
const controller = new AbortController()
fetch('/api/items', { signal: controller.signal })
  .catch((err) => console.log(err.name)) // 'AbortError'
controller.abort()
```

- `new AbortController()`는 인수가 없고, `signal` 프로퍼티는 읽기 전용입니다.
- `abort(reason)`의 `reason`은 어떤 값이든 됩니다. 생략하면 `AbortError` 이름의 DOMException이 reason이 됩니다.
- 컨트롤러는 한 번만 쓸 수 있습니다. 이미 취소된 신호는 되돌릴 수 없고, `abort()`를 다시 불러도 아무 일이 없습니다. 다시 요청하려면 새 컨트롤러를 만듭니다.
- 이미 취소된 신호로 `fetch()`를 부르면 요청을 보내지 않고 바로 거부됩니다.
- AbortController와 AbortSignal은 Baseline 2019로 널리 지원됩니다. 워커에서도 씁니다.

**흔한 실수:** 컨트롤러 하나를 요청마다 재사용하는 것입니다. 첫 `abort()` 이후 만든 모든 요청이 시작하자마자 거부됩니다. 요청마다 컨트롤러를 새로 만듭니다.

## AbortSignal

AbortSignal은 취소 상태를 담은 읽기 전용 객체입니다. `EventTarget`을 상속하므로 `abort` 이벤트를 받을 수 있습니다(이벤트 일반은 07편).

| 멤버 | 설명 |
|------|------|
| `aborted` | 취소되었으면 `true` |
| `reason` | 취소 사유. 취소 전에는 `undefined` |
| `abort` 이벤트 | 취소되는 순간 한 번 발생. `onabort` 속성도 있음 |
| `throwIfAborted()` | 취소되었으면 `reason`을 throw하고, 아니면 아무것도 하지 않음 |
| `AbortSignal.abort(reason)` | 이미 취소된 신호를 만드는 정적 메서드 |

```js
const signal = AbortSignal.abort()
signal.aborted       // true
signal.reason.name   // 'AbortError'
signal.throwIfAborted() // AbortError를 throw
```

### abort reason과 AbortError·TimeoutError

`fetch()`는 신호가 취소되면 그 신호의 `reason`으로 프라미스를 거부합니다. 그래서 어떤 이유로 취소됐는지가 에러에 그대로 담깁니다.

| 취소 방법 | reason(에러) |
|-----------|--------------|
| `controller.abort()` | `AbortError` DOMException |
| `controller.abort(값)` | 넘긴 값 그대로 |
| `AbortSignal.timeout(ms)` | `TimeoutError` DOMException |
| 이미 취소된 신호를 `AbortSignal.abort()`로 생성 | `AbortError` DOMException |

```js
try {
  await fetch(url, { signal })
} catch (err) {
  if (err.name === 'TimeoutError') showTimeout()
  else if (err.name === 'AbortError') return // 의도한 취소
  else showError(err) // 네트워크 오류는 TypeError
}
```

- `AbortError`는 대개 의도한 취소이므로 에러 화면을 띄우지 않고 조용히 무시합니다.
- 시간 초과는 `TimeoutError`로 구분해서 "응답이 늦습니다" 같은 안내를 보입니다.
- 사용자 정의 reason을 넘기면 `err.name`으로 구분할 수 없으므로, 에러 객체를 직접 만들어 넘기거나 `signal.reason`을 비교합니다.
- 응답 본문을 읽는 중에 취소되면 본문 스트림이 같은 reason으로 에러가 나서 `await res.json()`이 거부됩니다.

### throwIfAborted()와 abort 이벤트

`throwIfAborted()`는 신호를 받지 않는 긴 동기·비동기 작업의 중간 지점에서 취소를 검사할 때 씁니다. 반복문 안에서 불러 두면 취소 즉시 작업을 끝낼 수 있습니다.

```js
async function processAll(items, signal) {
  for (const item of items) {
    signal.throwIfAborted() // 취소됐으면 여기서 중단
    await handle(item)
  }
}
```

`abort` 이벤트는 취소 시점에 정리 작업을 하고 싶을 때 씁니다. 이미 취소된 신호에는 이벤트가 다시 오지 않으므로, 리스너를 달기 전에 `aborted`를 먼저 검사해야 합니다.

```js
if (signal.aborted) return cleanup()
signal.addEventListener('abort', cleanup, { once: true })
```

### AbortSignal을 받는 API 목록

| API | 취소했을 때 |
|-----|-------------|
| `fetch()`, `new Request()` | 프라미스가 reason으로 거부, 본문 스트림도 에러 |
| `addEventListener()`의 `signal` 옵션 | 리스너가 제거됨 |
| `ReadableStream.pipeTo()`·`pipeThrough()` | 파이프가 중단됨(자세히는 38편) |
| `navigator.locks.request()` | 락 요청이 취소됨 |
| `scheduler.postTask()` | 작업이 취소되고 프라미스가 reason으로 거부(미Baseline) |

- 리스너 해제에 쓰는 방법은 한 컨트롤러로 여러 리스너를 한 번에 제거할 수 있다는 점이 장점입니다. 컴포넌트 정리 패턴은 67편에서 다룹니다.
- 신호를 받지 않는 API(`setTimeout`, 직접 만든 Promise 등)는 `abort` 이벤트나 `throwIfAborted()`로 직접 연결해야 합니다.
- 신호는 취소를 알릴 뿐 작업을 강제로 멈추지 않습니다. 서버는 이미 요청을 받아 처리 중일 수 있으므로, 취소가 서버 쪽 부작용(결제, 저장)을 되돌리지는 않습니다.

## 요청 Timeout

fetch에는 타임아웃 옵션이 없으므로 신호로 만듭니다. `AbortSignal.timeout(ms)`는 지정 시간이 지나면 `TimeoutError`로 취소되는 신호를 돌려줍니다(Baseline 2024).

```js
const res = await fetch('/api/items', {
  signal: AbortSignal.timeout(5000),
})
```

- 시간은 0부터 `Number.MAX_SAFE_INTEGER` 사이의 밀리초입니다.
- 타이머는 경과 시간이 아니라 활동한 시간 기준입니다. 서스펜드된 워커나 bfcache에 들어간 문서에서는 타이머가 멈춥니다.
- 타임아웃은 요청을 보낸 시점이 아니라 신호를 만든 시점부터 셉니다. 신호는 요청 직전에 만듭니다.
- 이 신호는 조기에 취소할 방법이 없습니다. 완료 후 타이머를 걷어내고 싶다면 `AbortController`와 `setTimeout`·`clearTimeout`을 직접 씁니다.
- 지원하지 않는 환경에서는 `AbortSignal.timeout`이 없어 TypeError가 납니다.

### AbortSignal.any()로 신호 합치기

사용자 취소와 타임아웃처럼 취소 원인이 여럿일 때 `AbortSignal.any(iterable)`로 신호를 하나로 합칩니다. 합친 신호는 원본 중 하나라도 취소되면 취소되고, reason은 가장 먼저 취소된 신호의 reason입니다(Baseline 2024).

```js
const userCancel = new AbortController()
const signal = AbortSignal.any([
  userCancel.signal,
  AbortSignal.timeout(5000),
])
await fetch('/api/items', { signal })
```

- 하나라도 이미 취소된 상태면 합친 신호도 만들어질 때 이미 취소되어 있습니다.
- `signal.reason`의 이름으로 `AbortError`(사용자)와 `TimeoutError`(시간 초과)를 구분할 수 있습니다.
- 지원이 없는 환경에서는 `AbortController` 하나를 만들어 각 신호의 `abort` 이벤트에서 `abort(reason)`을 부르는 방식으로 대신합니다.

### 재시도마다 타임아웃 새로 만들기

한 요청의 제한 시간과 전체 작업의 제한 시간은 다릅니다. 시도마다 새 `AbortSignal.timeout()`을 만들고, 전체 취소 신호와는 `any()`로 합칩니다. 시도 하나가 시간 초과로 끝나도 전체 신호는 취소되지 않아 재시도를 이어 갑니다.

## Retry 전략

재시도는 일시적 실패를 사용자 모르게 넘기는 방법입니다. 재시도해도 되는 요청과 실패를 가려내는 것이 먼저입니다.

### 재시도해도 되는 요청

- 메서드가 멱등이어야 합니다. 멱등 메서드는 같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같은 메서드이고, GET·HEAD·OPTIONS·PUT·DELETE가 해당합니다. POST와 PATCH는 멱등이 보장되지 않으므로 그대로 재시도하면 중복 생성 같은 부작용이 생길 수 있습니다.
- POST를 재시도해야 하면 서버가 중복을 걸러내도록 요청마다 고유한 멱등 키를 헤더로 보내는 방식이 흔합니다. 헤더 이름과 동작은 서버 API가 정하며 브라우저 표준이 아닙니다.
- 본문이 스트림인 요청은 한 번 보내면 다시 읽을 수 없어 재시도할 수 없습니다.

| 실패 | 재시도 |
|------|--------|
| 네트워크 오류(`TypeError`) | 한다 |
| `TimeoutError` | 한다 |
| 429, 503 | 한다. `Retry-After`가 있으면 따른다 |
| 502, 504 등 일시적 서버 오류 | 한다(멱등 요청만) |
| 400, 401, 403, 404, 422 등 | 하지 않는다. 같은 요청은 같은 결과가 나온다 |
| `AbortError`(사용자 취소) | 하지 않는다 |

HTTP 오류 상태는 fetch가 거부하지 않으므로 `res.ok`를 검사해 직접 던져야 재시도 로직에 걸립니다(자세히는 36편).

### 지수 백오프와 지터

지수 백오프는 재시도할 때마다 대기 시간을 배로 늘리고 상한(cap)을 두는 방식입니다. 서버가 회복할 시간을 주고 요청 폭주를 막습니다. 지터는 대기 시간에 무작위를 섞는 것으로, 수많은 클라이언트가 같은 순간에 재시도해 서버를 다시 쓰러뜨리는 현상을 흩뜨립니다.

| 방식 | 대기 시간 |
|------|-----------|
| 지터 없음 | `min(cap, base * 2 ** n)` |
| 풀 지터 | `random(0, min(cap, base * 2 ** n))` |

`n`은 지금까지 실패한 횟수, `base`는 첫 대기 시간, `cap`은 상한입니다. AWS의 비교 글은 풀 지터와 직전 대기 시간에 기대는 변형(상관 지터)이 지터 없는 방식보다 훨씬 낫다고 보고하며, 풀 지터가 전체 작업량이 조금 더 적다고 설명합니다. 이 편은 풀 지터를 씁니다.

```js
async function withRetry(task, { tries = 3, base = 300,
  cap = 5000, signal } = {}) {
  for (let n = 0; ; n++) {
    try {
      return await task(signal)
    } catch (err) {
      if (n + 1 >= tries || !isRetryable(err)) throw err
      const max = Math.min(cap, base * 2 ** n)
      const wait = err.retryAfter ?? Math.random() * max
      await sleep(wait, signal)
    }
  }
}
```

대기도 취소할 수 있어야 사용자가 취소했을 때 재시도 대기 중이던 작업이 바로 끝납니다.

```js
function sleep(ms, signal) {
  return new Promise((resolve, reject) => {
    signal?.throwIfAborted()
    const id = setTimeout(resolve, ms)
    signal?.addEventListener('abort', () => {
      clearTimeout(id)
      reject(signal.reason)
    }, { once: true })
  })
}
```

판단 함수는 에러 이름과 상태로 가릅니다.

```js
function isRetryable(err) {
  if (err.name === 'AbortError') return false
  if (err.name === 'TimeoutError') return true
  if (err instanceof TypeError) return true // 네트워크 오류
  return [429, 502, 503, 504].includes(err.status)
}
```

### Retry-After

`Retry-After` 응답 헤더는 서버가 클라이언트에게 기다릴 시간을 알립니다. 값은 초 단위 정수이거나 HTTP 날짜 형식이고, 주로 429와 503에 붙습니다. 이 헤더가 있으면 계산한 백오프보다 이 값을 우선합니다.

```js
function retryAfterMs(res) {
  const v = res.headers.get('Retry-After')
  if (!v) return undefined
  if (/^\d+$/.test(v)) return Number(v) * 1000
  const t = Date.parse(v)
  if (Number.isNaN(t)) return undefined
  return Math.max(0, t - Date.now())
}
```

- 교차 출처 응답에서는 서버가 `Access-Control-Expose-Headers`로 노출해 주지 않으면 JavaScript가 이 헤더를 읽지 못합니다(CORS는 62편).
- 서버가 큰 값을 보낼 수 있으므로 사용자가 기다릴 수 있는 한도를 앱에서 정해 두고, 넘으면 재시도 대신 에러 화면을 보여 줍니다.
- 총 재시도 횟수와 전체 소요 시간에 상한을 둡니다. 상한 없는 재시도는 장애 때 서버 부하를 키웁니다.

**흔한 실수:** 모든 실패를 재시도하는 것입니다. 400대 오류를 재시도하면 같은 실패만 반복하고, 비멱등 POST를 재시도하면 같은 주문이 두 번 접수됩니다.

## 중복 요청 방지

같은 데이터를 요청하는 컴포넌트가 여럿이거나 사용자가 버튼을 연타하면 같은 요청이 동시에 여러 번 나갑니다. 진행 중인 요청을 키로 기억해 두고 같은 키의 요청에는 그 프라미스를 돌려주면 한 번만 보냅니다.

```js
const inflight = new Map()

function dedupe(key, start) {
  if (inflight.has(key)) return inflight.get(key)
  const p = start().finally(() => inflight.delete(key))
  inflight.set(key, p)
  return p
}
// dedupe('GET /api/me', () => getJson('/api/me'))
```

- 키는 메서드, URL(쿼리 포함)과 응답을 바꾸는 요청 헤더·본문을 모두 포함해야 합니다. 일부만 쓰면 다른 요청이 같은 응답을 받습니다.
- 공유 대상은 `Response`가 아니라 파싱한 결과입니다. 본문은 한 번만 읽을 수 있고 `clone()`은 하나씩 따로 해야 하므로, `start()`가 JSON까지 읽은 데이터를 돌려주게 합니다.
- `finally`로 성공과 실패 모두에서 키를 지웁니다. 실패한 프라미스를 남기면 이후 요청이 계속 같은 실패를 받습니다.
- 대상은 GET 같은 읽기 요청입니다. 쓰기 요청의 중복 방지는 버튼을 `disabled`로 만들거나 전송 중 플래그로 막습니다.
- 공유한 요청에 취소 신호를 하나씩 넘기면 한 구독자가 취소할 때 모두가 취소됩니다. 구독자 수를 세어 마지막 구독자가 취소할 때만 `abort()`하거나, 공유 요청은 취소하지 않고 결과만 무시합니다.

이전 요청을 취소하고 마지막 요청만 쓰는 방식은 같은 문제를 다른 방향으로 푸는 것으로 39편에서 다룹니다.

## 캐시 가능한 데이터

같은 데이터를 다시 받지 않는 방법은 두 층으로 나뉩니다. 브라우저의 HTTP 캐시는 헤더가 규칙을 정하고 브라우저가 자동으로 처리합니다. 앱 캐시는 메모리 같은 저장소에 코드가 직접 둡니다. 저장소 쪽 캐시(Cache API, 영속 저장)는 42편에서 다룹니다.

### 캐시할 수 있는 데이터 고르기

- 읽기 전용이고 자주 바뀌지 않는 데이터가 좋습니다: 코드 목록, 설정, 상세 정보.
- 사용자별 데이터는 캐시 키에 사용자를 구분하는 값이 들어가야 하고, 로그아웃하면 비워야 합니다.
- 쓰기 요청 결과, 실시간성이 높은 값, 민감한 정보는 캐시하지 않습니다.

### Cache-Control 헤더

서버가 `Cache-Control` 응답 헤더로 브라우저와 중간 캐시에 저장·재사용 규칙을 알립니다.

| 지시어 | 의미 |
|--------|------|
| `max-age=N` | 응답 생성 후 N초 동안 신선함. 신선하면 요청 없이 재사용 |
| `no-cache` | 저장은 하되, 재사용할 때마다 서버에 재검증 |
| `no-store` | 어떤 캐시에도 저장하지 않음 |
| `private` | 브라우저 같은 개인 캐시에만 저장 |
| `public` | 공유 캐시(CDN 등)에도 저장 가능 |
| `s-maxage=N` | 공유 캐시에서만 `max-age`를 대체 |
| `must-revalidate` | 신선도가 끝나면 반드시 재검증 후 재사용 |
| `immutable` | 신선한 동안 바뀌지 않음. 새로고침 때도 재검증하지 않음 |

- `no-cache`는 캐시하지 말라는 뜻이 아닙니다. 매번 재검증하라는 뜻이며, 저장 금지는 `no-store`입니다.
- 파일 이름에 해시를 넣는 정적 파일은 `public, max-age=31536000, immutable`로 오래 두고, URL이 바뀌어 갱신합니다.
- `Cache-Control`이 없어도 `Last-Modified`가 있으면 브라우저가 경험적으로 신선 기간을 정해 캐시할 수 있습니다. 의도한 동작이 필요하면 명시합니다.
- 같은 URL이라도 요청 헤더에 따라 응답이 다르면 `Vary`로 알립니다. 예를 들어 `Vary: Accept-Language`는 언어별로 따로 저장합니다.
- 코드에서는 `fetch(url, { cache })`로 요청 단위 동작을 조절합니다.

| `cache` 값 | 동작 |
|------------|------|
| `default` | 신선하면 재사용, 오래됐으면 재검증, 없으면 요청 |
| `no-store` | 캐시를 보지 않고 저장도 하지 않음 |
| `reload` | 캐시를 보지 않고 받은 응답은 저장 |
| `no-cache` | 있으면 재검증한 뒤 사용 |
| `force-cache` | 오래됐어도 있으면 그대로 사용, 없으면 요청 |
| `only-if-cached` | 있으면 사용, 없으면 504. `mode`가 `same-origin`일 때만 |

### 조건부 요청과 304

캐시가 오래됐을 때 전체를 다시 받지 않고, 서버에 "바뀌었나요"를 묻는 것이 조건부 요청입니다. 서버가 응답에 검증자를 실어 보내고, 브라우저가 다음 요청에 그 값을 되돌려 보냅니다.

| 검증자 | 응답 헤더 | 요청 헤더 |
|--------|-----------|-----------|
| 엔터티 태그 | `ETag: "abc"` | `If-None-Match: "abc"` |
| 수정 시각 | `Last-Modified: 날짜` | `If-Modified-Since: 날짜` |

```http
GET /api/items HTTP/1.1
If-None-Match: "33a64df5"

HTTP/1.1 304 Not Modified
```

- 변경이 없으면 서버는 본문 없이 `304 Not Modified`로 답하고, 브라우저는 저장해 둔 응답을 다시 신선한 것으로 씁니다. 왕복은 필요하지만 본문 전송은 생략됩니다.
- 바뀌었으면 새 응답과 함께 `200`을 보냅니다.
- `ETag`는 `W/"abc"`처럼 약한 검증자일 수 있습니다. 바이트 단위 동일이 아니라 의미상 같은 응답이라는 뜻입니다.
- `If-Match`와 `If-Unmodified-Since`는 쓰기 요청에 붙여, 그사이 서버 데이터가 바뀌었으면 `412 Precondition Failed`로 거절받는 낙관적 잠금에 씁니다.
- 브라우저 HTTP 캐시가 알아서 보내므로 코드에서 `If-None-Match`를 직접 붙일 일은 드뭅니다. 앱 캐시에서 검증을 직접 구현할 때만 씁니다.

### stale-while-revalidate

stale-while-revalidate는 오래된 응답을 즉시 보여 주면서 뒤에서 새로 받아 오는 전략으로, 대기 시간을 사용자에게 숨깁니다. HTTP 확장 지시어이면서 앱 캐시의 흔한 패턴입니다.

```http
Cache-Control: max-age=600, stale-while-revalidate=30
```

- 위 응답은 600초 동안 신선하고, 이후 30초 동안은 오래된 응답을 먼저 쓰면서 뒤에서 재검증할 수 있습니다. 30초가 지나면 일반 재검증으로 돌아갑니다.
- 앱 캐시에서는 캐시 값을 먼저 렌더링하고 요청이 끝나면 값을 교체하는 구조로 만듭니다.

```js
async function swr(key, load, render) {
  const hit = cache.get(key)
  if (hit) render(hit.data) // 오래됐어도 먼저 보여 줌
  if (hit && Date.now() - hit.at < TTL) return
  const data = await load()
  cache.set(key, { data, at: Date.now() })
  render(data)
}
```

- 오래된 데이터를 보여 주는 것이 허용되는 화면에만 씁니다. 가격, 재고처럼 틀리면 안 되는 값은 재검증이 끝나기 전에는 확정 표시를 하지 않습니다.
- 갱신 요청도 중복 방지와 취소를 거치게 해서 같은 키의 갱신이 겹치지 않게 합니다.

### 앱 캐시의 무효화

저장소가 어디든 앱 캐시에는 세 가지가 필요합니다.

- 키: 요청을 구분하는 모든 값(URL, 쿼리, 사용자)으로 만듭니다.
- 수명(TTL): 신선하다고 믿는 기간입니다.
- 무효화: 쓰기 요청이 성공하면 영향을 받는 키를 지웁니다. 지우거나 갱신하지 않으면 사용자가 방금 바꾼 값 대신 옛 값을 봅니다.

성공한 응답만 캐시하고, 실패는 캐시하지 않습니다. 진행 중인 요청 자체(프라미스)를 캐시에 넣으면 중복 방지와 결과 캐시가 한 구조가 됩니다.

## Data Service / Repository 계층

데이터 서비스(또는 리포지토리) 계층은 컴포넌트와 네트워크 사이에 두는 모듈로, 요청 방법과 데이터 모양을 한곳에 가둡니다. 컴포넌트는 `repo.getUser(id)`처럼 의미 있는 메서드만 부르고, URL·헤더·재시도·캐시를 모릅니다.

| 책임 | 계층 안에서 하는 일 |
|------|---------------------|
| 요청 구성 | 기본 URL, 헤더, 직렬화 |
| 오류 정규화 | 네트워크·HTTP·파싱 오류를 하나의 에러 타입으로 변환 |
| 신호 전달 | 호출자가 준 `signal`을 `any()`로 타임아웃과 합쳐 fetch에 전달 |
| 재시도·중복 방지·캐시 | 위의 전략을 적용 |
| 모델 변환 | 서버 응답 구조를 화면에서 쓰는 모양으로 변환 |

```js
class UserRepository {
  #cache = new Map()
  getUser(id, { signal } = {}) {
    const hit = this.#cache.get(id)
    if (hit) return hit
    const p = http.get(`/api/users/${id}`, { signal })
      .then(toUser)
      .catch((e) => { this.#cache.delete(id); throw e })
    this.#cache.set(id, p)
    return p
  }
}
```

- 호출자의 `signal`을 인수로 받아 아래 계층까지 전달하는 규칙을 지킵니다. 취소는 호출자가 결정하고, 계층은 전달만 합니다.
- 오류는 계층에서 한 번 정규화하고(`status`, `retryAfter`, `kind`), 컴포넌트는 종류만 보고 화면을 정합니다. 계층 아래 기술(fetch 사용)이 바뀌어도 컴포넌트는 그대로입니다.
- 서버 응답 모양을 화면용 모델로 바꾸는 코드는 계층 안에 둡니다. 서버가 필드 이름을 바꿔도 변경이 한곳에서 끝납니다.
- 계층은 인스턴스로 만들어 주입합니다. 테스트에서는 가짜 리포지토리로 바꿔 끼울 수 있습니다(테스트는 68편).
- 상태 관리는 별도의 역할입니다. 리포지토리는 데이터를 가져오는 일만 하고, 로딩·에러 상태와 상태 소유는 상태 계층이 맡습니다(31편, 32편). 위 예의 캐시는 응답 재사용 목적일 뿐입니다.
- 요청 흐름 전체는 `컴포넌트 → 리포지토리 → HTTP 클라이언트(타임아웃·재시도) → fetch` 순서로 쌓입니다. 각 층이 자기 책임만 가지면 한 층만 갈아 끼울 수 있습니다.

**흔한 실수:**

- 컴포넌트에서 `fetch()`를 직접 불러 URL·재시도·오류 처리를 컴포넌트마다 복제하는 것입니다.
- 리포지토리가 캐시한 객체를 컴포넌트가 직접 수정하는 것입니다. 같은 객체를 쓰는 다른 화면까지 바뀝니다. 읽기 전용으로 다루거나 복사해서 돌려줍니다.
- 캐시한 프라미스가 취소로 거부된 채 남아 이후 요청이 모두 실패하는 것입니다. 위 예의 `catch`처럼 실패하면 캐시에서 지웁니다.

## 핵심 정리

- AbortController는 취소하고 AbortSignal은 취소 상태를 전달합니다. 한 번 취소하면 되돌릴 수 없어 요청마다 새로 만듭니다.
- fetch는 취소되면 `signal.reason`으로 거부합니다. `AbortError`는 의도한 취소, `TimeoutError`는 시간 초과로 구분하고, 합칠 때는 `AbortSignal.any()`, 제한 시간은 `AbortSignal.timeout()`을 씁니다.
- 재시도는 멱등한 요청의 일시적 실패(네트워크 오류, 시간 초과, 429·503 등)에만 하고, 지수 백오프에 지터를 섞으며 `Retry-After`가 있으면 따릅니다.
- 같은 읽기 요청이 동시에 나가면 진행 중인 프라미스를 키로 공유하고, 끝나면 성공·실패 모두 키를 지웁니다.
- HTTP 캐시는 `Cache-Control`과 검증자(`ETag`, `Last-Modified`)로 동작하고, 오래된 값을 먼저 보여 주는 stale-while-revalidate 전략은 화면과 HTTP 양쪽에 쓰입니다.
- 취소·타임아웃·재시도·캐시는 데이터 서비스 계층에 모아 컴포넌트가 fetch를 직접 부르지 않게 합니다.

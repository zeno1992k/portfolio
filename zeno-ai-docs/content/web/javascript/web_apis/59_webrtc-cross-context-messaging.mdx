## WebRTC 개요

WebRTC(Web Real-Time Communication)는 플러그인 없이 브라우저끼리 오디오·영상·임의의 데이터를 직접(peer-to-peer) 주고받게 하는 표준 묶음입니다. 지원 상태는 Baseline 2020입니다. 화상 통화, 화면 공유, 파일 교환, 실시간 동기화에 쓰입니다.

| 인터페이스 | 역할 |
|-----------|------|
| `RTCPeerConnection` | 두 피어 사이의 연결과 그 수명 주기를 관리 |
| `RTCDataChannel` | 연결 위에서 임의의 데이터를 양방향으로 전송 |
| `MediaStream`, `MediaStreamTrack` | 카메라·마이크 같은 미디어(자세히는 51편) |

- 모든 WebRTC 연결은 기본적으로 암호화됩니다. 데이터 채널은 DTLS로, 미디어는 SRTP로 보호합니다.
- 미디어와 데이터는 피어끼리 직접 흐를 수 있지만 연결을 시작하려면 서버가 필요합니다. WebRTC 자체에는 상대를 찾고 정보를 교환하는 기능(시그널링)이 없습니다.
- 피어 사이에 NAT나 방화벽이 있으면 직접 연결이 안 될 수 있어 중계 서버를 쓰기도 합니다(아래 "ICE·STUN·TURN").
- 브라우저 간 구현 차이가 있어 adapter.js 같은 shim으로 흡수하는 경우가 있습니다.

## RTCPeerConnection과 시그널링

`RTCPeerConnection`은 로컬 피어와 원격 피어 사이의 연결 하나를 나타냅니다. 만들 때 ICE 서버 목록을 설정으로 넘깁니다.

```js
const pc = new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.example.com:3478' }],
})
pc.addEventListener('connectionstatechange', () => {
  console.log(pc.connectionState) // 'connected' 등
})
```

시그널링(signaling)은 연결을 맺는 데 필요한 정보를 두 피어가 주고받는 과정입니다. 주고받는 정보는 세션 설명(SDP)과 ICE 후보, 연결 제어 메시지입니다. 이 채널은 WebRTC가 정하지 않으므로 직접 고릅니다.

- 보통 WebSocket(자세히는 58편)을 쓰고, HTTP POST나 다른 프로토콜도 가능합니다.
- 시그널링 서버는 메시지를 상대에게 전달할 뿐 내용을 해석하지 않아도 됩니다. 연결이 맺어진 뒤에는 서버가 끼지 않고 피어끼리 직접 통신합니다.
- 서버에는 방(room) 개념, 사용자 인증, 연결 대상 선택 같은 앱 로직이 들어갑니다.

## offer·answer와 SDP

SDP(Session Description Protocol)는 미디어의 종류와 형식, 전송 프로토콜, 끝점의 IP·포트 같은 세션 정보를 적은 텍스트 형식입니다. 연결을 시작하는 쪽(caller)이 보내는 SDP를 offer, 받는 쪽(callee)이 응답하는 SDP를 answer라고 합니다. 각 피어는 자신을 설명하는 로컬 설명과 상대를 설명하는 원격 설명을 가집니다.

순서는 다음과 같습니다.

1. caller가 트랙이나 데이터 채널을 추가하면 `negotiationneeded` 이벤트가 발생합니다.
2. caller가 `createOffer()`로 offer를 만들고 `setLocalDescription(offer)`로 적용합니다.
3. offer를 시그널링으로 callee에게 보냅니다.
4. callee가 `setRemoteDescription(offer)`로 적용하고 `createAnswer()`로 answer를 만든 뒤 `setLocalDescription(answer)`로 적용합니다.
5. answer를 시그널링으로 caller에게 보내고, caller가 `setRemoteDescription(answer)`를 호출합니다.

```js
// caller
const offer = await pc.createOffer()
await pc.setLocalDescription(offer)
signaling.send({ type: 'offer', sdp: pc.localDescription })
// 답이 오면
await pc.setRemoteDescription(answerFromCallee)
```

```js
// callee
await pc.setRemoteDescription(offerFromCaller)
const answer = await pc.createAnswer()
await pc.setLocalDescription(answer)
signaling.send({ type: 'answer', sdp: pc.localDescription })
```

- `createAnswer()`와 `addIceCandidate()`는 `setRemoteDescription()`이 끝난 뒤에 호출해야 합니다.
- 상대의 미디어는 `track` 이벤트로 도착하고, 이때 `event.streams[0]`를 `video` 요소의 `srcObject`에 연결합니다.

## ICE·STUN·TURN

ICE(Interactive Connectivity Establishment)는 NAT 뒤에 있는 두 장치가 연결할 수 있는 경로를 찾는 프로토콜입니다. 각 피어는 연결 가능한 주소 후보를 모으고, 후보 쌍을 시험해 가장 좋은 쌍을 골라 연결합니다.

| 후보 유형 | 출처 |
|-----------|------|
| `host` | 장치의 로컬 IP 주소 |
| `srflx` (server reflexive) | STUN 서버가 알려 준, NAT 바깥에서 보이는 주소 |
| `prflx` (peer reflexive) | 연결을 시험하는 중에 피어가 발견한 주소. 트리클 ICE에서 흔함 |
| `relay` | TURN 서버가 중계해 주는 주소 |

- **STUN**(Session Traversal Utilities for NAT)은 자기 공인 주소를 알려 주는 가벼운 서버입니다. `srflx` 후보를 만듭니다.
- **TURN**(Traversal Using Relays around NAT)은 직접 연결이 불가능할 때 데이터를 중계하는 서버입니다. `relay` 후보를 만들며, 트래픽이 서버를 지나므로 비용과 지연이 큽니다. 인증 정보(`username`, `credential`)가 필요합니다.
- 서버는 `iceServers` 배열에 넣습니다.

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.example.com:3478' },
    {
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: 'secret',
    },
  ],
})
```

후보는 한꺼번에 모이지 않고 하나씩 발견됩니다. 발견될 때마다 `icecandidate` 이벤트가 발생하고, 이를 시그널링으로 상대에게 보내 `addIceCandidate()`로 추가하는 방식을 트리클 ICE(trickle ICE)라고 합니다. 모든 후보를 기다리지 않아 연결이 빨리 시작됩니다.

```js
pc.addEventListener('icecandidate', (e) => {
  if (e.candidate) {
    signaling.send({
      type: 'candidate',
      candidate: e.candidate,
    })
  }
})
// 받은 쪽: await pc.addIceCandidate(msg.candidate)
```

**흔한 실수:** TURN 없이 배포하는 것입니다. 개발 환경에서는 STUN만으로 연결되어도 사용자의 방화벽이 엄격하거나 NAT 때문에 직접 연결이 안 되면 연결이 실패합니다. 실서비스에서는 TURN을 준비합니다.

## RTCDataChannel

`RTCDataChannel`은 피어 연결 위에서 임의의 데이터를 주고받는 양방향 채널입니다. API는 WebSocket과 비슷하지만 서버를 거치지 않고 피어끼리 직접 전송합니다. 하나의 연결에 최대 65,534개 채널을 만들 수 있고, 전송은 SCTP over DTLS 위에서 일어납니다.

```js
const dc = pc.createDataChannel('chat', { ordered: true })
dc.onopen = () => dc.send('hello')
dc.onmessage = (e) => console.log(e.data)
// 원격 피어: pc.ondatachannel = (e) => { const dc = e.channel }
```

- 만든 쪽에서 `createDataChannel()`을 부르면 `negotiationneeded`가 발생해 offer가 만들어집니다. 상대는 `datachannel` 이벤트로 채널을 받습니다.
- `readyState`는 `connecting`, `open`, `closing`, `closed`입니다.
- `send()`는 문자열, `ArrayBuffer`, `Blob`, 타입 배열을 보냅니다. `binaryType`은 `'arraybuffer'`가 기본이고 `'blob'`도 쓸 수 있습니다.
- `bufferedAmount`는 큐에 쌓인 바이트 수이고, 이 값이 `bufferedAmountLowThreshold`(기본 0) 아래로 내려가면 `bufferedamountlow` 이벤트가 발생합니다. 큰 파일을 보낼 때 이 이벤트로 전송 속도를 조절합니다.

옵션으로 신뢰성 방식을 고릅니다.

| 방식 | 옵션 |
|------|------|
| 순서 있음 + 신뢰성 있음 (기본) | `ordered: true` |
| 순서 없음 + 신뢰성 있음 | `ordered: false` |
| 순서 있음 + 신뢰성 낮음 | `maxRetransmits` 또는 `maxPacketLifeTime` 지정 |

- `maxRetransmits`는 재전송 횟수 상한, `maxPacketLifeTime`은 전송을 시도하는 최대 시간(밀리초)입니다. 둘은 함께 쓰지 않습니다.
- `negotiated: true`와 `id`를 주면 양쪽이 미리 약속한 채널을 각자 만들어, offer를 통한 협상 없이 같은 채널을 씁니다.
- 게임 상태처럼 오래된 값이 의미 없는 데이터는 신뢰성을 낮추고, 채팅이나 파일은 기본값을 씁니다.

## BroadcastChannel

BroadcastChannel은 같은 출처의 탭, 창, iframe, 워커가 이름이 같은 채널로 메시지를 방송하는 API입니다. Baseline 2022이고 워커에서도 쓸 수 있습니다.

```js
const bc = new BroadcastChannel('auth')
bc.postMessage({ type: 'logout' })
bc.onmessage = (e) => {
  if (e.data.type === 'logout') showLoggedOut()
}
// 더 쓰지 않으면 bc.close()
```

- 같은 이름으로 `new BroadcastChannel(name)`을 만든 모든 객체가 메시지를 받습니다. 메시지를 보낸 객체 자신은 받지 않습니다.
- 데이터는 구조화 복제(자세히는 54편)로 전달되므로 객체, 배열, `Blob` 등을 보낼 수 있습니다. 복제할 수 없는 값은 `messageerror` 이벤트가 발생합니다.
- 같은 출처만 통신합니다. 더 나아가 저장소 파티셔닝(top-level 사이트 기준) 때문에, `a.com`에 삽입된 `b.com` iframe은 따로 열린 `b.com` 페이지와 통신하지 못합니다.
- 연결이 필요 없는 일 대 다 방송이라 응답을 보장하지 않습니다. 받는 탭이 없으면 메시지는 사라집니다.
- 사용처는 탭 간 로그인·로그아웃 동기화, 설정 변경 알림, 캐시 무효화, 한 탭만 연결을 맡도록 하는 조율입니다.
- 객체가 필요 없어지면 `close()`로 연결을 끊어야 가비지 컬렉션됩니다(자세히는 67편).

BroadcastChannel은 이벤트를 방송하는 용도이고, 한 번에 하나의 탭만 어떤 작업을 하도록 보장하는 상호 배제는 Web Locks API의 역할입니다. 워커로 연결을 공유하는 구조는 55편에서 비교합니다.

## window.postMessage

`postMessage()`는 서로 다른 출처의 창, 팝업, iframe 사이에서도 메시지를 안전하게 전달하는 방법입니다. 같은 출처 정책(자세히는 62편)이 직접 접근을 막는 곳에서 허용된 통로로 쓰입니다. Baseline 2015입니다.

```js
// 보내는 쪽
const frame = document.querySelector('iframe')
frame.contentWindow.postMessage(
  { type: 'ping' },
  'https://widget.example.com',
)
```

```js
// 받는 쪽
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://app.example.com') return
  console.log(e.data) // { type: 'ping' }
})
```

시그니처는 `postMessage(message, targetOrigin, transfer)` 또는 `postMessage(message, { targetOrigin, transfer })`입니다.

| 인수 | 설명 |
|------|------|
| `message` | 구조화 복제로 직렬화되는 값 |
| `targetOrigin` | 수신 창의 origin이 이 값과 같을 때만 전달. `'*'`는 아무 origin, `'/'`는 보내는 쪽과 같은 origin |
| `transfer` | 소유권을 넘기는 전송 가능 객체 배열(자세히는 54편) |

- `targetOrigin`을 `'*'`로 두면 수신 창이 이동했거나 다른 출처로 바뀌어도 메시지가 전달됩니다. 민감한 데이터는 `'*'`로 보내지 않고 정확한 origin을 적습니다.
- 받는 쪽은 `message` 이벤트의 `origin`을 반드시 확인하고, `data`의 형태와 타입도 검증합니다. 확인하지 않으면 어떤 사이트나 `window.open`된 창이든 메시지를 보내 동작을 일으킬 수 있습니다.
- `data`를 `innerHTML`에 넣거나 `eval`하는 것은 XSS가 되므로 하지 않습니다(자세히는 63편).

**흔한 실수:** 받는 쪽에서 `e.origin.includes('example.com')`처럼 부분 일치로 검사하는 것입니다. `example.com.evil.net`도 통과합니다. 허용 origin 목록과 정확히 비교합니다.

## MessageEvent의 origin·source·ports

`message` 이벤트 객체인 `MessageEvent`는 다음 속성을 가집니다.

| 속성 | 의미 |
|------|------|
| `data` | 보낸 값(구조화 복제된 사본) |
| `origin` | 보낸 쪽의 origin. 보낸 쪽이 속인 값이 아니라 브라우저가 채움 |
| `source` | 보낸 창(`WindowProxy`), 포트(`MessagePort`), 서비스 워커 중 하나 |
| `ports` | 메시지와 함께 전달된 `MessagePort` 배열 |
| `lastEventId` | SSE에서 쓰는 값. 창 간 메시징에서는 쓰지 않음 |

- `origin`은 신뢰의 근거입니다. `data` 안에 적힌 출처 주장은 믿지 않습니다.
- `source`는 응답을 보낼 대상입니다. 응답은 `e.source.postMessage(reply, e.origin)`처럼 `e.origin`을 `targetOrigin`으로 쓰면 올바른 상대에게만 전달됩니다.
- 하나의 페이지에 iframe이 여럿이면 `e.source === frame.contentWindow`로 어느 iframe이 보냈는지 구별합니다.
- 구조화 복제로 되살릴 수 없는 메시지가 오면 `messageerror` 이벤트가 발생합니다.

`ports`는 채널 메시징(Channel Messaging API)에 쓰입니다. `MessageChannel`은 `port1`과 `port2` 한 쌍을 만들고, 한쪽 포트를 `postMessage`의 전송 목록에 담아 상대에게 넘기면 두 쪽만의 전용 양방향 통로가 생깁니다.

```js
const channel = new MessageChannel()
frame.contentWindow.postMessage(
  { type: 'init' },
  'https://widget.example.com',
  [channel.port2], // 소유권을 넘김
)
channel.port1.onmessage = (e) => console.log(e.data)
// iframe 쪽: const port = e.ports[0]; port.postMessage('ok')
```

- 포트를 넘기면 원래 컨텍스트에서는 쓸 수 없게 됩니다.
- `onmessage`에 대입하면 수신이 자동으로 시작되지만, `addEventListener('message')`를 쓸 때는 `port.start()`를 불러야 합니다.
- 전용 포트를 쓰면 이후 메시지는 `window`의 `message` 이벤트를 거치지 않아 다른 창이 끼어들 수 없습니다. 안 쓰는 포트는 `close()`합니다.

## window.open()과 opener·noopener

`window.open(url, target, windowFeatures)`는 새 브라우징 컨텍스트(탭이나 팝업)를 열고 그 창의 `WindowProxy`를 돌려줍니다. 팝업 차단 등으로 열지 못하면 `null`입니다.

```js
button.addEventListener('click', () => {
  const url = 'https://example.org'
  const win = window.open(url, 'pay', 'popup')
  if (!win) showBlockedMessage() // 차단됨
})
```

- 팝업 차단을 피하려면 클릭 같은 사용자 조작(transient activation) 안에서 직접 호출해야 합니다. `setTimeout`이나 비동기 응답 뒤에 부르면 막힙니다.
- `popup` 기능을 주면 최소한의 UI의 팝업 창으로 열리고, 기본은 새 탭입니다.
- 열린 창은 기본적으로 `window.opener`로 연 창을 참조할 수 있습니다. 신뢰할 수 없는 대상을 열 때는 이 참조를 끊어야 합니다.
- `windowFeatures`의 `noopener`는 새 창의 `window.opener`를 `null`로 만듭니다. `noreferrer`는 `Referer` 헤더를 보내지 않으며 `noopener`를 함께 켭니다(링크에서는 `rel="noopener"`, `rel="noreferrer"`).
- 응답 헤더 `Cross-Origin-Opener-Policy`는 창 사이의 참조를 끊을 수 있고, 이 경우 `closed`가 `true`로 보입니다(자세히는 62편).

팝업과 연 창이 `postMessage`로 통신하는 흐름이 필요하면 `noopener`를 쓰지 않고, 서로 `origin`을 검증합니다. 결제나 OAuth 팝업이 이 방식으로 결과를 부모 창에 돌려줍니다. 팝업 창을 닫았는지는 `win.closed`로 확인합니다.

**흔한 실수:** 사용자 입력이나 외부 링크를 `window.open`으로 열면서 `noopener`를 쓰지 않는 것입니다. 열린 페이지가 `window.opener`로 연 창을 참조할 수 있게 됩니다.

## iframe과 부모 창 간 메시지 프로토콜 설계

부모 페이지와 iframe(결제 위젯, 임베드 콘텐츠, 샌드박스 편집기 등)이 서로 다른 출처라면 `postMessage` 위에 약속된 형식을 정해 사용합니다. 형식을 정하지 않고 아무 메시지나 보내면 확장과 보안 점검이 어렵습니다.

메시지 봉투(envelope)를 하나로 통일합니다.

```js
// 요청
{ v: 1, kind: 'request', id: 'r7', type: 'getSize' }
// 응답
{ v: 1, kind: 'response', id: 'r7', ok: true,
  payload: { h: 480 } }
// 알림(응답 없음)
{ v: 1, kind: 'event', type: 'resized',
  payload: { h: 520 } }
```

| 필드 | 역할 |
|------|------|
| `v` | 프로토콜 버전. 호환되지 않으면 거절 |
| `kind` | `request`, `response`, `event` 구분 |
| `id` | 요청과 응답을 짝짓는 값 |
| `type` | 동작 이름. 허용 목록으로만 처리 |
| `payload` | 구조화 복제 가능한 데이터 |

설계 규칙은 다음과 같습니다.

- **수신 검증**: 모든 `message` 핸들러는 `e.origin`을 허용 목록과 비교하고, `e.source`가 기대한 창(`iframe.contentWindow` 또는 `window.parent`)인지 확인하고, `data` 형태를 검증한 뒤에 처리합니다.
- **정확한 송신 대상**: `targetOrigin`에 `'*'`를 쓰지 않습니다. iframe은 부모의 origin을 `document.referrer`나 설정값으로 알고, 부모는 iframe의 `src` origin을 압니다.
- **핸드셰이크**: iframe은 로드가 끝나면 `ready` 이벤트를 먼저 보내고, 부모는 그 뒤에 `init`을 보냅니다. iframe이 준비되기 전에 보낸 메시지는 사라지기 때문입니다.
- **요청·응답**: 요청마다 `id`를 만들어 Promise를 보관하고, 같은 `id`의 응답이 오면 이행합니다. 응답이 없을 때를 대비해 시간 제한(타임아웃)을 둡니다.
- **전용 포트**: 핸드셰이크 때 `MessageChannel`의 포트 하나를 넘겨 이후 통신은 포트로 합니다. 같은 창으로 오는 다른 메시지와 섞이지 않고 `origin` 검사가 포트 수립 시점 한 번으로 줄어듭니다.
- **허용 목록**: `type`이 목록에 있는 것만 실행하고, 알 수 없는 값은 무시합니다. 부모가 iframe에 함수를 직접 실행하게 하는 메시지는 만들지 않습니다.
- **크기 보고**: iframe 높이를 부모에 알리는 `resized` 이벤트가 흔한 사용 예입니다.

```js
function request(win, origin, type, payload) {
  return new Promise((resolve, reject) => {
    const id = crypto.randomUUID()
    pending.set(id, { resolve, reject })
    const msg = { v: 1, kind: 'request', id, type, payload }
    win.postMessage(msg, origin)
    setTimeout(() => reject(new Error('timeout')), 5000)
  })
}
```

- 같은 출처의 여러 탭에 알리는 일은 BroadcastChannel로, 창 한 쌍 사이의 요청·응답은 `postMessage`로 나눕니다.
- iframe의 `allow` 속성으로 권한을 제한하는 방법은 60편에서 다룹니다.

## 핵심 정리

- WebRTC는 피어 사이의 직접 통신이지만 시그널링은 직접 구현해야 하며, 연결은 `createOffer`, `setLocalDescription`, 전송, `setRemoteDescription`, `createAnswer`, ICE 후보 교환 순서로 맺습니다.
- ICE는 `host`, `srflx`, `prflx`, `relay` 후보 중 연결 가능한 쌍을 고르고, STUN은 공인 주소를 알려 주며, TURN은 직접 연결이 안 될 때 중계합니다.
- `RTCDataChannel`은 `ordered`, `maxRetransmits`, `maxPacketLifeTime`으로 신뢰성 방식을 정하고 `bufferedAmount`로 전송 속도를 조절합니다.
- BroadcastChannel은 같은 출처(와 같은 저장소 파티션)의 컨텍스트에 방송하며 보낸 객체 자신은 받지 않고, 상호 배제가 필요하면 Web Locks를 씁니다.
- `postMessage`는 `targetOrigin`을 정확히 쓰고 받는 쪽에서 `origin`, `source`, `data` 형태를 반드시 검증합니다. 부분 일치 비교는 쓰지 않습니다.
- 외부 대상을 `window.open`으로 열 때는 `noopener`로 `window.opener`를 끊고, iframe 통신은 버전·`id`·`type`을 가진 봉투와 핸드셰이크, 전용 `MessagePort`로 설계합니다.

## SPA Routing 원리

SPA 라우팅은 페이지를 새로 불러오지 않고 URL에 맞는 화면을 같은 문서 안에서 갈아 끼우는 방식입니다. 라우터가 하는 일은 네 가지입니다.

1. 이동 요청을 잡는다(링크 클릭, 뒤로·앞으로 가기, 코드 호출).
2. 주소를 바꾼다(`pushState`나 Navigation API).
3. 새 주소에 맞는 라우트를 찾는다.
4. 라우트의 페이지 컴포넌트를 본문 자리(outlet)에 넣는다(자세히는 33편).

History API(34편)만으로 만든 가장 작은 라우터는 다음과 같습니다.

```js
function navigate(path, { replace = false } = {}) {
  const method = replace ? 'replaceState' : 'pushState'
  history[method](null, '', path)
  render()
}
addEventListener('popstate', render)
render() // 처음 로드 때는 이벤트가 없으므로 직접 호출
```

- 처음 로드에서는 `popstate`가 오지 않으므로 시작할 때 `render()`를 한 번 호출합니다.
- 링크 클릭은 브라우저가 문서를 새로 불러오므로 가로채야 합니다(아래 절).
- 서버는 앱이 처리하는 모든 경로에서 같은 HTML을 내려 줘야 합니다. 그렇지 않으면 `/orders/7`에서 새로고침했을 때 서버가 404를 돌려줍니다.
- 해시 라우팅은 서버 설정이 필요 없지만 프래그먼트 본래 용도와 충돌합니다(자세히는 34편).

## Route Table

라우트 테이블은 URL 패턴과 화면을 짝지은 목록입니다. 라우터는 현재 경로를 위에서부터 차례로 맞춰 보고 처음 일치하는 항목을 씁니다.

```js
const routes = [
  { path: '/', tag: 'home-page', title: '홈' },
  { path: '/orders', tag: 'orders-page', title: '주문' },
  { path: '/orders/:id', tag: 'order-page', title: '상세' },
  { path: '/*', tag: 'not-found-page', title: '없는 페이지' },
]
```

- 항목에는 패턴과 컴포넌트 외에 제목, 레이아웃, 접근 조건(로그인 필요 여부) 같은 메타데이터를 둡니다.
- 일치는 처음 맞는 항목에서 끝나므로 구체적인 패턴을 앞에, 포괄적인 패턴을 뒤에 둡니다. `/orders/new`를 `/orders/:id` 뒤에 두면 `new`가 `id` 값으로 잡힙니다.
- 테이블은 한곳에 모아 두면 앱의 모든 화면을 한눈에 볼 수 있고 링크를 만드는 코드도 같은 정의를 쓸 수 있습니다.

## URLPattern으로 경로 매칭

`URLPattern`은 URL을 패턴에 맞춰 검사하고 일부를 추출하는 표준 API입니다. Baseline 2025입니다.

```js
const p = new URLPattern({ pathname: '/orders/:id' })
p.test({ pathname: '/orders/7' })  // true
const m = p.exec({ pathname: '/orders/7' })
m.pathname.groups.id               // '7'
p.exec({ pathname: '/orders' })    // null
```

- 생성자는 구성 요소별 객체(`pathname`, `search`, `hostname` 등) 또는 문자열과 기준 URL을 받습니다. 지정하지 않은 구성 요소는 모두 일치합니다.
- `test()`는 불리언을, `exec()`는 일치하면 구성 요소별 결과 객체를, 아니면 `null`을 돌려줍니다. 추출한 값은 `result.pathname.groups`에 있습니다.
- 입력은 문자열 URL이나 같은 모양의 객체입니다.

| 문법 | 의미 | 예 |
|------|------|----|
| `:name` | 한 경로 조각을 이름 붙여 캡처 | `/orders/:id` |
| `:name?` | 있어도 되고 없어도 되는 조각 | `/orders/:id?` |
| `:name+`, `:name*` | 한 개 이상, 0개 이상 조각 | `/files/:path*` |
| `*` | 임의의 문자열 | `/docs/*` |
| `(정규식)` | 정규식 제한 | `/orders/:id(\d+)` |
| `{ }` | 묶음에 수량자 적용 | `/book{/:id}?` |

- 정규식 그룹을 쓰는지는 `hasRegExpGroups`로 알 수 있습니다.
- 라우트마다 `new URLPattern(...)`을 한 번만 만들어 재사용합니다. 이동할 때마다 만들면 낭비입니다.
- 지원하지 않는 브라우저를 위한 폴리필이 있습니다. 기능 검사는 `'URLPattern' in globalThis`로 합니다.

## Route Params와 Query

라우트 매개변수(param)는 경로 안에서 화면이 어떤 대상인지를 가리키는 값이고, 쿼리(query)는 같은 화면을 다듬는 선택 값입니다.

| 구분 | 예 | 담는 것 |
|------|----|---------|
| 경로 매개변수 | `/orders/7` | 대상의 식별자(필수) |
| 쿼리 | `/orders?status=open&page=2` | 필터, 정렬, 페이지(선택) |

```js
const url = new URL(location.href)
const m = pattern.exec({ pathname: url.pathname })
const id = m?.pathname.groups.id          // '7'
const page = Number(url.searchParams.get('page') ?? 1)
```

- 매개변수와 쿼리는 모두 문자열입니다. 숫자로 쓰려면 변환하고, `NaN`이거나 범위를 벗어나면 기본값이나 404로 처리합니다.
- 라우트 매칭에는 경로만 쓰고 쿼리는 일치 조건에서 뺍니다. 쿼리가 바뀌어도 같은 라우트라서 페이지를 다시 만들지 않고 페이지가 쿼리 변화에 반응하게 합니다.
- 식별자가 유효한지(그 주문이 있는지)는 라우터가 아니라 데이터를 불러온 페이지가 확인하고, 없으면 Not Found 화면을 보여 줍니다.
- 링크를 만들 때는 문자열을 이어 붙이지 않고 `URL`과 `URLSearchParams`를 씁니다(자세히는 34편).

## Nested Route

중첩 라우트는 URL의 앞부분이 바깥 화면을, 뒷부분이 안쪽 화면을 정하는 구조입니다. 바깥 화면은 안쪽 화면이 들어갈 자리를 따로 가집니다.

```js
const routes = [{
  path: '/settings', tag: 'settings-page',
  children: [
    { path: 'profile', tag: 'profile-pane' },
    { path: 'billing', tag: 'billing-pane' },
  ],
}]
```

- 매칭은 한 라우트가 아니라 라우트 사슬(`settings-page` → `billing-pane`)을 돌려줍니다.
- 렌더링은 바깥에서 안쪽 순서로 합니다. 각 수준은 자기 안의 outlet에 다음 수준을 넣습니다.
- 같은 부모 아래에서 자식만 바뀌면 부모 컴포넌트는 그대로 두고 자식만 교체합니다. 사이드바 같은 부모의 상태와 스크롤이 유지됩니다.
- 공통 틀(레이아웃)을 공유하는 가장 흔한 방법입니다. 부모 라우트가 레이아웃이고 자식이 페이지입니다(자세히는 33편).

```js
let host = outlet
for (const route of chain) {
  const cur = host.firstElementChild
  const el = cur?.localName === route.tag
    ? cur
    : document.createElement(route.tag)
  host.replaceChildren(el)
  host = el.querySelector('[data-outlet]')
}
```

## 404와 Not Found

일치하는 라우트가 없을 때 보여 줄 화면이 필요합니다. 테이블 맨 끝에 모든 경로와 일치하는 라우트(`/*`)를 둡니다.

- 404는 두 종류입니다. 라우트가 없는 경우(주소를 잘못 입력)와 라우트는 있지만 대상이 없는 경우(`/orders/999`에 주문이 없음)입니다. 둘 다 같은 Not Found 화면을 보여 주되, 앞의 것은 라우터가, 뒤의 것은 페이지가 판단합니다.
- 클라이언트 라우터는 HTTP 상태 코드를 바꿀 수 없습니다. 서버가 모든 경로에 같은 앱을 내려 주면 없는 주소도 200으로 응답합니다. 검색 엔진이 이런 페이지를 정상 페이지로 오해하지 않도록 Not Found 화면에 `noindex` 메타 태그를 추가하거나, 서버가 라우트 목록을 알고 404를 응답하게 합니다(자세히는 76편).
- Not Found 화면에는 홈이나 이전 화면으로 돌아가는 링크를 둡니다.

## 링크 클릭 가로채기와 제외 조건

History API로 만든 라우터는 링크 클릭을 가로채 `preventDefault()`하고 `navigate()`를 호출합니다. 가로채면 안 되는 경우를 먼저 걸러야 합니다.

```js
document.addEventListener('click', (e) => {
  if (e.defaultPrevented || e.button !== 0) return
  if (e.metaKey || e.ctrlKey) return
  if (e.shiftKey || e.altKey) return
  const path = e.composedPath()
  const a = path.find((n) => n instanceof HTMLAnchorElement)
  if (!a || (a.target && a.target !== '_self')) return
  if (a.hasAttribute('download')) return
  if (a.origin !== location.origin) return
  e.preventDefault()
  navigate(a.pathname + a.search + a.hash)
})
```

| 제외 조건 | 이유 |
|-----------|------|
| `defaultPrevented` | 다른 코드가 이미 처리함 |
| `button`이 0이 아님 | 가운데·오른쪽 클릭은 새 탭 열기, 메뉴 등 |
| 수정 키(`ctrl`, `meta`, `shift`, `alt`) | 새 탭·새 창·다운로드 같은 브라우저 동작을 사용자가 요청함 |
| `target`이 `_self`가 아님 | 다른 창이나 프레임에서 열라는 지시 |
| `download` 속성 | 파일을 내려받는 링크 |
| 출처가 다름 | 외부 사이트는 라우터가 처리할 수 없음 |

- Web Components에서는 링크가 Shadow DOM 안에 있을 수 있어 `e.target`이 호스트 요소로 바뀝니다(리타깃팅). `composedPath()`로 실제 `a` 요소를 찾습니다(자세히는 7편, 21편).
- `mailto:`나 `tel:` 링크는 `origin`이 `'null'`이라 출처 비교에서 걸러집니다.
- 해시만 다른 같은 문서 링크(`#section`)는 브라우저에 맡깁니다.
- 가로챌지 말지의 판단이 틀리면 새 탭으로 열기와 다운로드가 깨져 사용자 불만이 큽니다. 이 목록을 직접 관리하는 부담이 Navigation API가 생긴 이유 중 하나입니다.

## Navigation API 개요

Navigation API는 이 창의 모든 이동을 `navigation` 객체 하나로 다루는 API입니다. History API의 후속으로, 링크 클릭·폼 제출·`location` 대입·`pushState`·뒤로 가기가 모두 같은 `navigate` 이벤트로 들어옵니다.

- 지원 상태: Baseline 2026입니다. 2026년 1월부터 핵심 브라우저의 최신 버전에서 지원합니다. 이전 버전을 지원해야 하면 `'navigation' in window`로 검사해 History API 라우터로 대체합니다.
- 구성: `Navigation`(전체 제어), `NavigateEvent`(이동 이벤트), `NavigationHistoryEntry`(기록 항목), `NavigationTransition`(진행 중인 전환), `NavigationDestination`(목적지).
- 이 창과 같은 출처의 항목만 다루므로 다른 프레임이나 다른 출처의 기록은 보이지 않습니다.

History API와 비교하면 다음과 같습니다.

| 항목 | History API | Navigation API |
|------|-------------|----------------|
| 이동 감지 | `popstate`와 링크 클릭 직접 가로채기 | `navigate` 이벤트 하나 |
| 기록 목록 | `length`만 알 수 있음 | `entries()`로 항목과 키를 읽음 |
| 이동 시작 | 직접 `pushState` 후 직접 렌더링 | `navigate()`가 이벤트를 거쳐 처리 |
| 진행 상태 | 없음 | `transition`, `navigatesuccess`, `navigateerror` |
| 상태 저장 | `history.state` | 항목마다 `getState()` |
| 취소 | 불가 | `signal`로 이동이 취소되면 알림 |

## navigate 이벤트와 intercept()

`navigate` 이벤트는 이 창이 이동하기 직전에 `navigation`에서 발생합니다. `event.intercept()`를 호출하면 브라우저의 전체 문서 로드를 막고 같은 문서 안의 이동으로 바꾸며, 화면 갱신은 `handler`가 맡습니다.

```js
navigation.addEventListener('navigate', (e) => {
  if (!e.canIntercept || e.hashChange) return
  if (e.downloadRequest !== null || e.formData) return
  const url = new URL(e.destination.url)
  e.intercept({
    async handler() { await show(url) },
  })
})
```

`NavigateEvent`의 주요 속성은 다음과 같습니다.

| 속성 | 뜻 |
|------|----|
| `canIntercept` | 가로챌 수 있는지. 다른 출처로의 이동은 `false` |
| `destination` | 목적지(`url`, `getState()` 등) |
| `navigationType` | `'push'`, `'replace'`, `'reload'`, `'traverse'` 중 하나 |
| `hashChange` | 프래그먼트만 바뀌는 이동인지 |
| `downloadRequest` | 다운로드 링크이면 파일 이름, 아니면 `null` |
| `formData` | POST 폼 제출이면 `FormData`, 아니면 `null` |
| `userInitiated` | 사용자가 일으킨 이동인지 |
| `signal` | 이동이 취소되면 중단되는 `AbortSignal` |
| `info` | `navigation.navigate()` 등이 넘긴 임의의 데이터 |

- 이 이벤트는 이 창의 이동에서만 발생합니다. 수정 키 클릭이나 `target="_blank"`는 다른 창의 이동이어서 이 창에는 이벤트가 오지 않으므로 앞 절의 제외 조건을 직접 검사할 필요가 없습니다.
- 처음 문서가 로드될 때는 `navigate` 이벤트가 발생하지 않으므로 시작 시 현재 주소의 화면을 직접 그려야 합니다.
- 해시 이동, 다운로드, 폼 제출은 앱 정책에 따라 가로채거나 건너뜁니다. 폼 제출은 `formData`로 본문을 받아 `fetch`로 보낼 수 있습니다.
- `intercept()`는 다음 순서로 진행됩니다. `precommitHandler`가 있으면 먼저 실행하고, 이동이 확정(commit)되어 `currentEntry`와 주소가 바뀌고, `handler`가 실행되고, 모든 약속이 이행되면 `navigatesuccess`가 발생합니다.
- `handler`는 확정 뒤에 실행됩니다. 즉 주소는 데이터를 기다리기 전에 이미 바뀝니다. 약속이 거부되면 `navigateerror`가 발생하고 이동은 실패로 끝납니다.
- `signal`을 `fetch`에 넘기면 사용자가 다른 링크를 눌러 이동이 취소될 때 진행 중 요청도 중단됩니다(자세히는 37편, 39편).
- `handler`를 여러 번 `intercept()`로 등록할 수 있고, 이동은 모든 약속이 끝나야 완료됩니다.

```js
navigation.navigate('/orders/7', { state: { tab: 'info' } })
navigation.navigate('/login', { history: 'replace' })
```

- `navigation.navigate(url, options)`: 코드로 이동합니다. `history`는 `'push'`, `'replace'`, `'auto'`이고, `state`는 항목에 붙고, `info`는 이벤트로 전달됩니다.
- `back()`, `forward()`, `reload()`: 같은 이름의 이동입니다. 갈 수 없는 방향은 `canGoBack`, `canGoForward`로 확인합니다.
- 이동 메서드는 `committed`와 `finished` 약속을 가진 객체를 돌려줍니다. `await navigation.navigate(url).finished`로 완료를 기다립니다.
- 같은 `NavigateEvent`가 `history.pushState()`로 이뤄지는 이동에서도 발생합니다. 기존 코드가 `pushState`를 쓰고 있어도 한곳에서 처리됩니다.

## entries·currentEntry·traverseTo

`navigation.entries()`는 이 창에서 같은 출처인 기록 항목의 배열을 돌려줍니다. 현재 위치와 이전·이후 항목을 읽을 수 있다는 점이 `history.length`와 다릅니다.

```js
const entries = navigation.entries()
const here = navigation.currentEntry
here.index   // 현재 항목의 위치
here.url     // 절대 URL 문자열
here.key     // 이 자리(slot)의 식별자
here.getState() // 항목에 붙은 상태의 복제본
```

- `NavigationHistoryEntry`의 `key`는 기록 목록의 자리를 가리키며 그 자리가 다른 항목으로 대체되어도 유지됩니다. `id`는 항목 자체의 식별자로 바뀌지 않습니다. 이동에는 `key`를 씁니다.
- `navigation.traverseTo(key)`는 해당 항목으로 이동합니다. 몇 칸 뒤인지 계산하는 `history.go(-n)`과 달리 항목을 직접 지정합니다. 목록 화면의 키를 저장해 두었다가 상세 화면의 "목록으로" 버튼에서 그 키로 돌아가면 화면 사이를 오간 횟수와 상관없이 같은 항목에 갑니다.
- 항목에 붙은 상태는 `navigate()`의 `state` 옵션으로 정하고 `getState()`로 읽습니다. 현재 항목의 상태는 `updateCurrentEntry({ state })`로 이동 없이 바꿉니다.
- 항목이 기록에서 사라지면(앞으로 갈 수 있던 항목이 새 이동으로 잘림) 그 항목에 `dispose` 이벤트가 발생합니다. 항목별로 저장한 자원을 정리할 때 씁니다.

## navigation.transition과 성공·실패 이벤트

가로챈 이동이 진행되는 동안 `navigation.transition`은 `NavigationTransition` 객체이고, 진행 중인 이동이 없으면 `null`입니다.

| 멤버 | 뜻 |
|------|----|
| `navigationType` | 진행 중 이동의 종류 |
| `from` | 이동 전의 기록 항목 |
| `committed` | 주소가 바뀌어 `currentEntry`가 갱신되면 이행 |
| `finished` | `navigatesuccess`에서 이행, `navigateerror`에서 거부 |

```js
navigation.addEventListener('navigate', () => {
  progress.hidden = false
})
navigation.addEventListener('navigatesuccess', () => {
  progress.hidden = true
})
navigation.addEventListener('navigateerror', (e) => {
  progress.hidden = true
  showError(e.error) // handler가 던진 오류
})
```

- `navigatesuccess`는 모든 `handler`가 성공했을 때, `navigateerror`는 하나라도 거부되거나 이동이 중단되었을 때 `navigation`에서 발생합니다.
- `navigation.transition.finished`를 기다리면 이벤트 없이도 같은 결과를 얻습니다. 진행 표시줄, 로딩 상태, 오류 화면에 씁니다.
- 이동이 다른 이동으로 교체되면 앞의 이동은 중단되고 `signal`이 중단됩니다.

## 라우트 단위 코드 스플리팅

라우트 단위 코드 스플리팅은 각 화면의 코드를 별도 파일로 나눠 그 라우트에 처음 들어갈 때 불러오는 방식입니다. 동적 `import()`가 쓰입니다(자세히는 14편).

```js
const routes = [
  {
    path: '/orders', tag: 'orders-page',
    load: () => import('./pages/orders-page.js'),
  },
]
async function show(route) {
  await route.load()   // 모듈이 컴포넌트를 정의함
  outlet.replaceChildren(document.createElement(route.tag))
}
```

- 모듈은 한 번 불러오면 캐시되어 두 번째 이동부터는 즉시 해결됩니다.
- 불러오는 동안 로딩 화면을 보여 줍니다. 이동이 취소되면 늦게 도착한 결과로 화면을 덮어쓰지 않도록 확인합니다(자세히는 39편).
- 사용자가 곧 갈 만한 라우트는 미리 가져옵니다. 링크 위에 마우스를 올리거나 유휴 시간에 `import()`를 호출하거나 `modulepreload` 힌트를 씁니다(자세히는 15편).
- 불러오기는 실패할 수 있습니다. 새 배포로 파일 이름이 바뀌었거나 네트워크가 끊겼을 때입니다. 실패하면 오류 화면과 다시 시도 버튼을 보여 주고, 배포 버전 불일치가 의심되면 문서를 새로 불러옵니다(자세히는 73편).
- 모든 라우트를 쪼개면 이동할 때마다 지연이 생깁니다. 첫 화면에 필요한 코드는 묶고 나머지를 나눕니다.

## 라우트 전환 후 포커스·스크롤·제목 처리

문서가 새로 로드되면 브라우저가 알아서 하던 일을 SPA는 직접 해야 합니다. 안 하면 키보드와 스크린 리더 사용자는 화면이 바뀐 것을 알 수 없습니다.

| 할 일 | 방법 |
|-------|------|
| 포커스 | 새 화면의 제목(`h1`)이나 `main`으로 옮김. 대상에 `tabindex="-1"` 필요 |
| 스크롤 | 새 이동이면 맨 위로, 뒤로 가기이면 이전 위치로 |
| 문서 제목 | `document.title`을 라우트의 제목으로 갱신 |
| 알림 | 제목 변경만으로는 알리지 않으므로 포커스 이동이나 `aria-live` 영역 사용 |

Navigation API의 `intercept()`는 기본으로 `focusReset`과 `scroll`이 `'after-transition'`입니다. 이동이 끝나면 `autofocus` 요소나 `body`로 포커스를 되돌리고, 스크롤은 프래그먼트·복원 규칙을 따릅니다. 앱이 직접 하려면 `'manual'`로 바꿉니다.

```js
e.intercept({
  focusReset: 'manual',
  scroll: 'manual',
  async handler() {
    await show(url)
    document.title = route.title
    document.querySelector('h1')?.focus()
    e.scroll() // 내용이 그려진 뒤 기본 스크롤 규칙 적용
  },
})
```

- `e.scroll()`은 기본 스크롤 동작(맨 위 이동, 뒤로 가기 복원, 프래그먼트 이동)을 원하는 시점에 실행합니다. 첫 내용을 그린 뒤 부가 내용을 비동기로 그리는 경우에 씁니다.
- 포커스를 `body`로 되돌리는 기본 동작은 키보드 사용자를 문서 맨 앞에서 다시 시작하게 합니다. 제목으로 옮기는 편이 낫습니다(자세히는 28편).
- 문서 제목은 화면 이동을 알리는 첫 신호이므로 경로마다 다르게 둡니다. 모든 화면이 같은 제목이면 탭과 기록에서 구별되지 않습니다.
- History API 라우터에서는 `popstate`와 `navigate()` 각각에서 같은 일을 직접 합니다. 뒤로 가기의 스크롤 복원은 `scrollRestoration = 'manual'`로 두고 `history.state`에 저장한 위치를 씁니다(자세히는 34편).
- 레이아웃의 건너뛰기 링크와 본문 `main` 대상은 그대로 유지됩니다(자세히는 33편).

## precommit 핸들러

`precommitHandler`는 `intercept()` 옵션으로, 이동이 확정되기 전에 실행되는 핸들러입니다. 미Baseline이라 일부 핵심 브라우저가 아직 지원하지 않습니다.

```js
e.intercept({
  async precommitHandler(controller) {
    if (!signedIn) {
      controller.redirect('/signin', { history: 'push' })
    }
  },
})
```

- 일반 `handler`는 확정 뒤에 실행되므로 데이터를 기다리는 동안에도 주소가 이미 바뀌어 있습니다. 접근 권한이 없거나 필수 데이터를 불러오지 못하면 되돌릴 방법이 없어 두 번째 이동을 따로 해야 합니다.
- `precommitHandler`가 끝나기 전에는 주소와 `currentEntry`가 바뀌지 않으므로 그 안에서 권한을 검사하고, 거부하거나 `controller.redirect()`로 다른 주소로 확정시킬 수 있습니다. `redirect()`는 `state`와 `history` 옵션을 받습니다.
- `controller.addHandler()`는 확정 뒤에 실행할 핸들러를 추가합니다.
- 취소할 수 없는 이동(`cancelable`이 거짓)에서 `precommitHandler`를 쓰면 SecurityError입니다.
- 지원하지 않는 환경에서는 `handler` 안에서 `navigation.navigate('/signin', { history: 'replace' })`로 대체합니다. 라우트 메타데이터의 접근 조건을 한곳에서 검사하면 대체 코드도 한곳에 둘 수 있습니다.

## 핵심 정리

- SPA 라우터는 이동을 잡고, 주소를 바꾸고, 라우트를 찾고, 페이지를 outlet에 넣습니다. 처음 로드는 이벤트가 없어 직접 렌더링하고, 서버는 앱의 모든 경로에 같은 HTML을 내려 줘야 합니다.
- 라우트 테이블은 위에서부터 처음 일치하는 항목을 쓰고(구체적인 것이 앞), 맨 끝에 404 라우트를 둡니다. 경로 매개변수는 대상을, 쿼리는 선택 값을 가리키며 모두 문자열입니다. 중첩 라우트는 바깥에서 안쪽으로 그리고 부모를 유지한 채 자식만 교체합니다.
- `URLPattern`(Baseline 2025)은 `exec()`로 `pathname.groups`에서 매개변수를 추출합니다.
- History API 라우터는 링크 가로채기에서 수정 키, `target`, `download`, 외부 출처, 가운데 클릭을 제외해야 합니다. Navigation API(Baseline 2026)는 이 창의 이동만 `navigate` 이벤트로 받으므로 그 부담이 줄어듭니다.
- `intercept({ handler })`의 `handler`는 이동이 확정된 뒤 실행되고, 성공은 `navigatesuccess`, 실패는 `navigateerror`로 알립니다. `entries()`와 `traverseTo(key)`로 기록을 직접 다루고, `precommitHandler`(미Baseline)는 확정 전 단계의 검사와 리다이렉트에 씁니다.
- 전환 뒤에는 포커스 이동, 스크롤, `document.title` 갱신을 직접 합니다.

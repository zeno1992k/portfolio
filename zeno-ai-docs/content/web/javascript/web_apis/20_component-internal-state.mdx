## Private Fields (#field)

비공개 필드(private field)는 이름이 `#`로 시작하는 클래스 필드이며, 그 클래스의 본문 안에서만 읽고 쓸 수 있습니다. 컴포넌트의 내부 상태를 외부에서 건드리지 못하게 막는 언어 수준의 장치입니다(언어 자체는 ECMAscript 과목에서 다룹니다).

```js
class Counter extends HTMLElement {
  #count = 0
  increment() { this.#count += 1 }
  get count() { return this.#count }
}
const c = new Counter()
c.#count // SyntaxError (클래스 밖에서는 문법 오류)
```

- 밑줄 관례(`_count`)는 이름만 숨길 뿐 일반 프로퍼티라서 외부에서 읽고 쓸 수 있고 `Object.keys`에도 나옵니다. `#count`는 어떤 방법으로도 클래스 밖에서 접근할 수 없습니다.
- 서브클래스도 부모의 비공개 필드에 접근하지 못합니다. 서브클래스가 필요로 하는 값은 메서드나 getter로 열어 줍니다.
- 필드가 없는 객체의 `#count`에 접근하면 TypeError입니다. `Proxy`로 감싼 요소를 `this`로 메서드를 호출하면 이 오류가 납니다.
- 필드 초기화는 `super()`가 돌아온 직후에 실행됩니다. 업그레이드와 파서 생성에서도 생성자가 먼저 끝나므로, 이후에 호출되는 `attributeChangedCallback` 같은 콜백에서는 비공개 필드가 항상 준비되어 있습니다(자세히는 18편).
- 비공개 메서드(`#render() {}`)와 정적 비공개 멤버도 같은 방식입니다. 클래스 필드와 비공개 멤버는 널리 지원됩니다.
- 비공개 필드는 DOM을 숨기지 않습니다. DOM 캡슐화는 Shadow DOM의 일입니다(자세히는 21편).

## 내부 상태와 외부 상태 분리

컴포넌트의 상태는 누가 쓰고 누가 읽는지에 따라 세 가지로 나뉩니다.

| 종류 | 쓰는 쪽 | 저장·노출 방법 |
|------|---------|----------------|
| 입력 | 사용하는 쪽 | 속성과 프로퍼티(자세히는 19편) |
| 내부 상태 | 컴포넌트 자신 | 비공개 필드 |
| 출력 | 컴포넌트 자신 | 읽기 전용 프로퍼티, 이벤트, 사용자 정의 상태 |

- 입력은 원칙적으로 컴포넌트가 바꾸지 않습니다. 컴포넌트가 `value` 속성을 직접 고치면 사용하는 쪽이 준 값과 컴포넌트가 계산한 값이 뒤섞입니다. 사용자 조작의 결과는 내부 상태에 두고 출력으로 알립니다.
- 내부 상태는 한 곳에만 저장합니다. 같은 값을 DOM(`input.value`)과 필드에 모두 두고 서로 맞추지 않습니다. DOM은 상태를 그린 결과이지 상태 저장소가 아닙니다.
- 내부의 변경 가능한 객체를 getter로 그대로 돌려주면 내부 상태가 외부에 새어 나갑니다. 복사본이나 동결한 값을 돌려줍니다(아래 "불변 데이터와 변경 가능한 데이터").
- 외부에서 쓰면 안 되는 출력 상태는 속성이 아니라 사용자 정의 상태로 노출합니다(아래 "CustomStateSet").

## 파생 상태(Derived State)

파생 상태는 다른 상태에서 계산할 수 있는 값입니다. 저장하지 않고 필요할 때 계산합니다.

```js
#items = []
#query = ''
get visibleItems() {
  const q = this.#query
  return this.#items.filter((i) => i.name.includes(q))
}
get isEmpty() { return this.visibleItems.length === 0 }
```

- 파생 값을 필드에 따로 저장하면 원본이 바뀔 때 함께 갱신해야 하고, 한 곳이라도 빠뜨리면 두 값이 어긋납니다. 진실은 한 곳에 둡니다.
- 계산이 비싸면 입력에 대한 마지막 결과를 캐시합니다. 입력 참조가 같으면 캐시를 쓰고 다르면 다시 계산합니다. 이 방식은 상태를 불변으로 갱신할 때만 안전합니다(아래 "불변 데이터와 변경 가능한 데이터").
- 속성 값에서 파싱한 숫자·열거형도 파생 값입니다. 속성이 진실이고 getter가 계산합니다(자세히는 19편).

## 상태 변경과 렌더링 트리거

상태를 바꾸는 모든 경로(setter, 속성 변경, 이벤트 핸들러, 비동기 결과)는 하나의 "무효화" 함수로 모아 렌더링을 예약합니다. 렌더링은 상태만 읽어서 화면을 만드는 함수 하나에 둡니다.

```js
#dirty = false
#invalidate() {
  if (this.#dirty) return
  this.#dirty = true
  queueMicrotask(() => {
    this.#dirty = false
    if (this.isConnected) this.#render()
  })
}
```

- 같은 작업 안에서 상태가 여러 번 바뀌어도 마이크로태스크로 모아 한 번만 렌더링합니다. 프로퍼티 세 개를 연달아 설정해도 렌더링은 한 번입니다.
- 렌더링은 연결된 동안에만 합니다. 연결되지 않은 요소의 변경은 `connectedCallback`에서 한 번 렌더링하면 따라잡습니다.
- 값이 같으면 무효화하지 않습니다(`if (Object.is(old, v)) return`). `attributeChangedCallback`은 같은 값에도 호출되기 때문입니다.
- 상태를 바꾸는 코드가 DOM을 직접 고치지 않고 `#invalidate()`만 호출하게 하면, 화면은 항상 상태의 결과가 됩니다.
- 렌더링 방식과 갱신 전략은 30편, 반응형 상태 설계는 31편에서 다룹니다.

## ElementInternals

`ElementInternals`는 브라우저가 모든 요소에 제공하는 내부 기능을 커스텀 요소 작성자가 쓰게 하는 객체입니다. 사용하는 쪽이 아닌 컴포넌트 작성자를 위한 것이라서 비공개로 보관합니다.

| 영역 | 멤버 | 자세히 |
|------|------|--------|
| 사용자 정의 상태 | `states` | 이 편 |
| shadow root 접근 | `shadowRoot` | 21편 |
| 폼 참여 | `setFormValue`, `setValidity`, `form`, `labels`, `validity`, `willValidate`, `validationMessage`, `checkValidity`, `reportValidity` | 26편 |
| 접근성 | `role`, `ariaLabel` 같은 ARIA 반영 프로퍼티 | 27편 |

- `states`와 접근성 멤버는 폼 연결 요소가 아니어도 쓸 수 있습니다. 폼 관련 멤버는 `formAssociated`가 `true`인 요소에서 동작합니다.
- ElementInternals는 Baseline 2023입니다. 일부 멤버는 지원 시기가 다르므로 사용 전에 확인합니다.
- `internals.shadowRoot`는 닫힌(closed) shadow root도 돌려줍니다. 컴포넌트가 자신의 닫힌 shadow root를 다시 찾을 때 씁니다.

## HTMLElement.attachInternals

`attachInternals()`는 요소의 `ElementInternals`를 만들어 돌려주는 메서드이며, 보통 생성자에서 한 번 호출해 비공개 필드에 보관합니다.

```js
class LoadingButton extends HTMLElement {
  #internals
  constructor() {
    super()
    this.#internals = this.attachInternals()
  }
}
```

다음 경우에는 NotSupportedError입니다.

| 경우 | 설명 |
|------|------|
| 커스텀 요소가 아님 | 정의가 없는 요소와 내장 요소 |
| 확장형(customized built-in) | `is` 값이 있는 요소 |
| `disabledFeatures`에 `internals` | 정의에서 기능을 끈 경우(자세히는 17편) |
| 두 번째 호출 | 요소당 한 번만 가능 |
| 아직 업그레이드되지 않았거나 실패한 요소 | 생성 중이거나 업그레이드가 끝난 요소만 가능 |

- 공개 프로퍼티로 노출하지 않습니다. `internals`를 가진 쪽은 요소의 상태, 폼 값, 접근성 의미를 마음대로 바꿀 수 있습니다.
- 한 번만 호출할 수 있으므로 서브클래스와 부모 클래스가 각각 호출하지 않도록 한 곳에서만 만듭니다.

## CustomStateSet

`CustomStateSet`은 `internals.states`로 얻는, 문자열 집합(Set과 같은 형태)입니다. 컴포넌트의 상태를 이름으로 추가·삭제하면 CSS가 그 이름으로 요소를 선택할 수 있습니다.

```js
const s = this.#internals.states
s.add('loading')     // 상태 켜기
s.has('loading')     // true
s.delete('loading')  // 상태 끄기
s.clear()            // 모든 상태 끄기
```

- 이름은 `add`, `delete`, `has`, `clear`, `size`, `forEach`, `keys`, `values`, `entries`로 다룹니다. Set과 같은 인터페이스입니다.
- 이 집합은 불리언 상태만 표현합니다. 세 가지 이상의 값은 서로 배타적인 불리언으로 나눕니다(`loading`, `ready`, `error`). 값을 바꿀 때 이전 상태를 `delete`하고 새 상태를 `add`합니다.
- 상태를 쓸 수 있는 것은 `internals`를 가진 컴포넌트뿐입니다. 외부 코드는 상태를 바꿀 수 없고 CSS로 읽을 수만 있어서 읽기 전용 상태를 노출하기에 알맞습니다.
- 자율형 커스텀 요소에서만 쓸 수 있습니다. 상태 변화를 알려 주는 이벤트는 없으므로 JavaScript로 알려야 하면 이벤트를 따로 발생시킵니다(아래 "상태 변경 알림 이벤트").

## CSS :state()

`:state()` 의사 클래스는 `CustomStateSet`에 해당 이름이 있는 커스텀 요소에 일치합니다.

```css
user-card:state(loading) {
  opacity: 0.5;
}
```

shadow root 안의 스타일에서는 `:host()`와 함께 씁니다. `::part()`로 노출된 부분에도 붙일 수 있습니다.

```css
:host(:state(loading))::before {
  content: '...';
}
question-box::part(checkbox):state(checked) {
  color: green;
}
```

- 인수는 식별자라서 CSS 식별자 규칙에 맞는 이름을 씁니다.
- 속성 선택자(`[loading]`)와 달리 마크업에 흔적이 남지 않고 외부가 바꿀 수도 없습니다.
- 지원 여부는 `CSS.supports('selector(:state(loading))')`로 확인할 수 있습니다.

### 지원 상태와 폐기된 --dash 문법

`CustomStateSet`과 `:state()`는 Baseline 2024입니다(Chrome 125, Firefox 126, Safari 17.4). 2024년 5월부터 핵심 브라우저 전체가 지원합니다.

- 예전 Chrome(90부터)은 `states.add('--loading')`으로 상태를 켜고 `:--loading`으로 선택하는 문법을 썼습니다. 이 문법은 폐기되었고 `:state(loading)`로 대체되었습니다.
- 새 코드는 `--` 없이 `states.add('loading')`과 `:state(loading)`을 씁니다. MDN은 옛 코드와의 호환을 위해 `--`로 시작하는 이름도 `:state()`와 함께 동작한다고 설명합니다.
- Baseline 이전의 브라우저를 지원해야 하면 같은 상태를 속성으로도 반영해 선택자를 이중으로 둡니다.

## 상태 머신으로 UI 상태 모델링

상태 머신(state machine)은 UI가 가질 수 있는 상태를 유한한 목록으로 정하고, 허용된 전이(transition)만 둡니다. 여러 불리언 필드(`isLoading`, `hasError`)를 조합하면 있을 수 없는 조합(로딩 중이면서 오류)이 생기는데, 하나의 상태 필드는 이를 막습니다.

```js
const NEXT = {
  idle: ['loading'],
  loading: ['success', 'error'],
  success: ['loading'],
  error: ['loading'],
}
#status = 'idle'
#to(next) {
  if (!NEXT[this.#status].includes(next)) return
  this.#status = next
  this.#invalidate()
}
```

| 현재 상태 | 이벤트 | 다음 상태 |
|-----------|--------|-----------|
| `idle` | 요청 시작 | `loading` |
| `loading` | 응답 성공 | `success` |
| `loading` | 응답 실패 | `error` |
| `success`, `error` | 다시 요청 | `loading` |

- 허용되지 않은 전이는 무시하거나 오류로 처리합니다. 이중 요청, 늦게 도착한 응답이 상태를 망치는 일을 막습니다(자세히는 39편).
- 현재 상태를 `CustomStateSet`으로 노출하면 CSS가 상태별 모습을 정할 수 있습니다. 전이 함수에서 이전 상태를 `delete`하고 새 상태를 `add`합니다.
- 상태가 늘어나면 상태 안의 상태를 만들기보다 `loading`, `retrying`처럼 이름을 늘려 평평하게 유지하는 편이 단순합니다.
- 상태 전이가 곧 렌더링 입력이라서, 렌더링은 `#status`로 분기하면 됩니다.

## 불변 데이터와 변경 가능한 데이터

불변(immutable) 데이터는 만든 뒤 고치지 않고 바뀔 때마다 새 값을 만드는 방식입니다. 변경 가능(mutable) 데이터는 같은 객체를 제자리에서 고칩니다.

```js
this.#items.push(item)               // 변경: 참조가 그대로
this.#items = [...this.#items, item] // 불변: 새 배열
this.#invalidate()
```

| 항목 | 불변 갱신 | 제자리 변경 |
|------|-----------|-------------|
| 변경 감지 | 참조 비교로 가능 | 불가(같은 참조) |
| 파생 값 캐시 | 안전 | 갱신 누락 위험 |
| 외부와 공유 | 안전 | 외부가 고칠 수 있음 |
| 비용 | 새 객체 할당 | 낮음 |

- 컴포넌트 안에서만 쓰고 밖으로 나가지 않는 큰 버퍼는 제자리 변경이 낫습니다. 갱신 뒤 `#invalidate()`를 직접 호출합니다.
- 프로퍼티로 받은 객체와 getter로 돌려주는 객체는 경계를 넘는 값입니다. 받을 때 복사하고 돌려줄 때 복사하거나 `Object.freeze`로 동결해서 공유를 피합니다. `Object.freeze`는 얕은 동결입니다.
- 깊은 복사가 필요하면 `structuredClone`을 씁니다. 함수는 복제할 수 없습니다(ECMAscript 과목 참조).
- 중첩된 객체를 불변으로 갱신하려면 바뀌는 경로의 단계마다 새 객체를 만듭니다(스프레드 문법은 ECMAscript 과목 참조).

## 상태 초기화 / 리셋

초기 상태를 만드는 코드를 하나로 모으고, 생성자와 `reset()`이 같은 코드를 쓰게 합니다.

```js
#init() {
  this.#status = 'idle'
  this.#items = []
  this.#internals.states.clear()
}
constructor() {
  super()
  this.#internals = this.attachInternals()
  this.#init()
}
reset() { this.#init(); this.#invalidate() }
```

- 초기값을 필드 선언과 `reset()`에 각각 쓰면 한쪽이 바뀔 때 어긋납니다. 초기값의 진실은 한 곳에 둡니다.
- 연결과 해제는 상태를 초기화하지 않습니다. 떼었다 다시 붙인 요소는 같은 상태로 돌아옵니다(자세히는 18편). 리셋은 사용자가 명시적으로 요구했을 때만 합니다.
- 리셋할 때는 진행 중인 비동기 작업도 취소합니다. 취소하지 않으면 리셋 이후에 응답이 도착해 상태를 되살립니다.
- 폼 연결 요소의 리셋은 브라우저가 `formResetCallback`으로 알려 줍니다(자세히는 26편).
- 입력(속성·프로퍼티)은 리셋하지 않습니다. 리셋 대상은 컴포넌트가 만든 내부 상태입니다.

## 상태를 속성으로 반영할지 정하는 기준

상태를 CSS에 보이게 하는 방법은 속성 반영과 사용자 정의 상태 두 가지입니다. 기준은 "누가 쓰는가"입니다.

| 기준 | 속성 | 사용자 정의 상태 |
|------|------|------------------|
| 사용하는 쪽이 마크업으로 설정 | 가능 | 불가 |
| 컴포넌트가 계산한 결과 | 외부가 덮어쓸 수 있음 | 외부가 쓸 수 없음 |
| 복제·직렬화·서버 렌더링 결과에 포함 | 포함 | 포함하지 않음 |
| 자주 바뀌는 값 | 속성 갱신과 관찰 비용 | 부담이 적음 |
| 지원 | 모든 브라우저 | Baseline 2024 |

- 입력은 속성이고, 컴포넌트가 만든 출력은 사용자 정의 상태입니다. `open`처럼 사용하는 쪽이 설정하고 컴포넌트도 바꾸는 값은 속성과 프로퍼티로 둡니다.
- 서버에서 렌더링한 HTML이나 복제본에 남아야 하는 상태는 속성으로 반영합니다.
- 접근성에 필요한 상태(`aria-busy`, `aria-checked`)는 ARIA 속성이나 `internals`의 ARIA 프로퍼티로 따로 표현합니다. `:state()`는 접근성 정보가 아닙니다(자세히는 27편).

## 상태 변경 알림 이벤트

사용자 정의 상태는 JavaScript에 변화를 알려 주지 않으므로, 외부 코드가 상태 변화에 반응해야 하면 이벤트를 발생시킵니다.

```js
#to(next) {
  const from = this.#status
  this.#status = next
  this.dispatchEvent(new CustomEvent('statuschange', {
    detail: { from, to: next },
  }))
  this.#invalidate()
}
```

- 사용자 동작이나 비동기 결과 같은 내부 활동의 결과로만 발생시킵니다. 호스트가 프로퍼티를 설정했다는 이유로 발생시키면 설정하는 쪽의 리스너와 무한 루프가 생길 수 있습니다(자세히는 19편).
- 값이 실제로 바뀐 경우에만 발생시킵니다. `detail`에는 이전 값과 새 값을 담고, 내부 객체를 그대로 넣지 않습니다.
- 내장 요소가 쓰는 이벤트 이름(`change`, `input`, `toggle`)은 그 의미에 맞을 때만 재사용합니다. 그 밖에는 컴포넌트 접두사가 있는 이름을 씁니다.
- 이벤트 이름, `detail` 형태, 버블링 여부는 공개 API입니다(자세히는 25편).

## 핵심 정리

- 상태는 입력(속성·프로퍼티), 내부(비공개 필드), 출력(읽기 전용 프로퍼티·이벤트·사용자 정의 상태)으로 나누고, 값은 한 곳에만 저장합니다.
- 파생 값은 저장하지 않고 계산하며, 모든 상태 변경은 하나의 무효화 함수로 모아 마이크로태스크에서 한 번 렌더링합니다.
- `attachInternals()`는 생성자에서 한 번 호출해 비공개로 보관하고, `internals.states`로 상태를 켜고 끄면 CSS의 `:state()`로 선택됩니다.
- `CustomStateSet`과 `:state()`는 Baseline 2024이고, 옛 `:--name` 문법은 폐기되었습니다.
- 상태 머신은 허용된 전이만 두어 불가능한 조합을 막고, 불변 갱신은 변경 감지와 안전한 공유를 돕습니다.
- 초기화 코드는 생성자와 `reset()`이 공유하고, 입력은 속성으로 출력은 사용자 정의 상태로 노출하며 변화 알림은 이벤트로 합니다.

## Cache API

Cache API는 `Request`와 `Response` 쌍을 이름 붙인 캐시에 저장하는 브라우저 저장소입니다. 원래 Service Worker용으로 만들어졌지만 window와 Worker 어디서나 쓸 수 있고 보안 컨텍스트(HTTPS)가 필요합니다. Baseline 2018입니다(Service Worker는 56편).

진입점은 `caches`(`CacheStorage`)이고, 이름으로 연 `Cache` 객체에서 읽고 씁니다.

```js
const cache = await caches.open('assets-v1')
await cache.add('/logo.svg')            // fetch + put
await cache.put('/data.json', await fetch('/data.json'))
const hit = await cache.match('/data.json')
// hit: Response 또는 undefined
await cache.delete('/logo.svg')         // true 또는 false
```

| 객체 | 메서드 |
|------|--------|
| `CacheStorage` (`caches`) | `open(name)`, `has(name)`, `delete(name)`, `keys()`, `match(request)` |
| `Cache` | `match`, `matchAll`, `add`, `addAll`, `put`, `delete`, `keys` |

- `add(url)`은 `fetch`와 `put`을 합친 것이고, `put(request, response)`는 이미 가져온 응답을 저장해서 제어가 더 자유롭습니다.
- `caches.match()`는 모든 캐시에서, `cache.match()`는 그 캐시에서만 찾습니다.
- GET 요청만 저장할 수 있습니다. 206 Partial Content 응답은 저장이 거부됩니다.
- 같은 URL을 다시 `put`하면 이전 항목을 덮어씁니다. 키 일치는 응답의 `Vary` 헤더도 따집니다.
- Cache API는 HTTP 캐시 헤더를 따르지 않습니다. 만료도 자동 갱신도 없고, 지우기 전까지 항목이 남습니다. 버전 관리와 정리는 개발자 몫입니다.
- 응답 본문은 한 번만 읽을 수 있으므로 저장하면서 화면에도 쓰려면 `response.clone()`을 `put`에 넘깁니다.

```js
const res = await fetch('/api/items')
if (res.ok) await cache.put('/api/items', res.clone())
return res
```

**흔한 실수:** 응답을 `put`한 뒤 같은 객체를 다시 읽으려는 것입니다. 본문이 이미 소비되어 `TypeError`가 납니다. `put`에는 반드시 복제본을 넘깁니다.

## Storage Quota

브라우저는 origin마다 저장 공간 상한(할당량)을 둡니다. 할당량은 IndexedDB, Cache API, OPFS, Web Storage, Service Worker 등록 같은 저장소들이 함께 나눠 씁니다. 값은 브라우저와 기기에 따라 다르며 MDN이 정리한 기준은 다음과 같습니다.

| 브라우저 | 기준(MDN) |
|----------|-----------|
| Chrome·Edge | 전체 디스크 크기의 최대 60퍼센트(origin당) |
| Firefox | 기본 모드는 디스크의 10퍼센트와 10GiB 중 작은 값. 영속 모드는 디스크의 50퍼센트(상한 8TiB) |
| Safari | 최신 macOS·iOS의 브라우저 앱은 디스크의 약 60퍼센트. 교차 출처 프레임은 부모 할당량의 약 10분의 1 |

- 할당량은 남은 공간이 아니라 전체 디스크 크기를 기준으로 계산해서, 사이트가 사용자의 디스크 상태를 알아내지 못하게 합니다.
- 수치는 버전에 따라 바뀌므로 코드에서 가정하지 않고 실행 중에 조회합니다.
- 한도를 넘으면 쓰기가 `QuotaExceededError`로 실패합니다(IndexedDB는 41편).
- 프라이빗 브라우징에서는 할당량이 다를 수 있고, 세션이 끝나면 데이터가 보통 삭제됩니다.

### navigator.storage.estimate()

`navigator.storage.estimate()`는 현재 origin의 사용량과 할당량을 Promise로 돌려줍니다. Baseline 2021이며 Worker에서도 쓸 수 있습니다.

```js
const est = await navigator.storage.estimate()
const { usage, quota, usageDetails } = est
console.log(Math.round((usage / quota) * 100) + '%')
// usageDetails는 저장소 종류별 사용량(브라우저가 제공할 때)
```

- 값은 추정치입니다. 정확한 용량 계산이 아니라 사용자에게 보여 주는 대략적인 안내나 정리 시점 판단에만 씁니다.
- 큰 쓰기 전에 `quota - usage`로 여유를 확인하고, 부족하면 오래된 캐시를 먼저 지웁니다.

## 저장소 축출과 origin 단위 삭제

저장 공간이 부족하면 브라우저가 데이터를 자동으로 지웁니다. 이를 축출(eviction)이라 하고 규칙은 다음과 같습니다.

- 기본 모드는 최선 노력(best-effort)입니다. 저장 공간 압박이나 브라우저 전체 한도 초과 시 지워질 수 있습니다.
- 영속 모드로 허가받은 origin은 사용자가 직접 지우기 전에는 축출되지 않습니다(아래 persist()).
- 가장 오래 쓰이지 않은 origin부터(LRU) 지웁니다. 압박이 계속되면 다음 origin으로 넘어가고 영속 모드 origin은 건너뜁니다.
- 삭제는 origin 단위로 전부 이루어집니다. IndexedDB만 지우고 Cache API는 남기는 식의 부분 삭제는 하지 않아서, 저장소 간 데이터 불일치가 생기지 않습니다.
- MDN에 따르면 Safari는 7일 넘게 사용자 상호작용이 없는 origin의 스크립트 작성 데이터를 선제적으로 지웁니다(서버가 설정한 쿠키는 제외). web.dev는 설치한 PWA를 이 제한의 예외로 설명합니다.

이 규칙 때문에 저장소의 데이터는 언제든 사라질 수 있다고 가정하고 설계합니다. 서버에서 다시 받을 수 있는 데이터는 캐시로 취급하고, 다시 만들 수 없는 사용자 데이터는 영속 저장을 요청하거나 서버에 동기화합니다.

### persist()와 persisted()

`navigator.storage.persist()`는 영속 저장을 요청하고 허가되면 `true`를 돌려줍니다. `persisted()`는 이미 허가됐는지 확인합니다. 둘 다 Baseline 2021입니다.

```js
if (!(await navigator.storage.persisted())) {
  const granted = await navigator.storage.persist()
  console.log(granted ? '영속 저장' : '축출될 수 있음')
}
```

- 허가 여부는 브라우저가 결정합니다. Firefox는 사용자에게 묻고, Chrome은 설치한 PWA, 북마크, 사용 빈도 같은 기준으로 판단합니다(MDN).
- `persist()`는 Worker에서 쓸 수 없고 `persisted()`는 쓸 수 있습니다. origin이 불투명하거나 저장소를 끈 경우에는 `TypeError`입니다.
- 거절당하면 `false`가 나오므로 거절돼도 동작하는 설계가 필요합니다. 영속 모드여도 사용자가 브라우저 설정에서 지우면 사라집니다.

## 메모리 캐시

메모리 캐시는 JavaScript 변수(`Map`, 객체)에 값을 두는 가장 빠른 캐시입니다. 페이지를 닫거나 새로 고치면 사라지고 용량은 힙 크기가 한계입니다.

```js
const cache = new Map()
async function getUser(id) {
  if (cache.has(id)) return cache.get(id)
  const res = await fetch(`/api/users/${id}`)
  const user = await res.json()
  cache.set(id, user)
  return user
}
```

- 진행 중인 요청 자체를 저장하면 같은 키로 동시에 요청이 여러 번 나가는 것을 막습니다. 값 대신 Promise를 저장하는 방식입니다(자세히는 37편).
- 무한히 쌓이면 메모리 누수입니다. 항목 수 상한을 두고 오래된 것부터 지웁니다(자세히는 67편).
- 한 탭 안에서만 공유되므로 새로 고침이나 다른 탭에는 영향이 없습니다.

| 저장 위치 | 수명 | 용량 | 용도 |
|-----------|------|------|------|
| 메모리(`Map`) | 페이지 수명 | 작음 | 화면 안의 반복 조회 |
| Cache API | 지울 때까지(축출 가능) | 할당량 | 네트워크 응답, 정적 자산 |
| IndexedDB | 지울 때까지(축출 가능) | 할당량 | 구조화된 앱 데이터 |
| OPFS | 지울 때까지(축출 가능) | 할당량 | 큰 바이너리, 파일 |

## Persistent Cache

영속 캐시는 새로 고침 뒤에도 남는 캐시입니다. 응답 단위로 저장하려면 Cache API, 가공한 데이터는 IndexedDB를 씁니다. 둘 다 할당량 안에서 축출될 수 있다는 점은 같습니다.

- 응답 그대로 재사용하는 네트워크 자원은 Cache API가 맞습니다. 헤더와 상태 코드까지 저장되어 `respondWith`로 바로 돌려줄 수 있습니다.
- 정렬·검색이 필요한 데이터나 레코드 단위 갱신은 IndexedDB가 맞습니다.
- web.dev는 앱을 로드하는 데 필요한 네트워크 자원에는 Cache Storage, 파일 기반 콘텐츠에는 OPFS, 그 밖의 데이터에는 IndexedDB를 권장합니다.
- 캐시한 데이터는 원본이 아니라 복사본임을 전제로 하고, 없을 때는 네트워크로 되돌아가는 경로를 둡니다.

## Cache Invalidation

Cache API에는 만료가 없으므로 무효화를 직접 설계해야 합니다. 방법은 크게 세 가지입니다.

| 방법 | 동작 | 적합한 경우 |
|------|------|-------------|
| 캐시 이름 버전 | `assets-v2`처럼 새 캐시를 열고 옛 캐시를 삭제 | 배포 단위로 바뀌는 정적 자산 |
| 항목 단위 갱신 | 같은 키로 다시 `put` 하거나 `delete` | 일부 데이터만 바뀔 때 |
| 시각 기록 | 저장 시각을 함께 두고 기준 시간이 지나면 폐기 | API 응답 |

```js
const KEEP = ['assets-v2']
const names = await caches.keys()
await Promise.all(
  names
    .filter((n) => !KEEP.includes(n))
    .map((n) => caches.delete(n)),
)
```

- 캐시 객체에는 저장 시각 필드가 없으므로, 시각이 필요하면 별도 키(IndexedDB 등)에 기록하거나 응답에 사용자 정의 헤더를 넣어 `put`합니다.
- 갱신하는 동안 오래된 값을 먼저 보여 주고 뒤에서 새로 받는 방식(stale-while-revalidate)도 같은 도구로 구현합니다(자세히는 56편).
- 데이터가 바뀌는 시점(저장, 삭제)에 관련 캐시 항목을 함께 지우는 것이 가장 단순한 규칙입니다.

**흔한 실수:** 배포하면서 캐시 이름을 바꾸지 않아 옛 응답이 계속 나가는 것입니다. 옛 캐시는 자동으로 지워지지 않습니다.

## 컴포넌트 상태 Persist

새로 고침 뒤에도 유지할 컴포넌트 상태(필터, 정렬, 접힘, 작성 중인 초안)는 크기와 성격에 따라 저장소를 고릅니다.

| 상태 | 저장 위치 |
|------|-----------|
| 공유 가능한 위치·필터 | URL 쿼리(자세히는 34편) |
| 작은 개인 설정(테마, 접힘) | `localStorage`(자세히는 40편) |
| 탭 하나의 임시 상태 | `sessionStorage`(자세히는 40편) |
| 큰 초안, 구조화된 데이터 | IndexedDB |

- 저장 형식에 버전을 넣고, 읽을 때 검증합니다. 저장된 값이 현재 코드의 기대와 다를 수 있기 때문입니다.
- 저장은 모든 변경이 아니라 디바운스하거나 `pagehide`·`visibilitychange` 시점에 합니다(자세히는 60편).
- 저장소가 비어 있거나 읽기에 실패해도 기본값으로 시작해야 합니다. 값이 없다는 것은 정상 상황입니다.
- 비밀번호나 토큰 같은 민감한 값은 저장하지 않습니다.

## 오프라인 데이터 전략

오프라인에서도 동작하려면 자원(앱 셸)과 데이터를 따로 정합니다.

| 대상 | 전략 | 저장소 |
|------|------|--------|
| 앱 코드, 정적 자산 | 설치 시 미리 저장하고 배포 때 버전 교체 | Cache API |
| 읽기 데이터 | 저장해 둔 값을 먼저 보이고 온라인이면 갱신 | IndexedDB |
| 쓰기(작성·수정) | 로컬에 먼저 쓰고 대기열에 넣었다가 온라인이 되면 전송 | IndexedDB |

- 쓰기 대기열은 각 항목에 고유 id를 붙여 재전송해도 서버가 중복 처리하지 않게 합니다.
- 충돌은 서버 버전이나 수정 시각을 비교해 결정하는 규칙(마지막 쓰기 우선, 병합, 사용자 선택)을 미리 정합니다.
- 영속 저장을 요청하고, 다시 받을 수 없는 데이터는 서버로 동기화합니다(Service Worker와 백그라운드 동기화는 56편, 57편).

## OPFS와 createSyncAccessHandle

OPFS(Origin Private File System)는 origin 전용 파일 시스템입니다. 사용자에게 보이지 않고 권한 프롬프트가 없으며, 용량은 할당량에 포함되고 사이트 데이터를 지우면 함께 지워집니다. Baseline 2023입니다(MDN 기준 2023년 3월).

```js
const root = await navigator.storage.getDirectory()
const fh = await root.getFileHandle('note.txt', {
  create: true,
})
const w = await fh.createWritable()
await w.write('hello')
await w.close()
const text = await (await fh.getFile()).text() // 'hello'
```

- 진입점은 `navigator.storage.getDirectory()`이고 `getFileHandle`, `getDirectoryHandle`에 `{ create: true }`를 주면 만들고 생략하면 기존 항목을 엽니다.
- 메인 스레드에서는 비동기 API(`createWritable`, `getFile`)를 씁니다.
- 전용 Worker에서는 `createSyncAccessHandle()`로 동기 읽기·쓰기 핸들을 얻습니다. 메인 스레드에서는 호출할 수 없습니다(Worker는 54편).

```js
// Worker 안
const h = await fh.createSyncAccessHandle()
h.write(new TextEncoder().encode('abc'), { at: 0 })
h.flush()
console.log(h.getSize()) // 3
h.close() // 잠금 해제
```

- 핸들은 `read`, `write`, `truncate`, `getSize`, `flush`, `close`를 동기로 제공합니다. 쓰기 직후 `flush()`로 저장을 확정하고 끝나면 반드시 `close()`합니다.
- 기본 모드(`readwrite`)에서는 파일에 독점 잠금을 겁니다. 이미 핸들이 열려 있으면 `NoModificationAllowedError`입니다. `read-only`는 여러 핸들이 동시에 읽고, `readwrite-unsafe`는 여러 핸들이 동시에 쓸 수 있습니다.
- 제자리 바이트 단위 접근이 필요한 SQLite 같은 대용량 데이터에 적합합니다.

## 저장소 분할과 서드파티 컨텍스트

서드파티 iframe의 저장소는 임베드한 origin과 최상위 사이트를 함께 키로 삼아 분리(partition)하는 방식이 쓰입니다. 같은 서드파티가 `a.example`에 임베드됐을 때 저장한 데이터는 `b.example`에 임베드됐을 때 보이지 않습니다. 사이트 간 추적을 막기 위한 장치입니다.

- MDN은 Firefox에서 `localStorage`, `sessionStorage`, Cache API, IndexedDB, BroadcastChannel, Shared Worker, Service Worker가 이렇게 분할된다고 설명합니다(Firefox 103부터 기본).
- 분할된 프레임도 저장소에 접근할 수는 있지만 최상위 사이트마다 따로입니다. 분할되지 않은 접근은 Storage Access API(`document.requestStorageAccess()`)로 요청합니다(자세히는 62편).
- 분할 정책은 브라우저마다 다르고 계속 바뀝니다. 서드파티 프레임에서 저장한 값이 다른 사이트에서도 보일 것이라고 가정하지 않습니다.
- 브라우저가 서드파티 저장을 막은 설정이면 서드파티 iframe에서 IndexedDB 접근이 실패할 수 있습니다(41편).

## Storage Buckets (Chromium 전용)

Storage Buckets API는 데이터를 이름 붙인 버킷으로 나눠, 브라우저가 버킷별로 따로 삭제하게 하는 API입니다. 지우면 곤란한 데이터(작성 중인 메일 초안)와 다시 받을 수 있는 캐시를 다른 버킷에 두어, 저장 공간 압박 때 중요한 쪽이 살아남게 합니다. Chromium 계열에서만 지원되는 미Baseline API입니다.

```js
const sb = navigator.storageBuckets
const draft = await sb.open('drafts', {
  persisted: true,
  durability: 'strict',
})
const req = draft.indexedDB.open('mail', 1)
// 버킷 안의 IndexedDB
```

- `open(name, options)`의 `persisted`(기본 `false`)와 `durability`(`strict` 또는 `relaxed`)는 Chrome 문서에서 확인한 옵션입니다.
- Chrome 문서는 버킷 안의 저장소로 `bucket.indexedDB`만 구현 상태로 소개합니다. 그 밖의 접근자는 확인하지 못해 다루지 않습니다.
- 지원하지 않는 브라우저를 위해 `'storageBuckets' in navigator`로 확인하고 일반 저장소로 대체합니다.

## Web Locks API로 탭 간 조율

Web Locks API는 같은 origin의 탭과 Worker가 이름 붙은 잠금으로 공유 자원 접근을 조율하는 API입니다. Baseline 2022입니다(MDN 기준 2022년 3월). 보안 컨텍스트가 필요하고 Worker에서는 `WorkerNavigator.locks`로 씁니다.

```js
await navigator.locks.request('sync-db', async (lock) => {
  await syncToServer() // 한 번에 한 탭만 실행
}) // 콜백이 끝나면 잠금 해제
```

| 옵션 | 효과 |
|------|------|
| `mode: 'exclusive'` (기본) | 한 번에 한 보유자. 리더 선출에 사용 |
| `mode: 'shared'` | 여러 보유자가 동시에 가능. 읽기 공유, 쓰기 독점 패턴 |
| `ifAvailable: true` | 잠금이 없으면 기다리지 않고 콜백이 `null`을 받음 |
| `steal: true` | 같은 이름의 잠금을 빼앗음. 기존 보유자는 취소됨 |
| `signal` | `AbortSignal`로 대기를 취소하거나 시간 제한을 둠 |

- 잠금은 콜백이 반환한 Promise가 정착(settle)하면 자동으로 풀립니다. 탭이 닫혀도 풀립니다.
- 범위는 origin 단위입니다. `navigator.locks.query()`로 현재 잠금과 대기 상태를 확인할 수 있습니다.
- 여러 탭이 같은 IndexedDB를 갱신하거나 마이그레이션할 때, 서버 동기화를 한 탭만 하게 할 때 씁니다.
- 잠금 이름을 서로 다른 순서로 중첩해서 요청하면 교착(deadlock)이 날 수 있습니다. 순서를 정해서 요청합니다.

```js
const got = await navigator.locks.request(
  'leader',
  { ifAvailable: true },
  async (lock) => {
    if (!lock) return false
    await runLeaderTask()
    return true
  },
)
```

## 저장 데이터 스키마 버전과 마이그레이션

저장된 데이터는 배포한 코드보다 오래 삽니다. 사용자 브라우저에는 이전 버전 코드가 만든 데이터가 남아 있으므로 새 코드는 옛 형식을 읽을 수 있어야 합니다.

- IndexedDB는 데이터베이스 버전이 스키마 버전입니다. `upgradeneeded`의 `oldVersion`으로 단계별 변환을 이어 씁니다(자세히는 41편).
- `localStorage`나 Cache API는 내장 버전이 없으므로 `schemaVersion` 값을 직접 저장하거나, 캐시 이름과 키 이름에 버전을 넣습니다.
- 마이그레이션은 앞 버전부터 한 단계씩 적용하는 함수 목록으로 둡니다. 어느 버전에서 시작해도 최신 형식에 이릅니다.
- 변환이 실패하거나 해석할 수 없는 값이면, 다시 받을 수 있는 캐시는 버리고 사용자 데이터는 백업한 뒤 처리합니다.
- 다중 탭에서는 한 탭이 옛 코드로 새 형식을 덮어쓰지 않도록, 새 버전이 열리면 옛 탭이 연결을 닫게 합니다(IndexedDB의 `versionchange`는 41편). 변환을 한 탭에서만 실행하려면 Web Locks를 씁니다.

```js
const migrations = [
  (d) => ({ ...d, theme: d.theme ?? 'light' }), // v1 -> v2
  (d) => ({ ...d, lang: 'ko' }),                // v2 -> v3
]
function migrate(data, from) {
  const todo = migrations.slice(from - 1)
  return todo.reduce((d, m) => m(d), data)
}
```

## 핵심 정리

- Cache API는 GET 요청의 `Request`와 `Response` 쌍을 저장하며, HTTP 캐시 헤더를 따르지 않고 만료가 없어서 이름 버전과 정리를 직접 해야 합니다.
- 저장소들은 origin 단위 할당량을 나눠 쓰고, `estimate()`는 추정치입니다. 공간이 모자라면 LRU로 origin 전체가 한꺼번에 축출됩니다.
- `persist()`는 영속 저장을 요청하며 허가 여부는 브라우저가 정합니다. 거절돼도 동작하도록 설계하고, 다시 받을 수 없는 데이터는 서버에 동기화합니다.
- 저장 위치는 수명과 성격으로 고릅니다. 메모리는 화면 단위, Cache API는 응답, IndexedDB는 구조화 데이터, OPFS는 큰 파일(Worker의 `createSyncAccessHandle`은 동기·독점 잠금)입니다.
- Web Locks는 탭 간 독점·공유 잠금으로 동기화와 마이그레이션을 한 탭에서만 하게 하고, Storage Buckets는 Chromium 전용이라 점진적 향상으로 다룹니다.
- 저장 데이터에는 스키마 버전을 두고 옛 형식에서 최신으로 단계별 변환하며, 서드파티 프레임의 저장소는 최상위 사이트별로 분리될 수 있습니다.

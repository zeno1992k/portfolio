## Browser Compatibility

브라우저 호환성은 같은 코드가 엔진(Blink, Gecko, WebKit)과 버전에 따라 다르게 동작하거나 동작하지 않는 문제입니다. 표준이 정해져도 구현 시점이 엔진마다 달라서 생깁니다. 사용 전에 세 가지를 확인합니다.

- 어떤 엔진이 어떤 버전부터 지원하는가.
- 부분 구현이거나 플래그 뒤에 있는가.
- 표준 트랙이 아니거나 실험적·폐기 상태인가.

확인할 수 있는 곳은 MDN 문서 하단의 Browser compatibility 표와 Can I Use입니다. 둘 다 같은 데이터에서 나옵니다.

### MDN 호환성 데이터(BCD)와 caniuse

BCD(browser-compat-data)는 웹 API, CSS, HTML, JavaScript 등의 브라우저 호환성 정보를 담은 기계 판독용 데이터 프로젝트입니다. MDN 호환성 표와 Can I Use가 이 데이터로 만들어집니다. npm 패키지 `@mdn/browser-compat-data`로 코드에서 읽을 수도 있습니다.

- 기능은 계층 구조이고, 각 기능의 `__compat` 객체에 브라우저별 지원 정보가 있습니다.
- 지원 정보에는 `version_added`(처음 지원한 버전), 플래그 요구 여부, 상태(`experimental`, `deprecated`, `standard_track`)가 들어 있습니다.
- 표에서 "플래그 뒤"로 표시된 지원은 사용자가 설정을 켜야 하므로 사실상 미지원으로 취급합니다.

Can I Use는 기능별로 브라우저 버전 지원 표를 보여 주고, 사용 통계를 바탕으로 한 지원 점유율을 함께 보여 줍니다. BCD는 정확한 버전과 상태를 확인할 때, Can I Use는 한눈에 영향 범위를 가늠할 때 씁니다.

## Baseline 개념

Baseline은 어떤 웹 기능을 지금 안전하게 쓸 수 있는지 알려 주는 체계입니다. Chrome 팀에서 시작해 WebDX 커뮤니티 그룹이 관리합니다. 기준이 되는 핵심 브라우저 집합은 Chrome(데스크톱·Android), Edge, Firefox(데스크톱·Android), Safari(macOS·iOS)입니다.

| 상태 | 뜻 |
|------|-----|
| Limited availability | 핵심 브라우저 일부만 지원 |
| Newly available | 핵심 브라우저 전체에서 지원되기 시작함 |
| Widely available | Newly available이 된 지 30개월 지남 |

- 연도 표기: "Baseline 2023"은 2023년에 Newly available이 된 기능을 가리킵니다. 목표를 연도로 정하면 "Baseline 2023 이하 기능만 쓴다"처럼 범위가 명확해집니다.
- 판단 기준: 별도 폴백 없이 쓰려면 Widely available, 폴백을 준비하면 Newly available까지 고려합니다. Limited availability는 점진적 향상 대상입니다.
- Baseline 상태는 MDN, Can I Use, Chrome DevTools(CSS 속성), Lighthouse에서 볼 수 있습니다.

### web-features와 Baseline 연도 표기

web-features는 W3C WebDX 커뮤니티 그룹이 관리하는 웹 플랫폼 기능 카탈로그입니다. 기능마다 식별자와 Baseline 상태가 있고, npm 패키지 `web-features`로 받을 수 있습니다.

| 필드 | 값 |
|------|-----|
| `status.baseline` | `false`(Limited), `"low"`(Newly available), `"high"`(Widely available) |
| `baseline_low_date` | Newly available이 된 날짜 |
| `baseline_high_date` | Widely available이 된 날짜 |

Baseline 연도 표기는 `baseline_low_date`의 연도를 따릅니다. 이 문서 시리즈의 지원 상태 표기는 web-features 3.40.1 데이터 기준이며, 다시 확인하면 값이 바뀔 수 있습니다.

### Browserslist의 Baseline 쿼리

Browserslist는 대상 브라우저 목록을 한 곳에 정의해 Autoprefixer, Babel, Stylelint 같은 도구가 공유하게 하는 설정입니다. `.browserslistrc` 파일이나 `package.json`의 `browserslist` 키에 적습니다. 설정이 없을 때의 기본값은 `> 0.5%, last 2 versions, Firefox ESR, not dead`입니다.

Baseline 쿼리로 목표를 지정할 수 있습니다.

| 쿼리 | 선택되는 브라우저 버전 |
|------|------------------------|
| `baseline widely available` | Widely available 기능을 모두 지원하는 버전 |
| `baseline newly available` | 현재 Newly available 기능까지 모두 지원하는 버전 |
| `baseline 2023` | 해당 연도 말 기준 Newly available 기능을 모두 지원하는 버전 |
| `baseline widely available on 2025-01-01` | 그 날짜의 Widely available 기능 집합을 지원하는 버전 |

```text
# .browserslistrc
baseline widely available
```

- `npx browserslist`로 선택된 브라우저 목록을 확인합니다.
- Browserslist는 트랜스파일·접두사 같은 빌드 단계 도구의 대상을 정할 뿐입니다. 런타임에 기능이 있는지 검사하거나 폴리필을 넣어 주지는 않습니다.

## Feature Detection

기능 탐지(feature detection)는 브라우저 이름이나 버전이 아니라 기능이 실제로 있는지를 코드로 확인해 분기하는 방식입니다. User-Agent 문자열로 브라우저를 추정하는 방식은 위조·변경이 쉽고 새 버전에서 틀리므로 쓰지 않습니다(자세히는 1편).

| 대상 | 탐지 방법 |
|------|-----------|
| 전역 API | `'IntersectionObserver' in window` |
| 객체의 메서드·프로퍼티 | `'showPopover' in HTMLElement.prototype` |
| 생성자 | `typeof ResizeObserver === 'function'` |
| CSS 문법 | `CSS.supports(...)`, `@supports` |
| HTML 속성 | 요소 프로퍼티 존재 여부 또는 동작 결과 |

- 존재 여부와 정상 동작은 다릅니다. 부분 구현이거나 버그가 있는 API는 이름만 있고 동작이 다를 수 있으므로, 중요한 기능은 작은 동작 검사로 확인합니다.
- 탐지 코드는 한 곳에 모아 이름 있는 상수로 내보냅니다. 컴포넌트마다 흩어지면 폴백 기준이 어긋납니다.
- 탐지는 사용하는 시점이 아니라 첫 사용 전에 한 번만 수행합니다.

## CSS @supports

`@supports`는 브라우저가 지원하는 CSS 기능에 따라 규칙을 적용하는 조건 규칙(feature query)입니다.

```css
.card-list { display: flex; flex-wrap: wrap; }

@supports (display: grid) {
  .card-list { display: grid; }
}
@supports not selector(:has(a)) {
  .card { padding: 8px; }
}
```

| 조건 형태 | 예 |
|-----------|-----|
| 선언 | `(display: grid)` |
| 선택자 | `selector(:has(a))` |
| at-rule | `at-rule(@keyframes)` |
| 글꼴 기술·형식 | `font-tech(color-COLRv1)`, `font-format(woff2)` |
| 논리 연산 | `and`, `or`, `not` |

- 브라우저는 모르는 선언이나 값을 무시합니다. 속성 하나는 폴백 선언을 먼저 쓰고 새 선언을 뒤에 쓰는 것만으로 충분합니다.
- `@supports`는 여러 속성이 함께 바뀌는 레이아웃 전환, 선택자·at-rule 지원 판정처럼 선언 하나로 구분되지 않을 때 씁니다.
- `@supports` 자체는 2015년 9월부터 널리 지원됩니다. 이를 모르는 브라우저는 블록 전체를 무시하므로 폴백은 바깥에, 새 문법은 안쪽에 둡니다. `not` 조건 안에 폴백을 두면 그런 브라우저에서 적용되지 않습니다.

### CSS.supports()

`CSS.supports()`는 같은 검사를 JavaScript에서 하는 정적 메서드이며 불리언을 돌려줍니다. 두 가지 형태가 있습니다.

```js
CSS.supports('display', 'grid')             // 속성과 값
CSS.supports('display: grid')               // 조건 문자열
CSS.supports('selector(:has(a))')           // selector() 포함
CSS.supports('(--x: red) and (display: grid)')
```

CSS 지원 여부에 따라 클래스를 붙이거나 컴포넌트가 다른 구현을 고를 때 씁니다. CSS 안에서 끝나는 분기는 `@supports`가 더 단순합니다.

## JS API 존재 여부 검사

JS API 검사는 기능이 객체에 노출됐는지를 확인해 분기하는 일입니다. 사용 전에 가드를 두고, 없으면 대체 경로를 탑니다.

```js
const hasIO = 'IntersectionObserver' in window
const proto = HTMLElement.prototype
const hasInternals = 'attachInternals' in proto
const hasSheets = 'adoptedStyleSheets' in document

if (hasIO) observeLazy(el)
else loadImmediately(el)
```

- 전역 객체는 `in` 연산자나 `typeof x !== 'undefined'`로 검사합니다. 선언되지 않은 전역을 `x`로 직접 읽으면 `ReferenceError`가 납니다.
- 옵셔널 체이닝(`navigator.share?.()`)은 값이 `undefined`일 때 호출을 건너뛸 뿐 폴백 로직은 직접 써야 합니다.
- 생성자·메서드가 있어도 보안 컨텍스트(HTTPS)나 권한, 사용자 활성화가 없으면 쓸 수 없는 API가 있습니다(자세히는 60편). 존재 검사와 사용 가능 검사를 구분합니다.
- 커스텀 요소 환경 검사는 `'customElements' in window`, Shadow DOM은 `'attachShadow' in Element.prototype`로 합니다(자세히는 16편).

## Fallback UI

폴백 UI는 기능이 지원되지 않거나 아직 준비되지 않았을 때 사용자가 보게 하는 대체 화면입니다. 기능을 못 쓰더라도 내용은 읽고 핵심 동작은 할 수 있어야 합니다.

| 상황 | 폴백 방법 |
|------|-----------|
| JS가 꺼져 있거나 로드 전 | 의미 있는 HTML 자식 콘텐츠, `noscript` |
| 커스텀 요소가 아직 정의되지 않음 | 라이트 DOM 자식이 그대로 보임. `:not(:defined)`로 모양 정리 |
| 슬롯에 내용이 없음 | `slot` 안의 폴백 콘텐츠(22편) |
| API 미지원 | 동일 목적의 다른 방법(예: 공유 API가 없으면 링크 복사) |
| 데이터 로딩 실패 | 오류 메시지와 재시도 버튼 |

```html
<x-map lat="37.5" lng="127">
  <a href="/map?lat=37.5&lng=127">지도에서 보기</a>
</x-map>
```

- 정의 전 `x-map`은 알 수 없는 인라인 요소처럼 자식 링크를 보여 줍니다. 정의되면 컴포넌트가 이를 지도로 대체합니다.
- 정의되기 전 깜박임은 `x-map:not(:defined)`에 크기를 예약하거나, `customElements.whenDefined('x-map')` 이후에 표시해 줄입니다.
- 폴백 경로도 테스트합니다. 사용하지 않는 코드는 가장 먼저 썩습니다.

## Polyfill 기준

폴리필은 브라우저에 없는 기능을 JavaScript로 채워 넣는 코드입니다. 넣을수록 번들 크기와 유지보수 비용이 늘어나므로 기준을 두고 판단합니다.

| 판단 항목 | 질문 |
|-----------|------|
| 지원 대상 | 지원하기로 한 브라우저에 실제로 없는가 (Baseline 목표와 대조) |
| 대체 가능성 | JavaScript로 동등하게 구현 가능한 기능인가 |
| 비용 | 크기와 성능 비용이 얻는 가치보다 작은가 |
| 대안 | 폴리필 없이 폴백 UI로 충분하지 않은가 |

- 구현 가능한 것: 새 배열·문자열 메서드, 단순한 API 객체. 구현 불가능하거나 한계가 큰 것: CSS 문법, 네트워크·보안 모델이 필요한 API(Service Worker, CORS), 하드웨어·권한 API, Shadow DOM의 스타일 캡슐화.
- 폴리필은 기능이 없을 때만 설치되도록 탐지 뒤에 둡니다. 지원하는 브라우저에서는 원본을 그대로 씁니다.
- 지원 목표를 Baseline Widely available로 정하면 폴리필이 필요한 기능 자체가 줄어듭니다.
- 폴리필이 표준과 100퍼센트 같지는 않으므로 동작 차이를 문서에 남깁니다.
- 가능하면 필요한 브라우저에만 전달합니다. 현대 브라우저가 쓰지 않는 코드를 내려보내지 않도록 동적 `import()`로 조건부 로드합니다(자세히는 14편).

**흔한 실수:** 모든 기능에 습관적으로 폴리필을 넣는 것입니다. 지원 대상 브라우저에 이미 있는 기능을 다시 채우는 코드는 낭비입니다.

## Graceful Degradation

우아한 성능 저하(graceful degradation)는 최신 환경을 기준으로 만들고, 기능이 부족한 환경에서는 기능을 줄여서라도 동작하게 하는 접근입니다. 반대 방향이 점진적 향상(progressive enhancement)입니다.

| 항목 | Graceful Degradation | Progressive Enhancement |
|------|----------------------|--------------------------|
| 출발점 | 전체 기능 | 핵심 기능(HTML) |
| 방향 | 없는 것을 덜어냄 | 있는 것을 더함 |
| 설계 질문 | 이 기능이 없으면 어떻게 되는가 | 가장 단순한 환경에서 무엇이 되는가 |

점진적 향상의 층은 다음과 같습니다.

1. 콘텐츠와 핵심 동작을 HTML로 구성한다(링크, 폼 제출).
2. CSS로 레이아웃과 모양을 더하고, 미지원은 `@supports`로 가른다.
3. JavaScript로 상호작용을 더하고, API 존재를 검사한다.
4. 최신 API는 있을 때만 추가한다.

- 웹 컴포넌트에서는 라이트 DOM 콘텐츠가 곧 1층입니다. 정의되면 업그레이드되어 향상되는 구조가 자연스럽습니다(자세히는 16편).
- 실패가 사용자의 핵심 작업을 막아서는 안 됩니다. 예: 날짜 선택 컴포넌트가 로드되지 않아도 `input`에 직접 입력할 수 있어야 합니다.
- 두 접근은 배타적이지 않습니다. 새 기능은 향상으로 얹고, 이미 있는 복잡한 앱은 폴백을 점검하는 식으로 섞어 씁니다.

## Customized Built-in 호환성 주의

Customized Built-in 요소는 `HTMLButtonElement` 같은 기존 요소를 상속하고 `customElements.define(name, Class, { extends: 'button' })`로 정의한 뒤 `is` 속성으로 쓰는 커스텀 요소입니다.

```html
<button is="x-confirm-button">삭제</button>
```

- Safari는 지원하지 않습니다(MDN). 즉 `is` 속성이 무시되어 일반 `button`으로 남고 정의한 동작이 실행되지 않습니다. Chrome과 Firefox는 지원합니다.
- 일반(autonomous) 커스텀 요소는 모든 주요 브라우저에서 지원됩니다.
- Customized Built-in은 상속한 요소의 접근성·폼 동작을 공짜로 얻는 장점이 있지만, 미지원 환경에서는 향상이 사라집니다. 사라져도 원본 `button`으로 동작하므로 점진적 향상 방식으로만 씁니다.
- 지원 탐지는 정의 뒤 인스턴스가 클래스의 것인지로 확인합니다.

```js
class Probe extends HTMLButtonElement {}
let ok = false
try {
  const ext = { extends: 'button' }
  customElements.define('x-probe', Probe, ext)
  const opt = { is: 'x-probe' }
  const el = document.createElement('button', opt)
  ok = el instanceof Probe
} catch {}
```

- 폼 연동이 목적이면 일반 커스텀 요소에 `ElementInternals`를 쓰는 편이 모든 엔진에서 동작합니다(자세히는 26편). 접근성이 목적이면 내부에 네이티브 요소를 두고 감싸는 방식도 있습니다.

## 실험적 API 격리

실험적 API는 표준화·구현이 진행 중이라 이름, 동작, 지원 범위가 바뀔 수 있는 API입니다. 핵심 경로가 의존하면 안 됩니다.

### 오리진 트라이얼과 실험 플래그

- 오리진 트라이얼(origin trial)은 Chrome이 실험 기능을 정해진 기간 동안 등록한 사이트에서만 쓰게 하는 제도입니다. 토큰을 받아 `<meta http-equiv="origin-trial" content="토큰">`, `Origin-Trial` HTTP 헤더, 또는 JavaScript로 제공합니다.
- 기간이 끝나거나 토큰이 잘못되면 Chrome이 그 토큰을 무시하므로 기능이 조용히 사라집니다. 토큰 유무와 상관없이 기능 탐지가 필요한 이유입니다.
- 실험 플래그(Chrome의 `chrome://flags` 등)는 사용자가 직접 켜는 설정이라 사용자 환경에 기대할 수 없습니다. 개발자가 자기 브라우저에서 시험할 때만 씁니다.

격리 방법은 다음과 같습니다.

| 방법 | 내용 |
|------|------|
| 어댑터 모듈 | 실험 API 호출을 한 모듈에 모으고 앱은 그 모듈만 호출 |
| 탐지 후 사용 | 존재와 `availability` 같은 상태를 확인한 뒤 호출 |
| 폴백 필수 | API가 없거나 실패해도 같은 목적의 기본 경로가 동작 |
| 지연 로드 | 동적 `import()`로 미지원 브라우저에는 코드를 보내지 않음 |
| 제거 계획 | 표준이 되거나 폐기될 때 걷어낼 위치를 한 곳으로 제한 |

```js
export async function share(data) {
  if ('share' in navigator) return navigator.share(data)
  await navigator.clipboard.writeText(data.url) // 폴백
}
```

### 단일 엔진 API 다루기

특정 엔진에서만 제공되는 API가 있습니다. 대표적인 것이 Chrome이 제공하는 내장 AI API입니다. 아래 상태는 Chrome 문서를 확인한 시점의 것이며 빠르게 바뀝니다.

| API | 상태(Chrome 문서 기준) |
|-----|------------------------|
| Translator, Language Detector, Summarizer | 안정(Chrome 138) |
| Prompt API | 안정(Chrome 148)은 확장 프로그램 한정. 웹은 오리진 트라이얼 |
| Writer, Rewriter | 개발자 트라이얼 |
| Proofreader | 오리진 트라이얼 |

Translator API의 경우 Chrome 138 이상과 Edge 148 이상에서 지원되고 Firefox와 Safari는 지원하지 않습니다. 데스크톱 전용이고, 모델 다운로드에는 사용자 활성화가 필요하며, Web Worker에서는 쓸 수 없고, 교차 출처 iframe에서는 `allow="translator"` 권한이 필요합니다.

```js
if ('Translator' in self) {
  const opt = { sourceLanguage: 'en', targetLanguage: 'fr' }
  const state = await Translator.availability(opt)
  // state에 따라 만들기·다운로드 안내·폴백 분기
}
```

- 탐지는 이름 존재 확인(`'Translator' in self`)으로 시작해 `availability()`로 해당 언어 쌍을 쓸 수 있는지 확인합니다. 모델은 기기에 내려받아야 하므로 `monitor` 옵션의 `downloadprogress` 이벤트로 진행 상황을 보여 줍니다.
- 반드시 대체 경로를 둡니다. 서버 측 번역, 번역 버튼 숨김, 원문 표시 등 기능이 없을 때의 동작을 정합니다.
- 핵심 기능이 단일 엔진 API에 의존하게 만들지 않고, 있으면 더 좋아지는 향상 기능으로 둡니다.
- 입력 데이터가 기기 안에서 처리되는지, 서버로 나가는지 사양과 사용 조건을 문서로 확인해 사용자에게 알립니다.

## 호환성 테스트 매트릭스

호환성 테스트 매트릭스는 지원 대상의 조합을 표로 정하고, 조합마다 무엇을 어떻게 검증할지 정해 두는 계획입니다. 모든 조합을 같은 깊이로 시험하지 않고 우선순위를 둡니다.

| 축 | 값의 예 |
|----|---------|
| 엔진 | Chromium, Gecko(Firefox), WebKit(Safari) |
| 플랫폼 | 데스크톱, Android, iOS |
| 버전 | 지원 목표의 가장 오래된 버전과 최신 버전 |
| 입력 | 마우스, 터치, 키보드 |
| 사용자 설정 | 다크 모드, 모션 감소, 강제 색상, 확대, JS 비활성(핵심 경로) |

- 우선순위: 사용자 분석 데이터에서 비중이 큰 조합, 그리고 엔진이 달라 문제가 나는 조합(WebKit)을 먼저 봅니다.
- 자동화: 브라우저 자동화 도구에 엔진별 프로젝트를 만들어 같은 테스트를 Chromium, Firefox, WebKit에서 돌립니다(자세히는 69편).
- 자동화가 대신하지 못하는 것: iOS Safari의 실제 동작, 실제 기기의 터치·키보드, 보조 기술은 실기기로 확인합니다.
- 기준은 Baseline 목표와 일치시킵니다. 목표가 Baseline Widely available이면 매트릭스의 가장 오래된 버전은 Browserslist 쿼리의 결과와 같아야 합니다.

### Interop 프로젝트

Interop은 Apple, Google, Igalia, Microsoft, Mozilla가 함께 웹 플랫폼의 브라우저 간 일관성을 높이는 협력 프로젝트입니다. 해마다 중점 영역(예: Navigation API, View Transition, Storage Access API 같은 API와 CSS 기능)을 정하고 web-platform-tests 통과율로 점수를 냅니다. 어떤 기능이 Interop 중점 영역이면 엔진 간 차이가 줄어들 가능성이 높다는 신호이므로 도입 시기를 판단할 때 참고합니다.

## 핵심 정리

- 호환성은 MDN 표와 Can I Use(둘 다 BCD 기반)로 확인하고, 플래그 뒤 지원과 실험·폐기 상태는 미지원으로 취급합니다.
- Baseline은 핵심 브라우저(Chrome, Edge, Firefox, Safari) 전체의 지원 상태이며, Newly available 30개월 후가 Widely available입니다. Browserslist의 `baseline widely available` 같은 쿼리로 빌드 대상에 반영합니다.
- 브라우저를 추정하지 말고 기능을 탐지합니다. CSS는 `@supports`·`CSS.supports()`, JS는 `in` 검사와 동작 검사를 씁니다.
- 폴백 UI와 점진적 향상으로 핵심 작업이 항상 동작하게 하고, 폴리필은 지원 대상에 없고 JavaScript로 채울 수 있는 기능에만 씁니다.
- Customized Built-in은 Safari 미지원이므로 향상 용도로만 쓰고, 실험·단일 엔진 API(내장 AI API 포함)는 어댑터 뒤에서 탐지·폴백과 함께 격리합니다.
- 테스트 매트릭스는 엔진·플랫폼·버전·입력·사용자 설정 축으로 우선순위를 정하고, 실기기 확인을 남겨 둡니다.

## Bundler 없이 배포하기

번들러 없이 배포한다는 것은 작성한 ES Module 파일을 변환 없이 그대로 서버에 올리고 브라우저가 `import`를 따라 직접 불러오게 하는 방식입니다. 모듈 스크립트는 Baseline 2018입니다(자세히는 14편).

```html
<script type="module" src="/ui/x-button.js"></script>
```

```js
// /ui/x-button.js
import { baseSheet } from './styles.js' // 확장자 필수
```

- 브라우저는 확장자를 보충하지 않습니다. `./styles`가 아니라 `./styles.js`로 씁니다.
- 서버는 JavaScript MIME type(`text/javascript`)으로 응답해야 합니다. 다른 MIME type이면 모듈 스크립트 로드가 실패합니다.
- 패키지 이름만 쓴 `import 'lit'` 같은 bare specifier는 해석 규칙이 없어서 TypeError입니다. import map으로 이름을 URL에 연결합니다(아래 "import map으로 CDN 의존성 고정").
- 모듈 하나가 다음 모듈을 요청하므로 의존 깊이만큼 요청이 순서대로 이어집니다. 알려진 모듈은 `rel="modulepreload"`로 미리 병렬 요청합니다(Baseline 2023). 의존 모듈까지 자동으로 받을지는 브라우저마다 다르므로 필요한 모듈을 각각 적습니다.

```html
<link rel="modulepreload" href="/ui/x-button.js">
<link rel="modulepreload" href="/ui/styles.js">
```

| 장점 | 단점 |
|------|------|
| 빌드 도구와 변환 단계가 없음 | 파일이 많으면 요청이 늘고 지연이 쌓임 |
| 소스와 배포 파일이 같아 디버깅이 쉬움 | 의존성 이름을 import map으로 직접 관리 |
| 파일 단위로 캐시되어 일부만 바꿔도 재다운로드가 작음 | 타입 선언, 압축, 변환(JSX·TypeScript)은 별도 |

소스를 브라우저가 이해하는 JavaScript와 CSS로만 작성하는 소규모 라이브러리에 적합합니다.

## Bundler와 함께 배포하기

번들러는 모듈 그래프를 합치고 압축해서 소수의 파일로 내보냅니다. 요청 수와 전송량을 줄이고, TypeScript 같은 소스를 변환할 때 씁니다.

Vite의 라이브러리 모드(`build.lib`)는 라이브러리용 번들을 만듭니다. 단일 진입점은 기본으로 `es`와 `umd`, 진입점이 여러 개이면 `es`와 `cjs`를 냅니다. `formats`로 바꿀 수 있습니다.

```js
// vite.config.js
export default {
  build: {
    lib: { entry: 'src/index.js', formats: ['es'] },
    rolldownOptions: { external: ['lit'] },
  },
}
```

- `external`에 적은 의존성은 번들에 넣지 않고 `import` 문으로 남깁니다. 사용자의 앱이 같은 의존성을 한 벌만 갖게 하려는 설정입니다. 최신 Vite 문서는 `rolldownOptions`를 쓰고, 이전 버전은 `rollupOptions`였습니다.
- 컴포넌트마다 파일을 따로 내보내면(진입점을 여러 개로) 사용자가 쓰는 컴포넌트만 가져갈 수 있습니다. 하나로 합친 번들은 CDN에서 한 줄로 불러오기 쉽습니다. 둘 다 내보내는 라이브러리가 많습니다(진입점 설계는 72편).
- 번들 안에서 CSS를 가져오면 별도 CSS 파일로 나옵니다. Shadow DOM 컴포넌트는 CSS를 JavaScript 문자열이나 `CSSStyleSheet`로 포함시켜 shadow root에 붙입니다(자세히는 72편, 24편).
- 압축 파일에는 소스 맵을 함께 배포해야 사용자의 디버깅이 가능합니다.
- 번들 결과의 대상 브라우저 범위를 문서화합니다. Vite 8 기본 대상은 Baseline Widely Available 기준의 Chrome 111, Edge 111, Firefox 114, Safari 16.4 이상입니다.

## NPM 패키지화

npm 패키지는 `package.json`과 배포할 파일을 묶은 tarball입니다. 패키지에 담을 파일과 진입점을 `package.json`이 정합니다.

```json
{
  "name": "@acme/ui",
  "version": "1.4.0",
  "type": "module",
  "exports": {
    ".": "./dist/index.js",
    "./button": "./dist/x-button.js"
  },
  "files": ["dist"],
  "customElements": "custom-elements.json"
}
```

| 필드 | 역할 |
|------|------|
| `name`, `version` | 패키지 이름과 버전. `version`은 node-semver로 해석되어야 하고 배포에 필수 |
| `exports` | 공개 진입점. 적지 않은 경로는 가져올 수 없음. `main`보다 우선(자세히는 72편) |
| `files` | 배포에 포함할 파일. 생략하면 전체를 포함하되 `package.json`, `README`, `LICENSE`는 항상 포함 |
| `type` | `module`이면 `.js`를 ES Module로 해석 |
| `customElements` | Custom Elements Manifest 파일 위치(자세히는 75편) |
| `peerDependencies` | 사용자의 앱이 설치해야 하는 의존성. npm 7부터 자동 설치 |

- `npm pack --dry-run`은 파일을 만들지 않고 어떤 파일이 담길지 출력합니다. 배포 전에 `files`가 맞는지 확인합니다.
- `npm publish`로 올리고, 같은 버전 번호는 다시 올릴 수 없다는 전제로 운영합니다. 한 번 배포한 버전은 수정하지 않고 새 버전을 냅니다(아래 "Semantic Versioning").
- `npm version patch`, `minor`, `major`는 `package.json`의 버전을 올리고 기본으로 git 커밋과 태그를 만듭니다. `--no-git-tag-version`으로 끌 수 있습니다.
- `peerDependencies`로 두는 대상은 사용자 앱과 공유해야 하는 것(프레임워크, 같은 컴포넌트 기반 라이브러리)입니다. 번들에 넣으면 앱에 두 벌이 실립니다.
- 컴포넌트 라이브러리는 `package.json`에 `sideEffects` 필드로 부수 효과를 알립니다(자세히는 72편).

## Semantic Versioning

유의적 버전(Semantic Versioning 2.0.0)은 버전을 `MAJOR.MINOR.PATCH` 세 숫자로 쓰고, 어떤 종류의 변경이 어느 숫자를 올리는지 정한 규칙입니다.

| 올리는 자리 | 언제 |
|-------------|------|
| MAJOR | 하위 호환이 깨지는 공개 API 변경 |
| MINOR | 하위 호환을 유지하는 기능 추가. 공개 API를 폐기 예고(deprecated)로 표시할 때도 올림 |
| PATCH | 하위 호환을 유지하는 버그 수정 |

- 규칙의 전제는 공개 API를 선언하는 것입니다. 무엇이 공개 API인지 정하지 않으면 어떤 변경이 breaking인지 정할 수 없습니다(아래 "API 변경 관리").
- 배포한 버전의 내용은 바꾸지 않습니다. 고치려면 새 버전을 냅니다.
- `0.y.z`는 초기 개발 단계로, 언제든 바뀔 수 있고 공개 API를 안정적으로 보지 않습니다. `1.0.0`이 공개 API가 정의되었다는 선언입니다.
- 사전 배포 버전은 하이픈을 붙여 `1.0.0-beta.1`처럼 쓰며 정식 버전보다 우선순위가 낮습니다. 빌드 메타데이터는 `+` 뒤에 붙이고 우선순위 비교에서 무시됩니다.
- 버전은 왼쪽부터 숫자로 비교합니다. `1.9.0`보다 `1.10.0`이 큽니다.

사용자는 범위 표기로 업데이트 허용 범위를 정합니다.

| 표기 | 허용 |
|------|------|
| `~1.0.4` 또는 `1.0.x` | 패치만 |
| `^1.0.4` 또는 `1.x` | 마이너와 패치 |
| `*` | 모든 버전 |

따라서 PATCH나 MINOR에 breaking 변경을 넣으면 `^`로 범위를 잡은 모든 사용자의 앱이 깨집니다. 판단이 애매하면 MAJOR를 올립니다.

## API 변경 관리

Web Component의 공개 API는 사용자 코드나 마크업이 직접 의존하는 모든 표면입니다. 컴포넌트는 JavaScript 메서드뿐 아니라 HTML 속성, 이벤트, CSS 훅까지 공개 API가 됩니다(자세히는 19편).

| 표면 | 호환을 깨는 변경 | 호환을 유지하는 변경 |
|------|------------------|----------------------|
| 태그 이름 | 이름 변경, 삭제 | 새 태그 추가 |
| 속성·프로퍼티 | 이름 변경, 삭제, 허용 값·타입 축소, 기본값 변경 | 새 선택 속성 추가, 허용 값 확대 |
| 메서드 | 이름·인수·반환값 변경, 삭제 | 선택 인수 추가 |
| 이벤트 | 이름 변경, 버블링·`composed` 변경, `detail` 구조 변경 | `detail`에 필드 추가, 새 이벤트 추가 |
| 슬롯 | 이름 변경, 기본 슬롯 의미 변경 | 새 슬롯 추가 |
| `::part`, `:state()` | 이름 변경, 삭제, 가리키는 요소 변경 | 새 part·상태 추가 |
| CSS 커스텀 속성 | 이름 변경, 삭제, 허용 값 변경 | 새 속성 추가 |
| 접근성 동작 | 역할, 키보드 조작, 이름 계산 변경 | 기존 동작 유지한 개선 |

- shadow tree 안의 DOM 구조와 클래스 이름은 공개 API가 아니라고 문서에 선언합니다. `::part()`로 연 요소만 약속에 들어갑니다(자세히는 24편).
- 기본값 변경은 겉보기에 사소해도 동작이 바뀌므로 breaking으로 다룹니다. 폼 값의 직렬화 형식, 이벤트 발생 시점의 변경도 마찬가지입니다.
- breaking 변경은 곧바로 하지 않고 단계를 거칩니다. 새 API 추가(MINOR) → 옛 API 폐기 예고(MINOR) → 옛 API 제거(MAJOR).
- 속성 이름을 바꿀 때는 옛 이름과 새 이름을 함께 받는 기간을 둡니다. `attributeChangedCallback`에서 옛 속성이 오면 새 속성 처리로 넘기고 경고를 냅니다(자세히는 18편).
- 공개 API를 사람이 읽는 문서와 별개로 기계가 읽는 목록으로 두면(Custom Elements Manifest) 버전 사이의 차이를 도구로 비교할 수 있습니다(자세히는 75편).

## CDN 배포

CDN(Content Delivery Network)은 파일을 사용자와 가까운 서버에서 내려 주는 서비스입니다. 라이브러리를 npm에 올리면 npm 미러형 CDN이 그 파일을 곧바로 서빙합니다. jsDelivr는 `/npm/패키지@버전/파일` 형식의 주소를 씁니다.

```html
<script type="module"
  src="https://cdn.jsdelivr.net/npm/acme-ui@1.4.0/a.js">
</script>
```

| 주소의 버전 부분 | 의미 | 운영 사용 |
|------------------|------|-----------|
| `@1.4.0` | 정확히 그 버전 | 권장 |
| `@1` 또는 `@1.4` | 범위의 최신 버전 | 가능하나 내용이 바뀜 |
| `@latest` 또는 생략 | 최신 버전 | jsDelivr가 운영 사용을 권하지 않음 |
| `@beta` 같은 태그 | 태그가 가리키는 버전 | 운영 사용을 권하지 않음 |

- 정확한 버전 주소를 쓰면 내용이 고정되므로 CDN 캐시를 길게 잡을 수 있고, 배포 시점에 앱이 갑자기 바뀌는 일이 없습니다.
- 파일 이름에 `.min`을 붙이면 jsDelivr가 압축본을 생성해 주고, 경로를 생략하면 패키지의 기본 파일이 압축되어 나옵니다. 이렇게 생성된 파일은 직접 올린 파일과 바이트가 달라서 SRI 해시를 그 파일 기준으로 다시 계산해야 합니다.
- 자체 도메인 CDN을 쓰면 파일 이름에 해시나 버전을 넣어 영구 캐시하고, HTML이 가리키는 주소만 바꾸는 방식이 일반적입니다.
- 다른 출처에서 모듈을 불러오므로 서버가 CORS 응답 헤더를 보내야 합니다. 모듈 스크립트는 항상 CORS 모드로 요청됩니다(자세히는 62편).

## import map으로 CDN 의존성 고정

**import map**은 모듈 지정자를 URL에 연결하는 JSON 표입니다. `script` 요소의 `type="importmap"`으로 선언하고, 이후의 `import` 문에 적용됩니다. Baseline 2023입니다.

```html
<script type="importmap">
{
  "imports": {
    "@acme/ui": "https://cdn.example/ui@1.4.0/index.js",
    "lit": "https://cdn.jsdelivr.net/npm/lit@3.3.1/+esm"
  }
}
</script>
```

```js
import '@acme/ui' // 위 URL로 해석됨
```

- import map은 이를 사용하는 모듈 스크립트보다 먼저 선언되어야 합니다. 이미 해석된 지정자를 나중의 import map이 바꿀 수는 없습니다.
- `src`, `async`, `defer`, `crossorigin`, `integrity` 같은 속성은 import map의 `script` 요소에 쓸 수 없습니다.
- import map은 `import` 문과 `import()`에만 적용됩니다. `script src` 주소나 워커 스크립트의 주소에는 적용되지 않습니다.
- 키와 값이 모두 `/`로 끝나면 접두사 매핑입니다. `"@acme/ui/": ".../@acme/ui@1.4.0/dist/"`로 쓰면 `@acme/ui/x-button.js`가 해당 경로로 해석됩니다.
- 모든 의존성의 버전을 import map 한 곳에 적으면 버전 변경이 한 곳에서 일어나고, 소스 코드의 `import` 문은 버전과 무관해집니다.
- `<script type="importmap">`을 여러 개 두면 합쳐지는 기능은 Chrome 133, Safari 18.4부터 지원하며 Firefox는 기본 지원이 아니어서 Baseline이 아닙니다. 하나로 작성합니다.
- 서버가 만든 HTML에서 같은 import map을 모든 페이지에 넣고, 배포 때 그 한 곳만 갱신하면 CDN 버전을 일괄 바꿀 수 있습니다.

## CDN 리소스 SRI 적용

SRI(Subresource Integrity)는 불러온 파일의 해시가 기대한 값과 같을 때만 사용하도록 브라우저에 지시하는 기능입니다. CDN이나 CDN 계정이 침해되어 파일이 바뀌어도 사용되지 않게 막습니다. Baseline 2018입니다.

```html
<script type="module" crossorigin="anonymous"
  src="https://cdn.jsdelivr.net/npm/@acme/ui@1.4.0/index.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K">
</script>
```

- `integrity`는 `알고리즘-base64해시` 형식이고 `sha256`, `sha384`, `sha512`를 지원합니다. 여러 해시를 공백으로 구분해 적을 수 있고, 알고리즘이 섞여 있으면 가장 강한 알고리즘의 해시만 비교합니다. 같은 알고리즘의 해시가 여럿이면 하나라도 맞으면 통과합니다.
- 해시가 맞지 않으면 브라우저는 리소스를 사용하지 않고 네트워크 오류를 냅니다.
- 다른 출처 리소스는 CORS 요청이어야 하므로 `crossorigin`을 지정해야 합니다. 없으면 `no-cors` 요청이 되어 항상 실패합니다.
- `script`, 그리고 `rel`이 `stylesheet`, `preload`, `modulepreload`인 `link`에 쓸 수 있습니다.
- 해시는 바이트 단위로 계산되므로 버전 범위(`@1`), `latest`, 서버 압축을 바꿀 수 있는 주소와는 함께 쓸 수 없습니다. 정확한 버전과 SRI를 함께 씁니다.
- 해시는 `cat 파일 | openssl dgst -sha384 -binary | openssl base64 -A`로 만듭니다.

불러오는 모듈에도 SRI를 적용하려면 import map의 `integrity` 키에 URL별 해시를 적습니다. Chrome 127, Firefox 138, Safari 18부터 지원합니다.

```html
<script type="importmap">
{
  "imports": { "ui": "https://cdn.example/ui@1.4.0/i.js" },
  "integrity": {
    "https://cdn.example/ui@1.4.0/i.js": "sha384-..."
  }
}
</script>
```

- 모듈이 다른 모듈을 `import`하므로 `script` 요소의 `integrity`만으로는 의존 모듈이 검증되지 않습니다. 의존 모듈까지 검증하려면 import map의 `integrity`에 각각 적습니다.
- 사이트 전체에서 SRI를 강제하려면 `Integrity-Policy` 응답 헤더로 `blocked-destinations=(script)` 같은 정책을 선언하고, 먼저 `Integrity-Policy-Report-Only`로 위반을 확인합니다.

## 여러 버전 공존과 스코프 레지스트리

한 페이지에 같은 라이브러리의 두 버전이 실리면 전역 `customElements`에서 태그 이름이 충돌합니다. 같은 이름으로 `define()`을 두 번 호출하면 `NotSupportedError`입니다.

| 방법 | 동작 | 제약 |
|------|------|------|
| 태그 접두사에 버전·팀 포함 | `x2-button`처럼 이름이 다름 | 사용자가 마크업의 태그를 바꿔야 함 |
| 정의 가드 | 이미 있으면 정의하지 않고 먼저 로드된 쪽을 사용 | 두 번째 버전이 첫 버전을 대신함 |
| 범위 지정 레지스트리 | shadow root마다 별도 레지스트리에 같은 이름 정의 | 지원 엔진이 제한됨 |
| import map `scopes` | 경로별로 다른 버전의 URL로 연결 | JavaScript 모듈 그래프만 분리하고 태그 충돌은 별도 처리 |

```js
const registry = new CustomElementRegistry()
registry.define('x-button', ButtonV2)
const root = host.attachShadow({
  mode: 'open',
  customElementRegistry: registry,
})
```

- 범위 지정 레지스트리는 Chrome·Edge 146, Safari 26부터 지원하고 Firefox는 지원하지 않아 Baseline이 아닙니다. 점진적 향상으로 다루고 접두사 방식을 대체 경로로 둡니다(자세히는 29편).
- import map의 `scopes`는 가져오는 쪽 스크립트의 URL이 키와 맞을 때만 적용되는 별도 매핑입니다. `/legacy/` 아래 스크립트는 구 버전 URL로, 나머지는 새 버전 URL로 해석하게 할 수 있습니다. 가장 구체적인 스코프가 우선합니다.
- 같은 패키지의 두 버전을 npm으로 함께 설치하려면 별칭 문법을 씁니다. `npm install ui1@npm:@acme/ui@1`처럼 설치하면 `ui1`이라는 이름으로 가져올 수 있습니다. 별칭은 프로젝트 안에서만 적용되고 하위 의존성의 이름은 바꾸지 않습니다.
- 가장 안전한 정책은 한 페이지에 한 버전만 싣는 것입니다. 공존이 필요하면 마이크로 프런트엔드 경계처럼 경계가 분명한 곳에서만 합니다.

## 폐기 예고(deprecation) 경고 전략

폐기 예고는 API를 제거하기 전에 사용자에게 대체 방법과 제거 일정을 알리는 단계입니다. 유의적 버전은 폐기 예고를 MINOR 증가로, 제거를 MAJOR 증가로 정합니다.

```js
const warned = new Set()
export function deprecate(key, message) {
  if (warned.has(key)) return
  warned.add(key)
  console.warn(`[x-ui] ${message}`)
}
```

```js
// 옛 속성 type을 variant로 바꾸는 중
attributeChangedCallback(name, _old, value) {
  if (name === 'type') {
    deprecate('type', 'type은 4.0에서 제거됩니다. variant 사용')
    this.variant = value
  }
}
```

- 경고에는 무엇이 폐기되었는지, 대신 무엇을 써야 하는지, 언제 제거되는지를 모두 적습니다.
- 같은 경고는 한 번만 냅니다. 요소마다 반복하면 콘솔이 묻혀서 다른 경고도 보이지 않습니다. 위의 `warned` 집합이 그 역할입니다.
- 개발 빌드에서만 경고하고 운영 번들에서는 제거하는 방식도 있습니다. 다만 운영에서만 보이는 문제를 놓치므로 폐기 API 사용 여부를 확인하는 방법은 따로 둡니다.
- 폐기 기간 동안 옛 API는 새 API와 같은 동작을 유지합니다. 경고만 추가하고 동작을 바꾸지 않아야 MINOR 변경으로 허용됩니다.
- 제거는 폐기 예고 이후의 MAJOR에서 합니다. 폐기를 알린 버전과 제거 버전을 경고, 변경 기록, 문서에 같은 값으로 적습니다.
- npm에서는 `npm deprecate 패키지@버전 "메시지"`로 특정 버전이나 범위를 폐기 표시합니다. 사용자가 설치할 때 registry의 경고가 나오고, 패키지는 삭제되지 않아 계속 설치할 수 있습니다. 메시지를 빈 문자열로 주면 표시가 해제됩니다.

## 변경 기록과 마이그레이션 문서

변경 기록(changelog)은 버전마다 무엇이 바뀌었는지 사람이 읽도록 정리한 파일입니다. Keep a Changelog 형식은 최신 버전을 위에 두고, 버전 제목을 `[1.4.0] - 2026-10-05`처럼 쓰며, 변경을 분류별로 모읍니다.

| 분류 | 내용 |
|------|------|
| Added | 새 기능 |
| Changed | 기존 동작의 변경 |
| Deprecated | 곧 제거될 기능 |
| Removed | 제거된 기능 |
| Fixed | 버그 수정 |
| Security | 보안 취약점 수정 |

```md
## [Unreleased]

## [2.0.0] - 2026-10-05
### Removed
- `type` 속성 (3.2.0에서 폐기 예고)
### Changed
- `x-dialog`의 `close` 이벤트가 버블링하지 않음
```

- 맨 위에 `Unreleased` 절을 두고 배포 때 그 내용을 새 버전 항목으로 옮깁니다.
- 철회한 버전은 `[1.3.0] - 2026-09-01 [YANKED]`처럼 표시합니다.
- 변경 기록은 사람이 읽는 요약이므로 커밋 목록을 그대로 붙이지 않습니다. 사용자가 해야 할 일이 바뀌는 항목을 앞에 둡니다.

마이그레이션 문서는 MAJOR 버전을 올릴 때 사용자가 따라 할 수 있는 이전 절차입니다.

- 깨지는 변경마다 이전 코드와 새 코드를 나란히 보여 줍니다.
- 영향을 받는 대상(태그, 속성, 이벤트, 슬롯, part, 커스텀 속성)을 표로 모읍니다.
- 가능한 변경은 코드 변환 스크립트나 검색 패턴을 제공해 사용자가 직접 찾지 않게 합니다.
- 폐기 예고 단계에서 이미 경고한 내용이면 그 버전을 명시해 두어서 사용자가 어디까지 이전했는지 확인할 수 있게 합니다.

## 핵심 정리

- 번들러 없는 배포는 확장자가 있는 상대 경로와 import map, `modulepreload`로 구성하고, 번들 배포는 `external`로 공유 의존성을 번들에서 빼고 소스 맵을 함께 냅니다.
- npm 패키지는 `exports`로 공개 진입점을 정하고 `files`로 담을 파일을 제한하며, `npm pack --dry-run`으로 내용을 확인한 뒤 배포합니다.
- 유의적 버전은 호환을 깨면 MAJOR, 기능 추가와 폐기 예고는 MINOR, 버그 수정은 PATCH이며, 먼저 공개 API(태그, 속성, 이벤트, 슬롯, part, 커스텀 속성, 접근성 동작)의 범위를 정해야 적용됩니다.
- CDN에서는 정확한 버전 주소를 쓰고, import map으로 의존성 URL을 한 곳에 고정하며, `integrity`와 `crossorigin`으로 SRI를 적용합니다.
- 두 버전의 공존은 접두사 분리나 범위 지정 레지스트리(미Baseline)로 풀고, 폐기는 대체 API·제거 버전을 담은 경고를 한 번만 내는 단계를 거쳐 MAJOR에서 제거합니다.
- 변경 기록은 분류별로 쓰고 MAJOR 때는 이전 절차를 담은 마이그레이션 문서를 함께 냅니다.

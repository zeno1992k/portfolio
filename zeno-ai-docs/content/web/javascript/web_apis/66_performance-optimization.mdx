## Reflow와 Repaint 최적화

브라우저는 화면 갱신마다 JavaScript, 스타일, 레이아웃, 페인트, 합성(composite) 단계를 거칩니다(렌더링 모델은 02편). 무엇을 바꾸느냐에 따라 거치는 단계가 달라집니다.

| 바꾸는 것 | 거치는 단계 | 예 |
|-----------|-------------|----|
| 기하(geometry) | 스타일, 레이아웃, 페인트, 합성 | `width`, `height`, `top`, `margin`, `font-size` |
| 그리기만 | 스타일, 페인트, 합성 | `background-image`, `box-shadow`, `color` |
| 합성만 | 스타일, 합성 | `transform`, `opacity` |

- 레이아웃 단계를 다시 하는 것이 리플로(reflow), 페인트를 다시 하는 것이 리페인트(repaint)입니다. 리플로는 요소의 크기·위치가 바뀌면 일어나고, 후손과 이웃에 영향을 주면 범위가 넓어집니다.
- 합성기 전용 속성은 `transform`과 `opacity` 둘뿐입니다. 애니메이션은 이 속성으로 만들면 레이아웃과 페인트를 건너뜁니다(애니메이션은 46편).
- 요소를 따로 합성 레이어로 올리는 힌트가 `will-change: transform`입니다. 레이어마다 메모리를 쓰고 GPU로 올리는 비용이 들므로 필요한 요소에만 쓰고, 끝나면 제거합니다.
- 60fps에서 한 프레임은 약 16.7ms이고, 브라우저 자체 작업을 빼면 코드가 쓸 수 있는 시간은 10ms 안팎입니다.

```css
.box { left: 0; }
.box.moved { left: 100px; }  /* ❌ 레이아웃부터 다시 */

.box { transform: translateX(0); }
.box.moved { transform: translateX(100px); } /* ✅ 합성만 */
```

- 여러 스타일을 바꿀 때는 개별 속성을 하나씩 대입하지 말고 클래스를 한 번 바꿉니다. 바꾸는 시점이 모이면 브라우저가 한 번에 처리합니다.
- 일부 요소를 렌더링에서 빼려면 `display: none`으로 뺀 채 고친 뒤 되돌리거나, `DocumentFragment`에서 조립한 뒤 한 번에 붙입니다(삽입은 04편).

## Layout Thrashing 방지

레이아웃 스래싱(layout thrashing)은 DOM 쓰기와 기하 읽기를 번갈아 반복해, 읽을 때마다 레이아웃을 강제로 다시 계산하게 만드는 패턴입니다. 강제 동기 레이아웃(forced reflow)이라고도 합니다.

```js
for (const p of paragraphs) {
  p.style.width = `${box.offsetWidth}px`
  // ❌ 쓰기 다음 읽기가 반복되어 매번 레이아웃 계산
}
```

- 스타일이 바뀌어 레이아웃이 무효가 된 상태에서 `offsetWidth`, `offsetHeight`, `getBoundingClientRect()` 같은 기하 값을 읽으면, 브라우저는 값을 정확히 돌려주려고 즉시 레이아웃을 계산합니다(요소 기하는 06편).
- 레이아웃이 한 번뿐이면 괜찮고, 반복문에서 쓰기와 읽기가 번갈아 나올 때 비용이 요소 수만큼 곱해집니다.

### 읽기·쓰기 일괄 처리

모든 읽기를 먼저 끝낸 뒤 모든 쓰기를 합니다.

```js
const width = box.offsetWidth         // 읽기 한 번
for (const p of paragraphs) {
  p.style.width = `${width}px`        // 쓰기만 반복
}
```

- 요소마다 다른 값을 읽어야 하면 읽기 단계에서 배열에 모두 모은 뒤, 쓰기 단계에서 적용합니다.
- 읽기와 쓰기를 여러 모듈이 각자 할 때는 `requestAnimationFrame` 콜백에 쓰기를 모아 다음 프레임의 렌더링 직전에 한꺼번에 실행합니다(스케줄링은 08편).
- 기하 값을 꼭 읽어야 하는 비동기 흐름에서는 `ResizeObserver`·`IntersectionObserver`로 값을 받으면 읽기를 위한 강제 레이아웃이 없습니다(자세히는 43편).
- DevTools 성능 패널이 강제 리플로를 표시합니다(자세히는 70편).

## 이벤트 최적화

이벤트 핸들러는 입력과 가까운 경로에 있어서 느리면 INP에 바로 나타납니다. 핸들러 수와 실행 빈도, 핸들러 안의 일을 줄입니다.

| 기법 | 효과 |
|------|------|
| 이벤트 위임 | 부모에 리스너 하나만 달고 `event.target`으로 구분. 리스너 수와 등록 비용을 줄이고 동적으로 추가된 자식도 처리 |
| `passive: true` | 핸들러가 `preventDefault()`를 호출하지 않겠다고 약속. 스크롤이 핸들러 완료를 기다리지 않음 |
| 디바운스 | 연속 입력이 멈춘 뒤 한 번만 실행(검색어 입력) |
| 스로틀 | 일정 간격마다 최대 한 번 실행(스크롤, 리사이즈) |
| `requestAnimationFrame` 합치기 | 이벤트에서는 값만 저장하고 프레임당 한 번 갱신 |
| `once: true` | 첫 실행 후 자동 제거 |

```js
el.addEventListener('touchstart', onTouch, { passive: true })

let y = 0, queued = false
addEventListener('scroll', () => {
  y = scrollY
  if (queued) return
  queued = true
  requestAnimationFrame(() => { queued = false; update(y) })
})
```

- `window`, `document`, `document.body`에 단 `wheel`, `touchstart`, `touchmove` 리스너는 기본이 `passive: true`입니다. 요소에 단 리스너는 기본값이 다르므로 명시합니다.
- passive 리스너 안의 `preventDefault()`는 무시됩니다.
- `pointermove`, `scroll`, `resize`처럼 한 프레임에 여러 번 발생하는 이벤트는 핸들러를 가볍게 하거나 위 표의 기법으로 줄입니다(이벤트 종류는 09편).
- 루프 안에서 리스너마다 새 익명 함수를 만들지 말고 하나의 함수를 재사용합니다. 제거 방법은 67편에서 다룹니다.

**흔한 실수:** 위임을 쓰면서 `event.target`을 그대로 비교하는 것입니다. 클릭한 곳이 자식 요소이면 일치하지 않으므로 `event.target.closest('.item')`으로 찾습니다.

## INP 개선을 위한 긴 작업 분할

50ms를 넘는 작업은 Long Task이고, 그동안 메인 스레드가 입력에 응답하지 못해 INP가 나빠집니다(측정은 65편). 해결은 작업을 쪼개 중간에 메인 스레드를 양보하는 것입니다.

```js
async function handleClick() {
  showSpinner()       // 먼저 보여 줄 UI
  await scheduler.yield()
  doHeavyWork()       // 다음 작업으로 미룸
}
```

- `scheduler.yield()`는 메인 스레드를 양보하고, 이어서 실행할 부분을 우선순위가 올라간 큐에 넣는 Promise를 돌려줍니다. `setTimeout`으로 양보할 때보다 다른 작업에 밀리지 않습니다.
- 현재 Baseline이 아니므로 기능 탐지가 필요하고, 없으면 `setTimeout(resolve, 0)`으로 대신합니다.

```js
const yieldToMain = () =>
  globalThis.scheduler?.yield
    ? scheduler.yield()
    : new Promise((r) => setTimeout(r, 0))
```

- 목록을 처리할 때는 항목마다 양보하지 말고, 마지막 양보 이후 일정 시간(예: 50ms)이 지났을 때만 양보합니다. 양보 자체에도 비용이 있습니다.
- `isInputPending()`은 입력이 대기 중인지 확인하는 API였지만 권장되지 않습니다. 입력이 있어도 `false`를 돌려줄 수 있고 애니메이션 같은 비입력 갱신을 고려하지 않기 때문입니다.
- 쪼갤 수 없는 계산은 Web Worker로 옮깁니다(자세히는 54편).
- 사용자에게 먼저 보여 줄 피드백(스피너, 상태 변경)을 양보 앞에 두고, 무거운 일은 양보 뒤에 둡니다.

## DOM 노드 수 관리

DOM이 크면 초기 렌더링, 갱신, 메모리 모두 느려집니다. 선택자 매칭은 더 많은 트리를 훑고, DOM을 바꾸는 상호작용마다 스타일·레이아웃 비용이 커지며, 요소 참조가 메모리를 차지합니다.

- Lighthouse는 노드가 약 800개를 넘으면 경고하고 1,400개를 넘으면 과도하다고 봅니다.
- 개수는 `document.querySelectorAll('*').length`로 셉니다. DevTools 성능 모니터에서 실시간으로도 볼 수 있습니다.

줄이는 방법입니다.

- 불필요한 래퍼 요소와 깊은 중첩을 없앱니다.
- 화면 밖 항목은 만들지 않고 필요할 때 만듭니다(아래 "가상 스크롤").
- 만들어 두어야 한다면 `content-visibility: auto`로 화면 밖 렌더링을 건너뜁니다.

```css
.card {
  content-visibility: auto;
  contain-intrinsic-size: auto 400px;
}
```

- `content-visibility: auto`는 화면 밖 요소의 레이아웃·스타일·페인트를 건너뛰지만 DOM과 접근성 트리에는 남아서 찾기와 포커스 이동이 계속 동작합니다. Baseline 2024입니다.
- 건너뛴 요소는 크기가 0으로 취급되어 스크롤바가 흔들리므로 `contain-intrinsic-size`로 예상 크기를 줍니다. `auto` 키워드를 앞에 쓰면 한 번 렌더링된 뒤에는 실제 크기를 기억합니다.
- `content-visibility: hidden`은 `display: none`처럼 내용을 그리지 않지만 요소는 DOM에 그대로 남습니다.

## 가상 스크롤

가상 스크롤(virtual scrolling)은 목록 전체를 DOM에 두지 않고 화면에 보이는 항목과 앞뒤 여유분만 렌더링하는 구현 기법입니다. 표준 API가 아니라 직접 구현하거나 라이브러리를 씁니다. 수천 개 이상의 목록에서 노드 수를 일정하게 유지합니다(실전 구조는 80편).

동작 방식입니다.

1. 컨테이너에 전체 높이를 주어 스크롤바를 만듭니다(항목 수 곱하기 항목 높이, 또는 높이 합).
2. 스크롤 위치로 보여야 할 항목의 인덱스 범위를 계산합니다.
3. 그 범위만 DOM에 두고 `transform: translateY(...)`로 제자리에 놓습니다.
4. 스크롤하면 범위를 다시 계산해 노드를 재사용하거나 교체합니다.

```js
const first = Math.floor(scrollTop / rowHeight)
const count = Math.ceil(viewHeight / rowHeight) + 2
const visible = items.slice(first, first + count)
// 이 항목만 렌더링. 위치는 first * rowHeight
```

- 항목 높이가 제각각이면 측정해서 캐시해야 하므로 구현이 복잡해집니다. 고정 높이가 가장 단순합니다.
- 화면 밖 항목이 DOM에 없으므로 브라우저 내장 찾기, 앵커 이동, 스크린 리더 탐색이 그 항목에 닿지 않습니다. 접근성에 필요한 `aria-rowcount`·`aria-setsize` 같은 정보를 직접 제공해야 합니다(자세히는 27편).
- 노드가 수백 개 수준이면 `content-visibility: auto`가 더 적은 구현으로 충분합니다.

## Lazy Component

Lazy Component는 컴포넌트의 정의와 인스턴스 생성을 실제로 필요한 시점까지 미루는 방식입니다. 초기 JavaScript와 초기 DOM을 줄입니다.

```js
const slot = document.querySelector('#chart-slot')
new IntersectionObserver(async (entries, io) => {
  if (!entries[0].isIntersecting) return
  io.disconnect()
  await import('./ui-chart.js') // 정의가 등록됨
  slot.append(document.createElement('ui-chart'))
}).observe(slot)
```

- 동적 `import()`는 모듈을 비동기로 불러 모듈 네임스페이스 객체로 이행하는 Promise를 돌려줍니다. 일반 스크립트에서도 쓸 수 있고 Baseline 널리 지원(2020년 1월부터)입니다. 같은 모듈은 한 번만 불러옵니다(모듈 로딩은 14편).
- 불러올 시점은 보통 뷰포트 진입(`IntersectionObserver`), 사용자 동작(클릭, 호버), 유휴 시간입니다(옵저버는 43편).
- 커스텀 요소는 태그가 문서에 이미 있어도 정의가 등록될 때 업그레이드됩니다. 정의를 늦게 불러도 마크업은 그대로 둘 수 있습니다(업그레이드는 17편).
- 정의가 오기 전의 모습은 `:not(:defined)` 선택자로 크기를 확보하거나 자리 표시를 보여 줍니다. 이 구간이 CLS의 원인이 되지 않게 크기를 예약합니다.
- 불러오기가 실패하면 `import()`의 Promise가 거부됩니다. 재시도나 대체 UI를 준비합니다.

## 코드 스플리팅

코드 스플리팅(code splitting)은 번들을 여러 조각으로 나눠 처음에 필요한 코드만 보내는 기법입니다. 초기 JavaScript 용량을 줄여 INP와 LCP에 도움이 됩니다.

| 방식 | 내용 |
|------|------|
| 엔트리·벤더 분리 | 자주 안 바뀌는 서드파티 코드를 별도 번들로 빼서 따로 캐시 |
| 동적 `import()` 분리 | `import()`를 만나는 지점에서 번들러가 조각을 나눠, 그 시점에 불러옴 |

- 번들러(webpack, Rollup, Parcel 등)가 `import()` 지점을 별도 청크로 분리합니다. 직접 분리 설정을 쓰는 방법은 번들러마다 다릅니다.
- 라우트 단위나 컴포넌트 단위로 나누는 것이 가장 단순합니다. 라우트별 청크는 해당 화면에 들어갈 때 불러옵니다(라우팅은 35편).
- 너무 잘게 나누면 요청 수와 폭포 지연이 늘어납니다. 사용자가 곧 쓸 청크는 `<link rel="modulepreload">`나 `prefetch` 같은 힌트로 미리 받게 합니다(자세히는 15편).
- 서버에서 HTML을 미리 그려 주는 방식과 함께 쓰면 초기 콘텐츠 표시가 더 빨라집니다(자세히는 76편).

## 이미지 크기 지정과 CLS 방지

CLS의 흔한 원인은 크기를 모르는 이미지가 뒤늦게 로드되며 아래 내용을 밀어내는 것입니다. 이미지가 로드되기 전에 자리를 예약합니다.

```html
<img src="a.jpg" width="800" height="450" alt="..." />
```

```css
img { max-width: 100%; height: auto; }
.thumb { aspect-ratio: 16 / 9; }
```

- `width`와 `height` 속성은 렌더링 크기가 아니라 비율을 알려 줍니다. 브라우저가 이 비율로 공간을 먼저 확보하고, CSS `height: auto`로 반응형을 유지합니다.
- 속성을 줄 수 없으면 CSS `aspect-ratio`로 비율을 지정합니다.
- 광고·임베드·늦게 주입되는 콘텐츠도 `min-height`나 `aspect-ratio`로 자리를 확보합니다. 사용자 동작 없이 기존 콘텐츠 위에 삽입하지 않습니다.
- 웹 폰트는 `font-display: optional`과 비슷한 크기의 대체 폰트로 글자가 바뀌며 밀리는 것을 줄입니다.
- 애니메이션은 `top`·`left` 대신 `transform`으로 만들어야 레이아웃 이동이 생기지 않습니다.

## srcset과 sizes 반응형 이미지

`srcset`과 `sizes`는 화면에 맞는 크기의 이미지 파일을 브라우저가 고르게 해서 전송량을 줄입니다. HTML이 CSS·스크립트보다 먼저 이미지를 미리 받기 때문에 CSS가 아닌 마크업으로 표현합니다.

```html
<img
  srcset="a-480.jpg 480w, a-800.jpg 800w, a-1600.jpg 1600w"
  sizes="(width <= 600px) 100vw, 800px"
  src="a-800.jpg"
  width="800" height="450" alt="..." />
```

- `srcset`의 `w` 설명자는 파일의 본래 너비(px)입니다. `sizes`는 이미지가 레이아웃에서 차지할 슬롯 너비이며, 앞의 조건부터 검사해 처음 맞는 값을 씁니다. 브라우저는 슬롯 너비와 기기 화소 밀도를 곱한 값에 가까운 파일을 고릅니다.
- `sizes`를 생략하면 슬롯이 `100vw`라고 가정합니다. 이미지가 더 작게 보이면 낭비가 생기므로 정확히 씁니다.
- 화소 밀도만 다를 때는 `x` 설명자를 씁니다. `srcset="a-1x.jpg, a-2x.jpg 2x"`처럼 쓰고 `sizes`는 필요 없습니다.
- 레이아웃별로 다른 자르기나 포맷을 쓰려면 `picture` 안에 `source`와 `media`를 둡니다(아트 디렉션). 마지막의 `img`는 필수 대체입니다.
- `srcset`은 브라우저에게 후보를 주는 힌트입니다. 어느 파일을 고를지는 브라우저가 결정합니다.
- 화면 밖 이미지의 지연 로딩(`loading="lazy"`)은 15편에서 다룹니다.

## bfcache 차단 요인 제거

bfcache(back/forward cache)는 사용자가 이동해 나갈 때 페이지를 메모리에 그대로 보관했다가 뒤로·앞으로 가기에서 즉시 복원하는 브라우저 최적화입니다. 복원되면 네트워크 요청과 레이아웃 이동이 없습니다. 차단 요인이 있으면 매번 새로 로드합니다.

| 차단 요인 | 대처 |
|-----------|------|
| `unload` 리스너 | 쓰지 않는다. `pagehide`로 대체 |
| `Cache-Control: no-store` | 민감한 페이지에만 쓴다. 그 밖에는 `no-cache`나 `max-age=0` |
| `window.opener` 참조 | `rel="noopener"`(요즘 브라우저 기본값) |
| 진행 중인 `fetch`, 열린 IndexedDB·WebSocket·WebRTC 연결 | `pagehide`에서 닫고 `pageshow`에서 다시 연다 |

- 복원 여부는 `pageshow` 이벤트의 `event.persisted`가 `true`인지로 알 수 있습니다. `pagehide`의 `persisted`가 `true`이면 페이지가 캐시에 들어갈 수 있다는 뜻일 뿐 보장은 아닙니다.
- 복원된 페이지는 이전 상태 그대로이므로, 로그인 상태나 오래된 데이터를 `pageshow`에서 갱신합니다(페이지 수명 주기는 60편).
- 이유를 알려면 네비게이션 엔트리의 `notRestoredReasons`를 읽습니다. `unload-listener`, `fetch`, `websocket`, `lock` 등이 보고됩니다. 이 API는 현재 Baseline이 아닙니다. Chrome DevTools의 Application 패널에서도 테스트합니다.
- bfcache에서 복원되면 로드 자체가 없어서 LCP와 CLS 같은 지표에도 유리합니다.

## 성능 예산

성능 예산(performance budget)은 성능에 영향을 주는 지표에 미리 정해 두는 한도입니다. 기능을 추가할 때 한도를 넘기면 최적화하거나 기능을 줄이거나 추가를 막습니다.

| 유형 | 예 |
|------|----|
| 수량 기반 | JS 총 용량, 이미지 크기, 요청 수, 스크립트 수 |
| 마일스톤 | FCP, LCP, INP 같은 사용자 체감 시점 |
| 규칙 기반 | Lighthouse 점수 같은 모범 사례 점검 결과 |

- 수량 기반 지표는 팀에 설명하기 쉽고 개발 초기에 정하기 좋지만 체감 품질을 직접 말해 주지는 않습니다. 마일스톤은 체감에 가깝지만 측정 환경이 필요합니다.
- 예산은 프로젝트 초기에 정해야 나중에 되돌리는 일이 줄어듭니다.
- 강제는 빌드와 CI에서 합니다. webpack, bundlesize, Lighthouse CI 같은 도구를 빌드에 연결해 한도를 넘기면 막습니다.
- web.dev는 예시 기준으로 3G 모바일에서 Time to Interactive 5초 이내, 핵심 경로 리소스 압축 후 170KB 이내를 제시합니다. 이 값은 예시이며 서비스의 사용자 환경에 맞춰 정합니다.
- 현장 데이터(65편)로 실제 사용자의 LCP·INP·CLS를 추적하고, 예산은 그 목표(2.5초, 200ms, 0.1)와 연결해 정합니다.

## 핵심 정리

- 합성 전용 속성(`transform`, `opacity`)은 레이아웃과 페인트를 건너뛰고, 기하 속성을 바꾸면 전체 파이프라인을 다시 돌립니다.
- 레이아웃 스래싱은 쓰기와 기하 읽기를 번갈아 하는 데서 생기며, 읽기를 먼저 모두 하고 쓰기를 모아서 해결합니다.
- 이벤트는 위임, passive, 디바운스·스로틀, 프레임 단위 합치기로 줄이고, 50ms 넘는 작업은 `scheduler.yield()`(없으면 `setTimeout`)로 쪼개 INP를 지킵니다.
- DOM 노드는 800개 안팎부터 경고 대상이며, `content-visibility: auto`와 가상 스크롤로 화면 밖 비용을 줄입니다. 지연 로딩은 `import()`와 코드 스플리팅으로 초기 JS를 줄입니다.
- 이미지는 `width`·`height`나 `aspect-ratio`로 자리를 예약하고 `srcset`·`sizes`로 알맞은 파일을 받게 하며, `unload`·`no-store` 같은 bfcache 차단 요인은 제거합니다.
- 성능 예산은 한도를 미리 정해 CI에서 강제합니다.

## 코어를 나누는 기준

애플리케이션 코어는 화면 컴포넌트가 공통으로 기대는 네 조각입니다. 의존은 한 방향입니다.

| 조각 | 책임 | 아는 것 | 모르는 것 |
|------|------|---------|-----------|
| 기반 클래스 | 생명주기, 정리, 스타일, 이벤트 발행 | DOM | 상태, URL |
| 반응형 기반 클래스 | 속성 선언, 갱신 예약, 렌더 호출 | 기반 클래스 | 스토어, 라우터 |
| 라우터 | URL과 화면의 대응, 이동 처리 | 라우트 표, 페이지 태그 이름 | 상태 구조 |
| 스토어 | 공유 상태, 변경 알림 | 상태 값 | DOM, 컴포넌트 |

- 라우터와 스토어는 서로를 모릅니다. 연결은 앱 조립 단계에서 합니다(자세히는 82편).
- 코드는 모두 설계를 읽기 위한 축약본입니다. 오류 처리와 타입은 줄였습니다.
- 상태 설계는 31편, 데이터 흐름은 32편, 렌더링 방식은 30편, 라우팅 원리는 35편에서 다뤘습니다.

## Component Base Class 만들기

기반 클래스는 모든 컴포넌트가 반복하는 작업을 한곳에 모은 `HTMLElement` 하위 클래스입니다. 반복하는 작업은 네 가지입니다. shadow root와 스타일 준비, 한 번만 하는 초기화와 연결마다 하는 작업의 분리, 연결 해제 시 정리, 이벤트 발행입니다.

### 뼈대와 초기화

```js
export class BaseElement extends HTMLElement {
  static styles = []      // CSSStyleSheet 배열
  static template = null  // HTMLTemplateElement
  #ac = null
  #inited = false

  constructor() {
    super()
    const open = { mode: 'open' }
    this.root = this.shadowRoot ?? this.attachShadow(open)
  }
}
```

- 생성자에서는 shadow root 준비만 합니다. 속성을 읽거나 자식을 추가하지 않습니다(자세히는 18편).
- `this.shadowRoot ??` 검사는 Declarative Shadow DOM으로 이미 만들어진 root를 재사용하기 위한 것입니다(자세히는 21편, 76편).
- 스타일은 `adoptedStyleSheets`로 인스턴스 사이에 공유합니다(자세히는 24편).

### 연결과 해제

```js
connectedCallback() {
  this.#ac = new AbortController()
  if (!this.#inited) {
    this.#inited = true
    this.root.adoptedStyleSheets = this.constructor.styles
    const t = this.constructor.template
    if (t && !this.root.hasChildNodes()) {
      this.root.append(t.content.cloneNode(true))
    }
    this.init()
  }
  this.connected()
}
```

```js
disconnectedCallback() {
  this.#ac.abort()
  this.disconnected()
}
connectedMoveCallback() {}  // moveBefore 이동은 정리하지 않음
init() {}
connected() {}
disconnected() {}
```

- `init()`은 처음 연결될 때 한 번, `connected()`는 연결될 때마다 실행됩니다. 요소는 떼었다 다시 붙일 수 있기 때문입니다(자세히는 18편).
- 연결마다 새 `AbortController`를 만들고 해제 때 `abort()`합니다. 연결 수명의 모든 구독을 이 신호 하나로 정리합니다.
- `connectedMoveCallback`을 정의하면 `moveBefore()`로 옮길 때 `connectedCallback`과 `disconnectedCallback` 대신 이것만 호출됩니다. 비워 두면 이동 중에 정리와 재초기화가 일어나지 않습니다.
- 서브클래스는 `connectedCallback`을 덮어쓰지 않고 `init`, `connected`, `disconnected` 훅만 구현합니다. 덮어쓰면 기반 클래스의 정리 보장이 깨집니다.

### 정리와 이벤트 발행 도우미

```js
get signal() { return this.#ac?.signal }

on(target, type, fn, opts = {}) {
  const o = { ...opts, signal: this.signal }
  target.addEventListener(type, fn, o)
}

emit(type, detail, opts = {}) {
  const init = { detail, bubbles: true, composed: true }
  const e = new CustomEvent(type, { ...init, ...opts })
  return this.dispatchEvent(e)
}

$(selector) { return this.root.querySelector(selector) }
```

- `on()`은 `signal` 옵션을 붙여 등록하므로 연결이 끊기면 리스너가 모두 해제됩니다. 해제 코드를 따로 쓰지 않습니다(자세히는 7편, 18편).
- `emit()`은 `bubbles`와 `composed`를 켠 `CustomEvent`를 보냅니다. 바깥은 이벤트 이름과 `detail`만 압니다(자세히는 25편).
- `on()`은 `connected()` 안에서 `window`, `document`, 스토어 같은 바깥 대상에 쓰는 도우미입니다.

**흔한 실수:** `init()`에서 `this.on(...)`을 쓰는 것입니다. 요소가 떼였다 붙으면 `init()`은 다시 실행되지 않는데 신호는 이미 중단되어 리스너가 사라집니다. 자기 shadow 안의 요소에 다는 리스너는 `init()`에서 `addEventListener`로 직접 달고, 바깥 대상에 다는 리스너는 `connected()`에서 `on()`으로 답니다. 자기 shadow의 요소는 요소와 함께 사라지므로 해제가 필요 없습니다.

### 설계 판단

- 기반 클래스는 상속 구조의 한 층만 둡니다. 층이 깊어지면 서브클래스가 부모의 내부 순서에 묶입니다(자세히는 29편의 상속보다 합성).
- 컴포넌트 이름 정의는 클래스 안에 두지 않고 `register` 같은 함수로 호출자가 정합니다(자세히는 33편).
- 모든 컴포넌트가 Shadow DOM을 쓸 필요는 없습니다. 쓰지 않는 컴포넌트가 많으면 `root`를 `this`로 바꾸는 `static shadow = false` 옵션을 둘 수 있지만, 이때 `adoptedStyleSheets`와 슬롯은 쓸 수 없습니다.

## Reactive Base Component 만들기

반응형 기반 클래스는 기반 클래스에 "프로퍼티가 바뀌면 렌더를 한 번 호출한다"는 규칙을 더한 것입니다. 구성 요소는 세 가지입니다. 선언한 프로퍼티의 접근자, 속성과 프로퍼티의 상호 변환, 마이크로태스크로 모으는 갱신 예약입니다(자세히는 19편, 30편, 31편).

### 프로퍼티 선언

```js
class CounterBox extends ReactiveElement {
  static properties = {
    count: { type: Number, reflect: true, default: 0 },
    label: { type: String },
  }
}
CounterBox.register('counter-box')
```

| 옵션 | 뜻 |
|------|----|
| `type` | 속성 문자열을 프로퍼티 값으로 바꾸는 방법. `String`, `Number`, `Boolean` |
| `reflect` | 프로퍼티가 바뀌면 속성에도 반영 |
| `default` | 값이 없을 때 읽히는 값 |

- 객체와 배열 프로퍼티는 `type`을 주지 않고 프로퍼티로만 씁니다. 속성은 문자열만 담기 때문입니다(자세히는 19편).
- `observedAttributes`는 `define()` 시점에 읽히므로 `register`가 먼저 접근자를 만들고 그다음 `define()`을 호출합니다.

### 접근자와 속성 변환

```js
static get observedAttributes() {
  return Object.keys(this.properties).map(toKebab)
}
```

```js
static register(tag) {
  const props = Object.entries(this.properties)
  for (const [name, opt] of props) {
    Object.defineProperty(this.prototype, name, {
      get() { return this.#vals.get(name) ?? opt.default },
      set(v) {
        const old = this.#vals.get(name)
        if (Object.is(old, v)) return
        this.#vals.set(name, v)
        this.requestUpdate(name, old)
      },
    })
  }
  customElements.define(tag, this)
}
```

- `#vals`는 인스턴스의 값 저장소이고 접근자는 프로토타입에 한 번만 정의합니다. 같은 값을 대입하면 갱신을 요청하지 않습니다.
- `toKebab`은 `maxValue`를 `max-value`로 바꾸는 작은 함수입니다.

```js
attributeChangedCallback(attr, _old, value) {
  if (this.#reflecting) return
  const name = toCamel(attr)
  const { type } = this.constructor.properties[name]
  this[name] = fromAttr(type, value)
}
```

```js
function fromAttr(type, v) {
  if (type === Boolean) return v !== null
  if (type === Number) return v === null ? null : Number(v)
  return v
}
```

- 불리언 속성은 값이 아니라 있고 없음이 뜻입니다. 속성이 있으면 `true`, 제거되면 `false`입니다.
- `#reflecting`은 프로퍼티를 속성에 반영하는 중에 `attributeChangedCallback`이 다시 프로퍼티를 바꾸는 순환을 막는 플래그입니다.
- 마크업에 속성이 있으면 `connectedCallback` 전에 `attributeChangedCallback`이 먼저 호출됩니다. 그래서 첫 렌더는 항상 연결 뒤로 미룹니다.

### 갱신 예약

```js
#changed = new Map()   // 이름 → 이전 값
#pending = false
#done = Promise.resolve()
hasUpdated = false

get updateComplete() { return this.#done }

requestUpdate(name, old) {
  const ch = this.#changed
  if (name && !ch.has(name)) ch.set(name, old)
  if (this.#pending || !this.isConnected) return
  this.#pending = true
  this.#done = Promise.resolve().then(() => this.#flush())
}
```

- 같은 콜백 안에서 프로퍼티를 여러 번 바꿔도 `#pending`이 막아서 갱신은 한 번입니다. 갱신은 마이크로태스크로 실행되어 화면이 그려지기 전에 끝납니다(자세히는 8편, 30편).
- `#changed`는 바뀐 이름과 이전 값을 모읍니다. 렌더는 이 맵을 보고 바뀐 부분만 고칩니다.
- `updateComplete`는 갱신이 끝나는 약속입니다. 프로퍼티를 바꾼 직후에는 DOM이 아직 낡았으므로 DOM을 읽는 코드는 이 약속을 기다립니다.

### 갱신 실행

```js
#flush() {
  if (!this.isConnected) { this.#pending = false; return }
  this.willUpdate(this.#changed)  // 여기서 바꾼 값은 같은 갱신에 합류
  const changed = this.#changed
  this.#changed = new Map()
  this.#pending = false
  this.render(changed)
  this.#reflect(changed)
  this.hasUpdated = true
  this.updated(changed)           // 여기서 바꾸면 다음 갱신
}
```

| 훅 | 시점 | 용도 |
|----|------|------|
| `willUpdate(changed)` | 렌더 전 | 파생 값 계산. 여기서 바꾼 프로퍼티는 추가 갱신을 일으키지 않음 |
| `render(changed)` | 갱신 중 | DOM 갱신. 프로퍼티를 바꾸지 않음 |
| `updated(changed)` | 렌더 후 | DOM을 읽는 작업, 포커스, 외부 알림 |

- `updated()` 안에서 프로퍼티를 바꾸면 갱신이 한 번 더 일어납니다. 조건 없이 바꾸면 무한 루프이므로 값이 실제로 달라질 때만 바꿉니다(자세히는 31편).
- 연결 해제 중에 예약된 갱신은 그냥 끝나고 `#changed`는 남깁니다. 다시 연결되면 모은 변경으로 렌더합니다.

```js
connectedCallback() {
  super.connectedCallback()
  if (!this.hasUpdated) {
    const ch = this.#changed
    for (const k in this.constructor.properties) {
      if (!ch.has(k)) ch.set(k, undefined)
    }
  }
  this.requestUpdate()
}
```

- 첫 렌더는 선언된 모든 프로퍼티를 바뀐 것으로 취급해서 DOM의 초기 상태를 한 번에 채웁니다.

```js
#reflect(changed) {
  this.#reflecting = true
  for (const k of changed.keys()) {
    const o = this.constructor.properties[k]
    if (o?.reflect) setAttr(this, k, this[k], o.type)
  }
  this.#reflecting = false
}
```

- 반영은 렌더 뒤에 모아서 합니다. 속성 쓰기가 갱신 중에 흩어지지 않습니다.

### 사용하는 쪽

```js
const tpl = document.createElement('template')
tpl.innerHTML = '<button><span id="n"></span></button>'
```

```js
class CounterBox extends ReactiveElement {
  static template = tpl
  static properties = {
    count: { type: Number, default: 0 },
  }
  init() {
    const btn = this.$('button')
    btn.addEventListener('click', () => this.count++)
  }
  render(changed) {
    if (!changed.has('count')) return
    this.$('#n').textContent = this.count
  }
}
```

- 템플릿은 한 번 만들어 복제하고, `render`는 바뀐 프로퍼티에 해당하는 DOM만 고칩니다. DOM 비교 없이 변경점을 직접 추적하는 방식입니다(자세히는 30편).

### 업그레이드 전 프로퍼티 보존

요소가 정의되기 전에 `el.count = 5`를 대입하면 접근자가 없어서 인스턴스에 일반 프로퍼티로 남습니다. 생성자에서 이 값을 꺼내 접근자로 다시 대입합니다(자세히는 19편, 33편).

```js
constructor() {
  super()
  for (const k in this.constructor.properties) {
    if (!Object.hasOwn(this, k)) continue
    const v = this[k]
    delete this[k]
    this[k] = v
  }
}
```

**흔한 실수:**

- `render()` 안에서 프로퍼티를 바꾸는 것입니다. 갱신이 끝나기 전에 다음 갱신이 예약되어 렌더가 반복됩니다.
- 객체 프로퍼티를 제자리에서 고치는 것입니다(`this.items.push(x)`). `Object.is` 비교가 같다고 판단해서 갱신이 일어나지 않습니다. 새 배열을 대입합니다.

## Router 만들기

라우터는 URL과 화면 컴포넌트를 짝짓고, 이동이 일어날 때 그 화면을 출구(outlet)에 넣는 모듈입니다. 구성은 라우트 표, 매칭, 이동 가로채기, 렌더로 나뉩니다. 원리는 35편, 층 구조는 33편을 따릅니다.

### 라우트 표와 매칭

```js
const routes = [
  { path: '/', tag: 'home-page', title: '홈' },
  { path: '/orders/:id', tag: 'order-page', title: '상세',
    load: () => import('./pages/order-page.js') },
  { path: '/*', tag: 'not-found-page', title: '없는 페이지' },
]
```

```js
export class Router extends EventTarget {
  #routes
  #outlet
  constructor(routes, outlet) {
    super()
    this.#outlet = outlet
    this.#routes = routes.map((r) => ({
      ...r, pattern: new URLPattern({ pathname: r.path }),
    }))
  }
}
```

- `URLPattern`은 Baseline 2025입니다. 패턴은 생성자에서 한 번만 만듭니다. 지원하지 않는 환경은 폴리필을 씁니다.
- 라우터는 `EventTarget`을 상속해서 `routechange` 같은 이벤트를 `addEventListener`로 구독하게 합니다. `EventTarget` 생성자는 Baseline 2020입니다.

```js
match(url) {
  for (const route of this.#routes) {
    const m = route.pattern.exec({ pathname: url.pathname })
    if (m) {
      const params = m.pathname.groups
      return { route, params, query: url.searchParams }
    }
  }
}
```

- 위에서부터 처음 일치하는 항목을 씁니다. 구체적인 패턴이 앞, 포괄 패턴이 뒤입니다. 맨 끝의 `/*`가 404를 맡아서 `match`는 항상 결과를 돌려줍니다.
- 결과 하나가 이후 모든 단계에 전달되는 라우트 컨텍스트입니다: 라우트 정의, 경로 매개변수, 쿼리.

### 이동 가로채기

```js
start() {
  const on = (e) => this.#onNavigate(e)
  navigation.addEventListener('navigate', on)
  this.#show(new URL(location.href), noAbort)
}
```

```js
#onNavigate(e) {
  if (!e.canIntercept || e.hashChange) return
  if (e.downloadRequest !== null || e.formData) return
  const url = new URL(e.destination.url)
  e.intercept({
    focusReset: 'manual',
    scroll: 'manual',
    handler: async () => {
      await this.#show(url, e.signal)
      e.scroll()
    },
  })
}
```

- 링크 클릭, 뒤로 가기, `navigation.navigate()`가 모두 `navigate` 이벤트로 들어옵니다. 링크를 가로채는 클릭 리스너가 필요 없습니다.
- 가로채지 않는 조건은 다른 출처(`canIntercept`가 거짓), 해시만 바뀌는 이동, 다운로드, 폼 제출입니다.
- 첫 문서 로드에는 `navigate` 이벤트가 없으므로 `start()`가 현재 주소를 직접 한 번 그립니다. `noAbort`는 취소되지 않는 신호(`new AbortController().signal`)를 모듈에 하나 만들어 둔 상수입니다.
- `e.signal`은 이동이 취소되면 중단됩니다. 렌더 단계가 이 신호를 확인합니다.
- 포커스와 스크롤은 `'manual'`로 바꾸고 렌더 뒤에 직접 처리합니다. 포커스는 `#mount`가 outlet으로 옮기고 스크롤은 `e.scroll()`이 기본 규칙을 적용합니다. 기본 `'after-transition'`은 포커스를 `body`로 되돌립니다(자세히는 35편).
- Navigation API는 Baseline 2026입니다. 이전 브라우저는 아래 대체 경로를 씁니다.

### 화면 렌더

```js
#mount(tag, hit) {
  const page = document.createElement(tag)
  page.routeContext = hit
  this.#outlet.replaceChildren(page)
  this.#outlet.focus()   // outlet은 tabindex="-1"인 main
}
```

```js
async #show(url, signal) {
  const hit = this.match(url)
  try {
    await hit.route.load?.()
    if (signal.aborted) return
    this.#mount(hit.route.tag, hit)
  } catch {
    if (signal.aborted) return
    this.#mount('error-page', hit)
  }
  document.title = hit.route.title
  const detail = hit
  const ev = new CustomEvent('routechange', { detail })
  this.dispatchEvent(ev)
}
```

- `load()`는 라우트별 코드 스플리팅입니다. 모듈이 컴포넌트를 `define()`한 뒤에 요소를 만듭니다(자세히는 14편, 35편).
- `await` 뒤에는 `signal.aborted`를 확인합니다. 사용자가 다른 링크를 눌러 이동이 취소됐다면 늦게 온 결과로 화면을 덮지 않습니다(자세히는 39편).
- 페이지에는 요소를 만든 뒤 프로퍼티로 컨텍스트를 줍니다. 객체는 속성으로 전달할 수 없습니다(자세히는 32편).
- 불러오기가 실패하면 오류 화면으로 바꿉니다. 취소로 중단된 경우에는 아무것도 하지 않습니다.
- `routechange` 이벤트로 내비게이션의 `aria-current` 갱신, 분석 전송 같은 부가 작업이 구독합니다.

### 접근 제어와 코드로 이동

```js
const hit = this.match(url)
const to = await hit.route.guard?.(hit)
if (to) {
  navigation.navigate(to, { history: 'replace' })
  return
}
```

- 라우트 정의에 `guard`를 두고 렌더 앞에서 검사합니다. 거부하면 다른 경로로 `replace` 이동해서 기록에 차단된 주소가 남지 않게 합니다.
- 이동은 주소가 확정된 뒤에 `handler`가 실행되기 때문에 이 방식은 주소가 잠깐 바뀝니다. 확정 전에 걸러 주는 `precommitHandler`는 지원 상태가 고르지 않아 대체 경로로만 둡니다(자세히는 35편).
- 코드에서 이동할 때는 `navigation.navigate(path)`를 직접 부릅니다. 라우터를 거치지 않아도 같은 `navigate` 이벤트로 처리됩니다.

### History API 대체 경로

```js
#startHistory() {
  addEventListener('popstate', () => {
    this.#show(currentUrl(), noAbort)
  })
  document.addEventListener('click', (e) => {
    const a = linkOf(e)
    if (!a) return          // 제외 조건은 linkOf에서 검사
    e.preventDefault()
    history.pushState(null, '', a.href)
    this.#show(currentUrl(), noAbort)
  })
}
```

- `'navigation' in window`가 거짓이면 `start()`가 이 경로를 씁니다. `linkOf`는 35편의 제외 조건(수정 키, `target`, `download`, 다른 출처, 가운데 버튼)을 한곳에 모은 함수입니다.
- `popstate`는 `pushState`로 만든 이동에는 발생하지 않으므로 클릭 처리에서 직접 렌더합니다. `noAbort`는 취소할 일이 없다는 뜻으로 넘기는 신호이고 위에서 정의한 상수입니다.
- 두 경로는 `#show`를 공유합니다. 이동 감지만 교체되고 매칭과 렌더는 한 벌입니다.

**흔한 실수:**

- 시작 때 현재 주소를 그리지 않아 첫 화면이 비는 것입니다.
- 라우트 표에 `/*`를 앞에 두어 다른 라우트가 모두 가려지는 것입니다.
- 빌드 결과를 하위 경로에 배포했는데 라우트 경로에 그 접두사를 반영하지 않는 것입니다. 서버는 알 수 없는 경로에도 같은 HTML을 돌려줘야 새로고침과 직접 접근이 동작합니다(자세히는 73편).

## Store 만들기

스토어는 앱의 공유 상태를 컴포넌트 밖의 한 객체에 두고, 변경을 구독자에게 알리는 모듈입니다. 상태는 불변으로 다루고 변경은 새 객체를 만들어 대입합니다.

### 상태와 변경

```js
export function createStore(initial, actions = {}) {
  let state = initial
  const subs = new Set()
  const get = () => state

  function set(patch) {
    const next = typeof patch === 'function'
      ? patch(state) : { ...state, ...patch }
    if (Object.is(next, state)) return
    const prev = state
    state = next
    for (const fn of [...subs]) fn(state, prev)
  }
  // 이어서 subscribe, act, 반환
}
```

- 객체를 넘기면 얕게 합치고, 함수를 넘기면 현재 상태로 다음 상태를 계산하고 함수가 돌려준 값이 통째로 다음 상태가 됩니다(그래서 액션은 `...s`로 나머지 키를 이어받습니다). 함수 형태는 이전 값에 의존하는 변경에 씁니다.
- 새 상태가 이전과 같은 참조면 알리지 않습니다. 변경 여부를 참조 비교 한 번으로 판별하려면 상태를 제자리에서 고치지 않아야 합니다(자세히는 25편).
- 알림은 구독자 복사본을 순회합니다. 구독자가 알림 도중에 해제하거나 추가해도 이번 순회가 흔들리지 않습니다.
- 알림은 동기입니다. 렌더 일괄 처리는 구독하는 컴포넌트의 갱신 예약이 맡으므로 스토어가 또 모을 필요가 없습니다.

### 구독과 선택자

```js
function subscribe(fn, opts = {}) {
  const { select = (s) => s, equals = Object.is } = opts
  let last = select(state)
  const sub = (s) => {
    const v = select(s)
    if (equals(v, last)) return
    const prev = last
    last = v
    fn(v, prev)
  }
  subs.add(sub)
  if (opts.immediate) fn(last, undefined)
  return () => subs.delete(sub)
}
```

- 선택자(select)는 상태의 일부만 뽑는 함수입니다. 뽑은 값이 이전과 같으면 구독자를 호출하지 않아서 관련 없는 변경에 컴포넌트가 다시 그려지지 않습니다.
- 선택자가 매번 새 객체를 만들어 돌려주면(`(s) => ({ a: s.a })`) 항상 달라진 것으로 판단됩니다. 원시 값이나 상태 안의 기존 참조를 돌려주거나 `equals`를 직접 줍니다.
- `immediate`는 구독 직후 현재 값을 한 번 전달합니다. 컴포넌트의 초기 값 채우기를 구독 코드 한 곳으로 모읍니다.
- 구독 함수는 해제 함수를 돌려줍니다. 해제하지 않으면 DOM에서 빠진 컴포넌트가 스토어에 매달려 메모리에 남습니다(자세히는 67편).

### 액션

```js
const act = {}
for (const [name, fn] of Object.entries(actions)) {
  act[name] = (...args) => set((s) => fn(s, ...args))
}
return { get, set, subscribe, act }
```

```js
const store = createStore({ todos: [] }, {
  add: (s, text) => ({
    ...s, todos: [...s.todos, { text }],
  }),
})
store.act.add('buy milk')
```

- 액션은 현재 상태와 인수로 다음 상태를 돌려주는 순수 함수입니다. 상태를 바꾸는 방법을 이름 붙여 한곳에 모으면 컴포넌트가 상태 구조를 직접 만지지 않습니다.
- 비동기 작업(네트워크 요청)은 액션 안이 아니라 호출하는 쪽이나 서비스에서 하고, 결과를 액션으로 반영합니다(자세히는 82편).
- 객체 안쪽을 고칠 때는 바꿀 경로의 단계마다 스프레드로 새로 만듭니다. 깊은 중첩은 정규화로 줄입니다(자세히는 32편).

### 컴포넌트에 연결

```js
bind(store, select, prop) {
  const off = store.subscribe(
    (v) => { this[prop] = v },
    { select, immediate: true },
  )
  this.signal.addEventListener('abort', off)
}
```

```js
connected() {
  this.bind(app.store, (s) => s.todos, 'todos')
}
```

- `bind`는 반응형 기반 클래스에 두는 도우미입니다. 구독 해제를 연결 신호의 `abort`에 걸어서 따로 해제하지 않습니다.
- 스토어 값을 프로퍼티에 대입하면 접근자가 갱신을 예약합니다. 컴포넌트는 스토어를 직접 읽지 않고 자기 프로퍼티만 렌더합니다. 그래서 같은 컴포넌트를 스토어 없이 속성만으로도 쓸 수 있습니다.
- 스토어 인스턴스는 전역 변수에서 가져오지 않고 앱 조립 단계에서 만들어 컴포넌트에 전달합니다. 테스트에서 새 스토어로 바꿔 끼울 수 있습니다(자세히는 25편의 Context, 82편).

### 저장과 탭 간 동기화

```js
export function persist(store, key) {
  try {
    const saved = localStorage.getItem(key)
    if (saved) store.set(JSON.parse(saved))
  } catch {}
  store.subscribe((s) => {
    const json = JSON.stringify(s)
    try { localStorage.setItem(key, json) } catch {}
  })
}
```

- 저장소 접근은 비공개 모드나 용량 초과로 실패할 수 있으므로 `try`로 감쌉니다(자세히는 40편).
- 저장할 수 있는 값은 JSON이나 구조화 복제로 직렬화되는 값뿐입니다. 함수와 DOM 노드는 상태에 넣지 않습니다. `structuredClone`은 함수를 복제하지 못하고 `DataCloneError`를 던집니다.
- `storage` 이벤트는 같은 저장소를 쓰는 다른 문서에서만 발생합니다. 다른 탭의 변경을 받으려면 이 이벤트에서 `newValue`를 읽어 `store.set()`합니다. 현재 상태와 같으면 건너뛰어 서로 되쓰는 반복을 막습니다.
- 변경이 잦은 상태는 저장을 매번 하지 않고 모아서 합니다. 큰 데이터는 IndexedDB를 씁니다(자세히는 41편).

**흔한 실수:**

- 상태를 제자리에서 고치는 것(`state.todos.push(x)`)입니다. 참조가 같아서 알림이 가지 않습니다.
- 구독자 안에서 같은 스토어를 `set()`해서 알림이 끝없이 이어지는 것입니다. 파생 값은 저장하지 않고 선택자로 계산합니다.
- 컴포넌트가 전체 상태를 구독해 모든 변경에 렌더하는 것입니다. 필요한 조각만 선택자로 구독합니다.

## 핵심 정리

- 기반 클래스는 shadow root, 한 번만 하는 `init`과 연결마다 하는 `connected`, 연결 신호 기반 정리, `emit`을 맡고, 서브클래스는 `connectedCallback`을 덮어쓰지 않고 훅만 구현합니다.
- 반응형 기반 클래스는 선언한 프로퍼티의 접근자가 변경을 `Map`에 모으고 마이크로태스크 한 번으로 `render`를 호출합니다. 속성 변환과 반영은 순환 방지 플래그를 둡니다.
- 라우터는 `URLPattern`으로 매칭하고, Navigation API의 `navigate` 이벤트에서 `intercept()`로 화면을 바꾸며, 첫 로드와 취소(`signal`)를 직접 처리합니다. 대체 경로는 History API 클릭 가로채기입니다.
- 스토어는 불변 상태에 구독자 목록을 두고, 선택자로 필요한 조각만 구독하며, 해제 함수를 돌려줍니다.
- 컴포넌트는 스토어 값을 프로퍼티로만 받아 렌더하고, 구독 해제는 연결 신호에 걸어 둡니다. 라우터와 스토어는 서로를 모르고 조립 단계에서 만납니다.

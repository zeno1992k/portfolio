## Blob

Blob은 바이트 덩어리를 나타내는 변경 불가능한 객체입니다. 만들고 나면 내용을 바꿀 수 없고, 크기(`size`)와 MIME 유형(`type`)만 가집니다. Baseline 2015부터 널리 지원되고 워커에서도 쓸 수 있습니다.

```js
const json = JSON.stringify({ hello: 'world' })
const blob = new Blob([json], { type: 'application/json' })
blob.size // 17 (바이트)
blob.type // 'application/json'
```

- 생성자의 첫 인수는 조각의 배열입니다. 조각은 문자열, `ArrayBuffer`, 타입 배열(`Uint8Array` 등), 다른 `Blob`일 수 있고 순서대로 이어 붙여집니다. 문자열은 UTF-8 바이트로 들어갑니다.
- `type`은 소문자 ASCII로 저장되고 지정하지 않으면 빈 문자열입니다. 알 수 없는 유형도 빈 문자열입니다.
- 수정이 필요하면 새 Blob을 만듭니다. 기존 Blob을 조각으로 재사용하면 됩니다.

```js
const edited = new Blob([a.slice(0, 10), 'X', a.slice(10)])
```

- Blob은 구조화된 복제와 `postMessage()`로 다른 컨텍스트에 전달할 수 있습니다(IndexedDB에 저장하는 방법은 41편).
- 다른 API의 결과로도 얻습니다: `fetch` 응답의 `response.blob()`, `canvas.toBlob()`.

## File

File은 사용자 파일에 대한 정보를 더한 Blob입니다. `Blob`을 상속하므로 Blob을 받는 곳이면 어디서든 쓸 수 있습니다. Baseline 2020(생성자 기준)부터 널리 지원됩니다.

| 속성 | 의미 |
|------|------|
| `name` | 경로를 뺀 파일 이름 |
| `lastModified` | 마지막 수정 시각(1970년 1월 1일 기준 밀리초) |
| `webkitRelativePath` | 폴더 선택(`webkitdirectory`)으로 얻었을 때의 상대 경로 |
| `size`, `type` | `Blob`에서 상속 |

File을 얻는 경로는 세 가지입니다.

- `input type="file"`의 `files` 속성
- 드래그 앤 드롭의 `event.dataTransfer.files`(자세히는 49편)
- `FileSystemFileHandle.getFile()`(아래 File System Access 절)

코드에서 직접 만들 수도 있습니다.

```js
const file = new File(['a,b\n1,2'], 'data.csv', {
  type: 'text/csv',
  lastModified: Date.now(),
})
```

- `file.type`은 브라우저가 정한 값이라 비어 있거나 실제 내용과 다를 수 있습니다. 서버 검증이 반드시 필요합니다.
- `file.slice()`는 File이 아니라 Blob을 돌려줍니다.
- 이름에는 경로가 없습니다. 이름이 같은 파일이 서로 다른 폴더에 있을 수 있습니다.
- 사용자가 고르거나 끌어다 놓은 파일만 읽을 수 있고 경로 문자열로 임의의 파일을 열 수는 없습니다.

## FileList와 input의 파일 속성

`input type="file"`의 `files`는 `FileList`입니다. 읽기 전용이고 `length`, `item()`, 인덱스 접근이 있으며 `for...of`로 순회할 수 있습니다. 배열 메서드가 필요하면 `Array.from(input.files)`로 변환합니다.

```js
input.addEventListener('change', () => {
  const files = Array.from(input.files)
  handle(files)
  input.value = '' // 같은 파일을 다시 선택해도 change가 발생하도록
})
```

| 속성 | 설명 |
|------|------|
| `accept` | 선택창의 파일 필터. 확장자(`.pdf`), MIME 유형(`image/png`), 와일드카드(`image/*`)를 쉼표로 나열 |
| `multiple` | 여러 파일 선택 허용 |
| `capture` | 모바일에서 카메라·마이크로 바로 촬영. `user`(전면), `environment`(후면). `accept`의 `image/*`, `video/*`와 함께 씀 |
| `webkitdirectory` | 폴더를 선택하고 그 안의 모든 파일을 `files`에 담음. 각 File의 `webkitRelativePath`에 상대 경로가 들어감 |

- `accept`는 선택창에 주는 힌트일 뿐 검증이 아닙니다. 사용자가 필터를 바꾸거나 드롭으로 다른 파일을 올릴 수 있으므로 코드와 서버에서 다시 검사합니다.
- `capture`는 모바일 브라우저(Chrome Android, Firefox Android, Safari iOS)용입니다. Baseline이 아니며 데스크톱에서는 동작을 기대하지 않습니다(카메라 API 자체는 51편).
- `webkitdirectory`는 이름에 비표준 접두사가 남아 있지만 Baseline 2025입니다. 데스크톱은 Chrome·Edge 13, Firefox 50, Safari 11.1부터이고 모바일은 Chrome 132, Safari 18.4, Firefox 142부터입니다.
- `input.value`는 `C:\fakepath\파일이름` 형태의 가짜 경로입니다. 실제 경로는 노출되지 않습니다.
- 이벤트: `change`(선택됨), `input`, `cancel`(선택 없이 닫음).
- 입력창은 `display: none`이면 키보드 포커스를 받지 못합니다. 시각적으로만 숨기고 `label`이나 `::file-selector-button`(Baseline 2021)으로 꾸밉니다.
- 폼으로 제출하려면 `enctype="multipart/form-data"`가 필요합니다. 파일 필드는 본문에서 `Content-Disposition: form-data; name=...; filename=...`로 구분됩니다(폼은 11편).

## Blob 읽기 메서드

Blob의 내용은 `Promise`를 돌려주는 메서드로 읽습니다.

| 메서드 | 결과 | 지원 |
|--------|------|------|
| `text()` | UTF-8로 해석한 문자열 | Baseline 2021 |
| `arrayBuffer()` | `ArrayBuffer` | Baseline 2021 |
| `bytes()` | `Uint8Array` | Baseline 2026 (Chrome·Edge 144, Firefox 128, Safari 18) |
| `stream()` | 바이트 청크의 `ReadableStream` | Baseline 2021 |
| `slice(start, end, type)` | 구간을 잘라 낸 새 Blob | Baseline 2015 |

```js
const text = await blob.text()           // 문자열
const buf = await blob.arrayBuffer()     // 바이너리
const head = await blob.slice(0, 4).text() // 앞 4바이트만
```

- `text()`는 항상 UTF-8로 디코딩합니다. 다른 인코딩이면 `arrayBuffer()`로 받아 `TextDecoder`에 넘깁니다(아래 절).
- `slice()`는 즉시 새 Blob을 만들 뿐 내용을 복사해 읽지 않습니다. 음수 인덱스는 끝에서부터 셉니다. 큰 파일을 구간별로 처리하거나 분할 업로드할 때 씁니다.
- `stream()`은 파일 전체를 메모리에 올리지 않고 조금씩 읽어 처리합니다. 스트림 처리는 38편에서 다룹니다.
- 비슷하게 `new Response(blob).text()`로도 읽을 수 있습니다.

```js
const reader = file.stream().getReader()
for (;;) {
  const { done, value } = await reader.read()
  if (done) break
  consume(value) // Uint8Array 청크
}
```

## FileReader

FileReader는 Blob을 비동기로 읽는 이벤트 기반 객체입니다. Promise 메서드가 나오기 전의 API라서 새 코드는 `text()`·`arrayBuffer()`를 우선하고, FileReader는 아래 경우에 씁니다.

- `readAsDataURL()`로 data URL이 필요할 때(Blob에 대응하는 Promise 메서드가 없음)
- 읽는 중 `progress` 이벤트와 `abort()`가 필요할 때

| 메서드 | `result` |
|--------|----------|
| `readAsText(blob, encoding)` | 문자열. 인코딩 기본값은 UTF-8 |
| `readAsArrayBuffer(blob)` | `ArrayBuffer` |
| `readAsDataURL(blob)` | `data:` URL 문자열 |
| `readAsBinaryString(blob)` | 바이너리 문자열(폐지 예정) |
| `abort()` | 읽기 중단 |

```js
const reader = new FileReader()
reader.onload = () => console.log(reader.result)
reader.onerror = () => console.error(reader.error)
reader.readAsDataURL(file)
```

- `readyState`: `0`(EMPTY), `1`(LOADING), `2`(DONE).
- 이벤트: `loadstart`, `progress`(`loaded`, `total`, `lengthComputable`), `load`, `error`, `abort`, `loadend`(성공·실패·중단 모두).
- 읽는 중(LOADING)에 같은 객체로 다시 읽기를 시작하면 `InvalidStateError`입니다. 파일마다 새 FileReader를 만듭니다.
- `FileReaderSync`는 워커 안에서만 쓸 수 있는 동기 버전입니다(자세히는 54편).

Promise로 감싸면 `await`로 쓸 수 있습니다.

```js
const readDataURL = (blob) =>
  new Promise((resolve, reject) => {
    const r = new FileReader()
    r.onload = () => resolve(r.result)
    r.onerror = () => reject(r.error)
    r.readAsDataURL(blob)
  })
```

**흔한 실수:** `reader.result`를 `load` 전에 읽는 것입니다. 읽기가 끝나기 전에는 `null`입니다.

## TextEncoder / TextDecoder

문자열과 바이트를 서로 변환하는 API입니다. Baseline 2020부터 널리 지원되고 워커에서도 씁니다.

```js
const enc = new TextEncoder()
const bytes = enc.encode('가a') // Uint8Array(4)
const text = new TextDecoder().decode(bytes) // '가a'
```

`TextEncoder`는 항상 UTF-8만 씁니다.

- `encode(string)`은 새 `Uint8Array`를 돌려줍니다.
- `encodeInto(string, uint8Array)`는 기존 버퍼에 써 넣고 `{ read, written }`(읽은 문자 수, 쓴 바이트 수)를 돌려줍니다. Baseline 2021입니다. 버퍼가 모자라면 문자 단위로 잘라 쓰고 멈춥니다.

`TextDecoder`는 인코딩을 고를 수 있습니다.

```js
const buf = await file.arrayBuffer()
const text = new TextDecoder('euc-kr').decode(buf)
```

| 항목 | 설명 |
|------|------|
| `label` | 인코딩 이름. 기본 `utf-8`. `utf-16le`, `shift_jis`, `euc-kr` 등. 모르는 이름이면 `RangeError` |
| `fatal` | 기본 `false`: 잘못된 바이트를 U+FFFD로 대체. `true`: `TypeError`를 던짐 |
| `ignoreBOM` | 기본 `false`: 앞의 BOM(바이트 순서 표시)을 걷어 냄. `true`: 결과에 BOM을 남김 |
| `decode(buf, { stream: true })` | 청크가 중간에서 끊겨 멀티바이트 문자가 쪼개져도 다음 호출과 이어서 처리 |

- 스트림으로 조금씩 디코딩할 때 `stream: true`를 쓰지 않으면 청크 경계에서 글자가 깨집니다. 이 용도에는 `TextDecoderStream`이 편합니다(Baseline 2022, 자세히는 38편).
- 인코딩을 모르는 파일은 `fatal: true`로 시험해 UTF-8이 맞는지 확인할 수 있습니다.
- 인코딩 레이블은 사용자 입력이 아니라 알려진 값을 쓰게 제한합니다.

## URL.createObjectURL

`URL.createObjectURL(blob)`은 Blob(또는 File, MediaSource)을 가리키는 짧은 `blob:` URL을 만듭니다. 파일 내용을 문자열로 복사하지 않고 `img`, `video`, `a`, `iframe`의 주소로 쓸 수 있습니다.

```js
const url = URL.createObjectURL(file)
// 'blob:https://example.com/3f9c0a1e-...'
img.src = url
```

- 형식은 `blob:출처/uuid`입니다. 같은 출처에서만 쓸 수 있습니다.
- 호출할 때마다 새 URL이 만들어집니다. 같은 파일이어도 호출한 횟수만큼 생깁니다.
- 동기 함수라서 읽기를 기다릴 필요가 없습니다.
- 워커에서도 쓸 수 있지만 서비스 워커에서는 쓸 수 없습니다. Baseline 2015부터 널리 지원됩니다.

### revokeObjectURL()과 메모리

Object URL은 문서가 닫힐 때까지 Blob을 붙잡고 있어서 가비지 컬렉션 대상이 되지 않습니다. 더 쓰지 않으면 `URL.revokeObjectURL(url)`로 해제합니다.

```js
img.onload = () => URL.revokeObjectURL(img.src)
```

- 문서가 닫히면 자동으로 풀리지만, 오래 켜 두는 단일 페이지 앱에서는 수동 해제가 필요합니다.
- 이미지가 로드된 뒤의 해제는 안전합니다. 이미 시작한 다운로드도 해제 후에 이어집니다.
- 같은 URL을 나중에 다시 써야 하면(`src` 재할당, 다운로드 링크 클릭 전) 아직 해제하지 않습니다.
- 해제한 URL로는 더 이상 불러올 수 없습니다.
- 컴포넌트에서는 만든 URL을 기록해 두었다가 항목이 제거되거나 컴포넌트가 문서에서 빠질 때 해제합니다(자세히는 67편).

### data URL과 blob URL 비교

| 항목 | data URL | blob URL |
|------|----------|----------|
| 형태 | `data:image/png;base64,...` | `blob:https://출처/uuid` |
| 내용 | URL 문자열 안에 데이터가 들어 있음 | 메모리의 Blob을 가리키는 참조 |
| 크기 | Base64로 약 33퍼센트 커지고 문자열 메모리를 씀 | 복사 없음 |
| 만드는 법 | `FileReader.readAsDataURL()`(비동기) 또는 직접 조합 | `createObjectURL()`(동기) |
| 수명 | 문자열이 있는 동안 | 문서 수명, 해제가 필요 |
| 이동·보관 | 문자열이라서 저장·전송 가능 | 같은 출처·같은 문서에서만 의미 있음 |
| 최상위 탐색 | 브라우저가 차단 | 가능 |

- 큰 파일이나 많은 파일의 미리보기에는 blob URL이 가볍습니다.
- 데이터를 문자열로 저장·전송해야 하거나 CSS·작은 아이콘을 인라인할 때는 data URL을 씁니다.

## atob·btoa와 바이너리 Base64

Base64는 바이트를 64개 ASCII 문자로 표현하는 인코딩이며 크기가 약 4/3배(33퍼센트)로 늘어납니다. 브라우저에는 두 함수가 있습니다(Baseline 2015).

```js
btoa('Hello') // 'SGVsbG8='
atob('SGVsbG8=') // 'Hello'
```

- `btoa()`는 "바이너리 문자열"을 받습니다. 각 문자의 코드가 0–255(한 바이트)여야 하고 그 밖의 문자가 있으면 `InvalidCharacterError`입니다. 한글이나 이모지가 든 문자열은 바로 넣을 수 없습니다.
- `atob()`는 잘못된 Base64에 `InvalidCharacterError`를 던지고 바이너리 문자열을 돌려줍니다.

유니코드 문자열은 UTF-8 바이트로 바꾼 뒤 바이너리 문자열을 거쳐 인코딩합니다(MDN 방식).

```js
const toBinary = (bytes) =>
  Array.from(bytes, (b) => String.fromCodePoint(b)).join('')
const toBase64 = (bytes) => btoa(toBinary(bytes))
const fromBase64 = (b64) =>
  Uint8Array.from(atob(b64), (c) => c.codePointAt(0))

const b64 = toBase64(new TextEncoder().encode('한글 🙂'))
new TextDecoder().decode(fromBase64(b64)) // '한글 🙂'
```

- 이미 `Uint8Array`가 있으면 `toBase64()`와 `Uint8Array.fromBase64()`를 씁니다. 문자열 변환 단계가 없습니다. Baseline 2025(Chrome·Edge 140, Firefox 133, Safari 18.2)입니다.
- `toBase64({ alphabet: 'base64url', omitPadding: true })`는 URL에 넣을 수 있는 변형(`-`, `_`, 패딩 없음)을 만듭니다.
- File의 Base64가 필요하면 `readAsDataURL()`의 결과에서 쉼표 뒤를 취하거나, `bytes()`로 읽어 `toBase64()`를 씁니다.

```js
const b64 = (await file.bytes()).toBase64() // 지원 환경
```

- Base64는 암호화가 아닙니다. 누구나 되돌릴 수 있습니다.

## 파일 업로드 컴포넌트

업로드 컴포넌트는 파일을 받아 검증하고, 서버로 보내며, 항목별 상태를 보여 줍니다. 입력 경로는 파일 선택(`input`), 드롭, 붙여넣기이며 드롭과 붙여넣기는 49편에서 다룹니다. 모두 `File` 배열로 모아 같은 처리를 합니다.

항목마다 상태를 가진 모델을 둡니다.

```js
const item = {
  id: crypto.randomUUID(),
  file,
  status: 'queued', // uploading, done, error, canceled
  progress: 0,
  error: null,
}
```

- 검증은 사용자에게 빨리 알리는 UX 장치입니다. 개수, 크기(`file.size`), 형식(`file.type`과 확장자)을 확인하고 이유를 항목에 표시합니다. 서버 검증을 대체하지 못합니다.
- 중복은 이름·크기·`lastModified`를 조합한 키로 거릅니다.
- 전송은 `FormData`에 파일을 담아 보냅니다(폼 데이터는 11편, 요청은 36편). `fetch`에서 `Content-Type` 헤더를 직접 지정하지 않습니다. 브라우저가 멀티파트 경계(boundary)를 붙인 값을 넣어 줍니다.
- 동시 업로드 수를 제한하고 나머지는 큐에 둡니다.
- 항목마다 `AbortController`를 두어 개별 취소를 지원합니다(취소·재시도는 37편, 경쟁 상태는 39편).
- 접근성: 선택 버튼은 `label`과 연결된 입력창으로 키보드에서 열리게 하고, 상태 변화는 `aria-live` 영역으로 알립니다(자세히는 27편).
- 컴포넌트 안의 파일은 이벤트로 바깥에 알립니다(자세히는 25편). 폼에 참여시키는 컴포넌트는 `ElementInternals.setFormValue()`에 `FormData`를 넘겨 여러 파일을 제출합니다(자세히는 26편).

**흔한 실수:** 크기·형식 검증을 클라이언트에서만 하는 것, 큰 파일을 `FileReader.readAsDataURL()`로 읽은 문자열을 JSON에 담아 보내는 것(Base64로 33퍼센트 커지고 메모리를 씁니다)입니다. 파일은 `FormData`나 Blob 본문으로 그대로 보냅니다.

## 업로드 진행률과 분할 업로드

`fetch`는 업로드 진행률을 알려 주는 표준 방법이 없습니다. 진행률이 필요하면 `XMLHttpRequest`의 `upload` 객체를 씁니다(`fetch`의 요청 본문 스트리밍은 Baseline이 아니며 HTTP/2와 `duplex: 'half'`가 필요합니다. Chromium만 지원).

```js
function upload(formData, onProgress) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest()
    xhr.upload.onprogress = (e) => {
      if (e.lengthComputable) onProgress(e.loaded / e.total)
    }
    xhr.onload = () => {
      xhr.status < 300 ? resolve() : reject(xhr)
    }
    xhr.onerror = () => reject(xhr)
    xhr.open('POST', '/upload')
    xhr.send(formData)
  })
}
```

- `upload` 이벤트: `loadstart`, `progress`(`loaded`, `total`, `lengthComputable`), `load`, `error`, `abort`, `timeout`, `loadend`.
- `total`은 파일 크기가 아니라 요청 본문 전체 크기(멀티파트 머리글 포함)입니다. 퍼센트는 `loaded / total`로 계산합니다.
- 진행률 100퍼센트는 전송이 끝났다는 뜻일 뿐 서버 처리 완료가 아닙니다. 응답이 올 때까지 "처리 중" 상태를 둡니다.
- 취소는 `xhr.abort()`입니다. `AbortSignal`과 이으려면 `signal.addEventListener('abort', () => xhr.abort())`로 연결합니다.

큰 파일은 `slice()`로 잘라 조각 단위로 보냅니다. 한 조각이 실패해도 그 조각만 다시 보내면 되고, 서버가 받은 위치를 기억하면 중단된 업로드를 이어 갈 수 있습니다.

```js
const SIZE = 5 * 1024 * 1024
async function uploadChunks(file, id) {
  for (let off = 0; off < file.size; off += SIZE) {
    const chunk = file.slice(off, off + SIZE)
    const res = await fetch(`/upload/${id}`, {
      method: 'PUT',
      headers: { 'X-Upload-Offset': String(off) },
      body: chunk,
    })
    if (!res.ok) throw new Error(`chunk ${off} failed`)
  }
}
```

- 조각 크기와 헤더 이름, 병합 방식은 서버와 약속한 규약입니다. 위의 헤더는 예시입니다.
- 전체 진행률은 `(완료한 조각의 바이트 + 현재 조각의 loaded) / file.size`입니다.
- 조각별로 재시도하고(자세히는 37편) 순서대로 보낼지 병렬로 보낼지 정합니다. 병렬이면 서버가 오프셋으로 재조립해야 합니다.
- 업로드를 이어 가려면 먼저 서버에 "어디까지 받았는가"를 묻고 그 위치부터 보냅니다.
- 조각이 손상되지 않았는지 해시로 확인할 수 있습니다(자세히는 64편).

## 파일 Preview

미리보기는 업로드 전에 선택한 파일을 화면에 보여 주는 일입니다. 파일 종류별로 수단이 다릅니다.

| 종류 | 수단 |
|------|------|
| 이미지 | `img.src = blob URL` |
| 동영상·오디오 | `video.src`, `audio.src`에 blob URL(자세히는 50편) |
| PDF | `iframe`이나 `object`의 주소에 blob URL |
| 텍스트·CSV·JSON | `file.text()`. 큰 파일은 `slice(0, N)`으로 앞부분만 |
| 이미지 썸네일 | `createImageBitmap(file)`로 디코딩해 캔버스에 그림(자세히는 52편) |

- 종류 판별은 `file.type.startsWith('image/')` 같은 값으로 하되, 비어 있을 수 있으므로 확장자를 보조로 씁니다.
- 이미지는 blob URL이 data URL보다 메모리와 속도에서 유리합니다.
- SVG는 `img`로 표시하면 스크립트가 실행되지 않습니다. 텍스트로 읽어 `innerHTML`에 넣으면 XSS가 되므로 그렇게 하지 않습니다(자세히는 63편).
- 미리보기 URL은 만든 쪽이 해제합니다. 파일 객체를 키로 보관하면 중복 생성도 막습니다.

```js
class PreviewStore {
  #urls = new Map()
  urlFor(file) {
    if (!this.#urls.has(file)) {
      this.#urls.set(file, URL.createObjectURL(file))
    }
    return this.#urls.get(file)
  }
  release(file) {
    URL.revokeObjectURL(this.#urls.get(file))
    this.#urls.delete(file)
  }
}
```

- 항목을 지울 때, 파일을 교체할 때, 컴포넌트가 문서에서 빠질 때(`disconnectedCallback`) `release()`를 호출합니다(자세히는 18편).
- 큰 이미지를 목록 여러 개로 한꺼번에 디코딩하면 메모리를 많이 씁니다. 화면에 보이는 항목만 만드는 지연 처리를 합니다(자세히는 43편).

## 다운로드 구현

다운로드는 브라우저가 URL의 내용을 화면에 표시하지 않고 파일로 저장하게 하는 일입니다. 서버에 있는 파일이면 링크를, 코드로 만든 데이터면 Blob URL을 씁니다.

```js
function download(blob, name) {
  const url = URL.createObjectURL(blob)
  const a = document.createElement('a')
  a.href = url
  a.download = name
  document.body.append(a)
  a.click()
  a.remove()
  URL.revokeObjectURL(url)
}
```

- 생성한 CSV·JSON·이미지는 `Blob`으로 만들어 위 함수로 저장합니다.
- 인증 헤더가 필요한 API의 파일은 `fetch`로 받아 `response.blob()`을 같은 방식으로 저장합니다. 이 경우 본문 전체가 메모리에 올라오므로 아주 큰 파일에는 맞지 않습니다. 쿠키 인증이면 링크로 직접 내려받게 하거나, 스트림을 파일에 직접 쓰는 방법(아래 File System Access, 자세히는 38편)을 씁니다.
- 저장 위치와 확인 대화상자는 브라우저와 사용자 설정이 정합니다. 페이지가 저장 완료나 취소를 알 수 있는 표준 이벤트는 없습니다.

### a 요소 download 속성과 Content-Disposition

`a`의 `download` 속성은 링크를 따라가는 대신 저장하게 하고, 값은 제안 파일 이름입니다. Baseline 2019부터 널리 지원됩니다.

```html
<a href="/report.pdf" download="2026-보고서.pdf">내려받기</a>
```

- 같은 출처 URL에서만 동작하고 `blob:`, `data:` URL은 예외로 허용됩니다. 다른 출처 URL에서는 속성이 조용히 무시됩니다.
- 값이 없으면 `Content-Disposition` 헤더, URL 마지막 경로, MIME 유형 순으로 이름을 정합니다.
- 이름 안의 `/`와 `\`는 `_`로 바뀌고 파일 시스템에 맞지 않는 문자는 브라우저가 고칩니다.

서버는 응답 헤더 `Content-Disposition`으로 표시와 저장을 정합니다.

```http
Content-Disposition: attachment; filename="report.pdf"
Content-Disposition: attachment; filename*=UTF-8''%EA%B0%80
```

| 값 | 의미 |
|----|------|
| `inline` | 브라우저 안에서 표시(기본) |
| `attachment` | 저장 대화상자로 내려받게 함 |
| `filename` | 제안 이름. 비 ASCII 문자는 쓰지 않고 퍼센트 인코딩도 피함 |
| `filename*` | UTF-8 퍼센트 인코딩 이름. 한글 파일명은 이쪽 |

- `filename*`와 `filename`을 함께 주면 `filename*`가 우선하므로 호환을 위해 둘 다 둡니다.
- 응답에 `filename`이 있으면 `download` 속성의 이름보다 우선합니다. `inline`이면 Chrome과 Firefox는 `download` 속성을 우선합니다.
- 요청 본문(멀티파트 업로드)의 `Content-Disposition: form-data`는 같은 헤더 이름을 쓰지만 `name`과 `filename`만 쓰며 `filename*`는 허용되지 않습니다.
- 다른 출처 응답의 `Content-Disposition`을 `fetch`로 읽으려면 서버가 `Access-Control-Expose-Headers`로 노출해야 합니다(자세히는 62편).

## File System Access API 개요

File System Access API는 사용자가 허락한 로컬 파일과 폴더를 선택창으로 열고, 같은 파일에 다시 저장할 수 있게 하는 API입니다. 일반 `input`과 `a download`는 읽기와 "다른 이름으로 내려받기"만 되지만, 이 API는 열었던 파일에 덮어쓸 수 있습니다.

```js
const [handle] = await window.showOpenFilePicker({
  types: [{
    description: 'Text',
    accept: { 'text/plain': ['.txt'] },
  }],
})
const file = await handle.getFile()   // 읽기
const w = await handle.createWritable()
await w.write('새 내용')              // 쓰기
await w.close()                       // 닫아야 반영됨
```

| 진입점 | 결과 |
|--------|------|
| `showOpenFilePicker(options)` | `FileSystemFileHandle`의 배열. `multiple`, `types`, `excludeAcceptAllOption`, `startIn` 옵션 |
| `showSaveFilePicker(options)` | 저장 위치를 고른 `FileSystemFileHandle` |
| `showDirectoryPicker()` | `FileSystemDirectoryHandle`. 폴더 안의 항목을 순회 |

- 핸들 객체는 `FileSystemFileHandle`(`getFile()`, `createWritable()`)과 `FileSystemDirectoryHandle`(`getFileHandle()`, `getDirectoryHandle()`, `entries()`, `removeEntry()`)이며 둘 다 `FileSystemHandle`을 상속합니다.
- 쓰기는 `createWritable()`이 돌려주는 `FileSystemWritableFileStream`으로 합니다. `write()`에 문자열, Blob, 버퍼나 `{ type: 'write', position, data }` 같은 명령을 주고 `close()`로 마칩니다. 스트림이라서 `pipeTo()`로 큰 데이터를 바로 쓸 수 있습니다(자세히는 38편).
- 선택창은 보안 컨텍스트(HTTPS)와 사용자 조작(버튼 클릭 등)이 있어야 열립니다. 사용자가 창을 닫으면 `AbortError`로 거부되므로 이를 정상 흐름으로 처리합니다.
- 핸들은 구조화된 복제가 되어 IndexedDB에 저장해 다음 방문에 재사용할 수 있습니다. 이때 권한이 풀려 있을 수 있어 `queryPermission()`·`requestPermission()`으로 다시 확인합니다(자세히는 41편).
- 브라우저 샌드박스 안의 보이지 않는 저장소인 Origin Private File System(`navigator.storage.getDirectory()`)은 같은 핸들 인터페이스를 쓰지만 선택창이 필요 없습니다. 이쪽은 Baseline 2023입니다(자세히는 42편).

### 지원 상태

선택창 함수와 권한 메서드는 Baseline이 아니며 Chromium 계열만 지원합니다(web-features 3.40.1 기준).

| 기능 | 지원 |
|------|------|
| `showOpenFilePicker`, `showSaveFilePicker`, `showDirectoryPicker` | 데스크톱 Chrome·Edge 86, Android Chrome 132. Firefox·Safari 미지원 |
| `queryPermission`, `requestPermission` | Chrome·Edge 86. Firefox·Safari 미지원 |
| `createWritable`, `FileSystemWritableFileStream` | Baseline 2025 (Chrome·Edge 86, Firefox 111, Safari 26) |
| 핸들 인터페이스와 OPFS | Baseline 2023 |

- 점진적 향상으로 씁니다. `'showOpenFilePicker' in window`로 감지하고, 없으면 열기는 `input type="file"`, 저장은 Blob URL과 `a download`로 대체합니다.
- 대체 경로에서도 같은 컴포넌트 인터페이스를 유지합니다. 호출자는 파일을 받고 결과를 저장한다는 점만 알면 됩니다.
- 사용자 허락 없이 임의의 경로를 열 수 없고 시스템 폴더처럼 민감한 위치는 선택이 거부될 수 있습니다.

## 핵심 정리

- Blob은 변경 불가능한 바이트 덩어리이고 File은 이름과 수정 시각을 더한 Blob이며, `slice()`는 항상 Blob을 돌려줍니다.
- 읽기는 `text()`·`arrayBuffer()`·`bytes()`·`stream()` Promise 메서드가 기본이고, FileReader는 data URL과 진행 이벤트가 필요할 때 씁니다. 인코딩이 UTF-8이 아니면 `TextDecoder`를 씁니다.
- Object URL은 가볍지만 `revokeObjectURL()`로 직접 해제해야 하고, data URL은 Base64로 33퍼센트 커지지만 문자열로 보관·전송할 수 있습니다.
- `btoa()`는 Latin-1 범위만 받으므로 유니코드는 `TextEncoder`를 거치거나 `Uint8Array.toBase64()`를 씁니다.
- 업로드는 클라이언트 검증과 서버 검증을 모두 하고, 진행률은 XHR의 `upload` 이벤트, 큰 파일은 `slice()` 분할로 처리합니다.
- 다운로드는 Blob URL과 `download`, 서버의 `Content-Disposition`을 쓰고, File System Access API의 선택창은 Chromium 전용이라 대체 경로가 필요합니다.

## IndexedDB

IndexedDB는 브라우저가 origin 단위로 제공하는 트랜잭션 기반 객체 데이터베이스입니다. 구조화된 값을 키와 함께 저장하고, 인덱스로 조회하며, 쿠키·Web Storage(자세히는 40편)와 달리 용량이 크고 비동기로 동작합니다. Worker에서도 쓸 수 있습니다.

| 항목 | IndexedDB |
|------|-----------|
| 저장 단위 | 오브젝트 스토어 안의 레코드(키 + 값) |
| 값 | 구조화된 복제가 가능한 값(Blob·File 포함) |
| 동작 방식 | 비동기. 요청 객체에 이벤트로 결과가 도착 |
| 범위 | origin 단위. 다른 origin은 접근할 수 없음 |
| 일관성 | 트랜잭션 단위로 전부 반영되거나 전부 취소 |

API는 Promise가 아니라 `IDBRequest` 객체와 이벤트로 설계되었습니다. 기본 흐름은 `indexedDB.open()`으로 연결을 열고, 연결에서 트랜잭션을 만들고, 트랜잭션에서 스토어를 꺼내 요청을 보내는 것입니다.

```js
const req = indexedDB.open('app-db', 1)
req.onsuccess = () => {
  const db = req.result // IDBDatabase 연결
  console.log(db.name, db.version) // app-db 1
}
req.onerror = () => console.error(req.error)
```

`indexedDB.databases()`는 현재 origin의 데이터베이스 이름과 버전 배열을 Promise로 돌려줍니다. 배열 순서는 정해져 있지 않고 Baseline 2024입니다. `indexedDB.deleteDatabase(name)`은 데이터베이스를 지웁니다.

## 데이터베이스 버전과 upgradeneeded

데이터베이스는 이름과 정수 버전을 가집니다. `open(name, version)`에서 요청한 버전이 저장된 버전보다 높거나 데이터베이스가 새로 만들어지면 `upgradeneeded` 이벤트가 발생합니다. 스키마(스토어·인덱스 생성과 삭제)는 이 이벤트 안에서만 바꿀 수 있습니다.

```js
const req = indexedDB.open('app-db', 2)
req.onupgradeneeded = (e) => {
  const db = req.result
  if (e.oldVersion < 1) db.createObjectStore('users')
  if (e.oldVersion < 2) db.createObjectStore('logs')
}
```

- 버전은 정수입니다. 소수는 반올림되므로 2.1과 2.4는 같은 버전 2입니다.
- 버전을 생략하고 열면 이미 있는 데이터베이스는 현재 버전으로 열리고, 없으면 버전 1로 만들어집니다.
- 저장된 버전보다 낮은 버전으로 열면 `VersionError`로 요청이 실패합니다.
- `e.oldVersion`으로 어디서부터 올라왔는지 알 수 있어서 버전 단계별 마이그레이션을 `if`로 이어 씁니다. 새 데이터베이스는 `oldVersion`이 0입니다.
- 이벤트가 끝나면 `versionchange` 트랜잭션이 완료된 뒤 `success`가 발생합니다. `upgradeneeded` 안에서 `req.transaction`으로 그 트랜잭션에 접근해 기존 레코드를 읽고 고칠 수 있습니다.

**흔한 실수:** 이미 배포한 버전의 `upgradeneeded` 코드를 고치는 것입니다. 이미 그 버전이 된 사용자는 이벤트가 다시 발생하지 않으므로 변경을 반영하려면 버전을 올려야 합니다.

## 오브젝트 스토어·keyPath·autoIncrement

오브젝트 스토어는 레코드를 담는 단위로, 관계형 데이터베이스의 테이블에 해당합니다. `createObjectStore(name, options)`로 만들고 키를 어떻게 정할지 `keyPath`와 `autoIncrement`가 결정합니다.

| keyPath | autoIncrement | 키가 정해지는 방식 | 값 |
|---------|---------------|--------------------|----|
| 없음 | 없음 | 쓸 때마다 키를 직접 인수로 전달 | 아무 값 |
| 있음 | 없음 | 값의 해당 프로퍼티가 키 | 객체만 |
| 없음 | 있음 | 키 생성기가 자동 생성 | 아무 값 |
| 있음 | 있음 | 프로퍼티가 있으면 그 값, 없으면 자동 생성 | 객체만 |

```js
db.createObjectStore('users', { keyPath: 'id' })
db.createObjectStore('notes', { autoIncrement: true })
const s = db.createObjectStore('todos', {
  keyPath: 'id',
  autoIncrement: true,
})
```

- 키 생성기는 1에서 시작해 1씩 증가하고, 레코드를 지우거나 스토어를 비워도 줄어들지 않습니다.
- 키는 숫자, 날짜, 문자열, 바이너리, 배열만 될 수 있고 크기 순서는 이 순서입니다. 불리언, `null`, 일반 객체는 키가 될 수 없고 쓰면 `DataError`입니다.
- `keyPath`는 `'user.id'`처럼 점으로 중첩 경로를 쓰거나 `['a', 'b']`처럼 배열로 복합 키를 만들 수 있습니다.
- 레코드는 `add(value, key?)`와 `put(value, key?)`로 쓰고 `get(key)`, `delete(key)`, `clear()`로 읽고 지웁니다. `add`는 같은 키가 있으면 `ConstraintError`로 실패하고 `put`은 덮어씁니다.

## 인덱스와 unique·multiEntry

인덱스는 값의 다른 프로퍼티를 키로 삼아 레코드를 조회하게 해 주는 보조 구조입니다. `createIndex(name, keyPath, options)`는 스키마 변경이므로 `upgradeneeded` 안에서만 호출합니다. 값이 객체인 스토어에만 만들 수 있습니다.

```js
const store = db.createObjectStore('users', {
  keyPath: 'id',
})
store.createIndex('by_email', 'email', { unique: true })
store.createIndex('by_tag', 'tags', { multiEntry: true })
store.createIndex('by_name_age', ['name', 'age'])
```

| 옵션 | 효과 |
|------|------|
| `unique: true` | 같은 인덱스 키를 가진 레코드를 둘 이상 저장하지 못함. 어기면 `ConstraintError` |
| `multiEntry: true` | 키 경로 값이 배열이면 배열 자체가 아니라 원소마다 인덱스 항목을 만듦 |
| 배열 keyPath | 여러 프로퍼티를 묶은 복합 인덱스 |

- 인덱스 조회는 스토어에서 `store.index('by_tag')`로 꺼내 `get`, `getAll`, `openCursor` 등을 호출합니다.
- 같은 인덱스 키를 가진 레코드가 여럿이면 `get`은 그중 기본키가 가장 작은 하나를 돌려줍니다.
- 키 경로에 해당하는 값이 없거나 유효한 키가 아닌 레코드는 인덱스에 들어가지 않습니다.
- `multiEntry` 인덱스로 `get('js')`를 하면 `tags` 배열에 `'js'`가 들어 있는 레코드를 찾습니다. 복합 인덱스는 `get(['Kim', 20])`처럼 배열로 조회합니다.

## 트랜잭션 모드와 자동 커밋 수명

모든 읽기·쓰기는 트랜잭션 안에서 이루어집니다. `db.transaction(storeNames, mode)`로 만들고 접근할 스토어와 모드를 미리 정합니다.

| 모드 | 용도 | 동시성 |
|------|------|--------|
| `readonly` (기본) | 읽기 | 범위가 겹쳐도 동시에 여러 개 실행 |
| `readwrite` | 읽기와 쓰기 | 같은 스토어에서는 한 번에 하나만 활성 |
| `versionchange` | 스키마 변경 | `open()`이 버전 올릴 때 자동 생성. 직접 만들 수 없음 |

```js
const tx = db.transaction(['users', 'logs'], 'readwrite')
tx.objectStore('users').put({ id: 1, name: 'Kim' })
tx.objectStore('logs').add({ msg: 'saved' })
tx.oncomplete = () => console.log('모두 반영됨')
tx.onabort = () => console.log('모두 취소됨', tx.error)
```

- 스토어 이름 배열이 비어 있으면 `InvalidAccessError`, 없는 스토어를 지정하면 `NotFoundError`, 모드가 잘못되면 `TypeError`입니다. 읽기 전용 트랜잭션에서 쓰면 `ReadOnlyError`입니다.
- 트랜잭션은 명시적으로 닫지 않습니다. 이벤트 루프로 돌아간 시점에 대기 중인 요청이 하나도 없으면 자동으로 커밋됩니다. 이 때문에 결과 이벤트를 받는 콜백 안에서는 요청을 더 보낼 수 있습니다.
- 트랜잭션이 활성인 구간은 요청을 만든 코드 실행 중과 요청 결과 이벤트가 디스패치되는 동안입니다. 이 구간이 끝나고 새 요청이 없으면 비활성이 되고, 비활성 트랜잭션에 요청을 보내면 `TransactionInactiveError`입니다.
- 한 트랜잭션 안의 요청은 모두 성공해야 반영됩니다. 요청 하나가 실패하고 오류 이벤트에서 `preventDefault()`를 호출하지 않으면 트랜잭션 전체가 취소됩니다. `tx.abort()`로 직접 취소할 수도 있습니다.
- `tx.commit()`은 대기 중인 요청의 이벤트를 기다리지 않고 커밋을 바로 시작합니다. 필수는 아니며 비활성 트랜잭션에서 호출하면 `InvalidStateError`입니다. 2021년 9월부터 브라우저 전반에서 지원됩니다.
- 완료 여부는 `complete`와 `abort` 이벤트로 판단합니다. 요청의 `success`는 아직 커밋되기 전일 수 있습니다.

**흔한 실수:** 트랜잭션 도중에 `fetch`나 타이머 같은 IndexedDB 밖의 비동기 작업을 기다리는 것입니다. 기다리는 동안 트랜잭션이 끝나 이후 요청이 `TransactionInactiveError`가 됩니다. 필요한 값을 먼저 가져온 뒤 트랜잭션을 만들고, 쓰기는 하나의 트랜잭션에 모읍니다.

## durability 옵션

`transaction()`의 세 번째 인수 `{ durability }`는 커밋을 언제 완료로 볼지 정합니다.

| 값 | 의미 |
|----|------|
| `default` | 브라우저의 기본 동작을 따름(생략 시 기본값) |
| `strict` | 변경이 영구 저장소에 기록된 것을 확인한 뒤 커밋으로 간주. 성능보다 데이터 손실 방지가 중요할 때 |
| `relaxed` | 변경이 운영체제에 전달되면 커밋으로 간주. 더 빠르며 캐시 같은 일시 데이터에 적합 |

```js
const tx = db.transaction('cache', 'readwrite', {
  durability: 'relaxed',
})
```

- `relaxed`는 `complete` 이벤트 뒤에 운영체제가 비정상 종료되면 마지막 변경이 사라질 수 있다는 뜻입니다.
- Firefox 40부터 `default`가 이미 완화되어 있어서 `complete`가 디스크 기록 완료를 보장하지 않습니다.
- Firefox 전용 비표준 모드 `readwriteflush`는 디스크에 기록한 뒤 `complete`를 발생시킵니다. 표준 코드에서는 쓰지 않고 `strict`를 씁니다.

## IDBKeyRange와 커서

`IDBKeyRange`는 조회할 키의 범위를 나타내는 객체입니다. 스토어와 인덱스의 `get`, `getAll`, `count`, `openCursor`가 키 하나 대신 범위를 받을 수 있습니다.

| 메서드 | 범위 |
|--------|------|
| `only(v)` | 키가 v인 것 하나 |
| `lowerBound(v)` / `lowerBound(v, true)` | v 이상 / v 초과 |
| `upperBound(v)` / `upperBound(v, true)` | v 이하 / v 미만 |
| `bound(a, b, lowerOpen, upperOpen)` | a부터 b까지. 열린 끝 여부는 불리언 |
| `range.includes(key)` | 키가 범위에 속하는지 불리언으로 반환 |

```js
const range = IDBKeyRange.bound('A', 'F', false, true)
// 'A' 이상 'F' 미만
const req = store.openCursor(range, 'prev')
```

커서는 레코드를 하나씩 순회합니다. 결과 이벤트마다 커서 한 위치가 전달되고, 끝에 도달하면 `result`가 `null`입니다.

```js
store.openCursor().onsuccess = (e) => {
  const cursor = e.target.result
  if (!cursor) return // 끝
  console.log(cursor.key, cursor.value)
  cursor.continue()
}
```

- `continue()`는 다음 레코드로, `continue(key)`는 그 키 이후로 건너뜁니다. `advance(n)`은 n개를 건너뜁니다.
- 방향은 두 번째 인수로 정합니다: `next`(기본), `prev`, 인덱스에서 같은 키를 한 번만 방문하는 `nextunique`, `prevunique`.
- 인덱스에서 `openCursor()`는 값 전체를, `openKeyCursor()`는 기본키만 돌려줍니다. 인덱스 커서에는 `key`(인덱스 키)와 `primaryKey`(기본키)가 따로 있습니다.
- `cursor.update(newValue)`와 `cursor.delete()`로 현재 위치의 레코드를 바꾸거나 지웁니다. `readwrite` 트랜잭션에서만 됩니다.
- 시작 위치가 잘못된 범위를 넘기면 `DataError`입니다. 예를 들어 `bound`에서 아래쪽 끝이 위쪽 끝보다 큰 경우입니다.

## getAll·getAllKeys·count

레코드 여러 개를 한 번에 읽을 때는 커서보다 `getAll`이 간단하고 빠릅니다. 커서는 값을 지연 생성하는 반면 `getAll`은 결과를 한 번에 만들기 때문입니다.

```js
const all = store.getAll()                    // 전체 값
const some = store.getAll(range, 10)          // 범위 + 최대 10개
const keys = store.getAllKeys()               // 키만
const total = store.count()                   // 레코드 수
const byTag = store.index('by_tag').getAll('js')
```

| 메서드 | 결과(`request.result`) |
|--------|------------------------|
| `getAll(query?, count?)` | 일치하는 값의 배열 |
| `getAllKeys(query?, count?)` | 일치하는 기본키의 배열 |
| `count(query?)` | 일치하는 레코드 수 |

- `query`는 키 하나 또는 `IDBKeyRange`이고 생략하면 전체입니다. `count`는 0부터 2의 32제곱 마이너스 1 사이여야 하며 벗어나면 `TypeError`입니다.
- `getAll({ query, count, direction })`처럼 옵션 객체도 받으며 `direction`으로 정렬 방향을 정합니다. `getAll`은 Baseline 2020부터 널리 지원됩니다.
- 스토어와 인덱스 양쪽에 있습니다. 인덱스의 `getAllKeys`는 인덱스 키가 아니라 기본키를 돌려줍니다.
- 전체를 한 번에 메모리로 올리므로 레코드가 매우 많으면 `count`로 나눠 읽거나 커서를 씁니다.

## 요청 이벤트를 Promise로 감싸기

`IDBRequest`는 `then`이 없어서 `await`할 수 없습니다. 요청의 `success`와 `error`를 Promise에 연결하는 작은 함수를 만들면 됩니다.

```js
const wrap = (req) =>
  new Promise((resolve, reject) => {
    req.onsuccess = () => resolve(req.result)
    req.onerror = () => reject(req.error)
  })

const user = await wrap(store.get(1))
```

연결과 트랜잭션도 같은 방식으로 감쌉니다. 트랜잭션은 `complete`에서 resolve하고 `error`와 `abort`에서 reject합니다.

```js
const done = (tx) =>
  new Promise((resolve, reject) => {
    tx.oncomplete = () => resolve()
    tx.onerror = () => reject(tx.error)
    tx.onabort = () => reject(tx.error)
  })
```

- 한 트랜잭션 안에서 `await wrap(...)`으로 요청을 이어 보내도 트랜잭션은 유지됩니다. 요청 이벤트의 콜백과 이어지는 마이크로태스크가 활성 구간에서 실행되기 때문입니다. 하지만 IndexedDB와 관계없는 Promise(`fetch`, `setTimeout` 래퍼)를 사이에 `await`하면 트랜잭션이 끝납니다.
- 쓰기의 성공 여부는 마지막 요청이 아니라 `done(tx)`로 확인합니다. 요청이 성공해도 커밋 중에 실패할 수 있습니다(할당량 초과 등).
- 직접 만들지 않고 Promise 기반 래퍼 라이브러리를 쓰는 경우도 많지만, 위 두 함수가 핵심입니다.

## versionchange·blocked와 다중 탭 업그레이드

같은 origin의 여러 탭이 같은 데이터베이스를 열어 둘 수 있습니다. 새 버전 탭이 업그레이드하려면 구버전 연결이 모두 닫혀야 해서 두 이벤트가 쓰입니다.

| 이벤트 | 발생 대상 | 의미 |
|--------|-----------|------|
| `versionchange` | 이미 열려 있는 `IDBDatabase` 연결 | 다른 곳에서 버전 변경이나 삭제를 요청함. 닫을 기회 |
| `blocked` | 업그레이드를 요청한 `IDBOpenDBRequest` | 열린 연결이 남아 있어 업그레이드가 대기 중 |
| `close` | `IDBDatabase` | 브라우저가 연결을 강제로 닫음(디스크 접근 손실 등) |

```js
const req = indexedDB.open('app-db', 3)
req.onblocked = () => alert('다른 탭을 닫아 주세요')
req.onsuccess = () => {
  const db = req.result
  db.onversionchange = () => {
    db.close() // 업그레이드가 진행되도록 양보
    location.reload()
  }
}
```

- `versionchange` 이벤트의 `oldVersion`과 `newVersion`으로 변경 내용을 알 수 있고, `deleteDatabase`일 때 `newVersion`은 `null`입니다.
- 연결을 닫지 않으면 업그레이드는 `blocked` 상태로 대기하고, 연결이 모두 닫히면 이어서 `upgradeneeded`가 발생합니다.
- 모든 연결에 `versionchange` 핸들러를 달아 `db.close()`를 호출하는 것이 다중 탭 앱의 기본 규칙입니다. 닫은 뒤에는 새 스키마를 쓰도록 페이지를 새로 고치거나 다시 엽니다.
- `db.close()`는 열린 트랜잭션이 끝나기를 기다린 뒤 연결을 닫고, 닫은 연결에서 `transaction()`을 호출하면 `InvalidStateError`입니다.
- 브라우저 종료나 디스크 접근 손실로 연결이 끊기면 진행 중인 트랜잭션은 `AbortError`로 취소됩니다. `unload`에 저장 로직을 걸어도 완료를 보장하지 못합니다.

## 저장 가능한 값(구조화된 복제)

저장하는 값은 구조화된 복제 알고리즘으로 복사됩니다. `postMessage`와 `structuredClone`이 쓰는 것과 같은 규칙입니다.

- 저장할 수 있는 값: 원시 값(심벌 제외), 일반 객체, 배열, `Date`, `RegExp`, `Map`, `Set`, `ArrayBuffer`와 타입 배열, `Blob`, `File`, `ImageData`, `CryptoKey` 등.
- 저장할 수 없는 값: 함수, DOM 노드, 심벌. 저장하려 하면 `DataCloneError`입니다.
- 클래스 인스턴스는 일반 객체가 됩니다. 프로토타입 체인, getter와 setter, private 필드는 복제되지 않으므로 읽을 때 메서드가 없습니다.
- 복제는 요청을 보내는 시점에 이루어지므로 이후에 원본 객체를 바꿔도 저장된 값은 그대로입니다.
- `Blob`과 `File`을 직접 저장할 수 있어서 이미지·파일 캐시에 쓰입니다(자세히는 48편).

```js
class Pt { constructor() { this.x = 1 } move() {} }
store.put({ id: 1, p: new Pt() }) // 가능하지만
// 읽으면 p는 { x: 1 } 일반 객체. p.move는 undefined
store.put({ id: 2, run() {} })    // DataCloneError
```

**흔한 실수:** 객체를 그대로 저장하고 읽어서 메서드를 호출하는 것입니다. 저장 전에 일반 데이터로 바꾸고, 읽은 뒤 클래스로 다시 만드는 변환 함수를 둡니다.

## getAllRecords()(미Baseline)

`getAllRecords()`는 `getAll()`과 `getAllKeys()`를 합친 새 메서드입니다. 스토어와 인덱스에서 `IDBRecord` 배열을 돌려주고, 각 레코드는 `key`, `primaryKey`, `value`를 가집니다. 값과 기본키를 한 번에 얻어 커서 순회보다 빠를 수 있습니다.

```js
const req = store.getAllRecords({
  query: IDBKeyRange.lowerBound(100, true),
  count: 50,
  direction: 'prev',
})
req.onsuccess = () => console.log(req.result[0].primaryKey)
```

- 인수는 옵션 객체 하나이며 `query`, `count`, `direction`을 받습니다. `count`가 범위를 벗어나면 `TypeError`입니다.
- Baseline이 아니므로 모든 브라우저에서 쓸 수 있다고 가정하면 안 됩니다. `typeof store.getAllRecords === 'function'`으로 확인하고, 없으면 `getAll`과 `getAllKeys`를 같은 범위로 보내 합치거나 커서를 씁니다.

## 오류와 할당량 초과 처리

요청 하나가 실패하면 요청의 `error` 이벤트가 발생하고, 이벤트는 트랜잭션과 데이터베이스로 버블링합니다. 처리하지 않으면 트랜잭션이 취소됩니다.

| 오류 | 원인 |
|------|------|
| `ConstraintError` | `add`의 중복 키, `unique` 인덱스 위반 |
| `DataError` | 유효하지 않은 키나 키 범위, 키 경로로 키를 만들 수 없음 |
| `DataCloneError` | 구조화된 복제를 할 수 없는 값 |
| `TransactionInactiveError` | 비활성이거나 이미 끝난 트랜잭션에 요청 |
| `ReadOnlyError` | `readonly` 트랜잭션에서 쓰기 |
| `VersionError` | 저장된 버전보다 낮은 버전으로 열기 |
| `QuotaExceededError` | 저장 공간이 부족해 커밋하지 못함 |
| `AbortError` | 브라우저 종료·연결 손실로 트랜잭션이 취소됨 |

```js
db.onerror = (e) => {
  console.error('요청 실패', e.target.error?.name)
}
tx.onabort = () => {
  if (tx.error?.name === 'QuotaExceededError') {
    // 공간 확보 후 재시도 또는 사용자에게 안내
  }
}
```

- 요청 오류 이벤트에서 `e.preventDefault()`를 호출하면 트랜잭션이 취소되지 않고 계속 진행됩니다. 호출하지 않으면 요청 하나의 실패가 트랜잭션 전체의 취소로 이어집니다.
- 저장 공간이 모자라 커밋하지 못하면 명세에 따라 트랜잭션의 변경은 하나도 기록되지 않고 취소되며 `tx.error`가 `QuotaExceededError`입니다. 이 오류는 `complete`가 아니라 `abort` 쪽에서 확인합니다.
- 할당량 초과에 대비하려면 쓰기를 작은 트랜잭션으로 나누고, 오래된 데이터를 지운 뒤 재시도하는 경로를 둡니다. 사용량 조회와 영속 저장 요청은 42편을 참고합니다.
- 서드파티 iframe은 브라우저가 서드파티 저장을 막으면 IndexedDB에 접근할 수 없습니다.

## 핵심 정리

- IndexedDB는 origin 단위의 비동기 트랜잭션 객체 저장소이며, 스키마는 `upgradeneeded` 안에서 버전을 올려야만 바꿀 수 있습니다.
- 스토어의 키는 `keyPath`와 `autoIncrement` 조합으로 정해지고, 인덱스는 `unique`와 `multiEntry`로 제약과 배열 펼치기를 지정합니다.
- 트랜잭션은 요청이 더 없으면 자동 커밋되고 비활성 구간에 요청하면 `TransactionInactiveError`입니다. 완료는 `complete`와 `abort`로 확인합니다.
- 조회는 키 범위를 쓰는 `get`, `getAll`, `getAllKeys`, `count`, 커서로 하며 `getAllRecords()`는 미Baseline입니다.
- 다중 탭에서는 `versionchange` 핸들러에서 `db.close()`를 호출해야 `blocked`가 풀리고, 값은 구조화된 복제로 저장되어 함수와 DOM 노드는 저장되지 않습니다.
- 할당량 초과는 커밋 실패인 `QuotaExceededError`로 나타나며 트랜잭션 전체가 취소됩니다.

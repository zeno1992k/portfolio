## 판정과 첫 의심

채점 결과 이름과 세분은 채점기마다 다릅니다. 이 문서의 약어는 널리 쓰이는 관례입니다. 판정은 원인이 아니라 증상이므로, 먼저 어느 쪽을 의심할지 정합니다.

| 판정 | 뜻 | 먼저 의심할 것 |
|------|----|----------------|
| WA | 출력이 정답과 다름 | 해석, 경계, 초기화, 출력 형식, 알고리즘 |
| TLE | 시간 제한 초과 | 복잡도, 무한루프, 느린 연산 |
| MLE | 메모리 제한 초과 | 자료 크기, 복사본, 상태 수 |
| RE | 실행 중 비정상 종료 | 예외, 재귀 깊이, 범위 밖 접근 |

- 같은 원인이 다른 판정으로 나타납니다. 무한루프는 보통 TLE지만 반복마다 값을 쌓으면 MLE가 됩니다.
- 판정만 알려 주고 입력은 알려 주지 않는 경우가 많습니다. 증상에서 후보를 만들고, 직접 만든 입력으로 재현합니다(자세히는 79편, 80편).

## 무한루프 탐지

무한루프는 종료 조건이 영원히 참(또는 거짓)으로 남아 반복이 끝나지 않는 상태입니다. 출력도 없이 시간만 흐르다 TLE가 됩니다.

대표 원인은 네 가지입니다.

- 갱신 누락: 반복 변수를 증가시키지 않거나 반대 방향으로 갱신합니다.
- 제자리 갱신: 이분 탐색에서 `lo = mid`로 두면 `mid`가 `lo`와 같을 때 범위가 줄지 않습니다(자세히는 28편).
- 도달하지 못하는 조건: 부동소수점을 `===`나 `!==`로 비교합니다.
- 방문 처리 누락: 그래프나 격자 탐색에서 사이클을 다시 돌면 큐나 스택이 끝나지 않습니다(자세히는 36편, 38편).

```js
// 0.1씩 더하면 정확히 1이 되는 순간이 없다
for (let x = 0; x !== 1; x += 0.1) {
  // x: 0.1, 0.2, 0.30000000000000004, ...
  // 0.9999999999999999, 1.0999999999999999, ... (무한)
}
```

```js
while (lo < hi) {
  const mid = (lo + hi) >> 1
  if (a[mid] < x) lo = mid      // ❌ lo=0, hi=1이면 mid=0
  else hi = mid
}
// ✅ lo = mid + 1
```

탐지는 반복 횟수에 상한을 두는 가드로 합니다. 상한은 문제의 최대 연산 횟수보다 넉넉하게 잡습니다.

```js
let guard = 0
while (cond) {
  if (++guard > 1e7) {
    console.error('loop guard', { lo, hi, mid })
    throw new Error('infinite loop')
  }
  // ...
}
```

- 가드가 발동하면 그 시점의 변수를 표준 오류로 찍어서 값이 변하는지 확인합니다(아래 "표준 오류로 디버그 출력 분리").
- 변하는 값이 없거나 같은 값이 되풀이되면 그 변수가 갱신 대상입니다.
- 작은 입력으로 반복 두세 번을 손으로 추적하면 가드 없이도 찾을 수 있습니다(자세히는 15편).
- 가드는 확인용입니다. 제출 전에 지웁니다.

## TLE 원인 분석

TLE는 연산 횟수가 시간 제한을 넘었다는 뜻입니다. 분석은 두 단계입니다.

1. 알고리즘의 복잡도를 입력 최댓값에 대입해 연산 횟수를 어림합니다(자세히는 13편, 14편). 이 값이 크게 넘으면 구현을 다듬어도 해결되지 않고 알고리즘을 바꿔야 합니다.
2. 복잡도가 맞는데도 느리면 반복 안에 숨은 비용을 찾습니다.

JavaScript에서 숨은 비용이 되는 코드는 정해져 있습니다.

| 코드 | 한 번의 비용 | 대체 |
|------|--------------|------|
| 반복 안의 `includes`, `indexOf`, `find` | 배열 길이만큼 | `Set`, `Map` |
| `Array.shift` 큐 | 배열 길이만큼 | head 인덱스 큐 |
| 반복 안의 `slice`, `concat`, `[...arr]` | 복사한 길이만큼 | 인덱스로 범위 지정 |
| `reduce` 안의 `[...acc, v]` | 누적 길이만큼 | `acc.push(v)` |
| 반복 안의 `sort` | N log N | 한 번만 정렬 |
| 줄마다 `console.log` | 출력 호출 | 배열에 모아 `join` |
| 메모이제이션 없는 중복 재귀 | 호출 수 폭증 | `Map`·배열 캐시 |

- 반복 안의 O(N) 연산은 전체를 O(N²)으로 만듭니다. N이 10만이면 약 10^10번의 비교입니다.
- 입력 읽기도 비용입니다. 줄마다 읽는 방식 대신 한 번에 읽습니다(자세히는 08편).
- 재귀가 같은 인자로 반복 호출되면 상태 수만큼만 계산하도록 캐시합니다(자세히는 40편).
- 값이 같아도 최악의 입력이 따로 있습니다. 정렬된 배열, 모든 값이 같은 배열, 일직선 트리를 직접 만들어 시간을 재 봅니다.

```js
// 느림: 매번 배열을 훑는다
for (const x of queries) if (list.includes(x)) cnt++
// 빠름: 해시로 한 번에 찾는다
const seen = new Set(list)
for (const x of queries) if (seen.has(x)) cnt++
```

**흔한 실수:** 작은 입력에서 빨랐다는 이유로 안심하는 것입니다. 제한 조건의 최댓값으로 시간을 재야 합니다. 채점기의 실행 속도와 이 문서의 환경이 같다고 가정할 수 없으므로, 절대 시간보다 연산 횟수와 구현 사이의 상대 비교로 판단합니다.

## MLE 원인 분석

MLE는 프로그램이 쓰는 메모리가 제한을 넘었다는 뜻입니다. 자료의 개수 곱하기 한 개의 크기로 어림하고, 같은 데이터를 몇 벌 들고 있는지 셉니다(자세히는 14편).

| 원인 | 예 | 줄이는 법 |
|------|----|-----------|
| 입력 복사본 여러 벌 | 원문, 줄 배열, 토큰 배열, 숫자 배열을 모두 보관 | 쓴 뒤 놓아 주거나 한 단계만 보관 |
| 과한 상태 배열 | 방문 배열을 상태 차원마다 곱해 선언 | 상태를 정수 하나로 인코딩, 비트마스크 |
| 큐에 경로 통째 저장 | 노드마다 지나온 배열을 복사해 push | parent 배열로 경로 복원 |
| 큰 DP 표 | 2차원 표 전체 | 필요한 행만 유지(롤링 배열) |
| 큰 문자열 키 | `Map`의 키가 긴 문자열 | 정수 인코딩 |
| 무한루프 안의 누적 | 반복마다 push | 무한루프부터 고침 |

- 숫자를 많이 담을 때는 `Int32Array` 같은 TypedArray가 요소당 크기가 정해져 있어서 어림이 정확합니다. `Int32Array`는 요소당 4바이트라서 천만 개는 40,000,000바이트입니다(자세히는 86편).
- 재귀의 호출 스택도 메모리를 씁니다. 깊은 재귀는 메모리보다 깊이 한계에 먼저 걸립니다(아래 "RE 원인 분류").

실제 사용량은 `process.memoryUsage()`로 봅니다. 단위는 바이트이고 `heapUsed`가 JavaScript 힙 사용량, `rss`가 프로세스 전체 상주 메모리입니다. 배열 버퍼는 `arrayBuffers`에 잡힙니다.

```js
const mb = (x) => (x / 1024 / 1024).toFixed(1)
const m = process.memoryUsage()
console.error('heap', mb(m.heapUsed), 'rss', mb(m.rss))
```

Node.js의 힙이 한계에 닿으면 `FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory`를 출력하고 프로세스가 비정상 종료합니다. try/catch로 잡을 수 없습니다. 채점기가 이를 MLE로 표시하는지 RE로 표시하는지는 채점기마다 다릅니다.

- 힙의 상한은 `--max-old-space-size=SIZE`(MiB 단위)로 바꿀 수 있습니다. 채점기에서 실행 옵션을 줄 수 있는지는 확인하지 못했으므로 옵션에 기대지 않고 코드로 줄입니다.
- 줄여도 안 되면 알고리즘의 상태 수가 너무 큰 것입니다. 상태를 줄이는 쪽으로 모델을 바꿉니다(자세히는 84편).

## WA 원인 분류

WA는 실행은 끝났지만 출력이 정답과 다르다는 뜻입니다. 시간·메모리·예외 같은 단서가 없어서 원인 범위가 가장 넓습니다. 아래 표의 위에서 아래로 점검하면 싸게 확인되는 것부터 지웁니다.

| 분류 | 증상 | 확인할 것 |
|------|------|-----------|
| 입력 파싱 | 값이 하나 더 있거나 어긋남 | `\r`, 빈 토큰, 줄 번호(08편) |
| 출력 형식 | 값은 맞는데 틀림 | 공백, 줄바꿈, 소수점, BigInt `n`(08편) |
| 문제 해석 | 예제는 맞고 다른 입력에서 틀림 | 조건·단위·범위·"이상/초과" |
| 경계·엣지 | 최소·최대·빈 입력에서만 틀림 | N=1, 같은 값, 음수, 0(79편) |
| 초기화 누락 | 여러 케이스에서 두 번째부터 틀림 | 케이스마다 새로 만드는지(08편) |
| 수의 범위 | 큰 입력에서만 틀림 | 2^53 초과, 32비트 비트 연산(85편) |
| 정렬·비교 | 순서가 이상함 | 기본 `sort`는 사전순(26편) |
| 원본 변경 | solution 함수에서만 틀림 | 매개변수 배열을 바꿨는지 |
| 알고리즘 | 반례가 있음 | 탐욕의 정당성, 점화식, 방문 처리 |
| 최적화 | 빠르게 고친 뒤 틀림 | 가지치기와 조기 종료의 조건 |

```js
[1, 10, 9].sort()                // [1, 10, 9] (문자열 순서)
[1, 10, 9].sort((a, b) => a - b) // [1, 9, 10]
'a b '.split(' ')                // ['a', 'b', ''] (빈 토큰)
```

원인을 못 정하겠으면 정답을 확실히 아는 느린 풀이와 비교합니다. 작은 입력을 무작위로 만들어 두 풀이의 출력이 처음 달라지는 입력을 찾고, 그 입력을 가장 짧게 줄입니다(자세히는 80편).

- 예제 입력이 통과했다는 사실은 정확성의 증거가 아닙니다. 예제에는 경계와 큰 값이 거의 없습니다.
- 경계에서 틀리는 것은 대개 `<`와 `<=`, 인덱스의 off-by-one입니다(자세히는 15편).
- 한 번에 하나만 바꿔 다시 냅니다. 여러 곳을 동시에 고치면 무엇이 맞았는지 알 수 없습니다.

## RE 원인 분류

RE는 실행 중 예외나 비정상 종료로 프로그램이 끝났다는 뜻입니다. Node.js에서 잡히지 않은 예외는 스택 트레이스를 표준 오류에 출력하고 종료 코드 1로 끝납니다. 첫 줄의 에러 이름과 메시지, 그리고 `파일:줄:열` 위치가 단서입니다.

| 에러 | 메시지의 일부 | 흔한 원인 |
|------|---------------|-----------|
| `TypeError` | `Cannot read properties of undefined` | 배열 범위 밖 접근 뒤 다시 접근 |
| `TypeError` | `Cannot mix BigInt and other types` | BigInt와 Number 혼합(85편) |
| `TypeError` | `Assignment to constant variable.` | `const` 재대입 |
| `RangeError` | `Maximum call stack size exceeded` | 재귀가 너무 깊음(86편) |
| `RangeError` | `Invalid array length`, `Invalid string length` | 배열·문자열 크기 한계(86편) |
| `ReferenceError` | `x is not defined` | 선언하지 않은 변수, 오타 |
| `SyntaxError` | `Cannot convert abc to a BigInt` | BigInt 변환할 수 없는 문자열 |
| 비정상 종료 | `JavaScript heap out of memory` | 힙 한계(위의 MLE) |

JavaScript는 배열 범위 밖을 읽어도 에러가 아니라 `undefined`를 줍니다. 그래서 첫 번째 접근에서는 터지지 않고, 그 결과에 다시 접근할 때 터집니다.

```js
const grid = [[1]]
grid[-1]       // undefined (에러 없음)
grid[-1][0]    // TypeError (undefined의 속성 읽기)
Number(undefined) // NaN (에러 없이 WA로 이어짐)
```

- 격자에서 `grid[nr][nc]`를 읽기 전에 `nr`, `nc`의 범위를 검사합니다(자세히는 17편).
- 입력이 부족할 때 `lines[2].split(' ')`처럼 줄이 없으면 `TypeError`입니다. 줄 수와 토큰 수를 입력 형식과 맞춰 봅니다.
- 범위 밖 접근이 에러 없이 `undefined`와 `NaN`을 퍼뜨리면 RE가 아니라 WA가 됩니다. RE가 아니라고 안전한 것이 아닙니다.
- 재귀 깊이는 입력 크기에 비례해 늘면 위험합니다. 반복문으로 바꿉니다(자세히는 22편, 86편).
- try/catch로 감싸 두면 어느 입력에서 터졌는지 표준 오류로 남길 수 있습니다. 다시 던져서 종료 코드는 그대로 둡니다.

```js
try {
  solve()
} catch (e) {
  console.error('state', { n, i, j })
  throw e
}
```

## 실행 시간 측정

시간 측정은 TLE를 추측이 아닌 숫자로 바꿉니다. 두 가지 도구가 있습니다.

`console.time(label)`과 `console.timeEnd(label)`은 두 호출 사이의 경과 시간을 `label: 225.438ms` 형태로 출력합니다. 단위는 크기에 맞게 바뀌어서 3869ms는 `3.869s`로 나옵니다. `console.timeLog(label)`은 타이머를 끝내지 않고 중간 값을 출력합니다. 라벨을 생략하면 `'default'`입니다.

```js
console.time('sort')
arr.sort((a, b) => a - b)
console.timeEnd('sort') // sort: 12.3ms (예)
```

`performance.now()`는 밀리초 단위의 고해상도 값을 숫자로 돌려줍니다. 0이 현재 프로세스의 시작 시점이고 거꾸로 가지 않으므로 두 값의 차가 경과 시간입니다. 숫자로 받으므로 여러 구간을 모아 비교할 수 있습니다. 공식 문서는 `perf_hooks`에서 가져오는 방식을 보이지만 Node.js 24에서는 전역으로도 동작합니다.

```js
const t0 = performance.now()
const result = solve(input)
const t1 = performance.now()
console.error('solve ms', (t1 - t0).toFixed(1))
```

- 구간을 나눠 잽니다. 입력 읽기, 전처리, 본 계산, 출력 만들기를 따로 재면 어디가 느린지 바로 드러납니다.
- 제한 조건의 최댓값과 최악 형태의 입력으로 잽니다.
- 같은 코드도 실행마다 값이 달라집니다. 여러 번 재고 한 번의 숫자로 결론 내지 않습니다.
- 입력 크기를 두 배로 늘려 시간이 몇 배가 되는지 보면 복잡도의 감이 잡힙니다. 두 배가 되면 선형, 네 배가 되면 제곱에 가깝습니다.
- 로컬 시간과 채점 시간의 배수는 확인하지 못했습니다. 절대 시간으로 합격을 단정하지 않습니다.

**흔한 실수:** `console.time`의 출력은 표준 출력으로 나갑니다. 표준 입출력 형식에서 제출 코드에 남아 있으면 정답 출력에 시간 줄이 섞여 WA가 됩니다. 측정 결과는 아래처럼 표준 오류로 보내고, 제출 전에 지웁니다.

## 표준 오류로 디버그 출력 분리

`console.log`는 표준 출력(stdout)에, `console.error`는 표준 오류(stderr)에 씁니다. `console.warn`은 `console.error`와 같습니다. 정답 비교는 표준 출력만 대상으로 하는 것이 보통이므로, 디버그 값은 `console.error`로 보내서 정답 출력과 섞이지 않게 합니다.

```js
console.log('42')            // 정답 (stdout)
console.error('i =', i)      // 디버그 (stderr)
```

- 로컬에서는 두 출력을 파일로 갈라서 확인합니다. `node sol.js < in.txt > out.txt 2> err.txt`는 정답을 `out.txt`, 디버그를 `err.txt`에 담습니다.
- 정답 파일과 `out.txt`만 비교하면 디버그 출력에 영향받지 않고 검증됩니다.
- 채점기가 표준 오류를 어떻게 다루는지는 채점기마다 다르고 확인하지 못했습니다. 제출 전에는 디버그 출력을 지우는 것을 기본으로 합니다.

켜고 끌 수 있는 디버그 함수로 두면 지우다가 풀이를 건드리는 실수를 줄입니다.

```js
const DEBUG = process.env.DEBUG === '1'
const dbg = (...args) => {
  if (DEBUG) console.error(...args)
}
dbg('queue size', queue.length)
```

- `DEBUG=1 node sol.js < in.txt`로 켭니다. 환경 변수가 없으면 아무것도 출력하지 않습니다. 환경 변수 문법은 셸마다 다릅니다.
- 반복 안에서 많이 찍으면 그 자체가 TLE를 만듭니다. 조건을 걸어 필요한 때만 찍습니다.
- 객체는 `console.error(JSON.stringify(obj))`로 한 줄에 찍으면 로그가 길어지지 않습니다. BigInt가 들어 있으면 `JSON.stringify`가 TypeError를 던집니다(자세히는 85편).
- solution 함수 형식에서는 `console.log`가 채점에 쓰이지 않지만 같은 습관으로 표준 오류를 쓰는 편이 안전합니다(자세히는 08편).

## 핵심 정리

- 판정은 증상입니다. WA는 해석·경계·초기화·형식, TLE는 복잡도와 숨은 O(N) 연산, MLE는 자료 크기와 복사본, RE는 예외와 재귀 깊이부터 의심합니다.
- 무한루프는 갱신 누락, 제자리 갱신(`lo = mid`), 부동소수점 `===`, 방문 처리 누락에서 생기고 반복 횟수 가드로 탐지합니다.
- TLE는 복잡도로 연산 횟수를 어림한 뒤, 반복 안의 `includes`·`shift`·복사·`sort`·출력 호출을 찾습니다.
- JavaScript는 범위 밖 읽기가 `undefined`라서 RE로 터지지 않고 WA로 번지거나 한 단계 뒤에 `TypeError`로 터집니다.
- 시간은 `console.time`이나 `performance.now`로 구간별, 최악 입력으로 잽니다. 시간 출력은 표준 출력에 섞이면 안 됩니다.
- 디버그 출력은 `console.error`로 표준 오류에 보내고, 제출 전에 지웁니다.

## Meet In The Middle 개념

Meet In The Middle은 문제를 두 절반으로 나눠 각각 완전탐색하고, 두 결과를 중간에서 만나게 맞춰 답을 얻는 기법입니다. 전체를 한 번에 탐색하면 `2^n`개의 경우를 봐야 하지만 절반씩 나누면 `2^(n/2)`개씩 두 번 보면 됩니다. 시간을 줄이는 대신 한쪽 결과를 저장하는 메모리를 쓰는 시간-공간 교환입니다.

| n | 전체 `2^n` | 절반 `2^(n/2)` |
|---|-----------|----------------|
| 20 | 1,048,576 | 1,024 |
| 30 | 1,073,741,824 | 32,768 |
| 40 | 1,099,511,627,776 | 1,048,576 |
| 50 | 약 1.1 × 10의 15제곱 | 33,554,432 |

- n = 40이면 전체 탐색은 약 1조 번이라 불가능하지만 절반은 약 100만 개라서 충분히 만들고 정렬하고 탐색할 수 있습니다(시간 계산은 13편).
- 이름은 "중간에서 만난다"에서 왔고, 이중 암호화를 푸는 공격에서 처음 쓰였습니다. 두 개의 56비트 키를 한꺼번에 시도하면 2의 112제곱이지만 한쪽을 표로 저장해 다른 쪽과 맞추면 2의 57제곱 안팎으로 줄어듭니다.
- 일반 형태의 시간은 두 절반을 만드는 `O(2^(n/2))`에 결합 비용이 더해지고, 결합이 정렬과 이분탐색이면 `O(2^(n/2) · n)`입니다. 공간은 `O(2^(n/2))`입니다.

쓸 수 있는 조건입니다.

- 전체 답이 두 절반의 결과를 합·개수·최댓값 같은 단순한 규칙으로 결합해서 나옵니다.
- 한 절반의 선택이 다른 절반의 선택 가능 여부에 영향을 주지 않습니다(서로 독립).
- 절반의 모든 경우를 메모리에 둘 수 있습니다.

같은 구조의 문제입니다.

| 문제 | 나누는 방법 | 결합 |
|------|-------------|------|
| 부분집합 합 | 원소를 앞뒤 절반으로 | 두 절반의 합이 목표가 되는 쌍 |
| 네 배열에서 하나씩 골라 합이 0 | 네 배열을 둘씩 두 묶음으로 | 한 묶음의 합과 다른 묶음의 합이 서로 반대 부호 |
| 양방향 BFS | 시작과 목표 양쪽에서 | 두 탐색이 같은 상태에서 만남(자세히는 39편) |

다른 방법과 고르는 기준입니다.

| 조건 | 알고리즘 |
|------|----------|
| n이 20 이하 | 완전탐색·비트마스크(16편, 24편) |
| n이 40 안팎, 값이 매우 큼 | Meet In The Middle |
| n이 크고 값(합)의 범위가 작음 | DP(41편) |

**문제의 단서:** "n이 최대 40", "각 원소의 크기가 10억 이상", "부분집합의 합이 S인 경우의 수·최댓값"이 함께 나오면 Meet In The Middle입니다. n이 40 안팎이고 원소가 커서 합의 범위로 DP 표를 만들 수 없는 것이 핵심 단서입니다.

**흔한 실수:** n이 40인데 합의 범위가 작아도 되는지 확인하지 않고 쓰는 것입니다. 합의 범위가 작으면 DP가 더 간단하고 빠릅니다.

## 배열 절반 분할

배열을 가운데에서 둘로 나눕니다. n이 홀수면 뒤쪽이 하나 더 많습니다.

```js
const a = [1, 3, 4, 6]
const mid = a.length >> 1          // 2
const left = a.slice(0, mid)       // [1, 3]
const right = a.slice(mid)         // [4, 6]
```

- 두 절반의 크기가 거의 같아야 이득입니다. 한쪽이 훨씬 크면 그쪽의 `2^k`가 병목이 됩니다. n = 40을 10과 30으로 나누면 `2^30`이라 이득이 없습니다.
- `>> 1`은 32비트 정수로 바꿔 오른쪽으로 한 칸 미는 연산이라 `Math.floor(n / 2)`와 같은 값(n이 2의 31제곱 미만일 때)입니다(자세히는 02편).
- 홀수 n에서 어느 쪽을 크게 둘지는 결과에 영향이 없습니다.

각 절반에서 부분집합의 합을 모두 만듭니다. 원소 하나를 더할 때마다 지금까지의 합 전체에 그 원소를 더한 값을 덧붙이는 방식이 가장 간단하고 `O(2^k)`입니다. 합 `0`은 공집합입니다.

```js
function subsetSums(arr) {
  const sums = [0]                       // 공집합
  for (const x of arr) {
    const size = sums.length
    for (let i = 0; i < size; i++) sums.push(sums[i] + x)
  }
  return sums
}
subsetSums([1, 3])  // [0, 1, 3, 4]
subsetSums([4, 6])  // [0, 4, 6, 10]
```

- 비트마스크로 `0`부터 `2^k - 1`까지 돌리며 켜진 비트의 원소를 더하는 방법도 있지만 `O(2^k · k)`라서 위의 덧붙이기가 빠릅니다(자세히는 24편).
- 원소가 k개이면 합이 `2^k`개 나옵니다. 같은 합이 여러 번 나올 수 있고, 그 중복이 곧 서로 다른 부분집합의 수입니다.
- 합의 크기가 `Number.MAX_SAFE_INTEGER`(2의 53제곱 − 1)를 넘지 않는지 확인합니다. 원소가 10억이고 20개면 합은 200억이라 안전합니다. 넘으면 BigInt를 쓰지만 느려집니다(자세히는 02편).

정렬할 때 JavaScript의 함정이 있습니다. 일반 배열의 `sort()`는 비교 함수가 없으면 문자열로 바꿔 비교합니다. 반면 TypedArray의 `sort()`는 비교 함수 없이도 숫자 크기순입니다.

```js
[10, 9, 1].sort()                    // [1, 10, 9] ❌ 문자열 순
Float64Array.from([10, 9, 1]).sort() // [1, 9, 10] ✅
[10, 9, 1].sort((p, q) => p - q)     // [1, 9, 10] ✅
```

이후 코드는 정렬된 합 목록을 만드는 이 함수를 씁니다.

```js
function sortedSums(arr) {   // 숫자순으로 정렬된 Float64Array
  return Float64Array.from(subsetSums(arr)).sort()
}
```

- 정수 합이 `Int32Array` 범위(약 ±21억)에 들어오면 `Int32Array`를, 아니면 `Float64Array`를 씁니다. `Float64Array`는 2의 53제곱 이하의 정수를 정확하게 담습니다(자세히는 05편).
- 성능도 TypedArray가 낫습니다. Node.js 24에서 무작위 정수 약 100만 개(2의 20제곱)를 직접 정렬하니 비교 함수를 준 일반 배열이 0.2초 안팎, `Float64Array`가 0.1초 안팎, `Int32Array`가 0.05초 안팎이었습니다(환경에 따라 다름).
- `Math.max(...sums)`처럼 100만 개를 스프레드로 넘기면 호출 인수 한계로 RangeError가 날 수 있습니다. 반복문으로 구합니다(자세히는 86편).

## 부분집합 합

부분집합 합 문제는 n개의 정수에서 일부를 골라 합이 목표 S가 되게 하는 문제이고, 존재 여부·경우의 수·S 이하의 최대 합을 묻습니다. 일반적으로 NP-완전이라 n이 크면 효율적인 풀이가 알려지지 않았고, n이 40 안팎일 때 Meet In The Middle(Horowitz와 Sahni, 1974)이 정석입니다.

원소를 두 절반으로 나눠 각각의 부분집합 합 목록 `L`, `R`을 만듭니다. 전체 부분집합은 L의 한 합 `x`와 R의 한 합 `y`를 짝지은 것과 하나씩 대응하므로 합이 S인 부분집합은 `x + y = S`인 쌍입니다.

`a = [1, 3, 4, 6]`, `S = 7`로 따라갑니다.

| 단계 | 결과 |
|------|------|
| 나누기 | `[1, 3]`과 `[4, 6]` |
| `L` (앞 절반의 합) | `[0, 1, 3, 4]` |
| `R` (뒤 절반의 합) | `[0, 4, 6, 10]` |
| `x + y = 7`인 쌍 | `1 + 6`, `3 + 4` |
| 개수 | 2 (부분집합 `{1, 6}`, `{3, 4}`) |

- 전체 탐색은 `2^4 = 16`개 합을 만들지만 여기서는 두 목록 `4 + 4`개만 만들어 짝을 찾습니다.
- 공집합 문제: L의 `0`(공집합)과 R의 `0`이 짝이면 전체 공집합이 세어집니다. 목표가 0이고 공집합을 세지 않는다면 결과에서 1을 뺍니다.
- 음수 원소가 있어도 방법은 같습니다. 합의 목록을 정렬하는 데 부호가 상관없습니다.
- 개수는 최대 `2^n`이라 n = 40이면 약 1조이고 Number로 정확히 담깁니다.

변형은 결합 방법만 다릅니다.

| 묻는 것 | 결합 |
|---------|------|
| 합이 정확히 S인 개수 | `y = S - x`인 개수를 센다 |
| 합이 S인 부분집합이 있는가 | 개수가 0보다 큰가 |
| 합이 S 이하인 최대 합 | `y <= S - x`인 가장 큰 `y`를 찾는다 |
| S에 가장 가까운 합 | `S - x` 양쪽의 가장 가까운 두 `y`를 본다 |

**흔한 실수:** 두 목록을 그냥 이중 반복문으로 짝지어 보는 것입니다. 각각 100만 개면 1조 쌍이라 전체 탐색과 다를 바 없습니다. 아래의 정렬 결합을 써서 한쪽을 `O(1)` 또는 `O(log)`에 찾습니다.

## 이분탐색 결합

한쪽 목록 R을 정렬해 두고, 다른 목록 L의 합 `x`마다 R에서 필요한 값 `S - x`를 이분탐색으로 찾습니다. 같은 합이 여러 번 있으니 `lowerBound(R, S - x + 1) - lowerBound(R, S - x)`가 R에서 `S - x`인 원소의 개수입니다. 정수에서 `S - x + 1`은 바로 다음 값이기 때문입니다(`lowerBound`는 28편).

```js
function countSubsets(a, S) {
  const mid = a.length >> 1
  const L = subsetSums(a.slice(0, mid))
  const R = sortedSums(a.slice(mid))
  let count = 0
  for (const x of L) {
    count += lowerBound(R, S - x + 1) - lowerBound(R, S - x)
  }
  return S === 0 ? count - 1 : count   // 공집합 제외
}
countSubsets([1, 3, 4, 6], 7)  // 2
```

- 시간은 합 만들기 `O(2^(n/2))`, 정렬 `O(2^(n/2) · n)`, L의 원소마다 이분탐색 `O(n)`이라 전체 `O(2^(n/2) · n)`입니다. n = 40이면 100만 개 × 20단계 안팎입니다. Node.js 24에서 무작위 입력으로 직접 재면 0.3초 안팎이었고 환경에 따라 다릅니다.
- L은 정렬하지 않아도 됩니다. 정렬은 이분탐색 대상인 R만 하면 됩니다.
- 어느 절반을 R(정렬해 탐색하는 쪽)로 삼아도 결과가 같습니다.
- `lowerBound`는 정수 값 비교라서 실수 합에서는 `S - x + 1`로 개수를 세면 안 됩니다. 실수라면 `upperBound`를 따로 씁니다.

S 이하의 최대 합은 R에서 `S - x` 이하인 가장 큰 값을 찾는 문제입니다. `lowerBound(R, S - x + 1) - 1`이 그 위치이고 0보다 작으면 없습니다.

```js
function bestAtMost(a, S) {          // 공집합(합 0) 포함
  const mid = a.length >> 1
  const L = subsetSums(a.slice(0, mid))
  const R = sortedSums(a.slice(mid))
  let best = -Infinity
  for (const x of L) {
    const k = lowerBound(R, S - x + 1) - 1   // S-x 이하의 마지막
    if (k >= 0) best = Math.max(best, x + R[k])
  }
  return best
}
```

이분탐색 결합은 한쪽만 정렬하면 되고 부등호 조건(이하·이상·가장 가까운 값)까지 한 가지 틀로 풀 수 있어서 가장 범용입니다.

- 응용으로 0/1 배낭에서 무게가 매우 큰 경우가 있습니다. 각 절반에서 (무게, 가치) 쌍의 부분집합을 만들고 R을 무게순으로 정렬한 뒤 앞에서부터의 최대 가치를 누적해 둡니다. L의 한 쌍 `(w, v)`마다 R에서 무게가 `한도 - w` 이하인 마지막 위치를 이분탐색해 `v + 누적 최대 가치`의 최댓값을 구합니다. 쌍을 100만 개 만들어야 해서 무게와 가치를 두 TypedArray로 따로 담는 편이 메모리를 아낍니다.

**흔한 실수:**

- R을 정렬하지 않고 이분탐색하는 것입니다.
- 일반 배열에 `sort()`를 비교 함수 없이 써서 문자열 순서가 되는 것입니다.
- 같은 합의 중복을 무시하고 "있는가"만 확인해 개수를 틀리는 것입니다. 개수는 `upperBound − lowerBound`입니다.
- 두 절반의 크기가 크게 달라 큰 쪽에서 메모리나 시간이 터지는 것입니다. 반으로 정확히 나눕니다.

## 투 포인터·Map 개수 세기로 결합

두 목록을 모두 정렬하면 이분탐색 대신 투 포인터로 `O(2^(n/2))`에 결합합니다(투 포인터는 30편). L은 앞에서, R은 뒤에서 시작해 합이 S보다 작으면 L의 포인터를 올리고 크면 R의 포인터를 내립니다. 같은 값이 여러 개일 때는 각 값의 개수를 곱해 더합니다.

```js
function countPairs(L, R, S) {        // L, R 오름차순
  let i = 0, j = R.length - 1, count = 0
  while (i < L.length && j >= 0) {
    const sum = L[i] + R[j]
    if (sum < S) i++
    else if (sum > S) j--
    else {
      let ci = 0, cj = 0
      for (const x = L[i]; L[i] === x; i++) ci++
      for (const y = R[j]; R[j] === y; j--) cj++
      count += ci * cj
    }
  }
  return count
}
```

- `L`, `R`은 정렬된 TypedArray라서 범위 밖 인덱스를 읽으면 `undefined`가 되어 `L[i] === x` 반복이 끝납니다.
- 같은 합이 `ci`개와 `cj`개 있으면 짝은 `ci * cj`개입니다. 이 곱을 빼먹고 1만 더하는 것이 흔한 실수입니다.
- 합이 S 이하인 최대 합도 같은 이동으로 구합니다. L을 올리면 R의 포인터는 줄어들기만 합니다.

```js
function bestAtMost2(L, R, S) {       // L, R 오름차순
  let j = R.length - 1, best = -Infinity
  for (let i = 0; i < L.length; i++) {
    while (j >= 0 && L[i] + R[j] > S) j--
    if (j >= 0) best = Math.max(best, L[i] + R[j])
  }
  return best
}
```

정렬이 필요 없는 방법도 있습니다. 합이 정확히 S인 개수만 필요하면 R의 합을 Map에 세어 놓고 L의 `x`마다 `S - x`의 개수를 읽습니다. 평균 `O(1)`이라 전체가 `O(2^(n/2))`입니다.

```js
function countByMap(L, R, S) {
  const freq = new Map()                 // 합 → 개수
  for (const y of R) freq.set(y, (freq.get(y) ?? 0) + 1)
  let count = 0
  for (const x of L) count += freq.get(S - x) ?? 0
  return count
}
```

- Map의 키 비교는 `0`과 `-0`을 같게 봅니다. 숫자 키를 쓸 때 문자열로 바뀌는 Object와 달리 Map은 숫자 그대로 키가 됩니다(자세히는 09편, 10편).
- 정렬이 필요 없지만 Map은 키마다 항목을 따로 저장해서 정렬된 TypedArray보다 메모리를 더 씁니다.
- 부등호 조건에는 쓸 수 없고 정확히 일치하는 값만 찾습니다.

세 방법을 비교합니다.

| 방법 | 정렬 | 결합 시간 | 적합한 경우 |
|------|------|-----------|-------------|
| 이분탐색 | R만 | `O(2^(n/2) · n)` | 가장 범용(이하·이상·가장 가까운 값) |
| 투 포인터 | L, R 모두 | `O(2^(n/2))` | 정렬을 이미 했거나 합이 정확히 S·S 이하일 때 |
| Map | 필요 없음 | 평균 `O(2^(n/2))` | 정확히 일치하는 개수만, 메모리가 넉넉할 때 |

- 정렬이 들어가는 이분탐색과 투 포인터는 전체가 `O(2^(n/2) · n)`으로 같고, 정렬이 없는 Map만 평균 `O(2^(n/2))`입니다. 안전한 기본값은 이분탐색입니다.
- 두 목록을 정렬된 채로 만들면 정렬을 건너뜁니다. 원소 하나를 더할 때 `sums`와 `sums + x`가 둘 다 정렬되어 있으니 두 정렬 배열의 병합으로 새 정렬 배열을 만들면 `O(2^k)`입니다. 코드가 길어서 이 문서에서는 개념만 둡니다.

**흔한 실수:**

- 투 포인터에서 같은 값의 개수를 곱하지 않고 한 쌍만 세는 것입니다.
- 정렬이 안 된 `L`에 투 포인터를 쓰는 것입니다.
- Map 방식을 부분집합 합이 S 이하인 최대 합에 쓰는 것입니다.
- 합이 `Number`로 안전한 범위를 넘는데 확인하지 않는 것입니다.

## 핵심 정리

- Meet In The Middle은 `2^n` 완전탐색을 두 절반의 `2^(n/2)`으로 쪼개 결과를 결합하는 기법이며, n이 40 안팎이고 값이 커서 DP를 못 쓰는 문제에 맞습니다.
- 배열을 가운데에서 거의 같은 크기로 나누고 각 절반의 부분집합 합을 원소를 더하며 덧붙이는 방식으로 `O(2^k)`에 만듭니다.
- 부분집합 합은 앞 절반의 합 `x`와 뒤 절반의 합 `y`의 `x + y = S` 쌍으로 세고, 목표가 0이면 공집합을 한 번 뺍니다.
- 이분탐색 결합은 한쪽만 정렬하면 되고 개수·최대·가장 가까운 값까지 풀며, 투 포인터는 둘 다 정렬해 `O(2^(n/2))`, Map은 정확히 일치하는 개수만 센다.
- JavaScript에서 숫자 정렬은 TypedArray의 `sort()`를 쓰고 일반 배열은 비교 함수를 줘야 하며, 100만 개 이상을 스프레드로 넘기면 안 됩니다.

## Constraint 먼저 읽기

제약(constraint)은 문제에서 입력의 크기와 값의 범위, 시간·메모리 제한을 정한 조건입니다. 문제 설명보다 먼저 제약을 읽습니다. 풀이 방향이 제약에서 정해지기 때문입니다.

| 확인 항목 | 알아내는 것 |
|-----------|-------------|
| 입력 크기 N, M | 허용 시간복잡도(14편) |
| 값의 범위 | 합·곱이 Number 안전 범위를 넘는지, 음수·0이 있는지 |
| 시간 제한 | 허용 연산 횟수 |
| 메모리 제한 | 만들 수 있는 배열 크기 |
| 중복·정렬 여부 | 중복 처리가 필요한지, 이미 정렬돼 있는지 |
| 출력 형식 | 답이 없을 때 출력, 여러 답 중 무엇을 낼지 |

값의 범위로 오버플로 위험을 확인하는 예입니다. N ≤ 10^5이고 각 값이 10^9 이하이면 합의 최대는 10^14이고, Number의 안전한 정수 상한 9007199254740991(2^53 − 1, 약 9.0 × 10^15)보다 작아서 Number로 충분합니다. 값이 10^10이고 N이 10^6이면 합이 10^16까지 가서 정밀도를 잃으므로 BigInt가 필요합니다(02편).

- 제약이 작은 쪽(N ≤ 10, 20)은 완전탐색 신호이고 큰 쪽(N ≥ 10^5)은 O(N log N) 이하 신호입니다.
- 입력 형식(한 줄, 여러 줄)도 함께 읽어 읽는 코드를 정합니다(08편).

## 시간복잡도 역산

시간복잡도 역산은 제약에서 허용 연산 횟수를 구한 뒤, 그 안에 들어오는 복잡도를 거꾸로 정하고 그 복잡도로 풀 수 있는 기법을 고르는 순서입니다.

1. N의 상한과 시간 제한으로 허용 복잡도를 구합니다(1초에 약 10^8 연산으로 어림, 14편).
2. 가장 단순한 풀이(완전탐색)의 복잡도를 구해 허용치와 비교합니다.
3. 초과하면 복잡도를 한 단계 낮추는 기법을 고릅니다.

| 목표 복잡도 | 후보 기법 |
|-------------|-----------|
| O(N) | 해시(10편), 누적합(29편), 투 포인터(30편), 슬라이딩 윈도우(31편) |
| O(N log N) | 정렬(26편), 이분 탐색(28편), 힙(46편), 분할 정복(25편) |
| O(N²) | 이중 반복, 2차원 DP(41편), 플로이드-워셜(49편) |
| 지수·팩토리얼 | 백트래킹(23편), 비트마스킹(24편) |

예를 들어 "합이 K인 쌍의 개수, N ≤ 10^5"에서 모든 쌍은 약 5 × 10^9번이어서 허용치를 넘습니다. 배열을 한 번 훑으며 `Map`에서 K − x의 개수를 조회하면 O(N)입니다.

- 이 표는 후보를 좁히는 용도이고 정답을 보장하지 않습니다.
- 처음부터 최적 풀이를 찾으려 하기보다, 단순 풀이로 정확한 답을 낸 뒤 병목 반복문을 줄이는 방식이 안전합니다.

## 메모리 제한 역산

메모리 제한 역산은 제한(MB)을 요소 하나의 바이트 수로 나눠 만들 수 있는 요소 수의 상한을 구하는 것입니다.

```text
최대 요소 수 = 메모리 제한(바이트) / 요소당 바이트
```

- MB를 10^6바이트로 어림하고, 메모리 제한을 256MB로 예를 들면 약 2.56 × 10^8바이트입니다. 값은 문제마다 다릅니다.
- 요소 크기는 `Int32Array` 4바이트, `Uint8Array` 1바이트, `Float64Array` 8바이트입니다(14편). 일반 배열·객체는 바이트 수를 정확히 계산할 수 없습니다.
- 입력 문자열, 런타임, 다른 배열이 메모리를 함께 씁니다. 계산한 상한의 절반 이하로 계획합니다.

| 자료 | 칸 수 | 크기 |
|------|-------|------|
| 5000 × 5000 `Int32Array` | 2.5 × 10^7 | 100MB |
| 5000 × 5000 `Uint8Array` | 2.5 × 10^7 | 25MB |
| 10^4 × 10^4 `Int32Array` | 10^8 | 400MB (256MB 초과) |

- 2차원 DP를 N × M 표로 만들지 말고 필요한 줄만 보관하는 식으로 공간을 줄이는 선택지를 먼저 떠올립니다(41편).
- 메모리 상한을 넘으면 값의 범위를 줄이거나(Int32 대신 Int16) 필요한 상태만 저장합니다.

## Pseudocode

의사코드(pseudocode)는 특정 언어의 문법 없이 풀이 단계를 한국어나 영어로 적은 글입니다. 코드를 쓰기 전에 알고리즘의 구조만 고정하는 것이 목적입니다.

문제 예: 배열에서 가장 긴 연속 증가 구간의 길이를 구합니다.

```text
len = 1, best = 1
i = 1부터 N-1까지 반복:
  a[i]가 a[i-1]보다 크면 len을 1 늘림
  아니면 len을 1로 되돌림
  best = max(best, len)
best 출력
```

```js
function longestRun(a) {
  let len = 1
  let best = 1
  for (let i = 1; i < a.length; i++) {
    len = a[i] > a[i - 1] ? len + 1 : 1
    best = Math.max(best, len)
  }
  return best
}
```

- 의사코드에는 변수의 의미, 반복 범위, 갱신 순서만 적고 API 이름은 적지 않습니다.
- 줄 수가 길어지면 단계가 많은 것이므로 함수로 나눠 적습니다.
- 의사코드가 안 써지면 문제를 아직 이해하지 못한 것입니다. 코드로 바로 가지 않습니다.

## Dry Run

Dry run(손으로 추적)은 코드를 실행하지 않고 작은 입력으로 변수 값이 변하는 모습을 한 줄씩 직접 따라가는 검증입니다. 실행했을 때의 결과와 비교하기 전에 손으로 먼저 정답을 계산해 둡니다.

위 `longestRun`에 `[3, 5, 7, 2, 4, 1, 2, 3, 4]`를 넣고 추적합니다.

| i | a[i-1] → a[i] | 증가? | len | best |
|---|---------------|-------|-----|------|
| 시작 | | | 1 | 1 |
| 1 | 3 → 5 | 예 | 2 | 2 |
| 2 | 5 → 7 | 예 | 3 | 3 |
| 3 | 7 → 2 | 아니오 | 1 | 3 |
| 4 | 2 → 4 | 예 | 2 | 3 |
| 5 | 4 → 1 | 아니오 | 1 | 3 |
| 6 | 1 → 2 | 예 | 2 | 3 |
| 7 | 2 → 3 | 예 | 3 | 3 |
| 8 | 3 → 4 | 예 | 4 | 4 |

- 정답은 1, 2, 3, 4 구간의 4입니다. 표의 마지막 `best`가 4이므로 맞습니다.
- 표의 열은 변하는 변수마다 하나씩 둡니다. 반복 횟수가 많으면 처음 몇 번과 끝 몇 번, 분기가 바뀌는 지점만 적습니다.
- 추적에 쓰는 입력은 길이 5–10 정도로 작게, 모든 분기(증가, 감소)가 한 번씩은 지나가게 고릅니다.
- 직접 출력(`console.log`)으로 중간값을 볼 수도 있지만 제출 전에 지웁니다. 표준 출력을 채점하는 형식에서는 디버그 출력이 정답 출력에 섞여 오답이 됩니다.

## Test Case

테스트 케이스(test case)는 입력과 그에 대한 기대 출력의 쌍입니다. 문제의 예제만 통과했다고 정답이 아닙니다. 예제는 정해진 몇 가지 경우만 담고 있습니다.

| 종류 | 예 (`longestRun`) | 기대값 |
|------|-------------------|--------|
| 문제 예제 | 주어진 입력 | 주어진 출력 |
| 최소 크기 | `[7]` | 1 |
| 전부 증가 | `[1, 2, 3, 4]` | 4 |
| 전부 감소 | `[4, 3, 2, 1]` | 1 |
| 전부 같음 | `[2, 2, 2]` | 1 |
| 최대 크기 | N = 10^5 임의 값 | 시간 안에 종료 |

- 기대값은 코드를 돌려 나온 값을 베끼지 않고, 손으로 계산하거나 단순 풀이로 구합니다.
- 작은 입력에서는 완전탐색 결과와 비교하고, 큰 입력에서는 시간을 확인합니다. 자동으로 무작위 입력을 만들어 비교하는 방법은 80편에서 다룹니다.
- 통과했던 테스트 케이스는 코드를 고칠 때마다 다시 돌려서 이전 정답이 깨지지 않았는지 확인합니다.

## Edge Case와 Corner Case

엣지 케이스(edge case)는 입력 범위의 경계에서 하나의 조건이 극단인 경우이고, 코너 케이스(corner case)는 둘 이상의 경계 조건이 동시에 겹친 경우입니다. 두 용어는 구분 없이 쓰이기도 하니 모두 "경계 입력"으로 점검하면 됩니다.

| 점검 대상 | 예 |
|-----------|----|
| 최소 크기 | N = 1, 빈 배열, 빈 문자열 |
| 최대 크기 | 시간·메모리 한계, 재귀 깊이 |
| 값의 극단 | 0, 음수, 최댓값(오버플로) |
| 모두 같은 값, 이미 정렬, 역순 | 분기가 한쪽으로만 흐르는 입력 |
| 중복 | 같은 값이 여러 번 |
| 답이 없는 경우 | `-1`, 0 출력 규칙 |
| 겹침 | 최소 크기이면서 모두 같은 값 |

- 반환값이 `undefined`·`NaN`이 되는 입력을 찾는 것이 목적입니다. 빈 배열에 대한 `Math.max(...arr)`는 `-Infinity`이고, 초깃값 없는 빈 배열의 `reduce`는 TypeError입니다.
- 경계 입력은 문제에서 "N ≥ 1"처럼 제외했는지 먼저 확인하고, 허용되면 반드시 시험합니다.
- 경계 테스트를 따로 정리하는 방법은 79편에서 이어집니다.

## Off-by-one Error

Off-by-one 오류(off-by-one error)는 반복 횟수나 인덱스, 구간 끝이 정확히 하나 어긋나는 오류입니다. 경계 조건 `<`와 `<=`, 0부터 세는 인덱스와 1부터 세는 번호, 닫힌 구간과 반열린 구간을 섞을 때 생깁니다.

```js
// 길이 K인 윈도우의 개수는 N - K + 1
for (let i = 0; i <= n - k; i++) {} // ✅ 마지막 윈도우 포함
for (let i = 0; i < n - k; i++) {}  // ❌ 마지막 하나 누락
```

| 상황 | 올바른 계산 |
|------|-------------|
| 인덱스 a부터 b까지(양끝 포함) 원소 수 | b − a + 1 |
| `arr.slice(a, b)`의 원소 수 | b − a (b는 제외) |
| 점 N개 사이의 간격 수 | N − 1 |
| 마지막 인덱스 | `arr.length - 1` |

- `arr[arr.length]`는 에러 없이 `undefined`를 줍니다. 오류가 조용히 넘어가므로 값이 이상하게 나오는 곳을 찾아야 합니다.
- 구간은 `[시작, 끝)`처럼 끝을 포함하지 않는 반열린 구간으로 통일하면 길이가 끝 − 시작이어서 실수가 줄어듭니다(34편).
- 문제의 번호가 1부터 시작하면 배열 크기를 N + 1로 잡아 인덱스를 그대로 쓰거나, 읽을 때 1을 빼서 0부터로 바꿉니다. 둘을 섞지 않습니다.
- 경계 입력(N = 1, 최소 구간)으로 추적하면 가장 잘 드러납니다.

## Invariant 찾기

불변식(invariant)은 반복문이 매번 돌 때마다 항상 참인 조건입니다. 반복문이 올바르다는 근거를 세 가지로 확인합니다.

- 초기화: 반복 시작 전에 불변식이 참이다.
- 유지: 한 번 반복하고 나서도 불변식이 참이다.
- 종료: 반복이 끝나면 불변식에서 원하는 답이 따라 나온다.

`longestRun`에서 i번째 반복을 끝낸 뒤의 불변식은 다음입니다.

- `len`은 `a[i]`로 끝나는 가장 긴 증가 구간의 길이입니다.
- `best`는 `a[0]`부터 `a[i]`까지에서 가장 긴 증가 구간의 길이입니다.

초기(i = 0)에는 `len`과 `best`가 1이어서 참입니다. 유지는 `a[i]`가 앞보다 크면 구간이 하나 늘고 아니면 새로 시작하며 `best`는 둘 중 큰 값이어서 참입니다. 끝나면 `best`가 배열 전체의 답입니다.

- 불변식은 코드에 주석으로 한 줄 적어 두면 디버깅 때 어디서 깨지는지 찾기 쉽습니다.
- 이분 탐색의 "답은 항상 `lo`와 `hi` 사이에 있다"(28편), 투 포인터의 "윈도우 합이 항상 갱신돼 있다"(30편)가 대표 불변식입니다.
- 불변식이 안 세워지는 반복문은 한 반복에서 하는 일이 너무 많은 것입니다. 쪼개서 생각합니다.

## Counterexample 만들기

반례(counterexample)는 내 아이디어가 틀렸음을 보이는 구체적인 입력 하나입니다. 풀이가 맞다는 증명은 어렵지만 틀렸다는 증명은 반례 하나면 됩니다. 특히 Greedy(33편)처럼 그럴듯하지만 틀리는 풀이를 걸러 낼 때 씁니다.

동전 {4, 3, 1}로 6원을 만드는 최소 동전 수에서 "큰 동전부터 쓰는" 그리디를 시험합니다.

```text
그리디: 6 → 4 + 1 + 1 → 3개
최적:   6 → 3 + 3     → 2개   ← 반례
```

- 반례는 작은 입력(N ≤ 5)에서 찾습니다. 크기를 줄여도 틀리는 입력이 아니면 아이디어를 바꿔야 합니다.
- 규칙: 입력의 크기를 1, 2, 3으로 늘려 가며 손으로 최적해와 내 풀이의 답을 비교합니다.
- 작은 입력에서 아이디어와 완전탐색의 답을 자동으로 비교하는 방법이 Stress Test입니다(80편).
- 반례를 못 찾았다는 것이 맞다는 증명은 아닙니다. 정당성은 교환 논증처럼 따로 증명합니다(33편).

## Refactoring

리팩터링(refactoring)은 결과를 바꾸지 않고 코드 구조만 읽기 좋게 고치는 작업입니다. 정답을 확인한 뒤에 합니다. 정확성 확인 전에 구조를 바꾸면 오답의 원인을 찾기 어려워집니다.

```js
// 전
for (let d = 0; d < 4; d++) {
  const nr = r + [0, 0, 1, -1][d]
  const nc = c + [1, -1, 0, 0][d]
}
// 후
const DR = [0, 0, 1, -1]
const DC = [1, -1, 0, 0]
for (let d = 0; d < 4; d++) {
  const nr = r + DR[d]
  const nc = c + DC[d]
}
```

| 정리 | 예 |
|------|----|
| 이름 짓기 | `a`, `b` 대신 `price`, `limit` |
| 매직 넘버 제거 | `1000000007`을 `MOD` 상수로 |
| 중복 제거 | 같은 계산을 함수로 |
| 반복 안의 불변 계산 끌어내기 | `arr.length`를 한 번만 계산 |
| 함수 분리 | 입력 읽기, 풀이, 출력을 나눔 |

- 정리 전후에 같은 테스트 케이스를 모두 돌려 결과가 같음을 확인합니다.
- 짧게 쓰려고 `filter().map().reduce()`를 연달아 쓰면 중간 배열이 매번 만들어져 느려질 수 있습니다. 성능이 빠듯한 곳은 반복문을 유지합니다(자세히는 86편).
- 코딩테스트에서는 완벽한 구조보다 정확하고 시간 안에 끝나는 것이 우선입니다.

## 핵심 정리

- 제약을 먼저 읽고 허용 시간복잡도와 메모리 상한을 역산해 알고리즘 후보를 좁힙니다.
- 코드 전에 의사코드로 구조를 정하고, 작은 입력을 손으로 추적해서 기대값을 먼저 구합니다.
- 테스트는 예제, 최소·최대 크기, 같은 값, 정렬·역순, 답 없음 등 경계 입력을 포함합니다.
- off-by-one은 구간 표기를 통일하고 경계 입력으로 추적해서 잡습니다.
- 불변식으로 반복문의 정당성을 확인하고, 아이디어는 작은 입력의 반례로 걸러 내며, 리팩터링은 정답을 확인한 뒤에 합니다.

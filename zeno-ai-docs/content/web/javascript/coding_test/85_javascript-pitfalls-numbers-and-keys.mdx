## Number 정밀도

`Number`는 64비트 부동소수점(IEEE 754 double)이라서 정수도 모두 정확하게 담지는 못합니다. 정수를 오차 없이 다룰 수 있는 범위는 `-(2^53 - 1)`부터 `2^53 - 1`까지입니다. 그 밖에서는 표현할 수 있는 값이 듬성듬성해져서 계산 결과가 가장 가까운 값으로 반올림됩니다.

```js
2 ** 53          // 9007199254740992
2 ** 53 + 1      // 9007199254740992 (❌ 1이 사라짐)
2 ** 53 + 2      // 9007199254740994
9007199254740993 // 9007199254740992 (리터럴도 반올림)
```

- 2^53부터 2^54 사이에서는 2의 배수만 표현할 수 있습니다. 더 커질수록 간격이 벌어집니다.
- 소수의 오차(`0.1 + 0.2 === 0.3`이 `false`)는 별개 문제입니다(자세히는 02편).
- 에러가 나지 않고 값만 틀립니다. 그래서 작은 입력에서는 통과하고 큰 입력에서 WA가 됩니다.

코딩테스트에서 이 한계에 닿는 전형적인 경우는 다음과 같습니다.

| 상황 | 이유 |
|------|------|
| 입력 값이 10^18 | 입력 자체가 이미 안전 범위 밖 |
| 큰 값을 많이 더하기 | 10^5개 곱하기 10^12는 10^17 |
| 두 수의 곱 | 10^9 곱하기 10^9는 10^18 |
| 팩토리얼·피보나치·거듭제곱 | 값이 빠르게 커짐 |
| 이분 탐색의 `mid * mid` | 제곱이 범위를 넘음 |

문제를 읽을 때 입력 최댓값으로 결과의 최댓값을 어림합니다. 그 값이 `2^53 - 1`(약 9.007 곱하기 10^15)을 넘을 수 있으면 `Number`로 풀지 않습니다.

- 정답을 나머지로 요구하는 문제도 중간 곱이 이 범위를 넘을 수 있어서 BigInt를 씁니다(자세히는 83편, 57편).
- Node.js 24에서 `Number`로 계산한 22!은 BigInt로 계산한 값과 정확히 같았고 23!부터 달랐습니다. 이렇게 안전 범위를 넘고도 우연히 맞는 값이 있기 때문에 "얼마까지는 된다"는 식의 기준을 외우지 말고 어림으로 판단합니다.

## Overflow와 MAX_SAFE_INTEGER

`Number.MAX_SAFE_INTEGER`는 `9007199254740991`(2^53 - 1)입니다. 정확히 표현되고 다른 정수와 구별되는 가장 큰 정수라는 뜻입니다. `Number.isSafeInteger(x)`가 안전 범위인지 검사합니다.

```js
Number.MAX_SAFE_INTEGER          // 9007199254740991
Number.isSafeInteger(2 ** 53 - 1) // true
Number.isSafeInteger(2 ** 53)     // false
Number.MAX_SAFE_INTEGER + 1 ===
  Number.MAX_SAFE_INTEGER + 2   // true
```

JavaScript에서 "오버플로"는 세 가지 모양으로 나타나고 서로 다르게 동작합니다.

| 모양 | 동작 |
|------|------|
| `Number`가 2^53 이상 | 에러 없이 정밀도를 잃음 |
| `Number`가 `Number.MAX_VALUE`를 넘음 | `Infinity`가 됨 |
| 32비트 비트 연산·`Int32Array` | 에러 없이 32비트로 되돌아감(감김) |

```js
Number.MAX_VALUE * 2         // Infinity
const a = new Int32Array(1)
a[0] = 2 ** 31               // -2147483648 (감김)
```

- `Number`에는 C++의 `int`처럼 값이 감기는 일이 없습니다. 정밀도를 잃을 뿐입니다.
- `Int32Array`, `Uint8Array` 같은 TypedArray는 범위를 넘는 값을 에러 없이 해당 비트 폭으로 잘라 저장합니다(자세히는 05편, 86편). 합을 담는 배열의 자료형을 입력 최댓값으로 정합니다.
- 계산 결과를 `Number.isSafeInteger`로 검사하면 정밀도를 잃었는지 알 수 있습니다. `Number.isSafeInteger(a * b)`가 `false`이면 곱이 안전 범위를 넘은 것입니다. 디버깅에서 유용하고 제출 코드에서는 지웁니다.
- 중간 값이 넘고 최종 값은 작은 경우(`a * b % m`)도 틀립니다. 곱을 먼저 하고 나머지를 취하는 순서가 문제입니다.

## BigInt 사용

BigInt는 크기 제한 없는 정수 자료형입니다. 정수 리터럴 뒤에 `n`을 붙이거나 `BigInt()`로 만듭니다.

```js
const a = 9007199254740993n          // 리터럴
const b = BigInt('1000000000000000001') // 문자열에서
const c = BigInt(5)                  // 정수 Number에서
a + 1n        // 9007199254740994n
10n ** 30n    // 1000000000000000000000000000000n
```

- 큰 수 입력은 문자열로 받아 `BigInt(문자열)`로 바꿉니다. `Number(문자열)`로 먼저 바꾸면 이미 정밀도를 잃습니다. `Number('1000000000000000001')`은 `1000000000000000000`입니다.
- `BigInt(9007199254740993)`처럼 큰 `Number` 값을 넘기면 이미 반올림된 값(`...992n`)으로 만들어집니다. 소수는 `RangeError`입니다.
- `BigInt('')`은 `0n`입니다. 빈 줄이 `0`으로 읽히므로 입력 줄 수를 확인합니다. 숫자가 아닌 문자열(`'1.5'`, `'abc'`)은 `SyntaxError`입니다.

연산 규칙은 정수 전용입니다.

```js
7n / 2n      // 3n   (0 방향으로 절삭)
-7n / 2n     // -3n  (Math.floor와 다름)
-7n % 3n     // -1n  (나머지의 부호는 나뉘는 수를 따름)
2n > 1       // true (비교는 Number와 섞어도 됨)
0n == 0      // true
0n === 0     // false (자료형이 다름)
```

- 산술(`+ - * / % **`)과 비트 연산은 BigInt끼리만 됩니다. 음수 나머지 보정은 `Number`와 같은 방식으로 합니다(자세히는 11편).
- `Math.sqrt`, `Math.max` 같은 `Math` 메서드는 BigInt를 받지 않습니다. `>>>`와 단항 `+`도 쓸 수 없습니다.
- 속도는 `Number`보다 느립니다. Node.js 24에서 천만 번 더하기를 재 보니 `Number`가 약 8ms, BigInt가 약 420ms였습니다(한 번의 측정이므로 대략의 감각으로만 씁니다). 안전 범위에 들어가는 값에는 `Number`를 씁니다.
- 큰 수가 필요한 부분만 BigInt로 하고 나머지는 `Number`로 둡니다. 둘이 만나는 경계에서 변환합니다(아래 "BigInt와 Number 혼합 금지").
- 64비트로 자르려면 `BigInt.asUintN(64, x)`(부호 없음), `BigInt.asIntN(64, x)`(부호 있음)를 씁니다.
- 정렬은 기본 `sort()`가 문자열 순이라 `[10n, 9n, 2n].sort()`가 `[10n, 2n, 9n]`입니다. 비교 함수는 아래에서 다룹니다.

## BigInt와 Number 혼합 금지

BigInt와 `Number`를 한 산술식에 섞으면 `TypeError`입니다. 자동 변환이 없고 변환은 직접 해야 합니다.

```js
1n + 1           // TypeError (BigInt와 Number 혼합)
1n + BigInt(1)   // 2n
Number(5n) + 1   // 6
let sum = 0n
for (const x of nums) sum += x   // ❌ x가 Number이면 TypeError
for (const x of nums) sum += BigInt(x)  // ✅
```

| 연산 | BigInt와 Number를 섞으면 |
|------|--------------------------|
| `+ - * / % **` | `TypeError` |
| 비트 연산, `<<` | `TypeError` |
| `Math.max(1n, 2)` | `TypeError` |
| `<`, `>`, `==` | 허용(수학적 값으로 비교) |
| `===`, Map의 키 | 자료형이 다르므로 같지 않음 |

- 변환 방향이 서로 다릅니다. `BigInt(number)`는 정수만 받고 `Number(bigint)`는 2^53을 넘으면 정밀도를 잃습니다(`Number(2n ** 64n + 1n)`은 `18446744073709552000`).
- `n * arr.length`처럼 배열 길이(`Number`)와 BigInt를 곱하는 곳에서 자주 터집니다. `BigInt(arr.length)`로 맞춥니다.
- 입력을 받는 순간 BigInt로 바꾸고 계산 내내 BigInt로 유지하고, 인덱스나 반복 횟수처럼 작은 값만 `Number`로 둡니다. 섞이는 지점을 줄이는 것이 핵심입니다.
- BigInt 배열의 숫자 정렬에서 `(a, b) => a - b`는 반환값이 BigInt라서 Node.js 24에서 `TypeError`가 났습니다. 비교 결과를 `Number`로 만들어 돌려줍니다.

```js
const big = [10n, 9n, 2n]
big.sort((a, b) => (a < b ? -1 : a > b ? 1 : 0))
// [2n, 9n, 10n]
```

- `Map`과 `Set`은 `1`과 `1n`을 다른 키로 봅니다. `new Map([[1n, 'a']]).get(1)`은 `undefined`입니다.
- `JSON.stringify`는 BigInt를 만나면 `TypeError`입니다(아래 "BigInt 출력").

## BigInt 출력

BigInt를 그대로 `console.log`하면 `n` 접미사가 붙어서 출력됩니다. 정답 출력이 `10`이어야 하는데 `10n`이 나가면 WA입니다.

```js
console.log(10n)            // 10n (❌)
console.log(String(10n))    // 10
console.log(`${10n}`)       // 10
console.log(10n.toString()) // 10
console.log([1n, 2n])       // [ 1n, 2n ] (❌)
console.log([1n, 2n].join(' ')) // 1 2
```

- 문자열로 바뀔 때는 접미사가 없습니다. `String`, 템플릿 문자열, `toString()`, `join`, 문자열과의 `+`가 모두 해당합니다.
- 여러 값은 `join`으로 이어 한 번에 출력합니다. 배열이나 객체를 `console.log`에 그대로 넘기면 안쪽도 `n`이 붙습니다.
- `process.stdout.write(10n)`은 문자열만 받아서 `TypeError`입니다. `String(x)`로 바꿔 씁니다.
- `JSON.stringify({ a: 1n })`도 `TypeError`입니다. 출력용으로 쓸 때는 값을 먼저 문자열로 바꿉니다.
- 진법 출력은 `x.toString(2)`, `x.toString(16)`입니다.
- 매우 큰 수의 문자열 변환과 연산은 비용이 큽니다. 한 번에 모아 출력하는 방식을 유지합니다(자세히는 08편).
- `Number`로 되돌려 출력하면 정밀도를 잃습니다. 출력 직전까지 BigInt로 두고 문자열로 바꿉니다.

## 비트 연산의 32비트 제한

비트 연산자(`& | ^ ~ << >>`)와 `>>>`는 피연산자를 32비트 정수로 바꾼 뒤 계산합니다. 32비트를 넘는 부분은 버려지고, 결과의 최상위 비트가 1이면 음수입니다(`>>>`만 부호 없는 결과).

| 식 | 결과 | 이유 |
|----|------|------|
| `1 << 30` | `1073741824` | 31비트 안 |
| `1 << 31` | `-2147483648` | 최상위 비트가 켜져 음수 |
| `1 << 32` | `1` | 시프트 양은 32로 나눈 나머지 |
| `2 ** 31 >> 0` | `-2147483648` | 32비트 부호 있는 정수로 변환 |
| `5000000000 >> 0` | `705032704` | 상위 비트를 잘라 냄 |
| `(2 ** 33 + 3) & 3` | `3` | 2^33은 버려짐 |
| `2 ** 40 >> 1` | `0` | 하위 32비트가 0 |
| `-1 >>> 0` | `4294967295` | 부호 없는 32비트 |

- 이 제한에 걸리는 곳은 비트마스크 상태(원소가 32개 이상), `x >> 1`로 하는 반 나누기(`x`가 2^31 이상), `x | 0`·`~~x`로 하는 절삭, `1 << n`의 `n`이 31 이상일 때입니다(자세히는 24편).
- `Number`는 안전 범위까지 정확하지만 비트 연산은 32비트까지만 정확합니다. 값이 2^31 이상이면 산술 연산으로 바꿉니다. `Math.floor(x / 2)`, `x % 2`, `x * 2 ** k`처럼 씁니다.
- 큰 이분 탐색에서 `mid = (lo + hi) >> 1`이 틀립니다. `Math.floor((lo + hi) / 2)`로 씁니다(자세히는 83편).
- 부호 없는 32비트로 보고 싶으면 `x >>> 0`입니다. `(1 << 31) >>> 0`은 `2147483648`입니다.
- 32비트를 넘는 비트 집합은 BigInt가 필요합니다. `1n << 40n`처럼 `n`을 붙인 BigInt끼리만 시프트하고, `1n << 2`는 `TypeError`입니다.

```js
let mask = 0n
mask |= 1n << 40n               // 40번 비트 켜기
const on = (mask >> 40n) & 1n   // 1n
const bits = mask.toString(2).length  // 41
```

- 비트마스크 DP는 원소 수가 보통 20 안팎이라 32비트로 충분합니다. 제한에서 원소 수가 30을 넘으면 방법을 바꿔야 한다는 신호입니다.
- `Number`의 비트 연산 결과는 부호 있는 정수라서 `mask < (1 << k)` 같은 비교가 음수 때문에 틀릴 수 있습니다. `k`가 31 미만일 때만 안전합니다.

## Object vs Map

둘 다 키로 값을 찾는 자료구조지만 키의 처리가 다릅니다. 해시로 쓸 때 기본값은 `Map`이 안전합니다(자세히는 09편, 10편).

| 항목 | Object | Map |
|------|--------|-----|
| 키 자료형 | 문자열, 심벌 (숫자는 문자열로 변환) | 모든 값 |
| 기본 키 | 프로토타입의 키가 있음(`toString` 등) | 없음 |
| 순회 순서 | 정수 형태 키 오름차순 먼저, 나머지 삽입 순 | 삽입 순 |
| 크기 | `Object.keys(o).length` | `m.size` |
| 순회 | `for...in`, `Object.keys` | `for...of`, `keys()` |
| 삭제 | `delete o[k]` | `m.delete(k)` |
| 값 읽기 | `o[k]` (없으면 `undefined`) | `m.get(k)` (없으면 `undefined`) |

- Map이 "자주 넣고 빼는 경우에 더 낫다"는 것이 MDN의 설명입니다. 속도는 키 종류에 따라 달랐습니다. 같은 횟수의 빈도 세기에서 Node.js 24는 정수 키에서 Object가, 문자열 키에서 Map이 앞섰습니다(한 번의 측정). 어느 한쪽이 항상 빠르다고 보지 않고 안전한 쪽을 고릅니다.
- 키가 `0`부터 이어지는 작은 정수라면 둘 다 아니라 배열(`new Int32Array(n)`)이 가장 단순하고 가볍습니다.
- 문자열 키를 Object로 세면 프로토타입 키와 부딪칩니다. 키가 `'constructor'`나 `'toString'`인 경우 `(o[k] || 0) + 1`이 함수에 1을 더한 문자열이 됩니다. 아래 "Object Key 문자열화 주의"에서 다룹니다.

```js
const m = new Map()
m.set('constructor', 1)
m.get('constructor')        // 1
const o = {}
o['constructor'] = (o['constructor'] || 0) + 1
typeof o['constructor']     // 'string' (❌)
```

- 빈도수와 방문 표시처럼 키가 입력에서 오는 경우에는 `Map`을 씁니다. 키가 코드에 고정된 몇 개의 이름이라면 Object도 괜찮습니다.
- 순서가 필요한 순회에서 숫자 문자열 키가 섞이면 Object는 삽입 순이 아니라 숫자 순으로 나옵니다. 삽입 순서가 의미 있는 문제(LRU, 먼저 들어온 순)에는 `Map`입니다(자세히는 09편).

## Array vs Set

배열은 순서와 인덱스가 있는 목록이고, `Set`은 중복 없는 값의 모음입니다. "이 값이 있는가"를 반복해서 묻는다면 `Set`입니다.

| 항목 | Array | Set |
|------|-------|-----|
| 존재 확인 | `includes`, 길이에 비례 | `has`, 평균적으로 훨씬 빠름 |
| 중복 | 허용 | 없음 |
| 순서 | 인덱스 순 | 삽입 순 |
| 인덱스 접근, 정렬 | 가능 | 불가(배열로 변환) |
| 값 비교 | `includes`는 `NaN`을 찾음, `indexOf`는 못 찾음 | `NaN`을 같은 값으로 봄 |

```js
const list = [3, 1, 3, 2, 1]
const uniq = [...new Set(list)]   // [3, 1, 2] (처음 순서 유지)
const seen = new Set(list)
seen.has(2)                       // true
list.includes(2)                  // true (배열 전체를 훑음)
```

- MDN은 `Set`의 접근 시간이 평균적으로 요소 수에 대해 준선형이어야 한다고 명세가 요구한다고 설명합니다. 같은 크기의 배열에서 `includes`보다 평균적으로 빠르다고도 밝힙니다.
- 직접 재면 차이가 큽니다. Node.js 24에서 5만 개 요소에 5만 번 물었을 때 `includes`는 약 650ms, `Set.has`는 1ms 안팎이었습니다(한 번의 측정, 대략의 감각).
- 반복 안에서 `includes`를 부르는 코드는 O(N²)입니다(자세히는 81편). 조회가 반복되면 처음에 `Set`으로 한 번 바꿉니다.
- 조회가 한 번뿐이면 `Set`을 만드는 비용이 더 들 수 있습니다. 요소가 수십 개 이하이거나 한 번만 찾을 때는 `includes`가 간단합니다.
- 인덱스, 정렬, 구간 자르기가 필요하면 배열입니다. 집합 연산(교집합, 합집합)이 필요하면 `Set`입니다(ES2025의 Set 메서드는 09편).
- `Set`은 객체를 참조로 비교합니다. `new Set([[1], [1]]).size`는 `2`입니다. 값이 같은 배열을 합치려면 문자열이나 정수로 바꿔 넣습니다(아래).

## Map에서 객체 / 숫자 Key

`Map`의 키는 어떤 값이든 되고, `SameValueZero`로 비교됩니다. 변환 없이 키 자체가 비교되므로 숫자 `1`과 문자열 `'1'`은 다른 키입니다.

```js
const m = new Map()
m.set(1, 'num')
m.set('1', 'str')
m.size     // 2
m.get(1)   // 'num'
m.get('1') // 'str'
```

- `NaN`은 `NaN`과 같은 키로 취급되고, `0`과 `-0`은 같은 키입니다(`m.set(-0, 'y')`는 `0`의 값을 바꿈).
- 객체와 배열 키는 값이 아니라 참조로 비교됩니다. 내용이 같아도 다른 객체는 다른 키입니다.

```js
const m = new Map()
m.set([1, 2], 'a')
m.get([1, 2])      // undefined (❌ 다른 배열)
const k = [1, 2]
m.set(k, 'b')
m.get(k)           // 'b' (같은 참조)
```

- 좌표 `(r, c)`나 상태처럼 값이 같으면 같은 키여야 할 때는 복합 값을 하나의 원시 값으로 바꿔서 키로 씁니다.

| 방법 | 코드 | 주의 |
|------|------|------|
| 정수로 합치기 | `r * W + c` | 열 수 `W`를 정확히 사용하고 `W`보다 큰 `c`가 없어야 함 |
| 문자열로 합치기 | `` `${r},${c}` `` | 구분자를 꼭 넣음. 느리고 메모리를 더 씀 |
| 비트로 합치기 | `(r << 16) + c` | 각 값이 16비트 안이어야 함(32비트 제한) |

- 가능하면 정수 키가 가볍고 빠릅니다. 범위를 정해 합칠 때 곱하는 수는 가능한 값의 개수 이상이어야 합니다. `r * 100 + c`인데 `c`가 100 이상이면 `(0, 100)`과 `(1, 0)`이 같은 키가 됩니다.
- 문자열 키는 구분자가 없으면 `(1, 23)`과 `(12, 3)`이 모두 `'123'`이 됩니다.
- 키가 큰 정수(2^53 초과)이면 `Number` 키는 반올림되어 서로 다른 값이 같은 키가 됩니다. BigInt 키를 쓰되 `1n`과 `1`이 다른 키라는 점에 주의합니다.

## Object Key 문자열화 주의

Object의 키는 문자열(또는 심벌)이라서 다른 값을 키로 쓰면 문자열로 변환됩니다. 서로 다른 값이 같은 문자열로 변환되면 같은 키가 되고, 읽을 때 되돌려 받는 키는 항상 문자열입니다.

```js
const o = {}
o[1] = 'a'
o['1']            // 'a'  (숫자 1과 문자열 '1'이 같은 키)
o[[1, 2]] = 'b'
Object.keys(o)    // ['1', '1,2']  (배열은 '1,2'로 변환)
```

- 모든 객체는 `'[object Object]'`로 변환됩니다. 서로 다른 객체를 키로 쓰면 같은 키로 덮어씁니다.

```js
const a = { id: 1 }, b = { id: 2 }
const o = {}
o[a] = 'A'
o[b] = 'B'
Object.keys(o).length  // 1 (❌ 두 객체가 같은 키)
o[a]                   // 'B'
```

- `Object.keys`, `for...in`, `Object.entries`가 돌려주는 키는 모두 문자열입니다. 숫자로 쓰려면 변환합니다. `'1' + 1`은 `'11'`이고 `Number(k) + 1`이 `2`입니다.

```js
const o = { 3: 'x', 10: 'y' }
Object.keys(o)             // ['3', '10']
Object.keys(o).map(Number) // [3, 10]
for (const k in o) k + 1   // '31', '101' (문자열 이어 붙임)
```

- 정수 형태의 키(`'0'`, `'10'`)는 숫자 오름차순으로 먼저 나오고, 그다음 나머지 문자열 키가 삽입 순서로 나옵니다. 키를 `10, 9, 2` 순서로 넣어도 `['2', '9', '10']`입니다. 음수·소수·`'01'`처럼 정수 형태가 아닌 키는 삽입 순입니다.
- `-0`은 `'0'`으로, `1e21`은 `'1e+21'`로 변환됩니다. 아주 큰 수와 소수는 표기가 달라져 예상한 키와 어긋날 수 있습니다.
- 프로토타입에서 오는 이름이 문제입니다. `'toString'`, `'constructor'`는 값을 넣지 않아도 `in` 연산에서 `true`이고 `o[k]`가 `undefined`가 아닙니다.

```js
const o = {}
'toString' in o               // true
Object.hasOwn(o, 'toString')  // false (ES2022)
const bare = Object.create(null)  // 프로토타입이 없는 객체
bare['toString'] = 1
```

- 존재 확인은 `k in o`가 아니라 `Object.hasOwn(o, k)`(ES2022) 또는 `o[k] !== undefined`로 합니다. 키에 `__proto__`가 들어오면 일반 객체에서 대입이 의도대로 저장되지 않습니다. 입력이 만드는 키는 `Map`이나 `Object.create(null)`로 받습니다.
- 숫자 키를 인덱스처럼 쓰면 `Map`이나 배열이 더 안전합니다. 순서와 변환 문제가 한꺼번에 사라집니다.

## 핵심 정리

- `Number`는 2^53 - 1까지만 정수를 정확히 다루고, 넘으면 에러 없이 틀립니다. 입력 최댓값으로 결과 크기를 어림해 넘을 수 있으면 BigInt를 씁니다.
- BigInt는 Number와 산술에서 섞을 수 없고(`TypeError`) 입력 시점에 문자열에서 만들어 끝까지 BigInt로 유지하며, 출력은 `String`·`join`으로 `n`을 없앱니다. 속도는 Number보다 느립니다.
- 비트 연산은 32비트 정수에서 이뤄집니다. 값이 2^31 이상이거나 비트가 32개 이상이면 산술 연산이나 BigInt를 씁니다.
- 해시로 쓸 때는 Map이 기본입니다. Object는 키가 문자열로 변환되고 프로토타입 키와 정수 키 순서의 함정이 있습니다.
- 존재를 반복해서 묻는다면 배열의 `includes` 대신 `Set`의 `has`를 씁니다. 조회가 한 번이거나 요소가 적으면 배열도 괜찮습니다.
- Map의 객체·배열 키는 참조로 비교되므로 좌표 같은 복합 키는 정수나 문자열 하나로 바꿔서 쓰고, Object의 키는 숫자·배열·객체가 모두 문자열로 바뀌는 점을 기억합니다.

## 그리디 개념

그리디(greedy)는 매 단계에서 그 순간 가장 좋아 보이는 선택을 하고, 한 번 한 선택은 되돌리지 않는 방법입니다. 선택 기준만 정하면 반복문 하나로 끝나서 구현이 짧고 빠릅니다.

그리디가 정답이 되려면 두 성질이 필요합니다.

| 성질 | 뜻 |
|------|----|
| 그리디 선택 성질 | 지금 가장 좋은 선택을 해도, 그 선택을 포함하는 최적해가 항상 존재한다 |
| 최적 부분 구조 | 선택하고 남은 문제의 최적해에 선택을 더하면 원래 문제의 최적해가 된다 |

성질이 하나라도 깨지면 그리디는 틀린 답을 냅니다. 겉보기에 그럴듯한 기준이 틀리는 경우가 많으므로 정당성 확인이 풀이의 일부입니다(아래 "그리디 정당성").

문제 풀이 단계는 다음과 같습니다.

1. 한 번에 하나씩 고르는 구조인지 본다. 선택 순서가 정해지면 답이 결정되는 문제다.
2. 선택 기준을 정한다. 대개 정렬 기준이 곧 선택 기준이다.
3. 작은 입력으로 반례를 찾거나 증명한다.
4. 기준대로 정렬하고 한 번 훑으며 고른다. 시간은 정렬이 지배하므로 O(N log N)이다.

다른 방법과의 비교입니다.

| 방법 | 선택 | 시간 |
|------|------|------|
| 그리디 | 한 가지만 고르고 되돌리지 않음 | 보통 O(N log N) |
| 완전탐색 | 모든 경우를 확인(자세히는 16편) | 지수 시간 |
| DP | 부분 문제의 답을 저장하고 최선을 고름(자세히는 40편) | 상태 수에 비례 |

그리디를 의심하는 단서는 "최대한 많이", "최소한의 횟수로", "가장 작은 비용"처럼 최적을 묻는데 N이 커서 완전탐색이 불가능하고, 점화식을 세우기엔 선택이 단순해 보일 때입니다.

**흔한 실수:** 예제 몇 개가 맞는다고 그리디를 확정하는 것입니다. 샘플은 대개 그리디가 우연히 맞는 경우입니다.

## 정렬 기반 그리디

정렬 기반 그리디는 정렬한 순서가 곧 선택 순서인 풀이입니다. 정렬을 먼저 하고 앞(또는 뒤)에서부터 차례로 고르거나 양 끝에서 짝을 짓습니다(비교 함수는 26편).

직접 만든 유형 문제입니다.

> 몸무게 배열 `weights`와 보트 한 대의 무게 제한 `limit`가 주어진다. 보트에는 한 번에 최대 두 명까지 탈 수 있고 두 사람의 몸무게 합이 `limit` 이하여야 한다. 모두 건너려면 보트가 최소 몇 대 필요한가? 한 사람의 몸무게는 `limit` 이하다.

가장 무거운 사람은 누구와도 짝을 못 지을 수 있습니다. 그러니 가장 가벼운 사람과 먼저 짝을 시도하고, 안 되면 가장 무거운 사람은 혼자 태웁니다.

```js
function boats(weights, limit) {
  const w = [...weights].sort((a, b) => a - b)
  let lo = 0, hi = w.length - 1, count = 0
  while (lo <= hi) {
    if (w[lo] + w[hi] <= limit) lo++ // 가벼운 사람도 같이 탄다
    hi--                             // 가장 무거운 사람은 출발
    count++
  }
  return count
}
boats([70, 50, 80, 50], 100) // 3
```

`[50, 50, 70, 80]`, 제한 100에서 흐름입니다.

| lo | hi | 합 | 결과 | 보트 |
|----|----|----|------|------|
| 50 | 80 | 130 | 80 혼자 | 1 |
| 50 | 70 | 120 | 70 혼자 | 2 |
| 50 | 50 | 100 | 둘이 함께 | 3 |

- `lo`가 `hi`를 넘으면 모두 탄 것입니다. `lo === hi`인 마지막 한 사람은 `w[lo] + w[hi]`가 두 배가 되어 대개 조건에 실패하고 혼자 탑니다. 같은 사람을 두 번 태우지 않도록 `hi--`가 항상 실행됩니다.
- 정렬이 O(N log N), 훑기가 O(N)입니다. 입력 배열을 바꾸지 않으려고 `[...weights]`로 복사해 정렬했습니다.
- `sort`에 비교 함수를 빼먹으면 숫자가 문자열 순서로 정렬됩니다(자세히는 26편).

정렬 기준은 문제 유형으로 정해집니다.

| 문제 유형 | 정렬 기준 |
|-----------|-----------|
| 구간을 겹치지 않게 최대한 많이 | 끝나는 시각 오름차순 |
| 구간을 점으로 모두 덮기 | 끝점 오름차순 |
| 예산 안에서 가장 많이 사기 | 가격 오름차순 |
| 가치가 큰 것부터 고르기(분할 가능) | 단위 무게당 가치 내림차순 |
| 마감 기한이 있는 작업 | 이익 내림차순 |
| 두 배열의 곱의 합을 최소로 | 한 배열은 오름차순, 다른 배열은 내림차순 |

**흔한 실수:** 객체나 구간을 정렬하면서 한 기준만 쓰는 것입니다. 기준이 같은 값 사이의 순서(동점 처리)가 답을 바꾸는 문제가 있습니다(아래 "회의실 배정").

## 최소값 선택

최소값 선택은 매 단계에서 남은 것 중 가장 작은 값을 고르는 그리디입니다. 비용이 작은 것부터 쓰면 같은 예산으로 더 많이 고를 수 있다는 원리입니다.

> 물건 가격 배열 `prices`와 예산 `budget`이 주어진다. 예산 안에서 살 수 있는 물건의 최대 개수를 구한다.

```js
function maxItems(prices, budget) {
  const sorted = [...prices].sort((a, b) => a - b)
  let count = 0
  for (const p of sorted) {
    if (p > budget) break // 가장 싼 것도 못 사면 끝
    budget -= p
    count++
  }
  return count
}
maxItems([4, 1, 7, 2, 3], 9) // 3
```

| 순서 | 가격 | 남은 예산 | 개수 |
|------|------|-----------|------|
| 1 | 1 | 8 | 1 |
| 2 | 2 | 6 | 2 |
| 3 | 3 | 3 | 3 |
| 4 | 4 | 4가 3보다 커서 중단 | 3 |

- 정당성: 개수가 k인 어떤 구매가 있다면, 그중 하나라도 더 싼 물건으로 바꿔도 예산을 넘지 않습니다. 그러므로 가장 싼 k개를 사는 것이 가능한 최선입니다.
- 정렬된 뒤에는 한 번 못 사면 이후 것도 모두 못 사므로 `break`로 끝냅니다.
- 개수가 아니라 "합이 최소"를 구하는 문제도 같은 정렬입니다. 매번 최솟값을 새로 찾는 반복(N번 × O(N))은 O(N²)이라서 정렬 한 번이 낫습니다.
- 값이 계속 바뀌는 집합에서 최솟값을 반복해서 꺼내야 하면 정렬이 아니라 힙을 씁니다(자세히는 46편, 47편).

**흔한 실수:** 예산을 `budget`에서 빼며 진행하는데 원본 배열을 직접 `sort`해서 호출한 쪽의 배열을 바꾸는 것입니다. `sort`는 제자리에서 정렬하므로 복사 후 정렬하거나 바뀌어도 되는지 확인합니다.

## 최대값 선택

최대값 선택은 매 단계에서 선택 가능한 것 중 가장 큰 값을 고르는 그리디입니다. 값의 자릿수가 앞일수록 영향이 크다는 성질이 있을 때 자주 씁니다.

> 숫자 문자열 `num`에서 숫자 `k`개를 지워 만들 수 있는 가장 큰 수를 구한다. 남은 숫자의 순서는 바꾸지 않는다.

앞자리가 클수록 수가 커집니다. 그래서 앞자리가 바로 뒤 숫자보다 작으면 지우는 것이 이득입니다. 지울 횟수가 남은 동안 이 판단을 스택으로 처리합니다(스택은 19편).

```js
function biggest(num, k) {
  const stack = []
  for (const ch of num) {
    while (k > 0 && stack.length && stack.at(-1) < ch) {
      stack.pop() // 작은 앞자리를 지운다
      k--
    }
    stack.push(ch)
  }
  return stack.slice(0, stack.length - k).join('')
}
biggest('1924', 2) // '94'
```

`'1924'`, `k = 2`에서 흐름입니다.

| 읽은 숫자 | 동작 | 스택 | 남은 k |
|-----------|------|------|--------|
| 1 | 넣기 | 1 | 2 |
| 9 | 1이 9보다 작아 1을 지움, 넣기 | 9 | 1 |
| 2 | 9가 더 커서 넣기 | 9 2 | 1 |
| 4 | 2가 4보다 작아 2를 지움, 넣기 | 9 4 | 0 |

- 문자열 한 글자씩 비교하는 `stack.at(-1) < ch`는 같은 길이의 숫자 문자 비교라서 숫자 크기 순서와 같습니다. `at`은 ES2022이고 구형은 `stack[stack.length - 1]`입니다.
- 반복이 끝났는데 `k`가 남아 있으면 숫자가 내림차순으로 이미 정렬된 경우입니다(예: `'54321'`, `k = 2`). 그래서 뒤에서 `k`개를 잘라 냅니다. `'543'`이 답입니다.
- 각 숫자는 스택에 한 번 들어가고 한 번 나가므로 O(N)입니다.
- 지울 때마다 앞자리 선택이 더 커지고, 같은 길이 중에서는 앞자리가 큰 쪽이 항상 크다는 것이 정당성의 핵심입니다.

**흔한 실수:**

- `k`가 남은 채로 끝나는 경우를 처리하지 않는 것입니다. `slice(0, stack.length - k)`가 빠지면 길이가 틀립니다.
- 숫자를 `Number`로 바꿔 비교하다가 자릿수가 많은 입력에서 정밀도를 잃는 것입니다. 큰 수는 문자열로 다룹니다(자세히는 02편).

## 회의실 배정

회의실 배정은 시작·끝 시각이 있는 회의들 중 서로 겹치지 않는 회의를 가장 많이 고르는 문제입니다. 회의실이 하나이고, 끝나는 시각에 다음 회의가 바로 시작할 수 있습니다. 구간 선택 문제의 가장 기본 형태입니다.

기준은 끝나는 시각이 가장 빠른 회의를 먼저 고르는 것입니다. 일찍 끝나는 회의를 고르면 남은 시간이 가장 많이 남습니다. 같은 끝 시각이면 시작이 빠른 쪽이 먼저 오도록 정렬합니다.

```js
function meetings(list) {  // list: [[start, end], ...]
  const s = [...list]
    .sort((a, b) => a[1] - b[1] || a[0] - b[0])
  let end = -Infinity, count = 0
  for (const [st, en] of s) {
    if (st >= end) { // 직전 선택이 끝난 뒤에 시작
      count++
      end = en
    }
  }
  return count
}
```

| 정렬 순서 | 구간 | 판단 | 마지막 끝 시각 | 선택 수 |
|-----------|------|------|----------------|---------|
| 1 | [1, 4] | 첫 회의라 선택 | 4 | 1 |
| 2 | [3, 5] | 3이 4보다 작아 겹침 | 4 | 1 |
| 3 | [0, 6] | 겹침 | 4 | 1 |
| 4 | [5, 7] | 5 ≥ 4 선택 | 7 | 2 |
| 5 | [3, 8] | 겹침 | 7 | 2 |
| 6 | [8, 11] | 8 ≥ 7 선택 | 11 | 3 |

입력 여섯 개 `[[1,4],[3,5],[0,6],[5,7],[3,8],[8,11]]`의 답은 3입니다.

표준 입력 형식으로 감싸면 다음과 같습니다. 첫 줄이 회의 수 N이고 다음 N줄에 시작과 끝이 공백으로 구분됩니다(입출력은 08편).

```js
const fs = require('fs')
const lines = fs.readFileSync(0, 'utf8').trim().split('\n')
const n = Number(lines[0])
const list = lines.slice(1, n + 1)
  .map((l) => l.split(' ').map(Number))
console.log(meetings(list))
```

- 비교 `st >= end`에서 등호가 "끝나는 순간 다음 회의가 시작 가능"을 뜻합니다. 문제가 경계가 겹치는 것을 허용하지 않으면 `st > end`로 바꿉니다. 경계 표기는 34편에서 다룹니다.
- 정렬은 O(N log N), 훑기는 O(N)입니다.
- 시작과 끝이 같은 회의(길이 0)가 있으면 동점 처리가 답을 바꿉니다. `[[2,2],[1,2],[2,3]]`은 끝 시각이 같은 `[2,2]`와 `[1,2]` 중 `[1,2]`가 먼저 와야 세 개를 모두 고릅니다. `[2,2]`가 먼저면 `[1,2]`가 `1 < 2`로 겹쳐 버려 답이 2가 됩니다.
- 회의실이 여러 개일 때 필요한 최소 개수는 다른 문제이며 34편에서 다룹니다.

**흔한 실수:** 끝 시각만으로 정렬해서 시작 시각이 같거나 길이 0인 구간의 순서를 `sort`의 안정성에 맡기는 것입니다. 안정 정렬은 입력 순서를 유지할 뿐이므로 두 번째 기준을 직접 써야 합니다(안정 정렬은 26편).

## 동전 문제

동전 문제(거스름돈)는 금액을 가장 적은 개수의 동전으로 만드는 문제입니다. 큰 동전부터 가능한 만큼 쓰는 그리디가 맞는 동전 체계가 있고 틀리는 체계가 있습니다.

```js
function coins(amount, units) {
  let rest = amount, count = 0
  for (const c of [...units].sort((a, b) => b - a)) {
    count += Math.floor(rest / c) // 가능한 만큼 사용
    rest %= c
  }
  return rest === 0 ? count : -1  // 못 만들면 -1
}
coins(4200, [1, 5, 10, 50, 100, 500, 1000]) // 6
```

4200원은 `1000 × 4 + 100 × 2`이므로 동전 6개입니다.

- 몫과 나머지로 한 번에 처리하므로 금액이 커도 동전 종류 수만큼만 반복합니다. 한 개씩 빼는 반복은 금액이 큰 입력에서 시간 초과입니다.
- 단위 중에 1이 없으면 만들 수 없는 금액이 생기므로 `rest !== 0` 검사가 필요합니다.
- 각 동전이 `n_i`개까지만 있는 문제면 `Math.min(Math.floor(rest / c), n_i)`로 개수를 제한합니다. 이때는 그리디의 정당성이 다시 필요합니다.

### 그리디가 맞는 경우

큰 단위가 작은 단위의 배수이면 그리디가 최적입니다. 예를 들어 1, 5, 10, 50, 100, 500은 각 단위가 바로 아래 단위의 배수입니다.

이유는 교환 논증으로 설명됩니다. 인접한 두 단위 `a`, `b`(`b`는 `a`의 배수이고 `b`가 더 큼)에서 최적해가 `a`를 `b / a`개 이상 쓰면, 그 동전들을 `b` 하나로 바꿔 개수를 줄일 수 있습니다. 그러므로 최적해는 각 단위를 `b / a`개 미만으로만 쓰고, 이런 해는 금액마다 하나뿐입니다. 그 하나가 큰 동전부터 최대한 쓰는 그리디의 해입니다. 1부터 500까지 모든 금액을 DP 결과와 비교해도 일치합니다.

### 그리디가 틀리는 경우

배수 관계가 아닌 체계는 반례가 생깁니다. 단위가 1, 3, 4이고 금액이 6이면 그리디는 `4 + 1 + 1`로 3개를 쓰고, 최적은 `3 + 3`으로 2개입니다.

```js
coins(6, [1, 3, 4]) // 3 (그리디), 실제 최소는 2
```

- 단위가 배수 관계가 아니면 DP로 풉니다. 금액 `W`, 단위 수 `n`이면 O(nW)입니다(자세히는 41편).
- 그리디가 맞는 체계를 정식으로 정규(canonical) 체계라 부르며, 주어진 체계가 정규인지 다항 시간에 검사할 수 있습니다. 문제에서는 배수 관계가 명시되는 경우가 대부분입니다.

**흔한 실수:** 문제의 동전 단위가 배수 관계라는 보장을 확인하지 않고 그리디를 쓰는 것입니다. 단위가 입력으로 주어지면 배수 관계인지 먼저 읽습니다.

## 구간 선택

구간 선택은 구간들을 어떤 기준으로 골라 조건을 만족하게 하는 문제군입니다. 회의실 배정은 "겹치지 않는 최대 개수"였고, 이번에는 "모든 구간을 점으로 덮는 최소 개수"를 봅니다. 두 문제 모두 끝점 오름차순 정렬이 기준입니다.

> 구간 `[l, r]`들이 주어진다. 각 구간이 점 하나 이상을 포함하도록 점을 찍을 때 필요한 점의 최소 개수를 구한다. 점은 구간 경계에도 찍을 수 있다.

가장 먼저 끝나는 구간의 끝점에 점을 찍습니다. 그 점이 포함되는 구간은 모두 해결되므로, 점에 닿지 않는 첫 구간이 나올 때 새 점을 찍습니다.

```js
function minPoints(segs) {
  const s = [...segs].sort((a, b) => a[1] - b[1])
  let last = -Infinity, count = 0
  for (const [l, r] of s) {
    if (l > last) { // 마지막 점이 이 구간에 닿지 않음
      count++
      last = r      // 구간의 끝점에 새 점
    }
  }
  return count
}
minPoints([[1, 4], [2, 6], [5, 8], [7, 10], [9, 12]]) // 3
```

| 구간 | 마지막 점 | 판단 | 점 수 |
|------|-----------|------|-------|
| [1, 4] | 없음 | 4에 점을 찍음 | 1 |
| [2, 6] | 4 | 2 ≤ 4 ≤ 6이라 이미 덮임 | 1 |
| [5, 8] | 4 | 5가 4보다 커서 새 점 8 | 2 |
| [7, 10] | 8 | 이미 덮임 | 2 |
| [9, 12] | 8 | 새 점 12 | 3 |

- 점을 구간의 끝에 찍는 이유는 이후 구간들 중 가장 많은 구간에 닿을 수 있는 가장 오른쪽 위치이기 때문입니다. 끝점 정렬이므로 현재 구간의 끝점보다 오른쪽 점은 현재 구간에 닿지 않습니다.
- 정렬 O(N log N), 훑기 O(N)입니다.
- 이 문제와 회의실 배정은 짝을 이룹니다. 닫힌 구간에서 끝점이 닿는 것도 겹침으로 볼 때, 서로 겹치지 않는 구간의 최대 개수가 모든 구간을 덮는 점의 최소 개수와 같습니다. 위 예에서 `[1, 4]`, `[5, 8]`, `[9, 12]`가 서로 겹치지 않고 점도 3개입니다.

### 다른 기준이 틀리는 이유

겹치지 않는 구간 최대 개수 문제에서 끝점 외의 기준은 반례가 있습니다.

| 기준 | 반례 | 기준의 답 | 실제 최댓값 |
|------|------|-----------|-------------|
| 시작이 가장 빠른 것 | [1, 10], [2, 3], [4, 5] | 1 | 2 |
| 가장 짧은 것 | [1, 5], [4, 7], [6, 10] | 1 | 2 |

시작이 빠른 것은 길게 늘어진 구간 하나가 모든 구간을 막습니다. 가장 짧은 것 `[4, 7]`은 양옆의 두 구간과 모두 겹쳐서 하나만 고르게 됩니다. 두 기준 모두 끝점 정렬이 올바른 답을 줍니다.

**흔한 실수:** 점의 위치를 구간의 시작에 찍는 것입니다. 시작점은 앞쪽으로 치우쳐서 이후 구간에 닿을 가능성이 가장 낮습니다.

## 그리디 정당성

그리디의 정당성은 선택한 기준이 항상 최적해로 이어진다는 증명입니다. 증명이 어려우면 작은 입력에서 완전탐색과 비교해 반례를 찾습니다.

### 교환 논증

교환 논증(exchange argument)은 임의의 최적해를 그리디 선택을 포함하는 형태로 바꿔도 값이 나빠지지 않음을 보이는 증명입니다.

1. 그리디가 첫 번째로 고르는 것을 `g`라고 한다.
2. 임의의 최적해 `O`가 `g`를 포함하지 않는다고 가정한다.
3. `O`의 어떤 원소를 `g`로 바꿔도 조건이 유지되고 값이 나빠지지 않음을 보인다.
4. 그러면 `g`를 포함하는 최적해가 존재한다(그리디 선택 성질).
5. 남은 문제에 같은 논리를 반복한다(최적 부분 구조).

회의실 배정에 적용하면 다음과 같습니다. 끝이 가장 빠른 회의 `g`를 고릅니다. 최적해 `O`에서 끝이 가장 빠른 회의를 `o`라 하면 `g`의 끝이 `o`의 끝보다 늦지 않으므로, `o`를 `g`로 바꿔도 `O`의 나머지 회의와 겹치지 않습니다. 회의 수는 그대로여서 `g`를 포함한 최적해가 있습니다. 이후 `g`가 끝난 시각 이후의 회의들만 남은 문제로 같은 논리를 반복합니다.

### 반례 찾기

증명이 어렵거나 기준이 맞는지 불안하면 작은 입력으로 완전탐색과 그리디를 비교합니다. 두 결과가 다른 입력이 하나라도 나오면 그 기준은 틀립니다.

| 단계 | 내용 |
|------|------|
| 입력 | 값 범위를 작게(N ≤ 6, 값 ≤ 10) 모든 입력 또는 무작위 입력 생성 |
| 비교 | 완전탐색 답과 그리디 답이 같은지 확인(자세히는 16편) |
| 결과 | 다르면 그 입력이 반례. 같으면 수천 개 입력에서도 같은지 확인 |

- 반례가 나오지 않는다고 증명된 것은 아니지만, 틀린 기준은 거의 항상 작은 입력에서 걸립니다(자세히는 80편).
- 반례 후보로 먼저 볼 것: 같은 값(동점), 한 원소가 다른 원소를 모두 포함하는 경우, 길이 0, 원소가 하나뿐인 입력.
- 반례가 나오면 기준을 바꾸거나 DP로 넘어갑니다. 0/1 배낭이 그 예입니다(아래 "분할 가능 배낭").

**흔한 실수:** "일찍 끝나는 것이 좋을 것 같다" 같은 감으로 기준을 정하는 것입니다. 기준 후보를 여럿 세우고 반례로 하나씩 지워 가는 것이 안전합니다.

## 분할 가능 배낭

분할 가능 배낭(fractional knapsack)은 물건을 쪼개서 담을 수 있는 배낭 문제입니다. 용량이 `cap`인 배낭에 무게 `w`, 가치 `v`인 물건들을 담아 가치 합을 최대로 만듭니다. 물건 하나를 일부만 담으면 가치도 그 비율만큼 담습니다.

단위 무게당 가치(`v / w`)가 큰 물건부터 담으면 최적입니다. 같은 무게에서 가치가 가장 큰 것을 먼저 채우는 셈입니다.

```js
function fractional(items, cap) { // items: [{ w, v }, ...]
  const s = [...items].sort((a, b) => b.v * a.w - a.v * b.w)
  let total = 0
  for (const { w, v } of s) {
    if (cap === 0) break
    const take = Math.min(w, cap) // 담을 수 있는 무게
    total += (v * take) / w
    cap -= take
  }
  return total
}
const it = [
  { w: 10, v: 60 }, { w: 20, v: 100 }, { w: 30, v: 120 },
]
fractional(it, 50) // 240
```

용량 50일 때 흐름입니다. 단위 무게당 가치는 6, 5, 4입니다.

| 물건 | 남은 용량 | 담은 무게 | 얻은 가치 |
|------|-----------|-----------|-----------|
| (10, 60) | 50 | 10 | 60 |
| (20, 100) | 40 | 20 | 100 |
| (30, 120) | 20 | 20 | 80 |

- 정렬 비교는 나눗셈 대신 `b.v * a.w - a.v * b.w`로 교차 곱해서 비교합니다. `v / w`는 소수라 오차가 생길 수 있지만 곱은 정수로 정확합니다. 곱이 2^53을 넘을 수 있으면 `BigInt`를 씁니다(자세히는 02편).
- 마지막 물건만 일부를 담고, 앞의 물건은 전부 담습니다. 정렬 O(N log N)입니다.
- 정당성은 교환 논증입니다. 비율이 낮은 물건을 담았는데 비율이 높은 물건이 남아 있다면, 같은 무게만큼 바꾸면 가치가 늘어납니다.

### 0/1 배낭에서는 틀린다

물건을 쪼갤 수 없는 0/1 배낭에 같은 기준을 쓰면 틀립니다. 위 물건에서 용량 50이면 그리디는 (10, 60)과 (20, 100)을 담아 가치 160입니다. 남은 용량 20에는 (30, 120)이 들어가지 않습니다. 최적은 (20, 100)과 (30, 120)을 담은 220입니다. 쪼갤 수 없으면 앞의 선택이 이후 선택의 가능성을 막으므로 그리디 선택 성질이 깨집니다. 0/1 배낭은 DP로 풉니다(자세히는 41편).

**흔한 실수:** 문제가 물건을 쪼갤 수 있는지 읽지 않고 배낭 문제를 그리디로 푸는 것입니다. "쪼갤 수 있다", "일부만 담아도 된다"가 단서입니다.

## 마감 기한이 있는 작업 스케줄링

마감 기한이 있는 작업 스케줄링은 각 작업이 시간 1을 쓰고, 마감 기한 안에 끝내야 이익을 얻을 때 이익의 합을 최대로 하는 문제입니다. 작업은 한 번에 하나만 하고, 시각 1, 2, 3, …에 하나씩 배치합니다.

> 작업 `[마감, 이익]` 목록이 주어진다. 마감이 `d`인 작업은 시각 1부터 `d` 사이의 한 칸에서 수행해야 한다. 이익의 합을 최대로 하는 값을 구한다.

이익이 큰 작업부터 보면서, 각 작업을 자기 마감에 가장 가까운 빈 칸에 넣습니다. 빈 칸이 없으면 버립니다. 마감에 가까운 뒤쪽 칸에 넣는 이유는 이른 칸을 아껴 두어 마감이 빠듯한 다른 작업이 들어갈 자리를 남기기 위해서입니다.

```js
function jobs(list) { // list: [[deadline, profit], ...]
  const maxD = Math.max(...list.map(([d]) => d))
  const slot = Array(maxD + 1).fill(false)
  let total = 0
  const byProfit = [...list].sort((a, b) => b[1] - a[1])
  for (const [d, p] of byProfit) {
    for (let t = d; t >= 1; t--) { // 마감에 가까운 빈 칸
      if (!slot[t]) { slot[t] = true; total += p; break }
    }
  }
  return total
}
jobs([[2, 100], [1, 19], [2, 27], [1, 25], [3, 15]]) // 142
```

이익 내림차순 `100, 27, 25, 19, 15`로 흐름입니다.

| 작업(마감, 이익) | 넣은 칸 | 합 |
|------------------|---------|-----|
| (2, 100) | 2 | 100 |
| (2, 27) | 2는 차 있고 1이 빔 | 127 |
| (1, 25) | 1이 차 있어 버림 | 127 |
| (1, 19) | 버림 | 127 |
| (3, 15) | 3 | 142 |

- 안쪽 반복이 최대 `maxD`번이라서 시간은 O(N log N + N × D)(D는 최대 마감)입니다. D가 크면 느리므로 칸을 분리 집합으로 관리해 빈 칸 찾기를 거의 O(1)로 줄이는 방법이 있습니다(자세히는 51편).
- `Math.max(...list.map(...))`는 요소가 아주 많으면 호출 인수 개수 한계에 걸립니다. 입력이 크면 `reduce`나 반복문으로 최댓값을 구합니다.
- 작업마다 소요 시간이 다르고 끝낼 작업 수를 최대로 하는 변형도 있습니다. 마감 오름차순으로 훑으며 고른 작업을 소요 시간의 최대 힙으로 관리하고, 누적 시간이 마감을 넘으면 가장 오래 걸리는 작업을 버립니다(자세히는 47편).
- 정당성은 교환 논증입니다. 이익이 큰 작업이 어느 칸에든 들어갈 수 있다면, 그 작업 대신 이익이 작은 작업이 들어 있는 최적해에서 둘을 맞바꿔도 마감을 어기지 않고 이익은 늘어납니다.

**흔한 실수:** 작업을 마감 오름차순으로 정렬해 먼저 오는 것부터 넣는 것입니다. 마감이 이르다고 이익이 큰 것은 아닙니다. 이익을 기준으로 고르고, 마감은 넣을 칸을 찾는 데만 씁니다.

## 핵심 정리

- 그리디는 매 단계 가장 좋아 보이는 선택을 하고 되돌리지 않으며, 그리디 선택 성질과 최적 부분 구조가 있어야 정답입니다.
- 선택 기준이 곧 정렬 기준이고 시간은 정렬이 지배하는 O(N log N)입니다. 회의실 배정과 구간 덮기는 끝점 오름차순이며 동점 처리가 답을 바꿉니다.
- 동전 문제의 그리디는 큰 단위가 작은 단위의 배수일 때 맞고, 1, 3, 4원에서 6원 같은 반례가 있으면 DP를 씁니다.
- 분할 가능 배낭은 단위 무게당 가치 내림차순이 최적이지만, 쪼갤 수 없는 0/1 배낭에서는 틀립니다.
- 마감 기한 작업은 이익 내림차순으로 보고 마감에 가까운 빈 칸에 넣습니다.
- 정당성은 교환 논증으로 증명하거나 작은 입력에서 완전탐색과 비교해 반례를 찾아 확인합니다.

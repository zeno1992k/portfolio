## 입력 크기로 알고리즘 판단하기

문제의 입력 크기 상한 N은 쓸 수 있는 알고리즘 후보를 걸러 내는 가장 빠른 단서입니다. 풀이를 떠올리기 전에 N의 상한을 보고 허용 연산 횟수를 계산합니다.

- 이 문서는 어림 기준으로 "1초에 단순 연산 약 10^8번"을 가정합니다. 채점 환경의 실제 처리량은 공식 자료로 확인하지 못했으므로 판정 기준이 아니라 감각용 가정입니다.
- 시간 제한이 2초이면 허용 연산을 2배로, 0.5초이면 절반으로 봅니다.
- 계산 절차는 세 단계입니다. N의 상한을 읽는다, 후보 알고리즘의 복잡도에 상한을 대입한다, 10^8과 비교한다.

예를 들어 N ≤ 2 × 10^5입니다.

| 후보 | 대입 | 연산 횟수 | 판정 |
|------|------|-----------|------|
| O(N²) | (2 × 10^5)² | 4 × 10^10 | 400배 초과, 불가 |
| O(N log N) | 2 × 10^5 × 17.6 | 약 3.5 × 10^6 | 여유 |
| O(N) | 2 × 10^5 | 2 × 10^5 | 여유 |

- 불가 판정이 나면 시간복잡도를 한 단계 낮추는 도구(정렬, 해시, 이분 탐색, 투 포인터 등)를 찾습니다.
- 계수가 큰 코드는 어림보다 느립니다. 안쪽에 `Map`·정렬·문자열 연산이 들어 있으면 한 단계 보수적으로 봅니다.
- 입력 크기에서 알고리즘을 고르는 연습은 77편에서 이어집니다.

## 입력 크기별 허용 시간복잡도 감각

앞의 가정(1초, 10^8)으로 N 상한마다 허용되는 복잡도를 정리하면 다음과 같습니다.

| N 상한 | 허용 복잡도 | 대입한 연산 수 |
|--------|-------------|----------------|
| 10 이하 | O(N!) | 10! = 약 3.6 × 10^6 |
| 20 이하 | O(2^N), O(2^N × N) | 2^20 × 20 = 약 2 × 10^7 |
| 500 이하 | O(N³) | 500³ = 1.25 × 10^8 (한계선) |
| 5000 이하 | O(N²) | 5000² = 2.5 × 10^7 |
| 10^6 이하 | O(N log N) | 10^6 × 20 = 약 2 × 10^7 |
| 10^7 이하 | O(N) | 10^7 |
| 10^9 이상 | O(log N) 또는 O(1) | 수십 번 |

- 표의 연산 수는 N이 그 상한일 때 해당 복잡도의 식에 대입한 값입니다. 10^8 안팎이면 한계선이라서 상수가 크면 시간 초과가 날 수 있습니다.
- N이 10^18 같은 값이면 입력을 훑을 수 없으므로 공식이나 로그 시간 방법이 정답입니다. 이때는 Number 안전 범위(약 9.0 × 10^15)를 넘으므로 BigInt를 씁니다(02편).
- 입력에 N 말고 다른 크기(값의 범위, 쿼리 수)가 있으면 각각 대입해서 본 뒤 가장 비싼 것을 기준으로 합니다.

## 공간복잡도

공간복잡도(space complexity)는 입력 크기 N에 대해 알고리즘이 쓰는 추가 메모리의 증가 속도입니다. 표기는 시간복잡도와 같습니다.

- 보통 입력 자체는 세지 않고 추가로 만든 배열·객체·재귀 스택만 셉니다. 입력까지 합칠 때는 "입력 포함"이라고 밝힙니다.
- 메모리 제한이 있는 문제에서는 시간만큼 중요합니다.

```js
let sum = 0
for (const x of arr) sum += x           // 추가 공간 O(1)

const prefix = new Array(arr.length + 1).fill(0) // O(N)
const dp = Array.from({ length: n }, () =>
  new Array(m).fill(0)) // O(N × M)
```

| 복잡도 | 대표 사례 |
|--------|-----------|
| O(1) | 변수 몇 개로 끝나는 풀이, 제자리 연산 |
| O(N) | `visited` 배열, 누적합 배열, 큐, 1차원 DP |
| O(N²) | 인접 행렬, 2차원 DP, N × N 격자 |

- 시간과 공간은 서로 맞바꿀 수 있습니다. 메모이제이션(40편)이나 `Set`은 공간을 써서 시간을 줄입니다.
- 2차원 DP에서 이전 줄만 필요하면 두 줄만 보관해서 공간을 O(M)으로 줄이는 방법이 있습니다(41편).
- 정확한 메모리 크기를 어림하는 방법은 아래 "값의 메모리 크기 감각"에서 다룹니다.

## 재귀 호출 스택 공간

재귀 호출은 호출이 끝날 때까지 호출 하나당 스택 프레임 하나를 쌓아 둡니다. 따라서 재귀 풀이의 추가 공간은 가장 깊은 호출 깊이에 비례합니다.

```js
function sumTo(n) {
  if (n === 0) return 0
  return n + sumTo(n - 1)   // 깊이 n
}
// 시간 O(N), 스택 공간 O(N)
```

| 재귀 구조 | 깊이 | 스택 공간 |
|-----------|------|-----------|
| 한 칸씩 줄이는 재귀 (sumTo, DFS 경로) | N | O(N) |
| 절반으로 나누는 재귀 (분할 정복, 25편) | log N | O(log N) |
| 반복문으로 바꾼 같은 풀이 | 없음 | O(1) |

- 호출이 두 번 이상 뻗어도(피보나치) 스택에 동시에 쌓이는 것은 한 갈래의 깊이뿐입니다. fib(n)의 스택 공간은 O(N)입니다.
- JavaScript 엔진은 호출 스택 크기가 유한합니다. 넘으면 V8(Chrome, Node.js)에서 `RangeError: Maximum call stack size exceeded`가 발생합니다. 한계 깊이는 환경에 따라 다르고 공식 문서가 고정값을 정하지 않으므로 숫자로 외우지 않습니다.
- 깊이가 N인 재귀(N이 10^5 수준인 DFS, 연결 리스트 길이 순회 등)는 반복문이나 직접 만든 스택으로 바꿉니다(자세히는 22편, 86편).

## 분할 상환 (Amortized)

분할 상환(amortized) 분석은 한 연산이 가끔 비싸더라도 연산을 연속해서 수행한 총비용을 연산 횟수로 나눠 평균을 보는 방법입니다. 입력의 확률 가정 없이 최악의 연산 순서에 대해 성립하는 보장이라서, 확률 평균인 평균 경우(13편)와 다릅니다.

첫째 예는 동적 배열의 끝 추가입니다. 용량이 가득 차면 두 배 크기로 새로 만들어 복사한다고 모델링하면, N번 추가할 때 복사 횟수는 1 + 2 + 4 + … 로 2N을 넘지 않습니다. 따라서 추가 한 번당 평균 O(1)입니다. 실제 엔진의 증설 방식은 명세에 정해져 있지 않으므로 이 모델은 개념 설명이며, 코딩테스트에서는 `push`를 O(1)로 씁니다.

둘째 예는 반복문 안의 `while`입니다.

```js
const stack = []
for (const x of arr) {
  while (stack.length > 0 && stack[stack.length - 1] > x) {
    stack.pop()
  }
  stack.push(x)
}
```

- `while`은 한 번에 N번 돌 수 있지만 모든 원소는 한 번 들어가고 최대 한 번 나옵니다. 전체 `pop`은 N번을 넘지 않아서 합계가 O(N)입니다.
- 이 논리는 Monotonic Stack(32편), 투 포인터(30편), 슬라이딩 윈도우(31편)의 복잡도 증명에 그대로 쓰입니다.

**흔한 실수:** 바깥 반복 N번, 안쪽 `while`이 최악 N번이라서 O(N²)이라고 판단하는 것입니다. 안쪽 반복이 공유하는 자원(스택 원소, 포인터 이동 거리)의 총량이 N으로 한정되면 전체는 O(N)입니다.

## 자료구조별 연산 복잡도

자주 쓰는 JavaScript 자료구조의 연산 비용입니다. 반복문 안에서 부르면 이 값을 곱해서 셉니다.

| 자료구조 | 연산 | 복잡도 |
|----------|------|--------|
| Array | 인덱스 읽기·쓰기 | O(1) |
| Array | `push`, `pop` (끝) | O(1) (분할 상환) |
| Array | `shift`, `unshift` (앞) | O(N) |
| Array | `splice`로 중간 삽입·삭제 | O(N) |
| Array | `includes`, `indexOf`, `find` | O(N) |
| Array | `slice`, `concat`, 스프레드 | O(복사하는 길이) |
| Array | `sort` | O(N log N)으로 가정 |
| Map, Set | `get`, `set`, `has`, `delete` | 평균 O(1)로 가정 |
| Map, Set | 전체 순회 | O(N) |

- `sort`의 복잡도는 명세가 보장하지 않고 구현에 따릅니다. 안정 정렬은 ES2019부터 명세가 요구합니다(26편).
- `Map`의 명세는 평균 접근 시간이 요소 수에 대해 준선형이면 된다고만 요구합니다. MDN은 내부 구현이 해시 테이블(조회 O(1))일 수도, 검색 트리(조회 O(log N))일 수도 있다고 설명합니다. 코딩테스트에서는 평균 O(1)로 어림하며 최악의 경우는 더 느릴 수 있습니다(10편).
- Heap, Union-Find, 세그먼트 트리 같은 자료구조의 연산 비용은 각 편(46편, 51편, 62편)에서 다룹니다.

## Array.shift와 unshift의 비용

`shift`는 첫 요소를 빼고 나머지를 모두 왼쪽으로 한 칸 옮기는 연산입니다(MDN: "shifts all values to the left by 1"). `unshift`는 기존 요소의 인덱스를 모두 오른쪽으로 옮기고 앞에 넣습니다. 길이 N인 배열이면 N개를 옮기는 연산이므로 개념적으로 O(N)입니다.

- 엔진이 내부적으로 최적화할 수 있지만 문서가 그 비용을 보장하지 않습니다. 코딩테스트에서는 O(N)으로 계산합니다.
- 한 번이 느린 것이 아니라 반복문 안에서 N번 부르는 구조가 문제입니다. N번 호출하면 총 O(N²)입니다.

큐를 `shift`로 구현하면 이 문제가 생깁니다. 값을 지우지 않고 읽는 위치만 옮기는 head 인덱스 방식이 O(N)입니다.

```js
// ❌ 매번 O(N): 전체 O(N²)
while (queue.length > 0) {
  const x = queue.shift()
}

// ✅ 위치만 이동: 전체 O(N)
let head = 0
while (head < queue.length) {
  const x = queue[head++]
}
```

- 앞쪽에 계속 넣어야 하면 `unshift`를 반복하지 말고 뒤에 `push`한 뒤 마지막에 `reverse`를 한 번 합니다.
- 큐와 덱의 구현은 20편에서 자세히 다룹니다.

## 값의 메모리 크기 감각

메모리 제한이 있는 문제에서는 자료를 얼마나 만들 수 있는지 크기를 어림해야 합니다.

JavaScript의 `Number`는 IEEE 754 배정밀도 64비트 값입니다(8바이트). TypedArray는 요소 하나의 바이트 수가 정해져 있어서 메모리를 정확히 계산할 수 있습니다.

| TypedArray | 값 범위 | 요소 크기 |
|------------|---------|-----------|
| `Uint8Array` | 0–255 | 1바이트 |
| `Int16Array` | −32768–32767 | 2바이트 |
| `Int32Array` | 약 ±2.1 × 10^9 | 4바이트 |
| `Float64Array` | 배정밀도 실수 | 8바이트 |
| `BigInt64Array` | −2^63–2^63−1 | 8바이트 |

- 크기는 길이 × 요소 바이트입니다(MB는 10^6바이트로 어림). 10^6개면 `Uint8Array` 1MB, `Int32Array` 4MB, `Float64Array` 8MB입니다. 10^7개면 각각 10MB, 40MB, 80MB입니다.
- 새로 만든 TypedArray는 0으로 채워져 있어서 `fill(0)`이 필요 없습니다.

```js
const dist = new Int32Array(1000000)   // 4000000바이트
dist[0]                                // 0
const visited = new Uint8Array(n + 1)  // 방문 여부는 1바이트
```

- 일반 배열과 객체가 실제로 차지하는 바이트 수는 엔진 구현에 따라 다르고 공식 문서에 정해져 있지 않습니다. 정확한 값을 계산할 수 없고, 값 하나(8바이트)보다 크다는 점만 확실합니다. 특히 객체는 요소 하나당 프로퍼티·내부 관리 비용이 더 붙습니다.
- 그래서 메모리가 빠듯하면 TypedArray로 바꾸는 것이 상한을 계산할 수 있는 방법입니다. 1000 × 1000 격자의 `Int32Array`는 정확히 4MB입니다.
- 힙 크기는 Node.js에서 `--max-old-space-size`(MiB 단위)로 바꿀 수 있습니다. 채점 환경이 이 옵션을 주는지는 확인할 수 없으므로 코드가 정할 수 없는 값으로 봅니다.
- 메모리 제한에서 허용 크기를 거꾸로 계산하는 방법은 15편에서 다룹니다.

## 변수가 둘 이상인 복잡도

입력이 서로 독립인 크기를 둘 이상 가지면(배열 두 개, 행과 열, 정점과 간선) 변수를 하나로 합치지 않고 따로 씁니다.

| 구조 | 복잡도 | 설명 |
|------|--------|------|
| 순차: A를 돌고 B를 돈다 | O(N + M) | 합 |
| 중첩: A 안에서 B를 돈다 | O(N × M) | 곱 |
| 격자 R × C를 모두 훑기 | O(R × C) | 칸 수에 비례 |
| 정점 V, 간선 E 그래프 탐색 | O(V + E) | 35편 |
| 길이 L인 문자열 N개를 정렬 | O(N log N × L) | 비교 한 번이 O(L) |

두 배열의 공통 원소를 찾는 두 방법으로 차이를 봅니다.

```js
// 두 배열의 공통 원소: a는 N개, b는 M개
a.filter((x) => b.includes(x))      // O(N × M)

const set = new Set(b)              // O(M)
a.filter((x) => set.has(x))         // O(N)
// 합계 O(N + M)
```

- N × M이 곱이어도 N과 M 중 하나가 상수이면 한 변수의 식이 됩니다. N × 4이면 O(N)입니다.
- 어느 쪽이 지배하는지 알 수 있으면 간단히 쓸 수 있지만, 알 수 없으면 둘 다 남깁니다. O(N + M)에서 둘 중 큰 것만 남기는 것은 N과 M이 같은 규모라고 확실할 때만 허용됩니다.
- N = M = 10^5이면 O(N × M)은 10^10이어서 불가능하고, O(N + M)은 2 × 10^5여서 여유 있습니다.

**흔한 실수:** 배열 두 개를 모두 N으로 두고 O(N²)이라고 쓰는 것입니다. 제한이 다를 수 있으니(N ≤ 10^5, M ≤ 100이면 O(N × M) = 10^7로 가능) 변수마다 상한을 따로 대입합니다.

## 핵심 정리

- N 상한을 허용 연산 횟수(1초에 약 10^8 어림)와 비교해 알고리즘을 걸러 냅니다. 이 수치는 감각용 가정입니다.
- 공간복잡도는 추가 메모리의 증가 속도입니다. 재귀는 깊이만큼 스택 공간을 씁니다.
- 분할 상환은 연산 연속 수행의 총비용 평균입니다. 안쪽 `while`이 공유 자원 총량 N으로 한정되면 전체는 O(N)입니다.
- 배열 앞쪽 연산(`shift`, `unshift`)과 중간 `splice`, `includes`는 O(N)입니다. 큐는 head 인덱스로 구현합니다.
- 메모리는 TypedArray의 요소 크기(1·2·4·8바이트)로만 정확히 계산할 수 있습니다. 독립 변수는 O(N + M), O(N × M)처럼 따로 씁니다.
